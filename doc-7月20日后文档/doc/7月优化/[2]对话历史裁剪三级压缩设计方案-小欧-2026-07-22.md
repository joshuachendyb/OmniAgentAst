# 对话历史裁剪三级压缩设计方案

> **编写人**: 小欧
> **创建时间**: 2026-07-22 18:00:00
> **版本**: v1.0

---

## 一、设计目标

**不设轮次上限假设**。无论 5 轮、50 轮还是 200 轮，LLM 都能看到完整的决策链——旧轮次的工具结果被摘要替代，但"做了什么→为什么→结论"保留。

---

## 二、借鉴与创新

从 OpenCode / Hermes 优中选优，再加我们自己的方法：

### 2.1 借鉴

| 借鉴自 | 机制 | 为什么好 |
|--------|------|---------|
| **OpenCode Prune** | 旧 tool output → 占位符，不删消息只替内容 | 不破坏 FC 配对结构 |
| **Hermes Pass2** | 工具感知摘要（工具名+路径+行数+耗时） | 一行说完关键信息 |
| **Hermes _previous_summary** | 上一次摘要结果作为迭代锚点 | 冷区可以累积压缩 |
| **OpenCode tail_turns** | 保尾用轮数而不是消息数 | 语义清晰，FC 对整轮保留 |

### 2.2 我们自己创造的方法

| 创新 | 说明 |
|------|------|
| **三级压缩（T1/T2/T3）** | 按占用窗口比例逐级加重，轻→中→重，不是一刀切 |
| **T2 冷区合并** | 最早整批 FC 对合并为一句话概要，替代 LLM 摘要（零成本） |
| **工具摘要模板体系** | 基于我们自己的工具注册名，比 Hermes 更精确（readtext/listdir/grep/find/fetchpage 等各有专属模板） |
| **三步递进** | 替内容→并轮次→删消息，信息丢失逐级增加，给 LLM 最大能见度 |

## 三、核心概念

### 3.1 消息的三个层级

```
                   时间轴 →
┌──────────────┬──────────────────┬────────────────┐
│  Cold Zone   │    Warm Zone     │   Hot Zone     │
│  (最早 N轮)   │   (中间区)       │  (最近 N 轮)   │
│              │                  │                │
│  被合并为     │  tool obs 被摘   │  FC 对完整     │
│  概要句      │  要, asst 完整   │  不动          │
└──────────────┴──────────────────┴────────────────┘
```

| 区域 | 处理方式 | 信息保留度 |
|------|---------|-----------|
| **Hot** | 完整保留，不动 | 100% |
| **Warm** | tool content → 一行摘要，assistant 完整 | 决策 100%，执行细节摘要 |
| **Cold** | 整批 FC 对 → 一行的概要 | 关键决策点保留，细节丢失 |

### 3.2 触发与行为矩阵

| 占用窗口 | 触发级别 | Hot 区 | Warm 区 | Cold 区 |
|---------|---------|--------|---------|---------|
| < 50% | — | 完整 | 完整 | 完整 |
| 50%~75% | **T1 工具摘要** | 完整 | obs→摘要 | obs→摘要 |
| 75%~90% | **T2 冷区合并** | 完整 | obs→摘要 | 合并为概要 |
| 90%~95% | T1+T2+**加深压缩** | 完整 | obs→摘要+精简 | 合并 |
| > 95% | **T3 紧急裁剪** | KEEP_TAIL 轮完整 | 移除最早直到 < 50% | — |

## 四、T1 工具摘要（50%~75% 触发）

### 4.1 触发条件

```
粗估 tokens > MAX_CONTEXT_TOKENS × 0.50
```

### 4.2 做法

扫描 Warm + Cold 区的所有 tool 消息，将其 content 替换为工具感知一行摘要。

保留：
- tool_call_id（FC 配对不破坏）
- role="tool"（消息结构不变）
- content → 替换为摘要行

不删消息。

### 4.3 工具摘要模板

基于我们的工具注册名（`tool_constants.py` 中 `tool_descriptions`），每个工具有自己的摘要模板：

| 工具 | 模板 | 示例 |
|------|------|------|
| **readtext** | `[readtext] {path} ({line_count}行)` | `[readtext] src/config.py (120行)` |
| **listdir** | `[listdir] {path} ({file_count}项)` | `[listdir] backend/app/ (48项)` |
| **grep** | `[grep] '{pattern}' in {path} ({match_count}个匹配)` | `[grep] 'timeout' in src/ (3个匹配)` |
| **find** | `[find] {path} → {result_count}个文件` | `[find] backend/ → 15个py文件` |
| **fetchpage** | `[fetch] {url} ({content_len}字符)` | `[fetch] example.com (4,200字符)` |
| **shell** | `[shell] {command} exit={code}` | `[shell] pytest tests/ exit=0` |
| **read_docx** | `[docx] {path} ({para_count}段)` | `[docx] doc/report.docx (85段)` |
| **read_pdf** | `[pdf] {path} page={n} ({char_count}字符)` | `[pdf] manual.pdf page=3 (2,100字符)` |
| **default** | `[{tool_name}] {path_or_summary}` | `[read_xlsx] data.xlsx (10行×5列)` |

模板数据的来源：从已有 `llm_data["action"]["params"]` 和 `data` 中提取参数，不进新字段。

**注意**: 如果压缩轮次超过 3 次（即同块 warm 区被反复压缩），后续不再重复压缩，避免反复替换同一段。

### 4.4 效果估算

- 原本 1000 行 × 100 字符的 readtext obs（~100K chars≈25K tokens）
- 压缩后 `[readtext] src/config.py (1000行)`（~45 chars）
- **压缩比 > 99%**

## 五、T2 冷区合并（75%~90% 触发）

### 5.1 触发条件

```
粗估 tokens > MAX_CONTEXT_TOKENS × 0.75
且已有 T1 压缩（至少过一次）
```

### 5.2 做法

取 Cold 区（最早 30% 的 FC 对），将其替换为概要句：

```
[此区域为第 1~8 轮的历史概要: 完成了项目结构分析(config.py读取→15个工具文件查找→3个测试运行→README文档确认)]
```

### 5.3 概要句的生成

纯字符串拼接，不调 LLM：
1. 从 Cold 区的 assistant 消息提取 `action`（tool 调用名）
2. 按顺序拼接为 `工具A→工具B→工具C` 链
3. 限制在 200 字符以内

```
# 冷区原始: readtext→grep→shell→readtext→listdir→shell→grep
# 合并概要: 完成了项目结构分析(config.py→timeout搜索→测试运行)
```

### 5.4 对 _previous_summary 的迭代

如果 Cold 区已经有过一次概要，下次触发时：
- 新 Cold 区 = 上次概要 + 新被冷区的轮次
- 合并为新的概要

```
第1次压缩: [概要: 完成项目结构分析]
  ↓ (又过了15轮)
第2次压缩: [概要: 完成项目结构分析 → 配置文件修改 → 测试用例编写]
```

## 六、T3 紧急裁剪（> 95% 触发）

### 6.1 触发条件

```
粗估 tokens > MAX_CONTEXT_TOKENS × 0.95
```

### 6.2 做法

1. 保尾 `KEEP_TAIL_ROUNDS=5` 轮完整 FC 对
2. Cold + Warm 区已全部被 T1/T2 压缩
3. 从最旧往最新删完整的 FC 对，直到 total < `MAX_CONTEXT_TOKENS × 0.50`
4. `_rebuild_and_validate` → `_trim_fc_pairs` 清理孤儿

**这层会丢信息**——但 95% 触发意味着窗口快爆了，必须丢。T1+T2 保证了 95% 之前信息都是保留的（只是摘要化），T3 是最后兜底。

## 七、关键常量

| 常量 | 值 | 说明 |
|------|-----|------|
| `MAX_CONTEXT_TOKENS` | 200000 | 窗口上限（配置可覆盖） |
| `CHARS_PER_TOKEN` | 4 | chars→token 换算 |
| `TRIGGER_T1_RATIO` | 0.50 | T1 工具摘要触发比例 |
| `TRIGGER_T2_RATIO` | 0.75 | T2 冷区合并触发比例 |
| `TRIGGER_T3_RATIO` | 0.95 | T3 紧急裁剪触发比例 |
| `TRIM_TARGET_RATIO` | 0.50 | T3 裁剪目标比例 |
| `KEEP_TAIL_ROUNDS` | 5 | 保尾轮数 |
| `COLD_ZONE_RATIO` | 0.30 | Cold 区占非 Hot 轮次的比例 |
| `SUMMARY_MAX_CHARS` | 200 | 概要句最大字符数 |
| `COMPRESS_RETRY_LIMIT` | 3 | 同一 block 最大压缩次数 |

## 八、数据流

```
trim_history() 入口
  │
  ├── msg_count ≤ 5 → return
  │
  ├── 估算 total = _estimate_tokens()
  │
  ├── [T1] total > T1_RATIO × MAX_CONTEXT_TOKENS ?
  │   └── 扫描 Warm+Cold, 对每个未压缩的 tool obs 做工具摘要
  │   └── 标记已压缩轮的 z_compressed_round = T1
  │   └── 重算 total
  │
  ├── [T2] total > T2_RATIO × MAX_CONTEXT_TOKENS 且 T1 已执行?
  │   └── 取最早 30% FC 对 → 合并为概要句
  │   └── 替换整批为一消息 z_zone_summary
  │   └── 重算 total
  │
  ├── [T2 deepen] total > T2_RATIO 且尚有未压缩的 Warm 轮?
  │   └── Warm 区加深压缩（精简多余空格/缩短路径）
  │   └── 重算 total
  │
  ├── [T3] total > T3_RATIO × MAX_CONTEXT_TOKENS ?
  │   └── 保尾 KEEP_TAIL_ROUNDS 轮
  │   └── 从最旧删除 FC 对直到 total < TRIM_TARGET_RATIO
  │
  └── _rebuild_and_validate → _trim_fc_pairs
```

## 九、与 OpenCode / Hermes 对比

| 维度 | OpenCode | Hermes | 本方案 |
|------|----------|--------|--------|
| **tool obs 压缩** | ✅ Prune（占位符） | ✅ Pass2（工具摘要） | ✅ **工具摘要模板** |
| **去重** | ❌ | ✅ Pass1 MD5 | 🔲 预留 |
| **tool_call 参数截断** | ❌ | ✅ Pass3 | 🔲 预留 |
| **LLM 摘要** | ✅ Process | ✅ _generate_summary | ❌ **零 LLM 成本** |
| **冷区处理** | Select 区分 head/tail | 同左 | ✅ **冷区合并（新）** |
| **保尾单位** | tail_turns=2（轮数） | protect_last_n=20（消息数） | **KEEP_TAIL_ROUNDS=5（轮数）** |
| **防抖动** | ❌ | ✅ 连续无效跳过 | ✅ **同一 block 最多压缩 3 次** |
| **溢出回退** | ✅ needsCompaction | ✅ 413+overflow | 🔲 预留 |
| **消息数安全网** | ❌ | ✅ 400 条 | 🔲 预留（可加） |
| **手工触发** | ✅ /compact | ✅ /compress | 🔲 预留 |
