## 二、背景与目标

### 2.1 历史遗留问题

在 v0.18.0 ~ v0.18.11 的「全量扁平化重构」中，日志相关代码长期处于分裂状态：

1. **两套日志入口混用**：既有 `logging.getLogger(__name__)`（标准库直连），又有 `app.utils.log_config.setup_logger()`（自研封装）。不同模块调用姿势不一，导致 handler 重复添加、日志级别错乱。
2. **Windows 文件锁竞争**：多个 logger 各自创建独立的 `RotatingFileHandler` 指向同一个日志文件。在 Windows 平台，日志轮转（`doRollover`）触发 `os.rename` 时，另一个仍打开的 handler 句柄会锁住文件，引发 `PermissionError`，且往往在 `handleError` 中死循环打印，污染 stderr。
3. **console 截断误伤前缀**：早期 `_TruncateConsoleFormatter` 对整个格式化后的字符串（含 `时间 - 级别 - 文件名 - 消息` 前缀）统一截断，导致关键前缀（文件名/行号）被砍，排查问题时无法定位来源。

### 2.2 本版本目标

| 目标 | 说明 | 对应变更 |

| 统一入口 | 删除 `app.utils.log_config` 体系，所有使用方改为 `from app.logger import logger` | 新建模块 + 114 文件 import 改写 |
| 消除锁竞争 | 全进程只保留一个文件 handler（单例共享） | SafeRotatingFileHandler 单例 |
| 修复截断 | console 截断只作用于消息体，不动前缀 | `_TruncateConsoleFormatter` 重写 |
| 修复副作用 | observation_formatter 不再 `pop` 原始 data | `pop` → `get` + 长度截断 + None 守卫 |

### 3.3 SafeRotatingFileHandler 单例共享消除 Windows 文件锁竞争

**提交**：`44c286167` fix: app/logger/{config,setup_logger} SafeRotatingFileHandler单例共享消除Windows文件锁竞争+注释补充 — 小欧-2026-07-11

**根因分析**：

> 旧实现中，每个 `setup_logger(name)` 调用都会为各自 logger 新建一个 `RotatingFileHandler` 指向同一文件。Windows 下 `RotatingFileHandler.doRollover()` 执行 `os.rename(base, backup)` 时，其他仍持有文件句柄的 handler 会锁住原文件，导致 rename 失败抛出 `PermissionError`。异常在 `handleError` 内被再次记录，又触发轮转，形成 stderr 噪声死循环。

**修复手段**：全进程只创建 **一个** `SafeRotatingFileHandler` 实例，所有 logger 共享同一文件描述符。

**`setup_logger.py` 单例实现（真实代码）**：

```python
# 关键：整个进程只创建一个 SafeRotatingFileHandler，所有 logger 共用
# 根因：7个 handler 分别写同一文件 → Windows rename 被其他句柄锁住
# 修复：1 handler → 1 文件描述符 → 0 竞争
# — 小欧 2026-07-11
_FILE_HANDLER: Optional[SafeRotatingFileHandler] = None

def _get_shared_handler() -> SafeRotatingFileHandler:
    """获取全局唯一的文件 handler — 小欧 2026-07-11"""
    global _FILE_HANDLER
    if _FILE_HANDLER is None:
        from app.logger.config import _get_log_file_path
        log_file = _get_log_file_path()
        _FILE_HANDLER = SafeRotatingFileHandler(
            log_file,
            maxBytes=LogConfig.get_max_bytes(),
            backupCount=LogConfig.get_backup_count(),
            encoding='utf-8',
        )
    return _FILE_HANDLER
```

`setup_logger()` 内部对该共享 handler 仅做 `setFormatter` / `setLevel`，**绝不重复 addHandler 到已初始化的 logger**（通过 `if logger.handlers: return logger` 守卫）：

```python
def setup_logger(name: str) -> logging.Logger:
    logger = logging.getLogger(name)
    if logger.handlers:
        return logger
    ...
    file_handler = _get_shared_handler()      # 全局共享，单例
    console_handler = logging.StreamHandler()  # 每 logger 独立
    logger.addHandler(file_handler)
    logger.addHandler(console_handler)
    logger.propagate = False
    return logger
```

**`config.py` 中 `SafeRotatingFileHandler` 增强（真实代码）**：

```python
class SafeRotatingFileHandler(logging.handlers.RotatingFileHandler):
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        self._current_date = now_str('%Y-%m-%d')

    def doRollover(self):
        """重写：super 失败后恢复流，防止流永久损坏 — 小欧 2026-07-11"""
        try:
            super().doRollover()
        except OSError:
            self.stream = self._open()

    def emit(self, record):
        try:
            self._check_and_rotate_by_date()
        except Exception:
            self.handleError(record)
        super().emit(record)
```

要点：
- **日期轮转**：`_check_and_rotate_by_date()` 检测日期变更后切换 `baseFilename` 并 reopen，不新建 handler；
- **大小轮转**：`doRollover()` 包裹 `OSError` 保护，失败则重新 `_open()` 恢复流，杜绝流永久损坏；
- **单例保证**：`setup_logger` 通过模块级 `_FILE_HANDLER` 全局变量确保全进程唯一文件 handler。

**影响**：彻底消除 Windows 下日志轮转的 `PermissionError` 噪声；多 logger（如 `react_cycle`、`base_service` 会 `logger.info` 写日志）共享同一句柄后不再相互锁文件。

### 3.4 console 截断只截消息体不截前缀

**提交**：`84deab50f` fix: setup_logger.py console截断只截消息体不截前缀 — 小欧-2026-07-11

**Before（缺陷实现）**：

```python
class _TruncateConsoleFormatter(logging.Formatter):
    """console 日志截断 Formatter — 写文件完整，console 只显示前 100 字符"""
    def format(self, record):
        msg = super().format(record)
        if len(msg) > 100:
            msg = msg[:100] + f"...(截断{len(msg)-100}字符)"
        return msg
```

**问题**：`super().format(record)` 已将 `时间 - 级别 - 文件名 - 消息` 拼成完整字符串，再 `msg[:100]` 会把前缀（尤其是 `文件名:行号`）一并砍掉，导致 console 上完全看不到日志来自哪个文件哪一行。

**After（修复实现，真实代码）**：

```python
class _TruncateConsoleFormatter(logging.Formatter):
    """console 日志截断 Formatter — 只截断消息体%(message)s，前缀不动 — 小欧 2026-07-11"""
    def format(self, record):
        raw = record.getMessage()
        if len(raw) > 100:
            record.msg = raw[:120] + f"...(截断{len(raw)-120}字符)"
            record.args = None
        return super().format(record)
```

**对比分析**：

| 维度 | Before | After |
|------|--------|-------|
| 截断对象 | 完整格式化字符串（含前缀） | 仅 `record.getMessage()`（消息体） |
| 前缀 `文件名:行号` | 被截断丢失 | 保留完整 |
| 实现路径 | 先 format 再切 | 先改写 `record.msg` 再 format |
| 参数副作用 | 无 | 截断后 `record.args=None` 避免重复展开 |

**影响**：console 上长消息（如 LLM 响应片段）被截断，但 `时间/级别/文件名:行号` 前缀始终完整，排障时一眼定位来源。文件 handler 不受影响，仍写全量。

### 3.6 P6-01 文件不存在断言含工具结果检查

## 四、关键技术点

### 4.1 单例 Handler 消除 Windows 文件锁竞争

核心思想：**handler 是资源（文件描述符），不应按 logger 数量倍增**。标准库 `logging` 的设计允许多个 logger 挂多个 handler，但当多个 handler 指向同一物理文件并各自独立轮转时，Windows 的强制文件锁（不同于 Linux 的 advisory lock）会直接导致 `os.rename` 失败。

本版本用模块级全局变量 `_FILE_HANDLER` + `if logger.handlers: return` 双保险，确保：
- 文件 handler 进程内唯一 → 轮转时只有一把锁在动；
- 轮转失败有 `OSError` 兜底 reopen，流不会永久损坏；
- 日期轮转复用同一 handler 实例，仅切换 `baseFilename` 并 reopen。

### 4.2 import 批量替换策略

- 旧路径 `app.utils.logger` / `app.utils.log_config.*` 全量 → `app.logger.*`；
- 采用「脚本替换 + AST 语法自检 + 全量测试」三段式，避免漏改/错改；
- 旧模块 `app.utils.log_config/`（4 文件，372 行）与 `app.utils/logger.py`（29 行）在 `e52806e27` 中整体删除，无残留（仅 `file_path_checker.py` 仍用 `logging.getLogger(__name__)` 标准库直连，属合规用法，见第六章）。

## 六、风险与遗留

### 6.1 残留的 `logging.getLogger` 标准库直连

经 Grep 全仓扫描（`backend/**/*.py`），仅 3 处 `logging.getLogger`：

| 文件 | 行 | 说明 | 风险 |
|------|----|------|------|
| `app/tools/validate/file_path_checker.py` | 15 | `logger = logging.getLogger(__name__)` | **低风险**：该 logger 未挂任何 handler，日志会走 root 默认（可能不输出），但不影响文件锁竞争（不写文件） |
| `app/logger/setup_logger.py` | 59 | `logger = logging.getLogger(name)` | 设计内用法，单例 handler 由此管理 |
| `app/main.py` | 37 | `logging.getLogger("uvicorn.access").setLevel(logging.WARNING)` | uvicorn 自带 handler，与本项目文件 handler 不同文件，无竞争 |

**结论**：`file_path_checker.py` 的直连虽不引发锁竞争，但与其余模块统一走 `app.logger` 的规范不一致，建议在后续版本统一改为 `from app.logger import logger`，提升日志可观测性一致性。

### 6.2 单例 handler 与多进程

当前单例仅保证「单进程内唯一」。若未来以多进程（gunicorn/fork）部署，每个进程各自持有一份 `_FILE_HANDLER`，Windows 下仍可能因多进程写同一文件产生竞争。本版本未覆盖该场景（当前部署为单进程 uvicorn），记为遗留项。

### 6.3 `record.args = None` 的潜在副作用

`_TruncateConsoleFormatter` 截断时设 `record.args = None`。若该 `record` 被多个 formatter（文件 + console）共享，`super().format(record)` 在文件 handler 处也会因 `args=None` 而忽略占位符。当前实现中文件 handler 与 console handler 共用同一 `formatter` 实例但 `format` 各自调用，且 `record.msg` 已被改写、args 置空，文件 handler 同样只写截断后的消息体——**文件日志同步被截断**。这属于潜在非预期行为，建议后续将截断限制在 console handler 专用的 formatter 实例上，避免污染文件日志。
