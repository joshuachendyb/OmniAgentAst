## 二、背景与目标

### 2.1 问题：状态设置分散（「状态设置散点」）

重构前，Agent 状态 `agent.status` 的赋值散落在 5+ 个模块：

- `react_cycle.py`：循环内 `agent.set_failed / set_cancelled / agent.status = EXECUTING`
- `action_handler.py`：`set_failed`（tool_name 空、安全检查 blocked/user_rejected）
- `answer_handler.py`：`set_failed`（空内容）/ `set_completed`（正常完成）
- `step_emitter.py`：`exit_with_error` 内 `self.agent.set_failed`
- `run_sse_stream.py`：`agent.set_cancelled / set_failed`
- `initialize_run_state.py`：`agent.status = THINKING`

任何一处改动都可能破坏状态机的合法性，且无集中校验。— 小欧 2026-07-12

### 2.2 问题：handler 越权设状态（SRP 违反）

Handler 本应只负责「把 LLM 解析结果转成 Step 流」（业务逻辑），却同时承担了「终态决策」职责。这造成两类 bug：

1. 同一错误路径在 handler 内 `set_failed`，而编排层又在 `finally` 补 `set_failed`，重复且易触发非法转换异常。
2. `answer_handler` 空内容走 `FinalStep(response="")` + `set_failed`，但 `FinalStep` 本意是成功，语义混淆，前端空响应守卫难以区分。

### 2.3 问题：SSE 映射混乱

`run_sse_stream` 的 `agent.status → end_type` 映射缺少 `SUSPENDED`，且多处 `agent.set_*` 调用绕过统一入口，导致新引入的 SUSPENDED 状态在 SSE 层无归宿。

### 2.4 目标

1. 建立**唯一**可改动 `agent.status` 的入口（`status_table.py` 纯函数 + 转换表校验）。
2. Handler 只 `yield Step`，编排层从 event type 推断终态 → 调 `status_table`。
3. EXECUTING/THINKING 精确映射「调 LLM / 跑工具」两个真实动作时机。
4. SSE 层完整覆盖 SUSPENDED，error 分类补齐 httpx 网络/超时。— 小欧 2026-07-12

## 三、逐项变更详解

### 3.1 Agent 状态集中管理重构 v2（commit 61acbd104）

#### 3.1.1 新建 status_table.py

新建 `backend/app/services/agent/core_agent/status_table.py`（注：后续 v0.18 扁平化已上移至 `app/services/agent/status_table.py`；当前 `AgentStatus` 枚举也已并入该文件，原 `types/agent_status.py` 仅保留 3 行增量）。核心设计：

```python
# 当前文件结构（节选，status_table.py 第18-87行）— 小欧 2026-07-12
class AgentStatus(Enum):
    IDLE = "idle"
    THINKING = "thinking"
    EXECUTING = "executing"
    COMPLETED = "completed"
    FAILED = "failed"
    CANCELLED = "cancelled"
    RETRYING = "retrying"
    SUSPENDED = "suspended"   # 真挂起

_TRANSITIONS = {
    AgentStatus.IDLE: {THINKING, CANCELLED, FAILED},
    AgentStatus.THINKING: {EXECUTING, COMPLETED, FAILED, CANCELLED, RETRYING, SUSPENDED},
    AgentStatus.EXECUTING: {THINKING, COMPLETED, FAILED, CANCELLED, RETRYING, SUSPENDED},
    AgentStatus.RETRYING: {THINKING, FAILED, CANCELLED},
    AgentStatus.SUSPENDED: {THINKING, EXECUTING, RETRYING, FAILED, CANCELLED},
    AgentStatus.CANCELLED: set(),   # 终止态不可转换
    AgentStatus.COMPLETED: set(),
    AgentStatus.FAILED: set(),
}
```

**set_status 带锁 + 合法性校验 + 双写 prompt log**：

```python
_status_lock = threading.RLock()

@_synchronized
def set_status(agent, new_status, reason=""):
    if not _validate_transition(agent.status, new_status):
        raise ValueError(f"非法转换: {agent.status} → {new_status}")
    old_status = agent.status
    agent.status = new_status
    logger.info(f"[Agent] {old_status} → {new_status}: {reason}")
    try:
        get_prompt_logger().log_status(str(old_status), str(new_status), reason)
    except Exception:
        pass
```

> KISS-DIRECT：转换表只保留代码中实际存在的路径，无死代码；用纯函数而非类，编排层与 handler 共享同一入口。— 小欧 2026-07-12

#### 3.1.2 新增 SUSPENDED 转换条目

SUSPENDED 在 v0.17.10 已作为「真挂起」语义引入（区别于 RETRYING 的错误重试，对应「用户暂停任务 / HITL 等用户确认」）。本版本正式把它接入 `_TRANSITIONS`：

- `THINKING/EXECUTING → SUSPENDED`：挂起。
- `SUSPENDED → THINKING/EXECUTING/RETRYING/FAILED/CANCELLED`：恢复或终止。

这补齐了状态机缺失的一支（背景 2.3 提到的 SSE 映射缺失问题在 3.3 解决）。— 小欧 2026-07-12

#### 3.1.3 EXECUTING / THINKING 精确状态循环

重构前 `run_react_cycle` 一进循环就把 `agent.status = EXECUTING`，与「THINKING=调 LLM」语义不符。重构后：

- **THINKING 设在循环尾部**（每次 single_step 完成后，若仍是 EXECUTING 则转 THINKING）：

```python
# react_cycle.py _dispatch_handler 之后（约第350行上下文）
if agent.status == AgentStatus.SUSPENDED:
    agent._retry_count = getattr(agent, '_retry_count', 0) + 1
    if agent._retry_count > 3:
        set_failed(agent, "可恢复错误重试超限")
        break
    set_status(agent, AgentStatus.THINKING, f"第{agent._retry_count}次重试")
elif agent.status == AgentStatus.EXECUTING:
    set_status(agent, AgentStatus.THINKING)
```

- **EXECUTING 设在 LLM 出完整响应后**（`_process_single_step` 收到 `response` chunk 时）：

```python
# react_cycle.py _process_single_step（约第219行）
elif chunk_type == "response":
    llm_response = chunk_data
    chunk_buffer.clear()
    set_status(agent, AgentStatus.EXECUTING)   # 收到完整响应=开始执行动作
```

- **THINKING 初始态**由 `initialize_run_state` 通过 `set_status(agent, AgentStatus.THINKING)` 设置（替代旧 `agent.status = THINKING`），并新增 `agent._retry_count = 0` 重置。

**语义对齐效果**：

| 状态 | 触发时机 | 真实动作 |
|------|----------|----------|
| THINKING | 循环尾部 / 初始化 | 调用 LLM |
| EXECUTING | LLM 返回完整响应 | 执行工具 / 组织答案 |
| SUSPENDED | _dispatch_handler 见 recoverable error / except 块 | 暂停等用户确认 |
| COMPLETED/FAILED/CANCELLED | 终态 | 结束 |

> 详见 3.2「event type 推断状态」与本详解第四节「关键技术点」。— 小欧 2026-07-12

#### 3.1.4 base_agent 关联改动

`base_agent.py` 改动 15 行，主要是移除 `UniversalAgent` 中 `_loaded_categories` 的 shadow 赋值（详见 v0.17.14 已做，本版本同步收敛），并把状态方法调用统一指向 `status_table`。`agent.status` 仍保留为属性，但所有写操作经 `set_status`。— 小欧 2026-07-12

#### 3.2.3 _dispatch_handler 按 event type 推断状态

`_dispatch_handler` 被重构为「先分派 handler 收集所有 event，再统一推断终态」：

```python
async def _dispatch_handler(agent, llm_response, chunk_buffer):
    parsed_type = llm_response.get("type", "answer")
    if parsed_type == "action":
        handler = handle_action(agent, llm_response, chunk_buffer)
    elif parsed_type == "answer":
        handler = handle_answer(agent, llm_response, chunk_buffer)
    elif parsed_type == "error":
        handler = _handle_llm_error(agent, llm_response)
    else:
        handler = _handle_unknown(agent, llm_response)

    seen_types = set()
    last_error_event = None
    async for event in handler:
        seen_types.add(event.type)
        if event.type == "error":
            last_error_event = event
        yield event

    if "error" in seen_types:
        error_msg = last_error_event.get_content() if hasattr(last_error_event, 'get_content') else ""
        if getattr(last_error_event, 'recoverable', False):
            set_status(agent, AgentStatus.SUSPENDED, error_msg)
        else:
            set_failed(agent, error_msg)
    elif "final" in seen_types:
        set_completed(agent)
```

> 注意：`_is_recoverable_error`（FC 格式错误 / asyncio.TimeoutError / httpx 网络异常）在 `_dispatch_handler` 内被复用，是 SUSPENDED 推断的核心依据。— 小欧 2026-07-12

### 3.3 SSE + SUSPENDED 映射（commit 663e2dc19）

#### 3.3.1 run_sse_stream 导入 status_table

`run_sse_stream.py` 新增导入并在 finally 前用统一入口：

```python
from app.services.agent.core_agent.status_table import set_cancelled, set_failed

# cancelled 分支

    set_cancelled(agent)

    pass
```

> 加 `try/except ValueError` 是为了防御「非法转换」——例如 agent 已处于 COMPLETED 又被 cancel，转换表会拒绝，捕获后不影响 SSE 正常结束。— 小欧 2026-07-12

#### 3.3.2 SUSPENDED → "failed" SSE end_type 映射

`finally` 中 `agent.status → end_type` 映射补齐 SUSPENDED：

```python
_m = {
    AgentStatus.COMPLETED: "final",
    AgentStatus.FAILED: "failed",
    AgentStatus.CANCELLED: "interrupted",
    AgentStatus.SUSPENDED: "failed",   # 挂起在前端表现为失败结束流
}
end_type = _m.get(agent.status, "unknown")
```

语义：SUSPENDED 是「暂停等用户确认」，但在单次 SSE 连接视角下，连接已结束，前端应停止接收并标记失败/中断，由独立 resume 接口续跑。

#### 3.3.3 sys_error_classifier 添加 httpx 分类

`app/utils/sys_error_classifier.py` 在 HTTP 状态码检查前插入 httpx 网络/超时分支：

```python
# 1b. 检查httpx网络/超时异常 — chendyg 2026-07-01
try:
    import httpx
    if isinstance(error, (httpx.TimeoutException, httpx.NetworkError)):
        return SystemErrorCategory.SERVER
except ImportError:
    error_type_name = type(error).__name__
    if error_type_name in ("ReadTimeout", "ConnectTimeout", "WriteTimeout",
                           "PoolTimeout", "ConnectError", "ReadError",
                           "WriteError", "CloseError"):
```

> 这是「可恢复错误」判定的数据来源之一——httpx 网络异常被识别为 SERVER 类，进而 `_is_recoverable_error` 将其归为可恢复 → 触发 SUSPENDED 重试链路。— 小欧 2026-07-12

```python
def mark_completed(self):
    current_log = self._get_current_log()
    if current_log:
        current_log["基本信息"]["状态"] = "已完成"

def mark_error(self, error_msg: str):
```

## 四、关键技术点

### 4.1 status_table 状态机设计

- **单一写入点**：除 `status_table` 的 `set_status/set_failed/set_completed/set_cancelled` 外，全代码库不再出现 `agent.status = X` 直接赋值（已由本版本消除散点）。
- **转换表校验**：`_validate_transition` 非法转换抛 `ValueError`，配合 `threading.RLock` 防并发竞态。
- **双写**：每次状态变更同时记 `logger` 与 `prompt_logger.log_status`，可观测性与 prompt 审计一致。

### 4.2 EXECUTING / THINKING 精确循环时机

- THINKING 是「下一轮要调 LLM」的意图态，设在 single_step 完成后（尾部），而非循环入口。
- EXECUTING 是「已拿到 LLM 完整响应、即将执行动作」的态，设在收到 `response` chunk 时。
- 二者交替构成 `THINKING → EXECUTING → THINKING → ... → COMPLETED/FAILED`，与 ReAct「思考-行动」严格对应。

### 4.3 event type 推断状态

核心思想：**handler 只产出带 `type` 字段的 Step，终态决策权上收编排层**。

| event 集合 | recoverable | 推断结果 |
|------------|-------------|----------|
| 含 error + recoverable=True | 是 | SUSPENDED |
| 含 error + recoverable=False | 否 | FAILED |
| 含 final | — | COMPLETED |
| 其它（chunk/thought/tool） | — | 不改状态 |

`recoverable` 由 `ErrorStep.recoverable` 携带，其源头是 `_is_recoverable_error`（FC 格式错误 / asyncio 超时 / httpx 网络异常）与 `sys_error_classifier` 的 SERVER 分类。这是 SUSPENDED 能被正确触发的链路保证。— 小欧 2026-07-12

## 六、风险与遗留

1. **SUSPENDED 端到端未闭环**：本版本只把 SUSPENDED 接入状态机与 SSE→failed 映射，但「用户确认后 resume 续跑」的接口与前端交互在 v0.18.11 才进一步分离（见第七节），v0.17.16 时 SUSPENDED 实际多表现为「重试超限→FAILED」。
2. **`_retry_count` 跨 SSE 连接不持久**：`agent._retry_count` 在 `initialize_run_state` 重置，单次连接内有效；多轮对话跨连接计数归零，重试上限保护弱。
3. **mark_completed 仅 chat_stream 主路径调用**：非 chat_openai 入口（如直接调 `run_react_cycle` 的测试脚本）若未显式 `mark_completed`，prompt 日志依赖 `save()` 兜底推断，可能与真实终态略有延迟。
4. **`except ValueError` 静默吞转换异常**：`run_sse_stream` 捕获后不记录，极端非法转换场景可能掩盖状态机 bug，建议后续补 `logger.debug`。— 小欧 2026-07-12
