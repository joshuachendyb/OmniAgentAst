## 二、背景与目标

### 2.1 为什么要做这次变更

v0.18.6 之前，项目已对全部工具做过 `llm_data` 去冗余重构（v0.18.1～v0.18.3 等），强调「工具返回的原始 `data` 与给 LLM 消费的 `llm_data` 分离」。重构后大量工具改为 `build_success(data={}, llm_data=...)` 或 `build_error(data={}, llm_data=...)`，即 `data` 故意留空，所有可读信息下沉到 `llm_data.metrics` / `summary`。

这带来一个隐患：**肉眼观察 prompt log 时，看到 `data={}` 很容易误判为「工具没返回任何东西 = bug」**。为了区分「设计意图的空 `data`」与「真正的缺陷」，小欧于 2026-07-08 对 54 个工具的 prompt log 做了 raw data 与 formatted 结果的逐项审查。

> 审查目标：① 确认 `data={}` 是否为设计意图；② 在此前提下，揪出仍然存在的真实 bug。
> — 编写人：小欧 - 2026-07-12

### 2.2 54 工具分析结论

- **数据分层设计确认**：54 个工具中，绝大多数 success/error 返回 `data={}` 或仅含少量标量，属于「`data` 承载原始结构化数据、`llm_data` 承载 LLM 可读摘要」的分层设计（见 v0.18.1～v0.18.3 重构说明）。`data={}` 非 bug，是设计意图。
- **反向验证**：通过把 `llm_data.metrics` / `summary` 与 raw `data` 对照，确认 LLM 实际拿到的信息完整、正确。
- **发现 3 个真实 bug**：在分层设计正确的前提下，仍有 3 处逻辑缺陷导致「LLM 拿到错误/缺失信息」，分别为 read_xlsx / ping_port / delete_file（即 B1/B2/B3）。

> 说明：v0.18.7 时期的工具总数为 54（后续版本陆续增长至 63，详见附录八关联版本）。本次分析覆盖当时全部 54 个工具。
> — 编写人：小欧 - 2026-07-12

### 2.3 设计意图：为什么 `data={}` 是合理的

以 delete_file 的成功分支为例（当前代码，`backend/app/tools/file/delete_file.py:192`）：

```python
return build_success(
    data={},
    llm_data=llm_data,
)
```

对应 `observation_formatter` 路由（`delete_file.py:176` 注释）：

```
# branch: #0 空data (L73)
# trigger: data 为 {} → if not data: return ""
# handler: 直接返回空字符串
```

即：空 `data` 在前端观察层被格式化为空字符串，真正展示给 LLM 的内容来自 `llm_data.summary`（如「删除 xxx，成功: 放入回收站」）与 `llm_data.metrics`。这样避免了重复信息，也避免了原始结构化数据污染 LLM 上下文。这是经过 v0.18.x 多轮重构确立的规范，并非缺陷。

> — 编写人：小欧 - 2026-07-12

### 3.1 B1：read_xlsx —— `row_count` 丢失导致 summary 永远「0 行」

#### 3.1.1 涉及文件
- `backend/app/tools/document/read_xlsx.py`（`_read_xlsx_inner` 函数，约 115–124 行）

#### 3.1.2 动机
read_xlsx 主函数 `read_xlsx()` 在成功分支通过 `result.get("row_count", 0)` 读取行数，写入 `llm_data.summary`（如「读取Excel xxx，成功: 100行，3个工作表」）。但内部函数 `_read_xlsx_inner` 在「单 sheet」分支提前把 `row_count` 弹掉了，主函数永远读到 `0`。多 sheet 分支原本也漏传 `row_count`。结果：无论读多少行，summary 都显示「0 行」，LLM 拿到的行数信息错误。

主函数侧（v0.18.6）：

```python

        sheet_count = len(result.get("sheet_names", []))
        result.pop("row_count", None)            # 二次 pop（此时已无此键）

```

#### 3.1.4 真实代码 After（v0.18.7）


> 关键修复点：① 删除单 sheet 分支的错误 `pop`，让 `row_count` 能顺利上达主函数；② 多 sheet 分支补 `"row_count": total_rows`，其中 `total_rows` 在 `for sheet in target_sheets` 循环中通过 `total_rows += row_count` 累计（见 `read_xlsx.py:86`、`111`）。
> — 编写人：小欧 - 2026-07-12

#### 3.1.5 影响分析
- 修复前：单/多 sheet 读取，`summary` 均显示「0 行」，LLM 无法感知实际行数，下游基于行数的判断（如「是否读全」「是否需要分页」）全部失真。

- 数据层 `data` 仍按 v0.18.x 规范在**主函数**处 `result.pop("row_count", None)` 后返回（即 `data` 不含 `row_count`，由 `llm_data.metrics` 承载），分层设计保持不变，无回归。

> — 编写人：小欧 - 2026-07-12

### 3.2 B2：network_diagnose（ping_port）—— 中文 locale 下 ping 包数推算后备

#### 3.2.1 涉及文件
- `backend/app/tools/network/network_diagnose.py`（`_ping` 函数，约 179–189 行）

#### 3.2.2 动机
`_parse_ping_output` 对 Windows 平台用正则从 ping 输出中提取 `packets_sent / packets_received / loss_rate`：

```python
loss = re.search(r"(?:已发送|Sent\s*=\s*)(\d+).*?(?:已接收|Received\s*=\s*)(\d+).*?(?:丢失|Lost\s*=\s*)(\d+).*?(\d+)%", raw_output, re.DOTALL | re.IGNORECASE)
```

该正则同时兼容中文「已发送/已接收/丢失」与英文「Sent/Received/Lost」。但 Windows 不同语言包、不同区域设置的 ping 输出文案不完全一致（例如部分中文locale 的字段名、顺序、分隔符差异），导致正则整体匹配失败，`packets_sent` 保持默认值 `0`。

然而 ping 实际成功——输出中存在 `TTL=128` 之类的回包标记。此时 `parsed["is_reachable"]` 已被 `if "TTL=" in raw_output.upper()` 置为 `True`，但 `packets_sent/packets_received` 仍为 `0`，LLM 拿到「可达但收到 0 包」的矛盾信息。

> — 编写人：小欧 - 2026-07-12

#### 3.2.3 真实代码 Before（v0.18.6）

```python
    parsed = _parse_ping_output(raw_output, platform.system().lower())
    reachable = parsed["is_reachable"]
    data = {**parsed}
    # 数据一致性校验：packets_sent=0 但 latency 存在 → 矛盾，清空 latency
    if data.get("packets_sent", 0) == 0 and data.get("min_latency") is not None:
        data.update(min_latency=None, avg_latency=None, max_latency=None)
    if not reachable:
        data.update(packets_received=0, packets_lost=parsed["packets_sent"],
                     loss_rate=100.0, min_latency=None, avg_latency=None, max_latency=None)
    return {"success": True, "data": data, "is_reachable": reachable, "parsed": parsed}
```

#### 3.2.4 真实代码 After（v0.18.7）

```python
    parsed = _parse_ping_output(raw_output, platform.system().lower())
    # 后备：locale不匹配时正则失败但TTL=存在 → 从TTL计数推算包数 — 小欧 2026-07-08
    if parsed["is_reachable"] and parsed["packets_sent"] == 0:
        ttl_count = len(re.findall(r"TTL=|ttl=", raw_output, re.IGNORECASE))
        if ttl_count > 0:
            parsed["packets_received"] = ttl_count
            parsed["packets_sent"] = count
            parsed["packets_lost"] = max(0, count - ttl_count)
            parsed["loss_rate"] = round(parsed["packets_lost"] / count * 100, 1)
    reachable = parsed["is_reachable"]
    data = {**parsed}
    # 数据一致性校验：packets_sent=0 但 latency 存在 → 矛盾，清空 latency
    if data.get("packets_sent", 0) == 0 and data.get("min_latency") is not None:
        data.update(min_latency=None, avg_latency=None, max_latency=None)
    if not reachable:
        data.update(packets_received=0, packets_lost=parsed["packets_sent"],
                     loss_rate=100.0, min_latency=None, avg_latency=None, max_latency=None)
    return {"success": True, "data": data, "is_reachable": reachable, "parsed": parsed}
```

> 后备逻辑核心：仅当「可达（`TTL=` 存在）且 `packets_sent==0`（说明正则没解析出包数）」时才触发；用 `re.findall(r"TTL=|ttl=", raw_output)` 统计回包行数作为 `packets_received`，`packets_sent` 取请求参数 `count`，据此反推 `packets_lost` 与 `loss_rate`。
> — 编写人：小欧 - 2026-07-12

#### 3.2.5 影响分析
- 修复前：中文 locale 下，可达主机被报成「收到 0 包 / 丢失 100%」，LLM 误判网络不可达或严重丢包。
- 修复后：即使正则失败，也能从 `TTL=` 行数合理推算收到包数，LLM 拿到正确的 `packets_received / loss_rate`。
- 该后备**不改变** `is_reachable` 判定（仍由 `TTL=` 决定），仅补全包数统计，属于安全兜底，不影响正常 locale 的解析路径（正常路径 `packets_sent != 0`，不进入后备分支）。

> — 编写人：小欧 - 2026-07-12

### 3.3 B3：delete_file —— error 分支 hint 动态映射

## 四、关键技术点

### 4.1 row_count 位置错误根因（为什么「弹早了」就会读 0）

`row_count` 的生命周期跨越两个函数层级：

1. **内部函数 `_read_xlsx_inner`**：构造每个 sheet 的 `sheet_data` 含 `row_count`（`read_xlsx.py:108`），多 sheet 时累加 `total_rows`（`:111`）。
2. **主函数 `read_xlsx`**：成功分支 `row_count = result.get("row_count", 0)`（`:226`）读取后，才在 `:228` 做 `result.pop("row_count", None)` 把该键从 `data` 中剔除（因为 `data` 不应携带已上移到 `llm_data.metrics` 的字段）。

v0.18.6 的 bug 是：**内部函数单 sheet 分支也执行了 `result.pop("row_count", None)`**，等于在「数据还没上达主函数」之前就把键销毁了。主函数 `get` 时只剩默认值 `0`。这是典型的「清理职责越层」——`pop` 的归属权应只在主函数（统一负责 `data` 与 `llm_data` 的分层），内部函数只应**返回**原始数据，不该替主函数做裁剪。

> 修复本质：把 `pop` 职责收回到主函数单一出口，内部函数只增不减。符合项目「内部 helper 只返回 raw dict」的铁规（见文件头注释 `read_xlsx.py:8-11`）。
> — 编写人：小欧 - 2026-07-12

### 4.2 TTL 推算包数后备的触发条件设计

后备段有两道闸门，缺一不可：

| 闸门 | 条件 | 目的 |
|------|------|------|
| 闸门1 | `parsed["is_reachable"]` 为 True | 确保确有回包（`TTL=` 存在），不是彻底不通 |
| 闸门2 | `parsed["packets_sent"] == 0` | 仅在正则「完全没解析出包数」时兜底，正常 locale 不进入 |

`ttl_count = len(re.findall(r"TTL=|ttl=", raw_output, re.IGNORECASE))` 直接数回包行数。Windows ping 每个成功回包输出一行含 `TTL=xxx` 的文本，故 `ttl_count ≈ packets_received`。`packets_sent` 回退为请求参数 `count`（默认 4），进而 `packets_lost = count - ttl_count`、`loss_rate` 按比例计算。

> 设计取舍：后备不追求精确（无法从 `TTL=` 行读出具体延迟），只补全「包数/丢包率」这一最关键信息，延迟仍由后续 `min_latency/avg_latency` 一致性校验逻辑处理。属于「不完整但正确」的兜底，优于「完整但恒为 0」。
> — 编写人：小欧 - 2026-07-12

### 4.3 hint 动态映射的分派策略

delete_file 的 hint 映射采用「关键字包含匹配（case-insensitive）」的 if/elif 链，顺序有讲究：

1. `recursive` 优先：非空目录错误最具体，应最先识别，引导加参数。
2. `safety` 其次：安全拦截属系统级阻断，提示权限/策略。
3. `任务ID` 再次：业务前置条件缺失。
4. 兜底：其余未知错误回退到通用「请检查文件是否存在和权限」。

该策略无需精确错误码枚举，靠 `error_detail` 的自然语言关键词即可分派，鲁棒且易扩展。后续 v0.18.14 演进为「异常类型 → `hint_for_write_error` 集中映射」，是同一思路的归一化。

## 六、风险与遗留

### 6.1 风险

| 风险点 | 说明 | 等级 |
|--------|------|------|
| B2 后备精度 | `TTL=` 计数法在极端情况下（如某些 Windows 版本回包行不含 TTL）可能漏计，但至少不会是「恒为 0」 | 低 |
| B3 关键词匹配 | 若未来 `error_detail` 文案调整，关键字可能失配，回退到通用 hint（不报错，仅提示不够精准） | 低 |
| B1 多 sheet 计数 | `total_rows` 仅累加「数据行」（`row_count` 不含表头），与单 sheet 口径一致，无口径偏差风险 | 无 |

> — 编写人：小欧 - 2026-07-12

### 6.2 遗留 / 后续演进

- **B3 的归一化**：v0.18.7 的「关键字分派」在 v0.18.14 被进一步统一为 `hint_for_write_error(e, ...)` 集中函数，覆盖 file 类 13 工具，消除硬编码通用 hint（见 v0.18.14 变更汇总）。

- **54 工具分析产出**：本次分析确认 `data={}` 为设计意图，为后续「错误提示诚实化」（v0.18.14）提供了正确性基线。
