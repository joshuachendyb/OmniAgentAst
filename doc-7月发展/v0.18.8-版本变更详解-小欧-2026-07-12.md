## 二、背景与目标

本章说明 v0.18.8 为何而做，避免读者只看到"改了什么"而不知"为何改"。

### 2.1 文档写工具缺少行内格式能力

此前 `write_docx / write_pdf / write_pptx` 仅能写"纯文本"，大模型生成的 Markdown 源文中的 `**加粗**`、`*斜体*`、`` `行内代码` `` 会被原样当作字符串落盘，用户拿到的是带星号的裸文本，可读性极差。目标：让三个写工具对行内 Markdown 做渲染，且逻辑共享、单一来源（DRY）。

### 2.2 tree 缺乏深度保护

`tree` 目录树默认递归 `max_depth=10`，对深层目录（如 `node_modules`）会产生超长输出、拖慢 LLM 上下文。目标：将默认深度收敛到 `5`，并公开 `max_depth` 参数供调用方按需调整（1~20）。

### 2.3 llm_data 合并导致的索引错位

并行工具执行时，旧逻辑对每个工具返回的 `llm_data` 做 `_merge_llm_data` 合并成一个 dict，再与并行结果 1:1 索引。一旦某个工具未返回或返回结构异常，下游（observation / SSE）按索引取用时错位，且 merge 会丢失多工具各自的细节。目标：改为"列表直接传递"，`llm_data` 始终为 `List[Dict]`，前端取首项消费，保留全量。

### 2.4 多个 Prompt 日志暴露的真实缺陷

通过 v0.18.7 的 54 个工具 prompt log 深度分析（见 version.txt v0.18.7），发现：

- N3：`clipboard_control` 写入返回键名 `content`，而读取返回 `text`，前后端约定不一致导致下游解析失败。
- N4：`registry_read` 键不存在与值不存在共用一条 hint，排障方向模糊。
- N7：`execute_shell_command` 的 stderr 含大量良性诊断输出（如 PowerShell 进度条、警告），被误判为错误。

### 3.1 feat：docx/pdf/pptx 写工具行内 Markdown 格式支持

#### 3.1.1 新增共享模块 md_inline_utils.py

文件：`backend/app/tools/document/md_inline_utils.py`（全新增，小欧 2026-07-08）。

核心函数 `_parse_inline_md(text)`：解析行内 Markdown，返回 `[(文本, 粗体, 斜体, 代码, 链接URL)]` 元组列表，支持 `**粗体**`、`*斜体*`、`***粗斜体***`、`` `代码` ``、`[文本](链接)`，**不做嵌套**（遵循 KISS 原则）。

```python
# md_inline_utils.py（v0.18.8 新增）
def _parse_inline_md(text: str):
    """解析行内Markdown，返回 [(文本, 粗体, 斜体, 代码, 链接URL)]"""
    segments = []
    pos = 0
    while pos < len(text):
        # 代码 `code` 优先（避免匹配`内的**bold**）
        m = re.match(r'`([^`]+)`', text[pos:])
        if m:
            segments.append((m.group(1), False, False, True, None))
            pos += m.end(); continue
        m = re.match(r'\*\*\*([^*]+)\*\*\*', text[pos:])   # 粗斜体
        if m:
            segments.append((m.group(1), True, True, False, None))
            pos += m.end(); continue
        m = re.match(r'\*\*([^*]+)\*\*', text[pos:])       # 粗体
        if m:
            segments.append((m.group(1), True, False, False, None))
            pos += m.end(); continue
        m = re.match(r'\*([^*]+)\*', text[pos:])           # 斜体
        if m:
            segments.append((m.group(1), False, True, False, None))
            pos += m.end(); continue
        m = re.match(r'\[([^\]]+)\]\(([^)]+)\)', text[pos:])  # 链接
        if m:
            segments.append((m.group(1), False, False, False, m.group(2)))
            pos += m.end(); continue
        segments.append((text[pos], False, False, False, None))
        pos += 1
    return segments
```

PDF 专用 `_md_to_pdf_xml(text)`：将行内格式转成 reportlab 的 Paragraph XML 标签（`&lt;b&gt;`、`&lt;i&gt;`、`&lt;font face="Courier"&gt;`）。

## 四、关键技术点深度分析

### 4.1 `_parse_inline_md` 的设计取舍

- **单一来源**：docx/pdf/pptx 三工具共用一份解析，杜绝三套正则各自漂移（DRY）。
- **不嵌套**：明确拒绝 `**粗体*斜体**` 这类嵌套，正则按"代码 > 粗斜体 > 粗体 > 斜体 > 链接 > 普通字符"顺序贪婪匹配，简单直接（KISS）。
- **代码优先**：先匹配 `` `code` ``，避免反引号内 `**bold**` 被误判为粗体。

### 4.2 llm_data 列表模式的本质

旧模型：`List[llm_data] → merge → 单 dict`，隐含"多工具信息可压扁"的错误假设。
新模型：`List[llm_data]` 原样透传，observation/SSE 各自决定如何消费（取首项或遍历）。
收益：并行索引 1:1，无错位；保留每个工具的完整 status/metrics；截断分支同构，形态一致。

### 4.3 N3 / N4 / N7 的共性

三者均来自"prompt log 实测暴露的真实缺陷"（非臆测），修复原则是"让错误信息对 LLM 诚实且可操作"：

- N3：键名统一 → 下游能稳定解析。
- N4：区分"键不存在 / 值不存在" → hint 精准。
- N7：白名单过滤良性 stderr → 减少误报。

## 六、风险与遗留

### 6.1 风险

- `md_inline_utils` 不做嵌套格式，若 LLM 输出嵌套 Markdown（如 `**a*b**`），按当前顺序匹配结果可能不符合直觉，但符合 KISS、可预期。
- sse.ts 列表兼容为"取首项"降级，若未来前端需展示多工具全量 llm_data，需进一步改造渲染层。
- `_merge_llm_data` 仍被单行场景引用，属过渡共存，非技术债但需关注后续是否彻底移除。

### 6.2 遗留项

- tree 的 `max_depth` 上限 20 与 `file_schema` 约束需保持同步，若 schema 改范围而 tree.py 未改，将出现静默截断。
- N7 白名单为关键字命中，新增良性 stderr 模式需持续补充，避免重新误报。
