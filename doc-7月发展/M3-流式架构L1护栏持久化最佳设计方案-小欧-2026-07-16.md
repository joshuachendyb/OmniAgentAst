## 一、问题根因（逐行代码验证，非臆测）

### 1.1 流式架构导致"护栏对用户所见无效"

| # | 事实 | 代码证据 |
|---|------|---------|
| 1 | 后端**逐字流式**：每个 token 以 `ChunkStep` yield 到前端的 SSE | `llm_stream.py:142-150` |
| 2 | 前端**气泡文本 = 流式累积**，非 `FinalStep.content` | `useChatCallbacks.ts:288-302` `streamingContentRef.current += chunk` → `message.content` |
| 3 | 有 chunk 时 `FinalStep` 正文**被前端丢弃** | `AIMessageBubble.tsx:127-134` `step.type === 'final' && hasChunk → return false` |
| 4 | 终值优先选流式累积，`FinalStep.content` 只作空流兜底 | `useChatCallbacks.ts:395` `finalContent = streamingContentRef.current \|\| finalResponse` |

### 1.2 本地代码存在有害的"超长外置"逻辑

`answer_handler.py:307-314` 的执行顺序：
```
① 去重（_dedup_repeat）          → content = 去重后文本
② 超长外置（_externalize_if_long）→ content = "625字+文件路径"（覆盖去重结果！）
③ FinalStep(response=content)    → stream_state.current_content = "625字+文件路径"
④ finalize_message                → DB存的是"625字+文件路径"
```

**这是真 bug**：外置在去重之后执行，将去重后的内容覆盖为"625字+文件路径"；用户上翻时看到的不是完整文本、不是去重文本，而是摘要+路径。同时 `reports/` 目录未挂载静态服务，路径不可点击，功能半残。

**结论**：超长外置不仅无价值，还直接破坏了去重结果和 DB 持久化内容。

### 1.3 退化检测同样无实际价值

- `_is_degenerate`：检测 final 是否为"规划句"退化。但纠正走重调 LLM 产生新流 (`_correct_degenerate`)，新流同样经此函数 → 检测结果对 DB 无影响。
- `_correct_degenerate`：重调 LLM，增加一次 LLM 调用成本，但用户已在流式中看到了原始内容。
- **结论**：退化检测+纠正既无益于流式显示，也无益于 DB 持久化。

### 1.4 thought 字段未持久化到 `chat_messages` 主表

- `FinalStep.thought` 从 LLM 响应解析得到（`answer_handler.py:265` `thought = parsed.get("thought", content)`）
- 已作为 `ThoughtStep` 独立落库到 `chat_message_steps` 表（`answer_handler.py:267-270`）
- **但不在 `chat_messages.content` 列中**，`finalize_message` 只写 `content` 与 `status`
- 外部读取 `message.content`（API 返回/导出）时取不到 thought

### 1.5 步过滤规则（上翻时）

`AIMessageBubble.tsx:127-134`：
```js
if (step.type === 'chunk') return false;
if (step.type === 'final' && hasChunk) return false;
```

上翻 execution panel 显示：`thought` 步骤 + `action_tool` 步骤 + `observation` 步骤。当前过滤规则正确，无需修改。

## 二、核心设计决策

### 2.1 总原则

> **流式过程中不做任何检测/修改**（数据已经发给前端，改也没用）。
> **检测只在 DB 入库时生效**——唯一有价值的是重复检测（去重后文本存入 DB，上翻时显示干净版本）。

### 2.2 三件事

| # | 做什么 | 为什么 |
|---|--------|--------|
| ① | 从 `answer_handler.py` **删除** `_externalize_if_long`、`_is_degenerate`、`_correct_degenerate`、`_safe_degrade_final`、`_extract_tool_results` 以及全部关联常量和调用 | 这些是"错误功能"（用户原话），不仅无价值，还破坏 DB 持久化内容 |
| ② | `final_quality_guardrail` **精简**为仅剩 `_dedup_repeat`（重复检测） | 唯一有用的检测，DB 入库时生效 |
| ③ | `chat_messages` 表新增 `thought` 列，`finalize_message` 写入 `thought` | 让 API 返回/导出/主气泡能取到 thought |

### 2.3 十大原则符合度

| 原则 | 符合度 | 说明 |
|------|--------|------|
| SRP | ✅ | 流式只管输送，入库只管持久，各司其职 |
| DRY | ✅ | 复用现有 `_dedup_repeat` + `stream_state.current_content` 链路 |
| KISS-DIRECT | ✅ | 删除无用代码（KISS），仅保留去重 + thought 列 |
| SLAP | ✅ | 不在流式循环混入 DB 逻辑，DB 在 finally 收口 |
| YAGNI | ✅ | 不加在线门禁/抽象/op_id 贯通；**删除无价值代码（更YAGNI）** |
| 禁止 backward | ✅ | 全部清理，不保留"兼容旧模式"分支 |
| OCP | ✅ | `thought` 新列对现有逻辑零影响 |
| LSP | ✅ | `FinalStep`/`ThoughtStep` 接口不变 |
| ISP | ✅ | `finalize_message` 接口窄 |
| 复用优先 | ✅ | 全量复用现有链路 |
