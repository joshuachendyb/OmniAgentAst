## 二、背景与目标

### 2.1 一致性痛点（小欧 2026-07-05）
v0.17.21 已统一文件工具与 shell 持久引擎，但 63 个工具的 `llm_data` 输出存在四类漂移：
1. **`_act_params` 缺漏**：file/network 工具未在 `action.params` 回显用户传入的关键参数（如 `user_offset`、`timeout`、`proxy`），导致 LLM 无法从 observation 反推「自己刚才传了什么」。
2. **`error detail` 空泛**：多数 error 分支 `detail` 缺位或硬编码「请检查文件是否存在」，LLM 无从定位根因。
3. **`metrics` 不统一**：部分工具有 `lines`/`bytes` metric，部分缺失，summary 信息不齐。
4. **`hint` 不分支**：错误提示不随失败路径（键不存在 vs 值不存在、空文件 vs 超范围）变化。

### 2.2 目标（小欧 2026-07-05）
- 全部 63 工具 `llm_data` 满足统一三段式（`action`/`status`/`metrics`）。
- `action.params`（`_act_params`）透传用户真实入参，形成「Observation 归一闭环」——LLM 看到的 observation 与真实调用一一对应。
- `observation_formatter` 的 `format_data_detail` 在每个 `_build_*_llm_data` 处标注命中 route（branch + handler + file:line），消除「工具不知道自己被什么 formatter 分支渲染」的黑盒。
- 删除 3 处死代码，清理废弃 `runcode` 引用与过期 notes。

## 三、逐项变更详解

### 3.1 observation_formatter route 标注（全部 63 工具 10 分类）
**动机**：`format_data_detail` 按 `data` 结构分派到若干 branch（#0 空data、#2 raw str、#3 entries、#5 rows、#10 raw text、#21 fallback 等），但工具侧长期不清自己命中哪条 route，导致截断/渲染预期错位。

**涉及文件**：`backend/app/services/agent/observation_formatter.py`、`backend/app/tools/{file,network,desktop,fundamental,timer,system,dataanalysis,document,shell,win_registry}/*_tools.py`

**做法**：在每个工具的 `_build_*_llm_data` 返回 `build_success` 前，插入统一注释块：
```python
# ---- observation_formatter route -------------------------------------------
# branch: #2 raw str
# trigger: "content" in data and isinstance(data["content"], str)
# handler: inline — 直接返回 data["content"], OBS_MAX_STRING_LENGTH 截断
# file:    observation_formatter.py:117-122
# ------------------------------------------------------------------------------
return build_success(data=_data, llm_data=llm_data)
```
真实示例见 `read_text_file.py:450-456`（branch #2）、`timer_set.py:146-152`（branch #21 fallback）、`registry_read.py:166-171`（branch #0 空data）。

**死代码删除（小欧 2026-07-05）**：
- `safe_json_dumps` 的 import（formatter 已改用标准 `json.dumps` 兜底）。
- `#1 content-wrapped` 旧版分支（content 包裹判断已废弃）。
- `#7 output legacy` 旧版输出分支（legacy 渲染路径已移除）。

**影响**：63 工具全部显式标注 route，后续 formatter 改动可精准回溯受影响工具，减少回归误伤。

        data={},

## 四、关键技术点

### 4.1 route 标注机制
每个 `_build_*_llm_data` 在 `build_success` 前以注释固化 `branch`/`trigger`/`handler`/`file:line` 四元组，使「工具 → formatter 渲染分支」映射显性化。`observation_formatter.py` 头部（20-55 行）的工具→handler 映射表与工具内 route 注释双向印证。

### 4.2 _act_params 透传约定
`_act_params` 仅在 main 函数内由 `_build_*_llm_data` 组装，遵循「铁规1」：helper 不构建 llm_data。透传规则：
- 必传 `path`/`target` 恒入参。
- 可选用户参数（`offset`/`limit`/`timeout`/`proxy`/`callback` 等）仅在非默认值时加入，避免噪声。

### 4.3 hint 逐分支细化约定
- error 分支 `hint` 优先使用调用点传入的精准字符串，缺省回退到 builder 内的通用兜底（如 `hint if hint else "请检查文件路径和参数是否正确"`）。
- success/warning 分支 `hint` 携带「下一步建议」（如 readtext 部分读取时 `hint="可使用offset+limit继续读取后续内容"`）。

### 4.4 一致性校验清单（小欧 2026-07-05 内部口径）
v0.17.22 收口后，每个工具的 `_build_*_llm_data` 须满足：
1. `_act_params` 含 `path`/`target` 且可选参数条件性回显；
2. error 分支 `detail` 非空且由失败路径动态生成；
3. error 分支 `hint` 与 `detail` 对应根因，不硬编码通用语；
4. success 分支 `metrics` 含可量化指标（行数/字节/耗时/数量）；
5. `build_success` 前附 `observation_formatter route` 注释块。

### 4.5 死代码删除影响面
3 处死代码（`safe_json_dumps` import / `#1 content-wrapped` / `#7 output legacy`）删除后，`format_data_detail` 仅保留当前生效分支（#0~#21），渲染逻辑单一化，后续 v0.18.1 去冗余重构无需再兼容旧分支，降低回归面。

### 6.3 回归检查清单（小欧 2026-07-12 建议）

### 6.4 测试覆盖说明
