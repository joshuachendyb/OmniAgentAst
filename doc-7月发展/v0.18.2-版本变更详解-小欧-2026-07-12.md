### 1.3 设计原则回顾
本版本延续 v0.17.21 确立的"工具返回 `data` + `llm_data` + `other_data` 三层结构"（`tool_response.py`），并进一步强化两条铁律：
- **data 只承载格式化所需原始数据**，统计类字段（affected_rows / total_matches 等）一律迁到 `llm_data.metrics`，避免 data 与 observation 文本双重表达。
- **llm_data 是给 LLM 看的"精简版"**，action.params 等字段统一截断到 50 字符，杜绝把完整 SQL / 完整 body 等超大字段回灌给 LLM 造成 token 浪费。

## 二、背景与目标

### 2.1 问题背景
在进入 v0.18.2 之前，工具层经历了 v0.17.21 的 `llm_data` 补齐与 v0.18.1 的部分裁剪，但依然存在三类冗余：

1. **data 冗余字段**：大量工具在 `data` 中塞入了与 `llm_data` / observation 文本重复的信息，例如 `execute_sql` 的 `data` 中带 `sql`、`generate_chart` 的 `data` 中带 `chart_type`、桌面工具 `data` 中带坐标等。这些字段既不被 formatter 渲染，又让 `data` 体积膨胀。
2. **llm_data 大字段回灌**：部分 `_build_*_llm_data` 在 `action.params` 中直接放完整 `sql` / `headers` / `body`，单次调用可多耗数百 token。
3. **observation_formatter 输出样式臃肿**：v1 版本采用"观察 + 结果 + 统计 + 建议"四段式，对 LLM 而言信息密度低、且 `metrics` 已并入"观察:"行后还重复展示统计段。

### 2.2 目标
| 目标 | 量化指标 | 落地手段 |
|------|----------|----------|
| data 去冗余 | 删 sql / chart_type / 坐标等冗余键 | 工具 builder 重写 data 返回 |
| llm_data 字段裁剪统一 50 | action.params 各字符串字段 ≤ 50 字符 | `_build_*_llm_data` 统一 `[:50]` |
| 删 ch6 | 旧版注释 / 死代码章节清空 | observation_formatter v1 代码删除 |
| observation 精简 | 四段式 → 两段式（状态行 + 观察行） | `_format_llm_data` 重写 |

> 设计要点：工具的统计数据（total_matches / total_files / affected_rows 等）已通过 `llm_data.metrics → summary → _format_llm_data` 嵌入"观察:"行，最终给 LLM 的文本必然包含。data 中不再重复存放。— 小欧 2026-07-06 18:39:02（见 `observation_formatter.py` 第 482~485 行注释）

### 2.3 token 浪费估算
以一个典型多轮任务（单次请求含 2~3 个工具调用，每天 200 轮）估算：
- 旧版单工具 `llm_data.action.params` 含完整 `sql`（平均 80 字符）或完整 `headers/body`（可达 300~600 字符），每工具每次约多耗 60~120 token（含 JSON 包装）。
- 3 个批次工具（execute_sql / http_request / edit_text_file 等）高频调用，日均额外 token ≈ 200 轮 × 2.5 工具 × 90 token ≈ **45,000 token / 天 / 用户**。
- 截断到 50 字符后，单工具 params 稳定 ≤ 50 字符（约 15~25 token），冗余下降约 75%。
- observation 由四段式（观察 + 结果 + 统计 + 建议）改为两段式，单工具 observation 文本减少 2~4 行，长任务历史累积收益显著。

> 上述为基于真实字段长度的工程估算，非精确计量；目的是说明"去冗余"并非洁癖，而是有实际 token 成本的优化。编写人：小欧 - 2026-07-12 21:57:29

### 2.4 数据契约规范（三层结构）
v0.18.2 强化了工具返回的三层契约（`tool_response.py` 第 21~69 行）：
- **data**：仅承载 formatter 渲染所需原始数据（如 `rows/matches/entries/text`），不参与 LLM 语义表达。可空 `{}`。
- **llm_data**：LLM 观测层。含 `status / action / summary / metrics / duration_ms`，是给 LLM 看的"精简版"，必须自包含（不依赖 data 即可读懂结果）。
- **other_data**：前端 /  Agent 编排层专用（如附件、return_direct、retry_count），绝不进入 LLM observation。

违反契约的典型反模式（v0.18.2 已清除）：在 `data` 放 `sql` / `chart_type` / 坐标，或在 `llm_data.action.params` 放完整大字段。编写人：小欧 - 2026-07-12 21:57:29

## 三、逐批次详解

### 3.1 批次 1：核心链路（action_handler / llm_stream / message_builder）
核心链路不直接改工具，而是修复 tool_call 传递与 llm_data 装配逻辑，为后续工具批次铺路。

- **action_handler.py**：`build_observation` 中将并行场景的 `llm_data` 改为**直接列表传递**（不 merge），与 `_parallel_results` 索引 1:1（第 403~404 行 `llm_data_list = _all_llm_data if _all_llm_data else None`）。错误结果分支增加 `exec_code` 解析防御（第 303~317 行）。
- **llm_stream.py**：`_build_tool_calls_response` 精简 tool_call 聚合逻辑，多 tool_call 直接 `extend` 到 `built_tool_calls`（第 23~44 行），去掉了对首条之外的冗余包装；增加残缺 tool_call 参数告警（第 25 行）。
- **message_builder.py**：`add_assistant_tool_call` 与 `add_tool_result` 严格按 `tool_call_id` 配对，1 条 assistant（带 N 个 tool_calls）+ N 条 tool 的历史结构固化（第 62~80 行 + 第 322~333 行 `action_handler` 调用处）。修复多轮 trim 时 tool 角色丢失的潜在 bug。

### 3.2 批次 A：observation_formatter 精简（去冗余 + 注释旧版 v1 + 删 v1 旧代码）
对应 commit：`969dedb9a`（v1 旧代码删除）、`d5d9cfd21`（精简 `_format_llm_data` 输出）、`26bf374d4` / `c86fd14cc`（精简 + 文档）。

关键改动：
- **删除 v1 旧函数 `_format_llm_data` 的四段式实现**，改为注释保留（第 375~420 行整段被 `#` 注释，标注"旧版 v1 — 观察+结果+统计+建议"）。
- **重写 `_format_llm_data`**（第 422~471 行）：合并"观察 + 结果"为一行，去掉"统计"段，保留"建议"。状态行模板：
  ```
  工具执行: {tool_zh} 调用工具-{tool}{,处理对象-{target}} - 执行结果: 成功/失败/完成-[有警告]
  观察: {message} - {summary}
  ```

- **error 不再追加详情段**：`format_llm_observation` 第 491~492 行，error 时 data 仅含 `error_detail + params` 原始 dict，错误信息已通过"✖ 错误 / 建议"两行完整呈现，不再追加详情段避免混淆 LLM。

## 五、核心文件改动详解

### 5.1 action_handler.py
- **`build_observation`**（第 298~426 行）：llm_data 改列表直传（第 403~404 行 `llm_data_list`），与 `_parallel_results` 索引 1:1；新增逐条 `llm_data` 日志（第 406~411 行），截断 summary 至 120 字符避免日志膨胀。
- **`_merge_llm_data` / `_merge_other_data`**（第 221~295 行）：并行场景合并逻辑保留，但单批 / 列表直传场景下优先走 `llm_data_list`，减少 merge 损耗。

## 七、风险与遗留

### 7.1 无回滚设计（禁止 backward）
依据 AGENTS.md 铁规，本版本**坚决杜绝向后兼容**：工具 `data` 字段删除后，旧前端 / 旧下游若仍读取 `data.sql` / `data.chart_type` 将得到 `KeyError` 或缺失。这是有意设计的"去冗余"代价，要求前端版本与后端同步升级。

### 7.2 builder 签名依赖
`_build_*_llm_data` 函数在多批次被反复签名调整（如 `http_request` 保留 `headers/body` 形参但不使用，`edit_text_file` `replace_all→mode`）。遗留风险：
- 形参保留但注释"防止大字段回灌"，若后续误将 `headers` 重新写入 `_act_params` 会回退到 token 浪费。需在 code review 中维持纪律。
- `diff` 在 `edit_text_file` 经 `metrics.diff[:500]`（第 256 行）截断，部分成功时 `data={"diff": ...}` 未再截断，极端长 diff 仍可能膨胀 observation（但受 formatter `_format_scalar_data` 的 `OBS_MAX_STRING_LENGTH` 二次兜底）。

### 7.3 formatter 与工具路由耦合
formatter 的 `#0`~`#23` 分支依赖工具 `data` 的 key 形态（如 `rows` 命中 `#5`、`matches` 命中 `#9`）。工具 data 去冗余时若误删 formatter 依赖的 key，会导致渲染降级到 `#21 fallback`。本版本通过"路由注释表"（各工具文件第 ~214 行 `observation_formatter route` 注释）反向锁定依赖，降低风险。

### 7.4 跨版本前端同步风险
v0.18.2 删除 `data.sql / data.chart_type / 坐标` 等键，若前端某组件仍读取这些键展示（如图表类型徽标、坐标预览），将显示空白或异常。前端（`frontend/src/`）与后端必须同版本发布；该风险已在 v0.18.3 summary 统一时一并收敛。

### 7.5 遗留技术债
- `http_request._build_http_request_llm_data` 仍保留 `headers / body` 形参（不使用），属"签名兼容占位"，长期应清理以避免误导（违反 KISS-DIRECT，但受历史调用方约束未删）。
- `edit_text_file` 的 `diff` 在 `metrics.diff[:500]` 截断，但 `data={"diff": ...}` 部分成功分支未二次截断，极端长 diff 仍可能膨胀 observation（受 formatter `OBS_MAX_STRING_LENGTH` 兜底，实际风险低）。
- formatter `#21 fallback` 36 个标量工具的 `_format_scalar_data` 仍有 `OBS_DICT_MAX_KEYS=100` 上限，工具 data 键数超 100 会被折叠，需在新增标量工具时留意。

### 7.6 监控建议
建议在 CI 中加入静态检查：扫描所有 `_build_*_llm_data` 中 `action.params` 的 `[:N]` 截断，确保 N ≤ 50；并扫描 `build_success/build_error/build_warning` 的 `data=` 实参，告警出现 `sql / chart_type / headers / body` 等已禁键名，防止回归。编写人：小欧 - 2026-07-12 21:57:29
