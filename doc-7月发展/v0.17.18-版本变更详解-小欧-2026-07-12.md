## 二、背景与目标

### 2.1 背景

v0.17.17 已把 FC 解析错误升级为 `FCFormatError` 强类型异常，并引入 L1/L2 重试体系。但在真实 LLM 调用中，仍暴露出三类问题：

1. **FC 降级 Text 模式不兜底**：当 FC 模式多次重试均因 `FCFormatError` 失败、降级到 Text 模式后，Text 模式内部若再次抛出 `FCFormatError`（理论上不应，但解析链路复杂），整个 `call_llm_with_fallback` 协程直接崩溃，前端收不到任何响应。这是一处**真实的崩溃缺口**。
2. **LLM 返回残缺/非标准 JSON**：LLM 受 system prompt 中示例影响，经常返回**单引号 Python dict 格式**（`{'key': 'value'}`）或**被截断的 JSON**（缺右括号）。原 `_try_fix_incomplete_json` 只做右括号/引号修补，对 Python dict 格式完全失效，导致大量合法工具调用被误判为解析失败。
3. **截断 JSON 静默修复无感知**：`base_service.py` 中虽能自动修复残缺 JSON 参数，但修复行为对 LLM 是"黑箱"，LLM 不知道自己返回错了、被改成了什么，下一轮仍可能重复犯错。
4. **历史裁剪逻辑混用单一预算**：原 `trim_history` 把"轮次过多"和"字符过多"两个条件耦合进同一套 `_trim_to_budget` 预算裁剪，导致轮次触发时预算被错误收紧（`_ROUND_TRIM_BUDGET=30000` 上限），裁剪结果不可预期。

### 2.2 目标

- **目标 A**：堵住 FC 降级链路的崩溃缺口，任何层级的 `FCFormatError` 都应有统一、友好的错误响应（前端可读、可重试）。
- **目标 B**：最大化 LLM 残缺/非标准 JSON 的自动修复率，且修复动作**对 LLM 可见**（注入 warning）。
- **目标 C**：将分散在 `base_service.py` 的 JSON 容错函数集中到 `json_utils.py`，落实"公共函数先查后建、禁止业务层重复"的规范。
- **目标 D**：让历史裁剪、消息注入、错误格式化收敛为单一入口，提升可维护性与可观测性。
- **目标 E**：增强控制台与 Prompt 日志，使长链路多步推理"肉眼可追"。

```python
    if FC_FALLBACK_ENABLED:
        logger.warning(f"[FC降级] FC模式{FC_MAX_RETRIES}次重试均失败，降级到Text模式")
        try:
            async for item in call_llm_stream(agent, messages, openai_tools=None):
                yield item
        except FCFormatError as e:
```

**(2) JSON 修复支持 Python dict 格式（base_service.py `_try_fix_incomplete_json`）**

LLM 在 system prompt 示例中见过大量 Python dict 写法，输出时常常写回单引号 dict。原实现仅做括号/引号修补，对 `{'a': 1}` 完全失败。新增第 1 步 `ast.literal_eval`：

Before:
```python
    s = json_str.strip()
    # 原有JSON修补策略(缺少括号/引号)
    fixes = [s, s + '"}', s + '}', s + '"', ...]
```

After:
```python
    s = json_str.strip()
    # 第1步: ast.literal_eval处理Python dict格式(单引号/True/False/None等)
    try:
        result = ast.literal_eval(s)
        if isinstance(result, dict):
            return result
    except (ValueError, SyntaxError, MemoryError):
        pass
    # 第2步: 原有JSON修补策略(缺少括号/引号)
    fixes = [s, s + '"}', s + '}', s + '"', ...]
```

> 影响：单引号 dict、`True/False/None` 字面量、无引号的 key 现在可自动还原为合法 dict，FC 工具调用成功率显著提升。注意 `import ast` 在此提交一并补入 `base_service.py`；后续 `4588a3f5b` 又把整函数迁到 `json_utils.py`（见 3.2.1）。

```python
        return
    # 两个条件都不达标 → 不裁剪
    if total < self.MAX_CONTEXT_CHARS * 0.8 and msg_count <= _MAX_ROUNDS * 2 + 2:
        return
    ...
    # 条件1: 轮次太多 → 保留最近 _MAX_ROUNDS 轮
    if msg_count > _MAX_ROUNDS * 2 + 2:
        all_fc = sorted(obs_list + assistant_msgs, key=lambda m: original_order.get(id(m), 0))
        kept_fc = all_fc[-(_MAX_ROUNDS * 2):]
        obs_list = [m for m in kept_fc if m.get("role") == "tool"]
        assistant_msgs = [m for m in kept_fc if m.get("role") == "assistant"]
    # 条件2: 字符太多 → 按预算裁(70%余量)
    if total > self.MAX_CONTEXT_CHARS * 0.8:
        always_keep_chars = self._total_chars(system_msgs) + self._total_chars(user_msgs)
        available_budget = max(0, int(self.MAX_CONTEXT_CHARS * 0.7) - always_keep_chars)
        trimmed = self._trim_to_budget(obs_list, assistant_msgs, available_budget)
    else:
        trimmed = sorted(obs_list + assistant_msgs, key=lambda m: original_order.get(id(m), 0))
```

> 关键差异：**条件1（轮次）**与**条件2（字符）**现在相互独立——轮次超了只按 `_MAX_ROUNDS*2` 截取最近 FC 对，不再被 30000 预算腰斩；字符超了才走 `_trim_to_budget` 预算裁剪。日志触发标记按 `msg_count > _MAX_ROUNDS*2+2` 区分"消息数/字符"来源。

## 四、关键技术点

### 4.1 FC 降级 Text 异常保护（崩溃缺口封堵）

原 `call_llm_with_fallback` 在 FC 重试耗尽后降级到 `call_llm_stream(..., openai_tools=None)`（Text 模式）。由于 `call_llm_stream` 内部对 `FCFormatError` 是 `raise` 而非 `yield error`，一旦 Text 分支因任何原因再次触发 `FCFormatError`，协程无捕获点直接异常上抛，前端永远收不到 `type:error` 响应。修复后降级分支被 `try/except FCFormatError` 包裹，统一走 `_yield_error_response`，保证**任何层级解析失败都有前端可读的错误闭环**。`947d651d2` 又将其文案收口到 `_format_fc_error`。

### 4.2 `_try_fix_incomplete_json` 容错三阶段

当前 `json_utils._try_fix_incomplete_json`（v1.0 最终态）的容错顺序：

1. **Python dict 阶段**：`ast.literal_eval(s)` 处理单引号、裸 key、`True/False/None` 等 LLM 常见"Python 味"输出；
2. **JSON 修补阶段**：依次尝试 `s` / `s + '"}'` / `s + '}'` / `s + '"'` / 反斜杠归一化后 `+"}"` / `+"}"`；
3. **空壳防护**：若修补出 `{}` 且原串无冒号（`":" not in s`），跳过该误修结果，避免把 `"abc"` 误修成 `{}`。

> 空壳防护在 `5bea30ed3` 由最初 `len(s) < 4`（过宽，会放过 `{}x` 之类）收紧为 `":" not in s`（语义精确），是同日一次重要的补丁式修正。

### 4.3 trim_history 双条件独立裁剪

核心收获是**解耦**：条件1 只在"轮数超 `_MAX_ROUNDS*2+2`"时按最近 N 轮 FC 对截取，不受字符预算掣肘；条件2 只在"字符超 `MAX_CONTEXT_CHARS*0.8`"时按 70% 预算从旧到新裁。二者可单独或同时触发，日志明确标注触发源，便于调参。system+user 消息永保，`_trim_fc_pairs` 保证配对完整。

## 六、风险与遗留

1. **`ast.literal_eval` 安全性**：对不可信输入理论上存在资源消耗风险（超大字符串），但输入来自 LLM 工具参数片段、量级可控；`MemoryError` 已纳入捕获，风险低。
2. **`_repair_warning` 链路较长**：warning 需经 `base_service → llm_stream → action_handler → observation` 四跳透传，任一处遗漏字段即丢失可见性；当前三处均已补齐，但后续新增 handler 须同步携带该字段（建议在 FUNCTIONS.md / 编码规范中固化）。
3. **trim_history 阈值依赖常量**：`_MAX_ROUNDS=20`、`MAX_CONTEXT_CHARS*0.8` 为经验值，极端超长单轮（如超长文件读取）仍可能触发字符裁剪导致上下文丢失，属已知权衡。
4. **控制台 `print` 与 `logger` 并存**：perf 提交引入的 `print` 用于实时可读，与结构化 `logger` 双轨；生产环境高并发下 `print` 非线程安全，建议后续评估统一改 `logger.info`。
5. **遗留**：v0.17.18 未触及 FC 重试的 L2 反压参数调优（在 v0.17.15/v0.17.17 已落地），本版本聚焦"降级兜底 + 容错 + 观测"，L2 逻辑未变。
