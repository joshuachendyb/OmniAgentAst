## 二、背景与目标

### 2.1 命名混乱现状（背景）

在 v0.18.13 之前，路径类参数的规范名在各工具中高度不统一，存在以下三类问题：

1. **目标/输出路径命名多样**：`download` 用 `destination_path`、`screen_capture` 用 `output_path`、`generate_chart` 用 `output_path`、`file` 类双路径工具用 `source_path`/`destination_path`。
2. **文件/键/库路径命名多样**：`document` 类 8 工具用 `file_name`；`win_registry` 类用 `key_path`；`query_sql`/`execute_sql`/`get_db_schema` 用 `db_path`。
3. **旧别名与规范名不一致**：早期把 `file_path`/`dir_path`/`search_dir` 等作为「规范名」，后来又把它们降级为别名，概念摇摆。

### 2.2 目标

- **统一短名**：路径类参数收敛为 `path`（单路径）与 `dest`（双路径工具的目标端）两个规范名，降低 LLM 选参歧义。
- **三处同步**：每个参数改名必须同时同步 **(a) Pydantic Schema 字段名 → (b) 工具函数形参名 → (c) `param_alias_mapper.PARAM_ALIASES` 别名映射**，避免一处漏改导致派发失败。
- **旧别名兜底**：旧规范名（file_path/dir_path/key_path/db_path/file_name…）及大众化同义词（dst/to/source/target…）统一降级为别名，保证历史 LLM 输出不失效。
- **端到端校验**：用 `verify_dispatch` 对 17 工具 / 85 别名逐条跑 `normalize_params → schema 校验`，确保全绿。

— 小欧 2026-07-12

## 三、逐项变更详解

### 3.1 download（网络类）

- **动机**：目标路径参数名 `destination_path` 过长且与其他工具不统一，统一为 `dest`。— 小欧 2026-07-12

- **参数 before → after**：
  - Schema 字段：`destination_path: Optional[str]` → `dest: Optional[str] = None`（已实测当前源码 `dest: Optional[str] = None`）

## 五、registry_write 历史 bug 修复（根因与修复）

### 5.1 根因

`param_alias_mapper.PARAM_ALIASES["registry_write"]` 早期版本将 LLM 可能返回的 `"value"` 与 `"data"` 两条别名错误地映射到 **`value_data`**：

```
# 错误（修复前）
"registry_write": {
    ...
    "value": "value_data",
    "data": "value_data",
}
```

但 `RegistryWriteInput` 的实际规范字段名为 `value`（实测 `value: Union[str, int] = Field(...)`），**根本不存在 `value_data` 字段**。这导致：当 LLM 返回 `{"value": "xxx"}` 或 `{"data": "yyy"}` 时，`normalize_params` 会把它重命名为 `value_data`，随后 schema 校验因无此字段而失败，写入操作被拒。这是一个「预存 bug」——别名指向了不存在的目标参数。— 小欧 2026-07-12

### 5.2 修复

将别名目标改为真实存在的规范名 `value`：

```
# 正确（修复后，当前态）
"registry_write": {
    "registry_key": "path",
    "reg_key": "path",
    "regpath": "path",
    "key_path": "path",
    "key": "path",
    "value": "value",
    "data": "value",
}
```

- `value→value`：同名直通（LLM 直接用 `value` 时无需映射，但保留条目保证一致性与日志可观测）
- `data→value`：旧版「数据」语义统一并入 `value` 字段
- 配合 §3.4 的 `key_path→path` 同步，registry_write 的键路径与值参数全部对齐。

### 5.3 影响

- 修复前：LLM 若用 `value`/`data` 传值，registry_write 必失败。
- 修复后：所有值别名正确映射到 `value`，schema 校验通过，写入成功。
- 该修复与 commit `fa9b18a00`（别名表 6 双路径工具别名指向旧 source/destination 导致派发失败，改指 path/dest）属同类「别名目标失真」问题，本版一并根除。

— 小欧 2026-07-12

## 六、verify_dispatch 端到端校验机制

### 6.1 定位

`verify_dispatch` 是本版开发期使用的**临时端到端校验脚本**（工作区临时文件，未在 git 提交，后于「文档/清理」阶段随 `_audit_path`/`check_downstream`/`scan_path_leak`/`scan_write_success` 一并删除）。其职责是：对本次改名的 17 工具 / 85 别名，验证「别名输入 → normalize_params → schema 校验」链路全绿。— 小欧 2026-07-12

### 6.2 校验原理（基于真实代码还原）

校验依赖两条真实代码路径：

1. **`normalize_params(tool_name, params)`**（`param_alias_mapper.py:328`）
   - 入参：工具名 + LLM 风格参数字典
   - 逻辑：遍历 `params`，若 `key` 命中 `PARAM_ALIASES[tool_name]`，则替换为规范名；若规范名已存在则忽略别名（避免覆盖）；返回 `(normalized, has_mapping)`
   - 随后做参数值别名映射（`PARAM_VALUE_ALIASES`，如 grep 的 `files_with_matches→only_files`）
2. **Schema 校验**：归一化后的参数字典喂给各工具 Pydantic `Input` 类（`document_schema.py` / `network_schema.py` / `desktop_schema.py` / `dataanalysis_schema.py` / `win_registry_schema.py`），若 `ValidationError` 即判红。

### 6.3 校验流程（伪逻辑，还原脚本意图）

```
for tool in 17工具:
    for alias_key, canonical in PARAM_ALIASES[tool].items():
        input_params = {alias_key: "测试值"}          # 用别名作 key
        normalized, mapped = normalize_params(tool, input_params)
        assert normalized.get(canonical) is not None  # 别名已归一到规范名
        try:
            SchemaClass(**normalized)                  # 跑 schema 校验
            print(f"[GREEN] {tool}: {alias_key}→{canonical}")
        except ValidationError as e:
            print(f"[RED]   {tool}: {alias_key}→{canonical} -> {e}")
assert 全部 GREEN
```

### 6.4 校验结论

- 17 工具 / 85 别名映射经 `normalize_params → schema` 全绿（version.txt 记录：「端到端校验 verify_dispatch：17工具/85条别名映射 normalize_params→schema 全绿」）。
- 关键护栏：§5 的 `registry_write` 别名失真修复、§3.3 的 `generate_chart.path→data` 反向特例，均在本次校验中被覆盖，确保不会把「输出路径别名」误送入「数据字段」。

— 小欧 2026-07-12

## 八、风险与遗留

### 8.1 三处同步风险（最高优先级）

路径改名的核心风险在于 **Schema 字段名、函数形参名、别名映射** 三处必须同步。任一处遗漏即导致：
- 别名未同步 → LLM 旧参数名无法归一 → schema 拒收
- 函数形参未同步 → `normalize_params` 归一成功但函数收不到值
- Schema 未同步 → 归一后字段仍不被接受

本版通过 `verify_dispatch` 全绿已验证 17 工具无遗漏，但**新增工具若再用路径参数，必须同步三处**，否则会重蹈 `registry_write.value_data` 覆辙。

### 8.2 别名语义特例风险

`generate_chart.path→data` 与 `screen_capture.path→dest` 同名不同向，属「按工具独立配置」的合理设计，但后续维护者若误将 `generate_chart` 的 `path` 当成输出路径，会写错文件。建议在别名表注释中明确标注（当前 `param_alias_mapper.py:240` 已有注释）。

### 8.3 遗留

- `registry_path_checker._normalize_key_path(key_path, hive)` 内部局部变量名仍为 `key_path`，与对外 `path` 不冲突（局部变量），但命名风格未完全统一，留待后续清理。
- 临时校验脚本 `verify_dispatch` 已删除，建议将 §六 的校验逻辑沉淀为常驻 pytest 用例，防止未来回归（本版未沉淀，属遗留项）。
