## 二、背景与目标

### 2.1 回收站容量治理（feat 动机）

v0.18.0 之前的回收站（`~/.omniagent/recycle_bin`）仅按 `BACKUP_RETENTION_DAYS=30` 的时间窗做过期清理，由 `cleanup_expired_backups()` 根据 `file_operations.backup_expires_at` 字段删除过期备份。该机制存在两个容量治理盲点：— 小欧-2026-07-12

1. **时间窗过长**：30 天保留期在大文件高频编辑场景下，回收站会无限膨胀，占用系统盘空间。
2. **无大小上限**：仅按时间清理，无法约束总量；若用户在 30 天内大量备份大文件，磁盘会被写满。

v0.18.1 引入 **「时间窗 + 大小上限」双保险**：保留期从 30 天收紧到 5 天，并新增 `RECYCLE_BIN_MAX_SIZE_GB=10` 硬上限，超上限时按目录名（即时间戳前缀）升序从最旧备份开始删除，直至回落到上限内。— 小欧-2026-07-12

### 2.2 LLM data 裁剪起步（refactor 动机）

v0.18.0 完成了 166 个质量问题修复与全量 llm_data 重构，但工具回传给 LLM 的 `llm_data.action` 参数里仍携带 `data`/`conditions`/`headers`/`body` 等大字段，以及 `sql`/`message` 等长文本（截断 200 字符）。这些字段对 LLM 决策无价值，反而挤占上下文。— 小欧-2026-07-12

v0.18.1 作为 **「LLM data 字段裁剪 + 50 字符截断统一」的起点**：挑选数据分析和网络 8 个高字段体积工具先行裁剪，截断阈值从 200 统一收敛到 50。这套规则在后续 v0.18.2 被扩展到全部 163 个工具。— 小欧-2026-07-12

### 2.3 promptlog 与错误处理一致性（fix 动机）

- promptlog 记录的 observation 内容，此前用的是 `result.get("message")` 原始字段，与真实喂给 LLM 的格式化文本不一致，导致复盘时无法还原 LLM 视角。
- 6 个工具的错误分支此前只构造了 `llm_data` 但未 `return build_error(...)`，存在「构造了错误信息却返回默认成功字典」的隐患；部分 hint 重复（先设 hint 再赋值覆盖）。— 小欧-2026-07-12

#### 3.1.2 operation_cleanup 新增大小清理能力

`backend/app/services/safety/operation_cleanup.py` 新增两个函数：`_get_folder_size()` 递归统计文件夹字节数；`_cleanup_by_size()` 超上限时按目录名升序删最旧备份。— 小欧-2026-07-12

```python
def _get_folder_size(path: Path) -> int:
    """递归计算文件夹总字节数"""
    total = 0
    try:
        for entry in path.rglob("*"):
            if entry.is_file():
                total += entry.stat().st_size
    except Exception:
        pass
    return total


def _cleanup_by_size() -> int:
    """总大小超过上限时，从最旧的备份开始删"""
    from app.tools.file.delete_file import remove_readonly
    from app.services.safety.operation_executor import FileSafetyConfig
    config = FileSafetyConfig()
    max_bytes = config.RECYCLE_BIN_MAX_SIZE_GB * 1024 ** 3
    recycle_path = config.RECYCLE_BIN_PATH
    if not recycle_path.exists():
        return 0
    total = _get_folder_size(recycle_path)
    if total <= max_bytes:
        return 0
    folders = sorted(
        [p for p in recycle_path.iterdir() if p.is_dir()],
        key=lambda p: p.name,           # 目录名含时间戳前缀，升序=最旧优先
    )
    count = 0
    for folder in folders:
        if total <= max_bytes:
            break
        try:
            folder_size = _get_folder_size(folder)
            shutil.rmtree(folder, onerror=remove_readonly)  # onerror 解决 Windows 只读文件锁
            total -= folder_size
            count += 1
            logger.info(f"Size cleanup: removed {folder.name} (saved {folder_size / 1024**3:.2f}GB)")
        except Exception as e:
            logger.error(f"Failed to size-cleanup {folder}: {e}")
    return count
```

**关键技术点**：目录名形如 `{timestamp}_{uuid8}`，`sorted(key=p.name)` 即按时间戳升序，实现「最旧优先淘汰」；`shutil.rmtree(onerror=remove_readonly)` 规避 Windows 下 copy2 备份后只读属性导致的 `[WinError 5]` 删除失败。— 小欧-2026-07-12

#### 3.1.4 operation_executor 每次备份后触发

`backup_to_recycle_bin()` 在 `shutil.copy2/copytree` 成功后，立即调用 `cleanup_expired_backups()`，使「备份即治理」——每次产生新备份都会同步触发过期 + 超限清理：— 小欧-2026-07-12

`backend/app/services/safety/operation_executor.py:39-56`

```python
def backup_to_recycle_bin(source_path: Path) -> Optional[Path]:
    """备份文件到回收站"""
    config = FileSafetyConfig()
    try:
        timestamp = timestamp_for_filename()
        backup_dir = config.RECYCLE_BIN_PATH / f"{timestamp}_{uuid4().hex[:8]}"
        backup_dir.mkdir(parents=True, exist_ok=True)
        backup_path = backup_dir / source_path.name
        if source_path.is_dir():
            shutil.copytree(source_path, backup_path)
        else:
            shutil.copy2(source_path, backup_path)
        logger.info(f"File backed up to recycle bin: {source_path} -> {backup_path}")
        cleanup_expired_backups()   # ← v0.18.1：每次备份后调用
        return backup_path
    except Exception as e:
        logger.error(f"Failed to backup file to recycle bin: {e}")
        return None
```

同时，备份过期时间写入改用新常量：`backup_expires_at = datetime.now() + timedelta(days=config.BACKUP_RETENTION_DAYS)`（`operation_executor.py:113`），保留期随之从 30 天变为 5 天。— 小欧-2026-07-12

**影响**：回收站体积受「5 天 + 10GB」双重约束，磁盘占用可预期；代价是误删文件的可恢复窗口从 30 天缩短到 5 天（见第六章风险）。— 小欧-2026-07-12

## 四、关键技术点

### 4.1 回收站大小上限自动清理算法

- **计算口径**：`_get_folder_size()` 用 `path.rglob("*")` 递归累加 `entry.stat().st_size`，仅统计文件（目录本身不计）。
- **淘汰顺序**：`recycle_path.iterdir()` 过滤目录后按 `p.name` 升序；因目录名前缀为 `timestamp_for_filename()` 生成的时间戳，升序即「最旧优先」。
- **循环退出**：每删一个文件夹后 `total -= folder_size`，一旦 `total <= max_bytes` 立即 `break`，最小代价回落到上限内。
- **Windows 兼容**：`shutil.rmtree(folder, onerror=remove_readonly)`，`remove_readonly` 来自 `app.tools.file.delete_file`，清除只读位后重试删除，规避 `[WinError 5]`。— 小欧-2026-07-12

### 4.2 LLM data 50 字符截断起点

v0.18.1 将 `sql`/`message`/`old_string`/`new_string` 的截断阈值从 200 收敛到 50。这一阈值成为后续 v0.18.2 全量 163 工具统一的基线（见 `observation_formatter.py:80` 注释「截断统一50字符」）。`diff` 字段单独保留 500 字符（因为它承载编辑前后差异，对 LLM 定位改动有价值）。— 小欧-2026-07-12

### 4.3 截断双层模型

observation 文本的最终长度由「工具层截断（机器一）」与「formatter 层截断（机器二，`OBS_MAX_STRING_LENGTH=10000` 等）」共同决定，取先到先得。v0.18.1 的 50 字符裁剪发生在「机器一」（llm_data.action 参数），与 formatter 的 data 展示截断相互独立、互不冲突。— 小欧-2026-07-12

## 六、风险与遗留

### 6.1 风险

1. **可恢复窗口缩短**：保留期 30→5 天，误删文件的可恢复时间从一个月缩到 5 天，需用户认知到位。— 小欧-2026-07-12
2. **大小清理的目录名依赖**：`_cleanup_by_size` 强依赖目录名的时间戳前缀排序；若历史备份目录被手工改名，排序将失真（但正常路径由 `backup_to_recycle_bin` 统一生成，风险可控）。
3. **diff 截断 500**：超长 diff 在 llm_data 中被截断，极端大文件多处编辑时 LLM 可能看不到完整差异（完整 diff 仍存 `data`，前端可查）。— 小欧-2026-07-12

### 6.2 遗留

- 8 工具裁剪仅为起点，剩余 155 个工具的同类大字段/长文本裁剪在 **v0.18.2** 全量完成（见第七章）。
- `RECYCLE_BIN_MAX_SIZE_GB` 当前为硬编码常量，未接入 `config/config.yaml` 环境变量覆盖（与 `BACKUP_RETENTION_DAYS` 同为类属性）。— 小欧-2026-07-12
