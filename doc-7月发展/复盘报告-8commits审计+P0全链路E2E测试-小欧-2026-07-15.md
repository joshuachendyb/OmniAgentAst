## 4 发现的问题

### 4.1 问题描述：`check_logs` 时间过滤微秒精度不匹配

**表现**：P0-01 和 P0-13 首次运行时在 `assert lc["session_records_found"]` 处失败，断言日志应有 session 操作记录。

**调试过程**：
1. 添加 `_debug_raw_lines` / `_debug_filtered_lines` / `_debug_session_in_raw` / `_debug_session_in_filtered` 四个诊断字段
2. P0-13 复现失败，输出为：
   - `session_in_raw=True` — session_id 确实在原始日志中 ✅
   - `session_in_filtered=False` — session_id 不在时间过滤后的内容中 ❌
   - 定位到时间过滤环节

**根因分析**：
```
日志时间戳: strptime("10:29:46", "%H:%M:%S") → 10:29:46.000000  (微秒=0)
test_start:  datetime.now()                       → 10:29:46.500000  (微秒=500000)

比较: 10:29:46.000000 >= 10:29:46.500000  →  False  ❌
```
- 日志只有**秒级精度**（`%H:%M:%S` 格式）
- `datetime.now()` 有**微秒级精度**
- 同秒内日志行因微秒值小于 `start_time` 的微秒值而被错误过滤掉

**修复方案**：
```python
start_time_sec = start_time.replace(microsecond=0)
```
将筛选阈值截断到秒级精度，与日志精度对齐。

## 5 经验教训

### 5.1 精度对齐原则

| 场景 | 核心要求 |
|------|---------|
| 日志时间戳比较 | 两边精度必须一致，高精度不要直接跟低精度比 |
| 微秒 vs 秒 | 截断到低精度方（日志只有秒就用秒） |
| 毫秒 vs 微秒 | 截断或四舍五入到公共精度 |

### 5.2 测试诊断原则

- E2E 测试断言失败时，必须能直达根因
- `session_records_found` 断言加上 `_debug_*` 字段输出，避免盲猜
- SHOULD 级检查也要保诊断信息

### 5.3 E2E 测试执行要点

- 一次一个 case，禁止批量（已遵守）
- 真实 LLM + 真实后端 + 真实工具（已遵守）
- 失败必须排查根因，不能重复跑等运气（本次做到了）
