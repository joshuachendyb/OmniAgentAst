# 多线程与异步编程详解对比

下面从核心概念、工作原理、适用场景三个维度展开，最后各附一个可运行的 Python 代码示例。

## 一、核心概念

**1. 多线程（Multithreading）**

多线程是在同一进程中创建多个执行流（线程），每个线程拥有独立的调用栈、寄存器状态和程序计数器，但共享进程的堆内存、全局变量和已打开的文件描述符。它强调的是"多个执行体同时（或交替）占用 CPU 干活"，是一种**并行的执行模型**。典型实现有 pthread、Java 的 Thread、Python 的 `threading` 模块等。

**2. 异步编程（Asynchronous Programming）**

异步编程是一种 **I/O 与流程编排模型**，其核心不是"同时跑多少个执行体"，而是"遇到耗时等待（如网络请求、磁盘读写）时，主动把控制权交还给调度器，先去干别的活，等等待事件完成后再回来继续"。它通常配合事件循环（Event Loop）、回调（Callback）、Future/Promise、协程（Coroutine）等机制实现，代表有 Node.js 的 libuv、Python 的 asyncio、Go 的 goroutine+channel。

两者的关系常被误解：异步 ≠ 并发，并发 ≠ 并行；多线程可以承载异步代码，异步也可以运行在单线程上（如 Node.js）。

---

## 二、工作原理

| 维度 | 多线程 | 异步编程 |
|---|---|---|
| 调度主体 | 操作系统内核（线程调度器） | 用户态事件循环（如 epoll / io_uring / kqueue） |
| 切换触发 | 时间片轮转、系统调用阻塞、主动让出 | I/O 就绪事件、显式 `await`/yield |
| 切换成本 | 高（线程上下文切换涉及内核态、栈切换、缓存失效，约几微秒） | 低（协程切换仅保存/恢复少量寄存器，几纳秒） |
| 阻塞影响 | 一个线程阻塞只影响自己，其他线程不受影响 | 阻塞调用会卡住整个事件循环，所有任务都停摆 |
| 资源占用 | 每线程约 1–8 MB 栈空间，线程数受限（通常几千级别） | 每协程约几 KB，可轻松承载数十万级并发任务 |
| 编程复杂度 | 低（同步写代码，直觉友好） | 高（需处理状态机、回调地狱、协程传染） |
| 并发正确性 | 需处理竞态、死锁、锁粒度、内存可见性 | 单线程异步天然无竞态，但需处理异常传播与任务取消 |
| 对 CPU 的利用 | 真并行，可利用多核 | 单线程只能串行执行 CPU 密集代码，无法利用多核 |

一句话总结：**多线程靠"多个人干多件事"解决阻塞；异步靠"一个人干一件事但绝不空等"解决阻塞。**

---

## 三、适用场景

**适合多线程的场景：**
- CPU 密集型任务：图像处理、数值计算、密码学、渲染、视频编解码。这类任务无法通过"等待 I/O"来缓解，必须靠多核并行。
- 需要利用多核硬件，且任务可自然切分。
- 与 C/C++/Fortran 等只能写同步代码的第三方库交互（如 OpenCV、NumPy BLAS、商业 SDK）。
- 实时性要求相对宽松的后台任务，且能容忍锁带来的复杂性。

**适合异步编程的场景：**
- I/O 密集型任务：高并发 Web 服务、API 聚合、爬虫、聊天服务器、数据库连接池、RPC 网关。
- 并发量极大（数万级）但单任务计算量小的场景，如即时通信、行情推送。
- 需要精细控制资源、避免线程爆炸的长连接服务。
- 前后端交互、事件驱动型系统（前端 Event Loop、Node.js 微服务）。

**典型反例：**
- 用多线程做 10 万个 HTTP GET → 线程数爆炸，上下文切换开销吃掉全部收益。
- 用 asyncio 做图像卷积 → 事件循环被 CPU 卡死，其他请求全部超时。
- 正确做法：I/O 密集用异步，CPU 密集用多线程/多进程，混合场景可用"线程池 + 异步事件循环"的桥接（如 `asyncio.to_thread` 或 `run_in_executor`）。

## 四、代码示例

**示例 A：多线程（CPU 密集型 —— 计算多个大质数）**

~~~python
import threading
import time
from concurrent.futures import ThreadPoolExecutor

def is_prime(n: int) -> bool:
    """简单的质数判定，纯 CPU 计算"""
    if n < 2:
        return False
    for i in range(2, int(n ** 0.5) + 1):
        if n % i == 0:
            return False
    return True

def worker(n, results, idx):
    results[idx] = is_prime(n)          # 计算阻塞在这里，但其他线程不受影响

nums = [9999991, 9999973, 9999961, 9999937]
results = [None] * len(nums)

t0 = time.perf_counter()
with ThreadPoolExecutor(max_workers=4) as pool:
    for i, n in enumerate(nums):
        threading.Thread(target=worker, args=(n, results, i)).start()
        pool.submit(lambda: None)        # 仅为演示结构，实际用上面 Thread
# 更规范的写法：
with ThreadPoolExecutor(max_workers=4) as pool:
    futs = [pool.submit(is_prime, n) for n in nums]
    for n, f in zip(nums, futs):
        print(n, "->", f.result())

print("多线程总耗时:", round(time.perf_counter() - t0, 3), "s")
~~~
要点：4 个线程在 4 个 CPU 核上真正并行计算；Python 因 GIL 限制，CPU 密集场景建议改用 `multiprocessing` 或 `ProcessPoolExecutor`。

**示例 B：异步编程（I/O 密集型 —— 并发抓取多个网页）**

~~~python
import asyncio
import time
import aiohttp

URLS = [
    "https://httpbin.org/delay/1",
    "https://httpbin.org/delay/1",
    "https://httpbin.org/delay/1",
    "https://httpbin.org/delay/1",
]

async def fetch(session: aiohttp.ClientSession, url: str):
    # await 处，事件循环会切换到其他任务，而不是阻塞整个线程
    start = time.perf_counter()
    async with session.get(url) as resp:
        data = await resp.json()
        return url, round(time.perf_counter() - start, 2)

async def main():
    t0 = time.perf_counter()
    async with aiohttp.ClientSession() as session:
        # gather 同时驱动所有协程，共享一个线程和一个事件循环
        results = await asyncio.gather(*(fetch(session, u) for u in URLS))
    for url, dt in results:
        print(url, "耗时", dt, "s")
    print("异步总耗时:", round(time.perf_counter() - t0, 2), "s")

asyncio.run(main())
~~~
要点：4 个请求总耗时约 1 秒（而不是 4 秒），因为只有一个线程，但它在 4 个 I/O 等待之间来回切换——**用 1 个线程获得了 4 路并发**。若要并发 10 万个请求，改异步只需几 MB 内存，改多线程会因线程栈耗尽而崩溃。

## 五、选型速查

1. 任务主要是**等**（网络、磁盘、超时）→ 优先**异步**。
2. 任务主要是**算**（CPU 打满）→ 优先**多线程/多进程**，并让线程数 ≤ CPU 核数。
3. 两者混合 → 异步框架里用 `to_thread` / `run_in_executor` / `process_pool` 把 CPU 任务丢到线程或进程池。
4. 需要严格吞吐 SLA、且并发量不大（< 几百）→ 多线程更简单稳妥。
5. 高并发长连接服务（< 10 万连接）→ 异步几乎是唯一合理选择。

**记住一句口诀：CPU 密集用线/进程，I/O 密集用异步，混合场景做桥接。**
