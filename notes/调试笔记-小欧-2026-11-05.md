## 一、背景与方式

按设计文档 `[11]第三方CLI模型接入网关技术方案` v6.8 §9.1–§9.6 落盘实施:
通用层 `gateways\`（七文件零方言）+ 驱动层 `gateways\vendor\opencode\`（driver +
opencode_client v1.1 入库）。落盘方式为**从文档代码围栏逐字抽取**（extract_v68.py）,
未人工转录。冒烟环境: `E:\Appsw\python31311\python.exe`（fastapi 0.136.1 /
httpx 0.26.0 / uvicorn, 与后端同款）; 下游 `runtime\opencode-cli.exe` 版本
`opencode v2.2.0`（在兼容区间 >=2.2.0 <2.3.0）。

冒烟三段（smoke.py）+ 流式补测（smoke_stream.py）最终全绿:
- `GET /healthz` → 200（status=ok, cli=up, 池 2 实例, driver_version=2.2.0）
- `GET /v1/models` → 200（三关准入全过, 9 个免费层模型）
- `POST /v1/chat/completions` stream=0 → 200（big-pickle 回答"可用", usage 全）
- `POST /v1/chat/completions` stream=1 → 200（SSE: 角色帧 → 增量帧 → 末帧 → [DONE]）

## 三、遗留观察项（记档, 未改代码）

1. **上游心跳缺失**: `streamer.sse_comment()` 定义了但无人调用——文档 4.5 的
   ": ping" 15 s 心跳当前不产生。已提交后若模型思考超过宿主读超时会有断流风险
   （网关 aclient read=60 s 靠下游 heartbeat 保活; 宿主侧读超时由 ai.opencli.timeout=900 兜底）。
2. **on_event DeprecationWarning**: FastAPI 的 on_event 弃用警告系文档原样代码, 外观性, 保留。
3. **免费层外部依赖**: E2E 依赖 opencode 远端免费额度, 429 free-limit 走 R5 冷却为内建语义。
4. `restart_backoff`（R7）在首启失败转失败-重启链路时观察到 60 s 退避, 属设计内行为。
5. **big-pickle 自身 tool-call 标记泄漏（2026-11-05 11:55 北京老陈实测定性, 非网关缺陷）**:
   模型偶发把自家原生工具调用标记（`<｜DSML｜>` 包裹的 JSON `name:bash+arguments`）混在正文里输出,
   网关按 5.5 降级为纯文本透传（设计内）。用户对照实验: **opencode 桌面直连同一模型同样出现**,
   与网关转发/协议/鉴权无关, 属免费层 agentic 模型自带行为。验收撞到按重试处置, 不记网关 FAIL;
   若要观感清洗（剥除泄漏标记）属新功能, 动 5.5 规格, 待用户拍板另立项。

## 五、追加: 工具循环与标记泄漏的根因闭环（2026-11-05 12:41:00, 小欧）

### 5.1 三条现象

1. 宿主 UI 看不到流式 chunk（正文一次整段出现，或干脆没有正文块）。
2. 工具调用标记泄漏比 opencode 桌面直连时更频繁，正文里夹着 `<tool_call>` 或 `<|DSML|>` 原文。
3. 让模型做"改文档"这类有写操作的任务时，它反复调用 bash / grep / read，从不写文件，看起来像死循环。

### 5.2 取证方式与原始证据

只读打开下游 CLI 的会话库 `%LOCALAPPDATA%\opencli-gateway\xdg\data\i0\opencode\opencode.db`，导出近 71 条消息逐条比对（脚本 `%TEMP%\opencode\db_scan.py`、`db_timeline.py`，均只读，不改库）。

命中计数：`<tool_call>` 出现在 6 条消息里，`No tool named` 7 条，`Permission denied` 5 条，`external_directory` 4 条，`DSML` 1 条。

assistant 消息里的 tool 部件错误原文为 `No tool named "bash"`、`No tool named "grep"`、`No tool named "write"`；被拒绝的路径错误为 `Permission denied: external_directory`。

最关键的一条是模型自己的推理原文：

> It keeps interpreting any `<tool_call>` as a platform tool call.

这句话说明模型确实把 `<tool_call>` 当成了平台级工具调用语法；但后续源码核对证明，真正被 CLI 执行的是它以原生 `tool_calls` 发出的那一份，正文里的文本块只是同一意图的残留。

### 5.3 根因（三条彼此独立，不能合并处理）

[1] 协议示例教了 CLI 的工具名，模型据此发出原生调用（v1.3 按 CLI 源码改判）。网关 5.2 教模型输出 `<tool_call>{"name":"bash",...}</tool_call>`，模型把示例里的 bash / grep / write 当成可调用的内置工具，直接以原生 `tool_calls` 发给下游。opencode CLI 并不解析正文里的文本调用块（v2.2.0 的 `packages/**/*.ts` 搜索 `<tool_call>`、`tool_use>`、`invoke name=` 均无匹配），它只执行 provider 返回的原生 `tool_calls`；按名查找不到同名工具，就回灌 `No tool named ...`，模型再换一个名字重试。这是"泄漏比桌面直连更频繁"和"调用拿不到"共同的主因。v1.2 原写的"CLI 自带文本解析器、界符同名被截获"不成立。

[2] 下游是 agent 程序，自带工具并自跑多轮。即使会话权限写了 `deny *`，那只是拒绝执行，工具清单仍然摆在模型面前，于是它调一次失败一次、换个工具再试；CLI 默认 build agent 还会自己跑多轮 ReAct。网关要的"一次纯文本补全"被夹在中间，单轮 completion 冲到 6000–18201 token，耗时 82–110 s。

[3] 流式层三处实现缺陷。`_frames` 对空文本也发帧（思考模型的 reasoning 帧被误当空 delta）；`_stream_tools` 把整段正文一帧发出，不符合 5.6 的 200–400 字/帧；请求日志的 `stream=` 是硬编码常量 0，纯文本流式链路没有请求日志，排障时据此误判"宿主没要流式"。

附带一条环境事实：下游沙箱权限拒绝 `F:\`，模型连待改文档都读不到，自然不会写。这是"只读不写"的放大器，不是主因。

### 5.4 修复（对应设计文档 9.1.10.2）

FIX L，`gateways\fc.py`：界符改为 `<<<OPENCLI_CALL>>>` 与 `<<<END_OPENCLI_CALL>>>`，旧界符保留解析兼容；协议头改口径为"只能输出文字，不能执行命令、不能读写文件、不能调用任何内置工具"。

FIX M，`gateways\vendor\opencode\driver.py`：在隔离 XDG 配置中注册无工具 agent `opencli-plain`（`tools: {"*": false}` 加 `permission: {"*": "deny"}`），建会话时钉死 `agent` 字段。试过 `steps: 1`，会触发 CLI 注入 "CRITICAL - MAXIMUM STEPS REACHED" 并把正文挤没，已撤掉。

FIX N，`gateways\gateway.py`：空 delta 不发帧且不占 ordinal；工具模式按 300 字/帧切分；日志按实际 `stream` 值输出；纯文本流式补请求日志。

改动前备份在 `gateways\backup\20261105_before_fix_lm\`（fc.py / driver.py / gateway.py / vendor\driver.py，注意两个 driver.py 分目录存放，不能平铺，否则同名覆盖）。

### 5.5 修复前后实测

工具模式单次请求的 completion token：修复前 6000 / 6766 / 18201，修复后 33 / 67 / 72 / 92 / 97。A7 单工具用例 2.1 s。

纯文本流式：修复后 8 个 content 块、总 2.2 s、无空帧；日志出现 `stream=1` 的正确记录。

端到端"读文件 → 三处替换 → 写文件"：4 轮收敛，读 2.4 s、写 2.6 s、补写 5.2 s、收尾 3.4 s，合计 13.6 s，落盘内容 `第一行：香蕉很好吃。…` 逐字正确。修复前同类任务会空转几十秒且不落笔。

回归：A+C+D+E 快速套件 12 过 0 败 3 跳。

### 5.6 对 §三 第 5 条的补充说明

§三 第 5 条把标记泄漏定性为"模型自带行为、非网关缺陷"，这一条在"模型本身确实会自发输出原生标记"的意义上仍然成立，不删除。但本次取证补上了缺失的一半：网关在协议示例里直接给出了 bash / grep / write 这些下游工具名，模型照着以原生 `tool_calls` 发出，是"网关模式下泄漏与失败更频繁"的直接放大器。结论修正为——模型行为是内因，协议示例给出的工具名是外因，两者叠加才出现验收看到的频率。外因已由 FIX L 改为私有界符与"不能调用任何内置工具"的措辞来降低诱因（注意：这只是降低诱因，不是解除抢执行，CLI 从未解析正文文本块），内因仍需按 5.5 降级透传处理。

## 六、追加: CLI 源码核对与开关实验（2026-11-05 13:11:58, 小欧）

### 6.1 方式

用户明确要求"不能只看 API 说明，必须查 CLI 源码"。为此克隆 opencode CLI 源码 tag v2.2.0 到 `%TEMP%\opencode\oc-src`，逐处核对 `packages/core/src` 的工具注册、权限过滤与会话上下文；再用本地假模型（`%TEMP%\opencode\mock_llm.py`，监听 127.0.0.1:28998）在隔离 XDG 目录下跑开关矩阵，记录 CLI 发给上游的真实请求体。全程未消耗真实额度。

脚本：`exp_decl.py`（声明式开关矩阵 r1–r3、s3–s5）、`exp_mock.py`（m1–m9，含原生 tool_calls）、`exp_session.py`（复刻网关会话路径）、`exp_agentdump.py`（打印 CLI 眼里的 agent 权限）。

### 6.2 六项结论

[1] CLI 不解析正文里的文本调用块。在 `packages/**/*.ts` 搜索 `<tool_call>`、`tool_use>`、`invoke name=` 无匹配；工具执行入口只接受 provider 返回的原生 `tool_calls`（`No tool named` 的唯一来源是 `packages/core/src/tool.ts` 第 315–317 行）。实验：build agent 有 12 个工具时，正文里的 `<tool_call>{"name":"shell",...}</tool_call>` 仍原样保留，没有 `tool_use` 事件。

[2] 原生调用的名称不匹配会触发重试循环。假模型发 name=bash 的原生调用后，CLI 执行失败，把 `No tool named "bash" is currently available.` 作为 tool 结果回灌，再次请求模型；持续返回原生调用时循环不终止（首次 240 s 超时），改成只发一次后 1.4 s 收敛。日志里能看到 assistant 的 `tool_calls` 与随后的 `tool` 消息原文。

[3] agent 级 `deny *` 摘不掉 `skill`，会话级可以。`packages/core/src/tool.ts` 的 `whollyDisabled()`（326–329 行）只按 action 找最后一条规则，再要求 resource 为 `*` 且 deny；内置 `{action:"skill", resource:"browser", effect:"deny"}`（`plugin/agent.ts` 81–93 行）排在 `deny *` 之后，findLast 命中它但 resource 不是 `*`，skill 因此幸存。实测：agent 配 `deny *`（或只配 `tools:{"*":false}`，或两者都配）时上游仍有 1 个 `skill`；会话 `permissions` 传 `deny *` 时上游 0 个工具；传 `deny *` 加 `allow read Z:/nope/*` 时只剩 `read`。

[4] 模型级工具开关无效。`capabilities.tools=false`、`tool_call=false`、`body.tool_choice="none"` 都没有改变上游 tools 清单；v2 形状写错时 CLI 直接报 `provider.no-route`，请求没发出去。

[5] `generate/text` 在免费层不可用。该接口请求只有 `prompt` 与 `model`，响应只有 `{data:{text}}`，不走 session 与 agent；对假模型可用（1 次上游请求、无 tools），对 opencode 免费模型返回 429 `provider.free-limit`，而同一时刻会话路径可正常返回。

[6] 当前取舍。保留 FIX M 的两层钉死（agent 无工具 + 会话 `deny *`），保留 FIX L 的私有界符作为降低诱因的措辞手段；不引入 `generate/text`，不做模型级开关。

### 6.3 对已有结论的影响

§5.3 第 1 条与 §5.6 已按本节改判：真正被 CLI 执行的是模型以原生 `tool_calls` 发出的调用，正文文本块不参与执行；界符改动的作用从"解除抢执行"降级为"降低模型照抄旧标记的诱因"。FIX M 的有效性不变，但依据更精确：会话级 `deny *` 才是把工具清单清零的那一刀，agent 级单独使用会漏 `skill`。
