## 三、发现的问题

### 3.1 公网产物在当前机器不可达（环境限制，附带前端健壮性不足）
agnes COS 域名 `cos-platform-outputs.agnes-ai.cn` 直连与本机 7890 代理均 `net::ERR_CONNECTION_CLOSED`。浏览器里所有公网产物卡片 `<img>`/`<video>` 显示空白（naturalWidth=0），只剩"查看/下载"链接。前端 `GeneratedMediaView` 与 `GenerationResultCard` 对 `<img>`/`<video>` 未设 onError 降级，加载失败时无明确提示。属环境限制，但前端缺少加载失败提示是可改进的健壮性点。

### 3.2 LLM 在最终回复里粘贴了产物 URL（规范遵从问题，非代码逻辑）
工具描述明确要求成功后"不要粘贴 URL、不要写 markdown 链接"。t2v 成功回复里仍明文写出 `产物URL：https://cos-platform-outputs...mp4`；t2i 那次则正确未贴。属模型遵从不稳定，非生成链路代码错误。

### 3.3 question 工具阻塞 94.8 秒 + 大 base64 落入步骤记录（agent 行为/机制隐患）
b64 落盘任务中，LLM 自行调 readmedia 读出 903KB base64 后，又调 question 工具等待用户确认，阻塞 94.8s 才返回；该 903KB base64 随之落入 chat_task_steps.step_json。经复核：生成链路本身的 data/llm_data/other_data 干净（见 3.2 节 PASS），此现象由测试提示词"把 base64 落盘为本地附件"诱导 + question 工具的等待机制共同造成，是无人值守自动化生成场景的隐患。

### 3.4 每次生成前 LLM 需 searchtool 1~3 次才发现生成工具（性能）
t2i 任务 7 步中 2 步为 searchtool，t2v 首轮 2 次、失败分支 1 次。增加延迟与 token 消耗，非功能错误。

## 四、未覆盖分支与外部限制

- 多图合成 images、视频 i2v/reference 与 keyframe(first_frame/last_frame) 模式：本次未逐一真机发起。
- sensenova 方言（size 档位换算、多图数组、只返 b64 落盘）：因 sensenova 端点 network_error 未能真机验证，仅完成代码契约核对。
- 本地附件 blob 浮层预览：浮层关闭即回收 objectURL（当天设计），未截到图；network 日志证实 raw 接口 200 且 blob URL 创建成功。

## 五、结论

当天生图生视频功能的主要分支真机验证通过，三态语义、产物落点、b64 防泄漏、前端三处呈现均符合当天设计，未发现生成链路的功能性代码错误。挖出的问题集中在：公网产物不可达时的前端降级提示缺失（3.1）、LLM 规范遵从不稳定（3.2）、question 阻塞与大 base64 落步骤记录（3.3）、工具发现开销（3.4），其中 3.1/3.3 值得后续改进。sensenova 方言与视频多模式受外部网络/时间限制未真机覆盖。

## 六、补充排查：图片为何渲染不出来（2026-11-22 04:21:55，小健）

### 6.1 agnes 公网图渲染失败——根因是网络 TLS 层，非代码
- DNS 正常（`agnes-ai.cn` → 腾讯云 COS 南京 `119.45.110.19`），TCP 443 连通。
- `curl -v` 实测：无论经 `127.0.0.1:18080` 代理还是直连，TLS 握手均 `schannel: failed to receive handshake`——连上后收不到服务端 TLS 响应。
- 对照：`baidu.com`/`github.com` 均 HTTP 200，`cos-platform-outputs.agnes-ai.cn`/`cos.ap-nanjing.myqcloud.com` 均 HTTP 000。
- 前端 `<img>` 代码正常：对照实验 data URI 图片可显示（1×1），后端落库 `raw_data.url` 完整未截断。
- 结论：这台机器访问腾讯云 COS 域名时 TLS 握手失败（网络/代理层拦截），浏览器无法 GET 公网产物，故图片空白。代码未改错；今天把 markdown `![]` 改为直渲 `<img>` 是正确的（避免本地路径 401），两种渲染都依赖浏览器能访问 COS。

### 6.2 sensenova 图片能否渲染——渲染链路通，但生图端点本身失败
- sensenova 产物形态：`sensenova-u1.5-lite` 只回 b64（`prepare_image_body` 把 `response_format=b64_json` 放 extra_body），走 b64 落盘为本地附件（`form=file` + `attachment_id`），前端经 `/api/v1/attachments/id/{id}/raw` 带 token 取 blob → `URL.createObjectURL` → `<img src=blob:>` 渲染，**不依赖外网 COS**。
- 决定性验证：在浏览器里直接对 b64 落盘附件（id=d320dfc5…）调 raw 接口 → HTTP 200 / content-type=image/png / blob 677973 字节 → `img.onload` 成功、naturalWidth=1024×1024。**本地附件 blob 渲染链路完全正常。**
- 但 sensenova 生图本身两次失败：`network_error: EndOfStream`（`ERR_GENERATE_INCOMPLETE`/warning，settled=False），是 `token.sensenova.cn/v1/images/generations` 端点连通性问题，非渲染问题。第三次重测 LLM 误判"generate_image 未加载"未调用工具。
- 结论：只要 sensenova 真能出图，其图片**能正常渲染**（走本地 blob，不受 COS 网络问题影响）；当前渲染不出来是因为生图端点失败、根本没有产物，而非渲染机制缺陷。

### 6.3 统一策略
1. **区分两类产物的渲染路径**：公网 URL（agnes）依赖浏览器出网访问 COS，本地附件（sensenova b64 落盘）走本地 raw+blob。两者都不该静默空白。
2. **前端加加载失败降级**：`GeneratedMediaView` 和 `GenerationResultCard` 的 `<img>`/`<video>` 补 `onError`——公网图失败显示"预览加载失败，请点击查看/下载"，本地附件失败显示"产物读取失败"，杜绝空白卡片。
3. **网络层**：若要让 agnes 公网图在本机显示，需解决腾讯云 COS 域名的 TLS 握手失败（检查 18080 代理对 COS 的转发/证书处理，或将该域名加入直连白名单）。这是环境配置，非代码。
4. **不改代码**：按授权本次只测试与分析，未修改任何代码；上述改进待用户确认后实施。

## 九、三堂会审整改（2026-11-22 05:28:33，小欧）

- 消除 sessionId 全局依赖（后端为主正解）：`media_generate.invoke_generate` 的 result 带 `session_id`；`generate_image`/`generate_video` 工具把 `session_id` 写进产物 data；前端两组件从 `artifact.session_id`/`data.session_id` 读，彻底删除 `useForegroundSession` 依赖。
