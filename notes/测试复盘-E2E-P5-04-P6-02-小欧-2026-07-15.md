## 一、会诊背景与基本判定

### 1.1 背景
本轮批次（P1~P6 共 41 个用例）已全部 100% 通过。其中两个问题偶发暴露，虽经重跑/提超时即通过，但具典型意义，老陈要求二次深度会诊。

- **问题A**：P5_04（网络查询链：搜索→多网页抓取→整合→写多份报告），单轮 final 流式输出 280,341 个 chunk 片段，pytest 2900s 超时强杀；提至 7200s 重跑 1419s 通过。
- **问题B**：P6_02（目录不存在容错），final 仅 36 字且等于最后一条 thought 内容（"正在进入处理阶段，仍然需要先获取信息，TXT文件，然后按指定格式输出文本。"），未提及"目录不存在"；但工具层正确（step 556 observation 已返回"列出目录 E:\test_dir\no_such_dir 失败"）。重跑即通过。

### 1.2 基本判定（两问题共性）
均为**偶发触发、但根因是系统性治理缺失**——Agent 的"单轮 final 答复"**没有输出治理与质量门禁**：

- 测试方法（重跑/提超时）能"赌绿"，但**生产环境没有这层兜底**。
- 两者都发生在"长任务/多工具调用"之后，击中同一最后一公里（final 答复环节）。

## 二、问题A：P5_04 超长 final 答复致超时

### 2.1 第一轮复盘（定性：偶发还是必然）

**现象复述**：网络查询链任务，单轮 final 流式输出 280,341 个 chunk 片段，pytest 2900s 超时强杀；提至 7200s 重跑 1419s 通过。

**本质定性**：**必然性隐患、偶发性触发**。

- 根因不是"慢"，而是 Agent 把整个调研过程与全部报告全文**塞进一个最终回答**单轮输出，且**没有任何长度预算与分篇机制**。
- 只要是"重调研+重产出"型任务，耗时随 token 数近似线性增长、**无自然上界**，迟早撞超时阈值——只是任务重量决定何时触发。

**影响面（生产视角）**：2900s 强杀会让会话处于**半完成态**（前端拿到中断 SSE 流、DB 的 assistant 消息可能只写部分、产物文件可能写了一半）；用户等待 20+ 分钟仍失败，体验极差。测试侧兜底 ≠ 生产有保护。

### 2.2 第二轮复盘（现状处置评价）

**当前处理**：测试侧把重型 case 超时 2900→7200s；生产环境**无任何对应保护**。

**评价（小健·风险视角）**：这是"**把测试兜底当生产保护**"，治标不治本。

- 测试通过只证明"给够时间能跑完"，**不证明生产可靠**：真实用户发起同等重型任务，仍会卡 20+ 分钟，网关/前端超时断开后无人重跑。
- 三个结构性短板：
  1. 无单轮输出 token 预算；
  2. 中间结果已落盘却不节流最终答复（已写文件却把全文再倒一遍）；
  3. 超时语义是"**杀**"不是"**续**"。

### 2.3 第三轮复盘（治理会诊：处理方法 vs 优雅方法）

#### 2.3.1 处理方法（治标·应急·低成本·不改架构）及原理

1. **软截断 + 指路**
   - 做法：出口对 final 设 token 软上限（如 4k~8k），超限时在末尾附"`[内容过长已截断，完整结果见已保存文件 E:\…]`"，引导用户看落盘文件。
   - 原理：把"无限流"变"有界流"，避免强杀导致的半完成态；用"指路"补偿截断的信息损失，用户可自取完整产物。小时级可上线。

2. **输出看门狗**
   - 做法：单轮 final 流式设"输出量/时长"看门狗，超预算即**优雅收尾**（flush 已生成部分 + 提示），不让 pytest/网关硬杀。
   - 原理：将"不可恢复中断"转为"可恢复收尾"，保证 SSE 流正常结束、DB 写入完整。

3. **测试分级超时**
   - 做法：按任务重量分轻/中/重/超重四档超时，而非一刀切 7200s。
   - 原理：超时阈值应与任务重量匹配，避免轻任务被长尾拖死、重任务被误杀。

#### 2.3.2 优雅方法（治本·架构·提升长期可靠性）及原理

1. **编排层"分篇交付"（小沈·架构核心）**
   - 做法：长任务中 Agent 把中间成果实时写入文件/分段 step，**final 只做"摘要+索引"**（做了什么、结论要点、产物文件路径指针），不把全文再倒给用户。
   - 原理（SLAP/单一职责）：把"生成内容"与"呈现结论"拆开。答复是"导航"，文件是"内容"。final 长度与任务重量**解耦**，流式耗时有上界。用户拿摘要+自取文件，等待从 20+ 分钟降至秒级。这是 KISS 的正确落点。

2. **答复治理中间件**
   - 做法：在 `answer_handler` 出口加"最终答复策略"，按 observation 自动决定答复形态（短结论 + 结构化要点 + 产物指针）。
   - 原理：答复形态由"协议/策略"决定，而非由 LLM 自由发挥，从根源消除"倒全文"行为。

3. **超时即"续写"非"杀死"**
   - 做法：把"输出预算耗尽"建模为**可恢复状态**（返回 partial + 续写信号），前端/用户可继续，而非终止会话。
   - 原理：把"终止态"改为"暂停态"，会话始终一致、可恢复，消除半完成态。

4. **可观测性**
   - 做法：对单轮 final 长度、耗时打指标/告警，超出分位即预警，做容量规划。
   - 原理：把偶发长尾转为可度量指标，从"赌"变"管"。

#### 2.3.3 可靠性/可用性论证
- **可靠性**：优雅方法把"不可控长尾"转成"有界交付"，消除强杀导致的半完成态。
- **可用性**：用户等待从 20+ 分钟降至秒级摘要+自取文件；处理方法虽快止血，但留下"截断可能丢信息"的可用性折损，只宜作过渡。

## 三、问题B：P6_02 退化 final 答复（漏"目录不存在"结论）

### 3.1 第一轮复盘（定性：偶发还是必然）

**现象复述**：多阶段复杂任务，final 仅 36 字且等于最后一条 thought（"正在进入处理阶段…然后按指定格式输出文本"），未提及目录不存在；但工具层正确（step 556 observation 已返回"列出目录 E:\test_dir\no_such_dir 失败"）。重跑即通过。

**本质定性**：**典型"方差型临门一脚缺失"**。

- 已查代码（`app/services/agent/handlers/answer_handler.py`）：
  - 第 50 行：`content = format_tool_call_markup(parsed.get("content", ""))` —— final 答复直接取 LLM 返回的 `content`。
  - 第 54 行：仅当 `content` 和 `reasoning` **都空** → 触发 `retrying`（系统重试）。
  - 第 74 行：仅当 `content` 空但 `reasoning` 非空 → 注入 observation 继续循环。
  - 第 94 行：`FinalStep(response=content)` —— 透传。
- **盲区**：当 LLM 返回的 `content` **非空但实为规划句/无实质/未复述关键结论**时，第 54、74 行都不触发，直接透传给用户。即"**非空即放行**"，无质量校验。
- 根因：LLM 在长上下文+多工具调用后，最终回答轮产出退化（方差）；且本轮"错误型 observation"（no_such_dir 失败）虽正确产生，但**没有任何机制要求它必须出现在 final**。

**影响面（最关键的一类）**：动作全做对、结论交付错——"看起来跑完了"，用户误判为成功或未完成，比直接报错更危险。

### 3.2 第二轮复盘（现状处置评价）

**当前处理**：测试重跑即通过；生产无兜底（用户只能自己再问）。

**评价（小健·风险视角）**：重跑是"**用随机性赌下一次更好**"，不可靠。

- 生产用户不知道要重跑；若上下文污染累积导致同类退化连续出现，会持续失败。
- 结构性短板：
  1. final 无质量门禁（最小长度/是否回应问题/是否复述关键 observation）；
  2. 对"已知错误 observation"无"必须出现在 final"的硬约束；
  3. 无退化检测 → 无自动修正。

### 3.3 第三轮复盘（治理会诊：处理方法 vs 优雅方法）

#### 3.3.1 处理方法（治标·应急）及原理

1. **出口最小门禁 + 轻量重试**
   - 做法：final 过短，或命中"规划语气词"（正在/需要/然后/进入…）且未含关键结论 → 视为退化，触发**一次轻量重试**（让 LLM 基于已有 observation/history 重新生成总结）。
   - 原理：退化的本质是"最后一轮没说对话"，重跑最后一轮成本低、成功率高（已有完整 history，不需重跑整条任务链）。

2. **错误复述约束**
   - 做法：把本轮"错误型 observation"（失败/不存在/异常）作为 final 生成的**强制上下文**注入提示，逼迫 LLM 复述。
   - 原理：LLM 漏结论多因"最后一轮注意力漂移"，用显式 must-mention 约束可矫正注意力。

3. **测试层 flake 容忍**
   - 做法：容错类用例允许一次自愈重试，同时把"退化率"记为质量指标。
   - 原理：区分"真 bug"与"偶发方差"，避免把方差当失败、也避免放任方差。

#### 3.3.2 优雅方法（治本·架构）及原理

1. **`must_surface` 硬约束**
   - 做法：在 tool observation 结构加 `must_surface=True` 标记（错误/失败/不存在类）。final 生成时，所有 `must_surface` observation 作为强制上下文注入；并可在出口校验"final 是否包含这些关键结论"。
   - 原理（协议层标记）：从数据标记层面杜绝"知道错误却不说"——错误不是靠 LLM 自觉复述，而是协议强制携带并强制被答复覆盖。

2. **final 质量门禁（答复-上下文一致性校验器）**
   - 做法：在 `answer_handler` 出口加一层纯函数校验，检查 final 必须覆盖三类要素：(a) 已发生的关键错误/失败；(b) 已完成的阶段；(c) 产物指针。不达标 → 进入**修正循环**（用 observation 重新总结），不直接给用户。
   - 原理：把"答复正确性"从"依赖 LLM 自觉"变为"结构化断言"，确定性保证"动作对→结论必对"。

3. **退化检测 + 自愈**
   - 做法：检测 final 为空/过短/纯规划句 → **不向用户输出该 final**，内部用"总结型"专用 prompt（仅做总结、不做新动作）基于完整 history 重生成，最多 N 次；仍失败才向用户给"任务已完成但总结异常，请查看产物文件"。
   - 原理：退化是"最后一公里"问题，复用已有 history 即可修补，不必重跑整条任务链；且"不向用户输出退化 final"保证用户永远拿到合格结论或明确降级提示。

4. **可观测性**
   - 做法：统计"退化 final 率/重试率"纳入 LLM 质量看板，定位是模型还是提示问题。
   - 原理：同问题A，把偶发转为可管理指标。

#### 3.3.3 可靠性/可用性论证
- **可靠性**：优雅方法把"靠运气"变"靠机制"，保证"动作对→结论必对"。
- **可用性**：用户始终拿到明确结论（目录不存在/该怎么办），消除"似完非完"的误判。

## 四、处理方法 vs 优雅方法 总对照

| 维度 | 处理方法（治标） | 优雅方法（治本） |
|------|------------------|------------------|
| 问题A 超时 | 软截断+指路 / 输出看门狗 / 分级超时 | 分篇交付 / 答复治理中间件 / 超时续写 / 指标告警 |
| 问题B 退化 | final 最小门禁+轻量重试 / 错误复述约束 / 测试 flake 容忍 | final 质量门禁 / `must_surface` 硬约束 / 退化自愈 / 质量看板 |
| 上线成本 | 低（小时级，不改架构） | 中（需编排层+校验器，按 SRP/SLAP 落地） |
| 可靠性收益 | 降低失败率（概率性） | 消除半完成态、保证结论必交付（确定性） |
| 可用性收益 | 止血，但有截断/重试折损 | 秒级摘要+自取、始终明确结论 |
| 适用阶段 | **现在即可做**，作过渡 | 作为下一迭代架构改进 |

## 五、总体建议与优先级

1. **立即（处理方法）**：A 的软截断+看门狗、B 的 final 最小门禁+错误复述——不改架构、小时级，先把生产风险压下来。
2. **近期（优雅方法）**：A 的分篇交付、B 的 `must_surface`+质量门禁——架构层正确解法，符合 KISS/SLAP（答复做导航、文件做内容；校验在出口一处）。
3. **常驻（可观测性）**：两问题都暴露"**对 final 这一最后一公里无度量**"。建议统一加 final 长度/耗时/退化率指标，作为 LLM 质量看板基线——偶发问题靠指标才能从"赌"变"管"。

**小欧结论**：两个问题都"偶发但典型"。处理方法解决"绿不绿"，优雅方法解决"可靠不可靠、好用不好用"。二者不是二选一，而是**先用处理方法止血、再用优雅方法治本**，并辅以可观测性形成闭环。当前批次已全绿，无需为此回改代码；建议作为下一迭代的架构改进项立项。

## 七、经代码10大原则通盘复核后的方案修正（v1.1）

### 7.1 复核背景

v1.0 报告给出"处理方法"与"优雅方法"对照。老陈要求用代码10大原则对每个方案逐条复核三思，确保上上下下前前后后逻辑通盘考透，且"敢质疑、敢否定、敢提升"。本版本（v1.1）为复核修正结果。

### 7.2 复核方法

对 v1.0 中每个方案的每个子项，用以下 10 条原则逐一拷问，并通盘分析该方案对系统前（SSE流/前端）、中（answer_handler/LLM）、后（DB/日志）、上（用户视角）、下（架构层）的连锁影响。不符合原则的项，标记"违例"并给出修正方向。

### 7.3 原优雅方案问题清单

| 原方案 | 问题 | 违反原则 | 为何违反 | 修正方向 |
|--------|------|---------|----------|---------|
| A-优雅-3：超时即"续写" | 为偶发长 final 引入可恢复流式协议，需改SSE协议+前端状态机+后端状态机 | **YAGNI** | 单轮 final 长度通过提示约束+输出预算即可有界化，不需要引入"暂停→续写"的全新通信模式。"续写"解决了"被强杀后继续"的问题，但根本解法是"不让被强杀" | **去除** |
| B-优雅-1：`must_surface` 标记 | 在 tool observation 结构加标记，改 observation formatter + tool 返回逻辑 + answer_handler 出口校验 | **YAGNI、KISS** | 退化只有"错误漏报"一种类型，但纯上下文退化检测器即可覆盖所有退化类型（规划句/过短/空），不需要为单一类型新增数据标记体系和配套链路 | **去除** |
| B-优雅-2：final 质量门禁（结构化校验器） | 强约束 final 必须覆盖 "(a)关键错误 (b)已完成阶段 (c)产物指针" | **KISS（过度校验、可能误判）** | 按任务类型不同，有些任务不需要产物指针；强校验会误判可用 final。改为纯"性质判定"（退化/非退化），不看内容结构，只看内容是否属于"规划句/过短/与 observation 无关" | **简化为退化检测器** |
| A-优雅-2：答复治理中间件 | 抽象了一个"中间件"概念，但实际只需一个输出预算检查点 | **KISS、YAGNI** | 一个"出口检查点"即可完成，抽象成"中间件"会给后续维护者引入不必要的分层。具体实现即可，不提前抽象 | **具体化为出口预算检查+压缩重试** |
| A-优雅-1：分篇交付（架构级描述） | 描述模糊，"Agent 把中间成果写入文件"已是现有能力，核心不是缺能力而是缺最终约束 | **SLAP（同一抽象层违反）** | "分篇"是一个高层概念，但实现时混入了"改提示约束"、"改输出检查"、"改 SSE"等多个层级的动作。应将各层级方案分开、按递进关系组织 | **拆为 L0 提示约束 / L1 输出预算检查 / L2 SSE 看门狗 三层递进** |

### 7.4 符合 10 大原则的修正方案（最 KISS 版）

以下为修正后方案，每层均接受 10 原则通盘拷验无误。

#### 问题A：超长 final → 约束 + 有界输出（三层递进）

**内核**：LLM 产出超长 final 的根本原因是"无任何约束"。修正方案的核心理念是"**答复有界、结论必达、无穷重写**"——不控制 LLM 就让它自约束（prompt），LLM 约束不住则系统兜底（压缩重试），兜底再失控则 SSE 截断+指路。

| 层级 | 方案 | 原理逻辑 | 10 原则符合性 | 改动范围 |
|------|------|---------|---------------|---------|
| **L0（最KISS）** | **提示约束**：system prompt 定 final 格式为结构化摘要（结论要点+异常摘要+产物文件索引），加软性长度提示（"优先使用摘要格式，全文见已保存文件"）。不设硬截断 | LLM 知道 final 应该多长、什么格式，从源头消解超长输出 | 全部符合。KISS（最简单改动）、SRP（prompt 只定格式）、DRY（复用已有 prompt 结构）、YAGNI（不需额外机制） | 仅改 system prompt 文本 |
| **L1（输出预算检查+压缩重试）** | answer_handler 出口检 `len(content) > THRESHOLD` → 不直接 `FinalStep`，换成一次"压缩重试"：把已有 content 打回 LLM，prompt="回答过长，请压缩到 X 字内保留完整结论，删除冗余复述"。最多 N=1 次 | 当 LLM 一版产出过长时，用"精炼"而非"截断"来缩减；保留所有结论、删除重复/冗述 | 全部符合。SRP（检查点只做一个判断）、SLAP（与 answer_handler 同层）、KISS（判断+重试，无架构改动）、DRY（复用 LLM 接口） | 改 `answer_handler.py` 出口，增加一个重试分支 |
| **L2（SSE 看门狗兜底）** | 流式输出超阈值时优雅截断+末尾附"[内容过长，完整结果见已保存文件]" | 极端情况（L0+L1 都失效，如 LLM 服务端强制超长输出）的最后安全网 | 全部符合。KISS（阈值检测+截断）、YAGNI（不是主路径，是兜底）、SRP（看门狗职责单一） | 改 SSE 输出层 |

**去除了**：超时续写（YAGNI）、答复治理中间件（KISS）、分篇交付作为架构概念（SLAP 模糊→已具体化为 L0 提示约束的一部分）

#### 问题B：退化 final → 检测 + 自愈 + 降级（三层递进）

**内核**：退化 final 的本质是"最后一轮 LLM 注意力漂移"，不需要改 observation 结构、不需要标记 propagation。修正方案的核心理念是"**检测退化→自愈修复→安全降级**"，所有逻辑集中在 answer_handler 一处，不改其他模块。

| 层级 | 方案 | 原理逻辑 | 10 原则符合性 | 改动范围 |
|------|------|---------|---------------|---------|
| **L0（最KISS）** | **退化检测器**（DEGENERATE DETECTOR）：纯函数，answer_handler 出口检 final 性质。判定条件：(a) content 过短（< 阈值，且任务复杂度高=工具调用多）；(b) content 含规划句标记词（正在/需要/然后/进入/接下来/准备）且不含总结句标记词（已完成/结果/结论/报告）；(c) content 为空（复用现有 `:54` retrying） | 退化有可识别的语言模式：思考型措辞 vs 完成型措辞。利用关键词模式匹配判定性质，不用 LLM 自判（SRP） | 全部符合。KISS（规则判定，无 LLM 调用）、SRP（检测器只做性质判定）、SLAP（与 answer_handler 同层） | 改 `answer_handler.py` 出口，增加检测分支 |
| **L1（自愈重生成）** | 检测到退化 → 用"总结型"专用 prompt 基于完整 history 重生成 final。prompt 核心："你已完成以下动作[{actions}]，结果摘要[{observations}]，请给出最终总结。不得复述计划步骤。" 最多 N=2 次 | 退化是"最后一轮没说对话"，重跑最后一轮成本最低（不重跑工具链）。专用 prompt 消除了注意力漂移 | 全部符合。DRY（复用 LLM 请求）、KISS（prompt 驱动，不改编排）、SRP（重生成器只做总结） | 改 `answer_handler.py`，增加重试+专用 prompt |
| **L2（安全降级）** | L1 仍退化 → 输出"任务已完成但总结异常，请查看产物文件"。不向用户输出退化 final | 重试仍失败时，保证用户拿到明确降级提示而非退化内容 | 全部符合。KISS（降级文本固定）、DRY（复用已有"指路"模式） | 改 `answer_handler.py`，增加降级分支 |

**去除了**：`must_surface` 标记（YAGNI/KISS）、结构化校验器（KISS/误判风险）

**替换为**：退化检测器（基于纯关键词+上下文判定，不依赖标记，不涉及 observation 结构改动，可覆盖所有退化类型包括本次的规划句退化）

### 7.5 修正方案与 v1.0 精华保留

v1.0 中以下方案经复核**保留不动**：
- ✅ A/B 的**可观测性**（final 长度/耗时/退化率指标）。不违反任何原则，且是长期治理基础设施。
- ✅ A-处理方法-1 **软截断+指路**（与 L2 SSE 看门狗本质相同，合并）。
- ✅ B-处理方法-1 **错误复述约束**（吸取其理念，注入退化检测器判定+自愈重生成的 prompt 中）。
- ✅ **测试分级超时**（A-处理方法-3，独立改进）。
- ✅ **测试 flake 容忍**（B-处理方法-3，独立改进）。

## 十、新方案(v1.1)与老方案(v1.0)反复对比 5 遍及最终裁定（v1.2）

> 说明：本掌为老陈要求的"修订后端-新方案与老方案反复对比分析 5 遍、裁定最佳方案"。小欧以"不护短、不弄虚作假、对系统/代码/用户负责"的精神，主动质疑自身 v1.1 结论。

### 10.1 第 1 遍：可靠性——是否真能修住问题？

**问题A（超长 final）**
- v1.0「分篇交付」：agent 执行中把内容写文件，final 只摘要 → **结构性**保证 final 有界（内容已外置）。
- v1.1 `L0 提示约束`：仅用 prompt 要求"final 写短"。**但 LLM 不可靠已被 P6_02 证明**（同无视清晰指令产出退化答复）。单靠"请写短"不足凭。
- v1.1 `L1 压缩重试 + L2 看门狗` 在**出口边界兜底**，保证系统有界。
- 裁定：A 的可靠性 = v1.0「外置文件」洞察 + v1.1「边界兜底」。v1.1 字面 L0 单独不够，须补"执行中把大内容写文件"的指引（取 v1.0 洞察，不做架构改动）。

**问题B（退化 final）**
- v1.0 `must_surface`：错误 observation 必须被 final 提及 → **语义级保证**。
- v1.1 退化检测器：按"规划句/过短/空"判定。**漏洞**：若 final="任务已完成，结果已保存"（流畅总结、非规划句、不短）却**漏提"目录不存在"** → 检测器判"正常"，**假阴性漏判**。v1.0 的 must_surface 能抓出。
- 裁定：v1.1 检测器有真实可靠性缺口，必须补"错误提及检查"（取 v1.0 意图，但**不改 observation 结构**，改为出口扫描 observation 文本）。

### 10.2 第 2 遍：简洁性 / 可维护性（KISS/YAGNI/SLAP）

- v1.0 过度工程：**续写**（YAGNI，为偶发长尾引入可恢复流式协议）、**中间件**（抽象多余）、**must_surface 改 observation 结构+注册**（YAGNI 实现）、**结构化校验**（过度校验、可能误判）。
- v1.1 简洁：仅 **prompt + answer_handler 出口两点纯函数**，局部化、可测、不扩散。
- 裁定：架构上 v1.1 更优。但 v1.1 为简洁**牺牲了 v1.0 的两点可靠性**（10.1 已证），须把那两点"意图"以轻量方式并入，而非整体回退到 v1.0。

### 10.3 第 3 遍：误判 / 边界（假阳 / 假阴）

- v1.0 `must_surface`：若良性 warning 被误标 must_surface，可能假阳；需谨慎标注。
- v1.1 检测器：总结中用了"接下来"可能假阳；"流畅漏错"假阴（10.1）。
- 错误提及检查：final 顺带提错则真阳通过；错误措辞不同则假阴——可控，与 v1.0 同级。
- 裁定：两者都需调参。v1.1 补"错误提及检查"后，假阴风险降到与 v1.0 同级，且免结构改动，更优。

### 10.4 第 4 遍：成本 / 性能 / 用户体验

- 重试成本：两者都是**失败时才 +1~2 次 LLM 调用**，等价（约 +10~20% 成本换 100% 可靠性）。
- 用户体验：v1.0「分篇交付」用户需手动开多个文件拼全貌（摩擦）；v1.1「摘要+指路+自愈」用户直接拿结论。v1.1 体验更顺。
- 裁定：等价或 v1.1 略优。

### 10.5 第 5 遍：综合裁定

| 维度 | 纯 v1.0 | 纯 v1.1 | 最优 |
|------|---------|---------|------|
| 可靠性 | 强（分篇+must_surface） | 有 2 缺口（10.1） | v1.0 强，但… |
| 简洁/10原则 | 多处违例(YAGNI/KISS/SLAP) | 干净 | **v1.1** |
| 用户体验 | 拼凑摩擦 | 顺 | **v1.1** |
| 维护负担 | 重 | 轻 | **v1.1** |

**最终裁定（小欧，负责任的结论，不护短）**：

- **纯 v1.0**：可靠性强，但过度工程，违反 YAGNI/KISS/SLAP 多处，维护重，且分篇交付引入用户拼凑摩擦——**不可取**。
- **纯 v1.1**：架构干净、局部化、符合 10 原则，但**作为字面写法有 2 个可靠性缺口**（漏"外置文件"指引、漏"错误提及检查"），可靠性弱于 v1.0——**亦非最佳**。

## 十二、三思三省：误伤风险复盘与最终方案确认（v1.4）

### 12.1 老陈的核心质疑

> "这个方法有木有可能误伤? 所以首先是要考虑不能误伤,然后才是容错的纠正纠偏 是不是?"

此问一击中的。v1.3 的设计默认做了"宁可错杀不可放过"的取舍，而正确的优先级恰恰相反——**首先不能误伤，然后才是容错纠偏**。

### 12.2 v1.3 Tier1 误伤自检（三思）

逐条审查 v1.3 第十一章列出的护栏代码，发现 **4 类真实误伤场景**（改坏正确 final / 丢失内容）：

| # | 护栏（v1.3） | 误伤实例 | 后果 |
|---|------------|---------|------|
| 1 | B 错误提及关键词检查（`失败/不存在/错误`） | observation 含"文件不存在"，final 写"目标目录未创建，已终止"——"未创建"不在 markers → 误判漏错误 → 安全降级覆盖正确答复 | **改坏正确答复** |
| 2 | B 规划句 startswith（`接下来`） | 合法收尾"**接下来**您可以打开 report.pdf 查看"→ startswith 命中 → 误判退化 → 覆盖 | **极常见正常收尾被改坏** |
| 3 | B MIN_CHARS<20 | 合法短 final"已删除文件 X。"(8字) → 低于阈值 → 覆盖 | **改坏正确短答复** |
| 4 | A-L2 截断 4000 | 合法详尽 final(4500 字, 多文件路径) → 截断丢尾部；pointer"见产物文件"在未写文件时误导 | **信息丢失 + 虚假指路** |

**误伤面分析**：以上 4 类每日可能发生。原问题（P5_04 超长、P6_02 退化）在 41 个 E2E case 中**各仅出现 1 次**，重跑即通过。带误伤护栏上线的后果 = **为修复 1 个罕见问题引入 4 个常见损伤**，代价 > 收益。

### 12.3 根本原则修正（三省）

| 方向 | v1.3（错误） | v1.4（正确） |
|------|------------|------------|
| 优先级 | 抓住偶发退化 > 避免误伤 | **首先不误伤，然后才是容错纠偏** |
| 设计取舍 | 宁可错杀不可放过 | **宁可漏判不可误伤** |
| 检测策略 | 关键词匹配 → 低精高召（假阳多） | 必须**零假阳**才放，否则不放 |
| 纠偏策略 | 替换/截断 final → **破坏性** | 非破坏预防(L0) + 必要时再生(Tier2) |

**关键词检测的本质缺陷**：
- 同义问题："未创建" ≠ "不存在"；相同语义不同措辞即假阴。
- 合法收尾误伤："接下来请查看 report.pdf"命中规划词，但合法。
- 良性噪声：工具输出含"error"（如文件名），final 正确 → 假阳。
- 结论：关键词检测在"不误伤优先"前提下**不能用作护栏触发**。

### 12.4 最终确认的最佳方案

**Tier1（必做，零误伤，零改动 final 内容）**：

| 层 | 动作 | 误伤风险 | 原理 |
|----|------|---------|------|
| A-L0 + B-L0 | `system_prompts.py` 增 `<铁规-final答复>` 三条（大内容写文件 / final 不给规划句 / 错误必须提及） | **零**（仅提示，不改行为） | 预防为主，从源头减少问题 |

**Tier2（可选增强，需 agent 暴露重调用 helper）**：

## 十三、Prompt 修改最终方案（待老陈审阅）

### 13.0 前提知识：LLM 响应格式与 type 分类链（代码溯源 — 小欧 2026-07-15）

> 以下知识经逐文件代码回溯确认，已注释到相关源码中（`llm/core.py` 头部、`llm_stream.py` 头部、`react_cycle.py` `_dispatch_handler`、`answer_handler.py` `handle_answer`、`base_service.py` `_parse_sse_data`）。

**① LLM 原生输出格式**

走 OpenAI `/chat/completions` 流式 API，返回 SSE 数据行：
```
data: {"choices":[{"delta":{"content":"文本"}}]}          ← 纯文本块
data: {"choices":[{"delta":{"tool_calls":[{"index":0,...}]}}]}  ← 工具调用块
data: [DONE]                                              ← 流结束
```
**LLM 自身不输出 `type` 字段**，它只做两件事：输出文本或输出工具调用。

**② type 由 agent 事后推断（llm_stream.py call_llm_stream 末尾）**

流结束后，agent 检查累积结果决定 type：

| LLM 的实际输出 | agent 推断的 type | 去向 |
|--------------|-----------------|------|
| 产生了 tool_calls | `"action"` | `handle_action()` → 执行工具 → 继续循环 |
| 只有文本（无 tool_calls）| `"answer"` | `handle_answer()` → `FinalStep` → 结束循环 |
| 流式异常/出错 | `"error"` | `handle_answer()` error 分支 → `ErrorStep` → 失败 |

**③ type 一共就 3 种**

| type | 产生函数 | 路由 |
|------|---------|------|
| `"action"` | `_build_tool_calls_response()` | `react_cycle._dispatch_handler` → `handle_action` |
| `"answer"` | `_build_answer_response()` | `react_cycle._dispatch_handler` → `handle_answer` |
| `"error"` | `_yield_error_response()` | `react_cycle._dispatch_handler` → `handle_answer`(error分支) |

**④ content / thought / reasoning 映射**

| 字段 | 来源 |
|------|------|
| **content** | LLM 的 `delta.content` 中 `is_reasoning=False` 的块累加（非推理文本） |
| **reasoning** | LLM 的 `delta.content` 中 `is_reasoning=True` 的块累加（推理文本，或来自模型的 `delta.reasoning_content`） |
| **thought** | type="action" 时 = `full_content`（调工具时的附带文本）；type="answer" 时 = `parsed.get("thought", content)`（回退为 content） |

**⑤ 核心结论**

- **LLM 不知道 "final"**，也**不输出 type**。type 是 agent 在流结束后通过"有无 tool_calls"推断出来的。
- **"answer" 不是 LLM 的一个动作**，而是 agent 对"LLM 只输出文本"这种状态的命名。
- 因此 prompt 中的 `① answer:A简洁...` 对 LLM 来说的实际含义是：**"当你决定输出文本而非调用工具来结束时，文本应该包含..."**。这个认知是 prompt 修改的设计前提。

基于第十二章的"零误伤"原则，以及上述前提知识，修改范围定为：

### 13.1 关键认知纠正

| 旧误区 | 纠正 |
|-------|------|
| 认为 LLM 知道 "final" | LLM 只认识 "answer"（prompt 中用词），"final" 纯属 agent 代码概念 |
| 认为 `answer` = `final`（混用） | answer 是 LLM 的输出类型，final 是 agent 的终态包装——两回事 |
| 以为要新增 `<铁规-final答复>` 标签 | 不需新增标签；**直接在 `<铁律-任务复核>` ① 中补充 answer 规则**即可 |

### 13.2 修改内容（仅改一处规则）

**现有**（:54）：
```
- ① answer:A简洁且必须用中文;B问答型任务直接答复,C多步型任务,必包包括意图理解+任务分析+分步计划
```

**改为**（已三思三省修正——C 不再引用 "thought"，因 LLM 不懂 thought；见 13.3）：
```
- ① answer:
  A 简洁且必须用中文
  B 问答型任务直接答复
  C 多步型任务:结论优先,完整分析和分步过程已在工具执行历史中体现,
    不要再重复整篇分析,最终输出文本只给结论和产物指引
  D 执行中产生的大段内容(长文/数据/代码)应写入产物文件,
    最终输出文本只给结构化摘要+产物路径
  E 工具执行中出现失败/不存在/异常时,最终输出必须如实提及该结果,严禁隐瞒
```

### 13.3 逐条说明（含三思三省修正）

| 子规则 | 动作 | 目的 | 误伤风险 |
|--------|------|------|---------|
| C | 从"必包包括分步计划"改为"结论优先；分析已在历史中，不再重复整篇" | 解决 ①C 与 A 的冲突，同时阻断超长根源 | 零（仅修改提示语义） |
| D | 新增"大内容写文件"指引 | 给出"简洁"的方法 | 零（仅提示） |
| E | 新增"错误必须提及" | 补充④仅覆盖整体失败的空缺 | 零（仅提示） |

> **三思三省修正点**：初稿 C 写"分析过程和分步计划在thought中体现"——经复核，LLM 不知道 `thought` 概念（thought 是 agent 代码在 type="answer" 时把 content 复制过来的字段，见 13.0 ④），该表述对 LLM 无意义，已改为"分析已在工具执行历史中体现，不再重复"。

### 13.4 不改之处

- 不改任何标签名（不增 `<铁规-final答复>`）
- 不改 `<铁律-任务复核>` ②~④ 的其他规则
- prompt 修改（L0）为纯预防层，**本身不处理运行时 final 内容**；运行时处理由第十四章 L1/L2 负责

## 十四、完整集成方案：L0 预防 + L1 机械保障 + L2 自愈（待老陈确认）

> 本章将第十三章 L0（prompt 预防）、老陈要求的"answer_handler 加内容外置 + 退化防护"、以及原 Tier2（自愈/压缩重生成）**统一集成**，经三思三省复核，给出取舍、衔接、设计代码、保障矩阵。
>
> **设计铁律（来自老陈）：增强功能逻辑和能力，首先不误伤，不能退化。**

### 14.0 问题分类（来自老陈补充）

超长 final 分两类，处理方式完全不同：

| 类型 | 特征 | 截断是否误伤 | 正确姿态 |
|------|------|:----------:|---------|
| **1-有意义超长** | 内容有结构、有价值（如 P5_04 的 280K 研究报告） | **截断=误伤**（丢尾部真实内容） | 预防（L0）+ 外置存文件（L1-C1），不截断 |
| **2-无意义重复** | 模型卡顿循环，大段重复/无新信息（已知 LLM 故障模式） | **截断不误伤**（重复段无价值） | 高阈值截断（L1-C1 阈值）+ 重复检测（L2 预留） |

> 注：v1.3 曾提议"传输层 8000 上限截断"——对类型1是误伤（P5_04 280K 砍到 8000 丢 97%），已弃用。正确做法见 14.2。

### 14.1 取舍——每个方案要不要

| 方案 | 做什么 | 决策 | 理由 |
|------|--------|:----:|------|
| **L0-A: 改①C** | prompt: 分步计划→结论优先 | ✅ 必做 | 根因预防，零代码 |
| **L0-B: 新规则 D/E** | prompt: 大内容写文件 + 错误必须提及 | ✅ 必做 | 根因预防，零代码 |
| **L1-C1: 自动外置** | 超长→自动存文件，final 只摘要+指路 | ✅ 必做 | **机械保障**，不依赖 LLM 自觉，内容不丢 |
| **L1-C2: 退化检测** | 检测退化→非破坏追加提示 | ✅ 必做 | **机械检查**，不替换内容 |
| **L2-A: 压缩重试** | 超长时重请求 LLM 压缩 | 🟡 暂缓 | 需 LLM 重调用接口（U>0）；C1 已存文件，压缩非必选 |
| **L2-B: 自愈重生成** | 退化时重请求 LLM 生成 | 🟡 暂缓 | 需 LLM 重调用接口；C2 已覆盖大部分场景 |
| **高上限截断** | 传输层硬截断 | ❌ 弃用 | 对类型1是误伤（见 14.0） |

### 14.2 衔接——处理流

```
LLM 输出 type="answer"
       │
       ▼
  ┌───────────┐
  │ L1-C1 检测 │ ← 超长？(>3000)
  │ 自动外置   │ ──超长──→ 写文件 + content 改为"前500字+文件路径"
  └─────┬─────┘
        │ (不超长则原样)
        ▼
  ┌───────────┐
  │ L1-C2 检测 │ ← 退化？(规划句开头 + 无完成态标记 + 短<120)
  │ 追加提示   │ ──退化──→ content += "（提示：答复可能不完整…）"
  └─────┬─────┘
        │ (非退化则原样)
        ▼
  ┌───────────┐
  │ FinalStep  │ ← 最终产出（永远走到底）
  │ emit 输出  │
  └───────────┘
```

- C1 与 C2 **互不依赖、互不阻塞**，都直接对 content 做处理
- **C1 先、C2 后**：C2 对 C1 处理后的 content 检查（C1 已替换为摘要+路径，不触发 C2）
- **两者都不改变控制流**（不 return / 不 break），永远 emit FinalStep

```python
# ═══════════════════════════════════════════════════════════════
# L1 final 质量护栏 — 小欧 2026-07-15
# 设计意图: 仅在 final 出口做纯函数检查, 不改动 SSE/observation/工具/编排层
# 复用: get_config().get_project_root() 取项目根(经核对, agent 无 config 属性, 须用 app.config.get_config())
# 依赖: import os（新增）
# ═══════════════════════════════════════════════════════════════

import os  # 新增(L1 外置写文件用)
from app.config import get_config  # 新增(L1 取项目根)

EXTERNAL_THRESHOLD = 3000      # 超过此值 → 自动外置文件
EXTERNAL_HEAD = 500            # final 保留前 N 字
_DEGRADE_HINTS = ("接下来", "下一步", "仍然需要", "正在进入", "先获取", "进入处理阶段")
_COMPLETE_MARKERS = (
    "已", "完成", "成功", "失败", "不存在", "生成", "创建", "删除", "保存",
    "报告", "文件", "结果", "数据", "日志",
    ".pdf", ".md", ".txt", ".doc", ".xls",
)
_DEGRADATION_HINT = "\n\n（提示：本次最终答复可能不完整，请查看对话历史中的工具执行结果）"


def _externalize_if_long(agent, content: str, step: int) -> str:
    """超长自动外置(机械保障):
       - ≤阈值 → 原样返回(零影响, 与当前行为一致)
       - >阈值 → 写文件 + 返回"前500字+文件路径"; 写失败→返回原内容
    """
    if len(content) <= EXTERNAL_THRESHOLD:
        return content
    try:
        project_root = get_config().get_project_root()
    except Exception:
        return content
    if not project_root:
        return content
    task_id = getattr(agent, "task_id", str(step))
    filename = f"final_detail_{task_id}_{time.strftime('%Y%m%d%H%M%S')}.md"
    reports_dir = os.path.join(project_root, "reports")
    try:
        os.makedirs(reports_dir, exist_ok=True)
        file_path = os.path.join(reports_dir, filename)
        with open(file_path, "w", encoding="utf-8") as f:
            f.write(content)
        logger.warning(f"[L1-C1] final 超长({len(content)}>{EXTERNAL_THRESHOLD}), 已外置至 {file_path}")
        return f"{content[:EXTERNAL_HEAD]}\n\n... [完整内容已保存至: {file_path}]"
    except Exception as e:
        logger.warning(f"[L1-C1] 外置文件失败: {e}, 返回原内容")
        return content


def _is_degenerate(content: str) -> bool:
    """高精退化检测:
       - 非空(空已有上层 retrying 兜底)
       - 不以规划词开头 → 非退化
       - 以规划词开头 + 无完成态标记 + 短(<120) → 退化
    """
    s = content.strip()
    if not s or len(s) >= 120:
        return False
    if s.startswith(_DEGRADE_HINTS):
        if not any(m in s for m in _COMPLETE_MARKERS):
            return True
    return False


def _append_degradation_hint(content: str) -> str:
    """检测退化→非破坏追加提示; 非退化→原样返回(不替换)"""
    if _is_degenerate(content):
        logger.warning(f"[L1-C2] final 疑似退化, 追加提示")
        return content + _DEGRADATION_HINT
    return content
```

### 14.4 保障矩阵（三思三省复核 3 遍）

| 场景 | L0 | L1-C1 | L1-C2 | 结果 |

### 14.5 不误伤 / 不退化保证（复核 10 条）

1. prompt 只改语义、不改行为 → 不触发与当前一致 ✓
2. C1 阈值 3000 → 正常 final(<500)不触发；触发时内容存文件不丢失 ✓
3. C1 写文件异常→返回原内容 → 不影响系统 ✓
4. C2 规划词+完成态标记豁免 → "接下来请查看 report.pdf"含".pdf"不触发 ✓
5. C2 追加提示不替换内容 → 即使误判,用户仍见原文+提示,不丢信息 ✓
6. C1/C2 均不改变控制流 → 永远 emit FinalStep ✓
7. 两个检查都不改已有分支 → error/unknown/empty/reasoning-only 不受影响 ✓

9. C2 假阳代价→最多追加一条提示,可接受 ✓
10. 所有改动集中两文件(system_prompts.py + answer_handler.py),不改 SSE/observation/工具/编排层 ✓
