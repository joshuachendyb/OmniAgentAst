## 一、先说结论：系统处理错误分两大类

整个系统里所有出错情况，按"任务停不停"分成两大类：
系统中所有错误分 两大类型，互不重叠，各自独立路径：


错误处理架构-A
├── 一、系统层次错误 (System Errors)
│   ├── 1.1 LLM流层错误（3种，同根因）
│   ├── 1.2 ReAct循环层错误（8种，全部正确）
│   └── 1.3 基础设施层错误（2种，全部正确）
│
└── 二、Tool层次错误 (Tool Errors)
    ├── 2.1 前置校验错误（3种，全部正确）
    ├── 2.2 执行重试错误（4种，全部正确）
    └── 2.3 重试耗尽错误（1种，全部正确）

错误处理架构-B
│
├── 系统类错误（任务停）：LLM流层 + ReAct循环层 + 基础设施层----A：系统层次错误（System Errors）
│   ├── 特征：Agent循环中断，设FAILED/CANCELLED/RETRYABLE_ERROR
│   └── 位置：llm_stream → _process_single_step → _dispatch_handler → run_react_cycle
│
└── tool层错误（任务不停车）：前置校验 + 执行重试 + 重试耗尽---B：Tool层次错误（Tool Errors）
    ├── 特征：Agent循环继续，错误作为ObservationStep喂回给LLM
    └── 位置：action_handler → tool_executor → tool_retry_engine

核心区别：

特性	系统层次错误	Tool层次错误
循环是否中断	是，直接break	否，LLM看到错误结果后自行决定
前端看到什么	ErrorStep + FinalStep	ObservationStep（error状态）
Agent状态	FAILED / RETRYABLE_ERROR / CANCELLED	保持THINKING，循环继续
能否恢复	一部分可以（RETRYABLE_ERROR）	可以，LLM重试或换工具
谁创建Step	ErrorStep + FinalStep	ObservationStep
错误码来源	error_type字符串	constants.py中的ERR_xxx


### 第一类：系统层次的错误（任务会停）

比方说：
- 调AI大模型的时候网络断了
- AI大模型返回的数据格式完全不对
- 跑任务跑超时了（太久没出结果）
- 安全检查认定某个操作有风险，不让执行
- 用户点了"取消"

遇到这类错误，**任务直接终止**，系统告诉用户"任务失败了，原因是XXX"。

> 简单理解：**系统自己出了问题，任务没法继续了。**

定义：发生在工具执行过程中的错误。每个工具独立处理，自带重试机制，不炸到系统层。

B4. 工具层次错误处理流程
LLM say "use tool X"
    ↓
System execute tool X
    ↓
ToolRetryEngine starts:


比方说：
- AI说要调一个工具，但这个工具的名字系统里找不到
- AI调工具时给的参数不对
- AI漏了必填的参数
- 调工具时出错了（比如网络超时），重试了几次还是不行

遇到这类错误，**任务不终止**。系统把"工具执行出错了"这个信息包装好，喂回给AI大模型。AI大模型自己决定下一步怎么办：
- 重试一次这个工具
- 换别的工具试试
- 直接回答用户"这个事我办不了"



> 简单理解：**工具执行不顺利，但AI自己会想办法，任务还能继续。**

### 两类错误的核心区别

| 比什么 | 系统层次错误 | 工具层次错误 |
|--------|------------|-------------|
| **任务停不停** | **停** | **不停** |
| **用户看到什么** | "任务失败，原因是..." | AI自己处理，用户可能看到AI说"我重试一下"或者"办不了" |
| **谁来决定下一步** | 系统自己决定（终止/重试整轮） | AI自己决定（重试/换工具/放弃） |

## 三、工具层次的错误（共7条，都有对）

### 核心思想

AI说"我要用工具X"→ 系统去执行工具X → **工具执行有问题**

但**问题不传到系统层**，而是：
1. 把错误包装成**结构化的结果**
2. 通过"观察步骤"喂给AI
3. AI自己决定下一步

| 24 | 参数非法 | AI给的参数里有工具不认识的字段 | 返回"参数有非法字段"的结构化结果 | ✅ |
| 25 | 缺少必需参数 | AI漏了工具的必填参数 | 返回"缺少必需参数"的结构化结果 | ✅ |
| 26 | 工具执行可重试异常 | 调工具时出错了（如超时），这种错误可以重试 | 按这个工具配置的重试次数自动重试 | ✅ |
| 27 | 工具执行不可重试异常 | 调工具时出错了，但重试也没用（如参数不对） | 直接返回错误的结构化结果 | ✅ |
| 28 | 重试全部用完还是失败 | 第26条的情况重试N次全都失败了 | 返回"重试耗尽"的结构化结果 | ✅ |

### 工具层次错误的完整流程

```
AI说"用工具X"
    ↓
系统去执行工具X
    ↓
工具重试引擎开始工作：
    ├── 工具名字找不到 → 返回"工具未找到"
    ├── 参数不对 → 返回"参数错误"
    ├── 缺参数 → 返回"缺少参数"
    ├── 可重试的异常 → 自动重试N次
    │   └── 还是不行 → 返回"重试耗尽"
    ├── 不可重试的异常 → 直接返回"执行失败"
    └── 执行成功 → 正常返回结果
                        ↓
             包装成"观察步骤"给AI
                        ↓
             AI看到结果，自己决定继续还是放弃
```

## 五、唯一要修的地方

29条错误路径中，**只有第1、2、3条有问题**。毛病出在同一个地方：

**问题**：
第1、2、3条错误发生时，系统把错误消息伪装成了"普通回答"发给用户。用户看到的是"LLM流式错误：XXX"这样的内容，以为这是AI的正常回答。

**根因**：一个叫"生成错误响应"的函数里，本应标记为"错误"的，被写死标记为"普通回答"。

**怎么修（一共改8处）**：
1. **修1处根因**：把这个函数的标记从"普通回答"改成"错误"
2. **加1处分派**：在分派中心加一个"错误来了怎么处理"的分支——建错误步骤、标记任务失败
3. **删5处补丁**：删掉之前为绕过这个问题打的5个补丁（包括一个临时新建的文件）
4. **不动1处**：一个叫"错误处理器"的文件不用动，它管的是程序抛异常的情况，跟这个不是一回事

**修完之后的效果**：

改之前：
```
AI报错了 → 错误被伪装成"普通回答" → 用户看到"LLM流式错误：..."以为这是正常回答
```

改之后：
```
AI报错了 → 错误被标记为"错误" → 分派中心识别到是错误 → 建错误步骤、标记任务失败 → 用户看到"任务失败，原因是XXX"
```
