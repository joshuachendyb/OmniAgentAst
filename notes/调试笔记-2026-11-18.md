## 1 排查 [46] 文档所述后端 ~2s 固定延迟 【IPv6 localhost 解析副作用，非后端瓶颈】2026-11-18 04:40:00

### 1.1 现象

按 [46] 文档 2.5 节 P3 专项，对真实后端 `:8100` 实测所有端点延迟：`/health`、`/tasks`、`/messages`、`/files/root`、`/models`、`/config/full` 均稳定在 2040~2110ms，与响应体大小（1KB ~ 147KB）无关。

### 1.2 排查过程

1. 排除端点/DB 差异：`/health`（纯探针，1KB）同样 ~2.05s，说明是全局固定开销。
2. 排除后端中间件：`CORSMiddleware` / `GZipMiddleware` / `_RequestTimingMiddleware` / `MonitoringMiddleware` 均为纯 ASGI 包装，落库走 `spawn_bg` 不阻塞响应路径。
3. 对比主机名：`http://localhost:8100/api/v1/health` = 2071ms；`http://127.0.0.1:8100/api/v1/health` = 2ms。
4. DNS 验证：`getaddrinfo('localhost')` 本机优先返回 `::1`，其次 `127.0.0.1`。
5. TCP 验证：`connect(::1:8100)` = 2054ms 后 `ConnectionRefused`；`connect(127.0.0.1:8100)` = 0.4ms 成功。
6. 监听确认：后端仅绑定 IPv4 `0.0.0.0:8100`。
7. 真实浏览器路径：Playwright 同源 `fetch('/api/v1/health')` 经 Vite 代理 = 66ms / 311ms，无 2s 延迟（Node 侧将 localhost 解析到 IPv4）。

### 1.3 结论

[46] 文档观察到的"`/tasks` 等所有端点 ~2s 固定延迟"是**本机 Windows 下 `localhost` 优先解析为 IPv6 `::1`、后端只绑 IPv4 导致的客户端连接回落开销**，并非后端慢查询、SQLite 写锁或 models/config 重载。真实前端经 Vite 代理走 IPv4，不受影响。

**处置结论（H4）**：无需修改后端代码；如需消除 Python 脚本/CLI 经 `localhost` 访问 :8100 的 2s 开销，客户端改用 `127.0.0.1` 即解，或后端启动时绑定双栈地址（会变更监听语义，需另行评估，不在本次实施范围）。
