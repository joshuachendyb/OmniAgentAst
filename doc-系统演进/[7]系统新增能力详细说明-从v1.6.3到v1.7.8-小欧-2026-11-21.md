> ### 版本号辨析（阅读前必看）
>
> 本项目存在两套互不相干的版本号，极易混淆：
>
> | 体系 | 样例 | 权威来源 | 含义 |
> |---|---|---|---|
> | **系统版本** | `v1.6.3` `v1.7.8` | git tag + 根目录 `version.txt` | 软件发布点 |
> | **文档版本** | `v1.0` `v1.6` `v3.4` | 各文档头部版本历史表 | 该文档自身修订次数 |
>
> 本文所有版本区间一律以**系统版本**为准。
>
> **区间计数的口径**：本文每版 commit 数一律用 `git rev-list --count <上一tag>..<本tag>` 实测。`version.txt` 各版本块括号里的 `(N个commit: ...)` 是当时执笔人按自己看到的范围统计的，与 tag 区间口径不同（例如 v1.7.4 块自记 38 个，tag 区间实算 3 个；v1.7.8 块自记 61 个，tag 区间实算 62 个）。两者不是矛盾，是两把尺；本文表格同时给出两个口径，便于回溯。
>
> **本阶段 tag 断档说明**：区间内实际存在 14 个 tag（v1.6.4/5/6/7/9、v1.7.0~v1.7.8）。**没有 v1.6.8**——`version.txt` 里留有 v1.6.8 汇总段，但对应 tag 在"合并远端→清理重打"中被删除（见第十三章纪律问题）。另有 `v1.7.9` 汇总块被写入又被清掉（commit 标题"version.txt v1.7.9 汇总…并打 tag"，随后"清掉已删 tag 对应的 v1.7.6~v1.7.9 汇总块"），`git tag -l v1.7.9` 实测为空。

## 第二章 能力一：第三方 CLI 模型接入网关与免费车道

### 2.1 问题：闭源模型接不进、按量车道用不上

v1.6.3 的模型来源主要走直连 HTTP。两类需求没有出口：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 部分闭源模型只有 CLI 客户端，没有标准 API | 系统里看不到、调不到 |
| 2 | CLI 的 tool-call 用私有界符（如 `<tool_call>`），与系统 JSON 协议不同 | 解析失败、工具轮断裂 |
| 3 | 免费按量车道（opencode2api / 免费网关）需要协议整形与出口代理 | 想用也接不上，token 门禁、未知模型 404 无处安放 |
| 4 | 三种不同来源（直连 / CLI 网关 / 免费车道）配置格式各异 | 用户配置一套模型要懂三套语法 |

### 2.2 架构：通用 vendor 驱动 + 协议整形 + 两条免费车道

`gateways/` 采用通用 `vendor<provider>` 驱动分层（v6.7 起），不按具体 CLI 写死：

```text
CLI 进程 ──▶ driver_api.py（驱动装载/启停）──▶ gateway.py（HTTP 服务）
                                              ├─ upward.py（向上翻译：私有界符→标准 tool_call）
                                              ├─ bodies.py（请求/响应体整形）
                                              ├─ mapping.py（模型名/能力映射、输出格式归一）
                                              └─ streamer.py（流式转发）
```

关键机制：

- **私有界符回退**：FIX L 用 `<tool_call>` 私有界符 + 向下翻译收口 `build_prompt` + 解析容错；大 pickle 自带的 tool-call 标记泄漏经对照实验定性为**非网关缺陷**。
- **协议门禁**：`/v1/models` 补 token 门禁（A3-A4-B8）、未知模型 404 本地校验（C3），下游 404 假设经 v2.2.0 实测纠正。
- **失败重启按实例收口**：竞态形状统一、日志轮转、启动清场，避免多个网关实例互相踩踏。
- **命名对齐**：`driver → driver_api`、`fc → upward`、`opencode_client → bodies`，Protocol 装载期校验。

两条免费车道（`doc-11月优化/[16][17][18]`）：

| 车道 | 做法 |
|---|---|
| 方法 1 | `dsh_freelane` 直连函数库，绕过网关 |
| 方法 2 | `opencode2api` 协议整形网关 + WARP 出口池 + `/64` 双出口轮换；`config.json` 默认启用 warp 出口，实测延迟 6~ 级 |

`opencli_gateway/` 是方法 2 的部署载体：`opencode2api.exe` 改由钉版源码（v1.4.8，前移源码快照 `159d7fdf`）本地编译，SHA256 校验；新增重试启动脚本，解决 WARP 隧道间歇性建立失败（双击即成功，最多 11 次）；配 `gateway.bat/.ps1` 启停壳与配置说明。另一条 `OpenCode-Proxy/` 线补了部署/体检/启动/停止 4 个 bat + watchdog 静默化，`opencode-ECONNREFUSED` 归因到 Bun uSockets 网络栈并给 Node 代理方案。

### 2.3 落地

| 版本 | 内容 |
|---|---|
| v1.6.4 | `gateways/` 落地（driver_api / gateway / upward / bodies / mapping / streamer），v6.5→v6.14 方案迭代与实测回写；配置/启停脚本；验收回归脚本入库 |
| v1.6.5 | 失败重启按实例收口、竞态/日志轮转、三堂会审注释规范化 |
| v1.6.6 | `opencli_source` 免费车道部署物 + `opencode2api.exe`；opencli 网关方言映射补齐（metadata 降嵌套、max_output/cost 别名、effort 档位、tool_call 能力） |

## 第六章 能力五：卡死根治第二阶段——进程宿主隔离

### 6.1 问题：8100 假死与 shell 后台失控

第 6 文档阶段已根治"一条 shell 命令拖死全站"（零线程读管道 + 可回收租约）。本阶段出现两类新形态：

| # | 问题 | 后果 |
|---|---|---|
| 1 | grep 用 `re` 匹配，遇到灾难性回溯把事件循环烧死（8100 服务假死事故） | 端口在听、服务不响应，与第 6 文档的卡死同症状不同根因 |
| 2 | shell 后台进程：正常完成被误杀、通知丢失、续跑链根继承错误、假轮转配置 | 后台任务结果拿不到、进程树残留 |
| 3 | 子进程仍挂在调用方控制台，关窗/控制台选中（QuickEdit）可阻塞 | 镜像线程 flush 永久阻塞、stdout 停写 |
| 4 | 线程池槽位无凭证，超时 `mark_lost` 后容量永久泄漏 + 并发双扣 | 池容量越用越少，最终全站排队 |

### 6.2 架构：正则换引擎 + 控制台隔离 + 槽位状态机

**① grep 灾难根治**：匹配引擎 `re → regex`（带单行 `finditer` 超时 `GREP_INPUT_MATCH_TIMEOUT_SECONDS=5` + 逐行 deadline），从引擎层面杜绝回溯烧死；`requirements` 补 `regex` 依赖声明（原靠 dateparser 间接带入）。

**② 进程宿主隔离**（`doc-11月优化/[42]`）：

| 层 | 做法 |
|---|---|
| P0 | frozen 启动 `FreeConsole` + stdio 重定向（`utils/console_mode.py`）；`is_console_detached` 探测 + detach 后 console 镜像旁路，启动摘要落文件 |
| P2 | 运行代码统一 `console_mode` 隔离子进程；`execute_shell_command` 加 `_child_console_isolation_kwargs`，前台 ps/cmd/bash 与后台 `_popen` 均隔离 |
| P4 | `utils/win_job_object.py`：`SetInformationJobObject` 改用 ExtendedLimitInformation，打包版 exe 顶层 KILL_ON_JOB_CLOSE Job Object，关窗自动杀进程树不留孤儿锁 DLL |
| 阶段 1(L1) | health 读缓存、库探活后台线程、槽位凭证 SlotLease、子进程统一 `proc_io` 零线程读、spawn 收紧 |

**③ 槽位状态机**：`workers` 的 `SlotLease` 改为 `held/released/lost` 三态机，`lost→released` 迟到回收，根治容量泄漏与双扣。

**④ 后台命令链路**：`msg_kind` 消息种类（user/system_notice）+ `creation_source` 任务创建来源维度 + `bg_shell_notifier` DB 反查通知 + `bg_task_query` 改名（原 `bash_result`）+ 续跑链根继承 + 正常完成不杀后台进程 + 删假轮转配置。

`proc_spawn.py` 单函数独立模块违反 KISS（且 `proc_io` 本是其调用方），并入 `proc_io.py`；`safety/shell_parse/parse_kill.py` 收口杀进程三态口径与边界误拦修复。

|---|---|
| v1.7.0 | 8100 假死根治（regex + 超时）；bash 后台运行详细设计 `[33]`；msg_kind + bg_task_query 改名 + 后台输出目录归口；`[40]` 事故分析文档 |

## 第九章 能力八：生图生视频接入对话工具链

### 9.1 问题：生成能力在对话之外、厂商方言各异

生图/生视频此前不在对话工具链里；而厂商协议确实不同：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 生成端点是独立 HTTP 调用，Agent 调不到 | 用户无法在对话里让模型生成图/视频 |
| 2 | agnes 用 size 档位+ratio，sensenova 用 WIDTH×HEIGHT（32 倍数）、image 只认数组 | 硬编码一家会在另一家 400 |
| 3 | 有的厂商返公网 URL，有的只返 4MB b64（SenseNova U1.5） | b64 塞进 LLM 回复会爆上下文 |
| 4 | 本地图 i2i/i2v、视频编码差异（MJPG/MP4V） | 图片编辑要公网图床，视频投给模型直接 400 |

### 9.2 架构：MEDIA 分类 + generation_client + adapter(OCP) + 产物落盘

**新分类 MEDIA**：`tools/media/`（`generate_image` / `generate_video` / `media_register` / `media_schema`），至此工具 register 9→11。

**generation_client 单点 + adapter(OCP)**：

```text
新厂商接入 ──▶ 协议兼容 OpenAI：零定制直接用 general_gen_image/general_gen_video
           └─▶ 有差异：建 adapter 覆写差异钩子（agnes / sensenova）
adapter 基类：prepare_image_body / prepare_video_body（通用）
             parse_image_result / parse_video_status / reason / url（响应方言钩子）
```

- `general_gen_image/general_gen_video` 为通用引擎，新厂商零定制；
- agnes 方言（档位 size/ratio/return_base64/extra_body.response_format）由 `AgnesAdapter` 承载；sensenova 由 `SensenovaAdapter`（size 像素表 WIDTH×HEIGHT、钳制 4096、image 归一数组）；
- 响应解析钩子在 `prepare_video_body` 之后调用，使请求/响应方言各自聚合（同一抽象层）。

**产物落盘**（`utils/artifacts.py` 契约收敛）：公网 URL 走 markdown 内联；b64/本地产物由 `attachment_service.save_generated_bytes` 落盘为会话附件，返回 `file_path`/`attachment_id`，不把 4MB dataURI 塞进回复。`artifacts.py` 收敛产物声明契约（五字段 form 形、统一去重/存在性/上限），落点 `llm_data.action` 与 `other_data`；17 个工具 + 遥测 + 存储读口 + 前端分派同步。

**关键护栏**：`max_retries=0` 防重复提交扣费；视频 `timeout=660` 保险丝覆盖 400s 生成；b64 护栏（键名含 b64/base64 的字符串一律按产物本体剔除 + 8192 长度第二道网）；未交付产物一律报 error（b64 落盘失败/厂商无产物），warning 只留未定（队列满/网络/超时）。

### 9.3 落地：协议适配、公网化、呈现、契约

| 批次 | 内容 |

## 第十四章 阶段小结

### 14.1 这一阶段的性质

上一阶段（v1.6.3）回答的是「**跑得稳、解释得清、坏了查得出**」，这一阶段回答的是「**能吃进多模态、能调外部大脑、能自己生成内容、能问人能汇报**」。

三条主线并行推进：

| 主线 | 内容 |
|---|---|
| **输入边界外扩** | 第三方 CLI 网关 + 免费车道 + 附件资产域 + 多能力字段统一 + 视觉通道 + 输入即能力 |
| **输出边界外扩** | 生图生视频工具链 + 产物落盘呈现 + question/schedule/HITL 交互框架 |
| **体验与稳定性** | 卡死根治第二阶段（正则/控制台/槽位）+ 首屏性能 + 视觉令牌统一 + 参数容错 |

类型分布也印证了这一点：**feat 17.2% 较上一阶段 14.8% 回升，perf 2.0% 翻倍，fix 25.7% 仍高于 feat**。这不是"放弃做稳"，而是**在做稳的地基上重新加速扩边界**——新增的能力（网关/附件/生成/交互）都配了对应的单源真源、契约和会审整改。

同样值得注意的是：**这一阶段最有价值的部分仍是"收口"**——

- 附件三入口收成 `FileDrawer` 一抽屉；
- 模型能力收成 input/output 双维 + `capability_router` 一真源；
- 生成方言收成 adapter(OCP) + `artifacts.py` 一契约；
- 交互收成 `interact` 四态事件一模型；
- 视觉收成 spacing/controlScale/字号阶梯三令牌。
