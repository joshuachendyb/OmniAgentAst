## 一、问题现象

用户使用真实 grep 工具（log 文件中 task_tracker 参数不匹配排查）时，同一 grep 调用被连续触发 50+ 次（step 48 → 99），链路表现为：工具返回 success → LLM 视为"未办成" → 再次同参数 grep → 再 success → 再调用，形成退化死循环，最终把对话上下文打爆、LLM 开始胡言乱语。

## 二、真相核实（硬证据，非推测）

### 2.1 实测方法

走真实管线，不经任何 mock：

```
res = execute_tool_with_retry('grep', {
    'pattern': 'task_tracker.*param|param.*mismatch|占位符',
    'path': 'G:\\OmniAgentAs-desk\\backend\\logs',
    'glob': 'app_2026-07-18.log*',
    'context': 3,
    'output_mode': 'content'})
```

返回 `success`，matches=36，data 原始大小 **1,411,186 字节**（≈1.4MB）。

### 2.2 逐字段字节称重（utf-8 .encode() 实测）

| 字段 | 字节数 | 说明 |
|------|--------|------|
| 原始 data | 1,411,186 | 单工具调用产出 |
| content | 668,506 | 含 context 上下文 |
| matched | 518,635 | 命中行 |
| before | 109,953 | 前 3 行 |
| after | 109,227 | 后 3 行 |

### 2.3 上下文预算

`backend/app/constants.py:89` —— `MAX_CONTEXT_CHARS = 200000`（200K）。

1.4MB 远超 200K，必然触发 `message_builder.trim_history`（`_trim_to_budget`，message_builder.py:277-334）整条丢弃该观察。

## 三、真病根（不是 formatter，不是 trim_history）

**grep 工具在源头产出无界巨块数据，单行/单匹配均无长度上限**（注：2026-07-14 小沈加过 `OBS_MAX_DISPLAY_ITEMS` 条数上限，只管结果条数、管不到单行长度，故"超长方"此前未被处理）。源码定位：

`backend/app/tools/file/grep_file_content.py:205-224`（`_grep_files_sync` 内构造 match_item）：

```
match_item = {
    'path': ...,
    'line': m.start(),
    'matched': m.group(0),          # 整行原样，无长度上限 → 435KB 单行
    'content': line_content,        # 含 context，无上限
    'before': '\n'.join(...),       # 无上限
    'after': '\n'.join(...),        # 无上限
}
```

用户 pattern 中 `.*` 跨整行匹配，日志行本身又把大段文本拼成单行（445KB），于是单条匹配即可达 435KB。36 条累积成 1.4MB 巨块。

**链路**：grep 源头零截断 → 1.4MB 巨块 → trim_history 超预算整条丢 → 观察"假成功/似空" → LLM 判断"没办成" → 退化重调同参数 → step48→99 死循环。

`observation_formatter._format_matches`（observation_formatter.py:935-977）只封顶条数、matched 未截，是**下游受害者**，非病根。

## 四、为什么"在 formatter 截断"是掩耳盗铃

- 病根在 grep 源头：数据一旦以 1.4MB 形态进入消息，message_builder 的唯一手段是"整条丢弃"（非裁剪），早已无可救。
- 在 formatter 砍已生成巨块 = 垃圾已传到门口才扫，治标不治本，且破坏"工具产出保真"原则。
- 正确位置：grep 产出的那一刻就截断单行（2000）/单匹配（300），下游所有环节自然健康。

## 五、修复方法（grep 级源头截断）

### 5.1 原理

在 grep 内部加两个常量 + 一个纯字符串切片 helper，于构造 match_item 时直接截断 `matched / content / before / after`：

- `GREP_LINE_MAX_CHARS = 2000`：单行/上下文上限
- `GREP_MATCH_MAX_CHARS = 300`：单匹配命中上限（避免把整行塞进 matched）
- `_trunc_line(text)`：超长切片加 `...(已截断 N 字符)`，纯字符串操作，不触发任何网络/计时，符合 grep_file_content.py 头部铁规（helper 只返 raw dict、禁调 truncate_data_for_frontend、子函数禁计时）。

### 5.2 已实现 diff（已落地 grep_file_content.py）

位置：常量区（紧邻 `_MAX_PATTERN_LENGTH = 200`）：

```
GREP_LINE_MAX_CHARS = 2000    # grep 单行/上下文产出上限（小欧-2026-07-19）
GREP_MATCH_MAX_CHARS = 300    # grep 单匹配命中上限（小欧-2026-07-19）

def _trunc_line(text: str) -> str:
    """超出 GREP_LINE_MAX_CHARS 截断并在尾部标注，纯字符串切片，不触发IO/计时。小欧-2026-07-19"""
    if text is None:
        return ''
    if len(text) > GREP_LINE_MAX_CHARS:
        return text[:GREP_LINE_MAX_CHARS] + "…（行内容过长已截断）"
    return text
```

### 5.3 已接入点（_grep_files_sync 内 match_item 构造，真实结构）

实际 match_item 结构：`matched` 为 list、`content` 为单行字符串、`before/after` 为 list of `{line, text}`：

```
# 源头截断:单行/单匹配超限即切,避免巨块撑爆LLM 200K上下文(小欧-2026-07-19)
matched_texts = [m.group(0)[:GREP_MATCH_MAX_CHARS] for m in matches_in_line]
match_item = {
    "file": str(fpath),
    "line": line_no,
    "matched": matched_texts,
    "content": _trunc_line(line.rstrip('\n\r')),
}
if context > 0:
    match_item["before"] = [
        {"line": i + 1, "text": _trunc_line(lines[i].rstrip('\n\r'))}
        for i in range(lo, line_no - 1)
    ]
    match_item["after"] = [
        {"line": i + 1, "text": _trunc_line(lines[i].rstrip('\n\r'))}
        for i in range(line_no, hi)
    ]
```

预期：单工具 data 从 1.4MB 降到 ≈300KB 以内，观察 ≤~300KB，run_react_cycle 同任务 step≤3 不再退化循环。

## 六、规范自检（代码10大规范）

- **KISS-DIRECT**：纯切片，无抽象、无中间层，直线落地。
- **SLAP**：_trunc_line 为 grep 内部底层 helper，与构造逻辑同层，不越级。
- **DRY**：单行/上下文/前/后统一走 _trunc_line，不重复写切片。
- **YAGNI**：只加"截断"两常量一函数，不引注册表/配置开关等过度设计。
- **禁止 backward**：直接改产出形态，不保留"兼容旧长块"分支。
- **不退化**：截断仅裁超长行，正常短匹配行为完全不变。

## 七、验证方法

1. 源码落地后，重跑 2.1 同参数真实 grep，断言：
   - `len(json.dumps(res['data']))` ≤ ~300KB
   - 单条 `max(len(x['matched']), len(x['content']))` ≤ ~2000
2. 真实 run_react_cycle 跑同任务，观察 step 数 ≤ 3，无重复 grep 循环。
3. 跑 `pytest -k grep` 确认既有单测不退化。

## 八、结论

真病根是 **grep 源头无界巨块产出**（非 formatter、非 trim_history、非 limit 被拒）。limit 被拒只是 step48 前的触发器（`含非法字段:['limit']`），不是死循环根因。修复必须且已经定位到 grep 内部，以"源头截断单行/单匹配"根治，已落地常量与 helper，待接入 match_item 构造并实测。
