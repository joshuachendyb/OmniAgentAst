## 一、背景

本文档分析 `AgentStatus` 各枚举值在**代码逻辑层面**的真实含义（不是字面翻译），以及 `EXECUTING↔THINKING` 的实际切换行为。

分析依据（v1.1 更正路径，均为扁平化后的当前位置）：
- `backend/app/services/agent/status_table.py` — 枚举定义 + 合法转换表（`_TRANSITIONS`）
- `backend/app/services/agent/react_cycle.py` — 主循环（`run_react_cycle` / `_process_single_step` / `_dispatch_handler`）
- `backend/app/services/agent/initialize_run_state.py` — 初始状态
- `backend/app/services/agent/handlers/action_handler.py` — HITL 等待确认时挂起
- `backend/app/services/chat/stream.py` — SSE 层 `end_type` 映射 + 取消处理
- `backend/app/services/task/task_runtime.py` — 用户暂停 → `SUSPENDED`

> 注：v1.0 引用的 `types/agent_status.py`、`core_agent/status_table.py`、`core_agent/react_cycle.py`、`core_agent/initialize_run_state.py`、`react_sse_wrapper/run_sse_stream.py` 均在 v0.18.11 全量扁平化中迁移，上述路径为 2026-07-12 现状。

## 二、代码执行全流程（逐步追踪，v1.1 更正）

### 2.1 流程总图（8 状态）

```
__init__ → IDLE

run_react_cycle 开始
  ├─ initialize_run_state → IDLE → THINKING            ← 初始化（initialize_run_state.py:68）
  │
  ├─ while 循环（反复执行 _process_single_step）
  │   ├─ LLM 调用（此时 status=THINKING）              ← 状态=思考
  │   ├─ 响应到达 → set_status(EXECUTING)（react_cycle.py:195）← 进入执行
  │   ├─ _dispatch_handler：
  │   │   ├─ error + 可恢复 → RETRYING                  ← 新增状态（2026-07-12 分离）
  │   │   ├─ error + 不可恢复 → FAILED
  │   │   ├─ final → COMPLETED
  │   │   └─ action/answer（无异常）→ 工具执行（此时 status=EXECUTING）
  │   │
  │   └─ 回到 while:
  │       ├─ COMPLETED/FAILED/CANCELLED → break
  │       ├─ RETRYING:                                  ← 可恢复错误重试中间态
  │       │   ├─ 重试 ≤ 3 次 → THINKING（react_cycle.py:320）
  │       │   └─ 重试 > 3 次 → FAILED（react_cycle.py:318）
  │       ├─ SUSPENDED:                                ← 真挂起（用户暂停/HITL）
  │       │   ├─ 用户恢复 → THINKING（task_runtime.py:123）或 EXECUTING（action_handler.py:110）
  │       │   ├─ 用户取消 → CANCELLED
  │       │   └─ 挂起期间异常 → RETRYING（react_cycle.py:352 except 块）
  │       └─ EXECUTING → set_status(THINKING)（react_cycle.py:322）← 每轮切换已实现
  │
  └─ 循环结束 → 无终态兜底 → FAILED（react_cycle.py:336）
```

### 2.2 关键发现（v1.1 更正）

**`EXECUTING` 现在每轮都会切换**：`_process_single_step` 在 LLM 响应到达后（Phase 3，react_cycle.py:195）设 `EXECUTING`，随即分派执行工具；一次迭代结束后 while 循环（react_cycle.py:322）将其设回 `THINKING`。因此：

- **`THINKING` = 正在调 LLM（思考阶段）**
- **`EXECUTING` = 正在跑工具（执行阶段）**

v1.0 中"EXECUTING 全程焊死、状态撒谎"的问题，已在 2026-07-01 的 v2 状态集中管理重构中**通过 `EXECUTING→THINKING` 每轮切换解决**。本文 v1.0 第四节提议的改进已被采纳。

## 三、每个状态在代码逻辑层面的真实含义（8 状态，v1.1 更正）

### 3.1 IDLE — "Agent 创建完毕，还没开始跑"

| 维度 | 说明 |
|------|------|
| **设值位置** | `BaseAgent.__init__` 中设置（默认初值） |
| **代码意义** | Agent 对象存在但尚未开始任何任务 |
| **持续时间** | 从对象创建到 `initialize_run_state` 调用之间 |
| **产出** | 基本不参与逻辑，只是一个初始值 |

### 3.2 THINKING — "即将调 LLM / 正在调 LLM"

| 维度 | 说明 |
|------|------|
| **设值位置** | `initialize_run_state.py:68`（初始化）、`react_cycle.py:320`（RETRYING 重试时）、`task_runtime.py:123`（用户恢复暂停时） |
| **代码意义** | "准备进入主循环"或"正在调用 LLM（思考阶段）" |
| **持续时间** | 从初始化到首次 LLM 调用；每轮工具执行完后又回到 THINKING，直到下次 LLM 调用 |
| **注意** | 现在 THINKING 准确反映"思考中"，不再像 v1.0 所述"仅初始化+SUSPENDED 重试时出现一次" |

### 3.3 EXECUTING — "正在执行工具"

| 维度 | 说明 |
|------|------|
| **设值位置** | `react_cycle.py:195`（每轮 LLM 响应到达、分发工具前，仅此核心一处）、`action_handler.py:106`（用户拒绝 HITL→恢复 EXECUTING）、`action_handler.py:110`（HITL 确认后→EXECUTING） |
| **代码意义** | **"正在执行工具（ReAct 的执行阶段）"** |
| **持续时间** | 从 `react_cycle.py:195` 设入，到本轮回合结束 while 循环设回 THINKING（react_cycle.py:322） |
| **和字面意思的区别** | 与字面一致——现在 EXECUTING 真等于"执行工具"，不再笼统覆盖"调 LLM+跑工具" |

### 3.4 RETRYING — "可恢复错误后的重试中间态"（v1.1 新增，2026-07-12 从 SUSPENDED 分离）

| 维度 | 说明 |
|------|------|
| **设值位置** | `_dispatch_handler:126`（error + recoverable）、`react_cycle.py:352`（except + recoverable） |
| **代码意义** | "发生了可恢复错误（FC 格式错、网络超时、httpx 异常等），暂挂等待重试" |
| **后续处理** | 不在这里变终态，交给 while 循环统一处理（→THINKING 重试 或 →FAILED 超限） |
| **阈值** | 最多重试 3 次（`agent._retry_count > 3` → FAILED，react_cycle.py:317-319） |
| **与 SUSPENDED 区别** | RETRYING=错误重试（程序自动）；SUSPENDED=真挂起（人介入：用户暂停/HITL） |

### 3.5 SUSPENDED — "真挂起：用户暂停任务 / HITL 等用户确认"（v1.1 更正语义）

| 维度 | 说明 |
|------|------|
| **设值位置** | `action_handler.py:95`（HITL 等用户确认工具执行）、`task_runtime.py:106`（用户暂停任务） |
| **代码意义** | "任务被人为挂起，等待人或用户决策"——**不是错误重试**（那归 RETRYING） |
| **后续处理** | HITL 确认 → EXECUTING（action_handler.py:110）；用户拒绝 → EXECUTING（action_handler.py:106）；用户恢复暂停 → THINKING（task_runtime.py:123）；用户取消 → CANCELLED；挂起期间抛可恢复异常 → RETRYING（react_cycle.py:352） |
| **SSE 映射** | → `"paused"` 类型（stream.py:246） |
| **注意** | **v1.0 将 SUSPENDED 描述为"出错了还能重试"是错误的**——那是 RETRYING 的职责。2026-07-12 已将二者语义分离 |

### 3.6 COMPLETED — "任务成功结束"

| 维度 | 说明 |
|------|------|
| **设值位置** | `_dispatch_handler:130`（handler 产了 final event → set_completed） |
| **代码意义** | "LLM 认为任务完成，产生了最终回答" |
| **性质** | 终态，不可再转换 |
| **SSE 映射** | → `"final"` 类型（stream.py:242） |

### 3.7 FAILED — "不可恢复错误"

| 维度 | 说明 |
|------|------|
| **设值位置** | 多处：空响应（react_cycle.py:203）、截断超限（react_cycle.py:248）、chunk 累积超时（react_cycle.py:326）、循环结束无终态（react_cycle.py:336）、不可恢复异常（react_cycle.py:354）、`_dispatch_handler` 不可恢复错误（react_cycle.py:128）、`max_steps<=0`（react_cycle.py:295） |
| **代码意义** | "出错了且无法恢复，任务以失败终止" |
| **性质** | 终态，不可再转换 |
| **SSE 映射** | → `"failed"` 类型（stream.py:243） |

### 3.8 CANCELLED — "用户取消了"

| 维度 | 说明 |
|------|------|
| **设值位置** | `react_cycle.py:219`（LLM 客户端侦测 `_cancelled`）、`task_runtime.cancel_task` 经 `set_cancelled`、SSE 层 `stream.py` 取消处理 |
| **代码意义** | "用户主动中断了任务" |
| **性质** | 终态，不可再转换 |
| **SSE 映射** | → `"interrupted"` 类型（stream.py:244） |

### 3.9 SSE `end_type` 映射速查（stream.py:242-246）

| AgentStatus | end_type |
|------------|----------|
| COMPLETED | `"final"` |
| FAILED | `"failed"` |
| CANCELLED | `"interrupted"` |
| RETRYING | `"failed"`（仅当循环异常结束于 RETRYING 时；正常会先转 THINKING/FAILED） |
| SUSPENDED | `"paused"` |
| THINKING / EXECUTING / IDLE | 活跃态，不产 end_type（任务进行中） |

## 四、EXECUTING↔THINKING 实际切换（v1.1 更正）

### 4.1 v1.0 的疑问

v1.0 分析时（基于更早草稿）认为"`EXECUTING` 全程焊死、状态撒谎"。第四节提议在每轮工具执行后加 `set_status(THINKING)`、LLM 响应后加 `set_status(EXECUTING)`。

### 4.2 现状：该切换已实现

v2 状态集中管理重构（2026-07-01）已落地该逻辑：

```
while 循环:
   第1次迭代: THINKING(初始化) → 调LLM（思考）
     → 响应到达 set EXECUTING（react_cycle.py:195） → 执行工具
     → 回合结束 while: EXECUTING → set THINKING（react_cycle.py:322）
   第2次迭代: THINKING → 调LLM（思考）
     → 响应到达 set EXECUTING → 执行工具
     → while: EXECUTING → THINKING
   第3次迭代: THINKING → 调LLM → 出 final → COMPLETED
```

**结论**：状态已准确反映真实动作——`THINKING`=调 LLM，`EXECUTING`=跑工具。转换表中 `EXECUTING→THINKING`（status_table.py:59）是**真实生效**的合法路径，不是死代码。

### 4.3 转换表是否需要 `EXECUTING→THINKING`

| 问题 | 答案（v1.1） |
|------|------|
| 表里 `EXECUTING→THINKING` 是不是多余的？ | **不是多余的，且代码真实走它**（react_cycle.py:322） |
| 加它有什么好处？ | 状态与实际动作对得上，前端/SSE/日志可清晰区分"思考"与"执行" |
| v1.0 说的"删掉行不行" | **不行**，删了每轮切换会触发 `ValueError(非法转换)` |

## 五、decision（v1.1 更新）

1. **`EXECUTING→THINKING` 保留且生效** — 并非死代码，每轮切换依赖它。
2. **`SUSPENDED` 语义已纠正** — 现指"真挂起（用户暂停/HITL）"，与 `RETRYING`（错误重试）严格分离，二者不可混淆。
3. **转换表 = 8 状态完整契约** — `status_table.py` 的 `_TRANSITIONS` 覆盖所有当前实际路径（含 RETRYING、SUSPENDED 的恢复/取消/失败分支），比实现略宽属正常（KISS-DIRECT：契约可留扩展）。
4. **引用路径全部迁到扁平化后位置**（见第一节）。
