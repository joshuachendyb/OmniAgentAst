## 一、概述

### 1.1 核心设计原则

重试分两级，各自独立、互不干扰：

```
工具级重试（各 tool 自己管）       系统级重试（SUSPENDED）
─────────────────────────────    ─────────────────────────────
一层：工具执行时的网络/超时重试     二层：编排层识别可恢复错误，调度 LLM 重新试
透明：重试成功对上层无感           可见：发 MetaStep.retrying 事件通知前端
工具：各 tool 自己决定             范围：所有可恢复错误（含 LLM 调用失败）
上限：各 tool 自定                 上限：3 次
```

| 维度 | 工具级 | 系统级 |
|------|--------|--------|
| **触发时机** | 工具执行抛异常（超时/网络） | `_dispatch_handler` 收到 `ErrorStep.recoverable=True` |
| **决策者** | 各 tool 自己的重试逻辑（ToolRetryEngine 是其中一种） | `_dispatch_handler` 判断 ErrorStep.recoverable |
| **计数器** | 各 tool 自定（ToolRetryEngine 用 `RetryEngine.attempt_count`） | `RetryTracker.suspend_retries` |
| **失败后果** | 返回 error dict（含 retry_count） | 设 `agent.status = SUSPENDED` |
| **重试成功** | 返回正常 result，上层无感知 | 设 `agent.status = THINKING`，发 retrying 事件 |
| **适用工具** | 各 tool 自己决定（可复用 ToolRetryEngine 或自实现） | 全部（含 LLM 调用） |
| **最大次数** | 各 tool 自定（ToolRetryEngine 默认 3） | 3（`RetryTracker.MAX_SUSPEND_RETRIES`） |
| **退避策略** | 各 tool 自定（ToolRetryEngine 默认指数退避 backoff=2.0） | 立即（编排层重试不等待） |

### 1.3 核心原则：recoverable 决策基于错误类型，不基于重试次数

```
错误类型                     recoverable    例子
─────────────────────────    ───────────    ──────────────────────────
网络超时                      True          连接对端超时
网络连接拒绝                   True          目标端口不通
服务器 5xx                    True          对端返回 503
API 限流                     True          429 Too Many Requests
Shell 进程超时                True          外部命令执行超时
─────────────────────────    ───────────    ──────────────────────────
文件不存在                    False         文件已删除
权限拒绝                      False         无读取权限
参数非法                      False         用户传入了错误参数
解析错误                      False         LLM 返回了非 JSON
─────────────────────────────────────────────────────────────────────

recoverable=True 的不一定经历过工具级重试（比如 FILE 类没有配置工具级重试，但
某个 FILE 错误恰巧是可恢复的也一样走 SUSPENDED）；recoverable=False 的即
使工具级重试（如果有）耗尽了也一样直接 FAILED（比如"文件不存在"重试 3 次仍然不存在）。
两级完全独立，互不依赖。
```

### 1.2 现有机制全景（标注两级归属）

```
┌──────────────────────────────────────────────────────────────┐
│                    7层重试归属两级                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  工具级（各 tool 函数独立管自己的重试）:                          │
│  ├── Layer 3: 工具执行重试 ─── tool_retry_engine.py  ✅ 可选 │
│  │              共享工具，各 tool 可以选择是否复用              │
│  └── Layer 7: 工具内建重试 ─── http_request.py         ✅ 保留 │
│                  http_request 自己管自己的重试                 │
│                  不与 ToolRetryEngine 叠加                     │
│                                                              │
│  系统级（编排层 + LLM 层）:                                      │
│  ├── Layer 1: LLM SDK重试   ─── base_service.py        ✅ 保留 │
│  │              LLM 客户端内建重试（http 调用层面）            │
│  ├── Layer 2: FC降级重试    ─── llm_stream.py           ✅ 保留 │
│  ├── Layer 4: 截断重试      ─── react_cycle.py          ✅ 并入│
│  │                                          RetryTracker      │
│  ├── Layer 5: Tool-less重试 ─── react_cycle.py          ✅ 并入│
│  │                                          RetryTracker      │
│  └── Layer 6: RETRYABLE_ERROR─ react_cycle.py           🔴 死 │
│                              → SUSPENDED     代码             │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 关键死代码证据

`RETRYABLE_ERROR` 状态在代码中无人设置、无人触发：

| 位置 | 代码 | 事实 |
|------|------|------|
| `agent_status.py:19` | `RETRYABLE_ERROR = "retryable_error"` | 有枚举，无人设 |
| `step_emitter.py:30` | `self.agent.set_failed(...)` 先于 ErrorStep 创建 | recoverable 被忽略 |
| `react_cycle.py:294` | `if agent.status == RETRYABLE_ERROR:` | 条件永远不成立 |
| `react_cycle.py:311` | `not in (... RETRYABLE_ERROR ...)` | 永远不走这段代码 |
| `react_cycle.py:327` | `if status != RETRYABLE_ERROR:` | 永远为 True |

**根因**：设计文档（v1.8）要求 `exit_with_error` 只 emit 不设状态，但代码从未改过。

### 2.3 设计文档 vs 代码差异

| 设计文档要求（v1.8） | 代码现状 | 缺口 |
|---------------------|---------|------|
| `RETRYABLE_ERROR` → `SUSPENDED` | 还是 `RETRYABLE_ERROR` | 枚举未改 |
| `_dispatch_handler` 判断 ErrorStep.recoverable → 设 SUSPENDED | 不判断，直接 set_failed | 整个逻辑缺失 |
| `exit_with_error(recoverable=True)` 不 set_failed | 总是 set_failed | 行为不一致 |
| `run_react_cycle` while 循环处理 SUSPENDED | 处理 RETRYABLE_ERROR（死代码） | 不生效 |
| 编排层 retry_count + max_retries=3 | 无 | 整个机制缺失 |

## 三、系统级重试问题

### 问题 S1: RETRYABLE_ERROR 是 100% 死代码（P0）

**严重程度**：P0-紧急

**影响**：设计文档的 SUSPENDED 三路分流机制无法落地。可恢复错误当前都被当作不可恢复的 FAILED 处理。遇到可恢复错误就直接结束，没有让 LLM 换参数重试的机会。

### 问题 S2: _dispatch_handler 无视 recoverable 标记（P0）

**严重程度**：P0-紧急

**影响**：ErrorStep.recoverable 字段被创建但从未被消费。`exit_with_error(recoverable=True)` 调了也白调。

### 问题 S3: 编排层重试分散计数（P1）

**严重程度**：P1-高

| 重试场景 | 计数方式 | 问题 |
|---------|---------|------|
| RETRYABLE_ERROR | `agent.status` 判断 | 死代码 |
| 截断重试 | `agent._consecutive_truncations` | agent 属性，不受控 |
| Tool-less 重试 | `agent._notool_retried` | agent 属性，布尔值 |
| SUSPENDED | **不存在** | 整个机制缺失 |

**影响**：新增重试场景需重新实现计数逻辑，容易遗漏或重复。

### 问题 S4: error_handler 分类与 UnifiedErrorClassifier 重叠（P2）

**严重程度**：P2-中

**描述**：`error_handler._classify_error` 自己再做一次分类（fc_format / network / unknown 三路），与 `UnifiedErrorClassifier.classify_error`（14 类）重叠。两套分类结果可能不一致。

### 问题 S5: 前段看不到重试信息（P2）

**严重程度**：P2-中

**描述**：前端 SSE 事件流中无重试事件，用户看不到"系统正在重试"的反馈。

## 四、系统级重试修改策略

### 4.1 总体方案

```
当前                             改后
─────                           ────
RETRYABLE_ERROR 枚举             SUSPENDED 枚举
exit_with_error 先 set_failed    exit_with_error 只 emit，不碰状态
_dispatch_handler 不判断         _dispatch_handler 判断 recoverable → SUSPENDED
run_react_cycle 死代码 if         run_react_cycle SUSPENDED + RetryTracker + max_retries=3
分散计数（_notool_retried 等）    RetryTracker 统一计数
无前端通知                        MetaStep.retrying 事件
```

### 4.2 修改 S1: RETRYABLE_ERROR → SUSPENDED

**文件**: `agent_status.py`

```python
# 删
RETRYABLE_ERROR = "retryable_error"
# 增
SUSPENDED = "suspended"
```

### 4.3 修改 S2: exit_with_error 不设状态

**文件**: `step_emitter.py`

```python
def exit_with_error(self, step_count, error_type, error_message, recoverable=False):
    # 不设状态，只创建 ErrorStep
    # _dispatch_handler 根据 recoverable 决定状态
    error_step = ErrorStep(step=step_count, error_type=error_type,
                           error_message=error_message, recoverable=recoverable)
    return self.emit(error_step)
```

**调用方适配**：`react_cycle.py:174` 的 `exit_with_error(step, "empty_response", "LLM返回空响应")` — 这个场景不可恢复，调用方需在 yield 后显式调 `agent.set_failed()`。

### 4.4 修改 S3: _dispatch_handler 判断 recoverable

**文件**: `react_cycle.py`

```python
async def _dispatch_handler(agent, llm_response, chunk_buffer):
    ...
    elif parsed_type == "error":
        content = llm_response.get("content", "")
        agent.message_builder.add_assistant_message(content or "")
        agent.set_failed(content or "LLM流式错误")  # LLM 返回 type=error，不可恢复
        yield agent._step_emitter.emit(ErrorStep(step=step, ...))
    else:
        ...  # 未知类型，set_failed
```

关键变化在 **handler 的 yield chain 消费** — _dispatch_handler 从 handler 遍历中收集 recoverable 标记：

```python
# 在 _dispatch_handler 中处理 handler yield chain 时（当前已有 seen_types + last_event）：
_recoverable_seen = False
async for event in handler_generator:
    if isinstance(event, ErrorStep) and event.recoverable:
        _recoverable_seen = True
    yield event

# handler 结束后，根据 event type + recoverable 决策
if "error" in seen_types:
    if _recoverable_seen:
        from app.services.agent.core_agent.react_cycle import set_status
        set_status(agent, AgentStatus.SUSPENDED)
    else:
        agent.set_failed(...)
elif "final" in seen_types:
    agent.set_completed()
```

### 4.5 修改 S4: run_react_cycle + SUSPENDED 重试循环

**文件**: `react_cycle.py`

**新增 RetryTracker**：

```python
class RetryTracker:
    """系统级重试统一追踪 — SRP: 只计数，不设状态"""
    MAX_SUSPEND_RETRIES = 3
    MAX_CONSECUTIVE_TRUNCATIONS = 3

    def __init__(self):
        self.suspend_retries = 0
        self.consecutive_truncations = 0
        self.notool_retried = False
```

**替换**：`agent._consecutive_truncations` → `retry_tracker.consecutive_truncations`，`agent._notool_retried` → `retry_tracker.notool_retried`。

**while 循环改动**：

```python
retry_tracker = RetryTracker()

while agent.llm_call_count < max_steps:
    ...
    async for event in _process_single_step(agent, chunk_buffer):
        yield event

    # agent 被 _dispatch_handler 设为 SUSPENDED → 系统级重试（重新调 LLM）
    if agent.status == AgentStatus.SUSPENDED:
        if retry_tracker.suspend_retries >= RetryTracker.MAX_SUSPEND_RETRIES:
            agent.set_failed(f"系统重试{RetryTracker.MAX_SUSPEND_RETRIES}次耗尽")
            yield agent._step_emitter.emit(ErrorStep(
                step=agent.llm_call_count, error_type="retry_exhausted",
                error_message=f"系统重试{RetryTracker.MAX_SUSPEND_RETRIES}次耗尽",
            ))
            break
        retry_tracker.suspend_retries += 1
        logger.warning(f"[run_react_cycle] 第{retry_tracker.suspend_retries}次系统重试")
        # 发 retrying 事件给前端
        yield agent._step_emitter.emit(MetaStep(
            step=agent.llm_call_count, type="retrying",
            message=f"第{retry_tracker.suspend_retries}/{RetryTracker.MAX_SUSPEND_RETRIES}次系统重试",
        ))
        set_status(agent, AgentStatus.THINKING)
        continue

    # 正常终止
    if agent.status in (COMPLETED, FAILED, CANCELLED):
        break
    ...
```

```python
def _should_retry(self, e, retryable_errors, engine):
    error_category = UnifiedErrorClassifier.classify_error(e)
    is_retryable = error_category.is_retryable or error_category.name.lower() in retryable_errors
    return is_retryable and not engine.exhausted
```

## 六、工具级重试问题

### 问题 T1: ToolRetryEngine 强制所有工具走统一重试（P1）

**严重程度**：P1-高

**描述**：`tool_executor.py` 自动把所有工具的执行都包在 `ToolRetryEngine` 里，`TOOL_RETRY_MAX` 只有 `{"default": 3}`。各 tool 没有选择权——要么全部重试，要么全部不重试。FILE/REGISTRY/DESKTOP 等本地操作也被迫重试 3 次。

**影响**：各 tool 不能独立决定自己的重试策略。file 操作不需要重试，但被迫等 3 次超时。

### 问题 T2: http_request 与 ToolRetryEngine 双重重试（P1）

**严重程度**：P1-高

**描述**：http_request 这个 tool 有自己的内建 retry 参数（retry=3），同时又被 ToolRetryEngine 统一重试。两条重试路径叠加。

**执行链**：
```
action_handler → ToolRetryEngine (重试3次)
                    → http_request (内建 retry=3)
```

最坏情况 3×3=9 次网络调用后失败。

**注意**：各 tool 可以独立实现自己的重试逻辑。http_request 自己管自己的重试是可以的，但需确保不被 ToolRetryEngine 再重一次——二选一，不要两个都重试。

### 问题 T3: action_handler 不设 recoverable，所有错误都 FAILED（P1）

**严重程度**：P1-高

**描述**：无论错误类型是可恢复（超时）还是不可恢复（文件不存在），`action_handler` 收到 error dict 后一律 `set_failed()`。`ErrorStep.recoverable` 字段从未被赋值，系统级 SUSPENDED 无法进入。

### 问题 T4: TOOL_RETRYABLE_ERRORS 只有 timeout（P2）

**严重程度**：P2-中

**描述**：`TOOL_RETRYABLE_ERRORS["default"] = ["timeout"]`，只有 timeout 被显式配置。网络错误、连接错误等都依赖 `UnifiedErrorClassifier.is_retryable` 的判断。配置不够精细。

### 问题 T5: ToolRetryEngine 缺少灵活配置（P2）

**严重程度**：P2-中

**描述**：ToolRetryEngine 当前配置只有 `{"default": 3}` 一刀切，没有给选择使用它的工具提供灵活配置（比如按工具名或按 ToolCategory 区分）。

## 七、工具级重试修改策略

### 7.1 基本原则

1. **各 tool 自己决定是否重试**：ToolRetryEngine 是共享工具，不是强制框架。tool 可以自己实现重试逻辑（如 http_request 的内建 retry），也可以复用 ToolRetryEngine
2. **消除双重重试**：同一 tool 的内建重试和 ToolRetryEngine 二选一，禁止叠加（当前 http_request 的 3×3 问题）
3. **recoverable 基于错误类型**：action_handler 按错误类型/分类设 recoverable，不依赖工具级重试是否耗尽（这是系统级 SUSPENDED 的事，和工具级无关）
4. **谁用谁配**：使用 ToolRetryEngine 的 tools 按需配置（按工具名或按 ToolCategory），不用的不配

### 7.2 修改 T1: ToolRetryEngine 按需配置（给愿意用它的 tool 用）

**思路**：ToolRetryEngine 当前的 `TOOL_RETRY_MAX={"default": 3}` 一刀切。改为：各 tool 通过注册信息或按类型选择是否使用 ToolRetryEngine。不在配置表中的工具不重试。

**文件**: `tool_constants.py`

```python
from app.tools.tool_types import ToolCategory

# 按工具类型配置重试（给使用 ToolRetryEngine 的 tool 用）
TOOL_RETRY_BY_CATEGORY = {
    ToolCategory.NETWORK: {"max_retries": 3, "retryable": ["timeout", "network", "connect", "server", "rate_limit"]},
    ToolCategory.SHELL:   {"max_retries": 2, "retryable": ["timeout", "network"]},
    # 其他类型不在字典中 → 不重试
}
```

**文件**: `tool_retry_engine.py` — `_get_retry_config()` 按 category 查，不在配置表中的回报 0（不重试）：

```python
def _get_retry_config(self, action: str):
    """获取重试配置 — 按工具类型查（给使用 ToolRetryEngine 的 tool 用）"""
    from app.tools.registry import tool_registry
    metadata = tool_registry.get_tool(action)
    category = metadata.category if metadata else None
    
    if category and category in TOOL_RETRY_BY_CATEGORY:
        cfg = TOOL_RETRY_BY_CATEGORY[category]
        return (
            cfg.get("max_retries", 3),
            TOOL_RETRY_BACKOFF.get("default", 2.0),
            cfg.get("retryable", ["timeout"]),
            TOOL_TIMEOUTS.get(action, TOOL_TIMEOUTS["default"]),
        )
    # 不在配置表中的工具不重试（max_retries=0）
    return (0, 0, [], TOOL_TIMEOUTS.get(action, TOOL_TIMEOUTS["default"]))
```

**注意**：各 tool 可以不经过 ToolRetryEngine，自己实现重试（如 http_request 的内建 retry）。这条修改只影响那些选择使用 ToolRetryEngine 的工具。

### 7.3 修改 T2: 消除双重重试

**原则**：各 tool 可以独立实现自己的重试逻辑，但不能和 ToolRetryEngine 叠加。二选一：

**方案 A**：http_request 自己的 retry=0，改用 ToolRetryEngine

```python
async def http_request(url, method="GET", ..., retry: int = 0, ...) -> Dict[str, Any]:
```

**方案 B**：http_request 保留自己的重试，ToolRetryEngine 跳过 http_request（max_retries=0）

选择任一方案，消除 3×3=9 的双重重叠。

### 7.4 修改 T3: action_handler 按错误类型设 recoverable

**文件**: `action_handler.py`

`action_handler` 在收到工具 error 时，根据错误类型/分类决定 `recoverable`，**不依赖工具级重试是否耗尽**：

```python
# action_handler 中收到 error dict 后的简化逻辑
result = ...  # 工具执行结果
if result.get("status", {}).get("exec_code") == "error":
    # 根据错误类型分类，判断是否可恢复
    error_category = UnifiedErrorClassifier.classify_error(
        result.get("error_message", "")
    )
    recoverable = error_category.is_retryable  # 超时/网络 → True；文件不存在 → False

    yield agent._step_emitter.exit_with_error(
        step_count=step,
        error_type=error_category.name.lower(),
        error_message=result.get("error_message", ""),
        recoverable=recoverable,
    )
    # 不设 agent.status，交给 _dispatch_handler 决策
    return
```

### 7.5 修改 T4: 可重试错误类型精细化（供使用 ToolRetryEngine 的 tool 用）

**文件**: `tool_constants.py`

```python
# 供使用 ToolRetryEngine 的工具按需引用

    ToolCategory.NETWORK: ["timeout", "network", "connect", "protocol", "rate_limit", "server"],
```

配合 T1 的 `TOOL_RETRY_BY_CATEGORY` 使用。各 tool 如果自己实现重试（如 http_request），自定自己的可重试错误列表。

## 八、两级重试的关系

### 8.1 执行流程：两条独立分支

**左分支 — 工具级重试（对上层透明）**：
```
工具执行抛异常（超时/网络）
      ↓
该工具配置了重试且错误可重试？
  ├─ 是 → ToolRetryEngine 重试（按工具配置次数，指数退避）
  │        ├─ 第 N 次成功 → 返回正常 result，上层无感
  │        └─ 耗尽 → 返回 error dict（同右分支）
  └─ 否 → 直接返回 error dict（同右分支）
```

**右分支 — 工具返回 error dict**（不分是否经历过工具级重试）：
```
error dict
      ↓
action_handler 按错误类型分类
      ↓
  ┌── UnifiedErrorClassifier.classify_error()
  │   ├─ 超时/网络/服务端 5xx/限流 → 可恢复 → recoverable=True
  │   ├─ 文件不存在/权限拒绝/非法参数 → 不可恢复 → recoverable=False
  │   └─ shell 超时 → 可恢复 → recoverable=True
  │
  └──→ yield ErrorStep(recoverable=...)
       ↓
_dispatch_handler 消费 ErrorStep
       ↓
recoverable?
  ├─ True  → set_status(SUSPENDED)          ← 系统级重试
  │           run_react_cycle 检测到 SUSPENDED
  │           ├─ suspend_retries < 3 → THINKING + continue（重新调 LLM）
  │           └─ suspend_retries >= 3 → FAILED("系统重试耗尽") + break
  │
  └─ False → set_failed("不可恢复错误")      ← 直接结束
```

**关键**：工具级重试的有无/成功/耗尽，不影响右分支的 recoverable 决策。恢复能力只由错误类型决定。

### 8.2 职责划分

| 场景 | 谁处理 | 方式 |
|------|--------|------|
| 网络闪断，第2次重试成功 | 工具级 | 透明，上层无感 |
| 网络超时，工具级重试 3 次耗尽，返回 error | 工具级耗尽 | 返回 error dict（不自动触发 SUSPENDED）|
| action_handler 收到 error，发现是"超时"→ recoverable=True | 系统级 | ErrorStep(recoverable=True) → SUSPENDED |
| SUSPENDED 后 LLM 换了参数，工具成功 | 系统级 | 前端看到 retrying 事件，然后正常完成 |
| SUSPENDED 3 次都失败 | 系统级 | set_failed("系统重试耗尽") |
| 文件不存在（不可恢复），直接 FAILED | 系统级 | ErrorStep(recoverable=False) → set_failed |

**注意**："工具级耗尽"和"系统级 SUSPENDED"之间没有自动传导关系。工具级耗尽只是让 error dict 被返回，action_handler 根据错误类型独立决定 recoverable。

### 8.3 不重叠原则

```
工具级重试 ≠ 系统级重试
───────────   ───────────
重试对象：工具函数调用    重试对象：整个 LLM 轮次
计数器：各 tool 自定      计数器：RetryTracker
条件：各 tool 自定        条件：recoverable=True
上限：各 tool 自定        上限：3（全局）
退避：各 tool 自定        退避：立即
```
