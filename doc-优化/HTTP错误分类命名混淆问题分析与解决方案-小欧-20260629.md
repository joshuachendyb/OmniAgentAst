## 1. 问题发现（历史记录，已解决）

在review tool重试架构时，发现HTTP错误分类存在命名混淆问题：

### 1.1 命名混淆（已消除）
原`error_classifier.py`中`ErrorCategory`枚举使用了`API_`前缀来命名HTTP状态码错误：
```python
# 旧的 error_classifier.py（已废弃）
API_RATE_LIMIT = "api_error_429"      # 实际是HTTP 429
API_UNAUTHORIZED = "api_error_401"    # 实际是HTTP 401  
API_FORBIDDEN = "api_error_403"       # 实际是HTTP 403
API_BAD_REQUEST = "api_error_400"     # 实际是HTTP 400
```

**已解决**：通过系统层/工具层分离重构，该文件已拆分为两个独立分类器，不再存在`API_*`命名。

### 1.2 逻辑矛盾（已解决）
原`http_request`工具的重试逻辑存在跨层引用：
```python
# 旧的 constants.py
RETRYABLE_HTTP_STATUS_CODES = {HTTP_RATE_LIMIT, HTTP_INTERNAL_ERROR, ...}
```
`TOOL_RETRY_CONFIG`中缺少`"api_error_429"`，导致HTTP 429不会被重试。

**已解决**：`RETRYABLE_HTTP_STATUS_CODES`已删除。工具层使用`TOOL_RETRYABLE_HTTP_CODES`（直接判HTTP状态码）决定是否传播给`ToolRetryEngine`，`ToolRetryEngine`再用`ToolErrorCategory`判断重试类型，两层各司其职。

## 2. 当前错误分类架构（2026-06-30重构后）

### 2.1 两层分离架构

```
┌──────────────────────────────────────────────────────────────┐
│  系统层（sys_error_classifier.py）                            │
│  SystemErrorClassifier                                       │
│  判断方式：按异常消息字符串中的数字（如 "429"）                │
│  职责：LLM API 错误分类、熔断检测                             │
│  SystemErrorCategory: SERVER / CIRCUIT_OPEN / IDLE_TIMEOUT   │
│                        EMPTY_RESPONSE / UNKNOWN               │
├──────────────────────────────────────────────────────────────┤
│  工具层（tool_error_classifier.py）                           │
│  ToolErrorClassifier                                         │
│  判断方式：按异常类型名（如 "HTTPStatusError"）               │
│  职责：工具执行错误分类、工具重试判断                         │
│  ToolErrorCategory: TIMEOUT / CONNECT / NETWORK / PROTOCOL   │
│                      PERMISSION_DENIED / FILE_NOT_FOUND      │
│                      INVALID_PARAMS / TOOL_NOT_FOUND / UNKNOWN│
└──────────────────────────────────────────────────────────────┘
```

### 2.2 HTTP状态码处理流程

```
工具 HTTP 请求（如 http_request.py）
    │
    ├─ 状态码在 TOOL_RETRYABLE_HTTP_CODES 中？ ──→ 抛异常给 ToolRetryEngine
    │   (429, 500, 502, 503, 504)                    │
    │                                                 ├─ ToolErrorClassifier 按异常类型名分类
    │                                                 └─ TOOL_RETRY_CONFIG 匹配 → 重试
    │
    └─ 状态码不在列表中？ ──→ build_error() 返回（不重试）
```

### 2.3 常量分层

| 层 | 文件 | 相关常量 | 用途 |
|----|------|---------|------|
| 系统层 | `constants.py` | `HTTP_RATE_LIMIT = 429` + `RATE_LIMIT_STATUS_CODES` | LLM API 限流检测 |
| 工具层 | `tool_constants.py` | `TOOL_RETRYABLE_HTTP_CODES = {429, 500, ...}` | 工具 HTTP 请求重试判断 |

### 2.4 分类器对照

| 维度 | 系统层 SystemErrorClassifier | 工具层 ToolErrorClassifier |
|------|---------------------------|--------------------------|
| 文件 | `app/utils/sys_error_classifier.py` | `app/tools/tool_error_classifier.py` |
| 输入 | 异常对象 + 消息字符串 | 异常对象 + 类型名 |
| 判断依据 | 消息中的数字（`"429"`） | 异常类型名（`"HTTPStatusError"`） |
| HTTP 429结果 | `SystemErrorCategory.SERVER` | 不处理（由`TOOL_RETRYABLE_HTTP_CODES`前置判断） |
| 是否区分 HTTP 状态码 | 统一归为 `SERVER` | 不区分，只看异常类型 |
| 重试判断 | 自身 `is_retryable` 属性 | `TOOL_RETRY_CONFIG` 字典 |

## 3. 实际解决路径

问题不是通过文档中的方案A/B/C解决的，而是通过**系统层/工具层常量分离 + 分类器独立**彻底解决的：

### 3.1 常量分层迁移（2026-06-30）
1. `RETRYABLE_HTTP_STATUS_CODES` 从 `constants.py` 删除（死代码）
2. `TOOL_RETRYABLE_HTTP_CODES = {429, 500, 502, 503, 504}` 加入 `tool_constants.py`
3. `http_request.py` import 从 `app.constants` 改为 `app.tools.tool_constants`
4. 233个 `ERR_*` 工具错误码从 `constants.py` 迁入 `tool_constants.py`
5. `constants.py` 死代码清理（9个 `HTTP_*` 常量删除）

### 3.2 分类器分离（2026-06-29 ~ 2026-06-30）
1. 旧 `error_classifier.py` 拆分为两个独立文件
2. 系统层：`app/utils/sys_error_classifier.py`（`SystemErrorClassifier`）
3. 工具层：`app/tools/tool_error_classifier.py`（`ToolErrorClassifier`）
4. 两个分类器零交叉引用

### 3.3 重试配置匹配（已正确）
`TOOL_RETRY_CONFIG` 中的 `retryable` 列表值与 `ToolErrorCategory.value` 精确匹配：
```python
# tool_retry_engine.py
TOOL_RETRY_CONFIG = {
    "http_request":     {"max_retries": 3, "retryable": ["timeout", "connect", "network", "protocol"]},
    "download_file":    {"max_retries": 3, "retryable": ["timeout", "connect", "network", "protocol"]},
    "fetch_webpage":    {"max_retries": 2, "retryable": ["timeout", "connect", "network", "protocol"]},
    "search_web":       {"max_retries": 2, "retryable": ["timeout", "connect", "network"]},
    "execute_shell_command": {"max_retries": 2, "retryable": ["timeout"]},
    "execute_code":     {"max_retries": 3, "retryable": ["timeout"]},
    "network_diagnose": {"max_retries": 2, "retryable": ["timeout", "connect"]},
}
```

## 4. 验证要点（当前状态）

| 验证项 | 状态 | 说明 |
|-------|------|------|
| HTTP 429 → ToolRetryEngine 重试 | ✅ | `TOOL_RETRYABLE_HTTP_CODES` 含429，直接传播 |
| HTTP 5xx → ToolRetryEngine 重试 | ✅ | `TOOL_RETRYABLE_HTTP_CODES` 含500,502,503,504 |
| HTTP 4xx → 不重试（客户端错误） | ✅ | 400,401,403 不在 `TOOL_RETRYABLE_HTTP_CODES` 中 |
| 网络异常（timeout/connect/network/protocol）→ 重试 | ✅ | 异常类型名被 `ToolErrorClassifier` 正确分类 |
| `TOOL_RETRY_CONFIG` 与 `ToolErrorCategory.value` 匹配 | ✅ | 列表值完全一致 |
| 系统层 `RATE_LIMIT_STATUS_CODES` 与工具层 `TOOL_RETRYABLE_HTTP_CODES` 隔离 | ✅ | 两个 `429` 在不同层，用途不同 |
| 两个分类器零交叉引用 | ✅ | 物理+逻辑完全独立 |
