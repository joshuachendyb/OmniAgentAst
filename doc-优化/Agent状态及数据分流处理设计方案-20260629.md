## 一、背景与问题及新设计说明

### 1.0--架构设计与数据分流的新模式

架构叫:Agent状态及数据分流处理设计方案

Agent状态（元数据）集中到 status_table 管，
数据（Step）通过 yield chain 统一流转。handler 只 yield Step（数据层的事），
编排层从 Step 取 type（状态层的事）

#### 1.0.1 agent状态与数据分流的两个维度说明

两个维度，不是两个正交的事，也不是同一类问题——是互补的：

状态层（agent.status）：管元数据——"现在是什么阶段"
数据层（yield chain）：管数据本体——"具体内容是什么"

#### 1.0.2 agent状态的设计原则

agent.status 管"是什么类型"，yield handler 管"具体数据是什么"
agent.status = THINKING    → 类型：正在思考
    yield ThoughtStep(...) → 数据：具体思考内容

agent.status = EXECUTING   → 类型：正在执行
    yield ActionStep(...)  → 数据：具体调用哪个工具
    yield ObservationStep(...) → 数据：工具返回的结果
    ↑ 数据本身给前端展示 + 给 LLM context（两个消费，是数据层的事）

agent.status = FAILED      → 类型：失败了
    yield ErrorStep(...)   → 数据：具体错误信息

agent.status = SUSPENDED   → 类型：可恢复失败，等待重试
    yield ErrorStep(recoverable=True) → 数据：错误信息（第三路：走重试）


#### 1.0.3 handle及数据风流说明

LLM → handler 执行 → 产出 Step 事件 → 前端展示
                                    → 判断状态（要不要继续）
                                    → 加 context（下一轮 LLM 用）
                                    → 判断 recoverable → 走重试（第三路）

正确的设计：handler 除了 yield Step，什么也不做。
ObservationStep 的内容进 message_builder，是编排层（react_cycle）收到 Step 后自己加，不是 handler 加。

三个出口，两个是后门。应该：

handler 产出 Step → yield（唯一大门）
                     ↓
              编排层统一消费：
                ├─ _dispatch_handler 从 event type 推状态
                │  └─ recoverable ErrorStep → set_status(SUSPENDED) → 第三路：重试
                ├─ react_cycle yield 循环提取 content → message_builder
                └─ yield → 前端（SSE）



### 1.1 当前问题：handler 多出口

Agent 状态赋值分散在 10 处、6 个文件中，无统一入口、无合法转换校验：

| 文件 | 行号 | 当前写法 | 问题 |
|------|------|---------|------|
| `base_agent.py` | 53 | `self.status = AgentStatus.IDLE` | 初始化，可保留 |
| `base_agent.py` | 98 | `self.status = AgentStatus.FAILED` | 在 set_failed 内部，OK |
| `base_agent.py` | 104 | `self.status = AgentStatus.COMPLETED` | 在 set_completed 内部，OK |
| `react_cycle.py` | 188 | `agent.status = AgentStatus.CANCELLED` | 直接赋值 |
| `react_cycle.py` | 281 | `agent.status = AgentStatus.EXECUTING` | 直接赋值 |
| `react_cycle.py` | 295 | `agent.status = AgentStatus.THINKING` | 直接赋值 |
| `initialize_run_state.py` | 60 | `agent.status = AgentStatus.THINKING` | 直接赋值 |
| `step_emitter.py` | 32 | `self.agent.status = AgentStatus.RETRYABLE_ERROR` | 直接赋值 |
| `run_sse_stream.py` | 212 | `agent.status = AgentStatus.CANCELLED` | 直接赋值 |
| `run_sse_stream.py` | 228 | `agent.status = AgentStatus.FAILED` | 直接赋值 |

此外，handler 层通过 `set_failed()` / `set_completed()` 绕过了编排层的状态控制。

**不止状态，数据也有同样问题。** handler 层还直接操纵 `message_builder`，跳过编排层把数据灌进 LLM 上下文：

| 文件 | 行号 | 函数 | 越界调用 | 越界行为 |
|------|------|------|---------|---------|
| `action_handler.py` | 255 | `build_observation` | `ctx.agent.message_builder.add_observation(obs_text, fc)` | handler 层直接加 observation 到 LLM context |
| `action_handler.py` | 259 | `build_observation` | `ctx.agent.message_builder.add_observation(obs_text, {})` | 异常兜底同 |
| `answer_handler.py` | 26 | `handle_answer` | `agent.message_builder.add_assistant_message("")` | handler 层直接加 LLM 回复到 context |
| `answer_handler.py` | 45 | `handle_answer` | `agent.message_builder.add_assistant_message(content)` | 同上，正常路径 |

**本质是一个问题**：handler 有多个对外出口，大多数是后门。


handler 干了三件事，其中两件不归它管：

handler 做的事	归属	问题
① yield Step 事件给前端	handler 该做的 ✅	—
② set_failed/set_completed 状态	编排层该管的 ❌	已被修正（yield-only）
③ ObservationStep 内容加到 message_builder	编排层该管的？ ❓	您说的"还有一个不好"

两个后门（② 和 ③）做的事不同——一个管"类型（状态）"，一个管"数据（context）"——但毛病一样：**handler 通过 yield 以外的通道直接影响系统其他部分**。

### 1.2 本轮设计审查中发现的新问题

本设计方案 v1.0–v1.4 采用的是 "handler return dict" 方案（handler 作为 async generator 在 yield 完事件后用 `return {"action": "complete/fail/continue"}` 传递状态信号），但在设计审查中发现该方案本身存在设计缺陷：

| 问题 | 描述 | 严重程度 |
|------|------|---------|
| **双通道设计** | handler 有两条产出通道——yield event（SSE 事件流）和 return dict（状态信号）。同一信息分两条线传递，违反 SRP | 🔴 设计错误 |
| **StopAsyncIteration 捕获** | 调用方需要 try/except 从 `.value` 提取 return dict。每个中间层（check_safety_and_confirm → handle_action → _dispatch_handler）都要透传这个异常 | 🔴 复杂度高 |
| **return 与 yield 的隐式顺序依赖** | handler 必须在 yield 完最后一个 event 后才 return dict。如果 yield 完忘记 return，无声无息丢状态信号 | 🟡 极易出错 |
| **dict 格式无契约** | `{"action":"complete","response":...}` 的 key 全靠约定。没有人强制写"action"而不是"status"，也没有类型校验 | 🟡 脆弱 |

**根因**：`async generator return` 的 `StopAsyncIteration.value` 机制虽然 Python 原生支持，但在多层 yield chain 中透传需要每层都 try/except，代码复杂且容易遗漏。

**更本质地说，这不是一个孤立问题，而是 handler 产出消费未分离的一个表现。** 整个系统有三个消费者 consume handler 产出的 Step：

```
Step 的消费者：        当前 handler 怎么服务：      应该怎么服务：
┌──────────────┐    ┌──────────────────────┐    ┌─────────────────────────┐
│ 前端（展示）    │    │ yield Step → SSE      │ ✅ │ yield Step → SSE       │
├──────────────┤    ├──────────────────────┤    ├─────────────────────────┤
│ 状态机        │    │ set_failed/set_completed│ ❌ │ _dispatch_handler       │
│（判断继续/停）│    │ （绕过编排层走后门）    │    │ 从 event type 推断状态   │
├──────────────┤    ├──────────────────────┤    ├─────────────────────────┤
│ LLM context  │    │ handler 直接调         │ ❌ │ 编排层收到 ObservationStep│
│（observation │    │ agent.message_builder  │    │ 或 FinalStep 后自己加    │
│  内容给下轮） │    │ （4处：已代码核实）     │    │ 内容到 message_builder   │
└──────────────┘    └──────────────────────┘    └─────────────────────────┘
```

**当前 handler 有三个对外出口**：yield（大门）、set_xxx（6处后门）、直接加 message_builder（4处后门）。后门越多，越难控制。

**正确设计**：handler 只通过 **yield** 一个出口（单一事件通道），三个消费者都由编排层统一从 Step 中取信息。

**解决方案**：抛弃 return dict，改用 **yield-only + 编排层统一消费**：
1. _dispatch_handler 从 yield chain 的 event type 推断状态（fix set_xxx 后门）
2. 编排层（react_cycle 的 yield 循环）在透传 ObservationStep/FinalStep 时，提取 content 加 message_builder（fix add_message 后门）
3. handler 只 yield Step，不 return dict、不 set_xxx、不 add_message

### 1.3 根因分析

**根因1：无状态机**。没有合法转换表，任何代码可以在任何时候设任意状态。代码层没有契约约束，程序员只能靠记忆和文档来避免误用。

**根因2：无唯一入口**。状态赋值没有集中管控，谁想设就设。改了 A 处的状态，B 处又在另一个分支改，两处逻辑冲突时只能在运行时暴露。

**根因3：层次混淆**。状态管理本质上是编排层的职责，但 handler（执行层）、step_emitter（工具层）、run_sse_stream（运输层）都在设状态。每一层的改动都可能无意中改变状态流转逻辑。

**根因4：无非法转换检测**。例如从 `IDLE` 直接到 `COMPLETED` 不会报错，只在运行时产生奇怪的行为。状态转换的错误在 agent 行为异常时才被发现，定位成本高。

### 1.4 设计目标

| 目标 | 说明 | 验收标准 |
|------|------|---------|
| **零处直接赋值** | 不允许 `agent.status = X` 出现在业务代码中 | grep 'agent\.status\s*=' 返回仅 __init__ 一行 |
| **统一入口** | 所有状态变更必须经过 `status_table.set_status()` | 所有调用均通过 import 的函数 |
| **合法转换校验** | 运行时检测非法转换，提前暴露错误 | 非法转换时抛 `ValueError`，500ms 内可定位 |
| **层次隔离** | handler 不碰状态，编排层唯一负责状态流转 | handler 代码中无 `set_failed`/`set_completed`/`status=` 调用 |
| **单通道事件传递** | handler 只 yield event，不 return dict、不 set_xxx、不 add_message | _dispatch_handler 从 event type 推断状态 + 从 Step content 加 context，handler 无后门 |


### 1.5 设计原则

本方案遵守以下原则：

| 原则 | 在本方案中的体现 |
|------|----------------|
| **SRP — 单一职责** | `status_table.py` 只做一件事：管理状态转换。不处理 SSE 事件、不处理 DB、不处理 LLM 调用 |
| **KISS-DIRECT — 简单直接** | 函数式，不用类。`set_status(agent, new_status)` — 3 行代码内部逻辑。直来直去，没有中间层 |
| **SLAP — 同一抽象层** | `react_cycle.py` 编排状态流转（高层），不混入 `agent.status = X` 的底层实现。底层实现封装在 `status_table.py` |
| **YAGNI — 不过度设计** | 不加注册表、不加回调、不加事件总线。当前只需要一个状态转换校验 + 四个导出函数 |
| **禁止 backward** | 旧代码全部改，不保留 `base_agent.set_failed()` 兼容方法。一次性彻底迁移，不存在新旧两套并存的过渡期 |

## 二、新方案：Agent状态管理及数据分流概要设计

### 2.1 架构总览

```
 数据分流（yield chain）                      状态集中（status_table）
 ──────────────────────                      ─────────────────────
                                                          
 ┌─────────────────────────────────────────────────────────────┐
 │                       运输层                                  │
 │    run_sse_stream.py        SSE 流                         │
 │    ├─ 消费 yield 事件 → 前端                ↑              │
 │    └─ 外部异常 → set_failed/set_cancelled   │              │
 ├───────────────────────────────────────────┼─────────────────┤
 │                      │                     │   编排层        │
 │    react_cycle.py    │ yield chain 透传     │              │
 │    ┌─ run_react_cycle():                   │              │
 │    │  ├─ while 循环调度（含超时/取消检查） │                 │
 │    │  ├─ _process_single_step():           │              │
 │    │  │  ├─ LLM 调用（含截断检测/B3重试）  │                   │
 │    │  │  └─ _dispatch_handler() 分派       │              │
 │    │  │     ├─ "error" → handle_llm_error  │  → 调        │
 │    │  │     ├─ "answer" → handle_answer    │  status_table │
 │    │  │     ├─ "action" → handle_action    │  设状态       │
 │    │  │     └─ unknown → _handle_unknown   │              │
 │    │  │  从 yield chain 提取 Step content  │              │
 │    │  │  → message_builder (observation/final)│              │
 │    │  └─ 循环结束无终态 → set_failed       │              │
 │    │  从 Step content 提数据 → message_builder            │
 │    │  ├─ "observation" → add_observation   │              │
 │    │  └─ "final" → add_assistant_message   │  → 调        │
 │    └─ (run_react_cycle 内异常兜底)         │  status_table │
 │                      ↑                     │  设状态       │
 ├──────────────────────┼─────────────────────┼──────────────┤
 │                      │    执行层            │              │
 │    handlers/ ————————┘ 只 yield Step       │              │
 │    ├─ answer_handler.py  yield FinalStep    │  不碰状态    │
 │    ├─ action_handler.py  yield ObsStep      │  不碰context │
 │    ├─ error_handler.py   yield ErrorStep    │              │
 │    └─ step_emitter.py    yield ErrorStep    │              │
 │                               ↓             │              │
 │                          SSE 流 → 前端       │              │
 ├─────────────────────────────────────────────┼──────────────┤
 │                       状态机                 ↓              │
 │    status_table.py   ← 编排层调              │              │
 │    ┌─ _TRANSITIONS — 合法转换表              │              │
 │    └─ set_status/set_failed/set_completed/   │              │
 │       set_cancelled（物理改 agent.status）   │              │
 └─────────────────────────────────────────────────────────────┘
```

**架构说明**：`_process_single_step` 是编排层的关键中间层，负责 LLM 调用、截断检测、B3 重试、取消检测等业务逻辑。它当前直接调 `agent.set_failed/cancelled` 和 `message_builder.add_xx`，改造后所有状态变更必须委托 `status_table`，所有 context 写入必须从 Step content 提取，不得在业务逻辑中直接操作。

### 2.2 合法转换表

```
IDLE        → THINKING                     [启动 agent]
THINKING    → EXECUTING                    [LLM 返回工具调用]
THINKING    → COMPLETED / FAILED           [LLM 返回最终答案 / LLM 返回空]
EXECUTING   → THINKING / SUSPENDED         [工具执行完 / 工具可恢复失败]
EXECUTING   → COMPLETED / FAILED           [工具 return_direct / 工具不可恢复失败]
SUSPENDED   → THINKING / FAILED            [重试 / 重试次数用尽]
CANCELLED   → (终态，不可转换)
COMPLETED   → (终态，不可转换)
FAILED      → (终态，不可转换)
```

**终态不可转换的含义**：一旦 agent 进入 CANCELLED、COMPLETED、FAILED 之一，任何后续调 `set_status` 都会抛 `ValueError`。这意味着 react_cycle 的 while 循环会在下一次循环判断时 break，不会再次尝试。

**SUSPENDED 说明**：SUSPENDED 是非终态中间状态，表示工具执行出错但错误可恢复。编排层见到 SUSPENDED 后不走 break，而是继续 LLM 重试。重试成功则转 THINKING，重试次数（默认 3 次）用尽则转 FAILED。

**数据表定义**：

```python
_TRANSITIONS = {
    AgentStatus.IDLE:      {AgentStatus.THINKING, AgentStatus.CANCELLED, AgentStatus.FAILED},
    AgentStatus.THINKING:  {AgentStatus.EXECUTING, AgentStatus.COMPLETED, AgentStatus.FAILED, AgentStatus.CANCELLED},
    AgentStatus.EXECUTING: {AgentStatus.THINKING, AgentStatus.COMPLETED, AgentStatus.FAILED, AgentStatus.SUSPENDED},
    AgentStatus.SUSPENDED: {AgentStatus.THINKING, AgentStatus.FAILED},
    AgentStatus.CANCELLED: set(),
    AgentStatus.COMPLETED: set(),
    AgentStatus.FAILED:    set(),
}
```

### 2.3 三层职责边界

| 层级 | 文件 | 职责 | 能否改状态 | 能否改数据(message_builder) |
|------|------|------|-----------|---------------------------|
| **运输层** | `run_sse_stream.py` | SSE 收发、DB 存取、用户取消、捕获外部异常 | ❌ 正常流程不能。仅在用户取消时调 `set_cancelled`、捕获到顶层未预期异常时调 `set_failed` | ❌ 正常流程不能。finally 中只读 agent.status 存 DB |
| **编排层** | `react_cycle.py` (含 `run_react_cycle` + `_process_single_step` + `_dispatch_handler`) | 主循环调度、LLM 调用（含截断检测/B3 重试）、_dispatch_handler 从 event type 推断状态+从 Step content 加 context、异常兜底 | ✅ 唯一正常设状态的地方 | ✅ 唯一正常加 context 的地方 |
| **执行层** | `handlers/answer_handler.py` | 处理 LLM 返回的 final answer，生成 ThoughtStep/FinalStep | ❌ 绝对不能，只能 yield Step 对象 | ❌ 绝对不能，只能 yield Step 对象 |
| **执行层** | `handlers/action_handler.py` | 处理 LLM 返回的工具调用，生成 ThoughtStep/ActionStep/ObservationStep | ❌ 绝对不能，只能 yield Step 对象 | ❌ 绝对不能，只能 yield Step 对象 |
| **执行层** | `step_emitter.py` | 创建 ErrorStep/ObservationStep/FinalStep 等步骤对象 | ❌ `exit_with_error` 不设状态，只创建 ErrorStep | ❌ 不碰 message_builder |
| **执行层** | `error_handler.py` | 处理 LLM 解析错误、网络异常等 | ❌ 不设状态，只创建/返回 ErrorStep | ❌ 不碰 message_builder |
| **状态机** | `status_table.py` | 唯一改得动 `agent.status` 的地方，提供合法转换校验 | ✅ 唯一物理上改属性的地方 | ❌ 不碰 message_builder |

**运输层（run_sse_stream.py）的例外说明**：
- 用户取消（`KeyboardInterrupt` 或前端发取消信号）：这是运输层的直接责任，它持有连接上下文，不能等到编排层去处理。允许调 `set_cancelled`
- 顶层未预期异常：例如数据库连接断开、LLM 客户端 HTTP 错误等。这些发生在编排层之外，运输层捕获后调 `set_failed`
- 正常流程（无取消、无异常）下，运输层不做任何状态操作

### 2.4 Handler 协议 — yield-only

#### 2.4.1 协议定义

handler 不再调任何 `set_xxx` 函数，不再调 `message_builder.add_xxx`，也不再 `return dict`。handler 是 **async generator**，只 `yield Step` 对象。所有信息通过 **yield chain** 单一通道传递。

`_dispatch_handler` 在遍历 handler 的 yield 链时，跟踪每个 event 的 type。handler 结束后，根据 type 决定状态：

| 关键判断 | 含义 | 状态动作 |
|----------|------|---------|
| yield 链中出现 `type == "error"` 且 `recoverable=True` | handler 发生了可恢复错误 | `set_status(agent, SUSPENDED)` → 第三路：重试 |
| yield 链中出现 `type == "error"` 且非 recoverable | handler 发生了不可恢复错误 | `set_failed(agent, ...)` |
| 无 error，但有 `type == "final"` | handler 正常完成 | `set_completed(agent)` |
| 无 error、无 final（如 observation） | handler 需要继续循环 | 不设状态 |

**为什么抛弃 return dict：**

| 方案 | 问题 | 结论 |
|------|------|------|
| async generator return dict | 每个中间层都要捕获 `StopAsyncIteration` 提取 result，代码复杂度高 | ❌ 复杂、易错 |
| yield 事件 + return dict 双通道 | 同一信息两条通道传递，违反 SRP | ❌ 重复设计 |
| **只 yield，用 event type 推断** | 单通道自然传递，各层只需 `async for event: yield event` | **✅ 选此方案** |

#### 2.4.2 handler 的 yield 模式

```
完成路径:
  yield ThoughtStep / ActionStep ... → yield FinalStep
                                        有 "final" 无 "error" → set_completed

失败路径（不可恢复）:
  yield ErrorStep(recoverable=False) [→ yield FinalStep]   有 "error" 且非 recoverable → set_failed

失败路径（可恢复，第三路：重试）:
  yield ErrorStep(recoverable=True)         有 "error" 且 recoverable → set_status(SUSPENDED)

继续路径:
  yield ThoughtStep → yield ActionStep → yield ObservationStep → (返回)
  无 "error"、无 "final" → continue（不设状态）

LLM error 类型路径:
  LLM 返回 type=error → handle_llm_error(agent, llm_response)
  → yield ErrorStep(error_type="llm_error")（只 yield，不设状态、不碰 message_builder）
  → _dispatch_handler 看到 "error" in seen_types → set_failed

LLM 未知类型路径:
  LLM 返回其他 type → _handle_unknown(agent, llm_response)
  → yield ErrorStep(error_type="unknown_response")（不可恢复）
  → _dispatch_handler 看到 "error" in seen_types → set_failed
```

**为什么检查 `any("error")` 而不是仅检查最后一个 event：**

handler 可能在 yield ErrorStep（失败信号）之后再 yield FinalStep（给前端的终态事件）。例如 answer_handler 空内容分支目前就是先 yield FinalStep 再 `set_failed`。如果只看最后一个 event 的 type（"final"），会错误地设为 completed。**只要 yield 链中出现过一次 ErrorStep，就应该 set_failed（除非 recoverable）。**

**注意**：error 和 unknown 类型也必须走 yield-only 协议。不允许 `_dispatch_handler` 在分派时直接 `add_message` + `set_failed`。所有响应类型（action/answer/error/unknown）统一经过 handler 函数 → yield chain → _dispatch_handler 从 event type 推断状态这条路径。

#### 2.4.3 概要说明

`_dispatch_handler` 按 LLM 响应类型分派到对应 handler（handle_action / handle_answer / handle_llm_error / _handle_unknown），**统一通过 handler 变量引用**，单次 `async for` 遍历 handler 的 yield 链，同时跟踪 `seen_types` 和 `last_event`。遍历结束后根据 event type 推断状态："error"→set_failed、"final"→set_completed、其他→continue。

handler 在此过程中只 yield Step，不 return dict、不 set_xxx、不调 message_builder.add_xxx。ObservationStep 和 FinalStep 的 content 提取由编排层（react_cycle 的 yield 循环）统一处理。

具体实现代码见 §4.7 改动2。

### 2.5 异常兜底策略

当编排层（react_cycle）调用 handler 的过程中出现未预期异常时，编排层自身负责兜底：

```
编排层捕获异常
    → 创建 ErrorStep（含异常信息）
    → yield ErrorStep（给前端看）
    → set_failed(agent, str(error))（设状态）
    → 下一次 while 循环判断时 break
```

这意味着，即使 handler 内部崩溃了，状态流转仍然是可控的：一定经过 `set_failed`，一定是合法转换，一定不会出现悬空状态。

### 2.6 SUSPENDED — 可恢复失败 + 重试机制（第三路：重试）

RETRYABLE_ERROR 在 v1.x 中被列为"死代码待删除"，但在完整"数据分流"设计中，**可恢复错误应该走第三路——重试**。本方案将其改造为 SUSPENDED 状态 + 编排层重试逻辑：

| 维度 | 旧 RETRYABLE_ERROR | 新 SUSPENDED |
|------|-------------------|-------------|
| 状态性质 | 中间态，但循环中需特殊条件判断 | 标准中间态，在 _TRANSITIONS 表中与其他状态平级 |
| 触发方式 | `step_emitter` 直接设 `agent.status` | handler yield ErrorStep(recoverable=True)，_dispatch_handler 识别后调 set_status(SUSPENDED) |
| 何时重试 | 下一次循环无判断直接 agent.status=THINKING | 编排层见到 SUSPENDED 后检查重试次数（默认 3 次），未超限则继续 LLM 调用，超限则 set_failed |
| 数据流 | 无，RETRYABLE_ERROR 只是状态 | 第三路：ErrorStep 经 yield 给前端显示，编排层提取错误信息作为 observation 传给 LLM 重试时的 context |

**重试流程**：

```
工具执行失败 → exit_with_error(step, type, msg, recoverable=True)
    → yield ErrorStep(recoverable=True)          [第一路：前端展示]
    → _dispatch_handler 识别 recoverable=True
    → set_status(agent, SUSPENDED)               [第三路标记：需要重试]
    → run_react_cycle 见 SUSPENDED:
        判断 retry_count < 3
        → set_status(agent, THINKING) + LLM 调用
        → 重试成功 → 正常流转
        → 重试再次失败且 retry_count=3 → set_failed
```

**修改要点**：

| 文件 | 改动 |
|------|------|
| `step_emitter.py:32` | `if recoverable: self.agent.status = AgentStatus.RETRYABLE_ERROR` → 去掉直接赋值，保留 recoverable 参数供 ErrorStep 元数据使用 |
| `react_cycle.py` | 删除旧 RETRYABLE_ERROR 特殊判断，改为 while 循环感知 SUSPENDED，编排层检查 retry_count |
| `_TRANSITIONS` 表 | 新增 `EXECUTING → SUSPENDED`、`SUSPENDED → THINKING/FAILED` |

### 2.7 非标准路径状态管理（第1次复核补充）

除 §2.4 的 handler yield-only 标准路径外，`run_react_cycle` 中还存在 **6 处非标准路径**，它们不在 handler 内，而是在编排层的主循环中直接设状态。这些路径同样必须遵循"调 status_table"的规则，不允许 `agent.status = X` 或 `agent.set_failed/set_cancelled` 等旧写法：

| 序号 | 当前代码位置 | 触发条件 | 当前写法 | 改后写法 |
|------|------------|---------|---------|---------|
| ① | `run_react_cycle` 循环开始 | 循环启动时标记正在执行 | `agent.status = AgentStatus.EXECUTING` | `set_status(agent, AgentStatus.EXECUTING, "循环启动")` |
| ② | `run_react_cycle` 循环内超时检查 | 总耗时超 TASK_TIMEOUT | `agent.set_failed(...)` | `set_failed(agent, ...)` |
| ③ | `run_react_cycle` 循环内 chunk 超时 | chunk_buffer 累积超时 | `agent.set_failed(...)` | `set_failed(agent, ...)` |
| ④ | `_process_single_step` 截断重试 | LLM 连续截断 3 次 | `agent.set_failed(...)` + `yield FinalStep` | `set_failed(agent, ...)` + yield ErrorStep(recoverable=False) + yield FinalStep |
| ⑤ | `run_react_cycle` max_steps 检查 | max_steps ≤ 0 | `agent.set_failed(...)` | `set_failed(agent, ...)` |
| ⑥ | `run_react_cycle` 循环结束无终态 | while 结束但 status 不是终态 | `agent.set_failed(...)` | `set_failed(agent, ...)` |

**改造原则**：
1. 所有 6 处直接将 `agent.set_xxx()` 改为 `set_xxx(agent, ...)`（从 `status_table` import）
2. `agent.status = X` 直接赋值改为 `set_status(agent, X, reason)`
3. 涉及 yield FinalStep 做失败通知的（如 ④），改为先 yield ErrorStep（表明失败性质）再 yield FinalStep（终态通知前端）
4. 这些路径虽然不经过 _dispatch_handler 的 event type 推断，但状态变更仍需通过合法转换表校验

**为什么不能全部走 yield chain 推断**：这些路径是在编排层主循环中由系统条件触发的（超时、资源限制、配置错误），不是 handler 的处理结果。它们不需要经过 handler → yield chain → dispatch 的路径，直接 set_failed 即可。**关键在于调用 `status_table.set_failed` 而不是 `agent.set_failed`。**

### 3.1 新建：`status_table.py`

**路径**: `backend/app/services/agent/core_agent/status_table.py`

**职责**: 函数式状态机，唯一能改得动 `agent.status` 的地方。纯函数 + 数据表，不用类。

**导出函数**：`set_status(agent, new_status, reason)` 是唯一改得动 `agent.status` 的入口，内部做三件事：查 `_TRANSITIONS` 合法转换表 → 非法时抛 `ValueError` → 合法时赋值并记录日志。另有 3 个快捷函数 `set_failed`、`set_completed`、`set_cancelled`，内部委托 `set_status`。

**日志**：级别 INFO，格式如 `[Agent] AgentStatus.EXECUTING: 准备执行工具调用`。仅记状态流转，不记业务详情。

**线程安全考虑**：
由于 Agent 在单次会话中是单线程运行的（每个会话一个协程），
不需要额外的锁机制。但如果未来支持并发访问，需要在
`set_status` 函数中添加线程锁。

**具体实现方案**：
```python
import threading

# 线程安全的 status_table.py 实现
_status_lock = threading.RLock()

def _synchronized(func):
    """状态操作同步装饰器：确保所有状态变更线程安全"""
    def wrapper(agent, *args, **kwargs):
        with _status_lock:
            return func(agent, *args, **kwargs)
    return wrapper

@_synchronized
def set_status(agent, new_status: AgentStatus, reason: str = ""):
    """线程安全的状态设置函数"""
    allowed = _TRANSITIONS.get(agent.status, set())
    if new_status not in allowed:
        raise ValueError(f"非法转换: {agent.status} → {new_status}")
    
    old_status = agent.status
    agent.status = new_status
    
    if reason:
        logger.info(f"[Agent] {old_status} → {new_status}: {reason}")
    else:
        logger.info(f"[Agent] {old_status} → {new_status}")

@_synchronized
def set_failed(agent, reason=""):
    set_status(agent, AgentStatus.FAILED, reason)

@_synchronized
def set_completed(agent):
    set_status(agent, AgentStatus.COMPLETED)

@_synchronized
def set_cancelled(agent):
    set_status(agent, AgentStatus.CANCELLED)
```

```python
async def _dispatch_handler(self, agent, llm_response, chunk_buffer):
    seen_types = set()
    last_event = None

    # 按响应类型分派 handler
    parsed_type = llm_response.get("type", "answer")
    if parsed_type == "action":
        handler = handle_action(agent, llm_response, chunk_buffer)
    elif parsed_type == "answer":
        handler = handle_answer(agent, llm_response, chunk_buffer)
    elif parsed_type == "error":
        handler = handle_llm_error(agent, llm_response)
    else:
        handler = _handle_unknown(agent, llm_response)

    # 统一遍历：跟踪 event type + 透传
    # 注意：last_error_event 单独跟踪，因为空内容路径 yield 顺序为 ErrorStep → FinalStep，
    # 此时 last_event 是 FinalStep（无 recoverable 属性和错误消息），
    # 必须从 ErrorStep 中提取错误信息和 recoverable 标记
    last_error_event = None
    async for event in handler:
        seen_types.add(event.type)
        last_event = event
        if event.type == "error":
            last_error_event = event
        yield event

    # handler 遍历完毕 → 根据 event type 推断状态
    if "error" in seen_types:
        error_event = last_error_event  # 使用最后一次 ErrorStep，而非 last_event
        error_msg = error_event.get_content() if hasattr(error_event, 'get_content') else ""
        # 第三路：recoverable → SUSPENDED（重试），否则 → FAILED
        if hasattr(error_event, 'recoverable') and error_event.recoverable:
            set_status(agent, AgentStatus.SUSPENDED, error_msg)
        else:
            set_failed(agent, error_msg)
    elif "final" in seen_types:
        set_completed(agent)
    # 否则 continue（不设状态）
```

**改动 4：`run_react_cycle` — while 循环 + 取消处理 + 异常兜底 + 重试（第三路）**

```python
async def run_react_cycle(self, agent, task):
    """核心循环：LLM 调用 → 工具执行 → dispatch → 状态推断 → 重试"""
    chunk_buffer = []
    retry_count = 0
    max_retries = 3
    last_error = ""
    
    while agent.status in (AgentStatus.THINKING, AgentStatus.EXECUTING, AgentStatus.SUSPENDED):
        try:
            # 取消检查
            if agent.cancelled:
                set_cancelled(agent)
                yield agent._step_emitter.emit(FinalStep(step=agent.llm_call_count,
                    agent_status=agent.status.value, response="用户取消"))
                break
            
            if agent.status == AgentStatus.SUSPENDED:
                # 第三路：重试，将上次错误作为 observation 传给 LLM
                retry_count += 1
                if retry_count > max_retries:
                    set_failed(agent, f"重试{max_retries}次仍失败: {last_error}")
                    yield agent._step_emitter.emit(ErrorStep(error_type="retry_exhausted",
                        error_message=f"重试{max_retries}次仍失败: {last_error}"))
                    break
                set_status(agent, AgentStatus.THINKING, f"第{retry_count}次重试")
                if last_error:
                    agent.message_builder.add_assistant_message(
                        f"[系统] 上次工具调用出错，正在重试（{retry_count}/{max_retries}）：{last_error}")
                continue  # 回到循环顶部，执行 LLM 调用
            
            if agent.status != AgentStatus.THINKING:
                set_status(agent, AgentStatus.THINKING)
            llm_response = await agent.llm_client.chat(
                messages=agent.messages,
                tools=agent.enabled_tool_defs,
                stream=True,
                chunk_buffer=chunk_buffer,
            )
            if not llm_response:
                set_failed(agent, "LLM返回空响应")
                yield agent._step_emitter.emit(ErrorStep(error_type="llm_error",
                    error_message="LLM返回空响应"))
                break
            
            # 工具执行（仅 action 类型）
            if llm_response.get("type") == "action":
                set_status(agent, AgentStatus.EXECUTING)
                execute_result = await agent.tool_manager.execute(llm_response, chunk_buffer)
                if execute_result.get("code") != 0:
                    # 判断是否可恢复 — 由 exit_with_error 的 recoverable 参数决定
                    err_msg = str(execute_result) or "工具调用失败"
                    last_error = err_msg
                    # yield ErrorStep(recoverable=True)，_dispatch_handler 会设 SUSPENDED
                    yield agent._step_emitter.emit(ErrorStep(error_type="tool_error",
                        error_message=err_msg, recoverable=True))
                    continue  # 不走 dispatch，直接下一轮循环（重试）
            
            # dispatch handler（yield-only，状态在 _dispatch_handler 中推断）
            async for event in self._process_single_step(agent, llm_response, chunk_buffer):
                if event.type == "observation":
                    obs_text = event.get_content() or ""
                    if obs_text:
                        agent.message_builder.add_observation(obs_text, {})
                elif event.type == "final":
                    response = event.response or ""
                    if response:
                        agent.message_builder.add_assistant_message(response)
                yield event
        
        except asyncio.CancelledError:
            set_cancelled(agent)
            yield agent._step_emitter.emit(ErrorStep(error_type="cancelled",
                error_message="用户取消"))
            break
        
        except Exception as e:
            set_failed(agent, f"循环异常: {e}"[:200])
            yield agent._step_emitter.emit(ErrorStep(error_type="system_error",
                error_message=f"循环异常: {e}"[:200]))
            break
    
    finally:
        # 确保终态有 FinalStep
        if agent.status == AgentStatus.FAILED:
            yield agent._step_emitter.emit(FinalStep(step=agent.llm_call_count,
                agent_status=agent.status.value, response="任务执行失败"))
        _finalize_cycle(agent)
```

**chunk_buffer 说明**：由编排层在 `run_react_cycle` 循环内维护，传给 LLM client 和 tool_manager 做流式数据缓冲，handler 层不碰。

**取消处理流程**：`run_react_cycle` 内每次循环先检查 `agent.cancelled`。取消时调 `set_cancelled(agent)` → yield FinalStep → break。

### 5.3 逐层对比

| 层级 | 维度 | 当前流程 | 新设计 | 好处 |
|------|------|---------|--------|------|
| **运输层** | 状态变更方式 | `agent.status = CANCELLED/FAILED` 直接赋值 | `set_cancelled(agent)` / `set_failed(agent, msg)` | 经过校验入口，非法转换直接报错 |
| **编排层** | 状态变更分散度 | 6 处散布在 _dispatch_handler + run_react_cycle | 全部收敛在 _dispatch_handler + run_react_cycle | 一处改状态，排查问题只需看一个函数 |
| **编排层** | SUSPENDED 重试 | 无（RETRYABLE_ERROR 死代码） | SUSPENDED + _TRANSITIONS + max_retries=3 | 工具恢复失败自动重试，第三路分流完整 |
| **执行层** | handler 职责 | yield 事件 + 设状态 (双重职责) | 只 yield 事件 (单一职责) | SRP 原则，handler 可独立测试 |
| **执行层** | handler 返回方式 | return dict (双通道) | yield-only (单通道) | 简化和清晰，无需解析 return 值 |
| **执行层** | step_emitter | exit_with_error 创建 ErrorStep + 设状态 | 只创建 ErrorStep | 工具层不越权 |
| **执行层** | error_handler | 3 处 set_failed，与 ErrorStep 创建混在一起 | 只创建 ErrorStep | 异常处理与状态管理解耦 |
| **执行层** | LLM context 数据 | handler 直接 message_builder.add_xxx（4 处越界） | handler 只 yield Step，编排层在 yield 透传时统一加 context | handler 零 context 副作用，可独立测试 |
| **状态机** | 合法转换校验 | 无 | _TRANSITIONS 表 + 运行时校验 | 非法转换 → ValueError，500ms 内定位 |
| **状态机** | 状态变更入口 | 8 个文件 14+ 处 | 1 个文件 4 个导出函数 | 加日志/加回调只需改一个地方 |

### 5.4 数据流路径对比

```
当前:
  handler yield 事件 → SSE 流
  handler 设状态   → agent.status (直接/通过 setter)
  handler 加数据   → message_builder (直接调 add_xxx)

新设计 (yield-only):
  handler yield 事件 → SSE 流
                       → _dispatch_handler 从 event type 推断状态 → status_table 设状态
                       → 编排层从 ObservationStep/FinalStep 提取 content → message_builder
  handler 没有其他出口
```

**当前路径**：事件流、状态流、数据流三条通道混在 handler 里。handler 干了它不该干的事。

**yield-only 路径**：handler 只有一个产出通道（yield event）。状态（agent.status）和数据（message_builder）都由编排层从 yield chain 中统一消费。handler 零副作用。

### 5.5 改动好处总结

| 好处 | 说明 | 直接效果 |
|------|------|---------|
| **① 零处直接赋值** | `grep 'agent.status ='` 仅返回 `__init__` 一行 | 新人接手不用猜哪里改了状态 |
| **② 非法转换校验** | `_TRANSITIONS` 表 + `ValueError` | 非法转换在 500ms 内暴露，不等到用户反馈 |
| **③ 层次隔离** | 执行层不碰状态，编排层唯一负责 | handler 改 bug 不会意外改状态；react_cycle 改状态流转不会影响 handler |
| **④ 统一日志** | 所有状态变更都经过 `set_status`，带原因 | 排查问题时 `grep '[Agent]'` 可回溯完整状态变化历史 |
| **⑤ 简化循环+重试机制** | SUSPENDED 取代 RETRYABLE_ERROR，编排层 while 循环统一处理重试 | while 循环逻辑更直白，重试有限次不无限卡死 |
| **⑥ 可扩展性** | 新状态只需加一行到 `_TRANSITIONS` | 状态机扩展只需改一个表 |
| **⑦ handler 可独立测试** | handler 不依赖 agent.status 副作用 | handler 测试可以纯测事件，不 mock 状态 |
| **⑧ yield-only 零双通道** | handler 只 yield，不 return dict | 代码简化，无 StopAsyncIteration 捕获，无 dict 契约 |
| **⑨ 数据流统一** | handler 不直接加 message_builder，编排层统一消费 Step content | handler 零 context 副作用，编排层独占 LLM context 写入权 |

### 6.2 实施顺序说明

第一步先做，确保"统一入口 + 合法转换校验"的基础设施落地，同时删除执行层的状态赋值（error_handler、step_emitter）。此时 handler 仍然通过 `base_agent.set_failed()`（已改为委托）设状态，测试基本不受影响。

第二步改 handler 为 yield-only，这是影响最大的部分。handler 从"yield + set_xxx"变为"只 yield event"，dispatch_handler 从 event type 推断状态。所有 handler 测试需检查 yield 的事件序列是否包含预期的 ErrorStep/FinalStep。这一步才真正实现"handler 零接触状态"。

### 10.3 MessageBuilder Token 监控与截断实现

**问题**：重试时 message_builder 可能累积过多 token，导致 LLM 调用失败。

**具体实现方案**：

```python
# 在 MessageBuilder 类中添加 token 监控和截断方法
class MessageBuilder:
    def __init__(self, max_context_chars: int = 8000):
        self.max_context_chars = max_context_chars
        self.messages = []
        self._token_counter = 0
    
    def get_token_count(self) -> int:
        """获取当前 token 总数（估算）"""
        return self._token_counter
    
    def truncate_early_conversations(self, keep_last_n: int = 3):
        """智能截断：保留最近 N 轮关键对话
        
        策略：
        1. 保留最近的系统提示
        2. 保留最近 N 轮工具调用和结果
        3. 保留所有用户消息
        4. 删除早期的 assistant 消息和 observation
        """
        if len(self.messages) <= keep_last_n * 2:  # 每轮至少2条消息
            return
        
        # 找到最近的工具调用和结果
        tool_calls_and_results = []
        for i, msg in enumerate(reversed(self.messages)):
            if msg.get("role") in ["assistant", "tool"]:
                tool_calls_and_results.append((len(self.messages)-1-i, msg))
            if len(tool_calls_and_results) >= keep_last_n * 2:
                break
        
        # 保留这些消息的索引
        keep_indices = {idx for idx, _ in tool_calls_and_results}
        
        # 保留所有用户消息和系统消息
        for i, msg in enumerate(self.messages):
            if msg.get("role") in ["user", "system"]:
                keep_indices.add(i)
        
        # 重建 messages 列表
        self.messages = [msg for i, msg in enumerate(self.messages) if i in keep_indices]
        
        # 重新计算 token 数
        self._recalculate_tokens()
    
    def _recalculate_tokens(self):
        """重新计算 token 数量（字符级估算，非精确 token 计数）
        
        注意：字符数 ≠ token 数，中英文混合场景下差异明显。
        如需精确计数，建议接入 tiktoken 库（如 self._token_counter = 
        num_tokens_from_messages(self.messages)）。
        当前字符级估算可满足截断判断需求（误差在可接受范围内）。
        """
        self._token_counter = sum(len(str(msg)) for msg in self.messages)
    
    def add_assistant_message(self, content: str):
        """添加 assistant 消息，检查 token 限制"""
        self._check_and_truncate()
        self.messages.append({"role": "assistant", "content": content})
        self._token_counter += len(content)
    
    def add_observation(self, content: str, fc: dict):
        """添加 observation，检查 token 限制"""
        self._check_and_truncate()
        self.messages.append({"role": "tool", "content": content, "fc": fc})
        self._token_counter += len(content) + len(str(fc))
    
    def _check_and_truncate(self):
        """检查 token 数量，超过阈值时截断"""
        threshold = int(self.max_context_chars * 0.8)  # 80%阈值
        if self._token_counter > threshold:
            self.truncate_early_conversations(keep_last_n=3)
```

**在 run_react_cycle 中使用**：

```python
async def run_react_cycle(self, agent, task):
    """核心循环：LLM 调用 → 工具执行 → dispatch → 状态推断 → 重试"""
    chunk_buffer = []
    retry_count = 0
    max_retries = 3
    last_error = ""
    
    while agent.status in (AgentStatus.THINKING, AgentStatus.EXECUTING, AgentStatus.SUSPENDED):
        try:
            # 取消检查
            if agent.cancelled:
                set_cancelled(agent)
                yield agent._step_emitter.emit(FinalStep(step=agent.llm_call_count,
                    agent_status=agent.status.value, response="用户取消"))
                break
            
            if agent.status == AgentStatus.SUSPENDED:
                # 第三路：重试，将上次错误作为 observation 传给 LLM
                retry_count += 1
                
                # 检查重试次数
                if retry_count > max_retries:
                    set_failed(agent, f"重试{max_retries}次仍失败: {last_error}")
                    yield agent._step_emitter.emit(ErrorStep(error_type="retry_exhausted",
                        error_message=f"重试{max_retries}次仍失败: {last_error}"))
                    break
                
                # 检查 token 数量
                current_tokens = agent.message_builder.get_token_count()
                max_tokens = agent.message_builder.max_context_chars
                threshold = int(max_tokens * 0.8)  # 80%阈值
                
                if current_tokens > threshold:
                    # 智能截断：保留最近3轮工具调用和结果
                    agent.message_builder.truncate_early_conversations(keep_last_n=3)
                    logger.info(f"[Agent] Token 超过阈值({current_tokens}/{max_tokens})，已截断早期对话")
                
                # 检查 token 增长趋势（连续重试时）
                if retry_count > 1 and current_tokens > max_tokens * 0.9:
                    set_failed(agent, f"token 超过阈值({current_tokens}/{max_tokens})，停止重试")
                    yield agent._step_emitter.emit(ErrorStep(error_type="token_limit",
                        error_message=f"token 超过阈值({current_tokens}/{max_tokens})，停止重试"))
                    break
                
                set_status(agent, AgentStatus.THINKING, f"第{retry_count}次重试")
                if last_error:
                    agent.message_builder.add_assistant_message(
                        f"[系统] 上次工具调用出错，正在重试（{retry_count}/{max_retries}）：{last_error}")
```

### 10.6 `chunk_buffer` 线程安全说明
由于每个 Agent 实例在单次会话中是独立的，`chunk_buffer` 不需要线程同步。但在重试场景中：
- 重试前不清空 buffer，保留必要的上下文信息
- 确保 buffer 在重试过程中不被污染
- 监控 buffer 大小，防止内存泄漏

**具体实现**：
```python
class ChunkBuffer:
    def __init__(self, max_size: int = 100):
        self.buffer = []
        self.max_size = max_size
        self._lock = threading.RLock()  # 如果需要多线程支持
    
    def add(self, chunk):
        """添加 chunk，自动清理旧数据"""
        with self._lock:  # 如果单协程可省略
            self.buffer.append(chunk)
            # 保持 buffer 大小
            if len(self.buffer) > self.max_size:
                self.buffer = self.buffer[-self.max_size:]
    
    def clear(self):
        """清空 buffer（仅在会话结束时调用）"""
        with self._lock:
            self.buffer.clear()
    
    def get_all(self):
        """获取所有 chunk（复制避免修改）"""
        with self._lock:
            return self.buffer.copy()
```
