## 一、当前架构

### 1.1 重试层级总览

系统重试分两层，位于 LLM 调用链的不同位置：

```
用户请求
  │
  ▼
run_react_cycle()               ← react_cycle.py:255  ReAct循环
  │
  ▼
_process_single_step()          ← react_cycle.py:122  单步处理
  │
  ▼
call_llm_with_fallback()        ← llm_stream.py:154   L2: FC降级重试
  │  循环 2 次, 仅 catch FCFormatError
  │  catch → continue（无反压）
  │  耗尽 → 降级 Text 或返回错误
  │
  ▼
call_llm_stream()               ← llm_stream.py:77   流式封装
  │  内部 try/except 判 isinstance FCFormatError → raise 穿透
  │  stream_error → error response → return
  │
  ▼
request_stream()                ← base_service.py:193 L1: LLM SDK重试
      while 循环 3 次, catch 所有 Exception
      可重试→退避 sleep→continue
      不可重试→yield error_chunk→return
      FCFormatError→raise 穿透（不在此层重试）
```

### 1.2 各层详情

#### L1 — LLM SDK 流式重试

| 属性 | 值 |
|:----|:----|
| 位置 | `base_service.py:210` `request_stream()` |
| 循环模式 | `while retry_count <= max_retries` |
| 最大重试 | `LLM_STREAM_MAX_RETRIES = 3`（`llm_constants.py:12`） |
| 退避策略 | `2 ** retry_count`（2s, 4s, 8s） |
| 可重试判断 | `UnifiedErrorClassifier.classify_error(e).is_retryable` |
| 可重试 7 类 | TIMEOUT / NETWORK / CONNECT / PROTOCOL / API_RATE_LIMIT / IDLE_TIMEOUT / SERVER |
| FCFormatError | 不在此层重试，`except _FCFormatError: raise` 穿透 |

#### L2 — FC 降级重试

| 属性 | 值 |
|:----|:----|
| 位置 | `llm_stream.py:161` `call_llm_with_fallback()` |
| 循环模式 | `for attempt in range(FC_MAX_RETRIES)` |
| 最大重试 | `FC_MAX_RETRIES = 2`（`llm_constants.py:17`） |
| 退避策略 | 无（`continue` 立即重试） |
| 触发条件 | 仅 `FCFormatError`（所有 tool_call 参数 JSON 解析失败） |
| 耗尽后 | `FC_FALLBACK_ENABLED` 为 True → 降级 Text 模式；否则 → 返回错误 |

### 1.3 错误判定机制

`UnifiedErrorClassifier.classify_error()`（`error_classifier.py:252`）按 6 步逐级判定：
1. 特殊错误（IdleTimeoutError、FCFormatError → INVALID_PARAMS）
2. httpx 异常名匹配
3. Python 内置异常 isinstance（TimeoutError、PermissionError 等）
4. 模式匹配（类型名 + 关键词）
5. HTTP 状态码（字符串包含）
6. 关键词匹配（"rate limit"、"unauthorized" 等）

最终 7 类标记为 `is_retryable`。

## 二、问题分析

### 2.1 问题清单

| 编号 | 问题 | 位置 | 等级 | 性质 |
|:----:|------|:----:|:----:|:----:|
| A | L1 退避首跳 2s 过高 | `base_service.py:299` | P3 | 参数不合理 |
| B | L2 FC 重试无反压 | `llm_stream.py:169` | P3 | 策略缺失 |
| C | 无重试可观测性 | L1+L2 全域 | P2 | 体验缺失 |
| D | FCFormatError 无结构化 detail | `core.py:16-18` | P3 | 信息缺失 |
| E | inline import ×3 | `base_service.py:204/208/386` | P3 | 代码不规范 |
| F | 注释残留 RETRYABLE_ERROR | `react_cycle.py:100` | P3 | 文档陈旧 |

**当前没有 P0/P1 问题。** 重试机制功能正确，上述问题均为优化项。

### 2.2 逐项分析

#### 问题 A：L1 退避首跳 2s

`base_service.py:299`:
```python
wait_time = 2 ** retry_count
```

retry_count=1 时首跳 2s。对于 <100ms 的瞬态网络波动（TCP 丢包重传、DNS 抖动），用户也要等待 2s。

#### 问题 B：L2 FC 重试无反压

`llm_stream.py:168-169`:
```python
except FCFormatError as e:
    continue  # 立即重试
```

FCFormatError 场景：LLM 在 tool_call arguments 中生成了无法解析的 JSON。如果 LLM 当前状态导致它生成坏 JSON，立即重试大概率还是坏 JSON。两次白消耗后才去降级 Text。

#### 问题 C：无重试可观测性

L1 和 L2 重试时仅在日志中有一行记录，前端流式事件中完全没有。用户看到的只是长时间"等待"，无法区分"系统在自动重试" vs "真的卡死了"。

#### 问题 D：FCFormatError 无 detail

`core.py:16-18`:
```python
class FCFormatError(Exception):
    pass
```

抛出处（`base_service.py:286-287`）传字符串：
```python
raise _FCFormatError(f"所有tool_calls参数解析失败: {failed_parses}")
```

到 L2 catch 处只能拿到字符串，无法程序化获取 `failed_parses` 列表来分析具体哪些 tool 解析失败。

#### 问题 E：3 处 inline import

| 行号 | import |
|:----:|--------|
| 204 | `from app.services.llm.llm_constants import LLM_STREAM_MAX_RETRIES, LLM_STREAM_OPTIONS` |
| 208 | `from app.services.llm.core import FCFormatError as _FCFormatError` |
| 386 | `from app.utils.error_classifier import UnifiedErrorClassifier` |

没有循环引用必要（`error_classifier.py` 不引用 `app.services`），应移到模块级。

#### 问题 F：注释残留

`react_cycle.py:100`:
```
P0-5 RETRYABLE_ERROR不应补发FinalStep
```
RETRYABLE_ERROR 枚举已删除（commit 70ab81cbd），注释过时。

## 三、新设计

### 3.1 设计原则

1. **不改变架构**：L1 和 L2 处理不同的错误类型（网络 vs FC），在不同抽象层，保持分离
2. **最小改动**：只改参数和细节，不引入新架构
3. **向前兼容**：所有变更对外部调用方透明

### 3.2 新架构对比

```
改前:                                   改后:
┌──────────────────┐                   ┌──────────────────┐
│ base_service     │                   │ base_service      │
│ L1: 2s/4s/8s     │                   │ L1: 1s/2s/4s cap10│
│ silent retry     │                   │ + [Retry][L1] 日志│
│ 3 inline import  │                   │ 模块级 import     │
└──────┬───────────┘                   └──────┬────────────┘
       │                                      │
       ▼                                      ▼
┌──────────────────┐                   ┌──────────────────┐
│ llm_stream       │                   │ llm_stream        │
│ L2: 无反压       │                   │ L2: 0.5s 反压     │
│ FCFormatError    │                   │ FCFormatError      │
│ 无 detail        │                   │ 带 details dict   │
└──────────────────┘                   └───────────────────┘
```

### 3.3 设计决策记录

| 决策 | 选项 | 选择 | 理由 |
|:----|:----|:----:|:------|
| L1 退避 | 固定 2s / `0.5×2^n` capped / Full Jitter | `0.5×2^n` cap 10 | 首跳 1s 覆盖瞬态抖动，cap 防 future overflow |
| L2 反压 | 无 / 固定 0.5s / 指数退避 | 固定 0.5s | 只需躲过 LLM 瞬时状态，不需要指数 |
| L1+L2 合并 | 统一 RetryHandler | **否** | 不同错误类型、不同抽象层，硬合增加耦合 |
| 重试事件 | MetaStep yield / 仅有日志 | **仅有日志** | L1 无 agent 引用，yield MetaStep 需要加耦合到 agent，不值得 |
| FCFormatError 构造 | 改 `__init__` / 保持 pass | 改 `__init__` | 加 details 字段可程序化访问 |
| inline import | 移到模块级 / 保持方法内 | 移到模块级 | 无循环引用风险 |

### 3.5 FCFormatError 兼容说明

旧用法 `raise _FCFormatError("字符串")` 在新设计下仍然兼容（`message` 参数有默认值 `"FC格式错误"`）。外部代码 catch `FCFormatError` 不需要改——`str(e)` 仍然返回可读字符串。

推荐新用法：
```python
raise _FCFormatError(message="...", details={...})
```

catch 方可访问 `e.details` 获取结构化信息。

### 3.6 各模块详细改动

#### 3.6.1 L1 退避公式 — base_service.py:299

```diff

```

| retry_count | 改前 | 改后 |
|:-----------:|:----:|:----:|
| 1（首试失败）| 2s | 1s |
| 2 | 4s | 2s |
| 3 | 8s | 4s |

同步强化日志前缀，方便 grep：

```diff

+                    logger.warning(f"[Retry][L1] 重试 {retry_count}/{max_retries}, 等待{wait_time:.1f}s, 错误: {e}")
```

#### 3.6.2 L2 反压 — llm_stream.py:168-169

```diff
         except FCFormatError as e:
             last_error = e
-            logger.warning(f"[FC降级] FC模式第{attempt+1}次失败: {e}")
+            logger.warning(f"[Retry][L2] FC模式第{attempt+1}/{FC_MAX_RETRIES}次失败: {e}")
```

0.5s 固定延迟。理由：
- 只需要让 LLM 的瞬时状态过去
- 固定延迟足够，不是网络重试不需要指数退避
- 和 L1 的 1s 首跳拉开差距，避免两层退避混叠

## 四、不做的内容

- ❌ 不合 L1+L2（不同层、不同错误类型）
- ❌ 不前端的重试 UI（只加强日志）
- ❌ 不重构 `UnifiedErrorClassifier` God Class（改动大、风险高、与重试无关）
- ❌ 不涉及 `tool_retry_engine.py`（独立的工具级重试子系统，完全不在本次范围）
