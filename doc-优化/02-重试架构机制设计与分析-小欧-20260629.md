## 一、概述

### 1.1 重试机制分类

本文档覆盖两类重试机制，逐章独立分析：

| 分类 | 范围 | 机制 | 章节 |
|------|------|------|------|
| **系统重试** | LLM通信层，与tool零关系 | L1: LLM流重试 + L2: FC降级重试 | §二~§四 |
| **工具重试** | tool执行层 | Tool-1: ToolRetryEngine外部重试 + Tool-2: 内建重试(待取消) | §五~§七 |
| **非重试**（仅列出，不分析）| 编排层 | 截断重试 / Tool-less重试 | §1.2(全景) |

**核心分界**：
- 系统重试：LLM通信层的故障恢复，**不调用任何tool函数**
- 工具重试：tool函数调用时的临时性故障恢复，**与LLM通信层无关**

### 1.2 现有机制全景

```
系统重试（与tool无关）:
  L1: LLM SDK流重试    ─── base_service.py:210      ✅ 生效
  L2: FC降级重试       ─── llm_stream.py:161        ✅ 生效

工具重试（与tool相关）:
  Tool-1 外部重试      ─── ToolRetryEngine           ✅ 可选共享工具
  Tool-2 内建重试      ─── http_request              🔴 待取消→并入Tool-1

非重试（编排层循环控制）:
  截断重试             ─── react_cycle.py:214       ✅ observation注入→继续
  Tool-less重试        ─── react_cycle.py:191       ✅ observation注入→继续
```

### 1.3 核心原则

1. **系统重试与工具重试完全独立** — L1/L2 只与 LLM 通信有关，Tool-1/Tool-2 只与 tool 执行有关，互不干涉
2. **各 tool 自己决定是否重试** — ToolRetryEngine 是共享工具，不是强制框架

### 1.4 一句话矩阵

```
           ┌── 系统级（LLM层） ── L1 base_service（HTTP传输）
           │                    L2 llm_stream（FC格式）
重试机制 ──┤
           └── 工具级（tool层） ── Tool-1 ToolRetryEngine（外部）
                                   Tool-2 内建（待取消）
```

## 二、系统重试现状分析（L1/L2）

### 2.1 L1: LLM 流重试

**文件**: `base_service.py:203-305`

```python
retry_count = 0
max_retries = LLM_STREAM_MAX_RETRIES  # =3
while retry_count <= max_retries:
    try:
        ...
    except _FCFormatError:
        raise  # FCFormatError 穿透，不由 L1 处理
    except Exception as e:
        if self._should_retry(e) and retry_count < max_retries:
            retry_count += 1
            wait_time = 2 ** retry_count  # 2s, 4s, 8s
            await asyncio.sleep(wait_time)
            continue
        else:
            yield error_chunk; return
```

**`_should_retry`** —— `base_service.py:384-387`：

```python
def _should_retry(self, e):
    return UnifiedErrorClassifier.classify_error(e).is_retryable
```

| 维度 | 值 |
|------|-----|
| 最大重试 | 3（`LLM_STREAM_MAX_RETRIES`） |
| 退避策略 | 指数退避 `2^retry`（2s → 4s → 8s） |
| 可重试判断 | `UnifiedErrorClassifier.classify_error(e).is_retryable` |
| 可重试类型 | TIMEOUT / NETWORK / CONNECT / PROTOCOL / API_RATE_LIMIT / IDLE_TIMEOUT / SERVER |
| 例外穿透 | `FCFormatError` 不在此层处理，原样抛出 |

## 三、系统重试问题（L1/L2）

### 问题 P1-L1: 退避首跳 2s 偏高（P3）

**严重程度**：P3-低

**描述**：`wait_time = 2 ** retry_count`，首次重试（retry_count=1）等待 2s。对于瞬时网络闪断（<100ms级别），2s首退偏保守。

**影响**：用户体验上，10ms的网络瞬时抖动需要等待 2s 才恢复。

### 问题 P2-L2: FC 重试无反压无退避（P3）

**严重程度**：P3-低

**描述**：`for attempt in range(FC_MAX_RETRIES)` 中 `continue` 后立即重试，无退避。FC 格式错误来自 LLM 同一个模型实例，连续 2 次几乎同时失败，降级效率不受影响（因为即使有退避，降级是必然结果，只是快慢差别）。

**影响**：无功能影响。仅在 LLM 返回"错误好但解析失败"的极端情况下略有冗余调用。

### 问题 P3: 无重试事件可观测性（P2）

**严重程度**：P2-中

**描述**：L1 和 L2 的重试触发/成功/耗尽都只有 `logger.warning` 日志，前端 SSE 事件流中无重试事件。用户看不到"系统正在重试"的反馈。

**影响**：用户感知上，长时间等待但无反馈。

### 问题评估总览

| 编号 | 描述 | 严重程度 | 当前状态 |
|------|------|---------|---------|
| P1-L1 | 退避首跳2s偏高 | P3 | 非必改，优化建议 |
| P2-L2 | FC重试无反压 | P3 | 非必改，优化建议 |
| P3 | 无可观测性 | P2 | 可改可不改 |

**结论**：L1/L2 当前运行正常，三个问题均为非功能性优化建议，不阻塞功能。

## 四、系统重试修改策略

### 4.1 当前方案

L1/L2 当前运行正常，无阻塞性问题。无需紧急修改。

### 4.2 优化建议（可选）

| 问题 | 优化方案 | 工作量 |
|------|---------|:------:|
| P1-L1 | 退避策略改为 `min(0.5 * 2^retry, 10)` 降低首跳延迟 | ~3行 |
| P2-L2 | FC重试间加 0.5s 退避 | ~2行 |
| P3 | L1/L2 重试触发时 emit `MetaStep.retrying` 事件到前端 | ~10行 |

**不做**：
- ❌ L1 不加 jitter（单用户场景不需要）
- ❌ L2 不加指数退避（仅2次重试没必要）
- ❌ L1/L2 不加独立计数器（系统重试次数固定且合理）

### 5.2 Tool-1: ToolRetryEngine 外部重试

`tool_retry_engine.py:153-157`：

```python
def _should_retry(self, e, retryable_errors, engine):
    error_category = UnifiedErrorClassifier.classify_error(e)
    is_retryable = error_category.is_retryable or error_category.name.lower() in retryable_errors
    return is_retryable and not engine.exhausted
```

两个条件任意满足则重试：

| 条件 | 来源 | 覆盖范围 |
|------|------|---------|
| `ErrorCategory.is_retryable` | 通用分类器 | TIMEOUT, NETWORK, CONNECT, PROTOCOL, API_RATE_LIMIT, IDLE_TIMEOUT, SERVER |
| `TOOL_RETRYABLE_ERRORS["default"]` | 工具配置 | 当前仅 `["timeout"]` |

### 5.3 Tool-2: 工具内建重试（现状）

| 工具 | 方式 | 默认值 | 当前问题 |
|------|------|:------:|---------|
| **http_request** | 内建 `retry` 参数，`for` 循环 + 指数退避 | 3 | 和 ToolRetryEngine 叠加 → 3×3 双重重试 |
| **fetch_webpage** | Cloudflare 403 fallback（特定场景） | - | 非通用重试，是业务降级策略 |
| **search_web** | 多引擎级联 Parallel→Exa→Bing | - | 非重试，是多引擎策略 |
| **其他所有工具** | 无自实现重试 | - | - |

### 5.4 废弃状态: RETRYABLE_ERROR 枚举

`RETRYABLE_ERROR` 是废弃的枚举值，与普通 tool 错误（文件不存在/权限拒绝等）一样处理——`set_failed()` → 对话结束。无特殊路径。

| 位置 | 代码 | 事实 |
|------|------|------|
| `agent_status.py:19` | `RETRYABLE_ERROR = "retryable_error"` | 枚举定义，无人设 |
| `react_cycle.py:294-296` | `if agent.status == RETRYABLE_ERROR:` | 死代码，条件永假 |
| `react_cycle.py:311` | `not in (... RETRYABLE_ERROR ...)` | 冗余 |
| `react_cycle.py:327` | `if status != RETRYABLE_ERROR:` | 永远为 True |
| `step_emitter.py:28-37` | `exit_with_error()` 先 `set_failed()` | recoverable 参数被忽略 |

**根因**：设计文档（v1.8）要求特殊处理路径，但代码从未改过。现确认 RETRYABLE_ERROR 不特殊处理，和普通 tool 错误一样对待。

## 六、工具级重试问题

### 问题 T1: ToolRetryEngine 强制所有工具走统一重试（P1）

**严重程度**：P1-高

**描述**：`tool_executor.py` 自动把所有工具的执行都包在 `ToolRetryEngine` 里，`TOOL_RETRY_MAX` 只有 `{"default": 3}`。各 tool 没有选择权——要么全部重试，要么全部不重试。FILE/REGISTRY/DESKTOP 等本地操作也被迫重试 3 次。

**影响**：各 tool 不能独立决定自己的重试策略。file 操作不需要重试，但被迫等 3 次超时。

### 问题 T2: http_request 与 ToolRetryEngine 双重重试（P1）

**严重程度**：P1-高

**描述**：http_request 有自己的内建 retry 参数（retry=3），同时又被 ToolRetryEngine 统一重试。两条重试路径叠加。

执行链：
```
action_handler → ToolRetryEngine (重试3次)
                    → http_request (内建 retry=3)
```

最坏情况 3×3=9 次网络调用后失败。

### 问题 T3: RETRYABLE_ERROR 是废弃枚举（P3）

**严重程度**：P3-低

**描述**：`RETRYABLE_ERROR` 枚举定义在 `agent_status.py:19`，但无人设置。react_cycle.py:294 的分支条件永远为假。这本身**不是问题**——RETRYABLE_ERROR 和普通 tool 错误一样 `set_failed()` → 结束，不需要特殊处理路径。只是历史遗留的死代码，可清理。

### 问题 T4: TOOL_RETRYABLE_ERRORS 只有 timeout（P2）

**严重程度**：P2-中

**描述**：`TOOL_RETRYABLE_ERRORS["default"] = ["timeout"]`，只有 timeout 被显式配置。网络错误、连接错误等都依赖 `UnifiedErrorClassifier.is_retryable` 的判断。配置不够精细。

### 问题 T5: ToolRetryEngine 缺少灵活配置（P2）

**严重程度**：P2-中

**描述**：ToolRetryEngine 当前配置只有 `{"default": 3}` 一刀切，没有给选择使用它的工具提供灵活配置（按工具名或按 ToolCategory 区分）。

### 问题 TR6: error_handler 分类与 UnifiedErrorClassifier 重叠（P2）

**严重程度**：P2-中

**描述**：`error_handler._classify_error` 自己再做一次分类（fc_format / network / unknown 三路），与 `UnifiedErrorClassifier.classify_error`（14 类）重叠。两套分类结果可能不一致。

## 七、工具级重试修改策略

### 7.1 基本原则

1. **各 tool 自己决定是否重试**：ToolRetryEngine 是共享工具，不是强制框架
2. **消除双重重试**：取消 http_request 的内建重试，改用 ToolRetryEngine
3. **谁用谁配**：使用 ToolRetryEngine 的 tools 按需配置，不用的不配
4. **只用一个引擎**：ToolRetryEngine 内联 RetryEngine 的 while 循环逻辑，不保留两层引擎

#### 7.1.1 需要 ToolRetryEngine 重试的 tool（共 7 个）

| 工具 | 分类 | 重试次数 | 可重试错误 |
|------|------|:--------:|-----------|
| **http_request** | NETWORK | 3 | timeout, network, connect, protocol, rate_limit, server |
| **fetch_webpage** | NETWORK | 3 | timeout, network, connect, protocol, rate_limit, server |
| **download_file** | NETWORK | 3 | timeout, network, connect, protocol, rate_limit, server |
| **search_web** | NETWORK | 3 | timeout, network, connect, protocol, rate_limit, server |
| **network_diagnose** | NETWORK | 3 | timeout, network, connect, protocol, rate_limit, server |
| **execute_shell_command** | SHELL | 2 | timeout |
| **execute_code** | SHELL | 2 | timeout |

#### 7.1.2 不需要 ToolRetryEngine 重试的工具（55 个）

| 分类 | 工具数 | 理由 |
|------|:-----:|------|
| FILE (13) | read/write/edit/copy/move/delete/rename/list/search/grep/compress/extract/media | 本地文件操作，无临时故障 |
| DESKTOP (11) | mouse/keyboard/screen/clipboard/window | 本地桌面操作 |
| DOCUMENT (8) | read/write docx/pdf/pptx/xlsx | 本地文档读写 |
| DATAANALYSIS (6) | query/execute sql, analyze/filter/chart/db_schema | 纯内存/本地计算 |
| FUNDAMENTAL (7) | time/tool_search/system_info/calendar/notification | 本地操作 |
| SYSTEM (4) | task crud, event_log | 本地系统操作 |
| TIMER (3) | timer_set/list/clear | 注册回调 |
| WIN_REGISTRY (3) | registry_read/write/delete | 本地注册表操作 |

#### 7.1.3 非重试的业务策略（tool 自己实现，ToolRetryEngine 不管）

| 工具 | 机制 | 说明 |
|------|------|------|
| **fetch_webpage** | 403 CF 降级 | 遇到 CF 挑战时换 User-Agent 再试 1 次。不是循环重试，是单次降级策略 |
| **search_web** | 多引擎级联 | 一个引擎搜不到→换引擎。不是"重试同一次调用"，是"换源搜" |

#### 7.1.4 Tool-1 外部重试执行链

```
执行流程：

tool_executor.py                入口
  execute_tool(tool_name, params)
       │
       ▼
ToolRetryEngine                 工具级重试（处理临时性故障）
  execute_tool_with_retry():
    ├─ _get_retry_config() → 查 tool 名字典
    │   ├─ 命中配置（7 个工具）→ max_retries>0 → 走重试循环
    │   └─ 未命中配置（其他 55 个）→ max_retries=0 → 直通
    │
    ├─ 重试循环（max_retries>0 时）：
    │   loop: execute_once()
    │     ├─ error ∈ retryable → backoff sleep → 继续循环
    │     ├─ error ∉ retryable → 立即中断，返回当前 error
    │     └─ attempt ≥ max_retries → 返回最后一次 error
    │
    └─ 返回最终结果（成功或最终 error）
       │
       ▼
action_handler                  收到结果
    ├─ 成功 → 正常继续
    └─ 执行失败 → set_failed() → 结束
```

**工具执行失败后的所有错误统一处理**，不区分 error_type，一律 `set_failed()` → 对话结束。

#### 7.1.5 Tool-1 与 Tool-2 的关系

| 维度 | Tool-1 外部重试（ToolRetryEngine） | Tool-2 内部重试（tool 自建） |
|------|-----------------------------------|---------------------------|
| 位置 | tool 函数外编排 | tool 函数内 |
| 调用方式 | 每次 clean call，不感知重试 | tool 自己管理循环 |
| 当前使用 | 7 个 NETWORK/SHELL tool | 待取消（http_request 原用） |
| 是否独立 | 不依赖对方 | 不依赖对方 |
| 谁先谁后 | 先执行 | 先执行（但不应同时存在） |

当前系统**没有** tool 需要 Tool-1 + Tool-2 两层重试。已有案例 `http_request` 被确认为双重重试 bug，修复方案为取消内建重试（Tool-2）、改用 ToolRetryEngine（Tool-1）。

### 7.2 修改 T1: ToolRetryEngine 按需配置

### 7.3 修改 T2: 消除双重重试（http_request）

#### 7.3.1 问题

http_request 是当前**唯一**一个既有内部重试又被 ToolRetryEngine 包裹的工具：

| 层级 | 重试次数 | 退避 | 是否生效 |
|------|---------|------|---------|
| L0：内部循环 `for attempt in range(retry+1)` | 默认 3 | `0.5×2ⁿ`，上限 10s | ✅ 生效 |
| L1：ToolRetryEngine `_execute_with_retry` | 默认 3 | `2ⁿ` | ❌ 被绕过（http_request 永不抛异常，全 catch 回 dict）|

#### 7.3.2 分析：ToolRetryEngine 能否替代

| 异常类型 | http_request 内部 | ToolRetryEngine（tool `retryable` 列表） | 结果 |
|---------|-----------------|----------------------------------------|------|
| `TimeoutException` | ✅ 重试 | `"timeout" in retryable` | ✅ 等价 |
| `HTTPStatusError(500/502/503/504)` | ✅ 重试 | `"server" in retryable` | ✅ 等价 |
| `HTTPStatusError(429)` | ✅ 重试 | `"rate_limit" in retryable` | ✅ 等价 |
| `ConnectError` | ✅ 重试 | `"connect" in retryable` | ✅ 等价 |
| `NetworkError` | ✅ 重试 | `"network" in retryable` | ✅ 等价 |
| `HTTPStatusError(403/404/400/401)` | ❌ 不重试 | 不在显式清单中 | ✅ 等价 |

**结论**：`TOOL_RETRY_CONFIG` 中 http_request 的 `retryable` 已全部覆盖内建重试的 5 种场景。

#### 7.3.3 具体改动

| 改动 | 文件 | 说明 |
|------|------|------|
| 删除 `for attempt in range(retry+1)` 循环 | `http_request.py:163-197` | 不再自己处理重试 |
| 删除 `retry` 参数 | `http_request.py` + `network_schema.py` | LLM 不需要控制重试次数 |
| 404/403 等非重试状态码仍 catch 后 `build_error` | `http_request.py` | 不传播异常到 ToolRetryEngine |
| 超时/5xx/429/连接失败 → **不 catch，让异常传播** | `http_request.py` | ToolRetryEngine 按 tool retryable 判→重试 |

## 八、系统重试与工具重试的关系

### 8.1 两条独立路径

```
系统重试路径（L1/L2，LLM通信层，与tool无关）:
  LLM 调用 → 网络超时/5xx/FC格式错误
       ↓
  L1 base_service 重试（3次指数退避）
  L2 llm_stream 降级（2次FC→Text）
       ↓
  重试成功 → 正常返回
  重试耗尽 → 生成错误chunk/降级Text

工具重试路径（Tool-1，tool执行层）:
  tool 调用 → 抛异常/返回error
       ↓
  ToolRetryEngine 重试（按分类配置）
       ↓
  重试成功 → 正常返回
  重试耗尽 → 返回error dict → action_handler → set_failed() → 结束
```

### 8.2 职责划分

| 场景 | 谁处理 | 方式 |
|------|--------|------|
| LLM 网络超时，L1 第 2 次成功 | L1 | 透明，上层无感 |
| LLM FC 格式错误，L2 降级 Text | L2 | 透传至调用者 |
| tool 网络闪断，ToolRetryEngine 第 2 次成功 | Tool-1 | 透明，上层无感 |
| tool 超时，ToolRetryEngine 3 次耗尽 | Tool-1 | 返回 error dict → set_failed() |

### 8.3 不重叠原则

```
系统重试 ≠ 工具重试
─────────   ─────────
对象：LLM 通信    对象：tool 函数调用
条件：错误可重试   条件：error ∈ 配置
上限：3次(L1)     上限：各分类配置
     2次(L2)
退避：指数退避     退避：指数退避
```
