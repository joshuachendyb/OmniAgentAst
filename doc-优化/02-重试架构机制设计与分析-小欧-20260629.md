## 一、概述

### 1.1 核心设计原则

重试分两级，各自独立、互不干扰：

```
工具级重试（各 tool 自己管）       系统级重试（RETRYABLE_ERROR）
─────────────────────────────    ────────────────────────────────
一层：工具执行时的网络/超时重试     二层：action_handler 按 error_type 判 recoverable
透明：重试成功对上层无感           透明：react_cycle 自动设 THINKING + continue
工具：各 tool 自己决定             范围：仅 RECOVERABLE_TYPES（tool_not_found/missing_param/invalid_params）
上限：各 tool 自定                 上限：max_steps（循环自然上限，无独立计数器）
```

| 维度 | 工具级 | 系统级 |
|------|--------|--------|
| **触发时机** | 工具执行抛异常（超时/网络） | `action_handler` 收到 `result.error_type` 在 `RECOVERABLE_TYPES` 中 |
| **决策者** | 各 tool 自己的重试逻辑（ToolRetryEngine 是其中一种） | `action_handler` 直接按 error_type 设 RETRYABLE_ERROR |
| **计数器** | 各 tool 自定（ToolRetryEngine 用 `RetryEngine.attempt_count`） | `max_steps`（循环自然上限，无独立计数器） |
| **失败后果** | 返回 error dict（含 retry_count） | 设 `agent.status = RETRYABLE_ERROR` |
| **重试成功** | 返回正常 result，上层无感知 | `react_cycle` 自动设 `agent.status = THINKING`，继续循环 |
| **适用工具** | 各 tool 自己决定（可复用 ToolRetryEngine 或自实现） | 仅三类可恢复错误（LLM 换策略能救的） |
| **最大次数** | 各 tool 自定（ToolRetryEngine 默认 3） | `max_steps`（循环自然上限） |
| **退避策略** | 各 tool 自定（ToolRetryEngine 默认指数退避 backoff=2.0） | 立即（编排层重试不等待） |

### 1.3 核心原则：系统级 recoverable 只看 error_type，不依赖工具级重试次数

```
系统级可恢复（RECOVERABLE_TYPES）   recoverable    含义
─────────────────────────────     ───────────    ──────────────────────────
tool_not_found                     True          LLM 可换一个 tool
missing_param                      True          LLM 可补全参数后重试
invalid_params                     True          LLM 可修正参数后重试
─────────────────────────────     ───────────    ──────────────────────────
timeout / network / 5xx / 429      False         ToolRetryEngine 已处理过
文件不存在 / 权限拒绝               False         再试也还是不存在
参数非法 / 解析错误                 False         LLM 自己犯的错，改 prompt 才有用
```

**关键**：timeout/network/5xx/429 等错误**不过系统级 recoverable 层**。它们由 ToolRetryEngine（工具级）处理——重试成功则透明，重试耗尽则返回 error dict 给 LLM。action_handler 按 `result.error_type` 判 recoverable，只有 `RECOVERABLE_TYPES` 中的三类才会设 `RETRYABLE_ERROR`。

**两级完全独立**：无论 ToolRetryEngine 重试 0 次还是 3 次，action_handler 只看 error_type。recoverable 不依赖工具级重试是否耗尽。
```

### 1.2 现有机制全景（标注两级归属）

```
┌──────────────────────────────────────────────────────────────┐
│                    7层重试归属两级                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  工具级（各 tool 函数独立管自己的重试）:                          │
│  ├── Layer 3: 工具执行重试 ─── tool_retry_engine.py  ✅ 可选 │
│  │              共享工具，各 tool 可以选择是否复用              │
│  └── Layer 7: 工具内建重试 ─── http_request.py         ✅ 保留 │
│                  http_request 自己管自己的重试                 │
│                  不与 ToolRetryEngine 叠加                     │
│                                                              │
│  系统级（编排层 + LLM 层）:                                      │
│  ├── Layer 1: LLM SDK重试   ─── base_service.py        ✅ 保留 │
│  │              LLM 客户端内建重试（http 调用层面）            │
│  ├── Layer 2: FC降级重试    ─── llm_stream.py           ✅ 保留 │
│  ├── Layer 4: 截断重试      ─── react_cycle.py          ✅ 并入│
│  │                                          RetryTracker      │
│  ├── Layer 5: Tool-less重试 ─── react_cycle.py          ✅ 并入│
│  │                                          RetryTracker      │
  │  └── Layer 6: RETRYABLE_ERROR─ react_cycle.py           🔴 死 │
  │                              → RETRYABLE_ERROR  代码           │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 三、系统级重试问题

### 问题 S1: RETRYABLE_ERROR 是 100% 死代码（P0）

**严重程度**：P0-紧急

**影响**：设计文档（v1.8）的 SUSPENDED 三路分流机制无法落地。本方案采用最小改动（§4），不引入 SUSPENDED，不涉及三路分流，因此此问题在最小方案中不直接存在。实际问题是：action_handler 不按 error_type 判 recoverable，所有工具错误都 FAILED。

### 问题 S2: action_handler 不判 error_type（P0）

**严重程度**：P0-紧急

**描述**：无论 error_type 是什么，action_handler 收到 tool error dict 后一律 `set_failed()`。`tool_not_found`、`missing_param`、`invalid_params` 等 LLM 换策略能救的错误也被当作不可恢复处理。

**影响**：本该走 RETRYABLE_ERROR 让 LLM 重试的错误直接结束对话。本方案改动点就是修这个——action_handler 按 error_type 设 RETRYABLE_ERROR 或 FAILED。

### 问题 S3: 编排层重试分散计数（P1）—— 最小方案已消除

**严重程度**：已解决（最小方案不做独立计数器）

**描述**：旧 SUSPENDED 方案需要 RetryTracker 统一管理截断重试、Tool-less 重试、SUSPENDED 重试三个计数器。

**本方案**：不加独立计数器。系统级重试由 `max_steps` 自然兜底——action_handler 设 RETRYABLE_ERROR → react_cycle 继续循环 → LLM 再次尝试。总轮次受 `max_steps` 限制，不设独立上限。

### 问题 S4: error_handler 分类与 UnifiedErrorClassifier 重叠（P2）

**严重程度**：P2-中

**描述**：`error_handler._classify_error` 自己再做一次分类（fc_format / network / unknown 三路），与 `UnifiedErrorClassifier.classify_error`（14 类）重叠。两套分类结果可能不一致。

### 问题 S5: 前段看不到重试信息（P2）

**严重程度**：P2-中

**描述**：前端 SSE 事件流中无重试事件，用户看不到"系统正在重试"的反馈。

## 四、系统级重试修改策略

### 4.1 现状

当前 RETRYABLE_ERROR 是 100% 死代码。状态枚举存在但无人设置，react_cycle 的处理分支存在但无人触发：

| 位置 | 代码 | 事实 |
|------|------|------|
| `agent_status.py:19` | `RETRYABLE_ERROR = "retryable_error"` | 枚举定义，无人设 |
| `react_cycle.py:294-295` | `if agent.status == RETRYABLE_ERROR: agent.status = THINKING; continue` | 条件永假，从未执行 |
| `step_emitter.py:28-37` | `exit_with_error()` 先 `set_failed()` 再 emit ErrorStep | recoverable 参数被忽略 |

### 4.2 修改方案

**原则：最小改动，只做两件事：**

1. `action_handler` 执行完工具后按 `result.error_type` 判 recoverable，设 `RETRYABLE_ERROR` 或 `FAILED`
2. 确认 `react_cycle.py:294-296` 的 `RETRYABLE_ERROR` 分支正常工作

**不需要做的：**
- ❌ 不改枚举名（RETRYABLE_ERROR 保留，不叫 SUSPENDED）
- ❌ 不加 RetryTracker（react_cycle 的 `max_steps` 是自然上限，不需要独立计数器）
- ❌ 不改 `_dispatch_handler`（action_handler 直接设状态，不经过 dispatch_handler 中转）
- ❌ 不加独立状态机（`RETRYABLE_ERROR → THINKING → continue` 已在 react_cycle 中）
- ❌ 不加前端 retrying 事件（最小 P0 改动，可观测性以后做）

### 4.3 修改 S1: action_handler 设 RETRYABLE_ERROR

**文件**: `action_handler.py`

`action_handler` 在收到工具 error 时，根据 `result.error_type` 决定 `recoverable`：

```
# action_handler 收到 ToolRetryEngine 返回的最终结果
result = execute_tools(...)

if result.status == "error":
    if result.error_type in {"tool_not_found", "missing_param", "invalid_params"}:
        agent.status = RETRYABLE_ERROR          # 可恢复—让 LLM 换策略
    else:
        agent.set_failed("不可恢复：" + error)   # 不可恢复—直接结束

    yield ErrorStep(step, error_type, error_message, recoverable=recoverable)
    return
```

**注**：此逻辑与工具级重试是否耗尽无关。无论 tool 在 ToolRetryEngine 重试 0 次还是 3 次，action_handler 只按 `error_type` 判。详见 §7.4 T3 完整伪代码。

### 4.4 修改 S2: 确认 react_cycle 分支

**文件**: `react_cycle.py:294-296`

当前已存在（从未执行过）：
```python
if agent.status == AgentStatus.RETRYABLE_ERROR:
    set_status(agent, AgentStatus.THINKING)
    continue
```

`action_handler` 加上 RETRYABLE_ERROR 设置后，此分支自动生效。无需任何代码改动。
如果 `RETRYABLE_ERROR` 后 LLM 再次执行工具失败、又设 `RETRYABLE_ERROR`，循环自然用 `max_steps` 限制总次数。

### 4.5 与旧 SUSPENDED 设计（v1.8）的差异

| 维度 | 旧 SUSPENDED 方案 | 本方案（最小改动） |
|------|------------------|------------------|
| 枚举 | RETRYABLE_ERROR → SUSPENDED | 保留 RETRYABLE_ERROR |
| 谁设状态 | _dispatch_handler 判 recoverable → SUSPENDED | action_handler 按 error_type 直接设 RETRYABLE_ERROR |
| 计数器 | RetryTracker.suspend_retries（上限 3） | 无独立计数器，max_steps 自然兜底 |
| 状态机 | SUSPENDED → THINKING 独立状态 | RETRYABLE_ERROR → THINKING（已有代码）|
| 前端事件 | MetaStep.retrying | 暂不做（P2）|
| 代码改动量 | ~60 行（枚举改名 + dispatch_handler + RetryTracker + 前端适配）| **~15 行（仅 action_handler）** |

def _should_retry(self, e, retryable_errors, engine):
    error_category = UnifiedErrorClassifier.classify_error(e)

## 六、工具级重试问题

### 问题 T1: ToolRetryEngine 强制所有工具走统一重试（P1）

**严重程度**：P1-高

**描述**：`tool_executor.py` 自动把所有工具的执行都包在 `ToolRetryEngine` 里，`TOOL_RETRY_MAX` 只有 `{"default": 3}`。各 tool 没有选择权——要么全部重试，要么全部不重试。FILE/REGISTRY/DESKTOP 等本地操作也被迫重试 3 次。

**影响**：各 tool 不能独立决定自己的重试策略。file 操作不需要重试，但被迫等 3 次超时。

### 问题 T2: http_request 与 ToolRetryEngine 双重重试（P1）

**严重程度**：P1-高

**描述**：http_request 这个 tool 有自己的内建 retry 参数（retry=3），同时又被 ToolRetryEngine 统一重试。两条重试路径叠加。

**执行链**：
```
action_handler → ToolRetryEngine (重试3次)
                    → http_request (内建 retry=3)
```

最坏情况 3×3=9 次网络调用后失败。

**注意**：各 tool 可以独立实现自己的重试逻辑。http_request 自己管自己的重试是可以的，但需确保不被 ToolRetryEngine 再重一次——二选一，不要两个都重试。

### 问题 T3: action_handler 不设 recoverable，所有错误都 FAILED（P1）

**严重程度**：P1-高

**描述**：无论错误类型是可恢复（超时）还是不可恢复（文件不存在），`action_handler` 收到 error dict 后一律 `set_failed()`。`ErrorStep.recoverable` 字段从未被赋值，系统级 RETRYABLE_ERROR 无法进入。

### 问题 T4: TOOL_RETRYABLE_ERRORS 只有 timeout（P2）

**严重程度**：P2-中

**描述**：`TOOL_RETRYABLE_ERRORS["default"] = ["timeout"]`，只有 timeout 被显式配置。网络错误、连接错误等都依赖 `UnifiedErrorClassifier.is_retryable` 的判断。配置不够精细。

### 问题 T5: ToolRetryEngine 缺少灵活配置（P2）

**严重程度**：P2-中

**描述**：ToolRetryEngine 当前配置只有 `{"default": 3}` 一刀切，没有给选择使用它的工具提供灵活配置（比如按工具名或按 ToolCategory 区分）。

## 七、工具级重试修改策略

### 7.1 基本原则

1. **各 tool 自己决定是否重试**：ToolRetryEngine 是共享工具，不是强制框架。tool 可以选择自己的策略性回退（如 fetch_webpage 的 CF 降级 / search_web 的引擎级联），也可以复用 ToolRetryEngine
2. **消除双重重试**：取消 http_request 的内建重试，改用 ToolRetryEngine 统一管理（详见 §7.3）
3. **recoverable 基于错误类型**：action_handler 按错误类型/分类设 recoverable，不依赖工具级重试是否耗尽（这是系统级 RETRYABLE_ERROR 的事，和工具级无关）
4. **谁用谁配**：使用 ToolRetryEngine 的 tools 按需配置（按工具名或按 ToolCategory），不用的不配
5. **只用一个引擎**：ToolRetryEngine 内联 RetryEngine 的 while 循环逻辑，不保留两层引擎（当前 RetryEngine 的 execute() 无人调用，是死代码）。详见 §7.6

#### 7.1.4 内部重试（tool 自己实现）

当前系统**没有** tool 需要真正的内部重试。以下两个工具虽然有"类重试"逻辑，但它们**不是重试机制**，是业务层面的策略性回退：

| 工具 | 机制 | 性质 | 说明 |
|------|------|------|------|
| **fetch_webpage** | 403 Cloudflare fallback | 内容提取备用方案 | 遇到 CF 挑战时换 User-Agent 再试 1 次。不是循环重试，是单次降级策略。不在 ToolRetryEngine 管辖范围 |
| **search_web** | 多引擎级联 Parallel→Exa→Bing | 多引擎搜索策略 | 一个引擎搜不到→换引擎。不是"重试同一次调用"，是"换源搜"。不在 ToolRetryEngine 管辖范围 |

**规则**：上述业务策略性回退由 tool 自己实现，ToolRetryEngine 不管它。**除此之外，没有 tool 需要自己的内部重试**。http_request 的内建重试已取消，改用 ToolRetryEngine。详见 §7.3。

#### 7.1.5 外部重试机制概要设计 — ToolRetryEngine + action_handler 配合

**定义**：外部重试是指由 ToolRetryEngine 在 tool 函数外部编排重试循环，tool 函数本身每次被 clean call，不感知重试。

|------|-------|-----------|-----------|-----------|
| **file/** | 13 | 无 | ToolRetryEngine（超时）| 不需要 |
| **shell/** | 6 | 无 | ToolRetryEngine（超时）| 不需要 |
| **network/** | 5 | http_request 已下线；fetch_webpage/search_web 是业务策略非重试 | ToolRetryEngine（超时/网络）| 不需要 |
| **desktop/** | 14 | 无 | ToolRetryEngine（超时）| 不需要 |
| **document/** | 10 | 无 | ToolRetryEngine（超时）| 不需要 |
| **dataanalysis/** | 8 | 无 | ToolRetryEngine（超时）| 不需要 |
| **fundamental/** | 9 | 无 | ToolRetryEngine（超时）| 不需要 |
| **system/** | 6 | 无 | ToolRetryEngine（超时）| 不需要 |
| **win_registry/** | 5 | 无 | ToolRetryEngine（超时）| 不需要 |

**理论可能性**：一个 tool 可以同时有「tool 特有的临时性故障（如 port 被占）→内部处理」和「通用故障（超时）→ToolRetryEngine」。但当前没有 tool 需要这个。未来如需引入，需确保内部重试的类型与 ToolRetryEngine 的可重试类型不重叠。

#### 7.1.7  外部重试机制设计全景：

```
执行链（三层，职责分离）：
┌─────────────────────────────────────────────────────────────────┐
│ tool_executor.py                入口，所有工具统一经过这里调用    │
│   execute_tool(tool_name, params)                                │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ ToolRetryEngine          第一层：工具级重试（处理临时性故障）     │
│                                                                  │
│   execute_tool_with_retry():                                      │
│     ├─ _get_retry_config() → 查 category 配置                    │
│     │   ├─ 命中配置（NETWORK/SHELL）→ max_retries>0 → 走重试循环  │
│     │   └─ 未命中配置（其他 55 个）→ max_retries=0 → 直通        │
│     │                                                             │
│     ├─ 重试循环（max_retries>0 时）：                              │
│     │   loop: execute_once()                                      │
│     │     ├─ error ∈ retryable_errors AND attempt < max_retries  │
│     │     │   → backoff sleep → 继续循环                          │
│     │     ├─ error ∉ retryable_errors                            │
│     │     │   → 立即中断，返回当前 error（不该重试的错误不重试）    │
│     │     └─ attempt ≥ max_retries                               │
│     │         → 返回最后一次 error（重试耗尽）                     │
│     │                                                             │
│     └─ 返回最终结果（成功或最终 error）                            │
│                                                                  │
│   关键：不依赖 ToolRetryEngine 的 tool（如 fetch_webpage CF 降级 / search_web 引擎级联）          │
│   在此层 max_retries=0，直通，不干涉内部策略性回退                       │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ action_handler           第二层：系统级恢复决策                    │
│                                                                  │
│   收到 ToolRetryEngine 返回的最终结果：                            │
│     ├─ 成功 → 正常继续                                           │
│     └─ 执行失败 → 按 error_type 分类：                           │
│         ├─ tool_not_found / missing_param / invalid_params       │
│         │   → ERROR_STEP(recoverable=True)                       │
│         │   → agent.status = RETRYABLE_ERROR                     │
│         │   → react_cycle 继续循环，LLM 换策略再试                 │
│         │                                                         │
│         └─ 其他（文件不存在/权限拒绝/unknown 等）                   │
│             → ERROR_STEP(recoverable=False)                      │
│             → agent.status = FAILED（不可恢复，终止）              │
│                                                                  │
│   关键1：action_handler 只按 result.error_type 判 recoverable     │
│         不依赖 ToolRetryEngine 的重试次数，两者完全解耦            │
│   关键2：timeout/network/5xx/rate_limit 不过此层                   │
│         它们是 ToolRetryEngine 的领域，已在那里处理完               │
└──────────────────────────────────────────────────────────────────┘
```

**两级协作关系**：

| 维度 | ToolRetryEngine（工具级） | action_handler → RETRYABLE_ERROR（系统级） |
|------|-------------------------|-----------------------------------|
| 目标 | 消化临时性故障（网络抖动、超时） | 处理持续性错误，让 LLM 换策略重试 |
| 操作 | 相同参数重复调同一 tool | LLM 换参数、换 tool、换思路 |
| 对前端 | 透明（重试成功无感） | 可见（发 retrying 事件） |
| 决策依据 | 错误是否在 retryable_errors 中 | result.error_type 是否在 recoverable_types 中 |
| 是否依赖对方 | 不依赖 | 不依赖 |
| 谁先谁后 | ToolRetryEngine 先执行 | action_handler 后收到结果 |

**设计原则**：
1. **解耦**：ToolRetryEngine 重试结果不影响 recoverable 判断。无论重试 0 次还是 3 次，action_handler 只按 `result.error_type` 判是否在 `recoverable_types` 中
2. **可配置**：外部重试按 category 配置。新增一个 category 到 `TOOL_RETRY_BY_CATEGORY` 即获得重试，无需改代码
3. **单一路径**：http_request 取消内建重试后，所有使用 ToolRetryEngine 的工具经统一入口，没有两条路径打架的问题
4. **无侵入**：tool 函数不需要 import 任何重试相关代码，纯函数式调用

### 7.2 修改 T1: ToolRetryEngine 按需配置（给愿意用它的 tool 用）

**思路**：ToolRetryEngine 当前的 `TOOL_RETRY_MAX={"default": 3}` 一刀切。改为：各 tool 通过注册信息或按类型选择是否使用 ToolRetryEngine。不在配置表中的工具不重试。

**文件**: `tool_constants.py`

```python
from app.tools.tool_types import ToolCategory

# 按工具类型配置重试（给使用 ToolRetryEngine 的 tool 用）
TOOL_RETRY_BY_CATEGORY = {
    ToolCategory.NETWORK: {"max_retries": 3, "retryable": ["timeout", "network", "connect", "server", "rate_limit"]},
    ToolCategory.SHELL:   {"max_retries": 2, "retryable": ["timeout", "network"]},
    # 其他类型不在字典中 → 不重试
}
```

**文件**: `tool_retry_engine.py` — `_get_retry_config()` 按 category 查，不在配置表中的回报 0（不重试）：

```python
def _get_retry_config(self, action: str):
    """获取重试配置 — 按工具类型查（给使用 ToolRetryEngine 的 tool 用）"""
    from app.tools.registry import tool_registry
    metadata = tool_registry.get_tool(action)
    category = metadata.category if metadata else None
    
    if category and category in TOOL_RETRY_BY_CATEGORY:
        cfg = TOOL_RETRY_BY_CATEGORY[category]
        return (
            cfg.get("max_retries", 3),
            TOOL_RETRY_BACKOFF.get("default", 2.0),
            cfg.get("retryable", ["timeout"]),
            TOOL_TIMEOUTS.get(action, TOOL_TIMEOUTS["default"]),
        )
    # 不在配置表中的工具不重试（max_retries=0）
    return (0, 0, [], TOOL_TIMEOUTS.get(action, TOOL_TIMEOUTS["default"]))
```

**注意**：各 tool 可以不经过 ToolRetryEngine，自己实现策略性回退（如 fetch_webpage 的 CF 降级 / search_web 的引擎级联）。本条修改只影响那些选择使用 ToolRetryEngine 的工具。当前所有工具中，只有 http_request 需要从内部重试切换到 ToolRetryEngine（详见 §7.3）。

### 7.3 修改 T2: 消除双重重试（http_request）

#### 7.3.1 问题

http_request 是当前**唯一**一个既有内部重试又被 ToolRetryEngine 包裹的工具：

| 层级 | 重试次数 | 退避 | 是否生效 |
|------|---------|------|---------|
| L0：内部循环 `for attempt in range(retry+1)` | 默认 3 | `0.5×2ⁿ`，上限 10s | ✅ 生效（因 http_request catch 所有异常→返回 dict） |
| L1：ToolRetryEngine `_execute_with_retry` | 默认 3 | `2ⁿ` | ❌ 被绕过（因 http_request 永不抛异常） |

实际效果：http_request 的 3 次内部重试正常跑，ToolRetryEngine 的 3 次**从未触发**。如果不小心改了 http_request 让它冒泡异常（例如删了 catch），就是 3×3=9 次请求的地雷。

#### 7.3.2 分析：ToolRetryEngine 能否替代 http_request 的内部重试？

能。逐项对比（基于 T6 最终设计：`is_retryable` 已从 `_should_retry` 移除，只靠 per-category 的 `retryable_errors` 显式清单）：

| 异常类型 | http_request 内部 | ToolRetryEngine（per-category: `name in retryable_errors`） | 结果 |
|---------|-----------------|-----------------------------------------------------------|------|
| `TimeoutException` | ✅ 重试 | `"timeout" in NETWORK.retryable_errors` | ✅ 等价 |
| `HTTPStatusError(500/502/503/504)` | ✅ 重试 | `"server" in NETWORK.retryable_errors` | ✅ 等价 |
| `HTTPStatusError(429)` | ✅ 重试 | `"rate_limit" in NETWORK.retryable_errors` | ✅ 等价 |
| `ConnectError` | ✅ 重试（属 RequestError） | `"connect" in NETWORK.retryable_errors` | ✅ 等价 |
| `NetworkError` | ✅ 重试（属 RequestError） | `"network" in NETWORK.retryable_errors` | ✅ 等价 |
| `HTTPStatusError(403/404/400/401)` | ❌ 不重试 | 各映射到 `API_FORBIDDEN/UNKNOWN…`，不在显式清单中 | ✅ 等价 |

**结论**：T4（per-category 显式清单）+ T6（删除 `is_retryable` 后，NETWORK 配置已全部覆盖 http_request 内部重试的 5 种场景。`TOOL_RETRY_BY_CATEGORY` 中的 NETWORK 条目为唯一来源。


#### 7.3.3 结论：http_request 取消内部重试，改用 ToolRetryEngine

| 改动 | 文件 | 说明 |
|------|------|------|
| 删除 `for attempt in range(retry+1)` 循环 | `http_request.py:163-197` | 不再自己处理重试 |
| 删除 `retry` 参数 | `http_request.py` + `network_schema.py` | LLM 不需要控制重试次数 |
| 404/403 等非重试状态码**仍** catch 后 `build_error`（不传播异常） | `http_request.py` | 这类错误不应冒泡到 ToolRetryEngine，ToolRetryEngine 看到它们也会判不可重试，但让它们提前返回更干净 |
| 超时/5xx/429/连接失败 → **不 catch，让异常传播到 ToolRetryEngine** | `http_request.py` | ToolRetryEngine 按 per-category `retryable_errors` 判→重试 |
| `TOOL_RETRY_CONF` | 替换为 `TOOL_RETRY_BY_CATEGORY`（§7.2）| 默认 `["timeout"]` 不再使用，NETWORK 显式清单覆盖全部 5 种场景 |
| 可删 `RETRYABLE_HTTP_STATUS_CODES` | `constants.py` | 不再需要（但也不影响功能）|

### 7.4 修改 T3: action_handler 按 error_type 设 recoverable

**文件**: `action_handler.py`

`action_handler` 在收到工具 error 时，根据 `result.error_type` 决定 `recoverable`，**不依赖工具级重试是否耗尽**：

```python
# action_handler 中收到 error dict 后的简化逻辑
result = ...  # ToolRetryEngine 返回的最终结果
if result.get("status", {}).get("exec_code") == "error":
    # 按 error_type 判是否可恢复（不查 is_retryable——那是 ToolRetryEngine 用的）
    RECOVERABLE_TYPES = {"tool_not_found", "missing_param", "invalid_params"}
    error_type = result.get("error_type", "unknown")
    recoverable = error_type in RECOVERABLE_TYPES  # tool_not_found → True；权限拒绝 → False

    if recoverable:
        agent.status = AgentStatus.RETRYABLE_ERROR
    else:
        agent.set_failed(result.get("error_message", "工具执行失败"))

    yield agent._step_emitter.emit(ErrorStep(
        step=step,
        error_type=error_type,
        error_message=result.get("error_message", "工具执行失败"),
        recoverable=recoverable,
    ))
    return
```

**注意**：action_handler 的 recoverable 只查 `result.error_type` 是否在 `RECOVERABLE_TYPES` 中，不查 `is_retryable`。
工具级重试决策（ToolRetryEngine._should_retry）只查 per-tool 的 `retryable_errors` 配置，也不查 `is_retryable`。
详见 §7.7。

### 7.6 修改 T5: 消除两层引擎（合并 RetryEngine → ToolRetryEngine）

**问题**：当前 ToolRetryEngine 创建 RetryEngine 实例但不调 `engine.execute()`，自己在外面另写 while 循环。
RetryEngine 的 `execute()` 方法无人调用，是死代码。两层引擎一半重叠一半死，徒增维护成本。

```

  └─ 自己管理 _execute_single_attempt → return/None 两条路径
  └─ 只用 RetryEngine.attempt_count + current_delay 当计数器

RetryEngine（execute:82-123）
  └─ execute() — 没人调用，死代码
  └─ 用 record_attempt() 被 ToolRetryEngine 当计数器
```

**方案**：合并 RetryEngine 逻辑进 ToolRetryEngine。

| 文件 | 动作 |
|------|------|
| `backend/app/utils/retry_engine.py` | **删除**（173行）|
| `tool_retry_engine.py:_execute_with_retry` | 内联 while 循环 + 计数器 + 退避延迟逻辑 |
| `tool_retry_engine.py:_should_retry` | 去掉 `is_retryable` 判断（详见 §7.7）|

**改动内容**：
1. 删除 `retry_engine.py`，其 while 循环逻辑内联到 `ToolRetryEngine._execute_with_retry`
2. 原 `engine.record_attempt()` / `engine.current_delay` / `engine.exhausted` 改为本地变量
3. `_get_retry_config` 返回的 `max_retries=0` 时直接跳过 while 循环，单次执行后返回
4. 对外接口 `execute_tool_with_retry(action, action_input)` 不变
5. `tool_executor.py`、`base_agent.py` 不碰

**变动文件**：
- `backend/app/services/agent/tool_retry_engine.py` — 内联 RetryEngine 逻辑，精简
- `backend/app/utils/retry_engine.py` — 删除

### 7.7 修改 T6: is_retryable 从工具级决策中移除

**问题**：ToolRetryEngine._should_retry() 当前同时检查两套标准：

```python
def _should_retry(self, e, retryable_errors, engine):
    error_category = UnifiedErrorClassifier.classify_error(e)
    is_retryable = error_category.is_retryable or error_category.name.lower() in retryable_errors
    return is_retryable and not engine.exhausted
```

既然各 tool 自己决定重试策略，统一分类的 `is_retryable` 不应该掺和工具级决策。

**文件**: `tool_retry_engine.py` — `_should_retry()`

```python
def _should_retry(self, e: Exception, retryable_errors: list, engine) -> bool:
    error_category = UnifiedErrorClassifier.classify_error(e)
    # 只查 per-tool 配置，不查统一 is_retryable
    is_retryable = error_category.name.lower() in retryable_errors
    return is_retryable and not engine.exhausted
```

`ErrorCategory.is_retryable` 属性保留不动，给以下场景用（与工具级重试无关）：
- LLM 客户端 HTTP 重试（base_service.py:387）
- Agent 级错误处理（error_handler.py）

action_handler 的 recoverable 决策（§7.4）不查 `is_retryable`，只查 `result.error_type` 是否在 `RECOVERABLE_TYPES` 中。

## 八、两级重试的关系

### 8.1 执行流程：两条独立分支

**左分支 — 工具级重试（对上层透明）**：
```
工具执行抛异常（超时/网络）
      ↓
该工具配置了重试且错误可重试？
  ├─ 是 → ToolRetryEngine 重试（按工具配置次数，指数退避）
  │        ├─ 第 N 次成功 → 返回正常 result，上层无感
  │        └─ 耗尽 → 返回 error dict（同右分支）
  └─ 否 → 直接返回 error dict（同右分支）
```

**右分支 — 工具返回 error dict**（不分是否经历过工具级重试）：
```
error dict
      ↓
action_handler 按 result.error_type 分类
      ↓
  ┌── tool_not_found / missing_param / invalid_params
  │   → recoverable=True（LLM 换策略能救，让 LLM 重新试）
  │
  ├── timeout / network / 5xx / rate_limit
  │   → 不过此层，ToolRetryEngine 已在第一层处理完
  │   → action_handler 不判 recoverable，直接以 Observation 给 LLM
  │
  └── 文件不存在 / 权限拒绝 / unknown 等
      → recoverable=False（LLM 换策略也救不了，直接结束）
       ↓
yield ErrorStep(recoverable=...)
       ↓
recoverable?
  ├─ True  → agent.status = RETRYABLE_ERROR  ← 系统级重试
  │           run_react_cycle 检测到 RETRYABLE_ERROR
  │           → THINKING + continue（重新调 LLM，LLM 可换参数/换工具/换思路）
  │
  └─ False → agent.set_failed("不可恢复错误") ← 直接结束
```

**关键**：工具级重试的有无/成功/耗尽，不影响右分支的 recoverable 决策。recoverable 只由 `result.error_type` 决定。

### 8.2 职责划分

| 场景 | 谁处理 | 方式 |
|------|--------|------|
| 网络闪断，第2次重试成功 | ToolRetryEngine | 透明，上层无感 |
| 网络超时，工具级重试 3 次耗尽，返回 error | ToolRetryEngine 耗尽 | 返回 error dict，以 Observation 给 LLM。LLM 看到超时决定下一步 |
| action_handler 收到 error，发现 `error_type = missing_param` → 可恢复 | action_handler | ErrorStep(recoverable=True) → RETRYABLE_ERROR → react_cycle 继续循环 |
| RETRYABLE_ERROR 后 LLM 补全了参数，工具执行成功 | 系统级 + ToolRetryEngine | 正常完成 |
| 系统级循环超出 max_steps | 系统级 | set_failed("max_steps 耗尽") |
| 文件不存在（不可恢复），直接 FAILED | action_handler | ErrorStep(recoverable=False) → set_failed |

**注意**：ToolRetryEngine 重试耗尽不会自动触发系统级 RETRYABLE_ERROR。只有 `result.error_type` 在 `RECOVERABLE_TYPES` 中的错误才会触发。

### 8.3 不重叠原则

```
工具级重试 ≠ 系统级重试
───────────   ───────────
重试对象：工具函数调用    重试对象：整个 LLM 轮次
计数器：各 tool 自定      计数器：react_cycle max_steps（间接）
条件：error ∈ retryable  条件：result.error_type ∈ RECOVERABLE_TYPES
上限：各 tool 自定        上限：max_steps（循环自然上限）
退避：各 tool 自定        退避：立即
```
