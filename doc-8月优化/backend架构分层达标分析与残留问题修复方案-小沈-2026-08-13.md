| API 层 | services/* | tools/*, safety/*, db/* |
| 编排层 | services 内部子域 + safety + tools(公共接口) + utils + db | tools 具体实现模块 |
| 业务服务层 | safety + tools(公共接口) + utils + db | tools 具体实现模块 |
| 安全层 | tools/*(公共接口+security包) + utils + db | services/* |
| 工具层 | utils + config + constants | services/*, safety/* |
| 公共基础设施层 | 无（最底层） | 所有上层 |

### 2.3 各层功能详述与三思三省审查

#### 2.3.1 应用入口层（main.py）

| 项目 | 说明 |
|------|------|
| **位置** | `app/main.py` |
| **职责** | FastAPI 应用入口：注册9个路由器、CORS中间件、异常处理器、启动事件(初始化DB+注册工具+启动清理任务)、关闭事件(lifecycle reset) |
| **允许依赖** | api/v1/*, tools(注册启动), services/lifecycle, monitoring(顶层能力层), services/task, db, config, logger, constants |
| **禁止依赖** | 无特殊限制（入口层可接触所有层，但应最小化） |

**三思三省审查**：

| 审查项 | 结论 |
|--------|------|
| main.py 直接 import `app.tools`（`ensure_tools_registered`）是否违规？ | **不违规**。main.py 是应用入口，启动时注册工具是初始化职责，不属于任何业务层 |
| main.py 直接 import 各 api/v1 路由是否合理？ | **合理**。FastAPI 必须在入口注册路由器 |
| main.py 是否内嵌业务逻辑？ | **否**。仅注册+启动+关闭，无业务逻辑 |

#### 2.3.2 API / 接口适配层（app/api/v1/）

| 项目 | 说明 |
|------|------|
| **位置** | `app/api/v1/` |
| **职责** | HTTP 路由定义 + 请求/响应 DTO + 协议封装（SSE/WS 传输格式、HTTP 状态码、错误码映射）。**薄壳化**：路由函数只做 DTO 解包→调 service→返回 Response，不含业务逻辑 |
| **允许依赖** | services/*（编排层+业务服务层） |
| **禁止依赖** | tools/*, safety/*, db/*（业务数据库） |

**子域拆解**：

| 子目录/文件 | 路由端点 | 调用的 service 层 |
|------------|---------|------------------|
| `chat/chat_routes.py` | POST /chat/stream, cancel/pause/resume/confirm, validate, reconnect | stream_orchestrator, task_runtime, task_registry, hitl_confirmation |
| `chat/execution_stream.py` | GET /chat/execution/{id}/stream | chat/storage |
| `chat/models.py` | (纯DTO) | 无 |
| `health.py` | GET /health, POST /echo | db(直接查DB健康) |
| `sessions.py` | CRUD /sessions | session_service |
| `messages.py` | CRUD /sessions/{id}/messages | message_service |
| `config_routes.py` | 13个配置CRUD路由 | model/resolver, model/config_helpers, model/config_service |
| `tool_routes.py` | GET /tool/list, POST /tool/execute | services/tool(门面) |
| `task_queries.py` | GET /tasks, rollback, file-operations, report | task/TaskQueries, task_rollback_service, visualization, db/operation_queries |
| `metrics.py` | GET/POST /metrics | monitoring |

**三思三省审查**：

| 审查项 | 结论 |
|--------|------|
| `health.py` 直接 import `app.db` 是否越层？ | **轻微越层**。health 端点查 DB 健康状态，语义上"健康检查"需直接感知 DB 存活，经 service 间接查反而不自然。可接受 |
| `config_routes.py` 371行非纯薄壳 | **残留问题P3**。A7仅迁出 update_config，其余12个CRUD路由仍内联业务逻辑 |
| `task_queries.py` 直接 import `app.db.operation_queries` 是否越层？ | **轻微越层**。file-operations 查询经 db 层直读，绕过 service。但该查询是纯只读SQL无业务逻辑，经 service 包装反而增加无意义透传层。可接受 |
| DTO 边界是否被 services 层反向依赖？ | **否**。services 层不 import api/v1 的 DTO，API 层负责解包 DTO 为原始参数传入 service |

#### 2.3.3 编排层（services/agent/ + services/chat/stream_orchestrator）

| 项目 | 说明 |
|------|------|
| **位置** | `app/services/agent/`、`app/services/chat/stream_orchestrator.py` |

### 5.1 P1（中）— safety→tools 具体实现依赖 `remove_readonly`

#### 5.1.1 当前问题

`safety/operation_maintenance.py` 和 `safety/operation_rollback.py` 延迟导入 `remove_readonly`：

```python
# app/safety/operation_maintenance.py:41
from app.tools.file.delete_file import remove_readonly

# app/safety/operation_maintenance.py:79
from app.tools.file.delete_file import remove_readonly

# app/safety/operation_rollback.py:37
from app.tools.file.delete_file import remove_readonly
```

`remove_readonly` 是一个纯文件系统辅助函数（为 `shutil.rmtree` 的 `onerror` 回调提供只读文件权限恢复+删除能力），其逻辑不依赖任何工具层状态、注册表或安全层设施。

#### 5.1.2 病根

`remove_readonly` 定义在 `tools/file/delete_file.py` 中，因为它是 delete_file 工具的内部辅助函数。但 safety 层的备份清理和回滚操作也需要"删除只读文件"能力，导致 safety→tools 具体实现依赖。

虽然通过延迟导入规避了循环依赖，但违反了"safety 层不应知道 tools 层具体实现"的分层原则。

#### 5.1.3 修复方案：提取到公共基础设施层

**目标**：`remove_readonly` 是纯文件系统操作，不涉及工具注册/安全校验/任务上下文，语义上属于公共基础设施层。提取后 safety 和 tools 两层都从公共层导入，消除 safety→tools 实现依赖。

**步骤**：

1. **新建 `app/utils/file_utils.py`**，将 `remove_readonly` 函数**整段复制**迁入（业务逻辑一字不改，仅改归属）：

```python
# app/utils/file_utils.py
"""文件操作公共辅助函数 — 纯文件系统操作，不依赖任何业务层"""
import stat
import os
from pathlib import Path

def remove_readonly(func, path, _):
    """shutil.rmtree onerror 回调: 恢复只读文件写权限后重试删除
    来源: 从 app/tools/file/delete_file.py 复制迁入 — 小沈 2026-08-13
    """
    try:
        os.chmod(path, stat.S_IWRITE)
        func(path)
    except Exception:
        pass
```

from app.utils.file_utils import remove_readonly

### 5.4 P4（轻微）— agent→chat 反向引用（持久化耦合）

#### 5.4.1 当前问题

```python
# app/services/agent/agent_runner.py:47-50
from app.services.chat.sse_events import save_execution_steps_to_db
from app.services.chat.storage import allocate_and_insert_message, append_execution_step, finalize_message
from app.services.chat.stream_reader import _load_previous_messages, _log_task_end
```

agent_runner 是 Agent 后台运行器，由 chat 编排器（stream_orchestrator）调度。但它反向依赖 chat 模块的持久化函数，形成 agent→chat 循环引用：

```
stream_orchestrator → agent_runner → chat/sse_events + chat/storage + chat/stream_reader
       ↑_________________________________|
```

#### 5.4.2 病根

agent_runner 的"结果持久化"职责委托给了 chat 模块。从概念上：
- chat 是"会话编排"（上层），负责调度 Agent + 消费 SSE + 持久化
- agent 是"执行引擎"（下层），负责 ReAct 循环 + 工具调用

agent 不应知道 chat 的存在。当前 agent_runner 承担了"执行完成后把结果写入 DB"的职责，而 DB 写入函数定义在 chat 模块，导致反向依赖。

#### 5.4.3 修复方案：回调/接口注入

**目标**：agent_runner 不直接 import chat 模块，持久化能力通过回调注入。

**步骤**：

1. **在 `agent_runner.py` 的 `run_agent_in_background` 函数签名中增加持久化回调参数**：

```python
from typing import Callable, Optional

async def run_agent_in_background(
    agent,
    task_id: str,
    user_input: str,
    system_prompt: Optional[str],
    next_step,
    session_id: str,
    state,
    task_start_time: float,
    # 新增：持久化回调（由调用方注入）
    on_save_steps: Optional[Callable] = None,
    on_load_previous: Optional[Callable] = None,
    on_log_task_end: Optional[Callable] = None,
):
```

2. **agent_runner 内部改用回调**：

```python
# 替换原: from app.services.chat.sse_events import save_execution_steps_to_db
# 替换原: from app.services.chat.stream_reader import _load_previous_messages, _log_task_end

# 函数内使用:
if on_save_steps:
    await on_save_steps(...)
if on_load_previous:
    previous = await on_load_previous(session_id, task_id)
if on_log_task_end:
    on_log_task_end(...)
```

3. **`stream_orchestrator.py` 调用 `run_agent_in_background` 时注入回调**：

```python
from app.services.chat.sse_events import save_execution_steps_to_db
from app.services.chat.stream_reader import _load_previous_messages, _log_task_end

bg_task = asyncio.create_task(run_agent_in_background(
    agent, task_id, user_input, None, next_step, session_id, state, _task_start_time,
    on_save_steps=save_execution_steps_to_db,
    on_load_previous=_load_previous_messages,
    on_log_task_end=_log_task_end,
))
```

4. **storage 操作同理**：`allocate_and_insert_message`/`append_execution_step`/`finalize_message` 也通过回调注入，或在 agent_runner 内改用 `app.db` 直接操作（如果逻辑足够简单）。

5. **删除 agent_runner.py 的 chat 导入**：

```python
# 删除:
# from app.services.chat.sse_events import save_execution_steps_to_db
# from app.services.chat.storage import allocate_and_insert_message, append_execution_step, finalize_message
# from app.services.chat.stream_reader import _load_previous_messages, _log_task_end
```

**迁移后依赖方向**：

```
修改前: agent/agent_runner.py → chat/sse_events + chat/storage + chat/stream_reader  (agent→chat 反向依赖)
修改后: chat/stream_orchestrator.py → agent/agent_runner.py  (chat→agent 单向)
        chat/stream_orchestrator.py → chat/sse_events + chat/storage + chat/stream_reader  (chat 内部调用)
        agent_runner 通过回调接收持久化能力，不直接依赖 chat
```

#### 5.4.4 三思三省

| 维度 | 分析 |
|------|------|
| **可行性** | 中。需要修改 `run_agent_in_background` 签名和调用方，但改动面可控（当前只有 stream_orchestrator 一处调用） |
| **风险** | 中。agent_runner 是核心后台运行器，回调注入需确保异常处理和 finally 块中的持久化不遗漏 |
| **替代方案** | ①保持现状（agent→chat 反向依赖可接受，因 agent_runner 本身就是 chat 域的延伸）；②将持久化函数提取为独立模块 `services/persistence/` |
| **是否引入新抽象** | 是，回调参数。但这是最小侵入的解耦方式 |

#### 5.4.5 三堂会审
