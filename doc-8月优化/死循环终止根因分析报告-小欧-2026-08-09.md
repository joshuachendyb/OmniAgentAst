## 三、核心病根: delete 在 R6 拦截后的 LLM 鲁棒性缺陷

### 3.1 事实链(证据)

以 session `d1ec0cbc`(15:52:16–15:53:20) 为例:

1. **LLM 发起7个并行delete**(`llm_stream.py:206`): `tool_calls(7)=['delete'×7]`, 目标为回收站目录 `E:\test_dir\_cleanup_recycle_20260809`(递归清理)。
2. **R6无条件拦截**(`delete_safety.py:55-56`): `check_delete_risk` 判定 `recursive=True` 且路径在项目根(`F:\OmniAgentAs-repair`)之外 → `SafetyResult(blocked=True, message="禁止删除项目根外目录(递归): ...")`。
3. **反馈已正确写入LLM历史**(`action_handler.py:245-272` `_add_denial_feedback`): prompt_003010 中序号44-46 为 `[Observation] 工具 delete 被安全策略拦截: 禁止删除项目根外目录(递归): E:\test_dir\_cleanup_recycle_20260809. 请改用其他工具或方式完成用户任务。`(该文件中共出现463次"被安全策略拦截"、519次"禁止删除")。
4. **LLM连续5轮无视反馈**: 5轮 Thought 逐字相同("`_cleanup_recycle_20260809` 是之前的回收站目录, 直接清理"), 5轮调用签名完全相同(7个delete并行, `_tool_call_signature` 逐字一致)。
5. **死循环终止**(`react_cycle.py:486`): count>=5 → FAILED, error_type=same_tool_loop。此session `llm_calls=13`, 累计 prompt_tokens≈52万(526826), 其中后5轮(约38K×4+39K)为纯空转浪费。

### 3.3 病根判定

> **v1.1 更正(2026-08-09 23:08:55 小欧)**: 本报告 v1.0 将 R6 拦截的前提判定为「路径在项目根(F:\OmniAgentAs-repair)之外」, 该前提基于「项目根=代码库根」的错误认知。经 2026-08-09 后续勘测确认: **真实项目根应为 config 的 `app.project_root=E:\test_dir`**(未配置则取用户主目录), 目标 `E:\test_dir\_cleanup_recycle_20260809` 实为**项目根内**递归删除, 应走 R4(需确认)而非 R6(拒绝)。故 d1ec0cbc/62166ff7 两处死循环的**真正根因是项目根定义错误导致递归删除被误判 R6 拦截**, 而非"LLM 鲁棒性"主因。项目根收敛(统一走 `config.get_project_root()`)后, 此类误判消除、死循环不再由本项目根缺陷触发。后续处理统一在《项目根目录定义混乱分析报告-小欧-2026-08-09.md》跟踪。

**这不是"安全拦截吞掉delete且无反馈"的系统缺陷**(修正自初版报告的auto_confirm推论), 而是:

1. **主因(LLM鲁棒性)**: 反馈已写入LLM历史, 但LLM(sensenova-6.7-flash-lite)连续5轮无视 blocked observation, 重复相同调用直至被强制终止。
2. **次因(系统未及时止损)**: R6 blocked 属于不可恢复的硬拦截, 但当前机制仅依赖"LLM自行换方案" + 5步后终止, 期间浪费约5轮×38K tokens。纠偏警告(react_cycle.py:202)在 blocked 之后仍允许继续重复, 未在 blocked 计数达阈值时主动提示更换目录/工具。
