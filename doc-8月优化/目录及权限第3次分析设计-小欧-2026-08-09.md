## 一、背景

北京老陈反映: 对回收站目录 `E:\test_dir\_cleanup_recycle_20260809` 发起递归删除(recursive=True)时，系统错误判定为「项目根外目录(递归)」并 R6 无条件拦截(blocked)，而实际该目录位于用户真实工作区 `E:\test_dir` 之内。

老陈指出: 项目根目录理应由配置文件定义，无配置时取用户主目录，但系统却出现了「代码安装目录」作为项目根，属逻辑错误。

本报告据 2026-08-09 实地勘测 + 代码定位，梳理项目根的多套并行定义及其矛盾，给出收敛方案。

---

## 二、项目根「唯一正源」应当是什么(北京老陈裁定)

- 项目根目录 = 配置文件显式定义的值(`app.project_root`);
- 若配置文件未定义, 项目根 = 用户主目录(`Path.home()`);
- 任何场合都不应把「代码安装位置」充当项目根。

**此定义不因授权目录/白名单变化而改变**(2026-08-10 00:18 北京老陈重申): 项目根始终「有配置用配置值, 无配置用用户主目录」; 授权目录(`app.allowed_dirs`)只是**额外扩展** tool 可访问目录的白名单, 与项目根定义互不干涉。

此口径已在本次确认, 作为本次修复的判定基准。

---

## 三、逻辑理顺定稿: 「代码库根」与「项目根」是两个概念, 不得混淆(小欧 2026-08-09 22:50)

> 本次梳理发现: 项目内长期混用两个不同概念, 是产生矛盾的根本。必须先拆开, 全文口径才可能一致。

### 3.1 概念区分(2026-08-10 10:34 小欧 重拆两表; 2026-08-10 11:07 小欧 扩三表: 概念定义 + 禁区说明 + 技术实现)

> **概念层次分离**: 表一「概念定义」= 真实存在的目录(逻辑层, 有获取方式/配置); 表二「禁区说明」= 禁区分级(系统禁区/非系统禁区)与读写删权限(概念层); 表三「技术实现」= 代码逻辑判断用的**三张名单**(白名单/黑名单/临时名单, 实现层, **不是目录**)。任何「目录」都是表一的真实目录; 白名单/黑名单/临时名单是代码判定名单; 禁区分级是**独立概念层次**, 不混入技术实现表。

> **禁区 = 系统禁区 + 非系统禁区(普通禁区)**, 是权限层面的一组概念说明, **不是代码判定集合**。禁区**读取一律允许**; 差异只在写/删。

> 即: 两类禁区的区别只在**写**——系统禁区写直接禁止且永不授权, 非系统禁区写需授权; 读都允许, 删都禁止。实现层黑名单**只有一张**, 判定时按操作分流: 写规则命中→系统禁写/非系统禁写需授权; 删除规则命中→一律禁删(表三, 3.2.8)。

**表三: 技术实现定义表(实现层, 代码逻辑判断用, 不是目录)**

> **三张名单并列**: **白名单(常驻允许) / 黑名单(常驻禁止) / 临时名单(运行期动态放行)**。**黑名单只有一张 = 禁区路径清单**(系统禁区+非系统禁区的全部路径, 禁区是概念层叫法、黑名单是实现层叫法, 同一批路径), 判定时按操作分流走**两套规则**: 写规则(系统禁区硬拦永不授权/非系统禁区写可任务级授权)、删除规则(一律硬拦永不授权)。临时名单**既不是白名单也不是黑名单**——它是运行期由 **LLM 工具参数/任务点名目录**动态产生的放行名单, 用户确认后入单, **与 task 绑定, task 结束清零**; **只在「白名单与黑名单都不在」时建立**——白名单内直接放行, 黑名单内(=禁区)按禁区原则处理, 都不在(白名单外·非禁区)才建临时名单(**「都不在才建」是 LLM 触发的建立条件, 任务级授权 3.2.13 不受此限**)。

| 名单 | 本质 | 代码逻辑判定 | 判定规则 | 说明 |
|------|------|------------|---------|------|

**3.2.1 目录关系总览(两个层级 + 三区互斥)**

**总体汇总关系图(路径判定决策流, 2026-08-10 13:17 小欧按北京老陈图式重画; v1.37 13:55:51 小欧补全白名单组成+写删分支+触发源; 前版「三区空间树」2026-08-10 10:15 弃用)**: 任何路径进入后按此顺序判定——

```text
路径进入
├── 白名单内     → 直接放行，不建临时名单(读/写/删都容许; 删受R3-R6, 递归删需用户授权)
│       └── 白名单组成 = 用户主目录 + 系统临时目录(/tmp,/var/tmp) + 项目根 + 授权目录
├── 黑名单内(=禁区) → 按禁区原则处理，不建临时名单
│     ├── 系统禁区   → 读✅ / 写❌永不授权 / 删❌永不授权
│     └── 非系统禁区 → 读✅ / 写⚠️任务级授权(用户点名=经temp_auth入单, 不受「都不在才建」限, 3.2.13) / 删❌永不授权
└── 都不在(白名单外·非禁区)
      ├── 读         → ✅ 直接放行(只读工具), 不建临时名单
      └── 写/删      → ⚠️ 建临时名单(LLM工具参数触发 或 任务级用户点名 → 用户确认 → 入单; 与task绑定, task结束清零; 删受R3-R6, 递归删需用户授权)
```

- **层级一: 真实目录(实体, 有获取方式/配置位置)** —— 代码库根、项目根、用户主目录、系统临时目录、系统目录、系统磁盘根、授权目录、任务临时目录;
- **层级二: 名单(代码逻辑判断用的规则, 不是实体目录, 3.2.7~3.2.13)** —— **白名单**(常驻允许, `validate_tool_path` 放行判定)、**黑名单**(常驻禁止, `_is_forbidden_path` 拦截判定, **只有一张**, 判定时按操作分流走写规则/删除规则)、**临时名单**(运行期动态放行, 既非白名单也非黑名单, 3.2.12);
- **三区互斥**: 任意路径必落且仅落一区——白名单(常驻允许区) / 白名单外·非禁区(临时名单区) / 黑名单(常驻禁止区); 临时名单是**运行期授权标记(与 task 绑定)**, 不在三区中新增一区, 只是对白名单外·非禁区路径的动态放行; 入单后本 task 内有效, task 结束清零;
- **集合与成员**: 白名单 = 用户主目录 + 系统临时目录 + 项目根 + 授权目录 的并集; 黑名单(**只有一张**) = 系统禁区(系统目录+盘根) + 非系统禁区(代码库根及其子/父级), 判定时按操作分流走**写规则/删除规则**(3.2.8); 临时名单 = **白名单与黑名单都不在**的路径(LLM 工具参数给出或任务点名目录), 用户确认后临时入单, **与 task 绑定, task 结束清零**(LLM 触发「都不在才建」, **任务级授权 3.2.13 不受此限**——用户点名非系统禁区代码库根写可入单);
- **用户下命令提到的目录**: **不是第四区, 不是独立概念**——它就是一个路径, 落哪区按哪区判定; 只是触发「临时名单」的任务级场景(3.2.13): 任务启动时把用户点名的路径一次性入临时名单, 任务结束清除。

**3.2.2 代码库根——获取方式与使用方法**

- **定义**: 程序安装/代码所在目录;
- **获取方式**: `config._get_code_root()` = `Path(__file__).parent.parent.parent`(基于代码位置推算); 公开 API `get_code_root()`(str);
- **使用方法**: 仅用于定位程序自身资源(`config/config.yaml`、`version.txt`、`logs/`、模板); 属**非系统禁区**(=普通禁区, 读✅/写⚠️临时授权/删❌硬拦); **严禁充当项目根**(3.4 函数命名分离)。

**3.2.3 项目根——获取方式与使用方法**

- **定义**: 用户实际工作/数据目录 = tool 工作区;
- **获取方式**: `config.get_project_root()`(str) —— 配置 `app.project_root` **优先**; 未配置(空) → 用户主目录 `Path.home()`(不再用代码位置当项目根, ①);
- **使用方法**: R3-R6 删除判定、下载目录、输出目录、prompt 注入、规则文件注入; 属**白名单**(读/写/删放行)。

**3.2.4 用户主目录——获取方式与使用方法**

- **定义**: 当前系统用户的 home 目录;
- **获取方式**: `Path.home()`;
- **使用方法**: 白名单自动放行区(读/写/删, 删受 R3-R6); **双重身份**——既是白名单成员, 又是项目根未配置时的兜底(3.2.3)。

**3.2.5 系统临时目录——获取方式与使用方法**

- **定义**: 操作系统临时目录(`/tmp`、`/var/tmp`);
- **获取方式**: 常量 `Path("/tmp")`、`Path("/var/tmp")` 恒定拼入白名单;
- **使用方法**: 白名单自动放行区, tool 可在系统临时目录内读/写/删(删受 R3-R6 判定); 3.3决策② 明确保留。

**3.2.6 授权目录——获取方式与使用方法**

- **定义**: 除项目根外, 用户额外授权 tool 访问的工作目录(可多个);
- **获取方式**: `config.get_allowed_dirs()`(list) —— 配置 `app.allowed_dirs`(YAML 列表); 项目根天然在授权内, 无需重复列入(决策④);
- **边界约束**: 指向代码库根或其子/父级 → `ValueError` 拒绝加载(3.3 边界约束/⑦禁区冲突); 非字符串条目 → `ValueError`;
- **使用方法**: 等同项目根——读/写/删/浏览, 参与 R3-R6 删除判定; 属白名单。

**3.2.7 白名单——目录组成与使用规则(判定集合)**

- **目录组成**: = 用户主目录(`Path.home()`) + `/tmp` + `/var/tmp` + 项目根 + 授权目录(3.3决策②, `get_default_allowed_paths()`/`ALLOWED_PATHS`); **废除「所有现存盘符」全盘放开**——各盘只有落在用户主目录/项目根/授权目录内的路径才允许;
- **使用规则**: 白名单内**读/写/删都容许**(删受 R3-R6 约束); **递归删除(删目录树)需用户授权**;
- **代码逻辑用途**: `validate_tool_path()` 对白名单内路径判定放行。

**3.2.8 黑名单(禁区)——完整目录清单与使用规则(一张名单, 按操作分流写规则/删除规则)**

- **目录组成(6类, 按判定方式)**:
  - 第1类 跨平台精确: `/etc/shadow`、`/etc/sudoers`;
  - 第2类 跨平台前缀: `/proc`、`/sys`;
  - 第3类 Windows 精确: `C:\Windows`、`C:\Program Files`、`C:\Program Files (x86)`、`System32\config\SAM`、`System32\config\SYSTEM`、`System32\config\SECURITY`、`System32\config\SOFTWARE`、`System32\config\DEFAULT`;
  - 第4类 Windows 前缀: `System32\config`、`WinSxS`;
  - 第5类 磁盘根: 所有盘根(如 `C:\`、`E:\`);
  - 第6类 代码库根: `F:\OmniAgentAs-repair` 及其子/父级(⑦动态判定, 含 get_code_root)。
- **归属禁区**: 第1-5类 → **系统禁区**; 第6类 → **非系统禁区**(=普通禁区);
- **一张名单 + 按操作分流**(北京老陈 2026-08-10: 黑名单分写/删好处理 → 2026-08-10 定稿: 黑名单只有一张, 判定时按操作走两套规则):
  - **写规则**: 命中即拦写——系统禁区写硬拦永不授权(3.2.9), 非系统禁区写需**任务级**临时授权(3.2.13);
  - **删除规则**: 命中即拦删——系统禁区删硬拦、非系统禁区删硬拦, **删一律硬拦永不授权**(3.2.9/3.2.10);
- **判定位置**: 系统禁区 = `tool_constants.FORBIDDEN_PATHS_*` + `_is_forbidden_path` 盘根判定; 非系统禁区 = `_is_forbidden_path` ⑦ 代码库根判定;
- **代码逻辑用途**: `_is_forbidden_path()` 命中即按操作分流——写操作走黑名单写规则, 删除操作走黑名单删除规则。

**3.2.9 系统禁区——目录与使用规则(黑名单·系统部分)**

- **目录组成**: FORBIDDEN_PATHS 常量(系统敏感, 3.2.8 第1-4类) + 所有磁盘根(3.2.8 第5类);
- **使用规则**: 读✅放行(内容敏感性由 contentFilter 兜底); 写❌硬拦(写规则); 删❌硬拦(删除规则); **永不参与临时授权**。

**3.2.10 非系统禁区(=普通禁区)——目录与使用规则(黑名单·非系统部分)**

- **目录组成**: 代码库根及其子/父级(3.2.8 第6类, ⑦ `_get_code_root()` 动态判定);
- **使用规则**: 读✅放行; 写⚠️**任务级**临时授权后放行(写规则, 3.2.13); 删❌硬拦(删除规则); 临时授权**仅写可授权, 仅走任务级**(用户点名), LLM 参数触发不能授权禁区。

**3.2.11 白名单外路径——目录与使用规则(落区概念)**

- **目录组成**: 白名单与黑名单之外的路径(如用户主目录/项目根/授权目录之外、非禁区的其他盘路径);
- **使用规则**: 读✅只读工具直接放行(不弹确认); 写/删⚠️临时名单入单后放行, 未入单 blocked(3.3决策⑤, 临时名单见 3.2.12);
- **与临时名单的关系**: 白名单外路径是**临时名单的触发落区**——LLM 工具参数带路径, **先判白名单、再判黑名单, 都不在**才入临时名单(3.2.12), 不是「给了路径就入」; 非系统禁区写**不在此列**(黑名单内), 走任务级临时授权(3.2.13), 系统禁区永不入。

**3.2.12 临时名单(动态名单, 对应 3.3 决策⑤)**

- **定位**: 临时名单是**第三张动态名单**, **既不是白名单也不是黑名单**——白名单=常驻允许(配置/常量), 黑名单=常驻禁止(常量/动态, 一张名单按操作分流), 临时名单=**运行期动态放行**(LLM 工具参数触发, 用户确认后临时入单, **与 task 绑定, task 结束清零**);
- **触发判定(谁给路径 → 落哪张名单)**: 路径是 **LLM 在 ReAct 循环的工具调用参数中动态给出的**(如 `path`/`dest` 等), 系统不预登记任何"待授权目录"。LLM 每发起一个工具调用, Safety 层 `check_before_execute` → `_check_known_risks` → `validate_tool_path` 校验该路径, **按固定三步判定**:
  1. **先判白名单**: `validate_tool_path()` 判定路径在白名单内 → 直接放行, **不建临时名单**(白名单内本就读/写/删都容许);
  2. **再判黑名单(=禁区)**: `_is_forbidden_path()` 判定路径在黑名单内 → **按禁区原则处理, 不建临时名单**——写规则: 系统禁区写硬拦永不授权、非系统禁区写需**任务级**临时授权(3.2.13); 删除规则: 一律硬拦永不授权;
  3. **都不在(白名单外·非禁区) → 建临时名单**: 路径**既不在白名单也不在黑名单**(即白名单外·非禁区, 如用户主目录/项目根/授权目录之外、非禁区的其他盘路径) → 写/删才入临时名单(先申请→确认→入单);
  > **临时名单只在「白名单+黑名单都不在」时建立**——白名单内直接放行不建, 黑名单内(=禁区)按禁区原则处理不建; 非系统禁区写可授权**不走 LLM 触发**, 走**任务级临时授权**(3.2.13)。
- **触发链路**(已实施, 代码与设计一致): LLM 工具参数带白名单外·非禁区路径 → **白名单判定(不在)** → **黑名单判定(不在)** → Safety 返回 `requires_confirmation=True` + `auth_path`(取真正越权参数的真实路径, BUG-D) → `action_handler` 走 HITL 前端弹确认 → 用户点允许 → `grant_temp_auth(auth_path, recursive=True)` 入临时名单, **本 task 内有效** → **task 结束 `finally` 调 `clear_temp_auth()` 清零**(BUG-E);
- **与任务级的关系**: 3.2.13「任务级临时授权」是**另一条触发路径**(任务启动解析用户点名目录, 一次性批量授权), 与本文 LLM 路径触发**并行不冲突**——两者最终都入同一临时名单(`temp_auth`); **任务级是「非系统禁区写可授权」的唯一通道**(用户点名代码库根 → 写可授权, LLM 参数触发不能授权禁区);
- **与 task 绑定**: 临时名单生命周期=**task 级**——入单后**本 task 内持续有效**(读/写/删都可走), **task 结束 `finally` 调 `clear_temp_auth()` 清零**(BUG-E), **不跨 task 残留**; 支持递归(授权目录含其子目录树); 一次一申请(本 task 内有效, 新 task 需重新申请);
- **禁区与临时名单**: 系统禁区永不入临时名单(写/删均不可); 非系统禁区**仅写可入**(任务级, 3.2.13), 删不可——**「都不在才建」是 LLM 触发的建立条件, 任务级授权不受此限**(用户点名即显式授权);
- 临时名单不写入 `allowed_dirs`(持久授权仍走配置白名单);
- **任务临时目录与临时名单的关系(2026-08-10 19:20 小欧, v1.43)**:
  - **任务临时目录**(表一概念层) = 用户下命令时在任务文本中提到的目录(如 `D:\我的视频`), 是**真实目录实体**, 不是技术术语;
  - **临时名单**(表三实现层) = 运行期动态放行名单, 是**代码判定载体**, 不是真实目录;
  - **关系**: 任务临时目录是临时名单的**触发源之一**, 不是独立分区、不是新名单——它只是一个路径, 经 3.2.13 解析后按落区判定进入临时名单(或禁区不入);
  - **临时名单的两个触发源汇总**:

| 触发源 | 来源 | 建立条件 | 入单范围 |
|--------|------|---------|---------|
| **LLM 工具参数**(3.2.12) | ReAct 循环 LLM 调用工具时带的路径参数 | **白名单+黑名单都不在才建** | 仅白名单外·非禁区(写/删) |
| **任务级用户点名**(3.2.13) | 任务启动时解析用户任务文本中的路径 | **不受「都不在才建」限**——用户点名即显式授权 | 非系统禁区写可入(唯一通道); 白名单外·非禁区写/删均可入; 系统禁区永不入 |

  - 两个触发源最终都入**同一张临时名单**(`temp_auth`), 生命周期一致(task 级, task 结束清零); 区别仅在**触发时机**(LLM 运行期 vs 任务启动期)和**禁区准入范围**(LLM 不能授权禁区 vs 任务级可授权非系统禁区写)。

**3.2.13 任务级临时授权(用户下命令提到的目录 → 入临时名单)**

- **定位**: 用户下命令时在任务文本中提到的目录(如 `D:\我的视频`)**不是独立概念、不是新分区**(关系详解见 3.2.12「任务临时目录与临时名单的关系」)——它就是一个路径, 落哪区按哪区判定(3.2.14); 它只是触发「临时名单(3.2.12)」的**任务级触发路径**: 用户点名 → 任务期间入临时名单;
- **触发流程**: 任务启动(`initialize_run_state`)解析用户任务文本中的路径(`盘符:\...` 模式) → 前端一次性确认清单 → 批量 `grant_temp_auth(recursive=True)` → 任务结束 `clear_temp_auth()` 恢复;
- **非系统禁区写的唯一授权通道**: 代码库根(非系统禁区)在黑名单内, LLM 参数触发建不了临时名单——**只有用户点名代码库根(任务级授权) 才能放行写**, 删仍硬拦; 系统禁区永不授权(3.2.9);
- **读写定义**(按该路径落在三区中的位置判定):
  - 落白名单内(用户主目录/项目根/授权目录) → 本就放行, 无需任务授权(递归删除仍需用户授权);
  - 落白名单外·非禁区 → 读✅ / 写⚠️入临时名单 / 删⚠️入临时名单;
  - 落非系统禁区(代码库) → 读✅ / 写⚠️任务级临时授权 / 删❌硬拦;
  - 落系统禁区 → 读✅ / 写❌硬拦 / 删❌硬拦, **永不授权**。

**3.2.14 完整判定规则(读/写/删, 文字版)**

- **白名单内**(用户主目录+`/tmp`+`/var/tmp`+项目根+授权目录): 读✅ / 写✅ / 删受 R3-R6 判定, **递归删除需用户授权**;
- **白名单外·非禁区**: 读✅放行 / 写⚠️临时授权 / 删⚠️临时授权(递归);
- **非系统禁区**(代码库及父子级): 读✅放行 / 写⚠️**任务级**临时授权(3.2.13) / 删❌硬拦;
- **系统禁区**(系统目录/盘根): 读✅放行 / 写❌硬拦 / 删❌硬拦。

**3.2.15 操作类型(mode)判定依据**

- **读**(只读工具, 按 tool_name 集合): listdir/tree/find/grep/readtext/readmedia/read_pdf/read_docx/read_pptx/read_xlsx 等只读操作(以真实注册名为准, 三堂会审发现5: `stat` 在 registry 无对应注册工具已剔除, `listdir` 为注册名 `list_directory` 仅别名; 清单见 9.3.1 P2);
- **删**: delete;
- **写**: 其余路径类工具(compress/extract/move/copy/rename/writetext/download/generate_chart/screen_capture 等)。

## 六、根因: 项目根存在多条并行定义, 且 delete_safety 用了错误的一条

**审计发现的 2 个既有漏洞**(独立于⑦, 且必须先于⑦修正):

1. **漏洞A: `dest` 目标/输出参数全面漏检**(高危)
   - 8个工具的目标/输出路径参数名是 `dest`(compress/extract/move/copy/rename/generate_chart/download/screen_capture), 全部不在 `_PATH_PARAM_KEYS` 中 → `validate_tool_path` 找不到、不校验 → **dest 可指向任意目录(含代码库根/系统目录)而放行**。
   - 即使不加⑦禁区, 当前白名单机制对 dest 也形同虚设: copy/move 可把文件拷入系统目录或任意盘, compress 可把压缩包输出到任意位置。
   - 修法: `_PATH_PARAM_KEYS` 增加 `"dest"`, 并在 `validate_tool_path` 中对**所有**命中路径参数逐一遍历校验(当前只取第一个命中参数, 见下漏洞B)。

2. **漏洞B: `validate_tool_path` 只校验第一个路径参数**(path_safe_check.py:265-272)
   - 当前逻辑 `for key in _PATH_PARAM_KEYS: real_path = params.get(key); if ...: break` — **只取第一个命中的参数校验, 其余路径参数放行**。
   - 即使补了 `dest`, 若 path 先命中, dest 仍漏检。**必须改为遍历所有命中参数逐一校验**, 任一越权即拒绝。
   - 修法: 遍历 `_PATH_PARAM_KEYS`, 对 params 中出现的每个路径参数都调 `validate_path`, 全部通过才算通过。

**⑦禁区正确实施的前置条件**(缺一不可):
- ⑧ 补 `_PATH_PARAM_KEYS` 加 `dest`(漏洞A)
- ⑨ `validate_tool_path` 改为多路径参数全量校验(漏洞B)
- ⑦ `_is_forbidden_path` 新增代码库根及其父级→forbidden(本义)
- ⑦ 经 ⑧⑨ 覆盖后, 才真正封死代码库根的一切 read/write/delete/浏览

### 7.8 授权目录与白名单外临时授权设计(北京老陈需求 2026-08-09 23:47 + 2026-08-10 00:18, 决策项确认见 3.3)

**目标**: 除项目根外, tool 可访问多个「授权目录」; 白名单=主目录+`/tmp`+`/var/tmp`+项目根+授权目录; 白名单外路径经弹窗/对话临时授权**本 task 内放行(task 结束清零)**; 项目根定义不变(有配置用配置值, 无配置用用户主目录)。

**配置格式**(config.yaml):
```yaml
app:
  project_root: E:\test_dir
  allowed_dirs:
    - D:/data
    - G:/backup
```

**实现要点**:
1. **config 新增 `get_allowed_dirs()`**(修改⑩):
   - 读 `app.allowed_dirs`, 返回 `List[str]`;
   - 空/未配置 → 返回空列表(不报错, 白名单=主目录+`/tmp`+`/var/tmp`+项目根);
   - **校验: 任一授权目录是代码库根或其父/子级 → 抛 ValueError 拒绝加载**(与⑦禁区冲突, 防止授权目录变相开放代码库);
   - 授权目录存在性: 不强制存在(可在运行期创建), 但不存在时不自动创建(与项目根下载/输出目录自动创建区分)。

2. **白名单设定**(修改⑪, `path_safe_check.py:90`):
   - `ALLOWED_PATHS = [Path.home(), Path("/tmp"), Path("/var/tmp")] + [Path(project_root)] + [Path(d) for d in get_allowed_dirs()]`;
   - **废除**「所有现存盘符」的全盘放开: `get_default_allowed_paths()` 不再拼接 `get_existing_drives()`;
   - 效果: 各盘只有落在主目录/项目根/授权目录内的路径才允许, 其余盘位置拒绝。

3. **删除判定多授权域**(修改⑫, `delete_safety.py:51`):
   - `allowed_roots = [Path(project_root)] + [Path(d) for d in get_allowed_dirs()]`;
   - 目标在任一 allowed_roots 内 → R3-R5 正常流程, 递归走 R4 确认;
   - 目标在全部 allowed_roots 外 → R6 拒绝(递归)或按 R5 判定;
   - **授权目录等同项目根**: 授权目录内的递归删除不再被误判 R6。

4. **`_guard_forbidden_delete`(delete_file.py:56/94)同步扩展**:
   - 保护对象从「项目根」扩展为「项目根+授权目录」: 禁止删除任一授权根自身及其父级祖先(与⑦禁区配合, 代码库根由⑦承接)。

5. **白名单外临时授权**(修改⑮, 北京老陈 2026-08-10 裁定, **与 task 绑定, task 结束清零, 支持递归**):
   - **原则**: 白名单(主目录+tmp+项目根+授权目录)外路径**默认拒绝**, 必须**弹窗/对话授权**后才放行**本次申请的那一次操作**;
   - 交互: tool 要访问白名单外路径 → 安全检查 blocked + 前端弹授权框(显示路径+操作) → 用户点击允许 → **本次**放行; 拒绝/超时 → blocked;
   - **触发源(v1.28 补)**: 待授权路径由 **LLM 工具调用参数动态给出**(ReAct 循环中 LLM 每选一个白名单外路径发起写/删, 就触发一次授权请求), 系统不预登记「待授权目录」(详见 3.2.12);
   - **与 task 绑定(老陈裁定)**: 授权**本 task 内持续有效**, **task 结束清零**, 不跨 task 残留; 新 task 必须重新申请, 不缓存复用;
   - **支持递归(老陈裁定)**: 授权某目录后, **其整个子目录树的递归操作在该授权范围内**(如整体复制/删除/打包该目录树可一并授权, 不需逐目录重复申请);
   - 实现: `validate_path` 白名单未命中时, 若该路径已入本 task 临时名单(含递归范围) 则放行, 否则返回需授权信号(前端弹框); task 结束 `clear_temp_auth()` 清零;
   - **代码库根(⑦=非系统禁区)写⚠️可经任务级临时授权**; 删❌硬拦永不授权; 系统禁区(系统目录/盘根)永不参与临时授权(写删永久封锁)。此为 v1.13 禁区分级后的新规(7.9.1), 取代本条未分级前的「代码库根永久封锁」旧述; 见 3.2.10/3.2.13/表五。
   - 临时授权**不写入 `allowed_dirs`**(持久授权仍走配置)。

**与现有机制的边界**:
- 下载目录/输出目录仍在项目根下(`project_root/download`、`project_root/output`), 不受授权目录影响(授权目录不承接自动建目录职责);
- 授权目录仅影响**路径白名单与删除判定**, 不改变项目根定义、不改变配置定位(config.yaml 仍在代码库根);
- 授权目录与项目根可重叠(重复配置无副作用, 去重即可);
- 临时授权**不覆盖** R1/R2/R3-R6 与⑦禁区(仅跳过白名单范围检查, 危险操作确认流程仍走安全层)。

**回归用例**(实施后必测):
- 白名单: 授权目录内操作 → 放行; 项目根内操作 → 放行; 主目录内操作 → 放行(保留); 未授权盘位置(如 `D:\娱乐\视频`) → 默认 blocked(废除全盘放开);
- 临时授权: 对 `D:\娱乐\视频` 弹窗点允许 → **本 task 内放行**; 未点/拒绝 → blocked;
- 禁区: 系统禁区(如 `C:\Windows\*`)写/删→硬拦; `F:\OmniAgentAs-repair\*` 读→放行 / 写→任务级临时授权(用户点名) / 删→硬拦(非系统禁区新规, 见 7.9.1);
- 删除: 授权目录内递归删除 → R4 确认; 授权目录外递归删除 → R6 拒绝;
- 禁区冲突: `allowed_dirs` 含代码库根 → 配置加载报错;
- 配置缺省: 无 `app.allowed_dirs` → 白名单=主目录+`/tmp`+`/var/tmp`+项目根。

### 7.9 禁区分级 + 读放行 + 任务目录临时授权设计(北京老陈 2026-08-10 08:25 裁定, v1.13 新增, **待三堂会审/实施**)

> **背景**: 北京老陈 2026-08-10 提出——①任务信息中提到的目录应作为临时授权可访问; ②禁区内**读取**应放行, **删除**绝不可; ③禁区按性质分两类。据此对 7.8「禁区全操作硬拦」模型做分级重构。

**7.9.1 禁区分级(两类, 老陈裁定)**

| 禁区类别 | 内容 | 读 | 写 | 删 |
|---|---|---|---|---|
| **系统禁区** | `C:\Windows`、`C:\Program Files`、`C:\Program Files (x86)`、`System32\config`(含 SAM/SYSTEM/SECURITY/SOFTWARE/DEFAULT)、`WinSxS`、`/etc/shadow`、`/etc/sudoers`、`/proc`、`/sys`、**所有磁盘根**(盘根写删高危, 安全优先归此类) | ✅ 放行 | ❌ 硬拦 | ❌ 硬拦 |
| **非系统禁区** | 代码库根 `F:\OmniAgentAs-repair` 及其子/父级(⑦) | ✅ 放行 | ⚠️ 临时授权后放行 | ❌ 硬拦 |

> 与 7.8「⑦ 代码库根永久封锁、不参与临时授权」的差异: 新规下非系统禁区(代码库)**读放行、删硬拦、写可临时授权**; 系统禁区仍不参与任何授权(写删永久封锁)。

**7.9.2 只读放行(第一层)**: 只读工具(list/read/search/stat/file_tree 等, 按 tool_name 集合判定)操作白名单外**非禁区**路径 → 直接放行, 不触发确认。理由: 只读不改数据, `_is_forbidden_path`(禁区)仍硬拦, 风险仅内容敏感 → contentFilter 兜底。此层解决 LLM 读取卡确认最常见阻塞。

**7.9.3 任务目录临时授权(第二层)**: 任务启动时解析用户任务文本中的路径(`盘符:\...` 模式) → 前端一次性展示确认目录清单 → 全部 `grant_temp_auth`(recursive=True) → 任务结束 `clear_temp_auth`。授权后任务目录内读/写/删顺滑执行(删仍受 R3-R6 判定)。与 7.8-5 临时授权一致: **与 task 绑定、支持递归、task 结束清零**。

**7.9.4 Prompt 告知(第三层) — 经评估可省(YAGNI)**: 二层任务目录授权为**递归**(recursive=True), 子目录树变体全覆盖; 一层读全放行; 写/删确认流兜底 → LLM 无需额外被告知任务目录, 单独注入 `【任务目录】` 属过度设计, 不实施。(已实施的 7.9 前置: `_get_project_root_info`/`_get_environment_info` 注入授权目录与项目根同源, 2026-08-10)

**7.9.5 完整判定矩阵**

| 目标路径 | 读 | 写 | 删 |
|---|---|---|---|
| 白名单内(主目录+tmp+项目根+授权目录) | ✅ | ✅ | R3-R6 判定 |
| 白名单外·非禁区 | ✅ 放行 | ⚠️ 临时授权 | ⚠️ 临时授权(递归) |
| **非系统禁区**(代码库) | ✅ 放行 | ⚠️ 临时授权 | ❌ 硬拦 |
| **系统禁区**(系统目录/盘根) | ✅ 放行 | ❌ 硬拦 | ❌ 硬拦 |

**7.9.6 实现改动清单(待实施)**

| 文件 | 改动 |
|---|---|
| `path_safe_check.py` | `_is_forbidden_path` 扩展返回禁区类别(system/non_system); 新增只读工具集合; `validate_tool_path(tool_name, params, mode)` 按 mode(读/写/删)+禁区类别+白名单分级判定 |

**mode 来源**: 按 tool_name 分三组——只读工具集合(读)、`delete`(删)、其余路径工具(写), 不依赖新增元数据字段(KISS)。

**7.9.7 边界约束(不可突破)**
- 系统禁区永不参与临时授权: `is_temp_authorized` 判定前先过禁区分类, 系统禁区直接硬拦;
- 非系统禁区删操作硬拦, 临时授权无效; 写操作可授权;

- 解析误报/漏报(否定语境等): v1.13 先按"用户显式提及即算", 语境过滤不纳入本期(YAGNI)。

**7.9.8 回归用例(实施后必测)**
- 读: list/read 白名单外非禁区目录 → 直接放行(不再弹确认); 读代码库根下文件 → 放行; 读 `C:\Windows\...` → 放行(内容过滤兜底);
- 写: 白名单外非禁区目录 → 确认+临时授权后放行; **代码库根下写** → 确认+临时授权后放行(非系统禁区新规); **系统目录写** → 硬拦, 授权无效;
- 删: 代码库根删除 → 硬拦(即使临时授权); 系统目录删除 → 硬拦; 白名单外非禁区递归删除 → 临时授权+确认;
- 任务目录: 任务文本提到 `D:\我的视频` → 任务启动确认后其内读写删顺滑, 任务结束清除后再次访问需重新授权。
