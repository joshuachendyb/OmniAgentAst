## ◈ v2.0 定稿：核心数据模型重构（以本章为最终准绳）

> **决策（北京老陈 2026-08-19 拍板）**：v1.x 各章为讨论依据；本 v2.0 定稿为最终可执行依据。凡与 v2.0 冲突处，以 v2.0 为准。
> 背后主线：`chat_messages` 名实不符（混存 user/assistant 双角色、assistant 信息散乱）→ **新建专属 user 消息表，assistant 信息与 final 字段对齐**，老表冻结废弃。

### ◈.1 定稿后的四表数据模型

| 表 | 定位 | 说明 |
|----|------|------|
| **`chat_user_message`**（新建） | user 消息 + AI 最终回答汇总 | `content`(用户输入) + `response/reasoning/outcome/model/provider/accumulated_usage`（对齐 final）+ `session_id`/`task_id` + client 采集字段 + `created_at` |
| **`chat_task_steps`**（原名 `chat_message_steps`，改名） | AI 响应的全部执行 step | final step 完整信息（response/reasoning/outcome/model/provider/accumulated_usage）均在其 `step_json`；**每行新增 `usage` 列承载该轮 token** |
| **`chat_tasks`**（保留） | 任务汇总视图 | `response` 快照 + `model/provider/accumulated_usage` + 统计（status/duration/llm_call_count/total_steps…） |
| **`chat_messages`**（**冻结废弃**） | 存量历史（不写新链路，降级可读） | 保留 2132 条历史供前端降级展示；不再有代码写入；后续择机清理 |

关系：`chat_user_message.task_id` ⇄ `chat_tasks.task_id`；`chat_task_steps.task_id/message_id` ⇄ 任务/消息；`chat_tasks.user_message_id` → `chat_user_message.id`。

### ◈.2 新建 `chat_user_message` 表（最终字段清单）

| 字段 | 类型 | 来源/对齐 | 处置 |
|------|------|-----------|------|
| id | INTEGER PK | 自增 | 保留 |
| session_id | TEXT NOT NULL | 所属会话 | 保留 |
| content | TEXT NOT NULL | 用户输入（去 role 后恒为 user） | 保留 |
| task_id | TEXT | 关联任务（= chat_tasks.task_id） | 在（改动6 挂接） |
| response | TEXT | = **FinalStep.response**（AI 最终回答） | 新增（对齐 final） |
| reasoning | TEXT | = **FinalStep.reasoning**（推理过程，原 `chat_messages.thought` 语义） | 新增（对齐 final） |
| outcome | TEXT | = **FinalStep.outcome**（终态 completed/failed/cancelled，原 `chat_messages.status` 语义） | 新增（对齐 final） |
| model | TEXT | = **FinalStep.model** | 新增（对齐 final） |
| provider | TEXT | = **FinalStep.provider** | 新增（对齐 final） |
| accumulated_usage | TEXT | = **FinalStep.accumulated_usage**（token 累计） | 新增（对齐 final） |
| client_os / browser / device / network | TEXT | 客户端采集（功能未落地，老陈定保留） | 保留（待用） |
| created_at | TEXT | 落库时间 | 新增 |

> **不进入新表的旧气泡字段**（随老 `chat_messages` 一并废弃，无需新表承担）：`role`、`execution_steps`、`display_name`、`status`、`thought`、`metadata`、`reply_to_message_id`（新表以 `task_id` 关联替代）。
> **成果**：一行 `chat_user_message` 即可取出"用户问什么 + AI 怎么答 + 用什么模型 + token 花多少 + 终态 outcome"，前端直接用，无需 join。

### ◈.4 老 `chat_messages` 冻结废弃处置

- **不再有任何新链路代码写入** `chat_messages`（用户发消息、assistant 落库全部改走 `chat_user_message` + `chat_task_steps`）。
- 存量数据（user 994 + assistant 1066，共 2132 条）**保留不动**，供前端历史消息降级展示；数据回读处设"新表有则读新表、无则读老表"的降级。
- 冻结后，原"清 execution_steps 列 / 删死字段（status/thought/display_name/metadata/device/network）"的清理**不再逐一执行**——整表逐步废弃即统一覆盖，避免在老表上做零碎 DDL。
- 保留 `chat_messages` 元信息（索引）即可，不新建索引。

### 〇.6 合理性总评

> 四表命名规范、主键/外键/类型合理，索引基本覆盖存量查询路径。问题集中为"**冗余与死字段**"而非"命名缺失"。

- **命名/结构**：合理，无命名歧义。
- **关键冗余判断**：
  1. `chat_messages.execution_steps` 列 = 双写快照（改动2 清）。
  2. `chat_messages` 的 `timestamp` **双索引**（idx_messages_timestamp + idx_msg_timestamp）。

## 1、方案背景与目标

当前聊天存储存在 5 处"名实不符 / 冗余双写 / 关联缺失 / 未落地接口"问题，本方案一次性收敛：

1. **表名 `chat_message_steps` 名实不符**：该表实际存的是**任务级整套执行步骤**（一行一步，已挂 `task_id`），但名字暗示"消息级步骤"。按原始设计意图（一个 task 对应一整套 step 消息）改名 `chat_task_steps`。
2. **`chat_messages.execution_steps` 旧列仍在双写 + 回退读取**：系统同时把步骤快照写进 `chat_messages.execution_steps` 列（整块 JSON），而权威步骤早已逐步落库 `chat_message_steps`。存在双重写入、违反 DRY 与「禁止backward」。
3. **任务级回放/统计接口（C1/C2）未实现**：现有 `chat_tasks` 已建行且有步骤流可查，但无按 `task_id` 的详情统计（C1）与步骤回放（C2）。只有按 message 的降级回放（C3，`execution_stream`）。
4. **`chat_session_title_history` 死表未清理**：建表 + 写入函数 + 调用链均已存在，但系统已不再消费该历史，属待清理死表。
5. **消息↔任务关联缺失**：`chat_messages` 中 **user 消息从不挂 `task_id`**（994 条全 None），`reply_to_message_id` 关联字段全表 0 条被填（废字段）。task↔user 唯一关联在 `chat_tasks.user_message_id`，聊天消息表内部无法 self 达任务/互指 user↔assistant。

> 本文档所有【已证实】引用均经本地代码逐一核对；【待决策】点需北京老陈拍板后再执行。

## 6、改动 5：消息↔任务关联补全（user 挂 task_id + user/assistant 互指）

> 来源：北京老陈 2026-08-19 现场核对实测数据后拍板纳入。实测：`chat_messages` 中 user 消息 994 条全部 `task_id=None`；`reply_to_message_id` 字段全表 0 条被填（废字段）；task↔user 唯一关联在 `chat_tasks.user_message_id`。

### 6.1 目标
补齐消息↔任务双向关联，使三者互达（KISS-DIRECT，不引入反向冗余存储）：
- user 消息挂 `task_id`（任务启动后回填）。
- assistant 消息落库时写 `reply_to_message_id = 其 user 消息 id` + `task_id`（已写）。

### 6.2 现状根因（【已证实】）
| 事实 | 证据 |
|------|------|
| 现网主用 assistant 插入走 S2 `allocate_and_insert_message` | `storage.py:283` `INSERT INTO chat_messages(id, task_id, session_id, role, content, timestamp)`——**无 `reply_to_message_id`** |
| 旧链路 `insert_assistant_message` 支持 `reply_to` | `storage.py:191-196` INSERT 含 `reply_to_message_id`，但非现网主路径 |
| user 消息插入早于 task_id 生成（时序） | 实测同任务 user id=1003854 / assistant id=1003855，task_id 在任务启动时才生成，故 user 消息落库时无号可挂 |

### 6.3 改动点（【已证实】落点）
| # | 文件:行 | 现状 | 改为 |
|---|---------|------|------|
| 1 | `stream_orchestrator.py`（db_ops.insert_task 闭包 :254-259） | 建 task 时仅 INSERT chat_tasks | 在 insert_task 后紧接 `UPDATE chat_messages SET task_id=? WHERE id=?`（`id=_user_msg_id`），为 user 消息回填任务号。`db_ops` 增 `link_user_task`（或并入 insert_task 回调） |
| 2 | `storage.py:283`（allocate_and_insert_message） | INSERT 无 `reply_to_message_id` | INSERT 增 `reply_to_message_id` 列，值 = 本任务的 `user_message_id`。`db_ops.allocate_and_insert` lambda（stream_orchestrator:246）需把 `_user_msg_id` 一并传入函数签名 |
| 3 | `chat_messages` DDL / `_ensure_column` | `reply_to_message_id` 列已存在（`db_initializer.py:129` 附近 ensure 列表内） | 无需新增列；user 侧不反存 assistant_message_id（KISS，靠 reply_to 单向可达） |

### 6.4 关联可达矩阵（改动后）
```
task ──chat_tasks.user_message_id──▶ user 消息
user 消息 ──task_id──▶ task
assistant 消息 ──task_id──▶ task ──chat_tasks.user_message_id──▶ user
assistant 消息 ──reply_to_message_id──▶ user 消息（直接互指）
```

### 6.5 文档同步
- 文档[2] 4.8.x 关联定义、消息落库时序章节核对修订，标注关联已补齐。

### 6.6 验收
- 新完成一个任务后：user 消息 `task_id` 非空、assistant 消息 `task_id` 非空且 `reply_to_message_id = 对应 user 消息 id`。
- C1/C2 能通过该链拼出"用户输入 → 步骤流 → 助手回答"完整回放。
- 全量 pytest 无新增失败。

## 7、执行顺序与依赖

1. **改动 1（改名）** 先行：先建新表名 DDL + 迁移 RENAME，代码引用同步。
2. **改动 4（清死表）** 与改动 1 无依赖，可并行处理。
3. **改动 2（清 column）** 依赖改动 1（`chat_task_steps` 是保底迁移目标），须在改动 1 之后，且先 3.4 保底再 3.5 删列。
4. **改动 3（C1/C2）** 依赖改动 1（按 `chat_task_steps` / `task_id` 查询），在改动 2 之后联调。
5. **改动 5（关联补全）** 依赖改动 1/2（user 回填 `task_id`、assistant 写 `reply_to`），与改动 3 联调（C1/C2 消费该链）。
6. **改动 6（清死字段/冗余索引，待 D7 定）** 依赖改动 2（删列协同），最后一批执行。
7. **文档同步** 贯穿全程，最后统一修订。

> 六改动均为 MAJOR/MINOR 级结构变更（DDL + 现网 ~1.36GB 库迁移），涉及现网库 RENAME / DROP COLUMN / DROP TABLE / 回填迁移。执行前需停服或确认无并发写入窗口。
