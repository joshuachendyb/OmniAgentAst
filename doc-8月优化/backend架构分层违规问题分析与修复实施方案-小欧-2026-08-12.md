## 1. 设计目的、意义与要解决的问题

### 1.1 设计目的

本文档面向 `backend/app/` 后端代码，目标是：**建立并落地一套"分层清晰、依赖单向、职责单一"的后端架构基线**，让每一个架构分层（API 层 / 编排层 / 业务服务层 / 安全层 / 工具层 / 公共基础设施层）只依赖其下层，任何模块改动的影响面可预期、可测试、可回归，为后续新增工具、新增 Agent 实现、修复代码演进提供稳定的骨架。

### 1.2 设计意义

| 意义 | 说明 |
|------|------|
| **可维护性** | 依赖单向后，改一处不会连锁影响无关模块；定位问题可沿依赖方向快速收敛。 |
| **可扩展性** | 新增工具只需在工具层注册、新增服务只需在业务服务层实现，无需跨层改动既有代码（OCP）。 |
| **可测试性** | 层间解耦后，各层可独立单测、可替换实现（接口注入），降低回归成本。 |
| **可演进性** | 分层边界一旦明确并被守护，后续新增工具、新增 Agent 实现、扩展安全策略等演进有据可依，不会再次腐化。 |

### 1.3 要解决的问题（7 个架构分层违规）

| 编号 | 优先级 | 问题 | 一句话说明 |
|------|--------|------|-----------|
| A1 | P0 | tools 层与 services/safety 双向依赖 | 工具层写操作反向依赖安全/任务服务，安全校验又依赖工具注册表 |
| A2 | P1 | app/safety 内部循环依赖 | 备份/清理/记录三个模块互相引用成环 |
| A3 | P1 | tool_retry_engine.py 目录位置错误 | 工具层基础设施放在 Agent 编排层目录 |
| A4 | P2 | api/v1/health.py 越层直接操作工具 | API 层直接导入 tool_registry 并暴露 /tool/execute |
| A5 | P2 | file_path_checker.py 职责混杂 | 路径校验与 SQL/数据/读写错误提示函数同文件 |
| A6 | P2 | base_agent.py 抽象基类依赖具体 tool_registry | 抽象基类绑定具体工具注册表实现 |
| A7 | P1 | API 层职责膨胀 | 编排逻辑与业务 CRUD 内嵌在路由文件 |

### 1.4 设计目标与成功标准

本次审查对象：`backend/app/` 目录下的代码布局、模块职责划分、层间依赖关系。

设计目标：
1. 识别并消除上述 7 个架构分层违规
2. 给出可落地的修复方案，并经过三思三省和三堂会审；
3. 制定分阶段实施计划，确保改动可验证、可回滚；
4. 建立"依赖方向守护测试"，让分层边界可持续被验证，杜绝再次腐化；
5. 将安全层提升为独立顶层目录 `app/safety/`（与 services/tools 平级），实现"层 = 目录"的架构一致性。

**成功标准**：
- 依赖方向恒为 `api → services → safety → tools → utils/db/logger` 单向、无环；
- `tools/` 下不再出现 `from app.services.*` 的导入；
- `api/v1/` 下不再出现 `from app.tools.*` 的导入；
- `pytest` 全量 + 依赖方向守护测试全部通过；
- 安全层目录为 `app/safety/`，全文无 `app.services.safety` 残留。

**范围说明**：本方案仅针对 `backend/app/` 目录，不涉及、不关联任何其他目录（如 `repair-code/`），该目录与本方案无任何关联。

## 2. 系统架构设计与目录对应关系

### 2.1 理想分层架构

backend/app 的理想分层应为单向依赖结构，上层可调用下层，下层不反向依赖上层：

```
┌─────────────────────────────────────────────────────────────┐
│  API / 接口适配层（Backend-for-Frontend）                    │
│  app/api/v1/                                                │
│  职责：HTTP 路由、请求/响应 DTO、参数校验、协议封装           │
│        （SSE/WS 传输格式、HTTP 状态码、错误码映射）           │
│      │                                                      │
│      ▼                                                      │
│  编排层（ReAct 循环、Agent 状态管理、聊天流编排）             │
│  app/services/agent/  app/services/chat/stream_orchestrator  │
│      │                                                      │
│      ▼                                                      │
│  业务服务层（聊天、任务、LLM、模型、提示词等）                 │
│  app/services/chat/  app/services/task/  app/services/llm/   │
│  app/services/model/  app/services/prompts/                  │
│  app/services/lifecycle/  app/services/monitoring/           │
│      │                                                      │
│      ▼                                                      │
│  安全层（工具执行前检查、操作记录、回滚）                     │
│  app/safety/                                                  │
│      │                                                      │
│      ▼                                                      │
│  工具层（具体工具实现与注册）                                │
│  app/tools/                                                 │
│      │                                                      │
│      ▼                                                      │
│  公共基础设施层（通用工具、数据库、日志、配置）                │
│  app/utils/  app/db/  app/logger/  app/config.py             │
└─────────────────────────────────────────────────────────────┘
```

> **说明（架构调整）**：安全层（`app/safety/`）是**独立顶层目录**，与 `app/services/`、`app/tools/` 平级，不再作为 services 的子目录。依赖上仍位于业务服务层之下、工具层之上（`api → services → safety → tools`），仅目录归属独立成层。

### 2.2 目录与架构层对应表

| 架构层 | 对应目录/文件 | 核心职责 | 允许依赖的下层 |
|--------|-------------|---------|--------------|

## 4. 问题逐一分析、修复方案与三堂会审

### 4.1 A1. P0 — tools 层与 services/safety 层双向依赖

#### 4.1.1 当前问题

**依赖方向一：tools → safety/services**

大量文件操作工具直接导入 safety（原 app.services.safety）与 services 层：

```python
# app/tools/file/copy_file.py:36
from app.safety import record_operation, execute_with_safety

# app/tools/file/delete_file.py:32
from app.safety import record_operation, execute_with_safety

# app/tools/file/write_text_file.py 等同理
```

以及任务上下文：

```python
# app/tools/file/copy_file.py:37
from app.services.task.task_context import get_current_task_id
```

**依赖方向二：safety → tools**

安全层路径校验依赖工具注册表：

```python
# app/safety/path_safe_check.py:55-63
from app.tools.registry import tool_registry
from app.tools.tool_types import ToolCategory
from app.tools.tool_constants import (
    FILE_OPERATION_TOOLS, SKIP_DIRS, WINDOWS_SYSTEM_DIRS, ...
)
from app.tools.tools_alias_mapper import get_aliases_for_tool

# app/safety/tool_safety_checker.py:64
from app.tools.registry import tool_registry
```

#### 4.1.2 病根

- 工具执行需要"被记录"和"被保护"，所以工具直接调用 `record_operation`/`execute_with_safety`；
- 安全校验需要知道"这是哪个工具""参数是什么"，所以 safety 层直接读取 `tool_registry`；
- 双方都把对方当成基础设施，导致层间边界破裂。

#### 4.1.3 修复方案（推荐：依赖注入 + 安全 hook 抽象）

**目标**：让工具层不再直接依赖 services 层与 safety 层，安全保护能力通过 hook 注入保持完整。

> **关键发现（三思三省修订，小沈 2026-08-12）**：原方案 `before_execute`/`after_execute` 两方法设计**无法覆盖 `execute_with_safety` 的完整语义**。实际代码中 `execute_with_safety`（`operation_record.py:124-232`）是**三阶段安全执行器**：
> 1. Phase 1：DB 标记 EXECUTING
> 2. 备份：DELETE/MODIFY 操作前备份原文件到回收站
> 3. Phase 2：执行工具核心逻辑
> 4. Phase 3：记录执行结果（成功/失败），失败时保留备份供回滚
>
> 工具函数的调用模式为：`operation_id = record_operation(...)` → `success, detail = await asyncio.to_thread(execute_with_safety, operation_id, _sync_func)`。
> 若仅用 before/after 两方法，**备份和回滚语义将丢失**，造成功能退化。因此 hook 接口必须包含 `record_operation` 和 `execute_with_safety` 两个核心方法。

**步骤**：

1. **新建安全 hook 接口** `app/tools/security_hooks.py`：

```python
from typing import Protocol, Callable, Tuple, Optional

class ToolSecurityHooks(Protocol):
    """工具执行安全 hook 接口 — 封装 record_operation + execute_with_safety 两个核心能力
    
    设计依据：execute_with_safety 是三阶段安全执行器（DB标记→备份→执行→记录→回滚），
    无法拆分为简单的 before/after 回调。工具函数通过此接口获取安全保护，
    不再直接 import safety 层，消除 tools→safety 反向依赖。
    """

    def record_operation(self, tool_name: str, params: dict, task_id: str, **kwargs) -> Optional[str]:
        """记录操作并返回 operation_id，供后续 execute_with_safety 使用"""
        ...

    def execute_with_safety(
        self, operation_id: str, operation_func: Callable, *args, **kwargs
    ) -> Tuple[bool, Optional[str]]:
        """安全执行：备份→执行→记录结果→失败保留备份供回滚
        
        语义与 app.safety.operation_record.execute_with_safety 完全一致：
        - 预期失败：operation_func return False 或 (False, str)
        - 意外异常：让异常抛出，本函数 catch 后 return (False, str(e))
        - 成功：return True 或 (True, None)
        """
        ...
```

> **删除 NoOpSecurityHooks**（三思三省修订）：工具执行**永远需要安全保护**（备份+记录+回滚），"无安全执行"不应作为选项。NoOp 会静默跳过备份和记录，违反安全原则，且无实际使用场景（测试应 mock 真实 hooks 而非用空实现）。

2. **改造 tool_executor.py**，在调用工具时注入 hooks：

```python
# app/services/agent/tool_executor.py
from app.tools.security_hooks import ToolSecurityHooks

async def execute_tool(
    agent,
    tool_name: str,
    tool_params: dict,
    hooks: ToolSecurityHooks | None = None,
) -> dict:
    """执行工具 — hooks 由调用方注入，工具函数通过 agent._security_hooks 访问"""
    if hooks is not None:
        agent._security_hooks = hooks
    result = await _call_tool_impl(agent, tool_name, tool_params)
    return result
```

3. **在 `app/safety/` 中实现 `DefaultToolSecurityHooks`**：

```python
# app/safety/default_hooks.py
from typing import Callable, Tuple, Optional
from app.tools.security_hooks import ToolSecurityHooks
from app.safety.operation_record import record_operation as _record, execute_with_safety as _exec_safety

class DefaultToolSecurityHooks:
    """默认安全 hooks — 逻辑全部复制自 operation_record.py，仅改导入路径"""
    
    def record_operation(self, tool_name: str, params: dict, task_id: str, **kwargs) -> Optional[str]:
        return _record(task_id=task_id, **kwargs)

    def execute_with_safety(
        self, operation_id: str, operation_func: Callable, *args, **kwargs
    ) -> Tuple[bool, Optional[str]]:
        return _exec_safety(operation_id, operation_func, *args, **kwargs)
```

4. **移除 tools/file/*.py 中对 `app.safety` 和 `app.services.task.task_context` 的直接导入**：
   - 删除 `from app.safety import record_operation, execute_with_safety`；
   - 删除 `from app.services.task.task_context import _current_task_id`；
   - 工具函数改为通过 `agent._security_hooks.record_operation(...)` 和 `agent._security_hooks.execute_with_safety(...)` 获取安全保护；
   - `task_id` 改为通过 executor 传入的参数获取（不再依赖 ContextVar）。

5. **把 `path_safe_check.py` 迁回 tools 层** `app/tools/security/path_safe_check.py`：
   - 该文件本质是"工具参数层面的路径安全校验"，属于工具层能力；
   - 保留 `validate_path(file_path, mode, tool_name)` 接口不变；
   - 它依赖 `tool_registry` 获取工具分类和参数，这在本层内是合理的（工具层内部闭环）。

6. **`tool_safety_checker.py` 调用新位置的 `path_safe_check`**：

```python
# app/safety/tool_safety_checker.py
from app.tools.security.path_safe_check import validate_path, is_temp_authorized
```

此时依赖方向变为：
- `safety/tool_safety_checker.py → tools/security/path_safe_check.py`（safety → tools，单向）
- `services/agent/tool_executor.py → safety/default_hooks.py`（编排层 → 安全层，单向）
- `tools/file/*.py` 不再依赖 services 与 safety

**边界澄清（重要，防止误迁移）**：

`safety/tool_safety_checker.py` 当前也直接导入 `tool_registry`（L64 `from app.tools.registry import tool_registry`，L106 调用 `tool_registry.get_tool(tool_name)` 获取 tool_meta 确认策略），但**它不随 path_safe_check 迁移**。原因：

- `path_safe_check.py` 迁回 `tools/security/` 的依据是：其本质是"工具参数层面的路径安全校验"，它依赖 `tool_registry.get_categories()` 属于**工具层内部闭环**（L56 导入、L415 调用），服务层不应承载工具参数校验细节；
- `tool_safety_checker.py` 的职责是"工具执行前的安全编排"（确认判定、已知风险检测、拦截分流），属于**安全层**职责，应留在 `safety/`；
- **依赖合法性**：按 2.2 表安全层"允许依赖 `tools/*, utils/*, db/*`"，`safety` 依赖 `tools/registry` 属**合法单向依赖**，无需回避；
- 迁移后 `tool_safety_checker.py` 通过 `from app.tools.security.path_safe_check import validate_path` 调用工具层能力，此时 `safety → tools` 是**合法的单向依赖**（安全层可依赖工具层，见 2.2 表）；其自身对 `tool_registry` 的直接引用保持合法（安全层→工具层注册表），或收敛到 `path_safe_check` 内部承载，二者皆可，不改变分层结论。

> 一句话：`path_safe_check` 迁走是为了"工具参数校验回工具层闭环"；`tool_safety_checker` 留下是因为"安全编排留在安全层"且其依赖工具层**本就合法**。两者一迁一留，最终消除 tools→services/tools→safety 的反向依赖，保持 safety→tools 合法单向（本段即该项决策落点）。

#### 4.1.4 备选方案（改动较小但不彻底）

仅把 `path_safe_check.py` 从 `safety` 迁到 `tools/security`，保留 tools/file/*.py 对 safety 的导入。

**缺点**：只解决 safety→tools 方向的越层，未解决 tools→services/tools→safety 方向的反向依赖，架构仍不健康。

#### 4.1.5 三思三省

**补充：operation_rollback.py 的 safety→task 越层依赖（审核定案）**

**根因（三思三省）**：`mark_rolled_back()` 是**任务统计**职责（把已回滚的操作 ID 记入 task_tracker），它本属于 task 域；被放进了安全层的回滚模块，导致 safety 反向依赖 task。**正确做法是职责归位，不是技术妥协式的依赖注入**。

**定案方案：职责归位 + 上层编排（task_rollback_service）**：

| 步骤 | 做法 | 说明 |
|------|------|------|
| 1 | `operation_rollback.py` 删除 `from app.services.task import get_tracker` 与 `mark_rolled_back` 调用 | `rollback_session` 退化为纯回滚：只回滚操作、返回回滚结果（`success`/`failed`/`operations`/`success_op_ids`），不再触碰任务统计 |
| 2 | 新建 `app/services/task/task_rollback_service.py` | task 域业务服务，编排"回滚 + 统计"：调 `safety` 的 `rollback_session` 拿回滚结果，再调 task 域 `get_tracker().mark_rolled_back()` 补统计——两者都在 task 服务内部完成，依赖方向单向向下 |
| 3 | `api/v1/task_queries.py`（L16/L59）改为调用 `task_rollback_service` | API 层只做路由+DTO，不再直接触碰 safety 层细节 |

```python
# app/services/task/task_rollback_service.py（示意）
from typing import Dict
from app.safety import rollback_session as _safety_rollback
from app.services.task import get_tracker

def rollback_session_with_stats(task_id: str) -> Dict:
    """任务域回滚编排：回滚 + 统计，safety 层保持纯回滚职责"""
    result = _safety_rollback(task_id)
    if result.get("success") and result.get("operations"):
        success_op_ids = [op["operation_id"] for op in result["operations"] if op["success"]]
        if success_op_ids:
            get_tracker().mark_rolled_back(task_id, op_ids=success_op_ids)
    return result
```

依赖方向变化：

```
修改前: api/v1/task_queries → safety/operation_rollback ──→ services/task   (safety 反向依赖 task，越层)
修改后: api/v1/task_queries → services/task/task_rollback_service ──→ safety → tools → utils
                                    └──────────────┬─────────────┘   （单向向下，无环）
                                          get_tracker() 统计归 task 域
```

**扩展性**：未来回滚策略变化（批量回滚/审计/失败补偿）只改 `task_rollback_service`（业务编排层），回滚动作不变只改 safety 层，统计口径变化只改 task 域——三块职责独立演进，互不越界。

> 备选"依赖注入（回调传入 on_rolled_back）"被否：它把"统计编排"推给调用方，调用方要懂统计细节，且 rollback_session 签名被污染，扩展性差；"回调注册表"引入不必要间接层，KISS 劣于直排。**职责归位是唯一符合分层+SRP 的最优解**。

> 若暂缓实施，须在 `operation_rollback.py` 头注明确标注 `# TODO: safety→task 越层依赖，待 task_rollback_service 编排改造`，杜绝静默蔓延。

> **双路径问题（三思三省修订，小沈 2026-08-12）**：原方案 `tool_facade.execute_tool` 自行实现安全检查+执行，与 chat 路径（`action_handler→tool_safety_checker→tool_executor`）形成**两条独立的工具执行路径**，安全检查力度可能不一致。修正：facade 的 `execute_tool` 必须**复用 `tool_executor`**（统一执行入口），facade 只做 API 适配（安全预检 + task 上下文管理），不重复实现执行逻辑。

**步骤**：

1. **在 services 层新增工具门面** `app/services/tool/tool_facade.py`（新建 `app/services/tool/` 包）：

```python
# app/services/tool/__init__.py
from .tool_facade import list_tools, execute_tool

# app/services/tool/tool_facade.py
import uuid
from app.tools.registry import tool_registry
from app.safety.tool_safety_checker import check_tool_safety
from app.safety.default_hooks import DefaultToolSecurityHooks
from app.services.task.task_context import _current_task_id

async def list_tools() -> dict:
    """供 API 调用的工具列表（只读，无需安全检查）"""
    tools = tool_registry.to_openai_tools()
    result = []
    for t in tools:
        func = t.get('function', {})
        name = func.get('name', '')
        desc = func.get('description', '')
        params = func.get('parameters', {})
        required = params.get('required', [])
        props = list(params.get('properties', {}).keys())
        required_set = set(required)
        result.append({
            "name": name,
            "description": desc[:100] if desc else "",
            "required_params": required,
            "optional_params": [p for p in props if p not in required_set],
            "inputSchema": params,
        })
    return {"total": len(result), "tools": result}

async def execute_tool(tool_name: str, params: dict) -> dict:
    """供 API 调用的安全工具执行入口 — 复用 tool_executor 统一执行路径"""
    # 1. 安全预检（与 action_handler.check_safety_and_confirm 同源）
    safety = await check_tool_safety(tool_name, params)
    if safety.blocked:
        return {"success": False, "error": f"安全拦截: {safety.message}"}

    # 2. 设置任务上下文（必须 try/finally 恢复，防止 ContextVar 泄漏污染并发请求）
    task_id = str(uuid.uuid4())
    token = _current_task_id.set(task_id)
    try:
        # 3. 复用 tool_executor（统一执行入口），注入 DefaultToolSecurityHooks
        #    与 chat 路径共享同一 executor + hooks，消除双路径
        from app.services.agent.tool_executor import execute_tool as _exec
        hooks = DefaultToolSecurityHooks()
        # 构造轻量 agent 上下文供 executor 使用（仅含 _security_hooks）
        class _FacadeAgent:
            _security_hooks = hooks
        agent = _FacadeAgent()
        result = await _exec(agent, tool_name, params, hooks=hooks)
        return {"success": True, "result": result if isinstance(result, dict) else {"output": str(result)}}
    finally:
        _current_task_id.reset(token)
```

> **统一执行路径说明**：chat 路径和 API 路径都走 `tool_executor.execute_tool(agent, name, params, hooks=hooks)`，安全保护由注入的 hooks 提供（`record_operation` + `execute_with_safety`），安全预检由调用方负责（`action_handler.check_safety_and_confirm` 或 `facade.check_tool_safety`）。**一条执行路径，两处安全预检入口，hooks 保证底层保护不遗漏**。

2. **修改 `api/v1/health.py`**：

### 4.6 A6. P2 — `base_agent.py` 抽象基类依赖具体 `tool_registry`

#### 4.6.1 当前问题

`app/services/agent/base_agent.py` 是抽象基类（ABC），却直接导入具体实现：


同时，`ToolLoader` 类也定义在 `base_agent.py` 中，且依赖 `tool_registry`。

#### 4.6.2 病根

抽象基类应只定义接口和通用骨架，不应绑定具体工具注册表实现。当前把工具加载逻辑放在基类里，导致：
- 所有继承 `BaseAgent` 的实现都被迫依赖 tools 层；
- 单测基类困难；
- `ToolLoader` 与 `BaseAgent` 耦合在同一文件。

#### 4.6.3 修复方案

**目标**：抽象基类不依赖 `tool_registry`；工具加载逻辑下放到子类或独立初始化模块。

**步骤**：

1. **把 `ToolLoader` 类独立为 `app/services/agent/tool_loader.py`**。

2. **修改 `base_agent.py`**：
   - 删除 `from app.tools.registry import tool_registry`；
   - 删除 `from app.tools.tool_types import ToolCategory`（如果基类不需要）；
   - 删除 `ToolLoader` 类定义；
   - `__init__` 中不再初始化 `_tools_dict`、`_tool_loader`、`_retry_engine`；
   - 保留 `run_react_cycle` 等抽象/委托方法。

```python
# app/services/agent/base_agent.py 简化后
class BaseAgent(ABC):
    def __init__(self, llm_client: Any, task_id: str, max_steps: Optional[int] = None, **kwargs):
        self.llm_client = llm_client
        self.task_id = task_id
        self.max_steps = max_steps or get_config().get_max_steps()
        self.status = AgentStatus.IDLE
        self.message_builder = MessageBuilder(...)
        self._step_emitter = StepEmitter(self)
        # 工具相关状态由子类/初始化器设置

    @abstractmethod
    async def run_react_cycle(self, task, context=None, max_steps=None, task_id=None):
        ...
```

3. **在 `universal_agent.py` 中完成工具加载**（注意：**不是** `initialize_run_state.py`，见步骤 4 的澄清）：

```python
class UniversalAgent(BaseAgent):

```

4. **职责澄清（审核修正，纠正原方案假设）**：原方案假设"如果 `initialize_run_state.py` 负责创建 Agent，则工具加载可由该模块统一调用"。经代码核实：**`initialize_run_state.py` 不创建 Agent 实例，也不引用 tool_registry**，其职责仅是"每次运行前重置 Agent 状态"（steps/message_builder/status/llm_call_count，注入 system prompt 与 task，import 仅 `app.constants`/`status_table`/`chunk_buffer`/`logger`/`db`）。**真正的 Agent 实例化点在 `api/v1/chat/openai.py:254`**：`agent = UniversalAgent(llm_client=ai_service, task_id=task_id)`。因此：

- 工具加载逻辑放在 `UniversalAgent.__init__`（即步骤 3）即可覆盖全部调用方，**无需**在 `initialize_run_state.py` 额外加载；
- 若后续新增 Agent 实例化点，统一走 `UniversalAgent(...)` 构造，工具加载天然生效；
- `initialize_run_state.py` 保持现状（状态重置职责），不引入工具加载逻辑。

```python
# app/api/v1/chat/openai.py:254  （真实 Agent 创建点，openai.py:46 import UniversalAgent）
agent = UniversalAgent(llm_client=ai_service, task_id=task_id)
```

```python
import time
import uuid
from dataclasses import dataclass

from app.services import get_service
from app.services.model.resolver import get_ai_config_resolver
from app.services.chat.handlers import create_error_response, send_start_step

    create_stream_buffer,
    get_stream_buffer,

from app.services.chat.storage import get_user_message_id

_agent_tasks: set = set()


# 注：orchestrator 不依赖 api/v1 的 DTO，避免 services 层反向依赖 API 层。
# API 层负责把 ChatRequest 解包为原始参数传入。


def generate_task_id() -> str:
    return f"task-{uuid.uuid4().hex}"


async def validate_chat_config():
    """聊天配置校验 — 从 api/v1/chat/openai.py 迁入 orchestrator"""
    try:
        resolver = get_ai_config_resolver()
        is_valid, final_provider, final_model, error_messages = resolver.validate_config()
        if not is_valid:
            return {
                "valid": False,
                "message": f"配置验证失败: {', '.join(error_messages)}",
                "provider": final_provider or "unknown",
                "model": final_model or "",
            }
        return {
            "valid": True,
            "message": f"配置验证通过: {final_provider} ({final_model})",
            "provider": final_provider,
            "model": final_model,
        }
    except Exception as e:
        logger.error(f"验证AI服务配置失败: {e}")
        return {
            "valid": False,
            "message": f"验证失败: {str(e)}",
            "provider": "unknown",
            "model": "",
        }


@dataclass
class StreamState:
    llm_call_count: int = 0
    current_content: str = ""
    current_thought: str = ""
    step_events: list = None

    def __post_init__(self):
        if self.step_events is None:
            self.step_events = []


async def chat_stream_orchestrator(
    messages: list,
    session_id: Optional[str] = None,
) -> AsyncGenerator[str, None]:
    """聊天流编排入口：负责任务生命周期、Agent 启动、SSE 消费。"""
    if not messages:
        yield create_error_response(error_type="invalid_request", error_message="消息列表不能为空")
        return

    user_input = messages[-1].content or ""
    if not user_input.strip():
        yield create_error_response(error_type="invalid_request", error_message="消息内容不能为空")
        return

    ai_service = get_service()
    session_id = session_id or str(uuid.uuid4())
    _model_warning = get_ai_config_resolver().pop_model_warning()

    task_id = generate_task_id()
    _task_token = _current_task_id.set(task_id)  # 三思三省修订：必须 try/finally reset，防 ContextVar 泄漏（同 A4 4.4.3）
    set_session_id(session_id)
    next_step = create_step_counter()
    execution_steps = []
    state = StreamState()

    # Task 生命周期日志
    _task_start_time = time.time()
    _user_msg_id = None
    try:
        _user_msg_id = get_user_message_id(session_id)
    except Exception:
        logger.warning(f"[chat] 获取user_message_id失败: session_id={session_id}")
    log_and_print(f"INFO: {time.strftime('%Y-%m-%d %H:%M:%S')}")
    log_and_print(
        f"[TASK_START] provider={ai_service.provider} model={ai_service.model} |\n "
        f"task_id={task_id} session_id={session_id} "
        f"user_message_id={_user_msg_id} |\n "
        f"user_input={user_input}"
    )

    try:
        buffer = create_stream_buffer(task_id)
        await register_task(task_id, ai_service)

        is_cancelled, cancel_msg = await task_cancel_check(task_id)
        if is_cancelled:
            yield cancel_msg
            return

        async for event in _step_start(
            ai_service, task_id, next_step, user_input, execution_steps, session_id, warning=_model_warning
        ):
            yield event

        if _model_warning:
            _final = FinalStep(
                step=next_step(), response="",
                outcome="failed",
                error_type="config_error",
                error_message=_model_warning,
                model=ai_service.model, provider=ai_service.provider,
                display_name=f"{ai_service.provider} ({ai_service.model})",
            )
            yield format_agent_sse(_final.to_dict())
            return

        agent = UniversalAgent(llm_client=ai_service, task_id=task_id)
        bg_task = asyncio.create_task(run_agent_in_background(
            agent, task_id, user_input, None, next_step, session_id, state, _task_start_time))
        _agent_tasks.add(bg_task)
        bg_task.add_done_callback(_agent_tasks.discard)

        async for sse_chunk in _stream_with_control(
            buffer, task_id, next_step, session_id, execution_steps, state
        ):
            yield sse_chunk
    except asyncio.CancelledError:
        logger.info(f"[chat_stream_orchestrator] 客户端断开(task={task_id})，agent 后台继续")
    except Exception as e:
        logger.error(f"[chat_stream_orchestrator] Error: {e}", exc_info=True)
        yield create_error_response(error_type="orchestrator_error", error_message=f"编排异常: {str(e)}")
    finally:
        _current_task_id.reset(_task_token)  # 三思三省修订：ContextVar 泄漏修复，与 A4 4.4.3 对齐


async def _step_start(ai_service, task_id, next_step, user_input, execution_steps, session_id, warning=None):
    """发送 start 步骤"""
    try:
        start_step = await send_start_step(
            ai_service=ai_service, task_id=task_id, next_step=next_step,
            user_message=user_input, security_check_result={}, warning=warning,
        )
        start_dict = start_step.to_dict()
        execution_steps.append(start_dict)
        yield format_agent_sse(start_dict)
    except Exception as e:
        yield create_error_response(error_type="start_failed", error_message=f"start步骤失败: {e}")


async def _stream_with_control(buffer, task_id, next_step, session_id, execution_steps, state=None, after_seq: int = 0):
    """SSE 消费者包装"""
    from app.services.chat.stream import stream_reader
    async for sse_chunk in stream_reader(buffer, task_id, after_seq):
        async for pause_event in task_pause_check_and_yield(task_id, next_step):
            yield pause_event
        cancelled_sse = await task_cancel_check_and_yield(
            task_id, next_step, session_id, execution_steps,
            state.current_content if state else "")
        if cancelled_sse:
            yield cancelled_sse
            return
        yield sse_chunk


async def chat_stream_reconnect_orchestrator(
    task_id: str, session_id: Optional[str] = None, after_seq: int = 0
) -> AsyncGenerator[str, None]:
    """SSE 重连编排"""
    buffer = get_stream_buffer(task_id)
    if not buffer:
        yield create_error_response(error_type="not_found", error_message="任务不存在或已结束")
        return
    next_step = create_step_counter()
    async for sse_chunk in _stream_with_control(
        buffer, task_id, next_step, session_id or "", [], None, after_seq
    ):
        yield sse_chunk
```

| `api/v1/sessions.py` | `services/chat/session_service.py` | `create_session`、`list_sessions`、`update_session`、乐观锁逻辑、标题历史、删除会话的 display_name 清理 |
| `api/v1/messages.py` | `services/chat/message_service.py` | `get_session_messages`、`save_message`、`display_name_cache` 缓存维护 |
| `api/v1/model_routes.py` | `services/model/config_service.py` | `update_config` 等接口的**业务编排逻辑**（备份→改字段→修复验证→写回→reload→删备份）与越层调用 `app.safety.operation_backup.clear_backup_paths`（API→safety 越层，随汇入 config_service 后改由业务服务层经 services→safety 访问，消除越层）。注意：YAML 低层 I/O（`read_yaml_config`/`write_yaml_config`/`save_config`/`_backup_config`/`_auto_fix_and_validate`）**已经下沉**在 `services/model/persistence.py`（L30-48），API 层只剩编排与 `yaml` 直用，迁移时只迁编排、**复用 persistence.py，不重复迁移底层 I/O**。 |

**迁移边界补充（审核新增）**：

1. **`_agent_tasks` 强引用表**：`openai.py:59` 模块级 `_agent_tasks: set` 用于持有后台 Agent 任务引用防止被 GC。迁移时**随编排逻辑一并迁入 orchestrator**，由 orchestrator 管理任务句柄生命周期（注册/清理），API 层不再持有任务状态。
2. **`display_name_cache` 跨文件耦合**：`messages.py:44` 定义 `display_name_cache = LRUCache(...)`，`sessions.py:278` 在删除会话时调用 `display_name_cache.delete(...)`（sessions.py L21 import messages 模块）。拆分后缓存归属 `message_service` **独占**，`session_service` 通过调用 message_service 提供的清理方法（如 `message_service.delete_session_display_names(session_id)`）完成联动，**禁止 session_service 直接 import message_service 的缓存对象**（保持模块间单向方法调用，不共享可变状态）。
3. **StreamState / step_start / generate_task_id / validate_chat_config**：`openai.py` 中 `StreamState`（L163-173）、`step_start`（L130-142）、`generate_task_id`（L62-64）、`validate_chat_config`（L67-93）均为编排辅助，全部迁入 orchestrator；API 层只保留路由薄壳。

API 层改造后只保留：
- 路由装饰器；
- Pydantic DTO；
- 调用 service 层并返回 `Response` / `StreamingResponse`；
- HTTP 异常转换。

**DTO 边界约定**：API 层负责把 `ChatRequest` 等 DTO 解包为原始参数再传入 orchestrator，禁止 services 层（含 orchestrator）反向依赖 `api/v1` 的 DTO 定义。

#### 4.7.4 三思三省

| 维度 | 分析 |
|------|------|
| **可行性** | 高。本质是代码搬迁，业务逻辑不变；FastAPI 路由调用 service 函数是标准做法。 |
| **风险** | 中。`chat_stream` 是核心链路，搬迁时需保证 SSE 格式、任务状态、断线重连行为完全一致。 |
| **替代方案** | 保留现状，仅加注释说明；但 API 层会持续膨胀，后续更难拆分。 |
| **是否引入新抽象** | 是，`stream_orchestrator` 是必要抽象，符合 SRP 和 SLAP。 |
| **一次性全迁（定案）** | `chat_stream` 采用**一次性全迁**：先新建 `stream_orchestrator.py` 并补充 SSE 逐字节对比单测（断言与现 `openai.py:176-272` 行为一致），验证通过后再删除 `openai.py` 旧逻辑。分步迁会留"双份编排并存"中间态，易再次腐化。 |

5. **依赖方向守护测试（审核新增，防回归护栏）**：

   分层的根本问题是"改完容易、腐化更快"，单靠手工查环不可持续。建议新增一个 pytest 用例 `tests/test_architecture_boundaries.py`，静态扫描 `app/` 下所有模块的 import 语句，断言分层规则，任何越层改动一跑测试即红：

   | 断言规则 | 实现要点 |
   |---------|---------|
   | `api/` 不得 import `tools/`、`safety/`、`db/`（业务数据库） | 扫描 `app/api/` 下 `from app.tools`、`from app.safety`、`from app.db`（允许 `db.models` 只读模型例外需显式声明）。A7 前 `model_routes.py` 直接 import `app.safety.operation_backup.clear_backup_paths`（API→safety 越层），随 A7 下沉 config_service 后消除，此规则为回归护栏 |
   | `tools/` 不得 import `services/`、`safety/` | 扫描 `app/tools/` 下 `from app.services`、`from app.safety`（A1 修复后 tools→safety 亦消除） |
   | `safety/` 不得 import `services/task/` | 扫描 `app/safety` 下 `from app.services.task`（A2 定案后强制，operation_rollback 越层修复的回归护栏） |
   | 无循环依赖 | `import app.main` 启动检查 + `pytest` 全量 |

   ```python
   # tests/test_architecture_boundaries.py（示意）
   import ast
   from pathlib import Path

   FORBIDDEN = {
       "app/api":    {"app.tools", "app.safety"},
       "app/tools":  {"app.services", "app.safety"},
       "app/safety": {"app.services.task"},
   }

   def test_layer_boundaries():
       app_root = Path(__file__).resolve().parents[1] / "app"
       violations = []
       for src_dir, banned in FORBIDDEN.items():
           for py in (app_root / src_dir).rglob("*.py"):
               tree = ast.parse(py.read_text(encoding="utf-8"), filename=str(py))
               for node in ast.walk(tree):
                   if isinstance(node, ast.ImportFrom) and node.module:
                       for b in banned:
                           if node.module == b or node.module.startswith(b + "."):
                               violations.append(f"{py}: imports {node.module}")
       assert not violations, "\n".join(violations)
   ```

   该测试在三个实施阶段中**逐步收紧**：阶段一建立基线（断言 api 禁 tools，tools 禁 services，两条硬边界），阶段一内追加 safety→task（A2-越层）与 api 禁 safety、tools 禁 safety（A7/A1 消除 model_routes→safety 与 file→safety 越层后变绿），阶段二追加 tools/services+safety（随 A1 完成），阶段三全量启用并固化全部规则。
