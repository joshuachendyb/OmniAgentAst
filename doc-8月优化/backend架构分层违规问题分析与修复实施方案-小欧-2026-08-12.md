## 2. 系统架构设计与目录对应关系

### 2.1 理想分层架构

backend/app 的理想分层应为单向依赖结构，上层可调用下层，下层不反向依赖上层：

```
┌─────────────────────────────────────────────────────────────┐
│  API 层（HTTP 适配）                                         │
│  app/api/v1/                                                │
│      │                                                      │
│      ▼                                                      │
│  编排层（ReAct 循环、Agent 状态管理）                         │
│  app/services/agent/                                        │
│      │                                                      │
│      ▼                                                      │
│  业务服务层（聊天、任务、LLM、模型、提示词等）                 │
│  app/services/chat/  app/services/task/  app/services/llm/   │
│  app/services/model/  app/services/prompts/                  │
│  app/services/lifecycle/  app/services/monitoring/           │
│      │                                                      │
│      ▼                                                      │
│  安全层（工具执行前检查、操作记录、回滚）                     │
│  app/services/safety/                                        │
│      │                                                      │
│      ▼                                                      │
```

### 2.4 当前实际依赖 vs 理想依赖

**理想依赖方向**（只允许向下依赖）：

```
api/v1/  →  services/agent/  →  services/safety/  →  tools/  →  utils/
              ↓
           services/chat/, services/task/, services/llm/ 等
              ↓
           services/safety/  →  tools/  →  utils/
```

**当前实际依赖**（存在双向/越层）：

```
api/v1/health.py ────────────┐
                             ▼
                          tools/registry.py ◄──────────┐
                             ▲                         │
                             │                         │
services/agent/ ─────────────┘                         │
                                                       │
services/safety/path_safe_check.py ────────────────────┘
                             ▲
                             │
services/safety/tool_safety_checker.py
                             ▲
services/agent/action_handler.py
                             │
                           tools/file/*.py  ────────────► services/safety/
                                                       ───► services/task/
```

**主要违规点**：
1. `tools/file/*.py` 直接导入 `services/safety` 和 `services/task`（工具层反向依赖服务层）；
2. `services/safety/path_safe_check.py` 直接导入 `tools/registry`（服务层越层依赖工具层细节）；
3. `api/v1/health.py` 直接导入 `tools/tool_registry`（API 层越层依赖工具层）。

### 2.5 修复后的目标依赖关系

```
api/v1/  →  services/tool/（新增门面）  →  services/agent/ + services/safety/
                                            ↓
                                         tools/
                                            ↓
                                         utils/
```

关键点：
- API 不再直接接触 `tools/`；
- `tools/file/*.py` 不再直接导入 `services/*`，改由 `services/agent/tool_executor.py` 注入安全 hook；
- `path_safe_check.py` 迁到 `tools/security/`，与 `tool_registry` 同层交互；
- `services/safety/tool_safety_checker.py` 调用 `tools/security/path_safe_check.py` 的结果；
- 所有层对 `utils/`、`db/`、`logger/` 的依赖保持单向。

## 4. 问题逐一分析、修复方案与三堂会审

### A1. P0 — tools 层与 services 层双向依赖

#### 3.1.1 当前问题

**依赖方向一：tools → services**

大量文件操作工具直接导入 services 层：

```python
# app/tools/file/copy_file.py:36
from app.services.safety import record_operation, execute_with_safety

# app/tools/file/delete_file.py:32
from app.services.safety import record_operation, execute_with_safety

# app/tools/file/write_text_file.py 等同理
```

以及任务上下文：

```python
# app/tools/file/copy_file.py:37
from app.services.task.task_context import get_current_task_id
```

**依赖方向二：services → tools**

安全层路径校验依赖工具注册表：

```python
# app/services/safety/path_safe_check.py:55-63
from app.tools.registry import tool_registry
from app.tools.tool_types import ToolCategory
from app.tools.tool_constants import (
    FILE_OPERATION_TOOLS, SKIP_DIRS, WINDOWS_SYSTEM_DIRS, ...
)
from app.tools.tools_alias_mapper import get_aliases_for_tool

# app/services/safety/tool_safety_checker.py:64
from app.tools.registry import tool_registry
```

#### 3.1.2 病根

- 工具执行需要"被记录"和"被保护"，所以工具直接调用 `record_operation`/`execute_with_safety`；
- 安全校验需要知道"这是哪个工具""参数是什么"，所以 safety 层直接读取 `tool_registry`；
- 双方都把对方当成基础设施，导致层间边界破裂。

#### 3.1.3 修复方案（推荐：依赖注入 + 安全 hook 抽象）

**目标**：让工具层不再直接依赖 services 层，让安全校验在 tools 层内部闭环。

**步骤**：

1. **新建安全 hook 接口** `app/tools/tool_security_hooks.py`（或 `app/tools/toolhelper/security_hooks.py`）：

```python
from typing import Protocol, Callable, Any

class ToolSecurityHooks(Protocol):
    """工具执行前后的安全/记录 hook 接口"""
    async def before_execute(self, tool_name: str, params: dict, task_id: str | None) -> dict:
        """返回可能被修改后的 params，或抛出异常阻止执行"""
        ...

    async def after_execute(
        self,
        tool_name: str,
        params: dict,
        result: dict,
        task_id: str | None,
        operation_meta: dict | None = None,
    ) -> None:
        """记录操作、触发回滚准备等"""
        ...

# 默认空实现，保证不传入 hooks 时工具仍可独立运行
class NoOpSecurityHooks:
    async def before_execute(self, tool_name: str, params: dict, task_id: str | None) -> dict:
        return params
    async def after_execute(self, **kwargs) -> None:
        pass
```

2. **改造 tool_executor.py**，在调用工具时传入 hooks：

```python
# app/services/agent/tool_executor.py
async def execute_tool_with_hooks(
    tool_name: str,
    params: dict,
    hooks: ToolSecurityHooks | None = None,
    task_id: str | None = None,
) -> dict:
    hooks = hooks or NoOpSecurityHooks()
    params = await hooks.before_execute(tool_name, params, task_id)
    result = await _call_tool_impl(tool_name, params)
    await hooks.after_execute(tool_name, params, result, task_id)
    return result
```

3. **在 `app/services/safety/` 中实现 `DefaultToolSecurityHooks`**：

```python
# app/services/safety/default_hooks.py
from app.tools.toolhelper.security_hooks import ToolSecurityHooks
from app.services.safety.operation_record import record_operation
from app.services.task.task_context import get_current_task_id

class DefaultToolSecurityHooks(ToolSecurityHooks):
    async def before_execute(self, tool_name, params, task_id):
        # 原有 execute_with_safety 中的"执行前记录/校验"逻辑迁移至此
        return params

    async def after_execute(self, tool_name, params, result, task_id, operation_meta=None):
        _tid = task_id or get_current_task_id()
        record_operation(tool_name, params=params, result=result, task_id=_tid, **(operation_meta or {}))
```

4. **移除 tools/file/*.py 中对 `app.services.safety` 和 `app.services.task.task_context` 的直接导入**：
   - 删除 `from app.services.safety import record_operation, execute_with_safety`；
   - 删除 `from app.services.task.task_context import get_current_task_id`；
   - 工具函数签名中不再主动记录，改为通过 executor 传入的 hooks 完成。

5. **把 `path_safe_check.py` 迁回 tools 层** `app/tools/security/path_safe_check.py`：
   - 该文件本质是"工具参数层面的路径安全校验"，属于工具层能力；
   - 保留 `validate_path(file_path, mode, tool_name)` 接口不变；
   - 它依赖 `tool_registry` 获取工具分类和参数，这在本层内是合理的（工具层内部闭环）。

6. **`tool_safety_checker.py` 调用新位置的 `path_safe_check`**：

```python
# app/services/safety/tool_safety_checker.py
from app.tools.security.path_safe_check import validate_path, is_temp_authorized
```

此时依赖方向变为：
- `services/safety/tool_safety_checker.py → tools/security/path_safe_check.py`（services → tools，单向）
- `services/agent/tool_executor.py → services/safety/default_hooks.py`（编排层 → 安全层，单向）
- `tools/file/*.py` 不再依赖 services

#### 3.1.4 备选方案（改动较小但不彻底）

仅把 `path_safe_check.py` 从 `services/safety` 迁到 `tools/security`，保留 tools/file/*.py 对 services.safety 的导入。

**缺点**：只解决 services→tools 方向的越层，未解决 tools→services 方向的双向依赖，架构仍不健康。

#### 3.1.5 三思三省

| 维度 | 分析 |
|------|------|
| **可行性** | 高。Python Protocol + 依赖注入机制成熟；已有 `execute_with_safety` 逻辑可直接迁移到 hook 实现。 |
| **风险** | 中。涉及 file 分类下 10+ 个工具文件、tool_executor、action_handler 等核心链路，需全量回归。 |
| **替代方案** | 备选方案改动小但治标不治本；推荐方案虽改动大，但能根治双向依赖。 |
| **是否引入新抽象** | 是，但 `ToolSecurityHooks` 是必要抽象，符合 OCP（后续新增审计、权限等 hook 无需改工具代码）。 |

#### 3.1.6 三堂会审

| 规范 | 审查 | 结论 |
|------|------|------|
| SRP | 工具只负责执行，安全/记录由 hook 处理 | PASS |
| DRY | `record_operation`/`execute_with_safety` 逻辑集中在 DefaultToolSecurityHooks | PASS |
| KISS-DIRECT | 调用链：`executor → hooks → tool_impl`，单向清晰 | PASS |
| SLAP | hooks 属于工具层协议，DefaultHooks 属于安全层实现，分层明确 | PASS |
| YAGNI | hooks 接口为后续扩展预留，当前即解决双向依赖，非过度设计 | PASS |
| 禁止 backward | 旧导入直接删除，无兼容 shim | PASS |
| 分层架构 | 工具层独立，services 单向依赖 tools | PASS |

### A2. P1 — services/safety 内部循环依赖

#### 3.2.1 当前问题

循环链：

```
operation_backup.py
  → operation_cleanup.cleanup_expired_backups
operation_cleanup.py
  → operation_record.FileSafetyConfig
operation_record.py
  → operation_backup.backup_to_recycle_bin
```

代码证据：

```python
# app/services/safety/operation_backup.py:27
from app.services.safety.operation_cleanup import cleanup_expired_backups

# app/services/safety/operation_cleanup.py:46
from app.services.safety.operation_record import FileSafetyConfig

# app/services/safety/operation_record.py:53
from app.services.safety.operation_backup import backup_to_recycle_bin
```

#### 3.2.2 病根

- `FileSafetyConfig` 作为配置数据类，被多个模块共用，但放在 `operation_record.py`；
- `cleanup_expired_backups` 作为清理逻辑，被 `operation_backup.py` 调用，但放在 `operation_cleanup.py`；
- `backup_to_recycle_bin` 作为备份实现，被 `operation_record.py` 调用，但放在 `operation_backup.py`。

三个模块互相调用，职责边界模糊。

#### 3.2.3 修复方案

**目标**：打破循环，使模块间依赖呈单向树状。

**步骤**：

1. **抽离共享数据模型** `app/services/safety/models.py`：

```python
# app/services/safety/models.py
from dataclasses import dataclass
from datetime import datetime
from typing import Optional

@dataclass
class FileSafetyConfig:
    """文件安全操作配置"""
    enable_backup: bool = True
    backup_dir: Optional[str] = None
    retention_days: int = 7
    max_backup_size_mb: int = 100
```

2. **把 `cleanup_expired_backups` 迁移到 `operation_record.py` 或新建 `operation_maintenance.py`**：
   - 建议新建 `app/services/safety/operation_maintenance.py`，统一负责"过期备份清理""历史记录归档"等维护操作；
   - `operation_backup.py` 改为从 `operation_maintenance.py` 导入 `cleanup_expired_backups`。

3. **调整导入关系**：

```
operation_backup.py
  → operation_maintenance.cleanup_expired_backups
  → models.FileSafetyConfig

operation_cleanup.py
  → models.FileSafetyConfig
  → operation_record.*

operation_record.py
  → operation_backup.backup_to_recycle_bin
  → models.FileSafetyConfig

operation_maintenance.py
  → operation_backup.backup_to_recycle_bin  （可选，用于清理时确认备份存在）
```

新依赖图：

```
              models.py  （底层共享数据）
              /        \
 operation_backup.py   operation_record.py
        |                    |
 operation_maintenance.py  operation_cleanup.py
```

无循环。

#### 3.2.4 三思三省

| 维度 | 分析 |
|------|------|
| **可行性** | 高。仅是模块间移动类和函数，业务逻辑不变。 |
| **风险** | 低。导入路径变化，需全局搜索替换并跑 safety 相关单测。 |
| **替代方案** | 保持现状，靠局部导入避免运行时错误；但结构劣化。 |

#### 3.2.5 三堂会审

| 规范 | 审查 | 结论 |
|------|------|------|
| SRP | backup/record/cleanup/maintenance 各司其职 | PASS |
| DRY | FileSafetyConfig 单一定义 | PASS |
| KISS-DIRECT | 依赖单向，无循环 | PASS |
| SLAP | 数据模型独立，业务模块在同层 | PASS |
| YAGNI | models.py 当前即解决共享问题，非过度 | PASS |
| 禁止 backward | 旧导入路径删除 | PASS |
| 分层架构 | services/safety 内部无循环 | PASS |

### A3. P1 — `tool_retry_engine.py` 目录位置错误

#### 3.3.1 当前问题

文件路径：`app/services/agent/tool_retry_engine.py`

文件自身注释 L47-50 明确说明：

> **归属分层：【工具层】— 虽在编排层目录，但本质是工具的外部重试机制**

当前只有 `app/services/agent/base_agent.py:33` 导入：

```python
from app.services.agent.tool_retry_engine import ToolRetryEngine
```

#### 3.3.2 病根

文件职责与所在目录不匹配。工具重试引擎属于工具层基础设施，不应放在 Agent 编排层。

#### 3.3.3 修复方案

**步骤**：

1. **移动文件**：
   - 源：`app/services/agent/tool_retry_engine.py`
   - 目标：`app/tools/toolhelper/tool_retry_engine.py`

2. **更新导入**：

```python
# app/services/agent/base_agent.py:33 修改前
from app.services.agent.tool_retry_engine import ToolRetryEngine

# 修改后
from app.tools.toolhelper.tool_retry_engine import ToolRetryEngine
```

#### 3.4.2 病根

- API 层（最高层）直接依赖工具注册表（最底层），跳过了 services 层；
- `/tool/execute` 接口直接执行工具实现，**绕过 Agent 编排层和安全检查**，存在严重安全和审计风险：
  - 不经过 `tool_safety_checker` 的路径白名单/黑名单校验；
  - 不经过 `record_operation` 操作记录；
  - 不经过任务上下文追踪；
  - 不经过 StepEmitter 的状态汇报。

#### 3.4.3 修复方案

**目标**：API 层只调用 services 层，不直接接触 tools；`/tool/execute` 必须走安全/审计链路。

**步骤**：

1. **在 services 层新增工具门面** `app/services/tool/tool_facade.py`（新建 `app/services/tool/` 包）：

```python
# app/services/tool/__init__.py
from .tool_facade import list_tools, execute_tool

# app/services/tool/tool_facade.py
from typing import Any
from app.tools.registry import tool_registry
from app.services.safety.tool_safety_checker import check_tool_safety
from app.services.safety.default_hooks import DefaultToolSecurityHooks
from app.services.agent.tool_executor import execute_tool_with_hooks
from app.services.task.task_context import _current_task_id

async def list_tools() -> dict:
    """供 API 调用的工具列表"""
    tools = tool_registry.to_openai_tools()
    result = []
    for t in tools:
        func = t.get('function', {})
        name = func.get('name', '')
        desc = func.get('description', '')
        params = func.get('parameters', {})
        required = params.get('required', [])
        props = list(params.get('properties', {}).keys())
        required_set = set(required)
        result.append({
            "name": name,
            "description": desc[:100] if desc else "",
            "required_params": required,
            "optional_params": [p for p in props if p not in required_set],
            "inputSchema": params,
        })
    return {"total": len(result), "tools": result}

async def execute_tool(tool_name: str, params: dict) -> dict:
    """供 API 调用的安全工具执行入口"""
    # 1. 安全检查
    safety = await check_tool_safety(tool_name, params)
    if safety.blocked:
        return {"success": False, "error": f"安全拦截: {safety.message}"}

    # 2. 设置任务上下文
    task_id = str(uuid.uuid4())
    _current_task_id.set(task_id)

    # 3. 通过 Agent 编排层的 executor 执行，带上安全 hooks
    hooks = DefaultToolSecurityHooks()
    result = await execute_tool_with_hooks(tool_name, params, hooks=hooks, task_id=task_id)

    return {"success": True, "result": result if isinstance(result, dict) else {"output": str(result)}}
```

2. **修改 `api/v1/health.py`**：

```python
# 删除
from app.tools import tool_registry

# 改为
from app.services.tool import list_tools, execute_tool

@app.get("/tool/list")
async def list_tools_endpoint():
    return await list_tools()

@app.post("/tool/execute")
async def execute_tool_endpoint(request: ToolExecuteRequest):
    return await execute_tool(request.tool_name, request.params)
```

   - 增加显式 `X-Test-Mode` 头校验；
   - 或在生产环境禁用该接口（通过配置开关）。

| **风险** | 中。`/tool/execute` 直接执行工具，改动后必须确保安全检查链路完整，否则可能引入新的安全问题。 |
