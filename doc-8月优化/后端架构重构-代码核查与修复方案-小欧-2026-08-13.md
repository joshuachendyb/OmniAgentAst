### 4.1 [CRITICAL] storage.py:241 `local_time` 未定义即引用（NameError）

**现象**：`allocate_and_insert_message` 中 `local_time` 仅在 `if is_new:`（L234）内赋值，但 L242 `UPDATE chat_sessions SET ... updated_at=? WHERE id=?` 无条件引用 `local_time`。

**上下关联逻辑**：该函数唯一活跃调用方为 `agent_runner.py:176-178`（同步 runner，每任务首次进入且 `ai_message_id is None` 时调用）。`_allocator.allocate`（storage.py:91-128）在"同一 session 已有对应用户消息的 assistant 回复落库"时，L119-120 返回 `(expected, False)`。此时 `is_new=False` → `local_time` 永不绑定 → L242 抛 `NameError` → `allocate_and_insert_message` 崩溃，agent_runner 任务直接失败。**触发条件**：同一 session 第 2 次及以上任务（SSE 流式路径 `save_execution_steps` 已在 8/12 重写为直调 allocate+insert_assistant_message，不受影响）。

**确认**：真实（2026-08-13 二次复核逐行核对 storage.py:229-244、91-128、agent_runner.py:176-178）。

**修复方法（三堂会审通过）**：把 `local_time` 提到 `if is_new:` 之前，或把 UPDATE 移入 `if is_new:` 内（因 `update_session_message_count` 已在同一函数 L215 完成计数更新）。推荐：
```python
def allocate_and_insert_message(conn, session_id) -> int:
    ensure_session_exists(session_id, conn)
    ai_message_id, is_new = _allocator.allocate(session_id, conn)
    local_time = get_local_iso_timestamp()   # ← 提到此处, 消除未定义
    if is_new:
        conn.execute(
            "INSERT INTO chat_messages(id, session_id, role, content, timestamp) "
            "VALUES (?, ?, 'assistant', ?, ?)",
            (ai_message_id, session_id, "", local_time),
        )
    conn.execute(
        "UPDATE chat_sessions SET message_count=message_count+1, updated_at=? WHERE id=?",
        (local_time, session_id),
    )
    return ai_message_id
```
合规：单一赋值点；合理：复用同一时间戳；关联：与 L215 `update_session_message_count` 不冲突（后者更新 message_count，此处更新 updated_at）。

### 4.3 [中—降级] tool_retry_engine.py:474-480 clamp 门控对数组形式 type 仍有残余窗口

**现象**：clamp 门控 `if _t in ("integer","number"):` 用 `spec.get("type")` 判定；L466-469 注释显示 8/12 已将范围提取改走 `_extract_numeric_bounds`（L361-375），且 L363 注释实证本项目的 Pydantic v2 Optional[int] 生成 `{"anyOf":[{...min/max...},{"type":"null"}], "type":"integer"}`——顶层 `type="integer"`，门控**命中**，anyOf 里取到 min/max，clamp 生效。

**二次复核修正（2026-08-13）**：原报告"clamp 整体失效"表述过重。当前实际状态：
- ✅ 8/12 已修复主路径：`_extract_numeric_bounds` 兼容 anyOf 嵌套，日志实证的 limit=1200 漏过问题已解决。
- ⚠️ **残余窗口**：若任一 Optional 字段的 schema 顶层 `type` 为数组形式（如 `["integer","null"]`），`_t in ("integer","number")` 不命中（list 与 str 比较为 False），整段 clamp 仍被跳过。当前 schema 形态未穷举验证。
- ⚠️ #31 仍真实：L372-374 `any_of[0]` 顺序依赖，Pydantic 把 null 排前时取不到 min/max。

**上下关联逻辑**：与 #31 叠加——即使门控修好，anyOf 成员顺序不定仍可能取不到边界。JSON-Schema `anyOf` 成员顺序不保证。

**确认**：部分修复（主体已修，残余窗口待闭环）。

**修复方法（闭环）**：门控改为"能取到数值边界即 clamp"，并对 anyOf 全量扫描：
```python
for k, v in params.items():
    spec = props.get(k)
    if not spec:
        continue
    minimum, maximum = self._extract_numeric_bounds(spec)
    if minimum is None and maximum is None:
        continue
    if isinstance(v, (int, float)):
        if minimum is not None and v < minimum:
            params[k] = minimum
        elif maximum is not None and v > maximum:
            params[k] = maximum
```
```python
# _extract_numeric_bounds anyOf 分支改为全量扫描(顺序无关):
any_of = spec.get("anyOf")
if isinstance(any_of, list):
    for a in any_of:
        if isinstance(a, dict) and ("minimum" in a or "maximum" in a):
            return a.get("minimum"), a.get("maximum")
return None, None
```
合规：DRY，复用 `_extract_numeric_bounds`；合理：以"边界存在"为准，不依赖顶层 type 形态。

### 4.4 [HIGH] move_file.py:77 缺自嵌套防护

**现象**：`_move_file_impl` 仅 `src.resolve() == dst.resolve()`（精确相等），无"目标在源子树内"判定。`copy_file.py` 有对应防护（防套娃递归），move 漏了。

**上下关联逻辑**：`move(src_dir, dst_inside_src, overwrite=True)` 通过校验后到 `shutil.move(str(src), str(dst))`；对已有目标目录会 `copytree(src, dst/src_basename)` 再 `rmtree(src)` → 复制进自身子树，深递归/WinError206/部分数据丢失。copy 有防护而 move 无，违反 YAGNI/一致性与"增强不退化"。

**确认**：真实（已核对 `_move_file_impl` L69-99，仅 L77 精确相等）。

**修复方法**：在 `move()` 与 `_move_file_impl` 入口各加子树包含判定（复用 `Path.is_relative_to`，Python 3.9+）：
```python
if src.resolve() == dst.resolve() or (src.is_dir() and dst.resolve() != src.resolve()
        and src.resolve() in dst.resolve().parents):
    return {"success": False, "error_detail": f"目标路径位于源目录内部,禁止移动造成递归: {source_path}", ...}
```
合理：与 copy_file 口径一致；关联：不影响 overwrite 同目录平级移动（平级 `dst.resolve()` 不在 `src.resolve().parents`）。

### 4.5 [HIGH] 长路径修复未闭环：文件工具未调用 to_win_long_path

**现象**：`to_win_long_path`（`app/utils/path_utils.py:19`）仅在 `app/safety/*`（备份/回滚/清理/记录）使用；`app/tools/file/*`（copy/move/delete/compress/write/edit_text_file）全部用裸 `str(path)` 调 shutil/zipfile/open/os.walk/unlink/rmdir。

### 4.9 [中] storage.py:264-270 嵌套列表截断失效

**现象**：`_truncate_tool_result` 的 dict 分支 L262-263 与 list 分支 L270 递归调用丢弃返回值。

**二次复核修正（2026-08-13）**：精确边界——dict 分支内对嵌套 dict 的递归是**引用传递 + 原地修改**，实际生效；仅当"list 内嵌超长 list"（如 `{"rows": [[…1001 项…]]}` 外层 rows 长度 ≤1000 未触发 L259，进入 L264 list 分支后内层 row list 超长，L267 `return tr[:MAX]` 的新列表被父级丢弃）或"dict 内嵌 list 的 list"时截断失效。

**上下关联逻辑**：函数注释承诺覆盖嵌套大列表防 SQLite TEXT 超限，但上述嵌套场景截断失效 → SQLite 防溢出保护在部分嵌套结构下被绕开。

**确认**：真实（范围窄于原报告，2026-08-13 二次复核确认）。

**修复方法**：递归始终回写返回值：
```python
def _truncate_tool_result(tr, tag=""):
    if isinstance(tr, dict):
```

**确认**：真实（2026-08-13 复核时新发现，逐行核对 react_cycle.py:588-621）。

**修复方法**：统一计数点——删除 L592 的累加，异常来源只 `set_status(RETRYING)` + `continue`，计数统一由 L615 执行；L593-596 的 `>3` 判断改为依赖 L615 累计结果（若需提前判死，放在 L615 累计后）。或改用两个独立计数器（`_llm_retry_count` / `_cycle_retry_count`）。推荐前者（最小改动，语义统一）：
```python
except Exception as _step_err:

        yield agent._step_emitter.emit(MetaStep(type="retrying", ...))
```

合理：一次异常只计一次；关联：来源 B（L273）不受影响。
