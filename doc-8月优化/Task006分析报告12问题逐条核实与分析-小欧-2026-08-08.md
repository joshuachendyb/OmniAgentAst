### P1: SQLite 多语句执行限制

| 核实项 | 结论 |
|--------|------|
| 日志原文 | ✅ 真实存在（23:29:00、23:29:01、23:51:43、23:52:05、00:01:55 全部逐字匹配） |
| 真实出现次数 | 约 8 次（08-07 23:29/23:51/23:52、08-08 00:01 等，均为后端启动后的真实运行；另有 09:00/09:15 2 次无 session 疑似测试） |
| 代码定位 | ✅ `execute_sql.py` L243/L254：sqlite 路径 `conn.execute(text(sql))` / `cursor.execute(sql)` 直接执行 |
| 代码行为 | ✅ 属实。SQLite 的 `execute()` 仅支持单条语句，LLM 生成 `CREATE TABLE...; INSERT INTO...;` 多语句时必然抛 `sqlite3.ProgrammingError: You can only execute one statement at a time.` |
| 已有防护 | dry_run 校验（L170-231）会用 `conn.execute(sql)` 预检，多语句在 dry_run 阶段即报语法错误（syntax_valid=False） |
| **判定** | ✅ **真实系统问题（低危）** |

**合规修正方法**：
1. 在执行前对 SQL 做多语句预检（`sqlite3.complete_statement()` 或统计未引号包裹的 `;` 数量），检测到多语句时**提前返回错误并附 hint**："SQLite 仅支持单条语句，请拆分后逐条执行"，避免真实执行时报底层驱动错误、形成低效重试循环。
2. hint 复用 `sql_error_hint` 机制，将"多语句"作为一类已知错误给出针对性提示。
3. 不建议自动拆分多语句执行（YAGNI）：SQLite 多语句自动拆分涉及字符串分号处理、失败原子性等复杂度，且真实场景 LLM 应生成单条语句，预检+提示即可闭环。

**【2026-08-09 v1.1 落地记录 — 小欧】**
- **落地方式与报告修正**：经实验验证，**不做字符串分号预检**（`split(';')` 计数会误伤 `CREATE TRIGGER ... BEGIN ... UPDATE ...; END` 这类含分号的合法单条，实验1 已证明 sqlite3 可正常执行）。改用**依托 sqlite3 权威解析器**：多语句执行时 `sqlite3` 本身抛 `ProgrammingError: You can only execute one statement at a time.`，只需让错误提示精准即可。
- **改动 1（`file_path_checker.py` `sql_error_hint`）**：新增 `"one statement at a time"` 分支 → 返回 "SQLite仅支持单条语句执行，请将SQL拆分为单条语句后逐条执行"。真实执行与 dry_run 两条路径共用此函数，DRY。
- **改动 2（`execute_sql.py` dry_run 分支）**：原先 dry_run 校验失败只返回笼统 "SQL语法校验失败 / 请检查SQL语法"，异常被吞掉。现保留 `dry_run_error`，失败时 detail 带异常原文、hint 走 `sql_error_hint` 精准分支。
- **验证通过**：真实执行多语句 → hint 精准；dry_run 多语句 → detail=`SQL语法校验失败: You can only execute one statement at a time.` + hint 精准；`CREATE TRIGGER` 仍 success（不误伤）；正常单条 success；`tests/tools/param_combination/test_execute_sql.py` 47 用例全过。
