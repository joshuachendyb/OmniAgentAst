## 四、一问：C12×6 详解

### 4.1 观测点与现象

- 观测点：`shell_engine.py:484` `_close()` 关闭 stderr 句柄前 `safe_read_file(self._stderr_path).strip()` 有内容则 WARNING tail[:200]
- C12 全部出现在任务 `COMPLETED/final 成功` 后的 **Cleanup 关闭实例时刻**（非执行中途）
- 残留内容特征：`out-lineoutput: ...ps1:1` + `Line | 1 |` + `The object of type "...FormatEntryData" is not valid or not in the correct sequence`（3654 字节）

### 4.2 根因（实验逐字节复现）

ps_cmd 管道结构（shell_engine.py:394-399）：

```
[Console]::OutputEncoding=UTF8; $OutputEncoding=UTF8; $global:rc=0; & { cmd; if (-not $?) { $global:rc=... } } 2>&1 |
ForEach-Object { if ($_ -is [ErrorRecord]) { $_ | Out-File -FilePath "...err" -Append } else { $_ | Out-File -FilePath "...out" -Append } };
$global:rc | Out-File "...code";
(Get-Location).Path | Out-File "...cwd"
```

触发链：

1. 命令含 **Format-Table / Format-List 且输出多对象**时（如 L17537 `Get-CimInstance -ClassName Win32_Processor | Format-Table`）
2. PS 格式引擎生成 `FormatEntryData` 等内部格式对象
3. `2>&1` 将 stdout 流与错误流合并后，格式对象经管道到达 `Out-File`
4. **管道破坏 PS 格式引擎序列** → `Out-File` 报 `FormatEntryData is not valid or not in the correct sequence`
5. 该错误发生在 ForEach-Object 块内、**不受 `& {} 2>&1` 保护** → 直接渲染到**进程 stderr**
6. 实例存活期间 stderr 累积（`ps_*.err` 文件），关闭时被 C12 观测点读到

**关键补充**：`execute_shell_command.py:1041` 已有 `Format-Table` 保护（追加 `| Out-String -Width 4096`），但**未覆盖 `Format-List`**；且该保护只作用于 execute_shell_command 层，ps_cmd 内嵌命令仍可能触发。

### 4.3 实验证据

## 五、二问：C10×2 详解

- C10 观测点：`execute_shell_command.py:1083` CMD communicate 超时 → `_kill_and_read_output`（L699-724）

4. 07:18:39/07:19:39 两条 SSE 60s 超时即 C10 的 communicate 超时点，**非独立故障**

### 5.3 C10 结论

非卡死、非池问题。属**路由判定 + CMD 超时链**：Windows 11 上 systeminfo 经 `.bat` 分支执行异常缓慢，触发有界兜底，异常分支正确完成清理。

### 8.0 R0（最高优先级）—— CMD 分支 poll loop 大输出死锁根治

#### 8.0.1 隐患背景（老陈质疑触发）

老陈提出关键质疑："systeminfo 这种简单命令在 CMD 分支都要 60/120s，复杂命令不得卡死？CMD 分支是不是完全不可用？" 经深入实验验证，**质疑完全成立，且系统信息慢只是表象，真正隐患远超 systeminfo**。

#### 8.0.2 根因（实验铁证）

`execute_shell_command.py:1076-1080` 的 poll loop（防 `start /b` 子进程持管道，2026-07-27 引入）在等待期间**从不读取 stdout/stderr 管道**：

```python
_deadline = _time_mod.time() + timeout
_poll_sleep = 0.1
while _time_mod.time() < _deadline and proc.poll() is None:
    _time_mod.sleep(min(_poll_sleep, max(0, _deadline - _time_mod.time())))
    _poll_sleep = min(_poll_sleep * 2, 1.0)   # ← 只睡不读，管道越积越满
```

**死锁链**：子进程输出写满管道缓冲（Windows 默认 64KB）→ 子进程 write() 阻塞 → cmd.exe 等待子进程退出 → poll 永远 `None` → 死锁直至 deadline 杀树。杀树后仅能读到 4096 字节残存，**全部输出丢失**。

**实验证据（同机实测）**：

| 场景 | 方式 | 结果 |
|---|---|---|
| `type 200KB文件` | **poll loop（现实现）** | **15s 超时，残存仅 4096 字节** ❌ |
| `type 200KB文件` | communicate | 0.0s 完成，266890 字节完整 ✅ |
| `type 200KB文件` | **poll loop + 非阻塞读管道（修复方案）** | **0.3s 完成，读满 116736+2154 字节** ✅ |
| systeminfo ×3 | poll loop | 3.5s 完成（3342 字节 < 64KB 缓冲，侥幸未触发） |

**为何 systeminfo 日志超时**：systeminfo 正常输出仅 3342 字节，但其真实执行涉及 Windows 组件查询，在 07:09/07:17 当时系统负载下 CMD 管道输出可能叠加其他字节流（如编码转换/回显）触及缓冲；更重要的是，**同一隐患下任意大输出命令（type/dir/findstr/日志查询/pip list 等）必然触发死锁**，systeminfo 只是碰巧成了日志里被记录的那一个。**这是 CMD 分支的系统性缺陷，不是 systeminfo 特例。**

#### 8.0.3 定稿修改（execute_shell_command.py:1076-1080）

```python
# [卡死场景C10-v2] poll loop + 非阻塞读管道: 防 start /b 子进程持管道 + 防大输出写满缓冲死锁 — 小欧 2026-08-07 (三堂会审定稿)
_deadline = _time_mod.time() + timeout
_poll_sleep = 0.1
if proc.stdout: os.set_blocking(proc.stdout.fileno(), False)   # Windows 管道支持非阻塞
if proc.stderr: os.set_blocking(proc.stderr.fileno(), False)
_stdout_chunks: List[bytes] = []
_stderr_chunks: List[bytes] = []
while _time_mod.time() < _deadline and proc.poll() is None:
    for _s, _ch in ((proc.stdout, _stdout_chunks), (proc.stderr, _stderr_chunks)):
        if _s is None: continue
        try:
            _d = _s.read(65536)
            if _d: _ch.append(_d)
        except (BlockingIOError, OSError):
            pass
    _time_mod.sleep(min(_poll_sleep, max(0, _deadline - _time_mod.time())))
    _poll_sleep = min(_poll_sleep * 2, 1.0)
if proc.stdout: os.set_blocking(proc.stdout.fileno(), True)
if proc.stderr: os.set_blocking(proc.stderr.fileno(), True)
if proc.poll() is None:
    timed_out = True
    logger.warning(f"[卡死C10] CMD命令超时{timeout}s(子进程持管道/死循环) → 杀进程树+读残存 (cmd={cmd_short})")
    stdout_b, stderr_b = _kill_and_read_output(proc)
else:
    # 进程已退出: 读清剩余管道 + communicate兜底 — 小欧 2026-08-07
    try:
        _t = proc.stdout.read() if proc.stdout else b""
        if _t: _stdout_chunks.append(_t)
    except OSError:
        pass
    try:
        _t = proc.stderr.read() if proc.stderr else b""
        if _t: _stderr_chunks.append(_t)
    except OSError:
        pass
    stdout_b = b"".join(_stdout_chunks)
    stderr_b = b"".join(_stderr_chunks)
    timed_out = False
```

**要点**：
1. 保留 poll loop 结构（防 `start /b` 持管道挂满 timeout 的初衷不丢）
2. 循环内**非阻塞读管道**，缓冲写满即被消费，死锁链从根上断开
3. 进程退出后读清剩余字节再拼接，不丢数据
4. `os.set_blocking` 在 Windows 管道上已验证可用（`python nt set_blocking supported: True`）

### 8.9 G2 普遍性根治方案（C12 管道层根治，替代 R1 枚举式保护）—— 会审定稿待确认

**提出时间**: 2026-08-07 13:19:21
**提出背景**: 老陈批评"解决问题不能只解决单个问题，shell 是复杂场景，每个方法必须有普遍意义，不能头疼医头"。经三轮实验证实 R1 存在**真实盲区**（别名 fl/ft/fw 触发 C12），并最终定位 C12 的**管道层根因**，设计出普遍性根治方案 G2。

#### 8.9.1 R1 盲区实测（三轮实验铁证）

老陈问"R1 是否有普遍意义"触发深入调查。**完整真实链路（execute_shell_command → R1保护 → 引擎）** 实测：

| 命令 | R1 保护是否命中 | 进程级 stderr 残留 |
|---|---|---|
| `Format-List *`（完整名） | ✅ 命中 | **无** ✅ |
| `Format-Table`（完整名） | ✅ 命中 | **无** ✅ |
| `Format-Wide`（完整名） | ✅ 命中 | **无** ✅ |
| `fl *`（别名） | ❌ **不命中** | **有（3654字节）** ❌ |
| `ft Name,Status`（别名） | ❌ **不命中** | **有** ❌ |
| `fw Name`（别名） | ❌ **不命中** | **有** ❌ |

**结论**：R1 对**完整命令名**有效（普遍），但对**别名 fl/ft/fw** 无效（盲区）。`Format-*` 的别名与变体枚举不完（Format-Custom、`ft -AutoSize`、大小写、换行分号连接等），**枚举式保护无法根治，是"头疼医头"**。

> 注意：早期实验曾"误判 R1 无效"——因直接调 `engine.exec()` 绕过了 execute_shell_command 的 R1 保护层，传入未保护命令。用真实 `shell()` 链路验证后确认 R1 对完整名有效、对别名无效。

#### 8.9.2 管道层根因（隔离复现，通用真相）

在**隔离环境完整复刻引擎 ps_cmd 结构**（`pwsh -Command -` + dot-source 喂入 + 进程 stderr→文件）逐项验证：

| 场景 | 进程级 stderr 残留 |
|---|---|---|
| 无保护 `Format-List *`（引擎原样单对象） | **3654 字节**（out-lineoutput: FormatEntryData is not valid）|
| 无保护 `Get-Service \| Format-List *`（引擎原样多对象） | **243389 字节** |
| `Format-List * \| Out-String -Width 4096`（R1方案） | **0 字节** ✅ |
| 无保护 `fl *`（别名，引擎原样） | **3654 字节** |
| `fl * \| Out-String -Width 4096` | **0 字节** ✅ |
| 无保护 `Format-Wide *` | **3654 字节**（同类）|

**根因定性（精确定位，2026-08-07 13:31:55 复核）**：`out-lineoutput: FormatEntryData is not valid` 的根因**不是某个命令名**，而是 **ps_cmd 管道结构 + ForEach 内直接落盘**：

```powershell
& { 命令 } 2>&1 | ForEach-Object { 错误→err文件 否则→out文件 }
```

**任何 Format 类输出**（Format-List/Wide/Custom/别名 ft/fl/fw...）经 `2>&1` 进入 ForEach-Object 后，成功分支 `$_ | Out-File` **直接落盘时**——Out-File 尝试把 FormatEntryData（格式对象）渲染成文本写文件，触发 `out-lineoutput` 错误 → 写进进程 stderr 文件 → `_close()` 检测到残留 → 报 C12。引擎原样结构实测（含 `if (-not $?)` + `-Width 4096 -Append` 完整后缀）：单对象残留 3654、多对象残留 243389，与日志逐字节一致。

> 注：早期隔离实验曾出现"老结构多对象残留=无"的假象——因构造 ps1 时遗漏了引擎完整的 `-Width 4096 -Append` 及 `if (-not $?)` 后缀，管道渲染路径不同。以**引擎原样 ps_cmd** 为准（见上实测）。

**只要命令末尾有 `| Out-String -Width 4096`（无论完整名还是别名），残留=0**——验证了根因在管道结构而非命令名。

#### 8.9.3 A/B 两个方向方案（数据对比定稿）

**核心思路**：不再枚举命令名，而是**从 ps_cmd 管道结构层根治**。方向 A 整体 `| Out-String` 文本化（格式对象不进入 ForEach）；**B6 定稿**保留 `2>&1 | ForEach-Object` 但**成功对象不落盘**——原样下传由管道末端统一 `| Out-String` 文本化，杜绝"Out-File 直接渲染 FormatEntryData"这条 C12 触发路径。

**改造前结构（shell_engine.py:396-401，枚举式依赖命令名，别名/变体漏网 → C12）**：

```python

    f'...; & {{ {command}; ... }} 2>&1 | '
```

### 8.10.4 B6 回归测试挖出的四缺陷（B6.1/B6.2 根治记录）

> 2026-08-07 小欧。B6 实施后，按 8.9.5 回归计划新建 31 用例回归测试，初跑 **28 过 3 败**，3 败中 2 个为 B6 结构性缺陷（另 1 个为测试 fixture 签名错误已修），再加探测共挖出 **4 个 B6 真实缺陷**：

| # | 缺陷 | 复现命令 | B6 现状 | 根因 | B6.1/B6.2 修复 |
|---|---|---|---|---|---|
| BUG#1 | `;` 复合命令前段错误 rc 漏报 | `Get-Service NOSUCHSVC; Get-Service w32time \| fl *` | rc=0（错误进 err 但业务层判 success） | `if (-not $?)` 中 `$?` 只反映块内**最后一条**命令 | rc 判定改 errs 分类：errs 含非 NativeCommandError 错误 → rc=1 |
| BUG#2 | PS5 native 写 stderr 误报失败 | `cmd /c "echo x 1>&2"`（PS5） | rc=1 | PS5 中 native 写 stderr 使 `$?`=False（PS7 不敏感，双引擎不一致） | NativeCommandError（native stderr）不计错 |
| BUG#3 | LASTEXITCODE 跨命令残留污染 | 先 `cmd /c "exit 3"` 再 `Get-Item Nonexistent` | rc=3（应 1） | `$LASTEXITCODE` 跨 exec 残留，cmdlet 错误时误读上次 native 退出码 | 前置 `$global:LASTEXITCODE = 0` 清残留 |
| BUG#4 | throw 终止性错误假超时 | `Write-Output before; throw "boom"` | rc=-1，触发 C8/C14 30s 超时+杀进程+引擎重建 | 终止性错误中断 ps_cmd，rc/cwd 文件不写 | try/catch 移入 `& {}` 块内兜底：catch 记录文本到 errs + rc=1，管道不中断 → throw 前 stdout 完整落盘 |

**B6.1 → B6.2 演进**：B6.1 初版 catch 在块外，探测发现 throw 场景 throw 前的 stdout（`before`）在管道中丢失；将 try/catch 移入 `& {}` 块内（B6.2），catch 后管道继续执行 → out 文件完整写入，实测 `Write-Output before; throw` 时 out 保留 `before`。其余语义与 B6.1 相同。
