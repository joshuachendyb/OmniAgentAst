## 一、核查背景原因与处理方法原则

### 1.1 背景与原因（为什么会有丢失 commit）

- 2026-07-20 至 07-31 期间，代码/git 仓库发生丢失事故：**263 条 commit 的 tree 全部丢失**，仅 commit 元消息存活
- 8/3 已通过 final_backend_app 差异对比重建批次 0-4，但**重建是否完整落地、是否正确**需逐条核实
- 因此需要对丢失期间的每一条 commit 逐一核查：其声称的功能是否已在当前 live 代码中实现

### 1.2 权威依据（处理的基本原则）

| 原则 | 说明 |
|------|------|
| **权威=commit 元消息** | 唯一权威依据是 `repair-code\docs\repair_commits-20260803.txt` 中 7/21-7/31 的 commit 信息（共 293 条） |
| **排除 final_backend_app** | `final_backend_app` 在 7/31 本身也没做完，不可作对照标准，一律不查 |
| **按日倒序** | 每天一个章节，从 7/31 开始逐日倒序核查到 7/21 |
| **逐条不遗漏** | 当日所有 commit 每条都要给出结论，禁止凭印象跳过 |

### 1.3 核查方法（基于上述原则的具体做法）

1. 按日提取该日全部 commit 清单（解析脚本 extract_day.py）
2. 逐 commit 读取消息 → 提取"功能符号"（函数名/常量/参数/行为变化）
3. 到 live 主仓代码验证：
   - **存在性**: 声称的函数/常量/文件是否存在
   - **正确性**: 代码逻辑行为是否符合 commit 意图（**必须读代码逻辑，禁止仅凭注释/编辑历史判断**）
4. 三遍复核纪律：先初步核查 → 再对照代码反证 → 最后交叉核对 commit 编号与分类，确保无错误、无遗漏

### 1.4 结论分类定义

| 分类 | 判定标准 |
|------|---------|
| **已实现** | 代码存在，且逻辑行为符合 commit 意图 |
| **未实现/未达标** | 代码缺失，或实现行为与 commit 声称不符 |
| **部分实现** | 同一 commit 含多个子问题，部分子项已实现、部分未实现 |
| **低风险跳过** | import 清理/注释/报告/changelog 等非功能逻辑类，不改变行为 |
