## 〇、核心设计原则

> **北京老陈 2026-08-04 梳理确认**，本文档一切设计围绕此原则展开。

### 〇.1 总纲：先分类别，再定处置

- **系统磁盘 / 系统目录**（盘根 `C:\`、`G:\`、系统核心目录）：按原有规则 **无条件拒绝执行**，不参与确认流程，属不可恢复禁区。
- 以下确认策略，全部针对 **非系统目录 / 非系统磁盘**。

### 〇.2 最终决策矩阵

| # | 目标 | 删除方式 | 处置 |
|---|------|----------|------|
| R1 | 系统盘根 / 系统核心目录 | 任意（含递归） | **无条件拒绝**（不可恢复禁区）|
| R2 | 磁盘根（含非系统盘 `D:\`、`E:\`…） | 递归删除 | **拒绝执行** |
| R3 | 项目根内 | 普通删除 | **不需确认**（正常操作，不打扰用户）|
| R4 | 项目根内 | 递归删除 | **需确认**（递归杀伤力大，二次确认）|
| R5 | 项目根外 | 普通删除 | **需确认**（用户确认后可执行）|
| R6 | 项目根外 | 递归删除 | **拒绝执行** |

**规则速记：**

- **拒绝**：系统盘/系统目录任意删除、磁盘根递归删除、项目根外递归删除
- **需确认**：项目根内递归、项目根外普通
- **不需确认**：项目根内普通

### 〇.3 递归删除一律视为危险命令

- **判定维度：目录 + 磁盘 全覆盖。** 无论目标在哪个**磁盘**（`C:\`、`G:\`、`D:\`…）、哪个**目录**（项目内/项目外/任何层级/深层子目录），只要 `recursive=True` 递归删除，一律视为危险命令。
- **处置分档**：
  - 系统盘根/系统核心目录递归 → **无条件拒绝**（R1）
  - 磁盘根（含非系统盘）递归 → **拒绝执行**（R2）
  - 项目根外递归 → **拒绝执行**（R6）
  - 项目根内递归 → **必须用户确认**（R4）
- 递归删除会整棵子树级联删除，误删影响范围广，级别稳定危险，不因"是否在项目内"而降低。
- **注意**：危险命令判定**不限于磁盘根**——磁盘根、项目根、项目内任意子目录、项目外任意目录，凡递归删除一律危险，不因目录层级深浅而豁免。

### 〇.4 补充硬约束

> 系统盘根（`C:\`、`G:\`）与系统核心目录为**不可恢复禁区**，任何情况下**无条件拒绝执行**（R1），不因用户确认而放行。R3-R6 均为非系统目标。

## 一、需求背景

### 1.1 问题来源

2026-08-02 曾发生 E2E 测试 `test_dl4_delete_root_protection` 真删 G 盘根目录事故。为应急，当时在 `delete_file.py` 内部新增了 `_guard_forbidden_delete` 最后防线（无条件硬阻断删除盘根/项目根/系统保护目录）。

**根因复盘（关键教训）：**

- 前期安全加固资源几乎全部投向 `shell`（`SHELL_DANGEROUS_PATTERNS` 高危命令分级表，历经多轮迭代），而 **`delete` 工具长期处于安全盲区**——只有一刀切 `needs_confirmation=True`，无按路径/递归分级的规则。
- 安全机制分布**严重不均**：高风险面（shell）反复加固，同等级破坏性的 delete（可删代码库、可递归删目录）却被忽视，最终导致 G 盘根目录被真删、代码库遭破坏。
- 应急补丁（`_guard_forbidden_delete`）硬编码进 delete 工具内部，违反 SRP 分层（工具层负责执行，安全策略应归 Safety 层）。

### 1.2 需求诉求（北京老陈 2026-08-04 梳理）

删除操作的"确认策略"以 **项目根目录** 为核心安全边界，历经多轮梳理，最终收敛为：

| 场景 | 处置 |
|------|------|
| 项目根目录**之内**的普通删除 | 不需要确认 |
| 项目根目录**之内**的递归删除 | 需要用户确认 |
| 项目根目录**之外**的删除（普通） | 需要用户确认 |
| 项目根目录**之外**的递归删除 | **拒绝执行**（危险）|
| 磁盘根递归删除 | **拒绝执行**（危险）|
| 系统盘/系统目录 | **无条件拒绝** |

> 注：完整、精确定义的处置规则见「〇、核心设计原则」最终决策矩阵。

### 1.3 设计原则

1. **职责归属正确**：安全策略归 Safety 层统一判定，**不硬编码进 delete 工具内部**。
2. **确认 ≠ 拒绝**：项目根之外的删除可以执行（user 确认），并非绝对禁止。
3. **绝对禁区仍需硬拦截**：盘根（C:\、G:\）、系统核心目录为不可恢复禁区，任何情况下直接拒绝（不因确认而放行）。
4. **安全覆盖必须均衡（G 盘事故教训）**：同等级破坏面的工具（shell/delete/execute_sql 等）都应具备同等粒度的专属安全规则，**禁止出现"高危工具安全盲区"**。

## 二、需求细节

### 2.1 判定维度

删除是否"需确认"，由两个维度共同决定：

1. **路径位置**：目标路径是否属于"项目根目录"范围
2. **删除方式**：是否为递归删除（`recursive=True`）

### 2.2 项目根目录定义

采用 `delete_file.py:_get_project_root()` 现有实现（2026-08-02）：
- **主判定**：以代码位置推算（`backend` 的父级），可靠不可篡改
- **兜底**：config 的 `project_root` 仅作辅助（生产 config 可能被改为测试目录，不可信）

### 2.3 规则表（目标行为）

| # | 位置 | recursive | 处置 | 说明 |
|---|------|-----------|------|------|
| R1 | 系统盘根/系统核心目录 | 任意 | **无条件拒绝（blocked）** | 不可恢复禁区，按原规则无条件拒绝，不参与确认 |
| R2 | 磁盘根（含非系统盘 D:\、E:\…） | True | **拒绝（blocked）** | 磁盘根递归删除直接拒绝 |
| R3 | 项目根内 | False | **False（不需确认）** | 普通删除，不打扰用户 |
| R4 | 项目根内 | True | **True（需确认）** | 递归删除杀伤力大，二次确认 |
| R5 | 项目根外 | False | **True（需确认）** | 普通删除，用户确认后可执行 |
| R6 | 项目根外 | True | **拒绝（blocked）** | 项目根外递归删除直接拒绝 |

### 2.4 处置判定顺序（优先级）

1. **R1 系统盘/系统核心目录 → 无条件拒绝**（最优先，任何配置下不可删，不参与确认）
2. **R2 磁盘根递归 / R6 项目根外递归 → 拒绝**（危险命令直接拒绝）
3. **R4 项目根内递归 / R5 项目根外普通 → 需确认**
4. **R3 项目根内普通 → 不需确认**
5. 确认策略受安全开关 `security.enabled` 约束：
   - 开关 `true`：`needs_confirmation=True` 的工具 → 问用户确认
   - 开关 `false`：`needs_confirmation=True` 的工具 → `auto_confirm` 放行（不挂起）

> **盘根硬拦说明（全文会审 v1.12）**：盘根（含非系统盘 `D:\`、`E:\`…）**任意方式删除一律拒绝**——`_is_forbidden_path` 用 `os.path.splitdrive` 判定，any-mode 硬拦、不区分递归。R2 表列为"磁盘根递归"为规则语义表述，实现上非系统盘根普通删除同样拒绝（盘根为目录边界，普通删除无意义且易误伤）。

## 三、现状分析

### 3.1 现有防线分布

| 层 | 位置 | 职责 |
|----|------|------|
| Safety 层 path 越权 | `path_safe_check.py:_is_forbidden_path` (L74-95) | 盘根黑名单（splitdrive 全盘符，L76-78）+ 系统敏感路径（L82-95）|
| Safety 层已知风险 | `tool_safety_checker.py:_check_known_risks` | 路径越权/写入大小保护/代码注入（无条件防线） |
| delete 内防线 | `delete_file.py:_guard_forbidden_delete` (L56-105) | 盘根/项目根/系统保护（不依赖开关，但硬编码在工具） |

### 3.2 存在的不足（系统薄弱点分析）

1. **delete 无专属安全规则表（核心差距）**：`shell` 有 `SHELL_DANGEROUS_PATTERNS` 分级表（HIGH 拒绝 / MEDIUM 确认），而 `delete` 工具**只有一刀切的 `needs_confirmation=True`**（file_register.py:239-241），所有 delete 一律确认，无法按"路径位置 + 递归类型"差异化处置。安全粒度远低于 shell。
2. `_is_forbidden_path` 盘根判定（`os.path.splitdrive` + 剩余为空，path_safe_check.py:76-78）**已覆盖全盘符**（`D:\`、`G:\`…），故"磁盘根递归=拒绝"（R2）实际已由 known_risks 无条件覆盖；**真正的差距是 R3-R6（项目根边界 + 递归差异）无专属安全规则篇**
3. delete 内防线 `_guard_forbidden_delete` 硬编码在工具内部，职责归属不符合分层设计（应急补丁遗留，2026-08-02）
4. **已知风险检测 `_check_known_risks` 与工具专属规则未分层**：路径越权/写入保护等通用逻辑与 delete 特有规则（项目根边界/递归）混在一起，无 shell 那样的"通用层 + 专属层"结构

### 3.3 已确认可行的基础设施

- `ToolRegistry.register(..., action_confirmation=...)` 支持按 action 字段分派（fundamental_register.py:129）
- `ToolSafetyChecker._get_needs_confirmation` 支持 `action_confirmation` 优先解析
- 但 `DeleteInput` 无 `action` 字段（有 `path` + `recursive`），`action_confirmation` 不适用 → 需新增按 `recursive`+项目根判定的专用逻辑

## 四、设计方案

### 4.1 方案总览

为 `delete` 工具新增**专属安全检查模块**，复用 shell 已有先例（`execute_shell_command_safety.py`）的工具级特殊安全层模式：

```
Safety 层入口 (tool_safety_checker.check_before_execute)
  ├─ 通用检查（所有工具）：
  │    ├─ 未注册检查 → blocked
```

### 4.2 delete 专属规则表 DELETE_RULES

### 4.3 接入方式

`ToolSafetyChecker.check_before_execute` 对 `delete` 工具调用 `delete_safety.check_delete_risk(params)`（`params` 为工具参数字典，含 `path`/`recursive`，签名与第六章 6.2 一致）：

- 返回 `blocked=True` → 直接拒绝（R6；R1/R2 已由 known_risks 在 6.3② 提前拦截）
- 返回 `requires_confirmation=True` → 进入确认流程（R4/R5，受开关约束）
- 返回放行 → 直接执行（R3）

**保留**：`_check_known_risks` 的路径越权/写入保护/代码注入（无条件防线）不撤，与 delete 专属规则叠加生效。

**可选清理**：delete 内防线 `_guard_forbidden_delete` 与 `DELETE_RULES` R1 职责重叠，可精简——列入评审，不建议本次删除。

## 五、安全开关（security.enabled）语义设计

> 北京老陈 2026-08-04 提出补充：`security.enabled` true/false 的语义需独立成章明确。本章为全局安全开关语义设计；delete 专属精确消费链见第六章 6.4。

### 5.1 开关语义总纲

`security.enabled`（config.yaml）**仅控制"是否询问确认"，不控制危险防护**。操作按风险分三类，处置取决于"风险等级"而非开关状态：

| 操作类别 | 定义 | 是否受开关影响 |
|---------|------|--------------|
| **高危操作（blocked）** | 绝对禁区 / 危险命令，检测到即拒绝执行 | **完全无关** |
| **需确认操作（requires_confirmation）** | 可执行但有风险，需用户确认后才执行 | **开关相关** |
| **安全操作（放行）** | 正常操作，直接执行不打扰用户 | **完全无关** |

### 5.2 处置矩阵

| 操作类别 | enabled=true（正常模式） | enabled=false（E2E测试模式） |
|---------|--------------------------|------------------------------|
| **高危 blocked** | **拒绝执行** | **拒绝执行（绝不放行）** |
| **需确认 requires_confirmation** | **人工确认**（HITL弹窗，SUSPENDED等用户） | **自动确认**（auto_confirm，不挂起） |
| **放行** | 直接执行 | 直接执行 |

> **铁律（安全底线）**：高危操作在 E2E 测试模式下**同样拒绝**，绝不因测试自动化而放行——防止误删系统盘/系统目录/代码库。

### 5.3 false = E2E 测试模式（auto_confirm 语义）

- `security.enabled=false` 的用途是 **E2E 自动化测试（无人值守）**，不是"关闭安全"。
- **需确认操作**：`check_before_execute` 返回 `SafetyResult(requires_confirmation=True, auto_confirm=True)` → action_handler 消费 `auto_confirm` → `resolve_confirmation(confirmed=True)` 立即通过；MetaStep 照出但**不挂起**（不等待用户）。
- **高危操作**：仍返回 `blocked=True` → 直接拒绝；`auto_confirm` 不消费 blocked（action_handler:161 先判 blocked，186 才判 auto_confirm）。
- **安全操作**：直接放行，无确认流程。

### 5.4 与 delete R1-R6 映射

| 规则 | 类别 | enabled=true | enabled=false(E2E) |
|------|------|--------------|--------------------|
| R1 系统盘/系统目录 | 高危 | 拒绝 | **拒绝** |
| R2 磁盘根递归 | 高危 | 拒绝 | **拒绝** |
| R6 项目根外递归 | 高危 | 拒绝 | **拒绝** |
| R4 项目根内递归 | 需确认 | 人工确认 | **自动确认** |
| R5 项目根外普通 | 需确认 | 人工确认 | **自动确认** |
| R3 项目根内普通 | 放行 | 直接执行 | 直接执行 |

### 5.5 设计落地点（双轨接入支撑，详见第六章）

- 高危（R1/R2/R6）走 `_check_known_risks`（无条件防线，先于开关分支）→ 开关无关 ✓
- 需确认（R4/R5）走 `_get_needs_confirmation` + 开关分支 → true 人工 / false auto_confirm ✓
- 放行（R3）→ 免确认 ✓
- 消费链：action_handler blocked→ErrorStep / requires_confirmation→MetaStep+auto_confirm 已有 ✓

### 5.6 与现有代码一致性核对

真实代码 `tool_safety_checker.py`（2026-08-04 小欧 注释）：
- "开关false仍拒绝已知风险: bypass只跳过确认询问不跳过危险防护, `_check_known_risks`(路径越权/写入保护/代码注入)检测到即 blocked 拒绝执行"
- `_is_skip_safety()` 只影响确认询问分支，不影响危险防护

**本章设计与之完全一致**，并把"高危开关无关 + 需确认开关分流 + false=E2E测试自动确认"语义显式固化。

> **盘符动态化原则（北京老陈 2026-08-04 补充，v1.13）**：系统盘符**不硬编码单一值**，采用"**写死常见默认 + 运行时动态识别真实系统盘符**"的灵活性设计：
>
> - **写死保底（默认模板）**：`FORBIDDEN_PATHS_WINDOWS_EXACT/PREFIX` 保留以 `C:\` 书写的常见系统目录名集（`\Windows`、`\Program Files`、`\Program Files (x86)`、`\Windows\System32\config`、`\Windows\WinSxS`…）——系统目录**名称集写死**，确保常规环境零配置生效。
> - **运行时动态（灵活性）**：安全检查时刻（`_is_forbidden_path` 内）调用新增工具函数 `get_system_drive()`，将模板中 `C:` 前缀**动态替换为真实系统盘符**后再匹配——系统装在非 C 盘、盘符被重映射时**不漏判**；真实盘符不在 `C:` 时**不误伤**。
> - **`get_system_drive()` 识别优先级**：`SystemRoot`/`WINDIR` 环境变量 `splitdrive` → `SystemDrive` → 探测存在 `\Windows` 的盘符 → 兜底 `C:`。
> - **`get_existing_drives()`（v1.14，北京老陈补充——磁盘递归删除判定专用）**：**对磁盘进行递归删除的判定时刻**，动态获取**当前磁盘符号列表**（遍历 `A-Z` 探测 `os.path.exists(f"{c}:\\")`，或 `ctypes.GetLogicalDrives()`），识别目标是否为现存磁盘根。盘符可能变化（U 盘插拔、盘符重映射），列表**不写死**，安全检查时刻实时获取。服务 R2（磁盘根递归删除→拒绝）与白名单盘符枚举，与 `get_system_drive()`（服务 R1 系统目录）各司其职。
> - **白名单盘符枚举同步动态化**：`get_default_allowed_paths`（path_safe_check.py:50-53）现硬编码字母表上限 `J`，改为遍历 `A-Z` 动态探测**当前存在的盘符列表**（安全检查时刻获取），消除系统盘/数据盘在 `J` 后被白名单漏列的问题。
> - **归属**：`get_system_drive`/`get_existing_drives`/盘符枚举为 **Safety 层公共函数**（app/utils/ 或 path_safe_check.py），供 `_is_forbidden_path` 与 `get_default_allowed_paths` 复用（DRY），禁止工具层重复实现。
> - **不影响 R3-R6**：R3-R6 判定以项目根为边界，与系统盘符无关；本设计仅作用于 R1（系统盘/系统核心目录）判定。

> **复用铁律（三堂会审合规结论）**：`_is_forbidden_path`（path_safe_check.py:60-100）已包含"磁盘根(L76-78) + 系统目录(L82-95)"双重判定，**禁止**新增 `_is_disk_root`/`_is_system_dir` 重复函数（DRY），直接复用 `_is_forbidden_path`。

### 6.2 判定入口 + 顺序 (Codable Spec, 三堂会审修正 v1.8)

> **分工原则（修正 R1/R2 死代码缺陷）**：R1(系统盘/系统目录) 与 R2(磁盘根递归) **已由 `_check_known_risks → validate_tool_path → _is_forbidden_path` 无条件覆盖**（known_risks 为开关无关防线），`check_delete_risk` **不重复实现** R1/R2，只负责 R3-R6 差异判定。**恒返回 SafetyResult（R3→`_PASS`），不用 `None` 表示放行**（防 R3 免确认失效）。

```python
# backend/app/services/safety/delete_safety.py  (NEW)
def _as_bool(v: Any) -> bool:
    """布尔强转 — 防 LLM 原始参数 'false'/'true' 字符串陷阱: bool('false')==True 错误 """
    if isinstance(v, bool):
        return v
    return str(v).strip().lower() in ("1", "true", "yes", "on")


_PASS = SafetyResult(blocked=False, requires_confirmation=False,
                     message="", safety_level="safe")          # 放行统一产物


def check_delete_risk(params: dict) -> SafetyResult:
    """delete 专属差异判定（R3-R6）。

    恒返回 SafetyResult（从不用 None），使调用侧可用 `delete_risk is not None`
    区分"是delete工具"，R3 用 _PASS 表示免确认 —— 修复 v1.9 版本 R3=None
    导致 _get_needs_confirmation 落入原逻辑 needs_confirmation=True 的缺陷。
    R1/R2 由 _check_known_risks(validate_tool_path) 覆盖, 此处不重复。
    """
    path = str(params.get("path") or "").strip()
    recursive = _as_bool(params.get("recursive", False))       # 6.1 递归默认 False, 防字符串陷阱

    try:                                                        # 6.1 路径归一化
        p = Path(os.path.expanduser(path)).resolve()
    except Exception:
        return _PASS                                             # 路径异常→放行, 工具层validate会拦

    proj_root = _get_project_root_safety()                      # 6.1 项目根(上移Safety层, 评审项2, 恒非None)
    inside_proj = (p == proj_root) or (proj_root in p.parents)

    # --- R6 项目根外递归 → 拒 ---
    if (not inside_proj) and recursive:
        return SafetyResult(blocked=True, message=f"禁止删除项目根外目录(递归): {path}", safety_level="dangerous")

    # --- R4 项目根内递归 → 确认 / R5 项目根外普通 → 确认 ---
    if (inside_proj and recursive) or (not inside_proj):
        return SafetyResult(requires_confirmation=True, blocked=False,
                            message=f"删除需确认: {path}", safety_level="destructive")

    # --- R3 项目根内普通 → 放行(免确认), 恒非None ---
    return _PASS
```

判定顺序与 **2.4 处置优先级** 一致：R1/R2(known_risks) → R6 → R4/R5 → R3。

### 6.3 接入点 (Codable, 三堂会审修正 v1.8)

> **关键修正（原直接 return 会绕过开关分支）**：不能把 `check_delete_risk` 的结果在 known_risks 前直接 `return`——那会使 R4/R5 的确认**绕过 `_is_skip_safety()` 的 auto_confirm 分支**，破坏 6.4 的开关交互。正确做法是**双轨接入 + 一次性计算**，保持 `check_before_execute` 现有流程结构不变（KISS-DIRECT）：

```python
# tool_safety_checker.py —— 修改 check_before_execute（保持现有流程骨架）
def check_before_execute(self, tool_name, params=None):
    params = params or {}
    tool_meta = tool_registry.get_tool(tool_name)
    if tool_meta is None:
        return SafetyResult(blocked=True, message=f"工具{tool_name}未注册", safety_level="dangerous")

    # ① delete 专属判定一次性计算, 供②③两处消费(DRY)
    delete_risk = check_delete_risk(params) if tool_name == "delete" else None

    # ② 已知风险无条件防线(开关无关): R1/R2(盘根/系统目录) + R6(项目根外递归)
    known_risk = self._check_known_risks(tool_name, params, delete_risk=delete_risk)
    if known_risk is not None:
        known_risk.safety_level = "dangerous"
        return known_risk

    # ③ 确认策略分流: 开关只影响"是否询问", 不影响危险防护(现有分支不动)
    if _is_skip_safety():
        if self._get_needs_confirmation(tool_meta, params, delete_risk=delete_risk):
            return SafetyResult(requires_confirmation=True, auto_confirm=True,
                    blocked=False, message="安全开关已绕过(提示照出)", safety_level="destructive")
        return SafetyResult(requires_confirmation=False, blocked=False,
                message="安全开关已绕过", safety_level="safe")
    # ... 后续 check_fn / needs_confirm 分支原样, 确认值改由 _get_needs_confirmation(delete_risk) 提供
```

对应两处消费函数修改（同文件）：

```python
@staticmethod
def _check_known_risks(tool_name: str, params: Dict, delete_risk: Optional[SafetyResult] = None) -> Optional[SafetyResult]:
    is_valid, msg = _validate_tool_path(tool_name, params)
    if not is_valid:
        return SafetyResult(blocked=True, message=f"路径越权: {msg}")   # 覆盖R1/R2
    if delete_risk is not None and delete_risk.blocked:
        return delete_risk                                               # R6 项目根外递归
    # ... 写入大小保护等原逻辑不动

@staticmethod
def _get_needs_confirmation(tool_meta, params: Dict, delete_risk: Optional[SafetyResult] = None) -> bool:
    if delete_risk is not None:                       # delete: 动态判定(R3免/R4/R5确认)
        return delete_risk.requires_confirmation      # R3→_PASS→False(免确认); R4/R5→True
    # ... 原 action_confirmation / needs_confirmation 逻辑不动(仅非delete工具)
```

> **消费链正确性（v1.9 缺陷修复后）**：`check_delete_risk` 恒返回 SafetyResult → 对 delete 工具 `delete_risk is not None` 恒真 → R3 返回 `_PASS.requires_confirmation=False` → 免确认；R4/R5 返回 True → 确认；R6 返回 blocked=True → `_check_known_risks` 无条件拦截。**R3 免确认不再落入原逻辑 needs_confirmation=True**。

> **说明**：R1/R2 由 `_validate_tool_path → _is_forbidden_path` 无条件拦截（盘根+系统目录），R6 由 `check_delete_risk` 判定并经 known_risks 无条件拦截，三者均**不依赖 security.enabled**；R4/R5 经 `_get_needs_confirmation` 流入开关分支，`enabled=false` 时 `auto_confirm=True` 放行（与 6.4 一致）。
