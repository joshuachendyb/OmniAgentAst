## 〇、核心设计原则

> **北京老陈 2026-08-04 梳理确认**，本文档一切设计围绕此原则展开。

### 〇.1 总纲：先分类别，再定处置

- **系统磁盘 / 系统目录**（盘根 `C:\`、`G:\`、系统核心目录）：按原有规则 **无条件拒绝执行**，不参与确认流程，属不可恢复禁区。
- 以下确认策略，全部针对 **非系统目录 / 非系统磁盘**。

### 〇.2 最终决策矩阵

| # | 目标 | 删除方式 | 处置 |
|---|------|----------|------|
| R1 | 系统盘根 / 系统核心目录 | 任意（含递归） | **无条件拒绝**（不可恢复禁区）|
| R2 | 磁盘根（含非系统盘 `D:\`、`E:\`…） | 递归删除 | **拒绝执行** |
| R3 | 项目根内 | 普通删除 | **不需确认**（正常操作，不打扰用户）|
| R4 | 项目根内 | 递归删除 | **需确认**（递归杀伤力大，二次确认）|
| R5 | 项目根外 | 普通删除 | **需确认**（用户确认后可执行）|
| R6 | 项目根外 | 递归删除 | **拒绝执行** |

**规则速记：**

- **拒绝**：系统盘/系统目录任意删除、磁盘根递归删除、项目根外递归删除
- **需确认**：项目根内递归、项目根外普通
- **不需确认**：项目根内普通

### 〇.3 递归删除一律视为危险命令

- **判定维度：目录 + 磁盘 全覆盖。** 无论目标在哪个**磁盘**（`C:\`、`G:\`、`D:\`…）、哪个**目录**（项目内/项目外/任何层级/深层子目录），只要 `recursive=True` 递归删除，一律视为危险命令。
- **处置分档**：
  - 系统盘根/系统核心目录递归 → **无条件拒绝**（R1）
  - 磁盘根（含非系统盘）递归 → **拒绝执行**（R2）
  - 项目根外递归 → **拒绝执行**（R6）
  - 项目根内递归 → **必须用户确认**（R4）
- 递归删除会整棵子树级联删除，误删影响范围广，级别稳定危险，不因"是否在项目内"而降低。
- **注意**：危险命令判定**不限于磁盘根**——磁盘根、项目根、项目内任意子目录、项目外任意目录，凡递归删除一律危险，不因目录层级深浅而豁免。

### 〇.4 补充硬约束

> 系统盘根（`C:\`、`G:\`）与系统核心目录为**不可恢复禁区**，任何情况下**无条件拒绝执行**（R1），不因用户确认而放行。R3-R6 均为非系统目标。

## 一、需求背景

### 1.1 问题来源

2026-08-02 曾发生 E2E 测试 `test_dl4_delete_root_protection` 真删 G 盘根目录事故。为应急，当时在 `delete_file.py` 内部新增了 `_guard_forbidden_delete` 最后防线（无条件硬阻断删除盘根/项目根/系统保护目录）。

**根因复盘（关键教训）：**

- 前期安全加固资源几乎全部投向 `shell`（`SHELL_DANGEROUS_PATTERNS` 高危命令分级表，历经多轮迭代），而 **`delete` 工具长期处于安全盲区**——只有一刀切 `needs_confirmation=True`，无按路径/递归分级的规则。
- 安全机制分布**严重不均**：高风险面（shell）反复加固，同等级破坏性的 delete（可删代码库、可递归删目录）却被忽视，最终导致 G 盘根目录被真删、代码库遭破坏。
- 应急补丁（`_guard_forbidden_delete`）硬编码进 delete 工具内部，违反 SRP 分层（工具层负责执行，安全策略应归 Safety 层）。

### 1.2 需求诉求（北京老陈 2026-08-04 梳理）

删除操作的"确认策略"以 **项目根目录** 为核心安全边界，历经多轮梳理，最终收敛为：

| 场景 | 处置 |
|------|------|
| 项目根目录**之内**的普通删除 | 不需要确认 |
| 项目根目录**之内**的递归删除 | 需要用户确认 |
| 项目根目录**之外**的删除（普通） | 需要用户确认 |
| 项目根目录**之外**的递归删除 | **拒绝执行**（危险）|
| 磁盘根递归删除 | **拒绝执行**（危险）|
| 系统盘/系统目录 | **无条件拒绝** |

> 注：完整、精确定义的处置规则见「〇、核心设计原则」最终决策矩阵。

### 1.3 设计原则

1. **职责归属正确**：安全策略归 Safety 层统一判定，**不硬编码进 delete 工具内部**。
2. **确认 ≠ 拒绝**：项目根之外的删除可以执行（user 确认），并非绝对禁止。
3. **绝对禁区仍需硬拦截**：盘根（C:\、G:\）、系统核心目录为不可恢复禁区，任何情况下直接拒绝（不因确认而放行）。
4. **安全覆盖必须均衡（G 盘事故教训）**：同等级破坏面的工具（shell/delete/execute_sql 等）都应具备同等粒度的专属安全规则，**禁止出现"高危工具安全盲区"**。

## 二、需求细节

### 2.1 判定维度

删除是否"需确认"，由两个维度共同决定：

1. **路径位置**：目标路径是否属于"项目根目录"范围
2. **删除方式**：是否为递归删除（`recursive=True`）

### 2.2 项目根目录定义

采用 `delete_file.py:_get_project_root()` 现有实现（2026-08-02）：
- **主判定**：以代码位置推算（`backend` 的父级），可靠不可篡改
- **兜底**：config 的 `project_root` 仅作辅助（生产 config 可能被改为测试目录，不可信）

### 2.3 规则表（目标行为）

| # | 位置 | recursive | 处置 | 说明 |
|---|------|-----------|------|------|
| R1 | 系统盘根/系统核心目录 | 任意 | **无条件拒绝（blocked）** | 不可恢复禁区，按原规则无条件拒绝，不参与确认 |
| R2 | 磁盘根（含非系统盘 D:\、E:\…） | True | **拒绝（blocked）** | 磁盘根递归删除直接拒绝 |
| R3 | 项目根内 | False | **False（不需确认）** | 普通删除，不打扰用户 |
| R4 | 项目根内 | True | **True（需确认）** | 递归删除杀伤力大，二次确认 |
| R5 | 项目根外 | False | **True（需确认）** | 普通删除，用户确认后可执行 |
| R6 | 项目根外 | True | **拒绝（blocked）** | 项目根外递归删除直接拒绝 |

### 2.4 处置判定顺序（优先级）

1. **R1 系统盘/系统核心目录 → 无条件拒绝**（最优先，任何配置下不可删，不参与确认）
2. **R2 磁盘根递归 / R6 项目根外递归 → 拒绝**（危险命令直接拒绝）
3. **R4 项目根内递归 / R5 项目根外普通 → 需确认**
4. **R3 项目根内普通 → 不需确认**
5. 确认策略受安全开关 `security.enabled` 约束：
   - 开关 `true`：`needs_confirmation=True` 的工具 → 问用户确认
   - 开关 `false`：`needs_confirmation=True` 的工具 → `auto_confirm` 放行（不挂起）

## 三、现状分析

### 3.1 现有防线分布

| 层 | 位置 | 职责 |
|----|------|------|
| Safety 层 path 越权 | `path_safe_check.py:_is_forbidden_path` (L74-78) | 盘根 `C:\` 黑名单（仅硬编码 C:，不通用） |
| Safety 层已知风险 | `tool_safety_checker.py:_check_known_risks` | 路径越权/写入大小保护/代码注入（无条件防线） |
| delete 内防线 | `delete_file.py:_guard_forbidden_delete` (L56-105) | 盘根/项目根/系统保护（不依赖开关，但硬编码在工具） |

### 3.2 存在的不足（系统薄弱点分析）

1. **delete 无专属安全规则表（核心差距）**：`shell` 有 `SHELL_DANGEROUS_PATTERNS` 分级表（HIGH 拒绝 / MEDIUM 确认），而 `delete` 工具**只有一刀切的 `needs_confirmation=True`**（file_register.py:239-241），所有 delete 一律确认，无法按"路径位置 + 递归类型"差异化处置。安全粒度远低于 shell。
2. `_is_forbidden_path` 盘根黑名单 **仅精确匹配 `C:\`**，对 `G:\`、`D:\` 等其他盘根的拦截不通用（依赖 delete 内防线兜底）——无法支撑"磁盘根递归=拒绝"（R2）规则
3. delete 内防线 `_guard_forbidden_delete` 硬编码在工具内部，职责归属不符合分层设计（应急补丁遗留，2026-08-02）
4. **已知风险检测 `_check_known_risks` 与工具专属规则未分层**：路径越权/写入保护等通用逻辑与 delete 特有规则（项目根边界/递归）混在一起，无 shell 那样的"通用层 + 专属层"结构

### 3.3 已确认可行的基础设施

- `ToolRegistry.register(..., action_confirmation=...)` 支持按 action 字段分派（fundamental_register.py:129）
- `ToolSafetyChecker._get_needs_confirmation` 支持 `action_confirmation` 优先解析
- 但 `DeleteInput` 无 `action` 字段（有 `path` + `recursive`），`action_confirmation` 不适用 → 需新增按 `recursive`+项目根判定的专用逻辑

## 四、设计方案

### 4.1 方案总览

为 `delete` 工具新增**专属安全检查模块**，复用 shell 已有先例（`execute_shell_command_safety.py`）的工具级特殊安全层模式：

```
Safety 层入口 (tool_safety_checker.check_before_execute)
  ├─ 通用检查（所有工具）：
  │    ├─ 未注册检查 → blocked
  │    ├─ 已知风险（路径越权/写入大小保护/代码注入）→ blocked（无条件防线）
  │    └─ 确认策略分流（needs_confirmation / auto_confirm）
  │
  └─ 工具专属安全模块（特殊层，按工具接入）：
       ├─ shell      → execute_shell_command_safety.py（SHELL_DANGEROUS_PATTERNS 表）
       └─ delete     → 【新增】delete_safety.py（DELETE_RULES 表，R1-R6）
```

### 4.2 delete 专属规则表 DELETE_RULES

参照 `SHELL_DANGEROUS_PATTERNS` 结构，新增 `delete_safety.py`，规则表按 R1-R6 设计：

| # | 匹配条件 | 级别 | 处置 |
|---|----------|------|------|
| R1 | 系统盘根（C:\、G:\）/ 系统核心目录 | — | **无条件 blocked** |
| R2 | 磁盘根（含非系统盘 D:\、E:\…）+ `recursive=True` | HIGH | **blocked（拒绝）** |
| R3 | 项目根内 + 普通（非递归） | 安全 | 放行（不需确认）|
| R4 | 项目根内 + `recursive=True` | MEDIUM | 需确认 |
| R5 | 项目根外 + 普通 | MEDIUM | 需确认 |
| R6 | 项目根外 + `recursive=True` | HIGH | **blocked（拒绝）** |

判定输入：`path` + `recursive` + 项目根引用（`_get_project_root()`）。

### 4.3 接入方式

`ToolSafetyChecker.check_before_execute` 对 `delete` 工具调用 `delete_safety.check_delete_risk(path, recursive)`：

- 返回 `blocked=True` → 直接拒绝（R1/R2/R6）
- 返回 `requires_confirmation=True` → 进入确认流程（R4/R5，受开关约束）
- 返回放行 → 直接执行（R3）

**保留**：`_check_known_risks` 的路径越权/写入保护/代码注入（无条件防线）不撤，与 delete 专属规则叠加生效。

**可选清理**：delete 内防线 `_guard_forbidden_delete` 与 `DELETE_RULES` R1 职责重叠，可精简——列入评审，不建议本次删除。

### 4.4 安全开关交互

| 开关 | R3 项目根内普通 | R4/R5 需确认 | R1/R2/R6 拒绝 |
|------|----------------|--------------|---------------|
| `enabled=true` | 直接执行 | 问用户 | blocked（不确认）|
| `enabled=false` | 直接执行 | `auto_confirm` 放行 | **blocked（不受开关影响）** |

> **关键约束**：R1/R2/R6 的 blocked 是硬拦截，不因开关 `false` 而放行。
