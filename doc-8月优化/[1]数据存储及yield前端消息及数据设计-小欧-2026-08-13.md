### 0.3 设计基本原则

> 本章定位：本文档所有设计决策遵循的原则。每条原则解决一个具体问题，标注在本文档的落点，方便审核它是否被正确贯彻。

**原则一：单一权威（Single Source of Truth）。** 同一份数据只在一个地方持有权威副本，其他地方只引用、不复制。这解决的是"同一份数据存两处、口径漂移"的痛点。本文档的落点是：工具执行结果的唯一权威是 `ActionStep.execution_result`（含 `{data, llm_data, other_data}` 三字段），前端 30+ Renderer 全从它取数（1.8）；`ObservationStep` 的 `tool_result`/`llm_data`/`other_data`/`parallel_results` 四字段是冗余副本，按 7.1.1 删掉。回放时 observation 文本由 `execution_result` 重新派生（3.1 治理首选方案），不另存一份派生字符串。例外与边界：5.1 文件A 是 `execution_result` 的**仅排查用不截断副本**（非权威源、不参与展示与回放、不构成口径漂移，副本定位见 5.1）；文件B 是喂 LLM messages 的排查快照，同理非权威源。

**原则二：两路同构（Yield 与 Storage 同一份对象）。** 前端看到的字段 == 落库能还原的字段 == `to_dict()` 序列化的字段。这解决的是"前端能展示但回放还原不了、或反过来"的割裂问题。本文档的落点是：`step_dict` 双路分发（1.1），SSE 消息就是 `step_dict` 本身（1.4），前端展示与历史回放共用同一套渲染函数（3.7.6），"显示什么样、回显就什么样"。

**原则三：单向依赖（加字段须建立在删冗余之上）。** 新增字段时，如果存在冗余字段，必须先删冗余再加新的，不能只加不删。这解决的是"加一个字段解决一个问题、却制造更多冗余"的膨胀问题。本文档的落点是：启用保真 `observation_text` 依赖"删四字段"先行落地（3.1 约束-依赖方向），纯加不删会让冗余从 4 个字段增至 5 个（7.3 不做）；"删四字段"本身独立安全、可单独落地（7.1.1），与是否加保真字段无耦合。

**原则四：禁止 backward（重新设计，不试图向后兼容旧模式）。** 重新设计就彻底改，不保留旧模式的兼容路径。这解决的是"新旧混杂、代码越来越混乱"的退化问题。本文档的落点是：前端展示从"分步卡片"彻底推翻为"流水线式"（2.8/3.7），废弃 StepRow 体系卡片渲染、ExecutionPanel 分块卡片式展示（3.7.8），不试图兼容旧卡片模式；chunk 思考流与 thought 完整思考的展示去重（3.6）也只做前端一处收敛，不改后端。

**原则五：YAGNI（基于现状、前瞻扩展、当前可落地）。** 设计以当前现状为出发点，先盘清扩展性需求与问题，再定方案：方案要**具有前瞻性与扩展性，功能只增不减（不能退化）**；同时拒绝为臆想的未来需求提前堆砌抽象——任何扩展设计都必须建立在**当前系统能落地实现**之上，绝不做到当前系统都无法实现。这解决的是"只顾眼前不留扩展口、或过度设计做不出来"的两极问题。本文档的落点是：`observation_text` 保真兜底仅在"需要回看当时逐字喂 LLM 的 observation"的排查/审查场景启用，不默认落库（3.1 决策标准）——是按需启用而非拒绝扩展；token_usage 表不做计费/限额（10.6 不做）——统计先行、计费留待有真实需求再扩展；截断机制不做激进取舍，各 tool 已自行截断，storage 仅做安全兜底防 SQLite 行溢出（5.7 阈值依据）；5.1 的存储演进（会话→任务→消息→步骤）、token 四维度归属落库（第 10 章）、文件A/B 副本与 conversation_history（5.1）均为**基于现状的前瞻扩展设计**，可平滑演进对象存储，不属"用不上提前堆砌"。

**原则六：前端随后端（契约以后端字段为准）。** 前端不质疑后端字段，后端改了前端跟着改。这解决的是"前后端字段口径不一致、各改各的"的协作问题。本文档的落点是：前端 ToolResultRenderer 全读 `execution_result.llm_data`（1.8），成功判定统一以 `llm_data.status.exec_code === "success"` 为准（1.8）；observation 步骤当前读 `obsStep.observation` 是死分支（2.6），修正后改读 `observation_text`/`content`（3.5 前端取数修正），字段以后端 `to_dict()` 输出为准。

#### 1.1 全链路数据流（一次任务事件如何到达前端）

```

        └─ ② yield 路：_append(event_dict)（agent_runner.py:102-113）

                ▼

```

关键结论：SSE 消息 == step_dict 本身（format_agent_sse 只加 type/step/timestamp 头，其余字段原样透传），yield 与落库是同一份 step_dict，两路同构。因此「前端能看到的字段」==「落库能还原的字段」==「to_dict() 序列化的字段」。前端看不到的字段，历史回放也还原不了。

> start 事件属旁路（不予 1.1 双路分发混淆）：上图"run_react_cycle 双路分发"只覆盖运行期步骤（thought/action/observation/final 等）。start 事件由 `step_start`（stream_orchestrator.py:208-220）在 agent 启动前直接 `yield format_agent_sse(start_dict)`，不进 1.3 的缓冲、不走双路分发。后果：start 不落 event_log → 断线重连(after_seq=N)不会重放；它只 append 进 orchestrator 的 execution_steps 内存列表并 yield SSE，**不落库**（P4 重构后持久化全在 agent_runner 内，start 不进 chat_message_steps、不进 event_log 缓冲）。

##### 1.1.1 源头：LLM 流式 chunk 的逐片转发与事后分类

> 本节定位：1.1 主链路图从 `run_react_cycle()` 产出 Step 开始。本小节补上更上游的源头——LLM 流式返回的文本如何进入主链路。整体机制分两段：流式期间「chunk 逐片实时转发」+ 流结束后「action/answer 事后分类」。

**阶段一（流式期间）：chunk 逐片实时转发**

LLM 以流式逐片返回文本（OpenAI SSE），服务端逐片消费（`llm_stream.py` 的 `call_llm_stream`）：

1. 每片有文本即打上 `is_reasoning` 标记（判定规则见 `app/llm/reasoning.py`）：`True` → 思考区文字，`False` → 答案区文字。
2. 每片文本产出 `ChunkStep(content, is_reasoning)` 实时 yield。
3. `react_cycle` 消费后 emit，进入 1.1 主链路双路分发 → SSE → 前端。前端实时逐字看到思考文字与答案文字流出。

**不是所有 LLM chunk 都转发**：只有带 `content` 文本的 chunk 才会产出 ChunkStep。纯 `tool_calls` 增量、`usage` 用量、`finish_reason` 结束标记等不转发文本——`tool_calls` 增量在服务端累积，`usage`/`finish_reason` 随最终响应携带（见阶段二）。

**阶段二（流结束后）：action/answer 事后分类**

`type` 不是 LLM 原生输出，而是 agent 在流结束后「事后分类」加上的：

| 流结束时的判定 | type | 携带内容 |
|---|---|---|
| 有 `tool_calls` | action | `thought`=答案区全文、`reasoning`=思考区全文、`tool_calls`=累积的调用 |
| 无 `tool_calls`、仅文本 | answer | `content`=答案区全文、`reasoning`=思考区全文 |
| 流异常/出错 | error | 错误信息 |

action 响应进入 handler 后产出 `ThoughtStep`/`ActionStep` 等业务步骤（各场景产出序列见 1.7；thought 步骤的 `content`=答案区全文、`reasoning`=思考区全文，见 action_handler.py）。

**同源关系（与 2.7、3.6 呼应）**：chunk 与 thought 内容同源——chunk 是流式期间的逐片转发形态，thought 是流结束后拼接的完整文本。前端同时收到二者属同一份 LLM 输出的两种形态，展示需去重（问题见 2.7，方案见 3.6）。

#### 1.3 生产者/消费者解耦模型（task_state.py:24-55）
生产者 = run_agent_in_background（agent_runner.py:69），内部 _append（agent_runner.py:102-113）把 run_react_cycle() 产出的每个事件写入 event_log 并 notify_all 唤醒消费者。

消费者 = stream_reader（stream_reader.py:119-144），纯消费者，按 seq 从 event_log 读取并转发为 SSE，重连时传 after_seq 续传；它由 _stream_with_control（stream_orchestrator.py:223-239）包装后经编排器推给前端

- StreamBuffer（task_state.py:24-34）：`event_log`(append-only 含 seq) / `cond` / `done` 三件套。
- create_stream_buffer（task_state.py:41-45）：注册 task_id→buffer。
- agent_streams（task_state.py:38）：全量流态缓冲表（task_id→StreamBuffer）。
- _append（agent_runner.py:102-113）：生产者写 `event_log` + `notify_all`。
- stream_reader（stream_reader.py:119-144）：纯消费者，按 seq 转发，重连传 `after_seq` 续传。
- reclaim_stream_buffer（task_state.py:53-55）：任务结束后延迟 300ms 回收（agent_runner.py:350-352）。

- 断线重连：`chat_stream_reconnect_orchestrator(task_id, session_id, after_seq)`（stream_orchestrator.py:242-254）复用同一 buffer 按 seq 续传，不重复事件。
- 防挂死：`cond.wait()` 加 60s 超时（asyncio.wait_for），超时后重检 `buffer.done`（stream_reader.py:136-144，2026-07-30 后端卡死根因修复）。
- 防漏事件：排空后复查 `len(buffer.event_log)`（stream_reader.py:131-133，#30 fix，防 done 前追加丢事件）。

> event_log 定性：`event_log` 是 `StreamBuffer` 的成员（task_state.py:32），一个 append-only 的进程内存 `List[Dict]`，存放在 `agent_streams`（task_state.py:38，进程内全局 dict，task_id→StreamBuffer）。它只服务于当次运行的 SSE 实时转发 + 断线按 seq 续传，不是持久化——任务结束由 `reclaim_stream_buffer` pop 回收即消失。真正的持久化走另一条独立路：`append_execution_step` 落 `chat_message_steps.step_json`（DB）。即 event_log（内存回放）与 step_json（DB 落盘）是两条互不相同但同构独立的通道；event_log 不写磁盘、不写 DB。

#### 1.4 SSE 事件格式（utils/sse_formatter.py:35-59）


- `format_agent_sse(step_dict)`（sse_formatter.py:53-59）→ `format_sse_event`（:35-50）：纯字符串拼接，`json.dumps(ensure_ascii=False)`；循环引用由 `_break_circular` 兜底（sse_formatter.py:20-32）。

#### 1.6 各 Step 字段契约（steps/ 目录，to_dict 输出 == SSE == step_json）

`ReasoningStep.to_dict()`（base.py:70-78）统一输出 `{type, step, timestamp, content}` 四键，再叠加各 Step 的 `_extra_fields()`。`content` 由 `get_content()` 产出。

- ThoughtStep（type=`thought`）：content 来源 = content/thought；顶层字段 = thought、reasoning、tool_name、tool_params。
- ActionStep（type=`action_tool`）：content 来源 = 空串（get_content 返回 ""，action_step.py:40-41）；顶层字段 = tool_name、tool_params、execution_status、execution_result（完整 {data, llm_data, other_data} 3 字段）、action_retry_count、execution_time_ms。
- ObservationStep（type=`observation`）：content 来源 = llm_data 各条 summary 拼接（observation_step.py:44-48）；顶层字段 = content(summary)、llm_data(列表)、tool_result、other_data、parallel_results。
- FinalStep（type=`final`）：content 来源 = response；顶层字段 = response、thought、outcome(completed/failed/cancelled)、error_type、error_message、model、provider、display_name、accumulated_usage、**total_steps、llm_call_count、tool_stats（dict：tool_name→次数）、retry_count、duration、artifacts**（任务级终态统计字段，字段名与 chat_tasks 落库列一致，后端计算统一下发，文档2 6.1.6② / 4.8.3-A；**设计目标待实施**——现状 final_step.py:93-105 `_extra_fields` 暂只输出 10 键、该组字段无产出）。
- ErrorStep（type=`error`）：content 来源 = error_message；顶层字段 = error_type、error_message。
- ChunkStep（type=`chunk`）：content 来源 = 流式回复片段；顶层字段 = content。
- MetaStep（type=`start`/`paused`/`resumed`/`retrying`/`authorization_required`/`truncated`/`usage`/`stats`/`context_overview`）：content 来源 = 统一 content 文本（base.py:126 字段契约）；顶层字段 = 透传 kwargs（confirm_id/tool_name/params/safety_level/wait_time/data 等）。**现状实际产出 6 种 type**：start/paused/resumed/retrying/usage/cancelled（cancelled 为前端 SSE 前置取消检测的流终止提示，见 1.5.8）；`authorization_required`/`truncated`/`stats`/`context_overview` 为**设计目标事件类型、现状无产出点**（authorization_required 旧数据经 migrate_steps 转 paused；truncated 以工具 data["truncated"] 标记承载；stats/context_overview 待实施，见文档2 6.1.6① / 6.1.12）。
  - `usage`（type=`usage`）：顶层字段 = prompt_tokens、completion_tokens、total_tokens（react_cycle.py:398-407，单任务 token 动态累计，见 1.5.14）。
  - `stats`（type=`stats`）：顶层字段 = step_count、llm_call_count、duration、retry_count（任务级统计流式累计值，字段名与 chat_tasks 落库列一致，后端计算统一下发，文档2 6.1.6①，见 1.5.15；**设计目标待实施**）。
  - `context_overview`（type=`context_overview`）：顶层字段 = summary、message_count、estimated_tokens、truncated（上下文概况，文档2 6.1.12，见 1.5.16；**设计目标待实施**）。
  注：`cancelled` 于 2026-07-18 重构后**不再作为终态类型**（终态由 FinalStep(outcome="cancelled") 承载，见 1.5.8 / 文档2 6.1.14），但前端 SSE 消费路径的前置取消检测（task_cancel_check_and_yield）仍会产出 MetaStep(type="cancelled") 作为流终止提示，故前端 sse.ts 该分支非完全不可达。

- 终态统一由 `final` 承载：FinalStep 多态（outcome=completed/failed/cancelled），前端按 outcome 分流（final_step.py:24-105，2026-07-18 重构）。
- 步骤计数：`create_step_counter()`（base.py:84-93）闭包 `next_step()` 全局唯一递增。
- 各 Step 在同一抽象层：Step 对象在 react_cycle 内 `emit` → `_step_emitter.emit(step)`，最终回到 agent_runner 的 `async for event` 循环。

#### 1.7 各场景产出的 Step 类型（前端看到的剧本）

> 注：`MetaStep(start)` 由 `step_start`（stream_orchestrator.py:208-220）在 agent 启动前前置产出，不走 1.3 缓冲（见 1.1 旁路说明）；其余步骤均由 react_cycle 产出。

- 正常调工具（单/并行）：MetaStep(start) → ThoughtStep → ActionStep(每工具一条) → ObservationStep → … → MetaStep(stats)（流式随行，**设计目标**）→ FinalStep(completed)（含任务级终态统计字段，**设计目标**，见 1.5.6 / 1.6）。
- 并行工具：1 条 assistant 带 N 个 tool_calls + N 条 ActionStep + 1 条 ObservationStep（action_handler.py:656-663 配对规则）。
- 空响应/未调工具（B3）：MetaStep(start) → MetaStep(retrying) → 循环 → FinalStep。
- 同工具/同参数死循环：ThoughtStep + 纠偏 warning（_temp_same_tool_warn 临时标记，不入库）→ 循环 → FinalStep。
- 截断：MetaStep(truncated)（上下文超限，**设计目标**；现状走截断检测 FinalStep(outcome="cancelled")，见 1.5.13）。
- 失败：MetaStep(start) → … → FinalStep(outcome="failed", error_type, error_message)。
- 取消：终态 = FinalStep(outcome="cancelled")（agent_runner.py:205-216 取消分支 set_cancelled + finally 守卫 L246-276 补发终态；react_cycle.py 取消 L583-586，2026-07-18 重构后终态不再用 MetaStep(cancelled)）；前端 SSE 前置检测路径仍产 MetaStep(type="cancelled") 作流终止提示（见 1.5.8，与文档2 6.1.14 定案一致）。
- 暂停：MetaStep(paused) / MetaStep(resumed)。

#### 1.8 前端消费实况

- 工具结果渲染：ToolResultRenderer 的 30+ 个 Renderer（frontend/src/components/Chat/ToolResultRenderer/types/*.tsx）全部从 `step.execution_result` 取 `llm_data`：
  ```ts
  const execResult = (step.execution_result || {}) as Record<string, unknown>;
  const llmData = (execResult.llm_data || {}) as Record<string, unknown>;
  ```
  成功判定统一以 `llm_data.status.exec_code === "success"` 为准（各 Renderer 文件头注释一致）。
- observation 步骤展示（现状有缺陷）：StepContent.tsx:140-474 observation 分支以 `obsStep.observation` 是否为 object 判定展示（`isObjFormat = obsStep.observation !== null && obsStep.observation !== undefined && typeof obsStep.observation === 'object'`，与 StepContent.tsx:144-146 一致），但后端 `ObservationStep._extra_fields()` 从不产出 `observation` 字段（仅输出 `llm_data`/`tool_result`/`other_data`/`parallel_results`，observation_step.py:50-59）。故 `obsStep.observation` 恒为 `undefined` → `rawObs = null` → `llmData/summary` 全走 `??` 兜底 → 最终 `summary = ''`。即当前 observation 步骤在前端实际渲染为空（ExecutionPanel.tsx:387-391 case 'observation' 同理）。这是"前端看不到真实 observation"的更直接根因，比"只存 summary"更根因。
- 依赖方向：前端随后端修改，契约以后端 step_dict 为准，前端不质疑后端字段（AGENTS.md 1.5 前后端规范）。

### 2 问题

#### 2.1 真身不入库/不 yield

`build_observation_text`（observation_formatter.py:1466）的产物 `obs_text`（action_handler.py:729 异常分支 / 733 正常分支）与最终 `merged_obs`（action_handler.py:779，`"\n\n".join(obs_parts)`）是喂给 LLM 的确切 observation 文本（经 message_builder.add_tool_result 进 conversation_history，message_builder.py:124-144、action_handler.py:768/772）。但 ObservationStep.to_dict() 不序列化该文本——它不进 SSE、不入库。

#### 2.2 落库的只是 summary 拼接

ObservationStep.get_content() 仅从 llm_data 各条取 `summary` 字段拼接（observation_step.py:44-48）。summary 是各 tool 自己写的短摘要，不是喂 LLM 的完整 observation 文本。

#### 2.3 历史回放失真

多轮上下文加载 `_load_previous_messages`（stream_reader.py:87-116）→ `_parse_observations`（stream_reader.py:67-84）只读 `step.get("content")`（= summary），用它重建 `role:tool` 消息。结果：历史回放中 LLM 看到的 observation 是截断后的 summary，而非原始完整 observation——功能退化（多轮对话上下文质量下降、复杂任务需回读全文时信息丢失）。

#### 2.4 排查困难

日志/DB 中无 observation 原文，排查"LLM 为什么这么回答"需重新跑 observation_formatter 格式化逻辑才能复原（action_handler.py:738-745 处仅日志记录 raw_data，无格式化后文本）。

#### 2.5 字段冗余（次要问题）

ObservationStep 同时携带 content(summary) 与 llm_data/tool_result，两处信息冗余且口径不一致（summary 截断 vs 完整 data），字段职责不清。

#### 2.6 前端事实性硬伤

原版本（v2.0）1.6 节称"前端 observation 分支读 `obsStep.observation`（object 时读其 llm_data）"，但后端 `ObservationStep` 从不产出 `observation` 字段，该分支是永不触发的死路——前端 observation 步骤实际渲染为空。这才是"前端看不到真实 observation"的直接根因；改进方案必须同步修正前端取数字段名（读 `observation_text`/`content`），而非沿用 `obsStep.observation`。

#### 2.7 chunk 思考流与 thought 完整思考重复展示（内容同源）

同一份思考内容，前端会收到两遍：
- chunk（is_reasoning=true）：LLM 流式返回时每吐一段思考即 yield `ChunkStep`（llm_stream.py:166），前端 sse.ts:1250 逐段实时显示（MessageContent ChunkRenderer 灰色斜体"思考区"）。
- thought：响应解析完，后端再 emit `ThoughtStep(content=thought, reasoning=reasoning)`（action_handler.py:910-915、answer_handler.py:179-193），前端 sse.ts:1209 追加一条完整思考步骤（StepContent.tsx:475 渲染"💭 思考"+"🧠 reasoning 卡片"）。

两者文本同源：`ThoughtStep.reasoning` 来自 `parsed.reasoning`，而它正是流式阶段累积的 `full_reasoning`（llm_stream.py:163 同一份累积串）。因此正常流式场景下，同一份思考文字在前端显示两遍（思考区 + 思考卡片）。

但 thought 不是纯冗余，不可删：
① 行动声明：ThoughtStep 带 `tool_name`/`tool_params`（下一步要调什么工具），chunk 只带文本——"思考→调用工具"的步骤链靠 thought 衔接；
② 非流式 reasoning 兜底：部分 LLM 思考是一次吐完（reasoning 不流式），此时 chunk 里根本没有 is_reasoning=true，思考只能靠 thought 显示；
③ 历史回放载体：断线重连（after_seq 续传）与 DB 回放时 chunk 不重放（start 同理见 1.1 旁路），thought 是完整思考的唯一可靠来源。

#### 2.8 现有前端展示模式与流水线式交互不匹配（北京老陈裁定推翻重写）

现状前端是"分步卡片"式：StepRow/StepContent/ExecutionPanel 把 thought/action_tool/observation/final 各渲染成独立边框卡片，带"💭 思考""🧠 推理""下一步""工具调用"等明显分块标记，对话页呈现为卡片堆叠。

北京老陈裁定：前端显示模式全部推翻重写，改为流水线式——前端发送任务消息后，AI 的处理按后端事件流顺序（start → thought → action_tool → observation → chunk → final）在对话页面连贯自然流出，去掉全部框框，不再有分块视觉标记。

与既有问题/方案的关系：本裁定与 2.6/2.7/3.6 方向一致但更彻底——2.7/3.6 是"保留卡片只去重"，本裁定是展示层整体重写，thought/chunk 重复、observation 死分支、分块割裂感一并在新模式下消解（思考统一走灰色斜体自然流出，工具过程内联弱化显示，不再有独立边框卡片）。

### 3 更好的方案（逐问题一方案：治理区 3.1~3.7 + 升级区 3.8~3.13）

> **总纲**：本章按"**一个问题一个方案**"组织，分两个半区：
> - **A 治理区（3.1~3.7）**：修第 2 章 2.1~2.8 的现状缺陷——一个问题一小节，与 2.x 逐条对应（3.1↔2.1/2.2、3.2↔2.3、3.3↔2.4、3.4↔2.5、3.5↔2.6、3.6↔2.7、3.7↔2.8），先派生、后保真、单向依赖；
> - **B 升级区（3.8~3.13）**：承接 0.2.2 升级需求（存储维度不完整 / 展示与定案脱节 / 排查数据源），**罗列全部新需求的概要设计**，细节归第三部分 5.1（存储载体）/ 7（存储收敛）/ 10（token 统计）与《会话任务前后端架构设计2.0》——本文档=概要定案、文档2=实施落点。
> 前端流水线展示为纯前端设计，单独成节（3.7，实施归文档2 6.2）。

#### 3.1 治理：observation 真身进 SSE + 落库（对应问题 2.1 / 2.2）

**问题**：喂给 LLM 的确切 observation 文本（`obs_text` / `merged_obs`）不 yield、不入库（2.1）；落库的仅是 llm_data 各条 summary 拼接（2.2），历史回放与排查拿不到"当时逐字喂 LLM 的 observation"。

**方案（双轨）**：

- **首选（默认，DRY 单一来源，零新增字段）**：回放时由 `ActionStep.execution_result` + 同一 `build_observation_text`（action_handler.py:733）重新派生 observation 文本，而非落库一份派生字符串。`execution_result`（`{data, llm_data, other_data}`）已是完整权威副本，喂 LLM 的 `merged_obs` 由其确定性派生（= `build_observation_text(result, tool_name, tool_params)` 拼接），无需新增字段，最契合 DRY/YAGNI。
- **保真兜底（仅排查/审查场景按需启用）**：`ObservationStep` 增 `observation_text` = `merged_obs` 全文（action_handler.py:779，含异常分支 obs_text:729 与 repair_warning 前缀:759-761），随 SSE yield + 随 step_json 落库，供"回看当时逐字喂 LLM 的 observation"。启用须满足下述约束（单向依赖），否则引入新冗余。

> 诚实边界："重跑同一函数"可近似复原，不能逐字节复原——`merged_obs` 含运行时上下文，回放无法重建：①异常分支包装 `f"Observation: 工具...执行异常: {result}"`（action_handler.py:729）；②`repair_warning` 前缀（action_handler.py:759-761，**来自运行时 LLM tool_call 参数截断修复 `_repair_warning`（base_service.py:311，经 llm_stream.py:64/78 → action_handler.py:853/864 传递）**，不入库；`_temp_same_tool_warn` 是独立机制——同工具死循环纠偏临时消息标记（react_cycle.py:219-229，由 pop_temp_messages 按 `_temp_*` 前缀弹出，不入库），两者来源不同勿混）。这些前缀只在发生相应运行时分支时存在，多数正常路径可精确复原；但在异常/纠偏路径上与当时喂 LLM 的文本有差异。

**决策标准（是否新增 observation_text，取决于是否接受两处近似）**：(a) `repair_warning`/异常包装的近似复原；(b) `build_observation_text` 日后变更导致的漂移。默认用首选（零字段、零膨胀）；仅在需要"回看当时逐字喂 LLM 的 observation"的排查/审查场景启用保真。

**约束（单向依赖，保真启用须全满足）**：

- 依赖方向：要求——"加 observation_text" 依赖 "删四字段"（纯加会冗余增到 5 个，见 3.4 / 7.3）；"删四字段" 本身独立安全，首选方案下可单独落地。理由——删四字段只需"前端不从 ObsStep 加字段取数 + 回放改从 execution_result 派生"，与是否加保真字段无耦合；只有"只加不删"才会退化，故仅约束"加须建立在删之上"，不强制双向同批回滚。
- 落库口径：要求——`observation_text` 直接对已截断后的 execution_result 派生、原样落库，不再二次截断。理由——各 tool 已自行截断输出（第三部分 5.7 阈值依据），故 `merged_obs` 体量受 tool 层截断约束、无爆炸风险；对已截断数据派生使两源天然同口径，无需为"是否截断"设双轨，消解"保真 vs 截断"矛盾。
- 多轮回放：要求——`_parse_observations`（stream_reader.py:67-84）：首选方案下由 execution_result 重新派生；保真方案下优先读 `observation_text`、回退 `content`（见 3.2）。理由——多轮对话上下文质量与首次一致（功能增强，禁止 backward）。
- 前端取数修正：要求——前端 observation 分支改读 `observation_text`/`content`，删除 `obsStep.observation` 死分支（问题 2.6，见 3.5）。理由——否则加字段前端也读不到，定案名不副实。

**两方案对比**：

- 字段：首选 = 不新增；保真兜底 = ObservationStep 增 `observation_text`（observation_step.py 增构造参数 + `_extra_fields()` 输出 + `get_content()` 优先返回）。
- 数据源：首选 = execution_result（action_handler.py:656-662 已产出）；保真兜底 = action_handler.py:779 `merged_obs`（含异常分支 obs_text:729 与 repair_warning 前缀:759-761）。
- 落库：首选 = 无新增、回放派生；保真兜底 = 随 step_json 持久化。
- yield：首选 = 无新增；保真兜底 = SSE 自动透传，前端无需改传输层。
- 体积：首选 = 零增长；保真兜底 = 需评估（可能与 execution_result 截断口径冲突）。

**方案理由**：原 v2.0"一增全通"用 DRY 作为删四字段的理由，转头却新增一份派生文本 `observation_text` 落库，标准不自洽。本方案把"删冗余原始副本"与"是否存派生文本"分开决策——先选零字段派生（最优），确有保真需求再存，且存时须建立在"删四字段"之上（单向依赖）、口径一致、前端改读。不新增 is_success/summary 等冗余字段（llm_data.status.exec_code 已是权威源）。

**落点**：实施见 4.1.1（首选）/ 4.1.3（保真）；落库细节见 7.1.4 / 8.1.5。

#### 3.2 治理：多轮回放改派生完整 observation（对应问题 2.3）

**问题**：多轮上下文加载 `_parse_observations`（stream_reader.py:67-84）只读 `step.get("content")`（=summary 截断版），回放喂 LLM 的 observation 失真（功能退化）。

**方案**：`_parse_observations` 改派生完整 observation——首选由 `execution_result` 重新派生（与 3.1 首选同源同函数）；保真优先读 `observation_text`、回退 `content`。派生入参（tool_name/tool_params/result）须与 `build_observation_text` 完全一致，建议抽公用函数（复用优先，先查 FUNCTIONS.md）避免两份格式化逻辑漂移。

**落点**：实施见 4.1.1 / 4.2（风险）；本方案是 3.1 约束"多轮回放"的展开。

**方案**：排查数据源改**文件A/B 副本**（排查/审计专用，非回放/展示数据源）——文件A `tool_raw` = `execution_result` 不截断副本；文件B `conversation_history` = 喂 LLM 的确切消息全文快照（system prompt 全文、未截断 `merged_obs` 等 DB 结构化/截断版无法完整还原的内容）。**概要设计见 3.13，完整设计见 5.1（载体二）**。

**问题**：ObservationStep 同时携带 `content`(summary) 与 `llm_data`/`tool_result`，与 ActionStep.execution_result 冗余双存储（详见第三部分 6.1），信息冗余且口径不一致。

**落点**：7.1.1 / 7.1.2 / 8.1.1 / 8.1.2。

**问题**：前端 observation 分支读 `obsStep.observation`（StepContent.tsx:140-146）是永不触发的死分支（后端从不产出该字段，observation_step.py:50-59 无 observation 输出），observation 实际渲染为空。

#### 3.6 治理：chunk 思考流 vs thought 完整思考：前端展示去重（对应问题 2.7）

两事件都保留，只在前端去重展示——后端零改动，纯前端一处收敛。

- 不删 chunk 思考流：流式实时打字机体验不可替代；删除后流式阶段无思考展示。
- 不删 thought：它承载行动声明（tool_name/tool_params）、非流式 reasoning 兜底、历史回放载体（详见 2.7 三点），删除即功能退化（禁止 backward）。
- 收敛动作：StepContent.tsx:475 thought 分支——当同 step 已收到 is_reasoning=true 的 chunk（前端 executionSteps 中该 step 已存在思考流 chunk）时，thought 卡片只渲染行动声明（"💭 思考 → 调用工具 X"），不重复贴完整 reasoning 文本；当无流式思考（非流式 reasoning 的 LLM、断线重连续传、历史回放）时，thought 仍按现逻辑完整渲染。判定依据是前端既有数据（executionSteps 内同 step 的 chunk.is_reasoning），无需新增字段、无需后端配合。
- 效果：正常流式 = 思考区实时显示（chunk）+ 步骤卡片只留行动声明；异常/回放 = 思考完整卡片兜底。功能增强、零退化。

#### 3.7 治理：流水线式前端展示重写（对应问题 2.8，前端设计，单独小节）

推翻现有"分步卡片"式展示，改为流水线式——前端发送任务消息后，AI 的处理按后端事件流顺序在对话页连贯自然流出，去掉全部框框。本方案是 2.8 裁定的完整落地设计（**纯前端设计，单独成节**），覆盖界面结构、事件呈现、流式过程、交互、回放一致、边界情况与改造范围（3.7.1~3.7.8）。

##### 3.7.1 设计总则（四条铁律）

- 一条线：一次 AI 回复 = 一条流水线，从任务开始到最终回复，页面自上而下完全按后端事件产出顺序（start → thought → action_tool → observation → chunk → final，异常/控制事件穿插其中，顺序定义见 1.5/1.7）连贯自然流出，不打断、不跳跃。
- 去全部框框：所有步骤不再有边框卡片，不再有"💭 思考""🧠 推理""下一步""工具调用"等明显分块标签；视觉区分完全靠字体样式（灰色斜体=思考、黑色正文=回复）、缩进、颜色，靠对话节奏自然流转。
- 后端事件流驱动：实时 = SSE 逐事件生长流水线；回放 = DB step_json 按 seq 顺序重放同一流水线。前端只按事件流排布，不自己造结构。
- 显示什么样、回显就什么样：实时与回放共用同一套流水线渲染函数，视觉元素与布局零差异。

##### 3.7.2 对话界面整体结构

- 对话区纵向排布：用户消息在上、AI 流水线在下，多轮交替。
- 一条 AI 流水线自上而下由两段构成：
  - 头部·模型标识：极弱化灰色小字（模型名，取 start.display_name，start 缺失用 final.display_name 兜底），提示本次回答来源；无边框、无头像卡片。
  - 正文流：思考流（灰色斜体）↔ 工具行（内联弱化）↔ 思考流 ↔ … ↔ 最终回复（黑色正文），完全按事件流生长。
- token 消耗展示（去消息尾部，文档2 4.5.3 定案）：消息尾部不再显示 token 小字；单任务 token 动态累计进任务信息条（usage 逐次累加）、终值入右侧查看区底部静态统计块（final.accumulated_usage），前端只渲染不自算（文档2 4.5.3/6.2.15）。
- 去框框范围：AI 侧全部无边框；用户消息沿用现有对话气泡样式（对话惯例，不在本设计改动范围）。

##### 3.7.3 各事件类型的流水线呈现（严格按后端字段契约）

按事件逐类设计（字段以 1.6 契约为准，行号以核实源码为准）：

###### 3.7.3.1 start（模型标识）

- 呈现：模型标识小字放流水线最上方（display_name）。注：start 不再呈现安全拦截——`security_check` 空占位字段**已定案待实施清理**（文档2 6.1.13/6.2.14；现状 sse_events.py:136/148-153 仍保留参数与组装、调用方传空 `{}`），真实安全拦截在 HITL confirm 链路（authorization_required/paused 内联确认，见 3.7.3.9），不在 start 呈现。
- 不再显示"🤔 AI 正在思考..."占位卡片（sse.ts:1163 现文案废弃）；start.content（用户消息回显）不重复显示——用户消息在对话界面本就可见。
- 模型不在列表（config_error）场景：后端随后直接下发 final(outcome=failed, config_error)（stream_orchestrator.py:156-166），前端按 3.7.3.6 failed 渲染。

###### 3.7.3.2 thought（思考段）

- 字段：content/thought/reasoning/tool_name/tool_params。
- 呈现：灰色斜体文字自然流出，无框、无标签，成为流水线中的"思考段"。
- 行动声明（tool_name/tool_params）不单独展示，由随后的 action_tool 工具行呈现（3.7.3.4），thought 只贡献思考文本。
- 与 chunk(is_reasoning=true) 的合并：同一轮思考，chunk 先逐段流出灰色斜体思考流，thought 到达时其 reasoning 与已流出文本同源（问题 2.7），不重复追加（合并规则见 3.7.6）。

###### 3.7.3.3 chunk（流式）

- is_reasoning=true：思考流片段，灰色斜体逐字流出（延续 MessageContent ChunkRenderer 既有灰度斜体约定），与 thought 合并为同一思考段。
- is_reasoning=false：最终回复片段，黑色正文逐字流出（打字机效果）。
- 流式光标：流出中的文本末位显示闪烁光标，流结束后消失。

###### 3.7.3.4 action_tool（工具行）

- 字段：content=""、tool_name、tool_params、execution_status、execution_result、action_retry_count、execution_time_ms。
- 呈现：内联弱化一行小字 "→ 调用工具 {tool_name}"，紧跟在其思考段之后，缩进与字号弱于正文：
  - 执行中（实时）：行尾显示"…"，流水线在此短暂停留；
  - 完成：按 execution_status 显示状态符号（成功不标、失败"⚠"、warning"!"）；
  - 重试次数 action_retry_count>0：行尾极弱化小注"（重试 N 次）"。
- 整行可点开展开执行结果：再次点击收起。展开区无边框、缩进弱化文字，复用既有 ToolResultRenderer 对 execution_result.llm_data 的渲染逻辑（去掉边框卡片包装）。默认收起，保持流水线轻量。

###### 3.7.3.5 observation（并入工具行展开区）

- 字段：content(首条 summary)、llm_data[]、tool_result、other_data、parallel_results。
- 呈现：不单独占流水线一行——并入紧邻 action_tool 的展开区（与 execution_result 同源，见 3.1 治理首选方案）。并行多工具（parallel_results）时，每个 action_tool 工具行对应一个展开区，llm_data[] 按索引 1:1 匹配。
- 回放兜底：老数据缺 execution_result 时，展开区回退显示 observation 的 summary/content 弱化文本。
- 现状 obsStep.observation 死分支（问题 2.6）在新模式下彻底不渲染，随 3.7.8 删除。

###### 3.7.3.6 final（终态正文 + 状态）

- 字段：content=response、response、thought、outcome、error_type、error_message、display_name、accumulated_usage。
- outcome=completed：response 作为最终回复黑色正文；若前面已有 is_reasoning=false 的 chunk 流式正文（同源），不重复渲染，chunk 无正文时由 final 补上；token 消耗不在消息尾部显示（去消息尾部 token，文档2 4.5.3 定案：任务信息条动态累计 + 静态统计块终值）。
- outcome=failed：显示可读正文（response/thought 内容）+ 下方一行弱化警示文字（error_message；若已由 error 事件展示则不重复）。
- outcome=cancelled：保留已流出内容 + 一行弱化"已取消"。
- model/provider/display_name：与 start 同源，只取一次放流水线头部。

###### 3.7.3.7 error（警示行）

- 字段：error_type、error_message。
- 呈现：流水线中一行弱化警示文字（如"⚠ 工具确认超时，已跳过：xxx"），无框。error 后若任务继续（工具被拒/超时跳过），流水线继续生长；若任务终止，后随 final(outcome=failed) 收尾。

###### 3.7.3.8 usage（token 用量，事件契约与存储本文档定，展示归文档2）

- 字段：content=""、prompt_tokens/completion_tokens/total_tokens（react_cycle.py:398-407，每轮 LLM 响应 emit 本次三值、单任务逐次累加）。
- 事件契约：见 1.5.14 / 1.6（MetaStep(type="usage")）；**不落 chat_message_steps.step_json**（Meta 步骤不入业务存储，token_usage 独立表承载，见 10.3）。
- 呈现：**不进流水线正文视觉**。前端展示口径以文档2 4.5.3 / 6.2.15 为准（北京老陈 2026-08-15 定案：前端实施归文档2 6.2）：任务信息条动态实时累计（usage 逐次累加）、右侧静态统计块终值（final.accumulated_usage，同口径），消息尾部不再显示 token；前端不再消费 PerformanceMetrics 流式估算。

###### 3.7.3.9 paused（暂停，两种来源）

- HITL 工具确认（paused 带 confirm_id/tool_name/params/safety_level，action_handler.py:240-248）：内联提示行 + 文字式操作按钮（无框）——"需要确认执行工具 {tool_name}：〔允许〕〔拒绝〕〔信任本次会话〕"，与工具行同样弱化内联。确认后流水线继续、该工具行随后呈现；拒绝/超时后跟 error 警示行（action_handler.py:271-282）。
- 用户手动暂停（content="任务已暂停"，task_runtime.py:120）：弱化小字"任务已暂停"插在当前流水线位置，已流出内容冻结。

###### 3.7.3.10 resumed（恢复）

- HITL 授权后（content="已临时授权白名单外路径…"，action_handler.py:292-296）：弱化小字记录后流水线继续。
- 用户恢复（content="任务已恢复"，task_runtime.py:138）：弱化小字"任务已恢复"，流水线继续生长。

###### 3.7.3.11 retrying（重试）

- 字段：content、wait_time(可选)。
- 呈现：弱化小字"LLM 请求异常，准备重试…"（react_cycle.py:609-613 / answer_handler.py:140-145），之后继续思考流；重试达上限后 error/final 结束。

###### 3.7.3.12 cancelled（取消）

- 字段：取消为终态、由 FinalStep(outcome="cancelled") 承载（response="任务已取消"，agent_runner.py:205-216 取消分支 + finally 守卫 L246-276 补发；react_cycle.py 取消 L583-586，2026-07-18 重构后终态不再用 MetaStep(cancelled)，与文档2 6.1.14 定案一致）。
- 呈现：弱化小字"已取消"收尾（按 final 的 outcome 渲染取消态，前端不依赖独立 cancelled 事件渲染终态），流水线终止；已流出内容完整保留。

##### 3.7.4 流式过程与终态呈现

- 思考流打字机：灰色斜体文本逐字流出，末位闪烁光标；工具行执行中行尾"…"（或轻旋转小图标，无框）。
- 事件衔接无缝：事件与事件之间无卡片空隙、无分块空隔，仅靠字体/颜色/缩进区分段落。
- 终态定格：final/error/cancelled 到达后光标消失、流水线定格为最终形态。

##### 3.7.5 交互设计

- 工具行展开/收起：点击整行切换；展开区无边框、缩进弱化文字；默认收起。
- HITL 授权确认：内联文字式按钮（允许/拒绝/信任本次会话），确认后从流水线移除提示行（回放时该确认步骤在事件流中已不存在，流水线由事件流重建，故"移除"与回放天然一致）；拒绝后跟 error 行。
- 滚动跟随：流式过程中用户未手动滚动时自动滚到底部，手动滚动后暂停跟随。
- 取消/暂停控制：沿用现有对话页控制按钮（不在本设计改动范围），流水线按 3.7.3.9/3.7.3.12 呈现状态。

##### 3.7.6 回放一致性（同一套渲染）

- 同一个渲染函数：实时（SSE 逐事件增量构建流水线数组）与回放（DB step_json 全量按 seq 组装）喂给同一个 PipelineRenderer，事件元素与布局完全一致，实现"显示什么样、回显就什么样"。
- 思考合并规则一致：实时与回放都按"chunk 思考流 + thought 完整思考合并为同一思考段（同源文本去重）"规则渲染；回放时 DB 无 chunk 思考流（非流式 LLM、老数据）则直接用 thought 文本作为思考段（即 2.7 的 thought 兜底价值，在新模式下统一进思考流，无卡片）。
- 工具展开兜底一致：回放缺 execution_result 时展开区显示 observation 的 summary/content 弱化文本（3.7.3.5）。
- 断线续传（after_seq）：已渲染部分不重绘，从断点 seq 继续生长，同一渲染函数天然支持（列表末尾 append）。

##### 3.7.7 边界情况

- 安全拦截：start 不承载安全检查字段（security_check 空占位**已定案待实施清理**，文档2 6.1.13/6.2.14），真实安全拦截在工具执行前由 `tools/security` 域 / HITL confirm 链路承担（见 3.7.3.9 authorization_required → paused 内联确认）。
- 空思考/非流式推理：无 chunk(is_reasoning=true) 思考流时，thought 直接作为完整思考段（灰色斜体）呈现。
- 无回复直接失败：无正文、final(outcome=failed) 时，流水线显示 error_message 弱化警示行收尾。
- 纯工具任务：思考→工具→思考→工具反复，最终回复短或空；流水线以工具行序列为主体，final 收尾。
- 多轮对话：每轮"用户消息 + AI 流水线"为一组，轮次间以自然间距分隔（非卡片、非分隔框）。
- 模型不在列表（config_error）：start 后直接 final(outcome=failed)，流水线头部模型标识 + 失败警示行。
- HITL 超时：paused 提示后等待超时，跟 error 警示行（"确认超时未响应"），流水线继续。

### 5 存储现状与逻辑原则

#### 5.1 存储数据逻辑原则（总纲）

> 本节是第三部分存储设计的**总纲**：数据分两类载体——**DB**（结构化、需查询、需回放）与**文件**（tool 证据链 + conversation_history，排查/审计副本）。边界由"需求驱动"（记录历史 + 历史信息查看 + 调试排查），不由代码现状驱动。

**载体一：DB（必进）——两条铁律**

1. **需查询/聚合/关联 → 必进 DB**：会话/任务/消息/步骤骨架、`token_usage`，一切需要 SELECT/GROUP BY/JOIN 的结构化数据。进 DB 才能按会话/任务/模型/事件四维度统计、随会话级联清理。
2. **前端展示 + 回放重建共用 → 必进 DB**：`execution_result.llm_data`（30+ Renderer 与回放共用）。回放若读文件，每次多轮上下文重建都产生文件 IO 放大，且文件一清理回放即断链。**回放保真的数据源固定为 DB**（治理首选方案 3.1：由 `execution_result` 派生 observation 文本，零新增字段）。

**载体二：文件（tool 证据链 + conversation_history）——记录历史 + 调试排查**

LLM 调用相关的完整数据（调用参数与输出的详细数据）借用现状 prompt-logs 已实现的方法（`log_observation` 的"内容/原始内容"双字段模式，见 prompt_logger.py），正式化为**两个按任务组织的文件**（存放位置见下方"组织与存放位置"），供历史查看与调试排查：

- **文件A：tool 参数 + 原始结果表** `tool_raw_{task_id}_{message_id}_{start_time}.jsonl`（存放于任务目录 `~/.omniagent/files/{session_id}/{task_id}/` 内；**文件名必须带时间 + 消息ID**：`task_id`=任务 ID、`message_id`=该任务对应用户消息的 chat_messages.id、`start_time`=任务开始时间戳，时间戳在名称尾部，北京老陈 2026-08-15 定案）：每行一条 tool 执行（行首 `step_id`=对应 DB 步骤主键 `chat_message_steps.id`；同一 DB 步骤含多 tool 并行时加 `tool_no` 递增区分）——`params_raw`（LLM 原始 response 参数）、`params_final`（修正后实际执行参数，**双列保留修改痕迹**；LLM 参数大部分无需修正、少数经 repair_warning 截断修复）、`raw_output`（工具执行原始结果，不截断）、`llm_data`（结构化展示字段**全量保留**，不截断）。定位=DB 中 `execution_result` 的**不截断完整副本**（同源数据的两份载体）：DB 存截断版供展示/回放，文件A 存全量版供排查/比对。
- **文件B：conversation_history（给 LLM 的全面数据消息流）** `conversation_history_{task_id}_{message_id}_{start_time}.jsonl`（同存于任务目录 `~/.omniagent/files/{session_id}/{task_id}/` 内，命名同文件A：带 task_id + 消息 id + 开始时间戳，时间戳在名称尾部）：给 LLM 的全面数据落文件、**消息粒度、按消息加入时间顺序存放、每条消息只写一行（零冗余）**——完整覆盖每次 LLM 调用喂进去的全部 messages：`system`（最初的 prompt，含 system 指令）、`user`（用户每一轮输入）、`assistant`（含 function call 与最终回复）、`tool`（tool 结果 observation，`merged_obs` 全文含 repair_warning 前缀与异常包装，不截断）。数据源=message_builder 中喂给 LLM 的 `conversation_history`（messages 数组，**构建处 = message_builder.py:233-254 `prepare_messages_for_llm`（L243 逐条复制 + L245-246 追加 temp_history）；L124-144 仅为 `add_tool_result` 单点追加，非完整数组**）逐消息落盘的排查副本，与 2.1 所述同一份 messages。每行标注 `call_no`（该消息**首次加入上下文**时的 LLM 调用序号）+ `msg_seq`（文件内消息顺序号，**与 1.x 的 SSE 事件 seq 无关**）；还原"第 N 次 LLM 调用看到的内容"= `call_no ≤ N` 的消息按 `msg_seq` 连续前缀。

**文件A/B 与 DB 的关系（副本定位）**：展示与回放**只信 DB**（数据源固定，见载体一铁律2）；文件A=DB `execution_result` 的不截断副本；文件B=实际发送给 LLM 的确切消息全文快照（system prompt 全文、未截断 `merged_obs` 等 DB 结构化/截断版无法完整还原的内容）。两文件均仅供排查/审计，**绝不作为回放/展示数据源**；回放保真仍走 DB（3.1 治理首选方案由 `execution_result` 派生 / 4.1.3 保真兜底 `observation_text`），文件B 只供人审排查、不替代。

**与《会话任务前后端架构设计2.0》chat_messages 的跨文档互指（同源不同载）**：文档2 3.1.3 的 `chat_messages`（含 `chat_tasks.user_input/response` 快照）是**给人看的对话记录**——会话页气泡、历史列表的**权威源**（结构化、可查询、可聚合）；本文件B `conversation_history_{task_id}_{message_id}_{start_time}.jsonl` 是**给 LLM 看的确切输入快照**——本 DB 存不全/存不了的内容（system prompt 全文、未截断 `merged_obs`），落文件仅供排查。两者同一次执行过程、同源不同载：一个进 DB 给人查、一个落文件给排查，互不冲突。另注：yield 与落库本即同一份 step_dict（1.1 双路分发，逐事件落库）；start 为唯一例外只 yield 不落库（stream_orchestrator.py:154 旁路，模型标识由 final 步骤补齐落库）。

**组织与存放位置**：根目录 `~/.omniagent/files/`（与 DB 同根、用户级持久），按**会话/任务两级目录**组织——`~/.omniagent/files/{session_id}/{task_id}/` 一个任务一个目录，目录内两个文件；**文件名必须带时间 + 消息ID（北京老陈 2026-08-15 定案）**：`tool_raw_{task_id}_{message_id}_{start_time}.jsonl`（文件A）/ `conversation_history_{task_id}_{message_id}_{start_time}.jsonl`（文件B），三个标识 = 任务 ID / 任务对应用户消息 chat_messages.id / 任务开始时间戳（**时间戳在名称尾部**）。文件名全三标识可预测、全局唯一、可平滑演进对象存储（路径即键）。DB 在**任务/会话级**存文件目录根引用 `{"$dir": "files/{session_id}/{task_id}/"}`（具体文件名由 `task_id`/`message_id`/`start_time` 三标识按模板推导，无需重复落库），action_tool 步骤存 `{"$file": "tool_raw_{task_id}_{message_id}_{start_time}.jsonl", "step_id": <chat_message_steps.id>}` 定位点；排查路径=任务级引用 → 文件A（按 `step_id` 定位具体 tool 行）→ 顺链文件B（按 `call_no`/`msg_seq` 看该次 LLM 调用喂进去的完整上下文）。

**文件头元信息**：每个文件首行 header 记 `session_id`/`task_id`/时间范围/模型/服务商/schema 版本，供排查快速定位与版本兼容。

**旁路写入原则**：文件A/B 写入是**旁路（异步、尽力而为）**，写失败只降级排查能力、**不得阻塞主链路**（DB 落库/SSE 推送）；主链路对文件写入零等待。

**与 prompt-logs 的关系（不复用，并行过渡后取消）**：现状 prompt-logs（prompt_logger.py）是同源的人审调试日志——文件名 uuid+timestamp 不可预测、DB 无引用、无生命周期 GC，只供人工排查，**不复用**；本设计的正式文件存储是新建机制，仅**借用其 jsonl 写法**（`log_observation` 的"内容/原始内容"双字段模式已在正式文件A/B 中落地：文件A=params_raw/final + raw_output + llm_data 全量，文件B=全部消息类型的 conversation_history）。过渡策略：**两套并行运行一段时间**，待正式文件存储（文件A/B + DB 引用 + GC）验证稳定后，**取消 prompt-logs**，避免双写长期重复。

**GC 联动**：文件A/B 与 DB 会话级联同生命周期——任务/会话删除或按保留策略清理时，级联删除对应文件，不产生孤儿文件。

**分流边界一句话**：需查询/聚合/关联、前端展示与回放共用 → **DB**；tool 证据链（参数 raw/final + 原始结果 + llm_data 全量）→ 文件A（DB 的不截断副本），给 LLM 的全面数据（system/user/assistant/tool 消息流按时间序）→ 文件B（conversation_history），均作排查/审计副本；回放保真数据源固定 DB。

- append_execution_step（storage.py:325-334）：每步独立事务写 chat_message_steps（截断 → safe_json_dumps → INSERT）。
- finalize_message（storage.py:353-358）：finally 轻量终态：UPDATE content/status/thought。
- load_execution_steps（storage.py:337-350）：读侧从新表组装，无数据回退 chat_messages.execution_steps 旧列（兼容）。

调用关系（agent_runner.py）：
- 每产出一步：`append_execution_step`（agent_runner.py:179-188，ai_message_id 首次经 allocate_and_insert_message 分配）
- 异常分支：final 步也立即落库（agent_runner.py:231-234）
- finally 守卫补发 FinalStep（agent_runner.py:246-276）→ `finalize_message`（agent_runner.py:305-306）
- ai_message_id 未分配兜底：`save_steps` 整批写（agent_runner.py:307-310）
- IntegrityError 不重试（UNIQUE，YAGNI）（agent_runner.py:312-314）

依赖方向（2026-08-13 P4 重构）：agent_runner 不再直接 import chat 模块，6 个持久化回调由 stream_orchestrator 以 `db_ops` SimpleNamespace 注入（stream_orchestrator.py:171-183），依赖方向 chat→agent 单向。

#### 5.6 渐进耐久设计

- 每步独立事务 → 崩溃时已产出步骤不丢；finally 只做轻量终态更新。
- 启动迁移：migrate_steps.py 一次性把旧 execution_steps 列数据迁移到 chat_message_steps（schema_migrations 守卫），启动从 25s→<1s。

#### 5.7 存储层截断机制（storage.py:252-322）

- MAX_TOOL_RESULT_ITEMS = 1000：列表超 1000 条截断（storage.py:255）。
- MAX_TOOL_RESULT_STR_LEN = 100000：单字符串超 10 万字符截断并附加「原长 N 字符」标记（storage.py:256, 307-322）。
- _truncate_tool_result（storage.py:258-273）：递归截断过大的列表（2026-08-13 #9 修复 list 内嵌超长 list）。
- _truncate_tool_result_strings（storage.py:307-322）：递归截断所有超长字符串（base64/长文本）。
- _truncate_step_dict（storage.py:276-298）：作用对象：`tool_result` / `execution_result` / `parallel_results[].tool_result / execution_result`（不碰 observation）。
- storage.py:254 标注：「实验性的功能: TODO 做正式的持久化设计后进行更新」——本设计文档即该 TODO 的正式落点。

> 阈值依据（2026-07-23 北京老陈驱动）：各 tool 已自行截断输出，storage 仅做安全兜底防 SQLite 行溢出（约 1MB TEXT 上限），不做激进取舍。

#### 5.8 现状存储形态：同一工具结果两处存放（问题根源）

ActionStep（action_handler.py:656-663）：
```python
ActionStep(step, tool_name, tool_params, execution_result=result, execution_status=_ec)
```
存完整 `execution_result` = {data, llm_data, other_data} 3 字段。

ObservationStep（action_handler.py:817-823）：
```python
ObservationStep(step, llm_data=llm_data_list, tool_result=…, other_data=merged_other, parallel_results=_parallel_results or None)
```
又存一遍 `llm_data`(列表) + `tool_result` + `other_data` + `parallel_results`。

提取过程（action_handler.py:781-800）：从每个 result 重新拆 `_all_llm_data/_all_tool_results/_all_other_data/_parallel_results`，同一份数据第二份副本。

### 6 问题

#### 6.1 双重存储（核心问题）

同一工具结果存两份——ActionStep.execution_result（完整 3 字段，action_handler.py:656-663）与 ObservationStep.tool_result/llm_data/other_data/parallel_results（action_handler.py:786-800、817-823）。后果：
- 库膨胀：大工具结果（文件列表、搜索全文）双份持久化，chat_message_steps 体积翻倍；
- 写 I/O 翻倍：每步截断 + dumps + INSERT 处理两份数据；
- 字段漂移风险：两处口径一旦不同步（如某 tool 改返回结构），前端读 execution_result、回放读 observation，出现不一致；
- 截断双重处理：_truncate_step_dict 需同时兜底 execution_result 与 observation 的 tool_result/parallel_results（storage.py:282-297），复杂度与漏截风险高。

#### 6.2 截断机制未定案

storage.py:254 临时 TODO「实验性的功能」未正式化；截断范围（哪些字段）与阈值（1000/100000）无正式设计依据背书。

### 7 更好的方案（一删、一治本、一收敛）

#### 7.1 动作清单

##### 7.1.1 删四字段

删 ObservationStep 四字段：`tool_result`/`llm_data`/`other_data`/`parallel_results`。理由——单一权威副本=ActionStep.execution_result；前端渲染本就全从 execution_result 取（第二部分 1.8 节），删除无退化。独立安全落地；若启用保真 observation_text（第二部分），其"加"须建立在本次"删"之上（单向依赖，纯加会冗余）。

##### 7.1.2 治本删二次拆包

`build_observation` 内 `action_handler.py:781-800` 的二次拆包（重循环 `ctx.results` 拆 `_all_llm_data/_all_tool_results/_all_other_data/_parallel_results`）删除，ObservationStep 直接复用 ActionStep 已持有的 `execution_result`（或第一轮循环结果）。理由——双存储的根因是"同一份 result 被拆两遍"，仅删字段只堵出口、二次拆包代码仍残留；根治须让 ObservationStep 引用已产出副本，消除冗余拆包与算力浪费。

##### 7.1.3 截断对象收敛

截断对象收敛为仅 ActionStep.execution_result。理由——observation 已删 tool_result，截断只需兜底 execution_result 一处。

##### 7.1.4 保真口径

`observation_text`（保真兜底时）对已截断 execution_result 派生、原样落库，不二次截断。理由——两源天然同口径，无需"是否截断"双轨；tool 层已自行截断故无膨胀，DB 行溢出风险已由 execution_result 截断兜底覆盖（原 TODO 本为防 SQLite 行溢出）。

##### 7.1.5 删临时 TODO

删 storage.py:254 临时 TODO，引用本设计文档。理由——消除「实验性」残留，正式定案。

##### 7.1.6 保留 content（summary）

ObservationStep 保留 content（summary）用于前端展示。理由——前端 observation 步骤展示总结文本（第二部分 1.8 节修正后改读 observation_text/content），不重复取数。

#### 7.2 收敛后存储形态

- ActionStep.execution_result：完整权威副本（截断兜底对象）；首选方案下回放由其重新派生 observation，零新增字段。
- ObservationStep.observation_text（仅保真兜底时）：喂 LLM 的完整 observation 文本，对已截断 execution_result 派生、原样落库，不二次截断（两源天然同口径）。
- ObservationStep.content：summary 展示文本；
- 其余（tool_result/llm_data/other_data/parallel_results）不再入 ObservationStep，随 execution_result 单一存放；`build_observation` 内二次拆包代码同步删除（治本）。

#### 7.3 不做

- 不新增 is_success/summary 冗余字段（llm_data.status.exec_code 已是权威源）；
- 不新建独立 observation 表（step_json 已结构化，无需第三张表）；
- 不拆多条步骤（保持一行=一步的既有契约）；
- 不"只加不删"（纯加 observation_text 会让冗余从 4 个字段增至 5 个）；"删四字段"本身独立安全、可单独落地（7.1.1 删四字段），与是否加保真字段无耦合。

#### 7.4 影响面核对

- 前端 30+ Renderer 全从 execution_result.llm_data 取数 → 删 observation 内冗余字段不影响；
- StepContent.tsx observation 分支：删除 `obsStep.observation` 死分支，改为读 `observation_text`/`content`（第二部分 2.6）；
- _parse_observations：首选方案下由 execution_result 重新派生；保真方案下优先读 observation_text 回退 content，回放质量增强；
- _truncate_step_dict：删 observation 相关分支（tool_result/parallel_results），仅保留 execution_result；
- react_cycle 终态语义、derive_status_from_steps（storage.py:71-83）、load_execution_steps 均不受影响。

### 10 token 消耗统计（四维度归属落库）

#### 10.1 需求（北京老陈提出）

token 消耗归属**四个维度**统计：哪个模型、哪个会话、哪个任务、哪个事件（每次 LLM 调用）。事件粒度取"每次流式响应（一次 action/answer 产出）记一条 usage：prompt/completion/total + model"，落库可逐条查询。

#### 10.2 现状（已核实）

| 维度 | 现状 | 缺口 |
|------|------|------|
| 事件（每次 LLM 调用） | react_cycle 内逐次累加进 accumulated_usage，emit MetaStep(type="usage") 带本次三值 | **不落库**，逐条明细丢失 |
| 任务 | TASK_END 带 usage_tokens（agent.accumulated_usage 累计值） | 仅总量，无逐次明细 |
| 会话 | 无会话级 token 记录 | 跨任务不可聚合 |
| 模型 | 无模型级 token 记录 | 无法按模型对比消耗 |

现有数据来源：
- 每次 LLM 调用：`llm_response.get("usage")`（react_cycle 第 388 行提取，三字段逐次累加）。
- 任务累计：`agent.accumulated_usage`（base_agent.py），TASK_END 输出（stream_reader）。
- 前端展示：归文档2 4.5.3 / 6.2.15（任务信息条动态累计 usage、静态统计块终值 final.accumulated_usage、顶栏会话链聚合），3.7.3.8 已对齐（北京老陈 2026-08-15 定案：前端实施归文档2 6.2）。

#### 10.3 方案：新增 token_usage 落库表

**目标**：每次 LLM 调用落一行，四维度皆可查询。

**表结构**（chat_history.db 新增，db_initializer 注册）：

```
token_usage
├─ id             INTEGER PK AUTOINCREMENT
├─ session_id     TEXT NOT NULL        -- 哪个会话
├─ task_id        TEXT NOT NULL        -- 哪个任务
├─ model          TEXT NOT NULL        -- 哪个模型
├─ provider       TEXT                 -- 服务商
├─ prompt_tokens  INTEGER DEFAULT 0    -- 本次调用 prompt
├─ completion_tokens INTEGER DEFAULT 0 -- 本次调用 completion
├─ total_tokens   INTEGER DEFAULT 0    -- 本次调用 total
└─ created_at     TEXT                 -- 时间戳
```

索引：`session_id`、`task_id`、`model` 各建索引（按会话/任务/模型聚合查询）。

**落库点**：react_cycle 的 usage 处理处（现第 388 行起，提取 `_usage` 后累加处）追加一次 INSERT。同一位置已有 `MetaStep(type="usage")` 产出与累加逻辑，落库与现逻辑同源，不新增数据流。INSERT 使用 get_conn（数据库访问机制见 5.4）。

**session_id/model 来源**：session_id 由 stream_orchestrator 传入（现 TASK_END 已用）；model/provider 从 llm_response 或 agent 配置取（start 步骤已产出模型标识，同源）。

#### 10.4 四维度查询

| 维度 | 查询口径 |
|------|---------|
| 哪个事件 | 按 task_id 查 token_usage 明细（每次 LLM 调用一行） |
| 哪个任务 | GROUP BY task_id，SUM 三字段 |
| 哪个会话 | GROUP BY session_id，SUM 三字段（跨任务聚合） |
| 哪个模型 | GROUP BY model，SUM 三字段（跨会话/任务聚合） |

聚合结果经 API 暴露给前端（与会话页设计文档 4.5.1 信息分布矩阵的顶栏消费点对应，真实值以本表 SUM 为准）。

#### 10.5 与 3.7.3.8 的关系（不冲突）

- 3.7.3.8 事件契约：usage 事件不进流水线正文视觉——**展示**口径归文档2 4.5.3 / 6.2.15（任务信息条动态累计 + 静态块终值），3.7.3.8 已对齐。
- 本表是**存储与统计**口径：补全 3.7.3.8 无法提供的四维度查询（明细/任务/会话/模型聚合）。
- 两处同源（同一次 usage 数据），一个走展示、一个走统计，不重复展示。

#### 10.6 不做

- 不拆前端实时逐条上报（usage 由后端 react_cycle emit、前端消费展示，见文档2 4.5.3 / 6.2.15；本文档只定义事件契约与落库）。
- 不做 token 计费/限额（YAGNI，超出统计范畴）。
- 不落 usage 到 chat_message_steps.step_json（Meta 步骤不入业务存储，与 1.1.1 阶段一机制一致，token_usage 独立表承载）。
- 不落 stats / context_overview 到 chat_message_steps.step_json（同为 Meta 步骤不入业务存储，流式瞬时值；历史回放统计由任务详情接口从 chat_message_steps 按 task_id 重建，见文档2 6.1.6③）。
