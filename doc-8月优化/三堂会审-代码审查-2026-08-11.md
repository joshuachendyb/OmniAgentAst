### 2.2 P1 问题(重要, 影响功能正确性)

#### P1-1: operation_rollback MOVE/CREATE/COPY/COMPRESS回滚分支未长路径化

**提交**: 7b9bda1e7
**文件**: `backend/app/services/safety/operation_rollback.py` L65-97
**发现人**: 三堂会审

**病根**: MODIFY/DELETE分支(L50-63)已用`to_win_long_path`处理超长路径, 但MOVE/CREATE/COPY/COMPRESS四个分支仍用普通`Path.exists()`/`Path.rename()`/`shutil.rmtree()`/`Path.unlink()`。超长路径(>260字符)时`Path.exists()`返回False→回滚静默跳过。

**病因**: 长路径化提交(7b9bda1e7)聚焦MODIFY/DELETE(有备份的恢复链路), MOVE/CREATE/COPY/COMPRESS(无备份的撤销链路)遗漏。

**影响**:
- MOVE: `dest_path.exists()`对超长dst返回False→不执行rename→文件留在dest无法移回src→**数据丢失风险**
- CREATE: 超长dst的created文件/目录残留→**空间泄漏**
- COPY/COMPRESS: 超长dst的copied/compressed文件残留→**空间泄漏**

**证据**: 同文件L53已用`to_win_long_path(Path(backup))`, L56-58连续3处`to_win_long_path`, 但L68-97完全未用。

**关联逻辑**: copy_file防嵌套(992e64ab7)场景会产生深嵌套目录, 路径极易超260→备份成功但回滚时MOVE/COPY分支静默失败→**防嵌套+长路径闭环断裂**。

**修复方法(已三堂会审确认; 复核补全: 2026-08-11 remove_readonly 需导入)**:

**当前影响**: 无。所有调用者(operation_backup/cleanup/record/rollback)均传入绝对路径(tool参数经validate_path保证)。
**修复方法**:

```python
def to_win_long_path(path: Path) -> str:
    r"""Windows长路径 \\?\ 前缀, 绕过MAX_PATH(260)限制 — 小欧 2026-08-11
    仅NT系统生效; 已带前缀或非绝对路径保持原样。
    """
    if os.name != "nt":
        return str(path)
    s = str(path)
    if s.startswith("\\\\?\\") or not Path(s).is_absolute():
        return s
    return "\\\\?\\" + s
```
