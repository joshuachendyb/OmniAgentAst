### 4.2 真病根一：命令本身语法错误（尾逗号）—— 已复现铁证

- 350a05a5 卡死命令中的数组 **`'E:\test_dir\all_processes.csv',` 末尾多了一个逗号**：
  ```powershell
  $files = @(
      'E:\test_dir\all_processes.csv',      ← 尾逗号 = PowerShell 语法错误
  )
  ```
- **PowerShell 不允许数组尾逗号**（Python/JS 允许，LLM 按后两者习惯生成）：
  - 实测 `@('x','y',)` → `ParserError: Missing expression after ','`
  - c6e4386c 则因 `python -c "..."` 内嵌引号/转义在 PS 脚本上下文解析失败（`tmp4e044vy6.ps1:1`）

### 4.3 真病根二：引擎 ParserError 假超时漏洞（真正让"卡死"的元凶）—— 双向复现铁证

| 执行方式 | 同一语法错误命令 | 结果 |
|------|------|------|
| 裸跑 `.ps1`（`pwsh -File`） | `$a = @('x','y',)` | **0.68s 立即返回** rc=1 + ParserError（不卡） |
| 真实引擎 `PersistentShell.exec()` | 同命令 | **11.77s 空等 timed_out=True（假超时）** |

**机制根因**（shell_engine.py:433-443 的 ps_cmd 结构）：
- 命令被内联进 `& { try { <command> } catch { ... } }`，但 **ParserError 是 PowerShell 解析期（编译期）错误**，发生在 try 块**进入之前** → `catch`（只抓运行期异常）**接不住**
- 于是写 rc 文件的那行（`$global:rc | Out-File code`）**永不执行** → `_poll_for_file`（shell_engine.py:466）轮询 rc 文件直到 timeout（60s）
- 与文件头 B6.1 **BUG#4 同类**（"throw 终止性错误中断 ps_cmd → rc 文件不写 → 假超时"）；`_fix_ps7_assignment_operators`（execute_shell_command.py:360）只修了 `&& $env:X=` 一种 ParserError 面，尾逗号等其余语法错误面未覆盖

### 4.4 结论修正

- **"包装"本身正确**（C4 修复，防多行命令经 stdin 卡死，2026-07-18），**不应去除**。
- 真问题 = LLM 命令语法错误（尾逗号/引号嵌套）+ 引擎对"解析期错误"无快速失败机制 → 假超时 60s。
- 引擎有界超时护栏（C8/C14）能兜底不强杀永久死锁，能自恢复（step=47 立起新进程）；但**假超时 60s 是真实体验缺陷**，应修复。
- **修正方法（diff）详见 §十。**

## 十、问题二修正方法（diff）—— 引擎 ParserError 快速失败

> **背景**：北京老陈 2026-08-08 指令"先落到文档，把修正方法尤其是 diff 的修正方法写完整准确了"。以下修正方案已**逐条实证**（真实 pwsh 引擎跑通），非纸面推断。

### 10.1 修正目标

让 `shell_engine.py` 遇到 **PowerShell 解析期（编译期）错误**（ParserError）时**立即返回 build_error**，不再空等 60s 假超时。方案基于实证：**解析期错误在"命令独立文件 + dot-source 外层 try/catch"结构下可被捕获**（现测 rc=1、err=ParserError 原文、0.x 秒返回）。

### 10.2 方案对比（为何选方案二）

| 方案 | 做法 | 结论 |

| 方案三（预检） | Python 侧 `[System.Management.Automation.Language.Parser]::ParseInput` 语法预检 | 每命令多起一次进程/调用，成本高；且预检结论与实跑易不一致（PS 解析上下文差异） |

### 10.6 普遍意义论证（北京老陈 2026-08-08 指示"有无普遍意义"—— 结论：有，覆盖一整类而非单点）

> **本修复不是"尾逗号特判"，而是针对"命令不可解析"这一整类问题的通用解法。**以下为普遍性论证。

**① 机制通用（对所有 ParserError 生效，非特判）**

本次仅撞见 2 种 ParserError（数组尾逗号、`python -c` 引号嵌套），但 ParserError 是**大类**：

| ParserError 类别 | 示例 |
|------|------|
| 数组尾逗号 | `@('x','y',)` |
| 引号未闭合/嵌套错误 | `"unterminated string` |
| 括号不匹配 | `(1+2` |
| 花括号不配对 | `foreach ($x in $y) {` |
| 操作符错误 | `1 +* 2` |
| 非法表达式/关键字拼错 | `ifif ($x) {}` |

**只要命令解析失败，旧内联结构一律假超时 60s；新 dot-source 结构全部统一 0.x 秒快速失败。**一把钥匙开一类锁。

**② 提炼通用设计原则（根本价值）—— "rc 落盘无条件化"**

本修复与 BUG#4（throw 终止性错误假超时）**同族同根**，合并后揭示一条铁律：

> **引擎必须保证 rc 落盘"无条件化"** —— 命令无论**成功 / 执行失败 / 解析失败 / 终止性异常**，rc 文件都必须在有界时间内写出。任何让 rc 文件不写的路径都是假超时温床（C8/C14 只能兜底 60s，是体验缺陷）。

方案本质：把"命令解析时机"从**框架编译期**（旧：内联进 ps_cmd 字符串，解析即崩）移到**框架运行时 catch 内**（新：dot-source 延迟解析，catch 统一兜底）→ 框架对一切命令失败有统一快速失败路径。

**③ 普遍性的边界（诚实标注，不夸大）**

| 场景 | 覆盖 | 依赖 |
|------|------|------|
| 一切解析期错误 (ParserError) | ✅ | 本方案 |
| 运行期非终止错误 | ✅ | B6.1 errs 分类 |
| 运行期终止错误 (throw) | ✅ | BUG#4 |
| **语法正确但死循环/挂起** | ❌ | 依赖 C8/C14 timeout（另一条线，属问题一 c1e4603c） |

即：**"命令不可用"已系统性覆盖；"命令能用但跑不完"仍靠超时兜底** —— 二者互补，非替代。

**④ 结论**：该修复具**普遍工程意义**，值得落码并沉淀为引擎级设计原则（供 shell_engine 后续维护/新人复用）。
