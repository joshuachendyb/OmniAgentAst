## 一、需求与要求（基于现状的升级设计）

本文档是**基于当前现状的升级设计**：以现有会话页与后端数据实现为起点，做 2.0 升级。现状是升级的基线（可复用、不推倒重来）；设计允许按目标演进（如数据库结构按"会话 → 任务 → 消息 → 步骤"演进，见第三章），但升级范围、依赖、兼容都围绕现状展开。

### 1.1 升级基线：当前现状

**后端现状（详见 3.4）：**

- 数据库：`chat_sessions` / `chat_messages` / `chat_message_steps` 三表，`db_initializer.py` 初始化，`_ensure_column` 幂等补列。
- 会话服务：`session_service.py` 提供 create / list / update / delete，`version` 乐观锁，标题历史有写入但无读取方（现状存在、设计不建表，见 3.1.5）。
- 任务生命周期：TASK_START / TASK_END 日志承载任务级信息（后端日志，非 SSE 事件）。

**前端现状（详见 4.1）：**

- 会话页 NewChatContainer 硬编码三块布局（标题区 / 消息区 / 输入区），模型切换在全局顶栏。
- 状态层 hooks/chat 已按"门面 + 分域"拆 8 个 hook，可复用不推翻。
- 渲染器 ToolResultRenderer 已是"类型 → 渲染器"注册表，消息流水线直接复用。

### 1.2 升级需求（待解决的问题）

1. **布局写死**：新增功能面板（文件、知识库、上下文等）需要改骨架，不是"加一块"。
2. **模型全局化**：无法按会话/按任务选择模型，多 Provider 混排、A/B 对比、按任务选模型都做不了。
3. **展示与设计定案脱节**：《数据存储及yield前端消息及数据设计》3.6 已定案流水线式展示，当前仍是分步卡片形态。

### 1.3 升级要求（设计目标）

1. 会话页骨架支持**插槽化面板注册**，加功能不动骨架。
2. 模型选择支持**三层继承覆盖**（全局默认 → 会话级 → 任务级）。
3. 消息主列按**事件流流水线**渲染（呼应《数据存储》3.6 定案）。
4. 输入区**组件化**，为多模态与命令面板留口。

### 1.4 扩展性需求（设计目标之一，供审核）

扩展性围绕"**可加、可演进、不破坏**"三原则展开。这里不用表格，把每个扩展点"解决什么问题、应对什么潜在需求"用文字讲清楚，方便审核它是否必要、是否正确。

**前端：骨架可插、类型可扩。** 现状布局写死，加一个功能面板就得改骨架（对应 1.2-①）；渲染器虽是"类型 → 渲染器"注册表，但主列还是分步卡片、与新定案流水线脱节（对应 1.2-③）。扩展上做两件事：一是**插槽化面板注册**（4.2.2 SessionPanelRegistry），未来文件、知识库、上下文等新面板即插即用，不动骨架；二是**渲染器注册表复用**（4.3.2），未来新增步骤 / 工具类型只注册一个渲染器即可零侵入接入。这解决的是"加东西要动老结构"的痛点，潜在需求是面板和事件类型会持续增多。

**模型：三层继承，可混排、可对比。** 现状模型是全局的，无法按会话、按任务选择（对应 1.2-②）。扩展上做**三层继承覆盖**（5.1 / 5.2）：全局默认 L1 → 会话级 L2 → 任务级 L3，解析链固定、新增服务商只加配置。这解决的是"模型选择维度太粗"的痛点，潜在需求是多 Provider 混排、同一条消息不同模型重跑做 A/B 对比、按任务选快/强模型，以及未来的会话级限额与模型路由——这些都能挂在这条解析链上，不用改骨架。

**后端数据：表结构对新增属性友好。** 现状给表加一个非结构化属性就要 ALTER TABLE，改表有破坏风险。扩展上做三件事：一是三张核心表（会话 / 任务 / 消息）各留一个 **metadata JSON 扩展列**（3.1.1 / 3.1.2 / 3.1.3），会话偏好、任务标签、消息附注这类还没定型的属性即插即用；二是**步骤表用 step_json 开放结构**（3.1.4），新步骤类型只扩展 JSON schema、不加列；三是 **role / status 这类枚举用 TEXT 开放值域**（3.1.3 / 3.1.2），将来出现 system / function 角色、新状态值都不用改表。这解决的是"新增属性要动表结构"的痛点，潜在需求是属性与事件类型会随产品演进持续增加。

**数据演进：能分析、能升级、不破坏。** 现状会话累计 token 无法按维度聚合，容易拿单任务值冒充会话累计。扩展上新增 **token_usage 明细表**（3.1.6），每次 LLM 调用一行，按会话 / 任务 / 模型任意维度聚合，未来的成本审计、模型用量、时间维度分析都直接消费它；同时**所有字段新增走幂等补列**（3.5.7），旧库平滑升级、回滚安全、旧数据零破坏。信任清单按 **tool_name 行存**（3.1.7），新工具自动纳入信任管理、可单个撤销。

一句话收口：以上扩展点分别解决"加面板改骨架、选模型太粗、加属性要改表、成本没法分析、升级怕破坏"五个痛点，且都有明确的落点章节；扩展性不另立章，统一体现在数据库表结构与前端骨架中。

## 二、核心概念定义（必读，全文以此为准）

> ⚠️ 本设计一切"维度"表述以本章定义为准，不得混用。会话与任务是两个不同的数据维度，贯穿全文（4.2.4 侧栏、5.1 模型层级、4.5 信息分布、4.5 token 分工）。本章用叙述方式定义二者的内容与关系，不讲表格，只讲清楚它们各是什么、各含什么。**4.2.4 侧栏、4.5 信息矩阵、4.5 token 分工里出现的每一个信息点，都必须能在本章定义里找到出处——本章是全文信息唯一的权威清单。**

### 2.1 会话（session）

会话是一个**对话空间**。一个会话从用户新建对话空间开始，一直存在下去，中间可以进行很多次对话，每一次对话就是一次任务。会话本身不执行任何东西，它是任务的容器，把发生在它里面的所有任务按时间顺序装在一起。

会话的基本属性分两级：**核心属性**（会话成立的骨架，缺一不可）与**支撑属性**（服务于核心属性的其他一切属性）。

#### 2.1.1 会话的核心属性：记录对话/任务 + 历史任务

会话的核心属性，就是"**记录**"——把发生在这个对话空间里的一切按时间记录下来，形成历史任务。核心有两个，缺一不可：

- **记录对话/任务**：这个对话空间里用户和 AI 之间往来的一切（对话记录），每一次对话、每一条消息都顺序落在其中，构成整个对话空间的正文。
- **历史任务**：会话里按时间顺序装下的所有任务（一串 `task_id`）。

记录里离不开"消息"，本文统一三种含义，不再混用（三者关系见 2.3）：

- **用户消息**：用户发起对话时发出的那一条，与任务是一一对应的触发源（发一条用户消息 → 生成一个 `task_id`）。
- **AI 消息**：某次任务执行结束后 AI 回复的正文（final 的结果），归属那次任务。
- **消息数**：会话内全部消息的条数（用户消息 + AI 消息），是会话级的聚合计数，不含过程中的 thought / action / observation 等步骤。

#### 2.1.2 会话的支撑属性

会话的其余属性，全部服务于"记录 + 历史任务"这个核心：

- 会话的标识（`session_id`）：支撑"历史任务"——一个对话空间唯一，是历史任务的归属锚点。
- 会话标题：支撑"记录"——这个对话空间的名字。
- 会话的时间（创建时间、最后更新时间）：支撑"历史任务"——会话何时建立、最后活动于何时。
- 会话的规模（任务数、消息数）：支撑"历史任务"——装了多少任务、多少消息。
  - 任务数（对话次数）：用户发起过多少次对话（多少个任务）。因"一条用户消息 = 一个任务"，所以任务数 = 用户消息数。
  - 消息数（message_count）：会话内全部消息（用户消息 + AI 消息）。因每次任务通常产出一条 AI 消息，所以 消息数 ≥ 任务数；任务失败/取消时 AI 消息缺省，该任务仅一条用户消息，此时消息数 = 任务数（仍是 ≥ 的下界，与 3.1.3 / 3.3 口径一致）。
- 会话的累计消耗（会话累计 token）：支撑"历史任务"——跨任务聚合的累计成本，来源于 token_usage 按 session 聚合。
- 会话的配置：支撑"后续任务执行"——会话级模型覆盖（model_override，即模型三层的 L2，见 2.3）、本会话信任的操作清单（chat_session_trust，见 4.6）。
- 会话的上下文：支撑"记录的连续性"——当前上下文摘要（对会话历史的浓缩描述）、裁剪状态。

##### 2.1.2.1 会话字段级技术属性清单（据源码核实）

会话直接对应 `chat_sessions` 表，并关联 `chat_messages` / `chat_message_steps`；累计 token 来自 `token_usage` 按 session 聚合。字段如下：

| 属性 | 值域 | 来源 | 说明 |

| 标题历史 | list | ~~chat_session_title_history~~（**设计不建**，见 3.1.5） | 现状仅写入无读取（死数据），按 YAGNI 不建；会话当前标题由 chat_sessions.title 承载 |

### 2.2 任务（task）

任务是一次**对话**。在会话这个对话空间里，用户每发起一次对话（发出一条用户消息），后端就为这次对话生成一个 `task_id`，启动一次 Agent 执行（`run_react_cycle()`）。这一次执行从 start 事件开始，经过一轮轮"思考、调用工具、看结果"的循环（loop），最终以 final 事件结束（后端另打 TASK_END 日志标记收尾，仅日志、非事件）。**一次对话就是一个任务，会话里有多次对话，就有多个任务。**

任务的内容分两块：**业务内容**与**基本属性**；其中"基本属性"附一份字段级技术属性清单作为落地明细（见 2.2.2.1）。

#### 2.2.1 任务的业务内容

也就是这一次对话里 AI 究竟做了什么、回了什么：

- 任务本身，就是用户发来的那一条用户消息（任务输入），它是这一次对话的起点，start 事件里带着它。
- AI 响应的全部信息，也就是整个 loop 的过程信息——每一轮思考（thought）、每一次工具调用（action）、每一条观察结果（observation）、流式输出的一段段文本（chunk），这些过程信息按顺序串起来，就是这一次对话的执行过程。
- 任务的结果，就是 AI 最终给出的回答（final 事件里的 response，即 AI 消息），连同它结束时的状态。

#### 2.2.2 任务的基本属性

任务的基本属性分两级：**核心属性**（任务成立的骨架，缺一不可）与**支撑属性**（其余一切属性，全部为核心属性服务、支撑，不脱离核心独立存在）。

**核心属性（3 个）：**

- `task_id`：任务 ID，一次对话唯一，结束后不复用。
- 用户输入消息：触发本任务的那一条用户消息。
- AI 响应消息：本任务最终给出的回答正文。

一句话：**任务 = `task_id` + 用户输入消息 + AI 响应消息**（用户输入消息与 AI 响应消息的完整刻画见 2.2.1）。

**支撑属性（全部服务于核心三要素）：**

- 模型（model/provider/display_name）：支撑"AI 响应消息"——是谁执行出这条响应的（L3 覆盖落点，见 2.3 与第五章）。
- 时间（开始/结束/耗时）：支撑"任务"——何时执行、花了多久。
- token 消耗（accumulated_usage）：支撑"任务"——耗了多少。
- 步骤（steps/步骤数/轮次/工具统计）：支撑"AI 响应消息"——是怎么一步步执行出来的。
- 状态（生命周期 executing/completed/failed/cancelled + 执行中 paused/resumed/retrying）：支撑"任务"——进行到哪一步、最终去向。
- 归属（session_id）：支撑"任务"——发生在哪个对话空间。
- 辅助（重试次数/security_check/错误信息/任务产出物）：支撑"任务"——执行途中的重试、安全检查、失败原因、产出物。

支撑属性的字段级清单见 2.2.2.1。

##### 2.2.2.1 字段级技术属性清单（依据当前源码核实）

任务在运行时不是一个单一对象，它的技术属性分散在三处生产者——TASK_START / TASK_END 日志、步骤流 execution_steps、agent 运行期。总表如下，标注字段、值域与来源：

### 2.3 会话、任务与消息的关系

一句话讲清楚：**会话是一个对话空间，里面装着一串任务；一次对话就是一个任务，多次对话就是多个任务，任务在会话里按时间先后发生。**

- 一个会话含多个任务：在对话空间里，每发起一次对话，就生成一个新 `task_id`，做一次独立执行。
- 每个任务必须归属一个会话：`task_id` 和 `session_id` 同时存在（TASK_START 日志成对打印），不存在脱离会话的任务。
- **"消息、任务、会话"三角对应**（收口 2.1 定义的三种"消息"）：
  - 用户消息与任务一一对应，是任务的触发源（一个用户消息 → 一个 `task_id`）。
  - AI 消息归属某个任务，是那次任务的结果正文。
  - 消息数是会话内全部用户消息 + AI 消息，是会话级聚合计数。
  - 一句话：**用户消息触发任务，任务产出 AI 消息，会话装下全部任务和消息。**
- **模型三层与维度的映射**（详见第五章）：全局默认（L1，系统级）→ 会话级覆盖（L2，session 的 model_override）→ 任务级覆盖（L3，为该条用户消息对应的一次执行临时指定，重跑场景）。维度上：L1 系统级、L2 会话级、L3 任务级，与本章两种维度严格对应。解析顺序见 5.2。
- **"当前/最近任务"的锚定**：会话含多个任务，侧栏"任务执行面板"展示的是当前/最近一次任务——锚定规则：优先取会话内尚未终态（executing）的任务；若都已终态，取时间上最后结束的一个。
- 维度归类铁律：
  - 会话级（session 维度）是跨任务聚合的：会话标题、任务数、消息数、会话累计 token、会话级模型配置、信任清单、上下文状态。
  - 任务级（task 维度）是单次对话（单次执行）内的：执行状态、任务耗时、步骤数、轮次数、工具统计、单任务 token、错误信息、重试次数、任务产出物。
  - 禁止把任务级信息标成"会话级"，也禁止把单任务 token 当成会话累计 token。

这就是本设计所有"维度"表述的依据。后面凡提到"会话级 / 任务级"，指的就是上面这两套内容各自的范围，不再混用。

## 三、后端设计（数据与数据库）

会话任务系统的后端，核心是**数据与数据库**：会话、任务、消息、执行步骤这些都落库为可查询、可聚合的数据。`chat_sessions` / `chat_tasks` / `chat_messages` / `chat_message_steps` / `chat_session_trust` / `token_usage` 等表及其关联（`chat_session_title_history` 按 YAGNI 不建，见 3.1.5），字段级定义已在第二章 2.1.2.1 / 2.2.2.1 给出，本节从"数据库与存储、聚合"的角度收口后端设计。

### 3.1 数据库表结构（设计，按"会话→任务→消息→步骤"四级）

> 本设计按"会话 → 任务 → 消息 → 步骤"四级层级组织数据库表：**会话不存储消息**，消息挂在任务下面。本节为设计目标，与现状源码的差异见 3.4。

**扩展性与发展性设计要点（数据库表级）**：①步骤表 chat_message_steps 以 `step_json` 开放结构承载任意步骤类型，新增类型不加列（见 3.1.4）；②三张核心业务表（chat_sessions / chat_tasks / chat_messages）预留 `metadata` JSON 扩展列，未来非结构化属性即插即用，避免频繁 `ALTER TABLE`——**使用边界**：metadata 只承载"尚未定型、无需查询/索引"的非结构化属性（如会话侧偏好、任务标签、消息附注）；一旦某属性需要被查询、聚合、索引，应升级为正式列（走 `_ensure_column` 幂等补列），不得长期躺在 metadata 里；③任务表以 user_input / response 冗余快照独立可读、token_usage 按维度聚合，新增统计不牵动主链路；④字段新增遵循 `_ensure_column` 幂等补列（可空 / 默认），旧库旧数据零破坏（迁移路径见 3.5.7）。扩展性与发展性不另立章，统一体现在下表结构中。

#### 3.1.1 chat_sessions：会话表（不存储消息）

**干什么的**：一个对话空间的容器，只存会话本体信息（标题、时间、状态、版本），**不存储任何消息**。任务经 session_id 归属它，消息经任务归属会话。

| 字段 | 类型 | 说明 |
|------|------|------|
| session_id | TEXT（PK） | 会话唯一标识 |
| title | TEXT NOT NULL | 会话标题 |
| created_at | TEXT | 创建时间（本地ISO，无Z） |
| updated_at | TEXT | 最后更新时间（本地ISO，无Z） |
| is_valid / is_deleted | BOOLEAN | 有效 / 软删除标记 |
| title_locked / title_updated_at | BOOLEAN / TEXT | 标题锁定、锁定时间 |
| version | INTEGER | 乐观锁版本 |
| model_override | TEXT（可空） | 会话级模型覆盖（模型三层 L2，见 5.1），空 = 跟随全局 |
| metadata | TEXT（可空） | 扩展属性（JSON），预留未来会话级配置 / 上下文摘要等，发展性兼容列，不破坏表结构 |

消息数、累计 token 是聚合值，不由会话表存储（见 3.3）。

#### 3.1.2 chat_tasks：任务表（会话里面的任务）

**干什么的**：会话里面的一次次对话，一行一个任务。由用户消息触发，记录**任务内容（任务输入 user_input + 任务结果 response）** + 任务执行的状态、时间、模型、token、步骤摘要等全部任务级属性（对应第二章任务基本属性 2.2.1/2.2.2）。

| 字段 | 类型 | 说明 |
|------|------|------|
| task_id | TEXT（PK） | 任务 ID，一次对话唯一 |
| session_id | TEXT（FK，ON DELETE CASCADE） | 所属会话（删会话级联删任务，见 3.1.8） |
| user_message_id | INTEGER（FK） | 触发本任务的那条用户消息 |
| user_input | TEXT | **任务输入（用户消息内容）**——任务内容之一（来源 TASK_START 日志，见 2.2.1） |
| response | TEXT（可空） | **任务结果正文（AI 消息内容）**——任务内容之一（来源 final 步骤，见 2.2.1），失败/取消时可空 |
| status | TEXT | 生命周期状态：executing（进行中）/ completed / failed / cancelled（终态）；paused 等运行期态见 Meta 小事件，不落本字段 |
| start_time / end_time / duration | TEXT / TEXT / FLOAT | 开始、结束、耗时 |
| provider / model / display_name | TEXT | 生效模型信息 |
| accumulated_usage | JSON | 单任务 token（prompt/completion/total） |
| llm_call_count / total_steps | INTEGER | LLM 调用次数 / 步骤总数 |
| error_type / error_message | TEXT | 失败原因 |
| retry_count | INTEGER | 重试次数 |
| max_steps | INTEGER | 最大步骤数限制（agent 运行期参数，落库为任务级上限） |
| created_at | TEXT | 创建时间 |
| metadata | TEXT（可空） | 扩展属性（JSON），预留未来任务级标签 / 统计等，发展性兼容列，不破坏表结构 |

#### 3.1.3 chat_messages：消息表（任务下面的消息）

**干什么的**：它是**"对话聊天的消息流"**——会话页里展示的一个个气泡，每行 = 一条消息（role=user 用户发的 / role=assistant AI 回的，content 为正文）。一个任务含一条用户消息（触发任务）+ 一条 AI 消息（结果正文；任务失败/取消时 AI 消息缺省，此时任务仅一条用户消息）。消息归属任务（task_id），不直接归属会话。

**与上下表的关联（一条链）**：

```
chat_sessions（会话）──< chat_tasks（任务）
                              │  ← 消息.task_id 挂这里（任务必须归属会话）
                              └─< chat_messages（消息）
                                     │  ← 步骤.message_id 挂这里
                                     └─< chat_message_steps（步骤）
```

一句话记忆：**消息挂任务，任务挂会话，步骤挂消息。** 会话是最外层容器，步骤是最内层细节。

**与 chat_tasks 的内容冗余关系（重要）**：一个任务 = 两次消息（你的 user_input 触发任务、AI 的 response 返回结果，两条消息共用同一 task_id）。因此同一份内容出现两处：

| 存储位置 | 存的内容 | 角色 |
|---------|---------|------|
| chat_messages.content | 消息流里这条消息的正文（role=user / role=assistant） | **权威数据源**（会话页渲染、历史回放主数据） |
| chat_tasks.user_input / response | 任务输入与任务结果正文 | 冗余快照（让任务表**不 join 也能独立读出**任务内容） |

> 结论：`chat_messages.content` 是权威，`chat_tasks.user_input/response` 是任务表为独立可读而保留的快照。两者同源，落地时写入点一致（user_input 取 TASK_START 的 user_input、response 取 final 的 response，与消息落库同源），禁止背道而驰。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER（PK）自增 | 消息 ID |
| task_id | TEXT（FK，ON DELETE CASCADE） | 所属任务（消息挂任务，关联 chat_tasks.task_id；删任务级联删消息，见 3.1.8） |
| session_id | TEXT | 冗余，便于会话级查询 |
| role | TEXT | user / assistant（AI）；TEXT 列可扩展 system / function 等新角色值，不改表结构（发展型） |
| content | TEXT NOT NULL | 消息正文（权威） |
| timestamp | TEXT | 消息时间（本地ISO，无Z） |
| display_name | TEXT | 模型显示名 |

#### 3.1.7 chat_session_trust：会话信任清单表（**设计新增**）

> ⚠️ 本文档按"会话级"新增此表，**现状不存在**。需先讲准现状才不误导：现状信任 = `grant_temp_auth`（temp_auth.py）——是 **task 级**临时授权、**内存态**（ContextVar）、**task 结束 clear_temp_auth 清零**，且授权对象是**路径**（`Path → recursive`）而非工具名；`hitl_confirmation.py` 的 `trust_session` 只是一枚 HITL 应答布尔，**不落任何表**。因此现状**没有"按会话持久化某工具信任"的能力**，本表是为此能力提供的会话级落库方案。

**干什么的**：把"用户在本会话内勾选信任的操作（工具名）"**按会话（session_id）持久化**，使该会话内的后续任务（跨 task）复用信任、不再反复弹 HITL 确认框，且可从侧栏随时撤销（撤销 = 删行）。**价值**：相比现状——①现状信任随 task 结束即失效、无法跨任务复用；②现状"勾选信任"后无撤销入口（缺陷）；③现状无持久化、进程重启即丢。本表补齐这三点成为会话级可持续能力。

**与会话 / 任务的关系（准确）**：
- **归属方 = 会话（session 维度）**：字段 `session_id`（FK → chat_sessions.id），逻辑是"我信任**这个会话**里的这个工具"，一个会话可信任多个工具（一行一个）。
- **消费方 = 任务（task 维度）**：每次任务执行到高危工具时，按该任务所属 session 查此表判断"是否已信任、要不要再弹 HITL"；表本身不存任务，任务通过 `session_id` 关联使用它。
- 一句话：**信任按会话存、按任务用**；与会话是归属关系、与任务是消费关系。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER（PK） | 记录 ID |
| session_id | TEXT（FK） | 所属会话（归属维度），ON DELETE CASCADE |
| tool_name | TEXT NOT NULL | 被信任的工具名 |
| created_at | TEXT | 信任时间 |

> 说明：本表按 **tool_name** 行存（非路径、非整表一个 JSON 数组），配合 4.6 侧栏"信任的操作清单"按 session 读写撤销；具体到工具的"精确路径授权"仍由现状 `grant_temp_auth` 在 task 内承担，二者各司其职、不冲突。

#### 3.1.8 各表之间的关系（哪条线靠哪个字段挂钩）

**一张图看懂全部关联（每条线都标了挂钩字段）：**

```
chat_sessions（会话）
   │   ← chat_tasks.session_id  →  chat_sessions.id
   │   ← chat_session_trust.session_id → chat_sessions.id
   ▼
chat_tasks（任务）
   │   ← chat_messages.task_id  →  chat_tasks.task_id（消息挂任务）
   │   ← token_usage.task_id    →  chat_tasks.task_id（token 记任务）
   ▼
chat_messages（消息）
   │   ← chat_message_steps.message_id → chat_messages.id（步骤挂消息）
   ▼
chat_message_steps（步骤）
```

**一句话记忆：消息挂任务（task_id）、任务挂会话（session_id）、步骤挂消息（message_id）。** 会话是最外层容器，步骤是最内层细节。

**逐条说明：**

1. **四级层级，逐级一对多（核心链）**：会话 1─< 任务 1─< 消息 1─< 步骤。**会话不存储消息**——消息挂在任务下面（chat_messages.task_id → chat_tasks.task_id），经任务归属会话（chat_tasks.session_id → chat_sessions.id）。会话页读一个会话的消息 = `chat_messages JOIN chat_tasks ON task_id WHERE chat_tasks.session_id = ?`。
2. **任务由用户消息触发**：chat_messages 中 role=user 的用户消息触发任务（chat_tasks 加一行，chat_tasks.user_message_id → chat_messages.id）；任务结果（AI 消息，role=assistant）也落 chat_messages，归属同一 task_id。
3. **token 挂任务**：token_usage.task_id → chat_tasks.task_id（按 task 聚合 = 单任务，按 session 聚合 = 会话累计）。
4. **信任挂会话**：chat_session_trust.session_id → chat_sessions.id，ON DELETE CASCADE。
5. **删除级联**：删会话 → 级联删其任务、消息、步骤、信任清单（标题历史表按 YAGNI 不建，见 3.1.5）；删任务 → 级联删其消息与步骤。
6. **索引**：chat_tasks 按 session_id；chat_messages 按 task_id / timestamp；chat_message_steps 按 message_id 与 (task_id, step_index)；token_usage 按 session_id / task_id / model（对齐《数据存储》9.3），并建议补 created_at 索引支撑时间维度聚合（发展型分析）；chat_session_trust 按 session_id。

### 3.2 会话、任务、消息、步骤的存储关系

- **会话不存消息**：会话表只有本体；消息挂在任务下，经任务归属会话。
- **任务 = 一次对话**：用户消息触发任务，任务表一行；任务结果是 AI 消息（chat_messages 中 role=assistant），归属该任务。
- **步骤挂消息**：任务的执行过程落 chat_message_steps，每条消息一段步骤序列。
- **会话累计 token 独立聚合**：token_usage 表按 session 聚合（跨任务 SUM），不靠消息数推算。

### 3.3 数据聚合：任务数、消息数、累计 token

| 聚合值 | 维度 | 口径 | 数据来源 |
|--------|------|------|---------|
| 任务数（对话次数） | 会话级 | chat_tasks 行数（一条用户消息 = 一个任务） | chat_tasks 按 session 统计 |
| 消息数 | 会话级 | 会话下全部任务的消息（用户 + AI；失败/取消时 AI 消息缺省，该任务仅一条用户消息，此时消息数 = 任务数，仍满足消息数 ≥ 任务数） | chat_messages 经 task 归属会话统计 |
| 会话累计 token | 会话级 | 跨任务 SUM（不得用单任务值替代） | token_usage 表按 session 聚合 |

### 3.4 后端实现现状与设计差异

- **现状**：`db_initializer.py` 建 `chat_sessions` / `chat_messages` / `chat_message_steps` 三表 + 索引，`_ensure_column` 幂等补列（message_count / is_deleted / is_valid / status / thought 等）；会话服务 `session_service.py` 提供 create / list / update / delete，`version` 乐观锁，标题历史虽有写入（`record_title_history`）但无读取方（死数据，设计不建其表，见 3.1.5）；任务生命周期靠 TASK_START（provider/model/task_id/session_id/user_message_id/user_input）与 TASK_END（task_id/end_type/duration/llm_calls/usage_tokens/total_steps）日志打印，均为后端日志、非 SSE 事件。
- **现状与设计（3.1）的差异**：现状中消息与任务同落 `chat_messages`（status/thought 等任务属性也在该表）、会话表冗余 message_count；本设计按"会话 → 任务 → 消息 → 步骤"四级拆分——任务属性上收为独立任务表（chat_tasks）、消息表只留消息、会话表不再存消息与聚合值。该差异是设计演进方向，落地时按 3.1 表结构迁移。

**② chat_session_trust（会话信任清单表，设计新增）**

**干什么的**：把用户在本会话内勾选信任的高危工具（tool_name 一行一条）**按会话持久化**，该会话后续任务（跨 task）复用信任免弹窗、可从侧栏随时撤销（撤销 = 删行，见 4.6）。

**维度关系（准确）**：**归属 = 会话**（session_id FK → chat_sessions.id，"我信任这个会话里的这个工具"），**消费 = 任务**（任务执行时按所属 session 查表决定是否要再弹 HITL，表本身不存任务）。一句话：**信任按会话存、按任务用**。

**与现状的关系**：现状信任 = `grant_temp_auth`（temp_auth.py）是 **task 级内存临时授权**（task 结束清零、授权对象是路径），`trust_session` 仅一枚 HITL 应答布尔、不落库——**现状无本表**，本表是会话级持久化、可撤销、跨 task 复用的设计新增，补齐现状三点缺口（跨任务失效 / 无撤销入口 / 进程重启丢失）。

| 字段 | 处置 | 说明 |
|------|------|------|
| id | 新增 | 记录 ID |
| session_id | 新增 | 所属会话（归属维度，FK → chat_sessions.id，ON DELETE CASCADE） |
| tool_name | 新增 | 被信任的工具名 |
| created_at | 新增 | 信任时间 |

关系：**会话 1─< 信任清单**（一个会话可信任多个工具，每个工具一行）；删会话级联删其全部信任项。按 tool_name 行存（非整表一个 JSON 数组），新增工具自动纳入信任管理、单个撤销，是扩展性设计（见 3.1.7）。

**③ token_usage（token 用量明细表，新增）**

**干什么的**：记录**每次 LLM 调用**的 token 用量（每次调用一行，一个任务多次调用 → 多行，对齐《数据存储》9.3）；是"会话累计 token"的唯一聚合来源（按 session 跨任务 SUM），杜绝用单任务值冒充会话累计。

| 字段 | 处置 | 说明 |
|------|------|------|
| id | 新增 | 明细记录 ID |
| session_id | 新增 | 所属会话（→ chat_sessions.id） |
| task_id | 新增 | 归属任务（→ chat_tasks.task_id） |
| model | 新增 | 本次调用模型 |
| provider | 新增 | 服务商 |
| prompt_tokens / completion_tokens / total_tokens | 新增 | 本次调用三种 token 计数 |
| created_at | 新增 | 记录时间 |

关系：**任务 1─< token_usage**（一个任务多次 LLM 调用 → 多行）；token 挂任务，按 task_id 聚合 = 单任务 token，按 session_id 聚合 = 会话累计 token，按 model 聚合 = 模型级消耗（见 3.1.6 与《数据存储》9.3 / 9.4）。

#### 3.5.7 迁移要点

1. 新增表（chat_tasks / chat_session_trust / token_usage）直接 `CREATE TABLE IF NOT EXISTS`。
2. chat_sessions 删 message_count：先确保统计路径（3.3）就绪再删，避免前端列表空值。
3. chat_messages 删除列：`status`/`thought`/`execution_steps`/设备遥测列属 SQLite 无法直接 DROP COLUMN（低版本），落地按"新建表复制 + 改名"或逐列保留弃用二选一，原则是**前端与查询路径先切到新结构**，再物理清理。
4. 新增列（model_override / metadata）一律可空、默认为 NULL，沿用现状 `_ensure_column` 幂等补列（可空类型），旧行旧数据不报错、零破坏——属**发展性兼容列**，未来加字段沿用同一机制即可。

#### 4.2.4 侧栏面板清单（职责体系化）

> 会话（session）与任务（task）两个维度的完整定义见第二章，本节直接引用：会话 = 对话空间（含多个任务，跨任务聚合），任务 = 一次对话（一次执行，单次对话内数据）。

侧栏不是一块内容，而是**五个可独立开关/折叠的面板**，各自职责单一（SRP），互不耦合：

| 面板 | 维度 | 内容 | 数据来源 | 开关时机 |
|------|------|------|---------|---------|
| 会话概览 | 会话级 | 会话标题、任务数（对话次数）、消息数、会话累计 token（跨任务聚合）、创建/更新时间 | chat_tasks 按 session 统计（任务数）+ chat_messages 统计（消息数）+ token_usage 表按 session 聚合（累计 token） | 常驻，默认展开 |
| 任务执行 | 任务级 | 当前任务执行状态徽标、任务耗时、步骤数、轮次数、工具统计（各工具调用次数）、错误信息（失败时）、重试次数、任务产出物 | 前端流式统计 + FinalStep（accumulated_usage 为单任务值） | 任务进行中，默认展开，任务结束保留最近一次 |
| 模型配置 | 会话级 | 当前生效模型 + 来源徽标、三层继承的「跟随全局/指定模型」切换 | session model_override | 常驻，默认收起 |
| 信任的操作清单 | 会话级 | 已信任 tool_name 列表，可撤销 | chat_session_trust 表（见 4.6） | 有信任项时提示，默认收起 |
| 会话上下文 | 会话级 | 当前上下文摘要、剪裁状态（触发剪裁时可见）、可挂载知识库 | message_builder 统计 | 默认收起，剪裁时提示展开 |

- 侧栏整体可折叠；五面板在侧栏内用 Collapse 或 Tab 呈现，各面板开关状态随会话持久化。
- 任务执行面板显示的是**当前/最近一次任务**（task_id 维度），任务完成后切换展示最近一次；跨任务聚合统计（累计 token 等）归会话概览。
- 会话概览 + 任务执行是"信息充分准确"的核心载体，其余面板按需展开，不挤占空间。

### 4.3 消息主列：流水线渲染（呼应《数据存储》3.6 定案）

#### 4.3.1 原则

主列不做分步卡片，按后端事件流顺序自然流出，实时与回放同一套渲染（与《数据存储及yield前端消息及数据设计》3.6 一致）。

#### 4.3.2 渲染器注册表复用

沿用 ToolResultRenderer 的「类型 → 渲染器」注册表：
- chunk / thought / action / observation / final / error 各注册渲染器，DefaultRenderer 兜底。
- 流水线顺序 = 事件 seq 顺序，不做分组重排。

#### 4.3.3 与 ExecutionPanel 的关系

ExecutionPanel 保留为「底部面板」提供步骤级详情（可折叠），主列流水线只呈现自然流。两者同源（同一事件流），形态不同：主列是"看过程"，面板是"查明细"。

**步骤量大的处理（防止面板无限变长）：**

现状缺陷：ExecutionPanel 对 steps 全量渲染（steps.map），无分页、无虚拟滚动、无高度上限，result 又按"不截断完全显示"要求完整输出——步骤几十上百步 + 长 result 时，底部面板会被撑得极长，挤占主列。

对策（KISS，不引入 react-window 等重依赖）：

1. **高度可拖拽**：BottomPanel 支持拖拽调整高度（如 30%~60vh），用户拖过的高度记忆到会话本地，不写死 45vh。默认收起，执行开始时自动展开。
2. **执行中/执行完状态区分**：
   - 执行中：**自动展开最新步骤**，滚动跟随，用户实时看到过程；旧步骤自动收起为标题行。
   - 执行完：全部步骤收起为标题行（图标 + 工具名 + 耗时 + 状态），面板紧凑。
3. **轮次锚点导航（替代嵌套折叠）**：底部面板内嵌一条横向导航条——**轮次锚点**（"第 1 轮 / 第 2 轮 / …"，sticky 置顶，点击跳转到对应步骤段）+ **类型过滤标签**（全部 / 思考 / 工具 / 观察 / 结果）。不做"面板 → 分组 → 步骤"三层嵌套折叠，只两层：导航条 + 步骤列表，避免执行中连点两层。
4. **步骤可折叠**：每步默认只显示标题行，点击展开看 params / result（展开后 result 仍完整显示，不违背"不截断"要求）。
5. **不做虚拟滚动**：步骤以标题行呈现时 DOM 轻量，数百步内可承受；超过阈值（如 500 步）再评估引入 rc-virtual-list（antd 内置依赖，非新增重库）。

**主列自身长度管理（双层管控）：**

底部面板有高度管控，主列同样需要：消息流水线是对话流，单条超长内容会无限撑高主列。

1. **长 AI 消息折叠**：单轮 final 文本超过阈值（如 30 行/2000 字）时默认折叠为摘要行（首 2 行 + "展开全文"），点击展开完整内容，不截断（与"不截断"铁规一致，折叠非截断）。
2. **长 result / observation 折叠**：工具结果超长时默认收起标题行（工具名 + 结果首行摘要），点击展开；与底部面板共用同一折叠逻辑。
3. **主列滚动**：主列自身 `overflow-y: auto`，与底部面板滚动独立，互不干扰。
4. **与底部面板分工**：主列"看过程"（自然流 + 折叠摘要），底部面板"查明细"（轮次导航 + 步骤详情），两者同源不重复。

#### 4.3.4 小事件去向：主列过滤 + 底部过程状态条

**原则**：Meta 小事件（start / paused / resumed / retrying / cancelled）是过程状态，不是对话内容，**不进主列流水线**，避免打断消息流。

- 前端渲染主列时按类型过滤：只渲染 chunk / thought / action / observation / final / error，过滤 start / paused / resumed / retrying / cancelled（start 步骤虽含 model / provider 等字段，其生效模型信息由顶栏徽标承载，见 4.5.1，主列不渲染 start 本身）。
- 底部面板顶层新增**过程状态条**：小事件按时间戳滚动显示，图标 + 文案 + 时间（如 "⏸️ 任务已暂停 11:42:05"），新事件插入顶部，自然淡出或保留可清空。
- 主列过滤与小事件展示同源：同一事件流，主列取业务类型，状态条取 Meta 类型，互不重复。

### 4.5 信息呈现：信息分布矩阵 + token 三处分工

#### 4.5.1 信息分布矩阵（信息充分且准确）

会话/任务两个维度的信息统一收口，每个信息点落在明确位置、有明确来源，避免散落或重复：

| 信息点 | 维度 | 位置 | 数据来源 | 更新时机 |
|--------|------|------|---------|---------|
| 会话标题 | 会话级 | 顶栏区 | session 记录 | 创建/重命名 |
| 会话累计 token | 会话级 | 顶栏区 + 会话概览 | token_usage 表按 session 聚合（跨任务 SUM） | 每任务结束后聚合更新 |
| 会话消息数 | 会话级 | 会话概览 | chat_messages 统计 | 每消息落库后 |
| 会话任务数（对话次数） | 会话级 | 会话概览 | chat_tasks 按 session 统计（一条用户消息 = 一个任务） | 每任务结束后 |
| 会话创建/更新时间 | 会话级 | 会话概览 | session 记录 | 更新时 |
| 当前任务执行状态徽标 | 任务级 | 顶栏区 + 任务执行面板 | 前端流式状态（执行中/暂停/完成/失败/取消） | 状态变化即时 |
| 任务耗时 | 任务级 | 任务执行面板 | 前端时间戳（start~final 结束） | final 事件到达 |
| 步骤数 / 轮次数 | 任务级 | 任务执行面板 | 前端流式统计（step 数、ReAct 轮） | 实时递增 |
| 工具统计（各工具调用次数） | 任务级 | 任务执行面板 | 前端流式统计（action 分组） | 实时递增 |
| 任务错误信息（失败原因） | 任务级 | 任务执行面板 | error_type / error_message | 任务失败时 |
| 任务重试次数 | 任务级 | 任务执行面板 | 前端流式统计（retrying 计数） | 实时递增 |
| 任务产出物 | 任务级 | 任务执行面板 | 任务结果（如 report_path） | 任务结束时 |
| 单任务 token 用量 | 任务级 | 消息尾部（final 步骤） | FinalStep.accumulated_usage | final 步骤到达 |
| 生效模型 + 来源徽标 | 会话级 | 顶栏区 + 模型配置面板 | 三层继承解析结果（见五） | 模型变更即时 |
| 小事件（暂停/恢复/重试/取消） | 任务级 | 底部过程状态条 | executionSteps 的 Meta 类型 | 事件发生即时 |
| 实时速率 TTFT / tokens/s | 任务级 | 输入区性能条（流式期间） | 前端流式统计（PerformanceMetrics） | 流式期间实时 |
| 上下文摘要 | 会话级 | 会话上下文面板 | message_builder 统计 | 剪裁触发时 |
| 上下文剪裁状态 | 会话级 | 会话上下文面板 | message_builder 统计 | 剪裁触发时 |
| 待批准 HITL | 任务级 | 弹窗 + 主列高亮 | 后端 paused + confirm_id | 授权请求到达 |

**信息聚合原则**：顶栏区 = 一眼可见的核心信息（会话标题、会话累计 token、当前任务状态）；会话概览面板 = 会话级聚合（任务数/消息数/累计 token/时间）；任务执行面板 = 当前任务完整统计（状态/耗时/步骤/轮次/工具）；实时过程信息（小事件/速率）随事件流就近显示；不重复渲染同一信息点。

#### 4.5.2 token 用量显示：三处分工（区分会话/任务维度）

token 消耗按"看得见、不干扰"原则分三处显示。**会话累计（跨任务）与单任务消耗严格区分来源**：会话累计查 token_usage 表按 session 聚合；单任务值用 FinalStep.accumulated_usage（TASK_END 日志的 usage_tokens 仅供后端核对，前端消费不到）。

| 位置 | 内容 | 维度 | 数据来源 | 说明 |
|------|------|------|---------|------|
| 消息尾部（final 步骤） | 单任务 tokens：prompt/completion/total | 任务级 | FinalStep.accumulated_usage | 与模型信息同处，小字灰显，如 "🤖 deepseek-v3 | tokens 3560" |
| 顶栏常驻 | 本会话累计 tokens（跨任务） | 会话级 | token_usage 表按 session 聚合 SUM | 会话级资源总消耗，每任务结束后聚合更新 |
| 输入区性能条（流式期间） | 实时速率 TTFT / tokens/s / 实时 token | 任务级 | 前端流式统计（PerformanceMetrics 已有） | 仅流式期间显示，结束后消失，不残留 |

注意：前端当前只消费了流式估算（PerformanceMetrics），尚未消费 FinalStep 的 accumulated_usage（后端已随 final 事件下发，见《数据存储》文档 3.6.8）。本次设计必须补上这处消费。**前端单任务 token 唯一数据源 = FinalStep.accumulated_usage；TASK_END 日志里的 usage_tokens 仅作后端核对、前端消费不到，不得作为前端数据源。会话累计不得用单任务值，须按 token_usage 表（见《数据存储》文档 9.3）跨任务聚合**。

### 4.6 HITL 授权交互：阻断式弹窗 + 主列联动 + 侧栏信任清单

**原则**：高危工具操作必须让用户先决策，保持**阻断式居中弹窗**（现有 AuthorizationModal 形态不动），并做两处增强：

1. **弹窗联动主列**：弹窗打开时，主列流水线中对应 action 步骤高亮（橙色描边 + 呼吸边框），用户能一眼定位"哪条工具调用正在等批准"；弹窗关闭后高亮消除。
2. **"本会话信任"可管理**：现勾选后无撤销入口。升级为侧栏"信任的操作清单"面板，按 tool_name 列出已信任项，可随时撤销；撤销后再次执行同工具将重新触发弹窗。信任项落库 `chat_session_trust` 表（见 3.1.7），前端按 session 读写。

交互时序：工具执行触发安全确认 → 后端 paused + confirm_id → 前端弹窗 + 主列该 action 高亮 → 用户选择（允许/拒绝/勾选信任）→ 弹窗关闭、高亮消除 → 信任项写入侧栏清单。

## 五、策略设计

贯穿前后端的**策略与规则**设计：模型如何在全局 / 会话 / 任务三个层级间继承与覆盖，是本章的核心。

### 5.1 模型三层继承策略

| 层级 | 作用域 | 说明 |
|------|--------|------|
| L1 全局默认 | 系统级 | 现有顶栏 Select / Settings 管理，继承自配置文件 |
| L2 会话级覆盖 | 单个 session | 会话内独立选模型，不写全局配置，落库 session 记录 |
| L3 任务级覆盖 | 单条用户消息对应的一次执行 | 单条重跑换模型（重跑 = 新建任务，如重跑失败消息、对比效果） |

### 5.2 解析优先级

生效模型 = L3（任务级，若存在）→ L2（会话级，若存在）→ L1（全局默认）。

### 5.3 UI 表达

- 会话顶栏/侧栏显示当前生效模型 + 来源徽标：`deepseek-v3（会话级）` / `gpt-4o（继承全局）`。
- 会话级选择提供「跟随全局 / 指定模型」切换；选择会话级模型时写入 session 配置。
- 任务级覆盖（用户侧叫"消息级"：操作入口在用户消息上，消息操作菜单：重跑 → 选模型）仅在重跑场景出现，不常驻；重跑时新建一条用户消息（reply_to_message_id 关联原消息，见 3.5.4）并对这条新用户消息新建一次任务执行，仍满足"一条用户消息 = 一个任务"（见 2.3）。

### 5.4 扩展收益

1. 多 Provider 混排：不同会话用不同服务商。
2. A/B 对比：同一条用户消息用不同模型重跑，结果对照。
3. 按任务选模型：日常用快模型，复杂任务切强模型。
4. 未来成本控制：会话级限额、模型路由均可挂在此层。

## 六、与现有架构的对接

1. **状态层**：不改 hooks/chat 结构；新增模型层级解析可放 useChatFacade 门面内新增 selector，或独立 useModelLayer hook。
2. **配置层**：会话级模型落库需后端 session 表新增字段（如 model_override），任务级覆盖（消息重跑）随单次任务请求携带。后端先定契约，前端迎合后端。
3. **渲染器**：复用 ToolResultRenderer 注册表，扩类型不扩结构。
4. **骨架**：新增 SessionLayout 组件包装现有 NewChatContainer，逐步迁移，避免一次性大改。
5. **token 消费**：前端补两处——FinalStep 的 accumulated_usage 渲染到消息尾部（单任务，前端唯一数据源）；**会话累计 token 查 token_usage 表按 session 聚合**（跨任务，顶栏/会话概览）。TASK_END 日志的 usage_tokens 仅作后端核对，不作前端数据源。后端 token_usage 表与聚合 API 见《数据存储》文档 9.3/9.4。
6. **HITL 信任清单**：信任项落库 `chat_session_trust` 表（见 3.1.7），前端侧栏清单通过 API 读写；撤销 = 删记录，无需改弹窗链路。
7. **小事件过滤**：主列过滤逻辑在渲染入口按类型分流（业务类型进主列、Meta 类型进状态条），数据源仍是一条 executionSteps，不拆流。
8. **折叠与高度**：主列与底部面板共用折叠组件（长文本折叠 = 折叠非截断）；BottomPanel 高度拖拽用原生 mouse 事件 + localStorage 记忆，不引第三方 resize 库。轮次锚点由步骤流按 ReAct 轮分组生成（轮次边界以 thought/action 序列识别）。

## 七、实施优先级

| 优先级 | 事项 | 理由 |
|--------|------|------|
| P1 | 会话级模型覆盖（L2） | 收益最大、改动集中（后端 session 字段 + 前端会话级选择） |
| P1 | token 消费补全（4.5.2 三处显示） | 后端已下发数据，纯前端消费，改动小收益直观 |
| P2 | 消息主列流水线渲染 + 小事件过滤（4.3.4） | 呼应 3.6 定案，前端渲染重写 |
| P2 | 主列长度管理 + 步骤折叠（4.3.3） | 与流水线渲染同批，防长内容撑高 |
| P2 | HITL 弹窗联动主列高亮（4.6-1） | 不涉及存储，前端联动即可 |
| P3 | 插槽化骨架 + 侧栏/底部面板（含过程状态条） | 结构性改造，与 P2 可并行设计 |
| P3 | 侧栏信任清单可管理（4.6-2） | 依赖后端 session_trust 落库，与 L2 存储改造同批 |
| P4 | 任务级覆盖（L3）、附件区 | 依赖 L2/P2 落地后再做 |
