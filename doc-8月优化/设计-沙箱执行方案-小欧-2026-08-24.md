## 一、背景与目标

### 1.1 背景

当前系统安全体系（`backend/app/safety/tool_safety_checker.py`）对工具执行做三级分级（safe/destructive/dangerous），destructive 级命令走 HITL 人工确认后**直接在真机执行**。存在风险：

- 高危 shell 命令（删除、格式化、改注册表等）确认后无预演，误操作直接落真机
- LLM 生成的长命令链副作用不可预估，人工确认只能看命令文本无法看实际影响面

### 1.2 设计目标

#### G1 触发范围目标：明确哪些操作启用沙箱

**唯一触发依据**：checker 判定 **destructive 级**（即 `sandbox_required=True`），无论该次调用是否被会话信任豁免确认（豁免只跳 HITL 不跳沙箱，见 3.2.2 路径B）。对应到具体工具：

| 类别 | 工具 | 典型危险点 | 预检方式 |
|------|------|-----------|---------|
| shell 命令执行类 | `execute_shell_command`、`execute_shell_command_safety` | 删除/格式化/改系统配置/杀进程等任意命令副作用 | 沙箱内真实试执行 |
| 文件删除类 | `delete_file` | 不可恢复删除 | 影子副本预演 |
| 注册表写删类 | `registry_write`、`registry_delete` | 改坏系统注册表 | 静态影响面分析 |
| 覆盖写/解压/移动类 | `write_text_file`(覆盖非空文件)、`extract_archive`(覆盖已存在文件)、`copy_file`/`move_file`(覆盖目标) | 覆盖用户数据 | 影子副本预演 |

> 注：上表"典型危险点"是设计期归纳，**运行时以 checker 实际分级为准**——若未来某工具分级调整，沙箱触发范围自动跟随，无需改沙箱代码（复用分级的好处）。不触发的完整清单统一归口 **4.1 节**。

#### G2 预检-落地流程目标

destructive 级操作先在隔离环境试执行：通过 → 放行真机执行一次（结果以真机为准）；失败 → 错误细节反馈 LLM 自我纠正，真机零污染。

#### G3 后端可插拔架构目标

接口先行（`SandboxBackend` 协议），当前**唯一实现为轻量隔离**（与真机同 Windows 环境，预检结果真实有效）；跨平台脚本场景未来可实现容器后端接入（评估结论见 2.5.3，本方案不做自动探测）。详细策略见 2.3 节。

#### G4 架构约束目标

主干零侵入（不动 ReAct/HITL/备份回滚）、分层合规（safety 层无越层 import）、存量代码改动控制在插桩式增量（约 80 行内）。

### 1.3 本机环境约束（调研结论）

| 项目 | 现状 | 影响 |
|------|------|------|
| Docker | 未安装 | **评估后不采用**（v1.9 会审）：Windows 命令在 Linux 容器中预检结果失真（误拦/语义漂移），详见 2.5.2 排除表 |
| WSL2 | 已装（Ubuntu） | 当前方案不依赖；未来若实现跨平台脚本容器后端，可作为其底座 |
| 安全体系 | `app/safety/` 三级分级 + HITL + operation_backup 备份回滚 | 直接复用，不重建 |
| Shell 引擎 | `shell_engine.py` PersistentShell 进程池（持久 pwsh） | 沙箱预检**不走进程池**，独立 subprocess，避免污染池实例 |

## 二、总体架构设计

### 2.1 核心原则

| 原则 | 说明 |
|------|------|
| 预检不改状态 | 沙箱内执行绝不触碰真实目标路径，shell 的写操作只落在工作区内 |
| 结果以真机为准 | 沙箱只是验证器，放行后真机重新执行一次 |
| 主干零侵入 | 不修改现有 ReAct 循环/HITL/备份回滚的既有逻辑，只在 action_handler 增加两个局部函数（预检+处置）并在三处汇合点插桩（见 3.2.3） |
| 失败即反馈 | 预检失败不是终止任务，是把错误细节喂回 LLM 自我纠正 |
| 环境同构（v1.9） | 预检环境必须与真机一致（Windows），异构环境的预检结果视为无效——这是排除容器后端做自动探测的根因 |

### 2.2 执行流程全景

```
LLM 发起工具调用 (destructive级)
        │
        ▼
tool_safety_checker.check_before_execute()          ← 现有，不动主干
        │  SafetyResult 增加 sandbox_required=True 字段
        ▼
check_safety_and_confirm() HITL 人工确认             ← 现有逻辑不动, 仅插入预检调用(见3.2.3)
        │  确认通过
        ▼
┌─────────────────────────────────────────────┐
│ 【新增】SandboxExecutor.pre_execute()         │
│                                             │
│  1. 创建沙箱工作区 (%TEMP%\omniagent_sandbox\{task}) │
│  2. 文件类: 影子副本进工作区                   │
│     shell类: cwd=工作区 + JobObject 包裹执行  │
│  3. 试执行, 收集 stdout/stderr/rc/影响文件清单 │
│  4. 判定: rc==0 且影响面在白名单内 → 放行       │
│     超时/环境性失败(未完成有效验证)             │
│       → 转 HITL 用户裁决                       │
│     危险型失败 → 经 _denied 通道反馈 LLM       │
│  5. finally: 销毁工作区 + 终止后端进程树       │
└─────────────────────────────────────────────┘
        │ 放行
        ▼
真机原路执行（execute_shell_command / delete_file ...）← 现有，不动
        │
        ▼
operation_backup / execute_with_safety               ← 现有备份回滚兜底
```

### 2.3 沙箱后端架构（可插拔，唯一实现 JobObject）

概念澄清：**沙箱是隔离环境的"概念"，Docker 只是实现沙箱的"手段之一"**。本方案将两者解耦——后端可插拔：

```
destructive 命令触发沙箱预检
        │
        ▼
后端分派（直线 if 判断, 无探测开销）
  sandbox.backend 配置 = "job_object" → 唯一实现轻量隔离(零依赖, 永远在线)
```

**为何不做多后端自动探测（v1.9 会审定论）**：本系统真机是 Windows、LLM 生成 PowerShell 命令。若自动探测到 Docker 就把命令路由进 Linux 容器，`Remove-Item/reg/taskkill` 不存在 → rc≠0 **误拦**；即便跑通语义也不同 → **误放**。探测越"智能"，预检结果越失真。故一期只保留与真机同构的 JobObject 后端，配置 `backend` 键作为扩展位预留。

- 后端实现同一接口 `run(command, workspace, timeout) -> BackendResult`，executor 不感知差异（OCP：未来跨平台脚本场景新增容器后端只加类不改编排）
- 容器后端的完整评估结论见 2.5.3 排除表

### 2.4 两类操作的预检策略

| 类型 | 工具示例 | 预检方式 |
|------|---------|---------|
| **shell 命令** | execute_shell_command | subprocess + JobObject，cwd=沙箱工作区，真实跑一遍（危险效果被限制在工作区内） |
| **高危文件操作** | delete_file / registry_write 等 | 影子副本：把目标文件/目录复制到工作区，对**副本**执行同样操作，验证可行性并报告影响面（文件数/字节数）；registry 类仅做路径合法性+影响范围静态分析（注册表无法影子副本） |

> registry_write/delete 注册表项的"预检"为静态检查（键存在性、值类型、递归范围统计），不做动态试删。此局限在文档明示。

### 2.5 各沙箱环境技术特点对比

#### 2.5.1 Job Object 轻量隔离（当前唯一后端）

| 维度 | 说明 |
|------|------|
| 原理 | Windows 内核原生机制组合：①临时工作区（%TEMP% 下圈定沙箱目录，cwd 指向它）；②Job Object 进程作业对象（收编命令进程及其全部子孙进程，统一管控） |
| 隔离面 | 相对路径写操作被约束在工作区内；进程树一键击杀（TerminateJobObject）；内存上限（JOBOBJECT_LIMIT_PROCESS_MEMORY） |
| 启动参数 | pwsh 以 `-NoProfile -NoLogo -NonInteractive -ExecutionPolicy Bypass` 启动——`-NoProfile` 阻断用户 profile 污染（覆盖 cmdlet/外联/改策略），`Bypass` 保证自身临时脚本可运行（对齐引擎 L395 已有 `-NoProfile` 先例；审查建议的 Restricted 会禁掉自身脚本，不可取） |
| 依赖 | **零外部依赖**——Windows 内核 API（ctypes 标准库直调）+ Python 标准库 tempfile |
| 启动开销 | ~10ms 工作区 + 0.5~1.5s pwsh 冷启动 |
| 取结果能力 | rc/stdout/stderr 直取；工作区 diff 影响清单 |
| 局限 | **非硬墙**：绝对路径写操作（`Remove-Item D:\x`）物理上拦不住，靠"先扫描写意图→命中转人工确认"缓解（R1）；不隔离网络 |
| 定位 | 当前唯一后端，零依赖永远在线；同 Windows 环境，与真机执行一致性最高 |

#### 2.5.2 其他候选方案（评估后排除，留档）

| 方案 | 排除原因 |
|------|---------|
| Docker 容器 | 隔离强度虽高，但容器是 Linux 环境：本系统真机为 Windows、LLM 生成 PowerShell 命令，`Remove-Item/reg/taskkill/C:\路径` 在容器内不存在或不识别 → 预检要么误拦要么语义漂移误放，**结果失真收益为零**；仅对纯计算类跨平台脚本有边际价值，不值得为此引入探测/分派/提示复杂度（v1.9 会审移除，接口预留） |
| Windows Sandbox | Win10/11 专业版功能；每次启动 10s+ 且销毁即弃，无法程序化取回执行结果，不适合 Agent 自动化闭环 |
| 完整虚拟机（Hyper-V/VMware） | 资源开销大（GB级）、启动分钟级、快照回滚复杂，收益配不上成本 |
| WSL2 直接执行 | 与 Docker 同属 Linux 环境差异问题且无文件系统硬隔离，不如直接用容器，无独立价值（WSL2 的正确用法是作为 Docker Desktop 的底座间接使用） |

#### 2.5.3 选型结论

- **一致性与隔离强度的权衡**：容器隔离强但环境异构（Linux≠真机 Windows），预检结果失真；轻量隔离弱但环境同构（就是真机同款 shell），预检结果真实有效
- 因此本方案以轻量隔离为唯一后端；`SandboxBackend` 协议作为扩展位保留——未来若出现"跨平台脚本预检"的真实需求，实现协议接入即可，编排层零改动

#### 3.1.2 job_object.py — Windows Job Object

```python
class SandboxJob:
    """ctypes 封装 Windows Job Object"""
    def __init__(self) -> None                          # CreateJobObject + JOBOBJECT_LIMIT_PROCESS_MEMORY(默认2048MB, 可经sandbox.process_memory_limit_mb配置)
```

#### 3.1.3 backend.py — 后端协议与实现（ISP: 接口隔离）

- 协议保留 `probe` 方法作为未来后端（如跨平台脚本容器）的探测契约；当前唯一实现恒返回 True，无运行时探测开销

#### 3.1.4 executor.py — 编排入口（SRP: 只编排，不碰实现细节）

```python

@dataclass
class PreCheckResult:
    passed: bool                 # 是否放行真机
    blocked_reason: str = ""     # 失败原因(喂给LLM)
    needs_ruling: bool = False   # 未完成有效验证(超时/环境性失败): 处置转HITL用户裁决而非危险型blocked反馈
    impacts: List[FileImpact] = field(default_factory=list)   # 影响文件清单(喂给LLM辅助判断) — 可变默认必须用field工厂(v1.12 F7)
    stdout_tail: str = ""        # 输出尾部(截断4096字符)

class SandboxExecutor:
    async def pre_execute(self, tool_name: str, params: Dict) -> PreCheckResult:
        """总开关唯一判定点(v1.10): 入口先查 get_config().get('sandbox.enabled', True),
        False 时直接返回 passed=True 的短路结果——checker 四条置位路径不读配置,
        开关在唯一入口单点生效, 不存在遗漏分支; 关闭后行为与实施前完全一致"""

    # 统一入口(action_handler 唯一调用点): 内部按 normalize_tool_name 分派 shell类→_pre_execute_shell / 文件类→_pre_execute_file_op

    async def _pre_execute_shell(self, command: str, timeout_sec: int) -> PreCheckResult      # 私有, 由pre_execute分派

```

> 注：`needs_ruling` 即此前版本的 `timed_out` 字段扩展语义（字段更名以名实相符）——涵盖超时**及环境性失败**（工作区缺上下文导致命令找不到文件、目标被占用致影子副本失败等），这类"未能在沙箱内完成有效验证"的情况统一转 HITL 用户裁决，不作为危险型拒绝。

- `FileImpact` 数据结构：`{path, change_type(added/modified/removed), size_bytes}`，一期在 blocked_reason 中拼纯文本，二期可结构化下发（见 5.2）
- 并发闸门：`pre_execute` 入口先 `async with semaphore:` 再进入编排（信号量见 3.1.3）

`_pre_execute_shell` 内部直线流程（KISS-DIRECT）：
1. `backend = 后端分派()` → 2. `workspace.create()` → 3. `backend.run(command, workspace.path, min(声明timeout, max_timeout_sec))` → 4. 收集 rc/stdout/stderr/是否超时 → 5. `workspace.diff_impacts()` → 6. 判定 → 7. `finally: 后端清理进程树 + workspace.destroy()`

#### 3.2.3 M3：action_handler 插入预检调用点

文件：`backend/app/services/agent/handlers/action_handler.py` 的 `check_safety_and_confirm()` 循环体。

**关键约束（v1.6 会审 F4/F5 定稿）**：循环体内有三条汇合路径——①auto_confirm 分支以 `continue` 结尾、②用户确认路径自然落出分支块、③无需确认的调用（safe 直通/会话信任豁免）直接跳过整个 `requires_confirmation` 块。为使**每个 call 恰好经过一次预检且不重复**，用局部函数收敛逻辑（DRY），在三条路径各插一处：

三处插入点位置不变：
- **①** auto_confirm 汇合路径（现 L321-322，`continue` 之前）
- **②** 用户确认汇合路径（现 L353 之后，末尾加 `continue`）
- **③** 循环体末尾兜底（仅 safe 直通/会话信任豁免的调用触达）

语义对齐说明：
- 危险型失败走 `_denied` 三元组通道（tool_name, reason, call）+ MetaStep(type=error) 下发——与现有"被安全策略拦截"（L289）同构，LLM 收到的是普通失败观察，可自我纠正
- 超时型失败复用现有 HITL 原语（paused 步骤/confirm_id/等待裁决），用户可拍板"直接真机执行"，前端零新交互
- safe 级调用 `sandbox_required=False` → `_sandbox_precheck()` 返回 None，三处插入点均零开销直通
- 已知行为（接受）：auto_confirm 路径中 resolve_confirmation 先落了会话信任，随后预检拒绝该次执行——安全性不受影响（下次同工具调用仍会因 sandbox_required 进入沙箱），仅多一次豁免记录

## 四、判定规则

### 4.1 触发范围汇总（单一事实源）

**触发**：checker 判定 destructive 级（SafetyResult `sandbox_required=True`）的调用，**含被会话信任豁免确认的场景**（工具明细见 1.2 G1 表）。

**不触发（直通现有链路）**：

| # | 条件 | 说明 |
|---|------|------|
| 1 | safe 级分级（`sandbox_required=False`） | 无风险直跑；注意：会话信任豁免的调用虽返回 safe 级，但 `sandbox_required` 按真实危险度置位（见 3.2.2 路径B），不适用本行 |
| 2 | dangerous 级分级 | 已被现有逻辑直接 blocked，无需预检 |
| 3 | 无覆盖风险的写操作 | 追加模式写文件、新建文件等 |
| 4 | 只读白名单快速通道 | `Get-*/ls/cat/type/git status` 等前缀匹配跳过预检。**收紧条件（v1.10 FP1）**：仅当整条命令为单命令（无管道 `\|`、无分号 `;`、无调用操作符 `&`）时生效——防止 `Get-ChildItem \| Remove-Item xxx` 这类"Get- 开头、删除结尾"的管道逃逸；不满足则走正常预检 |
| 5 | `sandbox.enabled = false` | 配置总开关（逃生门）。判定点唯一：executor.pre_execute 入口短路（见 3.1.4），关闭后 checker 置位照旧但预检整体跳过，行为与实施前完全一致 |
| 6 | 后端不可用场景 | **不存在此分支**：唯一后端 JobObject 零外部依赖永远在线（v1.9 移除多后端探测后，"无后端不预检"的场景在架构上不可能发生） |
| 7 | 声明 timeout 超过硬上限 | LLM 声明 timeout > max_timeout_sec(300s) 的命令**不做预检**，直接转 HITL 用户裁决（等待不可接受，见 4.2 超时规则）（v1.12 F8 补录） |

### 4.2 预检放行条件（全部满足才放行）

| # | 条件 | 不满足时的反馈 |
|---|------|--------------|
| 1 | 进程退出码 rc == 0 | stderr 尾部原文喂 LLM |
| 2 | 无未捕获异常堆栈 | traceback 尾部喂 LLM |
| 3 | 影响文件全部落在工作区**或系统临时目录**内（shell 类天然满足；文件类校验副本操作成功） | 越界路径清单喂 LLM。豁免 `%TEMP%`：pip/npm 等合法工具大量写系统临时目录，不豁免会误拦正常命令（v1.10 FP3） |
| 4 | 执行耗时 < 预检timeout（取 `min(工具声明timeout, max_timeout_sec)`） | 超时型未通过（`needs_ruling=True`），处置见下方超时规则 |

**超时/环境性失败规则（区别于危险型失败）**：

- **未完成有效验证 ≠ 危险**：超时、或环境性失败（工作区缺上下文导致命令找不到真实文件、目标被占用致影子副本失败等——v1.10 FP2/FP4），都只说明"未能在沙箱内完成有效验证"，不代表命令有害
- **为何不按普通失败反馈 LLM**：LLM 收到后大概率原样重发 → 再失败 → 死循环烧 token
- **预检 timeout 联动**：`min(LLM在工具参数中声明的timeout, sandbox.max_timeout_sec)`——LLM 声明跑 120s 构建时不被默认值误掐；声明超过硬上限(300s)的命令不预检，直接转 HITL 强确认
- **处置分流**：`needs_ruling=True` → 转 HITL 用户裁决（用户可拍板"直接真机跑"）；危险型失败（rc≠0 且非环境性/异常/越界）→ 走普通 `_denied` 反馈 LLM 纠错

### 4.3 性能开销评估

| 环节 | 开销 |
|------|------|
| 工作区创建/销毁 | ~10ms |
| 影子副本 | 视文件大小，通常 <100ms |
| subprocess 冷启动 pwsh | 0.5~1.5s |
| 合计（典型场景） | **1~2 秒/次**，仅 destructive 级触发；并发受信号量(默认3)约束 |

## 五、前端影响与增强规划

> 分析方法说明：从后端数据流推演前端影响，不依赖现有前端代码现状。结论依据：本方案刻意未新增 Step 类型与 SSE 事件类型，预检结果全部复用现有下发通道。

### 5.1 一期：前端零改动（强制基线）

```
沙箱预检结果(PreCheckResult)
    │
    ├─ passed=false(危险型) ──→ 转 _denied 通道 ──→ MetaStep(type="error", content=失败原因+影响清单)
    │                                              └─ 复用前端现有的错误步骤渲染
    ├─ passed=false(未完成有效验证) ─→ paused 步骤等用户裁决 ──→ 复用现有 HITL 确认交互，无任何新交互形态
    ├─ passed=true ──────────→ 正常执行原工具 ──→ 现有 ToolStep/MetaStep 事件流，无任何新事件
```

| 项目 | 结论 |
|------|------|
| 前端改动量 | **零** |
| 用户可见变化 | 仅多一类普通错误提示；超时场景复用现有确认弹窗，渲染走现有通道 |
| HITL 确认交互 | 完全是现有流程（含超时裁决），前端无感知沙箱存在 |

### 5.2 二期可选增强（需后端配套加字段）

| # | 前端展示 | 后端配套字段/事件 | 触发条件建议 |
|---|---------|------------------|-------------|
| 1 | 步骤卡片标"已沙箱预检"徽标 | MetaStep/ToolStep 增加 `sandbox_backend` 字段 | 预检通过的 destructive 调用 |
| 2 | 影响文件清单可视化（新增/修改/删除着色列表），替代纯文本 | PreCheckResult.impacts 结构化下发（JSON 数组而非拼接字符串） | 预检完成且 impacts 非空 |

### 5.3 实施建议

- 一期严格按本方案实施，前端不动（符合"后端为主、前端迎合"铁规）
- 二期增强在一期跑通、实际使用验证体验后再决定是否启动——避免过度设计（YAGNI）
- 后端一期实施时**预留**上述两个字段的扩展位（字段不加，结构留白），使二期增强无需重构即可接入

## 八、检查与测试方案

> 设计原则：每个用例都必须声明"它要抓什么 Bug"——写不出抓虫目标的用例不进方案。分层执行：单测 → 路径矩阵 → 集成 → E2E → 对抗性，逐层放大。

- **P2 行为零退化违反**：`enabled=false` 时与实施前行为有任何可观测差异

| safe 级全部路径 → sandbox_required=False 且对象可 pickle/复制无误 | 字段污染 |

### 8.3 路径覆盖矩阵（组合遗漏猎杀）

四种预检结果 × 三个插入点 = **12 格，每格至少 1 条集成用例**（注：矩阵行是"结果类型"，勿与 checker 的四条置位路径 A/B/C/D 混淆——A/B/C/D 已由 8.2.4 单测覆盖）：

| | 插入点① auto_confirm | 插入点② 用户确认 | 插入点③ 无需确认 |
|---|---|---|---|
| 预检通过放行 | security.enabled=false 场景 | 正常 HITL 确认场景 | 会话信任豁免场景 |
| 危险型拒绝 | bypass 下危险命令 | 确认后危险命令 | 信任豁免下危险命令 |
| 未完成有效验证→裁决通过 | **bypass 下不适用：直接放行**（v1.13 V2 免打扰语义） | 确认后长命令/环境性失败，用户批准 | 豁免下长命令，用户批准 |
| 未完成有效验证→用户拒绝 | bypass 下不适用（同上） | 同上用户拒绝 | 同上用户拒绝 |

> 注：插入点①列的裁决两格因 v1.13 V2（bypass 免打扰）语义变更为"直接放行"，仍保留格子用于回归断言"该场景不得出现 SUSPENDED"。

矩阵之外专项断言：**同一 call 全流程恰好经过一次预检**（executor 计数器断言，防双重预检回归）；裁决通过后状态机 SUSPENDED→EXECUTING 迁移正确。

### 8.4 E2E 全链路（真实后端+真实 LLM，一次一个 case）

| Case | 步骤要点 | 主要抓虫目标 |
|------|---------|-------------|
| E2E-1 拦截→纠错→放行 | 让 LLM 执行 `Remove-Item <项目内真实临时文件>`；先制造预检失败（文件被占用），观察反馈→LLM 自改→二次放行 | 反馈通道有效性、死循环检测(P1) |
| E2E-2 误判回归 | 引用项目真实文件的命令（沙箱内必找不到）→ 应转用户裁决而非危险拒绝 | FP2 环境性失败误判 |
| E2E-3 长命令裁决 | 声明 timeout=400s 的构建类命令 → 不预检转裁决 → 用户批准直接真机跑 | 硬上限联动、HITL 分支 |
| E2E-4 开关零痕迹 | enabled=false 跑同批 destructive 任务 → 日志断言无任何 sandbox 调用记录 | 总开关完整性 |
| E2E-5 会话信任链路 | 先确认一次工具建立信任 → 再发 destructive 命令 → 仍必须走预检 | F1 回归 |

### 8.7 出门标准（全部满足才可合入）

1. destructive 级 shell 命令：预检失败 → LLM 收到具体原因并能自我纠正 → 纠正后放行 → 真机成功执行，全程真机零污染
2. destructive 级文件删除：影子副本预演通过 → 真机删除成功且有备份记录
3. safe 级命令延迟增加 < 50ms（白名单快速通道生效）
4. `sandbox.enabled=false` 时行为与本方案实施前完全一致（零退化）
5. 现有全量测试套件无回归
6. 后端架构：`backend` 配置键生效（当前唯一合法值 job_object）；并发预检受信号量约束（同时最多 max_concurrent_sandboxes 个）；pwsh 以 -NoProfile 启动（Profile 污染用例通过）
