## 一、背景与问题

`action_handler.build_observation` 在构造 `ActionStep.tools[i].target`（执行前展示「操作对象」）时，原实现使用硬编码映射 `_TARGET_FIELD`：

```python
_TARGET_FIELD = {
    "read": "file_path", "writetext": "file_path", "edittext": "file_path",
    "delete": "file_path", "copy": "file_path", "move": "file_path",
    "extract": "file_path", "compress": "file_path",
    "listdir": "dir_path", "find": "search_dir", "grep": "pattern",
    "shell": "command", "httpget": "url", "fetchpage": "url",
    "download": "url", "web_search": "query", "ping_port": "host",
    "query_sql": "sql", "execute_sql": "sql",
}
```

经实测与 registry 探查（`ensure_tools_registered` 后逐一比对真实 `input_schema.properties`），该映射**双重失配**，是一个真实 bug：

1. **键失配**：映射键 `"read"`、`"web_search"` 与注册名 `"readtext"` / 未注册不符，`_TARGET_FIELD.get(tool_name)` 直接返回 `None` → 回退为工具名。
2. **字段失配**：文件类映射值 `file_path`/`dir_path`/`search_dir` 与真实 schema 属性名 `path`/`pattern` 不符，`_params.get(...)` 取到空串 → 回退为工具名。

> 注：grep/shell/httpget/fetchpage/download/ping_port/query_sql/execute_sql 的映射值恰与 schema 一致，旧代码本可工作；推导化后统一正确且新增工具自动获得 target。

此外，原代码存在 **10 大原则违例**：
- **DRY**：`_TARGET_FIELD` 重复了工具 schema 的「主参数」知识；且与 `observation_formatter._format_llm_data` 的 target 截断形成两处手写截断（action 侧 120 / format 侧 200），规则还不一致。
- **复用优先**：两处手写截断均未使用 `FUNCTIONS.md` 已登记的公共 `truncate_text`。

## 二、设计决策（方案选型）

| 方案 | 做法 | 结论 |
|------|------|------|
| A 硬编码映射（原状） | `_TARGET_FIELD` 字典 | ❌ 否决：字段名错配致 target 恒为工具名；DRY 违例；新增工具需手改本文件 |
| **B schema 主参数优先级推导** | 从 `tool_registry` 真实 `input_schema.properties` 按 `_TARGET_PARAM_PRIORITY` 选字段；预留 `target_param` 显式声明（OCP 扩展点） | ✅ **选定**：DRY+OCP 双满足、修掉错配真 bug、新增工具自动获得、零侵入 |
| C 全显式声明 | 每个工具注册时传 `target_param`，无启发式 | 语义最精确但需改 ~19 处注册（churn 大、YAGNI 风险）；B 已含 C 能力（歧义工具一行显式即可覆盖） |
| D 复用结果 `llm_data.action.target` | ActionStep 也读工具返回 | ❌ 不可行：ActionStep 在 `execute_tools` **之前**发射（action_handler.py:881 vs :892），彼时无结果，只能取入参 |

**选定 B 的关键依据**：
- ActionStep 是「执行前参数快照」，LLM 已回传**确定的参数值**，`call["tool_params"]` 即具体值；schema 仅用于判定「哪个字段是操作对象」。**值取自入参，字段名由 schema 推导**——二者同源于 parameter，处于不同阶段（入参 vs 结果）。
- `format` 侧 `llm_data.action.target` 是执行后工具回报（可能经归一化），与 ActionStep 天然异源、服务不同消费者（前端 action 预览 vs LLM 观察文本），是**必要独立路径而非冗余**。

## 三、实施方案

### 3.1 action_handler.py（核心重构）

**设计如何落地**：本节改造的核心是把「操作对象字段名」的知识从 action_handler 内部硬编码映射，上移到「由 tool_registry 中工具的真实 schema 推导」，并预留显式声明扩展点。改造后 action_handler 不再知道任何工具的字段名，新增工具零改动即可自动获得 target（DRY + OCP 双达成）。

- 新增导入 `from app.tools.registry import tool_registry`。
- 删除 `_TARGET_FIELD`；新增 `_TARGET_PARAM_PRIORITY` 元组与 `_resolve_target_field(tool_name)`。
- `_extract_target(call)`：字段名由 `_resolve_target_field` 推导，值取自 `call["tool_params"]` 的 LLM 确定入参；**ActionStep.target 极少截断**（按北京老陈要求保留完整值）。

**① 常量 `_TARGET_PARAM_PRIORITY`（action_handler.py::614）** — 字段名推导的「主干知识」，取代旧 `_TARGET_FIELD` 字典：

```python
_TARGET_PARAM_PRIORITY = (
    "command", "sql", "url", "host", "pattern",
    "path", "dir_path", "file_path", "source_path", "query", "content",
)
```

设计要点：
- 该元组的顺序**不是**任何工具的 schema 顺序，而是「人类对'操作对象'的语义优先级」；`pattern` 刻意置于 `path` 之前，是为了让搜索类工具（grep/find）优先命中「搜索词」，而非「目录/路径」。
- 它不再重复任何工具名，只列出「候选主参的字段名」——同一份知识本由工具 schema `properties` 提供，此处只是给出「命中顺序偏好」（KISS-DIRECT：单一优先级表，无分支字典）。

**② `_resolve_target_field`（action_handler.py::620）** — 推导函数，四层策略（显式 → 优先级 → 必填 → 首参数）：

```python
def _resolve_target_field(tool_name: str) -> Optional[str]:
    _tool = tool_registry.get_tool(tool_name)
    if _tool is None:
        return None
    _props = (_tool.input_schema or {}).get("properties") or {}
    if not _props:
        return None
    _explicit = getattr(_tool, "target_param", None)
    if _explicit and _explicit in _props:
        return _explicit          # ① 显式声明优先（OCP 扩展点）
    for _cand in _TARGET_PARAM_PRIORITY:
        if _cand in _props:
            return _cand          # ② 优先级元组命中
    for _r in (_tool.input_schema or {}).get("required", []) or []:
        if _r in _props:
            return _r             # ③ 必填参数兜底
    return next(iter(_props))     # ④ 首个属性兜底
```

设计落点映射：
- **DRY**：字段名不再与 schema 重复维护——直接从 `input_schema.properties` 读；表达式顺序 `properties→required` 与 schema JSON Schema 语义一致，无二次认知负荷。
- **OCP**：`_explicit = getattr(_tool, "target_param", None)` 开了一个「零侵入本函数」的扩展点——若某个工具想覆盖启发式（如 find 想显示目录而非搜索词），只需在注册处传 `target_param`（见 3.2/file_register），本函数无需改动。
- **KISS-DIRECT/关联逻辑**：`pattern` 在 `path` 前，天然区分 grep（取搜索词）与其余路径类工具；第 ③④ 层兜底保证任何异常 schema（无 properties、全空、极简）都不会抛异常，只会回退。

**③ `_extract_target`（action_handler.py::642）** — 值侧提取，字段名由 ② 推导，值取自 LLM 已回传的确定入参：

```python
def _extract_target(call: Dict[str, Any]) -> str:
    _name = call.get("tool_name", "")
    _params = call.get("tool_params", {}) or {}
    _field = _resolve_target_field(_name)
    if not _field:
        return _name              # 未推导到字段名 → 回退工具名（安全兜底）
    _val = _params.get(_field, "")
    return str(_val) if _val != "" else _name
```

设计落点映射：
- **取你不取果**：这里读的是 `call["tool_params"]`（执行前快照），与 observation 里展示的 `llm_data.action.target`（执行后工具回报）**同源不同阶段**，故是必要独立路径（见「二、设计决策」方案 D 否决说明）。
- **回退不崩溃**：`_field` 为空或 `_val` 为空一律回退工具名，绝不让 ActionStep.target 出现空串/异常。
- **关联逻辑（功能增强非退化）**：旧代码因字段名错配恒回退工具名；现在能拿到真实参数值，恰好修正了该 bug（见「一、背景与问题」）。

**④ 调用点（handle_action，action_handler.py::898）** — `_extract_target` 唯一消费方，构造 ActionStep 的结构化 `tools[]`：

```python
_action_tools = [{
    "tool": c.get("tool_name", ""),
    "target": _extract_target(c),
    "params": c.get("tool_params", {}) or {},
} for c in _exec_calls]
yield agent._step_emitter.emit(ActionStep(
```

> 设计闭环：执行前 yield 一次（§10.3.3(2)）→ 此处 `_extract_target` 从入参取操作对象 → 供前端「操作对象」预览。整条链路 action_handler 零硬编码。

### 3.2 tool_types.py + registry.py（OCP 扩展点）

**设计如何落地**：`target_param` 是一条贯穿「元数据定义 → 注册参数 → 注册表读写」的显式声明通道。设计上它默认留空（`None`），让 `_resolve_target_field` 走 3.1 的自动推导；仅当某工具确实需要覆盖启发式时才显式指定。

**① `ToolMetadata.target_param` 字段（tool_types.py::97）** — 元数据侧新增一个可空字段：

```python
# 【2026-08-18 小健 三堂会审】主参数(操作对象字段名): target展示自动推导的显式声明扩展点;
# 留空则由action_handler._TARGET_PARAM_PRIORITY按input_schema.properties自动推导(DRY/OCP)
target_param: Optional[str] = None
```

设计要点：
- 字段归属 `ToolMetadata`（单一定义源）而非 action_handler，正是 OCP「对扩展开放」的落点——扩展能力长在数据上，而非分派逻辑里。
- 默认 `None` 保证**向后行为默认一致**：任何既有工具不声明也照常工作（自动推导），不符合「禁止 backward」的担忧（这是新能力的默认通路，非兼容旧写法）。

**② registry.py `register`（:139）/ `_update_existing_tool`（:188）/ `_register_new_tool`（:226）** — 三个读写函数全部贯通 `target_param`：

```python
# register 形参末尾新增:
def register(...,
    deps: Optional[List[Union[str, Dict[str, Any]]]] = None,
    target_param: Optional[str] = None,
) -> Dict[str, Any]:

# _register_new_tool 透传给 ToolMetadata:
metadata = ToolMetadata(
    ...
    dependencies=dependencies or [],
    target_param=target_param,        # 写入元数据
)
```

设计落点：
- **DRY + 复用优先**：三个入口共用同一 `ToolMetadata` 构造（`_register_new_tool`）与 `_update_tool_metadata`（`_update_existing_tool`），新增字段只在构造处落位，无需三处分别维护。
- **SRP/SLAP**：`register` 只做「分派新/旧」，旧的交给 `_update_existing_tool`、新的交给 `_register_new_tool`，`target_param` 作为普通字段随流程走，未破坏原有职责边界。

**③ registry.py 装饰器 `register_tool`（:356）** — 装饰器形式的注册也暴露 `target_param` 形参，并在内部透传给 `register`：

```python
def register_tool(..., dependencies=None, target_param: Optional[str] = None):
    ...
    register(name=..., ...,
        dependencies=dependencies,
        target_param=target_param,     # 透传
    )
    return func
```

> 设计闭环：无论工具用「命令式 `register(...)`」还是「装饰器 `@register_tool(...)`」注册，都能带上 `target_param`。action_handler 侧统一 `getattr(_tool, "target_param", None)` 读取，与实际注册形式解耦。

**④ 扩展点真实消费：`find` 的显式声明（file_register.py::253）** — 本次重构中唯一用到显式覆盖的工具，也是 3.1 方案 B「OCP 扩展点」的活例：

```python
# 2026-08-18 小健 三堂会审: find 的操作对象是"搜索目录"(自报 action.target=search_dir);
# 默认按 _TARGET_PARAM_PRIORITY 推导会先命中 pattern(搜索词), 致 ActionStep 与 observation 两端 target 不同源,
# 故显式声明 target_param="path" 使两端一致(OCP 扩展点, 与 grep 取 pattern 的语义区分)
_tp = "path" if name == "find" else None

tool_registry.register(
    name=name, ..., target_param=_tp,   # 一行显式覆盖，本函数无需改动
)
```

设计落点：
- **OCP 闭环**：find 因默认优先级 `pattern` 在 `path` 前，会先命中「搜索词」，而其工具自报的 `llm_data.action.target = search_dir`（搜索目录）——两处 target 不同源。解决方式**不是改 `_resolve_target_field`**，而是用 3.1 ② 预留的扩展点在注册处 `target_param="path"` 一行覆盖，恰印证「对扩展开放、对修改封闭」。
- **与 grep 语义区分**：grep 的目标就是要搜的模式串（`pattern`），find 的目标是搜索目录（`path`）——二者虽同属搜索类且 schema 都含 `pattern`，但显式声明让语义各归其位。

### 3.3 observation_formatter.py（截断收敛 + 去重）

**设计如何落地**：本节两件事——①把 `_format_llm_data` 里 target 的手写截断换成公共 `truncate_text`（复用优先）；②新增 `_tool_target(llm_data)` 助手，把散落在 5 处的 `llm_data.action.target` 读取收敛为单点（DRY），并顺带补齐 per-tool formatter 缺失的 str-action 防御。

**① 导入公共截断函数（observation_formatter.py::92）**：

```python
from app.utils.text_utils import truncate_text  # 2026-08-18 小健: target展示截断收敛到公共函数(消除120/200手写分歧)
```

**② `_safe_llm_sub` 助手（:126）** — Bug#7 防御的统一取值点，供 `_tool_target` 复用：

```python
def _safe_llm_sub(llm_data, key: str) -> dict:
    _v = (llm_data or {}).get(key)
    return _v if isinstance(_v, dict) else {}   # 非 dict（如 str）一律返回 {}，防 AttributeError
```

**③ `_tool_target` 助手（:133）** — 收敛 5 处 `action.target` 读取的 DRY 单点：

```python
def _tool_target(llm_data) -> str:
    _action = _safe_llm_sub(llm_data, "action")     # Bug#7 防御：action 可能为 str
    _t = _action.get("target", "") if isinstance(_action, dict) else ""
    return str(_t) if _t else ""                    # str() 兜底（WindowsPath 等非 str）
```

设计落点：
- **DRY**：旧实现 `_format_llm_data` 与 4 个 per-tool formatter（`_format_fetchpage_result`:1310 / `_format_readtext_result`:1335 / `_format_edittext_result`:1358 / `_format_xlsx_result`:1393）各自 `(llm_data or {}).get("action", {}).get("target", "")` 重复读取，改成统一调 `_tool_target(llm_data)`。
- **复用优先 + Bug#7**：原先 per-tool formatter 没有 str-action 防御（`get` 到 str 会崩），本次通过 `_safe_llm_sub` 一并补齐；且 `_format_llm_data` 与 per-tool formatter 共用 `_safe_llm_sub`/`_tool_target`，两处防御一致。

**④ `_format_llm_data` 截断收敛（:633）** — 由手写切片改为公共函数，且仅此一处对 LLM 侧做 200 截断：

```python
target = _tool_target(llm_data)          # 统一取值
if target:
    target, _ = truncate_text(target, 200, suffix="...")   # 公共截断，消除手写"[:200]+..."
```

设计要点：
- **复用优先**：`truncate_text` 是 `FUNCTIONS.md` 已登记的公共函数，旧代码 `target[:200]+"..."` 属局部重造轮子，本次废弃。
- **收敛规则分歧**：旧实现出现「action 侧手写 120 / format 侧手写 200」两套不一致截断；设计定案为——format（LLM 观察）统一 200，action（前端预览）**不截断保留完整入参**，两处职责分明、不再冲突。
- **关联逻辑（不退化）**：`_target_part = f",处理对象-{target}" if target else ""` 的展示语义与截断后文本格式完全不变，仅数据来源与截断手段更干净。

> 设计闭环汇总（target 全生命周期）：
> 1. **执行前**：handle_action → `_extract_target(call)` → ActionStep.tools[].target（前端预览，不截断）。
> 2. **执行后**：工具返回 `llm_data.action.target` → `_tool_target` 读取 → `_format_llm_data` 统一 `truncate_text(200)` → LLM 观察文本。
> 3. 两处**同源不同阶段**（同为 parameter），服务不同消费者，属必要独立路径（见方案 D 否决说明）。

### 3.4 测试

**设计如何落地**：测试从「断言旧 bug 行为」反转为「断言设计与实现」，并建立对 registry 的依赖（推导本身源于 schema，测试必须确保工具已注册）。

- 新增 `tests/test_target_derivation.py`：19 工具字段推导断言、`_extract_target` 取确定入参值（不再回退工具名）、截断收敛、旧 `_TARGET_FIELD` 已删除、`_tool_target` 与 per-tool formatter 的 str-action 防御。
- 更新 `tests/test_10_3_refactor.py` 的 `TestExtractTarget`（原断言编码的是已修复的 bug 行为），并加 `ensure_tools_registered` 自动 fixture（推导依赖 registry）。

测试要点逐条对应设计：
- **19 工具字段推导**：逐一 `assert _resolve_target_field(tool_name) == 期望字段`——断言的是「推导结果正确」，而非「映射写对了」，把 3.1 ② 的四层策略固化成回归网。
- **`_extract_target` 取确定入参值**：旧 test 断言回退工具名（那是 bug 行为），现改为断言返回 `tool_params[field]` 的真实值，直击「一、背景」里的字段失配 bug。
- **旧 `_TARGET_FIELD` 已删除**：断言整个方案的核心——硬编码映射彻底移除，防 DEV 悄悄加回。
- **`ensure_tools_registered` 自动 fixture**：因为 3.1 ② 依赖 `tool_registry` 里有真实 schema，测试前必须注册工具，否则推导空转——fixture 把「编码前先注册」固化为不变式，保证测试可复现。

## 四、三堂会审结论

| 审查 | 结论 |
