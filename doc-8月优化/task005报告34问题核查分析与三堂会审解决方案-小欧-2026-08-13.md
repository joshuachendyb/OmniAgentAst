## 二、运行期实测复现问题（7个，判定：真实）

### 【问题1】storage.py: NameError — local_time 未绑定变量
- **文件**: `backend/app/services/chat/storage.py` / **Commit**: `6de1accf1`
- **真实性判定**: ✅ 真实（运行期复现）
- **复现证据**: 修复前 `local_time = get_local_iso_timestamp()` 仅写在 `if is_new:` 块内；`is_new=False`（同session二次任务的 agent_runner 路径）执行 UPDATE 语句引用 `local_time`，实测抛 `NameError: cannot access local variable 'local_time'`。
- **三堂会审解决方案**:
  - **合规**: 条件赋值导致变量存在分支差异，违反"防御性边界"；KISS 最小改动——赋值提前到 `if is_new:` 之前，保证所有路径可访问。
  - **合理**: 单次提前赋值即覆盖 INSERT/UPDATE 两分支，无重复、无中间层，逻辑最直。
  - **关联逻辑**: UPDATE 路径是 agent_runner 二次任务的正常入口，修复后实测 `is_new=True/False` 两次调用均无异常，无退化。
  - **落地方案**: 将 `local_time` 赋值行移动到 `if is_new:` 判断之前，两分支共用同一时间值。

### 【问题2】storage.py: _truncate_tool_result 递归返回值丢失
- **文件**: `backend/app/services/chat/storage.py` / **Commit**: `6de1accf1`
- **真实性判定**: ✅ 真实（运行期复现）
- **复现证据**: 修复前 dict 分支对 list 值 `_truncate_tool_result(val, tag)` 递归但**丢弃返回值**；实测 `{"rows": [[1001个元素]]}` 嵌套结构内层 list 未被截断，外层截断后内层仍 1001 项，截断完全失效。
- **三堂会审解决方案**:
  - **合规**: 递归返回值丢失违反正确性；DRY——dict/list 两分支统一走"原地截断+回写"。
  - **合理**: 统一 `tr[key] = _truncate_tool_result(val, tag)` 回写所有递归结果，list 分支原地截断后继续递归元素，单一数据流。
  - **关联逻辑**: 修复后实测内层截到 1000，外层/内层一致；不影响正常短结果路径（递归天然返回原值）。
  - **落地方案**: dict 分支递归结果必须回写；list 分支 `del val[K:]` 后逐元素递归。

### 【问题3】react_cycle.py: timeout 错误被误判 FAILED
- **文件**: `backend/app/services/agent/react_cycle.py` / **Commit**: `b85f9625b`
- **真实性判定**: ✅ 真实（运行期验证）
- **复现证据**: 修复前 `_RECOVERABLE_ERRORS = ("user_rejected", "blocked")` 缺 `"timeout"`；用户确认超时（HITL超时）属"软拒绝"，应换工具继续而非 FAILED，与 `_add_denial_feedback` 注入的"改用其他工具"引导自相矛盾。实测 `"timeout" in _RECOVERABLE_ERRORS` 为 False。
- **三堂会审解决方案**:
  - **合规**: 集合定义不完整属"根因漏项"；KISS 最小补集。
  - **合理**: timeout 与 user_rejected/blocked 同属用户侧软拒绝，语义一致，一个集合内并列判断。
  - **关联逻辑**: 仅扩充判定集合，不改任何分支逻辑，FAILED 硬拒绝路径零影响。
  - **落地方案**: `_RECOVERABLE_ERRORS = {"user_rejected", "blocked", "timeout"}`。

### 【问题4】tool_retry_engine.py: clamp 门控 type 数组判定失效
- **文件**: `backend/app/tools/tool_retry_engine.py` / **Commit**: `317ff1add`
- **真实性判定**: ✅ 真实（运行期验证）
- **复现证据**: 修复前 `if _t in ("integer", "number"):` 门控，Pydantic v2 Optional 字段的 `type=["integer", "null"]` 时 `_t` 是 list，恒为 False，clamp 整段跳过；实测 `limit=1200` 越界值原样漏到工具层。修复后钳制到 maximum=100。
- **三堂会审解决方案**:
  - **合规**: 依赖顶层 type 做门控是脆弱抽象（YAGNI 反向：过度依赖 schema 形状）；改"能取到数值边界即钳制"，依赖数据而非形态。
  - **合理**: `_extract_numeric_bounds(spec)` 返回边界，`minimum/maximum` 均 None 才 continue，再 `isinstance(v,(int,float))` 类型兜底，一条直线判断。
  - **关联逻辑**: 整型/浮点值钳制逻辑不变，仅放宽门控，合法值（未越界）行为零变化。
  - **落地方案**: 废除顶层 type 门控；有数值边界即钳制。

### 【问题5】tool_retry_engine.py: anyOf 取边界顺序依赖
- **文件**: `backend/app/tools/tool_retry_engine.py` / **Commit**: `317ff1add`
- **真实性判定**: ✅ 真实（运行期验证）
- **复现证据**: 修复前 `_extract_numeric_bounds` 固定取 `any_of[0]` 的 min/max；当 anyOf[0] 恰为 null 分支（无边界）时返回 `(None, None)`，clamp 静默失效。实测 `anyOf=[{"type":"null"},{"type":"integer","minimum":1,"maximum":100}]` 旧逻辑返回 `(None,None)`、新逻辑返回 `(1,100)`。
- **三堂会审解决方案**:
  - **合规**: 顺序依赖违反确定性；全量扫描使结果与成员顺序无关。
  - **合理**: `for a in any_of: if isinstance(a,dict) and ("minimum" in a or "maximum" in a): return ...`——取首个含边界成员，不假设位置。
  - **关联逻辑**: JSON Schema anyOf 成员顺序规范不保证，扫描后各成员形状下均能取到边界，无路径退化。
  - **落地方案**: 全量扫描 anyOf 成员取边界。

### 【问题6】react_cycle.py: 可恢复异常重试计数双累加
- **文件**: `backend/app/services/agent/react_cycle.py` / **Commit**: `b85f9625b`
- **真实性判定**: ✅ 真实（逻辑模拟验证）
- **复现证据**: 修复前 except 块内 `_retry_count+1` 后又 `set_status(RETRYING)` 触发主循环 RETRYING 处理**再次 +1**，一次异常计2次，上限3实际第2次异常即 FAILED。模拟：旧=2次计数、新=1次。
- **三堂会审解决方案**:
  - **合规**: 双计数违反正确性与 KISS；两来源（except内直接计数 / _dispatch_handler 走 RETRYING）职责重复。
  - **合理**: 来源A（可恢复异常）直接 `continue` 回循环顶重试，计数在 except 内单次完成；来源B（工具重试）仍走 set RETRYING→主循环单次计数。两来源各自单计、互不干扰，符合 SLAP 单层职责。
  - **关联逻辑**: 循环顶取消/暂停检测保留；不 set RETRYING 则主循环 L614 分支不再被来源A触发，来源B路径原样保留，上限3语义恢复正确。
  - **落地方案**: except 可恢复分支去掉 `set_status(RETRYING)`，保留计数后直接 `continue`。

### 【问题7】react_cycle.py: task_id ContextVar 泄漏（潜伏）
- **文件**: `backend/app/services/agent/react_cycle.py` + `app/services/task/task_context.py` / **Commit**: `b85f9625b`
- **真实性判定**: ✅ 真实（潜伏，逻辑验证）
- **复现证据**: `set_current_task_id()` 在 action_handler 设置，`reset_current_task_id()` 原零调用（不对称）。当前 SSE 独立 asyncio.Task 场景不漏，长连接/复用 context 会跨请求泄漏。模拟验证 set/reset 对称后 `get_current_task_id()` 返回 None。
- **三堂会审解决方案**:
  - **合规**: 有 set 无 reset 违反资源对称性/防御性。
  - **合理**: 在 task 级 `finally` 与 `clear_temp_auth()` 并列收口，set/reset 严格配对，与既有的授权清理模式 DRY。
  - **关联逻辑**: 当前场景本就不漏，修复零行为变化（纯防御）；`finally` 覆盖所有 break/异常/自然退出路径（max_steps<=0 提前 return 在 try 之前，无 set 产生，不经过 finally 亦无泄漏）。
  - **落地方案**: `finally` 块中调用 `reset_current_task_id()`。

### 8.1 【复核发现A】#13 修复方法"缩小失败误判成功" → 已修

- **原修复代码**: `resize_ok = (_r2 - _l2 >= new_width - 2) and (_b2 - _t2 >= new_height - 2)` —— 单向容差只防大不防小。
- **缺陷**: 缩小请求完全失败（MoveWindow 无效、窗口纹丝不动）时，实际尺寸 = 旧尺寸 > 目标，`800 >= 600-2` 恒真 → **误报成功**。放大钳制场景（800→950 目标1000）反而 `950 >= 998` 误报失败。
- **实证**: 模拟8场景对比，旧判定 2 处 X!（缩小失败误判成功、放大钳制误判失败）。
- **改法**: 双条件判定——"精确达目标(容差2) **或** 尺寸确实发生变化(接受系统钳制)"：
  ```python
  _target_reached = abs((_r2 - _l2) - new_width) <= 2 and abs((_b2 - _t2) - new_height) <= 2
  _width_changed = (_r2 - _l2) != curr_width
  _height_changed = (_b2 - _t2) != curr_height
  resize_ok = _target_reached or _width_changed or _height_changed
  ```
- **三堂会审**: 合规=KISS 两个布尔+一个或、无中间层；合理=用"是否真正变化"区分钳制与失败，逻辑直线；关联=保留 #13 钳制容忍意图、同时检出缩小失败，8场景实测无新退化。
- **验证**: monkeypatch 6 场景全 OK（缩小失败/缩小钳制/放大钳制/放大失败/精确达到/保持原尺寸）。
- **落点**: `backend/app/tools/desktop/window_resize.py`

### 8.2 【复核发现B】#30 修复方法 HTTP-date 时区偏移 → 已修

- **原修复代码**: `wait_time = max(int(time.mktime(_dt.timetuple()) - time.time()), 1)`
- **缺陷**: `parsedate_to_datetime` 返回 aware UTC datetime，`.timetuple()` 丢弃时区信息，`time.mktime` 再按**本地时区**解释 UTC 字段。东八区环境下偏移8小时，HTTP-date 格式 Retry-After 正确 3600 秒被算成负数、clamp 成 **1 秒** → 限流后每 1 秒狂重试，违背"尊重服务端 Retry-After 提示"意图。
- **实证**: 本机 UTC+8（time.timezone=-28800），Retry-After=UTC12:00 vs now=UTC11:00：正确 3600 秒，现方案实测 **1 秒**。
- **改法**: `_dt.timestamp()`（aware datetime 直接给 UTC epoch）与 `time.time()` 直接相减，时区无关：
  ```python
  wait_time = max(int(_dt.timestamp() - time.time()), 1)
  ```
- **三堂会审**: 合规=最小改动一行、无重复；合理=aware→epoch 是标准做法，不依赖本地时区；关联=整数/浮点秒分支不动，仅修 HTTP-date 分支。
- **验证**: HTTP-date 未来 3600 秒 → wait=3599 ✓；`py_compile` 通过 ✓。
- **落点**: `backend/app/services/llm/base_service.py`

### 8.3 【理论瑕疵记录】#31 anyOf 边界跨分支分布（按 YAGNI 不改）

- **现实现**: `_extract_numeric_bounds` 取"首个含 min 或 max 的 anyOf 成员"，若成员A仅含 minimum、成员B仅含 maximum，会漏一个边界。
- **实际影响**: Pydantic v2 `Optional[int]` 生成的 anyOf 同分支同时含 min+max，跨分支分布场景现实中不产生。
- **决定**: 按 YAGNI 原则不改，如实记录。若未来接入非 Pydantic schema 再增强为 min/max 分别扫描。
