## 第一部分　yield 前端消息数据

### 1 现状

#### 1.1 全链路数据流（一次任务事件如何到达前端）

```
UniversalAgent.run_react_cycle() 产出 Step 对象
        │  event.to_dict() → step_dict（agent_runner.py:164-171）
        ▼
step_dict（同一份对象，双路分发）
        ├─ ① 落库路：append_execution_step → chat_message_steps.step_json（见第二部分）
        └─ ② yield 路：_append(event_dict)（agent_runner.py:102-113）
                │  d["seq"] = len(buffer.event_log)
                │  buffer.event_log.append(d) + cond.notify_all()
                ▼
          stream_reader(buffer, task_id, after_seq)（stream.py:119-144）
                │  按 seq 偏移读取 → format_agent_sse(step_dict)
                ▼
          SSE 字符串："data: {json}\n\n"（utils/sse_formatter.py:35-59）
                │
                ▼
          前端 fetch/SSE 解析（frontend/src/utils/sse.ts processSSEData）
```

关键结论：**SSE 消息 == step_dict 本身**（format_agent_sse 只加 type/step/timestamp 头，其余字段原样透传），yield 与落库是同一份 step_dict，两路同构。因此「前端能看到的字段」==「落库能还原的字段」==「to_dict() 序列化的字段」。前端看不到的字段，历史回放也还原不了。

> **start 事件属旁路（不予 1.1 双路分发混淆）**：上图"run_react_cycle 双路分发"只覆盖运行期步骤（thought/action/observation/final 等）。**start 事件由 `step_start`（stream_orchestrator.py:208-220）在 agent 启动前直接 `yield format_agent_sse(start_dict)`**，不进 1.2 的缓冲、不走双路分发。后果：start 不落 event_log → 断线重连(after_seq=N)不会重放；它只 append 进 execution_steps 列表随消息落库 DB。

#### 1.2 生产者/消费者解耦模型（task_state.py:24-55）

| 组件 | 位置 | 职责 |
|------|------|------|
| StreamBuffer | task_state.py:24-34 | event_log(append-only 含 seq) / cond / done 三件套 |
| create_stream_buffer | task_state.py:41-45 | 注册 task_id→buffer |
| agent_streams | task_state.py:38 | 全量流态缓冲表（task_id→StreamBuffer） |
| _append | agent_runner.py:102-113 | 生产者写 event_log + notify_all |
| stream_reader | stream.py:119-144 | 纯消费者，按 seq 转发，重连传 after_seq 续传 |
| reclaim_stream_buffer | task_state.py:53-55 | 任务结束后延迟 300ms 回收（agent_runner.py:350-352） |

- 断线重连：`chat_stream_reconnect_orchestrator(task_id, session_id, after_seq)`（stream_orchestrator.py:242-254）复用同一 buffer 按 seq 续传，不重复事件。
- 防挂死：`cond.wait()` 加 60s 超时（asyncio.wait_for），超时后重检 `buffer.done`（stream.py:136-144，2026-07-30 后端卡死根因修复）。
- 防漏事件：排空后复查 `len(buffer.event_log)`（stream.py:131-133，#30 fix，防 done 前追加丢事件）。

> **event_log 定性**：`event_log` 是 `StreamBuffer` 的成员（task_state.py:32），一个 **append-only 的进程内存 `List[Dict]`**，存放在 `agent_streams`（task_state.py:38，进程内全局 dict，task_id→StreamBuffer）。它**只服务于当次运行的 SSE 实时转发 + 断线按 seq 续传，不是持久化**——任务结束由 `reclaim_stream_buffer` pop 回收即消失。**真正的持久化走另一条独立路**：`append_execution_step` 落 `chat_message_steps.step_json`（DB）。即 event_log（内存回放）与 step_json（DB 落盘）是**两条互不相同但同构独立**的通道；event_log 不写磁盘、不写 DB。

#### 1.3 SSE 事件格式（utils/sse_formatter.py:35-59）

> **本节定位**：本节省**格式化层**（纯字符串工具），不是"事件清单"。所有发给前端的事件都会经过 `format_agent_sse` 拼成此格式，但"有哪些事件"由 1.4（Step 字段契约）与 1.5（各场景产出序列）定义；start 事件在 1.4 MetaStep 行、1.5 各场景开头均有，只是不在此节。文件在 `backend/app/utils/sse_formatter.py`（不在 services/chat/）。

```
data: {"type":"<type>","step":<N>,"timestamp":"<本地ISO>", ...step_dict其余字段}\n\n
```

- `format_agent_sse(step_dict)`（sse_formatter.py:53-59）→ `format_sse_event`（:35-50）：纯字符串拼接，`json.dumps(ensure_ascii=False)`；循环引用由 `_break_circular` 兜底（sse_formatter.py:20-32）。
- timestamp 全程本地时区 ISO 无 Z（2026-08-08 全程统一本地时区）。
- 调用方（均经此处出口）：consumer `stream_reader` 转发（stream.py:129）、start 旁路（stream_orchestrator.py:218）、config_error 终态（stream_orchestrator.py:156-166）、错误/终态（handlers.py:44/122）、任务状态（task_runtime.py:76/81）。

#### 1.4 各 Step 字段契约（steps/ 目录，to_dict 输出 == SSE == step_json）

`ReasoningStep.to_dict()`（base.py:70-78）统一输出 `{type, step, timestamp, content}` 四键，再叠加各 Step 的 `_extra_fields()`。`content` 由 `get_content()` 产出。

| Step | type | content 来源 | 顶层字段（_extra_fields 叠加） |
|------|------|--------------|------------------------------|
| ThoughtStep | thought | content/thought | thought、reasoning、tool_name、tool_params |
| ActionStep | action_tool | 空串（get_content 返回 ""，action_step.py:40-41） | tool_name、tool_params、execution_status、**execution_result**(完整 {data, llm_data, other_data} 3 字段)、action_retry_count、execution_time_ms |
| ObservationStep | observation | llm_data 各条 summary 拼接（observation_step.py:44-48） | content(summary)、**llm_data**(列表)、**tool_result**、**other_data**、**parallel_results** |
| FinalStep | final | response | response、thought、outcome(completed/failed/cancelled)、error_type、error_message、model、provider、display_name、accumulated_usage |
| ErrorStep | error | error_message | error_type、error_message |
| ChunkStep | chunk | 流式回复片段 | content |
| MetaStep | start/cancelled/paused/resumed/retrying/authorization_required | 统一 content 文本（base.py:126 字段契约） | 透传 kwargs（confirm_id/tool_name/params/safety_level/wait_time/data 等） |

- 终态统一由 `final` 承载：FinalStep 多态（outcome=completed/failed/cancelled），前端按 outcome 分流（final_step.py:24-105，2026-07-18 重构）。
- 步骤计数：`create_step_counter()`（base.py:84-93）闭包 `next_step()` 全局唯一递增。
- 各 Step 在同一抽象层：Step 对象在 react_cycle 内 `emit` → `_step_emitter.emit(step)`，最终回到 agent_runner 的 `async for event` 循环。

#### 1.5 各场景产出的 Step 类型（前端看到的剧本）

> 注：`MetaStep(start)` 由 `step_start`（stream_orchestrator.py:208-220）**在 agent 启动前前置产出**，不走 1.2 缓冲（见 1.1 旁路说明）；表中其余步骤均由 react_cycle 产出。

| 场景 | 产出序列 |
|------|---------|
| 正常调工具（单/并行） | MetaStep(start) → ThoughtStep → ActionStep(每工具一条) → ObservationStep → … → FinalStep(completed) |
| 并行工具 | 1 条 assistant 带 N 个 tool_calls + N 条 ActionStep + 1 条 ObservationStep（action_handler.py:656-663 配对规则） |
| 空响应/未调工具（B3） | MetaStep(start) → MetaStep(retrying) → 循环 → FinalStep |
| 同工具/同参数死循环 | ThoughtStep + 纠偏 warning（_temp_same_tool_warn 临时标记，不入库）→ 循环 → FinalStep |
| 截断 | MetaStep(truncated)（上下文超限） |
| 失败 | MetaStep(start) → … → FinalStep(outcome="failed", error_type, error_message) |
| 取消 | MetaStep(cancelled) + FinalStep(outcome="cancelled")（agent_runner.py:205-216 取消分支 + finally 守卫补发） |
| 暂停 | MetaStep(paused) / MetaStep(resumed) |

#### 1.6 前端消费实况

- **工具结果渲染**：ToolResultRenderer 的 30+ 个 Renderer（frontend/src/components/Chat/ToolResultRenderer/types/*.tsx）**全部从 `step.execution_result` 取 `llm_data`**：
  ```ts
  const execResult = (step.execution_result || {}) as Record<string, unknown>;
  const llmData = (execResult.llm_data || {}) as Record<string, unknown>;
  ```
  成功判定统一以 `llm_data.status.exec_code === "success"` 为准（各 Renderer 文件头注释一致）。
- **observation 步骤展示（现状有缺陷）**：StepContent.tsx:140-474 observation 分支以 `obsStep.observation` 是否为 object 判定展示（`isObjFormat = obsStep.observation !== null && obsStep.observation !== undefined && typeof obsStep.observation === 'object'`，与 StepContent.tsx:144-146 一致），但**后端 `ObservationStep._extra_fields()` 从不产出 `observation` 字段**（仅输出 `llm_data`/`tool_result`/`other_data`/`parallel_results`，observation_step.py:50-59）。故 `obsStep.observation` 恒为 `undefined` → `rawObs = null` → `llmData/summary` 全走 `??` 兜底 → **最终 `summary = ''`**。即当前 observation 步骤在前端**实际渲染为空**（ExecutionPanel.tsx:387-391 case 'observation' 同理）。这是"前端看不到真实 observation"的更直接根因，比"只存 summary"更根因。
- **依赖方向**：前端随后端修改，契约以后端 step_dict 为准，前端不质疑后端字段（AGENTS.md 1.5 前后端规范）。

### 2 问题

#### 2.1 真身不入库/不 yield

`build_observation_text`（observation_formatter.py:1466）的产物 `obs_text`（action_handler.py:729 异常分支 / 733 正常分支）与最终 `merged_obs`（action_handler.py:779，`"\n\n".join(obs_parts)`）是**喂给 LLM 的确切 observation 文本**（经 message_builder.add_tool_result 进 conversation_history，message_builder.py:124-144、action_handler.py:768/772）。但 ObservationStep.to_dict() **不序列化该文本**——它不进 SSE、不入库。

#### 2.2 落库的只是 summary 拼接

ObservationStep.get_content() 仅从 llm_data 各条取 `summary` 字段拼接（observation_step.py:44-48）。summary 是各 tool 自己写的短摘要，**不是**喂 LLM 的完整 observation 文本。

#### 2.3 历史回放失真

多轮上下文加载 `_load_previous_messages`（stream.py:87-116）→ `_parse_observations`（stream.py:67-84）只读 `step.get("content")`（= summary），用它重建 `role:tool` 消息。结果：**历史回放中 LLM 看到的 observation 是截断后的 summary，而非原始完整 observation**——功能退化（多轮对话上下文质量下降、复杂任务需回读全文时信息丢失）。

#### 2.4 排查困难

日志/DB 中无 observation 原文，排查"LLM 为什么这么回答"需重新跑 observation_formatter 格式化逻辑才能复原（action_handler.py:738-745 处仅日志记录 raw_data，无格式化后文本）。

#### 2.5 字段冗余（次要问题）

ObservationStep 同时携带 content(summary) 与 llm_data/tool_result，两处信息冗余且口径不一致（summary 截断 vs 完整 data），字段职责不清。

#### 2.6 前端事实性硬伤

原版本（v2.0）1.6 节称"前端 observation 分支读 `obsStep.observation`（object 时读其 llm_data）"，但后端 `ObservationStep` 从不产出 `observation` 字段，该分支是**永不触发的死路**——前端 observation 步骤实际渲染为空。这才是"前端看不到真实 observation"的直接根因；改进方案必须同步修正前端取数字段名（读 `observation_text`/`content`），而非沿用 `obsStep.observation`。

### 3 更好的方案（先派生、后保真，单向依赖）

#### 3.1 首选方案（DRY 单一来源，零新增字段）

回放时由 `ActionStep.execution_result` + 同一 `build_observation_text`（action_handler.py:733）重新派生 observation 文本，而非落库一份派生字符串。`execution_result`（`{data, llm_data, other_data}`）已是完整权威副本，喂 LLM 的 `merged_obs` 由其确定性派生（= `build_observation_text(result, tool_name, tool_params)` 拼接），无需新增字段，最契合 DRY/YAGNI。

> **诚实边界**："重跑同一函数"可**近似复原**，不能**逐字节复原**——`merged_obs` 含运行时上下文，回放无法重建：①异常分支包装 `f"Observation: 工具...执行异常: {result}"`（action_handler.py:729）；②`repair_warning` 前缀（action_handler.py:759-761，来自运行时 `_temp_same_tool_warn`，不入库）。这些前缀只在发生相应运行时分支时存在，多数正常路径可精确复原；但在异常/纠偏路径上与当时喂 LLM 的文本有差异。

#### 3.2 首选/保真决策标准

是否新增 `observation_text`，取决于**是否接受两处近似**——(a) `repair_warning`/异常包装的近似复原；(b) `build_observation_text` 日后变更导致的漂移。默认用首选（零字段、零膨胀）；仅在需要"回看当时逐字喂 LLM 的 observation"的**排查/审查**场景启用保真。启用保真须满足下述约束，否则引入新冗余：

| 约束 | 要求 | 理由 |
|------|------|------|
| 依赖方向 | **单向依赖**："加 observation_text" 依赖 "删四字段"（纯加会冗余增到 5 个）；"删四字段" **本身独立安全**，首选方案下可单独落地 | 删四字段只需"前端不从 ObsStep 加字段取数 + 回放改从 execution_result 派生"，与是否加保真字段无耦合；只有"只加不删"才会退化，故仅约束"加须建立在删之上"，不强制双向同批回滚 |
| 落库口径 | `observation_text` 直接对**已截断后的 execution_result** 派生、原样落库，**不再二次截断** | 各 tool 已自行截断输出（第二部分 5.6 阈值依据），故 `merged_obs` 体量受 tool 层截断约束、无爆炸风险；对已截断数据派生使两源天然同口径，无需为"是否截断"设双轨，消解"保真 vs 截断"矛盾 |
| 前端取数修正 | 前端 observation 分支改读 `observation_text`/`content`，**删除 `obsStep.observation` 死分支**（问题 2.6） | 否则加字段前端也读不到，定案名不副实 |
| 多轮回放 | `_parse_observations`（stream.py:67-84）：首选方案下由 execution_result 重新派生；保真方案下优先读 `observation_text`、回退 `content` | 多轮对话上下文质量与首次一致（功能增强，禁止 backward） |

#### 3.3 两方案对比

| 维度 | 首选方案 | 保真兜底方案 |
|------|---------|-------------|
| 字段 | 不新增 | ObservationStep 增 `observation_text`（observation_step.py 增构造参数 + `_extra_fields()` 输出 + `get_content()` 优先返回） |
| 数据源 | execution_result（action_handler.py:656-662 已产出） | action_handler.py:779 `merged_obs`（含异常分支 obs_text:729 与 repair_warning 前缀:759-761） |
| 落库 | 无新增；回放派生 | 随 step_json 持久化 |
| yield | 无新增 | SSE 自动透传，前端无需改传输层 |
| 体积 | 零增长 | 需评估（可能与 execution_result 截断口径冲突） |

#### 3.4 方案理由

原 v2.0"一增全通"用 DRY 作为删四字段的理由，转头却新增一份派生文本 `observation_text` 落库，标准不自洽。本方案把"删冗余原始副本"与"是否存派生文本"分开决策——**先选零字段派生（最优），确有保真需求再存，且存时须建立在"删四字段"之上（单向依赖）、口径一致、前端改读**。不新增 is_success/summary 等冗余字段（llm_data.status.exec_code 已是权威源）。

### 4 实施计划

#### 4.1 实施计划

| 步骤 | 动作 | 涉及文件 | 依赖 | 验证 |
|------|------|---------|------|------|

#### 5.7 现状存储形态：同一工具结果两处存放（问题根源）

**ActionStep**（action_handler.py:656-663）：
```python
ActionStep(step, tool_name, tool_params, execution_result=result, execution_status=_ec)
```
存**完整** `execution_result` = {data, llm_data, other_data} 3 字段。

**ObservationStep**（action_handler.py:817-823）：
```python
ObservationStep(step, llm_data=llm_data_list, tool_result=…, other_data=merged_other, parallel_results=_parallel_results or None)
```
又存一遍 `llm_data`(列表) + `tool_result` + `other_data` + `parallel_results`。

提取过程（action_handler.py:781-800）：从每个 result 重新拆 `_all_llm_data/_all_tool_results/_all_other_data/_parallel_results`，同一份数据第二份副本。

### 6 问题

#### 6.1 双重存储（核心问题）

同一工具结果存两份——ActionStep.execution_result（完整 3 字段，action_handler.py:656-663）与 ObservationStep.tool_result/llm_data/other_data/parallel_results（action_handler.py:786-800、817-823）。后果：
- **库膨胀**：大工具结果（文件列表、搜索全文）双份持久化，chat_message_steps 体积翻倍；
- **写 I/O 翻倍**：每步截断 + dumps + INSERT 处理两份数据；
- **字段漂移风险**：两处口径一旦不同步（如某 tool 改返回结构），前端读 execution_result、回放读 observation，出现不一致；
- **截断双重处理**：_truncate_step_dict 需同时兜底 execution_result 与 observation 的 tool_result/parallel_results（storage.py:282-297），复杂度与漏截风险高。

#### 6.2 截断机制未定案

storage.py:254 临时 TODO「实验性的功能」未正式化；截断范围（哪些字段）与阈值（1000/100000）无正式设计依据背书。

### 7 更好的方案（一删、一治本、一收敛）

#### 7.1 动作清单

| 动作 | 内容 | 理由 |
|------|------|------|
| 删 | ObservationStep 删 `tool_result`/`llm_data`/`other_data`/`parallel_results` | 单一权威副本=ActionStep.execution_result；前端渲染本就全从 execution_result 取（第一部分 1.6 节），删除无退化。**独立安全落地**；若启用保真 observation_text（第一部分），其"加"须建立在本次"删"之上（单向依赖，纯加会冗余） |
| 治本 | `build_observation` 内 `action_handler.py:781-800` 的二次拆包（重循环 `ctx.results` 拆 `_all_llm_data/_all_tool_results/_all_other_data/_parallel_results`）删除，ObservationStep 直接复用 ActionStep 已持有的 `execution_result`（或第一轮循环结果） | 双存储的根因是"同一份 result 被拆两遍"，仅删字段只堵出口、二次拆包代码仍残留；根治须让 ObservationStep 引用已产出副本，消除冗余拆包与算力浪费 |
| 定 | 截断对象收敛为**仅 ActionStep.execution_result** | observation 已删 tool_result，截断只需兜底 execution_result 一处 |
| 定 | `observation_text`（保真兜底时）**对已截断 execution_result 派生、原样落库，不二次截断** | 两源天然同口径，无需"是否截断"双轨；tool 层已自行截断故无膨胀，DB 行溢出风险已由 execution_result 截断兜底覆盖（原 TODO 本为防 SQLite 行溢出） |
| 清 | 删 storage.py:254 临时 TODO，引用本设计文档 | 消除「实验性」残留，正式定案 |
| 保 | ObservationStep 保留 content（summary）用于前端展示 | 前端 observation 步骤展示总结文本（第一部分 1.6 节修正后改读 observation_text/content），不重复取数 |

#### 7.2 收敛后存储形态

- ActionStep.execution_result：完整权威副本（截断兜底对象）；首选方案下回放由其重新派生 observation，零新增字段。
- ObservationStep.observation_text（仅保真兜底时）：喂 LLM 的完整 observation 文本，**对已截断 execution_result 派生、原样落库，不二次截断**（两源天然同口径）。
- ObservationStep.content：summary 展示文本；
- 其余（tool_result/llm_data/other_data/parallel_results）不再入 ObservationStep，随 execution_result 单一存放；`build_observation` 内二次拆包代码同步删除（治本）。

#### 7.3 不做

- 不新增 is_success/summary 冗余字段（llm_data.status.exec_code 已是权威源）；
- 不新建独立 observation 表（step_json 已结构化，无需第三张表）；
- 不拆多条步骤（保持一行=一步的既有契约）；
- **不"只加不删"**（纯加 observation_text 会让冗余从 4 个字段增至 5 个）；"删四字段"本身独立安全、可单独落地（7.1 表"删"行），与是否加保真字段无耦合。

#### 7.4 影响面核对

- 前端 30+ Renderer 全从 execution_result.llm_data 取数 → 删 observation 内冗余字段不影响；
- StepContent.tsx observation 分支：删除 `obsStep.observation` 死分支，改为读 `observation_text`/`content`（第一部分 2.6）；
- _parse_observations：首选方案下由 execution_result 重新派生；保真方案下优先读 observation_text 回退 content，回放质量增强；
- _truncate_step_dict：删 observation 相关分支（tool_result/parallel_results），仅保留 execution_result；
- react_cycle 终态语义、derive_status_from_steps（storage.py:71-83）、load_execution_steps 均不受影响。
