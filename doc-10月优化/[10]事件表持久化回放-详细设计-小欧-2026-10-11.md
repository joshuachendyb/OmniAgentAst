## 一、需求点

### 1.1 北京老陈原始需求（2026-10-11）

> 「这个事件表里面有好些事件，也不是一个 reject。我的设想是——事件表，任务跑完成了，事件表信息回填后端，下一次看历史任务的时候，事件表能够显示和不显示，我可以设置。这样简单点，不是的吗」

### 1.2 拆解为可验收条目

| # | 需求点 | 验收标准 |
|---|--------|---------|
| N1 | 任务事件表（paused/resumed/retrying/rejected/error/裁剪/压缩等**全部**事件，非仅 reject）在任务结束时持久化 | 任务完成后 `chat_tasks` 新列有值；中断任务不写（可接受） |
| N2 | 历史任务回放时事件表能显示 | 刷新页面/切历史会话，事件列表条数与实时一致 |
| N3 | 事件表显示与不显示**用户可配置** | 设置项开关，持久生效 |
| N4 | **不破坏**「meta 不落库」既有设计 | `chat_task_steps` 表结构不变；`M_SKIP` 集合不变；统计口径不变 |
| N5 | 实时与历史的事件文案**完全一致** | 同一事件在实时/历史下文案逐字相同 |

### 1.3 明确不在本期范围

- 不改 `chat_task_steps` 表结构与逐步落库链路
- 不改 `M_SKIP` / `SSE_ONLY_TYPES` 两个集合的成员
- 不改 `total_steps` / `step_count` 等统计口径
- 不改 pipeline 业务流（`isBusinessStep` 分流）

## 二、现状定案（实读代码，非推测）

### 2.1 事件当前在哪里被丢弃

`agent_runner.py:480-505` 的 `_route_step_to_db` 是事件落库的**唯一真源**（注释自述「扫描机制退役后本函数为唯一真源」）：

```python
def _route_step_to_db(ed: Dict) -> None:
    _t = ed.get("type", "")
    if _t in SSE_ONLY_TYPES:
        if _t == "usage":
            _step_queue.put_nowait(("token", int(ed.get("step") or 0), ed))
        return                                    # 仅 SSE 不落 chat_task_steps
    ...
```

`SSE_ONLY_TYPES` 定义在 `agent_telemetry.py:91-94`：

```python
SSE_ONLY_TYPES = frozenset({          # 维度1: 仅 SSE 下发, 不落 chat_task_steps
    "chunk", "thought-start", "error", "usage", "paused",
    "resumed", "retrying", "cancelled", "rejected",
})
PERSISTED_NON_BIZ_TYPES = frozenset({ # 维度2: 落库(需回放)但不计业务步
    "start", "stats", "history_context", "final_stats", "authorization_required",
})
M_SKIP = SSE_ONLY_TYPES | PERSISTED_NON_BIZ_TYPES
assert not (SSE_ONLY_TYPES & PERSISTED_NON_BIZ_TYPES)
```

**实测佐证**：直接查 `~/.omniagent/chat_history.db` 的 `chat_task_steps.step_json`，
type 分布为 `stats 5063 / thought 4282 / action 4232 / observation 4232 /
history_context 1609 / start 797 / final 782 / final_stats 781 / merged 116`，
**`rejected` 为 0 条**——与代码一致。

### 2.2 前端两条数据通道

`useTaskInfo(steps, frames, ...)` 消费两条**独立**通道：

| 通道 | 来源 | 承载 |
|------|------|------|
| `steps: ExecutionStep[]` | `chat_task_steps`（逐步落库） | 时间线：thought/action/observation/final |
| `frames: TaskMetaFrames` | `chat_tasks`（任务级汇总） | `startInfo` / `finalStats` / `contextSummary` / `taskAccumulated` |

事件列表 `processEvents` 目前**完全由 `steps` 遍历派生**（`useTaskInfo.ts:221` 起
`for (const s of steps) { switch (s.type) ... }`）。因 `steps` 里永无 SSE-only 类型，
`paused`/`retrying`/`rejected`/`context_trimmed` 等事件**历史回放时一律消失**。

### 2.3 已完成的实时链路（本期基线，已提交 `c32bda115` 之外的独立改动）

2026-10-11 已实施并提交：sseParser 让 `rejected` 入流、`META_STEP_TYPES` 加 `rejected`、
`useTaskInfo` 恢复 `case 'rejected'`。**该改动只解决实时，历史仍缺**（本文解决）。

### 2.4 既有可复用资产（复用优先，不新建轮子）

| 资产 | 位置 | 复用方式 |
|------|------|---------|
| JSON 列先例 | `chat_tasks.artifacts TEXT DEFAULT '[]'` | 新列照抄形态 |
| 幂等迁移器 | `_ensure_column(conn, 表, 列, 定义)` | 已在 `chat_tasks`/`chat_sessions` 跑 6 次 |
| 终态写入点 | `agent_runner.py:769 _finalize_task_db` | 事件表挂此处同事务 |
| 偏好单一真源 | `config.yaml → appearance.step_render` | 加一键，开关走同款 |
| 偏好读取 hook | `useStepRenderPrefs` | 事件表开关复用该通路 |
| 事件条数上限 | `useTaskInfo` `slice(-20)` | 体积天然有界，≤20 条 |
| 归因映射 | `ToolCallLine.REJECT_LABEL_MAP` | 已导出，文案同源 |

## 三、方案选型

### 3.1 候选对比

| 方案 | 覆盖范围 | 是否破坏 meta 不落库 | 后续加新事件成本 | 派生一致性 | 结论 |
|------|---------|--------------------|----------------|-----------|------|
| ① `rejected` 挪进 `PERSISTED_NON_BIZ_TYPES` | 仅 rejected 一种 | **是** | 每加一种改一次后端 | 同一份代码 | 否 |
| ② 新建 `chat_task_rejects` 表 | 仅 rejected | 否 | 同上 | 需双源合并 | 否 |
| **③ 事件表整表回填 task 行（本方案）** | **全部事件** | **否** | **零改动** | **同一份代码** | **采纳** |

### 3.2 方案③的核心设计决策

**决策1：存原始帧，不存成品文案。**

存 `{type, step, content, timestamp, reject_type?, tool_name?}`，**不存**拼好的
`安全 · 工具delete_file：xxx`。回放时前端复用**同一套 `useTaskInfo` 派生逻辑**。
若存成品文案，该格式会散落进 Python 与 TypeScript 两处，日后改文案必分叉，
直接违反 N5。

**决策2：后端主动写，前端不回传。**

后端在 `_route_step_to_db` 处本就持有全部事件帧（丢弃前），顺手收集即可。
若走前端 POST 回传，则多一条 API、多一处客户端可信度问题，且用户关页面即丢。

**决策3：任务结束时一次性写，失败即失败。**

挂在 `_finalize_task_db` 的既有 `atxn`。服务器中断→不写，用户已明确可接受
（事件表是辅助展示信息，非审计数据）。

**决策4：走 `frames` 通道而非 `steps` 通道。**

事件表是「任务级汇总」，与 `finalStats`/`startInfo` 同粒度，归 `chat_tasks` 行，
回放时并入 `frames`。**不动 `chat_task_steps`，`META_STEP_TYPES` 与
`isBusinessStep` 分流零改动。**

#### ① `backend/app/monitoring/agent_telemetry.py` —— 新增事件收集器

在 `M_SKIP` 定义之后（约 101 行）新增：

```python
# 2026-10-11 小欧 - 北京老陈令(事件表持久化回放): SSE-only 事件收集器
PROCESS_EVENT_CAP = 20          # 与前端 useTaskInfo slice(-20) 同上限, 体积有界

def collect_process_event(agent, ed: Dict) -> None:
    """收集 SSE-only 事件到 agent 内存(任务结束时一次性回填 chat_tasks.process_events)
    仅在 _route_step_to_db 的 SSE_ONLY_TYPES 分支调用, 不影响落库路由"""
    lst = getattr(agent, "_process_events", None)
    if lst is None:
        lst = []
        agent._process_events = lst
    lst.append({
        "type": ed.get("type", ""),
        "step": ed.get("step"),
        "content": ed.get("content", ""),
        "timestamp": ed.get("timestamp"),
        "reject_type": ed.get("reject_type"),
        "tool_name": ed.get("tool_name"),
    })
    if len(lst) > PROCESS_EVENT_CAP:
        del lst[:-PROCESS_EVENT_CAP]      # 超限丢最旧, 保最近
```

**注意**：仅收集 `SSE_ONLY_TYPES` 成员。`start`/`stats`/`final_stats`/
`history_context` 属 `PERSISTED_NON_BIZ_TYPES`，已在 `chat_task_steps` 里，
**不重复收集**（否则事件列表会双份）。

#### ⑦ `frontend/src/features/chat/hooks/useTaskInfo.ts` —— 事件源合并

现状：`processEvents` 只由 `for (const s of steps)` 派生（约 221 行起）。
改为：**先把 `frames.processEvents` 铺入**，再叠加 steps 派生的事件。

```ts
// 2026-10-11 小欧 - 历史回放事件源(北京老陈令): frames.processEvents 是后端回填的原始帧,
//   与实时 steps 派生走同一套文案规则, 保证 N5 实时/历史一致。
//   实时态 frames.processEvents 为 null, 行为与从前逐字一致。
const _historyEvents = frames.processEvents ?? [];
if (_historyEvents.length > 0) {
    for (const e of _historyEvents) {
        processEvents.push({
            kind: e.type as ProcessEvent['kind'],
            text: deriveEventText(e),     // 抽出的共用文案函数, 见 ⑧
            time: e.time,
        });
    }
}
```

**关键约束**：`kind` 必须是 `ProcessEvent['kind']` 合法值。非法值需过滤，
否则 `EVENT_ICON_MAP[e.kind]` 取到 `undefined` 导致图标空白。

#### ⑧ 文案派生抽函数 —— `useTaskInfo.ts` 内

当前各 `case` 内是硬编码文案（`s.content || '发生错误'` 等）。需抽
`deriveEventText(e)` 纯函数，供**实时 steps 派生与历史 frames 派生共用**，
这是 N5 的实现关键。`rejected` 分支沿用既有写法：

```ts
const _label = REJECT_LABEL_MAP[e.reject_type ?? ''] ?? REJECT_DEFAULT_LABEL;
text = `${_label} · ${tool}${content ? '：' + content : ''}`;
```

## 五、风险与回滚

### 5.1 风险清单

| # | 风险 | 等级 | 缓解 |
|---|------|------|------|
| R1 | `kind` 非法值致图标空白 | 中 | 写入前按 `ProcessEvent['kind']` 白名单过滤，非法值跳过 |
| R2 | 偏好键未在 settings registry 登记致读取失败 | 中 | 实施时实读 registry 并同步登记（该坑已在 `useStepRenderPrefs` 注释中写明） |
| R3 | 中断任务丢事件表 | **低（已接受）** | 用户明确「失败就失败，不紧要」 |
| R4 | 事件表与 `chat_task_steps` 双份 | 低 | 收集器只收 `SSE_ONLY_TYPES`，与已落库类型互斥 |
| R5 | 大任务事件表膨胀 | 低 | 上限 20 条硬截断（前后端同值） |
| R6 | 存量任务无该列数据 | 低 | `DEFAULT '[]'`，前端 `?? []` 兜底，旧任务事件列表为空（与今天一致） |

### 5.2 回滚方式

本方案**不修改既有数据**，仅加一列，故回滚极简：

- **代码回滚**：`git revert` 对应 commit，`chat_task_steps` 与统计口径从未被触碰
- **数据回滚**：`ALTER TABLE chat_tasks DROP COLUMN process_events;`（SQLite 3.35+ 支持）
- **残留**：已写入的 `process_events` 值不被读取即等于无影响

## 七、三堂会审自查（小欧 2026-10-11 08:56:28）

### 7.1 合规检查（10 大规范）

| 规范 | 结论 |
|------|------|
| SRP | 收集器只做「收集+截断」，不碰落库路由；`update_task` 只加参数不加工 |
| DRY | 列形态抄 `artifacts`；迁移抄 `_ensure_column`；偏好抄 `useStepRenderPrefs`；文案抽共用函数供实时/历史共用 |
| KISS-DIRECT | 链路单一：`_route_step_to_db` 收集 → `_finalize_task_db` 随既有事务写出，无中间层 |
| SLAP | 收集器不读 DB、不发 SSE，只拼 dict |
| YAGNI | 不建新表、不加索引、不做前端回传 API、不改 `SSE_ONLY_TYPES` |
| 禁止 backward | 无兼容分支，旧数据靠 `DEFAULT '[]'` + 前端 `?? []` 天然兜底 |
| OCP | 新增事件类型无需改本方案任何代码（收集器按运行时 type 收集） |
| 复用优先 | 7 项既有资产全部复用（见 2.4），零新建轮子 |
| 关联逻辑 | 已核 `M_SKIP`/统计/`isBusinessStep` 三处下游不受影响 |
| 编辑历史 | 各文件头集中记录，最新条目置旧条目之后 |

### 7.2 合理检查

- **为何不存成品文案**：会导致文案格式双语言分叉，违反 N5。已定为存原始帧。
- **为何后端主动写而非前端回传**：后端本就持有帧；回传多一条 API 且客户端数据不可信。
- **为何上限 20**：与前端 `slice(-20)` 同值，避免「后端存 50 条前端只显 20 条」的隐性截断不一致。
- **为何挂 `_finalize_task_db` 而非新开事务**：复用既有 atxn，少一次写，且与终态数据同批提交，天然一致。

### 7.3 关联检查

| 上下游 | 是否受影响 | 依据 |
