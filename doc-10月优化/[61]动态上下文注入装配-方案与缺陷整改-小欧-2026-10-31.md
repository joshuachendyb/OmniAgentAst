## 一、结论摘要

北京老陈提出：昨天的两个大更新（引用后台优化、事项工作目录优化）都往 `role=user` 新任务消息里塞信息，是不是最佳方案。

**核对结果：塞进 user 消息这个方向是对的；具体装配方式不对，而且不统一。**

| 注入项 | 位置 | 装配通道 | 证据 |
|--------|------|----------|------|
| 引用正文（refs） | 用户原话**之前** | `_start_meta` 结构化透传 → agent 层 `init_history` | `message_builder.py:334` |
| 事项目录（workspace） | 用户原话**之后** | orchestrator 层字符串拼接 `_append_ws_suffix` | `stream_orchestrator.py:470-473` |

由此得出三条结论：

1. **载体正确**（第三章）：进 system 破坏 prefix cache 且越权；独立 user 消息会造幻影轮次；`role=tool` 直接 400；让模型自己调工具取则不可靠。
2. **装配错误**（第四章）：两条独立通道 + 相反位置，已经造成插话漏注（D1），并派生出截断优先级、可观测性、标志一致性等 5 条缺陷。
3. **收口方案**（第五章）：单一装配点 `build_user_turn_text`，两块统一前置、统一标志、统一截断与回执，用户原话永远最后一段。

## 二、现状

### 2.1 首发链路（新任务）

```
orchestrator  user_input = messages[-1].content                 # 用户原话，干净
orchestrator  sanitize_refs(refs) → prepare_refs(...) → _final   # 越界过滤 + 读盘 + 体积裁决
orchestrator  agent._start_meta["refs"] = _final                 # 通道 A：结构化
orchestrator  run_agent_in_background(..., _append_ws_suffix(user_input), ...)   # 通道 B：字符串（:970）
        ↓
react_loop.py:208     init_history(sys_prompt, task, refs=_start_meta["refs"])
message_builder.py:334  add_user_message(render_refs_block(refs) + task_prompt)
```

### 2.2 插话链路（任务执行中注入）

```
stream_orchestrator.py:672
inject_message_to_task(_active_tid, render_refs_block(_ifinal) + user_input, _user_msg_id)
```

只拼引用块，**没有**目录块。2026-10-30 的 A19 整改把 refs 收口到 `prepare_refs` 流水线并覆盖了插话分支，workspace 仍是首发路径专属。

插话落位有两条分支（`react_step.py:260-270`）：

| 分支 | 条件 | 结果 |
|------|------|------|
| 并入末条 | 末条已是 user（用户刚发完、模型还没回） | 追加到同一条 user 消息尾部 |
| 独立成轮 | 末条非 user（生产常态） | 新增一条 user 消息 |

### 2.3 两条通道的差异（D1 的根因）

| 维度 | refs（通道 A） | workspace（通道 B） |
|------|---------------|-------------------|
| 载体 | `_start_meta` 结构化字段 | 已拼好的字符串 |
| 装配点 | agent 层 `init_history` | orchestrator 层 `_append_ws_suffix` |
| 位置 | 问题之前 | 问题之后 |
| 插话能否复用 | 能（同一渲染函数） | 不能（分支里没有调用） |

通道不同不是风格问题，而是**结构性保证的差异**：通道 A 有"单一渲染函数"，通道 B 只有"一个只在首发路径被调用的私有函数"。插话漏注是这种结构的必然结果，不是某次改动的疏忽。

### 2.4 数据边界：什么落库、什么不落库

两个注入块**都不落会话库**，只在交给 agent 的 `last_message` 上叠加：

| 数据 | 内容 | 证据 |
|------|------|------|
| 用户消息入库 | 前端 POST 原文，后端不重写 | `message_service.py:240` |
| `chat_tasks.user_input` | 编排层的干净 `user_input` | `stream_orchestrator.py:839` |
| 历史回灌 | `chat_user_message.content`，不含块 | `history_loader.py:241` |
| 注入块 | 只存在于本轮 `last_message` | `stream_orchestrator.py:970`、`message_builder.py:334` |
| prompt 日志 | 含块，属可审计调试产物，不是会话数据 | `agent_runner.py:355` |

这个边界必须守住，理由见 7.3。

### 2.5 摘要与裁剪如何对待注入块

| 机制 | 是否接触注入块 | 依据 |
|------|--------------|------|
| 启动摘要 | **不接触**。输入是 `agent._injected_history_msgs`，来自 DB 历史 | `start_step.py:348` |
| 启动阶段超窗收缩 `shrink_to_budget` | **不接触**。作用在同一份 DB 历史 | `start_step.py:442` |
| loop 内轮次裁剪 `trim_history` | **接触**。作用在 `conversation_history` | `message_builder.py:585` |
| 单条超长截断 `truncate_oversized_message` | **不接触 user**，只处理 `tool`/`assistant` | `split_turn.py:219` |
| 旧轮 tool 清零 `prune_tool_output_keeping_tail` | **不接触**，只清 tool 输出 | `prune.py:184` |

裁剪对两块**没有差别待遇**：

- 切点对齐 user 边界、整轮不拆（`find_tail_start(align_turn=True)`，`message_builder.py:633`），块随所在 user 轮整体保留或整体丢弃；
- 当轮必在保护区（倒数 N 个工具轮，默认 5，`find_recent_rounds_start`），所以当前轮的块不会被裁；
- 任务变长后该轮变旧轮，则**两个块一起走**，不存在"引用丢、目录留"。

**唯一例外**：插话合并超长时保尾部（`react_step.py:248-250`），前置的注入块会先被截掉。这是有意的优先级（用户原话 > 元信息），但属静默丢块，需补日志（5.6）。

结论口径：**摘要与块无关；裁剪连轮带块一起丢；在裁剪口径内两块同生共死，唯一例外是超长插话截断（见上）。**

## 三、载体选型：为什么必须塞进同一条 user 消息

### 3.1 否决：进 system prompt

system 在消息序列位置 0、会话级构建一次。动态内容进 system 等于每轮改写前缀，**prefix cache 全失效**。更严重的是 refs 属用户可控文本（不可信数据），放进 system 等于把它抬到系统权限，与现有「不可信数据边界」声明自相矛盾（`refs/render.py`）。

### 3.2 否决：单独发一条 `role=user` 注入消息

本系统以 user 消息为轮次边界：`find_tail_start(align_turn=True)` 按 user 切轮；保护区轮数与摘要注入件尾部轮数都按 user 计数（`resolve_protect_rounds`）；摘要阈值与裁剪预算全部建立在"轮"语义上。

伪造一条 user 消息会造出**幻影轮次**：轮次计数虚高、保护区实际变短、摘要切片错位，而且该消息会被写入历史，前端出现脏消息。

插话路径在"末条已是 user"时选择并入末条（2.2），正是为了不产生连续 user——这是同一条约束的另一面。

### 3.3 否决：`role=tool` 注入

没有配对的 `tool_call_id`，上游 provider 严格校验直接 400（本仓已有同类实证：`message_builder.py` 编辑历史记录的「tool result's tool id not found (2013)」）。

### 3.4 否决：让模型按需调工具取

多一轮 LLM 往返（延迟 + token），且模型经常不调。事项目录是**执行前提**而不是可选资料，不能赌模型主动查询。

### 3.5 小结

注入进本轮 user 消息正文是正解，业界同类实现（Claude Code 的 `system-reminder` 块）同样选择塞进 user 消息。真正要解决的是"怎么装"，不是"装哪"。

## 四、缺陷清单

### D1｜插话路径漏注事项目录（高）

- **现象**：任务执行中用户改了事项目录后插话，目标 agent 收不到任何目录信息。
- **证据**：`stream_orchestrator.py:672` 只拼 refs；对照 `:970` 首发路径有 `_append_ws_suffix`。
- **后果**：模型继续按旧目录写临时/中间文件，用户以为改了目录就生效，实际文件落在旧路径。
- **建议**：并入 5.1 单一装配点；批 1 可先补一行调用止血，批 2 该行随 `_append_ws_suffix` 一起删除（不保留双实现）。

### D2｜位置口径相反，尾部放置违背「问题压末」（中）

- **现象**：refs 前置、目录块尾置，同一轮两种相反的排版约定。
- **证据**：`message_builder.py:334` vs `stream_orchestrator.py:470`。
- **后果**：目录块的约束句「要求生成临时/中间文件，请写入…」压在用户原话之后，与主任务争抢末位权重；长上下文下模型更容易把元指令当主任务收尾。
- **建议**：统一前置，用户原话永远最后一段（5.2）。

### D3｜截断优先级错位：默认工作区不优先（中）

- **现象**：`_append_ws_suffix` 按纯路径字典序排（`sorted(entries, key=path)`），贪心累计到 `MAX_WS_INJECT_CHARS=4096` 后跳过剩余。
- **证据**：`stream_orchestrator.py:440-478`；`workspace_service.py:47`（上限）、`:28`（`MAX_WORKSPACES=64`）。
- **量化**：64 目录 × 约 250 字符 ≈ 16KB，实际只能留约 16 条、跳过 48 条。默认工作区（`is_default=True`）若字典序靠后会被优先跳过。
- **后果**：模型不知道默认工作区，临时文件写到别处或反问用户。
- **建议**：截断前按「默认工作区 → 带属性/memo → 其余」排序，并对默认工作区设保留位（5.4）。

### D4｜可观测性不对称（中）

- **现象**：refs 有完整回执（越界/不可读/截断都点名给用户），目录块注入零回执、零日志。
- **证据**：`refs/pipeline.py` + `refs/notice.py` 三通道回执；目录侧仅 `_append_ws_suffix` 内拼接。
- **后果**：目录被截断（D3）或插话未注入（D1）时前端完全无感，用户无从判断模型为何走错路径。
- **建议**：注入/跳过条数进日志；被截断时复用现有 notice 通道给一句轻提示（5.6）。

### D5｜块标志与块内用语不一致（低）

- **现象**：三处不一致，详见 5.3。
  1. refs 块没有包裹标签（只有首句声明 + `【引用N】` + 分隔线 + 尾句），目录块有 `<会话工作目录>` 标签；
  2. 标签词「会话工作目录」与 UI 术语「事项目录」不一致；
  3. 块内指代词与位置耦合（目录块用「以下」、refs 用「以上」），位置一改必须同步改，否则指错对象。
- **后果**：模型看到的标志风格不统一，且会照着旧术语回话，与界面用词错位。
- **建议**：统一标签与内部用语（5.3），随位置调整同批做。

### D6｜`_absorb_inbox` docstring 过期，误导「user 永不裁剪」（低）

- **现象**：`react_step.py:216-219` 仍写「user 消息在 trim_history 中**永保**」并引用 `always_keep_tokens = system+user`。
- **证据**：`always_keep_tokens` 全库已无定义（仅两处注释残留）；「user 永保 + 只裁 FC 对」的设计已于 2026-10-25 删除（`message_builder.py:679-683` 有明文记录，实测致悬空 user 堆积），现为轮次级整轮滑动。
- **危害**：注释与真实行为相反，是"注入块会不会被裁"这类疑问的直接来源。
- **建议**：随批 1 订正注释（零逻辑变更）。

## 五、目标设计

### 5.1 单一装配点

```
orchestrator：只做数据准备
    ├─ refs：sanitize → prepare_refs → _final（现有流水线不动）
    └─ ws  ：get_ws_snapshot()（现有 ContextVar 快照不动）
                ↓ 同一份 turn context（结构化，不预拼字符串）
agent 层：build_user_turn_text(user_input, refs, ws_snapshot)
                ↓
<引用资料>…</引用资料> + <事项目录>…</事项目录> + 用户原话
```

三条要求：

1. 装配下沉到 agent 层，与 `init_history` 同址；orchestrator 不再拼 prompt 字符串（消除通道 B）。
2. 插话改为同一函数：`inject_message_to_task(_active_tid, build_user_turn_text(...), ...)`，快照取目标任务当前值。
3. `_append_ws_suffix` 删除，不留双实现（禁止 backward）。

### 5.2 装配顺序

```
<引用资料>
  安全声明 + 【引用N】条目 + 重读约定
</引用资料>

<事项目录>
  目录清单 + 写入约定
</事项目录>

用户原话（永远最后一段）
```

- 用户原话必须是 content 的最后一段，任何注入块不得追加在其后（D2）。
- 两块之间空行分隔；标签只包裹、不嵌套，避免模型把层级当结构指令。
- 位置调整必须同步核对块内「以上/以下」指代（D5 第 3 条）。

### 5.3 块标志规范

统一为「同款包裹标签 + 标签词与内部用语一致 + 指代与位置一致」：

| 项 | 引用块 | 目录块 |
|----|--------|--------|
| 外层标签 | `<引用资料>`（新增） | `<事项目录>`（由 `<会话工作目录>` 改） |
| 内部条目 | `【引用N】`（不变） | `  - <路径>`（不变） |
| 首句用语 | 「以下是用户随本条消息提供的引用内容…」 | 「以下是你可用的事项目录：」 |
| 尾句用语 | 「以上引用正文随本条消息进入上下文…」 | 「要求生成临时/中间文件，请写入事项目录。」 |
| 不可信声明 | 保留（引用正文是用户可控数据） | 不需要（目录清单由系统生成） |

三条硬约束：

1. 标签词、首句、尾句必须用同一个术语，不得混用「会话工作目录/事项工作区/事项目录」。
2. 前置后「以下」只指块内内容，「以上」只指块内内容——不得跨块指代。
3. 标签名与代码标识符解耦：代码保留 `session_workspace` / `get_ws_snapshot`，只改面向模型的文案。

### 5.4 截断与优先级

| 规则 | 内容 |
|------|------|
| 上限 | 沿用 `MAX_WS_INJECT_CHARS=4096`（预算口径不变） |
| 优先级 | 默认工作区 > 带属性/memo 的目录 > 其余（同级按路径字典序） |
| 保底 | 默认工作区至少保留一条；单条超限则截路径不截整条 |
| 省略提示 | 保留「...(还有 N 项省略)」，条数按实际跳过数计 |
| 引用侧 | 沿用现有 refs 预算裁决，不改口径 |

### 5.5 多块并存（插话）

按 D1 补上目录块后，同一任务的历史里会出现多个目录块（并入末条时同一条消息两个块；独立成轮时两条消息各一个）。必须定义「以哪一块为准」，否则模型可能读到已被用户改掉的旧目录。

| 场景 | 处理 |
|------|------|
| 快照未变，历史中仍有有效块 | 不重复注入（插话只带引用块） |
| 快照未变，历史中已无有效块（被裁剪） | 重新注入 |
| 快照已变化 | 注入新块，并把历史中旧块正文就地替换为「（已被后续更新覆盖，以最新一条为准）」 |
| 快照变化但旧块已被裁剪 | 直接注入新块 |

选择「就地作废」而不是「多块并存 + 声明最新」：模型对同类信息的多份副本没有可靠的版本比较能力，多份目录清单最常见的失败模式就是按第一份执行。作废是确定性做法，且只改内存（块不落库，2.4），代价可控。

代价：就地改历史会让该位置的 prefix cache 失效一次；插话本身已追加消息、本就要付一次缓存代价，可接受。

注意与 7.1 的边界：7.1 反对的是「首发/每轮按变化才注入」，本节的判断顺序是**先看历史里有没有块，再看变没变**，两者不冲突。

### 5.6 回执与日志

| 场景 | 动作 |
|------|------|
| 正常注入 | 一行日志：注入条数 / 跳过条数 / 快照来源 |
| 目录被截断 | 复用 refs 的 notice 通道给一句轻提示，不新增前端组件 |
| 插话合并超长截断（2.5 例外） | 补一行日志，说明块被牺牲（当前是静默的） |
| 插话路径 | 与首发同源，不另写文案（DRY） |

### 5.7 术语

| 层 | 口径 |
|----|------|
| 面向模型文案 | 「事项目录」 |
| 前端 UI | 「事项工作区 / 事项目录」（已统一，不改） |
| 代码标识符 | 保留 `session_workspace` / `get_ws_snapshot`（避免全链路重命名） |

## 六、实施

### 6.1 批次划分

| 批次 | 内容 | 性质 | 风险 |

## 七、不采纳项与风险

### 7.1 不采纳：首发/每轮「按快照变化才注入」

看似省 token，但块是瞬时的（2.4），压缩/裁剪后无法从 DB 回灌；一旦跳过注入而历史又被裁，模型会永久丢失目录认知。省下的 token 换不来这个风险。插话场景的"未变不重复"见 5.5，判断前提是历史里已有有效块。

### 7.2 不采纳：把目录块放进 system prompt

同 3.1：破坏 prefix cache，且目录随会话变化，system 会话级构建无法承载。

### 7.3 不采纳：把注入块写入 `user_input` 落库

会导致历史累积、前端回显变脏、POST 防双发比对失效。现状（只在 wire 的 `last_message` 上叠加）必须保持。

### 7.4 风险：批 2 的签名扩散

`init_history` 加参数会触及 `react_loop` 与相关单测。本仓禁止 backward 兼容，因此采取「一次改到位 + 同步改单测」，不留双路径。

### 10.3 关键实现说明（与六章预告的差异一并列明）

1. **装配顺序唯一**：`build_user_turn_text` = 引用块 → 事项目录块 → 用户原话；用户原话恒为末段。空块自动省略，两块皆空时与改造前逐字节一致。
2. **`init_history` 签名不变**：六章 6.2 原计划"扩 ws 入参 + 同步改 `react_loop`"。落码改为**本层自取** `get_ws_snapshot()`（ContextVar 中立层，任务创建时随上下文复制），故 `react_loop.py` **零改动**，7.4 的签名扩散风险实际未发生。
3. **插话三态**（`build_interject_text`）：历史里已有同内容目录块 → 只带引用块不重复注入；有旧块但内容已变 → 注入新块并把旧块正文就地替换为作废文案；历史中已无有效块（被裁剪）→ 直接注入。
4. **作废只改内存**：`_invalidate_ws_blocks` 用正则替换 `conversation_history` 里的旧块正文，不动 DB、不动落库消息；旧块保留标签，让模型知道"这里曾有一份旧清单"。
5. **目录块截断纪律**：按「默认工作区 > 带 memo / 非 read_write 属性 > 其余」排序；默认工作区恒保留（单条超长则截路径不截整条），其余超 `4096` 字符跳过并在块尾附"其余 N 条省略"。
6. **编排层只剩一个降级分支**：插话取不到目标任务 agent 时（注册表已回收、无历史可判重），直接 `build_user_turn_text(...) + render_workspace_block(...)` 全量装配，不写第二套格式。
7. **落库口径未变**：`chat_user_message.content` 与 `chat_tasks.user_input` 仍是用户原话，注入块只在本进程历史的 wire 上，符合 7.3。

### 10.6 5.6 / D4 补齐记录（2026-10-31 21:12:27 小欧）

#### 10.6.1 一处改动同时解决两个问题

原实现里渲染发生在 `message_builder`（自取 ContextVar 快照），编排层拿不到 `kept/skipped`，
所以既写不出汇总日志，也发不出"目录被截短"的提示。本次把**渲染权收归编排层**：

```
编排层渲染一次 → WsBlock(text, kept, skipped)
   ├─ text  ── 首发经 _start_meta.ws_block / 插话直接传参 → 装配（唯一注入样本）
   ├─ kept/skipped ── report_ws_block 一行汇总日志
   └─ skipped>0 ── build_ws_notice 走 notice 信封下发轻提示
```

注入、日志、回执三处取的是**同一次渲染的数字**，不会再出现"日志说 3 条、实际注入 2 条"。

#### 10.6.2 逐项落点

| 项 | 实现 | 位置 |
|----|------|------|
| 渲染结果带数字 | `WsBlock(text, kept, skipped)`，`render_workspace_block` 返回它；`select_ws_lines` 同时给出保留/跳过条数 | `workspace_block.py` |
| 汇总日志 | `report_ws_block(scope, block, snapshot, action)` 一行：`[ws] scope=… action=… kept=… skipped=… source=session|none` | `workspace_block.py` |
| 超限提示 | `build_ws_notice` → `{type:notice, kind:ws_inject, phase:done, content:"事项目录过长，已省略 N 条（默认目录始终保留）"}`，首发 `yield`、插话经目标任务 buffer | `workspace_block.py` + `stream_orchestrator.py` |
| 装配不再渲染 | `init_history(..., ws_text)`、`build_interject_text(..., ws_text)` 只装配；插话返回 `(正文, 动作)` 供日志使用 | `message_builder.py` |
| 首发透传 | `_start_meta["ws_block"] = text`，`react_loop` 取用 | `stream_orchestrator.py` / `react_loop.py` |
| 日志落位 | 首发放在引用阻断判定**之后**——请求被拒时不说"已注入" | `stream_orchestrator.py` |
| 信封登记 | `NOTICE_KINDS` 补 `ws_inject`（唯一登记点） | `steps/__init__.py` |
| 前端图标 | `NOTICE_CONFIG["ws_inject_done"] = WarningOutlined`（不新增组件；未命中时原本回退成常转的 spin 图标，故必须登记） | `infoMaps.tsx` |

插话日志动作取值：`inject`（注入新块）/ `invalidate`（内容已变，注入新块并作废旧块）/
`skip_dup`（内容未变，不重复注入）/ `skip_none`（无目录快照，本轮无块）。

#### 10.6.3 为什么 phase 用 done 而不是新增 degraded

通知信封契约只有 `start/done/failed`，前端 `useTaskInfo` 按这三态决定是否占位4。
用 `done` 语义是"本轮目录已装配完成、有省略"，且 `done` 只清除**同 kind** 的占位提示，
不会误抹主任务"生成摘要中"等提示（该坑 2026-10-30 已踩过一次）。图标用警示色与
`refs_ready_done`（绿色对勾）区分，用户能看出"进去了但有省略"。
