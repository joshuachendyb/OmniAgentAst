## 一、信任+授权权限的现状

### 1.1 双系统对照（全景SA1-SA8，顺序固定：SA1双入口→SA2预查→SA3总闸→SA4 delete→SA5路径→SA6确认授权→SA7沙箱→SA8体内）

| | 会话信任（DB） | 临时授权（ContextVar） |
|---|---|---|
| 存储 | `chat_session_trust(session,tool,path)`，永久累积无TTL | `{Path→recursive}`本task作用域，task结束`clear` |
| 写 | `save_session_trust`（仅HITL确认后，`hitl_confirmation:198`） | `grant_temp_auth`（safety_gate三处：bypass:249/确认后:307/直通:325） |
| 读 | `resolve_skip→check_session_trust`（SA2，B规则跨工具前缀） | `is_temp_authorized`（SA5内，文件精确/目录递归） |
| 撤销 | `storage.delete_session_trust`（粗：非空跨工具全删） | task结束自动清零 |

### 1.2 九格矩阵（`validate_path`层，T2消费）

system×写/删硬拦永不授权；non_system×写可授权、删硬拦；None×写/删可授权；读三格全放行；白名单内全放行。`sandbox_required⇔destructive`六处置位（checker:244/264/300/309/385/404），注释声称的②③在checker恒False、④在executor——注释名不副实，设计以代码为准。

**系统保护目录：判定单源**

| 项 | 现状 |
|---|---|
| 唯一判定 | `path_safe_check.is_system_protected_path()`（`:185`），`parts[1]` 精确匹配 `SYSTEM_PROTECTED_DIR_NAMES`，**异常即判受保护**（fail-closed） |
| 两个调用点 | `_is_forbidden_path:242`（Safety判权限）+ `file_path_checker.validate_not_system_path`（SA8兜「绕过Safety直调工具」）。判定点两处、逻辑同一份 |
| 名单单源 | `tool_constants.SYSTEM_PROTECTED_DIR_NAMES` 9项：windows / program files / program files (x86) / programdata / boot / recovery / winnt / system32 / system |
| 位置顺序 | 在 `_is_forbidden_path` 的 `os.name=='nt'` 分支内、**⑦代码库根检查之前** → 代码库根若落在系统保护目录下判 `system`（写删永不授权），方向 fail-closed |
| `validate_path` | 不再自行判定系统保护目录，语义由 `_is_forbidden_path` 统一分流承担，**九格结论不变** |

### 1.3 双入口差

Agent链：HITL等人+三处grant+三处沙箱。facade：**无grant、无沙箱**、自建uuid task（授权跨调用不可见）。facade 两处失败返回带 `safety` 字段（SafetyResult 原对象，`tool_routes` 用 `asdict` 转 dict），调用方据 `blocked/requires_confirmation/auth_path` 区分「被拦截」与「待确认」。P0-1/P0-2 成立。

### 1.4 职责边界：SA3 只判权限，SA8 判业务

SA3 `_check_known_risks` 只判路径越权（system/non_system/白名单外）与 delete R6，`is_valid=True` 即 `return None`（`:412-415`）。文件大小属业务规则，不在 SA3 判，归口 `SA8 file_path_checker.validate_path_for_overwrite`（>1MB warning / append>100MB warning）。SA8 `validate_not_system_path` 调用 SA5 的 `is_system_protected_path`，依赖方向 `tools.validate → tools.security` 合法。

## 二、问题说明

- **P0-1** facade无沙箱（`tool_facade.execute_tool:123-157` 全文零 `pre_execute`，destructive经API绕过影子预检）。
- **P0-2** facade从不grant，白名单外写预检放、执行期`validate_path`再拦，API路永不可用。
- **P0-3** bash删降级：`_validate_shell_write_targets`（`:461`）内 `:504` 一律 `validate_path(raw_path, mode="write")`，non_system删经shell从硬拦降为可授权（`tool_safety_checker:374`判`bash≠delete`），与函数自述「删语义完全一致」矛盾。
- **P1-1** 双轨分叉：`auth_path` 轨（`tool_safety_checker:367` 校验取 `failed_path`）vs `trust_path` 轨（`trust.extract_trust_path` 取首个parse路径）；grant走auth、save走trust，`copy`类path合法+dest越权必反复弹窗；组键（auth∨trust `safety_gate:171`）与计数（仅trust `:199`）分裂。`auth_path` 带回落（`:391`/`:410`：`failed_path or params.get("path") or params.get("dest")`），`failed_path` 为空时回落成 path/dest，可能≠trust_path。
- **P1-2** severity第四态：豁免分支（destructive+不拦不问）被外层:247覆写成`dangerous`，契约破坏。
- **P1-3** bypass分支不校验verdict即进沙箱（`safety_gate:245`）：`confirmed=False,expired=False`时`_bypass_confirmed=False`仍调`run_sandbox_gate`（`:254`），沙箱`auto_confirm`直过 → `_ok=True` → `:258 continue`把"拒绝"吞掉。真HITL `:262` 分支本身正确（拒即continue不沙箱），三汇合点口径因此不一致。**注**：bypass 下网关自动确认使该路径难触发，属防御性修复，非可主动利用的漏洞。
- **P1-4** `execute_command`组键退化：`refusal_key:92`用原始名，跨命令共用确认+拒绝记忆污染。
- **P1-5** 三词表不同源：预检all_shells、执行层单查、沙箱扫描器各一套，口径漂移。
- **P1-6** 检查点A（`safety_gate:180 if _group_key in _rej_cache:`）缺 `and not _bypass`，bypass可被历史拒绝阻断，与 `:176` 注释「bypass全自动不受约束」相悖（对照 `sandbox_gate` 检查点B的 `not (trusted or main_confirmed)`，A 少一层）。`:178` 的 `if _skip:` 是清记忆，非本项。
- **P2-1** 信任无TTL、无清理；撤销（跨工具全删）粗于落库（单行）。
- **P2-2** facade `skip`恒False（设计，缺注释）。
- **P2-3** T2注释“T1传mode”与实现（内部推断）错位。
- **P2-4** 架构守护测试当前实测已红5项（4.0.1）：`path_safe_check`越层`app.safety` + 4个`document/write_*`文件带UTF-8 BOM致`ast.parse`失败。不先清，P2批完成判据「架构守护绿」不可达。
- **P2-5** `path_safe_check:189` docstring 非 raw string，内含 `C:\system32`，`pytest` 报 `SyntaxWarning: invalid escape sequence '\s'`（`py_compile` 同告警）。改 `r"""`，随 4.0.1 同批清。
- **P2-6** `tool_routes.py` 缺行尾换行（`\ No newline at end of file`），与仓库行尾一致规不符。
- **P3-1** `file_path_checker` 文件头「工具层与Safety层两层独立运行、互不调用」注释与现状不符：该层 `validate_not_system_path` 调 SA5 的 `is_system_protected_path`。依赖方向 `tools.validate → tools.security` 合法（守护测试只禁 `tools → services/safety`），反向 `tools.security → tools.validate` 会成环，当前无。
- **P3-2** `_resolve_env_fragment` 目前定义在 `app/safety/sandbox/executor.py:111`，被 `:124` 自用、`path_safe_check:503` 跨层 import。两处共用一份跨层依赖，是 P2-4 红项1 的根；随 4.11 迁入 `shell_static_guard` 收口。

      ↓ 需确认

      ↓

      ↓
