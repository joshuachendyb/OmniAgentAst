## 二、现有 shell 进程模型的问题分析

### 2.1 当前实现（PS7/PS5 走池，bash/cmd 走独立子进程）

```
execute_shell_command.py
├─ ps7/ps5 → shell_pool.acquire() → engine.exec(cmd, timeout)   ← 同步阻塞(已在子线程执行, 见 §2.3)
│                └─ shell_engine._exec_locked()
│                     ├─ 写 cmd.ps1 / ps_cmd.ps1（UTF-8-BOM）
│                     ├─ stdin 喂单行 dot-source（先 poll 探活=C5）
│                     ├─ _poll_for_file(paths.code, timeout)   ← 完成判定＝"文件出现"
│                     └─ 超时 → M6 daemon 守卫清理 → return timeout（非永久阻塞）
└─ bash/cmd → subprocess.Popen + proc.communicate(timeout=timeout)   ← 有硬超时
```

### 2.2 问题一：完成判定模型错误（反复卡死的根因）

`_exec_locked` 用**"结果文件出现"**作为命令完成信号：

| 现实 | 后果 |
|------|------|
| 命令被 kill / 进程半死 / 管道 desync | 结果文件**永远不会出现** |
| `_poll_for_file` 的 `timeout` 是命令超时（默认 60s，可配到 600s） | 卡在它之前（实例锁 `with self._lock` / `stdin.write`）时，**连这个上限都不存在**（`acquire`/`_probe` 本已有界，见 §1.2.3③，层3 靶点见 §4.3） |

**关键**：把"命令是否完成"寄托在"文件副作用"上，两者**不是同一件事**。进程已死与文件未写可以同时成立且不矛盾，于是形成**事实与判定不一致**的窗口——每次修复只是补上这个窗口的一个具体场景，**判定模型没变，所以必然复发**（`[53]` 记 20+ 处：C4/C5/C6/C8/C10/C12/C13/C14、B6、R0~R4、M1~M8，仍卡）。

**正确模型**：完成信号应是**进程退出**。`proc.communicate(timeout=...)` 返回即代表进程已结束、管道已关闭，**OS 保证此刻文件已落盘**——"进程死了但文件没写"在物理上不可能发生，判定与事实天然一致。

### 2.3 问题二：调用侧卸载**已存在**（v1.1 更正），真正风险在循环侧残留同步点

**已核实（v1.1）**：bash 工具在 `tool_retry_engine._execute_tool_once`（`:198-202`）已被 `asyncio.to_thread` + `wait_for` 卸载，顺序/并行两路（`:604`/`:352`）与 `tool_facade:146` 全部同源。**故 v1.0 所述"任何一次 shell 卡死 = 整个服务僵死"不成立；在子线程里再开一层 `to_thread`（v1.0 层1 diff）对 Q1 零作用，已删除。**

**仍需治理的循环侧同步点（结构性存在，与本次现场是否由它引起无关）**：

1. `agent_runner.py:849` `finally → cleanup_shell_pool_by_task → inst.close()`：锁等待 5s + `taskkill`，**直接跑在事件循环上**（`tools/__init__.py:20-23` 无卸载）；
2. `log_and_print` / logger handler 同步写；
3. 其他未卸载的同步 IO —— 由 §1.2.2 取证收敛，不预设。

**顺带记账（v1.1）**：`asyncio.wait_for` 超时只放弃等待、**不能终止线程** → 卡死的 `to_thread` 线程永久占住默认线程池 1 个 worker 与该 key 的信号量槽位（详见 §2.4 线程泄漏）。

### 2.4 问题三：常驻池的共享状态是双刃剑

- **收益**：省进程启动（~200-500ms）+ `cd`/环境变量/会话连续性。
- **代价**：跨任务共享的池锁与实例状态；一次"卡在 exec 内"会连带后果：
  - `finally: shell_pool.release(engine)`（`:1130-1131`）**永不执行** → 实例永久标记 busy、信号量槽位永久不归还；
  - 后续同 `(task_id, shell_type)` 的 `acquire()` 会在 `Phase0` `sem.acquire(timeout=2s)` 处抛 `ShellPoolBusyError`（C2 已有界）——**不会无限排队，但也意味着该任务后续 shell 全废**。
  - **线程泄漏（v1.1 新增）**：`wait_for` 超时无法终止线程，卡死的 `to_thread` 线程永久占用默认线程池 1 个 worker（上限 `min(32, cpu+4)`）与 1 个信号量槽位（`release` 永不执行）；worker 累积会拖累**同池**的 `health → db.atxn`（`database.py:308`）与文件类工具 —— 但如 §1.2.2 注所述，它**只能**解释 health 单独超时，**不能**解释 F4 无 ping，故不作根因。

**已经做对的部分（不必重做）**：`M1 _CLEANUP_GUARD_TIMEOUT=15` / `M2 _poll_pid_exit` / `M3 _kill_tree` / `M6 daemon 守卫（"返回 timeout，非永久阻塞"）` / `M7 _probe` / `M8 acquire 探活后重建` / `C2 acquire 2s 有界` / `C5 写 stdin 前探活` / `C13 死实例不放回池`。

### 2.5 只有只读命令走的分支本身是安全的

bash 分支用 `proc.communicate(timeout=timeout)`（`:1228`），**完成判定 = 进程退出、硬超时由 OS 保证**——正是 2.2 说的正确模型。**它今天仍"卡"，只能是卡在进入该分支之前**（三路检测 / `_find_bash` / `_sanitize_env` / `Popen`），这与 §1.2.2 Q2-H4 一致，也解释了为什么"bash 分支明明有超时却没超时日志"（F3）。

**v1.1 补充（关联检查）**：F2 表明本次现场走的**就是 bash 分支**（本就是一次性子进程、本就不是池）——**只治 PS 池（层2/层3）覆盖不到本次现场**。三者关系必须讲清：层2/层3 是**独立健壮性改进**（分别针对 §2.2 判定模型与 §4.3 无上限点），本次现场的正解只能由 §4.5（第1步循环侧定点，H2 可先行、其余取证后合入）给出。

## 三、新的架构修改方法

### 3.1 双通道执行模型（核心变更）

| 通道 | 适用命令 | 执行方式 | 完成判定 | 硬超时 |
|------|----------|----------|----------|--------|
| **A 一次性通道**（优化，非默认） | 命中**单源只读白名单**、且该 (task_id, shell_type) **池内无实例**（无会话态可依赖）的命令 | **同一 shell 解释器**一次性 `Popen` + `communicate(timeout)`（ps7→pwsh、ps5→powershell、cmd→.bat、bash→现分支，**不跨解释器**）；`cwd` 用工具参数原值 | **进程退出** | OS 保证 |
| **B 状态通道**（**默认**，保留池） | 其余全部命令（含 `cd`/环境变量/会话连续性；**池内已有实例时的全部命令**——实例存在即可能持有会话变量/别名/PS drive） | 常驻池；执行本已在子线程（§2.3），补齐池内各段上限（§4.3） | 文件轮询（保留；既有命令 timeout≤600s 即绝对上限，**零改动**） | 各段独立上限 |

**判断规则**（KISS、可测；**两个条件必须同时满足才出池**，任一不满足走 B）：
1. **不依赖会话**：`shell_pool.has_session(task_id, shell_type)` 为 False —— 池内无实例 ⇒ 无会话变量/别名/PS drive/cd 历史可依赖。反例：① 池里先 `$env:X='hi'`（进程级 env，实测真持久）后 `echo $env:X`（`echo` 在白名单）出池必打印空、留池才输出 `hi`（2026-10-04 实测：`$env:`/location 跨 exec 真持久，`$greeting` 类 PS 变量池内亦不持久故不作例）；② 池里 `Set-Location HKLM:\Software` 后的只读命令出池 → 用工具参数 `cwd` 则**落在错误目录静默产出错结果**（若改为透传会话 cwd 则更糟：非文件系统盘直接让 `Popen(cwd=...)` 抛异常）。白名单只管"写不写"，管不到"依赖不依赖会话"。**实例存在与否即会话态判据，无需新增状态追踪**；
2. **只读安全**：命中单源白名单 `is_readonly_whitelisted`（其内部已含 `FAST_CHANNEL_FORBIDDEN` 拒管道/分号/重定向；**单源 `app/utils/shell_readonly.py`**，2026-10-04 自 `executor.py:68,161` 迁出——全量测试 `test_architecture_boundaries` 暴露"tools 禁 import app.safety"架构红线，而白名单需双侧共用，中立 utils 为唯一合法落点，executor 同名转发零行为变化）。**禁止在本层另立正则** —— 复用单源（见 §4.2）。

条件1 使 `cwd` 问题消失：无实例 ⇒ 会话 cwd 不存在 ⇒ 一次性子进程直接用工具参数 `cwd`，无需任何透传。**默认走 B（池，保守）**。
