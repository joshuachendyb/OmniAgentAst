### v3.8 后端实施核查结论（2026-10-13 18:09:06 小欧）

本节为后端落地后的**逐条对齐核查**记录，避免后人再把「文档写了」当成「代码做了」。

**核查结果**：18 项后端功能需求中 **18 项已实现**（含 J5 的后端约定与 refs 协议）；**2 项未做且均属前端范围**（J3 设为会话工作目录、4.2 全部前端实施）。测试 **123 通过 / 10 跳过**，覆盖文档 4.1.10 要求的 18 类必测。

**核查中发现并修复的两个真 BUG**（均由「照着文档写完就报完成、未独立验证语义」导致）：

| # | BUG | 后果 | 根因 |
|---|---|---|---|
| BUG-1 | **refs 链路断裂** | 用户点「发送到输入框」，Agent 收到**空引用**，文件正文一个字都进不去 | `chat_routes` 透传 pydantic `ChatRef` **对象**，而 `_render_refs_block` 只收 dict → `isinstance(data, dict)` 判定失败整条丢弃。当时 110 条测试全绿，因为**全部直接构造 dict 调末端函数，全链路一次都没跑过** |
| BUG-2 | **`recent_files` 相对路径全废** | 「最近文件」列出的全是 `backend/xxx.md` 这类**不存在的路径**，点开 404 | 照抄 4.1.7 示例代码 `Path(raw).resolve()`，相对路径被解析到**进程 CWD**（`backend/`）而非项目根 |

**两条由此沉淀的测试纪律**（已落为测试文件内的组名与注释）：

| 组 | 用途 |
|---|---|
| `x01~x07` **全链路组** | 从**真实数据形态**（`ChatRef` 对象）出发，穿过 API 层解包 → 编排过滤 → 渲染 → `init_history`。`x06` 直接跑真实 `chat_routes.chat_stream_endpoint` 捕获实参。**每条测试都写明「能抓什么」，并已用「故意改坏 → 确认变红 → 还原」验证过有效性** |
| `j01~j05` **端点层组** | 补齐 4.1.10 第 10/18 类，并新增 `j05` 钉死 **HTTP 响应体形状**（`error.code`，非 `detail.code`）——原 `g01` 只验了 service 层 `detail`，漏了全局处理器这一层 |

**已知验证盲区（如实记录）**：

| 盲区 | 原因 | 影响 |
|---|---|---|
| 符号链接越界（4.1.10 第 4 类） | 本机 `os.symlink` 报 `WinError 1314`（客户端无所需特权） | 该安全路径**在本机从未真实执行过**，10 条 skip 中含此类。**必须在有特权的环境（开发者模式 / CI 的 Linux）复跑** |
| 最近文件上限 200 步 / 50 条 | 桩数据未造到阈值 | `j02` 只验证了去重/顺序/过滤，未验条数上限截断 |
| `big5` 编码 | 本机无该编码 | 编码兜底链的最后一档未实跑 |

### 1.4 三组必须写死的概念区分

**① 「显示」与「查看」**：树上列出 = 全部条目（不跳过、不设黑名单）；点开看内容 = `.txt`/`.md` + 位图/SVG（仅这两类可打开）。

**② 「注入」与「发送」**：注入只填充（I2），发送由用户触发；失败只回填用户草稿（I3）。

**③ 「引用正文」与「引用路径」的价值分层**（M1 带来的新认知）：
- **正文仅当轮有效**——随请求上行供 LLM 一次性消费，**不入库、不进历史**；
- **路径长期有效**——进入 user content（`@README.md`）随历史持久化，日后 Agent 仍能凭路径用 `read` 工具重读全文。

这不是妥协，而是有意分层：**短内容靠引用即时送达，长内容靠路径随时重取**。引用正文里的「请自行 read 该文件」引导正是这条规则的延伸（v3.4 已删体积降级，改为固定提示）。

**④ 「代码库根禁区」与「功能可用性」可能互斥**：按 S6 消解。

### 2.2 后端概要设计

| 端点 | 入参 | 出参要点 |
|------|------|----------|
| `GET /files/root` | — | `{project_root, allowed_dirs, code_root_blocked}` —— 供前端做路径归一与 J1 校验（M24） |
| `GET /files/tree` | `path`（子树起点，空=根）、`max_depth`、`max_nodes` | 嵌套 `nodes[]`，每个节点**一次带出** name/type/size/mtime；`truncated`；取任意子树由 `path` 承担（M26 删 list） |
| `GET /files/read` | `path`（txt/md） | `content` / `encoding` / `size` / `total_lines` |
| `GET /files/raw` | `path`（图片） | 二进制流（`FileResponse`，框架内置 ETag/Range）+ 补 304 |
| ~~`GET /files/stat`~~ | — | **已删除**（v3.4）：节点信息随树一次返回，不再设 hover 单查端点 |
| `GET /files/recent-files` | `session_id` | 本会话 Agent 最近读过的文件列表（T3，M3 新增） |
| `POST /chat/stream`（**既有，扩字段**） | body 增加 `refs[]` | user content 保持干净；refs 当轮消费（M1/M20） |

> **M26**：`/files/list` 已删。`tree` 传 `path=<某目录>` 即等价于该目录的单层列表，无需第二个端点，也少一处排序/过滤可能分叉的实现。

设计要点：

1. **单一路径边界函数** `_resolve_within_root()`：所有端点共用；
2. **`resolve()` + 祖先关系判边界**，不用字符串前缀；
3. **唯一扫描实现 `_scan_dir()`**（M8）：`tree` 各层共用；**不跳过任何目录**（`.git` / `node_modules` / `dist` 等一律正常列出），大目录的开销由 C2 双闸门（深度 5 / 节点 5000）兜底，超限即 `truncated` 降级；
4. **`os.scandir` 替代 `Path.iterdir`**：复用系统调用取 `is_dir`；每个条目**一次返回** name/type/size/mtime，不另设 hover 查询；
5. **递归双闸门**：深度 5 / 节点 5000，超限 `truncated`；
6. **304 唯一自研点**，其余缓存/断点能力由 Starlette 内置承担；
7. 挂载走 `_mount()` 自动继承鉴权；
8. **`/files/root` 必须返回 `code_root_blocked`**：让前端能提前知道"本环境下代码库根禁区是否生效"（S6 降级状态），从而把「设为会话目录」按钮的可用性提示提前到点击前。

#### 2.5.2 统一概念 FileRef

「路径 + 可选行号范围 + preview 类型」作为一等公民，**四处复用**（输入框引用卡片 / `PathLink` / 树定位高亮 / `FileRefChip`），且共用同一个校验函数，避免多套路径处理逻辑分叉。

- **T2 就这个提问**：一键填 `@文件` + 模板；
- **T3 Agent 动过的文件**：树上标 `●`。

#### 2.5.4 J5：Agent 侧文件引用的实现选型

**目标**：让 Agent 提到的文件变成可点卡片，且**不引入误伤**。

**为什么不用「前端识别裸路径」**（路线 A）：须在 hast 上识别文本节点。核实 `hast-util-to-jsx-runtime/lib/index.js:154` —— `node.type === 'text'` 分支**排在元素处理之前**，组件级映射无机会介入，只能写 rehype 插件；而组件层又拿不到祖先上下文（项目注释已实测 hast 无 parent 指针），跳代码块还得在插件里自维护栈。叠加 Windows 反斜杠转义、URL/日期误伤、存在性校验四道闸，收益远小于风险。**路线 A 列入 4.7 备案。**

**采纳方案：显式标记 + 字符串预处理 + 组件分流**（最省，且两个渲染分支都能做）：

```
① 系统提示约定：提到文件时输出 [[文件:<相对路径>]] 或 [[文件:<相对路径>#L12-L20]]
② 前端在【进入 MarkdownSlot 之前】把标记替换为标准 markdown 链接：
     [[文件:a/b.md#L12-L20]]  →  [📄 a/b.md#L12-L20](/file-ref?path=a/b.md&lines=12-20)
③ MarkdownText 的 a 组件按 href 前缀 /file-ref 分流 → 渲染 FileRefChip（App 内跳转）
④ MarkdownBody（MD_IMPL=1）在 INLINE_RE 加一组捕获 + 分支，同样渲染 FileRefChip
```

**关键点：`a` 组件不能复用。** `MarkdownText.tsx:265-278` 的 `a` 硬编码 `target="_blank"`，且 `SANITIZE_SCHEMA` 注释明确「不补 a[target/rel]——外链属性由本文件 a 组件硬编码渲染」。若直接复用，文件引用会**新开浏览器标签页**（桌面端体验灾难）。故必须新增 `FileRefChip` 组件并在 `a` 里按 href 前缀分流。

**为什么两个渲染分支都要改**：`MD_IMPL` 是改一个数字即切换的开关（`MarkdownSlot.tsx:31`）。只改 react-markdown 分支，一旦切到 `MD_IMPL=1` 功能**静默消失**，无任何报错。

**待实测确认**：② 生成的是相对 URL，需确认 react-markdown 的 `defaultUrlTransform` 放行相对 URL（只拦 `javascript:` 等危险协议）。若被拦截，退路是改用非 `href` 的自定义标记 + `components` 映射。

**安全**：标记来自**模型输出**，其中的路径必须走 `resolve()` + 根目录内 + 存在性校验（与 J1 同一套 `FileRef` 校验函数），**绝不直接拼进 `href` 或任何 HTML**。校验不过即退化为纯文本。

### 2.6 跨端兼容性（不绑定浏览器）

- 天然可用：双头鉴权、`/api/v1` 前缀、JSON + 二进制流，均为协议层约定；
- 补齐 K1（统一错误码）、K2（304）、Range/206（框架内置）；
- blob/objectURL/拖拽等浏览器味只在前端，不影响后端契约。

### 2.7 缓存与断点契约（K2）

`/files/raw` 的 `etag` / `last-modified` / `accept-ranges` 由 Starlette `FileResponse` **内置**提供，`Range → 206/416` 亦内置。本期**只补 `If-None-Match → 304`**，且 ETag 必须与框架同算法，否则条件请求永不命中。`Cache-Control: no-cache`（非 `no-store`，否则条件请求白做）。

            break
        except (UnicodeDecodeError, LookupError):
            continue
    else:
        fail(UNDECODABLE)
    return {"path": rel, "name": target.name, "size": size,
            "content": content, "encoding": enc,
            "total_lines": content.count("\n") + 1 if content else 0}

#### 4.1.3 扫描实现 `_scan_dir()` 与递归体 `_walk()`（M8）

**`_scan_dir` —— 单层扫描，唯一实现**（`build_tree` 每层都调它，杜绝排序/过滤两处分叉）

```python
def _scan_dir(root: Path, target: Path, rel: str) -> List[Dict[str, Any]]:
    """列一层目录，返回条目列表（已排序）。

    ① 不跳过任何目录、不做类型过滤 —— 目录里有什么就返回什么（v3.4 裁定）
    ② os.scandir 而非 Path.iterdir：DirEntry 复用系统调用，is_dir 近乎免费
    ③ 每条一次带出 name/type/size/mtime（无 hover 单查端点）
    ④ 单条目异常（权限/坏链接）跳过并计数，不让一个坏条目拖垮整个目录
    ⑤ 排序：目录在前 + 名称不区分大小写升序
    """
    entries: List[Dict[str, Any]] = []
    with os.scandir(target) as it:
        for de in it:
            try:
                is_dir = de.is_dir(follow_symlinks=True)
                st = de.stat(follow_symlinks=True)
            except OSError:            # ④ 权限/坏链接：跳过，不中断
                _scan_skipped += 1
                continue
            entries.append({
                "key": f"{rel}/{de.name}",          # key 用相对路径，防同名撞车
                "name": de.name,
                "type": "dir" if is_dir else "file",
                "size": None if is_dir else st.st_size,
                "mtime": _fmt_time(st.st_mtime),
                "preview": _preview_of(Path(de.name)),   # text/image/none，前端据此渲染
            })
    entries.sort(key=lambda e: (e["type"] != "dir", e["name"].lower()))  # ⑤
    return entries
```

**`_walk` —— 递归体**（节点/深度双闸门；超限即停并置 `truncated`）

```python
def _walk(root: Path, rel: str, depth: int, max_depth: int,
          max_nodes: int) -> Tuple[List[Dict[str, Any]], bool]:
    """广度优先递归。返回 (nodes, truncated)。

    节点 key 一律用相对路径：backend/app 与 frontend/app 若用 name 作 key 会撞车，
    展开一个连带错位另一个（M8）。
    """
    if depth > max_depth:
        return [], True
    items = _scan_dir(root, root / rel, rel)
    nodes: List[Dict[str, Any]] = []
    truncated = False
    for e in items:
        if len(nodes) >= max_nodes:          # 节点闸门
            truncated = True
            break
        node = dict(e)
        if e["type"] == "dir":
            node["truncated_child"] = True   # 未展开 → 前端挂 loadData 按需补拉
        nodes.append(node)
    return nodes, truncated
```

> **降级衔接**：初版 `tree` 已带回前 5 层；被 `truncated_child` 标记的目录，前端展开时再以该目录为 `path` 调一次 `/files/tree` 补拉，并用 `loadedKeys` 记账不重复请求（4.2.5）。

#### 4.1.4 路径边界 `_resolve_within_root()`（唯一实现）

**规则**（五个对外端点全部经它，安全逻辑只此一处可审）

```
rel_path 空 → "."
拒绝对路径（is_absolute / 盘符 / UNC）
root = Path(get_config().get_project_root()).resolve()
target = (root / rel_path).resolve()            # 消解 .. 与符号链接
边界：target == root 或 root in target.parents → 否则 403 PATH_OUTSIDE_ROOT
符号链接解析后越界的条目不返回
（无文件类型黑名单，此处不做任何类型判定）
禁区：命中 code_root → 403 PATH_FORBIDDEN；
      但 project_root 落在 code_root 子树内 → 跳过禁区，模块级 warned 标志只 warn 一次（S6/M17）
```

**实现**

```python
_CODE_ROOT_WARNED = False    # 2026-10-13 小欧 - S6/M17: 降级提示只打一次，否则每次请求刷屏


def _code_root_conflicts(root: Path) -> bool:
    """project_root 是否落在代码库根子树内 → 决定禁区是否生效。"""
    try:
        cr = Path(os.path.realpath(get_code_root()))
    except Exception:
        return False
    return cr == root or cr in root.parents


def _resolve_within_root(rel_path: str) -> Tuple[Path, str]:
    """把用户传入的相对路径解析为根目录内的绝对路径。

    返回 (target, normalized_rel)。任何越界/非法一律 fail()，绝不返回半成品。
    """
    global _CODE_ROOT_WARNED
    raw = (rel_path or "").strip()
    rel = raw or "."
    if Path(rel).is_absolute() or rel.startswith(("\\\\", "\\")):
        fail(INVALID_PATH)                                  # 拒绝对路径与 UNC
    if ".." in Path(rel).parts:
        fail(INVALID_PATH)                                  # 显式拒绝穿越（双重保险）

    root = Path(get_config().get_project_root()).resolve()
    try:
        target = (root / rel).resolve()                     # 消解 .. 与符号链接
    except OSError:
        fail(INVALID_PATH)

    # 边界判定：祖先关系，**严禁字符串前缀比较**
    # （F:\proj-evil 是 F:\proj 的兄弟，不是子目录，前缀会误放行）
    if target != root and root not in target.parents:
        fail(PATH_OUTSIDE_ROOT)

    # 代码库根禁区；与可用性冲突时按 S6 降级（只读浏览场景可用性优先）
    if not _code_root_conflicts(root):
        try:
            cr = Path(os.path.realpath(get_code_root()))
            if target == cr or cr in target.parents:
                fail(PATH_FORBIDDEN)
        except Exception:
            pass
    elif not _CODE_ROOT_WARNED:
        _CODE_ROOT_WARNED = True
        logger.warning("[file_browse] project_root 落在代码库根内，"
                       "已按 S6 跳过代码库根禁区（只读浏览场景可用性优先）")

    return target, str(Path(rel).as_posix()).strip("./") or "."
```

#### 4.1.5 图片流与 304（不自研 Range）

实测：Starlette `1.0.0` `FileResponse` **已内置** `etag`（md5 of mtime+size）、`last-modified`、`accept-ranges`，并原生处理 `Range → 206`、越界 `416`。**唯一未实现的是 `If-None-Match → 304`**：

```python
def read_image_file(rel_path: str, request: Request) -> Response:
    """读图片：类型 → 存在性 → 大小 → 条件请求 → FileResponse。"""
    target, rel = _resolve_within_root(rel_path)
    suffix = target.suffix.lower()
    if suffix not in IMAGE_EXTS:
        fail(UNSUPPORTED_TYPE)                      # raw 端点的白名单，不成万能下载口
    if not target.exists():
        fail(NOT_FOUND)
    if target.is_dir():
        fail(INVALID_PATH, "该路径是目录，请使用目录树接口")
    st = target.stat()
    if st.st_size > MAX_IMAGE_BYTES:
        fail(IMAGE_TOO_LARGE)

    # 2026-10-13 小欧 - ETag 必须与 Starlette FileResponse 同算法(md5 of "mtime-size")，
    # 否则前端带的 If-None-Match 永不命中，304 白做（框架版本升级时需回归本行）
    etag = f'"{hashlib.md5(f"{st.st_mtime}-{st.st_size}".encode(), usedforsecurity=False).hexdigest()}"'
    if request.headers.get("if-none-match") == etag:
        return Response(status_code=304,
                        headers={"ETag": etag, "Cache-Control": "no-cache"})
    # no-cache 而非 no-store：允许条件请求；Range/206/416 由 FileResponse 内置处理
    return FileResponse(
        target,
        media_type=IMAGE_MIME[suffix],
        headers={
            "Cache-Control": "no-cache",
            "Content-Disposition": f"inline; filename*=UTF-8''{quote(target.name)}",
        },
    )
```

#### 4.1.7 recent-files 聚合（T3/M3）

```
SELECT step_json FROM chat_task_steps WHERE session_id = ? ORDER BY id DESC LIMIT 200
→ 解析 type=='action' 的 tools[]，取 params.path（及 target 兜底）
→ 过滤：能 resolve 且在 project_root 内
→ 去重（按路径），取最近 N=50 条，按最近出现时间倒序
→ 返回 [{path, name, preview, last_seen_at}]
```

- 必须**校验 session 存在**，否则 404（M7，参照既有 `session_exists`）；
- 只读 SQLite，不入 memory，不建新表。

```python
_RECENT_LIMIT = 200      # 扫描步数上限
_RECENT_KEEP  = 50       # 返回条数上限


def recent_files(session_id: str) -> List[Dict[str, Any]]:
    """本会话 Agent 最近读过的文件（树上的 ● 标记，T3）。

    数据源：chat_task_steps.step_json 里的 action.tools[].params.path。
    """
    from app.services.chat.workspace_service import session_exists   # 函数内 import，避免循环
    with db.get_conn("chat") as conn:
        if not session_exists(conn, session_id):
            fail(SESSION_NOT_FOUND)
        rows = conn.execute(
            "SELECT step_json FROM chat_task_steps "
            "WHERE session_id = ? ORDER BY id DESC LIMIT ?",
            (session_id, _RECENT_LIMIT),
        ).fetchall()   # 命中 idx_steps_session(session_id, step_index) 复合索引

    root = Path(get_config().get_project_root()).resolve()
    seen: Dict[str, Dict[str, Any]] = {}
    for (blob,) in rows:
        try:
            step = json.loads(blob)
        except (TypeError, ValueError):
            continue
        if not isinstance(step, dict) or step.get("type") != "action":
            continue
        for t in (step.get("tools") or []):
            if not isinstance(t, dict):
                continue
            raw = (t.get("params") or {}).get("path") or t.get("target")
            if not raw or not isinstance(raw, str):
                continue
            # ★ v3.8 BUG 修正 —— 相对路径必须拼 project_root ★
            #   LLM 给的绝大多数是**相对项目根**的路径。直接 Path(raw).resolve() 会把它绑到
            #   **进程 CWD**（后端启动时 cd backend/），产出 backend/docs/x.md 这类**不存在的路径**，
            #   列表里看得到、点开全 404。绝对路径仍需支持，故先归一到绝对、再取相对，最后送唯一判定入口。
            try:
                cand = Path(raw)
                abs_path = cand.resolve() if cand.is_absolute() else (root / cand).resolve()
                rel_in = abs_path.relative_to(root).as_posix()   # 不在 root 下 → ValueError → 丢弃
            except (OSError, ValueError):
                continue
            try:
                _target, rel = _resolve_within_root(rel_in)      # 唯一入口：连带代码库根禁区
            except Exception:
                continue
            key = str(abs_path)
            if key in seen:
                continue
            try:
                mtime = _fmt_time(abs_path.stat().st_mtime)
            except OSError:
                mtime = ""
            seen[key] = {
                "path": rel,                 # 复用唯一入口归一出的相对路径，与 tree 口径一致
                "name": abs_path.name,
                "preview": _preview_of(abs_path),
                "last_seen_at": mtime,
            }
    return list(seen.values())[:_RECENT_KEEP]
```

> `_preview_of(path)` 是全模块唯一的类型判定（`.txt/.md → text`、图片后缀 → `image`、其余 `none`），**后缀规则只此一处**，前端不自己判（M18）。

#### 4.1.11 `/files/search` 与实施期核查（v3.8 新增）

**为什么加这个端点**：用户在**对话页输入框手打 `@文件名`** 时也应能带内容。北京老陈裁定走方案 **B2（后端搜索）**，而非纯前端过滤 —— 因为树只在**打开文件页时**才进前端内存，用户从没开过文件页就搜不到任何东西，该限制会被直接感知为"我打 @ 什么都不出来"。

**接口**：

```
GET /api/v1/files/search?q=readme&limit=20
→ {"keyword","results":[{"path","name","type","preview","dir"}],"scanned","hit_limit","scanned_cap"}
```

- `path` 可直接喂 `/files/read`；`dir` 单独给出，供前端**区分同名文件**；
- 广度优先，**每层先文件后目录**（用户找的通常是文件，早命中早停）；最大 4 层 / 20000 节点（复用 tree 同款双闸门思路）；
- **空关键词直接短路**（必然零命中，不该白扫一遍仓库）；
- 越界符号链接与越界根路径不入结果（与 `_scan_dir` 同口径）。

**`truncated` 拆为两个字段的理由**：`build_tree` 的 `truncated` = 节点触顶，而搜索的截断有**两种成因**（结果达 `limit` / 扫描超 `max_nodes`），混成一个 bool 前端无法区分"结果太多被截"与"仓库太大没扫完"，提示会说错。故拆为 `hit_limit` 与 `scanned_cap`，语义互不覆盖（沿用 `_ScanResult` 已有的"标志不覆盖"模式）。

**本节同时是实施期的核查结论**，两个真 BUG 与其根因见文首 §v3.8 核查结论表。**一条通用教训**：

> 两次 BUG 的成因相同：**照着文档写完就报完成，从未独立验证语义**。
> BUG-1 是类型契约（pydantic 对象 vs dict），BUG-2 是路径语义（相对路径 vs CWD）。
> 后者的讽刺之处尤其深——**bug 本身就是从本文档 4.1.7 的示例代码照抄来的**，写文档时推演了一遍却没跑过。
> **结论：设计文档的示例代码不是可信来源，落地时必须用真实输入实跑验证。**

#### 4.2.2 输入框接入 `ChatInput.tsx`（M1/M4/M5/M21/M25/M27）

**必须订阅，不能只在挂载时取一次（M21 —— 否则引用静默丢失）**

核实：ChatInput **常驻不卸载**（`readPanelVisible` 对 input 面板永不返回隐藏，`useChatPanels.tsx:323-355` 未声明 `persistVisible`）。若用 `useEffect(..., [])` 取一次，则：

```
已在对话页 → 切到会话 B → 去文件页选文件点"发送"
  → navigate('/?session_id=B')，路径仍是 '/'，仅 query 变 → React **不重挂载**
  → takeAll 不再执行 → 引用进了 store 没人取 → **凭空消失，无报错**
```

正解（与项目既有 `useChatStreamSession.ts` 同一模式）：

```tsx
// composerRefStore 需暴露 subscribe + getSnapshot（useSyncExternalStore 契约）
const incoming = useSyncExternalStore(
  composerRefStore.subscribe,
  composerRefStore.getSnapshot,        // 返回待消费队列（长度）
);
useEffect(() => {
  if (incoming === 0) return;
  const refs = composerRefStore.takeAll();
  setRefs(prev => [...prev, ...refs]);
  setDraft(d => `${d}${d ? ' ' : ''}${refs.map(r => `@${r.label}`).join(' ')} `);
}, [incoming]);
```

只要 store 一有数据就消费，**与组件是否重挂载无关**——这正是当初选「单例 + 订阅」而不是「传参」的回报。

**发送与失败处理**：

```tsx
const handleSendInternal = async () => {
  const userText = draft.trim();
  if (!userText || sendBlocked) return;

```

**跨会话清理（M25）—— 注意落点不在 ChatInput 内**：

项目有前科（2026-09-02「useEffect 重置 draft 防跨会话泄漏」），refs 必须同样归零。但**draft 的单一真源已在 `hooks/useInputDraft.ts`，不在 ChatInput 里**（2026-10-10 重构后外提）：`useInputDraft.ts:70-84` 才是按 `sessionId` 切换草稿的那段 effect；`ChatInput.tsx:84-86` 是「`sessionId` 变化 → 复位历史翻动游标」，二者别混。

refs 与 draft 同生命周期，故清理必须与 draft **同处**完成：

```tsx
// ① 首选：让 useInputDraft 一并托管 refs（refs 与 draft 同生共死，不分家）
//    useInputDraft.ts 的 applyDraft 出口处同时 setRefs([])
```

若坚持放在 ChatInput，则须保证**覆盖 `useInputDraft` 的全部切换出口**（初始化、sessionId 切换、发送回填、clear），漏一个即跨会话泄漏。**不得只在某个 `useEffect([sessionId])` 里补一行 —— 那挡不住发送回填路径。**

**发送失败时 refs 的去留（M4，本节新增决策点）**：现有 `handleSendInternal`（`ChatInput.tsx:177-196`）的 `backup` **只有 draft 字符串，无 refs 备份位**。发送失败时：

| 方案 | 行为 | 代价 |
|---|---|---|
| **推荐** | draft 恢复，**refs 保留** | 用户重试时 Agent 仍拿得到内容；否则他重试后 Agent 收不到任何东西，却不知道自己丢了什么 |
| 备选 | refs 一并清空 | 行为"干净"，但用户必须重新去文件页选一遍，且大概率不知道为什么内容没了 |

**选推荐方案**。实现上 `refs` 独立于 draft state，故失败分支不需动 `backup` 逻辑，只需**不调 `setRefs([])`**（当前代码只在 `await onSend` 成功后才清 —— 已符合，无需改）。

**发送中注入（I8）**：`sendBlocked` 时仍收 refs 并显示卡片，顶部提示「当前正在生成，请等待本轮结束后编辑并发送」。注意 `sendBlocked`（`ChatInput.tsx:116` → `utils/sendGate.ts`）已是单一真源，被提交按钮置灰等多处消费，refs 相关改动**不得另立判据**。

#### 4.2.8 设为会话工作目录（J3 / M22 —— 常见配置下会整单 422）

#### 4.2.9 消息侧文件引用渲染（J5）

三处改动，一个新组件：

**① 新增 `FileRefChip`**（建议置于 `components/markdown/FileRefChip.tsx`，属中立层而非 chat 下）

```

点击:  navigate(`/files?path=${relPath}${lineRange ? `&line=${lineRange.start}-${lineRange.end}` : ''}`)
                                                            ↑ 参数格式统一为 start-end，与下方预生成 href 保持一致
```
- **不可删除**（是 Agent 的输出，不是用户的引用）；
- 校验不通过 → 由调用方退化为纯文本，**不渲染成 chip**；
- 复用 T1 的行级高亮能力：带 `line` 参数时打开文件页后滚动并 `<mark>`。

**② 字符串预处理**（放在 `MarkdownSlot.tsx` 内、进入 `MarkdownText`/`MarkdownBody` 之前）

> `MarkdownSlot.tsx:46-61` 是两分支**共用的唯一预处理位**（markdown 开关分流 + `MD_IMPL` 分发），且 `TextStream.tsx:32` / `ResponseStream.tsx:34` 两个消费端都在它之上 —— 预处理放这里，两分支自动都吃到。**不要放进 `MarkdownText` 或 `MarkdownBody` 内部**，否则 MD_IMPL=0/1 行为分叉。

```ts
const preprocessFileRefs = (text: string): string =>
  text.replace(/\[\[文件:([^\]#|]+)(?:#L(\d+)(?:-L?(\d+))?)?\]\]/g, (_m, p, a, b) => {
    // ★ 校验在此收口：不合法就原样返回，保留模型原文，不制造假链接
    if (!isValidRelPath(p)) return _m;
    const lines = a ? `&line=${a}${b ? `-${b}` : ''}` : '';
    return `[📄 ${p}](/file-ref?path=${encodeURIComponent(p)}${lines})`;
  });
```

**v4.0 更正 `isValidRelPath()` 的职责边界（原设计会造成第三份边界实现）**

原设计写「与 J1 的 `isViewablePath()` 抽成同一个函数（DRY：同一套边界规则不许存在两份）」。**方向对，但那样会是第三份实现**：

| 实现 | 判定内容 | 现状 |
|---|---|---|
| 后端 `_resolve_within_root` | 空串归一 / 拒绝对路径 / 拒 UNC / 拒 `..` / **祖先关系判界**（非字符串前缀）/ 符号链接消解 / **代码库根禁区** | 唯一权威 |
| 前端 `isViewablePath` | 同上（设想） | — |
| 前端 `isValidRelPath` | 同上（设想） | — |

而**浏览器没有 `Path.resolve()`**，前端只能自己拼，这套规则必然与后端分叉 —— 后端实施期已经踩过这个坑：`_ref_path_in_root` 曾与 `_resolve_within_root` 并存，两份实现分叉（agent 层那份**漏了代码库根禁区**），已收敛回唯一入口（见 4.1.6 与 4.1.11）。

**v4.0 定案：前端只做「形态校验」，权威判定一律交给后端。**

```ts
// 前端唯一一份、且只管形态（不碰符号链接/代码根禁区这类后端语义）
function isValidRelPath(p: string): boolean {
  if (!p || /^[a-zA-Z]:/.test(p) || p.startsWith('/') || p.startsWith('\\\\')) return false; // 绝对/UNC
  return !p.split(/[\\/]/).includes('..');                                                  // 穿越
}
```

前端**不再**判定「是否落在 project_root 内」「符号链接是否越界」「是否命中代码库根禁区」—— 这三类全交后端：

| 场景 | 后端行为 | 前端表现 |
|---|---|---|
| 点击 chip 深链到越界文件 | `/files/read` 返 `error.code=PATH_OUTSIDE_ROOT` | 显示该 code 的错误提示 |
| refs 携带越界 path | `sanitize_refs` **整条丢弃**（正文也不给模型） | 不提示亦可（用户本就看不到内容）；若要提示须明确"该条目已被丢弃" |
| `isViewablePath` 的"存在性" | `/files/read` 返 `NOT_FOUND` | 显示"文件不存在" |

**代价**：用户点一个无效 chip 后才知道它无效，而不是点击前就禁用。**换取的是后端唯一判定点不被稀释** —— 这个交换是划算的，且与后端 v3.8 的收敛方向一致。

**③ 两个渲染分支各挂一处**

| 分支 | 改哪里 | 改法 |
|---|---|---|
| `MD_IMPL=0`（**当前实际取值**，`MarkdownSlot.tsx:31`） | `MarkdownText.tsx:265-278` 的 `a` 组件 | `href?.startsWith('/file-ref?')` → 渲染 `FileRefChip`（**不 target=_blank**）；否则原逻辑不变 |
| `MD_IMPL=1` | `MarkdownBody.tsx:42-43` 的 `INLINE_RE` + `renderInline`（`:48-96`） | **该分支当前完全没有链接解析**，需新增一组捕获。注意 `:38-39` 的警告：「不可另立捕获组，`String.split` 会把每个捕获组都作为独立片段返回」→ 新分支须并入既有分组或另起一次 split，**是实质改动成本** |

> `MarkdownText.tsx:265` 的 `a` 组件**硬编码 `target="_blank"` 且不可配置** —— FileRefChip 分支必须在此处**提前 return**，否则同一条记录会被 `target=_blank` 带到新标签页，与 4.2.9 预生成的 `navigate('/files?path=…')` 深链方案冲突。

**必须回归**：`markdown-text-fence.test.tsx`（围栏切分 + 复制按钮），并新增用例：标记在代码块内不生效、非法路径退化为原文、`#L12-L20` 行号正确解析、**两个 MD_IMPL 分支表现一致**。

**待实测确认（v4.0 仍未测，已挂多日）**：预处理产出的是相对 URL，需确认 `react-markdown` 的 `defaultUrlTransform` 放行相对 URL（只拦 `javascript:` 等危险协议）。若被拦截，退路是改用非 `href` 的自定义标记 + `components` 映射（此时需在 `SANITIZE_SCHEMA` 补标签与属性，第三处净化放开需单独评估）。**这是 J5 唯一的未决技术风险，动手前应先花 10 分钟实测掉。**

### 4.3 架构决策论证

#### 4.3.1 跨页通道选型

| 方案 | 评估 | 结论 |
|------|------|------|
| URL query | 正文可达数十 KB，URL 长度/编码风险，污染历史 | ❌ |
| sessionStorage | 半持久化，清理时机分散，易脏读 | ❌ |
| props 透传 | 跨 Route 物理不可行 | ❌ |
| **模块级单例 + 一次性消费** | 与既有 `chatStreamStore` 同风格；零新依赖；无残留；与来源解耦 | ✅ |

#### 4.3.2 为什么引用必须走结构化 `refs`

v3.0 为求「后端零改动」把正文拼进 user content，核实后确认三个必然副作用（复制污染 / 历史回放 200 字怪文本 / 正文长期占上下文）。结构化 refs 以「动 5 处」换取副作用消除，并**打开「将来渲染成卡片」的路**。

#### 4.3.3 为什么 refs 拼在 `message_builder.init_history` 而非 orchestrator

见 4.1.6 三条理由。补充一条容易被忽略的：**插话路径不经过 `_append_ws_suffix`**（首发才走），若拼在 chat 层则插话丢 refs；拼在 `message_builder` 则首发与插话天然统一。

#### 4.3.4 为什么 refs 正文不入库、且接受"不会被 compaction 清理"

入库会污染存储与历史；路径才是长期有效的最小充分信息。至于 compaction 不清理 user 正文（M23），这是既有设计（`trim_history` 保 user）的必然结果，改动风险过高，**本期不改机制**；v3.4 亦未设体积闸门，改由发送按钮的字符数提示（M11）让用户知情。

#### 4.3.5 为什么引用是独立 state 且必须订阅 store

- 独立 state：`ChatInput.tsx:84-86` 的 `useEffect([sessionId])` 会清空 draft（跳回对话页时 URL 带 sessionId 必触发）；
- 必须订阅（M21）：ChatInput 常驻不卸载，同路由仅 query 变化不重挂载，挂载时取一次会静默丢引用。**这正是「单例 + 订阅」设计的价值所在**。

#### 4.3.6 为什么 J3 不做前端预判

禁区判据（`_is_forbidden_path` + `validate_path` + `_is_broad_root`）在 `workspace_service`，是唯一真源。前端复制一份必然随规则演进而漂移，**漂移的后果是"前端说能用、后端说不行"**，用户无从理解。只做错误如实呈现。

#### 4.3.7 为什么删掉 `/files/list`

`tree` 传 `path=<目录>` 即等价于该目录的单层列表；两个端点意味着两处排序/过滤实现，必然分叉（M8 的老问题）。**少一个端点、少一处分叉面。**

#### 4.3.8 为什么不用 `tool/execute`

生产双重禁用；返回 LLM 视角结构；且用户主动浏览 ≠ Agent 执行工具的语义。

#### 4.3.9 为什么全量优先 + 自动降级

| 方案 | 优点 | 缺点 |
|------|------|------|
| 纯懒加载 | 性能最稳 | 小仓库也要逐层点箭头 |
| 无限制整树 | 最省事 | `antd 5.29.3` `Tree` **无 virtual**，大仓库渲染卡死；全量 stat 极慢 |
| **全量优先 + 自动降级** | 小仓库一次到位；大仓库首屏只 5 层/5000 节点 | 需一个递归端点 |

#### 4.3.10 为什么 J4 移出本期（M2）

`with_artifacts` 零调用方意味着「产物登记」需要横跨多个产出类工具各自改造，属独立专题。把它塞进本方案会让「互惠闭环」变成空头支票，不如如实移出并写明前置条件。

#### 4.3.11 J5 为什么不用「前端识别裸路径」而用「显式标记」

| | 路线 A：识别裸路径 | 路线 B：显式标记（采纳） |
|---|---|---|
| 能否拦截文本节点 | **不能**（`hast-util-to-jsx-runtime/lib/index.js:154` 短路在元素分支之前）→ 必须写 rehype 插件 | 不需要拦文本，**在进解析器前的字符串预处理**即可 |
| 跳过代码块 | 组件层拿不到祖先（hast 无 parent 指针），需在插件里自维护祖先栈 | 标记由模型显式输出，落在代码块里就自然不生效 |
| Windows 反斜杠转义 | 需按转义后形态写正则 | 不涉及 |
| 误伤 URL / 日期 / 比例 / 日志行 | 需白名单式识别，漏一道即误判 | 无 |
| 存在性校验成本 | 每个疑似路径一次 stat | 只对模型明确标记的少数路径校验 |

#### 4.3.12 为什么 `a` 组件不能复用（J5 的必踩点）

`MarkdownText.tsx:265-278` 的 `a` 硬编码 `target="_blank"`，`SANITIZE_SCHEMA` 注释亦明确「不补 a[target/rel]」。复用它 = 文件引用**新开浏览器标签页**，桌面端不可接受。故新增 `FileRefChip` 并在 `a` 内按 href 前缀分流——这是本条唯一"不能省"的组件级改动。

#### 4.3.13 为什么两个渲染分支都要覆盖

`MD_IMPL` 是改一个数字即切换的开关（`MarkdownSlot.tsx:31`，注释已警示「静态引入」）。只改 react-markdown 分支，一旦切到 `MD_IMPL=1`，文件引用会**静默退化为死文本**，无任何报错。故：
- 分支 0：字符串预处理 + `a` 组件按前缀分流；
- 分支 1：`INLINE_RE` 加一组捕获 + 一个渲染分支（约 10 行）。

#### 4.3.14 为什么标记路径必须走校验而不直接拼 href

> **v4.0 更正定案**：原文主张前端实现 `isValidRelPath()` 并"与 `isViewablePath()` 抽成同一个函数"，隐含前端要复刻完整边界判定（含 `resolve()` 与落根判断）。现改为：**前端只做形态校验，权威判定全交后端**（实现见 4.2.9）。

**不变的前提**：标记来自**模型输出**，属不可信输入。任一校验不满足即**退化为纯文本**，绝不生成 href，也绝不 `dangerouslySetInnerHTML`。这一条无论判定放前端还是后端都成立。

**变化的是判定范围**：

| | 原设想 | v4.0 定案 |
|---|---|---|
| 前端判定 | 落根内 + 符号链接越界 + 代码库根禁区 | **仅形态**：拒绝对路径 / 拒 UNC / 拒 `..` |
| 越界与存在性 | 前端 `resolve()` + 判界 + stat | **后端 `error.code` 回答**（`PATH_OUTSIDE_ROOT` / `NOT_FOUND`） |
| 份数 | 变成**第三份**边界实现 | 零重复 |

**为何不能让前端判**：浏览器无 `Path.resolve()`，祖先关系判界与符号链接消解无法忠实复刻。

**实证教训**：后端实施期 `_ref_path_in_root` 与 `_resolve_within_root` 并存时，两份实现**已经分叉**（agent 层那份漏了代码库根禁区），最终收敛回唯一入口（4.1.6）。同一类错误不应在前端再犯第三次。

代价与接受理由：用户点击无效 chip 后才知其无效，而非点击前禁用。**换取后端唯一判定点不被稀释，划算。**

### 4.4 安全自检（三堂会审）

| 检查项 | 结论 |
|--------|------|
| 越权读文件 | `resolve()` + 祖先关系；拒绝对路径与 `..` |
| 符号链接逃逸 | `resolve()` 消解；越界条目不返回 |
| 代码库根泄漏 | 命中即 403；`project_root` 落在其内时跳过禁区并 **warn 一次**（S6/M17） |
| 未鉴权暴露 | 走 `_mount()`；严禁手写 `include_router` |
| ~~敏感文件黑名单~~ | **已删除**（v3.4）：目录里有什么显示什么，`.env`/`*.pem` 等与普通文件同等可读 |
| prompt injection | refs 块标「不可信数据」边界 + 系统提示常驻声明（S7） |
| 类型越权 | 前端置灰 + 后端 415 双侧；`raw` 另有图片后缀白名单 |
| SVG 脚本注入 | 仅 `<img src=blob:>`；严禁 `dangerouslySetInnerHTML` |
| objectURL 泄漏 | 统一 `clearImage()` 切文件/卸载即 `revoke` |
| 图片鉴权绕过 | 不用裸 `<img src=API_URL>` |
| 竞态错显 | AbortController + 请求序号（I7） |
| 缓存白做 | ETag 与框架同算法；`no-cache` 非 `no-store` |
| 路径拼接注入 | J1 的 LLM 原始 path 必须 resolve 后判界（M6） |

| 404 | `NOT_FOUND` | 文件/目录不存在 |
| 404 | `SESSION_NOT_FOUND` | session 不存在 |
| 413 | `FILE_TOO_LARGE` | 文本 > 2MB |
| 413 | `IMAGE_TOO_LARGE` | 图片 > 10MB |
| 415 | `UNSUPPORTED_TYPE` | 非 `.txt`/`.md` 且非图片后缀 |
| 415 | `UNDECODABLE_ENCODING` | 编码兜底链全失败 |

> ⚠️ **HTTP 响应体实际形状**（`j05` 端点层测试钉死）：
> ```json
> {"success":false,"error":{"code":"IMAGE_TOO_LARGE","message":"图片超过 10MB，本期不支持预览"},
>  "status_code":413,"timestamp":"2026-10-13T18:05:13.835020"}
> ```
> **前端取 `error.code`，不是 `detail.code`** —— 全局 `http_exception_handler`（`main.py:141-156`）把 `detail` 放进了 `error` 键。

## 六、媒体引用（图片/视频）可行性核查

> 北京老陈 2026-10-13 19:42:32 提问：「前端输入框提交图片视频，是否也走 refs 通道？」
> 本章为**实测核查结论**，非推演。所有判断均给出可复核的文件与行号。
> 编写人：小欧

### 6.1 结论（一句话）

**当前不能，且卡点不在 refs 通道 —— 在上游模型链路根本不接受图片输入。**
refs 通道本身对文本是完全可用的（见 5.6），它不是瓶颈。

### 6.2 五处卡点（逐条实测）

| # | 卡点 | 实测证据 |
|---|---|---|
| 1 | `kind` 白名单不含媒体类型 | `message_builder.py:88` → `_REF_KINDS = frozenset({"file","selection","log","message"})`；`models.py:34` 描述亦为「file/selection/log/message」。传 `kind="image"` 会被 `_render_refs_block` 的 `if kind not in _REF_KINDS: continue` **静默丢弃** |
| 2 | `content` 语义是正文文本 | `models.py:40` → `content: str`，上限 `MAX_REF_CONTENT_CHARS = 2_000_000`（2 MB） |
| 3 | 🔴 **base64 会被丢弃** | `services/agent/observation_formatter.py:604-613` 见 6.3 |
| 4 | 消息 content 类型锁死 `str` | `message_builder.py:204/210` → `add_system_message(content: str)` / `add_user_message(content: str)`；多模态要求 content 是**数组** `[{"type":"text"},{"type":"image_url"}]` |
| 5 | **全库无多模态实现** | 全后端检索 `image_url` / `multi_modal` / `multimodal` / `"type": "image"` → **零命中** |

### 6.3 真正的卡点：Agent 现在看不见任何像素

`app/services/agent/observation_formatter.py:604`（**2026-07-20 北京老陈本人裁定的门限治理**）：

```python
"""readmedia 媒体文件 — 仅元数据 + base64 字符数摘要
base64 为二进制编码, 非可读文本, 不可按文本行×列处理(LLM 无法消费截断 base64, 且体积大浪费 token);
Tool 输出零截断(3.7); observation 仅渲染元数据摘要, 不展开 base64(6.4)。"""
# 实际输出形如：photo.jpg [image/jpeg, 204800 bytes] [base64: 273104 chars]
```

即：Agent 调用 `readmedia` 后，**只得到"这是个 204KB 的 jpg"**，图片内容以 `base64_data` 存在于 `data` 里，但在进 LLM 前被 `observation_formatter` 换成了一句字符数摘要。

**推论**：前端即便把图片塞进 refs 并正确上行，Agent 侧收到后同样无法消费 —— **改了 refs 协议也是白改**。

这正是 4.7 第 6 条早已备案的判断：

> 6. 图片进入引用（**需 Agent 侧先具备多模态入参** —— `readmedia` 的 base64 当前不进模型）

### 6.4 三方案代价对比

| 方案 | 改动范围 | Agent 能否真看到图 | 判断 |
|---|---|---|---|
| **A. 只改前端**（把图片转成文字描述塞进 refs） | 小 | ❌ | 描述由前端伪造，不可信且白占 token。**否决** |
| **B. 改 refs 协议**（`kind` 加 `image`、`content` 带 base64、上限 2MB→10MB+） | 中（前后端 + DTO） | ❌ | **白做**：模型侧仍丢 base64，卡点 3/4/5 一个都没碰 |
| **C. 打通多模态**（真方案） | **大**：① `message_builder` 的 content 类型放开为 `str | list` ② `llm_client` 组装多模态 wire ③ `readmedia` 的 base64 从"只给字符数摘要"改为真传给模型 ④ 视口/缩略图与 token 预算策略 | ✅ | 唯一可行路径 |

### 6.5 token 与体积账（方案 C 的现实约束）

| 项 | 数值 | 说明 |
|---|---|---|
| base64 膨胀 | **+33%** | 2 MB 图片 → 约 2.67 MB 字符串 |
| 折算 token | 约 **1500 token / 张**（多数厂商按 ~1800 px 折算） | 单张可接受 |
| 上限场景 | 10 MB 图 ≈ **8500 token** | **必须**做单轮张数与体积预算，否则一次拖垮上下文 |
| **视频** | 几十 MB 起步，转 base64 再涨 33% | **无厂商接受视频输入**；本方案对视频不适用 |

> **视频的现实路径**（若将来要做）：只能走「抽帧 → 送关键帧图片」，即退化为方案 C + 抽帧，属独立专题，**不在本期也不在下一期**。

### 6.6 落地顺序建议（关键：顺序不能反）

| 阶段 | 内容 | 时机 |
|---|---|---|
| **第一步** | refs 通道**只做文本**（`.txt` / `.md` / 选区 / 日志）。`kind` 白名单已天然挡住媒体类型，**前端不需要为媒体做任何特殊处理** | 本期 |
| **第二步** | **先打通 Agent 侧多模态**（让 Agent 真能看图） | 独立专题 |
| **第三步** | 多模态就绪后，再做前端图片引用（`kind=image` + base64 + 张数/体积预算） | 独立专题 |

**为什么不能反着做**（必须写进设计，避免将来有人"顺手"先做前端）：

> 若先做前端图片引用，用户点发送 → 卡片显示正常 → 请求成功 → Agent 收到一张图 →
> **Agent 什么也看不见**，只会回一句「你发的是个 jpg」。
> 这比**没有这个功能更糟**：用户会以为系统坏了，且难以自证（卡片在、请求成功、无任何报错）。
> 这与 4.1.6⑥ 记录的 `extra='ignore'` 静默失效是**同一类事故** —— 表面成功、实质空转。

### 6.7 前端本期应有的行为（防止误实现）

前端在媒体引用上**必须**做到：

| 要求 | 理由 |
|---|---|
| 输入框**不提供**图片/视频附件按钮 | 无对应后端能力，做了就是假功能 |
| 若历史消息里存在媒体卡片，**不渲染成"已发送"的可信态** | 该内容 Agent 未消费，属误导 |
| `@` 补全的候选**只列** `.txt` / `.md`（与 `_preview_of()` 的 `text` 判定对齐） | 避免用户选中一张图却发不出内容 |

> 依据：`browse_service._preview_of()` 是**后缀类型的唯一真源**（5.1 图中标注）。前端候选过滤应与之对齐，不自己另立规则（4.0.2 的 M18 约定）。
