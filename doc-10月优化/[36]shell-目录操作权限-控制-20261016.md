# 第一章 权限判定链路总览

```
┌─ 入口 ─────────────────────────────────────────────────────────────┐
│  Agent 链    handle_action → safety_gate                            │
└──────────────────────────┬─────────────────────────────────────────┘
                           ↓
┌─ Safety 层（app/safety/）── 判"权限" ──────────────────────────────┐
│  path_check_entry.validate_tool_path                               │
│    ├─ bash → shell_path_check.validate_shell（命令专用通道）        │
│    ├─ multi → multi_path_check.validate_multi_path（复合工具）      │
│    └─ 单动作 → LINE_BY_ACTION 三线分派                              │
│         ├─ read_path_check / write_path_check / delete_path_check  │
│         └─ 三线共调 path_guard.classify_forbidden_path ◀── 判定点①  │
│              └─ path_guard 4 谓词单源 ★ 判定依据                     │
│               （is_system_protected_path / is_disk_root /           │
│                is_code_root_path / is_protected_root_itself）       │
│         分流：system → blocked 永不授权                            │
│              non_system → 写可任务级授权 / 删硬拦                   │
│              白名单外 → 需确认                                      │
│         异常 → 判 system（fail-closed，不静默放行）                 │
└──────────────────────────┬─────────────────────────────────────────┘
                           ↓ requires_confirmation
                   HITL 弹窗 → grant_temp_auth（临时授权）
                           ↓
┌─ 工具层（app/tools/）── 判"路径合法性" ───────────────────────────┐
│  工具函数体内                                                       │
│    file_path_checker.validate_path   ← 只判合法性，不判权限          │
│      ① 基础(非空/盘符/保留字符/保留名) ② 存在性+类型 ③ 业务警告     │
│    delete_file._guard_forbidden_delete   ◀── 判定点 ②（唯一）       │
│         └─ path_guard 单源（A族系统目录/盘根 + B族受保护根及上级）  │
│         （删文件专属，不读 security.enabled）                        │
└───────────────────────────────────────────────────────────────────┘

★ 判定依据：app/safety/path_guard.py（工具层硬底线与安全层共调，
  本模块零配置读取、零 I/O、不读 security.enabled）
```

**读法**：判定点①②都汇到同一个 ★（`path_guard`），口径必然一致；② 存在的意义是"绕过 Safety 直接调
delete 函数"时仍不失守。`classify_forbidden_path` 异常时返回 `"system"`（fail-closed），异常不放行。

工具层 3 层检查（`file_path_checker.validate_path`，L235-278）

目录权限(系统目录/磁盘根/代码库根/受保护根)已移出本层 ——
权限由 Safety 层单一决策，硬底线由 `delete_file._guard_forbidden_delete` 镜像 A 族。
故本层不判权限。

Safety 只判**权限**，不判路径格式；下列 3 层全是工具层职责（函数体 `validate_path` **L235-278**，
第1、2层本体在 `validate_path_layers12` **L179-232**，本函数 = 前两层单源 + 第3层警告）。

**第1层：基础校验（L194-213）** —— 非空 + 盘符 + 保留字符 + 保留名

| 检查 | 例子 |
|---|---|
| 路径非空 | `""` → "路径不能为空" |
| 驱动器是否存在 | `Z:\a.txt` → "驱动器: Z不存在。可用驱动器: …" |
| 多余盘符 | `E:\dir\E:\file` → "路径: …中包含多余的盘符" |
| 文件名含 Windows 保留字符 | `a<b.txt` → "文件: a<b.txt名包含Windows保留字符" |
| 文件名是 Windows 保留名 | `CON.txt` `NUL.txt` → "文件: …名包含Windows保留名" |

> 实码：`_has_windows_reserved_name` 判定保留名；保留字符只查文件名部分（`Path(path).name`，
> 排除路径分隔符与盘符 `:`）。

**第2层：存在性与类型（L215-232）** —— 按操作类型要求"存在"且"是文件/是目录"，
不存在时打 `[TOCTOU]` 日志（含 `drive_exists` / `parent_exists` / `parent_dir`）。
WRITE 类操作 `check_exist=False` 跳过本层；delete 的 `force=True` 走幂等删除（不存在即视为已删）。

**第3层：业务警告（L266-278）** —— 覆盖大文件(>1MB)、append 到超大文件(>100MB)、递归删目录、
永久删除、覆盖已有目标（`overwrite + source`）

> 第3层返回的是 **warning 不是 error —— 允许执行，只提醒**。
> （实测：覆盖 2MB 文件 → `valid=True, error=None, warning='覆盖大文件(2097152字节)，请确认'`）

**L262-264 实码原文**（权限为何不在本层）：

```
# 2026-10-14 北京老陈裁定: 本层只判参数合法性(格式/存在性/类型/大小/递归), 不判权限。
#   目录权限(系统目录/磁盘根/代码库根/受保护根)统一由 Safety 层决策, 硬底线由
#   delete_file._guard_forbidden_delete 镜像 A 族 —— 权限判定权收敛到唯一一处。
```
LLM 调工具
  │
  ▼
 门前初查:precheck_path_legality ，只跑前两层
  │
  ▼
SA1 入口安检（check_safety_and_confirm，含 precheck_path_legality 门前初查，只跑前两层）
  │
  ▼
SA2 会话信任预查（resolve_skip）
  │
  ▼
SA3 安全总闸（path_check_entry.validate_tool_path → 读/写/删三线）
  │  判权限：禁区/白名单/要不要授权
  │  不通过 → blocked/弹确认，到此为止
  │
  ▼ 通过
SA6 HITL 确认 + 授权入库（grant_temp_auth）
  │
  ▼
SA7 沙箱门（run_sandbox_gate，沙箱预检另有 _is_outside_write_target / _OUTSIDE_TARGET_RE）
  │
  ▼
工具函数执行 ──→ validate_path（file_path_checker）
                   判合法性：格式/存在/类型/大小
                   不通过 → 返回 error/warning，不干活
  │
  ▼ 通过
真正读写文件

**分工落点**：权限判定权收敛到 Safety 层一处，工具层只判参数合法性。

# 第二章  shell 命令路径的摘出与读写判定

## 2,1 现状分析

bash 类命令的绝对路径**由 Safety 层摘出并复用三线路径权限判定**，实码
`app/safety/shell_path_check.py:29 validate_shell`（调用方 `path_check_entry.py:174-176`
`normal_name == "bash"` 特判，不经 action_kind 分派）。

bash 属 `FUNDAMENTAL`，走命令专用通道：命中写意图时，把命令里的绝对路径逐个交给
对应单线的 `validate_delete` / `validate_write`，返回值直接作为 `validate_tool_path`
的返回值。故 bash 复用与 write/delete **完全一致**的 `system`（硬拦，永不授权）/
`non_system`（写可授权、删硬拦）语义，**不新增第二套判定**（DRY）。

**读写区分**（`shell_path_check.py:50`）：含删动词走删线，否则走写线。
删与写若混一张表，删系统禁区只会被判成「可授权的写」，**授权后等于放行删系统目录**。
删动词表 `_DELETE_CMD_RE`（`shell_command_guard.py:414`）与写动词表 `_WRITE_CMD_RE`
（`shell_command_guard.py:387`）并列而非替换。

**两段文本分开用**：

| 用途 | 用哪段文本 | 原因 |
|---|---|---|
| 判写意图 | **剥引号后**的文本（`mask_quoted_spans`） | 否则 `Select-String -Pattern "del" <路径>` 这类只读查询会因模式里的动词字面量被误判为写意图 → 误要求授权 |
| 抽绝对路径 | **原文**（引号区保留，引号区先完整取出） | 抽路径要保住含空格的完整路径；裸路径只在引号区之外扫描，防同一段路径被截断 |
| 判重定向 | 剥引号后是否含 `>` | 重定向目标提取用 `_REDIRECT_RE`（`shell_command_guard.py:395`），只负责提取目标 |
| 环境变量 | `_resolve_env_fragment` 先展开 `$env:XXX` 再抽 | 否则 `$env:TEMP\a.txt` 形态抽不到盘符路径 |

**边界**：`cwd` 按写线先判（`shell_path_check.py:39-43`，`cd C:\Windows && echo x > a.txt`
里的相对写落在 cwd）；UNC（`\\host\share`）不在 `_ABS_WIN_PATH_RES`
（`shell_command_guard.py:432`，仅覆盖盘符引号/裸路径）覆盖内，UNC 与 `~`、`$env:`、
注册表驱动器形态由沙箱预检 `_OUTSIDE_TARGET_RE`（`shell_command_guard.py:396`）覆盖。

**留痕**：违规时打 `[shell_path_check] bash写目标越权` warning，含 `category` / `path` /
`command` 前 200 字符 —— 下游 `tool_safety_checker` 只记 `tool=bash` 没有命令原文，
无此日志则排查时无法定位"是哪个命令想写这个路径"。

## 2.2 shell 工具内自保检查的分工

shell 命令过两道**互不重叠**的检查，二者都在 Safety/工具链内、都先于执行：

| | SA5 路径权限 | shell 工具内自保 |
|---|---|---|
| 位置 | `app/safety/shell_path_check.py:29` `validate_shell` | `app/tools/fundamental/execute_shell_command.py:1122` `check_shell_command_risk` |
| 判什么 | 命令里**绝对路径**是否越权（system/non_system/白名单） | **命令模式**危险度（注入、`Format-Volume`、递归删、杀进程…） |
| 规则表 | `_WRITE_CMD_RE` / `_DELETE_CMD_RE` / `_ABS_WIN_PATH_RES`（`shell_command_guard.py:387-436`） | `SHELL_DANGEROUS_PATTERNS`（`execute_shell_command_safety.py:59`，共 **43** 条） |
| 分标签条数 | —— | `ps` 13 + `cmd` 14 + `bash` 7 + `st_tag=None`（双兼容）9 = 43 |
| 实际生效条数 | —— | ps7/ps5 = 13+9 = **22**；cmd = 14+9 = **23**；bash = 7+9 = **16** |
| HIGH 处置 | —— | **blocked 立即拦截**（L1125-1129，返 `ERR_SHELL_INJECTION`，hint 提示换策略） |
| MEDIUM 处置 | —— | **只置位 `requires_confirmation`，本级放行**（见下） |

> **生效条数口径**：`st_tag=None` 的 9 条**对全部 shell 生效**，故某 shell 的实际生效条数
> = 该标签专属条数 + 9。只数标签条数会算少（ps 13→22、cmd 14→23、bash 7→16）。
> `shell_type` 取值 `"ps7"/"ps5"/"cmd"/"bash"`；要查全部 shell 应用 `check_shell_command_risk_all_shells()`（L272），不要传 `None`。

**`execute_shell_command.py:1122` 的中风险「留」已定案**：本层**不弹窗**，`requires_confirmation`
仅记 warning 后放行，确认由上游安全门禁（SA3→SA6 HITL）承担 —— 实码注释明写
**「中风险命令本级放行(确认由上游安全门禁承担, 无弹窗非缺陷)」**（L1130-1131）。
故本层不重复弹窗，避免同一命令在工具层与 Safety 层各弹一次。

两处 HIGH 降级规则：
- 临时目录清理降级 —— 递归删目标为已知安全临时目录时降为 MEDIUM；但命令含 `..` 穿越符号时
  **不予降级、维持 HIGH 拦截**（L191-199）。仅递归删类可降，其他 HIGH 不降。
- 引号内字面量降级 —— HIGH 规则**仅**命中引号内字面量时降为中风险（需确认），L202 起。
  对全部 HIGH 规则生效（不只递归删类）；引号外也命中则维持原硬拦，只"降级不豁免"。

## 2.3 shell 权限判定与处理流程

Shell 过 **3 道独立检查**：① Safety 路径权限（判路径越权）→ ② 工具内模式风控（判命令危险度）→
③ 沙箱预检（判越界写目标）。① 在执行前由 Agent/Safety 门禁触发，②③ 在工具函数体内触发。

```
LLM 调 bash(command, cwd, shell_type)
  │
  ▼ ① SA1 门前初查
  │  path_check_entry.precheck_path_legality
  │  只跑 file_path_checker 前两层（格式/存在/类型），警告不要
  │
  ▼ ② SA3 安全总闸（判权限，backend/app/safety/）
  │  path_check_entry.py:174 validate_tool_path
  │    └─ bash 特判 → shell_path_check.py:29 validate_shell
  │         ├─ cwd 按写线先判（L39-43）
  │         │    cd C:\Windows && echo x > a.txt → 相对写落 cwd，cwd 越权直接拦
  │         ├─ 剥引号后文本判写意图（L45-47）
  │         │    _WRITE_CMD_RE（shell_command_guard.py:387）或含 ">"
  │         │    无写意图 → 放行（读命令不判路径）
  │         ├─ 删/写分线（L50）
  │         │    _DELETE_CMD_RE（shell_command_guard.py:414）命中 → 删线
  │         │    否则 → 写线
  │         └─ 逐路径判定（L52-62）
  │              _resolve_env_fragment 展开 $env:XXX →
  │              _extract_abs_win_paths 抽绝对路径（引号区完整+裸路径，引号外扫描）
  │              → delete_path_check.validate_delete / write_path_check.validate_write
  │                └─ 共调 path_guard.classify_forbidden_path（path_guard.py:173）
  │                     ├─ system（系统目录/磁盘根）→ blocked，永不授权
  │                     ├─ non_system（代码库根/受保护根）→ 写可任务级授权 / 删硬拦
  │                     ├─ 白名单外非禁区 → 确认 + 授权
  │                     ├─ 白名单内 → 放行
  │                     └─ 异常 → system（fail-closed）
  │              违规打 [shell_path_check] bash写目标越权（含 category/path/command 前 200 字符）
  │  不通过 → blocked / 弹 HITL 确认（SA6 grant_temp_auth），到此为止
  │
  ▼ ③ 工具内模式风控（判命令危险度，backend/app/tools/fundamental/）
  │  execute_shell_command.py:1122 check_shell_command_risk
  │    规则表 SHELL_DANGEROUS_PATTERNS（execute_shell_command_safety.py:59，共 43 条）
  │    生效：ps7/ps5=22，cmd=23，bash=16（st_tag=None 的 9 条全壳生效）
  │    ├─ HIGH → blocked，返 ERR_SHELL_INJECTION（L1125-1129）
  │    │    两处降级：临时目录递归清理降为 MEDIUM（含 .. 穿越则不降）；
  │    │    仅命中引号内字面量降为需确认（L202-216）
  │    └─ MEDIUM → 只置 requires_confirmation，本级放行记 warning（L1130-1131），
  │         确认由上游 SA3→SA6 承担，不在本层弹窗
  │
  ▼ ④ 沙箱门（run_sandbox_gate）
  │  沙箱预检 _is_outside_write_target / _OUTSIDE_TARGET_RE
  │  （UNC/~/$env:/注册表驱动器形态在此覆盖，Job Object 隔离兜底）
  │
  ▼ ⑤ 执行 + 工具层合法性校验
     file_path_checker.validate_path（L235-278，只判格式/存在/类型/大小，不判权限）
     delete 专属硬底线 delete_file._guard_forbidden_delete（SA8，不读 security.enabled）
```

分工记忆点：

- **路径越权**（写哪）→ ② Safety 三线，唯一决策者。
- **命令危险**（干什么，如 `Format-Volume`/注入/杀进程）→ ③ 工具内 `SHELL_DANGEROUS_PATTERNS`。
- **相对路径/UNC/注册表** → ④ 沙箱预检补位（`_ABS_WIN_PATH_RES` 只抽盘符绝对路径）。
- **直接调 delete 函数绕过 Safety** → ⑤ `_guard_forbidden_delete` 硬底线兜底。
## 3.0 背景与目标：shell 写和删除的安全策略归属重划（系统的归系统，工具的归工具）

**目标**：把 shell 命令中「写」与「删除」这类操作的安全策略（识别、判定、拦截、授权）相关代码与功能，
逐项归属重划 —— 该归系统的归系统，该归工具的归工具，名词名副其实。

**结论依据均为实码 AST 依赖实测。**

# 第三章  shell的权限处理优化方案

### 3.1 归属总则

**要求 3 的正面回答（老陈原问「move 是单独列吗？类似其他的需要单独的函数」）**：

**结论：动词表层、拆分层都已单独；出入口层不设第三个函数 —— 这是有意的，理由如下。**

| 层 | move 是否独立 | 形态 | 为什么 |
|---|---|---|---|
| ① 动词表层 | ✅ **独立一列** | `SHELL_MOVE_RE` | 与 DELETE / WRITE 三列并列，互不重叠 |
| ② 拆分层 | ✅ **独立函数** | `_extract_shell_move_paths(command) -> (源列表, 目标列表)` | 必须保位置序（`-Destination` 开关 / `mv 源 目标`），与无序的 `shell_extract_abs_win_paths` 不能混用 |
| ③ **出入口层** | ❌ **不设 `shell_move_paths`** | move 源 → `shell_delete_paths`；move 目标 → `shell_write_paths` | ★ move 的后果**不是第三类**，而是**已存在的两类**：源 = 从原位抹掉（同 del），目标 = 写入（同 write）。若单设 `shell_move_paths`，编排层就得**再判一次 mode**（这个路径是判还是写），等于回到老陈已否掉的「让调用方猜 mode」的老路 |

> **一句话回答**：**move 已经单独到「表」与「拆词」两层；只在「出入口」层不单独，因为它的源和目标分属已有的删线与写线，再单设第三个出口只会把判定责任推回调用方。**
> 落地形态见 5.3.3.3 的 `_shell_path_lines`（归属规则①源→删线、②目标→写线、⑤交集取严）。

#### 3.5.6 写/删目标识别拆两个函数

**必须拆成 `shell_delete_paths` 与 `shell_write_paths`，公用部分可公用，差异逻辑必须分开。**

理由：两者后果不同 —— 删到系统目录是**硬拦、永不授权**；写到系统目录是**可弹窗授权**。
两种后果必须由两个名字各自说清，不能塞进一个函数再让调用方去猜返回的 mode。

##### 3.5.6.1 三个函数的职责

```
app/safety/shell_command_process.py   【新建·系统层】

┌─ _extract_shell_paths(command, verb_re) ─── 删和写共用的抽路径工序
│  做什么用：按给定的动作动词表去命令里找路径。两种策略都要做这步，所以公用。
│  怎么做  ：换行归一 → 引号内容涂成空格(shell_blank_out_quotes)
│            → 按 verb_re 判断有无该类动作 → 展开 $env:VAR → 抽绝对路径
│  返回    ：(删路径列表, 写路径列表)；无该类动作返回空列表
│  不做什么：不管权限，不管白名单 —— 它只认文本
│
├─ shell_delete_paths(command) ────────────── 删除策略
│  做什么用：看这条命令会**从原位抹掉**哪些路径
│  认哪些  ：Remove-Item / Remove-ItemProperty / del / erase / rd / rmdir / ri / rm
│            + Move-Item / mi / mv 的**源参数**（移动的源被删，与 del 同级）
│  明确不含：重定向 > 与 >>（3.9.2 第一档裁定：目标恒为文件，非系统区改判据误伤正常写入；
│            系统区本就硬拦，改判据零收益）
│  返回    ：会被删的路径列表；无删动作则空列表
│
└─ shell_write_paths(command) ─────────────── 写入策略
   做什么用：看这条命令会写入哪些路径
   认哪些  ：Copy-Item / cp / cpi / New-Item / ni / Set-Content / Add-Content
             / ac / Out-File / Expand-Archive / reg / setx / regedit
             + Move-Item / mi / mv 的**目标参数** + 重定向 > 与 >>
   返回    ：会被写的路径列表；无写动作则空列表
```

**归属判定**：两个出入口的唯一调用方是 `path_safe_check`（系统层），工具层无一调用（AST 实测）。
按 3.1 判据属系统层，故置于 `app/safety/shell_command_process.py`。

**调用方**（系统层瘦身为纯编排，先问删、再问写）：

```
app/safety/shell_path_check.py
  def _validate_shell_targets(command):     【由 shell_path_check.validate_shell 改名/瘦身】
      delete_paths, write_paths = _extract_shell_paths(command)   # 一次抽取，两类分列
      for p in delete_paths:               # 先问：删哪些路径？逐个判（mv 源在此）
          ok, err, cat = delete_path_check.validate_delete(p)
          if not ok: return False, err, p, cat
      for p in write_paths:                # 再问：写哪些路径？逐个判（mv 目标/重定向在此）
          ok, err, cat = write_path_check.validate_write(p)
          if not ok: return False, err, p, cat
      return True, None, None, None
```

> 编排从「先删后写整块二选一」改为**两列都判**：mv 命令源与目标后果不同（源=删不可授权、
> 目标=写可授权），整块二选一会让目标漏判或把源错授。三线入口是 `delete_path_check.validate_delete`
> 与 `write_path_check.validate_write`（非 `check_path_permission`，后者已无对象，见 3.5.4）。

##### 3.5.6.3=2 动词表改造（三组增补 = 删除策略的判据基础）

| # | 动作 | 补入理由 | 现状 | 改造后（**按 3.9.2 第一档裁定**） |
|---|---|---|---|---|
| 1 | `Move-Item` / `mi` / `mv` | 移动的源被删除，与 `del` 风险同级 | 缺（只在写表 L388） | **源路径走 delete 出入口，目标路径走 write 出入口**（非整命令一刀切 delete） |
| 2 | `>` / `>>` 重定向 | 覆盖即抹除 | 缺（仅参与写意图） | **留 write 出入口**（不划 delete：重定向目标恒为文件，非系统区改判据会误伤工作区正常写入；系统区本就硬拦，改判据零收益） |
| 3 | `Remove-ItemProperty` | 已在删表 L415，缺在写表 → 第一道即漏 | 缺在写表 | 补入写意图总表 + delete 出入口 |

既有动词归属调整：`del`/`rm`/`Remove-Item`/`erase`/`rd`/`rmdir`/`ri` 两表都有 → **仅 delete 出入口**（消除重复）；
`Copy-Item`/`New-Item`/`Set-Content`/`reg` 等 → **仅 write 出入口**（不变）。

**落定后动词表全集**：

| 出入口 | 动词/标记 |
|---|---|
| 写意图总表 | delete 全集 ∪ 纯写全集（两出入口共用的前置判据） |
| delete 出入口 | `Remove-Item` `Remove-ItemProperty` `del` `erase` `rd` `rmdir` `ri` `rm` + `Move-Item`/`mi`/`mv` 的**源参数** |
| write 出入口 | `Copy-Item` `cp` `cpi` `New-Item` `ni` `Set-Content` `Add-Content` `ac` `Out-File` `Expand-Archive` `reg` `setx` `regedit` + `Move-Item`/`mi`/`mv` 的**目标参数** + `>` `>>` |

**实施约束**：三组增补必须与拆函数**同一次落地，不得分期**。先拆函数不补判据，
`shell_delete_paths` 只会得到一个名字正确、判据残缺的空壳。时序固定为：
**① 补三组判据 → ② 抽公用内核 → ③ 落两个出入口 → ④ 系统层改调用**，四步一次提交。

**验证要求**：拆分前先补 12 条实测用例为红测（当前 5 条即红），拆分后全绿，再跑全量 `pytest`。
三组增补各需独立断言：① `mv C:\Windows\a.txt E:\tmp\` → 源判 delete（授权后系统目录仍硬拦）、
目标判 write；② `echo x > C:\Windows\a.txt` → write（系统目录硬拦，工作区正常写入不误伤）；
③ `Remove-ItemProperty C:\Windows\a` → delete（不得为 None 放行）。

# 第四章 运行时进程防护（防自杀）：现状、正确流程与实施清单

## 4.1 现状分析（含错误点）

**在防什么**：防自杀——LLM 生成的杀进程命令（`Stop-Process -Force` / `taskkill /F /PID` /
bash `kill`）把自己人干掉。自己人 = 后端自身与父进程（uvicorn reload 父子双进程，
`os.getpid()` + `os.getppid()`）+ shell 常驻池进程（`shell_pool.get_all_pids()`），
三者现拼入 `_protected_pids()`（`tool_safety_checker.py:183-193`）。按名杀
（`Get-Process python | Stop-Process`）另由 `_protected_process_names()`（L162）按 PID 反查名补位。
命中即 blocked“系统保护进程，禁止终止”（L343-344）。

**现行接线（两处，口径不一致）**：

| 链路 | 取 PID 方式 | 评价 |
|---|---|---|
| 执行层 `execute_shell_command.py:1122` | 参数透传 `protected_pids=shell_pool.get_all_pids()` | 最干净，合规 |
| 预检层 `tool_safety_checker.py:192` | 函数内 `from app.tools.fundamental.shell_engine import shell_pool` 再读 | 方向债，8 条越层之一 |

**错误点**：

1. 原 3.5.2 方案新建 `shell_process_guard` 注册表（register/unregister）——有状态，
   进程崩溃残留脏 PID 会误拦正常 kill，比现状差，不采纳（见 3.9）。
2. 预检层直 import 1100 行的 `shell_engine`，只为读一个 PID 集合——杀鸡用牛刀，
   且是安全层→工具层的方向债（3.3.1 第 3 行）。
3. `is_process_kill_protected` 本体是纯函数，位置不动，只需换调用姿势，不需搬家。

## 4.2 合理正确的流程逻辑

PID 现用现取，不存量；判定只收三样东西。

```
执行层（shell_engine，生产者，只负责上报）
  PersistentShell 启动成功 ──→ 池内登记 {pid, shell_type, task_id, 启动时间}
  池进程退出/被回收 ────────→ 池内注销（池自己维护，本来就有 get_all_pids）
                │
                │ 系统层不 import 引擎，改由上游调用方把快照“递”进来
                ▼
安全层（消费者，只读快照，不持有状态）
  build_protected_pids(pool_pids) -> pids     # 自身+父进程 ∪ 池快照，每次现拼，无缓存
  build_protected_names(pids) -> names        # 按 pid 反查进程名，防按名杀
                │                             # （pool_pids=None 退化为仅自身+父进程，并打 warning 留痕）
                │
                ▼
判定（纯函数，可单测，无 IO）
  is_process_kill_protected(command, pids, names)
    ├─ 从命令里抽目标：Stop-Process -Id / taskkill /PID / bash kill pid
    ├─ 按名杀（Get-Process X | Stop-Process）→ 查 names
    └─ 命中任一 → blocked“系统保护进程，禁止终止”；未命中 → 放行
```

三条死规矩：

1. **安全层零状态**：不建 register/unregister 注册表，不存 `set()`。进程生死是引擎的事，
   安全层只在判定那一刻读一次快照——崩溃残留、注销遗漏两类脏数据天然不存在。
2. **引擎零感知**：`shell_engine` 不 import 安全层任何东西，不调 register。它只维护自己
   本来就要维护的池表（`get_all_pids` 已有），快照由上游调用方递入。
3. **快照只在判定瞬间有效**：PID 会被 OS 重用，快照不得缓存、不得跨命令复用。
   `_protected_pids()` 现在就是每次现拼（`tool_safety_checker.py:183-193`），这点现状是对的，
   保留——要改的只是把“直接 import 引擎”换成“上游递快照”，不新建模块、不改判定逻辑。

一句话：**池是唯一的真相源，安全层每次现问、问完即扔，判定函数只认传进来的三样
（命令、pids、names）**。

```python
"""shell 进程防护快照组装 — 安全层无状态纯函数（零 import 工具层）"""
import os
from typing import Optional

from app.logger import logger


def build_protected_pids(pool_pids: Optional[set] = None) -> set:
    """宿主关键进程 PID 集合（后端自身+父进程+传入的 shell 池快照）"""
    pids = {os.getpid(), os.getppid()}  # 原 tool_safety_checker.py:190
    if pool_pids:                       # 原 L191-195 的 try/import 块删除，改由上游递入

    elif pool_pids is None:  # 三堂会审补：None=上游未递入（留痕）；空集=池空闲（常态，不留痕）

    return pids                         # pool_pids=None 退化为仅自身+父进程，不崩


def build_protected_names(pids: set) -> set:
    """受保护进程名集合（由 PID 反查名，防按名杀）—— 原 _protected_process_names 本体"""
    names = set()

        import psutil
    except ImportError:
        return names

            names.add(psutil.Process(pid).name())
```

## 4.6 遗留问题
复刻 `shell_path_check.py:44-63` 现行逻辑，对 12 条命令实测，**5 条不符**：

| 命令 | 期望 | 现行实码 | 后果 |
|---|---|---|---|
| `del` / `rm` / `Remove-Item C:\Windows\a.txt` | delete | delete | OK |
| **`mv` / `Move-Item` / `mi C:\Windows\a.txt E:\tmp\`** | delete | **write** | 移动删源，被判成可授权的写 |
| **`echo x > C:\Windows\a.txt`** | delete | **write** | 重定向覆盖=抹除，被判成可授权的写 |
| **`Remove-ItemProperty C:\Windows\a`** | delete | **None（整条放行）** | 只在删表不在写表，第一道写意图判定即漏 |
| `cp` / `Set-Content` / `reg add` / `dir` | — | — | OK |

**病根**：mode 判据只认显式删除动词，不认结果上是删除的动作。
`_DELETE_CMD_RE`（L414-416）不含 `Move-Item`/`mi`/`mv`，也不含重定向；
`_WRITE_CMD_RE`（L387-391）却含 `Move-Item|mi|mv`；
`Remove-ItemProperty` 只在删表，而 `shell_path_check.py:46` 用 `_WRITE_CMD_RE` 判有无写意图
→ 该命令在第一道就被放行。

**安全影响**：mode=`write` 意味着非系统禁区可申请临时授权。用户一旦授权，
`mv C:\Windows\a.txt E:\tmp\` 即把系统目录文件搬走 —— 与 4.10-1 所修属同一类漏洞，同一处又漏三个动作。

```python
#   原表(L402-406)含两族本设计已剔掉的词, 剔除理由如下(不是抄漏, 是设计决定):
#     ① move 族 Move-Item / mi / mv  —— 归 SHELL_MOVE_RE 单独处理(源删/目标写, 见归属规则①②);
```

#### 5.3.3.3 预处理产物、归属分类与三个出入口完整代码

```python
class ShellText(NamedTuple):
    """一条命令的两种用途文本 — 小欧 2026-10-16（[36] 5.3.3）

    为什么用不可变产物而不是让每个出入口各跑一遍预处理(v1.1 的做法 = 同命令跑三遍):
    预处理是纯函数, 但"跑三次"既冗余又违背本文件自己声明的"公共工序只到预处理一级" ——
    编排层跑一次, 三个判据共用同一份文本, 谁都不许自行重算(KISS-DIRECT)。
    """
    extract_src: str   # 抽取用: 换行归一 + $env: 展开的原文 —— 抽路径要保住含空格完整路径
    intent_src: str    # 判意图用: 换行归一 + 引号内容涂成等长空格
                       # —— 否则 `Select-String -Pattern "del" <路径>` 会因模式里的动词字面量被误判


def prepare_shell_text(command: str) -> ShellText:
    """预处理只跑这一次 — 小欧 2026-10-16（[36] 5.3.3，修正 v1.1「三入口各跑一遍」）

    干什么用  : 通道 B 编排层一次产出，供 shell_has_write_intent / shell_delete_paths /
                shell_write_paths 三个判据共用。
    口径说明  : 抽取用文本先展开 $env: —— 否则 `$env:TEMP\\a.txt` 形态抽不到盘符路径(现网既有语义, 不改);
                判意图用文本把引号涂成**等长空格** —— 保偏移, 防误判且不打乱后续正则位置。
    """
    normalized = (command or "").replace("\r\n", " ").replace("\n", " ")
    return ShellText(shell_resolve_env_fragment(normalized), shell_blank_out_quotes(normalized))


def _dedup_keep_order(paths: List[str]) -> List[str]:
    """去重且保序(同一路径在 move 源与删动词目标中各出现一次, 只判一次) — 小欧 2026-10-16"""
    seen = set()
    out = []
    for p in paths:
        key = (p or "").lower()
        if p and key not in seen:
            seen.add(key)
            out.append(p)
    return out


def shell_has_write_intent(text: ShellText) -> bool:
    """这条 shell 命令会不会改动东西 — 小欧 2026-10-16（[36] 5.3.3）

    干什么用: 通道 B 入口门判据 —— 只读命令整条放行, 不打扰用户(HITL 零打扰)。
    口径    : 宽表命中 或 判意图文本含 ">"(重定向, 与 >> 同权)。
    消费方  : app.safety.shell_path_check.validate_shell（唯一）。
    不做什么: 不判权限、不判危险等级、不抽路径 —— 它只答有/无。
    """
    return bool(SHELL_WRITE_INTENT_RE.search(text.intent_src)) or ">" in text.intent_src


def _verb_flags(intent_src: str) -> Tuple[bool, bool, bool]:
    """判三类动作在这条命令里有没有 —— 只出开关, 不抽路径 — 小欧 2026-10-16（[36] 5.3.3）

    干什么用: 归属分类的**决策层**。把"要不要走哪条线"这件事从"抽什么路径"里彻底拆开,
              三个出口各返回一个布尔量, 谁也不该在别的函数里重新匹配一遍动词。
    返回    : (del_hit, write_hit, move_hit)
              del_hit   —— 有删除动词(删线规则③)
              write_hit —— 有纯写动词或重定向 >/>>(写线规则④)
              move_hit  —— 有移动动词(删线①/写线②共用一个开关)
    """
    return (bool(SHELL_DELETE_RE.search(intent_src)),
            bool(SHELL_WRITE_RE.search(intent_src)) or ">" in intent_src,
            bool(SHELL_MOVE_RE.search(intent_src)))


def _collect_targets(extract_src: str, del_hit: bool, write_hit: bool, move_hit: bool
                     ) -> Tuple[List[str], List[str]]:
    """把候选路径抽出来 —— 只做抽取工序, 不做归属决策 — 小欧 2026-10-16（[36] 5.3.3）

    干什么用: 归属分类的**工序层**。绝对路径**只抽一次**(DRY: 同一条命令不得重复扫同一批原语),
              移动源/目标走有序切词(必须保位置序, 与无序抽取不能混用)。
    返回    : (move_src, move_dst) —— 仅 move_hit 时非空; 绝对路径由调用方直接取本函数外的
              一次抽取结果(见 _shell_path_lines)。
    """
    if move_hit:
        return _extract_shell_move_paths(extract_src)
    return [], []


def _assign_to_lines(delete_line: List[str], write_line: List[str]
                     ) -> Tuple[List[str], List[str]]:
    """交集取严: 同一条路径既被删线提又被写线提, 只归删线 — 小欧 2026-10-16（[36] 5.3.3）

    干什么用: 归属分类的**策略层**(规则⑤)。缺这一步会导致同一路径在两线各判一次,
              failed_path/category 取决于代码顺序 = 行为不确定(2026-10-16 老陈退回时补)。
    保序    : 一律用列表推导过滤, 不用 sorted —— sorted 会打乱"命令里出现的先后",
              而失败路径是要报给用户的, 顺序必须可预期。
    """
    both = {p.lower() for p in delete_line} & {p.lower() for p in write_line}
    if not both:
        return delete_line, write_line
    return ([p for p in delete_line if p.lower() in both] + [p for p in delete_line if p.lower() not in both],
            [p for p in write_line if p.lower() not in both])


def _shell_path_lines(text: ShellText) -> Tuple[List[str], List[str]]:
    """写删目标归属分类 —— 编排层, 返回 (删线路径, 写线路径) — 小欧 2026-10-16（[36] 5.3.3）

    归属规则五条, 顺序即优先级:
      ① 移动动词的【源参数】→ 删线(从原位抹掉, 与 del 同级)
      ② 移动动词的【目标参数】→ 写线(可任务级授权)
      ③ 删除动词命令里的绝对路径 → 删线
      ④ 纯写动词命令里、或重定向 > / >> 的绝对路径 → 写线
      ⑤ **交集取严**: 同一条路径既被删动词提又被写动词提 → 只归删线, 从写线剔除。
         ★一条路径只归一条线, 任何情况下不重复判定。

    本函数**只编排, 不含逻辑**(SLAP/KISS-DIRECT, 2026-10-16 三堂会审订正):
      决策 → _verb_flags   工序 → _collect_targets + 一次 shell_extract_abs_win_paths   策略 → _assign_to_lines
    """
    del_hit, write_hit, move_hit = _verb_flags(text.intent_src)
    if not (del_hit or write_hit or move_hit):
        return [], []                                   # 纯读命令: 两口皆空, 不做无用抽取
    abs_paths = shell_extract_abs_win_paths(text.extract_src) \
        if (del_hit or write_hit) else []                # ★只抽这一次, 两线按开关取用(DRY)
    move_src, move_dst = _collect_targets(text.extract_src, del_hit, write_hit, move_hit)
    delete_line = _dedup_keep_order(move_src + abs_paths) if del_hit else []
    write_line = _dedup_keep_order(move_dst + abs_paths) if write_hit else []
    return _assign_to_lines(delete_line, write_line)


def shell_delete_paths(text: ShellText) -> List[str]:
    """看这条命令会**从原位抹掉**哪些路径 — 小欧 2026-10-16（[36] 5.3.3）

    干什么用: 删线出入口 —— 返回的路径逐个交 delete_path_check.validate_delete,
              命中 system/non_system 均 blocked, **永不授权**(删系统目录没有"授权后放行"这条路)。
    入参    : prepare_shell_text 的产物(预处理只跑一次, 三个判据共用, 见 5.3.3.1)。
    认哪些  : 归属规则①③⑤ —— 删除动词(Remove-Item/Remove-ItemProperty/del/erase/rd/rmdir/ri/rm)
              命令里的绝对路径 + 移动动词(Move-Item/Rename-Item/move/ren/mi/mv)的源参数。
    不认    : 重定向 > 与 >> (目标恒为文件, 恒为写; 见 5.3.3.2 注释③); 纯写动词目标。
    契约    : 返回去重保序的盘符绝对路径; 相对路径 / UNC / ~ / 未展开的 $env: 形态**一律不抽**
              (交沙箱预检 SHELL_OUTSIDE_TARGET_RE 覆盖, 见 3.6 已裁定项)。
              本函数**不判权限、不判白名单** —— 它只认文本, 结论由 path_guard.classify_forbidden_path 出。
    """
    return _shell_path_lines(text)[0]


def shell_write_paths(text: ShellText) -> List[str]:
    """看这条命令会**写入**哪些路径 — 小欧 2026-10-16（[36] 5.3.3）

    干什么用: 写线出入口 —— 返回的路径逐个交 write_path_check.validate_write,
              system 硬拦 / non_system 可任务级授权 / 白名单外需确认。
    入参    : prepare_shell_text 的产物(同上)。
    认哪些  : 归属规则②④⑤ —— 移动动词的目标参数 + 纯写动词(Copy-Item/cp/cpi/New-Item/ni/
              Set-Content/Add-Content/ac/Out-File/Expand-Archive/reg/setx/regedit)命令里的绝对路径
              + 重定向 > 与 >> 的目标。
    不认    : 删除动词目标与移动动词源参数(归 shell_delete_paths)。
    契约    : 同 shell_delete_paths —— 去重保序、只抽盘符绝对路径、不判权限。
    """
    return _shell_path_lines(text)[1]
```

> **关于「mv 与 del 混用」的口径变更**（北京老陈 2026-10-16 11:57 明确批准分线，v1.1 自作主张已纠正）：
> 原实码把整条命令当纯删除处理，故 move 的**目标**也按删线判（硬拦永不授权）——「更严但语义错」
> （目标路径是被写入而非抹除）。现按语义分线：源走删线、目标走写线。
> **安全性论证**：① 源仍走删线（真正的风险点，一个不漏）；② 目标走写线后，**system 区照样硬拦**
> （`write_path_check.validate_write` 对 system 返回 blocked，永不授权）；③ non_system 区走可授权分支，
> 而「允许把文件写进 non_system 受保护根」的语义与文件工具 `move_file` 既有口径**同源**，非新增能力。
> **配套用例**：① `mv <non_system 受保护根> <non_system 受保护根>` 仍被**源侧**删线拦住；
> ② `mv <普通盘符> <受保护根>` 走写线可授权；③ 用例 5/6/13 锁定。
>
> **★ 落码时发现的第 7 处设计缺陷（小欧 2026-10-16 16:5x，三堂会审漏项）**：
> 冒烟测试 15 例中 5 例失败，根因是 **`abs_paths` 不带「属于哪个动词」的信息**——
> `shell_extract_abs_win_paths` 是「整条命令一次抽完」，返回值只是一批路径，无法按动词分线。
> 而 v1 的「各抽一次再分线」方案已因 **D2**（`verb_re` 形参无法独立指定 + 两表正交性与交集处理在此自相矛盾）
> 被裁定删除。于是混合命令（删写动词同现）按 v2.2 设计无法正确分线。
> **处置：取严，不引新抽象**（KISS-DIRECT / YAGNI）——
> 删写动词**同时命中**时 `abs_paths` 一律归删线，写线只收 move 目标。
> 理由三条：① 误把写路径归删线 = 更严（安全方向）；反向则是**放宽**（危险方向）；
> ② 与实码现状（混合命令整条走删线）**行为一致 = 零退化**，不需另立等价性论证；
> ③ 只有单一动词时 `abs_paths` 必然属于它，按规则③④正常分线，此问题不存在。
> **副作用（已知且接受）**：`Copy-Item C:\a C:\b` 单独出现时 `C:\b` 仍归写线（正确）；
> 但 `Copy-Item C:\a C:\b; Remove-Item C:\a` 里 `C:\b` 也归删线（偏严）。
> 要做到「`C:\b` 精确归写线」必须按动词切目标窗口（引入 `_paths_in_verb_windows`），
> 属**新增能力而非修 bug**，且会改变现网行为 → 按 YAGNI 本批**不做**，登记为后续可选优化。
> **实码落点**：`_shell_path_lines`（`app/safety/shell_command_process.py`），三分支直写，无中间变量。

## 6.2 Batch-D：shell 判定重复跑的收敛（D-1 性能 / D-2 安全口径）

### 6.2.1 它是什么

**一次 `bash` 工具调用，shell 命令会被判定 5 次**（逐条账见 **3.3.2 总账表**）：

| 类别 | 遍数 | 是否重复 |
|---|---|---|
| 危险度分级 | 3 遍（预检 2 + 工具内 1） | **预检那 2 遍是同一函数同参数跑两次 → 可合并** |
| 杀进程防护 | 2 遍（预检 1 + 工具内 1） | ❌ **不是重复**：预检版含 PID + 按名杀 + 无目标兜底，工具内版仅 PID，属**覆盖面不同的分层复核** |

Batch-D 想把这两件事分开处理：**D-1 只合并真正重复的，D-2 是另一回事、性质完全不同**。

### 6.2.2 D-1：合并预检内的重复判定（可做，判定结果不变）

**现状**：`_check_known_risks`（L352）扫一遍取 `blocked`；`_get_needs_confirmation`（L308）又用
`check_shell_command_risk_all_shells(_cmd)` 扫一遍取 MEDIUM 文案。**同一函数、同一参数**。

**改法**：在 `check_before_execute` 里**算一次**，存局部变量，当参数递给两个被调函数。

**四条实施纪律**（防止重蹈 Bug-2「隐藏状态覆辙」）：

| # | 纪律 | 原因 |
|---|---|---|
| 1 | 两个函数都是 `@staticmethod`，互相拿不到对方的局部变量 → **必须在 `check_before_execute` 里算一次** | 否则只能退化成实例属性或全局变量 = 隐藏状态 |
| 2 | `_get_needs_confirmation` 有 **3 个调用点**（bypass 分支 / 会话信任分支 / 主分支），**三处都要传** | 漏一处 = 那条路径仍重复跑（属优化不彻底，不是错） |
| 3 | **bypass 分支可能在 `_check_known_risks` 之前就早退** → 早退路径上传 `None`，此时 `_get_needs_confirmation` 需**明确回退到自行扫一遍** | 宁可慢一次，也不能拿到脏值 |
| 4 | **严禁**存实例属性 / 全局 / 模块级缓存 | 那正是 Bug-2 的形态（全局单例残留误拦） |

**验收**：① 4 条定向（HIGH→blocked / MEDIUM→弹窗 / 无风险→直放 / 杀防护→blocked）全绿；
② 用 monkeypatch 计数断言 `check_shell_command_risk_all_shells` 在**无风险命令**上**只被调 1 次**
（改造前是 2 次）—— 这条断言是 D-1 的**核心验收**，必须写死。

### 6.2.3 D-2：改用真实 `shell_type`（⚠️ 收窄拦截，须老陈单独批准）

**现状**：预检用 `check_shell_command_risk_all_shells` —— 对 ps7/cmd/bash **各判一次取最严** = **并集**。
**提议**：改成按 `params` 里真实的 `shell_type` 只判一次。

**为什么这必须单独批准**：

| 项 | 说明 |
|---|---|
| 拦截范围 | **必然收窄** —— 并集是"任一壳命中就拦"，单壳是"只判那一个" |
| 具体后果 | bash 专属 HIGH 规则（`dd` / `mkfs` / `chmod 777`，见 `tool_safety_checker.py:84` 注释）在 `shell_type=ps7` 的会话里**从"拦"变成"不拦"** |
| 逻辑上说得通吗 | 说得通 —— 实际执行的就是 ps7，不该按 bash 规则拦 |
| 但性质是 | **安全口径的放宽**。放宽必须显式批准，**绝不能当"顺手优化"混进任何提交** |
| 另一个代价 | 原注释实测「并集：召回 15 条 / 白名单误伤 0/30 / 日常误伤 0/24」（L302-306）。改成单壳后这套实测基线**需重测**，否则等于没有回归依据 |

**若老陈批准，改动面**：`all_shells` 两处调用（L308 / L352）→ 改调 `check_shell_command_risk(_cmd, shell_type)`；
并**重跑**上述四组实测（召回 / 白名单误伤 / 日常误伤 / 降级回归）留档。
**若不批准**：Batch-D 只做 D-1 与 D-3，本节留档即销。

### 6.2.4 D-3：宽表补 `Rename-Item` / `ren`，堵沙箱 F-B 扫描的缺口（✅ 属收紧，不需批准）

**这是什么缺口**（2026-10-16 实码核验发现，见 3.3.3 偏离说明 ③）：

| 词 | 沙箱 F-B 越界写扫描（宽表 `SHELL_WRITE_INTENT_RE`） | 通道 B 权限判定（`SHELL_MOVE_RE`） |
|---|---|---|
| `Move-Item` / `mi` / `mv` | ✅ 有 | ✅ 有 |
| **`Rename-Item` / `ren`** | ❌ **无**（实码 `_WRITE_CMD_RE` 不含） | ✅ 有 |

**成因**：2026-10-16 三堂会审把 `rename/ren/Rename-Item` 补进了 `_MOVE_CMD_RE`（因为它们与 `mv` 同为"删源+写目标"），
**但没同步补进宽表**——宽表是沙箱 F-B 扫描唯一的词表。

**后果**：`ren C:\Windows\x.txt y.txt` 在**权限判定层能被正确拦**（走 move 表，源走删线硬拦），
但**沙箱预检的越界写扫描扫不到它** → **少一道独立复核**。属**实码既有缺口，非本设计引入**
（本设计的宽表基线与实码逐字符一致，等于原样保留）。

**D-3 的动作**：宽表补 `Rename-Item` 与 `ren`，与 `SHELL_MOVE_RE` 对齐。

**为什么不需要老陈单独批准**（与 D-2 恰好相反）：

| 对比 | D-2 | **D-3** |
|---|---|---|
| 方向 | 拦截**收窄**（放宽） | 拦截**扩大**（收紧） |
| 性质 | ⚠️ 安全口径放宽 → **须批准** | ✅ **补一道本该有的复核**，更严不改松 |
| 风险 | 放过原本该拦的 | **误伤**：短词 `ren` 是否会误命中别的命令（见下） |

**因此 D-3 的真正门槛不是"批不批"，而是"误伤实测"**：

| 前置 | 要求 |
|---|---|
| 误伤实测 | 沿用第四章既有基线口径：**白名单 30 条误伤 = 0**、**日常命令 24 条误伤 = 0**（见 `tool_safety_checker.py:302-306` 注释的实测法） |
| 召回实测 | 至少 `ren C:\Windows\x.txt y.txt`、`Rename-Item C:\Windows\x y` 两条**必须被扫到** |
| 边界确认 | 宽表用 `\b...\b` 前后向断言，`ren` 不会命中 `render` / `parent` 之类子串（落码前须逐条核） |
| 联动 | 补表后 **5.3.7.3 的 `BASELINE_WRITE_INTENT` 必须同步更新**（该基线的作用就是钉死词面，防漂移） |

### 6.4.1 四级的职责边界（2026-10-16 补）

| 级 | 只回答 | 归属模块 | 与路径的关系 |
|---|---|---|---|
| ① 自杀 | 要不要杀自己人 | `shell_process_guard` | 无关 |

用户连确认机会都没有。

## 7.1 老陈口述的四层规则（本章主纲）

```
一条 shell 命令进来，解析只回答四个问题：

① 进程    这条命令要不要杀进程？        → 是则不可隔离，绝不进沙箱预检真跑
② 危险    哪些命令危险？                → 直接返回拒绝（不含 path 的命令）
③ 中等    哪些命令属中等？              → 返回 need_confirm（含 path 的命令）
④ 含 path 剥出「路径」与「动作」两部分   → 按动作分别交 write / delete / read 权限判定函数
```

**关键澄清（此前一直混淆，现按老陈口径统一）**：

| 层 | 产出 | 归属模块 | 是否含常量 |
|---|---|---|---|
| ① 杀进程 | 布尔（要不要杀） | `shell_command_process` | 12 个 |
| ② 危险命令 | `SafetyResult(blocked)` | `shell_command_risk` | 43 条模式表 |
| ③ 中等→需确认 | `SafetyResult(requires_confirmation)` | `tool_safety_checker` | 0 |
| ④ 路径+动作 | 路径清单 + 动作类别 | `shell_command_process` → `shell_path_check` 编排 | 10 个 |

**解析命令本身只需要第 ④ 层的能力（路径解析 + 动作解析）与基础文本处理**，
第 ② ③ 层是判定层，不属于"解析"。此前把四层混在一个模块里讲，是本人表述失当。

## 7.2 32 个常量的用途归类（按用途，不按出现顺序）

### 7.2.1 第 ① 层：杀进程（12 个）

| 常量 | 处理什么情况 |
|---|---|
| `SHELL_HIDDEN_KILL_VERBS` | 动词词表：`stop-service`/`restart-service`/`pkill`/`killall`/`kill` 等 |
| `_PROCESS_KILL_VERBS` | **同上的真子集（重复 3 词）→ 待删** |
| `_PROCESS_KILL_VERB_RE` | 上表编译为正则 |
| `_UNCONTAINABLE_RE` | WMI/CIM 绕路杀：`Get-WmiObject` + `.Terminate()` |
| `_METHOD_KILL_RE` | `.Kill()` / `.Terminate()` 方法调用形态 |
| `_CIM_KILL_RE` | `Invoke-CimMethod` 形态 |
| `_ENCODED_RE` | 藏起来的杀进程命令（`[char]0x64` 拼出的 `del`） |
| `_PIPE_KILL_RE` | 管道杀：`(Get-Process) \| kill -9` |
| `_HELPISH_RE` | 排除 `kill -help` 这类假杀 |
| `_PID_TARGET_RES` | 从 `-PID 888` / `/PID 888` 抠出进程号 |
| `_NAME_TOKEN` / `_KILL_NAME_RES` | 从 `-name python` / `/im x.exe` 抠进程名 |

### 7.2.2 第 ④ 层：路径 + 动作解析（10 个）

| 常量 | 处理什么情况 |
|---|---|
| `SHELL_WRITE_INTENT_RE` | **宽表**：这条命令改不改动东西？（通道 B 与沙箱 F-B 两个消费方共用） |
| `SHELL_DELETE_RE` | 哪几个词算删除（`Remove-Item`/`del`/`rm`/`rd`/`rmdir`/`ri`/`erase`/`rmdir`） |
| `SHELL_MOVE_RE` | 哪几个词算移动（`Move-Item`/`Rename-Item`/`move`/`ren`/`mi`/`mv`） |
| `_SHELL_WRITE_VERBS` / `SHELL_WRITE_RE` | 哪几个词算写入（13 词：`cp`/`Set-Content`/`New-Item` 等） |
| `_MOVE_DEST_SWITCHES` | `-Destination`/`-dest`/`-newname` 之后的路径是**目标**不是源 |
| `_MOVE_TOKEN_RE` | 按位置切词（源/目标分界靠它） |
| `_ABS_PATH_HEAD_RE` | 判断 token 是否为盘符绝对路径 |
| `_SHELL_ABS_WIN_PATH_RES` | 抽取绝对路径的正则组（3 条：引号内 2 + 裸路径 1） |

### 7.2.3 沙箱越界预检（4 个）——**只有 `executor.py` 用**

| 常量 | 处理什么情况 |
|---|---|
| `SHELL_OUTSIDE_TARGET_RE` | 什么形态算越界（盘符 / UNC / `$env:` / `~` / 注册表驱动器） |
| `SHELL_REDIRECT_RE` | `>` 与 `>>` 后面那个目标是谁 |
| `SHELL_SANDBOX_SELF_RE` | 识别"要删的是沙箱自己"（N7 carve-out） |
| `SHELL_REGISTRY_SYSTEM_VERBS` | 注册表类动词（Job Object 拦不住注册表，须静态拦） |

### 7.2.4 文本基础处理（5 个）+ 只读白名单（2 个）

| 常量 | 用途 |
|---|---|
| `_CONCAT_PART` / `_CONCAT_RE` | 拼接折叠（`a''b` → `ab`） |
| `_CHAR_RE` | `[char]0x64` 形式的字符解码 |

## 7.3 四层的消费关系（谁调谁）

```
              execute_shell_command（工具层·真正执行）
                          │
        ┌─────────────────┼──────────────────┐
        ▼                 ▼                  ▼
   ① 杀进程         ② 危险命令            ③ 中等命令
 executor.F-B      shell_command_risk   tool_safety_checker
 (shell_has_       .check_shell_command  (定级/分流)
  hidden_kill)      _risk_all_shells
        │                 │                  │
        └────────┬────────┴──────────────────┘
                 ▼
        ④ 路径 + 动作解析（唯一"解析"层）
     shell_command_process.shell_write_and_delete_paths
                 │ 返回 (删线清单, 写线清单)
                 ▼
        shell_path_check（只编排，不判不取）
                 │
        ┌────────┴────────┐
        ▼                 ▼
 delete_path_check   write_path_check
   .validate_delete   .validate_write      ← 权限判定在这一层
```

**边界铁律**：`shell_command_process` **只取路径与识别动作，不判权限**；
权限判定永远在 `delete_path_check` / `write_path_check` / `read_path_check`；
两者分层不得合并（老陈 2026-10-16 明确要求"shell path-权限的函数要分开"）。

### 7.4.2 需先答问题才能动（老陈 2026-10-16 未拍板）

| 项 | 问题 |
|---|---|
| 宽表与细表能否合一张 | `SHELL_WRITE_INTENT_RE` 词序（`rm,ri,del,erase,rd,rmdir`）与 `SHELL_DELETE_RE`（`del,erase,rd,rmdir,ri,rm`）**不同**，边界符也不同（`\b` vs `(?<![a-z0-9_-])`）。**合表 = 改正则字符 = 可能改拦截行为**。是否接受？ |
| 动词表边界是否统一 | 统一为一种边界会改变哪些词能命中，属行为变更 |
| `mv` 目标归属缺陷（5.3.10.1 #1） | 修它须按动词切目标窗口，属**新增能力**，老陈已令暂不修 |

### 7.4.3 本章不承担的（分层理由已说明，不再混入"解析"）

- ② 危险命令（43 条表）：属**危险等级判定**，与解析无关
- ③ 中等命令：属**确认策略**，与解析无关
- 权限判定（`delete/write/read_path_check`）：属**权限裁决**，与解析无关

> 此前"常量太多"里有相当一部分是因为把 ①②③ 的判定职责也算进了"解析命令"，导致职责边界模糊。
> 按本章四层归口后，`shell_command_process` 应只保留 **① + ④ + 基础文本处理** 三类，
> 即 12 + 10 + 5 = **27 个**（再减去待删的重复项 1 个 → **26 个**），
> 沙箱越界 4 个与只读白名单 2 个因服务独立消费方（`executor` / 沙箱直通），单列成块并注明专属消费方。
