## 一、目标与约束

### 1.1 两个目标（对应北京老陈本次指令）

| 目标 | 判定标准（可量化） |
|---|---|
| **KISS** | 「引用一个文件」这件事，全仓只有 **1 处实现**；路径判定只有 **1 份**；深链拼装只有 **1 处**；域之间**无反向依赖** |
| **后续加功能可靠** | 新增一个引用入口（如文档[42] 的 O3 产出物可点、O6 上下文包）只需 **调用 1 个函数**，不需复制读盘/push/错误处理三件套；新增一个路径展示只需 **1 个组件** |

### 1.2 硬约束（本次重构不可违背）

| # | 约束 | 依据 |
|---|---|---|
| C1 | **不新增后端端点、不改后端契约** | 文档[42] §4.3 已定：本轮纯前端 |
| C2 | **迁移即删除**：文件搬家必须删旧文件 + 改全部 import，**不留 re-export 兼容层** | AGENTS「禁止 backward」 |
| C3 | **行为零退化**：本轮只改结构，不改用户可见语义（引用行为、文案、交互顺序全部逐字保持） | AGENTS §1.6 复查纪律「功能只能正确/增强/优化，杜绝退化」 |
| C4 | **不加抽象层**：不引入注册表/工厂/泛型容器；每新增一个文件都要能一句话说清它只做一件事 | AGENTS KISS-DIRECT / YAGNI |
| C5 | **纯函数优先**：能抽成纯函数的一律纯函数（可直接单测，不依赖 React/网络） | 可靠性基础 |
| C6 | **注释带署名+日期**，只写技术信息，不写文档号/章节号/bug 序号 | AGENTS §1.1 |

### 1.3 分层约定（本次确立，写入 `AGENTS.md` 的前端约定节）

```
src/components/     跨域共享展示件（无业务状态）   例：fileIcon / FilePathLink
src/utils/          跨域纯函数（无 React 副作用）   例：projectPath / fileDeepLink / format / clipboard
src/hooks/          跨域通用 hook（与具体 feature 无关）例：useProjectRoot / useRecentFiles / useOptionalNavigate
src/services/api/   后端接口层（类型 + 请求）
src/features/<f>/   域内组件与状态（域之间**禁止**直接 import）
src/features/refs/  【本次新增】跨域共享能力：引用（refs）的唯一真源
```

**依赖方向（单向，无环）**：

```
pages/*  →  features/*  →  components/ | utils/ | hooks/ | services/api/
                          ↘  features/refs（共享域，chat 与 files 都依赖它）
```

**硬规则**：`features/chat` 与 `features/files` **互不 import**；跨域只经 `components/` / `utils/` / `hooks/` / `features/refs/`。

## 二、架构审计（实码取证）

> 全部结论来自实读本地代码，标注 `文件:行号` 可复核。

### 2.1 引用生命周期：当前横跨 5 个文件、**3 份近似实现**

| 环节 | 现状实现 | 实码证据 |
|---|---|---|
| ① 引用（读盘 + 入队） | **3 处各自实现**：`fileApi.readFile` → 手工组装 `{id,kind,label,path,content,size,lineRange}` → `composerRefStore.push` → 各自的成功/失败提示 | `FileTrailPanel.tsx:110-126`、`TaskListPanel.tsx:184-203`、`pages/Files/index.tsx:534-557` |
| ② 消费（输入框订阅） | `ChatInput` **内联** `useSyncExternalStore` + `takeAll()` + `mergeRefs()` + 组件内 `useState` 托管 | `ChatInput.tsx:121-142` |
| ③ 发送前校验 | `ChatInput` **内联 46 行**：逐条重读 + 行号切片 + `invalid` 标记 + 阻断发送 | `ChatInput.tsx:271-322` |
| ④ 上行 | `buildStreamBody` 组 refs | `chatStreamTransport.ts:214-266` |
| ⑤ 台账 | `setServerTaskId` → `pushSentRefs` | `chatStreamStore.ts:1106-1117 / 809-824` |

**三个致命后果**：

1. **复制粘贴即分叉**：文档[42] 的 O3（产出物可点）、O6（上下文包）若照现有写法做，仓库里会出现**第 4、5 份**「read + push + 错误提示」；将来加"发送前校验"也要改 3~5 处。
2. **正文读两遍**：引用时读一次存 `content`（①），发送前再逐条 `readFile` 重读（③）。大文件双倍 IO，且两份逻辑对"行号切片""失效判定"的口径可能漂移。
3. **状态两份**：`ChatInput` 组件内 `refs` state（待发）vs store 台账（已发）—— 两个世界，跨面板读不到"用户现在待发了什么"。

### 2.2 文档[28] 声称的共享 hook **不存在**

文档[28] v5.15/v5.17 多次声称已建 `features/chat/hooks/useComposerRefs.ts`（"S1 地基 12 件"含它、"9 个文件全部到位"含它）。**实码：全仓只有 `features/chat/streams/composerRefStore.ts`，`useComposerRefs.ts` 不存在**（`Get-ChildItem -Recurse *ComposerRefs*` 零命中）。

> 结论：文档[28] §10.10.4「S1 地基 12 件 ✅」是**虚报**（或该 hook 已并入 ChatInput 但未回写文档）。这正是"文档说做了、实码没做"的典型样本 —— 本次重构必须把这类偏差清干净。

### 2.3 路径判据 **两份**

| 位置 | 内容 |
|---|---|
| `utils/projectPath.ts:36-66` `toRelativePath` | 唯一真源：拒 URL / 控制字符 / `..`，绝对路径按 projectRoot 归一，分隔符边界校验 |
| `TaskListPanel.tsx:63-78` `normalizeRelPath` | **自抄一份**：大小写不敏感前缀 + 兄弟目录边界 + 拒绝对路径 |

两者语义基本等价，但**分叉风险已存在**（新增判据必漏一处）。文档[42] §5.4 新增 `✎` 标记还要再判路径 —— 若不先收口，会出现第 3 份。

### 2.4 跨域反向依赖

`pages/Files/index.tsx:53` → `import { composerRefStore, newRefId } from '@/features/chat/streams/composerRefStore'`

即：**文件页依赖会话域的私有 internals**（`streams/` 是 chat 的内部目录）。叠加文档[42] 的 O5（工作目录反链）与 O2（引用历史面板），这条反向依赖会变成**双向依赖**（chat → files 深链，files → chat 台账），形成环 —— 违反分层，是后续加功能最容易出环的地方。

### 2.5 页面组件过胖

`pages/Files/index.tsx` **920 行**，持有 **18 个 useState + 20 个 useCallback**：

| 类别 | 成员 |
|---|---|
| 树状态机 | `tree / treeStatus / loadedKeys / expandedKeys / scanNotices` + `beginTreeReq / claimDir / loadTree / loadDir / patchNodes` |
| 深链 | `linkErr` + `expandToPath / openPath` |
| 选中与多选 | `selected / multiFiles / lineRange / narrowTab` |
| 引用收集 | `collectedKeys` + `pushRef / goChat / clearCollected / refSelectedFiles`（**与 store 重复记账**） |
| 其他 | `projectRoot / rootErr / leftW / value / err` |

再加 O3/O4/O5/O6 只会继续膨胀（预计破 1200 行），且每次改动都要在同一个文件里"找得到那一段"。

### 2.6 文件域缺"域层"

`features/files/` 只有 3 个组件（`FilesTree` / `FilePreview` / `highlight`），**没有域内的取数层与状态层**；取数在全局 `services/api/file.api.ts`，状态散在页面与 `src/hooks/`。结果是"文件相关的东西"横跨三层目录，无明确归属：

```
services/api/file.api.ts        取数
hooks/useRecentFiles.ts         状态（文件域的，却放在全局 hooks）
hooks/useProjectRoot.ts         状态（同上）
features/files/components/*      组件
pages/Files/index.tsx           容器（920 行）
```

### 2.7 审计结论：10 项架构债

| # | 架构债 | 违反 | 严重度 |
|---|---|---|---|
| A1 | 「引用一个文件」3 份实现 | DRY | **高** |
| A2 | 共享 hook 不存在（文档虚报） | SRP / 文档纪律 | **高** |
| A3 | 正文读两遍（引用时 + 发送前） | DRY / 性能 | 中 |
| A4 | 路径判据两份 | DRY | 中 |
| A5 | 跨域反向依赖（files → chat internals） | 分层 | 中 |
| A6 | 页面 920 行 / 18 state | SRP / SLAP | 中 |
| A7 | 引用收集状态两份（页面 state + store） | DRY / 双真源 | 中 |
| A8 | 文件域无域层（取数/状态/组件散三层） | 分层 | 中 |
| A9 | 校验逻辑内联在组件（不可单测） | C5 纯函数优先 | 中 |
| A10 | 无分层守卫（架构退化无告警） | 可靠性 | 低 |
| — | ~~共享层依赖域（`utils/viewState.ts` → `features/chat/hooks/useTaskInfo`）~~ | **v1.3 自审复核：非违规** —— 该引用是 `import type { TaskBadge }`（类型导入，编译期即擦除，无运行期依赖）→ 守卫误报，已收紧规则（G1b 豁免类型导入） | 已消解 |

### 3.3 为什么"共享域 `features/refs/`"而不是放进 chat 或 files

| 方案 | 评价 |
|---|---|
| 放 `features/chat/` | 文件页要 import 会话域 internals → **现状的病根**，不解决 A5 |
| 放 `features/files/` | 会话页要 import 文件域 → 变成反向病根（chat → files），且"引用"概念不专属文件（未来 message/log 引用也走它） |

> **YAGNI 自检**：这不是"提前抽象"——**已经有 4 个生产方 + 1 个消费方**在用同一套概念，符合 YAGNI 的"已有多个使用点才上提"门槛。

```diff
+  /** 有条目正在载入（发送闸门据此阻断） */
+  pending: boolean;

+  /** 按谓词移除（@ 补全失败时按 path 删占位，无 id 可用） */
+  removeWhere: (pred: (r: ComposerRef) => boolean) => void;

+  clear: () => void;
+  /** 直接并入一条（@ 补全插 pending 占位，不经 store） */
+  add: (ref: ComposerRef) => void;
+  /** 整体替换（refreshRefs 回写校验结果） */
+  setAll: (refs: ComposerRef[]) => void;
+}

+export const useComposerRefs = (): UseComposerRefsResult => {
+  const [refs, setRefs] = useState<ComposerRef[]>([]);
+  const count = useSyncExternalStore(
+    composerRefStore.subscribe,
+    composerRefStore.getSnapshot,
+    composerRefStore.getSnapshot
+  );
+
+  useEffect(() => {
+    if (count === 0) return;
+    const incoming = composerRefStore.takeAll();
+    if (incoming.length === 0) return;
+    setRefs((prev) => mergeRefs(prev, incoming));
+  }, [count]);
+
+  const remove = useCallback((id: string) => {
+    setRefs((prev) => prev.filter((x) => x.id !== id));
+  }, []);
+
+  const removeWhere = useCallback((pred: (r: ComposerRef) => boolean) => {
+    setRefs((prev) => prev.filter((r) => !pred(r)));
+  }, []);
+
+  const clear = useCallback(() => setRefs([]), []);
+
+  const add = useCallback((ref: ComposerRef) => {
+    setRefs((prev) => mergeRefs(prev, [ref]));
+  }, []);
+
+  const setAll = useCallback((next: ComposerRef[]) => setRefs(next), []);
+
+  return {
+    refs,
+    pending: refs.some((r) => r.pending),
+    invalid: refs.some((r) => r.invalid),
+    remove,
+    removeWhere,
+    clear,
+    add,
+    setAll,
+  };
+};
```

```diff
+export interface QuoteResult {

+  /** 失败原因（ok=false 时给出，可直接展示） */

+  opts?: { label?: string; content?: string; size?: number }
+): Promise<QuoteResult> => {

+  path: string,
+  range: { start: number; end: number },
+  opts?: { label?: string; content?: string; size?: number }
+): Promise<QuoteResult> => {
+  const label = opts?.label ?? (path.split('/').pop() ?? path);

+    const content = opts?.content ?? (await fileApi.readFile(path)).content;

+      id: newRefId(),
+      kind: 'selection',
+      label,
+      path,
+      content,

+  } catch {

+  }
+};

+ * ⚠ 包内无 path → 后端 sanitize_refs 放行（"无 path 的条目不校验"），
+ *   _render_refs_block 以 label 作锚 —— 不需要任何后端改动。
+ */
+export const quotePack = async (
+  files: { path: string; label?: string }[],
+  opts?: { max?: number }
+): Promise<QuoteResult> => {
+  const max = opts?.max ?? 10;
+  if (files.length === 0) return { ok: false, reason: 'empty' };
+  if (files.length > max) {
+    return { ok: false, reason: 'too_many' };
+  }
+  const parts: string[] = [
+    `【文件清单】\n${files.map((f) => f.path).join('\n')}`,
+  ];
+  for (const f of files) {
+    try {
+      const r = await fileApi.readFile(f.path);
+      parts.push(`【文件】${f.path}\n${r.content}`);
+    } catch {
+      parts.push(`【文件】${f.path}\n（读取失败，已跳过）`);

+    label: `${files.length} 个文件`,
+    path: '',   // 包无单一路径：点击不跳深链（文档[42] §5.7）
+    content,
+    size: content.length,
+    lineRange: null,
+  });
+  return { ok: true };
+};
```

```diff
+// 编辑历史: 2026-10-22 小欧 - 新建：发送前引用校验与保鲜（唯一实现）— 小欧-2026-10-22
+/**
+ * refreshRefs —— 发送前对每条引用**重读一遍**
+ *
+ * 为什么重读（语义不变，只搬家）：① 文件被删/不可读 → 标 invalid、阻断发送并点名
+ *   （不让模型收到失效内容）；② 读成功的把 content 换成最新（内容保鲜）；

+ * 为什么抽函数：原实现内联在 ChatInput 里 46 行，不可单测；
+ *   抽成纯函数后，失效判定与切片口径有单测兜底（可靠性目标）。

+import { fileApi } from '@/services/api/file.api';
+import type { ComposerRef } from './store';
+
+/** 按行区间切片（1-based 闭区间）；越界 → null（判失效） */
+export const sliceByLineRange = (
+  content: string,
+  range: { start: number; end: number }
+): string | null => {
+  const lines = content.replace(/\r\n/g, '\n').split('\n');
+  if (range.start > lines.length || range.end > lines.length) return null;
+  return lines.slice(range.start - 1, range.end).join('\n');
+};
+
+/** 逐条重读 + 保鲜 + 失效标记 */
+export const refreshRefs = async (
+  refs: ComposerRef[]
+): Promise<ComposerRef[]> =>
+  Promise.all(
+    refs.map(async (r) => {
+      // v1.4（修 D6）：pending 占位由发送闸门拦截，不进重读（显式跳过，不靠隐式时序保证）
+      if (r.pending) return r;
+      if (!r.path) return r;
+      try {
+        const f = await fileApi.readFile(r.path);
+        if (r.lineRange) {
+          const content = sliceByLineRange(f.content, r.lineRange);
+          if (content === null) return { ...r, invalid: true };
+          return {
+            ...r,
+            content,
+            size: new TextEncoder().encode(content).length,
+            invalid: false,
+          };
+        }
+        return { ...r, content: f.content, size: f.size, invalid: false };
+      } catch {
+        return { ...r, invalid: true };
+      }
+    })
+  );
```

## 八、重构安全网与守护测试矩阵

> 本章回答一个问题：**怎么保证重构后"架构升级了、功能没少、分支没乱、且是增强而非退化"**。
> 结论先行：**靠"先锁行为、再动结构"的五道网**，而不是靠事后肉眼审查。

### 8.1 五道安全网

| 网 | 保证什么 | 机制 | 客观判据 |
|---|---|---|---|
| **网1 架构升级可量化** | 架构真的变好了 | `frontend/scripts/arch-check.mjs`（架构守卫脚本）+ 指标对照表 | 违规数 **8 → 0**（`npm run arch:check:strict` 由红变绿）；重复实现数 3→1；判据份数 2→1 |
| **网2 功能不少** | 一个用户可见能力都没丢 | **功能矩阵**（§8.3）：能力 → 守卫用例编号 → 重构后逐行打勾 | 矩阵每行有 ✅；新增能力必须新增行（不许覆盖旧行） |
| **网3 分支不错乱** | 每个条件分支的行为没串 | **场景剧本矩阵**（§8.4）：分支 → 用例编号 → 逐条跑 | 每个分支至少 1 条用例；分支清单由**代码枚举**得出（不是拍脑袋） |
| **网4 等价性可证** | 搬迁/替换的实现与原来**逐字等价** | **差分测试**（§8.5）：旧实现冻结为参考实现，同一批样本喂新旧，逐字比对 | 样本集全覆盖（正常/边界/非法），差异数 = 0 |

### 8.5 差分测试法（网4，最强的一条）

**做法**（对 R3/R5/R6 这类"应当零行为变化"的改动）：

1. **冻结旧实现**：把被替换/被搬走的实现原样复制到 `__legacy__` 参考文件（**仅本地留存，不提交**）；
2. **固定样本集**：每种判据/每个分支准备 N 组输入（正常 3 + 边界 3 + 非法 3 起）；
3. **同批喂新旧**：新旧实现对同一批输入各跑一遍，**逐字比对输出**；
4. **判定**：差异必须为 0；有差异 → 先问"旧实现是不是本来就错"，再决定是修旧还是保旧（**禁止**直接改新实现去迁就旧 bug）。

**收益**：这是唯一能**证明**"重构等价"的手段 —— 人工审查只能发现"看起来对"的差异。

> 依据 AGENTS「测试目的是发现问题，不是跑脚本」+「严禁以测试代码作为锁死错误系统逻辑的修改借口」：差分测试发现旧实现有错时，**改产品代码**，不改测试去迁就。
