## 一、背景：本次 bug 的直接起因

**现象**（北京老陈 2026-10-05 报）：任务中途页面出问题 → 刷新 → 输入框下方模型选择器**自动跳回"跟随全局"** → 但新任务实际仍用会话覆盖的 `glm-5.2` → 界面与实际用型不符。

**已实施的表层修复**（commit `68b5bf6d8`，v3 审查通过）：
`STORAGE_KEY` 四个写入点全漏 `sessionModel` → 已在缓存层收口 schema（`ChatCacheState` + `buildChatCacheState`/`parseChatCacheState`），读侧补回 `sessionModel`/`sessionVersion`，并修掉 `sessionVersion` 硬编码 1。

**但表层修复只堵住了一半**：三遍复核发现 `restoreState` 这条独立恢复路径**返回体不含 `sessionModel`**，且**消费端根本没调用 `setSessionModelOverride`**。故本文档做全局设计与收口。

## 三、方案论证（为什么是 B）

### 3.1 方案 A：定点补字段（治标，不采纳）

在场景 3（缓存分支）、场景 4（最近会话分支）各补一行 `setSessionModelOverride(...)`，并给 `restoreState` 返回体补 `sessionModel`。

| 维度 | 判定 |
|---|---|
| 效果 | 能修好本次现象 |
| DRY | ❌ **明知 6 处重复，仍手工同步第 N 次**；机制未变，下次新增字段照样漏 |
| 稳定性 | ❌ 未降低同类 bug 发生概率 |
| 结论 | **不采纳**（属"治标"，与老陈"标本兼治"要求不符） |

### 3.2 方案 B：收口为单一注入函数（标本兼治，**裁定采纳**）

在 `useChatSession.ts` 内新增**唯一注入出口**，6 个调用点全部改走它；字段清单只存在一份。

| 维度 | 判定 |
|---|---|
| DRY | ✅ 字段清单单一来源，新增字段只改 1 处 |
| KISS-DIRECT | ✅ 一个直线函数，无分支、无状态机、无 class |
| SRP | ✅ "把某份会话快照写进 state" 这一职责单一化 |
| SLAP | ✅ 不引入新层、不碰数据获取层 |
| 禁 backward | ✅ 不保留旧的 6 段手工注入路径（无兼容层、无双轨） |
| 复用优先 | ✅ 复用既有 8 个 setter，不造新机制 |
| OCP | ✅ 新增字段对 6 个调用点透明 |
| YAGNI | ✅ 不加配置项、不加开关、不做"将来可能需要" |
| 行为等价 | ✅ 逐调用点保持原赋值顺序与兜底语义（见 §四） |

### 3.3 方案 C：注入下沉到 `useChatState`（越界，不采纳）

让 `useChatState` 暴露 `applySession(snapshot)`，其余 hook 不再各自持有 setter。

| 维度 | 判定 |
|---|---|
| 优点 | 最彻底 |
| SLAP | ❌ `useChatSession` 的职责本就是"会话生命周期"，注入属其内；下沉到 `useChatState` 会让聊天状态模块反向承担会话装载语义，**越层** |
| YAGNI / 风险 | ❌ 改动覆盖 6 个 hook，回归面过大，收益与风险不匹配 |
| 结论 | **不采纳** |

### 3.4 裁定

**采纳方案 B。** 理由：A 的全部修复点被 B 完全包含（不存在"先 A 后 B"两次改动）；C 属越层；B 在"不动数据获取层、不动后端、不改任何业务语义"的前提下消灭整类事故的成因。

## 四、方案 B 的完整实施设计

### 4.1 唯一注入函数签名（新增于 `useChatSession.ts` 顶层，`initializeSession` 之前）

```ts
/**
 * 会话状态注入唯一出口 —— 2026-10-05 小欧(文档[10] 方案B)
 *
 * 存在理由(结构性, 非风格): 会话快照有 8 个状态字段, 此前在 6 个注入点手工同步
 *   (loadSession / initializeSession 的 URL·缓存·最近会话三处 / handleNewSession / handleClear),
 *   字段清单各不相同 —— 缓存分支少 2 个、最近会话分支少 1 个。已因此连出三次同型事故:
 *   2026-09-30 sessionVersion 硬编码1(恢复后必撞409) / 2026-10-03 linkEnabled 漏传(刷新丢勾选) /
 *   2026-10-05 sessionModel 漏注(刷新误显示跟随全局)。
 *   本函数把"字段清单"收敛为唯一一份: 新增字段只改这里, 6 个调用点自动覆盖。
 *
 * 语义(每字段的缺省兜底显式声明, 不隐式继承):
 *   - 本函数只做"写 state", 不发请求、不读缓存、不做业务判断(KISS-DIRECT);
 *   - 传 undefined 的字段**保持原值不动**(由调用方决定要不要显式传 null 复位),
 *     避免"漏传 = 被清零"这类反向事故;
 *   - 显式传 null 才是"清空"(用于新会话/清空场景)。
 */
const applySessionState = (snapshot: {
  sessionId?: string | null;
  title?: string;
  version?: number;
  titleLocked?: boolean;
  lastSavedTitle?: string;
  sessionModel?: SessionModelOverride | null;
  linkEnabled?: boolean;
  messages?: Message[];
}): void => { ... };
```

### 4.4 明确不做（防止过度设计 / 防止无边界重构）

- ❌ 不动 `chatHistory.ts` / `sessionStorage.ts` 缓存层（本次已修好，勿再动）
- ❌ 不动后端任何代码
- ❌ 不改 `restoreState` 的 `useCache:false` 校验逻辑与"本地兜底"策略（属独立议题，见 §六遗留）

- ❌ 不给 `applySessionState` 加可选开关/策略参数（YAGNI）

### 4.5 实施后校正（v1.1 追加：与 v1.0 设计的 5 处差异 + 1 处设计缺陷）

**实施时间**：2026-10-05 22:0x（代码已落，本节为设计的事后订正，防止文档与代码不一致）

#### 4.5.1 【设计缺陷】v1.0 的注入点统计不完整 —— 6 处实为 **9 处**

v1.0 §2.2 按"会话加载三场景 + 新建 + 清空"人工阅读计数，得 6 处。实施前改用**机械全量扫描**（`Select-String 'setSession(Id|Title|Version|ModelOverride)\(|setTitleLocked\(|setLastSavedTitle\(|setLinkEnabled\('`）复核，发现**漏 3 处**：

| # | 漏掉的注入点 | 是否活路径 | 若不改的后果 |
|---|---|---|---|
| 1 | `updateSessionTitle` 成功分支 | ✅ 常规路径 | 该路径仍手写字段，**bug 复发** |
| 2 | `updateSessionTitle` 的 **409 冲突回读分支** | ✅ **活路径**（多人同时改标题即触发） | 同上，且此路径最隐蔽（在 catch 里，易漏读） |
| 3 | `handleNewSession` 的**重试分支** | ✅ createSession 失败重试时触发 | 新建失败重试后会残留旧会话状态 |

> **方法论教训（比这次 bug 本身更重要）**：统计"某类代码有几个调用点"**不能用人工阅读数**，必须机械全量扫描。
> 本项目已因此吃过三次亏（`sessionVersion` / `linkEnabled` / `sessionModel`），每次都是"人工同步 + 漏一处"。
> 实施阶段的扫描正是靠机械手段才抓出这 3 处 —— 若沿用设计的 6 处清单直接改，**问题只会从 6 处扩散成 9 处，第四次复发照旧**。

#### 4.5.2 实施与设计的 5 处差异（逐条登记）

| # | v1.0 设计 | 实际实施 | 定性 |
|---|---|---|---|
| 1 | 6 个注入点 | **9 个调用点全部收口** | **设计缺陷**，见 4.5.1 |
| 2 | 配套改动 3 项 | 增第 4 项：`useChatSession` 内 `InitializeSessionOptions.restoreState` 返回类型也补 `sessionModel` | **设计漏项**（同一返回类型有两份声明，`useChatPersistence` 的那份是实现侧，`useChatSession` 的是调用侧类型声明） |
| 3 | 未提依赖清理 | 3 个 `useCallback` 依赖数组由 8 个 setter 收敛为 `applySessionState` 单项 | 收口后 setter 不再被直接引用，留着即死依赖 |
| 4 | 未提 | `handleClear` 依赖删 `currentSessionIdRef` | 该 ref 已收口进 `applySessionState` 内部，依赖项失效（eslint 报 unnecessary） |
| 5 | 未提 | `handleNewSession` 依赖删 `setMessages` | 同上（系统提示消息由 `applySessionState` 内部同一 setter 承载） |

#### 4.5.4 设计的正确之处（实施验证未被推翻）

- 「归一化字段清单、不合并业务分支」—— 完全按此执行，9 个分支语义各自保留
