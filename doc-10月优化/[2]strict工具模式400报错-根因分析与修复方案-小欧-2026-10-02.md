## 一、问题说明

### 1.1 现象

会话模型切到 `opencode (big-pickle)` 后发送消息，**每次必报** HTTP 400：

```
HTTP 400: Error from provider (Console): Upstream request failed:
[invalid_request_error] Invalid function description:
Invalid tool parameters: Strict mode validation failed for function 'bash':
- parameters: Object schemas must have 'additionalProperties: false' in strict mode
```

### 1.2 边界

| 项 | 情况 |
|---|---|
| 触发模型 | `opencodeZen` provider 下全部 6 个模型 |
| 触发时机 | 发消息、ReAct 循环首次调用 LLM 时 |
| 是否必现 | **必现**，与用户输入无关 |
| 其他 provider | agnes / sensenova / qiniu / zhipuai / Discoversh / openrouter **从不报** |
| 影响面 | 该 provider 6 个模型全部不可用 |

### 1.3 问题点数量

| 问法 | 答案 |
|---|---|
| 报错文本里显式点出的 | **1 条** —— 缺 `additionalProperties: false` |
| 以 `bash` 为样本实测出的违规 | **7 处**（详见 3.3） |
| 涉及的工具范围 | **全部 65 个工具**，无一例外（详见 3.4） |
| 另有「自由映射」特殊节点 | **10 处**，分布在 **8 个工具**，本次方案**覆盖不到**，需单独决策（详见 3.5） |
| 须改的代码位置 | **3 处**（详见 3.6） |

**为什么文本只显 1 条、实际有 7 处**：上游校验器**短路返回**，撞到第一条违规即抛错，不列出其余。故报错文本严重低估问题面。

## 三、根因分析

### 3.1 上游在卡什么（strict 三条硬规矩）

| # | 规矩 | 违反后果 |
|---|---|---|
| 1 | `parameters` 必须 `type: object` 且带 `additionalProperties: false` | **直接报本次这个错** |
| 2 | `properties` 里每个字段都必须列进 `required` | 修完第 1 条后继续报 |
| 3 | 不支持 `anyOf` / `oneOf` / `default` / `title` / `minimum` / `maximum` 等一批关键字 | 再修完第 2 条后继续报 |

**配合 C4：`bash` 只是字母序最小、第一个被校验到的工具，不代表只有它有问题。**

### 3.2 矛盾的出处：`_fix_schema_types`

**加工链**（C5）：

```
ShellInput.model_json_schema()          # Pydantic 原始产物
      ↓  schema_utils.py:81  _generate_input_schema()
_fix_schema_types()# schema_utils.py:16-72  ← 矛盾在此产生
      ↓
注册表 input_schema                      # 发给上游的就是它
```

**罪魁祸首 `schema_utils.py:37-49`**：
```python
if 'anyOf' in prop_info:
    non_null_types = [...]
    if len(unique_types) == 1:
        prop_info['type'] = unique_types[0]      # ← L48
```

**来历**：2026-05-06 小健加此函数，因为 Pydantic 对 `Optional[X]` 只吐 `anyOf`、**不吐 `type`**，而某些 API 要求 `properties` 内必须有 `type`。2026-05-13 小沈改过一次逗号拼接。方向是补齐，代价是造出下面的矛盾。

**矛盾长什么样**（`cwd` 在注册表里的实际值）：
```json
"cwd": {
  "anyOf": [ {"type": "string"}, {"type": "null"} ],
  "default": null,
  "description": "需要在特定目录下执行命令的工作目录(绝对路径).不设置则使用当前目录",
  "title": "Cwd",
  "type": "string"
}
```

**为什么算矛盾** —— `type` 与 `anyOf` 在 JSON Schema 里**不是二选一，是同时生效的合取**：

| 键 | 断言 |
|---|---|
| `type: "string"` | 值**必须**是字符串 |
| `anyOf: [{string},{null}]` | 值**可以是**字符串**或 null** |

两者同时满足 ⇒ 只能是 string ⇒ **`null` 通不过**。而同一个 `cwd` 的 `default` 就是 `null`。于是同一份 schema 里，默认值说「可以是 null」、类型约束说「绝不能是 null」，**自己跟自己打架**。strict 校验器同样按合取解释，故同样判不合规。

### 3.3 `bash` 样本：实际违规清单（7 处）

**实测对拍（Pydantic 原始 vs 过 `_fix_schema_types` 后）**：

| 字段 | Pydantic 原始 | 注册表实际 | 是否中招 |
|---|---|---|---|
| `command` | `type=string`，无 anyOf | `type=string`，无 anyOf | 干净 |
| `timeout` | `type=integer`，无 anyOf | `type=integer`，无 anyOf | **干净** |
| `shell_type` | 无 `type`，有 `anyOf`，`default='ps7'` | `type='string'` ← 被加 | **中招** |
| `cwd` | 无 `type`，有 `anyOf`，`default=None` | `type='string'` ← 被加 | **中招（最严重）** |
| `success_codes` | 无 `type`，有 `anyOf`，`default=None` | `type='array'` ← 被加 | **中招** |

即 **3 个 `Optional` 字段中招，`command` / `timeout` 本就干净**。这约束了修法：**必须按「该字段是否真有 `anyOf`」分支处理，不能按字段个数一刀切**，否则会把干净的字段改坏。

**逐项违规清单**：

| # | 违规项 | 位置 | 对应规矩 |
|---|---|---|---|
| 1 | 缺 `additionalProperties: false` | 顶层 | 规矩 1（E3） |
| 2 | `required` 只含 `command` | 顶层 | 规矩 2（E4） |
| 3 | `anyOf` | shell_type / cwd / success_codes | 规矩 3 |
| 4 | `default` | **全部 5 个字段** | 规矩 3 |
| 5 | `title` | **全部 5 个字段** | 规矩 3 |
| 6 | `minimum` / `maximum` | **timeout**（源自源码 `ge=1, le=600`） | 规矩 3 |
| 7 | `enum`，藏在 `anyOf` 内部 | shell_type | 约束丢失风险 |

**第 6 项来源**：`fundamental_schema.py:112` `timeout: int = Field(default=60, ge=1, le=600)`，Pydantic 把 `ge/le` 转成 `minimum`/`maximum`，strict 同样不支持。

**第 7 项最隐蔽**：
```json
"shell_type":     {"anyOf": [{"enum": ["ps7","ps5","cmd","bash"], "type": "string"}, {"type": "null"}]}
"success_codes":  {"anyOf": [{"items": {"type": "integer"}, "type": "array"},        {"type": "null"}]}
```
归一化时若只从 `anyOf` 取 `type`，`enum` 与 `items` 会一并丢失 —— `shell_type` 变成任意字符串、`success_codes` 变成任意元素数组，**等于用一个新缺陷换掉旧缺陷**。故第四章规则 5 专门处理。

### 3.4 全量统计：`bash` 不是特例，65 个工具全部违规

| 键 | 覆盖工具数 | strict 是否接受 | 处理 |
|---|---|---|---|
| `additionalProperties`（顶层） | **0/65 有，即 65/65 缺** | 必需 | 规则 1 补 |
| `title` | **65/65** | 不支持 | 规则 4剥 |
| `default` | 53/65 | 不支持 | 规则 4剥 |
| `anyOf` | 43/65 | 不支持 | 规则 3 转 |
| `required` 未覆盖全部 property | 53/65 | 需全覆盖 | 规则 2 补 |
| `minimum` / `maximum` | 21/65 / 18/65 | 不支持 | 规则 4 剥 |
| `enum` | 25/65 | **支持** | 规则 5 提升保留 |
| `items` | 10/65 | **支持** | 规则 5 / 递归保留 |
| `minLength` | 12/65 | 不支持 | 规则 4 剥 |
| `pattern` / `format` | 2/65 / 1/65 | 不支持 | 规则 4 剥 |
| `$ref` / `$defs` / `oneOf` / `maxLength` / `minItems` / `maxItems` / `uniqueItems` | **0/65** | 不支持但本仓库无 | 无需处理 |

**两条重要结论**：

1. **`bash` 只是字母序第一个被校验到的**（C4），65 个工具**全部**缺 `additionalProperties`、全部带 `title`。改动落在 `to_openai_tools` 这一层，**一次修复覆盖全体**，以后新增工具也不会再踩这类 400。
2. **好消息**：无 `$ref` / `$defs` / `oneOf`，所以递归处理不需要处理引用解析，方案复杂度可控。（此点修正了 v3.0 的一处自我怀疑——当时怀疑存在 `$ref` 嵌套风险，实测为零。）

### 3.5 例外：10 处自由映射字段，本次方案覆盖不到

E9 查出的 `Dict[str, Any]` 参数（`type: object` 且**无 `properties`**），**8 个工具共 10 处**：

| # | 工具 | 参数 | 位置 | 当前 `additionalProperties` |
|---|---|---|---|---|
| 1 | `analyze_data` | `data` | 数组元素 | `true` |
| 2 | `download` | `headers` | 参数本身 | `{'type': 'string'}` |
| 3 | `filter_data` | `data` | 数组元素 | `true` |
| 4 | `filter_data` | `conditions` | 数组元素 | `true` |
| 5 | `generate_chart` | `data` | 可选值分支 | `true` |
| 6 | `httpget` | `headers` | 参数本身 | `{'type': 'string'}` |
| 7 | `httpget` | `body` | 参数本身 | `true` |
| 8 | `screen_capture` | `region` | 参数本身 | `{'type': 'integer'}` |
| 9 | `write_pptx` | `slides` | 数组元素 | `true` |
| 10 | `write_xlsx` | `data` | 数组元素 | `true` |

**为什么是问题**：strict 规范要求每个 object 节点的 `additionalProperties` 必须是 `false`，**但自由映射（任意键的 dict）在 strict 下没有标准表达方式**。若规则 1 无条件给这些节点补 `false`，等于**禁止 LLM 传任何键** —— `httpget(headers={...})` 会被自己的 schema 拒掉，**这是功能退化，不是修复**。

**因此规则 1 必须收窄**：只对**有 `properties` 的** object 节点补 `additionalProperties`；对自由 map **原样保留**（规则 6）。

**残留风险（N3，未实测）**：上游若严格要求所有 object 都是 `false`，这几处仍会 400。处置方案见第七章决策表，**推荐先按保守策略落码并实测**，再决定是否要动这 6 个工具的入参契约。

## 四、解决方案分析

### 4.1 三案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A | 全局 `strict=False` | 一行改完 | 丢参数强校验；**gpt-5 系新模型要求 strict**，改了那些模型直接不可用 |
| **B（推荐）** | 在 `to_openai_tools` 内做 **strict 归一化** | 真正兼容严格端；归一化后语义等价，宽松端不受影响 | 需递归处理嵌套 object / array |
| C | 模型库加 `strict` 开关，按 provider 决定 | 精细可控 | 要改配置结构与调用链，多一处真相源 |

**结论：采纳 B + C。**

- **B 作根治**：我方按规范出牌，不依赖 provider 脾气。改动集中在 `tool_description.py` 一个文件，一次覆盖 65 个工具。
- **C 作兜底**：再遇更严的端可按模型粒度微调，不必动归一化逻辑。第五章代码 3 是 C 的落地入口。**本期不实施 C 的判定逻辑**（见 5.6）。

**不选 A 的理由**（两条，均为实质退化）：
1. 工具参数强校验对Agent 稳定性有实际价值——能挡掉 LLM 传错参数名。关掉是拿稳定性换改动量。
2. 新模型普遍要求 strict，A 会堵死后续接入路。

### 4.2 归一化的六条规则

| # | 规则 | 目的 |
|---|---|---|
| 1 | **有 `properties` 的** object 节点补 `additionalProperties: false`；**无 `properties` 的自由 map 原样保留** | 满足规矩 1，同时避开 3.5 的退化陷阱 |
| 2 | `required` 改为 `properties` 的全部 key | 满足规矩 2 |
| 3 | `anyOf:[{type:T},{type:null}]` → `{"type": [T, "null"]}`，并**覆盖与 `anyOf` 重复的顶层 `type`** | 满足规矩 2、3；消除 3.2 的矛盾 |
| 4 | 剥除 11 个不支持键（`default` / `title` / `format` / `examples` / `minimum` / `maximum` / `minLength` / `maxLength` / `pattern` / `minItems` / `maxItems` / `uniqueItems`）；**`description` 一律保留** | 满足规矩 3 |
| 5 | **`anyOf` 内非 null 分支的 `enum` / `items` 提升到外层**；提升 `enum` 时把 `"null"` 一并并入 | 防丢约束（针对 3.3 第 7 项） |
| 6 | **自由 map（`type: object` 且无 `properties`）整棵子树保留结构**：`anyOf` 不拆、`type` 不改、`additionalProperties` 原样保留；仅剥除 `default` / `title` 等不支持键 | 避免把 `httpget(headers={...})` 拒掉（针对 3.5） |

**规则 4 为何保留 `description`**：剥关键字会丢参数约束信息（如 `timeout` 默认 60），但本项目的参数语义本就写在 `description` 里（例：`"命令解释器: ps7=PowerShell 7+(推荐/默认)..."`），保留即可。

**规则 5 为何只提升 `enum` 与 `items`**：分支内的 `minimum` / `maximum` 属 strict 不支持，只能丢弃；而 `enum`（合法值集合）与 `items`（元素类型）是**语义本身**，丢了就变成另一个工具。

**规则 1 / 6 为何要分开写**：规则 1 是「补」，规则 6 是「别碰」。两者一起才既满足 strict、又不动自由 map。实现上只需一个判断：`if "properties" in out:` 才补 `additionalProperties`，否则原样返回。

**递归必要性**：顶层之外，嵌套 object 与 `array.items` 同样受 strict 约束；且 3.3 已证明约束会藏在 `anyOf` 内部，只处理顶层必然漏。

### 4.3 影响面评估

| 项 | 评估 |
|---|---|
| 覆盖范围 | **65/65 工具一次覆盖**（3.4），不是单点修补 |
| 宽松端（agnes 等） | 拿到的也是归一化后 schema，**语义等价**：可选参数的 `default` 被剥、`required` 变全。因字段类型含 `null`，不传即 `null`，等价于省略 |
| LLM 行为 | `description` 保留，参数语义不丢；`required` 变全是严格端放行的前提，不可两全 |
| 唯一真实变严 | `additionalProperties: false` 会挡掉 LLM 传的野字段。这正是 strict 的本意，**是把本该有的校验补回来**，不是拿功能换指标 |
| 自由 map | **不动**（规则 6），故 `httpget` / `download` / `screen_capture` 等 8 个工具的行为**零变化**；代价是这 10 处可能仍触发 N3，详见 4.4 |

### 4.4 专项：自由 map（8 个工具 10 处）的处置

本节把「自由 map」这一例外单独讲透。**字段清单见 3.5，此处不重复，只讲处置与决策。**

#### 4.4.1 它为什么是个例外

普通工具参数是"固定字段的对象"（如 `bash` 有 `command` / `cwd` / `timeout`…），strict 规规矩矩能表达。自由 map 是"任意键的字典"（`Dict[str, Any]`），长这样：

```json
"headers": { "type": "object", "additionalProperties": { "type": "string" } }
```

- strict 规矩 1 要求：object 节点的 `additionalProperties` **必须是 `false`**（＝一个额外键都不许有）
- 而字典的定义就是"键任意"

**两者直接冲突，且 OpenAI 规范没有为自由 map 提供任何替代表达方式**——这是规范的空白，不是我们的实现问题。所以严格端对这类节点**要么宽容放行，要么无解**（N3 即指这个未知）。

#### 4.4.2 若强行按规矩 1 补 `false` 会怎样（这正是要避免的）

以 `httpget` 的 `headers` 为例：

| | 归一化**前**（现状） | 若强行补 `false`（错误做法） |
|---|---|---|
| schema | `{"type":"object","additionalProperties":{"type":"string"}}` | `{"type":"object","additionalProperties":false}` |
| `headers={"A":"1","B":"2"}` | ✅ 通过 | ❌ **被拒**——等于禁止传任何键 |
| 实际后果 | — | `httpget` 工具**完全不可用** |

**这不是修 bug，是拿一个功能坏掉换一个 schema 好看。** 故规则 1 收窄为「仅有 `properties` 的才补」。

#### 4.4.2.1 实测又抓出第二层坑（v4.3 已修复）：规则 3 拆 `anyOf` 会连带丢掉约束

写完第一版代码后，把 5.3 的函数**原样复制出来对 65 个工具跑了一遍**，实测发现：

| | 归一化前 | 归一化后（第一版代码） |
|---|---|---|
| `download.headers` | `{"anyOf":[{"additionalProperties":{"type":"string"},"type":"object"},{"type":"null"}], "title":"Headers", ...}` | `{"description":"请求头…","type":["object","null"]}` ← **`additionalProperties` 整个消失** |
| `screen_capture.region` | `additionalProperties: {"type":"integer"}` | 同样丢失 |

**根因**：自由 map 常被包在 `anyOf` 里（`Optional[Dict[str,X]]` → `anyOf:[{object,additionalProperties:{type:X}}, {null}]`）。规则 3 为了把 `anyOf` 转成 `type:[X,null]` 而拆掉 `anyOf`，**`additionalProperties` 藏在分支内部，跟着一起没了** —— 于是「键值必须是字符串」这条约束凭空丢失，`headers={"a": 123}` 也能过。

**这与 3.3 第 7 项丢 `enum` 是同一类错误**（拆结构时把分支内的语义丢掉），我第一版只补了 `enum`/`items`，漏了 `additionalProperties` 藏在任何 `Dict[str, X]` 里这条路径。

**修复**：新增 `_is_freeform()` 前置判定，命中自由映射就**只剥键、不拆结构**（代码见 5.3）。

**复验结果（已跑）**：

| 检项 | 结果 |
|---|---|
| 4 处参数层自由 map 的 `additionalProperties` | **4/4 与改前逐字一致**（`{'type':'string'}` / `True` / `{'type':'integer'}` 全保住） |
| 数组元素层（`analyze_data.data[]` 等） | `items.additionalProperties: true` **保住** |
| 普通工具 `additionalProperties` 合规 | 65/65 PASS |
| `required` 全覆盖 | 65/65 PASS |
| `description` 逐字保留 | 65/65 PASS |
| `shell_type` enum 含 `null` / `success_codes` items | 均保住 |

#### 4.4.3 本次处置：不动，行为零变化

| 项 | 结论 |
|---|---|
| 归一化对这 10 处做什么 | **什么都不做**，子树原样返回 |
| 用户可见影响 | **零**。8 个工具的参数语义、校验行为完全不变 |
| 代价 | 这 10 处可能仍触发 N3（上游不放行）→ `httpget` 等 6 类 map 工具在严格端可能不可用 |
| 兜底 | 即便发生，也只影响带 map 参数的 8 个工具，**不影响 `bash` / `read` 等其余 57 个**，故本次修复的主要目标（让 `big-pickle` 能跑）不受牵连 |

#### 4.4.4 若 V10 证实 N3（上游不放行自由 map），三档处置

| 档 | 做法 | 代价 | 适用 |
|---|---|---|---|
| A | 维持现状（推荐先走这档） | 这 8 个工具在严格端不可用 | V10 显示上游其实宽容，或短期可接受 |
| B | map 参数改 JSON 字符串（`headers_json: str`） | 最合规；但改 8 个工具入参契约，牵动 E2E、前端、文档 | 确实不可用且必须支持 |
| C | map 改固定键结构 | 语义收紧，需逐工具设计键集，可能拦掉 LLM 想传的键 | 键集可穷举的场合（如 `region`） |

**建议顺序**：先落 A + 跑 V10（验收标准见第六章 V10），**只有 V10 报出 strict 错误时才升级到 B / C**。理由：N1 / N2 / N3 三条都因 E7（裸调被403 门禁挡住）未能实测，此刻就动 8 个工具的 API 属于无依据的过度设计。

+      - 只提升 enum 与 items; 分支内的 minimum/maximum 属 strict 不支持, 直接丢弃。
+      - 【v4.3·已实测复现并修复】自由映射必须整棵保留: 规则 3 拆 anyOf 时会连带丢掉
+        anyOf 分支内的 additionalProperties, 实测 download.headers 归一化后 additionalProperties
+        整个消失({"type":"object","additionalProperties":{"type":"string"}} → {"type":["object","null"]}),
+        即"值须为字符串"的约束凭空丢失。故此处先判自由映射, 命中则只剥键、不拆结构。
+      - 自由映射节点也可能出现在 array 的 items 里(analyze_data.data[] 等),
+        那一层由 items 递归自然覆盖, 无需额外分支。
+      - 递归处理嵌套 object 与 array.items, 避免深层 schema 漏改。
+      - 不就地改入参, 返回新 dict(入参来自注册表元数据, 就地改会污染全局工具注册表)。
+    """
+    if not isinstance(schema, dict):
+        return schema
+    out: Dict[str, Any] = {}
+    branch_types = set()
+    branch_extra: Dict[str, Any] = {}      # anyOf 内非 null 分支的约束(仅提升 enum/items)
+    freeform = False
+    for key, val in schema.items():
+        if key in ("anyOf", "oneOf"):
+            branches = val if isinstance(val, list) else []
+            freeform = freeform or _is_freeform(branches)
+            for item in branches:
+                if not isinstance(item, dict) or item.get("type") == "null":
+                    continue
+                t = item.get("type")
+                if t:
+                    branch_types.add(t)
+                if "enum" in item or "items" in item:
+                    branch_extra.update({k: v for k, v in item.items() if k != "type"})
+        elif key not in _STRICT_UNSUPPORTED_KEYS:
+            out[key] = val
+    if freeform:
+        # 自由映射: 只保留原 anyOf 结构与 additionalProperties, 剥掉 default/title 等;
+        # 删掉与 anyOf 重复的顶层 type, 避免"type:string vs anyOf 允许 null"的矛盾。
+        out["anyOf"] = list(schema.get("anyOf", []))
+        out.pop("type", None)
+        return out
+    if len(branch_types) == 1:
+        out["type"] = [next(iter(branch_types)), "null"]   # 覆盖重复 type, 补可选性
+    if "enum" in branch_extra:
+        out["enum"] = list(branch_extra["enum"]) + ["null"]  # 可选枚举需把 null 并入
+    if "items" in branch_extra:
+        out["items"] = _to_strict_schema(branch_extra["items"])
+    if "properties" in out:
+        props = out["properties"]
+        out["properties"] = {k: _to_strict_schema(v) for k, v in props.items()}
+        out["required"] = list(props.keys())
+        out["additionalProperties"] = False
+    items = out.get("items")
+    if isinstance(items, dict):
+        out["items"] = _to_strict_schema(items)
+    return out
