## 一、事件概述

2026-10-07 07:16:28，用户在前端提交消息 **"那你需要更新 问题 文件哦"**（13 字），任务 `task-11fe984aac1b43b487dabd114e62c4b0` 启动。

用户观察到的两个现象：

| 现象 | 持续时间 | 说明 |
|---|---|---|
| 现象 A：前端停在"执行中"，1 分多钟**没有任何反应** | 07:16:28 → 07:18:31（**123.47 秒**） | 界面无内容、无思考、无进度，仅保活 |
| 现象 B：模型输出"要更新问题报告并生成 5 种格式文档"，但**文件零产出** | 07:18:50 任务结束 | 目标目录根本不存在 |

**结论先行：现象 A 与现象 B 同源，根在「主循环之前的上下文压缩摘要阶段」。该阶段既不发 SSE 事件，又会丢弃模型在此期间产生的全部工具调用。**

## 三、根因链条（四层，逐层可验证）

### 3.1 第一层｜现象层：压缩阶段静默阻塞

- 位置：`react_loop.py:163-164` → `await _compact_injected_history(agent)`，位置在 `while agent.llm_call_count < max_steps`（L192）**之前**。
- 行为：该 `await` 期间主循环未启动，无任何 `publish`，因此 `stream_orchestrator` 无业务事件可转发。
- 前端唯一收到的是 4 个 `:ping` 注释帧（25 秒一次），**不含可渲染内容** → 界面只能停在"执行中"。
- **判定：确认**。日志 4 条心跳 + 零业务事件，无第二种解释。

### 3.2 第二层｜一级根因：摘要调用"角色混淆"，模型误以为自己要干活

- `compaction/summary.py:60-70`：`generate_anchored_summary(llm_agent, messages)` 把**完整会话历史原样**（仅 tool 消息 content 截断）喂给 LLM，前面拼一个 `SUMMARY_TEMPLATE` system 前缀。
- 历史最后一条正是用户指令 **"那你需要更新 问题 文件哦"**。
- 结果：模型在 122303 prompt tokens 的上下文里读到"待办任务"，**按正常干活模式作答**，而非产出摘要。返回 content 原文：

  > 好的，我将基于**真实代码验证和真实数据复核**的结果，更新问题报告和修改实施设计报告，剔除伪造的问题，修正失实的数据，并**重新生成 md/docx/xlsx/pptx/pdf 全格式文档**。
  > ### 任务执行计划
  > 1. 创建新的生成脚本，剔除伪造问题，修正真实数据（如 AI_ID null 79.13%、duration null 100%、总文件数 3066）。
  > 2. 生成 5 种带签名和时间戳的格式文档。
  > 3. 验证产物完整性。

- **判定：确认**（prompt 日志 `LLM调用记录[0].原始响应.content` 原文可查）。

### 3.3 第三层｜二级根因：协议字段契约不一致 → 摘要提取永远取空

这是本次故障最隐蔽的一环，纯代码可证：

**协议侧（`llm_response_builder.py:65-72`）**，action 类型 payload 构造为：
```python
result = {
    "type": "action",
    "thought": full_content,       # ← 正文放在 thought 键
    "reasoning": full_reasoning,
    "fc_context": {"tool_calls": built_tool_calls, ...},   # ← tool_calls 在这里
    "_pending_calls": _pending_calls, ...
}                                  # ← 没有 "content" 键
```

**消费侧（`compaction/summary.py:38-45`）**：
```python
async for item in call_llm_with_fallback(agent=llm_agent, messages=feed, openai_tools=None):
    _p = getattr(item, "payload", None)
    if _p is not None and isinstance(_p, dict) and _p.get("type") != "retrying":
        c = str(_p.get("content") or "").strip()   # ← 只认 content，action 无此键 → 取空串
        if c:
            content = c
return content      # ← 返回空串
```

**注意一个易误判点**：prompt 日志里能看到 `"content": "好的，我将…"`，那是 `_log_llm_response`（`llm_response_builder.py:62,63`）用 `assembled = {"content": full_content, ...}` **本地组装**后写进日志的，与流式协议 payload 是两个不同对象。**日志里有 content，协议里没有** —— 这正是该 bug 长期未被发现的原因。

后果链：
1. `generate_anchored_summary` 返回空串 →
2. `start_step.py:166` `if summary_text:` 不成立 → **压缩零生效** →
3. 历史仍为 135 条 204113 tokens 原样进入主循环 →
4. 主循环 prompt 达 **198552 tokens**（本可通过压缩降到数千）。

**旁证**：日志中**没有** `start_step.py:176 摘要回填完成` 这一行（该行仅在 `summary_text` 非空时打印）。其缺失即为压缩失效的直接证据。

**判定：确认**（代码 + 日志缺失双向印证）。

### 3.4 第四层｜三级根因：摘要路径无工具执行者 → tool_calls 静默丢弃

- `summary.py:38` 传 `openai_tools=None`，走 Text 模式。
- 经 `client_sdk.py:223-226` 核实：`if tools: body["tools"] = tools` / `if tool_choice: body["tool_choice"] = tool_choice` —— **tools=None 时请求体确实不含 tools 字段**（即我方请求构造无诱因，属**模型/网关侧行为偏差**：sensenova 网关 + glm-5.2 在无 tools 定义时仍返回标准 OpenAI 格式 tool_calls）。
- 即便模型返回了，`summary.py` 全程**只读 `content` 键**，从不读 `fc_context.tool_calls`，更无任何执行分支 → **5 个工具调用凭空蒸发**。

**被丢弃的 5 个动作（prompt 日志原文，非推测）**：

| 2 | `bash` | `cd '...task_prompt_log_audit_20261007'; python gen_report.py 2>&1`，timeout=60 |

**文件系统铁证**：

目录**不存在**；同级上一版 `task_prompt_log_audit_20261006`（00:12 生成）存在。**5 个动作零执行、零产出，已由文件系统证据锁死。**

**判定：确认**（prompt 日志 + 文件系统 + app 日志零 `tool_executor.py:88` 记录，三重印证）。

## 五、关于"最终统计没有工具调用"的准确回答

**问：这次新任务到底有没有 tool_calls 被丢弃？统计里为什么看不到？**

**答：有，5 个，全部丢弃，且已由文件系统证实零执行。统计里看不到，是因为它们从未进入 ReAct 主循环。**

需要区分两个"轮次"（prompt 日志 `LLM调用记录` 恰好记录了两条）：

| 记录 | 轮次 | 返回类型 | 结束原因 | 工具数 | 耗时 | 归属路径 | 工具是否执行 |
|---|---|---|---|---|---|---|---|
| **#1** | 0 | `action` | `tool_calls` | 记录字段缺失（**摘要路径不写工具数**） | **123.47s** | **压缩摘要**（`react_loop.py:163`，while 循环外） | **❌ 丢弃** |
| **#2** | 1 | `answer` | `stop` | 17 | 18.42s | 主循环第 1 轮（`react_step.py:339`） | 本次无需执行 |

判别依据（三条，非猜测）：

1. **字段完整度**：记录 #2 有 `调用类型/模型/提供商/消息总数/消息统计/工具数量/工具定义`；记录 #1 **只有** `轮次/返回类型/原始响应时间/解析结果/原始响应/结束原因/token信息`。同一 `log_llm_response` 入口不可能一填一空 → 两条记录来自**不同调用路径**，#1 非主循环。
2. **prompt token 差值**：#1 `prompt_tokens=122303`（摘要 feed：历史经 `summary_feed_max_chars` 截断后 + 摘要模板）；#2 `prompt_tokens=198552`（全量 135 条历史 + 系统 prompt）。两者差值与「截断摘要 / 全量」完全吻合。
3. **日志缺行**：压缩成功后必打的 `start_step.py:176 摘要回填完成` 在日志中**完全缺失** → 证明那次 action 响应走的正是压缩路径且摘要为空。

**因此 `TASK_END ... total_steps=1 / steps=[final=1]` 与"5 个工具调用丢失"并不矛盾**：这 5 个调用属于记录 #1（压缩阶段），从未进入主循环的 step 序列；主循环那一次（记录 #2）模型**自行选择直接输出答案**（未再发起任何工具调用），故统计确实为 0 次工具执行。

**这一条最需要警惕的系统性后果**：用户看到的最终答复是"## 最终验证结论（已逐行核对代码 + 全量扫描 3066 个日志文件）"——模型在压缩阶段已"承诺"要生成 5 种格式文档，主循环阶段却因历史里不存在任何已执行的工具记录而误判"任务已完成"，转而输出结论文本。**用户意图在框架层被静默吞掉，且模型被引向了错误结论。**

## 八、复现与验证方法

**复现前置**：会话历史累积到超过 `ctx243736 × start_trigger_ratio`（当前配置即 204113 > 121868），且用户消息含明确可执行待办。

**验证清单（三堂会审口径）**：

1. **代码错误异常检查**：`grep "摘要回填完成"` 应出现在成功压缩的任务日志中；本任务**缺失** → 压缩零生效
2. **调用链分析**：预期链路 `TASK_START → 超窗判定 → 压缩摘要(应发SSE) → while → 调用#N → 工具执行 → final`；实际 `压缩摘要` 阶段**零 SSE、零工具**
3. **参数正确性**：`Test-Path F:\OmniAgentAs-repair\task_report\task_prompt_log_audit_20261007` → False，证实 5 个动作零执行
4. **契约一致性**：`llm_response_builder.py` action payload 的键集 vs `summary.py` 提取的键集，取交集为空 → 契约不一致
