## 一、问题现象（北京老陈报）

1. 左侧「对话任务」菜单里**只有一个当前最新会话的任务**，看不到别的会话。
2. **从历史会话页进入其他会话进不去**：地址栏已切到目标会话，页面却停在「新会话 / 任务数 0 / 正文空白」。

## 二、复现与证据（真实浏览器，非推断）

## 三、根因：两个守卫并存，锁是多余的那一个

> **本章主线：减锁。** 全章围绕一个动作展开——**把重复职责的 loading 锁删掉，只留代际守卫**。
> 3.1~3.3 是现象与时序（锁怎么把会话加载挡死的）；**3.4 是病根**（锁为什么是多余的）；**3.5 是减锁的逐处代码改动**；**3.6 是减锁后剩下的机制清单**。

### 3.0 主线声明与一处提法更正

本章的结论一句话：**不是三个机制打架，是两个守卫并存、其中一个（锁）纯属多余。**

v1.1 曾把成因写成「StrictMode 双调用 × 代际守卫 × loading 锁，**三者**互斥」。**该提法不准确**，先更正：

| 要素 | 是不是「机制」 | 处置 |
|---|---|---|
| `generationRef` 代际守卫 | ✅ 是守卫，且是**唯一必需**的 | **保留** |
| `isLoadingHistoryRef` loading 锁 | ✅ 是守卫，但**职责与代际守卫重复** | **删除**（本章主线） |
| `<React.StrictMode>`（`src/main.tsx:28`） | ❌ **不是机制**，是 React 开发态行为，只是**触发器** | 无需处置 |

**真正的机制只有两个，且本该只有一个**；StrictMode 只是把互斥放大成 100% 必现。

| 要素 | 是不是「机制」 |
|---|---|
| `generationRef` 代际守卫 | ✅ 是机制 |
| `isLoadingHistoryRef` loading 锁 | ✅ 是机制 |
| `<React.StrictMode>`（`src/main.tsx:28`） | ❌ **不是机制**，是 React 开发态行为，只是**触发器** |

**真正的机制只有两个，两者互斥；StrictMode 只是把互斥放大成 100% 必现。** 且两个机制本就不该并存——见 3.4。

### 3.3 为什么精准对应两个症状

- **症状 1（只有当前最新任务）**：只有 `handleNewSession` 新建的会话能出任务，它**不走这条 URL 加载链**；凡经 `?session_id=` 进入的一律落到上述死路 → 左栏永远只剩当前最新那个。
- **症状 2（历史进不去）**：历史页 `handleResume()`（`History/index.tsx:366-375`）导航**是成功的**（URL 已切到目标 session），但页面停在「新会话/暂无任务」，用户观感即「进不去」。

**附带隐患（生产构建同样存在）**：`isLoadingHistoryRef` 是**全局单锁、不区分会话**，且**先上锁再 await**。「A 会话加载中切到 B」→ B 被同一把锁挡下 → 静默丢失。该条与 StrictMode 无关，StrictMode 只是把它放大成必现。

**2026-09-29 就是那个「没动结构」的人。** 事故不是浏览器/React 的问题，也不是需求变更的问题，是**只做加法不做收口**的结构性债务。

#### 3.4.3 减锁的目标状态：只留一个守卫

**判据：某个机制是否必需，看删掉它会不会破坏正确性。**

|职责 | 归属 | 判据结论 | 处置 |
|---|---|---|---|
| **旧请求结果不得覆盖新意图**（正确性，跨会话/同会话都成立） | 代际守卫 | 删掉则旧结果会污染新会话 → **必需** | **留** |
| **同一次意图别重复发请求**（性能，非正确性） | loading 锁 | 删掉后仍有代际守卫兜底，只是多发一次请求 → **非必需** | **删** |

**故锁是重复守卫：它不贡献正确性，只贡献「省一次请求」，而这点收益远小于它带来的 4 个释放义务与跨会话误锁。**

**结论：最终结构应为「1 个计数器 + 0 把锁」。**

对比现状「1 个计数器 + 1 把锁 + 4 个释放点」：

| 指标 | 现状 | 目标 |
|---|---|---|
| 守卫机制数 | 2（职责重叠、互斥） | **1** |
| 必须记得释放的点 | 4（`:459/:514/:586` 等，忘一处即锁死会话） | **0（无锁可忘）** |
| 跨会话互相拖累 | 有 | **无** |
| 未来多会话 Tab（`[63]` 第七章）并发放载 | 需再加键分锁 | **各会话天然独立，零改造** |

#### 3.4.4 为何减锁必须先做（优先级论证）

1. **它是 3.2 死锁的病根**：不删锁，任何局部改法（挪代际号、锁分键）都只是在**错误的结构上加补丁**。
2. **它会持续复发**：只要两个守卫并存，下次改动仍会踩同一个坑——本文件已记录**三次同型事故**，第四次已被本次证实。
3. **锁分键等替代方案会加重它**：任何「再加一道守卫」的做法（如按 sessionId 分键）都会把「必须记得释放」的点从 4 处扩到更多，**风险随改动量上升**。
4. **减锁是净减法**：删锁属**减少**状态机复杂度与释放义务，功能只增不减（代际守卫兜底），符合「功能只能正确/增强/优化，杜绝退化」。

#### 3.5.17 坑的机理：`return expr` 与 `finally` 的执行顺序（v1.3 自查发现，供后续复用）

**这是 v1.3 方案里真实存在的退化，已修正。记录机理以防重犯。**

**JS 语义**：`try { return expr } finally {...}` 的执行顺序是 **先求值 `expr` → 再执行 `finally` → 最后真正返回**。而 `expr` 若是一个 async 函数调用，它会**同步执行到第一个 `await` 才挂起**，挂起前的代码（含 `onLoadingStart()`）已经跑完。

**据此推演若按 v1.3 原写法（删掉递归分支的 `onLoadingEnd/onRenderEnd`，`finally` 无条件执行）**：

| 序 | 发生什么 | loading 指示器 |
|---|---|---|
| 1 | 递归 `initializeSession` 启动 → `onLoadingStart()` | 亮 |
| 2 | **外层 `finally` 执行 `onLoadingEnd()`** | **灭 ❌** |
| 3 | 递归仍在请求数据（弱网下可达数秒） | 应亮，实灭 |

**后果：重试期间转圈消失——纯退化。**

**正解**：`return await initializeSession(options)`。加 `await` 后外层 `finally` 会在**递归完全结束之后**才执行；递归自身的 `finally` 先灭灯，外层再灭一次（`onLoadingEnd`/`onRenderEnd` 均幂等，无害）。这样 `releasedLock` 这个「跳过 finally」的补丁变量就**彻底不需要了**——它本就是为锁而存在。

**泛化教训**：删除任何「跳过 finally」的标志位时，必须先查清它当年是为**哪个**机制而设。本例它是为「锁重新上锁后不被外层 finally 清掉」，删锁后若照抄旧结构就会漏掉它所掩盖的顺序问题。**减锁不只是删代码，还要把被它掩盖的坑一并接管过来。**

## 五、「进入旧会话并发消息后，它会变成最新会话」——机制与依据

**结论：会。** 代码级实证三条（2026-10-08 基于最新本地代码复核，行号已核对）：

| 事实 | 位置 |
|---|---|
| 历史列表排序 = `ORDER BY updated_at DESC, created_at DESC`（最后内容变更时间，最新排最前） | `backend/app/services/chat/session_service.py:135` |
| `touch_session_updated_at` 定义（刷 `updated_at`） | `backend/app/services/chat/storage.py:223-228` |
| **该函数在消息插入路径被调用**（`allocate_and_insert_message` 内，发消息必经） | `backend/app/services/chat/storage.py:249` |
| `updated_at` 语义 = **内容变更时间**；改开关**不刷**（代码专门注释，避免把会话意外顶到首位） | `backend/app/services/chat/storage.py:671-674` |

流程：点「继续」进入旧会话（成为当前会话）→ 发一条消息（`allocate_and_insert_message` 顺带刷 `updated_at`）→ **该会话自动跳到历史列表第一位**，成为「最新会话」。

即：**发消息前它是旧的，发完它就是最新的**。排序依据是「最后说话时间」而非「创建时间」——与微信/钉钉一致。你原本在用的那个最新会话不会丢，只是被顶到第二行，随时可点回去。

## 六、唯一采用的方法：减锁——删掉重复守卫，只留代际守卫（**已实施**）

> **本章只保留一种方法。** v1.0~v1.3 曾并排列 A/B/C 三案供选，v1.8 起按北京老陈定案
> 「只留全局逻辑最佳、可靠性最好的那一种」收敛：**方法唯一 = 减锁**（下称"本方法"）。
> 下方 6.2 保留被否方案的**否决理由**（不是备选，是防止后人重犯同样的错），6.3 是全局高度的选择判据。

### 6.1 方法本体：做什么、为什么这是唯一的最佳解

**一句话**：把与代际守卫职责重复的 loading 锁**整把删掉**，让「旧结果不得覆盖新意图」这唯一的正确性职责**由代际守卫单独承担**。

**为什么它逻辑最佳（全局高度）**——用一个判据贯穿：**某个机制是否必需，看删掉它会不会破坏正确性。**

| 职责 | 原承担者 | 删掉会怎样 | 判定 |
|---|---|---|---|
| 旧请求结果不得覆盖新意图 | `generationRef` | 旧会话数据会污染新会话（会话错位、右栏残留） | **必需 → 留** |
| 同一次意图别重复发请求 | `isLoadingHistoryRef` | 正确性不受影响（代际守卫仍择一落地）；仅多发一次 GET | **非必需 → 删** |

由此推出本方法的三个结构性优势：

1. **职责唯一**：同一职责只剩一个守卫，两个机制不再可能「各做一遍」——从根上消灭 3.4 那个「只加不减」的债务形态。
2. **义务归零**：锁需要「上锁 + 4 处释放 + 漏一处就锁死」，删锁后**「必须记得释放」的点由 4 降为 0**，事故入口随之归零。
3. **天然可扩展**：未来多会话 Tab（`[63]` 第七章）要并发加载多会话，全局锁会互相拖累；纯代际守卫下**各会话加载互不干扰**，扩展时零改造。

**一处必须做的配套修正（否则净退化）**：递归重试的 `return initializeSession(options)` 必须改 `return await`。
因 JS `try{return expr}finally{}` 是「先求值 expr → 再跑 finally」，而递归是 async、会同步跑到第一个 await（含 `onLoadingStart()`）；不补 `await`，外层 `finally` 会在递归仍在加载时**提前熄灭 loading 指示器**。机理见 3.5.17。

**已验证结果（第十章实录）**：净减 101 行；grep 8 项零命中；`tsc` EXIT=0；`eslint` 0 error；受影响 58 测试全过；真实浏览器 12 场景全过，`⏭️` 日志由 100% 必现降为 0。

### 6.2 被否方案与否决理由（留档防重犯）

> 以下**均已否决**，不作为备选。

| 原方案 | 否决理由 |
|---|---|
| **挪代际号**（把 `++generationRef` 移至上锁之后） | 只治 StrictMode 这一半，**两个重复守卫仍并存**——违背「消除重复职责」这一根因判据；跨会话互吞仍在；等于给错误结构打补丁 |
| **锁分键**（`isLoadingHistoryRef` 按 sessionId 记） | **假修**：锁键取不到。场景3（加载最近会话）的 sessionId 是 `loadLatestHistoryMessages()` 返回后才知，**发请求前手里没有键可分**→「A 加载中切 B」在该分支依然被吞。且它是在错误结构上**再加一道守卫**，把释放义务从 4 处扩到更多，风险随改动量上升 |
| **删锁但保留 releasedLock 结构** | `releasedLock` 本是为「锁重新上锁后不被 finally 清掉」而设；锁删后它失去载体，会掩盖顺序坑导致 loading 指示器提前熄灭。应随本方法一并删除并补 `await` |

### 6.3 全局选择判据（供后人复用）

选方法时按此三问排序，不看改动量大小：

1. **根因是否被消除**，还是在症状处打补丁？（消除重复职责 > 修好时序）
2. **是否减少必须人为记住的义务**？（释放点 / 生命周期配对，越少越可靠）
3. **是否给未来需求留出零改造路径**？（并发多会话、跨页切换）

本方法三条全中；三个被否方案各至少违反一条。

### 10.7 历史卡片改造（北京老陈逐条定案，零新增状态变量）

改法遵循 3.4.3 / 6.3 同一判据：**修根因（交互入口缺失），不在调用点打补丁**；一律复用既有 `handleResume` 与 `is_valid` 语义，`is_valid` 判定提为 `renderItem` 内局部常量 `invalid` 供四处复用（DRY）。

| 定案项 | 落点 |
|---|---|
| 标题置于**卡片左上角**、与右上角勾选框**同一行**、左对齐，**可点进入会话** | `Card.Meta.title` |
| 标题行下加**分割线** | 第1 行 `borderBottom` |
| 中间保留**消息数 + 状态角标** | 第 2 行 |
| 更新时间**靠左**、创建时间**靠右**，同一行 | 第 3 行 flex + `flex:1` 占位 |
| 「继续 / 删除」行**压扁** | 第 4 行自排版 |
| **跳转入口收敛为「继续」+「标题」两处** | 不给 Card 挂整卡 `onClick` |
| 无效会话 | 标题 `not-allowed` 且不跳，「继续」disabled（与原语义一致） |

**为什么不给整卡 `onClick`**：实测该做法会让「点勾选框」也带进会话——`click` 事件先于 `change` 冒泡，靠 `onChange` 里的 `stopPropagation` 拦不住（此坑由实测抓出，非推断）。故从根上不加整卡点击，只保留两个显式入口。

**为什么不用 antd 的 `extra` / `actions`**（两处均为截图实证）：
① `extra` 渲染在 Card 的 **head 行**，与 body 里的 `Card.Meta` 标题**不同行**，会多出一条「只有勾选框的空带」；
② `styles.actions` 只压得住容器 padding，压不动 `actions > li` 自身 padding，操作行仍过高。
改为 body 内四行自排版后两问题同时消失，且不新增 CSS 文件、不用全局选择器。

**版式实测**：卡片高度 **137px**（改前 200+）；标题左对齐 Δ<40px；勾选框靠右；标题与勾选框 Δy=**1.5px**；更新/创建同行 Δy<6px 且创建靠右。

**跳转入口 6 项实测**（真浏览器）：点标题跳 ✅ / 点继续跳 ✅ / 点卡片空白不跳 ✅ / 点勾选框只勾选不跳 ✅ / 点删除只弹确认框不跳（已取消，未删数据）✅ / 无效会话标题不跳且 `not-allowed` ✅。

**本轮我犯的两个错（如实记录）**：
1. 曾把标题塞进 `extra` → 截图才看出多出空带，已改为 body 自排版；
2. 曾**擅自移除状态角标**（把「中间只是保留消息数的显示」误读为「删掉角标」）→北京老陈指出后**已恢复原位置**。这属**功能退化被自查拦下**，记此警示：定案用语有歧义时必须确认，不得自行扩大解释。
