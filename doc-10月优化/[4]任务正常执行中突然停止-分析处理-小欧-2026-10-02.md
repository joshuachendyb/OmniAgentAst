## 一、服务中断情况分类

按"是否可控收信号"分两类。

### 1.1 共同后果

进程被中止 → Agent 内存态（LLM 上下文、执行步、工具调用栈）消失 → 任务只能回到 `task_interrupted`，需手动重发整个任务。

### 1.2 可控停止（收得到关闭信号）

| 场景 | 触发 | 能否落最终 checkpoint |
|------|------|----------------------|
| 正常关机 | 发送关机信号，进程收到 | ✅ 能 |
| 正常重启 | 同上 | ✅ 能 |
| 配置生效重启 / `--reload` | 收到重启请求 | ✅ 能 |

恢复点可贴近中断前。

### 1.3 突发中止（收不到信号）

| 场景 | 触发 | 能否落最终 checkpoint |
|------|------|----------------------|
| 断电 / 强制断电 | 无信号 | ❌ 不能 |
| OOM / `kill -9` | 进程被强杀 | ❌ 不能 |
| 机器死机 / 容器强杀 | 无信号 | ❌ 不能 |

只能回退到最近一次周期性 checkpoint，最多丢一个写入间隔。

### 1.4 共同行为

两类都丢失内存态；区别只在"恢复粒度"：可控停止可在 shutdown 钩子落最终 checkpoint；突发中止只能靠周期写入。

## 二、重启运行后进入当前会话——能否继续、如何运行

### 2.1 现状（[63] P3 完成后）

- 未完成任务：进程重启后返回 `task_interrupted`；前端只能降级加载 DB 历史，用户**手动重发**。
- 已完成任务：可从 Journal 按 seq 精确回放。

### 2.2 目标能力（R4）

重启运行后进入当前会话，系统自动**识别未完成任务**并**续算**：

```text
后端启动
  → 扫描 chat_tasks 中非终态任务
  → 有最近完好 checkpoint：重建 agent_runner，从 checkpoint 续跑
      新事件续写同一 task 的 Journal，seq 连续
      前端按 after_seq 自然续拉，无需感知
  → 无 checkpoint 或损坏：保持 task_interrupted（现状语义，不劣化）
```

### 2.3 不能继续的情形

| 情形 | 行为 |
|------|------|
| 无 checkpoint | `task_interrupted`，手动重发（同现状） |
| checkpoint 损坏 / 校验失败 | 降级 `task_interrupted` |
| LLM 配置版本不符 / generation 过期 | 降级 `task_interrupted`，丢弃跨代结果 |
| 不可序列化资源（进行中命令、文件句柄） | 该步骤标记"需重做"，禁止盲重放 |

## 三、本地最新代码现状及需要基本条件

### 3.1 本地最新版本与重启连续运行的现状

重启后未完成任务**不能续算**，只能回到 `task_interrupted`（现状语义，第二章 2.1 详述）。本地最新版本的关键缺口现状如下：

| 缺口 | 现状 | 影响 |
|------|------|------|
| G1 执行状态无持久化 | `llm_call_count` 等全在内存 | 不知跑到第几步 |
| G2 LLM 上下文无快照 | `conversation_history` 纯内存，`chat_messages` 表已 DROP | 续算要么丢上下文要么全量重放 |
| G3 副作用无幂等登记 | 无 `task_id+step+key` 落库 | 重放即重复写文件/执行命令 |
| G5 无恢复驱动 | 启动流程无非终态扫描 | 无代码推起中断任务 |
| G6 不可序列化资源无降级规则 | 进行中 shell/finalize 未完成 | 恢复时报错或静默半成品 |
| G7 无 `task_resumed` 事件 | 事件白名单无此类型 | 前端无法区分回放与续算 |
| G8 checkpoint 写入时机/事务边界未定 | — | 状态与事件可能撕裂 |
| G9 非终态无收敛 | **已由 L0 关闭** | 任务收敛为 `failed/task_interrupted`，不再骗人 |

### 3.2 需要连续运行的基本条件

R4 不独立存在，实现续算需要满足以下前置条件（[71] 门 1~门 5）：

| 门 | 条件 | 说明 |
|----|------|------|
| 1 | [63] P1/P2/P3 全部落地入库 | Journal（`chat_stream_events`）是 seq 续写的唯一源 |
| 2 | `task_id + seq` 唯一约束与 seq 分配器已上线 | 续算后新事件必须续写同一 task_id 的 seq |
| 3 | [63] P1~P9 全绿、两轮无新增 flaky | 基线稳定 |
| 4 | [69] LLM 连接池、[70] ConnectionScope 已实施 | 恢复路径必须复用统一连接/资源所有权 |
| 5 | 16 个缺口逐条复核无新增/无归属变更 | 当前状态：G9 已由 L0 实施关闭，G1/G2/G3/G5 仍成立 |

### 3.3 需要补充的条件/架构

以现状（3.1）对照，下列是实现续算**必须新建或改造**的条件/架构，不属于 [63] 已建范围：

| # | 需补充项 | 说明 | 现状 |
|---|---------|------|------|
| 1 | **消息序列化层** | `conversation_history` 的可恢复快照（G2）。`chat_messages` 表已 DROP，全库无序列化载体，需重建 | **空白，最大基础缺口** |
| 2 | **checkpoint 表 + 存储** | 新增 `task_checkpoint` 表及窄接口 load/save/remove | 不存在 |
| 3 | **checkpoint 写入点** | `agent_runner` 在副作用前/工具结果后/final 前/shutdown 钩子注入写入点 | 无 |
| 4 | **恢复引擎与状态机** | 启动扫非终态任务 → 校验 → 重建 agent_runner → 同 seq 续写（G5） | 无 |
| 5 | **副作用幂等登记模块** | 每个副作用写 `task_id + step + key`，重放避重（G3） | 无，最高风险 |
| 6 | **`task_resumed` 事件** | 事件白名单新增此类型，供前端区分回放与续算（G7） | 无 |
| 7 | **generation/operationId 校验** | 恢复后 session 侧 generation 过期即丢弃，防跨代串写 | 复用 [63] 4.5 |
| 8 | **连接/资源所有权统一** | 恢复路径必须走 [70] ConnectionScope + [69] 连接池，禁止裸建 | 依赖 [69]/[70] |
| 9 | **事务边界契约** | checkpoint 写入与 Journal seq、`chat_tasks.status` 同事务（G8） | 未定义 |

## 四、概要设计方案

### 4.1 UI 层：如何操作/启动中断任务的续算

| 路径 | 触发 | 行为 |
|------|------|------|
| 任务列表一键续算 | 对 `task_interrupted` 任务点「继续运行」 | 按 task_id 续算 |
| 会话进入续算 | 打开会话，发现未完成任务 | 「待继续」标识 +「继续运行」按钮 |
| 自动兜底续算 | 重启后扫出非终态任务，首次进入其会话 | 自动触发续算并推 `task_resumed` 提示 |
| 无法续算 | 无/坏 checkpoint 或校验失败 | 「继续运行」置灰，保留「重新发起」 |

### 4.2 后端：当前架构

```text
① 接入层    chat_routes/stream_orchestrator：POST /chat/stream 起任务；_agent_tasks 保活
② 流态层    StreamBuffer：event_log(append-only, seq=len)+publish 唯一写入口；内存+300s 回收
③ 消费层    stream_reader(buffer, after_seq)：按 seq 从 offset 转发 SSE
④ 执行层    agent_runner.run_react_background → react_loop.run_react_cycle；finally 终态落库
⑤ 状态层    Agent 实例内存态（MessageBuilder 等）；running_tasks 控制态
⑥ 持久层    SQLite：chat_tasks(status 权威)/chat_task_steps/token_usage
```

```
┌───────────────────────── 后端进程(当前) ─────────────────────────┐
│ POST /chat/stream ─► 接入层 ─► 流态层(StreamBuffer,内存)         │
│                            │        │                            │
│                            ▼        ▼                            │
│                     执行层(agent_runner) ─► 状态层(Agent内存态)   │
│                            │                                   │
│                            ▼                                   │
│                     持久层(SQLite, 仅结果无过程)                  │
│  ⚠ 重启后: 内存全部丢失 → 404 / task_interrupted, 无续算          │
└──────────────────────────────────────────────────────────────────┘
```

| 现状事实 | 重启后果 |
|---------|---------|
| 流态只进内存、300s 回收；`chat_stream_events` 不存在 | 取不到已发生事件，404 |
| 执行状态/LLM 上下文全在内存，无 checkpoint | 不知跑到第几步、上下文丢失 |
| 无 resume 入口、无非终态扫描 | 没有任何代码推起中断任务 |
| finally 不执行 → status 停留 `executing` | 由 L0 收尾为 `failed/task_interrupted`（G9 已修） |

### 4.3 后端：目标架构（连续运行新架构）

既有五层不动，只在既有对象上补缺口：

```text
① 接入层    启动后扫 chat_tasks 非终态 → 交恢复入口（新增，原 POST 链不动）
② 流态层    P3 落地后 event_log 与 chat_stream_events 双写同事务
③ 消费层    stream_reader 不变，续算事件天然按 seq 续读
④ 执行层    agent_runner 新增 resume 入口，复用 run_react_cycle，不新建引擎
⑤ 状态层    新增 task_checkpoint 存取 + 写入点（唯一新增状态源）
⑥ 持久层    非终态补 task_interrupted 收敛态
```

```
┌───────────────────────── 后端(目标架构) ─────────────────────────┐
│ 启动 ─► 扫 chat_tasks 非终态 ─► 有checkpoint? ─► 恢复入口 resume  │
│                                    │是                           │
│                                    ▼                             │
│              ┌─ 事件层(P3已建): chat_stream_events 双写P3表      │
│   agent_runner resume ─► 状态层(R4新增): task_checkpoint 写入点   │
│              └─ 执行层(R4新增): run_react_cycle 续跑             │
│                                    │否/损坏                      │
│                                    ▼                             │
│                    降级: task_interrupted（行为不劣化）           │
└──────────────────────────────────────────────────────────────────┘
```

三层叠加：事件层（P3 已建）/ 状态层（R4 新增）/ 执行层（R4 新增）。checkpoint 写入点：副作用前、工具 result 后、final 前、shutdown 钩子。无/坏 checkpoint → `task_interrupted`，行为不劣化。

### 4.4 前端：当前架构

```text
① 发送/连接   useSSE：POST /chat/stream；fetch+ReadableStream+AbortController（非 EventSource）
② 真源        React state + ref：executionSteps / lastSeqRef / serverTaskId / usageAccumRef
③ 备份        sessionStorage：sse_execution_steps_backup，5s 防抖，外壳 {steps,source,timestamp}
④ 重连        指数退避+Full Jitter，maxAttempts=3；GET after_seq=lastSeq+1
⑤ 重试耗尽    pollSessionTaskStatus：GET /sessions/{sid}/tasks 每 5s×30
⑥ 会话恢复    useChatSession → loadHistoryMessages(DB 历史) 或 restoreState
```

```
┌─────────────────────── 前端(当前架构) ───────────────────────────┐
│ POST /chat/stream ─► useSSE ─► 真源(组件内存 state/ref)          │
│                         │            │                            │
│                         │            ├── sessionStorage 5s备份    │
│                         │            └── GET after_seq 重连(×3)   │
│                         │                                       │
│                         └── 后端重启 → 404 → 轮询 → 提示手动重发   │
│  ⚠ 真源在组件内存、无共享Store、无task_resumed语义、刷新即丢流      │
└──────────────────────────────────────────────────────────────────┘
```

| 现状 | 缺口 |
|------|------|
| 真源在组件内存，L1 全局 Store 未实现 | 切页/刷新丢流 |
| `lastSeqRef` 不持久化 | 刷新后续传游标丢失 |
| 无 `task_resumed`/`task_interrupted` 事件语义 | 用户无法区分回放与续算 |
| 后端重启只出 404/轮询 | 无法拉续算事件源 |

### 4.5 前端：目标架构（连续运行新架构）

```text
真源：组件内存 → 共享 Store（[63] P1）+ 备份外壳补 {task_id,last_seq,status}
重连链：复用 after_seq=lastSeq+1，仅把 lastSeq 改为可持久化来源
```

## 五、link（任务上下文链）全链路分析与改造方案

> 本章为 2026-10-02 20:14~20:42 小欧对 link 前后端全量排查后的分析与改造方案。原 v1.5 第五章「conversation_history 持久化（G2 先行方案）」与本章主题不同，**已由北京老陈裁撤删除**（2026-10-02，"留着没有用"），故本章之下不再有 G2 留档节；v1.6 中"移入 5.10 留档、内容未删减"的描述随之失效，以本行为准。

### 5.1 需求语义定案（北京老陈 2026-10-02）

当前实现与真实需求**语义相反**，逐条定案如下：

| # | 语义条款 | 定案内容 |
|---|---------|---------|
| 1 | link 是**粘性状态** | 不是"每条消息各选各的"一次性参数。UI 设置一次后保持，**不得设置完就弹回** |
| 2 | 开启的含义 | 从"从不 link"改为"link"，表示**下一个新任务与前一条任务是连续的**，即并入当前组 |
| 3 | 持续性 | 此后每一条新任务都进入同一组，**一直持续到用户关闭 link 为止** |
| 4 | 关闭的含义 | 关闭 link 即组结束；下一次再开启 link 时**另起新组** |
| 5 | 分组边界 | 由 link **关闭的时刻**决定，而非每条消息各自决定 |
| 6 | 会话隔离 | 每个会话**各自独立记忆**自己的 link 状态 |
| 7 | 前一条任务口径 | 取会话内**最近一条任务，任意状态都算**（实际可取到 failed / cancelled / 中断态等非活跃态；`running`/`paused` 不会成为"前一条"，那种情况走消息注入而不新建任务，见 5.4「活跃任务注入」行） |
| 8 | 组可见性 | UI 上要能看到任务属于哪一组，加**组徽标** |

**关键推论**：link 关闭期间发出的任务各自为独立新组；link 一旦开启，新任务并入**前一条任务所在的组**（不论前一条自己当时开没开 link），随后每条都进这个组。

### 5.2 语义推演（示例）

设 `context_root_task_id` 为链根，相同链根即同组：

| 序 | link 开关 | 任务 | 前一条任务 | 链根 | 分组结果 |
|----|----------|------|-----------|------|---------|
| 1 | 关 | A | — | A | 新组 G1 |
| 2 | 关 | B | A | B | 新组 G2（关着就各组各的） |
| 3 | **开** | C | B | **B** | 并入 G2 |
| 4 | 开 | D | C | **B** | 并入 G2（链根沿用，不逐跳上跳） |
| 5 | **关** | E | D | **E** | 新组 G3（关 link 即切断） |
| 6 | **开** | F | E | **E** | 并入 G3 |

对照现状：第 3 步若前一条 B 是 `failed`，现有 SQL 直接跳过 B，导致 C 链根错误地回溯到更早的完成任务甚至自为链根 —— 这就是"各种状态都需要"要修的核心点。

### 5.4 现状盘点：后端

| 环节 | 位置 | 现状事实 |
|------|------|---------|
| DTO 默认值 | `api/v1/chat/models.py` 的 `ChatRequest.context_link_mode` | 默认 `"independent"`，**无校验** |
| 路由透传 | `api/v1/chat/chat_routes.py` 的 `chat_stream_endpoint` | 原样透传给编排器 |
| 白名单校验 | `services/chat/stream_orchestrator.py` 的 `chat_stream_orchestrator` | 非 `linked`/`independent` → 归一 `independent`；传 `None` 也归一 `independent` |
| 链根计算 | 同上 | 默认自为链根；**仅当**入参 `linked` 时才查上一任务链根 |
| **选链根 SQL** | `services/chat/storage.py` 的 `get_previous_task_chain` | `WHERE session_id=? AND status='completed' ORDER BY id DESC LIMIT 1` —— **只认 completed** |
| 链式继承 | 同上 | 返回值取上一任务自身的链根（为空则回退其 task_id），故链根沿用而非逐跳上跳 |
| 死字段 | 同上返回值 | 返回的 `task_id` 键**无消费方**；编排器只读取 `context_root_task_id`，故该 SQL 应只返回这一个键 |
| 历史装配 | `services/chat/history_loader.py` 的 `_load_previous_messages` | `independent` 直接返回空列表（**零历史**）；`linked` 才按消息区间取；其签名仍收 `context_link_mode` 且内含**二次兜底白名单** |
| 区间 SQL | `services/chat/storage.py` 的 `fetch_session_user_message_pairs` | 下界含、上界严格不含（已修过一次，防本任务消息自我回灌） |
| 落库 | `chat_tasks` 两列 | 每任务一行**事实记录**（非设置项） |
| **状态持久化** | `chat_sessions` 表 | **无 link 列**；配置文件亦无任何 link 配置项 |
| 会话更新契约 | `services/chat/session_service.py` 的 `update_session` | 仅认 `title` / `sessionModel` 二字段，且显式拒绝只传其它字段的请求。link 属会话属性但**不走此路径**（另设窄端点），避免为 link 改动既有会话更新契约 |
| DTO 未知字段行为 | `api/v1/chat/models.py` 的 `ChatRequest` | 未设 `model_config`，Pydantic v2 默认 `extra='ignore'` → **删字段后旧前端仍发该字段会被静默丢弃、不报错**。故删参数与前端停发必须同批交付（见决策 9） |
| **活跃任务注入** | `services/chat/stream_orchestrator.py` + `services/task/task_registry.py` | 同会话存在活跃任务（内存 `running_tasks` 中 status ∈ `running`/`paused`）时，新消息注入该任务、新 task_id 作废直接返回，另有并发占位守卫兜底竞态。**故真正插入 `chat_tasks` 行时，该会话必然无活跃任务** —— 这是条款 7「任意状态」口径不会引发同组并发的前提 |
| 列表接口 | `services/chat/storage.py` 的 `list_session_tasks` | 只 SELECT `context_link_mode`，**不含 `context_root_task_id`** → 前端拿不到分组键，无法渲染组徽标 |
| 列表端点契约 | `api/v1/sessions.py` 的 `list_session_tasks_endpoint` | **无 `response_model`**，直接返回 dict → SELECT 补列即生效，无需改任何 DTO |
| 测试契约 | 全仓 `backend/` 测试 | **无任何测试**引用 `context_link_mode` 或 `get_previous_task_chain` → 废止参数与改链根口径不破坏既有测试 |

**结论：后端完全没有任何"用户希望续聊"这一偏好的持久化**，只有逐任务的历史事实行，链的形成靠每请求传参 + 回查最近一条成功任务反推。

### 5.5 差距对照

| 语义条款 | 现状 | 差距 |
|---------|------|------|
| 1 link 粘性保持 | 发送即复位 | **完全相反** |
| 2 开=并入前一条所在组 | 无组概念，仅回查最近 completed | 口径不符 |
| 3 持续到关闭为止 | 无持续性 | 缺失 |
| 4 关=另起新组 | 无边界概念 | 缺失 |
| 5 边界由关闭时刻决定 | 无此逻辑 | 缺失 |
| 6 每会话独立记忆 | 无会话级存储，且切会话还会泄漏 | 缺失且反向有 bug |
| 7 任意状态任务 | 只认 completed | **口径不符** |
| 8 组徽标 | 无渲染 | 缺失 |

### 5.6 关键决策

| # | 决策点 | 结论 | 依据 |
|---|--------|------|------|
| 1 | link 状态存哪 | **后端 `chat_sessions` 新增列** | 条款 6 要求以会话为键；铁规 1.5「后端为主，前端迎合后端」；只有后端能权威判定组边界。存前端 localStorage 会出现多设备不一致 |
| 2 | 切会话行为 | 每会话各自独立记忆 | 北京老陈定案 |
| 3 | 链根口径 | 最近一条任务，任意状态都算 | 北京老陈定案 |
| 4 | 组徽标 | 加 | 北京老陈定案 |
| 5 | 逐请求参数 `context_link_mode` | **废止删除**，不做兼容保留 | 会话状态成为唯一真源；保留双真源必然产生矛盾（前端说 linked、后端说 independent 时以谁为准无解）；且铁规明令「禁止 backward」 |
| 6 | `chat_tasks.context_link_mode` 列 | **保留** | 它是任务级历史事实，遥测快照与 start 契约在用；组归属由 `context_root_task_id` 判定，两者职责不同 |
| 7 | 组判定唯一真源 | **`context_root_task_id` 列本身** | 组 = 同链根。列即唯一真源，徽标由前端读该列派生组号，**后端不新增任何分组聚合接口/函数**（DRY：组边界语义只在写链根处表达一次；YAGNI：不加当前用不上的接口） |
| 8 | 是否新增 link 读端点 | **不新增**，复用既有 `GET /sessions/{id}` | 会话级信息已有该端点，`link_enabled` 加入 `SessionResponse` 即可读到；另建读端点属 YAGNI 冗余。只增**一个**写端点 `PATCH /sessions/{id}/link` |
| 9 | 交付原子性 | **前后端同批交付，中间态不部署** | 铁规禁止 backward，故不做"后端先上、兼容旧前端"。若只上后端，旧前端仍发 `context_link_mode` 且被 `extra='ignore'` 静默丢弃，用户点 link 表现为无反应——此中间态不可接受 |
| 10 | `chat_tasks.context_link_mode` 落库值 | 会话 link 开 → `'linked'`；会话 link 关 → `'independent'` | 该列被 `start_step` 与遥测消费，必须明确取值口径，否则遥测语义漂移 |
