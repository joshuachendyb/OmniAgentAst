## 一、服务中断情况分类

按"是否可控收信号"分两类。

### 1.1 共同后果

进程被中止 → Agent 内存态（LLM 上下文、执行步、工具调用栈）消失 → 任务只能回到 `task_interrupted`，需手动重发整个任务。

### 1.2 可控停止（收得到关闭信号）

| 场景 | 触发 | 能否落最终 checkpoint |
|------|------|----------------------|
| 正常关机 | 发送关机信号，进程收到 | ✅ 能 |
| 正常重启 | 同上 | ✅ 能 |
| 配置生效重启 / `--reload` | 收到重启请求 | ✅ 能 |

恢复点可贴近中断前。

### 1.3 突发中止（收不到信号）

| 场景 | 触发 | 能否落最终 checkpoint |
|------|------|----------------------|
| 断电 / 强制断电 | 无信号 | ❌ 不能 |
| OOM / `kill -9` | 进程被强杀 | ❌ 不能 |
| 机器死机 / 容器强杀 | 无信号 | ❌ 不能 |

只能回退到最近一次周期性 checkpoint，最多丢一个写入间隔。

### 1.4 共同行为

两类都丢失内存态；区别只在"恢复粒度"：可控停止可在 shutdown 钩子落最终 checkpoint；突发中止只能靠周期写入。

## 二、重启运行后进入当前会话——能否继续、如何运行

### 2.1 现状（[63] P3 完成后）

- 未完成任务：进程重启后返回 `task_interrupted`；前端只能降级加载 DB 历史，用户**手动重发**。
- 已完成任务：可从 Journal 按 seq 精确回放。

### 2.2 目标能力（R4）

重启运行后进入当前会话，系统自动**识别未完成任务**并**续算**：

```text
后端启动
  → 扫描 chat_tasks 中非终态任务
  → 有最近完好 checkpoint：重建 agent_runner，从 checkpoint 续跑
      新事件续写同一 task 的 Journal，seq 连续
      前端按 after_seq 自然续拉，无需感知
  → 无 checkpoint 或损坏：保持 task_interrupted（现状语义，不劣化）
```

### 2.3 不能继续的情形

| 情形 | 行为 |
|------|------|
| 无 checkpoint | `task_interrupted`，手动重发（同现状） |
| checkpoint 损坏 / 校验失败 | 降级 `task_interrupted` |
| LLM 配置版本不符 / generation 过期 | 降级 `task_interrupted`，丢弃跨代结果 |
| 不可序列化资源（进行中命令、文件句柄） | 该步骤标记"需重做"，禁止盲重放 |

## 三、本地最新代码现状及需要基本条件

### 3.1 本地最新版本与重启连续运行的现状

重启后未完成任务**不能续算**，只能回到 `task_interrupted`（现状语义，第二章 2.1 详述）。本地最新版本的关键缺口现状如下：

| 缺口 | 现状 | 影响 |
|------|------|------|
| G1 执行状态无持久化 | `llm_call_count` 等全在内存 | 不知跑到第几步 |
| G2 LLM 上下文无快照 | `conversation_history` 纯内存，`chat_messages` 表已 DROP | 续算要么丢上下文要么全量重放 |
| G3 副作用无幂等登记 | 无 `task_id+step+key` 落库 | 重放即重复写文件/执行命令 |
| G5 无恢复驱动 | 启动流程无非终态扫描 | 无代码推起中断任务 |
| G6 不可序列化资源无降级规则 | 进行中 shell/finalize 未完成 | 恢复时报错或静默半成品 |
| G7 无 `task_resumed` 事件 | 事件白名单无此类型 | 前端无法区分回放与续算 |
| G8 checkpoint 写入时机/事务边界未定 | — | 状态与事件可能撕裂 |
| G9 非终态无收敛 | **已由 L0 关闭** | 任务收敛为 `failed/task_interrupted`，不再骗人 |

### 3.2 需要连续运行的基本条件

R4 不独立存在，实现续算需要满足以下前置条件（[71] 门 1~门 5）：

| 门 | 条件 | 说明 |
|----|------|------|
| 1 | [63] P1/P2/P3 全部落地入库 | Journal（`chat_stream_events`）是 seq 续写的唯一源 |
| 2 | `task_id + seq` 唯一约束与 seq 分配器已上线 | 续算后新事件必须续写同一 task_id 的 seq |
| 3 | [63] P1~P9 全绿、两轮无新增 flaky | 基线稳定 |
| 4 | [69] LLM 连接池、[70] ConnectionScope 已实施 | 恢复路径必须复用统一连接/资源所有权 |
| 5 | 16 个缺口逐条复核无新增/无归属变更 | 当前状态：G9 已由 L0 实施关闭，G1/G2/G3/G5 仍成立 |

### 3.3 需要补充的条件/架构

以现状（3.1）对照，下列是实现续算**必须新建或改造**的条件/架构，不属于 [63] 已建范围：

| # | 需补充项 | 说明 | 现状 |
|---|---------|------|------|
| 1 | **消息序列化层** | `conversation_history` 的可恢复快照（G2）。`chat_messages` 表已 DROP，全库无序列化载体，需重建 | **空白，最大基础缺口** |
| 2 | **checkpoint 表 + 存储** | 新增 `task_checkpoint` 表及窄接口 load/save/remove | 不存在 |
| 3 | **checkpoint 写入点** | `agent_runner` 在副作用前/工具结果后/final 前/shutdown 钩子注入写入点 | 无 |

## 五、link（任务上下文链）全链路分析与改造方案

> 本章为 2026-10-02 20:14~20:42 小欧对 link 前后端全量排查后的分析与改造方案。原 v1.5 第五章「conversation_history 持久化（G2 先行方案）」与本章主题不同，**已由北京老陈裁撤删除**（2026-10-02，"留着没有用"），故本章之下不再有 G2 留档节；v1.6 中"移入 5.10 留档、内容未删减"的描述随之失效，以本行为准。

### 5.1 需求语义定案（北京老陈 2026-10-02）

当前实现与真实需求**语义相反**，逐条定案如下：

| # | 语义条款 | 定案内容 |
|---|---------|---------|
| 1 | link 是**粘性状态** | 不是"每条消息各选各的"一次性参数。UI 设置一次后保持，**不得设置完就弹回** |
| 2 | 开启的含义 | 从"从不 link"改为"link"，表示**下一个新任务与前一条任务是连续的**，即并入当前组 |
| 3 | 持续性 | 此后每一条新任务都进入同一组，**一直持续到用户关闭 link 为止** |
| 4 | 关闭的含义 | 关闭 link 即组结束；下一次再开启 link 时**另起新组** |
| 5 | 分组边界 | 由 link **关闭的时刻**决定，而非每条消息各自决定 |
| 6 | 会话隔离 | 每个会话**各自独立记忆**自己的 link 状态 |
| 7 | 前一条任务口径 | 取会话内**最近一条任务，任意状态都算**（实际可取到 failed / cancelled / 中断态等非活跃态；`running`/`paused` 不会成为"前一条"，那种情况走消息注入而不新建任务，见 5.4「活跃任务注入」行） |
| 8 | 组可见性 | UI 上要能看到任务属于哪一组，加**组徽标** |

**关键推论**：link 关闭期间发出的任务各自为独立新组；link 一旦开启，新任务并入**前一条任务所在的组**（不论前一条自己当时开没开 link），随后每条都进这个组。

### 5.2 语义推演（示例）

设 `context_root_task_id` 为链根，相同链根即同组：

| 序 | link 开关 | 任务 | 前一条任务 | 链根 | 分组结果 |
|----|----------|------|-----------|------|---------|
| 1 | 关 | A | — | A | 新组 G1 |
| 2 | 关 | B | A | B | 新组 G2（关着就各组各的） |
| 3 | **开** | C | B | **B** | 并入 G2 |
| 4 | 开 | D | C | **B** | 并入 G2（链根沿用，不逐跳上跳） |
| 5 | **关** | E | D | **E** | 新组 G3（关 link 即切断） |
| 6 | **开** | F | E | **E** | 并入 G3 |

对照现状：第 3 步若前一条 B 是 `failed`，现有 SQL 直接跳过 B，导致 C 链根错误地回溯到更早的完成任务甚至自为链根 —— 这就是"各种状态都需要"要修的核心点。

### 5.6 关键决策

| # | 决策点 | 结论 | 依据 |
|---|--------|------|------|
| 1 | link 状态存哪 | **后端 `chat_sessions` 新增列** | 条款 6 要求以会话为键；铁规 1.5「后端为主，前端迎合后端」；只有后端能权威判定组边界。存前端 localStorage 会出现多设备不一致 |
| 2 | 切会话行为 | 每会话各自独立记忆 | 北京老陈定案 |
| 3 | 链根口径 | 最近一条任务，任意状态都算 | 北京老陈定案 |
| 4 | 组徽标 | 加 | 北京老陈定案 |
| 5 | 逐请求参数 `context_link_mode` | **废止删除**，不做兼容保留 | 会话状态成为唯一真源；保留双真源必然产生矛盾（前端说 linked、后端说 independent 时以谁为准无解）；且铁规明令「禁止 backward」 |

### 5.8 前端改造方案

#### 5.8.0 架构合理性论证（前后端整体）

**三层语义（互不矛盾、单一真源）**

| 层 | 载体 | 含义 |
|---|------|------|
| 真源 | `chat_sessions.link_enabled` | 会话当前开关，唯一权威 |
| 快照 | `chat_tasks.context_link_mode` | 任务启动那一刻的开关值（历史事实，**保留**，供遥测/展示） |
| 镜像 | 前端 `useChatState.linkEnabled` | 真源的只读镜像，随会话加载刷新 |

**最简链路（单向、无推演）**

```
点开关 → await PATCH /sessions/{id}/link → setLinkEnabled(后端返回值)   前端不猜
发消息 → 不带 mode → 后端读会话开关 → 算链根 → 装历史 → 落任务快照
```

**四点加固定案（以"简洁 + 不易错"为准绳）**

1. **竞态**：写路径取「服务端权威」——`await` PATCH 成功后再以**后端返回的** `link_enabled` 覆盖本地；失败保持原值。不乐观、不 pending、不留 UI 与库不一致窗口。
2. **链根口径**：`get_previous_task_chain` 取「会话最近一条任务（任意状态）」的链根。较原「仅成功任务」**少一个状态分支**，更简且更符合"组"语义（失败尝试亦属连续对话）。属**行为变更**，已确认。
3. **`context_root_task_id` 双取值**：落库=自身（independent 组由此天然成为自成一组的链根，前端分组所需）；传 `history_loader`=None（表"无链可沿"，不装历史）。同一字段两语境取值，是功能倒逼而非冗余，**不引入额外抽象**，以本文档标注固化。
4. **部署原子性**：本次删除请求级 `context_link_mode`，旧前端多发字段被 Pydantic `extra='ignore'` 静默丢弃 → 若后端先上线则续聊**静默失效**。**前后端必须同批原子发布**，不得滚动。

**简洁性自检**

| 关注点 | 方案 | 剩余出错点 |
|--------|------|-----------|
| 开关状态 | 后端权威，前端只镜像 | 无 |
| 链根判定 | 单判据（存在） | 无 |
| 字段取值 | 一字段两语境，自洽 | 文档标注 |
| 旧通道 | 全删，无双通道 | 部署须原子 |

**结论**：**一个真源 + 一次写 + 一次读 + 一个分组键，其余全删**——链路单向、无第二真源、无回读推演，符合系统设计基本原则。

#### 5.10.7 历史备份兼容（`lastContextLinkMode` 删除后的 `version=2` 备份）
