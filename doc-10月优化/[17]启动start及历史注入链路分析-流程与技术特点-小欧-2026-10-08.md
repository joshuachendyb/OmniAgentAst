## 一、链路总览

### 1.1 流程与逻辑

```
用户发消息
   │
   ├─▶ 先亮图标  emit thought-start        ← 不等任何数据, 先让用户看到"在动"
   │
   ├─▶ 取回历史只取本任务链范围内的, 不越链
   │
   ├─▶ 清洗    剔除越界消息 / 修补工具配对 / 剔除末条重复提问
   │
   ├─▶ 判断    历史 token > 窗口的一半 ?
   │     │
   │     ├─ 否 ──────▶ 直接用原文            快, 零 LLM 成本
   │     │
   │     └─ 是 ──────▶ 先降本  保尾区留原文, 更早的工具输出清零
   │                   └─▶ 调 LLM 生成锚定摘要   慢, 30~60s
   │                         └─▶ 失败或被取消 → 回退用原文(零退化)
   │
   ├─▶ 组装    [系统设定] + [摘要 或 原文] + [本轮问题]
   │
   ├─▶ emit 上下文概览首帧    反映压缩后的真实水位
   ├─▶ emit 任务契约
   │
   └─▶ 进入循环  每轮再亮图标; 裁剪时与每 5 轮刷新概览
```

**事件顺序**：thought-start → 上下文概览 → 任务契约

**这张图要说明的三件事**：

| 逻辑要点 | 图中位置 |
|---|---|
| 图标先亮、不等数据 —— 否则前端空窗 30~60s | 首行 |
| 超窗与否是**分支**，两条路都要能走通 | 判断处 |
| 概览帧在组装**之后**发 —— 否则读到压缩前水位 | 组装 → 概览 |

代码落点见 §1.3 表格与 §1.4。

### 1.4 两个关键事件的 emit 位置

#### 1.4.1 `thought-start` — 实时信号（第 1 发 + 后续发）

`ThoughtStartStep.TYPE = "thought-start"`，定义于 `steps/thought_start_step.py:10`。

| 发射点 | 代码位置 | step | 说明 |
|---|---|---|---|
| **第 1 发（前置）** | `agent_runner.py:604-605` | `1` | **在历史加载判断之前**发出，覆盖 DB 还原 + 压缩等待整段空窗 |
| 后续轮 | `handle_action.py:461` | 当前轮 | 4.4.2 第 2 发点，在 `thought` 前 |
| 后续轮 | `event_emitter.py:39 / 49 / 69` | 当前轮 | 三路事件发射器共用 |

**为什么第 1 发要前移**（`agent_runner.py:188` 注释 + `react_loop.py:12-14` 记原病根）：

> 旧 5 处发射点（`handle_action`×1 + `handle_answer`×4）均在 **LLM 响应之后**发（错），前端 waiting 图标时序错乱（obs 到即收 / 收尾轮误亮）。

前移后，`thought-start(step=1)` 在 `agent_runner.py:605` 落地，紧接着 `agent_runner.py:607-612` 才去加载会话历史 —— 所以**前端在 DB 还原与 30~60s 摘要等待期间已经有等待态图标**。

`handle_answer.py` 原 4 处已按 4.4.2 全部前移/删除（注释见 `handle_answer.py:41-42`）。

#### 1.4.2 `history_context` — 上下文概览帧

`MetaStep(type="history_context")`，构造器 `agent_telemetry.py:318 build_history_context_step(step)`。**DRY：提炼单一职责**，调用方只有两处。

| 发射点 | 代码位置 | step | 说明 |
|---|---|---|---|
| **首帧** | `react_loop.py:164-168` | `0` | 在 `publish start` **之前**；压缩与未压缩两种路径都发 |
| 后续更新 | `react_step.py:486` | `_llm_n`（当前 LLM 轮次） | 裁剪轮 / 每 5 轮更新水位 |

内容为 `agent_telemetry.py:332` 组装的 `MetaStep(step=step, type="history_context", content=_ov.get("summary"))`，其中 `injected_ratio` 为压缩率（注/装配口径）。

**为什么首帧要在 start 之前**（`react_loop.py:56-57` 注释）：

> 装配段前移: `init_history` + `inject_history` 从 emit start 之后移到之前, 使 `history_context` 首帧能读到**压缩后的真实水位**（压缩与未压缩两种路径都发）。

即：`init_history`(L158) → `inject_history`(L161/163) → `build_history_context_step`(L166) → `publish start`(L173) —— **顺序不可乱**。

#### 1.4.3 时序错误的后果（已修，勿回退）

| 错误时序 | 后果 |
|---|---|
| `thought-start` 在 LLM 响应后才发 | 前端 waiting 图标时序错乱：obs 到即收、收尾轮误亮 |
| `history_context` 在 `init_history` 前发 | 首帧读到的是**压缩前**水位，与真实 `conversation_history` 不一致 |
| `start` 在装配前发 | start 契约携带的 `context_summary` 与实际注入内容脱节 |

## 二、技术特点

### 2.1 特点一：「延迟建 conv」—— 全链路最关键的设计

`initialize_run_state.py:97` 明确写着：

> `此处不再 init_history 建 [system, task]; 推迟到压缩决策后由 react_loop 装配段建`

**为什么这是核心**：若 `init_history` 在初始化就建 `[system, task]`，则超窗判定时 `conversation_history` 里只有 task、**没有历史**，判定必然失真。2026-10-07 北京老陈把判定数据源从 `conversation_history` 改为 `_injected_history_msgs` 即为此（`start_step.py:152` 注释点明「零猜测」）。

**代价**：`init_history` 从 `initialize_run_state` 迁到 `react_loop:158`，破坏了「初始化即完整」的直觉，是当前设计里**最容易踩坑**的一点。

### 2.2 特点二：单一写入点 + 单一留存点

| 数据 | 存放位置 | 写入者 | 特点 |
|---|---|---|---|
| `_injected_history_msgs` | agent 属性 | `_build_injected_history` | **只留存，不进 conv** |
| `_start_summary` | agent 属性 | `_compact_injected_history` | 首行清零防异常残留上次值 |
| `conversation_history` | MessageBuilder | `react_loop:158/161/163` | **唯一写入点在装配段** |

**历史教训**：`_build_injected_history` 曾被误命名为 `_inject_conversation_history`（名字承诺会写 conv），导致历史被写两次 —— 「本阶段写 205 条，随后 `init_history` 清空再写」。改名 + 职责剥离是 2026-10-07 的核心修正。**函数名必须名实相符**（老陈铁律）。

### 2.3 特点三：FC 协议完整性是硬约束（三道防线）

| 位置 | 防护内容 |
|---|---|
| `history_loader._collect_turns:76-93` | 预扫 `observation` 建 `_obs_ids`，丢弃无配对的孤儿 `tool_call` |
| `history_loader._collect_turns:95-103` | 预扫 `action` 建 `_action_ids`，跳过孤儿 `truncated_output` observation |
| `start_step._build_injected_history:110-115` | `tool_calls` 逐元素 `isinstance(dict)`，非 dict 剥离，空则回退 content 分支 |

**第三道的病根**（值得单记）：DB 持久化的 `assistant.tool_calls` 若含非 dict 元素（截断/畸形 LLM 响应落库），原样回传致 provider **400**（`Can only get item item pairs from a mapping`）并触发 FC 降级 → `AgentStatus.FAILED`。

### 2.4 特点四：链范围而非会话范围（fail-closed）

`_load_previous_messages:211` 首行即短路：

```python
if not context_root_task_id:
    return []      # link 关即无链可沿: 从零不带历史, 防误灌
```

双边界才装历史，缺任一即 **fail-closed**（`:223`）：

```python
if _lower_id is None or upper_message_id is None:
    logger.warning(...)
    return []      # 原两种兜底都不安全(仅下界=自我回灌; 仅上界=越链灌入)
```

上界 `upper_message_id` 语义为 **`id < upper`（不含本任务 user 消息）**，对齐「本任务之前」。

### 2.5 特点五：还原忠实度 —— 按轮（step）分桶

`_collect_turns` 于 2026-10-07 重写：把原「全任务塌成一条 assistant」改为**按 step 分桶，每轮 assistant + 该轮 tool 交错展开**，最终答复独立成条。

同时补了 thought / reasoning 还原（`:62-74`），实测数据已写入注释：

```
thought 非空 8/48 共 200 字符, reasoning 非空 48/48 共 37754 字符
```

**理由**：原实现完全不读 thought step，还原出的 assistant 只有空 content，**模型看不到决策轨迹**。两字段分开存，与运行时 `message_builder` 的 assistant 结构一致（content + reasoning）。

### 2.6 特点六：SSE 时序 —— 三个事件的位置都是「血买来的」

**顺序**：`thought-start(step=1)`（`agent_runner.py:605`）→ `history_context(step=0)`（`react_loop.py:166-168`）→ `start(step=0)`（`react_loop.py:173-175`）。详见 1.3。

两条注释锁住顺序：

- `react_loop.py:56-57`：`装配段前移: init_history + inject_history 从 emit start 之后移到之前, 使 history_context 首帧能读到压缩后的真实水位`
- `agent_runner.py:188`：`thought-start 第1发前移到历史加载判断前(覆盖 DB还原+压缩等待)`

配套：`agent_runner` 把首个 `thought-start` 前移到历史加载判断之前 —— 实测摘要 await 30~60s，期间必须有等待态图标。

### 2.7 特点七：降级路径宽进严出

| 异常点 | 行为 |
|---|---|
| `context` 非 dict / 无 `previous_messages` | `_injected_history_msgs = []`，安全空转 |
| DB 查询异常 | `return []` + warning（不炸整批调用链） |
| 链边界缺失 | fail-closed 返回 `[]` |
| 摘要 await 失败 / 被取消 | 返回空串 → 调用方走 `else` 分支注入原历史（**零退化**） |
| 缺 `_start_meta` 或非 dict | `_build_start_contract` 返回 `None` 旁路 |

零退化的落点在 `react_loop:160-163`：

```python
if _summary:
    agent.message_builder.inject_history([{"role": "assistant", "content": _summary}])
else:
    agent.message_builder.inject_history(agent._injected_history_msgs or [])
```

**有摘要用摘要，没摘要用原历史**，两条路都成立。

## 三、值得称道的两点

### 3.1 token 口径全链同源

| 用途 | 实现 |
|---|---|
| 超窗判定 | `MessageBuilder._estimate_tokens` |
| 契约快照 | `_estimate_tokens` |
| Telemetry 基线 | `_estimate_tokens` |
| C3 裁剪 | `_msg_cost` → 复用 `_estimate_tokens` |

**全链没有第二处自算**。这正是 2026-10-08 把 `_msg_cost` 从 `len(content)/CHARS_PER_TOKEN` 改掉的原因 —— 原口径漏算 `assistant.tool_calls` 结构开销（实测决策消息 0 vs 41），致 budget 约束不准（`budget=2000` 实测输出 10245 tok）。

### 3.2 降本与保真做了显式取舍

摘要前降本采用「保尾保留 + 旧轮 tool 清零」（`[16]` 第二章）：真实 205 条实测 feed `135362 → 86472 tok`（省 36%），摘要 2048 字符且保住可核对的具体数字/签名/时间戳；纯全清零版虽省到 83673 tok，但摘要仅 1521 字符且**失掉工具输出证据**。

## 四、风险与建议（不擅自改动，供裁定）

### 4.1 风险一：摘要路径下不注入原历史，无兜底

压缩后 `conversation_history` = `[system, 摘要, task]`，原历史**全部丢弃**。

- 若摘要质量差（模型幻觉 / 漏段），**没有任何兜底**能救回
- 实测六段 6/6 是「当前模板 + `_SUMMARY_TAIL_USER` 收尾指令」的结果，**非结构性保证**

> `_SUMMARY_TAIL_USER` 的引入缘起（`summary_prompt.py` 头部编辑历史）：注入历史末条是 assistant，摘要 feed 以 assistant 收尾构成半截对话 → 模型按对话补全续写而非汇总，**实测六段命中率仅 16%**；末条补 user 请求后 **6/6 = 100%**。

**建议（若加固）**：摘要路径下保留最近 1~2 轮原文作为「近期锚」，而非纯摘要。

### 4.2 风险二：增量摘要的「旧声称残留」

`generate_chunked_summary` 实测（2026-10-08，完整数据见 `[16]` §2.5 与 §2.5.1）发现：

| 版本 | `Key Decisions` 段 | `Progress` 段 |
|---|---|---|
| 全量 `anchored` | 已含更正（实际 3066 份） | 已含更正 |
| 增量 `chunked` | **残留旧声称（158 份）** | 含「更正自声称的 158」✅ |

即：增量合并能正确覆盖前段错误结论（Progress 已更正），但**同一份摘要内两处口径不一致**。全量版无此问题（重新生成）。

另据 `[16]` §2.5 结论：单次压缩场景两段式合计 feed 9305 tok，比全量 7220 **贵 29%**、多一次 LLM 调用，故该函数**暂不接入**。

**风险叠加**：4.1 已无原历史兜底，若再叠加增量压缩，摘要一致性需**成对校验** `Key Decisions`（旧声称残留）与 `Progress`（更正记录），不能只看 Progress。
