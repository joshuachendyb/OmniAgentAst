## 一、需求定义

### 1.1 一句话说清

把输入框下方按钮行里那个置灰的「📎 附件」按钮变成真正能用的功能：**用户从电脑任意位置选一个文件（或直接粘贴截图），文件进入会话事务区，AI 能读它、能加工它、能基于它产出新文件；历史会话随时能找回来接着用。**

### 1.2 用户已拍板的三条

| 决策项 | 结论 |
|---|---|
| 功能方向 | **要做** |
| 落盘位置 | **会话事务区「默认创建的目录」里面**（即会话默认工作区，见 3.2；不是我最初提的 `~/.omniagent/uploads`） |
| 五项能力取舍 | ① ② ③ ⑤ **开发**；④ 是**现有引用区**（已实现），本次**零改动**；**不要透明注入** |

### 1.3 五项能力定义（含本次是否开发）

| # | 能力 | 是什么 | 用户得到什么 | 本次 |
|---|---|---|---|---|
| ① | **附件入账** | 附件不复制到云端，而是落进**会话默认工作区**，之后就是会话里的一个文件 | 文件在自己机器上、会话里一直找得到 | ✅ 开发 |
| ② | **进流水线** | 附件不只是「给 AI 看一眼」，Agent 可以对它跑工具：读、写、执行、比对 | 「分析这份数据并出图」→ AI 真的跑出图来 | ✅ 开发（落盘位置的附带收益，见 3.2） |
| ③ | **双向流动** | AI 产出的结果，可一键「存为附件」：工作区外的复制固化，工作区内的直接引用 | 临时目录里的产物不会用完就丢，工作区内的不重复占盘 | ✅ 开发（S4，范围小） |
| ④ | **统一上下文物件** | 文件、目录、选区、截图、命令输出，都是同一类「上下文物件」，可以混着给 | 一条消息里能同时给 CSV + 代码段 + 报错图 | ⛔ **现状，零改动**（现有引用区已实现，见 3.4） |
| ⑤ | **素材包** | 一组文件 + 一个名字 + 一句说明（可归组），存 DB，下次一键投喂 | 「月度报表」一点就齐 | ✅ 开发（S4） |

### 1.4 明确不做（YAGNI 边界，防过度设计）

| 不做项 | 理由 |
|---|---|
| 透明注入（原方案剔除项） | 用户明确不要 |
| 云存储 / 跨机器同步 | 本地优先，系统一贯风格 |
| 自动扫描用户磁盘找文件 | 安全与体验都不成立 |
| OCR（图片转文字） | 预留插槽，首期不做 |
| 图片真实视觉理解 | 当前模型无视觉能力，只做能力探测预留（见 3.8） |
| 桌面端（Electron）零落盘路径直引 | 将来前端换成桌面应用时再开，架构留口 |
| 产物版本管理（同名多次归档留历史） | 只做单次固化；要留版本由用户在文件页另存（YAGNI） |
| 素材包内复制文件 | 只存引用清单；复制会产生同名多份、磁盘翻倍（见 3.7.1） |

## 二、现状与可复用能力

设计原则：**能复用的一律复用，真正新增的只有两段——「上传 / 落盘 / 抽取」与「素材包 CRUD」；② 靠落盘位置天然获得，③ 复用附件表与引用链路。**

| 管道环节 | 现有实现 | 附件如何复用 |
|---|---|---|
| 引用入队 | `composerRefStore` / `quote.ts` | 附件上传成功后入同一队列，`kind='attachment'` |
| 发送闸门 | `refreshRefs` + `pending` 阻断 | 附件上传中同样阻断发送（同构） |
| 上行载荷 | `buildStreamBody.refs` | 零改动，附件就是一条 ref |
| 越界过滤 | `sanitize_refs`（根内相对路径 + 外部盘符放行） | 附件在项目根内 → 走相对路径分支 |
| 注入渲染 | `_render_refs_block` + `_FILE_REF_RULES`（不可信数据边界） | `_REF_KINDS` 加一个 `attachment` 即可 |
| **默认工作区标志** | `chat_session_workspaces.is_default=1` + `get_session_default_workspace`（[54] §2.8 创建时机与默认工作区） | **附件区地基**：`{默认工作区}\attachments\`；只读标志，不做目录名识别 |
| 文件类型真源 | `probe kind`（text / image / none） | 三通道分流直接调用，不另写判定 |
| 图片预览 | `read_image_file`（10MB 上限） | 图片附件预览直接复用 |
| 外部文件读取 | `read_external_file` | 选文件场景的兜底读取通道 |
| chip 渲染 | `FileRefChip` / `FilePathLink`（本轮刚补图钉引用） | 附件 chip 复用同一套渲染与引用按钮 |
| 素材包雏形 | `quotePack`（把一组文件压成**一条** ref） | **不复用**：素材包要保留一组独立 chip 与分组，投喂逐个 `quoteFile`（见 3.7.3），quotePack 只作"打包成一条"的既有能力保留 |

## 三、总体设计

### 3.1 数据流全景（五项能力落在哪一环）

```
用户操作：选文件 / 拖拽 / 粘贴截图
        │  浏览器只给「内容」，不给磁盘路径（安全限制）
        ▼
① 附件入账 ── POST /api/v1/attachments/upload
        │  落盘 → 计算 sha256 → 按类型判定（text / image / 富格式 / 超大）
        ▼
{默认工作区}\attachments\{时间戳}_{哈希前8位}_{安全文件名}
        │  登记 attachments 表（会话级持久）
        │  ← 文件页可见；在默认工作区白名单内（② 的地基）
        ▼
返回附件记录（`stored_path` 绝对路径为真源）→ 前端以**项目根内相对路径**入队 composerRefStore
        ▼
④ 统一上下文物件（**现状，不改**）── 引用区里三类 chip 并列：
                    📎 附件 chip    📄 文件引用 chip    ✂️ 选区 chip
        │  发送（上传/抽取未完成时阻断）
        ▼
refs 随消息上行 → sanitize_refs → _render_refs_block
        ▼
三通道注入 → LLM（全文 / 抽取文本 / 档案卡 + 工具深读）
        │
        ▼
② 进流水线 ── Agent 在工作区白名单内直接读写附件区文件
              读 / 写 / 执行 / 比对（零额外授权）
        │
        ▼
产物写回会话工作区 → 回答里 [[文件:...]] 给可点路径
        │
        ▼
③ 双向流动（存为附件）── 概览产出物行点「存为附件」，服务端判定：
        │  工作区外 → 复制进 attachments/ + 登记（固化）
        │  工作区内 → 不复制，直接加入引用（省一次点击，不重复占盘）
        ▼
⑤ 素材包 ── 一组文件 + 名称 + 说明 + 分组（存 DB），下次一键投喂
```

**能力 → 链路环节对照表**（配合 5.1 的界面位置一起看）：

| # | 能力 | 发生在数据流的哪一环 | 界面上的入口 |
|---|---|---|---|
| ① | 附件入账 | 上传 / 落盘 / 登记 | 按钮行左侧「📎 附件」（输入框下方那行） |
| ② | 进流水线 | Agent 执行阶段 | 无按钮（发消息后自然发生）；正文执行步骤 + 产物落工作区 |
| ③ | 双向流动 | 产物回流（服务端判定复制或直接引用） | 概览统计块产出物行「存为附件」按钮 |
| ④ | 统一上下文物件 | 引用区（**现状，本次不改**） | 输入框上方引用区（三类 chip 并列） |
| ⑤ | 素材包 | 组织 / 投喂 | 按钮行右侧「素材包」按钮（发送钮左边，S4） |

### 3.2 核心概念：附件 = 会话事务区里的一个文件 + 一条 ref

- **附件目录**：`{默认工作区}\attachments\`
  （默认工作区 = `chat_session_workspaces.is_default=1` 那一行；下文统一用「默认工作区」）
- **默认工作区**（既有规则，不新增概念）：`{项目根}\{YYYYMMDD-HHMMSS}-{会话ID前4位}`
  例：`E:\test_dir\20261028-174021-89bc`

- **附件解析规则**（唯一函数，单点实现）：

  ```
  ensure_session_attachment_dir(session_id):
    1. 读默认工作区标志：get_session_default_workspace(conn, session_id)
       → chat_session_workspaces 中 is_default = 1 的那一行（唯一真源，见 [54] §2.8.5）
       ⚠ 禁止用「目录名长什么样」来识别（用户裁定）：时间戳/会话前缀会变、用户可换盘符，
         正则一旦对不上就会每轮新建一个目录，且与标志真源分叉。
    2. 有标志行 → 直接用它
    3. 无标志行（首次进入 / 用户删掉了默认工作区 / 项目根已变）→ 调 reconcile_session_workspaces：
       它按 [54] §2.8.1 决策①「始终创建」补建默认工作区并置 is_default=1（幂等）；
       附件侧只消费标志，**不自建目录、不猜目录名**
    4. 建 {默认工作区}\attachments\ 子目录（exist_ok=True）
    5. 返回绝对路径
  ```

- **为什么必须放在项目根内**（这是本设计最重要的地基决策）：
  | 收益 | 说明 |
  |---|---|
  | 安全白名单天然覆盖 | 默认工作区在 `WorkspaceSnapshot.all_paths` 里，子目录前缀匹配自动生效，零安全改动 |
  | 工具可读写 | Agent 的 file 工具在项目根/工作区内直接可用，附件真能进流水线（能力②） |
  | 现有链路零改造 | 文件页深链、图片预览、chip 渲染、引用图钉全部原样可用 |
  | 用户可见可管理 | 用户在文件页就能看到附件目录，不是黑盒 |

### 3.3 附件生命周期

| 阶段 | 动作 | 说明 |
|---|---|---|
| 上传 | 内容 → 落盘 → 登记 → 返回记录 | 前端拉 `/text` 取注入文本后入队，chip 出现 |
| 待发 | 用户可删除、可预览 | 不上传成功不显示 chip（上传中显示进度态） |
| 发送 | 随 refs 上行，后端渲染注入 | 正文当轮消费，路径长期有效 |
| 历史 | 会话里随时可点开、可再引用 | 附件目录持久保留（**用户已拍板：持久**） |
| 删除 | 用户显式删除附件（可选同时删磁盘文件） | 默认只删记录不删磁盘，防误删 |

### 3.4 统一上下文物件模型

`refs.kind` 扩展表（首期只落地 attachment，其余为预留，YAGNI）：

| kind | 语义 | 来源 | 首期 |
|---|---|---|---|
| `file` | 整文件 | 文件页 / 足迹 / chip 图钉 | ✅ 已有 |
| `selection` | 行区间选区 | 正文选区引用 | ✅ 已有 |
| `attachment` | 上传的附件 | 📎 按钮 / 粘贴 / 拖拽 | ✅ **本次新增** |
| `snippet` | 命令输出片段 | 执行步骤「引用输出」 | ⬜ 预留 |
| `web_snapshot` | 网页快照 | 抓取工具产物 | ⬜ 预留 |

**关键**：注入层与 `file` 完全同构（都渲染成【引用N】），差别只在来源标记与档案字段——这正是「统一对象」的含义：**一类东西，一个区，同一个注入管道**。

> **④ 是现状，不是本次开发项**：现有 `refs`（`kind=file` / `selection`）已经把「文件 / 选区」统一建模，附件只是新增 `kind=attachment`；目录 / 截图 / 命令输出等在 3.4 表里是预留位。结论：本次只加一个 kind，不新建体系、不改引用区交互。

### 3.5 三通道注入策略（按类型分流）

| 类型 | 判定依据 | 注入给模型的内容 |
|---|---|---|
| 文本 / 代码（≤256KB） | `probe kind = text` | **全文**（当轮引用，不截断） |
| PDF / docx / xlsx | 后缀白名单 | 后端抽取文本（标注来源页码/工作表），原件保留可深读 |
| 图片 | `probe kind = image` | **档案卡**：路径 + 尺寸 + 格式 + 大小；并明示「当前模型无视觉能力」 |
| 超大文件（>256KB） | 文件大小 | **档案头**：元数据 + 前 40 行预览 + 总行数；Agent 用 file 工具深读 |

> 两个边界：① 富格式抽取出的文本若 >256KB，同样降级为档案头（与文本超大一视同仁）；② 用户在正文里写的说明（如「这张图是报错截图」）本身就是消息文本，自然进入上下文，**不需要也不该塞进档案卡**（档案卡由服务端生成，拿不到正文）。

设计意图（「电梯陈述 + 图书馆借阅」）：小文件一次讲完，大文件先给目录卡片，需要哪页再翻——**prompt 预算永远可控**。

所有附件注入沿用现有「不可信数据」边界声明（附件内容里的文字不得改变模型行为）。

### 3.6 双向流动（能力③：存为附件）

| 方向 | 实现 |
|---|---|
| 附件 → AI | 3.5 三通道注入（附件进上下文） |
| AI → 附件区 | 概览统计块（`StaticStatsBlock`）产出物行「存为附件」：工作区外 → 复制进 `attachments/` + 登记；工作区内 → 不复制、直接加入引用 → 两种情况都立刻成为可引用 chip |

**点下去两种结果（服务端判定，前端不判工作区）**：

| 产物位置 | 点击结果 | 理由 |
|---|---|---|
| 工作区外（`C:\Temp`、旧项目根、别的盘） | 复制进 `attachments/` + 登记 → toast「已存为附件」→ 自动加入引用区 | 这类路径随时可能被清理/改名，复制进附件区才是"不会用完就丢" |
| 会话工作区内（默认工作区 / 用户加的目录） | **不复制**，直接加入引用 → toast「已在会话工作区，已为你加入引用」 | 已在白名单内且持久保留，再复制纯属重复占盘 |
| 文件已不存在 | 按钮禁用，tooltip「产物已不存在」 | 不给假动作 |

- **为什么按钮不做条件显示**：前端要判"在不在工作区"，就得再取一份工作区状态并保持同步（多一处失效面）；而且隐藏按钮＝用户不知道有这个能力。统一显示、点后由服务端给结论，只有一条代码路径（KISS-DIRECT）。
- **命名取舍**：原叫「收为素材」，与能力⑤「素材包」撞词，用户直接看不懂两者区别 → 按钮改叫「**存为附件**」（动作即结果：存进附件区）。⑤ 仍叫素材包。
- **与 ⑤ 的边界**：③ 复制文件、范围是本会话；⑤ 只存清单、范围是全局；③ 的产物是普通文件，可被 ⑤ 打包，但 ⑤ 不依赖 ③。

### 3.7 素材包（能力⑤）

**定位**：把「一组文件 + 名字 + 一句说明（可归组）」存成可复用的投喂单元，**跨会话**可用（月度报表、排障资料本来就是反复用的）。

#### 3.7.1 存什么（DB 真源，两张表）

| 表 | 字段 | 说明 |
|---|---|---|
| `material_packs` | `id` / `name` / `note` / `group_name` / `created_at` / `updated_at` | `name` 唯一（COLLATE NOCASE，防同名混淆）；`group_name` 空串 = 未分组 |
| `material_pack_items` | `pack_id` / `seq` / `path` / `label` | 顺序 = 保存时引用区顺序；`path` 与引用同口径（项目根内相对 / 盘符绝对） |

- **分组不建表**：`group_name` 自由文本 + 新建时给「已有分组」下拉建议（combobox）。分组只是标签，为它建第三张表要 JOIN + 级联清理，收益不成立（KISS/YAGNI）；下拉建议已能收敛拼写。
- **只存清单、不复制文件**：素材包是"引用清单"，文件留原位（含 `attachments/`）。复制会让同名多份、磁盘翻倍，且改一处另一处立刻成旧档。

#### 3.7.2 长什么样（形态：Popover 面板，不是弹窗/抽屉）

| 项 | 设计 |
|---|---|
| 载体 | **Popover 432px**，贴「素材包」按钮右上方弹出；点外部即关，关掉就看见引用区 chips |
| 为什么不用 Modal / Drawer | 这一步是"往输入框填东西"，不是管理工作台。Modal/Drawer 会把会话内容挡在后面、且投喂完还要手动关，等于多一次点击 |
| 面板①顶部 | 搜索框（包名 / 说明 / 文件名，本地过滤）+ 分组筛选（全部 / 各分组） |
| 面板②列表 | 分组折叠区（默认全展开）→ 包行：名称 + 文件数徽标 + 说明（单行省略，hover 全量）+「投喂」主按钮 +「…」菜单（重命名 / 编辑说明 / 移分组 / 删除） |
| 面板③底部 | 「＋ 存为素材包（当前引用区 N 个）」；N = 0 时禁用并提示「引用区为空，先引用文件再存包」 |
| 新建/编辑 | **就地展开表单**（名称 / 说明 / 分组 combobox），不叠第二层弹窗；重名在输入框内联报错「已有同名素材包」 |

#### 3.7.3 怎么用（三个动作）

| 动作 | 步骤 | 结果 |
|---|---|---|
| 存包 | 引用区备好文件 → 点「素材包」→ 底部「＋ 存为素材包」→ 填名称/说明/分组 → 保存 | 面板里立刻出现该包；引用区不变 |
| 投喂 | 点包行「投喂」 | 逐个 `quoteFile` 入队 → 面板自动关闭 → 引用区出现 chips（已有同 path 引用按 `refKeyOf` 去重合并） |
| 维护 | 「…」菜单：重命名 / 改说明 / 移分组 / 删除包 | 删除只删包记录，**不动磁盘文件**（与附件删除同口径） |

#### 3.7.4 容量与失效

| 项 | 规则 |
|---|---|
| 单包文件数 | ≤10（与 4.5「单轮 ≤10」同口径） |
| 包总数 | ≤200（超限提示清理旧包） |
| 投喂容错 | 逐条读，失败跳过并汇总 toast：「已入队 8/10，2 个已失效：a.log、b.png」——**不让一个旧路径毁掉整包** |
| 失效展示 | 包行展开可见每个文件；已失效的置灰并给「移除该文件」，避免反复失败 |
| 发送闸门 | 投喂后照旧由现有 `refreshRefs` 兜底（invalid 红底 + 阻断），素材包不自建状态机 |

#### 3.7.5 典型场景

| 包名 | 内容 | 使用节奏 |
|---|---|---|
| 月度报表 | 3 个模板 + 1 份口径说明 | 每月新会话一键投喂 |
| 排障资料 | 日志 + 复现脚本 + 报错截图 | 遇到同类问题直接开问 |
| 项目交接 | 架构图 + 关键配置 + 目录说明 | 换人/换机时一次带走 |

### 3.8 模型能力探测（视觉预留，不返工）

- 后端 `model_meta.input_modalities` 已存在（当前 `agnes-2.5-flash` 为 `[]`，无视觉）；
- 图片附件的 ref 载荷同时携带 `path + mime + size`；
- 视觉升级点只在**消息 parts 组装层**（非 `_render_refs_block`，该函数保持纯渲染）：模型含 image → 附件 ref 转 `image_url` parts；不含 → 直接用服务端生成的档案卡文本；
- 结论：附件系统一次建成，将来换视觉模型**只动 S5 这一处**，前端与存储零改造。

## 四、后端设计

### 4.1 端点清单（附件既有 5 个 + 本次新增 5 个）

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/attachments/upload` | 上传（multipart：session_id + file），返回附件记录 |
| GET | `/api/v1/attachments?session_id=` | 会话附件列表 |
| GET | `/api/v1/attachments/{id}` | 单条附件详情（发送前存在性校验用，见 5.4） |
| DELETE | `/api/v1/attachments/{id}` | 删除记录（`?purge=true` 才删磁盘文件） |
| GET | `/api/v1/attachments/{id}/text` | 按 3.5 生成**注入文本**（前端入队前取用；也供预览与二次引用） |
| POST | `/api/v1/attachments/collect` | ③ 存为附件（body：session_id + source_path）→ 返回 `mode=copied\|referenced` + 相对路径（见 3.6） |
| GET | `/api/v1/material-packs` | ⑤ 素材包列表（含 items；分组/搜索在前端过滤） |
| POST | `/api/v1/material-packs` | ⑤ 新建包（name 唯一冲突 → 409，前端内联报错） |
| PATCH | `/api/v1/material-packs/{id}` | ⑤ 改名 / 改说明 / 移分组 / 改清单（整包覆盖 items，事务内先删后插） |
| DELETE | `/api/v1/material-packs/{id}` | ⑤ 删包（级联删 items，**不动磁盘文件**） |

### 4.2 服务层（新增 `app/attachments/` + `app/material_packs/`）

| 模块 | 职责 |
|---|---|
| `service.py` | 唯一业务入口：`save_upload` / `list_attachments` / `delete_attachment` / `ensure_session_attachment_dir`（目录只从 `get_session_default_workspace` 取，无标志则触发 reconcile，不猜目录名） |
| `extract.py` | 抽取器：`text` 直读 / `pdf`（pypdf）/ `docx`（python-docx）/ `xlsx`（openpyxl）/ 其他 → 档案卡 |
| `collect.py`（③） | `collect_artifact(session_id, source_path) -> {"mode": "copied" \| "referenced", "path": 相对路径}`：不在工作区 → 复制 + 登记（copied）；已在工作区 → 不复制、只回相对路径（referenced）。判定在后端一处，前端不做工作区判断 |
| `app/material_packs/service.py`（⑤） | 素材包 CRUD：`list_packs` / `create_pack` / `update_pack` / `delete_pack`；唯一约束冲突转 409；items 与包同事务写 |

铁律：
- 存储路径**只由服务端计算**，绝不接受客户端指定路径（防穿越）；
- 文件名 sanitize：去路径分隔符、控制字符、Windows 保留名、首尾空格与结尾点；
- 落盘失败必须清理半成品文件（不留垃圾）。

### 4.3 数据库表

```sql
CREATE TABLE IF NOT EXISTS attachments (
  id            TEXT PRIMARY KEY,          -- uuid
  session_id    TEXT NOT NULL,
  original_name TEXT NOT NULL,             -- 用户原文件名（仅展示）
  stored_path   TEXT NOT NULL,             -- 绝对路径（唯一真源）
  mime          TEXT NOT NULL,
  size          INTEGER NOT NULL,
  sha256        TEXT NOT NULL,             -- 去重 + 完整性
  kind          TEXT NOT NULL,             -- text | image | richdoc | binary
  extract_status TEXT NOT NULL DEFAULT 'none', -- none | pending | done | failed
  extract_chars INTEGER NOT NULL DEFAULT 0,
  source_path   TEXT,                      -- ③ 存为附件时的来源产物路径（上传为空，仅溯源展示）
  created_at    TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_attachments_session ON attachments(session_id);
CREATE INDEX IF NOT EXISTS idx_attachments_sha ON attachments(sha256);

-- ⑤ 素材包：只存引用清单，不复制文件
CREATE TABLE IF NOT EXISTS material_packs (
  id          TEXT PRIMARY KEY,                    -- uuid
  name        TEXT NOT NULL COLLATE NOCASE UNIQUE, -- 包名唯一，防同名混淆
  note        TEXT NOT NULL DEFAULT '',            -- 一句说明
  group_name  TEXT NOT NULL DEFAULT '',            -- 分组；空串 = 未分组（不建分组表）
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS material_pack_items (
  pack_id  TEXT NOT NULL,
  seq      INTEGER NOT NULL,                       -- 顺序 = 保存时引用区顺序
  path     TEXT NOT NULL,                          -- 与引用同口径：项目根内相对 / 盘符绝对
  label    TEXT NOT NULL DEFAULT '',
  PRIMARY KEY (pack_id, seq),
  FOREIGN KEY (pack_id) REFERENCES material_packs(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_pack_items_pack ON material_pack_items(pack_id);
```

### 4.4 注入链路改动（最小集）

|---|---|

| `backend/app/api/v1/chat/models.py`（ChatRef） | 增加可选字段 `mime`、`attachment_id`（加法，无兼容开关）；`kind` 描述补 `attachment` |

| 消息 parts 组装层 | **仅 S5**：`input_modalities` 含 image 时把附件 ref 转 `image_url` parts；首期零改动 |

### 4.5 安全与配额

| 项 | 规则 |
|---|---|
| MIME 白名单 | 图片（png/jpg/jpeg/gif/webp/bmp）、文本/代码后缀、pdf、docx、xlsx、csv、json、md |
| 单文件上限 | 图片 10MB（对齐现有 `MAX_IMAGE_BYTES`）；其他 20MB |

### 5.3 状态管理（复用，不新建 store）

- 上传成功后拉 `GET /attachments/{id}/text`，取**服务端按 3.5 生成的注入文本**（文本=全文 / 富格式=抽取文本 / 图片=档案卡 / 超大=档案头），再 `composerRefStore.push({ kind:'attachment', path: 相对路径, mime, size, content: 该文本, lineRange: null })` —— 注入正文**只有一个产生点（服务端）**，前端不拼（DRY；也保证永不走样）；
- 上传进度态放组件局部 state（不进 store）；
- 发送成功清引用（沿用现有 `clear`）。

### 5.4 发送闸门与失效校验

- 上传未完成 → 与 `refsPending` 同款阻断；
- `refreshRefs` 对 `kind='attachment'` **不重读正文**（二进制读不了），改调 `GET /attachments/{id}` 做存在性校验；
- 文件被删 → 标 `invalid`（红底 + 点名），阻断发送（与引用完全同款语义）。

### 5.5 错误文案（沿用既有 ErrorType 通道）

| 类型不支持 | 该文件类型暂不支持（支持图片、文本、PDF、Word、Excel） |
| 超限 | 文件超过大小限制（图片 10MB / 其他 20MB） |
| 上传失败 | 附件上传失败，请重试 |
| 文件已删 | 附件已失效，请在引用区移除后再发送 |
| 存为附件失败（③） | 保存产物失败，请重试 |

## 八、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 用户切换项目根 | 旧附件相对路径失效 | 存绝对路径为真源；发送时按当前根相对化，失败退化为绝对路径（外部引用口径） |
| 会话全自定义目录（无默认工作区） | 附件区无处落 | 调 `reconcile_session_workspaces` 按 [54] §2.8.1 决策①「始终创建」补建并置 `is_default=1`（幂等）；面板会多一条系统目录 |
| 大文件撑爆 prompt | 上下文超限 | 档案头策略 + 单文件大小上限 + 会话总量配额 |
| 模型无视觉 | 图片「问不出东西」 | 档案卡明示能力边界，不装假；视觉模型到位自动升级 |
| 附件内容含提示注入 | 模型被误导 | 沿用「不可信数据」边界声明（现成机制） |
| 磁盘膨胀 | 长期占用 | 会话总量上限 + 删除入口 + （后续）历史清理策略 |
| 素材包内路径失效 | 投喂时读不到 | 投喂逐条容错 + 汇总提示 + 包行标灰可「移除该文件」；发送闸门仍由 `refreshRefs` 兜底 |
| 素材包与附件重复占空间 | 磁盘翻倍 | ⑤ 只存清单不复制（见 3.7.1）；③ 只对工作区外产物复制，工作区内直接引用（见 3.6） |
| 「存为附件」被误当版本管理 | 需求膨胀 | 明确不做版本（1.4）；改名版本需求由用户在文件页另存 |
