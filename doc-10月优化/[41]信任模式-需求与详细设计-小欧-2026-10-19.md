## 一、需求要点清单

### 1.1 背景

当前 HITL（人工确认）弹窗提供「信任此操作（本次会话）」勾选项：勾选后该工具+路径被写入会话级信任表 `chat_session_trust`，**同一会话内**后续同类操作免弹窗（受 TTL 约束，默认 90 天）。该信任寿命与"会话"绑定，跨任务、跨轮次长期有效，但**跨会话互不可见**（`check_session_trust` 硬过滤 `WHERE session_id=?`，`trust_db.py:192`）。

北京老陈要求在该机制之上提供**可切换的信任作用域**，分三级：

- **会话级（session）**：即现状。信任在同会话内持久（受 TTL 约束）。
- **任务级（task）**：信任只在**本任务所属的「上下文链」内**有效；离开该链（发起新的独立任务）后同类操作重新弹窗。
- **全局级（global）**：**新增**。信任对所有会话生效（跨会话自动继承），是「会话 A 的信任清单被会话 B 继承」的通用解。

> **「任务」的口径（北京老陈 2026-10-19 裁定）**：任务级 = 本任务 **及其 link 续聊的任务链（组）**。
> 系统已有「上下文链」概念：`chat_tasks.context_root_task_id` 即链根——
> 独立任务 `root=自身`；link 续聊的任务并入上一任务所在组、`root=组根`。
> 故「任务级」以 **链根（`context_root_task_id`）为隔离键**：
> link 开启时，同一链内多个任务共享任务级信任（一条链＝一个「任务」）；
> link 关闭时，每个任务自成一链（退化为「仅本单个任务」）。

模式切换入口有两处：① 配置项（全局默认）；② 输入框底部功能行的开关（会话级覆盖）。

> **覆盖边界**：输入框开关只有三档（session/task/global），**不提供「跟随配置」档**。会话一旦显式选定，后续配置默认值变更不再影响该会话（显式覆盖优先）；如需回到配置语义，只能手工再选一次与配置相同的档位（落库后仍是显式值）。

此外，北京老陈要求提供**跨会话信任继承**（会话 A 的信任清单可被会话 B 使用），采用**两条路径并存**：

- **路径 G（全局级别）**：把信任作用域放宽到"全局"，授权对**所有会话**自动生效（含 A→B 及将来所有会话）。
- **路径 C（一次性导入）**：提供「把会话 A 的信任清单一次性复制进会话 B」动作，作用域仍限会话级，只是手动拷贝。

除上述作用域与继承外，总体需求还包含三条**贯穿性约束**：

- **任务级信任可查看/逐条撤销**：`TrustPanel` 提供「任务级信任」分组（v1.4 补做，R13）。
- **TTL 统一约束**：会话级、任务级、全局级三者均写 `expires_at` 并周期回收，到期自动失效（R12/R14）。
- **确认即锁定范围**：HITL 确认落库以弹窗此刻显示的档位为准（显示=上送=落库），弹窗存续期间切换底部开关不会改变本次授权的落表（D-11/R16）；落库同时回写会话列，刷新后开关与最后一次授权一致（D-14）。

| R16 | **确认携模落库**（v1.8 补，D-11） | `POST /chat/stream/confirm` 携带 `trust_mode`（弹窗显示值）；`save_trust` 优先按上送值分流，非法/缺省才回落读列，保证「显示=上送=落库」；**同事务回写 `chat_sessions.trust_mode`**（D-14），刷新后开关与最后一次授权一致 |

### 1.3 关键设计决策（已与北京老陈确认）

| 决策 | 结论 |
|------|------|
| D-1 任务级信任的存储与隔离键 | 另建表 `chat_task_trust`，以**链根 `context_root_task_id`** 为隔离键（**非**单个 `task_id`）；一条 link 链＝一个"任务"。不与 `chat_session_trust` 共用 |
| D-2 开关作用域 | **每会话覆盖（L2）+ 配置为全局默认（L1）**；生效值 = 会话列 ?? 配置 ?? `'session'`——该公式**仅用于展示与新授权的落表默认**：不参与查询过滤（见 D-4），不覆盖确认上送值（见 D-11）；开关三档**无「跟随配置」档**，显式选择永久覆盖配置默认 |
| D-3 粒度 | **与会话级一致**：目录收敛（`trust_scope_path`）+ 前缀递归匹配，三域共用同一套路径归一口径 |
| D-4 模式对已有信任的影响 | **越宽的信任越应默认生效**：`resolve_skip` **三域恒查**（全局 → 会话 → 任务，任一命中即免弹窗），**任何模式下三张表都查**——模式仅决定"新授权落哪张表"，不改变任何既有信任的效力（v1.4 修订：原「任务表仅 mode=task 时查」与本决策自相矛盾，且 `chat_task_trust` 为新表、存量 session 用户查询必为空集，恒查零行为变化，见 2.4 论证） |
| D-5 开关上送通道 | **随消息携带**（与 `link_enabled`/`allow_interject` 同契约），不新增独立 PATCH 端点 |
| D-6 HITL 弹窗是否需要后端下发模式 | **不需要**。模式随消息落会话列（该列只是**缺省/回退值**，非权威源）；前端本地镜像同步，弹窗按本地值显示文案；确认时前端上送该值（D-11），落库后回写会话列（D-14） |
| D-7 全局信任的定位 | 新增第三档作用域 `mode=global`；**全局信任不设"危险工具"特判** —— 北京老陈 2026-10-19 明确：**能进「信任清单」的本就是风险项目**，信任机制天然作用于风险操作，故 file/shell/注册表/SQL **一律可全局授权** |
| D-8 跨会话继承并存两路 | 路径 G（全局级别，自动继承）+ 路径 C（A→B 一次性导入）**两者都做**；导入只复制**未过期**的会话级行（`expires_at IS NULL OR expires_at > now`），**保留源 `expires_at` / `task_id`**（不续期）、`ON CONFLICT DO NOTHING` 幂等；不复制全局行（本就跨会话可见）与任务级行（链隔离，R13 明确不做） |
| D-9 全局信任撤销 | **独立「全局信任管理」面板**（查看 + 逐条撤销）；不能靠"删会话"撤销（全局行无会话归属）。任务级撤销与删会话清理的不同处理见 D-13 |
| D-10 生效模式解析的落位 | 单源置于 `app/safety/trust_db.py`（安全层）；`services` 层反向 import（**services→safety 合法**，`trust_db` 先例 `norm_trust_path` 同向），使 `resolve_skip` 无需越层 import services |
| D-11 授权落库以确认请求上送值为准（v1.4 新增） | `POST /chat/stream/confirm` 携带 `trust_mode`（= 弹窗文案此刻显示的前端值），`save_trust` **优先按上送值分流**，上送非法/缺省才回落读列——保证"**显示 = 上送 = 落库**"闭环。原设计（D-6 仅前端镜像显示、落库读列）存在 TOCTOU：弹窗存续期间用户切换底部开关时，文案实时变、列值不变，可产生"显示（本次会话）实际落全局表"的静默提权，或反向"显示（所有会话）实际落任务表"的承诺落空。D-6 随之修订：模式**仍不需后端下发**（显示用前端值），但**确认时必须上送** |
| D-12 信任 TTL 统一（v1.9 新增） | 三表均写 `expires_at = now + security.trust.ttl_days`；`check_*` 以 `expires_at IS NULL OR expires_at > now` 过滤；`cleanup_expired_trust` / `cleanup_expired_task_trust` / `cleanup_expired_global_trust` 在主循环**各占独立 try**（一个失败不影响另两个） |
| D-13 撤销与清理矩阵（v1.9 新增） | 会话级：TrustPanel 既有分组逐条撤销；**删会话不清理**（存量行为，孤儿行不影响判定）。任务级：TrustPanel「任务级信任」分组逐条撤销（R13）；**删会话时 `DELETE FROM chat_task_trust WHERE session_id=?`**（有归属）。全局级：独立「全局信任管理」面板逐条撤销（R11）；**删会话不清理**（无会话归属，D-9） |
| D-14 确认回写会话列（v1.9 新增，补 D-5×D-11 时序缺口） | `save_trust` 在按上送值落库的**同一事务**内回写 `chat_sessions.trust_mode = 本次确认模式`。否则"发消息时列=A、弹窗期间切 B 并确认"会留下「列=A、最后授权=B」，刷新后开关回退到 A。回写后列恒等于最后一次确认的模式；失败随事务回滚，不产生半更新 |

### 1.4 补充需求分析：跨会话信任继承

#### 1.4.1 问题的本质

"会话 A 的信任清单被会话 B 继承"不是"复制一张表"这么简单，而是**信任作用域的层级问题**。现有作用域只有一档（会话），要支持跨会话共享，本质是把作用域再放宽一级。因此正确的抽象不是"做一次拷贝"，而是**引入更高一档的作用域（全局级）**——一旦信任被授予"全局"，它对当前及将来所有会话**自动**生效，A→B 只是其中一个特例（恰好 B 在 A 之后）。

一次性导入（路径 C）是把"放宽作用域"降级为"一次性搬运"，靠用户手动选源会话执行。二者关系：

| 维度 | 路径 G（全局级别） | 路径 C（A→B 导入） |
|------|-------------------|-------------------|
| 生效范围 | 所有会话（含未来） | 仅被导入的目标会话 |
| 生效时机（对**其他会话**） | **自动**（其他会话无需任何操作）；授权本身仍需在弹窗勾选「信任此操作（所有会话）」 | **手动**（需选源会话执行导入） |
| 持久性 | 与源会话解耦（源删除不影响） | 解耦（拷贝副本，随目标会话） |
| 撤销 | 全局面板逐条撤销 | 撤销目标会话内的该行（**导入项与 B 原有同名项已合并，无法只撤导入项**，见 1.4.2） |
| 安全敞口 | 最宽 | 与普通会话信任相同 |
| 适用场景 | "这类操作我以后都信任" | "把 A 的既定信任带到 B 继续" |

#### 1.4.2 与既有机制的关系

- **全局信任 vs 会话/任务信任**：全局是**最宽**一档。按 D-4 的"越宽越先查"原则，`resolve_skip` 的查询顺序为 **全局 → 会话 → 任务**，任一命中即免弹窗。
- **全局信任 vs 危险工具**：按 D-7，**不设危险工具特判**。理由（北京老陈裁定）：进入信任清单的对象（shell 命令、注册表写入、文件删除、SQL 执行）**本身就是风险项**——信任机制存在的意义就是"对已确认过的风险操作免于重复确认"。故全局授权对所有工具开放，仅由 TTL + 独立撤销面板约束。
- **一次性导入 vs 全局**：导入不是"独立副本"，而是把 A 的行**并入 B 的会话级清单**（`session_id=B`）——键 `(tool_name, path)` 冲突时 `ON CONFLICT DO NOTHING` **保留 B 原行**，故无法单独撤销"导入来的那一条"（撤销即撤该会话该行）。行为与 B 自己勾选的信任完全一致；**导入复用 `chat_session_trust`，不新建表**。全局行本就对 B 可见，**导入动作不复制全局行**（否则重复）；任务级行按链隔离，也不复制。
- **与 `task_id` 旁挂列**：`chat_session_trust.task_id` 是"产生该信任的任务"审计列（不进唯一键、不参与判定），导入时原样带过来即可；`chat_global_trust` 新增 `origin_session_id`/`origin_task_id` 记录**首次授权来源**（纯审计）。

#### 1.4.3 风险与边界

- **安全敞口最大**：全局信任是唯一可能"一次授权、长期免疫、跨全部会话"的机制。缓解手段：① TTL（默认 90 天，可配）；② 独立撤销面板；③ 弹窗勾选文案明确标注"（所有会话）"，让用户在授权瞬间即知悉范围。
- **`path IS NULL` 去重局限**：全局表 `UNIQUE(tool_name, path)` 与其它两表**同源**的 SQLite NULL 局限（NULL 互不相等 → 无路径工具重复建行）。同一已知问题，文档与测试记录，不在本次修复（见 3.A.3 与 5.1）。
- **源会话被删**：`chat_global_trust` **无外键**（跨会话，不能随任一会话级联删除），故删源会话不影响全局行；`origin_session_id` 允许成为悬垂值（纯审计）。
- **导入的 TTL**：A→B 导入时**保留源行的 `expires_at`**（继承剩余寿命），不重新起算，避免"导入即续期"绕过 TTL 意图。注意该规则只对**新插入行**成立：若 B 已有同键行，`DO NOTHING` 保留 **B 的 `expires_at`**，源值不覆盖。
- **前端状态错误 = 授权范围误放大（v1.4 补）**：新授权落哪张表由前端上送的 `trust_mode` 决定（D-5 随消息携带），前端状态机任何镜像断裂/恢复默认错误都可能把"想授会话级"放大为全局级。单机自用场景威胁模型弱（可接受），缓解=全局档弹窗 warning 文案 + 独立撤销面板 + TTL；D-11 落库以上送值为准后，落库与显示强一致；D-14 回写会话列后，刷新/重连的开关值也与最后授权一致。但"显示值本身错"仍依赖 3.B 镜像链正确性。
- **复位覆盖（v1.4 补）**：前端复位点与 `sendMessage` 默认参数同构先例（`allowInterject=false`）取"默认送具体值"（`trustMode='session'`），任何复位后直接发消息的路径都会把会话列覆盖回 `session`。**该覆盖只改变"后续新授权落哪张表"，既有信任仍按 D-4 三域恒查、效力不受影响**；被覆盖的是会话级默认值与配置物化值。同构先例已接受该行为；实施约束：失败复位分支必须优先走 GET 恢复（3.B.7），恢复未完成前该次发送不携带 `trust_mode`（后端 `carry=None` 即沿用列值）。

### 2.2 为什么另建表而不复用 `chat_session_trust`

`chat_session_trust` 的 `UNIQUE(session_id, tool_name, path)` 无法承载另外两档作用域：

1. **任务级**：其 `task_id` 列**已在文档中声明为"只读旁挂、不进 UNIQUE、不参与豁免判定"**（`db_initializer.py:308-312`、`trust_db.py:33-38`）。若拿它过滤，会话级行与任务级行会面对同一条查询语义而混淆；若把 `task_id` 加进唯一键，又破坏会话级幂等。
2. **全局级**：`session_id` 有 `FOREIGN KEY → chat_sessions(id)`，全局行无会话归属，塞哨兵值会触发外键；且 `UNIQUE(session_id, ...)` 对 NULL 会话去重失效。

故新建**两张同构表**：

- `chat_task_trust`：以 **链根 `context_root_task_id`** 为隔离键（一条 link 链共享一行集）。
- `chat_global_trust`：无会话隔离键（`UNIQUE(tool_name, path)`），跨会话共享。

三张表共用同一套路径归一口径（`trust_scope_path`）与 TTL 判据，仅"查询域"不同。

### 2.3 生效模式解析

```
effective_mode = chat_sessions.trust_mode          -- L2 会话覆盖（可空）
             ?? security.trust.mode                 -- L1 全局配置（默认 'session'）
             ?? 'session'                            -- 硬默认
```

- `chat_sessions.trust_mode` 为 `NULL` → 未显式设置，走配置。
- 存量库 ALTER 后该列为 `NULL` → 全部走配置 → 配置默认 `session` → **与改动前 100% 一致**。
- 非法值（非 `session`/`task`/`global`）一律回落配置（fail-safe）。
- **配置物化语义（v1.4 补，v1.11 补第二物化点）**：前端会话内开关值来自 `GET /messages` 下发的**生效值**（含配置），首次随消息携带即把该生效值**物化进列**；确认落库时的回写（D-14）是**第二个物化点**（同一事务内写入本次确认模式）。故配置项修改只影响"尚未产生过消息的新会话/`NULL` 列会话"，**不回溯已物化会话**（3.C.6「新建会话默认值」的确切含义；验收时勿将此误判为"配置未生效"）。

### 2.4 三种模式的行为矩阵

| 阶段 | `session` 模式 | `task` 模式 | `global` 模式 |
|------|---------------|-------------|---------------|
| HITL 前预查（`resolve_skip`） | 查全局 → 查会话 → 查本链任务级（`root=context_root_task_id`）——**三域恒查（v1.4）** | 同左：三域恒查 | 同左：三域恒查 |
| 用户勾选信任后落库 | `insert_session_trust` | `insert_task_trust`（带链根） | `insert_global_trust` |
| 确认后回写会话列（v1.9，D-14） | 三档均在**同一事务**内回写 `chat_sessions.trust_mode = 本次确认模式`（列恒等于最后一次授权） | 同左 | 同左 |
| 信任寿命 | 同会话持久（TTL） | 仅本链（TTL + 链隔离） | **所有会话**（TTL） |
| 查询顺序 | 全局 → 会话 → 任务（三域恒查，短路 OR，任一命中即豁免；顺序仅由宽到窄表达与短路效率，**无覆盖/排他语义**——v1.4 措辞订正，原"查询优先级"易误读为覆盖关系） | 同左 | 同左 |
| 回收 | `cleanup_expired_trust` | `cleanup_expired_task_trust` | `cleanup_expired_global_trust` |

**D-4 论证（v1.4 修订）**：模式描述的是"**新授予**的信任放多宽"，而非"作废既有信任"。用户此前任一模式下显式授权过的信任是明确的持久许可，若因切到更窄模式而失效，会造成"我明明信任过，怎么又弹了"的意外打扰（违反最小惊讶原则）。**该论证对三张表完全对称**——任务级信任同样不因切离 `task` 模式而失效：`resolve_skip` 按 **全局 → 会话 → 任务** 由宽到窄**恒查三域**，任一命中即免弹窗；模式仅决定"新授权落哪张表"，不改变任何既有信任的效力。
> v1.4 复核修正：v1.3 及以前的实现 diff 曾写成"任务表仅 `mode=='task'` 时查"，与本论证自相矛盾（任务级效力被模式条件否决）；其"避免给 session 模式引入行为变化"的理由不成立——`chat_task_trust` 是新表，存量 session 用户恒查必为空集，**零行为变化**。v1.4 起以三域恒查为准，原 T6 断言同步反转（见 5.1）。

### 2.6 跨会话继承的两条路径

**路径 G（全局级别）**
- 用户把开关切到「全局级」，或在配置里把默认设为 `global`（**安全提示**：配置默认 `global` 会让**所有新会话**的授权默认落全局表，弹窗文案会显示「（所有会话）」；如非确需，保持 `session`）。
- HITL 勾选「信任此操作（所有会话）」→ `insert_global_trust`。
- 之后**任意会话**的 `resolve_skip` 第一步即查全局表并命中 → 免弹窗。A→B 自动成立。

**路径 C（A→B 一次性导入）**
- 面板/接口动作：`POST /api/v1/trust/import {from_session_id, to_session_id}`。
- 后端 `storage.import_session_trust`：把 `chat_session_trust` 中 `session_id=A` 的**未过期**行 `SELECT ... INSERT` 进 `session_id=B`（`ON CONFLICT(session_id,tool_name,path) DO NOTHING`；新插入行保留源 `expires_at` 与 `task_id`）。
- 结果：B 的会话级清单 = 原 B 行 ∪ A 行，**键冲突以 B 原行为准**（B 的 `expires_at` 不被覆盖）；不碰全局表、不碰任务表。

### 2.7 分层与依赖

- `app/safety/*` 内**读写**信任（不依赖 services）；**生效模式解析、全局/任务信任的 insert/check/cleanup_expired 均在此层**（`trust_db.py`）。
- `app/services/chat/storage.py` 负责**面向 API 的清单/撤销/导入**（list/delete/import），因 `app/api` 禁 import `app.safety`，API 只能经 services 触达。
- `app/services/chat/stream_orchestrator.py` 编排期落值；`message_service.py` 读生效模式用于显示；`services/task/hitl_confirmation.py` 确认时经 `trust.save_trust` 落库并**同事务回写会话列**（D-14）。
- 全部改动均为**架构级兼容扩展**（新列 / 新表 / 新可选形参，存量行为零退化）；**不保留旧函数名 / 旧配置键**（守"禁 backward"）。

### 3.C UI/UE 交互设计与文案（北京老陈授权小欧定案）

> 本节新增（v1.2）。以下为**已定案**的交互与文案；如与预期不符，见 5.4 可调整项。

#### 3.C.1 设计原则

1. **一致**：复用底部功能行既有范式（与 `续聊`/`插话开关` 同处一排、同尺寸、同交互），不新造独立区域。
2. **克制**：信任范围是**低频偏好**，控件保持紧凑，不抢发送按钮视线。
3. **透明**：每一档都让用户"一眼知道作用范围"，**全局档额外强调影响面更广**。
4. **可撤销**：全局信任必须有明显的撤销入口（独立面板），不可"授权即失踪"。
5. **无惊讶**：切档是纯偏好，不弹二次确认；但**全局授权**在弹窗内即时提示范围与撤销途径。
6. **中性措辞**：不使用"安全/危险"等误导词（信任对象本就是风险项，D-7），一律用"范围/作用/生效"等中性词。

#### 3.C.2 底部「信任范围」开关（`SubmitBar`）

- **形态**：盾牌图标 `SafetyCertificateOutlined` + 短标签三段 `Segmented`：`会话 | 任务 | 全局`。
- **为何用短标签**（而非 v1.1 的"信任·会话级"）：底部功能行宽度紧张；图标 + Tooltip 已充分释义，短标签降低视觉噪声。
- **选中态强调**：默认 `session` 平常态；切到 `global` 时给控件加 **warning 描边**（外层 `Tooltip`/自定义 `className`），提示"影响面更广"。
- **交互**：点击即生效，**无 toast**（控件状态即反馈）；值随下一次发送的消息上送并落库（D-5）。
- **位置**：插话开关之后、**会话事务空间之前**（发送按钮已移入输入框右下角，与 3.B.12 订正一致）。
- **无障碍**：`aria-label="信任范围"`；图标 `aria-hidden`；Tooltip 带 `title`；键盘可达。

### 6.2 核心交互时序（五条主流程）

**① 授权 → 免弹窗（主链）**

```
HITL 弹窗勾选（文案/title 随 trustMode 三值）
  → [信任并执行] 上送 trust_mode（D-11 第 4 参链：AuthModal → useAuthorization → task.api → confirm 端点）
  → resolve_confirmation → save_trust 按上送值落对应表（session/task/global 三表分流）
  → 下次同工具+同范围：resolve_skip 三域恒查命中 → 免弹窗
```

**② 切档（纯偏好，静默）**

```
点 Segmented → useChatState 真源更新（无 toast，控件状态即反馈）
  → 值随下一次发送消息上送 → 编排器落会话列 trust_mode
  → 授权场景的弹窗显示与落库经 D-11 统一按上送值，二者恒一致（无 TOCTOU）
```

**③ 全局撤销**

```
设置页「信任」分组 或 TrustPanel「全局信任」链接
  → GlobalTrustPanel 打开拉 GET /trust/global
  → 行内 [撤销]（Popconfirm 二次确认）→ DELETE /trust/global/{id}
  → message.success('已撤销') → 刷新列表 → 相关操作各会话重新弹窗
```

**④ 任务级 / 会话级撤销（同 Drawer 内两组）**

```
TaskInfoBar → TrustPanel 打开 → 会话组 load() ＋ 任务级组 loadTaskTrust() 并行
  → 任务级行 [撤销]（Popconfirm）→ revokeTaskTrust(id) → 行内移除
  → 两组互不触发对方刷新（一组一数据源，3.B.15b）
```

**⑤ A→B 会话导入（路径 C）**

```
TrustPanel 顶部「＋ 从其他会话导入」→ 源会话单选（排除当前会话）
  → [导入] → importTrust(from, to) → POST /trust/import（后端 ON CONFLICT 幂等）
  → 成功 message('已导入 N 条') → 刷新本会话清单；N=0 → '所选会话没有可导入的信任'
```
