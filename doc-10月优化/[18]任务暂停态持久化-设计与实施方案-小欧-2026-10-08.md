## 一、背景与定位

### 1.1 主线背景

北京老陈 2026-10-08 裁定四条特殊任务设计约束：

| 序号 | 决策 |
|------|------|
| 1 | 任务从属会话，**恒定不可变** |
| 2 | 新起特殊任务时，同时建立一个 1:1 伴随会话 |
| 3 | 隐藏任务 = 不显示步骤细节，**但进度与结果信息必须可见** |
| 4 | **暂停应该是持久化的** |

四块落地顺序（本文档只做第三块）：

| 顺序 | 内容 | 风险 | 状态 |
|------|------|------|------|
| 第一块 | 伴随会话创建流程 | 中 | 待做 |
| 第二块 | 后台运行内存治理（`event_log` 环形窗口） | 高（动核心） | 待做 |
| **第三块** | **暂停态持久化** | **低（纯新增）** | **本文档** |
| 第四块 | 隐藏态前端分层折叠 | 低（纯前端） | 待做 |

选第三块先做的两条理由：

1. **它是后台任务完整性的必要条件** —— 后台任务重启后若丢暂停态，会被 `reconcile_orphaned_tasks` 判为崩溃遗留并改成 `failed`，用户暂停的心血变成"失败"
2. **纯新增，无退化风险** —— 不改运行机制，只加持久化字段与写入点

### 1.2 为什么"必须跑到底"不需要改架构

北京老陈裁定"伴随会话切走，任务必须跑到底"。实证结论：**这个能力架构上已成立**，不需要改运行机制。

| 事实 | 位置 |
|------|------|
| `done` 由**生产者**在 finally 置位，与消费者无关 | `agent_runner.py:891` |
| SSE 消费者只是 `if buffer.done.is_set(): return` | `stream_orchestrator.py:757` |
| react_loop 内部两处过早 `done.set()` 已被删除 | `react_loop.py:328` 编辑历史 |

`react_loop.py:328` 编辑历史原文：

> 2026-09-12 小欧 - 竞态根因修复(方案): 删除内部两处过早 `_buf.done.set()` …… 在 done.set() 之后才写入 event_log, 无消费者转发 → SSE 漏发(X2 E2E 断言失败/DB 先落库不受影响)

**该修复当时是为根治 SSE 漏发的竞态，副作用是把"任务推进彻底脱离 SSE 消费者"这一性质坐实了。** 后台运行能力的地基在那次修复时已经打好，只是当时未被识别为目标设计的一部分。

## 二、现状实证

### 2.1 暂停态的完整存储链路

| 环节 | 现状 | 位置 |
|------|------|------|
| HTTP 入口 | `POST /chat/stream/pause/{task_id}` | `chat_routes.py:84` |
| 薄包装 | `pause_task(task_id, session_id)` | `task_registry.py:325` |
| 核心 | `set_paused(task_id)` | `task_registry.py:279` |
| 内存写入 | `running_tasks[task_id]["paused"]=True`、`["status"]="paused"` | 同上 |
| 唤醒机制 | `pause_event.clear()` | 同上 |
| 消费侧检查 | `check_paused()` / `get_pause_event()` | `task_state.py:186/218` |
| **DB 落库** | **无** | — |

`set_paused()` 函数体（`task_registry.py:279-292` 全文）：

```python
async def set_paused(task_id: str) -> dict:
    async with running_tasks_lock:
        task = running_tasks.get(task_id)
        if not task:
            return api_failure(message=f"任务 {task_id} 不存在")
        if task.get("cancelled"):
            return api_failure(message=f"任务 {task_id} 已被中断,无法暂停")
        task["paused"] = True
        task["status"] = "paused"
        pause_event = task.get("_pause_event")
        if pause_event:
            pause_event.clear()
        return api_success(message=f"任务 {task_id} 已暂停")
```

**结论：整个函数零 DB 操作，暂停态纯内存。**

### 2.2 `running_tasks` 的生命周期

`task_state.py:40`：

```python
running_tasks: dict[str, dict] = {}
```

纯进程内 dict，无任何持久化。进程退出即全部丢失。
`task_cleanup()`（`task_registry.py:345`）在 runner finally 调用时清理条目。

### 2.3 现有的重启恢复机制及其冲突

**关键发现 —— `reconcile_orphaned_tasks`（`storage.py:426`）会把暂停态吃掉。**

该函数在 `main.py:290` 的 `startup_event` 调用，逻辑是：

> 启动期僵尸任务收尾：把【上次进程崩溃遗留】的 status='executing' 残行改终态
> 病根：status 只由 agent_runner finally 改，进程被 kill 时 finally 不执行 → 残行永久'executing'，前端徽标永远显示"执行中"

其 UPDATE 语句（L436 起）：

```sql
UPDATE chat_tasks
   SET status = 'failed',
       error_type = 'task_interrupted',
       ...
 WHERE status = 'executing' AND start_time < boot_iso
```

**冲突点**：暂停中的任务，`status` 在内存被置为 `paused`，但 **DB 里仍是 `executing`**（因为现在不落库）。进程重启后：

```
暂停中的任务 → DB status='executing' → 命中 reconcile 条件 → 被改成 'failed'
```

**用户暂停的任务，重启后变成"失败"**。这是当前设计的实质缺陷，也是本方案要解决的核心问题。

### 2.4 `update_task` 可复用性

`storage.py:391` 的 `update_task()` 支持按需字段更新（缺省字段不覆盖，幂等）：

```python
def update_task(conn, *, task_id, response=None, status=None,
                end_time=None, duration=None, accumulated_usage=None,
                llm_call_count=None, total_steps=None, retry_count=None,
                error_type=None, error_message=None, artifacts=None) -> None:
```

**`status` 参数已存在**，可直接传 `"paused"`，无需扩签名。这是本方案能保持"纯新增"的关键。

## 三、设计目标与非目标

### 3.1 设计目标

| 序号 | 目标 |
|------|------|
| G1 | 暂停操作落 DB，`chat_tasks.status='paused'` |
| G2 | 恢复操作清暂停痕迹（status 回 `executing`，`paused_at` 置 NULL） |
| G3 | `reconcile_orphaned_tasks` **排除** `paused`，重启后恢复为暂停态 |
| G4 | 任务列表读 DB 时能正确显示"已暂停" |
| G5 | 恢复操作能在重启后真正唤醒任务（不只是显示，是真能跑） |

### 3.2 非目标（明确不做）

| 不做 | 理由 |
|------|------|
| 不改 `running_tasks` 内存结构 | 内存态是运行期快路径，必须保留 |
| 不做暂停点的 step 快照 | resume 从下一轮继续，语义已足够；做快照要引入 checkpoint 机制，超出本块范围 |
| 不做"重启后自动唤醒" | 重启后 Agent 进程不存在，唤醒需要从 checkpoint 重建整个循环，属第二块/后续独立议题 |
| 不动 `reconcile_orphaned_tasks` 的终态取值 | 沿用 `failed + error_type=task_interrupted`，不新增状态值 |

### 3.3 G5 的诚实说明

**G5 有一个无法在本方案内解决的边界，必须写明**：

暂停态能被持久化并正确显示，但**服务重启后无法自动恢复到"可继续执行"的运行态** —— 因为 ReAct 循环的运行上下文（`agent` 对象、`chunk_buffer`、工具执行栈）在进程退出时全部丢失。

本方案交付的是：
- ✅ 重启后任务**仍显示"已暂停"**（不再被误判 failed）
- ✅ 用户能看到"这个任务本来是暂停的"
- ❌ 不支持重启后点"继续"就跑起来

若要支持重启续跑，属`[71]后端重启运行中的未完成任务从 LLM-tool checkpoint 继续执行` 的范畴，需在 `chat_stream_events` 事件流上重建循环状态。这是独立设计，不在本文档。

## 四、方案设计

### 4.1 数据模型变更

`chat_tasks` 新增一列：

```sql
-- 幂等追加（_ensure_column 机制，与既有列一致）
ALTER TABLE chat_tasks ADD COLUMN paused_at TEXT;   -- 暂停时刻(本地ISO无Z)，NULL=未暂停
```

**为什么加列而不只靠 `status`**：

| 方案 | 问题 |
|------|------|
| 只看 `status='paused'` | 无法区分"用户主动暂停"与"其他原因"，也无法记录暂停时长 |
| 加 `paused_at` | 可算暂停时长（进度信息，契合决策3）、可做"暂停超龄"治理、语义明确 |

`status` 与 `paused_at` 的组合语义：

| status | paused_at | 含义 |
|--------|-----------|------|
| `executing` | NULL | 正常运行 |
| `paused` | 非 NULL | 用户主动暂停 |
| `paused` | NULL | 异常态（不应出现，`reconcile` 收尾时补齐） |
| 终态 | NULL | 已完成/失败/取消 |

### 4.2 写入点设计（三处改动）

#### 改动一：`set_paused()` 增 DB 落库

**位置**：`task_registry.py:279`

**改法**：`set_paused()` 内存写入成功后，追加一次 DB UPDATE。

关键决策：**落库必须 `to_thread` offload 出事件循环**。

依据：`agent_runner.py:857-870` 的既有做法 ——

```python
# 落库 offload 出事件循环(后端卡死修复 小欧 2026-08-24)
_sum_row, _auth_acc = await db.atxn("chat", lambda conn: (...))
```

`chat_routes.py` 的 pause 端点在事件循环内被调用，直接 `conn.execute` 会把 SQLite 同步 I/O 拉回主循环，复发 2026-08-24 那次"后端卡死"。**必须走 `db.atxn`。**

拟改：

```python
async def set_paused(task_id: str) -> dict:
    async with running_tasks_lock:
        task = running_tasks.get(task_id)
        if not task:
            return api_failure(message=f"任务 {task_id} 不存在")
        if task.get("cancelled"):
            return api_failure(message=f"任务 {task_id} 已被中断,无法暂停")
        task["paused"] = True
        task["status"] = "paused"
        pause_event = task.get("_pause_event")
        if pause_event:
            pause_event.clear()
    # 锁外落库（见 4.2 改动一说明：落库不放锁内，避免 DB I/O 串行化所有 pause/resume）
    await _persist_pause(task_id)      # 新增函数，见 4.3
    return api_success(message=f"任务 {task_id} 已暂停")
```

**为什么落库放在锁外**：现有 `set_cancelled()` 等函数全程持 `running_tasks_lock`。若 DB 写放在锁内，pause 请求的 DB 延迟会阻塞所有其他任务的 `running_tasks` 读写。放锁外后，锁只保护内存字典操作（微秒级），DB 写独立进行。

**为什么不用 shield**：pause 是用户主动的轻量操作，不是终态关键写。若进程此刻被 kill，暂停态丢失的后果是"重启后变failed"—— 由 `reconcile` 的 `executing` 分支兜底，可接受。不引入 shield 复杂度。

#### 改动二：`set_resumed()` 清暂停痕迹

**位置**：`task_registry.py:295`

拟改：`pause_event.set()` 之后落库 `status='executing', paused_at=NULL`。

```python
async def set_resumed(task_id: str) -> dict:
    async with running_tasks_lock:
        ...  # 现有逻辑不变
        task["paused"] = False
        task["status"] = "running"        # 注意：内存用 running（现有口径）
        pause_event = task.get("_pause_event")
        if pause_event:
            pause_event.set()
    await _clear_pause(task_id)           # 新增：status='executing', paused_at=NULL
    return api_success(message=f"任务 {task_id} 已继续")
```

**口径差异必须写明**：内存态 `set_resumed` 写 `status="running"`，而 DB 侧 `chat_tasks` 的合法值是 `executing/paused/completed/failed/cancelled`（见 `db_initializer.py:136` 与前端 `TaskListPanel.tsx:58` 的 `TASK_STATUS_LABEL`）。**DB 必须写 `executing`，不能写 `running`** —— 否则前端"执行中"标签匹配不到，会落到未知态。

这是内存与 DB 的口径差异，不是 bug（内存 `running` 是运行期内部语义，DB `executing` 是持久化枚举），但必须显式处理。

#### 改动三：`reconcile_orphaned_tasks` 排除 paused

**位置**：`storage.py:426`

现条件：`WHERE status = 'executing' AND start_time < boot_iso`

改为：`WHERE status = 'executing' AND status != 'paused' AND start_time < boot_iso`

由于 `status` 单值互斥（不可能同时等于 `executing` 和 `paused`），`status='executing'` 本身已天然排除 `paused`。**因此实际上无需改 WHERE 条件。**

但需补一处：**恢复 paused 的启动期收尾**。`paused_at` 非空且 `status='paused'` 的行，应当：
- 保持 `status='paused'`
- 补 `updated_at`（若需要）
- 不改终态

即：**`reconcile_orphaned_tasks` 对暂停态天然无操作，无需改代码，只需加一条防御性日志**说明"本次启动有 N 个暂停态任务被保留"。

这一条要在文档里写清楚，避免后人误以为要改 WHERE 而引入多余条件。

### 4.3 新增落库辅助函数

在 `task_registry.py` 内新增（与既有 `set_cancelled` 等同族）：

```python
async def _persist_pause(task_id: str) -> bool:
    """暂停态落库 chat_tasks(status='paused', paused_at=now) — 2026-10-08 小欧"""
    from app.db import database as db
    from app.services.chat import storage
    from app.utils.time_utils import get_local_iso_timestamp

    async def _do(conn):
        return storage.update_task(
            conn, task_id=task_id, status="paused",
            # paused_at 无 storage 包装，需专用 SQL 或扩 update_task 签名
        )
```

**这里遇到一个设计抉择**：`update_task()` 签名里没有 `paused_at` 参数。两个选择：

| 选项 | 做法 | 评价 |
|------|------|------|
| A | 扩 `update_task()` 加 `paused_at` 参数 | 改公共函数签名，影响面小（`agent_runner` 也调它），但更 DRY |
| B | `_persist_pause` 内写专用 UPDATE | 不动公共函数，但出现第二处 chat_tasks UPDATE 口径 |

**倾向 A**：`update_task` 已是 chat_tasks 的唯一 UPDATE 入口（`agent_runner` 终态、runner 每轮即时更新都用它），B 方案会制造第二个写入口，违反 DRY。扩一个可选参数 `paused_at=None` 缺省不覆盖，零行为变化。

## 七、与主线的衔接

暂停态持久化落地后，特殊任务主线的剩余三块：

| 块 | 依赖本文档？ | 说明 |
|----|--------------|------|
| 伴随会话创建 | 否 | 独立；需 `chat_sessions` 加反向指针 |
| 后台内存治理 | **是** | 需读 `paused_at` 判断"暂停中的后台任务是否仍占内存 buffer" |
| 隐藏态前端折叠 | 部分 | 折叠态要显示"已暂停（暂停于 MM-DD HH:MM）"，需读 `paused_at` |

**`paused_at` 是第三块与第四块的共享字段**，先做第三块可让第四块的进度信息直接复用。
