### 2.6 注入压缩阶段完整结论（链式任务语境）

**1. 本次任务属于 link 链式任务，注入历史的动作已执行，但结果未达设计要求。**
任务启动时 `start_step._inject_conversation_history`（`start_step.py:106-109`）将跨任务历史 PREPEND 到 `conversation_history` 头部，`_maybe_compact_injected_history` 超窗判定置位。注入本身成功（`message_builder.py:184-190` 列表拼接），但后续 C4 摘要回填未生效。

**2. 注入压缩分两阶段：无 LLM 调用的 + 有 LLM 调用的。**
- **无 LLM 调用**：C3 剪枝（`prune.py`，零 LLM，仅替换 tool content 占位）——但本任务所处代码路径未启用（`trim_history:277` 仍走 `_trim_to_budget`）。
- **有 LLM 调用**：C4 锚定摘要（`summary.py:generate_anchored_summary`）——本任务**执行了**，但产出为空。
真正出错的是 C4 这条：`generate_anchored_summary` 的 feed 组装逻辑（`summary.py:60-70`）把**完整 `conversation_history`（含用户最后一条待办指令）原样喂给 LLM**，这导致 LLM 未按摘要格式响应。这个"先 agent 封装再喂 LLM"的中间步骤，在喂入的上下文上**违背了"只做摘要、不执行"的设计前提**。

**3. LLM 压缩调用的设计要求是"问答模式、按模板返回摘要"，实际违背。**
设计要求（`summary_prompt.py:11-17`）：`SUMMARY_TEMPLATE` 要求返回**六段固定结构 Markdown**（Goal/Key Decisions/Next Steps/Critical Context/Relevant Files/Progress），是一次纯问答式文本输出（`openai_tools=None`）。实际 `LLM调用记录[0]` 返回的是：`type="action"`、`结束原因=tool_calls`、5 个并行 tool_calls、且 `content` 是"任务执行计划"文本而非摘要六段。**设计被完全颠覆**。

**4. 错误的 content 未进入主循环，但压缩失败本身已导致任务跑偏。**
`start_step.py:166` `if summary_text:` 因 `summary_text` 恒空而不成立 → `conversation_history` **保持原样**进入主循环。因此主循环 prompt=198K tokens 含的是原始历史，而非"错误摘要"。但压缩未生效意味着：**历史未压缩、用户待办指令直接进入主循环**——主循环里的模型因此把历史里的"待办"当成当前任务继续规划，输出了"## 最终验证结论"而非"已更新问题文件"，形成答非所问。

**5. 前端收到 thought-start，但未立即渲染"推理内容"徽标。**
`thought_start_step.py:13` 定义 `ThoughtStartStep`，在主循环第一轮 LLM 开始前 `step_emitter.py:64` 发出 `[StepEmit] thought-start step=1`（07:18:31）。但前端徽标的渲染依赖 `ChunkStep(is_reasoning=true)`（`chunk_step.py:37`），而 `ChunkStep` 仅在 `while` 循环内 `_process_single_step` 产出——压缩阶段不经过 while 循环，因此在 07:18:31 之前前端无任何可渲染事件，**徽标直到 07:18:50 才随 583 个 chunk 涌入而显示**。

**总结**：
1. **注入压缩完全失败**——C4 跑了，但摘要恒空、压缩零生效、用户意图被吞；
2. **前端未及时渲染"推理内容"**——因压缩阶段零 SSE 业务事件，思考区标签等到 142 秒后主循环第一轮才有内容。

## 三、出错点分析（2 个真问题 + 1 项统计失真）

### 3.0 设计与实施一致性核查（前置判断）

在进入问题点之前，先明确一件事：**注入压缩（C4 锚定摘要）在本次 10-07 事件中是否按设计接入？**答案：**是。触发位置、分流逻辑与设计一致**。

设计的双轨位置（`doc-8月优化/[4]` 与 `doc-7月优化/[2]`）：

| 阶段 | 触发位置 | 压缩方式 | 是否在 loop 内 | 是否调用 LLM |
|---|---|---|---|---|
| 任务启动（while 前） | `_compact_injected_history` 一次性回填 | C4 锚定摘要 | 否 | **是**（本次事故暴露的发起点） |
| 每轮 LLM 调用前（loop 内） | `message_builder.trim_history()` | 裁剪（`_trim_to_budget` 保底截断，非 C3 prune、非 T1/T2/T3） | 是 | 否 |

代码核实（`react_loop.py:147-321`）：

```python
_start_step = _assemble_start_step(agent, context)   # ① 注入历史 + 超窗判定
_start_dict = agent._step_emitter.emit(_start_step).to_dict()
await _publish(_start_dict)

# react_loop.py:159-164 ← 注入压缩只在这里、while 之前执行一次
if getattr(agent, "_needs_compact", False):
    await _compact_injected_history(agent)

while agent.llm_call_count < max_steps:              # ② loop 内只有裁剪
    ...
    agent.message_builder.trim_history()             # react_step.py:321
```

- `_maybe_compact_injected_history`（`start_step.py:112-142`）只在 start 装配时置位 `agent._needs_compact`，主循环中**不再重新置位**；
- `while` 循环内 `react_step.py:321` 每轮只跑 `trim_history()`，**不调用 `_compact_injected_history`**；
- 结论：**当前代码按原设计实施**，C4 只在任务启动阶段、超窗时一次性执行，loop 内未复用。

因此，本次 10-07 的故障**不是**"loop 内误用注入压缩"——它是 C4 在**启动阶段的一次性执行中跑偏**，且**只有一个源头**：`generate_anchored_summary`（`summary.py:60-70`）把含用户待办指令的完整历史原样喂给 LLM，模型因而按干活模式输出 action + tool_calls。由这一个源头派生出三个可见后果——① 摘要恒空、压缩零生效（`summary.py:42` 取 `content` 落空是**被动结果**）；② 5 个 tool_calls 静默丢失（压缩路径无执行器，属正常，因为设计上本不该有工具）；③ 前端 123s 无反馈（压缩阶段在 while 前静默 await，与本源头并列的独立问题）。另有统计失真（token 漏计）与本事故同源但独立。

### 核心追问与逐层拆解

**前提**：压缩是问答类调用（`openai_tools=None`，Text 模式），**按设计正常必定返回 `answer`**。因此"摘要恒空""工具丢失"都不是独立缺陷，而是**输入端被污染后的必然后果**。三个追问最终收敛到同一个源头。

**追问 1：压缩逻辑整体过程是否有问题？—— 有，是输入端链路级错位。**
原设计预期：`SUMMARY_TEMPLATE` 要求模型输出一段六段式 Markdown 摘要；实际执行中模型输出的是"任务执行计划 + 5 个 tool_calls"，完全偏离摘要目标。根因不在模板本身，而在**摘要调用喂入的上下文**——`generate_anchored_summary`（`summary.py:60-70`）把完整 `conversation_history`（含用户最后一条待办指令 `"那你需要更新 问题 文件哦"`）原样喂给 LLM，模型把"历史待办"误认为"当前任务"，按干活模式输出 tool_calls。

**追问 2：不应该调用 tool，为什么调用了 tool？—— 上下文里带着"待办指令"，模型按答题意图作答。**
压缩调用 `openai_tools=None`（`summary.py:38`），请求体不含 `tools`（`client_sdk.py:223`），本身是纯文本问答。但 `SUMMARY_TEMPLATE` 的措辞是"将 messages 归档为固定结构 Markdown 摘要"，配上**完整的、含待办指令的历史**后，模型判定自己在"回答一个任务"而非"归档一段历史"，于是输出了标准 FC 格式的 5 个 `tool_calls` + task plan 正文。这是**输入端语义污染**，不是协议缺陷、也不需要为它补分支设计。

**追问 3：响应的 content 是不是正确按照模板返回？—— 不是。**
模板要求六段 Markdown：`Goal / Key Decisions / Next Steps / Critical Context / Relevant Files / Progress`。实际 `LLM调用记录[0].原始响应.content` 是：

> 好的，我将基于真实代码验证和真实数据复核的结果，更新问题报告和修改实施设计报告…
> ### 任务执行计划
> 1. 创建新的生成脚本… 2. 生成 5 种带签名和时间戳的格式文档。3. 验证产物完整性。

这是**任务执行计划文本**，不是摘要六段结构。该响应是 `type="action"`，其正文在协议 payload 里挂在 `thought` 键下而非 `content` 键 —— 但**这不是需要修的契约不一致**：只要输入端不被污染，模型正常返回 `answer`，`content` 键必然存在、`summary.py:42` 自然取到六段摘要。**"content 取不到"是果，"喂进去的上下文带待办指令"才是因。**

### 问题点 1｜压缩摘要在主循环之外同步阻塞，零 SSE 事件

- **位置**：`react_loop.py:163-164`，`await _compact_injected_history(agent)` 在 `while`（L192）之前
- **行为**：压缩期间不发任何 MetaStep / thought-start / chunk 事件，只有 4 条心跳
- **影响**：前端 123 秒无任何可渲染内容；思考区标签依赖 `ChunkStep(is_reasoning=true)`，而 `ChunkStep` 仅在主循环内产出 → 前端 142 秒只能停在"执行中"
- **性质**：设计遗漏。压缩不应阻塞主循环启动，也不应零通知

### 问题点 2｜摘要调用未隔离任务意图，模型角色混淆

- **位置**：`summary.py:60-70`，`generate_anchored_summary` 把完整 `conversation_history`（含用户最后一条待办指令）原样喂给 LLM，仅 tool 消息 content 截断
- **行为**：模型在 122K tokens 的上下文中读到"那你需要更新 问题 文件哦"，按**干活模式**输出 tool_calls，而非摘要
- **影响**：压缩阶段模型产出的 5 个工具动作（write+bash×3）与用户意图直接相关，但框架无法承接，意图被吞
- **性质**：设计缺陷。摘要阶段应明确告诉模型"只做摘要"，且喂入的上下文应弱化"当前待办"语气

### 统计失真｜压缩调用未计入 llm_call_count 与 token 累计

- **位置**：`react_loop.py:163-164` 压缩路径不走 `_process_single_step`（`react_step.py:315` 的计数）
- **行为**：压缩消耗 132333 tokens、耗时 123 秒，全部不进 `TASK_END`、不进 session/chain 累计、不进 `llm_call_count`
- **影响**：`TASK_END llm_calls=1`（实际 2 次），token 用量 198552（漏 40%），max_steps 计数也被偷一步
- **性质**：统计体系缺一个"辅调"维度

## 四、解决策略

**前提认知**：压缩是问答类调用，**正常必定返回 answer**。修复方向不是给异常分支补设计，而是**守住输入端**、**让压缩阶段对前端可见**。

### P0｜立即修复（阻断型缺陷）

| 项 | 方案 | 落点 |
|---|---|---|
| P0-1 零 SSE 阻塞 | 压缩前先 `publish` 一个 MetaStep（如"正在压缩上下文 204113 tokens"），压缩后再发一条完成事件；让前端立刻有反馈，不必干等 123 秒 | `react_loop.py:163` 前后 |
| P0-2 **输入端污染（唯一根因）** | 摘要调用 feed **不得原样带入用户待办指令**。方案二选一：① 组装时剥离最后 N 条 user 原始指令；② 或在 `SUMMARY_TEMPLATE` 后追加硬约束（"你只做历史归档，禁止规划或执行任务，禁止输出任务计划"）。修复后模型应正常返回 answer + 六段摘要 | `summary.py:60-70` / `compaction/summary_prompt.py` |

### P1｜健壮性与可观测性

| 项 | 方案 | 落点 |
|---|---|---|
| P1-1 失败静默 | `start_step.py:166` 摘要为空时补 `logger.warning`，杜绝静默零生效 | `start_step.py:166` |
| P1-2 token 漏计 | 压缩调用的 usage 计入 task/session 累计，并单独标注 `aux_llm_calls` | `agent_runner` / `__init__.py:33` |
| P1-3 轮次失真 | 压缩调用纳入 `llm_call_count` 或单列辅调计数，明确区分主/辅 | `react_step.py:315` / `agent_runner` |

### 复现与验证

1. **日志检查**：`grep "摘要回填完成"` 应在成功压缩的任务日志中出现；本次**缺失**
2. **调用链**：预期 `TASK_START → 超窗判定 → 压缩摘要(发SSE) → while → 调用#N → final`；实际压缩阶段零 SSE、零工具
3. **文件系统**：`Test-Path ...20261007 → False`，证实 5 个动作零执行
4. **修复后回归**：构造 204K+ tokens 的会话，验证压缩后 prompt 下降、日志有 `摘要回填完成`、事件流在主循环前有 MetaStep
