## 一、背景与目标

### 1.1 背景
北京老陈指出：当前安全检查相关代码"**顺序乱、功能切分乱**"，要求**从全局逻辑、按人的思维模式**判断"哪些该在哪里"。经初查确认：乱象不是 L3（安全检查链）内部的孤立问题，根因在 **L2（工具调用管线）把"安全检查"当成一个 400 行黑盒塞进管线，未在 L2 层把"解析/路由/检查/确认"分开**。故本方案一次性覆盖 **L2 + L3**。

### 1.2 目标
1. 把一次工具调用的生命周期按**人类直觉**重新分层：**认领 → 合法性 → 危险性 → 权限 → 问人 → 执行**。
2. 让每一级**一段一责、顺序对所有工具一致、绝不按工具类型分叉**。
3. 消除职责错层（未注册判定、信任预算混入检查）、重复判定（delete 路径跑两遍）。

### 1.3 边界
- 本方案**只做设计与分析，不改任何代码**。
- 目标架构给出，具体函数名/文件落点在第 5、6 章；实施须老陈对本方案第 7 章裁定点确认后再动码（**裁定已于 v1.1 完成，见 7.2**）。

## 二、现状层级树（L0~L4）

### 2.1 层级树

```
L0 服务入口骨架
   HTTP /chat → stream_orchestrator → agent_runner → run_react_cycle (backend/app/services/agent/react_loop.py:93)
        │
L1 主流程核心 = ReAct 循环体（while llm_call_count < max_steps）
        │  THINKING(调LLM) → _dispatch_handler 按 type 分派 (react_dispatch.py:55)
        ▼
L2 【EXECUTING 段】handle_action 的 9 步管线 (handle_action.py:314)
        1 _build_call_list        解析 parsed → all_calls
        2 emit ThoughtStep + ActionStep 预览

        4 canonical ActionStep emit
        5 execute_tools           三分支执行(单/并行/顺序) (tool_runner.py:20)
        6 tool_retry_engine(隐蔽)
        7 build ObservationContext

        │

        │

        API 旁路 tool_facade.execute_tool (:127) 直调 SA3
```

### 2.2 三个定位问答

1. **"这是主流程吧？"** —— 是。它是 L2 的第 3 步，每次工具调用都必过，属主流程关键路径，不是旁枝。
2. **"主流程下有没有次级流程？"** —— 有，就是 L2 的 9 步管线。而且它自己也有顺序问题：现在 3(安全检查) 和 5(执行) 之间夹着 4(retry 回调装配)，7/8 观察构建又在执行之后。
3. **"三级流程要不要也梳理？"** —— 要。因为 L3 的乱（SA1 混四责、delete/shell 顺序分叉）根因是 L2 把"安全检查"当成一个黑盒塞进第 3 步，没有在 L2 层就把"解析/路由/检查/确认"分开。只动 L3 不动 L2，等于在错误的分层上修内部顺序，治标不治本。

### 2.3 一句话乱点小结

| 级 | 该是什么 | 现在乱在哪 |
|----|---------|-----------|
| L1 | 纯调度循环 | 基本干净 |
| L2 | 工具调用生命周期：解析→[路由]→检查→确认→执行→观察 | 把 9 步混在一个 handler，且"安全检查"是一个 400 行黑盒；retry 装配插在检查与执行之间 |
| L3 | 按职责分层的检查链 | 按工具类型分叉（delete 先路径、shell 先动作），职责错层（注册判定/信任预算混入 SA1） |
| L4 | 单一职责的判定 | 路径合法性散三处、validate_delete 对 delete 跑两遍 |

**结论**：要动的是 **L2 + L3 一起**——先在 L2 把"检查"拆成"解析/路由/检查/确认"的清晰阶段，L3 才能在稳定边界内按职责重排。只动 L3 会返工。

## 四、重构总原则（人类全局逻辑）

### 4.1 一次工具调用的人类生命周期模型

对**每一个** call，人脑的判定顺序恒为（由粗到细、由拒绝到放行）：

```
① 认领   —— 这是什么动作？（已注册？属哪类？）
② 路由   —— 属不属于本链？（PATH_TOOLS 门；非路径工具放行）
③ 合法性 —— 输入对不对？（空/穿越/语法/存在）
④ 危险+权限 —— 危险命令组在前、权限三线在后（同层内顺序固定，仅一处 = check_before_execute）：
               危险命令组（仅含 command 时）：危险命令 + 风险命令（一组）
               权限三线：读线 / 写线 / 删线；dual 与 bash 的文件动作复用对应线
                     （区域：系统/代码/授权/工作区内外 → 放行/确认/拒绝）
⑤ 确认   —— 要不要人工确认？（HITL / 信任豁免 / 临时授权）
⑥ 执行   —— 沙箱 + 跑
```

### 4.2 三条铁律

1. **一段一责**（SRP/SLAP）：每个阶段一个函数、一个抽象层。
2. **顺序固定**（KISS-DIRECT）：①②③④⑤⑥ 对所有工具完全一致。
3. **不分叉**：工具差异只体现在**某阶段选用的判定函数不同**——③ 是「危险命令组」（shell 命令危险度：危险命令 + 风险命令），④ 是「读/写/删三线」按动作分派（**delete = 删线，与读写并列，非特例**）；dual 与 bash 的文件动作**复用这三线**。绝不改变阶段顺序。

### 4.3 生命周期落地骨架（每 call）

```
对于每个 call：
① 认领(L2解析)  → ② 路由(PATH_TOOLS门) → ③ 合法性(路径初查)
→ ④ 危险+权限 = check_before_execute
      4-1 危险命令组（仅含 command 的 bash）
      4-2 读写删三线（按动作分派：delete=删线；dual/bash 文件动作复用）
→ ⑤ 确认(HITL+信任) → ⑥ 沙箱汇合执行
```

### 4.4 与现状的根本差异

现状是"**按工具类型分叉**"（delete 路径先、shell 动作先）；目标是"**按职责分层**"（全体统一，差异只在层内选函数）。

## 五、L2 目标管线设计

### 5.1 目标形状

`handle_action` 保持单入口，但把"检查"显式化为可编排的**阶段调用**，管线为：

```
handle_action(agent, parsed):
  1. calls = parse_calls(parsed)                    # 解析+归一(认领: 未注册/未知工具在此暴露)
  2. if not calls: emit error; return
  3. emit thought + action 预览                      # 前端齿轮先行
  4. exec_calls, denied, events = await safety_pipeline(calls)   # 检查+确认(黑盒下沉, 见第六章)
  5. results = await execute_tools(exec_calls, ...) # 执行(三分支, 不动)
  6. obs = await build_observation(...)            # 观察
  7. return_direct 检查
```

### 5.2 相对现状的改动

- **L2-1**：`safety_pipeline` 仍是黑盒，但**内部按第 6 章的阶段分层**；L2 只负责"编排顺序"，不掺检查逻辑。
- **L2-2**：`parse_calls` 阶段（现 `_build_call_list`）承担"未注册/未知工具"识别 → 见第 7 章**裁定点 1**（已裁定：上移）。
- **L2-3**：retry 回调装配不单独成"步"，归入执行段（随 `execute_tools` 调用点）。

> 说明：L2 的 9 步本身形状接近合理，**本方案不以"拆函数"为目标**，只做"责任归位"（未注册归解析、检查归检查、执行归执行）。

## 六、L3 目标检查链设计

### 6.1 目标阶段链（每 call 依次走）

```
for call in calls:
  ① 认领     : resolve_registered_tool  → 未注册? (归属见裁定点1)
  ② 路由      : normal_name not in PATH_TOOLS → 放行(不属本链)
  ③ 合法性    : precheck_path_legality   (唯一初查点: 空/穿越/语法/存在)
  ④ 危险+权限 : check_before_execute      (内部固定"危险命令组→读写删三线")
  ⑤ 确认      : HITL / 信任豁免 / 临时授权
  ⑥ 汇合执行   : sandbox_gate
```

> 落地骨架见 4.3（本章不重复）。

### 6.2 阶段 ④ `check_before_execute` 目标内部顺序（人类顺序 = 危险在前、权限在后）

```
check_before_execute(tool, params):
  1. 危险命令组(仅含 command 的 shell/bash, 老陈裁定为一组):
     a. 自杀/危险命令
     b. 风险命令
     → 命中即 blocked
  2. 权限三线(按"动作"分派到读/写/删; 与工具类型无关; 三线统一出 SafetyResult 封装口):
     a. 读动作 → 读线 check_read_permission(path)        (方案A: 无 params 死参)
     b. 写动作 → 写线 check_write_permission(path)       (方案A: 无 params 死参)
     c. 删动作 → 删线 check_delete_permission(path, params) (删根底线→路径禁区→工作区边界; params 供 recursive)
        ← delete 工具即走删线; dual/bash 的文件删除动作同样走删线
     → 命中即 blocked / requires_confirmation
  3. 返回 SafetyResult
```

**关键（老陈裁定：工具关系模型）**：
- delete **不是特例**，它就是**删线**；与读线、写线并列。
- **三线是唯一的权限判定入口**：delete 直接走删线；dual（copy/move/compress/extract/rename）与 bash 内的文件动作，**按各自动作复用对应线**（删动作→删线、写动作→写线、读动作→读线）。
- delete 的删线判定**唯一一处执行**，删除现状顶部 `:196` 的提前计算，消除 L3-5 重复。

def check_whitelist(file_path: str, allowed_paths: List[Path]) -> bool:
    """白名单前缀匹配 — 小欧 2026-10-15

    自 path_safe_check.validate_path(:357-382) 迁出。路径 realpath 化后, 与每个白名单根做
    parts 前缀比对; 白名单根为盘根(如 D:\\)时走盘根特例分支(整盘同盘即算命中)。
    比对统一走小写形式(Windows 路径不区分大小写)。

    Args:
        file_path: 待检查路径
        allowed_paths: 已解析的白名单根列表, 由 resolve_allowed_paths 取得

    Returns:
        命中任一白名单根返回 True; 全部未命中(含全部条目不可解析)返回 False。
    """
    real_path = Path(os.path.realpath(os.path.expanduser(file_path)))
    for allowed in allowed_paths:
        try:
            allowed_real = Path(os.path.realpath(allowed))
            real_parts = tuple(p.lower() for p in Path(real_path).parts)
            allowed_parts = tuple(p.lower() for p in Path(allowed_real).parts)

            if len(real_parts) >= len(allowed_parts):
                prefix_match = all(real_parts[i] == allowed_parts[i] for i in range(len(allowed_parts)))
                if not prefix_match:
                    continue

                if len(allowed_parts) == 1 and allowed_parts[0].endswith((":", ":\\", ":/")):
                    if str(real_path).lower() == str(allowed_real).lower() or real_parts[0] == allowed_parts[0]:
                        return True
                else:
                    # 2026-10-15 小欧 - P1-13: 此处原重复判 len 条件, 外层 if 已保证, 恒为真(死代码)。
                    return True
        except (ValueError, OSError, TypeError):
            # 坏条目(None/非路径对象)跳过=该条目不提供权限。TypeError 必须在内: realpath(None) 抛它。
            # 2026-10-15 小欧 - P3: 补 debug 日志(不用 warning: 每次路径检查都调, 会刷屏)。
            logger.debug(f"[path_check_common] 白名单条目无法解析, 已跳过: {allowed!r}")
            continue
    return False

    """三线共用: 遍历路径参数逐个判定, 首个越权即返回 — 小欧 2026-10-17

    read/write/delete 三条线的**工具级**封装口共用此循环(DRY), 只把"单路径判定"作为
    judge 回调注入; 空值硬拦 / 内容型跳过 / 路径解析 / 异常 fail-closed 四件事集中于此,
    各线不再重写(原 path_legality_router 内联循环, 2026-10-17 下沉到本模块)。
    """
    # 惰性导入: resolve_path_param 在 dual_path_check, 本模块被三线导入, 顶层导入会成环
    from app.safety.dual_path_check import resolve_path_param

                continue                                # 真没传(见 precheck 同处裁定)
            value = params[key]
            if key in CONTENT_PARAM_KEYS and not isinstance(value, str):
                continue                                # data 内容型参数: 内联结构非路径
            _empty = reject_reason_empty_path(value)    # 空值真源在原子

                return SafetyResult(blocked=True, severity="dangerous", message=_empty)

        return SafetyResult(blocked=True, severity="dangerous", message=f"路径安全检查异常: {e}")

def validate_delete(file_path: str, allowed_paths: Optional[List] = None) -> Tuple[bool, Optional[str], Optional[str]]:
    """删线validate_delete — 小欧 2026-10-15

    Returns:
        (is_valid, error_message, category), category ∈ {"system", "non_system", None}
        命中禁区时 category 原样带回, 供调用方按 system/non_system 分流。

        return False, f"路径验证失败: {str(e)}", "system"


def check_delete_risk(params: dict) -> SafetyResult:
    """delete 专属差异判定(R3-R6) — 由 delete_safety 迁入 — 小欧 2026-10-17

    恒返回 SafetyResult(从不用 None), 使调用侧可用 `delete_risk is not None`
    区分"是delete工具", R3 直接内联构造放行产物。
    R1/R2 由 _check_known_risks(check_tool_path_permission) 覆盖, 此处不重复。
    补D: 递归删除走 os.walk 时各子路径逐项判定, 任一越权即 R6。
    由总闸内调, R1/R2 回路径层覆盖 — 小欧-2026-10-14
    函数体逐字复制 delete_safety.check_delete_risk, 逻辑一字不改, 仅改日志前缀。
    """
    path = str(params.get("path") or "").strip()
    _rv = params.get("recursive", False)
    recursive = (str(_rv).strip().lower() in ("1", "true", "yes", "on"))  # 防 LLM 传字符串 'false' 被 bool() 当真

    try:                                                        # 路径归一化
        p = Path(os.path.expanduser(path)).resolve()
    except Exception as e:
        # fail-closed: 归一化失败即判 blocked, 宁可拒不可放(不依赖下一道防线)。
        logger.warning(f"[delete_path_check] 路径归一化失败, 按拒绝处理: {path!r} ({e})")
        return SafetyResult(blocked=True, requires_confirmation=False,
                            message=f"删除路径非法: {path}", severity="dangerous")

    try:
        allowed_roots = get_allowed_roots(session_workspace_paths())  # 单源: 项目根+授权目录+会话目录(⑫)
    except Exception as e:
        # fail-closed: 根集读不出时若继续判, inside 恒 False → 全部路径误判区外(R5/R6), 语义翻转
        logger.warning(f"[delete_path_check] 允许根读取失败, 按拒绝处理: {e}")
        return SafetyResult(blocked=True, requires_confirmation=False,
                            message=f"删除安全判定不可用(根集读取失败): {e}", severity="dangerous")

    inside_proj = any(p == root or root in p.parents for root in allowed_roots)

    # --- R6 全部允许根外递归 → 拒 ---
    if (not inside_proj) and recursive:
        return SafetyResult(blocked=True, message=f"禁止删除工作区外目录: {path}", severity="dangerous")

    # --- R4 允许根内递归 → 确认 / R5 允许根外普通 → 确认 ---
    if (inside_proj and recursive) or (not inside_proj):
        return SafetyResult(requires_confirmation=True, blocked=False,
                            message=f"删除需确认: {path}", severity="risk")

    # --- R3 允许根内普通 → 放行(免确认), 恒非None ---
    return SafetyResult(blocked=False, requires_confirmation=False,
                        message="", severity="safe")


def guard_forbidden_delete(file_path: str) -> Optional[str]:
    """删除硬底线: 命中禁区返回禁止原因, 允许删除返回 None — 系统层持一份 — 小欧 2026-10-17

    判据全部走 path_classify_category 单源, 本层不持名单; 与 tool 层
    path_utils.check_path_five_level 第⑤级同口径(各持一份调用壳, 判据同源)。
    """
    try:
        Path(file_path).expanduser().resolve()      # 归一化探针: 解析失败即 fail-closed
    except Exception as e:
        return f"安全校验: 路径解析失败({e})"
    if os.name == "nt" and is_system_protected_path(file_path, "delete"):
        return f"禁止删除系统目录: {file_path}"
    if is_disk_root(file_path):
        return f"禁止删除磁盘根目录: {file_path}"
    if is_code_root_path(file_path):
        return f"禁止删除代码目录(含其内部子级): {file_path}"
    _hit = is_allowed_root_itself(file_path)
    if _hit == "allowed_root_itself":
        return f"禁止删除项目根/授权根目录: {file_path}"
    if _hit == "allowed_root_ancestor":
        return f"禁止删除项目根/授权根上级目录: {file_path}"
    return None


def delete_permission(path: str, params: Optional[dict] = None) -> SafetyResult:
    """delete 单路径权限口(唯一封装口) — 供 dual_path_check / shell_path_check 复用 — 小欧 2026-10-17

    把三件事有机串成一条链, 统一返回 SafetyResult:
      ① guard_forbidden_delete — A族(系统目录/磁盘根/代码目录/允许根本身+上级) → 命中即拒绝
      ② validate_delete      — R1/R2(空值/穿越/禁区分类/白名单/临时授权) → 命中禁区即拒绝
      ③ check_delete_risk    — R3-R6(区外递归→拒 / 根内递归→确认 / 区外→确认 / 根内普通→放行)
    三函数原功能全部保留, 命中哪条即出对应的 拒绝/要确认/放行。
    白名单外(② 返 category=None)不在此硬拦, 交 ③ 定 拒绝/确认。
    消费方: path_tool_safety_checker(删工具) / shell_path_check(删源) / dual_path_check(删除动作)。
    """
    # ① A族/删根硬底线
    _guard = guard_forbidden_delete(path)
    if _guard:
        return SafetyResult(blocked=True, message=_guard, severity="dangerous")
    # ② R1/R2 路径禁区(系统/代码目录/允许根本身 → 硬拦; 白名单外 → 交 ③)
    _ok, _msg, _category = validate_delete(path)
    if not _ok and _category:
        return SafetyResult(blocked=True, message=_msg, severity="dangerous")
    # ③ R3-R6 工作区边界
    _params = dict(params or {})
    _params.setdefault("path", path)
    return check_delete_risk(_params)


def check_delete_permission(tool_name: str, params: Dict[str, Any]) -> SafetyResult:
    """删线工具级权限口 — 供 path_legality_router [6] 直调 — 小欧 2026-10-17

    遍历路径参数, 逐条走 delete_permission(带本次调用 params, 供 recursive 生效)。
    """
    return common.check_tool_paths(
        tool_name, params, lambda p: delete_permission(p, params))

def check_dual_permission(tool_name: str, params: Dict[str, Any]) -> SafetyResult:

        params: 归一化后的工具参数

    Returns:
        SafetyResult: 首个命中即返回该参数的结果(blocked / requires_confirmation);

    param_map = DUAL_ACTION_PARAMS.get(tool_name)
    if param_map is None:

        #   fail-closed 按写线最严处理(与 entry 未知档位同口径), 并打 warning 留痕。

        logger.warning(
            f"[dual_path_check] 工具 {tool_name} 声明为 dual 但 DUAL_ACTION_PARAMS 无声明, "
            f"按写线(fail-closed 最严档)处理; 请补声明表")

        hit = False
        for key in PATH_PARAM_KEYS:
            value = params.get(key)
            if value is None:
                continue
            hit = True

                return result
        if not hit:
            return SafetyResult(blocked=True, severity="dangerous",
                                message=f"工具 {tool_name} 声明为 dual 但调用不带任何路径参数")
        return SafetyResult.pass_result()
    for key, action in param_map.items():

        if value is None:
            continue

        if action == "read":
            result = read_path_check.read_permission(real_path)
            if result.blocked or result.requires_confirmation:
                return result
            # 系统源外泄拦截: 读线放行系统目录, 但搬运类工具不得以系统目录为数据源
            cat, msg = classify_forbidden_path(real_path, "write")

                real_path, {"recursive": os.path.isdir(real_path)})

分层: 取路径/分模式(本模块) 与 判权限(delete/write/read_path_check) 严格分开(老陈 2026-10-16 裁定)。

关注点(按用途归类):
  一、只读白名单    —— SHELL_READONLY_PREFIXES / SHELL_FAST_CHANNEL_FORBIDDEN / is_shell_readonly_whitelisted
  二、文本规范化    —— shell_normalize_command / shell_blank_out_quotes
  三、动作模板      —— READ_VERBS/WRITE_VERBS/DELETE_VERBS/DUAL_VERBS 四张动词表(3 核心 + dual)
  四、路径抽取      —— shell_extract_abs_win_paths / _extract_shell_move_paths
  五、动作解析入口  —— parse_shell_action(一条命令 → 模式 + 各线路径)

一、要解析哪些（解析对象清单）
解析 = 从一条 shell 命令里，抽出**"谁对哪个路径做了什么动作"**。要解析的要素分五维：

维度1 · shell 种类（语法三套，必须分开处理）

壳	特征
PowerShell (ps7/ps5)	-Param 命名参数、$env:、反引号转义、; 分隔、对象管道
CMD	/s /f /q 开关、%VAR%、^ 转义、& || && 分隔
bash (Git Bash/WSL)	-rf 字母开关、~、| 管道、&& ||、单双引号语义不同
维度2 · 命令文本结构 多语句分隔（; && || & |）、引号（"..." '...'）、转义（\ ^ 反引号）、子表达式（$( ) ` ` %X%）、变量/环境（$env:X $X %X%）、续行。

维度3 · 动作种类（这就是你说的"每一种解析"，4 种）

读：Get-Content/type/cat/Get-ChildItem/dir/ls/Get-Item/Select-String/...
写：Set-Content/Add-Content/Out-File/touch/New-Item/Copy-Item + 重定向 > >>
删：Remove-Item/del/erase/rm/rd/rmdir + 递归/强制开关
搬移(dual)：Move-Item/Rename-Item/mv/move/ren —— 源(删) + 目标(写)
维度4 · 路径参数形态 位置参数 vs 命名参数（-Path/-LiteralPath/-Destination/-NewName）、明确路径 vs 通配符（* ?）、绝对(盘符/UNC)/相对/~//$env:/变量、多值数组、管道来源（Get-ChildItem X | Remove-Item——删目标来自上游）。

维度5 · 修饰开关（决定危险度，必须随动作一起解析） 删：-Recurse/-Force/-rf/-r -f/del /s /q/rd /s；写：-Force/-Encoding/>>追加/-NoClobber；读：-Raw/-Tail。

二、总体解析逻辑
核心转变：从"一条命令 = 一种模式"（我上一版）改为 "一条命令 = 动作清单（可多条）"——Copy-Item a b; Remove-Item c 应产出 [写(b), 删(c)]，不是被并成一种。

输入: 原始命令 command + cwd + shell_type(缺省则自动识别)
 │
 ├[0] 预处理/归一   换行归一; 生成两份文本: extract_src($env展开) / intent_src(引号涂空)
 │
 ├[1] 语句拆分      按 ; && || | & 与换行拆成"原子命令序列"(引号/子表达式内不拆)
 │
 ├[2] 逐句分类      每句: 识别动作种类(读/写/删/dual), 一条句可多命中(取严)
 │
 ├[3] 分派解析      按种类调 parse_read / parse_write / parse_delete / parse_move

 ├[4] 抽路径+标注   抽出目标路径, 并贴上动作属性(递归/强制/追加/通配/管道来源)

每条记录形如：Action(mode, paths, flags, shell, source_stmt)。

#### 13.1.3 别及权限判定-命令解析的概要设计要求
一、先定性：解析在链条里的位置
命令 ──►【1 解析】──► 中间产物 ──►【2 处理权限】──► 放行/拒绝/需确认
                ↑ 本次要设计的
铁律：解析只负责"从命令里提取事实"，一个权限判据都不做；权限处理只负责"拿事实去判"。两者零耦合。

二、解析的【输入】——就三样
输入	类型	作用
command	str	待解析的原始命令串
shell_type	ps7/ps5/cmd/bash	决定语法（同一动词三套写法）——现在缺这个，是根本缺陷
cwd	str/None	相对路径的解析基准
旧设计只吃 command 一个参数、且不认壳 → 只能用一批正则"蒙"，必然又简又漏。

三、解析【什么】（解析对象 = 最佳对象）
解析对象不是"整条命令属于哪种模式"，而是命令里的"路径-动作 原子事实"。

一条命令 = 若干条原子事实。每条原子事实由三元组构成：

       动词(Verb)     +   路径实参(PathArg)   +   修饰开关(Modifier)
   Remove-Item              C:\data\x.txt           -Recurse -Force
        │                          │                        │
        ▼                          ▼                        ▼
     动作性质(read/           目标路径               动作属性
     write/delete)          (绝对化)             (recursive/force/append)
解析就是把这个三元组归一成权限处理能直接消费的形式。

必须解析的 4 个子要素：

动词 → 动作性质：读 / 写 / 删 / 搬移（搬移=源删+目标写）
路径实参 → 目标路径（位置参数 / 命名参数 -Path/-LiteralPath/-Destination）
修饰开关 → recursive / force / append(>>) 等
壳语法 → 同一动作在 ps7/ps5/cmd/bash 里的动词名、开关、写法
要跨过的难点（这就是体量的来源）： 多语句分隔（; && || | &）、引号/转义、子表达式、变量（$env:X %X% ~）、通配符、管道来源（GCI X | Remove-Item）。

四、解析【返回】什么（最佳返回契约）
返回：动作清单 List[PathAction]——不是"命令模式"，而是**"路径 × 动作"的扁平清单**。

PathAction:
    kind   : "read" | "write" | "delete"      # 动作性质
    path   : str                              # 已绝对化/归一的目标路径
    flags  : dict                             # {"recursive":bool,"force":bool,"append":bool}
    origin : str                              # 来源语句/动词（留痕用）

parse_shell_action(command, shell_type, cwd) -> List[PathAction]
为什么这是最佳返回：

权限处理三种入口 check_read_permission(path) / check_write_permission(path) / check_delete_permission(path, flags) 签名正好对上——返回即输入，零转换、零中间层（KISS-DIRECT）。
一条命令多动作：Copy-Item a b; Remove-Item c → [write(b), delete(c)]，不再被错误合并。
搬移天然拆两条：mv a b → [delete(a), write(b)]。
修饰随动作走，不随命令走：rm -rf X; echo Y 的 recursive 只挂在删 X 上。
对比：旧设计返回"一个模式 + 两列路径"，是一种命令级抽象，遇到多动作就塌；返回清单是动作级抽象，天然可组合。

#### 13.2.1 系统中关于 shell 命令解析、权限判定流程的主要问题

#### 13.2.2 新的需求梳理分析

**需求总纲**：把 shell 命令通道的"解析"，从**命令级、单模式、无壳**，重建为**动作级、多动作清单、三壳分治**；解析与判定**彻底零耦合**。解析产物直接等于权限处理的输入。

**功能需求**：

| 编号 | 需求 | 来源 | 说明 |
|---|---|---|---|
| R1 | 解析输入 = `command` + `shell_type` + `cwd` 三要素 | 13.1.3 | shell_type 必带（缺省内部自动识别，复用 `_looks_like_*`） |
| R2 | 解析对象 = `(动词, 路径实参, 修饰开关)` 三元组 | 13.1.3 | 归一为 `(动作性质, 绝对路径, flags)` |
| R3 | 解析返回 = **动作清单 `List[PathAction]`** | 13.1.3 | 动作级抽象，一条命令可多动作；**非命令级单模式** |
| R4 | 权限处理五情况由清单自然导出 | 13.1.1 | 空清单=8.0；单 kind=8.1/8.2/8.3；delete+write=8.4 |
| R5 | 三壳语法分治 | 13.1.3 维度1 | ps7/ps5/cmd/bash 各自动词表与开关 |
| R6 | **每种解析单独一文件**（读/写/删/搬移），各约 500 行 | 老陈口头 | 覆盖 3 壳 × 多动词 × 多参数形态 |
| R7 | 解析与判定零耦合 | 13.1.3 铁律 | 解析一个权限判据都不做 |
| R8 | 既有安全不回退 | AGENTS.md | 沙箱宽表/只读白名单/危险/中风险/自杀/三线/fail-closed 全保留 |
| R9 | 契约明确、无 backward | AGENTS.md | 上接 router[8]，下接三线 `check_*_permission`；旧函数/旧签名直接退场不留转发壳 |
| R10 | 遵守 10 大规范 + 公用函数先查后建 | AGENTS.md | DRY 动词单源、KISS-DIRECT、SRP、YAGNI |

**需求边界（明确不做）**：

- ❌ 不做完整 shell 语法树/词法器（YAGNI）；动作识别仍以"动词表 + 参数解析"为主。
- ❌ 不改动危险/中风险/自杀三层逻辑（仅将 shell_type 正确接入）。
- ❌ 不做通配符的文件系统展开（只标注 `wildcard` 标志，交沙箱预检）。
- ❌ 不引入任何向后兼容别名/转发壳。

**验收导向的需求一句话**：`parse_shell_action(command, shell_type, cwd) -> List[PathAction]`，输出可直接 `for a: dispatch(a.kind).check(a.path, a.flags)`，且一条命令多动作不丢。

#### 13.2.3 新的详细设计指导说明书

##### 13.2.3.1 设计目标与总原则

- **目标**：解析层输出"路径×动作"清单；判定层消费之。一条命令 = 若干 `PathAction`。
- **总原则**：解析与判定零耦合（R7）；动作级抽象（R3）；三壳分治（R5）；动词单源（DRY）；每动作一文件（R6）；简单直线（KISS-DIRECT）；不做未用抽象（YAGNI）；不留兼容（禁 backward）。

##### 13.2.3.2 总体架构与调用链（目标态）

```
path_tool_safety_checker.check_before_execute(tool, params)
  ├ [4-0] shell_process_guard.check_shell_self_kill(只读白名单需 shell_type)   ← 不变
  ├ [4-1] shell_danger_command / shell_command_risk（已分壳, 不变）
  └ [4-2] path_legality_router.check_tool_path_permission(tool, params)
            └ [8] bash → shell_path_check.check_shell_permission(command, cwd, shell_type)  ← 新增 shell_type
                      │
                      ├─【解析】shell_parse.parse_shell_action(command, shell_type, cwd)
                      │         → List[PathAction]
                      └─【判定】for a in actions:
                                  read_path_check.check_read_permission(a.path)
                                  write_path_check.check_write_permission(a.path)
                                  delete_path_check.check_delete_permission(a.path, a.flags)
```

关键改动点：**`shell_type` 从 params 一路透传到解析器**（修复 A1）；返回由"两列路径"升级为**动作清单**（修复 A2）。

##### 13.2.3.3 数据契约

```python
@dataclass
class PathAction:
    kind: str        # "read" | "write" | "delete"
    path: str        # 已绝对化/归一的目标路径
    flags: dict      # {"recursive": bool, "force": bool, "append": bool, "wildcard": bool}
    origin: str      # 来源语句/动词（留痕用）
```

- 搬移 `mv a b` → 展开为两条：`PathAction("delete", a, ...)` + `PathAction("write", b, ...)`。
- 五情况映射：`actions 为空 → 8.0`；仅 read → 8.1；仅 write → 8.2；仅 delete → 8.3；delete+write（搬移）→ 8.4。

| 3 | `shell_parse/parse_read.py` | **读解析**（3 壳） | `parse_read_action(stmt, shell, cwd)` |
| 4 | `shell_parse/parse_write.py` | **写解析**（含重定向 `>`/`>>`、追加） | `parse_write_action(stmt, shell, cwd)` |
| 5 | `shell_parse/parse_delete.py` | **删解析**（含递归/强制开关） | `parse_delete_action(stmt, shell, cwd)` |
| 6 | `shell_parse/parse_move.py` | **搬移解析**（源/目标分离） | `parse_move_action(stmt, shell, cwd)` |
| 7 | `shell_parse/parse_shell_action.py` | **唯一入口**：拆句 → 调 4 解析器 → 汇总 | `parse_shell_action(command, shell_type, cwd)` |

- "每种解析" = 3~6 号 4 个文件，各含 3 套壳语法，体量约 500 行级。
- 现有 `shell_command_process.py` **保留**沙箱宽表（`SHELL_WRITE_INTENT_RE` 等，executor 消费）、只读白名单、规范化函数；其"动作分线"部分迁入本包。

##### 13.2.3.6 三壳解析规范（设计要点）

| 动作 | PowerShell(ps7/ps5) | CMD | bash |
|---|---|---|---|
| 读 | Get-Content, gc, cat, type, Get-ChildItem, gci, ls, dir, Select-String | type, dir, findstr, more | cat, ls, head, tail, grep |
| 写 | Set-Content, Add-Content, Out-File, New-Item, Copy-Item, `>`/`>>` | echo>file, copy, `>`/`>>` | `>`, `>>`, tee, touch, cp |
| 删 | Remove-Item(-Recurse/-Force), del, rd, rmdir | del(/s /q /f), rd(/s), rmdir(/s) | rm(-rf, -r, -f), rmdir |
| 搬移 | Move-Item(-Destination), Rename-Item(-NewName) | move, ren | mv, move |

- 修饰解析：`-Recurse/-Force`(ps) · `/s /q /f`(cmd) · `-rf/-r/-f`(bash) → `flags`，**随动作绑定**（修复 B5）。
- 路径实参：位置参数 + 命名参数（`-Path/-LiteralPath/-Destination/-NewName`）；`~`/`$env:`/`%VAR%` 归一（修复 B2/B4）。
- 管道：`GCI X | Remove-Item` 识别为"上游产物删"，目标记为上游路径并标注来源（修复 B3）。

##### 13.2.3.7 与权限处理的接口（五情况映射）

| 情况 | 动作清单 | 判定调用 |
|---|---|---|
| 8.0 非路径 | `[]` | 直接 `pass_result()` |
| 8.1 单 read | `[read p...]` | `check_read_permission(p)` |
| 8.2 单 write | `[write p...]` | `check_write_permission(p)` |
| 8.3 单 delete | `[delete p...]` | `check_delete_permission(p, {recursive})` |
| 8.4 dual(move) | `[delete a, write b]` | 源 `check_delete_permission(a)`、目标 `check_write_permission(b)` |

- 通道 B 语义（无弹窗）：**delete 的 `blocked` 即拒，write/read 的 `requires_confirmation` 当通过**——统一在判定层表达，不再散落（修复 C3）。
