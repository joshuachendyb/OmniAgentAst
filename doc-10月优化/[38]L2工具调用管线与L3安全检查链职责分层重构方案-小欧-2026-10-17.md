## 一、背景与目标

### 1.1 背景
北京老陈指出：当前安全检查相关代码"**顺序乱、功能切分乱**"，要求**从全局逻辑、按人的思维模式**判断"哪些该在哪里"。经初查确认：乱象不是 L3（安全检查链）内部的孤立问题，根因在 **L2（工具调用管线）把"安全检查"当成一个 400 行黑盒塞进管线，未在 L2 层把"解析/路由/检查/确认"分开**。故本方案一次性覆盖 **L2 + L3**。

### 1.2 目标
1. 把一次工具调用的生命周期按**人类直觉**重新分层：**认领 → 合法性 → 危险性 → 权限 → 问人 → 执行**。
2. 让每一级**一段一责、顺序对所有工具一致、绝不按工具类型分叉**。
3. 消除职责错层（未注册判定、信任预算混入检查）、重复判定（delete 路径跑两遍）。

### 1.3 边界
- 本方案**只做设计与分析，不改任何代码**。
- 目标架构给出，具体函数名/文件落点在第 5、6 章；实施须老陈对本方案第 7 章裁定点确认后再动码（**裁定已于 v1.1 完成，见 7.2**）。

## 二、现状层级树（L0~L4）

### 2.1 层级树

```
L0 服务入口骨架
   HTTP /chat → stream_orchestrator → agent_runner → run_react_cycle (backend/app/services/agent/react_loop.py:93)
        │
L1 主流程核心 = ReAct 循环体（while llm_call_count < max_steps）
        │  THINKING(调LLM) → _dispatch_handler 按 type 分派 (react_dispatch.py:55)
        ▼
L2 【EXECUTING 段】handle_action 的 9 步管线 (handle_action.py:314)
        1 _build_call_list        解析 parsed → all_calls
        2 emit ThoughtStep + ActionStep 预览
        3 check_safety_and_confirm ◄──── 安全检查链在此(黑盒)
        4 canonical ActionStep emit
        5 execute_tools           三分支执行(单/并行/顺序) (tool_runner.py:20)
        6 tool_retry_engine(隐蔽)
        7 build ObservationContext
        8 build_observation
        9 return_direct 检查
        │
L3 【安全检查链】check_safety_and_confirm 内部 (safety_gate.py:171)
        SA1门前初查 · SA2信任预查 · SA3总闸 · SA4 delete差异 · SA5路径层 · SA6 HITL · SA7沙箱 · SA8删根底线
        │
L4 各 SA 内部

        SA4/SA8 check_delete_permission (delete_path_check.py:195)
        API 旁路 tool_facade.execute_tool (:127) 直调 SA3
```

### 2.2 三个定位问答

1. **"这是主流程吧？"** —— 是。它是 L2 的第 3 步，每次工具调用都必过，属主流程关键路径，不是旁枝。
2. **"主流程下有没有次级流程？"** —— 有，就是 L2 的 9 步管线。而且它自己也有顺序问题：现在 3(安全检查) 和 5(执行) 之间夹着 4(retry 回调装配)，7/8 观察构建又在执行之后。
3. **"三级流程要不要也梳理？"** —— 要。因为 L3 的乱（SA1 混四责、delete/shell 顺序分叉）根因是 L2 把"安全检查"当成一个黑盒塞进第 3 步，没有在 L2 层就把"解析/路由/检查/确认"分开。只动 L3 不动 L2，等于在错误的分层上修内部顺序，治标不治本。

### 2.3 一句话乱点小结

| 级 | 该是什么 | 现在乱在哪 |
|----|---------|-----------|
| L1 | 纯调度循环 | 基本干净 |
| L2 | 工具调用生命周期：解析→[路由]→检查→确认→执行→观察 | 把 9 步混在一个 handler，且"安全检查"是一个 400 行黑盒；retry 装配插在检查与执行之间 |
| L3 | 按职责分层的检查链 | 按工具类型分叉（delete 先路径、shell 先动作），职责错层（注册判定/信任预算混入 SA1） |
| L4 | 单一职责的判定 | 路径合法性散三处、validate_delete 对 delete 跑两遍 |

**结论**：要动的是 **L2 + L3 一起**——先在 L2 把"检查"拆成"解析/路由/检查/确认"的清晰阶段，L3 才能在稳定边界内按职责重排。只动 L3 会返工。

## 四、重构总原则（人类全局逻辑）

### 4.1 一次工具调用的人类生命周期模型

对**每一个** call，人脑的判定顺序恒为（由粗到细、由拒绝到放行）：

```
① 认领   —— 这是什么动作？（已注册？属哪类？）
② 合法性 —— 输入对不对？（空/穿越/语法/存在）
③ 危险性(命令组) —— shell 危险命令 + 风险命令（一组，仅含 command 时）
④ 权限(三线)     —— 读线 / 写线 / 删线；dual 与 bash 的文件动作复用对应线
                     （区域：系统/代码/授权/工作区内外 → 放行/确认/拒绝）
⑤ 问人   —— 要不要人工确认？（HITL / 信任豁免 / 临时授权）
⑥ 执行   —— 沙箱 + 跑
```

### 4.2 三条铁律

1. **一段一责**（SRP/SLAP）：每个阶段一个函数、一个抽象层。
2. **顺序固定**（KISS-DIRECT）：①②③④⑤⑥ 对所有工具完全一致。
3. **不分叉**：工具差异只体现在**某阶段选用的判定函数不同**——③ 是「危险命令组」（shell 命令危险度：危险命令 + 风险命令），④ 是「读/写/删三线」按动作分派（**delete = 删线，与读写并列，非特例**）；dual 与 bash 的文件动作**复用这三线**。绝不改变阶段顺序。

### 4.3 生命周期落地骨架（每 call）

```
对于每个 call：
① 认领(L2解析)  → ② 路由(PATH_TOOLS门) → ③ 合法性(路径初查)
→ ④ 危险+权限 = check_before_execute
      4-1 危险命令组（仅含 command 的 bash）
      4-2 读写删三线（按动作分派：delete=删线；dual/bash 文件动作复用）
→ ⑤ 确认(HITL+信任) → ⑥ 沙箱汇合执行
```

### 4.4 与现状的根本差异

现状是"**按工具类型分叉**"（delete 路径先、shell 动作先）；目标是"**按职责分层**"（全体统一，差异只在层内选函数）。

## 五、L2 目标管线设计

### 5.1 目标形状

`handle_action` 保持单入口，但把"检查"显式化为可编排的**阶段调用**，管线为：

```
handle_action(agent, parsed):
  1. calls = parse_calls(parsed)                    # 解析+归一(认领: 未注册/未知工具在此暴露)
  2. if not calls: emit error; return
  3. emit thought + action 预览                      # 前端齿轮先行
  4. exec_calls, denied, events = await safety_pipeline(calls)   # 检查+确认(黑盒下沉, 见第六章)
  5. results = await execute_tools(exec_calls, ...) # 执行(三分支, 不动)
  6. obs = await build_observation(...)            # 观察
  7. return_direct 检查
```

### 5.2 相对现状的改动

- **L2-1**：`safety_pipeline` 仍是黑盒，但**内部按第 6 章的阶段分层**；L2 只负责"编排顺序"，不掺检查逻辑。
- **L2-2**：`parse_calls` 阶段（现 `_build_call_list`）承担"未注册/未知工具"识别 → 见第 7 章**裁定点 1**（已裁定：上移）。
- **L2-3**：retry 回调装配不单独成"步"，归入执行段（随 `execute_tools` 调用点）。

> 说明：L2 的 9 步本身形状接近合理，**本方案不以"拆函数"为目标**，只做"责任归位"（未注册归解析、检查归检查、执行归执行）。

## 六、L3 目标检查链设计

### 6.1 目标阶段链（每 call 依次走）

```
for call in calls:
  ① 认领     : resolve_registered_tool  → 未注册? (归属见裁定点1)
  ② 路由      : normal_name not in PATH_TOOLS → 放行(不属本链)
  ③ 合法性    : precheck_path_legality   (唯一初查点: 空/穿越/语法/存在)
  ④ 危险+权限 : check_before_execute      (内部固定"危险命令组→读写删三线")
  ⑤ 确认      : HITL / 信任豁免 / 临时授权
  ⑥ 汇合执行   : sandbox_gate
```

> 落地骨架见 4.3（本章不重复）。

### 6.2 check_before_execute 目标内部顺序（人类顺序 = 危险在前、权限在后）

```
check_before_execute(tool, params):
  1. 危险命令组(仅含 command 的 shell/bash, 老陈裁定为一组):
     a. 自杀/危险命令
     b. 风险命令
     → 命中即 blocked
  2. 权限三线(按"动作"分派到读/写/删; 与工具类型无关; 三线统一出 SafetyResult 封装口):
     a. 读动作 → 读线 check_read_permission(path, params)
     b. 写动作 → 写线 check_write_permission(path, params)
     c. 删动作 → 删线 check_delete_permission(path, params) (删根底线→路径禁区→工作区边界)
        ← delete 工具即走删线; dual/bash 的文件删除动作同样走删线
     → 命中即 blocked / requires_confirmation
  3. 返回 SafetyResult
```

**关键（老陈裁定：工具关系模型）**：
- delete **不是特例**，它就是**删线**；与读线、写线并列。
- **三线是唯一的权限判定入口**：delete 直接走删线；dual（copy/move/compress/extract/rename）与 bash 内的文件动作，**按各自动作复用对应线**（删动作→删线、写动作→写线、读动作→读线）。
- delete 的删线判定**唯一一处执行**，删除现状顶部 `:196` 的提前计算，消除 L3-5 重复。

### 6.3 阶段编号规范

- ① ② ③ ④ ⑤ ⑥ 全局唯一定义，各函数注释引用同一套编号。
- 禁止出现 `②-5`、重复 `③` 之类自造子号（消除 L3-4）。

## 七、职责迁移表 与 裁定点

### 7.1 迁移表（从哪 → 到哪）

| 职责 | 现状位置 | 目标位置 | 依据 |
|------|---------|---------|------|
| 未注册识别 | `safety_gate.py:204` | 解析层 `_build_call_list`（**已裁定：上移**） | 认领=解析职责 |
| PATH_TOOLS 范围门 | `safety_gate.py:212` | 路由阶段（保留在链首） | 路由职责 |
| 路径初查 | `safety_gate.py:220` | ④ 合法性层（唯一初查点） | 合法性职责 |
| 信任预查 | `safety_gate.py:230` | ⑤ 确认层（**已裁定：移入**） | 确认职责 |
| 危险命令 + 风险命令 | `path_tool_safety_checker.py:205/218/229` | ④ 危险命令组（保持在前，一组） | 危险前于权限 |
| 读/写/删权限判定 | delete: `:196`+SA5；read/write: SA5 | ④ 权限三线（唯一入口，按动作分派；dual/bash 复用） | 消除 delete 重复、三线归一 |

### 7.2 裁定结果（老陈 2026-10-17）

**裁定点 1：未注册工具判定放哪？ → 已裁定：上移到 L2 解析层。**
- `_build_call_list` 产出 calls 时即识别未注册 → 检查链不再管"存不存在"。
- 影响：改动解析段与拒绝事件产生点（需对齐前端 `reject_type` 消费）。

**裁定点 2：信任预查（SA2）是否移入确认阶段 ⑤？ → 已裁定：移入确认层。**
- 信任计算与"是否免确认"同层，符合 SRP；需确认不影响 SA3 对 `_skip` 的消费。

**裁定点 3：delete 的权限判定口径？ → 已裁定（老陈纠正工具关系模型）：**
- **delete 不是特例，就是删线**；权限层是**读/写/删三线**，delete 与读、写并列。
- **dual（copy/move/compress/extract/rename）与 bash 的文件动作，按各自动作复用对应线**（删动作→删线、写动作→写线、读动作→读线）。
- 删线判定**唯一一处执行**，删除现状 `check_before_execute` 顶部 `:196` 提前计算 + SA5 重跑的双调，消除 L3-5 重复。
