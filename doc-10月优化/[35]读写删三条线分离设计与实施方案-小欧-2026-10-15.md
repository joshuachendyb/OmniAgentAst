## 〇、设计总则（北京老陈裁定，本文档最高准则）

> **一、读、写、删是三条线 —— 能够分开的地方必须分开，需要合并的时候再合并。**
>
> **二、不能因为少数几个复合动作，就限制整个设计策略。**
>
> **三、模块平铺，不建子目录。**
>
> **四、禁止向后兼容 —— 该删的删干净，该改的改到位，不留转发壳、不设兼容入口、不保留旧名别名、不做"零破坏"妥协。**
> （AGENTS 10 大规范 · 日常编码第 6 条：**禁止 backward**，违反后果 = 新旧混杂、代码混乱）

**总则的落地口径**：

| 总则 | 落地方式 | 本文对应章节 |
|---|---|---|
| 一 · 分 | 三线策略**各成独立文件** | 3.3 |
| 一 · 合 | 三线公共判定骨架**合为一份** | 3.3.2 / 3.3.3 |
| 二 | 复合动作工具**独立成通道**，不拖累主干 | 1.2 / 2.4 / 3.4 |
| 三 | 三线文件直接置于 `app/safety/` | 3.1 |
| **四** | **`validate_path` 及 `mode` 参数彻底删除，调用点全量迁移** | **3.1 / 3.3.6** |

> **总则四的判据（2026-10-15 北京老陈当场纠正）**：把 `validate_path` 保留下来、内部转发三线，看似"零破坏"，实为**新旧混杂的向后兼容套壳** —— 新代码通过旧壳出入，旧壳永远删不掉。**"调用方不用改"从来不是优点，是违规证据。**

> **结论**：单一动作工具 **35 个（89.7%）**，动作类型**静态可定**；复合动作工具仅 **4 个（10.3%）**。
>
> **单一动作工具应享受的三线分离，不容许被 10.3% 的复合工具拖累。**

## 1.3 三线策略矩阵（决策中心在 SA3）

**实测**：`tool_safety_checker.py:366-428`（`_check_known_risks`）以 `category × mode` 二维分流：

| category | 读 | 写 | 删 |
|---|---|---|---|
| `system`（系统禁区） | **放行** | blocked 永不授权 | blocked 永不授权 |
| `non_system`（受保护区域） | **放行** | 确认 + `auth_path` | **blocked 永不授权** |
| `None`（白名单外） | **放行** | 确认 + `auth_path` | **blocked 永不授权** |

> 三线在**策略层已分离**（矩阵显式可读），但在**代码层未分离** —— 35 个单一动作工具被迫共用一段含复合特判的代码路径。

## 1.4 mode 的现有赋值方式（问题根源）

**现状**：mode 在**运行时**由 `if` 链推断（`path_safe_check.py:515-523`）：

```python
if mode is None:
    if normal_name in READ_ONLY_TOOLS:
        mode = "read"
    elif normal_name == "delete":
        mode = "delete"
    else:
        mode = "write"
```

| # | 缺陷 | 后果 |
|---|---|---|
| D1 | **运行时启发式** | 35 个静态确定的工具，每次调用都重算 mode |
| D2 | **复合工具拖累多数派** | `:558-560` 为 4 个复合工具插入参数级特判，**35 个单一工具共享这段含特判的代码** |
| D3 | `else` 兜底为 `write` | 方向 fail-closed（正确），但新工具的动作类型从未被显式声明 |
| D4 | **mode 不可静态审计** | 无法一眼看出"哪些工具走读线" |

## 1.7 缺陷乙详证：`is_system_protected_path` 职责错位

**现状**：位于 `app/utils/path_utils.py`（通用工具层），职责却是**安全判定**。

**成因**：守护规则 `app.tools` 禁 import `app.safety`（`test_architecture_boundaries.py:29-32`），工具层硬底线 `delete_file.py:88`（`_guard_forbidden_delete`）需直接调用，故下沉 `utils`。

**实测约束力**：`app/tools/` 对 `app.safety` 的**实际 import = 0 条**（7 处命中全为注释中记述 2026-08-12 的历史动作）。该规则自述为**阶段性护栏**：*"safety→task 规则待 A2-越层修复后追加；api禁safety/tools禁safety 待阶段二 A1/A4/A7 完成后追加"*。

> 挡路的不是"包名 safety"，而是"整个 safety 可被 `security.enabled` 关闭"这一**实质事实**。解法不是绕开，而是**把不会被关闭的那部分切出来**。

## 2.2 判定准则

### 【分】准则 —— 满足任一即应分开

| 判据 | 说明 |
|---|---|
| **D1 独占语义格** | 该线有其它线不存在的判定格 |
| **D2 独立数据结构** | 该线有独立返回类型/契约 |
| **D3 独立调度时机** | 该线在调用链不同阶段被求值 |
| **D4 独立生命周期** | 该线可单独增删改而不影响他线 |
| **D5 主体占比** | 该线覆盖多数派对象 |

### 【合】准则 —— 满足任一即应合并

| 判据 | 说明 |
|---|---|
| **M1 判定逻辑同一** | 各线走同一段代码，差异仅参数取值 |
| **M2 少数派拖累多数派** | 少数特例迫使多数派共用特判代码 —— **特例应独立成线** |
| **M3 mode 为坐标轴** | 各线是同一矩阵的行/列，非并列关系 |

## 2.4 裁定结论：正确的拆分粒度

**两种分法对比**：

| 分法 | 结果 |
|---|---|
| ❌ **按 mode 拆**（把 mode 拆成三份） | 4 个复合工具的特判仍混在主干中，35 个单一工具继续共用含特判代码。**少数派照样拖累多数派** |
| ✅ **按动作属性分**（单一动作 vs 多动作） | 35 个走零特判的干净主干；4 个复合工具 + bash 走独立通道。**互不牵连** |

| 通道 | 覆盖 | 动作类型来源 | mode 求值 |
|---|---|---|---|
| **通道 A：单一动作** | **35 个（89.7%）** | **注册期静态声明**（3.2） | **零推断、零 if 链** |
| **通道 B：多动作** | 4 个 + `bash`（10.3%） | 参数 / 命令内容动态派发 | 运行时按参数语义 |

**通道 A 内部再按三线分文件**（3.3），**公共骨架合并为一份**（3.3.3）。

> **这才是总则一"能分开必须分开，需要合并再合并"的完整落地**：
> **分** = 三线策略各成文件 + 多数派与少数派分通道；**合** = 三线公共判定骨架合为一份。

## 2.5 强制按 mode 拆文件将引入的缺陷（对裁定 #1/#2/#10 的支撑）

| 缺陷 | 具体表现 |
|---|---|
| 违反 OCP | 新增动作类型须新增文件，对扩展**关闭** |
| 违反 DRY | 拆分后要么复制 60+ 行公共判定，要么抽私有 helper（**抽了等于没拆**） |
| 静默越权 | 读操作走写栅栏 = 过度拦截；写操作走读栅栏 = **放行越权**。编译期不可见 |
| 同类事故先例 | `_WRITE_CMD_RE` 曾因双份副本同步漏改而漏检（2026-10-15 才补齐） |

# 第三章 实施方案

## 3.1 目标架构（模块平铺，无子目录）

```
app/safety/
├─ path_policy.py          【新增】目录分类单源：路径规范化 → 分类判定
│                            SYSTEM_PROTECTED_DIR_NAMES / is_system_protected_path
│                            is_disk_root / is_code_root_path / is_protected_root_itself
├─ path_env.py             【新增·拆自现 577 行】① 磁盘枚举 + ② 白名单构建
│                            get_existing_drives / get_system_drive / get_default_allowed_paths
├─ path_line_common.py     【新增·拆自现 577 行】三线共用判定骨架（详见 3.3.3）
│                            check_preconditions / check_forbidden / check_whitelist
├─ read_line.py            【新增·拆自现 577 行】读线独有策略
│                            validate
├─ write_line.py           【新增·拆自现 577 行】写线独有策略
│                            validate
├─ delete_line.py          【新增·拆自现 577 行】删线独有策略
│                            validate
├─ path_safe_check.py      【保留·瘦身】③ 禁区分类内核（公共骨架的依赖项）
│                            _is_forbidden_path（禁区判定唯一真源，被 path_line_common 调用）
├─ multi_action_check.py   【新增】通道 B：4 复合工具 + bash
│                            validate_multi_action_path / validate_bash_targets
└─ path_dispatch.py        【新增·拆自现 577 行】⑤ 参数调度 + 双通道分发
                             validate_tool_path（**新建 API，非改名兼容**）
```

> **`validate_path` 与原 `validate_tool_path` 一律删除，不设转发层、不设兼容入口。**
>
> **理由（AGENTS 10 大规范 · 禁止 backward）**：`validate_path(file_path, mode="write")` 这个签名本身**就是"用参数模拟分支"** —— 它存在的唯一目的是让三条线穿同一条裤子。**它是要被消灭的对象，不是要被保留的对象。** 保留一个转发它的壳，等于新旧混杂，正是规范明令禁止的向后兼容。
>
> **正确做法是迁移，不是兼容**：全部调用点改写为直接调用对应线文件（`read_line.validate` / `write_line.validate` / `delete_line.validate`），无 mode 字符串、无转发层。

|---|---|

| 原 `validate_tool_path` | **删除**，由 `path_dispatch.validate_tool_path` 全新实现 |

## 3.2 关键设计一：动作类型静态化（解决 §1.4 四缺陷）

### 3.2.1 `ToolMetadata` 新增字段

```python
# app/tools/tool_types.py —— ToolMetadata
# 2026-10-15 北京老陈：动作类型注册期声明，读写删三线静态化(R7)
#   取代 path_safe_check.py:515-523 的运行时 if 链推断。
```

**默认值 `write`**：保持 fail-closed 方向（未声明的新工具按最严档处理），与现状 `else: mode = "write"` 行为完全一致。

### 3.2.2 注册期声明

| `write` | 24 | 取默认值 `write` |
| `delete` | 1 | `delete` 工具注册时显式 `action_kind="delete"` |
| `multi` | 4 | `compress` `copy` `extract` `move` 显式声明，走通道 B |

### 3.2.3 分发逻辑（取代 `:515-523` 的 if 链）

```python
# path_dispatch.py
def validate_tool_path(tool_name, params, mode=None):
    name = normalize_tool_name(tool_name)
    if name == "bash":
        return multi_action_check.validate_bash_targets(...)      # 通道 B
    kind = tool_registry.get_tool(name).action_kind              # 通道 A：静态查表，零推断
```

## 3.3 关键设计二：三线物理分离（落实总则一）

### 3.3.1 实测：三线差异仅 3 个分支，公共部分 60+ 行

`validate_path`（`path_safe_check.py:287-400`）逐段归属：

| `:317` | `_is_forbidden_path(file_path, mode)` 禁区分类 | **三线共用** |
| `:321-322` | `mode == "read"` → 禁区**放行** | **读线独有** |
| `:323-324` | `system` → blocked | 写/删共用 |
| `:325-333` | `non_system`：删硬拦 / 写查 `is_temp_authorized` | **写删各半** |
| `:337-352` | 路径穿越（`..` + realpath 比对，16 行） | **三线共用** |
| `:357-382` | 白名单前缀匹配（26 行，含盘根特例） | **三线共用** |

> **三线差异 = 读线 2 处 + 删线 1 处 + 写删分支**；**公共部分 60+ 行完全共用**。

### 3.3.2 错误拆法与本方案拆法对比

**错误拆法（违反 DRY）** —— 每线各写全逻辑：

```
read_line.py   ← 空路径 + 穿越 + 白名单 + 禁区放行     ~90 行
write_line.py  ← 空路径 + 穿越 + 白名单 + 分级 + 授权  ~95 行
delete_line.py ← 空路径 + 穿越 + 白名单 + 硬拦 + 授权  ~95 行
```

→ 公共逻辑复制 3 份，改一处漏两处（`_WRITE_CMD_RE` 即为前车之鉴）。

**本方案拆法（分差异、合公共）**：

```
path_line_common.py   ← 三线共用骨架（60+ 行，抽 1 份，零复制）
read_line.py          ← 读线独有策略
write_line.py         ← 写线独有策略
delete_line.py        ← 删线独有策略
```

→ 公共逻辑零复制；**三线策略物理分离**，查阅"删线为何硬拦"只看 `delete_line.py`，不必翻 577 行主文件。

### 3.3.3 各模块职责

| 模块 | 职责 | 规模 |
|---|---|---|
| `path_line_common.py` | ① 空路径判定 ② 禁区分类（调 `path_policy`） ③ 路径穿越 ④ 白名单前缀匹配 | ~110 行 |
| `read_line.py` | 读线策略：**禁区放行** + **白名单外放行**（内容敏感性交 `contentFilter` 兜底） | ~15 行 |

### 3.3.4 公共骨架接口（函数组合，非继承）

**不用基类继承**（避免模板方法反模式与隐式耦合），采用**函数组合** —— 各线显式编排调用顺序：

### 3.3.5 三线实现

```python
# read_line.py
def validate(file_path: str, allowed_paths=None) -> Tuple[bool, Optional[str], Optional[str]]:
    """【读线】禁区放行 + 白名单外放行（内容敏感性由 contentFilter 兜底）"""
    pre = common.check_preconditions(file_path)
    if pre:
        return pre
    forbidden = common.check_forbidden(file_path)
    if forbidden:
        return True, None, forbidden[0]              # 读线独有：禁区放行
    if common.check_whitelist(file_path, paths):
        return True, None, None
    return True, None, None                          # 读线独有：白名单外放行
```

```python
# write_line.py
def validate(file_path: str, allowed_paths=None) -> Tuple[bool, Optional[str], Optional[str]]:
    """【写线】system 硬拦 / non_system 可授权 / 白名单外可授权"""
    pre = common.check_preconditions(file_path)
    if pre:
        return pre
    forbidden = common.check_forbidden(file_path)
    if forbidden:
        if forbidden[0] == "system":
            return False, forbidden[1], "system"     # 写线独有
        if is_temp_authorized(file_path):
            return True, None, "non_system"
        return False, forbidden[1], "non_system"
    if common.check_whitelist(file_path, paths):
        return True, None, None
    if is_temp_authorized(file_path):
        return True, None, None
    return False, "路径超出允许的操作范围...", None
```

```python
# delete_line.py
def validate(file_path: str, allowed_paths=None) -> Tuple[bool, Optional[str], Optional[str]]:
    """【删线】禁区全部硬拦、无授权分支（R6 项目外递归由 delete_safety 叠加）"""
    pre = common.check_preconditions(file_path)
    if pre:
        return pre
    forbidden = common.check_forbidden(file_path)
    if forbidden:
        return False, forbidden[1], forbidden[0]      # 删线独有：无授权分支
    if common.check_whitelist(file_path, paths):
        return True, None, None
    if is_temp_authorized(file_path):
        return True, None, None
    return False, "路径超出允许的操作范围...", None
```

### 3.3.6 调用点全量迁移（无兼容层）

**`validate_path` 及其 `mode` 参数彻底删除**，调用点逐个改写为直接调线。

**迁移映射表**：

| `validate_path(p, mode="read")` | `read_line.validate(p)` |
| `validate_path(p, mode="delete")` | `delete_line.validate(p)` |

**迁移清单**（`path_safe_check.py` 内部，随拆分同步消解）：

| 原位置 | 原调用 | 去向 |
|---|---|---|
| `:476` | `validate_path(raw_path, mode=mode)` | 通道 B `multi_action_check`（bash 写/删目标） |

**fail-closed 保证**：三线均为显式入口，不存在"mode 未传时的默认分支" —— 调用方**必须**明确选择一条线，编译期即可见"这条调用点归哪条线"。这消除了原 `mode: str = "write"` 默认值带来的隐式行为。

> **禁止事项**：不得为降低改动量而保留 `validate_path` 转发壳；不得新增 `mode` 参数到三线入口；不得保留任何旧名别名。
