## 〇、设计总则（北京老陈裁定，本文档最高准则）

> **一、读、写、删是三条线 —— 能够分开的地方必须分开，需要合并的时候再合并。**
>
> **二、不能因为少数几个复合动作，就限制整个设计策略。**
>
> **三、模块平铺，不建子目录。**
>
> **四、禁止向后兼容 —— 该删的删干净，该改的改到位，不留转发壳、不设兼容入口、不保留旧名别名、不做"零破坏"妥协。**
> （AGENTS 10 大规范 · 日常编码第 6 条：**禁止 backward**，违反后果 = 新旧混杂、代码混乱）
>
> **五、本设计只处理「路径安全」域。没有 path 参数的工具，不进三线。**
> （北京老陈 2026-10-15："我们的安全目前只是涉及到 path，没有 path 有屁关系啊，自找麻烦"）

**总则的落地口径**：

| 总则 | 落地方式 | 本文对应章节 |
|---|---|---|
| 一 · 分 | 三线策略**各成独立文件** | 3.3 |
| 一 · 合 | 三线公共判定骨架**合为一份** | 3.3.2 / 3.3.3 |
| 二 | 复合动作工具**独立成通道**，不拖累主干 | 1.2 / 2.4 / 3.4 |
| 三 | 三线文件直接置于 `app/safety/` | 3.1 |
| 四 | **`validate_path` 及 `mode` 参数彻底删除，调用点全量迁移** | 3.1 / 3.3.6 |
| **五** | **无 path 参数的工具在分发处直接放行，不进通道 A/B** | **1.2.2 / 3.2.3** |

> **总则四的判据**：把 `validate_path` 保留下来、内部转发三线，看似"零破坏"，实为**新旧混杂的向后兼容套壳**。**"调用方不用改"从来不是优点，是违规证据。**

## 1.2 【关键实测】哪些工具真正涉及路径安全

### 1.2.1 两道筛子

`validate_tool_path` 对每个工具做**两道筛**：

**第一道**：工具是否属 `PATH_CATEGORIES`（FILE / DOCUMENT / DATAANALYSIS / NETWORK / DESKTOP）—— 决定"是否进入路径检查"。

**第二道**：工具的 `input_schema.properties` 是否含 `PATH_PARAM_KEYS` —— 决定"是否有路径可校验"。

```python
PATH_PARAM_KEYS = ("path", "source_path", "target_path", "file_path",
                   "directory", "file_name", "destination_path", "output_path", "dest")
```

> **第二道筛子才是关键**：没有路径参数的工具，第二道筛直接让它返回"通过" —— **与三线无关，不存在归读归写的问题。**

### 1.2.2 实测结果：39 个路径类工具中，仅 29 个有 path 参数

**【第一类】有 path 参数 → 进入三线（29 个）**

| 动作类型 | 数量 | 工具 | 路径参数 |
|---|---|---|---|
| **纯读** | **10** | `find` `grep` `listdir` `read` `read_docx` `read_pdf` `read_pptx` `read_xlsx` `readmedia` `tree` | `path` |
| **纯写** | **12** | `write` `write_docx` `write_pdf` `write_pptx` `write_xlsx` `analyze_data` `filter_data` `execute_sql` `get_db_schema` `query_sql` `generate_chart` `screen_capture` | `path` / `dest` |
| **纯删** | **1** | `delete` | `path` |
| **复合动作** | **6** | `compress` `copy` `extract` `move`（`path`+`dest`）<br>**`rename`（`path`+`dest`，源读目标写）**<br>**`edit`（`path`，读原文件后写回）** | 见左 |

**【第二类】无 path 参数 → 与三线无关，不进入路径安全（10 个）**

| 工具 | 实际参数 |
|---|---|

### 1.2.3 复合动作工具的实参语义（6 个）

| 工具 | 参数语义 | 说明 |
|---|---|---|
| `copy` / `move` | `path`=源（**读**）、`dest`=目标（**写**） | 源读目标写 |
| `compress` / `extract` | `path`=源（**读**）、`dest`=目标（**写**） | 同上 |
| **`rename`** | `path`=源（**读**）、`dest`=目标（**写**） | **v1.2~v1.4 漏判，v1.5 补正** |
| **`edit`** | `path`=单一文件（**读原内容 + 写回**） | **v1.2~v1.4 漏判，v1.5 补正** |

### 1.2.4 【代码缺口】现有复合判定不完整

现状 `path_safe_check.py:558-560`：

```python
_param_mode = mode
if key in ("src", "source_path") and normal_name in ("compress", "extract", "copy", "move"):
    _param_mode = "read"
```

**两处缺陷**：

| # | 缺陷 | 后果 |
|---|---|---|
| **G1** | 复合工具白名单只有 4 个，**漏 `rename`** | `rename` 的 `path`（源）按工具级 `write` 判定 → 白名单外的合法源被要求临时授权（**误拦合法读源**） |
| **G2** | 参数键只认 `src`/`source_path`，**不认 `path`/`dest`**；且 **`edit` 完全未考虑** | `copy` 的 `path` 参数实际按 `write` 判定（G2 前半）；`edit` 读改写同一文件，按 `write` 处理可接受但语义不显式 |

> **本方案在 3.4 将 6 个复合工具统一收进多动作通道，上述缺口一并补齐。**

## 1.3 三线策略矩阵（决策中心在 SA3）

**实测**：`tool_safety_checker.py:366-428`（`_check_known_risks`）以 `category × mode` 二维分流：

| category | 读 | 写 | 删 |
|---|---|---|---|
| `system`（系统禁区） | **放行** | blocked 永不授权 | blocked 永不授权 |
| `non_system`（受保护区域） | **放行** | 确认 + `auth_path` | **blocked 永不授权** |
| `None`（白名单外） | **放行** | 确认 + `auth_path` | **blocked 永不授权** |

> 三线在**策略层已分离**（矩阵显式可读），在**代码层未分离**。

## 1.4 mode 的现有赋值方式（问题根源）

**现状**：mode 在**运行时**由 `if` 链推断（`path_safe_check.py:515-523`）：

```python
if mode is None:
    if normal_name in READ_ONLY_TOOLS:
        mode = "read"
    elif normal_name == "delete":
        mode = "delete"
    else:
        mode = "write"
```

| # | 缺陷 | 后果 |
|---|---|---|
| D1 | **运行时启发式** | 静态可定的工具，每次调用都重算 mode |
| D2 | **复合工具拖累多数派** | `:558-560` 的复合特判混在主干中 |
| D3 | `else` 兜底为 `write` | 方向 fail-closed（正确），但动作类型从未显式声明 |
| D4 | **mode 不可静态审计** | 无法一眼看出"哪些工具走哪条线" |

## 1.7 缺陷乙详证：`is_system_protected_path` 职责错位

**现状**：位于 `app/utils/path_utils.py`（通用工具层），职责却是**安全判定**。

**成因**：守护规则 `app.tools` 禁 import `app.safety`（`test_architecture_boundaries.py:29-32`），工具层硬底线 `delete_file.py:88`（`_guard_forbidden_delete`）需直接调用，故下沉 `utils`。

> 挡路的不是"包名 safety"，而是"整个 safety 可被 `security.enabled` 关闭"这一**实质事实**。解法不是绕开，而是**把不会被关闭的那部分切出来**。

## 2.2 判定准则

### 【分】准则 —— 满足任一即应分开

| 判据 | 说明 |
|---|---|
| **D1 独占语义格** | 该线有其它线不存在的判定格 |
| **D2 独立数据结构** | 该线有独立返回类型/契约 |
| **D3 独立调度时机** | 该线在调用链不同阶段被求值 |
| **D4 独立生命周期** | 该线可单独增删改而不影响他线 |
| **D5 主体占比** | 该线覆盖多数派对象 |

### 【合】准则 —— 满足任一即应合并

| 判据 | 说明 |
|---|---|
| **M1 判定逻辑同一** | 各线走同一段代码，差异仅参数取值 |
| **M2 少数派拖累多数派** | 少数特例迫使多数派共用特判代码 —— **特例应独立成线** |
| **M3 mode 为坐标轴** | 各线是同一矩阵的行/列，非并列关系 |

| ❌ **按 mode 拆**（把 mode 拆成三份） | 6 个复合工具的特判仍混在主干中，23 个单一动作工具继续共用含特判代码。**少数派照样拖累多数派** |
| ✅ **按动作属性分**（单一动作 vs 多动作 vs 不涉及） | 23 个走零特判的干净主干；6 个复合工具 + `bash` 走独立通道；**10 个无 path 工具直接放行**。**互不牵连** |

| 通道 | 覆盖 | 动作类型来源 | mode 求值 |
|---|---|---|---|
| **通道 A：单一动作** | **23 个（89%）** | **注册期静态声明** | **零推断、零 if 链** |
| **通道 B：多动作** | **6 个 + `bash`** | 参数 / 命令内容动态派发 | 运行时按参数语义 |
| **通道 C：不涉及** | **10 个** | 无（无 path 参数） | **无 mode 概念** |

> 通道 A 内部再按三线分文件（3.3），**公共骨架合并为一份**（3.3.3）。

> **这才是总则一"能分开必须分开，需要合并再合并"的完整落地**：
> **分** = 三线策略各成文件 + 多数派与少数派分通道 + 无关工具出局；**合** = 三线公共判定骨架合为一份。

## 2.5 强制按 mode 拆文件将引入的缺陷（对裁定 #1/#2/#8 的支撑）

| 缺陷 | 具体表现 |
|---|---|
| 违反 OCP | 新增动作类型须新增文件，对扩展**关闭** |
| 违反 DRY | 拆分后要么复制 60+ 行公共判定，要么抽私有 helper（**抽了等于没拆**） |
| 静默越权 | 读操作走写栅栏 = 过度拦截；写操作走读栅栏 = **放行越权**。编译期不可见 |
| 同类事故先例 | `_WRITE_CMD_RE` 曾因双份副本同步漏改而漏检（2026-10-15 才补齐） |

## 3.2 关键设计一：动作类型静态化（解决 §1.4 四缺陷）

### 3.2.1 `ToolMetadata` 新增字段

```python
# app/tools/tool_types.py —— ToolMetadata
# 2026-10-15 北京老陈：动作类型注册期声明，读写删三线静态化(R7/R10)
#   取代 path_safe_check.py:515-523 的运行时 if 链推断。
#   23/39 单一动作工具的动作类型静态可定，无需每次调用重算。
```

| `write` | 12 | 取默认值 `write` |

| `multi` | 6 | `compress` `copy` `extract` `move` `rename` `edit` 显式声明 → 通道 B |
| **`none`** | **10** | DESKTOP 类（无 path 参数）显式声明 → **通道 C，不进三线** |

### 3.2.3 三通道分发（取代 `:515-523` 的 if 链）

```python
# path_check_entry.py
def validate_tool_path(tool_name, params):
    name = normalize_tool_name(tool_name)
    if name == "bash":
        return multi_path_check.validate_bash_targets(...)       # 通道 B

    kind = tool_registry.get_tool(name).action_kind               # 静态查表，零推断

    if kind == "none":
        return True, None, None, None                             # 通道 C：无 path 参数，直接放行
    if kind == "multi":
        return multi_path_check.validate_multi_path(...)   # 通道 B
    if kind == "read":
        return True, None, None, read_path_check.validate(...)          # 通道 A
    if kind == "delete":
        return True, None, None, delete_path_check.validate(...)        # 通道 A
    return True, None, None, write_path_check.validate(...)             # 通道 A，默认写线（fail-closed）
```

### 3.3.5 三线实现

```python
# read_path_check.py
def validate(file_path: str, allowed_paths=None) -> Tuple[bool, Optional[str], Optional[str]]:
    """【读线】禁区放行 + 白名单外放行（内容敏感性由 contentFilter 兜底）"""
    pre = common.check_preconditions(file_path)
    if pre:
        return pre
    forbidden = common.check_forbidden(file_path)
    if forbidden:
        return True, None, forbidden[0]              # 读线独有：禁区放行
    if common.check_whitelist(file_path, paths):
        return True, None, None
    return True, None, None                          # 读线独有：白名单外放行
```

```python
# write_path_check.py
def validate(file_path: str, allowed_paths=None) -> Tuple[bool, Optional[str], Optional[str]]:
    """【写线】system 硬拦 / non_system 可授权 / 白名单外可授权"""
    pre = common.check_preconditions(file_path)
    if pre:
        return pre
    forbidden = common.check_forbidden(file_path)
    if forbidden:
        if forbidden[0] == "system":
            return False, forbidden[1], "system"     # 写线独有
        if is_temp_authorized(file_path):
            return True, None, "non_system"
        return False, forbidden[1], "non_system"
    if common.check_whitelist(file_path, paths):
        return True, None, None
    if is_temp_authorized(file_path):
        return True, None, None
    return False, "路径超出允许的操作范围...", None
```

```python

    if pre:
        return pre
```

| `:476` | `validate_path(raw_path, mode=mode)` | 通道 B `multi_path_check`（bash 写/删目标） |

**外部调用点**（实施前逐个核实改写）：

| 文件 | 说明 |
|---|---|
| `app/services/chat/workspace_service.py:92` | `validate_path(p, mode="write")` → `write_path_check.validate(p)` |
| `app/safety/temp_auth.py:77-78` | 仅注释提及，随文档同步订正 |

**fail-closed 保证**：三线均为显式入口，不存在"mode 未传时的默认分支" —— 调用方**必须**明确选择一条线，编译期即可见"这条调用点归哪条线"。这消除了原 `mode: str = "write"` 默认值带来的隐式行为。

> **禁止事项**：不得为降低改动量而保留 `validate_path` 转发壳；不得新增 `mode` 参数到三线入口；不得保留任何旧名别名。
