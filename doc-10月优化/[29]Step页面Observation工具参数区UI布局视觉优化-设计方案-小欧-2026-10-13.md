| C3 | 折叠阈值按"项数"固定值定，不看内容体量 | `PARAMS_FOLD_THRESHOLD = 5`（`:124`）。5 项以内全量展开——若其中 1 项是 3000 字代码，阈值形同虚设 |
| C4 | 并行多工具高度**线性叠加** | 每工具子行独立展开（`expanded[]` 数组，`:288`），并行 5 个工具全展开 = 右栏内容 5 倍 |

高度量化表（按每行 18px）：

| 场景 | 参数行数（键数） | 叠加高度 |
|---|---|---|
| `read`（file_path/offset/limit/encoding） | 4 | 72px |
| `write`（6 键，其中 `content` 为 300 行代码，展开后按行摊开） | 6 键 | **6 键折叠态 108px；若 `content` 单值展开则 300 行 × 18 = 5400px+** |
| `find`（pattern/replace/glob… 23 项） | 23 | 414px |
| 并行 5 工具全展开 | — | **N 倍线性叠加** |

> **2026-10-13 核查订正**：初稿 write 行把「键数 6」与「高度 5400px+」并列成同口径算式（6×18=108≠5400），实为两件事——6 是键数、5400px 是 `content` 单值展开后按 18px 逐行摊开的结果（300 行）。现已拆清：折叠态恒 108px，展开态才是 5400px+，这正是 §2.2 要根治的对象。

## 二、优化问题解决方案

### 2.1 总体路线：双载体并存（展开区 JSON 树 + 浮层双视图）

**北京老陈 2026-10-13 裁定**：现有展开区**保留**，浮层是**新增**载体，二者并存互补。

| 载体 | 定位 | 渲染形态 | 高度行为 |
|---|---|---|---|
| **现有展开区** | 就地一眼扫读，不离开流水线语境 | **戊 · JSON 树**（顶层键默认折叠） | **恒定 N 行**，与参数值体量无关 |
| **浮层**（工具行内固定按钮触发） | 细看、复制、宽屏读长内容 | **乙 · 分组卡片**（默认）/ **甲 · 规格表**（切换） | 不进入右栏滚动流，**高度增长 0** |

**关键约定**

1. 并行 N 个工具**仍是 N 条独立子行**，每条独立可点（现状 `expanded[]` 数组机制不变）
2. 浮层**单例互斥**：点新的自动关旧的，任意时刻最多一个面板亮着
3. 浮层触发按钮**固定在工具行内**（跟在结果摘要右侧），**位置不随展开态移动**（D1 裁定，§3.10）
4. 浮层**不按项数二次折叠**：打开即展示全部参数键（与旧 `>5 项折成一行` 彻底告别）；**巨型值自身的「共 N 行 · 展开」不属二次折叠**（见 §2.3.3，那是单值的体量处理，不是整块折叠）
5. **两态互不牵连**（DC-18）：工具行折开收起与浮层开合各自独立，任一方动作不影响另一方
6. **嵌套深度不设上限**（DC-15）：由数据自身决定，深度失控由限高 240px 控制而非层级裁剪
7. **两处复制语义不同**（DC-16/DC-17）：浮层复制 `key=value` 逐行；展开区 JSON 树复制格式化 JSON

### 2.2 现有展开区改造：戊 · JSON 树

```
● write成功:从第1-200行  ▾   </> 浮层参数   ← 按钮固定在工具行行尾（D1 裁定乙 + D2 裁定顺序）

      ▸ "file_path"    : "F:\...\backend\app\main.py"
      ▸ "encoding"     : "utf-8"
      ▸ "shell_type"   : "powershell"
      ▸ "append"       : false
      ▸ "timeout"      : 30
      ▸ "content"      : "共 312 行"

```

**高度收益（本方案核心）**：顶层键**默认折叠**，每个参数恒占 1 行。

**行高口径**：新组件行高取 `FontSize.SECONDARY(12) + Spacing.XS(4) = 16px`，符合项目既定规则「行高 = 字号 + 4」（`stepStyles.ts:108-110` 北京老陈 2026-08-30 定案注释；`:13` 是无关条目，初稿引用错位已订正）。现状的 18px 是**继承**自 14px 根容器、并非按 12px 字号算出（属缺陷 A9），故下表"改造后"一律按 16px 计。

| 场景 | 改造前（行高 18px） | 改造后（行高 16px） |
|---|---|---|
| `write`（content 300 行） | 5400px+ | **7 行 × 16px = 112px 恒定** |
| `find`（23 项） | 414px | 24 行 × 16px = 384px（1 行树根 + 23 键） |
| 并行 5 工具全展开 | N 倍叠加（write 为例 5400px） | N × 112px |

**展开节点规则**：`▸ "content"` 展开后显示多行内容，但**内部限高 240px 滚动**，故单节点展开也不撑页。

**顺带解决（结构层面）**：A1（key/value 由**双色阶**区分——键 `TEXT.SECONDARY` / 值 `TEXT.STRONG`）、A5/A6（节点缩进结构替代 `break-all` 粗暴断行）、A10（按节点分列浏览）。其余 A2/A7/A9 由 §2.5 的 V1/V5/V7 令牌级改造解决，非结构本身带来。

**与浮层的口径差异**：展开区**不分组**——JSON 树的「树结构本身即分组」，按键原序纵览；浮层**按语义分组**（路径/开关/编码/正文载荷/其他），供快速定位。两者定位不同（就地纵览 vs 定向细看），故刻意采用不同组织方式。

#### 2.3.2 分组规则（乙视图）

按参数语义自动分**五类**（四类具名 + 一类兜底「其他」），**不硬编码工具名单**，按 key 形态与值形态判定。

**判定优先级链（严格自上而下，命中即止，防一个参数落进两组）**：

```
1. 正文载荷  ← 值含换行 / 值为 list|dict / 值.length > HUGE_VALUE_CHARS
2. 开关      ← 值为 boolean
3. 路径      ← key ∈ PATH_KEYS 或 值匹配路径特征
4. 编码      ← key ∈ {encoding, charset}
5. 其他      ← 以上皆非（兜底）
```

> **正文载荷置于最高优先级**的原因：`content`/`body` 之类的值往往极长，若先按"路径特征"或"编码"匹配，会被误分到语义更轻的组里；而它们恰恰是用户最需要一眼定位的参数，故优先占位。

| 类 | 判定规则 | 示例 |
|---|---|---|
| 路径 | key ∈ `PATH_KEYS`（`path`/`dir_path`/`file_path`/`source_path`/`dest`/`output_path`）**或** 值匹配路径特征（含分隔符且有扩展名） | `file_path`、`dest` |
| 开关 | 值为 boolean | `append`、`overwrite`、`recursive` |
| 编码 | key ∉ `PATH_KEYS` 且 key ∈ `{encoding, charset}` | `encoding` |
| 正文载荷 | 值含换行，或为 list/dict 对象，或字符串长度 > `HUGE_VALUE_CHARS`(200) | `content`、`body`、`data` |
| 其他 | 以上皆非（兜底） | `timeout`、`limit` |

> 「路径特征」判定细则：**同时**满足含 `/` 或 `\` **且**末段存在扩展名（`\.` + 1~8 位字母数字）。单独含分隔符但无扩展名（如 `a/b/c`）不判为路径，归「其他」，避免误伤 SQL 片段与代码片段。

#### 2.3.3 巨型值处理（两视图共用）

| 条件 | 呈现 |
|---|---|
| 含换行 / 超 `HUGE_VALUE_CHARS`(200) | 折叠为 `共 N 行 · 展开`；展开后限高 240px 内部滚动 |
| list/dict 对象 | `JSON.stringify(v, null, 2)` 多行缩进，按上行同样限高；嵌套深度不限（DC-15） |

> 展开区 JSON 树**不用**本表口径（只看是否含换行，不设字符阈值），理由见 §3.4.1。

#### 3.4.1 结构与默认态

> 示例仅列 2 键以便对齐阅读；完整结构与 §2.2 示意图（6 键）一致。

```
▾ {                      ← 树根常展
    ▸ "file_path"  : "F:\...\main.py"     ← 顶层节点默认折叠
    ▸ "content"    : "共 312 行"           ← 长值折叠为摘要
  }
```

| 节点类型 | 默认态 | 展开后 |
|---|---|---|
| 顶层标量键（string/数字/布尔） | 恒为单行 `key : 值`，**无折叠态**（本就一行，箭头不出现） | 无（不存在展开） |
| 顶层长字符串 / 含换行 | 折叠，显示 `共 N 行` | `<pre>` 限高 240px 内部滚动 |
| 顶层 list / dict 对象 | 折叠，显示 `{…} N 项` | 子节点树，嵌套限高 240px |
| **嵌套节点（任意深度）** | 随父节点展开态 | **不限嵌套层数**（DC-15），逐层独立折叠；限高 240px 由**每个展开体各自**承担 |

**嵌套深度不设上限（DC-15）**：嵌套层数由数据自身决定，是数据的客观结构，前端不应替后端做裁剪。深度失控的风险由**限高 240px**而非层级上限来控制——任意深度的内容展开后都只在 240px 内滚动，不会撑破展开区。故上表「嵌套限高 240px」指**每一层展开体各自限高**，非全局总高。

**长值在树内的截断口径**：折叠态单行恒显示，**不因长度换行、不截断**（单行 + 溢出省略）；展开态 `<pre>` 限高滚动，**不做字符级截断**——内容完整可读、可选中复制。这与浮层"巨型值超 200 字折叠"是**两套口径**（树内无字符阈值、只看是否含换行），刻意区分：展开区已天然限高，无需再按字符折叠。

**展开区复制（DC-17）**：见上文树头结构图，复制内容为 `JSON.stringify(params, null, 2)` 格式化 JSON（与浮层的 `key=value` 逐行**语义不同**，见 DC-16）——树形态是 JSON，复制自然也该是 JSON，便于直接粘进代码或交给 LLM。

**行高写法统一**：新组件内按既有模式内联 `${FontSize.CODE + Spacing.XS}px`（同 `ToolResultRenderer.tsx:109` 的 `FontSize.SMALL + Spacing.XS` 写法），**不新增 `LineHeight` 令牌组**，避免与仓内 6+ 处既有内联写法不一致。

**`HUGE_VALUE_CHARS`(200) 不进 stepStyles**：它是**判定阈值**而非视觉令牌，落 `ParamsPanel.tsx` 模块级 `const HUGE_VALUE_CHARS = 200`（与 `PARAMS_FOLD_THRESHOLD` 现状同范式），避免为单一消费方开设计令牌（YAGNI）。

**`Size` 命名说明**：既有组为 `BorderWidth`/`FontSize`/`Radius`/`Spacing`（"名 + 量纲"风格），故新组用 `Size.*` 承接面板尺寸，不新建 `PanelSize` 之类第四种风格。

**窄屏口径**：面板宽接系统断点矩阵（`TaskInfoBar.tsx:26` 记载的 wide/mid/narrow/xsmall）的**意图**，但落地由 §4.6 的纯 CSS 三件套承担（D-5）。**先厘清 CSS 真实语义再定阈值**：CSS 中 `min-width` **优先于**更小的 `max-width`，故 `width:640 + minWidth:320 + maxWidth:calc(100vw - 32px)` 的实际生效值为——

| 视口宽度 | 实际面板宽 | 说明 |
|---|---|---|
| ≥ 672px | **640** | `width` 生效，`maxWidth` 不构成约束 |
| 352px ~ 672px | **视口 − 32** | `maxWidth` 收紧，两侧各留 16 |
| < 352px | **320** | `minWidth` 优先于更小的 `maxWidth`；超出视口的部分由右栏 `overflowX:'hidden'` 裁剪（`SessionLayout.tsx:99,126`），**面板内滚动，不产生横向滚动条**（与 `EllipsisTip`「超宽不横滚、靠折叠/Tooltip 降级」原则一致） |

> **2026-10-13 核查订正**：初稿只写「最低不小于 320，窄于 320 的视口按 320 铺满」，而 T25 又写「面板宽 = `min(视口-32px, 640)`」——两处自相矛盾（视口 <352px 时 `min(视口-32,640)` < 320，与"不低于 320"打架；且真按该算式实现会得到 <320 的宽，违反下限）。现已统一为本表三档，与 §4.6 的三件套、T25 完全对齐。

#### 3.5.2 GroupView（乙 · 分组卡片 · 默认）

按 §2.3.2 判定优先级链分**五类**，每类：左侧 2px 色条 + 类名小字标题，类内键值行。**空类不渲染**（如无 boolean 参数则不显「开关」条）。

**色条用中性阶，不占用语义色**

| 类 | 色条色 | 说明 |
|---|---|---|
| 路径 | `Colors.BORDER.STRONG` `#bfbfbf` | 中性灰最深 |
| 开关 | `Colors.BORDER.DEFAULT` `#d9d9d9` | 中性灰中 |
| 编码 | `Colors.BORDER.DEFAULT` `#d9d9d9` | 中性灰中 |
| 正文载荷 | `Colors.BORDER.VERTICAL` `#e8e8e8` | 中性灰最浅 |
| 其他 | `Colors.BORDER.LIGHT` `#f0f0f0` | 中性灰最浅 |

> **为何不用语义色**：系统的 `Colors.WARNING(#AD6800)` / `ACCENT_ORANGE(#d4380d)` / `SUCCESS` / `ERROR` 承载**状态语义**（警告、事件计数、成功、失败）。拿它们当"参数分类色标"，用户会误读为"这个参数有警告/异常"。分类是**结构**，状态是**语义**，两者必须用不同视觉通道。故分类只用中性灰阶，类名靠**文字**区分。

#### 3.5.3 SpecView（甲 · 规格表）

固定两列：key 列宽 140px **左对齐**灰字（`TEXT.SECONDARY`），value 列左对齐深字（`TEXT.PRIMARY`）；行间 1px `Colors.BORDER.LIGHT` 分割线；巨型值整宽跨行成代码块（`BG.SECONDARY` + `BORDER.DEFAULT` + `Radius.SM` + `FontFamily.MONO` + `FontSize.CODE`，与 `MarkdownText` 代码块同款）。**2026-10-13 十二轮订正**：初稿此处写「key 列 140px **右对齐**」，与 §2.3 规格表示意图（`:298-303`，`file_path`/`encoding` 从同一左缘起）**自相矛盾**，也与分组视图 key 列（96px，未设对齐即左对齐）口径不一；现统一**左对齐**（key-value 表右对齐只适用于数字列，等宽字体下长短 key 右对齐会让扫读起点参差）。

**巨型值折叠切换规格（复用系统惯例）**：一律用 **`CircleArrow`(size=14, color=`Colors.PRIMARY`) + 文案「展开」/「收起」**（同 `CollapsibleText.tsx:109-115`），**不用 `▸`/`▾` 裸字符**——裸字符是本方案 v1.0 的旧写法，与系统既有折叠观感不一致。

**收起态一行的三部分与顺序（D2 裁定）**


**③ 按钮文案定稿（D3 裁定）**：标签文字为 **`浮层参数`**，不是 `参数`——"参数"二字在流水线语境里已被"展开区（JSON 树）"占用，同名会让用户误以为两者是同一个东西。`浮层参数` 一眼区分「就地展开的那块」与「弹出来的面板」。

```tsx
          animated={false}
```

`raw_data` 里保留着 `data_text` 已截断掉的完整数据，例如 `truncated` 标志、未截断的完整 rows。

#### 6.1.2 链路：后端已就绪，本次纯前端

**结论：后端与 SSE 层零改动，本功能 100% 前端工作。**

补充事实：`app/tools/` 下 60+ 个工具文件的「约定②」都写着「出参返回原始 data，**禁止走 `truncate_data_for_frontend` 截断**——只对前端 yield 兜底」。但该函数已在 `094701c78`（2026-07-10 删死代码）被删除，**当前后端对 `raw_data` 完全不截断**，与本章设计一致。

#### 6.1.3 不兜底铁律（本章最高优先级约束）

> **`raw_data` 是什么就渲染什么。不得兜底、不得回退、不得与其他字段关联。**

| 禁止 | 说明 |
|---|---|
| 禁止回退到 `llm_data` | `raw_data` 为空就是空，**不拿摘要/耗时/指标顶替** |
| 禁止回退到 `data_text` | 两者是不同数据，不可互替 |
| 禁止跨字段拼接 | 不做「`raw_data` 没有就去 `other_data` 找」这类联动 |
| 禁止"贴心"占位 | `data={}` 就显示空白，不写「该工具未返回原始数据」之类的解释 |

**理由**：兜底会让用户以为看到的是原始数据，实际是加工过的二手信息 —— 排查问题时这是致命的误导。

### 6.4 视图选型

#### 6.4.1 排除「分组视图」（北京老陈质疑后核实确认）

`categorize()` 的分类键集（`PATH_KEYS` / `SWITCH_KEYS` / `PAYLOAD_KEYS` / `SEARCH_KEYS` / `EXEC_KEYS` / `FORMAT_KEYS`）是**为工具入参调校**的：

| | 键集举例 | `raw_data` 实际键 |
|---|---|---|
| 入参 | `path` `url` `cwd` `content` `command` | — |
| 出参 | — | `stdout` `stderr` `exit_code` `entries` `rows` `columns` `line_count` `truncated` |

`stdout` / `exit_code` / `entries` / `rows` **均不在任何分类键集内**，将全部落入兜底类「其他参数」——**整个结果挤在一个组里，分类成为纯噪音**。

#### 6.4.2 排除 `ParamsTree`

`ParamsTree` 带 `{}` 包裹壳与逐节点折叠，是为「展开区一棵紧凑 JSON 树」设计的范式。套在整个结果外会多一层无意义外壳，且与「规格表同构」的预期不符。

#### 6.4.3 定案：规格表为基底 + 仅结果模式开启对象折叠

**原样规格表有一处缺口**（初稿遗漏，实测代码后才发现）：

```
isHugeValue = typeof v === 'string' && v.includes('\n')   // 只认「含换行的字符串」
fullTextOf  : object → JSON.stringify(v)                  // 紧凑单行，无缩进
```

对象 / 数组序列化后**单行、不含 `\n`** → `isHugeValue` 为假 → 不折叠、走 `PlainValue` 单行折行输出。`read` 一个 300 行文件时 `raw_data.content` 会变成一行超长文本，不可读。

**解法（依赖注入，参数视图零变化）**：`SpecView` 增一个**可选** prop `valueMode?: 'param' | 'result'`，默认 `'param'` 即现有行为。

| 判定 | `'param'`（默认，现状不变） | `'result'` |
|---|---|---|
| 值文本 | `fullTextOf(v)`（对象=紧凑单行 JSON） | 对象 / 数组 → `JSON.stringify(v, null, 2)` |
| 可折叠 | `isHugeValue(v)`（仅含换行字符串） | `isHugeValue(v)` **∪** 对象 / 数组 |

字符串的折叠规则两模式**完全一致**（沿用已定案口径「长单行字符串折行显示全部字符」）。

### 6.5 折叠与换行规则（北京老陈裁定）

| 裁定 | 落地 |
|---|---|
| **超长单行字符串不折叠，但可以换行** | 不改折叠规则。现有 `PlainValue` 已是 `whiteSpace:'pre-wrap'` + `wordBreak:'break-word'`，单行长串天然折行完整显示 |
| **顶层折叠，内部不折叠** | `'result'` 模式下仅顶层值可折叠；嵌套对象的内层 JSON 一次性展开，不再逐层可折叠 |

**两条裁定的共同效果**：`base64_data` 被排除（§6.3）后，剩下的单行长串（minified JSON、URL 串等）虽不折叠，但会正常折行 —— 不会被截断、不会被隐藏。

### 6.6 diff 着色（Q2 = A）

`edit_text_file` 的 `diff` 是结构化 diff（`@@ -a,b +c,d @@` hunk 头、`+` / `-` / 空格行首标记），后端 `observation_formatter.py:15` 已注明「格式已在工具内规范化」。纯黑文本渲染会丢失 diff 的视觉语义，故**在结果视图内为 diff 单独着色**：

| 行首 | 颜色令牌 | 语义 |
|---|---|---|
| `+` | `Colors.SUCCESS` `#52c41a` | 新增行 |
| `-` | `Colors.ERROR` `#ff4d4f` | 删除行 |
| `@@` | `Colors.PRIMARY` `#1677ff` | hunk 头 |
| 其他 | 常规前景色 | 上下文行 |

**实现约束**：

- 着色仅在 `'result'` 模式生效，**参数视图的 `diff` 参数不做着色**（规格表样式零改动）
- 着色判据是**字段名是 diff**（`keyName` 为 `diff` / `*_diff` / `*Diff`），**不是**「值含换行」—— 否则 `bash.stdout`、`read_file.content` 等普通多行文本的行首 `+`/`-` 会被误染成绿/红（2026-10-13 23:40 小欧 修正的实bug）
- 走 `ValuePre` 的 `<pre>` 容器，在渲染前把文本按行切分、对每行套 `<span style={{color}}>`；**不使用任何 HTML 注入**（React 文本节点天然转义，无 XSS 风险）
- 折叠行为与普通长文本一致（diff 必含换行 → 原生折叠生效），折叠摘要复用 `summaryOf` 的「共 N 行」
- diff 内部**不折叠**（§6.5 顶层折叠规则的延伸：巨型值展开后一次性全显）
- **⚠️ DC-21 语义色借用登记（2026-10-13 23:40 小欧）**：DC-21 规定「语义色只给状态语义用」，而 diff 的 `+`/`-` 是**内容语义**（增/删），非状态语义，严格讲属DC-21 例外。经北京老陈规格「`+` 绿、`-` 红」裁定，**diff 行级增删特批借用 `SUCCESS`/`ERROR` 两枚**。三条约束：(1) 只借用这两枚，**禁用 `ORANGE_RED`/`WARNING`/`WAIT_ACTION`**（色相或语义不符，见 §2.5 反面清单）；(2) 作用域严格限定为 `valueMode='result'` 且字段名是 diff 的行级 span，**不扩散到任何标签色、分类色、状态色**；(3) 不新增令牌，全部复用 `stepStyles.ts` 既有值

### 6.7 标签问题：北京老陈问「结果渲染里需要显示标签吗」

**结论：不显示任何额外标签。** 逐项裁定：

| 候选 | 决定 | 理由 |
|---|---|---|
| 分类标签（分组视图的色条 + 组名） | ❌ 不加 | 见 §6.4.1，对出参零信息量 |
| 类型标签（`str` / `list[100]`） | ❌ 不加 | 展开后 JSON 一眼可见，冗余（YAGNI） |
| 状态条（成功 / 失败 / 耗时） | ❌ 不加 | **展开区 `ToolResultRenderer` 已渲染**，浮层再放一份即重复展示 |
| 字段名（key） | ✅ 保留 | 这不是标签，是数据本身，且 `stdout` / `exit_code` 等字段名自解释 |

**职责切分由此确立**：展开区 `ToolResultRenderer` 管**元信息**（结果说成功了没、耗时多少），浮层「结果」标签管**结果正文与原始数据**，两者不重叠。

**唯一的例外是 diff 的着色（§6.6）**，那不是标签，是行内语义着色。

### 6.8 状态分支（**全部不兜底**）

#### 6.13.10 折叠摘要的三种形态（`summaryOf` 现有实现，非新增标签）

| 值形态 | 折叠行文案 | 示例工具 |
|---|---|---|
| 含换行字符串 | `共 N 行` | `bash.stdout`、`read_text_file.content`、`edit.diff` |
| 对象 / 数组 | `{…} N 项` | `query_sql.rows`、`get_db_schema.tables` |
| 标量 / 短串 | 不折叠，直接 `PlainValue` 直出 | `window_resize.width`、`execute_sql.syntax_valid` |
