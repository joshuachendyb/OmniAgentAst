## 一、目的

### 1.1 目的一：默认注入名单可控制

现状是**按分类（Type）粒度**控制：`universal_agent.py:38` 硬编码

```python
_INITIAL_CATEGORIES: Set[ToolCategory] = {ToolCategory.FUNDAMENTAL, ToolCategory.FILE}
```

粒度太粗——想"不要 `compress`"或"先不发 `readmedia`"，**做不到**，只能整个分类要或不要。实际需要的是**工具级白名单**：

| 想要的控制 | 现状能否做到 |
|---|---|
| 去掉 `bash` / `shell` 二选一 | **不能**（两个都在 FUNDAMENTAL 内） |
| 首发不发写类工具（防误写） | **不能**（`write`/`edit`/`delete`/`move` 都在 FILE 内） |
| 首发只发"读 + 搜"，写类留给 searchtool | **不能** |
| 按 token 预算动态裁剪 | **不能** |

### 1.2 目的二：减少 token

每次请求都把默认工具的完整 schema 发给 LLM。实测（`to_openai_tools` 输出，JSON 字符数）：

| 分类 | 工具数 | payload 字符 |
|---|---|---|
| FUNDAMENTAL | 7 | 7,504 |
| FILE | 14 | 12,558 |
| **合计（现状）** | **21** | **20,062** |

**这部分 token 每次请求都要重发**（system 前的 tools 段），且随对话轮次重复消耗。

### 1.3 分档实测（裁剪力度 vs 收益）

| 档位 | 工具数 | payload 字符 | 相对现状 |
|---|---|---|---|
| **现状**（按分类全量） | 21 | 20,062 | — |
| **A** 去 `shell` 别名 | 20 | 18,156 | **省 10%** |
| **B** 精简名单（去 `bash`/`shell`/`compress`/`readmedia`/`extract`） | 16 | 13,390 | **省 33%** |
| **C** 极简名单（10 个） | 10 | 11,855 | **省 41%** |
| **D** 极简名单（8 个） | 8 | 10,036 | **省 50%** |

### 1.4 现状里最刺眼的两处纯浪费

| 项 | 体积 | 说明 |
|---|---|---|
| `shell` 与 `bash` | 各 1,750 字符 | **同一实现的别名工具**（`fundamental_register.py:126`），FC parameters 逐字节一致 → 纯重复 1,750 |
| `read` 与 `read` | 各 1,610 字符 | 参数结构完全相同，分属 FUNDAMENTAL / FILE 两个分类 → 纯重复 1,610 |

两项合计 3,360 字符，**占现状 payload 的 17%，且不带来任何新增能力**。

### 1.5 明确不做的事（范围边界）

| 不做 | 理由 |
|---|---|
| 不改任何工具实现 | 方案只动"哪些工具下发给 LLM"，与工具功能无关 |
| 不改 `searchtool` 的检索机制本身 | 只解决"裁掉的工具还能否被找回"这一衔接问题，不重写检索 |
| 不与 `[2] strict 400` 方案混批 | 两件事互不相干，按 `AGENTS.md` 分批提交，避免互相干扰排障 |
| 不做运行时动态改名单 | YAGNI：先满足"可配置"（改常量即改），不做热更新 |

## 二、实施方案

### 2.1 现状机制（已逐行核实，代码事实）

下发清单由 `_loaded_categories` **单一驱动**，共 4 个消费点：

```
UniversalAgent.__init__  (universal_agent.py:60,71)
   └─ _INITIAL_CATEGORIES = {FUNDAMENTAL, FILE}
        └─ ToolLoader.init_tools(categories)          tool_loader.py:28-41
             ├─ agent._tools_dict.update(该分类全部实现)   ← 可执行工具集
             └─ agent._loaded_categories.add(cat)        ← 分类已注册标记

ToolLoader.load_category(cat)                      tool_loader.py:47-61   ← searchtool 动态注入走这里
   └─ 同上: _tools_dict.update + _loaded_categories.add

get_openai_tools(agent)                            tool_cache_manager.py:19-40
   └─ to_openai_tools(categories=agent._loaded_categories)   ← ★ 决定发给 LLM 的清单

patch_search_desc(agent)                           tool_cache_manager.py:63-112
   └─ 未加载分类 = 全集 - _loaded_categories → 拼进 searchtool 描述

auto_inject_from_search(matches)                   tool_executor.py:104-132
   └─ 命中工具的分类若不在 _loaded_categories → load_category → 失效缓存 + 改 searchtool 描述
```

**关键结构问题**：`_loaded_categories` 同时承担**两个不同语义**——

| 语义 | 实际用途 |
|---|---|
| ①「该分类的实现已注册到本 agent，可执行」 | `tool_executor.py:122` 判是否重复注入 |
| ②「该分类的工具要下发给 LLM」 | `tool_cache_manager.py:30` 筛下发清单 |

名单化后 ① 和 ② 必须**解耦**：分类仍可整类注册（保执行能力），但下发只给名单内的。

### 2.2 一个必须先说的隐患：裁掉 FILE 工具会让 searchtool 找不回

**这不是我的推测，是从 2.1 的代码链直接推出来的**：

| 步骤 | 现状行为 |
|---|---|
| 1 | `init_tools` 加载 FUNDAMENTAL + FILE → `_loaded_categories = {FUNDAMENTAL, FILE}` |
| 2 | FILE 全部 14 个工具下发（因为下发清单 = `_loaded_categories` 筛分类） |
| 3 | `patch_search_desc` 计算「未加载分类」= 全集 − {FUNDAMENTAL, FILE} = **8 个**，描述里**不含 FILE** |
| 4 | LLM 想用 FILE 里的工具 → 已经下发，直接调 |

**若把 FILE 裁到只剩 6 个**：

| 步骤 | 裁剪后行为 | 后果 |
|---|---|---|
| 1' | `_loaded_categories` 仍含 FILE（分类仍整类注册） | — |
| 2' | 只下发 6 个 | `copy` `move` `rename` `delete` `compress` `extract` `readmedia` 看不到 |
| 3' | 未加载分类仍**不含 FILE** | searchtool 描述不提 FILE |
| 4' | LLM 找 `compress` → 既没下发、searchtool 也不提示 FILE | **永久不可达** ← 功能缺失 |

**结论：FUNDAMENTAL 可以放心裁，FILE 裁剪必须同时解决"发现路径"，否则会静默丢能力。** 这是本方案最重要的一条约束。

### 2.3 三个候选方案

#### 路线一：仅隐藏下发（`expose_to_llm=False`，零结构改动）

| 项 | 内容 |
|---|---|
| 做法 | ① 首发名单里去掉 `shell`（保留 `bash`），靠 `tools_alias_mapper.py:366` 已有的别名映射兜住 LLM 误叫；② 首发名单里去掉 `read`（保留 `read`，参数结构相同） |
| 改动文件 | **2 个**：`fundamental_register.py`（别名注册）、`universal_agent.py`（名单常量） |
| 收益 | 20,062 → 约 16,700，**省 17%**（实测 FUNDAMENTAL 7 个 7,504 → 去 `shell`+`read` 后 3,821，省 3,683） |
| 风险 | `bash` 被 LLM 主动选择频率高，砍 `shell` 需确认别名映射真能兜住；`read`/`read` 砍 `read` 同理 |
| searchtool 影响 | **无**（FUNDAMENTAL 仍整类注册，未加载分类列表不变，兜底路径完好） |

#### 路线二：下发名单制（结构改动，见第三章对照）

| # | 风险 | 后果 | 防护 |
|---|---|---|---|
| R1 | 名单里写了已改名/已删除的工具 | 静默不发该工具，LLM 看不到 | 启动时校验「名单 ⊆ 注册表」，不匹配记 `error` 日志；加单测断言 |

| R5 | 名单写在代码常量，改名单要改代码发版 | 不够灵活 | **这是路线三才解决的问题**；路线二接受（维护者本人改，一处常量） |

### 2.7 验收标准

## 三、工具注册名归位：`shell` → `bash`（方法与 `read` 一致）

### 3.1 为什么要改

`fundamental_register.py` 把同一个工具注册了两次：

```python
"shell": shell,   # 原名
"bash":  shell,   # 2026-09-24 方案1别名，impl/schema/确认门/examples 全复用 shell
```

`bash` 的 `description` 原文写着「**与shell工具功能完全相同,任选其一即可**」。LLM 看到两个功能一样的工具会随机挑、甚至反复横跳，白费 token 还增加选错概率。

**改后**：只保留短名 `bash`，`shell` 降为别名兜底。默认注入 **18 → 17**。

### 3.2 改动清单（9 个 app 文件 + 2 个测试文件）

**D. 前端 — 0 处**

### 3.2.1 `validate_timeout` 加归一的理由

该函数原本是**精确查表**：

```python
if tool_name not in TIMEOUT_RANGES_SECONDS:
    return True, None, None      # 键不在表里 → 直接放行
```

后果有两层：

1. **本次改名直接踩中**——表键改成 `"bash"` 后，任何传 `"shell"` 的调用查不到范围即放行，`bash` 静默失去 1~600 秒的上下界保护。
2. **顺带堵掉一个既有洞**——LLM 用变体名调工具时（实测 `write_text` 映射到 `compress` 类场景）同样绕过上下界校验：

```
validate_timeout(9999, "write_text") = (True, None, None)                        # 归一前: 绕过
validate_timeout(9999, "compress")   = (False, 'compress的timeout不能大于1800秒')  # 正确
```

入口加一行归一即根治，与 `tool_safety_checker.py:310` 判 `delete` 的既有模式一致（防别名漏检）。

**注意**：`tools_alias_mapper.py` 的 `"bash": "shell"` 必须与表键改名**同批落码**，否则中间态下 `normalize("bash")→"shell"` 查不到新键，`bash` 会暂时失去超时校验。

### 3.3 `shell_type` 参数取值不改

`shell_type` 是参数名，其取值 `Literal["ps7","ps5","cmd","bash"]` 中的 `"bash"` 指 Git Bash 这个 shell 程序，与工具改名无关，原样保留：

`fundamental_schema.py:100`、`execute_shell_command.py` L189/697/974/982/1003/1060/1067/1071/1074/1092、`execute_shell_command_safety.py` L73-77/103-104/156/165、`shell_prompt_templates.py` L14/44、`system_adapter.py:121`、`fundamental_register.py` L75/L87（examples 内的 `"shell_type": "bash"`）。

### 3.4 与第四章的关系

| | 长名 | 短名（重复别名） | 处理 |
|---|---|---|---|
| 第四章 | `readtext`（FILE） | `read`（FUNDAMENTAL） | 删 FUNDAMENTAL 的 `read`，`readtext` 改名 `read` |
| 本章 | `shell`（FUNDAMENTAL） | `bash`（FUNDAMENTAL） | 删 FUNDAMENTAL 的 `bash`，`shell` 改名 `bash` |

TOOL_CATEGORY_OVERRIDE: dict[str, ToolCategory] = {

**为什么需要这张表**：原 `category` 在注册循环里按模块统一赋值（`file_register.py` 14 个工具共用一行、`network_register.py` 5 个共用一行），单个工具无法单独改分类。集中在 5 个工具涉及的 2 个模块，未改动 `system`/`fundamental` 等其余模块——本模块无覆盖项（属"归位"非"覆盖"），不引表。

**`system_register.py`** 是 SYSTEM 分类唯一注册点，故这两个工具的 category 天然正确，不进覆盖表。迁入内容：依赖声明、描述、examples、schema 引用、实现引用、注册项 6 处。

### 4.4 空分类防御

`tool_cache_manager.py` 的 `patch_search_desc`，`unloaded` 叠加一个条件：

```python
unloaded = [
    cat for cat in ToolCategory
    if cat not in agent._loaded_categories
    and tool_registry.get_implementations_by_category(cat)   # 2026-10-02 新增
]
```

**为什么必须加**：`ToolCategory` 是枚举全集遍历。SHELL 归零后若枚举还在，它会被算进"未加载分类"并写进 searchtool 描述，而该分类永远搜不到工具——LLM 反复搜同一目标达 3 次即触发 `tool_retry_engine` 防死循环熔断，任务 FAILED（同类后果在 `tools_alias_mapper.py` 的 `readfile`/`writeetext` 映射注释里有实证记录）。

这是**代码级防御**：今后任何分类被搬空都不会再误导 LLM，不依赖人工纪律。
