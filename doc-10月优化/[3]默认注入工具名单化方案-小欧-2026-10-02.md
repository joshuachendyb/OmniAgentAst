## 一、目的

### 1.1 目的一：默认注入名单可控制

现状是**按分类（Type）粒度**控制：`universal_agent.py:38` 硬编码

```python
_INITIAL_CATEGORIES: Set[ToolCategory] = {ToolCategory.FUNDAMENTAL, ToolCategory.FILE}
```

粒度太粗——想"不要 `compress`"或"先不发 `readmedia`"，**做不到**，只能整个分类要或不要。实际需要的是**工具级白名单**：

| 想要的控制 | 现状能否做到 |
|---|---|
| 去掉 `bash` / `shell` 二选一 | **不能**（两个都在 FUNDAMENTAL 内） |
| 首发不发写类工具（防误写） | **不能**（`writetext`/`edittext`/`delete`/`move` 都在 FILE 内） |
| 首发只发"读 + 搜"，写类留给 searchtool | **不能** |
| 按 token 预算动态裁剪 | **不能** |

### 1.2 目的二：减少 token

每次请求都把默认工具的完整 schema 发给 LLM。实测（`to_openai_tools` 输出，JSON 字符数）：

| 分类 | 工具数 | payload 字符 |
|---|---|---|
| FUNDAMENTAL | 7 | 7,504 |
| FILE | 14 | 12,558 |
| **合计（现状）** | **21** | **20,062** |

**这部分 token 每次请求都要重发**（system 前的 tools 段），且随对话轮次重复消耗。

### 1.3 分档实测（裁剪力度 vs 收益）

| 档位 | 工具数 | payload 字符 | 相对现状 |
|---|---|---|---|
| **现状**（按分类全量） | 21 | 20,062 | — |
| **A** 去 `shell` 别名 | 20 | 18,156 | **省 10%** |
| **B** 精简名单（去 `bash`/`shell`/`compress`/`readmedia`/`extract`） | 16 | 13,390 | **省 33%** |
| **C** 极简名单（10 个） | 10 | 11,855 | **省 41%** |
| **D** 极简名单（8 个） | 8 | 10,036 | **省 50%** |

### 1.4 现状里最刺眼的两处纯浪费

| 项 | 体积 | 说明 |
|---|---|---|
| `shell` 与 `bash` | 各 1,750 字符 | **同一实现的别名工具**（`fundamental_register.py:126`），FC parameters 逐字节一致 → 纯重复 1,750 |
| `read` 与 `readtext` | 各 1,610 字符 | 参数结构完全相同，分属 FUNDAMENTAL / FILE 两个分类 → 纯重复 1,610 |

两项合计 3,360 字符，**占现状 payload 的 17%，且不带来任何新增能力**。

### 1.5 明确不做的事（范围边界）

| 不做 | 理由 |
|---|---|
| 不改任何工具实现 | 方案只动"哪些工具下发给 LLM"，与工具功能无关 |
| 不改 `searchtool` 的检索机制本身 | 只解决"裁掉的工具还能否被找回"这一衔接问题，不重写检索 |
| 不与 `[2] strict 400` 方案混批 | 两件事互不相干，按 `AGENTS.md` 分批提交，避免互相干扰排障 |
| 不做运行时动态改名单 | YAGNI：先满足"可配置"（改常量即改），不做热更新 |

## 二、实施方案

### 2.1 现状机制（已逐行核实，代码事实）

下发清单由 `_loaded_categories` **单一驱动**，共 4 个消费点：

```
UniversalAgent.__init__  (universal_agent.py:60,71)
   └─ _INITIAL_CATEGORIES = {FUNDAMENTAL, FILE}
        └─ ToolLoader.init_tools(categories)          tool_loader.py:28-41
             ├─ agent._tools_dict.update(该分类全部实现)   ← 可执行工具集
             └─ agent._loaded_categories.add(cat)        ← 分类已注册标记

ToolLoader.load_category(cat)                      tool_loader.py:47-61   ← searchtool 动态注入走这里
   └─ 同上: _tools_dict.update + _loaded_categories.add

get_openai_tools(agent)                            tool_cache_manager.py:19-40
   └─ to_openai_tools(categories=agent._loaded_categories)   ← ★ 决定发给 LLM 的清单

patch_search_desc(agent)                           tool_cache_manager.py:63-112
   └─ 未加载分类 = 全集 - _loaded_categories → 拼进 searchtool 描述

auto_inject_from_search(matches)                   tool_executor.py:104-132
   └─ 命中工具的分类若不在 _loaded_categories → load_category → 失效缓存 + 改 searchtool 描述
```

**关键结构问题**：`_loaded_categories` 同时承担**两个不同语义**——

| 语义 | 实际用途 |
|---|---|
| ①「该分类的实现已注册到本 agent，可执行」 | `tool_executor.py:122` 判是否重复注入 |
| ②「该分类的工具要下发给 LLM」 | `tool_cache_manager.py:30` 筛下发清单 |

名单化后 ① 和 ② 必须**解耦**：分类仍可整类注册（保执行能力），但下发只给名单内的。

### 2.2 一个必须先说的隐患：裁掉 FILE 工具会让 searchtool 找不回

**这不是我的推测，是从 2.1 的代码链直接推出来的**：

| 步骤 | 现状行为 |
|---|---|
| 1 | `init_tools` 加载 FUNDAMENTAL + FILE → `_loaded_categories = {FUNDAMENTAL, FILE}` |
| 2 | FILE 全部 14 个工具下发（因为下发清单 = `_loaded_categories` 筛分类） |
| 3 | `patch_search_desc` 计算「未加载分类」= 全集 − {FUNDAMENTAL, FILE} = **8 个**，描述里**不含 FILE** |
| 4 | LLM 想用 FILE 里的工具 → 已经下发，直接调 |

**若把 FILE 裁到只剩 6 个**：

| 步骤 | 裁剪后行为 | 后果 |
|---|---|---|
| 1' | `_loaded_categories` 仍含 FILE（分类仍整类注册） | — |
| 2' | 只下发 6 个 | `copy` `move` `rename` `delete` `compress` `extract` `readmedia` 看不到 |
| 3' | 未加载分类仍**不含 FILE** | searchtool 描述不提 FILE |
| 4' | LLM 找 `compress` → 既没下发、searchtool 也不提示 FILE | **永久不可达** ← 功能缺失 |

**结论：FUNDAMENTAL 可以放心裁，FILE 裁剪必须同时解决"发现路径"，否则会静默丢能力。** 这是本方案最重要的一条约束。

### 2.3 三个候选方案

#### 路线一：仅隐藏下发（`expose_to_llm=False`，零结构改动）

| 项 | 内容 |
|---|---|
| 做法 | ① 首发名单里去掉 `shell`（保留 `bash`），靠 `tools_alias_mapper.py:366` 已有的别名映射兜住 LLM 误叫；② 首发名单里去掉 `read`（保留 `readtext`，参数结构相同） |
| 改动文件 | **2 个**：`fundamental_register.py`（别名注册）、`universal_agent.py`（名单常量） |
| 收益 | 20,062 → 约 16,700，**省 17%**（实测 FUNDAMENTAL 7 个 7,504 → 去 `shell`+`read` 后 3,821，省 3,683） |
| 风险 | `bash` 被 LLM 主动选择频率高，砍 `shell` 需确认别名映射真能兜住；`read`/`readtext` 砍 `read` 同理 |
| searchtool 影响 | **无**（FUNDAMENTAL 仍整类注册，未加载分类列表不变，兜底路径完好） |

#### 路线二：下发名单制（结构改动，见第三章对照）

| 项 | 内容 |

### 2.6 风险与防护

| # | 风险 | 后果 | 防护 |
|---|---|---|---|
| R1 | 名单里写了已改名/已删除的工具 | 静默不发该工具，LLM 看不到 | 启动时校验「名单 ⊆ 注册表」，不匹配记 `error` 日志；加单测断言 |

### 3.5 一处既有的漏判，以及本轮核查新增的两处安全遗漏

#### 3.5.1 既有一处漏判（本方案顺带修掉）

**先更正本文档早前一处不准确的判断**：v1.0 曾称「LLM 走 `bash` 调命令时安全门控一直被绕过」——**不准确**。查证：

| 调用点 | 是否走归一化 | 现状对 `bash` 是否生效 |
|---|---|---|
| `registry.get_tool()` | 先精确命中，命中则**不**映射 | `bash` 精确命中 → 生效 |
| `tools/security/path_safe_check.py:413` | 显式 `normalize_tool_name` | `bash`→`shell` → **生效** |
| `tools/trust.py:111,134` | 显式 `normalize_tool_name` | **生效** |
| **`safety_gate.py:79/176/179/210`** | **裸比较，未归一化** | **不生效 ← 唯一漏网点** |

**结论**：现状是「**一处**漏判」，不是「整体绕过」。

#### 3.5.2 本轮核查新增：v1.4 的改法有错，且漏了 2 处安全判定

**v1.4 的一处自相矛盾**：当时建议把 `safety_gate.py:79` 改为「归一化后比较」。但 3.4 又要求**删除** `"bash": "shell"` 映射——映射删掉后 `normalize_tool_name("bash")` 返回 `"bash"`，仍 `!= "shell"`，**改了等于没改**。

**正确改法**：既然 `shell` 这个注册名已被删除，`tool_name` 根本不可能再是 `"shell"`，所以应**直接改成 `== "bash"`**，不依赖归一化：

```python
# safety_gate.py:79
-    if _ref is None and tool_name == "shell":
+    if _ref is None and tool_name == "bash":
```

**同理必须补的两处安全判定（v1.4 完全遗漏）**——这两处都走 `normalize_tool_name`，映射一删就双双失效：

| 位置 | 现状 | 映射删除后的失效 | 必改 |
|---|---|---|---|
| `safety/sandbox/executor.py:74` | `_shell = frozenset({"shell", "executeshellcommand", "executeshellcommandsafety"})` | `normalize("bash")` → `"bash"`，**不在集合** → **shell 类工具的沙箱判定失效** | 集合加入 `"bash"` |
| `safety/tool_safety_checker.py:267` | `if normalize_tool_name(tool_meta.name or "") in ("shell", "execute_command")` | 同上 → **shell 专属安全检查不进分支** | 元组加入 `"bash"` |

> 这两处**在 v1.4 里完全没提**，属本次十遍核查补出。它们比 `safety_gate` 漏判更严重：前者是沙箱执行判定，后者是安全检查分支，静默失效不报错。

#### 3.5.3 第三处遗漏：超时校验表

```python
# timeout_validator.py:13
    "shell":  (1,   600),     # 1秒 ~ 10分钟
```

`validate_timeout(timeout, tool_name)` 按**工具名**查表。删掉 `shell` 后，`bash` 调用时表里没有对应键 → **运行时超时上下界校验失效**（`ShellInput.timeout` 虽有 `ge=1, le=600`，但这是两层不同的校验，运行时那层会失效）。故该键必须改为 `"bash"`。

#### 3.5.4 一次性影响：历史信任记录与新键不互通

`trust.py:111/134` 用 `normalize_tool_name(tool_name)` 作为信任落库/查询的键：

| | 键 |
|---|---|
| 改动前落库 | `"bash"` → 归一为 `"shell"` → 落 `"shell"` |
| 改动后落库 | `"bash"` → 映射已删 → 落 `"bash"` |

**后果**：改动前用户对 `bash` 建立的信任记录（键 `shell`）在改动后不再命中，需**重新信任一次**。属一次性、可接受的迁移代价；但需在实施记录中写明，避免上线后被当 bug 报。

### 3.6 对注入 / 未注入计算的影响（老陈重点关注项）

**结论：零影响。** 实测对比（同一进程模拟，仅改 `expose_to_llm` 标志，其余不动）：

| 项 | 现状 | 收敛后 | 说明 |
|---|---|---|---|
| `_tools_dict`（可执行工具集） | 21 | 21 | 实现函数未删，`shell`/`readtext` 仍可执行（名字映射进来时） |
| `_loaded_categories`（已注入分类） | FILE, FUNDAMENTAL | **不变** | 按"分类有没有实现"判定，与单个注册名无关 |
| searchtool「未加载分类」 | 8 个 | **不变** | 全集 − `_loaded_categories`，与单个注册名无关 |

| `readmedia`（读图片/音频/视频，返 Base64） | FILE | **DOCUMENT** | `fetchpage` 的工具描述里已写明"不能读取URL，网页中的图片/PDF请用 fetchpage"，而 `readmedia` 正是本地媒体的读取口，归 DOCUMENT 后两侧语义连贯 |
| `searchweb`（搜索引擎查最新信息） | NETWORK | **FUNDAMENTAL** | 属"基础信息获取"，与 `timenow` 同层；几乎所有任务都可能第一步用到 |
| `fetchpage`（抓网页正文） | NETWORK | **FUNDAMENTAL** | 同上，是 `readtext` 的网络对偶（读本地文件 ↔ 读远程网页） |
| `sysinfo`（查 OS/CPU/内存/磁盘/网络） | FUNDAMENTAL | **SYSTEM** | **回归原位**——代码注释明记「`sysinfo — 获取系统信息 (从SYSTEM迁入)`」「`"sysinfo": ["psutil"], # 从SYSTEM迁入`」（`fundamental_register.py:16`、`:33`）。且它的同族 `event_log` 至今仍在 SYSTEM，两者**都依赖 psutil、都是系统诊断类只读查询**，不该分家 |
| `which`（查找命令安装路径） | SHELL | **SYSTEM** | 属"系统环境查询"，与 `sysinfo`（系统资源）、`event_log`（系统日志）同族。SHELL 组仅此一个工具，且执行命令的 `shell` 早在 2026-07-28 就迁到 FUNDAMENTAL（`sandbox/executor.py:72` 注释自证「该枚举仅 `which`」）——该分类已是空壳 |

**`sysinfo` 与 `which` 的连带处置**：`which` 移出后 `SHELL` 分类将**零工具**，而 `ToolCategory` 是枚举全集遍历，`patch_search_desc`（`tool_cache_manager.py:82-85`）会把 `SHELL` 算进「未加载分类」并写进 searchtool 描述 → LLM 搜"命令执行工具"永远零结果 → 反复搜达 3 次触发 `tool_retry_engine` **防死循环熔断致任务 FAILED**（同类后果在 `tools_alias_mapper.py` 注释里有实证记录）。

**本方案对「空分类」采用代码级消除，不靠纪律约束**：删 `SHELL` 枚举的同时，给 `patch_search_desc` 加一条防御——「未加载分类」只统计**有实现**的分类（见 4.2.4）。这样即使将来任何分类变空，也不可能再误导 LLM。

**核查确认以下 4 处不依赖 `ToolCategory.SHELL`**，删除枚举安全：

|---|---|
| `sandbox/executor.py:72` `_is_shell_tool` | 注释明写「**不能仅凭 ToolCategory.SHELL 判定**」，用硬编码集合 `{shell, executeshellcommand, executeshellcommandsafety}` |
| `tools/validate/timeout_validator.py:13` | 按**工具名** `shell` 查超时区间，不按分类 |
| `services/agent/handlers/safety_gate.py:79/176/210` | 均按工具名 `shell` 比较，与分类无关 |
| `tools_alias_mapper.py:169` 的 `shell` 参数别名组 | 按工具名建表，与分类无关 |

#### 4.2.5 核查结论：提示词按分类生成，但**无调用方**，不构成缺陷

实测全仓 `generate_param_reminder` 的调用点**只有 2 处，且都在 `registry.py:333-335` 的定义转发**，`tool_description.py:65` 是本体——**没有任何业务代码调用它**（`tool_cache_manager.py` 只用它取 tools 描述，不取参数提醒）。

| 事实 | 结论 |
|---|---|
| 签名 | `generate_param_reminder(self, category=None, style="code")` —— 只有 `category` 一个筛选项，无工具名入口 |
| 调用方 | **零**（仅定义与转发） |

**因此「工具改分类后从提示词里漏掉参数提醒」不成立**——它压根没被拼进 prompt。本措施**不需要实施**，4.6 中原 H3 消除方式改为「无调用方，已排除」。

### 4.2.6 为什么这样仍是最小影响

`ToolRegistry` 在注册时用传入的 category 自动建索引：

```python
# registry.py:252-254
self._categories.setdefault(category, [])
if name not in self._categories[category]:
    self._categories[category].append(name)
```

即**索引、`get_implementations_by_category`、下发筛选全部自动跟随**，无需改 `registry.py`。

### 4.3 category 的全部消费点（实测枚举，确认无隐藏分支）

| 消费点 | 用途 | 改分类后是否需改代码 |
|---|---|---|
| `tool_description.py:34` | `to_openai_tools` 按 category 筛选**下发给 LLM** 的清单 | 否（自动跟随） |
| `tool_description.py:90` | `generate_param_reminder` 按 category 筛参数提示 | 否 |
| `tool_search.py:230` | `searchtool` 返回 `metadata.category.value` 供检索匹配 | 否 |
| `tool_executor.py:110` | 解析检索结果的分类 → **整类注入** | 否（但有连带体量问题，见 4.4） |
| `registry.py:293` | `list_tools` 返回 category 供前端展示 | 否 |

**结论：`category` 只影响「下发给谁 / 提示里提不提 / 检索归类 / 前端展示」四处，没有任何按分类的安全、参数或执行分支。** 这是本次改动能保持最小影响的根本原因。

### 4.4 实测影响（token 与清单）

> **重要**：以下为「覆盖生效后」的推算值。实测脚本未真正改 `category`（改注册表有副作用），故用清单推算方式评估；**另一个实测事实**：`network_register.py` 的 5 个工具（`httpget`/`download`/`fetchpage`/`searchweb`/`ping_port`）目前**全部**是 `NETWORK`，`file_register.py` 的 14 个**全部**是 `FILE`——正因统一赋值，不落覆盖字典就绝不会变。

|---|---|---|
| 现状 | 21 | 16,628 字符 |

**② ★连带风险：`searchtool` 整类注入的放大效应**

`tool_executor.py:110` 解析出分类后是**整类注入**（`load_category`），所以：

| | DOCUMENT 分类内容 | schema 合计 |
|---|---|---|
| 现状 DOCUMENT | 8 个（`read_docx`/`read_pdf`/`read_pptx`/`read_xlsx`/`write_docx`/`write_pdf`/`write_pptx`/`write_xlsx`） | 5,496 字符 |

**代价要说清**：

| 场景 | 现状 | 调整后 |
|---|---|---|
| LLM 想解压（`extract`） | 默认就下发，直接用，**零额外注入** | 需先 `searchtool` → **一次性注入 DOCUMENT 全部 11 个（7,787 字符）**才拿到 `extract` |
| LLM 想读图片 | 同上，默认可见 | 需注入 DOCUMENT 全部 11 个 |

**这是一次性的代价，不是每轮都付**（`invalidate_tool_cache` 后注入结果被缓存，后续轮次复用）。但对"偶尔解压一次"的任务而言，**为719 字符的 `extract` 先吃掉 7,787 字符**是不划算的。

**规避选项（供老陈取舍）**：
