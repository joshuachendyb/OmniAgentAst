## 一、服务中断情况分类

按"是否可控收信号"分两类。

### 1.1 共同后果

进程被中止 → Agent 内存态（LLM 上下文、执行步、工具调用栈）消失 → 任务只能回到 `task_interrupted`，需手动重发整个任务。

### 1.2 可控停止（收得到关闭信号）

| 场景 | 触发 | 能否落最终 checkpoint |
|------|------|----------------------|
| 正常关机 | 发送关机信号，进程收到 | ✅ 能 |
| 正常重启 | 同上 | ✅ 能 |
| 配置生效重启 / `--reload` | 收到重启请求 | ✅ 能 |

恢复点可贴近中断前。

### 1.3 突发中止（收不到信号）

| 场景 | 触发 | 能否落最终 checkpoint |
|------|------|----------------------|
| 断电 / 强制断电 | 无信号 | ❌ 不能 |
| OOM / `kill -9` | 进程被强杀 | ❌ 不能 |
| 机器死机 / 容器强杀 | 无信号 | ❌ 不能 |

只能回退到最近一次周期性 checkpoint，最多丢一个写入间隔。

### 1.4 共同行为

两类都丢失内存态；区别只在"恢复粒度"：可控停止可在 shutdown 钩子落最终 checkpoint；突发中止只能靠周期写入。

## 二、重启运行后进入当前会话——能否继续、如何运行

### 2.1 现状（[63] P3 完成后）

- 未完成任务：进程重启后返回 `task_interrupted`；前端只能降级加载 DB 历史，用户**手动重发**。
- 已完成任务：可从 Journal 按 seq 精确回放。

### 2.2 目标能力（R4）

重启运行后进入当前会话，系统自动**识别未完成任务**并**续算**：

```text
后端启动
  → 扫描 chat_tasks 中非终态任务
  → 有最近完好 checkpoint：重建 agent_runner，从 checkpoint 续跑
      新事件续写同一 task 的 Journal，seq 连续
      前端按 after_seq 自然续拉，无需感知
  → 无 checkpoint 或损坏：保持 task_interrupted（现状语义，不劣化）
```

### 2.3 不能继续的情形

| 情形 | 行为 |
|------|------|
| 无 checkpoint | `task_interrupted`，手动重发（同现状） |
| checkpoint 损坏 / 校验失败 | 降级 `task_interrupted` |
| LLM 配置版本不符 / generation 过期 | 降级 `task_interrupted`，丢弃跨代结果 |
| 不可序列化资源（进行中命令、文件句柄） | 该步骤标记"需重做"，禁止盲重放 |

## 五、link（任务上下文链）全链路分析与改造方案

### 5.1 需求语义定案（北京老陈 2026-10-02）

当前实现与真实需求**语义相反**，逐条定案如下：

| # | 语义条款 | 定案内容 |
|---|---------|---------|
| 1 | link 是**粘性状态** | 不是"每条消息各选各的"一次性参数。UI 设置一次后保持，**不得设置完就弹回** |
| 2 | 开启的含义 | 从"从不 link"改为"link"，表示**下一个新任务与前一条任务是连续的**，即并入当前组 |
| 3 | 持续性 | 此后每一条新任务都进入同一组，**一直持续到用户关闭 link 为止** |
| 4 | 关闭的含义 | 关闭 link 即组结束；下一次再开启 link 时**另起新组** |
| 5 | 分组边界 | 由 link **关闭的时刻**决定，而非每条消息各自决定 |
| 6 | 会话隔离 | 每个会话**各自独立记忆**自己的 link 状态 |
| 7 | 前一条任务口径 | 取会话内**最近一条任务，任意状态都算**（实际可取到 failed / cancelled / 中断态等非活跃态；`running`/`paused` 不会成为"前一条"，那种情况走消息注入而不新建任务，见 5.4「活跃任务注入」行） |
| 8 | 组可见性 | UI 上要能看到任务属于哪一组，加**组徽标** |

**关键推论**：link 关闭期间发出的任务各自为独立新组；link 一旦开启，新任务并入**前一条任务所在的组**（不论前一条自己当时开没开 link），随后每条都进这个组。

### 5.2 语义推演（示例）

设 `context_root_task_id` 为链根，相同链根即同组：

| 序 | link 开关 | 任务 | 前一条任务 | 链根 | 分组结果 |
|----|----------|------|-----------|------|---------|
| 1 | 关 | A | — | A | 新组 G1 |
| 2 | 关 | B | A | B | 新组 G2（关着就各组各的） |
| 3 | **开** | C | B | **B** | 并入 G2 |
| 4 | 开 | D | C | **B** | 并入 G2（链根沿用，不逐跳上跳） |
| 5 | **关** | E | D | **E** | 新组 G3（关 link 即切断） |
| 6 | **开** | F | E | **E** | 并入 G3 |

对照现状：第 3 步若前一条 B 是 `failed`，现有 SQL 直接跳过 B，导致 C 链根错误地回溯到更早的完成任务甚至自为链根 —— 这就是"各种状态都需要"要修的核心点。

| 1 | link 状态存哪 | **后端 `chat_sessions` 新增列** | 条款 6 要求以会话为键；铁规 1.5「后端为主，前端迎合后端」；只有后端能权威判定组边界。存前端 localStorage 会出现多设备不一致 |

#### 5.7.14 后端请求携带改动

**背景**：编排器 `stream_orchestrator.py:441` 纯从 DB 读 `get_session_link(conn, session_id)`，**不读请求** —— 值必须"提前存在于数据库"。现改为**值随消息到达**：后端在同一编排内完成"建会话/更新会话 → 读 link → 算链根"，载体与内容同时建立。

**5 个修改单元**

| # | 文件 | 改动 |
|---|------|------|
| 1 | `app/api/v1/chat/models.py` | `ChatRequest` 增 `link_enabled: Optional[bool] = None`。**语义**：`None`=未携带，沿用会话当前值；`True/False`=本次携带的开关真值。**不得复用已废止的 `context_link_mode` 名**（禁 backward） |
| 2 | `app/api/v1/chat/chat_routes.py` | 以**关键字**传 `link_enabled=request.link_enabled` 给编排器 |
| 3 | `app/services/chat/storage.py` | **新增 conn 级写函数** `set_session_link_conn(conn, session_id, enabled)`（与既有 `get_session_link` 同族同出口，判定/SQL 只在 storage 层 — SLAP） |
| 4 | `app/services/chat/session_service.py` | `set_session_link` 改为**委托** `set_session_link_conn` 复用同一份 SQL（DRY：消除重复 UPDATE 语句）；自身对外签名与 404 语义**不变**（其 6 个 case 不受影响） |

**为什么第 3、4 单元不可省（编排期 DB I/O 铁律）**

`stream_orchestrator.py:83-84` 登记「请求编排期 loop 零同步 DB I/O」（2026-08-24 后端卡死事故修复结论）。既有 `session_service.set_session_link` 是**同步**函数、走 `db.get_conn("chat")` 上下文管理器，**在 async 生成器里直接调用会阻塞事件循环**。既有 `get_session_link` 正是为此才在 5.10.1 被抽成 conn 级读函数并经 `db.atxn` offload。写侧须同构处理，故：

- 新增 `set_session_link_conn(conn, ...)`（SQL 单一来源）
- `session_service.set_session_link` 改为委托（避免两份 UPDATE SQL 漂移）
- 编排器经 `db.atxn("chat", lambda conn: set_session_link_conn(conn, session_id, link_enabled))` 调用

**禁 backward 自检**：`context_link_mode` **不得**在请求体复活。它与已废止字段同名同义，若复活即等于把"本次任务临时模式、不落库的旧通道"请回来，构成双通道。故 5.11.3 的 4 个"禁止 backward 残留"用例（`test_chat_request_has_no_context_link_mode`、`test_chat_route_does_not_forward_context_link_mode`、`test_orchestrator_signature_has_no_context_link_mode`、`test_no_context_link_mode_whitelist_dead_validation`）**继续有效且必须保留**。

**不受影响的部分**：修改 5 **只动取值来源，不动链根/历史判定逻辑**。故 5.7.3（`get_previous_task_chain` 任意状态口径）、5.7.11（链根下移 + `_chain_root`/`_history_root` 拆分）、5.7.12（fail-closed 双边界）等已落地实现与对应用例**全部继续有效**。`chat_tasks.context_link_mode` 列**已存在**，每任务 link 状态快照天然落库、可追溯，**无需新增**。

```
  → 读 link = true                          ← 值同时到达, 不需要"预先存在"
  → 算链根 / 装历史 / 落任务快照
```

| 真源 | `chat_sessions.link_enabled` | 会话当前开关，唯一权威 |
| 快照 | `chat_tasks.context_link_mode` | 任务启动那一刻的开关值（历史事实，**保留**，供遥测/展示） |
| 镜像 | 前端 `useChatState.linkEnabled` | 真源的只读镜像，随会话加载刷新 |

**最简链路（单向、无推演）**

```
勾开关 → 纯本地 setLinkEnabled(立即可见, 不发请求)
发消息 → 消息与 link_enabled 同一请求体到达
后端同一编排内: 建会话 或 更新会话 link_enabled → 读 link → 算链根 → 装历史 → 落任务快照
```

载体（会话）与内容（消息 + link）在同一请求内先后建立，故不存在"先有会话才无处写"的依赖问题。

**四点加固定案（以"简洁 + 不易错"为准绳）**

1. **竞态**：勾选与发消息本是一体（同一次交互的两个字段），故勾选**即本地可见（乐观 UI），落库随发送**。服务端权威体现在**会话加载时的初值来源** —— `GET /sessions/{id}/messages` 返回 `link_enabled` 决定刷新/打开会话时的勾选显示。写路径唯一（发送请求体），无乐观推演、无双通道。
2. **链根口径**：`get_previous_task_chain` 取「会话最近一条任务（任意状态）」的链根。较原「仅成功任务」**少一个状态分支**，更简且更符合"组"语义（失败尝试亦属连续对话）。属**行为变更**，已确认。
3. **`context_root_task_id` 双取值**：落库=自身（independent 组由此天然成为自成一组的链根，前端分组所需）；传 `history_loader`=None（表"无链可沿"，不装历史）。同一字段两语境取值，是功能倒逼而非冗余，**不引入额外抽象**，以本文档标注固化。
4. **部署原子性**：本次删除请求级 `context_link_mode`，旧前端多发字段被 Pydantic `extra='ignore'` 静默丢弃 → 若后端先上线则续聊**静默失效**。**前后端必须同批原子发布**，不得滚动。

**简洁性自检**

| 关注点 | 方案 | 剩余出错点 |
|--------|------|-----------|
| 开关状态 | 后端权威，前端只镜像 | 无 |
| 链根判定 | 单判据（存在） | 无 |
| 字段取值 | 一字段两语境，自洽 | 文档标注 |
| 旧通道 | 全删，无双通道 | 部署须原子 |

**结论**：**一个真源 + 一次写 + 一次读 + 一个分组键，其余全删**——链路单向、无第二真源、无回读推演，符合系统设计基本原则。

#### 5.8.19 前端请求携带链路

**原则**：勾选状态是**本地 UI 态**，随消息落库。一条链路到底：`linkEnabled` → 请求体 `link_enabled` → 后端落会话真源 → 算链根。不设第二个写入口。

| 层 | 做法 |
|---|---|
| `ChatInput.tsx` | `onSend(content, backupLinked: boolean)` —— 第二参传**布尔**，不做 `'linked'/'independent'` 字符串映射 |
| `useChatSend.ts` | `handleSend(messageContent, linkEnabled: boolean)`、`executeSend(userMessage, linkEnabled: boolean)` |
| `useChatStreaming.ts` | `sendMessage(content, customSessionId?, linkEnabled: boolean)`、`executeSend(userMessage, linkEnabled: boolean)` |
| `chatStreamStore.ts` | `SessionSnapshot.lastContextLinkMode` **改名为 `linkEnabled: boolean`**（`:243` 类型 / `:576` 初值 `false` / `:675` 每次发送赋值 / `:391` 进备份）；`sendMessage(sessionId, content, linkEnabled: boolean)` 收第 3 参 |
| `chatStreamTransport.ts` | **零新增形参** —— `sendStreamRequest(s, content)` 的 `s` 里已带 `linkEnabled`，body 直接 `link_enabled: s.linkEnabled`；删 `mode` 形参 |
| `backupTypes.ts` / `chatStreamPersistence.ts` | `lastContextLinkMode` 同步改名 `linkEnabled`，保留持久化与恢复 |

**为何 `lastContextLinkMode` 改名而非删除**：它是本链路在 store 侧的唯一载体，且随备份落盘、随恢复还原（重连/回放天然带值）。另起形参链反而多一层透传，并使值出现两个可能不一致的副本。

**字段名对照（严防错配）**

| 环节 | 名称 |
|---|---|
| React state / 各层形参 / session 字段 | `linkEnabled` |
| **HTTP 请求体** | **`link_enabled`** |
| 后端 `ChatRequest` / `chat_sessions` 列 | `link_enabled` |
| 后端 `chat_tasks` 快照列 | `context_link_mode`（既有 schema，由 `link_enabled` 推导） |

**禁 backward 自检**：`context_link_mode` **不得**在请求体复活 —— 它是已废止的"本次任务临时模式、不落库"旧通道，复活即成双通道。故 5.11.3 的 4 个"禁止 backward 残留"用例继续有效。

**边界澄清**：`chat_tasks.context_link_mode` 是 **DB 列名**、每任务 link 状态快照，与 wire 层的 `link_enabled` 不同域。DB 层与 wire 层不得再出现 `context_link_mode` 这个**字段名**（请求体、编排器签名、`history_loader` 形参三处均已禁）。

**与后端契约的对应（严防字段名错配）**

| 环节 | 字段名 |
|---|---|
| 前端 React state | `linkEnabled` |
| 前端各层形参 | `linkEnabled` |
| **HTTP 请求体字段** | **`link_enabled`** |
| 后端 `ChatRequest` 字段 | `link_enabled: Optional[bool]` |
| 后端 `chat_sessions` 列 | `link_enabled` |
| 后端 `chat_tasks` 快照列 | `context_link_mode`（**保持不变**，由 `link_enabled` 推导，5.7 项列名沿用既有 schema） |

**禁 backward 自检**：`context_link_mode` **不得**在请求体复活。它与已删字段同名同义，若复活即等于把已废止的"本次任务临时模式"通道请回来，构成双通道。故 5.11.3 的 4 个"禁止 backward 残留"用例（`test_chat_request_has_no_context_link_mode`、`test_chat_route_does_not_forward_context_link_mode`、`test_orchestrator_signature_has_no_context_link_mode`、`test_no_context_link_mode_whitelist_dead_validation`）**继续有效且必须保留**。

`_ensure_column` 的真实定义（`db_initializer.py`，逐字）：

```python
def _ensure_column(conn: sqlite3.Connection, table: str, column: str, col_type: str):
    """确保字段存在(添加异常处理,失败不中断init)"""
    try:
        rows = conn.execute(f"PRAGMA table_info({table})").fetchall()
        col_names = {row["name"].lower() for row in rows}
        if column.lower() not in col_names:
            conn.execute(f"ALTER TABLE {table} ADD COLUMN {column} {col_type}")
            logger.info(f"Added column {column} to table {table}")
    except Exception as e:
```

| # | 设计原写法 | 缺陷 | 实施纠正 |

#### 5.12.3 已知副作用登记（经评估**确认保留**，非疏漏）
