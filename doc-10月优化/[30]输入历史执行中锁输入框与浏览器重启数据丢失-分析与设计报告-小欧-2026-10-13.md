## 一、问题提出

北京老陈 2026-10-13 提出两个问题：

1. 模型执行中（`isReceiving=true` 且续聊关）输入框被 `disabled`，判定"这个肯定不能执行"——即锁死输入不可接受。
2. 数据存在浏览器中，**浏览器关闭后重启，数据还在不在**。

## 二、问题一：执行中输入框被锁死

### 2.1 根因定位

`ChatInput.tsx` 把同一个判据 `sendBlocked` 同时用于**两个不同性质**的用途：

```
sendBlocked = isSendBlocked(loading, isReceiving, allowInterject)

用途一（合理）：handleSendInternal 的提交门 —— 防止执行中抢发新任务
用途二（错误）：InputCore 的 disabled —— 连带把「编辑能力」一起禁掉
```

这是典型的**关注点混用**：发送门要拦的是「提交动作」，而不是「编辑能力」。文档[11] §3.5.2 的原始意图是"执行中不能抢着发新任务"，**从未要求"执行中不许写字"**。当前实现把意图扩大成了后者。

### 2.2 连带损失的功能

执行期间（模型正在回答，通常是数秒到数十秒）用户被剥夺了：

| 能力 | 本应可用 | 现状 |
|---|---|---|
| 起草下一条消息 | ✅ | ❌ 输入框禁用 |
| `↑`/`↓` 翻历史 | ✅ | ❌ 按键到不了 textarea |
| 打开「历史输入」面板选一条 | ✅ | ❌ 面板按钮仍可点，但选完无法编辑 |
| 草稿自动保存 | ✅ | ❌ |

**这恰好是用户最想翻历史的时段** —— 刚问完、等回答时最容易想"我刚才到底问了啥"。

### 2.3 关键证据：发送其实不需要锁输入框

读 `SubmitBar.tsx:83` 确认：执行中 `loading || isReceiving` 为真时，SubmitBar 渲染的是「停止」「暂停」两个按钮，**根本不渲染发送按钮**。即"阻止执行中抢发"这件事**已经由 UI 层独立完成了**，`disabled` 是重复防护且过度防护。

另读 `useChatSend.ts:107`：

```
const isInterject = isInterjectRoute(isReceiving, allowInterject);
```

当 `allowInterject=true`（插话开）时，执行中按 Enter **本来就允许发送**（走插话路由）。这证明「执行中一律禁发」并非系统不变量，而是当前 `disabled` 造成的表象。

### 2.4 方案对比

「不能发送」的 UI 体现，四个候选：

| 方案 | 内容 | 评价 |
|---|---|---|
| A | 执行中发送按钮消失 | 作废：北京老陈不选（太隐晦，用户不知道原因） |
| **B（选定）** | 发送按钮**保留但置灰** + hover Tooltip 说明不可发送 | ✅ 明确表达"有按钮但此刻不能按"，并解释原因 |
| **C（选定）** | 输入框下方**常驻灰字**说明当前状态与出路 | ✅ 把"为什么不能发 + 怎么才能发"直接摆在眼前 |
| D | 完全不提示 | ❌ 就是现状，最差 |

### 2.5 选定方案 B+C 的实施要点

**B — 发送按钮置灰 + Tooltip**

1. `SubmitBar` 在 `loading || isReceiving` 时，**除「停止」「暂停」外一并渲染发送按钮**，不再二选一。
2. 按钮 `disabled` 判据与提交门**共用同一真源** `isSendBlocked(...)`，保证「按钮能点 ⇔ 真能发」。
   - 这一条是关键：若按钮常亮而实际发不了，或按钮灰着而回车能发，都会制造新的矛盾。
   - 因此 `allowInterject=true`（插话开）时按钮**可用**，点击走插话路由——与 Enter 行为一致。
3. Tooltip 文案：「任务执行中，暂不可发送」。
   - `allowInterject=true` 时不显示 Tooltip（此时可发）。

**C — 输入框下方常驻灰字**

4. 在输入框与 SubmitBar 之间渲染一行灰字。
5. ⚠️ **显隐判据必须是 `sendBlocked`，与发送按钮置灰同源**。
   - 实施自纠：初版写成 `isReceiving && !allowInterject`，与按钮判据**两套打架**——在
     `loading=true` 而 `isReceiving=false` 的窗口里，按钮灰着却没有任何说明，又退回「不知道为什么」。
   - 已改为 `sendBlocked`，并按受阻原因分文案。
6. 复用 `Colors.TEXT.SECONDARY` 与 `FontSize.CAPTION` 令牌，不自写颜色。
7. 插话开关一打开，`sendBlocked` 变假 → 该行立即消失（此时已可发，无需解释）。

**配套修正（属缺陷修复）**

8. `InputCore` 的 `disabled` 不再绑定 `sendBlocked`，恒可编辑。
9. ⚠️ **Enter 行为改案（v1.1 → v1.2）**
   - v1.1 原写「Enter 被拦时弹一次提示」。实施中真浏览器实测发现**该做法本身造成功能退化**：
     `InputCore` 原先无条件 `if (!shiftKey) preventDefault()`，于是执行中按回车**既不换行也不发送**，
     用户打不了多行消息（实测：按回车后内容无换行、仅弹 toast）。
   - 改案为**按「能否发送」分流**：
     | 能否发送 | Enter 行为 |
     |---|---|
     | 能 | `preventDefault` 并提交 |
     | 不能 | **不拦截，照常换行** |
   - 「为什么不能发」由 B 与 C 表达，回车不再重复弹提示。
   - 实施方式：`InputCore` 的 `onPressEnter` 签名由 `() => void` 改为收事件，把决定权交回调用方；
     同时删除已成死参的 `disabled` prop。

### 2.6 风险评估

| 风险 | 评估 | 缓解 |
|---|---|---|
| 按钮置灰但回车能发（状态不一致） | 中 | 判据与提交门共用 `isSendBlocked`，并用回归用例锁死一致性 |
| 常驻灰行挤占垂直空间 | 低 | 仅执行中显示，`FontSize.CAPTION` 单行；执行中本就是等待态 |
| 与文档[11] §3.5.2 冲突 | 无 | `isSendBlocked` 仍是提交门单一真源，`sendGate.ts` 不改 |
| 双击连发 | 低 | 非执行中 `sendBlocked=loading` 仍拦 |

## 三、问题二：浏览器关闭重启后数据丢失

### 3.1 根因定位

| 数据 | 存储位置 | 浏览器关闭重启后 |
|---|---|---|
| 最近提交历史（`recentInputs.ts`） | `localStorage` | ✅ **还在** |
| 草稿（`chatStreamPersistence.ts` 的 `saveDraft/loadDraft`） | `sessionStorage` | ❌ **没了** |

`sessionStorage` 的语义是**按浏览器会话（标签页级）隔离**，浏览器窗口完全关闭即整体销毁。因此：

- 刷新页面（F5）→ sessionStorage 保留 → 草稿还在 ✅
- 关掉标签页/浏览器 → sessionStorage 销毁 → **草稿全丢** ❌
- 浏览器崩溃/系统强制结束 → 草稿全丢 ❌

### 3.2 方案对比

| 方案 | 内容 | 评价 |
|---|---|---|
| **A（选定）** | 草稿迁 `localStorage` + 保留期(TTL) + 数量上限 | ✅ 真正解决，且用 TTL/上限收敛风险 |
| B | 保持 `sessionStorage`，关闭前提示用户 | ❌ 没解决问题，只是提醒 |
| C | 草稿不落盘，纯内存 | ❌ 刷新即丢，比现状还差 |

### 3.3 选定方案 A 的设计要点（最终口径）

1. **存储后端**：`sessionStorage` → `localStorage`。
2. **保留期**：跟随会话生命周期 + 7 天孤儿兜底 + 50 条上限（§3.5 展开）。
3. **键名**：沿用既有 `DRAFT_KEY = sse_draft_v1_<sessionId>`，不新建命名体系。
4. **值结构**：由纯字符串改为 `{ t: string, ts: number }`；读到无 `ts` 的旧值按「内容有效但不计龄」处理，**不丢内容**。
5. **影响面**：`saveDraft/loadDraft` 被 `chatStreamStore.ts:1106` 用于「会话驱逐时清草稿」，改存储后端后该调用语义不变（仍是删键），无需改动该文件。

### 3.4 实施自纠（v1.2 补记）

| 自纠项 | 说明 |
|---|---|
| 清理函数挂在了打字路径上 | `evictStaleDrafts` 要遍历**整个** localStorage（不止草稿键，还有 `chat_session_state`、`execution_steps_backup` 等），而它原先在**每次按键**时被调用。键数上百时即为真实卡顿。已加 5 秒节流——清理本就是「过期/超额才删」的兜底，晚几秒无副作用 |
| 淘汰逻辑写得绕 | 初版用 `doomed` 反推待删条数，极易算错。已改为「收集存活项 → 排序 → 直接切前 N 个删」的直线写法 |

### 3.5 保留期最终口径（明确回答「保存多久」）

| 数据 | 键 | 何时被删 |
|---|---|---|
| 草稿 | `sse_draft_v1_<会话id>` | ① 会话被删 → **立刻跟着删**<br>② **7 天**未触碰且会话已不存在（孤儿键）→ 删<br>③ 超过 50 个会话草稿 → 淘汰最旧 |
| 最近提交 | `omniagent_recent_inputs_v1` | ① 手动点「清空」<br>② 超过 20 条 → 挤掉最旧<br>③ **无任何时间限制** |

**重要澄清**：**7 天不是「关浏览器 7 天就过期」**。草稿关闭浏览器多久都在，7 天只针对**孤儿键**（会话记录已消失、只剩草稿键残留）。最近提交则完全没有 TTL。

### 3.6 「会话删则草稿删」如何成立（核实结论）

未新拉清理线，而是核实后确认**自动成立**：`History` 页三处删除（`index.tsx` 的单删/批删/全删）均调用 `chatStreamStore.destroySession(sessionId)`，而其内部执行的就是 `saveDraft(sessionId, '')`——删除的是同一套键。故只要 `saveDraft` 换存储后端，该语义立即生效。

### 3.7 前端与后端都重启是否受影响（实测结论）

**不受影响**。草稿与最近提交**全程不经过后端**，就落在用户电脑磁盘的浏览器存储里，服务端重启对其零影响。

实测方式为最严苛路径：写入数据 → **彻底关闭浏览器进程** → 以同一磁盘 profile **全新启动**：

```
1st 落盘键: [ 'omniagent_recent_inputs_v1', 'sse_draft_v1_s1' ]
2nd 草稿:       "未发送的草稿"            ✅ 读回
2nd 最近提交:   ["第二条提问","第一条提问"]   ✅ 读回
```

### 3.4 风险评估

| 风险 | 评估 | 缓解 |
|---|---|---|
| 隐私：草稿在磁盘留痕更久 | 中 | TTL 7 天 + 用户可主动「丢弃草稿」 |
| localStorage 容量（约 5MB）被草稿占满 | 低 | 草稿是短文本（输入框可见 5 行）+ 50 条上限 |
| 旧格式值解析失败 | 中 | 第 5 点的兼容处理，保证不丢内容 |

## 六、已知边界（知情项）

| 边界 | 说明 |
|---|---|
| 草稿留痕期变长 | 换 localStorage 后隐私暴露面比 sessionStorage 大，靠 7 天孤儿 TTL + 「丢弃草稿」按钮收敛 |
| 不跨设备 | 换浏览器 / 换电脑 / 清浏览器数据即全丢，无跨设备同步 |
| 无痕模式 | 窗口关闭即丢（预期内） |
| 后端库被重置 | 会话 id 全变 → 草稿成孤儿键，7 天后自动清 |
| 最近提交是影子副本 | 后端 `chat_user_message.content` 已存全部提问（`GET /sessions/{id}/user_messages` 端点已存在），前端这份是**权宜副本**。迁后端需新增一个全局最近端点（现有端点按 `session_id` 取，答不了跨会话问题），本次不做 |
| 7 天的含义 | 是孤儿键保留期，**不是**「关浏览器 7 天过期」 |
