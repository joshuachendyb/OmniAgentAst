## 一、问题描述与病因

### 1.1 现象

任务执行中刷新浏览器，回来后正在跑的任务步骤消失，右栏却显示**别的任务**的结果。

实测证据：右栏显示 `运行耗时 134s`、`P:217636 C:9419 T:227055`，精确命中另一任务 `task-93bd8d9a`（该任务真实值 134.4s / 217636·9419·227055），而当前任务真实值是 80.1s / 93223·5681·98904。

### 1.2 病因：一条事件流被写了四份，互不校验

一次任务产生一条事件流，但落在四个地方，各有时间差，**没有任何一处校验是否同源**：

| # | 落点 | 写入时机 |
|---|---|---|
| 1 | `chat_stream_events`（Journal） | 实时，每帧 publish 即落 |
| 2 | `chat_task_steps` | ~~任务结束后补写~~ → 已改为运行期实时 |
| 3 | 内存 Store（`ChatStreamSession`） | 实时 |
| 4 | `sessionStorage` 备份 | 实时但 5s 防抖（仍保留，见第四章 #4） |

缺陷不在某处写错，而在**没有一处保证「读到的是不是同一份、同一个任务的数据」**。

### 1.3 四条链路的断点

| 链路 | 断点 |
|---|---|
| L1 产生→落库 | 跑完才补写。实测任务执行 80 秒期间 `chat_task_steps` 恒为 0 行 |
| L2 落库→传输 | 落库滞后 ⇒ 运行期 `GET /steps` 返回空，前端拿不到本任务步骤 |
| L3 传输→前端恢复 | `serverTaskId` 只经 5s 防抖落盘；`clearSteps` 删备份到下个 `commit` 之间是裸窗口 |
| L4 前端恢复→右栏 | 取不到时兜底把**全会话所有步骤平铺**当当前任务渲染 ⇒ 显示别的任务 |

四者叠加才产生用户看到的现象。

### 1.4 修复顺序

不能先修展示层：L1 缺失时 L4 拿不到本任务步骤；L3 锚点丢失时 L4 连"当前任务是谁"都判不出。故顺序固定 **A→E→B→C/D**。

## 六、B7 实跑验证与帧/步口径（v1.5）

FE-16（关标签页重开）、FE-14（刷新续传）headed 均通过，B7 首获运行时证明。

**帧数 ≠ 步数**（易反复混淆，记此备查）：

| 量 | 含义 | 增长时机 |
|---|---|---|
| **帧 / seq** | 包含 chunk、action、thought、stats、final 等全部细粒度事件 | 流式输出期间持续增长，最细 |
| **步 / step** | 只统计业务事件，**不含 chunk** | 一个业务动作完成才 +1 |

实测 25 步对应 5333 帧。故「帧数停滞」与「任务卡死」不等价。

e2e 代码此前从未被类型检查（`tsconfig.json` 只 `include ["src"]`），已增补 `tsconfig.e2e.json` 并写入 AGENTS.md 纪律。

## 七、计时冻结与格式门禁修复（v1.6）

### 7.1 遇到哪些问题

**1. 第二个任务计时全程不动**

同一会话连跑两个任务，第一个正常走字，第二个从一开始就不动。原因：`metaFrames` 存任务级数据（`startInfo`/`finalStats` 等），却存在会话级对象上，只在会话创建时初始化一次。任务 A 完成写入 `finalStats` 后**无人清理**，B 开始时 `case 'start'` 也不碰它。于是 B 全程 `taskFinished` 恒为真，秒表 `setInterval` 从未启动，耗时回退读 `finalStats.duration` —— A 的死数。后端 stats 正常递增，但被 `finalStats` 优先级挡住，显示不出来。A 正常是因为 A 启动时会话首次创建，`finalStats` 为 `null`。

**2. 任务跑完了，status 却是 failed**

任务实际跑完（6120 帧、`outcome=completed`、231.3s），但 `chat_tasks.status` 是 `failed`/`task_interrupted`。原因：`reconcile_orphaned_tasks` 判据是 `start_time < boot_iso`，分不清「上个进程遗留的僵尸」和「正在飞的任务」。开了 `--reload` 就有第二个实例，一启动就把在飞任务全标成终态，任务真跑完也没逻辑改回 `completed`。而前端 `findLiveTask` 正是靠 `status==='executing'` 找在飞任务，所以产品会挂不回任务。

**3. Prettier 门禁 91 个文件报错**

`printWidth: 80` + `trailingComma: es5`，这批文件按更宽行宽写的。其中 16 个本不该被检查（备份、Playwright 产物、认证状态、fixture、文档）。

**4. case 17 靠运气才绿**

进页面直接发新任务，靠「最近会话恰好有旧任务」才成立。命中空会话时 `旧task=[]`，「旧任务不被误改」这条核心判据直接落空。

### 7.2 如何修改的

**1. 计时冻结：改 1 行**

`chatStreamStore.ts` 的 `clearSteps()`：

```ts
s.isReceiving = false;
s.metaFrames = emptyMetaFrames();   // 新增
backupRemove(sessionId);
```

该函数注释自述「新请求/停止后置空」，已清 `executionSteps`/`currentResponse`/`pendingSteps`/`isReceiving`，`metaFrames` 是唯一漏项。在此补齐，三个消费方（秒表、`useTaskInfo`、`RightViewer`）同时转正确。停止路径 `stop()` 不调此函数，不影响停止后的终态耗时显示。

**2. Prettier 91 → 0**

- `.prettierignore` 补 16 个（备份/产物/认证状态/fixture/文档）
- 逐个格式化 75 个：生产 28、测试 41、e2e 6，每个都跑 eslint
- `npm run check:full` 全绿

**3. case 17 补阶段 0**

旧任务由 case 自己造，不靠环境：发短任务 → `waitDone` → 取 taskId → `pollTaskStatus` 必须 `completed` → 再发新任务。复用 18 已有 helper，没重造。另加硬判据 `oldTasks.includes(taskOld)`，确保验的是本 case 造的那个 A。
