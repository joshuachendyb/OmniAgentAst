## 一、背景与目标

### 1.1 背景

当前"删除路径权限判定"散落在三处，职责交叉：

| 规则 | 现位置 | 返回形态 |
|------|--------|---------|
| R1/R2 路径禁区（system/non_system → 硬拦）+ 白名单 / 临时授权 | `app/safety/delete_path_check.py` | 三元组 `(bool, msg, category)`，二元放行/拒绝 |
| R3-R6 工作区边界（允许根内/外 × 递归） | `app/safety/delete_safety.py` | `SafetyResult`（含 `requires_confirmation`） |
| A族（磁盘根/系统目录）+ 删根硬底线（tools 层，debug 门） | `app/tools/file/delete_file.py` | `str / None` |

读线（`read_path_check.py`）、写线（`write_path_check.py`）的判定已各自完整成文件，无此劈叉。

### 1.2 目标（北京老陈要求）

1. **删线**全部判定集中到 `delete_path_check.py`，包括 `delete_safety.py` 的 R3-R6，包括 `delete_file._guard_forbidden_delete`。
2. **目录分类**集中到一个文件 `path_classify_category.py`。
3. **读线 / 写线**判定各自集中在 `read_path_check.py` / `write_path_check.py`。

## 二、功能层次模型（目标态）

一条路径从"环境"到"能不能做"，依次经过六层，职责不可混：

| 层 | 回答的问题 | 文件 | 处置 |
|----|-----------|------|------|
| **L1 事实层** | 环境是什么（盘符 / 临时目录 / 允许根） | `path_env.py` | 不动 |
| **L2 分类层** | 这条路径是什么性质 | `path_classify_category.py` | 不动（已集中） |
| **L3 判定层** | 这个动作能不能做 | `read_path_check.py` | 不动（已完整） |
| | | `write_path_check.py` | 不动（已完整） |
| | | `delete_path_check.py` | **吸收** `delete_safety` + `guard_forbidden_delete` |
| **L4 公共零件层** | 三线共用判定子步骤 | `path_check_common.py` | 不动 |
| **L5 授权状态层** | 有没有被临时授权 | `temp_auth.py` | 不动 |
| **L6 编排层** | 分派 / 触发 HITL | `path_1st_legality_check` / `dual_path_check` / `shell_path_check` / `tool_safety_checker` | 不动 |

## 三、各层处置理由（逐函数）

### 3.1 L3 删线（本次唯一施工区）

| 函数 | 现在在哪 | 归到哪 | 返回 |
|------|---------|--------|------|
| `validate_delete(path)` | `delete_path_check.py` | 原地（R1/R2 路径禁区 + 白名单 + 临时授权） | `(bool, msg, category)` |
| `check_delete_risk(params)` | `delete_safety.py` | **移入** `delete_path_check.py`（R3-R6 工作区边界） | `SafetyResult` |
| `_guard_forbidden_delete(path)` | `delete_file.py` | **移入** `delete_path_check.py`，公开名 `guard_forbidden_delete`（A族 + 删根硬底线） | `str / None` |

### 3.2 L1 / L2 / L4 / L5（明确不动及理由）

| 文件 | 函数 | 不动的理由 |
|------|------|-----------|
| `path_env.py` | `get_system_drive` / `_system_temp_dir` / `get_default_allowed_paths` | 事实层 ≠ 分类层。该模块读环境变量 / 配置 / 会话，有 I/O 且依赖可失效；并入 `path_classify_category` 会砸掉"工具层唯一可依赖的纯判定模块"保证（见 3.3） |
| `path_classify_category.py` | `is_disk_root` / `is_system_protected_path` / `is_code_root_path` / `is_allowed_root_itself` / `classify_forbidden_path` | 已是唯一分类真源，无需搬 |
| `path_check_common.py` | `check_preconditions`（3 线用）/ `check_whitelist`（2 线用）/ `resolve_allowed_paths`（2 线用） | 被多条线共用；若按字面拆进各线，则 `check_preconditions` 抄 3 份、`check_whitelist` 抄 2 份，违 DRY / 复用优先 |
| `temp_auth.py` | `is_temp_authorized` / `grant_temp_auth` / `clear_temp_auth` / `get_authorized` | 任务级 ContextVar 状态，非分类非单线判定；写入/清空由 L6 编排层调用，判定层只调 `is_temp_authorized` |

### 3.3 关于 `path_env` 不可并入 `path_classify_category` 的正式结论

`path_classify_category.py` 模块头明文保证：

> 本模块为纯判定：零配置读取、零 I/O、不读 `security.enabled`；是**全套路径安全中唯一可被工具层直接依赖的部分**。

这是为 tools 层硬底线（在 `security.enabled=false`、config/会话不可用时仍须能判）而设的架构保证。`path_env` 恰恰执行环境变量读取 / 盘符探测 / 配置读取 / 会话取数，并入即意味着分类层背上 I/O 与可失效依赖，硬底线独立性被破坏。且 `get_default_allowed_paths`（白名单来源）与分类职责无关，并入属 YAGNI。

> 结论：`path_env` 与 `path_classify_category` 是"事实层 ↔ 分类层"的上下游依赖，不是同职。分类层继续 **函数内惰性 import** 使用 `get_system_drive`（现状即是），不合并。

## 五、接口与行为不变式（红线）

1. `validate_delete` 仍返三元组；`check_delete_risk` 仍返 `SafetyResult`。**不合并函数、不改返回类型。**
2. "确认 / HITL 弹窗"仍留在 `tool_safety_checker`。判定文件只产"该不该要确认"的决策。
3. `guard_forbidden_delete` 判据逐字搬迁，仍走 `path_classify_category` 四单源。
4. debug 门（`if get_config().get("logging.debug", False)`）**留在 `delete_file.py` 调用处**，仅函数体搬迁，开关行为零变化。
5. 零行为变化、零退化。

## 九、待优化项：HITL 临时授权提示语义缺失（北京老陈 2026-10-17 提出）

> 本章为**待优化项记录**，非本次施工范围；本次（L3 删线集中化）不动 HITL 文案链。

### 9.1 问题现象

临时授权请求触发 HITL 弹窗时，用户**看得到**"需授权 / 需临时授权"与"操作范围"，但**看不到**：

1. 这是**临时**授权（任务级、一次一申请、任务结束自动失效）；
2. 它与弹窗里那个"信任此操作"勾选框（**会话级信任 trust_session**）是**两套不同机制**。

实测：白名单外场景文案字面含"临时"（`该路径超出允许范围，需临时授权`），但未说明时效；`non_system` 受保护区写入场景连"临时"二字都没有（`该路径在受保护区域，写入需申请授权`）。

### 9.2 事实链（现状提示如何流出）

```
① tool_safety_checker._check_known_risks
     → SafetyResult(requires_confirmation=True,
                    message="该路径超出允许范围，需临时授权: <path>",   ← 文本在此诞生
                    severity="risk", auth_path=<path>)
② safety_gate.check_safety_and_confirm
     → _sl = _classify_safety_level(_msg, _cn)   ← ★用关键词"扫"上面那句中文来分类
     → _content = _msg (+同批提示)
     → ConfirmSpec(content, severity, safety_level, path=auth_path)
③ hitl_gateway.hitl_confirm
     → paused 帧{ content, severity, safety_level, trust_path, params, auto_confirm }
④ 前端 AuthorizationModal
     → safety_level="path_auth" → Tag「需授权」；content 原样展示；信任勾选 → trust_session
```

### 9.3 全局系统的关键事实

| # | 事实 | 影响 |
|---|------|------|
| 1 | **分类字段本已存在，但产地错**：`safety_level`（path_auth/shellparam/...）由 `_classify_safety_level`（`safety_gate.py:143-169`）**关键词扫 message 文本**得出（`"受保护区域" in msg or "超出允许范围" in msg → path_auth`），而非决策点直接给出 | 文本**承重**、非纯展示；改措辞可能悄悄改坏分类，"只改那句 f-string"非安全操作。**根因在此，不在"缺字段"** |
| 2 | 前端 `content` 被 **`WebkitLineClamp: 2` 截断**（`index.tsx:331`） | 把"仅本次任务有效"追加进 `content` 有被截掉风险（正是当前这类缺陷的成因） |
| 3 | **"任务结束自动失效"是后端不变式**：`temp_auth` 为任务级 ContextVar，`react_loop.py:365` 的 `finally clear_temp_auth` | 该语义由后端拥有；展示层不得篡改其含义 |
| 4 | `sandbox_gate.py:150` 已**直接**置 `safety_level="path_auth"`（不经关键词） | 存在"决策点直接置位"的既有范式，本次只是把它推广为唯一写法 |

### 9.4 HITL 相关字段清单（谁在用）

| 字段 | 含义 | 后端产出于 | 前端是否消费 |
|------|------|-----------|-------------|
| `safety_level` | 问题来源分类：`path_auth` / `shellparam` / `command_block` / `tool_delete` / `tool_execute` / `data_guard` / `unregistered` / `forbidden_zone` | `safety_gate._classify_safety_level`（**扫文本**）/ `sandbox_gate`（直接置位） | **✓ 已用**：`SAFETY_LEVEL_CONFIG` → Tag「需授权」（`index.tsx:135`） |
| `severity` | 安全分级：`safe` / `risk` / `dangerous` | `tool_safety_checker` 各分支 | **✗ 未用（死字段）** ← 北京老陈记忆中的"HITL 分类字段一直没被前端使用" |
| `content` | 原因句 | `SafetyResult.message` | ✓ 已用（2 行截断） |
| `trust_path` | 授权 / 操作范围 | `auth_path` | ✓ 已用（操作范围行） |

> **结论：无需新增 `reason_code`。**
> 你记忆里的死字段是 **`severity`**，但**不能拿它来用**：它语义是"危险等级"不是"问题类别"，且**后端仍在消费**（`tool_safety_checker.py:258` 用 `severity == "risk"` 决定是否进沙箱），挪作他途即语义污染。
> 真正该复用的是 **`safety_level`** —— 它**就是**分类字段，前端**已经在用**；唯一毛病是**产地错**（扫文本得出）。

### 9.5 候选落点评估

| 候选位置 | SSOT | 分层正确 | 脆弱耦合 | 结论 |
|---------|------|---------|---------|------|
| A. `tool_safety_checker` 内联 f-string（现状） | ✗ 文本散在判定代码 | ✗ 判定混入展示 | ✗ 分类反向解析它 | 不佳（现状） |
| B. `safety_gate._classify_safety_level` 关键词分类 | ✗ | ✗ | 正是耦合源 | 不佳 |
| C. `hitl_gateway` | ~ | ~ 网关不应管文案 | — | 仅适合透传 |
| D. 新增 `reason_code` 字段 | ~ | ~ 与 `safety_level` 职责重叠 | — 多一份分类真源 | 冗余（违反 DRY / YAGNI） |
| E. **复用现有 `safety_level`（产地归位到决策点）+ 前端目录补说明行** | ✓ 单一真源 | ✓ 判定=数据、展示=呈现 | ✓ 解耦 | **最佳** |

### 9.6 结论：一步到位（不新增任何字段）

**答案是：可以，用现有字段合成即可，不要新增 `reason_code`。** 一步做完，两处一起改：

| # | 动作 | 文件 | 说明 |
|---|------|------|------|
| 1 | **分类真源归位** | `tool_safety_checker.py`、`delete_path_check.py`、`safety_gate.py` | `SafetyResult` 增 `safety_level` 字段；各决策分支（path_auth / tool_delete / shellparam / command_block / tool_write / data_guard / unregistered / forbidden_zone）**直接置位**；`safety_gate` **删 `_classify_safety_level`**，改直读字段（`sandbox_gate.py:150` 已是此写法，归一）。→ 分类不再依赖文案措辞 |
| 2 | **提示合成（复用字段）** | `frontend/src/components/AuthorizationModal/index.tsx` | 在既有 `SAFETY_LEVEL_CONFIG` 目录里给 `path_auth` 增一行说明（如 `临时授权：仅本次任务有效，任务结束自动失效；系统禁区不可授权`），渲染成**独立一行**，紧贴"信任此操作"勾选框。→ 用现有 `safety_level` 合成，无新字段、无新后端文案 |
| 3 | **措辞补齐** | `tool_safety_checker.py` | 两条临时授权分支文案补齐（白名单外补时效、`non_system` 补"临时"二字）；因分类已不依赖文本，措辞可自由改 |

> 一句话：**分类字段早就有（`safety_level`）、前端早在用；要修的是它的产地（决策点直接给），不是再加一个 `reason_code`。** 说明文案复用同一目录（`SAFETY_LEVEL_CONFIG`）合成即可，一步到位。
