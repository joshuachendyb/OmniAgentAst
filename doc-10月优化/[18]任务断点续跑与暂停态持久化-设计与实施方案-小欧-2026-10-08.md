## 一、范围与决策链

### 1.1 北京老陈四条主设计约束（2026-10-08）

| 序号 | 决策 |
|------|------|
| 1 | 任务从属会话，**恒定不可变** |
| 2 | 新起特殊任务时，同时建立一个 1:1 伴随会话 |
| 3 | 隐藏任务 = 不显示步骤细节，但**进度与结果信息必须可见** |
| 4 | 暂停应该是持久化的 |
| 5 | （追加）系统崩溃后，**已落库数据要完整**；残缺要清理，保持 DB 是完整断面；新的能通过注入历史消息继续执行 |

### 1.2 第 5 条的关键澄清（避免了走偏）

小欧 v1.0/v1.1 曾把需求理解为"精确续跑到崩溃点"，进而推导出：需要循环状态快照 + 63 个工具全量幂等改造。

**北京老陈明确纠正：不追精确续跑，只要"断面完整 + 能注入历史继续"。**

两种理解的工程差异：

| 项 | 精确续跑（误读） | 断面续跑（定案） |
|---|---|---|
| 崩溃点的工具 | 需判是否已执行、要不要重放 | **不在断面里 = 当它没发生过** |
| 工具幂等 | 63 个工具全改造 | **不做** |
| 循环状态快照 | 需要 | **不需要**（从 DB 历史重建）|
| 恢复起点 | 崩溃那一条指令 | **上一个完整结束的 LLM 轮次** |
| 代价 | 覆盖全部工具，跨月工程 | 5 个文件，局部改动 |

**定案一句话**：不保证崩溃点后半步不丢，只保证崩溃点之前的完整、之后能从完整处重新开始。

## 三、设计目标与非目标

### 3.1 目标

| 序号 | 目标 | 验证判据 |
|------|------|---------|
| G1 | 崩溃残留任务不再被判`failed`，标记为可续跑 | 续跑成功后 status 回到 `executing` |
| G2 | 残缺数据被清理，DB 保持完整断面 | 无悬空 action（有 action 必有配对 observation）|
| G3 | 续跑从断面注入历史继续执行 | 注入后 `messages` 长度与 DB 步骤数同源 |
| G4 | 暂停态落库，重启后不被误判 | 重启后 status 仍 `paused` |
| G5 | 恢复后 DB 口径正确 | `set_resumed` 写 `executing`（**非** `running`）|

### 3.2 非目标（明确不做）

| 不做 | 理由 |
|------|------|
| 工具幂等改造 | 1.2 已定案：残缺点不当它发生过 |
| 循环状态快照 | 同上，从 DB 历史重建即可 |
| 崩溃点精确续跑 | 同上|
| 重启后自动唤醒暂停任务 | 暂停语义就是"等人点继续"，重启后仍暂停 |
| 改 `event_log` 内存策略 | 第二块范围 |
| 恢复的 工具集 `_loaded_categories` | 见 5.4 已知限制，接受降级 |

### 3.3 G5 口径陷阱（必须显式处理）

内存 `set_resumed()` 写 `task["status"] = "running"`（`task_registry.py:306`）。
DB `chat_tasks.status` 合法值：`executing/paused/completed/failed/cancelled`（`db_initializer.py:136` + 前端 `TaskListPanel.tsx:58` 的 `TASK_STATUS_LABEL`）。

**DB 必须写 `executing`**。写 `running` 前端标签匹配不到，落未知态。这不是 bug（内存 `running` 是运行期内部语义，DB `executing` 是持久化枚举），但**必须显式处理，不可顺手抄内存值**。

## 四、方案设计

### 4.1 数据模型变更

#### 变更一：`chat_tasks` 加 `paused_at`（**建表 DDL + 幂等迁移两处都要**）

v1.1 自查发现的问题：只加 `_ensure_column` 不改 `CREATE TABLE`，会造成"DDL 与实际结构两处漂移"。**两处同步**。

```sql
-- 建表 DDL 内（chat_tasks 定义块内，紧随 status TEXT DEFAULT 'executing' 之后）
paused_at TEXT,     -- 暂停时刻(本地ISO无Z)，NULL=未暂停 — 小欧 2026-10-08
```

```python
# 幂等迁移区（紧随 files_dir 之后）
_ensure_column(conn, "chat_tasks", "paused_at", "TEXT")
```

**为何要这一列而不只看 status**：

| 只看 status | 加 paused_at |
|---|---|
| 无法记录暂停时刻 | 可算暂停时长（契合决策 3"进度信息可见"）|
| 无法区分暂停来源 | 可做暂停超龄治理 |
| — | 语义明确 |

status 与 paused_at 组合语义：

| status | paused_at | 含义 |
|--------|-----------|------|
| `executing` | NULL | 正常运行 / 崩溃遗留待续跑 |
| `paused` | 非 NULL | 用户主动暂停 |
| `paused` | NULL | 异常态（不应出现，`reconcile` 补齐）|
| 终态 | NULL | 已完成/失败/取消 |

#### 变更二：新增 `resumable` 语义（不新增列，用 status 值区分）

**不新增 `resumable` 列** —— 用 `status='executing'` + `start_time < boot_iso` 双重条件识别崩溃遗留，这正是 `reconcile_orphaned_tasks` 现有的判据。

好处：零新增列，无迁移负担，且与既有 `boot_iso` 归属判据同源（防误起第二实例时误伤对方任务）。

### 4.2 改动一：残缺数据清理

#### 4.2.1 残缺的精确定义

因 `chat_task_steps` 是"一事件一行"，残缺形态**唯一**：

> 存在 `type='action'` 的行，其 `tools[]` 中某元素的配对键**在后续行里找不到对应 `type='observation'` 的 `tool_result[]` 中同一 `_tool_call_id`**。

崩溃窗口：`react_step` 执行工具 → 崩在 `_publish(observation)` 之前。action 已落库，observation 未落。

#### 4.2.2 清理范围

**只删悬空 action 及其之后的行**，不删之前的完整历史。

理由：断面定义是"上一次完整结束的 LLM 轮次"。悬空 action 之后的任何行（含 observation/chunk）都属于崩溃点之后的未完成部分，语义上不可信。

#### 4.2.3 实现要点

伪代码（落在 `storage.py` 新函数）：

```
def cleanup_incomplete_tail(conn, task_id) -> int:
    rows = SELECT step_index, step_json FROM chat_task_steps
           WHERE task_id=? ORDER BY step_index ASC
    # 收集已闭合的 tool_call_id 集合
    closed = { tr["_tool_call_id"] for row in rows
               if row.type=="observation" for tr in row.tool_result
               if tr.get("_tool_call_id") }
    # 从尾部回扫, 找第一处悬空 action
    cut_idx = None
    for i in reversed(range(len(rows))):
        r = rows[i]
        if r.type == "action":
            ids = {t.get("_tool_call_id") for t in r.tools}
            missing = ids - closed - {None, ""}
            if missing: cut_idx = i; break
    if cut_idx is None: return 0     # 无残缺
    DELETE FROM chat_task_steps WHERE task_id=? AND step_index >= rows[cut_idx].step_index
    return 被删行数
```

**兜底**：若 `_tool_call_id` 缺失（`observation_builder.py:42` 允许空串），则退化用"action 后紧邻的 observation 的 `tool_result` 数量 >= action 的 `tools` 数量"作次级判据。两者都不满足则视为残缺（宁可删，不可留）。

**铁律**：删之前必须 `logger.info` 记录删了什么（task_id、step_index、悬空的 tool_call_id、删了几行），否则事后无法追责。

#### 4.2.4 与现成 `journal_steps_reconcile` 的分工

`journal_steps_reconcile()`（`stream_event_journal.py:123`）是**计数级**对账（Journal 帧数 vs steps 行数），只告警。

本方案是**内容级**修复（配对检查 + 删除）。两者**不冲突，职责不同**：
- `reconcile` 回答"有没有缺帧"（观测）
- `cleanup_incomplete_tail` 回答"哪个 action 没闭合，删哪几行"（修复）

**不建议合并**，理由：观测与修复分离，修复逻辑要更严格（宁可删不可留），与只告警的观测器混在一起会让告警语义变浑浊。

### 4.3 改动二：`reconcile_orphaned_tasks` 改为不判死

**位置**：`storage.py:426`

现行为：把崩溃遗留 `executing` 全改 `failed`。

改为：**先不改状态**，交给续跑流程处理。续跑成功则 status 自然仍是 `executing`；续跑失败再改 `failed`。

```
启动期流程（main.py startup_event 内）:
  1. 扫崩溃遗留任务: status='executing' AND start_time < boot_iso
  2. 对每个任务:
     a. cleanup_incomplete_tail(task_id)      # 清理残缺
     b. 尝试续跑（见 4.4）
     c. 续跑失败 → update_task(status='failed', error_type='task_resume_failed')
  3. logger.info 汇总: 续跑 N 个 / 失败 M 个 / 清理残缺 K 行
```

**`reconcile_orphaned_tasks` 函数保留但不再用于判死**，改用于"列出崩溃遗留任务"（返回 task_id 列表供续跑流程消费）。这样：
- 保留 `boot_iso` 归属判据（防误伤第二实例）
- 保留原函数测试（若已有）
- 判死职责收口到续跑失败分支

**暂停态天然不受影响**：DB 里 `status='paused'`，不在 `status='executing'` 条件内，无需任何特判。

### 4.4 改动三：续跑执行

#### 4.4.1 恢复流程

```
async def resume_orphaned_task(task_id, session_id) -> bool:
    # 1. 读任务行: sessionModel / max_steps / llm_call_count / user_input
    row = SELECT session_id, sessionModel, max_steps, llm_call_count, user_input
           FROM chat_tasks WHERE task_id=?

    # 2. 清理残缺(已在 4.2 完成，此处假设已清理)

    # 3. 读干净断面
    steps = load_execution_steps(conn, ai_message_id, task_id)   # 现有函数, storage.py:322

    # 4. 建 agent(与 run_agent_in_background 同源)
    agent = UniversalAgent(llm_client=..., task_id=task_id, max_steps=row.max_steps)

    # 5. 注入历史  ← 核心
    agent.message_builder.inject_history(build_history_from_steps(steps))

    # 6. 回填轮次(react_step.py:318 每轮自增, 续跑要从 DB 值接着数)
    agent.llm_call_count = row.llm_call_count

    # 7. 继续循环
    await agent.run_react_cycle(agent, task=row.user_input, task_id=task_id, ...)
```

#### 4.4.2 `build_history_from_steps` 的职责（新增，最关键的一环）

把 `chat_task_steps` 的 step_dict 序列转回 LLM messages 结构。这是**新的转换逻辑**，现有 `start_step.py:100-101` 只处理已成形 messages，不处理 step_dict。

| step type | 转成 |
|---|---|
| `thought` | 跳过（推理内容，不是 messages）|
| `action` | `{"role":"assistant", "tool_calls":[...]}` |
| `observation` | `{"role":"tool", "tool_call_id":..., "content":...}` |
| `chunk` | 跳过（实时信号，不落库）|
| `final` | 循环已结束，不需要重建 |
| `error` | 视情况转 assistant 说明 |

**约束**：产出必须满足 `MessageBuilder._trim_fc_pairs`（`message_builder.py:521`）的配对要求 —— 每个 `assistant.tool_calls[].id` 必有对应 `role=tool`，否则**发给 LLM 直接 400**。

**这正是 4.2 清理残缺的必要性所在**：悬空 action 会产出无配对的 tool_calls → 400。

#### 4.4.3 启动期的并发安全

续跑是**后台协程**，而 `startup_event` 是启动流程。必须避免：
- 续跑协程阻塞启动（不能 `await` 完整循环）
- 多个实例重复续跑同一任务

**方案**：`startup_event` 只 `create_task` 起协程，不 await 循环体。续跑失败只记日志，不影响服务可用性。

**单实例保障**：沿用 `reconcile_orphaned_tasks` 的 `boot_iso` 判据（`start_time < boot_iso`），本进程启动前创建的任务才归我处理。若将来多实例，需加 `owner_pid/boot_id` 列（现有注释已预判此风险：`storage.py:430-431`）。

### 4.5 改动四：暂停态持久化

```python
        # fail-closed: DB 没写成就不算暂停成功, 回滚内存态
        ... 回滚 paused=False, pause_event.set()
        return api_failure(message="暂停失败: 状态未持久化, 请重试")
    return api_success(message=f"任务 {task_id} 已暂停")
```

**两个工程决策（v1.1 遗漏，v1.2 补）**：

**决策一：落库放锁外。** 现有 `set_cancelled` 等全程持 `running_tasks_lock`。若 DB 写在锁内，pause 的 DB 延迟会阻塞所有任务的状态读。锁只保护内存字典（微秒级），DB 写独立进行。

**决策二：fail-closed（落库失败则 pause 失败）。**

| 选项 | 后果 |
|---|---|
| **fail-closed**（采纳）| 落库失败 → 回滚内存态 → 前端报错 → 用户重试。**状态谎报的风险归零** |
| fail-open | 内存暂停成功但 DB 无 → 重启后变 failed → 用户以为暂停了，其实没暂停 |

**理由**：暂停是用户主动的状态变更，**谎报成功比失败更糟** —— 用户以为暂停了就去干别的，重启后任务继续跑或被判死，代价远大于"暂停失败请重试"。

#### 4.5.2 `set_resumed` 清痕迹

```python
    async with running_tasks_lock:
        ...  # 现有逻辑不变
        task["paused"] = False
        task["status"] = "running"        # 内存口径, 保留
        pause_event.set()
    ok = await _clear_pause(task_id)      # DB: status='executing', paused_at=NULL
    if not ok:  return api_failure(...)   # 同 fail-closed
    return api_success(...)
```

**必须写 `executing` 不是 `running`**（3.3 已述）。

#### 4.5.3 落库实现约束

- **必须走 `db.atxn` offload 出事件循环**。依据 `agent_runner.py:860`既有做法与注释：「落库 offload 出事件循环(后端卡死修复 小欧 2026-08-24)」。`chat_routes.py` 的 pause 端点在事件循环内，直接 `conn.execute` 会复发那次后端卡死。
- **不用 shield**。pause/resume 是用户主动的轻量操作，不是终态关键写。进程此刻被 kill 的后果是"重启后判 failed"，由 `reconcile` 兜底，可接受。不引入 shield 复杂度（YAGNI）。

#### 4.5.4 `update_task` 扩参（v1.1 未拍死的决策，现拍死）

**决策：扩 `update_task()` 加 `paused_at=None`。**

理由：`update_task` 已是 `chat_tasks` 的唯一 UPDATE 入口（外部调用仅 `agent_runner.py:770`、`stream_orchestrator.py:608` 两处）。另写专用 UPDATE 会制造第二处写入口，违反 DRY。

缺省 `None` 不覆盖，**零行为变化**，两处既有调用不受影响。

### 4.6 改动五：启动期编排

`main.py` 的 `startup_event`（L280起）调整顺序：

```
现状:
  db.init()
  reconcile_orphaned_tasks()   # 判死
  ensure_tools_registered()
  ...

改为:
  db.init()
  orphaned = list_orphaned_tasks(boot_iso)      # 列出, 不改状态
  for t in orphaned:  create_task(resume_orphaned_task(t))   # 不 await, 后台跑
  ensure_tools_registered()                    # 工具必须先注册! 续跑要用
  ...
```

**顺序铁律**：`ensure_tools_registered()` **必须在续跑协程真正开始建 agent 之前完成**。续跑要建 `UniversalAgent`，它 `__init__` 里就 `ToolLoader.init_tools()` 拿工具（`universal_agent.py:70-71`）。

用 `create_task` 不 await，天然保证注册先完成（协程在当前同步代码段之后才被调度）。**这一点必须在代码注释里写明**，否则后人调换顺序会导致续跑拿到空工具集。

### 5.3 落库顺序的额外发现（对残缺判定的影响）

`agent_runner.py:181` 编辑历史：

> `_enqueue_step` 只入队即返回, 进程被杀则队列内帧全丢(实测 task_interrupted 样本...)

**残缺不只是"action 无 observation"，还有"队列里没消费完的帧"。** 这意味着：

- 残缺可能**同时**丢掉 action 和 observation（两者都在队列里没消费）
- 也可能只丢 observation（action 已消费，observation 还在队列里）

`cleanup_incomplete_tail` 的判据**对两种情况都成立**（都是"最后闭合对不完整"），无需额外处理。

但要补一条：**清理后必须确认尾部不是恰好停在 observation 上**（即 observation 有但它的 action 被清了）。回扫时若发现 observation 的 `_tool_call_id` 无对应 action，**该 observation 也要删** —— 它是孤儿，发给 LLM 会 400。
