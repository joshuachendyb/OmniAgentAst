## 一、现状与要解决的问题

### 1.1 现状（当前实际行为，均经代码实证）

#### 1.1.1 任务与会话的结构（已落地，符合设计）

系统已有任务实体，不是"一条命令=一个进程"。DB 结构：

| 表 | 作用 | 关键列 |
|---|---|---|
| `chat_sessions` | 会话容器 | `id`(PK)、`title`、`message_count` |
| `chat_tasks` | **任务实体** | `task_id`(UNIQUE)、`session_id`(FK→chat_sessions)、`status`、`llm_call_count`、`sessionModel`、`max_steps` |
| `chat_task_steps` | 任务步骤流水 | **一事件一行**（`ON CONFLICT(ai_message_id, task_id, step_index) DO NOTHING`）|
| `token_usage` | token 四维明细 | `session_id` + `task_id` |
| `chat_stream_events` | SSE 事件持久流 | `PRIMARY KEY (task_id, seq)` |

**任务从属会话已实现**：`chat_tasks.session_id TEXT NOT NULL` + 外键到 `chat_sessions`，级联删除。这条不可变，无需改动。

#### 1.1.2 任务状态机（内存 + DB 双轨）

`status` 合法枚举：`executing` / `paused` / `completed` / `failed` / `cancelled`（`db_initializer.py:136` + 前端 `TaskListPanel.tsx:58`）。

运行时另有内存表 `running_tasks: dict[str, dict]`（`task_state.py:40`）承载活跃任务的控制态（cancelled / paused / `_pause_event` / `_inbox`）。

**两者不一致时，DB 是展示权威，内存是运行权威。** 这个双轨是后面所有问题的根源。

#### 1.1.3 任务列表（已可用，读 DB）

`GET /sessions/{id}/tasks`（`api/v1/sessions.py:85`）→ `list_session_tasks(conn, session_id)`，**读 DB 不读内存**。所以任何落库的状态变更前端自动可见，无需改接口。

#### 1.1.4 断线重连与事件回放（已可用）

| 机制 | 状态 |
|---|---|
| SSE 断线重连 `after_seq=N` | 已实现，事件按 `seq` 续传 |
| Journal 持久化 `chat_stream_events` | 已实现，`(task_id, seq)` 主键幂等 |
| 双路对账 `journal_steps_reconcile()` | **已存在，但只 `logger.error` 告警，不做任何修复** |

**关键：`done` 信号由生产者（`agent_runner.py:891` finally）置位，与 SSE 消费者无关。** 消费者仅 `if buffer.done.is_set(): return`（`stream_orchestrator.py:757`）。这意味着"用户切走但任务继续跑"在架构上**已成立**（9-12 修竞态时的副产品）。

#### 1.1.5 暂停（纯内存，进程退出即丢）

`set_paused()`（`task_registry.py:279-292`）**全文零 DB 操作**：

```python
async def set_paused(task_id: str) -> dict:
    async with running_tasks_lock:
        task = running_tasks.get(task_id)
        ...
        task["paused"] = True
        task["status"] = "paused"
        pause_event = task.get("_pause_event")
        if pause_event:
            pause_event.clear()
        return api_success(message=f"任务 {task_id} 已暂停")
```

暂停态只写内存 dict。

#### 1.1.6 重启行为（直接判死）

`storage.py:426` 的 `reconcile_orphaned_tasks()` 在启动时调用（`main.py:290`），把崩溃遗留的 `executing` 行改终态：

```sql
UPDATE chat_tasks
   SET status = 'failed',
       error_type = 'task_interrupted',
       error_message = '服务重启导致任务中断，后端不支持续算，请重新发起',
       end_time = ?, updated_at = ?
 WHERE status = 'executing'
   AND (start_time IS NULL OR start_time < ?)
```

**系统自己写的提示语就是"后端不支持续算，请重新发起"。**

### 1.2 要解决的问题（五个，均可复现）

#### P1 暂停中的任务重启后变成"失败"（缺陷，且必然发生）

**成因链**：
1. `set_paused()` 只写内存，DB 侧 `status` 仍是 `executing`（1.1.5）
2. 进程退出 → 内存 `running_tasks` 全丢
3. 重启 → `reconcile_orphaned_tasks` 命中 `status='executing'` → 改 `failed`

**后果**：用户暂停一个长任务，关掉程序，第二天回来看到"失败"，无法继续。

**复现**：起任务 → pause → kill 进程 → 重启 → 任务列表显示"失败"。

#### P2 崩溃后无法继续执行（能力缺失）

**现状**：重启即判死（1.1.6），无任何续跑入口。

**已有但未利用的能力**：
- `MessageBuilder.inject_history()`（`message_builder.py:219`）—— 注入历史对话的现成入口
- `chat_task_steps` —— 每轮 assistant tool_call 与 observation 都落了库

**即：数据齐备，缺的是"清理残缺 + 重建 + 续跑"这条链路。**

#### P3 残缺数据会污染续跑（隐藏的坑）

`_enqueue_step` 只入队即返回（`agent_runner.py:181` 编辑历史：「进程被杀则队列内帧全丢」）。所以崩溃时 `chat_task_steps` 可能处于三种残缺形态：

| 形态 | 场景 | 危害 |
|---|---|---|
| ① 悬空 action | action 已落库，observation 还在队列里没消费 | 注入历史后产出无配对的 `tool_calls` → **发 LLM 直接 400** |
| ② action+observation 都丢 | 两者都在队列里没消费 | 断面少最后一轮（可接受）|
| ③ 孤儿 observation | action 被丢，observation 已落库 | 孤儿 `role=tool` 无对应 assistant → **同样 400** |

**既有证据表明这个坑是已知的**：`message_builder.py:551` 有专门剔除孤儿的逻辑，注释写明「丢弃 tool_call_id 为空/无配对 assistant 的孤儿 tool 消息(否则发给 LLM 触发 400)」。

**结论**：残缺必须先清理再重建，否则续跑第一步就 400。

#### P4 残缺当前无任何检测

`journal_steps_reconcile()`（`stream_event_journal.py:123`）**已存在**但只做**计数级**对账（Journal 帧数 vs steps 行数）且**只告警**。

它答的是"有没有缺帧"，答不了"哪个 action 没闭合、该删哪几行"。内容级修复能力是空的。

#### P5 落库失败的半成功态（隐患，尚未暴露）

`set_paused` / `set_resumed` 若将来加落库，落库失败时会出现：
- 内存已置 `paused` / 已恢复
- DB 无记录
- 用户看到"操作成功"

**谎报成功比失败更糟**：用户以为暂停了就去干别的，重启后任务却变 failed。

**当前因不落库而未暴露，但本设计要引入落库，必须同时解决。**

| 序号 | 目标 | 对应问题 | 验证判据 |
|------|------|---------|---------|

### 1.5 关键澄清：不追精确续跑（避免走偏）

小欧 v1.0/v1.1 曾把需求理解为"精确续跑到崩溃点"，进而推导出需要循环状态快照 + 63 个工具全量幂等改造。

**北京老陈明确纠正**：只要"断面完整 + 能注入历史继续"。

| 项 | 精确续跑（误读）| 断面续跑（定案）|
|---|---|---|
| 崩溃点的工具 | 判是否已执行、要不要重放 | **不在断面 = 当没发生过** |
| 工具幂等 | 63 个工具全改造 | **不做** |
| 循环状态快照 | 需要 | **不需要**（从 DB 历史重建）|
| 恢复起点 | 崩溃那一条指令 | **上一个完整结束的 LLM 轮次** |
| 代价 | 覆盖全部工具，跨月工程 | 5 个文件，局部改动 |

**一句话定案**：不保证崩溃点后半步不丢，只保证崩溃点之前的完整、之后能从完整处重新开始。

**推论**：P3 的三种残缺形态里，形态①③必须清理（会产生 400），形态②是"少一轮"，属可接受损失。

`storage.py:append_execution_step` 的 INSERT：


### 3.1 S1（P1）：暂停状态要写进数据库

**问题是什么**

暂停只改了内存里的 `running_tasks`，数据库里的 `status` 还是 `executing`。程序一关，内存全没了，数据库里留着一个"正在执行"的假状态。重启时收尾程序看到"正在执行"，就当成崩溃遗留改成了"失败"。

**策略**

给 `chat_tasks` 表加一列 `paused_at`（暂停时刻）。暂停时写入 `status='paused'` + `paused_at=当前时间`，恢复时写回 `status='executing'` + `paused_at=NULL`。

**会踩的坑：内存和数据库各存一份状态，值还不一样**

暂停/恢复这套逻辑，内存和数据库两边都要改。而两边的合法值**不一样**：

| 位置 | 恢复后写什么 | 为什么 |
|---|---|---|
| 内存 `running_tasks` | `running` | 运行期内部语义，现有代码就是这么写的 |
| 数据库 `chat_tasks` | `executing` | 数据库枚举只有 `executing/paused/completed/failed/cancelled` |

数据库**没有 `running` 这个值**。

如果实现时顺手把内存的值抄进数据库，写进去 `running`，前端找不到对应标签（前端 `TaskListPanel.tsx:58` 的 `TASK_STATUS_LABEL` 里只有 `executing`），任务状态显示成空白或"未知"。

**应对方法**

1. 数据库侧**写死 `executing`**，不抄内存值
2. 单测断言：调完恢复，查询数据库，`status` 必须等于 `'executing'`
3. 代码注释写在两处值旁边，说明"内存 running / 数据库 executing，值不同不是 bug"

**另一个坑：写库不能放在锁里**

现有的 `set_paused` 全程拿着 `running_tasks_lock` 这把锁。如果写数据库也在锁里，一次写库的延迟（几毫秒到几十毫秒）会把**所有**其他任务的状态读写全部堵住。

**应对方法**：锁只用来改内存（微秒级），写库放到锁外面做。这个改动写在 §5.6.2 的 diff 里。

---

### 3.2 S2（P2 P4）：重启不判死，改成续跑

**问题是什么**

现在重启时，`reconcile_orphaned_tasks` 一律把崩溃遗留的任务改成 `failed`，提示语是"后端不支持续算，请重新发起"。这是个**主动放弃**的决策。

但数据其实是够的：每轮对话的助手消息和工具结果都存在 `chat_task_steps` 表里，只是没人去读、没人重建循环。

**策略**

把"判死"改成三步：

```
第一步：从数据库列出崩溃遗留的任务（不改任何数据）
第二步：清理这些任务的残缺数据（见 S3）
第三步：逐个尝试续跑 —— 建一个新的 Agent，把历史注入进去，继续跑
     续跑成功 → 状态自然还是 executing
     续跑失败 → 这时才改成 failed，错误类型记 task_resume_failed
```

**会踩的坑一：单测会失败**

`reconcile_orphaned_tasks` 现在有 3 个既有单测（`tests/test_p3_journal_guard.py` 的 L22/L213/L380），其中 L380 断言：

```python
assert got == "failed", f"BUG: 带 Z 的 start_time 字符串比较不可靠，残行未收尾（status={got}）"
```

改成"不判死"后，这个断言必然失败。

**应对方法**：给函数加一个参数 `mark_failed`，缺省 `True`（保持原来的判死行为）。续跑流程显式传 `mark_failed=False`。

- 既有 3 个单测**一行都不用改**
- 语义也清楚：谁调用、要什么结果，看参数就知道
- 这不是"新旧两套逻辑并存"，是同一个逻辑的两种配置

**会踩的坑二：暂停中的任务会被误捞起来续跑**

数据库里 `paused` 的任务，重启时会不会被当成"崩溃遗留"捞去续跑？

**不会，但必须确认这一点**。捞取条件是 `status='executing'`，而暂停的任务在数据库里是 `paused`，天然不满足。**不需要写任何特判代码**。

这一点是 S1 加了 `paused_at` 之后自然得到的：暂停时状态落了库，重启收尾的条件就自动把它排除了。

**会踩的坑三：续跑协程抢在工具注册前面跑**

续跑要建 `UniversalAgent`，而这个类的构造函数里就会去拿工具（`universal_agent.py:70-71` 调 `ToolLoader.init_tools()`）。

启动流程里，工具注册 `ensure_tools_registered()` 和续跑协程启动，谁先谁后？

如果续跑先跑，拿到的是**空工具集**，整个续跑过程一次工具都调不了。

**应对方法**：
- 续跑协程写在 `ensure_tools_registered()` **之后**
- 用 `asyncio.create_task` 起协程，**不 `await`** —— 这样续跑真正开始执行时，一定已经过了注册那行代码
- 代码注释写死"顺序禁调换"

---

### 3.3 S3（P3）：先清残缺，再重建

**问题是什么**

崩溃时数据库里可能留下"半个步骤"。具体有三种形态：

| 形态 | 什么情况 | 危害 |
|---|---|---|
| ① 只有动作、没结果 | 动作已写库，工具结果还在内存队列里没写 | **严重** |
| ② 动作和结果都没写 | 两者都在队列里没写 | 少最后一轮，可接受 |
| ③ 只有结果、没有动作 | 动作被丢，结果写进去了 | **严重** |

"动作"是 AI 说"我要调用某个工具"，"结果"是这个工具跑完的返回值。正常的步骤一定是成对的：一个动作后面跟着一个结果。

形态①和③为什么严重？

因为注入历史时，"动作"会变成给大模型的消息里的工具调用声明，"结果"会变成对应的返回值。**大模型的协议要求：每个工具调用声明必须有对应的返回值**（`message_builder.py:521` 的 `_trim_fc_pairs` 就是干这个校验的）。

- 形态①：有调用声明没返回值 → **发请求直接报 400**
- 形态③：有返回值没调用声明 → **同样 400**

代码里早就知道这个坑。`message_builder.py:551` 有专门剔除孤儿的逻辑，注释明写：

> 丢弃 tool_call_id 为空/无配对 assistant 的孤儿 tool 消息(否则发给 LLM 触发 400)

**策略**

在读取断面数据**之前**，先扫一遍，把没配对上的步骤行删掉（连同它后面的所有行），让数据库回到"上一次完整结束"的状态。

**怎么判断配对**

靠一个字段：`_tool_call_id`。每个工具调用都有唯一 ID，写在动作里、也写在结果里，靠它配对（代码位置 `observation_builder.py:42`）。

**会踩的坑：判断条件不能写死一条**

判断"残缺"不能只看一种情况，要覆盖三种：

1. 动作有 ID，但结果里找不到这个 ID → 删
2. 结果有 ID，但动作里找不到这个 ID → 也要删（形态③）
3. 动作没有 ID（空值）→ 无法配对，看它后面紧不跟着结果，不跟就删

只写第1 条会漏掉形态③，那续跑照样 400。

**应对方法**：三条全写，且**判定为残缺时一律删**（宁可删不可留）。删除前必须 `logger.info` 记录删了哪个任务、从哪一行开始、删了几行 —— 不记日志的话事后无法追责。

**另一个坑：顺序不能反**

清理必须在读断面**之前**。顺序反了就是拿着带残缺的断面去重建，一定会产出坏数据。

---

### 3.4 S4（P2）：用断面重建历史，注入后接着跑

**问题是什么**

崩溃时，ReAct 循环的运行状态（Agent 对象、消息列表、轮次计数器）全在内存里，随进程一起没了。需要重新造出来。

**策略**

不用精确恢复崩溃那一刻，只做一件事：**从数据库里已存的步骤，重新生成对话历史，注入进一个新的 Agent，然后从上次停的轮次继续**。

需要的四样东西，都能从数据库拿：

| 需要什么 | 从哪来 |
|---|---|
| 任务绑定的模型 | `chat_tasks.sessionModel`（这列是 NOT NULL 的，一定有）|
| 轮次计数器 | `chat_tasks.llm_call_count` |
| 最大步数上限 | `chat_tasks.max_steps` |
| 对话历史 | `chat_task_steps` 的步骤行，转成消息格式 |

注入历史这个动作，系统里**本来就有**（`MessageBuilder.inject_history()`），不是新造的。

**会踩的坑一：重建出的消息必须成对**

同上 S3 —— 生成的每条"工具调用声明"必须有对应的"返回值"，否则 400。这是 S3 必须先做的根本原因。

**会踩的坑二：用错模型**

数据库里有每个任务绑定的模型。续跑**必须用任务自己的模型**，不能用全局当前选中的模型。

为什么：用户在任务 A 运行期间把全局模型切成了 B，重启后续跑任务 A，如果用全局模型，任务 A 会用 B 继续跑 —— 行为不一致。

代码里已有同类问题的修复先例（2026-09-20 修"取消作用在错误对象上"，改成优先用 Agent 自己的模型快照）。同一个道理。

**会踩的坑三：建模型客户端会卡事件循环**

创建 LLM 客户端包含读配置、建连接等同步操作。如果直接 `await` 一个同步函数，会把事件循环卡住。

**应对方法**：用 `asyncio.to_thread` 丢到子线程做。

**关于"恢复不了的东西"**：工具加载状态、沙箱目录、排队等着的插话消息，这些都没恢复。这是**明确的取舍，不是遗漏** —— 工具集由 `UniversalAgent` 构造函数重建成初始集（文件类 + 基础类），其余靠 AI 搜索工具动态加载；沙箱目录本来就是崩了之后状态不确定，重建是对的。详见 §5.6。

---

### 3.5 S5（P5）：写库失败就说失败，别谎报成功

**问题是什么**

现在暂停不写库，所以这个问题还没暴露。但 S1 加了写库之后就会遇到：

如果写库失败，但函数返回"成功"，用户看到的是"已暂停"，实际数据库里什么都没记。用户以为暂停了就去干别的，重启后任务变成"失败"。

**策略**

**写库失败 → 判定暂停失败 → 把内存里刚才改的状态回滚 → 返回失败提示 → 让用户重试。**

**会踩的坑：回滚时也要拿锁**

改内存是加锁的，回滚内存也得加锁。如果回滚时忘了拿锁，可能把别的操作刚写进去的值覆盖掉。

**应对方法**：回滚逻辑和改内存一样，都要 `async with running_tasks_lock`。写成 §5.6.2 diff 里的样子。

**为什么选"失败就报错"而不是"失败也报告成功"**：因为谎报成功的后果（用户以为暂停了，实际没暂停，重启后任务乱跑）比"暂停失败请重试"严重得多。

---

### 3.6 S6（P1 P2）：建表语句和补列迁移要同时改

**问题是什么**

加数据库列有两种做法：

1. 写在建表语句里（新数据库用这条）
2. 写一段"如果没这列就加上"的迁移（旧数据库用这条）

如果只做了第 2 种，建表语句里就没有这一列。以后有人看建表语句，会以为这个字段不存在。

**策略**

两处同时改。

**会踩的坑：以为只改一处就够了**

只改迁移不改建表，功能上其实是能跑的（新库建成后再被迁移补上这列）。但这属于"两处结构定义不一致"，后面维护的人很容易被误导。

**应对方法**：§5.2 给的是两处的 diff，缺一不做。

## 四、三堂会审复核结论（2026-10-08 20:04:16）

> 北京老陈要求："对前 3 章熟读 10 遍，三思三省，从系统全局高度分析修改策略是不是最佳合理逻辑，不能违反代码 10 大规范"。
> 本章是**策略层 + 代码规范层**的复核结论：6 个问题（2 致命）。第五章的 diff 据此全部重写。

### 4.1 策略层结论：方向正确，但 W3/W5 技术路径整体错误

S1~S6 的问题分析与应对方向**经复核全部成立**（含北京老陈纠正的"断面续跑"取舍）。**策略层无需推翻。**

**但 v1.5 的技术路径建立在两个未经核实的假设上，两个都错**：

| 假设 | 实际情况 | 后果 |
|---|---|---|
| 续跑 = "新建 Agent 调 `run_react_cycle`" | `run_react_cycle` **不能单独调**，必须走 `run_agent_in_background` | **F1 致命** |
| `create_service_instance(provider=, model=)` | 真实签名 `(provider_config: dict, model_ref: ModelRef)` | **F6 必错** |

**认知偏差根源**：把"续跑"当成"再造一个循环"。实际是**复用与正常任务完全相同的启动链路**，只是入口前多一步历史注入。这导致 v1.5 的 W3/W5 全部偏离。

### 4.2 F1（致命）：v1.5 的续跑代码必定崩溃

#### 硬证据

`react_loop.py:run_react_cycle` 开头逐字：

```python
_buf = get_stream_buffer(task_id or getattr(agent, "task_id", ""))
if _buf is None:
    raise RuntimeError(f"[react_loop] StreamBuffer缺失(task={task_id or getattr(agent, 'task_id', '')})")
```

**无 StreamBuffer 直接抛异常。** v1.5 的 `resume_orphaned_task` 从未创建 buffer。

#### 除 buffer 外还缺 4 项前置

`run_react_cycle` 运行依赖由 `agent_runner` / `stream_orchestrator` 预置：

| # | 依赖 | 装配者 | 不装的后果 | 有守卫? |
|---|---|---|---|---|
| 1 | StreamBuffer（+ Journal sink + persist_sink + flush_sink）| `agent_runner.py:301` | **抛 RuntimeError** | 无，**必崩** |
| 2 | `_step_queue` 消费者 + `_flush_steps()` + `done.set()` | `agent_runner` 内建 | 循环永不置 done，落库不收尾 | 无 |
| 3 | `agent._start_meta` | `stream_orchestrator` | token 基线分支跳过 | 有 `getattr` 守卫 |
| 4 | `agent.file_persist` | `stream_orchestrator:670` | 落盘文件 A/B 缺失 | 有 `getattr` 守卫 |

v1.5 的 W3/W5 全漏这 4 项。

#### 定案：走 `run_agent_in_background`

唯一调用方是 `stream_orchestrator:682`，且前面有必须照做的装配（`:660-684`）：

```python
agent.file_persist = create_task_writer(
    session_id=session_id, task_id=task_id, ai_message_id=_ai_message_id,
    start_time_iso=get_local_iso_timestamp(),
    model=(_mr.model_dump(exclude_none=True) if hasattr(_mr, "model_dump") else None),
)
bg_task = asyncio.create_task(run_agent_in_background(
    agent, task_id, user_input, None, session_id, state, _task_start_time,
    db_ops=_db_ops, ai_message_id=_ai_message_id))
_agent_tasks.add(bg_task)
bg_task.add_done_callback(_agent_tasks.discard)
```

**关键**：`run_agent_in_background` 内部（`agent_runner.py:301-304`）**自带 buffer 缺省创建**，注释明写"确保既有直连入口（跳过 stream_orchestrator）亦可创建"—— **这条路是系统本来就留好的**，续跑走它才是设计意图。

#### 违反的规范

| 规范 | 违反说明 |
|---|---|
| **KISS-DIRECT** | 绕过 `run_agent_in_background` 封装直接调内层，本该一 call 到位的事手搓一遍必然缺件 |

### 4.3 F2（致命）：`mark_failed` 参数违反「禁止 backward」

v1.5 为保 3 个既有单测，加 `mark_failed=True` 缺省保留旧判死行为。

**项目铁规原文**：禁止 backward —— 所有代码修改坚决杜绝向后兼容做法，新旧混杂、代码混乱。

`mark_failed=True` 分支就是新旧混杂。续跑落地后判死那条路是"主动放弃"的旧决策，必须消亡。**保住单测不是保留旧行为的理由。**

且 `mark_failed: bool -> Union[int, List[...]]` 返回类型随参数变，是坏味道：调用方须先知道传了什么才能判断返回什么。

#### 定案：判死逻辑整体删除，改单一职责

```python
def list_orphaned_tasks(conn: Connection, boot_iso: str) -> List[Tuple[str, str]]:
    """列出崩溃遗留任务(不修改任何数据) — 小欧 2026-10-08
    旧 reconcile_orphaned_tasks 的判死逻辑整体消亡(禁止 backward):
      新设计只有"列出并续跑"一条路, 续跑失败由 task_resume 侧标 failed
      (错误类型 task_resume_failed, 与旧的 task_interrupted 区分)。"""
    rows = conn.execute(
        """SELECT task_id, session_id FROM chat_tasks
           WHERE status = 'executing'
             AND (start_time IS NULL OR start_time < ?)""",
        (boot_iso,),
    ).fetchall()
    return [(r["task_id"], r["session_id"]) for r in rows]
```

**单一职责、单一返回类型、零分支。**

#### 既有单测处理

`tests/test_p3_journal_guard.py` 3 处：L22 改 import；L213 逐个核，凡断言"判死"的改为断言"能列出"；L380 `assert got == "failed"` 改为断言返回列表含该 task_id。

**这 3 个单测原本在测"能发现崩溃残留行"这个能力** —— 能力没变，只是断言形态从"变成什么状态"改成"能不能列出来"。改断言是让它跟上设计，不是破坏单测。

### 4.6 F5（KISS-DIRECT）：残缺判定过重

```python
"""

Date: 2026-10-08

  3. 依赖方向清晰: 与 task_resume.py 同层, 续跑时一起 import, 不让 storage 继续膨胀。

# 2026-10-08 小欧 - 新建([18] v2.0 §5.4): find_unclosed_index(单一配对判定, F5 抽出)
#   + cleanup_incomplete_tail(调用判定 + DELETE + 留痕)。— 小欧-2026-10-08

from typing import Any, Dict, List, Optional, Tuple

from app.logger import logger
from app.utils.json_utils import parse_json


def find_unclosed_index(rows: List[Tuple[Any, Dict[str, Any]]]) -> Optional[int]:
    """找第一处未闭合点的行下标；全闭合返回 None — 小欧 2026-10-08

    【入参】rows = [(step_index, step_dict), ...]，按 step_index 升序
    【出参】未闭合点的行下标；无则 None

    【判定依据】action.tools[]._tool_call_id ↔ observation.tool_result[]._tool_call_id 必须成对
      (配对键来源: observation_builder.py:42  `_tid = _call.get("_tool_call_id", "")`)

    【三种残缺形态全覆盖 · 漏任何一条续跑就 400 · 见详设 §3.3】
      ① 悬空 action: action 有 id 但全库 observation 无此 id
      ② 孤儿 observation: observation 有 id 但全库 action 无此 id
      ③ 无 id 的 action: id 为空，且其后紧邻的不是 observation

    【为什么尾部回扫】崩溃只发生在尾部，完整前缀绝不该被删。
      从尾部回扫第一个不闭合点即 cut，之前的完整历史一律保留。
    """
    called_ids: set = set()
    observed_ids: set = set()
    for _, d in rows:
        t = d.get("type")
        if t == "action":
            for c in (d.get("tools") or []):
                if c.get("_tool_call_id"):
                    called_ids.add(c["_tool_call_id"])
        elif t == "observation":
            for tr in (d.get("tool_result") or []):
                if tr.get("_tool_call_id"):
                    observed_ids.add(tr["_tool_call_id"])

    for i in range(len(rows) - 1, -1, -1):
        d = rows[i][1]
        t = d.get("type")
        if t == "action":
            ids = {c.get("_tool_call_id") for c in (d.get("tools") or [])}
            ids.discard(None); ids.discard("")
            if ids - observed_ids:                       # ① 悬空 action
                return i
            if not ids:                                   # ③ 无 id 的 action
                nxt = rows[i + 1][1] if i + 1 < len(rows) else None
                if nxt is None or nxt.get("type") != "observation":
                    return i
        elif t == "observation":
            ids = {tr.get("_tool_call_id") for tr in (d.get("tool_result") or [])}
            ids.discard(None); ids.discard("")
            if ids - called_ids:                         # ② 孤儿 observation
                return i
    return None


def cleanup_incomplete_tail(conn: Any, task_id: str) -> int:
    """清理崩溃残留的残缺尾部，保持 DB 为完整断面 — 小欧 2026-10-08

    【详设】doc-10月优化/[18]…v2.0 §5.4
    【背景】_enqueue_step 只入队即返回(agent_runner.py:181 编辑历史"进程被杀则队列内帧全丢")，
             故残缺有三种形态，全部由 find_unclosed_index 覆盖。
    【返回】被删行数；0 = 无残缺
    【铁律·删必留痕】删前 logger.info 记 task_id / 起始 step_index / 删了几行，
             不记日志事后无法追责。
    【判定为残缺一律删】宁可删不可留 —— 留着必 400，删了只是少一轮。
    """
    raw = conn.execute(
        "SELECT step_index, step_json FROM chat_task_steps WHERE task_id=? ORDER BY step_index ASC",
        (task_id,),
    ).fetchall()
    if not raw:
        return 0

    rows = [(r["step_index"], parse_json(r["step_json"], label="step_json") or {}) for r in raw]
    cut = find_unclosed_index(rows)
    if cut is None:
        return 0

    cut_step_index = rows[cut][0]
    cur = conn.execute(
        "DELETE FROM chat_task_steps WHERE task_id=? AND step_index >= ?",
        (task_id, cut_step_index),
    )
    deleted = cur.rowcount
    logger.info(
        f"[Resume] 清理残缺尾部 task={task_id} cut_step_index={cut_step_index} "
        f"删{deleted}行 (总{len(rows)}行)"
    )
    return deleted
```

```python
def build_history_from_steps(steps: List[Dict[str, Any]]) -> List[Dict[str, Any]]:
    """把 chat_task_steps 断面(已清残缺)转回 LLM messages 结构 — 小欧 2026-10-08

    【映射规则】
      thought        → 跳过(推理内容，不是 LLM messages 的一部分)
      action         → {"role":"assistant", "content":"", "tool_calls":[...]}
      observation    → {"role":"tool", "tool_call_id":..., "content":...}
      chunk/error/final → 跳过(chunk 仅 SSE 不落库；error/final 已终态不进续跑)

    【铁律】产出必须满足 MessageBuilder._trim_fc_pairs(message_builder.py:521) 的配对要求：
           每个 assistant.tool_calls[].id 必有对应 role=tool(tool_call_id 相同)，
           否则发给 LLM 直接 400。这正是残缺清理必须先跑的原因。
    """
    history: List[Dict[str, Any]] = []
    for d in steps:
        t = d.get("type")
        if t == "action":
            tool_calls = []
            for c in (d.get("tools") or []):
                tid = c.get("_tool_call_id") or ""
                if not tid:
                    logger.warning(f"[Resume] action 缺 _tool_call_id 跳过: tool={c.get('tool')!r}")
                    continue
                tool_calls.append({
                    "id": tid,
                    "type": "function",
                    "function": {
                        "name": c.get("tool") or "",
                        "arguments": safe_json_dumps(c.get("params") or {}),
                    },
                })
            if tool_calls:
                history.append({"role": "assistant", "content": "", "tool_calls": tool_calls})
        elif t == "observation":
            for tr in (d.get("tool_result") or []):
                tid = tr.get("_tool_call_id") or ""
                if not tid:
                    continue
                history.append({"role": "tool", "tool_call_id": tid,
                                "content": _observation_content(tr)})
    logger.info(f"[Resume] build_history_from_steps: {len(steps)} 步 → {len(history)} 条 messages")
    return history


def _observation_content(tr: Dict[str, Any]) -> str:
    """把 tool_result 转成 role=tool 的 content 文本 — 小欧 2026-10-08

    【为何不直接 json.dumps】tool_result.llm_data 是已格式化好的 observation dict
    (经 format_llm_observation)，LLM 读的是那段文本而非原始 JSON。
    """
    llm_data = tr.get("llm_data")
    if isinstance(llm_data, dict):
        action = llm_data.get("action")
        if isinstance(action, dict):
            s = action.get("summary")
            if isinstance(s, str) and s.strip():
                return s
        status = llm_data.get("status")
        if isinstance(status, dict):
            m = status.get("message")
            if isinstance(m, str) and m.strip():
                return m
    for key in ("data_text", "content"):
        v = tr.get(key)
        if isinstance(v, str) and v.strip():
            return v
    return safe_json_dumps(tr)


async def resume_orphaned_task(task_id: str, session_id: str, llm_client: Any,
                             db_ops: Any = None,
                             ai_message_id: Optional[int] = None) -> bool:
    """崩溃残留任务的续跑入口 — 小欧 2026-10-08

    【流程】北京老陈定案：注入历史继续执行，不追崩溃点
      1. 清残缺尾部(task_integrity.cleanup_incomplete_tail) —— 保证断面完整
      2. 读干净断面(storage.load_execution_steps)
      3. build_history_from_steps 转 messages
      4. 建 UniversalAgent(llm_client 由调用方注入，见下方"为什么不自建 client")
      5. 注入历史(核心)
      6. 回填 llm_call_count(react_step.py:318 每轮自增，续跑须从 DB 值接着数)
      7. 走 run_agent_in_background(不是 run_react_cycle —— 见 §4.2 F1)

    【返回】True=续跑已成功启动(内部已 create_task，**调用方不要再包一层**)；False=启动失败
    """
    from app.services.agent.universal_agent import UniversalAgent
    from app.services.agent.agent_runner import run_agent_in_background

    try:
        # ---- 1. 清残缺尾部(必须在读断面之前) ----
        n_deleted = await db.atxn("chat", lambda c: task_integrity.cleanup_incomplete_tail(c, task_id))
        if n_deleted:
            logger.warning(f"[Resume] task={task_id} 清理残缺 {n_deleted} 行后重建")

        # ---- 2. 读任务行 + 断面 ----
        def _read(conn):
            row = conn.execute(
                """SELECT ai_message_id, sessionModel, max_steps, llm_call_count, user_input
                   FROM chat_tasks WHERE task_id=?""",
                (task_id,),
            ).fetchone()
            if not row:
                return None, None
            steps = storage.load_execution_steps(conn, row["ai_message_id"], task_id)
            return dict(row), steps

        task_row, steps = await db.atxn("chat", _read)
        if not task_row:
            logger.error(f"[Resume] 任务行不存在，无法续跑: task={task_id}")
            return False

        # ---- 3. 断面 → messages ----
        history = build_history_from_steps(steps or [])
        if not history:
            logger.warning(f"[Resume] task={task_id} 断面为空，将从原始 user_input 重新开始")

        # ---- 4. 建 agent ----
        agent = UniversalAgent(llm_client=llm_client, task_id=task_id,
                               max_steps=task_row.get("max_steps") or None)

        # ---- 5. 注入历史(核心) ----
        agent.message_builder.inject_history(history)

        # ---- 6. 回填轮次 ----
        agent.llm_call_count = int(task_row.get("llm_call_count") or 0)

        logger.info(
            f"[Resume] task={task_id} 续跑启动: 断面{len(steps or [])}步→messages{len(history)}条, "
            f"轮次从{agent.llm_call_count}继续, session={session_id}"
        )

        # ---- 7. 走 run_agent_in_background(不是 run_react_cycle) ----
        # 内部自带 buffer 缺省创建 + _step_queue 消费者 + finally 置 done，与正常任务同源。
        # 直调 run_react_cycle 必崩(§4.2 F1)。
        asyncio.create_task(run_agent_in_background(
            agent,
            task_id=task_id,
            last_message=task_row.get("user_input") or "",
            context=None,
            session_id=session_id,
            stream_state=None,
            db_ops=db_ops,
            ai_message_id=ai_message_id if ai_message_id is not None else task_row.get("ai_message_id"),
        ))
        return True

    except Exception as exc:
        logger.error(f"[Resume] task={task_id} 续跑启动失败: {type(exc).__name__}: {exc!r}")
        return False
```

- 残缺可能**同时**丢掉 action 和 observation（两者都在队列里没消费）
