### 4.1 概念更新（本章立论基础）

**一句话**：在我们的系统里，**会话 == 事务 == 项目**；会话 Workspace 就是**针对某个项目（会话）的可读写目录空间**。

系统因此有**三个目录空间**，前两个早已存在、**针对所有会话**，本次新增第三个：

| # | 目录空间 | 现键名 | 作用域 | 数量 | 状态 |
|---|---|---|---|---|---|
| 1 | **项目根目录** | `workspace.project_root` | **所有会话**（全局） | 单个 | 已有（设置页「通用」组） |
| 2 | **授权目录** | `workspace.allowed_dirs` | **所有会话**（全局） | 列表 | 已有（设置页「通用」组） |
| 3 | **本项目的 workspace** | 表 `chat_session_workspaces`（会话级，见 §4.4） | **只针对某一个会话/项目** | 列表 | **本次新增** |

关键含义（四条，逐条都是设计后果）：

1. **作用域不同**：前两个是"所有会话共用"，第三个是"**只属于这一个项目**"。这是本质区别，不是配置层级差异。
2. **1:N**：一个项目/事务可以开**多个**可读写目录。
3. **授权语义**：三者同源——都是安全白名单的组成部分，只是作用域不同。工具的可写范围 = ①∪②∪**③**。
4. **不进设置页**：第三个是会话级，按 §3.0 第三章决策 4，registry 装不下（79 个 `_item` 全是全局项、无 per-session 通道）。

> ⚠️ **语义澄清**：会话 workspace **不是收紧隔离**。项目根与授权目录是全局恒开且恒在白名单（§4.2），会话根的角色是**叠加放宽**——再挂几个本会话专用的额外目录。LLM 对项目根恒有读写权，与是否配置会话工作区无关。把本章理解为「项目根 + 该会话额外挂载目录」即可，勿当作「把项目隔离到会话专属子目录」。删默认目录后兜底回项目根（决策 28），隔离性不变。

> ⚠️ **"会话==项目"的边界**：上文"会话==事务==项目"说的是**产物落盘视角**（本次任务的产物归这个会话），**不是"项目上下文锚点"归会话**。`project_context.py:38` 读的是**全局项目根**的 `OmniAgent.md`，本设计**不改**（存量行为不动）。理由：会话目录是**可写工作区**——若把上下文锚点也放进可写目录，等于 LLM 这一轮写进 `OmniAgent.md` 的内容下一轮就会被当项目上下文读回执行，**提示注入面直接开在核心链路上**，收益远小于风险。故：**产物归属会话、上下文锚点留在全局项目根**，二者分工明确，实施者勿"顺手对齐"。

#### 4.3.1 决策点1 — 决策 26/27/28 的落地细则（目录命名）

| # | 裁定 | 说明 |
|---|---|---|
| 26 | **默认目录建在项目根下，直接建**，`{项目根}\{会话事务名+时间}` | **不加** `workspaces` 中间层——目录列表要喂给 LLM，路径越短越不容易被模型拼错 |
| 27 | **目录名 = 会话事务（标题）+ 时间**，标题**只取前 3 个字** | 同上理由：给 LLM 看，名字要简洁可辨（3 字足够模型判读，路径越短越不易拼错） |
| 28 | **默认目录可删除** | 删除后退化为**项目根兜底**——`workspace.project_root` 本就在白名单且恒 `rw`，故删掉默认目录后会话**仍有可写目录**，功能不残 |

**落地格式**（示例）：

```
项目根 = F:\我的项目
标题   = 修复登录 bug        ← 完整标题

目录名 = 20261006-143022-修复登        ← 只取前 3 个字（决策 27）
路径   = F:\我的项目\20261006-143022-修复登      ← 项目根的直接子目录
```

**目录名 sanitize 规则**（Windows 约束 + LLM 可读）：

| 规则 | 原因 |
|---|---|
| 前缀 `YYYYMMDD-HHMMSS-` | 一眼看出是哪个会话、什么时候建的，多个目录按时间天然有序 |
| 标题**只取前 3 个字** | 喂 LLM 的路径越短越不易被模型拼错（决策 27）；3 字足够模型判读用途 |
| 标题 Windows 非法字符替换为 `_`：``\ / : * ? " < > \|`` | 标题由用户自由输入，可能含上述字符 |
| 标题首尾空格与结尾 `.` 去除 | Windows 目录名不允许以空格或点结尾 |
| 标题为空时回落 `session` | 会话创建瞬间标题可能还没生成 |
| 同名冲突时后缀 `-2`/`-3` | 同秒同名极端情况（`UNIQUE(session_id, path)` 兜底） |

#### 4.3.3 决策点3 — 注入位置：**拼接在本任务用户消息的尾巴**（北京老陈裁定）

北京老陈裁定：本会话可读写目录与「产物落会话目录」约束，**直接拼接到本任务的用户消息尾部**，不单独放 system prompt。

先把原 system prompt 方案的四条理由摊开评估，再给出此项改判的权衡结论：

| # | 原 system 方案的理由 | 改判 user 尾部后的处置 |
|---|---|---|
| 1 | 与既有项目根/授权目录同源（system 有二者，新增也该 system） | **口径靠 ContextVar 快照统一**——user 尾部只承载"提示+约束"，真正放行的白名单仍只有 system prompt 那份 `path_safe_check` 依据（同一份快照） |

| 3 | user 消息会持久化 → 历史里留过期目录 | **这是改判的主要代价；**缓解方式：目录列表每任务由 ContextVar 快照重拼（新任务的 user 消息自带最新列表），且工具层放行永远以白名单实时计算为准——模型若照历史旧列表操作，也只会被白名单正确拒（撞墙即提示，非越界） |
| 4 | user 每轮重复；system 一个任务一次 | 目录条目通常 1~3 条绝对路径，拼在 user 尾部 token 开销小 |

**改判后的文案位置与形态（拼在最后一条 user 消息尾部）**：

### 4.4 存储设计（决策：独立表，2026-10-06 北京老陈定 a）

**不进 registry**（第三章决策 4：`settings_registry.py` 79 个 `_item` 全是全局项、无 per-session 通道）；**不加 `chat_sessions` 列**（1:N 列表压一格，将来无法反查）。

```python
# app/db/db_initializer.py —— 新建表（不是 ALTER，是首版建表）
CREATE TABLE IF NOT EXISTS chat_session_workspaces (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id   TEXT    NOT NULL,
    path         TEXT    NOT NULL,
    is_default   INTEGER NOT NULL DEFAULT 0,      -- 1=新会话自动创建的默认目录
    created_at   TEXT NOT NULL DEFAULT (datetime('now', 'localtime')),
    UNIQUE(session_id, path),         -- 同会话同路径不重复（配合落库前路径归一化，见下）
    FOREIGN KEY (session_id) REFERENCES chat_sessions(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_csw_session ON chat_session_workspaces(session_id);
-- 每个会话至多一条 is_default=1（§4.8.2 断言的 schema 落点；SQLite 部分唯一索引）
CREATE UNIQUE INDEX IF NOT EXISTS uq_csw_default ON chat_session_workspaces(session_id) WHERE is_default = 1;
```

> ⚠️ **删会话清理不靠 CASCADE**：`delete_session`（`session_service.py`）是**软删**（`UPDATE chat_sessions SET is_deleted=TRUE`），父行永不物理删除 → `ON DELETE CASCADE` 永久休眠。FK 保留仅作防御性约束，**真正的清理必须二选一落地**：(a) `delete_session` 末尾显式 `DELETE FROM chat_session_workspaces WHERE session_id=?`（推荐，与 `delete_session_display_names` 同位置）；或 (b) `get_session_workspaces` 查询 JOIN `chat_sessions WHERE is_deleted=FALSE` 过滤。选 (a) 为主（行级干净），(b) 为辅（防漏网）。验收见用例 10。

> **路径归一化（落库前必须做，否则 UNIQUE 防不住同目录多行）**：`set_session_workspaces_conn` 写入前逐条归一——`Path.resolve()` 绝对化 + 去尾部分隔符 + Windows 下 casefold（`F:\a\b`、`F:\a\b\`、`f:\A\B` 是同一目录，SQLite UNIQUE 是二进制比较）。归一后仍冲突的行直接丢弃（落库幂等）。

> **整体覆盖式写语义（本处钉死，三步有序不得简化）**：`set_session_workspaces_conn` 必须是**三步有序**，不得简化：
1. **先 SELECT 旧行入内存**（`SELECT path, is_default FROM ... WHERE session_id=?`）——决策 37 的「`is_default` 按 path 回查旧行保留」**依赖这一步的结果**；
2. 再 `DELETE FROM chat_session_workspaces WHERE session_id=?`；
3. 再逐条 INSERT：新行的 `is_default` = 内存旧行中同 path 的值（无匹配则 0），`created_at` 取本次插入时间（不保留旧值——覆盖写即"当前列表的快照"，旧时间无意义）。

> ⚠️ **为何不能用"UPSERT 一把梭"**：`ON CONFLICT(session_id,path) DO UPDATE` 只能保住**仍存在于新列表中**的行；被删掉的行不会被清掉 → 「删光目录」失效（决策 32 的核心用例直接破）。故必须"全删重插"三步式。
> ⚠️ **裸 INSERT 禁止**：跳过第 1 步则 `is_default` 必丢 → 弹窗的「默认」标记丢失、且 §4.4 注释所述部分唯一索引语义失真（见决策 30 交叉引用）。写库不碰 `chat_sessions.updated_at`（同 link 模式：改目录不是内容变更，否则每次改目录都把会话顶到列表首位）。

**两态而非三态**：不设 `none`——没有授权就等于**不在列表里**，在列表里就至少可读。多一个 `none` 态就要处理"列表里但等于没授权"的矛盾（KISS/YAGNI）。

### 4.5 可访问性模型（**无权限维度** —— 决策 30）

**结论：会话 workspace 目录没有 `rw`/`ro`，只有"在不在列表里"一个状态。**

#### 4.5.1 为什么取消 `ro`（实读定案，不是拍脑袋）

原设计拟给每个目录挂 `rw`/`ro`，判定挂在 `path_safe_check` 既有 mode 三态（`validate_path`（`:230`）内 read/delete/write 三段分支）上。核查后发现**该闸门拦不住 shell**：

| 证据 | 原文 |
|---|---|
| `path_safe_check.py:363` | `_PATH_PARAM_KEYS = ("path","source_path","target_path","file_path","directory","file_name","destination_path","output_path","dest")` —— **共 9 个键，不含 `command`** |
| `path_safe_check.py:448` | `hit_params = [key for key in _PATH_PARAM_KEYS if ...]` —— shell 的路径在 `command` 里 → 不命中 → **不校验** |
| `trust_db.py:15` | "path=None（**无路径工具: shell**/execute_sql/registry_*）" |
| `safety_gate.py:46` | "shell 不在 trust 两集合…`extract_trust_path` **恒 None**" |

**后果**：模型一句 `del /r D:\资料\*.md` 或 `echo x > file` 就能改掉标了"只读"的目录——文件类工具被拦住，shell 不拦。**这是假安全感，比没有更危险**（用户会放心把重要资料挂上去）。

> 补充：shell 并非"无保护"，它走的是**另一套机制**——HITL 人工确认（`safety_gate.py:59` "shell 确认门"、`:76` 按 command 全文分组弹窗，`:81-82` `if tool_name == "bash": _ref = "cmd:" + command`）。即**机器能判的让机器判，判不了的让人判**，是当年主动的分层设计，不是遗漏。

#### 4.5.2 那实际生效的规则是什么

不加 `ro` 后，会话目录只是**多几个白名单根**，完全复用现有语义：

| 规则 | 现状（既有代码，无需改） |
|---|---|
| 目录**在**列表里（会话根） | 读放行；写放行（跳过任务级临时授权）；删放行到下一层（仍需 `delete_safety` 的 R4 确认，见 §4.5.5）—— `path_safe_check.py:312-329` 命中即 `return True`，不看 mode，但"放行"指本层不再拦，不等于执行层无确认 |
| 目录**不在**列表里 | 读放行；写/删走任务级临时授权（`:338-346`） |
| shell（`command` 参数） | **不受本节任何规则约束**：shell 路径不进 9 键校验，一律走 HITL 人工确认门（见 §4.5.1）。"在不在列表里"对 shell 无意义 |

**所以新增的只有一句话**：会话目录并入白名单计算（见决策 42）。

> **合并点定义（决策 42；决策 31 分档后由两处增至四处）**：并入点只在下列调用点，**不改共享函数内部**——①`path_safe_check.py` 取白名单处并入会话根；②`delete_safety.py:46-48 _get_allowed_roots()` 内并入同一份快照；③`delete_file.py:95-110 protected_roots_` 改为每次调用现算、并入 `is_default=0` 的手动目录（决策 31 分档）；④编排器入口 user 尾拼接（§4.3.3）。**不得**直接改 `get_default_allowed_paths()` 函数内部：它是 6 处调用方（`delete_file.py:99`、`download_file.py:47`、`generate_chart.py:39`、`project_context.py:38`、`system_prompts.py:107`、`system_adapter.py:52`）的共享源，改内部等于让下载落点/图表输出/项目上下文等 5 处无关调用方静默获得会话根。

#### 4.5.3 现有判定逻辑无需改造（不引入最长前缀匹配）

"取最深匹配的根判权限"这套逻辑**只因不同根权限不同才有必要**。本设计无per-directory 权限（决策 28），命中 `D:\a`（宽根）还是 `D:\a\b`（窄根）结果完全相同 → **现有"第一个命中即 return"（`:312-329`）无害** → **不把循环改成长匹配**，砍掉一处安全敏感改造。

#### 4.5.4 若将来真要"只读"，正确做法（另议，不在本设计）

走 **OS 层**而非应用层解析：

| 方案 | 能绕吗 | 副作用 |
|---|---|---|
| **目录只读属性**（`attrib +r` / `chmod` 去写位） | ❌ OS 强制，绕不过 | 用户自己在资源管理器里也不能改，需手动恢复 |
| Windows ACL（deny-write） | ❌ 绕不过 | 权限管理复杂易乱 |
| 解析 shell 命令抽路径 | ⚠️ **可绕过，不建议** | `cd`+相对路径、`>` 重定向、`$(...)`、`*` 通配、别名、`python -c`、`%VAR%`、符号链接——任一正则/词法解析都会被绕过 |

> **不做 shell 命令路径解析**（YAGNI + 不可靠）：绕过手法清单见上，一旦有绕过比不做更糟。若要 shell 受限，正道是**限制 cwd** 或 **容器隔离**，那是独立设计。

#### 4.5.5 目录列表的**四个**消费方（决策 31：加 4，且 3 按 `is_default` 分档加）

2026-10-06 北京老陈追问"白名单不就两处用吗"——核查后确认**有四处**消费会话目录，全部从 `get_project_root() + get_allowed_dirs()` 取全局根，故**不改就静默不生效**：

| # | 消费方 | 取数位置 | 会话目录 | 理由 |
|---|---|---|---|---|
| 1 | 路径校验白名单 | `path_safe_check.py:139-140` | ✅ **加** | 核心诉求：目录内文件工具可访问 |
| 2 | 用户会话事务目录注入 | `stream_orchestrator` 入口拼到 user 尾部（原 `system_prompts.py` 增段一路已作废，见 §4.3.3 / 决策 29 改判） | ✅ **加** | 让模型知道能去哪干活 |
| 3 | 删除**硬拦**保护根 | `delete_file.py:95-110` `protected_roots_` | ⚠️ **按 `is_default` 分档加**：`is_default=0` 手动目录**加**、`is_default=1` 默认目录**不加** | 见下方论证 |
| 4 | 删除**软评估**白名单 | `delete_safety.py:46-48` `_get_allowed_roots()` | ✅ **加（必须）** | 见下方论证 |

**为什么 3 和 4 不是重复，但需分开裁定**——两者方向相反：

| | 加 3（硬拦） | 加 4（软评估） |
|---|---|---|
| 管的是 | **目录本身**能不能删 | **目录里面的东西**怎么删 |
| 加了之后 | 该目录根自身被硬拦（**仅 `is_default=0` 手动目录**；默认目录不加③、根自身仍可删） | 工作区里删文件**顺畅了**（不弹临时授权） |
| 方向 | **限制更多** | **限制更少** |

**决策 31：加 4；3 按 `is_default` 分档加**。

- **4 必须加**：不加则 `delete_safety.py:82` `inside_proj = _is_inside_any(p, allowed_roots)` 判 False → 在**自己工作区里删个临时文件**被判"白名单外删除" → 弹临时授权 → **工作区基本没法用**（功能退化）。
- **3 必须分档的理由**：「会话目录是系统为会话自动建的**临时工作区」，这话**只对 `is_default=1` 的默认目录成立**。**手动添加的目录（决策 34）进的是同一张表、同一份白名单**，性质是**用户长期资产**（用户在弹窗里一个个挑自己长期用的目录挂进来）。一律不加 ③ = 用户手挂的 `D:\我的重要资料` **根自身可被硬删**，与全局 `allowed_dirs` 里的授权目录享受的保护不对等（后者在 `protected_roots_` 内），是**保护等级倒退**。
- **3 分档后的效果**：

| | `is_default=1` 默认目录 | `is_default=0` 手动目录 |
|---|---|---|
| 加 3（硬拦） | ❌ 不加 | ✅ **加** |
| 根自身能否被删 | ✅ 能（挡住"任务做完把临时目录整个清掉"这个高频需求） | ❌ 不能（与全局授权目录同等待遇，保护用户长期资产） |
| 目录内部的东西 | 走 4 软评估 → R4 确认 | 走 4 软评估 → R4 确认 |

> **实现要点（勿漏）**：`protected_roots_` 现为**模块级静态量**（`delete_file.py:95-110`），要装入"当前会话的 `is_default=0` 会话根"必须改为**每次调用现算**：从 §4.6 的同一份 ContextVar 快照取 `is_default=0` 的子集。因快照元素需同时带 `path` 与 `is_default`，`_current_session_workspaces` 的元素类型应为 **`list[tuple[str, int]]`（或 dict）**，不纯是 `list[str]`——见 §4.6 步骤①的连带修正。ContextVar 经 `asyncio.to_thread` 可传播（见决策 46），故 `to_thread` 路径取得到。

> **同源要求（决策 43，四个消费方）**：`delete_safety`、`delete_file.protected_roots_`、`path_safe_check`、用户会话事务目录注入读到的会话根必须与**同一份 ContextVar 快照**一致（直读 DB 另起一套即 TOCTOU：校验放行了，软评估却认为不在 → 同一个删动作两层结论打架）。实现时四处同源，单测断言四处快照一致。
>
> **上表仅说明两类消费方方向相反**；实施口径以决策 31 分档裁定为准。

> **会话根与禁区档位的先后（禁区优先，会话根永不覆盖禁区；默认目录继承项目根信任）**：`validate_path` 内顺序是机械事实——禁区检查先行，白名单在后。实施规则分两档，实施者照做不讨论：
> ①**自动建的默认目录**：建在项目根下，由 `create_session` 生成，**继承项目根信任**，豁免"代码库根子级"这一档预检（项目根本身是用户配置的可信锚，其直属子目录不扩展任何新信任面；且项目根**本身删不掉**——`delete_file.py protected_roots_` 硬拦根自身及更上层，见下）。系统禁区（盘符根/Windows 等）对默认目录照样生效，命中即拒绝创建并明确报错。
> ②**手动添加的目录**：入库前必须过全套禁区预检（系统禁区 + 代码库根及其子级，口径与 `allowed_dirs` 的禁令一致）；命中任一禁区 → **拒绝入库并明确报错**，不进表、不进白名单、不进注入块。
> ③运行期兜底：若某会话根落入禁区（防御性兜底），以禁区处置为准（写查授权/删硬拦），白名单命中不得覆盖。
>
> **术语澄清（防混淆）**：本文"禁令"指**位置禁令**（目录不得位于禁区内）；"项目根删不掉"指**删除保护**（`protected_roots_` 硬拦根自身及更上层），两者是两回事。项目根的位置不受限（存量行为不动），删除受保护（既有行为不动）。

### 4.6 安全校验改造（会话上下文怎么到工具层）

**障碍**：`validate_tool_path(tool_name, params)`（`:393`）签名无会话/任务参数，白名单纯由 `get_config()` 全局决定。

**解法（KISS + 同构复用既有 ContextVar 模式）**：

| 步骤 | 落点 | 做法 |
|---|---|---|
| ① 上下文载体 | `app/tools/context.py:24` 旁（既有 2 个 ContextVar 之后） | 新增 **`_current_ws: ContextVar[Optional[WorkspaceSnapshot]]`**，存**快照对象**（决策 52）：`entries` 是 `WorkspaceEntry(path, is_default)` frozen dataclass 的 tuple，并在 **`set` 时**派生 `all_paths` / `manual_paths` 两个 frozenset。**不用裸 `list[tuple[str,int]]`**（无字段名，读代码要数下标才知含义）。存快照而非 session_id（免一次 IO）；**无权限维度**（决策 37） |
| ② 入口注入 | `stream_orchestrator.py:387`（`_current_task_id.set` 旁） | `set_current_session_workspaces(await _load_workspaces(session_id))` |
| ③ 收尾 reset | `stream_orchestrator.py:686` 收尾段（`bg_task.add_done_callback` 所在，其后即任务终结漏斗） | `reset_current_session_workspaces(token)`（`try/finally`，**必须收 token**——决策 53：既有 `reset_current_hooks(token)` 是这个形态，无参 reset 在嵌套/跨线程会 reset 错对象） |
| ④ 白名单计算 | `path_safe_check.py:139-140` 取白名单处 + `delete_safety.py:46-48` 内 + `delete_file.py:95-110` 取 `is_default=0` 子集 | **只在上述调用点并入会话根，不改 `get_default_allowed_paths()` 共享函数内部**（见决策 42；改内部会波及下载落点等 5 处无关调用方）。全局根恒在，会话根在列即放行，无权限维度（决策 30） |

> **`_load_workspaces(session_id) -> list[tuple[str,int]]` 定义（本处钉死）**：归属 `app/services/chat/storage.py`（与 get/set/resolve 同模块，§4.7 row 2 一并覆盖）。语义 = `get_session_workspaces` 取 DB 行 → 逐条归一化（resolve 绝对化 + 去尾部分隔符 + Windows casefold，与落库归一化同口径，保留 `is_default`）→ **三重过滤**：①`Path.exists()` 过滤已不存在的目录（决策 49）；②**禁区过滤**——决策 34 只管「添加时」，但表里的**老行从不被复查**：某目录入库时合法，之后项目根被改到代码库根下、或全局 `allowed_dirs` 禁令范围变化，老行就落入禁区了。**判据来源钉死**：复用 `path_safe_check._is_forbidden_path()`（返回 `system`/`non_system`/`None`，是全项目唯一的禁区判定实现；`config.py:251-259` 那段是 `get_allowed_dirs()` 的**私有内联逻辑、未导出**，严禁复制粘贴——DRY）。命中则**过滤掉**（不报错、只告警，因为它已不是用户此刻的显式选择）；③返回**新的** list（每次调用新对象，调用方不得持有旧引用复用）。DB 异常 → 返回 `[]`（**fail-open**：DB 异常不得阻断任务，空列表按「非空才追加」规则自然不拼块、不进白名单）。**验收**：库里塞一条已落禁区的行，断言它既不进白名单也不进注入块。⚠️ **批次约束**：本函数因依赖该禁区判据，**必须排在 `path_safe_check` 改造之后**（见 §4.7 批次表 W4），不得在 W1 阶段实现。

**为什么快照而非每次查 DB**：① 一任务内只查一次，避免每路径参数都 IO；② **正好符合"新任务及后续任务用新的 workspace"**——任务启动时取快照，任务执行中用户改列表不影响本任务，新任务才生效。语义与需求天然一致。

> **落值三态（决策 32，本处钉死）**：编排器收到 `session_workspaces` 必须三态分流——**`null`（字段缺席或未带）→ 沿用该会话当前已落库值**；**`[]`（显式空数组）→ 覆盖清空**；**非空列表 → 整体替换**。前端弹窗「确定」有增删（含删空）时**必须传完整新数组（空即 `[]`）**，绝不用 `null` 表达"我改过了"——否则删除全部目录会被误判为沿用，等于删不掉。本条贯穿 `message_service.save_message`（落库）与编排器入口（取生效值）两处，须同口径实现。
>
> **落库失败不拖消息（降级内聚在真源函数内）**：禁区预检命中时的降级（决策 36）**内聚在 `resolve_session_workspaces` 内**——它**不抛异常、不阻断调用方**，而是**保留旧值 + 返回 `workspace_rejected: [{path, reason}]`**，由 `save_message` 原样带给前端。实现者不得把 workspace 的校验失败做成 `save_message` 的抛出路径——**与插话 409 是两件事**：409 拒的是整条消息，workspace 只拒字段，粒度不同不可混用。
>
> **落点：单一真源，两处共用（2026-10-08 实读链路修正）**：三态分流与落库**只在 `storage.resolve_session_workspaces(conn, session_id, 携带值)` 一处实现**——照插话开关 `resolve_session_interject` 的**同款写法**（该函数已被 `save_message` 与编排器共用，是本项目既定单一真源模式，实读证据：`stream_orchestrator.py:206` 注释明写「与 save_message 共用单一真源」）。判定语义：携带值 `null`→读 DB 当前值沿用；`[]`→覆盖清空；非空→整体替换。
> - **两个调用点都调它**，不各写一套：①`message_service.save_message`（POST `/messages`，**主落库点**，落库发生在 SSE 之前——实读 `api/v1/messages.py:55 save_message_endpoint` → `message_service.py:191`）；②编排器入口（`stream_orchestrator`，覆盖 `:377` 自动建会话、后台注入等**不经 POST** 的路径）。
> - 因函数幂等（同 conn、同一三态语义），两处都调**不重复写、不打架**，反而消除了「谁先落」的竞态。
> - 续传/恢复任务（见决策 51）：不断流的续传沿用原快照；重建流的恢复按新任务走完整入口（含三态分流）。

```python
# ============ ① storage.py：归一化与判据各有唯一源（决策 49） ============

def _normalize_ws_path(p: str) -> str:
    """会话目录路径归一化 —— 全链路唯一实现。落库与读侧共用，禁写第二份(DRY)。

    resolve 绝对化 + 去尾部分隔符 + Windows casefold
    （F:\a\b、F:\a\b\、f:\A\B 是同一目录；SQLite UNIQUE 是二进制比较）
    """
    return str(Path(p).expanduser().resolve()).rstrip("\\/").casefold()


# ============ ② storage.py：落值真源内部三拆（决策 50，SRP） ============

def _ws_resolve_effective(conn, session_id: str, carried: Optional[list]) -> list[str]:
    """三态分流：null=沿用 DB 当前值 / []=覆盖清空 / 非空=整体替换。只判不定，不碰写。"""
    if carried is None:
        return [r["path"] for r in get_session_workspaces(conn, session_id)]
    return carried


def _ws_precheck(paths: list[str]) -> list[dict]:
    """禁区预检：复用 path_safe_check._is_forbidden_path()（全项目唯一判据）。
    返回被拒清单 [{path, reason}]；**不抛异常**——调用方按「拒字段不拒消息」降级。"""
    from app.tools.security.path_safe_check import _is_forbidden_path  # 延迟导入避环
    rejected = []
    for p in paths:
        category, msg = _is_forbidden_path(p)
        if category:
            rejected.append({"path": p, "reason": msg})
    return rejected


def _ws_apply(conn, session_id: str, paths: list[str]) -> None:
    """三步式覆盖写（决策 37）—— **唯一写库实现，禁再包一层(set_* 之类)重复定义**。

    SELECT 旧行 → DELETE 全删 → 逐条 INSERT。
    is_default 按 path 回查旧行保留；created_at 取插入时间；**不碰 chat_sessions.updated_at**。
    """
    old = {r["path"]: r["is_default"]
           for r in conn.execute(
               "SELECT path, is_default FROM chat_session_workspaces WHERE session_id=?",
               (session_id,))}
    conn.execute("DELETE FROM chat_session_workspaces WHERE session_id=?", (session_id,))
    now = get_local_iso_timestamp()
    conn.executemany(
        "INSERT INTO chat_session_workspaces(session_id, path, is_default, created_at) "
        "VALUES (?, ?, ?, ?)",
        [(session_id, p, old.get(p, 0), now) for p in paths])
        insert_session_workspace_conn(conn, session_id, p, is_default=old.get(p, 0))


def resolve_session_workspaces(
    conn, session_id: str, carried: Optional[list]
) -> tuple[list[str], list[dict]]:
    """**落值单一真源** —— save_message 与编排器都调它(禁各写一套)。

    返回 (effective_paths, rejected)：rejected 非空即决策 36 降级，调用方带出给前端。
    幂等：同 conn、同一三态语义，两处都调不重复写、不打架。
    """
    paths = [_normalize_ws_path(p) for p in _ws_resolve_effective(conn, session_id, carried)]
    paths = list(dict.fromkeys(paths))          # 去重且保序(归一后可能撞车)
    rejected = _ws_precheck(paths)
    if rejected:
        ok = [p for p in paths if p not in {r["path"] for r in rejected}]
        _ws_apply(conn, session_id, ok)         # 只落合法部分 = 保留旧值的实现方式
        return ok, rejected
    _ws_apply(conn, session_id, paths)
    return paths, []
```

```

│                                        [取消]  [确定]  │
└────────────────────────────────────────────────────────┘
```

- 弹窗标题：**会话事务空间**
- 顶部回显**项目根**（说明默认目录建在哪，也是删除全部目录后的兜底）
- 每行：目录名 + 删除 `×`。**无读写下拉**（决策 30：不做 `ro`）
- 默认目录行标记「默认」
- 底部：`＋ 添加已有目录…` + 取消/确定
- **「添加已有目录…」落表前必须 `Path(path).exists()` 校验**（决策 34）：不存在/非目录/非法 → 阻断并提示，**不进列表、不进白名单**。路径输入主路径用**系统目录选择器**（防手输 typo；手输作备选则必须失焦即校验）——决策 74。⚠️ **前端只能做这一道**：禁区清单（系统禁区 + 代码库根及其子级）**只存在于后端**（`config.py:249-259` 的 `get_allowed_dirs` 自带校验、`path_safe_check` 的禁区表），前端无从得知"代码库根"具体是哪些路径 → 前端不做本地禁区预检。决策 34 要求的**禁区预检只在后端落库前跑**；前端不做、也不必为此新增只读查询接口（YAGNI），非法路径的反馈经决策 36 的 `workspace_rejected` 呈现
- **弹窗「确定」有增删时传完整新列表（空列表也传 `[]`）**（决策 32）：用 `[]` 表达清空，绝不用 `null`；`null` 仅保留给「未改动」
- **弹窗显示本地暂存（含未落库改动），不是每次打开重拉 DB**（决策 75）
- **「取消」= 丢弃本地暂存，回到 DB 已落库状态**（决策 76）：因暂存会被持久化（§4.9 row 6），故钉死**取消 = 放弃本次及此前所有未落库改动，以 DB 为准**。用户若想保留改动，直接「确定」即可
- **存在本地暂存时，徽标数可能少于弹窗行数**（徽标 ②、弹窗 3 行）——决策 80：这是设计而非 bug
- **两个读通道的优先级（决策 77）**：见§4.8.0 决策 77；徽标一律按 DB 行数（决策 40）
- **示例路径一律绝对路径**（决策 79）：mock 里不得出现 `..\..\` 相对路径
- **每个会话至多一条 `is_default=1`**（创建默认目录时写死，删除默认目录即解除该行，不另置新默认）；若全部目录删除，下一条消息起**也不再自动补一个默认行**（决策 32：`[]`=显式清空，清空后走项目根兜底，不回退为自动建）
- **删除目录 ≠ 删除物理文件夹**：弹窗 `×`/删默认目录只移除 `chat_session_workspaces` 行与授权，**不删硬盘目录**；**删会话同样不删硬盘目录**（DB 行硬删、目录留存项目根，用户自行清理）

#### 4.8.3 操作流程

| # | 场景 | 用户操作 | 结果 |
|---|---|---|---|
| 1 | **新会话** | **零操作** | 建会话时后端自动建 `{项目根}\{时间戳}-{标题3字}` 并入列表；按钮徽标显示 `①`。**硬前提（决策 33物理目录生命周期之「建会话时生成默认目录」条）：`create_session` 必须在此同步生成默认目录并插入 `chat_session_workspaces`，否则「零操作」落空——首条消息若不携带 `session_workspaces`（null=沿用），表为空，LLM 无会话根可用（`mkdir` 失败等创建异常走决策 38 降级路径） |
| 2 | **添加已有目录** | 点按钮 → 弹窗 → `＋ 添加已有目录` → 选路径 → **确定** | 列表新增一行；**本任务不生效**，红点保留至下一条消息**落库采纳且本会话有新任务启动**（被 409 拒收/消息未被接纳时点「确定」产生的变更不清除，见下方生效时序；消费口径见决策 72） |
| 3 | **删除目录** | 弹窗内点行尾 `×` 即时移除本地行（暂存，红点出现），**确定**统一落盘 | 移除该行暂存；**下一条消息才生效**，红点保留至下一条消息落库采纳且本会话有新任务启动（口径见决策 72）；**删默认目录行点 `×` 后追加一次二次确认**（决策 78：因触发项目根兜底，语义特殊，其余行不需要） |
| 4 | **删掉默认目录** | 同流程 3 | 列表清空 → 弹窗顶部仍回显项目根 → 兜底为**项目根**（本就恒可写，功能不残，决策 28）；不再自动补建默认行（决策 32 的 `[]`=清空） |

> **无"改权限"流程**（决策 30）：目录没有 `rw`/`ro`，所以没有第 3 条"改读写"操作。

#### 4.8.4 ⚠️ 生效时序（UI 必须显式告知，否则会被当成 bug）

因决策 23（随消息下发 + 任务启动取快照），真实时序是：

```
用户改列表 → 列表变了
           → 但【当前正在跑的任务】仍用旧快照  ← LLM 仍按老目录写
           → 用户发下一条消息 → 新值随消息落库
           → 下一个任务启动读新快照 → 生效
```

**因此**：流程 2/3/4 完成后，按钮上必须显示**未生效红点**，红点仅在「改动已随下条消息成功落库采纳、且本会话有新任务启动消费新快照」后清除，被 409/未接纳拒收时保留（落库失败=改动从未生效；消费信号口径见决策 72）。理由——用户改完若以为立即生效，LLM 往新目录写却按老白名单被拒，模型反复重试浪费轮次（`agent.max_steps` 最高 10000），用户会判定功能有 bug。

> 关联：模型不知道哪些目录只读那个场景**已随决策 30 消失**（不再有只读目录）。用户会话事务目录注入的目的回归**单纯告诉模型"本会话可以在哪几个目录里干活"**（决策 29 仍然成立且必要——否则模型不知道往哪写）。
