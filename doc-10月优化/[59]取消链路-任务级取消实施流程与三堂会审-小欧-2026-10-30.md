## 一、结论摘要

1. 取消语义由「**打招呼让 agent 自己停**」改为「**直接掐掉 agent 协程，由它自己负责发终态**」。
2. 终态收敛为**单一生产者**：只有 `agent_runner` 的 `finally` 守卫可以发布 `final(cancelled)`；消费侧仅在 agent 协程确已结束（或未登记）**且 buffer 内无真实 `type=final`** 时兜底合成。
3. 前端 5s「取消等帧」看门狗降级为「**只落状态、不掐通道**」；资源释放交给帧到达（`settleCancelByFrame`）或连接自然结束。
4. 实测（本机，client_sdk 直连不响应服务端）：`task.cancel()` 从发出到 agent `finally` 完成 **0.06s**；TTFB 场景原需等满 provider `read_timeout` **5.01s / 生产 120~200s**。
5. 三堂会审结论：**0 处硬性违规**，3 处需留档的边界判定，4 项残余风险（R4 本轮已修）。

## 二、问题现象与判定口径

**现象（北京老陈实测）**：任务重试中点击「停止」，前端**完全无任何反应**；约 2 分钟后仍未收敛；左侧任务列表（读 DB）显示已取消，右栏与徽标仍显示执行中。

**判定口径（本轮确立，不得用「测试通过」代替）**：
- 现象**不是**「有 badge 没有 final 段」，而是**前端根本没收到后端的取消事件**。
- 必须以代码路径与真实链路日志说话，三个锚点缺一不可（见第九章）。

## 三、旧流程与五处断点

### 3.1 旧链路

```
前端 stop() → POST /cancel → cancel_task()
    → set_cancelled(flag) + llm_client.cancel()   （只置标记 + 关 HTTP 连接）
    → agent 只能在下一次 task_cancel_check_and_yield（轮边界）才察觉
前端 stop() 同时武装 5s 看门狗（CANCEL_FRAME_TIMEOUT_MS）
```

### 3.2 五处断点

| 编号 | 断点 | 位置 | 后果 |
|------|------|------|------|
| D1 | TTFB 阶段 `llm_client.cancel()` 是空操作（`_current_response` 仅在响应头到达后赋值） | `app/llm/client_sdk.py` | 取消后仍等 provider `read_timeout` 120~200s |
| D2 | 取消只靠 flag，agent 不查就继续跑 | `task_runtime.task_cancel_check_and_yield` | 5s 看门狗必然先到期 |
| D3 | `request_stream` 检测到取消后裸 `return`，不产任何 chunk | `app/llm/base_service.py:424` | 上层把「零 chunk」当空回答 → 按空响应重试 2 次（"2 分钟"的另一半） |
| D4 | 5s 看门狗到期调 `clearCompleted` → `abortController.abort()` + `pollSignal.aborted=true` | `chatStreamStore.settleCancelByDb` | **取消终态帧唯一通道就是这条 SSE，帧未到就 abort → 帧永远进不来**（"前端无反应"真凶） |
| D5 | `onComplete` 终态守卫只要 status 是终态就一律 `return` | `chatStreamTransport.broadcastHandlers.onComplete` | 帧侥幸到达也被吞，`settleCancelByFrame` 不执行、`complete` 事件不投递 |

**判定**：不是单点分支写错，而是「机制不足（D1/D2）+ 三处终态与通道处理写错（D3/D4/D5）」，横跨 UI→store→transport→API→task→agent→LLM→SSE 回程八层，单点修不动。

### 4.3 看门狗行为对照

| 项 | 改造前 | 改造后 |
|----|--------|--------|
| 到点动作 | 读 DB → 落 status → **`clearCompleted()`（abort + `pollSignal.aborted=true`）** | 读 DB → 落 status + 清 `pendingMessage`，**不碰连接** |
| 通道 | 被自己掐断 | 保持通畅，帧到达后由 `settleCancelByFrame` 释放 |
| 资源释放 | 看门狗超时立即释放 | 帧到达时释放；帧永不到则由既有 EOF / 60s 空闲超时收尾 |

### 4.4 LLM 层取消片段（D3 修复）

`request_stream` 检测到 `_cancelled` 时由裸 `return` 改为 `yield create_cancelled_chunk(self.llm_model)`（`app/llm/core.py:127`，`stream_error_type="cancelled"`）。
链路：`llm_call` 的 `stream_error` 分支 → `error_type=cancelled` → `handle_answer.py:111` 走 `err_type == "cancelled"` 分支 → `FinalStep(outcome="cancelled", cancel_source=...)` → `react_dispatch` 置 CANCELLED。

**与 ④ 的关系（不双发）**：④ 一旦注入 `CancelledError`，agent 协程立即在 await 点终止，**不会再走到 LLM 调用链**；本段是「agent 未被 cancel（如未登记句柄的老路径）」时的兜底。两条路径都在同一协程内串行，互斥。

## 五、终态单生产者规则

| 生产者 | 触发条件 | 是否落库 | 备注 |
|--------|----------|----------|------|
| `agent_runner` finally 守卫 | agent 协程终止（正常/异常/取消） | 是（`_publish` + `_persist_final`） | **唯一权威生产者** |
| `task_cancel_check_and_yield` 合成 | `check_cancelled=true` **且** `agent_task` 为 None 或已 done **且** `buffer.event_log` 内无 `type=final` | 否（只发 SSE） | 消费侧兜底，防"任务已取消但流无终态" |

判定顺序（`task_runtime.py`）：

1. 未取消 → `None`（不做任何扫描）。
2. 已取消且 `buffer.event_log` 已含 `type=final` → `None`（**R4 修复**：真实终态已在缓冲，继续转发即可，合成+`return` 会截断它后面的 `final_stats`）。
3. 已取消且 `agent_task` 仍存活 → `None`（等 agent 的唯一终态，防重复）。
4. 其余（agent 未登记或已 done 且缓冲无终态）→ 合成并在调用方 `return` 收尾。

**为什么必须单生产者**：合成帧不落库，若与 agent 的终态同时出现，会出现「DB 一条、SSE 两条」，且前端可能收到两个终态。

**R4 的判据为什么用「事件类型」而不是 seq/offset**：真实终态一旦产出，本连接后续必然转发到它；重连（`after_seq>0`）时更早的 `final` 已消费过，缓冲里若仍有该 `final` 说明它就是尚未转发的真实终态。用类型判据不引入额外状态，也不需要贯穿 seq 语义。扫描只在取消分支做（低频事件），不构成逐帧开销。

## 七、三堂会审

### 7.1 合规审查（十大规范）

| 规范 | 结论 | 依据 |
|------|------|------|
| SRP 单一职责 | 合规 | `settleCancelByDb` 只落状态；`settleCancelByFrame` 只释放资源；终态生产者收敛为 1 |
| DRY 不重复 | 合规（改善） | 两处内联 `getSnapshot().status` 收敛为一个 `streamStatus`；后端合成终态与 agent 终态不再并行 |
| KISS-DIRECT | 合规 | `cancel_task` 直线：取句柄 → `cancel()` → 由 runner 收尾，无中间层、无透传函数 |
| SLAP 同抽象层 | 合规 | `useChatStreaming` 只做快照透传，不掺业务判断 |
| YAGNI | 合规 | 未新增接口/状态；`status` 是既有快照字段透传；`llm_call` 的两处过度设计已撤回 |
| 禁止 backward | 合规 | `RightViewer`/`TaskInfoBar` 的 `storeStatus` 已由可选改**必填**，不留"不传则行为不变"垫片 |
| OCP / LSP / ISP | 合规 | 无继承体系改动；`status` 属"流式状态"职责范围内 |
| 复用优先 | 合规 | 复用 `useTaskInfo` 既有第 5 参、复用 Store 快照，未重造 |

**边界判定（留档，非违规）**：

1. `settleCancelByFrame` 保留了 `cancelFrameTimer !== null` 分支：不是兼容垫片，而是「帧先于 5s 到达」的必要路径——此刻 `status` 仍是 `active`，只能靠 timer 识别"取消在等"。删掉它会让快速取消路径不释放资源。
2. `task_cancel_check_and_yield` 的合成分支保留：它覆盖「agent 未登记句柄 / 已结束且缓冲无终态」两种情形，删掉会使这些路径失去终态兜底。R4 修复后该分支多了「缓冲已有真实 `final` 则不合成」的前置判据，属加固而非新增抽象。
3. `useTaskInfo` 第 5 参仍是 `storeStatus?: string`（既有契约，TaskInfoBar/RightViewer 是本轮才收紧到必填）。如后续统一，可一并收紧。

**风格提醒**：本轮新增注释 3 处偏长（4~6 行）。判断依据：两个文件的既有注释本就 8~10 行，压到 1~2 行会丢掉"为什么不能 abort"这类反直觉依据。若要求一律精简，可另行处理。

### 7.2 合理审查（是否最优雅）

| 检查项 | 结论 |
|--------|------|
| 是否引入注册表滥用 | 否。`set_agent_task` 只是把已有协程句柄登记到既有 `running_tasks` 字典的一个键，无新抽象、无新模块 |
| 调用链是否绕 | 否。取消只有一条主链：`cancel_task → agent_task.cancel → CancelledError → finally → final` |
| 是否有透传函数 | 否 |
| 是否有双重解析 | 否 |
| 是否有循环依赖 | 否（`task_runtime` 不 import `agent` 具体类型，只 `getattr`） |
| 是否提前落终态 | 否。`stop()` 成功后**不**写 `status='cancelled'`，避免与帧/DB 三处口径打架 |
| 释放时机是否正确 | 是。`clearCompleted` 内含 abort，只有在帧已到手（`settleCancelByFrame`）时才安全 |

**唯一可再优化点**：`task_cancel_check_and_yield` 的合成分支与新主链并存，属"双来源"。当前靠 `done()` + 「缓冲是否已有 `final`」双判据切换，是可接受的兜底；若将来确认所有入口都登记了 `agent_task`，可整段删除。

### 7.4 R4 修复的三堂会审追加（v1.1）

| 审查 | 结论 |
|------|------|
| 合规 | 合规。`task_cancel_check_and_yield` 仍是"取消检查"单一职责（多了一个"是否已有终态"的输入判据，仍属同一职责：要不要由我补终态）；`task_buffer` 复用既有 `StreamBuffer` 类型，无新抽象（YAGNI）；未留"不传 buffer 则行为不变"的可选参数垫片（禁止 backward），调用点唯一，直接改签名 |
| 合理 | 判据用事件类型而非 seq/offset，属最直白写法；扫描只发生在取消分支（低频），无逐帧开销；不引入惰性缓存、不做提前剪枝（缓冲本身是必要的，取消发生时长度受任务步数上限约束） |
| 关联 | 修复点在消费侧，不动 `agent_runner` 终态生产；`stream_reader` 的 `after_seq` 语义未受影响；合成路径仅在"agent 已结束且缓冲无终态"时仍会 `return`，这正是它该覆盖的兜底场景 |

### 7.3 关联审查（上下游退化点）

| 检查项 | 结论 |
|--------|------|
| 是否改善既有缺陷 | 是。原先取消后 agent 的 `final_stats` 会被合成终态截断（合成后 `return`）；本改动使 agent 仍在跑时不再合成，真实 `final` + `final_stats` 可完整下发 |
| DB 与 SSE 是否同源 | 是。终态由 `agent_runner` 一次 `_publish` + `_persist_final` 产出 |
| 重连/续传是否受影响 | 否。`stream_reader(after_seq)` 逻辑未动，`final` 仍在 `_SSE_FORWARD_TYPES` |
| 其它取消来源是否受影响 | `session_deleted`（`session_service.py:282/299`）同样走 `cancel_task`，自动获得任务级取消能力 |
| 前端自然完成路径是否被改变 | 否。`onComplete` 放行条件限定 `outcome==='cancelled' && status==='cancelled'`；`settleCancelByFrame` 对非 cancelled 状态仍按原逻辑不释放 |
| 是否有能力后退 | 有 3 处，见第八章（均为取舍，非缺陷） |

## 九、验证方法（三锚点）

| 锚点 | 位置 | 期望 |
|------|------|------|
| A1 取消请求 | `[TaskControl] 取消任务 {id} source=user_requested` | 用户点击后立即出现 |
| A2 agent 收敛 | `[Runner] 任务 {id} 被取消(CancelledError)` + `[Runner] 守卫兜底补发取消终态(...)` + `[Runner] done置位` | A1 之后 **<1s** |
| A3 SSE 送达 | `[SSE] reader退出(task={id}, ... 含 final_stats=true)` + 前端 console 收到 `final` 帧 | A2 之后立即，且 `final_stats=true` |

**判定**：A2−A1 < 1s 且 A3 存在 → 通过；A3 缺失或 `final_stats=false` → 不算通过（说明终态被截断）。

**R4 专用补充判定**：若 A3 的帧里 `outcome=cancelled` 且 `final_stats=false`，再查后端日志有无 `[CancelCheck] 任务 {id} 已有真实终态帧, 不合成(避免截断 final_stats)`。有 → 说明守卫按设计生效；随后跟随的 `final_stats` 帧若出现即通过。仍无 → R4 未覆盖到位。

**失败时的定位顺序**：A1 有 A2 无 → 看 `[Runner]` 是否有 `CancelledError`（`task.cancel()` 未命中协程）；A2 有 A3 无 → 看 SSE 侧 `[SSE] reader退出` 与前端 transport `onComplete` 守卫；A3 有 `final_stats=false` → 看是否走上 R4 所述路径。

## 十一、压缩/重试场景可取消性矩阵 与 三处收尾缺陷修复（v1.2）

### 11.1 逐场景可取消性（代码路径结论，**未经真实链路验证**）

| 场景 | 能否立即取消 | 实际路径 |
|------|--------------|----------|
| 压缩 LLM **调用前** | 能，且不会发起摘要请求 | `start_step.py:422-429`（全量）/ `549-551`（增量）`check_cancelled` 命中即 `return ""` → `react_loop.py:198-201` `_terminate_cancelled` 产终态 |
| 压缩 LLM **调用中** | 能，**立即打断**（旧机制须等摘要 30~60s 跑完） | `cancel_task` → `agent_task.cancel()` → `call_llm_text_task` 的 await 抛 `CancelledError`（`llm_call.py:412` 只 `except Exception`，不吞）→ 直抵 `agent_runner.py:668` |
| 压缩 LLM **调用后** | 能 | `start_step.py:434-436` / `557-559` 丢弃摘要结果 → `react_loop.py:198-201` 出终态 |
| **L1**（HTTP/provider）退避中 | 能 | `base_service.py:623-627` 的 `asyncio.sleep` 被任务取消直接打断（`CancelledError` 不是 `TimeoutError`，不被该处 `except` 吞） |

| 请求刚进来、`bg_task` 尚未创建（`resolve_refs`/建 agent 阶段） | 能，但只是"落标记" | 无协程可 cancel；压缩前的 `check_cancelled` 会阻止其调 LLM，装配后仍出终态 |

### 11.3 三处缺陷与修复（v1.2）

| # | 缺陷（现象） | 病根 | 修复 |
|---|--------------|------|------|
| 1 | 重试中/压缩中取消后，位4 仍挂"重试 2/3 等 1 秒…""摘要中"转圈 | `useTaskInfo.ts` 只在 `badge === 'completed'` 清 `candidates`；取消时这些过程事件的 `done` 帧随 agent 协程被打断而永不到达 | 清空条件加 `badge === 'cancelled'`（取消与成功完成同语义：任务已终结，位4 不留过程态） |
| 2 | 二次取消打断 `agent_runner` finally 收尾（R6） | `cancel_task` 每次都 `agent_task.cancel()`，`set_cancelled` 不判重 | `claim_agent_task_for_cancel` 原子领取"首次打断权"，首次返回句柄、其后恒 `None`；`cancel_task` 只在非 `None` 时 cancel，否则仅落标记并记日志 |
| 3 | 终态第二行显示"取消来源: user_requested"（英文枚举直出） | 后端 `CANCEL_SOURCE_TERMINAL_TEXT` 只服务 `response` 正文，第二行走裸键 | 前端 `CANCEL_SOURCE_TEXT`：`user_requested`→用户取消、`client_disconnect_timeout`→连接中断超时、`config_limit`→达到最大步数限制、`status_inconsistency`→执行状态异常、`orchestrator_error`→服务内部异常；未知键原样显示 |

### 11.4 v1.2 三堂会审

| 审查 | 结论 |
|------|------|
| 合规（SRP） | 合规。#2 的"是否该打断协程"判定归 registry（状态持有者），`cancel_task` 只做动作，职责不混 |
| 合规（DRY / 消除重复） | 合规。#3 的 5 条中文映射与后端 `CANCEL_SOURCE_TERMINAL_TEXT` 是"短句 vs 标签"两套文案（后端是整句终态描述，前端是来源标签），语义不同不强行共用；映射表集中一处，不在渲染处内联三元 |
| 合规（KISS-DIRECT） | 合规。#2 一个函数一次领取，无中间层、无透传函数；#1 只是判据加一个或项 |
| 合规（YAGNI / 禁止 backward） | 合规。未新增可选参数、未留"不传则行为不变"垫片；未知来源键原样显示属兜底而非兼容分支 |
| 合理 | #1 与 completed 同语义，最直白；#2 用"首次实际领取"而非 `task["cancelled"]` 作判据（后者可能在协程登记前已置位，会丢唯一一次打断机会）；#3 查表 O(1) |
| 关联 | #1 只影响位4 候选集，不动徽标与事件列表；#2 不改 `set_cancelled` 语义（标记照样落，取消仍幂等终止），`task_cancel_check_and_yield` 兜底判据不变；#3 只改显示串，`response` 首行文案与后端翻译链零改动 |
