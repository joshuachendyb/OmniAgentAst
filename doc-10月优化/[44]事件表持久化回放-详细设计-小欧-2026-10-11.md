## 二、现状定案（实读本地代码）

### 2.1 前端事件列表怎么来的

`useTaskInfo.ts` 的 `for (const s of steps)` 遍历派生 `processEvents`，
再由 `TaskInfoBar.tsx:199-242` 渲染进 `eventsTimeline`，
挂在 `TaskInfoBar.tsx:452-484` 的 `FloatingEntry`（点「事件 N」胶囊才弹出）。

**历史任务回放时，`steps` 来自 `chat_task_steps`**，
而多数事件类型本就不落 `chat_task_steps`，所以历史态事件列表**基本是空的**。

### 2.2 历史数据走 `detail` 通道，不是 `frames`

`TaskInfoBar.tsx:146`：

```js
const info = useTaskInfo(steps, frames, detail, liveError, storeStatus);
```

- `frames: TaskMetaFrames` —— 装 SSE 实时帧（`startInfo`/`finalStats`/…）
- `detail: TaskDetail` —— 装历史 REST 数据（`getTaskDetail` 返回）

**既有范式**见 `StaticStatsBlock.tsx:92`：`finalStats?.X ?? detail?.X`
（实时优先、历史兜底）。本方案的历史快照走 `detail`。

> ⚠️ 前四版把快照塞进 `frames` 是错的 —— `frames` 是实时通道，历史态它不承载 REST 数据。

### 2.3 现有资产（复用优先）

| 资产 | 位置 | 复用 |
|------|------|------|
| JSON 列先例 | `chat_tasks.artifacts TEXT DEFAULT '[]'` | 新列照抄形态 |
| 幂等迁移器 | `_ensure_column(conn, 表, 列, 定义)` | 已跑 6 次，同款调用 |
| 端点先例 | `task_queries.py:51 @router.post("/tasks/{task_id}/rollback")` | 新端点同文件同风格 |
| 历史数据通道 | `useTaskInfo` 第三参 `detail` | **无需加参数** |
| 浮层交互 | `TaskInfoBar.tsx:452-484 FloatingEntry` | **零改动** |
| 事件条数上限 | `useTaskInfo` `slice(-20)` | 前后端同限 20 |
| `EVENT_ICON_MAP` | `infoMaps.tsx:97` | 直接用 |

## 三、方案

### 3.1 为什么由前端送（这是前四版最大的错）

若由后端收集，后端必须自行判断「哪些帧会被显示」——
**而这个判断在前端 `useTaskInfo` 的 case 分支里**。
后端复制一份就是**第二份显示规则**，两份必然分叉；且后端无从知道哪些帧
最终产出了事件（如 `SSE_ONLY_TYPES` 含 `chunk`/`thought-start`/`usage`
三个在 `useTaskInfo` 里无 case、永远不显示的类型，回填它们违反 N1）。

前端送则**由构造保证**「显示什么就存什么」，后端零判断、零清单。

### 3.2 存什么

存 `ProcessEvent` 本体：`{kind, text, time}`。

**不存原始帧**（上一版的 `{type, step, content, timestamp, reject_type, tool_name}`
作废）—— 回填的既然是事件列表，存的就是列表条目；
好处是历史回放**直接渲染、不重走派生逻辑**，实时与历史文案天然逐字相同。

### 3.3 三个关键决策

**决策1：数据源 = `processEvents`（前端）**，见 3.1。

**决策2：final 时写一次，失败即失败。**
中断不写 —— 北京老陈：「回填失败就失败，不紧要」。
风险 R12 已接受。

**决策3：历史走 `detail`，不碰 `frames`。** 见 2.2。


#### ⑤ `frontend/src/features/chat/hooks/useTaskInfo.ts`

**⑤a** 返回值附带快照（供调用方回传），**全链路唯一一处过滤**：

```ts
// 2026-10-11 小欧 - 事件列表快照外送(北京老陈令 N3「heart 可以不需要」):
//   排除 heartbeat 是全链路唯一过滤, 其余事件类型一律保留, 不做任何类型判断。
processEventsSnapshot: processEvents.filter((e) => e.kind !== 'heartbeat'),
```

**⑤b** 历史合并 —— 走第三参 `detail`（现成，无需加参数）：

```ts
// 历史任务: 用回传的快照, 直接铺入, 不重走 steps 派生(快照已是成品, 见 3.2)。
// ⚠️ 必须在本 switch 之前、只 push 不进 switch —— 见 ⑤c。
if (detail?.process_events?.length) {
    for (const e of detail.process_events) processEvents.push(e);
}
```

> 快照在发送时即已按时间递增（`processEvents` 本就有序），历史态只有这一个来源，
> 不存在两源交错，**无需排序**。
> 前四版基于「后端收集」的「两工序（归一 + 排序）」**随该方案作废**。

**⑤c** badge 污染防护（**高危，必看**）：

`useTaskInfo` 的 switch 每个 case 都写 `badge`
（`case 'paused': badge='paused'` / `case 'final': badge='completed'` …）。
⑤b 的合并**只能在 switch 之前、只 push 不进 switch** ——
否则一个已完成任务会被其历史里的 `paused` 覆写成「已暂停」。

#### ⑥ `frontend/src/features/chat/components/taskinfo/TaskInfoBar.tsx` —— final 时回传

在 `final` 帧到达处调用一次（复用既有 `type==='final'` 判据）：

```ts
// 2026-10-11 小欧 - 事件列表回填(北京老陈令 N2「final 的时候回填」)。
//   失败只记日志不回滚, 不得打断任务收尾。
```

**幂等**：同一 task 只发一次（ref 标记），避免重渲染重复 POST。

## 七、三堂会审自查（小欧 2026-10-11 09:48:33）

### 7.1 合规检查

| 规范 | 结论 |
|------|------|
| SRP | 端点只收只存；前端只在 final 时调一次；不改 `useTaskInfo` 既有派生职责 |
| DRY | 列形态抄 `artifacts`；迁移抄 `_ensure_column`；端点抄 `rollback`；历史走既有 `detail` 通道，**零新增通道** |
| KISS-DIRECT | 一条直线：`processEvents → final 时 POST → 存列 → 历史 detail 读回 → 直接渲染`，无中间层、无派生重跑 |
| SLAP | 前端只在 final 边界触发，不侵入 `useTaskInfo` 的 steps 派生逻辑 |
| YAGNI | 不建新表、不加索引、不加显示开关、不做类型白名单、**不为任何类型写特例** |
| 禁止 backward | 无兼容分支，旧数据靠 `DEFAULT '[]'` 兜底 |
| OCP | 新增事件类型无需改本方案 —— 它自动出现在 `processEvents` 里，自动被回传 |
| 复用优先 | 7 项既有资产全部复用（2.3），零新建轮子 |
| 关联逻辑 | 已核 `badge` 状态机 / `EVENT_ICON_MAP` / `FloatingEntry` / `M_SKIP` / `isBusinessStep` 五处 |
| 编辑历史 | 集中文件头，最新条目置旧条目之后 |

### 7.2 合理检查

- **为何前端送而非后端收**：见 3.1，这是本设计成立的根本。
- **为何存成品条目而非原始帧**：回填的是事件列表，存成品即免掉历史侧重跑派生，实时与历史文案零漂移。
- **为何历史无需排序**：快照发送时已有序，历史只有单一来源。
- **为何不校验 `kind` 合法性**：送什么存什么（N1），后端零类型知识。
