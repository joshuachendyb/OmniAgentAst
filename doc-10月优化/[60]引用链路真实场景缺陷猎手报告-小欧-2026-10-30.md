## 四、逐条详述

### 4.1 R1-2 预检在途删掉的引用仍随本条上行

- **位置**：`ChatInput.tsx:284-305`（`precheckOrBlock`）→ `:325`（`refsToSend` 取自 `precheckOrBlock` 返回值）→ `:354-357`（`onSend(..., {refs: refsToSend})`）。
- **触发**：点发送 → `precheckRefs` 走 `stat`（真实网络，慢盘/慢网下可达数百毫秒）→ 该窗口内点 chip 的 ×。
- **根因**：`precheckRefs(refs)` 收到的是**点击瞬间**的数组快照；返回后 `setAll(checked)` 用它整体覆盖本地 `refs`，同时 `refsToSend = checked` 也取这份快照。用户此间的删除既没进快照、也被 `setAll` 抹掉。
- **后果**：本条 `refs` 里仍有被删条目 → 后端按 path 读盘 → 注入 prompt。**用户明确删掉的敏感/无关文件仍被模型看到。**
- **证据**：`expected [ 'keep.md', 'gone.md' ] to deeply equal [ 'keep.md' ]`。

### 4.2 R2-1 预检在途新加的引用被覆盖

- 同一处 `setAll(checked)` 的另一个方向：该窗口内新加的 `late.md` 不在快照里 → `setAll` 把它抹掉，chip 消失且不随本条上行。
- **证据**：`expected null not to be null`（`expect(screen.queryByText('late.md')).not.toBeNull()`）。
- 与 4.1 同根同源，但是两个相反方向的用户可见后果（多发 / 漏发），故分列。

### 4.3 R3-1 `@` 补全占位被删除后复活

- **位置**：`ChatInput.tsx:542-566`。先 `add({pending:true})` 占位，再 `await probeRef(...)`，无条件 `add({...pending:false})`。
- **根因**：`add` 走 `mergeIncoming` → `mergeRefs` 按 `path|range` 原地替换/追加，**不校验该条目是否已被用户删除**。
- **后果**：删除按钮重新出现，用户重复操作；若用户已改主意，还会误以为引用仍生效。
- **证据**：`expected <button type="button"> to be null`。

### 4.4 S1-1 阻断后叠加"空响应"假错误

- **位置**：后端 `stream_orchestrator.py:849-854`（先 `yield create_refs_notice_event` 再 `yield create_error_response("refs_blocked")`，后者**不带 `seq`**）；前端 `chatStreamTransport.ts:689`（以 `s.lastSeq >= 0` 判"正常结束"）→ `:714-725`（否则走空流终态并发 `empty_response`）。
- **根因**：错误帧无 `seq` → 前端 seq 守卫不推进 `lastSeq`（仍 -1）→ EOF 被判"空流" → 补发传输层错误。
- **后果**：一次阻断弹两条错误（第二条"未收到任何数据"纯属误导），并伴随 `status=failed` 与终态误判。
- **证据**：`expected [ 'refs_blocked', 'empty_response' ] to deeply equal [ 'refs_blocked' ]`。
- **修复方向**（未实施）：`create_error_response` 与其他事件同一载体（带 `seq`），或前端以"已收到 `from_backend` 错误帧"为终态判据之一。

### 4.5 S4-1 重建 chip 时抹掉刚下发的回执

- **位置**：`chatStreamStore.ts:867-877`，`restoreSentRefs` 在重建 chips 后调用 `refNoticeStore.clear()`。
- **根因**：真实帧序是 `refs_notice`（点名 missing，warn/error）→ `error(refs_blocked)`；前端先 `setMap` 落态，紧接着 `restoreSentRefs` 清空 → 刚重建的 chip 查不到回执 → `chipStateOf` 返回 `idle`。
- **后果**：4.8「对应 chip 标红」失效；用户看到一排常规 chip + 一句 toast，看不出哪条坏了。
- **证据**：`expected undefined to be truthy`（`refNoticeStore.getSnapshot().get('gone.md')` 为 `undefined`）。

### 4.6 R5-1 `MAX_REFS` 前端实际不生效

- **位置**：`features/refs/store.ts:113-123`。判据是 `queue.length >= MAX_REFS`，但 `queue` 是"待 `takeAll()` 的投递队列"，`useComposerRefs` 每次渲染都会 `takeAll()` 清空它 → 计数恒为 0/1。
- **后果**：真源（已入队 chip 数）从未被检查；第 21 条顺利入队，`refs` 上行 21 条 → 后端 `models.py:68` `max_length=MAX_REFS` → 422。用户得到的是通用请求错误，而不是 `refLimitText()` 的"一次最多引用 20 项"（`ChatInput.tsx:536` 的入口限制用的是另一份 `refs.length`，只覆盖 `@` 补全一条入口）。
- **证据**：`expected 21 to be less than or equal to 20`。

### 4.7 R6-1 阻断后草稿丢失

- **位置**：`ChatInput.tsx:347-349`（`backup = draft` 后 `setDraft('')`）与 `:369-373`（`catch` 才 `setDraft(backup)`）。
- **根因**：`refs_blocked` 走 SSE 事件链路，`onSend`/`sendMessage` **正常 resolve**，`catch` 永不进 → 草稿不回填。
- **后果**：违反 4.8「阻断时草稿保留」；用户被提示"请移除后重发"，正文却已清空。
- **证据**：`expected '' to be '请看看这个文件'`。

### 4.8 R7-1 阻断后 `loading` 不复位

- **位置**：`useChatCallbacks.ts:604-614`。`errorObj.from_backend === true` 时只清 `streamingContentRef` 与指纹 Set 后 `return`，跳过尾部的 `setLoading(false)` 与计时器清理。
- **后果**：`refs_blocked` 后输入框永久"正在提交，请稍候"（`InputCore` 的 `executingHint`），发送被禁；只有刷新页面才能继续。
- **证据**：`expected true to be false`。

### 4.9 R9-1/R9-2 chip 回执文案缺 detail/reason

- **位置**：`features/refs/notice.ts:66-72`（`chipStateText` 只按 5 态给固定文案）；`ChatInput.tsx:610-648`（chip 只放 `label` + 状态文案，`title` 只有 path）；`NoticeItem`（`notice.ts:30-35`）的 `detail`/`reason` 无任何消费方。
- **设计契约**：4.9 状态机表 —— `degraded` = "黄标 + **省略行数**"；`dropped` = "红标 + **原因**"。
- **后果**：后端为每条回执算了 `detail`（"已省略 1234 行"）与 `reason`（missing/out_of_root/range_out/compressed/rejected…），用户端只剩泛化四字文案，无法判断"文件不存在"还是"整批被拒"、也无法知道省略了多少。
- **证据**：
  - `expected 'big.md（已省略）' to contain '1234'`
  - `expected 'gone.md（已丢弃）×gone.md' to match /文件不存在|missing/`（`textContent` 与 `title` 两处都没有原因）

### 4.10 B1 行区间引用绕过单条上限

- **位置**：`backend/app/services/refs/resolver.py:113-124`。区间分支 `_read_blocks(...)` 后**直接** `return ResolvedRef(ref={**ref, "content": content}, ...)`，不经 `clip_text` 复核；而整份分支（`:146`）有 `clip_text(content, limits.read_max_bytes)`，其注释明确写"统一收口"。
- **设计契约**：4.6.2「单条有界（读取期）」；4.6.4「单条超上限 → resolved（头尾摘录） + 回执 `truncated`」。
- **后果**：用户在文件页框选一段长区间（本项目里等于"全选一个大文件"）→ 单条 56,000 token（上限 42,428）原样注入 prompt；合计未超 40%，`budget_refs` 也不裁 → 一条引用吃掉 66% 合计预算，且**回执为空**（用户与模型都不知道被截）。
- **证据**：`AssertionError: 区间引用单条 56000 token > 单条上限 42428，且回执=[]`
- 同类后果还有一档：区间更大时（> 拒绝线 127,286 tok）会整批 `rejected`，与"同一文件整份引用能成功摘录"形成不一致——根因同一处，不重复计条。

## 五、已证伪、不计入的候选

| 候选 | 结论 | 依据 |
|------|------|------|
| R4-1「发送后整轮任务期间 chip 未清空 → 下一条重复携带」 | **设计取舍，不计** | [57] 5.4.9（line 2096）明确裁定"`clear()` 保持发送成功即清"，`ChatInput.tsx:364-368` 按 id 精确移除即该裁定的落地；用例 FAIL 只反映"任务期间引用区仍显示"，不发第二条消息不会重复上行 |
| `_start_meta["refs"]` 可能是裁决前的数组 | 证伪 | 注入的是 `_final_refs`（`stream_orchestrator.py:866`），即 `budget_refs` 的返回值 |
| `stat_file` 与读取的 mtime 不同源 → 误报"内容已更新" | 证伪 | 两处都走 `_fmt_time(st.st_mtime)`（`browse_service.py:791`），同源同格式 |
| 同一 path「整份 + 区间」时区间被静默丢弃 | 证伪（按文档） | [57] A13（line 213）明写"整份优先，同 path 的区间条目直接丢弃"，非缺陷 |
| `warn → degraded("已省略")`、`dropped` 仅 error 级 | 证伪（按文档） | [57] 4.8（line 486-487）级别表如此定义 |
| `pickAtItem` 的 `catch` 分支（`ChatInput.tsx:567-569`） | 证伪（不可达） | `probeRef` 内部自捕（`probe.ts:67-74`），永不抛 → YAGNI 死分支，非用户可见缺陷 |
| chip 回执"级别倒挂"（后写覆盖） | 证伪（真实链路不可见） | 入队时 `mergeIncoming` 会 `clearPath`（`useComposerRefs.ts:64-67`），chips 发送成功即按 id 移除，重建只发生在 `refs_blocked`（且该路径本身被 4.5 的 clear 覆盖） |

> 另：**"回执残留（上一轮黄/红标跟到新 chip）"** 曾作为第 10 条候选，核查后**不成立**——`useComposerRefs.mergeIncoming` 在入队时对每条 `path` 调 `refNoticeStore.clearPath`，store 投递与 `@` 补全两条入口共用该函数，用户"删掉再引用"不会继承旧标。
