## 一、需求背景

### 1.1 现状问题

会话页面（ChatPage）的左侧和右侧区域使用固定的 flex 比例分配：
- 左列：`flex: '1 1 25%'`（约 25%）
- 右列：`flex: '1 1 75%'`（约 75%）

**问题**：
1. 用户无法根据内容调整面板宽度
2. 固定比例不适配不同屏幕尺寸
3. 左侧任务列表可能需要更宽空间显示

### 1.2 优化目标

1. 中间的线可以拖动改变两个区域的宽度
2. 左侧的宽度默认为 1/3
3. 不违反代码 10 大规范，全局逻辑代码最佳

---

## 二、技术方案

### 2.1 设计原则（10 大规范）

| 规范 | 应用 |
|------|------|
| **SRP** | SplitPane 组件只负责分割面板，不负责内容渲染 |
| **DRY** | 拖动逻辑只写一次，复用 Files 页的拖动模式 |
| **KISS-DIRECT** | 直接使用鼠标事件，不引入复杂抽象 |
| **SLAP** | SplitPane 是 UI 层，不混入业务逻辑 |
| **YAGNI** | 不引入第三方库，不预设未来需求 |
| **禁止 backward** | 不使用向后兼容的做法 |

### 2.2 架构设计

```
SessionLayout（布局容器）
  └── SplitPane（可拖动分割面板）
        ├── 左侧面板（任务列表等）
        ├── 分割线（可拖动）
        └── 右侧面板（查看器等）
```

### 2.3 核心实现

#### SplitPane 组件

**职责**：
- 管理左右面板的宽度拖动逻辑
- 提供键盘可访问性（←/→）
- 提供 ARIA 属性（role="separator"）

**状态管理**：
- `leftW`：左侧面板宽度（像素）
- 初始值：容器宽度的 1/3

**拖动逻辑**：
- `mousedown`：记录初始位置，添加 mousemove/mouseup 监听
- `mousemove`：计算新宽度，更新状态
- `mouseup`：清理监听器

**边界约束**：
- 最小宽度：200px
- 最大宽度：容器宽度的 80%（保留右侧最小空间）

#### SessionLayout 修改

**原代码**：
```tsx
<div style={{ flex: '1 1 25%', minWidth: 200, maxWidth: 560 }}>
  {renderSlot(panels, 'left')}
</div>
<div style={{ flex: '1 1 75%' }}>
  {renderSlot(panels, 'right')}
</div>
```

**新代码**：
```tsx
<SplitPane
  left={renderSlot(panels, 'left')}
  right={renderSlot(panels, 'right')}
/>
```

## 六、v1.1 宽度优化（2026-10-27 08:42）

### 6.1 问题反馈

用户反馈：左侧菜单栏宽度没有明显变窄，给右侧会话页面留的空间不够。

### 6.2 原因分析

1. **初始渲染问题**：`useEffect` 在容器渲染后执行，但 `container.offsetWidth` 可能为 0，导致宽度计算错误
2. **固定比例问题**：原来固定 1/3（约 33%），在 1440px 屏幕上约 480px，过宽
3. **状态无关**：右侧折叠/展开时，左侧宽度没有区别

### 6.3 优化方案

#### SplitPane 组件

> **实际实现（v1.3 修正）**：经用户确认，**不根据 rightOpen 调整默认宽度**，左侧固定为 `SPLIT_LEFT_DEFAULT_RATIO`（30%）。v1.1 原描述的"折叠 240px/展开 280px"**未实现且非需求**，此处修正为实际行为。

| 状态 | v1.0 宽度 | 实际实现宽度 | 变化 |
|------|-----------|-----------|------|
| 右侧折叠 | 480px（1/3） | 30%（固定，不区分） | 约 -10% |
| 右侧展开 | 480px（1/3） | 30%（固定，不区分） | 约 -10% |

**核心逻辑**（实际代码 `SplitPane.tsx`）：
```typescript
const getInitialWidth = (containerW: number): number => {
  const stored = readStoredWidth();
  if (stored !== null) {
    const maxW = Math.round(containerW * SPLIT_LEFT_MAX_RATIO);
    return Math.min(stored, maxW);
  }
  if (containerW === 0) {
    return 300;  // 容器未布局完成时返回固定偏好值
  }
  return Math.round(containerW * SPLIT_LEFT_DEFAULT_RATIO);  // 固定 30%
};
```

#### TaskListPanel 紧凑化

| 元信息行 gap | 8px | 6px | -25% |

## 七、v1.2 持久化与配置化（2026-10-27 09:08）

### 7.1 需求背景

用户反馈两个问题：
1. **拖动后宽度不记忆**：刷新页面/重启应用后回到默认 30%，用户改的宽度白费
2. **默认宽度硬编码在组件里**：想改默认值（如从 30% 改 40%）必须改组件源码

### 7.2 解决方案

#### ① localStorage 持久化

- **键名**：`omni.split.v1.leftWidth`（带版本号，未来可平滑迁移）
- **写入时机**：
  - 拖动 mouseup 时（仅一次，避免 mousemove 高频 IO）
  - 键盘 ←/→ 调整后（键盘事件频率低，无需防抖）
- **读取时机**：组件 useEffect 初始化时，优先读 localStorage，没有才按容器 30% 计算
- **容错**：
  - try/catch 包裹，隐私模式下 localStorage 抛 SecurityError 不崩溃
  - 脏数据校验（非数字/过小值）回退默认
  - 写入失败静默吞掉（偏好存储非阻断项）

#### ② 配置常量化

新建 `constants/layout.ts`，4 个配置项：

| 常量 | 默认值 | 说明 |
|------|--------|------|
| `SPLIT_LEFT_DEFAULT_RATIO` | 0.30 | 默认宽度占容器比例（改这里改默认） |
| `SPLIT_LEFT_MIN_PX` | 180 | 左侧最小宽度（px） |
| `SPLIT_LEFT_MAX_RATIO` | 0.80 | 拖动最大宽度占容器比例 |
| `SPLIT_PREFS_KEY` | `omni.split.v1.leftWidth` | localStorage 键名 |

**改默认宽度**：改 `SPLIT_LEFT_DEFAULT_RATIO` 一个数字，不用碰组件源码。

**配置位置理由**：项目已有 `constants/` 目录（settingsEvents.ts 先例），符合"常量上移中立层"原则，避免跨 feature 反向依赖。

#### ③ 双击设为默认宽度（v1.5 语义修正）

- **触发**：双击分割线
- **行为**：把当前宽度写入 localStorage 设为新默认，宽度保持不跳回
- **用途**：把当前拖到的位置固定为默认宽度（用户实测反馈 2026-10-27，原"重置回30%"语义与期望相反，修正为方案A）
- **提示**：分割线 title 属性 + aria-label 都提示"双击设为默认宽度"

### 7.3 代码结构

```
constants/layout.ts          # 配置常量（唯一定义点）
  └── SplitPane.tsx          # 唯一消费方（全仓 grep 验证）
        ├── readStoredWidth()    # 读 localStorage（含脏数据校验）
        ├── writeStoredWidth()   # 写 localStorage（失败静默）
        ├── clearStoredWidth()   # 已删除（v1.4：双击改为"设为新默认"后无调用点，按 YAGNI 移除）
        └── getInitialWidth()    # 优先 localStorage，否则按容器比例
```
