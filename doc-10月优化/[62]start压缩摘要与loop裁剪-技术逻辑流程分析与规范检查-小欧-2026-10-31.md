## 一、总览

### 1.1 两套机制的分工

| 维度 | start 阶段压缩摘要 | loop 中的裁剪 |
|------|-------------------|---------------|
| 何时跑 | 任务开始、首轮 LLM 调用之前（每任务 1 次） | 每轮 LLM 调用之前（`react_step` 每轮调） |
| 数据源 | `context.previous_messages` / `chain_delta_messages`（跨任务历史） | `message_builder.conversation_history`（本任务实时累积） |
| 手段 | **调 LLM 生成摘要**（语义压缩），把长历史折叠成一段六段式 Markdown | **纯本地丢弃/截断**（零 LLM），按轮滑窗丢旧段 |
| 产物 | `agent._start_summary`（注入为 1 条 assistant 消息）+ 可选尾部 N 轮 | 原地替换 `conversation_history` |
| 失败降级 | 摘要失败 → 注入"已收缩副本"（有损但有界），不阻塞主链 | 任何异常 → 保留原历史，跳过本轮裁剪 |
| 是否可关闭 | `tuning.compaction.start_enabled` | 无独立开关（由阈值天然决定） |

一句话：**start 管"跨任务带来的历史太大"（用 LLM 压成语义摘要），loop 管"本任务跑起来后历史还在涨"（用规则丢旧轮）**。两者共用同一批切分原语与同一套 token 估算，但**尺子不同**（见 1.3）。

### 1.2 一次任务的全局时序（按代码实际执行顺序）

```
stream_orchestrator 组装 context（load_previous / load_chain_summary）
        ↓
agent_runner.run_agent_in_background
        ↓  _build_history_context(db_ops, session_id)            ← 决定"锚点增量 or 全量老路"
        ↓  有锚点: {chain_summary_anchor, chain_delta_messages}
        ↓  无锚点: {previous_messages: 全量}
        ↓
initialize_run_state(agent, task, task_id, context)
        ├─ reset_per_run(): last_total_tokens=None / 冷却复位 / 信号缓存清空 / max_rounds 重读
        ├─ 压缩相关标记全部清零: _start_summary="" / _needs_compact? / _injected_history_msgs=None /
        │  _injected_delta_msgs=None / _pending_chain_summary_cover=None / _summary_tail_extras=None /
        │  _injected_effective_count=0 / _injected_effective_tokens=0 / _compressed_source_tokens=0
        └─ _sys_prompt = _get_system_prompt()；**不建 conversation_history**（2026-10-07 起推迟）
        ↓
run_react_cycle
        ├─ await assemble_start_step(agent, context)     ← 【start 压缩摘要全流程】第 2 章
        ├─ if task_id: _terminate_cancelled(...)         ← 摘要前后被取消 → 立即终态，不发 start 帧
        ├─ init_history(sys_prompt, task, refs)         ← 建 [system, user(task)]
        ├─ inject_history(_build_injected_msgs(agent))  ← 摘要/增量/全量三态注入（system 之后、task 之前）
        ├─ telemetry: history_context 首帧
        ├─ if 本轮新摘要: save_chain_cover_summary(...)  ← 落"覆盖上界任务行"，成为下次锚点
        ├─ publish start(step=0)
        └─ while llm_call_count < max_steps:
              ├─ 取消检查 / wait_for_resume / _flush
              ├─ _process_single_step(agent, chunk_buffer)
              │     ├─ await _absorb_inbox(agent)          ← 先并入插话 user
              │     ├─ if _trim_signal(): trim_history()   ← 【loop 裁剪】第 3 章
              │     ├─ telemetry.on_trim(...)
              │     ├─ messages = prepare_messages_for_llm()  ← 剥离内部标记
              │     ├─ call_llm_with_fallback(...)
              │     └─ usage.total_tokens → last_total_tokens（增量触发基准）
              └─ 循环
```

### 1.3 四把尺（务必分清，误改即引发过裁/误触发）

| 尺名 | 函数/位置 | 公式（缺省值） | 用途 | 体积口径 |
|------|-----------|----------------|------|----------|
| 压缩摘要 limit | `agent_utils.compress_summary_threshold(ctx)` | `int(ctx × 0.5)`（`tuning.compaction.start_limit_ratio`，**限制系数**） | ①start 老路"要不要压" ②增量 B 门"delta 要不要压" | **原文**（`MessageBuilder._estimate_tokens`） |
| conv 判定线 | `agent_utils.conv_threshold(ctx)` | `int(ctx × 0.8)`（`tuning.trim.trigger_ratio`，**调节系数**） | 摘要前窗口闸：判"压缩请求塞不塞得进窗口" | **feed**（`estimate_feed_tokens`） |
| trim 目标线 | `agent_utils.trim_conv_threshold(ctx)` | `int((ctx-20000-30000) × 0.8)` | 摘要前窗口闸：判"裁到哪"；loop"绝对值触发" | 闸内 feed / loop 原文 |
| 队列预算 | `agent_utils.trim_queue_budget(ctx)` | `int((ctx-20000-30000) × 0.8²)` | loop 裁剪"可裁队列能吃多少" | 原文 |

以缺省 `ctx=262144` 为例：`compress limit=131072`、`conv 判定线=209715`、`trim 预算基准=212144`、`trim 目标线=169715`、`队列预算=135772`。因为"目标线 = (窗口-50000)×0.8 < 判定线 = 窗口×0.8"，**裁完必然落在判定线之下**（`agent_utils.conv_threshold` docstring 明示）。

> 术语红线（2026-10-31 北京老陈令）：**0.5 是「限制系数」**（压缩摘要专用），**0.8 是「调节系数」**（loop 裁剪 + conv 判定线）。两者语义不同、不得混用，注释里也已订正。

## 二、start 阶段压缩摘要 — 实现技术逻辑与流程

### 2.1 上游：历史从哪来（`agent_runner._build_history_context`，248-279）

```
if 无 session_id/db_ops/load_previous:  return {}
try:
    _anchor = await db_ops.load_chain_summary()          # 链内最近"非空摘要锚点"任务行
    if _anchor:
        _delta = load_previous(session_id, lower_message_id=_anchor["delta_lower_message_id"])
        return {"chain_summary_anchor": _anchor, "chain_delta_messages": _delta or []}
except: 告警 → 降级
return {"previous_messages": load_previous(session_id)} if _prev else {}
```

要点：
1. **锚点命中只取"锚点之后新增"的 delta**，老历史不再拉、不再全量重压 —— 这是 2026-10-14 linked 增量摘要的设计根基。
2. 锚点查询/增量加载任一步抛异常 → 告警并**退回全量老路**，不让锚点机制反噬主链。
3. 本函数是唯一取数入口（SRP），`start_step` 只消费 `context` 里的三类键：`previous_messages` / `chain_summary_anchor` / `chain_delta_messages`。

### 2.2 入口：`assemble_start_step`（697-747）

顺序**不可乱**（docstring 明示）：

```
① _build_injected_history(agent, context)            → 置 agent._injected_history_msgs（不写 conversation_history）
①' _anchor_done = await _assemble_anchor_delta(...)   → 有锚点走增量；返回 False 表示没走通
    if not _anchor_done:
②      _maybe_compact_injected_history(agent)         → 原文口径判是否超 compress limit，只置 _needs_compact
③      if _needs_compact:
              _compact_attempted = True
              _start_summary = "[本次摘要]: " + await _compact_injected_history(agent)
              if _start_summary:
                  _pending_chain_summary_cover = True
                  _summary_tail_extras = _extract_summary_tail(_injected_history_msgs)
                  _apply_injection_facts(...)
    telemetry.set_injected_context({message_count, estimated_tokens})
④ return _build_start_contract(agent, previous_messages)   → StartStep（无 _start_meta 返 None）
```

注意 `_build_start_contract` 用的是 `context["previous_messages"]`（全量注入历史）做快照，**锚点路径下该键不存在 → message_count=0**（`_assemble_anchor_delta` docstring 已记此边界，telemetry 另走 `_injected_effective_*` 补真实值）。

### 2.3 步骤①：注入历史构建 `_build_injected_history` → `_strip_history_msgs`（270-348）

`_strip_history_msgs(prev, drop_last_user=False)` 的完整规则：

| 输入形态 | 处理 |
|----------|------|
| `prev` 非 list / 空 | 返回 `[]` |
| `role == "tool"` | 只保留 `role/tool_call_id/content`（`name` 有值才带）→ **丢弃一切内部标记** |
| `role == "assistant"` 且 `tool_calls` 为 list | 逐元素 `isinstance(t, dict)` 过滤（非 dict 剥离，防 provider 400）；过滤后非空 → `{role, tool_calls, content}` |
| `role == "assistant"` 且 `tool_calls` 为 dict | 包成单元素列表（容忍单对象） |
| `role == "assistant"` 无可保留 tool_calls | 仅当 `content` 非空才保留为纯正文条 |
| `role == "user"` / `"system"` | 仅当 `content` 非空才保留 |
| `drop_last_user=True` | 丢"最后一条 user"（start 阶段固定传 **False**，防链 1 的 user_input 被误丢 → 实测导致 LLM 不知"继续"指何事） |
| 收尾 | 统一 `remove_dangling_tool_calls(...)`：**双向剪孤儿**（无结果的 assistant(tool_calls)、无调用方的 tool） |

最后一条是 2026-10-30 的实测修复：注入历史全链路（全量/增量 delta）原先**从不**调用 `remove_dangling_tool_calls`（唯一调用点在 trim 分支），畸形 tool_calls 被剥离后其 tool 结果成孤儿直达 provider（实测"注入件 tool 1 条 / 有调用方 0 条"）。现在收口在 `_strip_history_msgs` 末尾，两路同源。

### 2.4 步骤①'：锚点增量四路径决策树

`_assemble_anchor_delta`（531-653）返回 bool：
- `False` = 锚点路径未处理（无锚点摘要）→ 调用方走老路②③；
- `True` = 锚点路径已处理完（下面 ①②③ 之一）。

前置：`anchor_summary = _strip_summary_labels(anchor["summary"])` —— **先剥来源标签**再当正文用，防"往次+本次"双层标签，也防污染喂给 chunked 摘要的"已有摘要"输入。

| 路径 | 触发条件 | LLM | 结果状态 |
|------|----------|-----|----------|
| ① 零增量复用 | `delta_msgs` 为空（剥离后） | 0 次 | `_start_summary="[往次摘要]: ..."`；`_injected_effective_count=1`；notice `done("复用锚点摘要(无增量)")` |
| ② 未超阈值复用 | `MessageBuilder._estimate_tokens(delta_msgs) < compress_summary_threshold(ctx)`（**B 门，原文口径**） | 0 次 | `_start_summary="[往次摘要]: ..."`；`_injected_effective_count=1+len(delta)`；token 按 `[摘要]+delta` 算；notice `done("复用锚点摘要(增量未超阈值)")` |
| ③ 增量压缩 | delta ≥ B 门 | 1 次（`generate_chunked_summary`） | 成功：`_start_summary="[本次摘要]: ..."`、`_injected_delta_msgs=None`（delta 整体已被压进摘要，防冗余+顺序错）、`_pending_chain_summary_cover=True`、`_summary_tail_extras=_extract_summary_tail(delta_msgs)`、`_apply_injection_facts(...)`、notice `done("增量摘要完成(N字)")` |
| ③失败 | 取消/异常/结构校验拒收 → `new_summary=""` | 1 次 | 回退 `"[往次摘要]: 旧摘要" + 全量 delta`；notice `failed("增量摘要失败，回退锚点")` |

路径③的细节分支（顺序即代码顺序）：

1. **阈值估算失败**：`try` 内取 `ctx/threshold/delta_tokens` 抛异常 → `logger.warning` 后**按"超窗"处理**（`_delta_tokens=1, _threshold=0`）→ 继续走 LLM 压缩（宁可多压，不放过超大 delta）。
2. **窗口闸（2026-10-31 新增）**：`delta_msgs = _shrink_before_summary(agent, delta_msgs, "增量")`，**裁后同步回 `agent._injected_delta_msgs`** —— 使失败回退注入的是收缩副本而非原样整段。
3. `agent._compact_attempted = True`（语义 = "确实调了 LLM"，供 telemetry 区分未触发/失败）。
4. **取消前查**：`check_cancelled(task_id)` 为真 → 不打 LLM，日志"跳过摘要(回退复用锚点摘要)"，`new_summary=""`。
5. `log_and_print("开始调 LLM 生成增量摘要: delta N条")` + `_emit_summarizing(agent,"增量",N)`（MetaStep notice，长等待期给前端心跳）。
6. `await generate_chunked_summary(agent, delta_msgs, anchor_summary)`。
7. **取消后查**：命中 → 丢弃结果（`new_summary=""`），"回退复用锚点摘要"。
8. 任何异常 → 告警 + `new_summary=""`。

### 2.5 步骤②③：老路全量 `_maybe_compact_injected_history` + `_compact_injected_history`

#### 2.5.1 判定（351-391）

```
_needs_compact = False
if not get_config().get('tuning.compaction.start_enabled', START_COMPACTION_ENABLED=True): return
history = _injected_history_msgs；空则 return
_threshold = compress_summary_threshold(agent.message_builder.MAX_CONTEXT_TOKENS)   # ctx × 0.5
rough = MessageBuilder._estimate_tokens(history)                                     # 原文口径
if rough > _threshold: _needs_compact = True
```

**口径声明（代码注释与 docstring 双重落字，防后人"统一"）**：本函数用**原文**体积判"要不要压缩"——它关心"历史真实有多大、值不值得压"；"压缩请求塞不塞得进去"由 `_shrink_before_summary` 的 **feed** 口径负责。两把尺**不同是设计**。

#### 2.5.2 生成（460-528）

```
_src = agent._injected_history_msgs or []
_hist_for_summary = [dict(m) for m in _src]        # 逐条浅拷贝：清零原地改 dict，绝不能污染原库
if not _hist_for_summary: _needs_compact=False; return ""
_hist_for_summary = _shrink_before_summary(agent, _hist_for_summary, "全量")   # 窗口闸
try:
    if task_id and await check_cancelled(task_id):   取消前查 → _needs_compact=False; return ""
    log_and_print("开始调 LLM 生成锚定摘要: 历史N条")
    await _emit_summarizing(agent, "全量", N)
    summary_text = await generate_anchored_summary(agent, _hist_for_summary)
    if task_id and await check_cancelled(task_id):   取消后查 → summary_text=""
except Exception: 告警 → summary_text=""
if summary_text:  notice done("摘要完成(N字)")
else:
    notice failed("摘要失败，回退完整历史")
    降级：agent._injected_history_msgs = _hist_for_summary      ← 复用"已收缩历史"，不再二次裁剪
_needs_compact = False
return summary_text
```

**失败降级语义变更（2026-10-31）**：原先是 `split_history_window` 再切一刀 + 二次清零；现在直接复用已经过窗口闸的 `_hist_for_summary`。
- 若判定超线 → 注入的是"阶梯裁到 trim 目标线以内"的副本；
- 若未超线 → `_hist_for_summary` 就是原注入历史的浅拷贝，注入它 == 原"回退完整历史"。

**必须知悉的副作用**：这条降级路径会**替换** `agent._injected_history_msgs`（有损，但保证不撞窗）；后续 `react_loop` 的 `_build_injected_msgs` 在"无摘要"分支返回的正是这份收缩副本。

### 2.6 摘要前窗口闸 `_shrink_before_summary`（408-457）+ 阶梯 `shrink_to_budget`

#### 2.6.1 闸门逻辑（两路共用同一道闸）

```
if not messages: return messages
try:
    _ctx = agent.message_builder.MAX_CONTEXT_TOKENS（缺省 0）
    _ctx_threshold = conv_threshold(_ctx)                 # 判定线 ctx×0.8
    _cur = estimate_feed_tokens(messages)                 # feed 口径（实际喂进去的体积）
    if _cur <= _ctx_threshold:  debug → return messages   # 不裁，零拷贝、零行为变化
    _target = trim_conv_threshold(_ctx)                   # 目标线 (ctx-50000)×0.8
    out = shrink_to_budget(messages, _target,
                           allow_prune=tuning.compaction.summary_prune_tool_output,
                           estimator=estimate_feed_tokens)   # 判/裁/保尾**同一把尺**
    if 裁后仍超: logger.error("...放行并留证") else: logger.info(完成)
    return out
except Exception: warning("降级为原样喂") → return messages   # 裁剪是纯优化，不得影响摘要主链
```

三处必须同传 `estimator`：**门限判定 / 裁剪动作 / 保尾边界**。实测反例已写进注释：预算 8000 时，原文口径只保 6 条/2648 tok，feed 口径应保 14 条/6981 tok —— 混用等于白丢 8 条本可容纳的尾部上下文。

#### 2.6.2 `shrink_to_budget` 五级阶梯（assembler 149-235）

每级动作不同、结果单调变小，**每级后复检，达标立即返回**；全程零 LLM。

| 级 | 动作 | 关键参数 |
|----|------|----------|
| 0 | 入口检查 | 空/`limit<=0` 直接返回副本；已达标 `return messages`（同一对象，零拷贝） |
| 1 | `truncate_oversized_message` | 单条 content > `SPLIT_TURN_MAX_ASSISTANT_CHARS`(4000) → 截头段 4000 + `…[split_turn]`，原文存 `_raw`（`keep_full_raw` 只保留更长者），置 `_truncated=True` |
| 2 | 保首 + 清零（受 `allow_prune` 支配） | 边界 `find_tail_start(messages, preserve_recent_budget(limit), estimator=est)`；"远段"深拷一层后：`compress_long_tool_output(min_release=0, protect_tokens=(500+20)/1.86)` 只压"比保首还长"的（>≈519 字，留 500 字首段），再 `prune_tool_output_keeping_tail(far, len(far))` 把剩余短条清零（`_compressed` 守卫跳过刚压过的） |
| 3 | `truncate_tool_call_args`（**无视 `allow_prune`**） | 旧轮（最后一条 user 之前）保 500 字、当前轮（最后 user 起 / 无 user 时取最后一轮 FC 决策起点）保 4000 字；结构化裁剪 `_fit_args_json` 保证**截后仍是合法 JSON**；原文存 `_args_raw` |
| 4 | `find_tail_start(..., int(limit*0.6), align_turn=True, estimator=est)` → `remove_dangling_tool_calls(前缀 + 尾部)` | 丢远轮，保 60% 预算 |
| 5 | 同上，`ratio=0.25` | 只保最近 1~2 轮 |
| 收尾 | 五级仍超 → `logger.error("五级后仍超 ... 放行并留证")`，返回当前结果 | 不阻塞主链 |

为什么第 3 级排在"丢轮"之前（注释已论证）：截参数**保留全部轮次**，丢轮**丢整段对话**，前者破坏性小得多；且早/中轮巨参数若不先截，第 4/5 级会把那一整轮直接丢掉。为什么第 3 级不受 `allow_prune` 支配：`allow_prune` 是"摘要质量 vs 成本"的偏好开关，第 3 级是"不截就 400"的硬防线，走到这里说明前面各级全空转，再尊重偏好就是拿整个请求换开关。

### 2.7 摘要引擎（`compaction/summary.py`）

#### 2.7.1 feed 构造（单一截断口径）

```

    [{**msg, "content": c} for msg in messages]

generate_chunked_summary(agent, new_block, previous_summary):

    if previous_summary: feed += [assistant: "[往次摘要]: ..."]
    feed += _build_feed(new_block, 2000)
```

- `_SUMMARY_TAIL_USER` 收尾指令是 2026-10-07 的实测修复：注入历史末条是 assistant，feed 以 assistant 收尾构成"半截对话"→ 模型续写而非汇总（六段命中率 16% → 补 user 后 6/6=100%）。

- 全量函数**不做分批**，只截单条 tool；这也是增量路必须补窗口闸的原因（见 2.6）。

#### 2.7.2 结构校验 `_valid_summary_or_empty`（4 条，任一不过即返空串）

## 三、loop 中的裁剪 — 实现技术逻辑与流程

### 3.1 调用点与时序（`react_step.py` 327-341）

```
agent.llm_call_count += 1
await _absorb_inbox(agent)                       # ① 先并入插话 user（在裁剪之前，保证同一轮一致组装）
if agent.message_builder._trim_signal():         # ② 先判信号（写 _trim_signal_result）
    agent.message_builder.trim_history()         # ③ 再执行裁剪（读缓存结果）
agent.telemetry.on_trim(_trimmed_this_round, _trimmed_tokens_this_round)
messages = agent.message_builder.prepare_messages_for_llm()   # ④ 组装 + 剥离标记
...
usage.total_tokens → agent.message_builder.last_total_tokens  # ⑤ 响应回来回填，供下轮增量触发
```

设计要点：
- **信号与动作分离**（2026-10-25）：`_trim_signal` 只算不算；`trim_history` 只读缓存 (`_trim_signal_result`)，两者通过 5 元组传递，避免重复估算。
- `last_total_tokens` 是 **provider 返回的精确 total_tokens**（含 tools schema），只在拿到 usage 时更新；首轮为 `None` → 增量触发天然不成立。
- `reset_per_run()` 会把 `last_total_tokens` 置 None、`_trim_cooldown.mark_compacted()`（复位计数）、`_trim_signal_result=None`，**新任务不继承上一任务的冷却状态**。

### 3.2 信号：`_trim_signal`（532-583）

```
msg_count = len(conversation_history)
_trimmed_this_round = False; _trimmed_tokens_this_round = 0        # 每轮重置
if msg_count <= TRIM_MIN_MESSAGES(5):
    _trim_signal_result = (False, 0, 0, False, False); return False   # 守卫：新任务不裁

rough_current = _estimate_tokens(conversation_history)             # 原文口径：content+tool_calls JSON+reasoning
trim_base     = trim_budget_base(MAX_CONTEXT_TOKENS)               # ctx-20000-30000
delta_trigger = last_total_tokens is not None and (rough_current - last_total_tokens) > _compaction_buffer(20000)
abs_trigger   = rough_current > trim_conv_threshold(MAX_CONTEXT_TOKENS)   # trim_base × 0.8
msg_ceiling   = _max_rounds * 2 + 5                                # 默认 max_rounds=100 → 205
signal        = delta_trigger or abs_trigger or msg_count > msg_ceiling
_trim_signal_result = (signal, rough_current, trim_base, delta_trigger, abs_trigger)
return signal
```

三个触发条件语义：

| # | 条件 | 语义 |
|---|------|------|
| 1 增量 | `本轮粗估 - 上轮精确 > 20000` | "这一轮又涨了 2 万 tok"（未到绝对值也裁） |
| 2 绝对值 | `粗估 > 预算基准×0.8` | 逼近窗口安全网 |
| 3 消息数 | `msg_count > max_rounds×2+5` | 大窗口模型下固定比例形同虚设时的兜底 |
| 守卫 | `msg_count <= 5` | 非 link 任务首几轮（system+task 才 2 条）不评估 |

`msg_count` 是**消息条数**（1 assistant + N tool 算 N+1 条），**不是 ReAct 轮次数、不是 token 数**；link 任务初始 ≈ 1(system)+N(注入)+1(task)，所以守卫不会拦。

### 3.3 执行：`trim_history`（585-677）全分支

```
if _trim_signal_result is None: return
signal, rough_current, trim_base, delta_trigger, abs_trigger = 结果
if not signal: return

# A. 重复触发抑制
if rough_current <= trim_base and not _trim_cooldown.allow(): return
    # 未溢窗：冷却期内直接跳过（allow() 自带自增；>2 轮才放行）
    # 已溢窗(rough>base)：无视冷却，强制裁（防 400）

hist   = truncate_oversized_message(conversation_history)   # 裁前截断单条 >4000 字符
prefix = count_system_prefix(hist)                          # 头部连续 system 数
keep_from = find_recent_rounds_start(hist, _keep_recent_rounds)   # 保护区起点
protected = hist[keep_from:]        # 倒数 1~N 个 FC 工具轮 + 末条 final answer（不裁）
queue     = hist[prefix:keep_from]  # 倒数 N+1 及更早（可裁）
protected_tokens = _estimate_tokens(protected)
budget_for_queue = trim_queue_budget(ctx) - protected_tokens       # 基准×0.8² - 保护区占用

if budget_for_queue > 0 and queue:
    tail_start = prefix + find_tail_start(queue, budget_for_queue, align_turn=True)
elif rough_current > trim_base and queue:                  # 真溢窗：队列整体让位
    tail_start = keep_from
    向前找 keep_from 之前最近的 user，若找到则 tail_start = 该 user 下标   # 只额外保"保护区那轮的提问"
else:                                                      # 未溢窗、仅"阈值×系数²"预算不够
    remaining = trim_base - protected_tokens
    tail_start = prefix + find_tail_start(queue, remaining, align_turn=True) if queue and remaining>0 else prefix

# 重建：头部 + 队列剩余 + 保护区
if tail_start <= prefix:  log "无旧轮可裁或预算不足, 保留原历史" ; return    # 不动刀、不复位冷却、不置旗
rebuilt = hist[:prefix] + hist[tail_start:keep_from] + protected
rebuilt = remove_dangling_tool_calls(rebuilt)              # 只有裁剪才可能拆散配对
if len(rebuilt) >= 2:
    conversation_history = rebuilt
    _trim_cooldown.mark_compacted()
    _trimmed_this_round = True
    _trimmed_tokens_this_round = max(0, rough_current - _estimate_tokens(rebuilt))
    log "[trim_history] 轮次滑动裁剪: X条/tok → Y条(触发: delta|abs|msg_count)"
else:
    log "重建后不足2条, 保留原历史"
except Exception:  warning "异常, 跳过裁剪保留原历史"（不抛出）
```

关键语义（易误读，逐条落字）：

1. **保护区是"至少保 N 轮"，不是"只保 N 轮"**：`queue` 才是裁剪候选区，预算够就尽量多留（2026-10-25 的 over-trim 修复）。
2. **三个预算分支的优先级**：够用系数²预算 → 按预算裁；不够但已溢窗 → 队列全让位（只补回提问 user）；不够且未溢窗 → **退回硬剩余预算**（`base - protected`）再判，仍留不下才早退（2026-10-30 修复：原 else 直接按"丢光队列"处理，实测一次清空 12 个旧轮）。
3. **未裁剪就不动刀**：`tail_start <= prefix` 时直接返回，**不做 dangling 清理**——"保留原历史"语义下 FC 配对本就完整，静默动刀属越权（2026-10-30 修订）。
4. **只裁剪、不改写保留消息**：`use_tool_summary` 语义替换 2026-10-30 已摘除（实测 `_summary` 只是一两行状态/计数，替换后正文灭失）。
5. **切点对齐 user**：`align_turn=True` 保证"user 提问与其回答同进退"，杜绝悬空 user 堆积（旧设计实测 39 任务会话裁后 14 条连续 user 有问无答）。

### 3.4 为什么队列预算用系数²

`trim_conv_threshold = base × r`（触发线），`trim_queue_budget = base × r²`（裁剪目标）。触发线之上再乘一次系数，保证"裁完必低于触发线"，否则裁了下一轮仍触发 → 死循环式反复裁剪。`agent_utils.trim_queue_budget` docstring 已把这条不变量写死。

### 3.5 请求前剥离（`prepare_messages_for_llm`，462-504）

| 步骤 | 内容 |

### 5.4 口径红线（写进文档，防后人"统一"）

1. **"要不要压"用原文**（`_maybe_compact_injected_history`、增量 B 门）：tool 截断前才是"历史真实有多大"。
2. **"塞不塞得进"用 feed**（`_shrink_before_summary`）：用原文判会虚报（实测 174 条样本虚报 325%）→ 误触发 → 白丢早段轮次。
3. **同一处内 判/裁/保尾 必须同传 estimator**（三处：`conv_threshold` 判定、`shrink_to_budget` 裁剪、`find_tail_start` 保尾边界）。
4. **保护区轮数只有一个旋钮**：`tuning.trim.keep_recent_rounds`（clamp 5~20），loop 保护区与 start 注入件尾部轮同源。

### 5.5 关联项（非本次分析对象，仅提示）

工作区另有**未提交**的 `backend/app/llm/client_sdk.py` wire 归一（`_wire_arguments` / `_normalize_wire_messages`，由 `_build_request_body` 单点调用）：它不参与"压缩/裁剪"决策，但它是"截断后 `arguments` 必须仍是合法 JSON"这条约束的**最后兜底**。与本主题的交集只有一句：`split_turn.truncate_tool_call_args` 已按"截后仍为合法 JSON"实现（结构化裁剪），wire 归一只是第二道防线，二者不重复、不冲突。
