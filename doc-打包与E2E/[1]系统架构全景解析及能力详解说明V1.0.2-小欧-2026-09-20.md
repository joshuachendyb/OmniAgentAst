## 一、阅读指引与取证纪律

### 1.1 这份文档解决什么问题

本仓库已有一份 `README.md`。本**不是**对 README 的复述，而是回答五个 README 没讲透的问题：

1. **后端由哪些部件构成、数据怎么流动** —— 第二章分层图与时序图。
2. **有哪些"服务端才做得到"的能力** —— 第三章与第十~十二章。
3. **运行机制怎么一层层跑起来** —— 第四~六章（Agent 循环 → Step 事件 → Prompt/Observation 装配）。
4. **两大主力工具（shell / 文件编辑）内部做了什么** —— 第七、八章。
5. **哪些是设计文档里有、代码里还没有** —— 第二十二章，避免把方案当现状。

### 1.2 取证标准（全篇遵守）

| 规则 | 说明 |
|------|------|
| 只认代码 | 每条结论后附 `文件:行号`。README/设计文档与代码冲突时**以代码为准** |
| 未实现即声明 | 检索不到实现就写"未实现"，不按设计意图推测 |
| 数字标明验证法 | 关键数字尽量两种方法交叉验证；**只有一种方法验证过就写明是哪一种** |
| 不美化 | 体量风险与遗留问题照实写入第二十二章 |

# 第二部分 服务端独有能力与内核机制

## 三、服务端五大独有能力（核心）

> 本章是全文重点。判定标准：**这件事如果只用 OpenAI SDK 套壳 + 一层 FastAPI，做不出来。**
> 机制层的展开见第四~六章。

> ⚠ 与 V1.0.7 文档的"六大独有能力"相比，v1.0.2 **无 ConnectionScope 代际连接池**（V1.0.7 能力四）和 **配置热重载 + 设置 API**（V1.0.7 能力五），故为五大能力。

### 3.1 能力一：把 SSE 做成"可回放的事件总线"

多数 Agent 后端的 SSE 是"生成器 yield 一次就消失"的单向流。本系统把它做成了**带游标、可续传、可跨页面、可对账**的事件通道。→ 机制细节见**第五章 5.2~5.5**。

```text
 Agent 内核                StreamBuffer（services/task/task_state.py）
 publish(event) ──────────────► ┌──────────────────────────────┐
（Agent 事件唯一入口           │ event_log: List[Dict]        │ ← append-only
  agent_runner._publish）       │ {seq:0, type:"start",...},   │ 永不缩短
  ⚠ 沙箱/HITL 网关有直调       │ {seq:1, type:"chunk",...},   │
  buffer.publish 的旁路         │ {seq:2, ...},                │
  sandbox_gate.py）             │ cond: asyncio.Condition      │ ← seq+append+notify
                                │ done: asyncio.Event         │ 锁内原子完成
                                └──────────────────────────────┘
                                 ▲
                                 │
  stream_reader(buffer, task_id, after_seq)
  │
  实时首连 after_seq=0 / 断线重连 after_seq=N
```

| 能力 | 实现 | 证据 |
|------|------|------|
| 断点续传 | 同一 `stream_reader` 传 `after_seq` 复用，首连/重连零重复 | `stream_orchestrator.py` |
| 重连不重跑 Agent | 重连编排器只 `get_stream_buffer(task_id)`，任务不存在则 `not_found` | `stream_orchestrator.py` |
| 终态对账日志 | 退出时打 `起点seq / 续传帧数 / 已转发 / 缓冲总长 / 末类型 / 含final_stats` | `stream_orchestrator.py` |
| 心跳（默认 25s，可配） | 发 `: ping\n`（**必须带换行**），周期取 `tuning.live_front.heartbeat_interval`（默认 25.0），与前端 `IDLE_TIMEOUT=60s` 错开 | `stream_orchestrator.py` |
| 历史回放端点 | `GET /chat/execution/{session_id}/stream` 把 DB 步骤重放成 SSE | `api/v1/chat/execution_stream.py` |

> **一个真实踩过的坑**（代码注释原文）：心跳原本 yield `": ping"` 不带换行，会与下一条 `data:` 事件粘连，前端 `split('\n')` 后整行前缀不是 `data: `，被 `sseParser.ts` 整行丢弃 —— **心跳之后的第一个业务事件被吞掉**。改成 `": ping\n"`才根治。

### 3.2 能力二：任务与连接彻底解耦（断线不杀任务）

```text
 HTTP 连接        编排层              后台 Agent 任务
 SSE 生成器 ──读缓冲──► stream_reader ◄──publish── asyncio.Task
 │ 客户端断开
 ▼
 CancelledError
 ├─ 编排层只 `return`，打印"agent 后台继续"
 ├─ 编排层 finally 仍归还资源
 └─ 只有"编排层自身异常"才 bg_task.cancel
   （且 runner 的 finally 仍会跑完落库）
```

| 机制 | 说明 | 证据 |
|------|------|------|
| 编排层强引用表 | 模块级 `_agent_tasks: set` + `add_done_callback(discard)` | `stream_orchestrator.py` |
| Runner 层自持 | `_background_tasks` 持有 `_self_task` | `agent_runner.py` |
| `done` 唯一置位点 | 全仓唯一置位在 runner finally | `agent_runner.py` |
| 收尾顺序 | `final_stats` → `task_cleanup` → `done.set` | `agent_runner.py` |
| 缓冲延迟回收 | `loop.call_later(300, reclaim_stream_buffer)`，给重连留 5 分钟窗口 | `agent_runner.py` |

## 四、Agent 内核与重试架构

### 4.1 ReAct 循环骨架

`run_react_cycle` 是**普通 async 函数而非 async generator** —— 零 `yield`，事件全部通过 `StreamBuffer.publish` 直写缓冲（`react_loop.py`）。这是第五章事件总线能成立的前提。

```text
 run_react_cycle(task, context, max_steps, task_id, start_time) react_loop.py
 │
 ├─ 取 max_steps（config agent.max_steps = 10000）
 ├─ 取 StreamBuffer（缺失直接 raise）
 ├─ 初始化运行态 + 遥测 + token 四层基线
 ├─ publish(start)（带 ai_message_id 锚）
 ├─ 开局压缩（超 50% 上下文则先摘要）
 ├─ max_steps<=0 → FinalStep(cancelled/config_limit) 早退
 │
 └─ while llm_call_count < max_steps:
    ├─ 取消检测（每轮 LLM 调用**前**检出，不打断在飞流）
    ├─ 暂停阻塞 await wait_for_resume（循环顶真阻塞）
    ├─ 单步 _process_single_step
    │ ├ Phase1 准备：trim_history 裁剪 react_step.py
    │ │ prepare_messages_for_llm message_builder.py
    │ ├ Phase2 流式：call_llm_with_fallback react_step.py
    │ └ Phase3 分发：_dispatch_handler → tool/answer react_dispatch.py
    ├─ 可恢复错误重试 >3 → failed + break
    ├─ 终态状态 break
    ├─ chunk 超时强停
    └─ 无终态兜底 cancel_terminal_text("status_inconsistency")
 │
 └─ finally: _finalize_cycle + 遥测落库 + clear_temp_auth
    + reset_current_task_id
```

#### 九重熔断/空转终止

| # | 触发条件 | 阈值 | 证据 |
|---|----------|------|------|
| 1 | 相同工具连续调用（无进展） | 2/3/4 次注入纠偏，第 **5** 次硬终止 | `react_inference.py`、`react_step.py` |
| 2 | 连续输出截断 | 常量 3 | `react_inference.py`、`react_step.py` |
| 3 | reasoning-only 空转 | 常量 3，判定 `> 3` → 容忍 3 轮、第 4 轮终止 | `reasoning_guard.py` |
| 4 | 同 (tool, 拒绝类型) 累计 | **3** 次 → FAILED | `react_dispatch.py` |
| 5 | 可恢复异常重试 | **3** 次 | `react_loop.py` |
| 6 | 工具自身重试 | per-tool `max_retries=2`（httpget/download/fetchpage/searchweb/ping_port） | `tool_constants.py` |
| 7 | 沙箱环境性失败 | 不与危险失败混流，避免 LLM 原样重发 | `sandbox_gate.py` |
| 8 | 任务侧熔断 | 沙箱并发信号量 / Shell 池 `ShellPoolBusyError` | `executor.py`、`shell_engine.py` |
| 9 | 429 限流 | 指数退避 `3**n` + 读 `Retry-After` | `base_service.py` |

### 4.2 上下文治理：双条件裁剪 + 锚定摘要

```text
 每轮 LLM 调用前 trim_history message_builder.py ★ 唯一裁剪入口
 ├ 增量触发：rough_current - last_total_tokens > compaction_buffer(20000)
 ├ 绝对触发：rough_current > MAX_CONTEXT_TOKENS × 0.75
 └ 轮数触发：msg_count > max_rounds(100) × 2 + 5
 │
 _classify_messages 四类分桶 (system / user / observation(tool) / assistant)
 │
 budget = MAX_CONTEXT_TOKENS - compaction_buffer - system/user 占用
 _trim_to_budget(obs_list, assistant_msgs, budget)
 _rebuild_and_validate → 失败则**保留原历史**（零退化）
 _trim_fc_pairs 清理配对不完整的 FC 对（防 provider 400）
 │
 MAX_CONTEXT_TOKENS 运行时覆盖为 llm_service.context_limit（默认 262144）

 开局压缩（跨会话注入的长历史）：
 超 context_limit × 0.5 → generate_anchored_summary（六段固定结构摘要）
 → history[] + [摘要] + history[-1:] start_step.py
 接线点：start_step.py（lazy import，避免循环依赖）
```

> **诚实提示**：`compaction/__init__.py` 导出 17 项，其中**只有 `generate_anchored_summary` 一个接入主链路**。`trigger.py`/`prune.py`/`split_turn.py`/`assembler.py` 的函数全仓无外部 import。当前真正生效的裁剪是 `message_builder.trim_history`。

### 4.3 重试架构

系统里的"重试"不是一个机制，而是**四层独立计数器 + 一条降级链**。四层互不共享状态，理论上可叠加。

#### 4.3.1 四层总览

| 层 | 位置 | 触发者 | 次数上限 | 退避 | 重试对象 |
|----|------|--------|---------|------|---------|
| **L1** LLM 流式 HTTP | `llm/base_service.py` | `_should_retry(e)` | `self.max_retries`=3 → **共 4 次 HTTP** | `3 ** retry_count` → 3s/9s/27s | 同一次 LLM 调用重发 HTTP（`llm_call_count` **不变**） |
| **L2** LLM 响应级 + FC→Text 降级 | `services/agent/llm_call.py` | `LLMResponseError` | `tuning.llm.response_retries`=**2** → **共 2 次尝试** | `min(0.5 * 2**attempt, 30)` | 整个 FC 流；耗尽后降级 Text 模式再跑一轮 |
| **L3** 工具执行 | `tools/tool_retry_engine.py` | `_should_retry` | per-tool `TOOL_RETRY_CONFIG`，**全为 2**；未配置 = **0** | `backoff_factor ** attempt`，`default=2.0` → 1s/2s | 同一工具同参数重执行 |
| **L4** Agent 轮次 | `react_loop.py` | `_is_recoverable_error` | `_retry_count > 3` → 第 4 次失败终止 | **无**（`continue` 立即回循环顶） | **整个 `_process_single_step`**（下一轮） |

```text
 一次 LLM 请求的失败可能走完整链条：
 ┌─ L1: HTTP 4 次（3s/9s/27s 退避） base_service.py
 │ LLMResponseError 不被 L1 吞（穿透） → 交给 L2
 ├─ L2: 响应级 2 次尝试（0.5s/1s 退避） llm_call.py
 │ 耗尽 → 发 retrying 事件 → 降级 Text 模式再跑
 └─ 仍失败 → 异常抛回 _process_single_step
    └─ L4: _retry_count+1 → continue 回循环顶 react_loop.py
       _retry_count > 3 → recoverable_retry_exhausted → FAILED
```

#### 4.3.2 L1：LLM 流式 HTTP 重试

**`max_retries` 优先级链**

| 优先级 | 来源 | 现值 |
|--------|------|------|
| 1 | provider 级 `ai.<name>.max_retries` | agnes 3 / sensenova 3 |
| 2 | `tuning.llm.stream_max_retries` | 3（`config.yaml`） |
| 3 | 全局默认 `LLM_STREAM_MAX_RETRIES` | 3 |

**超时逐轮递增**：`effective_timeout = self.timeout + (retry_count + 1) * 20`，逐轮 **170 → 190 → 210 → 230 秒**。

**可重试判定**：`SystemErrorClassifier.classify_error(e).is_retryable`（`error_classifier.py`），7 个枚举成员：

| 分类 | 可重试 | 触发条件 |
|------|--------|---------|
| `IDLE_TIMEOUT` | ✅ | `IdleTimeoutError` |
| `SERVER` | ✅ | 5xx 兜底；`LLMResponseError` 特殊映射；默认兜底 |
| `CLIENT` | ❌ | 4xx 兜底 |
| `RATE_LIMIT` | ❌ | HTTP 429 |
| `CIRCUIT_OPEN` | ❌ | 消息含 `circuit` + `open` |
| `EMPTY_RESPONSE` | ❌ | 消息含 `empty` + `response` |
| `UNKNOWN` | ❌ | Python 内置异常名集合 |

#### 4.3.3 L3：工具执行重试

**`TOOL_RETRY_CONFIG` 全表**（`tool_constants.py`）：

| tool | max_retries | retryable |
|------|-------------|-----------|
| `httpget` | 2 | timeout, connect, network, protocol |
| `download` | 2 | timeout, connect, network, protocol |
| `fetchpage` | 2 | timeout, connect, network, protocol |
| `searchweb` | 2 | timeout, connect, network |
| `ping_port` | 2 | timeout, connect |

不在表中的工具 `max_retries=0`，不重试。副作用工具（writetext/edittext/delete/shell）**均不在表中** → 不会被 L3 重复执行。

#### 4.3.4 L4：Agent 轮次重试（`_retry_count`）

| 项 | 事实 | 证据 |
|----|------|------|
| **无显式初始化** | 全部以 `getattr(agent, '_retry_count', 0)` 惰性建属性 | 全仓检索 |
| ⚠ **从不归零** | 全仓**无任何 `_retry_count = 0` 赋值** —— 一旦自增，整个任务不再回零 | 全仓检索 |
| **可恢复错误白名单** | `_RECOVERABLE_ERRORS = {"rejected","blocked","timeout"}` | `react_inference.py` |
| 终态 | `FinalStep(outcome="failed", error_type="recoverable_retry_exhausted")` + `set_failed` + `break` | `react_loop.py` |

> ⚠ **`_retry_count` 是任务级终身预算，不是每轮预算**（因为从不归零）。

#### 4.3.5 幂等性与副作用

| 问题 | 结论 | 证据 |
|------|------|------|
| **L1 重试会让 chunk 重复吗** | **会**。已 yield 的无法撤回；重试在同一 generator 的 `except`；`full_content`/`full_reasoning` 累加器跨重试**不重置** → 第二轮内容追加在第一轮之后 | `base_service.py` |
| 副作用工具会被 L3 重复执行吗 | **不会**。writetext/edittext/delete/shell 均不在 `TOOL_RETRY_CONFIG` | `tool_constants.py` |
| 有"不可重试"声明机制吗 | **没有**。不可重试是"未配置即 0"的隐式结果 | 全仓检索 |
| L4 重试会重跑工具吗 | **会**，但由 LLM 重新决策：conversation_history 里已完成的工具 observation 还在 | `react_step.py` |

#### final 的"长条 / 短五键"两形态（唯一裁剪点）


### 5.4 事件机制：是"日志"，不是"队列"

**它既不是排队，也不是传统发布订阅，而是"可回放的追加日志 + 条件变量唤醒"**。

| 维度 | 事实 | 证据 |
|------|------|------|
| 数据结构 | `StreamBuffer`：`event_log: List[Dict]` + `cond: asyncio.Condition` + `done: asyncio.Event` | `task_state.py` |
| publish 原子性 | `dict` 浅拷贝 → 持 `cond` 锁 → `step["seq"] = len(event_log)` → `append` → `notify_all`，**三步全在锁内** | `task_state.py` |
| **事件会丢吗** | **不会丢**。无 `popleft`、无消费游标写回。读侧只递增**局部变量** `offset`，`event_log` 永不缩短 | `stream_orchestrator.py` |
| 白名单外的事件 | 对 SSE 不可见（设计意图），**对 DB 可见**（`thought` 就是这样） | |
| 背压 | **无背压**。publish 持锁后立即 notify 返回，从不等消费者 | `task_state.py` |
| `event_log` 上限 | **无上限**。全仓无裁剪/限长代码；唯一回收是任务结束后 300s 整块丢弃 | `agent_runner.py` |
| 单播/广播 | **广播（多播）**。每个 SSE 连接各自 `stream_reader` 实例持独立局部 `offset`，互不消费；用 `notify_all` | `task_state.py`、`stream_orchestrator.py` |
| 重连起点 | `after_seq + 1`：`stream_reader` 首行 `offset = after_seq` | `stream_orchestrator.py` |

### 5.5 Step 与 LLM、与 DB 的对应关系

**一次 LLM 响应 = 1 个 step 号 + N 条事件**。所有事件的 `step` 字段统一取 `agent.llm_call_count`（**轮号**，非自增计数器）。

| 事件 | 发射点 | 一轮内数量 |
|------|--------|-----------|
| `chunk` | `react_step.py` | **N 个**（每 delta 一个，`is_reasoning` 区分） |
| `usage` | `react_step.py` | 0 或 1（响应带 usage 时） |
| `stats` | `react_step.py` | 恒 1（不依赖 usage） |
| `context_overview` | `react_step.py` | 条件（第 1 轮/本轮裁剪/每 5 轮） |
| `retrying` | `react_step.py` | 0 或 1 |
| `thought` | `handle_action.py` / `handle_answer.py` | 0 或 1 |
| `action` | `handle_action.py` | 0/1/2 |
| `observation` | `observation_builder.py` | 恒 1（工具轮） |
| `thought-start` | `react_loop.py` + `handle_action.py` | 工具轮次数 + 1 |
| `final` | `handle_answer.py` / 终态工厂 | 0 或 1 |

#### `thought` vs `thought-start`：为什么一落库一不落库

| 维度 | `thought` | `thought-start` |
|------|----------|----------------|
| 语义 | 思考**正文**（真实推理内容） | "等第一个 thought 出现"的**等待信号** |
| 载荷 | `content`(=thought) + `reasoning` | 空（无 `_extra_fields`） |
| SSE | **不转发** | 转发 |
| DB | **落库** | 不落库 |

> **根因**：`thought` 双通道冲突 —— 历史回放（DB）已带完整思考正文，若再走实时 SSE，前端会重复显示。`thought` 照常 `publish` 进 `event_log`（落库扫描/序号零改动），仅 reader 转发时按类型跳过。`thought-start` 反向：纯瞬时信号，落库只会污染历史。

#### DB 侧：一行 = 一个 step（不是一轮）

| 事实 | 证据 |
|------|------|
| 表注释明确"独立步骤表（一行=一步）" | `db_initializer.py` |
| 落库函数 `append_execution_step(...)` | `storage.py` |
| `step_index = len(current_execution_steps) - 1`，是**落库序号**（0,1,2…），与 step dict 内的 `step`（LLM 轮号）语义不同 | `agent_runner.py` |
| 一个 LLM 轮写多行（thought/action/observation/final/final_stats 各一行）；`chunk`/`thought-start`/`usage` 等**不写行** | `agent_runner.py` |
| `ai_message_id` **外键已退役**，改为纯贯通键 | `db_initializer.py` |
| 唯一索引 `UNIQUE(ai_message_id, task_id, step_index)` | `db_initializer.py` |

## 七、thought-only（只思考不出声）的处理

### 7.1 两种"空"的区分

| 情形 | 定义 | 路径 | 算重试吗 |
|------|------|------|----------|
| 真·空 | content + reasoning **皆空** | `handle_answer.py` → `MetaStep(type="retrying", wait_time=1)` → `_retry_count+1` | ✅ **算** |
| thought-only | content 空、reasoning **非空** | `reasoning_guard.note_reasoning_only` → `_consecutive_reasoning_only += 1` | ❌ **不算**（不增 `_retry_count`） |

### 7.2 reasoning_guard：单一写者

`reasoning_guard.py` 全文 21 行，是 `_consecutive_reasoning_only` 的**唯一写者**：

```python
REASONING_ONLY_MAX_ROUNDS = 3  # 容忍 3 轮，第 4 轮终止

def note_progress(agent):
    agent._consecutive_reasoning_only = 0

def note_reasoning_only(agent):
    agent._consecutive_reasoning_only += 1
    return agent._consecutive_reasoning_only > REASONING_ONLY_MAX_ROUNDS
```

- `note_progress`：非 reasoning-only 进展时归零（6 处调用点）
- `note_reasoning_only`：reasoning-only 一轮时累加；超限返回 True → 调用方走终止分支

### 7.3 thought-only 的终态

超限 → `FinalStep(outcome="failed", error_type="reasoning_only_loop")` + `set_failed` + `break`。
