## 一、打包

```powershell
cd F:\OmniAgentAs-01\frontend
npm run build        # tsc + vite build，约 1~2 分钟
```

产物：`frontend/dist/`（`index.html` + `assets/`，约 9 MB）。`dist/` 被 git 忽略，不入库。

### 后端地址烘焙（重要）

默认构建的包 API 走**同源** `/api`。若前端与后端**不同源**（不同端口即不同源），构建时指定：

```powershell
# 后端源码开发模式（端口 8000）
$env:VITE_API_BASE_URL="http://127.0.0.1:8000"
npm run build

# 后端打包版 exe（端口 8500）
$env:VITE_API_BASE_URL="http://127.0.0.1:8500"
npm run build
```

烘进 JS 后**不可再改**，换后端地址必须重打。

> **端口对照**：源码开发后端默认 8000，打包版 exe 默认 8500（见《后端打包手册》第七章）。

## 二、部署方式（四种，选一种）

> 先说结论：**本机自己用选方式一**，其他三种是给不同场景准备的。

### 方式一：`npm run dev`（开发调试，推荐新手）

```powershell
cd F:\OmniAgentAs-01\frontend
npm run dev
```

- 浏览器开 `http://localhost:5173`
- `/api` 请求由 vite **自动转发**给 `:8000`（开发模式后端端口），不用配任何东西
- 改代码自动热更新，适合日常使用和调试
- **缺点**：关掉窗口服务就停；需要装 node_modules（`npm install` 一次）

### 方式二：`npm run preview`（验证构建产物）

```powershell
cd F:\OmniAgentAs-01\frontend
npm run preview
```

- 浏览器开 `http://127.0.0.1:4173`
- 跑的是 `dist/` 里打好的包，不是源码
- 自带 SPA fallback：在 `/settings2` 这类子路径上刷新**不 404**
- 用途：发版前确认"打出来的包能不能跑"

### 方式三：`python -m http.server`（临时静态 serving）

```powershell
cd G:\Omni-AI\frontend
python -m http.server 4173
```

- 不需要 node，Python 自带，开箱即用
- **两个坑**：
  1. 不带端口默认 `:8000`（和后端撞车），**必须显式给端口**，且不能是 8000
  2. **无 SPA fallback**：在子路径（如 `/settings2`）上按刷新必 404，只能从根路径 `/` 进再点进去

### 方式四：Nginx（正式部署）

- 把 `dist/` 内容拷到 Nginx 静态目录
- `/` 指向静态文件，`/api/` 反代到后端
- 自带 SPA fallback（`try_files $uri /index.html`）+ 生产级性能
- 详见 §五配置；机器上没装 Nginx 时不用考虑本方式

## 三、端口与 CORS

### 3.1 规则

- 前端端口**随便换**（避开 8000 即可）。
- 换端口后必须把新源加进后端 `config.yaml` 的 `network.cors_origins`，**改完重启后端**（CORS 中间件只在启动时读一次）。
- `localhost` 与 `127.0.0.1` 是**两个不同的源**，用哪个访问就加哪个：
  `http://127.0.0.1:4173,http://localhost:4173`。

### 3.2 典型报错对照

| 报错 | 原因 |
|---|---|
| `No 'Access-Control-Allow-Origin' header` | 源不在白名单（最常见的是 localhost/127.0.0.1 写错一个） |
| `ERR_FAILED` + 无 CORS 头 | 同上 |
| `404 File not found`（纯文本页） | 不是 CORS，是 §四 的 SPA 问题 |

## 四、SPA fallback（python http.server 必踩）

React 是单页应用，`/settings2` 这类路径只存在于浏览器内存路由，磁盘上只有 `index.html`。

- `python -m http.server` 不懂这个：**在子路径上刷新必 404**。
- 解法：回根路径（`http://127.0.0.1:4173/`）再点进去；或换 `vite preview` / Nginx（自带 fallback）。

## 五、Nginx 生产配置（要点）

```nginx
location / {
    root   G:/Omni-AI/frontend;     # dist 内容拷到这里
    try_files $uri /index.html;    # SPA fallback，根治 §四
}
location /api/ {
    # 源码开发后端用 8000，打包版 exe 用 8500
    proxy_pass         http://127.0.0.1:8500;
    proxy_http_version 1.1;
    proxy_set_header   Connection '';
    proxy_buffering    off;        # SSE 必关，否则流式被攒住不下发
    proxy_cache        off;
    proxy_read_timeout 3600s;
}
```

## 六、配置修改铁律（实测教训）

1. **provider 键名别手改**：`ai.<键>` 是主键，被 `model_ref.provider` 等多处引用，改键不断引用必崩。要改显示名请改同级的 `label`（设置页 Provider 配置区可直接改，保存即生效）。
2. **改完 `config.yaml` 先校验**：后端 YAML 语法错不会立刻崩，但读到坏段就抛，后台日志查 `traceback`。
3. **清场只按端口杀**：`Get-NetTCPConnection -LocalPort <端口>` 精确杀，严禁按进程名批量杀（会误杀 vite/dev/工具自身，见 README §8.4.1）。
4. **`--reload` 是双进程**：只 kill 父进程无效，子进程会残留占端口；`Get-NetTCPConnection` 的 `OwningProcess` 偶发过期读数，动手前用 `tasklist /FI "PID eq <PID>"` 交叉确认进程真死。
5. **浏览器缓存**：`index.html` 被缓存会导致旧 JS 一直跑（表现：明明重打了包，行为还是旧的）。`F12` → Network 勾 `Disable cache` → 右键刷新选「清空缓存并硬性重新加载」。

## 七、部署命令与旧文件清理（实测教训，2026-10-27）

### 7.1 部署标准流程（先删后拷，铁律）

**必须先清空部署目录再复制**，不能直接覆盖。`Copy-Item -Recurse -Force` 只覆盖同名文件，**不会删除目标端旧文件**（见 7.2）。

```powershell
# 第1步：清空部署目录
Remove-Item -Recurse -Force "G:\Omni-AI\front"

# 第2步：重新复制
Copy-Item -Path "F:\OmniAgentAs-01\frontend\dist\*" -Destination "G:\Omni-AI\front" -Recurse -Force

# 第3步：验证（见 7.3）
```

> **为什么必须删**：Vite 构建产物文件名带 hash（`index-Cnpu8vcd.js` / `index-B75V9bkY.css` 等），每次 build hash 都变。只覆盖不删除会导致旧 hash 文件残留，`assets/` 里多个时间段的文件混杂堆积。

### 7.3 部署后验证

```powershell
# 验证 index.html 引用的 5 个资源文件是否全部存在
$html = Get-Content "G:\Omni-AI\front\index.html" -Raw
$refs = [regex]::Matches($html, 'assets/[\w.-]+')
foreach ($r in $refs) {
  Write-Host $r.Value, (Test-Path ("G:\Omni-AI\front\" + $r.Value))
}
# 全部 True 才合格
```

**建议**：每次部署前先清空 `G:\Omni-AI\front\assets`（`Remove-Item -Recurse -Force`），再 Copy-Item，避免堆积。

## 八、烘焙验证（实测教训，2026-10-27）

### 8.1 为什么需要验证

`VITE_API_BASE_URL` 是构建时烘进 JS 的，烘好后不可再改。但**怎么确认烘进去了**？

### 8.2 常见误判（踩坑记录）

用 `Select-String -Path "dist\assets\index-*.js" -Pattern "127\.0\.0\.1:8500"` 搜不到 → 误判"没打进去"。

**原因**：每次 build 主入口 hash 不同（如 `index-Cnpu8vcd.js`），`index-*.js` glob 匹配到的可能不是含 URL 的那个文件（含 URL 的可能是某个 lazy chunk 或主 entry）。

### 8.3 正确验证方法（node 脚本扫描全部 JS）

```powershell
node -e "
const fs=require('fs');
const d='F:/OmniAgentAs-01/frontend/dist/assets';
const files=fs.readdirSync(d).filter(f=>f.endsWith('.js'));
for(const f of files){
  const c=fs.readFileSync(d+'/'+f,'utf8');
  if(c.includes('127.0.0.1:8500'))console.log(f+': FOUND');
}
console.log('done, total:',files.length);
"
```

**全 70 个 JS 文件扫一遍**，只要有一个 JS 含 `127.0.0.1:8500` 即证明烘焙成功。

## 九、同源 404 排查法（实测教训，2026-10-27）

### 9.1 现象

前端用 `python -m http.server` 起在 2000 端口，后端 exe 在 8500 端口。浏览器打开 `http://127.0.0.1:2000` 后，控制台满屏 404：

```
api/v1/sessions?...:1  Failed to load resource: 404
api/v1/config/full:1   Failed to load resource: 404
api/v1/files/root:1    Failed to load resource: 404
api/v1/settings/schema:1  Failed to load resource: 404
```

### 9.2 根因

- 前端源码读 `VITE_API_BASE_URL`（构建时烘焙）。若**没设**该变量，`getApiBaseUrl()` 返回空串，axios 走**同源相对路径** `/api/v1/...`。
- 浏览器同源是 `http://127.0.0.1:2000`（静态服务器），请求打到 2000 端口的 `/api/v1/...`。
- 2000 端口只有静态文件，没有 `/api/v1` 路由 → **全 404**。
- 后端实际在 8500 端口，但前端根本不知道。

### 9.3 排查步骤

1. **F12 → Network 标签**：看 404 的 URL 是打到哪个端口（`http://127.0.0.1:2000/api/v1/...` 还是 `http://127.0.0.1:8500/api/v1/...`）。
2. 若打到**静态端口**（2000）→ 说明 API base URL 没烘焙进去或烘焙错。
3. 按 §八 验证烘焙；未设 `VITE_API_BASE_URL` 则重打：`$env:VITE_API_BASE_URL="http://127.0.0.1:8500"; npm run build`。
4. 重新部署（§七）后 Ctrl+F5 硬刷新。

### 9.4 与 §三 纯文本 404 的区别

| 404 类型 | URL 特征 | 原因 |
|---------|---------|------|
| SPA 路由 404（§三） | `/settings2` 等子路径刷新 | 静态服务器无 SPA fallback |
| API 同源 404（§九） | `/api/v1/...` 打到静态端口 | `VITE_API_BASE_URL` 未烘焙，走同源相对路径 |
