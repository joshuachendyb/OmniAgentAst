### 1.1 这一阶段做了什么

396 个 commit 的类型分布（按 commit 标题前缀实算）：

| 类型 | 数量 | 占比 |
|---|---|---|
| 文档 | 159 | 40.2% |
| **功能** | **89** | **22.5%** |
| **修复** | **87** | **22.0%** |
| 重构 | 52 | 13.1% |
| 样式 | 2 | 0.5% |
| 性能 | 1 | 0.2% |
| 合并 | 1 | 0.2% |
| 杂务 | 2 | 0.5% |
| notes | 2 | 0.5% |
| 未分类 | 1 | 0.2% |

与上一阶段（v1.1.4→v1.2.3：文档 34.8%、修复 22.8%、功能 17.0%）对比，这一阶段的**功能占比从 17.0% 升到 22.5%**，文档占比从 34.8% 升到 40.2%。**这一阶段的主线是「把安全体系重做一遍，并把工具与界面补齐」**，上一阶段是「往上加能力」。

按系统版本切分，commit 分布如下：

| 版本 | commit 数 | 性质 |
|---|---|---|
| v1.2.4 | 56 | PATCH（功能落地+修缺） |
| v1.2.5 | 35 | PATCH（事件快照+视觉统一） |
| v1.3.0 | 195 | MINOR（信任体系+三线分离+文件工作台） |
| v1.3.1 | 41 | PATCH（路径安全收口） |
| v1.3.2 | 27 | PATCH（配置命名空间嵌套+契约回迁） |
| v1.3.3 | 23 | PATCH（确认链治理+依赖治理） |
| v1.4.0 | 19 | MINOR（裁剪修复+范围门下沉+配置开关） |

从能力角度看，这 396 个 commit 收敛成 **9 条新能力线**：

| # | 能力 | 一句话 | 归属层 |
|---|---|---|---|
| 1 | **安全信任体系与三线分离** | 信任有 TTL、读写删判定各归其线、系统目录判定单源 | 安全层 |
| 2 | **安全配置开关体系** | 安全配置从扁平键变为三前缀嵌套、可见可改 | 安全层 / 界面层 |
| 3 | **安全确认链治理** | 确认文案工具自产、路径检查收口、shell 解析补洞 | 安全层 / 工具层 |
| 4 | **文件管理 Agent 融合工作台** | 能浏览项目目录、把文件引用带进对话 | 工具体系 / 交互层 |
| 5 | **工具依赖治理** | 缺库工具不再进 LLM 试调、pip 串行、锁定包不被顶升 | 工具体系 |
| 6 | **会话使用目录落地** | 会话用了哪些目录，界面上看得见 | 数据层 / 界面层 |
| 7 | **observation / summary / message 口径归一** | 中文显示不再乱、hint 不再谎报 | 前端展示层 |
| 8 | **参数区 UI 优化** | 参数区可读、浮层居中、raw_data 纯增量 | 前端渲染层 |
| 9 | **历史裁剪 FC 原子单元** | 并行 tool_calls 不再乱序、超预算不再丢全部历史 | 编排层 |

这九条不是并列的功能堆砌，它们共同回答同一个问题：

> v1.2.3 的系统是「能接着干、能中途改主意、看得见」。v1.4.0 的系统在此之上开始回答**「安全边界说得清、工具不可用提前知道、界面信息不骗人」**。

| 目标 | 由哪些能力支撑 |
|---|---|
| **安全说得清** | 信任 TTL + 三线分离 + 配置开关可见可改 |
| **判定不打架** | 系统目录判定单源 + 路径检查五级总入口 + 范围门下沉 |
| **工具可用** | 依赖治理（缺库过滤 + 串行锁 + 惰性自愈） |
| **界面不骗人** | observation/summary/message 归一 + 参数区双视图 |
| **历史不丢** | 历史裁剪 FC 原子单元 + 事件列表快照 |

## 第二章 能力一：安全信任体系与读写删三线路径分离

### 2.1 问题：安全约束散落、读写删判定混在一起

v1.2.3 的安全约束存在三个结构性问题：

1. **读写删判定混在一处**：`tools/security/path_safe_check.py` 一个文件里同时处理读、写、删，调用方无法判断某条路径到底走哪条线，新增工具时容易漏接。
2. **系统目录判定跨层各判一次**：系统层判一次、工具层再判一次，两处结论可能相反，出现「系统层说放行、工具层说拦截」的矛盾。
3. **信任没有 TTL**：会话信任只存在于内存/无过期语义，一旦授权就永久有效，风险窗口随时间扩大。

### 2.2 架构：信任 TTL 落库 + 三线分离 + 单源判定

| 层 | 措施 | 作用 |
|---|---|---|
| **信任 TTL** | `chat_session_trust` 增 `expires_at` / `task_id`，`trust_db` 读写校验，周期清理 | 信任有生命周期，可追溯最后一次授权 |
| **三线分离** | `read_path_check` / `write_path_check` / `delete_path_check` 各归其线，`dual_path_check` / `shell_path_check` 独立 | 读、写、删判定不再混在一起 |
| **单源判定** | 系统目录判定收敛到唯一真源，工具层不再重复判定 | 消除跨层结论相反 |
| **骨架正名** | `path_safe_check` → `path_legality_router`，`validate_path` 彻底删除 | 名实相符，不留 backward 套壳 |

### 2.3 三批落地

| 批次 | 内容 |
|---|---|
| **A（[33] TDD）** | 信任设计五章 + 实施步骤；P2/P3/P4 三批次按 TDD 完成；骨架正名与 guard 改名；信任 TTL 落列/写入/校验/清理/周期调度 |
| **B（[35] 拆线）** | `path_safe_check.py` 576 行拆三线；迁出 `validate_path` 与禁区判定；`multi_path_check` 真分开源目标各归其线；`shell_path_check` 自 `multi_path_check` 拆出 |
| **C（收编）** | 工具层收编解除对系统层依赖；会话快照迁中立层；`path_guard` 迁入正名；`tool_routes` 跟随系统结构回传 `SafetyResult` |

### 2.4 带来什么

- 信任从「一次授权永久有效」变为「有 TTL、可追溯、可回收」；
- 读、写、删判定各归其线，新增工具只需接对应线，漏接概率下降；
- 系统目录判定单源，跨层结论相反的问题从结构上消除；
- 安全层骨架正名，`validate_path` 等 backward 套壳彻底删除。

## 第三章 能力二：安全配置开关体系与命名空间嵌套

### 3.1 问题：安全配置扁平、不可见、开关语义混乱

v1.2.3 的安全配置是扁平键（如 `security.hitl_enabled`），存在三个问题：

1. **设置页不可见**：安全配置只存在于代码与配置文件中，使用者看不到当前生效值。
2. **开关语义混乱**：`hitl_enabled` 名实不符，读代码时无法判断它到底管什么。
3. **旧键残留**：分组迁移后，`hitl_confirmation.py` / `hitl_gateway.py` / `config_helpers.py` 仍读旧键，导致过期清理判据与确认超时不再同源。

### 3.2 架构：三前缀嵌套 + 12 项独立开关

键名按域嵌套为三组前缀：

| 前缀 | 含义 |
|---|---|
| `security.system.*` | 系统级硬拦（总闸、禁区、危险命令等） |
| `security.hitl.*` | 人工确认链路（enabled、倒计时、超时、只读白名单、路径确认等） |
| `security.trust.*` | 会话信任（TTL 等） |

本阶段落地 **12 项独立开关**（危险命令 / 中风险 / 路径授权 / shell 路径确认 / 目录名单 / 写删确认等），全部注册进 `settings_registry.py`，设置页可见可改。只读命令免确认白名单 `shell_readonly_prefixes` 也接入配置面，默认展示值取安全层内置清单。

### 3.3 目录名单统一

`path_dir_lists.py` 把目录名单的构建点收敛为唯一，作用域用 `ContextVar` 嵌套复用；安全 Tab 三类名单改读 `path_dir_lists`；设置页新增路径工具四类名单（read/write/delete/dual）**只读展示**，取值直接来自 `tool_constants` 判定名单，展示与实判同源、不可编辑。

### 3.4 带来什么

- 安全配置从「代码里」搬到「界面上」，当前生效值可见可改；
- 12 项开关各自独立，不再互相牵连；
- 目录名单构建点唯一，避免多处各拼一份导致漂移；
- 设置页四类工具名单只读展示，杜绝「展示归类」与「实际放行/拦截」两套口径。

## 第十章 能力九：历史裁剪 FC 原子单元与预算修复

|---|---|

| 组内升序展开 | 保证 `assistant` 恒在 `tool` 之前 |
| `_trim_fc_pairs` 顺序合法性 | `assistant` 声明位置 < `tool` 响应位置，乱序对双侧剔除兜底 |
| `break` → `continue` | 超预算单元整组跳过，继续试更早单元 |

### 10.3 带来什么

- 并行 `tool_calls` 不再触发上游 400；
- 超预算不再丢全部 FC 历史，保留更早的有效单元；

## 第十三章 阶段小结

### 13.1 这一阶段的性质

上一阶段（v1.2.3）回答的是「**能接着干、能中途改主意、看得见**」，这一阶段回答的是「**安全边界说得清、工具不可用提前知道、界面信息不骗人**」。

三条主线并行推进：

| 主线 | 内容 |
|---|---|
| **安全体系重做** | 信任 TTL + 读写删三线分离 + 系统目录单源 + 配置开关可见可改 + 确认链治理 |
| **工具与界面补齐** | 文件工作台 + 依赖治理 + 会话目录 + observation/summary/message 归一 + 参数区双视图 |
| **真实性校准** | 历史裁剪 FC 原子单元 + 事件列表快照 + 全量回归 11 失败清零 + 纪律问题如实记录 |

值得注意的是：**这一阶段最好的几个决定都是做减法**——删掉 `validate_path` backward 套壳、删掉 12 个旧结构文件、删掉跨层重复判定、删掉「试调才知道缺库」的路径。

### 13.2 五条可复用经验

| # | 经验 | 来源 |
|---|---|---|
| 1 | **同一判定只留一个真源。** 系统目录判定、路径检查、空值判定都应收口到唯一入口，重复判定必出矛盾 | 三线分离 + 五级总入口 |
| 2 | **信任必须有 TTL。** 一次授权永久有效等于风险窗口无限扩大 | 信任 TTL 落库 |
| 3 | **确认文案由工具自产。** 安全层硬编码工具名，新增工具就要改安全层 | `confirm_fn` / `op_param` |
| 4 | **展示与实判必须同源。** 设置页展示的工具名单若可编辑，会与实际放行/拦截口径漂移 | 四类工具名单只读展示 |
| 5 | **原子单元是并发正确性的底线。** 并行 `tool_calls` 下逐条裁剪会乱序，按原子单元收集才能保证 `assistant` 恒先于 `tool` | FC 原子单元 |
