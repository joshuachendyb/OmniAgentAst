## 一、测试定义

### 1.1 测试名称

**全链路端到端集成测试**（Full-Link End-to-End Integration Test）

**唯一目标**：用真实LLM（后端从config.yaml读取配置）模拟真实用户操作
 抓出烂代码的问题, 找不到 bug的测试都是垃圾测试.垃圾case---发现任何问题必须深挖问题的烂代码是什么 务必揪出烂代码.

**具体来说**：
1. Agent在真实LLM下能否正确完成用户请求
2. Agent在异常情况下（LLM返回垃圾/空内容/错误工具）能否容错
3. 系统各组件的串联是否完整（API→Agent→LLM→工具→DB）
4. 日志和数据库记录是否完整准确


### 1.2 为什么叫这个名

| 关键词 | 含义 | 在这个测试中的体现 |
|--------|------|-------------------|
| 全链路 | 覆盖系统所有组件 | 前端API→后端→Agent→LLM→工具执行→数据库→SSE响应 |
| 端到端 | 从用户发消息到收到完整结果 | POST /chat → SSE事件流 → final/error`事件 |
| 集成 | 验证各组件对接是否正确 | API路由、SSE封装、Agent循环、LLM调用、工具执行、数据库写入 |

### 1.5 核心测试原则（铁律）

**铁律1：测试的目的是发现问题，不是跑脚本。**

**铁律2：严禁批量跑测试用例。一次只能跑一个测试用例。**

| 允许 | 禁止 |
|------|------|
| ✅ 写一个脚本 → 跑一个 → 观察 → 检查 | ❌ 一次写完所有脚本 |
| ✅ 一个用例跑通后再写下一个 | ❌ 一次批量跑多个用例 |
| ✅ 每次跑完仔细观察系统运行过程 | ❌ 只看pass/fail就过 |
| ✅ 失败了停下来分析修复 | ❌ 失败了跳过继续下一个 |

**铁律3：所有测试统一基于真实后端运行，禁止Mock：**

| 环节 | 要求 | 禁止 |
|------|------|------|
| **后端** | 真实uvicorn启动，从config.yaml读取LLM配置 | ❌ 不启动后端、Mock后端 |
| **LLM** | 真实调用config.yaml中配置的provider/model | ❌ Mock LLM返回、假响应 |
| **工具** | 真实执行文件操作、命令、网络请求等 | ❌ Mock工具返回值 |
| **数据库** | 真实读写SQLite（系统DB：~/.omniagent/chat_history.db） | ❌ Mock数据库、内存数据库 |
| **SSE** | 真实解析后端返回的SSE事件流 | ❌ 假造SSE事件 |

**一句话：测试输入就是用户会说的话，测试过程就是真实系统的完整运行。**

#### 3.3.1 两种执行方式及区别（小欧 2026-07-04）

E2E测试涉及真实LLM调用，单次执行可能超过2分钟。opencode的bash工具默认超时120s，会强杀进程。有两种执行方式：

| 方式 | 命令 | 超时控制 | 适用场景 |
|------|------|---------|---------|
| **方式A：直接运行** | `python -m pytest tests/xxx.py -x --tb=long -v` | bash工具120s超时会强杀进程 | 快速测试（预期<120s完成） |
| **方式B：后台运行** | 用subprocess.Popen启动（见下方完整命令） | pytest自身timeout=3000s管理 | E2E测试（涉及LLM调用，可能>120s） |

**方式A的问题**：bash工具有默认120s超时限制。即使pytest.ini设了`timeout=3000`，bash工具会在120s时强杀整个进程树，pytest的超时设置来不及生效。

**方式B的原理**：用`subprocess.Popen`启动pytest子进程。bash工具只管启动脚本（瞬间结束），pytest子进程独立运行，不受bash 120s限制，由pytest.ini的`timeout=3000`管理。

**方式B完整操作步骤**：

### 3.5 分析的错误处理报告和处理流程（第4步发现FAIL时的必须流程）

```
**脚本错误的修改规则** 脚本分为:用例case脚本和核心测试过程的脚本,

错误分两类:
  A类(运行时): LLM超时/工具崩溃/死循环/SSE断流 → 查日志traceback
  B类(数据不一致): session缺失/messages丢失/steps不匹配 → 对比SSE vs DB

处理流程:
  ① 分类 → A类还是B类
  ② 定位 → 查后端日志 + SSE事件 + prompt-logs,定位到文件:行号
  ③ 分析 → 是代码bug还是测试用例问题
  ④ 修复 → 遵守10大规范 (SRP/DRY/KISS/YAGNI,禁止backward compat)
  ⑤ 复测 → 重跑该用例 + 跑关联测试确认无回归
  ⑥ 记录 → 写入测试报告

严重等级:
  P0(致命): 系统崩溃/死循环 → 立即停止,修复后从P0重跑
  P1(严重): 功能异常但不崩溃 → 修复后重跑该用例
  P2(一般): 非核心异常 → 记录,批量修复
  P3(警告): 性能偏差 → 记录,不阻塞

禁止事项:
  ❌ 看到FAIL就跳过   ❌ 只改测试不改代码
  ❌ 修复时不跑单元测试  ❌ 不记录直接修复
```

## 五、测试脚本编写规则

### 5.1 铁律：1个用例 = 1个函数

```
每个 E2E-XX-XX 编号对应一个 async def test_e2e_xx_xx_xxx()
每个函数只发一条用户指令
每个函数独立验证、独立清理
函数名 = test_ + 编号小写（如 test_e2e_p0_01_introduce_self）

为什么不能合并：
  · 合并后无法定位哪个场景失败
  · 合并后无法单独重跑失败的用例
  · 合并后一个场景的残留数据会影响下一个场景
```

### 5.2 验证分层

```
MUST层   → assert 硬断言   → 无死循环、DB有记录、文件存在
SHOULD层 → if...assert    → DB steps数偏差在2以内
MAY层    → if...print     → 工具名差异仅记录日志
```

### 5.3 测试记录写入（铁律）

```
每个测试用例跑完后，无论通过还是不通过，都必须自动生成测试记录文件。

触发位置：测试脚本的 finally 块中调用 write_test_record()
即使失败也要写：assert失败/异常退出时，记录文件必须写入（含失败原因）
文件位置：G:\OmniAgentAs-desk\notes\测试记录-{用例编号}-{日期}.md

脚本结构：
  passed = False; r = None; sid = None; ...
  try:
      # ... 测试逻辑 ...
      passed = True
  except Exception as e:
      passed = False; raise
  finally:
      write_test_record("用例编号","任务描述",u,r or {},db,ci,si,lc,passed,...)

注意事项：
  · 所有变量必须在try前初始化默认值（防止assert失败后未定义）
  · write_test_record必须在finally中调用（确保无论通过/失败都写入）
```

### 9.1 适用与范围（本手册定位）

第 9 章为 **UI 端到端测试实施手册**，覆盖两类：

### 9.2 通用端到端用例实施规范

**（1）仓库分层**（库做通用、case 只管特例）

| 层 | 位置 | 职责 |
|----|------|------|
| 公用库 | `frontend/e2e_front_lib/` | process.ts（进程/端口/服务）、stream-diag.ts（SSE 取证/对账/落盘）、chat-page.ts（POM）、normal-chat.ts（普通会话流环境 + 主流程） |

### 9.7 断流手段设计（为什么不能用 setOffline）

`context.setOffline` 只拦截**新发起**的请求，无法中断 in-flight 的 SSE 流（已实测无效）。故采用**杀 vite dev 进程**制造真断线：

```
页面(5173) ──分块流──> vite dev ──SSE──> uvicorn(8000)
     ▲                                        │
     │             杀 vite → TCP RST           │ 内存任务存活
     │◄──前端感知断线<──────────────────────────┤
     │             重启 vite :5173             │
     │──Full-Jitter 退避────► GET /chat/stream/{task_id}?after_seq=lastSeqRef+1
```

### 9.8 10 步断言要点

| 步骤 | 动作 | 断言 |
|------|------|------|
| 1 | 新建任务、发送指令 | "停止"按钮出现（isReceiving=true，流已启动） |
| 2 | 等待绿圈 | 已收 thinking 帧、实质开流（非强制，catch 忽略） |
| 3 | 累积 | waitForTimeout(4000) 让流累积几秒再断 |
| 4 | 断流 | `Stop-Process` 杀 :5173 vite dev |
| 5 | 断线检测 | console 出现"重连"字样（poll 30s） |
| 6 | 恢复 | 重启 vite、等 :5173 HTTP 200（poll 60s） |
| 7 | 流结束 | "发送"按钮复现（isReceiving=false，poll 300s） |
| 8 | 断点续传 | console 至少一次重连且 `after_seq>0`（poll 60s） |
| 9 | UI 一致性 | 终态正文完整（>30字符）+ 逐行 run-on 检测（行内 6~30 步长 3 相邻重复比对） |
| 10 | 后端对账 | 本轮新增日志含"重连请求接收...after_seq>0"（补点A，stream_orchestrator.py:554） |

### 9.11 方案演进 v2.12：进程分离（独立代理:9000）最终实况

> **新增章节**：小欧 2026-09-13 09:02:58（对应用例结构同 9.6 所列文件；本方案起 **5 轮×5 连跑实测全绿**）

**（1）为什么弃"杀 vite"改"杀独立代理"**

杀 vite(:5173) 会触发 `@vite/client` 的 `[vite] server connection lost. Polling for restart...` → **整页 reload**，销毁已加载页面 JS 上下文 → 已排队的重连异步任务随之死亡 → 二次重连永不发生（9.4~9.10 均为修复该问题前的旧路径取证，仅作原理性参考）。

真实部署前端经 nginx，**网关/反向代理重启不会 reload 已加载页面**。据此演进为"进程分离"：

```
页面(:5173 vite hmr:false 永活) ──API/SSE 直连(跨域 VITE_API_BASE_URL=http://localhost:9000/api/v1)──> 独立代理(:9000→8000)
      ▲                                                     │
      │              杀代理9000(浏览器直连RST, 页面不载)        │ 后端 uvicorn(:8000) 内存任务存活
      │◄──前端 fetch 流报错(真·断线)───────────────────────────┤
      │              重启代理9000                            │
      │──Full-Jitter 退避──► GET /chat/stream/{task_id}?after_seq=lastSeqRef+1 续传
```

- 集成组件：`frontend/e2e_case/api-proxy.ts`（node 原生 http 透明转发 9000→8000，进程内自落盘日志 `e2e_case/output/api-proxy.log`；axios 双前缀 `/api/v1/api/v1` 归一化；**不注入 CORS/不自答 OPTIONS**，全部透传后端 CORSMiddleware）
- vite 专用 config：`e2e_case/vite.e2e.config.ts`（`hmr:false` + `strictPort:true`；proxy `/api→:9000` 仅保留给相对路径场景，浏览器实测走绝对 URL 不经过它）

仓库分层：**通用设施** `frontend/e2e_front_lib/`（process.ts/stream-diag.ts/chat-page.ts，全 case 共用）+ **独立用例** `frontend/e2e_case/`（spec + 配套代理/配置，case 专有编排内聚），`tests/e2e/` 已废弃。
- 前端进程/端口封装：`frontend/e2e_front_lib/process.ts`（`ps()` 统一 `; exit 0`；`killPort` 遍历杀全量 listener owner；`waitPortUp` 放宽 2xx~4xx；`startDevServer` 支持 `set "VAR=val" &&` envCmd；`startProxyServer`）

## 十、并行会话多任务E2E测试（PAR专项）

先说清楚一件事。后端永远只有一个（8000端口，启动见6.1），所有并发都压这同一个后端。
所谓“并行”，指的是客户端怎么组织请求，有两种玩法：

- 方法A：一个人同时打三个电话（1个测试进程，同时发起3个会话的任务）。
- 方法B：三个人同时打电话到同一个客服中心（3个独立窗口，各跑各的用例）。

一次并行测试跑完，要能回答三个问题：各会话的回答有没有串到别人家？
有没有两个会话拿到重复的编号？后端日志干不干净？
PAR = Parallel，并行专项用例文件名与编号都带par/PAR，与P0~P9常规用例区分。

### 10.1 名词解释（先懂词，再看方法）

- 会话（session）：一次对话窗口。`send_chat`不传session_id就会新建一个，会测中每个任务独占一个。
- 任务：一个会话里从发消息到收到final的完整一轮。
- 流：每任务一条独立的消息流，读到final算结束。
- 串流：A会话的回答里混进B会话的内容，并行测试最要抓的毛病。
- 幻觉执行：大模型嘴上说做完了，实际上没调工具。工具类任务必须到磁盘上验真货。

### 10.2 为什么要做并行测试（担心什么，就验什么）

| 担心 | 对应机制 | 怎么验 |
|---|---|---|
| 多会话同时跑，回答串家 | E-1流读取、每任务独立缓冲 | 每会话回复必须含自己的关键词 |
| 并发下编号重复 | D-2分配器读写锁 | 全部session_id、user_msg_id两两不同 |
| 同一会话追加消息丢失 | B机制注入+串行守卫 | 会话内追加一轮，消息不少、顺序对 |
| 取消一个会话影响别人 | D-8取消去重+级联取消 | （PAR-03再覆盖） |
| 大模型并发被限流卡死 | P5软配额信号量 | 多会话同时跑不死锁、不500 |
| 并发写库互相锁死 | 共享连接池快照、WAL | DB校验全过 |
| 落库少消息、顺序错 | D-1注入消息补配对 | 消息顺序user在前、数量对 |

### 10.3 方法A：一个人同时打三个电话（主验证，能下结论）

做法：1个pytest进程里用`asyncio.gather`同时发起N个`send_chat`。
每个`send_chat`自己建会话、自己存消息、自己收流收到final。
N条会话、N条流在时间上重叠，后端看到的就是“同一时刻好几个会话在线”。
受压的是后端，客户端是不是多线程不影响结论。

写一个并行用例，照这8条做（另叠加第五章铁律）：

1. 取名：`test_e2e_par_XX_<场景>.py`，编号`E2E-PAR-XX`。
2. 输入隔离：纯对话类给每会话一个专属关键词（用来查串流）；
   工具类给每会话一个专属目录（如E:\test_dir\par_s1/s2/s3，用来验磁盘）。
3. 并发发起：`asyncio.gather` + `send_chat(输入)`，不传session_id，各建各的会话。
4. 先查隔离（MUST）：全部session_id两两不同，全部user_msg_id两两不同。
5. 再逐个会话查全套（MUST，全部复用e2e_helpers，不自造轮子）：
   流正常结束、有终态、无报错事件、回复里有自己的关键词、
   DB（会话/消息/顺序/字段/时间）、流库一致性、步骤合理性、
   日志按session_id过滤后零Traceback、零非安全ERROR。
6. 工具类再加磁盘验真（MUST）：产物文件必须真实存在，内容必须含本会话关键词。
   读盘用字节读+UTF-8/GBK双解码（工具写盘可能是GBK，UTF-8直读会误判，PAR-02实证）；
   读到半截写入时轮询重读几次（流结束与落盘刷写有竞态，PAR-02实证）。
   关键词要选词根（如“丝绸”而非“丝绸之路”），大模型爱意译，太长的词会被它改写掉（PAR-02实证）。
7. 记录：每会话一份`write_test_record`（编号后缀-S1/-S2…），finally里必写；
   再写一份主记录汇总（编号就是E2E-PAR-XX），不然notes/下会留一份空的FAILED占位。
8. 铁律同样适用：真实后端+真实大模型+真实工具+真实库，禁Mock；
   脚本里不设超时（统一pytest.ini timeout=3000）。

运行（独立窗口，输出落盘，见3.3.1）：

```
cd 'F:\OmniAgentAs-repair\backend'; python -m pytest e2etests/test_e2e_par_02_concurrent_tools.py -x --tb=short -v --junitxml='tests/output/PAR_A02_result.xml' > 'tests/output/PAR_A02_out.txt' 2>&1; Set-Content -Path 'tests/output/PAR_A02_done.txt' -Value $LASTEXITCODE
```

记录位置：`notes/测试记录-E2E-PAR-XX[-SX]-<日期>.md`（每会话一份+主记录一份）。

### 10.4 方法B：三个人打同一个客服中心（负载冒烟，只佐证）

做法：开N个独立PowerShell窗口（Start-Process -WindowStyle Normal），
每窗跑一个短用例（如p0_00/p0_12/p0_02），同时打同一个后端。
时序完全独立，最接近真实多用户，但每窗只能自己管自己，断言弱。

输出必须隔离，三个窗口各写各的文件：
`tests/output/PAR_B1_out.txt`、`PAR_B1_result.xml`（B2/B3类推）。
汇总时看：各窗result.xml零失败 + 后端日志无ERROR/Traceback。
它只证明“多进程并发负载下后端扛得住”，能不能过以方法A为准。

### 10.5 怎么算通过（清单）

下面任一条不满足，整个PAR用例判FAIL，走3.5流程：
会话编号全局唯一、消息编号全局唯一、每会话都有终态final、无报错事件、
回复里有自己的关键词、工具数达标（工具类）、磁盘验真通过（工具类）、
DB/一致性/步骤合理性全过、日志零Traceback零非安全ERROR。

### 10.6 和“一次一个case”铁律为啥不冲突

铁律本意是怕不同用例互相污染（日志/DB串了导致误判）。
PAR本身就是一个用例：一次只跑一个PAR文件，里面的多会话做了隔离
（日志按会话过滤、关键词/目录隔离、每会话独立记录），
B的多窗口只做冒烟。所以PAR不是违反铁律，是铁律在并发场景的落实。

### 10.7 标准执行顺序（照着做就行）

1. 按6.1重启后端（独立窗口，health显示healthy）。
2. 先B冒烟（3窗短用例并行），看后端日志干净。
3. 再A主验证（跑PAR用例），记录落notes/。
4. 查后端日志尾部（ERROR/Traceback）与DB，汇总结论。

### 10.8 局限（做不到的，如实说）

1. 方法A是并发请求，不是毫秒对齐的精确竞态；能验证重叠负载下的隔离性，
   复现不了某一个特定竞态。
2. 同一会话两条消息“同时发出”的注入竞态还没覆盖（B-3真正的race点）。
3. N=3只证明3并发没问题，不是压力上限。
下一步PAR-03：同会话双消息对齐同时发、并发取消、压力上限探测。
