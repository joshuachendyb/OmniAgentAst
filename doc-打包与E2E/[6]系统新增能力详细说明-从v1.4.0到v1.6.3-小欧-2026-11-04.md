## 第二章 能力一：输入框引用域（refs）全链路

### 2.1 问题：前端读正文、体积无裁决、回执不闭环

v1.4.0 时文件页已能把文件"引用"进对话，但那是一条**只通不管**的链路，六个缺陷同时存在：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 前端自己读正文（`quote.ts` 读盘、`pages/Files` 又一份、`refresh.ts` 第三份） | 三套读盘口径；大文件把浏览器内存打满 |
| 2 | 点引用读一遍、发送前再读一遍 | 两次全量 IO，纯浪费 |
| 3 | 体积无裁决（注释原文："引用多少发多少"） | 20 个 1MB 文件能直接把上下文顶爆 |
| 4 | 读失败只返回 `reason`，不弹提示 | 用户以为引用成功，发出去才发现没带上 |
| 5 | 同 path 的"整份 + 行区间"两条并存 | 同一文件 token 翻倍 |
| 6 | 无回执通道 | 被拒、被截断、被压缩，用户一概不知 |

### 2.2 架构：读取权收归后端 + 七模块流水线 + 双 scope 阈值

三条硬边界：

1. **正文不在前端**：前端只存标识（path / lineRange / size / mtime），正文由后端按标识读。前端唯一"读盘点"是 `probe.ts`，且只调 `stat` 轻端点取 `size`/`mtime`，不读正文。
2. **裁决不在前端**：体积裁决、行区间切片、同 path 合并全部在后端；前端只负责"把标识排好队"。
3. **阈值单一真源**：`services/refs/limits.py` 一处定义，前端 `store.ts` 的 `MAX_REFS=20` 只是同值双保险。

流水线（`pipeline.py`，首发与插话共用）：

```text
refs 标识 ──▶ resolver（按标识读正文，唯一读盘点）
          ──▶ budget（合计体积裁决：放行 / 等比压缩 / 整批拒）
          ──▶ clip（超长内容头尾摘录）
          ──▶ render（渲染 <引用资料> 块）
          ──▶ notice（回执 DTO + SSE 组帧）
```

阈值（`tuning.refs.*` 可覆盖，比例钳制在 `(0,1]`，越界回落默认）：

| scope | 单条上限 | 合计上限 | 拒绝线 | 说明 |
|---|---|---|---|---|
| `first`（首发） | 基准 × 20% | 基准 × 40% | 基准 × 60% | 超拒绝线整批拒；40%~60% 之间走单轮等比压缩 |
| `interject`（插话） | 基准 × 5% | 基准 × 5% | 基准 × 5% | 单条=合计=拒绝线，超限即整批拒，不降级 |

**预算基准不写死字节数**，而是与 loop 裁剪同源：

```text
预算基准 = context_length − compaction_buffer(20000) − tools_token_reserve(30000)
```

`chars_per_token = 1.86`，由 token 上限反推字符上限——这样换模型（窗口变大变小）不需要改任何常量。

其他关键参数：

| 参数 | 值 | 作用 |
|---|---|---|
| `MAX_REFS` | 20 | 单轮引用条数硬上限 |
| `REF_READ_TIMEOUT` | 5 s | 单条读取超时 |
| `REF_READ_CONCURRENCY` | 4 | 并发读取数 |
| `REF_READ_BLOCK_LINES` | 5000 | 区间读取分块 |
| `REF_HEAD_RATIO` / `REF_TAIL_RATIO` | 0.6 / 0.2 | 摘录头尾比例 |
| `REF_MIN_KEEP_LINES` | 10 | 行压缩后最少保留行 |
| `REF_LOG_PATHS_MAX` / `REF_LOG_DETAIL_MAX` | 5 / 5 | 回执日志点名上限 |

### 2.3 落地：后端 7 文件 911 行 + 前端 8 文件

## 第四章 能力三：上下文装配与压缩预算收口

### 4.1 问题：预算算式各写一份、摘要口径漂移、巨型参数无出路

| # | 问题 | 实证 |
|---|---|---|
| 1 | 预算基准算式在 `compaction`、`prune`、`message_builder`、`refs.limits` 各写一份 | 引用域与裁剪域口径可能各改各的 |
| 2 | 两个"系数"混用：压缩摘要的「限制系数」0.5 与 loop 裁剪的「调节系数」0.8 | 改一处误伤另一处 |
| 3 | 摘要模板六段，实现校验与模板曾经不同源 | 段名一比不一致 → 摘要被弃 → 回退原历史 → 上游 400 |
| 4 | 单轮巨型参数无任何截断路径 | 实测 `write` 90 万字参数（484,992 tok），旧四级缩容跑完一点未减，日志留证"四级后仍超…放行并留证" |
| 5 | 判断用原文尺、裁剪用 feed 尺 | 按 feed 判该裁、按原文裁会过裁 |

### 4.2 架构：agent_utils 单点 + 七段摘要 + shrink 五级阶梯

**预算单点（`agent_utils.py`，160 行）**：

```text
CHARS_PER_TOKEN          = 1.86
trim_budget_base(ctx)    = ctx − compaction_buffer(20000) − tools_token_reserve(30000)
compress_summary_threshold(ctx) = ctx × start_limit_ratio(0.5)      ← 压缩摘要 limit
trim_conv_threshold(ctx) = trim_budget_base(ctx) × trigger_ratio(0.8)   ← 触发线
trim_queue_budget(ctx)   = trim_budget_base(ctx) × trigger_ratio²       ← 队列预算
```

队列预算取**平方**不是笔误：触发线之上再乘一次系数，保证"裁完必低于触发线"，否则裁了仍触发就是死循环。三个函数各自只负责"基准 × 系数"这一层，基准只由 `trim_budget_base` 给出；引用域 `budget_base_of` 直调同一个函数。

**七段摘要模板（`summary_prompt.py` / `summary.py` 同源）**：

```text
Previous Task Goal → Task Plan and Decisions → Important Details
→ Progress → Summary → Important Context → Relevant Files
```

段名匹配容忍三种书写形式（`## 段名` / `段名:` / `**段名:**`），并有"去冒号子串兜底"作为第二重保险——2026-10-25 曾因 `## 段名` 与 `段名:` 不匹配导致摘要被误弃、回退原历史再撞窗 400。七段齐全才通过校验，任一不过返空串走"零退化"路径。摘要以 `assistant` 消息注入（非拼接进 system），并在 feed 末尾补一条 user 收尾指令，把"半截对话续写"扭成"汇总"（实测 16% → 100% 命中）。

**shrink 五级阶梯（`assembler.shrink_to_budget`）**：

| 级 | 动作 | 说明 |
|---|---|---|
| 1 | `truncate_oversized_message` | 单条 content > 4000 字符截断，原文存 `_raw` |

## 第五章 能力四：shell 卡死根治

### 5.1 问题：端口在听，服务已死

这是本阶段**唯一让整个服务不可用**的缺陷，症状极具欺骗性：

```text
SSE 空闲超时 60 秒 + 日志停写 + /health 超时（端口在监听 ≠ 服务活着）
```

唯一可靠定位手段是 `py-spy dump`。根因是三层叠加：

| # | 根因 | 后果 |
|---|---|---|
| 1 | `shell_engine` 同步 `exec()` 跑在事件循环里 | 一条命令挂死 → 全服务僵死 |
| 2 | 完成信号靠临时文件轮询 | 进程半死 → 信号永不到达 |
| 3 | 常驻池锁跨任务共享 | 一个任务持锁，所有任务排队 |
| 4 | `Popen.communicate` 内部起 `_readerthread` | 每次 shell 调用都新建线程；Windows **loader lock** 下线程创建与进程创建互锁 |
| 5 | 读管道线程持锁时 `_started.wait` 无超时 | 一个卡住 = 全站卡住，且无法回收 |

### 5.2 架构：零线程读管道 + ppid 树杀 + 常驻池 + 可回收租约

四个新模块，各解决一层：

| 模块 | 行数 | 做法 |
|---|---|---|
| `utils/proc_io.py` | 176 | **零线程读管道**：fd 改非阻塞 + `poll` 循环（有数据 1 ms、无数据退避到 50 ms），取代 `_readerthread`；进程已退出但管道未 EOF（孙进程/`start /b` 持写端）再等 2.5 s，超时截断且**截断对调用方可见** |
| `utils/proc_utils.py` | 87 | **ppid 全量映射 + BFS 杀树**：根进程退出后孙进程可能仍存活，故枚举所有 ppid 再从根 BFS；全程走 psutil Win32 API，**零 CreateProcess** |
| `utils/workers.py` | 89 | **统一常驻池**：`WorkerPool`（常驻线程消费队列）与 `ThreadLeasePool`（租约式独占），取代 `serial_worker.py` 与两处私有池实现 |
| `utils/spawn_gate.py` | 296 | **全局进程/线程创建闸门**：`popen_init` 与 `thread_start` 安装包裹；`Lease` 可强制回收 + 看门狗巡检 |

闸门参数（这组数字是"什么时候算异常"的唯一判据）：

| 参数 | 值 | 含义 |
|---|---|---|
| `ACQUIRE_TIMEOUT` | 15.0 s | 等锁上限（正常 CreateProcess 在 20 ms 级） |
| `SLOW_WARN` | 1.0 s | 建进程/等锁超过即告警（loader lock 窗口被拉长） |
| `HOLD_LIMIT` | 8.0 s | 持锁上限，超过由看门狗**强制回收**（牺牲该线程，保住全站） |
| `WATCHDOG_INTERVAL` | 0.5 s | 看门狗巡检间隔 |
| 回收前取证 | `_DUMP_POOL`（常驻 1 线程） | 全线程栈落盘到 `logs/pyspy`，且**不在看门狗线程内同步执行** |

另有 `utils/background_tasks.py`（36 行）：`spawn_bg` 统一后台任务生成口，强引用防 GC + done 自摘，替掉 `main.py` 四处"存引用防 GC"注释。

### 5.3 两阶段落地（v1.6.0 / v1.6.1）

| 阶段 | 版本 | 内容 |
|---|---|---|
| **第一阶段（卸载）** | v1.6.0 | shell_engine 同步 exec → `to_thread`；完成信号改 async 事件，免临时文件轮询；常驻池锁拆成任务级；`loop_watchdog` 双证据判据；DB `database is locked` 批修复（chat 高频写点补 `retry_locked=3`）；启动期预热 loop 默认线程池，根除非 shell 工具运行期 `Thread.start` |
| **第二阶段（根治）** | v1.6.1 | `proc_io` 零线程读 + `proc_utils` ppid 树杀 + `workers` 常驻池 + `spawn_gate` 可回收租约；启动期预热 ps7/ps5 + anyio 40 + 各池建满；`/health` 暴露 `runtime_thread_starts` 等闸门指标 |
| **文档与红队** | v1.6.2 | `[9]shell卡死根治` 追加第二阶段 v2.0（loader lock 互锁根因 + 修改⑤~⑧ + 三零判据 + 红队 52 例 + 两阶段关系） |

值得单独记一笔：**第一阶段的"卸载"不够**。把同步 exec 挪到 `to_thread` 只是把阻塞从事件循环挪到线程池，线程本身仍要 `Popen` → 仍要 `communicate` → 仍要起 `_readerthread` → 仍在 loader lock 窗口内。第二阶段把"线程创建"这件事本身干掉了（零线程读管道 + 常驻池），才是根治。

### 5.4 三零判据与带来什么

`/health` 新增 `spawn` 字段暴露闸门指标，运行期判据是"三零"：

| 指标 | 目标 | 含义 |
|---|---|---|
| `runtime_thread_starts` | **0** | 运行期不再新建线程 |
| `gate_timeouts` | **0** | 等锁从未超时 |
| `forced_reclaims` | **0** | 租约从未被强制回收 |

本阶段合并收口后在 8000 开发环境实测：`loop_lag_ms = 1.02`，三零全部为 0。

带来什么：

- **一条命令不再能拖死全站**：最坏情况是单任务失败，事件循环与 `/health` 仍活着。
- **健康检查自己先活**：DB 探测加 2 s 上限，线程池/闸门被占时 `/health` 报 `degraded` 而不是一起挂。
- **死因可判**：等锁超时、持锁超限、慢建进程分别计数，配 `py-spy` 栈落盘。
- **进程树不留孤儿**：根退出后孙进程也会被 BFS 清掉。

## 第六章 能力五：任务级取消链路

### 6.1 问题：取消重复打进协程、终态多生产者

v1.4.0 之前，"取消"是几处各写一遍的松链路：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 两次取消（用户点两下 / 前端重连补发）都直接 `agent_task.cancel()` | 协程被重复打断，异常链混乱 |
| 2 | 终态消息由消费侧与 `agent_runner.finally` 两处都可能写 | 双终态 / 晚到的旧终态覆盖新终态 |
| 3 | start 阶段摘要压缩期间取消 | 摘要不生效且取消不落地 |

### 6.2 架构：claim 幂等 + 终态单生产者

```text
cancel_task(task_id, session_id, source)
  └─ task_registry.claim_agent_task_for_cancel(task_id)   ← 幂等闸：首次调用才返回协程
       └─ agent_task.cancel()                             ← 只有抢到 claim 的那次打断
  └─ 其余重复调用：仅落取消标记，不打协程

终态生产者 = agent_runner.finally（唯一）
消费侧仅在"agent 已结束"时兜底合成终态
```

同一套控制原语同时服务暂停/恢复：`task_cancel_check_and_yield` / `task_pause_check_and_yield` / `wait_for_resume`——取消与暂停都走"检查点 + 让出"的同一形状，不再各写一套。

### 6.3 带来什么

| 变化 | 证据 |
|---|---|
| **重复取消安全** | `claim_agent_task_for_cancel` 首次才打断，重复只落标记 |
| **终态不打架** | 单生产者 + 消费侧仅兜底，`cancelled` 帧不再重复 |
| **start 阶段可取消** | 摘要压缩的 await 点纳入同一检查链 |
| **前端状态收敛** | 取消后 `chatStreamStore` 只收到一条终态，`runningTasksStore` 随之摘除 |

## 第八章 能力七：顶栏状态指示与服务可观测性

### 8.1 问题：只看得见"慢"，分不清死因

v1.4.0 时，前端感知后端只有两个信号：**请求有没有回来**、**过了多久**。于是三种完全不同的故障显示成同一种"慢"：

| 实际故障 | 用户看到的 |
|---|---|
| 进程重启过（内存态全丢） | 慢 |
| 网络/代理慢 | 慢 |
| 事件循环被占死（进程还在，但不再调度） | 慢 |
| 数据库挂了 | 慢 |

而且没有 PID、没有后端地址、没有存活时长——出问题只能靠猜。

### 8.2 架构：三胶囊 + 九档流状态 + /health 诊断字段

**`/health` 从"活着吗"升级为"哪条命、活了多久、卡在哪"**：

| 字段 | 含义 |
|---|---|
| `status` / `version` / `timestamp` | 原有 |
| `db_status` | 数据库自报状态（2 s 上限，拿不到报 `degraded`） |
| `host` | Host 头（前端实际访问到的后端地址） |
| `server_ip` | 本机局域网 IP（剔除 127./169.254./0.，UDP 选路首选、hostname 兜底） |
| `pid` | 进程号（区分"重启过"） |
| `uptime_s` | 进程存活时长（monotonic，不受系统时钟调整影响） |
| `loop_lag_ms` | 事件循环调度延迟点采样（区分"网络慢"与"循环被占死"） |
| `spawn{popen_calls, thread_start_calls, runtime_thread_starts, gate_timeouts, forced_reclaims, wait_max_ms, popen_max_ms, threads}` | 闸门指标（见第五章） |

**顶栏三胶囊**（共用 `PillShell` / `PillTip` 外壳，行数据共用 `streamPillRows.ts`）：

| 胶囊 | 回答的问题 | 关键判据 |
|---|---|---|
| `ConfigStatusPill` | 模型/配置就绪了吗 | `serviceStatus.model_ref` + 配置检查 |
| `ServiceStatusPill` | 连的是谁、这次测出什么、是哪条命活了多久 | 响应耗时毫秒、`loop_lag_ms ≥ 100` 判重、DB 状态、应答时刻、uptime、LAN 地址 |
| `StreamStatusPill` | 当前流在干什么 | 九档 phase + 其余在跑任务逐条列出 |

两个设计细节值得记：

- **数字只在异常时出现**：正常只给"正常"二字，避免顶栏变成仪表盘。
- **Tip 每次打开先静默重检**：保证看到的是此刻真值，不是挂载时的快照。

**九档流状态**（`useStreamPulse`，246 行）——判据拆三线：

| 线 | 含义 |
|---|---|
| `lastBizTs` | 有没有业务产出（真在干活） |
| `heartbeatTs` | 连接断没断（心跳上限 25 s） |
| `lastDataTime` | 对齐 60 s 判死 |

静默阈值 30 s = 后端心跳上限 25 s + 5 s 余量，保证灯不会在"正常静默期"掉档。九档各带 `phase` 标识，表现层按 `phase` 选视觉，**不拿中文文案当键**；标签统一 3 字等宽，胶囊不因档位跳宽。第 9 档 `detached(运行中)` 专治"本页已释放实时连接、后端任务仍在跑"——原逻辑会谎报"连接中"。

**`TitleStreamIcon`**：标题旁圈圈 8 档转速联动流状态；多流挑选改"业务帧优先"（不是"最新心跳优先"）。

**`HeaderWaitClock`**：等待计时三层解耦——`waitTiming.ts`（口径）/ `clockStopwatch`（表盘）/ `waitTimerText.tsx`（数码）。

### 8.3 落地

| 版本 | 内容 |
|---|---|
| v1.5.4 | 服务端信息前端展示研究（`[4]` 报告） |

### 8.4 带来什么

- **四种"慢"分得清**：`pid` 变 = 重启；`loop_lag_ms` 高 = 循环被占；`db_status` 异常 = 数据库；都正常只是耗时长 = 网络/排队。

## 第十章 能力九：数据治理与运维能力

### 10.1 问题：历史只增不减、请求无法对账、改日志要重启

| # | 问题 | 后果 |
|---|---|---|
| 1 | `chat_history.db` 会话/消息只增不减 | 长期使用后库无限膨胀 |
| 2 | 出问题只有"慢"和"错"两条日志，没有请求标识 | 前端报错对不上后端哪一条 |
| 3 | 只有慢请求没有阈值留痕 | 3 s 与 30 s 在日志里一样 |
| 4 | 调日志级别要重启 | 现场排障代价高 |
| 5 | monitoring 落盘在响应路径上同步写 | 慢盘直接拖慢接口（v1.5.6 根治） |

### 10.2 架构：保留期 + X-Request-Id + 日志级别热重载

**保留期（`chat_retention.py`，43 行）**：

| 项 | 值 |
|---|---|
| 配置键 | `system.chat_retention_days`（settings registry：int，0–3650，`restart=True`） |
| 默认 | **0 = 关闭** |
| 环境变量 | `OMNIAGENT_CHAT_RETENTION_DAYS` 可覆盖 |
| 执行时机 | **仅启动时 sweep 一次**（`main.py` startup，`>0` 才执行）；另有一条独立的 monitoring 保留期任务每小时清理 `task_tool_metrics` 等监控数据，两者目标不同，勿混 |
| 失败策略 | 只告警不阻断启动（`degrade`） |
| 非法值 | 非数字/越界 → 本轮不清理，WARNING 降级 |

**请求对账（`main._RequestTimingMiddleware`，纯 ASGI）**：

- 每个响应头回写 `X-Request-Id`；
- 只对 **> 3 s** 的请求落一条 `[slow]` 日志（不刷屏）；
- **计时口径量到 `response.start`（TTFB）即停**——SSE 连接可能挂数小时，按总时长落 `[slow]` 会把所有流式请求都打成慢请求；
- 中间件自身或流式 body 迭代期抛的异常直接穿出本层（头照写、`[slow]` 照记）。

**日志级别热重载（10 s 周期）**：

- 单键 `logging.level`；文件通道按 `>=` 阈值，控制台按 `==` 精确匹配（2026-11-03 撤销双键，北京老陈令"一个值即可"）；
- `uvicorn` 访问日志去镜像化（`UvicornAccessFilter` 挂 logger 级幂等安装），防刷屏。

### 10.3 带来什么

| 变化 | 证据 |
|---|---|
| **库可收敛** | 默认关闭（不打扰），需要时配一个天数即可 |
| **端到端可对账** | 前端日志的 `X-Request-Id` 与后端 `[slow]` 一一对应 |
| **慢请求有阈值** | 3 s 门槛 + TTFB 口径，流式请求不被误判 |
| **现场可调级别** | 10 s 内生效，不用重启丢现场 |
| **响应路径零同步 IO** | monitoring 落盘改 async + `db.atxn` 子线程池 + `create_task` 调度 |

## 第十一章 能力十：打包与部署双形态

### 11.1 问题：开发能跑、发布不会装

v1.4.0 之前，仓库只有"开发模式"一条路：`npm run dev` + `uvicorn`。要给别人用，需要回答三个问题：前端静态文件放哪、后端怎么随包走、用户双击哪个文件。

### 11.2 架构：同源 SPA + Tauri sidecar（后端零改动）

两种形态共用前两步，只在第三步分叉：

| 步骤 | 同源 SPA | Tauri 桌面 |
|---|---|---|
| ① 构建前端 | `npm run build` → `dist/` | 同左 |
| ② 打包后端 | PyInstaller → `OmniAgentBackend/`，`dist` 进 `_internal/web/` | 同左 |
| ③ 组装 | 不需要 | 把整个后端目录拷进 Tauri sidecar 目录 |
| ④ 编译壳 | 不需要 | `tauri build` → 安装包 / 绿色版 |

| 形态 | 启动方式 | 前端与后端关系 | 后端改动 |
|---|---|---|---|
| **同源 SPA** | 双击 `OmniAgentBackend.exe` | 后端 `serve` 静态文件 + SPA fallback，同源 | **零** |
| **Tauri 桌面** | 双击桌面应用 | Rust 壳启动 sidecar，前端 `VITE_API_BASE_URL` 空=同源 | **零** |

前端有一处环境自动检测（`client.ts` 约 5 行 + `main.tsx` 约 20 行 health-check 等待 + `index.html` 1 行），后端一行没改——这是有意的：**打包不应侵入业务代码**。

### 11.3 带来什么

- **交付可复制**：同源 SPA 是"双击即用"的最小形态；Tauri 是"桌面应用"形态。
- **开发/打包同一套前端产物**：两种形态共用第一步构建，不存在"打包专用前端分支"。
- **安全边界清楚**：打包版默认仅本机可访问，首次启动自动部署资源与配置示例。
- **文档齐备**：`同源SPA打包与部署说明-小杨-2026-10-27.md`（304 行）、`Tauri桌面打包与部署说明-小杨-2026-10-27.md`（645 行）。

### 12.2 参数别名 `edit.model → mode`

模型调 `edit` 时把 `mode` 写成 `model`，工具直接参数校验失败。实证：session `12b317fe` 一次 6 条 `edit` 全废。修法是 `tools_alias_mapper.py` 补一条别名映射（2 行）+ `FUNCTIONS.md` 登记（11 行）。小改动，但这属于"用户/模型侧不可控输入"的典型：**别名校准要放在入口，不要放在每个工具里。**

### 12.3 路径可点化与 `PathLink` 单点

v1.4.0 之后，正文裸路径、行内代码路径、工具参数里的路径、产出物路径、文件足迹行，五处都要"能点"。原来各处自写 `button + navigate + 渲染期读项目根`，口径会漂。收口为一个 `PathLink.tsx`：

- 判据（是否可链）、图标、点击口径、不可链接降级全部在组件内；
- 点击时读**实时项目根**，不用渲染期快照；
- 外部绝对路径 → 外部只读预览；根内绝对路径 → 归一为相对后树定位；目录命中只定位不动预览。

### 12.4 懒渲染与流式预处理节流

- `useLazyRender` 见 7.3。
- `useDeferredPreprocess`：流式期每个 chunk 都全量跑一遍文件引用预处理正则（含围栏拆分），长回复下 CPU 明显抖动。改为 `useDeferredValue`——**文本稳定后再处理**，渲染先跟手、预处理随后补齐，最终内容与 `preprocessFileRefs` 逐字节一致。
- `asciiArt.ts`：ASCII 艺术块识别，避免被 Markdown 表格/围栏误解析。

### 12.6 解析失败一律放行（never-trust 口径）

北京老陈 2026-10-28 定原则：

> 解析出错，就是解析失败，必须放行，不能去拦截和进行风险弹窗。解析失败都放行。

### 14.2 六条可复用经验

| # | 经验 | 来源 |
|---|---|---|
| 1 | **"卸载"不等于"根治"。** 把同步阻塞挪到线程池，只是把卡死点从事件循环挪到线程创建；真正的根治要干掉"创建"这件事本身 | shell 两阶段 |
| 2 | **锁必须有超时与回收。** 无超时的 `_started.wait` 会让"一个卡住"变成"全站卡住"；可回收租约 + 看门狗是兜底 | `spawn_gate` |
| 3 | **预算只能有一个基准。** 触发线、队列预算、引用预算必须同源，否则改一处必伤另一处 | `trim_budget_base` |
| 4 | **回执是能力的一部分。** 被拒、被截断、被压缩如果不说，用户会以为成功 | `refs_notice` / chip 五态 |
| 5 | **状态要有唯一主语。** 顶栏演谁、任务属于谁，必须由"页面发布"而不是"猜最新" | `foregroundSessionStore` |
| 6 | **指标要能分辨死因。** `pid` / `uptime_s` / `loop_lag_ms` / `db_status` 四个量合起来才能把"慢"拆成四种 | `/health` |
