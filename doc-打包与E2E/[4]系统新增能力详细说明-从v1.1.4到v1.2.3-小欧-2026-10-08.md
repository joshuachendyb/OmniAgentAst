## 第二章 能力一：shell 执行治理与心跳看门狗

### 2.1 问题：一次 shell 卡死拖垮全服务

v1.1.4 的 shell 工具与其他工具同构：同步 `exec()` 直接跑在事件循环里。后果是连锁的：

1. 一个 `shell` 调用不返回 → 事件循环被占住 → **整个服务僵死**（SSE 不再心跳、health 不再响应）
2. 常驻进程池的锁跨任务共享 → 下一个要 shell 的任务排队等一个永远不会结束的锁
3. 端口仍在监听，**表面健康、实则已死**，只能靠 `py-spy dump` 才能定位

这三条叠在一起，等于「一次 shell 卡死 = 服务不可用且难以定位」。

### 2.2 架构：三层卸载

| 层 | 措施 | 作用 |
|---|---|---|
| **只读分离** | `utils/shell_readonly.py` 独立判定 | 只读命令走独立子进程，不进共享池 |
| **执行卸载** | `utils/astream.py` + 异步流 | 阻塞命令不再占事件循环 |
| **心跳看门狗** | `monitoring/loop_watchdog.py` | 事件循环无心跳即判定僵死并留证 |

三层的分工是清晰的：**只读命令最易处理（走轻量独立进程）；执行命令必须卸载；万一是进程级死锁，靠看门狗留证据**。

### 2.3 分类消亡

| 项 | v1.1.4 | v1.2.3 |
|---|---|---|
| `tools/shell/` 目录 | 3 个文件（`__init__` / `register` / `schema`） | **已删除** |
| register 文件数 | 10 | **9** |
| 工具归属 | shell 独立分类 | 并入 `system`，只读判定独立成模块 |

**这不是"少了个分类"，而是 shell 的执行语义已与其它工具不同**——它需要独立的进程与超时策略，塞在通用注册结构里反而是误导。

### 2.4 带来什么

- shell 卡死从「全服务僵死」降级为「单任务失败」；
- 端口监听不再等于服务健康（看门狗能区分）；
- 工具分类数减 1，但**工具总数守恒**，能力没有缩水。

## 第三章 能力二：连续任务（link）

### 3.1 问题：多轮追问要重建上下文

用户发「继续」时，系统默认把这条消息当**全新一轮**：不带上一轮的任何任务上下文。于是每问一句都要重新解释背景，多轮追问体验割裂。

### 3.2 架构：随消息携带

v1.2.3 的取向是**不做 PATCH 改状态，只让开关随消息发出**：

```
用户在界面勾选「续聊任务」
   ↓
ChatInput → useChatSend(第二参 linkEnabled: boolean)
   ↓
POST /chat/stream  { content, link_enabled: true }
   ↓
编排器携带值落库（chat_tasks 链号）
   ↓
下一轮任务按链号继承上下文
```

**关键取向：改开关不是内容变更，不刷 `updated_at`。** 代码里专门为此把早前一个「PATCH 端点顺手刷 `updated_at`」的副作用删掉了——否则用户只是点了一下开关，这个会话就会被顶到历史列表首位，属不可预期行为。

### 3.3 三批落地

| 批次 | 内容 |
|---|---|
| **A** | `chat_sessions` 增 `link_enabled` 列（复用 `_ensure_column` 幂等迁移器，`COALESCE` 兜存量 NULL） |
| **B′** | 链根口径与编排器切换（链根改「最近一条任意状态」，返回值收窄为 `str`，兜底塌缩为 fail-closed，链根计算下移到注入判定后） |
| **C** | 后端端点与响应字段；随后**删除** PATCH `/sessions/{id}/link` 端点 |
| 前端 | `contextLinkMode` 改名 `linkEnabled` 透传 + 链号徽标 + 持久化三写入点补齐 + 本地优先 |

### 3.4 带来什么

- 多轮追问能承接上一轮上下文；
- 开关状态**只随消息落库**，不存在「界面显示开、DB 为关」这类不一致（那是插话开关踩过的坑，见 4.3）；
- 链接（链号）成为任务的可见归属，界面上能看出这条任务属于哪一组对话。

## 第四章 能力三：插话开关（interject）

### 4.1 问题：任务跑起来后只能说废话

v1.1.4 的活跃任务注入只能在**任务开始前**追加消息。一旦 SSE 已经开始流式输出，用户再发的消息只能等本轮结束才被处理——中间那段等待里，用户无法补一句「顺便也看一下 X」。

### 4.2 架构：会话级开关随消息携带

```
用户在界面打开「插话开关」（会话级，随会话走）
   ↓
POST /chat/stream { content, allow_interject: true }
   ↓
save_message 先落库 → 再判 409
   ↓
编排器读真源 storage.resolve_session_interject
   ↓
若已有任务在跑 → 走 postInterject / interjectSend 独立路径
   ↓
落库为独立块 → 左栏显示「追加 N 条」
```

### 4.3 死锁闭环：一条 409 引出的四环

这个能力在上线时被一个 409 卡死，四环连环，逐个修掉：

| 环 | 病因 | 修法 |
|---|---|---|
| ① | `save_message` 携带值**先落库再判 409** | 原实现先判 409，落库在编排器才做 → 409 门读到的还是**会话旧值**（关）→ 插话第一条**必被拒** |
| ② | 取值与落值两处 | 收敛为 `storage.resolve_session_interject` **单一真源**，编排器与 `save_message` 共用 |
| ③ | 插话在飞时第二发被挡死 | 插话单飞（`resetSendFlags` 统一复位），防网络失败/超限早退卡死 |
| ④ | 关态兜底失效 | 消息落库随携带 `allow_interject=true` + `MessageCreate` 补字段 |

最终形态是**四环一起闭环**，缺任一环都还是死锁。这一点值得记入经验：**一个「必现被拒」的 409，病根往往在写入顺序，而不是在判据本身。**

### 4.4 带来什么

- 任务执行中用户可以追加消息，不必等本轮结束；
- 插话内容以**独立块**落库并在左栏显式标注「追加 N 条」，不与本轮答复混为一谈；
- 发送门判据归一为 `utils/sendGate` 单一真源（原先 `ChatInput` 与 `useChatSend` 两处分叉）。

### 5.1 问题：会话状态散落多处

## 第六章 能力五：思考段渲染体系

### 6.1 问题：思考内容只能纯文本

### 6.2 架构：两套实现一个开关

### 6.3 带来什么

- 思考段从纯文本升级为可排版渲染；

## 第九章 能力八：安全说明体系与目录信任

### 9.1 问题：安全约束只存在于代码里

系统的安全约束（哪些路径受保护、命令如何分类、判定流程是什么）**只写在代码与开发文档里**，使用者在界面上看不到，等于「有约束但看不见」。

### 9.2 架构

三段说明弹框，文案各自落在 `app/datafile/` 下（随 app 整树打包，**零 spec 改动**）：

| 弹框 | 内容 |
|---|---|
| 策略说明 | 五组 22 条 |
| 判定流程 | 含 **mermaid 流程图**（八步表白名单） |
| 目录分类 | 分类表页面直出 |

前端由 `security_docs.py` 提供文案，`DirectoryAccessNote.tsx` 作为页面说明块，`MermaidBlock.tsx` 渲染流程图。

### 9.3 目录信任跨工具生效

原先目录信任是 **per-tool 隔离**：给 A 工具授权某目录，B 工具仍要重新授权。改为**跨工具生效**（北京老陈裁定 B）：

```sql
-- 改前：仅 tool_name 匹配
WHERE session_id = ? AND tool_name = ?

-- 改后：带 path 的信任跨工具通用
WHERE session_id = ? AND (tool_name = ? OR path IS NOT NULL)
```

含义：在同一会话内，信任了某个**具体路径**，则该路径对所有工具生效（不再逐工具重复授权）。

### 9.4 带来什么

- 安全约束从代码里**搬到界面上**，使用者看得见；
- 目录授权从「N 个工具 N 次」降为「一次」；
- 附件区在暂缓期**显式置灰占位**而不是隐藏，用户知道功能存在但未开放。

## 第十章 能力九：历史会话切换根治与卡片重做

### 10.1 问题：进不去，且标题点不动

两个独立缺陷叠在同一个页面上：

| 缺陷 | 现象 | 实测证据 |
|---|---|---|
| **会话加载静默失败** | 地址栏已切到目标会话，页面停在「新会话 / 任务数 0 / 正文空」 | DB 有 41 任务/43 消息；控制台仅 `⏭️ 正在加载中`，成功日志 `🔵 从URL加载会话` 零出现 |
| **卡片标题不可点** | 点标题（最自然的入口）毫无反应，只有「继续」小图标能进 | 卡片 `hoverable` 但无 `onClick` |

### 10.2 架构：减锁——删掉重复守卫

会话加载失败的真因不在加载逻辑，而在**两个守卫并存互斥**：

| 守卫 | 引入时间 | 职责 |
|---|---|---|
| `isLoadingHistoryRef` | 2026-03-13（作"防重复调用"） | 重复调用时早退 |
| `generationRef` | 2026-09-29（修"旧结果污染新会话"） | 旧结果到达时作废 |

两者职责重叠。React StrictMode 双调用下：

1. 第 1 次调用上锁、发请求 → 代际号 1
2. 第 2 次调用代际号 2，发现锁被占 → **早退**
3. 第 1 次的请求返回 → 代际 1 ≠ 2 → **结果丢弃**

**取到数据的被作废，能干活的被锁拦下，谁都没写状态。** `sessionId` 恒为 `null`，于是任务数恒 0。

修法是**做减法**：删掉整把锁，只留代际守卫承担唯一正确性职责。配套一处必改——递归重试的 `return initializeSession(options)` 要改 `return await`，否则外层 `finally` 会在递归仍在加载时提前熄灭 loading 指示器。

### 10.3 卡片四行自排版

| 行 | 内容 |
|---|---|
| 1 | 标题（左，可点进入会话）+ 勾选框（右），行下 1px 分割线 |
| 2 | 消息数 + 状态角标 |
| 3 | 更新时间（靠左）、创建时间（靠右） |
| 4 | 继续 / 删除（压扁） |

两处**弃用 antd 默认结构**的原因都是实测而非推断：`extra` 渲染在 Card 的 head 行，与 body 里的标题不同行，会多出一条空带；`styles.actions` 压不动 `actions > li` 自身 padding，操作行仍过高。改为 body 内自排版后卡片高度从 200+ 降到 **137px**。

跳转入口**收敛为「继续」+「标题」两处**，不给 Card 挂整卡 `onClick`——实测整卡点击会让「点勾选框」也连带跳进会话（`click` 先于 `change` 冒泡，靠 `onChange` 里的 `stopPropagation` 拦不住）。

### 10.4 带来什么

- 从历史页进入**任意**会话真的进得去，且能接着聊（旧会话发消息已端到端验证：该会话由列表第 19 位**升到第 1 位**）；
- 卡片密度提升约 30%；
- 状态角标取值补齐（发现漏 `retrying` 导致角标静默消失）。
