这七条不是并列的功能堆砌，它们共同回答同一个问题：

> v1.0.7 的系统是「能跑」。v1.1.4 的系统是**跑不坏、断不丢、说得清、不污染**。

| 目标 | 由哪些能力支撑 |
|---|---|
| **断不丢** | Journal 让事件可回放；注入让消息可追加 |
| **跑不坏** | 自愈让崩溃可恢复；撞锁让并发不崩 |
| **看得见** | 常驻让状态单一真相源；鉴权让访问可管控 |
| **说得清** | 0 行告警、降级粘滞标记、合并应答 |
| **不污染** | 数据目录隔离让测试与真数据彻底分开 |

### 1.5 工具归组重构（10 类 → 9 类）

这是本阶段**最晚发生**的一次结构改动（2026-10-02），也是唯一动到工具体系骨架的一次。

#### 1.5.1 问题：工具被拆在不属于它的分类里

```text
  sysinfo（获取系统信息）    依赖 psutil
       │                     却和 event_log 分散在不同模块
       ▼
  FUNDAMENTAL 分类                    SYSTEM 分类
  ┌─────────────────────┐            ┌─────────────────────┐
  │ bash / read / timenow│            │ create_task         │
  │ searchweb/fetchpage │            │ event_log  ← 同依赖 │
  │ searchtool / notify │            │ list_tasks          │
  │ sysinfo  ← 错放此处  │            │                     │
  └─────────────────────┘            └─────────────────────┘

  which（查找命令路径）
       │
       ▼
  SHELL 分类 —— 整个分类只有它 1 个工具
```

三处不合理：

| # | 不合理 | 后果 |
|---|---|---|
| 1 | `sysinfo` 与 `event_log` 同依赖 `psutil` 却分开 | 改依赖要动两个模块 |
| 2 | `which` 独占一个分类 | 分类的意义是聚合，单成员分类无意义 |
| 3 | 解压/压缩/媒体读取留在 file，网络搜索留在 network | 跨领域工具归类靠"实现放哪"而非"能力属于哪" |

#### 1.5.2 三层改动

```text
第一层：工具迁移（文件级）
  shell/find_command.py        → system/find_command.py
  fundamental/get_system_info.py → system/get_system_info.py
  shell/ 整个目录删除（3 文件 158 行）

第二层：归类覆盖表（新增单一真相源）
  tool_constants.py 新增 TOOL_CATEGORY_OVERRIDE：
    extract / compress / readmedia  → DOCUMENT
    searchweb / fetchpage           → FUNDAMENTAL
  register 模块从本表取 category，不再各写各的

第三层：零分类守卫
  tool_cache_manager 的 searchtool 描述拼接加条件：
    「该分类确有工具」
```

#### 1.5.3 三个关键决策

**① 为什么零工具分类必须清掉**

```text
  SHELL 分类迁空后若仍留在 searchtool 描述里：

  LLM 想查命令路径 → 调 searchtool 搜「SHELL」分类
      → 该分类零工具，搜不到
      → 重试 3 次
      → 触发熔断 → 整个任务 FAILED

  即：留一个空分类，能让 LLM 把整个任务搞失败。
```

**② 为什么枚举的序号要留空位**

`SHELL` 枚举删除时，其序号 2 **故意留着不动**。因为该序号参与工具搜索描述的拼接排序——如果连序号一起收，会改变描述文本顺序，造成与本次改动无关的行为退化。留空位是零影响的最小改法。

**③ 为什么迁移必须逐字不改**

`which` 的描述、依赖、schema 一字未改（R100 相似度 100%），`sysinfo` 的实现、schema、依赖声明、描述、7 条示例整体搬迁。旧模块的导出表同步移除，无重复导出。**归组是位置调整，不是内容改写**——一旦顺手改描述，就无法区分"归组导致的行为变化"和"改描述导致的行为变化"。

## 第二章 能力一：后端事件 Journal

### 2.1 问题：300 秒的记忆边界

v1.0.7 的续传机制依赖一个**纯内存**的事件缓冲，生命周期 300 秒。这条边界造成两类能力天花板：

| 场景 | v1.0.7 行为 | 用户感知 |
|---|---|---|
| 刷新页面 | 缓冲可能已过期 | 只能拿到残缺的步骤集 |
| 切走再切回（超过 5 分钟） | 同上 | 中间过程消失 |
| 进程重启 | 内存全部丢失 | 任务显示还在跑，实际已死 |

关键缺陷在于：**续传能力的天花板等于缓冲的存活时间**。而这个 300 秒是「看门狗」机制顺带产生的副作用，不是显式设计——没有人决定「事件只能记 5 分钟」，它只是碰巧如此。

### 2.2 架构：双层存储

v1.1.4 采用**热路径 + 持久层**双层设计。

```text
                    事件产生
                       │
        ┌──────────────┴──────────────┐
        ▼                             ▼
  ┌───────────┐                 ┌─────────────┐
  │ 内存缓冲  │                 │  事件 Journal │
  │ (300s 热) │                 │ (持久, 冷底) │
  └─────┬─────┘                 └──────┬──────┘
        │                             │
        │ 读：优先                     │ 读：兜底
        │ (目标 seq 在窗内)            │ (窗内查不到时)
        │                             │
        └──────────────┬──────────────┘
                       ▼
                  SSE 转发给前端
```

两层分工：

| 维度 | 内存缓冲 | 事件 Journal |
|---|---|---|
| 定位 | 热路径 | 冷底 |
| 存活 | 300 秒 | 保留期内（默认 7 天） |
| 读优先级 | 高 | 低 |
| 作用 | 常态低延迟 | 兜底不丢帧 |

这样设计的收益是**不牺牲常态性能**：绝大多数事件在 300 秒内被读到，走内存；只有跨窗的和进程重启后的才落到 Journal 查询。

### 2.3 六个口径

新增模块对外提供六个能力：

| 口径 | 职责 | 典型调用方 |
|---|---|---|
| `append` | 事件追加（异步） | 编排层与 Agent 落库路径 |
| `read_after` | 按序号断点续传读取 | 重连端点 |
| `get_persisted_task_status` | 从库读任务真实状态 | 断线恢复 |
| `is_producer_alive` | 生产者存活探测 | 僵尸判定 |
| `checkpoint_wal` | 预写日志落盘检查点 | 持久化加固 |
| `retention_cleanup` | 超保留期清理 | 独立后台任务 |

**关键设计决策**（实施中踩过坑后定下的）：

| 决策 | 内容 | 为什么 |
|---|---|---|
| 缓冲区创建升为生产唯一入口 | 并发双建时先到者胜 | 防双序列流撞主键，静默吞帧 |
| 内存回收函数改名 | 加 `memory` 字样 | 与 Journal 读库版绝不同名 |
| 任务状态查询改名 | 加 `running` 字样 | 两个语义不同的函数不能同名 |
| Journal 写入双路径注入 | 编排层与 Agent 各注入一次 | 只改一条路径会漏写 |
| 清理做成独立后台任务 | 绝不放进请求链路 | 与既有周期清理正交 |
| 清理范围限已终态 | 在跑任务永不删 | 防删掉正在产生的事件 |

后两条改名的理由值得单说：项目里已有同名的「从内存回收」和「从库读状态」两套实现，若不靠命名区分，调用方很容易用错，而**用错不会报错**。

### 2.4 断线续传完整流程

```text
客户端                     后端
  │                          │
  │  POST /chat/stream       │
  │ ───────────────────────► │  任务起跑
  │                          │  事件产生 ──► 同时写内存缓冲与 Journal
  │  ◄── SSE seq=1,2,3 ────  │
  │                          │
  │  ✗ 网络中断              │
  │                          │  ★ 客户端断开不取消后台任务
  │                          │    （这是产品语义）
  │                          │
  │  ⋯ 期间后端继续产生事件    │  seq=4,5,6 全部落 Journal
  │                          │
  │  GET /chat/stream/{id}   │
  │      ?after_seq=3        │
  │ ───────────────────────► │
  │                          │  读内存：4,5,6 在窗内 → 直接转发
  │  ◄── SSE seq=4,5,6 ────  │  若超窗 → 从 Journal 按序号续读
  │                          │
```

**这里有一个必须强调的语义**：客户端断线**不取消**后台任务。断线重连端点的存在本身，就说明任务在后端继续运行是预期行为。把它改成「断线即取消」是错的。

**重连端点的一处加固**：

```text
原实现：路由函数直接 try 包住生成器
  ✗ 路由是普通 async 函数，它并不迭代那个生成器
    → 生成器体内的异常根本传不到这个 try

加固：在生成器体内兜住回放异常，转「持久化降级」
  ✓ 取消异常不捕 —— 保持客户端断开的原有语义
  ✓ after_seq 改为禁止负数
    负数会让首帧被误判为「缺口」，导致重复推送
```

**前端三处配套，缺一不可：**

| 位置 | 改动 | 缺了会怎样 |
|---|---|---|
| 错误标签 | 补四个状态码的中文标签 | 界面直接显示英文枚举 |
| 事件解析 | 读取降级粘滞标记作观测 | 降级发生了但没人知道 |
| 重连会话标识 | 改三级兜底 | 见下 |

第三条是典型的「看起来能跑但功能失效」：重连时取会话标识，原来只取一处，缺省时发空串。**空串不会报错**，只是让后端的归属校验无从做起，Journal 回放的数据对不上号。

### 2.5 带来什么

| 能力 | v1.0.7 | v1.1.4 |
|---|---|---|
| 断线续传窗口 | 300 秒 | 保留期内均可 |
| 进程重启后恢复 | 不支持 | 支持 |
| 僵尸任务识别 | 无 | 有 |
| 事件可审计 | 否 | 是 |

## 第三章 能力二：统一 token 鉴权

### 3.1 问题：鉴权靠人记

v1.0.7 时代，12 个 router 各自声明令牌校验依赖。这个模式的隐患在代码注释里写得很直白：

> 新加功能路径，忘记写就静默失效。

这是典型的**靠人记性保证安全**。只要有一个新 router 漏写，那个接口就是裸奔的，而且不报错、不告警，测试也未必覆盖到。

### 3.2 架构：唯一挂载入口

v1.1.4 把散装声明收拢为一个函数，鉴权成为**默认行为而非可选行为**。

```text
原：13 处散装 include_router，每处自己记得写 dependencies
    └─ 漏一处 = 一个接口静默裸奔

新：唯一入口
    ┌───────────────────────────────────────────────┐
    │  def _mount(router, tags, *, exempt=False):  │
    │      app.include_router(                      │
    │          router,                              │
    │          prefix="/api/v1",                    │
    │          tags=[tags],                         │
    │          dependencies=None if exempt          │
    │                      else AUTHENTICATED,      │
    │      )                                         │
    │                                               │
    │  _mount(health.router, "health", exempt=True) │ ← 唯一豁免
    │  _mount(tool_router,    "tools")              │
    │  _mount(chat_router,    "chat")               │
    │  ... 共 14 处                                 │
    └───────────────────────────────────────────────┘
```

改法看起来只是把代码挪了个位置，价值却在于**失效模式变了**：

| | v1.0.7 | v1.1.4 |
|---|---|---|
| 新增 router 要做什么 | 记得写鉴权 | 什么都不用做 |
| 漏写的后果 | 接口静默裸奔 | 结构上不可能 |
| 鉴权声明的位置 | 14 个文件 | 1 个函数 |
| 豁免机制 | 各自判断 | 显式参数，唯一入口决定 |

**豁免名单的判定基准**定了一条重要取向：

> 判定基于服务端配置，不看客户端。

理由是服务端认知最可靠。如果默许范围被放大，恶意者不突破限制就等于已经突破限制。因此豁免名单做成服务端侧一个独立模块，被鉴权依赖统一引用，成为**唯一判据**，不允许各处自己写条件判断。

**顺带收口了一类散落逻辑**：密钥与口令的脱敏。原来至少两处各写一遍「空值即未配置」的判断，现在统一到一个出口。看似小事，但它消除一个隐蔽的 bug 源——两处判断哪天改得不一致，就会出现「某处认为已配置、某处认为没配置」的自相矛盾。

### 3.3 带来什么

| 项 | v1.0.7 | v1.1.4 |
|---|---|---|
| 鉴权声明位置 | 分散在 14 个文件 | 单一函数 |
| 漏写风险 | 静默裸奔 | 结构上不可能 |
| 豁免判定 | 各自实现 | 服务端单一判据 |
| 前端登录 | 无 | 登录页 + 授权弹窗 |
| 密钥展示 | 全部明文 | 显隐可控 + 脱敏 |

## 第四章 能力三：活跃任务注入

### 4.1 问题：任务跑起来就只能说废话

v1.0.7 的交互里，一个任务一旦起跑，用户就**失去了对这个任务的发言权**。想改主意只有两条路：等它跑完，或者杀掉重来。

对于耗时较长的任务，这两条路都很糟：

```text
  用户：帮我分析这三个月的销售数据
       │
       ▼
  Agent 起跑 ──────────────────────► 跑 5 分钟
       │                              │
       │  用户想补一句：重点看华东     │  ← 说不了
       │                              │  ← 只能等
       ▼                              ▼
  结果出来了                        但重点看错了
```

### 4.2 架构：注入完整生命周期

v1.1.4 增加了一条注入通道。

```text
  用户在任务跑着的时候追加一句
       │
       ▼
  ┌─────────────────────────────────────┐
  │  POST /sessions/{id}/messages       │  ← 先落库，再决定走向
  └──────────────┬──────────────────────┘
                 │
        ┌────────┴────────┐
        │ 目标任务是活跃的？│
        └────────┬────────┘
              是 │
                 ▼
      ┌──────────────────────────┐
      │  投递进该任务的收件箱     │
      │  返回「已合并」应答       │
      │  + 被并入的任务号        │  ← 明确告知并入哪个任务
      └──────────┬───────────────┘
                 │
                 │  ★ 工具执行过程中不打断
                 │
        ┌────────▼─────────┐
        │  Agent 下一轮     │
        │  调用大模型之前     │  ← 唯一的吸收点
        │  吸收收件箱内容    │
        └────────┬─────────┘
                 ▼
        注入内容作为正常用户消息
        参与本轮推理
```

**应答语义值得单说**：返回「已合并」而不是「错误」或「已创建」，是因为它既不是错误（任务没出问题），也不是新任务（没有新任务）。这个语义如果不显式表达，前端只能靠猜，或者干脆把注入当成普通发消息处理——那就退回到「新建了一个任务」的错误行为。

### 4.3 三条设计铁律

这三条是实施中反复确认的，任何一条破坏都会出问题。

**铁律一：落库行必须绑定执行期任务号**

```text
  ✗ 落库时任务号还没定 → 事后无法归属，历史回显对不上
  ✓ 落库行执行期绑定 → 任务号确定后回填
```

**铁律二：锚点取最后一条**

```text
  多条注入合并成同一个用户消息块时，锚点必须取最后一条
  取第一条会导致后续配对落库全部错位
```

**铁律三：吸收必须发生在裁剪之前**

```text
  ✗ 先裁剪历史，再吸收注入
    → 注入内容不进预算，被当历史裁掉，注入等于没注入

  ✓ 先吸收，再裁剪
    → 注入内容计入保留预算，参与本轮推理
```

第三条特别隐蔽。如果顺序反了，功能表面「看起来在工作」（消息确实进了系统），但实际可能被后续的裁剪逻辑丢掉。这类问题只有在长对话里才暴露。

### 4.4 前端三处表现

| 表现 | 内容 | 作用 |
|---|---|---|
| 提示条 | 「已并入」 | 告诉用户注入成功，且并入哪个任务 |
| 任务列表折叠块 | 展示注入内容 | 事后可查注入了什么 |
| 任务高亮 | 高亮被并入的任务 | 建立「注入 → 哪个任务」的视觉关联 |

**架构上的一处克制**：hook 本身不持有任务选中状态（那是任务选择层的职责），而是通过事件桥把任务号交给属主处理，不跨层直接改左侧栏状态。这样保持了层次边界。

### 4.5 带来什么

| 项 | v1.0.7 | v1.1.4 |
|---|---|---|
| 任务运行中追加指令 | 不支持 | 支持 |
| 应答语义 | 无 | 已合并 + 并入任务号 |
| 注入内容可查 | 无 | 任务列表折叠块 |
| 打断时机 | — | 仅在轮次边界，不打断工具执行 |
| Step 类型 | 18 种 | 19 种 |
| SSE 事件 | 17 种 | 18 种 |

## 第五章 能力四：崩溃自愈

### 5.1 问题：永久的「执行中」

任务状态表有一个致命特性：**只有执行器的收尾块会写终态**。

```text
  正常结束 ──► 收尾块执行 ──► 写终态 ✓
  正常异常 ──► 收尾块执行 ──► 写终态 ✓
  强制杀进程 ──► 收尾块不执行 ──► 状态永远停在「执行中」 ✗
```

后果是：任务列表里永远有一批「正在跑」的任务，而它们其实早就死了。v1.0.7 没有任何自愈机制。

### 5.2 架构：启动期对账

v1.1.4 在启动阶段做一次对账，把残行收尾。

```text
  进程启动
     │
     ├─► 初始化数据库
     │
     ├─► ★ 启动期对账              ← 新增
     │     │
     │     ├─ 取出所有「执行中」的任务
     │     ├─ 判定：是否本进程遗留？（见 5.3）
     │     └─ 是 → 一次性批量更新：
     │           状态     → 失败
     │           错误类型 → 任务被中断
     │           错误信息 → 含启动时间戳
     │           结束时间 → 补齐
     │
     ├─► 注册工具
     │
     └─► 开始服务
```

**这一轮是对账，不是逐个修**。启动期一次性批量处理，零表结构变更，不新增归属列。

### 5.3 归属判据

第一版实现有个严重缺陷：**把所有执行中的任务都当僵尸**。

同机跑多个工作进程或多实例时，实例 B 启动会把实例 A **正在跑**的任务误判为僵尸并杀掉。修法是加归属判据：

| | 无判据 | 有判据（现状） |
|---|---|---|
| 判据 | 状态是执行中就改 | **只看启动时间早于本进程启动时刻的** |
| 单实例 | 正确 | 正确 |
| 多实例 | 互相误杀 | 不误伤 |
| 额外代价 | 无 | 需要记录本进程启动时刻 |

边界要说清楚：**这不是严格归属**。跨时区、时钟漂移等场景下不成立。这一点在代码注释里明确声明了，没有含糊过去。

### 5.4 带来什么

| 项 | v1.0.7 | v1.1.4 |
|---|---|---|
| 进程被杀后任务状态 | 永久「执行中」 | 启动时自动收尾为失败 |
| 僵尸任务识别 | 无 | 有 |
| 多实例互相误杀 | — | 已防护 |
| 错误可诊断 | 难，没有痕迹 | 有错误类型 + 启动时间戳 |

## 第六章 能力五：会话流常驻

### 6.1 问题：流和页面绑死

这是本阶段最大的一次前端架构变更。

v1.0.7 的结构是**每个会话一个 hook**，实时链路和页面状态绑在同一个 hook 里：

```text
  ChatPage
    └─ useChatStreaming(sessionId)
         ├─ SSE 订阅
         ├─ 页面状态          ← 二者绑死
         └─ sessionStorage    ← 跨页续传的唯一依靠
```

后果：

| 场景 | v1.0.7 行为 |
|---|---|
| 刷新页面 | 取消订阅 + 删存储 + 丢续传，全量重装配；只能拿**残缺的步骤集** |
| 切走再切回（超 5 分钟） | 消息流按帧中断，看门狗失效 |
| 切到新会话 | 旧会话的流状态丢失 |

一句话概括：**「会话流常驻」这个能力当时是没有的**。刷新、切页、中断 300 秒，再回来就断了。

### 6.2 架构：全局 Store

v1.1.4 把状态提到全局，拆成五个模块。

```text
  ┌──────────────────────────────────────────────────────┐
  │  ChatPage                                            │
  │  └─ 只订阅快照，不持有流状态                            │
  └───────────────────────┬──────────────────────────────┘
                          │ 读快照 / 写操作
  ┌───────────────────────▼──────────────────────────────┐
  │  chatStreamStore                唯一真相源            │
  │    · 会话状态 + 实时流 + 页面锚点，三态合一            │
  │    · 多会话共存，各自独立                            │
  └───────────────────────┬──────────────────────────────┘
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
  ┌──────────┐   ┌──────────────┐   ┌──────────────┐
  │Transport │   │ Persistence  │   │ Session Hook │
  │断点续传   │   │跨页恢复       │   │会话生命周期  │
  │心跳       │   │              │   │              │
  │重连退避   │   │              │   │              │
  └──────────┘   └──────────────┘   └──────────────┘
```

五块各只做一件事：

| 模块 | 只做一件事 |
|---|---|
| Store | 状态收口，唯一的真相源 |
| Transport | 传输层：断点续传、心跳、退避重连 |
| Persistence | 跨页刷新后的状态恢复 |
| Session Hook | 会话生命周期编排 |
| BackupTypes | 类型定义 |

**目标范式**：

```text
  对话 = 任何时候发起的连贯对话，不随页面生命周期割裂
  SSE  = 流水线数据通道（可断点续传），不是一个活着的页面
```

各场景的应对方式统一了：

| 场景 | 处理方式 |
|---|---|
| 切页面 / 切标签 | 只读取快照 |
| 切换会话 | 挂到 Store，读历史走初始化钩子 |
| 关闭对话框 | 只卸载对话框，Store 仍存活 |
| 停止生成 | 调后端取消改终态，内存侧只调 Store |
| 删除会话 | 调后端删除，内存侧从 Store 删 |
| 多标签并发 | 内存仲裁 + 超时释放订阅 |

### 6.3 删掉了什么

这次重构**主动删除**了三样东西，这是判断重构是否彻底的一个硬指标。

| 删除项 | 为什么必须删 |
|---|---|
| 取消订阅调用 | 有 Store 了，页面卸载不该断流 |
| sessionStorage 设备协调 | Store 才是真相源，存储只是缓存 |
| 待发消息占位 | 同样由 Store 统一承担 |

保留这些会导致「页面卸载即断流」的老问题以另一种形式复活。

### 6.4 实施代价

这一条线的实施体量值得单独记录，它说明前端状态管理的真实复杂度。

| 指标 | 数值 |
|---|---|
| 设计文档版本数 | 16 版 |
| 识别出的实现缺陷 | 18 个（P0 3 个 + P1 8 个 + P2 7 个） |
| 其中规范违反 | 23 处 |
| 中途发现设计缺陷 | 9 次 |
| 推翻自己先前的定论 | 2 次 |
| 走查往返 | 8 个 |
| 最终验证 | 类型检查 0 错，规范检查 0 错，全量 1430/1430 通过 |

**中途发现设计缺陷 9 次**这个数字值得注意——说明初始设计考虑不周，需要在实施中不断修正。**推翻自己的定论 2 次**则说明前期有想当然的地方。

**一条方法论级的教训**：设计过程中有一次分析结论被**下调**过，从「可能造成功能不可用」降为「在特定场景下才会触发」。原因是在主组件里搜索时**漏掉了两个消费方**——它们走的是同一症状的另一条代码路径。

> 影响面分析必须穷举相关代码的前后上下逻辑功能，不能只在症状出处做搜索。

## 第七章 能力六：并发撞锁加固

### 7.1 问题：两个洞都静默

SQLite 是单写模型，并发起跑任务时必然撞写锁。v1.0.7 的问题不在于撞锁本身，而在于**撞锁之后的两个洞都是静默失败**。

**洞一：事务体内撞锁直接抛出**

连接获取和提交两处有保护，但事务体内部的执行阶段撞锁直接抛异常。

**洞二：静默降级**

```text
  计划：写任务行 → 追加步骤 → 写终态
  实际：写任务行撞锁失败（静默）
        → 任务行压根没建立
        → 追加步骤撞非空约束
        → 抛穿成错误与调用栈风暴
        → 日志里看不出发生了什么
        → 事后只能比对数据库才能定位
```

实测记录：一次故障里连撞四记锁，而日志里**一条痕迹都没有**。

### 7.2 架构：四层加固

```text
  ┌──────────────────────────────────────────────────────────┐
  │ 第四层  观测侧                                          │
  │   更新影响 0 行 → 统一告警出口                            │
  │   （原来静默，现在必留痕）                                │
  ├──────────────────────────────────────────────────────────┤
  │ 第三层  写入侧                                           │
  │   任务号缺失 → 显式失败 + 留痕 + 跳过写库                 │
  │   终态更新（四处）→ 有限重试                              │
  ├──────────────────────────────────────────────────────────┤
  │ 第二层  数据库 SDK 层                                    │
  │   事务体执行撞锁 → 有限重试                               │
  │   仅捕锁相关异常，其余原样抛                              │
  ├──────────────────────────────────────────────────────────┤
  │ 第一层  起跑侧                                           │
  │   建任务撞锁 → 有限重试                                   │
  │   耗尽 → 向上抛错，不再静默起跑                          │
  └──────────────────────────────────────────────────────────┘
```

四层分工：

| 层 | 解决什么 | 关键处置 |
|---|---|---|
| SDK 层 | 撞锁本身 | 有限重试，**只捕锁相关异常** |
| 起跑侧 | 静默起跑 | 耗尽后向上抛错，让失败可见 |
| 写入侧 | 任务行没建立 | 显式失败 + 留痕；终态更新加重试 |
| 观测侧 | 0 行无痕 | 统一告警出口 |

**为什么写入侧要特别处理终态更新**：终态更新失败的后果是任务**永久停留在执行中**——就是第五章要靠自愈机制兜底的那个问题。宁可重试也不能让它发生。

**为什么 SDK 层只捕锁相关异常**：如果把所有数据库异常都重试，会把真实故障（约束冲突、语法错误）也重试一遍，既掩盖问题又浪费时间。只有锁是「等一等就好」的，其他错误重试没有意义。

**关键取舍：默认关**。重试能力默认关闭，必须由调用方显式开启。

| 决策 | 理由 |
|---|---|
| 默认 0 次 | 旧调用逐字不变，零回归风险 |
| 只在已证实暴露的并发热写路径开启 | 杜绝全局行为扩大 |
| 退避节奏与既有保护一致 | 不引入第二套等待逻辑 |
| 等待用异步休眠 | 不占用工作线程，避免与内部等待叠加放大 |

注意最后一条：启动期的对账调用**没有**开启重试。这体现了一贯取向——只在真正观察到问题的路径上加固，不搞全面铺开。

### 7.3 带来什么

| 项 | v1.0.7 | v1.1.4 |
|---|---|---|
| 事务体撞锁 | 直接抛出 | 有限重试 |
| 任务行未建立 | 静默 | 显式失败 + 留痕 |
| 终态更新失败 | 永久执行中 | 有限重试 |
| 更新影响 0 行 | 静默无痕 | 统一告警 |
| 起跑撞锁耗尽 | 静默起跑 | 向上抛错 |

## 第八章 能力七：数据目录隔离

### 8.1 问题：测试在写真库

这一条上一版完全遗漏，但它是**架构级**改动。

v1.0.7 的数据目录解析是这样的：

```text
  数据目录 = 硬编码 家目录/.omniagent
       │
       │  在数据库管理器的构造函数里算一次
       ▼
  ┌─────────────────────────────────┐
  │  单例在模块导入期就构造完成       │
  │  → 路径被冻结                   │
  └─────────────────────────────────┘
       │
       │  想改路径？改不了
       ▼
  测试无法与真实数据隔离
```

两个叠加的问题：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 路径硬编码家目录 | 没有任何覆盖入口 |
| 2 | 路径在构造函数里算，而单例在**模块导入期**就构造 | 就算想改，导入顺序也让改动来不及生效 |

后果是**任何走数据库连接的测试都直写真库**。这不是理论风险——实际已发生两次：每跑一次全量单测，真实库里就多出几条空会话、几条垃圾会话。

### 8.2 架构：单一解析点 + 惰性解析

v1.1.4 做了三处改动。

```text
改动一：解析点唯一化
  ┌──────────────────────────────────────────┐
  │  def resolve_db_dir() -> Path:            │
  │      认环境变量 OMNIAGENT_DATA_DIR        │
  │      未设则回落 家目录/.omniagent          │
  └──────────────────────────────────────────┘
  所有需要数据目录的地方都调它，不再各自解析

改动二：解析时机从构造期移到连接期
  ✗ 构造函数里算 → 单例导入期就冻结
  ✓ 连接函数内惰性解析 → 每次取连接都重新认环境变量

改动三：新增测试覆盖口
  数据库管理器上加一个覆盖字典，测试可指定任意库
  含映射表之外的自定义库名
```

### 8.3 一处关键取向：不改生产逻辑迁就测试

覆盖口的设计有一条重要取向：**测试要指向任意库，走覆盖入口，而不是改生产解析逻辑去迁就测试**。

区别在于：

| 做法 | 后果 |
|---|---|
| 在测试里改生产解析逻辑 | 生产逻辑被测试污染，测试一删就出问题 |
| 在生产代码留一个覆盖口 | 生产逻辑干净，测试自己填参数 |

**效果最直观的体现**：任何走数据库连接的测试**自动够不到**真实库，不需要逐个打补丁，也不会漏掉将来新增的测试。这是「让错误无法发生」而不是「让错误被逐个修掉」。

### 8.4 边界

全链路端到端测试**不受影响**——它走 HTTP 打后端进程，库路径由后端进程的环境变量决定，与测试进程无关。这条边界在文档里明确写了，避免后来者误以为端到端测试也被隔离了。

### 8.5 带来什么

| 项 | v1.0.7 | v1.1.4 |
|---|---|---|
| 数据目录解析 | 硬编码家目录 | 单一解析点，认环境变量 |
| 能否覆盖 | 不能 | 环境变量 + 覆盖口 |
| 解析时机 | 构造期，单例导入期即冻结 | 连接期惰性解析 |
| 测试写真库 | 会，且已发生两次 | 不会，自动隔离 |
| 生产逻辑被测试污染 | — | 不被污染 |
| 端到端测试 | — | 不受影响，走独立进程 |

### 9.2 模型库：从猜到读真值

这是本阶段**最值得说的一个缺陷**——它揭示了一类隐蔽的错误模式。

```text
  后端本来就在下发价格元数据
        │
        │  但前端没用
        ▼
  前端靠「模型标识里含不含 -free」来猜是不是免费
        │
        │  实际数据用的是 冒号 free
        ▼
  实测 460 个模型，命中 0 个
        │
        ▼
  免费筛选框恒筛出空列表
```

**这类缺陷最坏的地方在于它不报错**。筛选框正常显示、正常点击、正常返回空结果。从代码和界面上看一切正常，只有用户知道功能是坏的。

修法是让后端下发的元数据成为真值来源。配套做了几件事：

| 改动 | 理由 |
|---|---|
| 改用价格元数据判定免费 | 不再猜 |
| 单行改表格 | 承载上下文、输出价、能力、输入模态四类元数据 |
| 筛选词表来自实勘 | 不靠猜 |
| 输出价只显一项 + 悬浮提示 | 远端价格有 6 个子键，全铺开撑爆列宽 |
| 模型列只显三项 + 悬浮提示 | 原本三行布局把行高撑高 3 倍 |

**筛选词表来自实勘**这一条值得展开。最初的设想是给各种能力参数都加筛选项，实际抓取 460 个模型逐项统计后发现：

| 输入模态 | 覆盖数 | 是否值得设筛选项 |
|---|---|---|
| 文本 | 460 | 不设，全覆盖无区分度 |
| 图像 | 292 | 设 |
| 文件 | 182 | 设 |
| 视频 | 85 | 设 |
| 音频 | 44 | 设 |

而 26 种能力参数里**只有 3 种有区分度**（工具调用、结构化输出、推理），其余 23 种设了筛选项也筛不出东西。

**另一处配套**：后端解析层补齐 8 个元数据字段并就地归一为声明类型。这个取向值得注意——归一发生在**数据入口**，而不是把返回类型退化成任意类型。因为接口挂了响应模型后，类型错了会 500 整个模型库，退化只会掩盖问题。

响应体也从 367KB 降到 1107KB，因为那个原始字段无一处消费。

### 9.3 日志：第二次同病根

2026-08-30 曾经治过一次同类问题：控制台输出阻塞事件循环。当时的修法是引入队列加守护线程，让所有打印走非阻塞入队。

**30 天后同病复发**——但这次是日志通道，而当时只治了打印通道。

```text
  2026-08-30  治了  打印通道      ┐
                                  ├──▶ 同一个病根
  2026-09-29  治了  日志通道      ┘
```

这次的取证很扎实，用进程栈采样工具抓到了卡死现场。

| 证据 | 结论 |
|---|---|
| 探测线程栈停在同步写错误流 | 写错误流阻塞 |
| 事件循环线程停在等同一把锁 | 锁竞争把事件循环一起拖死 |
| 纯内存接口同样超时 | 证明是事件循环停摆，不是数据库或线程池 |
| 日志文件正常写入 | 排除文件处理器 |

修法是新增一个日志处理器，**复用既有的**控制台队列（零新通道零新线程）。

> **这一条是本阶段最值得记的教训。** 同病根 30 天后以不同面貌复发，因为上一次修复**只堵了看得见的那个入口**。根因分析必须问「还有几个入口能走到这里」，而不是「我修的这个洞补上了吗」。

### 9.4 前端系统能力全面检查（成体系的一次审计）

这一条线上一版**完全遗漏**，但重要性高于本节前几项。它不是零散修 bug，而是一次成体系的前端能力审计，产出 41 条候选清单，最终保留 5 条 L3 级问题修复。

| 编号 | 问题 | 危害 |
|---|---|---|
| H3 | 恢复与验证请求**未绕过缓存**，导致缓存拿本快照自证，数据库与界面失联而不自知 | 严重：数据不一致无法被发现 |
| H18 | 任务状态标签未按后端状态映射，原先执行中、已暂停、已取消**全部显示为成功** | 严重：状态误导 |
| H19 | 退出键取消的标记复位只挂在失焦回调上，而 React 18 卸载时不派发合成失焦事件，**标记残留吞掉下一次保存** | 严重：数据丢失 |
| H12 | 终态判定用耗时或更新时间兜底，而这两个条件**恒真**，致运行中的任务被误判为已完成 | 严重：状态错误 |
| H1 | 记忆化漏一个依赖 | 一般 |

**H19 的排查过程值得记**：这是**实施者自查发现的**。首版实现把标记复位挂在失焦回调上，看起来合理，但 React 18 在组件卸载时不派发合成的失焦事件，导致复位根本不执行。这个缺陷用常规测试**测不出来**——因为它只在「输入后立刻切换」的特定路径上出现。

**H3 与 H12 是一对**：一个让界面拿缓存自证而不查数据库，一个让终态判定条件恒真。两者叠加会出现「界面显示一切正常，实际数据库早已失联」的状态。

> **这一条线的教训**：前端的能力缺陷往往不是「功能没有」，而是「功能有但判据错了」。恒真的兜底条件比没有兜底更危险——它会让错误看起来像正确。

### 9.5 其余四项

**任务列表可见性刷新**：切回标签页时重新拉取任务列表。修前用户刷新或切回可见，列表可能停留在旧数据。

**工具可信机制**：新增信任表与六个读写口径，用户对特定路径的一次性信任可落库复用，前端有对应面板。

**设置页布局收窄**：只收一处留白——标签栏的下边距归零。之所以不动卡片内边距，是因为那会波及全部 8 个标签的行间距。另新增一个搜索框宽度常量，**不复用**已有的全局搜索框宽度常量，两者视觉密度诉求不同。

**类型编译中断修复**：一处重连兜底引用了不存在的变量名，导致构建与类型检查全红。这类问题的特点是**一个拼写错误阻断整条流水线**。

> **一处归类澄清**：`allowlist` / `secret_utils` / `type_utils` 三个通用模块的引入提交在 2026-09-26 至 09-27 之间，属基线末尾的 `[72]` 与 `[75]` 工作，**不是本阶段的新增能力**。本阶段只是新增了调用方（统一鉴权入口、零散逻辑收口）。上一版把它们的「新建」与「收口」两件事在同一节里各算一次，属重复计数，此处更正。

## 第十章 一个尚未修复的缺陷

### 10.1 现象

切到某些模型服务商的系（严格校验的工具模式）发消息，必报：

```text
HTTP 400: Error from provider (Console): Upstream request failed:
[invalid_request_error] Invalid function description:
Invalid tool parameters: Strict mode validation failed for function 'bash':
- parameters: Object schemas must have 'additionalProperties: false' in strict mode
```

### 10.2 三处叠加违约

| # | 位置 | 问题 |
|---|---|---|
| 1 | 工具描述模块 + 注册表 | 无条件下发严格模式标记，且注册表不透传该参数，调用方**无法关** |
| 2 | 工具描述模块 | 工具参数原样透传，**不做任何严格模式归一化** |
| 3 | 数据模型产出 | 实跑参数字典：缺 `additionalProperties`；4 个可选字段未列入必填；含联合类型与默认值 |

问题出在**参数定义源头**。基座工具模型共 5 个字段，除主命令外 4 个都是可选，因此全部产出联合类型加默认值。

**这是一场「三连违约」**：补上 `additionalProperties` 后会接着报必填，补上必填后会接着报联合类型，**三条都得改，缺一个都过不去**。

### 10.3 为什么潜伏这么久

| 服务商 | 是否校验严格模式 | 结果 |
|---|---|---|
| agnes / sensenova / qiniu / zhipuai | **不校验**，静默忽略 | 一直好用，从不报错 |
| **opencodeZen 系** | **严格按规范校验** | 首个不合规工具即 400 |

按字母序 `bash` 是最小的不合规工具，所以报错永远指向它。

**这是长期潜伏的设计缺陷**：宽松的服务商把不合规的 schema 掩盖了数月，直到接入一个较真儿的才暴露。

### 10.4 方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A | 全局关闭严格模式 | 一行改完，见效最快 | 丢失参数强校验；且新模型系要求严格模式，改了那些直接不可用 |
| **B（推荐）** | 在工具描述内做**严格模式归一化**：补 `additionalProperties:false`、全字段进必填、联合类型改写为可空类型、剥除不支持的关键字 | 真正兼容严格端；归一化后 schema 语义等价，宽松端不受影响 | 需递归处理嵌套对象与数组，改动量中等 |
| C | 模型库加严格模式开关，按服务商粒度开关 | 精细可控 | 要改配置结构与调用链，多一处真相源 |

**结论：采纳 B + C。** B 作根治（不依赖服务商脾气），C 作兜底（万一再遇更严的，可按模型粒度微调）。改动落在工具描述一个文件加注册表透传，**不散**。

**风险**：归一化若剥关键字剥过头，会让模型丢失参数约束信息（如超时时间的默认值）。故只剥严格模式明确不支持者，描述字段全留——**它是模型唯一的参数语义来源**。
