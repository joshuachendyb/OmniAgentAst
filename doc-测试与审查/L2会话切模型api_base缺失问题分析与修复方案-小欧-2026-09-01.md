## 一、问题现象

老陈在会话中通过 ModelPicker 切换模型后发任务，后端日志出现 503：

```
切 deepseek-v4-flash:
HTTP 503: No available channel for model deepseek-v4-flash under group default (distributor)

切 sensenova-6.7-flash-lite:
[TASK_START] provider=sensenova model=sensenova-6.7-flash-lite
HTTP 503: No available channel for model sensenova-6.7-flash-lite under group default (distributor)
type=AgnesAI_error
```

两处都带 `(distributor)`、第二处明确 `type=AgnesAI_error`，而 sensenova 的 api_base 是 `https://token.sensenova.cn/v1`（非 agnes 域名）→ **请求实际被发到了 agnes 的地址，不是 sensenova 的地址**。

## 二、根因

L2 会话覆盖（sessionModel）切换模型时，前端只保存了 `provider`+`model`，没带 `api_base` / `api_key` / `model_params`；而后端快照用的 key、api_base、model_params 都是**全局 agnes** 的。于是把 sensenova 的模型名发到 agnes 域名 → agnes 分发组没这个模型的通道 → 503 + AgnesAI_error。

**三个要素是密切一组、缺一不可**：
- `api_base`：决定请求发到哪个域名
- `api_key`：决定能不能通过鉴权
- `model_params`（含 `context_limit`）：决定请求体带的推理参数（如 `reasoning_effort`）与上下文上限

并且 config.yaml 里**各 provider 的 api_key 全不相同**（agnes=sk-0bvy*** / sensenova=sk-BW2lJh***），各 model 的 `model_params` 也各异（如 sensenova/deepseek-v4-flash 配 `reasoning_effort: medium` + `context_limit: 900000`）。所以只修任一个都白搭，必须**一起按目标 provider+model 换成正确的**。

**关键约束（老陈拍板）**：api_key 属于敏感信息，不能明文写进 SQLite `chat_history.db` 的 `chat_sessions.sessionModel` 列，也不能经前端往返。故 api_key、api_base、model_params 皆**由后端按覆盖的 provider+model 从 config.yaml 内部查出**，不出后端、不落库。

## 三、为何我脚本实测 deepseek-v4-flash 是 200、程序却 503

我脚本用**正确**的 sensenova api_base（`https://token.sensenova.cn/v1`）+ sensenova 的 key 实测返回 200 OK。反证：模型两端点都可用，只是后端把请求发错了域名、用的是错的 key。

## 四、最终修复方案（后端 3 处：4.1 snapshot 注入 / 4.2 按 provider 查配置 / 4.4 _task_llm_model 同步）

> 前端 `get_model_list` / `ModelListItem` / `ModelPicker` / `chat_models` 全部**零改动**；sessionModel 仍只存 provider+model（晴文本就非敏感）。api_base、api_key、model_params（含 context_limit）均按目标 provider + 目标 model 从 config.yaml 查出，一并喂给快照。

> 1. 先查 `_pv_cfg`/`_pv_key`/`_pv_ebp`/`_pv_ctx`，再拼 `override_ref`，再 `snapshot(...)`。
> 2. `_pv_ebp` 是目标 model 的个性参数（如 sensenova/deepseek-v4-flash 的 `reasoning_effort: medium`），`_pv_ctx` 是其 `context_limit`（如 900000）。

### 4.3 改动逻辑链路

```
切 sensenova/deepseek-v4-flash
  → sessionModel = {provider: sensenova, model: deepseek-v4-flash}   (前后端不变)
  → 后端 _ov.provider=sensenova ≠ 全局 agnes
  → _pv_cfg = config.yaml[sensenova]
      api_base     = token.sensenova.cn
      api_key      = sk-BW2lJh***
      model_params[deepseek-v4-flash] = {reasoning_effort: medium, context_limit: 900000}
  → override_ref.api_base = token.sensenova.cn
  → snapshot(override_ref,
             api_key=sk-BW2lJh***,
             extra_body_params={reasoning_effort: medium},
             context_limit=900000)
  → LLMClient 用 Bearer sk-BW2lJh*** 发到 token.sensenova.cn, 带 medium, ctx=900000  → 200 成功
```

### 4.4 附加：`_task_llm_model` 同步（消除日志/telemetry 显示盲点，三轮会审发现）

**盲点**：`base_agent.py:67` 在 agent 构造时（orchestrator L270 `UniversalAgent(llm_client=ai_service)`）用**全局 agnes** 抓了 `_task_llm_model`。之后 L290 才替换 `agent.llm_client = session_client`，但 `_task_llm_model` 不更新。`react_cycle.py:417/530` 用 `_task_llm_model or llm_client.llm_model` 记录日志/telemetry 的 model —— 因前者非空（agnes）恒优先，故 **日志 `[LLM] 调用#... model=agnes-2.5-flash` 显示错**（实际已切 sensenova）。

- **不影响实际请求正确性**（请求走 `agent.llm_client.request_stream` = 快照，用对端点/key/model_params）。
- **但日志/telemetry model 显示失真**，排查误判；与已做的 TASK_START 修复（显示实际生效模型）同一精神，应一并修正。

**出路（推荐，1 处同步）**：orchestrator 在 `agent.llm_client = session_client` 后同步字段，让日志/telemetry 显示真实生效模型：

```diff
--- a/backend/app/services/chat/stream_orchestrator.py
+++ b/backend/app/services/chat/stream_orchestrator.py
                     session_client = ai_service.snapshot(
                         override_ref,
                         api_key=_pv_key,
                         extra_body_params=_pv_ebp,
                         context_limit=_pv_ctx,
                     )
                     agent.llm_client = session_client
+                    # 2026-09-01 小欧: 同步 _task_llm_model 为生效快照模型, 使 react_cycle 日志/telemetry
+                    # 显示真实生效模型(而非全局 agnes), 与 TASK_START 显示实际生效模型同一精神
+                    agent._task_llm_model = getattr(session_client, "llm_model", None)
                     logger.info(f"[chat] L2 sessionModel 已生效(独立客户端快照): session={session_id}, "
                                 f"provider={session_client.llm_model.provider}, model={session_client.llm_model.model}")
```

> 说明：`_task_llm_model` 已是既有属性（base_agent.py:67 赋值），orchestrator 在此同步仅覆盖值为生效快照模型，不改 agent 核心逻辑；无覆盖时（`session_id` 为空或 `_ov` 为空）不进入本分支，`_task_llm_model` 保持全局，行为与现状一致。
