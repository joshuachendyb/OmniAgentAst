## 一、背景与范围

本轮讨论围绕三件事：

1. **两个 dev 环境缺陷**：长任务切走会话后"运行中"消失；对长任务点"继续"打开空白会话页。
2. **一处长期存在的口径缺陷**：顶栏三件显示的状态，其"主语"与用户眼前实际显示的会话不一致。
3. **一条需要定死的规则**：顶栏三件在会话页 / 非会话页分别显示谁的任务状态。

约束（用户明确要求）：

- 只改开发环境源码（`F:\OmniAgentAs-01`），**不打包、不部署、不覆盖 8500 产物**。
- 调试只用开发后端 `http://127.0.0.1:8000` + 开发前端 `http://localhost:5173`。
- 本轮不提交、不打 tag。
- 不从"补丁堆补丁"的角度修，要按代码规范从全局流程上定口径。

## 二、四个问题与病根（有证据）

| # | 现象 | 病根 |
|---|------|------|
| 1 | 长任务切走会话后，顶栏圈圈/胶囊与历史页"运行中"角标一起消失 | `releaseUnsubscribed()` 在无人订阅 60s 宽限期到点时**无条件** `abort` 连接并写 `status='idle'`；顶栏 `buildStreamPulse()` 与历史 `getActiveSessionStatusList()` 只读这份内存状态，于是一起翻成"无任务" |
| 2 | 对那条任务点"继续"，打开空白会话页 | `resume()` 里 `await resumeStreamRequest()` 内含 `await pump()`，直到整条 SSE 关闭才 resolve；`useChatInit` 把历史加载挂在它的 `.then(...)` 后面，任务只要在推帧就永不 resolve → 页面空白 |
| 3 | 超过 5 分钟的任务，刷新或新开标签页后认不出 | `findLiveTask` 硬编码 `created_at` 300s 年龄窗 |
| 4 | 顶栏显示的状态不属于页面实际显示的会话 | 主语取 `URL session_id ?? readStoredSessionId()`；URL 为 `/`（无 `session_id`）时两者不一致。实测：任务 `task-cc61bd1c…` 在会话 `2c485d92-d164-4fd7-8ca8-6c8f48fb035d` 中执行，胶囊却报"无任务" |

## 三、已修复项（已落盘，未提交）

| 项 | 修法 |
|---|------|
| #2 空白会话 | 新增 `detachResumeStream()`：`resume()` / `attachActiveTask()` 建连后**立即返回** `'recovering'`，把"等待流结束"从调用链摘掉；`'recovering'` 不产生 toast。流仍由 `resumeStreamRequest` 全权负责建连/重连/轮询/终态/收尾 |
| #1 运行中消失 | 新增 `settleReleasedSession()`：宽限期到点时以后端 `chat_tasks` 为权威 —— `executing` → 保留非终态并每 `RELEASED_RECHECK_MS`(60s) 复核；终态 → 落真实状态；无任务 → `idle`；**查询失败 → 保留 + 复核**（绝不拿失败当"已结束"）。`releaseUnsubscribed()` 只负责排一个单飞 `releasedTimer`，句柄在 `clearSessionTimers` 统一清理 |
| #3 长任务认不出 | `findLiveTask(sessionId, excludeTaskId, maxAgeMs)`：发送去重传 `LIVE_TASK_FRESH_MS`(300s)，恢复/展示传 `null`（不限龄）；`attachActiveTask` 透传；`resume()` 重新锚定 taskId 时同样不限龄 |
| #1 配套相位 | `StreamPulse` 增 `released` 标志 + 第 9 相 `detached`（文案"运行中"，`.spin-detached` 动画 3s），位置在 `!pumpActive` 分支之前；`sameView` 参与比较 |
| #4 上半（中间步骤，已被第四章定稿取代） | 顶栏三件先收敛为"只认当前会话"：`buildStreamPulse(foregroundSessionId)` + `getPulse(id)` + `useStreamPulse(foregroundSessionId)`（按 id 缓存）；删除 `isBetterPick` / `lastActivityOf` 等"谁最近出数谁上镜"的挑选逻辑。此步只解决了"会话页主语不对"，非会话页仍会静止，故按 4.1 规则再收一次口（见 #4 下半） |
| #4 下半（定稿口径） | 主语升为 `PulseSubject`：会话页 = ChatPage 发布的 `{mounted, sessionId}`（空会话 → 静止），非会话页 = `LATEST_RUNNING`（本标签内开跑最晚且仍在跑）。排序键 `serverTaskStartedAt`（任务自身常量：start 帧时刻 / DB `created_at`），平局按 taskId 字典序。壳层解析主语，三件只收 `subject` |

实测验证：

- 新标签页打开一条已跑 >5 分钟的任务 → 标题 + "任务数 1" + 历史 + `GET /chat/stream/task-…` + 胶囊"流持续"。
- 切走会话 72s 后出现 `[Store] 无人订阅宽限期到…`，条目保持运行中，不再被强制写 idle。
- `npm run typecheck` 与改动文件的 eslint 通过。

## 四、顶栏主语规则（定稿，不再变）

### 4.1 规则表

| 场景 | 顶栏三件显示谁 |
|------|---------------|
| 会话页在眼前 | 该页正在显示的那个会话（ChatPage 发布 `{mounted, sessionId}`）；新建空会话 → 静止 |
| 非会话页 | 候选集 = 本标签页内**此刻仍在跑**的任务 → 取**开跑最晚**那条 |
| 非会话页、候选集为空 | 静止 / 无任务 |

### 4.2 竞争问题的解（排序键）

竞争的病根是"用会话的 `updated_at` 推断任务新旧"——该字段**任务每写一步就刷新**，两条任务交替落库即交替变大，图标来回跳。

**解**：排序键改用任务的 `created_at`（任务生命周期内是常量）。两条任务落库时间差 1 毫秒也不参与排序，图标没有可抖的键。因此：

- 不需要去抖、不需要滞后窗口、不需要锁；
- 主语只可能因两件真实事件改变：① 有新任务开跑（只可能发生在会话页）；② 当前主语任务结束（顺位给次新的在跑任务）。

### 4.3 老任务会不会被压住

"仍在跑"是**筛选条件**，不是选中即锁。每秒重算一次候选集，任务一旦结束立刻退出候选：

| 时刻 | 事件 | 顶栏显示 |
|------|------|---------|
| 10:00 | A 开跑（长任务） | A |
| 10:05 | B 开跑（短任务），A 仍在跑 | B（B 更晚开跑） |
| 10:07 | B 结束 | A —— B 退出候选，顺位即 A |
| 10:20 | A 结束 | 静止 / 无任务 |

因此"最晚开跑的先结束、老任务被压死"不会发生。若 B 在用户走到非会话页之前就已结束，B 从一开始就不在候选内，直接显示 A。

### 4.4 固有代价与平局

- **固有代价**：B 在跑的那段时间里，A 不上镜。同一时刻只能显示一条，规则必须确定，否则就是抖动。A 并非无痕：胶囊悬浮窗显示"并发 N 条"，并列出主语的任务号。
- **平局**（同一毫秒开跑，实际不可能）：按 taskId 字典序固定，在跑期间不变。

## 五、已否决方案（记录在案，防回潮）

| 方案 | 否决理由 |
|------|---------|
| 后台会话"谁最近出数谁上镜" | 显示内容与用户所看画面不一致，且会抖动 |
| DB 状态兜底 + 10s 轮询 + 静态"运行中"相位 | 轮询加负载，静态态是编造状态 |
| 非会话页取一次 `GET /sessions?page=1&page_size=1` + 后端 `append_execution_step` 刷 `updated_at` | 用"会话最新"间接推断"任务最新"，正是抖动来源，且要动后端 |
| 按落库时间（`updated_at`）排序 | 可变键，两条任务交替写库即翻脸 |
| 在跑任务轮流显示 / 三件改成分组列表 | 一直抖 / 顶栏放不下且改变 UI |
| 为 429 增加分类特判 | 429 是 provider 真实的 tpm/rpm 限流，类型优先的分类是对的，**不是缺陷** |

**结论：本轮后端零改动。** 原计划的 `touch_session_updated_at` 注入 `append_execution_step` 已撤销。

## 六、能力边界（v1.2 已突破，见第十章）

v1.0/v1.1 的边界：本标签页从未持有该任务的流 → 顶栏静止。典型情形：刷新后停在 `/history`、别的标签页起的任务。

**v1.2 起**：在跑列表与顶栏主语都以后端 `chat_tasks` 快照为准（`GET /sessions/tasks/running`，只读、单条 SQL、不轮询），
刷新/换标签页后仍显示全部并发任务（历史页角标 + 一览条 + 顶栏浮层"其他在跑"）。仅当后端不可达时退回内存口径
（`console.warn` 留痕，保留上次结果，宁可少刷新一次也不闪成 0；绝不编造"运行中"）。

## 十一、C 方案：强类型 + 穷尽检查（v1.3，2026-11-03 17:03:45，小欧）

### 11.1 为什么不改词（北京老陈问"统一成一个词不是更好"）

统一词更彻底，但它改的是**数据契约**，且删不掉翻译层：

1. 系统里有**三套**词表，不是两套：`chat_tasks.status`（5 值）、后端 `AgentStatus`（8 值，含 `thinking`/`suspended`）、前端 `StreamStatus`（8 值，含 `active`/`recovering`）。
2. 就算把 DB 与前端统一成 `active`，`AgentStatus.THINKING → DB executing`、`SUSPENDED → paused`、`RETRYING → failed` 这三条映射仍在 `agent_runner._m/_STATUS_MAP` 里，翻译层照样存在。
3. 前端多出的 `recovering`（断线续传）、`retrying`、`idle` 是客户端连接相位，DB 永远不该有 —— 边界层必须回答"DB 给了前端不认识的值怎么办"，改词只能把答案从 5 行缩成 1 行。
4. 真改词要动：后端 5 处字面量 + **一次性写库迁移**（`~/.omniagent/chat_history.db` 与 8500 生产库的历史 `executing` 行）+ 前端 10 处 + sessionStorage 旧备份；且迁移必须幂等并排在 `reconcile_orphaned_tasks` 之前，否则僵尸行永远收不了尾。

结论：真正的病根不是"词不一样"，而是 `Record<string, ...>` 让 `undefined` 静默通过类型检查。**让编译器抓**比**让人记得**更可靠，且零迁移。

### 11.2 落地内容

| 层 | 改动 |
|---|---|
| 后端词表 | `app/constants.py` 新增 `ChatTaskStatus`(str Enum) + `CHAT_TASK_TERMINAL_STATUSES` / `CHAT_TASK_STATUSES` / `CHAT_TASK_NON_RUNNING_STATUSES`，作为 `chat_tasks.status` 单一真源 |
| 后端收口 | `storage.py`：INSERT 字面量、`reconcile_orphaned_tasks` 的 WHERE、`list_running_tasks` 的排除集全部改引常量（原三处各写一份，加状态值必漏改） |

### 11.3 编译期拦截实测（证据）

临时把历史页 `TAG` 的 `retrying` 键改名 → `npm run typecheck`：

```

does not exist in type 'Record<"paused" | "retrying" | "active" | "recovering", ...>'
```

临时删除该键 → `npm run typecheck`：

### 11.4 边界设计原则（后续新增状态值照此办）

- **边界开放**：后端数据进入前端时类型仍是 `string`（`RunningTask.status`），先过 `toStreamStatus`，未知值告警。
- **内部封闭**：进入 store 之后只认 `StreamStatus`；映射表一律 `Record<StreamStatus|RunningStreamStatus, ...>`。
- **禁止**：`as StreamStatus` 断言、`Record<string, ...>` 映射表 + `?? 原文` 兜底（后者会把漏键静默变成英文原值）。
