## 零、设计基础需求与约束

### 0.1 使用场景

单机部署、单用户使用、多会话并存，这是记忆设计的起点。单机意味着没有网络分区与分布式一致性问题；单用户意味着不需要 tenant/user 多租户维度；多会话意味着记忆必须跨会话复用，且要处理"同一代码库不同事项"与"不同类型任务"并存的情况。

任务类型有相同也有不同：相同类型如不同会话处理同一个代码库的不同事项，这是程序记忆价值最高的场景——一次教会的步骤模板应在后续会话复用；不同类型并存则要求情景记忆按会话／任务隔离检索，避免把 A 任务的经验灌给 B 任务。四类记忆一起设计、一起实施，按阶段一（底座）／阶段二（四类读取与注入）／阶段三（治理与优化）推进，不按记忆类型分期（见 2.7、3.2.6）。

### 0.2 数据量约束：单机不等于小数据

单机单用户不代表数据量小，有两个明确的"大"：

- **代码类任务的代码库很大**：不同会话对同一个大代码库做不同事项，`chat_task_steps` 与代码图／索引的体量都大；
- **事务处理的知识库可能很大**：后续接入的知识库装大批量文档与块（R3 父子块：父块 800 字给 LLM、子块 200 字建索引；此 800 是字数，与记忆注入的 800 字符预算分属两套口径），原文按版本永久保留，体量只会增长。

现状实证：现有 `chat_task_steps` 已是百万行级（历史上出现过 185 万行／2.7GB 的膨胀），后续叠加知识库会更大。因此：

- 记忆读取必须是"按签名／场景检索 top_k"，禁止全表扫描；复用现有 `idx_steps_task`、`idx_steps_session` 索引；
- 注入必须设硬预算（800 字符）与裁剪，超限时记忆先于任务上下文被裁；
- 知识库检索走 FTS5 零依赖，不引 Milvus／Neo4j 等外部服务；
- 知识库与记忆互补不合并（见 2.8）：知识库存大批量外部文档原文，记忆只存少量运行经验，避免把知识库当记忆用导致上下文膨胀。

### 0.3 注入与上下文约束

沿用现有 `message_builder`，不新增 LLM schema 参数（R1 硬约束）。记忆注入必须落在 `conversation_history` 的 system 消息上，在任务启动装配阶段一次注入、全任务常驻（见 3.2.4）。记忆是"历史参考"不是"当前事实"：模板与当前步骤冲突时标注需核验，不自动覆盖当前决策。配置开关默认关，实测通过后才开。

### 0.4 进程模型约束

当前服务单进程部署（`run_server.py` 用 `uvicorn.Config + Server` 编程式启动，无 workers 参数），多会话靠 asyncio 并发。`running_tasks`、`agent_streams`、`_timer_callbacks` 等是进程内模块级 dict，用 asyncio 同步原语，跨进程无效。因此记忆层必须只读派生、从 DB 读取，不依赖任何进程内状态——这是记忆层对单／多进程中性的前提。若将来改多进程，需要外置的是 SSE buffer、取消／暂停标记、定时器句柄，这些都与记忆设计正交（记忆只读 DB，不依赖这些进程内状态）。

### 0.5 治理与安全约束

写入门槛（显式 pin 或频次≥3 才升级为长期记忆）、TTL=90 天过期淘汰、按 `source_task_id`／`source_session_id` 溯源与一键失效，三者共同防记忆污染（R2/R3）。阶段一~二只读派生、不写记忆，天然无污染。

数据读写走 `db.get_conn`／`db.atxn` 现有通道，不改生产解析逻辑；配置读写经 `get_config_path`，不硬编码路径；测试用 `db._db_overrides` 覆盖口，不碰真库。

### 0.6 工程规范约束

公用函数先查 `backend/FUNCTIONS.md`，有则复用、无则新建并登记；新建 `app/services/memory/` 模块与现有 `app/services/*` 服务结构对齐；代码头部按规范写编辑历史（署名+日期）。禁止以测试代码固化错误记忆逻辑，测试只用于发现问题，不提交测试 case 到仓库。文档按规范保留版本历史、章节连续，正文用标题+段落的人类写法。

### 1.2 各文档设计要点（记忆相关）

**1.2.1 R1 第59号文档（纲领，最新）**

- 现状实证：只有"会话历史 + 上下文压缩"（`compaction/`、`HistoryMemory`），无独立用户画像、无跨会话长期记忆、无程序性记忆；全仓 `memory/profile` 均指进程内存或模型能力画像。
- 解决目标："越用越懂你、一件事教一次即可复跑"。
- **不"三件套一起做"**：原文把"画像表 + 跨会话事实库 + 程序性记忆"打包称最小可行，实为三个子系统；只先做程序性记忆。
  - 程序性记忆（先做、零新表）：`chat_task_steps` 已完整记录每任务步骤序列，可直接沉淀为可复跑流程模板；
  - 用户画像（后置）：结构化偏好（常用路径、口头习惯、授权偏好）一张表，确有"每次重述偏好"痛点再加；
  - 跨会话事实库（后置）：SQLite + 简单检索即可，不引向量库。
- 附加约束：记忆注入沿用现有 `message_builder`，不新增 LLM schema 参数；注入量必须设预算与裁剪（复用 compaction 容量控制思路），否则记忆膨胀挤占任务上下文。
- 与持久调度器相关（例行任务复跑依赖程序性记忆），与多端/推送无关；可独立启动，不依赖阶段 1~3。

**1.2.2 R2 研究报告（治理机制来源）**

- 三分类：语义记忆（事实、实体、偏好，长期可更新）、情节记忆（做过什么、结果如何，事件表+摘要滚动淘汰）、程序记忆（SOP、工具用法、失败教训，结构化规则文件版本化）。
- 工程要点：对话后 LLM 抽取"值得记住的"条目噪音极多，必须有淘汰与合并策略；写入门槛 = 出现频次 + 冲突检测 + 用户显式 pin；污染防护 = 可溯源 + 一键失效。

**1.2.3 R3 落地方案与代码骨架（机制与预算来源）**

- 技术选型：不引 Milvus/Neo4j；记忆走同库单表 `kb_memories`；先做语义记忆，情节/程序记忆真需要再做（YAGNI）。
- DDL：`kb_memories(id, tenant_id, user_id, kind, content, hit_count, pinned, expired_at, created_at, updated_at)`，`kind` 取值 `semantic/episodic/procedural`。
- `kb/memory.py`：`remember()` 重复内容累加频次、达标延寿；`recall()` 只召回 pinned 或频次达标且未过期；`forget()` 用户显式遗忘。`MEMORY_PROMOTE_HIT`、`MEMORY_TTL_DAYS=90`。
- 预算：`kb_context.py` 的 `MEMORY_BUDGET=800`（记忆注入字符上限）、`RETRIEVAL_BUDGET=3000`；注入格式 `[长期记忆]\n...`。

**1.2.4 R4/R5 7月设计（检索与蒸馏来源）**

- `long_term_memory(scope/content/keywords/source_task_id/created_at/access_count)` + `memory_fts` FTS5 虚表 + 三同步触发器；FTS5 不支持时降级 LIKE。
- `MemoryStore.add_memory / retrieve / distill_and_store`；去重（相似度 > 80% 仅更新 access_count）；蒸馏门槛（步数≥5 且回答>200字）以避免短任务浪费 LLM 调用。
- 注入：`initialize_run_state` 中 `_inject_long_term_memory` 经 `inject_history` 注入 system 消息（**此注入点已随代码演进而失效，见 3.1.4**）。

### 1.3 设计演进与裁决冲突

| 冲突点 | 旧设计 | 最新裁决（R1） | 本设计取舍 |

**逐行解读（术语讲成人话）**：

- **先做哪类**：老方案想先存"事实/知识"（语义），新裁决说别——先做"教一次就能复跑"（程序），事实库往后放；本设计据此定案四类一起做、价值上程序优先（见 2.7）；

- **注入点**：老方案把记忆塞进 `initialize_run_state`，但代码早就不在那儿装配历史了（挪到了 start 装配段），所以必须改道走 `_injected_history_msgs`；
- **检索**：老方案想上向量库／LLM 蒸馏，新裁决说别——前两期不建表、不额外调 LLM，真有需求再加 FTS5。

## 二、记忆系统的分类、应用场景、对象与价值

### 2.1 四类记忆的定义与边界

用户问"长期记忆？程序记忆？还有情景记忆？"——本系统采用四类口径，其中前三类是业界通用分类，第四类是 R1 单列的应用侧概念：

| 类别 | 回答的问题 | 内容 | 生命周期 | 本系统对应 |
|---|---|---|---|---|
| **语义记忆 Semantic** | "知道什么" | 事实、实体、偏好、知识 | 长期，可更新 | R1 的"跨会话事实库"（后置） |
| **情景记忆 Episodic** | "经历过什么" | 做过什么、结果如何、当时的上下文 | 滚动淘汰 | 尚未显式建设；原料已在 `chat_tasks`/`chat_task_steps`/`process_events` |
| **程序记忆 Procedural** | "会做什么" | SOP、工具用法、失败教训、可复跑流程 | 版本化、长期 | R1 的"程序性记忆"（先做） |
| **用户画像 Profile** | "你是谁" | 常用路径、口头习惯、授权偏好 | 长期，结构化 | R1 的"用户画像"（后置）；可视为语义记忆的结构化子集 |

"长期记忆"不是与这三类并列的第四种记忆，而是**跨会话持久化的总称**：语义、情景、程序三类只要跨会话留存，都属于长期记忆。R1 中"长期记忆/程序性学习"的提法即"长期记忆方向里先落程序性学习"。

术语口径：本文统一用"情景记忆"与"程序记忆"；R2 原文的"情节记忆"即情景记忆，R1 的"程序性记忆"即程序记忆，均为同一概念的不同叫法。

### 2.2 短期记忆与长期记忆的辨析

承接 2.1 的"长期记忆是跨会话持久化的总称"，需要明确四类记忆与短期记忆的分界，避免与系统已有的会话上下文机制重复建设。

**按存储周期判定**：程序、语义、画像三类都是长期记忆——跨会话留存，学会或确认后长期可用；情景记忆是"长期存储 + 滚动淘汰"：原料（任务、步骤、过程事件）随库长期留存，但召回窗口偏向近期，远期事件价值衰减（与 R2 的"滚动淘汰"一致）。因此四类都属于长期记忆方向，区别只在淘汰策略，不在是否跨会话。

**本系统真正的短期记忆**（与四类记忆正交，已成熟，不重复建设）：

| 载体 | 生命周期 | 代码位置 |
|---|---|---|
| `conversation_history` / `temp_history` | 当前任务上下文，每次任务运行 `reset_per_run()` 清空（per-run，非 tool loop 每轮） | `message_builder.py:326-333` |
| `_injected_history_msgs` | 注入历史，每次任务运行清零（任务级，非 tool loop 每轮），防 agent 复用跨任务串味 | `initialize_run_state.py:83-89` |
| 进程内存缓冲（`StreamBuffer`、`_timer_callbacks`、`chat_stream_events` 内存队列） | 重启即丢，非持久化 | `task_state.py` / `timer_set.py` / `stream_event_journal.py` |

**还有一类中期／任务级记忆**：压缩摘要（`task_summary`、锚定摘要）跨轮、跨链但依附会话，介于短期与长期之间，由现有 compaction 机制承载（见 3.1.5）。

一句话：短期记忆（会话上下文 + 压缩）系统里已经很成熟；本次设计的是长期记忆层，两者职责分明，不重复建设。

### 2.3 情景记忆做哪些（专项回答）

**定义**：情景记忆是"那一次具体经历"——带时间、任务、步骤、结果、上下文的事件记录；与程序记忆的区别是"那一次的经过"（情景）vs "可复用的做法"（程序）；与语义记忆的区别是"有场景的事件"（情景）vs "无场景的事实"（语义）。

**在本系统里情景记忆做这些事**：

| 场景 | 做什么 | 数据来源（均已落库） | 价值 |
|---|---|---|---|
| 断点续跑 | 记住"上次这件事做到哪了、下一步是什么" | `chat_tasks.status/task_summary/context_link_mode`、`chat_task_steps.step_index` | 中断恢复后不从头再来 |
| 失败教训 | 记住"这个方法上次失败，原因是..." | `chat_tasks.error_type/error_message`、`chat_task_steps` 中 `error` 步 | 避免重复踩坑，决策前先查历史失败 |
| 决策溯源 | 记住"当时为什么选了 A 方案" | `chat_task_steps` 的 `thought/reasoning`、`artifacts`、`process_events` | 后续变更可追溯，可解释 |
| 例行复跑依据 | 定时到点时，"上次这个例行任务怎么干的、结果如何" | `chat_tasks.creation_source=system_triggered/system_resume` + 步骤表 + `timers` | 与持久调度器协同，让"到点自己干"有历史可依 |
| 巡检与对账 | 任务历史可回看、可统计、可核对 | `chat_tasks`、`chat_task_steps`、Journal `chat_stream_events` 三源对账（已实现） | 问题定位有据，不靠猜 |

**关键事实**：情景记忆的原料**已经全部在库**——`chat_tasks`（任务级：输入/输出/状态/摘要/产出物/创建来源）、`chat_task_steps`（步骤级：有序步骤 JSON）、`chat_tasks.process_events`（过程事件快照）、`chat_sessions`（会话级）。因此情景记忆不需要新表，只需要"按场景检索 + 预算内注入"的读取层。

### 2.4 各场景记忆的价值矩阵

四类一起设计实施，下表"价值兑现阶段"指该价值在哪个实施阶段兑现，不表示记忆类型有先后。

| 场景 | 主用记忆类型 | 价值 | 价值兑现阶段 |
|---|---|---|---|
| 同类任务再来一次，教过就会 | 程序 | 省去重复说明步骤，一次教会永久复跑 | 阶段二 |
| 中断/重启后接着干 | 情景 + 程序 | 恢复进度与方法，零重述 | 阶段二 |
| 上次失败的方法别再用 | 情景 + 程序 | 降低试错成本 | 阶段二 |
| 定时例行任务到点自己干 | 程序 + 情景 | 与持久调度器闭环，历史可依 | 阶段二（调度内核已完成） |
| "你上次给我配的那个路径/偏好" | 语义 + 画像 | 越用越懂你 | 阶段二~三 |
| 跨会话事实/结论复用 | 语义 | 不重复调研，知识沉淀 | 阶段二~三 |
| 手机看/批、主动推送 | 与记忆正交 | 不属于记忆方向 | 不在本设计范围 |

### 2.5 分类与 R1"三件套"的映射

| R1 三件套 | 本设计分类 | 处理 |
|---|---|---|
| 程序性记忆 | 程序 | 阶段二打通读取，零新表，从 `chat_task_steps` 派生 |
| 用户画像（一张表） | 画像 | 阶段二打通读取并默认关，阶段三确有痛点再加结构化表 |
| 跨会话事实库 | 语义（+部分情景） | 阶段二打通读取并默认关，阶段三按需 SQLite + 简单检索，不引向量库 |

情景记忆在 R1 中未单列，但原料已完备且对"断点续跑/失败教训/例行复跑"价值直接，本设计将其纳入**阶段二的四类读取层**，与其余三类一起实施，不新增表。

### 2.6 不同 agent 任务类型的记忆价值

2.4 的矩阵按"使用场景"看价值，本节按"实际执行的任务类型"看——两种视角互为补充。需先说明：系统实际执行体是单一 `UniversalAgent`，项目中定义的小沈／小健／小强等是协作人格，因此按任务类型而非人格拆分价值更贴近实际。

| 任务类型 | 价值最大的记忆 | 为什么 |
|---|---|---|
| 定时例行任务（`creation_source=system_triggered`） | 程序 ★★★ | 到点复跑直接复用"上次怎么做的"；timers 内核已完成，只差这一步 |
| 固定流程／批量任务（固定格式报告、文件整理、docx/pptx 生成） | 程序 ★★★ | SOP 固定，教一次永久复跑，收益最高 |
| 跨会话续聊／中断恢复（`context_link_mode=continue`） | 情景 ★★★ | "上次做到哪、下一步是什么"，零重述恢复 |
| 深度研究／多源搜索合并 | 语义 ★★★ + 情景 ★★ | 已调研过的事实不重复搜；上次失败的源和结论可直接用 |
| 大型文档／代码生成（几十章文档、重构） | 情景 ★★★ + 程序 ★★ | 长周期易中断，需进度恢复与决策溯源 |
| 失败重试／审查类任务（三堂会审、合规检查） | 情景 ★★★ + 程序 ★★ | 历史失败教训 + 固定审查 SOP |
| 配置／环境类任务（provider、路径、授权） | 画像 ★★★ + 语义 ★★ | 常用路径、授权偏好记住后不再重复问 |
| HITL 确认／问询任务 | 画像 ★（次要） | 主要价值是授权偏好减少重复确认 |
| 多媒体理解任务（图片／音频／附件） | 基本无关 | 靠模型能力画像，不是记忆 |

对应到协作人格：

- 小沈／小健（后端）：程序记忆价值最大——读代码→备份→修改→ruff→测试，流程固定；
- 小强／小资（前端）：程序 + 情景——`npm run check:full` 流程、上次 UI bug 的根因；
- 老杨（风险分析）：情景记忆价值最大——历史问题与失败教训是核心资产；
- 小许（需求／文档）：语义记忆价值大——历史需求、文档结构复用；
- 小欧（助手，全类型）：四类都用。

**价值结论**：四类一起设计实施，不存在"谁先谁后"；但价值密度有高低——"定时例行 + 固定流程"任务以程序记忆为主、价值最高，"跨会话续聊／中断恢复／长任务"以情景记忆为主。四类读取层在阶段二一起打通，这些价值届时一并兑现；R1 对程序性记忆的强调体现在价值排序上，不构成实施上的分期。

### 2.7 四类记忆各自的技术架构与方案概要

先回答"是不是四类一起做"：**是**。四类一起设计、一起实施，按实施阶段推进（阶段一底座、阶段二四类读取与注入、阶段三治理与优化），不按记忆类型分期。下面按类说明各自的技术架构概要，详细设计见第三章。

**2.7.1 程序记忆：零新表，阶段二打通**

原料来自 `chat_task_steps.step_json` 和 `chat_tasks.user_input`。存储上不建新表——任务签名与取出的历史步骤序列都只是查询结果，用完即弃，不落库。变成记忆的过程是：先把用户输入归一化成任务签名，按签名在"范围收敛 + top_k + 索引"约束下检索相似历史任务（禁止 LIKE 全表扫描，见第零章 0.2），再取该任务的步骤序列，渲染成"工具名 + 关键参数"的有序列表。进 LLM 的时机是任务签名命中相似历史任务时，以 `[程序性记忆]` 前缀的 system 消息注入。这一类与其他三类同在阶段二打通读取与注入。

**2.7.2 情景记忆：零新表，阶段二打通**

原料来自 `chat_tasks`、`chat_task_steps`、`process_events` 和 `chat_sessions`。同样不建新表，只读现有表。变成记忆的过程是：按 session_id、task_id 或关键词把"上次经过与结果"组装出来——任务状态、完成进度、失败原因、过程事件都直接从列里取。进 LLM 的时机是断点续跑、失败重试、定时复跑这类场景，以 `[情景记忆]` 前缀注入。这一类与其他三类同在阶段二打通。

**2.7.3 语义记忆：默认关，阶段二打通读取、阶段三可加表**

原料是跨会话事实与结论；阶段三确有必要才做 LLM 蒸馏。读取层在阶段二与其他三类一起打通；存储上到阶段三才按需加 `long_term_memory` 表与 FTS5 检索（参考 R4），默认关闭。变成记忆的过程是：抽取事实、按相似度 >80% 去重、写入主表并同步 FTS5，检索时取 top_k。进 LLM 的时机是检索命中，以 `[语义记忆]` 前缀注入。

**2.7.4 用户画像：默认关，阶段二打通读取、阶段三可加表**

原料是常用路径、口头习惯、授权偏好这类稳定信息。读取层在阶段二与其他三类一起打通；存储走结构化表或现有设置注册表（`settings_registry`），默认关。变成记忆的过程是：显式 pin 或出现频次 ≥3 才升级为长期偏好，并支持一键失效。进 LLM 的时机是配置类、偏好类任务，以 `[用户画像]` 前缀注入。

四类共用同一套底座（四层结构见 3.2.2）：治理层负责 800 字符预算、写入门槛、TTL 与溯源失效；注入层把记忆消息并入 `_injected_history_msgs`，经一次 `inject_history` 灌入；沉淀层只做"步骤→模板、事件→经过"的组装（只读不落库）；原料层只读现有 chat 库。差异只在"从哪些表派生、什么时候灌"，不在注入机制——即"分类但不分家、实施不分先后"。

### 2.8 记忆与知识库的异同与关系

先给结论：**有关系，但不是同一件事**——两者共用"检索 → 预算裁剪 → 注入 system 消息"这条管道，却管着不同来源、不同粒度的信息，互补而不合并。最直接的证据是 R3 的 `kb_context.py`：它把 `[长期记忆]` 与 `[知识库检索]` 拼在同一份上下文里，说明从设计一开始两者就是同管道的两类内容。

**2.8.1 相同点：同一个痛点，同一条管道**

两者都在解决"跨会话复用信息、不重复劳动"：知识库让外部文档与规则不必每次重读，记忆让系统自己走过的路不必每次重走。落地方式也同构——先检索出相关片段，按预算裁剪，再作为 system 消息经 `inject_history` 注入 LLM（R3 的 `kb_context.py` 里，记忆预算 800 字符、检索预算 3000 字符，分别计、合并拼装）。两者都倾向 SQLite 零依赖检索：知识库用 FTS5（不引 Milvus），记忆按 R1 不引向量库，阶段三真需要时才参考 R4 加 FTS5。

**2.8.2 不同点：来源、粒度、生命周期、写入、权限**

来源不同：知识库装的是外部输入的文档与规则——R2 判断项目里 `doc/` 下几百个 md 和 `AGENTS.md` 本身就是最大的知识资产；记忆装的是系统自己产生的运行痕迹——任务、步骤、过程事件、用户偏好。粒度不同：知识库按文档／块组织（R3 父子块：父块 800 字给 LLM、子块 200 字建索引），记忆按事件／方法／事实／偏好组织，粒度更细。生命周期不同：知识库原文与 `source_uri + content_hash` 永久保留、按版本增量；记忆按 TTL 与滚动淘汰，情景记忆近期价值高、远期衰减。写入方式不同：知识库靠显式 ingest 导入，记忆在阶段一~二是运行期只读派生（零新表），阶段三才按"显式 pin 或频次≥3"写入。权限不同：知识库写入时绑定 `acl_tenants`、查询只做等值过滤；记忆只在本机用，没有多租户维度。

**2.8.3 关系：同源不同层，互补不合并**

所以两者不是"有没有关系"的问题，而是"同管道、不同层"：知识库回答"外部知识说了什么"（学来的），记忆回答"我自己做过什么、会做什么、用户是谁"（长出来的）。知识库可以给记忆提供素材——例如把 `AGENTS.md`、规范文档 ingest 后，语义记忆可从中提炼少量稳定事实；记忆不反过来充当知识库，它没有文档版本、溯源哈希和权限模型。

**2.8.4 边界：语义记忆与知识库最容易混**

唯一会重叠的是语义记忆（跨会话事实库）与知识库：两者都存"事实"。划界办法是：知识库存大批量外部文档原文，要求完整、可溯源、可版本化；语义记忆只存系统自己提炼的少量事实与偏好，默认关、有写入门槛、有 800 字符预算。不要拿知识库当记忆用（会膨胀挤占任务上下文），也不要拿记忆当知识库用（没有版本和权限）。阶段一~二记忆严格零新表、不接知识库（知识库本身也尚未落地）；阶段三若两者都要保留，共用注入层但各管各的存储。

**2.8.5 代码智能工具在三类框架中的位置**

结合对当前开源项目的核查，那些"分析代码库、帮助理解与定位修改"的工具可以按 2.8 的框架归位。

**第一类是代码知识图谱，属知识库。** 代表有 colbymchenry/codegraph（本系统当前接入的就是它）、codegraph-ai/CodeGraph、Bikach/codeGraph（LadybugDB）、CodeGraphContext、sdsrss/code-graph-mcp、vitali87/code-graph-rag、FalkorDB Code-Graph、Graphify、code-review-graph、codebase-index。它们解析代码（静态外部输入）成符号／调用边／依赖图，持久化在本地 SQLite 或图库，检索后注入上下文；答案带 file:line 证据、可重建、可随文件变更增量同步。来源是外部输入而非运行经验，符合 2.8.2 对知识库来源的描述。它们生成的 `GRAPH_REPORT.md`、架构文档也是知识库产物。

**第二类是混合型，图是知识库、附带的 memory 层才是记忆。** codegraph-ai/CodeGraph 提供 7 个 memory 工具（store/get/search/context/list/invalidate/stats），存"调试心得、架构决策、已知问题"；还配套 Tempera 作为跨项目的情景记忆系统。Graphify 有带来源与历史的 shared Memory，code-graph-rag 能把运行时 trace 叠加进图。这正好印证 2.8.3：同管道、不同层、互补不合并。它们 memory 层存的内容，对应本设计的情景记忆（失败教训、决策溯源）与语义记忆（架构决策）。

**第三类是即时上下文工具，属于其他类型。** Aider 的 repo map、mackenney/repo-mapper、noambinabout-boop/repo-map 用 tree-sitter + PageRank 在每次请求时动态生成代码摘要塞进 prompt（Aider 默认 1k token 预算），不持久化知识。属于上下文工程／工具层，是知识库的即时视图，既不是知识库也不是记忆。

边界结论：代码理解走知识库（已有 codegraph），运行经验走记忆层（本设计），两条线通过同一注入管道汇合。核查中遇到的厂商自测数字（如"88% fewer tool calls"）只用于识别产品定位，未采信为事实。

**3.1.4 注入链（旧设计的注入点已失效，这是最重要的代码事实）**

- `backend/app/services/agent/initialize_run_state.py:120-122`：现代码明确"此处不再 `init_history` 建 `[system, task]`；推迟到压缩决策后由 `react_loop` 装配段建"。**R4 设计的 `initialize_run_state` 中 `_inject_long_term_memory` 注入点已不存在。**
- 现行注入链在 `backend/app/services/agent/start_step.py`：
  - `assemble_start_step`（`:732`）唯一对外入口，业务顺序固定：① `_build_injected_history`（`:354`，从 `context.previous_messages` 构建，存 `agent._injected_history_msgs`，不写 conversation_history）→ ①' `_assemble_anchor_delta`（增量锚点）→ ② `_maybe_compact_injected_history`（`:369`，超窗判定）→ ③ `_compact_injected_history`（`:481`，锚定摘要）→ ④ `_build_start_contract`（`:691`，StartStep）。

### 3.2 新方案总体说明

**3.2.1 设计原则**

1. 以 R1 为纲：四类一起设计实施、零新表起步、不引向量库；R1 对程序性记忆的强调体现为价值优先，不表现为实施上的先后。
2. 吸收 R2/R3 治理层：写入门槛、TTL 淘汰、冲突检测、防污染（溯源+一键失效）、注入预算。
3. 复用当前代码：只读 chat 库、走 `db.atxn("chat", ...)`；注入并入 `_injected_history_msgs` 通道；预算复用 compaction 口径。
4. 不新增 LLM schema 参数；短任务不做额外 LLM 调用（阶段一~二完全零 LLM 蒸馏）。
5. 可独立启动，不依赖阶段 1~3（第59号文档的实施阶段，非本文阶段一/二/三）任何产出；配置开关默认关（对齐旧设计 `memory_enabled` 默认关的保守口径）。
6. **前瞻性数据量约束（第零章 0.2）**：代码库与知识库都可能很大，检索从一开始就必须"范围收敛 + 有界候选 + top_k + 走索引"，禁止对 `chat_tasks`／`chat_task_steps`／知识库做 LIKE `%...%` 全表扫描；检索走 `db.atxn` 子线程不阻塞事件循环；注入始终受 800 字符硬预算约束。此为长期设计基线，不因当前数据尚小而后补。

**3.2.3 记忆表方案（按阶段，零新表起步）**

四类一起设计实施，阶段按实施步骤划分，不按记忆类型分期。

| 阶段 | 内容 | 表 | 说明 |
|---|---|---|---|
| 阶段一 | 四类共用底座 | 不建新表 | 打通 chat 库只读读取与 `_injected_history_msgs` 注入通道，建立 800 字符预算与裁剪，配置开关默认关 |
| 阶段二 | 四类读取与注入 | 不建新表 | 程序（任务签名→步骤模板）、情景（会话/任务→上次经过）、语义（事实检索）、画像（偏好检索）一起实现，按场景分类注入，共用治理层；按第零章 0.2 做范围收敛 + top_k + 索引检索，禁止 LIKE 全表扫描，走 `db.atxn` 子线程 |
| 阶段三 | 治理与优化 | 按需 | 写入门槛、TTL、溯源失效、冲突检测；真需要时按 R4 加 `long_term_memory` + FTS5；画像走结构化表或设置注册表 |

阶段一~二严格零新表：不新建 `memories` 表、不引向量库、不开多租户。这是与 R3/R4 最大的路径差异，也是 R1"零新表起步、收益最高成本最低"的直接落地。

**3.2.4 注入点方案（修正旧设计失效点）**

- 在 `start_step.assemble_start_step` 的 ①（构建注入历史）之后、②（超窗判定）之前，调用记忆读取层，把记忆消息（role=system，带 `[程序性记忆]` / `[情景记忆]` 前缀）追加到 `agent._injected_history_msgs`。
- 这样记忆与会话历史**同源**：自动参与 `_maybe_compact_injected_history` 判定、`_compact_injected_history` 摘要、`_shrink_before_summary` 裁剪，以及 `initialize_run_state.py:83-89` 的每次任务运行清零。
- 记忆注入独立预算：`MEMORY_BUDGET = 800` 字符（沿用 R3 数值），与历史预算**分别计、合并判**（记忆一段、历史一段各自计量，合并后判是否撞窗）——既防记忆挤占，又防总量撞窗。
- 不碰 `message_builder.inject_history` 本身，不新增 LLM schema 参数，符合 R1 约束。

**注入时机（代码实证）**：任务启动装配阶段、`while` 之前一次注入，不在 tool loop 内每轮灌。`react_loop.py` 顺序：`:228` `_assemble_start_step`（构建→判定→摘要→契约）→ `:250` `init_history` 建 `[system, task]` → `:264-265` `_build_injected_msgs` 决策 + `inject_history` 一次灌入 → `:320` `while` 才是 tool loop。注入落在 `conversation_history` 的 messages 数组，随后全任务常驻（每次 LLM 调用都带着，中间只追加 tool_calls/tool_result/observation）。`initialize_run_state.py:83-89` 每次任务运行清零的是注入态（非 loop 内每次调用）。插话不走 start 装配（`react_loop.py:243`），但记忆已常驻，无需重灌。

**分类策略（分类灌，不全灌）**：四类无差别全灌会撑爆 800 字符预算、挤占任务上下文，且记忆是"历史参考"不是"当前事实"，因此按任务场景选择性注入：

| 类型 | 什么时候才灌 | 前缀标签 |
|---|---|---|
| 程序 | 任务签名命中相似历史任务时才灌 | `[程序性记忆]` |
| 情景 | 断点续跑／失败重试／定时复跑／长任务才灌 | `[情景记忆]` |
| 语义 | 默认关，阶段二打通读取、阶段三启用，检索命中才灌 | `[语义记忆]` |
| 画像 | 默认关，阶段二打通读取、阶段三启用，仅配置／偏好类任务才灌 | `[用户画像]` |

四类共用 `MEMORY_BUDGET=800` 总量上限（四类各自计量、合并后受 800 上限约束）；打类型标签便于 LLM 区分来源与 telemetry 统计；触发判定全部在 start 装配阶段完成（不在 loop 内查库，避免每轮 IO）；超限时记忆先于任务上下文被裁。

**信息形态（库里结构化，灌给 LLM 是文本）**：

| 层次 | 形态 | 依据 |
|---|---|---|
| 存储层 | `chat_task_steps.step_json` 为 JSON 文本（一行一步）；`chat_tasks` 为列结构（user_input/task_summary/artifacts/process_events/error_type/creation_source…） | 现有表，零新表 |
| 注入层 | `{"role": "system", "content": "带标签的纯文本块"}`，由 `inject_history` 插在 system 之后、task 之前 | `message_builder.py:498-516` |

四类注入样例（content 正文）：

```text
[程序性记忆] 同类历史任务的可复跑步骤（仅供参照，需按当前情况核验）：
 1. listdir(path="F:\...\backend\app")
 2. read(path=".../config.py")
 3. write_docx(path=".../报告.docx")
（来源任务 task_20261114_xxx，2026-11-14）
```
```text
[情景记忆] 上次同一会话进展：任务「整理Q3报告」状态=paused，完成到步骤7/12，
 最后一步=读取 sales.xlsx；上次失败原因=路径越界被拦截。
（来源任务 task_20261120_yyy）
```
```text
[语义记忆] 常用工作目录 F:\OmniAgentAs-01\backend；报告偏好 docx 格式。
[用户画像] listdir/read 免确认，write 需确认；"整理一下"指按日期归档。
```

为什么是纯文本而不是 JSON：① 对齐 `inject_history` 的 `{"role","content"}` 字符串契约，灌 JSON 费 token 又难读；② 不新增 LLM schema（R1 约束），沿用 `[长期记忆]` 和摘要标签的既有格式；③ 结构化在读取层解析后渲染成"工具名+关键参数"的有序步骤，保留复跑信息但不倒原始 JSON；④ `hit_count`/`pinned`/`expired_at` 等治理字段只在存储检索时用，不灌给 LLM，仅保留一句来源溯源。

**3.2.5 治理机制（吸收 R2/R3）**

- 写入门槛：阶段一~二不写记忆（只读派生），天然无污染；阶段三引入写入时按"显式 pin 或频次≥3"才升级（R2/R3）。
- 淘汰：情景记忆召回窗口滚动偏近期、远期价值衰减，原料表不清理、随库长期留存（与 2.2 口径一致）；长期记忆 TTL=90 天（R3）。
- 防污染：每条记忆带 `source_task_id` / `source_session_id` 溯源；支持按来源一键失效（R2/R3）。
- 冲突检测：程序性模板若与当前步骤冲突（路径不存在/工具已改），注入时标注"历史参考，需核验"，不强行套用。

**3.2.6 实施阶段（四类一起推进）**

四类一起设计实施，阶段是实施步骤，不是记忆类型的先后。

| 阶段二 四类读取与注入 | 程序（任务签名→步骤模板）、情景（会话/任务→上次经过）、语义（事实检索）、画像（偏好检索）一起实现，按场景分类注入 | 阶段一 | 本设计提出 |

### 3.4 实施边界与风险

### 4.4 验收标准（可度量）

1. 同类任务第二次执行时，注入上下文含 `[程序性记忆]` 段且步骤模板来自历史任务，注入字符 ≤800。
2. 中断恢复任务时，注入上下文含 `[情景记忆]` 段，能给出上次 `task_summary` 与最后 `step_index`。
3. 注入总量（历史 + 记忆）参与现有超窗判定与裁剪，无撞窗、无 500。
4. 关闭配置开关时，注入内容与当前完全一致（零行为变化）。
5. agent 跨任务复用时，无上一任务记忆串味（依赖每次任务运行清零与签名隔离）。
6. 阶段一~二数据库表数量不增加（零新表可核查）。
7. **大数据量验收（第零章 0.2）**：在 `chat_task_steps` 百万行级、知识库万篇文档级下，单次记忆读取有耗时上限（检索量级 ≤100ms，可用 `EXPLAIN QUERY PLAN` 核查无全表 `SCAN`），四类注入合计仍 ≤800 字符；大知识库检索走 FTS5 索引 + top_k，不把原文全量注入。

### 4.5 后续实施建议

1. 阶段一：打通四类共用的原料读取（`chat_tasks`/`chat_task_steps`/`process_events`）与 `_injected_history_msgs` 注入通道，建立 800 字符预算与裁剪，配置开关默认关。
