## 零、设计基础需求与约束

本章沿用 [61] 第零章的约束框架并逐条核实，约束不变、表述收紧，作为后文一切设计的前提。

### 0.1 使用场景

单机部署、单用户使用、多会话并存。单机意味着无网络分区与分布式一致性问题；单用户意味着不做 tenant/user 多租户维度；多会话意味着记忆必须跨会话复用，且要处理"同一代码库不同事项"与"不同类型任务"并存的情况。

任务类型有相同也有不同：相同类型（如同一代码库的不同事项）是程序记忆价值最高的场景；不同类型并存要求情景记忆按会话／任务隔离检索，避免把 A 任务的经验灌给 B 任务。

### 0.2 数据量约束：单机不等于小数据

- **代码类任务的代码库很大**：`chat_task_steps` 已达百万行级（历史峰值 185 万行／2.7GB），检索必须"范围收敛 + 有界候选 + top_k + 走索引"，禁止全表模糊扫描。
- **事务处理的知识库可能很大**：第二阶段接入的知识库装大批量文档，原文按版本永久保留，体量只增不减，同样禁止全表扫描。
- 记忆读取与注入必须在 `db.atxn` 子线程完成，不阻塞事件循环；注入设硬预算与裁剪。

### 0.3 注入与上下文约束

沿用现有 `message_builder`，不新增 LLM schema 参数（R1 硬约束）。记忆与知识库内容必须落在 `conversation_history` 的 system 消息上，在任务启动装配阶段一次注入、全任务常驻。注入内容是"历史参考"不是"当前事实"：与当前步骤冲突时标注需核验，不自动覆盖当前决策。配置开关默认关，实测通过后才开。

### 0.4 执行模型约束

服务进程唯一：`run_server.py` 用 `uvicorn.Config` + `Server.run()` 编程式启动（`run_server.py:471-487`），不走 `uvicorn.run()`，无 supervisor、无 worker 分叉；全仓无 `ProcessPoolExecutor`／`multiprocessing.Process`。

但"单进程"不等于"单线程"，也不等于"只有一个 OS 进程"：

- 开发态经 `watchfiles`／`uvicorn --reload` 启动时是"重载器父进程 + 服务子进程"两个进程，只有子进程对外服务；
- 进程内常驻线程池约 140 条：`main.py:542`（tool-sync）、`main.py:571`（anyio 40）、`database.py:98`（db-txn 4）、`workers.WorkerPool`（shell-exec 32／tool-exec 16／bg-shell-wait 5）、`loop_watchdog`／`spawn_gate` 看门狗；
- 运行期按需派生子进程：pwsh 沙箱（`sandbox/backend.py:66`）、shell 执行、ffprobe/ffmpeg、通知弹出、模型配置探测、py-spy 转储。

由此对记忆层与知识库层产生三条硬约束（详见 [64] 第 4.6 节）：

1. **不得依赖进程内状态**。模块级 dict、缓存、句柄在多进程结构下均可失效；记忆层与知识库层的结论型数据一律只从 DB 读，不缓存跨任务的可变状态。
2. **写操作保持单写者思维**。WAL 下并发读安全、写仍串行；记忆巩固、知识库 ingest 即使将来跑在独立进程，也只做计算并把结果回传主进程，由主进程经 `db.atxn` 单一路径落库，不得另起进程写库。
3. **检索与注入放子线程**。沿用 `db.atxn` 既有纪律，检索不阻塞事件循环；此约束不依赖执行模型，故在执行模型演进中始终成立。

多进程不作为本设计的演进方向：SQLite 单写者、SSE 长连接请求亲和、进程内取消标记三处会在对称 worker 下同时退化。功能隔离型进程（如通用进程宿主、CPU 密集作业池）与记忆设计正交，各自独立演进。

### 0.5 治理与安全约束

写入门槛（显式 pin 或频次达标）、TTL 过期淘汰、按来源溯源与一键失效，三者共同防记忆污染。阶段一只读派生、不写记忆，天然无污染。

数据读写走 `db.get_conn`／`db.atxn` 现有通道，不改生产解析逻辑；配置读写经 `get_config_path`，不硬编码路径；测试用 `db._db_overrides` 覆盖口，不碰真库。

### 0.6 工程规范约束

公用函数先查 `backend/FUNCTIONS.md`，有则复用、无则新建并登记；新建 `app/services/memory/` 与 `app/services/kb/` 模块与现有 `app/services/*` 结构对齐；代码头部按规范写编辑历史（署名+日期）。禁止以测试代码固化错误逻辑，测试只用于发现问题，不提交测试 case 到仓库。文档按规范保留版本历史、章节连续。

## 一、整合说明：从两份独立设计到单一现行方案

### 1.1 设计谱系

[61] 与 [62] 是同一问题的两代独立设计（同日不同时段完成）。[61] 以文档谱系继承为主线，[62] 以前沿研判正向设计为主线。两者在八个维度上的裁决高度收敛（表该不该建、程序记忆优先、治理前置、零新表可行性、trigram 短词失效、任务卡漂移、知识库边界、文档互引缺失），分歧只在分期轴与落地精度。本文整合两者为单一现行方案，[61]／[62] 自此仅作历史参考，不再作为实施依据。

### 1.2 整合原则：按"数据是否已存在"分期

两份文档的根本分歧只有一条：表该不该前置。[61] 说全后置（阶段一二零新表），结果语义／画像成空壳；[62] 说全前置（M0 建表），结果最高价值的程序记忆被排到最后。正确分法不按记忆类型、也不按是否建表，而按一条硬标准：**数据是否已经存在于库中**。

| 期 | 内容 | 要不要新表 | 依据 |
|---|---|---|---|
| 一期 | 注入基座 + 程序记忆 + 情景记忆 | 零新表 | 原料已在 `chat_tasks`／`chat_task_steps`／`process_events`，只读派生即可跑通，立刻兑现 R1 的最高价值 |
| 二期 | `memory_items` 表 + 语义 + 画像 + 治理 | 要建表 | 这两类数据现在根本不存在，必须建表 + 写入 + 治理，否则永远空转 |
| 三期 | 巩固（去重／冲突／衰减）+ 向量／实体扩展 | 按需 | 得先有数据量，才有巩固的对象 |

这个分法同时修掉两份文档的病：修掉 [61] 的"语义／画像空壳"与"禁 LIKE 无索引"（一期只做精确锚定，不做相似任务模糊检索）；修掉 [62] 的"程序排最后"（提到一期）与"trigram 2 字失效"（二期建双索引兜底）。

### 1.3 实测证据：trigram 双字失效

[62] 的"词法优先"依赖 FTS5 trigram 分词器，实测（SQLite 3.50.4）发现硬约束：

| 查询词 | 长度 | 命中 |
|---|---|---|
| 用户偏好 | 4 | 1 |
| 偏好 | 2 | 0 |
| 路径 | 2 | 0 |
| E盘 | 2 | 0 |
| 结论先行 | 4 | 1 |

中文最高频的查询词恰恰是两个字（偏好／路径／测试／部署／报错／配置），trigram 对 2 字查询一律 0 命中。这不是调优问题，是分词器硬约束。因此二期建 FTS 时必须双索引（trigram 处理长词子串 + unicode61 处理短词），或 2 字查询在已收敛候选集内走 LIKE 兜底。该决策写死在一期文档，防止二期再踩坑。

### 1.4 记忆与知识库的关系：同管道、不同层、互补不合并

知识库回答"外部知识说了什么"（学来的），记忆回答"我自己做过什么、会做什么、用户是谁"（长出来的）。两者共用"检索 → 预算裁剪 → 注入 system 消息"这条管道，但管着不同来源、不同粒度的信息。知识库存大批量外部文档原文，要求完整、可溯源、可版本化；记忆存系统自己提炼的少量事实与偏好，默认关、有写入门槛、有预算约束。不拿知识库当记忆用（会膨胀挤占任务上下文），不拿记忆当知识库用（没有版本和权限）。阶段一记忆严格不接知识库；阶段二两者共用注入层但各管各的存储。

## 二、共同基座：记忆与知识库共享的管道设计

记忆与知识库是两层不同的信息，但它们流向 LLM 的路径是同一条：**检索 → 打分 → 预算裁剪 → 注入 → 观测**。这条管道设计一次、两处复用，是本文的第一优先级。

### 2.1 管道总览

```
┌─────────────────────────────────────────────────────────────────────┐
│  治理层：开关默认关 │ 预算分档 │ 写入门槛 │ TTL │ 溯源 │ 软删除 │ 审计  │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │ 注入层：build_context → 带标签 system 消息 → 并入              │  │
│  │        _injected_history_msgs（与会话历史同源，自动享受          │  │
│  │        超窗判定、锚定摘要、裁剪、每次任务运行清零）               │  │
│  │  ┌─────────────────────────────────────────────────────────┐ │  │
│  │  │ 检索层：范围收敛 → 有界候选 → 双索引词法（trigram+unicode61│ │  │
│  │  │        或候选内LIKE兜底）→ 打分 → 去冗余 → 预算裁剪        │ │  │
│  │  │  ┌───────────────────────────────────────────────────┐ │ │  │
│  │  │  │ 原料层：                                           │ │ │  │
│  │  │  │  记忆  = chat_tasks/chat_task_steps/process_events │ │ │  │
│  │  │  │        （一期只读派生）+ memory_items（二期落库）    │ │ │  │
│  │  │  │  知识库= kb_documents/kb_chunks（第二阶段新增）     │ │ │  │
│  │  │  └───────────────────────────────────────────────────┘ │ │  │
│  │  └─────────────────────────────────────────────────────────┘ │  │
│  └───────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.2 注入通道：唯一入口，绝不自建第二套

代码实证（基于 2026-11-25 最新本地代码）：现行注入链在 `start_step.py` 的 `assemble_start_step`（`:732`），顺序为 ① `_build_injected_history`（`:354`）→ ①' `_assemble_anchor_delta` → ② `_maybe_compact_injected_history`（`:369`）→ ③ `_compact_injected_history`（`:481`）→ ④ `_build_start_contract`（`:691`），最终经 `message_builder.py:498` 的 `inject_history` 插入到 system 之后、task 之前。旧设计（R4）在 `initialize_run_state` 里的注入点已失效。

**定案**：记忆与知识库的注入都在 `assemble_start_step` 的 ① 之后、② 之前，把带标签的 system 消息追加到 `agent._injected_history_msgs`。同源即自动享受超窗判定、锚定摘要、裁剪与每次任务运行清零（`initialize_run_state.py:83-89`），不需要第二套机制。自建第二套注入路径违反 KISS-DIRECT/DRY，且会绕过预算控制，明确禁止。

### 2.3 预算分档：分别计量、合并判定、总量封顶

单一 800 字符口径不够：全局偏好、项目约定、会话进度、外部知识是四种不同性质的内容，挤在一个池子里必然互相踩踏。采用分档配额、分别计量、合并判定：

| 范围 | 配额（字符） | 内容 | 来源 |
|---|---|---|---|
| 全局记忆 | 400 | 用户偏好、机器环境、跨项目通用坑点 | `memory_items(scope='global')`（二期） |
| 项目记忆 | 600 | 目录约定、构建测试命令、禁区、项目坑点 | 项目文件 + `memory_items(scope='project')`（二期） |
| 会话记忆 | 400 | 最近一到两张任务卡、当前约束 | 只读派生（一期）／`memory_items`（二期） |
| 知识库 | 800 | 外部文档片段、代码图证据 | `kb_chunks`（第二阶段） |
| **合计** | **2200** | 硬上限，超限先裁知识库，再裁会话记忆，再裁项目记忆，最后裁全局记忆 | — |

为什么知识库先裁：知识库是"学来的"，丢了可以重新 ingest；记忆是"长出来的"，丢了就真没了。全局记忆最后裁，因为它是用户偏好与机器环境，丢了等于每次重述。

### 2.4 检索层：范围收敛 + 有界候选 + 双索引词法

先过滤后打分，任何情况下不做全表扫描。

**范围收敛**：按 `scope` 与 `scope_ref` 收窄。会话范围只查当前会话；项目范围只查当前项目根；全局范围常驻但配额最小。

**有界候选**：索引命中取前 N（N 取 top_k 的四到五倍），再叠加同 `subject` 的当前有效条目。

**双索引词法**（二期起，知识库同用）：

```sql
-- 长词子串、路径、命令、错误串用 trigram
CREATE VIRTUAL TABLE memory_fts_tri USING fts5(
  title, content, subject, content='memory_items', content_rowid='rowid',
  tokenize='trigram'
);
-- 短词（2字中文、英文单词）用 unicode61
CREATE VIRTUAL TABLE memory_fts_uni USING fts5(
  title, content, subject, content='memory_items', content_rowid='rowid',
  tokenize='unicode61'
);
```

查询分发规则：查询词长度 ≥3 走 trigram；=2 走 unicode61；unicode61 未命中且候选集已收敛时，在有界候选内走 LIKE 兜底（`IN (候选id列表)`），绝不全表 LIKE。两个索引的结果做并集去重后统一打分。

**打分**（权重为初值，三期用评测集校准，权重走配置不写死）：

```
score = 0.40 * 词法相关度（bm25 归一化：映射到 0..1 区间后参与加权）
      + 0.20 * 时间衰减（半衰期 30 天）
      + 0.15 * 重要性
      + 0.10 * 使用命中（log 归一化）
      + 0.10 * 关联重合（同项目、同实体、同会话）
      + 0.05 * 范围匹配（越具体越高）
      + 可选 * 向量相似度（三期）
```

**去冗余**：最大边际相关筛选，同主题只留信息量最大的一条。

**预算裁剪**：按分数从高到低装入，超预算即停；单条超长截断正文但保留标题与来源。

**降级链**：FTS 不可用走 `subject` 精确匹配 + 范围过滤；向量不可用直接跳过；记忆层任何异常降级为"无记忆"，不得让任务失败。

### 2.5 治理层：从第一版就有最小集

治理不是企业专属，单机单用户同样需要。最小集四件：**来源、置信度、可删除、可审计**。

| 机制 | 一期（只读派生） | 二期（落库） |
|---|---|---|
| 来源溯源 | 每条注入带来源 task_id／时间 | `source_type` + `source_ref` 落库 |
| 置信度 | 不适用（不写） | 0..1 落库，候选制分级 |
| 可删除 | 不适用（不写） | 软删除 `status='rejected'`，审计表记录，可恢复窗口 |
| 审计 | 注入日志（条目 id 列表） | `memory_audit` 表：谁、在哪个任务、写了什么 |
| 冲突标注 | 注入时标注"历史参考，需核验" | 双时态 `valid_from/valid_to`，旧条目 `superseded` 不删除 |
| 遗忘 | 滚动召回窗口偏近期 | TTL + 重要性衰减 + 归档 |

写入门槛（二期起生效）：用户明说直接 `active`；模型推断进 `candidate`；外部内容一律 `candidate` 低置信、禁止自动提升；涉及路径、凭据、破坏性操作的主题不自动生效。

### 2.6 观测：每次注入一条日志

每次注入记录：任务 id、注入条目 id 列表、各范围占用字符、检索耗时、来源、后续是否被采纳（用户标注或行为推断）。这些数据直接支撑验收指标，也是三期巩固作业的输入。

## 三、第一阶段：记忆系统详细设计

### 3.1 目标与范围

目标一句话：**把任务流变成可沉淀、可检索、可治理的记忆资产，让第二个同类任务比第一个更快、更少错。**

第一阶段只做记忆，不接知识库。范围按"数据是否已存在"分三期推进，每期独立验收、独立回滚：

| 期 | 内容 | 新表 | 验收 |
|---|---|---|---|
| 一期 | 注入基座 + 程序记忆 + 情景记忆 | 零新表 | 同类任务第二次注入含 `[程序性记忆]`；中断恢复注入含 `[情景记忆]`；记忆注入合计 ≤1400 字符（三档配额内） |
| 二期 | `memory_items` + 语义 + 画像 + 治理 | 要建表 | 同一偏好重复询问不超过一次；错误记忆可一键删除且不再召回；外部内容不会自动成为高置信事实 |
| 三期 | 巩固 + 向量／实体扩展 | 按需 | 重复条目显著下降；precision@5 达标；每任务 token 不升 |

### 3.2 一期：程序记忆与情景记忆（零新表，只读派生）

#### 3.2.1 程序记忆：任务签名 → 可复跑步骤模板

原料：`chat_task_steps.step_json`（一行一步，含 type/step/timestamp/content/tools/thought）+ `chat_tasks.user_input`。

流程：
1. **任务签名**：`task_signature(user_input)` 归一化输入——去空白、去标点、去变量值（路径、日期、数字），保动作与对象。例："整理 Q3 报告"与"整理 Q4 报告"归一化为同一签名"整理 报告"。
2. **精确锚定检索**（一期不做相似任务模糊检索，规避"禁 LIKE 无索引"矛盾）：
   - 按 `session_id` 锚定（走 `idx_tasks_session`）+ 时间窗（走 `idx_tasks_created`）+ `creation_source` 过滤，取最近 N 条任务；
   - 对候选任务的 `user_input` 在内存中做签名匹配（候选集已收敛，量级几十条，允许内存计算）；
   - 命中则取 `task_id` 列表。
3. **步骤提取**：`steps_of(conn, task_id)` 复用 `storage.load_steps_by_task`（走 `idx_steps_task`），取可复跑步骤序列，渲染成"工具名 + 关键参数"的有序列表。
4. **注入**：命中时以 `[程序性记忆]` 前缀注入，带来源标注。

```text
[程序性记忆] 同类历史任务的可复跑步骤（仅供参照，需按当前情况核验）：
 1. listdir(path="F:\...\backend\app")
 2. read(path=".../config.py")
 3. write_docx(path=".../报告.docx")
（来源任务 task_20261114_xxx，2026-11-14）
```

#### 3.2.2 情景记忆：上次经过与结果

原料：`chat_tasks`（任务级）、`chat_task_steps`（步骤级）、`process_events`（过程事件）、`chat_sessions`（会话级）。

场景与取数：

| 场景 | 做什么 | 数据来源 |
|---|---|---|
| 断点续跑 | 上次做到哪、下一步是什么 | `chat_tasks.status/task_summary/context_link_mode` + `chat_task_steps.step_index` |
| 失败教训 | 这个方法上次失败，原因是 | `chat_tasks.error_type/error_message` + `chat_task_steps` 中 error 步 |
| 决策溯源 | 当时为什么选了 A 方案 | `chat_task_steps` 的 thought/reasoning、artifacts、process_events |
| 例行复跑依据 | 定时到点上次怎么干、结果如何 | `chat_tasks.creation_source=system_triggered` + 步骤表 + timers |

注入样例：

```text
[情景记忆] 上次同一会话进展：任务「整理Q3报告」状态=paused，完成到步骤7/12，
 最后一步=读取 sales.xlsx；上次失败原因=路径越界被拦截。
（来源任务 task_20261120_yyy）
```

**关键定案**：一期情景记忆**只读派生，不落库**。`chat_tasks.task_summary` 已是压缩摘要，`chat_task_steps` 是原文，不再第三处存储任务卡——避免 [62] 的"任务卡三处存储必然漂移"问题。任务卡作为"视图"在注入时现场组装，用完即弃。

#### 3.3.1 数据模型

统一条目表承载四类记忆（程序、情景一期的只读派生视图在二期可选择性落库为快照，但默认仍只读），范围与类型用字段区分：

```sql
CREATE TABLE memory_items (
```

#### 3.3.2 写入门控：候选制，不做全自动直写

| 来源 | 默认状态 | 置信度 | 提升条件 | 禁止 |
|---|---|---|---|---|
| 用户明说或显式记住 | active | 1.0 | 无 | 无 |
| 用户隐含表达（纠正、偏好） | candidate | 0.7 | 同类出现两次以上或用户确认 | 不自动升 active |
| 模型推断 | candidate | 0.5 | 人工确认 | 不得直接 active |
| 工具观测 | active（短 TTL） | 0.8 | 再次观测到则续期 | 不得跨项目复用 |
| 外部文档或网页 | candidate | 0.4 | 人工确认 | 禁止自动提升；涉及路径、凭据、破坏性操作一律拒绝 |

**候选确认闭环**（二期必须实现，否则门控是漏斗）：
- 对话内轻量确认：任务收尾时若产生候选，在响应末尾附一句"我注意到你偏好 X，要记住吗？"用户一句"记住"即提升；
- 管理页批量确认：前端记忆管理页列出候选队列，支持批量通过／拒绝；
- 超时自动降级：候选超过 30 天未确认且未再次触发，自动 `rejected`，不无限堆积。

#### 3.3.3 双时态检索语义

- `valid_from/valid_to` 是**世界时间**（事实何时成立／何时失效），`recorded_at` 是**系统时间**（何时被记录）。
- 检索默认只取 `status='active' AND (valid_to IS NULL OR valid_to > now)`。
- `superseded` 条目不参与打分，但保留链路供审计与"当时为什么那么做"的追溯。
- 同 `subject` 多条候选并列有效时，取来源权威性最高且最新的一条注入，其余作为候选展示。

### 3.4 三期：巩固与增强

巩固是分水岭——没有巩固的记忆系统本质是"聊天记录搜索"。

**巩固作业**（`consolidate.py`，幂等入口，可重入）：
1. 去重：同范围同类型同 `content_hash` 合并；
2. 冲突消解：同 `subject` 多条有效，新的取代旧的，旧的 `superseded`；
3. 提炼：情节卡稳定结论升为事实候选；同类任务成功三次以上提炼为做法模板候选（不自动生效）；
4. 衰减：半衰期降低重要性，低于阈值且长期未用归档；
5. 归档与索引重建：归档不参与检索，FTS 增量同步。

触发时机：任务收尾后异步、应用启动后延迟、定时空闲时。单步失败不阻断后续，不得阻塞主链路。

**增强**（按需）：可选向量列（本地 ONNX 小模型，关闭时零影响）、实体两跳扩展（SQLite 邻接表，不上图库）。

### 3.5 记忆工具（二期开放）

一期不开放模型主动查记忆的工具，避免注入不可控。二期提供三个：

- `memory_search`：按关键词与范围检索，走 2.4 管道；
- `memory_read`：读单条全文；
- `memory_write`：写候选，走门控。

工具描述明确"记忆是历史参考，与当前状态冲突时以当前为准"。

### 3.6 验收标准（记忆）

**一期**：
1. 同类任务第二次执行，注入含 `[程序性记忆]` 且步骤来自历史任务，注入 ≤400 字符（会话记忆配额内）；
2. 中断恢复任务，注入含 `[情景记忆]`，能给出上次 `task_summary` 与最后 `step_index`；
3. 注入总量（历史 + 记忆）参与现有超窗判定与裁剪，无撞窗、无 500；
4. 关闭配置开关时，注入内容与当前完全一致（零行为变化）；
5. 数据库表数量不增加（零新表可核查）；
6. 单次记忆读取 ≤100ms（`EXPLAIN QUERY PLAN` 核查无全表 SCAN）。

**二期**：
7. 同一偏好重复询问不超过一次；
8. 错误记忆可一键删除且不再召回；
9. 外部内容不会自动成为高置信事实；
10. 2 字中文查询（偏好／路径／测试）经 unicode61 或候选内 LIKE 兜底命中。

**三期**：
11. 巩固后重复条目显著下降；
12. precision@5 达标（人工判定）；
13. 每任务 token 不升。

## 四、第二阶段：知识库概要设计

本章为概要设计，详细设计在第一阶段记忆系统验收后另行展开。知识库是本项目需要创新的部分，以下方案在借用现有技术的基础上给出三个创新点。

### 4.1 定位与边界

知识库存外部输入的文档与规则——`doc/` 下的 md、`AGENTS.md`、外部导入的资料、代码图产物。与记忆的边界见 1.4：知识库回答"外部知识说了什么"，记忆回答"我自己做过什么"。两者共用第二章的注入管道，各管各的存储。

### 4.2 总体架构

```
外部文档（md/pdf/docx/代码库）
      │
      ▼
ingest 层：解析 → 清洗 → 版本化（source_uri + content_hash，增量同步）
      │
      ▼
分块层：结构感知分块 → 父子块（子块 200 字建索引，父块 800 字给 LLM）
      │
      ▼
索引层：FTS5 双索引（trigram + unicode61，与记忆同策略）+ 可选向量列
      │
      ▼
检索层：走第二章共用管道（范围收敛 → 有界候选 → 打分 → 预算裁剪）
      │
      ▼
注入层：并入 _injected_history_msgs，预算 800 字符，知识库范围先裁
```

### 4.3 创新点一：文档即图——知识库与 codegraph 的双向联动

现有 codegraph 已把代码库解析为符号／调用边／依赖图，产物 `GRAPH_REPORT.md` 是知识库的天然素材。创新在于双向：

- **正向**：代码图产物 ingest 进知识库，与自然语言文档同等可检索；
- **反向**：知识库检索命中某文档时，若该文档关联代码符号（通过 `source_uri` 中的路径前缀匹配），自动从 codegraph 拉取该符号的一跳邻居作为补充证据，一并注入。

这样"这份设计文档改了，会影响哪些代码"与"这个函数的调用方是谁，对应哪份设计"两个问题共用一条检索链。此为概要方向，具体联动协议在详细设计中定。

### 4.4 创新点二：活文档版本谱系

知识库文档不是静态原文堆积，而是带版本的活文档：

```sql
CREATE TABLE kb_documents (
  id TEXT PRIMARY KEY,
  source_uri TEXT NOT NULL,        -- 文件路径 / URL
  content_hash TEXT NOT NULL,      -- 内容哈希，增量判定
  version INTEGER NOT NULL,
  title TEXT,
  doc_type TEXT,                   -- md | pdf | docx | code_report
  status TEXT NOT NULL,            -- active | superseded | deleted
  created_at TEXT NOT NULL,
  UNIQUE(source_uri, version)
);

CREATE TABLE kb_chunks (
  id TEXT PRIMARY KEY,
  document_id TEXT NOT NULL,
  chunk_index INTEGER NOT NULL,
  parent_id TEXT,                  -- 父子块：子块建索引，父块给 LLM
  content TEXT NOT NULL,
  token_estimate INTEGER,
  FOREIGN KEY(document_id) REFERENCES kb_documents(id)
);
```

- **增量同步**：文件变更时 `content_hash` 变化即触发重切块，旧版本 `superseded` 不删除，保留"当时文档是怎么写的"的追溯能力——与记忆的双时态同一思想。
- **父子块**：子块 200 字建索引保证召回精度，命中后取父块 800 字给 LLM 保证上下文完整。两套口径分别计量，互不挤占。

### 4.5 创新点三：记忆反哺知识库——巩固层的跨层流动

记忆的巩固层（三期）把反复验证的稳定事实提炼为知识候选，经人工确认后可写回知识库卡片（`doc_type='memory_distilled'`）。方向严格单向：记忆 → 知识库，绝不反向。这样"系统自己长出来的经验"可以沉淀为"可版本化、可分享、可 ingest 到别处的知识资产"，同时知识库永远不被运行期自动写入污染。

### 4.6 概要接口

```python
# backend/app/services/kb/ingest.py
def ingest_path(path: str, *, doc_type: Optional[str] = None) -> dict: ...
    """解析 → 版本化 → 分块 → 建索引；增量判定走 content_hash"""

# backend/app/services/kb/retrieve.py
def search(conn, query: str, *, top_k: int = 5,
           budget_chars: int = 800) -> list[ScoredChunk]: ...
    """走第二章共用管道；命中子块取父块"""

# backend/app/services/kb/inject.py
def build_kb_context(conn, *, task_signature: str,
                     budget_chars: int = 800) -> list[dict]: ...
    """产出带 [知识库] 标签的 system 消息，并入共用注入通道"""
```

### 4.7 验收口径（概要）

- 万篇文档级下检索 ≤100ms，无全表扫描；
- 2 字中文查询命中（与记忆同一双索引策略）；
- 文档变更后增量同步，旧版本可追溯；
- 注入 ≤800 字符，超限时知识库先于记忆被裁；
- 与记忆共用注入通道，无第二套注入路径。

## 五、明确不做

- 不引入向量数据库、图数据库、外部记忆服务、外部知识库服务。
- 不做多租户、不做云端同步。
- 不做全自动抽取直写（候选制是唯一写入方式）。
- 不做每轮 top-k 注入（任务开始一次注入 + 二期起模型按需工具查询）。
- 不把摘要当记忆（一期情景记忆只读派生，不三处存储）。
- 不把知识库当记忆用，不把记忆当知识库用。
- 不在一期做记忆的自动改写与自我进化；知识库写回必须人工确认。
- 不自建第二套注入路径，一切走 `_injected_history_msgs`。
