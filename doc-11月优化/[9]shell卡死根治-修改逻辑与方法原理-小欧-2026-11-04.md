## 二、病根：卡死是如何被放大成全站僵死的

三个环节串成一条链，缺任何一环都不会导致全站僵死。

### 2.1 三段式根因链

```
① 卡死点被引入
   shell_engine._exec_locked 每条命令 new 一个临时写线程 → _wrt.start()
   （2026-10-04 治理层3 为"stdin 写入有界化"加入，提交 518686d1a）

② 卡死点被搬到热路径
   _probe() 复用 _exec() 做探活
   → 每次 acquire 复用实例都要走一遍完整执行框架（2026-08-06 的 DRY 复用，提交 a7c3d89eb）

③ 全局放大器
   shell() 是同步函数，经 asyncio.to_thread 落到【默认】executor
   → ThreadPoolExecutor.submit 需要新建 worker 时，是在【调用线程】里
     执行 Thread.start()（concurrent/futures/thread.py 的 _adjust_thread_count）
   → 而调用线程就是事件循环线程
```

### 2.2 py-spy 现场取证（决定性证据）

```
MainThread   : getaddrinfo ← run_in_executor ← _adjust_thread_count ← Thread.start()   ← 永久卡住
asyncio_0/1/2: _exec_locked:619 start() ← _probe:448 ← acquire:997                      ← 永久卡住
新线程        : CPU=0，threading.Event._started 从未置位（Thread.start 内部就停住了）
```

证据文件：`backend/logs/pyspy/hang_20261104_0115_final_nonblocking.txt`

### 2.3 一句话概括

> 线程创建停顿一次 → 那个 executor worker 再也回不来 → 超时重试逐个把默认 executor 的 worker 烧光 → 连 DNS 的 getaddrinfo 都排不上 → **端口在监听但服务已死**。

### 2.4 卡死指纹（便于日后快速判定）

| 指纹 | 说明 |
|------|------|
| 端口仍在监听 | `Get-NetTCPConnection -LocalPort 8000` 有 LISTEN |
| `/health` 超时 | 请求排不上事件循环 |
| 日志停写 | loop 僵死，无新日志 |
| 新建线程 CPU=0 且 `_started` 未置位 | `Thread.start()` 内部停顿 |

## 三、修改①：`_StdinWriter` — 把"每命令建线程"改成"每实例建线程"

### 3.1 修改前实现（每条命令一次）

```python
_wrt = threading.Thread(target=_do_write, daemon=True, name="shell-stdin-writer")
_wrt.start()          # ← 事故卡死点在这里
_wrt.join(5)          # 有界等待
```

### 3.2 修改后实现（每个 shell 实例一次，在 `_start()` 里建）

```python
class _StdinWriter:
    def __init__(self, stdin, name="shell-stdin-writer"):
        self._q = queue.Queue()
        self._broken = False
        self._thread = threading.Thread(target=self._run, daemon=True, name=name)
        self._thread.start()          # ← 只剩这一处，每实例一次

    def write(self, data: bytes, timeout: float):
        if self._broken:
            return BrokenPipeError("stdin writer 已标记损坏")
        evt, box = threading.Event(), []
        self._q.put((data, evt, box))          # 命令热路径只有这一句
        if not evt.wait(timeout):              # 有界等待，替代 join
            self._broken = True                # 写线程已卡死，无法自愈
            return TimeoutError(f"stdin写入{timeout}s未返回")
        return box[0] if box else None
```

### 3.3 设计要点

| 维度 | 原理说明 |
|------|---------|
| **热路径零线程创建** | 命令执行路径上只剩 `queue.put()` + `Event.wait(timeout)`，没有任何 `Thread.start()` |
| **超时语义完全等价** | 原 `join(5)` 超时 = 写线程卡住 → 判死重建；现 `wait(5)` 超时 → 置 `_broken` → 判死重建。对上层 `_exec_locked` 返回的仍是 `TimeoutError` → M6 守卫清理 + `_EXIT_PROCESS_DIED` |
| **`_broken` 标志的意义** | 卡在 `stdin.write()` 的线程**不会自愈**，所以后续写必须快速失败，否则每次都要白等 5s。这是"判死"语义，不是"重试"语义 |
| **线程归属** | `daemon=True`；`_discard_stdin()` 只投哨兵**不 join**（join 一个卡在管道写的线程 = 自己又卡一次）；空闲时立即退出，卡住时随实例销毁自灭 |
| **回收点** | `_close()` 与 `_cleanup_guard_start()` 都调用 `_discard_stdin()`，幂等 |
| **`healthy()`** | 只查"未损坏 + 线程存活"两个状态位，**不做任何阻塞操作** —— 这是修改②能成立的前提 |

### 3.4 效果

**线程创建次数：从「每命令 1 次」降到「每实例 1 次」（仅在实例重建时一次）。**

## 四、修改②：`_probe` 轻量化 + `_ready_handshake` 拆分

### 4.1 `_probe` 改为纯状态查询

修改前：

```python
def _probe(self, env=None, timeout=None):
    result = self._exec(_PROBE_CMD, timeout=timeout or 3)   # ← 完整执行框架
    return "__OMNI_PROBE__" in result.get("stdout", "")
```

一次探活要付出：建 6 个临时文件 + 起写线程 + 走完整执行链 + 轮询结果文件 + 秒级耗时。**而它位于 acquire 复用路径上，每次复用都走一遍** —— 于是"探活"本身成了卡死入口（现场 `acquire:997 → _probe:448 → _exec_locked:619`）。

修改后：

```python
def _probe(self) -> bool:
    if self._proc is None or self._proc.poll() is not None:
        return False                              # 进程死了
    w = self._stdin_writer
    if w is None or not w.healthy():
        self._close(); return False               # 写通道坏了
    return True
```

**微秒级，不建文件、不起线程、不执行命令。**

### 4.2 代价与兜底（必须明确）

轻量探活的判据从"**能不能执行**"降级为"**进程活着 + 写通道活着**"，因此**半死进程（假活）探不出来**。

兜底链路不变，只是延后到真执行时暴露：

```
_probe 放过半死实例
  → 真执行 _exec_locked → _poll_for_file(timeout) 超时
  → M6 守卫杀进程 + _EXIT_PROCESS_DIED
  → release 判死剔除出池
  → 下次 acquire 走 _start 重建
```

**代价 = 偶发一次命令 timeout；换来 = 探活零成本、零卡死风险。** 这个交换是刻意设计：探活是热路径（每次复用都跑），半死是低频事件。

### 4.3 `_ready_handshake()` 单独抽出，仍真跑一条命令

此处**没有**改成轻量，原因有三：

| 原因 | 说明 |
|------|------|
| stdout 是 `DEVNULL` | 无法靠回读输出判就绪，只能看结果文件 |
| 管道可写 ≠ 能执行 | profile 损坏 / 解析器异常，只有真跑一条才暴露 |
| 冷启动约 1.5s 必须落在 `_start` 内 | 否则这 1.5s 会吃掉调用方的 timeout 预算 → `timeout=1` 的命令重启后必然再超时 → 陷入"超时→重建→再超时"的恶性循环 |

**为什么现在安全**：这条路径原本也走 `_exec`，而它的线程创建点已被修改①根除；且它只在**新建实例**时走一次，不在热路径上。

## 五、修改③：shell 专用有界执行器 — 隔离 + 预热 + 有界

这是对"全局放大器"的根治，三点设计缺一不可。

### 5.1 隔离：shell 不再走默认 executor

```python
_SHELL_TOOL_NAMES = frozenset({"bash", "shell", "execute_shell_command", "execute_command"})

if action in _SHELL_TOOL_NAMES:
    return await self._execute_in_shell_executor(tool, normalized_input, timeout)
result = await asyncio.wait_for(asyncio.to_thread(...), timeout=timeout)   # 其余工具不变
```

默认 executor 从此只承载 DNS / 文件等**短任务**，shell 再卡也只卡自己那一池。

### 5.2 预热：运行期绝不创建线程

```python
class _ShellWorkerPool:
    def __init__(self, n, name):
        for i in range(n):
            threading.Thread(target=self._run, name=f"{name}-{i}", daemon=True).start()   # 导入期一次建满
    def submit(self, fn):
        fut = concurrent.futures.Future()
        self._q.put((fn, fut))        # 运行期只有入队
        return fut
```

`_SHELL_EXECUTOR_MAX = max(32, shell_pool_max_per_type × 4)`，`_SHELL_EXECUTOR` 在**模块导入期**就把 32 个 daemon 线程建满。

**为什么不用 `ThreadPoolExecutor`**：它的 worker 是懒创建的，且 CPython 的 `_idle_semaphore` 短路让"导入期预热"建不满 —— 结果运行期仍会在 loop 线程里执行 `Thread.start()`，等于没修。

**效果**：`Thread.start()` 这个动作在**运行期彻底不存在**；建不起来 = 启动即失败，早暴露，而不是运行到一半偶发卡死。

### 5.3 有界：占不到槽位就明确失败

```python
_SHELL_SLOTS = threading.BoundedSemaphore(_SHELL_EXECUTOR_MAX)

while not _SHELL_SLOTS.acquire(blocking=False):
    if loop.time() >= deadline:                 # deadline = now + 本次 timeout
        raise TimeoutError("shell 专用执行器无空闲 worker ...")
    await asyncio.sleep(0.1)
try:
    fut = _SHELL_EXECUTOR.submit(lambda: tool(**params))
except BaseException:
    _SHELL_SLOTS.release(); raise
fut.add_done_callback(lambda _f: _SHELL_SLOTS.release())   # 归还槽位
return await asyncio.wait_for(asyncio.wrap_future(fut), timeout=timeout)
```

| 设计点 | 原理 |
|--------|------|
| 提交前占位 | 卡死的 worker 不会被无界任务继续堆叠，池子不会越堆越烂 |
| 排队上限 = 本次 timeout | 拿不到 worker 说明前序 shell 调用卡死未归还 → 明确失败 |
| 抛 `TimeoutError` | 被 `ToolErrorClassifier` 归为 TIMEOUT → 走**既有**的重试 / 回退语义，不新增分支 |
| `set_running_or_notify_cancel()` | 排队期被 asyncio 取消的任务直接丢弃，不会白跑 |
| `add_done_callback` 归还 | 成功 / 异常 / 取消三条路径都归还，槽位不泄漏 |

### 5.4 明确否定熔断方案（设计决策，非遗漏）

**没有**采用"连续 N 次超时就全局禁用 shell"的方案。理由：

> 偶发故障不应污染后续正常请求。一次偶发卡死就长期禁用 shell，等于把局部故障升级成全局功能缺失，得不偿失。

当前实现是**单次请求级退避**（本次失败、本次明确报错、下次照常尝试），不是跨请求熔断。

## 六、修改④：看门狗 `_run_bounded` — 恢复取证能力

### 6.1 修改前的缺陷

```python
r = subprocess.run([py_spy, "dump", "--pid", str(pid)],
                   capture_output=True, text=True, timeout=30)   # ← timeout 不管用
```

**`subprocess.run(timeout=)` 的 timeout 只在 `Popen` 构造成功之后才生效。** 2026-11-04 事故中 py-spy 正是卡在 `Popen.__init__`（`CreateProcess`）内 —— 超时根本没开始计时，看门狗线程被永久占住，**现场全丢**（`backend/logs/pyspy` 最新文件仍停在 2026-10-29）。

### 6.2 修改后实现

```python
def _run_bounded(cmd, timeout):
    box = []
    def _worker():
        try:
            box.append(subprocess.run(cmd, ..., timeout=timeout))
        except Exception as e:
            box.append(e)
    t = threading.Thread(target=_worker, daemon=True, name="watchdog-pyspy")
    t.start()
    t.join(timeout + 5)          # 主线程只做有界等待
    return box[0] if box else None
```

调用侧：

```python
r = _run_bounded([...], 30)
if r is None:                       # 超 35s 未返回
    logger.warning("py-spy dump 超35s未返回(进程级挂起) → 手动取证")
    continue
if isinstance(r, Exception): ...
```

**整个外部调用放进一次性 daemon 线程，主线程只做有界 join** —— 这才是真正管得住 `Popen.__init__` 的方式。取证失败只告警，绝不打断看门狗巡检。

## 七、改动前后完整数据流对比

### 7.1 shell 一次命令执行

| 阶段 | 改前 | 改后 |
|------|------|------|
| acquire 复用 | `_probe` → `_exec` → 建 6 个临时文件 + **Thread.start()** + 秒级 | `_probe` → `poll()` + `healthy()`，**微秒级、零线程** |
| 卸载出 loop | `to_thread` → **默认 executor**（可能在此 `Thread.start()`） | `_SHELL_EXECUTOR.submit` → **只入队** |
| 写 stdin | **每命令** `Thread.start()` + `join(5)` | 常驻 `_StdinWriter` → `queue.put` + `Event.wait(5)` |
| 超时后果 | 永久占死一个默认 worker，拖累 DNS 乃至全站 | 只占死 shell 池一格，池满则明确报错 |

### 7.2 线程创建点统计

| 位置 | 改前 | 改后 |
|------|------|------|
| stdin 写 | 每命令 1 次 | 每实例 1 次 |
| executor worker | 运行期按需（在 loop 线程） | 导入期 32 次（在导入线程） |
| 探活 | 每复用 1 次 | 0 |
| **运行期 loop 线程内** | **不确定，偶发** | **恒定 0** |

## 九、风险与代价说明

| 项 | 说明 |
|----|------|
| 半死进程多一次 timeout | `_probe` 轻量化后不再验证"能执行"，半死实例会在真执行时以一次 timeout 暴露，之后由守卫清理 + 剔除重建 |
| 写线程卡住后不可复用 | `_broken` 置位后该实例后续写一律快速失败，必须重建；这是刻意选择（卡住的线程无法自愈） |
| shell 池容量上限 | `_SHELL_EXECUTOR_MAX` 恒定上限，极端并发下会明确报错而非无限排队；如需提高须同步评估线程数 |
| 看门狗仍可能拿不到栈 | 若目标进程整体挂起（连 CreateProcess 都阻塞），`_run_bounded` 只能放弃并留痕，属能力边界而非缺陷 |

## 十、结论

> **把"创建线程"这个动作，从 shell 执行的每一条命令、每一次探活、每一次提交里彻底拿掉** —— 命令路径只剩队列与事件等待；线程只在实例创建和模块导入时各建一次；再用专用池把 shell 的故障关在自己的笼子里，不让它通过默认 executor 传染给 DNS 和整个事件循环。

三处改动的关系可以概括为：

| 修改 | 解决的问题 | 若缺失的后果 |
|------|-----------|-------------|
| ① `_StdinWriter` | 消除卡死点本身 | 卡死仍会发生 |
| ② `_probe` 轻量化 | 把卡死点移出 acquire 热路径 | 卡死概率仍高（每次复用都触发） |
| ③ 专用有界执行器 | 卡死不再扩散到全站 | 即使卡死也只死 shell 一个请求，不会全站僵死 |
| ④ `_run_bounded` | 下次卡死能抓到现场 | 定位困难（本次事故曾因现场丢失而多花数小时） |
