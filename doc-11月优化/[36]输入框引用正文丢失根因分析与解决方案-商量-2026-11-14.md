## 1. 结论与影响面

**缺陷不是一个"文本文件"的个案，而是一类**：

> 计划器把条目判成 `native`（表示"该模型能用原生通道"），装配层却只给 `attachment`、`url` 两种来源写了 wire 占位；其余来源既不写占位、又被 `native` 集合剔出文本块 → **首发的 user 正文里整条消失**。

首发（`init_history` 带 `plans`）各分支结果：

| 来源 | 内容 | 视觉模型 | 非视觉模型 |
|---|---|---|---|
| `selection`（片段） | text | **丢失** | **丢失** |
| `file`（整份） | text | **丢失** | **丢失** |
| `log` / `message` | text | **丢失** | **丢失** |
| `file` / `selection` | image/video/audio/richdoc | **丢失**（判 native 却无占位） | 装配层可走文本卡，但**解析层读不了二进制，提前丢弃** |
| `attachment` | 任意 | 正常（原生占位） | 正常（降级文本卡） |
| `url` | text | 正常（仅链接，按设计） | 正常（仅链接） |
| `url` | image/video/audio/richdoc | 正常（原生占位） | 正常（降级文本卡） |

插话路径（`build_interject_text`）不传 `plans`，全部按文本块渲染，**不丢正文**；但 `attachment`/`url` 的媒体在插话里退化为文本卡/链接，**丧失原生投递**（已知降级，非本次主缺陷）。

> 止血方向见第 3 章；**根治标准（状态模型 + wire 前缀体系）见第 4 章**；**可落地的逐文件代码见第 5 章**。第 3 章与第 4 章不是两套并行方案——第 3 章只是"若不等 P1 的应急方向"，其临时判据（手写 `source_kind in SLOT_WRITERS`）在 P1 被第 4 章的 `delivery` 字段取代，正式落码以第 5 章为准。

## 2. 根因分析

### 2.1 证据链

**现场日志**（`app_2026-11-14.log` 12:10:17，任务 `61b37fd6-...`）：`.md` 第 111 行、114 字符 / 61 tok，`rejected=0`，`process_events` 记录"1 文件 1 片段"；但同任务 `user_message` 只有原话，模型推理原文 `there's no quote/reference content included in their message` → **统计成功、注入失败**。

```
[refs] OK scope=first files=1 fragments=1 items=1 tokens=61 rejected=0
    paths=20261114-063908-61b3/三堂会审分析报告.md:111-111
```

**装配层矩阵实测**（`branch_matrix.py` 直接 `import` 现有函数，未改源码）：

```

file-richdoc  file/richdoc       richdoc/native -> 无内容(丢失)  richdoc/degraded -> 正文可见*
```

`*` 为"装配层假设 content 已就绪"的乐观结果；**真实链路里 `file/selection` 非文本在解析层已被丢弃**（见下），到不了"正文可见"。

**解析层独立缺口**：`resolver.py:193-224` 非 url/attachment 一律走 `read_text_file`；`browse_service.py:930-934` 判非文本即 `fail(UNSUPPORTED_TYPE)`（415）。→ `.png/.pdf/.mp4`（kind=file/selection）在解析期即丢弃，**与模型是否视觉无关**，是独立的第二道门。

### 2.2 根因：判据用错了维度

现行"先剔除 native 再补占位"要求两集合恰好互补，实际：

- 集合 A（有占位来源）= `{attachment, url}`
- 集合 B（`state=native`）= `{attachment, url, text 全来源, 视觉模型下的 image/video/audio/richdoc}`

`B - A ≠ ∅` 时即丢。正确应以 **A 为准决定跳过文本块**，而非以 state 为准。一句话：**用"能力可达"当"投递方式"，判据维度错位**。

### 2.3 逐分支裁定

| 来源 | 关键表现 | 裁定 |
|---|---|---|
| `selection` / `file` | 首发 text 恒 native → 丢；媒体视觉下丢、非视觉解析层 415 | **有问题（首发）** |
| `log` / `message` | `classify_ref` 恒映射 text→native → 首发必丢；前端未接线不可达 | **潜伏缺陷**，随主修一并修 |
| `attachment` | 首发 native→占位→原生 part（失败降级文本），正常；插话失原生 | **首发正常**，插话降级需知会 |
| `url` | text→opaque 仅链接；媒体原生占位；前端无生产者 | **链路正确但未验证** |
| 素材包 / 产物 | `feedPack` 用 `quoteFile` 覆盖 kind 丢来源语义；产物图片/视频落 415 | **有隐患** |

生产者：`file/selection` 由 `quoteFile/quoteSelection` 产生（FileDrawer、`quoteToast`、`@`、素材包、产物引用），**无文本类型守卫**；`url/log/message` 前端全仓未找到创建入口，属"契约支持但未接线"。

### 2.4 三堂会审：合规与关联

| 规范 | 裁定 | 依据 |
|---|---|---|
| SRP | 基本合规 | `build_user_turn_text` 只做装配，但"来源有无占位"知识被隐式塞入 |
| DRY | **违规** | "哪些来源有占位"由 `message_builder` 硬编码 `attachment/url`，与 `attachment_wire` 两份知识易漂移 |
| KISS-DIRECT | **违反** | `native` 同时表达"全文注入"与"原生 part"，凭 state 走分支必然漏 |
| SLAP | 合规 | 装配层无底层细节 |
| YAGNI | 部分违规 | `url/log/message` 契约齐备但未接线，形成死能力 |
| 禁止 backward | 合规 | 未发现兼容分支 |
| 关联一致性 | **违规** | `state_of` 判 native、装配不投递，矩阵/徽标与运行时再次分叉（同类 11-12"矩阵错显"） |

关联面：上游 `state_of`（text→native，直接触发）、`resolver`（415 第二道门）；下游 `attachment_wire`（只有 ATTACHMENT/URL_ITEM 两通道）；旁路插话（不丢但媒体失原生）、素材包（kind 降级）；展示层矩阵/徽标（显示 native 与实际不符）。

## 3. 止血方案（战术，立即）

> 目标只有一个：**堵住静默丢失**；结构性根治见第 4 章。

### 3.1 装配层：止血静默丢失

`build_user_turn_text`：把"跳过文本块"的判据从 `state==native` 改成"**该来源确有 wire 占位**"。

```python
# 现状(231-241): 以 state 判
native = {id(r) for r, p in zip(refs or [], plans or []) if p.state == "native"}

# 修复: 以"有 wire 占位"判, 与 text_refs 严格互补防双写
native_slot = {
    id(r)
    for r, p in zip(refs or [], plans or [])
    if p.state == "native" and p.source_kind in SLOT_WRITERS
}
text_refs = [r for r in (refs or []) if id(r) not in native_slot]
for r, p in zip(refs or [], plans or []):
    if id(r) not in native_slot: continue
    if p.source_kind == "attachment": ...
    elif p.source_kind == "url": ...
```

配套（DRY）：来源集合只留一处真源。止血阶段临时取 `attachment_wire` 现有占位键集合；P1 起统一由 4.4 的 `SLOT_WRITERS.keys()` 提供，**不新增 `SLOT_SOURCES` 长期常量**（避免第二真源）。

效果：`file/selection/log/message + text` 回到文本块（正文恢复）；`file/selection` 媒体不再被剔出，走元信息卡（至少不静默丢）；`attachment/url` 仍走占位；不改 `state_of`，矩阵/徽标口径不变。取舍：不追求文件媒体真原生，真原生见 4.5 的 P3。

### 3.2 解析层：修复 file/selection 非文本 415

`resolver._read_one` 非 url/attachment 分支：先 `classify(Path(path), mime, size)`；文本走 `read_text_file`，非文本走 `extract` 对应文本出口（`_image_card`/`_video_card`/`_audio_card`/`_richdoc_body`/`_binary_card`），产出元信息卡而非丢弃。

```python
ck = classify(Path(path), mime, size)
if ck != "text":
    route = KIND_CONTRACT[("file", ck)]
    return ResolvedRef(ref={**ref, "content": route.extractor({...})}, truncated=False, note="")
# 以下保持既有文本读取/区间/摘录逻辑
```

效果：文件页/素材包/产物引用的图片、PDF、视频不再 415，与 `fallback_quality` 对齐。注意：`extractor` 对 attachment 需记录字段，file 场景需构造最小 att dict（path/label/kind）或新增单参文本出口，须保持"文本出口唯一产生点"。

- 不用测试用例固化错误逻辑来"证明没问题"；
- 不在插话里强行塞 native parts（历史恒为 str，需另立设计，本次只标注降级）。


### 3.4 与第 4/5 章的关系（回答"第 3 章的修改还要不要"）

**结论：第 3 章不作为独立落码方案，只保留为"若必须抢在 P1 前上线"的应急方向；正式落码以第 4 章标准、第 5 章代码为准。**

## 4. 根治标准：状态模型与 wire 前缀体系（战略）

> 本章不是补丁，是**标准**：把"状态标签"与"前导标签"按"语义唯一、单一真源、处理器一一对应"定到数据模型层与注册表层，使新增来源/内容类型只需登记一条，不改装配、不改展开、不做中途翻译。第 3 章止血收敛为本章的一次性切割。

### 4.1 分层原则（G0~G4）

| 治理层 | 名称 | 交付物 | 载体 | 守门 |
|---|---|---|---|---|
| G0 | 术语契约 | 每个词只有一个含义 | 本章 | 评审 |

### 4.2 状态模型（G1）

**问题**：`state ∈ {native, degraded, opaque}` 一个枚举背了五种语义——① 模型能力可达（矩阵）、② 投递方式（装配）、③ 保真度（徽标）、④ 可投递性（`state_of`）、⑤ 展示档位（`CapabilityBadge`）。实证：`_reason()` 的"载荷不可获取"分支永不可达（枚举缺格子）；前端用 `(content_kind, state)` 二次翻译文案。**结论：`state` 是"能力+动作+保真"三件事挤在一个词里，必须拆开，每词只答一问。**

#### 4.2.1 三个字段

| 字段 | 回答 | 取值（封闭） | 谁读 |
|---|---|---|---|
| `quality` | 最终能拿到**多好的信息** | `native_part` \| `text_full` \| `text_card` \| `link_only` \| `none` | 前端徽标、矩阵、指标 |
| `delivery` | 装配层**怎么投递** | `slot` \| `text` \| `none` | 仅 `build_user_turn_text` / wire |
| `reason` | 为什么没到更高档 | 自由文本（排障/tooltip） | 日志、UI |

`quality` 是保真结果、不驱动装配；`delivery` 是装配动作、不描述保真。二者声明式全映射，不在各处 `if` 翻译：

```python
QUALITY_TO_DELIVERY = {
    "native_part": "slot", "text_full": "text",
    "text_card": "text",  "link_only": "text", "none": "none",
}
```

#### 4.2.2 `quality` 唯一派生规则

```python
def quality_of(source_kind, content_kind, cap, slot_writer) -> str:
    route = kind_route(source_kind, content_kind)
    if slot_writer and cap.native:          # 有原生通道 + 模型支持
        return "native_part"
    return {"content": "text_full", "metadata": "text_card",
            "card": "text_card", "link": "link_only"}.get(route.fallback_quality, "none")
```

关键：`slot_writer` 是否存在**参与判定**。`file/selection` 的 image 在视觉模型下 `cap.native=True` 但来源无原生 slot → `text_card`，`reason="来源无原生投递通道"`（正是旧枚举无处安放、死代码想表达的情形）。

#### 4.2.3 旧值 → 新值映射（一次性替换，不做兼容）

| 旧 `state` | 实际情形 | 新 `quality` | 新 `delivery` |
|---|---|---|---|
| `native` | attachment/url 媒体，模型支持 | `native_part` | `slot` |
| `native` | text / richdoc 全文注入 | `text_full` | `text` |
| `native` | 模型支持但来源无 slot（旧丢失 bug） | `text_card` | `text` |
| `degraded` | 媒体元信息卡 | `text_card` | `text` |
| `degraded` | 富文档抽取全文 | `text_full` | `text` |
| `opaque` | 仅链接地址 | `link_only` | `text` |
| `opaque` | 未知/不可用 | `none` | `none` |

#### 4.2.4 装配契约：一个 `delivery` 对应一个分支

```python
if p.delivery == "slot":
    refs_block += SLOT_WRITERS[p.source_kind].make(ref)   # 注册表取用，无 source 硬编码
elif p.delivery == "none":
    refs_block += notice_line(p)                           # 明确告知"未投递"
else:                                                      # text
    text_refs.append(ref)                                  # 交 render_refs_block
```

- 禁止再出现 `if p.source_kind == "attachment" ... elif == "url"`；禁止在装配层重新解释 `quality`；
- `attachment + text` 由"slot 绕一圈降到 text"改为**直接 `text_full`**（正文由 resolver 已产出）。

#### 4.2.5 前端/矩阵投影与删除项

- `ref_capability_map` 更名 `ref_quality_map`，直接返回 `quality`（5 值），不由 `content_kind` 二次翻译；`CapabilityBadge` 的 key 从 `(content_kind, state)` 改为 `quality`；
- 徽标语义：`native_part`=原生投递、`text_full`=全文注入、`text_card`=元信息注入、`link_only`=仅链接、`none`=不可用；
- 删除 `STATES`，替换为 `QUALITIES`/`DELIVERIES`；删除无调用方的 `aggregate_state()`；`state_of()` 更名 `quality_of()`。

### 4.3 wire 前缀体系（G1）

#### 4.3.1 数据前缀分五层 + 提示区段头，括号风格唯一

| 层 | 用途 | 括号风格 | 闭合 | 方向 |
|---|---|---|---|---|

```python
# 2026-11-14 商量 新建: 引用槽位注册表(SlotWriter + SLOT_WRITERS + 编解码)。来源集合只由本表

"""ref_slots — 引用槽位注册表: 来源 → (正则, 占位构造器)。

SLOT_WRITERS.keys() 是"可写原生槽来源"的唯一真源; make(ref) 恒返回一行 wire 文本
(占位或占位失败时的降级链接文本), 装配层直接拼接, 不再按 source_kind 分派。
"""
import base64
import re
from dataclasses import dataclass
from typing import Callable, Dict, Tuple

from app.wire_prefix import (
    SLOT_ATTACHMENT_RE,
    SLOT_URL_RE,
    SLOT_LABEL_ATTACHMENT,
    SLOT_LABEL_URL,
)

_URL_ITEM_MAX = 512  # b64url 编码上限; 超长不写占位, 装配期降级链接文本


def attachment_slot(ref: dict) -> str:
    aid = str(ref.get("attachment_id") or "")
    return f"[[ATTACHMENT:{aid}]]" if aid else ""


def url_item_slot(item: dict) -> Tuple[str, str]:
    """URL → (占位, 链接文本)。编码超 512B 返回 ("", 链接文本) —— 不产生坏占位。"""
    url = str(item.get("url") or "")
    enc = base64.urlsafe_b64encode(url.encode("utf-8")).decode("ascii").rstrip("=")
    if len(enc.encode("ascii")) > _URL_ITEM_MAX:
        return "", url
    return f"[[URL_ITEM:{enc}]]", url


def decode_url_item(token: str) -> str:
    pad = "=" * (-len(token) % 4)
    return base64.urlsafe_b64decode(token + pad).decode("utf-8", errors="replace")


def _make_attachment(ref: dict) -> str:
    slot = attachment_slot(ref)
    return f"{SLOT_LABEL_ATTACHMENT}: {slot}\n" if slot else ""


def _make_url(ref: dict) -> str:
    slot, link = url_item_slot(ref)
    return (f"{SLOT_LABEL_URL}: {slot}\n" if slot
            else f"{SLOT_LABEL_URL}: (链接文本) {link}\n")


@dataclass(frozen=True)
class SlotWriter:
    pattern: re.Pattern
    make: Callable[[dict], str]


SLOT_WRITERS: Dict[str, SlotWriter] = {
    "attachment": SlotWriter(SLOT_ATTACHMENT_RE, _make_attachment),
    "url": SlotWriter(SLOT_URL_RE, _make_url),
}
```

```python
                         ws_text: str = "",
                         plans: Optional[list] = None) -> str:
    """装配本轮 user 消息正文: [引用文本块/槽位行][事项目录块][用户原话]。

    纯装配(零 IO / 零状态)。plan.delivery 决定每项去向(唯一分支依据):

    """
    plan_by_id = {id(r): p for r, p in zip(refs or [], plans or [])}
    text_refs: List[dict] = []
    wire_lines: List[str] = []
    for r in refs or []:
        plan = plan_by_id.get(id(r))
        delivery = plan.delivery if plan is not None else "text"
        if delivery == "slot":
            wire_lines.append(SLOT_WRITERS[plan.source_kind].make(r))
        elif delivery == "none":

        else:
            text_refs.append(r)
```

### 5.10 三堂会审（落码前自检）

**合规检查（10 大规范）**

| 规范 | 判定 | 落码证据 |
|---|---|---|
| SRP | 合规 | `ref_slots` 只做槽位编解码；`contract._plan_of` 只做判定；装配层只做拼接 |
| DRY | 合规 | "有无原生槽"仅 `SLOT_WRITERS.keys()` 一处；质量判定仅 `_plan_of` 一处（计划器/矩阵共用） |
| KISS-DIRECT | 合规 | 装配 `if delivery` 三分支直落，无 `source_kind` 硬编码、无中间透传层 |
| SLAP | 合规 | 装配层无正则/IO/分类细节，全部下沉 |
| YAGNI | 合规 | 未提前引入 `can()`/`expand` 等未用字段（`SlotWriter` 仅 `pattern`+`make`） |
| 禁止 backward | 合规 | 直接删 `state/transport/STATES/state_of/aggregate_state/ref_capability_map`，不留兼容分支 |
| OCP（重构） | 合规 | 新增来源只需在 `SLOT_WRITERS` 加一条，装配/展开零改 |
| LSP | N/A | 无继承体系 |
| ISP | 合规 | `SlotWriter` 接口最小（2 字段），不塞无关方法 |
| 复用优先 | 合规 | 复用 `extract` 唯一出口、`clip_text`、既有 `render_refs_block`，未重造 |

**合理检查（最优逻辑）**

- 计划器 `_plan_of` 三支直线：`有槽且模型支持 → native_part/slot`；否则按 `fallback_quality` 映射质量，`delivery` 由 `QUALITY_TO_DELIVERY` 查表（无第二处 if）；
- 装配层按 `delivery` 单维分派，`quality` 不参与装配（正交性落地）；
- 解析层在 `_read_one` 单点分流，媒体/富文档走契约出口，不改既有文本/区间逻辑。

## 7. 下一阶段立项（范围外分叉的全局方案）

本章收纳首批（第 5 章）明确不做的两条分叉。它们与本缺陷**同源但不同触发条件**，不属本批回归；本章给出问题定性、真实根因与基于全局逻辑的解决路径，作为下一阶段输入。两条均**不属于"补丁式小修"**：一条涉及契约是否该存在，一条涉及装配链路缺环。

### 7.1 议题一：内部来源引用 `log/message` 接线

#### 7.1.1 现象与定性

- `KIND_CONTRACT` 对 `("log", *)`、`("message", *)` 恒映射 `_BASE["text"]`（`contract.py:98-99`），`classify_ref` 恒返回 `text`（`contract.py:125-126`），注释声称"内部来源恒为文本语义"；
- 但全链路**没有任何生产方**，也无正文来源。这不是"日志功能出错"，而是一条**契约已声明、链路未接通**的悬空分支。

#### 7.1.2 三段链路全部断开

| 环节 | 事实 | 代码坐标 |
|---|---|---|
| 生产侧 | 前端 `ChatRefPayload.kind` 只有 `'file' \| 'selection' \| 'attachment'`，`ComposerRef` 同源，UI 无产生 `log/message` 条目的入口 | `frontend/src/types/chat.ts:281`、`refs/store.ts:53` |
| 传输侧 | 2026-10-29 起前端删除 `content` 字段，wire 不承载正文；`ChatRef` 后端仅放宽 `kind: str` | `types/chat.ts:17`、`api/v1/chat/models.py:42-44` |
| 解析侧 | `resolver._read_one` 仅对 `url`/`attachment` 分支，其余一律要求 `path`；`log/message` 无 `path` → `no_path` dropped | `resolver.py:179-195` |

结论：所谓"降级"实为"**不可达**"——没有任何真实消息会走到这段契约，因此现场永远不会报错，也永远不会生效。

#### 7.1.3 全局逻辑纠偏：正文来源应与"有无 path"正交

当前裁决把"能否解析正文"隐式绑定在"是否有文件 path"上。这是文件引用主导期留下的耦合。`log/message` 的语义是"**来源自带正文**"，正文应随条目的正文载荷到达，而非从磁盘读。

正确模型是引入一个正交维度 `body_source ∈ {inline, disk, fetch, table}`：
- `file/selection` → `disk`（读盘，现有逻辑）；
- `url` → `fetch`（链接文本/远取）；
- `attachment` → `table`（按 id 查表）；
- `log/message` → `inline`（条目自带正文）。

`resolver` 按 `body_source` 分流，`path` 只是 `disk` 分支的入参，不再是全局门槛。这与第 4 章"单一真源 + 正交拆分"一致，不新增第二套判定。

#### 7.1.4 方案（按前置条件分阶段）

- **阶段 0（阻塞项，先答产品）**：确认 `log/message` 的真实入口与语义——"引用某条日志事件"还是"引用内部消息"？**若无真实入口，按 YAGNI 直接删除契约中的 `log/message`**（连同 `classify_ref` 的两行恒等分支），不留不可达分支。这比接线更符合"禁止 backward / 不留死代码"。
- **阶段 1（仅当阶段 0 确认要接线）**：契约扩容——`ChatRefPayload.kind` 增 `'log' | 'message'`，新增 `content`（自带正文）或 `event_id`（后端反查）；`toWireRef` 白名单同步补字段（`identity.ts:37`），防字段被静默剥掉。
- **阶段 2**：`resolver._read_one` 前置分流新增 `inline` 分支：有正文 → `ResolvedRef(content, note="")`；无正文 → `note="err:inline_missing"`（与文件 `no_path` 区分，回执可归因）。
- **阶段 3（安全边界，不可省）**：自带正文必须经 `render_refs_block` 的"不可信数据"声明包裹并 `clip_text` 限长；正文不得入库（`chat_user_message` 无 refs 列）。此步等价于**重新开启"前端正文上行"通道**，须重审 prompt 注入面。
- **与 P1 的关系**：P1 已让 `text` 类统一走文本块出口，`log/message` 一旦具备正文会自动进入同一出口，装配层零改动。

#### 7.1.5 验收

- `log/message` + 有正文 → 首发 user 正文含该正文且带不可信声明；
- 无正文 → 回执 `reason=inline_missing`，显式告知而非静默 dropped；
- 契约表不再存在"恒等映射却无生产方"的死分支（要么接线、要么删除）。

### 7.2 议题二：插话路径原生投递（`plans` 未贯通）

#### 7.2.1 现象

任务运行中、会话开启插话（`allow_interject`）时，用户继续输入并带附件/图片/URL，媒体在插话这一轮降级为文本卡或链接，不生成原生占位，模型拿不到原生 parts。

#### 7.2.2 真实根因（纠正首批表述）

首批曾写作"历史恒为 str 的既有约束"，**该理由不成立**：首发同样是 str（占位文本存 `conversation_history`，wire 边界才展开 parts，见 `message_builder.py:637-639`、`expand_attachment_parts:641-652`、`react_step.py:406-407`）。真正差异在**计划裁决环节缺失**：

| 路径 | 解析 | 计划裁决 | 装配 |
|---|---|---|---|
| 首发 | `prepare_refs` | `react_loop.py:241` 调 `plan_refs(refs, profile)` → `init_history(plans=)` | `build_user_turn_text(..., plans)` 对 native 项写占位 |
| 插话 | `prepare_refs`（`stream_orchestrator.py:705`） | **无 `plan_refs`** | `build_interject_text(user_input, _ifinal, ws_text)`（`:757`）→ `build_user_turn_text` 收到 `plans=None`（`message_builder.py:232`），全部按文本块渲染 |

而 `expand_attachment_parts` 对**全部 user 消息**遍历展开（`react_step.py:407`），插话注入的 user 消息同样会被展开。因此：**只要插话写出占位，原生投递即自动生效，无需改 `inject_message_to_task` 的 str 契约**。插话降级的本质是缺 `plan_refs`，不是传输能力缺失。

#### 7.2.3 全局逻辑：装配输入 = 已解析正文 + 已裁决计划

装配函数 `build_user_turn_text` 的唯一输入应是"解析后的 refs + 裁决后的 plans"，首发/插话共用同一份。`plan_refs` 是纯函数 `(items, profile) → plans`，插话侧只需取目标任务的模型画像即可复用，不存在新机制。

#### 7.2.4 方案

- `stream_orchestrator` 插话分支：用与 `react_loop` 同口径的画像 `profile(getattr(_tgt_agent, "_task_llm_model", ...))`，对 `_ifinal` 调 `plan_refs` 得 `_iplans`；
- `build_interject_text` 增 `plans` 形参并透传 `build_user_turn_text`（`message_builder.py:424-449`）；
- `inject_message_to_task` 保持 str（占位文本），wire 展开在 `react_step` 统一完成，**无契约变更**；
- 预算不变：插话已用 `resolve_limits(..., "interject")`，plans 不改变预算口径；
- 一致性收益：插话与首发共用 `plan_refs`，从根上消除"首发原生、插话降级"的口径差。

#### 7.2.5 验收

- 插话带 `attachment/image` → 注入的 user 消息含 `[[ATTACHMENT:` 占位，且下一步 LLM 请求含原生 image part；
- 插话带 `url` → 含 `[[URL_ITEM:`；带文本 `file` → 仍走文本块；
- 全分支矩阵增加 `interject` 维度，断言与首发同口径。

### 7.3 与各批次的关系

| 批次 | 内容 | 依赖 | 备注 |
|---|---|---|---|
| P1（本批） | 状态拆 `quality/delivery`、装配三分支、文本出口修复 | — | 修复正文丢失主因 |
| P2 | `extract`/`attachment_service` 可见文案归一 | P1 | 改模型可见提示词，需同步 e2e |
| P3 | `file/selection` 原生槽 | P1 | 文件页图片直送视觉模型 |
| 7.1 | `log/message` 接线或删除 | 阶段 0 产品确认 | 无入口则删除，不做死分支 |
| 7.2 | 插话 `plans` 贯通 | P1（`ItemPlan` 新字段） | 改动仅插话分支 + 一个形参 |

7.1 与 7.2 互不依赖，可并行；7.2 必须在 P1 的 `ItemPlan` 新字段落地后进行，否则 `plan_refs` 产物与装配层字段不一致。
