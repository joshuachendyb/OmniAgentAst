## 一、要解决的问题（源自一次实测取证）

### 1.1 现象

后台 shell 命令执行完成后，后端会自动续跑（新建一个任务继续推进）。此时前端：

- AI 消息不流动（新任务的输出出不来）
- 任务面板状态停在旧任务
- 严重时"发不出新消息"

### 1.2 现状链路（代码实证，逐段核对）

```
① 后台 shell 跑完
   └→ bg_shell_notifier.notify_bg_shell_done()
        ├─ 同会话【有】活跃任务 → inject_system_notice() 注入 inbox
        │      ↑ 同一个 task_id，SSE 连接不断，正文照常流动 —— 此路径本来就没问题
        └─ 同会话【无】活跃任务 → resume_session_with_notice()
               └→ create_task_stream_buffer(新 task_id) + register_task(新 task_id)
                      ↑ 诞生了全新的 task_id，全新的 StreamBuffer
② 前端手里锚定的是旧 task_A，它的 SSE 流早已随 task_A 终态关闭
③ 前端靠 ChatPage 的 3 秒轮询兜底：
      index.tsx:217-225  setInterval(attachOrphanTask, 3000)
      └→ attachOrphanTask() 查 GET /sessions/{id}/tasks（SQLite）
           └→ 发现新的 executing 任务 → reanchorToTask() + detachResumeStream()
                └→ 才建立起 task_B 的 SSE，AI 消息开始流动
```

### 1.3 结论：功能是通的，但代价是"3 秒盲区 + 每 3 秒打一次库"

**必须纠正一个曾出现的错误判断**：不能说"前端永远发现不了新任务"。**已有 `attachOrphanTask` 3 秒轮询兜底**（2026-11-18 opencode 加入，`chatStreamStore.ts:1791`，`ChatPage/index.tsx:217-225`）。真实缺陷是下面四条，不是"完全不通"：

| # | 缺陷 | 后果 | 证据 |
|---|---|---|---|
| ① | **最坏 3 秒延迟** | 后台命令一结束，用户要盯着空界面等最多 3 秒才见消息 | `setInterval(attach, 3000)` |
| ② | **后台标签页被浏览器节流** | Chrome 对不可见页面的 `setInterval` 限流到 ≥1 分钟；用户切走再切回，才补上 | 浏览器行为，非代码可控 |
| ③ | **每 3 秒一次 SQLite 查询** | `GET /sessions/{id}/tasks` → `storage.list_session_tasks` 真查库；多标签页 × 多会话成倍放大 | `sessions.py:137` |
| ④ | **只在会话页挂载期间生效** | 用户在历史页/文件页，顶栏"在跑任务"感知不到新任务 | 轮询写在 `ChatPage` 内 |

### 1.4 根因（一句话）

> **订阅键是 `task_id`，但 `task_id` 会变。**
> 任务内容流以 `task_id` 为键（`agent_streams: dict[task_id]`），生命周期完全正确，但"任务换了"这个**事实**没有任何比 task 更长寿的通道能送达前端，前端只能靠定时查库去"猜"。

正解不是给轮询提速（3 秒→1 秒只会把库打得更狠），而是**引入一个生命周期比 task 长的订阅键：`session_id`**。

## 二、推送到已有几种方案（针对"外部系统接入 + 稳定可靠 + 灵活扩展"）

### 2.1 全清单与选型

| 方案 | 机制 | 稳定性 | 外部系统接入难度 | 扩展性 | 适用判断 |
|---|---|---|---|---|---|
| **短轮询** | 客户端定时 GET | 高，但浪费 | 最简单 | 差：压力随客户端数线性增长 | 只作兜底，不作主通道 |
| **长轮询** | 请求挂起至有数据或超时 | 高 | 简单 | 中：占连接/worker，超时需重平衡 | 老环境（不支持流式）时的降级 |
| **SSE** | HTTP 单向流 | **高**：纯 HTTP，反代/CDN/curl 通吃，断线重连与续传机制成熟 | **最容易**：任何 HTTP 客户端可用，`curl` 即可调试，无需专用库 | **好**：服务端无状态，可水平扩容 | ✅ **本项目主通道** |
| **WebSocket** | 协议升级，双向帧 | 中：需自写重连/心跳；反代须配 `Upgrade`；部分企业代理直接拦 | 难：必须引入专用客户端库 | 中：有状态长连接，扩容需粘性会话 | 仅在需要**双向**指令回执时 |
| **Webhook** | 服务端主动 POST 到外部 URL | 高（配重试） | **最容易**：外部系统只需暴露一个 HTTP 入口 | 好：一个 URL 一个订阅方 | ✅ **对外开放的标准答案** |
| **WebPush** | 浏览器推送服务（FCM/APNs） | 中：允许丢、有体积限制 | 不适用（浏览器专用） | 差：iOS 要求 PWA 加到主屏 | ✅ 只做"人不在时叫醒" |
| **MQTT / AMQP** | 消息代理（Broker） | 高 | 难：需部署 Broker + 客户端 | **最好**：弱网、海量设备、QoS | 未来多设备/离线设备群再上 |
| **Redis Pub/Sub / Kafka** | 服务间消息总线 | 高 | 不直接对外 | 好：多实例部署必备 | 后端要多进程/多实例时必上 |

### 2.2 三个必须分清的"推送"概念

混为一谈是设计翻车的根源：

| 概念 | 承载什么 | 能不能丢 | 本项目选型 |
|---|---|---|---|
| **A. 任务内容流** | AI 正文（thought / 工具调用 / 回答） | **不能丢**，必须可回放 | 已有：`StreamBuffer` + seq + Journal + `after_seq` 续传 |
| **B. 会话变更流** | 变更信封（任务起停、HITL 待处理） | **可以丢**，丢了靠对账 | 本文新增：`SessionEventBus` |
| **C. 系统通知** | "叫醒"一句话 | 允许丢 | [59] 2.2.3 主动推送：WebPush |

**A 与 B 绝不能合并**：A 要 seq/回放/落库，B 只是通知，塞进 A 会把 seq 语义污染（[59] 2.2.2 铁律：不做全局 seq）。

### 2.3 结论：为什么最终选 SSE 而不是 WebSocket

1. **现有真资产全在 HTTP 流上**：`after_seq` 续传、Journal 回放、指数退避重连、idle 看门狗（`chatStreamTransport.ts` 1436 行）——换 WS 等于全部作废重写。
2. **业务只需下行**：用户操作已走 REST（`POST /chat/stream/confirm`、`/answer`、`/cancel`）。WS 的双向能力**当前零消费方**（YAGNI）。
3. **外部系统接入**：SSE 用 `curl -N` 就能接；WS 必须引库，且企业代理常拦 `Upgrade`。
4. **扩展路径顺**：SSE 无状态 → 将来多实例，加一层 Redis Pub/Sub 把事件广播到各实例即可；WS 有状态 → 扩容要粘性会话。

> **什么时候才该上 WebSocket**：真需要"服务端下发指令、客户端必须回执"（远端执行端）。那属于 [59] 2.2.7 执行端抽象，当前判定"不预建"。

## 三、架构设计

### 3.1 总体结构：事件内核 + 多 Sink

```
                        ┌─────────────── 业务事件产生点（唯一、不可能漏）───────────────┐
                        │  register_task()          → task_started                     │
                        │  cleanup_task()/过期清理   → task_ended                       │
                        │  set_cancelled/paused/resumed → task_status_changed           │
                        │  create_confirmation()    → hitl_pending (kind=confirm)       │
                        │  create_question()        → hitl_pending (kind=question)      │
                        │  resolve_*()              → hitl_settled                      │
                        └───────────────────────────┬───────────────────────────────────┘
                                                    │  publish_event(type, session_id, payload)
                                                    ▼
                                    ┌───────────────────────────────┐
                                    │   EventBus（全局单例）         │  纯内存 · 无 seq · 可丢
                                    │   subscribers: Set[Queue]      │  最近 32 条 ring（重连补发）
                                    │  所有事件均携带 session_id     │  前端按 session 过滤
                                    └───────────────┬───────────────┘
                                                    │ 多 sink 分发给消费者
              ┌─────────────────────┬───────────────┴──────────────┬─────────────────────┐
              ▼                     ▼                              ▼                     ▼
    ┌──────────────────┐  ┌──────────────────┐        ┌──────────────────┐  ┌──────────────────┐
    │ SSE sink（本期）  │  │ Webhook sink     │        │ WebPush sink     │  │ MQ sink（未来）   │
    │ GET /chat/events │  │ （对外系统，阶段2）│        │ （手机叫醒，阶段3）│  │ 多实例/设备群     │
    │ 1 条常驻连接      │  │ 订阅表+HMAC签名   │        │ VAPID+订阅表      │  │                  │
    │                  │  │ 失败重试+退避     │        │ 只推终态+待处理   │  │                  │
    └──────────────────┘  └──────────────────┘        └──────────────────┘  └──────────────────┘
```

**为什么是"全局单总线"而非"每会话一条总线"**：

| 维度 | 每会话一个 bus | 全局单 bus + 事件带 session_id |
|---|---|---|
| 前端常驻连接数 | N（标签页 × 会话） | **1** |
| 后端对象管理 | dict + 回收逻辑 | **1 个对象，无回收** |
| 顶栏感知"别的会话有新任务" | 需额外全局流 | **天然支持**（事件本身就带 session_id） |
| 多用户/多租户 | 天然隔离 | 需按 user 拆 bus（本项目单用户本地私有化，无此需求） |

判据：项目定位是**本机单人使用**（[59] 1.2 宿主假设），全局单 bus 是当前形态下的正解；将来若要多用户，把 bus 按用户拆开即可（`dict[user_id, EventBus]`），事件契约不变。

**关键设计点：本期只实现 SSE sink，但事件内核一次做对，后续 sink 只加不改。**

### 3.2 事件契约（信封，绝不含正文）

| type | payload | 消费方动作 |
|---|---|---|
| `task_started` | `{task_id, created_at, trigger: "user"\|"resume"\|"timer"}` | 前端若 `task_id != 当前锚点` → `reanchorToTask` + 接流 |
| `task_ended` | `{task_id, status}` | 刷新任务列表；若正是当前锚点，标记终态 |
| `task_status_changed` | `{task_id, status}` | 更新暂停/恢复标识 |
| `hitl_pending` | `{task_id, hitl_id, kind, tool_name?, path?}` | 弹确认/问询 UI |
| `hitl_settled` | `{hitl_id, task_id}` | 收起 UI |
| `ping` | `{ts}` | 心跳，前端据此判断连接是否假死 |

**信封里带 `task_id` + `created_at` 是为了让前端不必再查库就能重新锚定** —— 这正是消除 3 秒延迟的关键。

### 3.3 可靠性设计：允许丢，但必须对账

信封流刻意**不做 seq、不落库**（相比 task 内容流省掉大量复杂度）。代价是重连期间可能丢事件，因此必须配套：

| 机制 | 做法 | 解决的问题 |
|---|---|---|
| **心跳** | 后端每 20s 发 `ping` | 检测"TCP 活着但不给数据"的假死连接 |
| **假死判定** | 前端 >45s 无任何事件 → 主动断开重连 | 同上 |
| **重连补发** | bus 保留最近 32 条，重连带 `last_event_id` 补齐 | 短暂断线不丢 |
| **重连对账**（兜底） | 重连成功后拉一次 `GET /sessions/tasks/running`，与本地锚点比对，不一致则重新锚定 | 长时间断线/服务重启后的事件真空 |
| **队列满即丢** | 订阅者队列有上限（如 256），满了丢弃最旧 | 慢消费者不拖垮生产者 |
| **无订阅者不占资源** | bus 在最后一个订阅者离开后延迟 60s 回收 | 内存不泄漏 |

> **哲学一致**：[59] 2.2.3 已定"推送只负责叫醒，真相以 Journal + after_seq 为准"。这里同理——**信封只负责说"变了"，真相去查 DB/内容流**。

### 3.4 广播点选择：为什么挂在 `register_task`/`cleanup_task` 而不是业务层

备选方案对比：

| 方案 | 遗漏风险 | 评价 |
|---|---|---|
| 在编排层 `_create_and_launch_task` 播 | ❌ 高：`resume_session_with_notice` 是另一条路径，将来 timer 触发是第三条 | 撒点，必漏 |
| 在各业务函数播 | ❌ 高：同[59] 2.2.2 已论证的"挂调用点必漏" | 撒点，必漏 |
| **在 `register_task` / `cleanup_task` 播** | ✅ **零**：任何任务诞生必过 `register_task`，任何任务终结必过 `cleanup_task` | ✅ 数据层唯一入口，天然收口 |

这正好复刻了 `StreamBuffer.persist_sink` 的教训（[59] 2.2.2 原话）：**"挂在 publish 收口而非调用点，因事件有三条发布路径，挂调用点必漏"**。

**注意**：`register_task` 返回 `str`（同会话已占位）时**没有真正注册新任务，不得广播**。

### 3.5 与现有系统的边界（不改什么）

| 已有能力 | 是否改动 |
|---|---|
| `StreamBuffer` 的 seq / Journal / `after_seq` 续传 | **零改动** |
| `persist_sink` / `flush_sink` | **零改动** |
| `chatStreamStore` 的 `reanchorToTask` / `detachResumeStream` | **复用，不改** |
| `runningTasksStore.refreshRunningTasks` | 保留，改为"重连对账 + 可见性变化"驱动 |
| `attachOrphanTask` 3 秒轮询 | **移除定时器**，函数本身保留作对账（逻辑复用） |

| **HITL 播报/快照/收敛（函数级 10 项）** | **全 PASS**：`hitl_pending`（confirm+question）播报、`GET /chat/hitl/pending` 可查、解决后 `hitl_settled` 且快照移除 |
| **HITL 信封不携带弹窗正文** | 通过（confirm 信封仅 `hitl_id/kind/task_id/tool_name/path`；question 仅加 `count`） |
| **HITL 真实端到端（真实 LLM）** | **通过**：LLM 调 write 工具写 `project_root` 外路径 → 安全层判 `write_outside_whitelist` → SSE 收到 `hitl_pending` → HTTP 快照查到（age 0.4s）→ 批准 → SSE 收到 `hitl_settled` → 快照移除 → **目标文件真实落盘** |
| **点角标跳转后弹窗能否出现** | **通过**：`GET /chat/stream/{task_id}?after_seq=0` 流内帧含 `interact`，content 带目标路径/拦截原因/授权时效，故跳过去弹窗可正常渲染 |
| 前端静态检查 | `typecheck` 通过、`eslint` 0 error、`prettier` 通过 |
| 后端静态检查 | `ruff --select F,E9` 全通过；导入无循环 |

> **2.2.9 跨端 HITL 路由的完成度（截至本期）**：
