- 编写: 小欧 2026-11-12

- 涉及文件:

  - 前端 `frontend/src/features/chat/components/input/CapabilityBadge.tsx`（三态徽标）
  - 后端 `backend/app/attachments/contract.py`（`state_of` / `ref_capability_map` 契约）

## 1. 功能现状（代码核实）

面板由 `ModelTabRefCapability` 渲染，数据 = `ModelEntry.ref_capability_map`，由后端 `contract.ref_capability_map()` 生成，前端只读投影不推导。

- 行 = content_kind 七类：text/image/video/audio/richdoc/binary/unknown
- 列 = source_kind 三通道：file(文件引用)/attachment(附件)/url(链接)
- 单元格 = 三态徽标：native(原生理解)/degraded(降级)/opaque(仅档案)，缺格显示「—」
- 底部 MetricsStrip：拉取 `GET /attachments/metrics` 展示近 1 天三比率 + fetch_fail 计数

三态判定（`state_of` 唯一状态函数）：
1. 该类型有原生通道 且 模型声明了该输入模态 且 载荷可获取 → native
2. 否则降级质量为 content/metadata → degraded
3. 否则 → opaque

## 2. 三个疑问的准确解答

### 2.1 左侧行是不是"输入模态支持类型"？三通道为什么只有 3 种？

**行不是输入模态**。行是「内容形态」——附件/引用物按后缀/MIME 二维分类出的 7 类（文本/图片/视频/音频/富文档/二进制/未知）。它与"输入模态"是两个概念：输入模态是模型声明"我能吃图片/视频"；内容形态是"送进来的这个东西是什么"。矩阵回答的是：**每类内容 × 每条通道，模型实际能理解到什么程度**。

**通道确实只有 3 种**，这是系统中用户把内容递给模型的全部入口（`classify_ref` 唯一分类点）：
1. **引用（file）**——工作区/项目里的文件路径引用（只记路径不复制，发送时现场读取）
2. **附件（attachment）**——聊天输入框上传的附件（复制进附件目录的文件实体，有 attachment_id）
3. **外链（url）**——粘贴的 URL 引用

分类是完备的：用户能提供的引用物只有"路径、上传、网址"三种来源，故 3 列覆盖全部入口，划分逻辑合理。另有 log/message 两内部来源恒映射 text，不对外展示。

### 2.2 模型从未使用过也有这张表，合理吗？

**合理，且是刻意设计**。这张表是**静态契约推演**（`ref_capability_map` 纯函数：模型 profile + 契约表 → 三态），回答"这个模型**应该**能做什么"，不依赖任何运行数据。作用正是让用户**在用之前**就能预判该模型适不适合带附件的任务——没用过恰好是这张表的价值所在。

与之对照，底部「运行指标条」是**动态实测**（近 1 天真实运行聚合），没跑过就没有数据（`if (!keys.length) return null` 直接不渲染）。

即：**矩阵 = 契约承诺（先验），指标条 = 实测印证（后验）**。两者分工明确，未使用时矩阵有值、指标条隐藏，属合理设计，不需要改。

### 2.3 运行指标条为什么看不到？什么时候出现？

指标条不是丢了，是**条件渲染**：`MetricsStrip` 拉取近 1 天 `GET /attachments/metrics` 聚合，**无任何数据（模型近 1 天没跑过附件/引用处理）时直接不渲染**（代码里 `if (!m) return null` 与 `if (!keys.length) return null` 两道闸）。

因此：
- 常用模型若近 1 天没处理过附件/引用 → 该行不出现（正常，不是丢失）
- 近 1 天发生过降级/失败/下载失败任一事件 → 该行出现
- 想看到它：用该模型跑一次带附件或 URL 引用的任务，之后 24 小时内打开模型页即可见

**视觉区别（随本方案落地）**：指标条加标题「运行指标（近 1 天实测）」与说明行，与上方静态矩阵明确区分——矩阵是推测（先验），指标条是实测（后验）。

## 4. 优化方案

### 4.1 (P0) 处理动作命名约定（按实际动作命名，不限于 3 种）

命名原则：不按"质量评价"命名（降级/仅档案都是评价词，用户读不懂），改按**实际处理动作**命名；动作种类按实际情况可以多于 3 种，**精准优先**；字数不限 4 字、以准确清晰为先（北京老陈定：媒体元数据注入/文件元数据注入/链接地址注入）。

后端三态枚举（native/degraded/opaque）**保留**，作为质量档位（聚合/preflight/指标用）；前端展示改用**动作名**，动作名与档位的映射是确定的：

| 动作名 | 档位 | 触发条件 | 实际处理 | 白话解释 |
|---|---|---|---|---|
| 全文注入 | native | text × 引用/附件/选区 | 读全文塞进请求体 | 原文完整给模型，无损失 |
| 原生直传 | native | image/video/audio/richdoc 且模型声明对应模态 | 原生模态 part 直传 | 图片/音视频按原生形态直接给模型 |
| 抽取注入 | degraded | richdoc 无原生通道 | 抽取正文文本注入 | 收到抽取后的文本，丢失版式/图表 |
| 媒体元数据注入 | degraded | video/audio 无原生通道 | 时长/编码等元数据注入 | 只知道参数，看不到内容 |
| 文件元数据注入 | opaque | image/binary 无原生通道 | 文件名/大小等元数据注入 | 只见文件名/大小，不见内容 |
| 链接地址注入 | opaque | url 来源 | 链接字符串注入 | 只见网址，不见内容 |

疑难裁定——**base64 图算不算降级**：base64 是把图片"转化"成文本再注入，属**转化注入**行为（degraded 档，虽无损但形态已转）；本系统原生图片走 image part（inline/url），不用 base64，若将来出现按转化注入展示。

`ModelTabRefCapability.tsx` 把隐藏 tooltip 改为常驻图例区，按档位分三组（绿=native 档：全文注入/原生直传；蓝=degraded 档：抽取注入/媒体元数据注入；灰=opaque 档：文件元数据注入/链接地址注入），每项色块+一句话白话解释。

### 4.2 (P1) tooltip 全量覆盖

补齐可解释组合，用动作名+白话解释，未覆盖组合给兜底文案（该模型对此类内容无原生理解通道）：
- text 全文注入：原文完整塞进请求体，无损失
- image 文件元数据注入：当前模型只能看到文件名/大小，看不到图片内容
- video 媒体元数据注入：只能读到时长/编码等元数据，看不到画面
- audio 媒体元数据注入：只能读到时长/编码等元数据，听不到声音
- richdoc 抽取注入：将收到抽取后的文本，丢失版式/图表
- url 链接地址注入：只收到链接字符串，未获取内容

### 4.3 (P1) 表标题 + 行列说明

表格上方加标题「**模型多态内容处理模式推测分析表**」，标题下加两行简注：
- 行（内容形态）：附件/引用物按后缀与 MIME 分出的 7 类——文本/图片/视频/音频/富文档/二进制/未知
- 列（引用通道）：内容递给模型的 3 种入口——**引用**（工作区文件路径，只记路径不复制，发送时现场读取）/ **附件**（上传复制进附件目录的文件实体）/ **外链**（URL，多数只注入链接地址，不抓取网页正文）

标题后缀「推测分析」与指标条的「实测」形成先验/后验对照，命名即说明数据来源是契约推演而非运行统计。

### 4.3.1 (P0) 表头标签统一：行头「内容形态」+ 列头「引用 / 附件 / 外链」

- 行头现文案「内容类型」改为「**内容形态**」——更贴切描述"送进来的是什么形态的东西"，避免与"类型"歧义
- 列头现文案「文件引用 / 附件 / 链接」改为「**引用 / 附件 / 外链**」——两字对齐、与输入框习惯用语一致
- 简注各带半句指针/实体差异说明（见 4.3）

### 4.4 (P2) 图标双重编码（色盲友好）

三态徽标加图标按档位：native 档 ✓ / degraded 档 ≈ / opaque 档 —（同档动作共用档位图标）。

### 4.5 (P2) 指标条标题、单位与方向

指标条上方加标题「运行指标（近 1 天实测）」，与静态矩阵形成推测/实测对照；列头加 (%)，表下加一行说明：指标越低越好；下载失败次数为近 1 天累计。

### 4.6 (P3) 空态

`map` 为空时显示"当前模型未提供能力数据"，不渲染空表格。

### 4.7 (P0) 后端判定修正（contract.py，两处错判）

审查结论：两处 `state_of` 判定与运行时实际处理不符，**错在后端判定公式**，必须修正：

**错判 1：text × 引用/附件 被判 degraded，实际是全文注入（native 档）**
- 现状：`_BASE["text"] = KindRoute(None, "content", _text_body, "reuse_text")`，native_modality=None → `state_of` 跳过 native 判定 → fallback="content" 落入 degraded
- 实际：resolver 按路径/附件记录读**全文**塞进请求体，无损，引用与附件处理完全一致（用户直觉正确）
- 根因：`state_of` 公式把"无原生模态"等同于"降级"，覆盖不到"文本本身就是模型的输入形态、无需模态通道"这一边界
- 修正：`state_of` 增规则——`fallback_quality=="content" 且 native_modality is None`（即 text 路由，file/attachment/selection/log/message）判 native 档（全文注入）

**错判 2：url × text 被判 degraded，实际是链接地址注入（opaque 档）**
- 现状：`_URL_OVERRIDE["text"]` 的 fallback_quality 标 "content"，`state_of` 判 degraded
- 实际：resolver 的 url 分支只注入 `_link_body`（链接字符串），不抓网页正文
- 根因：`_URL_OVERRIDE["text"]` 的 fallback_quality 标注与实际 extractor（_link_body）不符
- 修正：`_URL_OVERRIDE["text"]` 的 fallback_quality 改为 "link" → opaque 档（链接地址注入）

**联动影响**：`aggregate_state` 与 [23] preflight 随修正自动变准（文本引用不再误报"降级"警示）。**受影响测试**：`test_vision_parts.py:78`（`test_plan_refs_split_by_profile`）断言 text 附件 → `"degraded"`，修正后该断言应变 `"native"`——该测试断的是旧错误逻辑，随修正同步改为断 `"native"`（测试只用于发现问题，不得锁死错误逻辑）；`test_attachment_contract.py` 只断言状态合法性与映射一致性，无需改。

**落地方式**：`contract.py` **只修 state_of 两处错判，零新增函数**——动作名是纯展示词汇，唯一展示消费点在前端 CapabilityBadge，动作词表单源收口在前端（BADGE/TIP 映射），后端不下发动作投影（后端消费方 preflight 只用 aggregate_state 档位，投影无消费方；且与前端映射表重复构成双真源，重蹈 suffix_kind 整改前覆辙）。修正 1 并入 state_of 判定主线公式级修正：**degraded 的成立前提是"存在原生模态但未走原生"**——`native_modality is None` 的路由本无降级可言，直接按 fallback_quality 定档（content→native，card/metadata→degraded，link→opaque），不开特例分支。

## 6. 设计原则

- 后端三态枚举（native/degraded/opaque）保留为质量档位；`state_of` 两处错判修正属**纠错**（判定对齐运行时实际），非兼容性改动
- 动作名（全文注入/原生直传/抽取注入/媒体元数据注入/文件元数据注入/链接地址注入）是纯展示词汇，**单一真源收口在前端 CapabilityBadge**，后端不下发动作投影（后端消费方只用档位，投影无消费方且构成双真源，违反 DRY/YAGNI）
- CapabilityBadge 保持纯展示组件（不查表不推导），ModelTabRefCapability 保持只读投影，职责不变
- 文案映射集中在 BADGE/TIP 两处，不散落；底部缩写串从同一映射生成，不另建副本
- 前端仅两份小词典（content_kind→动作名、档位→图标），禁止 per-cell 查表中间层
- 仅增强可理解性/可访问性/判定准确性，不退化任何功能
