### 后端 Bug（11 条）

| # | 位置 | Bug 描述 | 严重度 |
|---|------|---------|--------|
| B-01 | `attachment_service.py:save_upload` | 初始读 `MAX_FILE_BYTES+1`(20MB+1) 对所有文件统一执行，但图片上限是 10MB。12MB 图片会被完整读入内存再被 `save_bytes` 拒绝，白白占 12MB 堆 | 低 |
| B-02 | `attachment_service.py:delete_attachment(purge=True)` | 先删磁盘文件再删 DB 行，但不级联清理 `material_pack_items` 中引用同路径的条目。purge 后素材包投喂该条目 → `quoteFile` 找不到文件 → 红底失效 | 中 |
| B-03 | `api/v1/attachments.py:get_attachment` | 端点只按 `attachment_id` 查，无 session 作用域。跨会话可获取任意附件记录（含 `stored_path` 绝对路径、`sha256` 等敏感信息） | 高 |
| B-04 | `attachment_service.py:list_attachments/get_attachment` | 不校验 session 是否存在。session 被删后，附件记录成为孤儿数据，`list_attachments` 仍返回 | 低 |
| B-05 | `db_initializer.py:attachments 建表` | `CREATE TABLE IF NOT EXISTS` 对存量库跳过，`UNIQUE(session_id,sha256)` 约束不会补到已有表。`save_bytes` 的 check-then-act 去重在并发下无 DB 级保护 | 中 |
| B-06 | `extract.py:classify` | 无扩展名 + mime=image/* + 文件内容是二进制(如未加扩展名的 PNG) → `_probe_text` 返回 False → `is not True`=True → 判 image(正确)；但无扩展名 + mime=video/* + 文件是二进制 → 判 video(正确)；无扩展名 + mime=image/* + 文件实际是视频 → 误判 image | 低 |
| B-07 | `collect.py:collect_artifact` | referenced 分支(行 80)和 copied 分支(行 85)各调一次 `target.stat()`。若文件在两次 stat 间被修改，copied 分支的 size 检查与实际 `read_bytes` 结果可能不一致 | 低 |
| B-08 | `resolver.py:_read_attachment` | `build_inject_text` 已按 256KB 阈值决定全文/档案头，返回文本可能接近 256KB。外层 `clip_text(text, limits.read_max_bytes)` 再裁一次，若 `read_max_bytes` < 256KB，文本正文会被二次截断，与 `extract.py` 的设计意图矛盾 | 中 |
| B-09 | `local_import.py:_import_roots` | 可导入根集合包含 `Path.home()`（Windows=`C:\Users\x`）。用户可导入 home 目录下任意文件（含 `.ssh`、`.env` 等敏感文件），消耗会话 200MB 配额且无审计 | 高 |
| B-10 | `api/v1/attachments.py:collect_attachment` | `CollectIn.source_path` 是自由字符串，API 层零校验。恶意输入 `../../etc/passwd` 依赖 `collect.py` 内部的 `_resolve_source` 拦截。若内部逻辑变更（如去掉越界检查），API 层无第二道防线 | 中 |
| B-11 | `material_pack_service.py:create_pack` | `MAX_PACKS` 总数检查在名称唯一性检查之前。用户已达 200 包上限且输入重名时，收到"总数已达上限"而非"已有同名素材包"——错误提示不精确 | 低 |
