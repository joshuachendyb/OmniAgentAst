## 一、概要

### 1.1 研究缘起

[63] 号设计（记忆与知识库一体化设计）第 0.4 节写下"当前服务单进程部署（`run_server.py` 编程式启动，无 workers）"，这句话在评审中被质疑：**单机单用户是不是就等于单进程？把这条当作记忆层的设计前提，靠得住吗？**

这个问题不是措辞问题。记忆层要保证"不依赖进程内状态、只从 DB 读"，知识库要在后台做 ingest 与索引重建，两者都需要先看清楚系统到底有几个进程、几类线程、什么在跨进程、什么困在内存里。如果执行模型判断错了，后面所有"只读 DB、不碰内存态"的约束就是建立在误判之上。

本文用三路证据把这件事查实：一是逐文件核对代码现状（含行号）；二是运行时实测（进程数、线程数、父进程关系、命令线）；三是核对 uvicorn 0.46.0 的启动源码，确认"无 workers"这句话在框架层面是否真的成立。结论不靠推断，每条都有可复核的出处。

### 1.2 核心结论

**结论一：服务进程唯一，"单进程"这句话成立，但只在打包态与直跑态字面成立。** `run_server.py` 用 `uvicorn.Config` + `Server.run()` 编程式启动（`run_server.py:471-487`），既没有 `workers` 参数，也没有经过 `uvicorn.run()`。核对 uvicorn 0.46.0 源码：`Server.run()` 的实现是 `asyncio_run(self.serve(...))`，同一进程内跑一个事件循环，不分叉、不拉起 supervisor；`workers` 参数只被 `uvicorn.supervisors.Multiprocess` 消费，本项目这条路径根本不经过它。全仓唯一的 `multiprocessing` 引用是 `run_server.py:77` 的 `freeze_support()`，那是 PyInstaller 打包兼容垫片，不代表使用多进程。

**结论二：开发态是两个进程。** 经 `start_dev.ps1` 启动时，`watchfiles`（或 `uvicorn --reload`）是"重载器父进程 + 服务子进程"，只有子进程对外服务。实测当前开发后端为 PID 19284（watchfiles 父）+ PID 19928（`python run_server.py` 子），父进程命令线 `.watchfiles --filter python -- "python run_server.py --host 0.0.0.0 --port 8100" F:\OmniAgentAs-01\backend\app`。

**结论三：单进程不等于单线程。** 实测开发态服务进程内 **144 条线程**、打包态 **110 条线程**。这些线程不是随手创建的，而是九个分类的常驻池加看门狗，每一类都有明确的容量上限与隔离职责（详见 2.3）。144 这个数字可以与代码常量逐项加总对上：主线程 1 + tool-sync 32 + anyio 40 + db-txn 4 + browse-probe 8 + shell-exec 32 + tool-exec 16 + bg-shell-wait 5 + watchdog 3 + spawn-gate-dump 1 + console 1 + browser 1 = 144。

**结论四：除线程外，运行期还持续派生短命子进程。** pwsh 沙箱、shell 执行、ffprobe/ffmpeg、通知弹出、模型配置探测、py-spy 转储，各走各的子进程路径。这些子进程不属于"服务进程"，但属于执行模型的一部分，且在 Windows 上与 loader lock 存在已知互锁风险（[42] 号文档的整篇事故分析即由此而来）。

**结论五：单机、单用户、单进程是三个正交维度，互不蕴含。** 单机单用户完全可以跑 `--workers 4`；多租户系统也常见单 worker。本项目选单进程不是"没做多进程"，而是在 SQLite 单写者、SSE 长连接请求亲和、进程内取消标记三处会同时退化的前提下，唯一正确的选择。

**结论六：console（conhost）是独立进程，但不是卡死根因。** `conhost.exe` 确实是独立进程（实测本机 13 个），`CreateProcessW` 会经 `GetConsoleMode` IOCTL 跨进程请求它。但实测显示有无控制台的平均耗时差异仅 10%（1.72 vs 1.89 ms），所以"有控制台就慢"是错误归因；真问题是 **CPython 在 `CreateProcessW` 期间不释放 GIL**（实测其他线程只剩 34.4% 执行机会）叠加 15ms 级长尾。当前已用 `FreeConsole` + stdio 重定向脱离控制台（实测打包态不再有 conhost 关联），但根因需 E1（进程宿主外置）才能从架构上移走。

**结论七：SQLite 是串行瓶颈，不是并发放大器。** 实测多进程写 8 进程仅 1.4 倍吞吐且失败率升到 0.8%；写进程 1→2 吞吐 85→88 次/秒（+3.5%）；多进程读 8 进程仅 1.2 倍（瓶颈是磁盘 I/O 非 CPU）。WAL 的真实优势是"读不被写阻塞"（实测 4 读 + 2 写全程 0 locked），而这个优势同一进程内多线程就已享受。**加进程换不来吞吐，只会让更多进程排队。**

**结论八：多 Agent 不需要多进程。** 三种形态中"多会话并发""单任务内协作"都是 I/O 密集（99% 时间等 LLM），协程即可支撑；只有"多 agent 并行做重计算"才需要进程池，而那属于局部需求。多进程反而会让"状态隔离"从"每 agent 一个 dict"退化为跨进程序列化。多 Agent 是并发编排问题，不是进程模型问题。

## 二、Omni 的进程与线程当前使用情况

### 2.1 进程拓扑：三层结构

把"进程"这个词拆开看，系统运行时实际存在三层：

```
第一层：服务进程（唯一，职责：HTTP、Agent 主循环、DB、调度）
  ├─ 打包态：OmniAgentBackend.exe（1 个）
  └─ 开发态：重载器父进程 + python run_server.py 子进程（2 个，只有子进程服务）

第二层：工具子进程（短命，按需派生，职责：隔离不可控的原生调用）
  ├─ pwsh 沙箱进程（sandbox/backend.py:66，被 Job Object 收编）
  ├─ shell 前台/后台命令进程（execute_shell_command / shell_background）
  ├─ ffprobe / ffmpeg（attachments/extract.py）
  ├─ 通知弹出（send_notification.py:76）
  ├─ 模型配置探测（config_service.py:405）
  └─ py-spy dump（loop_watchdog.py，看门狗触发时）

第三层：进程内并发（不是进程，但同属执行模型）
  ├─ 协程：所有 HTTP 请求、Agent 主链、后台周期任务
  └─ 线程：九个分类的常驻池（见 2.3）
```

三层各司其职，边界清晰：第一层是"不可复制的业务状态持有者"，第二层是"可抛弃的隔离沙袋"，第三层是"并发执行单位"。

### 2.2 为什么是单进程：三重独立证据

**证据一：启动代码。**

```python
# run_server.py:471-476
config = uvicorn.Config(
    _app_main.app, host=args.host, port=args.port,
    log_level=None, log_config=None,
    forwarded_allow_ips=args.forwarded_allow_ips)   # 无 workers
server = uvicorn.Server(config)
_app_main.app.state.uvicorn_server = server          # 挂到 app.state，供 /api/v1/shutdown 优雅停机

# run_server.py:487
server.run()
```

这里调的是 `Server.run()`，不是模块级 `uvicorn.run(...)`。这不是风格差异：`uvicorn.run()` 内部会判断 `config.workers > 1` 并转交 `Multiprocess` supervisor 拉起子 worker；`Server.run()` 是纯本地执行。选择编程式启动的原始动机写在 `run_server.py:468-469`——裸 `uvicorn.run` 无法从应用内拿到 Server 对象，关闭按钮就发不出优雅停机信号。**为了拿到 Server 句柄而绕开 supervisor，顺带把多 worker 的能力一并关掉了。**

**证据二：框架源码。**

实测 uvicorn 版本 0.46.0，`Server.run` 实现：

```python
def run(self, sockets: list[socket.socket] | None = None) -> None:
    return asyncio_run(self.serve(sockets=sockets), loop_factory=self.config.get_loop_factory())
```

一行，`asyncio_run` 在当前进程内跑一个事件循环。而 `Config.__init__` 里：

```python
workers: int | None = None,
self.workers = workers or 1
if workers is None and "WEB_CONCURRENCY" in os.environ:
    self.workers = int(os.environ["WEB_CONCURRENCY"])
```

注意后半段：`workers` 缺省时会读环境变量 `WEB_CONCURRENCY`。已实测本机该变量未设置，但即便设置了也不会生效——`Server.run()` 全程不读 `config.workers`，这个字段在多 worker 分叉路径之外是惰性的。**所以"无 workers 参数"是弱证据，"调用的是 Server.run 而非 uvicorn.run"才是强证据。**

**证据三：全仓符号与运行时实测。**

- `multiprocessing` / `ProcessPoolExecutor` / `multiprocessing.Process`：全仓（排除 backup、`_internal`、第三方依赖）仅 `run_server.py:77` 的 `freeze_support` 一处，用途是 PyInstaller 打包时的子进程重新执行保护，不是业务多进程。
- 运行时父子关系实测：打包态 PID 12668 无子进程（除本次查询命令自身）；开发态 PID 19284 → PID 19928 单链。
- 单实例保护：`run_server.py:254-275` 用命名 Mutex `OmniAgentBackend_SingleInstance` 抢锁，抢不到就当作"已有实例"去开浏览器后退出。注释写明了动机——双击两次时两实例都能通过端口预检，随后并发初始化同一 SQLite 库撞写锁，日志实证 `database is locked`。**这个 Mutex 本身就是"本系统设计为单实例单进程"的官方确认。**

### 2.3 进程内线程：九个分类的常驻池

线程不是散的，全部是"构造期建满、运行期只入队"的常驻模型。逐类清单：

| 分类 | 位置 | 容量 | 建满时机 | 承载什么 |
|---|---|---|---|---|
| 主线程 + 事件循环 | uvicorn `Server.run` | 1 | 启动 | 全部协程调度 |
| 默认 loop 线程池 `tool-sync` | `main.py:537-547` | `min(32, cpu+4)` | startup 预热强制建满 | `asyncio.to_thread` 的同步工具 |
| anyio 同步端点池 | `main.py:559-585` | 40 | startup 预热，`MAX_IDLE_TIME=86400` | `def` 端点（file_routes 等） |
| DB 事务池 `db-txn` | `database.py:98` | 4 | import 时 | `atxn` 异步事务壳 offload |
| 文件浏览探测池 | `browse_service.py:284` | 8 | import 时 | 目录探测 |
| shell 执行池 `shell-exec` | `tool_retry_engine.py:197` | 32 | import 时（WorkerPool 构造期） | shell 工具执行 |
| 非 shell 同步工具池 `tool-exec` | `tool_retry_engine.py:206` | 16 | import 时 | 有界执行的同步工具 |
| 后台 shell 等待池 `bg-shell-wait` | `shell_background.py:77` | 5（`tuning.concurrency.shell_max_background`） | import 时 | 后台命令 `proc.wait` 阻塞等待 |
| 看门狗 dump 池 | `loop_watchdog.py:54`、`spawn_gate.py:51` | 3 + 1 | import 时 | py-spy 抓栈落盘 |
| 控制台写线程 | `console_writer.py:160` | 1 | 首次写 | 非阻塞 stdout |
| 浏览器就绪线程 | `run_server.py:480-485` | 1（仅打包态） | 启动后 | 轮询 `/health` 后开浏览器 |

**为什么不用 `ThreadPoolExecutor` 而自建 `WorkerPool`**：`workers.py:36-42` 的注释给了根本原因——`ThreadPoolExecutor` 是懒建线程，`submit()` 在需要新建 worker 时会在**调用线程**里执行 `Thread.start()`，而调用方常常就是事件循环线程；Windows 上 `Thread.start()` 内部的 `self._started.wait()` 无超时，新线程 bootstrap 要拿 loader lock，而 `CreateProcessW` 调用期持 loader lock 且不释放 GIL，两者并发即永久互锁。于是 `WorkerPool` 的做法是构造期一次性建满 N 个 daemon 线程，运行期 `submit` 只做 `queue.put`。`workers.py:39-41` 把"运行期零 Thread.start"写成了不可协商的前提。

同理，`main.py:537-547` 与 `550-556` 的两个预热函数不是优化，是把懒建风险从运行期挪到启动期：故意提交 N 个阻塞任务逼 worker 逐个建满，再放行。

**为什么后台等待要单独一个池**：`shell_background.py:13-16` 记录了一次复核结论——后台命令默认无超时，如果沿用 `run_in_executor(None)` 共享 `tool-sync`，一个卡死的后台命令会永久霸占工具线程池；后台并发配到 32 时足以把整个工具线程池耗尽，使文件、网络、DB 工具全部饿死，形成系统级卡死。所以后台等待单独建池，容量与信号量 `_BG_SEM` 同源，一个在跑的后台恰好占一个线程，一对一不排队。

### 2.4 协程与后台任务

协程承载真正的高并发：HTTP 请求、Agent 主循环、SSE 推送、周期任务。后台任务统一由 `spawn_bg`（`utils/background_tasks.py:27`）创建并保留强引用，避免被 GC 收回。当前常驻的周期任务：

| 任务 | 入口 | 周期 |
|---|---|---|
| 会话/库清理 | `main.py:467-471` `_periodic_cleanup_loop` | 周期 |
| monitoring 库保留清理 | `main.py:502-517` | 3600s |
| Journal 保留清理 | `main.py:443` `_journal_retention_ref` | 周期 |
| 日志级别热重载 | `main.py:520-531` | 10s |

事件推送走 `services/task/event_bus.py`：`EventBus` 用 `asyncio.Queue` 做订阅者队列、`deque` 做环形重放缓冲，`publish` 明确要求"同步、无 await、O(订阅者数)，允许在 asyncio.Lock 内调用"。这是纯进程内结构——**一旦多进程，订阅者集合直接分裂**，这是多进程化最硬的一道墙（见 4.4）。

定时器走 `tools/timer/timer_set.py`：`_timers` 存 `asyncio.TimerHandle`、`_timer_callbacks` 存回调元数据，`loop.call_later` 注册，`_timer_lock` 是 `asyncio.Lock`；`rebuild_timers_from_db`（`:154`）在启动时从 `timers` 表重建，并做"已在内存调度则跳过"的去重，防同一 timer 挂两个句柄导致双触发。**这是"内存调度 + DB 唯一真源"的典型形态**：DB 抗重启，内存抗延迟。

### 2.5 子进程：七类创建点

| 用途 | 位置 | 隔离手段 |
|---|---|---|
| pwsh 沙箱执行 | `safety/sandbox/backend.py:66` | Job Object 收编 + `isolation_kwargs()`（不继承父控制台）+ 临时脚本即用即删 + stdout/stderr 尾部 4096 字符截断 |
| shell 前台执行 | `tools/fundamental/execute_shell_command.py:1243-1386` | `proc_io.isolation_kwargs()` + 零线程读管道 |
| 后台 shell | `tools/fundamental/shell_background.py` | 输出落文件 + 大小上限强杀 + 三态判定 |
| 音视频元数据/转码 | `attachments/extract.py:394`、`video_transcode.py:170` | `CREATE_NO_WINDOW` 防闪黑 + 超时 |
| 通知弹出 | `send_notification.py:76` | `DEVNULL` 丢弃输出 |
| 配置探测 | `config_service.py:405` | `DEVNULL` |
| py-spy 转储 | `loop_watchdog.py:178` | 有界执行（`subprocess.run` 的 timeout 管不到 `CreateProcess` 阶段，故自建有界） |

共同模式是：**原生不可控的东西一律扔到子进程，主进程只做协议编排。** 读取路径也统一——`proc_io.drain_until_exit` / `drain_after_exit` 用零线程轮询读管道，避免 `subprocess.communicate()` 每次起 2~3 条 `_readerthread` 与 `CreateProcessW` 抢 loader lock（`proc_io.py:9-17`、`extract.py:16-17` 的编辑历史明确记录了这一替换）。

### 2.6 跨进程的边界：什么困在内存里

单进程的代价集中体现在这张表上。以下状态全部是**模块级变量**，跨进程即失效：

| 状态 | 位置 | 失效后果 |
|---|---|---|
| `running_tasks` / `agent_streams` | 任务管理 | 停止/暂停信号打到别的进程即丢失 |
| SSE subscriber 集合 + 环形缓冲 | `event_bus.py:46-47` | 推送分裂，前端漏事件 |
| `_timers` / `_timer_callbacks` | `timer_set.py:49-51` | 每个进程各挂一份，重复触发 |
| `_injected_history_msgs` 等注入态 | `initialize_run_state.py:83-89` | 请求漂移到另一进程即丢上下文 |
| `_BG_REGISTRY`（后台进程注册表） | `shell_background.py` | 孤儿进程无人回收 |
| 各线程池与闸门租约 | `workers.py`、`spawn_gate.py` | 每个进程一套，容量翻倍 |
| DB 连接与 WAL 写锁 | `database.py` | 多进程放大写竞争 |

### 2.7 实测数据

| 项 | 打包态 | 开发态（服务子进程） |
|---|---|---|
| 进程数 | 1 | 2（重载器父 + 服务子） |
| 线程数 | 110 | 144 |
| 句柄数 | 723 | 597 |
| 工作集 | 161 MB | 92 MB |

线程数与 2.3 的容量加总严格吻合（144 = 各项之和），说明线程构成完全可解释、无泄漏迹象。打包态 110 低于开发态，差异来自 anyio 池与工具池的实际预热进度、以及当时活跃任务数的不同，不涉及结构差异。

内存占用并未随线程数线性增长：144 条线程仅 92 MB，因为绝大多数线程处于 `queue.get()` 阻塞态，只占栈预留不占物理页。

### 2.8 控制台（conhost）专题：一个独立进程引发的解释器冻结

这一节回答一个反复出现过的问题：**"输出到 console 这个东西是不是一个进程？它和 shell 之间是不是有交叉问题？"** 答案是：理解方向对了一半，需要精确化。

#### 2.8.1 conhost.exe 确实是独立进程

自 Windows 7 起，微软把控制台宿主从 `csrss.exe` 剥离出来，成为独立进程 **`conhost.exe`**。**每一个控制台会话对应一个 conhost 进程**。本机实测当前有 13 个 conhost 进程，分别挂在不同的父进程下：

```
ProcessId  ParentProcessId
     7384             2228
     8716             8412
    13420            12652
     ...
```

所以"输出到 console 是一个进程"这句话**实体上是成立的**：任何持有控制台的进程，其 `sys.stdout` 写入、`GetConsoleMode` 查询、窗口尺寸获取，都要跨进程与 conhost 通信（通过 LPC/ALPC）。

#### 2.8.2 卡死机理：不是"输出慢"，是 IOCTL 阻塞 + GIL 不释放

真正致命的是这条链，四步：

```
① Python 线程调用 subprocess.Popen()
        ↓
② CPython 的 _winapi.CreateProcess 调 CreateProcessW
        ↓
③ 子进程要继承父控制台时，CreateProcessW 内部会走 GetConsoleMode 类 IOCTL
        ↓
④ 该 IOCTL 跨进程请求 conhost 处理；conhost 若繁忙/卡住，IOCTL 不返回
        ↓
   ★ 而 CPython 在整个 CreateProcessW 期间不释放 GIL
        ↓
   ★ 全部 Python 线程冻结：事件循环、看门狗、心跳一并停摆
        ↓
   只能杀进程
```

关键点有两处，必须分开看：

- **conhost 是一条 IPC 路径**：它把"创建子进程"这个本地动作，变成了可能跨进程等待的远程调用；
- **CPython 不释放 GIL**：这是放大器。即使 conhost 只阻塞 100ms，那也是 100ms 内**整个解释器**什么都不做，而不是只有一个线程等。CPython 的 `_winapi.CreateProcess` 在调用 `CreateProcessW` 前后没有 `Py_BEGIN_ALLOW_THREADS` / `Py_END_ALLOW_THREADS` 包夹，这是上游行为，不是本项目能改的。

社区侧有对应记录可查：`python/cpython#75627`（`_winapi.CreateProcess` not thread-safe）、`python/cpython#87575`（Windows 上 `subprocess.Popen` 两次即可让 `Thread.join()` 可中断并死锁）。

#### 2.8.3 实测：控制台不是"必然变慢"，而是"多了一条可能无限阻塞的路径"

这一点必须实测澄清，否则容易过度归因。本机对照实验（同一脚本，`CREATE_NEW_CONSOLE` 拉起带真实控制台的子进程后测量）：

| 环境 | min | p50 | p90 | max | mean |
|---|---|---|---|---|---|
| 无控制台 | 1.23 ms | 1.52 ms | 1.96 ms | **15.38 ms** | 1.72 ms |
| 有控制台 | 1.18 ms | 1.65 ms | 2.42 ms | **14.73 ms** | 1.89 ms |

结论：**在理想路径下（cmd 在本地盘、无杀软 hook），有无控制台的平均耗时差异仅约 10%**。所以"有控制台就一定慢"是错误归因。

但另外两个数字才是真问题：

**其一，长尾始终存在**：无论有无控制台，`max` 都在 15ms 量级。这 15ms 内 GIL 是被占住的。

**其二，GIL 占用是实打实的**。另一次实测：一条线程疯狂起子进程，另一条线程做纯 CPU 计数，对比基线：

```
[基线] 无子进程: CPU 计数 22,958,704/秒
[实验] 起子进程: CPU 计数  7,907,922/秒
[结论] 起子进程时 CPU 计数速率 = 基线的 34.4%
```

即：**Popen 密集期，其他 Python 线程只能拿到约三分之一的执行机会**。这就解释了为什么"一次工具调用能把全站拖住"——不是 conhost 一定慢，而是**每多一个可能长尾的阻塞点，就多一次全解释器停顿的机会**。反之，一旦 conhost 因控制台缓冲区满、用户选中文本（见下）、conhost 自身卡住等原因不响应，这个 15ms 就会变成秒级甚至无限。

#### 2.8.4 顺带澄清："开了控制台只能看不能复制粘贴"

这是 Windows 控制台的另一个独立老问题，与 GIL 无关：**快速编辑模式（QuickEdit Mode）**。控制台窗口在 QuickEdit 开启时，用户只要在窗口里按下鼠标选中文本，控制台就进入"选择模式"，**输出会被暂停**（程序写 stdout 会阻塞在缓冲区满），直到用户按 Esc 或回车退出选择。表现出来就是"窗口开着、能看、但程序像卡住了、也复制不了（或复制完才恢复）"。

这与 2.8.2 的 conhost IOCTL 阻塞是两个不同层面：前者是"用户交互导致 stdout 写阻塞"，后者是"创建子进程导致 CreateProcessW 阻塞"。两者都通过 conhost 这条路径放大，但触发条件不同。

#### 2.8.5 当前状态：已脱离控制台，但根因未消除

核对代码与实测：

| 项 | 现状 |
|---|---|
| 打包配置 | `OmniAgentBackend.spec:179` 仍是 `console=True`（保留控制台子系统） |
| 启动行为 | `run_server.py:441-442` 在通过全部前置检查后调 `detach_console_if_needed()` |
| 具体动作 | `console_mode.py:49-64`：`FreeConsole()` 摘掉关联 → `sys.stdout/stderr` 重定向到 `logs/boot_*.log` → `sys.stdin` 指向 NUL |
| 排障开关 | `OMNI_KEEP_CONSOLE=1` 可保留控制台 |
| 实测验证 | 打包态 PID 12668 在 13 个 conhost 的父进程列表中**不存在**，确认已无控制台关联 |
| 用户可见表现 | 启动瞬间闪过一个窗口，之后无窗口、无信息显示，日志落 `logs/boot_*.log` |

**这个方案的正确性**：`FreeConsole` 之后父进程不再持有控制台，子进程无从继承，`GetConsoleMode` 那条 IOCTL 分支不再被触发。这是从"前提"上消除，比"每次都加 CREATE_NO_WINDOW"更彻底——因为 [42] 已实测证明 `CREATE_NO_WINDOW` **仍会分配一个隐藏控制台**，不能消除前提。

**遗留的两点**：

1. `console=True` 意味着 exe 仍带控制台子系统，启动瞬间仍会创建再脱离控制台（[42] 的 P1 是把打包改成 `console=False`，彻底不创建）；当前 FreeConsole 方案是等价效果的功能兜底，不是最彻底形态。
2. 更根本地，"CreateProcessW 会被 conhost 阻塞"这条**路径本身还在**——只要还有子进程创建。FreeConsole 只是保证了"本进程没有控制台可继承"，没有改变"CPython 在 CreateProcessW 期间不释放 GIL"这个上游事实。这正是 4.3 节 E1（进程宿主外置）要解决的问题：把 `CreateProcessW` 整体搬出主解释器。

#### 2.8.6 对"console 需求已经不重要"的确认

用户判断"系统已跑得差不多正常，console 需求不重要了"，与代码现状一致，并且**方向正确**：

- 早期的 console 用途是"肉眼看 LLM 来往信息是否正常"，属于调试期需求；
- 现在观测手段已转移到 `logs/` 文件（`boot_*.log`）、`/health`、监控库、事件总线，console 不再是信息出口；
- 因此"打包态启动瞬间开一下、之后完全无显示"是合理终态，进一步可以按 [42] P1 改为 `console=False`，连那一瞬的窗口都省掉。

需要强调的是：**console 只是"卡死"的一个疑点，不是根因本身**。根因是"主解释器直接调 CreateProcessW"。所以"关掉 console"降低了触发概率，但只有 E1（进程宿主外置）才是把这条路径从架构上移走。

### 2.9 SQLite 读写限制实测：它确实是全局瓶颈，但瓶颈的性质被误解了

用户提出的另一个关键点："一个大的影响所有进程的点是 SQLite 的读写限制"。这个判断**方向正确，但性质需要精确化**——SQLite 的限制不是"不能用多进程"，而是"多进程换不来吞吐"。以下为 2026-11-26 本机实测（SQLite 3.50.4，WAL 模式，`busy_timeout=500ms`，与应用配置一致）。

#### 2.9.1 多进程并发写：成功率下降，吞吐不升反降

每进程 200 次独立 `INSERT` + `commit`，逐进程独立连接：

| 进程数 | 总写入 | 成功 | 失败（locked/busy） | 墙钟 | 单次均耗时 | 吞吐 |
|---|---|---|---|---|---|---|
| 1 | 200 | 200 | 0（0%） | 1.32 s | 6.60 ms | 151 次/秒 |
| 2 | 400 | 400 | 0（0%） | 3.66 s | 9.15 ms | 109 次/秒 |
| 4 | 800 | 799 | 1（0.1%） | 5.67 s | 7.09 ms | 141 次/秒 |
| 8 | 1600 | 1588 | 12（0.8%） | 7.59 s | 4.74 ms | 211 次/秒 |

三个反直觉的结论：

1. **2 进程吞吐比 1 进程还低**（109 vs 151 次/秒）——进程启动开销 + 锁排队让总吞吐下降。加进程不是加法，先有一段减法。
2. **8 进程也只有 1.4 倍**（211 vs 151），远低于 8 倍。因为写入本质串行，多出来的进程在排队。
3. **失败率随进程数单调上升**：8 进程时 0.8% 的写会撞 `database is locked`，必须靠应用层退避重试兜底——**失败重试是额外成本，不是零成本**。

#### 2.9.2 多进程并发读：提升同样有限

8 进程各 300 次索引查询（表 5 万行，`WHERE k=?` 走索引）：

| 进程数 | 总查询 | 墙钟 | 吞吐 |
|---|---|---|---|
| 1 | 300 | 0.22 s | 1364 次/秒 |
| 2 | 600 | 0.61 s | 984 次/秒 |
| 4 | 1200 | 1.11 s | 1081 次/秒 |
| 8 | 2400 | 1.47 s | 1633 次/秒 |

8 进程相对 1 进程只提升约 20%。原因：**瓶颈是磁盘 I/O 与锁管理，不是 CPU**。SQLite 的 `sqlite3` 模块本身在 C 层已释放 GIL，所以"多进程"能带来的那点并行度，被 I/O 串行和页缓存命中吃掉了。**这也意味着：想靠多进程提速 SQLite 读，方向本身就是错的**——该提速的是索引设计和查询范围收敛，这正是 [63] 第 2.4 节"范围收敛 + 有界候选 + 双索引"要解决的问题。

#### 2.9.3 读写混合：写吞吐几乎不随写进程数变化

4 个读进程 + N 个写进程，持续 3 秒：

| 配置 | 读成功 | 读 locked | 写成功 | 写吞吐 |
|---|---|---|---|---|
| 4 读 + 1 写 | 1200 | 0 | 254 | 85 次/秒 |
| 4 读 + 2 写 | 1200 | 0 | 264 | 88 次/秒 |

**写进程从 1 加到 2，写吞吐只从 85 涨到 88（+3.5%），基本等于零收益**。同时注意：读进程全程 0 locked——**WAL 的真正优势是"读写不互斥"，这一点实测成立**。也就是说，WAL 让"读不被写挡住"，但**不会让"写变快"**。这个区分非常关键：

| 期望 | WAL 是否满足 |
|---|---|
| 读不被写阻塞 | ✅ 实测成立（4 读 + 1/2 写，读全程 0 locked） |
| 写能并发加速 | ❌ 实测不成立（+3.5%，等于没有） |
| 加进程提升总吞吐 | ❌ 实测不成立（1 进程 151，8 进程 211，1.4 倍） |

#### 2.9.4 对架构决策的含义

把 2.9 的结论收拢成三条，直接支撑第四章的取舍：

1. **SQLite 的写是全局单点，无法用"加进程"绕过。** 想让写变快，只有两条路：减少写次数（批量提交、合并事务）或换存储引擎（PostgreSQL 等）。加 worker 只是把排队搬到更多进程里。
2. **因此"对称多 worker"对 SQLite 应用是纯负收益**：吞吐不升、失败率上升、还要处理进程内状态分裂。这是第四章否决 `--workers N` 的**实测依据**，不再是推断。
3. **"读可并行"这个 WAL 优势是真的，但它应该用在同一进程内的并发读上**（多个协程/线程同时读），而不是靠开多进程去实现。当前 `db-txn` 4 线程池 + `busy_timeout=500ms` 的配置对"读不被写挡"已经足够。

## 三、当前进程/线程技术架构的优缺点

### 3.1 架构定型：四层执行模型

把 2.1~2.5 收拢，本系统的执行模型是一句话：**单进程宿主 + 事件循环承载高并发 + 常驻线程池承接阻塞 + 子进程隔离原生不可控**。

```
┌─ 单进程宿主（唯一，持有全部业务状态） ────────────────────────┐
│                                                              │
│  ┌─ asyncio 事件循环（1 线程） ─────────────────────────┐    │
│  │  HTTP 请求 │ Agent 主链 │ SSE 推送 │ 周期任务 │ 定时器 │    │
│  └───────────────┬──────────────────────────────────────┘    │
│                  │ await / to_thread / submit                │
│  ┌───────────────▼──────────────────────────────────────┐    │
│  │ 常驻线程池（9 类，共约 140 线程，构造期建满）           │    │
│  │ tool-sync│anyio│db-txn│browse│shell-exec│tool-exec│bg  │    │
│  └───────────────┬──────────────────────────────────────┘    │
│                  │ Popen（经 isolation_kwargs + spawn_gate）  │
└──────────────────┼───────────────────────────────────────────┘
                   ▼
      ┌─ 工具子进程（短命，可抛弃，Job Object 收编） ─┐
      │  pwsh │ ffmpeg │ 通知 │ py-spy │ 配置探测     │
      └──────────────────────────────────────────────┘
```

这个形状的一个关键特征：**越往下的层越可抛弃，越往上的层越不可复制**。事件循环持有全部业务状态，所以不能多份；子进程不持有任何业务状态，所以可以随便杀。这个分层决定了后面所有取舍。

### 3.2 优点

**优点一：状态零同步成本。** 单进程意味着 `running_tasks`、SSE 订阅表、取消标记、注入态全是普通内存对象，不需要序列化、不需要分布式锁、不需要一致性协议。Agent 任务的状态机（暂停、恢复、取消、HITL 等待）实现起来是直接改 dict，不是发消息。这是单进程最大的收益，也是它最难被替代的原因。

**优点二：SSE 长连接天然亲和。** 前端订阅会话事件建立一条 SSE 长连接，之后所有 `publish` 都在这条连接所在的事件循环里同步分发（`event_bus.publish` 明确要求同步无 await）。多进程下同一条会话的多次轮询可能命中不同进程，必须引入 sticky session 或外置消息总线——直接违反"单机、不引外部服务"的硬约束。

**优点三：Windows loader lock 风险已被系统性收口。** 这不是天生的优点，是花了大量补丁换来的：`spawn_gate` 把 `CreateProcessW` 与 `Thread.start` 变成互斥的可回收租约（`HOLD_LIMIT=8s`，超时强制回收并落盘全栈）；`WorkerPool` 保证运行期零 `Thread.start`；`proc_io` 用零线程轮询读管道替掉 `communicate` 的 `_readerthread`；`isolation_kwargs` 让子进程不继承父控制台。四道防线全部建立在"只有一个进程"的前提上——如果多进程，每个进程各有一套 `spawn_gate`，跨进程的资源争抢它管不到。

**优点四：故障域被切成两层且各有兜底。** 原生调用崩溃只带走子进程（Job Object 收编，父进程只收到非零返回码）；主进程若卡死，`loop_watchdog` 抓栈落盘但不杀进程，[42] 的方案进一步把 shell 执行准备外置到宿主进程。这种"主进程尽量不碰原生调用"的纪律是正确的方向。

**优点五：资源账目可核算。** 每个池的容量都是常量或配置项（`shell-exec=32`、`tool-exec=16`、`bg=5`、`db-txn=4`…），实测线程数与常量加总严格相等。这意味着容量规划是可算的，不是"跑起来看"。

### 3.3 缺点

**缺点一：单进程 = 单点。** 事件循环一卡，全站卡。历史事故不是理论推演：[40] 号文档记录的 grep 假死烧死事件循环、[42] 号文档记录的 `CreateProcessW` 持 loader lock 导致永久互锁，都是"一个工具调用拖垮整个服务"。现有的缓解手段（专用池隔离、有界执行、闸门超时回收）本质是**把爆炸半径关在池子里**，而不是消除单点。

**缺点二：CPU 并行能力为零。** Python 有 GIL，进程内多线程无法并行做纯 CPU 计算。当前的绕法是用子进程（ffmpeg/ffprobe/py-spy 都是原生可执行文件，天然释放 GIL）。**一旦出现"纯 Python CPU 密集"需求（典型就是本地 ONNX 向量化、大批量文档切块与哈希、巩固作业的全量重算），现有模型立刻不够用**——这是 4.1 的第一个真判据。

**缺点三：线程数偏高，调度与句柄开销真实存在。** 144 条线程、597 个句柄。线程本身便宜（阻塞态不占物理页），但每条线程有约 1MB 栈预留、参与 GIL 争抢、在 `threading.active_count()` 类操作上有成本；更实际的是**排障成本**：一次卡死要在一百多条线程里定位，故才有 `loop_watchdog` + py-spy 的组合。

**缺点四：池容量是硬编码常量，缺乏自适应。** `shell-exec=32`、`tool-exec=16` 都是写死的（`tool_retry_engine.py:196,205`），只有 `bg` 走了配置（`tuning.concurrency.shell_max_background`）。单用户场景问题不大，但"32 个 shell 并发"对普通笔记本是过量，对小任务又是浪费，且没有任何基于实际负载的伸缩。

**缺点五：进程内状态零持久化，重启即全丢。** 后台进程注册表 `_BG_REGISTRY` 是内存 dict，重启后上一世的后台任务句柄全丢——所以 `main.py:609-614` 被迫在启动期做一次"清理孤儿产物"的补丁。定时器有 DB 兜底（`rebuild_timers_from_db`），但后台 shell 没有等价机制。这是"能靠持久化解决却还没解决"的一处欠账。

**缺点六：开发态双进程，调试语义与实际运行不一致。** `watchfiles` 父子结构下，改代码触发热重载只重启子进程；父进程持有的任何状态（虽然当前很少）在调试时不会同步。更隐蔽的是 [42] 记录的"磁盘代码已更新但进程跑旧模块对象"——这在热重载下不会出现，但在打包态手工替换文件时会静默生效，排查代价很高。

### 3.4 关键取舍复盘

这几条不是随意为之，每一条背后都有事故或硬约束，复盘清楚才不会在演进时踩回去。

**取舍一：编程式启动而非 `uvicorn.run`。**
为的是拿到 `Server` 句柄做优雅停机（`run_server.py:468-469`）。代价是放弃了 supervisor 能力。这个取舍正确与否取决于是否需要多 worker——单用户不需要，所以正确。**但它把"多 worker"从配置问题变成了代码改造问题**，将来若真要加 worker，需要先换回 `uvicorn.run` 或在外部包一层 supervisor，这一点必须提前知道。

**取舍二：自建 `WorkerPool` 而非 `ThreadPoolExecutor`。**
理由是 Windows 懒建线程的 loader lock 死锁（`workers.py:39-41`），这是用事故换来的结论，不可回退。代价是失去了 `ThreadPoolExecutor` 的取消传播、异常聚合等现成能力，于是自建了 `WorkerSlots`/`SlotLease` 做槽位记账，并在 2026-11-15 修过一次"槽位容量永久泄漏"（迟到归还空操作导致 available 逐步侵蚀到 0）。**自建并发的代价是持续维护，这一点必须承认。**

**取舍三：`chat` 库 DELETE → WAL 回滚。**
`database.py:339-343` 的注释完整记录了因果：曾因误诊 Errno22 把 chat 库改 DELETE，2026-07-17 E2E 验证暴露 DELETE 模式在 185 万行/2.7GB 时每次写 journal + fsync 造成写 I/O 拥塞、`create_session` 同步写超 10s，于是回滚到 WAL 三库统一。**这条现在成了多进程化的主要障碍**（见 4.4）。

**取舍四：`busy_timeout=500ms` + 指数退避，而非长等待。**
`database.py:429-433` 明确写了"busy_timeout=30000 时已空等 30s，再加 retry 总等待 >31.5s，比不修更差（KISS-DIRECT 违规）"。改成 500ms 快速失败 + 应用层 0.5/1/2s 退避。这个口径对单进程是对的；**多进程下写竞争频率上升，500ms 快速失败的失败率会显著提高**，退避会变成常态路径。

**取舍五：`atxn` 把同步 DB I/O 整体 offload 出事件循环。**
`database.py:25` 记录：新增 `atxn`/`_run_txn` 异步事务壳，把同步 sqlite3 I/O 与锁重试 `time.sleep` 整体 offload 到 `db-txn` 池（4 线程）。这是"事件循环绝不碰阻塞 I/O"的纪律，也是记忆层设计"检索放子线程不阻塞事件循环"的既有样板。

## 四、拓展场景与进程/线程演化方向

### 4.1 判据：什么时候必须引入新的执行单元

先把判据立稳，避免凭感觉扩容。**只有满足以下任一条，才值得新增执行单元；不满足的一律优化现有层。**

| 判据 | 什么情况算满足 | 当前是否有 |
|---|---|---|
| ① CPU 密集要真并行（GIL 绕不开） | 纯 Python 计算占满单核且时长可观 | 部分：巩固作业全量重算、知识库批量切块与哈希、本地 ONNX 向量化 |
| ② 崩溃域需要硬隔离 | 第三方原生库可能段错误，且不能带走主进程 | 部分：pwsh/ffmpeg 已隔离；进程内 ONNX/字体渲染/MCP stdio 尚未 |
| ③ 吞吐扩展 | 多用户或高 QPS 要压满多核 | 否：单用户，同一时刻 1 条 Agent 主链 |
| ④ 内存泄漏需周期回收 | 长跑进程内存单调增长，重启可接受 | 否：单机重启成本≈双击一次 |
| ⑤ 长任务需独立生命周期 | 后台作业要脱离 Web 进程存活 | 否：已用 DB 持久化 timers + 进程内 asyncio 解决 |

结论：**① 与 ② 已经部分成立，但都指向"功能隔离型多进程"，不是"吞吐扩展型多进程"。** 这个区分是本章的核心，混淆两者会导致方向性错误。

### 4.2 两类多进程，只走一类

| 维度 | 吞吐扩展型（uvicorn `--workers N`） | 功能隔离型（独立职能进程） |
|---|---|---|
| 目的 | 压满多核、提高 QPS | 隔离崩溃域、承接 CPU 密集 |
| 进程间对称性 | 对称，每个都能接任意请求 | 不对称，各司其职 |
| 业务状态 | 需外置（Redis/总线） | 主进程独占，子进程无状态 |
| 对 SQLite 影响 | 写竞争放大 N 倍 | 子进程只读或批量写单一路径 |
| 对 SSE 影响 | 需 sticky session | 无影响（推送仍在主进程） |
| 本项目结论 | **不采用** | **按需采用** |

**为什么"吞吐扩展型"明确不采用**（四条硬约束，缺一条都足以否决）：

1. **SQLite 单写者。** WAL 允许多进程并发读，但写入全局串行，且运行期 `busy_timeout=500ms` 快速失败 + 指数退避。现有的实证是：仅仅两个进程并发初始化就撞 `database is locked`，被迫加命名 Mutex 单实例。`--workers 4` 等于把这个问题放大四倍，同时把"快速失败"变成常态。
2. **进程内状态是命门。** 2.6 表里七类状态全是模块级变量。多 worker 后：SSE 订阅表分裂、取消标记丢跨进程、定时器每个 worker 各注册一份导致重复触发、`_BG_REGISTRY` 各管各的孤儿。修这些必须外置消息总线与分布式注册表，直接违反"单机、不引外部服务"。
3. **请求亲和性。** Agent 任务是长生命周期状态机，一次任务的多次 HTTP 轮询必须命中同一进程。多 worker 要 sticky session，而 sticky session 在客户端重连、负载不均时会退化。
4. **治理机制是进程内的。** `spawn_gate` 的租约、`WorkerPool` 的常驻线程、启动期预热——全部是单进程内补丁。多进程后每个进程各一套，跨进程的资源争抢与 loader lock 风险它管不到，等于把已经收口的 Windows 顽疾重新放开。

**唯一会让人想上多 worker 的动机是 CPU 并行，而这个动机应该用"功能隔离型"满足，不该用对称 worker 满足。** 这是本章最重要的判断。

### 4.3 演化路线：分阶段，每阶段可独立回滚

以下路线按"判据是否触发"排序，不按时间排序。每一级都只在上一级跑稳且有真实需求时才启动。

**E0（当前形态，保持）：单进程 + 常驻池 + 子进程隔离。**
无需改动。当前形态已能承载单用户长任务，且所有已知卡死路径都有兜底。**不做任何"预防性多进程改造"**——YAGNI，且改造会破坏优点一、二、三。

**E1：通用进程宿主外置（[42] P3，详细方案见 [65]）。**
目标：主解释器零 `CreateProcessW`。做法是起一个**通用进程宿主**（独立进程，接口只有 `argv/cwd/env/timeout`，不含任何业务语义），主进程只发消息、不再碰 `Popen`；宿主内每命令一连接 + 独立 Job Object 杀树。收益有两层：**①卡死只冻宿主、主服务 5s 内自愈；②一次建设覆盖全仓 28 处子进程创建点**（shell 6 处、tools/system 8 处、注册表 3 处、环境探测 2 处、语法校验 1 处、媒体 2 处、其它 6 处），不必逐处重复实现。
现状核查：`backend/app/utils/` 下无 `proc_host.py`，即 **E1 尚未落地**；但落地方案已于同日完成（[65] v1.1，含五组 PoC 实测与代码骨架），可直接按清单实施。其中 4.2.5 已实测同一宿主跑通 pwsh/node/py-spy/cmd 四种异构程序（8 并发 0.27s），通用性成立。
触发条件：本项不需等触发——它是当前唯一能根治卡死的措施，[65] 已把改动成本压到"只切 PS 分支、跑稳再切"。
落地顺序：阶段一只切 `shell_type in ("ps7","ps5")` 分支，跑稳再切 cmd/bash，最后按需接入其它 22 处。

**E2：CPU 密集作业进程池（新，判据①）。**
形态：`ProcessPoolExecutor` 或自建 worker 子进程，**单向任务分发 + 结果回传，不共享任何业务状态**。
适用作业：记忆巩固的全量重算（去重/冲突消解/衰减）、知识库批量切块与 `content_hash` 计算、文档解析与格式转换、本地 ONNX 推理。
关键约束：
- 输入只传不可变数据（路径、id 列表），不传 ORM 对象或连接；
- 子进程不写库，结果回主进程由 `db.atxn` 单一路径写（保持 SQLite 单写者）；
- 必须可取消（父进程超时后杀整个池）；
- Windows 下进程池启动成本高（每个子进程重新 import），适合**批量作业**不适合**逐条请求**；
- `freeze_support()` 已在 `run_server.py:366` 调用，打包态进程池的前提已满足。
这一级与 E1 的区别：E1 是"隔离不可控的原生调用"，E2 是"并行可控的纯计算"。两者解决不同问题，不合并。

**E3：深度作业独立后台进程（判据⑤的真需求出现时）。**
形态：常驻后台工序进程，只做"读 DB → 计算 → 写 DB"，自带重启与心跳；主进程通过 DB 表（任务队列）与它协作，不共享内存。
适用：超大知识库全量重建索引、跨库大规模一致性检查、长时间巩固作业。
判定：当 E2 的批量作业时长已经影响主进程感知（如单次超过 5 秒并频繁发生）时才启动，且**必须先有 E2 的代码基础**。

**E4：多机 / 多租户（明确排除）。**
不设计、不预留。若将来真要做多用户或跨机器，需要重做的不是"加 worker"，而是：数据层换 PostgreSQL/外置存储、事件推送换 Redis/消息队列、状态与调度全部外置、文件系统换对象存储。那是一次产品形态变更，不是执行模型演进，不应在当前设计中为该场景预留任何抽象（YAGNI）。

### 4.4 若非要走吞吐扩展型，前置条件清单

写出来是为了让"否决"可被复核，也让将来若决策改变时知道代价。以下条件必须全部满足，缺一不可：

1. **SQLite 换成多写者友好的存储**，或把写操作集中到单一写服务。当前 WAL + 500ms 快速失败在多写者下会退化为高失败率。
2. **SSE 与取消标记外置**：需要跨进程可寻址的事件总线和共享的取消/暂停状态（Redis 或独立的推送进程 + 主进程订阅）。
3. **定时器改为单点调度**：`timer_set` 的内存句柄 + DB 真源模型在多 worker 下需要"只有一个进程负责调度、其余只读"的角色分离，或换成外部调度。
4. **`_BG_REGISTRY` 等注册表外置**，否则各 worker 独立回收孤儿，跨 worker 的后台进程无人管。
5. **`spawn_gate` 跨进程化**（或接受每个 worker 各自一套带来的风险放大）。
6. **请求亲和**：会话到 worker 的粘性路由，以及 worker 重启后的会话迁移策略。

**这六条加起来，已经不是"改个启动参数"，而是重做执行模型。** 在当前单机单用户的硬约束下，这六条全部违反或代价过高，所以结论是明确的否决，不是"暂时没做"。

### 4.5 值得做的轻量优化（不需要动进程模型）

在不动 E0 结构的前提下，有几处性价比明显更高的改进，属于"优化现有层"而非"新增执行单元"：

| 改进 | 现状 | 收益 |
|---|---|---|
| 池容量配置化 | `shell-exec=32`/`tool-exec=16` 写死 | 适配不同机器，避免小机过量、大机不足 |
| 后台进程注册表持久化 | `_BG_REGISTRY` 纯内存，重启后靠清理孤儿兜底 | 消除重启后孤儿窗口，与 `timers` 表同思路 |
| 线程命名规范化审计 | 已有 `thread_name_prefix`，但未统一清单 | 卡死时一眼定位归属池 |
| `/health` 暴露线程池水位 | 已有 spawn_gate 指标 | 提前发现池饱和，而非事后排查 |
| 看门狗分级告警 | 现有 `HOLD_LIMIT=8s` 强制回收 | 卡死前兆（3s/5s）就先落盘，留更完整现场 |

这些改动的共同特点：**不动执行模型、不动 SQLite 语义、不引外部服务**，与优点一、二、三完全兼容。

### 4.6 与记忆/知识库设计的衔接

[63] 号设计第 0.4 节把"单进程部署"写成了记忆层的设计前提，本文可以给出更准确的三条约束（建议以此替换 [63] 0.4 的表述）：

1. **不得依赖进程内状态**：记忆层与知识库层的任何结论型数据只从 DB 读，不缓存跨任务的可变状态。理由是多层进程结构下（重载器父进程、工具子进程、将来 E1/E2/E3 的职能进程），进程内状态都可失效。
2. **写操作保持单写者思维**：记忆巩固、知识库 ingest 即使将来跑在 E2 进程池里，也只做计算并把结果回传主进程，由主进程经 `db.atxn` 单一路径落库。这一条同时保证 SQLite 单写者不被打破。
3. **检索与注入放子线程**：沿用 `db.atxn` 的既有纪律，检索不阻塞事件循环；这一条与执行模型无关，但正因为不依赖执行模型，才在多进程演进中始终成立。

一句话概括衔接关系：**记忆与知识库的设计不应该假设"只有一个进程"来省事，而应该假设"任何进程内状态都随时可能消失"，这样无论执行模型怎么演进，设计都不用改。**

### 4.7 多 Agent 与执行模型：多 Agent 本身不需要多进程

用户提出"后续会支持多 Agent，但没想好支持什么类型"。这个问题必须先回答，因为它直接决定要不要为多 Agent 做多进程准备。结论：**多 Agent 不需要多进程，需要的是并发模型设计**。理由要把"多 Agent"拆成三种可能形态分别看。

#### 4.7.1 三种多 Agent 形态与执行单元需求

| 形态 | 典型场景 | 主要开销 | 需要什么执行单元 |
|---|---|---|---|
| **A. 多会话并发** | 用户同时开几个对话，各有独立 agent | 等 LLM 返回（I/O） | **协程**足够。100 个并发也只有 1% 时间在烧 CPU |
| **B. 单任务内多 agent 协作** | planner → executor → reviewer 串行或并行的流水线 | 等 LLM + 等工具（I/O） | **协程** + 现有线程池 |
| **C. 多 agent 并行做重计算** | 同时分析 10 个大型代码库、批量向量化 | 纯 CPU | **进程池**（即 4.3 的 E2），且这是局部需求 |

**核心判断**：多 Agent 的成本结构是 **"N 个 agent × 每步等 LLM 若干秒"**，99% 时间在等 I/O，不在烧 CPU。这与 2.1 的判据①（纯 CPU 计算占满单核）完全不重合。所以 A、B 两种形态在现有单进程 + 协程模型下**天然支持**，不需要任何改动。

本机实测支撑这一点：14 核 CPU，当前单进程 110~144 线程已经能承载多会话；而一次 LLM 调用通常 3~30 秒，期间协程让出，其他会话的 agent 照常推进。**并发上限由 LLM 的 rate limit 和 token 预算决定，不由进程数决定。**

#### 4.7.2 多 Agent 的真实挑战在执行模型之外

如果为多 Agent 上多进程，会去解决错误的问题。多 Agent 真正的四个挑战是：

| 挑战 | 需要什么 | 与进程模型的关系 |
|---|---|---|
| **状态隔离** | 每个 agent 独立的 `conversation_history`、注入态、工具上下文 | 现有机制已支持（每任务运行清零 `_injected_history_msgs`）。**多进程反而更难**：隔离变成"跨进程隔离"，要从内存对象变成序列化 |
| **并发控制** | LLM 调用的并发上限（信号量）、工具执行的有界池 | 现有 `WorkerSlots`/`_SHELL_SLOTS` 已是有界并发；再加一层 agent 级信号量即可，纯进程内机制 |
| **成本控制** | 每个 agent 的 token 预算、总预算 | 与进程无关，是记账逻辑 |
| **结果汇总** | 多个 agent 输出如何合并、冲突如何裁决 | 与进程无关，是编排逻辑 |

**注意第一行的反直觉之处**：多进程会让"状态隔离"这件事**变难而不是变简单**。单进程里"每个 agent 一个 dict"是最简单的隔离；多进程后每个 agent 的状态要么留在主进程（子进程只是执行器，无状态），要么得序列化传输。

#### 4.7.3 唯一的例外：什么时候多 Agent 需要进程隔离

只有一种情况需要：**agent 会执行不可信或会崩溃的代码**。具体两类：

1. **agent 要跑用户/模型生成的代码**（如数据分析、脚本执行）→ 需要沙箱进程。但这是**工具隔离**，不是 agent 隔离——现有 `sandbox/backend.py` 的 Job Object 沙箱已经在做，与"多 agent"无关。
2. **agent 依赖会段错误的原生库**（某些推理框架、某些解析库）→ 需要进程隔离。这时该做的同样是"把那个原生调用搬进子进程"（E1/E2 的思路），而不是把整个 agent 搬进子进程。

反过来看：Python 里 agent 的"崩溃"绝大多数是异常（`ValueError`、`TimeoutError`、API 报错），`try/except` 就够，不需要进程级隔离。真正需要进程级隔离的是**原生层崩溃**（段错误、死锁），而那恰恰不是 agent 逻辑的问题。

#### 4.7.4 建议的多 Agent 落地方向

不预设具体产品形态，但给出与执行模型无关的架构约束，这样无论将来选哪种多 Agent 形态都不用重构：

1. **每个 agent = 一个协程 + 一份独立状态**，挂在现有事件循环上，共享线程池与 DB 连接池。
2. **agent 级并发用信号量控制**，不用进程数控制。这样调并发是改配置，不是改架构。
3. **重计算下沉到工具层**：agent 自己不做重活，把活交给工具，工具再走 E2 进程池。这样"agent 数量增加"与"CPU 负载"解耦。
4. **agent 之间不共享内存态**，通过 DB + 事件总线通信（`event_bus.py` 已有）。这条约束现在就是对的，将来若要进程化也无需改。

一句话：**多 Agent 是"并发编排"问题，不是"进程模型"问题。用多进程去做多 Agent，是用错工具。**

### 4.8 多进程升级决策：基于实测的明确结论

用户提出"现在想升级架构支持多进程"。这一节把前面的分析收敛成一个可执行的决策，所有判断都有本章实测数据支撑。

> **编号说明**：本节用 `P0/P1/P2` 表示**执行优先级**（先做什么）；4.3 用 `E0/E1/E2` 表示**演进级别**（形态层级）。二者对应关系：P0=E0（保持现状）、P1=E1（进程宿主外置）、P2=E2（CPU 作业池）。另需注意，[42] 文档自身有独立的 P0~P4 编号（其 P3 即本文 E1，其 P1 是"打包改 console=False"），引用时会标明来源。

#### 4.8.1 先说 SQLite 这个"全局瓶颈"的真实性质

这是最容易被误解的一点，2.9 的实测已经给出答案，这里再压缩成一句：

> **SQLite 限制的不是"能不能多进程"，而是"多进程换不来吞吐"。**
>
> - 多进程**读**：8 进程只有 1.2 倍（1364 → 1633 次/秒），瓶颈是磁盘 I/O 不是 CPU；
> - 多进程**写**：写进程从 1 加到 2，写吞吐 85 → 88 次/秒（+3.5%），等于没有；
> - 多进程**总量**：8 进程写只有 1.4 倍（151 → 211 次/秒），且失败率从 0% 升到 0.8%。
>
> 而 WAL 真正给的是**"读不被写阻塞"**（实测 4 读 + 2 写，读全程 0 locked），这个优势在同一进程内多线程/多协程就已享受，不需要多进程。

所以"SQLite 是全局瓶颈"这个判断要改成更准确的说法：**SQLite 的写是全局单点，但它是"串行瓶颈"而不是"并发放大器"——加进程不会让它变快，只会让更多人排队。**

#### 4.8.2 该做的三件事（按优先级）

| 优先级 | 做什么 | 解决什么 | 依据 |
|---|---|---|---|
| **P0** | **保持单服务进程**，不加 `--workers` | 避免吞吐不升、失败率上升、状态分裂 | 4.2 四条硬约束 + 2.9 实测 |
| **P1** | **进程宿主外置**（[42] P3 → 本节 E1） | 把 `CreateProcessW` 整体搬出主解释器，消除 2.8.2 的冻结路径 | 2.8 实测：GIL 占用 34.4%，长尾 15ms |
| **P2** | **建 CPU 密集作业池**（E2），只在真有 CPU 密集活时启用 | 知识库 ingest、记忆巩固全量重算、本地向量化 | 2.1 判据①，且 `jieba`/`numpy`/`onnxruntime` 已装 |

**P1 是当前最该做的**：它不是"多进程"，但它是**唯一能从根本上解决卡死**的措施。做法是让一个专门的宿主进程去调 `CreateProcessW`，主进程只通过命名管道发命令——这样即使宿主里的 `CreateProcessW` 被 conhost 卡住，冻结的也只是宿主，主服务 5 秒内自愈（[42] 4.2 的验收标准）。这比"关 console"彻底得多，也是 [42] 早已设计好的方案，只是尚未落地。

**P2 要等触发器，不提前做**：现在没有任何指标显示 CPU 是瓶颈（14 核，负载远未饱和）。按 YAGNI，等知识库 ingest / 记忆巩固的真实数据量出来、实测单次超过 5 秒了，再启用进程池。提前建就是养一个没活干的进程池，白占内存、白增复杂度。

#### 4.8.3 明确不做的事

| 不做 | 为什么 |
|---|---|
| `uvicorn --workers N` 对称多 worker | 2.9 实测证明吞吐不升反降；且 SSE/定时器/取消标记/`_BG_REGISTRY` 四处会分裂 |
| 换掉 SQLite 上 PostgreSQL | 单机单用户，为"多写并发"引入运维对象不划算。真到写瓶颈，先试"批量提交 + 合并事务" |
| 三层架构拆成微服务 | 违反"单机、不引外部服务"硬约束，收益为零 |
| 为多 Agent 提前做多进程 | 4.7：多 Agent 是并发编排问题，协程即可支撑 |

#### 4.8.4 判断"该不该升级"的一句话标准

> **只有当"单次纯 Python 计算超过 5 秒且频繁发生"（P2 触发器）或"shell 类卡死再次复发"（P1 触发器）这两个信号出现时，才动执行模型；其余任何"感觉系统该升级了"的理由，都不构成升级依据。**

因为执行模型的每一次改动，代价都在"状态零同步"这个核心优势上打折扣。现在这个优势是 Omni 最值钱的资产，不能拿它换一个只提升 1.4 倍的吞吐。

## 五、总结

1. **"单进程"成立且可证**：代码调用 `Server.run()` 而非 `uvicorn.run()`、uvicorn 源码确认不读 `workers`、全仓无 `ProcessPoolExecutor`、命名 Mutex 单实例保护、运行时父子关系实测，五重证据一致。

2. **"单进程"不等于"单线程"**：九个分类的常驻线程池共约 140 条线程，容量写死在代码常量里，实测与常量加总严格吻合；另有七类短命子进程。

3. **单机 / 单用户 / 单进程是三个正交维度**：当前选择是在 SQLite 单写者、SSE 亲和、进程内状态三处约束下的正确解，不是能力缺失。

4. **console 是独立进程，但不是卡死根因**：`conhost.exe` 确实是独立进程（实测本机 13 个），`CreateProcessW` 会经 `GetConsoleMode` IOCTL 跨进程请求它；实测有无控制台平均耗时差异仅 10%（1.72 vs 1.89ms），所以"有控制台就慢"是错误归因。真问题是 **CPython 在 `CreateProcessW` 期间不释放 GIL**（实测其他线程只剩 34.4% 执行机会）加 15ms 级长尾。当前已用 `FreeConsole` + stdio 重定向脱离控制台（实测打包态无 conhost 关联），但这只降低触发概率，根因需 E1（进程宿主外置）才能移走。

5. **SQLite 是串行瓶颈，不是并发放大器**：实测多进程写 8 进程仅 1.4 倍吞吐且失败率升到 0.8%；写进程 1→2 吞吐 85→88 次/秒（+3.5%，等于零）；多进程读 8 进程仅 1.2 倍（瓶颈是磁盘 I/O 非 CPU）。WAL 的真实优势是"读不被写阻塞"（实测 4 读 + 2 写全程 0 locked），而这个优势同一进程内多线程就能享受。**加进程换不来吞吐，只会让更多进程排队。**

6. **多 Agent 不需要多进程**：三种形态中"多会话并发""单任务内协作"都是 I/O 密集（99% 时间等 LLM），协程即可支撑；只有"多 agent 并行做重计算"才需要进程池，而那属于局部需求。多进程反而会让"状态隔离"从"每 agent 一个 dict"退化为跨进程序列化。多 Agent 是**并发编排问题**，不是进程模型问题。

7. **优势来自"状态零同步 + 隔离在子进程"**；代价是单点、零 CPU 并行、线程数偏高、池容量写死。

8. **演进只走"功能隔离型多进程"**：P0 保持单服务进程 → P1 进程宿主外置（[42] P3，已设计未落地，是当前最该做的）→ P2 CPU 密集作业池（等触发器）。对称 worker 扩展明确否决，且列出了六条否决依据与将来反悔的前置条件。

9. **对记忆/知识库设计的交付**：把前提从"单进程"改为"进程内状态不可信、DB 是唯一真相、写操作单一路径"，这样设计对执行模型的演进免疫（已同步到 [63] 0.4）。

## 六、概念扫盲：本篇涉及的基础概念

本章为阅读前几章时容易卡住的术语提供白话解释，不追求学术严密，只求"看完能对上号"。已经熟悉这些概念的读者可直接跳过。

### 6.1 GIL 是什么

**GIL（全局解释器锁）= Python 规定"同一时刻只有一个线程能执行 Python 字节码"。**

比喻：一个厨房有 4 个厨子（4 条线程），但只有一把菜刀（GIL）。4 个人轮着用刀，谁拿到谁切，其余 3 个干看着。所以 Python 多线程**不会**让"切菜"这件事快 4 倍。

本机实测：Python 3.13.11 标准构建，`Py_GIL_DISABLED = False`，**有 GIL**。CPU 14 逻辑核。

> 注：Python 3.13 有实验性的 free-threaded 构建（3.13t，PEP 703）可去掉 GIL，但需要 numpy / onnxruntime 等全部依赖都有对应构建，且仍属实验状态。在本项目可预见期内不适用，所以"要用多核就得开进程"这个结论不会变。

### 6.2 CPU 密集 vs I/O 密集：GIL 只影响前者

这是理解全篇的关键区分：

| 类型 | 例子 | GIL 有没有影响 |
|---|---|---|
| **I/O 密集**（等外部） | 等 LLM 接口返回、读磁盘、等子进程、等网络 | **完全没影响**。刀交出去时人不在切菜是在等快递，其他人照样能用刀 |
| **CPU 密集**（烧脑子） | 10 万条记忆两两算相似度、1 万段文本切块+哈希、本地 ONNX 文本转向量 | **致命**。每个人从头到尾都在切菜，刀永远被占，4 线程≈1 线程 |

**Omni 现在约 99% 的活儿是 I/O 密集**（等模型、等工具、等文件），所以单进程 + 多线程是正确选择，线程没有白开。这一点必须先说清楚，避免误以为现有模型是"错的"。

回答用户的问题"CPU 密集是不是本地任务计算量大的任务"：**是的，就是本地自己算、不需要等外部的重活**。判断标准很简单——**把网络和磁盘全拔了，这个活还能不能跑完？** 能跑完且耗时长的，就是 CPU 密集。知识库的万篇文档切块、哈希、分词正是这种活，所以它确实会用到进程池（E2）。

### 6.3 CPU 密集作业进程池是什么

要真并行切菜，唯一办法是**每人配一把刀**——开多个操作系统进程，每个进程有独立解释器、独立 GIL、独立的"刀"：

```
单进程多线程（1 把刀）           多进程（4 把刀）
┌──────────────┐              ┌────┐ ┌────┐ ┌────┐ ┌────┐
│ 线程1 线程2... │              │进程1│ │进程2│ │进程3│ │进程4│
│  共用 GIL     │              │GIL1 │ │GIL2 │ │GIL3 │ │GIL4 │
└──────────────┘              └────┘ └────┘ └────┘ └────┘
 4 线程 ≈ 1 线程速度            4 进程 ≈ 3.8 倍速度
```

**代价（四条，必须提前知道）**：

1. **每个子进程要重新 import 一遍 app** —— 本机启动初始化约 1.7 秒（`run_server.py:43-48` 注释有记录），4 个进程就是 4 份开销；
2. **内存翻倍**：每进程约 50~100 MB；
3. **数据必须能 pickle 序列化**，不能直接传数据库连接、ORM 对象；
4. **Windows 是 spawn 模式**（不像 Linux 能 fork），启动更慢，且必须有 `if __name__ == "__main__"` 保护（本项目 `run_server.py:366` 已调 `freeze_support()`）。

**适用/不适用**：适合**批量作业**（一次处理 1 万个文档），不适合**逐条请求**（每条请求都开进程池，光是启动开销就吃掉收益）。

### 6.4 进程 / 线程 / 协程 对照

| 概念 | 白话 | 隔离性 | 上下文切换成本 | 本项目用法 |
|---|---|---|---|---|
| **进程** | 一个独立的程序实例，有自己的内存和 GIL | 完全隔离 | 最高（要换页表） | 1 个服务进程 + 若干工具子进程 |
| **线程** | 进程内的执行小分队，共享内存和 GIL | 共享内存，不隔离 | 中 | 约 140 条，分 9 个常驻池 |
| **协程** | 比线程更轻，等的时候主动让位，必须在同一线程跑 | 共享一切 | 极低（用户态切换） | 所有 HTTP、Agent 主链、定时器 |

一句话选择原则：**等 I/O 用协程，阻塞调用用线程，纯 CPU 计算用进程。**

### 6.5 WorkerPool 与 ThreadPoolExecutor 的区别

本项目没有用 `ThreadPoolExecutor`，而是自建了 `WorkerPool`（`app/utils/workers.py`）。这不是"没用对现有工具"，而是为了规避一个 Windows 特有的死锁。

**`ThreadPoolExecutor` 的致命特性**：懒建线程。`submit()` 一个任务时若没有空闲线程，它会在**调用 `submit()` 的那个线程里**当场执行 `Thread.start()`：

```
事件循环线程 submit() → 需要新线程 → Thread.start()
                                        ↓
                              Windows 上等 loader lock
                                        ↓
    而另一线程正在 CreateProcessW（持 loader lock，不释放 GIL）
                                        ↓
                                ★ 永久互锁，全站僵死
```

**`WorkerPool` 的做法**：构造期一次性建满 N 个 daemon 线程，运行期 `submit` 只做 `queue.put`，**零 `Thread.start()`**（`workers.py:39-41` 明确写了这个前提）。`main.py:537-547` 的 `tool-sync` 池也是同一思路的另一种实现——用"启动期提交阻塞任务逼建满"的预热绕过懒建。

**所以结论是：现在这样是对的，不要换回 `ThreadPoolExecutor`。** 若换回去，等于把 2026-11-04 那次事件循环僵死事故重新打开。真正的代价是自建需要维护取消传播、异常聚合、槽位记账（`WorkerSlots`/`SlotLease`），这是可接受的维护成本，比死锁便宜。

唯一值得改的是：把 `shell-exec=32`、`tool-exec=16` 这些写死的常量挪到配置（像 `bg-shell-wait` 那样读 `tuning.concurrency.*`），让不同机器能调。

### 6.6 uvicorn 与"编程式启动"

**uvicorn = 一个 Python 的 ASGI Web 服务器**，即跑 FastAPI 应用的"发动机"。分层关系：

```
前端浏览器
    ↓ HTTP
┌──────────────────────────────────┐
│ uvicorn  ← 监听端口、解析 HTTP、管连接 │  "发动机"
├──────────────────────────────────┤
│ FastAPI / Starlette                │  "车身"：路由、参数校验
├──────────────────────────────────┤
│ 业务代码 app.main:app               │  "货物"：Agent、工具、DB
└──────────────────────────────────┘
```

**ASGI** 是 Python 异步 Web 的标准接口（Asynchronous Server Gateway Interface）。FastAPI 写出来的 `app` 对象只负责"收到请求 → 返回响应"，**不会自己监听端口**，必须有服务器来跑它。

同一个 app 有三种跑法：

| 方式 | 写法 | 特点 |
|---|---|---|
| ① 命令行 | `uvicorn app.main:app --port 8100` | 最常见，uvicorn CLI 帮建 Config/Server |
| ② 便捷函数 | `uvicorn.run(app, host=..., port=...)` | 一行搞定，**但拿不到 Server 对象** |
| ③ **编程式启动** | 自己建 `Config` + `Server` + `run()` | **本项目用这个** |

**为什么本项目要用方式③**：Omni 有"关闭服务"按钮，需要优雅停机（收尾任务、关数据库、清后台进程），而优雅停机的开关是 `server.should_exit = True`——**必须拿到那个 Server 对象才能设置**。裸 `uvicorn.run()` 拿不到，所以只能自己建（`run_server.py:468-469` 注释写明了这个动机）。

**副作用**：走 `Server.run()` 就绕开了 `uvicorn.run()` 里的 supervisor 分支，**顺带把"多 worker"能力关掉了**。这是用"放弃多 worker"换"优雅停机"的交易，对单用户场景划算。

**Python 不只能用 uvicorn**。本机实测可用性：

| 服务器 | 本机 | 类型 | 结论 |
|---|---|---|---|
| **uvicorn** | 已装 | ASGI | **当前选择，最合适** |
| gunicorn | 未装 | WSGI/prefork | **Windows 不支持**（依赖 fork），排除 |
| hypercorn | 未装 | ASGI | 可行，但改启动代码无收益 |
| daphne | 未装 | ASGI | 可行，社区活跃度低于 uvicorn |
| granian | 未装 | ASGI (Rust) | 性能最高，但引入 Rust 二进制，打包变复杂 |
| waitress | 未装 | **WSGI** | **不支持 async**，跑不了 FastAPI 异步端点，排除 |

对"Windows + 单机 + 单进程 + 需要 Server 句柄"这四个条件，**uvicorn 编程式启动就是最优解，没有换的必要**。

### 6.7 概念速查表

| 概念 | 一句话 | 本项目结论 |
|---|---|---|
