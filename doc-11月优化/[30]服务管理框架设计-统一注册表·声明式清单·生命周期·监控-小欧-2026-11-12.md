## 一、背景与问题

### 1.1 现状

本系统目前有两个常驻服务，均游离在系统之外，靠手工双击 .bat/.ps1 启停：

| 服务 | 目录 | 启停方式 | 现状问题 |
|------|------|---------|---------|
| opencli 网关（opencode2api） | `opencli_gateway/` | start.bat / stop.bat | 位置固定、名称写死，前端无任何展示；是否在跑全靠记忆 |
| OmniVPN（mihomo 代理） | `OmniVPN/` | proxy-on/off/switch bat、rebuild-pool、update-pool-quick 等 | 启停动作多、语义复杂（换桶/巡检/重建/出口体检），无统一入口 |

问题本质：**服务的"存在性、生命周期、健康状态"三样东西，系统不知道、页面看不到、框架管不了**。后续还要接入 MCP server、插件等更多服务形态，若继续"一个服务一套手工办法"，每接一个就要重写一遍页面与逻辑。

**讨论定案的三个判断**（本文档的立论基础）：

1. **只做"进程 / 脚本遥控器"没有价值**——端口在不在跑，任务管理器就能看；框架的净增量只能是**无人值守的自愈**与**出事时的异常出口**（9.7 / 1.3）；
2. **两个服务是支撑服务（sidecar）**，不参与对话链路，出问题表现为"别的功能莫名其妙失败"，所以界面按"平时不看、看时一眼定位"设计，不做仪表盘（4.3.6 / 第十四章）；
3. **难点不在启停，在 Windows 单机桌面的"所有权与在场"**：backend 退出不能连杀服务（9.4）、用户正在对话时不能随便重启（9.7 presence）、休眠唤醒后要自检——这三件事通用框架都不做。

### 1.2 目标

设计一套**服务管理框架**，实现用户三问：

1. 新服务按某种规矩添加后，服务页面**自动识别**出来；
2. 页面上可**启动、停止**；
3. 启动后可**监控**查看服务状态（是否健康、端口、日志、自定义动作）。

并回答一个方向性问题：插件、MCP 等到底能不能和系统服务**统一管理**，还是必须分散管理。

再加一条底线：**支撑服务的可用性由框架保证，不靠人盯**——挂了框架自己纠偏（期望态 + 自愈，见 9.7），人工按下 [停止] 才算数。

### 1.3 定位：支撑服务的托管，不是产品功能页

**场景前提**：单机 Windows 桌面；使用者是**普通用户（非运维）**，不会去服务目录里翻东西，也不该被迫理解进程与端口；服务**不总是需要**——需要时起来撑住，不需要时可以停掉；出故障时他能做的只有三件事：**看看、关掉、重启**。

这两个服务是**支撑服务**：不参与对话链路本身，出问题时表现为"别的功能莫名其妙失败"，平时无人查看。据此定三条：

1. **价值 = 无人值守**：可用性由框架保证（期望态 + 自愈），不是靠人记得打开页面点按钮；
2. **界面 = 异常出口**：平时没人打开，出事才打开；所以瓦片区只给死活二值 + 端口 + 运行时长，细节全在 Tab（4.3）；
3. **边界收窄**：不做仪表盘、不做"能力目录 / 业务联动"，不与对话功能耦合（第十四章）。

**度量四个数**（做不到就说明本框架只是 bat 遥控器）：人工干预次数 / 故障恢复时长（MTTR）/ 新服务接入耗时 / 故障归因覆盖率（有事件可查的比例）。

### 1.4 命名与范围：微型运维（micro-ops）

给这套东西一个准确的名字：**支撑服务的微型运维**——不是数据中心运维，而是一台桌面机上"几个支撑服务"的最小运维闭环：**发现 → 启停 → 健康 → 纠偏 → 动作 → 留痕**。

| 维度 | 定案 | 对设计的影响 |
|------|------|-------------|
| **规模** | **常用 ≤20 个**（可安装/配置的可以很多，日常在跑的不多） | 瓦片区 + 顶部 Tab 足够（4.3.6）；全量扫描 + 5s 健康循环在 20 个量级无压力；**不引入分页与搜索**，分组与左侧 Tab 的触发条件见 4.3.6 规模表 |
| **来源** | **当前以自研为主**；架构稳定后开放给第三方提供 | 清单与契约按"外部人照单也能接"来写（第六、七章），不假设作者懂本项目代码 |
| **做法** | 自研服务多由上游开源改造而来 → **规范先行**：输入 / 控制 / 输出三面标准（7.7），少量修改换无缝；不改的只有语言与目录结构 | 第七章契约就是"改造清单"；第十三章两个样板是范例；**不为迁就存量脚本改框架** |

一句话：先把**自研支撑服务**的微型运维底座做扎实，再谈对外开放；开放时新增服务只写清单，不改框架（第十六章）。

## 二、需求定案（三思三省）

### 2.1 一省：要管的到底是什么

两个现有服务形态差异极大：

- opencli 网关：一个 exe，启动后监听端口，是标准**本地进程型服务**；
- OmniVPN：mihomo 进程 + 一堆运维动作（换桶、巡检、重建池、出口体检），是**进程 + 动作组**的复合体；
- 未来 MCP：可能是本框架拉起的 stdio 子进程，也可能是独立的 Streamable HTTP 端点；
- 未来插件：可能根本没有进程，只是"启用/禁用"的开关。

结论：**"管理"不是一件事，是四件事**——注册（发现）、生命周期（启停）、健康（监控）、动作（运维）。四件事的"框架层"必须统一，四件事的"实现层"因服务形态而异。这就是设计的分界线。

### 2.2 二省：集中还是分散

| 方案 | 描述 | 判定 |
|------|------|------|
| 全分散 | 每种服务自写一套管理代码和 UI | ❌ 重复造轮子，接一个服务重写一遍，违背 DRY |
| 全集中 | 框架假定所有服务都是"进程"，统一 Popen/kill | ❌ 对 MCP HTTP 型、插件型是暴力硬套，语义错位 |
| **集中监控、分散实现** | 框架统一管注册表、状态机、监控、UI；每种形态一个"执行器（executor）"，按 kind 分派 | ✅ 定案 |

定案理由：监督进程的 Popen/树杀/端口探测对"进程型"成立，对"MCP stdio（生命周期由 MCP 客户端会话决定）""插件（无进程，只有启用态）"不成立。所以**框架不能写死任何一种生命周期实现，只能统一生命周期语义**。执行器按 kind 注册进框架，框架对执行器只要求实现 `start / stop / snapshot / probe` 四个方法的语义契约（接口隔离，ISP；签名见 9.6.4）。

### 2.3 三省：新服务"自动识别"的规矩到底是什么

自动识别不能靠猜，必须靠**声明**。业界成熟答案高度一致：

- supervisord 的 `[include] files = /etc/supervisor/conf.d/*.conf`：新程序 = 往 conf.d 放一个文件，主配置零改动；
- systemd 的 `*.service` 单元目录：同构思想；
- Docker Compose 的 services 映射表：声明式定义 + healthcheck 声明。

定案：**drop-in 清单目录**。新服务 = 在应用根的 `ext_service/` 下新建一个服务子目录（内含 `service.json` 清单），框架启动扫描 + 目录变更热扫描，页面自动多一张服务瓦片与该服务的 Tab。零代码、零配置文件改动。这就是用户要的"按某种规矩添加后自动识别"的规矩。清单**锚定应用根**：发布态 = 运行 exe 所在目录，开发态 = 仓库根，两态布局同构。

### 2.4 底线约束（本仓现实）

- 后端自身已 assign 进 KILL_ON_JOB_CLOSE Job Object（打包版），**它直接 Popen 的子进程会继承同一 Job——backend 退出会连带杀光所有服务**。这是本框架最大的安全坑，设计中必须显式处理（见 9.4）。
- Windows only：树杀用现成 `proc_utils.py`（psutil BFS），不用 taskkill。
- 配置新增键走三同步（config.yaml.example + settings_registry.py + 运行 config.yaml）；本框架的服务清单**不进 config.yaml**，独立走 `ext_service/` 目录（清单是"服务注册"，不是"系统设置"，语义不同源，避免把配置文件变成半吊子注册表）。
- **规模与来源按 1.4**：常用 ≤20 个（可安装的可以很多，日常在跑的不多），先自研、后开放。因此**不为"服务很多"提前埋点**——不做分页、搜索、批量操作、多级分组（>30 才评估，4.3.6），也不做第三方市场的元数据字段（YAGNI）。

### 2.5 三层服务模型（本框架只负责第一层）

| 层 | 是什么 | 谁调度 | 本框架 |
|----|--------|--------|--------|
| **L1 支撑服务** | 独立进程，为 Agent 运行提供环境（网络出口、模型接入网关），**不参与对话内容** | 本框架（用户 / 任务前置 / 自愈） | ✅ 唯一负责对象（本文档全部内容） |
| **L2 集成服务** | 与 Agent 一体：工具、skill、MCP server、插件，**生命周期跟随会话/任务，由 Agent 或 LLM 调度** | Agent runtime | ❌ 不托管，只保留"状态只读上报"这一个接触点（P2 再议） |
| **L3 远端服务** | 云 API / 外部端点，本机无进程 | 外部 | ❌ 仅作只读监控（`http-endpoint` kind，P1） |

划这条线的目的：**防止本框架长成"什么都管"的调度中心**。L2 的启停语义是"按会话拉起、按任务释放"，与 L1 的"常驻 / 按需进程"是两套模型，硬塞进来必错。

### 2.6 服务不总是需要：三种激活模式 + 两种在场场景

**激活模式（清单 `activation`）**

| 模式 | 语义 | 谁触发 |
|------|------|--------|
| `on_demand`（缺省） | 平时不跑，需要时才起 | 用户点 [启动] / 任务前置 `ensure` / 自愈 |
| `follow_backend` | 跟随后端启动（常驻语义，不做空闲回收） | 后端启动扫描 |
| `manual` | 只认人手，永不自动（含后端启动与自愈） | 用户 |

`ensure` 是"按需"的唯一正确接口：**幂等**——在跑就立即返回，没跑就启动，正在启动就等它到终态。Agent / 任务调度器在开始前调 `ensure`，比 `start` 更贴合语义（不关心是谁启动的）。

**人工意图跨重启保持**：`desired` 与 `heal_paused` 落 runtime 快照（9.7），故 backend 重启后的扫描要尊重快照——`follow_backend` 服务若上次是人工 [停止]（`desired==stopped`），重启 backend **不拉起**；否则用户"关了又自己回来"，等于没有停止键。

**空闲回收**：`on_demand` 服务可声明 `idle_stop_seconds`（缺省 0 = 不回收）。超过该秒数无请求、无任务、无对话 → 自动停止，瓦片转灰并记一条 `idle_stop` 事件。桌面用户不需要"永远挂着的代理"。

**两种在场场景（presence）**

| 场景 | 状态 | 自愈取向 |
|------|------|---------|
| **A1 离场任务态** | 任务 / 定时任务在跑，人不在电脑边 | **激进**：立即重启、可多试几次；重启不打断任何交互 |
| **A2 在场对话态** | 用户正在与 Agent 沟通、看输出 | **温和**：等在飞请求归零再重启，先给降级提示；宁可慢，不可断 |

presence 由 Agent runtime 上报（有活动会话 / 正在流式输出 = `present`；任务执行且无输入活动 = `away`），框架只读不改。**同一次故障，两种场景两种处理**——这是单机桌面相对服务器的独有变量（9.7）。

## 三、业界取经结论

### 3.1 supervisord — drop-in 目录与生命周期字段

吸收要点：

| supervisord 概念 | 本框架对应 |
|-----------------|-----------|
| `[include] files = conf.d/*.conf` | `ext_service/*/service.json` 目录扫描（目录即服务） |
| `command` + `directory` + `environment` | 清单中的启动命令、工作目录、环境变量 |
| `startsecs`（启动后稳定 N 秒才算 STARTED） | 启动判定引入**稳定期**：进程活着 ≠ 服务就绪 |
| `startretries` / `autorestart` | 重试上限 + 自愈策略（策略 / 上限 / 退避，9.7） |
| `stopasgroup` / `killasgroup` | 统一树杀（Windows 下 proc_utils 已覆盖，不暴露选项） |
| `autostart` | 并入 `activation`：`follow_backend` = 跟随后端启动，`on_demand` 为缺省（见 2.6） |

没有吸收的：supervisord 的事件监听器/优先级组——本框架常用服务 ≤20 个（1.4），引入优先级拓扑是过度设计（YAGNI）。

### 3.2 Docker Compose — healthcheck 语义

这是本次最重要的吸收。supervisord 只判断"进程活着"，Docker 判断"服务健康"：

| Docker healthcheck 字段 | 本框架字段 | 用途 |
|------------------------|-----------|------|
| `test` | `health.check_type` + `health.check_target` | HTTP GET 端口路径 / TCP 连端口 / 进程存在 |
| `interval` | `health.interval_seconds` | 健康轮询间隔（默认 10s） |
| `timeout` | `health.timeout_seconds` | 单次探测超时（默认 3s） |
| `retries` | `health.retries` | 连续失败 N 次才判不健康（防抖，默认 2） |
| `start_period` | `health.start_grace_seconds` | 启动宽限期：宽限期内失败不计入 retries（服务冷启动慢是常态） |

**核心语义定案：start 成功 ≠ running。`start` 返回成功只表示"启动动作已受理"，必须健康探测通过才迁移到 running。** 这一条直接决定了状态机设计（见第八章），也是避免"端口还没监听，页面已经绿灯"这种假状态的关键。

### 3.3 MCP transports — kind 分派的依据

MCP 官方定义两类标准传输：

- **stdio**：客户端拉起子进程，stdin/stdout 换行分隔 JSON-RPC —— 进程由"使用方"管理生命周期，框架若拉起它，角色是"宿主"；
- **Streamable HTTP**：独立端点，进程与协议无关 —— 框架角色是"探活监控方"。

对框架的含义：MCP 服务不能硬套"进程型"执行器。stdio 型 MCP 的"启动"= 拉起宿主进程但**不**做 HTTP 探活（探活 = 进程存活 + 初始化握手），HTTP 型 MCP 的"启动"可能根本不属于本框架（进程已在别处，框架只监控）。所以 kind 必须一等公民化，MCP 作为独立 kind 后置到 P2。

### 3.4 其它（PM2 / Windows Services，简查）

- PM2 ecosystem 配置同样是"声明文件 + 统一守护"模式，佐证 drop-in 思路；其 `max_restarts`/`restart_delay` 字段语义并入自愈策略（阶段一，见 9.7）。
- Windows SCM 服务：注册成本高、需要管理员权限，与本系统"随包携带的轻量服务"定位不符，不采用；但其"服务状态查询与控制分离"（QueryServiceStatus / ControlService）佐证了**状态查询与控制命令分离**的 API 设计。

## 四、总体设计：后端架构与前端 UI 架构对应

### 4.1 架构判词与四问定案

一句话架构判词：

> **注册表、状态机、健康监控、UI 是公共的；"怎么启动、怎么停止、怎么探活"是每种 kind 自己的事。**

| 用户问题 | 定案 |
|---------|------|
| 新服务怎么自动识别？ | `<应用根>/ext_service/<service_id>/service.json` drop-in 清单（目录即服务，插件式插拔），启动扫描 + 热扫描，零代码注册 |
| 怎么启动停止？ | 框架按清单 `kind` 分派执行器；local-process 型 = Popen + 树杀；其他 kind 由各自执行器实现 |
| 启动后怎么监控？ | 统一健康引擎按清单 `health` 段轮询；统一状态机输出；UI 一服务一 Tab，Tab 内即该服务的过程状态视图 |
| 集中还是分散？ | **集中监控、分散实现**。插件/MCP 可以统一"管理"（注册、状态展示、页面呈现），但不统一"实现"（各自执行器）。插件在 P2 接入时是"仅启用/禁用"的能力子集，MCP 是"连接管理"的能力子集 |

### 4.2 后端架构（框架层 + 执行器层）

```
REST 路由层   /api/v1/services/*（_mount() 统一挂载 + 默认 token 鉴权）
     │
框架层（公共，与 kind 无关）
     ├─ 注册表      ext_service 清单扫描 / 热扫描 / invalid 隔离
     ├─ 状态机      stopped/starting/running/stopping/failed/unknown/invalid/disabled
     ├─ 健康引擎    单 asyncio 循环，按各服务 health 段轮询
     └─ 动作任务    白名单动作执行 / 长动作任务表 / to_thread 卸载
     │ 按清单 kind 分派
执行器层（每种形态一个，语义契约 start/stop/status）
     ├─ local-process   Popen(breakaway) + 树杀 + 端口确认
     ├─ http-endpoint   纯监控（不拥有进程）
     └─ (P2) mcp-server / plugin
     │
服务本体      ext_service/<id>/ 内的 exe / bat / 配置（自包含）
```

详设见第五章（架构总图与取舍）、第八章（状态机）、第九章（后端模块与 API）。

### 4.3 前端 UI 架构（UI 框架设计）

与 4.2 后端架构同权重、同层级，一一对应（映射表见 4.4）。UI 框架设计定死**骨架、组件、状态映射、交互框架**四件事；第十章只做实现级详设与示意图，不再另立框架。

#### 4.3.1 页面骨架（上：服务瓦片区 + 下：服务 Tab）

```
┌────────────────────────────────────────────────────────────────┐
│ A 服务瓦片区（≈页面 1/3，只读，一排 4~6 张迷你卡）      ⟳ 刷新  │
├────────────────────────────────────────────────────────────────┤
│ B 服务 Tab 栏（一服务一 Tab，Tab 名 = 服务名，label 内嵌状态点） │
│   ● OpenCLI 网关   ● OmniVPN   ◐ 数据同步   ▨ 新服务(invalid)   │
├────────────────────────────────────────────────────────────────┤
│ C Tab 内容区（当前服务的操作与详情，一屏读完，七段同构）          │
│   C1 状态条     期望/实际 + PID/端口 + uptime + 延迟 + 自愈开关     │
│   C2 主操作组   [启动][停止][重启]（能力闸门 + 状态驱动）         │
│   C3 健康点阵   最近 N 次 ok/fail + 连续成功/失败 + 最近错误      │
│   C4 附加操作组 清单 actions 声明的按钮（无则整段不出现）         │
│   C5 动作输出区 [STEP]/[OK]/[FAIL] 逐行追加（task_id 轮询）       │
│   C6 日志尾部   （P1）                                          │
│   C7 迁移时间线 （P1）                                          │
└────────────────────────────────────────────────────────────────┘
```

骨架定案：

1. **A 区 = 服务瓦片区**：一服务一张迷你卡，只有四项字段（名称 / 死活 / 端口 / 运行时长），**整卡可点 → 切到该服务 Tab**，卡内零操作按钮（操作入口唯一在 C 区）；字段、尺寸与取数时机见 4.3.7；
2. **B 区 Tab 名 = 服务名**，label 内嵌状态点（●/◐/▨ + 语义色）；C 区即该服务的全部信息，**空间不受卡片尺寸限制**——后续加段不用改骨架；
3. **C 区七段顺序固定**，段可缺省（capabilities 关闭或 P1 未实现则整段不出现），所有服务同构；
4. **不设详情抽屉、不设二级页面**：Tab 内容本身就是详情，任何叠加层都是"详情里再开一层详情"。

#### 4.3.2 信息架构（四层）

```
导航层   NavContent「服务管理」→ /services 路由（lazy）
     │
概览层   服务瓦片区（A 区）：一服务一张迷你卡（四项字段，只读）
     │        点瓦片 / 点 Tab，两条路径都通向同一个 Tab
视图层   服务 Tab 栏（B 区）：一服务一 Tab，label 带状态点
     │
内容层   当前 Tab 的操作与详情（C 区 C1~C7，无二次跳转，选中即展开）
     │
数据层   进入页面拉一次（GET /services 全量）+ 手动刷新 / 操作受理后回拉
        动作任务 2s 轮询（按 task_id，仅动作执行期间）
        （A 区与 B 区共用同一份快照，不各拉一次）
```

#### 4.3.3 组件框架（UI 元素 → antd 组件 → 数据源）

| UI 元素 | antd 组件（不引新 UI 库） | 数据源 |
|---------|--------------------------|--------|
| 页面壳 | 上下分栏容器（flex column）+ 标题 | — |

#### 4.3.4 状态 × 能力 → 视图映射（单源驱动 UI）

可用性由**两个维度**共同决定：`state`（后端状态机）+ `capabilities`（清单能力声明）。只按 state 渲染会给 http-endpoint / plugin 这类无启停能力的 kind 渲染出假按钮，扩展性在 UI 层就会破口。

**第一维：能力闸门（先于状态判断，决定"渲染与否"）**

| 能力 | 为 false 时的 UI 事实 |
|------|---------------------|
| capabilities.start / stop | C2 主操作段**整段不渲染**（不是置灰）——服务本就不具备该动作，置灰会误导用户以为"多试几次能好" |
| capabilities.status | C1 状态条与 C3 健康点阵不渲染（Tab 仍在，仅展示清单声明信息） |
| capabilities.actions | C4 附加操作段不渲染 |
| capabilities.logs | C6 日志段不渲染 |

**第二维：状态决定可用性（能力为 true 的部分）**

| 状态 | 徽标 | C2 主操作段（能力允许者） | C4 附加操作段 |
|------|------|---------------------|-----------|
| stopped | 默认灰点 | [启动]可用；[停止][重启]禁用 | 可用（与生命周期无关；声明了 requires_running 的动作置灰并注明原因） |
| starting | 蓝·转圈 | 全部转圈置灰 | 可用 |
| running | 绿 | [启动]禁用；[停止][重启]可用 | 可用 |
| stopping | 蓝·转圈 | 全部转圈置灰 | 置灰 |
| failed | 红 | [启动][重启]可用；[停止]禁用 | 可用 |
| unknown | 灰 | [接管][终止]（人工裁决，见 8.5） | 置灰 |
| invalid | 红框虚线 | 无操作（仅展示错误信息） | 无 |
| disabled | 灰 | 全部禁用 | 全部禁用 |

定案五条：

1. **按钮可用性由后端 state + capabilities 双源驱动，前端不自行推断**——后端是唯一真源；
2. 映射表是前后端的共同契约，两端各持一份同表实现；
3. capabilities 缺省按 kind 推导、清单只能收窄不能放宽（推导表见 9.6.4）；
4. **本表只约束 C 区**（操作与详情）；A 区瓦片只读，**不受能力闸门影响**（无操作就不需要闸门，状态怎么变都照实展示）。
5. **自愈开关不属于 capabilities**：它是框架级策略（框架对所有 `local-process` 都纠偏），只要 `restart.policy != never` 就渲染；`activation == manual` 时不渲染（该服务本就只认人手）；`capabilities.status == false` 时随 C1 整段消失（无进程生命周期，本就不需要纠偏），不另设位置。

#### 4.3.5 交互框架（反馈铁律的 UI 落法）

反馈三拍固定为三种 UI 机制，不做第二种花样（简约）：

1. **第 1 拍 按钮态**：点击瞬间按钮转圈/置灰（Button loading + disabled）；
2. **第 2 拍 受理可见**：成功→按钮转圈，回拉快照后 Tab label 状态点与该服务瓦片同步更新；失败→message 报因（含具体原因，如端口占用/互斥冲突/未声明动作 403）；
3. **第 3 拍 过程可见**：生命周期过程=状态点转圈直到终态；动作过程=当前 Tab 的 C5 动作输出区逐行追加直到 [OK]/[FAIL]。

时序示意见 10.3.3，详设见第十章。

#### 4.3.6 多服务承载与"切换"语义（瓦片区 + 一服务一 Tab）

定案一句话：**上半屏是服务瓦片区（一服务一张小卡，谁活着谁挂了一眼扫完），下半屏是单服务（一 Tab 一服务）；"切换服务" = 点瓦片或点 Tab，没有第二套导航。**

**上下两区职责边界**：

| 区域 | 回答什么问题 | 允许 | 禁止 |
|------|-------------|------|------|
| A 瓦片区（≈1/3 高） | "所有服务现在什么状况？" | 名称、死活（两种）、端口、运行时长；整卡点击切 Tab | **任何操作按钮**（启停/动作）——否则一个动作两个入口、两套反馈；也不放图表/趋势线/延迟 |
| B+C Tab 区 | "这个服务怎么操作、过程如何？" | 启停、附加操作、健康点阵、动作输出、日志、时间线（**少量实时信息只在这里**） | 横向罗列其它服务的内容（不重复瓦片） |

**Tab 放顶部还是左侧（定案 + 理由）**：

| 位置 | 评价 | 结论 |
|------|------|------|
| **顶部（定案）** | 只占一行（~46px），切换路径最短（鼠标横移/方向键），与"页面级视图切换"语义一致；上方已有瓦片区给全局，Tab 紧跟其下**层次自然** | ✅ P0 采用 |
| 左侧 | 能放多行元信息、垂直空间利用充分；但项目 Layout 已有左侧主导航（`AppLayout` 的 `Sider`），服务列表再靠左会形成**二级侧栏**：层级混乱、内容区被两次压缩（1440 屏下只剩 ~800px），而 C 区恰恰要宽度（健康点阵、等宽动作输出） | ❌ 不作默认 |
| 左侧（例外） | antd `tabPosition="left"` 一行配置可切；仅当服务 >30 或必须在标签里显示三行元信息时才评估，且**C 区零改动** | ⏳ 保留演进口 |

**其余承载定案**：

| 问题 | 定案 | 理由 |
|------|------|------|
| Tab 顺序 | **固定按 `name` 字典序**，绝不含状态因素；**永不按状态重排** | 重排会让用户正在看的 Tab 位移导致误点 |
| 默认激活哪个 Tab | 首个异常服务，全绿取第一个；对应瓦片同步高亮 | "打开页面就看到该看的"，不需要用户自己找 |
| 有没有"当前选中服务" | **有，就是 `Tabs.activeKey`**（瓦片高亮跟随）。它是**导航态**，不是操作前置条件：切到某 Tab 后，C 区的按钮全部属于该服务 | 语义单纯：选中即展开，操作对象永远是当前 Tab |
| 刷新页面后 | P0 回到默认激活规则；P1 才做 `?service=<id>` URL 化 | 避免"刷新后停在一个用户没预期的 Tab"这种中间态 |
| 加"全部概览" Tab？ | **不做**。全局概览职责已由瓦片区承担，再加概览 Tab 就是在 Tab 栏里塞第二个概览 | 单一职责：Tab = 单服务视图 |
| 同一服务多实例 | 不存在（单实例由 service_id 保证：清单目录唯一 + 7.2 第 4 条端口互斥 + 9.3 启动前置检查） | UI 不造后端没有的概念 |

多服务同屏的实际形态见 10.3.1（主页面示意图）。

三条由本形态直接导出的实现约束：

1. **一份快照喂两处**：A 区瓦片与 B 区 Tab 用**同一份** `GET /services` 快照（同一次响应、同一个时间点），绝不各拉一次——否则"瓦片说 running、Tab 说 failed"这种自相矛盾必然出现；
2. **一 Tab 一数据源**：C 区按钮态、置灰原因、动作按钮组全部来自该服务自己的 `state / capabilities / actions[]`，Tab 之间零共享可变状态（否则 A 服务点停止，B 服务跟着转圈）；
3. **动作输出不串台**：动作属于"某服务的某次任务"，落在该服务 Tab 的 C5 内；切到别的 Tab 时前一个任务仍在后台跑并有自己的 `task_id`，切回按 `task_id` 继续拉取（8.4 / 9.5）。**不做全局"任务中心"**（P0），也不在瓦片 / Tab label 上显示动作进度（它们只关心生死）。

**多服务规模边界（写明触发条件，防将来临时加塞）**：

| 服务数 | 承载方式 | 说明 |
|--------|---------|------|
| 1~20 | 瓦片区（一排 4~6 张，超出区高则区内滚动）+ 顶部 Tab | 当前设计，无需辅助导航；**常用上界按 20 设计（1.4）** |
| 21~30 | 瓦片区 + 按 kind/group 分组标题（Segmented 于瓦片区之上） | P1 评估；纯前端分组，不动后端契约 |
| >30 | 才评估 `tabPosition="left"` 的左侧 Tab | 此时多行元信息与垂直空间才划算；需接受与主导航并存的成本 |

规模上界之外一律不进 P0：左侧服务列表 + 右侧详情的"主从布局"被否决（多一步选中、与左侧主导航叠加成二级侧栏、且其列表与详情职责已分别由瓦片区和 C 区承担，再做一遍就是第三套）。

#### 4.3.7 服务瓦片（A 区）字段定案：一服务一张小卡，就四项

定位一句话：**A 区是一排小卡片，一张卡 = 一个服务；只回答"活着没、是哪个、跑了多久"，全部字段由服务端快照直接给，前端不做任何本地推算与动效。**

**一、瓦片字段（四项，多一项都不加）**

| # | 位置 | 内容 | 数据来源 | 说明 |
|---|------|------|---------|------|
| 1 | 卡片左侧 4px 竖条 | **二值色条**：绿 = 活着 / 灰 = 没活着 | `alive`（服务端给） | 扫一列颜色就知道谁死了，不用读字 |
| 2 | 第 1 行 | `服务名`（过长省略号） | `name` | 谁是谁 |
| 3 | 第 2 行 | `状态文字 · 端口`（"运行中 · 8080" / "已停止 · —"） | `alive` + `port` | 活着没 + 是不是我以为的那个实例 |
| 4 | 第 3 行 | `运行时长`（"3h45m"；没活着显示"—"） | `uptime_s`（服务端算好的秒数，前端只格式化） | 很短 = 刚崩过，这是瓦片唯一的时间信息 |

**就这四项。** 不全的量、不给图标、不给动画、不显示延迟、不做趋势。

**二、死活只有两种（瓦片层面的口径）**

| 瓦片 | 语义 | 包含哪些后端 `state` |
|------|------|---------------------|
| 绿条 + "运行中" | 活着 | `running` |
| 灰条 + "已停止" | 没活着 | `stopped` / `failed` / `unknown` / `starting` / `stopping` / `disabled` |
| 灰虚线边 + `!` | 清单非法 | `invalid`（第 2 行显示"清单非法 · —"，错误原文在它的 Tab） |

细化状态（启停中、失败原因、健康历史）**只在 Tab 里看**，瓦片不区分——瓦片不是监控面板，是"哪台机器还亮着"的指示灯。

清单非法留一个 `!` 徽标与灰虚线边：否则用户无法理解"这个服务为什么点了没反应"；具体哪一行清单错了，去它的 Tab 看。

**三、尺寸与排布**

| 项 | 定案 |
|----|------|
| 单卡尺寸 | `min-width: 200px`，高度约 88px（3 行内容 + 内边距） |
| 一排几张 | 4~6 张（容器宽度自适应，`flex-wrap: wrap`），gap 12px |
| 区高 | ≈ 页面 1/3（`34vh`，min 240px / max 420px）；装不下时**区内纵向滚动**，不做"更多"折叠、不做分页 |
| 点击 | 整卡可点 → 切到该服务 Tab；当前 Tab 对应的瓦片加 1px 主题色边框（高亮，不改变尺寸） |
| 排序 | **固定按 `name` 字典序，永不按状态重排**（见 4.3.6：位移会造成误点） |

**四、取数时机：进页面取一次，其余靠手动刷新**

| 时机 | 行为 |
|------|------|
| 进入服务管理页 | 拉一次 `GET /services`（全量），瓦片区与 Tab 同时渲染 |
| 点 ⟳ 刷新 | 再拉一次，同步更新瓦片区与 Tab label |
| 启停 / 动作受理后 | 回拉一次（用真实状态替换本地 pending 态），动作输出另按 `task_id` 拉 |
| 其余时间 | **不轮询、不定时器、不本地推算、不做动效** |

**五、少数需要实时的信息，全部放该服务的 Tab（在线详情页）**

瓦片 = 静态快照（进页面 / 点刷新时取一次）；**"会变的东西"一律在 Tab 内按需取**，两处职责不重叠：

| 信息 | 在哪 | 怎么取 |
|------|------|--------|
| 健康点阵 / 最近探测时间与延迟 | C1、C3 | 切到该 Tab 时拉一次 `GET /services/{id}`，需要更新点刷新 |
| 动作输出（[STEP]/[OK]/[FAIL]） | C5 | 动作执行期间按 `task_id` 2s 轮询，终态即停 |
| 日志尾部 | C6（P1） | 手动刷新 / 复制 |
| 状态迁移时间线 | C7（P1） | 切到该 Tab 时拉一次 |

**六、明确不做（防止瓦片长成大卡片）**

| 不做 | 原因 |
|------|------|
| 延迟 / 点阵 / 趋势图 / 迷你图表 | 动态信息属于 Tab 的监控，放瓦片就变成仪表盘 |
| 走时动画、数字滚动、呼吸灯 | 瓦片不是被注视的界面，动效只增加重渲染与视觉噪音 |
| 卡内操作按钮 / 展开折叠 / 点击浮层 | 操作入口唯一在 C 区；点卡只切 Tab |

**七、字段与后端契约同源（UI 与系统架构一一对应）**

瓦片的每个槽位都是对 `GET /services` 的硬要求：快照必须**一次返回全量**并带 `alive / port / uptime_s`，`invalid` 项随快照带 `error`（清单非法原文）——否则前端只能逐个再拉 `GET /services/{id}`，N 倍请求换来同屏 N 个时间点。

三条纪律：① 先定 9.2 响应结构，再写瓦片组件；② 死活/端口/时长只取后端单一写者（9.6），前端只做格式化与颜色映射；③ 缺字段就改契约，不许前端拼。

### 4.4 前后端对应关系（一一映射）

| UI 呈现 | 后端来源 |
|---------|---------|
| Tab 出现 / 消失 | 注册表扫描 + 热扫描（GET /services 列表增减） |
| Tab label 状态点 / 瓦片左侧色条（绿=活/灰=不活） | 状态机 `state`（瓦片读派生 `alive`） |
| 瓦片第 2/3 行（状态文字 · 端口 · 运行时长） | `alive` / `port` / `uptime_s`（4.3.7 字段表） |
| 瓦片 invalid 徽标（灰虚线 + `!`） | 注册表 invalid 项（错误原文只在其 Tab 展示） |
| 按钮**是否存在**（能力闸门） | 清单 `capabilities`（kind 推导，见 9.6.4）——无能力不渲染，不是置灰 |
| 启动 / 停止 / 重启按钮 | `POST start / stop / restart`（受理式，见 4.5） |
| 接管 / 终止按钮（unknown） | `POST adopt / terminate`（人工裁决，8.5） |
| C1 自愈开关 / "期望 running·实际 failed·已重试 N 次" | `desired` / `heal_paused` / `heal_attempts`（`POST heal`，9.7） |
| 按需拉起（无按钮，Agent 侧调用） | `POST ensure`（幂等，2.6） |
| C1 过程状态（转圈、延迟、uptime） | 状态机 + 健康引擎（GET /services/{id}） |
| C3 健康点阵 / C6 日志（P1） | GET /services/{id}（健康历史、日志尾部） |
| C4 附加操作按钮组（文案/二次确认/置灰原因） | 清单 `actions[]`（label/confirm/requires_running）→ `POST actions/{action_id}` |
| C5 动作输出区 | 动作任务表（GET /api/v1/action-tasks/{task_id}） |
| Tab 内 invalid 错误块 | 注册表 invalid 项 `error` |

原则：**UI 上每一个可见元素都必须能指到后端唯一数据源**——没有数据源支撑的 UI 元素不做（防镀金）。瓦片的字段级需求见 4.3.7，那里的槽位与 `GET /services` 响应字段是同一张清单。

### 4.5 操作模型定案：三主操作 + 附加操作

**主操作（三件套，所有服务统一，框架标配）**：

1. **启动**：受理式——点击即转圈（starting），健康探测转绿才算成；
2. **停止**：受理式——点击即转圈（stopping），端口释放确认才算完；
3. **查看过程状态**：**该服务的 Tab 内容区**（C1~C7）——状态迁移、健康延迟、uptime、动作输出等一切过程信息统一在这里看，不另开页面；

重启 = 停止 + 启动的组合便利（同一状态机路径 stop→start，不新增机制），与主操作同组。

**附加操作（附加功能，按服务声明，不是标配）**：OmniVPN 的换桶 / 巡检 / 出口体检、未来各服务的运维脚本——在清单 `actions` 白名单里声明了 UI 才渲染，不声明就不出现（UI 复杂度只随服务实际能力增长）。

**操作反馈铁律**：任何操作执行入口必须有反馈——

- 点击瞬间：按钮态即变（转圈 / 置灰），禁止"点了没反应"；
- 受理结果：受理成功 / 拒绝（403 / 互斥冲突）立即可见；
- 过程进展：starting→running 迁移、动作输出逐行追加，持续可见直到终态。

### 4.6 UI 设计原则

1. **遵守系统 UI 规范**：菜单进 NavContent 统一数组、路由进 App.tsx 统一 lazy 注册、页面落 `pages/Services/`、逻辑落 `features/serviceManager/`、API 封装走 `services/api/service.api.ts` 与 client.ts 的 `/api/v1` 前缀；组件全部用 antd 既有体系（Card / Tabs / Tag / Badge / Button / Modal / Timeline），不引新 UI 库；
2. **大气简约、信息分层克制**：瓦片区只放"一眼要判断的"（名称 / 死活 / 端口 / 运行时长），单服务细节全部收进该服务的 Tab 内容区；不堆大卡片、不叠浮层、不做二级跳转；配色沿用系统语义色（健康绿 / 异常红 / 进行中蓝），不造新色板，且只让"异常"用强调色；
3. **先不搞复杂**：P0 不做列配置、筛选器、拖拽、主题定制、瓦片折叠开关、趋势图等任何增值交互，默认状态即可用，能不加的控件一律不加（YAGNI）。

## 六、注册与落位：清单规范 · 自动识别 · 部署布局

### 6.1 清单文件规矩（锚定应用根，目录即服务）

- 位置：`<应用根>/ext_service/<service_id>/service.json`；
- **应用根解析**：发布态 = 运行 exe 所在目录；开发态 = 仓库根。唯一解析点 `svcmanager/paths.py::resolve_app_root()`（判别打包/frozen 标志），两态同构，其余模块一律经它取路径；
- **目录即服务**：一个子目录 = 一个服务。目录拷入 = 注册，目录移除 = 注销，天然"插件式插拔"；清单与它指向的 exe/配置/脚本同目录自包含，杜绝"清单指着目录外文件"的悬空引用；
- 清单文件名固定 `service.json`（一个目录一个服务，无需通配命名）；
- service_id = 子目录名，全局唯一，`^[a-z][a-z0-9_]{2,31}$`；
- 编码：UTF-8 无 BOM；
- **路径解析规矩**（清单内一律禁止绝对路径，两类根分开、各一解析点）：`command`/`args`/`workdir` 按**服务目录**解析，解析结果经 `resolve()` 后必须仍在服务目录内，越界（`../` 逃逸）判清单非法；`logs.path` 按 **`OMNI_SERVICE_DATA`** 解析，`status.json` 位置固定（7.4）不在清单声明（运行时生成物不落代码目录，见下一条）；
- **ext_service 视为只读**（发布态可能落在受保护目录）：清单、exe、脚本、配置随目录携带，**运行时生成物一律不落此处**；服务进程的可写区 = `<数据目录>/services/<service_id>/`，由框架以环境变量 `OMNI_SERVICE_DATA` 注入（布局见 6.5）；
- 运行时快照落数据目录（与 SQLite 同源解析点 `~/.omniagent`），不写 ext_service；
- 非法清单（schema 校验失败、id 冲突、kind 未知）**降级为 `invalid` 状态单独展示，不拖垮整个注册表**（一个坏目录不能让页面全挂——防御性设计）。

### 6.2 清单 schema

```jsonc
// ext_service/opencli_gateway/service.json （示例；command/args 相对服务目录，logs 相对 OMNI_SERVICE_DATA）
{
  "id": "opencli_gateway",
  "name": "OpenCLI 网关",
  "description": "第三方 CLI 模型接入协议整形网关（opencode2api）",
  "kind": "local-process",            // local-process | http-endpoint | mcp-server | plugin
  "enabled": true,                     // 总开关：false 时页面显示但禁用操作
  "activation": "on_demand",           // on_demand | follow_backend | manual（2.6）
  "idle_stop_seconds": 0,              // >0 且 on_demand：空闲该秒数自动停（0=不回收）

  "restart": {                         // 自愈策略（9.7）：只纠偏，不新增状态
    "policy": "on-failure",            // on-failure（缺省）| never；无 always（见 9.7）
    "max_attempts": 3,                 // 连续失败上限，超限停止纠偏并标 failed(crashloop)
    "backoff_seconds": [5, 15, 60]     // 逐次退避，用尽后固定最后一档
  },

  "spec": {                            // spec 段内容随 kind 而异，schema 按 kind 分支校验
    "command": "opencode2api.exe",     // 必须是常驻前台进程（禁自我后台化，契约 7.2.6）
    "args": ["-config", "config.json"],// 该 exe 为单横线参数；端口取自 config.json 的 listen
    "workdir": ".",                    // 缺省 = 服务目录自身
    "env": {},                         // 追加环境变量（框架另注入 OMNI_SERVICE_DATA，见 6.5）
    "listen_port": 8080,               // 树杀后验证端口释放用；纯监控型没有
    "encoding": "utf-8",               // 动作/日志输出解码声明：utf-8 | gbk（缺省 utf-8；bat 类脚本通常 gbk）——契约 7.2.5
    "stop": null                       // 该网关无 /shutdown 面 → 缺省树杀兜底（契约 7.5）
  },

  "health": {                          // 语义对齐 Docker healthcheck
    "check_type": "http",              // http | tcp | process
    "check_target": "http://127.0.0.1:8080/healthz",  // http=GET断言2xx; tcp=连端口; process=仅进程存活
    "interval_seconds": 10,            // 实测端点：/healthz 在 8080（备选 tcp:8080）
    "timeout_seconds": 3,
    "retries": 2,
    "start_grace_seconds": 20          // start_period 语义：宽限期内失败不计连续失败
  },

  "capabilities": {                    // 能力分级声明（ISP），UI 按此渲染；缺省按 kind 推导，此处只做显式确认
    "start": true, "stop": true, "status": true,
    "logs": true, "actions": true
  },

  "actions": [],                       // 网关无运维动作 → 附加操作组整组不渲染（声明制）

  "logs": {
    "kind": "stdout",                  // file | stdout | none；网关输出到控制台，由框架代收落文件
    "path": "service.log"              // 相对 OMNI_SERVICE_DATA 解析
  }
}
```

字段口径六条（避免实现期各自解释）：

1. `spec.command` 必须是**前台常驻进程**，自我后台化的脚本会让 PID 语义与树杀同时失效（7.2.6 硬约束）；
2. **`actions[].command` 是必填**（相对服务目录，越界拒绝）——框架凭 id 无从知道该跑哪个脚本；白名单校验对象是 `command` 的解析结果，不是 id 字符串；
3. `actions[]` 每项进 API 时带 `label`/`confirm`/`timeout_seconds`/`requires_running`/**`encoding`**（8.4 契约），UI 才有按钮文案、前置态与正确解码；
4. `spec.encoding` 是该服务文本产出的默认编码，**动作脚本可用 `actions[].encoding` 覆盖**（bat=GBK、PowerShell/mihomo 侧按 UTF-8 钉死，一个字段管两种进程必然乱码）；
5. `logs.path` 的相对根是 `OMNI_SERVICE_DATA`，不是服务目录；`status.json` 路径固定（7.4），清单无需声明；
6. `activation` 决定"谁能让它起来"：`manual` 连自愈都不做（纯人肉），`follow_backend` 在后端启动时按快照 `desired` 拉起（人工停止过的不拉起，2.6），`on_demand` 由用户 / `ensure` / 自愈触发；`idle_stop_seconds` 只对 `on_demand` 生效——`follow_backend` 是常驻语义，不回收。

schema 校验用 pydantic 模型族（`ServiceManifest` + 按 kind 的 `spec` 判别联合），错误信息落注册表 `invalid` 项的 `error` 字段，UI 展示。

### 6.3 首批两个清单

**opencli_gateway**：如上示例，kind=local-process，`listen_port=8080`，健康 `http://127.0.0.1:8080/healthz`，无运维动作（`actions: []`）。

**omnivpn**：语义最容易做错的一个，必须写死。

| 项 | 定案 | 理由 |
|----|------|------|
| `spec.command` | `omnivpn-start.ps1`（服务目录内前台 wrapper） | **不能写 `mihomo-slim.exe -d .`**：内核会在 `-d` 目录写 `cache.db`，而服务目录在发布态只读；wrapper 先用 `OMNI_SERVICE_DATA` 播种 config 再 `& mihomo-slim.exe -d $env:OMNI_SERVICE_DATA` **前台阻塞**（不是 `Start-Process`，故 PID 语义与树杀都成立，不违反 7.2.6） |
| 不能写 `proxy-on.bat` | 禁止 | 该脚本内部 `Start-Process` 起 mihomo 后**自己退出**：框架拿到的 PID 秒退 → 状态机判 failed，而 mihomo 在跑；且 `Start-Process` 使 mihomo 脱离父子链，**树杀杀不到** → "停止"按钮永远确认不了端口释放 |
| 系统代理开关 | 降级为动作 `proxy_on` / `proxy_off`（`timeout_seconds: 60`） | 设/清系统代理是"运维动作"而非"服务存续"，混进启动会让"启动"带副作用、无法单元重试 |
| 健康探测 | `tcp 127.0.0.1:7890` | 内核监听即就绪；HTTP 面需额外鉴权，不值得 |
| 动作集 | `proxy_on` / `proxy_off` / `proxy_switch` / `update_quick` / `rebuild_pool` / `exit_probe`（6 个，与 13.3.3 清单一致） | 除 `proxy_off` 外均 `requires_running: true`（stopped 时 UI 置灰并注明"需先启动"）——关系统代理与内核在不在无关，故它是唯一 `false` 的 |
| 长动作 | `proxy_switch`(300s) / `update_quick`(900s) / `rebuild_pool`(1200s) / `exit_probe`(900s) 走动作任务表 | 输出长、耗时分钟级（短动作阈值 30s，9.5） |

**首批目录迁移（P0 第一步，阶段一工单）**：将仓库根的 `opencli_gateway/`、`OmniVPN/` 两个目录 **git mv 迁入 `ext_service/`**，使开发态布局与发布态同构；同时清点仓库内对旧路径的全部引用（脚本/文档/代码）并同步更新。已核：OmniVPN 的 ps1/py 全用 `$PSScriptRoot`/`__file__` 相对定位，**无绝对路径**，迁移后自洽；但其 `log/`、`nodepool/` 产物目录在迁移后必须改指 `OMNI_SERVICE_DATA`（见 6.5 与第十三章改造清单）。

### 6.4 自动识别流程

```
框架启动 → 扫描 ext_service/*/service.json（resolve_app_root 锚定）
        → 逐个 pydantic 校验 → 合法项入注册表 / 非法项入 invalid
        → 按 runtime 快照做孤儿收养判定
        → activation=follow_backend 且 enabled 且快照 desired!=stopped 的服务排队 start（2.6）
运行期   → watchdog 线程监控 ext_service 变更
        → 新建子目录(含合法 service.json)=注册出新服务 Tab
        → 目录删除=先 stop 在跑实例再注销摘 Tab
        → 清单修改=差分热更新（不打断运行态，标 config_dirty）
```

热扫描差分规则：id 相同且清单内容 hash 未变 → 不动（不打断运行中服务）；内容变了 → 保留运行态，标记"配置已变更待生效"；目录消失（含 id 消失）→ 树杀后摘除。

### 6.5 部署布局与可写目录定案（基础架构，P0 必须落）

**两态布局同构**：

```
开发态  仓库根/
          ├─ backend/  frontend/  config/
          └─ ext_service/<id>/service.json + exe + 脚本 + 配置      ← 只读区（git 管理）
发布态  <exe 同级>/
          ├─ OmniAgentBackend.exe  _internal/  config/  version.txt
          └─ ext_service/<id>/...                                   ← 只读区（可能无写权限）
数据区  <数据目录>/                       = ~/.omniagent（与 SQLite 同源解析点）
          ├─ chat_history.db …
          ├─ services_runtime.json         ← 运行时快照（孤儿收养数据源）
          ├─ service_events/<id>.jsonl     ← 事件历史（P0 落盘，C7 展示 P1）
          └─ services/<service_id>/        ← 服务进程唯一可写区（OMNI_SERVICE_DATA）
                ├─ service.log               （logs.kind=stdout 由框架代收落此）
                ├─ status.json               （服务自报，契约 7.4）
                └─ …任意产物（OmniVPN 的 log/、nodepool/ 迁到这里）
```

**定案**：`ext_service` 只读，`OMNI_SERVICE_DATA` 可写且由框架在启动前 `mkdir -p` 后以环境变量注入。这条同时解决三处矛盾——"服务目录自包含"与"发布态无写权限"、"日志落服务目录"、"status.json 落服务目录"。**注入的环境变量全集（7.7 输入标准）**：`OMNI_SERVICE_ID`、`OMNI_SERVICE_DATA`、`OMNI_SERVICE_DIR`、`OMNI_SERVICE_PORT`（声明了 `listen_port` 时）、`OMNI_PRESENCE`（启动时的在场态初值）。运行期 presence 变化无法改子进程环境，另写 `<OMNI_SERVICE_DATA>/presence` 文件（即 `<数据区>/services/<id>/presence`）供服务按需读取。

**打包链改造（P0 必做）**：现状 `backend/OmniAgentBackend.spec:79-82` 的 datas 只有 `version.txt`/`config.yaml.example`/`OmniAgent.md` 三个单文件，`run_server.py::_deploy_resources` 也只能拷单文件（mtime 判据）。迁入 `ext_service/` 后必须补两处：

1. **spec**：`datas` 增加整目录条目 `(str(REPO/"ext_service"), "ext_service")`；
2. **部署器**：`_deploy_resources` 增加目录树递归部署（同 mtime 判据：源新于目标才覆盖，保护用户对 list 内配置的本地改动；目录缺失时整棵建），否则发布态 exe 旁边不会出现 `ext_service/`，页面永远空白。

**体积策略**：`mihomo/`（内核）与 `opencode2api.exe` 体积可观，随包会显著撑大安装包。定案 P0 先随包（同构、零运维）；"外挂清单来源"（大文件按需投放到 `<应用根>/ext_service/`）排阶段五（P2，12 章）；P0 不引入下载器（YAGNI）。

## 七、服务接入契约（UI 对接规范）

### 7.1 为什么需要契约

两个现有服务的信息出口都是**面向 console** 的：bat 脚本 echo 给人看、退出码语义随意、中文输出走 GBK、依赖控制台特性。UI 对接需要的是**机器可读**：成败怎么判、进度怎么看、状态怎么取、日志在哪。若不定规范，每个服务接入时各改各的，格式漂移、重复踩坑；定了契约，后续任何新服务照单编写即可对接。

契约分四级，**达标解锁、渐进接入**：T0 即入册，不因不达标把旧服务挡在门外。**此处 `T` 是"接入等级"**，与 2.5 的服务层次 `L1/L2/L3`（服务与 Agent 的关系）、9.6.1 的代码分层 `D0~D4`（模块依赖方向）是三个不同维度，不可混用。

| 级别 | 名称 | 要求 | 现有两服务改造量 |
|------|------|------|------------------|
| T0 可纳管 | 清单 | service.json 合法即可被框架管理（启停/进程监控） | 网关零改造（写清单即达）；OmniVPN 需加一个前台 wrapper（内核要写自身目录，见 6.3 / 13.3.2） |
| T1 可监控 | 健康与日志 | 健康探测通道（http / tcp / process 三选一）+ 文件日志（或声明 logs.kind=stdout 由框架代收落文件） | 小（OmniVPN 用 tcp:7890 即达 T1；网关若有 health 路由则用 http，否则 tcp） |
| T2 可运维 | 动作与自报 | 动作脚本符合 7.3 约定；可选 status.json 自报（7.4） | 中（bat 输出规范化、退出码补齐） |
| T3 原生 | 管理面 API | 服务自带 /status、/actions HTTP 管理端点 | 远期方向，本期不要求 |

UI 能力渲染与级别挂钩：T0 只有启停与基础状态；T1 解锁健康延迟与日志；T2 解锁动作输出区与自报指标面板。

### 7.2 无头运行约束（硬性，所有级别适用）

服务被框架拉起时运行在 `CREATE_NO_WINDOW` 无控制台环境，契约硬性要求（违者属服务 bug，不属框架兼容项）：

1. **禁止任何交互式输入**：`pause`、`set /p`、stdin 读取一律禁止——无控制台下会**永久挂起**（console 转 UI 最典型事故形态）；框架侧动作任务另设超时上限双保险（见 9.5）；
2. 禁止依赖控制台特性：标题、颜色、`cls`、console API；
3. 禁止任何弹窗（MsgBox 等）；报错走退出码 + 日志；
4. 单实例语义靠 listen_port 天然互斥即可，不要求服务自实现互斥；
5. **编码显式声明**：manifest `spec.encoding`（utf-8 | gbk，缺省 utf-8）是该服务文本产出的**默认**编码；**动作脚本可单独覆盖** `actions[].encoding`（bat 走 `chcp 936`=GBK，而 PowerShell/mihomo 侧按 UTF-8 钉死——用一个字段管两种进程必然乱码）。声明制而非猜测制；
6. **禁止自我后台化**：`Start-Process`、`start /b`、`nohup` 类"起完就退"的写法一律禁止。被管进程必须是**前台常驻**，否则框架拿到的 PID 立刻失效、状态机误判 failed，且子进程脱离父子链后树杀不可达（OmniVPN 的 `proxy-on.ps1` 就是这种形态，故 6.3 定案改用前台 wrapper 直接运行内核）；
7. 无监听端口的形态（plugin、stdio MCP）不自带互斥：互斥由框架按 service_id 的运行态保证（同一 id 不允许并行两个实例），但**不防用户手工双击 bat**——这是明确的边界，不扩大承诺。

### 7.3 动作脚本约定（T2）

console 现状：脚本输出给人看，成败全凭肉眼。UI 对接三条约定：

1. **退出码是成败唯一真源**：0=成功，非 0=失败；脚本任何失败分支必须 `exit` 非 0。框架以退出码定动作任务终态，stdout 只做展示；
2. **输出行半结构化**（人读优先，机器轻解析，不做 JSON 深解析——KISS）：

   ```
   [HH:mm:ss] [STEP] 正在拉取订阅源 1/9 ...
   [HH:mm:ss] [OK]   15001 条已入库
   [HH:mm:ss] [FAIL] 源 3 超时，跳过
   ```

   进度行打 `[STEP]`，结果行打 `[OK]/[FAIL]`；框架原样透传到 UI 动作输出区，仅按 `[OK]/[FAIL]` 前缀做高亮与成败汇总（一行正则的解析量）；
3. **长动作必须报进度**：预期 >30s 的动作按阶段打 `[STEP]` 行，UI 展示"最近一步"；清单 `actions[].timeout_seconds` 声明超时上限（缺省 600s），超时树杀动作进程判 failed。

**现有脚本现状（实测）**：OmniVPN 现有 5 个 bat **全部以 `pause` 结尾**，且 ps1 的退出码被 `pause` 覆盖（`pause` 返回值恒 0）——同时违反 7.2.1（禁交互）与 7.3.1（退出码唯一真源）：

| 脚本 | `pause` | 退出码透传 | P0 必须改 |
|------|---------|-----------|----------|
| proxy-on.bat | 有 | 无 | 去 `pause` + `exit /b %ERRORLEVEL%` |
| proxy-off.bat | 有 | 无 | 同上 |
| proxy-switch.bat | 有 | 无 | 同上（内含两段 ps1，需按段判定成败） |
| rebuild-pool.bat | 有 | 无 | 同上 |
| update-pool-quick.bat | 有 | 无 | 同上 |

不改的后果可预测：无头执行时 `pause` 永久挂起，动作任务只能等 600/900s 超时被树杀 → 用户在动作输出区看到的不是 `[OK]` 而是超时 failed。故这 5 个 bat 的规范化是 P0 工单，不是"顺手改"。

### 7.4 自报状态约定（T2 可选：status.json）

对非 HTTP 型服务（如 mihomo），"端口活着"之外还有丰富状态（当前出口、节点池计数、最近巡检时间）需要通道：

- 服务进程自行周期写 `<OMNI_SERVICE_DATA>/status.json`（间隔建议 5~10s，**原子写**：临时文件 + replace，防读到半截）；路径固定，清单无需声明；
- 字段外框契约固定，内容自由：

  ```jsonc
  { "updated_at": "2026-11-12T14:00:00", "state": "running",   // running | degraded | ...
    "metrics": { "exit_node": "...", "pool_alive": 132, "pool_dead": 7 }   // 各服务自定义
  }
  ```

- 框架读取展示在该服务 Tab 的 C1（状态条）；`updated_at` 落后当前时间 > 15s 即标"状态过期"（按 5s 写入节奏的 3 倍；写入间隔不进清单，框架不猜），不静默展示旧数据（防御性）；
- 写 status.json 是服务自己的事，框架只读不写——单写者，无并发问题。

### 7.5 停止语义约定

- 优雅停止优先：manifest `spec.stop` 可声明 `{"kind": "http-post", "target": ".../shutdown"}`；服务有 HTTP 面时推荐提供 `/shutdown`；
- 树杀是兜底而非首选：声明了优雅停止的，先 POST /shutdown，超时 5s 再树杀；未声明的直接树杀（proc_utils psutil BFS 已保证子进程无残留）；
- 服务方义务：收到停止信号后自行清理子进程/临时文件，保证**重入安全**（可被再次 start，不依赖上次的现场）。

本约定与 8.2 状态机 stop 语义、9.3 停止流程共用同一套判定，三处不各说各话。

### 7.6 新服务编写速查（给后续服务编写者）

```
1. 建 ext_service/<id>/ 目录，写 service.json                    → T0 完成，页面出该服务 Tab
2. 有监听端口 → health 用 tcp；有 HTTP → 提供 /health 路由用 http  → T1 健康绿灯+延迟
3. 日志落文件（或声明 logs.kind=stdout 由框架代收）               → T1 日志可见
4. 动作脚本按 7.3 改造（[STEP]/[OK]/[FAIL] + 退出码 + encoding 声明）→ T2 动作输出区
5. 想展示丰富状态 → 周期写 status.json                            → T2 自报指标
6. 全程遵守 7.2 无头约束（禁交互/禁弹窗/禁控制台依赖）
7. 按 7.7 三面标准自查（输入：数据区/参数/单实例；控制：前台/优雅停止/健康面；输出：编码/退出码/前缀/日志落点）
```

### 7.7 服务接入标准（输入 / 控制 / 输出三面，自研服务必须满足）

**先立规矩**：无缝整合不是靠框架猜，而是靠服务侧守标准。标准只落在三面——**怎么被喂（输入）、怎么被管（控制）、怎么说话（输出）**；每面都分"服务必须做"与"框架兜底"，兜底只能降级、不能替代标准。

**适用对象**：**自研新服务必须全达标**；存量与上游改造服务按 7.1 的四级（T0~T2）渐进达标，未达标项按"框架兜底"列**在页面标注降级**（如"仅端口探测"），不许静默假绿。

#### 一、输入标准（框架 → 服务）

| # | 项 | 要求 | 框架兜底（做不到的后果） |
|---|----|------|------------------------|
| 1 | **环境变量** | 必须读 `OMNI_SERVICE_DATA` 作为**唯一可写根**（日志/缓存/节点池全在其下）；可选读 `OMNI_SERVICE_ID`、`OMNI_SERVICE_DIR`、`OMNI_SERVICE_PORT`、`OMNI_PRESENCE` | 框架会注入；不读 = 产物写进只读安装目录，升级/换机即丢（6.5） |
| 2 | **启动参数** | 由清单 `spec.args` 传入；路径一律相对 `OMNI_SERVICE_DIR` 或数据区，禁止绝对路径 | 无兜底：绝对路径在别人机器上必错 |
| 3 | **不读 stdin** | 不 `pause`、不 `set /p`、不等键盘 | 框架把 stdin 接 NUL，`pause` 立即返回但脚本逻辑会错位 |
| 4 | **单实例** | **不需要服务自己做**：有 `listen_port` 的靠端口互斥 + 框架前置检查（7.2 第 4 条），无端口的靠框架按 service_id 的运行态锁（7.2 第 7 条）。服务自己再加锁文件无害，但不作要求 | 人工直跑的进程不在承诺范围内（第十四章）——它顶掉端口时，框架前置检查会让本次启动 `failed` 并报因，不会静默假绿 |
| 5 | **在场感知（推荐）** | 读 `OMNI_PRESENCE`（启动初值）或 `<OMNI_SERVICE_DATA>/presence` 文件（运行期变化）决定是否降级（如 A2 时不做重活） | 不读则按常规定速跑，可能在用户对话时抢资源 |

#### 二、控制标准（框架 → 服务的生命周期）

| # | 项 | 要求 | 框架兜底（做不到的后果） |
|---|----|------|------------------------|
| 1 | **前台阻塞** | 启动命令必须前台运行到底：不自我 daemonize、不 `start /b`、不 `Start-Process` 后自身退出 | 框架判"进程没了"→ 立即 failed；13.3 的 wrapper 就是为此存在 |
| 2 | **优雅停止** | 提供 `POST /shutdown`（HTTP 面）或约定退出信号；收到后清理子进程与临时文件，**可被再次 start** | 框架只能树杀：可能丢未落盘数据，且脏现场会连环失败 |
| 3 | **健康面** | 提供 `GET /healthz` 返回 `200` + `{"status":"ok","detail":""}`；无 HTTP 面则至少保证端口在就绪后才监听 | 框架只能做端口探活 → **端口能连 ≠ 服务可用**（假绿） |
| 4 | **状态自报（推荐）** | 周期原子写 `status.json`（外框固定，字段见 7.4：`updated_at` / `state` / `metrics{}`）到数据区 | 框架只能展示进程/端口/延迟，C1 无业务指标 |

#### 三、输出标准（服务 → 框架 → 用户）

| # | 项 | 要求 | 框架兜底（做不到的后果） |
|---|----|------|------------------------|
| 1 | **编码** | stdout/stderr 统一 UTF-8（确需 GBK 的存量脚本在清单 `encoding` 声明） | 框架按声明解码；声明错 = 中文乱码（7.3 已定双层解码） |
| 2 | **输出形态** | 一行一条事实，行缓冲刷新；不用进度条覆盖、不输出 ANSI 控制序列 | 框架原样落日志，C6 里会出现乱码行 |
| 3 | **退出码** | `0` 成功、非 `0` 失败且语义稳定（建议：1 配置错 / 2 端口占用 / 3 依赖缺失） | 退出码是成败**唯一真源**，无兜底 |
| 4 | **动作输出** | 长动作按 7.3 打 `[STEP]/[OK]/[FAIL]`，最后一行给成败汇总 | C5 只剩原始输出，用户看不出进度与结果 |
| 5 | **日志落点** | 写 `<OMNI_SERVICE_DATA>/<logs.path>`（缺省 `service.log`，与 6.2 同源），或声明 `logs.kind=stdout` 由框架代收 | 无日志 = 出事只能看进程还在不在 |

#### 四、改造清单（存量服务接入时"必须改"的就这些）

| 类别 | 项 | 改动量 |
|------|----|--------|
| 必须 | 去 `pause` / 去交互 | 删几行 |
| 必须 | 退出码透传（bat 末尾 `exit /b %ERRORLEVEL%`） | 加 1 行 |
| 必须 | 产物路径改 `OMNI_SERVICE_DATA` | 改几个常量 |
| 必须 | 前台运行（后台化的加 wrapper） | 新增 1 个 ps1 |
| 推荐 | `/healthz`、`/shutdown`、`status.json`、`[STEP]/[OK]/[FAIL]` | 各几十行，换真健康与真进度 |

**作用域**：本清单只约束**框架托管的启动命令与动作脚本**；人工双击入口（如 `opencli_gateway_start.bat`）不受约束——`pause` 在人工场景是功能不是缺陷（13.2.3）。

**改造前后长什么样（以 bat 为例）**：

```bat
:: 改造前：人工双击的写法
start /b mihomo-slim.exe -d .
pause

:: 改造后：可托管的写法（前台运行 / 产物落数据区 / 退出码透传 / 无交互）
set "DATA=%OMNI_SERVICE_DATA%"
mihomo-slim.exe -d "%DATA%"
exit /b %ERRORLEVEL%
```

**不改的只有两样**：语言与框架、目录结构。**其余"少改"是标准的一部分**，不是可选项——少改换的是"页面说的就是真的、用户不用看文档"。

**消费者视角**：普通用户永远看不到这些约定；标准存在的唯一目的，是让他打开页面时看到的状态、进度、报错都是真的，而不是"端口在所以显示绿"。

## 八、生命周期状态机

### 8.1 状态集

```
                   start(受理)                health 通过
  stopped ──────────────▶ starting ─────────────────────▶ running
     ▲                        │  │                            │
     │ stop(受理)             │  │ health 连续失败             │ stop(受理)
     │                        │  ▼ 超过宽限+retries             ▼
     ├──▶ stopping ◀──────────┘  failed                stopping
     │         │                                            │
     │         │ 树杀完成+端口释放确认                        │
     ▼         ▼                                            ▼
   stopped ◀───────────────────────────────────────────────── stopped
```

全状态集：`stopped / starting / running / stopping / failed / unknown / invalid / disabled`

| 状态 | 含义 | 进入条件 |
|------|------|---------|
| stopped | 未运行 | 初始 / stop 完成确认 |
| starting | 已发启动指令 | start 受理后；超时上限（start_grace + 2×interval）未就绪则**先树杀该进程**再判 failed（不树杀会累积僵尸，下一次启动被自己的残留堵成"端口占用"） |
| running | 健康通过 | 连续 retries 次探测失败会退回 failed |
| stopping | 停止中 | stop 受理后；树杀 + 端口释放确认后归 stopped |
| failed | 启动失败、健康劣化或进程消失 | starting 超时 / running 时健康连续失败 / 进程消失（含服务自己 `exit 0` 收场——没在跑就是没在跑，不粉饰成 stopped） |
| unknown | 存在性不明 | 孤儿收养前、runtime 快照丢失、探测通道异常 |
| invalid | 清单非法 | schema/冲突校验失败（附 error） |
| disabled | enabled=false | 清单总开关关闭 |

**迁移合法性矩阵（`state_machine.py` 的断言来源）**：

| 当前态 | 允许迁移到 | 触发者 |
|--------|-----------|--------|
| stopped | starting / unknown / disabled | start 受理 / 端口有监听但快照丢失 / 清单关闭 |
| starting | running / failed / stopping / disabled | 健康通过 / 启动超时（树杀后） / stop 受理 / 清单关闭 |
| running | failed / stopping / unknown / disabled | 健康连续失败 / stop 受理 / 探测通道异常 / 清单关闭 |
| stopping | stopped / failed / disabled | 树杀+端口释放确认 / 任一步未确认（告警） / 清单关闭 |
| failed | starting / stopping / stopped / disabled | 重新启动 / stop 受理 / 人工确认已停 / 清单关闭 |
| unknown | running / stopped / disabled | adopt 探测通过（人工接管）/ terminate 确认（人工终止）/ 清单关闭 |
| invalid | stopped / disabled | 清单修正后重扫 / 清单关闭 |
| disabled | stopped / invalid | 重新启用 / 清单非法 |

规则：**非法迁移不抛异常打断引擎**，而是记 warning 并保持原状态（健康引擎必须活着，一个服务的错状态不能冻结全站）；`disabled` 是兜底目标态（清单关闭/删除一律可进）；`unknown → running` 只能由人工接管（adopt）后的探测结果触发，不允许自动猜。

### 8.2 关键语义定案

1. **start ≠ Popen 成功**（Docker/K8s readiness 语义）：start 接口受理后立即返回 `starting`，健康引擎在宽限期后开始探测，通过才转 running。前端按钮态按 `starting` 渲染（转圈），不等 running 才反馈。
2. **健康连续失败防抖**：interval + retries + start_grace 三参数共同决定"慢启动不被误杀"（mihomo 首次拉起要加载配置与测速，天然需要宽限期）。
3. **stop 是验证式停止**：语义与契约 7.5 同源——声明 `spec.stop` 的先优雅 POST /shutdown（超时 5s），未声明直接树杀（proc_utils psutil BFS）→ 确认 PID 消失 → 确认 listen_port 释放 → 才置 stopped。任何一步未确认保持 stopping 并告警。
4. **自愈不是新机制**：`failed / stopped` 的拉起一律走 start 路径，由 9.7 的纠偏循环发起；`failed` 本身不再"自动重启三次"另行实现，避免两套重试逻辑打架。
5. **人工停止即期望态**：[停止] = `desired: stopped` + `heal_paused: true`，页面显示"手动停止（自愈已暂停）"；[启动] = `desired: running` 并清零计数。**不存在"按了停止又自己起来"**。
6. **操作互斥**：每服务一把 asyncio 锁，start/stop/restart 与自愈纠偏共用该锁；动作（action）不与服务互斥（换桶不重启服务时允许并发），但同类动作自身串行。

### 8.3 restart 语义

`restart = stop → start`，状态机走完整路径，不做原地重启捷径（保证每次都经过健康验证）。

### 8.4 状态输出

一套字段、两个视图（前后端契约单一真源）：`GET /services` 的每一项 = **扁平摘要**，`GET /services/{id}` = 同一对象 + `detail{}`（进程细节与健康历史）。**字段名两个视图必须一模一样**（`port` / `uptime_s` 不因嵌套改名），前端不做二次映射。

```jsonc
{
  "id": "omnivpn",
  "name": "OmniVPN",
  "kind": "local-process",
  "state": "running",
  "desired": "running",             // 期望态（9.7）：与 state 不一致才说明在纠偏或已止损
  "heal_paused": false,             // 人工停止 / 崩溃循环止损后为 true
  "heal_attempts": 0,               // 连续失败次数（成功 running 累计 60s 才清零）
  "last_active_at": "2026-11-13T08:12:00",   // 空闲回收判据（2.6）
  "alive": true,                    // state==running 的服务端派生，瓦片绿/灰直接用它（4.3.7）
  "port": 7890,                     // 来自清单 listen_port；无端口形态为 null
  "uptime_s": 3721,                 // 后端算好的秒数，前端只格式化
  "detail": {                       // 仅 GET /services/{id} 返回
    "pid": 12345,
    "health": { "last_probe_at": "...", "latency_ms": 23,
                "consecutive_ok": 41, "last_error": null },
    "health_history": [ { "at": "...", "ok": true, "latency_ms": 23 } ]   // 环形尾部，C3 点阵
  },
  "capabilities": { "start": true, "stop": true, "status": true, "logs": true, "actions": true },
  "actions": [                  // 对象数组，不是 id 字符串——UI 渲染按钮需要 label/confirm，无数据源不许造 UI（4.4）
    { "id": "proxy_switch", "label": "切换出口", "encoding": "gbk", "confirm": false, "requires_running": true, "timeout_seconds": 300 },
    { "id": "rebuild_pool", "label": "重建节点池", "encoding": "gbk", "confirm": true, "requires_running": true, "timeout_seconds": 1200 },
    { "id": "exit_probe",   "label": "出口体检",   "encoding": "gbk", "confirm": false, "requires_running": true, "timeout_seconds": 900 }
  ],
  "config_dirty": false,        // 清单已变更待生效
  "last_error": null,           // 最近一次健康/启动/动作失败摘要（C1 展示）
  "error": null                 // 清单非法原文（仅 invalid 时有值，落在该服务 Tab 的错误块）
}
```

`actions[]` 是对象数组而非 id 字符串（UI 渲染按钮要有文案与确认标记）；`requires_running` 用于前端置灰并注明原因，后端照旧 409 兜底；`encoding` 是动作级解码覆盖服务级默认（7.2.5）。`desired / heal_paused / heal_attempts / last_active_at` 是期望态（9.7），只读下发、由 manager 单写；`last_error`（运行期最近错误）与 `error`（清单非法原文）必须分开，否则"清单写错"和"服务挂了"在 UI 上是同一句话。

### 8.5 孤儿收养（adopt）

backend 重启后，服务子进程可能仍在跑（上一轮 backend 退出但 Job 隔离生效——这正是设计目标，见 9.4）。处理：

1. 启动扫描后，对每个清单项：若 runtime 快照有 PID 且该 PID 仍存活且进程命令行与清单 `spec.command` 匹配 → 收养：登记 PID、恢复健康轮询、状态转 running（探测通过后确认）；
2. PID 存活但命令行不匹配 → 不收养，按 stopped 处理，日志告警（防止把无关同名进程误收）；
3. 快照丢失但 listen_port 有监听 → 状态置 `unknown`，UI 给"接管/终止"双按钮，让用户显式裁决（不猜）。

### 9.2 API 设计（/api/v1/services）

| 方法/路径 | 语义 |
|-----------|------|
| `GET /api/v1/services` | 全量状态快照列表（前端进页面 / 手动刷新时拉取；含 actions 完整描述） |
| `GET /api/v1/services/{id}` | 单服务详情（含健康历史尾部） |
| `POST /api/v1/services/{id}/start` | 受理启动（返回 starting，不等待） |
| `POST /api/v1/services/{id}/stop` | 受理停止 |
| `POST /api/v1/services/{id}/restart` | 受理重启 |
| `POST /api/v1/services/{id}/ensure` | **幂等确保在跑**（Agent / 任务前置调用：running 直接返回，stopped 则启动，starting 等终态，见 2.6）；`activation=manual` 或 `enabled=false` → 409（manual 只认人手） |
| `POST /api/v1/services/{id}/heal` | 自愈意图开关 `{action: pause\|resume\|reset}`——只改纠偏意图，不碰进程（9.7） |
| `POST /api/v1/services/{id}/adopt` | **人工接管**（unknown→running，需 `confirm:true`，见 8.5） |
| `POST /api/v1/services/{id}/terminate` | **人工终止**（unknown→stopped，需 `confirm:true`，风险动作） |
| `POST /api/v1/services/{id}/actions/{action_id}` | 执行自定义动作（同步短动作直接返回；长动作返回 task_id） |
| `GET /api/v1/services/{id}/logs?tail=N` | 日志尾部（P1） |
| `GET /api/v1/action-tasks/{task_id}` | 长动作进度/结果（P0，随动作机制一起落） |

鉴权走 `_mount()` 默认 token 机制（`main.py:359` 全局唯一出口，自动挂 `_AUTHENTICATED`），无新增豁免。

**列表快照字段（瓦片区与 Tab 同源）**：`GET /services` 的每一项必须**一次带齐** `id / name / kind / state / desired / heal_paused / heal_attempts / alive / port / uptime_s / last_error / error / capabilities / actions[]` —— 这就是 4.3.7 瓦片字段表与 C1 的直接来源；`alive`（`state == running` 的服务端派生）、`uptime_s` 由后端算好下发，`desired/heal_paused/heal_attempts` 供 C1 显示纠偏状态（9.7），`error` 仅 `invalid` 项非空。两条禁令：前端不得为凑字段再逐个拉 `/services/{id}`（N 倍请求 + N 个时间点，同屏数据互相打架）；不得自算 uptime 或自行探测端口（第二套状态判定）。缺字段就改本契约，不许前端拼。

**`confirm` 语义收敛**：不要求"所有写操作都带 confirm"——`start/stop/restart` 的点击本身就是意图表达，再加确认层只是形式主义。定案：

| 操作 | 是否要求 `confirm: true` | 理由 |
|------|------------------------|------|
| start / stop / restart | 否 | 幂等、可恢复、前端已有按钮态与过程反馈 |
| 清单声明 `confirm: true` 的动作 | 是 | 作者声明"这个动作有代价"（重建池 15 分钟） |
| adopt / terminate | 是 | 人工裁决 + terminate 会杀进程 |

状态码约定（前端据此报因，不再自定义）：`403` 未声明动作/未认证；`409` 前置条件不满足（`requires_running` 未满足、生命周期互斥锁被占、清单 disabled/invalid）；`422` 清单字段非法；`200` 受理成功。

### 9.3 启动器细节（local-process）

```
启动流程（executors/local_process.py）：
1. 前置检查（受理时已转 starting）：enabled / 状态互斥锁 / 端口未被占用；任一不过 → 直接转 failed 并注明原因（走 starting→failed，迁移矩阵见 8.1）
2. 构造子进程：`CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW`，**不加 `CREATE_BREAKAWAY_FROM_JOB`**——Job 已设 `SILENT_BREAKAWAY_OK`（9.4），子进程自动落在 Job 外；带该标志反而在只设了 SILENT 位的 Job 下 `CreateProcess` 直接报 ERROR_ACCESS_DENIED。只有走 9.4 降级路径（Job 只设 `BREAKAWAY_OK`）时才加它。注入 7.7 环境变量全集（`OMNI_SERVICE_ID/DATA/DIR/PORT/PRESENCE`）并写 `<OMNI_SERVICE_DATA>/presence`，stdin 接 NUL
3. stdout/stderr 重定向：logs.kind=stdout 时由框架代收落日志文件（契约 7.1 的 T1 承诺）；kind=file 时服务自写，框架只读
4. 登记 PID → 写 runtime 快照 → 转 starting
5. 健康引擎接管：宽限期后按 interval 探测，通过 → running
6. 超时兜底：`start_grace + 2×interval` 仍未就绪 → **树杀该 PID** 再转 failed。不树杀会把挂住的进程留成僵尸，下一次启动被自己的残留堵成"端口占用 failed"（自造的故障链）
```

停止流程（与契约 7.5 同一套判定）：

```
1. 取互斥锁 → 转 stopping
2. 声明了 spec.stop 的先优雅停止：POST /shutdown，超时 5s；未声明直接进第 3 步
3. proc_utils.kill_process_tree(pid)   （psutil BFS，零 taskkill）
4. 等待树杀完成确认（poll pid 不存在，上限 10s）
5. listen_port 释放确认（`psutil.net_connections` 经 `to_thread` 执行，不走 shell netstat；上限 10s）
6. 清 runtime 快照 → 转 stopped；任一步未确认 → 保持 stopping + 告警事件
```

### 9.4 安全关键设计：Job Object 隔离（必须项）

**坑**：`run_server.py:317` 在 frozen 态把 backend 自身收编进 `KILL_ON_JOB_CLOSE` Job（`win_job_object.py`）。Windows 规则：子进程**默认自动继承**父进程所在 Job。后果链：backend Popen 服务 → 服务进 backend 的 Job → **backend 关闭/崩溃 → Job 句柄回收 → KILL_ON_JOB_CLOSE 连服务一起杀光**。与"服务独立于 backend 生存"直接冲突，是本框架唯一的一票否决项。

**定案**：

1. **主方案：给 backend 自己的 Job 加 `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`（0x00000800）**。语义是"子进程**不**自动收编进本 Job"——一次设置即解决，不必给每个子进程传 `CREATE_BREAKAWAY_FROM_JOB`，也不依赖策略环境是否允许 breakaway。改动点只有一处：`win_job_object.py:84` 的 `LimitFlags` 加该位（当前只设 `KILL_ON_JOB_CLOSE`）；
2. **降级路径**：`JOB_OBJECT_LIMIT_BREAKAWAY_OK` + Popen `CREATE_BREAKAWAY_FROM_JOB` 同样能脱离，但要求 Job 显式允许、部分策略下失败率更高；仅作 SILENT_BREAKAWAY_OK 不可用时的兜底保留；
3. **禁止"assign 到独立 Job"**：Win8+ 是**嵌套 Job**，`AssignProcessToJobObject` 到新 Job **不会**把进程从 backend 的 Job 里摘出来，父 Job 关闭照样连杀；"仅用于收集句柄便于枚举"也不成立（枚举用 psutil 即可）；
4. **双保险兜底**：runtime 快照落盘。即使发生意外连杀，下次启动的孤儿收养/unknown 流程仍能正确呈现事实。

**验证口径（开发态验证无效）**：Job 只在 `if getattr(sys,"frozen",False)` 时创建（`run_server.py:317`），**开发态根本没有 Job**，"关 backend 服务仍存活"必然绿。故该条验收必须在**打包态**执行，并断言三条：关 backend 后服务 PID 存活 + 端口仍监听 + 重启 backend 能收养为 running。

**这条不落实，框架就是负资产**——它会制造"关 backend 连带杀服务"的新故障模式，作为一票否决项核查。

### 9.5 自定义动作机制

- 动作必须在清单 `actions` 白名单声明，路由层对未声明的 `action_id` 直接 403（不给任意命令执行面）；白名单校验的是 `actions[].command` 经 `paths.py` 解析后的**实路径**（必须落在服务目录内，越界拒绝），不是 `action_id` 字符串——只校验 id 等于给了任意命令执行面；
- 动作执行 = 以清单 `spec.workdir` 为 cwd 调用 `actions[].command`，`CREATE_NO_WINDOW`，stdout/stderr 捕获并按 **`actions[].encoding` ?? `spec.encoding`** 解码（动作级覆盖服务级默认，契约 7.2.5——bat 是 GBK、PowerShell 侧是 UTF-8，同一个服务里两种动作并存，只用服务级一个字段必然乱码）；动作任务带超时上限（清单 `actions[].timeout_seconds`，缺省 600s），超时树杀动作进程并判 failed（对无头环境下脚本意外交互挂起的双保险，契约 7.2.1 的框架侧兜底）；
- 短动作（<30s 预期，如 proxy switch）同步返回输出尾部；
- 长动作（rebuild_pool / update_quick / exit_probe）走动作任务表（内存 dict + 落盘），返回 task_id，前端轮询；动作任务不进事件循环，用 `asyncio.to_thread` 卸载（教训来自 shell_engine 卡死事故：同步长任务跑在事件循环里会僵死全服务——这是本仓已定案的铁律）；
- 动作期间服务状态机不动（动作 ≠ 生命周期变更）；动作失败不影响服务 running 态，结果以动作任务状态呈现。

### 9.6 基础架构定案（依赖方向·数据所有权·并发·契约·错误隔离）

模块之间的接线不钉死，实现期必然长出循环引用、跨线程改状态、引擎被单服务异常拖死这三类通病。

#### 9.6.1 依赖方向（单向，禁止回环；各层包含哪些文件见 9.1）

三条硬规则：

1. **依赖只能自上而下**（D1→D2；D2→D3 与 D2→D4；D3/D4→D0），反向与同层横向引用一律禁止；
2. **executors 不得 import D3**：需要清单/目录就由 manager 组装 `ServiceContext` 传进去（下文 9.6.4）；否则 `local_process → state_machine → registry → executors` 立刻成环；
3. **health_engine 不得 import registry**：由 manager 注入"取注册表快照"的只读函数（依赖倒置），引擎对"服务从哪来"无认知。

#### 9.6.2 数据所有权（单一写者，杜绝"谁都能改一点"）

| 数据 | 唯一写者 | 读者 | 说明 |
|------|---------|------|------|
| 服务 state | `state_machine.py` | 全部 | 其它模块只能提交"迁移请求"，不能直接赋值 |
| 注册表快照 | `registry.py`（含 watchdog 交接后） | manager/前端 | 读方拿**不可变快照**，不拿活字典 |
| runtime 快照文件 | `manager.py`（启停/迁移后写） | 孤儿收养 | 原子写（临时文件+replace） |
| 期望态 `desired` / `heal_paused` / `heal_attempts` / `last_active_at` | `manager.py`（人工操作、`ensure`、纠偏循环、请求打点四处写，统一经 manager 方法） | 纠偏循环 / 前端 | 与 state 严格分离：state 归状态机，期望态归 manager，禁止互相赋值（9.7） |
| 健康历史/计数 | `health_engine.py` | 前端详情 | 环形缓冲，定长 |
| 动作任务表 | `actions.py` | 前端轮询 | 内存 dict + 落盘 |
| 事件历史 | `events.py` | 前端时间线 | 环形 200 条 + 落盘 |

#### 9.6.3 并发模型与跨线程交接（唯一入口）

- **一个 asyncio 事件循环**承载全部框架逻辑（health 循环、API handler、动作调度）；
- **每服务一把 `asyncio.Lock`**（生命周期专用）：start/stop/restart 互斥；**每个 action_id 一把锁**：同类动作串行，动作与服务不互斥（8.2 第 6 条）；
- **watchdog 是线程（看门狗只能阻塞等文件事件），交接只有一个入口**：
  `loop.call_soon_threadsafe(manager.request_rescan)` —— 线程**禁止**直接改注册表/状态；这条不写死，必然出现"线程改字典、循环读到半截"的诡异状态；
- **所有阻塞 OS 调用一律 `asyncio.to_thread`**：Popen 等待、psutil 枚举、端口确认、文件读写、动作子进程通信。清单（照此逐项核）：`proc_utils.kill_process_tree`、`psutil.net_connections`、`psutil.Process.cmdline`、runtime 快照读写、日志 tail 读。

#### 9.6.4 执行器契约（代码级，ISP 最小面）

```python
class ServiceContext(NamedTuple):
    manifest: ServiceManifest      # 只读
    service_dir: Path              # 只读区（ext_service/<id>）
    data_dir: Path                 # 可写区（OMNI_SERVICE_DATA）
    pid: Optional[int]

class Executor(Protocol):
    kind: ClassVar[str]
    async def start(self, ctx: ServiceContext) -> StartResult: ...   # 返回事实：ok / pid / error
    async def stop(self, ctx: ServiceContext) -> StopResult: ...     # 返回事实：pid_gone / port_free / error
    def snapshot(self, ctx: ServiceContext) -> Dict[str, Any]: ...   # 纯读，<1ms，禁阻塞
    async def probe(self, ctx: ServiceContext) -> ProbeResult: ...   # 健康探测
```

铁律：**执行器不改 state、不写 runtime 快照、不做重试**——它只回答"事实上发生了什么"，状态迁移由 `state_machine` 依据事实决定。这样"状态机单源"才真的是单源。

**kind → capabilities 推导表**（清单只能收窄，不能放宽）：

| kind | start | stop | status | logs | actions | 备注 |
|------|-------|------|--------|------|---------|------|
| local-process | ✔ | ✔ | ✔ | ✔ | ✔ | 全量 |
| http-endpoint | ✘ | ✘ | ✔ | ✘ | ✔ | 不拥有进程，纯监控 |
| mcp-server (stdio) | ✔ | ✔ | ✔ | ✔ | ✘ | 宿主拉起 + 初始化握手探活 |
| mcp-server (http) | ✘ | ✘ | ✔ | ✘ | ✘ | 等同 http-endpoint |
| plugin | ✔ | ✔ | ✔ | ✘ | ✘ | **start/stop 语义即"启用/禁用"**，复用状态机与按钮，前端零改动（这是"能力子集"的正确落法：不新造按钮，只映射语义） |

#### 9.6.5 错误隔离矩阵（一个服务坏了，不能拖垮页面）

| 故障点 | 处理 | 绝不能 |
|--------|------|--------|
| 单个清单非法 | 该项 `invalid` + error，其余正常 | 拖垮整个注册表 |
| `executor.start` 抛异常 | 该服务 `failed` + 错误摘要入 `last_error` | 冒泡终止 API 或引擎 |
| 健康探测异常/超时 | 记 `last_error`，计入连续失败 | 让健康循环整体退出 |
| registry 扫描 IO 异常 | 保留上次快照 + 该服务标 stale | 清空注册表（页面全空） |
| 动作进程卡住 | 超时树杀 + 任务判 failed | 无限等待 |
| runtime 快照读/写失败 | 降级 `unknown` + 告警日志 | 阻断框架启动 |
| 状态机非法迁移 | 记 warning，保持原状态 | 抛异常打断循环 |
| 服务进程被外部杀掉 | 健康失败 N 次 → `failed` | 静默显示 running |

#### 9.6.6 可观测（实现期不需要另造）

统一 `logger`，状态迁移与动作关键节点固定前缀：`[svc] <id> state <from>→<to> (<reason>)`、`[svc] <id> action <action_id> <task_id> <STEP|OK|FAIL>`；事件另入 `events.py` 环形缓冲供 UI 时间线。**日志即埋点**，P0 不引 metrics 体系（YAGNI）。

### 9.7 期望态与自愈（在场感知的纠偏循环）

**为什么必须有**：支撑服务的意义是"需要的时候撑得住"。没有纠偏，框架只是把双击 bat 换成单击 bat，价值为零。

**一句话模型**：`desired`（期望态）由清单、用户操作、`ensure` 写入；`state`（实际态）由状态机维护；reconcile 只做一件事——两者不一致且允许纠偏时，走**与按钮完全相同**的启动路径（`stopped → starting → running`），不新增状态、不走捷径。

**数据（单一写者仍是 manager，9.6.2）**

| 项 | 含义 | 存活 |
|----|------|------|
| `desired` | `running` / `stopped` | 内存 + runtime 快照（重启后恢复） |
| `heal_paused` | 人工暂停纠偏 | 内存 + 快照 |
| `heal_attempts` | 连续失败次数 | 内存 + 快照 |
| `last_active_at` | 最近一次被使用（请求 / 动作 / 对话） | 内存 + 快照（空闲回收判据） |
| `restart` / `activation` / `idle_stop_seconds` | 策略 | 清单（只读） |

**循环**（单 asyncio 任务，5s tick，与健康引擎同循环，不另起线程）

```
每个 tick，对每个服务：
  desired==state、heal_paused、activation==manual
      或 state ∈ {unknown, starting, stopping, invalid, disabled}
      → 不动（unknown 不猜，8.5；中途态不打断）
  desired==running 且 state ∈ {stopped, failed} 且 policy!=never
      → 取生命周期锁 → 记 heal 事件(attempt+1) → 走 start 路径（9.3）
  desired==stopped 且 state ∈ {running, failed}
      → 走 stop 路径（停止同样是纠偏，不靠"再拉一次"）
  activation==on_demand 且 idle_stop_seconds>0
      且 now - last_active_at > idle_stop_seconds
      → 转 desired=stopped 并记 idle_stop 事件
```

**策略只有两档**：`on-failure`（缺省）/ `never`。进程消失一律先判 `failed`（含服务自己 `exit 0` 收场，见 8.1），所以"要它在跑"只对应 `desired==running` 这一件事；不设 `always`——它与 `on-failure` 只在"人工停过但期望态仍 running"这种残留态上有差别，而 [停止] 已把 `desired` 置 `stopped`，该态根本不存在，多一个枚举值只会多一行死真值，实现期还容易写成自杀循环（YAGNI）。`never` = 设施层不自愈，4.3.4 定案 5 的自愈开关不渲染。

**presence 决定"急不急"（2.6）**

| presence | 纠偏前的等待 | 退避 | 上限 |
|----------|-------------|------|------|
| `away`（A1 离场任务态） | 不等 | `backoff_seconds` 原档 | `max_attempts`（缺省 3） |
| `present`（A2 在场对话态） | **等在飞请求归零**（最长 60s，超时则推迟到下一 tick） | 原档 ×2（更慢） | `max_attempts` 减 1（更保守） |

presence 由 Agent runtime 上报（有活动会话 / 正在流式输出 = `present`），框架只读不改。**不许用"重启一次也许能好"去赌用户当前这轮对话。**

**止损**：连续失败达到上限 → 停止纠偏、`heal_paused=true`、`failed(reason=crashloop)`、记 error 事件；成功 running 累计 ≥ 60s 才清零计数（"能起来但反复重启"不算健康）。

**三条不越界**

1. **不猜 unknown**：PID 在但快照丢失仍交人工 adopt/terminate，自动"接管"等于替用户杀进程；
2. **不改清单**：只在运行态纠偏；`invalid` 一律不纠偏，改文件重扫才恢复；
3. **人工优先**：[停止] 把 `desired` 置 `stopped` 并 `heal_paused=true`，页面显示"手动停止"，**不会自己爬起来**；[启动] 置 `running` 并清零计数；崩溃循环下人工点 [启动] = 一次显式重试，成功即清零。

**动作与自愈不耦合**：纠偏与 start/stop 共用同一把生命周期锁（不与人工抢跑），不参与动作锁（8.2 第 6 条）；纠偏重启会打断 `requires_running` 的长动作 → 动作按失败收尾并在 C5 说明原因；**不提供"暂停自愈等动作跑完"的隐式联动**（要等就人工暂停）。

**API**：`POST /services/{id}/ensure`（幂等确保在跑）、`POST /services/{id}/heal`（`pause` / `resume` / `reset`；reset 用于崩溃循环后人工修完清单再重试）。事件走 11 章的统一信封 `{ts, service_id, type, from, to, reason, trigger, context}`：`type=heal|idle_stop`，`context` 带 `attempt` / `presence` / `result`（落盘 P0，C7 可视化 P1）。

**验收（阶段一，必须打包态）**：`taskkill` 掉服务进程 → `away` 下 15s 内自愈回 running、页面不用刷新；`present` 下正在流式输出时杀掉 → 当前这轮不中断，输出结束后 60s 内自愈；把 `spec.command` 改成不存在的 exe → 3 次后停在 failed 并显示"已重试 3 次 / 自愈已暂停"；人工 [停止] 后等 60s 不再自动起。

### 10.4 数据流

- 进页面拉一次 `GET /services`（瓦片区与 Tab label 同源）；点 ⟳ 刷新再拉一次；
- start/stop/restart 为乐观受理：点击后立即置本地 pending 态，受理后回拉一次快照换成真实状态；
- 切 Tab 拉一次 `GET /services/{id}`（C1/C3 明细），需要更新点刷新；C6/C7 同为按需拉取；
- 动作任务轮询 2s，直至终态；
- 除动作执行期间外**没有任何定时器**：不轮询、不本地走时、不做动效；
- 不引新状态库（与全仓一致），页面内 `useState/useReducer` 足够（常用 ≤20 个，见 1.4）。

## 十一、可观测与度量

| 指标 | 来源 | 展示位置 |
|------|------|---------|
| 生命周期状态 | 状态机 | Tab label 状态点 + 瓦片左侧色条 |
| PID / 监听端口 | 执行器 | 瓦片（端口）/ C1（PID + 端口） |
| uptime | 执行器（启动时刻差值，服务端算 `uptime_s`） | 瓦片第 3 行 + C1 |
| 健康延迟 ms | 健康引擎每次探测 | C1 |
| 连续成功/失败计数 | 健康引擎 | C3 |
| 最近一次错误信息 | 健康引擎 | C1 / C3 |
| 日志尾部 | logs 段配置（P1） | C6 |
| 状态变迁事件历史 | events.py（落盘 P0，C7 展示 P1） | C7 时间线 |

**事件历史（落盘 P0，C7 展示 P1）**：所有事件共用一个信封 `{ts, service_id, type, from, to, reason, trigger, context}`，环形缓冲 200 条 + 落盘。四个字段各有定值域，不许自由发挥：

- `type`：`transition / heal / idle_stop / action`；`from` / `to` **只有 `transition` 有值**，其余留 null；
- `trigger`：`user / self-heal / backend / scan / action`——11.1 的"人工干预次数"只数 `trigger=user`；
- `reason`：一句话原因，给时间线直接展示（如"健康连续失败 3 次""端口被 PID 4321 占用"）；
- `context`：**出事当时的现场**——退出码、最后一次探测结果、presence、动作 id、占用端口的 PID 与命令行等键值对；能取到就写，取不到留空对象，不做推断填充。

"服务半夜为什么挂了"能回答，靠的是 `context` 里这些现场；11.1 的故障归因覆盖率只认 `context` 非空的失败条数。

### 11.1 托管有效性度量（证明框架不是 bat 遥控器）

四个数，全部从本框架自己的事件与动作留档算出，不引 metrics 体系：

| 度量 | 定义 | 算法（数据源） | 合格线 |
|------|------|---------------|--------|
| **人工干预次数** | 用户主动 start / stop / restart / heal 的次数 | 事件表按 `trigger=user` 计数（周维度） | 稳态下 ≤ 故障次数（即每次故障最多一次人工介入，其余自愈） |
| **MTTR** | 故障发生到恢复 running 的时长 | `failed` 事件 → 下一次 `running` 事件的时间差，取中位数 | 离场（A1）≤ 60s；在场（A2）≤ 会话结束后 60s |
| **新服务接入耗时** | 从建目录到页面可用 | 工单时间戳差（建目录时刻 → 页面可点时刻），人工记录 | ≤ 30 分钟且零框架代码改动 |
| **故障归因覆盖率** | 有完整现场（事件 + 日志尾 + 探测历史）的故障占比 | `events` 中带 `context` 的条数 / 总失败条数 | ≥ 90% |

这四条是阶段一/阶段二的验收口径之一：**只看"能启停"不算通过**，还要能拿这四条数说清楚框架省了什么。

SSE 推送（P2 再议）：服务状态变化是分钟级事件，前端进页面/刷新各拉一次已足够，没有后台轮询需要替代；SSE 只会增加连接管理复杂度，收益不足（YAGNI，留扩展点：事件历史落盘后 SSE 只是换传输层）。

**13.3.2 新增 `omnivpn-start.ps1`（为什么必须 wrapper：内核要写 `cache.db`）**

`OmniVPN/mihomo/` 里已有 `cache.db`——证明 mihomo 会往 `-d` 目录写盘；而服务目录发布态只读。故不能 `command: "mihomo/mihomo-slim.exe" -d .`。用系统自带的 `powershell.exe`（5.1，用户机器必有）而不是 `pwsh`（PS7，只在开发机装了）——wrapper 只用 `$PSScriptRoot` / `Test-Path` / `&` 这些 5.1 就有的东西。

```powershell
# omnivpn-start.ps1 — OmniVPN 前台启动 wrapper（小欧 2026-11-12）
# 只做两件事：把只读区的 config.yaml 播种到可写数据区；前台阻塞运行内核。
# 禁 Start-Process：后台化会让框架拿到的 PID 秒退、树杀也杀不到内核。
$ErrorActionPreference = 'Stop'
# 钉死输出编码：5.1 重定向到管道时默认按 OEM(936) 走，与清单 spec.encoding=utf-8 冲突必乱码
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
$OutputEncoding = [System.Text.Encoding]::UTF8
$data = $env:OMNI_SERVICE_DATA
if (-not $data) { Write-Output '[FAIL] OMNI_SERVICE_DATA 未注入'; exit 2 }
New-Item -ItemType Directory -Force -Path $data | Out-Null

$exe  = Join-Path $PSScriptRoot 'mihomo\mihomo-slim.exe'
$conf = Join-Path $PSScriptRoot 'mihomo\config.yaml'
if (-not (Test-Path $exe))  { Write-Output '[FAIL] 缺少 mihomo\mihomo-slim.exe'; exit 3 }
if (-not (Test-Path $conf)) { Write-Output '[FAIL] 缺少 mihomo\config.yaml'; exit 4 }

# 只在数据区缺失时播种：之后用户在数据区调参不会被覆盖
if (-not (Test-Path (Join-Path $data 'config.yaml'))) {
    Copy-Item $conf (Join-Path $data 'config.yaml')
}

Write-Output "[INFO] mihomo -d $data"
& $exe -d $data          # 前台阻塞，内核退出即 wrapper 退出
exit $LASTEXITCODE
```

> 已核：`mihomo/config.yaml` 无 geoip/rule-provider 之类相对资源引用（只有 port/socks-port/mode/controller/proxies/groups/rules），播种到数据区不会断链。

**13.3.4 动作脚本改造（5 个现有 bat 同构改造 + 1 个新增 exit-probe.bat）**

以 `rebuild-pool.bat` 为例（`proxy-on/proxy-off/proxy-switch/update-pool-quick` 四只同构）：

改造前：

```bat

echo  rebuild node pool: 11 steps (~15-20 min)
echo ============================================

```

改造后：

```bat
@echo off

exit /b %RC%
```

三条改动缺一不可：**去 `pause`**（无头会永久挂起）、**`exit /b %RC%`**（`pause` 会把退出码重置为 0，成败失真）、**`[STEP]/[OK]/[FAIL]` 前缀**（UI 高亮与成败汇总的唯一依据）。`proxy-switch.bat` 内含两段 ps1（switch + 轻量巡检），按第二段的退出码判定。

**新增 `exit-probe.bat`**（现有 `exit_probe.py` 无 bat 入口，动作必须经 `actions[].command` 指向一个可执行文件）：

```bat
@echo off
chcp 936 >nul
cd /d "%~dp0"
set PYTHONIOENCODING=gbk
echo [%TIME:~0,8%] [STEP] exit-probe 开始
python "%~dp0exit_probe.py"
set "RC=%ERRORLEVEL%"
if "%RC%"=="0" (echo [%TIME:~0,8%] [OK]   exit-probe 完成) else (echo [%TIME:~0,8%] [FAIL] exit-probe 失败 rc=%RC%)
exit /b %RC%
```

`set PYTHONIOENCODING=gbk` 与 `actions[].encoding: "gbk"` 配对（13.3.6）：**动作声明一种编码，全链路就必须只有一种**。

**13.3.5 产物目录改指数据区（3 处 Python + 2 处 ps1）**

```python
# 改造前（nodepool/_survey_buckets.py:21、_verify_nodes.py:25）
WORK_DIR = os.path.join(os.path.dirname(SCRIPT_DIR), "log")
# 改造后：优先数据区，人工直跑（无 env）时回落原地，保持可双击
_data = os.environ.get("OMNI_SERVICE_DATA")
WORK_DIR = os.path.join(_data, "log") if _data else os.path.join(os.path.dirname(SCRIPT_DIR), "log")
os.makedirs(WORK_DIR, exist_ok=True)
```

`exit_probe.py` 的报告目录、`rebuild-pool.ps1`/`update-pool-quick.ps1` 的写文件路径同法（ps1 用 `$env:OMNI_SERVICE_DATA`，为空则回落 `$PSScriptRoot`）。**原则**：脚本既能被框架托管，也能人工直跑，二者共用一套相对定位。

**13.3.6 中文编码（这是最容易翻车的一条）**

`"encoding": "gbk"` 的依据是 bat 里的 `chcp 936`——**只对 6 个 bat 动作成立**，故它们是**动作级** `actions[].encoding`；服务级 `spec.encoding` 是 `utf-8`，因为启动链是 `powershell.exe` wrapper + mihomo（前者已在脚本里钉死 UTF-8 输出，后者是 Go 输出 UTF-8），日志按服务级解码。这两层不能合并（7.2.5）。

第二层坑（PowerShell 5.1）：重定向到管道时它默认按 OEM 代码页（中文机器 = 936）编码自己的输出，**并且用同一代码页去解码子进程 mihomo 的 UTF-8 输出**——两头都错。定案由 wrapper 自己钉死（`[Console]::OutputEncoding` + `$OutputEncoding`，见 13.3.2），框架不解码猜测。

第三层坑：`exit-probe.bat` 若调用 Python，重定向到管道时 Python 的 stdout 编码可能是 UTF-8 → 与 gbk 解码冲突出现乱码。定案：**Python 型动作在 bat 里显式钉死 `set PYTHONIOENCODING=gbk`**，保证"动作声明一种编码 + 全链路一种编码"；`exit_probe.py` 的 `print` 不做二次编码处理。

**13.3.7 验收（逐条可执行）**

1. 启动 → starting → 30s 内 running；`Get-NetTCPConnection -LocalPort 7890` 为 Listen；
2. 停止 → 内核与 wrapper 双进程都消失（`Get-Process mihomo-slim, powershell`），7890 释放；
3. `~/.omniagent/services/omnivpn/config.yaml` 存在（播种生效），`cache.db` 也在数据区；
4. 点 [切换出口]（服务未启动时）→ 按钮置灰或 409 报"需先启动"；
5. 点 [轻量巡检] → 该服务 Tab 的 C5 动作输出区出现 `[STEP]` 行，结束后有 `[OK]`/`[FAIL]` 与汇总，**中文无乱码**；
6. 点 [重建节点池] → 弹二次确认（confirm:true）→ 输出逐行追加 → 终态可见；
7. 手工把某个 bat 改回带 `pause` → 动作在超时后判 failed 且进程被树杀（7.2.1 的框架兜底生效）；
8. 关闭 backend → mihomo 仍存活；重启 backend → 该服务的瓦片与 Tab 直接显示 `running`（收养成功）。

### 13.4 两个样板对框架的反向要求（框架没做到就打不通）

| 框架能力 | 被哪个样板用到 | 缺了会怎样 |
|---------|--------------|-----------|
| `OMNI_SERVICE_DATA` 创建 + 注入 | omnivpn wrapper、产物目录 | 内核写不了 cache.db，启动即失败 |
| `logs.kind=stdout` 代收落文件 | 两个样板 | 页面无日志，P1 的 C6 段空 |
| 编码双层解码（服务级默认 + 动作级覆盖） | omnivpn（服务 utf-8 / 动作 gbk） | 动作输出区乱码 |
| 动作任务表 + 超时树杀 | rebuild_pool / exit_probe | 长动作无法给进度，卡死拖全站 |
| `requires_running` 前置判定 | 4 个 VPN 动作 | 服务未起就能点，动作必失败 |
| 端口释放确认 | 两个样板 | "停止"变假绿，用户不敢信 |

## 十四、边界与明确不做

前述各项设计风险（Job 继承连杀、发布态目录只读、打包链缺目录、无头挂起、编码混流、长动作阻塞事件循环、清单坏文件、孤儿收养误判、端口占用、慢启动误判）**都已在对应章节给出定案，不在此重复追踪**。本章只留框架**不承诺**的范围——是划界，不是待办：

| 边界 | 说明 |
|------|------|
| 不防人工双击 bat | 单实例只保证被框架托管的实例；人工直跑的进程不接管、不抢占端口，启动前置检查发现端口被占即 failed 报因 |
| 不做服务间依赖编排 | 当前两服务无依赖，引入 depends_on 拓扑即过度设计 |
| 不做资源限额 | Windows 无低成本 cgroup 等价物 |
| 不做多机 / 远程管理 | 框架定位本机宿主 |
| 不做配置编辑 UI | 清单是文件、git 管理，不造第二个配置真源 |
| 不做清单安全沙箱 | `ext_service` 是本机可写代码目录，能写它就能执行任意程序（与插件同源的信任边界），靠文件系统权限与人工审阅，沙箱化成本远高于收益 |
| 不做仪表盘 / 趋势图 | 服务页是**异常出口**，不是运维大屏；需要趋势时看日志与动作留档，不在本页画图（4.3.6 已禁图表） |
| 不做"能力目录 / provides" | 支撑服务不参与对话链路，声明"我提供什么模型/出口"对本层无消费方，属镀金（将来 L2 集成服务再议，见 2.5） |
| 不做业务功能联动 | 不与对话、任务、模型路由耦合；服务页只管"活着没有、能不能用"，业务降级由 Agent 侧自行决定 |
| 不管 L2 集成服务 | 工具 / MCP / 插件的生命周期跟随会话，由 Agent runtime 调度（2.5）；本框架只到 P2 提供只读状态上报，不接管启停 |

## 十五、验收标准

1. **自动识别**：在 ext_service 下新建一个含合法 service.json 的服务目录，点 ⟳ 刷新后页面多出一张瓦片与该服务的 Tab（热扫描）；移除目录后两者一起消失，且运行中的实例被先停后摘。
2. **启停闭环**：opencli_gateway、omnivpn 均可页面启动 → starting→running 迁移可见 → 健康延迟展示 → 页面停止 → 端口确认释放。
3. **健康语义**：人为提供一个"启动慢"的服务（宽限内未就绪），验证宽限期防抖生效不误判；人为提供一个 health 声明 tcp/http 但"起进程不开端口"的服务，验证按期转 failed 而非假 running。
4. **Job 隔离（必须打包态执行）**：打包版服务 running 时关闭 backend，服务进程 PID 仍存活 + 端口仍监听；重启 backend 后孤儿收养恢复 running。**开发态无 Job，此条在 dev 下必然绿，不构成验证**（9.4）。
5. **动作**：OmniVPN 页面执行换桶/巡检/出口体检，输出在该服务 Tab 的 C5 可见；未声明动作被 403；`requires_running` 未满足时 409 且前端置灰并注明原因。
6. **防御性**：放一个非法 JSON 清单，对应瓦片显示灰虚线 + `!`、其 Tab 显示 error 原文，其余服务管理不受影响；运行中把某服务清单改成非法 → 仅该服务转 invalid，其余不动。
7. **接入契约**：OmniVPN 巡检动作在 C5 可见 `[STEP]/[OK]/[FAIL]` 与成败汇总，中文无乱码；人为构造含 `pause` 的脚本验证超时树杀生效（不永久挂起）。
8. **发布态可用（阶段一~三必验，dev 通过不算）**：打包 exe 启动后，`ext_service/` 出现在 exe 同级，页面瓦片区与 Tab 齐全，服务可启停；数据区生成 `services/<id>/`。
9. **能力闸门**：放一个 `kind=http-endpoint` 的清单（如某外部端点），其 Tab 内**不渲染**启停按钮，只显示状态与清单信息——验证 capabilities 闸门（4.3.4 第一维）。
10. **人工裁决闭环**：删掉 runtime 快照但让端口保持监听 → 该服务瓦片转灰、其 Tab 转 `unknown` → [接管] 后转 running、[终止] 后端口释放并转 stopped。
11. **两个样板逐条过**：按 13.2.4（gateway 5 条）、13.3.7（omnivpn 8 条）全部通过，视为样板验收完成。
12. **多服务共存与切换（4.3.6）**：同时有 4 个以上服务（含 1 个 failed、1 个 invalid）→ 瓦片区一服务一张小卡、Tab 与瓦片都按 name 字典序**永不重排**；点某 Tab 的[停止] 时其它 Tab 不转圈（一 Tab 一数据源）；在 A 服务跑长动作后切到 B 服务，A 任务仍在跑、切回 A 输出连续（不串台）；点瓦片与点 Tab 落到同一个服务；全程不需要打开任何浮层或二级页面。
13. **自愈闭环 A1 离场（必须打包态）**：`presence=away` 时 `taskkill` 掉服务进程 → 15s 内自动回到 running，页面不刷新即可见（瓦片与 Tab 同步），C7 记一条 `heal` 事件；把 `spec.command` 改成不存在的 exe → 按退避重试到上限后停在 `failed(crashloop)`，C1 显示"已重试 3 次 / 自愈已暂停"；人工 [停止] 后等 60s **不再自动起**。
14. **自愈闭环 A2 在场（必须打包态）**：对话正在流式输出时 `taskkill` 服务 → 当前这轮不中断（或给出明确降级提示而非静默超时），会话结束后 60s 内自愈回 running；`heal_paused` 打开时不重启，C1 明确显示"自愈已暂停"。
15. **按需启动 `ensure`（2.6）**：`activation=on_demand` 的服务在 stopped 下调用 `POST /ensure` → 起进程并等到 running 才返回；running 下重复调用 → 立即返回且不重启（幂等）；starting 中调用 → 等到终态返回。
16. **只写清单接入（阶段一硬指标）**：新建一个最小服务（如 `python -m http.server`），**只写 `service.json`、不改任何框架代码**，30 分钟内页面出现瓦片与 Tab 并可启停、健康转绿；达不到则不许进阶段二。
17. **接入标准符合性（7.7）**：两个样板按必须 4 项（去交互 / 前台运行 / 产物落数据区 / 退出码透传）逐条核对；缺项必须**在页面可见降级**而非静默——清单 `health.check_type` 为 `tcp`/`process`（即服务无 `/healthz`）时 C1 标注"仅端口探测"，未写 `status.json` 时不给业务指标；有 `/healthz` 与 `/shutdown` 的服务，健康判定与停止路径必须走它们（日志可见对应请求）。

## 十六、扩展路径：MCP / 插件 / 更多 kind

### 16.1 kind 注册与开闭原则

新增服务形态 = 新增一个执行器文件 + 清单 schema 的 spec 分支，框架其余零改动（对扩展开放、对修改封闭）。**当前只做 L1 支撑服务（2.5）**：`local-process` 在阶段一落地，其余 kind 均为扩展预留（含将来的 L2 集成服务 / L3 远端监控）。当前已知扩展：

| kind | 生命周期语义 | 能力集 | 接入时机 |
|------|-------------|--------|---------|
| `local-process` | Popen+树杀+健康探测 | 全量 | 阶段一 |
| `http-endpoint` | 无进程所有权，纯健康监控 | status/logs/actions | 阶段四 |
| `mcp-server` | stdio=宿主拉起+进程存活+初始化握手探测；http=端点探活 | 连接管理+启停（stdio） | 阶段五 |
| `plugin` | 无进程，启用/禁用状态位 | 仅 enable/disable（**用 start/stop 承载该语义，复用状态机与按钮，前端零改动**，见 9.6.4） | 阶段五 |

### 16.2 MCP 的特别说明

stdio 型 MCP 的"管理"与进程型服务有本质差异：MCP 客户端按会话拉起/关闭子进程。框架若"启动"一个 stdio MCP，实际是做一个**常驻宿主**（拉起子进程并保持，供 MCP 客户端连接）。其健康探测 = 进程存活 + MCP initialize 握手成功（协议级健康，比端口探测更准确）。Streamable HTTP 型 = http-endpoint kind 的直接复用（探活目标换成 MCP 端点）。结论：MCP 可以统一管理，但必须以独立 kind 承接，禁止硬塞进 local-process。

### 16.3 插件的特别说明

插件无进程诉求，管理语义退化为"注册表中的启用/禁用状态位 + 页面统一呈现"。接入后用户视角完全统一（都在服务页以 Tab 呈现，启用中/已禁用一眼可见），实现视角各走各的执行器——这正是"集中监控、分散实现"的完整体现。**按钮复用 start/stop**（语义=启用/禁用），不新造 enable/disable 按钮与 API：框架的状态机、锁、反馈三拍、Tab 内容七段全部原样可用，这是扩展性最省钱的做法。

### 16.4 对外开放的前提（不在当前范围）

路线是**先自研、后开放**（1.4）。开放需要三样东西先就位：

1. **清单 schema 与 7.7 接入标准可对外**：外部作者只读这两份就能接入，不需要读本项目代码；
2. **契约版本与废弃策略**：schema 带版本号，字段废弃给窗口期，否则第三方服务会随框架升级集体失效；
3. **安全边界写清**：`ext_service` 可写即可执行，不提供沙箱（第十四章），开放前必须先有准入与审阅流程。

当前只做第 1 项（随阶段一文档化），第 2、3 项等真有第三方接入者再议。
