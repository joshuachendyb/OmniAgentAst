## 一、背景与问题

### 1.1 现状

本系统目前有两个常驻服务，均游离在系统之外，靠手工双击 .bat/.ps1 启停：

| 服务 | 目录 | 启停方式 | 现状问题 |
|------|------|---------|---------|
| opencli 网关（opencode2api） | `opencli_gateway/` | start.bat / stop.bat | 位置固定、名称写死，前端无任何展示；是否在跑全靠记忆 |
| OmniVPN（mihomo 代理） | `OmniVPN/` | proxy-on/off/switch bat、rebuild-pool、update-pool-quick 等 | 启停动作多、语义复杂（换桶/巡检/重建/出口体检），无统一入口 |

问题本质：**服务的"存在性、生命周期、健康状态"三样东西，系统不知道、页面看不到、框架管不了**。后续还要接入 MCP server、插件等更多服务形态，若继续"一个服务一套手工办法"，每接一个就要重写一遍页面与逻辑。

### 1.2 目标

设计一套**服务管理框架**，实现用户三问：

1. 新服务按某种规矩添加后，服务页面**自动识别**出来；
2. 页面上可**启动、停止**；
3. 启动后可**监控**查看服务状态（是否健康、端口、日志、自定义动作）。

并回答一个方向性问题：插件、MCP 等到底能不能和系统服务**统一管理**，还是必须分散管理。

## 二、需求定案（三思三省）

### 2.1 一省：要管的到底是什么

两个现有服务形态差异极大：

- opencli 网关：一个 exe，启动后监听端口，是标准**本地进程型服务**；
- OmniVPN：mihomo 进程 + 一堆运维动作（换桶、巡检、重建池、出口体检），是**进程 + 动作组**的复合体；
- 未来 MCP：可能是本框架拉起的 stdio 子进程，也可能是独立的 Streamable HTTP 端点；
- 未来插件：可能根本没有进程，只是"启用/禁用"的开关。

结论：**"管理"不是一件事，是四件事**——注册（发现）、生命周期（启停）、健康（监控）、动作（运维）。四件事的"框架层"必须统一，四件事的"实现层"因服务形态而异。这就是设计的分界线。

### 2.2 二省：集中还是分散

| 方案 | 描述 | 判定 |
|------|------|------|
| 全分散 | 每种服务自写一套管理代码和 UI | ❌ 重复造轮子，接一个服务重写一遍，违背 DRY |
| 全集中 | 框架假定所有服务都是"进程"，统一 Popen/kill | ❌ 对 MCP HTTP 型、插件型是暴力硬套，语义错位 |
| **集中监控、分散实现** | 框架统一管注册表、状态机、监控、UI；每种形态一个"执行器（executor）"，按 kind 分派 | ✅ 定案 |

定案理由：监督进程的 Popen/树杀/端口探测对"进程型"成立，对"MCP stdio（生命周期由 MCP 客户端会话决定）""插件（无进程，只有启用态）"不成立。所以**框架不能写死任何一种生命周期实现，只能统一生命周期语义**。执行器按 kind 注册进框架，框架对执行器只要求实现 `start/stop/status/health` 的语义契约（接口隔离，ISP）。

### 2.3 三省：新服务"自动识别"的规矩到底是什么

自动识别不能靠猜，必须靠**声明**。业界成熟答案高度一致：

- supervisord 的 `[include] files = /etc/supervisor/conf.d/*.conf`：新程序 = 往 conf.d 放一个文件，主配置零改动；
- systemd 的 `*.service` 单元目录：同构思想；
- Docker Compose 的 services 映射表：声明式定义 + healthcheck 声明。

定案：**drop-in 清单目录**。新服务 = 在应用根的 `ext_service/` 下新建一个服务子目录（内含 `service.json` 清单），框架启动扫描 + 目录变更热扫描，页面自动出现新卡片。零代码、零配置文件改动。这就是用户要的"按某种规矩添加后自动识别"的规矩。清单**锚定应用根**：发布态 = 运行 exe 所在目录，开发态 = 仓库根，两态布局同构（v1.1 修订：原 backend/services.d 方案是开发视角的错置，已废弃）。

### 2.4 底线约束（本仓现实）

- 后端自身已 assign 进 KILL_ON_JOB_CLOSE Job Object（打包版），**它直接 Popen 的子进程会继承同一 Job——backend 退出会连带杀光所有服务**。这是本框架最大的安全坑，设计中必须显式处理（见 9.4）。
- Windows only：树杀用现成 `proc_utils.py`（psutil BFS），不用 taskkill。
- 配置新增键走三同步（config.yaml.example + settings_registry.py + 运行 config.yaml）；本框架的服务清单**不进 config.yaml**，独立走 `ext_service/` 目录（清单是"服务注册"，不是"系统设置"，语义不同源，避免把配置文件变成半吊子注册表）。

## 三、业界取经结论

### 3.1 supervisord — drop-in 目录与生命周期字段

吸收要点：

| supervisord 概念 | 本框架对应 |
|-----------------|-----------|
| `[include] files = conf.d/*.conf` | `ext_service/*/service.json` 目录扫描（目录即服务） |
| `command` + `directory` + `environment` | 清单中的启动命令、工作目录、环境变量 |
| `startsecs`（启动后稳定 N 秒才算 STARTED） | 启动判定引入**稳定期**：进程活着 ≠ 服务就绪 |
| `startretries` / `autorestart` | 重试上限 + 自启策略（框架期先显式手动，P2 再加自启） |
| `stopasgroup` / `killasgroup` | 统一树杀（Windows 下 proc_utils 已覆盖，不暴露选项） |
| `autostart` | 清单声明 `autostart`，框架启动时决定是否拉起（默认 false，避免打包版被动跑服务） |

没有吸收的：supervisord 的事件监听器/优先级组——本框架服务数量是个位数，引入优先级拓扑是过度设计（YAGNI）。

### 3.2 Docker Compose — healthcheck 语义

这是本次最重要的吸收。supervisord 只判断"进程活着"，Docker 判断"服务健康"：

| Docker healthcheck 字段 | 本框架字段 | 用途 |
|------------------------|-----------|------|
| `test` | `health.check_type` + `health.check_target` | HTTP GET 端口路径 / TCP 连端口 / 进程存在 |
| `interval` | `health.interval_seconds` | 健康轮询间隔（默认 10s） |
| `timeout` | `health.timeout_seconds` | 单次探测超时（默认 3s） |
| `retries` | `health.retries` | 连续失败 N 次才判不健康（防抖，默认 2） |
| `start_period` | `health.start_grace_seconds` | 启动宽限期：宽限期内失败不计入 retries（服务冷启动慢是常态） |

**核心语义定案：start 成功 ≠ running。`start` 返回成功只表示"启动动作已受理"，必须健康探测通过才迁移到 running。** 这一条直接决定了状态机设计（见第八章），也是避免"端口还没监听，页面已经绿灯"这种假状态的关键。

### 3.3 MCP transports — kind 分派的依据

MCP 官方定义两类标准传输：

- **stdio**：客户端拉起子进程，stdin/stdout 换行分隔 JSON-RPC —— 进程由"使用方"管理生命周期，框架若拉起它，角色是"宿主"；
- **Streamable HTTP**：独立端点，进程与协议无关 —— 框架角色是"探活监控方"。

对框架的含义：MCP 服务不能硬套"进程型"执行器。stdio 型 MCP 的"启动"= 拉起宿主进程但**不**做 HTTP 探活（探活 = 进程存活 + 初始化握手），HTTP 型 MCP 的"启动"可能根本不属于本框架（进程已在别处，框架只监控）。所以 kind 必须一等公民化，MCP 作为独立 kind 后置到 P2。

### 3.4 其它（PM2 / Windows Services，简查）

- PM2 ecosystem 配置同样是"声明文件 + 统一守护"模式，佐证 drop-in 思路；其 `max_restarts`/`restart_delay` 字段语义并入自启策略（P2）。
- Windows SCM 服务：注册成本高、需要管理员权限，与本系统"随包携带的轻量服务"定位不符，不采用；但其"服务状态查询与控制分离"（QueryServiceStatus / ControlService）佐证了**状态查询与控制命令分离**的 API 设计。

## 四、总体设计：后端架构与前端 UI 架构对应

### 4.1 架构判词与三问定案

一句话架构判词：

> **注册表、状态机、健康监控、UI 是公共的；"怎么启动、怎么停止、怎么探活"是每种 kind 自己的事。**

| 用户问题 | 定案 |
|---------|------|
| 新服务怎么自动识别？ | `<应用根>/ext_service/<service_id>/service.json` drop-in 清单（目录即服务，插件式插拔），启动扫描 + 热扫描，零代码注册 |
| 怎么启动停止？ | 框架按清单 `kind` 分派执行器；local-process 型 = Popen + 树杀；其他 kind 由各自执行器实现 |
| 启动后怎么监控？ | 统一健康引擎按清单 `health` 段轮询；统一状态机输出；UI 统一卡片 + 详情抽屉 |
| 集中还是分散？ | **集中监控、分散实现**。插件/MCP 可以统一"管理"（注册、状态展示、页面呈现），但不统一"实现"（各自执行器）。插件在 P2 接入时是"仅启用/禁用"的能力子集，MCP 是"连接管理"的能力子集 |

### 4.2 后端架构（框架层 + 执行器层）

```
REST 路由层   /api/v1/services/*（_mount() 统一挂载 + 默认 token 鉴权）
     │
框架层（公共，与 kind 无关）
     ├─ 注册表      ext_service 清单扫描 / 热扫描 / invalid 隔离
     ├─ 状态机      stopped/starting/running/stopping/failed/unknown/invalid/disabled
     ├─ 健康引擎    单 asyncio 循环，按各服务 health 段轮询
     └─ 动作任务    白名单动作执行 / 长动作任务表 / to_thread 卸载
     │ 按清单 kind 分派
执行器层（每种形态一个，语义契约 start/stop/status）
     ├─ local-process   Popen(breakaway) + 树杀 + 端口确认
     ├─ http-endpoint   纯监控（不拥有进程）
     └─ (P2) mcp-server / plugin
     │
服务本体      ext_service/<id>/ 内的 exe / bat / 配置（自包含）
```

详设见第五章（架构总图与取舍）、第八章（状态机）、第九章（后端模块与 API）。

### 4.3 前端 UI 架构（页面三层 + 数据层）

```
导航层   NavContent「服务管理」菜单 → /services 路由（lazy）
     │
列表层   卡片网格
     ├─ 状态徽标（一眼看清生死）
     ├─ 基本信息（端口 / 健康延迟 / uptime）
     ├─ 主操作组（启动 / 停止 / 查看过程状态）
     └─ 附加操作组（仅 actions 白名单内的服务才有，如 OmniVPN 换桶/巡检/体检）
     │
详情层   抽屉 = "查看过程状态"的承载
     ├─ 基本信息与最近健康探测
     ├─ 健康时间线 / 日志尾部（P1）
     └─ 动作输出区（[STEP]/[OK]/[FAIL] 透传展示）
     │
数据层   5s 轮询聚合接口 + 动作任务 2s 轮询（document.hidden 暂停）
```

界面示意图见 10.3，详设见第十章。

### 4.4 前后端对应关系（一一映射）

| UI 呈现 | 后端来源 |
|---------|---------|
| 卡片出现 / 消失 | 注册表扫描 + 热扫描（GET /services 列表增减） |
| 状态徽标（绿/蓝/红/灰） | 状态机 `state` |
| 启动 / 停止按钮 | `POST start / stop`（受理式，见 4.5） |
| 过程状态（转圈、延迟、uptime） | 状态机 + 健康引擎（GET /services/{id}） |
| 详情抽屉 | GET /services/{id}（健康历史、日志 P1） |
| 附加操作按钮组 | 清单 `actions` 白名单（POST actions/{action_id}） |
| 动作输出区 | 动作任务表（GET action-tasks，task_id） |
| invalid 红框卡片 | 注册表 invalid 项 `error` |

原则：**UI 上每一个可见元素都必须能指到后端唯一数据源**——没有数据源支撑的 UI 元素不做（防镀金）。

### 4.5 操作模型定案：三主操作 + 附加操作

**主操作（三件套，所有服务统一，框架标配）**：

1. **启动**：受理式——点击即转圈（starting），健康探测转绿才算成；
2. **停止**：受理式——点击即转圈（stopping），端口释放确认才算完；
3. **查看过程状态**：详情抽屉——状态迁移、健康延迟、uptime、动作输出等一切过程信息统一在这里看。

重启 = 停止 + 启动的组合便利（同一状态机路径 stop→start，不新增机制），与主操作同组。

**附加操作（附加功能，按服务声明，不是标配）**：OmniVPN 的换桶 / 巡检 / 出口体检、未来各服务的运维脚本——在清单 `actions` 白名单里声明了 UI 才渲染，不声明就不出现（UI 复杂度只随服务实际能力增长）。

**操作反馈铁律**：任何操作执行入口必须有反馈——

- 点击瞬间：按钮态即变（转圈 / 置灰），禁止"点了没反应"；
- 受理结果：受理成功 / 拒绝（403 / 互斥冲突）立即可见；
- 过程进展：starting→running 迁移、动作输出逐行追加，持续可见直到终态。

### 4.6 UI 设计原则

1. **遵守系统 UI 规范**：菜单进 NavContent 统一数组、路由进 App.tsx 统一 lazy 注册、页面落 `pages/Services/`、逻辑落 `features/serviceManager/`、API 封装走 `services/api/service.api.ts` 与 client.ts 的 `/api/v1` 前缀；组件全部用 antd 既有体系（卡片 / 徽标 / 抽屉 / 按钮 / Modal），不引新 UI 库；
2. **大气简约、信息分层克制**：卡片只放"一眼要看的"（徽标 / 端口 / 延迟 / uptime / 主操作），其余全收进抽屉；配色沿用系统语义色（健康绿 / 异常红 / 进行中蓝），不造新色板；
3. **先不搞复杂**：P0 不做列配置、筛选器、拖拽、主题定制等任何增值交互，默认状态即可用，能不加的控件一律不加（YAGNI）。

设计取舍说明：

- 执行器只放 `svcmanager/executors/` 下按文件分派（kind 数量少，if/elif 分派足够，不建注册表装饰器机制——KISS）；

## 六、服务清单（manifest）规范与自动识别规矩

### 6.1 清单文件规矩（锚定应用根，目录即服务）

- 位置：`<应用根>/ext_service/<service_id>/service.json`；
- **应用根解析**：发布态 = 运行 exe 所在目录；开发态 = 仓库根。唯一解析点 `svcmanager/paths.py::resolve_app_root()`（判别打包/frozen 标志），两态同构，其余模块一律经它取路径；
- **目录即服务**：一个子目录 = 一个服务。目录拷入 = 注册，目录移除 = 注销，天然"插件式插拔"；清单与它指向的 exe/配置/脚本同目录自包含，杜绝"清单指着目录外文件"的悬空引用；
- 清单文件名固定 `service.json`（一个目录一个服务，无需通配命名）；
- service_id = 子目录名，全局唯一，`^[a-z][a-z0-9_]{2,31}$`；
- 编码：UTF-8 无 BOM；
- **路径解析规矩**（清单内一律禁止绝对路径）：`workdir` 缺省 = 服务目录自身；`command`/`logs.path` 等相对路径**先按服务目录解析，再按应用根解析**（两跳次序固定，写死在 paths.py）；
- 运行时快照**不写 ext_service**（发布态 exe 目录可能有写权限限制）：落数据目录（与 SQLite 同源解析点 `~/.omniagent`）；服务目录保持"代码 + 配置 + 清单"自包含语义；
- 非法清单（schema 校验失败、id 冲突、kind 未知）**降级为 `invalid` 状态单独展示，不拖垮整个注册表**（一个坏目录不能让页面全挂——防御性设计）。

### 6.2 清单 schema

```jsonc
// ext_service/opencli_gateway/service.json （示例，路径均相对服务目录）
{
  "id": "opencli_gateway",
  "name": "OpenCLI 网关",
  "description": "第三方 CLI 模型接入协议整形网关（opencode2api）",
  "kind": "local-process",            // local-process | http-endpoint | mcp-server | plugin
  "enabled": true,                     // 总开关：false 时页面显示但禁用操作
  "autostart": false,                  // 框架启动时是否自动拉起（默认 false）

  "spec": {                            // spec 段内容随 kind 而异，schema 按 kind 分支校验
    "command": "opencode2api.exe",     // 相对服务目录解析（ext_service/opencli_gateway/）
    "args": ["--config", "config.json", "--port", "9900"],
    "workdir": ".",                    // 缺省 = 服务目录自身
    "listen_port": 9900,               // 树杀后验证端口释放用；纯监控型没有
    "encoding": "utf-8",               // 动作/日志输出解码声明：utf-8 | gbk（缺省 utf-8；bat 类脚本通常 gbk）——契约 7.2.5
    "stop": { "kind": "http-post", "target": "http://127.0.0.1:9900/shutdown" }   // 可选优雅停止（契约 7.5）；缺省 = 树杀兜底
  },

  "health": {                          // 语义对齐 Docker healthcheck
    "check_type": "http",              // http | tcp | process
    "check_target": "http://127.0.0.1:9900/health",   // http=GET断言2xx; tcp=连端口; process=仅进程存活
    "interval_seconds": 10,
    "timeout_seconds": 3,
    "retries": 2,
    "start_grace_seconds": 20          // start_period 语义：宽限期内失败不计连续失败
  },

  "capabilities": {                    // 能力分级声明（ISP），UI 按此渲染
    "start": true, "stop": true, "status": true,
    "logs": true, "actions": true
  },

  "actions": [                         // 自定义动作（白名单机制，见 9.5；脚本输出约定见契约 7.3）
    { "id": "rebuild_pool",   "label": "重建节点池",  "confirm": true },
    { "id": "update_quick",   "label": "轻量巡检",    "confirm": true },
    { "id": "exit_probe",     "label": "出口体检",    "confirm": false, "timeout_seconds": 900 }
  ],

  "logs": {
    "kind": "file",                    // file | stdout | none（P1 实现 tail；stdout=框架代收服务进程输出落文件）
    "path": "logs/gateway.log"         // 相对服务目录解析
  }
}
```

schema 校验用 pydantic 模型族（`ServiceManifest` + 按 kind 的 `spec` 判别联合），错误信息落注册表 `invalid` 项的 `error` 字段，UI 展示。

### 6.3 首批两个清单

**opencli_gateway**：如上示例，kind=local-process，check_type=http。

**omnivpn**（要点）：kind=local-process，健康探测 `tcp 127.0.0.1:7890`；actions 直接映射现有 bat（proxy-switch / rebuild_pool / update_quick / exit_probe），`exit_probe` 动作输出较长，走"动作任务"异步执行 + 前端拉取结果（见 9.5）。

**首批目录迁移（P0 第一步）**：将现有仓库根的 `opencli_gateway/`、`OmniVPN/` 两个目录 **git mv 迁入 `ext_service/`**，使开发态布局与发布态同构；迁移同时清点仓库内对旧路径的全部引用（脚本/文档/代码）并同步更新，OmniVPN 内部脚本均为目录内相对引用，迁移后自洽。

OmniVPN 换桶/巡检等动作本质是**运维脚本**而非服务启停，action 机制让它们首次有了统一 UI 入口——这是本框架对现状最直接的增益之一。

### 6.4 自动识别流程

```
框架启动 → 扫描 ext_service/*/service.json（resolve_app_root 锚定）
        → 逐个 pydantic 校验 → 合法项入注册表 / 非法项入 invalid
        → 按 runtime 快照做孤儿收养判定
        → autostart=true 且 enabled 的服务排队 start
运行期   → watchdog 线程监控 ext_service 变更
        → 新建子目录(含合法 service.json)=注册出卡片
        → 目录删除=先 stop 在跑实例再注销摘卡
        → 清单修改=差分热更新（不打断运行态，标 config_dirty）
```

热扫描差分规则：id 相同且清单内容 hash 未变 → 不动（不打断运行中服务）；内容变了 → 保留运行态，标记"配置已变更待生效"；目录消失（含 id 消失）→ 树杀后摘除。

## 七、服务接入契约（UI 对接规范）

### 7.1 为什么需要契约

两个现有服务的信息出口都是**面向 console** 的：bat 脚本 echo 给人看、退出码语义随意、中文输出走 GBK、依赖控制台特性。UI 对接需要的是**机器可读**：成败怎么判、进度怎么看、状态怎么取、日志在哪。若不定规范，每个服务接入时各改各的，格式漂移、重复踩坑；定了契约，后续任何新服务照单编写即可对接（这正是"框架"对"服务"的第二只手——第一只是第六章的发现机制，第二只是本章的信息契约）。

契约分四级，**达标解锁、渐进接入**：L0 即入册，不因不达标把旧服务挡在门外。

| 级别 | 名称 | 要求 | 现有两服务改造量 |
|------|------|------|------------------|
| L0 可纳管 | 清单 | service.json 合法即可被框架管理（启停/进程监控） | 零改造（写清单即达 L0） |
| L1 可监控 | 健康与日志 | 健康探测通道（http / tcp / process 三选一）+ 文件日志（或声明 logs.kind=stdout 由框架代收落文件） | 小（OmniVPN 用 tcp:7890 即达 L1；网关若有 health 路由则用 http，否则 tcp） |
| L2 可运维 | 动作与自报 | 动作脚本符合 7.3 约定；可选 status.json 自报（7.4） | 中（bat 输出规范化、退出码补齐） |
| L3 原生 | 管理面 API | 服务自带 /status、/actions HTTP 管理端点 | 远期方向，本期不要求 |

UI 能力渲染与级别挂钩：L0 只有启停与基础状态；L1 解锁健康延迟与日志；L2 解锁动作输出区与自报指标面板。

### 7.2 无头运行约束（硬性，所有级别适用）

服务被框架拉起时运行在 `CREATE_NO_WINDOW` 无控制台环境，契约硬性要求（违者属服务 bug，不属框架兼容项）：

1. **禁止任何交互式输入**：`pause`、`set /p`、stdin 读取一律禁止——无控制台下会**永久挂起**（console 转 UI 最典型事故形态）；框架侧动作任务另设超时上限双保险（见 9.5）；
2. 禁止依赖控制台特性：标题、颜色、`cls`、console API；
3. 禁止任何弹窗（MsgBox 等）；报错走退出码 + 日志；
4. 单实例语义靠 listen_port 天然互斥即可，不要求服务自实现互斥；
5. **编码显式声明**：manifest `spec.encoding`（utf-8 | gbk，缺省 utf-8），框架按声明解码动作输出与日志——Windows bat 默认 GBK 是历史现实，声明制而非猜测制。

### 7.3 动作脚本约定（L2）

console 现状：脚本输出给人看，成败全凭肉眼。UI 对接三条约定：

1. **退出码是成败唯一真源**：0=成功，非 0=失败；脚本任何失败分支必须 `exit` 非 0。框架以退出码定动作任务终态，stdout 只做展示；
2. **输出行半结构化**（人读优先，机器轻解析，不做 JSON 深解析——KISS）：

   ```
   [HH:mm:ss] [STEP] 正在拉取订阅源 1/9 ...
   [HH:mm:ss] [OK]   15001 条已入库
   [HH:mm:ss] [FAIL] 源 3 超时，跳过
   ```

   进度行打 `[STEP]`，结果行打 `[OK]/[FAIL]`；框架原样透传到 UI 动作输出区，仅按 `[OK]/[FAIL]` 前缀做高亮与成败汇总（一行正则的解析量）；
3. **长动作必须报进度**：预期 >30s 的动作按阶段打 `[STEP]` 行，UI 展示"最近一步"；清单 `actions[].timeout_seconds` 声明超时上限（缺省 600s），超时树杀动作进程判 failed。

现有脚本对照：OmniVPN 的 rebuild-pool / update-pool-quick 等输出本就接近该格式，补齐前缀与退出码即达 L2，改造量可控。

### 7.4 自报状态约定（L2 可选：status.json）

对非 HTTP 型服务（如 mihomo），"端口活着"之外还有丰富状态（当前出口、节点池计数、最近巡检时间）需要通道：

- 服务进程自行周期写 `<服务目录>/status.json`（间隔建议 ≥5s，**原子写**：临时文件 + replace，防读到半截）；
- 字段外框契约固定，内容自由：

  ```jsonc
  { "updated_at": "2026-11-12T14:00:00", "state": "running",   // running | degraded | ...
    "metrics": { "exit_node": "...", "pool_alive": 132, "pool_dead": 7 }   // 各服务自定义
  }
  ```

- 框架读取展示在详情抽屉；`updated_at` 超过 3× 写入间隔 → UI 标"状态过期"，不静默展示旧数据（防御性）；
- 写 status.json 是服务自己的事，框架只读不写——单写者，无并发问题。

### 7.5 停止语义约定

- 优雅停止优先：manifest `spec.stop` 可声明 `{"kind": "http-post", "target": ".../shutdown"}`；服务有 HTTP 面时推荐提供 `/shutdown`；
- 树杀是兜底而非首选：声明了优雅停止的，先 POST /shutdown，超时 5s 再树杀；未声明的直接树杀（proc_utils psutil BFS 已保证子进程无残留）；
- 服务方义务：收到停止信号后自行清理子进程/临时文件，保证**重入安全**（可被再次 start，不依赖上次的现场）。

本约定与 8.2 状态机 stop 语义、9.3 停止流程共用同一套判定，三处不各说各话。

### 7.6 新服务编写速查（给后续服务编写者）

```
1. 建 ext_service/<id>/ 目录，写 service.json                    → L0 完成，页面出卡片
2. 有监听端口 → health 用 tcp；有 HTTP → 提供 /health 路由用 http  → L1 健康绿灯+延迟
3. 日志落文件（或声明 logs.kind=stdout 由框架代收）               → L1 日志可见
4. 动作脚本按 7.3 改造（[STEP]/[OK]/[FAIL] + 退出码 + encoding 声明）→ L2 动作输出区
5. 想展示丰富状态 → 周期写 status.json                            → L2 自报指标
6. 全程遵守 7.2 无头约束（禁交互/禁弹窗/禁控制台依赖）
```

P0 实施时本章另落独立《服务接入契约规范》速查文档，供后续服务编写者直接引用，不要求读整篇设计。

## 八、生命周期状态机

### 8.1 状态集

```
                   start(受理)                health 通过
  stopped ──────────────▶ starting ─────────────────────▶ running
     ▲                        │  │                            │
     │ stop(受理)             │  │ health 连续失败             │ stop(受理)
     │                        │  ▼ 超过宽限+retries             ▼
     ├──▶ stopping ◀──────────┘  failed                stopping
     │         │                                            │
     │         │ 树杀完成+端口释放确认                        │
     ▼         ▼                                            ▼
   stopped ◀───────────────────────────────────────────────── stopped
```

全状态集：`stopped / starting / running / stopping / failed / unknown / invalid / disabled`

| 状态 | 含义 | 进入条件 |
|------|------|---------|
| stopped | 未运行 | 初始 / stop 完成确认 |
| starting | 已发启动指令 | start 受理后；超时上限（start_grace + 2×interval）未就绪则判 failed |
| running | 健康通过 | 连续 retries 次探测失败会退回 failed |
| stopping | 停止中 | stop 受理后；树杀 + 端口释放确认后归 stopped |
| failed | 启动失败或健康劣化 | starting 超时 / running 时健康连续失败 |
| unknown | 存在性不明 | 孤儿收养前、runtime 快照丢失、探测通道异常 |
| invalid | 清单非法 | schema/冲突校验失败（附 error） |
| disabled | enabled=false | 清单总开关关闭 |

### 8.2 关键语义定案

1. **start ≠ Popen 成功**（Docker/K8s readiness 语义）：start 接口受理后立即返回 `starting`，健康引擎在宽限期后开始探测，通过才转 running。前端按钮态按 `starting` 渲染（转圈），不等 running 才反馈。
2. **健康连续失败防抖**：interval + retries + start_grace 三参数共同决定"慢启动不被误杀"（mihomo 首次拉起要加载配置与测速，天然需要宽限期）。
3. **stop 是验证式停止**：语义与契约 7.5 同源——声明 `spec.stop` 的先优雅 POST /shutdown（超时 5s），未声明直接树杀（proc_utils psutil BFS）→ 确认 PID 消失 → 确认 listen_port 释放 → 才置 stopped。任何一步未确认保持 stopping 并告警。
4. **failed 不自动重启**（P0/P1）：自启/自动拉活（supervisord autorestart、PM2 max_restarts 语义）放 P2，避免初期故障回环难以观测。
5. **操作互斥**：每服务一把 asyncio 锁，start/stop/restart 互斥；动作（action）不与服务互斥（换桶不重启服务时允许并发），但同类动作自身串行。

### 8.3 restart 语义

`restart = stop → start`，状态机走完整路径，不做原地重启捷径（保证每次都经过健康验证）。

### 8.4 状态输出

单一状态快照结构（GET 接口直接返回，前后端契约单一真源）：

```jsonc
{
  "id": "omnivpn",
  "name": "OmniVPN",
  "kind": "local-process",
  "state": "running",
  "detail": { "pid": 12345, "listen_port": 7890, "uptime_seconds": 3721,
              "health": { "last_probe_at": "...", "latency_ms": 23,
                          "consecutive_ok": 41, "last_error": null } },
  "capabilities": { "start": true, "stop": true, "status": true, "logs": true, "actions": true },
  "actions": ["rebuild_pool", "update_quick", "exit_probe"],
  "config_dirty": false,        // 清单已变更待生效
  "error": null
}
```

### 8.5 孤儿收养（adopt）

backend 重启后，服务子进程可能仍在跑（上一轮 backend 退出但 Job 隔离生效——这正是设计目标，见 9.4）。处理：

1. 启动扫描后，对每个清单项：若 runtime 快照有 PID 且该 PID 仍存活且进程命令行与清单 `spec.command` 匹配 → 收养：登记 PID、恢复健康轮询、状态转 running（探测通过后确认）；
2. PID 存活但命令行不匹配 → 不收养，按 stopped 处理，日志告警（防止把无关同名进程误收）；
3. 快照丢失但 listen_port 有监听 → 状态置 `unknown`，UI 给"接管/终止"双按钮，让用户显式裁决（不猜）。

## 九、后端框架设计

### 9.1 模块落位

新子域 `backend/app/services/svcmanager/`（services 下已有 agent/chat/task/… 子域，svcmanager 不撞名）。文件级职责单一：

| 文件 | 职责 |
|------|------|
| `manifest.py` | pydantic 清单模型 + 校验（判别联合按 kind） |
| `paths.py` | 应用根/服务目录解析唯一入口（frozen 判别 + 两跳路径次序），registry/executors/actions 一律经它取路径 |
| `registry.py` | ext_service 扫描/差分/注册表存储 + 目录 watchdog |
| `state_machine.py` | 状态迁移与合法性断言（非法迁移抛错并告警） |
| `health_engine.py` | 单 asyncio 循环轮询全部服务健康 |
| `runtime_store.py` | 运行时快照落盘/加载（孤儿收养数据源） |
| `executors/base.py` | 执行器契约：`async start/stop/status` |
| `executors/local_process.py` | Popen（breakaway）+ 树杀 + 端口释放确认 |
| `executors/http_endpoint.py` | 纯健康监控（不拥有进程，无 start/stop） |
| `actions.py` | 动作白名单执行 + 动作任务表（异步长动作） |
| `routes` → `app/api/v1/service_routes.py` | REST API |

### 9.2 API 设计（/api/v1/services）

| 方法/路径 | 语义 |
|-----------|------|
| `GET /api/v1/services` | 全量状态快照列表（前端 5s 轮询此接口） |
| `GET /api/v1/services/{id}` | 单服务详情（含健康历史尾部） |
| `POST /api/v1/services/{id}/start` | 受理启动（返回 starting，不等待） |
| `POST /api/v1/services/{id}/stop` | 受理停止 |
| `POST /api/v1/services/{id}/restart` | 受理重启 |
| `POST /api/v1/services/{id}/actions/{action_id}` | 执行自定义动作（同步短动作直接返回；长动作返回 task_id） |
| `GET /api/v1/services/{id}/logs?tail=N` | 日志尾部（P1） |
| `GET /api/v1/services/action-tasks/{task_id}` | 长动作进度/结果（P0，随动作机制一起落） |

鉴权走 `_mount()` 默认 token 机制，无新增豁免。所有写操作（start/stop/restart/action）请求体带 `confirm: true` 才受理（破坏性动作双保险，与清单 `confirm` 声明呼应）。

### 9.3 启动器细节（local-process）

```
启动流程（executors/local_process.py）：
1. 前置检查：enabled / 状态互斥锁 / 端口未被占用（占用且无法收养 → 直接 failed 并注明）
2. 构造子进程：CREATE_BREAKAWAY_FROM_JOB | CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW
3. stdout/stderr 重定向：logs.kind=stdout 时由框架代收落日志文件（契约 7.1 的 L1 承诺）；kind=file 时服务自写，框架只读
4. 登记 PID → 写 runtime 快照 → 转 starting
5. 健康引擎接管：宽限期后按 interval 探测，通过 → running
```

停止流程（与契约 7.5 同一套判定）：

```
1. 取互斥锁 → 转 stopping
2. 声明了 spec.stop 的先优雅停止：POST /shutdown，超时 5s；未声明直接进第 3 步
3. proc_utils.kill_process_tree(pid)   （psutil BFS，零 taskkill）
4. 等待树杀完成确认（poll pid 不存在，上限 10s）
5. listen_port 释放确认（netstat 类查询，上限 10s）
6. 清 runtime 快照 → 转 stopped；任一步未确认 → 保持 stopping + 告警事件
```

### 9.4 安全关键设计：Job Object 隔离（必须项）

**坑**：打包版 backend 已被 `win_job_object.py` 收编进 KILL_ON_JOB_CLOSE Job。Windows 规则：子进程默认**继承**父进程所在 Job。后果链：backend Popen 服务 → 服务进 backend 的 Job → **backend 被关闭（或崩溃）→ Job 句柄关闭 → KILL_ON_JOB_CLOSE 把所有服务一起杀光**。这与"服务独立于 backend 生存"的目标直接冲突。

**解法（按优先级）**：

1. 首选 `CREATE_BREAKAWAY_FROM_JOB` 创建标志：前提是 Job 允许 breakaway（`JOB_OBJECT_LIMIT_BREAKAWAY_OK`）。本仓 Job 创建处需同步加该允许位——这是一处对现有 Job 初始化的必要增强；
2. 若 breakaway 被拒（策略环境），退路：为服务子进程 `AssignProcessToJobObject` 到框架自建的**独立** Job（无 KILL_ON_JOB_CLOSE，仅用于统一收集子进程句柄便于枚举），参考 `safety/sandbox/job_object.py::assign` 模式；
3. 双保险兜底：runtime 快照落盘。即使发生意外连杀，下次启动孤儿收养/unknown 流程仍能正确呈现事实。

设计定案：方案 1+3 落 P0，方案 2 作为兼容退路编码进 local_process.py（try breakaway → 失败则独立 Job assign）。

**这条不落实，框架就是负资产**——它会制造"关 backend 连带杀服务"的新故障模式。评审时作为一票否决项核查。

### 9.5 自定义动作机制

- 动作必须在清单 `actions` 白名单声明，路由层 403 拒绝未声明动作（不给任意命令执行面）；
- 动作执行 = 以清单 `spec.workdir` 为 cwd 调用对应 bat/命令，`CREATE_NO_WINDOW`，stdout/stderr 捕获并按 `spec.encoding` 解码（契约 7.2.5）；动作任务带超时上限（清单 `actions[].timeout_seconds`，缺省 600s），超时树杀动作进程并判 failed（对无头环境下脚本意外交互挂起的双保险，契约 7.2.1 的框架侧兜底）；
- 短动作（<30s 预期，如 proxy switch）同步返回输出尾部；
- 长动作（rebuild_pool / update_quick / exit_probe）走动作任务表（内存 dict + 落盘），返回 task_id，前端轮询；动作任务不进事件循环，用 `asyncio.to_thread` 卸载（教训来自 shell_engine 卡死事故：同步长任务跑在事件循环里会僵死全服务——这是本仓已定案的铁律）；
- 动作期间服务状态机不动（动作 ≠ 生命周期变更）；动作失败不影响服务 running 态，结果以动作任务状态呈现。

## 十二、扩展路径：MCP / 插件 / 更多 kind

### 12.1 kind 注册与开闭原则

新增服务形态 = 新增一个执行器文件 + 清单 schema 的 spec 分支，框架其余零改动（对扩展开放、对修改封闭）。当前已知扩展：

| kind | 生命周期语义 | 能力集 | 接入时机 |
|------|-------------|--------|---------|
| `local-process` | Popen+树杀+健康探测 | 全量 | P0 |
| `http-endpoint` | 无进程所有权，纯健康监控 | status/logs/actions | P1（轻） |
| `mcp-server` | stdio=宿主拉起+进程存活+初始化握手探测；http=端点探活 | 连接管理+启停（stdio） | P2 |
| `plugin` | 无进程，启用/禁用状态位 | 仅 enable/disable | P2 |

### 12.2 MCP 的特别说明

stdio 型 MCP 的"管理"与进程型服务有本质差异：MCP 客户端按会话拉起/关闭子进程。框架若"启动"一个 stdio MCP，实际是做一个**常驻宿主**（拉起子进程并保持，供 MCP 客户端连接）。其健康探测 = 进程存活 + MCP initialize 握手成功（协议级健康，比端口探测更准确）。Streamable HTTP 型 = http-endpoint kind 的直接复用（探活目标换成 MCP 端点）。结论：MCP 可以统一管理，但必须以独立 kind 承接，禁止硬塞进 local-process。

### 12.3 插件的特别说明

插件无进程诉求，管理语义退化为"注册表中的启用/禁用状态位 + 页面统一呈现"。接入后用户视角完全统一（都在服务页看到），实现视角各走各的执行器——这正是"集中监控、分散实现"的完整体现。

## 十四、风险与边界

| 风险 | 等级 | 缓解 |
|------|------|------|
| Job 继承连杀（9.4） | P0 | breakaway + 独立 Job 退路 + 快照兜底，一票否决项 |
| 清单坏文件拖垮注册表 | P1 | 单项降级 invalid，隔离展示 |
| 误杀无关进程（收养错 PID） | P1 | 收养必须命令行匹配；不匹配转 unknown 人工裁决 |
| 长动作阻塞事件循环 | P0 | 动作全部 to_thread 卸载（本仓既有教训铁律） |
| 端口被外部进程占用 | P2 | 启动前置检查 + failed 明确报因；不做抢占 |
| 双实例（用户又双击了 bat） | P2 | 启动前置端口检查直接 failed 报"已有人在监听"；孤儿收养覆盖 backend 重启场景 |
| mihomo 慢启动误判 failed | P1 | start_grace_seconds + retries 双参数防抖 |
| 动作脚本交互式输入在无头环境永久挂起 | P1 | 契约 7.2 禁交互（源头）+ 动作超时上限树杀（框架兜底，9.5/7.3） |
| 动作输出编码混乱（GBK/UTF-8 混流） | P2 | manifest spec.encoding 声明制解码（契约 7.2.5） |
| 轮询压力 | P3 | 服务数个位数，5s 轮询一条聚合接口，压力可忽略 |

边界（明确不做）：

- 不做服务间依赖编排（depends_on 拓扑）——当前两服务无依赖，引入即过度设计；
- 不做资源限额（CPU/内存 cgroup 类）——Windows 无低成本等价物；
- 不做多机/远程服务管理——本框架定位本机宿主；
- 不做配置编辑 UI——清单是文件，git 管理，不造第二个配置真源。

## 十五、验收标准

1. **自动识别**：在 ext_service 下新建一个含合法 service.json 的服务目录，页面 10s 内出现新服务卡片（热扫描）；移除目录后卡片消失且运行中的实例被先停后摘。
2. **启停闭环**：opencli_gateway、omnivpn 均可页面启动 → starting→running 迁移可见 → 健康延迟展示 → 页面停止 → 端口确认释放。
3. **健康语义**：人为提供一个"启动慢"的服务（宽限内未就绪），验证宽限期防抖生效不误判；人为提供一个 health 声明 tcp/http 但"起进程不开端口"的服务，验证按期转 failed 而非假 running。
4. **Job 隔离**：服务 running 时关闭 backend 进程，服务进程仍存活；重启 backend 后孤儿收养恢复 running 视图。
5. **动作**：OmniVPN 页面执行换桶/巡检/出口体检，输出在抽屉可见；未声明动作的请求被 403 拒绝。
6. **防御性**：放一个非法 JSON 清单，页面出现 invalid 卡片，其余服务管理不受影响。
7. **接入契约**：OmniVPN 巡检动作在页面动作输出区可见 `[STEP]/[OK]/[FAIL]` 行与成败汇总，中文无乱码；人为构造一个含 `pause` 的旧式脚本验证超时兜底生效（不永久挂起）。
