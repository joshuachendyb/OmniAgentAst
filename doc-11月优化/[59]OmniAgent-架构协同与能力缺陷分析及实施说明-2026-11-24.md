## 一、要解决的问题

本章只回答"要解决什么"——列清楚痛点、代码证据、卡住哪个应用方向；**不展开怎么做**（怎么做见第二章）。先交代现状与地基，再列方向，最后给出要解决的核心问题清单。

### 1.1 系统现状与已具备的地基

基于 **ReAct 的单 Agent**、面向 **Windows 本机**、**本地私有化**的全栈 Web 应用：Python/FastAPI + React，**11 类 67 工具**，任意 OpenAI 兼容模型，**四层安全（L0-L3）+ HITL + DB 事务回滚**，SQLite 5 库、数据不出机。它已经是"能干的 Agent + 一台自己的 Windows 电脑 + 一套过硬的安全防线（危险直接拦、有风险问人）"，不做云 VM、不做截图坐标，走 **Windows API/命令直调**的确定性路线。

下列能力是**真资产**，扩展时"升级接口、复用内核"，**不推倒重来**：

| 能力 | 代码落点 | 对扩展的价值 |
|---|---|---|
| 任务是"一等实体"（chat_tasks + 消息锚 + files_dir） | `stream_orchestrator._create_and_launch_task` | 任务不依赖某条前端连接，可被任意端查询/订阅 |
| 事件缓冲带单调 seq | `task_state.StreamBuffer`（task_state.py:50）`publish`+`publish_lock` | 事件可排序、可回放，是多端同步的地基 |
| 运行期逐步落库 | `persist_sink` / `flush_sink` | 事件不只在内存，刷新/换端可重建 |
| Journal 回放 | `publish_with_journal` | 断连后按序号补发 |
| SSE 断线续传（after_seq） | `/chat/stream/{task_id}`、`execution_stream.py`、`task_runtime.py` | 手机断网/切后台/换标签可续读 |
| agent 后台协程执行 | `run_agent_in_background`（定义于 agent_runner.py:348，编排层调用于 stream_orchestrator.py:1129） | 执行不绑 HTTP 请求生命周期 |
| 任务控制面：暂停/恢复/取消/运行中注入 | `task_runtime.py`、`task_registry.py` | 多端可对同一任务下发控制指令 |
| HITL 双向端点 | confirm / answer（`chat_routes.py`）、`hitl_confirmation.py`、`hitl_question.py` | 天然可"在另一台设备上确认 / 回答" |
| 后台命令完成唤醒续跑 | `resume_session_with_notice` + `inject_system_notice`（stream_orchestrator.py:1137） | 长命令完成可自动推进 |
| 中断任务启动期收尾 | `reconcile_orphaned_tasks`（storage.py:612），main.py 启动调用 | **"重启后任务不再永久显示执行中"已落地** |
| 数据与产物 | SQLite 5 库 WAL + `files/` + `assets` 静态托管 | 可做多端读取与下载 |

### 1.2 宿主假设：单进程·单用户·多会话·多任务（客观边界）

> **"单进程"指进程数为 1，不代表"单任务"或"单会话"**。当前是多会话（`chat_sessions` 多行）、多任务并发（`running_tasks` 按 `task_id` 多键、asyncio 同进程并发）的形态；真正受限的是**没有并发上限**（已按 2.2.1 补齐）与**各能力边界**（下表）。

| 编号 | 宿主假设 | 代码证据 | 破绽 |
|---|---|---|---|
| A | 执行态在内存、无队列，并发有上限（已设闸门） | `running_tasks`（task_state.py:42，`dict[task_id]` 多键并存→可并发）、`StreamBuffer.cond`、`_agent_tasks`；`agent.max_concurrent_tasks`（默认 3）+ `run_agent_gated` 信号量闸门已落地 | 进程重启 → 跑到一半的**执行**蒸发（中断本身已被诚实标注，不再误显示"执行中"）；并发已封顶，超限在闸门内排队，仍有**背压提示缺失**（排队期前端无"等待中"字样，用户只看到未开始） |
| B | 事件只有 HTTP-SSE，无主动推送 | 全仓仅 SSE/REST；前端无 `sw.js`/`manifest`/`vite-plugin-pwa`，后端无 `pywebpush`/VAPID | 手机锁屏、切后台 → 收不到"任务终态 / 待确认 / 待回答" |
| C | 单口令鉴权，无设备/端身份 | `security.access_token` + `verify_token`（deps.py） | 无法区分设备、无法定位"谁处理的" |
| D | 执行能力钉死宿主 Windows | tools/ 全是本机能力 | 手机只能当遥控器，无法"换端执行" |
| E | 调度器非持久（后端内核已补齐） | `timer_set._timers` 用 `asyncio.call_later`；timers 表已加 `session_id`，`rebuild_timers_from_db` 启动重建已落地 | 重启后定时器可恢复、可回会话建任务；仅"触发后离开页面也能叫醒人"仍依赖主动推送 |
| F | 单机单进程，无队列/worker/网关 | 5 库 + 单事件循环，任务用内存注册表 | 公网接入缺配对/隧道/加密/限流 |
| G | 无长期记忆与画像 | 仅有会话历史 + 上下文压缩（`compaction/`、HistoryMemory）；无独立用户画像/长期个人记忆/程序性记忆 | 每次都要重述需求，无法"越用越懂你、教一次可复跑" |
| H | 不能代表用户触达外部系统 | 工具均本机动作；无 OAuth/MCP 之类对外握手 | 不能"登录外部网站代表你下单/改签" |

### 1.3 四个应用方向

脱离应用方向谈问题，就会变成"什么都要补"。先把方向摆清楚：

| 方向 | 场景描述 | 你要的核心体验 |
|---|---|---|
| **A 本机单端深度使用** | 只在 PC 上，一个人用 | 长任务别丢、越用越顺手 |
| **B 多端协同** | PC + 手机，手机主要"看进度 / 处理确认与问询 / 接管" | 离开 PC 也能掌握和拍板 |
| **C 主动个人助理** | 定时/触发/例行任务，无需你在场 | 到点自己干、干完找你 |
| **D 跨域代理** | 代表你登录外部系统办事（下单/改签/填表） | 真替你在外部世界跑腿 |

### 1.5 底座判定：地基 / 上层 / 不预建

| 类别 | 包含项 | 为什么这样归类 |
|---|---|---|
| **地基**（已成型或改动极小，一次性收口） | 任务终态与中断收尾（**已完成**）；生命周期事件总线（**已实施**）；设备标识（轻量一档即可） | 上层能力都建立在"任务是谁的、事件发到哪、哪个设备有权处理"之上，改动面小、复用度高 |
| **上层**（真空白，按方向独立交付） | 手机端响应式；主动推送；持久调度器（**内核已完成**）；跨端 HITL（**可见性/收敛已完成**）；长期记忆（程序性优先） | 是地基上的消费者/插件，彼此可解耦，按应用方向分别挂载，不必同时上线 |

## 二、计划采取的方案

本章回答"怎么做"。先给总纲与设计原则，再逐项给出详细实施方案与取舍，最后给出分期路线。每项只描述**设计意图与实施方法**；**已落地的结果与实测**统一放在第三章。

### 2.1 方案总纲与设计原则

**总纲**：已完成的收口、已成型的不改名、无消费方的不预建；按应用方向分批交付，做一个方向只挂它需要的那几件。

**六条设计原则**（对应代码 10 大规范）：

| 原则 | 本文怎么用 |
|---|---|
| **KISS-DIRECT** | 逻辑直线、最简实现。调度器用既有 `call_later` 句柄 + 启动重建，不引 APScheduler/消息队列；HITL 收敛用"幂等 + 广播"，不引入租约/TTL |
| **YAGNI** | 不为不存在的使用方写抽象：执行端、跨域代表都不预建；设备标识只取轻量档，不建完整注册体系 |
| **SRP** | 一条能力只做一件事。生命周期事件总线与 `StreamBuffer` 职责正交、分开实现，不硬塞进随任务消亡的缓冲 |
| **DRY** | 复用现有内核：调度触发复用 `resume_session_with_notice`；记忆复用 `chat_task_steps`；推送复用 `EventBus` 两类信封 |
| **SLAP** | 同层调用：tools 层不 import services，用回调注入把跨层动作交给 app 层 |
| **禁止 backward 兼容** | 不新增 `interrupted`/`queued` 等与前端词表撞车的状态值；接口改动不做新旧并存 |

**一条架构铁律（决定持久调度器与主动推送的落地形态）**：`test_architecture_boundaries` 的 FORBIDDEN 表**禁止 `app/tools` import `app/services`**。因此：
- **持久调度器** 定时器要"触发时回会话建任务"，不能在 tools 层直接调 `resume_session_with_notice`（在 services 层）→ 用 **`set_timer_resume_callback` 回调注入**解越层，回调由 app 层 `main.py` 启动时注入；
- **主动推送** WebPush sink 在 services/app 层订阅 `EventBus`，不反向 import tools。

**公用件入库**：每个新公用函数/模块落地后更新 `backend/FUNCTIONS.md` 清单。

### 2.2 逐项实施方案

#### 2.2.1 任务调度可靠性

- **现状实证**：这一项做得比常见方案更严谨——`chat_tasks.status` 已落库（DEFAULT `'executing'`，配 start_time/end_time/error_type）；`reconcile_orphaned_tasks`（storage.py:612）启动期把遗留 `executing` 残行改终态并挂到 startup；用 `boot_iso` 做归属判据（`start_time < boot_iso`）不误杀本次新建任务；终态复用 `failed` + `error_type='task_interrupted'`（`'interrupted'` 已被前端 ToolCallLine 占用为"工具被拒"语义，新增会撞车）；`duration` 不补算（"被打断无真实耗时，补算即编造"）；前端已渲染对应文案。
- **要收口的缺口**：① 并发无上限——`running_tasks` 是 `dict[task_id]` 多键并存、asyncio 同进程并发，多会话同时跑重任务会撞 LLM 限流/文件锁/CPU，且无背压无提示；② 取消任务终态三处不一致（SSE `final.outcome` 与 `chat_tasks.status` 是 `cancelled`，`task_tracker.tasks.status` 却落 `failed`）。
- **实施方案**：
  1. **并发闸门**：`agent.max_concurrent_tasks`（默认 3）+ `agent_runner.run_agent_gated`（外层 `asyncio.Semaphore` 包装，超限在此排队）；编排层 `_create_and_launch_task` 改经 `run_agent_gated` 启动。**不新增 `queued` 状态**（DB 仍为 `executing`=已受理未完成，前端词表零改动），终态链路（finally 落库/done 置位）完全未动。排队期取消由 `start_step` 首查 `check_cancelled` 兜底。
  2. **终态一致**：`status_table` 新增 `tracker_terminal_status()` 作为 `AgentStatus → task_tracker` 终态值唯一映射源（`CANCELLED→cancelled`，非终态按 `failed`）；`TaskStatus` 补 `CANCELLED`，`TaskTracker.complete_task` 签名由 `success: bool` 改为 `status: str`（禁布尔三态混淆）；`step_emitter.complete_task()` 无参化读 `agent.status` 翻译落库；`react_loop._finalize_cycle` 收尾前用同步 `task_state.is_cancel_requested()`（与 `check_cancelled` 同源）按取消标记补 `set_cancelled`，自身终态不可变。
- **取舍**：**"队列"对单用户是过度设计**（不需要消息队列中间件、不需要"任务排队等待"的调度器）；只补"并发上限"这一个真实缺口。

#### 2.2.2 生命周期事件总线

- **现状实证**：`StreamBuffer`（task_state.py:50）已是单生产者多订阅者（`event_log` append-only 带单调 `seq`、`cond.notify_all()` 广播、已挂 `persist_sink`/`flush_sink` 两个 sink）。**但它的生命周期是 `task_id`**，任务终态即被 `reclaim_memory_buffer` 回收；而"任务终态"恰恰是必须发出的通知之一——**挂在随任务消亡的缓冲上，通知自身没有可靠发出时机**。"新任务诞生"同理。
- **结论**：**不把 `StreamBuffer` 改名为 `EventBus`**（改名不升级，违反 KISS），而是**新增一条独立的、比 task 更长寿的广播通道**。
- **实施方案**：新增 `app/services/task/event_bus.py`（全局单例 `EventBus` + `publish_event`），配 `GET /chat/events`（SSE）下发。两条总线职责正交、不可合并：
  - `StreamBuffer`（按 task）：AI 正文，有 seq + Journal + `after_seq` 续传，**不许丢**；
  - `EventBus`（全局）：变更信封（`task_started`/`task_ended`/`task_status_changed`/`hitl_pending`/`hitl_settled`），无 seq、不落库、**允许丢**，丢了靠重连对账（拉 `/sessions/tasks/running` 比对锚点）。
  - 可靠性模型 = at-least-once 播报 + 幂等对账：订阅者队列满弃最旧保最新；ring 缓冲保留最近 32 条供短暂断线补发；`epoch` 纪元号让前端在进程重启后丢弃陈旧 `last_event_id` 走对账。
- **铁律**：沿用"每任务单生产者 + seq 单调"，**坚决不做全局 seq**（会让回放/续传全乱）；`EventBus` 刻意不带 seq（只做通知），从设计上避开该铁律。

#### 2.2.3 主动推送（WebPush）

- **现状**：事件出口只有 HTTP-SSE。手机锁屏/切后台/杀进程就收不到"任务终态/待确认/待回答"。这是"单通道"的本质。
- **关键澄清：推送不是把 SSE 事件流复制一份发出去。** 只发两类"结论"，中间过程一律不推：

  | 会推送的（仅两类） | 永不推送的 |
  |---|---|
  | 任务进入终态：完成 / 失败 / 取消 | 思考过程、工具调用与返回、进度百分比更新 |
  | HITL 待处理项出现：待确认 / 待回答 | 以上全部中间事件 |

  一个跑 10 分钟、几百条事件的任务，**推送只有 1 条**（终态那条）。条数只与"任务结束次数 + HITL 弹窗次数"有关，与 SSE 事件数无关。

- **防刷屏四约束（实现必须全给）**：
  1. **只挂两类触发点**（任务终态、HITL 待处理项）——这是一条任务通知条数的根本上限；
  2. **通知带 tag 去重替换**：`showNotification` 传 `tag=task_id`（HITL 传 `tag=hitl_id`），同 tag 在通知栏**替换**而非堆叠；
  3. **页面可见即抑制**：主要靠前端（`visibilityState === 'visible'` 收到 push 也不展示，WebPush 是服务端推给浏览器推送服务，后端无法感知设备是否在前台，只能靠前端最后一跳自我抑制）；后端可叠"最近活跃时间"粗过滤；
  4. **时间窗合并**：3 秒内多个任务同时终态合并成一条，不做 N 条并列。
- **前端必须配合的五项**（缺任何一条推送就是纯骚扰）：① 可见性抑制；② 去重替换；③ 点击定位（`notificationclick` → 已有窗口 `focus()` 跳到该 task_id，未开窗口则 `openWindow('/?task=xxx')`，再靠 `after_seq` 补齐断线期间事件）；④ 权限克制（只在用户手势后 `requestPermission`，被拒不反复弹）；⑤ 开关分级（全局 + 按类型：终态/待确认/待回答，持久化在订阅表与 localStorage）。
  > **分工一条线**：**推送只负责"叫醒"，不携带正文真相；SSE + Journal + `after_seq` 负责"点开看全貌"**。正因为正文不走推送，推送才允许丢、允许重复（靠 tag 去重、靠回放补齐）。
- **硬前置（必须先解决）**：Service Worker 只能在 **HTTPS 安全上下文**注册（`localhost` 除外）。当前是"本机 HTTP + 局域网 `http://192.168.x.x:port`"，手机端 SW 注册会直接失败、WebPush 不可用。三条路径：① 自签证书 + 手机装信任（免费，每台设备手动信任一次，到期要换）；② 内网 HTTPS 反代（需域名与证书维护）；③ 隧道服务（最省事但与"数据不出机"冲突，不建议）。**推送自带一个 HTTPS 工程前置，成本要算进评估。**
- **平台限制**：iOS 需 16.4+ 且**必须"添加到主屏幕"以 PWA 形式打开**才生效，浏览器直访收不到；安卓 Chrome 无此限制。
- **实施方案**：
  1. 后端：VAPID 密钥对 + 订阅表（endpoint/p256dh/auth/device_id）+ 订阅/退订端点 + **WebPush sink**（订阅 `EventBus` 的 `task_ended` / `hitl_pending` 两类信封，翻译成推送载荷，约 200 行）；
  2. 前端：`manifest.json` + `sw.js`（只做 push 事件与 click 跳转）+ 权限申请与订阅注册（约 150 行）；
  3. 触发点严格只有两类；
  4. **一期只做 Web/PWA**，邮件/IM 多渠道留作后续 sink 扩展点，不提前抽象。
- **依赖顺序**：设备标识先于主动推送（没有稳定 `device_id` 只能盲推全部订阅，导致"人在电脑前，手机也响"）。

#### 2.2.4 设备标识

- **现状实证（半个基础已存在）**：前端 `clientInfo.ts` 已采集 `client_os/browser/device/network`，随消息经 `messages.py:49` → `message_service.py:340` → `storage.py:1018` 落库到 `chat_user_message`。**"识别客户端画像"已做**；缺的是 ① 跨会话**稳定的 `device_id`**（现在按 UA 解析，同一台手机换浏览器就变 label）；② 把设备归属用于**推送目标选择**与 **HITL 处理审计**。
- **真实需求只有一句**：审计与提示时能说清"这是哪台设备在处理"。
- **分两档，先做轻档**：
  - **轻量档（推荐一期）**：复用已有 `clientInfo` 采集，只补一个稳定 `device_id`——前端首次访问生成 UUID 存 `localStorage`，随请求头带；后端写入现有审计字段。**约 20 行，无新表、无配对流程。**
  - **完整档（暂不做）**：配对码 → 设备 token → 心跳/在线表 → 会话与设备多对多 → 主控端。只有需要"按设备收回权限/设备级远程注销"才值得，当前无此需求。
- **信任边界**：设备标识的信任根仍是单口令——口令泄露等于全部设备失陷；若将来上完整档，口令变更须吊销所有设备 token 并重新配对。
- **顺序**：先于主动推送落地。

#### 2.2.5 手机端响应式接入

先回答前置问题：**手机怎么接进来？接入方式不同，"要不要执行端抽象"的答案完全不同。**

| 方式 | 做法 | 现有基础 | 成本 | 适合 |
|---|---|---|---|---|
| **(a) 现有 Web 前端做响应式** | 同一套 React，加移动断点，手机浏览器直接访问 | `index.html` 已有 viewport meta；`clientInfo.ts` 已有 UA 识别；但**响应式只覆盖 9 个文件**（Layout/NavContent/Skeleton/ToolCallLine），**聊天主界面（消息流/输入框/任务面板）尚无移动适配** | 中 | 一期推荐。一套代码、无需发版、改完即用 |
| **(b) 独立移动端 App** | React Native / Flutter / Capacitor 套壳 | **零基础**（无 capacitor/cordova/react-native/antd-mobile） | 大 | 需原生能力（后台推送更稳、本地文件/相机）才考虑 |
| **(c) 集成到第三方 IM** | 微信/飞书/钉钉机器人、小程序 | **零基础**，且 IM 卡片做不了复杂交互（多选/多题/文件预览） | 中 | 只做"通知到人"，不做"看+处理"主界面 |

- **建议路径**：一期走 **(a) 响应式**——已有 viewport + UA 识别基础，补齐聊天区移动布局即可；推送用 WebPush（配主动推送的 HTTPS 前置）覆盖锁屏提醒。(b) 的原生优势这个阶段不值得翻倍成本；若后续发现"iPhone 必须加到主屏才能收推送"的体验无法接受，再评估 (b)。

#### 2.2.6 客户端 ≠ 执行端概念

无论走哪种接入方式，手机在这个阶段都只是**客户端**，不是**执行端**：

| 概念 | 职责 | 现有 | 需要什么 |
|---|---|---|---|
| **客户端（client）** | 看进度、处理确认与问询、发指令 | Web 前端（含未来移动适配版） | 只需主动推送 + 设备标识 + 跨端 HITL 路由 |
| **执行端（executor）** | 真正跑工具、动文件、调命令 | 只有 PC（后端进程本身） | 需要 `Executor` 接口 + 能力注册 + 分派 |

手机作为客户端接进来（看进度/处理 HITL）→ 任务仍在 PC 上跑 → **不需要执行端抽象**；只有要求"手机自己也能本地执行"（读手机相册、取定位、调手机上 App）才需要。

#### 2.2.7 执行端抽象

- **现状**：全部工具均为本机动作，无执行端注册/分派机制，**也没有任何消费方**。
- **结论**：当前不预建。一期手机走 (a) 响应式、"看+批"模式，没有第二个执行端。此时定义 `Executor` 接口（register/heartbeat/execute/cancel）、能力协商、能力标签映射，全是**为不存在的场景写抽象**（YAGNI）。
- **何时才需要**：真要"手机本地干活"，或"用浏览器执行端跑跨域任务"（D）时，届时按真实需求设计，比现在拍脑袋更准。

#### 2.2.8 持久化调度器

- **现状实证（好消息）**：timers 表结构已就绪——`timer_id / delay / callback / created_at / trigger_at / triggered_at / status='active'`，且已加 `session_id`。缺的只是"启动时把 active 且已到期的重建为 `call_later`"这一段。
- **解决什么**：timers 表驱动、重启可恢复的调度器，支持"到点创建任务 / 提醒 / 发起 HITL 确认"。
- **实施方案（后端内核）**：
  1. **启动重建**：`rebuild_timers_from_db()` 扫 `status='active'`——未到期按剩余秒重建 `call_later`、已过期立即补触发一次（不丢"到点该干"语义）、非 active 跳过；`main.py` startup 在注入回调后调用，失败降级不阻断启动；
  2. **触发动作统一走"回会话建任务"**：经 app 层注入的回调 `resume_session_with_notice`（tools 层禁 import services，用 `set_timer_resume_callback` 注入解越层；复用其"有活跃任务→注入 / 无→建新任务"双路，不直接调 HTTP）；无会话/无回调时维持原 log/http 行为；
  3. **落会话**：`timer_set` 落 `session_id`（取自新 ContextVar `get_current_session_id`，`tool_executor` 从 `agent._start_meta` 注入并 finally 清理）；
  4. **不引中间件**：单进程用 `loop.call_later` 句柄即可，与既有 timer 实现同构、零新依赖（放弃轮询+最小堆）。
- **取舍**：C 方向核心"到点自己干、干完找你"的两半——**调度器负责"干"、主动推送负责"找你"**，建议一起做，但内核可先落地、通知随推送分批交付（不阻塞）。

#### 2.2.9 跨端 HITL 路由

- **先正名（必须纠正）**：本节讨论的不是"审批"。系统里**没有"审批"机制**，HITL 只有两套，且 `blocked`（危险）根本不问人：

  | 概念 | 代码落点 | 语义 | 是否问用户 |
  |---|---|---|---|
  | **硬拦** | `SafetyResult.blocked=True` + `BLOCK_LEVELS` | 真危险：磁盘根/系统禁区、危险命令、非法路径、未注册工具 | **不问，直接拒绝**（弹窗只作诊断留痕） |
  | **需确认** | `SafetyResult.needs_confirm=True` + `CONFIRM_LEVELS` | 有风险/越权：白名单外删除、非禁区写入、中风险命令、含读写删的命令、`execute_sql`、任务与注册表操作 | **要问**，进 HITL 弹窗 |
  | **hitl_confirmation** | `hitl_confirmation.py`：create/wait/resolve | 征求同意：确认/拒绝，可选"信任本次会话"（落 `chat_session_trust`） | 要问，二值 + 信任 |
  | **hitl_question** | `hitl_question.py`：create/wait/resolve | 收集答案：`question` 工具问询，多题多选 + 自填 | 要问，**无信任语义** |

  > 一句话记法：**危险的（blocked）直接拦，不问；有风险的（needs_confirm）才问；问分两种——要不要干（confirmation）、要什么信息（question）。** 后续一律用"**待确认 / 待回答**"或合称"**HITL 待处理项**"，不再用"审批"。

- **问题**：确认与问询目前都是"当前会话前端弹窗"，只能弹在发起设备；换个设备就看不到、处理不了。
- **现状实证**：HITL 双向端点已存在（`confirm`/`answer`，`chat_routes.py`）；确认/问询经内容流的 `interact` 帧（`kind=confirm|question`）投递，弹窗由 `pendingAuthorization` / `pendingQuestion` 驱动。
- **实施方案（可见性 + 收敛）**：
  1. **待处理项进事件链路**：`create_confirmation` / `create_question` 播 `hitl_pending`（信封只带 `hitl_id/kind/task_id/session_id` + `tool_name`/`count`，**不含弹窗正文**）；`resolve_*` 播 `hitl_settled`；
  2. **跨会话告知**：新增 `GET /chat/hitl/pending` 权威快照（对账用），前端 `hitlPendingStore` 收信封 + 重连/切回可见时对账，顶栏 `HitlPendingPill` 角标，点击直达该会话；
  3. **任一端处理即收敛**：`hitl_settled` 广播后其余端角标自动消失；重复提交天然安全（`resolve_*` 对已 done 的 future 返回 False）。
- **与原方案的刻意偏离（须记录）**：原"怎么做"要求"**首次领取即锁 + 租约（TTL）**"。**本期不做**：允许多端同时看到同一项、谁先处理谁生效，靠 `resolve_*` 幂等 + `hitl_settled` 收敛即可，无需领取锁，也就没有"设备领了掉线 → 永久锁死"的问题（KISS-DIRECT，不为不存在的锁引入租约复杂度）。若将来出现"多端并发误操作"的真实痛点，再补租约。
- **弹窗详情不搬进信封**：仍由会话内容流的 `interact` 帧提供（切到该会话后 `GET /chat/stream/{task_id}?after_seq=0` 的流内含 `interact` 帧且 content 带完整信息），"点角标 → 跳会话 → 弹窗出现"整条链路成立。
- **超时策略（沿用既有实现，非新做）**：默认暂停；超时默认拒绝（`hitl_confirmation` 超时按未授权处理，见其 `expired=True` 分流）；`question` 超时返回空答案并标记 `expired`。
- **剩余部分（阶段 2）**：跨**设备**（手机）处理仍受设备标识 `device_id` 与 HTTPS 前置限制；离开页面时的"叫醒"依赖主动推送。

#### 2.2.10 长期记忆 / 程序性学习

- **现状实证**：只有"会话历史 + 上下文压缩"（`compaction/`、HistoryMemory），没有独立用户画像、没有跨会话长期记忆、没有"上次怎么做的、下次如何更快更省"的程序性记忆（全仓 `memory/profile` 均指进程内存或模型能力画像）。
- **解决什么**："personal"的核心——**越用越懂你、一件事教一次即可复跑**。
- **不"三件套一起做"**（原文把"画像表 + 跨会话事实库 + 程序性记忆"打包称最小可行，实为三个子系统）。**只先做程序性记忆**：
  - **程序性记忆（先做，零新表）**：`chat_task_steps` 已完整记录每个任务的步骤序列，可直接沉淀为"可复跑流程模板"，下次同类任务直接套用——收益最高、成本最低、不引入新概念；
  - **用户画像（后置）**：结构化偏好（常用路径、口头习惯、授权偏好）一张表，等确有"每次重述偏好"的痛点再加；
  - **跨会话事实库（后置）**：SQLite + 简单检索即可，**不引入向量库**。
- **附加约束**：记忆注入沿用现有 message_builder，不新增 LLM schema 参数；**注入量必须设预算与裁剪策略**（复用 compaction 容量控制思路），否则记忆膨胀挤占任务上下文。
- **与持久调度器相关**（例行任务复跑依赖程序性记忆），与多端/推送无关；**可独立启动**，不依赖阶段 1~3 任何产出。

#### 2.2.11 跨域代表

- **现状**：只会本机动作，无任何对外握手机制。
- **结论**：当前不排期、不设计。它属于"另一条产品线"（成本与风险最高：账号安全、外部失败代价、合规），且依赖执行端——而执行端已判定"不预建"。等需求真正指向 D 方向时再立项：① 先接 MCP/OpenAPI 标准握手而非硬编码各家；② 对外动作强制"确认 + 审计 + 可回滚"（复用四层安全）；③ 按服务细分权限作用域（只读/可读可发），而非一个大开关。

## 三、已经实施的部分（附增强能力说明）

本章回答"哪些已经做完、做完后系统多了什么能力"。**本章各节与第 2 章各节一一对应**：第 2 章列出的要实施方案，在本章中仅保留"已实施"的条目；其余条目因尚未实施，不在本章出现，详见第 4 章。

### 3.1 对应第 2 章 2.2.1 任务调度可靠性——已实施

- **实施内容**：① 并发闸门——`agent.max_concurrent_tasks`（默认 3）+ `run_agent_gated` 信号量排队，编排层经其启动；② 取消终态一致——`tracker_terminal_status` 作为 `AgentStatus → task_tracker` 终态唯一映射源，`TaskTracker.complete_task` 签名由布尔改为 `status: str`，`_finalize_cycle` 收尾按取消标记补 `set_cancelled`。
- **实测**：5 个慢任务上限 3 时耗时分层（8.4/10.3/10.5s vs 17.4/19.2s），全部正常完成、零僵尸；取消任务（工具执行中 / LLM 思考中 / 排队期）SSE、`chat_tasks`、`task_tracker` **三处全部 `cancelled`**；回归正常完成仍为 `completed / completed / success`。
- **增强后的系统能力**：
  - **重启不再"任务蒸发误显示"**：中断任务启动期被 `reconcile_orphaned_tasks` 诚实标注"任务已中断（服务重启，不会自动续算）"，用户看得到、可重发，而非永久卡"执行中"；
  - **并发可控**：多会话同时跑重任务时撞 LLM 限流/文件锁/CPU 的风险被闸门封顶，超限自动排队而非打满；
  - **取消语义正确**：取消任务不再被任务列表/历史误显示成"失败"，三处口径一致。

### 3.2 对应第 2 章 2.2.2 生命周期事件总线——已实施

- **实施内容**：独立 `EventBus`（全局单例 + `publish_event`）+ `GET /chat/events`（SSE）下发；`StreamBuffer` 原样不动（两者职责正交，见 2.2）。
- **实测**：发消息 → 前端收到 `task_started` 仅 **502ms**，替代 ChatPage 原每 3 秒一次的 SQLite 查询；续跑新建 task_id 同样即时广播。
- **增强后的系统能力**：
  - **跨会话即时感知**：任务起停/HITL 待处理经一条常驻 SSE 即时推到顶栏，用户不用手动刷新；
  - **消除 3 秒轮询**：省掉每 3 秒一次库查询与浏览器后台节流带来的最大 3 秒延迟；
  - **后台命令换任务也不失联**：`resume_session_with_notice` 新建 task_id + 新 `StreamBuffer` 时，靠比 task 更长寿的 `EventBus` 广播，前端无需锚在旧 task_id 上。

### 3.3 对应第 2 章 2.2.8 持久化调度器——已实施

- **实施内容**：① timers 表加 `session_id` 列（`_ensure_column` 幂等迁移）；② `timer_set` 落会话、触发经 app 层注入的 `resume_session_with_notice` 回调回会话建任务（`set_timer_resume_callback` 注入解越层，抽 `_schedule_handle` 供设置与重建共用）；③ `rebuild_timers_from_db` 启动扫 `status='active'` 未到期重建、过期补触发；④ `main.py` startup 注入回调 + 调用重建（失败降级）。
- **实测**（隔离数据目录，真 SQLite，跨进程）：DDL 幂等、`session_id` 落库、到点触发回调带正确 session、`triggered` 状态落库；跨进程重启恢复——进程 A 落 3 行 active（2 未来 + 1 过期），进程 B 新解释器恢复 → 未到期重建 2、过期补触发 1，过期任务正确回到其会话建任务，全部 PASS。
- **增强后的系统能力**：
  - **重启不再丢定时**：`call_later` 句柄重启即丢，但 timers 表是跨重启唯一真源，启动自动重建，"到点提醒/主动执行"从此可靠；
  - **重启期间错过的不丢**：重启时已过期（重启期间该触发的）会立即补触发一次，不丢"到点该干"语义；
  - **到点自己干**：定时器触发不再是"打条日志/发个 HTTP"，而是回到原会话建任务让 Agent 接着干活（复用 `resume_session_with_notice` 双路），这是"主动助理"的核心；
  - **架构合规**：用回调注入而非 tools 层直连 services，既实现"回会话建任务"又不破坏 `test_architecture_boundaries` 的层边界。

### 3.4 对应第 2 章 2.2.9 跨端 HITL 路由——已实施

- **实施内容**：`create_confirmation`/`create_question` 播 `hitl_pending`、`resolve_*` 播 `hitl_settled`；新增 `GET /chat/hitl/pending` 权威快照；前端 `hitlPendingStore` 收信封 + 重连/切回可见时对账，顶栏 `HitlPendingPill` 角标点击直达该会话。
- **实测**：任一端处理某待处理项后，`hitl_settled` 广播，其余端角标自动消失；重复提交安全（`resolve_*` 对已 done 的 future 返回 False）；切到该会话后 `interact` 帧确实携带完整信息（目标路径/拦截原因/授权时效），"点角标 → 跳会话 → 弹窗出现"整条链路成立。
- **增强后的系统能力**：
  - **跨会话告知**：正在会话 A，会话 B 冒出"待确认 / 待回答"，顶栏角标立刻提示，点击直达；
  - **任一端处理即全局收敛**：多端看到同一项时谁先处理谁生效，其余端自动收起，不会出现"两个地方都还挂着一个未处理的框"；
  - **对账兜底**：断线重连/页面切回可见时拉 `hitl/pending` 快照比对，保证不遗漏。

> **本章覆盖范围**：第 2 章列出 11 个要实施方案（2.2.1~2.2.11），本章仅覆盖其中已落地并实测的 4 个（2.2.1、2.2.2、2.2.8、2.2.9）。其余未实施项（2.2.3、2.2.4、2.2.5、2.2.6、2.2.7、2.2.10、2.2.11）详见第 4 章。

### 4.2 后续建议（按痛点优先级）

- **只在本机用（A 方向）**：真正该补的只有 **长期记忆/程序性学习**（零新表起步、可独立先做、性价比最高），其余都不必做——任务调度可靠性已完成，能"一件事教一次即可复跑"。
- **要手机看进度/拍板（B 方向）**：按序推进——**阶段 1 HTTPS 前置 → 手机端响应式 → 设备标识 → 主动推送 → 跨端 HITL 跨设备部分**。顺序不可颠倒（设备标识先于主动推送，否则盲推全部设备；手机端响应式先于主动推送，否则点开通知看到挤坏界面）。
- **要主动提醒/例行任务（C 方向）**：**"到点自己干"的内核（持久调度器）已完成**，只差"干完找你"——补上主动推送即闭环；两半不必同时到位，内核可先用。
- **对外代办（D 方向）**：才考虑 执行端抽象 + 跨域代表，当前**不立项**。

### 4.3 一句话总结

- **要不要一体化**：不需要。真正要做的核心是 **推送、程序性记忆、跨端 HITL 跨设备部分**，加 2 处小补齐（事件总线已补齐、设备标识）；走 B 方向再需手机端响应式接入。
- **哪些是过度设计（别做）**：把 `StreamBuffer` 改名当总线（已改为新增独立 `EventBus`，正文与标题同步更正）、完整设备注册体系（20 行够用）、`Executor` 接口预建（无消费方）、跨域代表立项（另一条产品线）、记忆"三件套打包"（程序性记忆可零新表起步）。
- **哪些已完成别重做**：任务调度可靠性（中断可恢复 + 并发闸门 + 取消终态一致）、生命周期事件总线、跨端 HITL 可见性/收敛、持久调度器内核，均已实测落地。
- **手机怎么接进来**：一期走**现有 Web 前端响应式改造**，不做独立 App、不集成第三方 IM；手机在"看进度 + 处理 HITL"模式下是**客户端不是执行端**，任务仍在 PC 跑，故**不需要执行端抽象**。
- **推送到底要不要**：要。"手机锁屏也能拍板/知道干完了"就必须有它，否则 C"干完找你"、B"离开 PC 拍板"都落空；但推送自带 **HTTPS 硬前置**，成本要算进去。且推送**不刷屏**：只推"任务终态"与"HITL 待处理项（待确认/待回答）"两类结论，配通知 tag 去重、页面可见即抑制、多任务合并，条数与 SSE 事件数无关。
- **真实痛点排序**：只在本机用 → 只补 长期记忆/程序性学习；要手机看/批 → 先 HTTPS 再 手机端响应式 + 主动推送 + 设备标识 + 跨端 HITL 跨设备部分；要主动提醒 → 再加 持久调度器（内核已完成）；对外代办 → 才考虑 执行端抽象 + 跨域代表。
- **说人话**：先把"手机能安全访问（HTTPS）+ 干完能叫醒你 + 到点能自己干"做成，再把"教一次就能复跑"加上；其余接口等真有需求再写，别为想象中的场景提前搭架子。
