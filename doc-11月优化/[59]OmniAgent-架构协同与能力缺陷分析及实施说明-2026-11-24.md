## 一、现状分析与基础能力

### 1.1 系统现状（一句话）

基于 **ReAct 的单 Agent**、面向 **Windows 本机**、**本地私有化**的全栈 Web 应用：Python/FastAPI + React，**11 类 67 工具**，任意 OpenAI 兼容模型，**四层安全（L0-L3）+ HITL + DB 事务回滚**，SQLite 5 库、数据不出机。

它已经是"能干的 Agent + 一台自己的 Windows 电脑 + 一套过硬的安全防线（危险直接拦、有风险问人）"，不做云 VM、不做截图坐标，走 **Windows API/命令直调**的确定性路线。

### 1.2 已具备的基础能力（复用地基，禁止重造）

| 能力 | 代码落点 | 对扩展的价值 |
|---|---|---|
| 任务是"一等实体"（chat_tasks + 消息锚 + files_dir） | `stream_orchestrator._create_and_launch_task` | 任务不依赖某条前端连接，可被任意端查询/订阅 |
| 事件缓冲带单调 seq | `task_state.StreamBuffer`（task_state.py:50）`publish`+`publish_lock` | 事件可排序、可回放，是多端同步的地基 |

### 1.3 宿主假设：单进程·单用户·多会话·多任务（客观边界）

> 澄清一个容易混淆的点：**"单进程"指进程数为 1，不代表"单任务"或"单会话"**。当前是多会话（`chat_sessions` 多行）、多任务并发（`running_tasks` 按 `task_id` 多键、asyncio 同进程并发）的形态；真正受限的是**没有并发上限**（见下表 A 行）。

| 编号 | 宿主假设 | 代码证据 | 破绽 |
|---|---|---|---|
| A | 执行态在内存、无队列，并发有上限（2026-11-24 已设闸门） | `running_tasks`（task_state.py:42，`dict[task_id]` 多键并存→可并发）、`StreamBuffer.cond`、`_agent_tasks`；`agent.max_concurrent_tasks`（默认 3）+ `run_agent_gated` 信号量闸门已落地 | 进程重启 → 跑到一半的**执行**蒸发（中断本身已被诚实标注，不再误显示"执行中"）；并发已封顶，超限在闸门内排队，仍有**背压提示缺失**（排队期前端无"等待中"字样，用户只看到未开始） |
| B | 事件只有 HTTP-SSE，无主动推送 | 全仓仅 SSE/REST；前端无 `sw.js`/`manifest`/`vite-plugin-pwa`，后端无 `pywebpush`/VAPID | 手机锁屏、切后台 → 收不到"任务终态 / 待确认 / 待回答"。**新增硬约束见 3.2** |
| C | 单口令鉴权，无设备/端身份 | `security.access_token` + `verify_token`（deps.py） | 无法区分设备、无法定位"谁处理的" |
| D | 执行能力钉死宿主 Windows | tools/ 全是本机能力 | 手机只能当遥控器，无法"换端执行" |
| E | 调度器非持久 | `timer_set._timers`（timer_set.py:36）用 `asyncio.call_later`（:147）；timers 表只记状态 | 重启丢定时，"到点提醒/主动执行"不可靠 |
| F | 单机单进程，无队列/worker/网关 | 5 库 + 单事件循环，任务用内存注册表 | 公网接入缺配对/隧道/加密/限流 |

## 二、针对应用方向的缺陷

脱离应用方向谈缺陷，就会变成"什么都要补"。先把方向摆清楚，再看每个方向被什么卡住。

### 2.1 四个应用方向

| 方向 | 场景描述 | 你要的核心体验 |
|---|---|---|
| **A 本机单端深度使用** | 只在 PC 上，一个人用 | 长任务别丢、越用越顺手 |

### 2.3 结论：为什么"地基已成型、只补真空白"

- **只做 A（本机单端）**：真正该补的只有"3.7 程序性记忆"一项（3.1 已完成），其余都不必做。
- **要做 B（多端）**：绕不开"3.2b 推送 + 3.6 跨端 HITL"；3.3 设备标识取最轻一档即可（20 行级），不必建完整注册体系。
- **要做 C（主动）**：绕不开"3.5 持久调度器 + 3.2b 推送"——**调度器负责"到点自己干"，推送负责"干完找你"，两者是同一件事的两半，缺一半就等于白干**。
- **要做 D（跨域）**：最难，需要"3.4 执行端 + 3.8 外部握手 + 3.6 跨端 HITL 路由 + 3.7 记忆"，是一整条独立产品线，**优先级最低，现在不预建**。

由此得出实施原则：

1. **已完成的不重做**（3.1），**已成型的不改名**（3.2 总线只加 sink），避免"用新名词包装旧代码"。
2. **真空白按方向分批交付**，做一个方向就只挂它需要的那几件，不提前引入用不上的抽象（YAGNI）。
3. **无消费方的接口不预建**（3.4/3.8），等真实需求出现再设计。

## 三、逐问题分析与实施说明

每节统一回答：**问题是什么 / 现状实证 / 解决什么 / 根重要吗 / 和谁耦合 / 怎么实施**。

### 3.1 任务调度可靠性（中断可恢复 / 并发闸门 / 终态一致）

- **问题**：任务的执行态、协程句柄在进程内存（`running_tasks`、`_agent_tasks`）。后端一重启，跑到一半的执行蒸发。
- **现状实证（重要）**：**这一项已基本做完**，且做得比常见方案更严谨——
  1. `chat_tasks.status` 已落库（DEFAULT `'executing'`），配 start_time/end_time/error_type；
  2. `reconcile_orphaned_tasks`（storage.py:612）在启动期把上次遗留的 `status='executing'` 残行改终态，main.py:642 已挂到 startup；
  3. 用 `boot_iso` 做归属判据（`start_time < boot_iso`），不会误杀本次启动新建的任务；
  4. 终态复用 `failed` + `error_type='task_interrupted'`，**不新增状态值**——因 `'interrupted'` 已被前端 ToolCallLine 占用为"工具被拒"语义，新增会撞车；
  5. `duration` 明确不补算，理由写在注释里："被打断无真实耗时，补算即编造"；
  6. 前端已渲染对应文案（ErrorDetail.tsx:162）。
- **解决什么（已解决）**：系统重启后**认得没跑完的任务**，诚实标注中断、让用户看到并重发。它本就**不承诺**"跑到一半的命令接着跑"——那需要工具级快照，属于另一个量级的问题。
- **原缺口不是"队列"，是"并发约束"（已补齐）。** 曾经没有排队概念也没有并发上限——`running_tasks` 是 `dict[task_id]` 多键并存，全局查无 `Semaphore`/`max_tasks`。**"单进程"只说明进程数=1，不代表任务数=1**：会话可多个（`chat_sessions` 多行），任务也可多个并发（asyncio 在同一进程内并发跑）。该缺口已由下条"已实施"的信号量闸门收口。
- **根重要吗**：**"队列"对单用户场景是过度设计**——不需要消息队列中间件，也不需要"任务排队等待"的调度器。但**"并发上限"曾是真实缺口**：用户开多个会话同时跑重任务时，会撞 LLM API 限流、文件锁冲突、CPU 打满，且无背压、无提示（已按上条收口）。
- **已实施（2026-11-24 商量）**：新增进程级并发闸门——`agent.max_concurrent_tasks`（默认 3）+ `agent_runner.run_agent_gated`（外层 `asyncio.Semaphore` 包装，超限在此排队）。编排层 `_create_and_launch_task` 改经 `run_agent_gated` 启动。**不新增 queued 状态**（DB 仍为 executing=已受理未完成，前端词表零改动），终态链路（finally 落库/done 置位）完全未动。实测：5 个慢任务上限 3 时耗时分层（8.4/10.3/10.5s vs 17.4/19.2s），全部正常完成、零僵尸；排队期取消由 `start_step` 首查 `check_cancelled` 兜底。
- **归属阶段**：**已完成（中断恢复 + 并发闸门 + 终态一致）**。
- **关联缺陷：任务终态三处方不一致（已修复）**：实测取消任务后`task_tracker.tasks.status`落成 `failed`（`GET /tasks` 返回 `failed`），而 SSE `final.outcome` 与 `chat_tasks.status` 均为 `cancelled` —— 任务列表/历史把"已取消"显示成"失败"。
  - **根因（两层，均与并发闸门无关）**：①`react_loop._finalize_cycle` 调 `complete_task(success=(agent.status==COMPLETED))`，把五态压成布尔二值，`CANCELLED` 落入 `success=False` 分支 → 写 `failed`；②即使不压二值，取消打断发生在 `await` 点，`react_cycle` 的 `finally` 先于 `agent_runner` 的 `CancelledError` 分支执行，此刻 `agent.status` 仍是 `EXECUTING/THINKING`，直接按 `agent.status` 映射同样得到 `failed`。
  - **修复**：①`status_table` 新增 `tracker_terminal_status()` 作为 `AgentStatus → task_tracker` 终态值唯一映射源（`CANCELLED→cancelled`，非终态按 `failed`）；②`TaskStatus` 补 `CANCELLED`，`TaskTracker.complete_task` 签名由 `success: bool` 改为 `status: str`（禁布尔三态混淆，不做兼容层）；③`step_emitter.complete_task()` 无参化，读 `agent.status` 翻译落库；④`react_loop._finalize_cycle` 收尾前用新增的同步 `task_state.is_cancel_requested()`（与 `check_cancelled` 同源字段）按取消标记补 `set_cancelled`，`set_cancelled` 自身终态不可变，已完成/已失败不受影响。
  - **实测（真实后端 + 真实 LLM + 真实 SQLite，三场景）**：工具执行中取消 / LLM 思考中取消 / 排队期取消（闸门上限 3），SSE、`chat_tasks`、`task_tracker` **三处全部 `cancelled`**；回归：正常完成仍为 `completed / completed / success`。
- **前次记录的更正**：上一版本把根因写成 `agent_runner.py` 的 `_STATUS_MAP` fallback，经实测不成立（该路径在该场景未触发，`chat_tasks` 始终正确为 `cancelled`，错的只有 `task_tracker`），此处已按实测重写，原判断作废。

### 3.2 事件总线与主动推送（含"单通道"）

原文把"总线"和"推送"合成一项，实际两者成熟度完全不同，须分开看。

#### 3.2a 事件总线 —— 复用内核形态，但新增的是独立总线（附理由）

- **现状实证**：`StreamBuffer`（task_state.py:50）**已经就是**单生产者、多订阅者的缓冲：
  - `event_log` append-only 列表（:61），每帧带单调 `seq`；
  - `cond: asyncio.Condition` + `cond.notify_all()`（:62/:84）—— 这本身就是向所有等待者广播；
  - 已有两个 sink 挂点：`persist_sink`（:70）、`flush_sink`（:73），注释明确"挂在 publish 收口而非调用点，因事件有三条发布路径，挂调用点必漏"。
- **结论**：**不需要把 `StreamBuffer` 改名为 `EventBus`**——那属"改名不升级"，违反 KISS。
- **已实施（2026-11-24 商量，详见 [60] 号文档）**：**没有**在 `StreamBuffer` 上再挂 sink，而是新增一条独立的**生命周期事件总线** `app/services/task/event_bus.py`（全局单例 `EventBus` + `publish_event`），配 `GET /chat/events`（SSE）下发。两条总线职责正交、不可合并：
  - `StreamBuffer`（按 task）：AI 正文，有 seq + Journal + `after_seq` 续传，**不许丢**；
  - `EventBus`（全局）：变更信封，无 seq、不落库、**允许丢**，丢了靠重连对账（拉 `/sessions/tasks/running` 比对锚点）。
- **为什么原判断"只需再挂一个 sink"落不了地（实证）**：`StreamBuffer` 的生命周期是 `task_id`，任务终态后即被 `reclaim_memory_buffer` 回收；而"任务终态"恰恰是必须发出的两类通知之一——**挂在一个随任务消亡的缓冲上，通知自身就没有可靠的发出时机**。"新任务诞生"同理：那时 buffer 才刚创建，也无从由它广播"任务存在"。故按"功能只能正确、不退化"的原则改为独立总线，而非硬塞进 `StreamBuffer`。
- 实测：发消息 → 前端收到 `task_started` 仅 **502ms**（替代原 3 秒查库轮询）；续跑新建 task_id 同样即时广播。**替代掉了 ChatPage 每 3 秒一次 SQLite 查询**。
- **铁律（已遵守）**：**沿用"每任务单生产者 + seq 单调"，坚决不做全局 seq**——全局 seq 会让回放/续传全乱。正因如此，新的 `EventBus` 刻意**不带 seq**（只做通知），从设计上避免触碰该铁律。

#### 3.2b 主动推送 —— 真空白、真必要，但有硬前置

- **问题**：事件出口只有 HTTP-SSE。手机一锁屏/切后台/杀进程，就收不到"任务终态 / 待确认 / 待回答"。所谓"单通道"，本质就是这个。
- **先把最容易被误读的一点说清：推送不是把 SSE 事件流复制一份发出去。** 推送只发两类"结论"，中间过程一律不推：

  | 会推送的（仅两类） | 永不推送的 |
  |---|---|
  | 任务进入终态：完成 / 失败 / 取消 | 思考过程 thought、工具调用与返回 observation、进度百分比更新 |
  | HITL 待处理项出现：待确认（`hitl_confirmation`）/ 待回答（`hitl_question`） | 以上全部中间事件 |

  **一个跑 10 分钟、产生几百条 SSE 事件的任务，推送只有 1 条**（终态那一条）。条数只与"任务结束次数 + HITL 弹窗次数"有关，**与 SSE 事件数无关**，不存在"成千上万条通知"。一个任务如果中途要确认 3 次，最多 3+1=4 条，且靠 `tag` 去重后通知栏同时只留最新一条。

  > 术语说明见 3.6「先正名」：这里只推"待确认 / 待回答"，**不推"危险操作"**——危险项（`blocked`）由安全层直接拦截，压根不产生待处理项，也无从推送。

- **前端具体场景（什么时候真的需要它）**：

  | 场景 | 现在的表现 | 有推送后 | 该场景推送条数 |
  |---|---|---|---|
  | PC 浏览器开着、人就在旁边 | SSE 实时，**够用，不需要推送** | 页面可见即抑制，行为与现在一致 | **0 条**（见下方配合项①） |
  | PC 浏览器关掉/切到别的标签页 | 页面不可见，SSE 可能被浏览器节流/断开 | 任务结束时弹 1 条浏览器通知 | **1 条**（该任务终态） |
  | 手机打开网页后锁屏 | **完全收不到** | 锁屏通知栏 1 条 | **1 条**，不是每条事件 1 条 |
  | 手机切到微信/其他 App | SSE 断开，回来靠 after_seq 补历史 | 后台收到通知，点开后补齐断线期间内容 | **1 条** |
  | 长任务（10 分钟+）期间人去吃饭 | 只能定期回来看 | 干完主动叫一次，不用守着 | **1 条** |
  | 需要确认的风险操作 | 只能等页面开着才发现 | 推送"需要你确认"，及时拍板 | **1 条/每次确认** |

  > **判据**：**人在屏幕前 → 不需要推送；人离开屏幕 → 必须推送**。推送的价值不在于"更快看到"，而在于"不用守着"。

- **为什么不会刷屏（四条硬约束，实现时必须全给）**：
  1. **只挂两类触发点**：任务终态、HITL 待处理项（待确认 / 待回答）。中间事件全不推，这是一条任务通知条数的根本上限。
  2. **通知带 tag 去重替换**：调用 `showNotification` 时传 `tag=task_id`（HITL 传 `tag=hitl_id`），同 tag 的通知在通知栏**替换**而非堆叠。即使后端误连发三次，用户也只看到一条。
  3. **页面可见即抑制**：主要靠前端——`document.visibilityState === 'visible'` 时收到 push 也不展示通知（WebPush 是服务端推给浏览器推送服务，**后端无法感知设备是否在前台**，只能由前端这最后一跳自我抑制）。后端可再叠一层"最近活跃时间"粗过滤（复用现有审计字段，非在线表），减少无谓推送。
  4. **时间窗合并**：3 秒内多个任务同时终态，合并成一条"3 个任务已完成"，不做 N 条并列。

- **推送后前端必须配合什么（缺任何一条，推送就是纯骚扰）**：

  | 配合项 | 具体做法 | 不做会怎样 |
  |---|---|---|
  | ① 可见性抑制 | 前端页面可见时不展示通知；后端按"最近活跃时间"粗过滤 | 人就在电脑前，手机还在响，纯骚扰 |
  | ② 去重替换 | `showNotification` 带 `tag` | 同一任务重复提醒堆成一片 |
  | ③ 点击定位 | `notificationclick` → 已有窗口则 `focus()` 并跳到该 `task_id`；未开窗口则 `openWindow('/?task=xxx')`，前端读 URL 参数定位任务，再靠 `after_seq` 补齐断线期间事件 | 点了通知只打开首页，还得自己翻任务 |
  | ④ 权限克制 | 只在用户手势（点"开启通知"按钮）后调 `requestPermission`；被拒后不反复弹，改在 UI 提示去设置里开 | 一进页面就弹权限框，用户直接永久拒绝 |
  | ⑤ 开关分级 | 全局开关 + 按类型开关（终态 / 待确认 / 待回答），持久化在订阅表与 localStorage | 全是强提醒，用户很快把推送整体关掉 |

  > **分工一条线**：**推送只负责"叫醒"，不携带正文真相；SSE + Journal + after_seq 负责"点开看全貌"**。正因为正文不走推送，推送才允许丢、允许重复（靠 tag 去重、靠回放补齐），代价只是"没被及时叫醒"，不会丢数据。

- **为什么说真必要（不是过度设计）**：
  - **C 方向的核心体验是"到点自己干、干完找你"**——调度器负责"干"，推送负责"找你"。**没有推送，主动助理等于白干，干完没人知道**。
  - **B 方向的核心体验是"离开 PC 也能拍板"**——需要你确认时锁屏能响一下，否则"SSE 断线续传"只有在页面开着时才有意义。
- **硬前置（原文档遗漏，必须先解决）**：**Service Worker 只能在 HTTPS 安全上下文注册**（`localhost` 除外）。当前是"本机 HTTP + 局域网 `http://192.168.x.x:port`"访问，手机端 **SW 注册会直接失败，WebPush 不可用**。三条可选路径：
  1. 自签证书 + 手机安装信任 —— 免费，但每台设备需手动信任一次，证书到期要换；
  2. 内网 HTTPS 反代（带域名/证书）—— 干净，需要域名与证书维护；
  3. 隧道服务 —— 最省事，但与"数据不出机"的定位冲突，不建议。
  > 结论：**推送不是"顺手加一行"，它自带一个 HTTPS 工程前置**。这个前置的成本要算进评估，否则会误判为"直接做就行"。
- **另一个平台限制**：iOS 的 WebPush 需 16.4+，且**必须"添加到主屏幕"以 PWA 形式打开**才生效，浏览器内直接访问收不到。安卓 Chrome 无此限制。
- **解决什么**：任务终态 / HITL 待处理项出现时"叫醒"人；推送允许不可靠，丢了靠 Journal + after_seq 回来补（见上"分工一条线"）。
- **根重要吗**：做 B/C 是必需；只做 A（PC 常开、人在旁边）则不必。
- **和谁耦合**：消费 3.2a 的 `EventBus`（订阅变更信封，作为 WebPush sink 的数据源）；依赖 3.3 知道推给哪台设备。
- **怎么做**：
  1. 后端：VAPID 密钥对 + 订阅表（endpoint/p256dh/auth/device_id）+ 订阅/退订端点 + **WebPush sink 实现**（订阅 `EventBus` 的 `task_ended` / `hitl_pending` 两类信封，翻译成推送载荷，约 200 行）；
  2. 前端：`manifest.json` + `sw.js`（只做 push 事件与 click 跳转）+ 权限申请与订阅注册（约 150 行）；
  3. 触发点严格只有两类（见前"为什么不会刷屏"第 1 条）：**任务终态**、**HITL 待处理项**（待确认 / 待回答，语义见 3.6）；
  4. **一期只做 Web/PWA**，邮件/IM 等多渠道留作后续 sink 扩展点，不提前抽象。
- **归属阶段**：**阶段 2（推送 + 多端看批）**，且**必须排在阶段 1（HTTPS 前置）之后**。

### 3.3 设备标识（原"会话-设备-身份"）

- **问题**：单口令鉴权，后台不知道"这条指令来自 PC 还是手机""谁有权处理 HITL"。
- **现状实证（半个基础已存在）**：前端 `clientInfo.ts` 已采集 `client_os / browser / device / network`，随消息经 `messages.py:49` → `message_service.py:340` → `storage.py:1018` 落库到 `chat_user_message`。**所以"识别客户端画像"已经做了**；缺的是两样：① 跨会话**稳定的 `device_id`**（现在每次按 UA 解析，同一台手机换个浏览器就变 label）；② 把设备归属用于**推送目标选择**与**HITL 处理审计**。
- **解决什么**：真实需求只有一句话——**审计与提示时能说清"这是哪台设备在处理"**。
- **根重要吗**：做 B/D 有影响；只做 A 不必。
- **分两档，先做轻的那档**：
  - **轻量档（够用，推荐一期）**：**复用已有 `clientInfo` 采集，只补一个稳定 `device_id`**——前端首次访问生成 UUID 存 `localStorage`，随请求头带；后端写入现有审计字段。约 20 行，无新表、无配对流程。
  - **完整档（暂不需要）**：配对码 → 设备 token → 心跳/在线表 → 会话与设备多对多 → 主控端。**只有需要"按设备收回权限""设备级远程注销"时才值得**，当前无此需求，不预建。
- **信任边界（无论哪档都要明确）**：设备标识的信任根仍是单口令——口令泄露等于全部设备失陷。若将来上"完整档"，口令变更须吊销所有设备 token 并重新配对。
- **归属阶段**：**阶段 2，且必须先于 3.2b 落地**——推送必须知道"推给哪台设备"，没有稳定 `device_id` 时只能退化为"该用户全部订阅都推"，直接造成"人在电脑前，手机也跟着响"。完整档不排期。

### 3.4 手机端接入方式与执行端抽象

这一节要先回答一个前置问题：**手机到底怎么接进来？** 接入方式不同，"要不要执行端抽象"的答案完全不同。

#### 3.4.1 三种接入方式（成本差异巨大）

| 方式 | 具体做法 | 现有基础 | 成本 | 适合 |
|---|---|---|---|---|
| **(a) 现有 Web 前端做响应式** | 同一套 React 代码，加移动断点，手机浏览器直接访问 | `index.html` 已有 viewport meta；`clientInfo.ts` 已有 UA 识别；但**响应式只覆盖 9 个文件**（Layout/NavContent/Skeleton/ToolCallLine），**聊天主界面（消息流/输入框/任务面板）尚无移动适配** | 中 | 一期推荐。一套代码、无需发版、改完即用 |
| **(b) 独立移动端 App** | React Native / Flutter / Capacitor 套壳 | **零基础**（package.json 无 capacitor/cordova/react-native/antd-mobile） | 大 | 需要原生能力（后台推送更稳、本地文件/相机）时才考虑 |
| **(c) 集成到第三方 IM** | 微信/飞书/钉钉机器人、小程序 | **零基础**，且受平台限制：IM 卡片做不了复杂交互（多选 / 多题 / 文件预览） | 中 | 只做"通知到人"，不做"看+处理"主界面 |

**建议路径**：**一期走 (a) 响应式**——现有前端已有 viewport 和 UA 识别的基础，补齐聊天区移动布局即可；推送用 WebPush（配 3.2b 的 HTTPS 前置）也能覆盖锁屏提醒，(b) 的原生优势（后台推送稳定）在这个阶段不值得翻倍成本。若后续发现"iPhone 必须加到主屏才能收推送"这个体验无法接受，再评估 (b)。

#### 3.4.2 关键概念：客户端 ≠ 执行端

无论走上面哪种方式，手机在这个阶段都只是**客户端**，不是**执行端**：

| 概念 | 职责 | 现有 | 需要什么 |
|---|---|---|---|
| **客户端（client）** | 看进度、处理确认与问询、发指令 | Web 前端（含未来移动适配版） | 只需 3.2b 推送 + 3.3 设备标识 + 3.6 跨端 HITL 路由 |
| **执行端（executor）** | 真正跑工具、动文件、调命令 | 只有 PC（后端进程本身） | 需要 `Executor` 接口 + 能力注册 + 分派 |

**这就是"多端"和"执行端"的区别**：手机作为客户端接进来（看进度 / 处理 HITL）→ 任务仍在 PC 上跑 → **不需要执行端抽象**；只有要求"手机自己也能本地执行"（比如读手机相册、取定位、调手机上的 App）→ 才需要执行端抽象。

#### 3.4.3 执行端抽象：当前不预建

- **现状实证**：全部工具均为本机动作，无执行端注册/分派机制，也**没有任何消费方**。
- **结论**：**当前不预建**。一期手机走 (a) 响应式、"看 + 批"模式，**没有第二个执行端存在**。此时定义 `Executor` 接口（register/heartbeat/execute/cancel）、能力协商、能力标签映射，全是**为不存在的场景写抽象**，是最典型的 YAGNI 违反。
- **何时才需要**：真要"手机本地干活"，或"用浏览器执行端跑跨域任务"（D）时。届时按真实需求设计，比现在拍脑袋定义的接口更准。
- **归属阶段**：**不排期，等 D 方向或其他真实执行端需求出现时再评估**。

### 3.5 持久化调度器

- **问题**：`timer_set` 用内存 `asyncio.call_later`（timer_set.py:36/:147），重启即丢；timers 表只记状态。这是"主动助理"的核心缺口——**没有可靠的到点触发器**。
- **现状实证（好消息）**：**timers 表结构已完全就绪**——`timer_id / delay / callback / created_at / trigger_at / triggered_at / status='active'`。缺的只是"启动时把 active 且已到期的重建为 `call_later`"这一段逻辑。
- **解决什么**：timers 表驱动、重启可恢复的调度器，支持"到点创建任务 / 提醒 / 发起 HITL 确认"。
- **根重要吗**：做 C 方向必需要，且是**当前投入产出比最高的一项**——表已就绪、逻辑简单、收益直接。
- **和谁耦合**：触发的任务复用 `_create_and_launch_task`；完成通知走 3.2b 推送（**两者是 C 方向的两半，建议一起做**）。
- **怎么做**：
  1. 启动扫描 `status='active' AND trigger_at<=now` 重建调度，已过期的立即触发（或按策略补偿）；
  2. 触发动作统一走"创建任务"（复用 `_create_and_launch_task`），**不直接调 HTTP**；
  3. 单进程用"轮询 + 最近到期最小堆"即可，1 秒粒度对单用户足够，**不引入消息队列/APScheduler 之类中间件**（YAGNI）。
- **已实施（2026-11-25 商量）**——**后端内核已落地并实测**（放弃轮询+最小堆，改用 `loop.call_later` 句柄 + 启动重建，与既有 timer 实现同构、零新依赖）：
  1. `timers` 表加 `session_id` 列（`_ensure_column` 幂等迁移，新库 CREATE 已含）；`timer_set` 落会话（取自新 ContextVar `get_current_session_id`，`tool_executor` 从 `agent._start_meta` 注入并 finally 清理）。
  2. 触发动作**统一走"回会话建任务"**：经 app 层注入的回调 `resume_session_with_notice`（tools 层禁 import services，用 `set_timer_resume_callback` 注入解越层；复用其"有活跃任务→注入 / 无→建新任务"双路，不直接调 HTTP）。无会话/无回调时维持原 log/http 行为。
  3. 新增 `rebuild_timers_from_db()`：启动扫 `status='active'`，未到期按剩余秒重建 `call_later`、已过期立即补触发一次（不丢"到点该干"语义）、非 active 跳过；`main.py` startup 注入回调后调用，失败降级不阻断启动。
  4. **实测**（隔离数据目录，真 SQLite）：DDL 幂等、`session_id` 落库、到点触发回调带正确 session、跨进程"重启恢复"（进程A 落 3 行 active，进程B 新解释器恢复 → 未到期重建 2 / 过期补触发 1，且过期任务正确回到该会话建任务），全部 PASS。
- **遗留（仍属阶段 3 后半，依赖推送）**："干完找你"（触发后离开页面也能收到通知）依赖 3.2b WebPush，留待推送就绪再挂；调度内核与通知两半按文档原意分批交付。
- **归属阶段**：**后端调度内核（启动重建 + 到点建任务）已完成**；"干完通知"随阶段 2 推送。

### 3.6 跨端 HITL 路由

- **先正名（原文档此处用语错误，必须纠正）**：本节讨论的不是"审批"。系统里**没有"审批"这个机制**，HITL 只有两套，且 `blocked`（危险）根本不问人：

  | 概念 | 代码落点 | 语义 | 是否问用户 |
  |---|---|---|---|
  | **硬拦** | `SafetyResult.blocked=True` + `BLOCK_LEVELS` | 真危险：磁盘根/系统禁区、危险命令、非法路径、未注册工具 | **不问，直接拒绝**。弹窗只作诊断留痕，前端不消费 |
  | **需确认** | `SafetyResult.needs_confirm=True` + `CONFIRM_LEVELS` | 有风险/越权：白名单外删除、非禁区写入、中风险命令（重启/改执行策略/杀进程）、含读/写/删动作的命令、`execute_sql`、任务与注册表操作 | **要问**，进 HITL 弹窗 |
  | **hitl_confirmation** | `hitl_confirmation.py`：create / wait / resolve | 征求同意：确认 / 拒绝，可选"信任本次会话"（落 `chat_session_trust`） | 要问，二值 + 信任 |
  | **hitl_question** | `hitl_question.py`：create / wait / resolve | 收集答案：`question` 工具问询，多题多选 + 自填 | 要问，**无信任语义** |

  > 一句话记法：**危险的（blocked）直接拦，不问；有风险的（needs_confirm）才问；问分两种——要不要干（confirmation）、要什么信息（question）。**
  > 所以本文后续一律用"**待确认 / 待回答**"或合称"**HITL 待处理项**"，不再使用"审批"。

- **问题**：确认与问询目前都是"当前会话前端弹窗"，只能弹在发起的那台设备上；换个设备就看不到、也处理不了。
- **现状实证**：HITL 双向端点已存在（`confirm` / `answer`，见 `chat_routes.py`）；确认/问询经内容流的 `interact` 帧（`kind=confirm|question`）投递，弹窗由 `chatStreamStore.pendingAuthorization` / `pendingQuestion` 驱动。
- **解决什么**：把 HITL 待处理项广播到"在线且被授权的端"，**任一端处理即收敛**；并定义超时/降级。
- **根重要吗**：多端同时用（B）或跨域代理需人工把关（D）时才需要；单端用不必。
- **和谁耦合**：HITL 请求走 3.2a 的 `EventBus`（变更信封）+ 3.2b 推送（离开页面时叫醒）；用 3.3 轻量档的 device 标识记录"谁处理的"。
- **已实施（2026-11-24 商量，详见 [60] 号文档）**——**"可见性"与"收敛"两半已落地**：
  1. **待处理项进事件链路**：`create_confirmation` / `create_question` 播 `hitl_pending`（信封只带 `hitl_id/kind/task_id/session_id` + `tool_name`/`count`，**不含弹窗正文**）；`resolve_*` 播 `hitl_settled`。
  2. **跨会话告知**：新增 `GET /chat/hitl/pending` 权威快照（对账用），前端 `hitlPendingStore` 收信封 + 重连/切回可见时对账，顶栏新增 `HitlPendingPill` 角标，点击直达该会话。
  3. **任一端处理即收敛**：`hitl_settled` 广播后其余端角标自动消失（已实测）；重复提交天然安全（`resolve_*` 对已 done 的 future 返回 False）。
  4. **弹窗详情不搬进信封**：仍由会话内容流的 `interact` 帧提供——已实测证明切到该会话后 `GET /chat/stream/{task_id}?after_seq=0` 的流内确实含 `interact` 帧且 content 带完整信息（目标路径/拦截原因/授权时效），故"点角标 → 跳会话 → 弹窗出现"整条链路成立。
- **与原方案的偏离（须记录）**：原文"怎么做"第 2 条要求"**首次领取即锁 + 租约（TTL）**"。**本期刻意不做**：本设计允许多端同时看到同一项、谁先处理谁生效，靠 `resolve_*` 幂等 + `hitl_settled` 收敛即可，无需领取锁，也就没有"设备领了掉线 → 审批永久锁死"的问题（KISS-DIRECT，不为不存在的锁引入租约复杂度）。若将来出现"多端并发处理导致误操作"的真实痛点，再按原方案补租约。
- **超时策略（沿用既有实现，非新做）**：默认暂停；**超时默认拒绝**（`hitl_confirmation` 超时按未授权处理，见其 `expired=True` 分流）；`question` 超时返回空答案并标记 `expired`，由上层决定是否继续。
- **剩余部分（阶段 2）**：跨**设备**（手机）处理仍受 3.3 `device_id` 与 HTTPS 前置限制；离开页面时的"叫醒"依赖 3.2b WebPush。
- **归属阶段**：可见性/收敛部分**本期已完成**；跨设备部分属**阶段 2**。

### 3.7 长期记忆 / 程序性学习

- **问题**：目前只有"会话历史 + 上下文压缩"（`compaction/`、HistoryMemory），没有独立用户画像、没有跨会话长期记忆、没有"上次怎么做的、下次如何更快更省"的程序性记忆。（已核实：全仓 `memory/profile` 关键词均指进程内存或模型能力画像，无个人记忆模块。）
- **解决什么**：这是"personal"的核心——**越用越懂你、一件事教一次即可复跑**。缺它，每次都要重述需求，像陌生人。
- **根重要吗**：**对"个人助理"这个定位，这是最该补的短板**，且对 A/B/C/D 全部有影响。它不依赖多端、不依赖推送，**可以独立、优先做**。
- **但"三件套一起做"不算最小可行**：原文把"画像表 + 跨会话事实库 + 程序性记忆"打包称"最小可行"，实际是三个子系统。**建议只先做程序性记忆**：
  - **程序性记忆（先做，零新表）**：`chat_task_steps` 已完整记录每个任务的步骤序列，可直接沉淀为"可复跑流程模板"，下次同类任务直接套用。这是**收益最高、成本最低、且不引入新概念**的一刀。
  - **用户画像（后置）**：结构化偏好（常用路径、口头习惯、授权偏好）一张表，等程序性记忆跑通、确有"每次都要重述偏好"的痛点再加。
  - **跨会话事实库（后置）**：SQLite + 简单检索即可，**不引入向量库**。
- **附加约束（避免埋坑）**：记忆注入沿用现有 message_builder，不新增 LLM schema 参数；**注入量必须设预算与裁剪策略**（复用 compaction 的容量控制思路），否则记忆会膨胀挤占任务上下文。
- **和谁耦合**：与 3.5（例行任务复跑依赖程序性记忆）相关；与多端/推送无关。
- **归属阶段**：**阶段 4（记忆）**，但**可独立启动**——不依赖阶段 1~3 的任何产出，想先做就能先做。

### 3.8 跨域代表（跨域外部系统握手）

- **问题**：只会本机动作，不涉"登录外部网站、代表你去下单/改签/填表"。
- **现状实证**：无任何对外握手机制。
- **根重要吗**：**只在你确实要"对外代办"（D 方向）时才需要。** 成本与风险最高（账号安全、外部失败代价、合规），且依赖 3.4 执行端——而 3.4 也已判定为"不预建"。
- **结论：当前不排期、不设计。** 它属于"另一条产品线"，写进路线图会被误当成待办。等内容/需求真正指向 D 方向时再立项，届时：
  1. 先接 MCP/OpenAPI 这类标准握手，而非硬编码各家；
  2. 对外动作强制"确认 + 审计 + 可回滚"（复用现有四层安全）；
  3. 按服务细分权限作用域（只读/可读可发），而非一个大开关。
- **归属阶段**：**不排期（待定项）**。

## 五、一句话总结

- **"要不要一体化"**：**不需要**。真正要做的只有 3 件事——**推送、持久调度器、程序性记忆**，加 2 处 20 行级小补齐（push sink、设备标识）；走 B 方向（多端看进度 + 处理 HITL）另需 2 项配套（手机端响应式接入、跨端 HITL）。
- **哪些是过度设计**：`EventBus` 新抽象的改名（`StreamBuffer` 已具备，只缺 sink）、完整设备注册体系（20 行够用）、`Executor` 接口预建（无消费方）、跨域代表立项（另一条产品线）、记忆"三件套打包"（程序性记忆可零新表起步）。
- **哪些已完成别重做**：3.1 三项均已落地并实测——①中断可恢复（`chat_tasks.status` 落库 + 启动期 `reconcile_orphaned_tasks` + 前端文案，端到端闭环）；②并发闸门（`agent.max_concurrent_tasks` 默认 3 + `run_agent_gated` 信号量排队，30 行级，未引消息队列）；③取消终态三处一致（`tracker_terminal_status` 单一翻译源，`cancelled` 不再误记 `failed`）。
- **手机怎么接进来**：一期走**现有 Web 前端响应式改造**（已有 viewport + `clientInfo` UA 识别基础，但聊天主界面尚无移动适配），不做独立 App、不集成第三方 IM。手机在"看进度 + 处理 HITL"模式下是**客户端不是执行端**，任务仍在 PC 跑，故**不需要执行端抽象**。
- **推送到底要不要**：**要**。确认"手机锁屏也能拍板/知道干完了"就必须有它，否则 C 方向"干完找你"、B 方向"离开 PC 拍板"都落空。但它自带 **HTTPS 硬前置**（SW 只在安全上下文注册），这部分成本要算进去。**且推送不刷屏**：只推"任务终态"与"HITL 待处理项（待确认 / 待回答）"两类结论（跑 10 分钟几百条事件也只推 1 条），配合通知 tag 去重、页面可见即抑制、多任务合并，条数与 SSE 事件数无关。
- **上一阶段的 4 项缺陷落点**：`无队列/检查点` → 3.1（中断恢复与并发上限均已完成，无需队列）；`单通道` → 3.2b（真必要）；`无长期记忆/程序性学习` → 3.7（程序性记忆优先）；`不跨公司代表` → 3.8（不排期）。
- **真实痛点排序**：只在本机用 → 只补 3.7 程序性记忆；要手机看/批 → 先做 HTTPS 前置，再做手机端响应式（3.4.1）+ 3.2b + 3.3 + 3.6；要主动提醒 → 再加 3.5；对外代办 → 才考虑执行端抽象（3.4.3）+ 3.8。
- 说人话：**先把"手机能安全访问（HTTPS）+ 干完能叫醒你 + 到点能自己干"这三件做成，再把"教一次就能复跑"加上；其余接口等真有需求再写，别为想象中的场景提前搭架子。**
