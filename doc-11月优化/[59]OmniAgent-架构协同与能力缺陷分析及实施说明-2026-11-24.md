# OmniAgent 架构协同与能力缺陷分析及实施说明

> 本文回答两个问题：
> **① 6 项架构扩展，必须"一体化协同更新"吗？**
> **② 上一阶段的 4 项能力缺陷（无长期个人记忆/程序性学习、不跨公司代表、单通道、无队列/检查点）与这 6 项是什么关系，能不能按阶段、分方向实施？**
>
> 立场：本文不以"要做大做全"为默认目标。判断标准只有一条——**是否卡住你要的那个应用方向**。其余一律视为"现在不必做"，避免过度设计。
>
> 证据：全部基于本地源码核实（`README.md`、`backend/app` 下 task / chat / agent / tools / safety / services），不臆测。

---

## 一、现状分析与基础能力

### 1.1 系统现状（一句话）

基于 **ReAct 的单 Agent**、面向 **Windows 本机**、**本地私有化**的全栈 Web 应用：Python/FastAPI + React，**11 类 67 工具**，任意 OpenAI 兼容模型，**四层安全（L0-L3）+ HITL + DB 事务回滚**，SQLite 5 库、数据不出机。

它已经是"能干的 Agent + 一台自己的 Windows 电脑 + 一套过硬的安全审批"，不做云 VM、不做截图坐标，走 **Windows API/命令直调**的确定性路线。

### 1.2 已具备的基础能力（复用地基，禁止重造）

| 能力 | 代码落点 | 对扩展的价值 |
|---|---|---|
| 任务是"一等实体"（chat_tasks + 消息锚 + files_dir） | `stream_orchestrator._create_and_launch_task` | 任务不依赖某条前端连接，可被任意端查询/订阅 |
| 事件缓冲带单调 seq | `task_state.StreamBuffer`（task_state.py:49）`publish`+`publish_lock` | 事件可排序、可回放，是多端同步的地基 |
| 运行期逐步落库 | `persist_sink` / `flush_sink` | 事件不只在内存，刷新/换端可重建 |
| Journal 回放 | `publish_with_journal` | 断连后按序号补发 |
| SSE 断线续传（after_seq） | `/chat/stream/{task_id}`、`execution_stream.py`、`task_runtime.py` | 手机断网/切后台/换标签可续读 |
| agent 后台协程执行 | `run_agent_in_background`（stream_orchestrator.py:1129） | 执行不绑 HTTP 请求生命周期 |
| 任务控制面：暂停/恢复/取消/运行中注入 | `task_runtime.py`、`task_registry.py` | 多端可对同一任务下发控制指令 |
| HITL 双向端点 | confirm / answer（`chat_routes.py`）、`hitl_confirmation.py`、`hitl_question.py` | 天然可"在另一台设备上审批" |
| 后台命令完成唤醒续跑 | `resume_session_with_notice` + `inject_system_notice`（stream_orchestrator.py:1137） | 长命令完成可自动推进 |
| 数据与产物 | SQLite 5 库 WAL + `files/` + `assets` 静态托管 | 可做多端读取与下载 |

**判断：这些都是真资产。扩展时"升级接口、复用内核"，不推倒重来。**

### 1.3 仍是"单体·单进程·单用户"的宿主假设（客观边界）

| 编号 | 宿主假设 | 代码证据 | 破绽 |
|---|---|---|---|
| A | 运行态全在内存 | `running_tasks`（task_state.py:42）、`StreamBuffer.cond`、`_agent_tasks`、`_timers` | 进程重启/PC 休眠 → 运行中任务蒸发 |
| B | 事件只有 HTTP-SSE，无主动推送 | 全仓仅 SSE/REST，无 WebSocket / 推送 | 手机锁屏、切后台 → 收不到"完成/需审批" |
| C | 单口令鉴权，无设备/端身份 | `security.access_token` + `verify_token`（deps.py） | 无法区分设备、无法定位"谁在批" |
| D | 执行能力钉死宿主 Windows | tools/ 全是本机能力 | 手机只能当遥控器，无法"换端执行" |
| E | 调度器非持久 | `timer_set._timers` 用 `asyncio.call_later`；timers.db 只记状态 | 重启丢定时，"到点提醒/主动执行"不可靠 |
| F | 单机单进程，无队列/worker/网关 | 5 库 + 单事件循环，任务用内存注册表 | 公网接入缺配对/隧道/加密/限流 |
| G | 无长期记忆与画像 | 仅有会话历史 + 上下文压缩（`compaction/`、HistoryMemory）；**无独立用户画像/长期个人记忆/程序性记忆** | 每次都要重述需求，无法"越用越懂你、教一次可复跑" |
| H | 不能代表用户触达外部系统 | 工具均本机动作；无 OAuth/MCP/Poppy 之类对外握手 | 不能"登录外部网站代表你下单/改签" |

### 1.4 底座判定：哪些是"地基"，哪些是"上层"

这是全文最关键的结论。

| 类别 | 包含项 | 为什么这样归类 |
|---|---|---|
| **地基（必须一体化设计，不能各做各的）** | ① 任务化 + 可恢复运行时；② 事件总线（seq 语义）；③ 身份（会话/设备） | 一切上层能力都建立在"任务是谁的、事件发到哪、哪个设备有权批"之上。若分头做，会各自造 seq、各自造身份、各自造任务状态，最后无法协同，违反 DRY、破坏 KISS |
| **上层（接口稳定后可独立、分方向交付）** | ④ 推送/多通道；⑤ 执行端抽象；⑥ 持久调度器；⑦ 跨端 HITL 路由；⑧ 长期记忆/程序性学习；⑨ 跨域代表 | 它们都是"地基上的消费者/插件"，彼此可解耦，按应用方向分别挂载，不必同时上线 |

**一句话：底座一体化，能力分方向。** 不是"6 项必须一起做完"，而是"3 根地基先统一收口，其余 6 项按方向分期挂载"。

## 二、针对应用方向的缺陷

脱离应用方向谈缺陷，就会变成"什么都要补"。先把方向摆清楚，再看每个方向被什么卡住。

### 2.1 四个应用方向

| 方向 | 场景描述 | 你要的核心体验 |
|---|---|---|
| **A 本机单端深度使用** | 只在 PC 上，一个人用 | 长任务别丢、越用越顺手 |
| **B 多端协同** | PC + 手机，手机主要"看进度/批审批/接管" | 离开 PC 也能掌握和拍板 |
| **C 主动个人助理** | 定时/触发/例行任务，无需你在场 | 到点自己干、干完找你 |
| **D 跨域代理** | 代表你登录外部系统办事（下单/改签/填表） | 真替你在外部世界跑腿 |

### 2.2 缺陷 × 应用方向 映射矩阵

> ● 强卡住　○ 有影响　— 基本无关

| 问题（合并后） | A 本机 | B 多端 | C 主动 | D 跨域 |
|---|:--:|:--:|:--:|:--:|
| 3.1 可恢复任务运行时（含无队列/检查点） | ● | ● | ● | ○ |
| 3.2 事件总线 + 推送 + 多通道（含单通道） | ○ | ● | ● | ○ |
| 3.3 会话-设备-身份 | — | ● | ○ | ○ |
| 3.4 执行端抽象与能力协商 | — | ● | ○ | ● |
| 3.5 持久化调度器 | — | ○ | ● | ○ |
| 3.6 跨端 HITL 路由 | — | ● | ○ | ● |
| 3.7 长期个人记忆 / 程序性学习 | ● | ○ | ● | ● |
| 3.8 跨公司代表（外部系统握手） | — | — | ○ | ● |

### 2.3 结论：为什么"地基一体化、能力分方向"

- **只做 A（本机单端）**：真正该补的只有"3.1 任务可恢复"和"3.7 长期记忆"。其余 6 项**现在都不必做**。
- **要做 B（多端）**：绕不开"3.1 + 3.2 + 3.3 + 3.6"这四件；其中 3.1/3.2/3.3 是地基，必须统一；3.6 是地基上的消费者。
- **要做 C（主动）**：绕不开"3.5 持久调度器 + 3.2 推送"（干完要能找到你），以及"3.7 记忆"（记得你的习惯和上次怎么干）。
- **要做 D（跨域）**：最难，绕不开"3.4 执行端 + 3.8 外部握手 + 3.6 跨端审批 + 3.7 记忆"，是一整条独立产品线，**优先级最低**。

由此得出实施原则：

1. **地基三项（3.1/3.2/3.3）一次性统一收口**，因为它们是公共契约，反复改成本最高。
2. **其余五项按方向分期挂载**，做一个方向就只挂它需要的那几件，不提前引入用不上的抽象（YAGNI）。
3. 你之前担心的"6 项要不要一体化"——**答案：地基一体化，功能不必。** 后面不同阶段做不同方向，完全成立。

## 三、逐问题分析与实施说明

每节统一回答：**问题是什么 / 解决什么 / 根重要吗（何时才需要）/ 和谁耦合 / 怎么实施**。

### 3.1 可恢复任务运行时（含"无队列/检查点"）

- **问题**：任务的运行态、事件缓冲、协程句柄全在进程内存（`running_tasks`、`StreamBuffer`、`_agent_tasks`）。后端一重启、PC 一休眠，任务蒸发，界面却可能还显示"执行中"。没有队列排队，也没有检查点快照。
- **解决什么**：把"任务状态"从内存搬到库里，让系统重启后**认得没跑完的任务**——标注"已中断/可续"，让用户看得到、能重发。它**不能让跑到一半的命令接着跑**，只保证"结果和待办不丢、你知道它断了"。
- **根重要吗**：**重要，且是地基。** 只要你经常重启后端、或要做多端（手机发起、PC 关机），就必须有。若你极少重启后端且只在本机用，可暂缓，但仍建议随地基一起做（成本低、收益长期）。
- **和谁耦合**：与 3.2（事件总线共享 seq/Journal）、3.5（调度器触发的任务也要可恢复）强耦合；是 3.6（审批态恢复）的前提。
- **实施方向（复用现有）**：
  1. 以 `chat_tasks + chat_task_steps + Journal` 为唯一真相源，把状态机落库：`queued / running / paused / waiting_approval / interrupted / done / failed / cancelled`；
  2. 进程启动时扫"非终态任务"，重建为 `interrupted`（**诚实标注，不假装恢复正在执行的工具/命令**）；
  3. "队列"先用"任务表 + 状态位"实现，单进程按需取放，不引入消息队列（YAGNI）；
  4. "检查点"先做到"事件级可回放"（Journal 已有），工具级快照后置。
- **归属阶段**：**阶段 0 地基**。

### 3.2 统一事件总线 + 推送 + 多通道（含"单通道"）

- **问题**：事件出口只有一条 HTTP-SSE（`StreamBuffer` 单任务、内存、单消费语义）。手机一锁屏/切后台/杀进程，就收不到"完成/需审批"。所谓"单通道"，本质就是这个。
- **解决什么**：把事件做成"单生产者、多订阅者"的 pub/sub，SSE 只是其中一个 sink，再加推送 sink。**补靠 after_seq，推靠 PushSink**——离开时能推，回来时能补。
- **需要"推送能力"吗？分两种**：
  - 只要"打开手机网页能看到进度" → **不需要推送**，现有断线续传就够；
  - 要"手机锁屏也能响一下、提醒你去处理" → **需要推送**（WebPush + PWA 即可，先不做原生 App）。
- **根重要吗**：做 B/C 方向是地基；只做 A 方向则不必。
- **和谁耦合**：是 3.6（审批事件广播）的载体；依赖 3.3（知道推给哪台设备）。
- **实施方向（复用现有）**：
  1. 把 `StreamBuffer.publish` 提升为 `EventBus.publish/subscribe(task_id, after_seq)`，**沿用"每任务单生产者 + seq 单调"，坚决不做全局 seq**（否则回放/续传全乱）；
  2. 新增 `PushSink`：任务终态/待审批时触发 WebPush，推送只负责"叫醒"，真相仍以 Journal + after_seq 为准（推送丢了也能补）；
  3. 多渠道（邮件/IM 等）作为后续 sink 扩展点，**一期只做 Web/PWA**，避免过度设计。
- **归属阶段**：**阶段 0 地基（总线）+ 阶段 1（推送）**。

### 3.3 会话-设备-身份

- **问题**：单口令鉴权（`deps.verify_token`），没有设备概念。后台不知道"这条指令来自 PC 还是手机""谁有权批"。
- **解决什么**：在**单用户**前提下加一层"设备身份"：设备注册/配对、设备 token、在线表。同一会话可被多端订阅，记录"发起端/主控端"，审计"谁在何时下发/审批"。
- **根重要吗**：做 B 方向是地基；只做 A 方向不必。**不做账号体系、不做多租户/RBAC**（YAGNI），仍是"一个用户、多台设备"。
- **和谁耦合**：3.2（推给哪台）、3.6（哪台能批）、3.4（哪台能执行）都依赖它。
- **实施方向（复用现有）**：
  1. 一次性配对码 → 设备 token → 心跳/在线表（落 SQLite 一表即可）；
  2. 会话与设备多对多，记录主控端；
  3. 控制指令带 `device_id`，写入现有审计。
- **归属阶段**：**阶段 0 地基**（与总线、可恢复一并收口）。

### 3.4 执行端抽象与能力协商

- **问题**：工具=宿主本机能力（Windows shell/桌面/文件），没有"执行端"概念，任务由"谁发起"隐含决定"谁执行"。
- **解决什么**：把"谁执行"从"谁发起"剥离——后台是控制面，PC/手机是执行端；执行端**注册能力**，控制面按能力分派；无匹配执行端时**显式降级**，不静默失败。
- **根重要吗**：只在"手机也要本地干活/多执行端协同"（B 深水区）或"跨域用浏览器执行端"（D）时才需要。**一期手机只做 view + approve，则不需要它**，手机当遥控器即可。
- **和谁耦合**：依赖 3.3（设备身份）；是 3.8（跨域代表）的执行底座。
- **实施方向（复用现有）**：
  1. 定义 `Executor` 接口：`register(capabilities) / heartbeat / execute(task_step) / cancel`；
  2. PC 先做 daemon（能力全），手机端一期不做本地执行；
  3. 工具→能力标签映射（shell/desktop/file/network），按能力分派与降级。
- **归属阶段**：**阶段 2（能力升级）**，D 方向的前置。

### 3.5 持久化调度器

- **问题**：`timer_set` 用内存 `asyncio.call_later`，重启即丢；timers.db 只记状态。所谓"无队列"的另一面，就是"没有可靠的到点触发器"。
- **解决什么**：timers.db 驱动、重启可恢复的调度器，支持"到点创建任务/提醒/审批"，是"主动个人助理"的核心——**主动、准时、不依赖有人在线**。
- **根重要吗**：做 C 方向才需要；不做定时/主动任务就不必。
- **和谁耦合**：触发的任务要能被 3.1 恢复；完成通知走 3.2 推送。
- **实施方向（复用现有）**：
  1. 启动扫描 due 定时器、重建调度；
  2. 触发动作统一走"创建任务"（复用 `_create_and_launch_task`），而非直接调 HTTP；
  3. 单进程先用"轮询 + 最近到期堆"，不引入消息队列（YAGNI）。
- **归属阶段**：**阶段 3（主动能力）**。

### 3.6 跨端 HITL 路由

- **问题**：审批确认/回答目前是"当前会话前端弹窗"，只能弹在发起的那台设备上。
- **解决什么**：审批事件广播到"在线且被授权的端"，**任一端处理即收敛**；定义超时/降级（危险操作默认拒绝）。
- **根重要吗**：多端同时用（B）或跨域代理需人工把关（D）时才需要；单端用不必。
- **和谁耦合**：审批请求作为事件进 3.2 总线 + 推送；依赖 3.3 设备身份；"首次领取即锁"可复用现有 `claim_agent_task_for_cancel` 思路。
- **实施方向（复用现有）**：
  1. 审批请求进 EventBus + PushSink；
  2. 首次领取即锁（复用"首次领取"语义）；
  3. 超时策略：默认暂停，可配置自动拒绝/放行（危险默认拒绝）。
- **归属阶段**：**阶段 1（多端协同）**。

### 3.7 长期个人记忆 / 程序性学习

- **问题**：目前只有"会话历史 + 上下文压缩"（`compaction/`、HistoryMemory），没有独立用户画像、没有跨会话长期记忆、没有"上次怎么做的、下次如何更快更省"的程序性记忆。（已核实：全仓 `memory/profile` 关键词均指进程内存或模型能力画像，无个人记忆模块。）
- **解决什么**：这是"personal"的核心——**越用越懂你、一件事教一次即可复跑**。缺它，每次都要重述需求，像陌生人。
- **根重要吗**：**对"个人助理"这个定位，这是最该补的短板**，且对 A/B/C/D 全部有影响。它不依赖多端、不依赖推送，**可以独立、优先做**。
- **和谁耦合**：与 3.1（记忆要能持久化、可恢复）、3.5（例行任务复跑依赖程序性记忆）相关；与多端/推送无关。
- **实施方向（最小可行，避免过度设计）**：
  1. **画像**：先落"结构化用户偏好"（如常用路径、口头习惯、授权偏好）到一张表，不引入向量库；
  2. **长期记忆**：跨会话的可检索事实库（先 SQLite + 简单检索），区分"历史数据/交互数据"；
  3. **程序性记忆**：把"做成的一次任务"沉淀为"可复跑流程模板"（复用现有任务步骤记录），下次同任务直接套用；
  4. 注入方式沿用现有 message_builder，不新增 LLM schema 参数（遵守既有约束）。
- **归属阶段**：**阶段 2（可与 B 并行，建议优先）**。

### 3.8 跨公司代表（跨域外部系统握手）

- **问题**：只会本机动作，不涉"登录外部网站、代表你去下单/改签/填表"，也无 Poppy/MCP 之类对外握手。
- **解决什么**：让 Agent 能在"多个不同公司/平台的系统之间"替个人跑腿——这是 Personal Agent 区别于普通 Agent 的判据之一。
- **根重要吗**：**只在你确实要"对外代办"（D 方向）时才需要。** 它是独立产品线，成本与风险最高（账号安全、外部失败代价、合规），**优先级最低**，不建议过早启动。
- **和谁耦合**：依赖 3.4（浏览器/执行端）、3.6（对外动作必须可审批）、3.7（记住你的账号偏好与授权规则）。
- **实施方向（若要做）**：
  1. 先接 MCP/OpenAPI 这类标准握手，而非硬编码各家；
  2. 对外动作强制走"审批 + 审计 + 可回滚"（复用现有四层安全），默认"要紧事之前先问"；
  3. 按服务细分权限作用域（只读/可读可发），而非一个大开关。
- **归属阶段**：**阶段 4（跨域，最后评估）**。

### 3.9 实施分期路线（回答"是否一体化"）

| 阶段 | 内容 | 对应方向 | 说明 | 复用地基 |
|---|---|---|---|---|
| **阶段 0　地基** | 3.1 可恢复任务运行时 + 3.2 事件总线（先总线，推送后置）+ 3.3 设备身份 | 所有方向公共 | **必须一次性统一收口**，这是"一体化"的真正含义 | task_db / task_registry / task_runtime / StreamBuffer / deps |
| **阶段 1　多端看批** | 3.2 推送（WebPush/PWA）+ 3.6 跨端 HITL 路由 | B | 手机当"看 + 批"的遥控器，不做本地执行 | execution_stream / chat_routes / hitl_* |
| **阶段 2　能力升级** | 3.7 长期记忆/程序性学习（优先）+ 3.4 PC 执行端 | A、B 深水区 | 记忆可独立先做；执行端按需 | compaction 思路、工具能力标签 |
| **阶段 3　主动助理** | 3.5 持久化调度器 + 复用推送 | C | 到点自己干、干完找你 | timer_set / _create_and_launch_task |
| **阶段 4　跨域代办** | 3.8 外部系统握手（依赖 3.4/3.6/3.7） | D | 成本风险最高，最后评估 | MCP / 四层安全 / 审计 |

**分期原则**：地基一套、上层按方向挂；做一个方向就只挂它需要的能力；每阶段"升级接口、复用内核；禁止 backward 兼容层；新公用件入库并更新 FUNCTIONS.md"。

## 四、一句话总结

- **"6 项要不要一体化"**：不是全部一体化，而是**"3 根地基（可恢复任务 / 事件总线 / 设备身份）一次性统一，其余按方向分期挂载"**。
- **上一阶段的 4 项缺陷**：`无队列/检查点` 就是"3.1 可恢复任务运行时"的另一面；`单通道` 就是"3.2 事件总线 + 推送"的另一面；`无长期记忆/程序性学习` 是 **3.7（最该补的 personal 短板）**；`不跨公司代表` 是 **3.8（独立产品线，最后做）**。
- **你现在的真实痛点排序**：若只在本机用 → 只补 **3.1 + 3.7**；要手机看/批 → 再加 **3.2 + 3.3 + 3.6**；要主动提醒 → 再加 **3.5**；要对外代办 → 才碰 **3.4 + 3.8**。
- 结论说人话：**先把"任务别丢 + 事件能补能推 + 认得出是哪台设备"这三根地基做扎实，剩下的能力想要哪个方向就挂哪个，不用一次做完，更不用现在就全上。**
