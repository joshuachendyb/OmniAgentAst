## 一、问题现象

### 1.1 现象

- 后端进程活着（PID 23088 `python run_server.py --port 8000`），端口 8000 在监听。
- `/api/v1/health` 8 秒超时无响应。
- 前端页面无响应、会话切换/发送失败、"设置加载失败"等奇怪提示。
- 数据库文件 `chat_history.db` 1.11 GB、`monitoring.db` 131 MB，08:55:29 后停写。

### 1.2 证据（py-spy 两次抓栈一致）

```
Thread 18880 (idle): "MainThread"
    get_conn (db\database.py:274)          ← conn.commit()
    __exit__ (contextlib.py:148)
    get_conn_with_retry (db\database.py:330)
    __exit__ (contextlib.py:148)
    persist_http_request (monitoring\storage.py:175)
    _record_response_metrics (monitoring\middleware.py:108)
    wrapper (monitoring\middleware.py:83)
    _send (main.py:221)
    ... (starlette/uvicorn 事件循环)
```

- 进程只有一个线程（MainThread），事件循环被这条同步调用独占 → 全站停摆。
- 两次抓栈间隔数分钟，位置完全相同 → **持续卡死**，不是瞬时。

## 二、根因分析

### 2.1 直接卡点

`monitoring/storage.py::persist_http_request` 在响应路径上**同步**执行：

```python
with _db.get_conn_with_retry("monitoring") as conn:
    conn.execute("INSERT INTO http_requests ...")
    conn.execute("INSERT INTO metrics ...")
    # commit 在 get_conn __exit__ 里执行
```

`get_conn_with_retry` 内部：
- `busy_timeout=500ms` 快速失败；
- 撞 `database is locked` 后 `_time.sleep(delay)` 指数退避（0.5/1/2s，共 ~3.5s）；
- 全部跑在事件循环线程上。

### 2.2 根因链

1. 监控中间件 `_record_response_metrics` 在 `http.response.start` 时同步写库。
2. `monitoring.db` 131 MB，写入频繁，与任务写入争 SQLite 写锁。
3. 撞锁 → 同步 sleep 重试 → 事件循环线程被独占 → 全站无响应（/health 超时、前端请求失败）。
4. 导火索：长任务（`Start-Sleep 90` / 连串 `git diff`）产生大量请求与日志写入，监控写库与任务写库争锁。

### 2.3 与前端代码的关系

- **不是**前端代码导致。前端 `useRef is not defined` 是另一独立缺陷（已修）。
- 后端卡死发生在 08:55:29，与前端改动无关。

## 三、修改方案

### 3.1 监控落盘异步化（核心修复）

**文件**: `monitoring/middleware.py`

```python
# 修改前：同步调用，阻塞事件循环
storage.persist_http_request(method, path, status_code, _kind, duration, request_size, 0)

# 修改后：异步，跑在 _DB_TXN_POOL 子线程
async def _record_response_metrics(self, message, start_time, method, path, request_size):
    ...
    try:
        await storage.persist_http_request(method, path, status_code, _kind, duration, request_size, 0)
    except Exception as _e:
        logger.error(...)
```

`wrapper` 内改为 `await self._record_response_metrics(...)`。

**文件**: `monitoring/storage.py`

```python
# 修改前：同步 get_conn_with_retry
with _db.get_conn_with_retry("monitoring") as conn:
    conn.execute(...)

# 修改后：async + db.atxn（跑在 _DB_TXN_POOL 子线程）
async def persist_http_request(...):
    ...
    def _q(conn):
        conn.execute(...)
        conn.execute(...)
    await _db.atxn("monitoring", _q)
```

**效果**：DB I/O 全部进线程池，事件循环永不被占；即使撞锁 sleep，也只睡子线程，主线程继续应答请求。

### 3.2 保留期清理（数据治理）

**文件**: `monitoring/storage.py` 新增 `retention_cleanup_monitoring(...)`：

```python
async def retention_cleanup_monitoring(http_days=7, metrics_days=7, task_days=30, llm_days=30) -> dict:
    ...
    def _q(conn):
        n["http_requests"] = conn.execute("DELETE FROM http_requests WHERE timestamp < ?", (_c_http,)).rowcount
        n["metrics"] = conn.execute("DELETE FROM metrics WHERE timestamp < ?", (_c_metrics,)).rowcount
        n["task_metrics"] = conn.execute("DELETE FROM task_metrics WHERE created_at < ?", (_c_task,)).rowcount
        n["task_tool_metrics"] = conn.execute("DELETE FROM task_tool_metrics WHERE task_id IN (...)", (_c_task,)).rowcount
        n["llm_calls"] = conn.execute("DELETE FROM llm_calls WHERE timestamp < ?", (_c_llm,)).rowcount
        return n
    return await _db.atxn("monitoring", _q)
```

**文件**: `main.py` 新增 `_start_monitoring_retention_task()` 后台任务（每小时）：

```python
async def _loop() -> None:
    while True:
        try:
            from app.monitoring import storage as _mon_storage
            n = await _mon_storage.retention_cleanup_monitoring(http_days=7, metrics_days=7, task_days=30, llm_days=30)
            if n and any(v for v in n.values()):
                logger.info("[Monitoring] retention cleanup: %s" % n)
        except Exception as exc:
            logger.warning("[Monitoring] retention cleanup failed (degrade): %r" % exc)
        await asyncio.sleep(3600)
```

启动时调用 `_start_monitoring_retention_task()`，关闭时 cancel。

### 3.3 chat_history 保留期（配置项）

**文件**: `services/chat/chat_retention.py` 新增 `retention_cleanup_chat(retention_days)`：

```python
async def retention_cleanup_chat(retention_days: int) -> int:
    if not retention_days or int(retention_days) <= 0:
        return 0
    ...
    def _q(conn):
        conn.execute("DELETE FROM chat_stream_events WHERE task_id IN (...)")
        conn.execute("DELETE FROM chat_task_steps WHERE session_id IN (...)")
        conn.execute("DELETE FROM chat_tasks WHERE session_id IN (...)")
        cur = conn.execute("DELETE FROM chat_sessions WHERE COALESCE(updated_at, created_at) < ?", (cutoff,))
        return cur.rowcount
    return await _db.atxn("chat", _q)
```

### 3.4 WAL + busy_timeout（已在 database.py，未改动）

- 所有库统一 WAL 模式：`conn.execute("PRAGMA journal_mode=WAL")`。
- `busy_timeout=500ms`（快速失败，应用层指数退避重试，不空等 30s）。
- `db.atxn` 在 `_DB_TXN_POOL` 子线程执行，多任务写经线程池并发 + SQLite 文件锁串行化。

## 四、数据治理策略

### 4.1 monitoring.db（自动，已启用）

| 表 | 保留期 | 说明 |
|----|--------|------|
| http_requests | 7 天 | 服务级流量，可再生 |
| metrics | 7 天 | 计数器，可再生 |
| task_metrics | 30 天 | 任务级指标 |
| task_tool_metrics | 30 天 | 工具级指标 |
| llm_calls | 30 天 | LLM 调用记录 |

后台任务每小时跑一次，失败只 warning 不阻断。

### 4.2 chat_history.db（默认关闭，需手动开启）

- 通过设置页面：设置 → 系统 → 数据治理 → "对话历史保留天数" 设为 >0（如 90），保存后重启。
- 或环境变量：`OMNIAGENT_CHAT_RETENTION_DAYS=90`。
- 或 config.yaml：`system.chat_retention_days: 90`。
- 默认 0 = 关闭，不删用户历史；开启前建议备份 `~/.omniagent/chat_history.db`。

### 4.3 备份文件清理（手动）

可删除的备份文件（释放 ~2.5GB）：
- `chat_history.db.bak-*`
- `chat_history_prebulkdel_*`
- `chat_history_precleanup_*`
- `operations.db.bak`

删除前建议先做一次全量备份。

### 4.4 启动时 WAL checkpoint

已有 `_start_journal_retention_task` 每小时做一次 `PRAGMA wal_checkpoint(PASSIVE)`，避免 WAL 无限增长。

## 附录：详细改动清单（文件/函数/作用）

### A. `backend/app/monitoring/middleware.py`

| 位置 | 改动 | 作用 |
|------|------|------|
| `_record_response_metrics` | `def` → `async def` | 使其可 await 异步 DB 写入，不阻塞事件循环 |
| `_record_response_metrics` 末尾 | `storage.persist_http_request(...)` → `await storage.persist_http_request(...)` + try/except | 落库进线程池，异常降级不阻断主链路 |
| `_make_send_wrapper` 内 `wrapper` | `self._record_response_metrics(...)` → `await self._record_response_metrics(...)` | wrapper 本身已是 async，await 不阻塞 |

### B. `backend/app/monitoring/storage.py`

| 位置 | 改动 | 作用 |
|------|------|------|
| `persist_http_request` | `def` → `async def`；`with get_conn_with_retry` → `await _db.atxn("monitoring", _q)` | 连接/执行/提交/关闭全部在 `_DB_TXN_POOL` 子线程内完成，事件循环永不被 DB I/O 或 sleep 占用 |
| 新增 `retention_cleanup_monitoring(http_days, metrics_days, task_days, llm_days)` | async 函数 | 监控库保留期清理：http_requests/metrics 保留 7 天，task_metrics/task_tool_metrics/llm_calls 保留 30 天；失败只 warning 降级 |

### C. `backend/app/main.py`

| 位置 | 改动 | 作用 |
|------|------|------|
| 全局变量 `_monitoring_retention_ref` | 新增 | 存储后台任务引用，防 GC |
| `_start_monitoring_retention_task()` | 新增函数 | 启动每小时循环：调用 `retention_cleanup_monitoring`，异常只 warning；asyncio.create_task 存引用 |
| `startup_event()` | 调用 `_start_monitoring_retention_task()` | 启动时启动监控保留期清理后台任务 |
