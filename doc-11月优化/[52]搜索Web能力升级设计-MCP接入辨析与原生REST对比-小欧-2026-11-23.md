## 1. 结论先行

| 问题 | 结论 |
|---|---|
| "MCP 接入方式"是什么意思 | MCP（Model Context Protocol）是 LLM 应用与外部工具之间的标准化通信协议。opencode 的 websearch 所谓 MCP 接入，本质是**向厂商托管的 MCP 端点发一个 JSON-RPC 2.0 `tools/call` HTTP POST**，再拆解返回的 `result.content[].text`。它不是在本地跑一个 MCP Server，也不是把搜索引擎"装进"系统。 |
| 需要先给系统增加 MCP 基础支持能力吗 | **不需要**。opencode 自己有两套 MCP 体系，但 websearch **刻意绕开了通用 MCP 客户端**，只用了一个 69 行的裸 HTTP helper；而本系统 `search_web.py:_search_mcp_engine` 已经具备同等能力（JSON-RPC 组包、SSE 帧解析、httpx 超时）。缺的不是 MCP 底座，是**provider 数量与调度治理**。 |
| 原生 REST 与 MCP 的差异 | REST 是 HTTP 资源语义（方法/路径/状态码）；MCP 是 JSON-RPC 方法语义（`tools/call`），HTTP 只是传输外壳，多一层 envelope、可能多一层会话握手。详见第 3 章。 |
| 升级路线 | 两阶段（见第 9 章）：阶段一底座增强 S1 Parallel 结构化 → S2 错误分类/冷却/轮转 → S4 响应上限 → S3 Tavily；阶段二社交搜索扩展。**S2 起 429 不再抛给 ToolRetryEngine**（见 7.4）；域名过滤、代理、查询拆分保留。 |
| 要不要"扩展槽" | 要，但只做**轻量调度底座**（统一错误分类/冷却/尝试轨迹/响应上限/结果字段），不建通用插件框架、不引入 MCP SDK。新增一个搜索源 = 一个解析函数 + 链条里加一行。 |
| websearch 与 fetchweb 是否合并 | **共享底座、分开工具、各自链条**。底座统一治理；两个工具的输入/输出/schema/前端展示/别名映射保持独立，前端零改动。 |

## 2. MCP 接入方式的准确含义

### 2.1 MCP 协议本身

MCP 是 Anthropic 开源的"LLM 应用 ↔ 外部工具"标准协议，解决的是每家工具都要写一套私有客户端的问题。它在两个层面定义契约：

- **传输层**：本地工具走 stdio（子进程 stdin/stdout）；远程 SaaS 工具走 HTTP（POST JSON-RPC 2.0，响应可以是普通 JSON，也可以是 SSE 流）。
- **消息层**：JSON-RPC 2.0 方法，如 `initialize`（握手/能力协商）、`tools/list`（工具发现）、`tools/call`（调用）、`notifications/initialized`。

一个"完整 MCP 客户端"应当具备：传输抽象、会话管理、工具发现、能力协商、OAuth、连接池等。opencode 确实有这套东西，但它**不服务于 websearch**。

### 2.2 opencode v2.3.2 的两套 MCP 体系（关键辨析）

| 体系 | 位置 | 是否用 SDK | 服务对象 |
|---|---|---|---|
| 通用 MCP 子系统 | `packages/core/src/mcp/{client,connection,pool,stdio,socket-client,oauth}.ts` | 是，依赖 `@modelcontextprotocol/client@2.4.0` | 用户在配置里声明的任意 MCP Server（stdio / socket / OAuth） |
| websearch 专用 helper | `packages/core/src/plugin/websearch/mcp.ts`（69 行） | **否**，只用 Effect 自带 `HttpClient` | 只服务 5 个内置搜索 provider |

websearch 专用 helper 实际做的事，逐条如下：

1. 端点写死在 provider 文件里（`https://mcp.exa.ai/mcp` 等）；
2. 工具名写死（`web_search_exa` / `web_search` / `firecrawl_search` / `search`）；
3. 组一个固定 JSON-RPC 体：`{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":<工具名>,"arguments":<参数>}}`；
4. `POST` 到端点，`Accept: application/json, text/event-stream`；
5. 响应如果是 SSE，就逐行找 `data: ` 开头的帧再 JSON 解析；否则直接 JSON 解析；
6. 从 `result.content[].text` 取文本（Parallel 例外，取 `structuredContent`）；
7. 响应体限 256KB，超时 25 秒，Effect Schema 校验输入输出。

**它不调用 `tools/list`，不做能力协商，不维持长连接，不跑本地进程。** 所谓"MCP 接入"在这里就是"按 MCP 消息格式发一次 HTTP 请求"。TinyFish 是唯一例外：服务端要求鉴权时先 `initialize` 拿 `Mcp-Session-Id`（协议版本 `2025-06-18`），再带着这个头调 `tools/call`——这是被服务端约束逼出来的握手，不是通用 MCP 能力。

### 2.3 本系统现状已经等价覆盖

`backend/app/tools/network/search_web.py:_search_mcp_engine` 的现有实现：

| 能力 | opencode `mcp.ts` | 本系统 `_search_mcp_engine` | 结论 |
|---|---|---|---|
| JSON-RPC `tools/call` 组包 | 有 | 有（L208-211） | 等价 |
| SSE `data:` 帧解析 | 有 | 有（L221-232） | 等价 |
| 纯 JSON 响应 | 有 | 有（L233-234） | 等价 |
| HTTP POST + Accept 头 | 有 | 有（L214-215） | 等价 |
| 超时 | 25s | 25s（`create_http_client(timeout_sec=25.0)`） | 等价 |
| 代理 | 无 | 有（proxy 参数透传） | 本系统更强 |
| 响应体大小上限 | 256KB | **无** | 需补（S4） |
| `structuredContent` 读取 | 有（Parallel） | 无，只读 `content[0].text` | 需补（S1） |
| `initialize` 会话握手 | 有（TinyFish） | 无 | 仅 S5 需要 |

**结论：本次升级不需要新建 MCP 基础能力层。** 只有在"用户可在配置里填任意 MCP Server URL、自动 `tools/list` 发现并注册为工具"这类需求出现时，才需要建通用 MCP 客户端——那是另一个立项，按 YAGNI 原则本次不做。

## 3. 原生 REST 与 MCP 的差异

### 3.1 本质差异

- **REST**：面向"资源"。语义在 HTTP 本身——方法（GET/POST）、路径（`/search`）、状态码（200/401/429）、JSON body。接口契约由厂商 OpenAPI 文档描述，调用方按文档拼参数。
- **MCP**：面向"工具调用"。语义在 JSON-RPC 消息里——`method: "tools/call"`、`params.name`、`params.arguments`。HTTP 退化成传输管道，常常见到"HTTP 200 但业务失败"的情况，因为错误在 JSON-RPC `error` 对象里。

一个直观类比：REST 像"按地址寄信并看回执"，MCP 像"按统一格式的工单派活，结果装在回执信封里的信封里"。

### 3.2 逐维度对比

| 维度 | 原生 REST | MCP（HTTP 形态） | 对本次升级的意义 |
|---|---|---|---|
| 协议语义 | HTTP 方法/路径/状态码 | JSON-RPC 2.0 方法（`tools/call`），HTTP 仅传输 | 两边错误判断逻辑不能混用：REST 看 status，MCP 还要看 envelope 里的 `error` |
| 接口发现 | OpenAPI 文档（人读，代码写死） | 协议支持 `tools/list` 运行时发现 | opencode 也没用发现（工具名写死），本系统照旧写死即可，零新增成本 |
| 鉴权 | `Authorization: Bearer` / API key 头，各家不一 | 同样是 Bearer / key，但可放 URL 参数（Exa）、专用头（TinyFish `X-API-Key`）、会话头（`Mcp-Session-Id`），还有 keyless 模式 | keyless 是 opencode 托管服务的特权（其文档明说"无需 key，直连后端托管 MCP"），**不能直接假设本系统也能免 key**，须实测 |
| 会话状态 | 无状态 | 可有状态（initialize → session id），TinyFish 即强制 | 有状态时不能用纯无状态的朴素封装，S5 才涉及 |
| 响应形态 | 直接 JSON / text | envelope：`result.content[].text`（文本里可能再嵌 JSON）或 `structuredContent`；还可能是 SSE `data:` 帧 | 多一层拆包 = 多一层解析失败点；本系统已有 SSE 兼容，补 `structuredContent` 即可 |
| 传输形态 | 仅 HTTP | stdio + HTTP/SSE 两种 | 本系统只用 HTTP 形态，不需要 stdio 与子进程管理 |
| 错误处理 | HTTP status 直接表达 | HTTP 200 + JSON-RPC `error` 并存；限流仍可能以 HTTP 429 + `Retry-After` 出现 | 冷却逻辑须识别 429；其余错误靠内容非空判断 |
| 调试成本 | 低（curl 即可复现） | 中（要拼 JSON-RPC、处理 SSE 帧） | REST provider 优先，出问题好排查 |
| 生态/通用性 | 每家一套私有 API | 同一套客户端代码可接不同 MCP Server（但工具名/参数仍各家不同） | 通用性收益在 websearch 这个封闭场景里几乎兑现不了——opencode 仍是每家单独写解析 |
| 稳定性 | 直接、少一层 | 多一层 envelope 与可能的会话握手 | Tavily 有原生 REST 就走 REST，这是 opencode 的选择，也是本系统的选择 |

### 3.3 为什么 opencode 里有的走 MCP、有的走 REST

不是技术信仰，是**厂商提供什么就用什么**：

- Exa / Parallel / Firecrawl / TinyFish 官方提供了托管 MCP 端点（且有免 key 或统一鉴权通道），走 MCP 省去自建抓取/索引；
- Tavily 官方搜索 API 是标准 REST，直接 POST 最省事、最稳；
- 结果解析方式也随 provider 而变：Exa 返回自然语言块（正则解析），Parallel/Firecrawl/TinyFish 返回内嵌 JSON（再解码），Tavily 直接是 JSON。

### 3.4 对 OmniAgent 的选型结论

1. **保留现有 MCP 通道**（Parallel / Exa），因为已验证可用且本系统有代理透传能力；
2. **新增 provider 时优先选 REST**（Tavily），降低解析脆弱性和调试成本；
3. **不引入通用 MCP 客户端 SDK**，不为 5 个封闭端点建通用发现/会话框架；
4. **MCP 特有机制按需逐点补**（`structuredContent`、256KB 上限、`initialize` 握手），不整体搬框架。

## 4. Provider 概念与三方实现对照

### 4.1 什么是 provider

provider（搜索后端）不是单纯"一家公司"或"一个 URL"，而是一个完整的接入单元，包含四个要素：

| 要素 | 含义 | 例（OmniAgent 现有） |
|---|---|---|
| 身份 | id + 显示名 | `parallel` / `exa` / `bing` |
| 接入端点 | URL + 调用方式 | `search.parallel.ai/mcp`、`mcp.exa.ai/mcp`、`cn.bing.com/search` |
| 鉴权 | 如何证明调用权限 | API key / Bearer / 免 key / 无（HTML 抓取） |
| 解析 | 把返回数据翻译成统一字段 | `structuredContent` / 文本块正则 / HTML DOM |

代码层面，一个 provider 就是"一个请求 + 解析函数 + 链条里一行注册"。每家的解析必须单独写，因为返回格式完全不同——opencode 为 5 家写了 5 份解析，Agent-Reach 也各自写。这正是第 6 章"调度统一、解析各自写"的由来。

OmniAgent 现有三个 provider：

- **Parallel**：`search.parallel.ai/mcp`，工具 `web_search`，JSON-RPC `tools/call`，读 `structuredContent`；
- **Exa**：`mcp.exa.ai/mcp`，工具 `web_search_exa`，免 key，返回 `Title:/URL:` 文本块；
- **Bing**：`cn.bing.com/search`，抓取 HTML 后按 `b_algo` 块解析——严格说是"抓取型 provider"，不是官方 API。

### 4.2 provider 与接入方式是两件事

同一厂家可以用不同接入方式：Exa 提供 MCP 端点；Tavily 提供 REST API；Bing 你们用的是 HTML 抓取。MCP / REST / HTML 解决"怎么连"，provider 解决"连谁、怎么看懂返回"，不能混为一谈。

百度、Google 同样可以做成 provider，但前提是有可调接口：Google 有 Custom Search JSON API（免费配额很少）或 Serper 等第三方封装；百度有开放平台 API（需申请 key）；直接抓首页 HTML 容易被反爬与验证码拦截，稳定性差。这也是 opencode 与 Agent-Reach 都不约而同选择 Exa / Tavily 这类"AI 专用搜索服务"的原因——返回的是干净结构化数据，不用跟 HTML 搏斗。

### 4.3 opencode v2.3.2 的实现

分层结构：

```
LLM
 │  tool call: websearch { query }
 ▼
packages/core/src/tool/plugin/websearch.ts      工具层：权限断言、首次同意表单、输出格式化
 │  websearch.query({ query }, { sessionID, onProvider })
 ▼
packages/core/src/websearch.ts                   服务层：provider 注册表、选择策略、429 冷却、会话粘性
 │  provider.execute({ query })
 ▼
packages/core/src/plugin/websearch/provider.ts   注册层：API key / 环境变量 / integration 打通
 │
 ├─ exa.ts / parallel.ts / firecrawl.ts / tinyfish.ts   MCP provider（走 mcp.ts）
 └─ tavily.ts                                           REST provider（直接 HttpClient）
```

五个 provider 的技术参数：

| Provider | 端点 | 工具名 | 鉴权 | 参数 | 结果取法 |
|---|---|---|---|---|---|
| Exa | `https://mcp.exa.ai/mcp` | `web_search_exa` | URL 参数 `exaApiKey` | `{query, numResults: 8}` | 文本按 `\n\n---\n\n` 分块，正则取 `URL:/Title:/Published:/Highlights:` |
| Parallel | `https://search.parallel.ai/mcp` | `web_search` | Bearer | `{objective: query, search_queries: [query]}` | `structuredContent.results`，excerpts 用 `\n\n` 拼 |
| Firecrawl | `https://mcp.firecrawl.dev/v2/mcp` | `firecrawl_search` | Bearer | `{query, limit: 8}` | `content[].text` 内嵌 JSON → `data.web[]` |
| TinyFish | `https://agent.tinyfish.ai/mcp` | `search` | `X-API-Key` + `Mcp-Session-Id` | `{query}` | `content[].text` 内嵌 JSON → `results[]` |
| Tavily | `https://api.tavily.com/search` | —（REST） | Bearer | `{query, search_depth: "basic", max_results: 8, chunks_per_source: 3}` | 直接 `results[]` |

统一结果契约（`packages/schema/src/websearch.ts`）：`Result = { url, title?, content?, time.published? }`。

服务治理层值得借鉴的六点：

1. **选择策略**：配置值 `random` / 指定 provider ID / `false`（禁用），持久化到 KV；
2. **429 冷却**：命中 429 后按 `retry-after` 计算冷却时长（纯秒数、HTTP-date 均可解析，缺省 60 秒），冷却中的 provider 被跳过；
3. **失败轮转**：`random` 模式下失败自动切下一个可用 provider，全部冷却才报错；
4. **会话粘性**：同一 session 复用已选 provider，避免并发请求把 provider 选来选去；
5. **工具可见性**：无可用 provider 时，用 session hook 把 `websearch` 从 LLM 工具列表里删掉，避免模型调用不存在的工具；
6. **安全收口**：Webfetch/Websearch 拒绝带凭据的 URL，忽略 `#fragment` 匹配权限规则，MCP 响应体硬限 256KB。

### 4.4 Agent-Reach 的实现

Agent-Reach（`D:\agent-reach`，v1.6.1）的 provider 比 opencode 更少但调度更精细。搜索只有 Exa 一家（免 key MCP），网页阅读是 Jina Reader 首选、Exa `web_fetch_exa` 兜底——OmniAgent 的 fetchpage 也在用 Jina Reader，属同一技术路线。

| 机制 | 实现位置 | 要点 |
|---|---|---|
| 声明式后端链 | `channels/base.py:30-49` | 每个动作声明 `(backend, method)` 有序列表，失败按序降级 |
| 错误分类与终止码 | `runtime/result.py:23-45` | 8 种错误码 + `FINAL_CODES`：参数错 / 不存在 / 限流 / 需登录 / 平台封禁不再换后端 |

| 共享超时预算 | `runtime/clock.py` | 一个动作的所有后端共享同一个 Clock，单个后端不得拖垮整链 |
| 公开网页兜底 | `runtime/public_web.py` | 未登录站点用 `site:` 搜索兜底，并标注来源与"完整性未验证" |

## 5. 与 OmniAgent 现状的逐项差距

| 项 | opencode v2.3.2 | OmniAgent 现状 | 差距定性 |
|---|---|---|---|
| Provider 数 | 5（Exa/Parallel/Firecrawl/TinyFish/Tavily） | 3（Parallel MCP / Exa MCP / Bing HTML） | 少 2 个，且第三级是脆弱的 HTML 解析 |
| 降级策略 | 429 冷却 + 轮转 | 失败即降级，无记忆，下次从头打同一个 | **核心差距** |
| Parallel 结果解析 | `structuredContent` 优先 | `content[0].text` 再 `json.loads` | 脆弱点 |
| Excerpts 利用 | 全部 excerpts 拼接 | 只取第一条 | 内容损失 |
| MCP 响应上限 | 256KB | 无 | 内存/异常风险 |
| 结果契约 | 统一 `{url,title,content,published}` Schema | 每家各自拼 dict（`snippet`、`source` 字段不统一） | 可维护性 |
| 工具可见性治理 | 无 provider 时从工具列表移除 | 仍暴露工具，靠 error llm_data 兜底 | 次要差距 |
| 域名白/黑名单 | 无 | **有，且按 host 边界匹配** | 本系统优势，保留 |
| 代理透传 | 无 | **有** | 本系统优势，保留 |
| 长查询拆分 | 无 | **有**（`_split_long_query`） | 本系统优势，保留 |
| Bing HTML 兜底 | 无 | **有** | 本系统优势，保留（但降为第四级） |

## 6. 总体架构决策：轻量扩展槽与 search/fetch 职责边界

### 6.1 扩展槽的正确粒度：调度统一，解析各自写

opencode 与 Agent-Reach 两个项目的实证结论一致：

| 能统一 | 不能统一 |
|---|---|
| 有序降级编排、错误分类、冷却/暂停、响应体上限、统一结果字段、尝试轨迹 | 每家的请求参数与响应解析——Exa 是 `Title:/URL:` 文本块，Parallel 是 `structuredContent`，Tavily 是 REST JSON，Bing 是 HTML，fetch 的 Jina 又是另一套 |

opencode 为 5 家写了 5 份解析，Agent-Reach 也每家单独解析。所以扩展槽的正确形态是"**调度层可插拔、解析层各自写**"。若做成通用插件框架（动态发现、统一参数 schema、元类注册），只是给几个封闭端点增加抽象成本，违反 YAGNI 与 KISS-DIRECT。

### 6.2 底座落地形态

新增 `backend/app/tools/network/net_backend.py`，只放共性，不碰业务逻辑：

| 件 | 内容 |
|---|---|
| 错误码 | `BAD_INPUT / RATE_LIMITED / UPSTREAM_BROKEN / TIMEOUT / NOT_FOUND / NEED_SETUP`（与 7.4 代码一致） |
| 终止码 | `BAD_INPUT / NOT_FOUND`——命中即停，换后端无意义；`RATE_LIMITED` 是**单 provider 级**：冷却当前 provider 后继续降级，全部 provider 都冷却才作为最终错误返回 |
| 后端描述 | `(id, kind, call, cooldown_seconds_by_code)` 的轻量结构，不用元类/注册表库 |
| 运行器 | `run_chain(kind, params, ctx) -> items + attempts + backend/error` |
| 冷却 | 按 `(kind, backend_id)` 记失败时间与到期时间；限流 3600s、上游坏 120s、超时/未安装 60s |
| 结果字段 | `{title, url, content/snippet, published, source}` 统一 |

`run_chain` 做且只做：跳过冷却 → 调后端 → 分类异常 → 记冷却 → 记 attempts → 成功返回、失败降级或终止。

冷却存储按部署形态二选一：单进程用模块级 dict 即可；多 worker 则照搬 Agent-Reach 的落盘 + 文件锁（`state.mutate` 模式）。默认按单进程实现，不做提前抽象。

### 6.3 新增一个搜索源只要三步

1. 在 `search_web.py` 写 `_search_xxx(query, num_results, proxy) -> List[dict]`，只管请求与解析，返回统一字段；
2. 在 `search_web.py` 顶部的 `SEARCH_CHAIN` 列表加一行 `(id, callable)`；
3. 若需密钥，在配置样例加一个键（经 `get_config_path()` 读写，禁止硬编码、禁止直接写 `config/config.yaml`）。

工具主函数、schema、别名映射、observation_formatter、前端全部不动。这就是"槽"的实际价值。

### 6.4 websearch 与 fetchweb：共享底座，分开工具，各自链条

结论：**不合并成一个工具**。

| 理由 | 说明 |
|---|---|
| 动作本质不同 | search 是发现（query → items[]），fetch 是检索（url → 正文）；输入、输出、超时、缓存策略都不同 |
| 上游几乎不重叠 | search 链是 Parallel / Exa / Tavily / Bing；fetch 链是 HTTP → Playwright → Jina Reader（现网实际，无 Exa） |
| 合并代价大 | 要改工具名、schema、别名映射（`websearch→searchweb`、`webfetch→fetchpage`）、观察格式化路由、前端展示，风险远大于收益 |
| 单一职责 | 底座负责共性，工具负责特性，一个工具一件事 |
| 实证 | Agent-Reach 正是"一个 WebChannel + 两个 Action（search/read）+ 各自 backends 列表"，没有把两者揉成一个工具 |

共享的只有底座（错误码、冷却、attempts、响应上限、统一字段）。`fetch_webpage.py` 现有的 trafilatura 抽取、Playwright 渲染、Jina 兜底、SSRF 防护全部保留，只把它的降级循环接到 `run_chain` 上。

### 6.5 第 4 章对照结论的采纳与风险定性更新

第 4 章给出了 opencode 与 Agent-Reach 的实现事实，此处只记录本项目的采纳决策：

| 第 4 章机制 | 采纳决策 |
|---|---|
| 声明式后端链（Agent-Reach） | 采纳：固定 if 链改为列表 + `run_chain`，与 6.2 合并 |

| 分级冷却（Agent-Reach） | 采纳：限流 3600s / 上游坏 120s / 超时 60s；多 worker 时补落盘 |

### 7.1 设计原则与前置假设

前置假设（已确认项以用户决定为准）：

1. 单 worker 部署，冷却用模块级 dict；若确认多 worker，只把 `net_backend.py` 的冷却存储换成落盘 + 文件锁，其余代码不变；
2. 429 行为变更**已确认接受**：**不重试**，命中即冷却该 provider 并直接换下一家；全部冷却才最终报错；
3. Tavily key 可选：无 key 时该 provider 不注册，链条自动跳过，S3 可滞后实施；
4. 阶段一完成后必须先验收，验收通过才启动阶段二（见 9.1 的阶段门禁）。

设计原则：

- **后端为主**：改动在 `backend/app/tools/network/` 内聚完成（新增 `net_backend.py` + 改 `search_web.py`），前端零改动；
- **KISS / YAGNI**：不引入 MCP SDK、不建通用插件框架（只做 6.2 的轻量调度底座）、不搞配置系统升级；每阶段只解决一个明确问题；

- **禁止 backward**：直接改现有逻辑，不加兼容开关、不留双路径；
- **拆分复制不重写**：按现有代码风格增量修改，保持函数边界与工具返回契约（`data.items` + `llm_data`）不变。

# -*- coding: utf-8 -*-
# 2026-11-23 小欧 - 网络检索后端统一调度底座：错误分类、分级冷却、尝试轨迹
"""网络检索后端调度底座 - 只做共性编排，不含任何 provider 业务逻辑。"""

import time

NOT_FOUND = "NOT_FOUND"

FINAL_CODES = frozenset({BAD_INPUT, NOT_FOUND})

DEFAULT_COOLDOWN_SECONDS = {
    RATE_LIMITED: 3600,
    UPSTREAM_BROKEN: 120,
    TIMEOUT: 60,
    NEED_SETUP: 60,
}


class NetError(Exception):
    """带统一错误码与重试等待的后端异常。"""

    def __init__(self, code: str, message: str, retry_after: Optional[float] = None):
        super().__init__(message)
        self.code = code
        self.message = message
        self.retry_after = retry_after


def _retry_after_seconds(value: Optional[str]) -> Optional[float]:
    """Retry-After 支持秒数与 HTTP-date，无法解析返回 None。"""
    if not value or not value.strip():
        return None
    try:
        return max(0.0, float(value.strip()))
    except ValueError:
        pass
    try:
        from datetime import timezone

        when = parsedate_to_datetime(value.strip())
        if when is None:
            return None
        if when.tzinfo is None:
            when = when.replace(tzinfo=timezone.utc)
        return max(0.0, when.timestamp() - time.time())
    except (TypeError, ValueError, OverflowError):
        return None


def classify(exc: BaseException) -> NetError:
    """把任意后端异常归一为 NetError。"""
    if isinstance(exc, NetError):
        return exc
    if isinstance(exc, httpx.HTTPStatusError):
        status = exc.response.status_code
        if status == 429:
            return NetError(RATE_LIMITED, "HTTP 429", _retry_after_seconds(exc.response.headers.get("retry-after")))
        if status == 404:
            return NetError(NOT_FOUND, "HTTP 404")
        if status in (401, 403):
            return NetError(NEED_SETUP, f"HTTP {status}")
        if status == 400:
            return NetError(BAD_INPUT, "HTTP 400")
        return NetError(UPSTREAM_BROKEN, f"HTTP {status}")
    if isinstance(exc, (httpx.TimeoutException, TimeoutError)):
        return NetError(TIMEOUT, "请求超时")
    if isinstance(exc, httpx.ConnectError):
        return NetError(UPSTREAM_BROKEN, "连接失败")
    return NetError(UPSTREAM_BROKEN, f"{type(exc).__name__}: {exc}")


@dataclass(frozen=True)
class Backend:
    id: str
    call: Callable[..., Any]


# 2026-11-23 小欧 - 默认单进程内存冷却；多 worker 部署时替换为落盘 + 文件锁
_COOLDOWNS: Dict[Tuple[str, str], float] = {}


def cooldown_left(kind: str, backend_id: str) -> float:
    """返回剩余冷却秒数，未冷却或已过期返回 0。"""
    key = (kind, backend_id)
    until = _COOLDOWNS.get(key)
    if until is None:
        return 0.0
    if until <= time.monotonic():
        _COOLDOWNS.pop(key, None)
        return 0.0
    return until - time.monotonic()


def mark_failure(kind: str, backend_id: str, error: NetError) -> None:
    """按错误码记录冷却；Retry-After 优先于分级缺省。"""
    seconds = error.retry_after
    if seconds is None:
        seconds = DEFAULT_COOLDOWN_SECONDS.get(error.code, 60)
    _COOLDOWNS[(kind, backend_id)] = time.monotonic() + seconds


async def run_chain(kind: str, chain: Tuple[Backend, ...], args: Tuple[Any, ...]) -> Dict[str, Any]:
    """按序尝试后端；返回 items/backend/attempts/error，不向外抛业务异常。"""
    attempts: List[dict] = []
    last_error: Optional[NetError] = None
    cooled_all = True
    for backend in chain:
        left = cooldown_left(kind, backend.id)
        if left > 0:
            attempts.append({"backend": backend.id, "result": "SKIPPED", "retry_after_seconds": int(left)})
            continue
        cooled_all = False
        try:
            items = await backend.call(*args)
        except BaseException as exc:
            error = classify(exc)
            attempts.append({"backend": backend.id, "result": error.code, "message": error.message})
            if error.code in FINAL_CODES:
                return {"items": [], "backend": None, "attempts": attempts, "error": error}
            mark_failure(kind, backend.id, error)
            last_error = error
            continue
        if not items:
            attempts.append({"backend": backend.id, "result": "EMPTY"})
            continue
        return {"items": list(items), "backend": backend.id, "attempts": attempts, "error": None}
    error = last_error or (
        NetError(RATE_LIMITED, "所有搜索引擎冷却中") if cooled_all else NetError(NOT_FOUND, "无搜索结果")
    )
    return {"items": [], "backend": None, "attempts": attempts, "error": error}

#### 9.3.2 新增文件 `backend/app/tools/network/net_mcp_stdio.py`

本地 MCP Server 走 stdio（JSON-RPC over 进程 stdin/stdout），与阶段一 `mcp.ts` 风格的 HTTP MCP 并列封装成通用调用。

```python
# -*- coding: utf-8 -*-
# 2026-11-23 小欧 - 本地 MCP Server 的 stdio 调用封装：JSON-RPC over 子进程管道
"""本地 MCP stdio 调用 - 供国内社交平台 MCP Server 复用。"""

import asyncio
import json
from typing import Any, Dict, Optional

_SOCIAL_MCP_CMD = "cn-scraper-mcp"


async def call_tool(tool: str, arguments: Dict[str, Any], timeout: float = 25.0) -> Optional[Any]:
    """启动本地 MCP Server，调用一个工具并取回结构化结果；失败返回 None 交链条降级。"""
    try:
        proc = await asyncio.create_subprocess_exec(
            _SOCIAL_MCP_CMD,
            stdin=asyncio.subprocess.PIPE,
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.PIPE,
        )
    except (FileNotFoundError, OSError):
        return None
    try:
        await _write_rpc(proc, {
            "jsonrpc": "2.0", "id": 1, "method": "initialize",
            "params": {"protocolVersion": "2024-11-05", "capabilities": {},
                       "clientInfo": {"name": "omniagent", "version": "1.0"}},
        })
        await _read_rpc(proc, timeout)  # initialize 应答，失败由 wait_for 抛出
        await _write_rpc(proc, {"jsonrpc": "2.0", "method": "notifications/initialized"})
        await _write_rpc(proc, {
            "jsonrpc": "2.0", "id": 2, "method": "tools/call",
            "params": {"name": tool, "arguments": arguments},
        })
        msg = await _read_rpc(proc, timeout)
        result = msg.get("result") or {}
        if result.get("isError"):
            return None
        content = result.get("content") or []
        text = next((c.get("text", "") for c in content if c.get("type") == "text"), "")
        return json.loads(text) if text.strip().startswith(("{", "[")) else text
    except (asyncio.TimeoutError, ValueError, OSError):
        return None
    finally:
        try:
            proc.kill()
            await proc.wait()
        except ProcessLookupError:
            pass


async def _write_rpc(proc: asyncio.subprocess.Process, payload: Dict[str, Any]) -> None:
    line = (json.dumps(payload, ensure_ascii=False) + "\n").encode("utf-8")
    proc.stdin.write(line)
    await proc.stdin.drain()


async def _read_rpc(proc: asyncio.subprocess.Process, timeout: float) -> Dict[str, Any]:
    """读一行 JSON-RPC 应答；stdio MCP 的响应逐行输出。"""
    line = await asyncio.wait_for(proc.stdout.readline(), timeout=timeout)
    return json.loads(line.decode("utf-8", errors="replace"))
```
