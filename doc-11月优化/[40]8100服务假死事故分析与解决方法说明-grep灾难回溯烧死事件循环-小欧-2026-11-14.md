## 3. 根因分析

### 3.1 直接根因: 单行内灾难回溯(ReDoS)

`grep_file_content.py` 旧实现中, 对每个匹配行的正则匹配在**单行文本**上执行 `finditer`。当用户 pattern 含嵌套量词(如 `(a+)+`)且行内容构造恶意时, 回溯次数随行长度指数爆炸, 单次匹配耗时可达数十秒以上。

关键缺陷点: 旧代码的 deadline(总时限)检查只在**文件间**进行——即"处理完一个文件才看一次表"。单行匹配一旦进入灾难回溯, 该行内部没有任何超时机制, deadline 形同虚设。更致命的是该匹配运行在 `asyncio.to_thread` 派生的线程中, 而 8100 后端该路径实际占死事件循环调度资源, 导致整个服务假死。

实测对照: 同一个 ReDoS 炸弹 pattern, 旧 `re` 引擎耗时 50.9 秒无响应; 换 `regex` 引擎 + timeout 后 0.1 秒返回。

### 3.2 放大因素: 两轮护栏删除放大了暴露面

- 缺陷本身自 2026-06-22 grep 拆分为独立文件时即存在(长期存在, 非近期退化)。
- 2026-07-20 删除单文件大小上限、2026-08-21 删除根目录拒绝护栏后, 工具可触达的输入面显著变大, 恶意/意外构造的行更容易进入匹配引擎, 事故概率被放大。

结论: **根因是匹配引擎无单次匹配超时**, 两轮护栏删除是放大器而非根因。因此修复方向是给引擎装真兜底, 而不是恢复任何不合理的限制闸门。

## 4. 解决方法

修复遵循"不设任何大小/根目录/正则限制, 靠流式 + 超时保证无限制下正常工作"的总原则, 共四项:

### 4.1 匹配引擎换 regex 库 + timeout(根因修复)

- `tool_constants.py` 新增 `GREP_INPUT_MATCH_TIMEOUT_SECONDS = 5`。
- `grep_file_content.py` 匹配引擎由 `re` 换为已安装的 `regex` 库(语法兼容 re), 每次单行匹配传入 `timeout=5`; 超时置 `_deadline_exceeded`, 走既有 truncated/warning 收口, 不抛异常不中断整体搜索。
- 两层防线: 引擎级 timeout(单行兜底) + 逐行 deadline 检查(`_search_one_file` 每行检查总时限, deadline 到即提前收口)。

### 4.2 大文件读取流式化(OOM 同类处置)

- `file_encoding.py` 的 `safe_read_lines` 改为流式: 编码探测改为头部 64KB 采样, 逐行 yield, 内存占用 O(行) 而非 O(文件)。
- grep 侧仅在 context>0(需要上下文行)时才物化列表, 其余路径全程流式消费。G 级日志文件可正常搜索。

### 4.3 删除静态 ReDoS 检测死代码

- 原 `_REDOS_PATTERNS` 静态拒绝清单与 regex+timeout 兜底功能重复, 且静态清单永远枚举不全(真兜底应是引擎超时而非黑名单)。按"超时收口唯一化"原则整段删除, 相应 4 处固化旧闸门行为的过时测试断言更新为新语义。

### 4.4 同步工具有界执行器泛化(事故形态架构级根治)

- `tool_retry_engine.py` 中原 shell 专用的 `_execute_in_shell_executor` 参数化为 `_execute_in_bounded_executor`, 新增 `_TOOL_EXECUTOR(16)`。
- 全部同步工具与 shell 同构隔离: 即使某同步工具内部卡死, 也只占用有界池的一个槽位, 不再侵蚀默认 executor 拖垮其他工具调度。
- 附带核实: `edit_text_file` 的四处 `findall` pattern 全部是 `re_mod.escape(old_string)` 生成的字面量, 零回溯风险, 按 YAGNI 不改。
