## 一、背景与目标

### 1.1 现状（串行降级链）

`search_web` 现在是**串行降级链**（`net_backend.run_chain`）：

```
parallel → exa → firecrawl → tinyfish → bing   （首中即停）
```

- 正常运行只打第一个存活的后端（parallel），拿到结果即返回；
- 前端失败 → 记冷却 → 降级下一家；五家都失败才报错。

### 1.2 串行的两个局限

| 局限 | 表现 | 影响 |
|------|------|------|
| **① 单源天花板（信息价值）** | 只取一家引擎的前 N 条，这家索引库/排序/snippet 决定一切 | 同 query 另一家可能召回完全不同但高度相关的优质结果，串行丢弃了 |
| **② 尾部延迟（可用性）** | 首选挂/慢时要吃满该家 timeout_cap 才降级 | 首选超时 20s 才轮到下一家，交互体验差 |

### 1.3 实测证据（充分支撑"并行合并有价值"）

对 **16 个不同领域 × 3 条 query（共 48 条）** + 12 条中文 + 4 条英文，复用真实引擎 `_search_mcp_engine` 实测：

| 指标 | 实测值 | 结论 |
|------|--------|------|
| 领域级 Jaccard 重叠率 | **0.00~0.09，平均 0.03** | 两家几乎**不重叠（97% 互补）** |
| exa 为 parallel 补新率 | 90%~100% | 并行合并能从第二家额外挖出近一倍互补结果 |
| 两家返回质量 | 均高质量、同 query 相关 | 互补非冗余假象 |
| parallel 连续高频 | **约 12~13 次后触发 429** | **parallel 免费层有真实配额限制**，是并行方案的硬约束 |
| exa 全程 | 48 次全部正常 | 稳定的配位发动机，可作 parallel 的可靠并源 |

**结论**：并行 parallel + exa 合并能带来串行单源**实质且确定**的信息增益（近翻倍），但必须**内建 parallel 配额保护**（429 自动让位 exa）。

## 二、方案目标

1. **信息价值**：一次搜索合并 parallel + exa 两家互补结果，URL 去重后输出更全的结果集（显著优于单源）。
2. **稳定性**：不引入新故障面；并行失败/限流自动降级，可用性不劣于现有串行链。
3. **配额保护**：parallel 触发 429 后自动让位（冷却降级到 exa 单源），绝不硬打限流的后端。
4. **向后兼容**：底层 `run_chain` 串行语义、classify 分类、mark_failure 冷却、attempts 轨迹全部保留，扩展并行合并为**总线新增模式**（OCP，不动现有串行调用方）。

## 三、总体架构

### 3.1 改造位置

```
search_web.py
 ├─ SEARCH_CHAIN（不变：parallel/exa/firecrawl/tinyfish）+ bing（不变）
 ├─ 新增 searchweb 入口分支：默认走「并行合并模式」 (P4)
 │    ├─ 前两家 parallel + exa 并行并发
 │    ├─ 两家都返回 → URL 去重合并
 │    ├─ parallel 429/失败 → 自动降级 exa 单源（配额保护）
 │    └─ 合并不足或两家都失败 → 续原 run_chain 串行兜底(firecrawl/tinyfish/bing)
 └─ 新增 _merge_search_results() 合并去重函数（DRY，结果项带 source 字段）
```

### 3.2 依赖关系（复用现有，零新增外部依赖）

| 依赖 | 来源 | 用途 |
|------|------|------|
| `_search_mcp_engine(engine,q,n,proxy,timeout)` | search_web 现有 | 并行并发调用两家 |
| `asyncio.gather(return_exceptions=True)` | 标准库 | 并行执行两家 + 异常隔离 |
| `classify()` | net_backend 现有 | 并行失败归一错误码 |
| `mark_failure()` / `cooldown_info()` | net_backend 现有 | 429/失败冷却 |
| `run_chain()` | net_backend 现有 | 合并不足时续串行兜底 |
| `_normalize_search_url()` | 新增（复用 fetch 链/搜索链已有 URL 归一习惯） | 合并去重键 |

**并发安全**：parallel/exa 各自独立 httpx client（`create_http_client` 每次新建），无共享可变状态；`_COOLDOWNS` 是进程内 dict，单 asyncio 事件循环无抢占（与现有串行链相同，多加的写入来自 gather 内两家，仍同循环安全）。

## 四、详细设计

### 4.1 searchweb 入口改造（并行合并模式）

在 `searchweb()` 主函数，把链头两家从"串行降级"改为"并行合并 + 串行兜底"：

```python
# search_web.py — 主函数内, 原有 proxy/query/num_results 校验之后
budget = SEARCH_WEB_TIMEOUT_DEFAULT if timeout is None else timeout

# P4 并行合并: 前两家 parallel + exa 并发, URL 去重合并; 不足或失败续串行兜底
result = await search_parallel_merge(
    query, num_results, proxy, budget,
    "search", (query, num_results, proxy),
)
```

### 4.2 核心函数 `search_parallel_merge`（并行合并 + 配额保护 + 串行兜底）

> **导入依赖说明**（实施时按 search_web.py 现存别名对齐）：`time` 在文件头已 `import time as _time_mod`, 故下方 `time.monotonic()` 实施时应写 `_time_mod.monotonic()`; `urlparse` 已导入(L47)。`asyncio` 需在 search_web.py 顶部新增 `import asyncio`（当前文件未直接 import asyncio, 实施时补上）。

```python
# search_web.py 新增 — 商量 2026-11-24
# 并行第一段(parallel+exa) + 串行第二段(firecrawl/tinyfish/bing) 两层编排
# parallel 免费层有 429 配额约束(实测), 触发即冷却让位 exa, 绝不硬打
def _remaining(deadline):
    """剩余预算秒数; deadline 为 None(不限)则返回 None"""
    if deadline is None:
        return None
    return max(0.1, deadline - time.monotonic())

async def search_parallel_merge(query, num_results, proxy, budget_sec, kind, args):
    deadline = None if budget_sec is None else (time.monotonic() + budget_sec)

    # ---- 第一段: 前两家并行(gather return_exceptions, 一家失败不拖垮另一家) ----
    # parallel 已冷却(429/上游坏/超时) → 不进并行组, 单走 exa(配额保护)
    p_left, _ = cooldown_info(kind, "parallel")
    e_left, _ = cooldown_info(kind, "exa")
    # (name, task) 二元组: 保证 gather 结果与后端名一一对应, 杜绝管道错位
    pending = []
    if p_left <= 0:
        pending.append(("parallel", asyncio.create_task(
            _search_mcp_engine("parallel", query, num_results, proxy, _remaining(deadline)))))
    if e_left <= 0:
        pending.append(("exa", asyncio.create_task(
            _search_mcp_engine("exa", query, num_results, proxy, _remaining(deadline)))))

    items_map, errors = {}, {}
    if pending:
        names = [n for n, _ in pending]
        tasks = [t for _, t in pending]
        results = await asyncio.gather(*tasks, return_exceptions=True)
        for name, res in zip(names, results):
            if isinstance(res, BaseException):
                errors[name] = res          # 异常统一抛给 _mk_parallel_out 分类+冷却
            elif res:
                items_map[name] = res       # 有结果才记; 空结果保持缺省 → 下游按 EMPTY
    par_items = items_map.get("parallel")
    exa_items = items_map.get("exa")

    # ---- 错误统一分类 + 冷却(与 run_chain 完全同口径, DRY 不与串行分裂) ----
    failures, attempts = _mk_parallel_out(
        name_map={"parallel": par_items, "exa": exa_items},
        errors=errors, kind=kind)

    # ---- 合并: URL 去重, 互补信息拼装 ----
    merged = merge_search_items([par_items, exa_items], num_results)

    # ---- 第二段: 合并已足 → 直接返回; 不足/两败 → 续串行兜底(firecrawl/tinyfish/bing) ----
    if merged and len(merged) >= num_results:
        return {"items": merged, "backend": "parallel+exa",
                "attempts": attempts, "failures": failures,
                "error": None, "budget_exhausted": False}

    # 兜底链 = 原 SEARCH_CHAIN 去掉前两家(已并行试过) + bing
    tail_chain = SEARCH_CHAIN[2:] + (Backend("bing", lambda q, n, p, t: _search_bing(q, n, p, t)),)
    leftover = await run_chain(kind, tail_chain, args, budget_sec=_remaining(deadline))
    # 合并结果 + 兜底结果(去重), 覆盖不足部分
    final = merge_search_items([merged, leftover.get("items")], num_results)
    merged_out = final or leftover.get("items", [])
    backend_src = leftover.get("backend") or ""
    return {**leftover, "items": merged_out,
            "backend": "parallel+exa" if merged else
                       ("parallel+exa+" + backend_src if backend_src else "parallel+exa"),
            "failures": failures + leftover.get("failures", [])}
```

> **设计说明**：
> - 并行组 `pending` 用 `(name, task)` 二元组，`names = [n for n,_ in pending]` 与 `tasks` 一一对应，`gather` 结果经 `zip(names, results)` 正确归属（误差隔离、冷却对应的后端不进 pending）。
> - `parallel` 429 冷却后 `cooldown_info("search","parallel")>0`，该家不进并行组，`par_items` 保持 None，结果仅由 exa 提供（配额保护，不硬打限流后端）；待 3600s 冷却结束自动恢复。
> - 两段编排：合并已足 → 直接返回（只用两家，最快）；不足 → 续 `run_chain`（firecrawl/tinyfish/bing）兜底，可用性不退化。

### 4.3 错误处理 `_mk_parallel_out`（并行组错误统一分类 + 冷却）

**并行组内错误统一用 gather 后的 `errors` 映射处理——不在 task 内记冷却（DRY，与 run_chain 同口径单点冷却）**：

```python
def _mk_parallel_out(name_map, errors, kind):
    """并行组错误统一分类 + 冷却; 返回 (failures, attempts), 与 run_chain 口径一致。
    - name_map: {backend_id: items}, 有结果才在; 冷却被跳过的家(items 缺省)记录为 SKIPPED
    - errors:   {backend_id: BaseException}, gather return_exceptions 捕获的异常
    返回元组与 run_chain 的 attempts/failures 结构保持一致, 前端与排障口径无变化。
    """
    failures, attempts = [], []
    for name in ("parallel", "exa"):
        err = errors.get(name)
        if err is not None:
            net = classify(err)
            mark_failure(kind, name, net)       # 429→3600s/上游坏→120s/超时→60s 冷却(与串行同)
            failures.append({"backend": name, "code": net.code, "message": net.message[:200]})
            attempts.append({"backend": name, "result": net.code,
                             "message": net.message[:200]})
        elif name in name_map:
            attempts.append({"backend": name, "result": "OK",
                             "items": len(name_map[name])})
        else:
            # 冷却被跳过 或 返回空: 统一 SKIPPED/EMPTY
            attempts.append({"backend": name,
                             "result": "SKIPPED" if cooldown_info(kind, name)[0] > 0 else "EMPTY"})
    return failures, attempts
```

> **修正说明（相对 4.2 早期草案）**：并行组 `pending` 用 `(name, task)` 二元组构造，`gather` 结果经 `zip(names, results)` 一一对应，**消除了"parallel 冷却只剩 exa 时管道错位"的隐患**——这是保证"架构稳定"的关键修正（此隐患在初稿的 `zip(("parallel","exa"), results)` 中存在，现已消除）。

### 4.4 配额保护核心语义

- 并行组 `gather(return_exceptions=True)`，一家失败**不中断**另一家；
- `classify` 把 429 归一 `ERR_NET_RATE_LIMITED` → `mark_failure` 记 3600s 冷却（由 4.3 `_mk_parallel_out` 统一处理）；
- 下次调用 `cooldown_info("search","parallel")>0` → parallel 直接不进并行组（`pending` 只加 exa），**exa 单源接管**；
- 绝无"死循环打限流后端"，与现有串行链冷却记忆完全同构。

### 4.5 合并函数 `merge_search_items`（DRY + 去重保序）

```python
# search_web.py 新增 — 商量 2026-11-24
# 多源结果 URL 去重合并: 保首源顺序, 次源新 URL 追加; 归一化去追踪参数, 冗余安全(source 已标注)
def _normalize_search_url(url: str) -> str:
    """URL 归一化键: 去 scheme/www/尾斜杠/#fragment/utm*/gclid 类追踪参数"""
    try:
        p = urlparse(url)
        host = (p.netloc or "").lower()
        if host.startswith("www."):
            host = host[4:]
        path = p.path.rstrip("/") or "/"
        return f"{host}{path}"
    except Exception:
        return (url or "").strip().lower()

def merge_search_items(sources: List[Optional[List[dict]]], num_results: int) -> List[dict]:
    """多源结果合并: URL 去重, 保顺序; 返回至多 num_results 条。
    - sources: 各来源 items 的列表(可为 None/空), 顺序即优先级(首源在前)
    """
    merged, seen = [], set()
    for items in sources:
        for it in items or []:
            if not it or not it.get("url"):
                continue
            key = _normalize_search_url(it["url"])
            if key in seen:
                continue
            seen.add(key)
            merged.append(it)
            if len(merged) >= num_results:
                return merged
    return merged
```

> 每项 result dict 已带 `source` 字段（Parallel/Exa/...），合并后用户/下游能分辨来源——**完全不破坏现有 observation_formatter 的 items 分支契约**。

### 4.6 预算核算

| 预算段 | 原串行 | 并行合并方案 |
|--------|--------|-------------|
| 链头 parallel + exa | 20+20=40s | **max(20,20)=20s**（并行并发，取较长一家） |
| 兜底 firecrawl+tinyfish+bing | 20+15+15=50s | 不变（合并不足才走） |
| 合计最坏 | ~90s | **~50s**（合并足时）/ ~70s（走兜底） |

**预算更宽裕、更不易耗尽**，且 `SEARCH_WEB_TIMEOUT_DEFAULT=90` 完全覆盖，无需改动该常量。

## 六、技术架构稳定性论证

| 稳定性维度 | 保障 |
|-----------|------|
| **并发安全** | parallel/exa 独立 httpx client；`_COOLDOWNS` 进程内 dict，单 asyncio 循环无抢占（与现有串行链一致） |

| **配额保护** | parallel 429 → classify→mark_failure→3600s 冷却→下次自动让位 exa；绝不硬打 |
| **兜底不退化** | 合并不足/两家都失败 → 续原 `run_chain` 串行(firecrawl/tinyfish/bing)，可用性与现状持平甚至更好 |
| **向后兼容** | 底层 run_chain/classify/冷却/attempts 全保留；串行调用方不受影响（新增并行模式） |
| **可回退** | `SEARCH_PARALLEL_MERGE` 一键切回原串行，故障秒回退 |
| **无新依赖** | 仅用 asyncio 标准库 + 现有网络底座，零新增第三方包 |
| **限流礼貌** | 并行只针对前两家(均无 hard 配额实测；parallel 有 429 但冷却自动降级)，不碰 Firecrawl 付费限速面 |

## 八、风险与缓解

| 风险 | 缓解 |
|------|------|
| 每次双打 quota 翻倍 → parallel 更快 429 | 实测 parallel 单发 keyless 无 hard 限；429 冷却自动降级 exa 单源；关键场景才启发并行（可选：按 query 重要性开关） |
| 结果合并引入重复/乱序 | 归一化去追踪参数 + 保首源顺序 + source 标注；误并不同页面已被尾斜杠/#fragment/track 归一规避 |
| gather 内一家慢拖累 | 各带剩余预算硬超时(与串行同) + 异常隔离，最坏=较慢一家耗时 |
| 对上游礼貌性 | 只并发前两家(无 hard 配额实测)，不并发 Firecrawl 限速面 |
| 取消/悬挂连接 | httpx async 取消点成熟 + 流式读 SSE 可中断，冒烟验证覆盖 |

## 九、结论

1. **实测已充分证明并行合并价值**：parallel + exa 互补性 97%（Jaccard 平均 0.03），一次合并信息增益近翻倍，串行单源给不了。
2. **方案切实可行且架构稳定**：复用现有 run_chain/classify/冷却/attempts 全部底座，仅新增"前两家并行合并 + URL 去重 + 配额保护"，后三家串行兜底不退化。
3. **配额保护是稳定关键**（实测 parallel 429）：429 冷却自动让位 exa，绝不硬打限流后端。
4. **零新增依赖 + 一键回退**：仅用 asyncio + 现有网络底座；`SEARCH_PARALLEL_MERGE` 一行开关可秒回串行。
5. **推荐实施**：按阶段1→4 渐进落地，每阶段独立可验证，风险可控。
