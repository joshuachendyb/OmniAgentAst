## 一、背景与目标

### 1.1 现状（串行降级链，2026-11-24 链序重排已实施）

`search_web` 现在是**串行降级链**（`net_backend.run_chain`）：

```
exa → tavily → parallel → tinyfish → firecrawl → bing   （首中即停）
```

- 正常运行只打第一个存活的后端（exa），拿到结果即返回；
- 前端失败 → 记冷却 → 降级下一家；六家都失败才报错。

### 1.2 串行的两个局限

| 局限 | 表现 | 影响 |
|------|------|------|
| **① 单源天花板（信息价值）** | 只取一家引擎的前 N 条，这家索引库/排序/snippet 决定一切 | 同 query 另一家可能召回完全不同但高度相关的优质结果，串行丢弃了 |
| **② 尾部延迟（可用性）** | 首选挂/慢时要吃满该家 timeout_cap 才降级 | 首选超时 20s 才轮到下一家，交互体验差 |

### 1.3 实测证据一：双源互补（parallel + exa）

对 **16 个不同领域 × 3 条 query（共 48 条）** + 12 条中文 + 4 条英文，复用真实引擎 `_search_mcp_engine` 实测：

| 指标 | 实测值 | 结论 |
|------|--------|------|
| 领域级 Jaccard 重叠率 | **0.00~0.09，平均 0.03** | 两家几乎**不重叠（97% 互补）** |
| exa 为 parallel 补新率 | 90%~100% | 并行合并能从第二家额外挖出近一倍互补结果 |
| parallel 连续高频 | **约 12~13 次后触发 429** | **parallel 免费层有真实配额限制**，是并行方案的硬约束 |
| exa 全程 | 48 次全部正常 | 稳定的配位发动机，可作 parallel 的可靠并源 |

### 1.4 实测证据二：三源互补（firecrawl + tinyfish + tavily，2026-11-24）

3 组 query（中文 AI Agent / 英文 FastAPI / 英文 SQLite）× 3 引擎 × 各 8 条，真实调用实测：

**延迟**：

| 引擎 | 平均延迟 | 稳定性 |
|------|---------|--------|
| tavily | **1.6s** | 最快最稳（1.5~1.7s） |
| tinyfish | 2.3s | 稳定（1.7~3.0s） |
| firecrawl | 5.7s | 最慢（4.7~6.9s，免费层限速） |

**两两重合度（Jaccard，越低越互补）**：

| 组合 | 均值 | 结论 |
|------|------|------|
| firecrawl vs tinyfish | 0.18 | 高互补 |
| firecrawl vs tavily | 0.34 | 中互补 |
| tinyfish vs tavily | 0.18 | 高互补 |

**各源特征画像**：

| 引擎 | 特征 | 定位 |
|------|------|------|
| tavily | 最快 + snippet 最长（平均 1200+ 字，带正文提取）+ 来源偏权威 | **质量最优，链序前移** |
| tinyfish | 快 + 英文技术 query 深挖官方源（github 源码/官方文档）+ snippet 短（~180 字） | 官方文档向独家补充 |
| firecrawl | 最慢 + snippet 两极分化（146 字简介或 3700+ 字全文）+ 社区源广 | **慢但能抓全文，scrape 模式主力** |

**结论**：三源两两 Jaccard 均值仅 0.18~0.34，合并后单 query 覆盖 11~15 个不同 URL，互补性成立。

### 1.5 实测证据三：云端代抓端点（2026-11-24）

为「fetchpage 云端代抓」设计做端点求证（原为 searchweb scrape 参数求证，§3.4 修订后用途归位 fetchpage）：

| 端点 | 实测结果 | 结论 |
|------|---------|------|
| firecrawl MCP `firecrawl_scrape` | 200，structured `{markdown: 37108字, metadata{title, sourceURL}}` | **scrape 主力**，返回 markdown 全文 |
| tavily REST `POST /extract` | 200，`{results:[{url, raw_content: 34790字}]}` | **scrape 降级源**，同 key 复用 |
| firecrawl 免费层 | 首调偶发 markdown 空（限速），二调正常 | 免费层限速真实存在，**必须有降级链** |

## 二、方案目标

1. **信息价值**：一次搜索并行多家互补结果，URL 去重合并后输出更全的结果集（显著优于单源）。
2. **稳定性**：不引入新故障面；并行失败/限流自动降级，可用性不劣于现有串行链。
3. **配额保护**：任一家触发 429 后自动让位（冷却），绝不硬打限流的后端。
4. **链序优化**：按实测质量/延迟重排降级链（exa 居首、tavily 次位、firecrawl 靠后）——已实施（§3.1）。
5. **抓取能力归位 fetchpage**：云端代抓（firecrawl_scrape / tavily /extract）并入 fetchpage 外部链并前置——已实施（§3.4），searchweb 保持纯搜索职责。
6. **向后兼容**：底层 `run_chain` 串行语义、classify 分类、mark_failure 冷却、attempts 轨迹全部保留，扩展并行合并为**总线新增模式**（OCP，不动现有串行调用方）。

## 三、总体设计决策

### 3.1 决策一：链序调整（按实测质量/延迟重排，已定稿并实施）

**新链序（2026-11-24 定稿）**：

```
exa → tavily → parallel → tinyfish → firecrawl → bing
```

| 位置 | 引擎 | 理由（实测依据） |
|------|------|------|
| exa 首位 | exa | 48 次全稳（§1.3），无 key 依赖、无配额风险，最可靠的首选 |
| tavily 次位 | tavily | 最快（1.6s）+ snippet 最长（1200+字）+ 来源权威（§1.4），有 key 即质量最优 |
| parallel 第三 | parallel | 结构化质量高，但有 429 配额约束（§1.3），不宜占首两位 |
| tinyfish 第四 | tinyfish | 快（2.3s）但 snippet 短，官方文档向补充 |
| firecrawl 第五 | firecrawl | 最慢（5.7s）+ 免费层限速，靠后兜底；主力价值转 scrape 模式 |
| bing 兜底 | bing | 不变 |

> 注：tavily 无 key 时抛 NEED_SETUP 由底座自动跳过（已实现），exa 首位不依赖任何 key 存在。

### 3.2 决策二：并行宽度 = 3 路（前 3 家并行）

**并行组**：`exa + tavily + parallel`（即新链序前 3 家）；**串行尾**：`tinyfish → firecrawl → bing`。

选择 3 路而非 2 路的理由：

| 维度 | 2 路（exa+tavily） | 3 路（exa+tavily+parallel） |
|------|------|------|
| 信息增益 | 两源合并 ~11-15 URL | 三源合并互补面更大，exa 48 次全稳兜住 parallel 429 缺位 |
| 延迟 | ~2s | ~2s（并行取 max，三家典型延迟 2/1.6/2s 几乎同档） |
| 配额风险 | parallel 不在组内，单点风险在 tavily 付费配额 | parallel 429 后仍有 2 家并行，鲁棒性更好 |

不并入 tinyfish/firecrawl 的理由：tinyfish snippet 短（~180 字）增益有限、留作串行首备；firecrawl 平均 5.7s 会拖慢整组（并行耗时=最慢一家）且免费层限速，不宜常驻并行组。

### 3.3 决策三：并行宽度**不作为 LLM 工具参数**

**结论：不进 searchweb 的 schema，固定为代码常量 `SEARCH_PARALLEL_WIDTH = 3`。**

理由：

1. **LLM 不该管基础设施调优**——工具参数应表达意图（query/num_results/scrape），并行宽度是引擎编排内部事，属实现细节；
2. **误用风险**：LLM 传 6 会把限速面（firecrawl）拖进并行组，并行耗时被最慢一家绑架，且配额翻倍烧穿免费层；
3. **YAGNI**：当前无任何场景需要 LLM 动态改变并行数；运营侧若将来要调，走 settings 配置项（如 `tool_websearch_parallel_width`，对齐 Tavily key 的注册模式）即可，不必进工具 schema。

### 3.4 决策四：scrape 不进 searchweb，云端代抓并入 fetchpage 外部链并前置（2026-11-24 修订定稿）

**修订原因**：原设计「searchweb 加 scrape 参数」与现有 fetchpage 工具职责重叠（都是"URL→全文"），违反 SRP/DRY——LLM 要某页全文直接调 fetchpage 即可，无需绕道 searchweb。firecrawl 的正确用法是作为 **fetchpage 的云端代抓源**（fetchpage 本机抓不动反爬站时，云端代抓能过）。

**fetchpage 外部抓取链重排（已实施）**：

```
Firecrawl(firecrawl_scrape, 云端代抓反反爬最强) → Tavily(/extract, 同key复用) → Jina Reader → Exa
```

- fetchpage 的 markdown 路径本就**外部链优先**（成功即返回，不占本机 httpx/Playwright），云端代抓前置后所有 fetchpage 调用默认先走 Firecrawl；
- 新增 `_fetch_via_tavily_extract`（REST /extract，key 复用 `tool_websearch_Tavily_key`），实测 34790 字；
- 每家失败返回 None 链续走，首个达标（≥EXTERNAL_FETCH_MIN_CHARS=200 字符）即用，语义与原链完全同构；
- **searchweb 保持纯搜索职责，不加任何参数**（原 §3.4 scrape 参数设计作废）。

### 4.2 核心函数 `search_parallel_merge`（3 路并行 + 配额保护 + 串行兜底）

> **导入依赖说明**（实施时按 search_web.py 现存别名对齐）：`time` 在文件头已 `import time as _time_mod`, 故下方 `time.monotonic()` 实施时应写 `_time_mod.monotonic()`; `urlparse` 已导入(L47)。`asyncio` 需在 search_web.py 顶部新增 `import asyncio`（当前文件未直接 import asyncio, 实施时补上）。

```python
# search_web.py 新增 — 商量 2026-11-24
# 并行第一段(exa+tavily+parallel, 宽度 SEARCH_PARALLEL_WIDTH=3) + 串行第二段(tinyfish/firecrawl/bing)
# 任一家 429/上游坏/超时 → 冷却让位, 绝不硬打
def _remaining(deadline):
    """剩余预算秒数; deadline 为 None(不限)则返回 None"""
    if deadline is None:
        return None
    return max(0.1, deadline - _time_mod.monotonic())

# 并行组后端名→调用函数映射(与 SEARCH_CHAIN 前 3 家一一对应, 链序变更时同步)
_PARALLEL_GROUP = {
    "exa": lambda q, n, p, t: _search_mcp_engine("exa", q, n, p, t),
    "tavily": _search_tavily,
    "parallel": lambda q, n, p, t: _search_mcp_engine("parallel", q, n, p, t),
}

async def search_parallel_merge(query, num_results, proxy, budget_sec, kind, args):
    deadline = None if budget_sec is None else (_time_mod.monotonic() + budget_sec)

    # ---- 第一段: 前 3 家并行(gather return_exceptions, 一家失败不拖垮另两家) ----
    # 冷却中的家不进并行组(配额保护); (name, task) 二元组保证 gather 结果与后端名一一对应
    pending = []
    for name in ("exa", "tavily", "parallel"):
        if cooldown_info(kind, name)[0] <= 0:
            fn = _PARALLEL_GROUP[name]
            pending.append((name, asyncio.create_task(
                fn(query, num_results, proxy, _remaining(deadline)))))

    items_map, errors = {}, {}
    if pending:
        names = [n for n, _ in pending]
        tasks = [t for _, t in pending]
        results = await asyncio.gather(*tasks, return_exceptions=True)
        for name, res in zip(names, results):
            if isinstance(res, BaseException):
                errors[name] = res          # 异常统一抛给 _mk_parallel_out 分类+冷却
            elif res:
                items_map[name] = res       # 有结果才记; 空结果保持缺省 → 下游按 EMPTY

    # ---- 错误统一分类 + 冷却(与 run_chain 完全同口径, DRY 不与串行分裂) ----
    failures, attempts = _mk_parallel_out(
        name_map=items_map, errors=errors, kind=kind,
        group=("exa", "tavily", "parallel"))

    # ---- 合并: URL 去重, 互补信息拼装 ----
    merged = merge_search_items(
        [items_map.get(n) for n in ("exa", "tavily", "parallel")], num_results)

    # ---- 第二段: 合并已足 → 直接返回; 不足/全败 → 续串行兜底(tinyfish/firecrawl/bing) ----
    if merged and len(merged) >= num_results:
        return {"items": merged, "backend": "+".join(items_map.keys()),
                "attempts": attempts, "failures": failures,
                "error": None, "budget_exhausted": False}

    tail_chain = SEARCH_CHAIN[3:] + (Backend("bing", lambda q, n, p, t: _search_bing(q, n, p, t)),)
    leftover = await run_chain(kind, tail_chain, args, budget_sec=_remaining(deadline))
    final = merge_search_items([merged, leftover.get("items")], num_results)
    merged_out = final or leftover.get("items", [])
    backend_src = leftover.get("backend") or ""
    par_names = "+".join(items_map.keys()) or "parallel-group"
    # attempts 必须显式合并: {**leftover} 会拿串行尾的 attempts 覆盖并行段, 丢前 3 家轨迹 — 商量 2026-11-24
    return {**leftover, "items": merged_out,
            "backend": f"{par_names}+{backend_src}" if backend_src else par_names,
            "attempts": attempts + leftover.get("attempts", []),
            "failures": failures + leftover.get("failures", [])}
```

> **设计说明**：
> - 并行组 `pending` 用 `(name, task)` 二元组，`zip(names, results)` 一一对应，杜绝"某家冷却缺席时管道错位"。
> - 任一家 429 → `mark_failure` 记冷却 → 下次调用该家不进并行组，其余家照常并行（配额保护，不硬打限流后端）。
> - 两段编排：合并已足 → 直接返回（只用前 3 家，最快）；不足 → 续 `run_chain` 串行尾，可用性不退化。
> - `SEARCH_CHAIN[3:]` 与新链序（§3.1）严格对应：前 3 位（exa/tavily/parallel）是并行组，尾 2 位（tinyfish/firecrawl）+ bing 是串行兜底。

### 4.3 错误处理 `_mk_parallel_out`（并行组错误统一分类 + 冷却）

**并行组内错误统一用 gather 后的 `errors` 映射处理——不在 task 内记冷却（DRY，与 run_chain 同口径单点冷却）**：

```python
def _mk_parallel_out(name_map, errors, kind, group):
    """并行组错误统一分类 + 冷却; 返回 (failures, attempts), 与 run_chain 口径一致。
    - name_map: {backend_id: items}, 有结果才在; 冷却被跳过的家(items 缺省)记录为 SKIPPED
    - errors:   {backend_id: BaseException}, gather return_exceptions 捕获的异常
    - group:    并行组成员元组(如 ("tavily", "parallel", "exa")), 驱动遍历而非硬编码
    返回元组与 run_chain 的 attempts/failures 结构保持一致, 前端与排障口径无变化。
    """
    failures, attempts = [], []
    for name in group:
        err = errors.get(name)
        if err is not None:
            net = classify(err)
            mark_failure(kind, name, net)       # 429→3600s/上游坏→120s/超时→60s 冷却(与串行同)
            failures.append({"backend": name, "code": net.code, "message": net.message[:200]})
            attempts.append({"backend": name, "result": net.code,
                             "message": net.message[:200]})
        elif name in name_map:
            attempts.append({"backend": name, "result": "OK",
                             "items": len(name_map[name])})
        else:
            attempts.append({"backend": name,
                             "result": "SKIPPED" if cooldown_info(kind, name)[0] > 0 else "EMPTY"})
    return failures, attempts
```

### 4.4 合并函数 `merge_search_items`（DRY + 去重保序）

```python
# search_web.py 新增 — 商量 2026-11-24
# 多源结果 URL 去重合并: 保首源顺序, 次源新 URL 追加; 归一化去追踪参数, 冗余安全(source 已标注)
def _normalize_search_url(url: str) -> str:
    """URL 归一化键: 去 scheme/www/尾斜杠/#fragment/utm*/gclid 类追踪参数"""
    try:
        p = urlparse(url)
        host = (p.netloc or "").lower()
        if host.startswith("www."):
            host = host[4:]
        path = p.path.rstrip("/") or "/"
        return f"{host}{path}"
    except Exception:
        return (url or "").strip().lower()

def merge_search_items(sources: List[Optional[List[dict]]], num_results: int) -> List[dict]:
    """多源结果合并: URL 去重, 保顺序; 返回至多 num_results 条。
    - sources: 各来源 items 的列表(可为 None/空), 顺序即优先级(首源在前)
    """
    merged, seen = [], set()
    for items in sources:
        for it in items or []:
            if not it or not it.get("url"):
                continue
            key = _normalize_search_url(it["url"])
            if key in seen:
                continue
            seen.add(key)
            merged.append(it)
            if len(merged) >= num_results:
                return merged
    return merged
```

> 每项 result dict 已带 `source` 字段（Tavily/Parallel/Exa/...），合并后用户/下游能分辨来源——**完全不破坏现有 observation_formatter 的 items 分支契约**。

## 六、技术架构稳定性论证

| 稳定性维度 | 保障 |
|-----------|------|
| **并发安全** | 三家独立 httpx client；`_COOLDOWNS` 进程内 dict，单 asyncio 循环无抢占（与现有串行链一致） |
| **异常隔离** | `gather(return_exceptions=True)` 一家失败不拖垮其他家；取消类(CancelledError)穿透（非 Exception 捕获） |
| **配额保护** | 任一家 429 → classify→mark_failure→3600s 冷却→下次自动让位其余家并行；绝不硬打 |
| **兜底不退化** | 合并不足/全败 → 续原 `run_chain` 串行尾(tinyfish/firecrawl/bing)，可用性与现状持平甚至更好 |
| **向后兼容** | 底层 run_chain/classify/冷却/attempts 全保留；串行调用方不受影响（新增并行模式） |
| **可回退** | `SEARCH_PARALLEL_MERGE` 一键切回原串行，故障秒回退 |
| **无新依赖** | 仅用 asyncio 标准库 + 现有网络底座，零新增第三方包 |
| **限流礼貌** | 并行只并发前 3 家（tavily 付费有配额但实测最稳、parallel 429 有冷却保护、exa 无配额实测）；firecrawl 限速面只在串行尾/scrape 模式出场 |

## 八、风险与缓解

| 风险 | 缓解 |
|------|------|
| 每次三打 quota 消耗更快 | tavily 付费有配额但延迟最稳；parallel 429 冷却自动让位；exa 无配额实测；最坏退化为 2 家并行仍优于单源 |
| 结果合并引入重复/乱序 | 归一化去追踪参数 + 保首源顺序 + source 标注；误并不同页面已被尾斜杠/#fragment/track 归一规避 |
| gather 内一家慢拖累 | 各带剩余预算硬超时(与串行同) + 异常隔离，最坏=最慢一家耗时（三家典型 1.6~2s 同档） |
| fetchpage 云端代抓前置消耗 Tavily 付费额度 | Firecrawl 限速时自动落 Tavily /extract；额度告警后可调链序或加开关 |
| 取消/悬挂连接 | httpx async 取消点成熟 + 流式读 SSE 可中断，冒烟验证覆盖 |

## 九、结论

1. **实测已充分证明并行合并价值**：双源互补 97%（Jaccard 平均 0.03），三源两两 Jaccard 均值 0.18~0.34，一次三路合并信息增益显著，串行单源给不了。
2. **链序已按实测重排并实施**：exa 居首（48 次全稳）、tavily 次位（最快+质量最优）、firecrawl 靠后兜底，新链序 `exa→tavily→parallel→tinyfish→firecrawl→bing`，六家 cap 之和=90 与预算对齐。
3. **并行宽度定 3 路**（exa+tavily+parallel），典型延迟 ~2s（取 max），配额保护下任一家 429 自动缩为 2 家，鲁棒性优于 2 路。
4. **并行宽度不作为 LLM 参数**：工具参数表达意图而非基础设施调优；固定常量 `SEARCH_PARALLEL_WIDTH=3`，运营侧将来可走 settings 配置项。
5. **抓取能力归位 fetchpage（已实施）**：firecrawl_scrape / tavily /extract 云端代抓前置进 fetchpage 外部链（Firecrawl→Tavily→Jina→Exa），searchweb 保持纯搜索职责不加参数。
6. **方案切实可行且架构稳定**：复用现有 run_chain/classify/冷却/attempts 全部底座，零新增依赖 + `SEARCH_PARALLEL_MERGE` 一键回退。
7. **推荐实施**：阶段1 已完成；按阶段2→5 渐进落地，每阶段独立可验证，风险可控。
