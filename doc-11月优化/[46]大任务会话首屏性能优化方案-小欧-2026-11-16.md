## 前言

本文档承接《[45]会话任务列表渲染性能优化方案》。实测发现：**任务列表渲染的 React.memo 优化（[45]）在 40/80/100+ 任务会话上并未带来用户可感知的提速**，因为真正的瓶颈不在渲染层，而在"首屏全量拉取超大历史消息"这一数据/网络层。本文档定位根因并给出可落地方案。

## 第 1 章 问题分析

### 1.1 现象

会话任务条数达到 40/80/100+ 后，打开会话页出现长达 **16~23 秒**的白屏——直到任务列表 DOM 出现为止用户什么都看不到。此前 [45] 的 React.memo 优化未能消除此卡顿。

### 1.2 实测证据（真实库 107 任务会话，Playwright + CDP 测量）

| 阶段 | 实测耗时 |
|---|---|
| DOMContentLoaded | ~0.8s |
| **首个任务项渲染** | **17~23s（白屏核心）** |
| ├ 前端主线程 CPU 渲染 | **~1s**（renderWithHooks/formatTime 等合计 <0.5s） |
| └ **主线程 idle 等待（等数据）** | **~16~21s** |

**结论：前端渲染 CPU 只占约 5%，剩余 95% 的时间在等网络数据。**

### 1.3 请求瀑布（白屏期 4 个超 20 秒的在飞请求）

| API | 浏览器内耗时 | 响应体量 |
|---|---|---|
| `GET /sessions/{id}/messages` | **20569ms** | **73.5 MB** |
| `GET /sessions/{id}/tasks` | 21472ms | 278 KB |
| `GET /files/root` | 21797ms | 89 B |
| `GET /files/recent-files` | — | 422 报错 |

### 1.4 根因定位（数据量线性爆炸）

同一 107 任务会话对比：**任务列表 `/tasks` 仅 278 KB**，而消息历史 `/messages` 高达 **73.5 MB**（394 条消息）。

**消息数与数据量线性正相关**：2 条消息 = 0.34MB，394 条 = 73.5MB（每消息约 187KB）。

#### 根因 1：首屏 `getSessionMessages` 全量拉取历史（★★★★★）

前端 `loadHistoryMessages`（`chatHistory.ts:240`）一次拉取**整个会话的全部消息**，每条消息都带完整 `execution_steps`（含 chunk 全文、thought 思考全文）。100+ 任务 = 70MB+，网络传输 + JSON 解析 + 后端拼装全部串行阻塞首屏。

```text
loadHistoryMessages ──await──▶ getSessionMessages ──▶ 后端拼 394 条消息(含每条 execution_steps) ──▶ 73.5MB ──▶ parseMessage ×394 ──▶ setMessages
                                                                                  （后端慢消耗在这里）
```

#### 根因 2：`execution_steps` 全量冗余下发（★★★★）

后端 `get_session_messages`（`message_service.py:186-188`）对每条 assistant 消息都挂载完整 `execution_steps`（含所有 chunk/thought）。首屏消息区编辑器只展示最近几条的正文，**历史消息的完整步骤链对首屏渲染无用**，却占去绝大多数字节。

#### 根因 3：消息列表与任务列表 await 串行（★★★★）

首屏必须先等 `loadHistoryMessages`（await 全量 messages）完成后，`setSessionId`/`setMessages` 才触发，任务列表 `tasks`（仅 278KB、本可秒出）被串行阻塞在 messages 之后。两者本可并行/先出列表。

#### 根因 4：任务列表接口与当前 UI 形态错位（★★★★★，架构层）

**最根本的问题**：`list_session_tasks`（`storage.py:1160`，2026-08-20 建）与 `get_session_messages`（`message_service.py:89`）在设计之初都只是"一张表的读取函数"。此后任务列表 UI 反复演进（引用台账、推荐行、续跑徽标、mergd 注入、链号、回复正文等逐项加入），**但这两个接口函数从未按当前页面 UI 的完整渲染要素对齐重构**，一直是"在老查询上逐次补丁"。

**实测差距**：TaskListPanel 当前每个任务项渲染所需的要素，来源分裂为 3 类：

| 任务列表渲染要素 | 数据源 | 是否在 `list_session_tasks` 返回契约内 |
|---|---|---|
| 时间/模型/状态/轮次/链号/续跑标/merged_inputs | `chat_tasks`(+注入消息表) | ✅ 在后端 SELECT 内 |
| **回复正文 response** | `final.response`（SSE）+ `liveTaskAnswer` 实时兜底 | ⚠️ 字段有，但任务表值被前端"只写 final"铁命令屏蔽，实为前端内存态 |
| **推荐行 recommendNode** | `/files/recent-files` 接口 + `executionSteps`(steps→roundHits) | ❌ **接口内没有**，靠前端另拉 + store |
| **引用台账 ledgerTags** | `chatStreamStore.getSentRefLedger`（纯前端内存态） | ❌ **接口内没有**，且前端内存态后端无持久化 |

**后果**：
- 任务列表接口**只保证渲染 60%** 的要素，其余 40%（推荐行、台账、回复正文）靠前端多路请求 + 内存态 store 拼凑；
- 冷启动/刷新后 `chatStreamStore` 内存态为空 → 台账丢失、推荐行 `roundHits` 无 steps 输入 → **列表"数据没到"连渲染数据都不全**，与 P0 的 messages 全量拉取叠加，雪上加霜；
- 消息接口同理：每条消息塞满 `execution_steps`（当初为"详情能看"设计的全量 payload）却从未按"首屏编辑器只需要正文"裁剪。

**这就是用户指出的架构要害**：接口应**按当前页面 UI 形态定义返回契约**——"获取任务"应同时携带任务列表渲染所需的全部关联要素（任务本体 + 每任务引用台账 + 会话足迹/推荐依据 + 回复正文），消息接口同理；而不是让前端在多张表、多个 store、多个接口间手工拼图。

### 1.5 为什么 [45] 优化"没有起到一点效果"

[45] 优化了 **TaskListPanel 渲染层**（React.memo / useMemo / CollapsibleText）。这些确实是首挂载/切会话重渲时的有效优化，但**前提是 tasks 数据已到达**。实测 100+ 任务会话中：

- 前端渲染 CPU 仅 ~1s（含 tasks 渲染）；
- 真正的 16~20s 全耗在"等 73.5MB messages 返回"。

**[45] 优化了"渲染有多快"，但痛点是"数据有多久才到"。** 数据未到时列表根本无物可渲，故 [45] 的优化对超大会话的游客无感。

### 1.6 瓶颈影响矩阵

| 根因 | 刷新页面 | 切换至大会话 | 复用会话缓存后 | 冷启动(store空) |
|---|---|---|---|---|
| ① 全量拉取 messages | ★★★★★ | ★★★★★ | ★★（命中缓存） | ★★★★★ |
| ② execution_steps 冗余 | ★★★ | ★★★ | ★★ | ★★★ |
| ③ 消息/任务列表串行 | ★★★ | ★★★ | ★ | ★★ |
| ④ 任务接口与 UI 形态错位(关联要素靠多路拼/内存态) | ★★★★ | ★★★ | ★★ | ★★★★★ |

> 根因④在"冷启动/刷新后 store 为空"时影响最大——推荐行无 steps 输入、台账丢失，任务列表即使渲染出来也不完整。

### 2.1 P0：messages 分页（后端 limit/offset + 前端首屏只拉最近 N 条）

#### 2.1.1 设计说明

**核心思路**：后端 `/sessions/{id}/messages` 增加 `limit`/`offset`（或按时间下限）分页，返回**最近 N 条**而非全量；前端首屏只拉最近 50 条渲染，需要更早历史时再增量加载。

同时保留默认行为（不带参数 = 全量）以兼容既有调用方——**仅优化首屏路径**，避免连锁改动。

**为什么按"最近 N 条"**：会话页首屏消息区展示的是最近对话；越旧的 exec_steps/正文用户越不可能立即看，先不拉。滚动/点"加载更早"再补。

**实施要点**：
- 后端返回结构补充 `total`（总消息条数）+ `has_more`（是否还有更早的），供前端判断"是否还有更早可加载"。
- 分页方向：按 `updated_at`/`created_at` 倒序取最近 N 条，再在内存中按正序返回给前端渲染（保持既有正序排列不变）。

```python
def get_session_messages(session_id: str, limit: int | None = None, offset: int = 0):
    """获取会话消息历史(21.3 重构,小沈 2026-05-25 实施) — 自 api/v1/messages.py 迁入

    [46] P0 小欧 2026-11-16: 新增 limit/offset 分页。默认(limit=None)返回全量,
    兼容既有调用方; 首屏传 limit=50 只取最近 50 条, 大幅消减超大会话首屏数据量。
    """
    from fastapi import HTTPException
    with db.get_conn("chat") as conn:
        cursor = conn.cursor()

        cursor.execute('''SELECT id, title, created_at, updated_at,
                          COALESCE(title_locked, 0) as title_locked,
                          COALESCE(title_updated_at, created_at) as title_updated_at,
                           COALESCE(version, 1) as version, COALESCE(is_valid, 1) as is_valid,
                          sessionModel,
                          COALESCE(link_enabled, 0) as link_enabled,
                          COALESCE(allow_interject, 0) as allow_interject
                       FROM chat_sessions WHERE id = ? AND is_deleted = FALSE''', (session_id,))
        session = cursor.fetchone()
        if not session:
            raise HTTPException(status_code=404, detail=f"会话不存在: {session_id}")

        # 北京老陈 2026-08-22 铁律: chat_messages 只写严禁读
        pairs = fetch_session_user_message_pairs(conn, session_id)

        # —— [46] P0 分页: 取总条数 & 截取"最近 limit 条" ——
        total = len(pairs)
        if limit is not None and limit > 0:
            # 取全量倒序的前 limit 条(最近), 再反转为正序返回(保持渲染正序)
            window = pairs[max(0, total - limit - offset):total - offset]
        else:
            window = pairs   # 全量(默认, 兼容旧调用方)
        has_more = bool(limit and (offset + (len(window) if window else 0)) < total)

        # ---- 后续用 window(而非 pairs)构建 messages, 其余逻辑与原本一致 ----
        _first_row: dict = {}
        _carrier: dict = {}
        for _i, _p in enumerate(window):
            _aid = _p.get("ai_message_id")
            if _aid is None:
                continue
            _first_row.setdefault(_aid, _i)
            if (_p.get("ai_content") or "") and _aid not in _carrier:
                _carrier[_aid] = _i
        for _aid, _i in _first_row.items():
            _carrier.setdefault(_aid, _i)

        _batch_keys = [
            (_aid, window[_i].get("pair_task_id"))
            for _aid, _i in _carrier.items()
        ]
        _steps_cache = load_execution_steps_batch(conn, _batch_keys)

        messages = []
        for _i, p in enumerate(window):
            # 用户消息气泡
            messages.append(MessageResponse(
                id=p['user_id'], session_id=session_id,
                role="user", content=p['user_content'] or "",
                timestamp=format_timestamp(p['created_at']),
                execution_steps=[], display_name=None, thought=None,
                task_id=p.get('pair_task_id'),
                msg_kind=p.get('msg_kind'),
            ))
            ai_id = p['ai_message_id']
            if ai_id is None or _carrier.get(ai_id) != _i:
                continue
            _s_key = (ai_id, p.get('pair_task_id'))
            steps = _steps_cache.get(_s_key, [])
            display_name = build_display_name(p['provider'], p['model']) if p['provider'] or p['model'] else None
            if not display_name and steps:
                display_name = extract_display_name_from_steps(steps)
            thought = None
            if steps:
                for s in steps:
                    if isinstance(s, dict) and s.get("type") == "thought":
                        thought = s.get("thought") or s.get("reasoning")
                        if thought:
                            break
            messages.append(MessageResponse(
                id=ai_id, session_id=session_id,
                role="assistant", content=p['ai_content'] or "",
                timestamp=format_timestamp(p['created_at']),
                execution_steps=steps, display_name=display_name,
                thought=thought, task_id=p.get('pair_task_id'),
                msg_kind=None,
            ))

        title_locked = bool(session['title_locked'])
        return {
            "session_id": session_id, "title": session['title'],
            "created_at": format_timestamp(session['created_at']),
            "updated_at": format_timestamp(session['updated_at']),
            "title_locked": title_locked,
            "title_source": "user" if title_locked else "auto",
            "title_updated_at": to_local_iso(session['title_updated_at']),
            "version": session['version'], "is_valid": session['is_valid'],
            "sessionModel": parse_session_model(session['sessionModel']),
            "link_enabled": bool(session['link_enabled']),
            "allow_interject": bool(session['allow_interject']),
            # [46] P0: 补 total / has_more 供前端判断"是否还有更早可加载"
            "total": total,
            "has_more": has_more,
            "messages": messages,
        }
```

### 2.2 P1：execution_steps 首屏裁剪（进详情再按需拉）

#### 2.2.1 设计说明

**核心思路**：首屏消息列表里每条 assistant 消息**不随消息下挂完整 `execution_steps`**（含 chunk/thought 全文）。只在用户展开某条消息详情/右栏时，通过既有详情接口 `getTaskDetail` 或轻量步骤接口按需拉取。

**为什么安全**：
- 首屏消息区（气泡列表）本就不展示每条的完整执行步骤链，只展示正文；
- `thought` 已由后端单独摘出下发的字段（`message_service.py:174-180`），首屏思考区消费的就是这个已收窄的 `thought`，不依赖完整 steps；
- 右栏 `RightViewer`/任务详情走的是 `getTaskDetail`，与 messages 的步骤是两条独立链路，不受影响。

**实施要点**：P1 与 P0 结合——分页后每条消息的 `execution_steps` 默认置空 `[]`，仅当 `detail=1`（或单独参数）时才挂载完整 steps。这样首屏消息体更小。

### 2.3 P2：任务列表接口按当前 UI 形态对齐 + 任务/消息解耦

> 本步骤是整份方案的**架构核心**（根因④）。它同时解决两件事：① 把 `list_session_tasks` 的数据契约一次性对齐当前任务列表 UI 的完整渲染要素（不再是"一张表的读函数补丁"）；② 与 messages 解耦，首屏先渲 tasks。

#### 2.3.1 设计说明

**第一层：解耦（承接原 P2 思路）**

任务列表（`/tasks` 仅 278KB）与消息历史（messages 73MB）**解除 await 串行**。首屏立刻渲染左栏任务列表（秒出），消息区独立异步加载、就绪后再填充。

- 现状：`useChatSession` 的 `loadHistoryMessages`（await 全量 messages）完成后才 `setSessionId`/`setMessages`；`useSessionTasks.refresh` 依赖 `sessionId` 变化才拉 tasks → **tasks 被 messages 串行拖慢**。
- 解耦：会话 ID 在进入页最早时刻确定（URL 带 session_id 或轻量 `listSessions`），使 `refresh` 立即拉 tasks；messages 并行异步。

**第二层：数据契约对齐当前 UI（本步骤新增、最关键）**

`list_session_tasks` 目前只返回 `chat_tasks` 表字段 + `merged_inputs`，但当前 TaskListPanel 一个任务项的完整渲染需要 4 类数据（见 1.4 根因④表格）。本次让**任务接口一次返回全部关联渲染要素**，消除前端多路拼凑与冷启动内存态缺失：

| 渲染要素 | 现来源 | 改造后任务接口返回 |
|---|---|---|
| 任务本体+merged_inputs | `list_session_tasks` SELECT | ✅ 保持 |
| **引用台账（sentRefLedger）** | `chatStreamStore` 前端内存态（后端无持久化） | ✅ **后端读取各任务的引用台账一并返回**（需后端起持久化或从任务消息/事件恢复） |
| **推荐行依据**：recent-files 命中 + 每任务被工具触达的路径 | `/files/recent-files` + `executionSteps`(store) | ✅ **后端返回每任务涉及的工具路径（roundHits 前身）**，供前端算推荐行，不再依赖 store 的 executionSteps |
| **会话足迹 recent-files** | `/files/recent-files` 独立接口 | ✅ 任务接口附会话级 `recent_files`（或保持独立接口并行拉，二选一，见 2.3.1.1 决策） |
| 回复正文 response | `final.response`/store | ⚠️ 见下方"response 铁命令说明" |

#### 2.3.1.1 决策：任务接口数据契约形态

**方案 A（推荐·复合契约）**：`GET /sessions/{id}/tasks` 返回体补齐渲染要素——每任务附 `ledger`（引用台账）、`tool_paths`（该任务引用的工具操作路径→roundHits 前身），会话级附 `recent_files`。一次请求拿到渲染任务列表的**全部数据**，前端零拼凑、冷启动不缺失。

**方案 B（保持拆分·并行拉）**：任务本体仍走 `/tasks`，推荐行/台账仍走 `/files/recent-files` + store。改动最小，但**根因④不根治**——前端仍需多路拼 + store 内存态，冷启动推荐/台账照旧缺失。

> **本方案取方案 A**。理由：根因④的本意就是把"接口不再按当前 UI 形态对齐"这层架构债一次还清。"获取任务"就应同时获得"任务列表渲染所需的全部信息"，这才符合 KISS-DIRECT（单一接口、单一数据源、前端不拼图）。

#### 2.3.1.2 response 铁命令说明（关键约束）

左侧回复区铁命令为"**只由 `updateTaskResponse(final.response)` 写入**，DB 的 `chat_tasks.response`（chunk 累积）不显示"。因此：
- 任务接口仍**返回** `response` 字段（保持契约），但前端 `refresh` 沿用既有 `finalResponsesRef.current.get(task_id)` + `liveTaskAnswer` 实时兜底逻辑——**不受本方案影响**；
- 本次不触碰 response 的写入铁命令，只解决"渲染需要的其他 3 类要素的获取"，避免引入"任务表 response 当正文显示"的回归。

在现有 SELECT 基础上，增加每任务的引用台账与工具触达路径读取（不引入 N+1，用会话级一次查询 + 内存分组）：

```python
def list_session_tasks(conn: Connection, session_id: str) -> Tuple[list, int, Optional[str]]:
    """B1/问题6(10.5): 会话任务列表 + 总数 + 最新任务id。
    [46] P2 小欧 2026-11-16: 数据契约对齐当前 UI —— 每个任务补 ledger(引用台账)/tool_paths(工具触达路径),
      使前端渲染任务列表(推荐行/台账/正文)只依赖本接口, 不再多路拼+内存态store冷启动缺失(根因④)。
    """
    total = conn.execute(
        "SELECT COUNT(*) FROM chat_tasks WHERE session_id=?",
        (session_id,),
    ).fetchone()[0]
    rows = conn.execute(
        """SELECT task_id, user_input, response, status, duration, sessionModel,
                  total_steps, llm_call_count, context_link_mode, context_root_task_id, user_message_id,
                  creation_source, created_at, updated_at
           FROM chat_tasks WHERE session_id=? ORDER BY id ASC""",
        (session_id,),
    ).fetchall()
    # ── 会话级一次取回按任务分组(替代前端多路/内存态) ──
    # ① 注入消息(原逻辑不变)
    _inj_by_task: Dict[str, list] = {}
    for _m in conn.execute(
            """SELECT id, task_id, content, msg_kind FROM chat_user_message
               WHERE session_id=? AND task_id IS NOT NULL ORDER BY id ASC""",
            (session_id,)).fetchall():
        _inj_by_task.setdefault(_m["task_id"], []).append(_m)
    # ② [46] P2 引用台账: 每任务涉及的文件引用(驱动“↩本轮引用”行)
    _ledger_by_task: Dict[str, list] = load_task_ledger_by_session(conn, session_id)
    # ③ [46] P2 工具触达路径: 每任务工具操作涉及的文件路径(驱动推荐行 roundHits)
    _tool_paths_by_task: Dict[str, list] = load_task_tool_paths_by_session(conn, session_id)

    out = []
    _seen_task_ids = set()
    for r in rows:
        d = dict(r)
        if d["task_id"] in _seen_task_ids:
            continue
        _seen_task_ids.add(d["task_id"])
        _sm = parse_session_model(d.pop("sessionModel", None))
        d["model"] = _sm.model if _sm else None
        d["provider"] = _sm.provider if _sm else None
        _reg_uid = d.pop("user_message_id", None)
        d["merged_inputs"] = [
            {"content": _m["content"], "msg_kind": _m["msg_kind"]}
            for _m in _inj_by_task.get(d["task_id"], [])
            if _m["id"] != _reg_uid
        ]
        # [46] P2: 补齐渲染关联要素
        d["ledger"] = _ledger_by_task.get(d["task_id"], [])      # 引用台账
        d["tool_paths"] = _tool_paths_by_task.get(d["task_id"], [])  # 推荐行依据
        out.append(d)
    latest_task_id = out[-1]["task_id"] if out else None
    return out, total, latest_task_id
```

#### 2.3.3 补充：引用台账/工具路径的持久化（后端地基）

### 3.3 不做项登记

|---|---|
