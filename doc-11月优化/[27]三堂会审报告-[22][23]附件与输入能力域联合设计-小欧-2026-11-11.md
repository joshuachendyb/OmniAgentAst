## 3. 合理检查 — 阻断级缺口（必须先改文档，P0 不得开工）

### A1【阻断】sanitize 的 no_path 丢弃会误杀 url 条目 — [22] 扩展点 0 不完整

- **事实**：`browse_service.sanitize_refs` 现状两道闸：①kind 白名单；②"无 path 一律丢弃"（A15，`browse_service.py:757` 起 path 必填，附件已豁免按 attachment_id 放行）。url 条目**没有 path 字段**。
- **后果**：[22] 扩展点 0 只写"白名单 REF_KINDS 增 url"，漏改 no_path 分支 → url 条目进 sanitize 即被丢弃（reason=no_path），URL 一等引用在入口就死，[23] 阶段 A 全部验收项不可能通过。
- **整改**：扩展点 0 补一句——sanitize 按 source_kind 分字段校验：url 条目按 `url` 字段必填校验（复用 `url_reject_reason` 语法级准入），不参与 path 越界校验（与附件豁免同款）；`REF_KINDS` 增 `url` 同步改 `render.py` 白名单（已同源，自动生效）。

### A2【阻断】插话路径的原生化未定义 — [22] §5.7/5.8 只覆盖首发

- **事实**：现状插话分支（`stream_orchestrator.py:630-689`）走 `prepare_refs → build_interject_text → build_user_turn_text`，**不经 react_loop**，故 `split_vision_refs` 从不作用于插话——现状插话带图片附件走文本档案卡（不原生），这是既有行为。
- **后果**：[22] §5.7 删除 `supports_image_input` 分支、§5.8 `build_user_turn_text(plans=...)` 后，插话侧的 plans 由谁算、用哪个模型的 profile，两文档均未定义。若插话不补 plans，插话 URL/图片永远降级（与首发不一致，违反"同一输入同一命运"）；若补，需在编排层用**目标任务 agent** 的 `_task_llm_model` 算 profile（插话时目标任务运行中，模型已定）。
- **整改**：[22] §5.7 补"插话装配点"：编排层插话分支在 `build_interject_text` 前调 `plan_refs(items, profile(_tgt_agent._task_llm_model))`，plans 经形参传入（与首发同一实现）；[23] §3.3 数据流图补插话支路；守门测试补"首发与插话同一输入产生相同 ItemPlan.state"。

### A3【阻断】wire 展开期依赖 ItemPlan 与"history 恒 str + 自描述占位"不变量冲突

- **事实**：现状占位是**自描述**的（`[[IMAGE_ATTACHMENT:<id>]]`，expand 时按 id 查附件表，不依赖任何请求期对象），因此多轮任务、模型切换、重连恢复后展开永远可用。[22] §5.4 却要求"`expand_attachment_slots` 只消费 `ItemPlan`（识别与能力判定均已完成）"。
- **后果**：ItemPlan 是请求期内存对象，不随 history 持久化。多轮后 plans 若丢失（agent 回收/异常路径），展开断链——占位原样进 prompt，比现状（自描述、永远可展开）是**功能退化**，违反关联检查"必须增强且进化功能，严禁退化"。
- **整改**：定案为**装配期/展开期职责分离**：plans 只在装配期决定"写占位还是写文本块"；展开期占位自描述解析（ATTACHMENT 按 id 查表、URL_ITEM 按 b64url 自解），transport/能力由 `capability.profile` 在展开期**重算**（纯函数，与发送前同源），失败降级文字——与现状 `expand_vision_parts` 每轮按当前 llm_model 门控的安全语义完全同构。删除 §5.4"只消费 ItemPlan"表述，改"展开期零请求期状态依赖"。
