# [29] 附件与引用概念辨析（源码核实）

- 编写: 小欧 2026-11-12
- 目的: 澄清「附件」与「引用（文件引用）」的区别、共同点、保存方式与相互转化关系
- 依据源码（三思三省逐条核实）:
  - `backend/app/attachments/attachment_service.py` — 附件唯一写盘点
  - `backend/app/attachments/collect.py` — 产物「存为附件」唯一入口
  - `backend/app/services/refs/resolver.py` — 引用读正文唯一 IO 点
  - `backend/app/attachments/contract.py` — source_kind 六来源契约

---

## 1. 一句话结论

- **附件 = 文件实体**：上传时把文件**复制**进 `{会话默认工作区}/attachments/` 目录落盘，并在 DB `attachments` 表登记一行（attachment_id、stored_path、sha256 等）。
- **引用 = 指针，不是实体**：只在消息里存一条 ref 记录（路径/区间/URL），**不复制任何文件**；发送时由 resolver 按路径**现场读盘**取正文。
- 二者是并列的三条入口中的两条（file / attachment / url），不是包含关系。

## 2. 逐项对照

| 维度 | 附件 attachment | 文件引用 file | 链接引用 url |
|---|---|---|---|
| 本质 | 文件实体（复制落盘） | 路径指针 | URL 指针 |
| 落盘 | 落盘到 attachments/ 目录 + DB 登记 | 不落盘不登记，只随消息存 ref | 不落盘，只随消息存 ref |
| 内容获取 | 按 attachment_id 查表 → stored_path 读 | 按 path 现场读盘（支持行区间） | fetch=optional，多数只取链接文本 |
| 去重键 | att:{attachment_id} | file:{归一化路径} | url:{归一化 URL} |
| 失效风险 | 文件被删 → available=false（DB 行还在） | 文件移动/删除 → 读时 missing | 链接失效/拒收 → err 回执 |
| 大小限制 | 单文件 20MB、单会话 200MB | 无复制，受读取预算闸门 | 远程图片 ≤4 张 |

## 3. 保存方式（回答"这个又保存吗"）

- **附件保存两份**：磁盘文件（attachments/ 目录）+ DB 登记行（含 sha256、抽取状态等 13 列）。
- **引用只保存指针**：refs 随消息上行，随消息一起持久化（stream_orchestrator 里 `"refs": _final_refs` 随消息落库）。**不复制文件内容**——这正是它与附件的根本区别。
- 推论：引用的文件如果后来被移动/删除，历史消息里的引用会**读不到**（missing 回执）；附件则不受源文件变动影响（已固化副本）。

## 4. 相互转化关系（回答"引用会转化为附件吗"）

存在一个明确的转化入口，方向是**产物 → 附件**（`collect.py` 唯一入口），分两种结果：

1. **referenced（不复制）**：产物已在会话工作区内 → 不复制，直接返回引用路径，前端走 quoteFile 变成文件引用。**此时不产生附件**。
2. **copied（复制固化）**：产物在工作区外 → 读字节复制进 `{默认工作区}/attachments/` 并调 `save_bytes` 登记 DB，**变成真附件**（可带 source_task_id 溯源）。

即：**"存为附件"这个动作，工作区内的东西保持为引用，工作区外的东西被复制固化为附件**。反过来，附件也可以生成引用——`rel_to_root` 把附件的 stored_path 转成项目根相对路径上行 refs（附件行 available=false 后引用会失效）。

## 5. 为什么设计成两套（设计逻辑）

- 附件解决**持久与固化**：上传的东西要跨消息、跨时间稳定可用，且要能收藏（scope=global）、统计用量（use_count）、去重（sha256）。
- 引用解决**轻量与实时**：工作区文件本来就在，复制一份既浪费又产生双真源；现场读还能支持行区间、拿到最新内容。
- 契约层面两者统一：`contract.py` 的 `classify_ref` 把六来源（file/selection/attachment/url/log/message）归一到同一张 KIND_CONTRACT 表处理，下游（状态判定/能力矩阵/注入）对二者无感知差异——**入口不同，出口同流**。

## 6. 给页面的启示

能力矩阵把 file 与 attachment 列为两列是正确的（来源不同、失效语义不同），但对用户而言"文件引用 vs 附件"的差异（指针 vs 实体）正是看不懂的根源之一——可在 4.3 的行列简注里各加半句话：
- 文件引用 = 只记路径，不复制文件，发送时现场读取（文件挪走就读不到）
- 附件 = 上传时复制一份存进附件目录，稳定不受源文件影响
