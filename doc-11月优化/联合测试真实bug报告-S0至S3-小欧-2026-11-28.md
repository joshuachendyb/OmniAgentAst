## 二、发现的 5 个真实缺陷

### 2.1 BUG-1：配置可指定 `track_task=True`，子 Agent 建台账、落 `sub-` 幽灵行

- **case**：J03 `test_J03_track_true_creates_ghost_ledger`
- **现象**：`AgentConfig(track_task=True)` 直接注册后委托，子 Agent 的 `_task_tracker` 非 None（实测为 `TaskTracker` 实例）。
- **根因**：S1 `AgentConfig.track_task` 允许 `True`（S1 探针 T01 只校验默认值 `False`，未禁止显式 `True`）；S3 `run_delegate` 把 `config.track_task` 原样透传 `UniversalAgent(track_task=...)`；S0 改造后的 `BaseAgent.__init__`（`base_agent.py:102`）见 `track_task=True` 即 `tracker.create_task(task_id=self.task_id, ...)`，于是为 `sub-{父}-{id}-{hex}` 建行。
- **影响**：违反"子 Agent 不落 `tasks` 台账"安全承诺；manifest 路径已强制 `track_task=False`，但直接 `register()` 的配置可绕过，产生幽灵任务行并可能覆盖/污染父任务状态。
- **修复建议**：S3 运行器建子 Agent 时**硬编码 `track_task=False`**（子过程语义不交给配置），或在 `AgentConfig` 构造期禁止 `track_task=True`；二选一，切勿两者都留口子。

### 2.2 BUG-2：ToolLoader 用注册名比对、get_tool 用归一名执行，口径分裂

- **case**：J11 `test_J11_alias_named_tool_bypasses_deny`
- **现象**：临时注册别名形态工具名后，它出现在子 Agent `_tools_dict` 与可见工具列表，绕过 `DELEGATE_DENY_TOOLS`。
- **归因更正（v1.1）**：初版写"`s3j_write_file` 归一后执行 `write`"属误述——实测该名不在别名表、`normalize_tool_name` 原样返回，`get_tool` 也按注册名精确命中。真问题是**口径分裂**：`ToolLoader.init_tools`/`load_category` 用注册名原样比对 `excluded_tools`（`tool_loader.py:58`/`:82`），而 `get_tool()` 对真实别名（如 `writefile`→`write`，实测归一成立）走归一名。若某工具以真实别名形态注册，装载比对用别名、执行归一到受限名，两层不一致。
- **影响**：别名形态注册名可绕过只读约束，且"可见性比对名"与"实际执行名"分裂时行为不可预测。
- **修复建议**：`ToolLoader` 装载/动态注入两处的比对键统一改用 `normalize_tool_name(name)`，与 `get_tool` 执行口径同源。

### 2.3 BUG-3：拒绝清单是名单制，新写工具未进 `PATH_*` 表即默认放行

- **case**：J12 `test_J12_new_write_tool_fail_open`
- **现象**：临时注册 `s3j_dangerous_write`（FUNDAMENTAL 类，不在任何 `DELEGATE_DENY_TOOLS`/`PATH_*` 表），委托后混入子 Agent 工具集，委托仍 `success`。
- **根因**：`DELEGATE_DENY_TOOLS = set(WRITE_PATH_TOOLS) | set(DELETE_PATH_TOOLS) | set(DUAL_PATH_TOOLS) | {...}`（`agent_config.py:30`）是**名单制**；设计文档 §1.4 承认"新工具自动兜底"是过高估计，`_find_unattended_blocker` 兜不住未声明确认的写类工具。本实测证实：新增 FUNDAMENTAL 写工具默认放行。
- **影响**：与"子 Agent 只读"承诺直接冲突；新增写类工具必须手工维护名单，漏一处即静默破口，且不会让测试变红、日志无告警。
- **修复建议**：对子 Agent 采用**能力白名单**（仅放行已审计的只读分类/工具，`AGENT`/`SYSTEM`/`MEDIA` 等已拒），或在新工具注册时强制校验"是否可写"元数据并默认拒绝；不能继续依赖名单制 fail-open。

### 2.4 BUG-4：`_build_sub_task` 只截 context 值与键数，不截键名，单行仍可塞超长文本

- **case**：J13 `test_J13_oversized_context_key_bounded`
- **现象**：传入 3000 字符的 context 键名，子任务描述中该行长度达 3005（值已按要求截到 200，键名未截）。
- **根因**：`_build_sub_task`（`delegateagent_runner.py:887` 起）只对值做 `len(_v)>200` 截断、对 `items[:20]` 限键数，`f"- {k}: {_v}"` 的 `k` 原样拼接。
- **影响**："长度有界"承诺不完整；超长键名可把子任务提示塞满，放大 token 消耗、挤占 `max_steps` 预算，且与 S2 Schema 的 task 上限 500 不一致。
- **修复建议**：键名也做长度上限（如 100 字符）并留截断 warning，与值/键数口径一致。

### 2.5 BUG-5：`available=False`（缺依赖）工具误触发确认兜底，导致委托被误拒

- **case**：J14 `test_J14_unavailable_tool_misblocks`
- **现象**：临时注册带 `confirm_fn` 的工具并置 `meta.available=False`（对 LLM 不可见），委托返回 error（被 `_find_unattended_blocker` 拒绝）。
- **根因**：`_find_unattended_blocker`（`delegateagent_runner.py:718` 起）遍历 `sub_agent._tools_dict` 全部 key，只看 `meta.category is AGENT or meta.needs_confirmation or meta.confirm_fn is not None`，**未检查 `meta.visible_to_llm`**；S0 改造后 `ToolMetadata.visible_to_llm = expose_to_llm and available`（`tool_types.py:121`），不可用工具本不进 LLM 工具列表，不应触发拒绝。
- **影响**：缺依赖工具（系统本就允许其注册并提示"不可用"）会误拒整个委托，属 fail-closed 过度；任何带 `confirm_fn` 的缺依赖工具都能让委托永远失败且原因难查。
- **修复建议**：`_find_unattended_blocker` 跳过 `not meta.visible_to_llm` 的工具，只检查对 LLM 实际可见者。

## 五、结论

- S0–S3 已实施代码的**主体链路正确**：14 条联合真实场景 case 中 9 条通过，覆盖工具→运行器全链路、6 路并发隔离、manifest 提权扣减、递归 fail-closed、超时、取消、SSE/台账/授权隔离、client 复用与输入主干截断。
- 发现 **5 个真实产品缺陷**（BUG-1 ~ BUG-5），均为名单制/配置口子/输入有界性/可见性判定类边界问题，其中 BUG-1/2/3 直接冲击"子 Agent 只读 + 不落台账"安全承诺，优先级最高。
- 探针按仓库铁律本地留存、不提交；5 个缺陷的修复不在本次"S3 实施"范围内，需另行排期与回归。

### 6.2 真伪复核结论

- 5 条 FAIL 的**失败信号全部为真**，整改后全部转绿；无一条靠放宽断言"修绿"。
