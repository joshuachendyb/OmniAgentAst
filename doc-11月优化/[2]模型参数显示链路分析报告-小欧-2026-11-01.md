## 二、问题 1：上下文窗口两个键名（本轮修）

**状态**：本轮修｜**严重度**：高｜**性质**：键名分裂，是后两个问题的病根

### 2.1 现象

同一个业务概念"上下文窗口"，在系统里有两个键名、两个存储块、两条写链：

```
模型 Tab  → ai.{provider}.model_params.{model}.context_limit     ← 我方自造名，运行时生效
模型库    → ai.{provider}.model_meta.{model}.context_length      ← 厂商通用名，运行时无人读
```

加一层全局配置 `llm.context_limit_default`、一层 Python 属性 `llm_service.context_limit`、一层前端预设 `context_limit`，一共 4 处用旧名。

### 2.2 根因

`context_limit` 是 2026-07-09 引入时的自造名（当时的定位是"运行时生效窗口"）；`model_meta` 块 2026-09-20 才诞生，2026-10-05 落 `context_length` 时按"保留厂商原生键名"原则写，于是两个键并存，且**从来没有一条读取链把两者串起来**。

### 2.3 证据

**（1）git 时间线**

| 时间 | 提交 | 当时的决策 | 留下的东西 |
|------|------|------------|------------|
| 2026-07-09 | `fda14daeb` | 引入 `model_params.context_limit` 作为"运行时窗口"，从参数里 pop 出来喂裁剪算法 | 自造键 `context_limit` |
| 2026-09-20 | `9038632b2` | 新建 `model_meta`，初始只有 `label` / `range` / `capabilities`，**纯 UI 元数据，与运行时零关系** | 一个"模型附加信息"口袋 |
| 2026-10-05 | `fbbabf60e` | 按"勾选即持久化、离线可见"需求，把厂商的 `context_length` / 模态落进 `model_meta`，保留厂商原名 | `model_meta.context_length`（只展示、无消费者） |
| 2026-10-26 | `bf5c8d3b7` | 给 `max_output_length` **同时**加了持久化和运行时消费者，但没顺手给 ctx 加 | 静态块里出现"一个生效、一个不生效" |

三次提交单看都合理（07-09 时 `model_meta` 还不存在；10-05 需求只要求"存下来能看"；10-26 去改 ctx 属越界）。**没有任何一次提交对"模型属性 → 运行时参数"这条全局一致性负责**，债是这么来的。

**（2）本机配置实证**（`F:\OmniAgentAs-01\config\config.yaml`）

```yaml
      # agnes（34、44 行）
        range:
          context_limit: {min: 1000, max: 2000000}
    model_params:
      agnes-image-2.1-flash:
        context_limit: 262144

      # sensenova（58、61、64、114、124、172 行）
      deepseek-v4-flash:   {reasoning_effort: medium, context_limit: 900000}
      glm-5.2:             {reasoning_effort: medium, context_limit: 900000}
      sensenova-6.8-flash-lite: {reasoning_effort: low, context_limit: 243736}

      # kilo（576-688 行）：只有 models + model_meta，没有 model_params 块
    model_meta:
      kilo-auto/free: {context_length: 256000, max_output_length: 32768}
```

同一份配置里两个键同时存在，是分裂的直接物证。

### 2.4 为什么当初名字不一样（不是随手起的）

| 维度 | `context_length` | `context_limit` |
|------|------------------|-----------------|
| 命名来源 | 上游厂商 API 原生字段（OpenRouter / kilo 就叫这个） | 我方自造，与 `llm.context_limit_default` 同族 |
| 语义 | 厂商**声明**的上限（事实） | 我方**生效**的窗口（决策） |
| 消费者 | 无 | 裁剪 / 压缩 / usage 帧 |
| 允许不相等 | 是（用户可主动调小省钱） | 是 |

两个语义确实不同，**但名字不该不同**——语义区分靠"存储块 + 优先级"表达，靠两个近义词表达只会让人漏改。

### 2.5 修法：全深度统一为 `context_length`

方向：`context_length` 是厂商通用名，且解析层 `_KEY_ALIASES` 的 canonical 本来就是它，统一到它。

| 层 | 改动 |
|----|------|
| 常量 | `DEFAULT_CONTEXT_LIMIT` → `DEFAULT_CONTEXT_LENGTH` |
| 设置项 | `llm.context_limit_default` → `llm.context_length_default` |
| 配置键 | `model_params.{model}.context_limit`、`model_meta.{model}.range.context_limit` → `context_length` |
| 运行时属性 | `BaseAIService.context_limit`、snapshot 参数、`llm_service.context_limit` → `context_length` |
| 函数形参 | `refs/limits.py`、`compaction/assembler.py`、`compaction/trigger.py` 的 `context_limit` → `context_length` |
| 前端 | `PARAM_DEFAULT_RANGES` / `PARAM_PRESETS` / `SettingsGroup` 分组键 / 注释 → `context_length` |
| 旧配置迁移 | **直接改写 `config.yaml` 与 `config.yaml.example`，不留兼容分支**（项目铁律：禁止 backward） |

**必须同时做到的一条（否则直接 400）**：`parse_model_params` 必须把 `context_length` 从 `model_params` 里 `pop` 出来。改名后若漏 pop，这个键会随 `extra_body_params` 进请求体，多数厂商不认。
**同样必须同步的一条**：`model_meta.range.context_limit` 不改名，参数区滑块会找不到范围，退化成纯数字框（2026-09-25 已踩过一次）。

### 2.6 验证

- 全仓 `grep context_limit` 只剩历史注释（编辑历史里的旧记录），代码与配置零残留。
- 参数区 `context_length` 滑块正常出范围（证明 `range` 改名同步）。
- 发一次真实请求，请求体不含 `context_length`（证明 pop 生效）。

## 三、问题 2：模型库保存的窗口运行时不生效（本轮修）

**状态**：本轮修｜**严重度**：高｜**性质**：缺读取链，存了从不用

### 3.1 现象

模型库把厂商声明的 `context_length` 准确算出来、写进配置，但运行时**完全不读它**：

```python
# lifecycle/service.py::parse_model_params（改前）
context_limit = specific_params.pop(
    "context_limit",
    get_config().get("llm.context_limit_default", DEFAULT_CONTEXT_LIMIT),  # 262144
)
```

优先级只有两层：`model_params.context_limit` → 全局默认 262144。`model_meta.context_length` 不在链上。

### 3.2 根因

`model_meta` 从诞生起定位就是"纯 UI 元数据"，2026-10-26 只给 `max_output_length` 单独加了消费者（`_resolve_max_tokens`），没有对 `context_length` 做同样处理。**没人负责"声明值 → 生效值"这一步换算。**

### 3.3 证据（用 kilo 实测值推演）

| 模型 | 厂商声明 ctx | 运行时实际窗口 | 差异后果 |
|------|-------------|---------------|----------|
| `reflection/beam-free` | 1,048,576 | 262,144 | 浪费约 4 倍可用窗口，长会话过早裁剪/压缩 |
| `nvidia/nemotron-3.5-super-vl:free` | 1,000,000 | 262,144 | 同上 |
| `cohere/north-mini-code:free` | 256,000 | 262,144 | 轻微超限 |
| `openrouter/free` | 200,000 | 262,144 | **超出模型上限**，长 prompt 可能被上游 400 |

也就是说：模型库把窗口算得再准，只要不进 `model_params`，运行时一字不用。

### 3.4 修法：补一层"厂商声明"兜底

`parse_model_params` 取值顺序改为四层，其余逻辑不动：

```
model_params.context_length（用户显式）
  > model_meta.context_length（厂商声明）
  > llm.context_length_default（全局默认）
  > DEFAULT_CONTEXT_LENGTH（常量兜底 262144）
```

只改这一个函数即双链同源——`create_service_instance`（全局默认模型）和 `stream_orchestrator`（L2 跨 provider 快照）都调它。

**为什么不用"把声明值写进 model_params"**（这是被否掉的思路，理由在问题 3 的 4.5）：

### 3.5 验证

- `reflection/beam-free` 长上下文会话，日志/`usage` 帧窗口值为 1,048,576 量级；
- `openrouter/free` 为 200,000 量级（此前 262,144 已超限）；
- 用户在②参数区显式设了 `context_length` 时，以用户值为准（不被声明值盖掉）。

## 四、问题 3：那个值是死值——两个界面都不能改（本轮修）

**状态**：本轮修｜**严重度**：高｜**性质**：缺编辑面，本次投诉的原点

### 4.1 现象

- **模型库 Tab** 的「上下文 / 输出上限」两列是**只读展示**，没有输入框，而且读的是**实时远端响应**，不是本地配置。
- **模型 Tab ②参数区** 只认 `model_params`，模型库写的是 `model_meta`，连行都不出现。

结果：存进配置的那个值，**两个界面都没有入口去改它**，是死值。

### 4.2 根因：②参数区的行集合 = `model_params` 的键

```tsx
// ModelParams.tsx:65
[...new Set([...Object.keys(defaults), ...Object.keys(params)])].map(...)
```

没有键就一行都没有，没有任何兜底、没有默认行。于是：

| 场景 | ②参数区表现 |
|------|-------------|
| 手动加过参数（temperature / top_p / context_limit / reasoning_effort） | 有行、有值 |
| 从模型库勾选进来、未手动加过参数（kilo 全部 5 个） | **零行** |
| 手动加的参数被删空 | 行消失 |

而 `_models_of`（`model_service.py:251-273`）只下发 `max_output_length`，**不下发 `context_length`**；前端 `ModelEntry` 也没这个字段。所以即便想显示也拿不到。

### 4.3 证据

**远端实测（kilo 网关 `/models`）**

| 模型 id | 顶层 context_length | top_provider.max_completion_tokens | 落库结果 |
|---------|--------------------|-----------------------------------|----------|
| cohere/north-mini-code:free | 256000 | 64000 | ctx + 输出上限 都存 |
| kilo-auto/free | 256000 | 32768 | 都存 |
| nvidia/nemotron-3.5-super-vl:free | 1000000 | 131072 | 都存 |
| reflection/beam-free | 1048576 | 131072 | 都存 |
| **openrouter/free** | 200000 | **null** | **只存 ctx，无输出上限** |

`openrouter/free` 是网关侧 `top_provider.max_completion_tokens = null`，而落库策略是"空值不写"，所以它天然没有输出上限。这与"前端不显示"是两个独立原因——**不要在前端造值**。

### 4.4 修法：下发 + 可编辑行 + 默认值兜底

1. 后端 `_models_of` 补一行：`"context_length": meta.get("context_length")`。
2. 前端 `ModelEntry` 补 `context_length` 字段。
3. 前端 `useSettings` 的 `load` / `selectProvider` / `selectModel` / `refreshModels` 四条通道：`defaults` 里没有 `context_length` 时，用 `model_meta` 声明值兜底。
4. ②参数区因此**自动多出一条普通可编辑参数行**，初值 = 厂商声明值，用户改了就写 `model_params`（最高优先级）。

**不做"只读展示两行"**：只读展示时该值依然没有编辑入口，等于没解决原问题。

### 4.5 为什么不是"库勾选时自动往 model_params 写"（撤回 v1.0 理由后的准确版本）

v1.0 曾写"污染参数区、制造假脏态"，**该理由不成立**（写入时把 `defaults` 一起对齐的话，`isDirty` 不会误判）。真实理由只有两条：

1. **双真源 + 覆盖冲突**：`model_params` 一有值就变成"用户已配置"。此后库重新勾选（厂商 ctx 变了），只能二选一——覆盖就吞掉用户手工值，不覆盖就新值失效，两种都在猜用户。用户把窗口从 200K 调小到 100K 省钱，一次勾选保存就可能被无声冲掉。
2. **账本语义混了**：②区的脏态、保存、删除、`remove_params` 键级删除、跨 provider 迁移，全部按"用户设置"解释。混进厂商值后，人和代码都分不清哪条是自己设的。

正确做法不是"搬家"，而是**给 `model_meta.context_length` 补运行时读取面**（问题 2）+ **补下发与编辑面**（问题 3）。写入侧一个字不用改，天然没有双写冲突。

### 4.6 验证

- 切到 5 个 kilo 模型，②参数区各出现一条可编辑 `context_length` 行，初值 = yaml 里的声明值；
- 改一下再改回 → 不弹未保存提示、保存栏不亮、yaml 的 `model_params` 无新增键；
- 改后保存 → `model_params.{model}.context_length` 有值，且该键**不出现在请求体**。

## 五、问题 4：API 地址两个名字（本轮修）

**状态**：本轮修｜**严重度**：中｜**性质**：同概念两名 + 每次都要翻译

### 5.1 现象

- 后端真源：`config.yaml` 的 `ai.{provider}.api_base`；
- 前端 DTO 与 UI 标签：`base_url`；
- 后端 `update_provider_config` 的 `key_map` 里同时登记 `base_url → api_base` 和 `api_base → api_base`，**每次保存都要翻译一遍**；
- `ProviderConfigUpdate` DTO 字段名也是 `base_url`，且 400 校验循环里同时判两个键。

### 5.2 根因

前端先起的名（`base_url`，类比 `httpx.base_url`），后端落盘名是 `api_base`，中间用 `key_map` 做兼容层，兼容层从此长期存在。

### 5.3 证据

- `model_service.py:543-545`：`key_map` 两个入口指向同一个落盘键；
- `model_routes.py:130`：DTO 字段 `base_url`；
- `model_service.py:562`：`for _url_key in ("base_url", "api_base")` 双判；
- 2026-09-27 已因两侧 strip 口径不一致，在 YAML 里存过带空格的地址（` https://x/v1 `），消费端不 strip 即请求失败。

### 5.4 修法

统一为 `api_base`：删 `key_map` 的 `base_url` 别名、DTO 字段改 `api_base`、前端类型与表单字段改 `api_base`、UI 标签同改。不留兼容分支。

### 5.5 验证

- 前后端各只剩一个名字（`grep base_url` 只命中 `API_BASE_URL` 这类**前端自身**的环境变量，与 provider 地址无关）；

## 十一、不是问题：名字相似但语义不同（禁止合并）

合并这几组会直接产出错误请求或丢信息，属"看起来统一、实际制造 bug"：

| 组合 | 语义差异 | 合并后果 |
|------|----------|----------|
| `max_output_length`（厂商目录声明） vs `max_tokens`（请求体字段） | 前者是模型属性，后者是每次请求要发的参数 | 请求体出现 `max_output_length`，多数厂商不认 → 400 |
| `capabilities`（我方勾选） vs `supported_features`（厂商声明） | 一个人工配置，一个厂商事实 | 无法表达"厂商支持但我方禁用" |
| `param_options`（我方允许值集合） vs `supported_parameters`（厂商参数名列表） | 一个是枚举取值，一个是参数名清单 | 语义彻底错位 |
| `model_params`（用户生效值） vs `model_meta`（厂商声明值） | 一个是我方决策，一个是厂商事实 | **存储块禁止合并**；但块内键名共用 `context_length`（见 11.1） |

### 11.1 更正：`context_length` 为什么可以两个块同名（v2.3 修正 v2.2 的自相矛盾）

v2.2 在此处把 `context_length`（厂商声明）与"用户生效窗口"列为"语义不同、禁止合并"，与第二章"统一为 `context_length`"**自相矛盾**。更正如下：

**改名与并块是两件事。**

| 动作 | 是否执行 | 理由 |
|------|----------|------|
| 把 `context_limit` 改成 `context_length`（改名） | **执行** | 两个块描述的是**同一个物理量**：token 数，同一单位、同一量纲、可数值比较、可串成 `min/max` 优先级链 |
| 把 `model_params` 与 `model_meta` 合成一个块（并块） | **禁止** | 两者写入者不同、刷新周期不同（详见 11.2） |

### 11.2 判定口径（可复用，两条按顺序判）

1. **这个键会不会进发往厂商的请求体？**
   - 会 → 必须用厂商认的线上字段名（`max_tokens`、`temperature`、`top_p`），**禁止按我方习惯改名**；改了就是 400。
   - 不会 → 它只是我方算法内部用的量（`context_length`、`max_output_length`），用"描述这个量"的名字即可。
2. **是不是同一个物理量？**
   - 是（同单位、同量纲、可比较）→ **同名，按存储块区分来源**。
   - 否（一个是属性、一个是参数名清单）→ **不同名**。

按这两条判：`context_length` 不进请求体、且两处都是 token 数 → **同名**；`model_params` 与 `model_meta` 写入者不同 → **分块**。`max_output_length` 与 `max_tokens` 一个是属性、一个要上线 → **不同名**。

另：`openrouter/free` 厂商侧 `max_completion_tokens = null`，属厂商事实，不是缺陷，**不得在前端造值**。

### 14.5 澄清：`state.model.defaults` 不是通用设置（v2.3，2026-11-01 13:15:58）

北京老陈提问"`defaults.context_length` 是通用设置的配置参数区吧"——**不是**。系统里关于上下文窗口实际有四层，`defaults` 只是其中一层的**内存副本**，最容易被误认：

| # | 名字 | 存在哪 | 谁写 | 作用域 | 消费方 |
|---|------|--------|------|--------|--------|
| 1 | `llm.context_length_default` | `config.yaml` 的 `llm:` 段 | 用户，在**通用 Tab** | 全系统 | 没单独配置的模型兜底 |
| 2 | `model_meta.{model}.context_length` | `config.yaml` 的 `ai.{p}.model_meta` | 模型库扫描自动写 | 单个模型 | 兜底 + 显示 |
| 3 | `model_params.{model}.context_length` | `config.yaml` 的 `ai.{p}.model_params` | 用户，在**模型 Tab ②参数区** | 单个模型 | 运行时实际窗口 |
| 4 | `state.model.defaults` | **只在浏览器内存，不落盘** | 前端从第 3 层复制 | 当前选中模型 | 仅用于脏判定比较 |

第 1 层才是"与厂商无关的通用配置"（北京老陈的原意，存在且正确）；第 4 层 `defaults` 是前端拿第 3 层做的"已保存基线副本"，只在 `isDirty(params, defaults)` 里参与比较，**既不落盘、也不进请求、更不是通用设置**。

**为什么这个混淆是必然的**：`defaults` 字面意思是"默认值"，而它实际语义是"已保存基线"。它与第 1 层的"default"撞名但不同物。**定案（北京老陈 2026-11-01 13:19:00 裁定）：改名为 `state.model.baseline`**（`frontend/src/features/settings2` 内 74 处，纯本地重命名，`tsc` 可全量验证）。此改名收益非零（消除与通用设置 `..._default` 的撞名），与 14.1/E4「`state.model.params` 不改名」不同——那项确实零收益。

**改名后各层名字一览（名字与语义一一对应，无撞名）**：

| 语义 | 名字 | 落盘 |
|------|------|------|
| 全局默认窗口（通用 Tab） | `llm.context_length_default` | 是 |
| 厂商声明窗口（模型库写入） | `model_meta.{model}.context_length` | 是 |
| 用户生效窗口（②参数区） | `model_params.{model}.context_length` | 是 |
| 当前编辑值（内存） | `state.model.params` | 否 |
| 已保存基线（内存，仅比脏） | `state.model.baseline` | 否 |

### 14.6 教训

1. **改名先查导入点**：常量改名，第一件事是 `grep` 全仓 import，不是改调用表达式。E1 就是只改调用处、漏了 import。
2. **涉及"基线 vs 当前值"的改动，必须同时定义基线取哪个源**，否则必然出现"永远脏"。
3. **删除语义必须显式定义**：有兜底的数据，删除一定等于"回落兜底"，不定义就会看起来像 bug。
4. **UI 文案也是契约**：e2e 用文本定位时，改标签等于改契约，必须在同一批次处理。

### 15.3 问题 7（断网即失明）实现细节

`ModelLibraryTab.tsx` 的「上下文」「输出上限」两列，原来**只读远端实时返回**：拉取失败时整列变 `–`，用户明明在库里存过值，界面却像没存。修法（不新增接口）：

| `pickMeta` | `:279` | 远端值优先；远端缺失/不可用时回落本地已存；都没有才 `null` → 显示 `–` |
| `renderMetaCell` | `:293` | 回落值后缀 `*` + Tooltip「远端未返回该字段，数值取自本地已存元数据」，杜绝把本地旧值误当远端实时值 |

| 排序器 | `:595`、`:607` | 与显示同源（`pickMeta`），避免「显示是 A 排序按 B」 |

### 16.3 第 9 轮定案的真缺陷 E5（已修）

**位置**：`frontend/src/features/settings2/components/ParamOptionsModal.tsx`（管理参数选项弹窗，悬空默认值确认分支）。

**改前**：

```ts
await modelApi.updateModel(provider, model, {
  param_options: draft,
  model_params: {
    ...baseline,                       // ← 整份基线展开
    [dangling]: (draft[dangling] ?? [])[0],
  },
});
```

**为什么是缺陷**（三重证据链，缺一不成立）：

1. `ParamOptionsModal` 的 `baseline` 由 `SettingsPage` 直传 `state.model.baseline`，而基线已被 `withDeclaredContextLength` 注入「厂商声明窗口」；
2. 后端 `update_model` 对 `model_params` 是 **merge** 语义（`new_params = dict(orig); new_params.update(mp)`），即**只要送变更键**就够；
3. 于是展开整份基线 = 把「用户没设过的注入值」当成用户设置写进 `ai.{provider}.model_params.{model}.context_length`。后果不是显示问题，而是**语义污染**：厂商日后把声明窗口从 1M 上调到 2M，该模型仍被这条物化旧值压住，且界面上看不出它已从「声明值」变成「用户值」。

**改后**：

```ts
await modelApi.updateModel(provider, model, {
  param_options: draft,
  // 只送被重置的那一个键（后端 merge 语义）
  model_params: { [dangling]: (draft[dangling] ?? [])[0] },
});
```

**连带核查**（同一轮内把所有请求体都过了一遍，确认只有这一处会物化注入键）：

| 请求体位置 | 送的内容 | 结论 |
|------------|----------|------|
| `useSettings.saveModelGroup` | `body.model_params = changed`（只含 `isDirty` 命中键） | 安全：`isDirty` 只遍历 `params` 键，注入行不在 `params` 里 |
| `ModelModals` 添加模型 | `collected.params`（用户在弹窗里勾选的模板） | 安全：与基线无关 |
| `SettingsPage` 透传 | `d.model_params`（原样转发弹窗结果） | 安全 |
| `ParamOptionsModal`（本处） | ~~`{...baseline, ...}`~~ → `{[dangling]: 首项}` | **本轮修** |
| `saveProviderDraft` | `providerDraft`（③区 diff） | 安全：不涉 `model_params` |
