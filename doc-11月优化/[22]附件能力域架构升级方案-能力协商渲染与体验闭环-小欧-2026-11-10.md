# 附件能力域架构升级方案 — 能力协商渲染与体验闭环

> 文档名称：[22]附件能力域架构升级方案-能力协商渲染与体验闭环
> 编写：小欧　2026-11-10
> 基线：[20]附件支持能力技术架构与功能逻辑流程（第五章关键结论与 D1~D6 缺陷）
> 范围：后端能力域与前端附件体验的全局架构升级，非单点补漏

---

## 0. 一页看懂

本方案不改"某一条缺陷"，而是**换掉产生缺陷的那套结构**。

当前系统的真问题只有一句话：

> **附件类型轴（kind）与模型模态轴（modality）是两套独立分类，二者之间只靠三处硬编码 if 临时对接。**

三处硬编码分别在：`attachments/extract.py:86 build_inject_text` 的 kind 分支、`services/agent/vision.py:101 split_vision_refs` 的 image-only 分流、`services/agent/media_payload.py:149 build_media_part` 的 image-only 构 part。

因此 D1~D6 不是六个独立 bug，而是**同一个结构性缺口**的六种表现：

- 新增一种附件（audio，D1）→ 没有入口，因为 kind 词典里根本没有它；
- 新增一种原生传输（file/video，D2）→ 无处安放，因为分流只认 image；
- 判定只有"能/不能"（D3）→ 因为能力被压缩成一个 bool；
- 实测只覆盖 image（D4）→ 因为探针和 accept 结构写死了 image；
- 矩阵无守门测试（D5）→ 因为矩阵不以数据形式存在，只散落在 if 里；
- 截断无完整性标记（D6）→ 因为抽取器各自为政，没有统一出口契约。

**目标架构：把"类型 × 能力 → 渲染方式"从代码分支提升为一份可测试的数据契约，再加一个纯函数计划器。**

一句话定义应用模式：

> **能力协商式附件渲染（Capability-Negotiated Attachment Rendering, CNAR）**：附件不以"文件类型"决定命运，而以"文件类型 × 当前模型有效能力 × 传输方言"三元组协商出唯一渲染计划；原生能收则发原生 part，不能则降维成内容文本，再不能则降为档案卡，且每一级降维对用户可见。

这套模式一次性把 D1~D6 全部收进同一张契约表、同一个计划器、同一个守门测试。新增任何类型/模态，**只加表行，不改流程**。

## 1. 现状与根因

### 1.1 两条轴与真正的耦合点

| 轴 | 取值 | 唯一真源 |
|---|---|---|
| 附件类型 kind | text / image / video / richdoc / binary | `attachments/extract.py:52 classify`（后缀词典 :38-49） |
| 模型模态 modality | text / image / audio / video / file | `services/model/model_service.py:910 normalize_modalities` |

两轴的对接现状（全部为隐式硬编码）：

1. `react_loop.py:218-231`：只有 `supports_image_input` 为真时才调用 `split_vision_refs` 把 image 摘出正文；其余类型一律走文本。
2. `vision.py:101 split_vision_refs`：以 `mime.startswith("image/")` 识别，天然只认图片。
3. `media_payload.py:149 build_media_part`：`if kind != "image": return None`，原生 part 只有图片一种。
4. `vision.py:75 supports_image_input`：读取 `media.accept.image` 实测值 → 回落 `input_modalities` 是否含 image，**结果是一个 bool**。

关键事实：resolver 在计划之前**已经把所有附件解析成了注入文本**（`services/refs/pipeline.py:38` → `resolver.py:249`）。也就是说——

> 每一份"降维文本"其实早已算好，只是当图片被判定走原生时被丢弃了。

这条事实决定了本方案最省的一步：**原生失败时无需重新抽取，直接复用 ref 上已存在的 `content` 作为降级文本**。

### 1.2 缺陷与根因映射

| 编号 | 现象 | 直接根因 | 结构性根因 |
|---|---|---|---|
| D1 | audio 无附件入口 | kind 词典无 audio；classify 无分支 | 类型轴与模态轴未对齐（modality 有 audio，kind 没有） |
| D2 | file/video 模态悬空 | 传输层只实现 image part | 缺"逻辑 part → 方言 part"的运输层 |
| D3 | 判定缺"降维可用"中间态 | 能力被压成 bool | 缺三级能力画像 |
| D4 | 实测只覆盖 image | accept 结构与探针写死 image | 探针未按模态维度建模 |
| D5 | 矩阵无守门测试 | 矩阵不存在，只在 if 里 | 缺可被测试的单一契约数据 |
| D6 | 截断无完整性标记 | 各抽取器各自决定 | 缺统一抽取出口契约 |

注意 D1 与 D4 的对称性：模态轴早就有 audio，类型轴与探针却都没有 —— 这正说明两条轴是各自演化的，没有共同契约。

## 2. 设计原则与不变量

### 2.1 五条设计原则（对齐 KISS-DIRECT）

1. **单一契约**：类型→模态→降级方式只允许存在于一张表里，前后端与测试共用其投影。
2. **声明≠可用**：配置声明只是候选，原生传输必须实测通过才启用；未实测一律走文本降维。这是防止整轮 400 的安全底线。
3. **降级必须保底**：每一种 kind 都必须有一个"永远成功"的文本出口（内容文本 / 元数据 / 档案卡三档之一）。
4. **不新增状态机**：沿用现有"history 恒 str + 占位 + wire 边界展开"的 V3 不变量，不做双份历史。
5. **不搞注册表膨胀**：契约是 6 行数据 + 一个纯函数计划器 + 一个 5 分支运输函数；不引入插件框架、不引入能力注册中心。

### 2.2 必须守住的不变量

- `conversation_history` 内 content 永远是可序列化字符串；压缩/裁剪/持久化零改动。
- base64/大文本不得入落库与日志；原生 part 只在 wire 边界生成。
- 失败不阻断本轮：任一条目失败退化为文字说明，继续发送。
- 输出模态（生图/生视频）不参与附件入参判定，只看 input 侧。

## 3. 目标架构

### 3.1 分层视图

```
┌─────────────────────────────────────────────────────────────┐
│ 体验层  前端：能力徽标 / 发送前对齐 / 抽取态可视化             │
├─────────────────────────────────────────────────────────────┤
│ 投影层  model DTO.ref_capability（kind → native/degraded/opaque）│
├─────────────────────────────────────────────────────────────┤
│ 计划层  contract.plan_refs(refs, profile) → (text_refs, native_refs)│
├─────────────────────────────────────────────────────────────┤
│ 能力层  capability.profile(llm_model) → {modality: NativeCap} │
├─────────────────────────────────────────────────────────────┤
│ 契约层  contract.KIND_CONTRACT（kind → 模态/降级质量/出口）     │
├─────────────────────────────────────────────────────────────┤
│ 运输层  media_payload(logical part) → wire part（chat/responses）│
├─────────────────────────────────────────────────────────────┤
│ 抽取层  extract.build_inject_text（统一完整性标记）             │
└─────────────────────────────────────────────────────────────┘
```

职责各一段，单向向下依赖，无回调、无环：

- 契约层只依赖 classify 的后缀词典与模态词汇，**零 IO、零配置**；
- 能力层只读配置与实测记录，纯函数；
- 计划层只做集合拆分，纯函数；
- 运输层只做格式翻译，纯函数 + 缓存；
- 抽取层是唯一读盘处。

### 3.2 核心数据结构

```python
# app/attachments/contract.py  （新增，零 IO）

# 降级质量：决定"降维后模型还能理解多少内容"
#   content  完整内容（文本正文 / 富文档抽取）
#   metadata 部分内容（视频/音频的时长/编码等）
#   card     仅档案信息（文件名/大小/类型，模型看不到内容）
@dataclass(frozen=True)
class KindRoute:
    native_modality: str | None      # 可尝试的原生模态；None=永远走文本
    fallback_quality: str            # content | metadata | card
    extractor: Callable              # 永远成功的文本出口
    on_native_fail: str              # reuse_text | notice

KIND_CONTRACT: dict[str, KindRoute] = {
    "text":    KindRoute(None,    "content",  _text_body,     "reuse_text"),
    "richdoc": KindRoute("file",  "content",  _richdoc_body,  "reuse_text"),
    "image":   KindRoute("image", "card",     _image_card,    "reuse_text"),
    "video":   KindRoute("video", "metadata", _video_card,    "reuse_text"),
    "audio":   KindRoute("audio", "metadata", _audio_card,    "reuse_text"),
    "binary":  KindRoute(None,    "card",     _binary_card,   "reuse_text"),
}

KIND_MODALITY = {k: r.native_modality for k, r in KIND_CONTRACT.items()}
```

```python
# app/services/agent/capability.py （新增，纯函数）

@dataclass(frozen=True)
class NativeCap:
    native: bool          # 可发原生 part
    transport: frozenset  # {"inline"} / {"inline","url"}
    source: str           # measured | declared | none

def profile(llm_model) -> dict[str, NativeCap]:
    """image/audio/video/file 四模态能力画像。
    规则：
      - media.accept[m] 实测存在（both/inline/url/none）→ 以实测为准；
      - 无实测但 input_modalities 含 m → native=True, transport={"inline"}, source=declared；
      - 否则 native=False, source=none。
    安全守门：video 必须实测才 native；file/audio 声明不直接放行（见 3.5）。"""

def ref_capability(profile) -> dict[str, str]:
    """kind → native | degraded | opaque（供前端直接索引，单一真源）。"""
```

```python
# app/attachments/contract.py

def plan_refs(refs, prof) -> tuple[list, list]:
    """计划器（纯函数）。返回 (text_refs, native_refs)。
    对每条附件引用：
      route = KIND_CONTRACT[classify(ref.path, ref.mime, ref.size)]
      if route.native_modality and prof[route.native_modality].native and wire_ok(...):
          native_refs.append(ref)     # ref.content 仍保留，作为失败降级
      else:
          text_refs.append(ref)       # 走既有渲染块
    """
```

```python
# 运输层：逻辑 part 只描述语义，不描述方言
LogicalPart = {"modality": "image|audio|video|file", "mime": str,
               "data": bytes | None, "url": str | None}

def to_wire_part(part: LogicalPart, dialect: str) -> dict | None:
    """dialect=chat 时产出 OpenAI 兼容 content part；
    dialect=responses 时由 adapter.to_responses_body 二次转换（沿用现有钩子）。
    video 无标准 chat part：仅当 provider 适配器显式声明支持才产出，否则 None。"""
```

### 3.3 能力画像：从 bool 到三级

| 状态 | 含义 | 判定 |
|---|---|---|
| `native` | 模型直接消费原始内容 | `profile[modality].native` |
| `degraded` | 模型读到内容文本或元数据 | 非 native 且 `fallback_quality ∈ {content, metadata}` |
| `opaque` | 模型只知文件名/大小 | `fallback_quality == card` |

这张表直接回答 D3：**"降维可用"是一等状态，不再是 bool 的副产物。** 前端拿到的是 kind→状态，不需要自己推。

### 3.4 计划器：唯一分流点

用 `classify()` 复用上传时的唯一分类真源，**不新增字段、不查库、不复制词典**：

```python
route = KIND_CONTRACT[classify(Path(ref["path"]), ref.get("mime",""), ref.get("size",1))]
```

- 对 attachment 引用：`classify` 用 `stored_path` 后缀，与上传时同一函数，天然一致；
- 对普通 file 引用：同函数也能分类，未来若模型支持 file 原生，可直接复用；
- 判定结果与今天逐字节一致：只有 image 会进 native_refs（其余 kind 的 native_modality 为 None 或未实测）。

### 3.5 运输层与安全守门

原生传输存在三重门槛，缺一不可：

```
native 可用 ⇔ 模型能力(实测/安全声明) ∧ 方言支持 ∧ 载荷可获取(内联/公网URL)
```

- **模型能力**：见 3.3；
- **方言支持**：`to_wire_part` 按 `dialect` 产出；video 在 chat 方言无标准结构，只有适配器显式支持才产出；
- **安全声明边界**（关键）：
  - `image` 允许"声明即内联"（历史行为，风险已实证可控）；
  - `file / audio / video` **必须实测**才允许原生（`video` 无论声明如何都必须实测）。
  这条规则让 D2 从"悬空能力"变成"待实测能力"：模型声明了 file，但没测过，就走富文档抽取，绝不冒 400 风险。

原生失败时：`on_native_fail == "reuse_text"`，直接使用 `ref["content"]`（resolver 早已算好）插入文本，不重新读盘、不重新抽取。这同时解决了"原生化后丢降级"和"失败无回执"两个问题。

### 3.6 抽取出口契约与完整性标记（D6）

所有抽取器返回 `str` 的出口统一经过一个 helper：

```python
def with_completeness(body: str, *, shown: int, total: int,
                      unit: str, path: str) -> str:
    """截断时追加统一尾注；未截断原样返回。
    尾注格式：\\n[已截断：仅呈现 {shown}/{total} {unit}；完整内容请用文件工具读取 {path}]"""
```

适用：`_text_body`（256KB 头尾摘录）、`_sheet_text`（行上限）、`_richdoc_body`（分页/截断）、`_video_card`/`_audio_card`（元数据本身即摘要，标注"仅元数据"）。
守门测试对每个抽取器喂超限样本，断言输出含尾注。**D6 由测试锁定，不靠自觉。**

## 4. 应用模式与体验设计

### 4.1 体验三条铁律

1. **预见性**：发送前就能看到"这个文件在当前模型下会被怎样处理"，而不是发完才知道。
2. **一致性**：前后端对同一文件同一模型给出同一结论；结论来自同一张契约投影，不各自解释。
3. **无惊扰**：降级是常态，静默完成；只有"opaque（模型只能拿到文件名）"才用醒目但不阻塞的提示。发送永远不被阻断（除非用户开启严格模式）。

### 4.2 状态矩阵（前端展示的唯一依据）

| kind \ 状态 | native | degraded | opaque |
|---|---|---|---|
| text | — | — | —（始终作为完整文本注入，显示"文本"） |
| image | 绿 原生理解 | — | 灰 仅文件名 |
| richdoc | 绿 原生理解 | 蓝 文本抽取 | — |
| video | 绿 原生理解 | 蓝 仅元数据 | — |
| audio | 绿 原生理解 | 蓝 仅元数据 | — |
| binary | — | — | 灰 仅文件名 |

颜色/文案是表现层，可本地化；**状态值必须来自后端 `ref_capability`**。

### 4.3 场景走查

| 场景 | 现状 | 升级后 |
|---|---|---|
| 上传 PDF，模型无 file 能力 | 无提示，发后靠回执 | 抽屉行显示"文本抽取"，发送前一致 |
| 上传 PDF，模型声明 file 但未实测 | 可能整轮 400（若强行 native） | 仍走文本抽取；"原生"不出现 |
| 上传 MP4 | 档案卡 | 蓝"仅元数据"（时长/分辨率/编码） |
| 上传 MP3 | 被拒或落 binary | 接收，蓝"仅元数据"（D1 闭环） |
| 引用图片后切到纯文本模型 | 图片卡（无内容） | 徽标实时变"仅文件名"，切模型即刷新 |
| 引用图片后切到视觉模型 | 绿 原生理解 | 同，且移除时不再残留占位 |
| 大文本/大表格被截断 | 末尾可能无提示 | 统一"已截断 N/M"尾注，预览可见 |
| 原生 part 发送失败 | 一行说明 | 自动改用已解析文本，回执说明降级原因 |

### 4.4 发送前预检

输入区维护 `worstState`：

```
worst = min(state(ref_i)) over 已引用条目，按 native > degraded > opaque 排序
opaque → 黄色行内提示："以下文件当前模型只能看到文件名：xxx、yyy。可切换模型或继续。"
degraded → 无提示（蓝徽标已表达）
native → 无提示
```

不弹窗、不阻断，符合"无惊扰"。

## 5. 后端升级说明书（逐文件）

### 5.1 新增 `backend/app/attachments/contract.py`

- `KIND_CONTRACT` / `KIND_MODALITY`（3.2）；
- `AUDIO_SUFFIXES`（迁入并成为唯一真源）；
- `plan_refs(refs, prof, wire_ok)`：纯函数；
- `effective_state(kind, prof)`：返回 native/degraded/opaque；
- `ref_capability_map(prof)`：kind→state，供 model DTO。
- 依赖仅 `extract.classify` 与模态词汇常量，不 import 配置/DB。

### 5.2 修改 `attachments/extract.py`

- 后缀词典：新增 `AUDIO_SUFFIXES = {".mp3",".wav",".m4a",".aac",".flac",".ogg",".opus",".wma"}`；
- `classify()`：audio 分支插在 video 之后、richdoc 之前；
- 新增 `_audio_card()`：ffprobe 取 duration/bitrate/codec，失败降级为档案卡（复用 video 的降级写法）；
- 新增 `_image_card()` / `_binary_card()`：从现有 build_inject_text 的兜底分支提为具名函数（契约需要有名字的出口）；
- 统一截断尾注 helper `with_completeness()`，接入 `_text_body`/`_richdoc_body`/`_sheet_text`；
- `build_inject_text()` 改为查 `KIND_CONTRACT[kind].extractor` 分派（从 5 分支 if 变为一次查表），**行为不变**；
- `extract_status` 仍由 attachment_service 依据异常/成功写入，不改表结构。

### 5.3 新增 `backend/app/services/agent/capability.py`

- `profile(llm_model)`：读 `model_meta.media.accept` 与 `input_modalities`；
- 保留并内聚现有 image 判定语义（实测优先、回落声明、accept=none 生效）；
- `supports_image_input(llm_model)` 改为 `profile(...)["image"].native` 的薄投影（仅此一处导出，避免语义分叉）；
- `transport_flags(modality)`：产出是否允许 inline / url；
- 供 `model_service._models_of()` 与计划器共用。

### 5.4 修改 `services/agent/vision.py` → 更名 `services/agent/attachment_wire.py`

更名理由：职责已从"视觉通道"扩展为"媒体附件 wire 展开"，名称须与职责一致（SRP + 禁止名实不符）。一次性全量改导入，不留兼容别名（禁止 backward）。

- `IMAGE_SLOT_RE` → `ATTACHMENT_SLOT_RE`（`\[\[ATTACHMENT:([0-9a-f]{32})\]\]`）；
- `split_vision_refs` → 移入 `contract.plan_refs` 并删除旧函数；
- `supports_image_input/accepts_*` → 移入 `capability.py`；
- `image_slot` → `attachment_slot`；
- `expand_image_slots` → `expand_attachment_slots`：识别所有占位，逐条取 attachment kind → 选运输 → 构逻辑 part → `media_payload.to_wire_part`；
- 展开失败：取 `ref["content"]`（resolver 已产出）替换为文本；仍无则一行说明；
- 外链图片正则与 `_NON_IMAGE_SUFFIX` 逻辑原样迁移（不变）。
- 存量数据迁移：一次性 SQL 将历史消息中的 `[[IMAGE_ATTACHMENT:` 改写为 `[[ATTACHMENT:`，使新旧记录统一走单一正则（不做双 token 兼容分支）。

### 5.5 修改 `services/agent/media_payload.py`

- `build_media_part(kind, ...)` → `build_logical_part(kind, attachment, transport)`：按模态构建逻辑 part；

## 8. 分阶段路线（每阶段可独立验收）

### P0 契约与守门（零行为变更）

- 验收：切换模型徽标实时变化；opaque 触发行内提示；无网络新增请求（复用模型 DTO）。

### P2 抽取完整性（D6）

## 10. 非目标与风险

### 10.1 明确不做（YAGNI）
- 不引入 OCR 让非视觉模型"读图"：image 的降级仍是档案卡；契约的 `extractor` 槽位已为未来 OCR 预留，但本期不实现。
- 不做"解析拖入即预览大图"等纯展示工程。
- 不为旧 token/旧函数保留双实现（禁止 backward）；用一次性数据迁移解决历史数据。

### 10.2 已知取舍
- **resolve 先于 plan**：原生路径也会先算一次抽取文本（浪费少量 IO）。换来的是"原生失败零重算"和"回执一致"。仅在性能画像证明必要时，才考虑 plan 前置 + 懒抽取（列为后续优化，不纳入本期）。
- **声明不直接放行 file/audio/video**：牺牲"配置即用"的便利，换取"绝不 400"的确定性。这是本方案的安全底线，不妥协。

### 10.3 风险
- 实测探针依赖样本配置：未配置时 file/audio/video 永远 degraded。这是"诚实降级"，不是缺陷；需在设置页说明。
- provider 方言差异：video 原生可能长期不可用；运输层已用"显式原因"表达，不制造虚假能力。
