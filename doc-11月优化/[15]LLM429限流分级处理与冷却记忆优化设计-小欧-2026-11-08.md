## 2. 厂商 429 语义差异（调研结论）

| 厂商 | 429 语义 | 判据 | Retry 提示 |
|---|---|---|---|
| OpenAI | 混合三态：速率限流 / 余额耗尽 / 支出上限 | `error.code`（rate_limit_exceeded vs insufficient_quota） | `Retry-After` + `x-ratelimit-reset-*` |
| Anthropic | `rate_limit_error`；过载另走 529 `overloaded_error` | error.type | `retry-after` + `anthropic-ratelimit-*` |
| Gemini | 429 + `RESOURCE_EXHAUSTED`，**同时表示 RPM 超限与每日配额** | 需再看 message 有无 daily/per day | 无文档化 Retry 头 |
| DeepSeek | 429 仅并发/RPM；余额不足走 **402** | 状态码即语义 | 无 |
| Kimi/Moonshot | OpenAI 兼容 | error.type | — |
| Bedrock | `ThrottlingException`（限流，须重试） | 异常类型名 | — |
| OpenRouter | 网关自身 429 或透传上游（双层） | metadata.raw | 不定 |

**通用约定（可放心依赖）**：① 429=瞬态可重试、其余 4xx=确定性失败；② 有 `Retry-After` 必须尊重；③ 429 必须再细分"限流 vs 账单"（无统一 token 词表，只能多 token 匹配）；④ 退避带抖动；⑤ 重试必须有上限。

## 3. 429 四态模型（设计核心）

把 429 从"一个状态码"细分为四种处理路径：

| 态 | 判据 | 策略 | 用户感知 |
|---|---|---|---|
| **A. 契约等待态** | 有 `Retry-After: N` | 进入 **pause 挂起**，倒计时 N 秒后自动恢复 | 前端倒计时提示，可随时"取消暂停=中断任务" |
| **B. 瞬态限速态** | error.type 命中限速词 / 裸 429 | 现有 L1 指数退避 + L2 重试 | notice 通道"模型限流，第 n 次重试" |
| **C. 配额打死态** | error.type 命中配额词 | 不重试，直接终态 | "配额/余额已用尽，请升级配额" |
| **D. 限速记忆态** | 某模型完整走完 L1+L2 重试仍 429 | 记入冷却注册表，**后续访问该模型主动延迟（首次 5s，升档见 §4.2）** | 顶栏/模型标识"限速中"徽标 |

## 4. 老陈两点意见的落地设计

### 4.1 Retry-After → pause 挂起 + 倒计时 + 可取消（A 态）

**语义澄清**：Retry-After 不是"不重试"，而是服务端给了精确恢复时刻——是四类中**最有价值的重试契约**。但从用户体验看，长时间静默 sleep 不如显式挂起。

设计：
- `base_service._retry_wait_seconds` 解析出 Retry-After 后，不再原地 sleep，而是 yield 一个 **pause chunk**：`{"type":"pause","pause_seconds":N,"wait_text":<人类可读时长>,"reason":"rate_limit_retry_after"}`（注：统一用 `wait_text`（后端算人类可读时长），摒弃 `resume_at`——与 §10.1/§11.5 帧契约一致）
- 前端收到 pause 帧：渲染倒计时（"模型限速，N 秒后自动恢复"），提供"立即中断"按钮。
- 倒计时结束：后端自动重发该次 LLM 调用（同一 step，不消耗 L1 重试次数——这是契约等待，不是失败重试）。
- 用户点中断：走现有 cancel 通道（`error_type=cancelled` → handle_answer 置 CANCELLED 终态），复用已修复的取消链路，零新增取消逻辑。
- 上限保护：pause 秒数超过 `RETRY_BACKOFF_CAP`(120s) 时封顶并提示"等待较长，可中断"。

注意 2026-10-05 曾修复"L1 退避睡眠不可中断"的取消倒退——pause 化后天然解决（pause 期间任务处于可取消等待态，不占 asyncio.sleep）。

### 4.2 重试耗尽 → 模型限速记忆 → 主动延迟（D 态）

设计：**ModelCooldownRegistry（模型冷却注册表）**，单例、内存态（不落库，重启清零即可）。

```
key:   model_id（或 provider+model）
值:    {cooldown_until: epoch, last_429_at: epoch, hits: int}
```

- **写入**：L1+L2 完整重试链耗尽且最终分类为 RATE_LIMIT 时（base_service 429 耗尽出口 / llm_call L2 耗尽出口），`registry.mark(model_id)`（首次 5s，后续命中按 hits 沿档位序列升档 5→10→20→30，封顶 30s）。QUOTA_EXCEEDED 为**固定 100s 独立冷却**（账务问题不随限速升档序列走，余额不可能秒级恢复；用户裁定 100s）。
- **读取**：`llm_call` 发起 LLM 调用前查 `registry.delay_for(model_id)`，剩余冷却 >0 则先 sleep 剩余秒数（可取消），并 yield notice"该模型限速中，等待 N 秒"。
- **衰减**：一次成功调用后 `registry.clear(model_id)`。连续命中升档 **5s→10s→20s→30s，封顶 30s**（粒度不宜过细——经验值 5/10/20/30 已够覆盖 RPM 60s 滑窗的恢复节奏，过密档位无必要）。
- **职责边界**：冷却只是"削峰减速带"——挡住紧跟的重复请求；**冷却 30s 封顶后仍撞 429 的，不再升档，直接交回 L1/L2 重试逻辑兜底**（冷却管"别马上去撞"，重试管"撞了再恢复"，不喧宾夺主）。
- **粒度**：用 provider+model 而非仅 model——同一模型名走不同网关限速互相独立。

价值：五会话并发场景（PAR-05 事故的根因场景）下，第一个会话耗尽重试后，后续会话不再各自白打 3~4 次 429，全局节流。

## 7. 边界与不做的事（YAGNI）

- 冷却注册表**不落库、不跨进程共享**——单机内存即可，重启清零无副作用。
- 不引入滑动窗口/令牌桶算法——档位升档 + 成功清零足够。
- `x-ratelimit-reset-*` 精细头**本期不接入**——Retry-After 已覆盖主路径，留作后续增强。
- OpenRouter 双层 429 不做专门解析——透传体已能被现有 error.type 提取覆盖。

## 8. 验收场景

1. **Retry-After 契约**：模拟 429+`Retry-After: 30` → 前端出倒计时，30s 后自动恢复成功；倒计时中点中断 → 任务 CANCELLED。
2. **配额打死**：429+`insufficient_quota` → 不重试，直接终态文案。
3. **冷却记忆**：会话甲连续 429 耗尽 → 会话乙 5 秒后发请求同模型 → 先等冷却剩余再发，不再白打 429。
4. **Gemini 歧义**：`resource_exhausted` + "daily quota" → QUOTA_EXCEEDED；无 daily 字样 → RATE_LIMIT 重试。
5. **取消回归**：pause 态/冷却等待态/退避态三种等待中取消，均立即终止（对齐 2026-10-05 取消修复）。

## 9. 消息提示优化：429 分类中文文案（老陈意见 2）

**现状**：后端 `stream_error` 文案已分两类——"模型限额/余额已用尽（429）"（quota_exceeded）与"模型限流（429）"（rate_limit）。前端 `ErrorDetail.ERROR_TYPE_LABELS` 有 `rate_limit: '速率限制'` / `quota_exceeded: '限额超限'`。

**问题**：SSE 过程帧（retrying/notice）与最终 error 帧的文案是两条链，用户看到的过程提示没有 429 分类中文标签；且"429"这个 HTTP 状态码对非技术用户不友好。

**优化**：在 429 后面直接拼中文分类缩略词，构成"429·限速"/"429·限额"/"429·延时"三类人话标签。（注：第四态冷却等待也区分——限额冷却显"模型限额，等待N秒"，限速冷却显"模型限速，等待N秒"，不混用。）

| 场景 | 后端 stream_error 文案（改后） | 前端 ERROR_TYPE_LABELS | 过程帧（retrying/notice）文案 |
|---|---|---|---|
| 限额打死 | `模型限额/余额已用尽（429·限额），请升级限额后重试` | `quota_exceeded: '429·限额'` | — |
| 瞬态限速 | `模型限流（429·限速），请稍后再试` | `rate_limit: '429·限速'` | `[调用]重试 n/N等w秒（429·限速）` |
| 契约等待（pause） | — | 新增 `rate_limit_wait: '429·延时'` | `模型限速，N秒后自动恢复（429·延时）` |
| 冷却等待（D 态） | — | — | `[冷却]模型限额/限速，等待 N 秒`（按冷却类型区分） |

**改动点**：
- `error_classifier.py:SYSTEM_ERROR_TYPE_TO_MESSAGE` 两条 429 文案加中文后缀。
- `base_service.py` 两处 429 耗尽出口文案同步。
- `llm_call.py:_format_retry_payload` 对 429 类重试事件文案加（429·限速）后缀。
- 前端 `ErrorDetail.tsx:ERROR_TYPE_LABELS` 更新两条 + 新增 `rate_limit_wait`。

## 10. Retry-After 前端倒计时设计（老陈意见 4）

**结论：需要前端配合，且不需要新增组件**——复用现有 `TaskInfoBar` 位置 2 动态状态 + `notice` 通道即可，与系统现有"重试中🔁"、"已暂停⏸️"视觉规范完全对齐。

### 10.1 交互设计

```
用户发送 → 后端收到 429+Retry-After: 30
  → 后端计算人类可读时长（秒/分/时自适应），生成 pause 帧:
    {"type":"pause","pause_seconds":30,"wait_text":"30秒","reason":"rate_limit_retry_after"}
  → llm_call 转 notice: kind=rate_limit_wait, phase=start, content="模型限速，30秒后恢复（429·延时）"
  → 前端 TaskInfoBar 位置 2 渲染: ⏳ 模型限速，30秒后恢复（429·延时）[中断]（纯展示，无本地逻辑）
  → 后端退避等待期间，跨单位边界时按需推送 notice update（如 61s→"约1分"），其余不推
  → 倒计时结束 → 后端自动重发 → notice done → 位置 2 清除
  → 用户点"中断" → 走现有 cancel → 任务 CANCELLED
```

### 10.2 视觉规范（对齐现有设计系统）

- **位置**：TaskInfoBar 第一行位置 2（动态状态固定位），不新开弹窗/浮层（弹窗打断感太强，不符合"可后台等待"的语义）。
- **图标**：`SyncOutlined spin`（与 retrying 同族，表示"正在等待/恢复"），不用 ⏸️（pause 语义已被 HITL 占用，避免混淆）。
- **颜色**：`Colors.WARNING`（#AD6800，与 retrying 同色系，表示"非故障、可自愈"）。
- **文案格式**：`模型限速，{人类可读时长}后恢复（429·延时）[中断]`——时长**由后端计算**（自适应单位：<60s 显秒 / <3600s 显分秒 / ≥3600s 显时分，双单位精度，整单位不补零），随 SSE notice 帧下发，前端**零逻辑纯展示**；超 120s 前缀加 `⚠ 等待较长`；"中断"为文本按钮（`StopOutlined` + "中断"），样式对齐现有 SubmitBar 的取消按钮。
- **倒计时驱动**：后端退避等待期间，仅跨越单位边界时按需推送 notice update（61s→60s 由"1分1秒"变"1分"），其余时刻不推（前端"新覆盖旧"规则自动刷新）；倒计时到 0 或收到 notice done 即清除。前端不设本地 timer、不新增格式化函数。
- **事件列表**：notice 帧进事件时间轴，kind=`rate_limit_wait`，phase=start/done，图标 `ReloadOutlined`（与 retrying 同图标族，表示恢复动作）。

### 10.3 状态机

| 状态 | 触发 | 位置 2 显示 | 用户操作 |
|---|---|---|---|
| 等待中 | 收到 pause 帧 | ⏳ 模型限速，30秒后恢复（429·延时）[中断] | 可点中断 |
| 长等待 | pause_seconds > 120s | ⏳ ⚠ 等待较长，模型限速，约2分5秒后恢复（429·延时）[中断] | 可点中断 |
| 倒计时递减 | 后端跨单位边界推 notice update | ⏳ 模型限速，约1分后恢复（429·延时）[中断] | 可点中断 |
| 自动恢复 | 倒计时到 0 / 后端重发成功 | notice done → 清除 | — |
| 用户中断 | 点"中断" | → 走 cancel → 位置 2 变 ⛔ 已取消 | 任务终态 |

### 10.4 边界情况

- **pause_seconds > 120s**：后端封顶 120s 并提示"等待较长，可中断"（文案前缀加"⚠"）。
- **pause 期间又收到新 429**：位置 2 新覆盖旧（现有"新覆盖旧无优先级"规则天然支持）。
- **任务切换/会话切换**：`useChatCallbacks` 的 `resetBuffers` 会清 isPaused/暂停计数，pause 状态随任务生命周期自然消亡，无需额外清理。

```python
    def mark(self, model_id: str, is_quota: bool = False) -> None:
        """L1+L2 重试耗尽后标记冷却"""
        entry = self._table.get(model_id, {"hits": 0})
        entry["hits"] += 1
        if is_quota:
            cooldown = MODEL_QUOTA_COOLDOWN
        else:
            idx = min(entry["hits"] - 1, len(MODEL_COOLDOWN_STEPS) - 1)
            cooldown = MODEL_COOLDOWN_STEPS[idx]
        entry["cooldown_until"] = time.time() + cooldown
        entry["is_quota"] = is_quota
        self._table[model_id] = entry
        logger.info(f"[ModelCooldown] {model_id} 标记冷却 {cooldown}s (hits={entry['hits']}, quota={is_quota})")

    def delay_for(self, model_id: str) -> float:
        """剩余冷却秒数；0 = 无冷却"""
        entry = self._table.get(model_id)
        if not entry:
            return 0.0
        remaining = entry["cooldown_until"] - time.time()
        return max(0.0, remaining)

    def clear(self, model_id: str) -> None:
        """成功调用后清零"""
        if model_id in self._table:
            logger.info(f"[ModelCooldown] {model_id} 成功调用，清除冷却")
            del self._table[model_id]


__all__ = ["ModelCooldownRegistry"]
```
