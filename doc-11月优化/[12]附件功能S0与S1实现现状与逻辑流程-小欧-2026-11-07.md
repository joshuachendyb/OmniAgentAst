## 一、口径说明（重要）

**"插件"在本项目对应"附件功能"。** 依据：

1. 全项目代码中"插件/plugin"一词几乎不出现（仅 `monitoring/agent_telemetry.py:32` 一处"未来插件"设想注释，非已实现模块）。
2. 全项目**唯一带明确 S0/S1 分级标记且代码已落地**的功能域是**附件功能**（`app/attachments/`、`app/api/v1/attachments.py`、前端 `features/refs/`），分级定义见设计文档 [10]。
3. S0 在 [10] 中即命名为"**基础通道**"，S1 为"文本正文"——与"基础性的功能"表述一致。

> 工具（`app/tools/`）系统虽是插件式架构（注册/注入/searchtool 动态加载），但**无 S0/S1 分级标记**，不在本文范围。若所指为工具系统，请告知补写。

**阶段轴是"附件类型"**（非功能模块）：S0 一次铺完与类型无关的全部地基，之后每加一种类型是一个独立可验收阶段。

| 阶段 | 目标 | 状态 |
|---|---|---|
| **S0** | 基础通道：任何类型都能传/落盘/引用/发送（AI 收到档案卡） | **已实现** |
| **S1** | 文本正文（≤256KB 全文 / 超限档案头） | **已实现** |
| S2 图片视觉 / S3 PDF·Office / S4 视频 | 后续类型阶段 | 未实现（`extract.py` 仅留占位卡片） |

## 二、S0 基础通道 — 已实现范围

### 2.1 数据层：3 张表（`db/db_initializer.py`）

| 表 | 职责 | 关键约束 |
|---|---|---|
| `attachments` | 附件登记（会话级素材库） | `UNIQUE(session_id, sha256)` 并发去重；`session_id` 外键级联删；`stored_path` 绝对路径真源；正文不落库（每轮由 extract 生成） |
| `material_packs` | 素材包（只存清单不复制文件） | `name` 唯一（COLLATE NOCASE）；`group_name` 空串=未分组 |
| `material_pack_items` | 素材包条目 | `pack_id` 外键级联删；存量库幂等补 `kind`/`attachment_id` 两列（投喂时按 id 恢复附件语义） |

### 2.2 API 层：8 个端点（`api/v1/attachments.py` 薄壳）

`upload` / `list` / `get` / `delete` / `text` / `collect` / `local-capability` / `import-local`。
薄壳只做参数解包与错误转译，业务全在服务层；挂载走 `main.py` 的 `_mount()`（自动注入 token 鉴权）。

### 2.3 服务层：落盘与登记（`attachments/attachment_service.py`）

- **`save_bytes`** — 落盘 + 登记**唯一实现**（上传 / 存为附件 / 本地导入三通道共用）：
  - 白名单校验：`_ALLOWED_SUFFIXES` = extract 五分类词典组合（类型轴唯一真源，免两份名单漂移）。纯 binary（.zip/.exe）一律 415。
  - 单文件限：图片 10MB / 其他 20MB；会话总量 200MB。
  - 去重：先查 `sha256`，命中直接回旧行；写库 `INSERT OR IGNORE` + 回查，并发同 sha 时**先删本次写出的孤儿文件**再回查。
  - 文件名 sanitize：去目录段/非法字符/Windows 保留名/结尾点（保留开头点以支持 .env/.dockerfile）。
  - 失败即 `stored.unlink` 清理半成品，不留垃圾。
- **`save_upload`** — HTTP 入口，`read(limit+1)` 先限后读（图片 10MB+1 / 其他 20MB+1，超限在读入阶段即拒），磁盘 IO 经 `asyncio.to_thread` 卸载。
- **`ensure_session_attachment_dir`** — 附件目录唯一解析（默认工作区 + `attachments/` 子目录；无默认行时 `reconcile_session_workspaces` 幂等补建，不猜目录名）。
- **`get_attachment_scoped`** — 会话归属校验（B-03）：不匹配视同不存在，API 端点与 resolver 注入共用此单一口径。
- **`delete_attachment`** — `purge=True` 时先删磁盘成功才删 DB 行，并级联清 `material_pack_items` 同 `stored_path` 条目。
- **`read_inject_text`** — 预览端点数据源，与 resolver 同一条生成路径（不产生第二套口径）。

### 2.4 存储全景：存什么、存在哪（三通道落盘位置）

**只存两样，无第三样。**

| 存储物 | 位置 | 内容 |
|---|---|---|
| 文件本体 | 磁盘 `{会话默认工作区}/attachments/` | 原始字节完整副本；不转码、不生成缩略图、不生成提取文本文件 |
| 登记记录 | SQLite `chat.db` → `attachments` 表 | 1 行 13 列（`_COLS`）：`id / session_id / original_name / stored_path / mime / size / sha256 / kind / extract_status / extract_chars / source_path / source_task_id / created_at` |

注入给模型的正文**不落盘**：每轮由 `extract.build_inject_text(att)` 从原文件按需实时生成（正文与文件本体不双存，避免两份内容不同步）。

**落盘路径公式**（`ensure_session_attachment_dir` + `_build_default_workspace_dir` + `get_project_root`）：

```
{workspace.project_root 或 Path.home()}          ← get_project_root(): 配置优先, 未配置回落用户主目录
  └─ {YYYYMMDD-HHMMSS}-{session_id 前 4 位}      ← 会话默认工作区(chat_session_workspaces.is_default=1)
       └─ attachments/                            ← _ATTACH_SUBDIR, 附件唯一落盘子目录
            └─ {YYYYMMDD-HHMMSS}-{sha256 前 8 位}-{sanitize 后原名}
```

> 现场对账：当前 `workspace.project_root` 指向 `E:\test_dir`，其下可见 `20261104-122151-46da` 这类目录（`20261104-122151` = 工作区创建时刻，`46da` = 会话标识前 4 位），即上述规则的产物；该目录内的 `attachments/` 就是本会话附件的落盘处。

**"本机 / 非本机"不是两套存储，是两条入口通道。** 三条入口最终都汇入同一 `save_bytes()`，落盘目标完全一致：

| 入口 | 端点 | 同机判定 | 文件来源 | 是否复制 |
|---|---|---|---|---|
| 上传 | `POST /attachments/upload` | 无 | 浏览器经 HTTP 传入字节 | 必然复制到工作区 |
| 本机导入 | `POST /attachments/import-local` | 有（`is_local_request` 按真实客户端 IP 判定，跨机 403） | 后端直读本机绝对路径文件 | **仍复制**（`read_bytes` → `save_bytes`）；`source_path` 仅记来源供溯源，非引用 |
| 存为附件 | `POST /attachments/collect` | 无 | 任务产物 | 工作区内 `referenced` 不复制 / 工作区外 `copied` |

> 推论：非本机客户端上传的文件，落在**后端进程所在机器**的项目根下该会话工作区的 `attachments/` 内——与同机上传同一位置。非本机唯一受限的是「从本机导入」（后端服务端读不到客户端本机磁盘）。

**磁盘生命周期**：`delete_attachment(purge=True)` 才删文件本体，默认只删记录留档；删除会话（`session_service.delete_session`）级联删 `attachments` 表行，但**不删磁盘目录**（与工作区目录同策略，代码注释明确"不删物理目录，用户自行清理"）。

### 2.5 分类与档案卡（`attachments/extract.py`）

- **`classify`** — 五分类唯一实现：`image` / `video` / `richdoc` / `text` / `binary`。扩展名唯一真源优先（不可伪造），mime 仅无扩展名时辅助，size 用于空文件判 binary。
- **五张档案卡**（S0 全部走卡片，任何类型上传后都能发送）：
  - `_image_card` / `_video_card` / `_richdoc_card` / `_binary_card` / `_text_card`——均输出 `[附件档案卡·X]` + head（文件名/路径/类型/大小）+ 说明文案。
- **`build_inject_text`** — 注入文本唯一产生点，按 `kind` 分派（S0 全部落卡片；S1 起 text 分支换 `_text_body`）。

### 2.6 注入真源（`services/refs/resolver.py`）

- **`_read_attachment`** — 按 `attachment_id` 查表（`get_attachment_scoped` 含会话归属校验）+ `extract.build_inject_text` 生成注入文本。失败 reason：`attachment_missing`（不存在/越会话）/ `attachment_failed`（读盘解析异常），均不阻断其余引用。
- **`_read_one`** — 首行分流 `kind=attachment` → `await asyncio.to_thread(_read_attachment,...)`（DB 查表同步阻塞 IO 卸载出事件循环）。
- 附件不参与行级读取/预算压缩（按 id 查表，不受 path 越界影响）。

### 2.7 产物「存为附件」（`attachments/collect.py`）

判定口径用**会话工作区表**（非 ContextVar 快照，后者 HTTP 期恒 None 会误判）。两种结果：
- `referenced`：产物已在会话工作区 → 不复制，直接回引用路径（前端走 quoteFile）。
- `copied`：产物在工作区外 → 复制进 `{默认工作区}/attachments/` 并登记，透传 `source_task_id` 溯源。

### 2.8 同机本地导入（`attachments/local_import.py`）

`local-capability`（探测是否同机启用）+ `import-local`（后端浏览+读盘+复用 `save_bytes`），与 `upload` 构成双通道。

### 2.9 前端（`frontend/src/features/refs/`）

- **`uploadAttachment.ts`** — 「把文件送进引用区」**唯一实现**：按钮选择/拖拽/粘贴截图 + ③存为附件全部走此；前置闸门（单批 ≤10、图片 ≤10MB、其他 ≤20MB）只此一份；先选文件选中后才建会话；类型白名单只留后端；F-01 上传前容量预检（occupancy + 本批 > MAX_REFS 整批拒绝）根除服务端孤儿记录。
- chip / 入队 / `quoteFile` 等配套（`store.ts` / `quote.ts` / `useComposerRefs.ts`）。

### 2.10 会话资产属性与资产管理能力（后端就绪 / 前端未接入）

**"会话资产"落在数据模型上**，非口头定性：`attachments.session_id` 为外键、`UNIQUE(session_id, sha256)` 按会话隔离去重、删会话级联删行。

后端**已实现**的会话维度资产管理能力（4 项，均经 `get_attachment_scoped` 做会话归属校验，跨会话视同不存在）：

| 能力 | 端点 | 服务层 | 说明 |
|---|---|---|---|
| 列出本会话附件 | `GET /attachments?session_id=` | `list_attachments` | 按 `created_at` 倒序；会话不存在返回空列表（B-04） |
| 查看单条详情 | `GET /attachments/id/{id}?session_id=` | `get_attachment_scoped` | 越会话返回 NOT_FOUND（B-03） |
| 查看注入正文预览 | `GET /attachments/id/{id}/text?session_id=` | `read_inject_text` | 与 resolver 同一条生成路径，不产生第二套口径 |
| 删除附件 | `DELETE /attachments/id/{id}?session_id=&purge=` | `delete_attachment` | `purge=false` 删记录留档 / `purge=true` 删文件 + 级联清素材包条目（B-02） |

**前端现状（实测）**：`services/api/attachment.api.ts` 已封装 `upload / list / get / text / delete / collect / localCapability / importLocal` 八个方法与后端端点一一对应；但全仓检索 `attachmentApi.list` 与 `attachmentApi.delete` **零调用点** —— UI 无「会话附件列表 / 删除」面板，当前实际使用的只有 `upload / get / collect / localCapability / importLocal`（其中 `get` 仅用于 `probe.ts` 发送前存在性预检，非列表展示）。

> 结论：**"会话内附件可查、可看、可删"后端已是完成态，缺的只是前端入口**；接入时后端无需任何改动。

## 三、S1 文本正文 — 已实现范围

S1 只替换 `extract.py` 中 text 分支的**一个函数**，分派结构不动（分阶段设计意图）：

1. **`classify` 补文本分支**：`TEXT_SUFFIXES`（.txt/.md/.py/.json/.csv/.yaml 等约 60 种）命中即判 `text`。此分支必须在"有扩展名但不在白名单 → binary"之前，否则文本会落 binary、文本档卡永远用不上。
2. **`_text_body` 替换 `_text_card`**（`build_inject_text` 中 `kind == "text"` 分支）：
   - `size ≤ 256KB`（`TEXT_INLINE_MAX`）→ **全文注入**：`[附件正文·文本]` + head + 正文。编码 utf-8 → gbk → latin-1 逐个试，失败 replace 兜底。
   - `size > 256KB` → **档案头**：`[附件档案头]` + head + 前 40 行（`ARCHIVE_HEAD_LINES`）+ 总行数（单遍扫描，不整篇入 prompt）+ 提示模型凭 path 用文件工具深读。
3. **resolver B-08 配套**：`_read_attachment` 中仅 `kind == "text"` **跳过 `clip_text` 二次截断**——因 `_text_body` 已按 256KB 做尺寸控制，再截会裁掉本应全文注入的 200KB 文本；非 text 卡片（远小于 `read_max_bytes`）保持 clip 兜底。

## 四、端到端逻辑流程

### 4.1 上传落盘链路（S0）

```
前端 uploadAttachment.ts（前置闸门：单批≤10 / 图片≤10MB / 其他≤20MB / 容量预检）
  → POST /api/v1/attachments/upload  (session_id, file)
  → attachments.save_upload
      read(limit+1) 先限后读 → asyncio.to_thread 卸载
  → attachment_service.save_bytes   ← 落盘+登记唯一实现
      ① 白名单校验(_ALLOWED_SUFFIXES)  ② 单文件限(图片10M/其他20M)
      ③ sha256 去重(命中回旧行)        ④ 会话总量限(200M)
      ⑤ ensure_session_attachment_dir(默认工作区+attachments/)
      ⑥ write_bytes 落盘 → extract.classify 五分类
      ⑦ INSERT OR IGNORE 登记 + 回查(并发孤儿文件先删)
      失败 → stored.unlink 清半成品
  → 返回附件记录(含项目根相对 path)
  → 前端构造 attachment ref 入引用区(chip)
```

### 4.2 发送注入链路（S0 + S1）

```
用户发送消息(引用区含附件 ref)
  → services/refs/resolver.resolve_refs
  → _read_one：kind==attachment 分流
  → await asyncio.to_thread(_read_attachment)   ← DB 查表卸载出事件循环
      ① get_attachment_scoped(id, session_id) 会话归属校验(不匹配→attachment_missing)
      ② extract.build_inject_text(att)
           kind==text → _text_body        ← S1
             ≤256KB → [附件正文·文本] 全文(utf-8→gbk→latin-1)
             >256KB → [附件档案头] 前40行+总行数(单遍扫描)
           kind==image/video/richdoc/binary → 各档案卡  ← S0
      ③ 仅 text 跳过 clip_text 二次截断(B-08)；非 text 卡片 clip 兜底
  → ResolvedRef(content=注入文本) → 拼入 LLM 上下文
```

### 4.3 产物「存为附件」链路（S0）

```
任务产物概览 → POST /attachments/collect (session_id, source_path, task_id?)
  → collect.collect_artifact
      用会话工作区表判产物是否在工作区
        在 → referenced(不复制, 回引用路径, 前端 quoteFile)
        外 → copied(复制进 attachments/ + save_bytes 登记, 透传 source_task_id 溯源)
```

## 六、一处与设计蓝图的差异提示

设计文档 [10] 的 S0 范围含"前端上传三入口 + chip + 预检 + D1"。本地实测前端 `features/refs/` 已落地 `uploadAttachment.ts`（唯一实现，含三入口与容量预检）及配套 store/quote；但 [10] v9 曾记录"附件功能整体未实现、[10] 是纯设计"，此后 v10~v13 经多轮三堂会审推进落地。**本文档只描述代码现状，S0/S1 核心链路（后端 8 端点 + 服务层 + 分类档案卡 + resolver 注入 + S1 文本正文）均已实现**；前端 UI 细节（chip 样式、D1 等）如需逐项核对，建议以 [10] v13 第六章验收清单为基准另行比对。
