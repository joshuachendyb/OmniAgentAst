## 第 1 章 立项定位

### 1.1 从 [46] P2b 继承什么、修正什么

[46] 文档 2.4 节把 P2b 定义为"任务列表接口按当前 UI 形态对齐 + 写侧持久化地基"。本立项继承该目标，但**修正方案形态**：

| 项 | [46] 2.4 原方案 | 本立项修正 | 理由 |
|---|---|---|---|
| 存储形态 | 新建 `chat_task_ledger` / `chat_task_tool_paths` 两张表 | **`chat_tasks` 加 `ref_ledger_json` / `tool_paths_json` 两个 JSON 快照列** | 当前 UI 只有"按任务展示台账/推荐行"的点查需求，无跨任务聚合查询——按 KISS-DIRECT + YAGNI，快照列零 JOIN、零额外查询、无 N+1，改动面最小；将来出现跨任务查询需求再升级为新表（列数据可直接迁移） |
| 字段命名 | 渲染要素字段名为 `ledger` / `tool_paths` | **统一为 `ref_ledger` / `tool_paths`**（接口、前端类型、store 读取三处一致） | 46 正文用 `ledger`，本立项改用语义更准的 `ref_ledger`（引用台账）；两文档并存时以本立项为准，避免实施时字段错配 |
| 写侧落点 | "任务收尾时台账快照落库 + 工具执行时路径落库"（两处写） | **两列各自写、互不依赖**：`tool_paths` 由后端在 finally 从 steps 派生经 `update_task` 落列；`ref_ledger` 由前端经扩展的 process-events 端点直接写列 | `tool_paths` 数据源在 `chat_task_steps.step_json`（前端 roundHits 现从 `action.tools[].params.path` 实时算），收尾时从 `current_execution_steps` 派生去重即可；`ref_ledger` 权威源在前端 store，只能由前端上交。两列分属不同写者，各自独立写、互不覆盖（`update_task` 缺省不覆盖 + 端点只写自身列），无时序竞态 |
| ledger 数据来源 | "任务收尾时台账快照落库"（后端无源） | **前端在任务 final 帧经扩展的 process-events 端点 POST 上交，端点直接写 `ref_ledger_json` 列** | 后端无 SSE refs 入口，台账唯一权威源在前端 `chatStreamStore.sentRefLedger`（`start` 帧时由 `pushSentRefs` 写入，wire 形态含 label/path/lineRange/taskId/ts）。不采用"内存暂存 + finally 汇合"——前端 POST 发生在收到 final 帧时（任务已终态），直接写列即可，避免汇合时序竞态 |

### 1.2 目标

任务列表接口 `/sessions/{id}/tasks` 一次返回渲染全部要素后，前端 TaskListPanel 在冷启动/刷新后（`chatStreamStore` 内存态为空时）**新任务**的台账行与推荐行不再缺失；数据源从"前端内存态 store 拼图"改为"任务表快照列单一真源"。存量任务因无持久化台账源，台账行为空（自上线累积）、推荐行由回填的 tool_paths 正常算出——属客观数据边界（见 3.2）。

## 第 2 章 数据契约设计

### 2.1 chat_tasks 新增两列（ALTER TABLE，幂等）

| 列 | 类型 | 默认 | 内容 |
|---|---|---|---|
| `ref_ledger_json` | TEXT | `'[]'` | 本任务引用台账快照：`[{label, path, lineRange?:{start,end}, ts}]`（wire 形态，前端上交原样，**只存路径不存正文**） |
| `tool_paths_json` | TEXT | `'[]'` | 本任务工具触达的相对 posix 路径**去重保序**数组：`["backend/app/x.py", ...]`（与 recentFiles.path 同口径，供前端计数推荐） |

> **设计约束（对齐 SentRefLedgerEntry 契约）**：快照只存路径不存正文——点台账 chip 时现场重读文件，恢复的是"引用意图"而不是旧快照。`taskId` 不落列（冗余，行本身即任务）。`ts` 保留用于台账条目的时序展示。
>
> **为什么不用新表**：两要素都是任务 1:N 附属物，读取永远以 task_id 为主键点查、无跨任务过滤/聚合需求（YAGNI）；快照列让 `list_session_tasks` 主 SELECT 直接带出，零额外查询。若将来出现"某文件被哪些任务引用过"的跨任务查询，届时再以两列数据迁移建表（数据无损）。

### 2.2 接口契约变化

`GET /sessions/{id}/tasks` 返回的 `tasks[]` 每项新增两字段（与既有字段平级，直接由 `list_session_tasks` SELECT 透出）：

```ts
interface SessionTaskItem {
  // ...既有字段...
  /** [46b] 引用台账快照(wire 形态, 冷启动不缺失; 上线前存量任务为 []) */
  ref_ledger?: Array<{ label: string; path: string; lineRange?: { start: number; end: number }; ts: number }>;
  /** [46b] 本任务工具触达的相对 posix 路径(去重), 推荐行 roundHits 依据 */
  tool_paths?: string[];
}
```

### 2.3 写侧数据流（两列各自写、互不依赖）

```
tool_paths(后端写):
  任务终态(agent_runner finally)
    → _finalize_task_db(conn)
        ├─ tool_paths = derive_tool_paths_from_steps(current_execution_steps)   # 从 steps 派生(后端权威)
        └─ update_task(..., tool_paths=...)   # 只写 tool_paths_json 列, 缺省字段不覆盖其他列

ref_ledger(前端写):
  前端 TaskInfoBar(final 帧)
    → 收集 chatStreamStore.getSentRefLedger(sessionId, taskId)
    → 随 process-events 回填捎带 ref_ledger 字段 POST /chat/execution/task/{taskId}/process-events
        → 端点 save_process_events(events) + 直接 UPDATE ref_ledger_json 列
```

> **写侧职责分工**：tool_paths 由**后端**从 `current_execution_steps` 派生（steps 是后端权威数据源，与现网 roundHits 同源同口径），在 finally 经 `update_task` 写 `tool_paths_json`；ref_ledger 由**前端**上交（台账唯一权威源在前端 store，后端无 SSE refs 入口），经扩展的 process-events 端点直写 `ref_ledger_json`。两列分属不同写者、各自独立写、互不覆盖（`update_task` 缺省字段不覆盖 + 端点只写自身列），无"内存暂存 + finally 汇合"的时序竞态。

+                out.append(rel)

### 3.2 阶段 2：存量回填（仅 tool_paths）

> **回填边界（已核实的客观数据边界）**：经全仓核实，两列的可回填性不同——
> - **`tool_paths` 可离线回填**：数据源 `chat_task_steps.step_json` 是后端持久化字段（`storage.py:324-354`），可靠。
> - **`ref_ledger` 不可从 DB 回填**：`chat_user_message.content` 只存用户原话（`message_service.py:256`），`<引用资料>` 块由 `build_user_turn_text` 拼出后仅进入 LLM prompt、不落任何 `chat_*` 表；`refs_notice` 首发路径是纯 `yield`、不落库（`stream_orchestrator.py:1005`）。唯一残留是 `conv_hist_*.jsonl` 诊断文件（best-effort、可能被 GC、非 DB），不可作为回填源。因此**存量会话的台账不回填，自上线起由前端上交累积**——这是数据客观边界，冷启动遇存量任务时台账行为空（推荐行不受影响，因 tool_paths 已回填）。

```python
"""[46b] P2b 存量回填: 从 chat_task_steps 离线派生 tool_paths_json — 小欧 2026-11-17
用法: python -m app.services.chat.backfill_tool_paths [--db PATH] [--apply]
  默认 dry-run(只统计不写); --apply 实际写入。
数据源: chat_task_steps.step_json 的 action.tools[].params.path(后端持久化, 可靠)。
只写 chat_tasks.tool_paths_json; 幂等(重跑一致), 不触碰其他列(尤其不碰 ref_ledger_json)。"""
import json, sqlite3, sys
from app.services.chat.storage import derive_tool_paths_from_steps  # 复用派生函数(DRY)

def backfill(db_path: str, apply: bool = False) -> dict:
    conn = sqlite3.connect(db_path); conn.row_factory = sqlite3.Row
    stats = {"tasks_scanned": 0, "tool_paths_updated": 0}
    # 按任务聚合 steps(同一任务多步, 逐步扫描 action.tools[].params.path)
    task_steps: dict = {}
    for r in conn.execute("SELECT task_id, step_json FROM chat_task_steps ORDER BY task_id, step_index"):
        task_steps.setdefault(r["task_id"], []).append(json.loads(r["step_json"]))
    conn2 = sqlite3.connect(db_path) if apply else None
    for task_id, steps in task_steps.items():
        stats["tasks_scanned"] += 1
        paths = derive_tool_paths_from_steps(steps)   # 归一与在线路径一致(项目根由 browse.root_relative 内部读 config)
        if not paths:
            continue
        stats["paths_total"] = stats.get("paths_total", 0) + len(paths)
        if apply:
            conn2.execute("UPDATE chat_tasks SET tool_paths_json=? WHERE task_id=?",
                          (json.dumps(paths, ensure_ascii=False), task_id))
            stats["tool_paths_updated"] += 1
    if apply:
        conn2.commit(); conn2.close()
    conn.close()
    return stats

if __name__ == "__main__":
    apply = "--apply" in sys.argv
    print(backfill(sys.argv[sys.argv.index("--db") + 1] if "--db" in sys.argv else "chat.db", apply))
```

> **说明**：本脚本只回填 `tool_paths`（可靠数据源）。`ref_ledger` 不回填的原因见本节开头边界说明——历史台账数据从未持久化到 DB，强行"解析重建"会产出全空结果，属无效代码，故删除。存量任务冷启动时推荐行由回填的 `tool_paths` 正常算出，台账行为空是可接受的客观边界。dry-run 先对账、幂等可重跑。
