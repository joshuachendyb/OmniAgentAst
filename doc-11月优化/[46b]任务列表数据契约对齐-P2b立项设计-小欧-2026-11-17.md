## 第 1 章 立项定位

### 1.1 从 [46] P2b 继承什么、修正什么

[46] 文档 2.4 节把 P2b 定义为"任务列表接口按当前 UI 形态对齐 + 写侧持久化地基"。本立项继承该目标，但**修正方案形态**：

| 项 | [46] 2.4 原方案 | 本立项修正 | 理由 |
|---|---|---|---|
| 存储形态 | 新建 `chat_task_ledger` / `chat_task_tool_paths` 两张表 | **`chat_tasks` 加 `ref_ledger_json` / `tool_paths_json` 两个 JSON 快照列** | 当前 UI 只有"按任务展示台账/推荐行"的点查需求，无跨任务聚合查询——按 KISS-DIRECT + YAGNI，快照列零 JOIN、零额外查询、无 N+1，改动面最小；将来出现跨任务查询需求再升级为新表（列数据可直接迁移） |
| 写侧落点 | "任务收尾时台账快照落库 + 工具执行时路径落库"（两处写） | **任务收尾时两列一次性快照写入（同一处写）** | 工具触达路径在 `chat_task_steps.step_json` 已有原始数据（前端 roundHits 现从 steps 的 `action` 步 `tools[].params.path` 实时算），收尾时从 `current_execution_steps` 派生去重即可，无需在工具执行热路径新增写操作 |
| ledger 数据来源 | "任务收尾时台账快照落库"（后端无源） | **前端在任务收尾时经既有 `process_events` 回填通道捎带 POST** | 后端无 SSE refs 入口，台账的唯一权威源在前端 `chatStreamStore.sentRefLedger`（`start` 帧时由 `pushSentRefs` 写入，wire 形态含 label/path/lineRange/taskId/ts）。后端凭空生成不了台账，只能由前端上交——与 `process_events` 回填同一模式（前端 POST → 后端 `update_task` 落列） |

### 1.2 目标

任务列表接口 `/sessions/{id}/tasks` 一次返回渲染全部要素后，前端 TaskListPanel 在冷启动/刷新后（`chatStreamStore` 内存态为空时）台账行与推荐行**不再缺失**；台账/推荐行的数据源从"前端内存态 store 拼图"改为"任务表快照列单一真源"。

### 1.3 现状事实核查（2026-11-17，对照基线代码）

| 事实 | 出处 | 结论 |
|---|---|---|
| `chat_tasks` 表无台账/工具路径列 | `db_initializer.py:160-186` | 需加 2 列 |
| `update_task` 已支持 `artifacts`/`process_events` 等 JSON 列的通用 SET 写入 | `storage.py:498-537` | 复用既有模式，加两个字段名进白名单即可 |
| 任务收尾 `_finalize_task_db(conn)` 在 `agent_runner.py:845-887` 统一调用 `update_task` | `agent_runner.py:845` | **唯一写侧落点**：在此处从 `current_execution_steps` 派生 tool_paths、接收前端捎带的 ref_ledger 一并写入 |
| 前端台账唯一权威源 = `chatStreamStore.sentRefLedger`（SentRefLedgerEntry：`{label,path,lineRange?,taskId,ts}`，新者前 ≤50 条） | `backupTypes.ts:73-79`、`chatStreamStore.ts:1171-1193` | 前端收尾上交 `getSentRefLedger(sessionId, taskId)` |
| roundHits 现从 `steps` 的 `action` 步 `tools[].params.path` 经 `toRelativePath` 归一后计数，与 recentFiles 同口径（相对 posix 路径） | `TaskListPanel.tsx:503-525` | 后端派生 tool_paths 必须**同口径归一**（绝对路径→项目根相对 posix），否则前端 recommend 键对不上恒 miss |

## 第 2 章 数据契约设计

### 2.1 chat_tasks 新增两列（ALTER TABLE，幂等）

| 列 | 类型 | 默认 | 内容 |
|---|---|---|---|
| `ref_ledger_json` | TEXT | `'[]'` | 本任务引用台账快照：`[{label, path, lineRange?:{start,end}, ts}]`（wire 形态，前端上交原样，**只存路径不存正文**） |
| `tool_paths_json` | TEXT | `'[]'` | 本任务工具触达的相对 posix 路径**去重保序**数组：`["backend/app/x.py", ...]`（与 recentFiles.path 同口径，供前端计数推荐） |

> **设计约束（对齐 SentRefLedgerEntry 契约）**：快照只存路径不存正文——点台账 chip 时现场重读文件，恢复的是"引用意图"而不是旧快照。`taskId` 不落列（冗余，行本身即任务）。`ts` 保留用于台账条目的时序展示。
>
> **为什么不用新表**：两要素都是任务 1:N 附属物，读取永远以 task_id 为主键点查、无跨任务过滤/聚合需求（YAGNI）；快照列让 `list_session_tasks` 主 SELECT 直接带出，零额外查询。若将来出现"某文件被哪些任务引用过"的跨任务查询，届时再以两列数据迁移建表（数据无损）。

### 2.2 接口契约变化

`GET /sessions/{id}/tasks` 返回的 `tasks[]` 每项新增两字段（与既有字段平级，直接由 `list_session_tasks` SELECT 透出）：

```ts
interface SessionTaskItem {
  // ...既有字段...
  /** [46b] 引用台账快照(wire 形态, 冷启动不缺失; 上线前存量任务为 []) */
  ref_ledger?: Array<{ label: string; path: string; lineRange?: { start: number; end: number }; ts: number }>;
  /** [46b] 本任务工具触达的相对 posix 路径(去重), 推荐行 roundHits 依据 */
  tool_paths?: string[];
}
```

### 2.3 写侧数据流（收尾时一次性快照）

```
任务终态(agent_runner finally)
  → _finalize_task_db(conn)
      ├─ tool_paths = derive_tool_paths(current_execution_steps, root)   # 从 steps 派生(后端权威)
      ├─ ref_ledger = 前端 POST 捎带(经 process_events 同一回填通道的扩展字段)  # 前端权威
      └─ update_task(..., tool_paths=..., ref_ledger=...)
前端 TaskListPanel / useTaskInfo
  → 任务 final 时收集 chatStreamStore.getSentRefLedger(sessionId, taskId)
  → 随 process_events 回填请求捎带 ref_ledger 字段 POST /tasks/{id}/process-events
```

> **写侧职责分工**：tool_paths 由**后端**从 `current_execution_steps` 派生（steps 是后端权威数据源，与现网 roundHits 同源同口径）；ref_ledger 由**前端**上交（台账唯一权威源在前端 store，后端无 SSE refs 入口）。两个来源在 `_finalize_task_db` 汇合，一次 `update_task` 落库。

```diff
+def derive_tool_paths_from_steps(steps: list, root: Optional[str]) -> list:
+    """[46b] P2b 小欧 2026-11-17: 从 execution_steps 派生工具触达的相对 posix 路径(去重保序)。
+    与前端 roundHits 同口径: 只取 type=action 步的 tools[].params.path, 经 browse.root_relative
+    归一为项目根相对路径(与 recentFiles.path 同键), 根外路径跳过。
+    收尾时调用一次, 替代前端 store 实时计算, 使推荐行冷启动不缺失。"""
+    out: list = []
+    seen: set = set()
+    for s in steps or []:
+        if not isinstance(s, dict) or s.get("type") != "action":
+            continue
+        for tool in s.get("tools") or []:
+            raw = tool.get("params", {}).get("path") if isinstance(tool, dict) else None
+            if not raw or not isinstance(raw, str):
+                continue
+            rel = browse.root_relative(raw)
+            if rel and rel not in seen:
+                seen.add(rel)
+                out.append(rel)
+    return out
```

### 3.2 阶段 2：存量回填（tool_paths 离线派生）

#### 文件 ⑤：`backend/app/services/chat/migrate_steps.py`（既有迁移脚本同目录，新增独立脚本 `backfill_tool_paths.py`）

```python
"""[46b] P2b 存量回填: 从 chat_task_steps 离线扫描派生 tool_paths_json — 小欧 2026-11-17
用法: python -m app.services.chat.backfill_tool_paths [--apply]
  默认 dry-run(只统计不写); --apply 实际写入。
只读 chat_task_steps.step_json, 只写 chat_tasks.tool_paths_json;
幂等(重跑结果一致), 不触碰其他列, 可在服务运行外执行(与 _ensure_column 幂等补列先后无依赖)。"""
import json, sqlite3, sys
from app.services.chat.storage import derive_tool_paths_from_steps  # 复用同一派生函数(DRY)

def backfill(db_path: str, apply: bool = False) -> dict:
    conn = sqlite3.connect(db_path)
    conn.row_factory = sqlite3.Row
    stats = {"tasks_scanned": 0, "tasks_updated": 0, "paths_total": 0}
    # 按任务聚合 steps(同一任务多步, 逐步扫描 action.tools[].params.path)
    task_steps: dict = {}
    for r in conn.execute(
            "SELECT task_id, step_json FROM chat_task_steps ORDER BY task_id, step_index"):
        d = json.loads(r["step_json"])
        task_steps.setdefault(r["task_id"], []).append(d)
    conn2 = sqlite3.connect(db_path) if apply else None
    for task_id, steps in task_steps.items():
        stats["tasks_scanned"] += 1
        paths = derive_tool_paths_from_steps(steps, None)   # root 归一与在线路径一致
        if not paths:
            continue
        stats["paths_total"] += len(paths)
        if apply:
            conn2.execute("UPDATE chat_tasks SET tool_paths_json=? WHERE task_id=?",
                          (json.dumps(paths, ensure_ascii=False), task_id))
            stats["tasks_updated"] += 1
    if apply:
        conn2.commit(); conn2.close()
    conn.close()
    return stats

if __name__ == "__main__":
    apply = "--apply" in sys.argv
    print(backfill(sys.argv[sys.argv.index("--db") + 1] if "--db" in sys.argv else "chat.db", apply))
```

## 第 4 章 实施顺序与验收

### 4.1 实施顺序

```
阶段1 写侧地基(文件①②③④: 建列→派生函数→收尾落库→回填接口扩展)
  → 后端单测(derive 归一口径 / update_task 两字段幂等 / 收尾汇合)
  → 上线即开始累积新任务的 ref_ledger/tool_paths(对老代码零风险, 老读方不读新列)
阶段2 存量回填(文件⑤: dry-run 对账 → --apply)
  → 抽查若干大会话, tool_paths_json 与 steps 手工核对一致
阶段3 读侧接口(文件⑥⑦: list_session_tasks 带列 + 前端类型)
  → 后端单测(新字段透出) + 接口契约复核
阶段4 前端切换(文件⑧: 台账双源 + roundHits 改接口 + 收尾上交)
  → vitest + 手动验证冷启动台账/推荐行恢复
```

> 阶段 1 可立即开工（与 [46] 的 P0/P1/P2a 并行，互不阻塞）；阶段 2 依赖阶段 1 的列存在；阶段 3/4 依赖阶段 1 的写入稳定。

### 4.2 验收标准

| 验收项 | 方法 | 预期 |
|---|---|---|
| 新任务台账落库 | 发起带引用的新任务 → 查 `chat_tasks.ref_ledger_json` | 非空、wire 形态正确、只存路径 |
| 新任务 tool_paths 落库 | 新任务含文件工具操作 → 查 `tool_paths_json` | 相对 posix 路径、去重、与 recentFiles 同键 |
| 派生归一口径 | 后端单测：绝对/反斜杠/根外 path 输入 | 归一与 `browse.root_relative` 一致，根外跳过 |

## 第 5 章 风险与回退

### 5.1 风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| ref_ledger 无历史源，上线前存量任务台账永久缺失 | 确定 | 老会话冷启动台账仍缺 | **已登记接受**（2.3/3.2 明示）；tool_paths 可回填，台账自上线起累积 |
| 前端收尾上交时机早于/晚于后端 finally 落库 | 中 | 台账漏写 | `_pending_ref_ledger` 暂存 + 已终态补交直写双通道；两通道幂等（update_task 缺省不覆盖） |
| 派生归一与前端 roundHits 口径漂移 | 中 | 推荐行 miss | 后端复用 `browse.root_relative`（与 list_session_task_artifacts 同源），单测锁定口径 |
| 快照列体积膨胀 | 低 | 单任务行变大 | 台账≤50 条、路径去重、只存路径不存正文，实测 KB 级 |
| 回填脚本误写 | 低 | 数据错 | 默认 dry-run；--apply 前抽查对账；幂等可重跑 |

### 5.2 回退
