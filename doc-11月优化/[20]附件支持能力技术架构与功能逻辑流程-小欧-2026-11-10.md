## 二、功能流程（按用户操作轴）

### F1 上传（浏览器通道）

```
POST /attachments/upload
  → save_upload(attachment_service.py:265)
      ① 按后缀分档初始读限(图片10MB/其他20MB, 超限在读入阶段即拒)
      ② 读入内存 → to_thread(save_bytes)
  → save_bytes(:183) —— 落盘+登记唯一实现
      ① session 存在校验
      ② _sanitize_name(去目录段/非法字符/Windows保留名/结尾点, 限长120)
      ③ 后缀白名单(extract 五分类词典组合; 纯 binary 415)
      ④ sha256 去重(同会话同内容复用旧行, 含并发 INSERT OR IGNORE + 回查)
      ⑤ 会话总量配额 200MB
      ⑥ 落盘 {默认工作区}/attachments/{时间戳}-{sha8}-{safe名}
         (目录由 ensure_session_attachment_dir 解析: is_default=1, 无则幂等补建)
      ⑦ classify 五分类 → INSERT 登记(kind/extract_status='none')
      ⑧ 任一步失败 → unlink 半成品文件, 不留垃圾
```

### F2 同机本地导入（第二通道）

```
POST /attachments/import-local (local_import.py:132)
  ① is_local_request: 真实客户端 IP 判同机;
     XFF 仅在受信代理后采信且取最右一跳(最左可伪造)
  ② _resolve_import_path: 绝对盘符/拒UNC/拒符号链接/拒敏感区(is_sensitive)
     /必须落在可读根集合(项目根+会话工作区+用户授权目录);
     未授权 → LOCAL_READ_DENIED(前端弹授权确认, 授权后重试即成功)
  ③ 先 stat 判大小再读盘, 读入后复核一次(防 stat 与 read 之间被替换)
  ④ 复用 save_bytes(source_path 记录来源, DRY)
```

### F3 产物「存为附件」

```
POST /attachments/collect (collect.py:59)
  ① 用会话工作区表判产物位置(不用 ContextVar 快照——HTTP 请求期恒 None)
  ② 在工作区内 → referenced: 不复制不落库, 回引用路径(前端走 quoteFile)
  ③ 在工作区外 → copied: 读入(20MB 上限) → save_bytes(source_task_id 溯源)
```

### F4 列表/收藏/删除/记账（资产台账）

```
GET  /attachments?scope=...   list_attachments(:295) —— 作用域唯一实现
     session(本会话, 排除任务产物溯源行) / recent(use_count>0)
     / global(scope='global') / ai(source_task_id 非空)
     每行补 available(磁盘文件还在) + favorited/global_id(同 sha 全局行, 1击收藏)
POST /attachments/id/{id}/promote   promote_attachment(:343)
     幂等 + sha 去重: 复制到 {data_dir}/assets/{YYYYMM}/ 建 scope='global' 行
     (session_id=NULL, 会话删除不影响); 同 sha 已有全局行直接复用
DELETE /attachments/id/{id}         delete_attachment(:491)
     global 行任意会话可删 / session 行限本会话;
     按存储路径引用计数决定是否删磁盘文件; 被合集引用未 force → 409;
     force 级联清理 material_pack_items; 磁盘删除失败记录保留
记账: touch_usage(:418) —— 发送注入成功后 use_count+1/last_used_at=now,
     「最近用过」唯一写入点; 预览/详情等读路径零写副作用
```

### F5 素材包

```
CRUD /material-packs (material_pack_service.py)
  约束: 单包≤10条目 / 包总数≤200 / 名称唯一(COLLATE NOCASE, 重名先于满额报错)
  条目保留引用身份: kind=attachment 时 attachment_id 必填,
    投喂按 id 恢复附件语义(不降格为普通文件引用)
  items 整包覆盖写(先删后插同事务); 删包只删记录不动磁盘
  包是「引用清单」: 文件留原位, 不复制
```

### F6 引用注入（发送链路）

```
用户点引用 → refs(kind=attachment, attachment_id) → orchestrator
  → resolve_refs(resolver.py:249)
      并发读(信号量4) + 单条5秒超时; 同 path 读取前去重(整份优先)
  → _read_one 分流 kind=attachment
  → _read_attachment(:115)
      ① get_attachment_scoped(auto_promote=True): global 放行 /
        本会话放行 / 跨会话自动升级为全局(不404), None 时 fail-closed
      ② extract.build_inject_text:
           text     ≤256KB 全文注入 / >256KB 档案头(前40行+总行数, 模型凭 path 深读)
           richdoc  复用工具层四读取器(pdf/docx/xlsx/pptx, 延迟导入)真抽取,
                    失败抛异常折算 attachment_failed(不吞半截)
                    xlsx 单 sheet 200 行上限, 超出提示模型用工具深读
           video    ffprobe 元数据(时长/分辨率/编码), 缺失降级不抛错
           image    档案卡(视觉模型不走此路, 见 F7)
           binary   档案卡
      ③ 真抽取成功/失败回填 mark_extract_result(仅首次, best-effort)
      ④ touch_usage 记账
      ⑤ clip_text 单条预算闸门(所有 kind 统一, 超限头尾摘录)
  → resolved/dropped/notices 回执(失败点名不阻断其余引用)
```

### F7 视觉通道（图片双路）

```
分流(react_loop.py:218-231):
  supports_image_input(任务模型) 为真 → split_vision_refs 摘出图片 ref
    文本 ref 走 resolver(档案卡兜底), 图片 ref 走占位
  为假 → 全走文本(与未接视觉前逐字节一致, 零退化)

占位(wire 前): image_slot → "[[IMAGE_ATTACHMENT:<id>]]" 入 user 消息
  (init_history 组装 refs_block)

wire 边界(react_step.py:398, 落盘/日志取占位原文之后):
  expand_vision_parts(message_builder.py:603)
    allow_inline = supports_image_input AND accepts_inline_image   ← 11-10 门控收口
    allow_url   = accepts_remote_url(实测含 url/both 才放行)
    → expand_image_slots(vision.py:134) 对全部 user 消息:
        占位 → _slot_parts: 查附件 → build_media_part:
          ① 公网 URL 直传(调用方按实测能力决定)
          ② 超内联上限(默认2MB) → 压缩(EXIF方向烧进像素, alpha走PNG其余JPEG)
             再内联; 压完仍超 → (None, 原因)
          ③ data URL 按「文件+上限+压缩参数」缓存复用(容量8, 最旧淘汰)
          ④ 任何失败 → 原位替换一行说明文字, 不塞必被拒的 part
        显式图片外链(markdown 图语法/带图后缀裸链接, 不猜工具结果里的链接)
          → build_url_part: 只收 http/https 公网地址
            (is_global 一处覆盖回环/内网/CGNAT; 组播单独判)
          → 拒收给用户可见回执 [图片链接未转发: 原因]
```

### F8 抽取态展示

```
mark_extract_result(attachment_service.py:437):

  档案卡不回填(避免占住 'none' 使真抽取永久无法回填);
  best-effort: 状态写失败只 WARNING 不阻断
```

## 三、逻辑流程核查（三堂会审口径：合规/合理/关联）

### 3.1 判定合理的功能分支（确认保留）

| 分支 | 判定 | 依据 |
|---|---|---|
| 五分类判定顺序：图→视→富→空→文本→有扩展名→mime 兜底 | ✅ 合理 | 扩展名唯一真源优先(不可伪造)，mime 仅无扩展名时辅助；文本分支在"有扩展名→binary"之前（extract.py:68-75 有明确注释） |
| 跨会话 auto_promote vs 预览严格 404 | ✅ 合理 | 写副作用只属于发送注入与手动收藏；预览纯读（resolver.py:124, attachment_service.py:534-541 口径一致） |
| 删除按路径引用计数删文件 | ✅ 合理 | 同名多行共享路径，直接删会"删一条其余全红" |
| 素材包引用清单不复制文件 | ✅ 合理 | 与附件删除的 pack_refs 级联闭环（409→force→清条目） |
| 视觉占位 str 化 + wire 边界展开 | ✅ 合理 | 压缩/裁剪/持久化/日志零改动；base64 不入库不入日志 |
| 内联双门控(supports AND accepts) | ✅ 合理 | 11-10 收口：声明无视觉且未实测的模型不内联，防整轮 400 |
| 外链"未探测不发"保守方向 | ✅ 合理 | 少一张图好过整轮失败（vision.py:92-98） |
| richdoc 失败抛异常不吞 | ✅ 合理 | 吞掉会让模型收到半截内容却以为完整 |
| video ffprobe 缺失降级不抛错 | ✅ 合理 | 元数据是增强信息非数据路径，降级不损主流程 |
| 素材包重名先于满额报错 | ✅ 合理 | 提示可行动（改名即可 vs 必须删包） |

### 3.2 发现的次优分支（记录，不动代码）

| # | 位置 | 现象 | 影响 | 建议 |
|---|---|---|---|---|
| R1 | extract.py:77 `browse._probe_text` | image 分支依赖 browse 内部私有函数，跨模块私有调用 | 契约脆弱（browse 改名即断），但功能正确 | 后续可提为 browse 公共函数；非缺陷 |
| R2 | resolver.py:141 `text.startswith("[附件档案卡·")` | 用文本前缀判断"是否真抽取"属字符串协议 | 能工作但脆弱；若档案卡文案改动需同步此处 | 可让 build_inject_text 返回 (text, is_real_extract) 元组；属可选重构 |
| R3 | media_payload.py:26 进程级 `_data_url_cache` | 无按会话隔离，多会话共享容量 8 | 仅缓存浪费/淘汰抖动，无正确性问题 | 可接受；如需精确可挂会话键 |
| R4 | attachment_service.py:208 上传大小按后缀预判 | 与 classify 的 mime 兜底分支不完全同源（无扩展名图片按 20MB 读） | 仅读限档位差异，最终裁决归 save_bytes 单一真源 | 可接受（KISS，避免读前再实探） |

### 3.3 结论

- **无违规分支**：V1~V7 不变量全部成立；安全纪律（同机判定/路径穿越/越权/敏感区）完整闭环。
- **关联逻辑增强而非退化**：S3 抽取复用工具层读取器（DRY）、S4 视频元数据降级不抛错、F6 注入与预览同口径、删除与素材包级联闭环。
- 3.2 所列 4 项均为"能工作但可更优"的次优点，不构成缺陷，不建议本轮动刀（避免为重构而重构）。

## 五、附件类型 × 输入模态支持矩阵（补充：小欧 2026-11-10）

> 模态轴现状（model_service.py:173 实测注释）：`input_modalities` 实际 5 种值——
> text(460 全覆盖) / image(292) / file(182) / video / audio；
> 能力判定统一口径：实测 media.accept 优先，无实测回落声明（vision.py:75-98）。

### 5.1 支持矩阵（以本地代码实际行为为准）

| 附件五分类 | 走的模态 | 视觉模型 | 非视觉模型 |
|---|---|---|---|
| text | text（隐式，全模型必备） | 正文注入 | 正文注入 |
| richdoc | text（抽取降维） | 真抽取正文（pdf/docx/xlsx/pptx 四读取器） | 同左（失败折算 attachment_failed） |
| video | text（档案卡 + ffprobe 元数据） | 同左 | 同左 —— 声明了 video 模态但原生线未接（[14] P5 规划项） |
| image | 双路分流 | `image_url` parts（内联 data URL/公网外链，media_payload 三级选路） | 档案卡「当前模型无视觉能力」 |
| binary | text（档案卡） | 同左 | 同左 |

### 5.2 矩阵关键结论

1. **image 是唯一「类型↔模态」真正联动的分支**：react_loop.py:219 按
   `supports_image_input` 分流——视觉模型摘出图片 ref 走 parts 线，
   非视觉模型全走文本线（档案卡），零退化。
2. **richdoc/video 本质是「模态降维」**：系统不直接消费 file/video 模态，
   而是把内容抽取/降维成 text 塞进 prompt——所以非视觉模型也能"读"PDF/Excel。
3. **audio/file/video 原生模态是声明了但未消费**：model_service 归一化时保留
   这些值，settings_registry P2 也已登记，但 wire 层只有 image part 构造
   （media_payload.py:152 明示「file/video 待线格式接入后在此扩展」），
   即 [14] P5 待规划项。
4. **输出模态（生图/生视频）与附件无关**：vision.py 边界第 5 条明确只看
   input 维度，防止生图模型被误判为看图。

### 5.3 矩阵缺陷分析与提升方向

| # | 缺陷 | 根因 | 影响 | 提升/升级方案 |
|---|---|---|---|---|
| D1 | **audio 附件五分类里根本没有**：上传白名单不含音频后缀，audio 模态在附件域无入口 | 五分类词典（extract.py:38-49）与模态轴未对齐 | 模型声明的 audio 模态永远空转 | 在五分类词典补 AUDIO 类 + 上传白名单；先落「档案卡+时长元数据」与 video 同款，再规划原生 audio parts |
| D2 | **file/video 原生模态声明即悬空**：管理面（models 表/DTO）声明了模态，wire 面没有对应 part 构造 | 管理面与执行面推进不同步（P5 未实施） | 模型能力展示与实际投喂不一致，用户以为能传视频给模型看 | 按供应商逐家落 file/video 线格式（media_payload.py:152 已留扩展点）；未落地前在前端能力展示侧标注「暂不支持原生投喂，将降维为文本」 |
| D3 | **模态判定是二值，缺「降维可用」中间态**：supports_image_input 只有真/假，非视觉模型对 image/richdoc 的"文本降维可读"没有独立信号 | 能力模型只有 input_modalities 单层 | 前端无法提示"此模型看不了图但能读档案卡"，体验降级被隐藏 | 能力判定返回 {native, fallback} 两级（vision.py 判定函数扩一档），前端按级展示 |
| D4 | **实测记录只覆盖 image**：media.accept 实测只有 image 维度，file/video/audio 无实测通道 | 实测探针未扩维 | 无实测时回落声明，声明错误无法被纠正 | 实测探针按模态扩维（file/video/audio 各一条最小用例），实测结果写回 media.accept 同构字段 |
| D5 | **矩阵无守门测试**：五分类↔input_modalities 的映射关系没有契约测试，词典改了模态轴不知道 | 缺少跨域一致性断言 | 未来新增分类/模态时两轴静默漂移 | 增加一条契约测试：遍历五分类×模态轴断言「有模态必有消费路径 or 有明确降维路径」，漂移即红 |
