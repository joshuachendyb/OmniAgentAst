## 一、分析

### 1.1 研究范围与判定口径

本章回答三个问题：Omni 现在到底有没有记忆、缺的是什么、业界已经收敛出哪些可用的做法。

判定口径不看"有没有一张叫 memory 的表"，而看一条更硬的标准：**上一个任务结束后，下一个任务能不能在不靠人复述的前提下，自动用上上次的经验、约束与结论。** 按这条标准，答案是否定的。

研究依据两块：一是对本地最新代码的实证，覆盖 `backend/app` 的服务层、数据库 schema、agent 主链、工具注册与注入链；二是对 2025–2026 年记忆系统研究的横向比对，包括抽取式、自主编辑式、双时态图、笔记式四派，以及上下文工程与评测口径的演进。本机环境也做了实测：SQLite 3.50.4、FTS5 的 trigram 分词可用，`jieba`／`numpy`／`onnxruntime` 已装，无 `torch`、无向量库、无图库。这些事实直接决定了后面的选型。

### 1.2 现状实证：有上下文管理，没有记忆系统

#### 1.2.1 已有的七项能力

| 能力 | 代码位置 | 实质 |
|---|---|---|
| 会话历史回放 | `services/chat/history_loader.py` | 从 SQLite 按轮次分桶还原 assistant 与 tool 的配对，服务"当前任务"的上下文 |
| 任务内压缩 | `services/agent/compaction/`（trigger／prune／summary／summary_prompt／split_turn／assembler） | 触发判定→工具结果剪枝→七段锚定摘要→保尾切分→预算收缩，一条完整流水线 |
| 摘要落库 | `chat_tasks.task_summary`，写入点在 `services/agent/react_loop.py` 任务收尾段 | 摘要只在"链式会话"上落库，独立任务不沉淀 |
| 任务链 | `chat_sessions.link_enabled` + `chat_tasks.context_root_task_id` + 增量摘要锚点 | 显式串行上下文，本质是"同一条线接着聊" |
| 目录备忘 | `chat_session_workspaces.memo` + `services/agent/workspace_block.py` | 目录级一句备注，随目录块注入，整块上限 4096 字符 |
| 项目规则 | `OmniAgent.md` → `services/prompts/project_context.py` | 静态全局注入，10000 字符截断；是"宪法"，不是记忆 |
| 资产与授权台账 | `attachments`（sha256／extract_status／use_count）、`material_packs`、`chat_session_trust` | 有元数据与安全记忆，无内容检索 |

#### 1.2.2 三个关键实证结论

第一，**沉淀是断的**。摘要在任务收尾时生成，但只有链式会话才写回 `chat_tasks.task_summary`；独立任务跑完，除了原始步骤行，没有任何"这次学到了什么"的成品。也就是说，绝大多数任务的经验只以原始日志形态存在，没有被提炼。

第二，**注入是静态的**。任务开始时能进上下文的只有三样：系统提示、项目规则文件、事项目录块。模型没有"回忆"这个动作，也没有任何工具能让它主动去查"上次那个事是怎么做的"。检索入口为零。

第三，**基础设施是够的，方向是缺的**。本机 SQLite 3.50.4 原生支持 FTS5，且 `trigram` 分词器可用——这意味着中文子串检索不需要外部分词器、不需要向量库就能做；`jieba`、`numpy`、`onnxruntime` 在，说明将来要加本地小向量模型也有路。但全仓没有任何 embedding、向量表、图结构、记忆表。缺的不是能力，是设计。

#### 1.2.3 一个容易被忽略的隐患

现有压缩模板是七段固定结构，涵盖目标、计划与决策、重要细节、进展、总结、重要上下文、相关文件，但它对"哪些内容绝对不能丢"没有硬保证。2026 年有一组公开实验很说明问题：给 agent 一条策略约束，让它跑足够长以触发压缩，然后统计违规率——约束被摘要保留时违规率为 0，被摘要丢掉后违规率升到 38%，覆盖 1323 次运行、7 个模型家族。Omni 的长任务正好踩在这个点上：约束一旦在压缩中丢失，后面几十轮都会带着错误前提跑。

### 1.3 四个真问题

把上面的实证收拢，问题不是"存不下"，而是四句话。

**记不住。** 跨会话断层。同一个代码库、同一类任务，换一个会话就从零开始；用户偏好、环境事实、踩过的坑，每次都要重新说一遍。

**取不出。** 没有检索。数据都在库里，但模型没有任何手段按"这次要干什么"去取相关历史；人只能靠翻历史页、靠手动开链式会话。

**信不过。** 没有来源、时效与冲突处理。即便将来把历史灌进去，也无法判断这条经验是三天前的还是三个月前的、是否已被后来的实践推翻、是谁在什么场景下得出的。

**不会忘。** 只增不减。压缩是"窗口内丢"，不是"记忆层淘汰"；没有 TTL、没有置信度衰减、没有容量上限，时间一长必然检索噪声大于信号。

### 1.4 前沿研判：九条收敛与三条反模式

收敛的九条。

第一，**分层是共识**。工作记忆（当前任务）／情节记忆（发生过什么）／语义记忆（世界是什么样）／程序记忆（该怎么做），四层职责不同，不能混成一个"记忆库"。

第二，**写入分四派，各有代价**。抽取式自动提炼事实，省事但有损；自主编辑式让模型用工具改自己的记忆块，可控但依赖模型自律；双时态图给每条事实加生效与失效时间，可审计但重；笔记式自组织卡片，灵活但容易碎片化。没有免费的午餐，选型要看治理成本。

第三，**检索必须混合**。词法、向量、结构扩展、时间衰减、重要性、使用频次一起用。纯向量在"路径、命令、错误串、中文术语"上是最差的一档，而这恰恰是 Omni 的高频内容。

第四，**上下文工程是四个操作：load、fetch、compact、isolate**。而 write 是这四者的前提——没写到窗口外的信息，压了就真没了。多数系统栽在只做 compact 不做 write。

第五，**文件系统即记忆**。一线编码 agent 几乎都走这条路：约定、笔记、计划写成文件，模型按需读。对单机单用户，这是成本最低、可解释性最好的一层。

第六，**巩固是分水岭**。会话结束后后台把情节提炼成事实与做法，否则记忆只会漂移。没有巩固的记忆系统，本质是"聊天记录搜索"。

第七，**治理不是企业专属**。记忆投毒在单机同样成立：一次网页注入被写成高置信事实，此后每次会话都带着它。自动抽取越激进，治理越不能省。

第八，**评测口径要换**。公开基准测的是长对话问答召回，对任务型 agent 是错的口径。该测的是重复犯错率、跨会话续做成功率、同类任务第二次的步数与 token、检索命中是否被采纳。

第九，**记忆是主动过程，不是检索索引**。写入、巩固、淘汰、冲突消解都是过程，索引只是其中一环。把它当索引做，三个月后一定烂。

必须避开的三个反模式：

- **全量向量化加每轮 top-k 注入**。噪声大、成本高、注意力被稀释，还会让提示前缀不稳定、缓存全废。
- **把摘要当记忆**。摘要是有损压缩的产物，再拿它当记忆二次压缩，越压越偏；记忆要存结构化字段与原文指针，不能只存一段话。
- **无限追加不遗忘**。检索精度随时间单调下降，最后"记得越多越不准"。

### 1.5 对 Omni 的适用性判断

前沿方案不能照搬，逐条过一遍。

**多租户与云端记忆服务**不适用。单机单用户，没有租户维度，引入只会增加复杂度。

**图数据库**不适用。SQLite 邻接表加一到两跳扩展，足够覆盖"文件—项目—任务—实体"的关联；上独立图库是多一个运维对象，换不来对等的能力。

**向量库**不作为硬依赖。可以把向量做成可选列，模型用本地 ONNX 小模型，失败就降级纯词法。记忆不能因为一个 embedding 服务挂了就不可用。

**文件系统即记忆**高度适用，且应当作为项目层记忆的主形态——用户能看、能改、能进版本库、换机器能带走。

**后台巩固**适用，且 Omni 已有定时与后台唤醒的内核，落地成本低。

**治理与审计**必须做，且要在第一版就有最小集（来源、置信度、可删除），不能等"以后再说"。

结论：Omni 该走的是**本地文件加 SQLite、混合检索、后台巩固**的轻量路线，而不是再引入一套外部记忆服务。

### 1.6 能力缺口清单

| 能力 | 现在 | 缺口 | 价值 |
|---|---|---|---|
| 工作记忆 | 靠压缩摘要临时承载 | 无结构化、可增量更新的任务状态；约束无硬保护 | 长任务不跑偏，压缩不丢铁律 |
| 情节记忆 | 原始步骤行加链内摘要 | 独立任务不沉淀；无检索 | 断点续跑、失败教训复用 |
| 语义记忆 | 无 | 无事实层、无时效、无冲突消解 | 越用越懂你，不重复调研 |
| 程序记忆 | 无 | 无做法模板、无成功率统计 | 教一次即可复跑，长期复利 |
| 项目记忆 | 目录一句备忘 | 无项目级约定、命令、禁区 | 换会话不重述项目背景 |
| 实体关系 | 无 | 无轻量关联，检索无法扩展 | 从"这个文件"扩到"这个项目" |
| 治理 | 无 | 无来源、置信度、审计、遗忘 | 防污染、可纠错、可持续 |

## 二、实施策略

### 2.1 目标与硬约束

目标一句话：**把任务流变成可沉淀、可检索、可治理的记忆资产，让第二个同类任务比第一个更快、更少错。**

硬约束不定死，方案就是空谈。

| 约束 | 内容 | 对设计的影响 |
|---|---|---|
| 部署 | 单机、单用户、Windows | 不做租户维度；路径与编码按 Windows 处理 |
| 存储 | SQLite 单一真源 | 记忆与业务同库或同目录，不引外部服务 |
| 模型 | 外部 LLM，额度有限、窗口不一 | 注入必须小；检索不能依赖每次额外调模型 |
| 算力 | 无 GPU、无 torch | 向量只做可选增强，默认词法 |
| 任务 | 长任务、多工具轮、有 HITL | 抗压缩、可中断恢复、可审计 |
| 数据量 | 步骤表已达百万行级 | 检索必须走索引、有界候选、top-k，禁止全表模糊扫 |
| 规范 | 数据与配置走既有通道，测试不碰真库 | 复用 `db.get_conn`／`db.atxn`／`_db_overrides` |

核心矛盾仍然是那四句：该记的没记、该忘的没忘、记了取不出来、取出来不敢信。方案要对这四句逐一给解，缺一条就不算完整。

### 2.2 总体策略：一个闭环、三层范围、四类记忆、三类支撑

**一个闭环**：写入 → 存储 → 巩固 → 检索 → 注入 → 反馈。六个环节缺一不可；只做"存加查"就是日志系统。

**三层范围**：全局、项目、会话。

全局放用户偏好、机器环境、模型能力、跨项目通用坑点。项目放目录约定、构建与测试命令、禁区、项目结构、项目专属坑点。会话放任务卡、本次决策、产物。

归属判定用一条规则：**能不能跨项目复用**。能复用上全局；只对某目录成立上项目；只对本次任务成立上会话。模型只提交候选，归属由门控规则定，不由模型自选。

**四类记忆**：工作记忆、情节记忆、语义记忆、程序记忆。

**三类支撑**：项目记忆（文件化）、实体关系（轻量图）、治理（来源、时效、冲突、遗忘、审计）。

整体形状如下：

```
任务事件流（用户发言／工具调用／观测／收尾）
        │
        ▼
   写入门控：候选生成 → 风险分级 → 自动／待确认／拒绝
        │
        ▼
   存储层：工作记忆(内存+DB) │ 情节 │ 语义 │ 程序 │ 项目(文件)
        │                └── SQLite + FTS5(trigram) + 可选向量列 ──┘
        ▼
   巩固层：去重 → 冲突消解 → 情节提炼事实 → 做法提炼 → 衰减归档
        ▼
   检索层：词法 + 时间衰减 + 重要性 + 使用频次 + 关联扩展 (+可选向量) → 去冗余
        ▼
   注入层：任务开始预载 │ 循环中按需取 │ 压缩前落盘／压缩后回填
        ▼
   反馈层：命中／采纳／纠正 → 调整重要性与置信度
```

### 2.3 七条关键取舍

**取舍一：候选制，不做全自动抽取直写。**
自动抽取的收益是省事，代价是错误会长期复利。单用户场景下，一条错误偏好会污染此后所有任务，代价远高于人工确认的成本。所以用户明说的直接生效；模型推断的进候选；外部内容一律低置信、禁止自动提升。

**取舍二：词法优先，向量可选。**
FTS5 的 trigram 对中文子串、路径、命令、错误串都友好，零依赖、毫秒级。向量只在"语义相近但用词不同"的场景有增益，且需要模型与额外存储。先做词法，把向量做成可插拔列，用得上再开。

**取舍三：SQLite 邻接表，不上图库。**
实体关系只需要回答"这个东西和那个东西有没有关系、隔几跳"。两张表加递归查询足够；独立图库带来的是运维与一致性成本，不是能力。

**取舍四：项目记忆文件化，正文不进数据库。**
项目约定要能被人直接看、直接改、能进版本库、换机器能带走。文件是唯一同时满足这四条的形态。数据库只存索引与元数据，正文以文件为准。

**取舍五：任务开始预载加循环中按需取，不做每轮 top-k。**
每轮注入会稀释注意力、破坏提示前缀稳定性、抬高成本。正确做法是开局装一小份高置信记忆，其余靠工具在需要时取。

**取舍六：双时态事实，失效不删除。**
新事实推翻旧事实时，旧条目置为失效并指向新条目，保留链路。删掉就再也说不清"当时为什么那么做"，而长任务最需要的恰恰是可追溯。

**取舍七：注入独立预算、可关闭、可审计。**
记忆必须有自己的预算，不能和历史抢；必须能一键关；必须记录这次注入了哪些条目、后来有没有被采纳。没有这三条，记忆会变成不可控的噪声源。

### 2.4 与现有机制的边界

不重复建设是这套方案能否活下去的前提。逐项划清。

| 现有机制 | 它的职责 | 与记忆的关系 |
|---|---|---|
| 压缩 | 窗口内生存：剪枝、摘要、保尾、预算收缩 | 记忆负责窗口外生存；压缩前把关键结论落盘，压缩后从记忆回填必须保留项。两者是上下游，不是替代 |
| 任务链 | 显式串行：同一会话接着聊 | 链是人指定的连续，记忆是按需的并行。链内摘要应升级为任务卡，成为情节记忆的一个来源 |
| 目录备忘 | 单目录一句备注 | 升级为项目记忆的一个字段，不另起一套 |
| 附件与素材包 | 文件台账与可复用文件集 | 是记忆的输入源之一，不是记忆本身 |
| 授权表 | 安全记忆：哪些操作已获准 | 保持独立；可被记忆层引用为偏好的证据 |
| 项目规则文件 | 静态全局约束 | 保持独立；记忆不得覆盖它，只能追加例外并标注 |
| 会话历史 | 原始事件流 | 是情节记忆的原料，不是成品 |

一句话：记忆层只做提炼、检索、注入、治理，不重做压缩、不重做历史回放、不重做安全。

### 2.5 分期策略

按"先验证价值、再补治理、最后做增强"的顺序推进，每期都能独立验收、独立回滚。

**M0 价值验证（最小闭环）**
范围是情节记忆、词法检索、检索工具、任务开始预载。不做语义事实、程序记忆、巩固作业、前端管理页。验收标准是跨会话问"上次那个事是怎么做的"，能给出任务卡与关键步骤，并带来源。

**M1 治理与语义**
范围是语义事实层（带双时态）、候选队列、来源审计、删除与纠正、记忆管理页。不做程序记忆、向量、图扩展。验收标准是连续二十个任务，同一偏好重复询问不超过一次；错误记忆可一键删除且不再召回。

**M2 程序记忆**
范围是做法模板（触发条件、步骤、前置校验、失败分支）、成功率统计、失败教训提炼。不做自动改写模板，先只读复用，人工确认后再改。验收标准是同类任务第二次执行的步数或 token 下降两成以上，重复犯错率下降。

**M3 增强**
范围是可选向量、实体两跳扩展、后台巩固作业、内部评测集。不做图库、云服务、多租户。验收标准是检索 precision@5 达标；巩固后重复条目显著下降；每任务 token 不升。

为什么是这个顺序：M0 用最小代价证明记忆有用，避免做完一整套没人用；M1 在数据变多之前把治理立起来，否则脏数据会先于价值到来；M2 才是长期复利，但它依赖 M0 的任务卡与 M1 的治理；M3 是优化，早做没有数据支撑。

### 2.6 风险与治理策略

| 风险 | 触发条件 | 对策 |
|---|---|---|
| 记忆膨胀 | 条目只增不减、检索面变大 | 容量上限、重要性衰减、归档；检索硬性 top-k 与预算 |
| 记忆投毒 | 网页或文档内容被写成高置信事实 | 来源分级；外部内容一律候选、低置信、禁止自动提升；路径、凭据、破坏性操作类主题不自动生效 |
| 摘要失真 | 压缩把约束或关键路径丢掉 | 约束单独成块、永不进摘要器；压缩前落盘、压缩后回填；摘要模板增加失败路径与环境变更两段 |
| 上下文挤占 | 记忆注入过多 | 独立预算、分档配额、超限先裁记忆 |
| 跨任务串味 | 上一个任务的记忆被当成本任务事实 | 会话范围隔离；注入时标注来源与时间；与当前状态冲突时标"需核验" |
| 误删 | 用户或模型删错 | 软删除、审计表、可恢复窗口 |
| 性能退化 | 百万行步骤表上做模糊检索 | 只走索引、范围收敛、有界候选；禁止全表扫描；检索放子线程不阻塞事件循环 |

### 2.7 验收口径

不用公开的长对话问答基准，那测的不是任务能力。用四类可采集的指标。

**重复犯错率**：同类任务中，重复出现过的失败原因占比。基线从历史任务里统计，改造后按月对比。

**跨会话续做成功率**：给定一个中断任务，新会话能否在不复述的情况下接上并完成。

**同类任务第二次的成本**：步数与 token 的下降比例。

**检索质量**：人工判定的 precision@5，以及注入后被采纳的比例。

每条都要有采集办法：前三条从 `chat_tasks`、`chat_task_steps`、`token_usage` 直接算；第四条在注入日志里记录条目 id，任务结束后由用户标注是否被采纳。

## 三、实施方案

### 3.1 总体架构与数据流

模块落在 `backend/app/services/memory/`，与现有服务同层。一次任务的生命周期里，记忆层出现三次。

```
任务开始
  ├─ 解析任务签名（归一化用户输入）
  ├─ 检索：全局偏好 + 项目约定 + 相关任务卡 + 相关做法
  ├─ 预算裁剪 → 生成带标签的 system 消息
  └─ 并入注入历史通道（与历史同源，共用超窗判定与裁剪）
循环中
  ├─ 工具：memory_search / memory_read / memory_write
  └─ 只在模型主动调用时查库，不每轮预载
任务收尾
  ├─ 生成任务卡（目标/结果/决策/失败路径/产物/环境变更）
  ├─ 关键结论落盘（防止压缩丢失）
  └─ 标记候选事实，交巩固作业
空闲、启动或定时
  └─ 巩固：去重、冲突消解、情节提炼事实、做法提炼、衰减归档、索引重建
```

### 3.2 数据模型

统一条目表承载四类记忆，范围与类型用字段区分，避免四张表四套代码。

```sql
CREATE TABLE memory_items (
  id            TEXT PRIMARY KEY,
  scope         TEXT NOT NULL,        -- global | project | session
  scope_ref     TEXT,                 -- 项目根路径 / session_id；global 为空
  kind          TEXT NOT NULL,        -- fact | preference | episode | procedure
  subject       TEXT,                 -- 归一化主题键，冲突消解用，如 user.python_path
  title         TEXT NOT NULL,
  content       TEXT NOT NULL,        -- 给模型读的自然语言
  structured    TEXT DEFAULT '{}',    -- 机读字段：路径/命令/步骤/参数
  source_type   TEXT NOT NULL,        -- user_stated | agent_inferred | tool_observed | doc_imported
  source_ref    TEXT NOT NULL,        -- task_id / message_id / 文件路径 / URL
  confidence    REAL NOT NULL,        -- 0..1
  importance    REAL NOT NULL,        -- 0..1
  valid_from    TEXT,                 -- 世界时间：何时开始成立
  valid_to      TEXT,                 -- 世界时间：何时不再成立
  recorded_at   TEXT NOT NULL,        -- 系统时间：何时被记录
  superseded_by TEXT,                 -- 被哪条取代
  status        TEXT NOT NULL,        -- candidate | active | superseded | archived | rejected
  last_used_at  TEXT,
  use_count     INTEGER DEFAULT 0,
  content_hash  TEXT NOT NULL,
  UNIQUE(scope, scope_ref, kind, content_hash)
);

CREATE INDEX idx_mem_scope   ON memory_items(scope, scope_ref, status);
CREATE INDEX idx_mem_subject ON memory_items(subject, status);
CREATE INDEX idx_mem_kind    ON memory_items(kind, status, importance DESC);

CREATE VIRTUAL TABLE memory_fts USING fts5(
  title, content, subject,
  content='memory_items', content_rowid='rowid',
  tokenize='trigram'
);
```

选 `trigram` 的理由：中文不需要外部分词器，路径、命令、错误串这类非自然语言也能命中；代价是索引比 `unicode61` 大，但对单机记忆量级完全可接受。若后续条目量级超出预期，再评估换分词器或加列，不改上层接口。

配套三张表。

```sql
-- 轻量实体关系（M3 才用，先建表不建逻辑）
CREATE TABLE memory_entities (

  aliases TEXT DEFAULT '[]', created_at TEXT NOT NULL

CREATE TABLE memory_edges (
  id TEXT PRIMARY KEY, src_id TEXT NOT NULL, rel TEXT NOT NULL, dst_id TEXT NOT NULL,
  valid_from TEXT, valid_to TEXT, source_ref TEXT NOT NULL,

-- 审计：谁在哪个任务里写了或改了什么

  id INTEGER PRIMARY KEY AUTOINCREMENT,
  item_id TEXT NOT NULL, action TEXT NOT NULL,   -- create | update | supersede | archive | delete
  actor TEXT NOT NULL,                            -- user | agent | job
  task_id TEXT, before_json TEXT, after_json TEXT, created_at TEXT NOT NULL
);
```

可选向量表默认不建，需要时再加。

```sql
CREATE TABLE memory_embeddings (
  item_id TEXT PRIMARY KEY, model TEXT NOT NULL, dim INTEGER NOT NULL,

```

任务卡不单独建表，用 `memory_items(kind='episode')` 承载；原始步骤仍以 `chat_task_steps` 为准，任务卡里只存摘要与指针。这样避免同一份内容两处存储、两处漂移。

### 3.4 写入路径与门控

**入口一：任务收尾，自动。**
在任务结束的收尾段生成任务卡，写 `kind='episode'`、`scope='session'`；同时把可复用的结论抽成候选事实，`status='candidate'`。这一步不额外调模型——任务卡用现有摘要能力生成，候选事实用规则抽取，来源限于用户明确纠正、明确偏好、明确路径约定。

**入口二：在线事件，半自动。**
工具观测到稳定信息时，如环境探测结果、命令失败原因，写 `kind='fact'`、`source_type='tool_observed'`，给较短有效期。用户明确表达偏好或纠正时，写 `kind='preference'`、`source_type='user_stated'`。

**入口三：用户显式，手动。**
界面上的"记住这条"按钮，或对话里明确说"记住"，直接 `active`，`confidence=1.0`。

门控规则。

| 来源 | 默认状态 | 置信度 | 提升条件 | 禁止 |
|---|---|---|---|---|
| 用户明说或显式记住 | active | 1.0 | 无 | 无 |
| 用户隐含表达（纠正、偏好） | candidate | 0.7 | 同类出现两次以上或用户确认 | 不自动升为 active |
| 模型推断 | candidate | 0.5 | 人工确认 | 不得直接 active |
| 工具观测 | active（短 TTL） | 0.8 | 再次观测到则续期 | 不得跨项目复用 |
| 外部文档或网页 | candidate | 0.4 | 人工确认 | 禁止自动提升；涉及路径、凭据、破坏性操作一律拒绝 |

降级与失效：同 `subject` 出现更新且来源更权威时，旧条目置 `superseded`；超过 TTL 未使用且重要性低于阈值时置 `archived`；用户删除时置 `rejected` 并写审计。

### 3.5 检索与排序

先过滤后打分，避免在百万行上做全量计算。

**范围收敛**：按 `scope` 与 `scope_ref` 收窄。会话范围只查当前会话；项目范围只查当前项目根；全局范围常驻。

**有界候选**：FTS 命中取前 N，N 取 top_k 的四到五倍，再叠加同 `subject` 的当前有效条目；不做全表扫描。

**打分**：

```
score = 0.40 * 词法相关度（归一化）
      + 0.20 * 时间衰减（半衰期 30 天）
      + 0.15 * 重要性
      + 0.10 * 使用命中（log 归一化）
      + 0.10 * 关联重合（同项目、同实体、同会话）
      + 0.05 * 范围匹配（越具体越高）
      + 可选 * 向量相似度
```

**去冗余**：对候选做最大边际相关筛选，同主题只留信息量最大的一条。

**预算裁剪**：按分数从高到低装入，超预算即停；单条超长时截断正文但保留标题与来源。

降级链：FTS 不可用则走 `subject` 精确匹配与范围过滤；向量不可用则直接跳过该项，不影响主流程。

### 3.6 注入路径

**时机一：任务开始。**
在装配注入历史的阶段调用，产出带标签的 system 消息，并入与历史相同的注入通道。这样能自动享受超窗判定、裁剪与每次任务清零，不需要第二套机制。

预算分档，单位为字符。

| 范围 | 配额 | 内容 |
|---|---|---|
| 全局 | 600 | 偏好、环境、通用坑点 |
| 项目 | 800 | 约定、命令、禁区、项目坑点 |
| 会话 | 600 | 最近一到两张任务卡 |
| 合计 | 2000 | 硬上限，超限先裁会话，再裁项目，最后裁全局中的低分条目 |

注入格式用纯文本，带来源，便于模型引用与人审计。

```text
[记忆-全局] 用户偏好：结论先行、中文答复；本机 Python 在 E:\Appsw\python31311。
  来源：user_stated，2026-11-20，置信 1.0
[记忆-项目] 本目录为后端代码根；提交前必过 ruff（F 类零容忍）；测试不写 config/config.yaml。
  来源：doc_imported，2026-11-18，置信 0.9
[记忆-会话] 上次任务「整理Q3报告」进行到第 7 步，卡在读取 sales.xlsx；失败原因：路径越界被拦截。
  来源：episode，2026-11-24，置信 0.8
```

**时机二：循环中。**
提供三个工具：`memory_search` 按关键词与范围检索，`memory_read` 读单条全文，`memory_write` 写候选。工具描述里明确"记忆是历史参考，与当前状态冲突时以当前为准"。默认不在循环内预载任何记忆。

**时机三：压缩前后。**
压缩前，把当前任务的约束、已确认结论、产物路径落盘为工作记忆条目；压缩后，从工作记忆回填必须保留的条目到新窗口。约束类条目永不进入摘要器，避免 1.2.3 描述的那类退化。

### 3.7 巩固作业

触发时机有三个：任务收尾后异步、应用启动后延迟、定时任务空闲时。三者都走同一个幂等入口，可重入。

第一步去重：同范围、同类型、同 `content_hash` 合并；高相似条目保留信息量大的，另一条指向它。

第二步冲突消解：同 `subject` 多条有效条目，按来源权威性与时间排序，新的取代旧的，旧的置 `superseded` 并写审计。

第三步提炼：情节卡中的稳定结论升为事实候选；同一类任务成功三次以上，提炼为做法模板候选，不自动生效，等确认。

第四步衰减：按半衰期降低重要性；低于阈值且长期未使用的归档。

第五步归档与重建：归档条目不参与检索；FTS 索引增量同步；统计条目数、命中率、平均长度，写日志。

失败处理：单步失败不阻断后续步骤，记录失败原因并在下一轮重试；巩固作业不得阻塞任务主链路。

### 3.10 测试与观测

测试分三层：存储与检索的纯函数单测，不碰网络；真实 SQLite 的集成测试，用临时数据目录；真实任务回放，真实模型、真实工具、真实库。测试只用于发现问题，不提交测试用例到仓库，也不以测试固化错误逻辑。

观测字段每次注入记一条：任务 id、注入条目 id 列表、各范围占用字符、检索耗时、后续是否被采纳。这些数据直接支撑第二章的四项验收指标。

性能红线：单次检索不超过 100ms；注入总量不超过 2000 字符；巩固作业单轮不超过 5 秒且不阻塞主链路；记忆层任何异常都降级为"无记忆"，不得让任务失败。

### 3.11 明确不做

- 不引入向量数据库、图数据库、外部记忆服务。
- 不做多租户、不做云端同步。
- 不做全自动抽取直写。
- 不做每轮 top-k 注入。
- 不把摘要当记忆，不把知识库当记忆。
