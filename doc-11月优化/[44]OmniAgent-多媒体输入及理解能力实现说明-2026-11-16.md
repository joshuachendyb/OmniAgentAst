## 0. 一句话结论

OmniAgent 的多媒体能力由两层构成：**输入层**把图片/视频/音频/富文档/文本/链接等统一采集、识别、分类；
**理解层**并不自建 OCR/ASR 模型，而是把多媒体按目标模型的能力画像**正确装配成原生多模态 part** 交给上游多模态模型理解，能力不可达时**有保真梯度地降级**为可读文本，绝不静默丢内容。全链以“识别（模型无关）→ 能力判定（模型相关）→ 装配（wire 边界）”两阶段单一管道贯穿，前后端共享同一契约真源。

---

## 1. 总体架构：两阶段管线 + 单一真源 + 薄前端厚后端

多媒体的“输入→理解”被拆成三个互不混杂的阶段，每阶段单一职责：

| 阶段 | 归属 | 是否依赖模型 | 核心实现 |
|---|---|---|---|
| ① 识别 | `attachments.extract` / `contract.classify_ref` | 否（模型无关） | 后缀词典、URL 分类、正文 URL 扫描 |
| ② 能力判定 | `attachments.contract.quality_of`（读 `capability.profile_of` 画像） | 是（读模型画像） | 质量四态 `native/text_full/meta_only/link_only` |
| ③ 装配 | `attachment_wire.expand_attachment_slots` + `media_payload` | 是 | `QUALITY_TO_DELIVERY` 派生投递动作，占位→wire part |

设计要点（均有代码佐证）：
- **单一管道**：前端 composer → `sanitize_refs` → `resolver`（唯一读盘点）→ `plan_refs`（唯一计划点）→ `build_user_turn_text`（占位入列）→ wire 边界 `expand_attachment_parts`（唯一展开点）。
- **薄前端厚后端**：识别、去重、质量判定、路由裁决全在后端；前端只做采集、投影、只读展示（`preflightItems.ts`、`QualityBadge.tsx` 均声明“零派生”）。
- **前后端单源**：模型能力矩阵经 `GET /attachments/capabilities` 与模型库 DTO `ref_quality_map` 下发，前端禁止再写死后缀表/大小上限（`attachments.py:226`、`model_service.py:335`）。

## 2. 输入通道：多媒体如何进入系统

前端输入入口集中在 `ChatInput.tsx`，三入口（按钮/拖拽/粘贴）统一落到 `handleFiles → uploadAttachments`（`ChatInput.tsx:783`）：

| 通道 | 触发 | 实现 |
|---|---|---|
| 文件上传 | 附件抽屉 / 按钮 | `uploadAttachments`，走附件上传白名单（后端 `accept` 唯一真源） |
| 拖拽文件 | `onDrop`，仅接管 `Files` 类型 | `filesFromDataTransfer` → `handleFiles`（`ChatInput.tsx:848`） |
| 粘贴截图 | `onPaste`，剪贴板含文件才接管 | 纯文本粘贴不拦截，避免挡正文（`ChatInput.tsx:869`） |
| 拖入链接 | `text/uri-list` 类型判据 | 交后端预检后 chip 化（`ChatInput.tsx:858`） |
| 粘贴/输入链接文本 | 正文整段交后端 `preflight` 扫描 | `captureUrlsFromText`，纯 URL 内容接管并从正文撤出（`urlCapture.ts:50`） |
| @ 引用 | `@` 补全 | 引用文件/目录路径 |
| 附件抽屉类型筛选 | `FileDrawer` | 后端 `expand_kind` 参数化 IN（`contract.py:56`） |

安全交互细节：拖拽只接管“带文件”与“链接”，普通文本拖拽放行浏览器默认；URL 采集的识别/去重/校验全部在后端完成，前端只消费逐项 `ok/reason` 与 `text_url_only`（`urlCapture.ts` 头注）。

## 3. 统一识别与分类：内容六类 + 来源四类

### 3.1 内容类型（content_kind）
`extract.py` 维护六分类后缀词典，是全文唯一真源（`extract.py:63`）：

| content_kind | 后缀集合（节选） |
|---|---|
| image | `.png .jpg .jpeg .gif .webp .bmp` |
| video | `.mp4 .mov .mkv .webm .avi .m4v` |
| audio | `.mp3 .wav .m4a .aac .flac .ogg .opus .wma` |
| richdoc | `.pdf .docx .xlsx .pptx` |
| text | `.txt .md .py .js .json .yaml .html .csv …`（大量代码/文本后缀） |
| binary / unknown | 其余后缀 / 无后缀兜底 |

### 3.2 来源类型（source_kind）
经 `contract.py` 收敛为 **4 类**：`file / selection / attachment / url`（`SOURCE_KINDS`，删除不可达的 log/message 内部来源）。

### 3.3 分类与扫描
- `classify_ref` 产出 `(source_kind, content_kind)`；url 来源只认“kind=url 或 有 url 且无 path”，带 path 的 file 不被 url 字段劫持；未知来源回落 file 路由，单条脏引用不崩整轮（`contract.py:44-47`）。
- URL 分类 `classify_url`（单参，纯依赖 url 本身）与 wire 展开期同源同判，消 suffixless URL 的“计划 native / 运行时降级”分叉。
- 正文 URL 扫描 `scan_text_urls`，上限 `MAX_TEXT_URLS = 8`（与 `contract.max_urls` 同常量）；裸链接正则不吞尾随标点（`extract.py:20`）。

## 4. 模型能力画像：理解能力的前提

多模态“理解”能否原生发生，取决于目标模型声明的能力画像。

- **声明真源**：配置 `ai.<provider>.model_meta.<model>.input_modalities`，经 `normalize_modalities` 归一到 `{text, image, audio, video, file}`。
- **画像构造**：`capability.profile_of(provider, model) → {modality: NativeCap}`（`capability.py:45`）。
  - 声明含某模态 → `NativeCap(native=True, transport={"inline"}, source="declared")`；
  - 实测 `media.accept[m] ∈ {url, both}` → 追加 `transport="url"` 并标 `source="measured"`（仅运输优化，不参与“是否原生”判定）。
- **设计原则**：声明即首选；实测探针只影响设置页展示与推荐排序，不改变运行时请求模式（避免过期样本误判）。

画像被三处同源消费：发送侧 `capability.profile(llm_model)`、预检侧 `preflight._resolve_profile(model_id)`、路由候选 `build_candidates`（`capability_router.py:132`）。

## 5. 质量四态与投递决策：保真梯度

状态模型已**正交化**（`contract.py:24`）：`quality`（保真档，不驱动装配）与 `delivery`（装配动作）分离，杜绝“一枚举背三义、凭它装配必然漏投”。

| quality | 含义 | delivery（`QUALITY_TO_DELIVERY` 单表派生） |
|---|---|---|
| native | 原生形态直接交给模型 | `slot`（写占位，wire 边界展开成 part） |
| text_full | 正文完整进入请求体 | `text` |
| meta_only | 仅注入抽取正文或文件元信息 | `text` |
| link_only | 只收到链接地址，未取内容 | `text` |

- `worst_quality`：逐项聚合，任一非 native 即 `degraded`（`preflight.py:57`）。
- `delivery` 不再单独枚举，一律由 `quality` 经单表派生（`render.py:66`、`message_builder.py:173`），消除装配与质量的口径分叉。
- 前端 `QualityBadge` 四档文案/配色单表（`QualityBadge.tsx:8`），与后端同源、前端零派生。

## 6. 原生多媒体理解与载荷构造（核心“理解”）

“理解”实际由上游多模态模型完成；OmniAgent 的职责是**把每类多媒体正确构造为 wire part**。载荷唯一构造点为 `media_payload.py`（`build_logical_part` / `to_wire_part` / `ensure_payload`）。

### 6.1 图片 image
- 原生路径：`image_url` part。
  - 内联：读盘（`_read_capped`）→ 超内联上限时压缩（缩图重编码，有 alpha 走 PNG 否则 JPEG；`ImageOps.exif_transpose` 把 EXIF 方向烧进像素，防竖直照片躺倒）→ base64 data URL；按「文件+上限+压缩参数」缓存复用，最多 8 条（`media_payload.py:73-91`）。
  - 直传：模型实测 `transport` 含 `url` 且外链合规 → 直传 `image_url`（免下载）。
- 内联上限 `media.inline_limit_mb`（默认 2MB，可调）；压缩参数 `compress_max_edge`（默认 2048）、`compress_jpeg_quality`（默认 85）。

### 6.2 音频 audio
- 原生路径：`input_audio`（内联 base64）或 `audio_url`（外链直传）。
- **格式不猜**：`to_wire_part` 按 mime 精确映射，仅 `wav` / `mp3`（`audio/mpeg → mp3`）走内联；非白名单容器返回失败，由调用方回落文本卡（`media_payload.py:16-17`）。

### 6.3 视频 video
- **仅外链直传** `video_url`。
- 本地视频不产内联 part：OpenAI 兼容 chat 方言无视频内联 part，`video_url` 需厂商侧可公网直连 GET，私有本地文件无公网地址 → 本地视频回落**文本元信息卡**（ffprobe 抽元数据，`FFPROBE_TIMEOUT=8s`，非零退出不抛、降级不阻断）。此为方言边界的明确未实现项（`media_payload.py:11-14`、`extract.py` 头注 S4）。

### 6.4 富文档 richdoc
- `richdoc_body` 真抽取（复用工具层四读取器）：PDF / Word / Excel / PowerPoint。
- 单 sheet 注入行上限 `RICH_MAX_ROWS = 200`，超出提示模型用 `read_xlsx` 等工具深读；抽取失败由 resolver 折算回执，不抛断轮。

### 6.5 文本 text
- `text_body`：≤ `TEXT_INLINE_MAX`（256KB）全文注入；超限走头尾摘录（`ARCHIVE_HEAD_LINES=40`），统一截断尾注（`app.wire_prefix.INLINE_TRUNCATED`）。

### 6.6 占位与 wire 展开（历史安全）
- `conversation_history` 恒为 `str`：附件写 `[[ATTACHMENT:<id>]]`、URL 写 `[[URL_ITEM:<b64url>]]` 占位入列，压缩/裁剪/持久化/回执零改动。
- 仅在 wire 边界 `expand_attachment_parts` 把占位展开成 parts，且须在落盘/日志取占位原文之后（防 base64 入库/入日志）。槽位来源唯一真源为 `ref_slots.SLOT_WRITERS`（`ref_slots.py:74`），新增来源加一条即自动纳入扫描。
- 展开失败（记录没了/超限/读不出）退化为一行说明文字，不阻断本轮（`attachment_wire.py` 头注边界 4）。

## 7. 降级与内容保真：绝不静默丢内容

能力不可达时按 `quality` 梯度降级，文本出口唯一（`extract.py` 公开名 + `render.py`）：

| 场景 | 降级产物 |
|---|---|
| 图片非视觉模型 | `image_card` 元信息卡 |
| 视频非原生 | `video_card`（ffprobe 元数据）+ 说明 |
| 音频非原生/容器不支持 | `audio_card` |
| 富文档抽取成功 | `richdoc_body` 抽取正文 |
| 富文档抽取失败 | `binary_card` / 回执警告 |
| URL 可抓文本 | `link_body`（下载后按文本出口注入正文，失败退链接文本） |
| URL 媒体内联 | `ensure_payload` 自理（下载→内联），失败降级 |

**附件物化**：本地 `file/selection` 的 image/audio 在“模型声明原生 + 大小 ≤ 内联上限 + 音频 wav/mp3”时，resolver 经 `_materialize_media → save_bytes` 入附件库（继承单文件/会话总量/sha 去重/会话归属），ref 补 `attachment_id` 后由计划器判 native；失败回落文本出口并下发 warn 回执（`resolver.py:42-49`）。这保证同一多媒体在后续轮次可持续原生复用。

`selection` 语义为文本行区间，指向 image/video/audio/richdoc 时显式 `dropped(selection_not_text)`，不物化、不产元信息卡（`resolver.py:50-51`）。

## 8. 输入预检与能力路由（[23] 阶段 D 核心新增）

### 8.1 预检端点（建议性，永不阻断）
`POST /inputs/preflight`（`inputs.py:38`），两阶段管线（`preflight.py:80`）：
1. 识别（模型无关，无条件执行）：`items[]` + 正文 `scan_text_urls` 合并 → `classify_ref`；
2. 能力判定（读画像）：`quality_of(source, kind, profile)` → 四态质量；准入复用 `url_reject_reason`（与下载同源同判）。

逐项产出 `key/source_kind/content_kind/ok/reason/quality/delivery/must_native/duplicate_of/url` + `worst_quality` + `routing_advice` + `text_url_only`。

**不做**：体积裁决、上限计数、下载、物化；`strict` 也只出建议，**拦截只在发送侧（409）**。预检整体有边界兜底：脏 items / 画像异常 / 模型库异常一律降级为空结果并告警，不放大为 500（`inputs.py:51-58`）。

### 8.2 能力路由（纯函数，零落库）
`capability_router.py`：
- `need_of(items, degraded_ok)`：聚合输入项原生需求。`content_kind∈{image,video,audio,richdoc}` 且 `quality != native` 才计入需求；**跳过 `ok=false` 与 `duplicate_of` 失败项**（失败项不产生流转需求）；`degraded_ok=True→optional_native`，`False→required_native`。
- `route(need, current_model, candidates, current_provider)`：
  - 无需求 → `keep`；
  - 无可行候选且必需 → `degrade`；可选无候选 → 静默 `keep`；
  - 有可行候选 → 裁决链 `_rank_key`：**同 provider → 实测优先(measured) → 上下文长度↓ → 配置顺序**，产出 `keep/switch`；`keep` 判定同时比对 `(model, provider)`，消同名异 provider 误判。
- `build_candidates`：候选唯一真源 = 模型库 `get_models()`，逐模型 `profile_of` 取原生/实测模态；短 TTL（30s）缓存并返回 tuple；单模型画像异常只跳过该模型、`context_length` 脏值安全解析为 0，不击穿全部候选。

### 8.3 路由模式与前端接线
- `mode: suggest | auto | strict`；`degraded_ok = (mode != strict)`。
- `useInputPreflight`：引用增删即防抖（150ms）整体重算，`seq` 递增丢弃迟到响应；无生效模型时不发预检（避免误报降级）；逐项 quality 按 key 回写 chip 徽标，`worst_quality`/`routing_advice` 直读后端。
- `RecommendationBar`：直读 `routing_advice` 原值，`switch` 渲染“切换”一键动作，`revertModel` 非空渲染“回退”；`keep` 且无回退不占位。
- `auto` 模式：`ChatInput.tsx:297` effect 自动切换，带 `autoSwitchedRef` 去重守卫**防回路**、切换前快照 `revertFrom` 供回退；会话切换复位路由会话态（`autoSwitchedRef/dismissedAdvice/revertFrom`），避免跨会话残留（`ChatInput.tsx:291`）。

## 10. 与 [23] 文档的落地状态对照（据实）

### 10.1 已实现
- 两阶段单一管道、质量四态 `native/text_full/meta_only/link_only`、`QUALITY_TO_DELIVERY` 单表派生投递。
- 输入预检端点 `POST /inputs/preflight`、永不阻断、逐项质量 + `worst_quality` + `routing_advice` + `text_url_only`。
- URL 一等引用：正文扫描接管、chip 化、非法即拒点名、纯 URL 撤出正文。
- 能力路由：`suggest/auto/strict`、`need_of`/`route` 裁决链、`build_candidates`。
- 前端：`useInputPreflight`（Composer 级重算）、`RecommendationBar`、`RoutingModePicker`、`QualityBadge`、附件抽屉类型筛选（`expand_kind`）。

### 10.2 已修正（阶段 D/D12 会审后）
- `need_of` 跳过 `ok=false`/`duplicate_of`（驳回项不污染路由需求）。
- `route` 的 keep 判定补 `(provider, model)` 比对（同名异 provider 不误判）。
- `build_candidates`：单模型画像异常隔离、`context_length` 安全解析、TTL 缓存 + 返回 tuple 防外泄篡改。
- `inputs.py` 整体边界兜底（脏 items/模型库异常不 500）、删死参 `session_id`。
- `preflight` 能力判定改实例口径（`quality_of` 透传 `has_slot`），消“预检报降级、运行时走原生槽”误报。
- `auto` 模式回环守卫 + 跨会话路由态复位 + 回退入口独立于建议存在。

### 10.3 未实现 / 受方言边界限制（如实标注）
- **视频内联理解**：未实现。OpenAI 兼容 chat 无视频内联 part，本地视频仅回落 ffprobe 元信息卡；仅外链 `video_url` 直传。代码注释明确为待扩展项（如 Gemini `inline_data`）。（`media_payload.py:11-14`）
- **本地视频帧抽取/理解**：未实现，仅元数据。
- **音频内联**：仅 wav/mp3，其他容器回落文本卡（格式不猜，非缺陷而是防误标）。

### 10.4 已知规范待收敛（非功能缺失，据阶段 D 会审）
- `RoutingAdvice` / `RoutingMode` 等值域在前后端多处重复声明为字面量，尚未收敛为单一共享契约。
- `urlCapture`（采集时）与 `useInputPreflight`（Composer 重算）各发一次预检，属当前实现的两次请求路径。

## 12. 各媒体 / 各来源渠道 输入操作指引

本章回答“用户怎么把某类媒体从某个渠道送进来，系统会怎样接收、物化、判质”。渠道路径与第 2 章一致，此处按“媒体类型 × 来源渠道”展开到可操作粒度。代码位置：`ChatInput.tsx`、`FileDrawer.tsx`、`uploadAttachment.ts`、`urlCapture.ts`、`resolver.py`、`contract.py`。

### 12.1 渠道定义与接管判据

| 渠道 | 用户操作 | 接管判据 | 处理落点 | 结果形态 |
|---|---|---|---|---|
| A 上传文件 | 输入区按钮或附件抽屉「上传文件」 | `accept` 白名单（后端 `capabilities.accept`），一次≤10 个 | `uploadAttachments`（`uploadAttachment.ts:105`） | 上传落盘→附件记录→`attachment` 引用（已物化） |
| B 拖拽文件 | 从资源管理器把文件拖进输入区 | `dataTransfer.types` 含 `Files` | `onDrop`→`filesFromDataTransfer`→`handleFiles`（`ChatInput.tsx:848`） | 同 A |
| C 粘贴文件/截图 | Ctrl+V 粘贴截图或复制的文件 | `clipboardData.files` 非空才拦截 | `onPaste`→`handleFiles`（`ChatInput.tsx:869`） | 同 A（截图自动命名） |
| D 拖入链接 | 从浏览器地址栏/页面链接拖入 | `types` 含 `text/uri-list` | `handleUrlText`→`captureUrlsFromText`（`ChatInput.tsx:858`） | 后端预检→URL chip |
| E 粘贴/键入链接 | 在正文粘贴或手输 URL | 正文整段交 `/inputs/preflight` 扫描；`text_url_only` 为真才撤出正文转 chip | `captureUrlsFromText`（`urlCapture.ts:50`） | 纯 URL→chip；混排保留正文 |
| F @ 引用 | 输入 `@` 触发补全，选文件/目录 | 项目内可链接相对路径；`@` 补全走 `probeRef` | 引用区 `file` 引用（未物化） | 发送时按需物化或走文本出口 |
| G 抽屉来源栏 | 附件抽屉点行加入本轮 | 六个来源栏互斥，各取唯一真源 | `FileDrawer.tsx` | 本会话附件/收藏/他会话附件为 `attachment`；项目文件/后端电脑为 `file` |
| H 产物存为附件 | 本会话产物行「存为附件」 | 产物为根内文件/根外产物 | `collectArtifact`→`enqueue` | 复制入附件库→`attachment` 引用 |

> 说明：`attachment` 来源（A/B/C/G 中的台账行、H）自带 `attachment_id`，注册在 `SLOT_WRITERS`，可直接写原生槽；`file` 来源（F、项目文件、后端电脑）未物化，不在 `SLOT_WRITERS`，由发送侧 `resolver._materialize_media` 在满足条件时补 `attachment_id` 后转原生（`resolver.py:42-49`）。

### 12.2 媒体 × 渠道 行为矩阵

| 媒体 | 上传/拖拽/粘贴（attachment） | @引用/项目文件/后端电脑（file，未物化） | 他会话附件/收藏（attachment） | URL（直链/网页） |
|---|---|---|---|---|
| 图片 image | 物化；模型声明视觉→`native` 内联；否则→`image_card`（`meta_only`） | 发送时若模型原生且≤内联上限→物化转 `native`；否则 `image_card` | 同左（跨会话自动升级全局） | 模型原生→按 `transport` 内联；否则 `link_body`（`link_only`） |
| 音频 audio | 物化；模型原生且容器为 wav/mp3→`native`；否则 `audio_card` | 同左（`resolver` 只对 image/audio 物化） | 同左 | 模型原生→内联；否则 `link_body` |
| 视频 video | 物化；模型原生→内联；否则 `video_card`（`meta_only`） | 不物化；模型原生→内联，否则 `video_card` | 同左 | 模型原生→内联；否则 `link_body` |
| 富文档 richdoc | PDF/Word/Excel/PPT；物化后模型有 file 槽→`native`，否则文本抽取 `text_full` | 文本抽取 `text_full`（`richdoc_body`） | 同左 | 运行时抓取正文（契约 `fallback_quality` 为 `link_only`，见第 13 章） |
| 文本/代码 text | 全文注入，受预算头尾裁剪 | 同左（`read_max_bytes`/`clip_text`） | 同左 | 运行时下载抽取正文（契约 `link_only`） |
| 二进制/压缩包 binary | 后端白名单外→415 拒绝（zip/exe 等） | 走 `binary_card`（`meta_only`），不读内容 | 同左 | `link_body` |

### 12.3 分媒体操作指引

**图片**
- 首选：Ctrl+V 粘贴截图，或上传/拖拽图片文件；单张 ≤ 后端图片档上限（默认 10MB）。
- 也可 `@` 或从「项目文件/后端电脑」引用本地图片：发送时由 resolver 在“模型声明视觉 + 不超内联上限”时自动物化为附件并走原生图片 part；不满足则产出图片档案卡（模型只看到元信息）。
- 模型无视觉能力时，任何渠道的图片都只会得到 `image_card`，不会静默丢失。

**音频**
- 用上传/拖拽（剪贴板一般不含独立音频文件）；单文件 ≤ 其他档上限（默认 20MB）。
- 原生内联仅支持 wav/mp3 容器；其余音频容器降级为 `audio_card`。
- `@`/项目文件来源的音频同样在发送时尝试物化，规则与上传一致。

**视频**
- 用上传/拖拽；`@`/项目文件引用不会物化，仅当模型原生支持视频时内联，否则 `video_card`（元信息卡）。
- 视频体积通常较大，优先上传走附件库，避免反复读盘。

**富文档（PDF/Word/Excel/PPT）**
- 上传/拖拽或 `@`/项目文件引用均可；默认文本抽取 `text_full` 进入正文。
- 已物化且模型具备文件原生槽时判 `native`；抽取失败会在附件页给出重跑入口。

**文本 / 代码**
- 直接粘贴正文，或 `@` 引用项目文件（可引用选区行区间）。
- 大文本按预算裁剪（头尾比例），超限部分不进入本轮。
- 选区引用（`selection`）只接受文本类文件；指向图片/音视频/富文档会被显式拒绝（`selection_not_text`）。

**链接（URL）**
- 两种操作：把链接拖进输入区（渠道 D），或直接粘贴/键入（渠道 E）。
- 只有“正文去掉链接后仅剩空白”（`text_url_only=true`）才把链接撤出正文、转为 URL chip；与文字混排时链接保留在正文，不做 chip 化。
- 网页/文档类链接在运行时下载并抽取正文；图片/音视频直链按模型原生传输能力内联，否则只传链接文本。
- 非法链接（协议/内网/体积等四闸门）在采集时即被拒并点名原因；超过引用配额的部分提示“未加入”。

**二进制 / 压缩包**
- 上传会被后端类型白名单拒绝（415）；`@`/项目文件引用只产出 `binary_card` 元信息，不解析内容。

### 12.4 通道共通约束
- 单批选择 ≤ 10，引用总数 ≤ 后端 `max_refs`；上传前做容量预检，避免“落库成功却入不了队”。
- 类型与大小上限的唯一真源是后端 `GET /attachments/capabilities`（`accept`/`limits`），前端不写死。
- 引用去重：前端按“归一路径 + 行区间”合并；URL 按 URL 归一。预检侧的键口径差异见第 13 章。

## 13. 代码审查：现存缺陷与风险

以下为对照前端采集链路与后端预检/解析/物化链路复核后，确认存在的实现缺陷或口径不一致；按影响面排序。仅列可定位到代码的事实，不含推测。

### 13.1 缺陷清单

| 编号 | 严重度 | 位置 | 现象 |
|---|---|---|---|
| D1 | 高 | `backend/app/services/inputs/preflight.py:63-69` | 注释与前端均约定“仅有 model 时退化按 model 解析”，但 `_resolve_profile` 只按 `/` 切分：无 provider 时 `provider=model、model=''`，`_meta_of` 因 model 为空返回空画像，导致所有条目被判非原生、`worst_quality` 假降级，并可能误出“切换模型”建议 |
| D2 | 中高 | `preflight.py:118-121` + `resolver.py:42-49` | 预检对未物化的 `file` 来源图片/音频按 `has_slot=False` 判 `meta_only`；但发送时 resolver 会在“模型原生 + ≤内联上限 + 音频 wav/mp3”时物化并判 `native`。同一引用在预检与运行时判质不一致，产生假降级徽标与误导的路由建议 |
| D3 | 中 | `contract.py:137-144` + `attachment_wire.py:149-150` | URL 文本/富文档契约 `fallback_quality=link_only`，但运行时 `fetch="text"` 会下载并注入正文（实际接近 `text_full`）。预检/徽标恒显示“仅链接”，`worst_quality` 对网页链接恒为 `degraded`，口径与真实投递不符 |
| D4 | 中 | `preflight.py:101-124` + `preflightItems.ts:40-43` | 预检去重键不含行区间：同一文件的两个不同选区（前端 `refKeyOf` 允许共存）在后端键相同，第二条被标 `duplicate_of`，且其 `quality` 为空串未被赋值 |
| D5 | 低 | `useInputPreflight.ts:77-78` | `qualityByKey[it.key] = it.quality` 无条件覆盖；当同键出现重复项（`quality=''`）时，会把首条已判定的质量覆盖为空，chips 徽标丢失 |
| D6 | 低 | `preflight.py:97-100` | `text_url_only` 用逐条 `str.replace` 判空：多个 URL 存在前缀包含关系时可能残留字符，把纯 URL 误判为混排（方向保守，结果是不 chip 化、保留正文） |
| D7 | 低 | `ChatInput.tsx:810-811` | 混排正文命中非法链接时，`urlHint='invalid-url'` 在 `!urlOnly` 提前返回之前设置；此时链接实际仍留在正文，提示与处理结果略不一致 |
| D8 | 低 | `FileDrawer.tsx` 上传 `accept` 绑定 `caps` | `capabilities` 未加载完成前 `accept` 为空，文件选择器不限类型，需依赖后端 415 兜底（体验层，不构成安全问题） |

### 13.2 修复建议（按缺陷）

- **D1**：`_resolve_profile` 在 `model` 为空时不要直接调用 `profile_of(provider, '')`。应显式区分“仅 model”与“未知模型”：前者按模型名在模型库中匹配唯一 provider 后取画像；匹配不到或不唯一时返回“未知画像”，预检对未知画像不判降级、不产生路由建议（与 `inputs.py` “无模型不路由”一致）。
- **D2**：预检应复用 resolver 的物化前置条件（模型原生、体积不超内联上限、音频容器白名单、是否已有会话）来决定 `file` 来源 image/audio 的可达质量；条件无法确定时以“未知”处理而非直接降级，避免与运行时相反。
- **D3**：让 URL 文本/富文档的预检质量与运行时 `fetch="text"` 对齐：可得正文的网页/文档按 `text_full` 预期展示（或引入“待抓取”态），不要把“可抓正文”的链接一律标成 `link_only`。
- **D4/D5**：预检键补入 `lineRange`（与前端 `refKeyOf` 同口径）；`qualityByKey` 写入时跳过空 `quality`，并对 `duplicate_of` 条目保留首条质量。
- **D6**：`text_url_only` 改为基于扫描区间的移除（记录每个 URL 的起止位置后统一裁剪），或先按 URL 长度降序替换，避免前缀包含导致残留。
- **D7**：把 `setUrlHint` 移到 `urlOnly` 判定之后，仅在链接真正被接管时给出非法链接提示。
- **D8**：`accept` 未就绪时禁用上传入口或提示“能力加载中”，避免选择器放开全部类型后由后端报 415。

### 13.3 非缺陷但值得关注
- 粘贴纯 URL 会触发两次预检：一次在 `urlCapture` 采集、一次在 Composer 级重算（`useInputPreflight`）。功能正确，但可合并为一次请求以降低时延与后端压力。
- 引用质量徽标、预检、路由建议三者当前共用 `worst_quality`，任何一条口径偏差都会同时放大到徽标与推荐条；D1/D2/D3 修复前，用户可能看到与真实投递不符的“降级/建议切换”。
