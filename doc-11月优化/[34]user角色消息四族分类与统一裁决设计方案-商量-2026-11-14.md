## 一、结论摘要

OmniAgent 落到 LLM 上下文里的 `role=user` 消息，实际有**两大类、四个族**（A 真实用户 / B 系统通知 / C 人类插话 / D 运行期合成；其中 B 按「有无活跃任务」再分 B1a/B1b 两支），它们在「是否落库、是否进 wire、是否展示、生命周期」上完全不同。**D 族中真正以 user role 进 wire 的只有 D1、D2**；B3 未调工具软引导现役为 **assistant role 持久消息**，不属 user 族，仅作对照列出（见 2.1/2.2）。过去多次优化（reasoning-only 空转防御、同签名工具死循环纠偏、B3 未调工具软引导、插话 inbox 吸收、临时消息发送即清）分别作用在不同族上。

**统一设计的核心不是把它们合并成一种，而是建立两条正交的身份轴，互不污染：**

| 轴 | 适用对象 | 载体 | 用途 |
|---|---|---|---|
| **落库身份（持久化）** | 真实用户消息 / 系统通知 / 人类插话 | `chat_user_message.msg_kind` + `chat_tasks.creation_source` | 历史回放、前端渲染、审计 |
| **运行期身份（内存）** | reasoning-only 警告（D1）/ 同工具纠偏（D2） | `conversation_history` 上的 `_temp_*` 或常驻标记 | 只服务当前任务本轮的 LLM 引导，绝不落库 |

二者**严禁互相套用**：给运行期消息补 `msg_kind` 会导致其被历史链路误持久化；给持久化消息套 `_temp_*` 会导致历史回放丢内容。这是本文档的第一道防退化红线。

### 2.2 各族代码锚点与语义

**A1 真实用户消息**
- 落库：`chat_user_message`，`msg_kind` 缺省 `'user'`。
- 进 LLM：`prepare_messages_for_llm` 从 `conversation_history` 取；`fetch_session_user_message_pairs` 只做历史回放。
- 前端：`TaskListPanel.tsx:448-485` 问题区，强文本样式 + 复制按钮。

**B1 系统通知（后台命令完成，按「有无活跃任务」分两支）**

B1 **不是一个族，而是同一事件的两条路径**，必须按场景分别渲染，不能揉成一族：

- **B1a 系统通知插话（会话有活跃任务）** — `bg_shell_notifier.py:37-41` → `task_registry.inject_system_notice`（`task/task_registry.py:150-193`）：消息 `msg_kind='system_notice'` 落库并投活跃任务 inbox，下一轮由 `_absorb_inbox` 吸收；**任务 `creation_source` 仍是 `'user'`（任务没变，只是被系统插了一条）**。渲染落点同 C1（「追加 N 条」），消息体加「系统通知」轻标。另有一条等价路径：`resume_session_with_notice` 竞态窗口（`stream_orchestrator.py:1155-1168`）判定后已有任务抢先注册 → 改走 `inject_message_to_task` 注入活跃任务并作废新任务，该通知消息同为 `msg_kind='system_notice'` 进 `merged_inputs`，渲染与吸收形态等同 B1a，不另立族。
- **B1b 续跑新任务（会话无活跃任务）** — `bg_shell_notifier.py:48` → `stream_orchestrator.resume_session_with_notice`（`stream_orchestrator.py:1125-1170`）：新建任务 `creation_source='system_resume'`，首条 user 消息 `msg_kind='system_notice'`。**它是一个正常新任务**，左右两侧照常输出/渲染；`user_input` 落库即通知原文——引用块/事项目录块仅在内存装配、不入库（`models.py` refs「当轮有效不入库」、DB 存 `message.content` 原文），故左栏正文无前缀块；照常渲染正文，只在消息头/尾加「续跑/系统通知」小标。
- 当前前端：`TaskListPanel.tsx:448-470` 用 `creation_source==='system_resume'` 把问题区渲染成灰字 + `SUCCESS` 左条 + 浅底（仅命中 B1b）；`TaskListPanel.tsx:417-430` 显示「续跑」徽标（B1b）。B1a 目前无独立样式，只混进「追加 N 条」。**并不存在「居中灰色通知条 + 齿轮图标」的现役 UI**。
- 进 LLM：B1a/B1b 的**当前轮**仍是 `role=user`（`[33]` 已实证 opencode synthetic→user role 同构），**不得在当前轮 LLM 边界按 `msg_kind` 过滤**。
- **瞬态裁剪（已是现役行为，须保留）**：`history_loader.py:245-247` 在装载**前序任务历史**时，遇 `msg_kind=='system_notice'` 跳过其 user 轮，只保留由它触发的 AI 答复（答复已吸收通知信息）。即系统通知是**瞬态输入**——渲染层照常展示，但不作为永久人类发言回灌历史；此为裁剪函数的既有功能，不得移除。

**C1 人类插话**
- 落库：`chat_user_message`，`msg_kind='user'`（插话就是真实人类输入，不是系统消息）。
- 归属：`inject_message_to_task` 把消息 id 挂到当前活跃任务，`list_session_tasks` 聚成 `merged_inputs`。
- 注入：`react_step._absorb_inbox`（`react_step.py:238-280`）在每轮 LLM 调用前 `drain_inbox` 并 `add_user_message` 并入；末条已 user 则并入末条，避免连续 user 破 OpenAI 交替性。
- 前端：`TaskListPanel.tsx:487-528`「↳ 追加 N 条」折叠块，逐条浅灰块展示。

**D1 reasoning-only 警告**
- `reasoning_guard.py:36-56`：连续 reasoning-only 无进展时，直接向 `conversation_history.append({role:'user', content: 任务+STAGNATION_WARNING})`。
- **设计意图：不挂 `_temp_`，常驻上下文**，空转期间反复提醒直到模型行动。这是「不持久化但常驻」的唯一样本。

**D2 同签名工具纠偏**
- `react_inference.py:150-168`：连续相同工具+相同参数，第 2/3/4 次各注入一条 `role=user` 纠偏，带 `_temp_same_tool_warn=True`，第 5 次硬终止（阈值见 `react_inference.py:41-43`）。
- 发送后由 `_temp_*` 清理机制脱落，不落库。

**B3 未调工具软引导（对照项，非 user 角色）**
- 现役 `services/agent/react_step.py:578-595`（场景 C）：reasoning-only 分支**只记 warning，不再注入**（警告已由 D1 `reasoning_guard.notify_stagnation` 统一发出，见 `react_step.py:582-586` 注释）；「answer 有内容但未调任何工具」分支走 `agent.message_builder.add_assistant_message(obs_text)`（`react_step.py:594-595`），是 **assistant role、无 `_temp_` 标记、随任务历史持久**的消息。
- 因此它**既不是 user 角色消息，也不是临时消息**，不参与本族谱「是否进 user wire」的判定。原文将其列为 D3 user 运行期消息、称带 `_temp_reasoning` 幂等 pop，与现役代码不符（`_temp_reasoning` 注入已于 2026-10-09 由 `notify_stagnation` 取代，现仅存于历史注释），此处据实更正。

> 说明：`_add_denial_feedback`（`observation_builder.py:49-77`）写入的是 `role=tool` 的 observation，不是 user 消息；但它与 D 族同属「运行期引导」，统一设计时一并纳入回归保护，避免误删。

1. 连续 reasoning-only 3 轮仍能触发 user 警告与终止。
2. 连续 5 次完全相同的工具调用仍被硬终止，且第 2/3/4 次有纠偏。

5. `_temp_*`、`_summary`、`user_message_id` 等内部标记不出现在 LLM wire。

## 四、三个争议点的裁决

### 4.1 主消息气泡 vs 居中灰色通知条（用户反馈点 2）

**现状澄清**：项目当前主视图是**流水线（pipeline）模式**——右侧 `PipelineRenderer` 渲染思考/工具/回答段，左侧 `TaskListPanel` 是任务清单。「居中灰色通知条 + 齿轮图标 + 不复制/不重发」这套是**消息流（气泡）视图**的形态，现役代码里没有实现；而且「齿轮」在现役 UI 是**工具执行等待图标**（`GearIcon` / `ToolWaitingIcon`），语义已被占用，拿它当系统通知图标会与工具等待混淆。

**裁决**：
- **不删**这套气泡/通知条的设计，但**明确其归属**：它是「消息流 UI 模式」的渲染方案，不是当前流水线模式的补丁。
- 近期**不实现**居中通知条与齿轮。当前 B1b 在流水线/左栏的灰字+绿条+「续跑」徽标已能表达「这是系统通知」，B1a 复用「追加 N 条」即可，满足可用性。
- 将「左右气泡模式 ↔ 流式瀑布模式」的切换作为**独立 UI 模式演进**（见第八章 roadmap），等消息流视图真正落地时，再按本文档的身份矩阵给 B1b 配通知条、给 B1a 配插话位、给 D 族永久不展示。
- **语义修正**：将来通知条图标不要用齿轮，改用「信息/通知」类图标，避免与工具等待齿轮撞语义。

### 4.2 左栏「追加N条」（用户反馈点 3）

**原方案的问题**：曾考虑「人类插话不应出现在追加N条（后端过滤）」，用户明确否决——插话本就应该被看到，过滤掉反而不合理。

**裁决**：
- **保留展示，不做后端过滤**。C1 插话继续聚合进 `merged_inputs`，继续显示「↳ 追加 N 条」。
- **用标记区分，而非隐藏**：在渲染层对 `merged_inputs` 中 `msg_kind='user'` 的项统一加轻量「插话」标识（小标签或左侧色条），不改库、不改正文。**不按正文前缀块判来源**——引用块/事项目录块仅在内存装配、不入库（`models.py` refs 当轮不入库、DB 存原文），落库正文恒为原始输入，故「正文已带前缀则不额外加壳」属死分支，已删除（见修订⑥）。
- 判定口径：C1 的 `msg_kind='user'` 与 A1 相同，**不能靠 msg_kind 区分插话与首次发问**；区分维度应是「该消息是否被并入某个已有任务」（即是否出现在 `merged_inputs`），这是任务归属维度，不是消息种类维度。禁止为了区分插话而给 C1 新造一个会破坏既有读取/渲染链路的枚举值。
- **B1a 同槽不同标**：B1a 系统通知插话也进 `merged_inputs`，与 C1 同落点，但它 `msg_kind='system_notice'`，故用「系统通知」小标区分；C1 仍用「插话」标识。二者共享「追加 N 条」容器，靠 `msg_kind` 区分标签。**该标签的 `msg_kind` 来自 DB（经 `list_session_tasks.merged_inputs` 外露），不依赖 inbox 元组**；inbox 仍是 `(content, uid)` 二元组，禁止为前端标签把 inbox 升三元组。

### 4.3 四族不混淆的统一判定原则（用户反馈点 4）

用户指出 user 消息经历多次优化（重复工具调用、reasoning_only 等），担心新设计让系统退化。裁决原则：

1. **按「谁写、写去哪、活多久」分类，不按文案分类。**
2. **持久化判定**：只有进 `chat_user_message` 的才谈 `msg_kind`；只在 `conversation_history` 的 D 族一律不碰持久化字段。
3. **进 wire 与展示解耦**：`msg_kind` / `creation_source` 只影响前端渲染与历史语义，**不得在 LLM 组装处当成过滤器**。

## 五、统一设计

### 5.1 标记体系（两条正交轴）

```
落库层（持久化，参与历史回放/前端渲染）
  chat_user_message.msg_kind
    'user'           ← A1 真实用户 / C1 人类插话（二者靠任务归属区分，不靠 msg_kind）
    'system_notice'  ← B1a/B1b 系统通知
  chat_tasks.creation_source
    'user' | 'system_resume' | 'system_triggered'  ← 任务级来源，前端主判定

  （注：B3 未调工具软引导为 assistant role 持久消息，不属本层，不参与 user 族）
  其它压缩/裁剪内部键       : _COMPACTION_TEMP_KEYS
```

### 5.2 前端渲染矩阵

| D1/D2 运行期（B3 为 assistant 对照项，不展示） | 无落库记录 | 不展示 | 不展示 |

### 5.3 后端规则

- 落库入口：`insert_user_message` 统一带 `msg_kind`，默认 `'user'`；系统通知显式 `'system_notice'`。
- 历史读取：`fetch_session_user_message_pairs`（storage.py:1046）已显式 SELECT 并外露 `msg_kind`（H8 已满足）；新增字段仍须补列，禁止依赖 `SELECT *`。

## 八、Roadmap：消息流视图与模式切换（暂不实施）

用户提出的「左右模式 ↔ 流式瀑布模式切换」作为独立 UI 演进，原则：

- **模式只影响渲染，不影响数据与 LLM**。切换开关是纯前端视图层状态，`msg_kind` / `creation_source` 语义在两种模式下一致。
- **流水线模式（现役）**：右侧分段渲染，左栏任务清单，保持现状。
- **消息流瀑布模式（未来）**：按会话顺序渲染气泡/通知条，复用本文 5.2 渲染矩阵。
- **切换不迁移数据**：同一份历史在两种模式下只是不同投影；不得为某模式单独落库或复制消息。
- 切换开关落地前，先完成 P0/P1，确保身份体系稳定，避免模式切换把 D1/D2 或 B1a/B1b 的渲染语义带偏。

## 九、不做什么（YAGNI）

- 不给 D 族（运行期消息）增加任何持久化字段。
- 不新增「插话」专属 `msg_kind` 枚举值（会破坏既有读取/渲染，且可用任务归属区分）。
- 不为 B1a 标签把 inbox 元组升三元组（标签取 DB `msg_kind`，inbox 保持 `(content, uid)`）。
- 不在 LLM 组装处按消息种类过滤 user 消息。
- 不在本期实现气泡/通知条 UI 或模式切换开关。
- 不为兼容旧字段保留双读分支。
