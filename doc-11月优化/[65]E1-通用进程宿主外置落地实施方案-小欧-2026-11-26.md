## 一、概念澄清：宿主、外置、内置分别是什么

方案开工前先把词说清，否则后面每一步都要打问号。

### 1.1 什么是"宿主"

**宿主（Host）= 一个专门用来"跑别人"的进程。**

它自己不干业务，只做三件事：接收指令、执行指令、回报结果。它的价值在于：**当它执行的东西把进程搞崩或搞卡时，崩溃范围只在这个进程里，真正干业务的主进程毫发无损。**

打个比方：主服务是"老板"，现在老板自己亲自下车间操作机床（`subprocess.Popen`）；机床卡死时，老板本人被卷进去，整个公司停摆。E1 的做法是**雇一个专门的工人（宿主进程），让工人去操作机床**——机床卡了，卡的是工人，老板照常办公，换一个工人继续。

**关键一点：这个工人不挑活。** 他只会"启动程序、收集输出、超时收工"这三件事，不关心启动的是 PowerShell、Node 还是 py-spy。所以这个宿主天生就是**通用进程执行能力**，不是 shell 专用（4.2.5 有实测证据）。

### 1.2 什么是"外置"

**外置（out-of-process / externalize）= 把这个动作从"本进程内执行"搬到"另一个进程执行"。**

对应的"内置"就是现在的情况：`execute_shell_command.py` 的 `shell()` 函数在被调用时，**在主服务进程内直接调用 `subprocess.Popen(...)`**——创建子进程这件事发生在主服务的解释器里。

所以：

| 说法 | 准确含义 |
|---|---|
| **现在的 shell 是"内置"的** | 创建 shell 子进程的动作，发生在主服务进程自己的 Python 解释器里（`execute_shell_command.py:1318/1350/1384`） |
| **"谁内置"** | 是**主服务进程自己**（`python run_server.py` 或 `OmniAgentBackend.exe` 那一个进程）在调 `subprocess.Popen` |
| **"外置"** | 把这个 `Popen` 调用搬到独立进程里。主进程只发一条"执行这个命令"的消息，不再碰 `Popen` |

**"内置"这个词的范围比 shell 大。** 全仓 18 个文件、28 处都在主进程内直接调 `subprocess.Popen`（清单见 4.2.5），shell 执行只是其中最主要的一处。所以外置的对象不是"shell"，而是"所有在主进程里创建子进程的动作"——这正是本文把模块命名为 `proc_host`（进程宿主）而非 `shell_host` 的原因。

### 1.3 为什么"内置"会出事：三个概念串起来

这里要把 [64] 2.8.2 的链条再说一次，因为这是整个 E1 的存在理由：

```
主服务进程内 Popen()
      ↓
CPython 的 _winapi.CreateProcess 调 CreateProcessW
      ↓
子进程要继承父控制台 → 内部走 GetConsoleMode 类 IOCTL → 跨进程问 conhost.exe
      ↓
conhost 不响应就无限等待
      ↓
★ 而 CPython 在整个 CreateProcessW 期间不释放 GIL
      ↓
★ 主进程全部 Python 线程冻结：事件循环停、看门狗停、心跳停
      ↓
用户看到"服务假死"，只能杀进程
```

三个致命点叠加：

1. **动作发生在主进程里**（内置）→ 卡住的是主进程；
2. **GIL 不释放** → 一条线程卡住等于全进程卡住，不是一个线程；
3. **超时机制管不到** → `drain_until_exit(proc, 600)` 的 600 秒超时只约束"读管道"，对"创建进程"这一步一步都不管（[42] 1.1 事故现场的 `_remaining = 599.9998042` 证明了这一点：超时一秒都没消耗就卡死了）。

外置之后，这三条同时被切断：在哪个进程卡（宿主）、会不会冻结全站（不会，宿主独立）、超时能不能管（宿主自己会被主进程超时杀掉重建）。

### 1.4 "进程宿主"和"沙箱"的区别

容易混，这里划清：

| 项 | 进程宿主（E1，本文） | 沙箱（`safety/sandbox/`，已有） |
|---|---|---|
| 目的 | **防止卡死传染主进程** | **防止危险命令破坏系统** |
| 换掉的是 | `CreateProcessW` 的调用位置 | 命令的权限、路径、内存上限 |
| 是否已有 | ❌ 未落地 | ✅ 已实现（Job Object + 工作区限制 + 内存上限） |
| 两者关系 | 互补，不替代。宿主内部执行时仍可套沙箱 | |

一句话：沙箱管"这条命令能干什么"，宿主管"这条命令把谁搞死"。两件事。

## 二、现状核查：内置到什么程度

### 2.1 主进程内创建子进程的位置（shell 为基础批，全量见 4.2.5）

`backend/app/tools/fundamental/execute_shell_command.py`（1499 行）的 `shell()` 函数，前台三处：

| 行号 | 分支 | 创建方式 |
|---|---|---|
| `:1318` | PS7 / PS5 | `subprocess.Popen([pwsh_exe, "-NoProfile", "-Command", cmd], ...)` |
| `:1350` | CMD | `subprocess.Popen(f'"{bat_path}"', shell=True, ...)` |
| `:1384` | bash | `subprocess.Popen([bash_exe, "--noprofile", "--norc", "-c", cmd], ...)` |

后台三处（`:1243 / :1251 / :1258`，`_popen_factory` 内），走 `shell_background.run_shell_background`。

沙箱一处：`safety/sandbox/backend.py:66`。

`notification`、`config_service` 各一处（非 shell，风险低）。

### 2.2 现有防护的边界

| 防护 | 位置 | 管什么 | 管不到什么 |
|---|---|---|---|
| `isolation_kwargs()` | `proc_io.py:45-63` | `CREATE_NO_WINDOW` + stdin=DEVNULL + STARTF_USESTDHANDLES，让子进程不继承控制台 | **只管"子进程不继承"，管不到"父进程自己调 CreateProcessW 时被 IOCTL 卡住"** |
| `FreeConsole`（[42] P0） | `console_mode.py:49-64` | 摘掉主进程与 conhost 的关联，父进程无控制台→子进程无从继承 | 路径仍存在，只是不再触发；若将来出现别的触发源（非控制台类 loader lock）依然会卡 |
| `spawn_gate` | `spawn_gate.py` | `CreateProcessW` × `Thread.start` 互斥，持锁超 8s 强制回收 | 是"事后补救"，回收一个已经卡住的线程，主进程仍是受损状态 |
| `drain_until_exit` 超时 | `proc_io.py:101` | 读管道超时即返回 | **对创建阶段零约束** |

结论：**现有防护把触发概率压得很低，但没有一条能把"卡住"的后果限制在可抛弃的范围内。** 这就是 E1 的位置。

### 2.3 为什么之前没有实施：四个原因

[42] 写于 2026-11-15，到今天 11 天。方案设计完整（协议、代码骨架、验收、回滚都有），却没落地。逐条分析：

**原因一：P0 + P1 见效太快，P3 的必要性被掩盖。**
[42] 的四阶段是"按见效速度/改动成本"排序：P0（`FreeConsole`，只改 py，重启即生效）、P2（指纹闭环）都很快落地了。P0 一落地，卡死现象立即消失——`logs` 里不再有 `database is locked`、不再有假死。**症状消失后，根治方案的优先级自然下降**。这是典型的"止血成功导致不治本"。

**原因二：改动面大，是唯一"需要重新打包 + 动核心执行路径"的阶段。**
P3 要新增两个模块、改 `execute_shell_command.py`（1499 行的核心工具）、改 `OmniAgentBackend.spec`（`hiddenimports` + 新增 `--proc-host` 启动分支）。相比之下 P0 只是加一次函数调用。风险与成本量级不同，自然被推迟。

**原因三：[42] 自己标注了一个未验证的前置条件。**
[42] 2.5 节写得很明确：「上面所有结论中，只有『`DETACHED_PROCESS` + 显式三句柄能否稳定跑 pwsh』未经本地实测……落 P3 前必须先跑这个探针，读结果再定宿主的创建参数」。附录 A 给了探针脚本，但**这个探针没有跑过**。也就是说：**方案卡在一个"待验证项"上，而这个待验证项没人跟进。**

**原因四：原方案里有一个隐患没被识别，导致方案"看起来不可行"。**
[42] 原设计用"单一命名管道 + JSON 行 + `id` 多路复用"。这个设计要手写：多路复用状态机、id 分发、并发调度、管道权限（`win32pipe.CreateNamedPipe` 的 9 个参数）。**光是"这一坨要自己保证正确"就足以让人望而却步**。而实际上，有更简单的做法（本文 4.3 节的一命令一连接），原设计把简单问题做复杂了，反而降低了可行性。

**结论：不是"忘了"，是"症状消失 + 成本高 + 有个待验证项卡着 + 原设计过复杂"四重叠加导致的自然搁置。** 本文把四件事逐条解决：症状消失不给推迟理由（因为它是根治，不是止血）、成本用分阶段压到最低、待验证项本次已全部跑完（见 4.2）、设计复杂度用一命令一连接砍掉。

## 三、目标与判据

### 3.1 一句话目标

**让主服务进程永不调用 `CreateProcessW`，从而把"卡死"的后果限制在一个可抛弃、可重建的宿主进程内。**

### 3.2 可验收的硬指标

| 指标 | 现在 | 目标 | 怎么量 |
|---|---|---|---|
| 主进程内 `CreateProcessW` 调用次数（前台 shell 路径） | 每次命令 1 次 | **0** | 代码审查 + `spawn_gate` 指标 `popen_count` |
| 卡死影响面 | 全站冻结 | 仅宿主冻结，主服务 ≤5s 自愈 | 注入卡死后 `/health` 响应时间 |
| 宿主创建模式 | — | `CREATE_NO_WINDOW`，禁 `DETACHED_PROCESS` | 见 4.2 实测 |
| 超时精度 | 创建阶段不受约束 | 宿主内 Job Object 杀树，误差 <0.1s | 见 4.2 实测 |
| 行为一致性 | — | 输出、退出码、`timed_out`、`truncated` 语义完全不变 | 现有测试全绿 |

### 3.3 明确不做

- 不改 `drain_until_exit` 的语义（宿主内继续复用它）。
- 不动 `isolation_kwargs()` 的参数（宿主内继续用它）。
- 不把后台 shell（`_popen_factory`）与沙箱纳入第一版（见 5.2 分阶段）。
- 不做多宿主负载均衡（单宿主够用，容量由 `_SHELL_PROC_SEM` 控制在 10）。

## 四、方案设计

### 4.1 架构对比

**现状（内置）**：

```
┌─ 主服务进程 ────────────────────────────────┐
│  execute_shell_command.shell()              │
│      ↓                                      │
│  subprocess.Popen()  ← ★ 卡在这里全站冻结    │
│      ↓                                      │
│  drain_until_exit()                         │
└─────────────────────────────────────────────┘
              ↓ CreateProcessW
         pwsh.exe / cmd / bash
```

**E1（外置）**：

```
┌─ 主服务进程 ─────────────────────────────┐
│  shell()                                 │
│      ↓                                   │
│  proc_host_client.run()  ← 只发消息      │
│      ↓ multiprocessing.connection        │
└──────┼───────────────────────────────────┘
       │ AF_PIPE（Windows 命名管道）
┌──────▼───────────────────────────────────┐
│  宿主进程 proc_host（独立，可抛弃）        │
│      ↓ 每命令一连接 / 一 Job Object        │
│  subprocess.Popen()  ← 卡在这里只冻宿主    │
│  Job Object 收编 → 超时 TerminateJobObject │
│  流式回传 stdout/stderr                   │
└──────────────────────────────────────────┘
              ↓ CreateProcessW
         pwsh.exe / cmd / bash
```

### 4.2 实测证据：五组 PoC，解决 [42] 遗留的四个未验证项

所有数据于 2026-11-26 本机实测（Python 3.13.11，14 核，PowerShell 7 位于 `E:\Appsw\powershell7\7\pwsh.exe`）。五组 PoC 依次回答五个问题：IPC 能不能用、超时怎么杀、宿主怎么起、能不能复用现成 Job、宿主是不是只能跑 shell。

#### 4.2.1 IPC 方案可行性：`multiprocessing.connection` 全通

[42] 原设计要先判断"pywin32 是否已有、没有就改 `multiprocessing.connection`"。**已核实：`pywin32>=306` 在 `requirements.txt:48`，且 `win32pipe` 可用。** 但实测表明**不需要 pywin32**——标准库的 `multiprocessing.connection`（Windows 走 AF_PIPE）已经足够，且代码量少一半：

| 测试 | 结果 |
|---|---|
| 基本执行 `cmd /c echo hello-poc` | ✅ `out=b'hello-poc\r\n'` rc=0，0.04s |
| 大输出流式（约 500KB） | ✅ `out_len=510000`，0.13s，分块回传无内存压力 |
| 超时（5s 命令，timeout=1s） | ✅ `timed_out=True` |
| 超时后宿主仍可用 | ✅ 后续命令正常返回 |
| **8 条命令并发** | ✅ 总墙钟 1.07s（8 条各约 1s，串行需 8s）→ **天然并发** |
| 客户端断开后宿主存活 | ✅ 正常处理后续连接 |

#### 4.2.2 超时策略：必须杀进程树，Job Object 最优

PoC 首轮暴露了一个 [42] 未识别的坑：**超时设 1s，实际耗时 3.08s**。原因是 `proc.kill()` 只杀了 `cmd.exe`，孙进程 `ping.exe` 仍活着并持有输出管道，读线程 `join` 卡满。

三种策略对比（命令 `cmd /c ping -n 6 ... & echo never-reached`，约 5s，超时设 1s）：

| 策略 | 实际耗时 | 判定 | 评价 |
|---|---|---|---|
| `proc.kill()`（只杀根） | **5.06s** | ❌ 严重超标 | 孙进程持管道，超时语义完全失效 |
| `taskkill /F /T /PID` | 1.25s | ✅ | 可用，但要额外创建 taskkill 进程（又踩 `CreateProcessW`） |
| **Job Object + `TerminateJobObject`** | **1.02s** | ✅✅ 最优 | 内核级杀整棵树，零额外进程，无残留（二次验证 `ping.exe` 前后均 0） |

**定案：宿主内每个子进程创建后立刻 `AssignProcessToJobObject`，超时用 `TerminateJobObject`。**

但**不能直接复用沙箱的 `SandboxJob`**——这一点经实测证伪，见 4.2.4。

#### 4.2.3 宿主创建模式：`DETACHED_PROCESS` 会静默丢输出（比崩溃更危险）

这是 [42] 附录 A 明确要求"落 P3 前必须先跑"的探针，本次跑完，结论**推翻了原假设**。

[42] 原文判断：「纯 `DETACHED_PROCESS` 实测 pwsh 会立即退出」。实测显示更糟：

| 创建模式 | pwsh7 | ps5 | cmd | bash |
|---|---|---|---|---|
| `inherit` | ✅ `ok-pwsh` 0.46s | ✅ 0.20s | ✅ 0.03s | ✅ 11.61s（WSL 慢） |
| `CREATE_NO_WINDOW` | ✅ `ok-pwsh` 0.30s | ✅ 0.22s | ✅ 0.03s | ✅ 0.20s |
| `DETACHED_PROCESS` | ⚠️ **rc=0 但 stdout 为空** | ⚠️ **rc=0 但空** | ✅ | ✅ |
| `DETACHED_PROCESS\|NEW_PROCESS_GROUP` | ⚠️ **rc=0 但 stdout 为空** | ⚠️ **rc=0 但空** | ✅ | ✅ |
| `CREATE_NEW_CONSOLE` | ✅ 0.45s | ✅ 0.39s | ✅ 0.15s | ✅ 0.33s |

**关键发现：`DETACHED_PROCESS` 下 pwsh/ps5 的返回码是 0，但 stdout 是空字符串。** 它不是"立即退出"，而是**跑完了但把所有输出丢了**。这比崩溃危险得多——因为上层判定逻辑看到 `rc=0 + 无输出`，会走进 `else` 分支判为"命令成功但无产出"，模型会收到"执行成功、没有输出"，从而误以为命令没产生结果，**静默丢掉真有价值的输出**。

**定案：宿主进程用 `CREATE_NO_WINDOW` 创建，禁止 `DETACHED_PROCESS`。** 安全性靠 [42] P0 已落地的前提保证——主进程已 `FreeConsole`（实测打包态 PID 12668 不在 13 个 conhost 的父进程列表中），因此宿主也无控制台可继承，`CREATE_NO_WINDOW` 此时退化为普通创建。

#### 4.2.4 关键反证：不能复用 `SandboxJob`（它会放跑孙进程）

初稿曾计划"直接复用 `safety/sandbox/job_object.py` 的 `SandboxJob`，不新写"。实测推翻了这个想法。

`SandboxJob.__init__`（`job_object.py:51-53`）置了三个标志：

```python
info.BasicLimitInformation.LimitFlags = (
    JOB_OBJECT_LIMIT_PROCESS_MEMORY | JOB_OBJECT_LIMIT_ACTIVE_PROCESS
    | JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK)     # ★ 这一条是致命的
```

`SILENT_BREAKAWAY_OK` 的含义是：**Job 内进程创建的子进程会自动脱离 Job**。这个设置在沙箱场景是**故意**的（`job_object.py:48-50` 注释："加 SILENT_BREAKAWAY_OK，覆盖任意 shell 后台进程，预检杀树不误杀"），但在进程宿主场景下效果正好相反——它让 `kill_tree()` 杀不到孙进程。

三组对照实测（命令 `cmd /c ping -n 20 127.0.0.1`，ping 作为 cmd 的孙进程）：

| 组 | Job 配置 | 杀树前 ping | 杀树后 ping | 判定 |
|---|---|---|---|---|
| A | 仅 `KILL_ON_JOB_CLOSE`（无 BREAKAWAY） | 1 | **0** | ✅ 孙进程已杀 |
| B | `PROCESS_MEMORY \| ACTIVE_PROCESS \| SILENT_BREAKAWAY_OK`（沙箱同配置） | 1 | **1** | ❌ **孙进程残留** |
| C | 直接 `import` 项目 `SandboxJob` | 1 | **1** | ❌ **孙进程残留** |

**结论：若照 4.5.1 骨架直接用 `SandboxJob`，超时杀树会完全失效**——`ping` 残留、继续持有输出管道、宿主随后卡在 `pump` 线程 `join` 上，等于把原来的问题原样搬进宿主。

**定案：为宿主新建独立 Job，配置为 `KILL_ON_JOB_CLOSE`（可选叠加 `PROCESS_MEMORY`/`ACTIVE_PROCESS`），绝不含 `SILENT_BREAKAWAY_OK`。** 实现位置选 `app/utils/win_job_object.py`（该文件已定义全部 ctypes 结构体，只缺 `create/assign/terminate/close` 四个薄函数），作为公用函数登记到 `backend/FUNCTIONS.md`。

这是"复用优先"原则的一个反例：**复用前必须核对被复用物的语义是否与当前场景一致**。沙箱 Job 的语义是"别误杀后台进程"，宿主的语义是"务必杀干净"，两者相反，不能共用同一个配置。

#### 4.2.5 通用性验证：同一宿主承载异构程序

这一节回答"这个宿主是 shell 专用，还是通用能力"。结论：**协议天然通用，必须按通用设计实现，否则全仓 17 处同类调用点将来各写一遍。**

先看全仓子进程创建点的分布（排除 `backup/`、`tests/`、`_internal/`）：

| 分类 | 文件 | 处数 | 程序 |
|---|---|---|---|
| shell 执行 | `tools/fundamental/execute_shell_command.py` | 6 | pwsh / cmd / bash |
| 系统查询与操作 | `tools/system/`（find_command、delete_task、event_log、list_tasks、create_task） | 8 | powershell |
| 注册表 | `tools/win_registry/`（read、delete） | 3 | powershell reg |
| 环境探测 | `services/prompts/system_adapter.py` | 2 | powershell 版本 |
| 语法校验 | `tools/toolhelper/syntax_validator.py` | 1 | node |
| 媒体元数据 | `attachments/extract.py` | 2 | ffprobe / ffmpeg |
| 其它 | `send_notification.py`、`model/config_service.py`、`monitoring/loop_watchdog.py`(py-spy)、`safety/sandbox/backend.py`、`shell_engine.py`、`tool_fc_helper.py` | 6 | 各种 |

**共 18 个文件、28 处。全部是"短命、一次一来回、输出即完"的特征，与宿主模型完全匹配。**

宿主接口只有 `argv / cwd / env / timeout / stdin`，**不含任何业务语义**（不认识"shell"这个词）。这一点由 PoC 直接验证——同一宿主连续执行 4 种异构程序：

| 程序 | 结果 |
|---|---|
| `pwsh -Command 'hello-from-pwsh'` | ✅ rc=0，0.52s |
| `node -e "console.log('hello-from-node')"` | ✅ rc=0，0.05s |
| `py-spy --version` | ✅ rc=0，0.57s，输出 `py-spy 0.4.2` |
| `cmd /c echo hello-from-cmd` | ✅ rc=0，0.02s |

以及三项关键能力验证：

| 验证 | 结果 |
|---|---|
| 8 条并发异构命令（pwsh/node/py-spy/cmd 混合） | ✅ 墙钟 0.27s，全部 rc=0（真并发） |
| 超时杀树对 `node -e "while(1){}"` 死循环 | ✅ `timed_out=True`，耗时 1.01s |
| 超时后宿主仍可用 | ✅ 后续命令正常返回 |

**结论：通用化不是"设计野心"，是"事实"。** 若只做成 shell 专用，将来 `tools/system/*` 的 8 处、注册表 3 处、`extract.py` 2 处都要重走一遍同样的搬迁——那不是复用，是复制 17 次。

**但通用不等于万金油**，边界必须写死（防过度设计）：

| 该通用 | 不该通用（过度设计，明确禁止） |
|---|---|
| 执行一个程序、回传输出、超时杀树 | ❌ `kind="shell"\|"ffprobe"\|"reg"` 之类类型分发 |
| `argv / cwd / env / timeout / stdin` | ❌ 插件注册表 / 扩展点 / 工厂模式 |
| 流式 out/err 分块、`timed_out`、`truncated` | ❌ 业务层参数校验（留在各调用方） |

**判据一句话：接口里只要出现任何一个业务名词，就说明抽象错了。** `run(argv)` 是唯一接口，符合 KISS-DIRECT。

**确实不适合的一类（说清边界，不硬塞）**：

| 场景 | 为什么不适合 | 当前是否涉及 |
|---|---|---|
| 需要持久双向交互（stdio MCP server、交互式 REPL、持续喂 stdin） | "一命令一连接"模型不匹配，需长连接 + 多路复用 | ❌ 当前 MCP 全走 HTTP（`mcp_client.py:82` 用 httpx POST），无 stdio 形态 |
| 需要长期存活的守护进程 | 生命周期模型不同 | ❌ 无 |

即：**当前全仓 28 处子进程创建点全部适配本宿主，无例外。** 将来若接本地 stdio MCP，需单独设计长连接宿主，不能硬塞进这个模型。

### 4.3 协议设计：一命令一连接（对 [42] 的改进）

[42] 原设计是"单一命名管道 + JSON 行 + `id` 多路复用"。本文改为**一命令一连接**，理由三条：

| 维度 | [42] 单管道 + id 复用 | 本文一命令一连接 |
|---|---|---|
| 并发 | 需手写 id 分发表 + 多路复用状态机 | **天然并发**，每连接独立（实测 8 并发 1.07s） |
| 取消 | 需发 `cancel(id)` 请求，宿主维护状态 | **连接断开 = 命令取消**，无需协议字段 |
| 代码量 | 状态机 + id 管理，约 200 行 | 约 80 行 |
| 故障定位 | 一条管道出错影响所有命令 | 一条连接出错只影响该命令 |
| 开销 | 无（复用） | 每命令一次 `Client()` 连接，实测 0.04s 内完成，可忽略 |

符合 KISS-DIRECT：**能用"多连接"天然解决的，不要用"单连接 + 多路复用"手写解决。**

协议帧（繁体为消息类型，均为 Python `dict`，经 `multiprocessing.connection` 传输）：

```
客户端 → 宿主（连接建立后首帧）:
  {"argv": [...], "cwd": str|None, "env": dict|None, "timeout": float|None}
  # 注意：env 已在主进程侧由 _sanitize_env() 处理完毕，宿主不再过滤

宿主 → 客户端（可多次，流式）:
  {"type": "out", "data": b"..."}      # stdout 分块
  {"type": "err", "data": b"..."}      # stderr 分块
  {"type": "done", "rc": int, "timed_out": bool, "truncated": bool, "pid": int, "elapsed": float}
  {"type": "error", "message": str}    # 创建失败（如找不到可执行文件）
```

`truncated` 语义与 `proc_io.drain_until_exit` 的第四返回值一致：进程已退出但管道被孙进程持有，有界等待后放弃残留输出。

### 4.5 代码骨架

#### 4.5.1 宿主 `backend/app/utils/proc_host.py`

```python
# -*- coding: utf-8 -*-
# 编辑历史:
# 2026-11-26 - 小欧 - 新建: 通用进程宿主(一命令一连接, Job Object 杀树; 接口只有 argv/cwd/env/timeout, 无业务语义)
"""proc_host — 通用进程宿主进程

【为什么独立进程】CreateProcessW 卡在控制台 IOCTL 时不释放 GIL, 同解释器内任何线程
(含看门狗、join 超时)都无法执行。唯一能把"卡住"限制在可抛弃范围的边界是进程边界。

【协议】AF_PIPE + multiprocessing.connection, 一命令一连接(无 id 多路复用):
  首帧 {"argv","cwd","env","timeout"} → 流式 {"type":"out"|"err","data":b} → {"type":"done",...}
  连接断开 = 命令取消。

【超时】每子进程挂 Job Object, 超时 TerminateJobObject 杀整棵树(实测 1.02s,
  对比 proc.kill() 5.06s —— 孙进程持管道会让根 kill 无效)。

【创建模式】宿主自身由主进程以 CREATE_NO_WINDOW 拉起; 禁用 DETACHED_PROCESS
  (实测该模式 pwsh/ps5 返回 rc=0 但 stdout 为空, 静默丢输出)。
"""
import ctypes
import os
import subprocess
import sys
import threading
import time
from multiprocessing.connection import Listener

PIPE_NAME = r"\\.\pipe\omni-proc-host"
AUTHKEY = b"omni-proc-host-key"
CONCURRENCY = int(os.environ.get("OMNI_PROC_HOST_CONCURRENCY", "12"))


def _serve_forever() -> None:
    """宿主主循环: 常驻 accept, 每连接一线程。"""
    listener = Listener(PIPE_NAME, authkey=AUTHKEY)
    _log(f"listening on {PIPE_NAME}, concurrency={CONCURRENCY}")
    _slots = threading.BoundedSemaphore(CONCURRENCY)
    while True:
        try:
            conn = listener.accept()
        except (OSError, EOFError):
            break
        threading.Thread(target=_handle, args=(conn, _slots), daemon=True).start()


def _handle(conn, slots) -> None:
    """一连接一命令。"""
    # 2026-11-26 - 独立 Job: 禁用 SILENT_BREAKAWAY_OK, 否则孙进程逃离 Job, kill_tree 失效
    #   (实测: SandboxJob 配置下 cmd/c ping 的 ping 残留; 仅 KILL_ON_JOB_CLOSE 时被杀净)
    from app.utils.win_job_object import (
        assign_to_job, close_job, create_kill_on_close_job, terminate_job,
    )
    job = None
    proc = None
    try:
        req = conn.recv()
        argv = req["argv"]
        if not slots.acquire(blocking=False):
            _send(conn, {"type": "error", "message": "宿主并发已达上限"})
            return
        try:
            t0 = time.monotonic()
            from app.utils.proc_io import isolation_kwargs
            try:
                proc = subprocess.Popen(
                    argv, cwd=req.get("cwd"), env=req.get("env"),
                    stdout=subprocess.PIPE, stderr=subprocess.PIPE,
                    **isolation_kwargs())
            except OSError as e:
                _send(conn, {"type": "error", "message": f"{type(e).__name__}: {e}"})
                return
            try:
                job = create_kill_on_close_job()
                assign_to_job(job, proc)      # 提权/收编失败上抛, 不静默
            except OSError as e:
                _log(f"job assign failed pid={proc.pid}: {e}; fallback to kill")
                if job is not None:
                    close_job(job)
                job = None

            pumps = [
                threading.Thread(target=_pump, args=(proc.stdout, "out", conn), daemon=True),
                threading.Thread(target=_pump, args=(proc.stderr, "err", conn), daemon=True),
            ]
            for t in pumps:
                t.start()

            timed_out = False
            try:
                proc.wait(timeout=req.get("timeout"))
            except subprocess.TimeoutExpired:
                timed_out = True
                if job is not None:
                    terminate_job(job)        # TerminateJobObject, 内核级杀整棵树
                else:
                    try:
                        proc.kill()
                    except OSError:
                        pass
                try:
                    proc.wait(timeout=3)
                except subprocess.TimeoutExpired:
                    pass
            for t in pumps:
                t.join(timeout=3)

            truncated = any(t.is_alive() for t in pumps)
            _send(conn, {
                "type": "done",
                "rc": proc.returncode if not timed_out else -1,
                "timed_out": timed_out, "truncated": truncated,
                "pid": proc.pid, "elapsed": round(time.monotonic() - t0, 3),
            })
        finally:
            slots.release()
    except (EOFError, BrokenPipeError, OSError):
        # 客户端断开(主进程被杀/取消): 杀掉该命令树, 不留孤儿
        if job is not None:
            try:
                terminate_job(job)
            except Exception:
                pass
        elif proc is not None:
            try:
                proc.kill()
            except OSError:
                pass
    finally:
        if job is not None:
            try:
                close_job(job)                # KILL_ON_JOB_CLOSE: 句柄关闭即杀全树, 幂等安全
            except Exception:
                pass
        try:
            conn.close()
        except Exception:
            pass


def _pump(stream, kind, conn) -> None:
    """流式读一路输出并回传; 连接断开即停止(调用方已死, 无需继续攒数据)。"""
    while True:
        try:
            chunk = stream.read(8192)
        except (ValueError, OSError):
            return
        if not chunk:
            return
        if not _send(conn, {"type": kind, "data": chunk}):
            return


def _send(conn, obj) -> bool:
    try:
        conn.send(obj)
        return True
    except (BrokenPipeError, OSError, EOFError):
        return False


def _log(msg: str) -> None:
    print(f"[proc_host] {msg}", flush=True)


def main() -> None:
    """宿主入口。frozen 时由 run_server.main() 按 --proc-host 直接调用。"""
    try:
        _serve_forever()
    except Exception as e:
        _log(f"fatal: {type(e).__name__}: {e}")
        raise


if __name__ == "__main__":
    main()
```

#### 4.5.2 客户端 `backend/app/utils/proc_host_client.py`

```python
# -*- coding: utf-8 -*-
# 编辑历史:
# 2026-11-26 - 小欧 - 新建: 进程宿主客户端(自愈重建, run() 与 drain 语义对齐)
"""proc_host_client — 与 drain_until_exit 语义对齐的宿主调用层

对外只有一个函数 run(), 返回四元组 (stdout_b, stderr_b, timed_out, truncated),
与 proc_io.drain_until_exit 完全一致, 调用方替换成本最低。

自愈: 连接失败(宿主未起/已死) → 拉起宿主并重试一次; 宿主在跑但连接超时 →
      杀宿主进程树后重建。绝不让调用方感知宿主生命周期。
降级: OMNI_PROC_HOST=0 时抛 _Disabled, 调用方回退本地 Popen 分支。
"""
import os
import subprocess
import sys
import threading
import time
from multiprocessing.connection import Client

PIPE_NAME = r"\\.\pipe\omni-proc-host"
AUTHKEY = b"omni-proc-host-key"
_CONNECT_TIMEOUT = 3.0      # 单次连接尝试上限
_START_WAIT = 10.0          # 拉起宿主后等其就绪的上限

_host_proc = None
_host_lock = threading.Lock()


class Disabled(RuntimeError):
    """宿主被配置关闭; 调用方应回退本地 Popen。"""


def _enabled() -> bool:
    return os.environ.get("OMNI_PROC_HOST", "1") != "0"


def _spawn_host() -> None:
    """拉起宿主: CREATE_NO_WINDOW(不用 DETACHED, 实测会静默丢 pwsh 输出)。"""
    global _host_proc
    if getattr(sys, "frozen", False):
        argv = [sys.executable, "--proc-host"]
    else:
        argv = [sys.executable, "-m", "app.utils.proc_host"]
    flags = subprocess.CREATE_NO_WINDOW if sys.platform == "win32" else 0
    _host_proc = subprocess.Popen(
        argv, stdin=subprocess.DEVNULL, stdout=subprocess.DEVNULL,
        stderr=subprocess.DEVNULL, creationflags=flags, close_fds=True)
    # 等管道可用
    deadline = time.monotonic() + _START_WAIT
    while time.monotonic() < deadline:
        try:
            c = Client(PIPE_NAME, authkey=AUTHKEY)
            c.close()
            return
        except (OSError, EOFError):
            time.sleep(0.05)
    raise RuntimeError("shell host 启动超时")


def _connect() -> "Client":
    """连接宿主; 失败则拉起后重试一次。"""
    try:
        return Client(PIPE_NAME, authkey=AUTHKEY)
    except (OSError, EOFError):
        with _host_lock:
            _spawn_host()
        return Client(PIPE_NAME, authkey=AUTHKEY)


def run(argv, cwd=None, env=None, timeout=None):
    """执行一条命令, 返回五元组 (stdout_b, stderr_b, timed_out, truncated, rc)。

    rc = 子进程退出码(超时为 -1)。之所以比 drain_until_exit 多带一个 rc, 是因为
    drain_until_exit 从 proc 对象上取 returncode, 而宿主路径下调用方拿不到 proc。
    调用方改造时: returncode = rc, 其余四项语义与 drain_until_exit 完全一致。

    宿主异常时抛 RuntimeError, 调用方按降级策略决定是否回退本地 Popen。
    """
    if not _enabled():
        raise Disabled("OMNI_PROC_HOST=0")
    conn = _connect()
    out, err = [], []
    timed_out = truncated = False
    rc = -1
    try:
        conn.send({"argv": argv, "cwd": cwd, "env": env, "timeout": timeout})
        while True:
            msg = conn.recv()
            t = msg["type"]
            if t == "out":
                out.append(msg["data"])
            elif t == "err":
                err.append(msg["data"])
            elif t == "error":
                raise RuntimeError(msg["message"])
            elif t == "done":
                rc = msg["rc"]
                timed_out = msg["timed_out"]
                truncated = msg["truncated"]
                break
    except (EOFError, BrokenPipeError, OSError) as e:
        # 宿主中途死亡: 视为该次执行失败, 上层按 error 处理, 下次调用自愈
        raise RuntimeError(f"shell host 通信中断: {type(e).__name__}: {e}") from e
    finally:
        try:
            conn.close()
        except Exception:
            pass
    return b"".join(out), b"".join(err), timed_out, truncated, rc
```

> 返回值定为**五元组**（比 `drain_until_exit` 多一个 `rc`）：宿主路径下调用方拿不到 `proc` 对象，取不到 `proc.returncode`，必须由客户端回传。改造时 `returncode = rc`，其余四项语义不变。

```python
            # 降级: 原本地 Popen 路径 (保留原代码不动, 见 4.6 阶段一)
            proc = subprocess.Popen([...], **_iso)
            stdout_b, stderr_b, timed_out, truncated = drain_until_exit(proc, ...)
            if truncated: kill_process_tree(proc); stderr_b += TRUNCATED_NOTE
            if timed_out:
                _tail_out, _tail_err = _kill_and_read_output(proc)
                stdout_b += _tail_out; stderr_b += _tail_err
            returncode = proc.returncode if proc.returncode is not None else -1
        except RuntimeError as e:
            # 宿主通信失败: 返回 error 结构, 不静默
            llm = _build_execute_shell_command_llm_data(
                "error", int((_time_mod.perf_counter() - t0) * 1000),
                processed_command, -1, shell_type, ERR_SHELL_EXCEPTION,
                f"进程宿主不可用: {e}", timeout=timeout, cwd=cwd or "",
                hint="宿主进程异常, 系统会自动重建; 若反复出现请查看 logs", cmd_short=cmd_short)
            return build_error(data={}, llm_data=llm)
        else:
            if truncated:
                stderr_b += TRUNCATED_NOTE
        stdout_str = _fix_encoding(_decode_bytes_safe(stdout_b))
        stderr_str = _fix_encoding(_decode_bytes_safe(stderr_b))
```

CMD 分支注意：`shell=True` + `.bat` 的路径，宿主内同样支持（`argv` 传 `f'"{bat_path}"'`，`shell=True` 需在宿主内判断）。为降低复杂度，**建议 CMD 分支在阶段一仍保留本地 Popen，阶段三再切**（见 5.2）。

### 4.6 分阶段落地

**核心原则：设计一次做通用，实施一次只切一条分支。** 模块从第一天就是通用的 `proc_host`，但调用点逐个迁移，每步跑稳再走下一步。

| 阶段 | 范围 | 验证期 | 回滚 |
|---|---|---|---|
| **阶段一** | 只切 **PS7/PS5 分支**（`:1318`，最常卡的一条）；CMD、bash 保留本地 Popen | 跑一周无回归 | `OMNI_PROC_HOST=0` 重启 |
| **阶段二** | 切 **bash 分支**（`:1384`） | 跑三天 | 同上 |
| **阶段三** | 切 **CMD 分支**（`:1350`，`shell=True` 需宿主内特殊处理）+ 后台 `_popen_factory` | 跑三天 | 同上 |
| **阶段四（可选，按需）** | 分批接入其它 22 处：`tools/system/*` 8 处 → `win_registry/*` 3 处 → `system_adapter.py` 2 处 → `syntax_validator.py` 1 处 → `extract.py` 2 处 → 其余 6 处 | 每批跑三天 | 同上 |
| 独立评估 | 沙箱 `sandbox/backend.py:66`（涉及安全语义，单独评估，不随本方案） | — | — |

阶段四不设完成期限——它的价值是"哪天某处再出卡死，切过去就行"，而不是"必须全部搬完"。**通用宿主的存在本身就消除了"将来要重复建设"的风险**，这是它与 shell 专用方案的实质差别。

## 五、与 [42] 原设计的差异（改进点汇总）

| # | [42] 原设计 | 本文 | 依据 |
|---|---|---|---|
| 1 | 单命名管道 + JSON 行 + `id` 多路复用 | **一命令一连接** | 4.2.1 实测天然并发（8 条 1.07s），省掉 200 行状态机，符合 KISS-DIRECT |
| 2 | IPC 依赖 `win32pipe`（当时待确认） | **`multiprocessing.connection`**（标准库，已验证） | 4.2.1 全通；少一半代码；pywin32 虽已装但不必依赖 |
| 3 | 超时"杀宿主重建" | **宿主内每命令挂独立 Job，超时只杀该命令树** | 4.2.2 实测：Job Object 1.02s，`kill` 5.06s；"杀宿主重建"会连累并发中的其他命令 |

| 6 | 改 `proc_spawn.spawn()` 统一出口 | **不引入 `spawn()`**（已在 [42] v1.2 按 YAGNI 删除），宿主内直接用 `subprocess.Popen` + `isolation_kwargs()` | 复用现有，不新增抽象层 |
| 7 | 未涉及 Job Object 复用问题 | **明确不复用 `SandboxJob`，新建独立 Job（无 `SILENT_BREAKAWAY_OK`）** | 4.2.4 实测：`SandboxJob` 下孙进程残留，`kill_tree` 失效 |

## 六、风险清单

| 风险 | 触发条件 | 对策 |
|---|---|---|
| **误复用 `SandboxJob` 导致杀树失效** | 开发者图省事 import 沙箱的 Job | 4.2.4 已写死结论；代码骨架直接 import `win_job_object`；代码审查必查项 |
| 宿主自身卡死 | 宿主内 `CreateProcessW` 被 conhost/loader lock 阻塞 | 主进程 `run()` 有 `_CONNECT_TIMEOUT`；看门狗监控宿主存活；超时杀宿主重建 |
| 多宿主同时启动抢同一管道名 | `_connect()` 判断失误时并发 spawn 两个宿主 | `_spawn_host()` 前用 `_host_lock` 串行化；宿主 `Listener` 绑定失败即退出；启动前先探测管道可连 |
| 宿主成为孤儿 | 主进程被强杀，宿主仍在 | 主进程启动时把宿主挂进自己的 KILL_ON_JOB_CLOSE Job（`win_job_object.assign_current_to_kill_on_close_job` 已把主进程放进 Job，宿主作为子进程自动继承）；宿主内另设空闲自退（无连接 10 分钟退出） |
| `KILL_ON_JOB_CLOSE` 误杀 | `close_job()` 在命令仍在跑时被调用 | `close_job` 仅在 `_handle` 的 `finally` 执行，此时 `proc.wait` 已返回，进程树已退出，杀之无害；异常路径先 `terminate_job` 再 close，语义一致 |
| 双份文件句柄/内存泄漏 | 每命令一连接，句柄未关 | `finally` 中 `conn.close()` + `close_job()`；72 小时长跑观察句柄数 |
| 输出顺序错乱（out/err 交错） | 两条 pump 线程并发 send | 与现有 `drain_until_exit` 同样不保证交错顺序（现状也不保证），行为一致，不属回归 |
| 打包后宿主找不到模块 | `hiddenimports` 遗漏 | 验收用例 1 在打包态跑一遍；`.spec` 明确列出模块 |
| CMD 分支 `shell=True` 在宿主内失效 | 阶段三才切 | 阶段一/二保留本地 Popen，不影响 |
| 性能回退（每命令一次 IPC 连接） | 高频小命令 | 实测单次连接开销 <0.04s；对秒级命令可忽略。若将来高频，可加连接池（YAGNI，先不做） |
| 宿主 conhost 被重建 | 宿主用 `CREATE_NO_WINDOW` 会分配隐藏控制台 | 主进程已 `FreeConsole` 的前提下宿主也无控制台可继承；`CREATE_NO_WINDOW` 的隐藏控制台在无父控制台时不产生 IOCTL 跨进程路径 |
