## 一、概念澄清：宿主、外置、内置分别是什么

方案开工前先把词说清，否则后面每一步都要打问号。

### 1.1 什么是"宿主"

**宿主（Host）= 一个专门用来"跑别人"的进程。**

它自己不干业务，只做三件事：接收指令、执行指令、回报结果。它的价值在于：**当它执行的东西把进程搞崩或搞卡时，崩溃范围只在这个进程里，真正干业务的主进程毫发无损。**

打个比方：主服务是"老板"，现在老板自己亲自下车间操作机床（`subprocess.Popen`）；机床卡死时，老板本人被卷进去，整个公司停摆。E1 的做法是**雇一个专门的工人（宿主进程），让工人去操作机床**——机床卡了，卡的是工人，老板照常办公，换一个工人继续。

**关键一点：这个工人不挑活。** 他只会"启动程序、收集输出、超时收工"这三件事，不关心启动的是 PowerShell、Node 还是 py-spy。所以这个宿主天生就是**通用进程执行能力**，不是 shell 专用（4.2.5 有实测证据）。

### 1.2 什么是"外置"

**外置（out-of-process / externalize）= 把这个动作从"本进程内执行"搬到"另一个进程执行"。**

对应的"内置"就是现在的情况：`execute_shell_command.py` 的 `shell()` 函数在被调用时，**在主服务进程内直接调用 `subprocess.Popen(...)`**——创建子进程这件事发生在主服务的解释器里。

所以：

| 说法 | 准确含义 |
|---|---|
| **现在的 shell 是"内置"的** | 创建 shell 子进程的动作，发生在主服务进程自己的 Python 解释器里（`execute_shell_command.py` 的 `shell()` 内 PS/CMD/bash 三分支，起于 `:1308/:1346/:1380`） |
| **"谁内置"** | 是**主服务进程自己**（`python run_server.py` 或 `OmniAgentBackend.exe` 那一个进程）在调 `subprocess.Popen` |
| **"外置"** | 把这个 `Popen` 调用搬到独立进程里。主进程只发一条"执行这个命令"的消息，不再碰 `Popen` |

**"内置"这个词的范围比 shell 大。** 全仓 19 个文件、29 处子进程调用点（其中 11 处直接调 `subprocess.Popen`/`subprocess.run`，18 处经 `proc_io.run` 间接调用，清单见 4.2.5）目前都在主进程内完成创建，shell 执行只是其中最主要的一处。所以外置的对象不是"shell"，而是"所有在主进程里创建子进程的动作"——这正是本文把模块命名为 `proc_host`（进程宿主）而非 `shell_host` 的原因。

### 1.3 为什么"内置"会出事：三个概念串起来

这里要把 [64] 2.8.2 的链条再说一次，因为这是整个 E1 的存在理由：

```
主服务进程内 Popen()
      ↓
CPython 的 _winapi.CreateProcess 调 CreateProcessW
      ↓
子进程要继承父控制台 → 内部走 GetConsoleMode 类 IOCTL → 跨进程问 conhost.exe
      ↓
conhost 不响应就无限等待
      ↓
★ 而 CPython 在整个 CreateProcessW 期间不释放 GIL
      ↓
★ 主进程全部 Python 线程冻结：事件循环停、看门狗停、心跳停
      ↓
用户看到"服务假死"，只能杀进程
```

三个致命点叠加：

1. **动作发生在主进程里**（内置）→ 卡住的是主进程；
2. **GIL 不释放** → 一条线程卡住等于全进程卡住，不是一个线程；
3. **超时机制管不到** → `drain_until_exit(proc, 600)` 的 600 秒超时只约束"读管道"，对"创建进程"这一步一步都不管（[42] 1.1 事故现场的 `_remaining = 599.9998042` 证明了这一点：超时一秒都没消耗就卡死了）。

外置之后，这三条同时被切断：在哪个进程卡（宿主）、会不会冻结全站（不会，宿主独立）、超时能不能管（宿主自己会被主进程超时杀掉重建）。

**边界要说清（否则目标无法验收）**：主进程不可能做到字面意义上的"零 `CreateProcessW`"——拉起宿主本身就要 `Popen` 一次。准确表述是：**业务命令的创建全部离开主进程，主进程只在启动期（阶段零）创建宿主一次，此时没有任何并发命令，即使卡住也只卡住启动**。所以 3.2 的硬指标按"稳态"计量。

### 1.4 "进程宿主"和"沙箱"的区别

容易混，这里划清：

| 项 | 进程宿主（E1，本文） | 沙箱（`safety/sandbox/`，已有） |
|---|---|---|
| 目的 | **防止卡死传染主进程** | **防止危险命令破坏系统** |
| 换掉的是 | `CreateProcessW` 的调用位置 | 命令的权限、路径、内存上限 |
| 是否已有 | ❌ 未落地 | ✅ 已实现（Job Object + 工作区限制 + 内存上限） |
| 两者关系 | 互补，不替代。宿主内部执行时仍可套沙箱 | |

一句话：沙箱管"这条命令能干什么"，宿主管"这条命令把谁搞死"。两件事。

|---|---|---|---|
| `isolation_kwargs()` | `proc_io.py:45-66` | `CREATE_NO_WINDOW` + stdin=DEVNULL + STARTF_USESTDHANDLES，让子进程不继承控制台 | **只管"子进程不继承"，管不到"父进程自己调 CreateProcessW 时被 IOCTL 卡住"** |
| `FreeConsole`（[42] P0） | `console_mode.py:49-64` | 摘掉主进程与 conhost 的关联，父进程无控制台→子进程无从继承。**仅打包态生效**（`:55-56` 非 frozen 直接 return，`OMNI_KEEP_CONSOLE=1` 也跳过） | 路径仍存在，只是不再触发；源码态根本没摘；若将来出现别的触发源（非控制台类 loader lock）依然会卡 |
| `spawn_gate` | `spawn_gate.py`，仅在主服务 `app/main.py:605` 安装 | `CreateProcessW` × `Thread.start` 互斥，持锁超 8s 强制回收 | 是"事后补救"，回收一个已经卡住的线程，主进程仍是受损状态；**宿主是另一个进程，默认不带这把闸门（4.5.1 必须自己装一次）** |
| `drain_until_exit` 超时 | `proc_io.py:101` | 读管道超时即返回 | **对创建阶段零约束** |

结论：**现有防护把触发概率压得很低，但没有一条能把"卡住"的后果限制在可抛弃的范围内。** 这就是 E1 的位置。

### 2.3 为什么之前没有实施：四个原因

[42] 写于 2026-11-15，到今天 11 天。方案设计完整（协议、代码骨架、验收、回滚都有），却没落地。逐条分析：

**原因一：P0 + P1 见效太快，P3 的必要性被掩盖。**
[42] 的四阶段是"按见效速度/改动成本"排序：P0（`FreeConsole`，只改 py，重启即生效）、P2（指纹闭环）都很快落地了。P0 一落地，卡死现象立即消失——`logs` 里不再有 `database is locked`、不再有假死。**症状消失后，根治方案的优先级自然下降**。这是典型的"止血成功导致不治本"。

**原因二：改动面大，是唯一"需要重新打包 + 动核心执行路径"的阶段。**
P3 要新增两个模块、改 `execute_shell_command.py`（1499 行的核心工具）、改 `OmniAgentBackend.spec`（`hiddenimports` + 新增 `--proc-host` 启动分支）。相比之下 P0 只是加一次函数调用。风险与成本量级不同，自然被推迟。

**原因三：[42] 自己标注了一个未验证的前置条件。**
[42] 2.5 节写得很明确：「上面所有结论中，只有『`DETACHED_PROCESS` + 显式三句柄能否稳定跑 pwsh』未经本地实测……落 P3 前必须先跑这个探针，读结果再定宿主的创建参数」。附录 A 给了探针脚本，但**这个探针没有跑过**。也就是说：**方案卡在一个"待验证项"上，而这个待验证项没人跟进。**

**原因四：原方案里有一个隐患没被识别，导致方案"看起来不可行"。**
[42] 原设计用"单一命名管道 + JSON 行 + `id` 多路复用"。这个设计要手写：多路复用状态机、id 分发、并发调度、管道权限（`win32pipe.CreateNamedPipe` 的 9 个参数）。**光是"这一坨要自己保证正确"就足以让人望而却步**。而实际上，有更简单的做法（本文 4.3 节的一命令一连接），原设计把简单问题做复杂了，反而降低了可行性。

**结论：不是"忘了"，是"症状消失 + 成本高 + 有个待验证项卡着 + 原设计过复杂"四重叠加导致的自然搁置。** 本文把四件事逐条解决：症状消失不给推迟理由（因为它是根治，不是止血）、成本用分阶段压到最低、待验证项本次已全部跑完（见 4.2）、设计复杂度用一命令一连接砍掉。

## 三、目标与判据

### 3.1 一句话目标

**让主服务进程在稳态下不再为业务命令调用 `CreateProcessW`（只在启动期创建宿主一次），从而把"卡死"的后果限制在一个可抛弃、可重建的宿主进程内。**

### 3.2 可验收的硬指标

| 指标 | 现在 | 目标 | 怎么量 |
|---|---|---|---|
| 主进程内 `CreateProcessW` 调用次数（前台 shell 业务路径） | 每次命令 1 次 | **稳态 0**（启动期创建宿主 1 次不计） | 代码审查 + `spawn_gate` 指标 `popen_calls`（`/health.spawn.popen_calls`，改前后取差值） |

- 不动 `isolation_kwargs()` 的参数（宿主内继续用它）。

## 四、方案设计

### 4.1 架构对比

**现状（内置）**：

```
┌─ 主服务进程 ────────────────────────────────┐
│  execute_shell_command.shell()              │
│      ↓                                      │
│  subprocess.Popen()  ← ★ 卡在这里全站冻结    │
│      ↓                                      │
│  drain_until_exit()                         │
└─────────────────────────────────────────────┘
              ↓ CreateProcessW
         pwsh.exe / cmd / bash
```

**E1（外置）**：

```
┌─ 主服务进程 ─────────────────────────────┐
│  startup: client.ensure_host()           │
│      ↓ 启动期只 Popen 这一次（无并发命令） │
│  shell()                                 │
│      ↓                                   │
│  client.run()  ← 只发消息                │
│      ↓ multiprocessing.connection        │
└──────┼───────────────────────────────────┘
       │ AF_PIPE（Windows 命名管道，每实例唯一名）
┌──────▼───────────────────────────────────┐
│  宿主进程 proc_host（独立，可抛弃）        │
│      ↓ 每命令一连接 / 一 Job Object        │
│  subprocess.Popen()  ← 卡在这里只冻宿主    │
│  Job Object 收编 → 超时 TerminateJobObject │
│  流式回传 stdout/stderr                   │
└──────────────────────────────────────────┘
              ↓ CreateProcessW
         pwsh.exe / cmd / bash
```

**为什么宿主必须在启动期就拉起（阶段零）**：若首次命令到来时才 `Popen` 宿主，那么"第一次卡死"仍然发生在主进程的请求路径上——GIL 照样被 `CreateProcessW` 卡住，E1 等于没做。启动期拉起 + 之后只重建（重建发生在超时判定之后、由专门线程执行），才能保证请求路径上主进程一次都不调 `CreateProcessW`。

### 4.2 实测证据：五组 PoC，解决 [42] 遗留的四个未验证项

所有数据于 2026-11-26 本机实测（Python 3.13.11，14 核，PowerShell 7 位于 `E:\Appsw\powershell7\7\pwsh.exe`）。五组 PoC 依次回答五个问题：IPC 能不能用、超时怎么杀、宿主怎么起、能不能复用现成 Job、宿主是不是只能跑 shell。

**证据强度声明**：下列数值是实测记录，但五组 PoC 脚本当时是临时文件、**未提交入库**（全仓检索无 `*poc*.py` / `*_probe*.py` 与本节对应），因此 v1.1 里"脚本存放于项目目录、可复核重跑"的说法不成立，本版改正为"数据可引用、脚本待补"。补交脚本列入落地清单第 1 项；在脚本补齐前，任何结论若要作为验收依据，必须现场重跑一次。

#### 4.2.1 IPC 方案可行性：`multiprocessing.connection` 全通

[42] 原设计要先判断"pywin32 是否已有、没有就改 `multiprocessing.connection`"。**已核实：`pywin32>=306` 在 `requirements.txt:48`，且 `win32pipe` 可用。** 但实测表明**不需要 pywin32**——标准库的 `multiprocessing.connection`（Windows 走 AF_PIPE）已经足够，且代码量少一半：

| 测试 | 结果 |
|---|---|
| 基本执行 `cmd /c echo hello-poc` | ✅ `out=b'hello-poc\r\n'` rc=0，0.04s |
| 大输出流式（约 500KB） | ✅ `out_len=510000`，0.13s，分块回传无内存压力 |
| 超时（5s 命令，timeout=1s） | ✅ `timed_out=True` |
| 超时后宿主仍可用 | ✅ 后续命令正常返回 |
| **8 条命令并发** | ✅ 总墙钟 1.07s（8 条各约 1s，串行需 8s）→ **天然并发** |
| 客户端断开后宿主存活 | ✅ 正常处理后续连接 |

#### 4.2.2 超时策略：必须杀进程树，Job Object 最优

PoC 首轮暴露了一个 [42] 未识别的坑：**超时设 1s，实际耗时 3.08s**。原因是 `proc.kill()` 只杀了 `cmd.exe`，孙进程 `ping.exe` 仍活着并持有输出管道，读线程 `join` 卡满。

三种策略对比（命令 `cmd /c ping -n 6 ... & echo never-reached`，约 5s，超时设 1s）：

| 策略 | 实际耗时 | 判定 | 评价 |
|---|---|---|---|
| `proc.kill()`（只杀根） | **5.06s** | ❌ 严重超标 | 孙进程持管道，超时语义完全失效 |
| `taskkill /F /T /PID` | 1.25s | ✅ | 可用，但要额外创建 taskkill 进程（又踩 `CreateProcessW`） |
| **Job Object + `TerminateJobObject`** | **1.02s** | ✅✅ 最优 | 内核级杀整棵树，零额外进程，无残留（二次验证 `ping.exe` 前后均 0） |

**定案：宿主内每个子进程创建后立刻 `AssignProcessToJobObject`，超时用 `TerminateJobObject`。**

但**不能直接复用沙箱的 `SandboxJob`**——这一点经实测证伪，见 4.2.4。

#### 4.2.3 宿主创建模式：`DETACHED_PROCESS` 会静默丢输出（比崩溃更危险）

这是 [42] 附录 A 明确要求"落 P3 前必须先跑"的探针，本次跑完，结论**推翻了原假设**。

[42] 原文判断：「纯 `DETACHED_PROCESS` 实测 pwsh 会立即退出」。实测显示更糟：

| 创建模式 | pwsh7 | ps5 | cmd | bash |
|---|---|---|---|---|
| `inherit` | ✅ `ok-pwsh` 0.46s | ✅ 0.20s | ✅ 0.03s | ✅ 11.61s（WSL 慢） |
| `CREATE_NO_WINDOW` | ✅ `ok-pwsh` 0.30s | ✅ 0.22s | ✅ 0.03s | ✅ 0.20s |
| `DETACHED_PROCESS` | ⚠️ **rc=0 但 stdout 为空** | ⚠️ **rc=0 但空** | ✅ | ✅ |
| `DETACHED_PROCESS\|NEW_PROCESS_GROUP` | ⚠️ **rc=0 但 stdout 为空** | ⚠️ **rc=0 但空** | ✅ | ✅ |
| `CREATE_NEW_CONSOLE` | ✅ 0.45s | ✅ 0.39s | ✅ 0.15s | ✅ 0.33s |

**关键发现：`DETACHED_PROCESS` 下 pwsh/ps5 的返回码是 0，但 stdout 是空字符串。** 它不是"立即退出"，而是**跑完了但把所有输出丢了**。这比崩溃危险得多——因为上层判定逻辑看到 `rc=0 + 无输出`，会走进 `else` 分支判为"命令成功但无产出"，模型会收到"执行成功、没有输出"，从而误以为命令没产生结果，**静默丢掉真有价值的输出**。

**定案：宿主进程用 `CREATE_NO_WINDOW` 创建，禁止 `DETACHED_PROCESS`。**

安全性分两种情况说清（v1.2 修正：v1.1 只写了打包态，结论被说绝对了）：

| 运行形态 | P0（`detach_console_if_needed`）是否生效 | 宿主创建的实际后果 |
|---|---|---|
| 打包态（`sys.frozen=True`，无 `OMNI_KEEP_CONSOLE=1`） | ✅ 生效（`console_mode.py:49-64` 调 `FreeConsole`，成功才重定向 stdio） | 主进程无控制台→宿主无可继承控制台，`CREATE_NO_WINDOW` 退化为普通创建，不产生跨进程控制台 IOCTL |
| 源码态（`python run_server.py` / `start_watch.bat`） | ❌ 不生效（`console_mode.py:55-56` 非 frozen 直接 return） | 主进程仍持控制台，宿主会新建隐藏控制台；**但宿主是独立进程，它卡住不冻结主进程**——这正是 E1 相对 P0 的增量价值 |
| 任一形态 + `OMNI_KEEP_CONSOLE=1` | ❌ 被显式跳过 | 同上 |

**所以 E1 不是 P0 的重复**：P0 只消掉"控制台 IOCTL"这一个触发源，且只在打包态生效；`CreateProcessW` 还可能被安全软件注入、网络盘加载 DLL、映像加载锁等其它源卡住，这些 P0 一概管不到。P0 是降低概率，E1 是限制后果——两者层级不同。

#### 4.2.4 关键反证：不能复用 `SandboxJob`（它会放跑孙进程）

初稿曾计划"直接复用 `safety/sandbox/job_object.py` 的 `SandboxJob`，不新写"。实测推翻了这个想法。

`SandboxJob.__init__`（`job_object.py:51-53`）置了三个标志：

```python
info.BasicLimitInformation.LimitFlags = (
    JOB_OBJECT_LIMIT_PROCESS_MEMORY | JOB_OBJECT_LIMIT_ACTIVE_PROCESS
    | JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK)     # ★ 这一条是致命的
```

`SILENT_BREAKAWAY_OK` 的含义是：**Job 内进程创建的子进程会自动脱离 Job**。这个设置在沙箱场景是**故意**的（`job_object.py:48-50` 注释："加 SILENT_BREAKAWAY_OK，覆盖任意 shell 后台进程，预检杀树不误杀"），但在进程宿主场景下效果正好相反——它让 `kill_tree()` 杀不到孙进程。

三组对照实测（命令 `cmd /c ping -n 20 127.0.0.1`，ping 作为 cmd 的孙进程）：

| 组 | Job 配置 | 杀树前 ping | 杀树后 ping | 判定 |
|---|---|---|---|---|
| A | 仅 `KILL_ON_JOB_CLOSE`（无 BREAKAWAY） | 1 | **0** | ✅ 孙进程已杀 |
| B | `PROCESS_MEMORY \| ACTIVE_PROCESS \| SILENT_BREAKAWAY_OK`（沙箱同配置） | 1 | **1** | ❌ **孙进程残留** |
| C | 直接 `import` 项目 `SandboxJob` | 1 | **1** | ❌ **孙进程残留** |

**结论：若照 4.5.1 骨架直接用 `SandboxJob`，超时杀树会完全失效**——`ping` 残留、继续持有输出管道、宿主随后卡在 `pump` 线程 `join` 上，等于把原来的问题原样搬进宿主。

**定案：为宿主新建独立 Job，配置为 `KILL_ON_JOB_CLOSE`，绝不含 `SILENT_BREAKAWAY_OK`。** 实现位置选 `app/utils/win_job_object.py`（该文件已定义全部 ctypes 结构体，只缺 `create/assign/terminate/close` 四个薄函数），作为公用函数登记到 `backend/FUNCTIONS.md`。

**另外两个标志不要随手加**（v1.2 补充，避免"为了安全"把功能改坏）：

| 标志 | 加了的后果 | 结论 |
|---|---|---|
| `JOB_OBJECT_LIMIT_ACTIVE_PROCESS`（尤其 limit=1） | Job 内并发进程数被限死，`cmd /c xxx` 这类"父起子"的合法命令直接创建失败 | ❌ 不加 |
| `JOB_OBJECT_LIMIT_PROCESS_MEMORY` | 按进程限内存，与本方案"防卡死"目标无关；设小了会让 ffmpeg/node 等正常命令 OOM | ❌ 不加（内存上限属沙箱职责，见 1.4） |

即：宿主 Job 只保留 `KILL_ON_JOB_CLOSE` 一条，职责单一（SRP）——"关句柄即杀全树"。

这是"复用优先"原则的一个反例：**复用前必须核对被复用物的语义是否与当前场景一致**。沙箱 Job 的语义是"别误杀后台进程"，宿主的语义是"务必杀干净"，两者相反，不能共用同一个配置。

**这个统计有一个落地含义，v1.1 漏了**：18 处间接调用全部收敛在 `proc_io.run` 这一个函数里（`proc_io.py:192` 那一个 `Popen`）。所以"`tools/system/*` 8 处 + 注册表 3 处 + `system_adapter` 2 处 + 其余 5 处"**不是 18 次搬迁，而是改 `proc_io.run` 一处的内部实现**——前提是宿主 `run()` 能把 `capture_output/text/encoding/timeout` 这几个参数语义映射过去。反过来，11 处直接创建才是一处一处改（其中 shell 的 PS 分支已在阶段一完成，CMD/bash 见 7.2/7.4）。这就是"设计通用、落地分阶段"的真实成本结构。

宿主接口只有 `argv / cwd / env / timeout`，**不含任何业务语义**（不认识"shell"这个词）。这一点由 PoC 直接验证——同一宿主连续执行 4 种异构程序：

| 程序 | 结果 |
|---|---|
| `pwsh -Command 'hello-from-pwsh'` | ✅ rc=0，0.52s |
| `node -e "console.log('hello-from-node')"` | ✅ rc=0，0.05s |
| `py-spy --version` | ✅ rc=0，0.57s，输出 `py-spy 0.4.2` |
| `cmd /c echo hello-from-cmd` | ✅ rc=0，0.02s |

以及三项关键能力验证：

| 验证 | 结果 |
|---|---|
| 8 条并发异构命令（pwsh/node/py-spy/cmd 混合） | ✅ 墙钟 0.27s，全部 rc=0（真并发） |
| 超时杀树对 `node -e "while(1){}"` 死循环 | ✅ `timed_out=True`，耗时 1.01s |
| 超时后宿主仍可用 | ✅ 后续命令正常返回 |

**结论：通用化不是"设计野心"，是"事实"。** 若只做成 shell 专用，将来 `tools/system/*` 的 8 处、注册表 3 处、`extract.py` 1 处都要重走一遍同样的搬迁——那不是复用，是复制 18 次。

**但通用不等于万金油**，边界必须写死（防过度设计）：

| 该通用 | 不该通用（过度设计，明确禁止） |
|---|---|
| 执行一个程序、回传输出、超时杀树 | ❌ `kind="shell"\|"ffprobe"\|"reg"` 之类类型分发 |
| `argv / cwd / env / timeout` | ❌ 插件注册表 / 扩展点 / 工厂模式 |
| 流式 out/err 分块、`timed_out`、`truncated` | ❌ 业务层参数校验（留在各调用方） |

**为什么不支持 `stdin`（v1.2 明确）**：`isolation_kwargs()` 本身就把 `stdin` 固定为 `DEVNULL`（`proc_io.py:60`，注释写明"不继承控制台输入句柄，输入缓冲区串行独占，读到即挂"）。宿主接口若声明支持 `stdin`，既与现网行为矛盾，又会重新引入"喂输入被挂住"的老问题。所以接口**只有 `argv/cwd/env/timeout`**，需要交互的程序不属于本宿主（见下表）。

**判据一句话：接口里只要出现任何一个业务名词，就说明抽象错了。** `run(argv)` 是唯一接口，符合 KISS-DIRECT。

**确实不适合的一类（说清边界，不硬塞）**：

| 场景 | 为什么不适合 | 当前是否涉及 |
|---|---|---|
| 需要持久双向交互（stdio MCP server、交互式 REPL、持续喂 stdin） | "一命令一连接"模型不匹配，需长连接 + 多路复用 | ❌ 不涉及：`mcp_client.py:82` 走 HTTP `POST`（JSON-RPC over HTTP），全仓无 stdio 形态 |
| 需要长期存活的守护进程 | 生命周期模型不同 | ❌ 不涉及：`loop_watchdog` 的 `_DUMP_POOL` 是常驻**线程池**，py-spy 取证是一次一进程；shell 池已于 2026-11-06 去池化（`shell_engine.py:143` 文档串） |

即：**当前全仓 29 处调用点全部适配本宿主，无例外**（沙箱 1 处因安全语义单独评估，见 4.6）。将来若接本地 stdio MCP，需单独设计长连接宿主，不能硬塞进这个模型。

### 4.3 协议设计：一命令一连接（对 [42] 的改进）

[42] 原设计是"单一命名管道 + JSON 行 + `id` 多路复用"。本文改为**一命令一连接**，理由三条：

| 维度 | [42] 单管道 + id 复用 | 本文一命令一连接 |
|---|---|---|
| 并发 | 需手写 id 分发表 + 多路复用状态机 | **天然并发**，每连接独立（实测 8 并发 1.07s） |
| 取消 | 需发 `cancel(id)` 请求，宿主维护状态 | **连接断开 = 命令取消**，无需协议字段 |
| 代码量 | 状态机 + id 管理，约 200 行 | 约 80 行 |
| 故障定位 | 一条管道出错影响所有命令 | 一条连接出错只影响该命令 |
| 开销 | 无（复用） | 每命令一次 `Client()` 连接，实测 0.04s 内完成，可忽略 |

符合 KISS-DIRECT：**能用"多连接"天然解决的，不要用"单连接 + 多路复用"手写解决。**

协议帧（均为 Python `dict`，经 `multiprocessing.connection` 传输）：

```
客户端 → 宿主（连接建立后首帧）:
  {"proto": 1, "argv": [...], "cwd": str|None, "env": dict|None, "timeout": float|None}
  # proto: 协议版本。宿主收到不认识的版本立即回 {"type":"error"} 并断开,
  #        避免"打包的是新宿主、跑的是旧客户端"时两边各说各话(静默错解帧)。
  # env 已在主进程侧由 _sanitize_env() 处理完毕, 宿主不再过滤。
  # 无 stdin 字段: isolation_kwargs() 固定 stdin=DEVNULL, 见 4.2.5。

宿主 → 客户端（可多次，流式）:
  {"type": "out", "data": b"..."}      # stdout 分块
  {"type": "err", "data": b"..."}      # stderr 分块
  {"type": "done", "rc": int, "timed_out": bool, "truncated": bool, "pid": int, "elapsed": float}
  {"type": "error", "message": str}    # 创建失败/参数非法/并发已满
```

`truncated` 语义与 `proc_io.drain_until_exit` 的第四返回值一致：进程已退出但管道被孙进程持有，有界等待后放弃残留输出。

**三条协议级约束（v1.2 补充，v1.1 缺，缺了会直接出错）**：

| 约束 | 事实依据 | 设计对策 |
|---|---|---|
| **一个连接同时只能有一个发送者** | `PipeConnection._send_bytes()` 用 `self._send_ov` 做"在途"标记，重复进入直接抛 `ValueError("concurrent send_bytes() calls are not supported")`（`multiprocessing/connection.py:284-288`）；而 `Connection.send()`（:202-206）自身不加锁 | 每个连接配一把 `threading.Lock`，`out`/`err`/`done` 全部经 `_send(conn, obj, lock)` 串行发出。**不这么做，两条 pump 线程并发回传必然抛 `ValueError`，命令随机失败** |
| **管道名与 authkey 必须每实例唯一** | v1.1 骨架把 `PIPE_NAME`、`AUTHKEY` 硬编码在两个模块里 | 由主进程在启动期生成 `omni-proc-host-<uuid4hex>` 与 `os.urandom(32)`，经环境变量传给宿主；客户端从同一环境变量读取。**否则开发态与打包态、或两个用户会话会抢同一管道；固定 authkey 还等于对本机任意进程开放命令执行** |
| **接收必须有截止时间** | `Connection.recv()` 无超时参数（`PipeConnection` 只有 `poll(timeout)`，`connection.py:253`） | 客户端循环改为 `if not conn.poll(remaining): 判定宿主卡死`；剩余时间由调用方 `timeout` 推算，另加 `_RECV_SLACK` 收尾余量 |

**连接数上限**：宿主每条连接在 `_handle` 读取首帧后申请 `BoundedSemaphore(CONCURRENCY).acquire(timeout=...)` 槽位，拿不到则**排队等待**（等待上限 = 该命令自身 timeout，未传则 600s）而不是直接报错——现网 `_SHELL_PROC_SEM.acquire(timeout=_remaining)`（`execute_shell_command.py:1294`）就是"排队 + 超时报错"语义，宿主若改成"立即拒绝"就是行为退化。

**运行期文件与日志（v1.2 补充）**：宿主被 `stdout/stderr=DEVNULL` 拉起（否则它会继承主进程句柄，且控制台写满会阻塞），所以 `print()` 等于丢弃。宿主日志必须自己落文件：`logs/proc_host.log`（走 `app.logger`，滚动策略与现有日志一致）。否则"宿主为什么被重建""Job 收编为什么失败"全部无迹可查——这类现场问题没有日志就等于不可诊断。

**为什么命名为 `proc_host` 而不是 `shell_host`**：宿主接口只认 `argv/cwd/env/timeout`，不含任何业务语义，是通用进程执行能力（4.2.5 已实测 pwsh/node/py-spy/cmd 四种异构程序）。命名为 shell 专用会误导后续开发者在 `tools/system/*`、`attachments/extract.py` 等处重新实现一遍——那正是要避免的"复制 18 次"。**设计做通用，实施仍分阶段**（4.6）：阶段一只切 shell 的 PS 分支控制风险，但代码结构从第一天就是通用的，后续接入只是"加一个调用方"。

**为什么放到 `app/proc_host/` 而不是 `app/utils/`**：
1. `app/utils/` 是"无状态公用函数层"（`AGENTS.md §1.3`），现有 29 个文件都是可随手 import 的纯函数或薄封装；宿主是长期存活的独立进程，有协议、有生命周期、有自愈，属子系统而非工具函数（SLAP）。
2. `host.py` 在模块导入期读 `OMNI_PROC_HOST_PIPE` / `OMNI_PROC_HOST_KEY`（骨架 `:502-503`），主进程任何模块误 import 即 `KeyError`。独立包把"只由 `-m app.proc_host.host` 或 `--proc-host` 拉起、禁止被业务代码 import"落到目录上。
3. 宿主必须保持依赖极简，而 `app/utils/` 的进程类模块普遍在导入期拉 `app.logger`（`proc_io.py:34`、`win_job_object.py:18`）：`app.logger` 一导入就启动 `console-writer` 守护线程（`logger/console_writer.py:160-163`）、读 `app.config`、建 `logs/` 目录。宿主以 `stdout/stderr=DEVNULL` 运行，这套控制台/配置副作用全是负担，且与主进程共用轮转日志文件存在竞争。客户端作为子系统门面，同样不混进公用层。
4. 与 `app/safety/sandbox/` 同构：子系统自身的东西（协议、实现、专用 Job、工作区）收在同一个目录，不散落进 `utils`；协议版本 `PROTO` 由包 `__init__.py` 单点定义，宿主与客户端同源导入，不会各写一份后漂移。

**复用 utils 的两处底层能力，但两者必须做到导入零副作用**：宿主起子进程用 `isolation_kwargs()`（`proc_io.py:45`，含 `stdin=DEVNULL`/`STARTF_USESTDHANDLES`/`CREATE_NO_WINDOW`，不可在宿主里重写一份），收编 Job 用 `win_job_object` 的新增 4 个函数。因此：
- `win_job_object.py`：原模块级 `from app.logger import logger` 移入唯一使用者 `assign_current_to_kill_on_close_job()`（函数体 `:92` 起，惰性导入在 `:101`），新增 4 个函数同样函数内惰性导入。
- `proc_io.py`：原模块级 `from app.logger import logger` 移入唯一使用点 `drain_until_exit` 的截断告警（`:148`）。

导入期只剩标准库/ctypes，宿主 import 这两个模块不会拉起控制台线程、读配置或建目录（验收用例 12 专门检查这一点）。

**为什么不新建 `job_helper.py` 而扩展 `win_job_object.py`**：该文件已完整定义 `JOBOBJECT_BASIC_LIMIT_INFORMATION`、`IO_COUNTERS`、`JOBOBJECT_EXTENDED_LIMIT_INFORMATION` 三个结构体与 `kernel32` 句柄（`win_job_object.py:59-90`），只是当前只对外暴露了 `assign_current_to_kill_on_close_job()` 一个函数。扩展它符合 `AGENTS.md §1.3` 的"先查后建、分层存放"，避免同一套 ctypes 定义出现两份（DRY）。

**不修改 `safety/sandbox/job_object.py`**：沙箱的 `SILENT_BREAKAWAY_OK` 是其自身场景的正确配置（见 4.2.4），不能为了复用而改它——那会把沙箱的"别误杀后台进程"语义改坏。

#### 4.5.1 宿主 `backend/app/proc_host/host.py`

```python
# -*- coding: utf-8 -*-
# 编辑历史:
# 2026-11-26 - 小欧 - 新建: 通用进程宿主(一命令一连接, Job Object 杀树; 接口只有 argv/cwd/env/timeout, 无业务语义)
# 2026-11-26 - 小欧 - 修正: 补单连接发送锁(并发 send 抛 ValueError)/每实例管道名与随机 authkey/协议版本握手/
#                     槽位排队而非立即拒绝/Job 收编失败 fail-closed/回传真实 returncode/自身装 spawn_gate/日志落文件
"""proc_host — 通用进程宿主进程

【为什么独立进程】CreateProcessW 卡在控制台 IOCTL 时不释放 GIL, 同解释器内任何线程
(含看门狗、join 超时)都无法执行。唯一能把"卡住"限制在可抛弃范围的边界是进程边界。

【协议】AF_PIPE + multiprocessing.connection, 一命令一连接(无 id 多路复用):
  首帧 {"proto","argv","cwd","env","timeout"} → 流式 {"type":"out"|"err","data":b} → {"type":"done",...}
  连接断开 = 命令取消。单连接同一时刻只允许一个发送者(见 _send)。

【超时】每子进程挂 Job Object, 超时 TerminateJobObject 杀整棵树(实测 1.02s,
  对比 proc.kill() 5.06s —— 孙进程持管道会让根 kill 无效)。

【创建模式】宿主自身由主进程以 CREATE_NO_WINDOW 拉起; 禁用 DETACHED_PROCESS
  (实测该模式 pwsh/ps5 返回 rc=0 但 stdout 为空, 静默丢输出)。

【命名】管道名与 authkey 由主进程每实例生成, 经环境变量传入; 不写死常量
  (写死会让开发态/打包态互抢同一管道, 且固定 authkey 等于对本机任意进程开放命令执行)。
"""
import os
import subprocess
import threading
import time
from multiprocessing.connection import Listener

from app.proc_host import PROTO      # 协议版本唯一真源(包 __init__), 握手两端同源

PIPE_NAME = os.environ["OMNI_PROC_HOST_PIPE"]                 # 形如 \\.\pipe\omni-proc-host-<uuid4hex>
AUTHKEY = bytes.fromhex(os.environ["OMNI_PROC_HOST_KEY"])     # 32 字节随机数
CONCURRENCY = int(os.environ.get("OMNI_PROC_HOST_CONCURRENCY", "12"))
_IDLE_JOIN = 3.0        # pump 线程收尾等待(秒): 与 proc_io.IDLE_AFTER_EXIT(2.5) 同量级, 超时即判 truncated
_LOG_PATH = os.environ.get("OMNI_PROC_HOST_LOG") or os.path.join("logs", "proc_host.log")
try:
    os.makedirs(os.path.dirname(os.path.abspath(_LOG_PATH)), exist_ok=True)
except OSError:
    pass


def _serve_forever() -> None:
    """宿主主循环: 常驻 accept, 每连接一线程。

    单个坏连接(握手失败 AuthenticationError / 对端立刻关闭 EOFError)只丢该连接, 不得让宿主退出:
    AuthenticationError 继承 ProcessError(Exception) 而非 OSError(multiprocessing/context.py:23),
    v1.1 骨架的 `except (OSError, EOFError): break` 会把一次失败握手升级成"宿主整体死亡"。
    """
    listener = Listener(PIPE_NAME, authkey=AUTHKEY)
    _log(f"listening on {PIPE_NAME}, concurrency={CONCURRENCY}")
    _slots = threading.BoundedSemaphore(CONCURRENCY)
    _bad = 0
    while True:
        try:
            conn = listener.accept()
        except Exception as e:                      # 含 ProcessError/AuthenticationError/OSError
            _bad += 1
            _log(f"accept failed({_bad}): {type(e).__name__}: {e}")
            if _bad >= 50:                          # 连续 50 次仍失败: 管道/句柄已不可用, 退出等主进程重建
                _log("accept 连续失败, 退出由主进程重建")
                return
            time.sleep(0.1)
            continue
        _bad = 0
        threading.Thread(target=_handle, args=(conn, _slots), daemon=True).start()


def _handle(conn, slots) -> None:
    """一连接一命令。"""
    # 2026-11-26 - 独立 Job: 禁用 SILENT_BREAKAWAY_OK, 否则孙进程逃离 Job, kill_tree 失效
    #   (实测: SandboxJob 配置下 cmd/c ping 的 ping 残留; 仅 KILL_ON_JOB_CLOSE 时被杀净)
    from app.utils.win_job_object import (
        assign_to_job, close_job, create_kill_on_close_job, terminate_job,
    )
    send_lock = threading.Lock()      # ★ 单连接同一时刻只允许一个发送者, 见 _send
    job = None
    proc = None
    try:
        req = conn.recv()
        if not isinstance(req, dict) or req.get("proto") != PROTO:
            proto_repr = req.get("proto") if isinstance(req, dict) else req
            _send(conn, {"type": "error", "message": f"协议版本不匹配: {proto_repr!r}"}, send_lock)
            return
        argv = req.get("argv")
        if not argv or not isinstance(argv, (list, tuple)):
            _send(conn, {"type": "error", "message": "argv 必须是 list/tuple"}, send_lock)
            return
        timeout = req.get("timeout")
        # ★ 排队等待槽位(不是立即拒绝): 与现网 _SHELL_PROC_SEM.acquire(timeout=_remaining) 同语义,
        #   立即拒绝会让"并发 20 条命令"从'排队后全部成功'退化为'一半直接报错'。
        if not slots.acquire(timeout=timeout if timeout else 600):
            _send(conn, {"type": "error", "message": "宿主并发已达上限(排队超时)"}, send_lock)
            return
        try:
            t0 = time.monotonic()
            from app.utils.proc_io import isolation_kwargs
            try:
                proc = subprocess.Popen(
                    list(argv), cwd=req.get("cwd"), env=req.get("env"),
                    stdout=subprocess.PIPE, stderr=subprocess.PIPE,
                    **isolation_kwargs())
            except (OSError, ValueError) as e:
                _send(conn, {"type": "error", "message": f"{type(e).__name__}: {e}"}, send_lock)
                return
            # ★ Job 收编 fail-closed: 没有 Job 就没有"杀整棵树"的保证, 超时承诺直接失效。
            #   故收编失败 → 杀掉刚起的进程并回 error, 绝不静默降级为 proc.kill()(只杀根, 孙进程残留)。
            #   竞态说明: Python 3.13 的 subprocess 无 CREATE_SUSPENDED 常量、Popen 也不暴露线程句柄,
            #   无法"挂起创建→收编→ResumeThread"; 因此只能"创建后立刻收编"。窗口在微秒级, 而子进程
            #   自身启动需数十毫秒, 实际不产生逃逸; 万一逃逸, close_job 的 KILL_ON_JOB_CLOSE 仍是兜底。
            try:
                job = create_kill_on_close_job()
                assign_to_job(job, proc)
            except OSError as e:
                _log(f"job assign failed pid={proc.pid}: {e} → fail-closed")
                if job is not None:
                    close_job(job)
                    job = None
                try:
                    proc.kill()
                except OSError:
                    pass
                _send(conn, {"type": "error", "message": f"Job 收编失败, 已终止命令: {e}"}, send_lock)
                return

            pumps = [
                threading.Thread(target=_pump, args=(proc.stdout, "out", conn, send_lock), daemon=True),
                threading.Thread(target=_pump, args=(proc.stderr, "err", conn, send_lock), daemon=True),
            ]
            for t in pumps:
                t.start()

            timed_out = False
            try:
                proc.wait(timeout=timeout)     # None = 不设上限, 由客户端截止时间兜底(会杀宿主重建)
            except subprocess.TimeoutExpired:
                timed_out = True
                terminate_job(job)            # TerminateJobObject, 内核级杀整棵树
                try:
                    proc.wait(timeout=3)
                except subprocess.TimeoutExpired:
                    pass
            for t in pumps:
                t.join(timeout=_IDLE_JOIN)

            truncated = any(t.is_alive() for t in pumps)
            if truncated:
                # 根已退出但管道未 EOF(孙进程/后台作业仍持写端): 关 Job 杀净, 语义与
                # proc_io.drain_until_exit 的 truncated=True 一致(调用方补 TRUNCATED_NOTE)
                terminate_job(job)
            _send(conn, {
                "type": "done",
                # ★ 回真实 returncode: 现网超时分支是 kill 后取 proc.returncode, 恒为已终止码而非 -1;
                #   写死 -1 会让调用方拿到的 returncode 与改造前不一致(行为一致性判据见 3.2)。
                "rc": proc.returncode if proc.returncode is not None else -1,
                "timed_out": timed_out, "truncated": truncated,
                "pid": proc.pid, "elapsed": round(time.monotonic() - t0, 3),
            }, send_lock)
        finally:
            slots.release()
    except Exception as e:
        # 客户端断开(主进程被杀/取消): 杀掉该命令树, 不留孤儿。
        # 注意不能只捕 (EOFError, BrokenPipeError, OSError): 握手失败是 AuthenticationError(ProcessError),
        # 并发发送是 ValueError, 二者都不继承 OSError, 漏捕会让整个线程静默崩掉且槽位不释放。
        _log(f"conn aborted: {type(e).__name__}: {e}")
        if job is not None:
            try:
                terminate_job(job)
            except Exception:
                pass
        elif proc is not None:
            try:
                proc.kill()
            except OSError:
                pass
    finally:
        if job is not None:
            try:
                close_job(job)                # KILL_ON_JOB_CLOSE: 句柄关闭即杀全树, 幂等安全
            except Exception:
                pass
        try:
            conn.close()
        except Exception:
            pass


def _pump(stream, kind, conn, send_lock) -> None:
    """流式读一路输出并回传; 连接断开即停止(调用方已死, 无需继续攒数据)。"""
    while True:
        try:
            chunk = stream.read(8192)
        except (ValueError, OSError):
            return
        if not chunk:
            return
        if not _send(conn, {"type": kind, "data": chunk}, send_lock):
            return


def _send(conn, obj, send_lock) -> bool:
    """串行发送: PipeConnection._send_bytes 用 _send_ov 标记在途, 并发调用直接抛 ValueError。

    两条 pump 线程 + 主线程的 done 共三个发送者, 必须由同一把锁串行化。
    """
    try:
        with send_lock:
            conn.send(obj)
        return True
    except Exception:      # 对端已关: BrokenPipeError/OSError/EOFError; 并发误用: ValueError
        return False


def _log(msg: str) -> None:
    """宿主日志: 必须落文件。主进程以 stdout/stderr=DEVNULL 拉起宿主, print 等于丢弃。"""
    line = f"{time.strftime('%Y-%m-%d %H:%M:%S')} [proc_host] {msg}"
    try:
        with open(_LOG_PATH, "a", encoding="utf-8") as f:
            f.write(line + "\n")
    except OSError:
        pass


def _watch_parent(parent_pid: int) -> None:
    """生命周期看门狗: 主进程消失即自杀, 不留孤儿。

    为什么不用"空闲 10 分钟自退": 宿主一退出, 下一条命令就得在主进程请求路径上重新 Popen 宿主,
    等于把 CreateProcessW 又搬回主进程(违背 4.1 的阶段零前提)。所以只在"父进程真的没了"时退出。
    为什么不用 Job 继承兜底: run_server.py:456-461 只在 is_frozen 时给主进程挂 KILL_ON_JOB_CLOSE,
    源码态(dev/E2E)没有, 靠 Job 继承在 dev 下不成立。
    """
    import ctypes
    k32 = ctypes.windll.kernel32
    SYNCHRONIZE, WAIT_OBJECT_0 = 0x00100000, 0
    while True:
        time.sleep(5.0)
        h = k32.OpenProcess(SYNCHRONIZE, False, parent_pid)
        if not h:
            _log(f"parent {parent_pid} gone (OpenProcess failed), exit")
            os._exit(0)
        try:
            if k32.WaitForSingleObject(h, 0) == WAIT_OBJECT_0:
                _log(f"parent {parent_pid} exited, exit")
                os._exit(0)
        finally:
            k32.CloseHandle(h)


def main() -> None:
    """宿主入口。frozen 时由 run_server.main() 按 --proc-host 直接调用。"""
    # ★ spawn_gate 只在主服务 app/main.py:605 装过一次, 宿主是另一个进程, 不装就没有任何闸门保护
    from app.utils.spawn_gate import install_spawn_gate
    install_spawn_gate()
    parent_pid = int(os.environ.get("OMNI_PROC_HOST_PARENT_PID", "0") or 0)
    if parent_pid:
        threading.Thread(target=_watch_parent, args=(parent_pid,), daemon=True).start()
    try:
        _serve_forever()
    except Exception as e:
        _log(f"fatal: {type(e).__name__}: {e}")
        raise


if __name__ == "__main__":
    main()
```

#### 4.5.2 客户端 `backend/app/proc_host/client.py`

```python
# -*- coding: utf-8 -*-
# 编辑历史:
# 2026-11-26 - 小欧 - 新建: 进程宿主客户端(自愈重建, run() 与 drain 语义对齐)
# 2026-11-26 - 小欧 - 修正: 补启动期 ensure_host(请求期零 Popen)/连接与接收真实截止时间(原 _CONNECT_TIMEOUT 是死常量)/
#                     每实例管道名与 authkey/协议版本握手/单飞重建
"""client — 与 drain_until_exit 语义对齐的宿主调用层

对外两个入口:
  ensure_host()  启动期调用, 拉起宿主并等就绪; 请求路径不再创建进程(见 4.1)。
  run()          返回五元组 (stdout_b, stderr_b, timed_out, truncated, rc)。

自愈: 连接失败(宿主未起/已死) → 重建后重试一次; 宿主在跑但接收超过截止时间 →
      杀宿主进程树后抛 HostError, 下一条命令自动重建。绝不让调用方感知宿主生命周期。
宿主不可用时按 error 返回, 不保留本地回退(v1.14 起收敛为宿主单路径)。
"""
import os
import subprocess
import sys
import threading
import time
import uuid
from multiprocessing.connection import Client

from app.proc_host import PROTO      # 协议版本唯一真源(包 __init__), 与宿主必须一致

_CONNECT_TIMEOUT = 3.0      # 单次连接尝试上限(原 v1.1 定义了却没用, 本版真正接上)
_START_WAIT = 5.0           # 拉起宿主后等其就绪的上限
_RECV_SLACK = 5.0           # 接收截止 = 命令 timeout + 本余量(覆盖杀树/收尾/时钟抖动)
_CHUNK_WAIT = 0.2           # 单次 poll 粒度

_pipe_name = None
_authkey = None
_host_proc = None
_host_lock = threading.Lock()


class HostError(RuntimeError):
    """宿主不可用(启动失败/中途死亡/无响应)。"""


def _identity() -> "tuple[str, bytes]":
    """本实例的管道名与 authkey: 每进程唯一, 由本进程生成后经环境变量传给宿主。

    写死常量的两个后果: ①开发态与打包态、两个用户会话互抢同一管道; ②固定 authkey
    等于对本机任意进程开放"执行任意命令"的能力。
    """
    global _pipe_name, _authkey
    if _pipe_name is None:
        _pipe_name = rf"\\.\pipe\omni-proc-host-{uuid.uuid4().hex}"
        _authkey = os.urandom(32)
    return _pipe_name, _authkey


def _app_root() -> str:
    """应用根: frozen=exe 同级, 源码=backend 目录。宿主以 -m 拉起时须以此为 cwd/PYTHONPATH。"""
    if getattr(sys, "frozen", False):
        return os.path.dirname(sys.executable)
    return os.path.dirname(os.path.dirname(os.path.dirname(os.path.abspath(__file__))))


def _default_log_path() -> str:
    """宿主日志绝对路径(与 app.logger 的 LOG_DIR 同源): frozen=exe同级/logs, 源码=backend/logs。"""
    return os.path.join(_app_root(), "logs", "proc_host.log")


def _host_concurrency() -> int:
    """宿主并发上限: 外部已设优先; 否则 max(12, 主进程 shell_max_processes)。

    宿主不得比主进程 _SHELL_PROC_SEM 更紧, 否则配置调大后宿主先限流、两级排队口径冲突。
    """
    env_val = os.environ.get("OMNI_PROC_HOST_CONCURRENCY")
    if env_val:
        try:
            return max(1, int(env_val))
        except ValueError:
            pass
    try:
        from app.config import get_config
        shell_max = int(get_config().get("tuning.concurrency.shell_max_processes", 10))
    except Exception:
        shell_max = 10
    return max(12, shell_max)


def _client_with_deadline(deadline: float):
    """在截止时间内完成连接。

    为什么不能直接 Client(): AF_PIPE 走 WaitNamedPipe(NMPWAIT_WAIT_FOREVER), 宿主活着但
    不 accept 时会**永久阻塞**——那正好把"宿主卡死"传导成"主进程线程卡死", 与 E1 目标相反。
    故把连接放进辅助线程, 主线程只做有界 join; 超时后辅助线程即便连上也不得留下悬挂连接(v1.14)。
    """
    box = {}
    abandoned = threading.Event()   # 主线程已放弃: 辅助线程连上后须自行关闭
    name, key = _identity()

    def _do():
        try:
            conn = Client(name, authkey=key)
        except Exception as e:      # AuthenticationError/OSError/EOFError
            box["err"] = e
        else:
            if abandoned.is_set():
                conn.close()        # 主线程已超时放弃, 不留悬挂连接等 GC
            else:
                box["conn"] = conn

    t = threading.Thread(target=_do, daemon=True)
    t.start()
    t.join(max(0.0, deadline - time.monotonic()))
    if t.is_alive():
        abandoned.set()
        raise HostError("连接宿主超时(宿主可能卡死)")
    if "err" in box:
        raise box["err"]
    return box["conn"]


def _kill_host() -> None:
    """杀掉宿主进程树后清空状态; 下一条命令会重建。

    宿主卡在 CreateProcessW 时不响应, 只能从外部杀。TerminateProcess 不需要宿主配合,
    因此这里不会因为宿主卡死而卡住。
    """
    global _host_proc
    p = _host_proc
    _host_proc = None
    if p is None:
        return
    try:
        p.kill()
        p.wait(timeout=5)
    except Exception:
        pass


def _spawn_host() -> None:
    """拉起宿主: CREATE_NO_WINDOW(不用 DETACHED, 实测会静默丢 pwsh 输出)。"""
    global _host_proc
    pipe_name, authkey = _identity()
    root = _app_root()
    if getattr(sys, "frozen", False):
        argv = [sys.executable, "--proc-host"]
    else:
        argv = [sys.executable, "-m", "app.proc_host.host"]
    env = dict(os.environ)
    env["OMNI_PROC_HOST_PIPE"] = pipe_name
    env["OMNI_PROC_HOST_KEY"] = authkey.hex()
    env["OMNI_PROC_HOST_PARENT_PID"] = str(os.getpid())
    env["OMNI_PROC_HOST_LOG"] = _default_log_path()
    env["OMNI_PROC_HOST_CONCURRENCY"] = str(_host_concurrency())
    if not getattr(sys, "frozen", False):
        # -m 依赖 sys.path 含 backend 根: 显式注入 cwd/PYTHONPATH, 不再依赖调用方 cwd
        prev = env.get("PYTHONPATH")
        env["PYTHONPATH"] = root if not prev else root + os.pathsep + prev
    flags = subprocess.CREATE_NO_WINDOW if sys.platform == "win32" else 0
    _host_proc = subprocess.Popen(
        argv, stdin=subprocess.DEVNULL, stdout=subprocess.DEVNULL,
        stderr=subprocess.DEVNULL, creationflags=flags, close_fds=True,
        env=env, cwd=root)
    # 等管道可用(只探测可连, 不发业务帧)
    deadline = time.monotonic() + _START_WAIT
    while time.monotonic() < deadline:
        if _host_proc.poll() is not None:
            raise HostError(f"宿主启动即退出 rc={_host_proc.returncode}")
        try:
            _client_with_deadline(min(deadline, time.monotonic() + 0.5)).close()
            return
        except HostError:
            raise
        except Exception:
            time.sleep(0.05)
    _kill_host()
    raise HostError("宿主启动超时")


def ensure_host() -> None:
    """启动期调用一次: 保证宿主就绪。请求路径不得再走到 _spawn_host()。"""
    with _host_lock:
        if _host_proc is not None and _host_proc.poll() is None:
            return
        _spawn_host()


def _connect():
    """连接宿主; 失败则重建后重试一次(单飞: 锁内复查, 避免并发各起一个宿主)。"""
    deadline = time.monotonic() + _CONNECT_TIMEOUT
    host_at_start = _host_proc
    try:
        return _client_with_deadline(deadline)
    except Exception as first:
        with _host_lock:
            if _host_proc is host_at_start:
                # 连接失败/超时且期间无人替换: 宿主可能卡死。必须杀进程而非仅清状态——
                # 卡死宿主的旧管道不销毁, 辅助线程会永久阻塞在 Client() 内累积。
                _kill_host()
                _spawn_host()
        try:
            return _client_with_deadline(deadline + _START_WAIT)
        except Exception:
            raise HostError(f"宿主不可用: {type(first).__name__}: {first}") from first


def run(argv, cwd=None, env=None, timeout=None):
    """执行一条命令, 返回五元组 (stdout_b, stderr_b, timed_out, truncated, rc)。

    rc = 子进程真实退出码(宿主回传; 取不到才为 -1)。比 drain_until_exit 多带一个 rc,
    是因为 drain_until_exit 从 proc 对象上取 returncode, 而宿主路径下调用方拿不到 proc。
    调用方改造时: returncode = rc, 其余四项语义与 drain_until_exit 完全一致。

    宿主异常时抛 HostError(继承 RuntimeError), 调用方按 error 结构返回, 不静默。
    """
    conn = _connect()
    out, err = [], []
    timed_out = truncated = False
    rc = -1
    deadline = time.monotonic() + (timeout if timeout else 600) + _RECV_SLACK
    try:
        conn.send({"proto": PROTO, "argv": list(argv), "cwd": cwd,
                   "env": env, "timeout": timeout})
        while True:
            # ★ 接收必须有截止时间: recv() 本身无超时参数, 宿主卡死时会永远等下去,
            #   于是"命令超时"退化成"工具调用永不返回"(比卡死更糟, 上层无从判定)。
            if not conn.poll(min(_CHUNK_WAIT, max(0.0, deadline - time.monotonic()))):
                if time.monotonic() >= deadline:
                    _kill_host()
                    raise HostError(f"宿主接收超时(>{timeout}s), 已杀宿主等待重建")
                continue
            msg = conn.recv()
            t = msg["type"]
            if t == "out":
                out.append(msg["data"])
            elif t == "err":
                err.append(msg["data"])
            elif t == "error":
                raise HostError(msg["message"])
            elif t == "done":
                rc = msg["rc"]
                timed_out = msg["timed_out"]
                truncated = msg["truncated"]
                break
    except (EOFError, BrokenPipeError, OSError) as e:
        # 宿主中途死亡: 视为该次执行失败, 上层按 error 处理, 下次调用自愈
        _kill_host()
        raise HostError(f"宿主通信中断: {type(e).__name__}: {e}") from e
    finally:
        try:
            conn.close()
        except Exception:
            pass
    return b"".join(out), b"".join(err), timed_out, truncated, rc
```

> 返回值定为**五元组**（比 `drain_until_exit` 多一个 `rc`）：宿主路径下调用方拿不到 `proc` 对象，取不到 `proc.returncode`，必须由客户端回传。改造时 `returncode = rc`，其余四项语义不变。

**CMD / bash 分支属未实施阶段**：其宿主侧 `argv` 口径、`shell=False` 与 `env` 约束见 7.2.1；本节只保留已实施（阶段一）的 PS 分支改造说明。

#### 4.5.5 存活、自愈与生命周期（v1.2 新增）

v1.1 只有一句"绝不让调用方感知宿主生命周期"，没有落地规则。这里把四个状态和对应动作写死：

| 状态 | 判定依据 | 谁来做 | 结果 |
|---|---|---|---|
| 正常 | `ensure_host()` 成功 / `Client()` 连上 | 主进程 | 命令直连 |
| 未启动 | `_host_proc is None` 或 `poll() is not None` | `_connect()` 锁内单飞重建 | 重建一次后重试；仍失败 → `HostError` |
| 连接卡住 | `Client()` 超过 `_CONNECT_TIMEOUT` 未返回 | `_client_with_deadline()` 辅助线程（超时后加放弃标记，辅助线程连上即自行关闭，不留悬挂连接） | 抛 `HostError`，不动宿主（可能只是忙） |
| 执行无响应 | `conn.poll()` 超过 `timeout + _RECV_SLACK` | `run()` | `_kill_host()` + `HostError`，下条命令重建 |

**为什么重建不放在请求路径上做"预防性拉起"**：重建本身要 `Popen`，而它只在"已经判定宿主异常"之后发生——此时本次命令已经失败，最坏后果是"这一次工具调用失败 + 主进程卡在 `CreateProcessW` 上"。这个风险无法完全消除（除非引入一个独立的 spawner 进程，属过度设计），所以对策是**把重建频率压到接近 0**：宿主只在两种情况下死——被外部杀掉、被 `run()` 判定无响应。正常路径上它一直活着。

**孤儿处理（v1.2 修正）**：v1.1 说"宿主作为子进程自动继承主进程的 KILL_ON_JOB_CLOSE Job"——只在打包态成立（`run_server.py:459-461` 有 `if is_frozen` 判断），源码态主进程根本没进 Job。因此改用**父进程存活看门狗**（4.5.1 `_watch_parent`）：宿主每 5s 用 `OpenProcess(SYNCHRONIZE)` + `WaitForSingleObject(h, 0)` 检查父进程，父进程没了就 `os._exit(0)`。这条对打包态/源码态都成立，不依赖 Job。

**为什么不做"空闲 10 分钟自退"**：宿主一退，下一条命令就得在请求路径上重新 `Popen`，正好破坏 4.1 的阶段零前提。空闲不退出，只随父进程退出。

### 4.6 分阶段落地（已实施部分）

**核心原则：设计一次做通用，实施一次只切一条分支。** 模块从第一天就是通用的 `proc_host`，但调用点逐个迁移，每步跑稳再走下一步。已实施的只有阶段零、阶段一与阶段二（底座加固，设计与验收见 5.3 与第六章）；阶段三及以后（bash / CMD / 后台 / 全量接入）属未实施计划，统见 7.2 清单与 7.4 阶段计划。

| 阶段 | 范围 | 验证期 |
|---|---|---|
| **阶段零（前置）** | 建模块 + 启动期 `ensure_host()`，但**不切任何调用点**（shell 仍走本地 Popen） | 跑三天：确认宿主常驻、日志正常、句柄数平稳、`/health` 不受影响 |
| **阶段一** | 只切 **PS7/PS5 分支**（分支起于 `:1308`，最常卡的一条），v1.14 起无本地回退、收敛为宿主单路径；CMD、bash 保留本地 Popen | 跑一周无回归 |
| **阶段二（底座加固）** | 宿主内每命令独立 Job、退避 / 熔断、请求路径零创建、后台监护人 + ping/pong、输出上限（详见 5.3 与 6.3） | 随阶段零/一回归持续观察 |

**为什么加阶段零**：v1.1 直接从阶段一开始，等于"新模块第一次上线就和核心工具改造同时发生"，出问题时无法判断是宿主本身不稳还是调用点改错。阶段零只验证"宿主能不能稳定常驻"，把两类风险拆开。

### 4.7 不回退，持续发展

阶段一验收通过后（v1.14），`OMNI_PROC_HOST` 开关与 `Disabled` 降级分支已删除，PS 分支收敛为宿主单路径——这是明确决定：**不保留运行时回退能力，后续阶段（bash / CMD / 后台 / 全量接入）继续迁移，直至主进程不再直接创建业务子进程**。

**为什么不回退**（v1.2 纠正 v1.1、v1.14 收口）：v1.1 曾写"三处调用点保留完整本地 Popen 分支，删掉 `try` 外层即回退"，等于**永久保留两套实现**——违反 `AGENTS.md` 禁止 backward：两套实现长期并存、逐步漂移（改了一处忘另一处），最后没人敢删。因此阶段一验收通过后即删除开关与 `Disabled` 分支，只留宿主一条路径；出错就修、往前走，不靠运行时开关退回改造前。

**单路径的爆炸半径（v1.15 补充）**：PS7/PS5 分支删除回退后，宿主不可用（被外部杀 / 崩溃 / 环境坏）的影响面是**全部 PS 命令**——该次调用以 `HostError` 结构化返回（不静默、不挂起），监护人每 5s 判定并在退避 / 熔断约束内重建，恢复后自动转好；环境坏（缺模块、`PYTHONPATH` 错）时所有 PS 命令持续失败，直到环境修复，期间由熔断把重建频率压到每 30s 一次而非每条命令一次。CMD/bash 分支此时仍在本地创建（阶段二 / 三迁移前），故该故障**不波及 CMD/bash**。这是"不回退"的既有代价与边界，接受它以换取单一实现、无两套逻辑漂移。

### 5.2 稳定性加固设计（消解台账 · 阶段二）

本节不再罗列"风险"，而是给出每个已知问题的**可落地解决方案**与落地后的状态；凡属物理 / OS 根本限制、进程内无法消除的，统一归入 5.4"无法消除边界"，并给出影响面收敛与恢复保证。凡能解决的都落到代码，不留只描述、不处置的条目。

#### 5.2.1 四条设计原则（底座总约束）

| 原则 | 含义 | 现有实现 |
|---|---|---|
| 失败显式化 | 任何异常都以明确 error 返回，绝不返回半截 / 脏数据、绝不静默降级 | 协议版本握手（`PROTO`）、`HostError`、`error` 帧、`truncated` 标记 |
| 有界等待 | 连接、接收、启动全部设截止时间，宁可杀宿主重建，绝不无限阻塞 | `_CONNECT_TIMEOUT` / `_START_WAIT` / `_RECV_SLACK` + `conn.poll` 截止 |
| 进程边界隔离 | 主进程事件循环永不被子进程创建或宿主冻结波及 | 宿主独立进程；请求路径零 `Popen`（5.3 落地） |
| 有界恢复 | 故障后自动恢复，恢复动作本身带退避与熔断，不放大故障 | 单飞重建（已落地）+ 指数退避 / 熔断（5.3 落地） |

#### 5.2.2 六项遗漏问题的消解方案

| 编号 | 问题与根因 | 解决方案 | 状态 |
|---|---|---|---|
| Q1 | 单宿主单点：宿主被外部强杀 / 崩溃，重建前命令失败一次 | 宿主无状态（只持连接与命令树，无业务数据）；`_connect` 单飞等待监护人重建（`client.py`）；后台监护人主动重建（5.3-④）；在飞命令以 `HostError` 显式返回（`execute_shell_command.py:1329-1338` 走 error 结构） | 已落地（5.3-③④） |
| Q2 | 僵死宿主：宿主内 `CreateProcessW` 被 conhost / loader lock 阻塞、不释放 GIL，整个宿主冻结；CPython 进程内无法解除 | ①进程边界隔离主进程；②`ping/pong` 健康探测（监护人每 5s 发 ping，3s 无 pong 判死），发现时延由"命令 timeout（最长 600s）"降到 ≤8s；③`_spawn_host` 补 `isolation_kwargs()` 消除控制台继承（Popen 卡 conhost 的诱因） | 已落地（5.3-①④⑤） |
| Q3 | 重建风暴：环境坏（缺模块 / `PYTHONPATH`）→ 启动即失败，每条命令都重建 | 指数退避 0.5→1→2→4→8→16→30s（cap 30s）+ 熔断器：连败 5 次打开，冷却 30s 内快速 `HostError` 不再 Popen；冷却后半开探测一次，探测失败重新冷却 30s；成功清零；日志同因 60s 去重 | 已落地（5.3-②） |
| Q4 | 大输出：client 把全部 stdout/stderr 攒在内存（`client.py:460` 起始容器、`:482-488` 累积与上限判定），GB 级输出 OOM | 输出总量上限 `OMNI_PROC_HOST_MAX_OUTPUT`（默认 64MB）：超限后丢弃后续 chunk、继续 drain 到 `done`、返回 `truncated=True`，`TRUNCATED_NOTE` 由工具层统一追加一次（复用 `proc_io.py:42` 语义）；管道层背压由 pump 线程边读边发 + 命令 `timeout` 兜底 | 已落地（5.3-⑥） |
| Q5 | 并发发送：`PipeConnection.send` 并发调用抛 `ValueError`（out / err / done 三来源） | 单连接 `send_lock` 串行化 `_send`（`host.py:208-218`） | 已落地 |
| Q6 | 启动期失败仅告警（`main.py:629-630`）；请求路径 `_connect` 仍 `_spawn_host`（违背"请求路径零创建"），且 `_spawn_host` 未隔离控制台 | ①`_spawn_host` 补 `isolation_kwargs()`；②后台监护人接管一切创建 / 重建，`ensure_host` 只做首次拉起 + 启动重试 3 次（0.5 / 1 / 2s）；③请求路径 `_connect` 只连接不创建，不可用即快速 `HostError`，由监护人后台恢复 | 已落地（5.3-①③④） |

#### 5.2.3 既有设计保障核对

原列的并发发送、管道名唯一、孤儿自退、`KILL_ON_JOB_CLOSE` 误杀、Job 收编失败、句柄泄漏、输出交错、IPC 开销、conhost 残留等保障项，均已由 5.2.2 的 Q1~Q6 与 5.3 的改造覆盖，无独立遗留。

### 5.4 无法消除边界（根本限制清单，非待办风险）

下列为物理 / OS 根本限制，进程内无法"解决"，只能收敛影响面并按边界使用；**明确不作为遗留风险清单，也无需在接入阶段反复处理**。

| 编号 | 根本限制 | 影响面收敛与恢复保证 |
|---|---|---|
| B1 | 宿主被外部强杀 / 崩溃瞬间**在飞**的命令必然失败 | 命令可能有副作用，禁止自动重放；以 `HostError` 显式失败，监护人立即重建，后续命令 100% 恢复 |

| B3 | 命名管道跨登录会话 / 服务账户访问受 ACL 与命名空间约束 | 本项目单用户桌面、父子进程同一会话，恒满足；若未来服务化需换带 ACL 的 `win32pipe` 或其它 IPC |

### 7.6 进程间通信可靠性论证（Windows 命名管道）

本系统主进程 ↔ 子进程宿主全部走 Windows 命名管道（AF_PIPE）+ `multiprocessing.connection`，不经 TCP / HTTP。本节从传输、鉴权、协议、失败收敛四层给出"为什么可靠"的论证，与第五章 Q1~Q6 的加固互为支撑。

#### 7.6.1 为何选命名管道而非 TCP/HTTP

| 维度 | 命名管道 | TCP loopback | HTTP |
|---|---|---|---|
| 传输路径 | 内核对象，进程间直接内存拷贝 | 网络栈协议栈（本地回环仍走 sock 层） | 在 TCP 之上再加报文/文本解析 |
| 端口 / 握手 / 状态 | 无端口、无握手、无 TIME_WAIT | 有端口、三次握手、TIME_WAIT | 更多层状态 |
| 防火墙 / 杀软 | 不经过网络，无网络策略拦截 | 可能被本机防火墙策略拦截 | 同左 |
| 生命周期感知 | 句柄关闭即 EOF，对端立刻感知 | 依赖 FIN/RST、超时 | 依赖连接与超时 |
| 消息边界 | 长度前缀 framing（见 7.6.2） | 字节流，需自行处理粘包/半包 | 需按报文/行切分 |

结论：本机父子进程的命令执行是"结构化小消息 + 流式输出"场景，命名管道在开销、时延、生命周期感知、消息边界上全面优于 TCP/HTTP，是正确选择。

#### 7.6.2 传输层：帧边界与失败显式

`multiprocessing.connection.Connection`（Windows 上即 AF_PIPE 实现）以**长度前缀**分帧：

- 发送：`_send_bytes` 先写 4 字节长度头（`struct.pack("!i", n)`；`n > 2^31-1` 时用 `-1` + 8 字节 `!Q`），再写 payload。
- 接收：`_recv_bytes` 先读 4 字节头得长度，再 `_recv(size)` **循环 `read` 直到凑满 `n` 字节**。

因此接收端**要么拿到完整一条消息，要么在断连时抛 `EOFError`，绝不会静默返回半截 / 脏数据**——不存在 TCP 式粘包 / 半包解析问题。这正是"高可靠"的关键：失败是显式的，不是隐式的。

#### 7.6.3 鉴权与命名

- 每实例唯一管道名 `\\.\pipe\omni-proc-host-<uuid4hex>`（`client.py:93`），开发态 / 打包态 / 并行测试互不抢管道。
- `os.urandom(32)` 随机 authkey（`client.py:94`）经环境变量传给宿主（`host.py:32-33`），握手由 `multiprocessing.connection` 的 HMAC 机制完成；外部进程无 authkey 无法发送命令，等于开放本机命令执行。

#### 7.6.4 协议层可靠性（叠加在传输层之上）

- **协议版本握手**：首帧校验 `PROTO`（`__init__.py` 唯一真源），新旧宿主 / 客户端错配直接回 `error` 帧并断开，不发生语义错乱。
- **单连接发送锁**：out / err / done 三来源共用一把 `send_lock`（`host.py:204`），杜绝并发 `send` 抛 `ValueError`。
- **连接断开 = 命令取消**：宿主 `_handle` 捕获断开异常后 `terminate_job` 杀整树，不留孤儿。
- **序列化显式失败**：pickle 遇不可序列化对象在发送端即抛错，不污染对端。

#### 7.6.5 失败矩阵（每类故障 → 检测 → 收敛）

| 故障 | 检测手段 | 收敛动作 |
|---|---|---|
| 宿主未启动 | `Client` 连接失败 | 监护人按退避 / 熔断重建（阶段二） |
| 宿主中途死亡 | `EOFError` / `BrokenPipeError` / `OSError` | 杀旧重建 + 在飞命令 `HostError` |
| 宿主冻结 | 连接 / 接收截止时间 + `ping/pong` | 判死 → `_kill_host()` → 重建 |
| 协议错配 | 首帧 `PROTO` 校验 | `error` 帧 + 断开 |
| 对端断开 | EOF | `terminate_job` 杀树 |
| 大输出 | 总量上限 `OMNI_PROC_HOST_MAX_OUTPUT` | `truncated=True` + `TRUNCATED_NOTE` |
| 环境坏、启动即败 | 连续启动失败计数 | 退避 + 熔断，快速失败 + 日志去重 |

#### 7.6.6 结论

命名管道在"本机父子进程命令执行"场景是可靠传输；但系统整体可靠性**不依赖管道"永不失败"**，而依赖"失败必被检测 + 有界收敛 + 恢复幂等"——传输层（7.6.2 帧边界）、鉴权层（7.6.3）、协议层（7.6.4）、恢复层（第五章 Q1~Q6 / 7.6.5）共同保证主进程事件循环零阻塞、命令结果不静默错乱。
