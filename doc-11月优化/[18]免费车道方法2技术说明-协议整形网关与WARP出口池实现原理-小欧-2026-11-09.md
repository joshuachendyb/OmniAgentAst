## 一、技术名称与定位

| 项 | 内容 |
|----|------|
| 技术名称 | **OpenAI 兼容协议整形网关（Protocol-Shaping Gateway）+ WARP 出口池轮换（Egress Pool Rotation）** |
| 实现载体 | opencode2api（Go, 钉 upstream commit `b296a61d` = O2A 1.4.7 血统），运行目录 `opencli\`，8 个运行时文件 |
| 解决的问题 | ① OpenCode Zen 免费车道**不收标准 OpenAI API**——门禁要求"官方 CLI 客户端形状"的请求；② 免费配额按**出口 IP** 记账，单 IP 烧窗即瘫数小时；③ CLI 方案（A''）是 agent 型会拦截工具，宿主工具无法执行——**结构性死穴** |
| 核心思路 | 宿主继续说标准 OpenAI 方言 → 网关在中间**翻译成官方 CLI 形状**（身份指纹+提示/工具注入+改写），并把每个请求**经 WARP 隧道出口发出**（429 被烧即换出口） |

## 二、端到端数据流

```
前端 :5173
   │ POST /api/v1/chat/stream (SSE)
后端 :8100  宿主管线（系统提示/历史注入/ReAct/工具执行/落库）——零代码改动
   │ resolver 读 config.yaml opencli 块 → OpenAI 兼容请求
   │ Bearer <server_keys 同值令牌>
   ▼
网关 :8080（协议整形层，本档主角）
   ① 鉴权（server_keys 常量比较） ② v1/v2 车道选择（免费层走 v2）
   ③ 体整形：官方系统提示全量前置 + 官方 13 工具逐字注入 + 宿主工具 clint_ 改名
   ④ 指纹装配：UA / 四会话头 / 降序会话 id / 40-hex project
   ⑤ 经 WARP 出口池发出（TLS 形状 Go 原生过门禁）
   ▼
WARP 出口池（userspace WireGuard，UDP 2408，无需 TUN/管理员）
   │ 出口 = Cloudflare 分配的公网 /64（IPv6）
   ▼
https://opencode.ai/inference（v2 车道上游）
   │
   └── SSE 原路回传：上游帧 → 网关翻译（clint_ 还原/usage 提取）→ OpenAI 流
       → 后端 chunk(is_reasoning)/action/observation/usage/final → 前端渲染
```

## 三、原理之一：协议整形（让上游认账的五大件）

上游免费层门禁验收过的事实（403=指纹拒 / 429=配额窗，判死活铁律）：

### 3.1 身份指纹（internal/identity + gateway）

| 件 | 原理 |
|----|------|
| UA 整串 | `opencode/latest/2.2.3/cli` 单独发送；**禁发** `x-opencode-request`（v2 车道见到即 403） |
| 四会话头同值 | x-opencode-session / -session-id / affinity / sid 成对同值；会话 id 由 `CanonicalSessionID` 铸造：`ses_`+12hex **降序时间戳编码**（低 12bit 限 0xfc0-0xfff）+14base62+慢钟日期（≤30 天）——2026-10-14 门禁专验此形状 |
| project 指纹 | `x-opencode-project` 每请求派生稳定 40-hex（sha256 派生）；`global` 是共享预烧桶，禁用 |
| TLS 指纹 | 门禁认 Node/Go 的 TLS ClientHello，curl/python 重放 429——Go 原生 http 过关，这也是网关选 Go 的原因之一 |

### 3.2 提示与工具注入（toolshape.go, go:embed）

- **官方系统提示全量前置**（`opencode_prompt_v2.txt`，≈5.7k token/轮）——门禁要求请求体必须长得像官方 CLI 发出的
- **官方 13 工具逐字注入**（`opencode_tools.json`：edit/execute/glob/grep/question/read/shell/skill/subagent/webfetch/websearch/write/patch）——上游校验工具集形状，缺了即拒
- 副作用（已知且已消化）：模型会自发调官方工具（如 grep）。纯问答用 system"不要使用任何工具"压制（实测有效）；Agent 场景走 ReAct 自然消化

### 3.3 工具名改写（结构性破 CLI 死穴的关键）

```
宿主工具 get_weather ──改名──▶ clint_<sha256:12> 上天（混入官方 13 工具中）
模型回吐 tool_calls{name:"clint_3fa2..."} ──响应侧还原──▶ name:"get_weather" 回宿主
```

上游只认"官方工具 + clint_ 挂件"这种形状；宿主工具借 `clint_<sha256:12>` 匿名混入，
历史与响应**两侧还原**——宿主 ReAct 循环无感知。**这就是 CLI 方案做不到、网关方案结构性成立的核心**：
CLI 是 agent（拦截并自己"执行"工具），网关是纯 HTTP 形状改写器（工具调用原样回宿主执行）。
实测：宿主真工具经此链读 version.txt 成功（§六）。

### 3.4 体整形细节

流式补 `include_usage`；无上限补 `max_completion_tokens:32000`；`tool_choice:'none'` 禁发；
title 请求免整形；高负载下上游可能以 JSON 返回整帧 SSE（shape 嗅探，vendor http.js 有实现）。

## 四、原理之二：WARP 出口池（配额窗的破解）

### 4.1 配额语义（上游记账规则）

免费层配额按 **project × 出口 IP 块** 记账：IPv6 按 **/64**、IPv4 按 **/32**。
本机直连（方法1）只有一块出口——烧窗即 429，Retry-After 实测 49924s≈14h。
**破解思路：配额是跟着出口 IP 走的，那就换出口 IP。**

### 4.2 WARP 隧道原理（internal/warp）

- **userspace WireGuard**（wireguard-go）：隧道整个跑在用户态，**不需要 TUN 网卡/管理员权限**，
  出网只要放行 UDP 2408——单机免安装部署的关键
- `registrar.go` 向 Cloudflare 自动注册设备拿凭证+对端配置，每个隧道出口=Cloudflare 分配的独立公网 /64
- `pool.go` 池策略（源码常量为证）：
  - `egressCooldown = 30min`：被上游 429 拒过的 /64 整块冷却——同块内新隧道只会重复同一答案
  - **重复出口检测**：Cloudflare 只发有限个不同 /64，连续 3 次拿到重复块即停手退避（1→5min），不锤注册接口
  - 429 即退役当前出口 → 后台补注册新出口 → 补位即 200
- 实测实录：首两出口（bac5:55f3 / bac1:6520 两个不同 /64）双双 429 被即时淘汰，
  新出口（bac5:55f7）补位**即刻 200**——"等 14 小时"变"换出口即刻过"

### 4.3 边界

共享 /64 可能被全球同款用户烧光（README 已述），表现为连续换出口——池会持续补位，
但极端时无新 /64 可拿；生产重用需观察。

## 五、网关内部实现逻辑（Go 模块如何协作）

| 层 | 模块 | 逻辑 |
|----|------|------|
| 入口 | `gateway.go` | 路由+鉴权（server_keys `crypto/subtle` 常量比较防时序）+**双车道**：v1=`/zen`(OpenCode 1.x 形状, 已退役保留) / v2=`/inference`(2.x 形状, 免费层走此) |
| 整形 | `toolshape.go`+`opencode_prompt*.txt`+`upstream.go` | §三所述五大件的装配点；upstream.go(64.7K 最大) 负责 OpenAI↔CLI 形状互转与 SSE 翻译 |
| 出口 | `pool.go`(代理传输)+`warp/` | proxyTransport(direct) 常规+**bun 伪装**双 client（free 流量伪装成 Bun runtime 发出）；健康跟踪/失败冷却；WARP 绑定经 `warp.go` |
| 韧性 | `first_event.go`/`probe.go`/`refresh.go`/`rotation.go` | 首事件 30s 超时判上游死；模型目录 300s 周期刷新；模型轮换别名 |
| 运维 | `health.go`/`admin`/`telemetry` | /healthz（ready/模型/WARP 状态一屏）；WebUI :8081；日志环 |

**与宿主集成零代码改动的原理**：网关外表面就是标准 OpenAI 兼容 API（`/v1/models`、
`/v1/chat/completions`）——宿主 resolver/ client_sdk 本就是通用 OpenAI 兼容处理器，
指向哪就是哪。接入仅改 `config.yaml` opencli 块（api_base+令牌，两处同值：网关
`config.json.server_keys` ↔ 宿主 `api_key`）。多轮走宿主两段式契约
（先 POST /sessions/{id}/messages 落库，再 /chat/stream+link_enabled），网关不感知会话。

## 七、风险与边界（生产注意）

1. **上游换代风险**：形状硬编码随上游门禁代次演进（v2.2.3 系）——上游换代后需按 PINNED 升级路径重钉
2. **官方 13 工具在场**：模型自发调用官方 grep/read 属已知边；Agent 场景 ReAct 消化，纯问答 system 压制
3. **WARP 共享 /64**：全球同款用户可烧光共享块，池会连续补位但极端时无块可拿
4. **无开机自启**：手动 start.bat；生产化需计划任务/服务包装
5. **熔断纪律**：单发验证不连发；每出口一次尝试即停，尊重 Retry-After——连发只会烧更多 /64

## 八、新旧网关身份轮换对比（会话 ID 之争）

### 8.1 旧网关（gateways 子项目）没有"换会话躲配额"

- cli_manager.py:504 会话 ID 全程随机生成——目的是防串味（不同对话不共享上游粘性状态），且为每对话开场随机一个，并非 429 后轮换
- cli_manager.py:614 + errors.py:13：429 处理 = 内部不等待，把 Retry-After（上限 30s）交还调用方——不换出口，更不换会话

### 8.2 新网关的等价实现（identity/request.go）

- 会话 ID 按对话粘性：系统提示+首条用户消息做种子经 CanonicalSessionID 铸造，同对话恒定；调用者之间以令牌指纹（scope）混合隔离——防串味照样达成，且多一层调用者隔离
- project ID 每请求随机新铸（request.go:86 RandomProjectID）：源码注释原文——免费层配额按 project × 出口记账，共享 id = 共享桶 = 天生预烧
- 429 轮换 WARP 出口（淘汰→30min 冷却→补位），见 §4.2

### 8.3 为什么不轮换会话 ID

配额桶钥匙 = project × 出口，会话 ID 不在钥匙里——轮换它配额一分不多。project 每请求已新（桶名维度满频轮换），出口维度由 WARP 顶；会话粘性反而要保住——同对话粘同一上游供应商，缓存与一致性不抖。

### 8.4 边界实测修正（2026-11-09 晚）

全新 /64 出口 + 全新 project 仍 3 秒内 429——上游在 project×出口之外还有更粗的记账（/64 聚合用量或模型级全局容量），big-pickle 全局饱和时换桶换 IP 皆无效，只能等窗口刷新。§4.3 边界的实证。
