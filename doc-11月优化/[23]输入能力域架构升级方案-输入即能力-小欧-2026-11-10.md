# 输入能力域架构升级方案 — 输入即能力

> 文档名称：[23]输入能力域架构升级方案-输入即能力-小欧-2026-11-10
> 编写：小欧　2026-11-10
> 层级定位：**母文档**（输入能力域总纲）。基础交付在 [22] 附件能力域架构升级方案，两者一体设计、分开验收。
> 架构原则：**薄前端、厚后端**——前端只做采集与渲染，一切判定（类型/去重/上限/准入/状态/路由）归后端。
> 基线：[20] 第五章支持矩阵与 D1~D6 缺陷；[22] CNAR 能力协商渲染。

---

## 0. 拆分决策：一体设计，两份交付

### 0.1 为什么不是"一份大文档"

[22] 已经确立了一条可独立验收的基础能力：**附件 kind × 模型能力 → native/degraded/opaque 的协商渲染**。它自身有完整闭环（契约表、计划器、运输层、守门测试），可以单独上线、单独验收。

如果把"输入框升级 / URL 一等引用 / 能力路由"硬塞进 [22]，会带来两个后果：
1. [22] 从"可独立验收的基础能力"变成"半成品大杂烩"，任何一处未完成都无法验收；
2. 输入框与模型路由属于**上层输入编排**，改动面横跨前端交互、refs 契约、模型选择，和 [22] 的后端渲染地基不是同一抽象层（违反 SLAP）。

### 0.2 最终决策

| 文档 | 角色 | 交付边界 | 验收方式 |
|---|---|---|---|
| [22] | 基础能力层（地基） | 附件 kind 轴、能力画像、运输层、抽取完整性、守门测试 | 独立验收，不依赖 [23] |
| [23]（本文） | 输入能力域总纲（上层） | 输入类型统一、URL 一等引用、输入框体验、抽屉分类筛选、能力路由 | 依赖 [22] 的地基，按阶段验收 |

一句话：**一个设计体系，两份可独立验收的文档。[22] 是 23 的后端地基，23 不重写 22，只在其上编排。**

本文第 1 章开始即为需求输入，后续章节逐条给出架构与落地。

## 1. 需求输入（输入要求，先于设计）

> 以下 5 条是本次设计的**唯一输入**。每条都给出"原始意图 → 可验收要求 → 不做什么"，防止设计跑偏或补漏式堆功能。

### R1 输入框必须支持"专门的 URL 输入"，而非只当普通文本

- **原始意图**：现在输入框只能贴全部文本，用户想给支持外链 Image_URL 的模型一个图片链接，怎么输入？怎么让模型真正读到？支持一个还是多个？
- **现状事实**：输入框 placeholder 已声称"可直接贴公网图片链接"（`InputCore.tsx:124`），后端 `vision._remote_image_urls` 会从**消息正文**里扫 markdown 图片语法或裸图片链接（`vision.py:122-131`），上限 `MAX_REMOTE_IMAGES=4`（`constants.py:134`），且必须模型**实测**支持外链（`vision.py:92-98 accept.image ∈ {url,both}`）。也就是说：**能贴，但只是文本旁路，不是一等输入；仅 image；无 chip、无发送前校验、无能力提示、超 4 条静默截断。**
- **可验收要求**：
  1. URL 成为**一等输入项**（chip 可见、可删、可去重），与附件同级，不再是"藏在正文里的链接"；
  2. 支持**多个** URL：图片沿用 4 条上限，全部 URL 合计上限 8 条，超限**显式提示**而非静默截断；
  3. 支持类型识别：图片 / 视频 / 音频 / 文档 / 未知，类型由后缀单一真源判定；
  4. 发送前即可见该 URL 在当前模型下的处理方式（原生直传 / 下载后处理 / 仅文本降级）；
  5. 准入校验前置：非法/内网/非 http(s) 链接在**加入时**即拒绝，不拖到发送后回执。
- **不做**：不抓取任意网页正文（那是爬虫，不在输入能力域）。

### R2 附件的本质是"输入能力提升"，不是"文件管理"

- **原始意图**：从"输入能力"视角看附件，而不是从网盘/文件管理器视角。
- **可验收要求**：
  1. 设计语言统一为**输入项（InputItem）**：文本、文件引用、选区、上传附件、外链 URL 都是"把外部信息送入模型的通道"，只是通道形态不同；
  2. 附件管理（收藏/最近/任务产物）降级为"输入的来源库"，不再是设计中心；
  3. 所有输入项共享同一套"能力协商 → 原生/降级/档案卡"命运规则，不允许某一类输入自建一套旁路。
- **不做**：不做附件资产运营、不做分享/协作。

### R3 输入信息到底有多少类型？如何组织？是否都走 ref 塞进 message？

- **原始意图**：盘清输入类型全谱与组织方式。
- **现状事实**：
  - 前端用户输入只有 1 个引用类型联合：`'file' | 'selection' | 'attachment'`（`types/chat.ts:278`）；
  - 后端来源白名单更宽：`REF_KINDS = {file, selection, log, message, attachment}`（`constants.py:190`），`log/message` 供工具日志、消息回溯内部引用；
  - 最终塞进 LLM 的方式：`resolver` 逐条读盘/查表产出 `content`（`resolver.py:155-228`，附件分支 `:168`）→ `render_refs_block` 拼成 `<引用资料>` 文本块（`render.py:34-71`）→ `build_user_turn_text` 把"引用块 + 图片占位 + 事项目录 + 用户原话"拼成一条 user 消息（`message_builder.py:198-211`）→ wire 边界 `expand_vision_parts` 把图片占位换成 parts（`message_builder.py:603`）。
  - **结论：是的，除纯文本外全部走 ref 引用通道；附件图片是唯一会在 wire 边界变成原生 part 的类型；正文里的外链图片是唯一绕过 ref 的旁路。**
- **可验收要求**：
  1. 明确"两条轴"：**来源轴**（ref kind）× **内容模态轴**（content kind），二者组合覆盖所有输入；
  2. 外链 URL 从旁路收编为 ref kind=`url`，与其它来源同管道；
  3. 不允许出现第三套"半管道"（如直接在正文里猜链接）。

### R4 附件弹框必须有文件分类筛选能力

- **原始意图**：附件抽屉要能按文件类别筛选。
- **现状事实**：抽屉只有 4 个**作用域**（本会话/最近/收藏/任务产物，`FileDrawer.tsx:113`）+ 文件名搜索；后端 `list_attachments` 只有 `q` 参数，**没有 kind 过滤**（`attachment_service.py:295-297`）。前端图标只按 `mime.startsWith('image/')` 判断（`FileRow iconOf`），无 audio。
- **可验收要求**：
  1. 类型筛选与作用域**正交**：作用域决定"从哪个库取"，类型决定"取哪一类"；
  2. 筛选必须**服务端执行**（否则与 offset 分页冲突，出现"筛出来这页空了但还有下一页"）；
  3. 类型集合来自后端 `classify` 单一真源，前端不自建后缀表；
  4. 至少覆盖：全部 / 图片 / 文档 / 视频 / 音频 / 文本。
- **不做**：不做多选标签筛选、不做自定义标签体系（YAGNI）。

### R5 附件类型与输入模态要和"模型优选顺序"关联，最终兜底文本模型

- **原始意图**：先优选合适模型，最终兜底文本模型；这一层是否要设计？
- **现状事实**：模型由用户在会话显式选择（L2 `sessionModel`，`model/resolver.py:206`）；失败时 `_fallback_snapshot` 退回全局默认（`:197`）。**没有任何"按输入需求选模型"的能力路由**；模型能力画像（[22] 的 `profile`）尚未被选择逻辑消费。
- **可验收要求**：
  1. 由输入项推断**输入能力需求**（需要哪些原生模态）；
  2. 给出**模型优选顺序**：用户显式选择 → 满足需求的可推荐模型 → 全局默认文本模型兜底；
  3. 默认**不静默换模型**：只给"推荐切换"，用户一键确认；自动优选必须显式开启；
  4. 任何情况下**不因能力不足阻断发送**，降级文本照发并回执说明；
  5. 兜底文本模型永远可用（纯文本输入能力恒存在）。
- **不做**：不做多模型并行投票、不做按 token 价格的自动竞价路由（YAGNI）。

## 3. 统一输入模型：InputItem

### 3.1 两条轴（回答 R3）

```
来源轴 ref.kind（信息从哪来）        内容轴 content kind（送进来的到底是什么）
  text        正文（永远存在）
  file        整文件引用                text     纯文本
  selection   行区间引用                image    图片
  attachment  上传附件                  video    视频
  url         外链资源（新增）          audio    音频（22/P3 新增）
  log         工具日志（内部来源）      richdoc  富文档（pdf/word/excel/ppt）
  message     消息回溯（内部来源）      binary   纯二进制（仅档案卡）
```

前端用户可发起来源 = 4 类（file/selection/attachment/url）；后端另有 log/message 两类内部来源，共用同一渲染与白名单。

### 3.2 一条消息的组织形态

```
Turn = { text: string, items: InputItem[] }

InputItem {
  kind: 'file' | 'selection' | 'attachment' | 'url' | ...
  label: string                 # 展示名
  # 来源定位（按 kind 取其一）
  path? / lineRange?            # file / selection
  attachment_id? / mime?        # attachment
  url?                          # url（新增）
  # 派生（后端计算，前端只读）
  content_kind?: string         # 由 classify 统一推断
}
```

**组织原则**：正文 `text` 与 `items` 分离；正文只承载用户原话，不承载任何"隐式资源"；所有资源必有引用项。

### 3.3 数据流（单一管道）

```
前端 composer
  └─ items[] (chips)                       ← 唯一用户意图表达处
        │ 上行（refs DTO，只带标识，不带正文）
        ▼
编排入口 sanitize_refs(kind ∈ REF_KINDS ∪ {url})   ← 白名单单一真源 constants.py:190
        ▼
resolver（按 kind 分支读写/查表/URL 校验）
        ▼
content_kind = classify_ref(item)         ← 内容类型唯一真源（[22] 契约复用）
        ▼
plans = plan_refs(items, profile)         ← [22] 来源无关计划器 → ItemPlan[]
        ├─ state=native → 占位 → wire 边界 → parts
        └─ 其余 → render_refs_block → 文本块（降级）
        ▼
build_user_turn_text：[引用块][原生占位][事项目录][用户原话]
        ▼
LLM message
```

**关键约束**：URL 不再在 `vision._remote_image_urls` 里"猜"，而是作为 items 的一项进入管道；`vision.py` 的正文扫描逻辑在 URL 收编完成后**删除**（禁止双轨），只保留兼容期的显式迁移说明（见 4.4）。

## 4. 输入框升级（R1，薄前端）

> 架构铁律：**前端只做 DOM 采集与渲染；一切类型判定、去重、上限、准入、状态、推荐模型由后端计算。** 本文不复制任何业务规则到前端。

### 4.1 职责边界

| 环节 | 归属 | 说明 |
|---|---|---|
| 粘贴/拖拽/手输的原始捕获 | 前端 | 浏览器事件只能前端接，原样上传，不做判断 |
| URL/文件类型识别 | 后端 | `contract.classify_ref`（22 P0） |
| 去重键归一 | 后端 | `contract.dedup_key`（22 P0） |
| 数量上限判定 | 后端 | `contract.limits` + 发送时强制（22 P0） |
| 准入（协议/内网/重定向） | 后端 | `remote_fetch` 准入函数（22 P4） |
| 每项状态 / 最差状态 | 后端 | `state_of`（22 P1）+ preflight |
| 推荐模型 | 后端 | `capability_router`（本文 §6） |
| chip / 徽标 / 提示渲染 | 前端 | 只读 preflight 返回值 |

### 4.2 交互（前端只做这些）

- **粘贴**：把剪贴板原始文本/uri-list 交给预检；后端返回哪些片段被识别为 `url`，前端据此"在正文中把该片段替换为 chip"。
- **批量**：一次粘贴多个链接，后端返回逐项 `ok/reason`；超限项 `ok=false` 并给出具体上限文案，前端只显示。
- **去重**：后端返回 `dedup_key`；同键项标记"已存在"，前端原位高亮，不自行归一。
- **拖拽**：文件拖入走上传接口；uri-list 拖入交给预检。
- **手输**：菜单"添加链接"提交原文给预检，非法即显示后端 `reason`。

### 4.3 唯一后端入口：输入预检（厚后端核心）

```
POST /api/v1/inputs/preflight
body: {
  session_id, model_id,
  text: string,
  items: [{ source_kind, path?, lineRange?, attachment_id?, url? }]
}
resp: {
  items: [{
    key, source_kind, content_kind,   # classify_ref 结果
    ok, reason?,                       # 非法/内网/超限
    state,                             # native | degraded | opaque（state_of）
    transport,                         # url | inline | none
    dedup_key
  }],
  worst_state,
  limits: { max_refs, max_urls, max_url_images },
  routing_advice: { action: keep|switch|degrade, model?, reason? },
  accepted: bool                       # 仅 strict 模式可能 false
}
```

- 前端任一输入变化 → 防抖调用；返回即渲染 chip/徽标/提示，不再二次计算；
- preflight 是**建议性**；发送时后端用同一函数**再校验一次**（唯一权威），禁止两头规则不一；
- 响应与发送共用 `plan_refs`/`state_of`，保证"看到的 == 发出的"。

### 4.4 发送前处理（完全交给 [22] 计划器）

| 场景 | 22 裁决 | 前端只显示 |
|---|---|---|
| `transport=url` 且模型支持外链 | 原生直传 | 绿"原生直传" |
| 支持内联、不支持外链 | `remote_fetch` 取字节 → 内联/抽取 | 蓝"下载后处理" |
| 无该模态能力 | `fallback_quality='link'` 文本降级 | 灰"仅链接文本" |
| 非法/内网/非 http(s) | `remote_fetch` 准入拒绝 | 红 `reason` |

**下载实现不在本文**：唯一实现在 22 `services/agent/remote_fetch.py`（逐跳 host 重判、拒私网、超时/限额）。本文只调用 `ensure_payload`。

### 4.5 与正文扫描的关系（一次性迁移，不留双轨）

- 新流程：URL 一律进 `items` → preflight → refs(kind=url) → 22 管道；
- 旧正文扫描（`vision._remote_image_urls`）：本文阶段 E **直接删除**；
- 历史数据：一次性迁移，把老消息正文中的图片链接抽出为 `ref kind=url` 行（与 22 的 `[[ATTACHMENT:` token 迁移同一批次），**不做运行期兼容分支**（禁止 backward）。

### 4.6 数量上限（唯一真源在 22）

```
22 contract.limits() = { max_refs: 20, max_urls: 8, max_url_images: 4 }
```

- 前端不自带任何上限常量，全部来自 preflight/配置接口；
- 后端在 preflight 与发送两处使用同一函数拦截，错误码点名具体上限。

- 前端筛选面板的选项由后端 `contract.kind_options()` 下发（经 `GET /attachments` 附带或独立接口），避免前后端词典漂移；
- SQL 只加一个 `IN` 条件，无新表、无迁移。

### 5.2 前端（FileDrawer）

- 作用域 tab（session/recent/global/ai）保持不变；
- 在其下方加一行**类型筛选**（Segmented / 标签）：全部、图片、文档、视频、音频、文本；

## 6. 能力路由与模型优选（R5）

### 6.1 输入需求画像（纯函数，消费 22 的 ItemPlan）

```python
# services/model/capability_router.py（新增）

@dataclass(frozen=True)
class InputNeed:
    required_native: frozenset   # 必须原生才能满足的模态（用户显式要求"必须原生"）
    optional_native: frozenset   # 原生更好、降级也可接受
    degraded_ok: bool            # 是否接受降级（默认 True）
    est_tokens: int              # 上下文估算（复用 limits）

def need_of(plans: list[ItemPlan]) -> InputNeed:
    """入参是 22 plan_refs 产出的 ItemPlan（已含 content_kind/state/transport），
       不直读 22 内部契约字段（fallback_quality 等），避免跨层耦合：
         state=degraded 且 content_kind∈{image,video,audio,richdoc} → optional_native；
         state=native → 需求已满足，不产生新的 required；
         用户显式勾选"必须原生"的项 → required_native；
         content_kind∈{text,binary} → 无原生需求。"""
```

> 该函数只做聚合，不做能力判定；能力与状态一律来自 22 的 `state_of`/`plan_refs`。

### 6.2 优选顺序（唯一裁决链）

```
① 用户显式选择的模型（会话 L2）                ← 尊重意图，永不静默替换
② 若 ① 不满足 required_native：
     a. 同 provider 内已实测满足的模型
     b. 其他 provider 已实测满足的模型（按上下文长度、最近使用、成本排序）
     c. 满足声明但未实测的模型 → 不推荐（安全底线，[22] 3.5）
③ 若 ② 无候选：给出"降级方案"建议（保持当前模型，文本/元数据降级）
④ 发送永远允许：最终兜底 = 全局默认文本模型（纯文本输入恒可用）
```

排序依据（稳定、可测）：`满足必需数 ↓ → 实测优先于声明 → 上下文长度 ≥ 需求 → 最近使用 → 配置顺序`。不做价格竞价、不做多模型并行。

### 6.3 三种模式（用户可控）

| 模式 | 行为 | 默认 |
|---|---|---|
| suggest（建议） | 只在输入区提示"推荐切换至 X"，不改变当前模型 | ✅ |
| auto（自动） | 自动切到候选模型，并在回执说明"为读取图片已切换至 X" | 可选开启 |
| strict（严格） | 缺少必需能力时阻断发送（仅高级用户） | 关闭 |

- 模式是**会话级**设置，不跨会话改变用户的全局默认模型；
- auto 模式下的切换必须可回退（切回原模型一键）；
- 任何模式下 `degraded_ok=False` 且无候选 → 明确告知，不偷偷降级。

### 6.4 与 [22] 的接口

```
[22] capability.profile(model) → {modality: NativeCap}
                    │
                    ▼
[23] need_of(items) → InputNeed
                    │
                    ▼
     route(need, current_model, candidates) → RoutingAdvice
        { keep | switch(model) | degrade(reason) }
```

- 路由只消费能力画像，不自己判断 accept；
- 路由结果不落库；
- 前端展示"模型能力矩阵"时复用同一份 profile 投影（[22] P5 面板）。

## 7. 前端体验闭环（R2 + R5）

### 7.1 三条体验铁律（沿用 [22] 并上移）

1. **预见性**：发送前知道每个输入项会被怎样处理；
2. **一致性**：前后端对同一输入同一模型给出同一结论（单一数据源 `ref_capability` + `RoutingAdvice`）；
3. **无惊扰**：降级静默完成（徽标表达），只有"opaque / 必需能力缺失"才提示，永不静默换模型。

### 7.2 输入区信息层级

```
chips 行：  每个输入项 1 个 chip = [图标][名称][能力徽标][×]
提示行：    only when 需要（推荐切换 / opaque / 超限 / 非法链接）
正文：      用户原话
```

> 徽标 `state` 一律取 preflight 返回的 `items[].state`（逐项，而非按 kind 查表）；`CapabilityBadge` 增加 `state` 直传入参，供 URL chip 与附件 chip 共用同一组件

### 7.3 状态矩阵（扩展 22 §4.2，单一真源）

> 主矩阵（text/image/richdoc/video/audio/binary）以 [22] §4.2 为唯一真源；本表只补本文新增的"URL 来源"行。状态值一律来自后端 `state_of`（22 P1），前端不推导。

| 输入项 | native | degraded | opaque |
|---|---|---|---|
| URL·图片 | 绿 原生直传 | 蓝 下载后处理 | 灰 仅链接文本 |

| 文件引用/选区/目录 | — | 蓝 文本注入 | — |

## 8. 分期路线（可独立验收）

> 顺序原则：先等 22 扩展点落地，再收编入口（URL 进管道），再做可见性，再做筛选，最后做路由。
> **硬依赖**：22 P0 → P1 → P2 → P4 未完成前，本文 A/B/C/D 不得开工。

### 阶段 A（依赖 22 P0 + P2 + P4）URL 一等引用
- 后端：`REF_KINDS` 增 `url`；`resolver` 增 url 分支；新增 `inputs/preflight` 服务与 API（复用 22 `classify_ref/plan_refs/state_of/dedup_key/limits`）。
- 前端：只做粘贴/拖拽原始捕获 + 调 preflight + 渲染 chip；不写识别/去重/上限/校验。
- 验收：多 URL 正常 chip 化；实测支持外链的模型收到 image_url part；不支持的模型降级并可见；非法链接加入时即拒；前端零业务常量。

### 阶段 B（依赖 22 P0 + P1）输入框体验统一
- chip 统一渲染（附件/文件/URL/选区同一组件）；能力徽标只读 preflight（复用 [22] `CapabilityBadge`）；发送前提示直接展示 preflight `worst_state`。
- 验收：所有输入项在发送前都能看到处理方式；前端无状态推导；无第三套旁路。

### 阶段 C（依赖 22 P0 + P3）抽屉分类筛选（R4）
- 后端 `kind` 参数 + `kind_options` 下发；前端筛选行只渲染选项与图标。
- 验收：筛选与作用域正交、分页正确、音频/视频/文档可筛。

### 阶段 D（依赖 22 P1 + P4 + P5）能力路由（R5）
- 新增 `capability_router.py`（纯函数，消费 `ItemPlan`）；suggest 模式默认；auto/strict 可选；推荐条数据来自后端 `routing_advice`。
- 验收：五种典型输入（纯文本/图片URL/PDF/视频/音频）在 3 类模型（全能力/部分/纯文本）下给出正确建议；不静默换模型；发送永不因能力被阻断（strict 除外）。

### 阶段 E（依赖 22 P4）收编旧旁路
- 删除 `vision._remote_image_urls` 正文扫描，**不留运行期兼容分支**；
- 一次性数据迁移：把老会话正文中的图片链接抽出为 `ref kind=url` 行（与 22 的 `[[ATTACHMENT:` token 迁移同批执行）；
- 验收：新消息不再依赖正文扫描；老消息经迁移后走同一 URL 管道，无第二实现。

## 9. 守门测试

### 9.1 后端
1. `REF_KINDS` 与前端 kind 联合类型、DTO schema 三方一致（枚举守门）。

7. `need_of`：各类输入组合的 required/optional 判定表驱动测试（输入为 `ItemPlan`）。

9. 分类筛选：`kind` 参数与 22 `classify` 同源；分页在筛选下不重复不遗漏。

### 9.3 跨层
14. 同一输入 + 同一模型：前端徽标状态 == preflight `state` == 22 `state_of` == 实际 wire part 形态（四处一致）。

## 10. 非目标、风险与取舍

### 10.1 非目标（YAGNI）
- 网页正文抓取、RSS、站点解析；
- 多模型并行/投票/竞价路由；
- 自定义标签、附件分享；
- 语音输入、截图 OCR（未来可作为新 InputItem 来源接入，本期不做）。

### 10.2 风险
- **URL 下载引入新的出网面**：唯一出口在 22 `remote_fetch`（逐跳校验 + 体积/超时上限）；默认只在"模型支持内联但不支持外链"时触发；
- **自动路由夺权**：默认 suggest，auto 必须显式开启且可回退；
- **旁路双轨**：一次性迁移老数据为 `ref kind=url`，运行期只保留一条管道，不留兼容分支。

### 10.3 已知取舍
- URL 未知类型不猜（不做 HEAD 探测）：宁可留在正文当文本，也不发一个可能 400 的 part；
- 分类筛选本期单值：多选标签会拉高前后端复杂度，收益不足。
