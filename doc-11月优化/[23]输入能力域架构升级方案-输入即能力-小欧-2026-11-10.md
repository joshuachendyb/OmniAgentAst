> 编写：小欧　2026-11-10
> 更新：小欧　2026-11-16（阶段 B 前端落地与实施核查标注）
> 层级定位：**母文档**（输入能力域总纲）。基础交付在 [22] 附件能力域架构升级方案，两者一体设计、分开验收。
> 架构原则：**薄前端、厚后端**——前端只做采集与渲染，一切判定（类型/去重/上限/准入/状态/路由）归后端。

## 0. 拆分决策：一体设计，两份交付

### 0.1 为什么不是"一份大文档"

[22] 已经确立了一条可独立验收的基础能力：**附件 kind × 模型能力 → quality 四态（native/text_full/meta_only/link_only）的协商渲染**。它自身有完整闭环（契约表、计划器、运输层、守门测试），可以单独上线、单独验收。

如果把"输入框升级 / URL 一等引用 / 能力路由"硬塞进 [22]，会带来两个后果：
1. [22] 从"可独立验收的基础能力"变成"半成品大杂烩"，任何一处未完成都无法验收；
2. 输入框与模型路由属于**上层输入编排**，改动面横跨前端交互、refs 契约、模型选择，和 [22] 的后端渲染地基不是同一抽象层（违反 SLAP）。

### 0.2 最终决策

| 文档 | 角色 | 交付边界 | 验收方式 |
|---|---|---|---|
| [22] | 基础能力层（地基） | 附件 kind 轴、能力画像、运输层、抽取完整性、守门测试 | 独立验收，不依赖 [23] |
| [23]（本文） | 输入能力域总纲（上层） | 输入类型统一、URL 一等引用、输入框体验、抽屉分类筛选、能力路由 | 依赖 [22] 的地基，按阶段验收 |

一句话：**一个设计体系，两份可独立验收的文档。[22] 是 23 的后端地基，23 不重写 22，只在其上编排。**

本文第 1 章开始即为需求输入，后续章节逐条给出架构与落地。

## 1. 需求输入（输入要求，先于设计）

> 以下 R1~R12 是本次设计的输入：R1~R5 为初始需求，R6~R12 为第二轮三堂会审转为设计输入。每条都给出"原始意图 → 可验收要求 → 不做什么"，防止设计跑偏或补漏式堆功能。

### R1 输入框必须支持"专门的 URL 输入"，而非只当普通文本

- **原始意图**：现在输入框只能贴全部文本，用户想给支持外链 Image_URL 的模型一个图片链接，怎么输入？怎么让模型真正读到？支持一个还是多个？
- **现状事实**：输入框 placeholder 已声称"可直接贴公网图片链接"，后端 `vision._remote_image_urls` 会从**消息正文**里扫 markdown 图片语法或裸图片链接，上限 `MAX_REMOTE_IMAGES=4`，且必须模型**实测**支持外链。也就是说：**能贴，但只是文本旁路，不是一等输入；仅 image；无 chip、无发送前校验、无能力提示、超 4 条静默截断。**（该旁路已于 [22] 正交化整改删除，识别迁入 `contract.scan_text_urls` 无模型依赖全类型。）
- **可验收要求**：
  1. URL 成为**一等输入项**（chip 可见、可删、可去重），与附件同级，不再是"藏在正文里的链接"；
  2. 支持**多个** URL：图片沿用 4 条上限，全部 URL 合计上限 8 条（`contract.limits().max_urls`），超限**显式提示**而非静默截断；
  3. 支持类型识别：图片 / 视频 / 音频 / 富文档 / 文本 / 二进制 / 未知（七类，见 [22] §3.2.1），类型由后缀单一真源判定（`suffix_kind`）；
  4. 发送前即可见该 URL 在当前模型下的处理方式（原生投递 / 全文注入 / 元信息注入 / 仅链接）；
  5. 准入校验前置：非法/内网/非 http(s) 链接在**加入时**即拒绝，不拖到发送后回执。
  6. **识别与能力判定分离**：类型识别（图片/视频/音频/富文档/文本/二进制/未知）无条件执行，**不因当前模型不支持而跳过**；"该模型是否支持"只在请求前（preflight）与发送前判定。
- **不做**：不抓取任意网页正文（那是爬虫，不在输入能力域）。

### R2 附件的本质是"输入能力提升"，不是"文件管理"

- **原始意图**：从"输入能力"视角看附件，而不是从网盘/文件管理器视角。
- **可验收要求**：
  1. 设计语言统一为**输入项（InputItem）**：文本、文件引用、选区、上传附件、外链 URL 都是"把外部信息送入模型的通道"，只是通道形态不同；
  2. 附件管理（收藏/最近/任务产物）降级为"输入的来源库"，不再是设计中心；
  3. 所有输入项共享同一套"能力协商 → 原生/降级/档案卡"命运规则，不允许某一类输入自建一套旁路。
- **不做**：不做附件资产运营、不做分享/协作。

### R3 输入信息到底有多少类型？如何组织？是否都走 ref 塞进 message？

- **原始意图**：盘清输入类型全谱与组织方式。
- **现状事实**：
  - 前端用户输入只有 1 个引用类型联合：`'file' | 'selection' | 'attachment'`；
  - 后端来源白名单更宽：`SOURCE_KINDS = {file, selection, attachment, url}`（`log/message` 已于 [39] 7.1 按 YAGNI 删除，无生产方不可达）；
  - 最终塞进 LLM 的方式：`resolver` 逐条读盘/查表产出 `content` → `render_refs_block` 拼成 `<引用资料>` 文本块 → `build_user_turn_text` 把"引用块 + 槽位行 + 事项目录 + 用户原话"拼成一条 user 消息 → wire 边界 `expand_attachment_parts` 把槽位换成 parts。
  - **结论：是的，除纯文本外全部走 ref 引用通道；attachment/url（含物化后 file/selection）是会在 wire 边界变成原生 part 的类型；正文里的外链图片是唯一绕过 ref 的旁路（已于 [22] 收编删除）。**
- **可验收要求**：
  1. 明确"两条轴"：**来源轴**（`source_kind`）× **内容模态轴**（`content_kind`），二者组合覆盖所有输入；
  2. 外链 URL 从旁路收编为 `source_kind='url'`，与其它来源同管道；
  3. 正文链接只走同一识别入口（`contract.scan_text_urls`），**识别与模型无关**；不得另起运行期旁路、不得在 wire 边界临时猜链接。

### R4 附件弹框必须有文件分类筛选能力

- **原始意图**：附件抽屉要能按文件类别筛选。
- **现状事实**：抽屉只有 4 个**作用域**（本会话/最近/收藏/任务产物）+ 文件名搜索；后端 `list_attachments` 只有 `q` 参数，**没有 kind 过滤**。前端图标已按 `record.kind`（权威字段）映射，含 audio。
- **可验收要求**：
  1. 类型筛选与作用域**正交**：作用域决定"从哪个库取"，类型决定"取哪一类"；
  2. 筛选必须**服务端执行**（否则与 offset 分页冲突）；
  3. 类型集合来自后端 `classify`/`kind_options` 单一真源，前端不自建后缀表；
  4. 至少覆盖：全部 / 图片 / 文档 / 视频 / 音频 / 文本（`kind_options()` 7 类：text/image/video/audio/richdoc/binary/unknown）。
- **不做**：不做多选标签筛选、不做自定义标签体系（YAGNI）。

### R5 附件类型与输入模态要和"模型优选顺序"关联，最终兜底文本模型

- **原始意图**：先优选合适模型，最终兜底文本模型；这一层是否要设计？
- **现状事实**：模型由用户在会话显式选择；失败时 `_fallback_snapshot` 退回全局默认。**没有任何"按输入需求选模型"的能力路由**；模型能力画像（[22] 的 `profile`）尚未被选择逻辑消费。
- **可验收要求**：
  1. 由输入项推断**输入能力需求**（需要哪些原生模态）；
  2. 给出**模型优选顺序**：用户显式选择 → 满足需求的可推荐模型 → 全局默认文本模型兜底；
  3. 默认**不静默换模型**：只给"推荐切换"，用户一键确认；自动优选必须显式开启；
  4. 任何情况下**不因能力不足阻断发送**，降级文本照发并回执说明；
  5. 兜底文本模型永远可用（纯文本输入能力恒存在）。
- **不做**：不做多模型并行投票、不做按 token 价格的自动竞价路由（YAGNI）。

---

### R6 契约必须支持「来源 × 内容」二维索引（第二轮会审输入）

- **原始问题**：同 kind 不同来源降级不同（URL·图片 vs 附件·图片），但契约表只有一维 kind。
- **可验收要求**：`KIND_CONTRACT` 按 `(source_kind, content_kind)` 建索引；`URL·image` 的降级/出口与 `附件·image` 可分别配置；守门测试断言两者可被区分表达。
- **不做**：不为 URL 在前端/计划器另建降级旁路。

### R7 URL 必须有独立占位 token 与 wire 展开通道

- **原始问题**：`ATTACHMENT_SLOT_RE` 只认 32 位 attachment id，URL 无 id，到 wire 边界断链。
- **可验收要求**：URL 项生成独立占位（URL 经 urlsafe-base64 内嵌，去重键仅用于去重）；`expand_attachment_slots` 按 `NativeCap.transport`（`url in transport`）分流；URL 降级文本（仅链接）有明确出口。
- **不做**：不改写 attachment 占位语义、不让 URL 复用 attachment id、不为 URL 引入持久化映射表。

### R8 resolver / sanitize 的 URL 归属必须单点定案

- **原始问题**：[22] 称 resolver 不动，[23] 要求 resolver 增 url 分支，归属矛盾。
- **可验收要求**：URL 分支归属唯一文档与唯一变更清单（归 [22] 扩展点 0），另一份文档只引用、不重复定义。
- **不做**：两处各自实现同一分支。

### R9 全文术语强制区分 source_kind 与 content_kind

- **原始问题**：kind 在 [22] 指内容类型、在 [23] 指来源；`KIND_CONTRACT[classify_ref(item)]` 对 URL 索引不到。
- **可验收要求**：`classify_ref` 返回 `(source_kind, content_kind)` 二元组；ref.kind 一律称 `source_kind`；计划器索引与契约表二维键统一。
- **不做**：同一符号两种含义。

### R10 历史数据不得写库、不得改写正文

- **原始问题**：refs 不入库，却要求把正文链接抽出为 ref 行；且改写用户正文。
- **可验收要求**：迁移只做消息内 token 替换；正文零改写；历史消息的正文链接在重放时按需派生，不持久化为 ref。
- **不做**：为历史 URL 新建存储、改写用户消息文本。

### R11 状态 / limits / 分类 / 去重必须各自唯一出口

- **原始问题**：状态两条来源（按 kind 查表 vs preflight）、limits 三个出口、classify 双调用点。
- **可验收要求**：状态唯一由 `quality_of(source_kind, content_kind, prof)` 计算；附件 chip 读取其二维投影 `ref_quality_map`，URL 逐项走 preflight `items[].quality`，守门测试断言两者相等；limits 唯一来自 `contract.limits()`；分类唯一来自 `classify_ref`（且在 `plan_refs` 内）；去重唯一来自去重键（`dedup_key` 已于 [22] 正交化删除，实施时按 preflight 定点声明）。
- **不做**：任何旁路判定或前端本地推导。

### R12 契约与接口完整性补齐

- **原始问题**：unknown 无表行、required_native 无字段、transport×source 组合未定义、worst_quality 无接口、`MAX_REFS` 残留。
- **可验收要求**：逐项补齐并写入守门测试；变更清单同步删除 `store.ts` 的 `MAX_REFS`（已删，改 `maxRefs` 缓存）与 `GET /attachments/limits` 冗余出口。
- **不做**：以"后续优化"名义遗漏。

## 3. 统一输入模型：InputItem

### 3.1 两条轴（回答 R3）

```
来源轴 source_kind（信息从哪来）      内容轴 content_kind（送进来的到底是什么）
  text        正文（永远存在）
  file        整文件引用                text     纯文本
  selection   行区间引用                image    图片
  attachment  上传附件                  video    视频
  url         外链资源（新增）          audio    音频（22/P3 新增）
                                        richdoc  富文档（pdf/word/excel/ppt）
                                        binary   纯二进制（仅档案卡）
                                        unknown  无法识别（兜底仅链接/档案）
```

前端用户可发起来源 = 4 类（file/selection/attachment/url）；后端 `SOURCE_KINDS` 与前端一致（`log/message` 已于 [39] 7.1 按 YAGNI 删除，无生产方不可达，不留死分支）。

### 3.2 一条消息的组织形态

```
Turn = { text: string, items: InputItem[] }

InputItem {
  source_kind: 'file' | 'selection' | 'attachment' | 'url'
  label: string                 # 展示名
  # 来源定位（按 source_kind 取其一）
  path? / lineRange?            # file / selection
  attachment_id? / mime?        # attachment
  url?                          # url（新增）
  must_native?: boolean         # 用户显式要求"必须原生"（InputItem 层，不在 ItemPlan）
  # 派生（后端计算，前端只读）
  content_kind?: string         # 由 classify_ref 统一推断
}
```

**组织原则**：正文 `text` 与 `items` 分离；正文只承载用户原话，不承载任何"隐式资源"；所有资源必有引用项。

### 3.3 数据流（单一管道）

```
前端 composer
  └─ items[] (chips)                       ← 唯一用户意图表达处
        │ 上行（refs DTO，只带标识，不带正文）
        ▼
编排入口 sanitize_refs(source_kind ∈ SOURCE_KINDS)   ← 白名单单一真源 contract.py:97
        ▼
resolver（按 source_kind 分支读写/查表/URL 校验；url 分支由 22 扩展点 0 交付；
         file/selection 图片/音频物化补 attachment_id，见 [39] 7.4 阶段 B）
        ▼
plans = plan_refs(items, profile)         ← [22] 内部调用 classify_ref（唯一分类点）→ ItemPlan[]
        ├─ delivery=slot（quality=native）→ 写槽（SLOT_WRITERS[source_kind].make）→ wire 边界 → parts
        └─ delivery=text（其余 quality）→ render_refs_block → 文本块（降级）
        ▼
build_user_turn_text：[引用块][槽位行][事项目录][用户原话]
        ▼
LLM message
```

**关键约束**：
- URL 不再在旧 `vision._remote_image_urls` 里"猜"，而是作为 items 的一项进入管道；旧正文扫描逻辑已删除（[22] 正交化），识别统一到 `contract.scan_text_urls`（无模型依赖、全类型），**无运行期双实现**。
- 装配层按 `QUALITY_TO_DELIVERY[quality]` 派生 `delivery`（slot/text），**不出现 `source_kind` 字面量分派**（[36] 4.4.3 纪律 2）。
- 插话路径与首发共用 `plan_refs`（[39] 7.2）：`build_interject_text` 增 `plans` 形参，编排层 `_iplans = plan_refs(_ifinal, profile(...))`，消插话恒降级文本。

## 4. 输入框升级（R1，薄前端）

> 架构铁律：**前端只做 DOM 采集与渲染；一切类型判定、去重、上限、准入、状态、推荐模型由后端计算。** 本文不复制任何业务规则到前端。

### 4.1 职责边界

| 环节 | 归属 | 说明 |
|---|---|---|
| 粘贴/拖拽/手输的原始捕获 | 前端 | 浏览器事件只能前端接，原样上传，不做判断 |
| URL/文件类型识别 | 后端（识别阶段） | `contract.classify_ref/scan_text_urls`（22 P0）；**无模型参数、全类型、无条件执行** |
| 去重键归一 | 后端 | 去重键（`dedup_key` 已删，实施时按 preflight 定点声明） |
| 数量上限判定 | 后端 | `contract.limits` + 发送时强制（22 P0） |
| 准入（协议/内网/重定向） | 后端 | `remote_fetch` 准入函数（22 P4） |
| 每项状态 / 最差状态 | 后端（请求前） | `quality_of`（22 P1）+ preflight；**读模型能力，不在识别阶段判定** |
| 推荐模型 | 后端 | `capability_router`（本文 §6） |
| chip / 徽标 / 提示渲染 | 前端 | 只读 preflight 返回值 |

### 4.2 交互（前端只做这些）

- **粘贴**：把剪贴板原始文本/uri-list 交给预检；后端在**识别阶段（无模型参数）**返回哪些片段被识别为 `url` 及各自 `content_kind`，前端据此"在正文中把该片段替换为 chip"。
- **批量**：一次粘贴多个链接，后端返回逐项 `ok/reason`；超限项 `ok=false` 并给出具体上限文案，前端只显示。
- **去重**：后端在 preflight 返回 `duplicate_of`（同键项的 key）；前端只按该标记原位高亮，不计算、不归一。
- **拖拽**：文件拖入走上传接口；uri-list 拖入交给预检。
- **手输**：菜单"添加链接"提交原文给预检，非法即显示后端 `reason`。
- **提示语（placeholder）**：现文案只暗示图片，与 R1 的图片/视频/音频/富文档/文本/二进制/未知七类识别不符；改为全类型统一提示（如"可直接贴图片/视频/音频/文档/文本链接，或拖入文件"），**不写死上限数字**（上限唯一来自后端 `contract.limits()`，避免双源漂移）。

### 4.3 两阶段管线：识别（模型无关）→ 能力判定（模型相关）

> 铁律：**识别不是能力判断。** 识别只回答"这是什么"，永远执行、与模型无关；"模型能不能用"只在请求前（preflight）与发送前（`plan_refs`）回答。识别阶段绝不因模型不支持而跳过，也不只识别图片。

#### 4.3.1 识别阶段（纯函数，无 `model_id`）

- 输入：原始 `items` 与正文 `text`；正文中粘贴的 URL 一律扫描，覆盖 `image/video/audio/richdoc/text/binary/unknown` 七类（见 [22] §3.2.1），**不再只认图片、不再以 `accept.image` 决定是否扫描**；
- 调用 `contract.classify_ref(item)` 与 `contract.scan_text_urls(text)`，产出 `source_kind/content_kind/key/duplicate_of`；
- 只做语法与准入级校验（协议/内网/后缀），不下载、不读模型配置；
- 识别结果对所有模型完全一致，可缓存、可重放；这是"请求前就能知道这是什么"的唯一来源。

#### 4.3.2 能力判定阶段（读模型画像）

- 输入：识别结果 + `model_id`；调用 22 `profile/plan_refs/quality_of`，产出 `quality/delivery/routing_advice`；
- 只在**请求前（preflight）**与**发送前（发送侧唯一权威）**执行；preflight 是建议性预览，发送侧再算一次；
- 切换模型只重算本阶段，不重跑识别。

#### 4.3.3 唯一入口：输入预检（厚后端核心）

```
POST /api/v1/inputs/preflight
body: {
  session_id, model_id,                # model_id 仅用于 4.3.2 能力判定
  text: string,
  items: [{ source_kind, path?, lineRange?, attachment_id?, url?, must_native? }]
}
resp: {
  items: [{
    key, source_kind, content_kind,   # 4.3.1 识别结果（模型无关）
    ok, reason?,                       # 非法/内网/超限（识别级校验）
    quality,                           # 4.3.2 能力判定（模型相关）native | text_full | meta_only | link_only
    delivery,                          # slot | text（由 QUALITY_TO_DELIVERY[quality] 派生）
    must_native,                       # 用户显式要求（InputItem 层）
    dedup_key,
    duplicate_of?                      # 同键已存在项的 key
  }],
  worst_quality,                       # 最差质量档（quality 聚合，替代旧 worst_state）
  routing_advice: { action: keep|switch|degrade, model?, reason? }
}
```

- 前端任一输入变化 → 防抖调用；返回即渲染 chip/徽标/提示，不再二次计算；
- 内部严格分两段执行：4.3.1 识别（无 `model_id`、模型无关）→ 4.3.2 能力判定（读模型画像）；识别结果不随模型变化，切换模型只重算能力段；
- preflight 只做**建议性预览**（不含 `accepted`、不含 limits）；limits/类型选项由 22 的 `GET /attachments/capabilities` 单出口提供；
- preflight 只做轻量校验：对 url 不下载（只做准入与后缀分类），对附件只读元数据，不触发二次抽取；真正下载/抽取在发送侧 `ensure_payload`；
- 发送时后端用同一 `plan_refs`/`quality_of` **再校验一次（唯一权威）**；strict 模式的阻断只在发送侧表达（HTTP 409 + 具体必需能力），preflight 永不阻断；
- 响应与发送共用 `plan_refs`/`quality_of`，保证"看到的 == 发出的"。

### 4.4 发送前处理（完全交给 [22] 计划器）

| 场景 | 22 裁决 | 前端只显示 |
|---|---|---|
| `url in NativeCap.transport` 且模型支持外链 | 原生直传 | 绿"原生直传" |
| 支持内联、不支持外链 | `remote_fetch` 取字节 → 内联/抽取 | 蓝"下载后处理" |
| 无该模态能力 | `fallback_quality='link_only'` 文本降级 | 灰"仅链接文本" |
| 非法/内网/非 http(s) | `remote_fetch` 准入拒绝 | 红 `reason` |

> `url in NativeCap.transport` 仅当该模态实测 accept∈{url,both} 且适配器有方言实现；video/audio 无方言实现时即便实测也降级为链接（不制造虚假原生，见 [22] §3.5）。投递动作由 `QUALITY_TO_DELIVERY[quality]` 单表派生（slot/text），装配层不二次翻译。

**下载实现不在本文**：唯一实现在 22 `services/agent/remote_fetch.py`（逐跳 host 重判、拒私网、超时/限额）。本文只调用 `ensure_payload`。

### 4.5 与正文扫描的关系（一次性迁移，不留双轨）

- 新流程：URL 一律进 `items` → 识别（模型无关，全类型）→ 能力判定 → refs(source_kind=url) → 22 管道；
- 旧正文扫描（`vision._remote_image_urls`）：已删除（[22] 正交化），识别能力迁入 `contract.scan_text_urls`，**无条件覆盖 `image/video/audio/richdoc/text/binary/unknown` 七类**；阶段 E 只确认删除旧入口，不重复删除；
- 新消息：识别出的正文 URL 一律进 items/refs，不再有"模型不支持就不识别"的旁路；
- 历史数据：**不写库、不改正文**。refs 本就不落库，历史消息只保留原文本；回放时对正文全部公网链接按需派生 `url` item（读时组装），派生同样与模型无关，不持久化、不删除正文片段；
- 22 的 `[[IMAGE_ATTACHMENT:` → `[[ATTACHMENT:` 迁移仅作用于消息内占位 token，与正文链接无关，两者不合并表述。

### 4.6 数量上限（唯一真源在 22）

```
22 contract.limits() = { max_refs: 20, max_urls: 8, max_url_images: 4,
                         max_image_bytes, max_file_bytes }
```

- 前端不带任何上限常量，唯一来源 `GET /attachments/capabilities`（22 交付，`limits`/`kind_options`/`accept` 同源）；启动时拉取一次并缓存，**接口失败回落内置默认 20 做入队期拦截**（可用性兜底：值仍来自后端下发，非前端第二真源；恢复后即被下发值覆盖）；`store.ts` 的 `MAX_REFS` 已删，改 `maxRefs` 模块缓存 + `setMaxRefs()`（22 侧已落地）；
- 后端在 preflight 与发送两处调用同一 `contract.limits()` 拦截，错误码点名具体上限；preflight 响应不重复回传 limits。

## 6. 能力路由与模型优选（R5）

### 6.1 输入需求画像（纯函数，消费 22 的 ItemPlan）

```python
# services/model/capability_router.py（新增）

@dataclass(frozen=True)
class InputNeed:
    required_native: frozenset   # 必须原生才能满足的模态（用户显式要求"必须原生"）
    optional_native: frozenset   # 原生更好、降级也可接受
    degraded_ok: bool            # 是否接受降级（默认 True）
    est_tokens: int              # 上下文估算（复用 limits）

def need_of(plans: list[ItemPlan]) -> InputNeed:
    """入参是 22 plan_refs 产出的 ItemPlan（已含 content_kind/quality），
       不直读 22 内部契约字段（fallback_quality 等），避免跨层耦合：
         quality ∈ {text_full, meta_only, link_only} 且 content_kind∈{image,video,audio,richdoc}
           → optional_native（降级可接受）；
         quality=native → 需求已满足，不产生新的 required；
         item.must_native=True 且 quality!=native → required_native（来自 preflight.items[].must_native）；
         content_kind∈{text,binary} → 无原生需求。"""
```

> 该函数只做聚合，不做能力判定；能力与质量一律来自 22 的 `quality_of`/`plan_refs`。

### 6.2 优选顺序（唯一裁决链）

```
① 用户显式选择的模型（会话 L2）                ← 尊重意图，永不静默替换
② 若 ① 不满足 required_native：
     a. 同 provider 内声明满足该输入需求的模型（声明模态即首选请求模式，失败自动回退）
     b. 其他 provider 声明满足的模型（按上下文长度、最近使用、配置顺序排序）
     c. 实测结果仅作参考标注展示（如"已实测通过"徽标），不作推荐门槛（探针数据可能过期/失效，见 [22] §3.5）
③ 若 ② 无候选：给出"降级方案"建议（保持当前模型，文本/元数据降级）
④ 发送永远允许：最终兜底 = 全局默认文本模型（纯文本输入恒可用）
```

排序依据（稳定、可测）：`满足必需数 ↓ → 实测优先于声明 → 上下文长度 ≥ 需求 → 最近使用 → 配置顺序`。不做价格竞价、不做多模型并行。

### 6.3 三种模式（用户可控）

| 模式 | 行为 | 默认 |
|---|---|---|
| suggest（建议） | 只在输入区提示"推荐切换至 X"，不改变当前模型 | ✅ |
| auto（自动） | 自动切到候选模型，并在回执说明"为读取图片已切换至 X" | 可选开启 |
| strict（严格） | 缺少必需能力时阻断发送（仅高级用户） | 关闭 |

- 模式是**会话级**设置，不跨会话改变用户的全局默认模型；
- auto 模式下的切换必须可回退（切回原模型一键）；
- 任何模式下 `degraded_ok=False` 且无候选 → 明确告知，不偷偷降级。

### 6.4 与 [22] 的接口

```
[22] capability.profile_of(provider, model) → {modality: NativeCap}   # preflight 侧统一入口
     capability.profile(llm_model)                                    # 发送侧投影
                    │
                    ▼
[23] need_of(plans) → InputNeed
                    │
                    ▼
     route(need, current_model, candidates) → RoutingAdvice
        { keep | switch(model) | degrade(reason) }
```

- 路由只消费能力画像，不自己判断 accept；
- 路由结果不落库；
- 前端展示"模型能力矩阵"时复用同一份 `ref_quality_map` 投影（[22] P5 面板，前端 `ModelTabRefQuality` 读 `quality` 四值，不再按 content_kind 二次翻译）。

## 7. 前端体验闭环（R2 + R5）

### 7.1 三条体验铁律（沿用 [22] 并上移）

1. **预见性**：发送前知道每个输入项会被怎样处理；
2. **一致性**：前后端对同一输入同一模型给出同一结论（单一数据源 `quality_of` 及其投影 `ref_quality_map` + `RoutingAdvice`）；
3. **无惊扰**：降级静默完成（徽标表达），只有"link_only / 必需能力缺失"才提示，永不静默换模型。

### 7.2 输入区信息层级

```
chips 行：  每个输入项 1 个 chip = [图标][名称][能力徽标][×]
提示行：    only when 需要（推荐切换 / link_only / 超限 / 非法链接）
```

> 徽标 `quality` 由后端给出：URL chip 取 preflight 返回的 `items[].quality`（逐项，而非按 kind 查表）；附件/文件 chip 取 `ref_quality_map[source_kind][content_kind]`；两者同源 `quality_of`，`QualityBadge` 统一以 `quality` 直传入参（前端只按 `quality` 查 `QUALITY_META` 单表，**不按 content_kind 二次翻译**，[36] 4.4.3 纪律 4）。

**后端守门（G1~G14）**：
1. `SOURCE_KINDS` 与前端 kind 联合类型、DTO schema 三方一致（枚举守门，§9.2 A11）。
2. 每个 `source_kind` 都有 resolver 分支且失败有 reason（不允许静默丢弃）。
3. URL 准入（22 `remote_fetch`）：内网/回环/保留/非 http(s)/重定向到内网 全部拒绝。
4. URL 上限（22 `contract.limits`）：8 条总量、4 条图片子限，超限显式错误码。
5. `preflight`：逐项 `content_kind/quality/delivery/去重键/duplicate_of` 与 22 `plan_refs` 一致；`worst_quality` 正确；非法项 `ok=false` 且带 reason；响应不含 limits/accepted（§9.2 A1~A5）。

8. `route`：候选为空、实测/声明混合、上下文不足、纯文本兜底，逐分支断言（§9.5 D2~D5）。
9. 分类筛选：`kind` 参数与 22 `classify` 同源；分页在筛选下不重复不遗漏（§9.4 C1/C4）。
10. `expand_kind` 复用 classify 后缀词典；`kind_options` 覆盖 7 类且下发（§9.4 C2/C3）。
11. `routing_advice` 三态：`{action: keep|switch|degrade, model?, reason?}` 逐一断言（§9.5 D7）。
12. 回放派生：不写库、不改正文、与模型无关（§9.6 E1/E2）。

**前端守门（G15~G20）**：
15. 粘贴多链接 → 按 preflight 返回原样渲染 chip，不本地去重/计数（§9.2 A1）。
16. 切换模型 → 附件/文件徽标按新 `ref_quality_map` 重索引（无请求），URL 徽标与推荐条由重调 preflight 刷新；两者结果一致（§9.3 B5）。
17. 筛选切换 → offset 重置、列表正确、空态文案正确（§9.4 C6/C7）。
18. `preflight` 字段缺失/请求失败 → 降级为 unknown 且不崩，不本地推断。
19. `store.ts` 无本地上限（`maxRefs` 来自 `contract.limits`）；`InputCore` placeholder 全类型提示（§9.2 A9/A10）。
20. chip 统一渲染（附件/文件/URL/选区同一组件）；提示行三类提示互不串扰；前端零派生（§9.3 B1/B4/B6）。

**跨层守门（G21~G26）**：
21. 同一输入 + 同一模型：URL 徽标 == preflight `quality` == 22 `quality_of` == 实际 wire part 形态；附件 chip == `ref_quality_map[source_kind][content_kind]` == 同一 `quality_of`（§9.2 A2）。
22. `must_native` 上行：`preflight.items[].must_native` 进入 `need_of`，满足/不满足两分支均有断言（§9.5 D6）。
23. 未知来源/内容：`(source_kind=url, content_kind=unknown)` 不崩，按链接兜底且不产生虚假绿。
24. 识别与模型无关：同一输入在"全能力/部分能力/纯文本"三类模型下，识别出的 URL 列表与 `content_kind` 完全一致；未实测/不支持外链的模型仍识别出 URL，仅 `quality/delivery` 不同（§9.2 A12）。

### 10.2 风险
- **URL 下载引入新的出网面**：唯一出口在 22 `remote_fetch`（逐跳校验 + 体积/超时上限）；默认只在"模型支持内联但不支持外链"时触发；
- **自动路由夺权**：默认 suggest，auto 必须显式开启且可回退；
- **旁路双轨**：新消息直接收编；历史正文不回写，回放时按需派生 url item，运行期只保留一条管道，不留兼容分支；
- **本地引用物化写副作用**：`file/selection` 图片/音频物化会复制用户本地文件到附件库（[39] 7.4 阶段 B），涉及存储成本、隐私与清理策略，须产品确认后启用；未确认则维持 `meta_only`。

### 10.3 已知取舍
- URL 未知类型不猜（不做 HEAD 探测）：宁可留在正文当文本，也不发一个可能 400 的 part；
- 分类筛选本期单值：多选标签会拉高前后端复杂度，收益不足；
- `video` 本地文件默认不可原生（chat 方言无内联 part，`media_payload` 视频分支显式回落；provider 声明支持视频内联时可按能力门控定制，[39] 3.2.5）。
