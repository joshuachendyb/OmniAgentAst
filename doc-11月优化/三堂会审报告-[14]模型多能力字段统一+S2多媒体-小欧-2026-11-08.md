## 一、真实违规清单（5 个）

### 违规 1：B3 迁移钩子完全未落地（model_service.py）
- **设计要求**（§3.3）：`_migrate_legacy_capabilities(config_path)` 启动一次性迁移函数（真实完整代码），在 `replace_provider_models`/`fetch_remote_models` 落盘前 + startup 对 `config/config.yaml` 与 `backend/config.yaml.example` 各调一次。
- **实际**：`model_service.py` 中**无 `def _migrate_legacy_capabilities` 定义、无任何调用**（仅 :716 注释提到）；其依赖的 `_read_yaml`/`_write_yaml` 也不存在；`_merge_capabilities_into_modalities`（:711）**只有定义、无调用（死代码）**。
- **后果**：agnes/ZenFree 老 `capabilities` 数据**无自动迁移兜底**（当前 config 无残留是手工/其他方式迁移的结果，非代码保证）；D4 决策（老数据一次性迁移）代码侧未落地；验收要点 5/6 依赖手工迁移而非代码保证。
- **违反原则**：DRY/SRP（迁移逻辑应单点化）、设计未实现。

### 违规 2：B4 违反 — `_KEY_ALIASES` 保留 `capabilities` + 双读兜底（model_service.py）
- **设计要求**（B4/§6.1）：`_KEY_ALIASES` 移除 `capabilities`（如有全链路引用），能力只走 `input_modalities` + `output_modalities` 双字段；验收要点 6：全链路无 `capabilities` 双读兜底。
- **实际**：`_KEY_ALIASES` 仍含 `"capabilities": ["capabilities"]`（:772）；`_parse_remote_models_body` 仍读 `merged.get("capabilities")`（:948）传给 `_merge_capabilities`（:699）。
- **后果**：全链路仍有 `capabilities` 双读（虽用于 `capabilities.reasoning` 推理布尔提取，非模态，但违反 B4 字面"移除 capabilities"与验收要点 6）。
- **说明**：`_merge_capabilities` 的 reasoning 提取是独立推理维度，设计文档未明确要删；但 `_KEY_ALIASES` 保留 capabilities 键名违反 B4 字面要求。

### 违规 3：测试与实现脱节（前端 tests 引用已删字段）
- **设计要求**（F2）：state `capabilities`→`inputModalities` 全 4 通道，`setCapabilities` 删除。
- **实际**：`frontend/src/tests/unit/settings2-capabilities-tdd.test.tsx` 大量引用已删除的 `state.model.capabilities`/`capabilitiesBaseline`（:210-214 等）与 `setCapabilities`（:264/275/288/298/319/357/373）；`settings2-edsave-red.test.tsx` 也用 `capabilities: []`（:91/109）。而 useSettings 已删除 `setCapabilities`（仅注释 :1592）、types.ts ModelState 已改 `inputModalities`/`outputModalities`（:65-68）。
- **后果**：测试引用不存在的字段/函数 → TS 编译失败 / 运行时失败（假红）；测试与实现脱节。
- **违反原则**：项目铁规"严禁以测试代码作为锁死错误系统逻辑的修改借口"（测试应真实反映新字段，而非停留在旧字段）。

### 违规 4：F3 输出模态行缺未知值灰色只读 Tag（SettingsPage.tsx）
- **设计要求**（§3.10.1 :495/:511）：输出模态行"未知值灰色只读 Tag 同'模型能力'行"。
- **实际**：输出模态行（:643-658）只有 `<Checkbox.Group>`，**无 `KNOWN_CAPABILITY_VALUES` 过滤 + 未知值灰色 Tag**；而输入模态行（:620-635）有该处理。
- **后果**：`output_modalities` 含未知值（如 `text`/`audio`）时，用户看不到该值（输入行能看到，输出行看不到），两行行为不一致。

### 违规 5：B21 两文件不同构 — example 的 sensenova 无 model_meta（config.yaml.example）
- **设计要求**（§3.4.3）："把 §3.4.1/§3.4.2 对 agnes/sensenova 的双维度能力标注**同样写入 example**，让模板与真实 config 同构"。
- **实际**：`backend/config.yaml.example` 的 **agnes 块已有 model_meta 双维度标注**（agnes-image-2.5-flash 等 ✓），但 **sensenova 块无 model_meta**（只有 `models: [deepseek-v4-flash, glm-5.2, sensenova-6.8-flash-lite, kimi-k3]`）。
- **后果**：新用户从模板起步的 sensenova 无能力标注，与真实 config 口径分叉；违反验收要点 12（两文件同构同步）。

## 二、存疑（1 个，需实测确认）

### 存疑：D5 标注修正 — deepseek-flash / kimi-k3 缺 image（config.yaml）
- **设计要求**（§3.4.2 :361）：`sensenova-6.8-flash`/`6.8-flash-lite`/`deepseek-flash`/`kimi-k3` 是**多模态理解模型**（`input_modalities:[text,image]`）。
- **实际**：config.yaml 的 `sensenova-6.8-flash` input:[text,image] ✓；但 `deepseek-flash` input:[text]（缺 image）、`kimi-k3` input:[text]（缺 image）。
- **存疑点**：设计文档 §3.4.2 说"config 已对"，但实际 deepseek-flash/kimi-k3 只有 [text]。需实测确认这两个模型是否真支持 `image_url` 看图；若支持则 config 漏标（违规），若不支持则设计文档判断有误（config [text] 正确）。
