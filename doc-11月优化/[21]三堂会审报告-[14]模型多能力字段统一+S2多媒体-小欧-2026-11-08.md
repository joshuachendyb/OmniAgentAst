## 一、真实违规清单（5 个）

### 违规 1：B3 迁移钩子完全未落地（model_service.py）
- **设计要求**（§3.3）：`_migrate_legacy_capabilities(config_path)` 启动一次性迁移函数（真实完整代码），在 `replace_provider_models`/`fetch_remote_models` 落盘前 + startup 对 `config/config.yaml` 与 `backend/config.yaml.example` 各调一次。
- **实际**：`model_service.py` 中**无 `def _migrate_legacy_capabilities` 定义、无任何调用**（仅 :716 注释提到）；其依赖的 `_read_yaml`/`_write_yaml` 也不存在；`_merge_capabilities_into_modalities`（:711）**只有定义、无调用（死代码）**。
- **后果**：agnes/ZenFree 老 `capabilities` 数据**无自动迁移兜底**（当前 config 无残留是手工/其他方式迁移的结果，非代码保证）；D4 决策（老数据一次性迁移）代码侧未落地；验收要点 5/6 依赖手工迁移而非代码保证。
- **违反原则**：DRY/SRP（迁移逻辑应单点化）、设计未实现。

### 违规 2：B4 违反 — `_KEY_ALIASES` 保留 `capabilities` + 双读兜底（model_service.py）
- **设计要求**（B4/§6.1）：`_KEY_ALIASES` 移除 `capabilities`（如有全链路引用），能力只走 `input_modalities` + `output_modalities` 双字段；验收要点 6：全链路无 `capabilities` 双读兜底。
- **实际**：`_KEY_ALIASES` 仍含 `"capabilities": ["capabilities"]`（:772）；`_parse_remote_models_body` 仍读 `merged.get("capabilities")`（:948）传给 `_merge_capabilities`（:699）。
- **后果**：全链路仍有 `capabilities` 双读（虽用于 `capabilities.reasoning` 推理布尔提取，非模态，但违反 B4 字面"移除 capabilities"与验收要点 6）。
- **说明**：`_merge_capabilities` 的 reasoning 提取是独立推理维度，设计文档未明确要删；但 `_KEY_ALIASES` 保留 capabilities 键名违反 B4 字面要求。

### 违规 3：测试与实现脱节（前端 tests 引用已删字段）
- **设计要求**（F2）：state `capabilities`→`inputModalities` 全 4 通道，`setCapabilities` 删除。
- **实际**：`frontend/src/tests/unit/settings2-capabilities-tdd.test.tsx` 大量引用已删除的 `state.model.capabilities`/`capabilitiesBaseline`（:210-214 等）与 `setCapabilities`（:264/275/288/298/319/357/373）；`settings2-edsave-red.test.tsx` 也用 `capabilities: []`（:91/109）。而 useSettings 已删除 `setCapabilities`（仅注释 :1592）、types.ts ModelState 已改 `inputModalities`/`outputModalities`（:65-68）。
- **后果**：测试引用不存在的字段/函数 → TS 编译失败 / 运行时失败（假红）；测试与实现脱节。
- **违反原则**：项目铁规"严禁以测试代码作为锁死错误系统逻辑的修改借口"（测试应真实反映新字段，而非停留在旧字段）。

### 违规 4：F3 输出模态行缺未知值灰色只读 Tag（SettingsPage.tsx）
- **设计要求**（§3.10.1 :495/:511）：输出模态行"未知值灰色只读 Tag 同'模型能力'行"。
- **实际**：输出模态行（:643-658）只有 `<Checkbox.Group>`，**无 `KNOWN_CAPABILITY_VALUES` 过滤 + 未知值灰色 Tag**；而输入模态行（:620-635）有该处理。
- **后果**：`output_modalities` 含未知值（如 `text`/`audio`）时，用户看不到该值（输入行能看到，输出行看不到），两行行为不一致。

### 违规 5：B21 两文件不同构 — example 的 sensenova 无 model_meta（config.yaml.example）
- **设计要求**（§3.4.3）："把 §3.4.1/§3.4.2 对 agnes/sensenova 的双维度能力标注**同样写入 example**，让模板与真实 config 同构"。
- **实际**：`backend/config.yaml.example` 的 **agnes 块已有 model_meta 双维度标注**（agnes-image-2.5-flash 等 ✓），但 **sensenova 块无 model_meta**（只有 `models: [deepseek-v4-flash, glm-5.2, sensenova-6.8-flash-lite, kimi-k3]`）。
- **后果**：新用户从模板起步的 sensenova 无能力标注，与真实 config 口径分叉；违反验收要点 12（两文件同构同步）。

## 二、存疑（1 个，需实测确认）

## 五、逐条复核结论（真伪核实 + 处理结果）2026-11-08 小欧

**复核人**: 小欧　**复核时间**: 2026-11-08　**复核方式**: 逐条比对落盘代码 + 真实配置 + 远端 `/models` 实测 + 本地跑类型检查

### 5.1 违规 1（B3 迁移钩子未落地）— 真，已修

- **核实**：属实。复核时 `model_service.py` 确无 `_migrate_legacy_capabilities` 定义与调用，`_merge_capabilities_into_modalities` 为死代码。
- **修复**：新增 `_migrate_legacy_capabilities(config_path) -> bool`（复用 `config_helpers.read_yaml_config`/`write_yaml_config`，把 `model_meta.*.capabilities` 并入 `input_modalities`、显式建 `output_modalities`、删旧键）与 startup 入口 `migrate_legacy_capabilities()`；`main.py` 的 `startup_event` 在 `install_access_noise_filter()` 后调用，`replace_provider_models` 落盘前调用。
- **幂等性验证**：临时 YAML 首跑返回 True 并完成迁移，次跑返回 False 且文件字节不变。
- **偏离说明**：设计写"startup 对 config.yaml 与 config.yaml.example 各调一次"；实际只迁真实配置，`backend/config.yaml.example` 作为受版本管理的模板按 §3.4.3 静态维护（运行期改写跟踪文件不合适）。
- **`fetch_remote_models` 未加调用**：该路径只读不落盘，无迁移语义。

### 5.2 违规 2（`_KEY_ALIASES` 保留 capabilities）— 部分属实，已按实质修

- **核实**：属实的只有 `_KEY_ALIASES` 中 `"capabilities": ["capabilities"]` 这一行——它是纯 identity 别名（映射到自身），删掉不影响解析（`_merge_capabilities` 仍直读原始键）。已删除该行。
- **不属实/不删的部分**：`_merge_capabilities()` 保留。它读的是 zenmux 的 `capabilities.reasoning` 布尔（推理特征维度，写入 `supported_features`），不是模态双读，删除会丢推理标注。B4/§6.1 的"移除 capabilities"针对模态，不覆盖该特征维度。

### 5.3 违规 3（测试引用已删字段）— 伪，报告有误

- **核实**：本仓库不存在 `frontend/src/tests/unit/settings2-capabilities-tdd.test.tsx` 与 `settings2-edsave-red.test.tsx`，`git log --all` 历史中也从未出现。既不编译失败也不运行失败，无「测试与实现脱节」。
- **结论**：报告此条为**误报**（可能把设计期的示例测试文件当成了已落盘文件），不做任何代码改动。

### 5.4 违规 4（F3 输出行缺未知值灰标）— 真，已修，并另有真实数据丢失缺陷

- **核实**：属实。输出模态行只有 `Checkbox.Group`，反序列化出的 `text`/`audio` 等非可选项用户完全看不见。
- **修复**：`modelUtils.ts` 新增单源 `KNOWN_OUTPUT_MODALITY_VALUES`（由 `OUTPUT_MODALITY_OPTIONS` 派生）；`SettingsPage.tsx` 输出行补灰色只读 `Tag`，与输入行同款。
- **附带发现（更严重）**：`useSettings.ts` 的 `setOutputModalities` 原为 `[...new Set(uiValues)]`，antd 的 `onChange` 只回传可选项，因此勾选「图片生成」会把已有 `text` 直接丢弃——落后端即数据丢失。已改为 `[...new Set([...uiValues, ...unknown])]`，与 `setInputModalities` 同法保留非可选项值。

### 5.5 违规 5（example 的 sensenova 无 model_meta）— 真，已修

- **核实**：属实。example 的 sensenova 块只有 4 个模型、无任何 `model_meta`，与真实 config 口径分叉。
- **修复**：`backend/config.yaml.example` 的 sensenova 块补全为 7 个模型 + 双维度 `model_meta`；各模型 input/output 按 5.6 的实测结论标注。

### 5.6 存疑（deepseek-flash / kimi-k3 是否多模态）— 已定：设计文档有误，config 正确

- **实测 1（远端声明）**：`GET https://token.sensenova.cn/v1/models` 逐模型下发 `input_modalities`——`deepseek-flash`、`deepseek-v4-flash`、`glm-5.2`、`glm-5.3`、`kimi-k3` 均为 `[text]`；`sensenova-6.8-flash`、`sensenova-6.8-flash-lite` 为 `[text, image]`。
- **实测 2（真实请求）**：向 `sensenova-6.8-flash-lite` 投 `image_url` parts 返回 HTTP 200；其余模型命中 `429 token plan entitlement exhausted`（配额耗尽），无法取得否定证据。厂商 `/models` 自述的模态声明已足以定性。
- **结论**：`config/config.yaml` 的 `deepseek-flash`/`kimi-k3` = `[text]` **正确**；设计文档 §3.4.2 把它们列为"多模态理解"是**事实错误**，已在设计文档就地加勘误说明（追加，不删原文）。config 侧无需改动。
