## 三、6层分层架构设计

```
┌───────────────────────────────────────────────────────┐
│ Layer 6: SSE Heartbeat (心跳保活)                      │
│   stream_reader 每 30s 发送 :keepalive\n\n            │
├───────────────────────────────────────────────────────┤
│ Layer 5: Per-session Concurrency (并发控制)            │
│   asyncio.Semaphore(3) per session                    │
├───────────────────────────────────────────────────────┤
│ Layer 4: Per-request BaseAIService (状态隔离)          │
│   每次请求新建，_cancelled/_stop_check/_current_response 独立│
├───────────────────────────────────────────────────────┤
│ Layer 3: Per-request LLMClient (薄包装)               │
│   每次请求新建，引用共享 httpx.AsyncClient              │
├───────────────────────────────────────────────────────┤
│ Layer 2: Shared httpx.AsyncClient (连接池共享)         │
│   模块级单例，10 连接池，所有请求共用                    │
├───────────────────────────────────────────────────────┤
│ Layer 1: SQLite WAL (已有)                             │
│   busy_timeout=30s, WAL mode, 无需改动                 │
└───────────────────────────────────────────────────────┘
```

## 四、逐决策点三思三省

### 决策1：Per-request BaseAIService（Layer 4 隔离层）

| 维度 | 思 | 省 |
|------|-----|-----|
| **正确性** | 每个请求独立 `_cancelled`/`_stop_check`/`_current_response`，消除竞态 | ✅ 通过 |
| **性能** | BaseAIService 是轻量包装器（无重资源），创建开销 ~1μs | ✅ 通过 |
| **内存** | httpx.AsyncClient 共享，不爆炸 | ✅ 通过 |
| **遗漏检查** | `_llm_sdk` 是懒初始化的，一旦创建就不变，可安全共享 | ✅ 无遗漏 |
| **异常安全** | 创建 BaseAIService 失败时，shared_client 由模块级管理，不泄漏 | ✅ 通过 |
| **关闭时机** | 请求结束时不需要 close shared_client（进程生命周期管理） | ✅ 通过 |
| **约束** | 单 provider 架构下安全；多 provider 时需 per-request header | ⚠️ 需标注约束 |

**结论**: ✅ 设计正确，符合 SRP + KISS 原则

### 决策2：Shared httpx.AsyncClient（Layer 2 连接池层）

| 维度 | 思 | 省 |
|------|-----|-----|
| **线程安全** | httpx 文档明确说 AsyncClient 是 asyncio 安全的 | ✅ 通过 |
| **连接池复用** | 避免 per-request 连接池爆炸（10 连接 vs N×10 连接） | ✅ 通过 |

## 四-补：新增决策点三思三省（2026-07-17 22:15:00 补充）

### 决策7：为 `file_state._state` 加锁（修复 X1）

| 维度 | 思 | 省 |
|------|-----|-----|
| **正确性** | 该全局 dict 被 `asyncio.to_thread` 派发的同步函数并行访问，无锁必有竞态 | ✅ 必须加锁 |
| **锁类型** | 访问方是线程池中的同步函数（`asyncio.to_thread`），非协程 → 必须用 `threading.Lock` | ✅ 用 threading.Lock（非 asyncio.Lock） |
| **隔离粒度** | 当前跨 task 共享，应至少按 task 或按文件隔离；最简方案是全局 `threading.Lock` 保护所有读写 | ✅ 全局锁可接受（临界区极短） |
| **异常安全** | 锁内只做 dict 读写，无 I/O，不会死锁 | ✅ 通过 |
| **性能** | 文件工具并发度低，全局锁开销可忽略 | ✅ 通过 |

**结论**: ✅ 设计正确，用 `threading.Lock` 包裹 `_state` 全部读写

### 决策8：跨任务文件冲突检测（修复 X2）

| 维度 | 思 | 省 |
|------|-----|------|
| **必要性** | 两个任务并发写同一文件，磁盘目标无互斥，数据丢失风险真实 | ✅ 必须设计 |
| **方案选择** | A: 全局文件锁（fcntl/msvcrt）B: 跨 task 冲突检测（借鉴 `_has_conflict` 扩展到跨 task）C: 按文件粒度 `asyncio.Lock`/`threading.Lock` 字典 | ⚠️ 见下 |
| **A 方案** | 操作系统级文件锁，最彻底，但 Windows 下 `msvcrt.locking` 仅支持阻塞锁，且与 `asyncio.to_thread` 模型配合复杂 | ⚠️ 复杂度高 |
| **B 方案（推荐）** | 在 `file_state` 或 operation 层维护"正在写入的文件集"，新任务写文件前检查是否有其他 task 正在写同一文件 → 若有则排队或告警 | ✅ KISS，复用现有 `_state` 结构 |
| **C 方案** | 每个被写文件一个锁对象，并发写同文件串行化 | ✅ 精确但需管理锁生命周期 |
| **当前决策** | **Phase 2 采用 B 方案（跨 task 冲突检测 + 告警/排队），标注为已知约束，不阻塞核心隔离实施** | ⚠️ 标注约束 |

**结论**: ⚠️ 设计采用"跨 task 冲突检测"轻量方案，完整文件锁留作后续增强

## 六、5遍交叉验证

### 第1遍：数据流完整性

```
用户请求 → create_request_service() → per-request BaseAIService
  → UniversalAgent(llm_client=per-request-service)
  → register_task(task_id, ai_service, session_id)
  → semaphore check → asyncio.create_task(run_agent_in_background(...))
  → agent.run_react_cycle() → call_llm_stream() → per-request request_stream()
  → shared httpx.AsyncClient.stream() → LLM API
```

**验证**: 每个请求的 `BaseAIService` 独立，`_cancelled`/`_stop_check`/`_current_response` 不共享 ✅

### 第2遍：取消/暂停/恢复安全性

```
cancel_task(task_id):
  → set_cancelled(task_id) → running_tasks[task_id]["cancelled"] = True
  → ai_service.cancel() → per-request 的 _cancelled = True（不影响其他请求）
  → _stop_check() → check_cancelled(task_id) → 读 running_tasks（不影响其他请求）

pause_task(task_id):
  → set_paused(task_id) → running_tasks[task_id]["paused"] = True
  → pause_event.clear() → task_pause_check() 阻塞（不影响其他请求）

resume_task(task_id):
  → set_resumed(task_id) → pause_event.set() → task_pause_check() 恢复
```

**验证**: 每个操作只影响指定 task_id，不影响其他请求 ✅

### 第3遍：SSE 重连兼容性

```
初始连接: POST /chat/stream → create_stream_buffer(task_id) → register_task(task_id, ...)
断线: CancelledError → agent 后台继续 → buffer.done.set()
重连: GET /chat/stream/{task_id}?after_seq=N → get_stream_buffer(task_id)
  → stream_reader(buffer, task_id, after_seq=N) → 重放事件
心跳: stream_reader 超时 → yield ": keepalive\n\n" → 前端忽略
```

**验证**: 心跳不进入 event_log，不影响 after_seq 重连 ✅

### 第4遍：DB 并发安全性

```
Task A: db.get_conn("chat") → allocate_and_insert_message() → append_execution_step() → conn.close()
Task B: db.get_conn("chat") → allocate_and_insert_message() → append_execution_step() → conn.close()
```

**验证**: SQLite WAL 模式允许并发读，单写串行化，busy_timeout=30s 足够 ✅

### 第5遍：资源泄漏检查

```
httpx.AsyncClient: 模块级管理，进程退出时 close
BaseAIService: per-request 创建，请求结束时无引用→GC 回收
LLMClient: per-request 创建，请求结束时无引用→GC 回收
_stream_buffer: call_later(300) 延迟回收
running_tasks: task_cleanup() 正常清理，cancelled 1h 后清理
_session_semaphores: session 删除时清理
```

**验证**: 无资源泄漏 ✅
