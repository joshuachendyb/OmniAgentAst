## 一、问题背景与现状

### 1.1 问题触发

2026-07-17 E2E 测试中，3 个 task 并发跑（task005/006/007，对应 unit-08/09/10）时，触发如下故障链：

```
三任务并发(17:50-18:03)
  → LLM provider(sensenova)带宽争抢
    → base_service.py:200 流调用总时长超时(500s) ×1次(18:00:53)
      → base_service.py:251 参数JSON解析失败 ×1次(18:00:53)
        → base_service.py:254 参数截断修复(残缺tool_call写回) ×1次(18:00:53)
          → client_sdk.py:196 HTTP 400 ×3次(18:00:53-55)
            → llm_stream.py:257 [Retry][L2] ×2次
              → llm_stream.py:262 [FC降级] ×1次
                → status_table.py:114 AgentStatus.FAILED ×1次(18:00:56)
```

**证据对比**：unit-07（串行，17:39-17:47）45 次 LLM call **零超时**；并发窗口 3 个 task 共 37 次 LLM call 中触发 **1 次超时**且链式崩溃。

### 1.2 当前系统并发现状

基于全代码逐行调研，当前并发架构如下：

#### 已有的隔离机制

| 层面 | 隔离状态 | 代码位置 | 说明 |
|------|---------|---------|------|
| Agent 实例 | ✅ 每 task 独立 | `openai.py:235` 每请求 new `UniversalAgent` | agent._tools_dict 独立 |
| 工具执行引擎 | ✅ 每 Agent 独立 | `base_agent.py:69` `ToolRetryEngine` 绑定到 Agent | 无 session 间共享 |

| 缺失点 | 后果 | 关键证据 |
|-------|------|---------|
| **LLM 请求排队** | 并发 session 直接争 provider 带宽→500s 超时 | `base_service.py:180` 无任何排队，直接发 HTTP 请求 |

| **日志隔离** | 单文件 app_{date}.log 全部 session 混写 | 排查时必须靠时间窗猜测 session 归属 |

| 风险点 | 问题 | 代码位置 |

## 二、设计总览

### 2.1 设计原则

以 AGENTS.md 10 大原则为纲，多 session 并发场景特化：

| 原则 | 在本设计中的体现 |
|------|----------------|
| **KISS-DIRECT** | Semaphore 隐式队列，不用 PriorityQueue + 消费者协程 |
| **SRP** | 调度器只管并发控制，配额器只管配额检查，日志格式化只管注入 |
| **YAGNI** | 不加优先级队列、不加独立调度服务、不加 Redis |
| **SLAP** | 每层在所属文件的同抽象层级做改动（scheduler→base_service、quota→react_cycle）|
| **禁止backward** | 每层改动是非侵入的：默认行为不变，配置驱动开启 |
| **复用优先** | 复用已有的 `_current_task_id`/`session_id_var` ContextVar |

### 2.3 通俗解释：`max_concurrent=2` 到底是什么？

```
误区：有人以为 max_concurrent=2 是"系统只能同时开 2 个用户对话"。
     ❌ 完全不是。

真相：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  用户层：可以同时开很多个 session（上限 5 个，Layer 0 控制）
  车道层：同时跑 LLM 的车道只有 2 条（Layer 1 控制）

  更具体的比喻：
    好比一个快餐店有 5 张桌子（5 个 session）。
    但厨房最多同时做 2 份菜（2 个 LLM 请求）。
    第 3 份菜单要等前面的菜出厨房后再开始做。

  但"做菜（调 LLM）"和"吃饭（跑工具）"是交替的：
  ┌─────────────────────────────────────────────┐
  │ Session A: 调LLM(占1车道) → 跑工具(释放)      │
  │ Session B: 调LLM(占1车道) → 跑工具(释放)      │
  │ Session C:   等待             → 调LLM(占1车道)│
  │                                              │
  │ 这样就实现了"看起来几乎同时响应"——            │
  │ 不是排大队，是交错执行。                       │
  └─────────────────────────────────────────────┘

  所以：max_concurrent=2 是对 LLM provider 的保护，
  不是对用户的限制。
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 三、Layer 0: API 入口限流

### 3.1 设计

FastAPI 中间件，在请求进入路由前计数活跃 session 数。

```
请求到达 → 全局计数器 +1
  → active >= MAX_ACTIVE_SESSIONS ? → HTTP 429 ("系统繁忙，请稍后重试")
  → 正常处理
  → 响应完成 → 全局计数器 -1
```

### 3.2 集成点

```python
# main.py — 在 CORSMiddleware 之后
@app.middleware("http")
async def session_rate_limit(request: Request, call_next):
    if request.url.path.startswith("/api/v1/chat/stream"):
        active = _active_sessions_count
        if active >= config.max_active_sessions:
            return JSONResponse(status_code=429, content={"error": "系统繁忙，请稍后重试"})
        _active_sessions_count += 1
        try:
            return await call_next(request)
        finally:
            _active_sessions_count -= 1
    return await call_next(request)
```

### 3.3 关键参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `max_active_sessions` | 5 | 最大并发 session 数（含排队等待 LLM slot 的） |

## 四、Layer 1: LLM 请求调度层（核心）

### 4.1 设计决策：三思三省

#### 思1：为什么不是 PriorityQueue + 消费者协程？

```
情景分析:
  Session A → request_stream() → 入PriorityQueue → (消费者出队) → HTTP流 → per-request Queue → 读回chunk
  Session B → request_stream() → 入PriorityQueue → (等待消费者出队)
  
问题:
  1. async generator(流式) + 消费者协程有阻抗不匹配:
     - generator yield chunk 需要直接把数据返回给调用者
     - 消费者协程出队后，流式数据必须通过 per-request Queue 回传
     - 于是需要两层队列(全局PriorityQueue + per-request Queue)
  2. 消费者协程有生命周期管理(启动/停止/异常处理)
  3. 复杂度高但收益有限(当前不需要优先级)
```

#### 思2：为什么 Semaphore 足够？

```
Semaphore方案:
  Session A → request_stream() → acquire(sem) → (等slot) → HTTP流 → yield chunk → release(sem)
  Session B → request_stream() → acquire(sem) → (等A的LLM完成时自动唤醒)
  
优势:
  1. asyncio.Semaphore 内部维护 waiter 队列 → 天然 FIFO
  2. acquire() 阻塞等待 → 等于"请求排队"
  3. release() 唤醒下一个 waiter → 等于"出队"
  4. 与 async generator 天然融合(一个acquire/release包裹)
  5. 不需要额外协程
  6. 总代码约 80 行(新文件) + 8 行(集成)
```

#### 思3：排队超时后怎么办？

```
场景: 所有 seat 被占用、排队超过 queue_timeout(120s)
处理: acquire(timeout=120) 抛 asyncio.TimeoutError
  → 返回 error chunk → L2重试发现type:"error" → 转FCFormatError → 重试(再次排队)
  → 重试再次超时 → FC降级(Text模式,不走LLM) → 任务正常完成(无LLM能力但不会崩)

这是正确的降级路径: 
  - 用户看到: "系统繁忙" → 稍后重试
  - 系统不会崩溃(FC降级兜底)
  - 不会死循环(FC重试次数有限)
```

### 4.2 最终方案选型：Semaphore 隐式队列

```python
# backend/app/services/llm/scheduler.py
class LLMRequestScheduler:
    """LLM请求调度器 — per-provider 并发控制
    
    每个 scheduler 绑定一个 provider。
    通过 asyncio.Semaphore 控制并发请求数，超出则排队等待。
    排队超时(queue_timeout)后返回错误，不阻塞客户端。
    """
    
    _instances: Dict[str, 'LLMRequestScheduler'] = {}
    _lock = threading.Lock()
    
    def __init__(self, max_concurrent: int):
        self._sem = asyncio.Semaphore(max_concurrent)
        self._active = 0
        self._total_accepted = 0
        self._total_rejected = 0
        self._total_completed = 0
    
    async def acquire(self, queue_timeout: float) -> bool:
        """等待LLM slot。queue_timeout内获取不到返回False"""
        self._total_accepted += 1
        try:
            await asyncio.wait_for(self._sem.acquire(), timeout=queue_timeout)
            self._active += 1
            return True
        except asyncio.TimeoutError:
            self._total_rejected += 1
            return False
    
    def release(self):
        self._sem.release()
        self._active -= 1
        self._total_completed += 1
    
    @property
    def stats(self) -> dict:
        return {
            "max_concurrent": self._max,
            "active": self._active,
            "total_accepted": self._total_accepted,
            "total_rejected": self._total_rejected,
            "total_completed": self._total_completed,
        }
    
    @classmethod
    def get(cls, provider: str, max_concurrent: int = 2) -> 'LLMRequestScheduler':
        """per-provider 单例工厂"""
        with cls._lock:
            if provider not in cls._instances:
                cls._instances[provider] = cls(max_concurrent)
            return cls._instances[provider]
```

### 4.3 与 BaseAIService 的集成点

```python
# backend/app/services/llm/base_service.py
# request_stream() — 在 while retry 循环前插入

from app.services.llm.scheduler import LLMRequestScheduler

async def request_stream(self, messages, tools=None, tool_choice="auto"):
    # ── LLM 请求调度器：排队等待 slot ──
    scheduler = LLMRequestScheduler.get(self.provider, max_concurrent=2)
    if not await scheduler.acquire(queue_timeout=120):
        yield StreamChunk(
            type="error",
            content="系统繁忙（LLM请求排队超时），请稍后重试",
        )
        return
    
    try:
        # 原有 retry 循环不变
        while retry_count <= max_retries:
            ...
    finally:
        scheduler.release()
```

**关键点**：
- acquire 在 retry 循环**外面**——整个 LLM 调用（含 L1 重试）只占 **1 个 slot**
- 重试期间不释放 slot——避免"重试→重新排队→slot 被占用→其他人等更久"
- finally 确保即使 L1 重试全部失败也释放 slot

### 4.4 为什么 max_concurrent=2（三思三省 + 通俗解释）

#### 先看一个真实时间线（理解"交错"的含义）

```
假设 3 个 session 基本同时启动（没有 max_concurrent=2 的后果）：

00:00  Session A → LLM 调用开始（5 秒后返回）
00:01  Session B → LLM 调用开始（和 A 同时进行）
00:02  Session C → LLM 调用开始（3 个同时打 LLM provider）
00:05  A 返回 → 开始跑工具
00:05  B 返回 → 开始跑工具（和 A 同时跑工具，没问题）
00:10  C 返回 → 开始跑工具
       ──────── 这次一切正常，因为 LLM quick response ────────

但如果是慢 LLM（如写长文档、分析大文件）：

00:00  Session A → LLM 调用开始（预计耗时 30 秒）
00:01  Session B → LLM 调用开始（预计耗时 25 秒）
00:02  Session C → LLM 调用开始（预计耗时 35 秒）
       ── 3 个同时跑 LLM，provider 带宽争抢 ──
00:30  A 没返回（带宽不足，耗时拉长到 45 秒）
00:35  B 没返回（耗时拉长到 50 秒）
00:40  C 也没返回（耗时拉长到 60 秒）
       ── 严重超时风险 → 这就是实际触发 500s 超时的场景 ──
```

#### 加了 max_concurrent=2 后，同一场景

```
00:00  Session A → LLM 调用开始（占 slot 1）
00:01  Session B → LLM 调用开始（占 slot 2）
00:02  Session C → 想做 LLM → 发现 slot 全满 → 排队等待
                   （C 在排队，不是死等——底层 httpx 连接还在，不会超时）
00:05  Session A → LLM 返回 → 开始跑工具（释放 slot 1）
00:05  Session C → 拿到 slot 1 → LLM 调用开始 ← C 只等了 3 秒！
00:07  Session B → LLM 返回 → 开始跑工具（释放 slot 2）
       ──────── 注意：A 和 B 在同时间跑工具（不冲突） ────────
00:12  Session C → LLM 返回 → 开始跑工具

关键点：
  - LLM 调用：同一时间最多 2 个（保护 provider）
  - 工具执行：不限并发（跑工具的 session 释放 slot 给其他人用）
  - 这就是"交错执行"——不是串行，是"LLM 排队、工具并行"
  - 用户感受：C 在 A 返回后立即开始，几乎感觉不到延迟
```

#### 三思三省

| 思次 | 考虑 | 结论 |
|------|------|------|
| 思1 | 实测 3 并发触发 1 次 500s 超时，1 串行 0 超时 | 3 路径不安全。串行 45 次 LLM call 零超时 → 超时确因并发争带宽 |
| 思2 | 设为 2 后，第 3 个 session 要等前面的 LLM 结束 | 不是"完全串行"——跑工具时释放 slot。典型场景中第 3 个 session 等 3-10 秒就能开始 LLM |
| 思3 | 是否默认该值？ | 默认 2 保守安全；在 `config.yaml` 可配置，验证后可调大 |

**最终决定**：`max_concurrent_requests: 2`，可配置。

## 五、Layer 2: Session 资源配额层

### 5.1 配额项

| 配额项 | 默认值 | 作用 | 超限后果 |
|-------|--------|------|---------|
| `max_llm_calls` | 50 | 防止单 session 无限重试 LLM | → Failed(LLM调用超限) |
| `max_steps` | 200 | 防止 ReAct 循环无限步 | → Failed(步骤超限) |
| `max_wall_time` | 600s(10min) | 防止 session 执行太久 | → Failed(执行时间超限) |

### 5.2 实现

```python
# backend/app/services/task/session_quota.py

class QuotaExceededError(Exception):
    """配额超限异常"""
    pass

class SessionQuota:
    """单 session 资源配额管理"""
    
    _quotas: Dict[str, 'SessionQuota'] = {}
    _lock = threading.Lock()
    
    def __init__(self, session_id: str, config: dict):
        self.session_id = session_id
        self.max_llm_calls = config.get("max_llm_calls", 50)
        self.max_steps = config.get("max_steps", 200)
        self.max_wall_time = config.get("max_wall_time", 600)
        self.llm_call_count = 0
        self.step_count = 0
        self.start_time = time.monotonic()
    
    def check_step(self):
        if self.step_count >= self.max_steps:
            raise QuotaExceededError(f"ReAct步骤超限({self.max_steps})")
        self.step_count += 1
    
    def check_llm_call(self):
        if self.llm_call_count >= self.max_llm_calls:
            raise QuotaExceededError(f"LLM调用次数超限({self.max_llm_calls})")
        self.llm_call_count += 1
    
    def check_wall_time(self):
        elapsed = time.monotonic() - self.start_time
        if elapsed > self.max_wall_time:
            raise QuotaExceededError(f"会话执行时间超限({self.max_wall_time}s)")
    
    @classmethod
    def get_quota(cls, session_id: str) -> Optional['SessionQuota']:
        return cls._quotas.get(session_id)
    
    @classmethod
    def create_quota(cls, session_id: str, config: dict) -> 'SessionQuota':
        quota = cls(session_id, config)
        cls._quotas[session_id] = quota
        return quota
    
    @classmethod
    def release_quota(cls, session_id: str):
        cls._quotas.pop(session_id, None)
```

### 6.1 文件路径跨 session 锁

**问题**：`action_handler.py:161-193` 的 `_has_conflict` 只检测同一 Agent 单次 batch 内的文件冲突。两个 session 同时写同一文件时无保护。

**方案**：全局 asyncio.Lock 按路径互斥

```python
# backend/app/services/safety/file_safety/file_path_lock.py

class FilePathLock:
    """跨session文件路径互斥锁"""
    _locks: Dict[str, asyncio.Lock] = {}
    _lock = asyncio.Lock()
    
    @classmethod
    async def lock(cls, path: str, timeout: float = 30) -> bool:
        normalized = os.path.abspath(os.path.normpath(path))
        async with cls._lock:
            if normalized not in cls._locks:
                cls._locks[normalized] = asyncio.Lock()
            target = cls._locks[normalized]
        try:
            await asyncio.wait_for(target.acquire(), timeout=timeout)
            return True
        except asyncio.TimeoutError:
            return False
    
    @classmethod
    def unlock(cls, path: str):
        normalized = os.path.abspath(os.path.normpath(path))
        if normalized in cls._locks:
            cls._locks[normalized].release()
```

**集成点**：在每个文件操作工具（`write_text_file`, `edit_text_file`, `delete`, `move`, `copy`）的 main 函数入口。

### 8.2 流程 F5（文件工具）：`file_state.py` 安全分析

**全局状态**：`_state: Dict[str, Tuple[int, str]]` — 路径→(mtime, hash)

**代码位置**：`file_state.py:15`

**分析结论**：**不需要锁**。理由：

```
风险情景：Session A 和 Session B 同时操作同一文件

Session A: read_file("X") → record_read → _state["X"] = (mtime_A, hash_A)
Session B: read_file("X") → record_read → _state["X"] = (mtime_B, hash_B)
                                  → B 覆盖 A 的条目（但两者 mtime 相同，因为文件未被修改）
                                  
Session A: check_conflict("X") → 读 _state["X"] = (mtime_B, hash_B)
                                  → mtime_B == 文件当前 mtime → 无冲突 ✅（因为文件没变）

Session B: write_file("X") → record_write → _state["X"] = (mtime_C, hash_B)
Session A: check_conflict("X") → mtime_C ≠ mtime_B → 检测到冲突 ✅（因为B确实改了X）
```

根本原因：`_state` 记录的 mtime 是**文件系统时间戳**，不是 session 内部计数器。无论哪个 session 最后一次写入 `_state` 条目，只要文件系统的 mtime 不变，冲突检测就正确。它天然是跨 session 安全的。

**TOCTOU 问题**：`check_conflict` → `write_file` 之间存在窗口，但这是**文件系统固有的竞态**（任何基于 mtime 的冲突检测都有），与 session 是否并发无关，本设计不特殊处理。

**结论**：✅ 不需要改 `file_state.py`。

#### G2：工具描述注入隔离
- **设计**：✅ 维持现状（`_tool_cache` per-agent 副本）。补充约束：全局 `tool_registry` 的 description **不得被运行时修改**，override 只发生在 per-agent cache 副本。

#### G5/G6：admin 路径（config 热加载 / 模型热切换）范围声明
- **设计**：⚠️ **超出本设计范围**。理由：这是管理端操作（触发于 `/api/v1/.../reload` 或模型切换接口），不是用户 chat 并发路径。本设计聚焦"多用户同时对话"的并发安全。

- **10 原则**：YAGNI（不为管理端热路径加 chat 层锁）、SRP（admin 锁在 admin 层做）。

#### G9：定时器回调不阻塞事件循环

- **10 原则**：KISS-DIRECT（小改）、SRP（回调执行不阻塞共享循环）。

#### G10：HITL 字典防御性加锁（可选）
- **设计**：当前单循环下安全。建议未来在 `hitl_confirmation.py` 用 `asyncio.Lock` 保护 `_pending_confirmations` 的读写，以防线程化改造。本设计不强制（YAGNI），列为后续改进。

#### G11：status_table 锁类型修正（可选）

## 十、三思三省记录（强化版）

每个决策经过 3 次自我质疑，确认为最佳方案才定稿。

### 10.1 决策1: 并发控制抽象 — Semaphore vs PriorityQueue

| 思次 | 视角 | 质疑 | 回答 |
|------|------|------|------|
| 思1 | FIFO 保证 | Semaphore 内部真的是 FIFO 吗？`asyncio.Semaphore` 使用 `asyncio.Condition`，`Condition.wait()` 将等待者入 `deque`，`notify()` 从左侧弹出——**确认为 FIFO**。不是偶然实现，是 CPython 标准行为。 |
| 思2 | L1 重试期间 | 整个 LLM 调用（含 L1 重试）一直占着 slot，是否不公平？ | **有意设计**。L1 重试是同一 LLM 调用的组成部分，不是新调用。如果中途释放 slot，重试时需重新排队——原始请求等更久、且其他 session 拿到 slot 后发现 provider 故障也失败。占用一个 slot 到 L1 重试全部结束，公平且正确。 |
| 思3 | 降级路径 | 排队超时后怎么办，是否直接放弃用户？ | 不走"放弃"。超时 → `yield error chunk` → L2 重试（`call_llm_with_fallback`）→ 再次排队 → 再次超时 → FC 降级到 Text 模式 → 正常完成。**排队超时不会导致任务崩溃**，完整降级链。 |
| 最终 | 综合| PriorityQueue 需全局消费者协程 + per-request Queue + 生命周期管理共 ~200 行。Semaphore ~80 行。**当前不需要优先级，选 Semaphore 正确。** |

### 10.2 决策2: max_concurrent_requests=2

| 思次 | 视角 | 质疑 | 回答 |
|------|------|------|------|
| 思1 | 样本量 | 只测了一次 3 并发触发超时，万一是网络抖动而非并发原因？ | unit-07 串行 45 次 LLM call 零超时；3 并发窗口 37 次 call 中唯一超时在 18:00:53。如果网络抖动，串行窗口也应出现——但未出现。**统计上排除巧合**。 |
| 思2 | 值太小 | 2 是否太保守？用户体验上 3 个 session 时第 3 个要排队。 | 注意"排队"只发生在**多个 session 同时要做 LLM call** 的时刻。Session A 跑工具（非 LLM）时释放 slot → Session B 可启动 LLM。这是**交错执行**，不是"第 3 个等前面全部完成"。实测多数 LLM call 在 5-30 秒，工具执行在 1-60 秒 —— 交错后等待时间可接受。 |
| 思3 | 是否应硬编码 | 这个值将来需要调怎么办？ | **不硬编码**。在 `config.yaml` 中 `llm.max_concurrent_requests` 可配置。建议默认 2，稳定验证后调到 3。 |
| 最终 |  | 默认 2 是安全边界（1 安全、3 不安全），可配置。**正确。** |

### 10.3 决策3: 日志方案 — 单文件+ContextVar

| 思次 | 视角 | 质疑 | 回答 |
|------|------|------|------|
| 思1 | 线程安全 | ContextVar 是 per-asyncio-task 的。但如果日志在**后台线程**（如 `asyncio.to_thread` 中的同步工具）被调用，session_id 还能读到吗？ | `asyncio.to_thread` 内部使用 `loop.run_in_executor`，Python 3.6+ **自动复制当前 context 到新线程**。所以工具线程内的 session_id_var.get() 返回原始值。但如果日志被**独立线程**（非 asyncio.to_thread，如 threading.Thread）调用，ContextVar 回退默认值 "-"。这是已知工程局限——但当前所有工具调用都走 asyncio.to_thread，不影响。默认值 "-" 保证不崩溃。 |
| 思2 | 分文件方案 | 按 session 分文件真的那么差吗？ | 分文件需要：① 每个 session 创建 FileHandler → 文件描述符管理开销。② session 结束时正确关闭 handler → 需在 session 生命周期钩子中做。③ logging 的 Handler 是线程安全的，但动态创建/销毁 Handler 是全局操作，可能相互干扰。④ 查跨 session 日志需合并多个文件。**单文件 + grep session_id 效率更高。** |
| 思3 | JSON 格式 | 是否应该改为 JSON 结构化日志以方便程序化分析？ | 暂时不需要（YAGNI）。当前文本格式人类可读。加入 session_id 后 `Select-String session_abc app.log` 即可过滤。将来需要 JSON 时可加第二个 Handler，不改现有格式。 |
| 最终 |  | **单文件 + ContextVar 注入是最优方案**。40 行代码解决问题，零侵入现有日志调用。 |

### 10.4 决策4: Layer 0 API 限流层级

### 10.5 决策5: 文件锁 — asyncio.Lock vs 文件系统锁

| 思次 | 视角 | 质疑 | 回答 |
|------|------|------|------|
| 思1 | 进程崩溃 | `asyncio.Lock` 不跨进程。如果持有锁的协程崩溃，锁是否永远不释放？ | 协程崩溃（未捕获异常）→ 所在的 `async with` 或 `try/finally` 中 unlock 被执行。即使整个进程崩溃 → 重启后 `_locks` 字典空，锁自动重置。**单进程下安全。** |
| 思2 | 跨进程 | 将来多 worker 怎么办？ | 当前是单进程架构。将来需要多进程时，改用文件系统锁（`portalocker` 或 `fasteners`）。届时更换实现，接口不变。YAGNI。 |
| 最终 |  | **当前单进程下 asyncio.Lock 是最轻量正确的选择。** |
