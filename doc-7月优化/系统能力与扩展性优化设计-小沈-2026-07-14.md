## 1 Token 成本可观测性

**思路**：usage_data 已从 LLM 响应流入 call_llm_stream 但未持久化。不走 MetricsCollector（内存收集器已死代码）。在 call_llm_stream 的唯一完成点直接 INSERT 到 operations.db 的 token_usage_stats 表。新增查询 API。

**核心接口**：
```python
# llm_stream.py
def _record_token_usage(task_id: str, model: str, provider: str,
                        usage: UsageData, llm_dur_ms: int):
    """INSERT INTO token_usage_stats; 失败仅 log warning 不阻断"""
    db = get_operations_db()
    db.execute("INSERT INTO token_usage_stats (...) VALUES (?,?,?,?,?,?,?,?)",
               (task_id, model, provider, usage.prompt_tokens,
                usage.completion_tokens, usage.total_tokens, llm_dur_ms, datetime.utcnow()))
```

**数据结构**（operations.db 新表）：

CREATE TABLE IF NOT EXISTS token_usage_stats (

## 2 多 Provider 路由 / fallback

### 概要设计

**思路**：不改 `get_service()` 已有路径。新增 `get_service_pool()` 返回 `ProviderPool` 实例。`ProviderPool` 只实现 `request_stream()` 和 `request()` 两个方法（不全量实现 BaseAIService 接口）。切备逻辑：try 主 provider → 异常时 try 备用 → 全部失败抛异常。取消通过 `asyncio.CancelledError` 透传。

**核心接口**：
```python
# provider_pool.py
@dataclass
class _Health:
    consecutive_fail: int = 0
    cooldown_until: float = 0.0

class ProviderPool:
    def __init__(self, candidates: List[BaseAIService]):
        self._candidates = candidates           # 主 + 备（按优先级）
        self._health: Dict[str, _Health] = {}   # provider_name → health

    async def request_stream(self, messages, tools=None, **kwargs):
        """try 每个 candidate，第一个成功返回；失败标记 cooldown 切下一个"""
        for svc in self._candidates:
            if self._is_on_cooldown(svc):
                continue
            try:
                async for chunk in svc.request_stream(messages, tools, **kwargs):
                    yield chunk
                # 成功 → 重置 health
                self._reset_health(svc)
                return
            except Exception as e:
                self._mark_failure(svc)
                last_exc = e
                continue
        raise last_exc  # 全部失败

    async def request(self, messages, **kwargs):
        """同上的非流式版本"""
```
**层次契约**（4 层独立、单向、不嵌套）：
```
熔断器 → 信号量(per-model) → ProviderPool → 单 provider 底座重试
```
熔断器先短路，信号量控并发，pool 层管跨 provider 切换，底座管同 provider 最后一搏。

**数据流**：
```
启动时: build_candidate_list() → 读 config.yaml ai.provider + fallback → 实例化 List[BaseAIService]
运行时: agent.llm_client → get_service_pool() → ProviderPool.request_stream()
  → 选主 provider 委托 → 成功返回
  → 异常(429/5xx/网络) → 标记 cooldown → 切下一候选
  → 全部失败 → 抛最后异常
```

### 改动文件

| 文件 | 改动 |
|------|------|
| `app/services/lifecycle/provider_pool.py` | **新建**：ProviderPool + _Health dataclass + 切备逻辑 |
| `app/services/lifecycle/service.py` | 新增 `get_service_pool()`（不改现有 `get_service()`）；新增 `build_candidate_list()` |
| `app/services/model/resolver.py` | 新增 `resolve_candidates()` 复用现有 _validate_* 方法 |

## 3 真实熔断器 + 全局限流

### 概要设计

**思路**：熔断器放 `base_service.py`，包裹现有 `while retry_count <= max_retries` 重试循环外圈。信号量改为 per-model（`_model_semaphores: Dict[str, asyncio.Semaphore]`），在 `_ensure_client()` 时创建。TokenBucket 同 per-model。`_is_rate_limit_status` 是死代码，不依赖它。

**核心接口**：
```python
# circuit_breaker.py
class CircuitBreaker:
    # states: CLOSED / OPEN / HALF_OPEN
    # failure_count, threshold=5, open_seconds=30
    # async def call(coro_factory) → 成功重置 / 失败+1 / OPEN 抛 CircuitOpenError

# rate_limiter.py
class TokenBucket:
    # rate: 每秒 tokens, burst: 最大积攒
    # consume(n) → bool; wait_for_token(n, timeout) → bool
```

**数据流**：
```
base_service.py request_stream():
  await breaker.call(lambda: _do_request_stream()):
    → CLOSED: 进入重试循环
      → while retry_count <= max_retries:
        async with model_semaphores[model]:
          → 尝试 HTTP 调用
          → 429(HTTPStatusError): classify_error 归为 retryable
            → TokenBucket.wait_for_token → retry_count++
          → 成功: 返回, breaker.reset()
      → 全部重试失败: breaker.record_failure()
    → OPEN: 不进入重试循环, 直接抛 CircuitOpenError
      → error_classifier 匹配 "circuit open" → is_retryable=False
```

### 改动文件

| 文件 | 改动 |
|------|------|
| `app/services/llm/circuit_breaker.py` | **新建**：CircuitBreaker + CircuitOpenError |
| `app/services/llm/rate_limiter.py` | **新建**：TokenBucket（per-model，从 config 读参数） |
| `app/services/llm/base_service.py` | `request_stream` 加熔断器外层 + per-model 信号量；删除 `_is_rate_limit_status` 死代码 |
| `app/constants.py` | 增 CIRCUIT_*, TOKEN_BUCKET_* 常量 |

### 关键修正（基于代码实测）

1. **熔断器放 `base_service.py` 而非 `client_sdk.py`**。`LLMClient` 职责是发 HTTP（基础设施），熔断器是业务决策。`base_service.py` 的 `request_stream`（line 154-277）已有重试循环（`while retry_count <= max_retries`），熔断在此循环外包裹——短路重试循环而非断路 HTTP 连接。
2. **信号量 per-model 非模块级**。`LLM_CONCURRENCY_SEMAPHORE = asyncio.Semaphore(5)` 在多个任务同时运行时形成误限。per-model 信号量在 `_ensure_client()` 时创建。
3. **`_is_rate_limit_status`（line 107-108）是死代码**。`client_sdk.py` 6 使用 `response.raise_for_status()`，httpx 在 4xx/5xx 时直接抛 `HTTPStatusError`，不会走到此方法。检测 429 的代码路径是 `except Exception → _should_retry → classify_error(name)`。
4. `SystemErrorClassifier.CIRCUIT_OPEN` 已定义（error_classifier.py line 36），熔断器实现后自动激活已有逻辑。

## 4 长上下文摘要压缩

**状态**：已搁置（P3）。当前 `MAX_CONTEXT_CHARS=200000`（config.yaml 500000），日常任务 <50 步撑不爆。以下设计保留供日后参考。

### 概要设计

**思路**：不在 `trim_history()`（每步调用）内做。改为在 `prepare_messages_for_llm` 内检测：若 `conversation_history` 字符 > `MAX_CONTEXT_CHARS * 0.75`，`asyncio.create_task` 异步触发摘要，结果缓存到 `_compaction_cache`。下次 `prepare_messages_for_llm` 时有缓存则替换被裁消息。

**核心接口**：
```python
# message_builder.py
def __init__(self, max_context_chars, llm_client=None):
    self._llm_client = llm_client
    self._compaction_cache: Optional[str] = None

async def _generate_summary_async(self, conversation_history) -> Optional[str]:
    """异步生成摘要，不阻塞当前步"""
    cutoff = MAX_CONTEXT_CHARS * 0.75
    if total_chars(conversation_history) <= cutoff:
        return None
    prompt = self._make_compaction_prompt(conversation_history)
    resp = await self._llm_client.request(...)
    self._compaction_cache = resp.content if resp.success else None
```

**数据流**：
```
prepare_messages_for_llm:
  → if total_chars > MAX_CONTEXT_CHARS * 0.75 AND not _compaction_cache:
      → create_task(_generate_summary_async(...))  # 异步, 不阻塞
  → if _compaction_cache:
      → 替换被裁旧消息为 {"role": "user", "content": "[压缩摘要]\n"+_compaction_cache}
      → 保持 system → [摘要user] → user → ... 序列合法（非 system 注入）
```

### 关键修正（基于代码实测）

1. **不在 `trim_history` 内做**。`trim_history()` 每步调用，加 LLM 调用会阻塞 key path。改为 `prepare_messages_for_llm` 内异步触发。
2. **摘要不注入为 system 消息**。违反 FC 协议（system 必须放最前）。改为替换被裁消息为 `{"role": "user", "content": ...}`。
3. **最低触发阈值 100K**。一次 LLM 调用成本 > 100K 字符处理成本。
4. **搁置原因**：当前无真实需求。等监控数据显示 context 使用率 > 70% 时再议。

## 5 长期记忆 / FTS5 检索

### 概要设计

**思路**：SQLite FTS5 做关键词检索，不加向量库。跨会话关键事实写入 `long_term_memory` 表 + `memory_fts` 虚表（手动同步）。`distill_and_store` 不放 `agent_runner.py` finally 块，改 `react_cycle.py` 的 `_on_after_loop()` hook 触发。FTS5 不支持时降级 LIKE 检索。

**数据结构**：
```sql
CREATE TABLE long_term_memory (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    scope TEXT NOT NULL DEFAULT 'general',
    content TEXT NOT NULL,
    keywords TEXT,              -- 逗号分隔，供 LIKE 兜底检索
    source_task_id TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    access_count INTEGER DEFAULT 0
);
-- FTS5 虚表（try-catch 包裹，不支持时跳过）
CREATE VIRTUAL TABLE memory_fts USING fts5(content, keywords, content=long_term_memory, content_rowid=id);
-- FTS5 同步触发器（确保 long_term_memory INSERT/UPDATE/DELETE 自动同步）
CREATE TRIGGER memory_fts_ai AFTER INSERT ON long_term_memory BEGIN
    INSERT INTO memory_fts(rowid, content, keywords) VALUES (new.id, new.content, new.keywords);
END;
CREATE TRIGGER memory_fts_ad AFTER DELETE ON long_term_memory BEGIN
    INSERT INTO memory_fts(memory_fts, rowid, content, keywords) VALUES('delete', old.id, old.content, old.keywords);
END;
CREATE TRIGGER memory_fts_au AFTER UPDATE ON long_term_memory BEGIN
    INSERT INTO memory_fts(memory_fts, rowid, content, keywords) VALUES('delete', old.id, old.content, old.keywords);
    INSERT INTO memory_fts(rowid, content, keywords) VALUES (new.id, new.content, new.keywords);
END;
```

**核心接口**（memory_store.py）：
```python
class MemoryStore:
    def add_memory(self, scope, content, keywords, source_task_id):
        """INSERT long_term_memory + FTS5 自动同步（trigger）
           先检查相似内容去重（FTS5 MATCH content 关键词，相似 > 80% 仅 update access_count）"""

    def retrieve(self, query, scope=None, top_k=5) -> List[Dict]:
        """1. FTS5 MATCH 检索; 2. 无结果/异常降级 LIKE '%kw%'; 3. 最多 top_k 条，总字符 ≤2000"""

    async def distill_and_store(self, llm_client, task, final_answer, scope, task_id):
        """任务结束时调一次 LLM 提取关键事实 → add_memory
           触发条件：步数 >= 5 且 最终回答 > 200 字符（避免短任务浪费 LLM 调用）"""
```

**数据流**：
```
initialize_run_state (每轮):
  → if config.memory_enabled:
      → memory_store.retrieve(task, top_k=3)
      → inject_history([{"role":"system","content":"[长期记忆]\n"+formatted}])  # 总字符≤2000

react_cycle._on_after_loop() (任务结束 hook):
  → if status==completed AND memory_enabled AND 步数>=5 AND 最终回答>200字:
      → create_task(distill_and_store(...))  # 异步不阻塞
```

### 改动文件

| 文件 | 改动 |
|------|------|
| `app/db/db_initializer.py` | `init_chat_db()` 加 long_term_memory + memory_fts 建表 + 同步触发器（DDL 全部 try-catch） |
| `app/services/agent/memory_store.py` | **新建**：MemoryStore（add_memory / retrieve / distill_and_store） |
| `app/services/agent/initialize_run_state.py` | 末尾加 `_inject_long_term_memory`（条件判断，在 `_inject_conversation_history` 之后） |
| `app/services/agent/react_cycle.py` | `_on_after_loop()` hook 触发 distill_and_store（不再放 agent_runner finally） |
| `app/config.py` | 增 `get_memory_enabled()` / `get_memory_top_k()`（默认关） |

### 关键修正（基于代码实测）

1. **`distill_and_store` 不放 `agent_runner.py` finally 块**。finally 块（line 189-246）已有 3 个退出路径 + DB 保存 + 生命周期清理 + buffer reclaim，再加重会增加失败风险。改为 `react_cycle.py` 的 `_on_after_loop()`（line 165-168）hook 触发。
2. **增加蒸馏触发门槛**：步数 >= 5 且最终回答 > 200 字符。短任务不做 LLM 调用提取事实。
3. **FTS5 建表加 try-catch**。`CREATE VIRTUAL TABLE ... USING fts5` 在未编译 FTS5 的 sqlite3 中抛 `OperationalError`。当前 `db_initializer.py` 无 try-catch，崩启动。不支持时降级 LIKE 检索。
4. **增加 FTS5 同步触发器**。`memory_fts` 是 `content=long_term_memory` 的外部内容 FTS5 表。`long_term_memory` 的 INSERT 不自动同步到 `memory_fts`——必须手动维护 trigger。设计遗漏此关键步骤。
5. **内存去重**：add_memory 前用 FTS5 MATCH 检查相似事实，content 相似度 > 80% 的不重复写入（仅更新 access_count）。
6. **`_inject_long_term_memory` 注入位置**：在 `_inject_conversation_history`（line 102）之后，因为它是 initialize_run_state 的最后一个操作。

## 6 任务持久化 / 断点续跑

### 概要设计

**思路**：每步 step 后异步 checkpoint（`create_task(save_checkpoint)`，不阻塞 producer）。任务进程崩溃后不自动恢复（标记 `suspended`），用户手动调用恢复 API。不在 `agent_runner.py` finally 加重，checkpoint 在 `_append` 后触发。

**数据结构**：
```sql
CREATE TABLE IF NOT EXISTS task_resume (
    task_id TEXT PRIMARY KEY,
    session_id TEXT NOT NULL,
    agent_id TEXT NOT NULL,
    snapshot_json TEXT NOT NULL,     -- _safe_json_dumps(conversation_history, default=str)
    step_index INTEGER DEFAULT 0,
    status TEXT DEFAULT 'running',  -- running / suspended / interrupted / consumed
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

**核心接口**（task_persistence.py）：
```python
class TaskPersistence:
    @staticmethod
    def _safe_json_dumps(obj, default=str) -> str:
        """json.dumps with default=str 兜底非序列化类型"""
    @staticmethod
    def save_checkpoint(task_id, session_id, agent_id, snapshot, step_index):
        """UPSERT: INSERT OR REPLACE; 失败仅 log warning"""
    @staticmethod
    def load_checkpoint(task_id) -> Optional[tuple]:
        """返回 (snapshot, step, status) 或 None"""
    @staticmethod
    def mark_suspended(task_id):    # 进程 crash → status='suspended'
    @staticmethod
    def mark_consumed(task_id):     # 正常完成 → status='consumed'
    @staticmethod
    def list_suspended():           # 启动时查询所有 status='suspended' 的任务
        """返回 List[Dict]，只记录不自动恢复"""
```

**数据流**：
```
每步 _append 后:
  → create_task(save_checkpoint(task_id, session_id, agent_id, _safe_json_dumps(conversation_history), step_index))
  → 异步 UPSERT，不 await，不阻塞

finally (正常退出):
  → DB 保存成功后 → mark_consumed()

进程崩溃 → 重启 → db.init() 后:
  → list_suspended() → 仅记录日志，不自动 spawn
  → 用户通过 UI 或 API 手动决定是否恢复
  → POST /api/v1/tasks/{task_id}/resume → initialize_run_state(resume_snapshot=snapshot)
```

### 改动文件

| 文件 | 改动 |
|------|------|
| `app/db/db_initializer.py` | `init_task_tracker_db()` 加 task_resume 表 |
| `app/services/task/task_persistence.py` | **新建**：TaskPersistence（_safe_json_dumps + save/load/mark/list） |
| `app/services/agent/agent_runner.py` | `_append` 后 `create_task(save_checkpoint)` + finally `mark_consumed`（DB 保存成功后） |
| `app/services/agent/initialize_run_state.py` | 增可选 `resume_snapshot` 参数 + 恢复分支（跳过 reset，直接反序列化 conversation_history） |
| `app/api/v1/task_router.py` | 增 `POST /api/v1/tasks/{task_id}/resume` 端点 |

### 关键修正（基于代码实测）

1. **每步 checkpoint + 异步写**。每 5 步太粗（98 步崩溃丢 20 步）。每步 `create_task(save_checkpoint)` 不 await，`default=str` 兜底非序列化类型。
2. **不自动恢复**。`recover_interrupted_tasks` 仅 list 不 spawn。用户手动决定是否续跑。
3. **`mark_consumed()` 在 DB 保存成功后执行**，而非 finally 入口处。
4. **分两期实施**：第一期只落地 checkpoint（不恢复），进程重启标记 `suspended`。第二期做真正 resume（跳过 6 个重置 + 重建 StreamBuffer）。

## 7 子 Agent / 多 Agent 协作

### 概要设计

**思路**：不做通用多 Agent 框架。只做"supervisor 委派子任务 → worker 并行执行 → 汇总"的窄模式。`WorkerAgent` 直接继承 `BaseAgent(ABC)`（不经过 `UniversalAgent`，跳过 TaskTracker/StepEmitter/ToolRetryEngine），直接调 `run_react_cycle`。Worker 事件静默消费不推 SSE。

**核心接口**（delegation.py）：
```python
class WorkerAgent(BaseAgent):  # 直接继承 ABC，不经过 UniversalAgent
    def __init__(self, llm_client, task_id, worker_prompt,
                 task_categories: Set[ToolCategory], max_steps: int = 5):
        self._worker_prompt = worker_prompt
        self._max_steps = max_steps
        # 不调 UniversalAgent.__init__，跳过 TaskTracker/StepEmitter/ToolRetryEngine
        super().__init__(llm_client, task_id, initial_categories=task_categories)

    def _get_system_prompt(self) -> str:
        return self._worker_prompt  # 替代 prompts.build_full_system_prompt()
```

**数据流**：
```

  → 创建 WorkerAgent（task_id = f"worker_{supervisor_id}_{idx}"）
  → if sequential: 顺序执行，前一个结果注入下一个 context
  → else: await asyncio.gather(*[agent.run_react_cycle(...) for agent in workers])
  → _silent_collector 包装逐条消费 worker event → 提取 final content
  → 结构化汇总 → 返 supervisor 合成
```

## 10 流式背压 / event_log 有界

### 概要设计

**思路**：`event_log` 从 `List[Dict]` 改 `deque(maxlen=5000)` 防 OOM。`_seq_counter` 独立于 deque 单调递增（解决 `len()` 换 deque 后 seq 不唯一问题）。保留 `cond.wait()` 消费者唤醒机制。满时 log warning 高水位。

**核心改动**：
```python
# task_state.py
from collections import deque
STREAM_BUFFER_MAX_EVENTS = 5000
STREAM_BUFFER_HIGH_WATERMARK = 4500

@dataclass
class StreamBuffer:
    event_log: deque = field(default_factory=lambda: deque(maxlen=STREAM_BUFFER_MAX_EVENTS))
    cond: asyncio.Condition = field(default_factory=asyncio.Condition)
    done: asyncio.Event = field(default_factory=asyncio.Event)
    _seq_counter: int = 0          # 独立于 deque 的单调计数器
    _min_seq_in_buffer: int = 0    # deque[0] 的事件 seq（用于消费者重连判断）

agent_runner.py _append:
    d["seq"] = buffer._seq_counter
    buffer._seq_counter += 1
    buffer.event_log.append(d)
    if len(buffer.event_log) == 1:   # 新 deque，min_seq 更新
        buffer._min_seq_in_buffer = d["seq"]
    if len(buffer.event_log) >= STREAM_BUFFER_HIGH_WATERMARK:
        logger.warning("StreamBuffer high watermark: %d events", len(buffer.event_log))
    async with buffer.cond:
        buffer.cond.notify_all()
```

**seq 实现**：`_seq_counter` 从 0 递增，与 deque 长度无关。deque 满时旧事件被挤出，`len(buffer.event_log)` 不变但 `_seq_counter` 继续递增。消费者通过 `event["seq"] > after_seq` 过滤不受 deque 影响。

### 改动文件

| 文件 | 改动 |
|------|------|
| `app/services/task/task_state.py` | `event_log: deque` + `_seq_counter` + `_min_seq_in_buffer`；保留 cond |
| `app/services/agent/agent_runner.py` | `_append` 用 `buffer._seq_counter` 生成 seq |
| `app/constants.py` | 增 `STREAM_BUFFER_MAX_EVENTS=5000` |

### 关键修正（基于代码实测）

1. **`seq = len(buffer.event_log)` 换 deque 后彻底崩掉**。当前 `agent_runner.py` line 75：`d["seq"] = len(buffer.event_log)`。deque(maxlen=5000) 的 `len()` 最大返回 5000，放入第 10001 个事件时仍返回 5000——seq 不唯一。消费者通过 `after_seq` 过滤时重复/漏事件。修复：独立 `_seq_counter` 累加，与 deque 长度解耦。
2. **保留 `cond.wait()`**。`stream_reader` line 106 `await buffer.cond.wait()` 是消费者等待新事件的唯一机制。去掉它消费者必须轮询浪费 CPU。消费者协程被取消时 `aclose` 自动释放锁，不会造成 producer 停摆。
3. **消费者重连的 seq 空洞处理**：重连时若 `after_seq < buffer._min_seq_in_buffer`，返回 `{"error": "truncation"}` 告知前端刷新。
4. **cond.wait() 加 timeout=60 兜底**：`await asyncio.wait_for(buffer.cond.wait(), timeout=60)`，防止极端情况消费者永久阻塞。

| **解决什么问题** | 63 个工具硬编码。新增工具必须改代码重注册。 |
| **别人有的（趋势）** | 是。OpenAI Plugins、LangChain Tools 都在做。插件是平台化基础。 |
| **别人没有的（创新）** | **不加 `ToolCategory.PLUGIN` 枚举**（不影响全局 system prompt 迭代）。插件工具注册到现有分类下。能力声明制安全策略。这是**差异创新**——别人做枚举隔离，我们做更简洁的注册到现有分类。 |
| **代码可行性** | 高。`@register_tool` 装饰器已存在。独立 `_loaded_plugins` set，不依赖 `_registered_categories`。去掉 `reload_plugin`（Python reload 不可靠）。 |
| **风险等级** | 低。默认空目录 = 不启用。 |
| **建议** | **搁置**。时机未到——等你真想写插件或有第三方需求时再做。 |

### 12.10 流式背压 / event_log 有界

| 维度 | 回答 |
|------|------|
| **解决什么问题** | `event_log` 无限增长 + `seq = len()` 在多消费者重连时重复推送（真实 bug）。 |
| **别人有的（趋势）** | 是。有界缓冲区是 IO 系统基本要求。 |
| **别人没有的（创新）** | **`_seq_counter` 独立于 deque 长度**——解决业界常见 "deque maxlen + len() 当 seq" 的 bug。保留 `cond.wait()`（加 timeout=60 兜底）防止消费者轮询浪费 CPU。 |
| **代码可行性** | 高。`deque(maxlen=5000)` 一行。`_seq_counter` 三行。 |
| **风险等级** | 中。seq 算法变化影响消费者 after_seq 行为。 |
| **建议** | **P0 干，核心修 seq bug**。deque 防 OOM 顺带做。 |

## 12.12 创新定位总结

| 项 | 技术路线 | 别人有的 | 我们创新的 |
|----|---------|---------|-----------|
| 1 Token 可观测 | 落 DB | SaaS 仪表盘 | 本地 DB + 多维度筛选 |
| 2 多 Provider | 简单切备 | 云原生健康检查 | 桌面场景轻量切备 |
| 3 熔断器 | per-model | 全局熔断 | per-model 信号量防误限 |
| 4 摘要压缩 | 异步 + 合法 FC | 同步截断 | create_task 异步 + user role 替换 |
| 5 长期记忆 | FTS5 手动标记 | 向量库 + 自动蒸馏 | **无依赖 FTS5 + 手动标记（差异化）** |
| 6 持久化 | 异步 checkpoint | Durable Execution | **桌面级轻量 checkpoint（实用创新）** |
| 7 子 Agent | BaseAgent 直接继承 | 通用多 Agent 框架 | **跳过 TaskTracker/StepEmitter 减重（定位创新）** |
| 8 插件 | 注册到现分类 | 枚举隔离 | 不加枚举，注册到已有分类 |
| 9 Trace | LoggerAdapter | OpenTelemetry 大方案 | 1 个文件改动的最轻量方案 |
| 10 背压 | _seq_counter | 有界缓冲区 | seq 独立计数器（解决 len 不唯一 bug）|
| 11 审计 | per-tool 注入 | 企业级审计平台 | 精准到每个工具、fail-open |
