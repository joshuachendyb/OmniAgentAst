## 一、架构总览

### 1.1 核心概念

Agent 状态管理分为两个互补维度：

- **状态层（agent.status）**：管元数据——"现在是什么阶段"，集中由 `status_table.py` 管理
- **数据层（yield chain）**：管数据本体——"具体内容是什么"，通过 async generator yield Step 对象统一流转

### 1.2 两维度协作关系

```
agent.status = THINKING    → 类型：正在思考
    yield ThoughtStep(...)  → 数据：具体思考内容

agent.status = EXECUTING   → 类型：正在执行
    yield ActionStep(...)   → 数据：具体调用哪个工具
    yield ObservationStep(...) → 数据：工具返回的结果

agent.status = FAILED      → 类型：失败了
    yield ErrorStep(...)    → 数据：具体错误信息

agent.status = SUSPENDED   → 类型：暂停（HITL 等待用户确认）
    yield MetaStep(authorization_required) → 数据：安全确认请求

agent.status = RETRYING    → 类型：可恢复失败，等待重试
    yield ErrorStep(recoverable=True) → 数据：错误信息（第三路：走重试）
```

### 1.3 设计原则（当前代码遵守的原则）

| 原则 | 体现 |
|------|------|
| **SRP — 单一职责** | `status_table.py` 只做一件事：管理状态转换。不处理 SSE 事件、不处理 DB、不处理 LLM 调用 |
| **KISS-DIRECT — 简单直接** | 函数式，不用类。`set_status(agent, new_status)` — 3 行代码内部逻辑 |
| **SLAP — 同一抽象层** | `react_cycle.py` 编排状态流转（高层），底层实现封装在 `status_table.py` |
| **YAGNI — 不过度设计** | 不加注册表、不加回调、不加事件总线 |
| **禁止 backward** | `base_agent.set_failed/set_completed/set_cancelled` 已全部删除，不存在新旧两套并存 |

## 二、状态管理（status_table.py）

### 2.1 状态枚举

`AgentStatus` 枚举定义在 `backend/app/services/agent/status_table.py`：

| 状态 | 性质 | 说明 |
|------|------|------|
| `IDLE` | 初始态 | Agent 创建后的初始状态 |
| `THINKING` | 中间态 | 正在 LLM 调用或准备工具调用 |
| `EXECUTING` | 中间态 | 正在执行工具 |
| `SUSPENDED` | 中间态 | 用户暂停 / HITL 等待确认 |
| `RETRYING` | 中间态 | 工具可恢复失败，等待重试 |
| `COMPLETED` | 终态 | 正常完成 |
| `FAILED` | 终态 | 失败 |
| `CANCELLED` | 终态 | 用户取消 |

### 2.2 合法转换表

```python
_TRANSITIONS = {
    AgentStatus.IDLE:      {AgentStatus.THINKING, AgentStatus.CANCELLED, AgentStatus.FAILED},
    AgentStatus.THINKING:  {AgentStatus.EXECUTING, AgentStatus.COMPLETED, AgentStatus.FAILED,
                            AgentStatus.CANCELLED, AgentStatus.RETRYING, AgentStatus.SUSPENDED},
    AgentStatus.EXECUTING: {AgentStatus.THINKING, AgentStatus.COMPLETED, AgentStatus.FAILED,
                            AgentStatus.SUSPENDED, AgentStatus.RETRYING},
    AgentStatus.RETRYING:  {AgentStatus.THINKING, AgentStatus.FAILED, AgentStatus.CANCELLED},
    AgentStatus.SUSPENDED: {AgentStatus.THINKING, AgentStatus.EXECUTING, AgentStatus.CANCELLED,
                            AgentStatus.FAILED},
    AgentStatus.CANCELLED: set(),
    AgentStatus.COMPLETED: set(),
    AgentStatus.FAILED:    set(),
}
```

终态（CANCELLED、COMPLETED、FAILED）不可转换，任何调 `set_status` 都会抛 `ValueError`。

### 2.3 状态变更函数

所有状态变更必须经过 `status_table.py` 的导出函数，这是唯一能修改 `agent.status` 的入口：

| 函数 | 签名 | 说明 |
|------|------|------|
| `set_status` | `(agent, new_status, reason="")` | 唯一入口：查 `_TRANSITIONS` 合法转换表 → 非法抛 `ValueError` → 合法赋值并日志 |
| `set_failed` | `(agent, reason="")` | 快捷调用 set_status(agent, FAILED, reason) |
| `set_completed` | `(agent)` | 快捷调用 set_status(agent, COMPLETED) |
| `set_cancelled` | `(agent)` | 快捷调用 set_status(agent, CANCELLED) |

**线程安全**：所有函数使用 `@_synchronized` 装饰器（`threading.RLock`）保护。

### 2.4 状态变更调用关系

```
                                  status_table.py
                                       │
      ┌──────────────┬─────────────────┼─────────────────┬──────────────┐
      │              │                 │                 │              │
 react_cycle.py  stream.py  initialize_run_state.py  action_handler.py
 (编排层)        (运输层)     (初始化)                   (HITL 暂停)
```

- `react_cycle.py`：`_dispatch_handler` 从 event type 推断状态 → 调 set_completed/set_failed/set_status(RETRYING)；`_process_single_step` 调 set_status(EXECUTING)；`run_react_cycle` 调 set_failed/set_status(THINKING) 重试
- `stream.py`：取消调 `set_cancelled`，异常调 `set_failed`
- `initialize_run_state.py`：启动调 `set_status(THINKING)`
- `action_handler.py`：HITL 确认时调 `set_status(SUSPENDED)`，确认/拒绝后恢复 `set_status(EXECUTING)`

## 三、三层职责边界

| 层级 | 文件 | 职责 | 能否改状态 | 能否改 message_builder |
|------|------|------|-----------|------------------------|
| **运输层** | `services/chat/stream.py` | SSE 收发、DB 存取、用户取消、捕获外部异常 | ❌ 正常流程不能。仅在取消时调 `set_cancelled`、顶层未预期异常时调 `set_failed` | ❌ 正常流程不能。finally 中只读 agent.status 存 DB |
| **编排层** | `react_cycle.py` | 主循环调度、LLM 调用（含截断检测/B3 重试）、_dispatch_handler 从 event type 推断状态、从 Step content 加 context、异常兜底 | ✅ 唯一正常设状态的地方 | ✅ 唯一正常加 context 的地方 |
| **执行层** | `handlers/answer_handler.py` | 处理 LLM 返回的 final answer，生成 ThoughtStep/FinalStep/ErrorStep | ❌ 绝对不能 | ❌ 绝对不能 |
| **执行层** | `handlers/action_handler.py` | 处理 LLM 返回的工具调用，生成 ThoughtStep/ActionStep/ObservationStep | ❌ HITL 除外 | ❌ 绝对不能 |
| **执行层** | `step_emitter.py` | 创建步骤对象，记录到 agent.steps | ❌ `exit_with_error` 不设状态 | ❌ 不碰 message_builder |
| **状态机** | `status_table.py` | 唯一改得动 `agent.status` 的地方 | ✅ 唯一物理上改属性的地方 | ❌ 不碰 message_builder |

### 运输层例外说明

- 用户取消（`KeyboardInterrupt` 或前端发取消信号）：运输层持有连接上下文，不能等到编排层处理，允许调 `set_cancelled`
- 顶层未预期异常（如数据库断开、LLM HTTP 错误）：发生在编排层之外，运输层捕获后调 `set_failed`
- 正常流程下运输层不做任何状态操作

## 四、Handler yield-only 协议

### 4.1 协议定义

Handler 不调任何 `set_xxx` 函数，不调 `message_builder.add_xxx`，不 `return dict`。Handler 是 **async generator**，只 `yield Step` 对象。

### 4.2 _dispatch_handler 推断状态

```python
async def _dispatch_handler(agent, llm_response):
    seen_types = set()
    last_event = None
    last_error_event = None

    # 按响应类型分派 handler
    parsed_type = llm_response.get("type", "answer")
    if parsed_type == "action":
        handler = handle_action(agent, llm_response)
    elif parsed_type == "answer":
        handler = handle_answer(agent, llm_response)
    elif parsed_type == "error":
        handler = handle_llm_error(agent, llm_response)
    else:
        handler = _handle_unknown(agent, llm_response)

    # 遍历 yield 链：跟踪 event type
    async for event in handler:
        seen_types.add(event.type)
        last_event = event
        if event.type == "error":
            last_error_event = event
        yield event

    # 遍历完毕后根据 event type 推断状态
    if "error" in seen_types:
        error_event = last_error_event
        if hasattr(error_event, 'recoverable') and error_event.recoverable:
            set_status(agent, AgentStatus.RETRYING)   # 第三路：重试
        else:
            set_failed(agent, error_msg)
    elif "final" in seen_types:
        set_completed(agent)
    # 否则 continue（不设状态）
```

| event type 组合 | 状态动作 |
|----------------|---------|
| 有 `"error"` 且 `recoverable=True` | `set_status(RETRYING)` → 第三路：重试 |
| 有 `"error"` 且非 recoverable | `set_failed(agent)` |
| 无 error，有 `"final"` | `set_completed(agent)` |
| 无 error、无 final | 不设状态（continue） |

### 4.3 Handler yield 模式

```
完成路径:
  yield ThoughtStep / ActionStep ... → yield FinalStep
                                       有 "final" 无 "error" → set_completed

失败路径（不可恢复）:
  yield ErrorStep(recoverable=False) [→ yield FinalStep]
                                       有 "error" 且非 recoverable → set_failed

失败路径（可恢复，第三路：重试）:
  yield ErrorStep(recoverable=True)   有 "error" 且 recoverable → set_status(RETRYING)

继续路径:
  yield ThoughtStep → yield ActionStep → yield ObservationStep → (返回)
  无 "error"、无 "final" → continue（不设状态）

LLM error 路径:
  LLM 返回 type=error → handle_llm_error(agent, llm_response)
  → yield ErrorStep(error_type="llm_error")（只 yield）
  → _dispatch_handler 看到 "error" → set_failed

LLM 未知类型路径:
  LLM 返回其他 type → _handle_unknown(agent, llm_response)
  → yield ErrorStep(error_type="unknown_response")（不可恢复）
  → _dispatch_handler 看到 "error" → set_failed
```

## 五、文件职责

### 5.1 `status_table.py`

**路径**: `backend/app/services/agent/status_table.py`  
**职责**: 函数式状态机，唯一能改得动 `agent.status` 的地方。纯函数 + 数据表，不用类。

导出函数：`set_status`、`set_failed`、`set_completed`、`set_cancelled`，全部线程安全。

### 5.2 `base_agent.py`

**路径**: `backend/app/services/agent/base_agent.py`  
**职责**: Agent 基类，定义通用接口和生命周期钩子。

关键设计：
- `set_failed/set_completed/set_cancelled` 方法**已删除**，所有状态变更必须通过 `status_table.py` 的导出函数
- `__init__` 中 `self.status = AgentStatus.IDLE` 保留（初始化不算状态流转）
- `run_react_cycle` 委托给 `react_cycle.py` 中的 `_run` 函数

### 5.3 `react_cycle.py`

**路径**: `backend/app/services/agent/react_cycle.py`  
**职责**: 核心编排逻辑，含 `run_react_cycle`、`_process_single_step`、`_dispatch_handler`。

关键函数：

| 函数 | 职责 | 状态操作 |
|------|------|---------|
| `run_react_cycle` | 主循环：LLM 调用 → 工具执行 → dispatch → 状态推断 → 重试 | while 循环检查状态，RETRYING 时计数重试（≤3次），超限 set_failed |
| `_process_single_step` | 三步处理：准备 LLM 消息 → LLM 流式调用 → 响应分派 | Phase 3 设 `EXECUTING`，空响应设 `FAILED`，取消设 `CANCELLED`，截断重试 |
| `_dispatch_handler` | 按 LLM 响应类型分派 handler，从 event type 推断状态 | 见 §4.2 |
| `handle_react_error` | 创建 ErrorStep（不设状态），由调用方在 except 块中设 FAILED | 不设状态 |
| `_handle_unknown` | 未知响应类型 → yield ErrorStep | 不设状态 |

### 5.4 `handlers/action_handler.py`

**路径**: `backend/app/services/agent/handlers/action_handler.py`  
**职责**: 处理 LLM 返回的 tool_call，执行工具并产出步骤事件。

关键函数：

| 函数 | 是否设状态 | 是否碰 message_builder |
|------|-----------|------------------------|
| `handle_action` | ❌ 只 yield Step | ❌ |
| `check_safety_and_confirm` | ✅ 例外：HITL 等待时设 SUSPENDED，响应后恢复 EXECUTING | ❌ |
| `execute_tools` | ❌ | ❌ |
| `build_observation` | ❌ | ✅ 添加 tool_call 消息和 tool 结果到 history |

**HITL 暂停流程**：在 `check_safety_and_confirm` 中，当工具需要用户确认时，调 `set_status(agent, SUSPENDED)` 暂停编排循环，等用户响应后恢复 `set_status(agent, EXECUTING)`。

### 5.5 `handlers/answer_handler.py`

**路径**: `backend/app/services/agent/handlers/answer_handler.py`  
**职责**: 处理 LLM 非 action 响应（answer、error、unknown）。

关键逻辑：
- `type="answer"` + 有内容 → yield ThoughtStep + FinalStep
- `type="answer"` + 纯思考（有 thought 无 content）→ yield ThoughtStep，不设终态，循环继续
- `type="answer"` + 空内容 → yield ErrorStep(recoverable=True)
- `type="error"` → yield ErrorStep(type="llm_error")
- 未知 type → yield ErrorStep(type="unknown_response")

一律不设状态、不碰 message_builder。

### 5.6 `step_emitter.py`

**路径**: `backend/app/services/agent/step_emitter.py`  
**职责**: 创建并记录 Step 对象。

关键方法：
- `emit(step)` → 追加到 `agent.steps`，返回该 step
- `exit_with_error(step_count, error_type, error_message, recoverable=False)` → 创建 ErrorStep 并 emit，**不设状态**

### 5.7 `services/chat/stream.py`（原 run_sse_stream.py）

**路径**: `backend/app/services/chat/stream.py`  
**职责**: SSE 流入口，协调 agent 执行和 SSE 事件输出。

关键逻辑：
- 创建 `UniversalAgent`，注册到 `running_tasks`
- 设 Stop-check 回调（取消/暂停检测）
- 调用 `agent.run_react_cycle` → 迭代事件 → 格式化 SSE → yield
- 异常处理：取消 → `set_cancelled`，异常 → `set_failed`

### 5.8 `initialize_run_state.py`

**路径**: `backend/app/services/agent/initialize_run_state.py`  
**职责**: 每次运行前初始化 agent 状态。

调 `set_status(agent, AgentStatus.THINKING)` 启动状态机，重置 `steps`、`llm_call_count`、`_retry_count`、`_consecutive_truncations`。

## 六、全链路数据流转

```
stream.py (运输层)
  └── agent.run_react_cycle (base_agent.py)
        └── _run (react_cycle.py::run_react_cycle)
              ├── initialize_run_state()
              │     └── set_status(THINKING)
              └── LOOP (while status in {THINKING, EXECUTING, RETRYING, SUSPENDED}):
                    ├── 取消检查 → set_cancelled → break
                    ├── RETRYING 处理
                    │     ├── retry_count > 3 → set_failed → break
                    │     └── set_status(THINKING) → continue
                    ├── _process_single_step()
                    │     ├── Phase 1: 准备 LLM 消息 + tools
                    │     ├── Phase 2: call_llm_with_fallback → yield ChunkStep
                    │     └── Phase 3:
                    │           ├── set_status(EXECUTING)
                    │           ├── 空响应 → set_failed → yield ErrorStep
                    │           ├── 取消 → set_cancelled → yield FinalStep
                    │           ├── 截断检测 → B3 重试或截断重试（≤3次）
                    │           └── _dispatch_handler()
                    │                 ├── "action" → handle_action() → yield Step 链
                    │                 ├── "answer" → handle_answer() → yield Step 链
                    │                 ├── "error"  → handle_llm_error() → yield ErrorStep
                    │                 └── else    → _handle_unknown() → yield ErrorStep
                    │                 └── 遍历完成后从 event type 推断状态
                    │                       ├── error+recoverable → set_status(RETRYING)
                    │                       ├── error+!recoverable → set_failed
                    │                       ├── final → set_completed
                    │                       └── 其他 → continue
                    └── 状态检查: COMPLETED/FAILED/CANCELLED → break
              └── finally: _ensure_failed_final_step + _finalize_cycle

编排层在 yield 透传时提取 Step content:
  - ObservationStep → agent.message_builder.add_observation()
  - FinalStep → agent.message_builder.add_assistant_message()
  - ErrorStep(recoverable=True) → 作为 retry observation 传给 LLM
```

## 七、状态变更汇总

### 谁调用了 status_table 函数

| 调用方 | 调用的函数 | 触发时机 |
|--------|-----------|---------|
| `react_cycle.py::_process_single_step` | `set_status(EXECUTING)`, `set_failed`, `set_cancelled` | LLM 调用后、空响应、取消、截断重试 |
| `react_cycle.py::_dispatch_handler` | `set_status(RETRYING)`, `set_failed`, `set_completed` | handler yield 链遍历完毕，从 event type 推断 |
| `react_cycle.py::run_react_cycle` | `set_failed`, `set_status(THINKING)` | 重试逻辑、max_steps 超限、循环结束 |
| `action_handler.py::check_safety_and_confirm` | `set_status(SUSPENDED)`, `set_status(EXECUTING)` | HITL 等待/确认/拒绝 |
| `initialize_run_state.py` | `set_status(THINKING)` | 运行初始化 |
| `services/chat/stream.py` | `set_cancelled`, `set_failed` | 取消/异常 |

### 当前状态：零处 `agent.status = X` 直接赋值

所有状态变更均经过 `status_table.py` 的导出函数。`grep 'agent\.status\s*='` 仅返回 `base_agent.py::__init__` 的 `self.status = AgentStatus.IDLE` 一行。
