## 1 背景与目标

在《LLM 系统优化方案-v2.0》已核查的 10 项之外，以全新、独立视角重新扫描 `backend/app/` 真实代码，聚焦两个维度挖掘新优化项：

- **系统能力**：可观测性、稳定性、长任务连贯性、记忆、排障。
- **扩展性**：多 Provider 容灾、并发门控、插件生态、多 Agent 协作、多租户合规。

**硬约束**（用户铁规）：
1. 每条设计必须首先满足代码 **10 大规范**（SRP / DRY / KISS-DIRECT / SLAP / YAGNI / 禁止 backward / OCP / LSP / ISP / 复用优先）。
2. 每条必须**确证增强系统能力或扩展系统能力**，剔除伪优化、过度设计、冗余复杂度。
3. 本机为**单机桌面单用户 Agent**（`~/.omniagent` SQLite，无多用户/无云），故 YAGNI 优先：能用 SQLite/标准库解决的不引 Redis/向量库/消息总线等重依赖；但"扩展点"必须真实存在、未来可平滑升级。

经 4 个探索 agent 实读代码 + 作者 5 遍复核，确认以下 **11 项全部达标**，无一项剔除。

## 3 各优化项详细设计

### 3.1 Token 成本可观测性

#### 3.1.1 现状核查
- `collector.py:50-57` `register_default_metrics()` 只注册 6 个 HTTP 指标，无 token 指标。
- `core.py` `StreamChunk` 已带 `usage: Optional[Dict]`（`prompt/completion/total_tokens`）。
- `base_service.py:263` 已在 SSE 流逐 chunk 带出 `usage`；`llm_stream.py:56-65` `_log_llm_response` 仅写日志，**从未调用 `MetricsCollector`**。
- `api/v1/metrics.py` 三端点只暴露 HTTP 指标。

#### 3.1.2 复用点
- 复用 `MetricsCollector.record_metric()`（`collector.py:74`）+ `register_default_metrics()`，新增指标名即可，不新建收集器。
- 复用 `metrics.py` 既有 `get_metrics_summary/get_raw_metrics/reset_metrics` 出口，指标自动进 summary。
- 复用已贯通的 `usage_data` 与 `agent.task_id` / `agent.llm_client.model`，零新增采集逻辑。

#### 3.1.3 设计方案
1. `collector.py`：注册 3 个 COUNTER `llm_prompt_tokens_total` / `llm_completion_tokens_total` / `llm_total_tokens_total`，labels `{model, task_id}`。
2. `collector.py` 模块级落单例 `default_collector = MetricsCollector()`；`middleware.py:14` 的独立 `_collector` 删除，改为 `from ...collector import default_collector`（**禁止 backward**：原引用名不变）。
3. `monitoring/__init__.py` 导出 `get_collector()`。
4. `llm_stream.py`：在 `call_llm_stream` 捕获 `usage_data`（130 行处）后新增一处调用 `_record_token_usage(usage_data, agent)`；该函数内用 `get_collector().record_metric(...)` 落 3 指标。**只在此一处记录（DRY）**，answer/action 分支都会经过。

#### 3.1.4 规范契合
- **SRP**：指标聚合单点，不混入业务流。
- **KISS-DIRECT**：仅加 3 指标 + 1 注入函数，无框架。
- **DRY**：单点记录，不重复。
- **YAGNI**：先做 token 计数，单价/币种换算不入本期。
- **复用优先**：复用 `MetricsCollector` 与已贯通 `usage_data`。

#### 3.1.5 增强/扩展价值
运营可查单 model/单 task 的 token 消耗，定位高成本会话；`get_summary()` 对 COUNTER 天然 sum。

#### 3.1.6 实施步骤
1. `collector.py` 注册 3 指标 + 模块级单例。
2. `middleware.py` 收敛单例引用。
3. `monitoring/__init__.py` 导出 `get_collector`。
4. `llm_stream.py` 加 `_record_token_usage` 并调用。

#### 3.1.7 风险与降级
- `record_metric` 仅 append，失败由 collector 内部兜底，无异常抛出路径（不阻断主流程）。
- `usage_data` 可能缺 `total_tokens`，用 `or 0` 防御。

### 3.2 多 Provider 路由 / fallback / 负载均衡

#### 3.2.1 现状核查
- `resolver.py:49-59` `resolve_provider_model()` 只从 `ai.provider/ai.model` 读**一个**候选，失败直接 `raise`。
- `client_sdk.py:72-99` `LLMClient.__init__` 构造时锁定单 provider+model。
- `lifecycle/service.py:19-21,89-114` 全局 `_instance` 仅缓存**一个** `BaseAIService`。
- `llm_stream.py:173-198` `call_llm_with_fallback` 仅 FC→Text 降级，**无任何 provider 级切换**。
- `config.yaml` 已配 10 个 provider，但只启用 1 个，**其余从未被路由使用**（真实闲置能力）。

#### 3.2.2 复用点
- 复用 `resolver.get_ai_config()` / `get_service_config()` / `_validate_*`（`resolver.py:17,61`）。
- 复用 `create_service_instance()`（`service.py:69-86`）。
- 复用 `SystemErrorClassifier.classify_error()`（`error_classifier.py:119`）+ `is_retryable` 判定是否切备。
- `BaseAIService` 接口稳定，pool 仅做同签名委托，调用点零改动。

#### 3.2.3 设计方案
1. 新建 `services/lifecycle/provider_pool.py`：`class ProviderPool`，构造入参 `List[BaseAIService]`（按优先级）+ 每实例 `_Health{cooldown_until, consecutive_fail}`。
   - `request_stream()/request()`：委托当前健康 backend；捕获异常后按 `SystemErrorClassifier` 决策（429/5xx/网络错→标记 cooldown 并切下一候选重新发起同一次流；FC 格式错不切）；全部失败抛最后错误。
   - `cancel()/close()/set_stop_check()` 透传当前 backend；`model/provider` 返回活跃 backend 的。
   - 负载均衡默认关（`ai.load_balance: false` 严格主→备）；开启时 round-robin 选 healthy。**YAGNI：不引 weight/一致性哈希**。
2. `service.py`：`build_candidate_list()` 以 `ai.provider/ai.model` 为候选[0]，读新增 `ai.fallback:[{provider,model}]` 生成有序候选，复用 `_validate_*` 跳过无效项；`get_service()` 缓存 key 改为候选签名，命中返 `ProviderPool`（**禁止 backward**：`_instance/_current_provider` 结构不变，仅扩展语义）。
3. `config.yaml` `ai:` 增 `fallback` 列表（空=无备）。
4. `resolver.py` 增 `resolve_candidates()`（复用现有校验方法）。

#### 3.2.4 规范契合
- **SRP**：路由/健康隔离于 `ProviderPool` 单文件。
- **KISS-DIRECT**：透明包装，无路由框架。
- **OCP**：新增 provider 只改配置，不改核心。
- **SLAP**：pool 负责跨 provider，底座负责同 provider 网络重试，两层正交。
- **复用优先**：复用 resolver/service/classifier。

#### 3.2.5 增强/扩展价值
主 provider 限流/宕机自动切备，单次任务不再整体失败；可把贵模型放主、免费模型放备做成本调度；配置已配的 10 个 provider 终于被利用。

#### 3.2.6 实施步骤
1. `resolver.py` 增 `resolve_candidates()`。
2. 新建 `provider_pool.py`（`ProviderPool` + `_Health` + 切备逻辑）。
3. `service.py` 增 `build_candidate_list()`，`get_service()` 返/缓存 `ProviderPool`。
4. `config.yaml` 增 `ai.fallback`。

#### 3.2.7 风险与降级
- 切备会增加一次失败往返；pool 层先于底座重试切备，避免叠加超时爆炸（底座 `LLM_STREAM_MAX_RETRIES` 在切备场景降为 1）。
- FC→Text 降级仍在 pool 内层，两者分层清晰。
- 配置热重载：pool 缓存签名变化即重建，无副作用。

### 3.3 真实熔断器 + 全局限流/并发信号量

#### 3.3.1 现状核查
- `error_classifier.py:35,147` `CIRCUIT_OPEN` 仅是枚举值 + 字符串匹配 `'circuit' in ... and 'open' in ...`，**无任何真实熔断器状态机**，该分支永不触发。
- `constants.py:32` `RATE_LIMIT_STATUS_CODES={429,1305}`，`base_service.py:107` `_is_rate_limit_status` 仅做集合判断，**无退避节流动作**。
- `base_service.py:268-274` 指数退避 `wait_time=2**retry_count` 硬编码，无 token-bucket、无全局并发控制。
- `client_sdk.py:93-96` httpx 连接池 `max_connections=10` 是每实例各自的，跨请求不共享，无法做全局并发上限。
- 全仓 grep：无 `Semaphore` / `token_bucket` / 真实 `CircuitBreaker`。

#### 3.3.2 复用点
- 复用 `RATE_LIMIT_STATUS_CODES`（`constants.py:32`）作触发源。
- 复用 `SystemErrorClassifier` 做错误分类，开路异常仍走 `is_retryable=False`（不破坏分类）。
- 复用 `httpx.Timeout/Limits` 配置入口。

#### 3.3.3 设计方案
新建 `services/llm/rate_limiter.py`（SRP：并发信号量 + token-bucket + 简单熔断器，三机制独立不耦合）：
1. **全局并发信号量**：模块级 `LLM_CONCURRENCY_SEMAPHORE = asyncio.Semaphore(DEFAULT_LLM_MAX_CONCURRENCY)`（`constants.py` 加 `=5`）；在 `client_sdk.py` `request/request_stream` 内 `async with ...:` 包裹 HTTP 调用（SLAP：HTTP 层只管拿/放信号量）。
2. **真实熔断器** `class LLMCircuitBreaker`：状态 `CLOSED/OPEN/HALF_OPEN`，计数 `failure_count/_opened_at`；阈值常量 `CIRCUIT_FAILURE_THRESHOLD=5`、`CIRCUIT_OPEN_SECONDS=30`。`async def call(self, coro_factory)` 包裹一次 LLM HTTP 调用：成功重置计数；失败（SERVER/CIRCUIT_OPEN 系）计数+1，超阈值置 OPEN；OPEN 态抛 `CircuitOpenError`（文案含 "circuit open"，使现有分类器命中并 `is_retryable=False`→快速失败不瞎重试）；超 `CIRCUIT_OPEN_SECONDS` 转 HALF_OPEN 放 1 探测。放在 `client_sdk` 的 `request_stream` 内，与信号量同层。
3. **Token-bucket 限流**：`class TokenBucket` 模块级单例；在 `base_service.py:268-274` 重试分支检测到 `_is_rate_limit_status` 时，用 bucket 算退避替换硬编码 `2**retry_count`，并向上喂熔断器计数（429 视为一次失败，防雪崩）。

#### 3.3.4 规范契合
- **SRP**：单文件三独立机制。
- **KISS-DIRECT**：无框架，信号量+状态机直写。
- **YAGNI**：先全局单例，不按 model 分桶。
- **禁止 backward**：去掉 `_is_rate_limit_status` 仅判断旧语义，改为"判断+行动"，调用方仍是 base_service 自身。
- **复用优先**：复用 `RATE_LIMIT_STATUS_CODES` / `SystemErrorClassifier`。

#### 3.3.5 增强/扩展价值
429/5xx 风暴时熔断开路快速失败而非堆积重试；多会话并发打 LLM 不再互相挤占；状态/桶余量后续可进 MetricsCollector（独立增量）。

#### 3.3.6 实施步骤
1. `constants.py` 加 `DEFAULT_LLM_MAX_CONCURRENCY` / `CIRCUIT_*` / `TOKEN_BUCKET_*`。
2. 新建 `rate_limiter.py`（`Semaphore` / `LLMCircuitBreaker` / `TokenBucket` / `CircuitOpenError`）。
3. `client_sdk.py` `request/request_stream` 包信号量 + 包熔断器。
4. `base_service.py:268-274` 429 走 token-bucket 退避并喂熔断器。

#### 3.3.7 风险与降级
- 信号量在 asyncio 事件循环内创建（FastAPI 单 loop），模块级 `asyncio.Semaphore()` 导入时创建允许（acquire 才需 loop）。
- 熔断器为进程内单例；若未来多 worker 需外部共享（Redis），属独立增量，不在本期。

### 3.4 长上下文摘要压缩（Compaction，非丢弃）

#### 3.4.1 现状核查
- `message_builder.py:180-222` `trim_history()` 触发后 `_trim_to_budget`（242-299）从旧到新裁，**被裁旧 FC 对直接丢弃，无摘要生成/注入**。
- `message_builder.py:96-114` `inject_history()` 系统消息之后、task 之前可注入 `history_msgs`，是现成摘要落点。
- `base_service.py:116-152` `BaseAIService.request()` 非流式已可用，返回 `ChatResponse.content`，压缩可直接复用同一 client。
- grep `summar`：工具层无历史摘要工具，需新建压缩函数。

#### 3.4.2 复用点
- 复用 `inject_history()`（插入点零新接口）。
- 复用 `agent.llm_client.request()` 做摘要（同 client，天然享受 3.2 的 pool 容错）。
- 复用 `_classify_messages()`（`message_builder.py:224`）挑出将被丢弃的旧片段。
- `MAX_CONTEXT_CHARS` 已由 `base_agent.py:60` 注入，无需新配置读取。

#### 3.4.3 设计方案
1. `message_builder.py` `__init__` 增可选 `llm_client=None`（默认 None，**禁止 backward**）；`base_agent.py:60` 实例化时传 `self.llm_client`，为 None 时降级为原丢弃。
2. 新增 `_make_compaction_prompt(discarded_msgs)`：拼 system 指令（压成"用户原始目标/关键决策/工具最终结果/未决任务"，中文 ≤N 字）+ 丢弃片段原文。
3. 新增 `_generate_summary(self, discarded_msgs) -> Optional[str]`：调 `self.llm_client.request(...)` 取 `resp.content`；失败/超时返回 `None`（降级为原丢弃，YAGNI 不加重试链）；超 `MAX_CONTEXT_CHARS*0.1` 截断。
4. 改 `trim_history()`：计算 `discarded = 原始 obs+assistant - trimmed`；若非空且字符 > `MAX_CONTEXT_CHARS*0.3`（小裁剪不浪费成本）则 `_generate_summary`；摘要非空则作为 `{"role":"system","content":"[History Summary]\n"+summary}` 注入 system 与 user 之间（复用 inject_history 语义）。保留最近 `_max_rounds` 原文不受影响。

#### 3.4.4 规范契合
- **SRP**：压缩逻辑为独立两函数。
- **KISS-DIRECT**：触发时调一次小 prompt，无独立摘要服务/后台任务。
- **YAGNI**：不加摘要分级/重试链（MVP）。
- **禁止 backward**：`llm_client` 默认 None，老调用路径完全兼容。
- **复用优先**：复用 `inject_history` / `request` / `_classify_messages`。

#### 3.4.5 增强/扩展价值
长任务早期上下文（用户初始目标/关键结论）被压缩保留，避免"忘了开头要做什么"；成本远低于每次全量重发。

#### 3.4.6 实施步骤
1. `message_builder.py` `__init__` 加 `llm_client=None`；新增 `_make_compaction_prompt` / `_generate_summary`。
2. `trim_history()` 算 discarded → 条件触发 → 摘要注入 rebuild 链路。
3. `base_agent.py:60` 传 `llm_client=self.llm_client`。

#### 3.4.7 风险与降级
- 每次超阈值 trim 多一次同步 LLM 调用，仅在跨越阈值那一轮发生（非每轮）。
- 摘要标注 `[History Summary] 以下为压缩摘要，可能不完整`，降低幻觉风险。
- 摘要为纯 system 消息，不参与 FC 配对（`_trim_fc_pairs` 原样保留），无破坏。

### 3.5 长期记忆 / RAG / 知识检索

#### 3.5.1 现状核查

- `message_builder.py:96` `inject_history()` 仅把 `chat_messages` 表多轮原文原样插入，**无语义/关键词筛选**。
- `db/models/chat_models.py` 仅 Session/Message；无记忆表。
- `ToolCategory` 10 类无 retrieval/search 类；`config.py` 无 memory 段。

#### 3.5.2 复用点
- 复用 `db.get_conn("chat")`（`database.py:52`）事务/WAL/外键，新表加在 `db_initializer.py:12 init_chat_db`。
- 复用 `initialize_run_state._inject_conversation_history`（`initialize_run_state.py:19`）已调 `inject_history`（支持 `role=system`）。
- 复用 `agent.llm_client`（蒸馏事实摘要）。
- 复用 `get_config().get("app.max_rounds")` 范式加 `app.memory_enabled` / `app.memory_top_k`。
- **FTS5**：Python 3.13 标准 `sqlite3` 自带，**零外部依赖**（YAGNI 不引向量库）。

#### 3.5.3 设计方案
1. `db_initializer.py` `init_chat_db` 加 `long_term_memory` 表（`scope/content/keywords/source_task_id/created_at/access_count`）+ `memory_fts` FTS5 虚表 + `idx_memory_scope` 索引（DDL 幂等）。
2. 新建 `services/agent/memory_store.py`（SRP：只管记忆读写检索）：
   - `add_memory(scope, content, keywords, source_task_id)` → 写主表 + 同步 `memory_fts`，事务内完成。
   - `retrieve(query, scope, top_k=5)` → 优先 `memory_fts MATCH`，无结果/异常降级 `LIKE '%kw%'`（复用 `keywords` 列），返回 top_k 条。
   - `distill_and_store(llm_client, task, final_answer, scope, task_id)` → 调一次 LLM 仅产出"关键事实/结论+关键词"（严格短输出）再 `add_memory`；放任务结束分支，唯一额外 LLM 调用。

- `constants.py` 加 `STREAM_BUFFER_MAX_EVENTS=5000`。
- `task_state.py:32` `event_log` 改 `deque(maxlen=STREAM_BUFFER_MAX_EVENTS)`（KISS，不引 `collections` 外依赖）。存 `(seq, event)` 元组，`seq` 由全局单调计数器（`buffer._seq_counter += 1`）生成，不受 pop 影响。
- 消费者按 `seq > after_seq` 过滤（deque 内顺序即 seq 顺序）。**禁止 backward**：消费者读取协议仍用 seq 偏移，仅语义上"超老事件不可回放"。

**机制 B — 生产者背压（防消费者被淹没）**
- `constants.py` 加 `STREAM_BUFFER_HIGH_WATERMARK=4500`。
- `agent_runner.py` `_append`：append 后若 `len(buffer.event_log) >= HIGH_WATERMARK` 则 `await buffer.cond.wait()`（持锁内）；消费者 `_stream_with_control` 每批消费后 `async with buffer.cond: buffer.cond.notify_all()`。经典有界缓冲生产者/消费者，复用现有 `Condition`，零新增依赖。
- `openai.py` reconnect 协议：若 `after_seq` 超出 deque 长度，返回明确"事件已过期，请刷新"提示（避免前端卡死）。

#### 3.10.4 规范契合
- **SRP**：有界容器 + 背压两机制正交。
- **KISS-DIRECT**：`deque(maxlen)` + `Condition.wait/notify` 直写，无框架。
- **SLAP**：背压逻辑只在 `_append`/消费者读取层，不掺业务。
- **禁止 backward**：消费者 seq 读取协议不变，仅超老事件语义变化。
- **复用优先**：复用 `StreamBuffer.cond` / `constants.py`。

#### 3.10.5 增强/扩展价值
长任务不再无限吃内存，服务稳定性提升；背压让慢客户端（断网重连慢）不反压成内存暴涨。

#### 3.10.6 实施步骤
1. `constants.py` 加 `STREAM_BUFFER_MAX_EVENTS` / `STREAM_BUFFER_HIGH_WATERMARK`。
2. `task_state.py` `event_log` 改 `deque(maxlen=...)`；`_append` 用 `_seq_counter` 生成全局 seq。
3. `agent_runner.py` `_append` 超限 `await cond.wait()`。
4. `openai.py` `_stream_with_control` 每批消费后 `notify_all`；reconnect 超窗返回"事件已过期"提示。

#### 3.10.7 风险与降级
- seq 语义：deque `pop(0)` 后已发 seq 与新下标错位，故存 `(seq,event)` 元组 + 全局单调计数器，消费者按 `seq > after_seq` 过滤。
- 背压 `await cond.wait()` 须在 `async with buffer.cond` 内，且不在持锁内做 IO（保持现有 `_append` 在持锁外做 `log_step_yield`）。
- 不改 `reclaim_stream_buffer` 300s 延迟回收语义（仍保留重连窗口）。

### 3.11 多租户配额 / 审计追踪

#### 3.11.1 现状核查
- `tool_safety_checker.py:65` `check_before_execute` 仅二元判定（`is_safe/requires_confirmation/blocked`），`SafetyResult`（`:44`）无 user/session/token 维度，无配额概念。

- `config.yaml:122` `security` 段只二元开关，无 quota 段。

- 复用 `SafetyResult` + `check_before_execute` 作配额拦截入口（注入式）。
- 复用 `react_cycle._RECOVERABLE_ERRORS` 的 `"blocked"` 降级路径（配额超限=一种 blocked，LLM 自动换方案不崩溃）。
- 复用 `action_handler.execute_tools` 已算 `elapsed` 与 `tool_names`。
- 复用 `api/v1/task_queries.py` 路由范式。
- 复用 `agent_runner` 持有的 `session_id/task_id/context`（用户维度从此传入）。

#### 3.11.3 设计方案
**A. 审计（Audit）**：新建 `services/safety/audit_recorder.py` + 新表 `tool_audit_log`（`db_initializer.init_operations_db` 内 CREATE）：
- 列：`id, user_id, session_id, task_id, tool_name, category, token_estimate, duration_ms, status, created_at`。
- `AuditRecorder.record(user_id, session_id, task_id, tool_name, category, token_estimate, duration_ms, status)`：`token_estimate` KISS 估算 = `len(prompt+response)//4`（字符/4，单机足够，不引 tiktoken，YAGNI）；INSERT 失败仅 log 不阻断主流程（沿用 `operation_recorder` 容错）。
- 注入点：`action_handler.execute_tools` 末尾（`:242-250` 已有 `elapsed` 与 `tool_names`）对每个 call 调 `AuditRecorder.record(...)`；user/session/task 从 `agent` 取（默认 `"default"` 兼容单机）。

**B. 配额（Quota）**：新建 `services/safety/quota_manager.py`：
- `config.yaml` 增 `quota` 段：`enabled:false`、`default:{daily_token_limit:2000000, daily_call_limit:500}`、`users:{}`。
- `QuotaManager.check(user_id) -> (allowed, reason)`：读 `tool_audit_log` 按 `user_id` + 当日 `date('now')` 聚合 `SUM(token_estimate)` 与 `COUNT(*)`，超阈值返 `(False, "配额超限…")`。
- 注入点：`tool_safety_checker.check_before_execute`（`:65`）开头：`if get_config().get("quota.enabled", False): qm=get_quota_manager(); allowed,reason=qm.check(user_id); if not allowed: return SafetyResult(is_safe=False, blocked=True, message=reason, safety_level="quota_exceeded")` —— 复用现有 `blocked` 分支（`action_handler.py:70` 已处理），LLM 收到"配额超限"observation 自动换方案（走 `_RECOVERABLE_ERRORS`，不置 FAILED）。

**C. 查询 API**：新建 `api/v1/audit.py`（`APIRouter` 仿 `task_queries.py`）：`GET /audit?user_id=&session_id=&task_id=&tool=&date=&limit=`；`GET /audit/quota/{user_id}`。在 `main.py` `api_router.include_router(audit_router)` 挂一行。

**D. user_id 来源（最小改动）**：`agent_runner.run_agent_in_background` 的 `context` 已透传；API 层（`messages.py` 创建任务处）从请求头 `X-User-Id` 或 session 取 user 写入 `context["user_id"]`，缺省 `"default"`。

#### 3.11.4 规范契合
- **SRP**：审计/配额各自独立模块。
- **KISS-DIRECT**：复用 `blocked` 路径做降级，不新造状态机。
- **SLAP**：配额检查与安全检查同抽象层。
- **YAGNI**：不引 tiktoken/Redis，字符估算 + SQLite 够单机。
- **禁止 backward**：旧安全逻辑不变，仅前缀注入。
- **OCP**：新表 + 新模块，核心循环未改。
- **复用优先**：复用 `SafetyResult` / DB 连接 / API 范式 / 降级路径。

#### 3.11.5 增强/扩展价值
单机也可按会话/用户统计成本与工具滥用，定位高耗任务；配额超限优雅降级（不崩、LLM 自适应）；审计表是未来 SaaS 多租户/计费/合规追溯的直接数据底座。
