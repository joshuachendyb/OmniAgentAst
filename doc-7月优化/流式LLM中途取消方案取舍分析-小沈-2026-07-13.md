# 流式 LLM 中途取消方案取舍分析

- 编写人：小沈
- 时间：2026-07-13 11:04:11
- 关联任务：v3.2 终态 Step 统一约定 — 用户取消语义落地

## 一、背景与问题

本次 v3.2 终态统一约定要求：用户取消 = `MetaStep(type="cancelled")`，DB `status` 列落 `cancelled`，前端明确显示"已取消"，**绝不能**误判为 `ErrorStep(failed)`。

静态审计发现一个**严重阻断缺陷**并已修复（循环粒度）：

- `react_cycle.py:198` 原用户取消检测 `getattr(agent.llm_client, '_cancelled', False)` 中，`_cancelled` 全局**从未被任何代码赋值**（grep 0 处赋值）。因此该分支是死代码，用户取消永远走不到 `MetaStep(cancelled)`，而是落到 `react_cycle` 场景 A：`llm_response` 为空/异常 → `ErrorStep(empty_response)` → 前端/DB 判为 `failed`。
- 修复：在 `run_react_cycle` 循环顶加入 `check_cancelled(task_id)` 真实检测，取消即干净终止为 `MetaStep(cancelled)`（已合入，源码层面取消语义正确）。

但修复后仍存在**一个未决的能力缺口**：当前取消只在"下一轮 LLM 调用之前"生效（循环粒度），无法在"LLM 正在流式输出"的途中打断。根因：

- `agent_runner.py:77` 试图注入 `llm_service.set_stop_check(_stop_check)`，但 `LLMClient`(`client_sdk.py`) **根本没有 `set_stop_check` 方法** → `hasattr` 为 False → 整段跳过。即 LLM 客户端从不持有停止回调。
- `client_sdk.request_stream` 只是 `httpx` 裸流式读取，逐行 `yield`，循环内没有任何停止检查。
- `llm_stream.call_llm_stream` 读取 chunk 时也没有轮询停止回调（仅 `except` 里有个对 `_cancelled` 的死分支判断，同样永不触发）。

## 二、当前已具备的能力（循环粒度，已修复可用）

- 用户在**两轮 LLM 调用之间**取消：下一轮循环顶 `check_cancelled` 命中 → `MetaStep(cancelled)`，终态正确。
- 用户取消导致 SSE 连接断开/后台任务被硬取消：`agent_runner` 的 `except asyncio.CancelledError` 兜底 → `MetaStep(cancelled)`。

## 三、待决方案：实现流式中途打断（LLMClient.set_stop_check）

### 3.1 方案描述

1. `LLMClient` 增加 `set_stop_check(coro)` 存 `self._stop_check`；`agent_runner` 注入现有的异步回调 `_stop_check`（返回 `check_cancelled(task_id) or check_paused(task_id)`）。
2. 在流式读取循环（`request_stream` 或 `call_llm_stream`）每读取若干 chunk 后，轮询 `await self._stop_check()`；命中则抛 `asyncio.CancelledError`（或返回 cancelled chunk）中断当前生成。
3. 异常沿 `call_llm_with_fallback → _process_single_step → run_react_cycle` 上抛，被 `agent_runner` 的 `except asyncio.CancelledError` 捕获 → `MetaStep(cancelled)`。

### 3.2 利

- 取消**真正即时**：LLM 生成到一半也能立刻停，不再浪费 token/时间，UX 与主流对话产品一致。
- 终态仍然纯净：走既有的 `CancelledError → MetaStep(cancelled)` 链路，不引入新表示。
- 顺带也让**暂停（SUSPENDED）** 可在流式途中生效（stop_check 同时查 `check_paused`），弥补 HITL 之外"用户中途暂停生成"的空白。

### 3.3 弊 / 风险

- **性能开销**：每个 chunk 轮询异步回调有微小开销。必须节流（如每 8~16 个 chunk 或按时间 50ms 轮询一次），否则高并发下放大会明显。
- **资源清理**：流式中途抛 `CancelledError` 必须保证 `httpx` 连接/流被关闭，否则连接泄漏。需依赖 `async with self._client.stream(...)` 上下文在异常时正确释放，并补 `aclose` 兜底。
- **异常语义混淆**：`CancelledError` 是 `BaseException`（非 `Exception`），可能绕过部分 `except Exception` 防御，掩盖真实 bug；且需确认整条调用链对它的传播处理一致（当前 `llm_stream` 140 行 `except asyncio.CancelledError: raise` 已上抛，`agent_runner` 已接住，链路基本通，但 `call_llm_with_fallback` 的 FC 重试逻辑需复核不会把它当可恢复错误吞掉）。
- **暂停/取消区分**：stop_check 同时返回 cancelled 与 paused，若在中途对"暂停"也抛 `CancelledError`，会被误判为取消。需区分：暂停应 yield `MetaStep(paused)` 而非取消；建议中途只 abort"取消"，暂停维持循环粒度（或单独映射）。
- **回归面**：改动触及 `LLMClient`(httpx 流式) + `llm_stream` + `call_llm_with_fallback` 重试，属底层热路径，需新增单测 + **真实 LLM 的 E2E** 才能放心。
- **实现工作量**：中等，需写 1~2 个单测（mock stop_check 触发中断）+ 1 个 E2E（真实取消中途打断）。

## 四、替代方案对比

| 方案 | 取消生效时机 | 实现风险 | 用户体验 | 建议 |
|------|------------|---------|---------|------|
| A. 实现流式中断（set_stop_check） | 生成途中即时 | 中（热路径+资源清理） | 最佳 | 作为后续增强独立排期 |
| B. 循环粒度取消（已修复） | 下一轮 LLM 调用前 | 低（已合入） | 可接受（多数 LLM 调用仅秒级；长生成任务需等本轮结束） | **当前采用** |
| C. 直接取消后台任务（硬 cancel） | 即时 | 中（易丢状态/连接泄漏，且当前 agent_runner 任务并未在用户取消时被显式 cancel） | 粗暴 | 不推荐，与"解耦 SSE/后端"设计相左 |

## 五、结论与建议

- **当前已落地 B（循环粒度）**：用户取消的"终态正确性"已 100% 满足设计（不再误判 failed），风险为零，建议保留。
- **A（流式中断）值得做但不急于本次**：它是"体验优化"而非"语义正确性"问题；且触及 LLM 客户端热路径，按北京老陈"不引入回归"铁规，应单独作为一个增强项，配套单测 + 真实 LLM E2E 后再合入。
- **C 不采用**：与 agent_runner 与 SSE 解耦的设计原则冲突。
- 建议决策：**本次保持 B**；若北京老陈要求"取消必须在生成途中即时停"，则排期实现 A，我会在 `LLMClient`/`llm_stream` 加节流轮询 + 连接清理 + 暂停/取消区分 + 对应测试。
