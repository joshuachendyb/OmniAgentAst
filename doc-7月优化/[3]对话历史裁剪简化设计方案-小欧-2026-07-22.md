## 一、前言：v2.1 的教训

v2.1（`对话历史裁剪4层触发设计方案.md`）的失败原因：

| 问题 | 具体表现 |
|------|---------|
| **脱离实际场景** | 设计 4 层触发（40%/75%/200条/溢出/手动），但我们的测试全是一次性 Agent run（5~15 轮），到不了 40% 和 75% |
| **压缩阶段无用** | `_compress_observations` 对已行×列收口的 observation 几乎零收益，白增加复杂度 |
| **优先级评分 YAGNI** | error/fail 关键词评分从未被实测验证，从最新往最旧删就够了 |
| **文档代码脱节** | `_compress_observations`/`_priority_score`/4层触发已被退回，但文档还保留着 |
| **参考对象错位** | 拿多轮会话系统（OpenCode/Hermes）对标单次 Agent run，设计目标偏差 |

**结论**: v2.1 是"理论上看起来很美，实际用不上"的设计。本方案只解决当下问题。

## 二、实际场景

| 维度 | 数据 |
|------|------|
| **运行模式** | 单次 Agent run，用户发一次请求 → Agent 自行 ReAct 循环 → 返回结果 |
| **ReAct 轮次** | 5~15 轮（典型），偶见 20+ 轮 |
| **每轮 token** | system(~5K) + user(~1K) + assistant(~0.5K) + obs(1K~125K) |
| **典型 total** | 10K~150K tokens |
| **上下文窗口** | `MAX_CONTEXT_TOKENS=200K`（默认，配置可覆盖） |
| **窗口模型** | deepseek-v4-flash 窗口 900K，`agent_runner.py` 用 `llm_service.context_limit` 覆盖 |

**注意**: `OBS_READTEXT_MAX_ROWS=1000` + `OBS_READTEXT_MAX_ROW_CHARS=2000` 意味着单次 readtext 的 observation 可达 1000 行×平均 100 字符=100K chars≈25K tokens，极端情况下（每行长文本）可达 500K chars≈125K tokens。

---

## 三、设计原则

| 原则 | 原因 |
|------|------|
| **只解决当下问题** | 不预先设计用不到的功能 |
| **1 个触发条件** | 多条件在单次 run 中大部分达不到，不如集中一个 |
| **简单裁剪** | 从最旧往最新删，保尾 N 轮，不搞压缩/评分/分层 |
| **够用就行** | 只覆盖实际可能超限的场景 |

## 四、设计方案

### 4.1 触发条件（1 个）

```
粗估 tokens > MAX_CONTEXT_TOKENS × TRIGGER_RATIO
```

| 常量 | 值 | 说明 |
|------|-----|------|
| `TRIGGER_RATIO` | 0.65 | 触发比例（200K×0.65=130K 触发） |
| `TRIM_TARGET_RATIO` | 0.50 | 裁剪目标（裁剪到 200K×0.50=100K） |

**为什么 65% 触发、50% 目标？**

- 65% 触发（130K/200K）：留 35% 给 LLM 输出 + 后续轮次，实际窗口 900K 时触发线=585K，足够宽松
- 50% 目标（100K/200K）：裁剪后留一半空间给后续轮次，降低频繁裁剪
- 窗口越小（如 128K），65%=83.2K 触发、50%=64K 目标，同样合理

**为什么去掉增量触发？**

上轮精确 `total_tokens` 来自 LLM Provider usage，本轮粗估用 `chars//4`，两者计算口径不同。差值的波动大（受 JSON tool_calls、content 编码等影响），容易误触发或不触发。单条件绝对值更可靠。

**为什么去掉消息数安全网？**

单次 Agent run 5~15 轮，消息数约 20~60 条（system+user+每轮 assistant+obs）。到不了 200 条的极端值。如果真到了，token 触发条件早就先触发了。

### 4.2 裁剪策略

```
trim_history() 入口
  │
  ├── 步骤1: 快速退出（msg_count≤5 或 total≤触发线）
  │
  └── 步骤2: 裁剪阶段
       ├── 保尾: 保留最近 KEEP_TAIL_ROUNDS=3 轮完整 FC 对
       ├── 预算: 从 total 中扣除 system+user+保尾 占用量
       ├── 扫描: 从最旧往最新删 obs/assistant 消息
       └── 重建: _rebuild_and_validate → _trim_fc_pairs 清理孤儿
```

**为什么不做压缩？**

observation 已被各 formatter 的行×列收口限制（OBS_READTEXT_MAX_ROWS=1000/OBS_READTEXT_MAX_ROW_CHARS=2000 等），额外压缩零收益。等真正有多轮会话、LLM 摘要压缩的需求时再引入。

**为什么不做优先级评分？**

从最旧往最新删，天然保尾。error/fail 关键词存在于 observation 文本中（工具返回内容），不决定消息结构。要保留关键信息，保尾 N 轮足够了。

### 4.3 保尾逻辑

**KEEP_TAIL_ROUNDS=3**：保留最近 3 个完整的 user→assistant→obs FC 组。

实现方式：从消息列表末尾往前找，找到第 3 个 user 消息，之后的全部保留。这 3 轮完整保留后，从剩余部分从最旧往最新删直到满足预算。

### 4.4 关键常量

| 常量 | 值 | 位置 |
|------|-----|------|
| `MAX_CONTEXT_TOKENS` | 200000 | `constants.py`（配置可覆盖） |
| `CHARS_PER_TOKEN` | 4 | `constants.py` |
| `COMPACTION_BUFFER` | 20000 | `constants.py`（保留给溢出回退用） |
| `TRIGGER_RATIO` | 0.65 | `constants.py`（新增） |
| `TRIM_TARGET_RATIO` | 0.50 | `constants.py`（新增） |
| `KEEP_TAIL_ROUNDS` | 3 | `constants.py`（新增） |

### 4.5 配置覆盖

```
config.yaml 中 max_context_tokens: NNNNNN → 覆盖 MAX_CONTEXT_TOKENS
所有触发/裁剪比例基于此值动态计算
```

## 五、与 v2.1 对比

| 维度 | v2.1（已退回） | 本方案 v1.0 |
|------|---------------|-------------|
| **触发条件** | 5 条（40%+75%+msg200+溢出+手动） | **1 条（65% 绝对值）** |
| **压缩阶段** | `_compress_observations` | **❌ 去掉**（零收益） |
| **优先级评分** | `_priority_score` | **❌ 去掉**（YAGNI） |
| **保尾** | 正常3轮/紧急1轮 | **KEEP_TAIL_ROUNDS=3 统一** |
| **裁剪策略** | FC 配对从最新往最旧保留 | **从最旧往最新删** |
| **增量触发** | 上轮精确 vs 本轮粗估差值>20K | **❌ 去掉**（口径不一致） |
| **消息数安全网** | msg_count>200 | **❌ 去掉**（单次 run 到不了） |
| **参考对象** | OpenCode+Hermes 多轮系统 | **基于自身场景** |
| **代码符合度** | 文档超前，代码未实现 | **设计=代码** |
| **总复杂度** | 高（压缩+评分+4层+流水线） | **低（1条件+1裁剪+保尾）** |

### 6.1 代码改动

| 文件 | 改动 |
|------|------|
| `constants.py` | 新增 `TRIGGER_RATIO=0.65`、`TRIM_TARGET_RATIO=0.50`、`KEEP_TAIL_ROUNDS=3` |
| | 保留 `MAX_CONTEXT_RATIO=0.8` → 改名 `MAX_CONTEXT_RATIO` 删掉（被 TRIGGER_RATIO 替代） |
| | 保留 `COMPACTION_BUFFER=20000`（作为溢出回退预留） |
| `message_builder.py` | `trim_history` 重写：1条件触发 + 保尾 + 从最旧删 |
| | 删 `_classify_messages`（不再需要分四组，直接从 conversation_history 操作） |
| | `_trim_to_budget` 重写：从最旧往最新删 + 保尾 3 轮 |
| | 保留 `_rebuild_and_validate` + `_trim_fc_pairs` |

### 6.2 测试验证

- 构造超大 observation（如 readtext 2000 行）→ 触发裁剪 → 验证保尾 3 轮 + 重建 FC 完整
- 构造小 observation × 20 轮 → 不触发 → 验证零退化
- 边缘：msg_count ≤ 5 快速退出
