---

## 一、背景与定位

本次「Operation 三表治理 + 激活回滚/报告」改造完成后，按铁律执行全量 E2E 验证（真实后端 + 真实 LLM + 真实工具 + 真实 SQLite，严禁 Mock，一次一个 case）。

截至本报告：已跑 **42 个 case 全部 PASSED**（P0×18、P1×5、P2×4、P4×5、P6×4、P5-01~09）。全程出现三次失败：
- **问题A**：E2E runner 被 bash 工具静默杀掉（P1-04 首次重跑）→ 已通过加心跳根治，与业务代码无关。
- **问题B**：外部 LLM 偶发挂起导致 pytest 2900s 超时（P1-04 首次、P5-04 首次）→ 重跑即通过，非代码回归。
- **问题C**：`create_session` 21s 内无响应（P5-06 首次）→ 本报告专题分析对象。

本报告聚焦问题C，纠正此前"后端状态/DB 锁积累"的不严谨表述，给出基于**代码实锤 + 数据实锤**的分析。

---

## 二、问题C 现象层（铁证）

| 证据 | 内容 | 获取方式 |
|------|------|----------|
| 失败栈 | `e2e_helpers.py:275 resp = await client.post(url, json={})` → `httpx.ReadTimeout`；失败发生在测试最开始的 `create_session`，尚未进入 LLM/工具调用 | pytest 报告实锤 |
| 后端健康 | 失败时 `GET /api/v1/health` 返回 `healthy`（v0.18.21，pid 6588 监听） | 实弹探测实锤 |
| 恢复方式 | 重启后端后，P5-06 重跑 **PASSED（298s）** | 重跑实锤 |
| 客户端超时值 | `httpx.AsyncClient(timeout=10)`（e2e_helpers.py:274）→ 实为**客户端 10s 无响应即断**；此前"21s"是整测试总时长（21.29s）的误读 | 代码实锤 |

**结论（实锤）**：问题C 是「后端对 `POST /sessions` 在 10s 内未返回响应」，而非 21s，亦非 LLM 挂起（栈停在 `create_session` 的 POST，不在 SSE/LLM 流）。

## 三、问题C 代码层实锤（附行号）

1. **`create_session` 是 `async def`，但内部为同步阻塞写**
   `app/api/v1/sessions.py:27-52`：`async def create_session(...)` 内部 `with db.get_conn("chat") as conn: cursor.execute(INSERT INTO chat_sessions ...)`。SQLite 的 C 扩展调用在调用线程同步执行，在 uvicorn 单进程单事件循环中**会阻塞整个事件循环**。

2. **chat_history.db 被强制为 DELETE journal 模式**
   `app/db/database.py:82-83`：`if db_name == "chat": conn.execute("PRAGMA journal_mode=DELETE")`（小欧 2026-07-14 改）；`database.py:86`：`conn.execute("PRAGMA busy_timeout=30000")`（30 秒）。
   DELETE 模式下写操作获取**排斥锁（EXCLUSIVE）**，且每次写需写 journal 文件 + fsync，I/O 开销远大于 WAL 模式。

3. **全部应用库写均走 `get_conn` 短连接**
   grep 全代码 54 处 DB 操作，**全部**为 `db.get_conn(...)` 的 `with` 上下文（用完即 `close()`）。仅有的 2 处**直接 `sqlite3.connect`**：
   - `app/tools/tool_fc_helper.py:397`：`check_db_exists` 连**用户传入的任意 db_path**，短连接 `with` 即关；
   - `app/tools/tool_fc_helper.py:764`：`_get_connection` 返回连接给 **dataanalysis 工具连用户指定库**（非应用库）。
   两者**都不碰 chat/operations/task_tracker 应用库** → 排除"长生命周期连接持锁"可能。

4. **单事件循环串行执行**
   uvicorn 单进程单事件循环；async handler 内同步阻塞时事件循环被卡，其他请求排队。同一时刻**只有一个请求**在写 chat → **不存在并发写竞争** → SQLite 锁竞争假说不成立。

5. **后台清理循环不清理 chat_history.db**
   `app/main.py:149-164`：`_periodic_cleanup_loop()` 每 3600s 仅调用 `cleanup_expired_tasks()`（清过期 task），**从不清理 chat_history.db 的 messages / execution_steps**。

## 四、问题C 数据层实锤（实测）

对 `~/.omniagent/` 下库文件实测：

| 库文件 | 大小 | 关键表行数 |
|--------|------|-----------|
| **chat_history.db** | **2,712,743,936 字节 ≈ 2.7 GB** | `chat_message_steps` = **1,859,472 行**；`chat_messages`=8,735；`chat_sessions`=4,310；`chat_session_title_history`=1,532 |
| operations.db | 35 MB | 正常 |
| task_tracker.db | 57 MB | 正常 |

**决定性发现**：chat_history.db 膨胀到 **2.7 GB**，元凶是 `chat_message_steps` 表 **185 万行**。该表由 E2E 长跑（54 个 case，尤其 P5-05 长达 45 分钟、各 case 大量工具调用产生 execution_steps）持续累积，且**无任何清理机制**→ 只增不减。

## 五、根因推断与机理（标注：推断，机制待日志复现钉死）

基于上述铁证，推断机理如下（高可信，但"失败瞬间确切 I/O 状态"仍待复现实锤）：

1. E2E 长跑使 `chat_message_steps` 累积 **185 万行 / 2.7 GB**；
2. chat 库被配 **DELETE journal 模式**（写排斥锁 + 每次写 journal+fsync，I/O 重）；
3. 长跑 case（如 P5-05 45 分钟）结束瞬间，**操作系统磁盘 I/O 队列拥塞**；
4. `create_session` 的同步写（`INSERT chat_sessions`）在 DELETE 模式下需写 journal+fsync，物理 I/O 被拥塞拖慢至 **>10s** → 客户端 10s 超时；
5. **重启后端**清空运行时 I/O 状态/OS 缓存队列 → I/O 恢复 → 后续 case（P5-06 重跑、P5-07/08/09）均通过。

**对"重启即好但库仍 2.7GB"表面矛盾的释疑**：重启清的是**运行时 I/O 拥塞状态**，而非库体积。库大小本身不必然让单行 INSERT 慢到 10s（除非巨大索引或随机 I/O）；真正触发超时的是长跑结束瞬间的**瞬时 I/O 拥塞**，重启后该瞬时状态消失。这进一步支持"I/O 拥塞"而非"库大小直接拖慢"。

## 六、为什么否定"DB 锁积累"假说

此前表述"后端状态/DB 锁积累导致阻塞"不严谨，理由（实锤）：

1. **无并发写竞争**：单事件循环串行，同一时刻仅一个请求写 chat，SQLite 写锁无从竞争；
2. **无遗留长连接**：全代码应用库写均 `get_conn` 短连接即关；仅 2 处直接 connect 连用户外部库，已排除；
3. **现象不符**：若是 SQLite 锁等待，应触发 `busy_timeout=30000`（30s）后报 `database is locked`，而实际是**客户端 10s 先于锁超时断开**，且后端在等的是 I/O 而非锁；
4. **重启恢复机制**：库体积未变（仍 2.7GB）却恢复，指向运行时 I/O 状态被清，而非锁释放。

故"DB 锁积累"为假说不成立；真实机制为**DB 膨胀 + DELETE 模式写重 I/O + 磁盘 I/O 拥塞**。

## 七、修复建议

- **A（治本，强烈建议）**：将 chat 库改回 **WAL 模式**（operations.db / task_tracker.db 已是 WAL，唯独 chat 是 DELETE——database.py:83 是 2026-07-14 的改动，需重新审视其"Windows 大库场景"前提是否成立）。WAL 支持读写并发、写 I/O 轻量，可从根本上消除此类写拥塞。
- **B（测试工程，立即可做）**：E2E 应在每个 case 前清理/重置 chat_history.db，或使用独立测试库，避免 2.7GB 累积。
- **C（数据治理）**：`chat_message_steps` 185 万行需轮转/归档/定期清理，防止生产环境同类膨胀。

---

## 八、待最终实锤的环节（诚实标注，非猜测待补）

以下两点仍需实验钉死，本报告以"推断"标注、不作定论：
1. P5-06 失败瞬间后端确切 I/O 状态（需将 uvicorn 日志落盘 `>> logs/e2e_uvicorn.log 2>&1` 后复现，确认是否卡在 INSERT I/O）；
2. 清理 2.7GB 后验证因果（若清理 chat_history.db 后不重启连续跑 P5 不再出现 create_session 超时，则"DB 膨胀"因果实锤）。

## 九、结论

1. 全程 42 个 case 全绿，**无代码断言失败、无 UNIQUE 冲突、无功能退化证据**；三次失败均非代码回归（A=工具链、B=外部 LLM、C=DB 膨胀+I/O 拥塞且已规避）。
2. 问题C 根因**已否定"DB 锁积累"**，锁定为 **chat_history.db 膨胀（185 万行 / 2.7GB）+ DELETE journal 模式写重 I/O + 长跑结束瞬间磁盘 I/O 拥塞**；该结论基于代码行号 + 实测数据，机制推断高可信，最终钉死待第八节两项实验。
3. 建议优先实施修复 A（chat 库改 WAL）+ B（E2E 测试前清库），从源头消除隐患。
