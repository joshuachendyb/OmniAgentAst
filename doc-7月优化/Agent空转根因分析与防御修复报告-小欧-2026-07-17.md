## 二、根因分析（实锤，读代码+日志，非凭印象）

### 2.1 根因①：searchweb 结果 url 被 `_format_items` 丢弃（设计缺陷，非退化）

- 位置：`backend/app/services/agent/observation_formatter.py` `_format_items`（约 587-590 行）
  ```python
  if desc: out.append(desc)
  elif url: out.append(url)   # 有 snippet/desc 时，url 被 elif 吞掉
  ```
- `search_web.py` 原始返回字段：`title / url / snippet / source`（分别在 150 / 207 / 280 / 299 行构造），**数据本身含 url**。
- git blame：`8946a36da9`（小沈 2026-07-10）起即 `if desc/elif url` 二选一，**是设计缺陷，不是近期退化**。
- 后果：LLM 在 step=3 收到的 observation 只有 `title + snippet + source`，**拿不到 url**，于是 reasoning 里反复"需要URL→没有→重新搜索"，形成死循环。

### 2.2 放大器：reasoning-only 分支无重复治理、无连续上限（空转驱动器）

- 位置：`answer_handler.py` reasoning-only 分支（原 line 111）
  ```python
  if not content and reasoning:
      agent.message_builder.add_assistant_message(reasoning)  # 原样注入，无去重、无限继续
      yield ThoughtStep(...)
      return
  ```
- 该分支 `return` 跳过下游 L1-C2b 重复检测（L1-C2b 仅对 `final` 的 `content` 生效，对 reasoning 不处理）。
- step=3 reasoning 单次生成内高频重复（据 prompt-logs 统计：`重新搜索`×213、`URL`×643、`让我先`×416、`fetchpage`×142、`需要URL`×70），全部原样注入 history，每轮再被 LLM"看见"后继续循环。
- `max_steps=100` 远未触发（实际 llm_calls=11），故无兜底止损。

### 2.3 对"B3 正反馈放大"论断的修正（重要偏差纠偏）

- 初判曾认为 `react_cycle.py:260` 的 B3（"LLM 返回 answer 但未调用任何工具"注入警告）与 reasoning-only 形成正反馈放大空转。
- **重新核查 B3 触发条件**：要求 `type=="answer" and content and not has_tool_results`，即 **content 必须非空**。
- reasoning-only 空转的 `content` 为空 → **B3 根本不触发**。
- 有 `content` 的 answer（如 step=11，29373 字）走 `answer_handler.py:119` 正常路径 → `FinalStep` **终态**，不循环；B3 警告虽注入 history 但任务已结束，无循环影响。
- **结论修正**：B3 与本次 reasoning-only 空转无关；真正的放大器是 **2.2 的 reasoning-only 分支（无去重 + 无连续上限）**。

## 三、修复方案与实施

### 3.1 根因①修复（提交 a0cb2e7a7，分支 feature/agent-optimization-18.1）

- 文件：`observation_formatter.py` `_format_items`
- 改法：desc 与 url **并存输出**（有 snippet/desc 时也附 `URL: {url}`），LLM 可拿到 url 去 `fetchpage`。
- 验证（临时脚本）：`_format_items` 三种情况（url+摘要 / 仅摘要 / 仅 url）均保留 url，零退化。

### 3.2 空转防御 A 增强版（提交 9c3dc5062，B 方案不做）

设计原则（符合 10 大规范，尤其 KISS-DIRECT / 防御增强不退化正常流程）：

- **仅在纯 reasoning-only 分支累加计数**：`_consecutive_reasoning_only += 1`。
- **正常任务永不触发**：正常 LLM 每轮给 `answer`(content 非空) 或 `action`(tool_call)，**不进 reasoning-only 分支，计数恒 0，完全不受影响**（已逐路径复核）。
- **重复剔除**：reasoning 先 `_dedup_repeat(reasoning)`（复用 L1-C2b 同函数，原样重复 >50% 截断），压缩 history，减少触发 `trim_history` 的风险。
- **连续上限终止**：达 `REASONING_ONLY_MAX_ROUNDS`（默认 **3**，可调常量；2 更激进、3 更宽松防误伤）即 `yield FinalStep`（"模型反复思考未产出有效结果，任务已终止（疑似陷入无效循环）"）终止，切断退化空转。
- **归零点**（防御残留误累计）：
  1. `action_handler.py`：本步 LLM 发起工具调用（execute_tools 后）→ 归零
  2. `answer_handler.py`：正常 final answer（content 非空）路径起始 → 归零
  3. `answer_handler.py`：真空 retrying 分支（content+reasoning 均空，非 reasoning 空转）→ 归零
- `react_cycle.py` **未改动**（reset 已在终端 handler 完成，符合 KISS 不多改）。
- 改动文件（均含头部编辑历史 # 记录，署名+日期+概要）：
  - `backend/app/services/agent/handlers/answer_handler.py`（加常量 + 分支改造 + 两处归零）
  - `backend/app/services/agent/handlers/action_handler.py`（调工具后归零）
  - `backend/app/services/agent/base_agent.py`（加 `_consecutive_reasoning_only` 字段）

### 3.3 B 方案评估（冗余，老陈确认不做）

- B 方案原拟消除 B3 正反馈；但 2.3 已证 B3 对 reasoning-only(content 空) 不触发、有 content 已终态不循环 → **B 在当前架构下无独立价值，冗余**。仅做 A 增强版。
