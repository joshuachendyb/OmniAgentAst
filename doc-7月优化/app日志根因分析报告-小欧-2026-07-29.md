## 三、问题一：ERR_SHELL_EXEC — Shell命令执行失败（165次）

### 3.1 现象

Linux命令在Windows cmd/ps7中执行失败，典型失败命令：

| 失败命令 | 错误信息 | 根因 |
|---------|---------|------|
| `mkdir -p E:\test_dir\...` | `-p`被当目录名 | Linux语法在cmd中 |
| `find . -name "*.py" \| head -30` | `head`命令不存在 | Linux命令 |
| `python3 -c "..."` | 命令未找到 | Windows用`python`非`python3` |
| `cd /E/test_dir && python ...` | 路径格式错误 | Linux路径格式 |
| `python3 << 'PYEOF'` heredoc | 语法错误 | PS5不支持heredoc |

### 3.2 根因分析（5层递进）

**根因1 — LLM训练数据偏重Linux（第1层）**
- LLM训练数据中以Linux命令居多
- 在Windows环境中仍持续输出`python3`、`mkdir -p`、`find | head`等Linux语法
- 系统没有在LLM生成环节做平台感知

**根因2 — shell_type默认值"ps7"不是错误选择（第2层，代码级）**
- ⚠️ **三堂会审修正**: 原报告说"应默认bash"，但 `get_default_shell_code()`（`system_adapter.py:107-115`）已实现平台检测：Windows有pwsh→ps7、无pwsh→ps5、非Windows→bash
- shell()函数默认"ps7"(L593)与检测结果一致——Windows+pwsh本就应该默认ps7
- **本质问题不是默认shell_type选错**，而是LLM生成Linux命令无论哪个shell_type都会失败：
  - ps7下：`mkdir -p`的`-p`被当目录名
  - bash下：`find | head`的`head`在Git Bash可能不存在
  - cmd下：`python3`不认识
- 改默认shell_type只是"换一个地方摔跤"，真正要治的是**命令翻译**

**根因3 — shell_type='cmd'时LLM仍传Linux命令，语法修复不全（第3层，代码级）**
- 即使LLM指定了`shell_type='cmd'`，传入的依然是`mkdir -p`等Linux语法
- `_auto_fix_cmd_syntax()`（execute_shell_command.py:502-513）只修了`$env:VAR→%VAR%`
- 没有覆盖Linux→Windows的命令翻译（如`mkdir -p`→`mkdir`、`find`→`dir /s`、`head`→PowerShell `Select-Object -First`）

**根因4 — `_shell_mismatch_hint()`只给提示不自动修复（第4层，代码级）**
- 文件: `execute_shell_command.py:488-499`
- 检测到命令不匹配时只返回hint字符串给LLM
- hint被放在`llm_data.status.hint`中返回给LLM
- 但LLM下次依然生成同样的Linux命令，没有收敛效果

**根因5 — python3的bash自动修复在其他shell_type下不生效（第5层，代码级）**
- `_auto_fix_bash_syntax()`（execute_shell_command.py:533-544）只在`shell_type="bash"`时执行
- 当LLM传`shell_type='cmd'`但命令含`python3`时，不会被修复
- `_auto_fix_cmd_syntax`也没有覆盖`python3→python`替换

### 3.2.1 系统防御链评估（容错维度）

当前系统对LLM生成错误命令的防御从前往后共8层，逐层评估：

| 防御层 | 位置 | 做了什么 | 覆盖 | 判定 |
|--------|------|---------|------|------|
| **L1 System Prompt** | `system_adapter.py:118-129` | 告诉LLM"【系统】Windows"+路径规则 | 告知OS但不禁止Linux语法 | ⚠️ 弱告警 |
| **L2 Schema描述** | `fundamental_schema.py:83-84` | command字段写"禁止使用python3" | 只禁python3 | ⚠️ 极弱 |
| **L3 TOOL_CALL_RULES** | `system_prompts.py:91-92` | `render_shell_section()`注入shell语法指引 | 只讲PS语法规则，无Linux对照 | ⚠️ 弱 |
| **L4 语法自动修复** | `execute_shell_command.py:651-666` | 三路修复：PS修.Property、CMD修$env:VAR、bash修python3 | 覆盖3种模式，无Linux→Windows翻译表 | ❌ 极窄 |
| **L5 安全检查** | `execute_shell_command_safety.py` | 拦rm -rf/格式化/关机等高危，不检查Linux语法 | 安全正确，语法不触发 | ⚠️ 不是本题范围 |
| **L6 执行路由** | `shell()` L682-760 | 四路正确路由到对应shell | 执行逻辑正确 | ✅ 正确 |
| **L7 失败后hint** | `_shell_mismatch_hint()` L488-499 | stderr含"not recognized"时提示换shell | 事后诸葛亮，mkdir -p不触发 | ❌ 被动 |
| **L8 错误detail标注** | `shell()` L811-817 | 加`[命令未找到]`/`[语法错误]`前缀 | 只标注不修复 | ⚠️ 被动 |

**关键发现**：L1-L4是主动防御，但覆盖极窄；L5-L8是被动响应。**最大的缺口是L4——没有bash特征检测→自动路由到Git Bash**。

```
            → cmd/bash/ps7三路都不拦截Linux语法
                → 执行失败 → 给hint让LLM自己改（永远改不好）
```

### 3.5 病根判定

| 维度 | 判定 | 依据 |
|------|------|------|
| **诱因** | LLM问题（占30%） | LLM训练数据偏Linux，输出`mkdir -p`、`python3`、`find \| head`等Linux命令 |
| **主因** | 系统Bug（占70%） | ⚠️ **三堂会审修正**: 根因2"shell_type默认ps7错误"→修正为"默认ps7正确(`get_default_shell_code()`已检测平台)"，但L4翻译层缺失、L7 hint被动、L3-L4覆盖率极低是核心缺陷 |
| **结论** | **混合问题** | LLM生成Linux命令是触发条件，但系统应当在执行前检测bash特征→自动路由到Git Bash（无需翻译表，Git Bash原生理解这些命令）——缺了这个关键环节 |

### 3.6 解决方案（准确·有效·可扩展）

**方案A（推荐·KISS-DIRECT）—— bash特征检测→自动路由到Git Bash**
- 在 `shell()` 阶段1.7之后（L666）、安全检查之前（L668），增加一段检测逻辑：

```python
# ── 阶段1.8【通用】: bash特征检测→自动路由（KISS-DIRECT，不翻译）
_BASH_PATTERNS = [
    r'\bmkdir -p\b', r'\bfind\b.*-name', r'\bgrep\b',
    r'\bhead\b', r'\btail\b', r'\bchmod\b', r'\bpython3\b',
    r'\bpip3\b', r'\bapt\b', r'\bwget\b', r'\bcurl\b.*-o\b',
]
if shell_type != "bash" and _find_bash():
    for pat in _BASH_PATTERNS:
        if re.search(pat, processed_command):
            logger.info(f"[Shell] 检测到bash语法,自动路由到Git Bash: cmd={cmd_short}")
            shell_type = "bash"
            processed_command = processed_command.replace('\\', '/')
            processed_command = re.sub(r'\bpython3\b', 'python', processed_command)
            break
```

**为什么这比翻译表好：**

| 对比 | 翻译表（旧方案） | 自动路由（新方案） |
|------|---------------|------------------|
| 原理 | 把Linux命令翻译成PS/CMD | 让Linux命令在Git Bash原生执行 |
| 覆盖 | 每条规则手工映射，漏一条就崩 | Git Bash原生理解数千条Linux命令 |
| 维护 | 越来越多规则 | 不需要新规则 |
| `find \| head` | 要写两个翻译规则 | Git Bash原生支持 |
| `mkdir -p a/b/c` | 翻译成`mkdir a\b\c`（父目录不存在时cmd::mkdir `-p`→当目录名） | Git Bash原生支持 |

**方案B（辅助）—— `\`→`/` 路径格式转换**
- Git Bash下反斜杠`\t`被解释为制表符（`E:\test_dir`→`E:	est_dir`）
- 如果shell_type转为bash，必须做机械式`\`→`/`转换：
  ```python
  if shell_type == "bash":
      processed_command = processed_command.replace('\\', '/')
  ```
- **只转换路径分隔符，不做语义翻译**——所以不是翻译表，是格式转换

**方案C（LLM侧）—— 注入平台提示**
- system prompt首行注入：`"你运行在 Windows 环境，所有shell命令必须使用Windows语法（cmd或PowerShell），禁止Linux/Unix命令"`
- 降低LLM生成Linux命令的概率（但不可靠，LLM仍然会出错）

**方案D（降级·fallback）—— 无bash时用命令翻译表**
- 仅在 `_find_bash()` 返回None时启用（如无Git Bash/WSL的环境）
- 使用旧方案A的翻译表（`mkdir -p`→`mkdir`、`find`→`dir /s`等）
- 优先级：**自动路由(bash) > 翻译表(fallback)**
- 降低LLM生成Linux命令的概率（但不可靠，LLM仍然会出错）

## 四、问题二：ERR_SHELL_TIMEOUT / ERR_TIMEOUT — 命令超时（83次）

### 4.1 现象

- 同一session `b5b5938d` 从01:04到02:00连续9次Python文件遍历脚本超时

### 13.4 BUG-2 修复设计思路（保险丝三路取值 + schema 默认兜底）

> 编写人：小欧 2026-08-05 22:17（v6.2 修正 inner 取值：原则3 由"与 base 取 max"改为**直接用 schema 默认值**，tool 值优先；原则4 明确取 max）
> 状态：**已实现（代码已落盘），待老陈审核通过后再提交。**
> 定位（老陈 2026-08-05 澄清）：本保险丝是 **toolretry 引擎的外部超时**（asyncio.wait_for 掐整个工具调用），**不是工具自身的内部超时**。故保险丝必须恒 ≥ 工具内部超时，`max(inner, CEILING)+BUFFER` 的 CEILING 托底（即使 LLM 传 300 也托到 630）是**正确设计**，不是"没用 LLM 的值"——它是保证外部超时恒大于工具内部 300s deadline 的安全兜底。
>
> 两条超时线（老陈 2026-08-06 10:05:21 梳理，与代码注释一致）：
> - **① 传给 tool 的超时（tool 内部执行用）**：随 `params` 原样传给 `tool(**params)`。有 timeout 参数工具：LLM 显式传 → **直接用 LLM 给的值**（经 `_validate_params` clamp ge/le）；LLM 未传 → **tool 用自己函数（schema）的默认值**。无 timeout 参数工具：tool 无内部超时概念，靠外部 wait_for 截断。
> - **② 保险丝超时（asyncio.wait_for 掐整个 tool 调用）**：由 `_compute_fuse` 计算，见上文两分支。
> - ★ 两值独立：传给 tool 的值 ≠ 保险丝值。例：LLM 传 `timeout=300` → tool 内部实际收 300，但保险丝 = `max(300,600)+30` = **630**（托底恒 ≥ 内部超时）。

#### 13.4.1 老陈给出的四条取值原则

| # | 场景 | 取值来源 |
|---|------|---------|
| 1 | 无 timeout 参数 → LLM 必然不能给 | 表里参数 或 default |
| 2 | 有 timeout 参数 + LLM 显式赋值 | 用 LLM 给的参数 |
| 3 | 有 timeout 参数 + LLM 未赋值 | **直接用 schema 默认值（tool 的 timeout 值优先）**；default 仅当 schema 无 timeout 参数时兜底走渐进 |
| 4 | 有 timeout 参数 + LLM 赋值但超 CEILING | **取 max**：`max(inner, CEILING)+BUFFER`，"inner 超 600 则随它去"（有 inner 分支内部的边界，注释已有） |

#### 13.4.2 关键事实核对（决定修复形状）

- 引擎在 `_validate_params` 已能拿到 schema（`tool_registry.get_tool(action).input_schema`）→ 同一途径可读 timeout 默认值，**无需新依赖**（DRY/复用）。

- 工具的**内部真实超时 = schema 默认值**。修复前 LLM 未传时保险丝 `min(60*(n+1),300)=60` 可能小于内部超时 → 截杀（compress=300 铁证）。

#### 13.4.3 实现方案（KISS-DIRECT，两 helper 收敛三路）

新增两个方法（`tool_retry_engine.py`），并让 `try_once` 与 `_execute_with_retry` 两处重复的保险丝分支收敛到 `_compute_fuse`（消除 DRY 违规）：

```python
def _get_schema_timeout_default(self, action):  # 读 schema timeout 默认值；无则 None
    metadata = tool_registry.get_tool(action)
    ... spec = metadata.input_schema["properties"].get("timeout")
    return int(default) if default>0 else None

def _compute_fuse(self, action, params, base_timeout, attempt):
    inner = params.get("timeout")
    if not (isinstance(inner,(int,float)) and inner>0):        # LLM 未传
        sd = self._get_schema_timeout_default(action)
        if sd is not None:
            inner = sd                                          # 原则3: 直接用schema默认(tool值优先)
    if isinstance(inner,(int,float)) and inner>0:               # 有 inner(含兜底)
        return max(int(inner), INSURANCE_CEILING) + INSURANCE_BUFFER   # 原则4: 取max
    return min(base_timeout*(attempt+1), PROGRESSIVE_MAX)       # 原则1: 无 timeout 参数→渐进
```

- 原则 2（LLM 传值）天然由 `inner = params.get("timeout")` 命中；原则 4（取 max）由有 inner 分支的 `max(inner,600)+30` 命中。
- 原则 3 用 **schema 默认值直接作为 inner**（tool 的 timeout 值优先），不做与 base 的 max/min 比较——避免 `min` 在 schema 默认>base 时丢弃 tool 真实值（如 schema 默认=1800、base=60 时若取 min 得 60，保险丝 630 反小于内部 1800 截杀）。
- `tool_registry.get_tool(action)` 与 `_validate_params` L250 同途径，无新增 import（DRY）。

| compress | 未传 | 60（截杀 ✗） | **630** | BUG-2 修复 ✓ |
| compress | timeout=300 | 630 | 630 | 不变 ✓ |
| compress | timeout=1800 | 1830 | 1830 | 原则4 取max，超600随它去 ✓ |
| shell/httpget/download/fetchpage/ping_port | 未传 | 60（可能截杀 ✗） | 630 | 一致性纠正 ✓ |
| httpget | timeout=30 | 630 | 630 | 不变 ✓ |
| listdir（无 timeout 参数） | 未传 | 60/180（渐进） | 60/180 | 不变 ✓ |

#### 13.4.5 为什么"不退化"（对既有工具的关联影响）

- **有 timeout 参数工具**（compress/shell/httpget/download/fetchpage/ping_port）：内部真实超时即 schema 默认值（300/60/30/60/30/5），修复后保险丝恒覆盖内部超时 → 不再被截杀。这些工具内部到点会自己抛 TIMEOUT 分类错误，保险丝 630 仅是兜底上限，正常流程内部先返回，不会真等满 630。这是从"可能截杀"纠正为"恒安全"，**功能只增强不退化**。
- **无 timeout 参数工具**（listdir/delete/find 等）：走原则 1 渐进路径，`_compute_fuse` 第 3 路与修复前完全一致（`min(base*(n+1),300)`），**行为零变化**。
- `ping_port` 同日已移出 `TOOL_TIMEOUTS`（设计一致性，见第十二章相关），移出后其 LLM 未传时走原则 3（schema 默认 5 → 保险丝 630），恒覆盖内部 5s，安全。

#### 13.4.6 BUG-2.5（新增发现, 2026-08-05 22:58）：compress `timeout` 缺 Field ge/le 约束, 内部 `timeout-2` deadline 过去 → 拿不到压缩信息

> 编写人：小欧 2026-08-05 22:58

##### 病根

- `file_schema.py:297`: `timeout: int = Field(default=300, description="...5-1800秒...")` —— **description 写 5-1800, 但 Field 没有 ge/le 约束**。
- `tool_retry_engine._validate_params`（L328-339）依据 `spec.get("minimum/maximum")` 做 clamp — compress timeout spec **无 min/max** → **clamp 完全失效** → LLM 傉 `timeout=1/-5` 不钳直塞 internal。
- compress 内部 L311-313: `_cf_timeout = timeout; _local_deadline = start + _cf_timeout - 2` —— LLM 传 timeout=1 → `_local_deadline = start - 1` (過去) → `_get_total_size_sync`/`_write_zip` 立即判定 timed_out → `compressed_files=[]` → **拿不到压缩成果** (拿不到信息的另一个根源, 與 BUG-2 同根)。

##### 验证（运行时, 2026-08-05 22:58）

- LLM 传 `timeout=1` (目前無 ge) → internal `_local_deadline` 过去 → 立即 timed_out, `compressed_files=[]`, observation "压缩超时" 但**未拿到压缩档** → **拿不到信息**。

##### 修复 (合规合理, SRP 单一职责: schema 约束)

- `file_schema.py` CompressInput.timeout **加 `ge=5, le=1800`** —— 实施 `description` 意图, 使 clamp 生效:
  - LLM 传 0/1/-5 → **clamp 到 5** → internal deadline ≥ start+3 (≥3s, 安全)
  - LLM 传 99999 → **clamp 到 1800** → 保险丝 1830 > internal 1798 ✓
- ge=5 + internal `-2` buffer: 保险丝 630 (LLM 未傳, principle 3) > internal 298; LLM 傳 T (5≤T≤1800) → 保险丝 `max(T,600)+30`, internal `T-2`, **margin 恒 ≥32s**:
  - T≤600: 保险丝 630, internal ≤598, margin ≥32s
  - T>600: 保险丝 T+30, internal T-2, margin = 32s
- **增强不退化**: 僅縮小非法輸入接收範圍 [無约束]→[5,1800]; 合理輸入 300(默認)/60(LLM 傳) 完全不受影響。

##### 影響 / 與其他修复之关联

- 與 BUG-2 (保险丝) 互补: BUG-2 修 "engine 保险丝 < internal 被截殺"; BUG-2.5 修 "schema 無约束 → LLM 傳過小值 internal 立即掛"。兩個一起才完整圍住"拿不到压缩信息"。
- 與 BUG-3 (clamp `number`) 同機制: BUG-3 修 clamp 漏 number 类型; BUG-2.5 補 `compress timeout` 的 ge/le, 讓 clamp 能作用在它。

#### 13.4.7 遗留观察（不构成 bug，供老陈决策）

- 有 inner 分支 CEILING=600 意味着有 timeout 工具保险丝下限 630s。对内部超时小的工具（如 ping_port=5）"偏大"，但内部会先返回，故无实际影响；如需收紧需改 CEILING 设计（超出本次 BUG-2 范围）。
