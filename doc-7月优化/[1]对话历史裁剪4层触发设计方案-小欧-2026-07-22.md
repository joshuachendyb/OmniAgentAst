## 一、设计背景

### 1.1 问题

对话历史随轮次增长持续膨胀，最终超出 LLM 上下文窗口。原 `trim_history` 只有两个条件：

- **条件1（轮次）**: 消息数 > 202 条 → 保留最近 100 轮（几乎从来不触发）
- **条件2（字符）**: total > 160K chars → 从最新往最旧扫，预算 140K chars，超了就丢弃

**缺点**: 触发太晚（160K 才动作）、无保尾机制、无重要性区分、无前置轻量压缩、无溢出回退

### 1.2 参考系统

| 系统 | 版本 | 参考内容 |
|------|------|---------|
| **OpenCode** | GitHub 开源 | 触发: 主动溢出检测 + overflow 回退 + 手动/compact<br>裁剪: prune(旧tool输出占位符) + select(分head+tail) + process(LLM摘要) + filterCompacted(重组) |
| **Hermes** | GitHub 开源 | 触发: Preflight(50%) + HTTP413 + context overflow + Gateway Hygiene(85%/400条) + 手动/compress<br>裁剪: should_compress(防抖) + _prune_old_tool_results + _generate_summary(LLM结构化摘要) + _sanitize_tool_pairs |

详见代码文件 `message_builder.py` 头部注释。

## 二、设计原则

| 原则 | 说明 |
|------|------|
| **零 LLM 成本** | 所有裁剪操作纯字符串处理，不调用 LLM |
| **保尾机制** | 最近 N 轮 FC 对完整保留，不被裁剪 |
| **分区域处理** | head(system+user) 不可裁，tail(最近 N 轮) 完整保留，middle(旧历史) 智能压缩 |
| **优先级保留** | 含 error/fail/批准 等关键词的消息提高保留权重 |
| **分层触发** | 轻量压缩先做，重度裁剪后做，溢出回退兜底 |

## 三、核心概念厘清：压缩 vs 裁剪

### 3.1 定义区别

| 维度 | 压缩 (Compression) | 裁剪 (Truncation) |
|------|-------------------|-------------------|
| **操作对象** | 消息的内容(content) | 消息本身(整条丢弃) |
| **操作方式** | 替换、精简、摘要 | 移除 |
| **消息条数** | 不变 | 减少 |
| **信息状态** | 有损但核心保留 | 完全丢失 |
| **OpenCode** | prune(tool output占位符)+process(LLM摘要) | 无(全用压缩) |
| **Hermes** | _prune_old_tool_results+_generate_summary | 无(全用压缩) |

### 3.2 什么时候用哪个

**任何时候都先压缩，压缩后还超预算再裁剪。**

```
总历史体积 > 阈值
  │
  ├── 压缩阶段（消息数不变）
  │   旧 tool observation → 一行摘要
  │   assistant 决策消息完整保留
  │   → 重新计算体积
  │      ├── 已低于阈值 → 完成（只压缩不裁剪）
  │      └── 仍高于阈值 → 进入裁剪
  │
  └── 裁剪阶段（消息数减少）
       保尾 N 轮完整保留
       中间区: 优先级保留
       最后手段: 丢弃剩余
```

**具体场景判断原则**：

| 场景 | 应用 | 原因 |
|------|------|------|
| tool observation 过长 | **压缩** | 核心信息在 assistant 决策中，observation 可精简 |
| assistant tool_calls 过大 | **压缩** | 参数 JSON 可截断(Hermes Pass 3 做法)，不丢决策 |
| 多轮相同的 tool 调用 | **压缩** | 去重保留最新(Hermes Pass 1 做法) |
| 早期轮次无关键决策 | **裁剪** | 信息已无价值，可直接丢弃 |
| 早期轮次含关键决策 | **压缩** | 保留 assistent 决策，压缩 tool obs |
| 历史体积轻微超限 | **只压缩** | 压缩后大概率已达标 |
| 历史体积严重超限 | **压缩→裁剪** | 先压缩再裁剪，双重降体积 |

### 3.3 为什么 OpenCode/Hermes 只用压缩不用裁剪

深入源码发现：**OpenCode 和 Hermes 都没有"丢弃整条消息"的操作**。它们通过两层压缩来解决体积问题：

1. **廉价压缩**（Prune）：不调 LLM，替换 tool output 为占位符/摘要
2. **LLM 压缩**（Summary）：调 LLM 对旧历史做结构化摘要

两个系统只在 `_sanitize_tool_pairs` 中删除孤儿配对（技术修复，非裁剪手段）。它们的高明之处在于——**压缩可以还原（有限回溯），裁剪不可逆**。

但我们的场景不同：我们没有 LLM 摘要这步，所以当压缩后体积仍然超限时，必须裁剪（丢弃部分消息）。这是合理的设计选择。

## 四、触发条件设计

### 4.1 检测单位：chars → tokens

**结论：直接改为 token 估算，零成本零依赖。**

OpenCode 和 Hermes 的 token 估算都只是纯数学除法，没有任何外部 tokenizer 依赖：

| 系统 | 核心实现 | 代码量 | 外部依赖 |
|------|---------|--------|---------|
| **OpenCode** | `util/token.ts`: `Math.round(input.length / 4)` | 7 行 | **无** |
| **Hermes** | `model_metadata.py`: `(len(text) + 3) // 4` | 10 行 | **无** |
| **本方案** | `_estimate_tokens()`: `total_chars // 4` | 3 行 | **无** |

OpenCode 和 Hermes 的 token 估算全部是纯数学运算——因为**压缩决策只需要相对大小比较，不需要精确 token 计数**。真实 token 数来自 LLM Provider 返回的 `usage` 字段（用于计费展示），从不用在决策路径上。

**具体做法**：
- 新增 `_estimate_tokens()` 方法：`return self._total_chars() // 4`
- `MAX_CONTEXT_CHARS` → `MAX_CONTEXT_TOKENS`，不变值只改语义：200K chars → **200K tokens**
- 触发条件：40%(80K) / 75%(150K) / 安全网 200 条
- `_total_chars()` 方法保留（供 `_estimate_tokens()` 底层调用）

**为什么改**：语义一致性。"历史占 75% 上下文窗口"比"历史占 75% 的 200K chars"直观得多，与 OpenCode/Hermes 对标也更直接。

### 4.2 触发条件分析

**当前 2 个条件的问题**：
- 条件1（消息数 > 202）：阈值过高，几乎永远不触发
- 条件2（total > 160K chars，80%）：唯一生效条件，但触发偏晚（留余量太少）

**对照 OpenCode/Hermes**：

| 系统 | 条件A(前置) | 条件B(核心) | 条件C(安全网) | 条件D(回退) | 条件E(手动) |
|------|------------|------------|-------------|------------|------------|
| OpenCode | ❌ | ≈100%(context-reserved) | ❌ | ✅ overflow | ✅ /compact |
| Hermes | ✅ 50% | 50% (同条件A) | ✅ 85%/400条 | ✅ 413+overflow | ✅ /compress |
| **本方案 v2** | **✅ 40%** | **✅ 75%** | **✅ msg_count>200** | **🔲 预留** | **🔲 预留** |

**5 个条件的各自定位**：

| 条件 | 阈值 | 触发时行为 | 目的 |
|------|------|-----------|------|
| A: 前置压缩 | total > 80K tokens (40%) | 仅压缩( _compress_observations ) | 提前释放空间，不急刹 |
| B: 核心裁剪 | total > 150K tokens (75%) | 压缩→裁剪流水线 | 主触发条件，留 25% 给 LLM 输出 |
| C: 消息数安全网 | msg_count > 200 | 紧急裁剪(保尾1轮) | 防止极端长会话 |
| D: 溢出回退 | HTTP 413/overflow | 紧急压缩→重试[预留] | 兜底防止崩溃 |
| E: 手动触发 | 用户指定 | 按需压缩[预留] | 用户主动管理 |

**关键优化说明**：
- 条件B从原来的 160K chars(80%) → **150K tokens(75%)**：提前触发，留 25% 输出缓冲区
- 条件C从 202 条降到 **200 条**：保持不变，作为极端安全网
- 条件A从原来的 100K chars(50%) → **80K tokens(40%)**：尽早做轻量压缩，对标 Hermes 的 Preflight(50%)
- `MAX_CONTEXT_CHARS=200K` → `MAX_CONTEXT_TOKENS=200K`：值不变只改语义，从 chars 纠正为 tokens

### 4.3 压缩→裁剪流水线

整个 trim_history 的执行逻辑是**"先压缩后裁剪"二阶段流水线**，而非之前的独立分层触发：

```
trim_history() 入口
  │
  ├── 步骤1: 快速退出 (msg_count ≤ 5)
  │
  ├── 步骤2: 压缩阶段（条件A 或 条件B+C 时执行）
  │   └── _compress_observations()
  │       旧 tool observation → 一行摘要
  │       消息数不变，体积缩小
  │   └── 重新计算 total
  │
  ├── 步骤3: 判断是否仍超限
  │   ├── total < 150K tokens 且 msg_count ≤ 200 → 完成（只压缩不裁剪）
  │   └── 仍超限 → 进入裁剪阶段
  │
  └── 步骤4: 裁剪阶段（条件B 或 条件C 时执行）
      └── _trim_to_budget(tail_protect=True)
          保尾 3 轮 → 优先级保留 → 预算从最新往最旧扫
      └── _rebuild_and_validate()
```

### 4.4 各条件触发的具体行为矩阵

| 触发条件 | 压缩阶段 | 裁剪阶段 | 保尾轮数 |
|---------|---------|---------|---------|
| 仅条件A (total∈[80K,150K) tokens) | ✅ 执行 | ❌ 跳过 | — |
| 条件B (total≥150K tokens) | ✅ 执行 | ✅ 执行 | 3 |
| 条件C (msg_count>200) | ✅ 执行 | ✅ 执行 | 1 (紧急模式) |
| 条件A+B 同时 | ✅ 执行 | ✅ 执行 | 3 |
| 条件B+C 同时 | ✅ 执行 | ✅ 执行 | 1 (紧急模式) |
| 都不触发 | ❌ 跳过 | ❌ 跳过 | — |

### 6.1 配置机制

`MAX_CONTEXT_TOKENS` 的取值优先级：

1. **配置覆盖**: `config.yaml` 中 `context_window: 128000`，有则用此值
2. **默认值**: 无配置时用 `MAX_CONTEXT_TOKENS=200000`（与原有 200K 数值一致，仅语义从 chars 纠正为 tokens）

设计中所有触发比例（40%/75%）始终基于实际生效的 `MAX_CONTEXT_TOKENS` 动态计算，而非硬编码绝对值。

## 八、深入调研：OpenCode 裁剪机制源码级分析

> 源码路径: `F:\agenttool\opencode\packages\opencode\src\session/`

### 8.1 触发检测 — `overflow.ts`

```typescript
// isOverflow() — 每次 LLM 返回后调用
const count = tokens.total || tokens.input+tokens.output+tokens.cache.read+tokens.cache.write
return count >= usable({cfg, model})

// usable() — 计算可用预算
reserved = cfg.compaction?.reserved ?? Math.min(20_000, maxOutputTokens)
return model.limit.input
  ? Math.max(0, model.limit.input - reserved)
  : Math.max(0, context - maxOutputTokens)
```

**核心**: token 制，预留 `reserved=20K` 作为输出缓冲区，剩余全用于历史。

### 8.2 `Prune()` — 廉价旧 tool 输出清除

从后往前扫描，跳过最近 2 个 user 轮次，跳过 `skill` 工具和已 compact 的消息。累计 token 直到 `PRUNE_PROTECT=40K`，超出保护阈值的旧 tool part 标记 `time.compacted=Date.now()`。只有 pruning 总量 > `PRUNE_MINIMUM=20K` 才实际写入 DB。

被 prune 的 tool output 在 LLM 请求中替换为 `"[Old tool result content cleared]"`（`message-v2.ts`）。

### 8.3 `Select()` — 分 head + tail

```typescript
limit = cfg.compaction?.tail_turns ?? 2  // 默认保尾 2 轮
budget = preserveRecentBudget({cfg, model})  // = usable × 25%, 范围 2K~8K tokens
all = turns(messages)  // 提取所有 user 轮次(跳过 compaction 类型)
recent = all.slice(-limit)  // 取最后 N 轮
```

对每轮计算 token 大小，从最新往最旧累加。如果整轮超出预算，尝试 `splitTurn()` 部分保留（从轮内某条消息开始截断）。最终返回 `{head(旧历史), tail_start_id(最近轮起始ID)}`。

### 8.4 `Process()` — LLM 摘要压缩

使用内部 `"compaction"` 专用 agent（无工具权限，特殊 system prompt），调用 `buildPrompt()` 包含预置的 `SUMMARY_TEMPLATE`：

```
## Goal
## Constraints & Preferences
## Progress (Done / In Progress / Blocked)
## Key Decisions
## Next Steps
## Critical Context
## Relevant Files
```

head 消息加上此 prompt，合并为一个 user 请求发给 LLM。LLM 返回的结构化 markdown 存入 assistant 消息（`summary: true` 标记）。

如果 `overflow=true`（上一次压缩溢出），回退到上一个没有 compaction 的 user 消息重新处理。如果 head 为空，返回 `"stop"`。

### 8.5 `FilterCompacted()` — 消息重组

给 LLM 最终的消息顺序：
```
[compaction_user(含tail_start_id)]
→ [summary_assistant(锚定总结)]
→ [tail_msgs(保留的最近2轮)]
→ [continue_user(继续当前任务)]
```

### 8.6 手动触发

- ACP slash 命令: 用户输入 `/compact` → SDK `session.summarize()` → HTTP API → compaction task
- TUI 快捷键: `<leader>c` → `session.compact` 事件
- 自动继续: 压缩成功后自动插入 `"Continue if you have next steps"` 用户消息

### 8.7 溢出回退

当 compaction 自身遇到 context overflow 时：
1. 尝试回退到更早的 user 消息（缩小 head 范围）
2. 如果也无法 fit → 设置 `finish="error"` → 返回 `"stop"`
3. compaction 错误消息不会被重试

### 8.9 opencode-old 保护体系分析

> 源码路径: `F:\agenttool\opencode-old\internal\llm\tools\` + `internal\tui\tui.go`

opencode-old（Go 实现，opencode 的早期版本）的保护体系与新版 OpenCode（TypeScript 实现）有本质差异——**opencode-old 没有入口拦截（单行截断），而是出口压缩（AutoCompact 会话摘要）**。

#### 8.9.1 4层保护体系

| 层 | 机制 | 文件 | 说明 |
|---|------|------|------|
| **L1 工具自截** | bash 30KB、view 2000字符/行 + 250KB文件、grep 100个匹配 | `bash.go:38`、`view.go:35-37`、`grep.go:145` | 工具在源头限大小 |
| **L2 cleanMessages** | 仅过滤空 Parts 消息 | `provider.go:170-179` | 极弱防护 |
| **L3 max_tokens** | 限制 LLM 输出（4K~50K），不限制输入 | `openai.go:170,182` | 输出侧防护 |
| **L4 🔑 AutoCompact** | ContextWindow 95% → LLM 压缩会话 | `tui.go:335-341` | **核心保护** |

#### 8.9.2 工具自身截断详情

| 工具 | 截断常量 | 截断策略 | 有单行截断？ |
|------|---------|---------|:-----------:|
| **bash** | `MaxOutputLength=30000` | 头15000+`[N lines truncated]`+尾15000 | ❌ 仅总体截断 |
| **view** | `MaxLineLength=2000`、`MaxReadSize=250KB`、`DefaultReadLimit=2000` | 行尾截断追加`"..."` | ✅ 2000字符 |
| **grep** | 匹配结果数上限=100 | 结果数截断 | ❌ **无** |
| **glob** | 结果数上限=100 | 结果数截断 | ❌ |
| **ls** | 文件数上限=1000 | 结果数截断 | ❌ |
| **fetch** | 读取上限=5MB | `io.LimitReader` | ❌ |

**grep 长行风险**：grep 对匹配行完全没有单行字符截断。400K+ 长行（如 minified JS 文件中搜索）原样进入 msgHistory，依赖 L4 AutoCompact 在窗口快满时一次性压缩。

#### 8.9.3 AutoCompact 触发条件（`tui.go:335-341`）

```go
tokens := a.selectedSession.CompletionTokens + a.selectedSession.PromptTokens
if (tokens >= int64(float64(contextWindow)*0.95)) && config.Get().AutoCompact {
    return a, util.CmdHandler(startCompactSessionMsg{})
}
```

**特征**：
- 阈值：**ContextWindow 的 95%**
- 触发时机：**LLM 返回后**（不是 API 调用前）
- 动作：调用 LLM Summarize() 生成结构化摘要 → 创建新会话
- 后续对话只保留摘要之后的消息（`agent.go:255-267`）

#### 8.9.4 完整数据流（以 grep 400K 长行为例）

```
rg 输出 400K 行 → grep.go:248 lineText = parts[2]（原样保存）
  → grep.go:166 直接格式化拼接（"  Line %d: %s\n"）
  → grep.go:177 NewTextResponse(output) → ToolResponse.Content
  → agent.go:415 ToolResult{Content: toolResult.Content}
  → agent.go:429-435 Message{Role: Tool}
  → agent.go:302 msgHistory = append(msgHistory, agentMessage, *toolResults)
  → provider/openai.go:119 直接转为 openai.ToolMessage() → API 调用
  → LLM API 接收完整 400K+ 输入（无入口截断）
  → LLM 返回后 tui.go:337 检查 95% 阈值
  → 达到 → AutoCompact 压缩会话
```

**中间没有任何截断。**

#### 8.9.5 关键缺失

| 缺失项 | 详情 |
|--------|------|
| ❌ 自定义 token 计数 | 所有 token 数据来自 LLM API 返回的 usage |
| ❌ 消息级 content 长度限制 | 无中间件/拦截器 |
| ❌ 入口总大小检查 | cleanMessages 只过滤空 Parts |
| ❌ Sliding window | 无 |
| ✅ 唯一行级截断 | 仅 view 有 `MaxLineLength=2000` |

#### 8.9.6 设计哲学对比

| 维度 | opencode-old | 新版 OpenCode | 本方案 |
|------|-------------|---------------|--------|
| **哲学** | 入口宽松，出口压缩 | 逐层精细控制 | 入口严格控制 |
| **长行防护** | ❌ 无（依赖 LLM API 自身） | ✅ Prune→Select→Process | ✅ 行×列+overwide统计 |
| **会话级压缩** | ✅ AutoCompact | ✅ Compaction | ❌ **缺失**（仅有 trim_history 丢弃） |
| **保护时机** | API 返回后 | API 调用前 | API 调用前 |
| **粒度** | 会话级 | 消息级+会话级 | 消息级 |

**与新版 OpenCode 的关联**：新版 OpenCode 的 compaction 机制（8.2~8.8 节）是 opencode-old AutoCompact 的进化版——保留了"LLM 摘要"核心思想，但加入了精细的 Prune（去旧 tool output）/Select（分 head+tail）/Process（LLM 摘要）/FilterCompacted（重组）四步流水线，粒度从会话级细化到消息级。

## 九、深入调研：Hermes 裁剪机制源码级分析

### 9.1 触发检测 — `conversation_loop.py`

**Preflight 触发**（每次 API 调用前）:
```python
_preflight_tokens = estimate_request_tokens_rough(messages, system_prompt, tools)
if compressor.should_compress(_preflight_tokens):
    for _pass in range(3):  # 最多压缩 3 轮
        messages = agent._compress_context(messages, system_message, ...)
        if len(messages) >= _orig_len: break  # 无法继续压缩
```

**Post-turn 触发**（LLM 返回后）:
```python
if agent.compression_enabled and compressor.should_compress(_real_tokens):
    messages = agent._compress_context(messages, system_message, ...)
```

**413 / Context Overflow 回退**: 捕获 API 错误后调 `agent._compress_context()` 再重试。

**Gateway 二级安全网**: token ≥ 85% context 或消息数 ≥ 400 条强制压缩。

### 9.2 `Should_compress()` — 防抖动

```python
def should_compress(self, prompt_tokens):
    if tokens < self.threshold_tokens:
        return False
    if self._ineffective_compression_count >= 2:  # 连续 2 次节省 <10%
        return False
    return True
```

### 9.3 `_prune_old_tool_results()` — 3 轮廉价预压缩

**Pass 1 — 去重（MD5 hash）**:
- 计算每个 tool result 的 MD5 hash
- 如果相同 hash 已存在（更近的相同内容），替换为 `"[Duplicate tool output — same content as a more recent call]"`

**Pass 2 — 工具感知摘要替换**:
- 对每个 >200 字符的旧 tool result，调 `_summarize_tool_result()` 生成结构化一行摘要
- 工具类型感知示例:
  ```
  [terminal] ran `npm test` -> exit 0, 47 lines output
  [read_file] read config.py from line 1 (3,400 chars)
  [search_files] content search for 'compress' in agent/ -> 12 matches
  [web_search] query='python tutorial' (15,230 chars result)
  [patch] replace in main.py (2,100 chars result)
  ```
- 多模态内容: `[screenshot removed] {text_summary[:200]}`

**Pass 3 — 截断大 tool_call 参数**:
- assistant 消息中的 tool_call arguments JSON >500 字符时，解析并截断内部长字符串，保持 JSON 合法

**边界保护**: token 预算（默认 ≈20K）+ `protect_tail_count=20` 作为硬下限。

### 9.4 边界计算

```python
compress_start = _protect_head_size(messages)  # system + protect_first_n(3)
compress_start = _align_boundary_forward(messages, compress_start)  # 跳过孤立 tool

compress_end = _find_tail_cut_by_tokens(messages, compress_start)
  # 从后往前累加 token，预算 ≈20K，硬下限 3 条消息
  # 不超过 budget × 1.5 防止单条超大消息破坏
compress_end = _align_boundary_backward(messages, compress_end)  # 避免分割 tool 组
compress_end = _ensure_last_user_message_in_tail(messages, compress_end, compress_start)
  # fix#10896: 确保最后一条 user 消息在 tail 中，防止 active task 丢失
```

### 9.5 `_generate_summary()` — LLM 结构化摘要

使用 auxiliary LLM（便宜/快速模型，可配置），包含:

**摘要模板章节**:
```
## Active Task
## Goal / Constraints & Preferences / Completed Actions
## Active State / In Progress / Blocked
## Key Decisions / Resolved Questions / Pending User Asks
## Relevant Files / Remaining Work / Critical Context
```

**关键细节**:
- `_compute_summary_budget()` = min(content_tokens×20%, max_summary_tokens), 下限 2K, 上限 12K
- `_serialize_for_summary()`: 每条消息截断到 6K 字符(前 4K + 后 1.5K)，tool args 截断到 1.5K
- 迭代更新: `_previous_summary` 保留上次摘要，新压缩时传递 `<previous-summary>` 作为锚点
- 失败处理: 冷却 600s；静态 fallback 提取关键路径/文件锚点；`abort_on_summary_failure` 可配置

### 9.6 `_sanitize_tool_pairs()` — 清理孤儿配对

1. 删除 tool_call_id 无对应 assistant 的 tool result
2. 为 assistant tool_calls 无对应 result 的插入 stub: `"[Result from earlier conversation — see context summary above]"`

### 9.7 组装压缩后列表

```python
# 系统提示追加压缩说明(仅在首次)
msg["content"] += "\n\n[Note: Some earlier conversation turns have been compacted...]"

# 选择 summary 的 role 避免与 head/tail 连续相同角色

    合并到第一条 tail 消息中

    if 合并模式且是 tail 首条:

```
