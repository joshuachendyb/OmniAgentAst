## 一、当前参数命名问题分析

### 1.1 路径参数命名混乱（最严重）

| 参数名 | 使用工具 | 数量 | 语义 |
|--------|---------|------|------|
| `file_path` | read_text_file, write_text_file, edit_text_file, read_media_file, analyze_data, filter_data | 6 | 文件路径 |
| `dir_path` | list_directory | 1 | 目录路径 |
| `search_dir` | search_files, grep_file_content | 2 | 搜索目录 |
| `source` | compress_files, extract_archive, move_file, copy_file, delete_file, rename_file | 6 | 源路径 |
| `destination` | compress_files, extract_archive, move_file, copy_file, rename_file | 5 | 目标路径 |
| `file_name` | read_pdf, read_docx, read_pptx, read_xlsx, write_docx, write_xlsx, write_pdf, write_pptx | 8 | 文件名（文档工具，仅文件名不含路径）|
| `output_path` | generate_chart, screen_capture | 2 | 输出路径 |
| `db_path` | query_sql, execute_sql, get_db_schema | 3 | 数据库路径 |
| `key_path` | registry_read, registry_write, registry_delete | 3 | 注册表路径 |
| `url` | http_request, download_file, fetch_webpage | 3 | URL地址 |
| `working_dir` | execute_code | 1 | 工作目录 |
| `cwd` | execute_shell_command | 1 | 当前工作目录 |

**问题**：
- ❌ 同样是"文件路径"，有`file_path`、`source`两种命名
- ⚠️ `file_name`用于文档工具，仅接受文件名（不含路径），语义不同，保持独立
- ❌ 同样是"目录路径"，有`dir_path`、`search_dir`、`working_dir`、`cwd`四种命名
- ❌ LLM难以理解，容易返回错误参数名

## 二、参数命名规范原则

### 2.1 核心原则

1. **语义清晰**：参数名应准确表达其含义
2. **命名统一**：相同语义的参数使用相同名称
3. **简洁明了**：避免冗余前缀/后缀
4. **符合惯例**：遵循业界命名惯例
5. **LLM友好**：易于LLM理解和推断

### 2.2 命名模式

| 语义 | 推荐参数名 | 说明 |
|------|-----------|------|
| 文件路径 | `path` | 统一使用path，简洁明了 |
| 目录路径 | `path` | 文件和目录都用path，由上下文区分 |
| URL地址 | `url` | 保持url，业界惯例 |
| 源路径 | `source` | 保持source，语义清晰 |
| 目标路径 | `target` | 统一使用target，避免destination过长 |
| 文本内容 | `content` | 统一使用content |
| 代码内容 | `code` | 保持code，语义清晰 |
| 命令内容 | `command` | 保持command，语义清晰 |
| 查询内容 | `query` | 保持query，语义清晰 |
| 超时时间 | `timeout` | 统一使用timeout |
| 代理地址 | `proxy` | 统一使用proxy |

## 三、规范化方案

### 方案A：全量统一（不推荐）

**原则**：所有路径参数统一为 `path`，所有内容参数统一为 `content`

**不推荐原因**：
- `cwd` 是业界标准缩写，`key_path` 格式与文件路径不同，`file_name` 语义为仅文件名
- 过度统一反而丢失语义区分度，不利于LLM推断

---

### 方案B：语义分组统一（推荐）

**原则**：
- 文件/目录路径 → `path`
- URL地址 → `url`
- 源/目标路径 → `source`/`target`
- 内容参数 → 根据类型使用`content`/`code`/`command`/`query`

**优点**：
1. **语义清晰**：从参数名可推断类型（path/url/source/target）
2. **破坏性小**：只修改21个参数，影响可控
3. **LLM友好**：语义清晰，易于理解
4. **符合惯例**：source/target是业界惯例
5. **易于维护**：命名规范明确
6. **保留特例**：cwd/key_path/file_name保持独立，避免过度统一

## 六、总结

### 推荐方案

**方案B（语义分组统一）**：
- 文件/目录/数据库路径 → `path`
- URL地址 → `url`
- 源路径 → `source`
- 目标路径 → `target`
- 内容参数 → `content`/`code`/`command`/`query`
- **保持独立**：`cwd`（业界标准）、`key_path`（注册表格式不同）、`file_name`（仅文件名）

3. **过渡期**：保留别名映射1个月，确保兼容
4. **长期**：移除别名映射，完全统一
