## 一、概述

### 1.1 重试机制分类

本文档覆盖两类重试机制，逐章独立分析：

| 分类 | 范围 | 机制 | 章节 |
|------|------|------|------|
| **系统重试** | LLM通信层，与tool零关系 | L1: LLM流重试 + L2: FC降级重试 | §二~§四 |
| **工具重试** | tool执行层 | Tool-1: ToolRetryEngine外部重试（Tool-2内建重试已取消） | §五~§七 |
| **非重试**（仅列出，不分析）| 编排层 | 截断重试 / Tool-less重试 / RETRYING可恢复错误重试 | §1.2(全景)、§十二 |

**核心分界**：
- 系统重试：LLM通信层的故障恢复，**不调用任何tool函数**
- 工具重试：tool函数调用时的临时性故障恢复，**与LLM通信层无关**
- 编排层循环控制（截断/RETRYING）：ReAct循环对"可恢复/可继续"情况的状态机调度，**既不是系统重试也不是工具重试**

### 1.2 现有机制全景

```
系统重试（与tool无关）:
  L1: LLM SDK流重试    ─── services/llm/base_service.py:173      ✅ 生效
  L2: FC降级重试       ─── services/agent/llm_stream.py:177        ✅ 生效（含0.5s反压）

工具重试（与tool相关）:
  Tool-1 外部重试      ─── ToolRetryEngine（services/agent/tool_retry_engine.py） ✅ 仅5个工具配重试

非重试（编排层循环控制）:
  截断重试             ─── react_cycle.py:240       ✅ observation注入→继续（_should_retry_truncated_tool）
  Tool-less重试        ─── react_cycle.py:225       ✅ answer未调工具→observation注入→继续
  RETRYING可恢复重试   ─── react_cycle.py:315/352   ✅ 可恢复错误→RETRYING→回THINKING重试（见§十二）
```

### 1.3 核心原则

1. **系统重试与工具重试完全独立** — L1/L2 只与 LLM 通信有关，Tool-1 只与 tool 执行有关，互不干涉
2. **各 tool 自己决定是否重试** — ToolRetryEngine 是共享工具，按 `TOOL_RETRY_CONFIG` 逐 tool 配置，未在字典中的 tool 默认 `max_retries=0`（不重试）
3. **编排层 RETRYING 是第三套机制** — 与 L1/L2（HTTP层）和 Tool-1（工具层）均独立，作用于 ReAct 循环的"可恢复错误→重回思考"场景

### 1.4 一句话矩阵

```
            ┌── 系统级（LLM层） ── L1 base_service（HTTP传输重试，退避2s/4s/8s）
            │                    L2 llm_stream（FC格式降级，0.5s反压）
 重试机制 ──┤
            └── 工具级（tool层） ── Tool-1 ToolRetryEngine（外部重试，退避1s/2s/4s，仅5个工具）

 编排层（非重试，状态机）: 截断重试 / Tool-less重试 / RETRYING可恢复错误重试
```

> 注：原文档的 "Tool-2 内建重试（待取消）" 已落地取消 —— `httpget`（原 `http_request`）的内建 `retry` 循环已删除，统一由 Tool-1 处理。— 小欧 2026-07-12

## 二、系统重试现状分析（L1/L2）

### 2.1 L1: LLM 流重试

**文件**: `services/llm/base_service.py:173-277`（`BaseAIService.request_stream`）

```python
retry_count = 0
max_retries = LLM_STREAM_MAX_RETRIES  # =3
while retry_count <= max_retries:
    effective_timeout = self.timeout + (retry_count + 1) * 20   # 每次重试超时+20s
    try:
        async for data_str in self._llm_sdk.request_stream(..., request_timeout=effective_timeout):
            ...
    except FCFormatError:
        raise  # FCFormatError 穿透，不由 L1 处理
    except Exception as e:
        if self._should_retry(e) and retry_count < max_retries:
            retry_count += 1
            wait_time = 2 ** retry_count  # 2s, 4s, 8s
            logger.warning(f"[Retry][L1] 重试 {retry_count}/{max_retries}, 等待{wait_time}秒, ...")
            await asyncio.sleep(wait_time)
            continue
        else:
            yield self._create_stream_error_chunk(e)
            return
```

**`_should_retry`** —— `services/llm/base_service.py:359-361`：

```python
def _should_retry(self, e: Exception) -> bool:
    """判断是否应该重试 — 委托给SystemErrorClassifier - 小沈 2026-06-17"""
    return SystemErrorClassifier.classify_error(e).is_retryable
```

| 维度 | 值 |
|------|-----|
| 最大重试 | 3（`LLM_STREAM_MAX_RETRIES`，定义于 `services/llm/base_service.py:19`） |
| 退避策略 | 指数退避 `2^retry`（2s → 4s → 8s） |
| 每次超时递增 | `effective_timeout = timeout + (retry_count+1)*20`（秒），缓解长尾超时 |
| 可重试判断 | `SystemErrorClassifier.classify_error(e).is_retryable` |
| 可重试类型 | 见下方"黑名单策略"说明 |
| 例外穿透 | `FCFormatError` 不在此层处理，原样抛出（交由 L2 降级） |

**`SystemErrorClassifier` 当前采用黑名单策略**（`services/llm/error_classifier.py`）：
- 分类枚举 `SystemErrorCategory` 仅 5 类：`CIRCUIT_OPEN / SERVER / UNKNOWN / EMPTY_RESPONSE / IDLE_TIMEOUT`
- `is_retryable` 为 `True` 的**只有** `SERVER` 与 `IDLE_TIMEOUT` 两类
- 默认兜底为 `SERVER`（可重试）—— 即所有未被显式排除的 httpx/httpcore/anyio 异常均走重试
- 显式**不可重试**：`FCFormatError`（→UNKNOWN，重试无意义，穿透给 L2）、Python 内置异常（ValueError/TypeError/...→UNKNOWN，代码bug不重试）、`CIRCUIT_OPEN`、`EMPTY_RESPONSE`

> 原文档 §2.1 列出的 "TIMEOUT / NETWORK / CONNECT / PROTOCOL / API_RATE_LIMIT / IDLE_TIMEOUT / SERVER" 为旧版白名单分类，**已不准确**。当前以黑名单为准。— 小欧 2026-07-12

## 三、系统重试问题（L1/L2）

### 问题 P1-L1: 退避首跳 2s 偏高（P3）

**严重程度**：P3-低  
**当前状态**：**未实施**（代码仍为 `wait_time = 2 ** retry_count`，见 `services/llm/base_service.py:271`）— 小欧 2026-07-12 核实

**描述**：`wait_time = 2 ** retry_count`，首次重试（retry_count=1）等待 2s。对于瞬时网络闪断（<100ms级别），2s首退偏保守。

**影响**：用户体验上，10ms的网络瞬时抖动需要等待 2s 才恢复。

### 问题 P2-L2: FC 重试无反压无退避（P3）

**严重程度**：P3-低  
**当前状态**：**已实施**（`services/agent/llm_stream.py:185` 已加 `await asyncio.sleep(0.5)`）— 小欧 2026-07-12 核实

**描述**：原 `for attempt in range(FC_MAX_RETRIES)` 中 `continue` 后立即重试、无退避。现改为 `continue` 前 `await asyncio.sleep(0.5)` 加反压。

**影响**：连续 FC 格式错误间有 0.5s 间隔，降低对同一个模型实例的瞬时压力。

### 问题 P3: 无重试事件可观测性（P2）

**严重程度**：P2-中  
**当前状态**：**部分实施** — 小欧 2026-07-12 核实

**描述**：L1 和 L2 的重试触发/成功/耗尽仍只有 `logger.warning` 日志（前缀 `[Retry][L1]` / `[Retry][L2]`），前端 SSE 事件流中无独立的系统重试事件。但**工具级** `ToolRetryEngine` 已引入 `on_retry_started` 回调（见 §5.2），可由 `action_handler` 消费并 yield 重试进度 Step 给前端；系统级 L1/L2 仍无前端事件。

**影响**：工具重试已有前端反馈通道；L1/L2 仍仅日志可见。

### 问题评估总览

| 编号 | 描述 | 严重程度 | 当前状态 |
|------|------|---------|---------|
| P1-L1 | 退避首跳2s偏高 | P3 | 未实施，优化建议 |
| P2-L2 | FC重试无反压 | P3 | **已实施**（0.5s反压） |
| P3 | 无可观测性 | P2 | 部分实施（Tool-1有回调；L1/L2仅日志） |

**结论**：L1/L2 当前运行正常，P2-L2 已修复，P1-L1 为非功能性优化建议（未实施），P3 部分修复。

### 5.2 Tool-1: ToolRetryEngine 外部重试

`services/agent/tool_retry_engine.py:242-249`：

```python
def _should_retry(self, e: Exception, retryable_errors: list, attempt: int, max_retries: int,
                   error_category: Optional[ToolErrorCategory] = None) -> bool:
    """判断是否应该重试 — 只查 per-tool 配置，不查 is_retryable — 小欧 2026-06-29"""
    if error_category is None:
        error_category = ToolErrorClassifier.classify_tool_error(e)
    # 使用 error_category.value 进行匹配，因为 TOOL_RETRY_CONFIG 中的字符串是 ToolErrorCategory.value
    is_retryable = error_category.value in retryable_errors
    return is_retryable and attempt < max_retries
```

判断逻辑：仅当 `ToolErrorCategory.value`（如 `"timeout"`/`"connect"`/`"network"`/`"protocol"`）出现在该 tool 在 `TOOL_RETRY_CONFIG` 的 `retryable` 列表中，且 `attempt < max_retries` 时才重试。

| 维度 | 值 |
|------|-----|
| 退避因子 | `TOOL_RETRY_BACKOFF["default"] = 2.0`（`tools/tool_constants.py:226-228`） |
| 退避公式 | `delay = backoff_factor ** attempt` → 第1/2次重试间隔为 1s / 2s（attempt=0,1） |
| 渐进超时 | 每次尝试 `timeout = min(base_timeout * (attempt+1), 300)`，给网络问题更长恢复窗口 |
| 可重试判断 | `error_category.value in retryable_errors`（per-tool 列表，见 §7.1.1） |
| 前端反馈 | `on_retry_started(action, attempt_1indexed, max_retries, error_msg)` 回调，重试前触发 |

## 八、系统重试与工具重试的关系

### 8.1 三条独立路径

```
系统重试路径（L1/L2，LLM通信层，与tool无关）:
  LLM 调用 → 网络超时/5xx/FC格式错误
       ↓
  L1 base_service 重试（3次，2s/4s/8s，超时+20s/次）
  L2 llm_stream 降级（2次FC→Text，0.5s反压）
       ↓
  重试成功 → 正常返回
  重试耗尽 → 生成错误chunk/降级Text

工具重试路径（Tool-1，tool执行层）:
  tool 调用 → 抛异常/返回error
       ↓
  ToolRetryEngine 重试（按TOOL_RETRY_CONFIG，1s/2s退避，渐进超时）
       ↓
  重试成功 → 正常返回
  重试耗尽 → 返回error dict → action_handler → set_failed() / RETRYING

编排层路径（RETRYING，ReAct循环，与上面两套独立）:
  可恢复错误（FC格式错/网络超时）→ ErrorStep.recoverable=True
       ↓
  _dispatch_handler 置 AgentStatus.RETRYING
       ↓
  react_cycle 循环回 THINKING 重新调用LLM（最多重试3次）
  超限 → set_failed()
```

### 8.2 职责划分

| 场景 | 谁处理 | 方式 |
|------|--------|------|
| LLM 网络超时，L1 第 2 次成功 | L1 | 透明，上层无感 |
| LLM FC 格式错误，L2 降级 Text | L2 | 透传至调用者 |
| tool 网络闪断，ToolRetryEngine 第 2 次成功 | Tool-1 | 透明，上层无感 |
| tool 超时，ToolRetryEngine 2 次耗尽 | Tool-1 | 返回 error dict → set_failed() |
| LLM流式调用抛可恢复异常 | 编排层 RETRYING | 回 THINKING 重新调用 LLM |

### 8.3 不重叠原则

```
系统重试 ≠ 工具重试 ≠ 编排层RETRYING
────────    ─────────    ───────────────
对象：LLM 通信    对象：tool 函数    对象：ReAct循环可恢复错误
条件：is_retryable 条件：error∈配置  条件：ErrorStep.recoverable
上限：3次(L1)     上限：各tool配置   上限：agent._retry_count>3→FAILED
      2次(L2)           (现最多2)
退避：2s/4s/8s     退避：1s/2s       退避：无（直接回THINKING重调LLM）
```

## 十二、编排层可恢复错误重试（AgentStatus.RETRYING）

> 本节为 v2.2 新增，因原文档未覆盖该机制。— 小欧 2026-07-12

### 12.1 概念

`AgentStatus.RETRYING` 是**编排层（ReAct 循环）**的可恢复错误重试中间态，**与系统级 L1/L2（HTTP 层）和工具级 Tool-1（工具层）完全独立**，是第三套机制。

- 它处理的是 **ReAct 循环层面**的可恢复错误（典型：LLM 流式调用抛出的 FC 格式错误、网络超时/连接错误），而非工具执行错误。
- 触发后，ReAct 循环**回到 THINKING 重新调用 LLM**（即发起一次新的 LLM 调用，而非原地重跑当前 step），最多重试 3 次（`agent._retry_count > 3` 则 `set_failed`）。

### 12.2 状态定义与转换

`services/agent/status_table.py:18-27` 定义 8 态，`RETRYING` 为其一。转换表（`status_table.py:39-87`）：

- `THINKING → RETRYING`：可恢复错误（`_dispatch_handler` 中 `recoverable=True`）— `:53`
- `EXECUTING → RETRYING`：可恢复错误 — `:63`
- `RETRYING → THINKING`：恢复，重新思考（react_cycle 重试机制）— `:69`
- `RETRYING → FAILED`：重试超限 — `:70`
- `RETRYING → CANCELLED`：用户取消 — `:71`
- `SUSPENDED → RETRYING`：挂起期间异常转重试（HITL 等待抛错）— `:78`

### 12.3 触发与处理链路

1. **`_dispatch_handler` 置态**（`react_cycle.py:122-128`）：handler 产出 `error` 事件时，若 `ErrorStep.recoverable=True` 则 `set_status(agent, AgentStatus.RETRYING, error_msg)`，否则 `set_failed`。

2. **`run_react_cycle` 循环处理**（`react_cycle.py:310-320`）：
   ```python
   if agent.status == AgentStatus.RETRYING:
       agent._retry_count = getattr(agent, '_retry_count', 0) + 1
       if agent._retry_count > 3:
           set_failed(agent, "可恢复错误重试超限")
           break
       set_status(agent, AgentStatus.THINKING, f"第{agent._retry_count}次重试")
   ```

3. **循环级异常兜底**（`react_cycle.py:343-354`）：`except Exception` 中 `handle_react_error` 生成 `ErrorStep`，若 `recoverable` 则递增 `_retry_count`，超限 `set_failed`，否则 `set_status(RETRYING)`。

4. **`recoverable` 判定**（`react_cycle.py:42-61` `_is_recoverable_error`）：
   - `FCFormatError` → 可恢复（True）
   - `asyncio.TimeoutError` → 可恢复
   - `httpx.TimeoutException / ConnectError / NetworkError / ProxyError / TooManyRedirects` → 可恢复
   - 其余 → 不可恢复（直接 `set_failed`）

### 12.4 与另两套机制的关系

`base_service.py:170-172` 注释明确：系统层 HTTP 请求重试（L1）"与 Agent 层（react_cycle.py）的 RETRYING 机制无关，是两套独立机制。Agent 层感知不到这里重试了几次。" 三者互不感知、互不干涉：

| 机制 | 层 | 重试对象 | 退避 | 上限 |
|------|----|---------|------|------|
| L1 | HTTP 通信 | LLM 请求 | 2s/4s/8s | 3 |
| L2 | FC 格式 | LLM 调用降级 | 0.5s | 2 |
| Tool-1 | tool 执行 | 工具调用 | 1s/2s | 各 tool 配置（现 2） |
| RETRYING | ReAct 循环 | 整轮 LLM 思考 | 无 | 3（`_retry_count`） |
