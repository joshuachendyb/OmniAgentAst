## 一、问题描述与病因分析

### 1.1 问题描述

任务 `task-5e57f3e3` 正在执行、UI 正在实时显示 step 时，用户刷新页面，结果：

| 位置 | 实际显示 | 应显示 |
|---|---|---|
| 左侧任务列表 | `执行中` | `执行中`（DB 当时也未完成，正常） |
| 右侧步骤区 | **task-93bd8d9a 的全部 step**（首个 step 文本为 "Let me analyze this task carefully…"） | task-5e57f3e3 已执行的 step |
| 右侧标题栏 | `已完成 / 运行耗时 134s / P:217636 C:9419 T:227055` | 本任务的实时状态 |
| 底部状态条 | `执行中 / 耗时 00:00:00 / 轮数 0 / 步骤 0` | 本任务实时数据 |
| 断点续传 | **120 秒内无 `GET /chat/stream/{task_id}?after_seq=N`** | 刷新后立即续传 |

失败断言：`fre2e_14_refresh_resume_seq.spec.ts:175`，`Timeout 120000ms exceeded`。

关键实测数据：

- 会话 `a0b60282-40f3-406d-a774-3210233cb6dd`，任务数 2
- `task-93bd8d9a`（06:35，`completed`，duration 134.4s，36 steps，token P217636/C9419/T227055）
- `task-5e57f3e3`（06:42，`completed`，duration 80.1s，24 steps，token P93223/C5681/T98904）
- 刷新时 `lastSeq=886`，该任务最终 `final seq=4210`
- 任务运行区间 06:42:55 → 06:44:15，而 `chat_task_steps` 最早行时间戳 06:44:13

### 1.2 后端病因

#### 1.2.1 主因：step 落库违背设计，堆在任务结束时

`backend/app/services/agent/agent_runner.py:430-434`：

```python
await agent.run_react_cycle(...)          # ① 整个 react loop 先跑完
for _scan_idx, event_dict in enumerate(list(buffer.event_log)):   # ② 结束后才扫描
    ...
    await _persist(event_dict)            # ③ 逐条 append_step 落库
```

逐条落库是对的，**时机全晚了**。这直接违背本仓设计意图，且是**遗漏而非设计**：

| 证据 | 位置 |
|---|---|
| 模块头注释明写"支撑运行期逐步落库+渐进耐久" | `storage.py:3` |
| 函数注释明写"运行期逐步落库"、"三键组(实时落盘)" | `storage.py:374` / `:380` |
| 建表注释明写"支撑运行期逐步落库" | `db_initializer.py:3` |
| **同库 token 累计已是每轮实时落库**（注释"用户裁定每轮即时落库"） | `react_step.py:435-443` |
| 同库 `monitoring.llm_calls` 每轮 checkpoint | `agent_telemetry.py:447-450` |
| **同一份事件流已实时落 Journal**（`chat_stream_events`） | `task_state.py:100` / `stream_event_journal.py:23-26` |

即：同一作者、同一批改造（2026-08-20/21、09-29）把 token、checkpoint、Journal 三者前移为实时，**唯独 `chat_task_steps` 没跟上**。同一份事件被落两遍，一遍实时一遍终态，step 那遍是后加的退化。

实测证实：任务执行 80 秒期间 `chat_task_steps` 恒 0 行。

#### 1.2.2 第二根因：消息内容也终态才落库

`chat_user_message` 的 `response/reasoning/outcome` 在 `agent_runner.py:672-682`（`finally` 内）才回填。运行中该行全 NULL。刷新页面的消息源是 `/sessions/{id}/messages`（`message_service.py:83/118/133`），因此**刷新必然拿到"别的已完成任务的结果"**。

#### 1.2.3 契约缺陷：消息不带 task_id，前端无法定位归属

- `MessageResponse`（`chat_models.py:83-92`）**无 `task_id` 字段**
- `message_service.py:118` 的 `load_execution_steps(conn, ai_id)` **单键聚合，不传 task_id**
- 能力其实已存在但零使用：`load_steps_by_task`（`storage.py:948-960`）+ `idx_steps_task` 索引 + `GET /chat/execution/task/{task_id}/steps` 接口（`db_initializer.py:111`）

### 1.3 前端病因

#### 1.3.1 `activeTaskId` 双写竞态（自相矛盾组合的成因）

`useTaskSelection.ts:67-87`，两个 effect 在同一次提交里都写 `activeTaskId`，互不排斥：

```ts
// ① :67-71
if (serverTaskId) setActiveTaskId(serverTaskId);
// ② :77-87
if (activeTaskId) return;                        // 读的是本次渲染的旧值
if (!isReceiving && latestTaskId) setActiveTaskId(latestTaskId);
```

②的守卫读旧值，看不到①的 pending 更新 ⇒ 两者都通过 ⇒ 最终值 = `latestTaskId`（DB 最新 = 5e57，正确），而 `serverTaskId` 仍为 null/陈旧。这正是"**`activeTaskId` 正确 + `serverTaskId` 失效**"这一矛盾组合的成因（实测 DOM `[pressed]` 在 5e57 上，证实 `activeTaskId` 正确）。

#### 1.3.2 `restore` 失效：`serverTaskId=null` + `metaFrames` 空

现象5（底部 `00:00:00 轮数0 步骤0`）**反证**"备份含 93bd 的 metaFrames"——若含，底部应显示 93bd 的耗时步轮。全仓**不存在**运行中清零 metaFrames 的写入点（`emptyMetaFrames` 仅 4 处真写入：建会话、legacy 归一）。故真相是 `restore` 未生效：

| 失效路径 | 位置 |
|---|---|
| 备份 key 缺失（`clearSteps` 的 `backupRemove` 后未重写） | `chatStreamStore.ts:842` / `:706-714` |
| `version !== 2` | `chatStreamStore.ts:843` |
| `isAnchorGroupIntact` 不过 | `chatStreamPersistence.ts:14-24` |
| legacy 归一（`taskId:null` + `metaFrames` 空 + `lastSeq:-1`） | `chatStreamPersistence.ts:67-78` / `:34-60` |

其中裸窗口确切存在：`chatStreamStore.ts:575-580`

```
persistNow → await attachActiveTask(HTTP RTT) → clearSteps(删备份) → await sendStreamRequest 才重新武装
```

发消息后到首个 commit 之间，备份是空的。

`restore` 是刷新后**唯一**状态来源，无任何"内存为空→查 DB 找 executing 任务"兜底。

#### 1.3.3 `serverTaskId` 写入路径的不对称

| 写入点 | 位置 | 是否立即落盘 |
|---|---|---|
| `attachActiveTask` | `chatStreamStore.ts:383-388` | ✅ |
| `store.setServerTaskId()` | `chatStreamStore.ts:749-756` | ✅ 但**生产零调用=死代码** |
| **transport start 帧** | `chatStreamTransport.ts:706-711` | ❌ **只吃 5s 防抖，是生产唯一入口** |
| `schedulePersist` 5s 防抖 | `chatStreamStore.ts:337-347` | `clearSessionTimers` 会杀待执行定时器且不补写 |

#### 1.3.4 右栏守卫以 `serverTaskId` 为前提，被绕过

```ts
// RightViewer.tsx:425-428  "执行中不读 DB" 守卫
if (activeTaskId === serverTaskId && !hasFinalStats) { setDetail(null); return; }
```

一旦 `serverTaskId` 为 null/陈旧，此守卫不成立 ⇒ 正在执行的 5e57 被当历史任务读 DB。

#### 1.3.5 C3 跨任务降级（显示 93bd 的直接产地）

```ts
// RightViewer.tsx:473-482
} else if (sessionId) {
  const msgResp = await sessionApi.getSessionMessages(sessionId);   // 整个会话
  const fallback: ExecutionStep[] = [];
  for (const m of msgResp.messages)
    for (const st of m.execution_steps ?? []) fallback.push(st);    // 全会话所有消息，无 task 过滤
  setHistorySteps(toExecutionSteps(fallback));
  writeFinalResponse(fallback);          // 还把别的任务的 final 写进左侧当前任务
}
```

因 1.2.1，5e57 的 `getTaskSteps` 返回空 ⇒ 触发 C3 ⇒ 会话内只有 93bd 有已落库步骤 ⇒ `displaySteps` 全是 93bd 的 ⇒ `finalStep` 取到 93bd 的 final ⇒ 标题栏显示 134s 与 P217636。

排除法证明 C3 是唯一路径：`liveSteps`/`settledSteps` 来自 store（刷新后为空，且 `RightViewer.tsx:246-251` 在 `activeTaskId` 变化时渲染期清空）；`getTaskSteps(activeTaskId)` 仅在 `activeTaskId=93bd` 时命中，已被 `[pressed]=5e57` 排除。

#### 1.3.6 任务列表刷新后永久冻结

`refreshTasks` 触发点仅 5 处，其中 SSE 驱动的两处是 `error` 与 `final_stats`；`final` 到达**不触发**（`useChatStreaming.ts:295-307`）。刷新后无 SSE ⇒ 无 `final_stats` ⇒ 除挂载那次外永不触发；`visibilitychange` 需用户切标签页。全仓无任务状态轮询。`TaskListPanel.tsx:217-229` 是纯快照渲染，故 DB 已 `completed` 而左侧仍显示"执行中"。

### 1.4 前后端关联影响

| 关联 | 说明 |
|---|---|
| 后端 → 前端 | step 不实时落库 ⇒ `getTaskSteps` 空 ⇒ 触发前端 C3 跨任务兜底 ⇒ 串 task。**后端是本缺陷的触发源** |
| 后端 → 前端 | `chat_user_message` 终态回填 ⇒ 刷新后 `/sessions/{id}/messages` 内容属上一任务 ⇒ 与 C3 叠加放大 |
| 前端 → 后端 | 前端无 `task_id` 契约可用，即便想按 task 过滤也做不到（后端契约缺失 + 前端未利用已有 `load_steps_by_task`） |
| 前端内部 | `serverTaskId` 失效 ⇒ 同时引发：断点续传短路、守卫失效、锚点 token 错。**一个错值造出两类症状** |
| 后端内部 | 取消/异常路径 `current_execution_steps` 为空 ⇒ 只写一条 final ⇒ 前面步骤全丢（与本 bug 同源） |
| 测试层 | E2E 的 `check_db` 有同源跨 task 兜底（`e2e_helpers.py:954-987`），且把"step 只在终态落库"写成豁免条件 —— **测试口径反向固化了缺陷** |

**完整因果链：**

```
后端·step 落库堆末尾（1.2.1，真根因）
  └→ 执行期 chat_task_steps 恒空
       └→ getTaskSteps(5e57) 空
            └→ C3 跨任务降级（1.3.5）→ 显示 93bd 的 134s/P217636

前端·activeTaskId 双写竞态（1.3.1）+ 备份失效（1.3.2）
  └→ activeTaskId=5e57（对）而 serverTaskId=null（错）
       ├→ transport 首行短路 ⇒ 无 after_seq 续传
       ├→ RightViewer 守卫失效（1.3.4）⇒ 正在执行任务被当历史任务读 DB
       └→ displaySteps 走 historySteps ⇒ C3 结果被当当前任务渲染

后端·消息终态回填（1.2.2）+ 契约无 task_id（1.2.3）⇒ 放大并固化串 task
```

### 3.1 改造红线（碰了就是新 bug）

### 3.2 解决方案

#### 方案一｜后端 step 实时落库（A 组）

**落点**：`agent_runner.py:294-301` 的 `_publish` —— 全部 12 处事件发点的唯一收口，`_persist` 闭包所需 `current_execution_steps`/`ai_message_id`/`db_ops`/`task_id` 全在此作用域内，闭包不必搬迁。

**顺序铁律**：`_publish`（SSE 已发）→ 投递队列 → 单消费者顺序落库。**不引入每步事务延迟，不改变 SSE 实时性。**

1. **单消费者 FIFO 异步写队列**：`_publish` 内只投递（O(1)，事件产生零阻塞）；单消费者消费 ⇒ step 序号顺序天然保证（R5）；`finally` 中 flush 队列后才做终态处理 ⇒ 崩溃前已落盘（真正实现 `storage.py:3` 的"渐进耐久"）。
2. **`step_index` 改由落库侧独立计数器维护**，解耦内存列表（解 A2），异常/取消路径不再撞唯一索引（解 A5/A6）。
3. **补幂等**：`ON CONFLICT DO NOTHING`（解 A3）。
4. **补护栏 + 降级**：每步落库 try/except；异常不阻断 SSE 发布（沿用 `agent_runner.py:347` t3 先于 t3' 风格）；失败置 `persistence_degraded`（解 A4/A9/A12）。
5. **`retry_locked` 必传**：不照抄 `react_step.py:440` 的缺参写法（解 A13/A14）。
6. **删除**末尾扫描循环 `agent_runner.py:434-486` 与 `:382-390` 过时注释（解 A1/A8）。
7. **取消/异常路径**改为复用落库队列，不再自建 step_index（解 A5/A6）。
8. `token_usage` 明细行同步改为实时（解 A10）；`chat_tasks.duration` 运行中即时写（解 A11）。

#### 方案二｜后端契约与消息（E13/E3/E4）

1. `MessageResponse` 增加 `task_id` 字段（解 E4）。
2. `load_execution_steps` 三个调用点补传 `task_id`（解 E3）。
3. `chat_user_message` 改实时回填 `response`（解 E13，刷新可见本任务回答）。
4. **E 组统计口径合并为单一真源**：`total_steps` 剔除集统一，`chat_tasks.total_steps` 与 telemetry 对齐（解 E1/E2）。
   - **只改代码，不碰存量数据**：老数据保持原值，新数据按新口径（**北京老陈裁定 2026-10-01**）
5. 唯一索引 NULL 缺陷修正（解 E5/E6）；`get_task_tool_stats` 支持并行多工具（解 E7）；`update_task` 0 行升级为 ERROR 留痕（解 E9）；死代码端点下线（解 E8）；两条出参契约统一（解 E11）。

#### 方案三｜前端锚点与恢复（B 组）

1. `useTaskSelection` 双写改**单一真源**：`serverTaskId` 存在时锚定它，否则用 `latestTaskId`，两者互斥由单一判定点承担（解 B1）。
2. 消除 `clearSteps` 裸窗口：`clearSteps` 不删备份，或删除后立即重写（解 B2）。
