## 前言

前端 E2E 用例在演进中先后演化出多套环境启动/隔离手法（普通链路、断流重连、配置隔离、临时 worktree），**散落在各 spec 与配置文件的注释里，未成文**——导致后续新增用例时"该用哪一套、端口怎么定、隔离到哪一层"需重新考古注释才能对齐。本文档把这套**用真实浏览器(Playwright) 直连验证、多隔离维度**的方法固化为可复用标准，供后续所有前端 E2E 用例沿用。

---

## 第 1 章 问题分析

### 1.1 现象

新写前端 E2E 用例时，开发者常困惑于：
- 该调 `startNormalUiEnv` 还是 `startIsolatedEnv` 还是 `startDevServer` + `startProxyServer`？
- 为什么有的用例端口是 5173、有的 5174、有的 5273？
- 为什么有的走 `/api` 相对路径、有的注入 `VITE_API_BASE_URL` 直连跨域？
- "隔离"到底隔离了几层？哪些用例必须隔离、哪些不必？

旧手法散落在 `fre2e_*.spec.ts` 头部注释和 `vite.*.config.ts` 中，**无单一标准文档**，新增用例易选错隔离层级，轻则冗余(不必要地多起进程)、重则误污染(配置类用例未隔离写真配置)。

### 1.2 根本原因

E2E 隔离方法随需求逐步叠加演化：
- 最初：普通功能用例——默认 vite dev + 同源 `/api` 转发（未刻意隔离）。
- 断流专项：需"杀 API 链路而不杀页面"——演化出**进程分离**（独立代理 9000）。
- 写配置专项：需"物理够不到真 config.yaml"——演化出**三进程配置隔离栈**。
- 临时验证：多 worktree 并行——演化出**临时端口隔离**。

这些是**不同隔离维度**的产物，但从未被系统归纳为"隔离链条标准"。

### 1.3 隔离链条（核心概念）

把一次 E2E 隔离拆成 **4 个可选隔离维度**，用例按真实需求组合取舍：

| 维度 | 说明 | 隔离手段 |
|---|---|---|
| **① 页面源隔离** | 不同用例的页面由不同端口/配置的 vite 服务，互不抢占 | 独立 vite 端口 + hmr 开关 |
| **② API 链路隔离** | 用例对应的后端交互走独立代理/独立目标 | `api-proxy.ts` 独立代理端口 + `PROXY_TARGET` |
| **③ 数据/配置隔离** | 用例写的数据落独立副本，够不到真 config | `isolated-env.ts` 临时 config 副本 + 隔离后端 |
| **④ 进程隔离** | 断流/杀进程类用例只杀目标进程，不影响页面活体 | `killPort` + 独立进程栈 |

**隔离原则**：用例**只需隔离它真正依赖防止污染的维度**，不必每维度都隔离——过度隔离会不必要地增加起进程与时长。

## 第 2 章 四种标准模式（固化标准）

### M-A：普通链路模式（复用优先，默认）

- **适用**：普通功能用例（发消息→等流→取正文），不写配置、不需断流。
- **隔离维度**：页面源 + API 链路都走默认。无刻意隔离（复用已有 dev server）。
- **链路**：`浏览器 → vite dev(:5173) → vite proxy(/api) → 后端(:8100)`，同源无 CORS。
- **入口**：`startNormalUiEnv(frontendDir)`（`e2e_front_lib/normal-chat.ts`）。
- **典型用例**：fre2e_02~05、07、13~19、21~23。
- **要点**：`ensureDevServer(5173,'run dev')` 复用优先——5173 已有活 vite 则直接用，不冷启动。

### M-B：断流重连模式（进程分离）

- **适用**：断线重连、杀进程、续传类用例（需"杀 API 链路而不杀页面"）。
- **隔离维度**：**①页面源(hmr:false 永活) + ②API链路(独立代理) + ④进程分离**。
- **链路**：`浏览器 → vite dev(5173, hmr:false) → 独立代理 api-proxy(:9000) → 后端(:8100)`；页面 API 经 `VITE_API_BASE_URL=http://localhost:9000/api/v1` 直连代理(跨域 CORS)。
- **为什么进程分离**：断流只 kill 代理 9000 —— 浏览器↔9000 RST 前端立即感知(真断线)，而页面(5173)永活不 reload → 重连 timer 存活 → 续传必达。若直接 target 8100 断流就要杀 vite，会触发 vite client 整页 reload 销毁重连逻辑。
- **入口**：`startDevServer` + `startProxyServer`（`e2e_front_lib/process.ts`）；config 用 `vite.e2e.config.ts`。
- **典型用例**：fre2e_01（重连/续传）、fre2e_06（时钟/等待）。
- **CORS 说明**：`api-proxy.ts` 自答 OPTIONS + 反射 Origin（替换后端 ACAO 为单值），因页面用 `localhost:9000` 源打开时后端 CORSMiddleware 只允许 5173。

### M-C：配置隔离模式（三进程栈）

- **适用**：**写配置类用例**（POST/PUT/DELETE providers/models/settings），须"物理够不到真 config.yaml"。
- **隔离维度**：**①页面源(独立5174) + ②API链路(独立9001) + ③数据/配置(隔离后端8898+临时config副本)**。
- **链路**：`浏览器 → vite.isolated(:5174, hmr:false) → 独立代理(:9001) → 隔离后端(:8898, OMNIAGENT_CONFIG_PATH→临时config副本)`。
- **为什么三进程**：真 config 只读拷一份到 `mkdtemp` 临时副本，隔离后端经 `OMNIAGENT_CONFIG_PATH` 改道副本；副本里 provider/api_key/models 仍是真值（不影响用真实模型），隔离的只是**写**的落点。
- **入口**：`isolatedEnvHooks(frontendDir)`（beforeAll 起 / afterAll 拆，`e2e_front_lib/isolated-env.ts`）。
- **典型用例**：fre2e_08~12（参数优化/provder链路/settings/模型库）。
- **多余事后果清理**：拆栈时 `rmSync` 删临时 config 副本，**真配置全程不可写、无需还原**（根治"事后还原不是可靠机制"）。

### M-D：临时 worktree 模式（验证用、不入库）

- **适用**：多 worktree 并行调试、临时验证某分支（避免抢默认端口/真实后端）。
- **隔离维度**：**①②④独立端口**（页面5273 + 代理9002 + 独立后端8010）。
- **入口**：`vite.interject.config.ts` + `playwright.interject.config.ts`（baseURL 显式指向 5273）。
- **典型用例**：历史临时插话验证（fre2e_2\d 曾用）。
- **要点**：注释标明"验证完删除，不入库"；`headless:false` + slowMo 供人工审看。

## 第 3 章 隔离维度与端口腔照（标准一览）

| 模式 | 页面 vite | API 代理 | 后端 | 数据隔离 | 入口函数 |
|---|---|---|---|---|---|
| M-A 普通 | 5173(默认) | 无(走 vite proxy) | 8100 | 不隔离 | `startNormalUiEnv` |
| M-B 断流 | 5173(hmr:false) | 9000→8100 | 8100 | 不隔离 | `startDevServer`+`startProxyServer` |
| M-C 配置隔离 | 5174(hmr:false) | 9001→8898 | 8898 | ✅ 临时config副本 | `isolatedEnvHooks` |
| M-D 临时worktree | 5273(hmr:false) | 9002→8010 | 8010 | 独立 | `vite.interject.config` |

**统一原则**：
1. `backend` 开发端口单源：`BACKEND_PORT` 环境变量（缺省 8100，`vite.config.ts` 与 `backend/start_dev.ps1` 同源）。
2. `api-proxy` 目标单源：`PROXY_TARGET`/`BACKEND_PORT`，缺省回落到 8100。
3. **/files/recent-files、token-usage、sessions/{id}/tasks 等高频轮询在日志层过滤**（`shared_handler.py`），避免刷屏。
4. 全局产物统一落 `e2e_case/output/`（报告/截图/代理日志/DIAG）。
5. Playwright `workers:1` 串行化，本地并行会导致真实后端探针互踩/残留。

## 第 4 章 沿用方法（如何选模式 & 落地步骤）

### 4.1 选型决策

```
要测的用例属于哪类？
├─ 功能链路(发消息/查天气/切会话/刷新) → M-A 普通模式
├─ 断线/重连/杀进程/续传 → M-B 断流重连模式
├─ 写 provider/models/settings 配置 → M-C 配置隔离模式(必须!)
└─ 多worktree/临时分支验证 → M-D 临时worktree模式
```

### 4.2 落地步骤（以新增 M-C 配置隔离用例为例）

1. 在 `e2e_case/` 建 `fre2e_XX_*.spec.ts`，`beforeAll` 引 `isolatedEnvHooks(frontendDir)`。
2. 页面基址用 `ISO_PAGE`(5174)，API 直连用 `ISO_API`(8898)；页面侧走 vite proxy 自动转发 9001→8898。
3. 写配置断言落盘路径用 `isoConfigPath()`（副本路径，勿硬编码真 config.yaml）。
4. 用例内用完，由 afterAll 拆栈 + 删副本（不需手动还原）。
5. 跑前端口未占用校验（`isolated-env.ts` 已内置；占用会显式报错提示释放）。

### 4.3 复用设施清单（e2e_front_lib）

| 文件 | 提供 | 用途 |
|---|---|---|
| `normal-chat.ts` | `startNormalUiEnv`/`runChatFlow` | 普通链路启动 + 消息流主流程 |
| `isolated-env.ts` | `isolatedEnvHooks`/`ISO_PAGE`/`ISO_API`/`isoConfigPath` | 配置隔离栈 + 端口/路径单源 |
| `process.ts` | `startDevServer`/`startProxyServer`/`ensureDevServer`/`killPort`/`waitPortUp/Down` | 进程/端口/服务控制 |
| `api-proxy.ts` | 独立后端代理 (跨源透传 + CORS 反射) | 断流 / 配置隔离的 API 链路 |
| `page-anchors.ts` | 左侧任务列表/地址栏读取 | 会话页断言锚点 |
| `stream-diag.ts` | 全链路诊断(网络+SSE console) | 失败取证 |
| `auth.ts`/`global-setup.ts` | 访问口令注入 + storageState | 鉴权统一注入 |

## 第 5 章 验收与常见陷阱

### 5.1 验收标准

- 新增用例能"照着本表选对模式"，不再考古注释；
- 写配置类用例**必须**走 M-C（防污染真 config，AGENTS.md 隔离铁律）；
- 断流类用例**必须**走 M-B（进程分离，页面永不 reload）；
- 端口按表分配，不抢占；产物统一落 `e2e_case/output/`；
- `tsc`/`eslint`/`prettier` 全绿，Playwright 串行通过。

### 5.2 常见陷阱

| 陷阱 | 后果 | 规避 |
|---|---|---|
| 写配置用例忘了 M-C | 测试值写真 config.yaml(进程被杀即永久残留) | 凡写配置一律 `isolatedEnvHooks` |
| 断流用例直接 target 后端 | 杀后端 → vite 不重载但续传语义失真(应杀代理保页面) | 用 M-B 独立代理 9000 |
| 端口抢占(5174/9001/8898 被占) | 隔离栈起不来 | 起栈前端口占用校验(已内置) |
| CORS 重复头(后端 ACAO + 代理注入) | 浏览器拒收 | 代理**替换**而非追加 Origin(已修) |
| 断言硬编码真 config 路径 | 判据盯真配置=把写真配置当验收 | 用 `isoConfigPath()` |
| localhost↔IPv6 解析 | vite dev server 健康误判 | `ensureDevServer` 用 127.0.0.1 严格 200 校验 |

## 第 6 章 后续扩展（不做项登记）

| 项 | 理由 |
|---|---|
| 引入 Docker 全栈隔离 | 当前真实后端 + 真实模型 + 进程分离已足够，过度引入反增环境复杂度 |
| 用例级数据快照/回滚框架 | 现有"配置用副本、断流用进程分离、普通用复用"已覆盖，未见更刚需场景 |
| 并行 worker 提升全量速度 | 已因"真实后端探针互踩/残留"定为串行(workers:1)，并行反而易假红 |
