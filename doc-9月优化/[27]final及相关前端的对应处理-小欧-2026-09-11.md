## 二、后端优化方案

### 2.1 final 加 duration

- **字段**：`final.duration: float`，值 `round(time.time() - telemetry._run_start_ts, 1)`，与 `agent_telemetry.py:207` 同式、与 DB `update_task` 同源。
- **注入时机**：`step_emitter.emit` 的 FinalStep 分支（与既有 `accumulated_usage`/三层 token 注入同模式），外部已传不覆盖；telemetry 缺失/无 `_run_start_ts` 时防御回退（不抛异常）。
- **短信号**：`agent_runner.py:399-400` 剥离键集合 `("type","step","timestamp","outcome")` → `+("duration")`，保证重连回放短信号也带运行时长，与实时一致。
- **实时时序**：final 是 react_loop 产出的第一终态实时帧，带 duration 后前端**收 final 即知状态+时长**，不再依赖 final_stats/DB。

### 2.2 final_stats 延后单发、字段补全

**（0）发布铁律（北京老陈 2026-09-11 铁令）：final_stats 必须全体段数据计算组装完成后才发，缺一段不发。**

- **禁止残缺组装即发**：现状 `emit_final_with_stats`（`step_emitter.py:67`）在 final 发射动作里同步 build_final_stats_step → 只装了 `duration/artifacts/final_status` 三块真值（`tool_stats/llm_call_count/retry_count/step_count` 根本没组装）就 publish——**违反本铁律，该做法彻底废弃**（产出+发布全部移出循环链）。
- **落库保留（不退化）**：现状 final_stats 走 `agent_runner.py:380-381` else 分支 `_persist` 落库（完整 dict 进 `chat_task_steps`，L405-410 再进终态缓冲统一补发）。改造后该落库行为**必须保留**：final_stats 在组装完成后由 runner 单发时，**SSE 发布 + DB 落库一并完成**，不得把现有已落库数据弄丢。
- **组装顶点**：全体段最终值取决于 ①工具记账（`_tool_stats`/`_artifacts`）②LLM 轮数/重试（`llm_call_count`/`_retry_count`）③步骤数（agent.steps）④运行时长（`_run_start_ts`）——全部在 react_loop **返回后**才为终值。故 final_stats **只能在 react_loop 返回后的 runner 收口点构建**，代码层杜绝提前。
- **发前完整性校验（硬门禁）**：构建后、publish 前逐段校验 7 键齐且类型正确——`duration(≥0 浮点)` / `artifacts(list)` / `final_status(非空)` / `tool_stats(dict)` / `llm_call_count(int)` / `retry_count(int)` / `step_count(int)`。任一缺失/类型错 → **不 publish** + ERROR 日志（抓代码 bug，禁残发）。
- **空值 ≠ 缺装**：`artifacts=[]`、`tool_stats={}`、`retry_count=0` 属合法终值（本次没调工具/没重试），正常发；缺键/None/类型错才是"没组装完"。

**（1）位置变更**：final_stats **移出 react_loop/react_step/handlers 实时链**，由 `agent_runner` 收口——在 react_loop 全部完成、telemetry 统计全齐后**统一构建单条：SSE 实时 publish + DB 落库（双保留）**。天然满足决定②"计算信息全部完成、每个地段都有信息后才发"与发布铁律（0），且不丢失现状落库数据。

**（2）字段补全**（`build_final_stats_step`）：

| 动作 | 字段 | 值 |
|------|------|----|
| 保留 | `duration` | 同源 `now - _run_start_ts` |
| 保留 | `artifacts` | `list(self._artifacts)` |
| 保留 | `final_status` | 显式 outcome |
| **新增** | `tool_stats` | `dict(self._tool_stats)`（按工具聚合，`_tool_stats` 是权威源） |
| **新增** | `llm_call_count` | `agent.llm_call_count` |
| **新增** | `retry_count` | `agent._retry_count` |
| **新增** | `step_count` | 与 `build_stats_step`（L188）同口径 |
| **删除** | `content=""` | 无信息量（注：content 键仍由基类 to_dict 恒输出、值恒空串，删除的是显式传值；改造后事件实为 11 键=4 基类+7 统计键，门禁仅查 7 统计键，不冲突） |
| **删除** | `severity="info"` | 无信息量 |
| 不动 | `step` | 前端按 event_log seq 排序，语义不动 |

**（3）全路径必达**：正常/异常/取消/守卫路径 final_stats 都必须发（现状异常/守卫路径本就缺失，一并补齐），字段空数组也要发。

**（4）发布点选择（v1.9 北京老陈拍板·方案 A：final_stats 即 DB 就绪信号）**：`agent_runner` 在 DB 终态落库段（`await _persist_final(db.atxn(...))`，即 update_task）**完成之后**调用（DB 成功则其后发；DB 失败也照发兜底，折叠必达不丢——v1.12 起该兜底覆盖"update_task 或 `append_step(final_stats)` 任一失败，均照发"）——统计在 react_loop 返回时已齐，**先落库、后发布**：前端**"收到 final_stats"即宣告"DB 已落库可读"**，折叠区与任务列表 refresh 以此为统一信号直接读 DB，零延时零轮询（不猜时间）。runner 一处收口，正常与守卫/异常路径统一在终态缓冲补发后同一调用点各调一次；`append_step(final_stats)` 落库在 publish 之前同步完成（见 3.5 代码）。发布铁律(0)只约束"组装完整"，不约束"先于 DB"，本顺序调整不冲突。

### 2.3 目标时序全景

**落库两级**：一个任务的数据写库分两级——**步骤级 `append_step`**（thought/action/observation/final/final_stats 等逐条写入 `chat_task_steps`，随循环/扫描同步进行，一条一事务，落得快）与**任务级 `update_task`**（任务整体终态写入 `chat_tasks`，status/duration/起止时间/token，整个任务结束后在 finally 一次大事务落库，**最晚**）。前端 `getTaskDetail` 读的是 chat_tasks，故"**能读 DB 的安全时刻 = 任务级落完**"。

| 时刻 | 事件 | 前端效果 |
|------|------|---------|
| t0 | react_loop 产 final → 实时 publish（**带 duration**） | 立即渲染状态+运行时长（**不查 DB**），左侧 response 即时处理 |
| t2 | react_loop 返回、扫描+短信号覆写 → runner 构建 final_stats（统计全齐）| 仅组装，**未发布**（杜绝残缺组装即发） |
| t3 | DB 终态落库完成：`update_task`（status/duration 同源）+ `append_step(final_stats)` | DB 终态写库完成 |
| t3' | **final_stats SSE publish（DB 就绪信号，v1.9 方案 A）** | **折叠区读 DB（`getTaskDetail`+`getTaskSteps`）复合组装渲染（事件 B）+ 任务列表 refresh** |

**发布↔落库相对顺序总述**：普通事件（thought/action/observation/chunk）**先发后落**（SSE 实时先达，步骤级随后跟进）；final 亦**先发后落**（步骤级），但其 SSE 早于任务级 `update_task`（t0≪t3）——故 final 不可作"DB 就绪"信号，正是 **R8 final 到达绝不读 DB** 的根因；**final_stats 是 v1.9 起全链唯一"先落库后发布"**（t2 组装→t3 落库→t3' 发布，居于任务级落完之后），充当前端"DB 就绪"总信号，收到即可读 DB，无延时无轮询。t0→t3' 与老陈定案三步顺序完全吻合（①final 先做状态+时长渲染 ②response 即时处理 ③统计计算与折叠详情由 final_stats+DB 异步补齐），根除"final 到→查 DB→闪旧值"竞态。

## 五、前端 final 与任务统计的需求说明

> 本章（北京老陈 2026-09-11 定案）只梳理**需求**与**规则**，不涉及实现方案；优化概要设计见第六章，前端优化详细设计见第七章。

### 5.1 final 事件渲染需求（R1~R2）

**R1 —— final 步骤必须完整渲染：** final 到达后，final 步骤的信息必须**完整渲染完毕**（状态/时长/正文/token/model/provider 等），渲染过程**不受任何其它事件干扰**。

**R2 —— final 渲染与统计区渲染分离：** 统计区（任务统计）可以使用 final 的数据，但**绝不能和 final 步骤渲染放在同一渲染事件里**——统计区渲染是**独立的第二次、第三次渲染事件**，不得与 final 步骤渲染并行/耦合/互相影响。

### 5.2 任务列表回复双源规则（R3~R4）

**R3 —— 实时（当前任务）：** 任务列表（`TaskListPanel`）当前任务的回复显示**只读 `final.response` 字段**（SSE 实时帧），不读 DB。注：本规则管辖 final 到达**之后**的显示；running 状态（final 未到达前）任务列表的显示规则不在本章范围内（小欧 2026-09-11 17:33:27 补注）。

**R4 —— 历史回显：** 仅在历史回放时（`listTasks` 读 DB 返回的 `SessionTaskItem.response`）才显示 DB 中的回复，`useSessionTasks.refresh()` 不得在 final 到达的瞬间触发（现状 `RightViewer.tsx:333-344` B16 在 `receiving` 翻 false 时触发 `refreshTasks` = final 到就读 DB，属错误行为）；**后置到 `final_stats` 到达（t3'，DB 就绪信号，v1.9 方案 A）后**才触发。

### 5.3 任务统计区两段式渲染需求（R5~R7）

**R5 —— 统计区拆为两部分、两次独立渲染事件：** 任务统计区（`StaticStatsBlock`）分为 **title 段**和**折叠区段**两段，**两次独立渲染事件**，且**都独立于 final 步骤渲染**。（注：三次渲染事件从 final 步骤渲染起算——第一次=final 步骤渲染（R1），第二次=title 段渲染（R6），第三次=折叠区段渲染（R7）；小欧 2026-09-11 17:33:27 补注）

**R6 —— title 段数据来源与规则：** title 段（标题行：任务统计 + 状态Tag + 运行时长 + ▼）数据来源=**final 帧**：`outcome`（状态）、`duration`（运行时长）、`model/provider`、`prompt_tokens`/`completion_tokens`/`total_tokens`（token 三层，对应后端 accumulated_usage 的三个子键；注：task/session/chain_accumulated_tokens 为后端 DB 聚合结构，前端 ExecutionStep 类型不承载，sseParser final 分支仅解析平铺 token 字段）。final 到达即可渲染（独立事件 A），**绝不读 DB**。

**R6-1 —— title 段排版规则（北京老陈 2026-09-11 补充）：** title 段承载的信息随 R6 增多，UI 排版须**视觉效果优先、清晰分层**：允许 title 拆为 **2 行**排布（上行：任务统计标题 + 状态 Tag + 折叠箭头；下行：运行时长 + model/provider + token 信息），不再强求单行塞入，分行/对齐/留白以视觉最佳为准；折叠/展开交互不变。

**R7 —— 折叠区段先读 DB 再渲染：** 折叠区段（展开内容：工具汇总/产出物/轮次/重试/步数/开始结束时间等）渲染之前**必须先读取 DB**（`getTaskDetail`+`getTaskSteps`）来组装折叠区的渲染数据；组装时可用 **final / final_stats / DB 读到的数据 三者复合**——即使 DB 仍读到 `executing` 等旧态，由复合规则兜底，不显示脏值。折叠区渲染是独立事件 B，**由 `final_stats` 事件触发（v1.9 方案 A：收到 final_stats = DB 已落库，直接读 DB 渲染，零延时零轮询）**，晚于 title 段。

### 5.4 读 DB 时机铁律（R8~R9）

**R8 —— final 到达绝不读 DB：** final 到达的一刻**绝对禁止读 DB**（此刻 `update_task` 尚未落库，读了必然拿到 stale `executing`/旧时长）——现状 `RightViewer.tsx:287-288` final 到达立即并行 `getTaskDetail`+`getTaskSteps` 即此错误。

**R9 —— 折叠区 DB 读在落库完成后：** 折叠区需要读 DB 的字段（DB 独有：开始/结束时间等）时序上必须位于 `update_task` 落库完成（t3）之后；v1.9 方案 A 将 `final_stats` 发布点后置到 t3 之后（t3'，DB 就绪信号），**收到 final_stats 即读 DB，天然满足 t3 之后**；t3' 之前的空白由 final/final_stats 帧复合兜底（R7），不阻塞、不显示中间态、无延时无轮询。
