## 一、目标是什么

### 1.1 要根治的病根（[63] 第一、二章）

| 组 | 病根 | 现象 | 归属 |
|---|---|---|---|
| 前端 F1~F7 | **流无家**：SSE 连接与步骤数据的寿命 = ChatPage 组件寿命 | 实时任务中切去历史页/设置页 → `useSSE.ts:1231-1246` 卸载清理 abort 连接 + 删 sessionStorage 步骤备份 + 清 pending；切回是全新白板，只能 `loadHistoryMessages` 拉最终结果，**中间 step 全丢** | 第四章 P1/P2 |
| 后端 B1~B3 | **事件无库**：事件仅存内存、300 秒回收，无持久事件源 | 刷新/切回超过 300 秒或后端重启后，已完成任务无法回放中间过程 | 第三章 P3 |

一句话定性（[63] L997）：**会话流常驻架构 ＝ 把对话流的"家"从聊天页面搬进全局总机室常驻，页面只当显示器。**

### 1.2 目标能力边界：三层防线 + P3（[63] L918-923 / L989-995）

| 层 | 目标覆盖场景 | 承诺效果 | 阶段 |
|---|---|---|---|
| **L1 内存 Store** | 路由来回切换（最常见） | **完全无缝**：切回大屏直接续显，**零等待、不重拉、不重建任务** | P1 |
| **L2 持久化 + 续传** | 浏览器刷新、标签页被冻结恢复 | 锚点组 + steps 原子快照写 sessionStorage，重挂载后按 `after_seq` 发 GET 补拉（仅 300 秒内存窗口内） | P2 |
| **L3 DB 历史兜底** | 超 300 秒 / 后端重启 | 退回现有历史加载，**行为等同现状、不劣化**（只可能变好） | P1/P2 |
| **P3 后端 Journal** | 300 秒后回放、后端重启后回放已完成任务 | `chat_stream_events` Journal 持久化 + reader 按 seq 回放；**未完成计算明确中断，不伪造续算** | P3 |

**边界纪律（[63] L931）**：P1/P2 是纯前端方案，**不覆盖 B1~B3**。准确表述必须是"P1/P2 交付后，切页不断流、300 秒内刷新可续；300 秒后与后端重启后的回放必须等 P3"。

### 1.3 关键设计原则（10 大规范对齐 + 9 条纠偏 + 生命周期语义）

**（1）架构层原则（[63] L925-929）**

| 原则 | 落地含义 |
|---|---|
| SRP | Store 只管"流"（连接/步骤/任务锚点/订阅）；消息历史、UI 态（滚动、回复区）仍留 `useChatState` |
| DRY | 会话流状态由 `useSSE` 与未来历史页实时化共用同一数据源，消除"每实例一套 ref 双写" |
| OCP | Store 按 `sessionId` 索引，**结构本身即多会话**（非预留位），新增消费者不必改 Store 内核 |
| 禁止 backward | `useSSE` 对外接口经薄适配层保留签名，消费者无感知切换；内部整体迁移，**不保留新旧两套路径** |

**（2）9 条实施纠偏（[63] L1080-1088，标注"后续代码必须以本节为准"）**：① `getSnapshot` 读缓存快照、禁读取阶段惰性创建；② 取消订阅/关闭视图/停止任务/删除会话是**四个不同动作**，关闭视图不得 `clear()` 或 abort；③ L2 同一份原子快照、终态立即落盘不靠 5 秒防抖；④ Store 补齐 `useSSE` 全部运行态/定时器/连接资源/HITL 状态；⑤ GET 续传必须处理 8 类恢复结果，**不能把"回退历史"当成自动发生的行为**；⑥ sessionStorage 只承担单标签页刷新恢复；⑦ 多会话 Tab 不纳入本轮；⑧ **F7 必须同步修复**（切回跳过重初始化）；⑨ 不引入 Service Worker/SharedWorker/BroadcastChannel/纯后端推送。

**（3）生命周期语义表（[63] L1093-1101，本架构的判定基准）**

```text
切路由/切 Tab   → 只取消页面订阅
切回会话页      → 先读 Store 快照；Store 有流则跳过 initializeSession（F7）
关闭视图        → 只移除视图，Store 和后端任务保留
停止任务        → 先调后端 cancel，确认终态后清理 Store（cancel 返回已结束按 STOP_RACE 处理）
删除会话        → 先调后端删除接口，确认删除后清理 Store
任务正常完成    → 保留最终快照，按 TTL/LRU 释放连接资源
浏览器刷新      → Store 丢失，使用 L2 原子快照恢复
```

**（4）红线（[63] L1103）**："我不看了" ≠ "停止任务"；任何关闭视图路径都不得调用 `clear()`、abort 或删除 sessionStorage。

**（5）本轮范围禁令（[63] L1113）**：多会话 Tab（第七章能力）、三类替代承载（B1~B3 仍在，换承载方式解决不了"谁持有流"）一律不采用。

### 1.4 目标的客观标尺：第六章验收门（[63] L3331-3340 放行判定）

1. P1~P3 全过；P4~P9 不得出现重复任务、重复步骤、永久接收中或静默丢失；
2. 切走期间产生的步骤（thinking/action/observation/final）切回后**可见且不重复**；
3. 刷新恢复通过 seq 单调性校验（M6），`lastSeq` 与 `steps` 来自同一 revision；
4. **F7 已闭环**：`__initCount` 切回后不增（M3），否则视为未完成；
5. 关闭视图不停止任务；停止任务必须先完成后端 cancel 确认，`STOP_RACE` 不报错；
6. 全程每 session 仅 1 个 taskId、1 次 POST；
7. **19 项改造清单（5.1~5.19）全部落地并逐项可追溯**；HITL 请求只有 Store 一个来源；
8. 10 大规范三堂会审通过：无状态双源、无第二套解析器、**无透传函数**、无无效抽象、**无向后兼容分支**。

### 3.1 🔴 D1：切回路径的状态覆盖与重复 GET（本轮最高优先级 · 唯一结构性错误）

**真实场景推演（v1.1 判定基准，此表为"代码错"的直接证据）**

| 场景 | 实际发生什么（逐行可证） | 用户可感后果 |
|---|---|---|
| **S1** 任务跑到第 8 步，切走 30 秒再切回 | `restore()` 用 ≤5 秒前备份 `Object.assign` 覆盖活会话（`chatStreamStore.ts:618-644`）→ `executionSteps` 回退到第 6 步，第 7、8 步消失 | 步骤**倒退再闪烁**。改造前是"切回是白板"（用户明确知道断了），现在是"步骤在跳"（用户以为系统抽风）→ **比改造前更糟** |
| **S3** 切回后**立刻点"停止"** | 后端 cancel 成功，但 `s.abortController` 已被多余 GET 覆盖（`chatStreamTransport.ts:171` 覆盖 `:124` 存的那个）→ 活流断不掉 → 后端若补发 `final`，`onComplete` 无条件写 `status='completed'`（`:574`） | **点了"停止"，界面显示"已完成"** —— 功能性错误，非观感问题 |
| **S12** 停止任务后切走再切回 | `restore()` 把 `status` 从 `cancelled` 覆盖成备份里的 `active` | **已取消的任务显示成运行中**，且 `clearCompleted` 清不掉（`:419` 直接 `s.pumpActive=false` 绕过 `commit`） |
| **S1 连接** | 每次切回多发一条 GET，`pump()` 在 `:415` 早退，`getReader()`（`:422`）从未调用 | **每次切回泄漏一条 SSE 连接** + `firstChunkTimeout` 定时器悬置 |

**蓝图错在哪（机理结论，不依赖任何条款优先级）**

`restore()` 的设计前提是 **"Store 是空的"**（页面刷新后从 sessionStorage 恢复）。但它被 `resume()` 无条件调用（`chatStreamStore.ts:343`），而 `resume()` 挂在 `useChatInit.ts:56` 的 effect（deps=`[urlSessionId]`）上 —— **每次挂载都跑**。于是同一个入口同时服务两种语义相反的场景：

```text
首屏/刷新  → Store 空 → restore 是正确行为
切回会话页 → Store 满（流仍在跑）→ restore 用旧副本盖活状态 = 必然出错
```

蓝图并非"写错了条款"，而是**把只在一个场景成立的函数复用到另一个场景，且缺判活流的前置条件**。`5.4` 自己已备好 `hasSession()`（`:1721`/`:1932`）却未在 `resume`/`restore` 中使用。

> 附：`:1095`（4.6.2）字面只写"跳过 `initializeSession`"（=F7，已实现），"跳过 `restore`/`resume`"系从 `:3036`（5.16「Store 丢失才 `restore/resume`」）+ `:970`/`:1045`（「不重拉」）推出。**但按 v1.1 基准，此歧义不影响结论** —— 无论文档如何表述，"用持久化副本覆盖在飞状态"在 S1/S3/S12 三个场景下都必然产生错误后果。

**文档要求（4 处互相印证，备查）**

| 位置 | 原文 |
|---|---|
| `[63]:970`（4.4.4 L1） | 切回大屏**直接续显，零等待、不重拉、不重建任务** |
| `[63]:1045`（4.5.2） | 重新订阅 Store → 立即拿到当前快照 → UI 直接续显，**零等待、不重拉、不重建任务** |
| `[63]:1095`（4.6.2，**"后续代码必须以本节为准"**） | 切回会话页 → **先读 Store 快照；Store 有流则跳过** initializeSession |
| `[63]:3036`（5.16 卸载语义对照表） | 切回时重挂载 → 读取缓存快照；**Store 有流直接续显，Store 丢失才 `restore/resume`** |

**实现（逐行实测）**

```text
useChatInit.ts:56   void chatStreamStore.resume(opts.urlSessionId ?? undefined).then(...)   ← 无条件调用
useChatInit.ts:57   if (r !== 'idle' && opts.urlSessionId) { loadSession(...); return; }      ← 只分 idle/非 idle
chatStreamStore.ts:339-352  resume()：ensureSession → await this.restore() → resumeStreamRequest()   ← 三步全无活流守卫
chatStreamStore.ts:618-644  restore()：Object.assign 覆盖 13 个字段，无 hasSession/pumpActive 判定
chatStreamTransport.ts:171  d.abortController = ctl;                                          ← 覆盖 sendStreamRequest:124 存的那个
chatStreamTransport.ts:415  if (s.pumpActive) return 'recovering';                            ← 早退发生在 :422 getReader() 之前
```

**后果链（静态可证，运行时未实测）**

1. **在飞状态被持久化快照覆盖（危害最大）**：`restore()` 用 ≤5 秒前的备份 `Object.assign` 覆盖活会话 —— `executionSteps`（**最近已渲染的 step 回退，且活流不会重发已消费帧 → 永久消失**）、`currentResponse`（正文缓冲回退）、`lastSeq`（**回退**，而正常 setter 是 `Math.max` 单调，`restore` 是唯一能回退之处）、`status`、`isConnected`（**强制 false，而活流仍在 pump → 快照自相矛盾**）。直接违反 6.5 第 2 条"切走期间产生的步骤切回后可见且不重复"与 6.3 P1"step 从断点续增"。
2. **多发一条 SSE GET**：切回必发 `GET /chat/stream/{task_id}?after_seq=N`，违反"不重拉"。
3. **响应体泄漏**：该 GET 的 `pump()` 在 `:415` 早退，`res.body.getReader()`（`:422`）从未调用 → 既不读也不 `cancel()`，连接与 `firstChunkTimeout` 定时器悬置。
4. **在飞流的 abort 通道被夺走**：`sendStreamRequest` 存于 `s.abortController` 的 controller 被 `:171` 覆盖后失联；此后 `stop()`→`clearCompleted()`（`chatStreamStore.ts:405`）、宽限期释放（`:543`）、`destroySession` 的 `abort()` 全部打在死 controller 上 → **在飞 POST 流断不掉**；`clearCompleted` 另在 `:419` 直接 `s.pumpActive = false`（绕过 `commit`），单飞守卫同时失效。
5. **终态可能被覆盖为 completed（条件性）**：`onComplete`（`chatStreamTransport.ts:568-579`）**无条件** `d.status = 'completed'`，无 `intentionalAbort` / 终态守卫。若用户点"停止"后后端仍下发 `final` 帧（在飞流未断），Store 状态会从 `cancelled` 被改回 `completed`。*（取决于后端 cancel 后是否下发 final；本项目 cancel 链路确有 final 下发记录，见 [41]）*

**归属判定（v1.1 修正）**：实现**逐字忠实于 5.4 蓝图**（`restore` 蓝图 `[63]:2179-2195` 与实现逐行等价，含 `isConnected: false`；`resume` 蓝图 `[63]:1997`；`useChatInit` 蓝图 `[63]:3073`）。v1.0 曾把归属记为"文档 70% / 实现 30%"并援引 `:1074` 条款优先级作为裁决依据 —— **该归属比例与依据均已撤回**：按场景基准，**代码在 S1/S3/S12 三个场景下产生用户可见错误，即为"代码错"**，无论蓝图如何。`5.4` 已提供 `hasSession()`（`:1721`/`:1932`）却未在 `resume`/`restore` 中使用 —— 修复所需 API 文档已备好，只是蓝图未用。**修复须同时改代码与蓝图**，否则下次照蓝图重做会再错一遍。

### 3.2 🟡 中 D2：render 期 `ensureSession` 违反三处硬约束（v1.0 定 🔴 高，v1.1 下调）

> **v1.1 严重度下调理由（场景基准）**：正常进会话页**功能完全正确**（零钟面已修，有红测佐证）。render 期写全局状态仅在"该次 render 被 React 丢弃/重启"时留下未订阅条目，单条约几百字节，且不产生用户可见错误。**对比之下真正的设计错误在蓝图**：`getClockSignals` 对不存在的会话返回**模块级共享 `ZERO_CLOCK`**（`chatStreamStore.ts:505-507`），这是任何 memo 都会钉死的陷阱值 —— 正确解是给它按 id 缓存的惰性零视图（见本节末"更优解"）。故定 **🟡 中**：手段违规、功能无缺陷。

**文档约束（三处互证）**

| 位置 | 原文 |
|---|---|
| `[63]:1080`（4.6.1①） | 禁止……**在读取阶段惰性创建状态** |
| `[63]:1744` / `:2255`（5.4 / 5.5） | `ensureSession()` **只能由挂载 effect 或用户动作显式调用**；"subscribe 回调不创建" |
| `[63]:2105`（5.4 `getClockSignals` 蓝图注释） | **render 期不得 `ensureSession`**（实现约束）；session 不存在返回零信号 |

**实现**：`useChatStreamSession.ts:28` `if (id) chatStreamStore.ensureSession(id);` —— 位于函数体 render 路径，在 `useSyncExternalStore` 与 `useMemo` 之前执行。

**成因链（真实缺陷驱动，非随意违反）**

```text
5.5 蓝图：getClockSignals 每次 render 新建对象（无 memo）
  → 实现加 useMemo([id, snapshot.heartbeatTs]) 修 useChatPanels.tsx:159 的 useMemo 永久重算
  → 首渲染时 session 尚未创建 → 拿到 ZERO_CLOCK（恒 0）→ 空流/无心跳场景 heartbeatTs 恒 0
    → memo 依赖永不变化 → 组件永久持有零钟面，lastBizTs 恒 0，等待动画与静默升档全失效
  → 只能把 ensureSession 提到 render 期（幂等：Map 命中即返回）
```

代码注释与单测证据齐备（`useChatStreamSession.ts:22-27/71-80`；曾记 A5 单测红：`expected 0 to be greater than 0`）。

**更优解（v1.1 明确，取代 render 期 ensureSession）**：`chatStreamStore.ts:503-529` 已把 `getClockSignals` 改为按会话惰性缓存 + 三字段全为活 getter，使 memo 命中与否都不影响正确性。若进一步给"**不存在的会话**"也返回**按 id 缓存的稳定零信号视图**（而非模块级共享 `ZERO_CLOCK`），则：

1. 首次 render 拿到的稳定视图引用不随 `heartbeatTs` 变化 → memo 不会永久钉死零钟面；
2. `useChatStreamSession.ts:28` 的 render 期 `ensureSession` 可**直接删除**，D2 归零；
3. 附带修掉"render 被丢弃 → 幽灵会话"隐患（该隐患与 D3 叠加：幽灵会话无订阅者 → `releaseUnsubscribed` 永不触发 → 永不淘汰）。

**读路径纪律实测合规**：`chatStreamStore.ts:268` `getSnapshot` 返回 `EMPTY_SNAPSHOT` 而**不**惰性创建，`:266` 注释明载"不惰性创建"；仅 `:272`/`:284` 的 `subscribe`/`subscribeEvents` 内创建（订阅为显式动作，创建合理，见 3.8-C）。

### 3.3 🟡 D3：终态资源上限缺 LRU 与容量上限

**文档要求**：`:1099`（4.6.2）「任务正常完成 → 保留最终快照，**按 TTL/LRU 释放连接资源**」；`:1759`「Store **必须有明确的终态资源上限**……按终态 TTL/LRU 释放」。

**实现**（`chatStreamStore.ts:535-583`）

```text
releaseUnsubscribed(id, 60s)：60s 宽限 → 释放客户端资源（abort + 清定时器 + 中止轮询）
  └─ if (isTerminalStatus(cur.status)) → setTimeout(evictSession, 600_000)   ← 仅此处排期终态 TTL
evictSession(id)：Map.delete + 清定时器（:567-583）
```

**缺口（三项，均实测确认）**

1. **无 LRU、无条数上限**：全 Store 检索 `sessions.size` / `MAX_SESSION` / `LRU` / `容量` / `上限` 命中 **0 处** → 长跑下 `Map` 无界增长。
2. **非终态与 idle 条目永不淘汰**：`evictSession` 只从终态 TTL 回调进入；`status` 为 `active`/`idle` 的条目无任何排期路径。
3. **终态但仍有订阅者时永不淘汰**：`evictSession` 首行 `if (cur.listeners.size > 0) return`（`:569`），而 TTL 只在"曾经零订阅"时排期一次 → 终态 + 持续订阅的会话条目永久驻留。

### 3.4 🟡 D4：恢复态未参与 UI 决策，回退历史仍自动发生

**文档要求**：`:1084`（4.6.1⑤）「GET 续传必须处理 `not_found`/`task_interrupted`/`task_state_incomplete`/`persistence_gap`/`persistence_degraded`/已完成/缓冲过期/后端重启；**不能把"回退历史"当成自动发生的行为**」。

**① D1 切回路径 —— 🔴 代码错（唯一一处结构性选择站错）**

| 场景 | 实际发生什么（逐行可证） | 判定 |
|---|---|---|
| S1 任务跑到第 8 步，切走 30 秒再切回 | `restore()` 用 ≤5 秒前的备份覆盖活会话 → 第 7、8 步从 UI 消失，第 9 步接着出现 → 用户看到步骤倒退再闪烁。改造前是"切回是白板"（用户知道断了），现在是"步骤在跳"（用户以为系统抽风）→ **比改造前更糟** | 代码错 |

> **结论**：代码错，必须改。改代码的同时蓝图也要改（否则下次照蓝图重做还会错）。
