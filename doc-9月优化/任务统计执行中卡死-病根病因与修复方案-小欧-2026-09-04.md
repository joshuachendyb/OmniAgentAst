## 背景

失败任务（如 quota_exceeded / 工具全部不可用等）结束时，右上角 `任务统计` 板块的状态 Tag 长期显示 **executing（执行中）**，与实际的失败终态不符，且永不刷新。北京老陈反馈已尝试修复 4-5 次未果，要求先找准病根病因、再定修复方案。本表将**现象 → 两套数据源差异 → 病根病因竞态 → 方案对比 → 三堂会审通过的修复代码方法**一并对齐。

---

## 一、问题现象

1. 任务实际已失败（LLM 配额耗尽 / 工具执行失败 / 任务异常终态）。
2. `TaskInfoBar`（输入框上方）状态徽标 **已能正确转 failed**（09-03 已修复）。
3. 但右上角 `任务统计`（StaticStatsBlock）标题行 Tag **一直显示 executing（灰）**，永不转 failed。
4. 展开 `任务统计` 后，错误信息（error_type / error_message）可能已出现，但状态 Tag 仍是 executing。

### 1.1 关键观察：同一个失败任务，两个状态展示组件一个对、一个错

| 组件 | 位置 | 状态数据源 | 当前状态 |
|---|---|---|---|
| **TaskInfoBar 徽标** | 输入框上方 | `useTaskInfo` / `hasFailedFinal` → 读**实时 SSE** `steps` 与 `frames.finalStats` | ✅ 09-03 已修好 |
| **StaticStatsBlock 任务统计 Tag** | 右上角 `任务统计` 标题行 | **直接读 `detail.status`**（REST `TaskDetail`） | ❌ 未修，就是它卡 executing |

## 二、当前链路分析

### 2.1 前端 `StaticStatsBlock.tsx` 直接信任 `detail.status`

`StaticStatsBlock.tsx`:

```tsx
// :32-35 状态颜色映射，只有 completed/failed
const STATUS_COLOR_MAP: Record<string, string> = {
  completed: 'success',
  failed: 'error',
};
// :49 未命中映射(如 executing) 落到 default(灰)
const statusColor = STATUS_COLOR_MAP[detail.status] ?? 'default';
// :90-92 标题行 Tag 直接渲染 detail.status
<Tag color={statusColor}>{detail.status}</Tag>
```

`detail` 来自 `RightViewer.tsx` 通过 `executionApi.getTaskDetail(activeTaskId)` 拉取的 REST `TaskDetail`，其 `.status` 即后端 `chat_tasks.status` 列（`storage.get_task_detail` 原样返回该列）。

### 2.2 `RightViewer.tsx` 拉取 detail 的时机（埋下竞态）

`RightViewer.tsx`:

```tsx
// :110-117 isCurrentLive 判定
const _hasFinal = liveSteps.some((s) => s.type === 'final');   // SSE 一到 final 即 true
const isCurrentLive =
  activeTaskId != null &&
  activeTaskId === serverTaskId &&
  !_hasFinal &&
  (receiving || liveBadge === 'running' || liveBadge === 'paused');

// :179-218 拉取历史 detail，依赖 isCurrentLive
useEffect(() => {
  if (!activeTaskId || isCurrentLive) { setDetail(null); return; }
  // ... executionApi.getTaskDetail(activeTaskId) + getTaskSteps
}, [activeTaskId, sessionId, isCurrentLive]);
```

**关键**：一旦 SSE 收到 `final` 事件 → `_hasFinal = true` → `isCurrentLive = false` → effect **立刻、仅此一次** 拉取 `getTaskDetail`。**若此刻后端 `chat_tasks.status` 尚未落为 failed，则拉回 stale 的 `executing`，且该 effect 无失败后重拉机制 → 永久缓存 executing。**

## 三、病根病因（前端+后端竞态）

### 3.1 后端时序：SSE final 事件先到，DB status 落库后到

`backend/agent_runner.py` 失败终态有两件事，**顺序先后且耗时不同**：

1. **SSE 发 final 事件（快，主循环内同步发生）**
   - `answer_handler.handle_answer` 里 `emit_final_with_stats(FinalStep(outcome="failed"))` → `agent_runner` 主循环 `else` 分支（`agent_runner.py:347-348`）**立即** `_append(event_dict)` → 写入内存 `event_log` 缓冲 → SSE 消费者**瞬间**推给前端。

2. **DB 落库 chat_tasks.status='failed'（慢，异步 offload）**
   - 同一任务的 `finally` 块里 `_persist_final(db.atxn("chat", _finalize_task_db))`（`agent_runner.py:528`，`db_ops.update_task(status='failed')`）。
   - 这段是 **`db.atxn` 后台线程 offload**（专为「后端卡死修复」设计，见注释），**耗时明显慢于 SSE 事件推送**，且与 ①②无同步屏障。

```
主循环(①)
   emit_final_with_stats(FinalStep(failed))
     ├─ _persist(final 步骤)          ← 落 chat_task_steps（执行步骤表）
     └─ _append(final SSE)   ← 前端此刻就收到 final → _hasFinal=true → 立刻拉 getTaskDetail
finally(②)
   _persist_final( update_task(status='failed') )  ← chat_tasks.status 此时才落库（可能尚未完成）
```

### 3.2 前端连锁反应

```
SSE 收到 final 事件
  → RightViewer._hasFinal = true
  → isCurrentLive = false
  → effect 立刻 getTaskDetail(activeTaskId)
       ↓ (可能早于后端 finally 的 status 落库)
  → detail.status = 'executing'   ← stale
  → StaticStatsBlock 渲染 executing，永不刷新
```

### 3.3 病根一句话

> **前端 `StaticStatsBlock` 直接信任刚拉取的 `detail.status`，而该值因「SSE final 事件先到、DB chat_tasks.status 落库后到」的竞态而陈旧为 executing；且 effect 无失败后重拉/兜底，导致永不刷新。**

### 3.4 为什么 TaskInfoBar 徽标没这问题

它不读 `detail.status`，而是从**实时 SSE 数据**（`steps` 里 `final.outcome='failed'` / `frames.finalStats.final_status`）派生，这些在①就到达前端，不依赖 DB 写库，故能正确转 failed。这正是 09-03 系列修复（`useTaskInfo.hasFailedFinal` + `agent_telemetry.build_final_stats_step` 增发 `final_status`）奏效的原因——**但只覆盖了 TaskInfoBar，没覆盖 StaticStatsBlock。**

---

## 四、修复方案对比

### 4.1 方案一（后端加固：确保 status 落库后再发 final）

**思路**：把终态 `final` / `final_stats` 这个 SSE 事件延迟到 `chat_tasks.status` 落库成功之后再发给前端。消除竞态源头。

### 4.2 方案二（前端补拉：拿到 final 后对 getTaskDetail 延迟补拉直到终态）

**思路**：`RightViewer` 在 final 后不信任第一次 getTaskDetail，改为轮询/延迟重试直到 status 为终态。

### 4.3 对比

| 维度 | 方案一（后端先落库） | 方案二（前端补拉） |
|---|---|---|
| 代码量 | 集中一处，小 | 分散，新增轮询+退避+重试+取消 |
| 逻辑简洁 | ✅ 直线、单一收口 | ❌ 绕（循环/延迟/终止条件） |
| 治本/治标 | ✅ 治本（消除竞态源头） | ❌ 治标（等后端落库） |
| 符合后端为主原则 | ✅ | ❌ |
| 出错面 | 低（终态 SSE 单点收口） | 高（异步边界多、状态叠加） |

### 4.4 结论

**选用方案一**。逻辑简洁、治本、符合「后端为主、前端迎合后端」原则。以下修复代码方法即方案一，已过三堂会审。

## 五、方案一修复代码方法（三堂会审通过）

> **只写方法，未实际改代码。** 以下为设计到位的修复逻辑，北京老陈拍板后另行落码。

### 5.1 设计要点

- **单点收口**：只在 `agent_runner.py` 主循环的 `else` 分支处理终态 SSE 的时机改动，不碰 `answer_handler` / `react_cycle` 内部逻辑（SRP）。
- **仅延迟 SSE，不延迟落库**：`final` / `final_stats` 的 `_persist`（执行步骤落 `chat_task_steps`）仍即时；只把「`_append`（推 SSE）」延迟到 DB status 落库成功之后。
- **过程事件不受影响**：`thought` / `action` / `observation` / `chunk` / `error` 等非终态事件仍即时 `_append`（保持实时性）。

### 5.2 修改点：`agent_runner.py` 主循环

**改动前（`agent_runner.py:327-348` 的 else 分支）**：final / final_stats 走 `_persist` + 立即 `_append`。

**改动后**：

```python
# 在 run_agent_in_background 内、主循环前声明待发终态缓冲（KSIS 直线，单一字段）
_pending_terminal: List[Dict] = []   # 终态 final/final_stats 待 DB status 落库后统一补发

# 主循环 else 分支内：
else:
    await _persist(event_dict)              # final/final_stats 仍即时刻库（行为不变）
    if event_type == "action":
        _action_steps.add(event_dict.get("step", 0))
        await _append(event_dict)           # action 非终态，即时 SSE
    elif event_type == "final":
        # 终态 final：不立即 _append，先入待发缓冲，待 finally DB status 落库成功后再补发
        if event_dict.get("outcome") == "completed":
            _s = event_dict.get("step", 0)
            if _s not in _action_steps and _s in _has_chunk_steps:
                _pending_terminal.append({k: event_dict[k] for k in ("type", "step", "timestamp", "outcome")})
            else:
                _pending_terminal.append(event_dict)
        else:
            _pending_terminal.append(event_dict)   # failed / cancelled 等终态
    elif event_type == "final_stats":
        _pending_terminal.append(event_dict)        # final_stats 终态统计，随 final 一起补发
    else:
        await _append(event_dict)                   # 其余（含 chunk/thought-start 等）即时 SSE

# stream_state.current_content 更新逻辑保留原样（主循环内 final 已处理，不受影响）
```

### 5.3 修改点：`agent_runner.py` finally 块

**改动前（`agent_runner.py:527-528`）**：`_persist_final(update_task(status))` 后直接结束。

**改动后**：在 `_persist_final` 成功之后、生命周期清理（`task_cleanup` 等）之前，补发待发的终态 SSE：

```python
# 终态必达防二次cancel(_persist_final 小欧 2026-08-24)
try:
    await _persist_final(db.atxn("chat", _finalize_task_db))
finally:
    # 方案一 收口：DB status 落库成功(或已尽力)后，统一补发终态 final/final_stats SSE —— 小欧-2026-09-04
    # 此时 chat_tasks.status 已为 failed/completed/cancelled，前端 getTaskDetail 拉到终态即正确
    for _term_dict in _pending_terminal:
        await _append(_term_dict)
    _pending_terminal.clear()
```

> 说明：用 `finally` 包裹补发，保证无论 `_persist_final` 是否抛异常，终态 SSE 都不会丢失（前端终态可达性优先，宁早勿丢；DB 正常路径下 status 已先落库，竞态即消除）。

### 5.4 关联影响核验（不退化）

| 影响面 | 核验 | 结论 |
|---|---|---|
| 前端 `_hasFinal` 触发时机 | 延后到 DB status 落库后，故 `getTaskDetail` 拉到的是终态 | ✅ 修复 |
| `stream_state.current_content` | 主循环 final 处已提前更新（`agent_runner.py:351`），`_finalize_task_db` 读 `saved_content` 不受影响 | ✅ 不退化 |
| `finally` 守卫补发 FinalStep（`:415-441`） | 异常/取消路径仍由守卫即时 `_append`，不经过 `_pending_terminal` | ✅ 异常兜底保留 |
| 重连窗口 / 缓冲回收（`:610-612` reclaim 300ms） | 终态 SSE 补发在 reclaim 之前完成（同一 finally 内），事件可达 | ✅ 不退化 |
| `final_stats.duration` | `build_final_stats_step` 在 emit 时已算好，缓存放行后值一致 | ✅ 不退化 |
| 非终态事件实时性 | 仅 final/final_stats 延迟，其余即时 | ✅ 不退化 |

## 六、三堂会审

### 6.1 合规检查（10 大规范）

- **SRP**：改动只负责「终态 SSE 发放时机」，职责单一，不新增旁路逻辑。 ✅
- **DRY**：`final` 的短信号/完整发逻辑原样保留，仅把 `_append` 改入缓冲，无重复实现。 ✅
- **KISS-DIRECT**：直线缓冲-补发，无中间层/无注册表/无跳转；单点收口 `_pending_terminal`。 ✅
- **SLAP**：主循环负责收集，finally 负责统一补发，同一抽象层，不混搭。 ✅
- **YAGNI**：不新增事件类型、不新增线程/队列，仅字段缓冲 + 补发循环。 ✅
- **禁止 backward**：不保留旧「立即发 final」的兼容分支，直接改为缓冲补发，行为面向新时序。 ✅
- **OCP 等重构四规范**：不涉及库/框架扩展，无继承体系，天然满足。 ✅
- **复用优先**：复用既有 `_append` / `_persist` / `_persist_final` channels，无重造轮子。 ✅

### 6.2 合理检查（逻辑最优雅）

- 方案直接把「状态展示依赖 DB status」与「DB status 落库时机」两个环节对齐，从源头消除竞态，逻辑最直线。
- 前端无需新增任何轮询/延迟/取消复杂度，维持现有 effect 简单结构。
- 终态 SSE 延迟量级为一次 `db.atxn` 后台写（毫秒级），用户无感知，实时性不受实质影响。

### 6.3 关联逻辑检查（增强不退化）

- 后端 status 落库时序：SSE final 事件 → 前端拉详情，现保证 status 已终态，**前端任务列表/统计/历史回放全部增强为正确终态**。
- 异常/取消分支仍由 `finally` 守卫即时补发，**兜底逻辑不回归**。
- `final_stats` 与 `final` 一并补发，`useTaskInfo.hasFailedFinal` 的 `frames.finalStats.final_status='failed'` 通道在 DB 落库后也必然正确，形成双通道一致。
