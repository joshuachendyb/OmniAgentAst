## 三、关键问题详解（STRONG / MED 必读）

### 3.1 【1·STRONG】useSessionTasks 刷新清空任务最终答复（H2）

**现象**：切换标签页（`visibilitychange`）、会话切换后，左列任务列表所有历史任务的"最终答复"被清空；仅当前选中任务经 updateTaskResponse 重新写回，其余任务回到只有占位 user 内容、答复区恒空白。

**证据链**：
- `useSessionTasks.ts:49`：`setTasks(res.tasks.map(t => ({ ...t, response: undefined })))` —— 任何一次全量 refresh 都把 response 置 undefined；
- `:61-66` sessionId 变化即 refresh；`:71-81` 页面回到前台（visibilitychange）又 refresh；
- `:90-94` updateTaskResponse 仅处理当前选中任务写回。

**推演**：用户提交任务 → 切到其他标签 → 回来（visibilitychange）→ listTasks 返回（DB 中含 response）→ 前端强制清空。此时 updateTaskResponse 只回填选中任务，其余任务"成功/失败"下无最终答复文本；数据并未丢失（DB 有），纯前端展示丢失，且无任何重建入口（除非再次选中后才回填——选中即回填，故**非选中任务永久空白**）。

**整改方向**：全量 refresh 不置 response；恢复选中任务逐条 onSelect 时按 task_id 从 DB/缓存回填；或将 response 写入 task 本地缓存（键 task_id）。

### 3.2 【2·STRONG】历史加载缓存自证失效（H3）

**现象**：历史会话/断线续传恢复后，消息流不出现或出现的是旧快照，DB 中的真实历史内容与 UI 永久失联。

**证据链**：
- `useChatPersistence.ts:315` 调 `loadHistoryMessages(data.sessionId)` 未传 `{ useCache: false }`；
- `utils/chatHistory.ts:130` `options?.useCache !== false` → 默认缓存优先；`:142` 缓存命中条件 `state.sessionId === sessionId`（同会话即命中）。

**推演**：续传恢复时先写一份 L2 快照（getSnapshot 落 sessionStorage），随后 loadHistoryMessages 命中"刚写入的同一会话快照"——校验时永远命中缓存、永远不会回源 DB。只有当缓存过期（SESSION_EXPIRY 5 分钟）或 sessionId 失配时才会真正拉 DB → 404 自证逻辑形同虚设。**缓存与 DB 出现分叉时，UI 永远展示旧快照**。

**整改方向**：恢复/续传路径传 `{ useCache: false }` 强制回源；缓存仅作纯 L2 崩溃兜底，不作为恢复主数据源。

### 3.3 【3·MED】退避重连窗口穿透 → 双 GET + 序号倒退（T1）

**证据链**：`chatStreamTransport.ts` scheduleReconnect `:976-1023` 置 reconnectStatus='reconnecting'；resume `:608` 的守卫依赖 `pumpActive/resumeInFlight/isProcessing` 三者——dead-gear 内重试失败后三者全 false（isProcessing 未因 reconnectStatus 置真）；`broadcastHandlers.onComplete` `:741-753` 在 reconnectStatus 期间提前清 ref。resume() 入口 `:505` 附近无 reconnectStatus 检查 → 穿透。

**推演**：传输层退避期间用户点击恢复/并发 resume → 用 ≤5s 前的备份覆盖 lastSeq（序号倒退）、executionSteps、currentResponse，并立即发 GET；旧定时器到点后再次 resumeStreamRequest → 同一 task 两个 GET 并存（abortController `:199-202` 槽位被后发覆盖，旧请求不可终止）。**A1 指纹去重与 sseParser seq 守卫能防"重放内容重复渲染"，但防不了序号倒退与双连接的资源浪费/乱序**。

### 3.4 【4·MED】空串/旧 sessionId 重发（H13）

**证据链**：`useChatStreaming.ts:424` `customSessionId ?? sessionId ?? ''`；`chatStreamStore.ts:565` `ensureSession(sessionId)` 无空串守卫（`:599` resume、`:640` stop 均守卫 falsy）；executeSend 404 分支 `:523-528` 置 ref+state 为 null 后 `:566` 的 `currentSessionIdRef.current ?? sessionId ?? undefined` 中闭包 `sessionId` 是旧值。

**推演**：①首条消息且未建会话（简短 timeout 场景）→ 空串 sendMessage → ensureSession('') 造 '' 鬼会话，后端收到 session_id=''；②任务 404/重建后，重发仍带旧 invalid id。注释"SSE将不带sessionId"（:523 附近）落空。

**整改方向**：sendMessage 入口对空串 `return`（与 resume/stop 对齐）；executeSend 404 路径把 `currentSessionIdRef.current=null` 语义改为传 `undefined`，并防止闭包 state 过期（经 ref 读当前值）。

### 3.5 【5·MED】任务状态标签恒"成功"（H18）

**证据链**：`TaskListPanel.tsx:206`（色）、`:213`（文）：`t.status === 'failed' ? '失败' : '成功'`。

**推演**：listTasks 状态域为 `executing/paused/completed/failed/cancelled`。执行中、已暂停、已取消任务全部渲染绿色/灰"●成功"。**活跃执行中的任务左列即显示"成功"**，用户无法从状态标签识别运行中/取消。

**整改方向**：全状态映射表（executing→执行中/paused→已暂停/completed→成功/failed→失败/cancelled→已取消），颜色分档。

### 3.6 【6·MED】Escape 取消被 onBlur 保存推翻（H19）

**证据链**：`ChatHeader.tsx:162-168` onBlur 在 `savingRef.current || savedThisEditRef.current` 均假时无条件 `handleSaveTitle()`；Escape `:154-157` 仅调 `onEditingCancel()`（useChatTitle:30-32 仅 `setEditingTitle(false)`），不清 savedThisEditRef。该文件 2026-08-27 修复#12 已实证"Input 卸载触发 blur"。

**推演**：编辑标题 → 改了几个字 → 按 Escape 想取消 → Input 卸载必然触发 onBlur → handleSaveTitle 保存"被取消"的改动。**Escape 取消语义失效，等于强制保存**。

**整改方向**：Escape 分支置 `savedThisEditRef.current = true`（或专用取消 ref `skipNextBlurRef`），onBlur 命中即 return。

### 3.7 【7·MED】running 任务误判"已完成"（H12）

**证据链**：`useTaskInfo.ts:136-141` `badge==='running' && (detail.duration>0 || detail.updated_at)` → badge='completed'。

**推演**：该"DB 滞后兜底"把含 updated_at/duration 的 running 任务一律打 completed。实际 backend 在 running 期间会随步骤更新 `updated_at`（连接不活跃但任务后台执行时同样满足）→ **真实执行中任务右侧状态显示"已完成"**。DB 滞后兜底应该只认 SSE final 帧驱动，不应以存在时间字段反推。

## 五、结论与建议

1. **优先整改（P0/STRONG 2 条 + P1/MED 6 条）**：#1 H2 刷新清空答复、#2 H3 缓存自证、#3 T1 双 GET、#4 H13 空串/旧 id、#5 H18 状态标签、#6 H19 Escape 保存、#7 H12 状态误判、#8 H1 rightOpen deps。此 8 条均可单测/单测级验证复现。
