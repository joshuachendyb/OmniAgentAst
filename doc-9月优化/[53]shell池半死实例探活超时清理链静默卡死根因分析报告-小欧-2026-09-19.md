## 二、病根病因挖掘实证分析

### 2.1 三层防线架构回顾（正常应如何演进）

| ② 探活失败上报 | shell_engine.py:367（_probe） | 打 `[卡死C8] 探活失败(半死)→已销毁` → `_close()` → 返回 False | ❌ **缺位** |

**结论**：①已执行，②③④全部未执行 → 卡死点位于 **①的清理链本身**（`shell_engine.py:518 _kill_tree()` → `:519 _close()` → `:520 return _ERROR_TIMEOUT` 之间），`_exec_locked` 未返回，导致 `_probe` 的 367 行永远走不到。

### 2.2 "命令超时3s" 是探活超时，非业务超时

- shell_engine.py:163 `_PROBE_TIMEOUT = 3`（探活默认超时）
- shell_engine.py:358-370 `_probe()`：`self._exec(_PROBE_CMD, timeout=timeout or _PROBE_TIMEOUT)` → 探活命令 `Write-Output __OMNI_PROBE__`，3s 未出 `__OMNI_PROBE__` 即判超时
- 业务命令超时是 LLM 传参（示例中 git diff=15s），与本次 3s 不符
- **→ 本次 3s 超时 = acquire 复用池实例时对该半死实例的响应性探活失败**

### 2.4 半死实例来源推断

- 池中两实例 `22064`、`12628` 为此前 step 使用放回的实例
- 其中一实例已进入「假活」状态（进程未死但 stdin 不再响应），探活写 `_PROBE_CMD` 后 `.code` 文件 3s 内未生成 → 触发 517 超时分支
- 半死根因候选（需探针进一步确认）：前序命令残留未消费管道、PS 引擎锁被长命令 hold、进程被系统降级/挂起

### 2.5 为何清理链静默卡死（核心病根）

静态审读 `_kill_tree()`（546-559）与 `_close()`（561-593）：

```python

        try:
            subprocess.run(["taskkill", "/T", "/F", "/PID", str(self._proc.pid)],
                           capture_output=True, timeout=SUBPROCESS_TIMEOUT_SHORT)  # 5s 有界
        except Exception as e:
            logger.warning(f"[卡死C11] taskkill异常 ...")
            ...

def _close(self):
    if self._proc:
        try:
            if self._proc.poll() is None:
                self._proc.kill()
                self._proc.wait(timeout=SUBPROCESS_TIMEOUT_SHORT)  # 5s 有界
        except Exception as e:
            logger.warning(f"[卡死C11] 关闭进程失败 ...")
        ...
    _safe_unlink(self._stderr_path)  # 3 次重试 × 0.05s = 有界
```

- 两函数均带 `timeout=`/重试上限，均有 except 留痕日志
- **但本次 517 打完后，C11/C9 均无留痕，且②③④全部缺位**
- → 卡死原语不在任务层超时范围内，属 **OS 级阻塞**（`taskkill`/`proc.wait()` 被 Windows 内核层挂起，未抛异常、未返回），python 层无法感知，只能靠最外层保险丝截断
- 另：bash 分支的 git diff 自 04:58:03 三路检测后亦无完成日志 → 同波被保险丝一次兜底，二者在同一 to_thread 线程池窗口内被整体截断

### 2.6 病根一句话

> **池中半死 PS 实例被 acquire 复用时探活 3s 超时，进入 `shell_engine.py:517` 超时清理分支后，`_kill_tree()`/`_close()` 在 OS 级原语上静默卡死（无异常、无日志），`_probe` 的失败上报与池层 C13 重试全部不可达，最终由引擎保险丝 630s 硬截断。**

## 三、解决方法最佳逻辑的方法

### 3.1 解决原则（KISS-DIRECT + 不退化）

1. **先诊断后修复**：静态代码无法 100% 钉死 OS 级阻塞行，必须先在 517-520 清理链注入 perf 探针日志，复现一次拿到精确卡点行，再对症修，杜绝盲改。
2. **一切清理必须有界且可观测**：超时分支内部每步都要有时间戳留痕，任何一步被系统挂起都能在日志定位。
3. **三防线闭环**：探活失败 → 上报 → 池层剔除重试 → 重建就绪，任一环节缺失即为 bug，必须有日志保证可见。
4. **禁止 backward**：不搞「兼容旧路径」，直接强化现有有界清理链。

### 4.2 M2 新增 `_poll_pid_exit()` 有界轮询确认函数

**位置**：shell_engine.py:236 `_poll_for_file` 之后，模块级新增

```python
# ── 原代码（无此函数） ──

# ── 新代码（插入于 _poll_for_file 之后） ──
def _poll_pid_exit(proc: Optional["subprocess.Popen"], timeout: int, interval: float = 0.1) -> bool:
    """[M2] 有界轮询确认进程已退出：替代裸 `proc.wait(timeout)` 的二次确认。
    背景: taskkill/proc.wait 可能在 Windows 内核级原语上静默挂起(无异常无返回, 见章2.5) → 本轮询
    poll() 为纯查询不阻塞, 超 timeout 秒即返回 False, 绝不永久阻塞 — 小欧 2026-09-19"""
    deadline = time.monotonic() + timeout
    while True:
        if proc is None or proc.poll() is not None:
            return True
        if time.monotonic() >= deadline:
            return False
        time.sleep(min(interval, max(0, deadline - time.monotonic())))
```

**设计解析**：
- `proc.poll()` 是**非阻塞查询**，与 wait/find 的原语调用性质不同，不会进入内核待等待 → 天然不卡
- 返回 bool 供调用方判断「确认死亡」/「放弃确认」，配合 M3 二次确认

    # [M3] 二次确认(B, 小欧 2026-09-19): taskkill 后轮询 poll() 确认进程已亡, 未亡则 kill() 兜底 + 留痕
    if self._proc and self._proc.poll() is None:
        try:
            subprocess.run(
                ["taskkill", "/T", "/F", "/PID", str(self._proc.pid)],
                capture_output=True, timeout=SUBPROCESS_TIMEOUT_SHORT,
            )
        except Exception as e:
            logger.warning(f"[卡死C11] taskkill异常 → proc.kill()兜底 (pid={self._proc.pid}): {e}")
        self._confirm_killed()                          # ── [M3] 二次确认 ──

def _confirm_killed(self):
    """[M3] taskkill 二次确认（方向B）: taskkill 后轮询 poll() 确认进程已亡, 未亡则 kill() 兜底 + 留痕 — 小欧 2026-09-19"""
    if self._proc is None:
        return
    if not _poll_pid_exit(self._proc, SUBPROCESS_TIMEOUT_SHORT):
        pid = self._proc.pid
        logger.warning(f"[卡死C11] taskkill 后 {SUBPROCESS_TIMEOUT_SHORT}s 进程仍在(疑似二次确认未亡) → kill() 兜底 (pid={pid})")
        try:
            self._proc.kill()
        except Exception:
            pass
        _poll_pid_exit(self._proc, SUBPROCESS_TIMEOUT_SHORT)   # 兜底后再次确认, 防假活残留
```

**设计解析**：
- 原代码 taskkill 失败才 kill 兜底，但 **taskkill "成功返回" ≠ 进程树已亡**（被杀进程可能未及时回收）→ 半死实例「假活」残留
- 二次确认把「taskkill 已执行」与「进程真的没了」分开验证，堵死假活源头
- `_confirm_killed` 独立成方法（SRP），M5 可复用它实现去重防护

### 4.6 M6 `_exec_locked()` 超时分支清理链硬超时守卫（核心）

if not _poll_for_file(paths.code, timeout):

- 若超守卫阈值 → `logger.error` 明确标记「OS级挂起」+ 放行；此后 acquire 会因 `_alive=False` 走 `_start` 重建（M8 分工）

def _probe(self, env: Optional[Dict[str, str]] = None, timeout: Optional[int] = None) -> bool:
    """...docstring 不变..."""
    if self._proc is None or self._proc.poll() is not None:
        return False
    try:                                            # [M7] 保序: 底层 _exec 任何异常都被捕获, 367 上报必达 — 小欧 2026-09-19
        result = self._exec(_PROBE_CMD, timeout=timeout or _PROBE_TIMEOUT)
    except Exception as e:
        logger.warning(f"[卡死C8] 探活异常(非timeout)→已销毁重建 (pid={getattr(self._proc, 'pid', None)}, err={e})")
        self._close()
        return False
    if result.get("timed_out"):

        self._close()
        return False
    return "__OMNI_PROBE__" in result.get("stdout", "")
```

**设计解析（方向C）**：
- 原代码若 `_exec` 抛异常（而非返回 `timed_out`），会**跳过 367 上报**直接向上冒 → ①缺、二层防线失序 → acquire 异常路径 release 槽位后直接把异常抛给 execute_shell_command → 屏蔽了 C13 重试
- 新代码：`_exec` 任何异常都等价于「探活失败」→ `_close` → `return False` → acquire 收到 `False` 走 Phase3 C13（池层剔除重试），三层防线闭环恢复
