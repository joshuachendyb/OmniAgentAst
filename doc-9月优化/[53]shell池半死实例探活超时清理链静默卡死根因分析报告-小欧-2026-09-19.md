### 2.2 "命令超时3s" 是探活超时，非业务超时

- shell_engine.py:163 `_PROBE_TIMEOUT = 3`（探活默认超时）
- shell_engine.py:358-370 `_probe()`：`self._exec(_PROBE_CMD, timeout=timeout or _PROBE_TIMEOUT)` → 探活命令 `Write-Output __OMNI_PROBE__`，3s 未出 `__OMNI_PROBE__` 即判超时
- 业务命令超时是 LLM 传参（示例中 git diff=15s），与本次 3s 不符
- **→ 本次 3s 超时 = acquire 复用池实例时对该半死实例的响应性探活失败**

### 2.4 半死实例来源推断：shell 执行环境污染遗传（源头机制）— 小欧 2026-09-19 07:00:36

> 北京老陈总结的源头机制：本池问题不是「某一组 tool 单独失败」，而是**前一组 tool 的 shell 执行完成后没有清理干净 → 环境污染 → 遗传到下一组 tool 复用同一个池实例的 shell 里**。本节把它钉死为半死实例的核心来源，并解释其偶发性与 LLM 调用策略的关系。

#### 2.4.1 池实例的「环境」不是干净复制的，而是累积的

- 池中两实例 `22064`、`12628` 为此前多组 tool 复用放回的实例，PS 会话**从启动后一直存活**，环境状态逐组累积
- 若前一组 tool 执行的 shell 出了**未清理净的副作用**，就会残留在该实例里并遗传给后一组：
  - **残留进程/作业**：命令启动了后台进程/定时器/管道对端（Start-Job、Start-Process、& 后台符），命令"结束"但子进程仍活着
  - **未消费管道 / 半读输出**：前一命令 stdout/stderr 没被读完就返回，句柄缓冲残留
  - **未回收临时文件/句柄**：C12 链上 shell_engine 建的临时文件、stderr 文件未被 `_safe_unlink` 全部回收
  - **PS 会话内部状态污染**：上一命令改变了 $LASTEXITCODE/环境变量/当前目录/Profile 状态，影响下一命令解析
- 下一组 tool 复用同一实例执行 → **蒙受上一次的残留环境污染** → 命令行为异常，甚至实例进入「假活」（进程未死但 stdin 不再响应）

#### 2.4.2 环境污染 → 假活 → 卡死的完整链路（闭环）

```
LLM 调用策略(工具序列/并发复用) → 前一组 tool 执行残缺(污染未清理)
   → 污染残留遗传 → 下一组 tool 复用同一池实例 → 命令执行异常/假活
   → acquire 响应性探活 3s 超时(517) → 清理链 OS 级静默卡死 → 保险丝 630s
```

#### 2.4.3 偶发性的解释：与 LLM 调用策略强相关

- 环境污染**不是必然发生**，而是取决于 LLM 每次的工具调用策略：
  - 是否连续多组 tool 复用同一个实例（并发间隔短）
  - 前一组执行的命令是否"干净"（纯查询命令几乎无污染；带副作用命令如后台、管道、写文件才可能产生残留）
  - 池满时是否强制复用旧实例（vs 新建干净实例）
- 本次实证：step3 四连并行全部成功（对照干净），step4 git log 复用旧实例后 3s 探活超时 → **同一实例、不同调用策略（复用时机/命令性质）结果不同**，正是「偶发」的直接证据
- **推论**：修复不能只补「超时后怎么清理」（那是中后段），必须**在源头防污染遗传**（用完即销毁/复用前校验/残留清理），并有探针实证

### 2.5 为何清理链静默卡死（核心病根）

静态审读 `_kill_tree()`（546-559）与 `_close()`（561-593）：

```python
def _kill_tree(self):
    if self._proc and self._proc.poll() is None:
        try:
            subprocess.run(["taskkill", "/T", "/F", "/PID", str(self._proc.pid)],
                           capture_output=True, timeout=SUBPROCESS_TIMEOUT_SHORT)  # 5s 有界
        except Exception as e:
            logger.warning(f"[卡死C11] taskkill异常 ...")
            ...

def _close(self):
    if self._proc:
        try:
            if self._proc.poll() is None:
                self._proc.kill()
                self._proc.wait(timeout=SUBPROCESS_TIMEOUT_SHORT)  # 5s 有界
        except Exception as e:
            logger.warning(f"[卡死C11] 关闭进程失败 ...")
        ...
    _safe_unlink(self._stderr_path)  # 3 次重试 × 0.05s = 有界
```

- 两函数均带 `timeout=`/重试上限，均有 except 留痕日志
- **但本次 517 打完后，C11/C9 均无留痕，且②③④全部缺位**
- → 卡死原语不在任务层超时范围内，属 **OS 级阻塞**（`taskkill`/`proc.wait()` 被 Windows 内核层挂起，未抛异常、未返回），python 层无法感知，只能靠最外层保险丝截断
- 另：bash 分支的 git diff 自 04:58:03 三路检测后亦无完成日志 → 同波被保险丝一次兜底，二者在同一 to_thread 线程池窗口内被整体截断

### 2.6 病根一句话

> **源头（环境污染遗传）**：前一组 tool 的 shell 执行完成后未清理干净（残留进程/管道/句柄/会话状态），污染累积残留于池实例，随复用遗传给下一组 tool。
> **触发（复用+探活）**：下一组 tool 复用该污染实例时，命令行为异常/假活 → acquire 响应性探活 3s 超时（`shell_engine.py:517`）。
> **失守（清理链静默卡死）**：进入 517 超时清理分支后，`_kill_tree()`/`_close()` 在 OS 级原语上静默卡死（无异常、无日志），`_probe` 失败上报与池层 C13 重试全部不可达 → 引擎保险丝 630s 硬截断。
> **偶发**：是否发生取决于 LLM 调用策略（复用时机 + 命令是否带副作用），故非必现。

## 三、解决方法最佳逻辑的方法

### 3.1 解决原则（KISS-DIRECT + 不退化）

1. **先诊断后修复**：静态代码无法 100% 钉死 OS 级阻塞行，必须先在 517-520 清理链注入 perf 探针日志，复现一次拿到精确卡点行，再对症修，杜绝盲改。
2. **一切清理必须有界且可观测**：超时分支内部每步都要有时间戳留痕，任何一步被系统挂起都能在日志定位。
3. **三防线闭环**：探活失败 → 上报 → 池层剔除重试 → 重建就绪，任一环节缺失即为 bug，必须有日志保证可见。
4. **禁止 backward**：不搞「兼容旧路径」，直接强化现有有界清理链。

### 3.2 第一步：探针复现方案（诊断优先）

#### 3.2.1 清理链分段探针（定位失守点，原方案）

在 `_exec_locked` 517-520 超时分支内注入分段时间戳探针：

```python

import time as _t
_t0 = _t.perf_counter()
logger.warning(f"[卡死C8/C14] 命令超时{timeout}s → 进入清理链 t0={_t0}")

logger.warning(f"[卡死C8/C14] _kill_tree 完成, 耗时={(_t.perf_counter()-_t0)*1000:.1f}ms")
self._close()
logger.warning(f"[卡死C8/C14] _close 完成, 累计耗时={(_t.perf_counter()-_t0)*1000:.1f}ms")

```

对 `_kill_tree`/`_close` 内部同样分段（taskkill 前后、poll/wait 前后、unlink 前后）。复现用例：制造一个不响应 stdin 的半死 pwsh 实例（如 `Write-Output 'stuck'; $a=...等待` 占住引擎），再并发触发两个 shell 命令，观察探针日志定位精确阻塞行。

### 4.2 M2 新增 `_poll_pid_exit()` 有界轮询确认函数

**位置**：shell_engine.py:236 `_poll_for_file` 之后，模块级新增

```python

# ── 新代码（插入于 _poll_for_file 之后） ──
def _poll_pid_exit(proc: Optional["subprocess.Popen"], timeout: int, interval: float = 0.1) -> bool:
    """[M2] 有界轮询确认进程已退出：替代裸 `proc.wait(timeout)` 的二次确认。
    背景: taskkill/proc.wait 可能在 Windows 内核级原语上静默挂起(无异常无返回, 见章2.5) → 本轮询
    poll() 为纯查询不阻塞, 超 timeout 秒即返回 False, 绝不永久阻塞 — 小欧 2026-09-19"""
    deadline = time.monotonic() + timeout
    while True:
        if proc is None or proc.poll() is not None:
            return True
        if time.monotonic() >= deadline:
            return False
        time.sleep(min(interval, max(0, deadline - time.monotonic())))
```

**设计解析**：
- `proc.poll()` 是**非阻塞查询**，与 wait/find 的原语调用性质不同，不会进入内核待等待 → 天然不卡
- 返回 bool 供调用方判断「确认死亡」/「放弃确认」，配合 M3 二次确认

    #   默认为 self._proc; 常规路径行为不变.

            capture_output=True, timeout=SUBPROCESS_TIMEOUT_SHORT,

**设计解析**：
- **异常/正常双路径职责分离**：taskkill 抛异常（进程已死/句柄失效）→ 立即 `kill()` 兜底并 `return`；taskkill 正常返回 → 才进入二次确认轮询。二者互不干扰，杜绝"异常后仍进二次确认空转"

```python
def _cleanup_guarded(self):
    """[M6] 清理链 daemon 线程守卫(A): 即使 _kill_tree/_close 被 OS 级挂起, 上层也绝不超期等待 — 小欧 2026-09-19
    背景: 同线程内 try/finally 无法拦截内核级挂起的 taskkill/proc.kill/proc.wait(见章2.5) →
          必须把清理整体移到独立线程, 主线程只做有界等待(join timeout), 超时即放行, 锁立即释放。
    时序:
      ① 主线程: 快照 _proc → 立即 _proc=None/_alive=False(不等清理完成)——满足 release 判活(M8),
         假活实例在池内已不可见, 杜绝回流复用
      ② daemon 线程: 对快照复调 _kill_tree(proc 参数, 见 M3)——taskkill 异常兜底 + 二次确认全在其中,
         全程不触碰 self._proc, 与主线程/后续 release 无状态竞态; 进一步 OS 挂起则 daemon 继续自生自灭(不阻塞任何人)
      ③ 主线程: 仅 join(timeout=_CLEANUP_GUARD_TIMEOUT), 超时即逝不当道; 探针记录耗时并留痕(可观测)
    """
    proc_to_kill = self._proc                      # 快照后方可置 None
    pid = getattr(proc_to_kill, 'pid', None)
    self._proc = None
    self._alive = False

    def _worker():
        if proc_to_kill is not None:
            # 复用 M3 _kill_tree(传快照): taskkill 异常兜底 + 二次确认 一条路, 决不触碰 self._proc — 小欧 2026-09-19
            self._kill_tree(proc_to_kill)

    _cleanup_start = time.monotonic()                # [M6] perf 探针 t0
    _t = threading.Thread(target=_worker, name="shell-cleanup-guard", daemon=True)
    _t.start()
    _t.join(timeout=_CLEANUP_GUARD_TIMEOUT)
    _elapsed = time.monotonic() - _cleanup_start
    if _t.is_alive():
        logger.error(f"[卡死C8/C14] 清理链超守卫阈值{_CLEANUP_GUARD_TIMEOUT}s仍在清理(OS级挂起) → 已放行, 后台线程继续 (pid={pid})")
    else:
        logger.warning(f"[卡死C8/C14] 清理链完成, 耗时={_elapsed * 1000:.1f}ms (pid={pid})")
```

**设计解析（本修改点核心，三处修正一次落地）**：
- **线程隔离而非 try/finally**（修正「守卫机制错误」）：同线程的 `finally` 在 `_kill_tree` 被挂起时**永远执行不到**，探针和"强制返回"全是空话；只有把清理移入独立 daemon 线程，主线程才能用 `join(timeout=)` 做到**必在有界时间内让出并释放 `self._lock`**
- **立即置死**（修正「假活回流」）：主线程快照后马上 `_proc=None/_alive=False`——不等清理线程完成 → release 的判活条件（v2.11：`inst._proc is None or poll() is not None`）在清理未竟时就已成立 → 假活实例**绝不放回池**，下次 acquire 不会再次复用卡死
- **清理线程不触碰 self 状态**：`_worker` 对快照 `proc_to_kill` 复用 `self._kill_tree(proc)`（M3 快照参数路径，taskkill 异常兜底 + 二次确认一条路），不经 `self._close()` → 与主线程持有 `self._lock`、后续 release/close 无任何状态竞态
- **观测留痕**：`join` 返回后统一探针打印耗时；`is_alive()` 判定是否 OS 级挂起（`logger.error` 明确标注「静默窗口不再静默」），全程无 >15s 的日志空窗
- **fuse 联动**：守卫线程即使被杀/挂起也不影响进程退出（daemon）；630s 保险丝（M9）保留为纵深最后防线

**位置**：shell_engine.py:358-370

```python

# ── 新代码（358-370） ──
def _probe(self, env: Optional[Dict[str, str]] = None, timeout: Optional[int] = None) -> bool:
    """...docstring 不变..."""
    if self._proc is None or self._proc.poll() is not None:
        return False
    try:                                            # [M7] 保序: 底层 _exec 任何异常都被捕获, 367 上报必达 — 小欧 2026-09-19
        result = self._exec(_PROBE_CMD, timeout=timeout or _PROBE_TIMEOUT)
    except Exception as e:
        logger.warning(f"[卡死C8] 探活异常(非timeout)→已销毁重建 (pid={getattr(self._proc, 'pid', None)}, err={e})")
        self._close()
        return False
    if result.get("timed_out"):
        logger.warning(f"[卡死C8] 探活失败(半死)→已销毁 (pid={getattr(self._proc, 'pid', None)})")
        self._close()
        return False
    return "__OMNI_PROBE__" in result.get("stdout", "")
```

**设计解析（方向C）**：
- 原代码若 `_exec` 抛异常（而非返回 `timed_out`），会**跳过 367 上报**直接向上冒 → ①缺、二层防线失序 → acquire 异常路径 release 槽位后直接把异常抛给 execute_shell_command → 屏蔽了 C13 重试
- 新代码：`_exec` 任何异常都等价于「探活失败」→ `_close` → `return False` → acquire 收到 `False` 走 Phase3 C13（池层剔除重试），三层防线闭环恢复

### 4.8 M8 `acquire()` Phase3 保证（配合 M7 的 C13 可达）

**位置**：shell_engine.py:695（Phase2 调用点）与 703（Phase3 C13）

```python
# ── 原代码（694-696） ──

# ── 新代码（694-696，仅调整注释，逻辑不变） ──
# ── Phase2(解锁): 新建→_start; 复用→_probe(失败必 return False, 经 _close 销毁, M7 保序) ──

    return inst
```

**设计解析**：M8 不是新逻辑，而是**契约硬化，双路径保障**：
- **探活路径（M7）**：`_probe` 返回的每个 `False` 都伴随实例已销毁/已交由守卫（`_alive=False`/`_proc=None`）
- **超时清理路径（M6）**：`_cleanup_guarded` 主线程**先快照再立即置死**（不等清理线程完成）——即使 daemon 清理被 OS 级挂起拖延，release 判活条件（v2.11：`inst._proc is None or poll() is not None`）在 `acquire` 返回后**立即成立** → 死/半死实例从池中剔除（C13）+ `inst.close()`，**绝不放回池**，杜绝下一次复用再次卡死
- 两路径共同保证：Phase3 C13（703）、release 判活（748）、下一次 acquire 之间**不存在任何半死对象入池窗口**

> 对应 3.1 原则3「三防线闭环」：探活失败（M7）→ 池层剔除重试（C13 703）→ 重建就绪（_start，427 日志），任一环节现在都有日志保证可见。
