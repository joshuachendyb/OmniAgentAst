### 1.2 事件分类规则（北京老陈定案）

| 分类 | 事件类型 | 规则说明 |
|------|---------|---------|
| **1. 仅前端（不落库）** | chunk, thought-start, error, usage, paused, resumed, retrying, cancelled, user_rejected, truncated, stats, context_overview | 实时展示用，不存DB，任务结束后丢弃 |
| **2. 前端+落库** | start, action(canonical), observation, final, final_stats | 实时展示+历史回放，必须存DB |
| **3. 仅落库（不给前端）** | thought | 历史回放用，不实时发，设计意图§10.3.3(1) |

### 1.3 分类验证（v6.0：emit() 统一出口分流）— 小欧-2026-09-11

> v6.0 改造：落库分流从 agent_runner 扫描段路由（已退役）前移进 **emit() 统一出口**（emit.py，5.2），
> agent_runner 通道路由删除、仅保留 SSE 时序同步。分类验证点改为 **emit.py 内部 _DB_TYPES/_PERSIST_ONLY_TYPES 分流**。

```python
# 本地代码实况（v6.0 emit.py，emit() 内 — 小欧-2026-09-11）
_DB_TYPES = {"start", "action", "observation", "final", "final_stats"}       # 分类2: 发送先行落库后处理
_PERSIST_ONLY_TYPES = {"thought"}                                            # 分类3: 仅落库(OCP可扩展)
category = event_dict.get("type")                                            # 分类判定
if category in _PERSIST_ONLY_TYPES:      # → 分类3: 仅落库(只落库存簿; publish跳过)
    await persist_step_to_db(event_dict, agent)
elif category in _DB_TYPES:              # → 分类2: 发送先行落库后处理(北京老陈裁定"前端越快越好")
    seq = await buffer.publish(event_dict)          # ① 发送先行（实时性第一）
    await persist_step_to_db(event_dict, agent)     # ② 落库后处理（db.atxn 子线程异步，非阻塞）
elif event_dict.get("_live_only"):       # → 分类1(预览): 仅publish(_live_only 预览, 落库由 canonical 承接)
    seq = await buffer.publish(event_dict)
else:                                    # → 分类1(其余): 仅publish(chunk/error/usage/thought-start/truncated/stats/context_overview/paused/resumed/retrying/cancelled/user_rejected)
    seq = await buffer.publish(event_dict)
```

> ⚠️ v6.0 遗留差异（北京老陈知悉，跟随 emit 分类表对齐）：
> 1.2 定案中 `truncated/stats/context_overview` 属分类1（仅前端），本地旧路由显式集合无此项、
> 实际走 `else` 落库——v6.0 统一收口 emit 后自然走分类1 仅publish（emit 分流不存在
> "不匹配集合即落库"的 else 陷阱），差异随重构消除，无需另立专项。

| 维度 | event_log（内存） | chat_task_steps（DB） |

## 三、当前架构问题

### 3.1 架构图

```
┌─────────────────────────────────────────────────────────────┐
│                     事件发射层                               │
└──────────────────────────┬──────────────────────────────────┘
                           │ publish()
                           ▼
┌─────────────────────────────────────────────────────────────┐
│              StreamBuffer.event_log（共享队列）               │
└──────────────────────────┬──────────────────────────────────┘
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
┌─────────────────────┐    ┌─────────────────────────┐
│   stream_reader     │    │   agent_runner._scan    │
│   (SSE消费者)        │    │   (DB落库消费者)         │
└──────────┬──────────┘    └────────────┬────────────┘
           ▼                            ▼
    SSE → 前端                    DB落库(chat_task_steps)
```

### 3.2 问题（北京老陈发现，全量列出）

#### 问题一：前端显示thought重复

**现象**：前端聊天界面中，LLM 推理内容（thinking）与正文内容重复显示。

**链路**：
```
LLM流 → chunk(is_reasoning=true) → SSE → 前端显示推理正文
                                    ↓
handle_action publish(ThoughtStep) → event_log → stream_reader → SSE → 前端又显示一次
```

**根因**：`handle_action.py:345-359` 将 ThoughtStep publish 到 event_log，
stream_reader 不加区分转发为 SSE，前端收到 chunk 与 thought 双份推理内容，
`PipelineRenderer.tsx` 靠 `endsWith` 去重（过渡补丁）。

#### 问题二：文档[6]设计要点未实施——thought被裹挟进event_log

**文档[6]原文**（§1.4路由表）：thought 仅落库，不发SSE。

**设计漏洞**：文档[6]只定义了"去向"（仅落库），没设计"怎么去"。
实施时 thought 仍走 `publish()` 进入 event_log，再由 agent_runner 路由过滤不发SSE。

**对比**：

| 设计 | thought路径 | event_log中是否有thought |
|------|------------|------------------------|
| [6]文档实施现状 | publish → event_log → 路由过滤 → 仅落库 | ✅ 有（被裹挟） |
| [1]文档§10.3.3(1)设计意图 | 完整数据落库，实时不发送 | ❌ 应无 |
| 本文档[26]重构目标 | persist_step_to_db → 直接写DB | ❌ 无 |

**结论**：[6]把 thought 从"发SSE"改成"仅落库"，但 thought 仍进入 event_log，
违反[1]§10.3.3(1)"thought完整数据落库、实时不发送"的设计意图。

#### 问题三：测试不彻底——只验SSE未验event_log

**测试现状**：文档[6]实施后的测试只验证了"前端不收到thought"（SSE输出），
未验证"event_log中没有thought"（内存状态）。

| 测试项 | 验证内容 | 结果 |
|--------|---------|------|
| SSE输出 | thought不在SSE中 | ✅ 通过（正确） |
| event_log内容 | thought不应在event_log中 | ❌ 未测试（漏洞） |

**后果**：问题二（thought被裹挟进event_log）长期未被发现，
前端去重补丁（`endsWith`）掩盖了架构缺陷。

#### 问题四：架构层面问题

1. **共享队列导致职责混乱**：event_log 同时服务SSE和DB落库，需要标记区分
2. **过渡方案不优雅**：`_no_sse` 标记是补丁，不是设计
3. **违反SRP**：stream_reader 需要理解业务逻辑（哪些事件该发）
4. **扩展性差**：新增事件类型需要修改 stream_reader 过滤逻辑

### 3.3 根因汇总

```
根因1（问题一+问题二）：
handle_action.py → publish(ThoughtStep) → StreamBuffer.event_log
                                              ↓
                        stream_reader → SSE ❌ 不该发
                        agent_runner → DB落库 ✅

根因2（问题三）：
测试只断言SSE输出，未断言event_log内容 → 裹挟问题漏网

根因3（问题四）：
SSE与DB落库共享event_log → 职责混乱 → 需标记/过滤区分
```

**设计意图**（[1]§10.3.3(1)）：thought 仅落库不发SSE，不进入实时通道
**实际行为**：thought 被 publish 到 event_log → 依赖路由过滤/SSE过滤/前端去重三层补丁

## 四、重构设计

### 4.1 设计原则

**纲领五原则**（v6.0 扩充为六大规范检索项，下分三组细化原则）：

| 纲领 | 说明 |
|------|------|
| **职责分离** | SSE和DB落库完全独立，不共享数据源 |
| **KISS-DIRECT** | 简单直接，不绕弯 |
| **SRP** | 每个函数/文件只做一件事，名字与职责一一对应 |
| **OCP** | 新增事件类型不修改消费者代码 |
| **DRY** | 事件发射逻辑不重复 |
| **名实相符** | 文件名/函数名必须名副其实：persist 只落库、emit 只发射分流、publish 只推前端 |

**第一组：统一落库DB原则（U）** — v6.0 新增（北京老陈裁定 2026-09-11）

| 原则 | 说明 |
|------|------|
| **U1 唯一落库函数** | 所有落库事件**必须且只能**经 `persist_step_to_db()`（persist.py），禁止任何其他函数/模块直调 `db.atxn` 写 chat_task_steps；`persist.py` 是**唯一**落库域 |
| **U2 名实相符** | 三职责三命名：`persist.py` 只落库、`emit.py` 只发射分流、`buffer.publish` 只推前端——谁也不往谁的文件里塞职责（emit 不放进 persist.py，杜绝"管落库的文件却发布事件"的语义错位） |
| **U3 落库事务一致** | event_dict/usage/step_index 由 persist_step_to_db 唯一构造与落库，杜绝多处跑马写库导致的字段/序号分裂 |

**第二组：调用原则（C）** — v6.0 新增

| 原则 | 说明 |
|------|------|
| **C1 发射点只调 emit** | react_loop/react_step/handle_action 事件发射一律 `await emit(buffer, agent, event_dict)`（import 自 emit.py）；禁止发射点直调 persist_step_to_db 或 buffer.publish（特殊点名目逐类登记于 4.4，如预览 `_live_only` 直连 `_buf.publish`、chunk 直连） |
| **C2 单向依赖无环** | 依赖链发射层 → emit.py → persist.py → db：`emit.py` import `persist_step_to_db`（自 persist.py），persist.py **不反向依赖** emit.py，无循环 |
| **C3 发射层不感知落库** | handler/驱动层只交付事件 dict，不感知落库分类与时机（SRP）；分类判定全部收敛在 emit 内部 |
| **C4 簿记单一归属** | 执行步骤簿记 `agent._exec_steps` 只由 persist_step_to_db（emit 内部调用）append；统计方（agent_runner finally）只读不写 |

**第三组：落库DB与publish分流原则（S）** — v6.0 新增（12:07 增补：时序/异步/final三分类，北京老陈三问定案）

| 原则 | 说明 |
|------|------|
| **S1 三分类分流** | 分类1仅publish / 分类2发送先行落库后处理 / 分类3仅落库（`_PERSIST_ONLY_TYPES`），判定用集合收敛于 emit() |
| **S2 发送先行** | 分类2必须 publish **先于** persist（北京老陈裁定：**前端越早收到越好**，实时性第一）；落库后处理（persist_step_to_db），与现网"publish 直写缓冲实时推 SSE、落库扫描后置"时序一致，杜绝"落库 IO 拖慢 SSE" |
| **S3 落库异步非阻塞** | `persist_step_to_db` 内部必须经 `db.atxn`（=`asyncio.to_thread` 子线程，database.py:257/269）执行，整段 `with get_conn` 在子线程跑（含锁重试 `time.sleep`），**事件循环永不被占**、不堵塞主 ReAct loop（2026-08-24 后端卡死修复）；落库失败静默告警不阻断 SSE |
| **S4 可扩展分流（OCP）** | 分类判定用集合：`_DB_TYPES`（分类2）/ `_PERSIST_ONLY_TYPES`（分类3）。**新增事件类型只扩集合，emit() 内部分流逻辑零改动**；新类型先在 4.4 分类表登记 |
| **S5 分类3准入门槛** | 仅落库事件（当前仅 thought）须同时满足：①历史回放必需 ②前端实时展示无价值（避免误发条数膨胀）③不发 SSE；满足后加入 `_PERSIST_ONLY_TYPES` 并登记 4.4 |
| **S6 final 三分类数据分离** | **发送数据 ≠ 落库数据，两套分别处理**（final）：completed 满足短信号前置条件（非 action 轮+已发正文 chunk）时 SSE 仅发剥离短信号 `{type,step,timestamp,outcome}`、落库始终完整 dict（response/accumulated_usage/三层 tokens）；cancelled/failed SSE 发完整+落库完整（含 cancel_source / error_type、error_message）；**发送侧剥离由 agent_runner finally 覆写原位保 seq（5.8.6）承载，落库始终经 persist_step_to_db 落完整 dict**，emit 内两路数据各自处理不乱 |

**v6.0 与 v4.x 的关键差异**：
1. 不再有"thought 单点直调 persist"与"其余扫描落库"的双轨——所有事件（含 thought）统一经 `emit()` 出口，`persist_step_to_db` 成为**唯一落库函数**（北京老陈裁定）。
2. **时序为发送先行、落库后处理**：emit() 内分类1/2 **先 `buffer.publish`（前端越早收到越好，实时性第一）**，分类2随后经 `persist_step_to_db` 落库（`db.atxn` 子线程异步 offload，不阻塞主 loop）——与现网"publish 直写缓冲实时推 SSE、落库扫描后置"时序完全一致（原则 S2/S3）。
3. agent_runner 扫描段退役落库职责（不再 `_persist`），仅保留 **SSE 时序同步**（final 短信号/覆写/current_content，见 5.3 改动3）。
4. **persist 与 emit 拆分为两个文件（名实相符）**：persist.py 只落库（5.1）、emit.py 只发射分流（5.2，含 `_DB_TYPES`/`_PERSIST_ONLY_TYPES` 集合，单向依赖 emit.py→persist.py 无环）——发射点 import 自 emit.py，不再从 persist.py 导入 emit。
5. **final 三分类发送/落库数据分离**（原则 S6）：completed/cancelled/failed SSE 侧与落库侧是两套数据，发送剥离短信号由 agent_runner finally 覆写承载，落库始终完整 —— 与现网 5.8.6 覆写机制一致。

### 4.3 事件分流逻辑（统一出口 emit，发送先行落库后处理）

**核心先后顺序（北京老陈裁定 12:07 修正）**：`emit()` 内部 **先 publish、后 persist** ——
**前端越早收到越好（实时性第一）**：publish 直写缓冲由 stream_reader 按 seq 实时转发 SSE，
落库后处理（persist_step_to_db 经 db.atxn 子线程异步 offload，不阻塞事件循环，原则 S2/S3）。
与现网"publish 先行、扫描落库后置"时序完全一致，v6.0 不改变 SSE 实时性。

```
事件发射点（react_loop / react_step / handle_action / handle_answer）
        │  await emit(buffer, agent, event_dict)
        ▼
┌──────────────────────── emit() 统一出口 ────────────────────────┐
│ 分类3 thought          → persist_step_to_db()        （只落库，   │
│                          不进 event_log，不发前端）                │
│ 分类2 发送先行         → buffer.publish()      （① 先推前端，      │
│      落库后处理         → persist_step_to_db()    前端越快越好）   │
│                       （② 后落库，db.atxn 子线程异步非阻塞）      │
│ 分类1 仅发布           → buffer.publish()             （不落库，   │
│                          纯实时事件）                             │
└──────────────────────────────────────────────────────────────────┘
```

```python
# 伪代码：emit() 内部按分类先后分流（emit.py，import persist_step_to_db 自 persist.py）
# ⚠️ 顺序 = 先后关键：分类2 必须【先 publish 后 persist】（北京老陈裁定"前端越快越好"）；
#    persist 内部经 db.atxn = asyncio.to_thread 子线程，不阻塞事件循环（原则 S3）
# ⚠️ final 三分类发送/落库两套数据（原则 S6）：发送剥离短信号由 agent_runner finally 覆写承载，
#    落库始终完整 —— emit 内 publish 完整 dict、persist 完整 dict，两路互不混淆
# ⚠️ 两文件各司其职（名实相符）：persist.py 只落库、emit.py 只发射分流（见 5.1/5.2）

# —— emit.py 模块级集合 ——
_DB_TYPES = {"start", "action", "observation", "final", "final_stats"}  # 分类2: 前端+落库(发送先行)
_PERSIST_ONLY_TYPES = {"thought"}   # 分类3: 仅落库 — 未来新增仅落库事件只需扩此集合(S4)

async def emit(buffer, agent, event_dict):
    event_type = event_dict.get("type", "")

    # 分类3: 仅落库 → 只落库存簿，不进 event_log（当前 thought；未来新类型扩 _PERSIST_ONLY_TYPES）
    if event_type in _PERSIST_ONLY_TYPES:
        await persist_step_to_db(event_dict, agent)
        return

    # action 预览(_live_only, 齿轮先行): 仅SSE不落库, 落库由 canonical 承接 — 小欧-2026-09-11
    if event_type == "action" and event_dict.get("_live_only"):
        await buffer.publish(event_dict)
        return

    # 分类2: 前端+落库 → 【发送先行，落库后处理】
    if event_type in _DB_TYPES:
        await buffer.publish(event_dict)             # ① 发送先行（实时性第一，前端越快越好）
        await persist_step_to_db(event_dict, agent)  # ② 落库后处理（db.atxn 子线程异步，非阻塞）
        return

    # 分类1: 仅前端（chunk/error/usage/...）→ 只发布
    await buffer.publish(event_dict)                 # ③ 不落库，纯实时
```

> 说明：`action` 的 `_live_only` 预览事件（tools=all_calls 齿轮先行）保持仅 SSE 不落库，
> 由 `emit()` 内识别 `_live_only` 标记走仅publish（见 5.2 emit 实现；行为与现行路由一致）。
> 未来新增"仅落库"事件类型：满足 4.1 原则 S5 后扩 `_PERSIST_ONLY_TYPES` 并登记 4.4，emit() 零改动（OCP）。
> **final 三分类**（原则 S6）：completed 有短信号前置条件时 SSE 发剥离短信号（agent_runner finally
> 覆写原位承载）、落库完整；cancelled/failed SSE 完整、落库完整（cancel_source/error_type 都带）。

## 五、详细设计

### 5.0 操作规范：复制然后修改

**铁律**: `persist.py` 的创建必须采用「**复制然后修改**」方式，禁止重写（5.0 铁律，逐字复制保证行为不变）。

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 复制 | 将 `agent_runner.py:331-359` 的 `_persist` 函数体**逐字复制**到 `persist.py` |
| 2 | 改签名 | 嵌套函数 → 模块级函数，闭包变量 → 参数/agent属性 |
| 3 | 改调用 | `_persist(event_dict)` → `persist_step_to_db(event_dict, agent)` |

**禁止**：重写逻辑、改变执行顺序、增删功能（仅允许按北京老陈裁定做的"统一落库"结构性收敛）。

### 5.1 新增文件: persist.py（从 _persist 复制然后修改 — 唯一落库函数）

**文件路径**: `backend/app/services/agent/persist.py`

**职责（名实相符，见 4.1 原则 U2）**: 只做**落库**；emit 分流放 emit.py（5.2），发射点调 `emit` 时经 `from app.services.agent.emit import emit`，`emit.py` import 本模块的 `persist_step_to_db`（单向依赖，C2 无环）。

**操作方式**: 从 `agent_runner.py:331-359` 的 `_persist` **逐字复制**，入口函数改为 `persist_step_to_db(event_dict, agent)`；**不加任何新职责**。

```python
# -*- coding: utf-8 -*-
# 编辑历史:
# 2026-09-11 小欧 新增: 事件落库与实时发送分流重构 — 从 agent_runner._persist 复制然后修改
#   源: agent_runner.py:331-359 _persist 嵌套函数
#   改: ①嵌套函数→模块级函数 ②闭包变量→参数传入 ③簿记 current_execution_steps→agent._exec_steps
#       — 小欧-2026-09-11

"""persist — 唯一落库函数模块（北京老陈裁定：所有落库事件必经唯一函数）

职责:
  - persist_step_to_db(): 将事件写入 DB chat_task_steps，唯一落库函数。
    分流（哪个事件落库/何时落库）不在本模块，在 emit.py（5.2）。
  - 本模块不 import emit.py（单向依赖 C2：emit.py → persist.py）。
  - 时序（原则 S3，北京老陈裁定）：emit() 内先 buffer.publish（发送先行）再调本函数
    （落库后处理）——落库经 db.atxn 内部 asyncio.to_thread 子线程执行即可，本函数

### 5.2 新增文件: emit.py（事件统一发射出口 — 分流判定，名实相符）

**文件路径**: `backend/app/services/agent/emit.py`

**职责（见 4.1 原则 U2/C2）**: 只做**发射/分流**；**单文件单职责**——落库在 persist.py（5.1），发布在 buffer.publish。发射点 `import` 自本模块，本模块 `import persist_step_to_db` 自 persist.py（单向依赖无环），**persist.py 不反向依赖本模块**。

**文件要点**：
- `_DB_TYPES`（分类2）/ `_PERSIST_ONLY_TYPES`（分类3）两个集合收敛所有分流判定（S1/S4）
- **仅落库泛化（S5/OCP）**：`thought` 不再硬编码判断，统一经 `_PERSIST_ONLY_TYPES` 集合——未来新增"仅落库"事件类型，只需满足 4.1 原则 S5 后扩集合，emit() 逻辑零改动，不必触碰分流代码

# 2026-09-11 小欧 新增: 事件统一发射出口 — 从 5.1 拆分独立, 名实相符(SRP/U2);

"""

from app.services.agent.persist import persist_step_to_db  # 唯一落库函数(单向依赖 C2) — 小欧-2026-09-11


# 分类2 落库类型集: 前端+落库, 发送先行(publish先, persist后) — 小欧-2026-09-11
_DB_TYPES = {"start", "action", "observation", "final", "final_stats"}

# 分类3 仅落库类型集: 只落库存簿, 不进 event_log, 不发前端 — 小欧-2026-09-11
#   v6.0 扩展设计(S5/OCP): 未来新增"仅落库"事件类型, 满足 4.1 原则 S5 后直接扩本集合,
#   emit() 分流逻辑零改动; 新类型先在 4.4 分流表登记
_PERSIST_ONLY_TYPES = {"thought"}


async def emit(buffer, agent, event_dict):
    """事件统一出口 — 小欧-2026-09-11

    先后顺序(北京老陈裁定 12:07 修正): 分类3仅落库 → 分类2发送先行(publish先persist后)
    → 分类1仅publish. 发射点(react_loop/react_step/handle_action/handle_answer)全部改走本函数.
    final 三分类(原则S6): 发送/落库两套数据 — 发送剥离短信号由 agent_runner finally 覆写承载,
    落库始终完整 dict; 本函数 publish 完整 dict、persist 完整 dict, 互不混淆.
    """
    if not isinstance(event_dict, dict):
        return  # 守卫: 非dict静默跳过(与 _persist 行为一致)
    event_type = event_dict.get("type", "")

    # 分类3: 仅落库, 不进 event_log, 不发前端 (当前 thought; 可扩展见 _PERSIST_ONLY_TYPES)
    if event_type in _PERSIST_ONLY_TYPES:
        await persist_step_to_db(event_dict, agent)
        return

    # action 预览(_live_only): 齿轮先行仅SSE, 不落库(与现行路由一致)
    if event_type == "action" and event_dict.get("_live_only"):
        await buffer.publish(event_dict)
        return

    # 分类2: 发送先行, 落库后处理（北京老陈裁定: 前端越快越好）
    if event_type in _DB_TYPES:
        await buffer.publish(event_dict)              # ① 发送先行(实时性第一, stream_reader按seq直转SSE)
        await persist_step_to_db(event_dict, agent)   # ② 落库后处理(db.atxn 子线程异步, 非阻塞)
        return

    # 分类1: 仅前端(不落库)
    await buffer.publish(event_dict)
```

## 十、总结

**v6.0 定案**（北京老陈裁定 2026-09-11，小欧重写 4.2-5.12/6-10；12:07 三问时序修正）：
v4.4-v5.9 的"维持 agent_runner 扫描落库 + handler 侧 thought 直落"双轨思路作废，收敛为
**统一出口 emit()（emit.py） + 唯一落库函数 persist_step_to_db（persist.py）**。核心收益：

1. **唯一落库函数（DRY 根治）**：全部落库（thought/start/action/observation/final/final_stats）
   仅经 `persist_step_to_db`，agent_runner 扫描段落库职责退役，终态兜底（异常/守卫/死循环）
   与常规路径同一函数，消灭双轨长尾（4.5 问题四）。
2. **发送先行、落库后处理（前端越快越好）**：emit() 内分类2先 publish 后 persist（北京老陈裁定
   12:07 修正，回归现网语义），实时性第一；落库经 `db.atxn`（=asyncio.to_thread 子线程）异步
   非阻塞，事件循环永不被占，落库失败静默降级不阻断 SSE（4.5 问题五/原则 S2/S3）。
3. **final 三分类发送/落库数据分离（S6）**：completed 短信号剥离（SSE 仅 `{type,step,timestamp,outcome}`）
   由 agent_runner finally 覆写原位承载、落库完整 dict；cancelled/failed SSE 完整+落库完整；
   final_stats 两路都走——发送与落库本质两套数据，各取所需（5.3/5.12）。
4. **三分类分流（KISS-DIRECT）**：分类3仅落库(thought)/分类2先publish后persist/分类1仅publish，
   源头分流，无标记/无过滤，stream_reader 零改动（4.3/4.4）。
5. **名实相符（SRP 文件级）**：persist.py 只落库、emit.py 只发射分流（_DB_TYPES/
   _PERSIST_ONLY_TYPES 集合收敛判定），单文件单职责、单向依赖（emit.py→persist.py）无环
   （4.1 原则 U2/C2）。
6. **簿记列表升格 agent._exec_steps**：`current_execution_steps` 由 run_react_cycle 局部
   变量迁为 agent 属性（5.4），发射点 append 与 total_steps 统计同源（4.5 问题六）。
7. **纯函数化保持（SRP）**：handle_answer 零改动（5.8），handler 落库副作用收敛到
   handle_action thought 一处（5.7），发射点统一由 react_loop/react_step 驱动（5.6）。
8. **可维护性（OCP）**：新增"仅落库"事件只需满足 4.1 原则 S5 后扩 emit.py `_PERSIST_ONLY_TYPES`
   集合（分类2 扩 `_DB_TYPES`），emit() 分流逻辑零改动，消费者（agent_runner/stream_reader）零感知。
