### 4.3 缺陷结论：task info 看不到重试

**现象与证据**：L1（ReadTimeout）与 L2 重试期间，**只有日志，没有任何 SSE meta/error 事件发往前端**，故 task info 无任何重试显示。

| 层级 | 是否发 retrying 给前端 | 现状 |
|------|--------------------|------|
| **L1**（base_service.py:414） | ❌ **否** | 仅 `logger.warning` + `sleep` + `continue`，不 yield 任何 meta |
| **L2**（llm_stream.py:286） | ❌ **否** | 仅日志 + sleep + continue，不 yield 任何 meta |
| 空响应重试（answer_handler.py:148-154） | ✅ 是 | `MetaStep(type="retrying", wait_time=...)`，前端可显示 |

**前端能力已具备**（只等后端发送）：
- `sseParser.ts:770` `case 'retrying'` → `onRetry(content, wait_time)`
- `TaskInfoBar.tsx:368` `🔁` 重试标记（▲实码 2026-09-02：删尾部"收起/展开"按钮后行号前移，现于过程事件条 `kind==='retrying'`）
- `chat.ts:201` `wait_time?: number`（注释明确「仅 retrying 时可选」）

**结论**：前端早就支持显示重试（含 wait_time），`answer_handler` 也示范了正确 emit；唯独 **L1 ReadTimeout 重试路径只打日志、从不发 retrying**。L1 实际重试间隔 3+9+27=39 秒，这 39 秒用户完全无感知，是体验缺陷。

### 4.4 关键补证：429 的 error 会被 L2 拦截再重试，全过程 front-end 不可见

**完整链路（依代码逻辑）**：
1. L1 三轮 ReadTimeout 全失败后（base_service.py:414），`base_service.py:420-424` **确实 yield 了一个含 `stream_error="API配额/速率限制已耗尽"` 的 StreamChunk**（quota_exceeded 类型）。
2. 该 StreamChunk 回到消费层 `llm_stream.py:154-155` 检出 `stream_error` → break → `llm_stream.py:201` yield `_yield_error_response(...)` → 产出 `("response", {"type":"error", ...})`。
3. **但这正是日志里的 `llm_stream.py:115 error`**。而 `call_llm_with_fallback`（llm_stream.py:278-281）**检测到 `type=="error"` 响应就 `raise LLMResponseError` → 触发 L2 重试**（日志 `llm_stream.py:286 [Retry][L2] 第1/2次`）。
4. 所以这条 429 error **被 L2 吞下重试，并未立即发前端**。L2 重试仍失败，最终 `call_llm_with_fallback` 末尾才 yield `type="error"` 给前端（前端看到最终「失败」，但全程无「重试中」过程提示）。

**一句话**：**「error」最终会 yield 给前端，但「重试过程」（L1/L2 每次重试）全程无任何 meta 发前端**；且中间那次 429 error 还被 L2 拦截重试，用户也看不到。

### 4.5 既有架构事实（回应老陈「我记得有 yield meta error 给前端」的疑问）

老陈的记忆**没有错**——「错误/重试要 yield meta error 给前端」的要求**确实存在且已实现**，证据充足：

- `agent_runner.py:39` 注释明确：`error/usage/paused/resumed/retrying/cancelled 划入仅SSE集合分支(不落库)`，即这些 meta **设计上就是要发前端的**。
- emit 点遍布 agent 层：`react_cycle.py` 多处 `MetaStep(type="error"/"retrying"/"truncated"/"usage"/"stats"/"cancelled")`、`action_handler.py:306/320/362/369/383/914`、`answer_handler.py:148`、`react_cycle.py:812/844` 等。

**但精确边界是**：这些 emit 全发生在 **agent 编排层（ReAct 循环 / handler 分派）**，针对的是「工具执行、响应解析、编排流程」层面的错误。它们**通过 StepEmitter → SSE**，前端可见。

**LLM 底层传输重试（L1/L2）不在这个路径上**：
- L1 在 `app/llm/base_service.py`（比 agent 层更底层），yield 的是原始 `StreamChunk`（error 走 `stream_error` 字段），**不经 StepEmitter，不产生 MetaStep**。
- L2 在 `call_llm_with_fallback`（llm_stream.py:286），也**只 sleep+continue，无任何 yield**。

**结论**：不是「要求被删除」，而是「该要求只实现到了 agent 层错误，LLM 底层传输重试（L1/L2）从架构上就从未接入 MetaStep 发射路径」，是既有盲区。这正是本报告要补的缺口。

### 5.0 设计目标与边界（对齐 §4.5 架构事实）

| 项目 | 结论 |

### 7.1 问题现象（重试放大）

同一 LLM 调用出现**乘法放大重试**，长期假死：

```
L1 1/3 → 2/3 → 3/3（4 次 HTTP，单次 ReadTimeout hang ~2.5min）
  → 429 / L2 第1/2次（L2 捕获 429 error 又重试）
  → 又从头跑 L1 1/3 → ...（L2 每重试一次，内部再跑一遍完整 L1）
  → L2 第2/2 失败 → Text 降级又跑一遍完整 L1
```

**单次 LLM 调用最大 HTTP 次数（乘法）**：`L2(2次) × L1(4次) + 降级(4次) = 12 次`，最长约 **30 分钟**。故障持续时主循环 `max_steps=10000` 会反复触发这套组合，导致**几十分钟到数小时的长时挂起**。

### 7.2 根因（三层，逐层定位）

| # | 根因 | 位置 |
|---|------|------|
| R1 | 429（quota_exceeded）被分类为 **SERVER 可重试**，L1 会对它打满 4 次重试 | `error_classifier.py:98` `429: SERVER`；`error_classifier.py:58-63` `is_retryable` 含 SERVER |
| R2 | L2 收到任何 `type=error` 一律 `raise LLMResponseError` 重试，**不区分错误种类**，把 L1 已处理的传输/限流错误再拉一轮 | `llm_stream.py:280-281`（▲实码 :277-291） |
| R3 | L1 失败转成的 error 响应**丢失错误类型**（`_yield_error_response` 只返回 `{type, content}`），L2 无从区分 | `llm_stream.py:117`（▲实码 :110-120，`error_type` 已落地 :120） |

### 7.3 设计原则（老陈否决③后的收紧）

- **不做全局熔断/超时上限**（否决项）。
- 改动**最小、最直接**：只补「错误类型透传」一个字段 + 「L2 精准分流」一处判断，不引入新框架/不新增重试层。
- 职责边界：**L1 管传输/连接/限流**；**L2 管"`type=error` 中非 L1 已处理的传输/限流类错误"**（真正需 L2 兜底的 LLM 调用异常/其它 error），二者互不越界、互不叠加。**注意**：空响应**不在 L2**——真·空在 `answer_handler.py:143-155` 走 `MetaStep(retrying)` 编排层重试（前端可见），与 L2 无关。

### 7.4 ① 快速失败 429（quota_exceeded）

**目标**：429 服务器已明确「稍后重试」，重试无意义 → 不进 L1/L2 重试，直接失败。

**改法（新增专属枚举，一处归类，DRY 就近）**：

- **改 A**（`error_classifier.py`）：**新增 `SystemErrorCategory.RATE_LIMIT` 枚举**（`429: SystemErrorCategory.RATE_LIMIT`），并确保其 `is_retryable=False`（RATE_LIMIT **不**加入 `is_retryable` 的 `retryable_categories` 集合，默认即不可重试）。L1 的 `_should_retry`（base_service.py:533 委托 `is_retryable`）即自然不再重试 429。
  - **为何不用复用 CLIENT**：CLIENT 的 `to_status="client_error"`、`description="客户端错误"` 会对 429 限流产生误导文案，且 M1 修复（:27）后 CLIENT 分支会透出「客户端错误:请求参数异常」式的误导信息，污染限流语义。故新增专属 `RATE_LIMIT`。
  - **新增枚举需同步的 4 处映射（防漏改，DRY）**：① `is_retryable` 的 `retryable_categories`（不加 RATE_LIMIT，保持默认不可重试）；② `to_status` 映射（加 `RATE_LIMIT: "rate_limit"`）；③ `description` 映射（加 `RATE_LIMIT: "接口限流/配额"`）；④ `SYSTEM_ERROR_TYPE_TO_MESSAGE`（:106 起）加 `RATE_LIMIT: ("rate_limit", "接口限流/配额已耗尽,请稍后重试")`。四处同为机械扩展，缺一会导致 `KeyError`/missing 展示缺失。

**效果与既有专支闭环（会审确认）**：改 A 后 L1 `base_service.py:394` 的 `_should_retry` 对 429 返回 False → 走 `:417` else 分支 → **已存在**的 `:419` `if ... response.status_code == 429` 专支立即 yield `quota_exceeded` StreamChunk 并 `return` → 上层 `set_failed` 快速失败。**`base_service.py:419-425` 配额专支在改 A 后自动承接 429，无需新增任何代码（改 B 冗余，KISS 剔除）；429 不再打满 L1 4 次、不再进 L2。**

> 关联核查（不退化）：
> - `tool_retry_engine.py:523` 的 `_should_retry`（L3 工具重试）注释明确「只查 per-tool 配置，**不查 is_retryable**」→ 改 A 不影响 L3，隔离良好。
> - `client_sdk.py:41 _RETRYABLE_STATUS=(429,500,502,503,504)` 仅用于打日志级别（:178,:225），不驱动重试 → 改 A 不改其日志行为，无副作用。
> - `get_error_info`（error_classifier:236 → sse_events.py:66）会透传 `retryable` 给前端 → 429 变为 `retryable=False` 属更准确展示，增强不退化。

### 7.5 ② L2 只重试"非 L1 传输/限流类的 error"，不再承接 L1 已处理的错误

**目标**：L2 分得清错误种类，只对它该管的（`type=error` 中真正需 L2 兜底的 LLM 调用异常/其它 error）重试；对 L1 已处理到底的传输/限流类 error 放行，不再拉一轮。

**改法（两处最小，配套 R2+R3）**：

- **改 C**（`llm_stream.py:107-117` `_yield_error_response`；▲实码 :110-120，**已落地** `error_type` :120）：响应体补带错误类型字段，**键统一定死为 `error_type`**（与 `_dispatch_handler`/react_cycle 既有 `error_type` 语义一致）。现状函数签名已收 `exc_type` 入参（由 `llm_stream.py:201`（▲实码 :204）传 `chunk.stream_error_type`），只需在返回 dict 里补上：`return ("response", {"type":"error", "content":..., "error_type": exc_type})`。这样 429 会带 `quota_exceeded`、ReadTimeout 会带 `idle_timeout`/`server` 等着。

- **改 D**（`llm_stream.py:274-283` `call_llm_with_fallback` 的 raise 处；▲实码 :277-291，**已落地**）：按 `error_type` 分流——
  - 传输/限流类（`quota_exceeded` / `idle_timeout` / `server` 等 L1 已处理过的）→ **不 raise**；**`yield item` 后 `return`**（直接结束 `call_llm_with_fallback`，把 error 交给上层 `set_failed`）。
  - 其它/未知（真正需 L2 兜底：LLM 调用异常、非传输限流的其它 error）→ 保持原 `raise LLMResponseError` 走 L2 重试（兜底不改变既有权重）。
  - **自洽佐证**：改 C 只给带 `exc_type` 的 L1 流式错误（`llm_stream.py:201`）填 `error_type`；而 `llm_stream.py:186` 的「LLM 调用异常」走 `_yield_error_response(f"LLM调用异常: {e}", agent, exc=e)` **未传 exc_type** → 改 C 后 `error_type` 为空 → 改 D 归「其它」→ 保持 L2 重试。即瞬时调用异常仍可重试，行为不退化。

  > ⚠️ **关键落法（三堂会审抓到的漏洞）**：放行时**必须 `return`**，不能仅 `yield item` 后继续循环。否则 L2 的 `for attempt in range(...)` 会 `continue` 到下一轮 → 再 `call_llm_stream` → 再跑一遍完整 L1 → **放大依旧，修了个寂寞**。`return` 同时避免走到 `:291` 的 Text 降级放大（429/传输错误重试无意义）。
  >
  > ⚠️ **空响应与本改法无关**：真·空（`content` 和 `reasoning` 皆空）在 `answer_handler.py:143-155` 走 `MetaStep(type="retrying")` 编排层重试（RETRYING 态驱动，前端可见），**不经 L2**；L2（`call_llm_with_fallback`）只对 `type=="error"`（:280-281）重试。故「L2 管空/无效响应」是错误表述，L2 与空响应无交集，改 D 不影响空响应路径。

**效果**：一次 LLM 调用最多 `L1(4次)`（429 经 ① 只 1 次即失败）**或** `L2(2次)`，**取其一，不再相乘**；传输错误不被 L2 拉一轮，429 不降级、快速失败。

### 7.6 明确不做（否决项）

- **③ 任务级全局熔断 / LLM 调用总时长/总次数上限**：北京老陈 2026-09-01 明确否决（"猪狗不如的烂代码"），本方案不实施。

### 7.7 验证要点

- ①：模拟 429，确认 L1 不再重试、直接 `quota_exceeded → set_failed` 快速失败。
- ②：模拟 L1 传输错误（ReadTimeout/429），确认 L2 不再重试、直接放行上层；模拟「LLM 调用异常」（非传输限流类），确认 L2 仍正常重试 2 次。
- 回归：正常任务（LLM 正常返回）不受影响，L1/L2 行为不变。
- 日志从 `[Retry][L1]`+`[Retry][L2]` 交叉爆炸收敛为单一层级重试。

### 9.3 前端分流权威表（1 个业务/元二分，确定"哪进 step、哪进 taskinfo"）
