## 一、问题描述

### 1.1 现象

1. 任务执行到一半，任务信息条的"耗时 Ns"计数器出现**清零、停表、恢复后回跳**。
2. 一处后端错误产生时，**弹窗、聊天内容变红字、计时清停**三处同步动作，观感为"一个错多处齐动"。

### 1.2 错误展示位置界定

本设计中错误展示位置共三处，后文统一引用：

| 编号 | 位置 | 说明 |
|---|---|---|
| P1 | 弹窗提示条 | 右上角 toast，自动消失 |
| P2 | 对话区消息气泡 | 正在播放的那段，出错时可能被替换为红字 |
| P3 | 任务信息条第4位 | 任务条靠右的 liveErrorText 段 |

### 1.3 实证结论

- **B1【已修复·已提交】**：计数器绑定任务成败徽标，错误一来徽标变"失败"连带计时清零停表，恢复后回跳。修复提交 `a3d7a38a0`，条件改为仅依赖"是否在接收实时数据"。
- **B3【本次修复】**:后端业务错误被误送进弹窗引擎，一次错误同时触发 P1/P2/P3 动作。
- 其余行为（左栏任务列表重刷、徽标自愈）属既有设计，不在本次范围。

## 二、根因分析

### 2.1 根因一：计数器与徽标耦合（B1，已修复）

"走不走表"绑定"任务成败徽标"。错误信号拉低徽标→计时清零停表；恢复后计时基准被重置→回跳。修复方式见 1.3，本章不再展开。

### 2.2 根因二：错误不分来源，后端错误误入弹窗引擎（B3，本次修复）

现状错误信号进入前端后**不区分来源**，统一送入 `handleSSEError` 弹窗链路，并连带执行消息替换、计时清停。后端业务错误本应只进 P3 显示，却触发 P1/P2/P3 全链路。

### 2.3 现状链路

```
后端 error 消息 ──┐
前端连接错误 ────┼──→ handleSSEError(弹窗) ──→ P1 弹窗 / P2 红字替换 / P3 计时清停
                  └──→ 消息替换、计时清停
```

#### 3.1.1 step控制类消息类的功能逻辑说明

两条 step 控制类消息（thought-start / start）都是"显示控制类"：为 step 页面/任务信息条服务，定位 UI 节点、控制符号，不承载任何业务载荷（不产正文/工具内容），且都不落库（start 只写 metaFrames 内存帧，thought-start 仅内存入列不同步 sessionStorage）。启动顺序：流量启动信号先到齐（start→时钟/上下文/身份徽章、thought-start→思考段定位），之后才进 think/action/chunk 业务消息。原第三条 startinfo 已并入 start（见 4.4.3），不再单列。

**① thought-start ——「已开始思考」业务流标记节点**（sseParser.ts:200-215 已读、PipelineRenderer.tsx:146-147 已读、ThinkingStream.tsx:21-50 已读）

字段一览：

| 字段 | 值 | 使用情况 |
|---|---|---|
| type | `'thought-start'` | 业务流"开始思考"标记，PipelineRenderer buildSegments 特判产出 `{kind:'waiting', step}` 等待段（4.4.2 起，PipelineRenderer.tsx:146-147），不产正文 |
| content | `''`（空） | 无载荷，无消费 |
| step | `Number(rawData.step) \|\| 1` | 步骤号，入列时锚定思考起点 |
| timestamp | 时间戳 | 入列时间，锚点记录 |

它入 executionSteps 并同步 ref，但仅是内存帧，不落 sessionStorage（不经持久化）。

在 UI 层，PipelineRenderer 的 buildSegments 专门为它写了 case（PipelineRenderer.tsx:146-147）：4.4.2（2026-09-07）起由"break 不产出任何段"改为直接产出 `{kind:'waiting', step}` 段——等待图标随该段就地渲染，首个思考内容（chunk/thought）到达时 waiting 段就地被 thinking/text 替换，图标消失由内容接管（渲染分支 PipelineRenderer.tsx:279-285，waiting-cursor aria-label"等待下一个思考内容"于 :105-106）。至于思考段内部尾随的 ▍ 呼吸光标，由 ThinkingStream 的 cursor prop 渲染，跟着 streaming 实时态走，与 thought-start 无关。

一句话定位：thought-start 是"思考开始"的时间/位置锚点，把每一步的思考起点锚进步骤列，实际光标符号由 thinking/streaming 渲染，它自己不画任何符号。

**② start ——「任务时钟 + 上下文概况 + 身份徽章」taskinfo 锚点**（sseParser.ts:181-197 已读、TaskInfoBar.tsx:81,218-223 已读、useTaskInfo.ts:205 已读）

字段一览：

| 字段 | 值 | 使用情况 |
|---|---|---|
| type | `'start'` | 任务启动信号，触发本消息处理 |
| content | context_summary 上下文摘要对象 | 写 frames.contextSummary → 无 contextOverview 时任务信息条上下文摘要兜底（start.content 为对象形态） |
| user_message / task_id / provider / model / api_base / display_name / system_prompt / warning | 任务启动装配元数据 | 身份/输入快照；task_id 另写 frames.startInfo（sseParser.ts:170-172 setServerTaskId → 任务入列表/会话标识） |
| ai_message_id | 后端发布前注入（react_loop.py:113） | 任务身份快照（4.4.3 后原 startinfo 职责并入 start） |
| startTimestamp | `Date.now()`（前端补） | 秒表首次锚定（startRef 仅锚首帧）+ processEvents"任务已开始"首行时间 |

它处理时写三个元信息帧：frames.contextSummary、frames.startTimestamp、frames.startInfo（五字段身份，sseParser.ts:184-195），不进入步骤列、不进右侧流水线。

UI 上三点消费：第一，startTimestamp 给 TaskInfoBar 秒表做首次锚定（startRef 只锚首帧，防抖动），同时作为 processEvents"任务已开始"首行的时间；第二，contextSummary 在任务信息条没有 contextOverview 时做上下文摘要兜底显示；第三，startInfo 驱动"执行中"徽章亮起与"任务已开始"过程条首行（见 ③）。

一句话定位：start 不是 UI 符号，而是 taskinfo 第一行的"时钟起点 + 身份徽章开关"——秒表从 start 帧开始计时，上下文概况由它占位，执行中徽章由它写入的 startInfo 点亮。

**③ start 内嵌的 startInfo 帧 ——「任务身份 + 状态徽标」驱动帧**（sseParser.ts:188-194 写入、useTaskInfo.ts:130,199-207,217-222 已读、useChatPanels.tsx:242 已读）

#### 3.1.2 HTL授权/安全消息-功能逻辑说明

授权弹窗不是独立 SSE 消息类型（后端没有"授权请求"事件），它是 **paused 事件带 `confirm_id` 字段时**触发的前端弹窗行为。与授权弹窗相关的 SSE 消息与处理链如下：

**1. 开弹窗——只有 paused（带 confirm_id）一条消息**

- SSE：`paused` 事件带 `confirm_id`（连同 tool_name/params/safety_level/trust_path/auto_confirm/confirm_timeout/backend_timeout 共 8 字段）→ 触发 `onAuthorizationRequired`（sseParser.ts:852-863）
- 前端：dispatch `authorization_required` 自定义事件（useChatCallbacks.ts:704-706）→ `useAuthorization` 监听后 setAuthorizationPending 显示弹窗（useAuthorization.ts:52-89）

**2. 关弹窗——三条路径**

- 用户按钮（确认/拒绝/勾选信任）：立即关窗 + fire-and-forget 调后端 `taskControlApi.confirm(confirmId, confirmed, trustSession)`（useAuthorization.ts:127-186）；确认且勾选信任成功后派发 `omni-trust-changed` 通知信任面板
- 倒计时归零自动处理：`auto_confirm=true` 自动代发放行，否则自动拒绝（AuthorizationModal/index.tsx:117-126）；计时解析：合法 0 = 禁倒计时，仅 NaN/负数兜底 60（useAuthorization.ts:19-22）
- **resumed（带 confirm_id）兜底关窗**：后端超时放行等恢复路径报 resumed 时，派发 `authorization_resumed`，校验 confirm_id 与当前弹窗一致即关（sseParser.ts:866-875；useAuthorization.ts:96-105）

**3. 弹窗互斥/覆盖**（useAuthorization.ts:60-65）

- 同 confirm_id 重放去重，不二次弹
- 新 paused+confirm_id 到达而旧弹窗未关：先对旧 confirmId 调 confirm(旧, false, false) 拒绝旧的，再开新窗
- 拒绝后弹出的后续：后端执行拒绝后发独立事件 `user_rejected`，前端走 `onDenied` → 被拒工具灰字点名 + 齿轮停转（sseParser.ts:561-571；useChatStreaming handleDenied），不占 liveErrorText、不出红字；`user_rejected` 不直接操作弹窗（弹窗已在按钮点击时关闭）

**4. user_rejected——用户拒绝后的独立消息（完整使用逻辑）**

**性质**：后端在弹窗被拒绝后**独立、单独发的一条消息**，不是 error 事件（sseParser.ts:560-571 注释早写明"拒绝不是 error 事件，后端独立 type='user_rejected' 单独发"）。

**什么时候来**：用户在弹窗上点了拒绝，或倒计时归零走了自动拒绝后，后端执行拒绝，随后单独补发这条 user_rejected 消息，通知前端"这轮工具是被用户拒掉的"。

**入口与去向**：进 `onDenied(step, message, toolName)`（sseParser.ts:561-569），三参带上被拒工具名。关键约束：**不占 error 通道、不写 liveErrorText**——它不走红字位、不触发弹窗、不清计时，与错误完全分道。

**前端处理链**：`handleDenied`（useChatStreaming.ts:220-225）→ `markDenied` → 聚合两处：① `deniedStepSet`（本执行轮 step 的 denied 计数，供齿轮停转判定）；② `deniedEntries`（step→被拒工具+理由点名条）。

**层层显示**：step 页面（流水线）该工具行 ToolCallLine 显示拒绝灰字点名，并因 denied 计数达成停齿轮（不再假装工具还在跑）；点名条按 step 取，多个被拒工具各自列出（ToolCallLine.tsx:379-387 渲染点名条；停齿轮判定 PipelineRenderer.tsx:356-360）。

**与 blocked/timeout 的关系**：同为"工具没能落刀"的三路聚合（B2方案C，北京老陈裁定）——blocked（工具被拦）和 timeout（超时未回）经 **error 事件**的 step/tool_name 字段聚合（sseOnError，useChatStreaming.ts:204-216），user_rejected 走**独立事件**；三路汇入同一 deniedStepSet/deniedEntries，UI 上灰字点名方式完全一致，只是来源不同。

**与授权弹窗的关系**：user_rejected **不直接操作弹窗**（弹窗在按钮点击时已经关闭，见第 2 点）；它的职责是补充"被拒"的显示痕迹——让流水线知道这个工具是用户拒的，不是失败/超时。

- error 消息：不入执行步骤，经 onError→liveErrorText → 徽标兜底置"失败"（被业务继续或 final 覆盖） useTaskInfo.ts:188-196（已读）

#### 3.1.4 任务信息条计时逻辑（耗時 Ns）线框说明

基于表 B4（taskinfo 计时）的计时逻辑线框图与文字说明如下。

**线框总览**

```
┌───────────── 任务信息条第 1 行： [徽章] 耗时 {shownElapsed}s 步骤 X / 轮次 Y [红字位] ─────────────┐
│                                                                                                  │
│  shownElapsed 三选一（逐级判断，先命中先取）：                                                    │
│                                                                                                  │
│  detail（历史任务） ──────────────► info.elapsedSec   = finalStats.duration ?? stats.duration ?? 0 │
│  receiving（实时收流中） ─────────► liveElapsed        = 本地秒表，按 start 锚点累加                │
│  其余（收场完成/连接断） ─────────► info.elapsedSec   = 终态后端 duration 回退                      │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

**本地秒表 liveElapsed 运转（useEffect 依赖 [receiving, detail]）**

```
                receiving && !detail ?
                 │
                 ├─ 是 ──► startRef 为 null ？首次锚定 startRef = frames.startTimestamp || Date.now()
                 │           （仅锚首帧，防计时抖动；任务切换时已复位）
                 │         setInterval 1s → liveElapsed = Math.max(0, (Date.now() - startRef) / 1000)
                 │         清理函数 clearInterval 停走
                 │
                 └─ 否 ──► liveElapsed = 0；startRef = null（任务切换/收场复位）→ 不产生计时周期
（R1 已修：依赖去掉 info.badge —— 错误/失败态下秒表继续走，不归零、不回跳）
```

**SSE 事件驱动的计时状态转换（对应表 B4 各行）**

```
   start ──────► frames.startTimestamp 写入 → 秒表起点锚定（TaskInfoBar.tsx:81）
   receiving ───► 实时流在 → 秒表走；首个 start 后持续累加
   final ───────► 收流结束 receiving=false → 停秒 → 显示终值 finalStats.duration（优先）/ stats.duration（兜底）
   final(outcome=cancelled) ─► 取消收尾 receiving=false → 停秒 → 回退终态 duration（4.4.1 后无独立 cancelled 事件）
   error ───────► R3 分道：A 后端业务错误 → 不停收流、不计时不受影响（任务还在走）
                   B 前端连接错误 → 停收流 → 停表（此为 R3 待改代码点 sseParser:554-555）
```

**计时逻辑要点说明**

1. **两个时钟源分工**：实时态以本地秒表 `liveElapsed` 为准（从 start 锚点起逐秒累加）；终态/历史态以**后端 duration** 为准（`elapsedSec`，finalStats.duration 优先、stats.duration 兜底，见 useTaskInfo.ts:245）。前后端不互相覆盖。
2. **start 只做锚定，不做计时开关**：秒表开关由 `receiving && !detail` 决定；startRef 仅在为 null 时写一次，防 start 帧重复/抖动导致计时回跳。
3. **错误不归零不回跳（B1/R1 修复核心）**：此前计时挂靠"徽标 running"，错误一来徽标变失败连带计时清零、恢复后又回跳；R1 已改为只依赖 receiving，秒表与徽标彻底解耦。R3 分道后 A 类后端业务错误甚至不触停收流，更谈不上停表。
4. **任务切换复位**：切走历史任务时 `startRef=null`、`liveElapsed=0`，再切回新任务重新锚定，互不串时。
5. **R3 分道边界**：表 B4 的差异/重设计点即在此——sseParser:554-555 现对 error 一律 `setIsReceiving(false)`，R3 应只对 B 类前端连接错误停表，A 类后端业务错误放行。

#### 3.1.5 上下文的显示逻辑说明

**显示位置**：任务信息条第 1 行中段，紧跟"本任务累计 T"之后。第一行横向分三段——左段：徽章/耗时/步骤·轮次/红字位/疑似卡死；中段：本轮 T → 本任务累计 T → 上下文；右段：信任面板。上下文是独立一格，用 `·` 与 token 数字隔开。

**数据来源**：两级来源、同一显示格——`overview` 与 `contextSummary` 两消息相互独立，谁有谁顶上，都没有就显示 0tok：

[1] `overview` 来自独立事件 `context_overview`——前端帧五字段：summary/message_count/estimated_tokens/truncated/injected_ratio（sseParser.ts:282-294）；后端实际另发 injected_message_count/injected_estimated_tokens/severity 等键（react_step.py:343-351），前端帧不收。
[2] `contextSummary` 来自 `start` 事件（content 即 context_summary）。

**显示逻辑**（四个分支，按优先级从上到下）：

1. `overview` 是字符串 → 显示"上下文摘要"，悬浮信息挂该字符串。
2. `overview` 是对象（由 `context_overview` 事件写入）→ 显示"上下文 Xtok"；`truncated=true` 时附加 🔴；悬浮信息显示 摘要 + 消息数/估算 tok。
3. 无 overview 但 `frames.contextSummary` 有值（由 `start` 事件写入，即 start.content）→ 显示"上下文摘要"，悬浮信息挂 contextSummary 字符串。
4. 以上都没有 → 显示"上下文 0tok"。


#### 3.1.6 错误消息（SSE 事件 type="error"）

后端把错误**单独**发成一条错误消息，载体统一为 SSE 事件 `type="error"`（`MetaStep(type="error")`，仅 SSE 推送、不落库），与收场消息（3.1.8 final）互不掺和。**只有一种 error 消息（type="error"），error_type 只是其中的一个字段**，取值来源分两类：

**error_type 取值来源之一（后端固定硬编码）：**

| error_type | 含义 | 触发条件（代码出处） | 处理 |
|---|---|---|---|
| invalid_action | 无效命令 | 模型要执行空命令（handle_action.py:331） | 仅 P3 显示；不弹窗、不碰消息、不清计时 |
| blocked | 工具被拦 | 安全系统拦下工具（safety_gate.py:82） | 同上 |
| timeout | 确认超时 | 等待用户确认超时（safety_gate.py:125） | 同上 |
| empty_response | 模型空回复 | 模型无任何输出（react_step.py:363） | 红字收场；不弹窗；计时清停 |
| chunk_buffer_timeout | 累积超时 | 长时间未攒够完整输出（react_loop.py:246） | 同上 |

**error_type 取值来源之二（循环内 LLM 调用抛异常，分类器现算）：**

循环内 LLM 调用抛异常时，handle_react_error 统一产 type="error"（react_inference.py:47-52），error_type=SystemErrorClassifier 分类名小写（error_classifier.py:190-234），content=异常文本。大类释义：

| error_type | 大白话含义 | 判定依据（error_classifier.py） | 可重试 |
|---|---|---|---|
| circuit_open | 熔断：该 LLM 服务先前已被判不可用，直接拒发请求 | 异常文本含 "circuit"+"open"（:218） | 否 |
| client | 我方请求有毛病：HTTP 4xx（模型名配错 400、Key 无效 401/403、404 等），重发必再失败 | HTTP 4xx 一律 CLIENT（:160-168） | 否 |
| server | 对方服务器出问题：HTTP 5xx（500/502/503/504）或未识别的网络异常，重试可能成功 | HTTP 5xx→SERVER；黑名单默认 SERVER（:169-172、:232-234） | 是 |
| unknown | 程序自身 bug：Python 内置异常（ValueError/TypeError 等），重试无意义 | 内置异常名匹配（:225-230） | 否 |
| idle_timeout | LLM 装死：请求发出后 30 秒未返回任何内容 | IdleTimeoutError 实例（:128-129） | 是 |
| rate_limit | HTTP 429：接口限流/配额耗尽 | 429→RATE_LIMIT（:103） | 否 |

处理统一：红字收场；不弹窗；计时清停。

**命名与语义的名不副实澄清**：以上分类名并不全部名副其实（对分类器判定逻辑核实，功能不受影响——真正驱动重试的是 `is_retryable` 判定）：
- `client / rate_limit / idle_timeout` 名副其实——分别真实对应 HTTP 4xx、HTTP 429、LLM 30 秒无输出。
- `server` **名不副实**：它是黑名单默认兜底（error_classifier.py:232-234），实际是"可重试综合类"——网络断连、连接错误、读超时、5xx 及一切未被认领的异常都归它，并非单指"服务器错误"。
- `unknown` **名不副实**：它只匹配 Python 内置异常（ValueError/TypeError 等，:225-230），实为"程序内部 bug"，不是"查不出原因"。
- `circuit_open` 判定靠异常文本含 "circuit"+"open" 字样（:218），不是读真实熔断器状态，严格说是"文本猜测"。

（注：改名需后端枚举/映射/透传元组与前端 58 条 ERROR_CONFIG_MAP 全链路同步，列为独立改造项）

#### 3.1.7   retrying  消息说明

后端把"LLM 调用出错，正在重试"单独发成一条 `type="retrying"` 消息（MetaStep、status=retrying），让前端把重试过程展示给用户。产生点（三条路径）：

1. **L1 可恢复重试**（react_loop.py:205-210）：主循环内 LLM 可恢复异常、重试计数 ≤3 时 → `MetaStep(type="retrying", content="LLM请求异常，准备重试: ...", severity="info")` emit+publish 进 SSE；计数 >3 则直接终态 `final(error_type=recoverable_retry_exhausted)`（react_loop.py:193-203 异常分支 / 228-238 RETRYING 状态分支）。
2. **L2 重试**（llm_call.py:252-263）：LLM 流式 error 未命中透传元组（circuit_open/server/unknown/empty_response 等可重试类）→ raise LLMResponseError → 每次重试前 yield `{"type":"retrying","content":"LLM响应重试 X/Y: ...", "wait_time": ...}` 透传前端（llm_call.py:257-261）。
3. **FC 降级**（llm_call.py:270-274）：FC 模式全部重试失败、降级 Text 前，再发一条 retrying 通知告知用户。

**前端消费**（sseParser.ts:818 `case 'retrying'`；stepStyles.ts:183 渲染"🔄 重试"状态行；status_table RETRYING）。

重试消息只负责说明"正在重试"；**重试失败后的收尾不在此消息，而是糅合进 final**（见 3.1.8）。

#### 3.2.3 三类弹窗（critical / warning / info）的展示差异

本节回答一个核对问题：红、黄、普通三类弹窗在大小、停留时间、信息多寡上有无差异。三类弹窗渲染自**同一个 antd v5 message 组件**（`getMessage()` 经 `App.useApp()` 桥接，bridge.ts:21），本工程未做任何尺寸/主题定制，因此差异只来自工程显式配置与文案本身。

**一、大小：三类无差异**

三类弹窗使用同一消息组件、同一套 `.ant-message-notice` 样式，高度、宽度、字号、圆角、间距完全一致。视觉差异仅在图标与颜色：critical 为红色 ×，warning 为黄色 ！，info 为蓝色 ⓘ。工程未设置主题 token（main.tsx:15 的 ConfigProvider 仅配 locale），也无全局 CSS 覆盖 `.ant-message`（index.css 无相关样式）。

**二、停留时间：critical 明显更长**

配置集中在 `UI_CONFIG`（handler.ts:38-44），`showMessage` 按 severity 取用（handler.ts:731-757）：

- critical（error）：停留 5 秒；
- warning：停留 3 秒；
- info：停留 3 秒。

三类弹窗都登记唯一 key（`eh-错误类型`），重复触发时不新增第二条、只更新该条内容并重置倒计时；critical 的 5 秒比另两类多 2 秒，用意是给严重错误留足阅读时间。

**三、"同时最多几条"的澄清**

`UI_CONFIG` 里确实预设了 error.maxCount=1、warning/info.maxCount=3，但这是一个**未接线的遗留配置**——`showMessage` 只用了 duration，全工程没有任何地方调用 `message.config()` 或向 message 实例传 maxCount，antd 默认不限制并存条数。因此"同时最多"的条数限制**实际不生效**，并发（多个不同错误在同一时刻先后触发）时的真实行为是：

- **同类去重（key 合并）**：同一错误类型连续触发，只保留 1 条（更新内容并重置计时，不堆叠）；
- **异类并存（无上限）**：不同错误类型各自一条、可同时堆叠多条，没有条数上限；
- **共用一个容器**：critical / warning / info 全部进入同一个 message 容器，不按类型分窗口、不互相让位。

**四、信息多寡：同为单行短句，无结构化详情**

`showMessage` 只渲染 `content` 一个字段：单行文案、无标题、无描述、无错误码、无堆栈、无"详情"按钮（handler.ts:724-757）。信息量的差别只在文案长短与措辞力度：

- critical（7 个）："动作 + 后果 + 强行动建议"，约 8~16 字，如"危险操作已被拦截""服务器内部错误，请稍后刷新页面重试"；
- warning（42 个）："失败 + 建议动作"，约 8~20 字，如"网络不稳定，请稍后重试""服务器连接被拒绝，请检查后端服务是否运行"；
- info（3 个）：最短的纯告知语，4~6 字，如"操作成功""任务操作成功"。

另有 3 处空文案（`retry_warning` / `WARNING` / `INFO`，message 字段为空）本身不弹空 toast（handler.ts:727 Bug6 修复），文案由调用方以 `customMessage` 传入，如重试提示场景。

**小结**：大小零差异；停留时间 critical 5 秒、warning 与 info 均为 3 秒；信息量三者同为单行短句，差异仅在文案长度与措辞力度。

**五、点击交互：可以点击，但不需要点击**

`showMessage` 给每类弹窗都显式绑定了点击关闭（onClick → destroy，handler.ts:733-756），三个要点：

- 可以点击：点一下立即销毁该条弹窗——这是工程显式绑定，不是 antd 默认行为；
- 不需要点击：倒计时一到自动关闭（critical 5 秒、warning/info 3 秒），不点不残留；
- 点击没有其他业务动作：不跳转、不重试、不看详情，仅"提前关闭"；与 HITL 工具确认弹窗（Modal，必须操作）性质不同。

## 四、优化的问题与设计目标与总原则

本次设计只动"错误消息"这一类：第三章列出的全部消息小类（后端 SSE 传来 + 前端本地）里，**除错误消息外，其余全部保持现状、零改动**。后面的设计目标、改动、验收全部围绕错误消息的处理展开。

### 4.1 总原则

> 前端自己的错误，只能弹窗提示；后端的错误，只进任务信息条第4位等展示，不弹窗。

### 4.2 目标行为决策表

| 错误 | 弹窗 | P2 消息内容 | 计时 | P3 第4位 |
|---|---|---|---|---|
| 后端·轻错（可恢复） | 不弹 | 不碰 | 不停 | 显示 |
| 后端·重错（终态） | 不弹 | 变红字（正常收场） | 清停 | 显示 |
| 前端·连线 | 弹 | 变红字 | 清停 | 不适用 |

### 4.3 设计目标

1. 后端业务错误**不进入弹窗链路**；
2. 可恢复错误**不触碰**消息内容与计时；
3. 终态错误保留既有收场动作（消息红字替换、计时清停）但**不弹窗**；
4. 前端连接错误行为完全不变。

### 4.4 优化要点说明及分析
#### 4.4.1 取消终态信号的分工：final+cancelled 单一承担收尾，type=cancelled 事件不进前端


**1. 现状分析**
**现象**：一次取消，后端前后脚发两个消息——先 `type='cancelled'`（task_runtime.py:88-92 `task_cancel_check_and_yield` 检测到取消标记立即发出），后 `final.outcome='cancelled'`（react_loop.py:139-149 循环收尾 publish FinalStep）。两者语义相同，是否重复？

**核读结论**：
1. **final 分支自身已完整收流**：sseParser.ts:468-476 `onComplete()` + :482-483 `setIsReceiving(false)/setIsConnected(false)`——final+cancelled 一到，停秒收流全做，不依赖 type=cancelled。
2. **type=cancelled 到前端走的收流动作（sseParser.ts:815 外层入队 + :849-857 内层收流）与 final 完全重复**，且驱动不了徽章（useTaskInfo.ts:163 只认 `final.outcome='cancelled'`）；前端 `case 'final'` 已在 sseParser.ts:148 同步解析 `outcome`，final+cancelled 到达即可完整替代。
3. **type=cancelled 的检测时机不能丢**：`task_cancel_check_and_yield`（task_runtime.py:80-92）每读一个 chunk 检测取消标记，是"SSE 流及时终止"与"取消确认心跳"（useChatCallbacks.ts:133-137 `isCancelEvent`，等待侧 useChatTaskControl.ts:125-148 `waitForCancelEvent`）的发出源——检测要保留，只须把**发出的 step 从 type=cancelled 改为 type=final+outcome=cancelled**，前端 `case 'final'` 全权接管收尾，心跳/徽章不受损。
4. **启动前取消分支同源**：`task_cancel_check`（task_runtime.py:100-105，stream_orchestrator.py:276-281 启动前调用）也产 type=cancelled，须一并转为 final+cancelled，否则前端删 case 'cancelled' 后该分支到达无法识别。

**2 修改方法**：
- `type='cancelled'` 作**后端内部取消控制逻辑**是对的（检测取消、终止循环）；
- 但**再作为 SSE 事件推到前端走那套收流是冗余**——取消收尾应由 `final+outcome='cancelled'` 单一承担，前端 `case 'cancelled'` 彻底删除，连接强关（task_runtime.py:57-63 `ai_service.cancel()`）再兜底；
- 表 B1 的 cancelled 事件行按此定论：**不承担显示收尾，事件本身从前后端完全移除**——后端检测取消后直接组装 final+cancelled 发出，前端仅按 final 收流。

#### 4.4.2 thought-start 信号：双发射点分析

**1. 现状分析**

**what**：thought-start（ThoughtStartStep）是"开始显示 thought 等待图标"的信号——前端收到即在思考区亮转圈等待图标；后续显示/消失逻辑走现有绿圈机制（waiting-cursor，PipelineRenderer.tsx:385-391）。

**how many**：一个任务从开始到结束，发射总量：

> **总数 = loop 里调工具次数 + 1（出 loop 的最终收尾轮）**

- loop 里每次调工具（handle_action:348）→ 发 1 个（调完回 loop 继续）；
- 出 loop 的最终收尾（handle_answer:169 正常 / :88 error / :103 未知 / :141 reasoning 超限终止）→ 发 1 个；
- 例外（loop 中既不调工具也不出答案的轮：真空重试→retrying:119、reasoning-only 继续→ThoughtStep:158）→ 不发。

例：调 3 次工具后回答 = 4 个；纯聊天直接回答 = 1 个。

**why 两个发射点**：每轮 LLM 返回经 `_dispatch_handler` 二选一（react_dispatch.py:73-76）——`type=="action"` 进 handle_action，其余进 handle_answer。两处是"哪条路径就哪个发"，互斥并列，**不是每轮两发**。

**时序差异（两处行为不同）**：

| 维度 | 调工具轮（handle_action:348） | 收尾轮（handle_answer:88/103/141/169） |
|---|---|---|
| 发射方式 | `_buf.publish()` 直接写流即发 | `_events.append()` 收集后统一 yield |
| 时序位置 | LLM 决定调工具后、工具执行前即发（:348），随后 thought(:349) → action 预览(:368) → 安全/授权 → 才执行 | 决定收尾即发，在同一轮 events 最前，紧跟 final |
| 前端看到 | 等待图标 → 思考正文 → 工具齿轮 | 等待图标 → 终态消息 |

**逻辑差异**：调工具轮 = 「thought-start → thought → action」行动单元开端；收尾轮 = 「thought-start → final」收尾单元开端（thought-start 即"本轮即将 emit final"的固定序幕）。

**前端 thought 等待图标的消失方法（现状）**：
1. **等待图标（绿色缺口圆弧 waiting-cursor）——内容覆盖制**：thought-start 信号本身不产内容（PipelineRenderer.tsx:110-111 `case 'thought-start': break;` 仅作信号入列）；图标是条件渲染 `showGreenCircle = taskActive && (!lastSeg || lastSeg.kind==='obs')`（:234），`taskActive = streaming || highlightToolName || badge running/paused`（:229-233）；**消失全靠条件变假**——首 chunk 一到末段变 thinking/text，条件即不成立图标瞬消，位置让给内容从同一首列打字机接管；任务结束（final/error 到达）同理，CSS 注释明确"禁止常驻，由内容覆盖接管"（index.css:55-57）。
2. **thinking 段内呼吸光标 ▍（.thinking-cursor）——末段限定 + streaming 门控**：`cursor = streaming && i===lastThink && i===segs.length-1`（:249）；仅亮在"最后一个 thinking 段且实时流中"，旧段不再是末段（新段到来）即灭，streaming 结束（final/error/断连）即灭，CSS `thinking-blink` 1s 闪烁（index.css:37-42）。

**结论**：当前等待图标消失完全依赖"后续内容（thinking/text 段或终态）到达后条件翻转"，不依赖 thought-start 信号驱动显示/消失；若按本小节前端新用法（收到 thought-start 即在新行首列亮图标），消失仍需沿用"首个 chunk 到后内容覆盖"制。

**2. 修改使用说明**

（本小节依北京老陈 2026-09-07 裁定写入正确发送时序。元规则一句话：**thought-start 是"等待 thought 出现"的信号，必须发在每次"可见轮"（进 loop 前、每次工具轮 observation 之后）的 LLM 请求之前，而非响应之后**；真空重试(:119)/reasoning-only 继续(:158) 等不可见中间轮豁免不发（其等待由既有可见轮的发射承接，见 §3.1 保留不动）。现状全部 5 个发射点都在 LLM 响应之后（handle_action:348、handle_answer:88/103/141/169），时序方向错误。）

   - 前端收到该信号后，开启一条新空白行，在**首列**显示 thought 等待图标动画（thought 等待图标）；

**3.4 TDD 驱动原则**

本方案落码采用 TDD 驱动（红 → 绿 → 重构），**所有行为细节必须先有失败测试再改实现**，严禁"先改代码、后补测试"。测试位置按代码分层落位：后端单测 `backend/tests/`（pytest，mock LLM 不连真实服务），前端 `frontend/src/tests/unit|reality/`（Vitest）。

1. **原则一：测试先行，先红后绿**。每一个改动细节都对应一条可执行测试用例；先写测试并跑出**失败（红）**，再改实现到**通过（绿）**；实现只做"让测试变绿的最小改动"，不写多余逻辑（YAGNI/KISS）。
2. **原则二：从纯函数起步（前端）**。先测 `buildSegments`（steps → 段数组，纯函数最易红绿驱动），覆盖本方案全部前端细节：thought-start 产 waiting 段、appendToLast 就地覆盖 waiting、thinking/text 相邻合并不变、多信号多 waiting、final 后 waiting 非末段退出、历史回放（非 live）不亮；再测 PipelineRenderer waiting 渲染门控（末段+taskActive）与首/后续信号位置。
3. **原则三：后端行为断言（mock 驱动）**。直接 mock LLM 响应注入 action/answer/error/unknown/空响应/reasoning 超限各形态，断言 `event_log` 中 thought-start 的**条数与时序**：纯聊天=恰 1 条且在 start 之后、while 之前；调 N 次工具=N+1 条、每条落在对应工具轮 observation 之后；return_direct 轮不发；error/unknown/reasoning 超限/正常 answer 轮均不发；真空重试/reasoning-only 既有逻辑不回归。
4. **原则四：一细节一用例，命名即行为**。用例名描述行为不改实现（如 `test_tool_round_emits_after_observation_before_next_request`）；每个细节单独一条，不合并、不遗漏、不偷懒。
5. **原则五：红绿可观测，全量回归**。改实现前跑该批测试确认红；实现后跑全量（后端 `pytest`、前端 `npm run test`）确认绿且无退化。
6. **原则六：保护既有绿基线**。修改前先跑既有相关测试（`test_react_cycle.py`、`test_path1_step4c_upstream.py`、`buildsegments-b2-bugs.test.tsx`、`pipeline-rendering.test.ts` 等）确认绿基线，落码后同批仍绿才算通过。
7. **原则七：重构不破绿**。行为正确后如需整理（如 showGreenCircle 去留、waiting 段并入既有渲染分支），一律在测试全绿前提下重构，重构完成再跑一遍全量。

**1.1 两个事件的来源**

**1.3 前端消费点**

| 事件 | 前端存储 | 消费者 | 用途 |
|------|---------|--------|------|
| start | `metaFrames.contextSummary` + `metaFrames.startTimestamp` | TaskInfoBar:218-219（上下文概况 Tooltip）、计时起点 | 内容摘要 + 计时 |
| startinfo | `metaFrames.startInfo`（task_id/display_name/provider/model/ai_message_id） | useTaskInfo:130 `hasStartInfo` → 徽标 running/idle（:199）、"任务已开始"过程条首行（:201-206） | 身份徽标 + 状态驱动 |

两者不冲突但**职责分散**：start 承载内容+计时，startinfo 承载身份+状态，前端需要解析两个事件才能凑齐"任务启动"的完整信息。

**1.4 三个问题**

**问题一：字段冗余违反 DRY**

task_id/provider/model 三字段（外加通用元数据 step/timestamp）在两个事件中重复，api_base/display_name 仅 start 携带、startinfo 不含（2026-09-07 小欧 核证）。startinfo 是 start 的严格子集（内容字段除外），多一次构造+多一次SSE传输+多一次前端解析，零增益。

**问题二：时序嵌套增加复杂度**

startinfo 不是独立事件，而是在订阅体通道路由中从 start 派生（agent_runner.py:354-364）：先 `_persist` 落库 → 再构造 startinfo → 再 `_publish`。一个事件拆成两步发射，通道路由逻辑变复杂（:352-364 是 start 专用的 13 行构造代码）。

**问题三：ai_message_id 分配时机是 split 根因**

start 发出时还不知道 ai_message_id（_persist 内部分配），所以需要 startinfo 来携带。这是历史设计遗留——原方案是 start落库 + startinfo 仅SSE 复用同一 ai_message_id（2026-08-18 小欧 注释）。但如果让 start 同时携带 ai_message_id，startinfo 就完全多余。

**1.5 合并可行性**

合并条件：让 start 的落库和 SSE 都在分配 ai_message_id 之后发射。

当前时序：`run_react_cycle` 内 `_publish(start)` → 订阅体 `_persist(start)` 分配 ai_message_id → 构造 startinfo → `_publish(startinfo)`。

目标时序：`run_react_cycle` 内 `_publish(start)` 携带 ai_message_id → 订阅体 `_persist(start)` 落库 → 前端从 start 一个事件解析全部信息。

难点：start 的 publish 在 run_react_cycle 内部（react_loop.py:98），而 ai_message_id 的分配在 agent_runner 的 `_persist`（:314-342），两者不同层。需要让 _persist 先分配 ai_message_id 再回填到已发布的 event_dict（或延迟 start 的 publish 到分配之后）。

**2 优化修正方法**

目标：`start` 发布时自带 `ai_message_id`，删除 `startinfo` 派生分支（agent_runner.py:354-364），前后端只剩 `start` 一个启动事件。

**2.1 为什么不需要"延迟 publish"——eager 值在 loop 启动前已就绪**

`ai_message_id` 并非 `_persist` 内部分配：12.2-C4 已改为 orchestrator eager 分配——`_setup_task_db` 内 `allocate_and_insert_message`（stream_orchestrator.py:356）→ `_ai_message_id`（:369）→ 以参数注入 `run_agent_in_background(ai_message_id=...)`（参数定义 agent_runner.py:195，orchestrator 调用点 stream_orchestrator.py:388-390）。`_persist` 的"惰性分配"注释已过时（:331 明确"ai_message_id已eager注入,惰性分支移除"），它只是**使用**该值落库，不再**产生**该值。

结论：`run_react_cycle` 启动前 `ai_message_id` 已知，无需重排 publish 时序，只需**透传**——把已知的 eager 值经 agent 对象递给 react_loop 的 start 发布点。

**2.2 为什么不能"在 _persist 里回填"——publish 浅拷贝截断**

`StreamBuffer.publish` 首行即 `step_dict = dict(step_dict)` 浅拷贝（task_state.py:49），缓冲里的副本与调用方传入的 dict 脱钩。`_persist` 里改 `event_dict` 只影响落库用的同一引用，实时 SSE 读到的是 publish 时的快照——start 发出时没有 `ai_message_id`，事后回填追不上。因此**必须在 publish 之前把 `ai_message_id` 装进 dict**，事后补救此路不通。

**2.3 前端只需合并分支——startInfo 字段实际只用了存在性**

`frames.startInfo` 全工程唯一读取点是 `hasStartInfo = frames.startInfo !== null`（useTaskInfo.ts:130），驱动徽标 running/idle（:199）与"任务已开始"首行（:201-206，时间取 `start` 事件的 `startTimestamp`）。`startInfo` 内部的 task_id/display_name/provider/model/ai_message_id 五个字段**无人消费**（全工程 grep 零读取）。合并后 `start` 分支同时置 `contextSummary`/`startTimestamp`/`startInfo`，徽标、首行、计时、概况行为全不变；且 `startInfo` 到达时机从"start 落库后"提前到"start 到达时"，徽章 running 只会更早亮，无退化。

**2.4 修改步骤（共 4 步，后端 3 + 前端 1）**

1. **透传**：`run_agent_in_background` 入口（eager 绑定旁，agent_runner.py:220-221 之后、`run_react_cycle` 调用 :296 之前）把 `ai_message_id` 挂到 agent 属性（`agent._ai_message_id`），供 react_loop 读取；
2. **装配**：react_loop.py:98 start 发布前，把 `agent._ai_message_id` 写入待发布 dict 顶层（publish 前装配；None 守卫——eager 分配失败时 `_ai_message_id` 为 None，前端按缺失处理，与现状 startinfo 缺失行为一致）；
3. **删除**：agent_runner.py:352-364 start 分支删 startinfo 构造 13 行，仅保留 `_persist` 落库；
4. **合并**：sseParser.ts:174-197 `case 'start'` 分支同时写 `startInfo`（含 `ai_message_id`），删除 `case 'startinfo'` 分支；`StartStep` 类不动（`ai_message_id` 走 dict 直挂，不入 Step 模型）。

#### 5.3.1 REQUEST_ABORT：连接层静默短路

**问题是什么**

`request_abort` 配置意图是**静默**（用户手动停止任务 / 组件卸载触发的中止，不应打扰用户），但连接层兜底映射把它误判为"请求等待超时"弹窗错误，三重打扰：

1. **配置意图**：`severity:'info'` + `silent:true`，应静默（出处 handler.ts:440-447）；
2. **实际行为**：`classifyError` 兜底映射 `case ErrorType.REQUEST_ABORT: return 'request_timeout'`，把中止误判为"请求等待超时"（出处 useSSE.ts:79-80）；
3. **触发链路**：用户停止任务或组件卸载 → catch 捕获 AbortError → `errorHandlerClassify` 返回 REQUEST_ABORT（判 name='AbortError'）→ 映射 request_timeout → 误弹 + 重连 + 覆盖消息（出处 useSSE.ts:725-757，handler.ts:819-821，useChatCallbacks.ts:525-556）。

**后果**：误弹"请求等待超时，服务器响应过慢"（warning）；按 request_timeout 判定可重试而自动重连；onError 把错误写进消息列表整体替换 assistant 消息。与静默意图及 4.4.1"取消收尾由 final+cancelled 承担"相悖。

**如何修正**

设计思想（KISS-DIRECT）：AbortError 是"终止"信号不是错误，不该进错误处理链。连接层 catch 块入口按纯分类函数先判一次，命中 REQUEST_ABORT 直接静默收尾返回，不进入 handleSSEError 弹窗/重连链路。


**设计修订：主动断开意图标记（最终方案，2026-09-07 已实施）**

上述"无差别短路"方案存在一个缺陷，经三审确认后修订为意图标记方案，最终形态与落点以本节为准。

**缺陷澄清**：`sendMessageInternal` 存在**两种主动 abort**，抛出的 AbortError 完全同型：

| 来源 | 位置 | 语义 |
|---|---|---|
| 用户停止 / 组件卸载 | `disconnect()` 内 `abortController.abort()` | 主动断开，应静默 |
| 180 秒请求总超时兜底 | `fetchTimeoutRef = window.setTimeout(() => controller.abort(), 180000)`（useSSE.ts:563-566） | **被动异常，应重连** |

`errorHandlerClassify` 仅判 `err.name === 'AbortError'`，无法区分二者来源。原"一律短路"会把 180 秒超时这条真实被动异常也静默掉——后端慢推理/卡死时（180s 兜底正是为 qwen 首次 CPU 推理约 2 分钟而设）前端既不重连、不耗尽后自动取消、也不报错，任务无声放弃。因此**不能按 error 对象判，必须按操作语义判**。

**最终方案（落点：`useSSE.ts`，无 handler/service 改动，无新依赖）**：

1. **新增 ref**（声明区）：
   ```ts
   const intentionalAbortRef = useRef(false);           // 主动断开意图标记
   const intentionalAbortTimerRef = useRef<number | null>(null); // 2s 兜底清残留
   ```
2. **`disconnect()` 确有活动连接时设标 + 2s 兜底清**：`if (abortControllerRef.current) { intentionalAbortRef.current = true; setTimeout(() => { intentionalAbortRef.current = false; }, 2000); ...abort... }`。无活动连接时**不设标**（不产生污染）。
3. **catch 入口消费短路**（先于 handleSSEError）：
   ```ts
   if (intentionalAbortRef.current && errorHandlerClassify(error) === ErrorType.REQUEST_ABORT) {
     intentionalAbortRef.current = false;
     abortControllerRef.current = null;
     setIsConnected(false);
     setIsReceiving(false);
     return;   // 静默收尾，不进错误中心
   }
   ```
4. catch 消费后置 false（唯一消费点）；未消费残留由 2s 兜底清理。

**修订后行为对照**（相对原方案差异标记"▲"）：

| 场景 | 原方案（一律短路） | 最终方案（意图标记） |
|---|---|---|
| 用户停止 / 组件卸载 → disconnect abort | 静默 ✓ | 设标 → 短路静默 ✓ |
| 180s fetchTimeout 被动 abort | 静默 ✗（失去重连） | 无标记 → 走 request_timeout 自动重连 ✓ ▲ |
| 断网 / 空闲超时 / 500 | 不短路，照旧 | 不短路，照旧 |
| reconnect() 前 `disconnect(false)` abort 旧流 | 短路，旧流不再追加重连 | 短路，旧流不再追加重连（消除双重重连隐患）✓ |
| 短路后 `serverTaskId` 自动取消（重连耗尽:164-170） | 不再触发 | 不再触发（用户已取消，不二次 cancel）✓ |

## 六、后端SSE传来的消息的优化处理方案

### 6.1 优化处理原则

后端业务错误一律不弹窗——可恢复（任务继续）不碰消息、不停计时，仅进任务信息条第4位（P3）显示；终态（任务收场）保留红字替换与计时清停，跳过弹窗引擎。分道依据：第四章 4.1 总原则。

**改动共三处，全部落点见 6.3。**

### 6.2 分道机制：来源标记

错误对象增加可选标记 `from_backend: boolean`，标注"该错误由后端业务产生"。该标记仅存在于前端类型内部，不新增网络协议。数据流：后端错误出厂打标（改动二，6.3.2）→ 前端 onError 按标记分道（改动三，6.3.3）。

#### 6.2.1 分道规则

1. **无 `from_backend` 标记，任意错误类型**：前端连接错误 → 原样进弹窗链路；
2. **`from_backend=true` 且为可恢复三型（invalid_action / blocked / timeout）**：直接放行——不弹、不碰消息、不清计时，仅 P3 显示；
3. **`from_backend=true` 其余（终态）**：跳过弹窗引擎，保留消息红字替换与计时清停。

#### 6.2.2 可恢复类型集合（白名单，北京老陈裁定）

```typescript
const RECOVERABLE_SSE_ERROR_TYPES = new Set(['invalid_action', 'blocked', 'timeout']);
```

### 6.4 修改后行为对照

1. **invalid_action / blocked / timeout（可恢复）**：弹窗无、消息替换无、计时清停无、P3 有；
2. **empty_response 等终态**：弹窗无、消息替换有（红字收场）、计时清停有、P3 有；
3. **前端 60 秒空闲等连接错误**：弹窗有、消息替换有、计时清停有、P3 无。

### 6.5 边界与兜底

1. **后端新增未知错误类型**：落入终态分支 → 不弹窗，仍符合总原则；
2. **可恢复类型遗漏未入清单**：落入终态分支 → 不弹窗，仅多替换一次红字，可接受；
3. **旧错误对象无标记**：按前端错误弹窗 → 宁肯弹窗，不静默吞错。

### 6.6 未改范围

- 后端代码零改动；
- 弹窗引擎、任务第4位、徽标状态、被拒工具灰字点名，均不动；
- 不加新网络协议，`from_backend` 仅存在于前端类型。

### 6.7 验收标准（后端板块）

1. **C1 blocked（后端·可恢复）**：不弹窗、不替换消息、计时不停，P3 有显示；
2. **C2 empty_response（后端·终态）**：不弹窗、消息变红字、计时清停；
3. **C3 60 秒空闲超时（前端·连接）**：照旧弹窗（守住现状基线）。
