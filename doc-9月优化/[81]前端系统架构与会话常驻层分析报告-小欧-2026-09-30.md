## 一、当前的前端系统架构情况分析说明

### 1.1 架构总体模型

当前前端（`frontend/`）采用 **模块级常驻 + React 订阅** 的四层模型。核心设计目标（[79] 会话流常驻架构）是：**会话流与任务不随 React 组件卸载/路由切换而中断或丢失**。

```
┌────────────────────────────────────────────────────────────────┐
│ L3 渲染/订阅层  React 组件树（可卸载、可切路由、可重建）            │
│  ChatPage 编排 13 个 hook                                        │
│  useChatFacade/useSessionTasks/useChatTitle/useChatPanels/…     │
│  UI 组件 ChatHeader/TaskListPanel/PipelineRenderer/             │
│  RightViewer/TaskInfoBar/SubmitBar/…                            │
│  ↑ 只订阅、只展示，不拥有流的生命周期                              │
├────────────────────────────────────────────────────────────────┤
│ L1 会话常驻层  chatStreamStore.ts（模块级单例，组件树碰不到）       │
│  会话表 Map（ensureSession/evictSession/destroySession）         │
│  commit() 唯一写入口 + bump() 快照通知 + terminalAt/TTL 驱逐      │
│  模块级 transport：sendStreamRequest/resumeStreamRequest/         │
│  scheduleReconnect/handleTransportError                          │
├────────────────────────────────────────────────────────────────┤
│ L2 备份层  chatStreamPersistence.ts（sessionStorage）            │
│  save/load/remove/draft：崩溃兜底 + 断点续传数据源                │
├────────────────────────────────────────────────────────────────┤
│ L0 后端  FastAPI :8000  /chat/stream?after_seq=（断点续传）       │
└────────────────────────────────────────────────────────────────┘
```

**分层的本质**：生命周期归属决定分层归属。
- L1 数据的生命周期 = 页面会话周期（模块加载起，直至 `evictSession`/`destroySession`/标签页关闭）；
- L3 的生命周期 = 组件挂载周期（随路由/刷新随时重建）；
- **L3 可任意销毁，L1 不受影响**——这就是"会话常驻"的落地方式。

### 1.2 各层职责与关键实现

| 层 | 文件（当前工作区） | 职责 | 关键实现 |
|----|--------------------|------|---------|
| L3 渲染/订阅 | `pages/ChatPage.tsx`、`features/chat/hooks/*`、`features/chat/components/*` | 编排、状态协调、UI 渲染 | ChatPage:76 注释"流状态已常驻 Store，本组件只订阅"；`useChatStreamSession`（render 期只读 ref 视图，**绝不 ensureSession 造 '' 假会话**） |
| L1 会话常驻 | `streams/chatStreamStore.ts`（单例 `:465`）、`streams/chatStreamTransport.ts` | 流状态持有、传输调度、重连/退避、终态驱逐 | `commit()` 唯一写入口（含终态 TTL 排期）、`bump()` 快照对比+通知、会话容量上界 MAX_SESSIONS=32 |
| L2 备份 | `streams/chatStreamPersistence.ts` | 崩溃兜底、跨刷新恢复 | 版本化快照 `save/load/remove`；`isAnchorGroupIntact` 校验锚点完整性 |
| L0 后端 | FastAPI `:8000` | SSE 推送、断点续传、DB 落库 | `GET /chat/stream?after_seq=` |

### 1.3 会话常驻核心机制

1. **模块级单例**（`chatStreamStore.ts:465`）：store 对象在模块加载时创建，不在任何组件/Context 内，React 卸载、路由切换、刷新都不会销毁它。
2. **commit() 唯一写入口**（`:242-260`）：所有状态写入必经 `commit`；终态跃迁在此**单点捕获**并排期 `scheduleTerminalEvictOf`（TTL 驱逐），离开终态则作废 `terminalAt` 维持不变式；纯资源字段（abortController/定时器）不进快照，避免无谓重渲染。
3. **bump() 快照通知**（`:264-283`）：浅比较 SNAPSHOT_KEYS，无变化不 revision；有变化递增 revision 并通知订阅者。
4. **L2 备份**：`schedulePersist`（防抖/节流）将状态快照写 sessionStorage；续传路径用 `after_seq` 断点，A1 指纹去重 + sseParser seq 守卫防重放。
5. **渲染端只订阅**：组件经 `useChatStreamSession` 获取会话只读引用，`getExecutionStepsRef` 等已去除 render 期造会话副作用（[79] D2，2026-09-30 根治"render 期 ensureSession('') 泄漏"）。

### 1.4 层间数据流与依赖方向

```
触发: L3 handleSend → L1 store.sendMessage → L0 SSE
帧推送: L0 events → L1 parseEvent/transport 写入 store(commit) → bump → L3 订阅者重渲染
恢复: L3 初始化 → L1 resume(读 L2 备份) → L0 after_seq 续传
持久化: L1 commit → schedulePersist → L2 sessionStorage
驱逐: L1 终态 → terminalAt → TTL → evictSession（同时清 L2 备份）
```

- 依赖方向为 **L3 → L1 → L2 → L0**，单向向下，L1 不感知 L3（通过 listener 回调解耦）。
- 该单向依赖是"组件随便销毁、常驻层不受损"的架构保证。

## 二、会话常驻留层的能力完备性分析、可靠性分析

### 2.1 能力完备性分析

以 [79] 会话流常驻架构要求为基准，对 L1（含 L2 配合）能力逐项核对：

| 能力要求 | 现状 | 结论 |
|---------|------|------|
| 切路由任务不中断 | store 为模块级单例，路由切换不卸载 | ✅ 具备 |
| 页面刷新数据不丢 | L2 sessionStorage 快照 + `after_seq` 断点续传 | ✅ 具备 |
| 状态有唯一写入口 | `commit()` 单点承接终态/排期/persist | ✅ 具备 |
| 订阅通知最小化 | `bump()` 浅比较 + 纯资源字段不进快照 | ✅ 具备 |
| 会话容量有界 | MAX_SESSIONS=32；`evictOverflow`（store:429-463）LRU + 硬上限兜底主动驱逐已实现（2026-09-30 复核确认，见 2.2.2.2 v1.1 改判；原「无主动驱逐预案」判据过时，S4 关闭） | ✅ 具备 |
| 终态定时回收 | terminalAt + TTL（TERMINAL_TTL_MS）驱逐 | ✅ 具备 |
| 异常备份不驻留 | invalid 备份置 idle、可复活 | ⚠️ 部分（缺 releasedAt/terminalAt，见 S1） |
| 防双发/防双连接 | `isProcessing`/`pumpActive`/`resumeInFlight` 三守卫 + 'recovering' | ⚠️ 部分（守卫存在，但存在穿透窗口，见 2.2 缺陷 T1/H17） |
| 传输重连/退避 | scheduleReconnect + reconnectStatus | ⚠️ 部分（退避窗口守卫穿透，见 T1） |
| 空会话不落库 | sendMessage/resume/stop 均应拒绝空 sessionId | ⚠️ 部分缺失（sendMessage 无空串守卫，见 H13） |

**能力完备性小结**：常驻能力的"骨架"（单例 + commit + 驱逐 + 备份）完备；"细节"（空会话拒绝、容量压力、守卫穿透、备份生命周期）存在缺口。

### 2.2 可靠性分析

#### 2.2.1 可靠性设计要点（已具备）

- **三守卫单飞**：`pumpActive`/`resumeInFlight`/`isProcessing` 防并发 pump / 防双发；
- **终态 TTL 幂等重排**：commit 内单点捕获终态，到点 `evictSession` 见非终态自会拒收，幂等安全；
- **渲染端零副作用**：render 期不 create 会话，杜绝幽灵会话（D2 已根治）；
- **重放防护**：A1 指纹去重 + sseParser `after_seq` 断点守卫，即"重连重复帧"不产生重复渲染副作用；
- **404 语义**：loadHistoryMessages 404→null、其余错误冒泡（2026-09-30 修复）。

#### 2.2.2 可靠性缺陷（复核后实际有效 8 条）

三遍复核（①代码实证→②反证→③证实方法，2026-09-30 小欧）后关闭 6 条（T5/T6/T8/T9/S4/T2），实际有效缺陷：

| 编号 | 缺陷 |
|------|------|
| T1 | resume 退避窗口守卫穿透，旧备份覆盖在飞状态致序号倒退（已修复，v1.2） |
| H13 | sendMessage 空串无守卫，可建 '' 鬼会话（已修复，v1.2） |
| H17 | 二次发送返回 'recovering' 零消费，静默无提示 |
| S1 | 失效备份置 idle 仅靠硬上限兜底删除 |
| S2 | 宽限 setTimeout 无句柄，重复退订叠加定时器 |
| T3 | pump 单飞早退，旧 pump 存续靠守卫兜底 |
| T4 | 轮询可重入，靠死径单次调用约束 |
| T7 | error 置 failed 后同批 final 丢 complete（极低概率） |

#### 2.2.3 可靠性结论

- **主干可靠**：单例生命周期、commit 单点写入、终态 TTL、备份与续传、A1+seq 防重放，构成的常驻主路径可信；
- **薄弱点集中在"并发/边界交互"**：v1.1 三遍复核后，核心风险收敛为 **T1 重连退避窗口穿透（resume 恢复覆盖在飞状态→序号倒退）**、**H13 sendMessage 空串守卫缺失**（'' 鬼会话）、**H17 'recovering' 返回值静默弃置** 三项；其中 T1/H13 实际成立，H17 无 UI 触发路径——均属"调用方传参/守卫对齐"层面的不闭环，级别 LOW；
- **无结构性缺陷**：未发现会直接丢失常驻数据或破坏 commit 不变式的问题；缺陷多为中低影响、可单点整改。v1.1 复核共关闭 6 条（T5/T6/T8/T9/S4/T2），降级 6 条，修正 2 条。
