## 一、问题总结

### 1.1 问题现象

2026-09-07 17:31:52，会话 `134656ce-3569-4dbb-bcc0-163c83984de0` 发起任务 `task-91713b24e59348cb9af41397ac38e29e`（请求整理 Python/React/Go 学习资源）。17:33:08 模型输出行动 step=2（`searchweb` 并行 3 路），17:36:39 任务以 `end_type=cancelled` 收尾，**用户全程未点击前端"中断"按钮**。

### 1.2 用户疑问（北京老陈）

1. 没有点击前端"中断"按钮，为何任务显示为已取消（cancelled）？
2. 除了用户手动中断，还有哪些情况会产生 `cancelled` 终态？

### 1.3 根因一句话总结

本次 `end_type=cancelled` 的直接触发源是**前端**：SSE 连接中断 → 重连 3 次全失败 → 前端按 2026-07-12 既定策略自动调用取消接口（useSSE.ts:169）→ 后端忠实执行取消防令直至终态。

但深入追查发现更本质的成因为**前后端↔LLM 超时机制不对齐**：tool_call 参数流式期间后端不向 SSE 产出任何事件（流结束后一次性 yield），前端在 60s 内收不到任何字节即按空闲判死，而此时后端其实仍在正常接收 LLM 数据（150s 空闲 + 500s 硬截断内不判死）。这比"网络断连"更贴合现象，是"假断连"的根因。

## 三、前端侧情况分析

### 3.1 空闲判定机制（useSSE.ts）

- `IDLE_TIMEOUT = 60000`（:360）：60 秒无数据判定为断开。
- **判定依据是"字节到达"而非"业务事件"**：每次 `await reader.read()` 前重置 `lastDataTimeRef.current = Date.now()`（:659）；判定看 `timeSinceLastData = Date.now() - lastDataTimeRef.current`（:648）。
- **推论**：只要 `reader.read()` 返回任何字节（含 SSE 注释行 `: ping`、空 frame），计时即被刷新，60s 判定永不触发——这是心跳方案可行的基础。

### 3.2 重连机制（useSSE.ts）

- `reconnectConfig = { enabled: true, maxAttempts: 3, baseDelay: 1000, maxDelay: 10000 }`（:327-332）。
- 重连退避采用 Full Jitter 指数退避（:252-263）。

### 3.3 自动取消触发（useSSE.ts:156-170）

```ts
if (!canRetry) {
  console.error(`[SSE] 超过最大重试次数(${reconnectConfig.maxAttempts})，停止重连`);
  // 【北京老陈 2026-07-12 小欧】重连 N 次全失败 → 才置为取消（不武断算取消）
  if (serverTaskId) {
    console.warn(`[SSE] 重连 ${reconnectConfig.maxAttempts} 次均失败，发起取消 task=${serverTaskId}`);
    taskControlApi.cancel(serverTaskId).catch(() => {});
  }
}
```

### 3.4 前端仅有的两处取消端点调用

| 位置 | 触发方式 | 说明 |
|---|---|---|
| `useChatTaskControl.ts:170` | 用户点击中断按钮 `handleCancel` | 人工触发 |
| `useSSE.ts:165-170` | `!canRetry` 即重连次数达 `maxAttempts=3` 后 | **自动触发，无人为点击** |

### 3.5 前端侧问题定性

自动取消行为本身是 2026-07-12 北京老陈定案的既定策略（"重连 N 次全失败 → 才置为取消，不武断算取消"），代码实现与该定案一致，本次属于该策略的正常生效，**非前端故障**。但该策略在 `after_seq` 续传机制完善后应降级为兜底（见 §六 6.3/6.6）。

### 4.2 后端↔LLM 超时机制（httpx 流式）

| 参数 | 值 | 位置 |
|---|---|---|
| 空闲超时（两字节间隙） | `DEFAULT_READ_TIMEOUT=150` 起，每次重试 +20s（effective_timeout=timeout+(retry+1)*20） | constants.py:80；base_service.py:257 |
| 总时长上限 | `STREAM_TOTAL_TIMEOUT=500` 硬截断，到点截断已收数据，**不判死、不重连** | constants.py:89；base_service.py:264/285-288 |

**关键澄清**：
- 后端↔LLM 并无可用的 "30秒/60秒" 空闲判死：`IdleTimeoutIterator`/`IdleTimeoutError`（app/utils/idle_timeout.py）全工程**零调用点**，仅 error_classifier.py:128 有 isinstance 判定；error_classifier.py:117"AI模型30秒内未返回任何内容"为**描述性文案，实际不生效**。
- 后端↔LLM 在总时长 500s 内基本"不超时持续连接"：只要 LLM 每两字节间隔 <150s，连接一直维持；500s 到也只是截断（保留已收数据继续），不判断开。故"一直连直到取得有效数据"在 500s 内成立。

### 4.3 content 与 tool_call 的转发时机差异（核心）

`base_service.request_stream` 逐 chunk 处理，两条转发路径**时机不同**：
- **文本 content（thought/正文）**：`_parse_sse_data` 产 chunk 后**立即** `yield chunk`（:334-336），经 llm_call.py:117 `yield chunk` 直透 → 前端立刻收到 SSE chunk。**只要 LLM 持续输出 content，前端 SSE 就有事件，不触发 60s 空闲超时**。
- **tool_call 参数**：**流结束后一次性 yield**（:338 注释"流结束后，如有聚合的tool_calls，原生结构一次性yield"、:342、:389），**流式期间不 yield 任何 content**。llm_call.py 只在 `chunk.content` 有值时 yield（:109-117），tool_call delta 期间无 content → **前端一个 SSE 事件都收不到**。

### 4.4 后端侧 cancelled 的其他路径

- E（`max_steps<=0`）、F（循环结束非终态兜底）、G（orchestrator 异常 BUG-32）为后端配置/状态/异常产生的 cancelled，属正常防护或后端缺陷处理，与本案例（B 路径）性质不同。

### 4.5 后端侧问题定性

后端无功能 bug：取消链（置标志→打断流→终态 CANCELLED→不误判 failed）在 2026-09-07 病根修复后语义正确。**但存在三处协同短板，构成"用户感知层面的原因在后端也有份"**（详见 §五 5.2-5.4）。

## 五、前后端协同缺口分析

### 5.1 超时不对齐（假断连，本案例深层根因）

**根因链条**：
1. LLM 进入 tool_call 轮次（如 searchweb 并行/长参数），content 为空、只剩 tool_call delta 持续到达。
2. base_service 继续收（read timeout 因字节不断而续命，500s 内不判死），但**不 yield**；等流结束后才一次性 yield tool_calls。
3. 此期间前端 SSE **零事件**。若 tool 参数生成 + 后续处理累计 >60s（100s/200s 完全可能），前端 `IDLE_TIMEOUT=60000` 判无数据 → 断开 → 重连 3 次失败 → **自动取消**。
4. 而后端其实完全正常：一直在收，500s 内收全 tool_call → 处理 → 出结果，只是这 100-200s 里前端早已超时取消。

**结论**：前端 60s 无事件时武断自杀，而后端能正确等到完整数据——比"网络断连"更贴合本案例成因。

### 5.2 断连语义不一致（体验缺口）

后端在客户端断开时明确"agent 后台继续"（stream_orchestrator.py:398-401），工具副作用会继续执行；而前端在重连耗尽后判定整个任务取消。于是出现"任务已被取消，但搜索工具副作用已经发生且结果不可回传"的矛盾体验。

### 5.3 取消文案误导排查

后端日志与终态文案一律使用"用户取消"字样（`handle_answer.py:107` 输出"用户取消"、`_cancel_final_dict` content="任务已被取消"），未区分"用户主动取消"与"连接中断自动取消"，对排查者产生误导（首轮排查即被此字样带偏）。

### 5.4 取消生效有约 13 秒延迟

17:36:26 置取消标志 → 17:36:39 打断流，约 13 秒。LLM 取消采用"循环/块粒度"检测（react_loop.py:136-149 注释方案 B 的已知权衡），非流式热路径逐 chunk 即时中断，属设计取舍而非缺陷。

## 六、解决方案汇总

### 6.1 方案分层总览

| 层 | 方案 | 侧 | 改动量 | 性质 |
|---|---|---|---|---|
| 第一层（预防） | SSE keep-alive 心跳 | 后端 | 1 行 yield | 防"假断连"，前端零改动 |
| 第二层（主策略） | 轮询观察模式 | 前端 | 中 | 重连失败后不再自动取消 |
| 第三层（正道） | after_seq 续传 | 前后端 | 小（复用现有） | 断连后补发漏掉事件 |
| 第四层（兜底） | 后端断连超时保护 | 后端 | 中 | 轮询/续传也失效时兜底 |
| 配套 | 取消来源区分 | 前后端 | 中 | 落库/文案/日志区分来源 |

### 6.2 方案一：SSE keep-alive 心跳（后端，防假断连）

> 北京老陈建议：tool 参数流式期间后端活着却一个事件都不发，应给前端"我还活着"的回应。

**可行性实证**：前端空闲判定基于字节到达（useSSE.ts:659），只要 `reader.read()` 返回任何字节即刷新计时；而 `processSSEData` 首行判断 `!trimmedLine || !startsWith('data: ')` → 直接 return（sseParser.ts:112-115），SSE 注释行 `: ping` 以冒号开头不命中 `data: ` 前缀 → **直接忽略**，不产生 JSON 解析、不干扰 seq/step/业务状态。

**实施点**：`stream_orchestrator.py:441` `stream_reader` 的 `cond.wait(timeout=60.0)` 超时处，超时即代表"60s 内无业务事件（可能正处于 tool 参数流式）"：

```python
try:
    await asyncio.wait_for(buffer.cond.wait(), timeout=60.0)
except asyncio.TimeoutError:
    # SSE keep-alive 心跳：60s 内无业务事件（如 tool 参数流式期间）向前端发注释行，
    # 刷新前端 IDLE_TIMEOUT=60000 空闲计时，防"后端活着却被判死自动取消"（本案例根因）。
    # 前端 processSSEData 对 `:` 注释行直接 return（sseParser.ts:112-115），零副作用 — 小欧 2026-09-08
    logger.debug(f"[SSE] cond.wait 60s超时, 发心跳保活后重检done: task_id={task_id}")
    yield ": ping"   # SSE 注释行心跳，前端不计为业务事件但刷新空闲计时
    if buffer.done.is_set():
        return
    continue
```

**效果与取舍**：

| 项 | 说明 |
|---|---|
| tool 流式期间 | 前端零业务事件，但后端每 60s 一次 `: ping` → 前端 `lastDataTimeRef` 刷新 → **不判死** |
| 心跳副作用 | `: ping` 不落入 `processSSEData` 业务解析（sseParser.ts:113 直接 return），**不影响 seq/step/任何状态** |
| 前端改动 | **零**（纯后端一行 yield） |
| 周期选择 | 60s 与 `cond.wait` 天然对齐、改动最小；若求更稳可缩至 30s（< 前端 60s 一半） |
| 与轮询/续传关系 | 心跳是**实时连接层的防线**（防断判死）；轮询/续传是**断连后的兜底**，两层互补：有心跳则前端根本不判断连，断连兜底几乎用不上 |

**结论**：心跳把"后端↔LLM 正常工作但长期无业务事件（tool 流式）"与"前端↔后端真正断连"区分开。真断连时心跳自然停发，前端仍按 60s 判死走重连/兜底。

### 6.3 方案二：轮询观察模式（前端，主策略）

重连 3 次 SSE 失败后，**不调 cancel**，改为：

1. 每隔 5-10 秒轮询一次 `GET /chat/history/{sessionId}/{serverTaskId}` 查任务状态。
2. 任务仍在跑（状态=executing）→ 前端保持"执行中"提示，显示"连接已断，等待重连或查看结果"。
3. 任务已终态（completed/failed/cancelled）→ 拉取结果，正常展示。
4. 轮询超过一定次数（建议 30 次，约 5 分钟）任务仍无变化 → 提示用户"任务可能已终止，是否手动刷新"。

**优点**：`after_seq` 机制自然生效；用户不会看到误取消；任务有自然终止出口（后端自身完成/失败/异常退出后 `running_tasks` 清理）。

### 6.4 方案三：after_seq 续传（前后端，正道）

`stream_orchestrator.py:417-446` 的 `after_seq` 续传已存在：
- 客户端断连后，后端继续产出事件（seq 递增）。
- 客户端重连或轮询时传 `after_seq`，后端补发漏掉的事件。

建议在 60 秒超时后，前端不立即取消，而是尝试一次 `after_seq` 拉取（如果还有 `serverTaskId`）：
- 拉取成功 → 展示结果，不再需要重连 SSE。
- 拉取失败（404/任务已清理）→ 才兜底提示"任务已终止"。

### 6.5 方案四：后端断连超时保护（兜底）

在 `task_runtime.py` 的取消链里，加一个"断连超时"来源标记，与用户主动取消区分：

> 修改要求（北京老陈 2026-09-08）：不同的 cancel 必须给**准确的取消原因说明**，让用户/排查者在终态文案、日志、落库中获知"为什么取消"。

| 编号 | 路径 | source 值 | 终态提示文案（用户可见） | 说明 |
|---|---|---|---|---|

| B | SSE 断连 + 重连耗尽自动取消 | `client_disconnect_timeout` | "连接中断多次重连失败，任务已自动取消" | 本案例路径，不再写"用户取消" |
| C | 流式中途检出取消标志（在飞 LLM 流被断） | 继承 A/B 的 source | 继承 A/B 对应文案 | 被动执行，来源取置于 A/B 的原值 |
| D | 循环顶检出取消标志 | 继承 A/B 的 source | 继承 A/B 对应文案 | 被动执行，来源取置于 A/B 的原值 |

> - **C/D 不新增独立 source**，随取消标志携带 A/B 的原 source，保证"一个取消动作一个来源"（DRY/KISS），避免状态分裂。
> - **E/F/G 为后端自发终态**，前端从未发起取消，source 在 `agent_runner.py`/`react_loop.py` 各自终态生成处直接写入，随 `FinalStep` 一并落库。
> - **文案落库路径**：`task_runtime.py:64-84` 记录 source → `handle_answer.py:102-112` 依 source 生成终态 `FinalStep.response/error_message` → `agent_runner.py` end_type 推导携带 → 前端按 source 展示对应提示。
> - **兼容原则**：`source` 为可选参数，缺省时默认 `user_requested`，保证既有调用（如纯人工取消）行为不变；终态文案在 source 缺失时保持现有"任务已被取消"。

```python
async def stream_reader(buffer, task_id: str, after_seq: int = 0):
    """纯消费者：从事件缓冲按 seq 偏移读取并转发 SSE — 小欧 2026-07-12

    解决什么问题：SSE 只做"读缓冲→转发"，断线即返回、不碰 agent；
    重连复用同一函数（传 after_seq 续传），避免重复事件。 — 北京老陈 2026-07-12
    """
    offset = after_seq
    while True:
        async with buffer.cond:
            while offset < len(buffer.event_log):
                logger.debug(f"[SSE] seq={offset} task={task_id}")
                yield format_agent_sse(buffer.event_log[offset])
                offset += 1
            if offset < len(buffer.event_log):
                continue
            if buffer.done.is_set():
                return
            try:
                await asyncio.wait_for(buffer.cond.wait(), timeout=60.0)
            except asyncio.TimeoutError:
                logger.debug(f"[SSE] stream_reader cond.wait 60s超时, 重检done: task_id={task_id}")
                if buffer.done.is_set():
                    return
                continue
```
