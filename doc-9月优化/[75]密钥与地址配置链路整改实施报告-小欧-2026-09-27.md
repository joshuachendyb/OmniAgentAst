## 1.1 这份文档是什么

本文记录**设置界面 API Key 链路 + 服务访问鉴权**这批整改的**实施结果**。整改起因是三件事：

1. **密钥（api_key）** 存在"界面留空 = 不改"但后端理解成"清空"的语义错位，且有 3 套并存的写入路径

# 二、已实施能力

## 第1章 api_key（密钥）

密钥是本批改动的主战场。以下 7 件事都围绕它，且**刻意收口到唯一写入口**。

### 1.1 写入语义：三态（空 = 不修改）

| 传入 | 语义 | 行为 |
|------|------|------|
| 字段不出现 / `null` | 不修改 | 跳过，不写 |
| `""` / 纯空白 | **不修改**（对齐界面"留空=保持原值"） | 跳过，不写 |
| 非空字符串 | 设置 | `.strip()` 后写入 |
| `clear: true` | 清空 | 显式写 `""`（唯一允许清空的途径） |

**实现**：`model_service.update_provider_config`（`key_map` 循环内对 `api_key` 特殊处理）。

**为什么要三态**：界面上"我不想改这个字段"和"我要把它删掉"是两种相反意图，却都用空字符串表达。修复本质是**把两种意图拆开** —— 不修改用"不传/空串"，删除只能用 `clear: true`。

### 1.2 去空格（写入侧 + 消费侧双保险）

| 位置 | 做法 |
|------|------|
| 写入侧 | `update_provider_config` 写入前 `str(v).strip()` |
| 消费侧 | `client_sdk` 组 header 前用 `cleaned_key` |

**为什么消费侧也要**：已落盘的历史脏 key（YAML 里带空格）也能工作，不必要求用户手工重录。

### 1.3 clear 与设置值互斥

同时传 `api_key` + `clear: true` → **400 拒绝**，不静默丢弃任何一方。

原实现里 `clear` 分支排在赋值之后且**无条件覆盖** —— 用户刚输入的新 key 会被静默丢弃。界面流程触发不了（清空走独立按钮），但后端 API 是公开的，不能依赖前端不同时发。

### 1.4 通道收口：密钥写入只有一条路

**历史上曾有 3 条并存的写路径，且其中 2 条没有空串保护**：

| # | 历史路径 | 缺陷 | 现状 |
|---|---------|------|------|
| ① | `model_service.update_provider_config`（provider 通道） | 无空串保护 | **唯一权威**（本节 1.1 三态 + 1.2 strip + 1.3 互斥） |
| ② | 旧通道 `PUT /config` → `_update_api_keys` | 无空串保护，还会记"更新成功"日志 | **已删**（随端点收敛，见 [第3章](#第3章-模型配置)） |
| ③ | `settings` 通用通道 | 无 secret 分支，`{clear:true}` 会被当 dict 写进 YAML | **显式拒绝** secret 项 |

**为何必须收敛为一条**：同一把密钥有三个写入口，就意味着"空串会不会擦掉它"这个问题有三份独立实现 —— 修一份漏两份，是本批整改最核心的教训。

**收敛后的唯一写入口**：

| 密钥 | 唯一写入口 |
|------|-----------|
| `ai.{provider}.api_key` | `PUT /api/v1/providers/{name}`（`clear: true` 清空） |
| `security.access_token` | `POST /api/v1/auth/token` |

`settings` 通用通道遇到 `secret=True` 的项**直接报错**并指引进正确通道，不做隐式兜底。

**防半吊子**：`settings_registry` 在模块加载时自检 —— 注册了 `secret=True` 却没登记写通道 → **开发期即拒启**。避免"开了 secret 却没实现写保护"，那正是本项整改前第六章描述的潜伏坑（`{clear: true}` 会被当普通 dict 值写进 YAML 写坏结构）。

### 1.5 掩码显示：后端一次生成最终串

`mask_secret_value` 是全项目掩码**唯一权威**（`/settings`、`/models`、`/config` 共用），返回 `{configured, masked}` 两键恒定。

| 条件 | `masked` |
|------|----------|
| `len > 8` | `s[:4] + "****" + s[-4:]` |
| `4 < len <= 8` | `"****" + s[-4:]` |
| `len <= 4` | `"****"`（真实内容零泄漏） |
| 空 / 纯空白 | `{configured: False, masked: ""}` |

key 一律先去掉全部空白再判空与分档；非字符串按 `str()` 兜底。

**前端零掩码逻辑** —— 不判断档位、不拼星号、不取末 4 位，直接回显 `masked`。

**为什么收成两键**：旧三键 `{configured, prefix, suffix}` 把"怎么拼"交给前端（前端自己判档位、点数星号），规则在前后端各实现一遍，已漂移出真实 bug —— 前端靠 `prefix === '****'` 猜档位，遇到真实 key 前 4 位恰为 `****` 时拼错。旧两档还有 `len<=4` 全量回显、`len==8` 拼回全量明文两处泄漏，现三档一并消除。

### 1.6 明文查看

| 项 | 结果 |
|----|------|
| 端点 | `GET /api/v1/providers/{name}/api-key` |
| 返回 | `{provider, api_key: <明文>, configured}` |
| 审计日志 | 记 provider 名 + 来源 IP（读密钥属敏感操作） |
| env 接管时 | **一律拒绝返回明文**（env 优先消费，YAML 里那个不是生效值，给用户看是假象） |
| 交互 | 二次确认弹窗 → 显示明文 → **30 秒自动恢复打码**，明文不写 localStorage |

**明文接口的硬依赖是 [第4章](#第4章-访问鉴权) 鉴权** —— 无鉴权时局域网任何客户端可直接调走全部明文密钥。故两者同批上线。

### 1.7 连通性检测（测 key）

| 项 | 结果 |
|----|------|
| 端点 | `POST /api/v1/providers/{name}/test-connection`，**key 走 body** |
| 为何不用 GET query | GET 的 query 会进 uvicorn access log（服务器日志留下明文 key）并进浏览器历史 |
| 支持测未保存的 key | 用户正在输入框里新输 key 时是最自然的验证场景 |

**四档分类**（关键：不能一律提示"连接失败"，用户无法判断该改地址还是改 key）：

| 分类 | 触发 | 含义 |
|------|------|------|
| `ok` | 2xx | key 有效 |
| `key_invalid` | 401 / 403 | key 无效或无权限 |
| `endpoint_unsupported` | 404 / 405 / 501 | 该 provider 无 `/models` 端点 → **key 可能是对的，不得判其无效** |
| `network_error` | 超时 / 连接失败 / 其它状态码 | base_url 或网络问题，与 key 无关 |

## 第2章 URL（地址）

### 2.1 必填语义：空 = 错误状态

| 字段 | 留空语义 |
|------|----------|
| `api_key` | **不修改**（第1章，允许"先建后填"） |
| `base_url` | **错误**（本章，不允许"先建后填"） |

**两者方向相反是刻意的**：`api_key` 可以先建 provider 之后再填，URL 不行 —— 没地址根本无法调用。

### 2.2 四道把关

| 层 | 做法 |
|----|------|
| 前端 · 添加 Provider 弹窗 | `rules: required`，未填不允许提交 |
| 前端 · 回显 | URL 为空时输入框下方显示**红色警示**「⚠️ URL 为空，此 Provider 无法调用」 |
| 前端 · 保存 | 保存按钮 `disabled` |
| 后端 | `update_provider_config` 收到空 `base_url` → **400**；`add_provider` → **400**；`client_sdk` 构造时 URL 为空 → **400** |

### 2.3 删掉静默兜底

已删除 `_default_base_url()` 与 `_DEFAULT_URLS`。

**为什么删**（那套"默认地址"机制是半成品）：

| provider | 清空 URL 后的**旧**行为 | 是否静默 |
|----------|------------------------|---------|
| ollama | 变 `http://localhost:11434` | ⚠️ 远程 ollama 配的是 `http://192.168.x.x:11434`，清空后**打向本机** |
| deepseek / qwen | 变硬编码官方地址 | ⚠️ 可能绕过用户想走的中转，**直连官方计费** |
| 其余 | 得空串 → 请求失败 | ✅ 会报错 |

且硬编码只覆盖 3 家，其余得空串 —— 既不完整也未被实际触发。**把"留空"解释为"恢复默认"是一个假便利。**

现行为：URL 为空 → **构造即报错**，文案指向"到设置页填写完整地址"。

### 2.4 跨 provider 切换时不回落别人的地址

会话切到另一个 provider 时，`api_base` **不回落**到全局默认 provider 的地址；跨 provider 且该 provider 未配地址 → **400 报错**。

**同 provider 必须沿用本代地址** —— 实施中曾无条件删除回落，导致同 provider 内切换模型时 `api_base=None` → 抛 400「URL 为空」，**功能 100% 不可用**（实测复现，属"修 A 坏 B"）。现按"是否跨 provider"区分。

### 2.5 已知限制

原本就为空的历史配置（手改坏 / 依赖过 ollama 兜底），**前端不拦、保存不报错**。

**为什么**：若按"当前为空即一票否决"，这类老配置的用户将**无法修改该 provider 的任何其它字段**（如 timeout / label），属功能退化。代价是：这类配置要等真正调用报 400 时才会被用户发现。已扫现网配置，7 个 provider 全部非空。

## 第3章 模型配置

**本章讲什么**：设置界面"当前使用哪个模型"这个配置（`ai.model_ref` = 哪个服务商 + 哪个模型），以及它的写入口为什么是现在这样。

**现在是什么样**：模型配置**只能通过 `PUT /api/v1/config` 写，且这个端点只准写模型这一项**。原来它能写 7 类配置，已收敛为 1 类。

密钥写入路径的多路收敛属于 [1.4](#14-通道收口密钥写入只有一条路)，不在本章重复。

### 3.1 收敛结果

`PUT /api/v1/config` 从"7 字段通用写入口"收敛为**只写 `ai_model_ref`（切全局模型）**：

| 项 | 收敛前 | 收敛后 |
|----|--------|--------|
| `ConfigUpdate` 字段数 | 7 | 1 |
| `FIELD_HANDLERS` 项数 | 7 | 1 |
| 能力 | 切模型 / 改密钥 / 改主题语言 / 改 max_steps / **改安全** / 改项目根 | 仅切模型 |

**被删掉的 6 项能力，各自去了哪**：

| 被删字段 | 内容 | 迁往 | 本文哪章讲 |
|---------|------|------|-----------|
| `provider_api_keys` | 各 provider 的 API 密钥 | provider 通道 | [第1章](#第1章-api_key密钥) |
| **`security`** | **访问口令 + 免口令白名单** | registry `security.access_token` / `security.access_token_allowlist` | **[第4章](#第4章-访问鉴权)** |
| `theme` / `language` | 主题 / 语言 | registry `app.theme` / `app.language` | 不在本文范围 |
| `max_steps` | 最大轮数 | registry `agent.max_steps` | 不在本文范围 |
| `project_root` | 项目根 | registry `workspace.project_root` | 不在本文范围 |

> 上表"能力"行里的**「改安全」= `security` 段 = 访问口令 + 白名单**。本章只是**记下它被删并迁走**这件事，**口令与白名单本身的内容与规则全部在 [第4章](#第4章-访问鉴权)**。

其余 6 项能力已全部迁移至 `PUT /settings` 对应 registry 项，**不留第二条写路径**（避免同一配置两个写入口产生分叉）。

### 3.2 为什么保留而不是整条删除

原计划**整条删除**（核实"前端零调用"）。实施时实测发现第四条调用链：`configApi.switchCurrentModel`（顶栏与设置页「切换全局模型」的唯一写链）**仍在用**该端点。整条删 → 该功能 404 失效（功能退化）。故改为保留但收敛。

> 原核实只查了 `configApi.updateConfig` 是否零调用，**漏查了 `switchCurrentModel`**。

### 3.3 顺带封死"第二个能擦除密钥"的入口

`provider_api_keys` 字段与 `_update_api_keys` handler **已删除**，`ConfigUpdate` 不再接受该字段 → 手工 `curl` 传 `{"provider_api_keys": {"xxx": ""}}` 会被 **422 拒绝**（未知字段）。

这是端点收敛的**直接后果**：字段没了，漏洞自然消失，无需再单独补一层空串保护。

## 第4章 访问鉴权

**这是什么功能**：给服务设一个暗号（访问口令），知道暗号才能调接口。附带一批"谁能用、谁不能改、怎么防别人探测"的功能。

**为什么必须有**：服务要对局域网开放（多机共用，这是硬前提，改不了）。开放之后，局域网内任何人的浏览器、任何程序、任何网页都能直接调你的接口 —— 把所有 API Key 明文拿走、把密钥擦掉、看别人的聊天记录。**开放是合理的，没锁是问题。**

> ⚠️ 后端 15 项功能全部做完；**前端还有 8 处没做完**（见 [4.3](#43-实施现状对的与错的)）。

| 4 | **本机免口令** | 服务端那台电脑自己打开网页不用输暗号 |

#### 4.1.3 三条容易搞混的规则

| 规则 | 说明 |
|------|------|
| **白名单内等于没门** | 里面的人能读走**全部明文密钥**、能改能擦。只放最信任的机器 |
| **白名单 ≠ 管理员** | 白名单只是"免登录"，能进得来但**改不了口令** |
| **设口令只能本机** | 局域网其它机器改不了。否则别人抢先设一口令，管理员被锁在门外 |

#### 4.1.4 401 和 403 的区别

| 状态码 | 含义 | 什么时候出现 |
|--------|------|------------|
| **401** | "口令不对" | 口令输错、或没设口令时硬闯 |
| **403** | "你压根不该做这事" | 非本机要设口令、没设口令时白名单硬闯 |

**为什么 401 文案要统一**：如果"没设"和"输错"文案不同，别人拿 curl 试一下就知道你有没有设口令，等于告诉他该不该继续试。代价是真没设口令时用户也看到"口令无效"这种误导提示 —— 有意取舍，真相由可查询的状态页告诉用户。

#### 4.1.5 后端能力的边界

| 限制 | 说明 |
|------|------|
| **只有两档：有口令 / 没口令** | 拿到口令就是全部权限，不分管理员和普通用户 |
| **设口令得去服务端那台电脑** | 人在别的机器上就改不了（有意的安全设计） |
| **白名单写错直接跳过** | 宁可少放一条，不误放（不放行写错的条目） |
| **没有登录日志** | 只在失败时留一条警告，没有"谁什么时候登录成功"的台账 |
| **口令不会自动过期** | 改了立即生效、旧的立即作废，但要人工去改 |
| **一人管多台机器** | 每台要单独设一次，没有"设一次处处生效"的账号体系 |
| **已设口令时查状态要口令** | 状态接口只在未设口令时匿名可调 → 恰恰是最需要引导的远程用户拿不到引导信息（[4.4.1](#441-改法一后端-status-改成无条件匿名并补两个字段先做是其余改动的前提) 要修的就是这条） |

### 4.2 前端应该设计成什么样

#### 4.2.1 问题的根源：前端在猜一件它猜不到的事

后端判定"能不能进"依赖三件事：**来源是不是本机、在不在白名单、有没有设口令**。

前两件**只有后端知道** —— 浏览器的 JavaScript 拿不到自己的真实 IP（`request.client.host` 是后端视角）。所以：

> 只要后端的规则里有"本机 / 白名单"这类**按来源区分**的分支，前端就一定会出现"文案和行为对不上"的问题 —— 因为它**没有信息**去判断该显示什么。

现在前端是怎么做的：**不判断，一律显示"填一个口令即可进入并自动保存"**。于是远程用户填完提交，被后端 403 拒掉，界面说法和行为当场打架。

**还有一个更隐蔽的死结**（设计时差点掉进去）：

> 前端想"先问后端我这个来源该怎么处理"，就得调 `/auth/status`。
> 但**这个接口在已设口令时是要口令的** —— 而要口令的正是那批需要被引导的用户。
> 结果：**问不到 → 猜 → 猜错**。
>
> 所以"后端下发结论"这个方案，**必须先让状态接口无条件匿名**，否则只是把猜换了个地方猜。详见 [4.2.2](#422-正确设计后端把针对你这个人的结论告诉前端)。

#### 4.2.2 正确设计：后端把"针对你这个人"的结论告诉前端

`GET /auth/status` 不该只回一个全局状态，而该回**针对当前请求来源的结论**：

| 字段 | 含义 | 前端拿它做什么 | 必要性 |
|---|---|---|---|
| `access_token_configured` | 全局：服务端设过口令没 | 区分"登录"和"首次设置" | 已有 |
| `can_set_access_token` | **针对你**：你能不能设置口令 | 决定显示"填了即设置"还是"去服务端那台电脑设" | **刚需** —— 缺它就会出现"远程用户被提示填口令，填完必被 403" |
| `current_client_requires_auth` | **针对你**：你这次访问要不要口令 | 手动打开 `/login` 时，白名单/本机用户显示"你无需登录"而不是登录框 | **边角** —— 白名单/本机用户正常根本不会被 401 打来登录页，唯一场景是手动输网址 |

后端算这两个值**零成本** —— 判定链路上本来就算出了 `_local` / `_allow` / `expected`，只是没返回给前端。

> **诚实标注**：`current_client_requires_auth` 是自查后**降级**的字段。设计它时我以为它是刚需，复核后发现它只覆盖"手动访问登录页"这一个边角场景。若要贯彻 YAGNI，可只做前两个字段 —— 但那样白名单用户手动打开 `/login` 会看到登录框，试一次才发现不用输。**取舍：值得做，因为它零成本且能消除一类困惑。**

> ⚠️ **这个设计有个前置条件，不满足就整个跑不通**（这是设计时漏掉、复核才发现的关键点）：
>
> **`/auth/status` 必须无条件匿名可访问 —— 不管设没设口令、不管来源。**
>
> 现状是**只有关联条件 `not expected`（未设口令）才豁免**（`deps.py`）。于是：
>
> ```
> 远程非白名单用户（未带口令）
>    → 调 /auth/status
>    → 走 ⑦⑧ 比对口令 → 没带 → 401
>    → ❌ 拿不到"能不能设口令"的结论
>    → ❌ 状态机第一步就断了
> ```
>
> **恰恰是最需要引导的那批用户，恰恰拿不到引导信息** —— 这是自相矛盾。
>
> **改成匿名安全吗？安全。** 三条理由：
> 1. `access_token_configured`（设了没）**本来就公开** —— 现有实现已经在放行它，不构成新增泄露。
> 2. 新增的两个字段是**针对请求者自己的结论**（"你能不能设"），不是全局信息 —— 别人问不到你的答案。
> 3. 拿不到引导的代价（用户永远不知道自己该去哪设口令）是**真实的可用性损失**，而收益只是多暴露一个早就公开的布尔值。

#### 4.2.3 前端状态机（照此实现，不留第二种分支）

```
        进登录页 / 任意请求收到 401
                      │
                      ▼
   GET /auth/status（不带口令也行，匿名可调 ← 前置条件）
                      │
          ┌───────────┴───────────┐
          │                       │
   current_client_requires_auth  已有口令且本次验证通过
        = false                   （status 200 且已配置）
          │                       │
          ▼                       ▼
   ┌─────────┐             ┌─────────────┐
   │ 直接进  │             │ 进主界面     │
   │ 主页    │             └─────────────┘
   └─────────┘
  （仅"手动打开 /login"时
    才走这条；白名单/本机
    用户正常根本不会被
    401 打来登录页）

 current_client_requires_auth = true
        │
        ▼
  access_token_configured ?
        │
   ┌────┴────┐
   未配置     已配置
   │         │
   ▼         ▼
 can_set_access_token ?   ┌──────────────────┐
   │        │             │ 显示"请输入访问口令"│
  是       否            │  （输入框 + 进入按钮）│
   │        │             └──────────────────┘
   ▼        ▼
"填一个口令  "请联系管理员
 即可进入"   在服务端本机设置"
 （输入=设置）  （不给输入框，别让
                用户白填一次）
```

**三个设计要点**：

| 要点 | 说明 |
|---|---|
| **前端不做任何来源判断** | 白名单/本机/远程的区分全部由后端结论驱动，前端不再"猜"，也就不会猜错 |
| **探针用 `/auth/status`，不用业务接口** | 现在用 `GET /models` 验证口令 —— 那是业务接口，语义不对。`/auth/status` 本身就是"要口令才能过"的接口，带对口令 200 / 错 401，**天然就是探针**，不需要新增端点 |
| **不给输入框的场合就不给** | 明知设不了还让人填口令，是把后端的限制转嫁成用户的白填 |

#### 4.2.4 口令的存放与携带

| 环节 | 正确做法 |
|---|---|
| 存放 | 浏览器 `localStorage`，键 `omniagent_auth`（zustand persist 包络，保持 `state` 包裹与 `version`） |
| 携带 | `client.ts` **全局请求拦截器**统一加 `Authorization: Bearer` → 业务页面零改动 |
| 流式对话 | 单独把口令传进去 —— 浏览器自带 `EventSource` 不能自定义请求头 |
| 读取时机 | **每次请求现取**，不缓存不同步（改完口令立刻生效，不等刷新） |
| 写入失败 | **必须报错**。静默吞掉会导致"以为改成功了，下次请求还带旧口令 → 401 → 被踢回登录页" |

#### 4.2.5 401 与 403 的前端分工

| 状态码 | 前端该做什么 |
|---|---|
| **401** | 口令不对 → 清掉本地口令 → 跳登录页 |
| **401 但失败凭据 ≠ 当前凭据** | 说明是改口令前发出的旧请求，**不动当前状态**（否则"改口令成功了却被踢回登录页"） |
| **403** | **直接显示后端返回的 `detail` 原话**。403 的文案本身就是精确的引导（如「设置或更换访问口令只能在服务端本机进行」），前端自己编一句泛化的话只会把用户引到错误方向 |

### 4.3 实施现状：对的与错的

#### 4.3.1 做对了的（7 项，其中第 7 项打折）

| # | 做法 | 为什么对 |
|---|------|---------|
| 1 | 全局请求拦截器统一带口令 | 装一处，业务页面零改动，新增页面不会漏 |
| 2 | 401 自动跳登录页 | 符合"锁"的语义，不做就白屏 |
| 3 | 登录页探针请求带 `_skip401` | 不带的话：探针 401 → 拦截器跳登录页 → 重载 → 再 401 → **死循环，且页面提示永远不显示** |
| 4 | 改口令后 `setAccessToken` 同步 | 不同步则下一个请求带旧口令 → 401 → 白改 |
| 5 | 存储保留 zustand persist 包络 | 展平回写会丢 `state` 包裹与 `version`，且解析出非对象时静默失败 → 口令没存上 |
| 6 | 流式对话单独传口令 | `EventSource` 不能自定义头，只能走别的传法 |
| 7 | 登录页进页先查 `status` 再决定显示什么 | **方向对，但只在"未设口令"时真有效** —— 查的时候用户还没输口令（`LoginPage.tsx:45`），已设口令时这个查询自己就 401 了，等于白查。**故不算完全对**，见错 8 |

#### 4.3.2 做错了的（8 项）

| # | 错在哪 | 证据 | 后果 |
|---|--------|------|------|
| 1 | **后端没告诉前端"你能不能设口令"** | `auth_routes.py` 的 `get_token_status` 不返回该信息 | 远程用户无从判断，只能显示误导性文案 → **错 2** |
| 2 | 提示写「输入一个口令即可进入并**自动保存**」 | `LoginPage.tsx:133-136` | 与后端"仅限本机"**直接矛盾**。远程用户填完必被 403，界面说法和行为打架 |
| 3 | **拿业务接口 `/models` 当口令验证探针** | `LoginPage.tsx:75` `api.get('/models', VERIFY_REQ)` | 语义错（那是模型列表不是鉴权）；且验证结果与业务请求混在一起，无法区分"口令错"和"服务端异常" |
| 4 | 403 按 401 的类型和口径显示 | `LoginPage.tsx:88-91` | 403 语义是"你不能做这事"，不是"口令错了" |
| 5 | 403 的后端原话被丢弃 | `client.ts:175` 只处理 401，403 落到 `handler.ts:919` | 后端明明返回「只能在服务端本机进行」，用户只看到泛化文案 |
| 6 | `AUTH_403` 默认文案是「权限不足，请检查配置」 | `handler.ts:270` | 表达不了"只能在服务端本机设置"这个具体语义 |
| 7 | `setAccessToken` 静默吞掉写入失败 | `client.ts:141-151` 三层 `try/catch` | 用户以为改成功，下次请求带旧口令 → 401 → 被踢回登录页 |
| 8 | **登录页主动查 `status` 在已设口令时查不到** | `LoginPage.tsx:45` 查的时候用户还没输口令；后端豁免带 `not expected` | **最常见的场景（已设口令）下这个查询自己就 401** → 拿不到任何信息，"先查状态再显示"沦为空转。这是[死结](#422-正确设计后端把针对你这个人的结论告诉前端)的直接后果，改法见 [4.4.1](#441-改法一后端-status-改成无条件匿名并补两个字段先做是其余改动的前提) 第 1 条 |

#### 4.3.3 一个更大的结构问题

**现状是"前端猜 → 猜错 → 打补丁"**：

```
后端改了裁定（限定本机、401→403）
        ↓ 前端收不到通知
前端只能显示自己以为对的文案
        ↓ 用户按提示操作
后端 403，文案与预期不符
        ↓
前端加 try/catch / 加提示 / 加判断
        ↓
下次后端再改规则，前端又要再补一轮
```

**根治办法不是继续补前端，而是 4.2.2 的"后端下发结论"** —— 让前端不再猜。改完之后，后端规则变化前端自动跟随，不需要再打补丁。

### 4.4 错的怎么改

#### 4.4.1 改法一：后端 status 改成无条件匿名并补两个字段（**先做，是其余改动的前提**）

| # | 改什么 | 怎么做 | 为什么 |
|---|---|---|---|
| 1 | **豁免条件去掉 `not expected`** | 状态接口的豁免判断从"未设口令才放行"改为"**无条件放行**" | **不修这条，后面全白做** —— 见 [4.2.2](#422-正确设计后端把针对你这个人的结论告诉前端) 的死结：最需要引导的用户恰恰问不到 |
| 2 | 补 `can_set_access_token` | 取 `_is_trusted_localhost(_client_ip(request))` | 消除"远程用户被诱导填口令然后被 403"这个死循环 |
| 3 | 补 `current_client_requires_auth` | 复用鉴权链路的中间结果：非本机且不在白名单 | 手动打开登录页时不再给白名单用户显示登录框 |
| 4 | 删 `masked`/`config_key`/`env_name` | 零消费字段（YAGNI） | 凭空扩大接口契约 |

**实现要点**：
- 豁免放宽到无条件后，**必须确认返回内容里没有任何全局敏感信息**。逐个核对：`access_token_configured`（早就公开）、两个新字段（针对请求者自己）—— 都安全。`masked` 是**打码**值不敏感，但已无消费方，仍按第 4 项删掉。
- 两个新值在鉴权依赖里**已经算出来了**，应由 `deps` 提供取值函数，`auth_routes` 调它，**不要重新实现一遍**（DRY）
- 放宽后补一条守护测试：**未带口令 + 非白名单来源 + 已设口令 → `GET /auth/status` 仍返回 200**，把这条钉死，防止以后又被收紧回去

#### 4.4.2 改法二：登录页按状态机重写

| 现状 | 改成 |
|---|---|
| 先 `/models` 探针 | 先 `GET /auth/status`（自带口令），它返回 200 就说明口令有效，**不必再发第二个探针** |
| 只有一个 `notConfigured` 状态 | 三个分支：`requires_auth=false` → 直接进主页；未配置 → 首设引导；已配置 → 登录框 |
| 不管能不能设都显示输入框 | `can_set_access_token=false` 时**不给输入框**，只显示"请到服务端本机设置" |
| 文案写"输入即自动保存" | 按 `can_set_access_token` 分流两套文案 |

#### 4.4.3 改法三：403 走独立处理，保留后端原话

| 层 | 改法 |
|---|---|
| `client.ts` 响应拦截器 | 增加 403 分支：**不跳登录页、不清口令**，把 `detail` 原样交给调用方 |
| `LoginPage` | 捕获 403 后 `showMessage` 显示**后端 detail 原文**，不再拼泛化文案 |
| `handler.ts` | `AUTH_403` 的默认文案改为兜底（如「此操作不被允许，请按提示处理」），**只在后端没给文案时才用** |

#### 4.4.4 改法四：`setAccessToken` 不再静默

| 改法 |
|---|
| 三层 `try/catch` 收敛为一层；写入失败**抛错或返回布尔** |
| 调用方（`settings.api.ts::setToken`）接到失败要提示用户，不能当成功 |
| 顺带按 [4.4.5](#445-顺带清理三处规范违规) 提常量、简分支 |

#### 4.4.5 顺带清理三处规范违规

| 规范 | 现状 | 改法 |
|---|---|---|
| **DRY** | 键名 `'omniagent_auth'` 写死 7 处（`client.ts:90/106/116/124/136/146/199`） | 提一个 `AUTH_STORAGE_KEY` 常量 |
| **KISS-DIRECT** | `setAccessToken` 约 50 行、4 个分支，实际只是"写一个字符串" | 合并为必要分支；**"裸对象格式"（无 `state` 包裹）这一分支建议直接删** —— zustand persist 一直是带包裹的，那是过度设计 |
| **不许静默失败** | 保存失败被吞 | 见 4.4.4 |

#### 4.4.6 实施顺序

```
① 后端 status 补两个字段 + 删三个死字段   ← 前提
        ↓
② 登录页按状态机重写（探针换 /auth/status、三分支分流）
        ↓
③ client.ts 加 403 分支 + handler.ts 文案兜底
        ↓
④ setAccessToken 收敛分支 + 提常量 + 不静默
        ↓
⑤ 前端补守护测试：三个状态分支各一条、403 文案透传一条、写入失败一条
```

### 5.6 `handler.ts`（修正两处文案）

**改哪两点**，其中第 2 点是**本章新发现**、此前 4.3 未列出：

> 这个错误在 [4.3](#43-实施现状对的与错的) 里**没被列出**（当时只注意到 403 的文案问题），是本章逐行读真实代码时才发现的。
