## 二、前端数据链路还原（action 到达 → 齿轮动画 → 结果渲染）

实时路径（逐环节已验证，均即时、无节流、无延迟）：

```
SSE action 事件
 -> sseParser.ts case action  setExecutionSteps + onStep      // 即时
 -> useChatStreaming.executionSteps 状态更新                  // 即时
 -> RightViewer.tsx  liveSteps={executionSteps}               // useChatPanels.tsx:237
 -> displaySteps = isCurrentLive ? liveSteps : historySteps   // RightViewer.tsx:266
 -> PipelineRenderer steps={splitSteps(displaySteps).business} streaming={isCurrentLive}  // RightViewer.tsx:286-288
 -> tool segment 立即生成                                     // PipelineRenderer.tsx:196-201
 -> ToolCallLine 齿轮动画条件                                 // ToolCallLine.tsx:230
```

关键门一：**齿轮动画条件**（ToolCallLine.tsx:230）

```ts
{!hasResult && tools.length > 0 && !interrupted && !replay && (
  <span className="tool-waiting-cursor" ...>  {/* 齿轮/loader SVG */}
)}
// we 2026-09-08 小欧：replay 由父级传入
```

其中 `replay`（PipelineRenderer.tsx:393 一带）：
```ts
replay={!streaming}
```
> 即 `streaming(false 历史回放)` → `replay=true` → **停齿轮**；`streaming(true 实时)` → `replay=false` → **显示齿轮**。正常实时任务应转齿轮。

关键门二：**实时判定 isCurrentLive**（RightViewer.tsx:125-129）

```ts
const isCurrentLive =
  activeTaskId != null &&
  activeTaskId === serverTaskId &&
  !_hasFinal &&
  (receiving || liveBadge === 'running' || liveBadge === 'paused');
```
> `isCurrentLive=true` 才走 `liveSteps`（实时实时）并传 `streaming=true`（齿轮转）。**只要它翻 false**：
> - `streaming={false}` → 全流水线 `replay=true` → **齿轮停转**；
> - `displaySteps = historySteps`（RightViewer.tsx:266）→ 实时步骤静默压进 `liveSteps` 但 `historySteps` 不长（任务未落库/未完成），右栏切空历史/空态；
> - REST effect 同时触发（RightViewer.tsx:219-230），但任务执行中拉回的步骤不全，气泡此消彼长 = **画面"冻结"**；
> - SSE 恢复 → `isCurrentLive` 转 true → `displaySteps` 切回 `liveSteps`，含缓冲的全部步骤**一次性渲染 = "整批显示"**。

**结论：`isCurrentLive` 在执行间隙翻 false = 症状的直接开关。**

## 三、isCurrentLive 为何会翻 false（根因定位）

`isCurrentLive` 的 OR 三态 `(receiving || running || paused)`，任一为真即稳。翻 false 只剩唯一路径：**`receiving=false` 且 `liveBadge` 落回 `idle`**。逐层证死：

### 3.1 badge 每次重算从 idle 起步

useTaskInfo.ts:124
```ts
let badge: TaskBadge = 'idle';
```

### 3.2 thought/action/observation 分支"只救 paused/failed，不救 idle"

useTaskInfo.ts:179-187
```ts
case 'thought':
case 'action':
case 'observation':
  if (badge === 'paused') badge = 'running';
  if (badge === 'failed') { badge = 'running'; _badgeRecovered = true; }
  break;
```
> 任务执行中的业务 step 已存在 `liveSteps` 里，但本分支**从不把 idle 顶成 running**——业务 step 证明执行中这一语义没有落到代码。

### 3.3 startinfo 门每次重算都被 receiving 压回 idle

useTaskInfo.ts:207-208
```ts
if (hasStartInfo && badge === 'idle')
  badge = receiving ? 'running' : 'idle';
```
> 本门每次重算都执行。只要 `badge` 此刻为 idle（含 3.2 从未被顶起的情况）且 `receiving=false`，**badge 恒被压回 idle**，无视 `liveSteps` 里已有多少 thought/action/observation。

### 3.4 receiving=false 的触发源（SSE 空闲断连/请求错误）

useSSE.ts：
- :631 重连路径 `disconnect(..., setReceiving=false)` —— 重连**不落 false**；
- :853 / :879 真错误路径 `setIsReceiving(false)` —— **此路径 receiving=false**；
- :724-745 空闲超时（`IDLE_TIMEOUT`，历史档 60s）→ `reconnect()`；若连接已僵尸，错误分类走 :862 `handleSSEError` → :879 `setIsReceiving(false)`。

> 即：任务执行中的 SSE 静默窗（工具执行 10-60s、网络抖动、proxy 断开）一旦触发真错误/重连，`receiving` 即 false。

### 3.5 三环节串联 = 翻车路径

```
工具执行静默窗 → SSE 真 error/重连 → receiving=false
 → useTaskInfo 重算: badge 从 idle 起步(§3.1) → 业务 step 分支不顶起(§3.2)
 → startinfo 门按 receiving 压回 idle(§3.3)
 → liveBadge='idle'
 → isCurrentLive = ... && (false || false || false) = false   // RightViewer.tsx:129
 → streaming=false(停齿轮) + displaySteps=historySteps(空/不全) → UI 冻结
 → SSE 恢复 receiving=true → badge='running' → isCurrentLive=true
 → displaySteps=liveSteps(含缓冲全体) → 整批显示(齿轮全程未转)
```

## 四、为何是"修复被击穿"（历史对照）

RightViewer.tsx 编辑历史 :37-38（2026-09-02 小欧）明确根治过同扇窗：

> 「根治纯网络空闲断连(无paused)60s重连间隙badge=idle致waiting消失的第4窗口」，修复手段：`isCurrentLive` 由单 `receiving` 改三态并集 `(receiving || running || paused)`。

**击穿点**：当时只改了 `isCurrentLive` 的门，未封 `liveBadge` 的派生源。三个 OR 态里：
- `receiving` 会被真错误置 false（useSSE.ts:853/879）；
- `paused` 仅在步骤流含 paused 事件时成立；
- 于是唯一稳定兜底 = `running`，而 `running` 恰恰在 §3.2/§3.3 的挟持下随 `receiving=false` 一起落 `idle`——**三态并集被同时清零**，第二扇门形同虚设。

即：2026-09-02 的修复封了门，没封源（badge 派生），13:27 症状是该历史缺陷在真断连窗口下的复发。

## 五、修复方案（KISS，待批准）

### 5.1 目标语义

> 业务 step（thought/action/observation）到达 = 任务执行中的**铁证**，优先级高于连接状态。任务已开始且有业务 step、且未见终态 final 时，badge 不得因 `receiving=false` 落回 idle。

### 5.2 改法（单文件 useTaskInfo.ts，一行 + 同步注释，无第二处改动）

useTaskInfo.ts:179-187 `thought/action/observation` 分支补齐 idle 恢复：

```ts
// 编辑历史: 2026-09-08 小欧 - 「前端UI静默10秒整批显示」修复(北京老陈 2026-09-08 批准实施, 文档:
//   doc-9月优化/前端UI静默10秒整批显示问题分析与修复方案-小欧-2026-09-08.md):
//   业务 step(thought/action/observation)到达即证任务执行中, 补 idle→running 恢复,
//   防 SSE receiving=false 窗内 startinfo 门(207-208)把 badge 压回 idle,
//   致 RightViewer.isCurrentLive 翻 false(停齿轮+切历史视图+整批回放)——三态并集修复(2026-09-02)被击穿根因 — 小欧-2026-09-08
case 'thought':
case 'action':
case 'observation':
  if (badge === 'idle') badge = 'running';
  if (badge === 'paused') badge = 'running';
  if (badge === 'failed') {
    badge = 'running';
    _badgeRecovered = true;
  }
  break;
```

### 5.3 三堂会审（合规 / 合理 / 关联逻辑）

合规：
- SRP：职责仍是"badge 派生"，本次只补一条证明路径，不动其它推导；
- DRY：与既有 `paused→running`/`failed→running` 恢复完全同型，不造新门，不重复逻辑；
- KISS：一行 + 注释，无中间层、无新配置。

合理：
- 逻辑直线：业务 step 到达 → running，比"连接状态证明执行中"更直接更真；
- 无副作用绕路，不引入新状态。

关联逻辑（重点验退）：
- **B33 语义**：`startinfo` 未到且无业务 step 时 badge 仍 `idle`（本分支不起作用），`startinfo` 到但无 step 仍按 `receiving` 决定——执行起点语义不变；
- **终态**：final 为步骤流末尾，case 'final' 覆盖 badge 为 completed/failed/cancelled，本分支在其前已执行完毕无覆盖权；`hasFailedFinal`（useTaskInfo.ts:77-79）单源兜底 failed 不变；
- **切历史任务**：`activeTaskId ≠ serverTaskId` 时 `isCurrentLive` 恒 false（RightViewer.tsx:126-128 硬前提），本改动不改该前提，历史任务跳动不受影响；
- **任务结束沿**：`_hasFinal`（RightViewer.tsx:120）已挡终态 live 卡位，badge 多立在 running 不会导致视图霸屏。

### 5.4 验收口径

修复后 13:27 同类场景期望行为：
1. action 到达即时渲染 ToolCallLine，齿轮（loader）**立即转**，全程不消失；
2. 工具执行静默窗（receiving=false）期间右栏仍显示 liveSteps（action 行 + 齿轮），**不切空历史、不冻结**；
3. SSE 恢复后 observation 到达，齿轮卸载、子行与结果按既有逻辑渲染，**无整批回放跳变**；
4. 全量回归：终态 / 切历史 / HITL 被拒停齿轮三路径无退化。

- 修复方案为单文件一行（useTaskInfo.ts:179-187 补 `idle→running`），已过三堂会审，**待北京老陈批准后落码**（批准后：改码 + 加编辑历史 + 前端 `npm run check`，不 tag）。
