# final三态字段验证与前端渲染契约方案

创建时间：2026-09-12 08:05:31
编写人：小欧

## 摘要

本文档是对 4C 改造（2026-09-06 commit `80bfec61f`）之后 SSE final 分支的 **字段准确性验证** 与 **前端渲染契约方案** 的定稿分析。

核心结论（均经代码实证）：
1. **第1步 publish 完整条时，成功/失败/取消三态的 final 字段全部正常**，无任何缺失或错误。
2. 右侧重复的真因不在后端字段构造，而在于 **前端 settledSteps 快照（实时流结束后）残留 completed final 的完整 response，与 chunk text 段二次渲染**。
3. 修复方向定为 **后端保持完整 publish（event_log 完整落库），前端按 outcome 消化渲染**——不开倒车、不污染落库、代码改动最小。

> 本文档仅为方案定稿分析，**尚未动任何代码**。实施细则待老陈指令后另行落盘实施。

## 一、4C 改造后 SSE final 数据流（4 步时序）

| 步骤 | 动作 | 位置 | 说明 |
|------|------|------|------|
| 1 | `emit_final_with_stats` → `await _publish(完整条)` | `react_step.py` 各发射点 → `agent_runner.py:261` | 带完整 response 进 event_log |
| 2 | `stream_reader` 独立协程按 seq 实时读 event_log → 原样转发 | `stream_orchestrator.py:450-467` | 仅过滤 thought（L447），对 final **零剥离** |
| 3 | `run_react_cycle` 返回 → agent_runner 扫描生成短信号 | `agent_runner.py:385` | 延后于实时转发 |
| 4 | finally 覆写 event_log 原位 = 短信号条 | `agent_runner.py:648` | **晚于实时转发，实时流已读走完整条** |

**关键推论**：4C 之后，实时 SSE 前端的 final 帧 = 第1步 publish 的完整条（短信号只服务于"覆写完成后"的重连/回放）。

## 二、第1步 publish 完整条——三态 final 字段构成验证（代码实证）

### 2.1 成功 completed

工厂：`step_emitter.py:81-86` `emit_completed_final(step, response, reasoning="")`

```python
FinalStep(
    step=step, response=response, outcome="completed", reasoning=reasoning,
)
```

| 字段 | 值 | 来源 |
|------|-----|------|
| response | 正文 | LLM 输出 或 return_direct 的工具结果 |
| reasoning | 推理文本 | 默认 "" |
| outcome | "completed" | 固定 |
| error_type / error_message / cancel_source | **均默认 ""** | 未传，FinalStep 默认值 |

### 2.2 失败 failed

工厂：`step_emitter.py:88-96` `emit_failed_final(step, response, error_type="", error_message="", reasoning="")`

```python
FinalStep(
    step=step, response=response, outcome="failed",
    error_type=error_type, error_message=error_message, reasoning=reasoning,

```

| 字段 | 值 | 来源 |
|------|-----|------|
| response | "任务执行失败" | 调用方固定传入 |
| error_type | 错误类型 | 调用方（如 agent_operation_error） |
| error_message | 错误信息 | 调用方，同时 `set_failed` 更新状态表 |
| reasoning | 错误信息 | 与 error_message 同源 |
| cancel_source | **默认 ""** | 未传，FinalStep 默认值 |

直接构造分支：`handle_answer.py:117-120`

```python

    step=step, response=cancel_terminal_text(cancel_source),
    outcome="cancelled", error_type="cancelled",
    error_message=content, cancel_source=cancel_source,

```

| 字段 | 值 | 来源 |
|------|-----|------|
| response | 取消文案 | `cancel_terminal_text(cancel_source)` |
| error_type | "cancelled" | 固定 |
| error_message | 取消原因文本 | 调用方 content |
| cancel_source | 取消来源 | 用户取消 / 超时 / 终止等 |

### 2.4 验证结论

**第1步三态字段全部正常。publish 完整条是正确的落库行为，event_log 是 DB 落库的唯一权威源，任何前置剥离都会污染历史回放。**

## 三、右侧重复现象根因（前端侧确认）

1. chunk 步骤（type=chunk）正文已渲染为 text 段。
2. final 到达 → `RightViewer.tsx:203-213` 快照 effect 将 executionStepsRef 全量固化到 settledSteps（**含 completed final 完整 response**）。
3. settledSteps 渲染时 `streaming=false` → `PipelineRenderer.tsx:360-363` 的 `if (streaming) return null` 不生效 → final 段 `ResponseStream`（L377-379）渲染 response 全文 → **与 text 段二次渲染**。

**只有实时流结束路径（settledSteps）重复**；历史回放（REST steps，无 chunk）不重复、且必须渲染 final.response。

## 四、前端三态渲染契约（方案）

### 4.1 原则

- **后端不动完全保留**：publish 完整条、event_log 完整落库、stream_reader 原样转发。
- **前端在快照处按 outcome 消化**：只处理渲染，不改 event_log、不动后端逻辑。

### 4.2 三态处理

| 形态 | 快照处理 | 前端渲染 |
|------|---------|---------|
| **completed** | `response` 清空（正文已由 chunk text 段承载） | 终态勾 + duration，不重复渲染正文 |
| **failed** | 不动（response / error_type / error_message / reasoning 保留） | 红字错误行 + 任务执行失败文案 |
| **cancelled** | 不动（response / cancel_source 保留） | 取消来源第二行（2026-09-11 已实现） |
| **历史回放** | 不经过快照 effect（steps 来自 REST，无 chunk） | final.response 照常渲染，正文不丢 |

### 4.3 落点

- 唯一改动点：`RightViewer.tsx:203-213` 快照 effect，落地对 `settledSteps` 中 `type=="final" && outcome=="completed"` 元素做浅拷贝并置空 response。
- 前端所需字段 `outcome / error_type / error_message / cancel_source / duration` **已全部解析**（`sseParser.ts:489-499`），无需新增解析。

### 4.4 后端第 3、4 步去留

- 若前端按 outcome 消化已兜底，后端第3步（agent_runner 扫描剥离短信号）与第4步（finally 覆写）**设计上可退役**，最终架构为：
  ```
  后端 publish 完整条 → event_log 落库完整 → stream_reader 原样转发 → 前端快照按 outcome 消化 → 渲染
  ```
- **去留决策待定**（需老陈指令），当前保持现状、不改动。
