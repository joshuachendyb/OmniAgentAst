## 二、前向链路审查：用户发送 → SSE流 → 前端渲染

### 2.1 链路主线（已核对调用链）
```
useChatSend.handleSend
  → POST /chat/stream (SSE, axios回调)
  → stream_orchestrator.chat_stream_endpoint
      → run_agent_in_background (⑨依赖peek装载start/无start任务/⑩stream_reader)
      → agent_runner → react_loop.run_react_cycle
  → SSE帧回推 (StreamBuffer.publish)
  → useSSE.ts (fetch reader) → sseParser.ts (18类事件分发)
  → useChatCallbacks.ts → useChatStreaming.ts (聚合) → useChatState → UI组件
```

### 2.2 start 契约（前后端逐字段核对一致 ✅）
| 字段 | 后端装配 (start_step.py:198-213) | 前端解析 (sseParser start) |
|------|------|------|
| type="start" step=0 | `_build_start_contract` 固定 step=0 | start 承载 |
| content=context_summary | `{session_id, context_link_mode, context_root_task_id, message_count, total_tokens}` | start.content |
| user_message | `_start_meta.user_input` 顶层 | 使用者直接取 |
| system_prompt | `agent._sys_prompt` | 透传 |
| task_id | `agent.task_id` (base_agent:59 权威) | 透传 |
| start_model | `llm_client.llm_model` (ModelRef单结构) | 前端派生 display_name |
| ai_message_id | react_loop.py:133 publish前装配 `agent._ai_message_id` | startinfo已合并，不再单独发 |

**结论**: S4/P4/P7 重构后 start 业务单一归属 start_step.py，前端 startinfo 合并入 start（4.4.3），契约双向闭合。

### 2.3 usage 帧（token 四层同构 —— 契约已核对 ✅）
后端发射（react_step.py:258-304）：
- 裁剪触发: `last_total_tokens` 供下轮增量裁剪
- 累积: `accumulated_usage[k] += int(v)` 逐次累加
- 任务级: `task_accumulated_tokens` 内存态逐轮累加
- 会话级: `_session_acc_base(基线,任务内恒定) + 任务累计`
- 链级: `_chain_acc_base(基线) + 任务累计`（计算派生，不落库）
- 发射: `MetaStep(type="usage")` 携带 `prompt/completion/total` + `llm_call_count_token` + `task/session/chain_accumulated_tokens`
- 运行中DB即时落库（每轮 update_task_accumulation/update_session_accumulation, 异常降级）

前端消费（useChainTokens.ts）：
- 实时源: `metaFrames.sessionAccumulated/chainAccumulated` 每次 SSE 跳动即覆盖 setState
- 静态源: 任务结束沿 + 会话加载补拉 `getChainTokens`
- 优先级: 实时 > 静态；`fetchedAnchorRef` 去重防重复拉取

**结论**: 顶栏 token 双源合并设计方案成立，无重复累加风险（agent_runner S2 已移除 update 防止翻倍）。实时帧有值即覆盖，会话切换复位（修复#42）。

## 三、反向链路审查：取消/暂停/授权 控制回路

### 3.1 取消链路
```
useChatTaskControl.handleCancel
  → taskControlApi.cancel (POST /chat/stream/cancel/{taskId}?session_id=)
  → 后端 task_state/task_runtime (写 cancel 标志, 方案B循环粒度)
  → react_loop.py 循环顶 check_cancelled(L183)
      → FinalStep(outcome="cancelled", cancel_source=...) + final_stats 双发
      → set_cancelled → break
  → SSE最终态 → 前端收 cancelled 终态
```
- 方案五(2026-09-08): 取消来源 A-G 全覆盖，`cancel_source` 落库+下发（user_requested/client_disconnect_timeout/config_limit/status_inconsistency/orchestrator_error）
- E/F 路径文案走 `cancel_terminal_text(source)` 单一源（DRY）
- 循环依赖治理: task_runtime 局部 import，task 包冷启动不踩 load-time 循环

### 3.2 暂停链路
用ChatTaskControl.togglePause → `POST /chat/stream/pause|resume/{taskId}` → 后端 wait_for_resume 纯阻塞等待，不产SSE错误；前端暂停/恢复SSE由 stream_reader 下发 paused/resumed 事件。

### 3.3 授权确认链路（useAuthorization.ts 全文已核对 ✅）
```
paused帧 → window 'authorization_required' CustomEvent
  → handleAuthorizationRequired (一次性注册[])
      → pendingRef 同步写入(堵React子先父后时序) 
      → normalizeAutoConfirm 四态归一(true/'true'/1/'1')
      → parseTimeout 合法0保留
  → AuthorizationModal countdown 统一倒计时
  → handleAuthorizationConfirm(confirmed, trustSession, confirmIdOverride)
      → setAuthorizationPending(null) 立即关弹窗(不等API)
      → taskControlApi.confirm (fire-and-forget, 后台发)
      → confirmed=true → recentConfirmedTool(2s高亮)
      → trustSession → dispatchEvent('omni-trust-changed')
```
- P1: 15s超时兜底 + clearTimeout 防弹窗永久滞留
- P2-1: 同 confirmId 重放去重不二次 resolve
- 404 判定: `res?.success===false` 走 reflect 错误分支，复用 handleError 统一弹窗

## 五、错误与恢复链路

### 5.1 错误分类权威（error/handler.ts）
- `classifyError` timeout 前置于 network；404 仅 url 含 sessions 归 SESSION_NOT_FOUND
- `sanitizeDisplayMessage` 防裸值（纯数字/非字符串/空白回退 ERROR_CONFIG_MAP 固定文案）
- `retryWithBackoff` async/await + 计数器防无限递归
- `extractErrorMessage`: 后端 detail/message 优先，数组 detail JSON.stringify 兜底

### 5.2 回调分道（useChatCallbacks.ts onError）
- `errorObj.from_backend===true` → 只清三refs即 return（不进弹窗/paused缓冲/setMessages），P2 红字
- 否则 → handleSSEError 弹窗 + pause缓冲 等待后续 frames
- `LiveError{text, requestLevel}` 位4数据源对象形态（6.3.4 北京老陈定案）

### 5.3 SSE 重连（useSSE.ts）
- 空闲超时走 reconnect 而非 disconnect；无任务ID不重新 POST（根治重复起任务）
- REQUEST-ABORT 静默短路（5.3.1）
- ERROR_CONFIG_MAP 为 canRetry 权威

## 七、可优化点建议（观察结论，未经北京老陈定案）

### 7.1 中优先级
1. **Token 双源竞态窗口**: useChainTokens 实时源 effect 与任务结束沿拉取 effect 并存，任务结束瞬间（isReceiving 翻转）两处可能同时写 setSessionTokens，存在极短窗口旧静态值覆盖新实时值的可能。建议 `isReceiving` 翻转时加最后写者判定或统一由 React 18 batching 消解（需实测验证）。
2. **IN progress 恢复时双重请求**: `useChatTaskControl.waitForCancelOrTimeout` 的 5s 超时兜底 + 后端 S1 超时放行双方都发 resumed，前端有两条路回 running，依赖时序。建议以 paused 事件 confirm_id 为唯一放行锚点。

### 7.2 低优先级
3. **`useChatPanels useMemo` 依赖数组 26 项**: 已多次同步（deniedSteps/deniedEntries/liveError/sessionTokens/chainTokens/recentConfirmedTool 等），每次加透传参数必须同步依赖数组，易漏。建议评估拆成 2 个 useMemo（topbar 组 / left-right 组）降低单次失效范围（属重构建议，暂不动）。
4. **`currentResponse` 解构存在但面板未用**: useChatPanels.tsx:139 解构 currentResponse 但依赖数组也含，unused dependency 增加无效重渲面。建议核对是否仍被传递（当前未见透传点）。
5. **execution_stream.py 与 C2 功能重叠**: 会话级 SSE 回放（execution_stream）与任务级 C2 步骤回放并存，语义一致但双实现。建议确认前端是否仍用 execution_stream 端点，若已弃用可走 YAGNI 清理。

## 八、结论

本次从后端到前端信息流程链路全面审查完成：
1. **四大方向链路全部闭合**，前向 SSE / 反向 REST / 详情拉取 / 错误恢复契约前后端逐字段核对一致；
2. **start/usage/final 三处关键帧发射与解析双向对齐**，token 四层同构（任务/会话/链级）无重复累加；
3. **取消终态语义窄化唯一**（final+outcome=cancelled+cancel_source），来源 A-G 全覆盖；
4. 发现 **5 项可优化点**（2 项中优先级、3 项低优先级），均为观察结论，是否整改待北京老陈定案。
