## 一、背景与目标

### 1.1 问题（G2 最终重复）

G2 指"任务终态 final 信号在实时流与重连流中形态分裂导致前端重复/异常"。实证（本次全链路通读）：

- 实时流收到的 final 是**长条**（含完整 response）
- 重连流（event_log 回放）读到的 final 是**短条**（无 response）
- 前端同一任务收到内容不同的两个 final，触发重复渲染/状态覆盖

根因：`event_log` 中 final 经历了「先入长条 → finally 覆写短条」两次形态变体，实时转发时长、覆写后重连时短，同一事件两种内容。

### 1.2 目标（老陈已拍板 X2）

1. **不加新事件 type**（否决 X1 `final-short`）；
2. **长短分叉在发射端一次定死**：DB 落长（完整 response，回放必需），SSE/重连发短（有正文时）或完整（无正文时）；
3. `event_log` 从源头回归「应转发子集」语义——终态只存一种形态，实时与重连天然一致，**G2 根治**；
4. 前端零改动（左侧任务回复只用 `final.response` 铁命令满足：短条时为空则留空，不设任何 DB 兜底，§4.4）；不新增事件 case（type 恒为 `final`）。

### 1.3 设计铁律

- 合规：SRP / DRY / KISS-DIRECT / SLAP / 禁 backward；
- 关联逻辑增强不退化：落库顺序、竞态语义、回放完整性、守卫/异常路径全覆盖；
- 复用现有机制：`_persist` 闭包、`_publish`/stream_reader、[27] final_stats 延后单发均不动。

### 2.2 关键事实

1. **长短形态现在由谁定**：agent_runner 扫描侧 `_has_chunk_steps`（L408，非推理 chunk）+ `_action_steps`（L412，action 轮）→ final 判定（L434-444）：
   - `outcome=="completed"` 且 step 非 action 轮 且 该轮有正文 chunk → **短条**（五键 type/step/timestamp/outcome/duration，L440）
   - 其余（completed 无正文 / failed / cancelled / return_direct）→ **完整条**（response 即正文，test_return_direct_response_lost 捕获过不可能剥离）
2. **落库顺序必须一致**：`_persist`（L269-297）`current_execution_steps.append(ed)` + `append_step(conn, ai_message_id, session_id, len(current_execution_steps)-1, ed)`——DB step 序号 = append 位置 = event_log 事件顺序。**任何旁落若不按此顺序将错乱**。
3. **竞态已由 [27] 解耦**：前端 `_hasFinal`（RightViewer.tsx:169）驱动快照（读 liveSteps，不读 DB）；`refreshTasks`/拉 token 由 `hasFinalStats`（RightViewer.tsx:176 = final_stats=DB 就绪 t3'）驱动。final 实时先到不影响 DB 读取。→ **X2 无需再让 final 等到 finally，长短分叉可在 emit 侧立即定形态，不回归**。
4. **守卫兜底**（agent_runner.py:519-549）：正常流程必已有 final 不触发；触发时构造的 failed/cancelled 终态**天然是完整形态**（非 completed 一律完整，符合短信号原则）。

## 三、X2 核心设计

### 3.1 一句话

**长短分叉从「扫描侧事后判定」上移到「发射侧当场判定」：event_log 从源头只存应转发形态（短/完整），DB 长条由发射侧缓存意图、扫描侧落库（保顺序），finally 覆写机制整体删除。**

### 3.2 三个关键点

| # | 关键点 | 说明 |
|---|--------|------|
| K1 | 发射收口 `_emit_publish` | react_step 全部 publish（12 处，含 chunk、handler 全事件与 completed final）收口为一个本地函数；final 当场判定长短后 publish（react_loop 顶层终态零改动，见 4.1.4） |
| K2 | 长条缓存载体 `agent._pending_final_db` | emit 侧把完整 dict 暂存 agent 上，扫描读到 final 时取来落库——**DB 落库仍走扫描侧 `_persist`，append 顺序与 event_log 天然一致**，杜绝 emit 侧提前 append 导致的 step 序号错乱 |
| K3 | 判定上下文 `agent._final_short_ctx` | chunk_steps/action_steps 登记由扫描累积（agent_runner L408/412）上移到发射侧（react_step emit 时登记），保证 emit final 时判定集合已就绪 |

### 3.3 改造后终态链路（X2 后全景，与 2.1 对称对照）

```
handler  (handle_answer.py / handle_action.py)
   │  emit_completed_final / emit_failed_final（step_emitter.py:81-96 终态工厂）
   ▼       ① 构造 FinalStep → emit() 注入 token/model/duration（step_emitter.py:43-61）→ to_dict() 长条（与现状相同）
react_step（react_step.py）★ 唯一分叉点在此定死（react_loop 顶层终态恒完整, 零改动, 见 4.1.4）
   │  新增 _emit_publish 统一收口（替代 12 处 await _publish: L231/255/307/341/346/366/419/429/445/450/483/495）
   │  ② final 当场分流长短：
   │     完整长条(含 response) ──────────→ 一律先缓存 agent._pending_final_db（供⑤扫描落库）
   │     短判定(有正文chunk的completed) → step_dict 剥五键 → await _publish 进 event_log（五键: type/step/timestamp/outcome/duration）
   │     长判定(error/failed/cancelled/return_direct) → await _publish 原样完整条进 event_log（=长条, 一枚两用: 缓存供DB + 转发前端）
   ▼       ③ event_log 只存应转发形态（短条 or 完整条）——源头终态唯一
stream_reader（stream_orchestrator.py:450-491）
   │  按 seq 逐条转发，仅过滤 _SSE_EXCLUDE_TYPES={"thought"}（L447/466，不变）

agent_runner（agent_runner.py）
   │  扫描路由 final 分支（改，原 L421/427-444）：
   │      从 agent._pending_final_db 取长条 → await _persist(event_dict)
   ▼       ⑤ 落库长条（完整 response，DB 回放必需）；缓存不 append → step 序号=事件顺序不变式保住
finally（agent_runner.py:640-661 简化）
   │  删除 L642-653 覆写整段（_pending_terminal_events / _final_publish_index / event_log 覆写）
   │  保留 L659-661 _publish_final_stats（[27] 延后单发）
   ▼       ⑥ event_log 原位即终态形态 → 重连流读到与实时完全相同的 final（短/完整）
```

> 注2：②的「短条」只替换有正文 chunk 的 completed；failed/cancelled/return_direct 一律「完整条」——与现状 §2.2 事实①的判定完全一致（非 completed 剥 response 会丢正文）。

| # | 环节 | 现状（2.1） | X2 后（3.3） |
|---|------|------------|--------------|
| ① | handler 产终态 | 长条 dict | **不变** |

| ④ | 实时转发 | 长条（G2 根因） | 短/完整（终态唯一，G2 根治） |

## 四、代码修改详设

### 4.1 `react_step.py`（真正发射收口）+ `react_loop.py`（判定上下文初始化）

#### 4.1.0 为什么改 + 主战场纠正（三堂会审实证）

**本版前错误设计自纠**：方案初稿把发射收口放 `react_loop.py`，声称"修改其 11 处 publish"。三堂会审逐点实证推翻如下：

| 初稿假设 | 真实代码实证 |
|---------|-------------|
| react_loop L211-212 是 handler 事件发射点 | `_process_single_step` **五个出口 L369/431/454/485/497 全部 `return []`**（empty_response/截断取消/truncated/死循环/正常 handler，事件均已在函数内 publish），L211 `for event in await _process_single_step(...)` **恒 0 次迭代=死代码** |
| react_loop 顶层 publish（L136/153/164/196/212*/225/229/259/269/283/289）为主战场 | 仅 start / thought-start / cancelled·failed 兜底终态 / retrying·error——**无 chunk、无 completed final**（L212* = 死代码循环内 publish，恒 0 迭代不执行，见上行） |
| completed final 发射点在哪 | `handle_answer`/`handle_action` `_events.extend(emit_completed_final)`（handle_answer.py:209 等）→ `_dispatch_handler`（**不 publish**，react_dispatch.py:165 return 列表）→ **react_step L494-495 `for event in await _dispatch_handler(...): await _publish(event.to_dict())`** |
| chunk 发射点在哪 | **react_step L255** `await _publish(...ChunkStep...)`（逐流式块） |

**结论**：真正发射收口在 **react_step.py**——12 处 publish，覆盖 chunk（L255）、handler 全部事件与 completed final（L495）、截断取消/死循环终态（L429/483）、usage/stats/context_overview/truncated/observation（L307/341/346/366/419/445/450）、retrying（L231）。判定上下文只在 react_loop 初始化一次（run_react_cycle 体首，每任务一次）。

### 4.2 `agent_runner.py`（扫描路由收窄 + 覆写删除）

#### 4.2.0 为什么改（现状问题 → X2 改法）

**现状（G2 根因链）**：final 的一生要过三道工序，两道在 agent_runner：

```
① 发射侧(react_step 为主场)   _publish(final_dict)  → event_log 记「完整长条」(stream_reader 按 seq 实时读走)
② 扫描循环           _persist(完整长条落库) + 依据 _has_chunk_steps/_action_steps 组装「短条」进 _pending_terminal_events 缓冲
③ finally            DB status 落库成功后, 短条覆写 buffer.event_log[_final_publish_index] 或 _publish 补发
```

同一 final 两种形态：**实时 SSE 收到长条、重连回放 event_log 收到短条**——前端 R3 读 `final.response` 时两帧不一致，G2 双发/形态分歧的病根。

**X2 改法（判定上移，配套收窄扫描侧）**：
- 长短判定提前到 react_step 发射侧（4.1 `_emit_publish`），event_log 从一开始就是「应转发形态」；
- 扫描侧只剩两件事：final 从发射侧缓存取**长条**落库（DB 恒完整，append 顺序=事件顺序不变式保持）；其余类型照旧；
- finally 覆写/补发段整体删除（原位即终态）；
- 当初缓冲+覆写机制为解「SSE final 先到、DB status 后到」竞态（2026-09-04 方案一），该竞态现由 `final_stats` 延后单发（[27]，DB 就绪信号）接管，机制失去存在理由。

## 五、关联逻辑审查（五问）

### 5.1 落库顺序是否保持（最险点）

- 现状：react_loop 返回后扫描循环逐条 `_persist` → append 顺序 = event_log 顺序。
- X2：emit 侧只**缓存**长条（不 append），扫描循环仍逐条处理、遇 final 从缓存取长条 `_persist`。append 顺序 = event_log 顺序，**与现状完全一致**，DB step 序号不漂移。
- 缓存单值覆盖：任务终态唯一，多 final 不存在；`dict()` 拷贝防事件 dict 后续被覆写（已无覆写，纯防御）。

### 5.2 竞态是否回归（SSE final 先到、DB status 后到）

- 现状：final 实时转发（长）先到 → 前端 `_hasFinal` 驱动快照（读 liveSteps）；DB 读取全部由 final_stats（[27] 延后 runner finally、DB 落库后单发）驱动。
- X2：final 实时转发（短/完整）先到时序不变，仅内容变短；快照仍读内存流不读 DB。**竞态语义与现状等价，无回归**。

### 5.3 回放完整性（DB response）

- 无正文 chunk 场景（return_direct / 工具结果即正文）：emit 判定非短 → 长条缓存 → 扫描 `_persist` 落**完整条** → 回放正文完整。`test_return_direct_response_lost` 语义保持。
- 有正文 chunk 场景：DB 仍落长条（缓存），SSE 发短条——回放从 DB 取完整正文，实时从 chunk 累计正文，两者各自完整。

### 5.4 守卫/异常/取消三兜底路径

| 路径 | 行为 | 改变 |
|------|------|------|
| 守卫补发（L519-549） | failed/cancelled 完整条：append+落库+publish | 无 |
| 异常分支（L483-507） | failed 完整条：同左 | 无 |
| react_loop 顶层兜底终态（L153/196/225/259/283） | 不动（4.1.4）：直接 `_publish` 完整条（cancelled/failed 非 completed 恒完整），扫描 `_pending_final_db or event_dict` 兜底落库完整条 | 无 |

### 5.5 G2 是否真正根治

- 实时流：`_emit_publish` 调 `_publish` 后 stream_reader 读到的 final 即**应转发形态**（有正文→短、无正文→完整）。
- 重连流：event_log 原位即为同一形态（覆写机制已删），`stream_reader` 从 after_seq 续传读同一事件同一内容。
- **同一 final 一种形态、一种内容，实时/重连语义一致** → G2 消除。
