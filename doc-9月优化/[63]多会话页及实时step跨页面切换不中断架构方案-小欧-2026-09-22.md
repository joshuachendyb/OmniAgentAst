## 一、问题描述与定性

### 1.1 用户可见的现象

会话页（`/`）实时任务执行中（SSE 正流式推送 Step），用户切换到**历史页**（`/history`）或**设置页**（`/settings2`），再切回会话页时：

1. 实时 Step（thinking/工具调用/执行结果/最终回答）**不续传**；
2. 切走期间产生的中间步骤**看不到**；
3. 若任务在切走期间已完成，回来只能看到**最终落库结果**，中间过程丢失；若任务还在跑，回来是**全新初始化**，不会自动接上正在跑的流；
4. 来回快速切换，每次进入会话页都触发一次重新初始化（重新拉历史、重建连接），实时进度 UI 反复跳变。

### 1.2 影响范围：高频真实操作

- 用户在实时任务运行中去历史页核对另一会话、去设置页调整配置，是**高频真实操作**；
- 当前行为实质是"切走即杀掉前端实时流"，与「任务后台继续跑」的预期（后端确实在跑，[51]已实证）割裂，用户感知为"实时 step 丢了"。

### 1.3 问题定性：前端断流 + 后端无事件源，两组病根叠加（对应第二章）

**切页时前端 ChatPage 被卸载 → SSE 连接 abort → 步骤备份被删 → 切回必重初始化（前端病根 F1~F7）；同时后端事件仅存进程内存且 300 秒回收、无持久事件源（后端病根 B1~B3），断了之后无处可续。** 两组病根叠加，不是"影响"，而是"中断且不续传"。

## 二、问题的根本原因（前端 F1~F7 / 后端 B1~B3 两组病根）

### 2.1 病根链（现状代码实证，分前端 / 后端两组）

> **重要口径：本问题不是"纯前端问题"。** 前端病根导致"切页即断流"，后端病根导致"断了之后无处可续"。两组病根叠加才构成完整故障链——只修前端，切页能不断流，但刷新/超 300 秒/后端重启仍无法恢复；只修后端，前端切页依旧断流。

#### 2.1.2 后端病根（3 条，1.1 现象 2/3 在"切走较久或后端重启"时的病因）

| # | 病根 | 证据位置（本地最新 HEAD） | 说明 |
|---|------|---------|------|
| B1 | 续传源是**进程内存**且有回收期 | `task_state.py:42-56` `event_log`；`agent_runner.py:766` 任务结束 300s 后 `reclaim_stream_buffer()` | 300 秒是**内存回收点**，不是数据保留期；超窗或重启后 `get_stream_buffer` 返回 None |
| B2 | 重连只查内存 buffer，无持久事件源 | `stream_orchestrator.py:646-656` `resume_sse` → `get_stream_buffer` 未命中即 `not_found` | 后端没有 `chat_stream_events` Journal，重启即"查无此事" |

**两组病根的因果关系**：F3/F4 造成"前端主动销毁续传凭据"，B1/B2/B3 造成"即便前端保留凭据也无处可续"。因此完整修复必须同时覆盖前端（P1/P2）与后端（P3，见第三章），单修任一侧都只能缓解一半。

### 2.2 问题本质：流无家（前端）+ 事件无库（后端）

**"正在进行的会话流"（In-Flight Session Stream）不是一个独立的一级状态实体**，它被绑定在 ChatPage 组件实例的 hook 生命周期上（前端病根 F2/F3/F4/F7）。UI 组件可以卸载重挂，但"流"是后台正在跑的东西，二者生命周期必须解耦。

同时，**已发生的会话事件也没有独立的一级持久实体**，只存在于 `StreamBuffer.event_log` 进程内存中并于 300 秒后回收（后端病根 B1/B2/B3）。

因此本问题有**两级本质**：前端"流无家"（切走即销毁），后端"事件无库"（断了无处续）。前者由 P1/P2 解决（第五章），后者由 P3 Journal 解决（第三章），缺任一侧都不算修完。

### 2.3 既有能力与目标的落差（可复用资产清单）

| 既有能力 | 现状 | 落差 |
|---------|------|------|
| 后端 `GET /chat/stream/{task_id}?after_seq=N` 续传 | **已存在**且幂等（路由 `chat_routes.py:116`，实现 `stream_orchestrator.py:646-656`，e2e 已验证多客户端多轮续拉） | 前端没有保存续传所需的 `(task_id, seq)`（F4） |
| 后端 `event_log` 事件缓冲 | **已存在**（`task_state.py:42-56`） | 仅进程内存 + 300s 回收，无持久事件源（B1/B2/B3） |
| 前端 steps 备份 | **已存在**（`useSSE.ts:456-478`，完整 `ExecutionStep[]`） | 卸载时被 `disconnect()` 默认删除（F3） |
| 后端按 session 找任务 | **已存在**，`GET /sessions/{id}/tasks` 返 `latest_task_id` | 可作为切回后定位任务兜底，但查不到执行中间态 |
| 历史拉取中间步骤 | **已存在**，`GET /sessions/{id}/messages` 含完整 execution_steps | 仅任务完成后可用，运行中任务不在 DB |

结论：**后端并非"没有问题"——它已具备内存窗口内的续传端点，但缺少跨进程的事件持久源（B1~B3），这使前端任何自救努力在超 300 秒或后端重启后都失效。** 因此 P1/P2 只能保证"切页不断流 + 300 秒内刷新可续"，"300 秒后与重启后可回放"必须由 P3（第三章）补齐。

## 三、后端能力层：事件 Journal 持久化、300 秒后回放与重启恢复（P3）

**事件 Journal 持久化（`chat_stream_events`）、300 秒后回放与重启恢复设计**

> 本章针对本地后端已核实的三个缺口：①`event_log` 仅存在 `StreamBuffer.event_log` 内存列表；②任务结束后 300 秒调用 `reclaim_stream_buffer()` 删除内存缓冲；③后端重启后没有可按 `task_id + seq` 回放的持久事件源。
>
> 本章与 [63] P1/P2 的关系：P1/P2 主要解决前端页面生命周期；本章是后端 P3，解决前端刷新/断线恢复依赖的后端数据耐久性。

**本章不改变 [70] ConnectionScope 的连接池所有权方案。**

### 3.1 需求边界与可实现目标（R1~R4 四级恢复）

本章将“恢复”拆成四个等级，禁止混淆：

| 等级 | 目标 | 可实现性 |
|------|------|----------|
| R1 内存级续传 | 任务运行期间断线，按 `after_seq` 从 `event_log` 续传 | 当前已支持 |
| R2 终态事件回放 | 任务完成且内存缓冲回收后，从持久 journal 按 `task_id + seq` 精确回放全部 SSE 事件 | 本章新增 |
| R3 后端重启后已完成任务回放 | 后端重启后，已完成任务仍可回放持久事件 | 本章新增 |
| R4 后端重启后继续计算未完成任务 | 重启后从 LLM/tool checkpoint 继续执行 | **不在本章实现**，需独立的 Agent checkpoint/resume 方案 |

**关键诚实边界：**后端重启后可以让已完成任务的事件不丢，也可以回放已落库事件；但后端进程已经消失，不能凭空继续一个未完成的 LLM/tool 执行。R4 不得伪装成“事件持久化已解决”。

### 3.2 代码证据与缺口（本地实测行号）

| 现状 | 代码证据 | 结论 |
|------|----------|------|
| `event_log` 是内存列表 | `backend/app/services/task/task_state.py:42`（`StreamBuffer.event_log` 字段；`publish()` 在 `:46-56`，seq 分配与 append 在 `:52-56`） | 进程退出即丢失 |
| 事件序号由 `len(event_log)` 分配 | `task_state.py:52-56`（`step_dict["seq"] = len(self.event_log)`，持 `cond` 锁原子完成） | seq 是内存数组偏移，DB 不能直接替代它 |
| 完成后 300 秒回收内存缓冲 | `backend/app/services/agent/agent_runner.py:766`（[70] 后 `await _snap_client.close()` 为无条件三分支 lease/aclose/no-op） | 300 秒是内存回收点，不是数据保留期限 |
| 重连只查内存 buffer | `backend/app/services/chat/stream_orchestrator.py:649`（[70] 后 `get_stream_buffer(task_id)`） | buffer 不存在直接 `not_found` |
| 连接池已由 ConnectionScope 统一所有（[70] 已落地） | `stream_orchestrator.py:305` `scope=get_scope()`、`agent_runner.py:535-538` 无条件 `close()` | Journal 的 SQLite 连接与 LLM httpx 池正交；Journal sink 复用 `scope` 生命期内创建，不另建池（见 3.5.1） |

### 3.3 目标架构：内存快路径 + SQLite 事件 Journal

```text

    ↓
```

### 3.5 事件写入路径：先持久化、后对 SSE 可见（失败按 3.6.2 降级）

当前 `StreamBuffer.publish()` 在 `task_state.py:46-56` 内分配 seq 并追加内存（该文件 [70] 未改动，仍 DB-agnostic）。改造为**依赖注入的发布 sink**：`create_task_stream_buffer(task_id, session_id, journal_sink)` 接收由 `agent_runner` 注入的 `stream_event_journal.append` 能力；`task_state.py` 只负责 seq、锁、内存可见性，不 import DB、不执行 SQL。**[70] 后补充**：`journal_sink` 的创建与调用发生在 `ConnectionScope` 的 lease 生命期内（`stream_orchestrator.py:305` `scope=get_scope()` 之后、`agent_runner.py:535` `close()` 之前），但 Journal 的 SQLite 事务与 LLM httpx 池的 lease 引用计数正交、互不持锁（见 3.5 第 3 步）。

1. `StreamBuffer` 增加任务级 `publish_lock`，保证同一 task 的 seq 分配与 journal 写入不并发交叉；
2. 在锁内取得当前 `seq`，复制事件并补入 seq；
3. **不持有 `buffer.cond` 锁（也不持有 `ConnectionScope` 的 pool 锁）执行 DB await**，避免阻塞生产者和 SSE reader；Journal 的 SQLite 事务与 httpx 池 lease 正交（[70] 后）；
4. 调用 `stream_event_journal.append()` 写入 SQLite；
5. journal 成功**或已按第 6 步标记降级**后，再在 `buffer.cond` 内追加 `event_log` 并 `notify_all()`（降级语义见 3.6.2 末段说明）；
6. journal 失败时执行有限重试；仍失败则记录 `stream_persistence_degraded`，继续当前实时流，但明确标记该 task 不具备 R2/R3 保证；
7. 终态 `final_stats` 写入失败必须保留错误日志和 degraded 状态，不能伪装成已持久化。

**禁止方案：**

- 先放内存、后异步落库：进程在两步之间崩溃会丢事件；
- 持有 `buffer.cond` 锁等待 SQLite：会阻塞生产者和 SSE 消费；
- DB 失败直接 `task.cancel()`：把存储故障扩大成任务执行故障；
- 每个事件单独创建连接/事务：违反 DRY/KISS，增加 SQLite 写放大。

#### 3.5.2 高频事件性能与背压边界

“先持久化后可见”不能无上限地把 SQLite 延迟加入实时链路。实施前必须以真实流量确定：

- `action/observation/final/final_stats` 等低频关键事件：单事件事务持久化；
- 高频 `chunk`：在同一 task 的 publish lock 内做有界批量提交，批次必须有最大条数/字节数和最大等待时间；
- 合批只合并事务提交，不合并事件内容：Journal 落库帧与原始发布帧 1:1，seq 逐帧分配；回放 `currentResponse` 组装与实时路径同一逻辑；
- Journal backlog 超过预算：进入 `stream_persistence_degraded`，实时流优先，记录缺口 seq，禁止宣称精确回放；
- 任何批量策略不得改变 seq 单调性，不得让 consumer 看到未持久化事件；
- 必须完成 SQLite 真实压测，至少验证长 chunk 流、工具并发、DB busy、磁盘写失败和清理并发；
- 未完成压测前不得把“每事件同步写 SQLite”直接定为最终实现。

### 3.7 事件读取与回放路径：内存优先，Journal 兜底

`GET /chat/stream/{task_id}?after_seq=N` 保持现有 API，不新增重复端点：

```text
1. get_stream_buffer(task_id)
   ├─ 存在：继续使用当前 stream_reader(event_log, after_seq)
   └─ 不存在：进入 journal_reader(task_id, after_seq)

2. journal_reader 查询 seq >= after_seq，按 seq 升序读取
3. 复用同一 format_agent_sse 和同一 _SSE_FORWARD_TYPES 白名单
4. 读到 final_stats/终态后结束
5. journal 有事件但没有终态：
   - task 已完成但 journal 尚未有终态：返回 task_state_incomplete，禁止伪造完成
   - task 未完成且后端已重启：返回 task_interrupted，前端进入历史降级
6. journal 无事件且 DB 无该 task：返回 not_found
```

**一致性要求：**

- `after_seq=N` 只返回 `seq >= N` 的事件；现有前端使用 `lastSeq + 1`，因此不得重复发送已处理事件；
- 回放使用和实时流相同的 `format_agent_sse`，禁止新增第二套 SSE 格式器；
- 回放不得启动新 Agent，不得调用 POST 编排入口；
- `not_found`、`task_interrupted`、`persistence_gap`、`persistence_degraded` 必须是明确错误事件，禁止都伪装成正常空流。

#### 3.7.1 Journal seq 缺口与降级状态

Journal reader 读取时必须校验首个 seq、连续 seq 和终态 seq：

```text
连续：after_seq+1、after_seq+2、…，允许精确回放
缺口：发现 seq 跳跃 → 发 persistence_gap，记录缺口范围，禁止宣称完整恢复
降级：Journal 写入失败但内存流继续 → 发 persistence_degraded，R2/R3 保证失效
```

`persistence_gap` 不得被前端当作正常 `final`；前端只能进入历史降级或显示“部分事件不可恢复”。

### 3.8 300 秒语义修正：内存回收而非数据保留（`reclaim_memory_buffer`）

当前 `loop.call_later(300, reclaim_stream_buffer)` 的语义应改名为：

```text
reclaim_memory_buffer(task_id)
```

它只释放：

- `StreamBuffer.event_log` 内存列表；
- `buffer.cond` 和 `buffer.done` 运行态对象。

它**不得删除** `chat_stream_events` 数据。改造后：

| 时间/状态 | 内存缓冲 | Journal | GET 续传 |
|-----------|----------|---------|----------|
| 任务运行中 | 保留 | 持续追加 | 内存快路径 |
| 任务结束 0-300 秒 | 保留 | 保留 | 内存快路径 |
| 任务结束超过 300 秒 | 回收 | 保留 | Journal 回放 |
| 后端重启、任务已完成 | 丢失 | 保留 | Journal 回放 |
| 后端重启、任务未完成 | 丢失 | 可能有部分事件 | `task_interrupted`，不继续计算 |

### 3.9 Journal 保留期与清理策略

- 300 秒只控制内存，不控制 SQLite 数据；
- Journal 清理必须按 `task_id` 终态和时间保留期执行，禁止在请求链路中全表扫描；
- 清理任务只删除已终态且超过保留期的事件，活跃 task 永不删除；`final_stats` 缺失不能成为永久不清理条件；
- `final_stats` 只用于校验正常完成，任务终态以 `chat_tasks.status` 为权威；
- 清理失败只记录 warning，不能阻断聊天主链路；
- 具体保留时长使用 `tuning` 配置集中管理，禁止在多个模块写死 300 秒或 7 天；
- 清理前必须确认 `chat_tasks.status` 已进入终态；未终态但已过保留期的任务进入人工诊断/隔离，不得直接删除。

### 3.10 后端重启后的恢复语义（禁止伪造续算）

后端启动时不能把旧 `agent_streams` 假装恢复。正确语义：

```text
journal 存在 + task 终态
  → 允许 GET after_seq 回放

journal 存在 + task 非终态
  → 返回 task_interrupted
  → 前端加载 DB 历史
  → 如需继续计算，另立 checkpoint/resume 方案

journal 不存在
  → 查询 chat_tasks
  → 有终态历史则加载历史
  → 无任务记录则 not_found
```

本方案不实现 Agent checkpoint、LLM 调用恢复、工具执行恢复，也不宣称“后端重启后任务自动继续”。这是两个不同问题，不能混为一谈。

#### 3.10.1 终态权威与前端状态对齐（禁止前端推断终态）

为避免 DB、Journal、SSE、前端四层状态互相覆盖，固定权威如下：

| 状态 | 唯一权威 | 其他层职责 |
|------|----------|------------|
| 后端任务是否终态 | `chat_tasks.status` | SSE/前端不得自行推断终态 |
| 事件是否可回放 | Journal seq 连续性 + `final_stats` | 前端只消费回放结果 |
| 前端是否正在接收 | Store 快照 `isReceiving` | 页面卸载不改变后端任务状态 |
| 最终展示内容 | DB 已完成步骤/最终响应 | Journal 用于事件回放，不替代 DB 权威 |

`final_stats` 是事件协议终态信号，不取代 `chat_tasks.status`；Store 的 `isReceiving` 是 UI 状态，不取代后端状态。

### 4.2 会话流常驻架构（Session Stream Residency，本文选定）

**核心思想**：
> 把「正在运行的会话流」从 ChatPage 组件实例中抽离，提升为**模块级全局单例 Store**（`Map<sessionId, ChatStreamSession>`）。SSE 连接、步骤、任务锚点由 Store 持有；组件只是**订阅者**。卸载组件=解绑订阅，流继续跑；重挂载=重新订阅即时拿快照。浏览器刷新（Store 丢失）由 sessionStorage 持久化 + GET after_seq 续传兜底。

**架构分层（P1/P2 三层防线，P3 另增后端 Journal 层）**：

| 层 | 防线 | 覆盖场景 |
|----|------|---------|
| L1 内存 Store | SSE 连接与状态全局常驻 | **路由来回切换（最常见）**：完全无缝 |
| L2 持久化+续传（P1/P2 当前） | 锚点组+steps 写 sessionStorage；mount 检测活动任务发 GET 续传 | **浏览器刷新/标签页冻结恢复**（当前后端仅保证 300 秒内存窗口内） |
| L3 DB 历史兜底（P1/P2 当前） | 现有 `loadHistoryMessages` 加载最终结果 | 窗口外/后端重启：行为等同现状，不劣化 |
| P3 Journal 回放（新增目标） | 后端 `chat_stream_events` + Journal reader | 300 秒后回放、后端重启后回放已完成任务；未完成计算不自动续算 |

**设计要点（10 大规范对齐）**：
- **SRP**：Store 只管"流"（连接/步骤/任务锚点/订阅），消息历史、UI 状态（滚动、回复区）仍留在 ChatPage/useChatState，职责分明；
- **DRY**：会话流状态让 useSSE 与未来历史页实时化共用同一数据源，消除"每实例一套 ref 双写"；
- **OCP**：Store 按 sessionId 索引，天然支持多会话并行/历史页订阅实时流，新增消费者不必改 Store 内核；
- **禁止backward**：useSSE 对外接口（sendMessage/onStep/onComplete…）经薄适配层保留签名，消费者无感知切换，但内部实现整体迁移，不保留新旧两套路径。

**会话流常驻架构的能力边界（必须说清，避免误以为它修完了全部病根）**：它是**前端**方案，只覆盖 F1~F7；后端 B1（事件仅内存 + 300s 回收）、B2（无持久事件源）、B3（只有 steps 非完整事件流）**不在其能力范围内**，必须由后端 P3 Journal 解决（第三章）。因此准确表述是：**P1/P2 交付后，切页不断流、300 秒内刷新可续；300 秒后与后端重启后的回放能力，必须等 P3。**

### 4.3 会话流常驻架构与其它三个候选方案的关系

- **Context 全局化 不用**：状态全局化后 UI 态与流态双源，且每次 `setMessages` 触发全树重渲染；
- **路由 keep-alive 不用**：4.1 两张对比表中已定为"不采用（最差）"，不写进任何实施阶段；
- **锚点续传补丁 吸收**：常驻架构的 L2 层（锚点组持久化 + GET 续传）直接复用其既有代码资产——`useSSE.ts:465-469` 备份 envelope、`useSSE.ts:830-840` GET 续传、后端 `chat_routes.py:116` 续传端点，**不重造轮子**；其组件内补丁式实现丢弃。

### 4.4 会话流常驻架构决策要点（白话版）

> 本节用最直白的话，把最终确定的"会话流常驻架构"完整讲清楚——是什么、怎么改、改完什么效果、极端情况怎么办。

#### 4.4.1 一句话讲清方案本质

**把"正在跑的对话流"从聊天页组件上摘下来，放到一个常住后台的全局 Store 里；聊天页面只是"看屏幕的人"，切走页面不再等于拔掉电话线。**

#### 4.4.2 类比说明：接线员与总机室

把现在的会话页想成"一个人同时当接线员＋显示器"：
- **现状**：你一转身（切换去历史页/设置页），整格人连人带桌子被撤走——电话线（SSE 连接）被拔断、贴墙的进度单（步骤备份）被撕掉。
- **会话流常驻架构**：把"接线员＋电话线＋进度记录"搬进楼下的**总机室**（全局 Store）常驻上班。聊天页面只负责"抬头看总机室传上来的大屏"（订阅显示）。
  - 你转身去别的房间 → 总机室电话照接、进度照记，**后台任务继续跑**；
  - 你走回来 → 大屏**立刻接着显示最新进度**，不用重新汇报、不用重新接线；
  - 只有你明确说"这条线不用了"（点击停止、删除会话或任务进入终态）→ 才挂断清理；新建会话只创建新视图，不自动停止旧任务。

#### 4.4.3 核心动作（改什么、不改什么）

| 动作 | 内容 |
|------|------|
| **新建** 1 个全局 Store（总机室） | `chatStreamStore.ts`——**以 `sessionId` 为键的 `Map<sessionId, ChatStreamSession>`**（落地实现见 5.4）：每条流持有 SSE 连接、已收步骤、任务 id、最新 seq、待发消息、接收中标记。**结构本身即多会话**（非"预留位"），本轮只交付单会话运行流，多会话 UI 属第七章 |
| **搬进去** SSE 全套逻辑 | 将现有 `useSSE.ts` 的建连接/收帧/断线重连/续传逻辑**迁移**到 Store，状态宿主改为 Store 快照；不复制第二套解析器，不保留双运行路径 |
| **聊天页面改为"只订阅"** | 新增 `useChatStreamSession(sessionId)` hook——页面挂载＝向总机室申请看这条线的屏；**页面卸载＝只看屏的人下线，电话线不断** |
| **反转卸载清理** | 现状：切走页面＝断线＋删进度单（`useSSE.ts:1231-1246`）。改为：切走页面＝只解除订阅；只有"显式离开会话/停止任务"才真正清理。**这是全方案最关键的 1 行行为反转** |
| **不动** 对外接口 | `useChatStreaming`/`useChatFacade`/`ChatPage` 的消费方代码签名不变（`sendMessage`/`onComplete`/步骤数组等照旧），改造内部、外部无感知过渡 |

#### 4.4.4 三层防线：L1 内存 Store / L2 续传 / L3 历史兜底

| 防线 | 管什么场景 | 效果 |
|------|-----------|------|
| L1 内存 Store | **切去历史页/设置页再切回来**（最常见） | 线不断，切回大屏**直接续显**，零等待、不重拉、不重建任务 |
| L2 持久化＋续传 | **浏览器按 F5 刷新、标签页被系统冻结恢复**（总机室也被端掉了） | 把步骤＋锚点组（任务id/最新seq/待发消息/上下文模式/接收中标记）先存进 sessionStorage；重挂载后自动按 `after_seq` 发 GET 补拉切走期间的新步骤（当前后端仅保证 300 秒内存窗口内） |
| L3 DB 历史兜底 | **超过 300 秒才回来 / 后端重启**（P1/P2 当前补拉也拿不到中间态） | 退回现有"加载历史最终结果"，行为与现在一致，**只可能变好、不会更差**；P3 实施后由 Journal reader 接管终态回放 |

> 关键认知：L1 解决的是"用户天天发生的切页"，L2/L3 是"各种意外断了之后的自救"。三层叠加，没有任何场景比现状更糟。

#### 4.4.5 复用的现有资产（不重造轮子）

- 后端 `GET /chat/stream/{task_id}?after_seq=N` 续传端点——**已经存在且被 E2E 验证过**，直接用；
- 前端现有 steps 备份机制——**复用其存储位置和定时器模式**，但改为原子快照写入，补齐 taskId/lastSeq/待发消息/上下文模式/接收中标记；终态和异常终态立即写入，不受 5 秒防抖延迟；
- 后端按会话找任务接口 `GET /sessions/{id}/tasks`——已经存在，作兜底定位；
- 现有历史加载 `loadHistoryMessages`——已经存在，作 L3 兜底。

#### 4.4.6 稳定性、可靠性与扩展性论证

- **稳定**：P1 核心行为反转是卸载不再断流；P2 再补锚点和续传；P3 才改变后端耐久性边界。
- **可靠**：当前 P1/P2 在 300 秒窗口内续传，窗口外依赖历史降级；P3 实施后才提供 Journal 回放。
- **可扩展**：Store 以 `sessionId` 为键（`Map` 结构，非预留位），历史页订阅、多任务与第七章多会话 Tab 直接复用同一数据结构；跨标签同步不属于本轮交付能力。

#### 4.4.7 落地节奏：P1 / P2 / P3 三步

| 阶段 | 做什么 | 效果 |
|------|--------|------|
| P1 常驻化 | 建总机室 + 卸载改"只解绑" | 切页不断流、切回续显（解决 90% 痛点） |
| P2 持久化＋续传 | 补锚点组(四元组+接收中标记) + 刷新自动续拉 | 当前 300 秒窗口内可续传；窗口外/降级时明确进入历史恢复，不承诺绝对不丢 |
| P3 后端增强 | `chat_stream_events` Journal 持久化、Journal reader 回放、终态清理 | 300 秒后和后端重启后，已完成任务可按 seq 回放；未完成计算明确中断，不伪造续算 |

**结论（终极一句话）**：会话流常驻架构 ＝ **把对话流的"家"从聊天页面搬进全局总机室常驻，页面只当显示器；切走断不了、刷新能自救、最坏不劣化，且为未来多会话/多页一定备好扩展位。**

### 4.5 改造前后逻辑流程对比：改的是流程，不是功能（白话）

> 明确回答"这是功能流程改变还是什么流程改变"：**改的不是功能流程，改的是三条"内功流程"——数据住哪、生命周期归谁、卸载时干什么。用户能看到的操作一个都没变。**

#### 4.5.1 改造前（现状）的逻辑流程

```
【实时任务中】
发送消息 ──→ ChatPage 里 useSSE 自己建立连接(POST /chat/stream)
              │          收帧 → 写进"页面自己的" executionSteps (state+ref)
              └─→ UI 渲染 step

【切去历史/设置页】   ← 问题根源在这
ChatPage 被卸载
   └─→ useSSE 卸载清理(useSSE.ts:1231):
        ① disconnect() → abort 连接(电话挂了)
        ② 删 sessionStorage 步骤备份(进度单撕了)
        ③ pendingMessage=null(待发消息丢了)
   └─→ 页面里所有状态(executionSteps/taskId/seq) 随组件一起销毁
后端任务: 继续在服务端跑(内存缓冲累积)，但没有前端接收了

【切回会话页】  ← 全新白板
ChatPage 重新挂载 → useSSE 全新实例(所有 state 归零)
   └─→ 初始化: loadHistoryMessages 从 DB 拉最终结果
   └─→ 任务若已跑完: 看到最终答案，中间 step 没了
   └─→ 任务若还在跑: 看不到实时，也不会自动续上；无 Store 锚点时重新 POST 可能触发当前后端的同会话任务注入/竞态路径，P1 必须从源头禁止无锚点重复 POST
```

**本质**：SSE 连接和步骤数据的"寿命 = 聊天页组件的寿命"。页面一卸载，连接和状态**跟着一起死**。

#### 4.5.2 会话流常驻架构改造后的逻辑流程

```
【实时任务中】
发送消息 ──→ 全局 chatStreamStore 建立连接(POST)  ← 连接迁到"总机室"
              │          收帧 → 写进 Store 的 executionSteps
              └─→ 通知订阅者(ChatPage) → UI 渲染    ← 页面只是"看屏的人"

【切去历史/设置页】
ChatPage 被卸载
   └─→ 仅"解除订阅"(useSyncExternalStore 自动 unsubscribe)
   └─→ Store、连接、步骤、taskId/seq 全部保留，任务继续边跑边存
后端任务: 继续跑，Store 继续接帧累积

【切回会话页】
ChatPage 重新挂载 → 重新订阅 Store → 立即拿到当前快照(最新steps/taskId/接收中)
   └─→ UI 直接续显，零等待、不重拉、不重建任务

【极端: 刷新页面(Store 也没了)】
restore sessionStorage(锚点组+steps) → 检测到活动任务 → GET /chat/stream/{task_id}?after_seq=N 补拉
   └─→ 刷新也拿回切走期间的中间步骤

【P1/P2 当前: 超300s/后端重启】→ 退回现有历史加载, 行为不劣化
【P3 目标: 终态 Journal 回放/后端重启后已完成任务回放】→ 按 seq 回放持久事件
```

**本质**：SSE 连接和步骤数据的"寿命 = 会话(任务)的寿命"，独立驻留全局 Store；卸载页面只是"看板下线"，流照跑。

#### 4.5.3 改的是哪三条流程 —— 三改一不改

| 维度 | 改前 | 改后 | 属于什么改变 |
|------|------|------|------------|
| **状态/连接住哪** | 组件 hook 内(useSSE 每实例一套) | 全局 Store(按 sessionId 索引) | **数据驻留位置改变**（架构层） |
| **生命周期归谁** | 归 ChatPage 组件 | 归会话(任务) | **生命周期归属改变**（架构层） |
| **卸载时干什么** | 断开连接+删备份+清状态 | 只解绑订阅 | **P1 核心行为反转**；P2 再补锚点/续传，P3 再补后端耐久性 |
| **用户操作**(发消息/看step/取消/暂停/HITL/历史) | — | — | **业务操作不改，但适配层必须完整实现现有消费接口，不得以“接口不变”为由漏迁移能力** |

#### 4.5.4 一句话总结

**功能流程完全没变，变的是"谁来养这条流"**——从"跟着页面生死"改成"常驻后台、跟任务生死"；附带把"卸载＝销毁"这一个错误行为反转成"卸载＝只看屏的人撤了"。

### 4.6 实施纠偏与生命周期语义（对本地代码的审核结论）

> 审核人：小欧 2026-09-25 13:15:20
>
> 审核依据：本地最新 `frontend/src/hooks/useSSE.ts`、`useChatStreaming.ts`、`useChatInit.ts`、`backend/app/services/chat/stream_orchestrator.py`、`task_state.py`。本节是对会话流常驻架构的实施纠偏，后续代码必须以本节为准。

#### 4.6.1 实施纠偏结论（9 条）

会话流常驻架构的方向是正确的：**运行中的 SSE 从 ChatPage/useSSE 生命周期中解耦，按 sessionId 放入运行时 Store**。但不能原样实施，必须按本章纠偏为可落地版本：

1. `useSyncExternalStore` 必须读取缓存快照，禁止每次 `getSnapshot()` 新建对象或在读取阶段惰性创建状态。
2. 取消订阅、关闭视图、停止任务、删除会话必须是四个不同动作；关闭视图不得调用 `clear()` 或 abort。
3. L2 持久化必须使用同一份原子快照；终态必须立即落盘，不能只依赖 5 秒防抖。
4. Store 必须补齐现有 `useSSE` 的运行态、定时器、连接资源和 HITL 状态，不能只迁移文档列出的少数字段。
5. GET 续传必须处理 `not_found`、`task_interrupted`、`task_state_incomplete`、`persistence_gap`、`persistence_degraded`、已完成、缓冲过期和后端重启；不能把"回退历史"当成自动发生的行为。
6. sessionStorage 只承担单标签页刷新恢复，不承担跨标签同步；多标签同步另立方案。
7. 多会话 Tab 是后续 UI 能力，不纳入本轮 P1/P2，避免 Store 迁移和 UI 重构同时发生。
8. **F7 必须同步修复**：`useChatInit.ts:22-66` 的初始化 effect 依赖 `[opts.urlSessionId]`，切回会话页必然重跑 `initializeSession`。Store 落地后若不并行处理，页面虽已改为"只订阅"，仍会因重新初始化而 UI 跳变——**改造范围必须含"切回/切 Tab 时跳过重初始化"**（见 4.6.2 与第五章 5.17）；
9. **不引入替代承载**：Service Worker/SharedWorker 承载 SSE、BroadcastChannel 跨标签同步、"纯后端推送"三类设想一律不采用——同源鉴权与 HITL 弹窗跨页归属复杂、多页 `seq` 仲裁成本高于收益，且**都不能替代后端 Journal**（B1~B3 仍在），换承载方式解决不了"谁持有流"这个真问题。


#### 4.6.2 会话流常驻架构的生命周期语义（纠偏后）

```text
切路由/切 Tab       → 只取消页面订阅
切回会话页          → 先读 Store 快照；Store 有流则跳过 initializeSession（F7，见 4.6.1⑧）
关闭视图            → 只移除视图，Store 和后端任务保留
停止任务            → 先调用后端 cancel，确认终态后清理 Store（cancel 返回已结束按 STOP_RACE 处理）
删除会话            → 先调用后端删除接口，确认删除后清理 Store
任务正常完成        → 保留最终快照，按 TTL/LRU 释放连接资源
浏览器刷新          → Store 丢失，使用 L2 原子快照恢复
```

**红线：**“我不看了”不等于“停止任务”；任何关闭视图路径都不得调用 `clear()`、abort 或删除 sessionStorage。

**口径说明（与 7.3.4 对齐）：** 上条红线约束的是"用户主动关闭视图"这一动作；7.3.4 的"关闭后无人认领的流按宽限期回收"是**另一件事**——它只经 `releaseUnsubscribed()` 释放客户端连接与定时器，不调用后端 cancel、不删快照、不改任务状态。两者不冲突：任何路径都不得因"回收"而停止后端任务。

### 5.2 持久化锚点组扩展（`chatStreamPersistence.ts`，L2 层）

备份 envelope 即 5.1 的 `StreamBackup`（**类型单一来源在 5.1，本节禁止重定义**），L2 只负责"锚点组（四元组 + 接收中标记）"的落盘与恢复纪律：

```ts
// frontend/src/features/chat/streams/chatStreamPersistence.ts
import type { StreamBackup } from './backupTypes';   // 5.1 唯一定义处

// 落盘/恢复前校验：锚点组必须来自同一份缓存快照（同一 revision）
export function isAnchorGroupIntact(b: StreamBackup): boolean {
  return b.lastSeq >= -1
    && (b.taskId !== null || b.pendingMessage === null)   // 无 taskId 不得声称已发
    && (b.pendingMessage?.state === 'sent') === b.isReceiving;
}
```

- 普通帧可沿用 5 秒防抖，但写入必须来自同一份缓存快照；
- `done/final/final_stats/error/cancelled/rejected` 等终态或异常终态必须立即调用 `persistNow()`，不得等待防抖；
- 写入失败必须记录可诊断信息，并将该恢复能力标记为不可用，不得伪装成功；
- 恢复时经 `isAnchorGroupIntact` 校验 `version/sessionId/taskId/revision/lastSeq` 同源，不合法快照直接丢弃并走历史加载；
- 路由卸载和关闭视图不得删除该快照；只有后端确认停止/删除或 TTL 清理后才允许删除。

**原子性要求：**`lastSeq` 表示后端 `event_log` 已处理偏移，不能使用最后一个可见业务 step 的序号；seq 与 steps 必须在同一个 Store 写入口更新。

**恢复合并规则：**

- `executionSteps` 必须按事件身份去重（本节若只定义 currentResponse/usageAccum，缺步骤去重会导致 Journal 回放与快照叠加出重复行）：以 `(type, step, seq)` 为键做存在性过滤，快照中已存在的步骤不再追加；`final` 与 `final_stats` 各自只保留一条，后者重复到达时按 payload 等价覆盖而非追加；
- `currentResponse` 以快照中的已确认前缀为基准，只追加 `seq > lastSeq` 的后续 chunk；禁止把已确认前缀重复拼接；
- `usageAccum` 按快照累计值恢复，后续 usage 帧按 `seq > lastSeq` 递增合并；
- `hitlWaitingKeys` 持久化为有序字符串数组；恢复时按数组重建等待集合，禁止恢复后把仍在等待的 HITL 误判为已超时；
- 快照中 `isConnected` 只表示写入时刻，不作为恢复后的连接状态；恢复后连接状态只能由当前 Store 的实际连接决定。

#### 5.2.1 模块职责与数据流

新增 `chatStreamPersistence.ts`，只负责 `load(sessionId)`、`save(snapshot)`、`remove(sessionId)` 三个动作；不得读取 Store 内部字段，不得触发 SSE，不得修改 React 状态。Store 在同一写入口生成快照后调用 `save`，终态调用 `save` 的立即写入模式。

```text
Store 写入口 → 生成不可变 StreamBackup → persistence.save()
页面恢复   → persistence.load() → 校验版本 → Store.hydrate()
```

禁止页面直接读写 sessionStorage，禁止 Store 解析存储，禁止把持久化逻辑塞进 `useSSE` 或 `useChatStreamSession`。

**落地实现（`chatStreamPersistence.ts`，真实代码）**

```ts
// frontend/src/features/chat/streams/chatStreamPersistence.ts
// [63] 5.2：三窄接口，只管存取，不碰 Store 内部字段、不触发 SSE、不改 React 状态
import type { StreamBackup } from './backupTypes';

// 沿用现有前缀 `sse_execution_steps_backup`（useSSE.ts 的 SSE_STORAGE_KEY）+ 版本后缀 `_v2_`，
// 不换前缀：换前缀会与旧备份形成双源；读取时按 v2 校验 version，不合法即丢弃走历史加载
const KEY = (sessionId: string) => `sse_execution_steps_backup_v2_${sessionId}`;

export function load(sessionId: string): StreamBackup | { version: 1; steps: unknown[] } | null {
  const raw = sessionStorage.getItem(KEY(sessionId));
  if (!raw) return null;
  try {
    return JSON.parse(raw) as StreamBackup;
  } catch (e) {
    console.warn('[Persistence] 快照解析失败，按无效处理:', e);
    sessionStorage.removeItem(KEY(sessionId));
    return null;
  }
}

export function save(b: StreamBackup): void {
  try {
    sessionStorage.setItem(KEY(b.sessionId), JSON.stringify(b));
  } catch (e) {
    // 容量满/隐私模式：写入失败必须标记恢复能力不可用，禁止伪装成功（5.9 约束）
    console.warn('[Persistence] 快照写入失败，刷新恢复能力不可用:', e);
  }
}

export function remove(sessionId: string): void {
  sessionStorage.removeItem(KEY(sessionId));
}

// 输入草稿 per-session 持久化：视图卸载不丢草稿，与流快照 key 分离
const DRAFT_KEY = (sessionId: string) => `sse_draft_v1_${sessionId}`;

export function saveDraft(sessionId: string, text: string): void {
  if (text) sessionStorage.setItem(DRAFT_KEY(sessionId), text);
  else sessionStorage.removeItem(DRAFT_KEY(sessionId));
}

export function loadDraft(sessionId: string): string {
  return sessionStorage.getItem(DRAFT_KEY(sessionId)) ?? '';
}
```

**L1 能力的本质**：订阅者链表 `listeners` 保证 ChatPage 卸载只调 `unsubscribe`，Store 与 fetch 连接**不销毁**。

### 5.3 新增 `chatStreamTransport.ts`（由 `useSSE.ts:779-1179` 迁入）

承载首连 POST、GET `after_seq` 续传、SSE 读循环、指数退避、180s 请求头超时、60s 空闲超时与 HITL 等待键；**不持有任何 React 状态**。

```ts
// frontend/src/features/chat/streams/chatStreamTransport.ts
// [63] 5.3：从 useSSE.ts 迁移，逻辑零改写，只改状态宿主为 Store session
import { processSSEData } from '@/features/chat/services/sseParser';
import { commit } from './chatStreamStore';
import { cancelTaskApi, sessionTaskApi } from '@/services/api/task.api';

const HEADER_TIMEOUT = 180_000;   // 请求头超时（fetch 返回即清除）
const IDLE_TIMEOUT = 60_000;      // 无数据判定断连（心跳 : ping 会刷新）
const MAX_ATTEMPTS = 3;           // 与现有 ERROR_CONFIG_MAP.retryable 口径一致

export async function sendStreamRequest(
  s: ChatStreamSession, clientMessageId: string, content: string,
  mode: 'linked' | 'independent',
): Promise<string> {
  const ctl = new AbortController();
  commit(s, (d) => { d.abortController = ctl; });
  const res = await fetch('/chat/stream', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ messages: [{ role: 'user', content }], stream: true,
                           session_id: s.sessionId, client_message_id: clientMessageId,
                           context_link_mode: mode }),
    signal: ctl.signal,
  });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  const taskId = await readTaskIdFromStartFrame(res, s);
  void pump(res, s);              // 首包 taskId 落定后转入与续传同一读循环
  return taskId;
}

export async function resumeStreamRequest(s: ChatStreamSession): Promise<ResumeResult> {
  if (!s.serverTaskId) return 'pending_draft';
  if (s.resumeInFlight) return 'recovering';
  commit(s, (d) => { d.resumeInFlight = true; });
  try {
    for (let attempt = 0; attempt < MAX_ATTEMPTS; attempt += 1) {
      commit(s, (d) => {
        d.reconnectStatus = attempt === 0 ? 'connecting' : 'reconnecting';
        d.abortController = new AbortController();
      });
      const url = `/chat/stream/${s.serverTaskId}`
                + `?session_id=${encodeURIComponent(s.sessionId)}&after_seq=${s.lastSeq + 1}`;
      try {
        const res = await fetch(url, { signal: s.abortController!.signal });
        if (res.status === 404) return await handleGetNotFound(s);      // GET_NOT_FOUND 族
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        armIdleWatch(s);
        return await pump(res, s);
      } catch (e) {
        if (s.abortController!.signal.aborted) return 'aborted';
        commit(s, (d) => { d.reconnectStatus = 'failed'; });
        if (attempt === MAX_ATTEMPTS - 1) return observeByPolling(s);    // 轮询观察终态
        await sleep(jitter(1000 * 2 ** attempt, 10_000));                 // 指数退避 + Full Jitter
      }
    }
    return 'failed';
  } finally {
    commit(s, (d) => { d.resumeInFlight = false; });
  }
}

async function handleGetNotFound(s: ChatStreamSession): Promise<ResumeResult> {
  const tasks = await sessionTaskApi.listTasks(s.sessionId);
  const t = tasks.tasks.find((x) => x.task_id === s.serverTaskId);
  if (!t) return 'not_found';
  if (t.status === 'completed' || t.status === 'failed' || t.status === 'cancelled') {
    commit(s, (d) => { d.status = t.status; });   // 终态以 chat_tasks 为权威（3.10.1）
    return 'terminal';
  }
  commit(s, (d) => { d.status = 'recovering'; });  // 非终态且查不到 → 核对中，禁止伪造完成
  return 'recovering';
}

function observeByPolling(s: ChatStreamSession): ResumeResult {
  commit(s, (d) => { d.pollSignal = { aborted: false }; });   // 30 次 × 5s，命中终态即静默收尾
  return 'polling';
}

function armIdleWatch(s: ChatStreamSession): void {
  commit(s, (d) => { clearTimeout(d.idleTimeout); });
  const t = setTimeout(() => {
    commit(s, (d) => { d.reconnectStatus = 'reconnecting'; });
    void resumeStreamRequest(s);                               // resumeInFlight 防双 pump（V4）
  }, IDLE_TIMEOUT);
  commit(s, (d) => { d.idleTimeout = t as unknown as number; });
}

// wire type → 内部 StreamEvent.kind 归一化（5.1 kind 是归一化 taxonomy，不是 wire 原样）：
// action/observation → step；final/final_stats → complete；chunk → chunk；error → error；
// paused+confirm_id → authorization（内部事件，同时写入 pendingAuthorization）；
// resumed/retrying/rejected/thought-start/usage/stats/start → 原样透传为同名 kind。
// 归一化只做命名收敛，不改白名单（白名单仍是后端的 _SSE_FORWARD_TYPES）。
const WIRE_KIND: Record<string, StreamEvent['kind']> = {
  action: 'step', observation: 'step',
  final: 'complete', final_stats: 'complete',
  chunk: 'chunk', error: 'error',
  paused: 'paused', resumed: 'resumed', retrying: 'retry', rejected: 'rejected',
};
// 后端错误事件 error_type → 恢复分支（3.7 五事件；走 HTTP 200 分块到达，由 onError 分流）
const ERROR_BRANCH: Record<string, ResumeResult> = {
  not_found: 'not_found',
  task_interrupted: 'task_interrupted',
  task_state_incomplete: 'task_state_incomplete',
  persistence_gap: 'gap',
  persistence_degraded: 'degraded',
};

async function pump(res: Response, s: ChatStreamSession): Promise<ResumeResult> {
  if (s.pumpActive) return 'recovering';
  commit(s, (d) => { d.pumpActive = true; });
  try {
    const reader = res.body!.getReader();
    const decoder = new TextDecoder('utf-8');
    const h = storeHandlers(s);
    let buf = '';
    for (;;) {
      const { done, value } = await reader.read();
      if (done) {
        buf += decoder.decode();
        if (buf.trim()) processSSEData(buf, h.hooks);
        const branch = h.takeBranch();
        if (branch) return branch;
        commit(s, (d) => { clearTimeout(d.idleTimeout); });
        return s.status === 'completed' ? 'terminal' : 'recovering';
      }
      buf += decoder.decode(value, { stream: true });
      const lines = buf.split('\n');
      buf = lines.pop() ?? '';
      processSSEData(lines.join('\n'), h.hooks);
      const branch = h.takeBranch();
      if (branch) {                                            // 错误帧到达即停泵分流，不当普通帧消费
        try { await reader.cancel(); } catch { /* 已结束 */ }
        return branch;
      }
      armIdleWatch(s);
    }
  } finally {
    commit(s, (d) => { d.pumpActive = false; });
  }
}

// Store 适配既有 processSSEData：React Dispatch 形接口用读写闭包承接，不造第二套分帧器；
// 去重沿用 parser 内 lastSeqRef 口径（seq <= 已处理即丢），执行者即本函数（M7）；
// paused+confirm_id 在此写入 pendingAuthorization（M1）。
function storeHandlers(s: ChatStreamSession) {
  let branch: ResumeResult | null = null;
  const set =
    <T,>(read: () => T, apply: (d: ChatStreamSession, v: T) => void): React.Dispatch<React.SetStateAction<T>> =>
    (u) => commit(s, (d) => { apply(d, typeof u === 'function' ? (u as (p: T) => T)(read()) : u); });
  const seqRef = {
    get current() { return s.lastSeq; },
    set current(v: number) { commit(s, (d) => { d.lastSeq = Math.max(d.lastSeq, v); }); },
  };
  return {
    hooks: {
      setExecutionSteps: set(() => s.executionSteps, (d, v) => { d.executionSteps = v; }),
      getCurrentExecutionSteps: () => s.executionSteps,
      executionStepsRef: { get current() { return s.executionSteps; } },
      onStep: (step) => emitEvent(s, 'step', step),
      onChunk: (chunk) => emitEvent(s, 'chunk', chunk),
      onComplete: (full) => emitEvent(s, 'complete', full),
      onRejected: (data) => emitEvent(s, 'rejected', data),
      onRetry: (message) => emitEvent(s, 'retry', message),
      onAuthorizationRequired: (a) => commit(s, (d) => {
        d.pendingAuthorization = { ...a };
        d.hitlWaitingKeys.add(a.confirm_id);
      }),
      onPaused: (confirmId?: string) => commit(s, (d) => { if (confirmId) d.hitlWaitingKeys.add(confirmId); }),
      onResumed: (confirmId?: string) => commit(s, (d) => { if (confirmId) d.hitlWaitingKeys.delete(confirmId); }),
      onError: (e: string | { error_type?: string; message?: string }) => {
        const t = typeof e === 'string' ? '' : (e?.error_type ?? '');
        branch = ERROR_BRANCH[t] ?? 'failed';
        emitEvent(s, 'error', typeof e === 'string' ? e : (e?.message ?? t));
      },
      setCurrentResponse: set(() => s.currentResponse, (d, v) => { d.currentResponse = v; }),
      responseBufferRef: { get current() { return s.currentResponse; } },
      setIsReceiving: set(() => s.isReceiving, (d, v) => { d.isReceiving = v; }),
      setIsConnected: set(() => s.isConnected, (d, v) => { d.isConnected = v; }),
      disconnect: () => {},
      setServerTaskId: set(() => s.serverTaskId, (d, v) => { d.serverTaskId = v; }),
      onSeq: (seq: number) => { seqRef.current = seq; },
      lastSeqRef: seqRef,
    },
    takeBranch: () => branch,
  };
}

export const cancelTask = (taskId: string, sessionId?: string) =>
  cancelTaskApi.cancel(taskId, sessionId);
export const listSessionTasks = (sessionId: string) => sessionTaskApi.listTasks(sessionId);
```

**实现约束：**

- `getSnapshot()` 在 session 尚不存在时返回冻结的空快照，不创建 session；`ensureSession()` 只能由挂载 effect 或用户动作显式调用。
- `revision` 变化时才创建新的 `snapshot`，`getSnapshot()` 只读缓存，不得创建对象或修改状态。
- 事件处理必须在一个 Store 写入口中完成 `lastSeq + steps + 接收状态` 的原子更新。
- `onStep/onChunk/onComplete/onError/onPaused/onResumed/onRetry/onAuthorizationRequired/onRejected` 统一转换为 `StreamEvent`，由 Store 事件分发器投递给当前订阅者；页面卸载后不再投递 UI 回调，终态仍保留在快照中供新订阅者读取。

```ts
// StreamEvent 的唯一定义在 5.1 backupTypes.ts，本模块只 import 使用，禁止二次定义
```

`StreamEvent` 只允许携带事件和版本信息，不携带 React 状态引用；页面事件回调只能读取事件和快照，禁止直接修改 Store 内部字段。
- 页面通过动作 API 发送、停止、恢复，禁止直接修改 `ChatStreamSession` 内部字段。
- 现有 `executionStepsRef` 不得继续作为可写第二真源；`useChatStreaming` 改为调用 `clearSteps()`/快照读取，`setIsReceiving`/`setServerTaskId` 改为 Store 动作，禁止 ref/state/Store 三方双写。
- `stop()` 是“停止任务”，`clearCompleted()` 是“释放已完成资源”，二者都不得由组件卸载或关闭视图触发。
- `releaseUnsubscribed()` 的边界明确为：订阅者数为 0 且超过宽限期（默认 60s）时，**只释放客户端侧资源**（fetch 连接、定时器、事件订阅），**不调用后端 cancel、不停止任务、不删除 sessionStorage 快照、不改 `chat_tasks.status`**；重新打开该会话按 `resume()` 续传。活跃订阅者存在时一律不回收。
- Store 必须有明确的终态资源上限：完成后保留最终快照供历史/恢复读取，连接 abortController、定时器和订阅者按终态 TTL/LRU 释放；活跃 session 不得被 LRU 淘汰。

```ts
// frontend/src/features/chat/streams/chatStreamStore.ts
// [63] 5.4 落地：会话级流运行时唯一真源；页面只订阅，卸载不销毁 — 小欧 2026-09-25
import { logger } from '@/logger';
import type { ExecutionStep } from '@/types/execution';
import type { MutableRefObject } from 'react';
import type { TaskMetaFrames, emptyMetaFrames, ClockSignals } from '@/types/sse';
import type { SessionSnapshot, StreamBackup, StreamEvent, StreamStatus } from './backupTypes';  // 5.1 唯一定义处
import { load as backupLoad, save as backupSave, remove as backupRemove, isAnchorGroupIntact } from './chatStreamPersistence';
import { sendStreamRequest, resumeStreamRequest, listSessionTasks } from './chatStreamTransport';

const EMPTY_SNAPSHOT: SessionSnapshot = Object.freeze({
  serverTaskId: null, lastSeq: -1, executionSteps: [], currentResponse: '',
  metaFrames: emptyMetaFrames(), usageAccum: { prompt: 0, completion: 0, total: 0 },
  isReceiving: false, isConnected: false, status: 'idle' as StreamStatus,
  pendingAuthorization: null, reconnectStatus: 'idle' as const,
});

export interface ChatStreamSession extends SessionSnapshot {
  sessionId: string;
  revision: number;
  // 锚点组（5.2 落盘口径，四元组 + 接收中标记已在 SessionSnapshot 内）
  pendingMessage: { clientMessageId: string; content: string; state: 'queued' | 'sent' } | null;
  lastContextLinkMode: 'linked' | 'independent';
  hitlWaitingKeys: Set<string>;        // HITL 待确认请求属流状态，保证非激活视图/多 Tab 下弹窗与 confirmId 归属正确
  // 连接与定时器资源句柄
  abortController: AbortController | null;
  idleTimeout: number | null;
  firstChunkTimeout: number | null;
  reconnectTimeout: number | null;
  saveStepsTimer: number | null;
  intentionalAbortTimer: number | null;
  pollSignal: { aborted: boolean };
  reconnectAttempts: number;
  responseBuffer: string;
  isProcessing: boolean;
  intentionalAbort: boolean;
  lastDataTime: number;
  lastBizTs: number;
  heartbeatTs: number;
  pendingSteps: ExecutionStep[];
  flushScheduled: boolean;
  pumpActive: boolean;                       // 读循环单飞标志，防双 pump
  resumeInFlight: boolean;                   // 恢复单飞标志，防重复 resume 建双 GET
  // 订阅与快照
  snapshot: SessionSnapshot;
  listeners: Set<() => void>;
  eventListeners: Set<(e: StreamEvent) => void>;
  /** 无人订阅回收的宽限起点（epoch ms）；null 表示当前有订阅者 */
  releasedAt: number | null;
}

const sessions = new Map<string, ChatStreamSession>();

/** 唯一写入口：一切字段变更经此函数，尾随快照重建与订阅通知（SLAP：transport 只调 commit，不直写字段） */
export function commit(s: ChatStreamSession, fn: (d: ChatStreamSession) => void): void {
  fn(s);
  bump(s);
}

/** 快照重建与订阅通知；不合成事件，事件只由 emitEvent 按真实帧发出 */
function bump(s: ChatStreamSession): void {
  s.revision += 1;
  s.snapshot = {
    serverTaskId: s.serverTaskId, lastSeq: s.lastSeq,
    executionSteps: s.executionSteps, currentResponse: s.currentResponse,
    metaFrames: s.metaFrames, usageAccum: s.usageAccum,
    isReceiving: s.isReceiving, isConnected: s.isConnected, status: s.status,
    pendingAuthorization: s.pendingAuthorization, reconnectStatus: s.reconnectStatus,
  };
  s.listeners.forEach((cb) => cb());
}

/** 真实帧事件投递：kind 按 5.3 WIRE_KIND 归一化；无帧不投递 */
export function emitEvent(s: ChatStreamSession, kind: StreamEvent['kind'], payload: StreamEvent['payload']): void {
  const e: StreamEvent = {
    seq: s.lastSeq, taskId: s.serverTaskId, sessionId: s.sessionId,
    kind, payload, revision: s.revision, occurredAt: Date.now(),
  };
  s.eventListeners.forEach((cb) => cb(e));
}

export const chatStreamStore = {
  /** 显式创建；getSnapshot 路径绝不创建（5.1 实现约束 + 4.6.1①） */
  ensureSession(sessionId: string): ChatStreamSession {
    let s = sessions.get(sessionId);
    if (s) return s;
    s = {
      sessionId, revision: 0, ...EMPTY_SNAPSHOT,
      pendingMessage: null, lastContextLinkMode: 'independent', hitlWaitingKeys: new Set(),
      abortController: null, idleTimeout: null, reconnectTimeout: null,
      firstChunkTimeout: null, saveStepsTimer: null, intentionalAbortTimer: null,
      pollSignal: { aborted: false }, reconnectAttempts: 0, responseBuffer: '',
      isProcessing: false, intentionalAbort: false, lastDataTime: 0, lastBizTs: 0, heartbeatTs: 0,
      pendingSteps: [], flushScheduled: false,
      pumpActive: false, resumeInFlight: false,
      snapshot: EMPTY_SNAPSHOT, listeners: new Set(), eventListeners: new Set(),
      releasedAt: null,
    };
    sessions.set(sessionId, s);
    return s;
  },

  hasSession: (sessionId: string) => sessions.has(sessionId),

  /** 返回缓存引用；session 不存在时返回冻结空快照，不惰性创建 */
  getSnapshot(sessionId: string): SessionSnapshot {
    return sessions.get(sessionId)?.snapshot ?? EMPTY_SNAPSHOT;
  },

  subscribe(sessionId: string, listener: () => void): () => void {
    const s = this.ensureSession(sessionId);
    s.listeners.add(listener);
    s.releasedAt = null;                    // 有订阅者 → 取消回收计时
    return () => {
      s.listeners.delete(listener);
      if (s.listeners.size === 0 && s.eventListeners.size === 0) {
        this.releaseUnsubscribed(sessionId);   // 最后一个订阅者离开即起宽限计时
      }
    };
  },

  subscribeEvents(sessionId: string, listener: (e: StreamEvent) => void): () => void {
    const s = this.ensureSession(sessionId);
    s.eventListeners.add(listener);
    s.releasedAt = null;
    return () => s.eventListeners.delete(listener);
  },

  /** 先落盘 queued 再 POST；taskId 落定后置 sent（5.4 约束：禁止无持久化直接 POST）；
      POST 前先查同会话活动任务：另一浏览器标签已起任务则直接附着（只读跟随，不发第二 POST） */
  async sendMessage(sessionId: string, content: string, mode: 'linked' | 'independent' = 'independent'): Promise<void> {
    const s = this.ensureSession(sessionId);
    const clientMessageId = crypto.randomUUID();
    commit(s, (d) => { d.pendingMessage = { clientMessageId, content, state: 'queued' }; });
    this.persistNow(sessionId);
    const live = await listSessionTasks(sessionId);
    const active = live.tasks.find((t) => t.status === 'executing' && t.user_input === content);
    if (active && active.task_id !== s.serverTaskId) {
      commit(s, (d) => {
        d.serverTaskId = active.task_id;
        d.pendingMessage = null;
        d.status = 'active';
      });
      this.persistNow(sessionId);
      await resumeStreamRequest(s);
      return;
    }
    const taskId = await sendStreamRequest(s, clientMessageId, content, mode);
    commit(s, (d) => {
      if (d.pendingMessage?.clientMessageId === clientMessageId) {
        d.pendingMessage = { ...d.pendingMessage, state: 'sent' };
      }
      d.serverTaskId = taskId;
      d.status = 'active';
    });
    this.persistNow(sessionId);
  },

  /** 恢复状态机（5.4）：LEGACY / PENDING_NO_TASK / ACTIVE / GET_* / STOP_RACE 全部在此分派 */
  async resume(sessionId: string): Promise<ResumeResult> {
    const s = this.ensureSession(sessionId);
    const restored = await this.restore(sessionId);
    if (restored === 'invalid') { commit(s, (d) => { d.status = 'idle'; }); return 'idle'; }
    if (restored === 'legacy' || (restored === 'ok' && !s.serverTaskId)) {
      return this.recoverWithoutTaskId(s);      // 不自动 POST，按 5.4 走查重附着
    }
    return resumeStreamRequest(s);                 // ACTIVE + GET_* 分支
  },

  async recoverWithoutTaskId(s: ChatStreamSession): Promise<ResumeResult> {
    const tasks = await listSessionTasks(s.sessionId);          // GET /sessions/{id}/tasks
    const same = tasks.find((t) => t.status === 'executing' && t.user_input === s.pendingMessage?.content);
    if (same) {                                                // 同内容活动任务 → 附着，禁止二次 POST
      commit(s, (d) => {
        d.serverTaskId = same.task_id;
        d.pendingMessage = null;
      });
      this.persistNow(s.sessionId);
      return resumeStreamRequest(s);
    }
    commit(s, (d) => { d.status = 'idle'; });                   // 交还显式待发草稿，由用户确认后只发一次
    return 'pending_draft';
  },

  async stop(sessionId: string): Promise<void> {
    const s = this.ensureSession(sessionId);
    if (!s.serverTaskId) return;
    const r = await cancelTask(s.serverTaskId, s.sessionId);
    if (r === 'already_terminal') {                             // STOP_RACE：任务已自然完成
      this.clearCompleted(sessionId);                           // 视为终态确认，不报错不重试
      return;
    }
    commit(s, (d) => { d.status = r.status; });                 // 以回读终态为准，禁止强写 cancelled
    this.persistNow(sessionId);
  },

  clearCompleted(sessionId: string): void {
    const s = sessions.get(sessionId);
    if (!s || !['completed', 'failed', 'cancelled'].includes(s.status)) return;
    s.abortController?.abort();
    s.abortController = null;
    clearTimeout(s.idleTimeout); clearTimeout(s.reconnectTimeout);
    s.idleTimeout = s.reconnectTimeout = null;
  },

  clearSteps(sessionId: string): void {
    const s = sessions.get(sessionId);
    if (!s) return;
    commit(s, (d) => { d.executionSteps = []; d.currentResponse = ''; d.pendingSteps = []; });
    this.persistNow(sessionId);
  },

  setReceiving(sessionId: string, v: boolean): void {
    const s = sessions.get(sessionId);
    if (!s || s.isReceiving === v) return;
    commit(s, (d) => { d.isReceiving = v; });
    this.persistNow(sessionId);
  },

  setServerTaskId(sessionId: string, taskId: string): void {
    const s = sessions.get(sessionId);
    if (!s || s.serverTaskId === taskId) return;
    commit(s, (d) => { d.serverTaskId = taskId; });
    this.persistNow(sessionId);
  },

  /** 钟面信号：lastBizTs/lastDataTime 以 getter 桥接 session 数字字段（heartbeatTs 直接读值），
      保持 ref 语义稳定，供 waitClock 与 7.3.3 等待感知消费（5.6 迁移纪律第 3 条） */
  getClockSignals(sessionId: string): ClockSignals {
    const s = this.ensureSession(sessionId);
    return {
      lastBizTsRef: {
        get current() { return s.lastBizTs; },
        set current(v: number) { s.lastBizTs = v; },
      } as MutableRefObject<number>,
      lastDataTsRef: {
        get current() { return s.lastDataTime; },
        set current(v: number) { s.lastDataTime = v; },
      } as MutableRefObject<number>,
      heartbeatTs: s.heartbeatTs,
    };
  },

  /** 宽限期后只释放客户端资源：不 cancel、不停任务、不删快照（4.6.2 红线）；
      终态快照再经终态 TTL 后删条目（sessionStorage 备份不受影响，重开按 5.2 恢复） */
  releaseUnsubscribed(sessionId: string, graceMs = 60_000): void {
    const s = sessions.get(sessionId);
    if (!s || s.listeners.size > 0) return;
    s.releasedAt = Date.now();
    setTimeout(() => {
      const cur = sessions.get(sessionId);
      if (!cur || cur.listeners.size > 0 || cur.releasedAt === null) return;
      cur.abortController?.abort();
      cur.abortController = null;
      clearTimeout(cur.idleTimeout); clearTimeout(cur.reconnectTimeout);
      cur.idleTimeout = cur.reconnectTimeout = null;
      logger.info(`[Store] 无人订阅宽限期到，释放客户端资源 session=${sessionId}（任务未停，条目保留）`);
      if (['completed', 'failed', 'cancelled'].includes(cur.status)) {
        setTimeout(() => this.evictSession(sessionId), 600_000);   // 终态条目 10 分钟后删，防 Map 无限增长
      }
    }, graceMs);
  },

  /** 删除内存条目：只删 Map entry，不删 sessionStorage 备份，不碰后端任务 */
  evictSession(sessionId: string): void {
    const cur = sessions.get(sessionId);
    if (!cur || cur.listeners.size > 0) return;
    if (!['completed', 'failed', 'cancelled', 'idle'].includes(cur.status)) return;
    sessions.delete(sessionId);
  },

  persistNow(sessionId: string): void { backupSave(this.toBackup(sessionId)); },
  async restore(sessionId: string): Promise<'ok' | 'legacy' | 'invalid'> {
    const raw = backupLoad(sessionId);
    if (!raw) return 'invalid';
    if (raw.version !== 2) {                                    // RESTORE_LEGACY_BACKUP：只读保留 steps
      const s = this.ensureSession(sessionId);
      commit(s, (d) => {
        d.executionSteps = (raw as { steps: ExecutionStep[] }).steps ?? [];
        d.lastSeq = -1;
      });
      this.persistNow(sessionId);                               // 立即回写 v2，legacy 分支此后不命中
      return 'legacy';
    }
    const s = this.ensureSession(sessionId);
    const b = raw as StreamBackup;
    if (!isAnchorGroupIntact(b)) return 'invalid';   // 锚点组非同一快照即丢弃，走历史加载
    commit(s, (d) => Object.assign(d, {
      serverTaskId: b.taskId, lastSeq: b.lastSeq, executionSteps: b.steps,
      currentResponse: b.currentResponse, metaFrames: b.metaFrames,
      usageAccum: b.usageAccum, isReceiving: b.isReceiving, isConnected: b.isConnected,
      status: b.status, pendingAuthorization: b.pendingAuthorization,
      pendingMessage: b.pendingMessage, hitlWaitingKeys: new Set(b.hitlWaitingKeys ?? []),
      lastContextLinkMode: b.lastContextLinkMode,
    }));
    return 'ok';
  },

  /** 生成不可变备份快照：lastSeq 与 steps 必须来自同一 revision（5.6 原子性要求） */
  toBackup(sessionId: string): StreamBackup {
    const s = this.ensureSession(sessionId);
    return {
      version: 2, revision: s.revision, sessionId: s.sessionId,
      taskId: s.serverTaskId, lastSeq: s.lastSeq,
      steps: [...s.executionSteps], metaFrames: s.metaFrames,
      currentResponse: s.currentResponse, usageAccum: { ...s.usageAccum },
      isReceiving: s.isReceiving, isConnected: s.isConnected, status: s.status,
      pendingAuthorization: s.pendingAuthorization,
      hitlWaitingKeys: [...s.hitlWaitingKeys],
      pendingMessage: s.pendingMessage, lastContextLinkMode: s.lastContextLinkMode,
      updatedAt: Date.now(),
    };
  },
};
```

#### 5.6.1 迁移承接：`resume()` 恢复状态机（实现在 5.4 `chatStreamStore.resume`）

```text
RESTORE_INVALID
  → 丢弃快照，初始化历史，status=idle

RESTORE_LEGACY_BACKUP（现存 sessionStorage 为旧格式）
  → 旧格式为裸 `ExecutionStep[]` 或 `{steps, source, timestamp}`，无 taskId/lastSeq
  → 迁移策略：保留 steps 用于**只读展示**，taskId/lastSeq 置空（-1），
     按 RESTORE_PENDING_NO_TASK 处理并走同会话活动任务查重附着；禁止直接丢弃用户已见步骤
  → 迁移成功后立即以 version=2 原子快照回写，legacy 分支此后不再命中

RESTORE_PENDING_NO_TASK + pendingMessage.state = queued
  → 不自动 POST，不创建隐式任务
  → 先查同会话活动/最新任务：若存在同内容且创建于最近 300 秒内的活动任务，直接附着该 task，进入 RESTORE_ACTIVE，禁止再次 POST，并立即把 pendingMessage 置 null 再持久化
  → 否则将 pendingMessage 恢复为显式待发草稿，并显示“尚未发送”
  → 用户确认后只发送一次；taskId 落定后立即把 state 改为 sent 并持久化

RESTORE_ACTIVE + taskId + lastSeq
  → 校验 sessionId/taskId
  → GET /chat/stream/{task_id}?session_id=...&after_seq={lastSeq + 1}
   → 合并新帧并推进 lastSeq（合并规则见 5.2，含 executionSteps 去重）
  → 收到 final / final_stats 终态事件：立即 persistNow，status=completed
  → reader 结束但**未见终态事件**（断流/缓冲回收/后端重启均可能）：
       禁止直接置 completed（终态权威是后端 `chat_tasks.status`，见 3.10.1；前端不得自行推断终态）
       → 查 GET /sessions/{session_id}/tasks 的该 task 状态：
            已终态 → status 置对应终态并 persistNow，加载历史终态内容
            非终态/查不到 → status=recovering，转入 GET_NOT_FOUND 同族核对，
                            由历史降级或再次 resume 决定，禁止伪造完成、禁止立即重发

GET_NOT_FOUND
  → P1/P2：查询任务/会话最终状态并加载历史
  → P3：若 Journal 有终态事件，按 seq 回放；终态缺失但 chat_tasks 已终态，走 GET_TASK_STATE_INCOMPLETE
  → 未找到或后端重启且无 Journal：清理无效快照，加载历史，status=failed 或 recovering（按上条核对结果二选一，禁止无依据直接置 failed）

GET_TASK_INTERRUPTED（后端 task_interrupted 事件：Journal 有部分事件、任务非终态、后端已重启）
  → 禁止重发、禁止附着到新任务；status=recovering
  → 加载 DB 历史已落库部分，UI 提示"任务在后端重启前中断，未完成部分不会自动续算"
  → 用户显式重发才建新任务（新 taskId，不复用旧 seq 基线）

GET_TASK_STATE_INCOMPLETE（对应 3.7 第 5 条，Journal 有事件但无终态）
  → 禁止当正常完成、禁止当失败弹错
  → 查 chat_tasks.status：已终态 → 置对应终态并加载历史；仍非终态 → status=recovering，
     提示"事件不完整，正在核对任务状态"，按退避重试核对，超过阈值仍非终态才降级历史

GET_PERSISTENCE_GAP（对应 3.7.1，Journal seq 跳跃）
  → 记录缺口范围，status=recovering，UI 标注"部分事件不可恢复"
  → 允许继续接收后续帧，但禁止宣称完整回放；终态一律以 chat_tasks.status 为准

GET_PERSISTENCE_DEGRADED（对应 3.5 第 6 条，Journal 写失败但实时流继续）
  → 实时流继续消费，status 不改；仅置"恢复能力不可用"标记并落日志
  → 用户侧提示"部分过程无法在刷新后恢复"，不得静默、不得弹错误遮罩

STOP_RACE（点停止时任务已自然完成/已取消）
  → cancel 返回"已结束/不存在"时，视为终态确认，改走 clearCompleted 释放资源，**不得报错、不得重试 cancel**
  → cancel 成功但回读到新终态（如 failed）时以回读终态为准，禁止强写 cancelled

PAUSED/RETRYING/HITL
  → 保留 taskId、isReceiving 和 HITL 状态
  → 继续按同一任务恢复，不重新 POST
```

禁止在恢复状态未确定时同时执行初始化历史、重新 POST 或清空旧快照；所有状态转移必须幂等，重复 `resume()` 不得建立两条 GET 连接。

`sendMessage()` 必须先把 `clientMessageId + content + queued` 持久化，再发起 POST；POST 成功并拿到 `taskId` 后，必须把同一条 `clientMessageId` 标记为 `sent`。禁止无持久化直接 POST，禁止同一 `clientMessageId` 发送两次。

| P4 超 300s | 窗口外 | P1/P2：GET 返回 `not_found` 后进入明确历史恢复态，不永久接收中；P3 后：Journal 按 seq 回放 | M1 M7 |
| P5 原子快照 | 一致性 | 快照 `lastSeq` 与 `steps` 同属一个 `revision`；终态不被 5 秒防抖吞掉 | M6 |
| P6 关闭≠停止 | 红线 | 关视图后任务继续、重开可见后续；停止才调 cancel；关视图零 abort/clear/删备份 | M1 M5 |
| P7 快照安全 | 渲染 | 无 `useSyncExternalStore` 无限渲染警告；快照引用仅 `revision` 变化时更换 | — |
| P8 恢复失败族 | 状态机 | 覆盖 paused/error/cancelled/completed/not_found/task_interrupted/task_state_incomplete/gap/degraded：无重复步骤、无永久 loading | M7 |
| P9 无 taskId 恢复 | 边界 | 不自动 POST、显式"尚未发送"；同内容活动任务只附着不重发；`clientMessageId` 不发两次 | M1 M6 |

### 6.4 执行检查（每 case 必做，顺序不可颠倒）

1. **异常检查（最高优先级）**：后端 `backend/logs/` 无 traceback/ERROR；前端控制台无未捕获异常；SSE 无 `error` 事件 → 有则**立即停**，先修再继续。
2. **调用链分析**：输出 `[CALL CHAIN]`（工具选择/顺序/LLM 次数）；确认切换后**无第二次 POST**；若有 GET 续传则 `after_seq` 连续且不回放已显示步骤。
3. **参数正确性**：续传 URL 的 `task_id` 与 `start` 帧一致、`session_id` 正确。

### 6.5 通过标准（放行判定）

- P1~P3 全过；P4~P9 不得出现重复任务、重复步骤、永久接收中或静默丢失；
- 切走期间产生的步骤（thinking/action/observation/final）切回后**可见且不重复**；
- 刷新恢复通过 seq 单调性校验（M6），`lastSeq` 与 `steps` 来自同一 revision；
- **F7 已闭环**：`__initCount` 切回后不增（M3），否则视为未完成；
- 关闭视图不停止任务；停止任务必须先完成后端 cancel 确认，且 `STOP_RACE`（任务已自然完成）不报错；
- 全程每 session 仅 1 个 taskId、1 次 POST；
- 18 项改造清单（5.1~5.18）全部落地并逐项可追溯；HITL 请求只有 Store 一个来源（5.15）；
- 10 大规范三堂会审通过：无状态双源、无第二套解析器、无透传函数、无无效抽象、无向后兼容分支。

### 7.1 现状问题分析（P1 实施前的代码事实）

#### 7.1.1 当前导航结构：页面级菜单，同一时刻只显示一个会话

左侧菜单（`Layout/index.tsx:402-467`）共 6 个功能菜单项（另有 2 个分隔线），真实可导航的路由页只有 3 个：

#### 7.1.2 会话切换机制：URL 参数 + 重新初始化，无并行

会话之间不存在"多个同时打开"，切换靠 URL + 全新初始化：

| 场景 | 动作 | 代码 |
|------|------|------|
| 进入 `/`（无 session_id） | 自动加载**最新会话** | `useChatSession.ts:206` 场景3 → `loadLatestHistoryMessages`（`chatHistory.ts:163-169`） |

**结论**：一次永远只有一个会话处于"当前显示 + 持有实时流"状态；会话切换＝换 URL 重新初始化，旧会话的实时流状态随之让位。

#### 7.1.3 与 [63] 问题的关系（方向不同）

### 7.2 可行性结论：能否支持与依据

**结论：第 2~6 章（尤其第三章 P3 Journal 与第四/五章 P1/P2）交付完成后具备实施条件，本章随之实施；不承诺在此之前开工。** 依据分三层：

| **会话视图（`ChatSessionView`）** | 消息历史、会话标题、`tasks` / `latestTaskId` / `total`（REST 拉取）、`activeTaskId` / `selectedDetail` 派生、输入草稿（编辑态在视图，落盘经 5.2 `saveDraft`/`loadDraft` per-session 持久化，卸载不丢）、滚动位置、DOM 锚点、面板可见性、`liveElapsed` 计时、钟面 `beatTick`、`liveError` | 历史与任务列表属业务数据而非流运行时，留在视图；视图与 Store 通过 `serverTaskId` 对齐，禁止把 REST 结果写回 Store 形成第二真源 |
| **Tab 层（`ChatTabsBar`）** | 各 Tab 的标题与运行态点 | 徽标在 **`ChatTabsHost` 单点聚合**：`isRunning/badge` 由 `useChatStreamSession(sessionId)` 快照派生 + 激活视图上报的会话标题/任务数汇总而成；**禁止**让 N 个非激活视图各自上报（重复计算），更**不得**为显示红点而常驻全量会话视图 |
| **禁止** | 在 `ChatSessionView` 内新建 `useSSE`（已在 5.1~5.4 删除）/ `useChatStreaming` / `useSessionTasks` 级独立资源 | 见 7.7 第 1 条 |

#### 7.3.4 生命周期要点（防重蹈 [63] 覆辙）

- **切 Tab ≠ 停止流**：Store 持有流，切 Tab 只切换哪个视图可见，流照跑；
- **切 Tab 改 URL 不得触发会话重初始化**：`?session_id=` 变化原本走"重新初始化该会话"链（P1 前会清 step/重载历史/断流），实施时必须由 `ChatTabsHost` 拦截标签引起的 URL 写入并置 `switchSource='tab'`，`useChatInit`（`useChatInit.ts:22-66`，5.1 之外新增改动，见 7.3.2 第 7 行）见到该标记**跳过重初始化**（缺此项一切换就断流）；`useChatInit` 消费标记后立即用 `replaceState` 从 URL 摘除 `switchSource`，刷新不携带、不误跳过；**浏览器前进/后退走同一 `openSessionTab` 通道**（7.3.2 第 8 行），同样不得触发重初始化；
- **同 session 只允许一个 Tab**：`openSessionTab(sessionId)` 对已打开项只做"激活"，绝不新建第二个视图；否则同一 Store 流被两视图消费，出现双输入框、滚动互踢与重复起任务；
- **关闭 Tab**：移除视图，**不调用** `clear()`、不 abort、不删 sessionStorage；是否停任务只由用户点"停止"决定；
- **关闭后无人认领的流必须回收**：若某 session 被关闭且不再重新打开，其流在"宽限期"（默认 60s，可配）内无人订阅则释放连接与定时器，Store 条目转入终态快照；否则长开会积累 fetch + 重连定时器，是资源泄漏口；
- **关闭最后一个 Tab**：自动新建一个空会话 Tab，不出现空白页或死路由；
- **刷新页面（多 Tab 口径）**：Store 内存态丢失后，**集合内每个已打开 session 各恢复自己的原子快照**（5.2 的 `sse_execution_steps_backup_v2_{sessionId}` 快照按 sessionId 逐个恢复，5.2 的单会话口径是它的特例）；集合顺序与激活项从 `chat_tabs_collection`（`order` + `activeId`）恢复，激活项以 URL 指向的会话为准（URL 优先于持久化，二者冲突以 URL 为准）；恢复后集合中仍有活动的 session 必须在标签栏显示其运行态。**两个 key 必须分离**（7.3.2 第 9 行），互相覆盖即视为实现错误。

```
· 历史页"继续"  → 顶部自动新增一个 Tab 打开该会话（不再跳转换页）
```

1. **禁止视图内实例化流**：`ChatSessionView` 及其子组件一律不得直接调用 `useSSE`（**注意：该 hook 已在 5.1~5.4 整体删除，本章不得再引用它**）/`useChatStreaming` 的独立实例，也不得自建 `useSessionTasks` 级独立资源；流、任务、授权数据只能经 `useChatStreamSession(sessionId)` 从 Store 读取。这是 7.1.2「每 session 仅 1 个 task id、1 次 POST」的落地保证。
2. **禁止改写流内核语义**：多会话层只做"订阅与显示"，不得改动 5.1~5.4 迁入后的 `chatStreamTransport` 的重连、退避、`after_seq`、轮询观察、错误分类逻辑。
3. **禁止双写**：视图不得再 `setExecutionSteps` / `setIsReceiving` / `setServerTaskId`（Store 动作为唯一写入口），只读快照 + 订阅。
4. **禁止把 `default-session` 当 Store key**：必须真实 `sessionId`。
5. **禁止隐式全局事件**：跨模块通信只用显式回调/Context（弃用 CustomEvent）。
6. **禁止 `destroyInactiveTabPane={false}` 式全量保活**：非激活会话视图懒挂载且只保 Store，不保多份 DOM 与定时器；antd Tabs 只用作视觉容器，会话视图由自维护集合控制挂载。
7. **禁止在第 2~6 章未交付时开工**（7.5 时序门）：P1 是数据前提，第三章 Journal 是恢复前提，且两者与本章争用同一批核心文件（前端 5.1~5.4 新增的 `chatStreamTransport`/`chatStreamStore`/`useChatStreamSession` 等与 `useChatStreaming`/`useChatFacade`，后端 `agent_runner`/`stream_orchestrator`），未交付即开工会造成回归无法归因。
8. **禁止把标签集合/激活项塞进 `chatStreamStore`**：集合与激活项是视图编排态，只放 `ChatTabsHost` + `chat_tabs_collection`（5.2 设计要点 SRP / 7.3.3 边界）；塞进 Store 即造成"刷新后集合与流一起被 5.2 快照覆盖"的错乱。
