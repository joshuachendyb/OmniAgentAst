## 一、问题描述

> 编写人：小欧 2026-09-22 20:38:55

### 1.1 现象

会话页（`/`）实时任务执行中（SSE 正流式推送 Step），用户切换到**历史页**（`/history`）或**设置页**（`/settings2`），再切回会话页时：

1. 实时 Step（thinking/工具调用/执行结果/最终回答）**不续传**；
2. 切走期间产生的中间步骤**看不到**；
3. 若任务在切走期间已完成，回来只能看到**最终落库结果**，中间过程丢失；若任务还在跑，回来是**全新初始化**，不会自动接上正在跑的流；
4. 来回快速切换，每次进入会话页都触发一次重新初始化（重新拉历史、重建连接），实时进度 UI 反复跳变。

### 1.2 影响范围

- 用户在实时任务运行中去历史页核对另一会话、去设置页调整配置，是**高频真实操作**；
- 当前行为实质是"切走即杀掉前端实时流"，与「任务后台继续跑」的预期（后端确实在跑，[51]已实证）割裂，用户感知为"实时 step 丢了"。

### 1.3 问题结论先行

**切换页面 = ChatPage 组件被卸载 → SSE 连接 abort → 步骤备份被删 → 切回全新初始化。** 不是"影响"，是"中断且不续传"。

## 二、问题的根本原因

> 编写人：小欧 2026-09-22 20:38:55

### 2.1 根因链（现状代码实证）

| # | 根因 | 证据位置 | 说明 |
|---|------|---------|------|
| R1 | 路由切换即卸载组件 | `App.tsx:57-73` `<Routes>` 单匹配渲染，`/history`/`/settings2` 匹配时 ChatPage 卸载 | 三个页面是独立路由路径，非同页 Tab |
| R2 | SSE 生命周期 = 组件生命周期 | `useSSE.ts:442-557` 全部状态 useState/useRef；仅 ChatPage 内部经 `useChatFacade`→`useChatStreaming` 调用 | 无模块级 SSE 单例，无 Context 承接 |
| R3 | 卸载 cleanup 三个破坏性动作 | `useSSE.ts:1231-1246` → `disconnect()`（默认 `clearStorage=true`）→ `clearStepsFromStorage()` 删备份（`useSSE.ts:688-690`）+ `abortController.abort()`（695-713）；`pendingMessageRef=null`（1238）；停轮询（1236） | 把唯一可恢复的数据源一并销毁 |
| R4 | 续传锚点全部是组件内存态 | `serverTaskId`(525-527)、`lastSeqRef`(546)、`pendingMessageRef`(550-553)、`lastContextLinkModeRef`(555-557) 均为 ref，卸载即失 | 备份 envelope（`useSSE.ts:465-469`）只有 `{steps, source, timestamp}`，无 task_id/seq/待发消息 |
| R5 | `isReconnect` 续传守卫绑定本实例重连计数 | `useSSE.ts:806-814` 要求 `reconnectAttemptsRef>0` + `serverTaskIdRef` 非空；新 mount 恒为 0 | 即使有 taskId 也只走 POST **重新发起新任务**，无法走 GET 续传（`useSSE.ts:830-840`） |
| R6 | mount 恢复 effect 只回填 steps，永不建连 | `useSSE.ts:595-623` 从备份读 steps 回填，不主动发 GET | 切回后"有数据可看"但"不会续接进行中的流" |
| R7 | 后端续传源是**内存缓冲且有时限** | `task_state.py:42-56` `event_log`；`agent_runner.py:761-765` 任务结束 300s 回收 | 切走超过 300s 或后端重启，after_seq 续传数据源即失 |

### 2.2 本质

**"正在进行的会话流"（In-Flight Session Stream）不是一个独立的一级状态实体**，它被绑定在 ChatPage 组件实例的 hook 生命周期上。UI 组件可以卸载重挂，但"流"是后台正在跑的东西，二者生命周期必须解耦。当前代码把所有鸡蛋放在组件实例一个篮子里，卸载即一切归零。

### 2.3 与既有能力的落差

| 既有能力 | 现状 | 落差 |
|---------|------|------|
| 后端 `GET /chat/stream/{task_id}?after_seq=N` 续传 | 已存在且幂等（`chat_routes.py:116-122`，e2e 已验证多客户端多轮续拉） | 前端没有保存续传所需的 (task_id, seq) |
| 前端 steps 备份 | 已存在（`useSSE.ts:456-478`，完整 `ExecutionStep[]`） | 卸载时被 `disconnect()` 默认删除（R3） |
| 后端按 session 找任务 | `GET /sessions/{id}/tasks` 返 `latest_task_id` | 可作为切回后定位任务兜底 |
| 历史拉取中间步骤 | `GET /sessions/{id}/messages` 含完整 execution_steps | 仅任务完成后可用，运行中任务不在 DB |

结论：**后端能力基本够，卡点在"前端把流锁死在组件实例 + 卸载时把恢复数据源删了"**。因此架构重心在前端会话流全局化，后端只做可选增强（延长缓冲窗口/持久化）。

## 三、解决策略分析及方案优劣说明

> 编写人：小欧 2026-09-22 20:38:55

### 3.1 候选方案总览

| 方案 | 一句话 | step不断 | 切回即时 | 改动范围 | 稳定性 | 扩展性 |
|------|--------|---------|---------|---------|--------|--------|
| A 全局 Context 硬搬 | 把 useChatFacade 整个搬进全局 Provider | 完全不断 | 即时 | 大 | 中（双源风险） | 中 |
| B keep-alive 隐藏不卸载 | ChatPage 改 `display:none` 常驻，绕过 Router 卸载 | 完全不断 | 即时 | 中（路由层） | 中（对抗 Router 语义） | 低 |
| C 持久化续传（补丁式） | 存四元组+卸载保留备份+重挂载发 GET | 断后≤300s续 | 需一次GET | 小（useSSE 内） | 高 | 低（单会话单文件） |
| **D 会话流 Store 架构（本方案）** | **流提升为全局独立 Store，多会话订阅，卸载只解绑不销毁，刷新靠持久化+续传双保险** | **完全不断** | **即时** | **中** | **高** | **高（多会话/历史页实时化天然扩展）** |

### 3.2 方案 A：全局 Context 硬搬

**做法**：仿 `AppContext` 再加 `ChatStreamProvider`，把 `useChatFacade` 整体搬进去，卸载组件不卸载 Provider。

**问题**：
- `ChatPage.tsx:74-76` 的 `onError`/`onSuccess` 是 ChatPage 私有闭包回调，全局化后必须改事件通道，隐性改造大；
- useChatState 的 DOM ref（`messagesEndRef` 等）与 UI 强耦合，全局持有造成"UI 状态 / 流状态双源并存"，违背单一职责；
- 每次 `setMessages` 触发整棵 Provider 树重渲染，与"三页面独立渲染"冲突。

**结论**：伤筋动骨且设计不整。**不采用。**

### 3.3 方案 B：keep-alive 隐藏不卸载

**做法**：ChatPage 移出 `<Routes>`，按 `location.pathname` 用 `display:none` 切换；历史/设置页正常卸载。

**优点**：改路由一层，SSE 完整不断，切回 0 延迟。

**问题**：
- 与 React Router `<Routes>` 单匹配卸载语义**对抗**，需自建"活动面板"标记；
- URL `?session_id` 变化时 `useChatInit.ts:66` 仍会重跑初始化（依赖 `urlSessionId`）；
- 只解决"这一个页面"，历史页/多条会话/多任务并行时无扩展能力；
- 常驻隐藏页吞内存，属"绕过问题"而非"解决问题"。

**结论**：可用作过渡，但非扩展性架构。**仅作 D 的退化选项。**

### 3.4 方案 C：持久化续传（补丁式）

**做法**：`useSSE.ts` 内补四元组持久化 + 卸载 `clearStorage=false` + mount 伪装重连走 GET 续传。

**问题（短视所在）**：
- 只保当前这一个 hook 实例，代码内聚但仍是"组件内补丁"，流依然跟着组件走；
- 多会话、历史页实时化、多标签同步等后续需求无法演进，每次都要再打一层补丁；
- 300s 窗口是硬约束，超出即退化（但可接受）。

**结论**：**方向对、范围小，但作为"唯一方案"目光短浅。** 其续传逻辑可作为方案 D 的**底层能力**复用，而不是终结方案。

### 3.5 方案 D：会话流 Store 架构（推荐）

**核心思想**：
> 把「正在运行的会话流」从 ChatPage 组件实例中抽离，提升为**模块级全局单例 Store**（`Map<sessionId, ChatStreamSession>`）。SSE 连接、步骤、任务锚点由 Store 持有；组件只是**订阅者**。卸载组件=解绑订阅，流继续跑；重挂载=重新订阅即时拿快照。浏览器刷新（Store 丢失）由 sessionStorage 持久化 + GET after_seq 续传兜底。

**架构分层（三层防线）**：

| 层 | 防线 | 覆盖场景 |
|----|------|---------|
| L1 内存 Store | SSE 连接与状态全局常驻 | **路由来回切换（最常见）**：完全无缝 |
| L2 持久化+续传 | 锚点组(四元组+接收中标记)+steps 写 sessionStorage；mount 检测活动任务发 GET 续传 | **浏览器刷新/标签页冻结恢复**（300s 窗口内） |
| L3 DB 历史兜底 | 现有 `loadHistoryMessages` 加载最终结果 | 窗口外/后端重启：行为等同现状，不劣化 |

**设计要点（10 大规范对齐）**：
- **SRP**：Store 只管"流"（连接/步骤/任务锚点/订阅），消息历史、UI 状态（滚动、回复区）仍留在 ChatPage/useChatState，职责分明；
- **DRY**：会话流状态让 useSSE 与未来历史页实时化共用同一数据源，消除"每实例一套 ref 双写"；
- **OCP**：Store 按 sessionId 索引，天然支持多会话并行/历史页订阅实时流，新增消费者不必改 Store 内核；
- **禁止backward**：useSSE 对外接口（sendMessage/onStep/onComplete…）经薄适配层保留签名，消费者无感知切换，但内部实现整体迁移，不保留新旧两套路径。

### 3.6 方案 D 与 B/C 的关系

- **不做 B**：不需要 keep-alive，Router 正常卸载（组件与流解耦后，卸载无害，反而释放 DOM 内存）；
- **吸收 C**：L2 层的持久化+续传复用 C 的全部既有代码资产（steps 备份、GET 端点、300s 窗口），不重造轮子。

### 3.7 最终确定方案：方案 D 策略要点汇总（白话）

> 更新人：小欧 2026-09-22 20:49:51
> 本节用最直白的话，把最终确定的"方案 D：会话流 Store 架构"完整讲清楚——是什么、怎么改、改完什么效果、极端情况怎么办。

#### 3.7.1 一句话讲清方案本质

**把"正在跑的对话流"从聊天页组件上摘下来，放到一个常住后台的全局 Store 里；聊天页面只是"看屏幕的人"，切走页面不再等于拔掉电话线。**

#### 3.7.2 打个比方（帮助理解）

把现在的会话页想成"一个人同时当接线员＋显示器"：
- **现状**：你一转身（切换去历史页/设置页），整格人连人带桌子被撤走——电话线（SSE 连接）被拔断、贴墙的进度单（步骤备份）被撕掉。
- **方案 D**：把"接线员＋电话线＋进度记录"搬进楼下的**总机室**（全局 Store）常驻上班。聊天页面只负责"抬头看总机室传上来的大屏"（订阅显示）。
  - 你转身去别的房间 → 总机室电话照接、进度照记，**后台任务继续跑**；
  - 你走回来 → 大屏**立刻接着显示最新进度**，不用重新汇报、不用重新接线；
  - 只有你明确说"这条线不用了"（新建会话/手动停止任务）→ 才挂断清理。

#### 3.7.3 核心动作（改什么、不改什么）

| 动作 | 内容 |
|------|------|
| **新建** 1 个全局 Store（总机室） | `chatStreamStore.ts`——按会话 id 存当前流：SSE 连接、已收步骤、任务 id、最新 seq、待发消息、接收中标记。**一个总机室可同时管多条会话线**（多会话并行是白送的扩展能力） |
| **搬进去** SSE 全套逻辑 | 把现在 `useSSE.ts` 里"建连接/收帧/断线重连/续传"整套代码**复制**进 Store（遵守项目"能复制就复制、不重写"铁规），不改业务行为 |
| **聊天页面改为"只订阅"** | 新增 `useChatStreamSession(sessionId)` hook——页面挂载＝向总机室申请看这条线的屏；**页面卸载＝只看屏的人下线，电话线不断** |
| **反转卸载清理** | 现状：切走页面＝断线＋删进度单（`useSSE.ts:1231-1246`）。改为：切走页面＝只解除订阅；只有"显式离开会话/停止任务"才真正清理。**这是全方案最关键的 1 行行为反转** |
| **不动** 对外接口 | `useChatStreaming`/`useChatFacade`/`ChatPage` 的消费方代码签名不变（`sendMessage`/`onComplete`/步骤数组等照旧），改造内部、外部无感知过渡 |

#### 3.7.4 三层防线（回答"断了/刷新了/太久没回来怎么办"）

| 防线 | 管什么场景 | 效果 |
|------|-----------|------|
| L1 内存 Store | **切去历史页/设置页再切回来**（最常见） | 线不断，切回大屏**直接续显**，零等待、不重拉、不重建任务 |
| L2 持久化＋续传 | **浏览器按 F5 刷新、标签页被系统冻结恢复**（总机室也被端掉了） | 把步骤＋锚点组（任务id/最新seq/待发消息/上下文模式/接收中标记）先存进 sessionStorage；重挂载后自动按 `after_seq` 发 GET 补拉切走期间的新步骤（后端续传能力已有，300 秒窗口内有效） |
| L3 DB 历史兜底 | **超过 300 秒才回来 / 后端重启**（补拉也拿不到中间态） | 退回现有"加载历史最终结果"，行为与现在一致，**只可能变好、不会更差** |

> 关键认知：L1 解决的是"用户天天发生的切页"，L2/L3 是"各种意外断了之后的自救"。三层叠加，没有任何场景比现状更糟。

#### 3.7.5 用了哪些现有资产（不重造轮子）

- 后端 `GET /chat/stream/{task_id}?after_seq=N` 续传端点——**已经存在且被 E2E 验证过**，直接用；
- 前端 5 秒防抖的 steps 备份机制——**已经存在**，只补锚点组 5 个字段（任务id/最新seq/待发消息/上下文模式/接收中标记），不新写；
- 后端按会话找任务接口 `GET /sessions/{id}/tasks`——已经存在，作兜底定位；
- 现有历史加载 `loadHistoryMessages`——已经存在，作 L3 兜底。

#### 3.7.6 为什么这就是"稳定、可靠、可扩展、不短视"

- **稳定**：核心改动只有一处行为反转（卸载不再断流），其余是搬代码，业务逻辑照旧；
- **可靠**：三层防线逐级兜底，最坏情况退回现状，不会劣化；
- **可扩展（不短视的证据）**：Store 按会话 id 索引，未来**历史页实时看任务进度、多任务并行、多标签页同步、全后台任务通知**全部是同一个总机室的自然扩展，不用再推翻重来。方案 C 那样只改一个 hook 的补丁式做法，每次新需求都要再打补丁，所以淘汰为底层复用，不作为终结方案。

#### 3.7.7 落地节奏（分三步，每步都稳）

| 阶段 | 做什么 | 效果 |
|------|--------|------|
| P1 常驻化 | 建总机室 + 卸载改"只解绑" | 切页不断流、切回续显（解决 90% 痛点） |
| P2 持久化＋续传 | 补锚点组(四元组+接收中标记) + 刷新自动续拉 | 刷新也不丢实时步骤 |
| P3 后端增强（可选） | 拉长缓冲窗口/运行中即落库 | 长任务跨天也能恢复（远期规划，不阻塞） |

**结论（终极一句话）**：方案 D ＝ **把对话流的"家"从聊天页面搬进全局总机室常驻，页面只当显示器；切走断不了、刷新能自救、最坏不劣化，且为未来多会话/多页一定备好扩展位。**

### 3.8 前后逻辑流程对比：改的是什么流程（白话）

> 更新人：小欧 2026-09-22 20:56:49
> 明确回答"这是功能流程改变还是什么流程改变"：**改的不是功能流程，改的是三条"内功流程"——数据住哪、生命周期归谁、卸载时干什么。用户能看到的操作一个都没变。**

#### 3.8.1 现状（改前）的逻辑流程

```
【实时任务中】
发送消息 ──→ ChatPage 里 useSSE 自己建立连接(POST /chat/stream)
              │          收帧 → 写进"页面自己的" executionSteps (state+ref)
              └─→ UI 渲染 step

【切去历史/设置页】   ← 问题根源在这
ChatPage 被卸载
   └─→ useSSE 卸载清理(useSSE.ts:1231):
        ① disconnect() → abort 连接(电话挂了)
        ② 删 sessionStorage 步骤备份(进度单撕了)
        ③ pendingMessage=null(待发消息丢了)
   └─→ 页面里所有状态(executionSteps/taskId/seq) 随组件一起销毁
后端任务: 继续在服务端跑(内存缓冲累积)，但没有前端接收了

【切回会话页】  ← 全新白板
ChatPage 重新挂载 → useSSE 全新实例(所有 state 归零)
   └─→ 初始化: loadHistoryMessages 从 DB 拉最终结果
   └─→ 任务若已跑完: 看到最终答案，中间 step 没了
   └─→ 任务若还在跑: 看不到实时，也不会自动续上(重新 POST 会并发起新任务,被守卫拦)
```

**本质**：SSE 连接和步骤数据的"寿命 = 聊天页组件的寿命"。页面一卸载，连接和状态**跟着一起死**。

#### 3.8.2 方案 D（改后）的逻辑流程

```
【实时任务中】
发送消息 ──→ 全局 chatStreamStore 建立连接(POST)  ← 连接迁到"总机室"
              │          收帧 → 写进 Store 的 executionSteps
              └─→ 通知订阅者(ChatPage) → UI 渲染    ← 页面只是"看屏的人"

【切去历史/设置页】
ChatPage 被卸载
   └─→ 仅"解除订阅"(useSyncExternalStore 自动 unsubscribe)
   └─→ Store、连接、步骤、taskId/seq 全部保留，任务继续边跑边存
后端任务: 继续跑，Store 继续接帧累积

【切回会话页】
ChatPage 重新挂载 → 重新订阅 Store → 立即拿到当前快照(最新steps/taskId/接收中)
   └─→ UI 直接续显，零等待、不重拉、不重建任务

【极端: 刷新页面(Store 也没了)】
restore sessionStorage(锚点组+steps) → 检测到活动任务 → GET /chat/stream/{task_id}?after_seq=N 补拉
   └─→ 刷新也拿回切走期间的中间步骤

【再极端: 超300s/后端重启】→ 退回现有历史加载, 行为不劣化
```

**本质**：SSE 连接和步骤数据的"寿命 = 会话(任务)的寿命"，独立驻留全局 Store；卸载页面只是"看板下线"，流照跑。

#### 3.8.3 到底改的是哪种流程？——三改一不改

| 维度 | 改前 | 改后 | 属于什么改变 |
|------|------|------|------------|
| **状态/连接住哪** | 组件 hook 内(useSSE 每实例一套) | 全局 Store(按 sessionId 索引) | **数据驻留位置改变**（架构层） |
| **生命周期归谁** | 归 ChatPage 组件 | 归会话(任务) | **生命周期归属改变**（架构层） |
| **卸载时干什么** | 断开连接+删备份+清状态 | 只解绑订阅 | **卸载清理时机/动作改变**（行为层，全方案唯一行为反转） |
| **用户操作**(发消息/看step/取消/暂停/HITL/历史) | — | — | **零改变**（接口签名不变，消费方无感知） |

#### 3.8.4 一句话总结

**功能流程完全没变，变的是"谁来养这条流"**——从"跟着页面生死"改成"常驻后台、跟任务生死"；附带把"卸载＝销毁"这一个错误行为反转成"卸载＝只看屏的人撤了"。

## 六、多会话页面支持问题分析

> 编写人：小欧 2026-09-22 21:10:28

> 背景：北京老陈提问"现在的菜单是不是只支持一个会话页面？能不能同时有多个会话页面互相切换？这个问题与[63]实时step跨页面切换问题有关系吗？"。本章回答该问题，并给出"多会话并行"的现状、可行性、支持方案与 UI 修改点。

### 6.1 现状问题分析

> 编写人：小欧 2026-09-22 21:10:28

#### 6.1.1 当前导航结构：页面级菜单，同一时刻只显示一个会话

左侧菜单（`Layout/index.tsx:402-467`）共 6 个功能菜单项（另有 2 个分隔线），真实可导航的路由页只有 3 个：

| 菜单项 | 路由 | 状态 |
|--------|------|------|
| 对话任务 | `/` | **唯一的会话页面** |
| 文件管理 | `/files` | 禁用（即将上线） |
| 知识库 | `/knowledge` | 禁用（即将上线） |
| 历史会话 | `/history` | 独立页面 |
| 快捷指令 | — | 弹出面板（非路由） |
| 设置2版 | `/settings2` | 独立页面 |

- `<Routes>`（`App.tsx:63-69`）单匹配渲染：同一时刻只渲染一个页面组件；
- `/` 底下只有**一个** `ChatPage` 实例（`App.tsx:64`），不存在多个会话页并行。

#### 6.1.2 会话切换机制：URL 参数 + 重新初始化，无并行

会话之间不存在"多个同时打开"，切换靠 URL + 全新初始化：

| 场景 | 动作 | 代码 |
|------|------|------|
| 进入 `/`（无 session_id） | 自动加载**最新会话** | `useChatSession.ts:206` 场景3 → `loadLatestHistoryMessages`（`chatHistory.ts:163-169`） |
| 菜单点"对话任务" | `navigate('/')` → 场景3 加载最新会话 | `Layout/index.tsx:487` |
| 历史页点"继续" | `navigate('/?session_id=xxx')` → 场景1 重新初始化该会话 | `History/index.tsx:323` → `useChatSession.ts:241-258` |

**结论**：一次永远只有一个会话处于"当前显示 + 持有实时流"状态；会话切换＝换 URL 重新初始化，旧会话的实时流状态随之让位。

#### 6.1.3 与 [63] 问题的关系（方向不同）

| | [63] 实时 step 跨页面切换 | 本章 多会话并行 |
|---|---|---|
| 问题本质 | **切走页面**杀掉实时流（组件卸载 → SSE abort） | 不存在**多会话并行**的结构基础 |
| 涉及机制 | 组件卸载清理（`useSSE.ts:1231-1246`） | 单会话实例 + URL 重载（`useChatSession.ts:241-258`） |
| [63] 方案D作用 | 把"流"从组件剥离，切页/切会话不杀流 | **为多会话并行打下数据地基（Store 按 sessionId 索引），但不自动长出并行 UI** |

**一句话**：多会话并行是方案 D 落地后的**自然下一步扩展**，不是 [63] 要解决的内容；两者不能混淆导致 [63] 范围膨胀。

### 6.2 能否支持

> 编写人：小欧 2026-09-22 21:10:28

**结论：能支持。** 依据分三层：

| 层 | 现状 | 对多会话并行的支持度 |
|----|------|---------------------|
| **后端** | 会话/任务均按 `session_id` / `task_id` 隔离存储（`chat_history.db`，会话消息、`chat_task_steps` 均带 session_id）；SSE 按 task_id 独立 | ✅ **完全支持**——后端无共享全局状态，多会话并发任务互不干扰（[51] 已实证切走不杀任务） |
| **前端数据层（方案D后）** | Store 按 `sessionId` 索引存储多颗流（`Map<sessionId, ChatStreamSession>`，见 4.1） | ✅ **天然支持**——总机室可同时接多条线，各 session 独立累积 |
| **前端 UI 层（当前）** | 单实例 + URL 单会话 | ❌ **不支持**——UI 没有"多会话标签/多视图"结构，需要新增 |

**结论细化**：
- 数据层与后端**零阻碍**，方案 D 落地后"同时跑多个会话的实时任务"在 Store 层面完全成立；
- 缺的只是**UI 层并行视图**（一次能看到/切换多个打开的会话）；
- 因此"能支持"的答案 = **后端能 + 数据层能（方案D后）+ UI 需要新增**。

### 6.3 如何支持（方案）及 UI 修改点

> 编写人：小欧 2026-09-22 21:10:28

> 设计原则：复用方案 D 的 Store 多会话能力，UI 层只做"多标签并行显示"层，不碰流内核；符合 10 大规范（SRP：标签层只管视图集合；DRY：会话视图复用现有 `SessionLayout`；OCP：新增标签不改变 ChatPage 内核）。

#### 6.3.1 整体架构（在方案 D 之上叠加"多会话标签层"）

```
全局 chatStreamStore（方案D，按 sessionId 多颗流）──┐
                                                        │
[会话标签栏] Tab1: 会话A  (运行中●)   Tab2: 会话B (运行中●)   + (新建会话)
   │              │
   │  每个 Tab 内渲染一个「会话视图实例」＝现有 SessionLayout 内容（消息区+step面板+输入条）
   │  每个视图通过 useChatStreamSession(sessionId) 订阅 Store 对应流
   ▼
历史页"继续" → 不跳走，而是在标签栏新增/激活一个 Tab（打开该会话）
```

#### 6.3.2 需要修改哪些 UI（清单）

| # | 位置 | 改动 | 职责 |
|---|------|------|------|
| 1 | **新增** `ChatTabs` 组件（标签栏） | 放于 ChatPage 顶部或 SessionLayout 上层：显示已打开会话 Tab（标题/运行中●/关闭×）+ 新建按钮 | 多会话视图的"容器与导航" |
| 2 | `ChatPage.tsx` | 由"单会话实例"改为"多会话 Tab 管理器"：持有打开会话集合 `{id, title, sessionId}[]`；按 URL `session_id` 新增/激活 Tab；渲染当前激活 Tab 的会话视图 | 多会话的"编排者"（原单会话职责不变，包一层集合） |
| 3 | **新增** `ChatSessionView.tsx` | 把现 `SessionLayout`（消息/step/输入条）+ 各 hook 抽成"单会话视图"组件，**复制现有代码不改逻辑**；每个 Tab 渲染一个该组件 | 单会话"视图"，与标签解耦（OCP） |
| 4 | 历史页"继续"按钮（`History/index.tsx:323,466`） | 由 `navigate('/?session_id=xxx')` 改为"通知标签栏打开该会话"（Context/CustomEvent/回调），URL 仅作默认聚焦 | 会话并行入口打通 |
| 5 | 左侧"对话任务"菜单（可选） | 语义由"进入最新会话"保留；可加"已打开 N 会话"微标 | 视图层提示 |

#### 6.3.3 数据流与状态归属（10 大规范对齐）

| 状态 | 归属 | 理由 |
|------|------|------|
| 会话集合「哪些已打开/激活哪个 Tab」 | ChatPage 本地 state（或轻量 Context） | 视图编排态，随页面生命，无需全局 |
| 每会话「消息/step/实时流」 | chatStreamStore（方案D 按 sessionId） | 流级状态，全局常驻，多 Tab 共享 |
| 每视图「滚动/DOM/输入框草稿」 | 各 ChatSessionView 内部 | UI 态，不回全局（避免双源） |

#### 6.3.4 生命周期要点（防重蹈 [63] 覆辙）

- **切 Tab ≠ 卸载视图**：方案 D 下 Store 持有流，切 Tab 只切换"哪个视图可见"，流照跑（与 [63] 解耦一致）；
- **关闭 Tab**：调 `chatStreamStore.clear(sessionId)`（显式离开才清理，见 4.4 行为反转）；
- **刷新页面**：Store 丢失 → 各 Tab 通过 L2 持久化恢复（锚点组+续传，见 4.6），标签集合可同步持久化 sessionStorage 恢复上次打开的 Tab 集。

#### 6.3.5 验证要点

- 两个会话同时跑任务（A 发消息→切 B 发消息→切回 A）：A 的 step 在 A Tab 继续累积，B 不被打断；
- 关闭 Tab 不影响其他会话流；
- 历史页连续"继续"打开多个会话，不产生重复 POST 任务；
- 回归 [63] 的 P1/P2 用例，确保多标签改造不破坏单会话切换不中断。

### 6.4 多会话最佳 UI 布局图示与选型（补充）

> 更新人：小欧 2026-09-22 21:18:15
> 北京老陈反馈"都是文字看不懂多会话 UI 长什么样"。本节画图说明：先记住现状布局，再给 3 种候选布局图，最后选定最优并给出代码改动点。

#### 6.4.1 现状布局（先记住，后面好对比）

现在的 `/` 会话页（`SessionLayout.tsx:61-161`）是**上中下三段结构**，整块只容纳"一棵会话"：

```
┌────────────────────────────────────────────────────────────┐
│ [顶栏 topbar] 标题 · 统计                                   │
├────────────────────────────────────────────────────────────┤
│ ┌─────────────┐ ┌────────────────────────────────────────┐ │
│ │ 左列 25%    │ │ 右列 75%                                │ │
│ │ 任务清单     │ │ 执行步骤流(实时 step/thinking)           │ │
│ │ (TaskList)  │ │ + 右侧查看区(可折叠 DoubleLeft)          │ │
│ └─────────────┘ └────────────────────────────────────────┘ │
│ [任务信息条 taskinfo]                                       │
│ [输入区 input]  ← flex 底部钉住                            │
└────────────────────────────────────────────────────────────┘
```

多会话要做的事：**把这"一棵会话"从 1 个变成 N 个，并在顶上加一条"切换栏"**。所以问题本质＝"在现有一棵之上叠什么容器"。下面 3 种画法就是答案。

#### 6.4.2 三种候选布局（画图对比）

**方案甲：顶部标签栏（Tab 栏）——浏览器/IDE 式 ⭐ 选定**

在现有一棵会话的"头上"叠一条横排 Tab 栏，每个打开中的会话一个 Tab；点 Tab 只切换"下面显示哪棵"，下面的 SessionLayout 结构原样不动，流不断（方案D保证）：

```
┌────────────────────────────────────────────────────────────┐
│ [会话Tab栏]（新增，高约 40px）                                │
│   ┌(会话A)─┐  ┌(会话B ●运行中)┐  ┌(会话C)─┐   [+ 新建会话]   │
│   └────────┘  └──────────────┘  └────────┘                  │
├────────────────────────────────────────────────────────────┤
│  ▼ 此区域只显示【当前激活 Tab＝会话B】的那一棵 SessionLayout    │
│ ┌─────────────┐ ┌────────────────────────────────────────┐ │
│ │ 左列 25%    │ │ 右列 75%                                │ │
│ │ 会话B任务清单 │ │ 会话B执行步骤流(实时, 切走时继续累积)      │ │
│ └─────────────┘ └────────────────────────────────────────┘ │
│ [任务信息条]  [输入区]                                      │
└────────────────────────────────────────────────────────────┘

交互语义：
· 点其他 Tab    → 下方整块立即换成那棵会话（后台流照跑，切回即续显）
· 历史页"继续"  → 顶部自动新增一个 Tab 打开该会话（不再跳转换页）
· Tab 尾部 ×    → 关闭该会话视图（调 store.clear 收流）
· "＋新建会话"  → 新建一个空会话 Tab
· ● 红色圆点    → 该会话正在实时运行中（未读提醒/运行态一眼可见）
```

**方案乙：左侧二级列表（邮箱式竖排）**

把多会话做成左侧导航下面的"第二层列表"，点列表项切换左侧整块：

```
┌────────┬───────────────────────────────────────────────────┐
│ 全局菜单 │  ↓ 整块是"当前选中会话"（无 Tab 栏）                 │
│ 对话任务 │ ┌─────────────┐ ┌──────────────────────────────┐ │
│ ┌────┐ │ │ 左列 任务清单  │ │ 右列 步骤流                   │ │
│ │会话A │ │ │ ...          │ │ ...                          │ │
│ │会话B●│ │ └─────────────┘ └──────────────────────────────┘ │
│ │会话C │ │ [任务信息条] [输入区]                             │
│ │ 新建 │ │                                                  │
│ └────┘ │                                                  │
│ 历史会话 │                                                  │
└────────┴───────────────────────────────────────────────────┘
缺点：①与全局菜单抢左栏空间；②"会话"和"页面导航"两个层级混在一起，用户难分清点哪个；
③竖排列表占位大，会话一多需要滚；④顶部没有"我在哪几个会话之间"的全局视野。
```

**方案丙：左右双屏并行（同时显示两个会话）**

把两个会话的整棵 SessionLayout 左右并排：

```
┌────────────────────────────────────────────────────────────┐
│ ┌─────────────┐ ┌────────────────────────────────────────┐ │
│ │ [会话A整棵]  │ │ [会话B整棵]                              │ │
│ │ 左列+步骤+输入│ │ 左列+步骤+输入                           │ │
│ └─────────────┘ └────────────────────────────────────────┘ │
│ (独立接收各自流)  (独立接收各自流)                             │
└────────────────────────────────────────────────────────────┘
优点：能"同一屏同时看/比对"两棵。缺点：①屏幕极挤；②输入区/taskinfo 重复两份难操作；
③会话 ≥3 直接放不下、不可扩展；→ 只适合偶尔比对，不是"多会话日常"主形态。
```

#### 6.4.3 选型结论：方案甲最优（逐项对比）

| 对比维度 | 甲 顶部 Tab 栏 | 乙 左侧二级列表 | 丙 双屏并行 |
|----------|:---:|:---:|:---:|
| SessionLayout 复用 | ★ 整棵结构零改动 | ★ 零改动 | ★ 零改动（复制占位） |
| 占用空间 | ★ 仅顶部 40px | ☆ 占满左栏再加列表 | ☆ 屏幕对半 | 
| 会话切换效率 | ★ 横排一眼扫全部+1击 | ☆ 竖排需滚动 | ☆ 无"全局视野" |
| 心智模型 | 浏览器/IDE 天然习惯 | 邮箱式,易与菜单混 | 少见,信息过载 |
| 扩展上限 | ★ 理论上无上限(横向滚动) | △ 列表可长 | ✗ ≥3 崩溃 |
| 运行中状态可见 | ★ Tab 上 ● 一眼可见 | △ 需看列表 | ✗ 双屏才见 |
| 与方案D契合 | ★ 切 Tab 组件卸载→Store接管 | ★ 同样契合 | ★，但浪费 |

**结论：选定方案甲（顶部 Tab 栏）。**

#### 6.4.4 方案甲的落实（UI 落点清单，对应 6.3.2）

| 落点 | 改动 | 复用/新增 |
|------|------|-----------|
| 会话页最外层包 Tab 容器 | antd `<Tabs type="card">`（或自绘 Tab），items ＝ 打开会话数组；`destroyInactiveTabPane={false}` 保活非激活 Tab 的 DOM，滚动/草稿不丢 | 新增 |
| 每个 Tab 内容 = 现有 SessionLayout | 每 Tab 渲染一棵"现有 SessionLayout + 现有 hooks" → 复制为 `ChatSessionView` | 复用代码复制新组件 |
| 历史页"继续" | 不再 `navigate('/?session_id=xxx')`，改向 Tab 容器 `openSession(sessionId)` 新增/激活 Tab | 改造 History/index.tsx:323 |
| URL 纵深 | `/`仍承载"默认聚焦会话"；`?session_id=` 仅决定初始激活那个 Tab，切 Tab 不改 URL（纯前端视图），避免路由卸载重演 | 改造 |

**关键点**：多 Tab 容器是"纯视图层"，会话流状态一律在 chatStreamStore（方案D），Tab 只订阅显示。切 Tab=切换显示，永不销毁流，与 3.8 的"三改一不改"原则完全自洽。
