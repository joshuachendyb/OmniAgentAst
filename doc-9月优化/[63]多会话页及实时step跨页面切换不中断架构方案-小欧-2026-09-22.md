## 一、问题描述

> 编写人：小欧 2026-09-22 20:38:55

### 1.1 现象

会话页（`/`）实时任务执行中（SSE 正流式推送 Step），用户切换到**历史页**（`/history`）或**设置页**（`/settings2`），再切回会话页时：

1. 实时 Step（thinking/工具调用/执行结果/最终回答）**不续传**；
2. 切走期间产生的中间步骤**看不到**；
3. 若任务在切走期间已完成，回来只能看到**最终落库结果**，中间过程丢失；若任务还在跑，回来是**全新初始化**，不会自动接上正在跑的流；
4. 来回快速切换，每次进入会话页都触发一次重新初始化（重新拉历史、重建连接），实时进度 UI 反复跳变。

### 1.2 影响范围

- 用户在实时任务运行中去历史页核对另一会话、去设置页调整配置，是**高频真实操作**；
- 当前行为实质是"切走即杀掉前端实时流"，与「任务后台继续跑」的预期（后端确实在跑，[51]已实证）割裂，用户感知为"实时 step 丢了"。

### 1.3 问题结论先行

**切换页面 = ChatPage 组件被卸载 → SSE 连接 abort → 步骤备份被删 → 切回全新初始化。** 不是"影响"，是"中断且不续传"。

## 二、问题的根本原因

> 编写人：小欧 2026-09-22 20:38:55

### 2.1 根因链（现状代码实证）

| # | 根因 | 证据位置 | 说明 |
|---|------|---------|------|
| R1 | 路由切换即卸载组件 | `App.tsx:57-73` `<Routes>` 单匹配渲染，`/history`/`/settings2` 匹配时 ChatPage 卸载 | 三个页面是独立路由路径，非同页 Tab |
| R2 | SSE 生命周期 = 组件生命周期 | `useSSE.ts:442-557` 全部状态 useState/useRef；仅 ChatPage 内部经 `useChatFacade`→`useChatStreaming` 调用 | 无模块级 SSE 单例，无 Context 承接 |
| R3 | 卸载 cleanup 三个破坏性动作 | `useSSE.ts:1231-1246` → `disconnect()`（默认 `clearStorage=true`）→ `clearStepsFromStorage()` 删备份（`useSSE.ts:688-690`）+ `abortController.abort()`（695-713）；`pendingMessageRef=null`（1238）；停轮询（1236） | 把唯一可恢复的数据源一并销毁 |
| R4 | 续传锚点全部是组件内存态 | `serverTaskId`(525-527)、`lastSeqRef`(546)、`pendingMessageRef`(550-553)、`lastContextLinkModeRef`(555-557) 均为 ref，卸载即失 | 备份 envelope（`useSSE.ts:465-469`）只有 `{steps, source, timestamp}`，无 task_id/seq/待发消息 |
| R5 | `isReconnect` 续传守卫绑定本实例重连计数 | `useSSE.ts:806-814` 要求 `reconnectAttemptsRef>0` + `serverTaskIdRef` 非空；新 mount 恒为 0 | 新 mount 丢失 taskId/seq，只能走无锚点路径；重复 POST 可能进入当前后端的同会话任务注入/竞态路径，无法保证走 GET 续传（`useSSE.ts:830-840`，`stream_orchestrator.py:346-357`） |
| R6 | mount 恢复 effect 只回填 steps，永不建连 | `useSSE.ts:595-623` 从备份读 steps 回填，不主动发 GET | 切回后"有数据可看"但"不会续接进行中的流" |
| R7 | 后端续传源是**内存缓冲且有时限** | `task_state.py:42-56` `event_log`；`agent_runner.py:761-765` 任务结束 300s 回收 | 切走超过 300s 或后端重启，after_seq 续传数据源即失 |

### 2.2 本质

**"正在进行的会话流"（In-Flight Session Stream）不是一个独立的一级状态实体**，它被绑定在 ChatPage 组件实例的 hook 生命周期上。UI 组件可以卸载重挂，但"流"是后台正在跑的东西，二者生命周期必须解耦。当前代码把所有鸡蛋放在组件实例一个篮子里，卸载即一切归零。

### 2.3 与既有能力的落差

| 既有能力 | 现状 | 落差 |
|---------|------|------|
| 后端 `GET /chat/stream/{task_id}?after_seq=N` 续传 | 已存在且幂等（`chat_routes.py:116-122`，e2e 已验证多客户端多轮续拉） | 前端没有保存续传所需的 (task_id, seq) |
| 前端 steps 备份 | 已存在（`useSSE.ts:456-478`，完整 `ExecutionStep[]`） | 卸载时被 `disconnect()` 默认删除（R3） |
| 后端按 session 找任务 | `GET /sessions/{id}/tasks` 返 `latest_task_id` | 可作为切回后定位任务兜底 |
| 历史拉取中间步骤 | `GET /sessions/{id}/messages` 含完整 execution_steps | 仅任务完成后可用，运行中任务不在 DB |

结论：**P1/P2 当前后端能力只满足内存窗口内续传；P1 的主要卡点在前端流生命周期。300 秒后精确回放、进程重启后已完成任务回放属于后端 P3，必须按第七章实施。**

## 三、解决策略分析及方案优劣说明

> 编写人：小欧 2026-09-22 20:38:55

### 3.1 候选方案总览

| 方案 | 一句话 | step不断 | 切回即时 | 改动范围 | 稳定性 | 扩展性 |
|------|--------|---------|---------|---------|--------|--------|
| A 全局 Context 硬搬 | 把 useChatFacade 整个搬进全局 Provider | 完全不断 | 即时 | 大 | 中（双源风险） | 中 |
| B keep-alive 隐藏不卸载 | ChatPage 改 `display:none` 常驻，绕过 Router 卸载 | 完全不断 | 即时 | 中（路由层） | 中（对抗 Router 语义） | 低 |
| C 持久化续传（补丁式） | 存四元组+卸载保留备份+重挂载发 GET | 断后≤300s续 | 需一次GET | 小（useSSE 内） | 高 | 低（单会话单文件） |
| **D 会话流 Store 架构（本方案）** | **流提升为全局独立 Store，多会话订阅，卸载只解绑不销毁，刷新靠持久化+续传双保险** | **完全不断** | **即时** | **中** | **高** | **高（多会话/历史页实时化天然扩展）** |

### 3.2 方案 A：全局 Context 硬搬

**做法**：仿 `AppContext` 再加 `ChatStreamProvider`，把 `useChatFacade` 整体搬进去，卸载组件不卸载 Provider。

**问题**：
- `ChatPage.tsx:74-76` 的 `onError`/`onSuccess` 是 ChatPage 私有闭包回调，全局化后必须改事件通道，隐性改造大；
- useChatState 的 DOM ref（`messagesEndRef` 等）与 UI 强耦合，全局持有造成"UI 状态 / 流状态双源并存"，违背单一职责；
- 每次 `setMessages` 触发整棵 Provider 树重渲染，与"三页面独立渲染"冲突。

**结论**：伤筋动骨且设计不整。**不采用。**

### 3.3 方案 B：keep-alive 隐藏不卸载

**做法**：ChatPage 移出 `<Routes>`，按 `location.pathname` 用 `display:none` 切换；历史/设置页正常卸载。

**优点**：改路由一层，SSE 完整不断，切回 0 延迟。

**问题**：
- 与 React Router `<Routes>` 单匹配卸载语义**对抗**，需自建"活动面板"标记；
- URL `?session_id` 变化时 `useChatInit.ts:66` 仍会重跑初始化（依赖 `urlSessionId`）；
- 只解决"这一个页面"，历史页/多条会话/多任务并行时无扩展能力；
- 常驻隐藏页吞内存，属"绕过问题"而非"解决问题"。

**结论**：可用作过渡，但非扩展性架构。**仅作 D 的退化选项。**

### 3.4 方案 C：持久化续传（补丁式）

**做法**：`useSSE.ts` 内补四元组持久化 + 卸载 `clearStorage=false` + mount 伪装重连走 GET 续传。

**问题（短视所在）**：
- 只保当前这一个 hook 实例，代码内聚但仍是"组件内补丁"，流依然跟着组件走；
- 多会话、历史页实时化、多标签同步等后续需求无法演进，每次都要再打一层补丁；
- 300s 窗口是硬约束，超出即退化（但可接受）。

**结论**：**方向对、范围小，但作为"唯一方案"目光短浅。** 其续传逻辑可作为方案 D 的**底层能力**复用，而不是终结方案。

### 3.5 方案 D：会话流 Store 架构（推荐）

**核心思想**：
> 把「正在运行的会话流」从 ChatPage 组件实例中抽离，提升为**模块级全局单例 Store**（`Map<sessionId, ChatStreamSession>`）。SSE 连接、步骤、任务锚点由 Store 持有；组件只是**订阅者**。卸载组件=解绑订阅，流继续跑；重挂载=重新订阅即时拿快照。浏览器刷新（Store 丢失）由 sessionStorage 持久化 + GET after_seq 续传兜底。

**架构分层（P1/P2 三层防线，P3 另增后端 Journal 层）**：

| 层 | 防线 | 覆盖场景 |
|----|------|---------|
| L1 内存 Store | SSE 连接与状态全局常驻 | **路由来回切换（最常见）**：完全无缝 |
| L2 持久化+续传（P1/P2 当前） | 锚点组+steps 写 sessionStorage；mount 检测活动任务发 GET 续传 | **浏览器刷新/标签页冻结恢复**（当前后端仅保证 300 秒内存窗口内） |
| L3 DB 历史兜底（P1/P2 当前） | 现有 `loadHistoryMessages` 加载最终结果 | 窗口外/后端重启：行为等同现状，不劣化 |
| P3 Journal 回放（新增目标） | 后端 `chat_stream_events` + Journal reader | 300 秒后回放、后端重启后回放已完成任务；未完成计算不自动续算 |

**设计要点（10 大规范对齐）**：
- **SRP**：Store 只管"流"（连接/步骤/任务锚点/订阅），消息历史、UI 状态（滚动、回复区）仍留在 ChatPage/useChatState，职责分明；
- **DRY**：会话流状态让 useSSE 与未来历史页实时化共用同一数据源，消除"每实例一套 ref 双写"；
- **OCP**：Store 按 sessionId 索引，天然支持多会话并行/历史页订阅实时流，新增消费者不必改 Store 内核；
- **禁止backward**：useSSE 对外接口（sendMessage/onStep/onComplete…）经薄适配层保留签名，消费者无感知切换，但内部实现整体迁移，不保留新旧两套路径。

### 3.6 方案 D 与 B/C 的关系

- **不做 B**：不需要 keep-alive，Router 正常卸载（组件与流解耦后，卸载无害，反而释放 DOM 内存）；
- **吸收 C**：L2 层的持久化+续传复用 C 的全部既有代码资产（steps 备份、GET 端点、300s 窗口），不重造轮子。

### 3.7 最终确定方案：方案 D 策略要点汇总（白话）

> 更新人：小欧 2026-09-22 20:49:51

#### 3.7.1 一句话讲清方案本质

**把"正在跑的对话流"从聊天页组件上摘下来，放到一个常住后台的全局 Store 里；聊天页面只是"看屏幕的人"，切走页面不再等于拔掉电话线。**

#### 3.7.2 打个比方（帮助理解）

把现在的会话页想成"一个人同时当接线员＋显示器"：
- **现状**：你一转身（切换去历史页/设置页），整格人连人带桌子被撤走——电话线（SSE 连接）被拔断、贴墙的进度单（步骤备份）被撕掉。

  - 你走回来 → 大屏**立刻接着显示最新进度**，不用重新汇报、不用重新接线；
  - 只有你明确说"这条线不用了"（点击停止、删除会话或任务进入终态）→ 才挂断清理；新建会话只创建新视图，不自动停止旧任务。

#### 3.7.3 核心动作（改什么、不改什么）

| 动作 | 内容 |
|------|------|

#### 3.7.4 三层防线（回答"断了/刷新了/太久没回来怎么办"）

| 防线 | 管什么场景 | 效果 |
|------|-----------|------|
| L1 内存 Store | **切去历史页/设置页再切回来**（最常见） | 线不断，切回大屏**直接续显**，零等待、不重拉、不重建任务 |

| L3 DB 历史兜底 | **超过 300 秒才回来 / 后端重启**（P1/P2 当前补拉也拿不到中间态） | 退回现有"加载历史最终结果"，行为与现在一致，**只可能变好、不会更差**；P3 实施后由 Journal reader 接管终态回放 |

#### 3.7.5 用了哪些现有资产（不重造轮子）

- 后端按会话找任务接口 `GET /sessions/{id}/tasks`——已经存在，作兜底定位；
- 现有历史加载 `loadHistoryMessages`——已经存在，作 L3 兜底。

#### 3.7.6 为什么这就是"稳定、可靠、可扩展、不短视"

- **稳定**：P1 核心行为反转是卸载不再断流；P2 再补锚点和续传；P3 才改变后端耐久性边界。
- **可靠**：当前 P1/P2 在 300 秒窗口内续传，窗口外依赖历史降级；P3 实施后才提供 Journal 回放。
- **可扩展**：Store 按 sessionId 索引，为历史页、多任务和后续标签页预留数据基础；跨标签同步和多会话 UI 不属于本轮交付能力。

#### 3.7.7 落地节奏（分三步，每步都稳）

| 阶段 | 做什么 | 效果 |
|------|--------|------|
| P1 常驻化 | 建总机室 + 卸载改"只解绑" | 切页不断流、切回续显（解决 90% 痛点） |
| P2 持久化＋续传 | 补锚点组(四元组+接收中标记) + 刷新自动续拉 | 当前 300 秒窗口内可续传；窗口外/降级时明确进入历史恢复，不承诺绝对不丢 |
| P3 后端增强 | `chat_stream_events` Journal 持久化、Journal reader 回放、终态清理 | 300 秒后和后端重启后，已完成任务可按 seq 回放；未完成计算明确中断，不伪造续算 |

**结论（终极一句话）**：方案 D ＝ **把对话流的"家"从聊天页面搬进全局总机室常驻，页面只当显示器；切走断不了、刷新能自救、最坏不劣化，且为未来多会话/多页一定备好扩展位。**

### 3.8 前后逻辑流程对比：改的是什么流程（白话）

> 明确回答"这是功能流程改变还是什么流程改变"：**改的不是功能流程，改的是三条"内功流程"——数据住哪、生命周期归谁、卸载时干什么。用户能看到的操作一个都没变。**

#### 3.8.1 现状（改前）的逻辑流程

```

发送消息 ──→ ChatPage 里 useSSE 自己建立连接(POST /chat/stream)

**本质**：SSE 连接和步骤数据的"寿命 = 聊天页组件的寿命"。页面一卸载，连接和状态**跟着一起死**。

#### 3.8.2 方案 D（改后）的逻辑流程

```
【实时任务中】
发送消息 ──→ 全局 chatStreamStore 建立连接(POST)  ← 连接迁到"总机室"
              │          收帧 → 写进 Store 的 executionSteps
              └─→ 通知订阅者(ChatPage) → UI 渲染    ← 页面只是"看屏的人"

   └─→ 仅"解除订阅"(useSyncExternalStore 自动 unsubscribe)

后端任务: 继续跑，Store 继续接帧累积

【切回会话页】
ChatPage 重新挂载 → 重新订阅 Store → 立即拿到当前快照(最新steps/taskId/接收中)
   └─→ UI 直接续显，零等待、不重拉、不重建任务

【极端: 刷新页面(Store 也没了)】

**本质**：SSE 连接和步骤数据的"寿命 = 会话(任务)的寿命"，独立驻留全局 Store；卸载页面只是"看板下线"，流照跑。

#### 3.8.3 到底改的是哪种流程？——三改一不改

| 维度 | 改前 | 改后 | 属于什么改变 |
|------|------|------|------------|
| **状态/连接住哪** | 组件 hook 内(useSSE 每实例一套) | 全局 Store(按 sessionId 索引) | **数据驻留位置改变**（架构层） |
| **生命周期归谁** | 归 ChatPage 组件 | 归会话(任务) | **生命周期归属改变**（架构层） |
| **卸载时干什么** | 断开连接+删备份+清状态 | 只解绑订阅 | **P1 核心行为反转**；P2 再补锚点/续传，P3 再补后端耐久性 |
| **用户操作**(发消息/看step/取消/暂停/HITL/历史) | — | — | **业务操作不改，但适配层必须完整实现现有消费接口，不得以“接口不变”为由漏迁移能力** |

**功能流程完全没变，变的是"谁来养这条流"**——从"跟着页面生死"改成"常驻后台、跟任务生死"；附带把"卸载＝销毁"这一个错误行为反转成"卸载＝只看屏的人撤了"。

### 3.9 对照本地代码的审核结论与实施红线（v1.6）

> 审核人：小欧 2026-09-25 13:15:20
>
> 审核依据：本地最新 `frontend/src/hooks/useSSE.ts`、`useChatStreaming.ts`、`useChatInit.ts`、`backend/app/services/chat/stream_orchestrator.py`、`task_state.py`。本节是对原方案 D 的实施纠偏，后续代码必须以本节为准。

#### 3.9.1 审核结论

方案 D 的方向仍然正确：**运行中的 SSE 从 ChatPage/useSSE 生命周期中解耦，按 sessionId 放入运行时 Store**。但原方案不能原样实施，必须修正为“修正版 D”：

1. `useSyncExternalStore` 必须读取缓存快照，禁止每次 `getSnapshot()` 新建对象或在读取阶段惰性创建状态。
2. 取消订阅、关闭视图、停止任务、删除会话必须是四个不同动作；关闭视图不得调用 `clear()` 或 abort。
3. L2 持久化必须使用同一份原子快照；终态必须立即落盘，不能只依赖 5 秒防抖。
4. Store 必须补齐现有 `useSSE` 的运行态、定时器、连接资源和 HITL 状态，不能只迁移文档列出的少数字段。
5. GET 续传必须处理 `not_found`、已完成、缓冲过期和后端重启；不能把“回退历史”当成自动发生的行为。
6. sessionStorage 只承担单标签页刷新恢复，不承担跨标签同步；多标签同步另立方案。
7. 多会话 Tab 是后续 UI 能力，不纳入本轮 P1/P2，避免 Store 迁移和 UI 重构同时发生。

#### 3.9.2 10 大规范落地约束

| 规范 | 本方案硬约束 |
|------|--------------|
| SRP | Store 只负责流运行时；消息历史、草稿、滚动位置仍由会话视图负责；持久化由独立快照模块负责。 |
| DRY | 只保留一个事件消费/合并入口；禁止 Store、useSSE、页面各自维护一套 steps、lastSeq、isReceiving。 |
| KISS-DIRECT | P1 只解决“路由切换不断流”；刷新续传独立为 P2；多会话 Tab 独立排期。 |
| SLAP | 页面订阅层不操作 fetch/AbortController/重连定时器；这些只由 Store 内部负责。 |
| YAGNI | 本轮不实现跨标签同步、不实现双屏、不实现通用事件总线注册表。 |
| OCP | Store 通过明确的快照和动作 API 扩展，不让页面读取并修改内部字段。 |
| LSP/ISP | 现有适配层必须完整实现订阅、发送、恢复、停止、清理动作；不能用半套接口冒充兼容。 |
| 禁止 backward | 不保留旧 useSSE 全量路径与新 Store 两套运行逻辑；只允许薄适配层调用新 Store。 |
| 复用优先 | 复用现有 `sendMessageInternal`、SSE parser、重连、暂停/取消和 GET 续传逻辑，不复制第二套解析器。 |
| 三堂会审 | 落盘前检查合规性、合理性、关联逻辑；重点核对定时器、闭包、状态原子性、终态和跨会话隔离。 |

#### 3.9.3 实施顺序调整

| 阶段 | 本轮实施内容 | 本轮不实施内容 |
|------|----------------|----------------|
| P1 | per-session 运行时 Store、路由卸载只解绑、完整状态迁移、事件快照分发、并发/重连测试 | 多会话 Tab、跨标签同步、后端持久化 |
| P2 | 原子 sessionStorage 快照、终态立即落盘、刷新后 GET 续传、not_found 恢复状态机 | UI 多视图改造 |
| P3 | 后端事件持久化、缓冲窗口策略、进程重启恢复 | 不作为 P1/P2 前置条件 |

#### 3.9.4 修正版 D 的生命周期语义

```text
切路由/切 Tab       → 只取消页面订阅
关闭视图            → 只移除视图，Store 和后端任务保留
停止任务            → 先调用后端 cancel，确认终态后清理 Store
删除会话            → 先调用后端删除接口，确认删除后清理 Store
任务正常完成        → 保留最终快照，按 TTL/LRU 释放连接资源
浏览器刷新          → Store 丢失，使用 L2 原子快照恢复
```

**红线：**“我不看了”不等于“停止任务”；任何关闭视图路径都不得调用 `clear()`、abort 或删除 sessionStorage。

**v1.15 补充（与 6.3.4 对齐，消除表面矛盾）：** 上条红线约束的是"用户主动关闭视图"这一动作；6.3.4 的"关闭后无人认领的流按宽限期回收"是**另一件事**——它只经 `releaseUnsubscribed()` 释放客户端连接与定时器，不调用后端 cancel、不删快照、不改任务状态。两者不冲突：任何路径都不得因"回收"而停止后端任务。

**实现约束：**

- `getSnapshot()` 在 session 尚不存在时返回冻结的空快照，不创建 session；`ensureSession()` 只能由挂载 effect 或用户动作显式调用。
- `revision` 变化时才创建新的 `snapshot`，`getSnapshot()` 只读缓存，不得创建对象或修改状态。
- 事件处理必须在一个 Store 写入口中完成 `lastSeq + steps + 接收状态` 的原子更新。
- `onStep/onChunk/onComplete/onError/onPaused/onResumed/onRetry/onAuthorizationRequired/onRejected` 统一转换为 `StreamEvent`，由 Store 事件分发器投递给当前订阅者；页面卸载后不再投递 UI 回调，终态仍保留在快照中供新订阅者读取。

```ts
interface StreamEvent {
  seq: number;
  taskId: string | null;
  sessionId: string;
  kind:
    | 'step'
    | 'chunk'
    | 'complete'
    | 'error'
    | 'paused'
    | 'resumed'
    | 'retry'
    | 'authorization'
    | 'rejected';
  payload: ExecutionStep | string | Record<string, unknown>;
  revision: number;
  occurredAt: number;
}
```

`StreamEvent` 只允许携带事件和版本信息，不携带 React 状态引用；页面事件回调只能读取事件和快照，禁止直接修改 Store 内部字段。
- 页面通过动作 API 发送、停止、恢复，禁止直接修改 `ChatStreamSession` 内部字段。
- 现有 `executionStepsRef` 不得继续作为可写第二真源；`useChatStreaming` 改为调用 `clearSteps()`/快照读取，`setIsReceiving`/`setServerTaskId` 改为 Store 动作，禁止 ref/state/Store 三方双写。
- `stop()` 是“停止任务”，`clearCompleted()` 是“释放已完成资源”，二者都不得由组件卸载或关闭视图触发。
- v1.15 明确 `releaseUnsubscribed()` 的边界（配合 6.3.4"关闭后无人认领的流回收"）：订阅者数为 0 且超过宽限期（默认 60s）时，**只释放客户端侧资源**（fetch 连接、定时器、事件订阅），**不调用后端 cancel、不停止任务、不删除 sessionStorage 快照、不改 `chat_tasks.status`**；重新打开该会话按 `resume()` 续传。活跃订阅者存在时一律不回收。
- Store 必须有明确的终态资源上限：完成后保留最终快照供历史/恢复读取，连接 abortController、定时器和订阅者按终态 TTL/LRU 释放；活跃 session 不得被 LRU 淘汰。

**L1 能力的本质**：订阅者链表 `listeners` 保证 ChatPage 卸载只调 `unsubscribe`，Store 与 fetch 连接**不销毁**。

### 4.2 新增模块：`frontend/src/features/chat/streams/useChatStreamSession.ts`

组件↔Store 桥接 hook（基于 `useSyncExternalStore`）：

```ts
import { useEffect, useSyncExternalStore } from 'react';

export function useChatStreamSession(
  sessionId: string,
  onEvent?: (event: StreamEvent) => void
) {
  const snapshot = useSyncExternalStore(
    (callback) => chatStreamStore.subscribe(sessionId, callback),
    () => chatStreamStore.getSnapshot(sessionId),
    () => chatStreamStore.getSnapshot(sessionId)
  );
  useEffect(() => {
    chatStreamStore.ensureSession(sessionId);
    return onEvent
      ? chatStreamStore.subscribeEvents(sessionId, onEvent)
      : undefined;
  }, [sessionId, onEvent]);
  return {
    ...snapshot,
    sendMessage: (content: string, mode?: ContextLinkMode) =>
      chatStreamStore.sendMessage(sessionId, content, mode),
    resume: () => chatStreamStore.resume(sessionId),
    stop: () => chatStreamStore.stop(sessionId),
  };
}
```

`getSnapshot()` 必须返回 Store 缓存的同一对象引用；只有 `revision` 变化才替换快照。禁止在 `getSnapshot()`、`subscribe()` 或 React render 阶段惰性创建 session。`onEvent` 必须由 `useCallback` 或 Store 适配层保持稳定引用，避免每次 render 触发事件订阅抖动。

组件卸载只触发 `unsubscribe`，不会触发 abort、清理 Store 或删除 sessionStorage。停止任务必须由显式 `stop()` 触发。

### 4.3 改造 `useSSE.ts` → 薄适配器（或并入 Store）

- **迁移而非复制第二套逻辑**：把 `sendMessageInternal`、SSE 解析、重连、暂停/取消、GET 续传和定时器清理迁入 Store，页面适配层只调用 Store 动作；禁止同时保留旧 hook 全量逻辑和新 Store 逻辑。
- **完整迁移现有运行态**：除状态字段外，必须迁移 `responseBuffer`、`isProcessing`、重连/空闲/首帧定时器、心跳时间、HITL 等待集合、pendingSteps 和 flush 调度状态。
- **保持消费接口完整**：`useChatStreaming` 所需的 `setIsReceiving`、`executionStepsRef`、`setServerTaskId`、`clearSteps`、`reconnectStatus`、`waitClock` 等能力必须由 Store 快照/动作完整提供；不能宣称“接口零变化”却不实现这些接口。
- **resume 状态机**：`resume()` 不得伪造 `reconnectAttempts=1` 作为唯一恢复机制；应直接调用恢复动作，处理 `not_found`、已完成、缓冲回收和后端重启。

#### 4.3.1 `resume()` 恢复状态机

```text
RESTORE_INVALID
  → 丢弃快照，初始化历史，status=idle

RESTORE_PENDING_NO_TASK + pendingMessage.state = queued
  → 不自动 POST，不创建隐式任务
  → 先查同会话活动/最新任务：若存在同内容且创建于最近 300 秒内的活动任务，直接附着该 task，进入 RESTORE_ACTIVE，禁止再次 POST，并立即把 pendingMessage 置 null 再持久化
  → 否则将 pendingMessage 恢复为显式待发草稿，并显示“尚未发送”
  → 用户确认后只发送一次；taskId 落定后立即把 state 改为 sent 并持久化

RESTORE_ACTIVE + taskId + lastSeq
  → 校验 sessionId/taskId
  → GET /chat/stream/{task_id}?session_id=...&after_seq={lastSeq + 1}
  → 合并新帧并推进 lastSeq（合并规则见 4.6，含 executionSteps 去重）
  → 收到 final / final_stats 终态事件：立即 persistNow，status=completed
  → reader 结束但**未见终态事件**（断流/缓冲回收/后端重启均可能）：
       禁止直接置 completed（7.9.1 终态权威是 chat_tasks.status，前端不得自行推断终态）
       → 查 GET /sessions/{session_id}/tasks 的该 task 状态：
            已终态 → status 置对应终态并 persistNow，加载历史终态内容
            非终态/查不到 → status=recovering，转入 GET_NOT_FOUND 同族核对，
                            由历史降级或再次 resume 决定，禁止伪造完成、禁止立即重发

GET_NOT_FOUND
  → P1/P2：查询任务/会话最终状态并加载历史
  → P3：若 Journal 有终态事件，按 seq 回放；若 Journal 无终态，返回 task_interrupted
  → 未找到或后端重启且无 Journal：清理无效快照，加载历史，status=failed 或 recovering（按上条核对结果二选一，禁止无依据直接置 failed）

PAUSED/RETRYING/HITL
  → 保留 taskId、isReceiving 和 HITL 状态
  → 继续按同一任务恢复，不重新 POST
```

禁止在恢复状态未确定时同时执行初始化历史、重新 POST 或清空旧快照；所有状态转移必须幂等，重复 `resume()` 不得建立两条 GET 连接。

`sendMessage()` 必须先把 `clientMessageId + content + queued` 持久化，再发起 POST；POST 成功并拿到 `taskId` 后，必须把同一条 `clientMessageId` 标记为 `sent`。禁止无持久化直接 POST，禁止同一 `clientMessageId` 发送两次。

### 4.6 持久化锚点组扩展（L2 层，吸收方案 C）

备份 envelope 扩展为带版本的原子快照：

```ts
interface StreamBackup {
  version: 2;
  revision: number;
  sessionId: string;
  taskId: string | null;
  lastSeq: number;                // event_log 已处理偏移，初始 -1
  steps: ExecutionStep[];
  metaFrames: TaskMetaFrames;
  currentResponse: string;
  usageAccum: { prompt: number; completion: number; total: number };
  isReceiving: boolean;
  isConnected: boolean;
  status: 'idle' | 'active' | 'paused' | 'retrying' | 'recovering' | 'completed' | 'failed' | 'cancelled';
  pendingAuthorization: AuthorizationRequest | null;  // v1.15 新增：与内存态同枚举同字段，保证快照可完整恢复 HITL 等待
  hitlWaitingKeys: string[];
  pendingMessage: {
    clientMessageId: string;
    content: string;
    sessionId?: string;
    state: 'queued' | 'sent';
  } | null;
  lastContextLinkMode: 'linked' | 'independent';
  updatedAt: number;
}
```

- 普通帧可沿用 5 秒防抖，但写入必须来自同一份缓存快照；
- `done/final/final_stats/error/cancelled/rejected` 等终态或异常终态必须立即调用 `persistNow()`，不得等待防抖；
- 写入失败必须记录可诊断信息，并将该恢复能力标记为不可用，不得伪装成功；
- 恢复时校验 `version/sessionId/taskId/revision/lastSeq`，不合法快照直接丢弃并走历史加载；
- 路由卸载和关闭视图不得删除该快照；只有后端确认停止/删除或 TTL 清理后才允许删除。

**原子性要求：**`lastSeq` 表示后端 `event_log` 已处理偏移，不能使用最后一个可见业务 step 的序号；seq 与 steps 必须在同一个 Store 写入口更新。

**恢复合并规则：**

- `executionSteps` 必须按事件身份去重（v1.15 补，原文只定义了 currentResponse/usageAccum，缺步骤去重会导致 Journal 回放与快照叠加出重复行）：以 `(type, step, seq)` 为键做存在性过滤，快照中已存在的步骤不再追加；`final` 与 `final_stats` 各自只保留一条，后者重复到达时按 payload 等价覆盖而非追加；
- `currentResponse` 以快照中的已确认前缀为基准，只追加 `seq > lastSeq` 的后续 chunk；禁止把已确认前缀重复拼接；
- `usageAccum` 按快照累计值恢复，后续 usage 帧按 `seq > lastSeq` 递增合并；
- `hitlWaitingKeys` 持久化为有序字符串数组；恢复时按数组重建等待集合，禁止恢复后把仍在等待的 HITL 误判为已超时；
- 快照中 `isConnected` 只表示写入时刻，不作为恢复后的连接状态；恢复后连接状态只能由当前 Store 的实际连接决定。

#### 4.6.1 持久化模块边界

新增 `chatStreamPersistence.ts`，只负责 `load(sessionId)`、`save(snapshot)`、`remove(sessionId)` 三个动作；不得读取 Store 内部字段，不得触发 SSE，不得修改 React 状态。Store 在同一写入口生成快照后调用 `save`，终态调用 `save` 的立即写入模式。

```text
Store 写入口 → 生成不可变 StreamBackup → persistence.save()
页面恢复   → persistence.load() → 校验版本 → Store.hydrate()
```

禁止页面直接读写 sessionStorage，禁止 Store 解析存储，禁止把持久化逻辑塞进 `useSSE` 或 `useChatStreamSession`。

**Case P1-RealTimeSwitch（L1 核心）**

**Case P5-AtomicPersistence（快照一致性）**
1. 在普通帧防抖窗口内刷新；
2. 在 `final/final_stats` 到达后立即刷新；
3. 断言恢复快照中的 `lastSeq` 与 `steps` 属于同一 revision，续传不重复、不丢失；终态不会被延迟 5 秒的防抖吞掉。

**Case P6-CloseViewVsStop（生命周期语义）**
1. 关闭会话视图但不点击停止；
2. 断言 SSE/后台任务继续，重新打开视图后可看到后续步骤；
3. 点击停止后才允许调用后端 cancel 并清理 Store；关闭视图不得触发 abort、clear 或删除备份。

**Case P7-SnapshotRenderSafety（Store 快照）**
连续接收多帧并切换路由，断言：`useSyncExternalStore` 无无限渲染警告，快照引用只在 revision 变化时更新，页面卸载期间无 UI 回调访问已销毁闭包。

**Case P8-ResumeFailure（HITL/终态恢复）**
分别覆盖 paused、error、cancelled、completed、not_found，断言恢复后状态、终态步骤、任务列表和历史消息一致，不出现重复步骤或永久 loading。

**Case P9-PendingNoTaskResume（无 taskId 待发分支）**
1. 发送消息后立即 reload，使 POST 已发出、内存和备份中 taskId 尚未落定，仅剩 pendingMessage.state=queued；
2. 断言恢复后未自动 POST，弹出"尚未发送"待发草稿；
3. 后端存在同内容活动任务时：继续或确认后不发起第二次 POST，直接附着并进入续传，且 pendingMessage 被清空；
4. 后端无同内容任务但用户确认发送时：精确一次 POST，taskId 落定后把 state 改为 sent 并持久化；
5. 断言不出现同一 clientMessageId 被发送两次、不出现重复任务。

### 5.3 执行检查（手动，每 case 逐项）

1. **代码错误异常检查（最高优先级）**：查后端 `backend/logs/` traceback/ERROR；前端控制台无未捕获异常；SSE 无 error 事件 → 有则立即停，走修复；
2. **调用链分析**：输出 `[CALL CHAIN]`——工具选择/顺序/LLM 次数合理；切换后无第二次 POST `/chat/stream`（无重复任务）；若有 GET 续传则 `after_seq` 连续且不回放已显步骤；
3. **参数正确性**：续传 URL 的 `task_id` 与 start 帧一致、`after_seq=lastSeq+1` 正确；session_id 正确。

### 5.4 通过标准

- P1-P3 全过，P4-P9 不得出现重复任务、重复步骤、永久接收中或静默丢失；
- 切走期间产生的步骤（thinking/action/observation/final）切回后**可见且不重复**；
- 刷新恢复必须通过 `after_seq` 连续性校验；`lastSeq` 与 steps 必须来自同一快照 revision；
- 关闭视图不得停止任务；停止任务必须先完成后端 cancel 确认；
- 全程每个 session 仅有 1 个任务 id、1 次 POST；超过的视为缺陷；
- 10 大规范三堂会审通过：无状态双源、无第二套解析器、无透传函数、无无效抽象、无向后兼容分支。

#### 6.3.4 生命周期要点（防重蹈 [63] 覆辙）

- **切 Tab ≠ 停止流**：Store 持有流，切 Tab 只切换哪个视图可见，流照跑；
- **切 Tab 改 URL 不得触发会话重初始化**：`?session_id=` 变化原本走"重新初始化该会话"链（P1 前会清 step/重载历史/断流），实施时必须由 `ChatTabsHost` 拦截标签引起的 URL 写入并置 `switchSource='tab'`，`useChatInit` 见到该标记**跳过重初始化**（v1.14 新增硬约束，缺此项一切换就断流）；
- **同 session 只允许一个 Tab**：`openSessionTab(sessionId)` 对已打开项只做"激活"，绝不新建第二个视图；否则同一 Store 流被两视图消费，出现双输入框、滚动互踢与重复起任务（v1.14 新增）；
- **关闭 Tab**：移除视图，**不调用** `clear()`、不 abort、不删 sessionStorage；是否停任务只由用户点"停止"决定；
- **关闭后无人认领的流必须回收**：若某 session 被关闭且不再重新打开，其流在"宽限期"（默认 60s，可配）内无人订阅则释放连接与定时器，Store 条目转入终态快照；否则长开会积累 fetch + 重连定时器（v1.14 新增，原文遗漏，是资源泄漏口）；
- **关闭最后一个 Tab**：自动新建一个空会话 Tab，不出现空白页或死路由；
- **刷新页面**：Store 丢失后，仅恢复当前 session 的原子快照（4.6 已定义）；多 Tab 集合从 sessionStorage 恢复并以 URL 指向的会话为激活项，恢复后集合中仍有活动的 session 必须在标签栏显示其运行态。

|---|------|-----------|
| V1 | A 发消息 → 切 B 发消息 → 切回 A | A 的 `executionSteps` 单调增长且**全程 POST 次数=2**（A、B 各 1）、无重复 GET 建连；切 Tab 期间 A 的 seq 连续无跳号（v1.15 修正：原断言"AbortController 引用不变"属 Store 内部字段，页面不可观测，改为可观测口径） |
| V2 | 同一会话从历史页"继续"两次 | 只产生 1 个 Tab、1 次会话初始化、1 次 POST；标签集合长度=1 |
| V3 | 关闭正在运行的 B Tab | A 的 step 不受影响；B 的 Store 条目在宽限期后释放；B 未被 abort（任务仍在后端跑），且重新打开 B 可按 seq 续看 |
| V4 | 切 Tab 触发 URL 变化 | 会话重初始化调用次数=0；`useChatInit` 跳过标记生效 |
| V5 | 离开 `/` 去 `/settings2` 再返回 | Tab 集合完整保留、激活项不变、运行态点仍正确 |
| V6 | 并发隔离（补 6.2 的"需实测"） | A/B 同时跑各自任务，工具执行、token 统计、HITL 授权弹窗互不串台（各自 confirmId 归属正确） |
| V7 | 资源上限 | 达上限后"新建"禁用并提示；超限请求不发 POST |
| V8 | 回归 | 本文 P1~P9 与 fre2e_01~12 全绿；P3 Journal 回放与 Store 快照/实时流并存时，按 4.6 的 `(type, step, seq)` 去重规则合并，事件不重复渲染、`final`/`final_stats` 各只一条 |

#### 6.3.6 实施硬约束（红线，违反即打回）

1. **禁止视图内实例化流**：`ChatSessionView` 及其子组件一律不得直接调用 `useSSE` / `useChatStreaming` / `useSessionTasks` 的独立实例；流、任务、授权数据只能经 `useChatStreamSession(sessionId)` 从 Store 读取。这是 6.1.2「每 session 仅 1 个 task id、1 次 POST」的落地保证。
2. **禁止改写流内核语义**：多会话层只做"订阅与显示"，不得改动 `useSSE` 的重连、退避、`after_seq`、轮询观察、错误分类逻辑。
3. **禁止双写**：视图不得再 `setExecutionSteps` / `setIsReceiving` / `setServerTaskId`（v1.9 已定 Store 动作为唯一写入口），只读快照 + 订阅。
4. **禁止把 `default-session` 当 Store key**：必须真实 `sessionId`（v1.9 已定）。
5. **禁止隐式全局事件**：跨模块通信只用显式回调/Context（弃用 CustomEvent）。
6. **禁止 `destroyInactiveTabPane={false}` 式全量保活**：非激活会话视图懒挂载且只保 Store，不保多份 DOM 与定时器；antd Tabs 只用作视觉容器，会话视图由自维护集合控制挂载。
7. **禁止在第 1~5 章 + 第七章未交付时开工**（6.5 时序门）：P1 是数据前提，第七章 Journal 是恢复前提，且两者与本章争用同一批核心文件（前端 `useSSE`/`useChatStreaming`/`useChatFacade`，后端 `agent_runner`/`stream_orchestrator`），未交付即开工会造成回归无法归因。

#### 6.4.2 三种候选布局（画图对比）

**方案甲：顶部标签栏（Tab 栏）——后续候选**

```
┌────────────────────────────────────────────────────────────┐
│ [会话Tab栏]（新增，高约 40px）                                │
│   ┌(会话A)─┐  ┌(会话B ●运行中)┐  ┌(会话C)─┐   [+ 新建会话]   │
│   └────────┘  └──────────────┘  └────────┘                  │

│ ┌─────────────┐ ┌────────────────────────────────────────┐ │
│ │ 左列 25%    │ │ 右列 75%                                │ │
│ │ 会话B任务清单 │ │ 会话B执行步骤流(实时, 切走时继续累积)      │ │
│ └─────────────┘ └────────────────────────────────────────┘ │
│ [任务信息条]  [输入区]                                      │
└────────────────────────────────────────────────────────────┘

交互语义：
· 点其他 Tab    → 下方整块立即换成那棵会话（后台流照跑，切回即续显）
· 历史页"继续"  → 顶部自动新增一个 Tab 打开该会话（不再跳转换页）
· Tab 尾部 ×    → 关闭视图但保留运行中的任务；需要停止时另行点击“停止任务”
· "＋新建会话"  → 新建一个空会话 Tab
· ● 红色圆点    → 该会话正在实时运行中（未读提醒/运行态一眼可见）
```

**方案乙：左侧二级列表（邮箱式竖排）**

把多会话做成左侧导航下面的"第二层列表"，点列表项切换左侧整块：

```
┌────────┬───────────────────────────────────────────────────┐
│ 全局菜单 │  ↓ 整块是"当前选中会话"（无 Tab 栏）                 │
│ 对话任务 │ ┌─────────────┐ ┌──────────────────────────────┐ │
│ ┌────┐ │ │ 左列 任务清单  │ │ 右列 步骤流                   │ │
│ │会话A │ │ │ ...          │ │ ...                          │ │
│ │会话B●│ │ └─────────────┘ └──────────────────────────────┘ │
│ │会话C │ │ [任务信息条] [输入区]                             │
│ │ 新建 │ │                                                  │
│ └────┘ │                                                  │
│ 历史会话 │                                                  │
└────────┴───────────────────────────────────────────────────┘
缺点：①与全局菜单抢左栏空间；②"会话"和"页面导航"两个层级混在一起，用户难分清点哪个；
③竖排列表占位大，会话一多需要滚；④顶部没有"我在哪几个会话之间"的全局视野。
```

**方案丙：左右双屏并行（同时显示两个会话）**

把两个会话的整棵 SessionLayout 左右并排：

```
┌────────────────────────────────────────────────────────────┐
│ ┌─────────────┐ ┌────────────────────────────────────────┐ │
│ │ [会话A整棵]  │ │ [会话B整棵]                              │ │
│ │ 左列+步骤+输入│ │ 左列+步骤+输入                           │ │

│ (独立接收各自流)  (独立接收各自流)                             │

优点：能"同一屏同时看/比对"两棵。缺点：①屏幕极挤；②输入区/taskinfo 重复两份难操作；
③会话 ≥3 直接放不下、不可扩展；→ 只适合偶尔比对，不是"多会话日常"主形态。
```

## 七、后端 event_log 持久化、300 秒后回放与重启恢复设计（v1.7）

> 编写人：小欧 2026-09-25 13:42:29
>
> 本章针对本地后端已核实的三个缺口：①`event_log` 仅存在 `StreamBuffer.event_log` 内存列表；②任务结束后 300 秒调用 `reclaim_stream_buffer()` 删除内存缓冲；③后端重启后没有可按 `task_id + seq` 回放的持久事件源。
>
> 本章与 [63] P1/P2 的关系：P1/P2 主要解决前端页面生命周期；本章是后端 P3，解决前端刷新/断线恢复依赖的后端数据耐久性。**本章不改变 [70] ConnectionScope 的连接池所有权方案。**

### 7.1 需求边界与可实现目标

本章将“恢复”拆成四个等级，禁止混淆：

| 等级 | 目标 | 可实现性 |
|------|------|----------|
| R1 内存级续传 | 任务运行期间断线，按 `after_seq` 从 `event_log` 续传 | 当前已支持 |
| R2 终态事件回放 | 任务完成且内存缓冲回收后，从持久 journal 按 `task_id + seq` 精确回放全部 SSE 事件 | 本章新增 |
| R3 后端重启后已完成任务回放 | 后端重启后，已完成任务仍可回放持久事件 | 本章新增 |
| R4 后端重启后继续计算未完成任务 | 重启后从 LLM/tool checkpoint 继续执行 | **不在本章实现**，需独立的 Agent checkpoint/resume 方案 |

**关键诚实边界：**后端重启后可以让已完成任务的事件不丢，也可以回放已落库事件；但后端进程已经消失，不能凭空继续一个未完成的 LLM/tool 执行。R4 不得伪装成“事件持久化已解决”。

### 7.2 当前代码证据与缺口

| 现状 | 代码证据 | 结论 |
|------|----------|------|
| `event_log` 是内存列表 | `backend/app/services/task/task_state.py:35-60` | 进程退出即丢失 |
| 事件序号由 `len(event_log)` 分配 | `task_state.py:46-55` | seq 是内存数组偏移，DB 不能直接替代它 |
| 完成后 300 秒回收内存缓冲 | `backend/app/services/agent/agent_runner.py:761-765` | 300 秒是内存回收点，不是数据保留期限 |
| 重连只查内存 buffer | `stream_orchestrator.py:614-625` | buffer 不存在直接 `not_found` |
| 事件步骤另有 DB 落库 | `agent_runner.py:429-464`、`chat_task_steps` | 这是历史步骤持久化，不是完整实时事件 journal；chunk/thought-start 等不能等价替代 event_log |
| 重连端点已存在 | `chat_routes.py:116-122` | 不需要新建重复端点，只需扩展数据源 |

### 7.3 目标架构：内存快路径 + SQLite 事件 Journal

```text
Agent publish
    ↓
StreamBuffer.publish（分配唯一 seq）
    ↓
StreamEventJournal.append(task_id, session_id, seq, event_type, payload)
    ↓ 持久化成功
StreamBuffer.event_log 可见并唤醒 SSE reader
    ↓
内存快路径：300 秒内直接从 event_log 读取
    ↓
内存缓冲回收后：GET /chat/stream/{task_id}?after_seq=N 改读 SQLite Journal
```

**唯一事件写入原则：**`event_log.seq` 和 `chat_stream_events.seq` 必须使用同一个分配结果；禁止前端重新编号、禁止 DB 另行生成 seq、禁止恢复时按时间猜测顺序。

### 7.4 数据表与索引设计

新增 `chat_stream_events`，不改变现有 `chat_task_steps` 的历史职责：

```sql
CREATE TABLE IF NOT EXISTS chat_stream_events (
    task_id TEXT NOT NULL,
    session_id TEXT NOT NULL,
    seq INTEGER NOT NULL,
    event_type TEXT NOT NULL,
    payload_json TEXT NOT NULL,
    created_at TEXT NOT NULL,
    PRIMARY KEY (task_id, seq)
);

CREATE INDEX IF NOT EXISTS idx_stream_events_session
    ON chat_stream_events(session_id, created_at);

CREATE INDEX IF NOT EXISTS idx_stream_events_type
    ON chat_stream_events(task_id, event_type, seq);
```

字段约束：

- `task_id + seq` 唯一，保证同一任务事件顺序和幂等写入；
- `payload_json` 保存完整事件 dict，包含 `seq`，不能用业务 Step 编号替代；
- `event_type` 仅为查询和诊断索引，SSE 白名单仍由 `stream_orchestrator._SSE_FORWARD_TYPES` 统一决定；
- 不新增事件总线注册表，不引入第二套事件类型白名单；
- 不把 `chat_task_steps` 复制一份作为 event journal，避免 DRY 违规和双源不一致。

### 7.5 写入路径：先持久化、后对 SSE 可见

当前 `StreamBuffer.publish()` 在 `task_state.py:46-56` 内分配 seq 并追加内存。为保持 `task_state.py` 不依赖 DB，改造为**依赖注入的发布 sink**：`create_stream_buffer(task_id, event_sink)` 接收由 `agent_runner` 注入的 `StreamEventJournal.append` 能力；`task_state.py` 只负责 seq、锁、内存可见性，不 import DB、不执行 SQL。

1. `StreamBuffer` 增加任务级 `publish_lock`，保证同一 task 的 seq 分配与 journal 写入不并发交叉；
2. 在锁内取得当前 `seq`，复制事件并补入 seq；
3. **不持有 `buffer.cond` 锁执行 DB await**，避免阻塞生产者和 SSE reader；
4. 调用 `StreamEventJournal.append()` 写入 SQLite；
5. journal 成功后再在 `buffer.cond` 内追加 `event_log` 并 `notify_all()`；
6. journal 失败时执行有限重试；仍失败则记录 `stream_persistence_degraded`，继续当前实时流，但明确标记该 task 不具备 R2/R3 保证；
7. 终态 `final_stats` 写入失败必须保留错误日志和 degraded 状态，不能伪装成已持久化。

**禁止方案：**

- 先放内存、后异步落库：进程在两步之间崩溃会丢事件；
- 持有 `buffer.cond` 锁等待 SQLite：会阻塞生产者和 SSE 消费；
- DB 失败直接 `task.cancel()`：把存储故障扩大成任务执行故障；
- 每个事件单独创建连接/事务：违反 DRY/KISS，增加 SQLite 写放大。

#### 7.5.1 正常路径与直连路径的 sink 注入

当前正常路径在 `stream_orchestrator.py:359` 创建 `StreamBuffer`，而 `agent_runner.py:261-265` 还会为直接调用入口补建 buffer。两条路径必须统一注入 Journal sink：

```text
stream_orchestrator 正常路径
  → create_task_stream_buffer(task_id, session_id, journal_sink)

agent_runner 直连兜底路径
  → create_task_stream_buffer(task_id, session_id, journal_sink)

两条路径均禁止裸调用 create_stream_buffer(task_id)
```

`create_task_stream_buffer()` 是唯一创建入口，负责组装 `StreamBuffer + StreamEventJournal sink`；`task_state.py` 不 import DB，`agent_runner.py` 不自行拼装第二套 sink。否则正常聊天任务会只写内存，第七章目标失效。

#### 7.5.2 高频事件性能与背压边界

“先持久化后可见”不能无上限地把 SQLite 延迟加入实时链路。实施前必须以真实流量确定：

- `action/observation/final/final_stats` 等低频关键事件：单事件事务持久化；
- 高频 `chunk`：在同一 task 的 publish lock 内做有界批量提交，批次必须有最大条数/字节数和最大等待时间；
- Journal backlog 超过预算：进入 `stream_persistence_degraded`，实时流优先，记录缺口 seq，禁止宣称精确回放；
- 任何批量策略不得改变 seq 单调性，不得让 consumer 看到未持久化事件；
- 必须完成 SQLite 真实压测，至少验证长 chunk 流、工具并发、DB busy、磁盘写失败和清理并发；
- 未完成压测前不得把“每事件同步写 SQLite”直接定为最终实现。

### 7.6 读取路径：内存优先，Journal 兜底

`GET /chat/stream/{task_id}?after_seq=N` 保持现有 API，不新增重复端点：

```text
1. get_stream_buffer(task_id)
   ├─ 存在：继续使用当前 stream_reader(event_log, after_seq)
   └─ 不存在：进入 journal_reader(task_id, after_seq)

2. journal_reader 查询 seq > after_seq，按 seq 升序读取
3. 复用同一 format_agent_sse 和同一 _SSE_FORWARD_TYPES 白名单
4. 读到 final_stats/终态后结束
5. journal 有事件但没有终态：
   - task 已完成但 journal 尚未有终态：返回 task_state_incomplete，禁止伪造完成
   - task 未完成且后端已重启：返回 task_interrupted，前端进入历史降级
6. journal 无事件且 DB 无该 task：返回 not_found
```

**一致性要求：**

- `after_seq=N` 只返回 `seq >= N` 的事件；现有前端使用 `lastSeq + 1`，因此不得重复发送已处理事件；
- 回放使用和实时流相同的 `format_agent_sse`，禁止新增第二套 SSE 格式器；
- 回放不得启动新 Agent，不得调用 POST 编排入口；
- `not_found`、`task_interrupted`、`persistence_gap`、`persistence_degraded` 必须是明确错误事件，禁止都伪装成正常空流。

#### 7.6.1 Journal seq 缺口与降级状态

Journal reader 读取时必须校验首个 seq、连续 seq 和终态 seq：

```text
连续：after_seq+1、after_seq+2、…，允许精确回放
缺口：发现 seq 跳跃 → 发 persistence_gap，记录缺口范围，禁止宣称完整恢复
降级：Journal 写入失败但内存流继续 → 发 persistence_degraded，R2/R3 保证失效
```

`persistence_gap` 不得被前端当作正常 `final`；前端只能进入历史降级或显示“部分事件不可恢复”。

### 7.7 300 秒回收语义修正

当前 `loop.call_later(300, reclaim_stream_buffer)` 的语义应改名为：

```text
reclaim_memory_buffer(task_id)
```

它只释放：

- `StreamBuffer.event_log` 内存列表；
- `buffer.cond` 和 `buffer.done` 运行态对象。

它**不得删除** `chat_stream_events` 数据。改造后：

| 时间/状态 | 内存缓冲 | Journal | GET 续传 |
|-----------|----------|---------|----------|
| 任务运行中 | 保留 | 持续追加 | 内存快路径 |
| 任务结束 0-300 秒 | 保留 | 保留 | 内存快路径 |
| 任务结束超过 300 秒 | 回收 | 保留 | Journal 回放 |
| 后端重启、任务已完成 | 丢失 | 保留 | Journal 回放 |
| 后端重启、任务未完成 | 丢失 | 可能有部分事件 | `task_interrupted`，不继续计算 |

### 7.8 数据保留与清理策略

- 300 秒只控制内存，不控制 SQLite 数据；
- Journal 清理必须按 `task_id` 终态和时间保留期执行，禁止在请求链路中全表扫描；
- 清理任务只删除已终态且超过保留期的事件，活跃 task 永不删除；`final_stats` 缺失不能成为永久不清理条件；
- `final_stats` 只用于校验正常完成，任务终态以 `chat_tasks.status` 为权威；
- 清理失败只记录 warning，不能阻断聊天主链路；
- 具体保留时长使用 `tuning` 配置集中管理，禁止在多个模块写死 300 秒或 7 天；
- 清理前必须确认 `chat_tasks.status` 已进入终态；未终态但已过保留期的任务进入人工诊断/隔离，不得直接删除。

### 7.9 后端重启后的恢复语义

后端启动时不能把旧 `agent_streams` 假装恢复。正确语义：

```text
journal 存在 + task 终态
  → 允许 GET after_seq 回放

journal 存在 + task 非终态
  → 返回 task_interrupted
  → 前端加载 DB 历史
  → 如需继续计算，另立 checkpoint/resume 方案

journal 不存在
  → 查询 chat_tasks
  → 有终态历史则加载历史
  → 无任务记录则 not_found
```

本方案不实现 Agent checkpoint、LLM 调用恢复、工具执行恢复，也不宣称“后端重启后任务自动继续”。这是两个不同问题，不能混为一谈。

#### 7.9.1 终态权威与前端状态

为避免 DB、Journal、SSE、前端四层状态互相覆盖，固定权威如下：

| 状态 | 唯一权威 | 其他层职责 |
|------|----------|------------|
| 后端任务是否终态 | `chat_tasks.status` | SSE/前端不得自行推断终态 |
| 事件是否可回放 | Journal seq 连续性 + `final_stats` | 前端只消费回放结果 |
| 前端是否正在接收 | Store 快照 `isReceiving` | 页面卸载不改变后端任务状态 |
| 最终展示内容 | DB 已完成步骤/最终响应 | Journal 用于事件回放，不替代 DB 权威 |

`final_stats` 是事件协议终态信号，不取代 `chat_tasks.status`；Store 的 `isReceiving` 是 UI 状态，不取代后端状态。

### 7.10 10 大规范对照

| 规范 | 设计落点 |
|------|----------|
| SRP | `StreamEventJournal` 只负责 journal 读写；`StreamBuffer` 只负责运行态缓冲；reader 只负责读和 SSE 转发；agent_runner 只负责调用发布入口。 |
| DRY | journal 回放复用现有 `format_agent_sse`、`_SSE_FORWARD_TYPES` 和 GET 路由；不复制 SSE parser/白名单。 |
| KISS-DIRECT | 内存快路径 + SQLite fallback；不引入 Redis、消息中间件、事件总线注册表。 |
| SLAP | DB 持久化不写进 `stream_reader`；SSE 转发不执行 SQL 清理。 |
| YAGNI | 不实现 R4 计算恢复，不实现跨标签事件总线，不复制 `chat_task_steps`。 |
| OCP | 新事件类型仍由现有 publish 和白名单登记，不修改 reader 分支体系。 |
| LSP/ISP | Journal 提供 append/read/retention 三个明确接口；调用方不直接操作表连接。 |
| 禁止 backward | 不保留“内存-only”和“DB-only”两套运行路径；内存是快路径，Journal 是唯一耐久源。 |
| 复用优先 | 复用现有 seq、stream_reader、format_agent_sse、chat_routes、chat_task_steps 终态数据。 |
| 三堂会审 | 逐项审查锁范围、seq 连续性、失败降级、重启语义、清理竞态和前后端契约。 |

### 7.12 验收门

必须全部通过：

1. 事件写入后进程被杀，重启后已完成任务可按 `after_seq` 回放；
2. 任务结束超过 300 秒后，GET 仍能回放终态前后的完整事件；
3. `seq` 严格连续、无重复、无跳号，`after_seq` 边界正确；
4. 正常 orchestrator 创建路径和 agent_runner 直连路径均注入 Journal sink，任一路径不得漏写；
5. chunk/thought-start 等实时事件与 action/observation/final 的回放策略符合白名单；
6. 高频 chunk 压测满足实时延迟预算，Journal backlog 超限能进入 degraded；
7. Journal seq 缺口能返回 `persistence_gap`，不静默跳过；
8. 内存回收不删除 Journal；
9. 后端重启且任务未完成时返回 `task_interrupted`，绝不重新启动或伪造完成；
10. Journal 写入失败有 degraded 日志，实时主链路按设计降级且不误报已持久化；
11. Journal 清理不删除活跃任务和未终态任务，且不因缺失 final_stats 永久泄漏；
12. 现有实时 SSE、取消、暂停、HITL、配置热重载和 [70] ConnectionScope 测试全部回归通过；
13. 通过合规、合理、关联逻辑三堂会审，未引入状态双源、重复解析器、无效抽象或 backward 分支。
