## 一、问题描述（北京老陈提问 2026-09-13）

用户观察到：页面左侧菜单栏的折叠按钮，在 **Edge 浏览器全屏**时可见；在 **Chrome 浏览器**下不可见。对 Chrome 进行页面缩放操作后发现，不只是折叠按钮——**右侧会话页面底部的输入框、输入框下面的模型选择整条，全都被隐藏到屏幕下方不可见**。

用户怀疑是否"不同浏览器在缺省全屏时存在不同的显示问题"。

**2026-09-13 用户补充现象（v1.2）**：Edge 浏览器**窗口缩小**时，页面能随窗口大小变化（左右、上下都跟随），页面各个部分都能在窗口内看到、无隐藏；而 **Chrome 浏览器窗口缩小**时，页面不跟随——只是窗口变小了，页面周边主要是**右侧、下侧**都隐藏到窗口外。

## 二、分析结论

### 2.1 直接回答用户疑问

**不是**"不同浏览器（Edge/Chrome）CSS 解析差异"导致，Edge 与 Chrome 同为 Chromium 内核，对 `100vh` 等属性的解析完全一致。真相是：

> **同一布局缺陷（高度链断裂 + 硬编码高度 + overflow 失效）在不同视口可用高度下的不同表现。**

- **Edge 全屏（F11）**：视口可用高度较大（浏览器 UI 基本全隐藏），`calc(100vh-59px)` 计算出的可用高度仍不小于页面内容自然高度 → 折叠按钮、输入框、模型条可见；
- **Chrome 缺省窗口**：视口被标签栏 + 地址栏 + 书签栏占用，可用高度变小；在"缩小窗口或页面缩放放大后，可用高度 < 页面内容自然高度"时，底部整条被推出屏幕，且因滚动链断裂滚不回来；
- **缩放后仍看不见**：页面缩放（zoom>100%）下，CSS 布局视口变小（物理窗口/zoom）、物理渲染像素成比例放大，页内写死常数（如 59px）与 `100vh` 的实际比例随之漂移 → 底部超出的那一段被等比例放大，物理视口内看不到、也滚不回来。

### 2.2 Edge/Chrome 缩窗行为差异归因（v1.2 补充）

用户补充现象：Edge 缩窗页面跟随自适应，Chrome 缩窗页面不跟随、右/下侧藏窗外。**这仍是同一病根，不是新病因**，理由：

1. **布局缺陷的本质是"页面跟着内容走、不跟视口走"**：`minHeight:100vh`（可撑高）+ `calc(100vh-59px)`（写死常数）+ Content overflow 失效（父链无固定高度）三者叠加，页面尺寸由内容量决定，而非视口。窗口尺寸、缩放级别、DPI 这类**环境变量**只要与内容偏移量失配，超出的部分就暴露在外且滚不回来。
2. **Edge 表现好的原因是恰好处在"环境变量匹配区"**：100% 缩放、视口高度 ≥ 内容自然高度时，布局贴在视口内，缩窗时 `100vh` 重新计算 → 页面跟随缩放，看起来完全正常。
3. **Chrome 表现差的强嫌疑点：浏览器级页面缩放（zoom）≠100%**。CSS 像素被放大后实际渲染尺寸超过视口 → 右侧、下侧被挤出，且滚动链断裂无法滚回。这与用户"曾对页面做缩放操作（Ctrl+滚轮）"或 `chrome://settings` 页面缩放被调过直接相关。
4. **就地验证法**：Chrome 内按 `Ctrl+0` 复位页面缩放后再缩小窗口——若现象消失，即证明是同一布局缺陷 + zoom 环境变量所致，病根未变。

### 2.3 根因链（四个关键断点）

1. **高度链只有 `min-height` 下限、没有 `height` 锁定**：`#root`（index.html:27）、外层 `Layout`（L572）给的都是 `min-height:100vh`，语义是"至少这么高"，**不阻止内容把页面撑更高**。`html/body` 无任何高度定义，正文高度由内容自然撑开——即整条高度链只有"下限守卫"，没有"顶部封顶"，内容涨一行、整页涨一行。
2. **右侧 Content 的 `overflow: auto` 失效**：`overflow: auto` 只在容器高度被**固定约束**时才产生内部滚动条；父链无人提供固定高度 → Content 不滚动，而是把外层一直撑大。
3. **Sider 被 flex 拉伸**：antd 布局是 flex 行，`Sider` 默认被 `align-items: stretch` 拉伸到与整行同高，行高 = 外层被撑高的高度 → Sider 全身拉长，底部折叠 trigger 按钮随之落出屏幕下缘。
4. **ChatPage 硬编码 `calc(100vh - 59px)`**：以写死的 59px 常数假设计算可用高度；该常数与真实可用空间（随缩放/DPI/浏览器 UI 占用/滚动条宽度变化）不匹配时，输入框与模型条被整体顶出视口。

## 三、代码依据（文件:行号）

### 3.1 外层 Layout 仅 `minHeight`（根因 1）

```
frontend/src/components/Layout/index.tsx:572
<Layout style={{ minHeight: '100vh' }}>
```

`#root` 与 `min-height` 只设下限，允许内容无限撑高；Layout 是页面骨架里**最外层唯一显式设高度的组件**，其只给 `min-height` 即等于向整棵内容树宣布"高度随意涨"，是整条高度链断裂的决策源头。

### 3.2 Content `overflow: auto` 父链无固定高度（根因 2）

```
frontend/src/components/Layout/index.tsx:725-733
<Content style={{ margin: 0, padding: '6px 6px 10px 6px', background: '#f8fafc', borderRadius: 12, minHeight: 400, overflow: 'auto' }}>
```

`overflow: auto` 必须在容器高度受约束时才有滚动效果；其父链（右侧 Layout L609 → 外层 Layout L572）中右侧 Layout 未设任何高度样式（高度由内容撑开），外层 Layout 仅 `minHeight:'100vh'`，均未提供固定高度给 Content——故 overflow 滚轮始终无效，底部被顶出后无法滚回。

### 3.3 Sider 被 flex 拉伸（根因 3）

```
frontend/src/components/Layout/index.tsx:593-605
<Sider width={180} theme="light" collapsible collapsed={collapsed} onCollapse={setCollapsed} ...>
```

antd 外层 Layout 为 flex 行布局，Sider 默认被 `align-items: stretch` 拉满整行高度；行高一旦被内容撑过视口，Sider 底部（折叠 trigger）即超出屏幕下缘。

### 3.4 ChatPage 硬编码高度（根因 4）

```
frontend/src/pages/ChatPage.tsx:224
height: 'calc(100vh - 59px)', // 2026-08-30 小欧: 精确贴合Content内容区高度=Header43+padding上6下10; 原calc(100vh-120px)矮61px致底部空白, height:100%会随父级撑高掉屏外, 两者均废弃
```

注释已自证：`calc(100vh-59px)` 是对"父级撑高掉屏外"的规避补丁，但 59px 是写死常数，一旦运行时 `100vh` 与 59px 差值失配（缩放/DPI/浏览器 UI 高度变化），Chrome 下即出现"输入框 + 模型条整条在屏幕下方不可见"。

### 3.5 全局高度链仅有 `min-height` 未锁定高度（根因旁证）

```
frontend/src/index.css:10-13
/* 全局样式：仅保留盒模型，不覆盖 AntD reset.css（避免全站 Card/Settings 被击穿） */
* {
  box-sizing: border-box;
}
```

```
frontend/index.html:16-29（内联骨架屏 CSS）
* {
  box-sizing: border-box;
  margin: 0;
  padding: 0;
}
body {
  background: #f5f5f5;
  font-family: -apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif;
}
#root {
  min-height: 100vh;
}
```

全局唯一的高度定义是 `#root { min-height: 100vh; }`（index.html:27-28）——与外层 Layout 的 `minHeight:'100vh'` **同属性同语义**（"至少这么高"，不阻止内容撑高），且 `html/body` 无任何 height 定义。整条高度链只有 min-height 度量的"下限"，没有 height 度量的"锁定"，内容撑高时全线跟着长。**3.5 不主张推翻"不覆盖 AntD reset"决策**，只需在既有 CSS 中**追加**高度链，不影响该决策本身。

### 4.2 实验验证记录（2026-09-13 小欧 v1.3 补）

2026-09-13 为"坐实病根、排除引擎差异"，做了三轮受控实验（复刻 HTML + Playwright 双引擎 + CDP 缩放模拟，指标逐项量化），**结论：headless/CDP 模拟浏览器缩放不可行，三次实验均未复现真实缺陷，且 Edge 与 Chrome 行为完全一致**。

| 轮次 | 实验方法 | 结果 | 结论 |
|---|---|---|---|
| 实验1 | `Emulation.setPageScaleFactor` 模拟 Chrome zoom 0.95/1.10/1.25 + Edge/Chrome 同视口对比（6组） | 全部同指标可见，未复现 | 引擎一致性成立；但 `setPageScaleFactor` 只做**显示像素缩放、不改布局视口**，与真实浏览器 zoom（改变 CSS 视口+渲染放大）机制不同，模拟方法无效 |
| 实验2 | 内容超高（消息8/30条）× 窗口缩小（900/700）× Edge/Chrome（8组），测 bodyScrollable、可达性 | 全部自洽可见、两引擎指标逐项相同 | 内容超高+缩窗本身不会触发缺陷；复刻仅有布局骨架，缺真实页面内容压力，仍无效 |
| 实验3 | zoom 等效 CSS 视口缩小（1440→1152→960，即物理 1440 被 zoom 125%/150% 剩下的 CSS 空间），Edge=100% 对照组 | 各视口下页面均按 `100vh` 重新计算、完全自洽 | **CSS 视口变小本身不触发缺陷**；真实缺陷依赖浏览器**真实页面缩放渲染**（zoom>100% 时布局像素·缩放值超出物理视口且滚动链断裂），而该缩放无法用 headless 注入 |

**实验总体结论**：
1. 三轮受控对比 Edge 与 Chrome 指标**逐项一致** → 再次证实 2.1 结论：非引擎解析差异；
2. 缺陷出现在"页面布局像素 × 浏览器真实缩放值 > 物理视口"这一组合下，依赖**浏览器持久化的页面缩放（zoom）环境变量**，headless/复刻法均无法携带该环境 → 唯一可行且准确的验证方法见 4.3。

### 4.3 可行且准确的验证方法（真机双浏览器实测，四步法）

**前置**：以 Edge 为参照（已知 Edge 正常），全程只动缩放与窗口，不改任何代码；按顺序执行，每步记录底部三元素（折叠按钮 / 输入框 / 模型条）的可见性与是否跟随窗口。

| 步骤 | 浏览器 | 操作 | 预期现象 | 判定 |
|---|---|---|---|---|
| ① | Edge | 打开会话页 → `Ctrl+0` 复位缩放 → 缩小窗口 | 页面跟随窗口，底部三元素全部可见 | 基线：布局在"正常缩放"下无缺陷 |
| ② | Chrome | 打开会话页 → `Ctrl+0` 复位缩放 → 缩小窗口 | 底部/右侧恢复正常（跟随窗口） | 证实：Chrome 此前"不跟随、藏窗外"由**持久化缩放(zoom)!=100%**触发 |
| ③ | Chrome | `Ctrl+0` 复位后 → `Ctrl+滚轮` 放大至 125% → 缩小窗口 | 底部/右侧藏窗外、且无法滚回 | 复现用户"Chrome 缩窗不跟随"现象 |

**判定逻辑**（修复前用于确认病根）：
- ①②通过 → 复位缩放后双浏览器一致 → 病根确为布局缺陷，zoom 只是环境触发变量，修复方向按第四章四文件方案；
- ③④同现 → 双浏览器同病根，排除引擎差异 → 与 4.2 实验结论互证；
- 若 ② 复位后仍不正常 → 存在非 zoom 因素，需带着页面停留现场重新溯源（不属本文假设范围）。
