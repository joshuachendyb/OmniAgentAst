## 摘要

本文档对「SSE 断线重连后，后端已发过的事件是否/为何会**重复发送**」进行完整分析与处理方案定稿。核心结论：

1. **重连不需要重复发**——只需补发「断点之后」未收到的新帧；**重复发不好**（chunk 增量二次拼接、步骤双份渲染）。
2. 重连机制本质是**传输可靠层**，与「订阅(yield) / publish」两代事件生产机制**无关**，一套代码跨两代共用、行为等价。
3. **最高准则（定稿）**：重连重复的根治**只该动 2 处**——**① offset 续传（源头不重发）② lastSeqRef 基线（前端精确续传与幂等校验）**。凡与此准则不一致的方案（叠守卫/改守卫/白名单/buffer 回收等）一律清理，只保留与本准则准确一致的思路。
 
  2 个点就能根治重复:① 后端 offset 从 lastSeqRef+1 续传(源头);② 前端 lastSeqRef 单调推进(基线)。 因为:
  后端 event_log seq 全局连续单调递增;
  TCP 流有序,不存在乱序;
  final 之后无业务帧,不存在"终态后晚到业务帧"。
4. **定理（准则的依据）**：后端 event_log 的 seq 全局连续单调递增 + TCP 流有序非乱序 + final 之后无业务帧 → **源头(offset 续传)与基线(lastSeqRef)闭合即根治，天然无第三者需要拦截**。
5. 两道核心现状**已全部就位且正确**（无需改动）：offset 续传（`stream_orchestrator.py` offset=after_seq）+ 前端 `?after_seq=` 续传、lastSeqRef 基线（单调推进 + S3 校验），09-12 P0-1 已消除基线比较的 string/number 失真。实现层残留（lastUsageSeqRef 第二基线等）见第七章整改清单。
6. 处理分工全景：后端 seq 注入与 offset 续传、前端 lastSeqRef 基线均体现 2 处根治；其余「待实施/可选」项（T2 白名单化、buffer 回收等）经准则检定**移出本方案**（属另一问题域或补丁，不属重连重复根治）。

**实证版本基线**：本文以当前 HEAD（`4bf3ea987`，2026-09-12）前端/后端代码实读为准，均已标注文件+行号；历史面基于代码注释记载（含编辑历史）。

## 一、问题定义

### 1.1 重连成功后需要重复发吗？

**不需要。** 断线只代表「断点之后」的新帧没收到；已收到并处理过的帧（前端已按 seq 推进 `lastSeqRef`）重连后应跳过。重连的职责仅是**续传**，不是**重播**。

### 1.2 重复发好吗？

**不好**，具体危害：

| 重复对象 | 危害 |
|---------|------|
| chunk（正文字符流） | chunk 是逐字增量数据，重复 = 正文二次拼接、run-on 叠加 |
| thought（推理） | 实时 thought + 回放 thought 双通道重复显示（G1 同源） |
| step 类（start/action/observation/final） | 步骤双份渲染、快照错位、计数重复 |
| 终态后帧（final 之后的业务帧） | 污染已完结渲染态（pendingSteps/executionSteps） |

### 1.3 前端要如何配合？

与最高准则唯一的配合路径：
1. **精确续传（核心②）**：重连请求带 `after_seq=lastSeqRef.current+1`，让后端只发断点后的帧（源头不重复）；
2. **基线幂等校验**：前端 `lastSeqRef` 单调推进，对重复帧按 `seq <= lastSeqRef` 吞掉（免疫能力）。

> 注：本版删除了早期「两条腿 + 作废守卫」表述——seq 幂等去重兜底即基线校验（`seq<=lastSeqRef`），**终态后作废守卫属补丁，按准则不采**。

## 二、重连机制的现状分析

### 2.1原貌（跨订阅/publish 两代共有）

重连是**传输可靠层**，不依赖事件如何产生，一套代码贯穿两代：

```
前端 lastSeqRef(已处理最大seq)
  → 重连 GET ?after_seq=lastSeqRef.current+1
  → 后端 stream_reader offset=after_seq             (stream_orchestrator.py/stream_reader)
  → 从 event_log 断点续读 → 逐帧 format_agent_sse 转发
  → 前端 sseParser 入口基线校验(seq<=lastSeqRef 拦截) → onSeq 推进 lastSeqRef
```

「重连复用同一函数（传 after_seq 续传），避免重复事件」为北京老陈 2026-07-12 拍定（`stream_orchestrator.py` 注释原文），早于 4C（09-06）两个多月。


### 2.2 现状防线（实证 + 准则检定）
| 防线 | 位置 | 与 2 处根治关系 | 准则检定 |
|------|------|----------------|---------|
| 后端每帧注入 seq | `task_state.py:44-54`（publish 重写 `seq=len(event_log)`） | offset 续传的前置（seq 供 offset 精确定位） | **保留**（核心①底座） |
| 前端精确续传 | `useSSE.ts:793` `?after_seq=${lastSeqRef.current + 1}` → 后端 `stream_reader` `offset=after_seq` | **核心① offset 续传** | 保留（已就位） |
| 前端基线校验 | `sseParser.ts:194-197`（`seq<=lastSeqRef` 拦截）+ `useSSE.ts:898/951`（onSeq 单调推进） | **核心② lastSeqRef 基线** | 保留（已就位） |

辅助点：
- `lastSeqRef` 初始 -1（`useSSE.ts:518`，首帧 seq=0 不被误拦）；新任务重置 -1（`useSSE.ts:779`）；重连**不断不重置**（保证续传基线连续）。
- 热路径与 done 收尾两路均推进 `lastSeqRef`（`useSSE.ts:898 / 951`）——基线唯一，两处各推进一次。

### 2.3 历史「一直没解决」的根因（实证）

两个历史根因横跨订阅/publish 两代，与 4C 改造无关：

1. **早期重连不带 after_seq（或从 0）**：前端重连请求未传断点，后端 stream_reader 从 event_log 头重播**全部事件** → 全量重复。09-10 S3 修复：改为 `after_seq=lastSeqRef.current+1`（正是核心②）。
2. **基线比较基准失真（真凶）**：早期守卫直接拿 `step.step`（后端下发为 string）与 `lastSeqRef`(number) 比较 → **string/number 比较恒 false → 守卫形同虚设**，重复帧一路漏进业务。09-12（本文落盘当日）P0-1 三堂会审修复：统一 `toStepNumber()` 归一化，使**基线校验真正生效**。

> 结论：历史上"代码里躺着守卫却从未生效"，是因为完成"基线推进/比较"的度量衡失配。修复 = **让基线正确**（P0-1），而非再加第三道防线。
## 三、设计原则：彻底修改改到最佳的模式逻辑

重连重复问题的根治逻辑可提炼为七条设计原则。每条遵循「根因 → 原则 → 实现 → 权衡」的推导结构，是事件流「发送-重连-消费」闭环的通用范式，适用于一切基于单调序号的事件传输系统：

### 3.1 单一计数权威原则（序号只由源头分配）

| 项 | 内容 |
|----|------|
| 根因 | 同一事件序号在系统多处各自计数，导致两套序号语义错位（历史病根一 6.6.2） |
| 原则 | 全局事件序号的分配权集中在**唯一源头**——生产者侧事件日志 |
| 实现 | 后端 publish 每帧 `seq=len(event_log)`，全局连续单调（`task_state.py:44-54`）；消费者（前端）只读不写、不复刻计数 |
| 权衡 | 序号来源唯一 → 物理上不存在"两套序号对不上"的可能；任何下游不得自造序号 |

### 3.2 单一下游基线原则（消费侧只持一条进度线）

| 项 | 内容 |
|----|------|
| 根因 | 消费侧为不同用途维护多份进度 ref，推进点散落、彼此不同步 |
| 原则 | 每个消费方只维护**一条**连续进度基线，作为断点续传与幂等去重的唯一依据 |
| 实现 | 前端 `lastSeqRef` 一条基线：初始 -1、单调推进、重连不断不重置；done 与热路径双路推进到同一 ref（`useSSE.ts:518/779/898/951`） |
| 权衡 | 进度单源 → 续传偏移与去重判断天然一致，无需多 ref 对账 |

### 3.3 断点续传原则（重发仅限断点之后）

| 项 | 内容 |
|----|------|
| 根因 | 早期重连未携带断点，后端从头重播全部事件 → 已消费帧全量重复（历史根因一） |
| 原则 | 重连请求必须携带消费方进度（断点），源头发送集 = 断点之后，绝不做全量重播 |
| 实现 | 重连 `GET ?after_seq=lastSeqRef+1`；后端 `stream_reader offset=after_seq` 从 event_log 断点续读（`stream_orchestrator.py`） |
| 权衡 | 补发集合由断点精确定义 → 断点正确性即治本关键；源头不重发，杜绝污染面 |

### 3.4 幂等去重原则（重复帧必须被静默吸收）

| 项 | 内容 |
|----|------|
| 根因 | 传输层不保证完全不重发（重试/抖动），消费侧必须自体免疫 |
| 原则 | 相同序号帧只生效一次：`seq <= 已消费基线` 的帧一律拦截丢弃 |
| 实现 | sseParser 入口基线校验 `seq <= lastSeqRef.current` 先于业务分发（`sseParser.ts:194-197`） |
| 权衡 | 去重置于消费入口 → 业务层永不接触重复；与 3.3 断点续传配合：源头少发 + 尾部兜底，双层闭合 |

### 3.5 度量衡一致原则（先归一化再比较）

| 项 | 内容 |
|----|------|
| 根因 | `step.step`(string) 与 `lastSeqRef`(number) 直接比较恒 false，守卫形同虚设（历史真凶，6.6.4） |
| 原则 | 一切序号比较前，参与比较的量必须落在同一类型/量纲 |
| 实现 | 入口统一 `toStepNumber()` 归一化后再推进/比较（`sseParser.ts:89/234` 等） |
| 权衡 | 单点归一化 → 比较恒可靠，消除"代码看似正确实则永不生效"的隐性缺陷 |

### 3.6 终态后无帧原则（无输入可拦的防线一律不建）

| 项 | 内容 |
|----|------|
| 根因 | 早期在源头+基线之外另建作废守卫，构成第二套度量衡（违规 SRP/YAGNI，6.6.6） |
| 原则 | event_log seq 全局连续单调 + TCP 有序 + final 后无业务帧 → 终态后物理上无新帧可拦；**一切"无输入可拦"的拦截层均不得新建** |
| 实现 | 作废守卫已退役删除，只保留 B2（源头断点续传）+ F2（尾部幂等吸收）两条直线 |
| 权衡 | 删除守卫零行为差异（本就拦不到任何帧）→ 清理即重构，不新增防线 |

### 3.7 单一实现原则（DRY：同一逻辑唯一实现）

| 项 | 内容 |
|----|------|
| 根因 | done 与热路径推进逻辑逐字复制；事件身份规则散落多处（6.6.3/6.6.5） |
| 原则 | 同一逻辑只实现一处：多处调用同一实现，规则单点定义 |
| 实现 | 基线推进单点实现（done/热路径共用）；thought「仅落库」身份由 `_SSE_FORWARD_TYPES` 白名单单点定义（未登记即不转发）；新增能力先查 FUNCTIONS.md 复用 |
| 权衡 | 改动只落一处 → 无隐式对账开销，行为恒定一致 |

**七条的层次关系**：3.1/3.2 定"序号权威"与"进度单源"（数据面基石）→ 3.3 定"断点续传"（源头防重）→ 3.4 定"幂等吸收"（尾部兜底）→ 3.5 定"比较可靠"（正确性前提）→ 3.6 定"防线边界"（不建无效层）→ 3.7 定"实现唯一"（DRY 纪律）。前四条约束事件流主链路，后三条约束代码质量与防线取舍。


## 四、新的概要设计（按第三章七原则）

按第三章七原则，目标形态**不是更多防线，而是更少**——七原则拆开只有「2 条真防线 + 5 条约束」。设计即两条直线，其余是全过程的纪律约束。

### 4.1 设计总览（双层闭合）

- **源头层（原则 3.3 断点续传）**：重连带 `?after_seq=lastSeqRef+1`，后端 `stream_reader offset=after_seq` 只发断点之后 → **源头不重复**。
- **尾部层（原则 3.4 幂等吸收）**：sseParser 入口 `seq<=lastSeqRef` 拦截 → **漏网重复必被吞**。
- 双层闭合：源头少发 + 尾部兜底，两条直线即根治；**不建第三条防线**。

### 4.2 防线表（只有 2 条真防线）

| 设计防线 | 依据原则 | 应落位置（设计语义，非现状坐标） | 设计要点 |
|---------|---------|-------------------------------|---------|
| B1 seq 后端唯一分配 | 3.1 单一权威 | 生产者计数侧（publish/append 唯一写入口，持锁原子 seq+追加） | 消费者只读不写、不自造序号；一处分配全局连续单调 |
| B2 源头断点续传 | 3.3 断点续传 | 后端流读取侧（stream_reader 以 offset 读缓冲） | 实时/重连同一咽喉点；只发断点之后，杜绝全量重播 |
| F1 前端单基线 + 精确续传 | 3.2 单一下游 | 前端连接层（重连请求侧） | 唯一 `lastSeqRef`：初始 -1/重置/重连不断；重连 `?after_seq=lastSeqRef+1` |
| F2 尾部幂等吸收 | 3.4 幂等去重 | 前端消费入口（入站解析侧） | `seq<=lastSeqRef` 拦截，先拦截再推进后放行，业务永不接触重复帧 |

> 本表只定义「防线该有的形态」，不绑定现状实现位置——**现状代码是补丁堆，不是蓝图**。对照 2.2 现状：现役 3 条防线正好就是这四条线里的 B1/B2/F1/F2，此后端源头少发 + 前端尾部兜底，双层闭合。

### 4.3 约束（非防线，全程纪律）

| 约束 | 依据原则 | 说明 |
|------|---------|------|
| seq 后端唯一分配 | 3.1 单一权威 | 上游底座，生产者计数侧唯一分配；前端不读不写不造号 |
| 前端只一条基线 | 3.2 单一下游 | `lastSeqRef` 唯一：初始-1/重置/重连不断；done/热路径推进同一 ref |
| 比较前归一化 | 3.5 度量衡一致 | 序号比较前统一 `toStepNumber()` 单点归一，杜绝 string/number 混比 |
| 无输入可拦不建 | 3.6 终态后无帧 | 作废守卫已退役删除，不再叠防线 |
| 同一逻辑唯一实现 | 3.7 DRY | 推进逻辑单点；thought 身份白名单单点定义 + 登记源双登记 |

### 4.4 设计效果预期

| 度量衡 | 预期 |
|--------|------|
| 拦截防线 | **后端 2 条 + 前端 2 条**（B1/B2 源头少发 + F1/F2 尾部兜底） |
| 序号来源 | 1 处（后端 publish） |
| 前端进度线 | 1 条（lastSeqRef） |
| 无效防线 | 0（作废守卫退役，不新增） |

### 4.5 新设计重连机制线条图

```
═══════════════════════════ 后端（源头层） ═══════════════════════════
   agent 产生事件                     生产者计数侧
        │                             publish() ①
        ▼                             seq=len(已入日志条数)   ← B1 唯一分配
   [ 事件日志缓冲 ] ────────────────► (每帧带全局连续 seq 0,1,2,...)

        │ ② 流读取侧(offset=after_seq)   ← B2 断点续传
        │    实时:       从 offset 读到末尾, 逐帧转发
        │    重连(after_seq=N): 只发 N 之后的帧 ── 源头不重复
        ▼
   [ SSE 帧流: data: {seq, type, ...} ]  (thought 不在白名单不转发)
        │
        │  TCP 连接(有序) → 断线 → 重连
        ▼
═══════════════════════════ 前端（基线 + 尾部层） ═════════════════════
        │
        ▼
   [ 连接层 ]  lastSeqRef  ← 唯一基线(初始-1/重置/重连不断)  ← F1
        │        重连带 ?after_seq=lastSeqRef+1
        ▼
   [ 消费入口 ]  seq<=lastSeqRef ?  ← F2 幂等吸收
        │
        ├─ 是 → 静默丢弃(重复帧, 不进业务)
        └─ 否 → 推进 lastSeqRef → 分发执行
                          │
                          ▼
                    [ 业务层: 永不接触重复帧 ]

时序(正常 + 重连):
  正常流:  publish seq=0,1,2,... → stream_reader 全发 → 前端逐帧推进 lastSeqRef
  断线:    前端 idle 判死 → reconnect() 不再 POST 而是 GET ?after_seq=lastSeqRef+1 (F1→B2)
  重连:    后端只发 lastSeqRef 之后的帧 → 已消费帧零重复
  兜底:    万一重复帧进线 → sseParser 入口按 seq<=lastSeqRef 吞掉 (F2)
```

> 图注：① 序号权威唯一（B1）→ ② 断点续传源头不重发（B2）→ ③ 前端单基线精确续传（F1）→ ④ 入口幂等兜底（F2）。四条线＝「后端源头少发 + 前端尾部兜底」双层闭合，即新设计的全部防线；虚线之外不建任何第三条防线（原则 3.6）。


## 五、订阅时代 vs publish 时代对比（判定：同层机制、行为等价）

| 维度 | 订阅时代（4C 前） | publish 时代（4C 后） | 判定 |
|------|------------------|----------------------|------|

## 十、前后端链接与端点重连问题分析和讨论

> 编写人：小欧，2026-09-13 04:35:49。本章将前九章"重连重复发送"的现象面分析收敛为**前后端链接（SSE 单一端点）与端点重连（断点续传）**的讨论结论，均为对前述已实证机制的再组织，不新增方案、不新下结论。

### 10.1 前后端链接：单一 SSE 端点

| 项 | 内容 |
|----|------|
| 链接形态 | 前端以 `GET {events 端点}` 与后端建立 SSE 流；实时与重连**共用同一端点同一 URL**，仅查询参数 `after_seq` 不同（实时缺省/重连 `after_seq=lastSeqRef+1`，useSSE.ts:793） |
| 端点语义 | "从断点 N 起的事件流"（event_log 断点续读，stream_reader `offset=after_seq`，stream_orchestrator.py）——REST 化、幂等、断点状态在 URL |
| 咽喉点 | `stream_reader` 为该端点唯一转发咽喉（实时/重连同一路径，第二章 2.2） |

结论：前后端之间只存在**一条逻辑链接**（单一端点 + 断点参数），不存在"实时链路/重连链路"两套通道——与第五章「重连机制是传输可靠层、跨两代共用一套代码」一致。

### 10.2 端点重连的本质：对同一端点发起带断点的续传请求

"断线重连"在端点语义上**等价于断点续传**：同一 URL、携带 `after_seq=lastSeqRef+1` 的新请求，后端只回「断点之后」的帧（3.3 断点续传原则）。端点上**没有"重发"动作，只有"从哪续"的问题**。

重连结果是否正确由三个要素决定（与 2.2/4.2 防线一一对应）：

1. **断点参数精度**：`after_seq=lastSeqRef+1`（F1 单基线精确续传，useSSE.ts:793）
2. **服务端断点续读**：`offset=after_seq` 只发之后帧（B2 源头断点续传，stream_orchestrator.py）
3. **客户端幂等兜底**：`seq<=lastSeqRef` 拦截重复帧（F2 尾部幂等吸收，sseParser.ts:194-197）

### 10.3 讨论：同一端点重复请求为何不会得到重复数据

重连（甚至重复重连）对同一端点取到的必是同一断点之后的集合，理由闭合（引用第三/四章）：

1. **seq 全局连续单调**（B1 底座，publish `seq=len(event_log)` 唯一分配，task_state.py:44-54）→ 断点位置唯一可枚举；
2. **TCP 有序非乱序** → "断点之后"的帧集是确定的前缀后缀关系，无交错歧义；
3. **final 之后无业务帧**（3.6 终态后无帧原则）→ 重连读到 final 即终点，没有"终态后晚到帧"污染断点结算；
4. **双层闭合**（B2+F2，4.2 真防线表）→ 源头少发 + 尾部兜底，即使源头意外多发也被 `seq<=lastSeqRef` 吞掉。

→ **端点重连天然幂等**：同一 `after_seq` 重复请求返回同一帧集，与"已消费历史"互不重叠。

### 10.4 端点重连讨论清单（常见疑问消解）

| # | 讨论 | 结论（基于前述实证） |
|---|------|---------------------|
| ① | 端点级重试是否需要额外去重始发 | 不需要。同一端点同一 after_seq 幂等；前端入口 `seq<=lastSeqRef` 已兜底（3.4 幂等去重原则） |
| ② | 断点粒度为何用 seq（事件级）而非字节/时间 | seq 与业务数据面对齐（chunk/step 均带 seq），断线不丢业务帧、续传无缝（3.1 单一计数权威原则） |
| ③ | 占号跳号是否影响续传精度 | 不影响。thought 已占号但不转发，前端只用"已收最大 seq"续传，跳号无碍（第五章） |
| ④ | 断点基线漂移是否为唯一致命点 | 是。单基线纪律 3.2（只一条 lastSeqRef）即为此而设；第二条基线 lastUsageSeqRef 拦截量 0，按 P6 退役 |
| ⑤ | 断点何时结算完毕 | done 权威置位后 final_stats 为末帧（9.3 验证点 11），重连以 final_stats 的 seq 为终断点，读毕 `[SSE] reader退出` |

### 10.5 小结（链接层定论）

前后端经**单一 SSE 端点**链接；**端点重连 = 断点续传**——同一 URL 带 `after_seq` 的新请求，源头只发断点之后、尾部幂等吸收，双层闭合使端点重连天然幂等。端点重复请求不会带来重复数据，2 处根治（offset 续传 + lastSeqRef 基线）即闭合（摘要第 3/5 点）。
