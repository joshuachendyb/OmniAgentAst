# 重连重复发送问题分析与处理

创建时间：2026-09-12 09:05:03
编写人：小欧

## 摘要

本文档对「SSE 断线重连后，后端已发过的事件是否/为何会**重复发送**」进行完整分析与处理方案定稿。核心结论：

1. **重连不需要重复发**——只需补发「断点之后」未收到的新帧；**重复发不好**（chunk 增量二次拼接、步骤双份渲染）。
2. 重连机制本质是**传输可靠层**，与「订阅(yield) / publish」两代事件生产机制**无关**，一套代码跨两代共用、行为等价。
3. **三道防线已就位**：后端每帧注入 seq（publish）→ 前端精确续传（after_seq=lastSeqRef+1）→ 前端 S3 seq 守卫去重兜底。
4. 历史「一直没解决」的根因（实证）：①早期重连不带 after_seq 而从 0 全量重播；②seq 守卫早期拿 `step.step`(string) 与 number 比较恒 false，守卫**形同虚设**——09-12 P0-1 已归一化修复。
5. **当前仍旧存活 1 处基准错位**：终态守卫记录 `stepNum`（步骤号）、作废守卫比较 `seq`（事件序号），两套度量衡混比，需修复（§六~七）。
6. **处理分工全景（§六）**：后端 4 项已实施（seq 注入 / 断点续读 / 重连不重播 / 挡 thought）、前端 6 项已实施（lastSeqRef / 精确续传 / S3 守卫 / 终态作废 / 防重复起任务 / 类型归一化 P0-1 今日刚完成）；待实施 3 个层级——L1 必改（§7.1 终态守卫记 seq、§7.2 onSeq 单 helper）、L2 应改（§7.3 step 源头 number 化、§7.4 守卫退役评估）、L3 可选加固（§7.5 通道路由表收敛/白名单化，原 T2 落此）。
7. **（v2 定稿）§6 全景补 5 项**：检测面（三定时器判死）、心跳车道 `: ping`、第二套 seq（usage）、buffer 生命周期竞态、sessionStorage 刷新恢复——重连问题全景从「发出/收到两半场」扩展为完整闭环。
8. **（v2 定稿）架构病根**：重连要处理 12 处是因 seq 权威分散（4 份 ref 违 SRP）、onSeq 推进复制（违 DRY）、step 类型不统一 12 处归一化（违 KISS）、路由散落 3 处（违 DRY/OCP）、守卫叠帽子（违 YAGNI）——处理原则 = **收敛而非叠补丁**（§六 记录问题、§七 修改方案）。

**实证版本基线**：本文以当前 HEAD（`4bf3ea987`，2026-09-12）前端/后端代码实读为准，均已标注文件+行号；历史面基于代码注释记载（含编辑历史）。

## 一、问题定义

### 1.1 重连成功后需要重复发吗？

**不需要。** 断线只代表「断点之后」的新帧没收到；已收到并处理过的帧（前端已按 seq 推进 `lastSeqRef`）重连后应跳过。重连的职责仅是**续传**，不是**重播**。

### 1.2 重复发好吗？

**不好**，具体危害：

| 重复对象 | 危害 |
|---------|------|
| chunk（正文字符流） | chunk 是逐字增量数据，重复 = 正文二次拼接、run-on 叠加 |
| thought（推理） | 实时 thought + 回放 thought 双通道重复显示（G1 同源） |
| step 类（start/action/observation/final） | 步骤双份渲染、快照错位、计数重复 |
| 终态后帧（final 之后的业务帧） | 污染已完结渲染态（pendingSteps/executionSteps） |

### 1.3 前端要如何配合？

两条腿走路：
1. **精确续传**：重连请求带 `after_seq=lastSeqRef.current+1`，让后端只发断点后的帧（源头不重复）；
2. **seq 幂等去重兜底**：即使后端/网络真发了重复帧、乱序帧，前端按全局事件序号把重复帧**吞掉**（免疫能力）。

## 二、重连机制原貌（跨订阅/publish 两代共有）

重连是**传输可靠层**，不依赖事件如何产生，一套代码贯穿两代：

```
前端 lastSeqRef(已处理最大seq)
  → 重连 GET ?after_seq=lastSeqRef.current+1      (useSSE.ts:789)
  → 后端 stream_reader offset=after_seq             (stream_orchestrator.py:458)
  → 从 event_log 断点续读 → 逐帧 format_agent_sse 转发
  → 前端 sseParser 入口 S3 守卫(seq<=lastSeqRef 拦截) → onSeq 推进 lastSeqRef
```

「重连复用同一函数（传 after_seq 续传），避免重复事件」为北京老陈 2026-07-12 拍定（`stream_orchestrator.py:452-454` 注释原文），早于 4C（09-06）两个多月。

## 三、现状三道防线（实证）

| 防线 | 位置 | 作用 |
|------|------|------|
| 1 后端每帧注入 seq | `task_state.py:44-54`（publish 重写 `seq=len(event_log)`） | 全局递增、连续、全帧携带 |
| 2 前端重连精确续传 | `useSSE.ts:789` `?after_seq=${lastSeqRef.current+1}` → 后端 `stream_orchestrator.py:458` `offset=after_seq` | 只发断点后的帧，源头不重复 |
| 3 前端 seq 去重守卫 | `sseParser.ts:190-197`（`seq<=lastSeqRef` 拦截）+ L199-215 终态后作废 + L218-220 onSeq 推进 | 重复/乱序/终态后帧进不了业务 |

辅助点：
- `lastSeqRef` 初始 -1（`useSSE.ts:514`，首帧 seq=0 不被误拦）；新任务重置 -1、终态标记重置 -1（`useSSE.ts:775-776`）；重连**不断不重置**（保证续传基线连续）。
- 热路径与 done 收尾两路均推进 `lastSeqRef`（`useSSE.ts:894 / 946`）。

## 四、历史「一直没解决」的根因（实证）

两个历史根因横跨订阅/publish 两代，与 4C 改造无关：

1. **早期重连不带 after_seq（或从 0）**：前端重连请求未传断点，后端 stream_reader 从 event_log 头重播**全部事件** → 全量重复。09-10 S3 修复：改为 `after_seq=lastSeqRef.current+1`。
2. **seq 守卫比较基准失效（真凶）**：早期守卫直接拿 `step.step`（后端下发为 string）与 `lastSeqRef`(number) 比较 → **string/number 比较恒 false → 守卫形同虚设**，重复帧一路漏进业务。09-12（本文落盘当日）P0-1 三堂会审修复：统一 `toStepNumber()` 归一化（`sseParser.ts:562` error、L579 final、L562/L645 等，编辑历史见 `sseParser.ts:73`）。

> 结论：代码里一直躺着守卫，但 09-12 之前它从未生效——这就是「感觉一直没解决」的实证。

### 6.6 架构病根：为什么「重连重复」要处理 12 处（老杨诊断 2026-09-12）

#### 6.6.1 事实：处理点共 12 处

| 层 | 处理点 | 位置 |
|----|--------|------|
| 后端(4) | ① publish 注入 seq ② offset 续读 ③ 重连 not_found 不重播 ④ _SSE_EXCLUDE_TYPES 挡 thought | `task_state.py:44`、`stream_orchestrator.py`、`chat_routes.py` |
| 前端(8) | ⑤ lastSeqRef ⑥ after_seq ⑦ 热路径推进 ⑧ done 块推进 ⑨ S3 守卫 ⑩ 终态作废守卫 ⑪ toStepNumber×12 ⑫ 防重复 POST | `useSSE.ts:514/789/894/946`、`sseParser.ts:190-215/562/579/646` |

**诊断：12 处对应「4 个 seq 信息源、4 份 seq 状态、2 个类型系统、3 处路由规则」——复杂度来自失配互补，不是必要设计。**

#### 6.6.2 病根一：同一「事件序号」前端拆 4 份 ref、各自推进各自守卫 —— 违 SRP(单一权威)

`lastSeqRef`(业务,`useSSE.ts:514`)、`terminalSeqRef`(终态,`useSSE.ts:516`)、`lastUsageSeqRef`(usage,`useSSE.ts:491`) + `usageAccumRef` 累加器，**同一概念("已处理到的序号") 4 处存放、推进点散落 894/946/usage/final/error(L557/638)**。无单一权威 → 比较基准必然失配 → string/number 恒 false 的历史 bug 正是此土壤。后端 publish 一处分配 seq(task_state.py:44-54)做对了，前端消费端未收敛。

#### 6.6.3 病根二：onSeq 推进代码复制两份 —— 违 DRY

`useSSE.ts:893-895`(done 块) 与 `944-946`(热路径) 是**逐字相同的两行推进逻辑**。F2 称"双路必要"——必要的是"两处各调一次"，但**实现被复制**。任一处将来改动漂移，守卫基准立即失配——复发通道就在这。

#### 6.6.4 病根三：step 字段类型不统一 + 12 处运行时归一化 —— 违 KISS-DIRECT「无双重解析」

后端 `step` 下发 string，前端要 number → `toStepNumber`(`sseParser.ts:85`) 在 **12+ 处**反复调用。**正解：后端 publish 时 `step` 直接落 number，前端 `step.step = rawData.step` 直取，12 处归一化全部删除（直线传递 A→E，不绕 B/C/D）**。

#### 6.6.5 病根四：事件「身份路由规则」散落三处 if —— 违 DRY/OCP，白名单化即对症

同一类 step 的身份：后端判(`_SSE_EXCLUDE_TYPES` thought 不转发)、前端作废守卫判(豁免 start/final_stats/usage，`sseParser.ts:207-209`)、useSSE 判(usage 去重)。**一份"这个类型怎么办"的路由规则，物理散落 3 文件**。收敛为单一路由表(类型→{落库?转发?作废豁免?usage?})即可 12 处收 3 处。

#### 6.6.6 病根五(最尖锐)：全部守卫是"打补丁的补丁" —— 违 YAGNI

**理论最小解只需 2 点：① 后端 offset 从 lastSeqRef+1 续传(源头) ② 前端 lastSeqRef 单调推进(基线)。** 因为后端 event_log seq 全局连续单调、TCP 流有序不乱序、final 后无业务帧。**S3 守卫、终态作废守卫、toStepNumber 归一化全是为补偿「防线 2 曾经坍塌(string/number 失效)」而叠的帽子**。复杂度与鲁棒性的失衡，正是"要改 12 处"的直接原因。

#### 6.6.7 10 大规范违反对照表

| 规范 | 违反证据 | 处置 |
|------|---------|------|
| **SRP 单一权威** | 4 份 seq ref 各自推进守卫(6.6.2) | 收敛为「后端唯一分配 + 前端唯一消费」 |
| **DRY 不重复** | onSeq 推进复制 2 份(6.6.3)；身份路由 3 处(6.6.5) | extract 单点 + 路由表 |
| **KISS-DIRECT** | step 类型不统一，12 处 toStepNumber(6.6.4) | 后端源头落 number，删全部归一化 |
| **OCP 开闭** | _SSE_EXCLUDE_TYPES 黑名单改现有集(6.6.5) | 改白名单(T2，方向正确) |
| **YAGNI 不过度** | 3 层守卫叠帽子(6.6.6) | P0-1 后重评，守卫可退役 |
| 未违反 | SLAP/LSP/ISP/复用优先/禁backward | — |

**病根一句话**：重连重复的根治只该动 2 处；动了 12 处，是因为 seq 权威分散(4 份状态)、类型不统一(step string)、路由规则散落(3 处)、推进逻辑复制(2 份)——四者互相制造失配，失配再造补丁。

## 七、处理方案（重写版 v2，老杨 2026-09-12 推翻重构；动代码先批）

### 7.0 方案总原则（v2 新增）

**收敛，而非叠补丁。** 按 §6.6 病根诊断，本方案分三层处置，优先级自上而下：

| 层 | 病症（§6.6） | 措施 | 定级 |
|----|-------------|------|------|
| L1 必改 | 病根①：终态守卫基准错位（T1，6.1 S4） | §7.1 统一记 seq | 必改 |
| L1 必改 | 病根②：onSeq 推进复制 2 份（DRY） | §7.2 收敛单 helper | 必改（防复发） |
| L2 应改 | 病根③：step 类型不统一 → 12 处归一化（KISS） | §7.3 源头 number 化 | 应改（收益最大） |
| L2 应改 | 病根⑤：3 层守卫叠帽子（YAGNI/OCP） | §7.4 守卫退役评估 | 应改（验证后定） |
| L3 加固 | 病根④：路由规则散落 3 处（DRY/OCP=T2） | §7.5 路由表收敛/白名单化 | 可选加固 |
| L3 加固 | 全景缺失6.5.4：buffer 生命周期竞态 | §7.5 buffer 回收时机界定 | 可选加固 |

### 7.1 终端守卫统一记 seq（必须改，L1，源自 v1 §7.1）

final 分支（`sseParser.ts:556-557`）与 error 分支（`sseParser.ts:637-638`）由「记 `stepNum`」改为「记本轮事件真正的 seq」：

```ts
// final 分支（替换 L557）
if (typeof rawData.seq === 'number' && terminalSeqRef) {
  terminalSeqRef.current = rawData.seq;   // 与作废守卫比较基准一致：都是事件序号
}
// error 分支（替换 L638）同构
```

**行为等价性论证**（v1 保留，补充 v2 定位修正）：
- 修复前：终态标记=步骤号；作废条件 `seq > stepNum`（宽松阈值）；
- 修复后：终态标记=终态事件的 seq；作废条件 `seq > finalSeq`（精确阈值）；
- 在 TCP 有序 + after_seq 精确续传下，`seq ∈ (stepNum, finalSeq]` 的晚到帧实际到不了作废守卫（晚到旧帧被 S3 `seq≤lastSeqRef` 先拦）——**真实拦截集合几乎不变，属"量纲一致性加固"而非行为更改**（§6.6 诊断后的精确定性）；
- 豁免清单（start/final_stats/usage，`sseParser.ts:207-209`）保持不变；
- `rawData.seq` 非 number 时**必须**回退不设终态标记（守卫非 number 不拦截，行为一致；防后端异常帧缺 seq 时 NaN 恒 false 失去保护）。

### 7.2 onSeq 推进收敛为单 helper（必须改，L1，DRY 病根②）

`useSSE.ts:893-895`(done 块) 与 `944-946`(热路径) 逐字相同的两行推进逻辑，收敛为一个 helper，两处仅调用：

```ts
// 建议位置：processSSEData 调用前的模块级或 useSSE 内 helper
const advanceLastSeq = (s: number) => {
  if (s > lastSeqRef.current) lastSeqRef.current = s;
};
// 热路径与 done 块均改调 advanceLastSeq(rawData.seq)
```

**论证**：必要的是"两处各调一次"（语义正确），**不是实现复制两份**。收敛后仅一份实现，杜绝未来单侧改动漂移导致守卫基准失配（§6.6.3 复发通道封死）。

### 7.3 step 源头 number 化（应改，L2，KISS 病根③）

- 后端：`publish` 时 `step` 直接落 number（`task_state.py` publish 或各 step 构造点），下发即类型正确；
- 前端：`sseParser.ts:85` `toStepNumber` 及其 **12 处调用**全部删除，`step.step = rawData.step` 直取，`final/action/error/user_rejected` 分支统一 `rawData.step`（number 直用）。

**论证**：直线传递 A→E，不绕 B/C/D。12 处归一化是"终止源头不统一"的代偿，改源头后全部消失（§6.6.4）。注意 `toStepNumber = (v) => Number(v) || 1` 对 `undefined` 归 1、对 `0` 归 1——源头 number 化后此 fallback 语义消除，需回归确认 `step=0`(请求级 error) 判定不受影响（`sseParser.ts:623` `rawData.step === 0` 独立读原始值，不受影响）。

### 7.4 守卫退役评估（应改，L2，YAGNI 病根⑤）

P0-1 修复后，S3 守卫/终态作废守卫已无可靠业务输入可拦（源头不重发、TCP 不乱序、终态后无业务帧），**先保留不作删除**，按 §7.6 验证后评估：

- 验证项 2/3/5 全过且重连 E2E 稳定后，**作废守卫可优先退役**（由 S3 + after_seq 双保险覆盖）；
- S3 守卫保留（免疫层成本最低、兜住未来 unknow 类型新帧）；
- 退役决策需 E2E 连续 3 轮 X2 重连 + 跳号续传通过。

### 7.5 通道路由表收敛 / 白名单化（可选加固，L3，DRY/OCP 病根④ = 原 T2）

- 保留黑名单 `_SSE_EXCLUDE_TYPES` 不动（行为已验证闭合，改动收益低、漂移风险高）；
- 改为：**加防漂移单测** `_SSE_EXCLUDE_TYPES ⊆ 注册工具/事件类型全集`（防错拼/幽灵类型/未来新增仅落库类型漏登记）；
- 事件身份路由规则（转发?/作废豁免?/usage 去重?）逐步收敛为**单一路由表常量**，前端 sseParser + useSSE 共查（§6.6.5），见后续细分方案。
- **（v2 新增）buffer 回收时机界定**：`reclaim_stream_buffer`（`task_state.py:74-76`）回收推迟至「重连窗口关闭」（终态发布后保留缓冲至超时/前端确认），使完结任务重连返回**终态空流**而非 not_found（§6.5.4），消除「已完结被误判为连接失败」的竞态；若暂不处置，维持现 not_found 语义并在 §7.6 验证项 8 确认前端无懈误判。

### 7.6 验证（回归，重写定稿）

1. **重连不重复**：真实后端 + 真实 LLM 跑任务，中断网络→重连，确认 `after_seq` 续传帧无重复、无重复渲染（E2E 铁律：真实后端/真实 LLM/真实工具/真实 SQLite，禁 Mock）。
2. **S3 守卫兜底**：构造重复帧（`seq <= lastSeqRef`）→ 断言被拦、业务不执行。
3. **终态后作废**：final 后注入更高 seq 的非豁免帧 → 断言被作废（防 pendingSteps 污染）。
4. **跳号续传**：含 thought 占号的会话重连，确认 seq 跳号不破坏断点衔接。
5. **终态标记边界**：final/error 分支 `rawData.seq` 为 number 时终态标记=seq；非 number 时不设标记。
6. **（v2 新增）§7.2 单 helper 等值**：收敛前后热路径/done 块推进语义逐字节等价（单测断言）。
7. **（v2 新增）§7.3 源头 number 化**：step=0 请求级 error 判定、`undefined` 输入 fallback 语义移除后行为回归（含 `toStepNumber` 原 12 处调用点逐一走查）。
8. **（v2 新增）§6.5.4 buffer 生命周期**：终态后立即重连 → 语义=返回终态空流而非 not_found（若按 §7.0 L3 处置则验证此条；不处置则维持现 not_found 并验证无懈误判）。

## 八、结论

1. 重连重复发送是**传输可靠层的老问题**，跨订阅/publish 两代同一机制、同一代码、行为等价，并非 4C 引入。
2. 三道防线（后端 seq 注入 / 前端精确续传 / S3 去重守卫）已就位；历史「没解决」的真凶（守卫 string/number 比较失效）已于 09-12 P0-1 修复。
3. 剩余**1 处存活的基准错位**（终态守卫记 stepNum、比 seq）按 §7.1 修复，量纲一致性加固、风险低。
4. （v2 定稿）全景补齐 5 项（§6.5）：检测面、心跳车道、第二套 seq、buffer 生命周期、刷新恢复——重连问题从「发出/收到两半场」扩展为完整闭环。
5. （v2 定稿）重连要处理 12 处的**架构病根**（§6.6）：seq 权威分散（4 份 ref）、DRY 推进复制、step 类型不统一、路由散落 3 处、守卫叠帽子——处置按 §7.0 三层收敛，而非继续叠补丁。
