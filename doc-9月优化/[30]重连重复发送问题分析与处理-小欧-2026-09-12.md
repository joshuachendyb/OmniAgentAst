# 重连重复发送问题分析与处理

创建时间：2026-09-12 09:05:03
编写人：小欧

## 摘要

本文档对「SSE 断线重连后，后端已发过的事件是否/为何会**重复发送**」进行完整分析与处理方案定稿。核心结论：

1. **重连不需要重复发**——只需补发「断点之后」未收到的新帧；**重复发不好**（chunk 增量二次拼接、步骤双份渲染）。
2. 重连机制本质是**传输可靠层**，与「订阅(yield) / publish」两代事件生产机制**无关**，一套代码跨两代共用、行为等价。
3. **最高准则（定稿）**：重连重复的根治**只该动 2 处**——**① offset 续传（源头不重发）② lastSeqRef 基线（前端精确续传与幂等校验）**。凡与此准则不一致的方案（叠守卫/改守卫/白名单/buffer 回收等）一律清理，只保留与本准则准确一致的思路。
 
  2 个点就能根治重复:① 后端 offset 从 lastSeqRef+1 续传(源头);② 前端 lastSeqRef 单调推进(基线)。 因为:
  后端 event_log seq 全局连续单调递增;
  TCP 流有序,不存在乱序;
  final 之后无业务帧,不存在"终态后晚到业务帧"。
4. **定理（准则的依据）**：后端 event_log 的 seq 全局连续单调递增 + TCP 流有序非乱序 + final 之后无业务帧 → **源头(offset 续传)与基线(lastSeqRef)闭合即根治，天然无第三者需要拦截**。
5. 两道核心现状**已全部就位且正确**（无需改动）：offset 续传（`useSSE.ts:789` + `stream_orchestrator.py` offset=after_seq）、lastSeqRef 基线（单调推进 + S3 校验），09-12 P0-1 已消除基线比较的 string/number 失真。
6. 违反本准则的存量补丁（**终态作废守卫** `sseParser.ts:199-215/557/638` 一套）将**退役删除**（§七/§八），属「清理重构」，非新增防线。
7. 处理分工全景：后端 seq 注入与 offset 续传、前端 lastSeqRef 基线均体现 2 处根治；其余「待实施/可选」项（T2 白名单化、buffer 回收等）经准则检定**移出本方案**（属另一问题域或补丁，不属重连重复根治）。

**实证版本基线**：本文以当前 HEAD（`4bf3ea987`，2026-09-12）前端/后端代码实读为准，均已标注文件+行号；历史面基于代码注释记载（含编辑历史）。

## 一、问题定义

### 1.1 重连成功后需要重复发吗？

**不需要。** 断线只代表「断点之后」的新帧没收到；已收到并处理过的帧（前端已按 seq 推进 `lastSeqRef`）重连后应跳过。重连的职责仅是**续传**，不是**重播**。

### 1.2 重复发好吗？

**不好**，具体危害：

| 重复对象 | 危害 |
|---------|------|
| chunk（正文字符流） | chunk 是逐字增量数据，重复 = 正文二次拼接、run-on 叠加 |
| thought（推理） | 实时 thought + 回放 thought 双通道重复显示（G1 同源） |
| step 类（start/action/observation/final） | 步骤双份渲染、快照错位、计数重复 |
| 终态后帧（final 之后的业务帧） | 污染已完结渲染态（pendingSteps/executionSteps） |

### 1.3 前端要如何配合？

与最高准则唯一的配合路径：
1. **精确续传（核心②）**：重连请求带 `after_seq=lastSeqRef.current+1`，让后端只发断点后的帧（源头不重复）；
2. **基线幂等校验**：前端 `lastSeqRef` 单调推进，对重复帧按 `seq <= lastSeqRef` 吞掉（免疫能力）。

> 注：本版删除了早期「两条腿 + 作废守卫」表述——seq 幂等去重兜底即基线校验（`seq<=lastSeqRef`），**终态后作废守卫属补丁，按准则不采**。

## 二、重连机制原貌（跨订阅/publish 两代共有）

重连是**传输可靠层**，不依赖事件如何产生，一套代码贯穿两代：

```
前端 lastSeqRef(已处理最大seq)
  → 重连 GET ?after_seq=lastSeqRef.current+1      (useSSE.ts:789)
  → 后端 stream_reader offset=after_seq             (stream_orchestrator.py/stream_reader)
  → 从 event_log 断点续读 → 逐帧 format_agent_sse 转发
  → 前端 sseParser 入口基线校验(seq<=lastSeqRef 拦截) → onSeq 推进 lastSeqRef
```

「重连复用同一函数（传 after_seq 续传），避免重复事件」为北京老陈 2026-07-12 拍定（`stream_orchestrator.py` 注释原文），早于 4C（09-06）两个多月。

## 四、历史「一直没解决」的根因（实证）

两个历史根因横跨订阅/publish 两代，与 4C 改造无关：

1. **早期重连不带 after_seq（或从 0）**：前端重连请求未传断点，后端 stream_reader 从 event_log 头重播**全部事件** → 全量重复。09-10 S3 修复：改为 `after_seq=lastSeqRef.current+1`（正是核心②）。
2. **基线比较基准失真（真凶）**：早期守卫直接拿 `step.step`（后端下发为 string）与 `lastSeqRef`(number) 比较 → **string/number 比较恒 false → 守卫形同虚设**，重复帧一路漏进业务。09-12（本文落盘当日）P0-1 三堂会审修复：统一 `toStepNumber()` 归一化（`sseParser.ts:562/579/646` 等），使**基线校验真正生效**。

> 结论：历史上"代码里躺着守卫却从未生效"，是因为完成"基线推进/比较"的度量衡失配。修复 = **让基线正确**（P0-1），而非再加第三道防线。

### 6.6 架构病根诊断（记录面；结论指向 2 处根治）

#### 6.6.1 事实：重连相关处理点一度达 12 处

| 层 | 处理点 |

`lastSeqRef` / `terminalSeqRef` / `lastUsageSeqRef` + 累加器并存，推进点散落。**收敛=只留 lastSeqRef 一条基线（核心②），其余退役**。后端 publish 一处分配 seq（`task_state.py:44-54`）本就正确。

#### 6.6.4 病根三：step 字段类型不统一 → 基线比较失真 —— 违 KISS「无双重解析」

后端 `step` 下发 string 曾致基线比较 string/number 恒 false。P0-1 归一化 `toStepNumber` 后基线生效——**修复对准的是「基线正确性」，与 2 处准则一致**。

#### 6.6.5 病根四：事件身份规则分散 —— 违 DRY（属通道治理，非根治）

thought 的「仅落库」身份由 `_SSE_EXCLUDE_TYPES` 单点定义（已满足）。
> 注：本版不再扩展「路由表白名单化(T2)」方案——其属通道治理另一域，不属重连重复根治（准则检定移出）。

#### 6.6.6 病根五：补丁叠帽子 —— 违 YAGNI，按准则退役

**定理**：event_log seq 全局连续单调 + TCP 有序 + final 后无业务帧 → **源头不重发、不会乱序、终态后无帧**。故除「offset 续传 ① + lastSeqRef 基线 ②」外的一切拦截（终态作废守卫）均**无输入可拦**，为纯补丁，退役删除。这与 6.6.2 一起构成 **12 处 → 2 处** 的收敛路径。

### 7.6 结论（并入原 §八 结论）

1. 重连重复发送是**传输可靠层的老问题**，跨订阅/publish 两代同一机制、同一代码、行为等价，并非 4C 引入。
2. **2 处根治是最优且足够**：源头不重发（offset 续传）+ 基线精确（lastSeqRef 单调 + seq<= 校验）；历史「没解决」的真凶是基线比较失真，09-12 P0-1 已修。
3. 清理路径：终态作废守卫（补丁）退役删除，**清理即重构，不新增防线**。
4. 全景边界：检测面/心跳/usage 幂等/buffer 生命周期/刷新恢复均非「已发帧重发」本体，不纳入 2 处根治。

```python
async def publish(self, step_dict: dict) -> int:
    """生产者直写：append + seq + 唤醒消费者。返回seq。"""
    step_dict = dict(step_dict)
    async with self.cond:
        step_dict["seq"] = len(self.event_log)   # 全局递增、连续、全帧携带 —— 核心①底座
        self.event_log.append(step_dict)
        self.cond.notify_all()
    return step_dict["seq"]
```
