# 重连重复发送问题分析与处理

创建时间：2026-09-12 09:05:03
编写人：小欧

## 摘要

本文档对「SSE 断线重连后，后端已发过的事件是否/为何会**重复发送**」进行完整分析与处理方案定稿。核心结论：

1. **重连不需要重复发**——只需补发「断点之后」未收到的新帧；**重复发不好**（chunk 增量二次拼接、步骤双份渲染）。
2. 重连机制本质是**传输可靠层**，与「订阅(yield) / publish」两代事件生产机制**无关**，一套代码跨两代共用、行为等价。
3. **最高准则（定稿）**：重连重复的根治**只该动 2 处**——**① offset 续传（源头不重发）② lastSeqRef 基线（前端精确续传与幂等校验）**。凡与此准则不一致的方案（叠守卫/改守卫/白名单/buffer 回收等）一律清理，只保留与本准则准确一致的思路。
 
  2 个点就能根治重复:① 后端 offset 从 lastSeqRef+1 续传(源头);② 前端 lastSeqRef 单调推进(基线)。 因为:
  后端 event_log seq 全局连续单调递增;
  TCP 流有序,不存在乱序;
  final 之后无业务帧,不存在"终态后晚到业务帧"。
4. **定理（准则的依据）**：后端 event_log 的 seq 全局连续单调递增 + TCP 流有序非乱序 + final 之后无业务帧 → **源头(offset 续传)与基线(lastSeqRef)闭合即根治，天然无第三者需要拦截**。
5. 两道核心现状**已全部就位且正确**（无需改动）：offset 续传（`stream_orchestrator.py` offset=after_seq）+ 前端 `?after_seq=` 续传、lastSeqRef 基线（单调推进 + S3 校验），09-12 P0-1 已消除基线比较的 string/number 失真。
6. 处理分工全景：后端 seq 注入与 offset 续传、前端 lastSeqRef 基线均体现 2 处根治；其余「待实施/可选」项（T2 白名单化、buffer 回收等）经准则检定**移出本方案**（属另一问题域或补丁，不属重连重复根治）。

**实证版本基线**：本文以当前 HEAD（`4bf3ea987`，2026-09-12）前端/后端代码实读为准，均已标注文件+行号；历史面基于代码注释记载（含编辑历史）。

## 一、问题定义

### 1.1 重连成功后需要重复发吗？

**不需要。** 断线只代表「断点之后」的新帧没收到；已收到并处理过的帧（前端已按 seq 推进 `lastSeqRef`）重连后应跳过。重连的职责仅是**续传**，不是**重播**。

### 1.2 重复发好吗？

**不好**，具体危害：

| 重复对象 | 危害 |
|---------|------|
| chunk（正文字符流） | chunk 是逐字增量数据，重复 = 正文二次拼接、run-on 叠加 |
| thought（推理） | 实时 thought + 回放 thought 双通道重复显示（G1 同源） |
| step 类（start/action/observation/final） | 步骤双份渲染、快照错位、计数重复 |
| 终态后帧（final 之后的业务帧） | 污染已完结渲染态（pendingSteps/executionSteps） |

### 1.3 前端要如何配合？

与最高准则唯一的配合路径：
1. **精确续传（核心②）**：重连请求带 `after_seq=lastSeqRef.current+1`，让后端只发断点后的帧（源头不重复）；
2. **基线幂等校验**：前端 `lastSeqRef` 单调推进，对重复帧按 `seq <= lastSeqRef` 吞掉（免疫能力）。

> 注：本版删除了早期「两条腿 + 作废守卫」表述——seq 幂等去重兜底即基线校验（`seq<=lastSeqRef`），**终态后作废守卫属补丁，按准则不采**。

## 二、重连机制的现状分

### 2.1原貌（跨订阅/publish 两代共有）

重连是**传输可靠层**，不依赖事件如何产生，一套代码贯穿两代：

```
前端 lastSeqRef(已处理最大seq)
  → 重连 GET ?after_seq=lastSeqRef.current+1
  → 后端 stream_reader offset=after_seq             (stream_orchestrator.py/stream_reader)
  → 从 event_log 断点续读 → 逐帧 format_agent_sse 转发
  → 前端 sseParser 入口基线校验(seq<=lastSeqRef 拦截) → onSeq 推进 lastSeqRef
```

「重连复用同一函数（传 after_seq 续传），避免重复事件」为北京老陈 2026-07-12 拍定（`stream_orchestrator.py` 注释原文），早于 4C（09-06）两个多月。


### 2.2 现状防线（实证 + 准则检定）
| 防线 | 位置 | 与 2 处根治关系 | 准则检定 |
|------|------|----------------|---------|
| 后端每帧注入 seq | `task_state.py:44-54`（publish 重写 `seq=len(event_log)`） | offset 续传的前置（seq 供 offset 精确定位） | **保留**（核心①底座） |
| 前端精确续传 | `useSSE.ts:793` `?after_seq=${lastSeqRef.current + 1}` → 后端 `stream_reader` `offset=after_seq` | **核心① offset 续传** | 保留（已就位） |
| 前端基线校验 | `sseParser.ts:194-197`（`seq<=lastSeqRef` 拦截）+ `useSSE.ts:898/951`（onSeq 单调推进） | **核心② lastSeqRef 基线** | 保留（已就位） |

辅助点：
- `lastSeqRef` 初始 -1（`useSSE.ts:518`，首帧 seq=0 不被误拦）；新任务重置 -1（`useSSE.ts:779`）；重连**不断不重置**（保证续传基线连续）。
- 热路径与 done 收尾两路均推进 `lastSeqRef`（`useSSE.ts:898 / 951`）——基线唯一，两处各推进一次。

### 2.3 、历史「一直没解决」的根因（实证）

两个历史根因横跨订阅/publish 两代，与 4C 改造无关：

1. **早期重连不带 after_seq（或从 0）**：前端重连请求未传断点，后端 stream_reader 从 event_log 头重播**全部事件** → 全量重复。09-10 S3 修复：改为 `after_seq=lastSeqRef.current+1`（正是核心②）。
2. **基线比较基准失真（真凶）**：早期守卫直接拿 `step.step`（后端下发为 string）与 `lastSeqRef`(number) 比较 → **string/number 比较恒 false → 守卫形同虚设**，重复帧一路漏进业务。09-12（本文落盘当日）P0-1 三堂会审修复：统一 `toStepNumber()` 归一化，使**基线校验真正生效**。

> 结论：历史上"代码里躺着守卫却从未生效"，是因为完成"基线推进/比较"的度量衡失配。修复 = **让基线正确**（P0-1），而非再加第三道防线。
## 三、设计原则：彻底修改改到最佳的模式逻辑

重连重复问题的根治逻辑可提炼为七条设计原则。每条遵循「根因 → 原则 → 实现 → 权衡」的推导结构，是事件流「发送-重连-消费」闭环的通用范式，适用于一切基于单调序号的事件传输系统：

### 3.1 单一计数权威原则（序号只由源头分配）

| 项 | 内容 |
|----|------|
| 根因 | 同一事件序号在系统多处各自计数，导致两套序号语义错位（历史病根一 6.6.2） |
| 原则 | 全局事件序号的分配权集中在**唯一源头**——生产者侧事件日志 |
| 实现 | 后端 publish 每帧 `seq=len(event_log)`，全局连续单调（`task_state.py:44-54`）；消费者（前端）只读不写、不复刻计数 |
| 权衡 | 序号来源唯一 → 物理上不存在"两套序号对不上"的可能；任何下游不得自造序号 |

### 3.2 单一下游基线原则（消费侧只持一条进度线）

| 项 | 内容 |
|----|------|
| 根因 | 消费侧为不同用途维护多份进度 ref，推进点散落、彼此不同步 |
| 原则 | 每个消费方只维护**一条**连续进度基线，作为断点续传与幂等去重的唯一依据 |
| 实现 | 前端 `lastSeqRef` 一条基线：初始 -1、单调推进、重连不断不重置；done 与热路径双路推进到同一 ref（`useSSE.ts:518/779/898/951`） |
| 权衡 | 进度单源 → 续传偏移与去重判断天然一致，无需多 ref 对账 |

### 3.3 断点续传原则（重发仅限断点之后）

| 项 | 内容 |
|----|------|
| 根因 | 早期重连未携带断点，后端从头重播全部事件 → 已消费帧全量重复（历史根因一） |
| 原则 | 重连请求必须携带消费方进度（断点），源头发送集 = 断点之后，绝不做全量重播 |
| 实现 | 重连 `GET ?after_seq=lastSeqRef+1`；后端 `stream_reader offset=after_seq` 从 event_log 断点续读（`stream_orchestrator.py`） |
| 权衡 | 补发集合由断点精确定义 → 断点正确性即治本关键；源头不重发，杜绝污染面 |

### 3.4 幂等去重原则（重复帧必须被静默吸收）

| 项 | 内容 |
|----|------|
| 根因 | 传输层不保证完全不重发（重试/抖动），消费侧必须自体免疫 |
| 原则 | 相同序号帧只生效一次：`seq <= 已消费基线` 的帧一律拦截丢弃 |
| 实现 | sseParser 入口基线校验 `seq <= lastSeqRef.current` 先于业务分发（`sseParser.ts:194-197`） |
| 权衡 | 去重置于消费入口 → 业务层永不接触重复；与 4.3 配合：源头少发 + 尾部兜底，双层闭合 |

### 4.5 度量衡一致原则（先归一化再比较）

| 项 | 内容 |
|----|------|
| 根因 | `step.step`(string) 与 `lastSeqRef`(number) 直接比较恒 false，守卫形同虚设（历史真凶，6.6.4） |
| 原则 | 一切序号比较前，参与比较的量必须落在同一类型/量纲 |
| 实现 | 入口统一 `toStepNumber()` 归一化后再推进/比较（`sseParser.ts:89/234` 等） |
| 权衡 | 单点归一化 → 比较恒可靠，消除"代码看似正确实则永不生效"的隐性缺陷 |

### 3.6 终态后无帧原则（无输入可拦的防线一律不建）

| 项 | 内容 |
|----|------|
| 根因 | 早期在源头+基线之外另建作废守卫，构成第二套度量衡（违规 SRP/YAGNI，6.6.6） |
| 原则 | event_log seq 全局连续单调 + TCP 有序 + final 后无业务帧 → 终态后物理上无新帧可拦；**一切"无输入可拦"的拦截层均不得新建** |
| 实现 | 作废守卫已退役删除，只保留 4.3+4.4 两条直线 |
| 权衡 | 删除守卫零行为差异（本就拦不到任何帧）→ 清理即重构，不新增防线 |

### 3.7 单一实现原则（DRY：同一逻辑唯一实现）

| 项 | 内容 |
|----|------|
| 根因 | done 与热路径推进逻辑逐字复制；事件身份规则散落多处（6.6.3/6.6.5） |
| 原则 | 同一逻辑只实现一处：多处调用同一实现，规则单点定义 |
| 实现 | 基线推进单点实现（done/热路径共用）；thought「仅落库」身份由 `_SSE_FORWARD_TYPES` 白名单单点定义（未登记即不转发）；新增能力先查 FUNCTIONS.md 复用 |
| 权衡 | 改动只落一处 → 无隐式对账开销，行为恒定一致 |

**七条的层次关系**：4.1/4.2 定"序号权威"与"进度单源"（数据面基石）→ 4.3 定"断点续传"（源头防重）→ 4.4 定"幂等吸收"（尾部兜底）→ 4.5 定"比较可靠"（正确性前提）→ 4.6 定"防线边界"（不建无效层）→ 4.7 定"实现唯一"（DRY 纪律）。前四条约束事件流主链路，后三条约束代码质量与防线取舍。

## 七、处理方案（定稿：只动 2 处根治；动代码先批）

### 7.0 最高准则（定稿）

> **重连重复的根治只该动 2 处：① offset 续传（源头不重发）；② lastSeqRef 基线（前端精确续传 + 幂等校验）。其余方案一律清理、删除，不与本准则共存。**
