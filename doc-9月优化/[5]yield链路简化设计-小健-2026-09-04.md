## 一、设计目标

**一句话**：6层→3层，跨层yield 87处→约54处（总量约66处，含LLM底层12处内部StreamChunk）。

**核心约束**：HITL暂停/恢复时序不变（paused必须在阻塞等待前发出）。

**设计原则**：关联不大的业务独立为模块被调用，不设中间转换层。react_cycle作为调度中枢，直接调用各业务模块。

---

## 二、当前架构问题

```
LLM StreamChunk(12)
  → llm_stream元组(15) [第1次转换]
    → Step对象(66) [第2次转换，跨层yield]
      → agent_runner转dict + event_log [第3次转换]
        → stream_reader格式化 [第4次转换]
          → orchestrator转发SSE(21) [第5次转换]
            → StreamingResponse [第6次转换]
              → 浏览器
```

**问题**：6次转换，87处yield，违反KISS/DRY/SRP。

## 三、优化的3层架构分析与设计

### 3.1 事件类型与Loop循环逻辑

系统按**事件类型**组织循环流程，理解事件类型是理解整个yield链路的前提：

#### 3.1.1 事件类型清单

| 事件类型 | Step类 | 谁发的（改造后） | 说明 |
|----------|--------|--------|------|
| thought-start | ThoughtStartStep | react_cycle | 开始思考的信号（每个轮次一次，_dispatch预发） |
| chunk | ChunkStep | react_cycle | 每段内容块（LLM原始输出） |
| thought | ThoughtStep | react_cycle | 推理内容（_dispatch预发/转换） |
| action | ActionStep | react_cycle | 工具调用请求（_result_out转出） |
| observation | ObservationStep | react_cycle | 工具执行结果（_result_out转出） |
| final | FinalStep | react_cycle | 终态答案（任务完成/失败，dict转出） |
| error | MetaStep(type="error") | react_cycle | 错误（_emit_events/_result_out转出） |
| usage | MetaStep(type="usage") | react_cycle | token用量 |
| paused/resumed | MetaStep | check_safety_and_confirm（3处live透传） | HITL暂停/恢复，sandbox裁决复用同一暂停通道 |
| retrying | MetaStep | react_cycle | L1/L2重试通知（StreamChunk.retry_notice转出） |
| cancelled | MetaStep | agent_runner | 任务取消 |

#### 3.1.2 Loop循环逻辑

```
agent_runner.run_agent_in_background()
  └─ for event in agent.run_react_cycle():  ← react_cycle是generator
       │
       ├─ react_cycle调用 llm_stream.call_llm_with_fallback() → StreamChunk
       │    → 逐段消费chunk → yield ChunkStep（chunk事件）
       │
       ├─ LLM响应拼接完成 → 按type分派
       │    ├─ type="answer" → answer_handler(function) → dict → _dispatch转Step → yield
       │    ├─ type="action" → handle_action(generator) → live-HITL透传 + _result_out dict → 转Step → yield
       │    └─ type="error" → answer_handler(function) → dict → 转Step → yield
       │
       └─ react_cycle yield Step
            │
            └─ agent_runner消费Step → 路由 + event_log → DB持久化
```

#### 3.1.3 改造前后对比

**改造前**：handler直接yield Step（跨层yield，87处）
```
handler yield Step → agent_runner消费 → 通道路由 → event_log → SSE
```

**改造后**：handler返回dict，react_cycle统一emit Step（跨层yield减少）
```
handler return dict → react_cycle统一emit Step → event_log → SSE
```

## 四、优化后的逻辑设计

### 4.1 架构设计与调用链
**架构设计（逻辑集中，独立调用）**：

```
调用链：
stream_orchestrator → agent_runner.run_agent_in_background()
  └─ agent_runner 调用 agent.run_react_cycle() [generator]
       ├─ react_cycle 调用 llm_stream.call_llm_with_fallback() → 返回StreamChunk → react_cycle emit ChunkStep
       ├─ react_cycle 驱动 handler/generator（HITL-live透传）→ 业务结果经输出参数（dict/_verdict/_result_out）→ 转为Step → yield Step
       └─ react_cycle yield Step
  └─ agent_runner 消费yield的Step → 路由 + event_log + DB持久化
       └─ stream_orchestrator 读event_log → 格式化SSE → yield给前端

llm_stream.py（LLM业务模块，被react_cycle调用）→ 不删除，yield StreamChunk
answer_handler.py（纯函数，被react_cycle调用）→ 返回dict
sandbox_gate.py（小generator，被check_safety驱动）→ live透传paused/resumed + _verdict传裁决
action_handler.py（generator，被react_cycle驱动）→ HITL-live透传 + _result_out传业务dict
agent_runner.py（consumer，不被react_cycle调用）→ 不变
stream_reader.py → 合并到stream_orchestrator.py（SSE输出业务）
```

**原则**：react_cycle是generator，被agent_runner消费。llm_stream被react_cycle调用；handler/sandbox为generator（live事件透传）+输出参数传业务结果（dict/_verdict/_result_out）。async generator不能return业务值——这是5.2/5.3/5.4采用输出参数的根本原因。不设中间转换层。
