## 二、问题 1：终态作废守卫（退役删除）

### 2.1 概要

`terminalSeqRef` 守卫曾在 final/error 后拦截「更高 seq 的非豁免晚到帧」，防渲染态污染。涉及 `sseParser.ts:199-215`(入口守卫块)、L557/638(终态标记录)、L139/170(接口/解构) 与 `useSSE.ts:516/776/897/949`(声明/重置/传参)。

### 2.2 病根/病因

- **第二套度量衡**：作废守卫以 `terminalSeqRef`(终态标记) 与 `lastSeqRef`(基线) 并存两套序号推进，比较语义割裂（曾记 stepNum 又比 seq，string/number 恒 false 的历史 bug 由此滋生）。
- **纯补丁，无输入可拦**：定理——后端 event_log seq 全局连续单调 + TCP 流有序不乱序 + final 后无业务帧 ⇒ 晚到高 seq 帧在物理上不存在,守卫零拦截量,属 YAGNI 违反。

### 2.3 处置建议

| 项 | 建议 |
|----|------|
| 定级 | **必做**（清理重构，直接删除，不加不修不漂移） |
| 动作 | 按 [30] §8.2 全套 diff：删 sseParser 守卫块 199-215、final/error 两处标记、接口/解构；删 useSSE 声明/重置/两处传参 |
| 验证 | `grep terminalSeqRef|terminalSeq` 全仓无残留；回归 §7.4 五项（含基线兜底/跳号续传/退役干净） |
| 防复发 | 在 FUNCTIONS.md/守卫纪律写入「禁止重新引入第二套 seq 守卫」 |

## 三、问题 2：检测面（重连触发判定）

### 3.1 概要

「如何判定需要重连」的检测机制：空闲超时 IDLE=60s 判死断开（`useSSE.ts:532,845-866`）、心跳 25s 保活（`constants.py:127`）、首响应 180s abort（`useSSE.ts:780-783`），含 HITL 等待期暂停 IDLE 豁免（`useSSE.ts:846-848`）。

### 3.2 病根/病因

- 属**触发可靠性**问题域，回答「连接何时算断」，与「已发帧是否重发」正交。
- 固有风险：判死阈值误触发 → 无谓重连 → 虽被基线兜底但多一轮流量；HITL 等待误杀（已有 S15 豁免缓解）。

### 3.3 处置建议

| 项 | 建议 |
|----|------|
| 定级 | 不处置（认知边界保留） |
| 现在 | 维持三定时器现状（P9/E2E 已验证稳定） |
| 观测 | 空闲超时触发的上下文打点(实证 60000 来源)保留，出现假死/误断再单独立案 |

## 四、问题 3：心跳车道 `: ping`

### 4.1 概要

`stream_orchestrator.py` 每 25s `yield ": ping\n"`：非 publish 产物，**不占 seq、不入 event_log**；前端 `sseParser.ts:113-115` 对非 `data:` 前缀整行丢弃。

### 4.2 病根/病因

- 保活机制，与 seq 续传**正交、零副作用**（正是它不占号才能不破坏跳号语义）。
- 若误以为心跳占号 → 会破坏「seq 跳号无碍」结论，属认知风险而非代码缺陷。

### 4.3 处置建议

| 项 | 建议 |
|----|------|
| 定级 | 不处置（现状即正确） |
| 动作 | 维持；在注释中固化「心跳不占 seq」性质（[30] §6.5.2 已记录），防后人误改 |

## 五、问题 4：第二套 seq（usage 幂等）

### 5.1 概要

`lastUsageSeqRef`/`usageAccumRef`（`useSSE.ts:491`）独立于业务基线 lastSeqRef 追踪 usage/meta 帧；`usage` 在作废守卫豁免清单（`sseParser.ts:209`，守卫删除后该豁免随之消失）。

### 5.2 病根/病因

- usage 是**元信息帧自己的幂等命题**，非业务帧重复——三防线本就不该管它。
- 作废守卫退役后，usage 帧按普通帧走基线校验（seq<=lastSeqRef），行为正确性由 P9 实证兜底。

### 5.3 处置建议

| 项 | 建议 |
|----|------|
| 定级 | 不处置（认知边界保留） |
| 动作 | 守卫退役后核对一处：usage 帧不再被豁免、只靠基线校验，确认去重语义不变（补一条单测断言） |
| 观测 | usage 累计/续传去重若现异常，单独立案，勿牵回本方案 |

## 六、问题 5：buffer 生命周期竞态

### 6.1 概要

`reclaim_stream_buffer`（`task_state.py:74-76`）回收时机未界定；重连端点 buffer 不存在时 `get_stream_buffer` 返回 not_found 不重播（`chat_routes.py:114-120`、`stream_orchestrator.py` reconnect orchestrator）。

### 6.2 病根/病因

- 属**任务生命周期治理**，非「已发帧是否重发」。
- 理论竞态：终态后 buffer 被回收、而前端最后一帧(final_stats)恰好丢失 → 重连 not_found → 前端把「已完结」误判为「连接失败」。

### 6.3 处置建议

| 项 | 建议 |
|----|------|
| 定级 | 不处置（认知边界保留；暂缓） |
| 现在 | 维持 not_found 语义（[30] §7.5 已注：不处置则验证前端无懈误判） |
| 将来 | 若报「任务已完结但被提示连接失败」，再评估「回收时机后移 / 完结点返回终态空流」二选一，单独立案 |

## 七、问题 6：刷新恢复（sessionStorage）

### 7.1 概要

页面刷新后 `useSSE.ts:558-586` 从 sessionStorage 恢复执行步骤（`source=legacy/unknown` 兼容解析）；刷新后 lastSeqRef 归 -1、isReconnect 判定依赖 pendingMessageRef。

### 7.2 病根/病因

- 属**页面级状态恢复**，独立于连接级续传；「刷新→恢复步骤→再续传」三态衔接的去重基准未定义。

### 7.3 处置建议

| 项 | 建议 |
|----|------|
| 定级 | 不处置（认知边界保留） |
| 动作 | 现状恢复逻辑与续传互不干扰（P9 实证）；不主动扩展 |
| 观测 | 出现「刷新后重复渲染/步骤丢失」再单独立案，牵涉 UI 层不属于传输可靠层 |

## 八、问题 7：T2 白名单化/路由表（通道治理）

### 8.1 概要

原待选项：将 `_SSE_EXCLUDE_TYPES = {"thought"}`（`stream_orchestrator.py`）黑名单改为 `_SSE_FORWARD_TYPES` 白名单 + 防漂移单测（显式化实时/重连共用咽喉点的过滤规则）。

### 8.2 病根/病因

- 属**通道路由治理**（thought 本应仅落库），不属于「重连重复根治」。
- 动机 = OCP 思路：黑名单对「新增仅落库类型」依赖人工维护；白名单可显式封闭。但反向风险：漏登记新实时类型 = 漏发（难测出），黑名单漏登记 = 多转发（显性易测）。

### 8.3 处置建议

> 本项的完整定稿在《[29]4C通道路由缺口核查报告》**§7.1**（两案对比 + 推荐 + 7.1c 代码样张 + 7.1e 防漂移单测），本节只作登记摘录，处置口径以其为准。

| 项 | 建议（[29] §7.1 口径） |
|----|----------------------|
| 定级 | 待批准加固（移出本方案域，由 [29] 域推进，动代码前先批） |
| 现在 | 维持黑名单 `_SSE_EXCLUDE_TYPES` 现状，行为已验证闭合 |
| [29] 推荐 | **方案二：白名单** `_SSE_FORWARD_TYPES` 正向允许表（默认拦截，结构性杜绝 thought 类漏登记事故重演）；并配 [7.1e] 防漂移单测 `assert live_types <= _SSE_FORWARD_TYPES` |
| 对比 | 方案一（黑名单增强，默认放行）被 [29] 否决原因是：thought 事故的发源地恰是黑名单漏加，黑名单延续默认放行 |
| 关联 | 实施入口：《[29]》§7.1 / §7.3；行为不变性见 [29] 7.1d；不在本域推进 |
