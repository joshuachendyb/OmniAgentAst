## 三、A组缺陷详解（5项）— X2仲裁/备份/级联取消

> 红case文件：`backend/tests/test_tdd_47_51_bug_a_red.py`

### 3.1 RED-A-1：`_arb_warning` 死变量（X2冲突提示死链路）

| 项 | 内容 |
|----|------|
| 缺陷 | `write_text_file` 中 `_arb_warning = acquire_write(...)` 拿到"占用者task_id"，但函数体从未读取该变量 |
| 证据 | 源码中 `_arb_warning` 仅赋值出现一次，无任何读取引用（`use_count == assign_count`） |
| 影响 | X2'冲突由工具层告警/排队/拒绝'未落地，跨任务写文件**静默覆盖依旧** |
| 文件 | `backend/app/tools/file/write_text_file.py` |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**：`acquire_write` 已返回"占用者 task_id"，读点消费它即把 X2 冲突提示真正落地——本地源码复核3遍：write_text_file.py:291 `_arb_warning = acquire_write(...)` 仅赋值一次、零读取（`use_count == assign_count`），复用已有返回值即可，不新增查询。
- **改法（合规，10规范）**：读取 `_arb_warning`，若非 None 且 != 当前 task_id，则经 `_build_write_text_file_llm_data` 新增 `arb_warning` 参数拼接进 warning 的 detail/hint，返回 `build_warning` 明示"目标文件正被任务X写入（可能覆盖）"，不阻断写（X2 冲突仅提示）：即 L289-292 读点 + L383-403 warning 分支并入。
- **复核**：SRP（arbiter 判占用、工具层消费提示）/ KISS（一行判定）/ SLAP（提示组装收口在 llm_data 构建函数）；红case A-1 修复后应转绿。

### 3.2 RED-A-2：arbiter 覆盖不全（仅 write_text_file 接入）

| 项 | 内容 |
|----|------|
| 缺陷 | X2'跨任务文件写仲裁'应覆盖全部会写文件的操作；实际仅 `write_text_file` 调用 arbiter |
| 证据 | edit_text_file / copy_file / move_file / delete_file / rename_file 源码中均无 `acquire_write` |
| 影响 | 其他写工具可与并行任务写操作冲突，X2覆盖不全 |
| 文件 | `backend/app/tools/file/*.py` |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**：arbiter 已提供 acquire/release 单点能力，缺的是接入面。源码复核3遍：edit_text_file/copy_file/move_file/delete_file/rename_file 均无 `acquire_write`；统一接入一个公共滚动点最优雅。
- **改法（合规，10规范）**：
  1. 在 `file_write_arbiter.py` 新增 `claim_write(file_path, task_id)` 上下文管理器：`acquire_write` + `yield` + `finally: release_write`（DRY 唯一实现，消灭各工具重复 try/finally）。
  2. edit_text_file/copy_file/move_file/delete_file/rename_file 主函数的写操作路径统一 `with claim_write(path, _current_task_id.get()):` 包裹（KISS：每个工具一行等价改动，逻辑零额外分支）。
- **复核**：SRP（仲裁单一职责）/ DRY（claim_write 统一）/ KISS-DIRECT（直线包裹）；红case A-2 修复后应转绿（断言 7 工具均登记）。

### 3.3 RED-A-3：arbiter 无 TTL（僵死占用永不回收）

| 项 | 内容 |
|----|------|
| 缺陷 | `acquire_write` 登记后若持有者不再 `release_write`（异常/被强杀路径遗漏），登记表永不主动回收 |
| 证据 | 红case：模拟占用已过期3600s且持有者不在 running_tasks，`who_writes` 仍返回占用者 |
| 影响 | arbiter 成为永久毒点，锁死后续写入 |
| 文件 | `backend/app/tools/file/file_write_arbiter.py` |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**：登记表应自我过期，僵死占用自动让位。源码复核3遍：file_write_arbiter.py 无任何 TTL/清理（`_write_claims` 只增删按 task_id）；且工具层**禁引 services.task**（守护规则），不可查 running_tasks，故用纯时间 TTL 惰性清理最合规。
- **改法（合规，10规范）**：
  1. 新增常量 `ARBITER_CLAIM_TTL = 1800`（秒）。
  2. `acquire_write` 锁内：若已有 holder 且 `time - holder["acquired_at"] > TTL`（过期僵死），视为无主，允许覆盖登记并 `logger.warning`。
  3. `who_writes` 同步过滤过期项（只读时返回 None）。
- **复核**：SRP（TTL 判定收敛 arbiter 内部）/ KISS（两处时间比较）/ YAGNI（不引跨层依赖）；红case A-3 修复后应转绿（过期 3600s 后 who_writes 返回 None）。

### 3.4 RED-A-4：registry 备份缓存键缺 session_id（跨会话误复用）

| 项 | 内容 |
|----|------|
| 缺陷 | `_backup_registry` 缓存键 `f'{root}\\{sub}'` 不含 session_id |
| 证据 | 红case：会话A备份后会话B对同一键操作直接复用A的备份文件（f_a == f_b） |
| 影响 | 回滚到错误会话的快照 |
| 文件 | `backend/app/tools/win_registry/registry_read.py` L58-85 |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**：缓存键必须携带会话身份，隔离跨会话备份。源码复核3遍：registry_read.py:60 `backup_key = f"{root_key}\\{sub_key}"` 不含 session_id（`_registry_session_backup` 全局共享）；调用方 registry_write/delete 传的 session 是常量 "reg_write"，进一步失去区分度。
- **改法（合规，10规范）**：
  1. 键改为 `f"{session_id}|{root_key}\\{sub_key}"`。
  2. 调用方（registry_write/delete）改传当前任务标识为 session（`_current_task_id.get()` 或任务级唯一 token），使不同任务/会话各自独立备份记录（KISS：一行传参）。
- **复核**：SRP（键语义=会话+路径）/ KISS-DIRECT（直改键拼接）；红case A-4 修复后应转绿（会话A/B 同键备份文件不同）。

### 3.5 RED-A-5：`_cancel_cascade` fire-and-forget（级联取消不等待）

| 项 | 内容 |
|----|------|
| 缺陷 | `delete_session → _cancel_cascade` 用 `run_coroutine_threadsafe` 提交后代即返回，不等待取消完成 |
| 证据 | 红case：调用 `_cancel_cascade` 后任务 status 仍为 running（取消尚未执行） |
| 影响 | 删除会话后后台任务仍可写库 → 孤儿数据 |
| 文件 | `backend/app/services/chat/session_service.py` |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**：`run_coroutine_threadsafe` 返回 Future，等待其完成即达成"级联取消先于删除会话落定"。源码复核3遍：session_service.py:235-236 提交后即丢弃 Future 不等待；cancel_task 本身快速（set_cancelled 立即置态），等待成本极低。
- **改法（合规，10规范）**：`_cancel_cascade` 收集全部 Future，末尾依次 `f.result(timeout=5)`（超时异常仅告警不阻断删除，防死等）；loop 已关闭/异常分支维持现状。KISS：只补等待，逻辑零新分支。
- **复核**：SRP（取消职责不变，单点补充落定语义）/ KISS（Future.result 一行）；红case A-5 修复后应转绿（级联取消后任务 status 非 running）。

### 4.1 RED-B-1：注入消息不落库

| 项 | 内容 |
|----|------|
| 缺陷 | 注入消息只进内存 inbox → message_builder，无任何持久化路径 |
| 证据 | 红case：注入消息被 `_absorb_inbox` 吸收后，`conversation_history` 中该消息无 `user_message_id` 锚 |
| 影响 | 刷新即丢；assistant 回复无法正确配对落库 |
| 文件 | `backend/app/services/task/task_registry.py` |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**："注入即落库"，持久化唯一位置收敛在编排注入入口，吸收侧只消费 `(content, user_message_id)`。源码复核3遍：`inject_message_to_task`（task_registry）入队仅存 content 字符串；`_absorb_inbox`（react_step.py:186-195）只调 `add_user_message`。把 user_message_id 融入注入数据流，落库一次、处处不重复。
- **改法（合规，10规范）**：
  1. 编排层注入前先 `db.atxn("chat")` 调既有 `storage.insert_user_message(conn, session_id, content)` 拿自增 user_message_id（复用公共函数，不重造，10规范-复用优先）。
  2. `inject_message_to_task(session_id, content)` 改入队 `(content, user_message_id)` 二元组。
  3. `drain_inbox` 返回该二元组；`_absorb_inbox` 每项调 `message_builder.add_user_message(content, user_message_id=uid)`（见 B-2 签名扩展）。
- **复核**：SRP（注入=落库+入队两职责合一原子）/ DRY（复用 insert_user_message）/ KISS（数据从注入到吸收全程带锚）；红case B-1 修复后应转绿（conversation_history 注入消息带锚）。

### 4.2 RED-B-2：注入回合回复错锚（锚首条消息）

| 项 | 内容 |
|----|------|
| 缺陷 | assistant 回复落库锚点恒定用任务启动时 `_user_msg_id`（首条），注入回合回复挂错消息 |
| 证据 | 红case：注入"第二轮问题"后两个user轮次只有1个独立 user_message_id |
| 影响 | 前端显示挂错气泡，历史数据错位 |
| 文件 | `backend/app/services/chat/storage.py` `update_user_message_final` |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**："锚随轮演进"，`message_builder` 维护最新 user 锚，终态回填消费该锚。源码复核3遍：agent_runner.py:635 `update_user_message_final(user_message_id=db_ops.user_msg_id)` 恒定首条；message_builder.add_user_message L119-123 无锚概念。收敛为单点状态（builder 持有 `_current_user_msg_id`），消费单点（终态回填）。
- **改法（合规，10规范）**：
  1. `message_builder.add_user_message(content, *, user_message_id: Optional[int] = None)`：新增可选锚参数；未传时自动分配合成 id（若该轮本就是新建用户轮次），内部始终更新 `_current_user_msg_id`。
  2. `_absorb_inbox` 吸收注入二元组 `(content, uid)` → `add_user_message(content, user_message_id=uid)`（B-1 落库 id）。
  3. agent_runner 终态回填改 `user_message_id=agent.message_builder.current_user_msg_id or db_ops.user_msg_id`（KISS：一处状态一处消费）。
- **复核**：SRP / DRY（锚只在 builder 一处演进）/ KISS（无绕行）；红case B-2 修复后应转绿（两轮各有独立 uid）。

### 4.3 RED-B-3：B机制 TOCTOU 双任务

| 缺陷 | 备份文件名 `reg_backup_{session}_{%Y%m%d_%H%M%S}.reg` 秒级粒度；调用方 session 恒为常量 → 同秒二次同名互覆 |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**：备份文件名必须**唯一**，用微秒+短随机后缀（或 uuid 片段）消除同秒/同会话撞名；配合 D-7/E-5（备份有效性）与本项同源收敛在 `_backup_registry` 一处。源码复核3遍：注册表备份 文件名 `reg_backup_{session}_{%Y%m%d_%H%M%S}.reg` 秒级；session 恒 "reg_write"。
- **改法（合规，10规范）**：
  1. `_backup_registry` 文件名改 `reg_backup_{session}_{%Y%m%d_%H%M%S}_{uuid4().hex[:8]}.reg`（唯一后缀）。
  2. 保留目录基路径与校验逻辑，仅文件名部分变更（KISS 最小面）。
- **复核**：SRP / KISS / 与 A-4（会话键）、E-5（每次重导）组合成"备份三原则"；红case D-6 修复后应转绿（两键文件不同）。

### 6.6 RED-D-7：registry 备份失败仍返回路径

| 项 | 内容 |
|----|------|
| 缺陷 | `_backup_registry` 失败（reg export 返回码非0/文件未创建）时仍 `return backup_file` |
| 证据 | 红case：fake returncode=100，函数仍返回一个不存在文件的路径 |
| 影响 | registry_write/delete 误以为"已备份"，后续回滚无据可依 |
| 文件 | `backend/app/tools/win_registry/registry_read.py` `_backup_registry` |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**：备份是写操作的**前置屏障**——导出失败必须让调用方明确得知。`_backup_registry` 出错返回 `None`，registry_write/delete 拿到 None 即中止写（返回"备份失败，已中止"错误），杜绝"误以为已备份"。源码复核3遍：D-7 当前失败仍 `return file`；write 侧无 None 判定。
- **改法（合规，10规范）**：
  1. `_backup_registry` 的失败分支返回 `None`（不返回不可用路径）；成功返回真实文件路径。
  2. `registry_write`/`delete` 前置：`backup_path = _backup_registry(...); if not backup_path: 返回 build_error("注册表备份失败，已中止写入")`（KISS 一行守卫）。
- **复核**：SRP（备份=返回可用路径或 None）/ KISS / 前置守卫前置；红case D-7 修复后应转绿（失败返回 None）。

### 6.7 RED-D-8：重连 cancelled 终态帧重复下发

|----|------|

| 证据 | 红case：首次与二次均返回 cancelled 终态帧（二次应 None） |
| 影响 | 每次重连前端再收到一次终止帧 → 重复终态 |
| 文件 | `backend/app/services/task/task_runtime.py` `task_cancel_check_and_yield` |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**：去重判定不该依赖"调用方瞬时传的列表"（重连时为空），而应以**DB 持久化状态**为准——二次重连时读取任务已落库的终态标记（status/终态 steps/event 记录）。源码复核3遍：task_runtime L137-151 用入参 `current_execution_steps` 判定 `has_cancelled`；重连调用方传空列表。
- **改法（合规，10规范）**：

  2. 保留原列表判定作为快速路径（若上游已持终态直接跳过）；DB 查询为权威（KISS：双源但 DB 为准）。
- **复核**：SRP（去重=持久态属性）/ KISS / DRY（复用 storage 查询函数）；红case D-8 修复后应转绿（二次不再返回终态帧）。

## 七、E组缺陷详解（5项）— SSE锁/回滚/重试/ID复用/备份缓存

> 红case文件：`backend/tests/test_tdd_59_63_bug_e_red.py`

### 7.1 RED-E-1：stream_reader 在 buffer.cond 锁内 yield（慢客户端拖死agent）

| 项 | 内容 |
|----|------|
| 缺陷 | `stream_reader` 的 `async with buffer.cond:` 包裹整个循环体，`yield format_agent_sse(...)` 在锁内 |
| 证据 | 红case：消费者暂缓期间 `buffer.publish` 被阻塞（timeout 0.5s） |
| 影响 | 慢客户端 socket 背压挂起消费者时，锁被持有，producer 的 publish 无限阻塞 → 拖死整个 agent 循环 |
| 文件 | `backend/app/services/chat/stream_orchestrator.py` L505/L513 |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**：**锁内只取数据，锁外才 yield**——把"读缓冲区快照"与"awaitable 交付"分离，绝对不在 `buffer.cond` 临界区内执行任何可挂起/用户可见的 yield（生产端 publish 永不阻塞）。源码复核3遍：L505 `async with buffer.cond:` 包裹 L513 循环体含 yield。
- **改法（合规，10规范）**：
  1. 重构为：`async with buffer.cond:` 内取**已就绪条目副本**（或 wait 后 pop 批量），退出锁后 `for item in batch: yield format_agent_sse(item)`（锁外交付）。
  2. 心跳/超时分支同样锁外落地；锁内零用户代码（SRP：锁只保护缓冲区结构）。
- **复核**：SRP / KISS-DIRECT（取-交分离，直线两段）/ 红线语义（锁内禁止 awaitable yield）；红case E-1 修复后应转绿（消费暂缓不再阻塞 publish）。

### 7.2 RED-E-2：registry_write 失败后从不回滚

| 项 | 内容 |
|----|------|
| 缺陷 | registry_write 备份后 SetValueEx/CreateKey 失败只返回 error，无任何从备份恢复的代码路径 |
| 证据 | 红case：源码审查，有备份（`_backup_registry`）却无 restore/rollback/undo |
| 影响 | 半修改状态残留，备份形同虚设 |
| 文件 | `backend/app/tools/win_registry/registry_write.py` |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**：写失败必须**从备份恢复原值**，使注册表回到写前态（fail-safe）。源码复核3遍：registry_write 各失败分支仅 return build_error，无 restore；备份文件已存但无消费。
- **改法（合规，10规范）**：
  1. registry_read 暴露 `restore_registry_backup(backup_path)`（`reg import` 回滚），供 write/delete 复用（DRY，入库 FUNCTIONS.md）。
  2. `registry_write`（及 delete）失败分支：`restore_registry_backup(backup_path)` 后 error detail 追加"已从备份回滚（成功/失败）"；若回滚失败告警级别升级。
- **复核**：SRP（写/回滚各守其责）/ DRY（restore 复用）/ KISS；红case E-2 修复后应转绿（写失败后触发回滚调用）。

### 7.3 RED-E-3：重试引擎把 error-dict 当成功

| 项 | 内容 |
|----|------|
| 缺陷 | `execute_tool_with_retry` 只认抛异常；工具返回 `{code:'error'/exec_code:'error'}` 结构化错误时被当成功（成功记录+不再重试） |
| 证据 | 红case：flaky_tool 返回可重试error dict，配置 max_retries=3，实际只执行1次 |
| 影响 | 可重试类错误返回dict即"一次过"，重试配置空转 |
| 文件 | `backend/app/tools/tool_retry_engine.py` L567-576 |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**：工具结果承诺 `{code,data,message}`（AGENTS.md），则 `execute_tool_with_retry` 的"成功"判定必须同时看**异常**与**结果结构**——error-dict 命中可重试类别时应驱动重试而非当作成功。源码复核3遍：L567-576 仅 `except` 触发重试，返回 dict 直接 return 成功。
- **改法（合规，10规范）**：
  1. 新增判定 `_is_retryable_error_result(result: dict) -> bool`：解析 `exec_code`/`code`/`message`，命中 `retryable_errors` 语义集（超时/连接/限流）为真；DRY 复用现有分类。
  2. 成功判定改为"非 dict 错误 或 非可重试错误类别"；可重试则 `continue` 进入重试计数循环（count、sleep、指数退避走既有逻辑）。
- **复核**：SRP / DRY（复用 retryable 分类）/ KISS（判定插点，不重构循环）；红case E-3 修复后应转绿（执行数==max_retries）。

### 7.4 RED-E-4：前端保存失败 → 陈旧 `_user_msg_id` 复用 → 一对多

| 项 | 内容 |
|----|------|
| 缺陷 | 前端保存失败仍继续发送 → orchestrator 用陈旧/兜底 `_user_msg_id`（上一条）创建新任务 → 同一 chat_user_message 被两个 chat_tasks 引用 |
| 证据 | 红case：一条 user 消息被2个task引用，`fetch_session_user_message_pairs` 返回2对 |
| 影响 | 旧气泡复制两份+终态被新任务覆写 |
| 文件 | `frontend/src/features/chat/hooks/useChatStreaming.ts`（保存失败路径）+ `backend/app/services/chat/storage.py` |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**：**后端是权威防线**——`fetch_session_user_message_pairs` 的 JOIN 已暴露 1:N；backend 在复用陈旧 `_user_msg_id` 前必须确认"该 user 消息尚无已挂任务"，有则**不再复用**、为新任务分配新 user 行（E-4 修复点在后端，前端仅配合重试/提示）。源码复核3遍：storage fetch 已用 LEFT JOIN 一对多暴露；编排侧无"该 user 是否已被 task 占用"校验。
- **改法（合规，10规范）**：
  1. backend：orchestrator 复用 `_user_msg_id` 前查 `chat_tasks` 中该 user_message_id 是否已存在任务（`COUNT(*)`）；若存在且任务非当前 → 调 `insert_user_message` 新建独立 user 行作为新任务锚（每个 task 唯一 user 引用，1:N 无法成形）。
  2. 前端 useChatStreaming 保存失败改为"提示重试，不静默继续"，且把`_user_msg_id 上下文清除`（KISS 配合）。
- **复核**：SRP（后端定归属）/ KISS（计数判定+/新行兜底）/ 禁 backward（老任务不回退，仅新任务锚新行）；红case E-4 修复后应转绿（每 user 消息最多 1 对）。

### 7.5 RED-E-5：registry 备份缓存永不刷新

| 项 | 内容 |
|----|------|
| 缺陷 | `_backup_registry` 缓存命中后同键永不重新导出；再次写前备份拿到的是首次备份文件（过期快照） |
| 证据 | 红case：同键二次调用 `_backup_registry`，导出仅1次（缓存命中首备份） |
| 影响 | 二次写前若键已变化，回滚目标为最初状态而非"二次写前状态" → 备份与当前快照脱节 |
| 文件 | `backend/app/tools/win_registry/registry_read.py` L58-63 |

**修改方案（小欧 2026-09-20 13:14:50）**：
- **思路（最佳逻辑）**：**写前备份必须是"当时键的最新快照"**——缓存只应防重复导出（同一次操作），跨操作次必须重新 `reg export` 覆盖。源码复核3遍：`_backup_registry` 命中 `_registry_session_backup` 缓存后直接 return 首备份文件路径（陈快照）。
- **改法（合规，10规范）**：

- **复核**：SRP / KISS / 与 D-6（唯一名）+A-4（会话键）共同构成备份三原则；红case E-5 修复后应转绿（二次调用再次导出）。
