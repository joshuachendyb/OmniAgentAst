## 四、根因判定

本次 `end_type=cancelled` 的**直接原因**是：**前端 SSE 连接于 17:34:14 中断，前端按既有策略重连 3 次全部失败后，于 17:36:26 自动调用取消接口**（`useSSE.ts:165-170`），后端随后忠实执行了该取消防令（置标志 → 打断在飞 step=3 的 LLM 流 → 终态 CANCELLED）。

**用户未点击中断按钮，结论不冲突**：前端取消端点全工程仅 2 处调用，一处为人工（按钮），一处为自动（重连耗尽）；用户确认无人工操作，则必然走自动路径。

**排除项**：后端进程重启不会产生此类 cancelled（`running_tasks` 为内存字典，重启后 `set_cancelled(task_id)` 找不到任务返回 False，标志无法置位），故本次与后端重启无关。

## 六、前后端责任分析（回答"原因前后端都有吗"）

**直接触发源在前端**：自动取消行为本身是 2026-07-12 北京老陈定案的既定策略（"重连 N 次全失败 → 才置为取消，不武断算取消"），代码实现与该定案一致，本次属于该策略的正常生效，非前端故障。**但在 `after_seq` 续传机制完善之后，自动取消应降级为兜底手段**（见§七），主策略改为轮询观察 + 续传。

**后端无功能 bug**：取消链（置标志→打断流→终态 CANCELLED→不误判 failed）在 2026-09-07 病根修复后语义正确。但存在三处协同短板，构成"用户感知层面的原因在后端也有份"：

1. **断连语义不一致（体验缺口）**：后端在客户端断开时明确"agent 后台继续"（stream_orchestrator.py:398-401），工具副作用会继续执行；而前端在重连耗尽后判定整个任务取消。于是出现"任务已被取消，但搜索工具副作用已经发生且结果不可回传"的矛盾体验。
2. **取消文案误导排查**：后端日志与终态文案一律使用"用户取消"字样（`handle_answer.py:107` 输出"用户取消"、`_cancel_final_dict` content="任务已被取消"），未区分"用户主动取消"与"连接中断自动取消"，对排查者产生误导（本次首轮排查即被此字样带偏）。
3. **取消生效有约 13 秒延迟**（17:36:26 置标志 → 17:36:39 打断流）：LLM 取消采用"循环/块粒度"检测（`react_loop.py:136-149` 注释方案 B 的已知权衡），非流式热路径逐 chunk 即时中断，属设计取舍而非缺陷。

## 七、改进建议（北京老陈 2026-09-08 裁定，三层递进策略）

### 7.1 第一层：主策略——重连失败后切换为"轮询观察"模式（前端）

重连 3 次 SSE 失败后，**不调 cancel**，改为：

1. 每隔 5-10 秒轮询一次 `GET /chat/history/{sessionId}/{serverTaskId}` 查任务状态。
2. 任务仍在跑（状态=executing）→ 前端保持"执行中"提示，显示"连接已断，等待重连或查看结果"。
3. 任务已终态（completed/failed/cancelled）→ 拉取结果，正常展示。
4. 轮询超过一定次数（建议 30 次，约 5 分钟）任务仍无变化 → 提示用户"任务可能已终止，是否手动刷新"。

**优点**：`after_seq` 机制自然生效；用户不会看到误取消；任务有自然终止出口（后端自身完成/失败/异常退出后 `running_tasks` 清理）。

### 7.2 第二层：兜底——后端补"断连超时保护"

在 `task_runtime.py` 的取消链里，加一个"断连超时"来源标记，与用户主动取消区分：

- `task_control.cancel(task_id, source="client_disconnect_timeout")` —— 新增 source 参数（可选，见 7.4）。
- 终态文案/日志明确写"因连接中断超时而结束"，不再混用"用户取消"字样。
- 该兜底仅在轮询观察也失效（后端长时间无清理信号）时由后端侧触发。

### 7.3 第三层：正道——正式利用 after_seq 续传机制

`stream_orchestrator.py:417-446` 的 `after_seq` 续传已存在：

- 客户端断连后，后端继续产出事件（seq 递增）。
- 客户端重连或轮询时传 `after_seq`，后端补发漏掉的事件。

建议在 60 秒超时后，前端不立即取消，而是尝试一次 `after_seq` 拉取（如果还有 `serverTaskId`）：
- 拉取成功 → 展示结果，不再需要重连 SSE。
- 拉取失败（404/任务已清理）→ 才兜底提示"任务已终止"。

### 7.4 后端配套：取消来源区分

| 改动 | 位置 | 说明 |
|---|---|---|
| cancel 端点增加 `source` 参数 | `chat_routes.py:57-59` | 区分 `user_requested` / `client_disconnect_timeout`，随取消请求落库 |
| 取消终态文案区分来源 | `handle_answer.py:102-112` | source=client_disconnect_timeout 时文案写"因连接中断超时而结束"，不再统一写"用户取消" |
| 日志区分来源 | `task_runtime.py:66` | `[TaskControl] 取消任务 {task_id} source={source}` |

### 7.5 原策略的历史定位

原"重连耗尽自动取消"（2026-07-12 北京老陈定案）在 `after_seq` 续传机制完善之前是合理的兜底策略。现在 `after_seq` 已可用，自动取消应降级为最后手段（轮询也失败、后端长时间无清理信号时），不再作为主策略。

### 8.5 后端↔LLM 超时机制澄清（v1.2 补充，答疑北京老陈疑问）

> 背景：北京老陈追问"记得后端与 LLM 之间有一个 60 秒超时"，核实后端↔LLM（httpx 流式）与前端↔后端（SSE）两条链路超时语义不同。此节澄清后者非 60s 判死，并推导出 tool_call 累积转发延迟 → 前端 60s 假超时的根因链条。

**8.5.1 两条链路的超时机制对照**

| 维度 | 前端↔后端（SSE） | 后端↔LLM（httpx 流式） |
|---|---|---|
| 空闲超时 | **60 秒**（IDLE_TIMEOUT=60000）→ 判断开 → 重连 3 次 → 自动取消 | **150 秒起**（DEFAULT_READ_TIMEOUT=150，constants.py:80），每次重试 +20s（base_service.py:257） |
| 语义 | 60s 无任何 SSE 事件 = 判死 | read timeout 是"两字节间隙"空闲超时，非总时长（base_service.py:282-283） |
| 总时长上限 | 无（靠 60s 空闲判死兜底） | **500 秒**硬截断（STREAM_TOTAL_TIMEOUT=500，constants.py:89；base_service.py:264） |
| 超时后果 | 断开 → 自动取消 | 500s 到 = **截断已收数据**，不判死、不重连（base_service.py:285-288） |
| 依据 | useSSE.ts:345-351 | base_service.py:257/264/282-283，constants.py:80/89 |

**关键澄清**：
1. **后端↔LLM "60 秒语气"不准确**——`IdleTimeoutIterator`/`IdleTimeoutError`（app/utils/idle_timeout.py）全工程**零调用点**，只有 error_classifier.py:128 的 isinstance 判定，无任何东西 raise 它。error_classifier.py:117"AI模型30秒内未返回任何内容"为**描述性文案，实际不生效**。
2. 后端↔LLM 在**总时长 500s 内基本"不超时持续连接"**：只要 LLM 每两字节间隔 <150s，连接一直维持；500s 到也只是**截断**（保留已收数据继续），不会判断开。故"一直连直到取得有效数据"在 500s 内成立。

**8.5.2 content 与 tool_call 的转发时机差异（核心）**

backend `base_service.request_stream`（app/llm/base_service.py）逐 chunk 处理，两条转发路径**时机不同**：
- **文本 content（thought/正文）**：`_parse_sse_data` 产 chunk 后**立即** `yield chunk`（:334-336），经 llm_call.py:117 `yield chunk` 直透 → 前端立刻收到 SSE chunk。故只要 LLM 持续输出 content，前端 SSE 就有事件，**不触发 60s 空闲超时**。
- **tool_call 参数**：**流结束后一次性 yield**（:338 注释"流结束后，如有聚合的tool_calls，原生结构一次性yield"、:342、:389），**流式期间不 yield 任何 content**。llm_call.py 只在 `chunk.content` 有值时 yield（:109-117），tool_call delta 期间无 content → **前端一个 SSE 事件都收不到**。

**8.5.3 根因链条：tool_call 累积转发延迟 → 前端 60s 假超时**

1. LLM 进入 tool_call 轮次（如 searchweb 并行/长参数），content 为空、只剩 tool_call delta 持续到达。
2. base_service 继续收（read timeout 因字节不断而续命，500s 内不判死），但**不 yield**；等流结束后才一次性 yield tool_calls。
3. 此期间前端 SSE **零事件**。若 tool 参数生成 + 后续处理累计 >60s（100s/200s 完全可能），前端 `IDLE_TIMEOUT=60000` 判无数据 → 断开 → 重连 3 次失败 → **自动取消**。
4. 而后端其实完全正常：一直在收，500s 内收全 tool_call → 处理 → 出结果，只是这 100-200s 里前端早已超时取消。

**结论**：这是"后端↔LLM 与前端↔后端**超时不对齐**"——后端能正确等到 LLM 完整数据，前端却因 60s 无事件而武断自杀。**比"网络断连"更贴合 [11] §一 的成因**。

**8.5.4 tool 获取失败的既有处理（后端不是裸死）**

- tool_call 参数 JSON 解析失败 → `_try_fix_incomplete_json` 自动修复（:357-361）；修不好记入 `failed_parses`（:363）。
- 全部 tool_call 解析失败 → raise `LLMResponseError`（:383-387）→ 交 llm_call.py L2 重试/FC 降级（:222-285）→ 最终 handle_answer 归口。
- 后端失败有完整链路，**问题只是这段耗时（数分钟）恰好越过前端 60s 门槛**，导致前端先于后端判定自杀。

**8.5.5 与 §七 三层策略的呼应**

§七 7.1（轮询观察）+ 7.3（after_seq 续传）正是针对此不对齐：前端在 60s 无事件时**不该武断取消**，而应知道后端可能仍在 tool_call 流式阶段，去轮询/续传等后端出结果。此节为 §七 提供了更扎实的成因依据。

### 8.6 SSE keep-alive 心跳方案（v1.2 补充，北京老陈建议）

> 北京老陈建议：tool 参数流式期间，前端一个 SSE 事件都收不到——可否**在后端活着时给前端一个"我还活着"的有效回应**，让前端不以为后端死掉。此即业界标准 **SSE heartbeat（心跳）** 机制。

**8.6.1 前端空闲判定的真实依据（实证）**

前端 useSSE.ts 的空闲计时**基于字节到达**，不是业务事件：
- 每次 `await reader.read()` 前把 `lastDataTimeRef.current = Date.now()`（useSSE.ts:659）；`IDLE_TIMEOUT=60000` 判定看 `timeSinceLastData = Date.now() - lastDataTimeRef.current`（:648）。
- 即：**只要 `reader.read()` 返回任何字节（含 SSE 注释行 `: ping`、空 frame），`lastDataTimeRef` 就被刷新，60s 判定永不触发**。
- 而 `processSSEData`（sseParser.ts:37）首行判断 `!trimmedLine || !startsWith('data: ')` → **直接 return**（:112-115）。SSE 注释行 `: ping` 以冒号开头，**不命中 `data: ` 前缀 → 直接忽略**，不产生任何 JSON 解析、不干扰 seq / step / 业务状态。

**结论**：后端发 SSE 注释行心跳 `: ping`，前端 `reader.read()` 返回 → 刷新空闲计时 → 不判死，且 `processSSEData` 忽略之，**零副作用、前端零改动**。

**8.6.2 后端实施点（stream_orchestrator.py:441）**

后端读取缓冲处 `stream_reader` 已有 `cond.wait(timeout=60.0)`（:441），超时后重检 `done` 再 continue。**此处正是心跳最佳插入点**——超时即代表"60s 内无业务事件（可能正处于 tool 参数流式）"：

```python
try:
    await asyncio.wait_for(buffer.cond.wait(), timeout=60.0)
except asyncio.TimeoutError:
    # SSE keep-alive 心跳：60s 内无业务事件（如 tool 参数流式期间）向前端发注释行，
    # 刷新前端 IDLE_TIMEOUT=60000 空闲计时，防"后端活着却被判死自动取消"（§8.5.3）。
    # 前端 processSSEData 对 `:` 注释行直接 return（sseParser.ts:112-115），零副作用 — 小欧 2026-09-08
    logger.debug(f"[SSE] cond.wait 60s超时, 发心跳保活后重检done: task_id={task_id}")
    yield ": ping"   # SSE 注释行心跳，前端不计为业务事件但刷新空闲计时
    if buffer.done.is_set():
        return
    continue
```

**8.6.3 效果与取舍**

| 项 | 说明 |
|---|---|
| tool 流式期间 | 前端零业务事件，但后端每 60s 一次 `: ping` → 前端 `lastDataTimeRef` 刷新 → **不判死** |
| 心跳副作用 | `: ping` 不落入 `processSSEData` 业务解析（sseParser.ts:113 直接 return），**不影响 seq/step/任何状态** |
| 前端改动 | **零**（纯后端一行 yield） |
| 周期选择 | 60s 与 `cond.wait` 天然对齐、改动最小；若求更稳可缩至 30s（< 前端 60s 一半） |
| 与 §七 关系 | 心跳是**实时连接层的防线**（防断判死）；§七 轮询/续传是**断连后的兜底**，两层互补：有心跳则前端根本不判断连，断连兜底几乎用不上 |

**8.6.4 结论**

心跳方案把"后端↔LLM 正常工作但长期无业务事件（tool 流式）"与"前端↔后端真正断连"**区分开来**：前者前端通过 `: ping` 保活续命，永不误判；后者（真断连、`reader.read()` 长时间无字节）心跳自然停发，前端仍按 60s 判死走重连/兜底。此方案与 §七 三层策略同为实现"前后端超时对齐"的目标，属**预防性、最小改动**的一层。
