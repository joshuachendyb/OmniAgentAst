## 一、问题描述

### 1.1 用户可见问题

配置页保存 Provider、模型、采样参数或模型参数后，配置热重载会触发生命周期 `reset()`。如果此时已有聊天任务正在执行，任务后续调用 LLM 可能出现：

```text
Cannot send a request, as the client has been closed.
```

该错误不是测试脚本制造的假失败，而是后端真实资源生命周期回归：

1. 任务开始时取得一个共享 `httpx.AsyncClient` 或连接池引用。
2. 配置写入成功，`reload_ai_config()` 调用 `reset()`。
3. `reset()` 关闭旧 `BaseAIService`。
4. 旧 `BaseAIService.close()` 释放共享 client。
5. 活动任务仍持有旧 client 的引用，下一次 `post()` 或 `stream()` 直接失败。

### 1.2 当前代码根因

当前工作树中，问题由以下链路共同造成。

#### 1.2.1 配置更新会直接触发 reset

`backend/app/services/model/config_helpers.py:143-147`：

```python
def reload_ai_config() -> None:
    config_obj = get_config_instance()
    config_obj._load_config()
    reset()
```

该 reset 链路本身是产品要求，不能删除。问题在于旧服务关闭时没有等待活动任务释放连接池引用。

#### 1.2.2 服务工厂在生命周期管理中混合了裸 client 所有权

`backend/app/llm/base_service.py:151-195` 当前同时维护：

- `_llm_sdk`
- `_shared_client`
- `_shared_lease`
- `_owns_client`

`BaseAIService` 创建 `LLMClient` 后又直接修改 SDK 私有字段：

```python
self._llm_sdk._client_lease = None
self._llm_sdk._owns_client = False
```

这导致 BaseAIService 和 LLMClient 都像“客户端所有者”，实际关闭时职责不唯一。

#### 1.2.3 共享池引用计数不是线程安全状态机

`backend/app/llm/client_sdk.py:64-146` 当前 `_SharedClientPool` 存在以下问题：

- lease 的 `_released` 与池 `_ref_count` 不在同一把锁内判断。
- `close()` 失败只记录 warning，不保留可重试状态。
- 没有 owner event loop 绑定。
- 同步配置线程可能直接在不同 loop 执行 `AsyncClient.aclose()`。
- `close_on_zero=False` 使“借用池”和“自有池”的所有权语义不清。
- 底层 client 被外部关闭后，池仍可能允许继续 acquire。

#### 1.2.4 resolver 使用反射和裸 client 回退

`backend/app/services/model/resolver.py:144-173` 当前存在：

- `getattr(type(ai_service), ...)`
- `ai_service.__dict__`
- `_shared_client` 裸对象回退
- `_DEFAULT_SHARED_UNSET`
- `lease_transferred` 布尔值推断所有权

这些兼容分支绕过了统一引用计数，无法证明 snapshot 实际持有哪个 lease。

#### 1.2.5 snapshot 交接前存在资源泄漏窗口

`backend/app/services/chat/stream_orchestrator.py:384-493` 当前先构造 `UniversalAgent`，再把 resolver 返回的 snapshot 替换给 `agent.llm_client`，最后才创建后台任务。

在以下任一阶段发生异常时，runner 的 finally 尚未接管 snapshot：

- snapshot 构造完成后的日志处理。
- DB eager 写入。
- 文件 writer 创建。
- `asyncio.create_task()`。

结果可能是 snapshot lease 已从 resolver 转出，但后台任务尚未启动，runner 无法释放。

#### 1.2.6 任务注册表保存的是全局 owner

`backend/app/services/task/task_registry.py:75-103` 当前 `register_task()` 保存 `ai_service`。任务实际使用的是后续替换的 snapshot，取消、关闭和所有权判断可能指向错误对象。

#### 1.2.7 runner 依赖私有 `_is_snapshot`

`backend/app/services/agent/agent_runner.py:527-538` 通过私有标记决定是否关闭客户端。私有标记不是所有权协议，且不能覆盖 snapshot 交接前的异常路径。

### 1.3 当前测试证据

此前定向和全量测试曾出现以下结果：

- 后端全量：7355 passed、1 skipped、127 warnings。
- 前端 Vitest：1333 passed。
- 正式前端 E2E：121 passed。
- 08/09 清理改动单独验证：3 passed。

这些结果不能作为本次修复的最终验收结论，因为当前实现仍存在：

- 引用计数竞态。
- 跨 event loop 关闭路径。
- lease 所有权转移不明确。
- 关闭失败不可重试。
- 旧测试仍验证 `_is_snapshot`、裸 `shared_client` 和过时取消契约。

本方案不以放宽测试断言或增加兼容分支解决问题。

### 1.4 本次范围

本次只处理真实后端资源生命周期回归：

- 共享 HTTP client 的唯一所有权。
- 配置 reload 与活动任务的安全共存。
- session snapshot 的 lease 保护。
- 任务注册、取消、runner 收尾的所有权一致性。
- 关闭失败、取消、跨 loop 的可观察性和可重试性。

不在本次源码实施中混入：

- 前端模型库功能。
- 设置页外部提交。
- 无关 logger 改动。
- 通过测试特例修改产品行为。

## 二、实施新的方案策略和优化后的效果优点

### 2.1 最终架构决策

新的唯一所有权链如下：

```text
BaseAIService owner
    └─ LLMClient
        └─ SharedClientLease
            └─ _SharedClientPool
                └─ httpx.AsyncClient
```

约束如下：

1. `_SharedClientPool` 是底层 `httpx.AsyncClient` 的唯一所有者。
2. `LLMClient` 只拥有一个 `SharedClientLease`，不再接收裸 `AsyncClient`。
3. `BaseAIService` 只负责业务参数、重试、取消和 snapshot，不直接操作 SDK 私有字段。
4. 同 Provider 的任务共享底层池，但每个任务拥有自己的 `LLMClient` 和 `BaseAIService`。
5. 跨 Provider 使用独立池。
6. resolver 在任何可能触发配置 reset 的 await 前取得 guard lease。
7. guard lease 创建 snapshot 成功后显式转移所有权；失败则在 finally 释放。
8. snapshot 交给后台 runner 前由 orchestrator 负责关闭；交接后由 runner 负责关闭。
9. `reset_sdk` 全仓没有生产调用，直接删除，不保留兼容 API。
10. `reset_cancel()`、`_current_response`、`_cancelled` 和取消短路全部保留。

### 2.2 资源状态机

```text
ACTIVE
  └─ ref_count 归零
       └─ CLOSING
            ├─ aclose 成功 → CLOSED
            └─ aclose 失败/取消 → CLOSE_FAILED
                                      └─ 可再次 retry_close
```

池状态必须保证：

- `ref_count`、`_released`、状态迁移在同一把锁内判断。
- 并发 release 不会重复减少引用。
- `CLOSED` 或 `CLOSE_FAILED` 状态不能重新 acquire。
- `client.is_closed` 必须在 acquire 时再次检查。
- `aclose()` 异常不得被吞掉。
- 关闭 future 在 owner loop 上只执行一次 `aclose()`。
- 关闭被取消时，future 保留，后续可重试。
- owner loop 不可用时明确失败，不静默创建新 loop 关闭底层 client。

### 2.3 事件循环策略

首次真实请求绑定 `owner_loop`：

- 同 loop 请求：直接执行。
- 其他 loop 请求：明确抛出 `RuntimeError`。
- 其他 loop 关闭：使用 `run_coroutine_threadsafe()` 回到 owner loop。
- owner loop 已停止：明确失败并保留 `CLOSE_FAILED`。
- 软配额 `Semaphore` 按 event loop 隔离，避免跨 loop 复用。

### 2.4 完整业务调用链

```text
配置更新
  └─ reload_ai_config()
       └─ reset()
            └─ 锁内摘除旧 owner
            └─ 锁外提交旧 owner.close()
                 └─ 释放 owner lease
                      └─ 活动 snapshot lease 仍存在
                           └─ 底层 pool 不关闭
                                └─ 活动任务继续请求
```

新任务启动链：

```text
orchestrator
  └─ active task 检查
       └─ acquire_service_lease()
            ├─ 工厂锁内确认当前 owner
            ├─ 创建/取得 BaseAIService
            └─ 取得 guard lease
                 └─ resolve_session_client()
                      ├─ await db.atxn()
                      ├─ 创建任务 snapshot
                      └─ transfer guard lease
                           └─ register_task(snapshot)
                                └─ runner 接管
                                     └─ finally 关闭 snapshot
```

### 2.5 优化后的优点

| 优化点 | 优化前 | 优化后效果 |
|--------|--------|------------|
| 所有权 | BaseAIService、LLMClient、resolver 多处持有可能 | 一个池、一个 lease、一个关闭入口 |
| 配置 reload | 旧 client 可能立即关闭 | 活动 lease 存在时底层 client 不关闭 |
| 并发安全 | ref_count 与 released 分离 | 同一锁保护状态迁移 |
| 跨 loop | 新 loop 直接 aclose | 回到 owner loop 关闭 |
| 配置读取 | DB await 前可能丢 owner | factory 锁内先取得 guard lease |
| 跨 Provider | 裸 client 回退语义不清 | 明确独立池 |
| 任务取消 | 注册表保存全局 owner | 注册表保存实际任务 snapshot |
| runner 收尾 | 依赖 `_is_snapshot` 私有标记 | 按任务所有权统一关闭 |
| 关闭失败 | warning 后丢失 | `CLOSE_FAILED` + retry |
| 软配额 | 全局 Semaphore 跨 loop | 按 loop 隔离 |
| 取消语义 | 重构时容易误删 | `reset_cancel`、响应追踪和取消短路保留 |
| 兼容代码 | 反射、裸 client、sentinel 并存 | 禁止 backward，删除废弃路径 |

13. `cancel_task()` 命中当前任务 snapshot。

15. `LLMClient.cancel()` 能关闭流式 HTTP response。

### 4.5 真实后端 E2E

真实 E2E 必须使用真实后端、真实 LLM、真实 SQLite，不使用 Mock。

每次只执行一个 case：

1. 启动后端。
2. 启动聊天任务。
3. 在任务仍运行时通过配置接口保存 Provider 或模型参数。
4. 等待任务继续产生 LLM 输出。
5. 检查日志无：

```text
Cannot send a request, as the client has been closed
```

6. 检查任务 SSE 正常结束。
7. 检查 DB 终态、token、步骤完整。
8. 检查配置对象无临时 Provider 或临时模型残留。
9. 检查 shutdown 时无未取出的关闭任务异常。

### 4.6 并发验证

至少执行以下并发矩阵：

| 场景 | 预期 |
|------|------|
| 同 Provider、两个任务、一个配置 reload | 两个任务继续请求，最后一个 lease 释放后 client 关闭 |
| 不同 Provider、两个任务、一个配置 reload | 各自 client 独立，不串 provider |
| 任务 A 取消、任务 B 继续 | 只取消 A 的 HTTP response |
| owner reset 发生在 resolver DB await 期间 | snapshot 创建成功，client 不关闭 |
| owner reset 发生在 runner 创建前 | orchestrator 关闭 snapshot，不泄漏 |
| runner 取消发生在 finally 收尾期间 | DB 和终态完成，client 最终释放 |
