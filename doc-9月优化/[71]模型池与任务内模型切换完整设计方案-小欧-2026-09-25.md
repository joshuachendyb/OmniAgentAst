## 零、背景与问题的提出

北京老陈提出**模型池**概念：配置多个备选模型，在任务执行中按需切换。

两个使用场景：

1. **场景一（故障转移 failover）**：一个任务选用模型 A 执行，若 A 连续多次调用失败/被拒绝，则自动切换到备选模型 B（有序优先队列），避免任务整体失败。价值：当前 `llm_call.py:243-245` 对 `quota_exceeded`/`rate_limit`/`idle_timeout`/`client` 四类错误**直接放行判死**——429 配额耗尽即任务失败，无任何挽回余地。模型池把这条死路改为"跨模型 failover"。

2. **场景二（多 Agent 各用各模型）**：后续演进为多 Agent 编排，一个主任务拆分为多个 sub-agent，Agent A 用模型 A、Agent B 用模型 B，实现角色化/专业化分工。

另有第三个能力与本方案同源——**任务内模型切换**（配置热切换时，正在执行的任务按对账点切换到新模型）。三者共享同一套底层设施：**运行时模型可变（reconcile）**。

## 一、三者关系与技术底座总览

### 1.1 结论：底层同源，触发点不同

| 能力 | 触发源 | 触发时机 | 复杂度 |
|------|--------|---------|--------|
| ① 配置热切换 | 事件驱动（reload_ai_config 后被动对账） | 轮边界（React 循环顶检查，天然安全） | 低 |
| ② 模型池 failover（场景一） | 错误驱动（LLM 调用失败后主动切换） | 调用失败点（重试耗尽瞬间，在生成器内部） | 最高 |
| ③ 多 Agent（场景二） | 编排驱动（sub-agent 创建时按 model_ref 建快照） | sub-agent 边界（创建即定型，无需运行中切换） | 中（重点在记账） |

### 1.2 共享底座：运行时模型可变设施（reconcile_llm_client）

三者的共同核心能力是：**让一个正在运行的 Agent/任务，把 `agent.llm_client` 从模型 A 换成模型 B**。

现状（阻碍任务内切换的 7 个点，均在 [70] 及现有代码中核实）：

1. **身份+传输捆绑为任务级一次性快照**：`base_agent.py:64-67` `self.llm_client` + `self._task_llm_model` 构造时定死，全任务不可变；换模型=必须重建快照+换 lease。
2. **React 循环无重解析点**：`llm_call.py:94` 每轮直接 `agent.llm_client.request_stream()`；`agent_runner.py:382` 一次捕获，无处可插。
3. **上下文门限启动时定死**：`agent_runner.py:383-384` 用启动模型 `context_limit` 覆盖 `message_builder.MAX_CONTEXT_TOKENS`，此后不再重算。
4. **消息历史按旧模型格式攒**：`message_builder.conversation_history` 是 FC 消息/工具调用配对/`_temp_reasoning` 标记，换模型后喂给新模型有格式兼容风险。
5. **记账是"任务级单模型"**：`token_usage.task_model`、`telemetry`、`step_emitter.py:55`、`llm_response_builder.py:29-31` 全走构造时定死的 `_task_llm_model`，只有"一个任务=一个模型"的格子。
6. **lease 生命周期=任务生命周期**：[70] 语义"任务 acquire 旧代 lease → 跑完 close 归还"；任务内换模=打破 close 三分支简单逻辑，一个任务横跨两代，令 `drain` 复杂化。
7. **设计哲学"任务零感知"**：[70] 定案（doc L179/181）"新请求即新代、旧任务零感知"——任务内切模需主动打破此边界（属需求升级）。

**共享底座设计（一次建设，三者复用）**：

```
模块: reconcile_llm_client(agent, session_id)  —— 运行时模型对账/切换
逻辑:
  1. 计算目标模型 target_model_ref：
     ① 配置热切换 → 当前 scope.model_ref（get_scope().ai_service.llm_model）
     ② failover    → 模型池有序队列中下一个可用模型
     ③ 多Agent     → 该 sub-agent 创建时固定的 model_ref（无需运行中调）
  2. 若 target == agent.llm_client.llm_model → 直接返回（零开销）
  3. 否则执行模型切换：
     a. release 旧 client_lease（归还旧代，[70] close 三分支幂等复用）
     b. acquire 新 scope lease（目标模型所在池，见 [70] scope.acquire_lease）
     c. 重建 snapshot：BaseAIService.snapshot(model_ref, shared_client=lease.client, client_lease=lease)
     d. 更新 agent.llm_client = 新快照、agent._task_llm_model = 新 model_ref
     e. 重算 agent.message_builder.MAX_CONTEXT_TOKENS = 新模型 context_limit
     f. 清理 _temp_reasoning/兼容标记（防跨模型格式污染）
     g. 发 SSE meta 事件（retrying/meta:type=model_switch）通知前端
  4. finally 由现有 run_agent_in_background close 流程收口新 lease
```

**关键点**：
- 换模型**不重建 message_builder 历史**（conversation_history 与 llm_client 已解耦，历史是纯文本列表，跨模型可继续喂；仅需重算上下文门限）。
- 记 account 段：token_usage 从"任务=单模型一行"扩展为"任务=多模型段"（见第五章）。

## 三、模型池配置设计

### 3.1 配置形式：有序优先队列（北京老陈拍板 2026-09-25）

配置项（新增，放 config.yaml 的 `ai` 区域或独立 `ai.model_pool`）：

```yaml
ai:
  model_ref:                       # 当前主用模型（现有，任务默认入口）
    provider: sensenova
    model: sensenova-6.8-flash-lite
  model_pool:                      # 新增：模型池有序优先队列
    enabled: false                 # 总开关（默认关，开=启用 failover）
    strategy: ordered              # 有序优先（唯一策略）
    candidates:                    # 备选队列 [主模型A, 备选B, ...]
      - provider: sensenova
        model: sensenova-6.8-flash-lite
      - provider: glm
        model: glm-5.2
    trigger:                       # 触发条件（场景一）
      error_types: [quota_exceeded, rate_limit, idle_timeout, timeout, server]
      consecutive_failures: 1      # 连续失败 N 次触发切换（建议从 1 起步，配合现有 L2 重试）
    switch_mode: task_level        # 任务级切换（切到 B 后本任务剩余轮次都用 B）
```

### 3.2 与现有重试机制的关系（关键设计决策）

现状 `llm_call.py` 三级重试链路全为"同模型内"：
- **L1 传输重试**（base_service 内，传输/限流瞬时错误）→ 保留
- **L2 响应重试**（`llm_call.py:253-273`，指数退避，默认 `response_retries` 次）→ 保留，作为"模型内先自救"
- **FC 降级 Text**（`llm_call.py:275-307`）→ 保留，同模型最后自救

**模型池 failover 插入点**：在 L2 重试耗尽 → FC 降级**之前**，先判定"是否属于池内可换错误类型"：

```
错误类型 ∈ {quota_exceeded, rate_limit, idle_timeout, timeout, server}？
  ├─ 是 → 直接走模型池：切下一候选模型 → 用新快照重新发起该轮 LLM 调用
  │        （不再单人独舞到死；429 这种模型级配额问题，换模型才是正解）
  └─ 否 → 维持现有逻辑（L2 重试 → FC 降级 → 判死）
```

**业务拒绝类（blocked/user_rejected/rejected）不触发切换**（拒绝≠模型坏了，换模型也照样拒绝，还会让拒绝语义混乱）。

## 四、场景一：模型池故障转移（failover）详细设计

### 4.1 状态机

```
任务当前模型 = A（池内下标 0）
   │
   ▼ 出现触发错误（quota_exceeded 等，连续失败≥consecutive_failures）
[尝试切 B（下标 1）] ──(当前是 A，队列还有下一名)──► reconcile_llm_client(agent, target=B)
   │                                                      │
   │ B 也失败（累计：A失败N + B失败N ≥ 池长度×N 仍不成）        │ 成功
   ▼                                                      ▼
[尝试切 C（下标 2）...直到池耗尽]                     本任务剩余轮次用 B（switch_mode=task_level）
   │
   ▼ 池耗尽仍失败
任务判失败（现有 error 兜底路径）
```

### 4.2 切换触发时机（在生成器内部）

`call_llm_with_fallback` 现状在 L243-245 对四类错误 `yield item; return` 直接放行判死。改造为：

```
for 该轮调用:
  while 模型池还有下一候选:
    尝试 call_llm_stream(当前模型)
    若失败 ∈ 可换错误类型（连续次数达标）:
       logger.warning + yield meta(model_switch:A→B)   # 前端可见
       reconcile_llm_client(agent, 队列下一模型)
       continue  # 用新模型重新发起该轮
    若失败 ∉ 可换错误类型: 走现有 L2 重试 → FC 降级 → 判死
  池耗尽: 现有 error 兜底
```

### 4.3 关键不变量

| 不变量 | 保证 |
|--------|------|
| **换模型不丢上下文** | conversation_history 纯文本列表跨模型可继续，不重建（仅重算窗口） |
| **换模型不脏记账** | token_usage 按"任务×模型段"分行/Segment（第五章） |
| **换模型不破坏取消** | 换前 `_check_stop()` 短路（复用 FC 降级前 C-2 的模式，已取消不发降级请求） |
| **换模型不反复横跳** | switch_mode=task_level：切到 B 后本任务不再回 A，轨迹单向向前 |
| **池有限** | 候选耗尽→任务失败（不无限循环） |

## 五、场景二：多 Agent 各用各模型详细设计

### 5.1 定位

多 Agent 是**编排层**能力（`stream_orchestrator` 上层），主任务拆分为多个 sub-agent，每个 sub-agent 在**创建时**通过 `resolve_session_client`/`snapshot(model_ref)` 绑定自己独立的 `llm_client`。**不需要运行时切换**（sub-agent 创建即定型）。

### 5.2 与现有的结合点

- 复用：`predictor.resolve_session_client` / `BaseAIService.snapshot(model_ref, shared_client, client_lease)` 已支持任意 model_ref 建独立快照（[70] 连接池语义天然支持多 scope 并存）。
- 新增：编排层 sub-agent 注册表（sub-agent_id → agent 实例 → model_ref → 父任务 task_id）。
- 记账扩展：一个主任务下挂多个 sub-agent 模型，`token_usage` 需按"任务×模型段"记录（见下）。

### 5.3 注意：多 Agent 的模型来源

| sub-agent | 模型来源 |
|-----------|---------|
| 默认 | 继承主任务 resolved 模型（现状 resolve_session_client） |
| 指定 | 编排配置中为 sub-agent 声明 model_ref（如"研究员用深度推理模型、代码 Agent 用代码模型"） |
| 兜底 | 该模型启动失败 → 可走场景一 failover 到模型池下一候选（两场景可叠加） |

## 六、记账与记录侧改造（共享）

### 6.1 记账：token_usage 由"任务=单模型"变"任务=模型段"

现状：`token_usage` 每任务一行，`task_model` 为 ModelRef JSON，`llm_call_count` 单计数。

改造方案（KISS，不推翻表结构）：
- `token_usage` 仍按任务一行，但 `task_model` 保留为**该任务最后一个模型**；**新增 `model_segments` JSON 数组列**（或独立表 `task_model_segments`），记录 `[{model, start_seq, end_seq, prompt_tokens, completion_tokens, calls}]` 模型段轨迹。
- `telemetry` / `step_emitter` / `llm_response_builder` 的模型归属从"读 `_task_llm_model`"改为"读当前段模型"（reconcile 切换时同步推进段指针）。
- SSE `usage`/`stats` 事件带当前段模型，前端可展示"本轮用的模型"。

### 6.2 记录侧：E2E helper `write_test_record` 1.1 表扩展

刚完成（本轮改动）的 `record_test_baseline` + `1.1 本次运行的任务 × 模型明细` 表，扩展为支持**任务内模型段**：

| 模型段 | 说明 |
|--------|------|
| 任务级多模型（现状已支持） | 同一 session 多个任务各用各模型 → 1.1 表按任务列出 |
| **任务内模型段（本方案新增）** | 同一任务内 A→B→C 切换 → 1.1 表加"段"维度：`run × task × segment(model, 起始轮, 结束轮)` |
| 多 Agent（场景二） | 主任务 × sub-agent × model → 按 sub-agent 分节列出 |

改造点：`write_test_record` 读 `token_usage.model_segments`（若存在）展开段轨迹，无则维持现"任务×模型"行为（零退化）。

## 七、架构影响与风险

### 7.1 对 [70] ConnectionScope 的影响

- **多模型并存**：模型池意味着多个 scope（A 池 + B 池）**同时活跃**。现状 [70] 是"一代一 scope，换代=任务边界"；本方案允许任务内跨代，需保证：
  - 任务结束时 `reconcile` 建的**新 lease 被 finally close 归还**（复用现有 close 三分支，新快照恒"共享池 lease"分支）。
  - `release_owner` 退休不影响正在被任务持有的旧代池（close_on_zero 语义天然成立）。
- **drain 简化约束**：任务可能横跨两代，停机 drain 仍按"各代 lease 归零"等待即可，无需特殊化（因为有 lease 计数撑着）。

### 7.2 风险清单

| 风险 | 等级 | 缓解 |
|------|------|------|
| 消息历史跨模型格式不兼容（FC 消息/工具配对喂不同模型） | 中 | 换模型前 `pop_temp_messages()` 清 `_temp_reasoning`；保守策略：仅在"工具无关的纯对话轮"允许换（或默认允许+日志记录） |
| 记账从单模型变多段，量级膨胀 | 低 | `model_segments` 段粒度=轮次，量小可接受 |
| 前端 UI 尚无语义 | 低 | 先发 retrying/model_switch meta 事件，前端后续版本消费 |
| 池配置错误（候选都不可用） | 低 | 配置校验（复用 config_helpers 校验链），池全不可用=等价不开启 failover |
| 多 Agent 编排与 HITL/回放一致性 | 中 | 场景二列为阶段二，独立评审后再实施 |

### 7.3 阶段划分

| 阶段 | 内容 | 依赖 |
|------|------|------|
| 阶段一 | 共享底座 reconcile_llm_client + 记账 model_segments + 记录侧段轨迹 | 无 |
| 阶段二 | 场景一 failover（模型池配置 + call_llm_with_fallback 改造） | 阶段一 |
| 阶段三 | 场景二 多 Agent（编排层 sub-agent + 各 agent model_ref） | 阶段一（独立） |

### 8.2 核心设计：reconcile_llm_client（详细）

#### 8.2.1 问题定位（现状锁死的 7 点，均有代码证据）

**结论：`message_builder.conversation_history` 与 llm_client 已解耦，历史是纯文本列表，跨模型可继续喂——这是底座实现的硬件基础。**

#### 8.2.2 切换执行逻辑（async，单事件循环安全）

```
async def reconcile_llm_client(agent, scope) -> bool:
    target = scope.ai_service.llm_model               # 当前配置代生效模型
    cur    = agent.llm_client.llm_model
    if target == cur: return False                     # 零开销热路径
    # ①先摘旧引用防泄漏，close 三分支幂等复用（[70]）
    old_lease = agent.llm_client.client_lease
    # ②acquire 新 scope lease（[70] scope.acquire_lease；若代已退休/池未建→跳过，维持旧模型继续跑，不中断任务）
    lease = scope.acquire_lease()
    # ③重建快照：BaseAIService.snapshot(target, shared_client=lease.client, client_lease=lease)
    # ④推进指针：agent.llm_client = 新快照；agent._task_llm_model = target
    # ⑤重算 message_builder.MAX_CONTEXT_TOKENS = 新模型 context_limit（压缩阈值同步变）
    # ⑥pop_temp_messages() 清 _temp_reasoning 跨模型格式标记
    # ⑦segment 记账推进（见 8.4）：关旧段、开新段
    # ⑧发 SSE meta(model_switch: old→new) 事件 + logger.warning
    # ⑨finally：旧 lease 归还（先 acquire 新、后 release 旧，防 acquire 失败丢池）
    return True
```

#### 8.2.3 关键顺序与 fail-soft 策略

| 要点 | 保证 |
|------|------|
| **先 acquire 新、后 release 旧** | acquire 失败时任务仍持有旧池，不裸奔 |
| **任何一步失败 → 维持旧模型继续跑** | 任务不中断（fail-soft，切换是增益不是风险源） |
| **热路径零开销** | target==cur 直接 return，不触发任何切换动作 |
| **取消优先** | 切换前 `_check_stop()` 短路（复用 FC 降级前 C-2 模式），已取消不发切换请求 |

### 8.3 段式记账设计（扩展性最佳的核心）

#### 8.3.1 裁定：独立表 `task_model_segments`（不挤 token_usage JSON 列）

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | INTEGER PK | 主键 |
| `task_id` | TEXT NOT NULL | 外键→chat_tasks |
| `agent_id` | TEXT NULL | **预留**：阶段二多 Agent 用子 agent 标识，底座时不填（NULL=主 agent） |
| `seq` | INTEGER NOT NULL | 段序号（任务内 A=0, B=1, C=2） |
| `model` | TEXT NOT NULL | ModelRef JSON（provider/model/display_name） |
| `start_round` / `end_round` | INTEGER | 段跨越的 LLM 轮次（[start, end] 闭区间） |
| `prompt_tokens` / `completion_tokens` | INTEGER | 段内 token 计数 |
| `calls` | INTEGER | 段内 LLM 调用次数 |
| `created_at` | TEXT | 段创建时间 |

#### 8.3.2 为什么独立表是"扩展性最好"

- `token_usage.task_model` 保留=**任务当前模型**（向后兼容既有 76 case 对账零破坏）。
- 段表承载**完整轨迹**：SSE-DB 对账、报告查询、任务重放都能精确到"哪个模型用了第几轮到第几轮、花了多少 token"。
- `agent_id` 列让**阶段二多 Agent 直接复用**：主任务→多 sub-agent→多段的立体账本，无需再迁移表结构。

#### 8.3.3 telemetry 改造

- `agent_telemetry.py:293-296` 读 `_task_llm_model` 处改为"读当前段模型"。
- LLM 轮次结束时把 token 累加到当前段；reconcile 时**关旧段（写 end_round）+ 开新段（seq+1）**。
- `step_emitter.py:55`、`llm_response_builder.py:29-31` 同步跟进（模型归属=当前段）。
- SSE `usage`/`stats` 事件带当前段模型，前端可展示"本轮用的模型"。

### 8.4 对账点位置（关键设计决策）

- **配置热切换的对账点**：放 `react_loop.py` **每轮 LLM 调用前**（循环顶），被动检查 `get_scope().ai_service.llm_model != agent.llm_client.llm_model` → reconcile。
- **failover 切入**（阶段一）：放 `llm_call.py` 错误分流处，与对账点**解耦**，同用 reconcile 底座。
- **分层原则**：对账点只负责"检测变化"，reconcile 只负责"切换"，后续任何新触发源（定时、人工 API、速率策略）都零改动接入——即扩展性落在"触发源与执行机制解耦"。
