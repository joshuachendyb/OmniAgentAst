## 一、背景与问题

HITL 弹窗顺序问题（问题1）：流水线先出"确认弹窗"，用户确认之后流水线里才出现工具等待图标（齿轮/扳手动画）。用户感知"顺序反了"——期望**先看到等待图标（工具将执行），再出弹窗确认**。

病根（后端协议顺序，非前端 bug）：齿轮（`ToolCallLine` 的 `!hasResult && tools.length > 0`）数据源是 `ActionStep.tools`；而 `ActionStep` 必须等 `safety_gate` 返回（= 用户确认完成后）才 emit。SSE 顺序必经：`thought-start → thought → paused(弹窗) → [用户确认] → resumed → action(齿轮) → observation`。

方案C是北京老陈 2026-09-06 现场纠定的最终方案，覆盖后端+前端全部处理修改方法。

## 二、方案C最终设计总览

三个核心裁定（北京老陈 2026-09-06）：

1. **拒绝不是 error 事件**：用户拒绝改独立 `type="user_rejected"` 单独发（无 `error_type`/`severity`，不占 error 通道、不触发红字）；仅 `blocked`（拦截）/`timeout`（超时）走 error。
2. **action 先发、弹窗后发**：单/多工具统一在安全检查**任一弹窗发出前**先把 `ActionStep` publish（齿轮先行）。
3. **预览/落库分离**：预览事件带内部标记 `_live_only`（仅SSE齿轮先行, agent_runner 路由跳过落库），真实执行集 `_exec_calls` 走 canonical（SSE+落库）。

三层职责：
- 后端 sse 序列：预览 action 齿轮 → paused 弹窗 → user_rejected/error 回执 → canonical action → observation；
- 前端聚合：`deniedSteps` Map（step→拒绝计数）实时聚合三 deny 型（独立拒绝 + blocked + timeout），**整批计数**判定停齿轮；
- DB 落库：仅 canonical 落库，全拒/拦截步不落 action（保 09-04"拦截action不落库"不变式）。

**前端收到两次 action 的分别处理**（小欧 2026-09-06 补充分析）：

1. **第一次（预览 action，tools=all_calls）**：`sseParser.ts:569` action case 按 `step.exec_type` + `rawData.tools` 填充 `step.tools`（含待确认工具），写入 `executionSteps`；此时齿轮先出现——`ToolCallLine` 的 `!hasResult && tools.length>0 && !interrupted && !replay` → 齿轮/扳手动画转起来（暂停等用户确认）。
2. **第二次（canonical action，同 step）**：再次进入 `buildSegments`（`PipelineRenderer.tsx:127-147`）——`segs.findIndex(kind==='tool' && action.step === s.step)` 按 step 找到已在的 action 段，用本次数据**覆盖**旧 action（`action: s`）、**保留**原有 observations；即 canonical 替换预览段，齿轮以真实执行集为准。
3. **后续 observation 到达**：挂到同 step 的 action 段下展示子行，齿轮随 `hasResult=true` 卸载。

关键结论：**界面/渲染层只保留一份**（canonical 覆盖预览，不会出现双 action 块）；`executionSteps` 列表里两条、`buildSegments` 按 step 去重协调为界面一条；deniedSteps（拒绝计数）是与两次 action 独立的事件流，并行聚合互不干扰。

```typescript
const [deniedSteps, setDeniedSteps] = useState<ReadonlyMap<number, number>>(new Map());
const markDenied = useCallback((step: number) => {
  if (typeof step === 'number' && step >= 0) {
    setDeniedSteps((prev) => {
      const next = new Map(prev);
      next.set(step, (next.get(step) ?? 0) + 1);
      return next;
    });
  }

// blocked/timeout 仍走 error 通道, 其错误对象现带 step —— 过滤聚合不打断原红字链路

      if (typeof _e.step === 'number') markDenied(_e.step);
    }
  }

// 独立拒绝事件回调(不占 error 通道, 无红字)
const handleDenied = useCallback((step, _message) => { markDenied(step); }, [markDenied]);
```

**场景分支**：
| 前端事件 | 来源 | deniedSteps 变化 |
|---|---|---|
| user_rejected | 独立事件 → handleDenied | `step` 计数 +1 |
| error blocked | error 事件带 step → sseOnError | `step` 计数 +1；同时红字提示链路不变 |
| error timeout | 同上 | `step` 计数 +1 |
| 新任务开始 | L226 | `setDeniedSteps(new Map())` 清空 |

### 4.4 `frontend/src/features/chat/components/pipeline/PipelineRenderer.tsx` — 整批计数判定停齿轮

**修改点**（L311-325 v1.6 修订）：`interrupted` 由"任一 error 存在"改**整批计数判定**——未执行工具数（denied≥候选工具总数）才停齿轮；数据源从 error 段（error 不入 liveSteps=死代码）换 `deniedSteps` 实时聚合；ToolCallLine 传 `replay`。

> **分母语义（v1.6，北京老陈纠定）**：判定分母用 tool 段保留的 `candidateCount`（= 预览 action 的 `tools` 全量候选数，即后端 `all_calls` 数量，**并行多少就是多少、可高达 10+**），**不得用 `seg.action.tools?.length`**——该字段在 canonical 到达后会被覆盖为**执行集**（只会更小不会保留全量），部分拒场景会误把执行中工具停齿轮（例：10 工具并行、拒 3、7 执行中 → `denied=3 > 执行集长度 7 的旧分母=7? 否 → 3<7 齿轮保持✓`；但若拒 7、3 执行中 → `denied=7 >= 执行集 3` → 误停齿轮✗）；而用 candidateCount=10 判定 → `7<10` 齿轮保持✓）。`candidateCount` 由 buildSegments action 去重时保留预览值（`PipelineRenderer.tsx:127-147` tool 段新增该字段，canonical 覆盖时 `existing.candidateCount ?? s.tools?.length` 保留预览全量）。

代码修改：
```typescript
const toolDeniedCount = deniedSteps?.get(seg.action.step as number) ?? 0;
const allDenied = toolDeniedCount >= (seg.candidateCount ?? seg.action.tools?.length ?? 0);
return (
  <ToolCallLine
    ...
    interrupted={toolObs.length === 0 && allDenied}
    replay={!streaming}
    ...
  />
);
```

**场景分支**（`candidateCount` = 该 step 全量候选工具数 N，可 10+；`deniedCount` = 被拒/拦/超时工具数，逐工具累加）：
| 场景 | interrupted | 齿轮 |
|---|---|---|
| 部分拒 + 部分执行中（拒 3、7 执行中，N=10） | `deniedCount(3) < candidateCount(10)` → false | 齿轮保持（还有工具在跑） |
| 拒 7、3 执行中（N=10） | `deniedCount(7) < candidateCount(10)` → false | 齿轮保持（还有工具在跑，旧分母 execution-set=3 会误判✗） |
| 全拒/全拦/全超时（N=10 全部未执行，无 canonical） | `deniedCount(10) ≥ candidateCount(10)` → true | 停齿轮，灰字 |
| 单工具被拒（N=1） | denied=1 ≥ candidateCount=1 → true | 停齿轮，灰字 |
| 有 observation | `toolObs.length>0` → false | 正常展示结果（齿轮已随 obs 卸载） |
| 回放（streaming=false） | — | replay=true 免齿轮 |

```

   候选数=1 → denied 1>=1 → interrupted=true → 停齿轮灰字

② 多工具部分被拒+部分执行（候选数 N 即并行工具总数，可 10+）：
   预览 tools=[N个]（全量，not 执行集）→ 拒k个 → denied[step]=k
   候选数=N → denied k<N → interrupted=false → 齿轮保持(还有工具在跑)
   —— k 无论多少，只要还有 m=N-k>0 个在执行中，齿轮不误停
   —— 反例（旧分母 execution-set 才犯）：拒7留在3，denied=7>=执行集3 → 误灰字✗；
      candidateCount 分母=10 → 7<10 齿轮保持✓

③ 全部工具执行成功：预览 tools=[N] → 无 denied → interrupted=false
   → 齿轮转 → observation 到达 hasResult=true → 卸载动画显示结果

④ 回放/历史（streaming=false）：replay=true → 齿轮动画整体不渲染
   （历史数据展示结果即可，无需"正在转"动画）
```

**要点**：`deniedSteps`（实时聚合）与 `executionSteps`（事件流）完全独立，靠 `action.step` 对齐——这也是"整批计数判定"数据源从 error 段换成 deniedSteps 后可用的原因（error 事件不入 liveSteps，原计数恒 0 死代码）。

### 4.9 流程合理性分析（资深评审视角）— 小欧 2026-09-06

**结论：当前流程合理，是既有架构约束下的较优解；同时如实记录 2 个轻微观察点（不构成阻塞），供北京老陈知悉。**

#### 一、合理性论证（为什么这样设计是对的）

| 维度 | 论证 |
|---|---|
| **核心冲突解决** | "齿轮先于弹窗"需要 action 事件提前于确认。后端预览双发（tools=all_calls）复用既有 `ActionStep` 框架，前端零新增 step 类型、零新增存储结构——**改动面最小**（不是新增的 step 类型或改协议） |
| **SRP 单一职责** | 四层各司其职：sseParser 只做解析分派 / useChatStreaming 只做聚合计数 / PipelineRenderer 只做派生判定 / ToolCallLine 只做渲染。无一层混入他层职责 |
| **计数判定准确性** | 整批计数（denied≥候选工具总数 candidateCount）比"任一 error"更精确——避免了"部分拒+部分执行中"误停齿轮的缝隙（分母用预览全量 N，非 canonical 覆盖后的执行集，N 可 10+）；观察点靠"有 obs 即不中断"兜底，语义完整 |
| **两边数据独立对齐** | `deniedSteps`（临时聚合信号）与 `executionSteps`（事件流）互不污染，仅靠 `action.step` 对齐——分工干净，任何一边改动不影响另一边 |
| **KISS-DIRECT** | 前端无需"每工具状态机"，只需要"该 step 被拒计数"一个标量；拒绝/拦截/超时三路统一进同一计数器，前端不感知原因差异（后端已分流），无多余抽象 |
| **回放免齿轮** | `replay=!streaming` 一个字面量，比"回放时初始化空齿轮集合"再多一套状态简洁得多（北京老陈定案） |

#### 二、替代方案对比（为什么不是"更好的其他方案"）

| 候选 | 放弃原因 |
|---|---|
| 后端新增独立"齿轮占位 step"类型 | 改动面大：新增 step 类型需进回放/存储/既有 8.4.x 消费链，比复用 ActionStep 多一个协议面 |
| 后端拒绝时只靠 paused→resumed 推理 | paused→resumed 只能表达挂起后继续，拒绝后无 resumed，无独立信号不可靠 |
| 前端给每个工具建状态机 | 过度设计（YAGNI）：当前整批标量足够，状态机引入退出/重连/回放三态复杂度，收益低 |

#### 三、如实观察点（v1.4 起已根治，读历史留档）

> **【小欧 2026-09-06 14:17 更新】** 以下两个观察点经北京老陈批准"方案2（后端标记）"实施根治，标志以最优雅形态落地为 **`preview=True` 预览标记**：后端预览 action 增发该字段（sse_formatter 剥离内部 `_live_only` 但保留 preview 下发，前端可见）；前端 sseParser 解析、useSSE 刷新恢复时剔除 `type=action && preview=true` 行。拦截/拒绝的 action 本就不落库，恢复后不再出现"无灰字工具行"与"双条 action"，**刷新恢复与 DB 回放语义完全一致**。涉及文件：`handle_action.py`（+preview=True）+ `types/execution.ts`（+preview 字段）+ `sseParser.ts`（+解析）+ `useSSE.ts`（+恢复过滤）。以下原文保留历史记录。

1. **回放/断线重连后"被拒工具"显示较简**：`user_rejected` 仅SSE不落库（北京老陈裁定），回放时 deniedSteps 为空、interrupted=false → 被拒工具行只显示工具名、无灰字说明（实时中才有灰字）。这与"拒绝过程属实时交互、历史确认结果"语义相符，且重连续传从 DB 恢复 canonical（tools=真实执行集），被拒工具本就不在 canonical 中、不会出现空转齿轮——故仅为显示层简化，非缺陷。
2. **sessionStorage 或存双条 action**：预览与 canonical 两次 `setExecutionSteps` 都会触发 `saveStepsToStorage`，DB/存储可能冗余同 step 两条 action 记录；渲染层 `buildSegments` 按 step 去重已兜底，不产生 UI 双实例。属轻微数据冗余，量级小，可选后续收口（例如 canonical 到达时跳过预览的持久化）。

#### 四、观察点根治方案（v1.4 新增，北京老陈批准"方案2 后端标记"）

**问题本质**：拦截/拒绝的 action 本就不落库（09-04 不变式），但前端 `saveStepsToStorage` 把仅SSE 齿轮先行的预览 action（tools=all_calls）也写进了 sessionStorage——刷新恢复时 executionSteps 恢复出"含被拒工具"的预览行，而 deniedSteps 是内存态已丢 → 出现"无灰字工具行"（观察点1）；同时预览+canonical 双条写入 → 存储冗余（观察点2）。

**根治标志（最优雅形态 = 后端 `preview=True` 预览标记，非逐工具 rejected 字段）**：

| 环节 | 改动 | 说明 |
|---|---|---|
| 后端 `handle_action.py` | 预览 ActionStep dict 增 `preview=True` | 与内部路由 `_live_only` 并存；`sse_formatter` 剥离 `_live_only`（内部不发给前端）但**保留 preview 下发**（前端可见契约字段）；对落库/路由零影响（落库只认 `_live_only` 判定） |
| 前端 `types/execution.ts` | `ExecutionStep` 增 `preview?: boolean` | action 预览行类型字段 |
| 前端 `sseParser.ts` | action case 解析 `step.preview = rawData.preview === true` | 实时渲染仍保留预览行（齿轮动画数据源） |
| 前端 `useSSE.ts` | sessionStorage 恢复时 filter 剔除 `type=action && preview=true` 行 | 恢复不再出现被拒工具预览行 |

**效果**：
- ①刷新/断线重连恢复：预览行被剔除 → 被拒工具行不出现（拦截 action 不落库 → DB 回放本来也没有）→ **刷新恢复与 DB 回放语义完全一致**；
- ②sessionStorage 不再有"双条 action"残留展示 → 观察点2收口；
- ③实时流式预览行仍进 executionSteps，齿轮先行动画不受影响；canonical 到达后 buildSegments 按 step 覆盖照常去重。

**是否改 DB？不改。** 拦截/拒绝 action 继续不落库（北京老陈裁定不可回退）；只在前端持久化(sessionStorage)边界收口，与 DB 回放对齐。

## 五、SSE 完整时序（最终形态）

```
handle_action 早发预览(齿轮先行):
  thought-start → thought
  action(tools=all_calls, _live_only=True, preview=True)  ← 齿轮此时出现(仅SSE, 不落库; preview 供前端刷新恢复剔除)
check_safety_and_confirm:
  pause/resume 事件(paused 弹窗到达——用户确认)
  结果回执:
    ├─ 拒绝           → user_rejected(step, content)      ← 独立事件, 不占error通道
    ├─ 拦截(危险型)   → error(error_type=blocked, step)
    ├─ 超时           → error(error_type=timeout, step)
    └─ 确认/直通      → 无回执, 继续
  sandbox needs_ruling 拒绝 → user_rejected(step)         ← 同构
  sandbox 危险拦截      → error(error_type=blocked, step)
canonical(落库):
  action(tools=_exec_calls 真实执行集, 无标记)           ← 仅正常执行才发
  observation(results)
```

前端视角：
- 流式期间收到 `user_rejected` → `onDenied` → `deniedSteps` 计数；
- 收到 `error(blocked/timeout, step)` → 红字提示（原链路）+ 按 step 计数；
- `deniedCount >= 候选工具总数(candidateCount，预览全量 N，可 10+)` 且无 obs → `interrupted=true` → 齿轮停转改灰字；
- 部分拒工具仍在跑 → 齿轮保持；obs 到达 → 齿轮卸载。
