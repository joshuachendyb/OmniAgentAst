## 七、轮 6 — 关联会审（数据流与 DB 一致性）

### 7.1 注入消息全链路推演（单条注入）

| 阶段 | 状态 |
|------|------|
| API 入口落库 | `chat_user_message` 新行，`task_id=NULL` |
| `inject_message_to_task` | 投 `(content, uid)` 元组，uid>0 校验 ✅ |
| `_bind_task_id` | 执行期 `UPDATE ... WHERE id=? AND task_id IS NULL` ✅ 补空窗 |
| 终态回填 | `agent_runner` 用 `message_builder.current_user_msg_id`（**注入 uid**）→ `update_user_message_final` |

### 7.2 关键推论：首条用户消息 `u1` 永远拿不到 `response`

`add_user_message(content, user_message_id=uid)` 演进 `_current_user_msg_id`（message_builder.py:153），故终态只回填**锚所在那一行**，`u1.response` 恒 NULL。

**判定：属设计预期，非缺陷** —— [76] 决策 2「carrier 合并渲染」正是为此兜底：多个 row 共享同一 `ai_message_id`，只在**首个有内容行**渲染 assistant（`message_service.py:118-131`）。此逻辑经复核正确：`_first_row` 兜底 + `_carrier` 优先有内容行，全空回落首见行保 steps。

### 7.3 ❌ D-01【高】`_merge_orphan_user_pairs` 合并判据错误

**位置**：`backend/app/services/chat/message_service.py:71-97`

**当前判据**：`ai_content 为空` 且 `pair_task_id` 非空 且 与前一行同任务 → 并入同一 run。

**问题**：该判据**无法区分"任务登记首条 u1"与"注入消息"**。二者在 DB 里形态完全相同（`response` 空 + 有 `pair_task_id`）。

**两条可复现错误路径**：

| 锚取值 | rows 形态 | 渲染结果 | 判定 |
|--------|----------|----------|------|
| 第一条（现状 `react_step.py:227`） | `[u1(空), u2(有内容), u3(空)]` | u2 的内容打断 run → 3 个气泡 | ❌ 内存侧合并为 1 个 → **刷新前后条数跳变，5.5 目标未达成** |
| 最后一条（[30] B-5 规定） | `[u1(空), u2(空), u3(有内容)]` | u1、u2 同任务同为空 → **合并** | ❌ **首条用户输入被并进注入气泡 = 显示错数据** |

**即：D-02 与 D-01 耦合。单修 D-02 会把"跳变"升级为"错数据"。**

**正确判据（DRY 复用既有口径）**：排除 `chat_tasks.user_message_id`（任务登记首条），只合并**注入行**。该 uid 在 `list_session_tasks` 已用（`_reg_uid`），`fetch` 侧补 `ct.user_message_id AS pair_first_uid` 即可复用同一判据。

## 十二、结论

1. **D-01 是本次唯一"高"级真缺陷**，且与 D-02 耦合，必须同批修：先给 `_merge_orphan_user_pairs` 补"排除任务登记首条"判据（复用 `chat_tasks.user_message_id`，与 `merged_inputs` 同口径），再定锚取值。
2. **D-05 意味着当前 E2E 注入用例必红**，不能声称 6.15 已落地。
3. **D-03 建议删除**而非修补：`task_id` 由 `uuid4().hex` 生成，重复分支不可达（YAGNI），且其"返回 None"使编排误判为注册成功 → 同 task_id 双跑，比修复前的"覆盖丢消息"更坏。
4. 其余 D-04 ~ D-12 为一致性/可维护性/文档同步类，不影响运行正确性，但违反 AGENTS.md 纪律，须闭环。
