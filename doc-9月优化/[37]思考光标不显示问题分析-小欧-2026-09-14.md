## 1 问题描述

为了诊断"打印机光标为什么不该消失时消失"，在 `PipelineRenderer` 与 `sseParser` 加了 CURSOR/chunk 打点日志，运行后观察到两个异常现象：

**现象一（核心，光标不该消失时消失）**：实时流式输出正文阶段，UI 上的打印机光标 `▍` 大部分时间消失。流式明明还在持续（SSE 的 chunk 源源不断到达），但光标只"闪一下"就没了，其余时间完全不显示。用户肉眼看到的是：大量 `CURSOR F` 日志在打印，但 UI 上光标却消失着。

**现象二（日志本身的噪声）**：
- `CURSOR F` 每秒打印十几条，且同一时刻重复 2~4 次；
- `chunk` 日志（`F =xxx`）一切正常，每个 chunk 恰好一条、无重复。

**期望行为**：流式输出末段期间（`streaming=true` 且该段为最后一段），打印机光标应持续闪烁在已输出文字的末尾，表示"还在输出中"。仅当流式结束、或该段不再是末段、或历史回放时，光标才消失。

## 2 问题分析

### 2.1 相关代码与数据链路

```
SSE chunk 帧到达过程:
  sseParser.ts:439  打 chunk 日志 (chunkContent 独立片段) —— 数据到达处, 无渲染耦合
  sseParser.ts:441  setCurrentResponse(buffer)  → useSSE state 更新 → 触发渲染
  sseParser.ts:464  pushAndFlush → rAF flushPendingSteps → useSSE.ts:477 setExecutionSteps(newSteps)
  → RightViewer liveSteps → <PipelineRenderer streaming={isCurrentLive}>
    PipelineRenderer.tsx:340  if (isLive) console.log('CURSOR F')   —— 渲染函数体内打点
    → <TextStream typing={isLive} cursor={isLive}>
      TextStream.tsx:68  {cursor && typing && shown < clean.length && <span>▍</span>}   —— 光标真实显示处
```

关键判定（`PipelineRenderer.tsx`）：
- thinking 光标：`const cursor = streaming && i === lastThink && i === segs.length - 1;`
- text 光标：`const isLive = streaming && i === lastText && i === segs.length - 1;`

即：光标（CURSOR T/F）的**打印条件** = `streaming=true` 且该段为最后一段。

### 2.2 病根（根本原因）

**打印机光标的"显示条件"绑死在了"打字机还没敲完"（`shown < clean.length`）上，而不是"流式正在进行"（`streaming`）上。**

`TextStream.tsx:68` 光标渲染需要三个条件**同时满足**：

```
cursor && typing && shown < clean.length
```

- `cursor`、`typing`：来自 `isLive`（末段 + 流式中）。流式期间**恒为 true**，没有问题。
- `shown < clean.length`（打字机进度门槛）：这才是病根。它的语义是 **"打字机还没敲完当前累积的全部文字"**，一旦打字机追平（`shown >= clean.length`），光标立刻消失——**即使流式还在继续、后面还有 chunk 在来**。

而 `ThinkingStream`（思考光标）的显示条件是 `{cursor && <span>▍</span>}`，**没有** `shown < clean.length` 这一门槛，所以思考光标从不出现该问题。两处不一致，即为病根所在。

### 2.3 病因（为什么表现为"光标大部分时间消失"）

打字机速度 vs chunk 到达速度严重不匹配：

| 项 | 数值 | 来源 |
|----|------|------|
| chunk 到达间隔 | 约 90~190ms | 日志实测 |
| 单次 chunk 增量 | 约 8~15 字符 | 日志实测 |
| 打字机步长 | `step = Math.max(1, Math.ceil(clean.length / 240))` | TextStream.tsx:43 |
| 打字机 tick | 每 16ms 推进 `step` 个字符 | TextStream.tsx:57 |
| 追平一次 chunk 增量耗时 | 增量 / (step / 16ms)= 增量×16/step ≈ **14~32ms** | 推算 |

以文本长度约 2000+ 字符为例：`step ≈ ceil(2000/240) = 9`，每 16ms 追 9 个字符。一次 chunk 增量（10 字左右）**1~2 个 tick（16~32ms）就打平**，随即 `clearInterval` 停表、`shown >= clean.length`、光标熄灭。

而下一个 chunk 要等 90~190ms 才到。于是：

```
光标亮 ~16ms → 灭 ~100ms → 下一 chunk 到再亮 16ms → 再灭 100ms ...
```

光标实际亮的窗口只占流式时长的 **8%~17%**，**其余绝大多数时间熄灭**。用户看到的就是"大量 CURSOR F 日志在打，光标却消失着"。

**一句话复述**：光标不是"流式进行中"的信号，而是"打字机还没敲完当前文字"的信号。流式还在继续，光标却因打字机阶段性追平而熄灭——这就是"不该消失时消失"。

### 2.4 日志现象二的分析（重复打印 + 与 UI 不同步）

**为什么会重复 2~4 次：**
1. `console.log` 被写在 `PipelineRenderer` **渲染函数体内的 map 循环里**（:340/:327）。React 铁律：render 必须纯函数、无副作用，这里用 console.log 是副作用，**每次渲染都会执行一次**。
2. 叠加 `React.StrictMode`（main.tsx:14）：开发模式渲染函数执行 2 次 → 一次渲染打 2 次。
3. 每个 chunk 有两次 setState（`setCurrentResponse` + `setExecutionSteps`）分别触发渲染批次，叠加后同一时刻出现 2~4 条同一内容的 log。

**为什么会"打 log 时 UI 光标已消失"：**
- CURSOR F 的打点条件 = `isLive`（streaming + 末段）。
- UI 光标显示条件 = `isLive` **且** `shown < clean.length`（打字机未追平）。
- 两者不等价：流式期间 `isLive` 恒 true，但光标多半已因打字机追平而熄灭 → **log 打点时刻与 UI 光标真实状态不同步**，log 是在报告"打字机应该工作"，而非"光标实际亮着"。

**对照组（chunk 日志为何正常）**：`chunk` 日志（sseParser.ts:439）打在**数据到达处**（每帧一次，无渲染依赖），所以每个 chunk 恰好一条、与 UI 无耦合。这个对照证明：打点应放在数据/真实状态变化的"源头"，而不是渲染循环里。

## 3 解决方法的详细说明

分为两步：核心 UI 修复 + 日志校准修复。

### 3.1 核心修复：光标与"流式进行中"绑定（TextStream.tsx:68）

**两种可选光标行为（工程取舍）**：

| 方案 | 光标行为 | 效果 |
|------|---------|------|
| **方案A：持续呼吸闪烁等待**（选定） | 打字机敲完当前已有文字后，光标**不灭**，继续在文字末尾呼吸闪烁——像打印机开着在等下一批纸；下一批 chunk 到达，文字变长，光标继续跟随末尾；直到流式结束 / 该段不再是末段才消失 | **全程可见**，用户始终知道"还在输出中" |
| **方案B：打字机敲完即走**（现状 = BUG） | 打字机敲完当前已有文字的一瞬间，光标**熄灭**；等 90~190ms 后下一批 chunk 到达、文字变长，光标才重新亮；几帧后敲完又灭 | 光标"一闪就灭"，**大部分时间看不见**（即现象一） |

**选方案A的理由**：光标语义应为"流式输出进行中"，而非"打字机进度"。方案B 把光标绑在打字机步进上，打字机追平即光标灭——这正是现象一的病根；方案A 光标只跟 `streaming` 走，流式期间恒亮，符合"打印机开着等待"的直觉。

**改动**：删除光标条件里的 `shown < clean.length` 门槛：

```tsx
// 旧（病根）：光标 = 打字机还没敲完当前文字
{cursor && typing && shown < clean.length && <span>▍</span>}

// 新（修复）：光标 = 末段 + 流式进行中
{cursor && typing && <span>▍</span>}
```

**语义变化**（这正是关键在于：修复前 vs 修复后的差别）：

| | 修复前（现状，有 bug） | 修复后 |
|--|------------------------|--------|
| 光标含义 | "打字机还没敲完当前累积文字" | "流式输出进行中" |
| 打字机追平当前文字后 | 光标立即熄灭，等下批 chunk 才重新亮 | 光标**持续闪烁**在已输出文字末尾，等下一批 chunk |
| 流式结束（streaming=false）| 光标消失 | 光标消失（`cursor`/`typing` 变 false） |
| 非末段 / 历史回放 | 光标消失 | 光标消失（`cursor` 变 false） |

**配套说明**：打字机的"追平即 `clearInterval` 停表"逻辑**保留不变**（这是 2026-09-02 防空转修复，防 CPU 空转，正确），只是**停表不再连坐光标**。打字机敲完后，shown 停在 `clean.length`，文本全量显示，光标停在末尾呼吸闪烁；下一批 chunk 到达，text 变长、`clean` 变化、effect 依赖刷新、打字机自动续打——光标始终跟随在末尾。

**`ThinkingStream` 光标不需改动**：它的条件 `{cursor && <span>▍</span>}` 已是"流式中"语义，本就正确。

### 3.2 日志校准：打点移到光标真实渲染处（翻转检测）

**改动一**：**删除** `PipelineRenderer.tsx:327` 与 `:340` 两处**渲染函数体内**的 `console.log`（或配套删除 ThinkingStream 侧的新打点逻辑中的错误点）。理由：
1. render 内打点是副作用，违反 React 纯函数铁律，StrictMode 双渲染必然产生 2~4 倍虚假重复（现象二根因）。
2. 打点条件（`isLive`）与 UI 光标真实条件（还需 `shown < clean.length`）不同步，日志不能反映真实光标状态。

**改动二**：在 `TextStream` / `ThinkingStream` **内部**、**光标真实渲染的位置**做**翻转检测**打点（false→true 才打一次）。

**为什么必须删除而非"改写条件留存"（组件边界根源）**：`shown`（打字机进度）是 `TextStream` **内部 useState**（TextStream.tsx:34），父组件 `PipelineRenderer` **无感知、拿不到**。所以 `isLive` 只能表达"末段+流式中"，**表达不了光标真实亮灭**——CURSOR 打点若留在 PipelineRenderer，无论怎么改条件都不可能打准。因此这两个 log **只能删除**，正确打点位置**只能下放**到拥有 `shown` 的 TextStream / ThinkingStream 内部。这回答了"pipe 的两个 log 为什么要删除、正确 log 在什么地方打"。小欧-2026-09-14

**为什么放 TextStream/ThinkingStream 内部（好处）**：
1. **条件与 UI 100% 同一表达式** —— 打点条件 = 光标实际渲染条件，日志打出的那一刻，光标必然真实亮起，彻底消除"打 log 时光标已消失"的不同步。
2. **翻转检测天然去重** —— 用 `prevRef` 记录上一状态，仅 false→true 翻转时打印一次。StrictMode 双渲染下 effect 只在翻转时执行，不再有 2~4 倍重复。
3. **render 纯函数合规** —— 打点移出 render 循环，放进 useEffect，符合 React 规范。

实现示意（TextStream）：

```tsx
const showing = cursor && typing && shown < clean.length;   // 光标真实显示条件（修复后为 cursor && typing）
const prevRef = useRef(false);
useEffect(() => {
  if (showing && !prevRef.current) {
    console.log(`${formatDebugTime()} CURSOR F`);
  }
  prevRef.current = showing;
}, [showing]);
```

ThinkingStream 同法（条件为 `cursor` prop）。

### 3.3 预期效果

- **UI**：流式输出正文期间打印机光标**持续呼吸闪烁**，只在流式结束/非末段/回放时消失——"不该消失时消失"根治。
- **日志**：每个 chunk 驱动光标重新亮起时恰好打一条 `[HH:MM:SS.mmm] CURSOR F`；熄灭时绝不打；无重复、无虚假。CURSOR 日志与 chunk 日志（`F =...`）一一对应，成为指针光标与内容到达的真实时间对照表。
- **性能**：光标从"每帧断断续续亮/灭"变为"恒亮"，打字机 stop 逻辑保留，无新增 CPU 空转。
