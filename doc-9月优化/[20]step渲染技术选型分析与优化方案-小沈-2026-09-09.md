## 一、概要

当前 step 渲染用**"全量数组 + 每次重算 + 命令式 setInterval + 同步持久化"**的命令式思维做流式渲染，与 SSE 增量数据的本质矛盾，存在 **5 处技术债**叠加，是"不同任务反复冻死"的底层原因。

本文给出**三层正交优化方案**（P0/P1/P2），并据"步骤可能几十上百"的长远需求，定**分两阶段实施**：先 P0+P1（低风险根治），再 P2（架构升级，性能恒定不随步数增长）。

| 层 | 优化 | 解决问题 | 改动量 | 风险 |
|----|------|---------|--------|------|
| P0 | saveStepsToStorage 防抖 | 病根A：同步阻塞主线程 | 2 文件 ~20 行 | 低 |
| P1 | obs Map + 打字机 rAF + useMemo | O(N²)→O(N)、消除高频 setState | 3 文件 ~60 行 | 低 |
| P2 | react-virtuoso + useTransition | O(N)→O(可视区)、性能恒定 | 3-4 文件 ~120 行 | 中 |

**组合结论**：P0+P1+P2 **正交不冲突、可叠加**，但建议**分两阶段**上（KISS-DIRECT，一次引入一个变量，出问题好定位）。步骤上百步是常态 → P2 必须上。

## 二、当前技术选型问题（5 处技术债）

### 2.1 全量重渲染，无虚拟化

| 项 | 代码位置 | 问题 |
|----|---------|------|
| 全量 map | PipelineRenderer.tsx:304 `segs.map((seg,i)=>{...})` | 全量渲染所有段，无虚拟列表 |
| 无虚拟化库 | package.json dependencies | 无 react-window / react-virtuoso / @tanstack/react-virtual |

**后果**：steps 累积到几十步，每次 `setExecutionSteps` 触发全量重建 + 全量 diff + 全量渲染，随步数线性增长。

### 2.2 buildSegments 每次全量重建

| 项 | 代码位置 | 问题 |
|----|---------|------|
| 无缓存 | PipelineRenderer.tsx:260 `const segs = buildSegments(steps)` | 每次渲染都遍历全量 steps 重建段数组 |

**后果**：O(N) 重建，即使段未变也重算。`useMemo` 因 `[...prev,step]` 每次新引用而失效。

### 2.3 tool 段 obs 查找 O(N²)

| 项 | 代码位置 | 问题 |
|----|---------|------|
| filter 遍历 | PipelineRenderer.tsx:394-399 每个 tool 段 `segs.filter(s => s.kind==='obs' && s.step.step===seg.action.step)` | N 个 tool 段 × N 次 filter = O(N²) |

**后果**：steps 多时 obs 查找成为性能瓶颈。

### 2.4 打字机 setInterval 16ms 高频 setState

| 项 | 代码位置 | 问题 |
|----|---------|------|
| setInterval 16ms | TextStream.tsx:44-57 `window.setInterval(()=>{ setShown(...) }, 16)` | 每 16ms 一次 setState，命令式定时器 |

**后果**：多个 TextStream 实例同时打字时，多个 setInterval 叠加，高频重渲染。打字机段滚出可视区后 setInterval 仍空转（TS-01 已部分修，但根本问题是 setInterval 本身）。

### 2.5 同步持久化（病根A，[19]文档详析）

| 项 | 代码位置 | 问题 |
|----|---------|------|
| 同步写 Storage | useSSE.ts:486 `sessionStorage.setItem(storageKey, JSON.stringify(steps))` | JSON.stringify 全量 + sessionStorage.setItem 同步阻塞 |
| setTimeout(0) 排队 | sseParser.ts:381/685/833 三处 `setTimeout(()=>{ saveStepsToStorage(newSteps) }, 0)` | N 个事件 → N 个宏任务依次阻塞，O(N²) 增长 |

**后果**：主线程被阻塞，React 渲染推迟，UI 冻结 20 秒。详见 [19] 文档第六章。

## 三、三层优化方案

### 3.1 P0：saveStepsToStorage 防抖（根治病根A）

**层**：持久化层

**useSSE.ts 改造**：
```ts
const saveTimerRef = useRef<number | null>(null);
const saveStepsToStorage = useCallback((steps: ExecutionStep[]) => {
  if (steps.length === 0 || !config.sessionId) return;
  if (saveTimerRef.current !== null) clearTimeout(saveTimerRef.current);
  saveTimerRef.current = window.setTimeout(() => {
    const storageKey = `${SSE_STORAGE_KEY}_${config.sessionId}`;
    try { sessionStorage.setItem(storageKey, JSON.stringify(steps)); }
    catch (e) { console.warn('[SSE] 保存失败:', e); }
    saveTimerRef.current = null;
  }, 300);
}, [config.sessionId]);
```

**sseParser.ts 三处改造**：去掉外层 setTimeout(0)，直接调 `saveStepsToStorage?.(newSteps)`（防抖内部处理）。

**效果**：N 次写 → 1 次防抖写，阻塞从 O(N²) 降到 O(1)。

**改动**：2 文件 ~20 行。

### 3.2 P1：obs Map + 打字机 rAF + useMemo（数据处理 + 渲染控件）

**层**：数据处理层 + 渲染控件层

#### P1a：tool 段 obs 查找改预计算 Map（O(N²)→O(N)）

**PipelineRenderer.tsx 改造**：buildSegments 内一次构建 `Map<step, ExecutionStep[]>`，渲染时 O(1) 查。
```ts
// buildSegments 内预计算
const obsByStep = new Map<number, ExecutionStep[]>();
for (const s of steps) {
  if (s.type === 'observation') {
    const arr = obsByStep.get(s.step as number) ?? [];
    arr.push(s);
    obsByStep.set(s.step as number, arr);
  }
}
// 渲染时
const toolObs = obsByStep.get(seg.action.step as number) ?? [];
```
**效果**：O(N²)→O(N)。

#### P1b：打字机改 requestAnimationFrame（消除 16ms 高频 setState）

**TextStream.tsx 改造**：`setInterval(16ms)` → `requestAnimationFrame` 帧调度。
```ts
useEffect(() => {
  if (!typing) { setShown(clean.length); return; }
  const step = Math.max(1, Math.ceil(clean.length / 240));
  let rafId: number;
  const tick = () => {
    setShown((prev) => {
      if (prev >= clean.length) return prev;
      const next = prev + step;
      return next >= clean.length ? clean.length : next;
    });
    rafId = requestAnimationFrame(tick);
  };
  rafId = requestAnimationFrame(tick);
  return () => cancelAnimationFrame(rafId);
}, [clean, typing]);
```
**效果**：rAF 同步帧调度（~16ms 一帧但与显示器刷新同步），不阻塞主线程，浏览器自动暂停非可视区帧。或进一步用 CSS `animation` + `steps()` 函数，GPU 加速零 setState。

#### P1c：buildSegments useMemo 缓存（避免每次全量重建）

**PipelineRenderer.tsx 改造**：用 `steps.length + 末步指纹` 做依赖（非 steps 引用）。
```ts
const lastStep = steps[steps.length - 1];
const fingerprint = `${steps.length}-${lastStep?.step}-${lastStep?.type}`;
const segs = useMemo(() => buildSegments(steps), [fingerprint]);
```
**效果**：同指纹不重算。注意：打字机 chunk 频繁到达会变指纹，但 chunk 合并到末段 text，指纹变化频率远低于每次渲染。

**改动**：3 文件 ~60 行。

### 3.3 P2：react-virtuoso + useTransition（渲染容器 + 调度）

**层**：渲染容器层 + 调度层

#### P2a：react-virtuoso 虚拟列表

**PipelineRenderer.tsx 改造**：
```tsx
import { Virtuoso } from 'react-virtuoso';

<Virtuoso
  data={segs}
  followOutput={'smooth' as any}  // 自动滚底（替代 RightViewer ResizeObserver 逻辑）
  atBottomStateChange={(atBottom) => { /* 用户上翻/回底状态 */ }}
  itemContent={(i, seg) => { /* 原 segs.map 内的渲染分支 */ }}
/>
```

**RightViewer.tsx 改造**：滚底逻辑迁移到 Virtuoso API：
- 删除 `scrollToBottomNow` / `ResizeObserver` / `scroll` 事件监听 / `visibilitychange` 兜底（Virtuoso 内置）
- `userScrolledUpRef` 改用 `atBottomStateChange` 回调维护
- `followOutput` 接管自动滚底

**TextStream.tsx 改造**：key 稳定化（当前 `key={text-${i}-${seg.text.slice(0,16)}}`，打字机 text 变化 key 变化，Virtuoso 需稳定 key）→ 改用 `key={text-${seg.step ?? i}}`。

**难点与应对**：

| 难点 | 说明 | 应对 |
|------|------|------|
| 动态高度 | 段高度不固定（thinking 几行、tool 展开多行、text 打字机动态变化） | Virtuoso 支持 `autoMeasure`；打字机段高度变化触发重测量，但 rAF 帧调度下变化平滑 |
| 打字机段滚出可视区 | setInterval/rAF 仍跑浪费 CPU | rAF 浏览器自动暂停非可视区帧（P1b rAF 优势）；或 `itemsRendered` 回调暂停非可视段打字 |
| key 稳定性 | 当前 key 含 text.slice(0,16)，打字机变化 key 变 | 改用 step 序号 + 段类型做 key |
| 滚底逻辑迁移 | 当前一套成熟逻辑（ResizeObserver+scroll+visibilitychange） | 迁移到 followOutput + atBottomStateChange，逻辑更简（Virtuoso 内置） |

#### P2b：React 18 useTransition

**useSSE.ts 或 RightViewer.tsx 改造**（二选一）：
```ts
// 方案1: setExecutionSteps 包 startTransition
const [startTransition] = useTransition();
setExecutionSteps((prev) => {
  const newSteps = [...prev, step];
  startTransition(() => { /* 无需额外，标记渲染低优先级 */ });
  return newSteps;
});

// 方案2: RightViewer 用 useDeferredValue
const deferredSteps = useDeferredValue(displaySteps);
// <PipelineRenderer steps={deferredSteps} ... />
```
**效果**：steps 渲染标低优先级，齿轮动画（高优先级）不被饿死。

**改动**：3-4 文件 ~120 行。新增依赖 `react-virtuoso`。

## 五、组合策略与实施顺序

### 5.1 三层正交性

| | P0 | P1 | P2 |
|---|---|---|---|
| 层 | 持久化 | 数据处理 + 控件 | 容器 + 调度 |
| 冲突 | 无 | 无 | 无 |

P0/P1/P2 解决不同层面问题，**正交不冲突、可叠加**。

### 5.2 分两阶段实施（推荐）

**阶段1（立即，根治当前问题）**：P0 + P1
- 改动：4 文件 ~80 行，低风险
- 效果：消除病根A，O(N²)→O(N)，消除高频 setState
- 验证：复现任务1，确认冻死消失

**阶段2（阶段1稳定后，架构升级）**：P2
- 改动：3-4 文件 ~120 行，中风险
- 效果：O(N)→O(可视区)，性能恒定不随步数增长
- 验证：步骤 50+ 场景流畅，动态高度 + 打字机兼容性

### 5.3 为什么分阶段不一起上

1. **KISS-DIRECT 原则**：一次引入一个变量，验证稳定再上下一个，出问题好定位
2. **P0+P1 低风险**：改动小、不引入新依赖、立即解决冻死
3. **P2 需验证**：动态高度 + 打字机 + 虚拟列表兼容性，在 P0+P1 稳定后上，避免问题交叉
4. **YAGNI 校验**：若 P0+P1 上完后几十步场景已流畅，P2 可暂缓；但上百步是常态则 P2 必须上

### 5.4 一次到位（可选，用户定）

若用户希望一次到位避免二次改动，P0+P1+P2 可一起上（正交不冲突）。但风险叠加，出问题难定位是哪层引入。**不推荐**，除非有充分测试覆盖。

## 六、长远扩展分析（步骤几十上百）

### 6.1 各方案对步数增长的性能

| 步数 | P0+P1 | P0+P1+P2 |
|------|-------|----------|
| 10 步 | 流畅 | 流畅 |
| 50 步 | 流畅（O(N) diff 可扛） | 流畅（恒定） |
| 100 步 | 偶卡（O(N) diff + 全量渲染） | 流畅（恒定） |
| 200+ 步 | 卡（全量渲染瓶颈） | 流畅（恒定） |

### 6.2 结论

- 步骤**几十步**：P0+P1 够用，P2 可暂缓（YAGNI）
- 步骤**上百步常态**：**P2 必须上**，否则全量渲染 O(N) diff + 全量 map 成为瓶颈
- P1 的 obs Map 把 O(N²)→O(N)，P2 虚拟列表把 O(N)→O(可视区)，**叠加后性能恒定不随步数增长**

### 6.3 P2 的长远价值

react-virtuoso 不只解决当前冻死，还为以下场景兜底：
- 超长任务（几百步）：只渲染可视区，内存/CPU 恒定
- 历史回访长任务：无需分页，虚拟列表自动处理
- 多任务切换：非可视任务不渲染，切换快
