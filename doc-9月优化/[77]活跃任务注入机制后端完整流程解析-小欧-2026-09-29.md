## 一、整体时序：一次注入要经过**两条 HTTP 请求**

关键前提：注入消息**不是**在 SSE 流里创建的，而是**先落库拿到 uid，再开流**。理解整条链路的前提是先接受这一点。

```
① POST /api/v1/sessions/{sid}/messages   ← 前端先把消息存了
      └─ save_message() → insert_user_message() → chat_user_message 新行(uid 自增)
      └─ _track_user_message(sid, uid)   ← 内存 track 记下 uid

② POST /api/v1/chat/stream (SSE)         ← 再开流
      └─ chat_stream_orchestrator()
      └─ _user_msg_id = get_user_message_id(sid)   ← 从 track 读回 ①的 uid
             ↓ track 丢失时 DB 兜底 get_last_user_message_id()
      └─ 判定同会话有无活跃任务 → 有则注入，无则正常新建
```

| 环节 | 位置 |
|------|------|
| SSE 入口 | `app/api/v1/chat/chat_routes.py:60` → `app/services/chat/stream_orchestrator.py:322` |
| 消息落库 | `app/services/chat/message_service.py:191` |
| uid 回读 | `app/services/chat/stream_orchestrator.py:381-397`（track 读 + DB 兜底） |

### 1.1 落库权责归一（设计 [76] 6.2）

`insert_user_message()` 写入 `chat_user_message`，`id` 由 **AUTOINCREMENT 原生分配**，**此时 `task_id = NULL`**。

> 历史缺陷：agent 侧 `_absorb_inbox` 还会再 `insert_user_message` 一次（双重落库），导致同一内容出现两行、uid 错位。设计 [76] 6.2 把落库权责**归一到 API 入口**，agent 侧只从 inbox 元组里取 uid，不再重落库。

## 二、写入侧：七步

### 2.1 消息落库（唯一落库点）

`message_service.py:191` → `storage.insert_user_message()`

写入后 `_track_user_message(session_id, message_id)` 把 uid 记进内存 track，供步骤 2.2 回读。

### 2.2 活跃任务判定

`stream_orchestrator.py:407` → `task_registry.py:123` `has_active_task_in_session(session_id)`

锁内遍历 `running_tasks`，找 `session_id` 相同且 `status ∈ ("running", "paused")` 的任务，返回其 `task_id`；没有则返回 `None`。

### 2.3 投递到 inbox

`stream_orchestrator.py:409` → `task_registry.py:133` `inject_message_to_task(task_id, content, user_message_id)`

四道闸门，任一不过即 `return False`：

| 闸门 | 位置 | 不过的后果 |
|------|------|------------|
| 任务存在且 `status ∈ (running, paused)` | `task_registry.py:139-141` | 降级新建任务 |
| `_inbox` 队列存在 | `:142-144` | 降级新建任务 |
| `uid > 0`（`(uid or 0) <= 0` 拒，防 `None` 触发 TypeError） | `:145-148` | 降级新建任务 |
| 队列未满（`except asyncio.QueueFull`） | `:149-153` | 降级新建任务 |

投进去的载荷是**元组** `(content, uid)`；队列 `maxsize=INBOX_MAX`（`app/constants.py:137`，`INBOX_MAX = 20`）。

### 2.4 执行期绑定（关键修复点）

`stream_orchestrator.py:412` → `_bind_task_id()` → `storage.bind_message_to_task()`

```sql
UPDATE chat_user_message SET task_id = ?
 WHERE id = ? AND task_id IS NULL
```

- `AND task_id IS NULL` 保证不覆盖既有归属，返回 `bool` 表示是否影响行；
- 影响 0 行有**两种成因**：uid 对应行不存在 / `task_id` 已非 NULL。`stream_orchestrator.py:267-270` 两种都只记 warning，**不报错、不阻断**（设计 5.6「降级优先于报错」），且终态回填会补绑。

> **为什么必须现在绑**：修复前 `task_id` 只由终态的 `update_user_message_final` 写入。任务**执行期间**注入消息的 `task_id` 恒为 NULL → 左侧任务列表与历史查询在执行期**根本查不到这条消息**（用户表现为"消息发了但界面没有"）。

### 2.5 SSE 应答（merged 事件）

`stream_orchestrator.py:413` → `_build_injected_ack(task_id)` 产出一个 `MetaStep`：

```
type = "merged"
content = "消息已并入当前执行中的任务，将在下一轮吸收"
merged_into_task_id = <目标任务 id>
severity = "info"
```

随后编排器 `return` —— **本次 SSE 流就地结束，不启动新 agent**。

| 设计要点 | 说明 |
|----------|------|
| `retrying` → `merged` | `retrying` 属**重试语义误用**，前端会渲染成「🔄 重试」 |
| 双登记纪律 | `merged` 同时登记在 `steps/__init__.py` 的 `ALL_STEP_TYPES` 与 `stream_orchestrator.py:627` 的 `_SSE_FORWARD_TYPES`（显式 frozenset，非派生），漏登记则被通道过滤点拦掉、前端永远收不到 |
| 第三登记点 | E2E 侧 `e2etests/e2emodel/e2e_helpers.py` 的 `_SSE_WANT` 也需含 `merged`，否则会被当成"落库事件"计数，导致步骤表顺序退化 |

### 2.6 B-3 竞态兜底（TOCTOU）

`has_active_task_in_session` 与 `register_task` 是**两次独立 await**，中间存在时间窗，并发双请求可能都判定"无活跃任务"。

`register_task`（`task_registry.py:99-109`）在锁内**再查一次**同会话占用；命中则**返回占位 tid**（方案②，不抛异常），编排层 `:422-424` 拿到占位 tid 后改道注入该任务，消息照样不丢。

### 2.7 降级路径（不丢消息）

注入返回 `False` → 走**正常新建任务**流程。消息已在步骤 2.1 落库，`task_id` 会在终态由 `update_user_message_final` 正常写入。

**降级既有用户进度（消息在库里、界面有气泡），又不产生错误态。**

## 三、Agent 侧吸收：每轮 LLM 调用**之前**

### 3.1 唯一吸收点

`react_step.py:301-314`：

```python
agent.llm_call_count += 1
await _absorb_inbox(agent)                     # ← 单一吸收点，所有轮共用
agent.message_builder.trim_history()            # 必须在裁剪之前
messages = agent.message_builder.prepare_messages_for_llm()
```

| 设计要点 | 理由 |
|----------|------|
| **不打断工具执行** | 安全底线：工具正在执行时插入的消息被忽略，等本轮跑完、下一轮 LLM 前再并入 |
| **放在 `trim_history` 之前** | 让本轮注入的 user 消息**计入 trim 预算**（`always_keep_tokens = system + user`，`message_builder.py:376`）；否则 `available_budget` 偏大，会多保留 FC 对导致超上下文 |
| **注入内容不会被裁掉** | `trim_history` 对 **user 消息永保**（见 3.2），与调用顺序无关 |
| **单一吸收点** | 全轮覆盖（含直接回答轮）不漏；无积压时 `drain_inbox` 返回空，零开销跳过 |

### 3.2 顺带核实：`trim_history` 对 user 消息永保

`trim_history`（`message_builder.py:337-393`）**只裁 observation(tool) 与 assistant，从不裁 user**：

| 环节 | 位置 | 事实 |
|------|------|------|
| 分类 | `:365` `_classify_messages()` | 拆成 system / **user** / observation(tool) / assistant 四组 |
| 预算预留 | `:376-377` | `always_keep_tokens = 估token(system_msgs) + 估token(user_msgs)`，先从 `MAX_CONTEXT_TOKENS` 里扣掉 |
| 实际裁剪 | `:378` `_trim_to_budget(obs_list, assistant_msgs, available_budget)` | **入参只有 obs 与 assistant**，从最新往最旧按 FC 配对扫，预算用完即止 |
| 重建 | `:474` `rebuilt = system_msgs + user_msgs + trimmed_msgs` | **user 全量放回**，随后 `_trim_fc_pairs` 只修 tool↔assistant 配对，不动 user |

> 触发条件为「增量超缓冲」或「绝对值超 `MAX_CONTEXT_TOKENS × TRIM_TRIGGER_RATIO`（3/4）」；另有轮次过多时只保留最近 `_max_rounds` 轮 FC 对（`:369-373`），**同样只动 FC 对，user 不参与**。
>
> **一个诚实的极端边界**：`_rebuild_and_validate:478-479` 的兜底分支在裁剪后不足 2 条时会返回 `history[:2] + history[-8:]`，该切片**可能丢掉中间的 user 消息**。触发条件极为苛刻（预算近乎耗尽），本件只记录不改动。

### 3.3 drain（取走）—— 两个来源

`task_registry.py:157` `drain_inbox(task_id)`：

1. **正常路径**：`running_tasks[task_id]["_inbox"]`；
2. **收尾窗口找回**：任务已被 `cleanup_task` / `cleanup_expired_tasks` 清出 `running_tasks`，但队列里还有未吸收消息 → `task_registry.py:203 / :239` 先转移进模块级 `_orphaned_inbox[task_id]`，`drain_inbox` 找不到任务时从 orphan 找回。

orphan 上限 100 条（`_ORPHAN_MAX_ITEMS`），超出丢弃最旧并记 warning（终态任务不会再有 `drain_inbox` 消费，无上限即永久滞留内存）。

### 3.4 合并与截断

`react_step.py:213-233`：

```python
_contents = [m[0] for m in _injected]
_uids     = [m[1] for m in _injected]
_merged   = "\n".join(_contents)                       # 多条合并成 1 条
_max_chars = tuning.content.temp_history_char_limit    # 与 message_builder._cap_temp_history 同键(DRY)
if len(_merged) > _max_chars:
    _merged = _merged[:_max_chars]                      # 尾部截断 + warning
_uid = _uids[-1]                                        # 锚取最后一条
```

**不变量（2026-09-28 10 轮会审核实）**：inbox 的**唯一写入者**是 `inject_message_to_task`，其入口强制 `uid > 0`；orphan 路径只搬运已校验元组。因此 `_uids` 必非空且全为正整数 —— 原 `_uids[0] if _uids else None` 的 `else None` 与 `if _uid is not None` 的单参降级都是**死代码**，已按 YAGNI 删除。

### 3.5 两种落位

`react_step.py:236-244`：

```python
_merge_into_last = isinstance(_last, dict) and _last.get("role") == "user"

if _merge_into_last:
    _last["content"] = str(_last.get("content") or "") + "\n" + _merged   # 并入, 锚不变
else:
    agent.message_builder.add_user_message(_merged, user_message_id=_uid)  # 独立成轮, 锚演进
```

| 场景 | 分支 | 效果 |
|------|------|------|
| 上一轮已产出 assistant / tool 结果（**生产常态**） | 独立成新 user 轮 | 新增一个 user 轮，锚演进到注入 uid |
| 末条仍是 user（如首轮 LLM 前就注入） | 并入末条 | 不产生连续 user，锚保持原值 |

> **为什么要防连续 user**：OpenAI 兼容协议要求 user/assistant 交替，连续 user 部分 provider 判非法。
> **锚演进的单点**在 `message_builder.py:153` —— 只有传入真实 uid 才更新 `_current_user_msg_id`；合成负 id **不演进**，避免终态拿负 id 去 `UPDATE` 命中 0 行。

## 四、终态回填：答案落在**锚所在那一行**

`agent_runner.py:648-651`：

```python
_active_uid = getattr(agent.message_builder, "current_user_msg_id", None)
_final_uid  = _active_uid if (_active_uid or 0) > 0 else db_ops.user_msg_id
update_user_message_final(conn, user_message_id=_final_uid, task_id=task_id,
                          response=..., reasoning=..., outcome=..., ...)
```

`current_user_msg_id` 是 `message_builder.py:118-124` 新增的**只读 property**。

> **历史根因**：此前 `agent_runner` 用 `getattr(mb, "current_user_msg_id", None)` 读取，但 builder 只有私有的 `_current_user_msg_id` → **恒为 None**，2026-09-20 的锚回填与 D-1 两个修复**从未生效**。补公开只读口（读私有、禁外部直读）才修掉根因。

### 4.1 两个必然推论

1. **只有一行拿到 `response`**。若由注入触发，答案落在**最后一条注入行**上。
2. 任务**登记首条**的 `task_id` 可能仍为 `NULL`（终态只写锚行）→ 读侧靠 `cum.id = ct.user_message_id` 兜底归任务（见 5.1）。

### 4.2 为什么锚取最后一条

| 依据 | 说明 |
|------|------|
| 设计明文 | `[30] §4.5 B-5`：「锚取**最后一条** uid」 |
| live 行为 | 前端 assistant 是**追加到末尾**的（`useChatStreaming.ts:494`）→ live 顺序 `[u1, u2, u3, 答案]` |
| 刷新行为 | 锚=最后一条 → carrier 把 assistant 渲在最后一条注入行 → `[u1, u2, u3+答案]`，**与 live 一致** |
| 反证 | 若锚取第一条，刷新后答案会出现在**第一条**注入行处 → 与 live 顺序不一致 |

## 五、读侧：刷新后长什么样

### 5.1 精确归属

`storage.py:778-789`：

```sql
LEFT JOIN chat_tasks ct ON ct.id = COALESCE(
    (SELECT MAX(id) FROM chat_tasks WHERE task_id = cum.task_id),      -- 注入行凭 cum.task_id
    (SELECT MAX(id) FROM chat_tasks WHERE user_message_id = cum.id)    -- 登记首条凭自身 id
)
```

- 注入消息凭 `cum.task_id`（执行期已绑）归任务；登记首条凭 `cum.id = ct.user_message_id` 归任务 —— **两条路径归一**；
- `ORDER BY cum.id ASC` 保证按落库顺序返回；
- `ct` 额外返回 `pair_task_id` 供渲染层同任务判据。

> **历史缺陷**：旧版是"会话级模糊兜底"（取本会话最后任务的 `ai_message_id`），会把消息配到**别的任务**上（跨任务错配）；同时删除了 D-1「复制 chat_tasks 行」的补配对 INSERT（复制源任务行会导致列表重复条目、React key 冲突、总数虚高）。零 DDL，改用精确 JOIN。

### 5.2 carrier：每个 assistant 只渲一次

`message_service.py:83-95`：

- `_first_row[ai_id]` = 该 `ai_message_id` 首次出现的行；
- `_carrier[ai_id]` = **首个有内容**的行；全空则回落首见行（保 steps）；
- 渲染循环 `if _carrier.get(ai_id) != _i: continue`，且 `load_execution_steps` 只在载体行调用一次。

> 解决的是「同一 assistant 连同 steps 重复渲染 N 次」。
> **曾经错误的做法**：在 carrier 之前先做「同任务连续空行合并成 1 个气泡」。该合并会制造**新的刷新跳变**（live 每次发送都追加一个气泡，后端单方面合并 → live N 个 / 刷新 1 个），且会把带答案的行挤出合并组致答案丢失。已于 2026-09-28 撤销，只保留 carrier。

### 5.3 刻意**不做**气泡合并

同一批行的多条注入，**各占一个气泡**，与 live 一致（`useChatSend.ts:135` 每次发送都 `setMessages([...prev, userMessage])`）。

> **概念区分**：`conversation_history` 合并（为满足 OpenAI 交替性，见 3.3）与「UI 气泡合并」（用户实际发送条数）是**两个层面**。前者必须做，后者不能做。

### 5.4 左侧任务条目

`list_session_tasks`（`storage.py:838+`）：

1. 按 `task_id` 折叠同 task 多行（保留 `ORDER BY id ASC` 首行，防御历史 D-1 假行）；
2. `merged_inputs` = 会话级**单次查询**取 `task_id IS NOT NULL` 的行按 task 分组，排除**任务登记首条 uid**（用行自带的 `user_message_id`，免子查询），`ORDER BY id ASC`；
3. 前端 `TaskListPanel` 渲染成「↳ 追加 N 条」`CollapsibleText` 折叠块。

> 存量脏数据由 `migrate_purge_injected_dupes`（`migrate_steps.py:217+`）一次性 DELETE，登记在 `schema_migrations` 防重跑；条件②用 `NOT EXISTS`（原 `NOT IN` 遇 `chat_tasks.user_message_id` 可空列会恒 UNKNOWN → 删 0 行静默失效）。

## 六、关键设计取舍汇总

| 取舍点 | 选择 | 理由 |
|--------|------|------|
| 打断工具执行吗 | **不打断** | 安全底线；只在 LLM 调用前吸收 |
| 落库在哪 | **只在 API 入口** | 双重落库 = uid 丢失根因 |
| uid 怎么传 | **随消息同行（元组）** | 免二次查询/二次落库，契约单一 |
| 多条注入 | **合并成 1 条** | OpenAI user/assistant 交替性 |
| 单条注入且末条是 user | **并入末条** | 防连续 user（[76] v1.11 F7） |
| 锚取哪条 | **最后一条** | 与 live 渲染顺序一致 |
| `task_id` 何时写 | **执行期就绑** | 否则执行期查不到消息 |
| 队列满 / uid 非法 | **降级新建任务** | 消息不丢、无错误态（设计 5.6） |
| 渲染层是否合并气泡 | **不合并** | live 就是 N 个，合并会造成新跳变 |
| DDL | **零 DDL** | 复用既有 `task_id` 列 + 既有 JOIN |

## 七、边界与降级矩阵

| 异常场景 | 检测位置 | 处置 |
|----------|----------|------|
| 队列满（≥ `INBOX_MAX`=20） | `task_registry.py:150` `QueueFull` | 拒注入 → 降级新建任务 |
| `uid <= 0` / `None` | `task_registry.py:145` | 拒注入 → 降级新建任务 |
| 目标任务已终态 | `task_registry.py:139` | 降级新建任务 |
| 并发双请求（TOCTOU） | `task_registry.py:100-109` B-3 | 返回占位 tid → 改道注入占位任务 |
