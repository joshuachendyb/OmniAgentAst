## 一、设计目标（本架构解决的三大问题）

1. **后端设置文件与设置项目一一对应**：`config/config.yaml` + `user_settings` 表的所有设置项，都能在前端设置页面找到对应的表单控件；后端新增设置项 = 只需在 registry 加一行，前端页面自动多出一个控件，不需要改前端代码。
2. **页面角度的读写友好**：用户/使用方从"打开设置页"这个角度就能完成所有读写——读：进页面即看到每个设置项当前实际值；写：改表单 → 保存 → 落到对应设置文件/表。所有设置项在页面上有且仅有一个读入口和一个写出口，不绕来绕去。
3. **前端不懂设置的问题**：当前前端 `theme/language` 是死字段（`api.ts` 有类型无 UI）、`temperature` 无设置入口，用户无从知道有哪些设置可调。新架构让"设置项长什么样、存哪里、怎么改"全部透明可见。

## 三、新架构总览（Schema 驱动 + 三接口 + 一键动态渲染）

### 3.1 一页看懂的数据流

```
【后端】                          【前端】
settings_registry.py  ──GET /api/v1/settings/schema──►  控件定义
(唯一Schema源:6分组/每项  ──GET /api/v1/settings──►      当前值
 key/type/默认/校验/存储位置) ──► 动态渲染表单
        │
        ▼  PUT /api/v1/settings {patch}
settings_service.py  ──system项→写 config.yaml(先备份)
                     └─preference项→upsert user_settings表
        ▼
  返回 {ok, updated:[...], need_restart:[...]}  ──►  页面提示"已保存"
        ▲
PreferenceContext + useSettings hook  ──localStorage "omni.prefs.v1"──► 双写缓存/离线降级
```

### 3.2 三大铁律（本架构的骨架）

1. **后端是唯一真相源**：所有设置项的 key、类型、默认值、值域、存哪，只在 `settings_registry.py` 定一次。前端不写死任何设置项。
2. **设置项与存储一一对应**：每一个设置项在 `config.yaml` 或 `user_settings` 表中**必须有且只有一个存储归属**（见第四章映射表）。
3. **前端"读 = 进页面即见，写 = 保存即落盘"**：不存在页面改了的值和后端设置文件不一致的情况（DB+缓存双写保证）。

## 五、后端设计

### 5.1 新增文件

| 文件 | 职责 |
|------|------|
| `backend/app/services/settings/settings_registry.py` | **唯一 Schema 源**：6 分组、每项 `key/type,label,default,options/range,validator,storage(YAML|DB),restart`，全静态 dict |
| `backend/app/services/settings/settings_service.py` | 读写合并核心：`get_settings(group)` 合并 YAML+DB；`update_settings(patch)` 校验→system 写 YAML(先备份)→preference upsert DB→清缓存；`get_setting(key, default)` 一行直取 |
| `backend/app/api/v1/settings_routes.py` | 3 个接口：schema / get / put |
| `backend/app/db/models/user_settings.py` | ORM 模型 + 建表 |

### 5.2 `user_settings` 表结构（SQLite，同 `chat_history.db` 库）

```sql
CREATE TABLE user_settings(
  key        TEXT PRIMARY KEY,   -- 如 chat.temperature / appearance.fontSize
  value      TEXT NOT NULL,      -- JSON 字符串，如 "0.7"
  updated_at TEXT NOT NULL       -- 2026-09-19 20:20:39
);
```

### 5.3 三个接口契约

```
GET  /api/v1/settings/schema                     → {groups:[{key,label,items:[{key,type,label,default,options|min|max|step,storage,restart}]}]}
GET  /api/v1/settings?group=appearance           → {data:{app.theme:"light",...}, version:"", mtime:""}
PUT  /api/v1/settings  body={patch:{app.theme:"dark"}} → {ok:true, updated:["app.theme"], need_restart:["app.language"]}
```

要点：
- schema 一次拉取，页面据此动态渲染所有分组表单（新增设置项=registry 加一行，前端零改动）。
- `update_settings` 中 system 项写 YAML 前**必先备份**为 `config.yaml.backup_YYYYMMDD_HHMMSS`（复用现有 `_helpers` 备份逻辑，符合现有规范）。
- 写入后立即校验 YAML 可回读，失败自动回滚备份，杜绝损坏 config.yaml。
- 旧 `/config/*` 路由保留兼容，新页面只调 `/settings/*`；待稳定后清理死字段。

### 6.3 页面读写流程（用户/使用方角度）

**读（进页面）**：
1. 打开 `/settings` → `PreferenceContext` 已有缓存时先显示缓存值（快）。
2. 同时 `GET /settings/schema` + `GET /settings` → 后端实际值覆盖缓存 → 每个控件显示**前后端一致的真实值**。
3. 控件只读项（config_path/version）以禁用态展示。

**写（保存）**：
1. 改控件 → 值立即写入 `localStorage["omni.prefs.v1"]`（前端即时生效，不卡顿）。
2. 点"保存" → `PUT /settings {patch}`。
3. 后端落盘（YAML 备份写 / DB upsert）→ 返回 `need_restart` 列表 → 页面提示"已保存，N 项需重启生效"。
4. 失败 → 回滚 localStorage 缓存 + 红色提示，不改后端。

### 6.4 页面读写便利示例

```tsx
// 前端任意处（页面组件内）一行读写 — 小强 2026-09-19
const { value: theme, update } = useSetting("app.theme");   // 读：value；写：update("dark")
const { data, save } = useSettings("chat");                 // 整组读写
```

### 6.5 DB+缓存双写细则（已确认采用）

| 场景 | 行为 |
|------|------|
| 有后端 | 拉后端为准 → 刷新 localStorage 缓存 |
| 无后端 | 读 localStorage 缓存降级 → 页面照常显示，保存时提示"后端未连接，仅本机生效" |
| 写偏好(chat/appearance 前端项) | 先写缓存 → PUT → 成功后后端 DB/YAML 为准回写对齐缓存 |
| 写系统项(security/model/general) | 先写缓存兜底 → PUT → 成功后 YAML 落盘返回需重启列表 |

## 七、前端设置页 UI 设计方案（UI 与 API 一一对应）

> 设计原则一句话：**UI 是 API 的可视化，设置页的每一个区域都对应一个明确的 API 调用；新增设置项 = 后端 registry 加一行 = 前端 UI 自动长出一个控件，前后端零重复定义。**

### 7.1 UI 与 API 三角对应

```
页面控件（User sees）        schema.type（API 定义）        后端存储（config.yaml / user_settings）
      │                            │                                │
      └────────── 完全一一对应 ─────┴────────────────────────────────┘
  由 GET /settings/schema 驱动渲染，页面零写死
```

| UI 层 | API 层 | 说明 |
|-------|--------|------|
| 左侧六分组导航 | `GET /settings/schema` → `groups[{key,label}]` | 分组由 schema 定义，页面只遍历不写死 |
| 右侧每个设置项控件 | `GET /settings/schema` → `items[{key,type,label,options,...}]` | 控件类型、可选项、单位全部来自 schema |
| 控件当前值 | `GET /settings?group=X` → `data` | 进页面先展示缓存 → 后端真实值覆盖，前后端一致 |
| 保存按钮 | `PUT /settings` → `{patch}` | 只提交用户改动过的项，后端按其存储位置落盘 |

**回答：是的，UI 必须和 API 对应**——而且是最好的那种对应：**schema 驱动**，后端是唯一真相源，UI 自动跟随，不存在 UI 改了 API 不同步的问题。

### 7.2 页面整体布局（左侧导航 + 右侧内容 + 底部保存栏）

```
┌──────────────────────────────────────────────────────────────────────┐
│ 系统设置                                        [🔍搜索设置项...] [还原默认] [💾保存] │
├──────────────┬───────────────────────────────────────────────────────┤
│  分组导航      │  ← 当前分组内容区（右侧，按 schema 动态渲染）                  │
│              │                                                       │
│ ① 通用       │   设置项行（每一行 = 一个设置项 = 一个 API key）              │
│ ② 模型       │   ┌─────────────────────────────────────────────────┐   │
│ ③ 安全       │   │ 主题         [light ▾]    🔍说明   💡热生效      │   │
│ ④ 聊天       │   │ 界面语言      [zh-CN ▾]    🔍说明   ⏳重启生效    │   │
│ ⑤ 外观       │   │ 项目根目录    [ E:\test_dir ] [📂浏览]  🔍说明   │   │
│ ⑥ 系统       │   └─────────────────────────────────────────────────┘   │
│              │                                                       │
│ Group徽标     │  未保存项：该行显示橙色"未保存"圆点                        │
│ 只读分组 🔒   │                                                       │
├──────────────┴───────────────────────────────────────────────────────┤
│ 底部保存栏（sticky）：[N 项未保存]  [还原默认]  [保存全部]   （有改动才出现）      │
└──────────────────────────────────────────────────────────────────────┘
```

布局要点：
- **左侧固定分组导航**：六分组 + 徽标（未保存数量）、只读分组锁标；点击即跳对应分组，含未保存项时弹确认（沿用现有 `isDirty` 逻辑）。
- **右侧内容区**：AntD `Card` 内按分组渲染设置项行；每行三区——左（显示名+说明 tooltip）、中（控件）、右（生效标签）。
- **底部 sticky 保存栏**：只有本分组有改动才出现，避免误操作；"还原默认"只还原当前分组。

### 7.3 六分组页面详细 UI

| 分组 | 页面布局 | 关键 UI 元素 |
|------|---------|-------------|
| ① 通用 | 单列表单（Spaced 行） | 系统语言 `Select`；项目根目录 `Input`+`浏览目录`按钮；日志级别 `Select`；日志文件上限/备份数 `InputNumber` |
| ② 模型 | 左 Provider 列表 + 右详情卡片（保留现有组件） | 顶部当前模型联动双下拉（Provider→Model）；右侧卡片：`api_base` Input、`api_key` 密码框（掩码+眼睛）、`timeout/max_retries` InputNumber、模型清单 `Select mode=tags`；卡片级"当前模型"星标 |
| ③ 安全 | `Collapse` 折叠（基础/命令黑白名单/内容过滤） | 基础开关组 `Switch`；黑白名单 `TextArea`（monospace，每行一条命令）；危险操作开关+确认；最大文件 `Select(10/50/100/500)` |
| ④ 聊天 | 单列表单 + 滑条区 | `temperature/top_p` 用 `Slider`+`InputNumber` 双显；`max_tokens/history_limit` InputNumber；`auto_title/stream` Switch |
| ⑤ 外观 | 顶部实时预览卡片 + 参数区 | 主题 `Segmented(亮/暗)` 即时整站变色；界面语言 `Select`；字号 `Slider(12~18)`+预览文字实时变大；密度 `Segmented(紧凑/舒适)`+预览消息气泡 |
| ⑥ 系统 | 可编辑 + 只读混排 | 可编辑：`debug` Switch、`max_context_tokens/history_length/rounds/steps` InputNumber；只读：`config_path/version` 禁用态 + 一键复制按钮 |

### 7.4 控件类型 ↔ schema.type ↔ antd 组件 ↔ 写入值类型（UI↔API 对应表）

| schema.type | 说明 | antd 组件 | 控件样子 | PUT patch 值类型 |
|------------|------|-----------|---------|-----------------|
| `text` | 短文本 | `Input` | 单行输入框 | `string` |
| `secret` | 密钥 | `Input.Password` | 密码框(掩码+切眼睛) | `string`（不填表示保持原值） |
| `textarea` | 多行 | `Input.TextArea` | 等宽字体多行 | `string` |
| `tags` | 列表 | `Select mode="tags"` | 标签添加/删除 | `string[]` |
| `int` | 整数 | `InputNumber` | 数字输入 | `number` |
| `float` | 小数 | `InputNumber(step)` | 数字输入(带精度) | `number` |
| `range` | 数值范围 | `Slider` + `InputNumber` | 滑条+数字双显 | `number` |
| `bool` | 开关 | `Switch` | 拨动开关 | `boolean` |
| `select` | 单选 | `Select` | 下拉选择 | `string` |
| `readonly` | 只读 | 文本 + `disable` | 禁用态+复制按钮 | 不提交 |

每个设置项行的右侧固定展示两个徽标（均来自 schema）：
- `💡热生效`（绿）：保存立即生效；`⏳重启生效`（橙）：保存后需重启后端。
- 存储位置 `YAML/DB`（hover 展示 `config.yaml` 对应行 或 `user_settings` 表对应 key）。

### 7.5 保存 / 还原 / 脏状态 / 重启生效 交互流程

```
改动任意控件 → 该行出现橙色"未保存"圆点 + 底部保存栏浮现(未保存数累计)
     │
     ├──► 点[保存] → 前端按 schema 即时校验(必填/取值范围)
     │      │
     │      ├─ 通过 → PUT /settings { patch: 仅提交改动项 }
     │      │    ├─ 成功 → toast"已保存"；若含需重启项 → Modal
     │      │    │        "以下 N 项重启后生效：[app.language]"
     │      │    └─ 失败 → 回滚该行值 + 红色 toast（展示后端错误详情）
     │      └─ 不过 → 第一个错误控件红色描边 + 定位滚动
     │
     └──► 点[还原默认] → 确认 Modal → 按该分组 schema.default 重置 → 进入待保存态

切换 Tab / 离开页面时有未保存 → Modal"当前有未保存修改，保存后切换？"
   [保存并切换] [放弃修改] [取消]   （沿用现有 isDirty 逻辑）
```

### 7.6 外观分组即时预览（对应 DB+缓存双写）

1. 主题切"暗" → 立即写 `localStorage["omni.prefs.v1"]` → 全站（含当前设置页）即时变色；点保存才 `PUT /settings` 落 YAML `app.theme`。
2. 字号拖动 → 预览区文字实时变化；密度切换 → 预览气泡间距实时变化。
3. 图标"本地生效"角标提示：未点保存前该行标注"仅本机生效"，保存后消失——**用户任何时刻都知道当前值落在哪一层**。

### 7.7 密钥与危险项的安全性 UI

- **api_key**：常态只显示"已配置 ······末尾4位"+ [修改]按钮；点修改才出现输入框和 [保存]；发送空值 = 保持原值（后端不覆盖）。
- **危险操作开关 / 黑白名单**：保存时二次确认 Modal，必须勾选"我确认上述改动"才能提交。
- **只读项**（config_path/version）：禁用态 + 复制按钮，禁止篡改。

### 7.8 加载 / 空 / 错误状态

| 状态 | UI 表现 |
|------|---------|
| 首次加载 | 分组内容区骨架屏 `Skeleton`；顶部进度条拉 schema |
| schema 拉取失败 | 全页 `Result status="warning"` + [重试] 按钮 |
| 设置项为空 | 分组内占位"暂无设置项" |
| 保存失败 / 后端未连接 | 页面顶部红色 `Alert banner`，内容区降级显示缓存值并标注"缓存模式" |
