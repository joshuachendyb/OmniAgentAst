## 第一章 api_key 未去空格即落盘

**级别**：中

### 1.1

同一个 `doSave` 函数内，**base_url 去了空格、api_key 没去**——是遗漏，不是设计：

| 环节 | 代码 | 去空格 |
|------|------|-------|
| 前端落盘 | `ProviderConfig.tsx:108` `patch.api_key = apiKey` | **否**（`trim()` 只用于该行条件判断） |
| 同函数对照 | `ProviderConfig.tsx:109` `patch.base_url = baseUrl.trim()` | **是** |
| 后端落盘 | `model_service.py:431` `if k in key_map and v is not None` | **否** |
| 旧通道落盘 | `config_helpers.py:414` `config_data[...]['api_key'] = api_key.strip()` | **是** |
| 会话覆盖消费 | `resolver.py:193` `(...).strip() or None` | **是** |
| 全局默认消费 | 单例 `self.api_key` ← `config.py:112` / YAML 原值 | **否** |
| SDK 组 header | `client_sdk.py:279` → `adapters/base.py:17` `Bearer {api_key}` | **否**（原样透传） |

### 1.2

粘贴带首尾空格或换行的 key → 界面提示"保存成功" → 实际调用 401。**界面无任何提示指向空格**，用户反复重输同一串 key 仍失败。

且**行为分叉**：同一份配置、同一串 key，走会话覆盖路径会被 strip 因而可用，走全局默认路径就 401。

### 1.3

去空格必须放**后端**（最后防线，所有调用方必经），前端同步做仅为体验一致。

- **后端（主）** `model_service.py` `update_provider_config`：`key_map` 循环内对 `api_key` 特殊处理，写入前 `str(v).strip()`。使落盘值与旧通道 `config_helpers.py:414` 对齐，消除双通道不一致。
- **前端（辅）** `ProviderConfig.tsx:108`：`patch.api_key = apiKey` → `patch.api_key = apiKey.trim()`，与 `:109` 写法统一。
- **消费端兜底（建议一并做）** `client_sdk.py:279`：组 header 前对 `api_key` 再做一次 `.strip()`，使**已落盘的历史脏 key 也能工作**，避免要求用户手工重录。

### 1.4

`backend/app/services/model/model_service.py`、`backend/app/llm/client_sdk.py`、`frontend/src/features/settings2/components/ProviderConfig.tsx`

### 1.5

- 写入带首尾空格与换行的 key → 保存 → 实际 LLM 调用成功
- 已中招的历史脏 key（YAML 中带空格）→ 不重录也能调用成功

## 第二章 跨 provider 场景下 key 空白，却偷用别的 provider 的 key ★最高优先

**级别**：**高**

> **v2.3 判定修正**：v2.0/v2.2 把本章描述为"空白 key 静默回落到全局默认 key"，**遗漏了一个关键区分**——`_pv_key=None` 有两种**性质相反**的情况，其中一种是正常的。北京老陈指出：「key 空白的就是空白的，不能瞎改，调用不通的时候直接报错就是了」。本章据其修正：**该报错的报错，不该报错的必须保留原行为**。

### 2.1 病根

两处代码叠加：

```
resolver.py:189   if _ov.provider and _ov.provider != ai_service.llm_model.provider:
                  │  ← 只有【跨 provider】才进这个分支去查目标 provider 的配置
resolver.py:193       _pv_key = (_pv_cfg.get("api_key") or "").strip() or None
                                                    └─ 空白 key → "" → or None → None
base_service.py:208   api_key=api_key or self.api_key
                                           └─ None → 沿用单例 self.api_key（全局默认 provider 的 key）
```

### 2.2 关键区分：`_pv_key=None` 的两种情况（v2.3 补，原文遗漏）

| 情况 | 触发条件 | 代码路径 | 现在的行为 | 判定 |
|------|---------|---------|-----------|------|
| **A 同 provider** | 会话只换了**模型名**，provider 未变（如 sensenova 的 A 模型 → B 模型） | **不进入** `resolver.py:189` 的 if，`_pv_key` 保持 None → `base_service.py:208` 用单例 key | 用单例 key | **正常，必须保留**。同一个 provider 本来就该用同一个 key |
| **B 跨 provider** | 会话切到**另一个** provider（全局默认 sensenova → 会话选 glm），而该 provider 的 key 是空白 | 进入 if → 查 glm 配置 → 空白 → `_pv_key=None` → `base_service.py:208` 用单例 key | **偷用 sensenova 的 key** | **瞎改，必须报错** |

→ **同一个 `None`，在 A 里是设计如此，在 B 里是错误。** 原文档把两者混为一谈，是表述错误。

### 2.3 后果（仅情况 B）

会话切到 provider B（key 空白）时：

- 请求 **B 的模型名 + B 的 api_base**，但 `Authorization` 头带的是 **A（全局默认 provider）的 key**
- **多数情况**：401（key 与端点不匹配）
- **最坏情况**：若 A 与 B 指向**同一个网关且 key 通用** → **请求成功**。用户以为配好了，实际一直在用 A 的 key，**完全不知情**
- **全程无一条日志**——本批最难查的一个

**对照**：`model_service.py:537`（拉远程模型列表）`os.environ.get(...) or str(p.get("api_key") or "")` 传空字符串，**不回落**。→ 两条链路对"空 key"处理相反。

### 2.4 改法：情况 B 直接报错，情况 A 原样不动

**原则**（北京老陈）：**key 空白就是空白，不能瞎改；调用不通就明确报错，不要偷偷换一个 key 顶替。**

- **主修 `resolver.py:193-193`**：在**跨 provider 分支内**（即 `:189` 的 if 体内）区分"查到了配置但 key 空白"与"配置本身查不到"
  - `_pv_cfg` 取到、但 `_pv_key` strip 后为空 → **抛错**（复用现有 `except` 之外的中断路径），文案明确指向配置项：「会话切换到 provider **B**，但该 provider 未配置 api_key，请先在设置页填写，或设置环境变量 B_API_KEY」
  - **必须带上 provider 名**（来自 `_ov.provider`），让用户知道该去配哪一个
  - `_pv_cfg` **取不到**（`:197` except 分支）→ 维持现状走 `_default_snapshot`（`:203-207`），此处已有 WARNING 日志，**不动**
- **不动情况 A**：`resolver.py:189` 之外的所有 fallback **保持原样**。同 provider 用单例 key 是正确行为，严禁一并"修掉"。**同 provider 的 `api_base` 同理**：`ModelRef` 构造时沿用本代地址（v3.6 订正：实施中曾随 `:211` 的 `or` 一并无条件删除，致同 provider 切模型必 400，已按是否跨 provider 区分修复，见 8.5 第 4 条）
- **补 env 误报核实（已确认安全）**：`get_service_config`（`resolver.py:191`）→ `get_ai_config`（返回 `self._config["ai"]`）→ `AIConfig` 已执行 `config.py:102-112` `_apply_env_overrides`，env 提供的 key **已写入配置**
  → **用环境变量提供 key 的 provider 不会被误判为"未配置"**，改报错是安全的
- **一致性** `model_service.py:537`：该路径传空串**不回落**（行为正确），无需改动；但需在注释中写明"此处不回落，与 resolver 情况 B 报错共同构成 'key 空白即失败' 的一致语义"，避免后人误加 fallback
- **配套（DRY）** `lifecycle/validation.py:52` 已有 `api_key.strip() == ""` 判定分支，可抽为公用判定函数供 resolver 复用，避免第三次出现不一致

### 2.5 报错如何送达前端（已定：编排层专属 catch + 补中文标签）

**背景**：`resolve_session_client` 由 `stream_orchestrator.py:410` 调用，其异常会被 `:536` 的 `except Exception` 兜住，统一包成 `router_error`（文案「路由异常: {原始异常}」）。`stream_orchestrator.py:162-169` 的 [70] 修订记录已批评这种做法**"泄露内部异常文案"**。

若只在 `resolver.py` 抛错，用户会看到「路由异常: xxx」，与 ConnectionScope 等系统错误混在一起，**分不出是配置问题还是系统问题**。故采用专属 catch：

| 层 | 改动 |
|----|------|
| `resolver.py` | 抛**专属异常类型**（如 `ProviderKeyMissingError`），消息带 provider 名，不混进通用 `Exception` |
| `stream_orchestrator.py:410` 外 | 单独 catch 该类型 → `create_error_response(error_type="config_error", ...)`（`:185` 已 import），人话文案，**不让它掉进 `:536` 的 `router_error` 兜底** |
| 前端 `ErrorDetail.tsx` | **必须补中文标签**：`ERROR_TYPE_LABELS` 现无 `config_error`（现有 20 项：`empty_response`/`timeout`/`network_error`/`server_error`/`rate_limit`/`authentication_error`/`authorization_error`/`validation_error`/`not_found`/`internal_error`/`quota_exceeded`/`idle_timeout`/`cancelled`/`client`/`server`/`unknown`/`circuit_open`/`llm_error`/`unknown_response`/`agent_operation_error` 等），`formatErrorType` 逻辑是 `LABELS[type] \|\| type`，**不补则前端直接显示英文 `config_error`**；同时在 `ERROR_COLORS_MAP` 补配色（现有分组：`security_error`/`agent`/`network`/`validation`/`file_system`/`security`/`unknown`/`default`） |
| 前端展示形态 | 走 `PipelineRenderer.tsx:391` 的**对话流错误块**（非 toast），与现有错误一致 |

**文案风格对齐** `stream_orchestrator.py:240-244` 已有先例（`f"配置验证失败: {...}"`），不新造一套。

**为什么不在首个 401 响应处报错**：401 无法区分"key 错"与"其它 401"（如网关鉴权、账号欠费），且此时已发出请求、浪费一次配额。`resolver` 阶段抛错可**早失败**且能直指配置项。

### 2.6 涉及文件

`backend/app/services/model/resolver.py`（主改）、`backend/app/services/model/model_service.py`（仅加注释）、`backend/app/services/lifecycle/validation.py`（抽公用判定，可选）

### 2.7 验收

- **情况 B**：会话切到 key 空白的 provider → **明确报错**，文案含 provider 名与"未配置 api_key"；**日志无"用别的 key"的痕迹**
- **报错呈现**：前端对话流显示**中文标签 + 人话文案**（非英文 `router_error`、非"路由异常"）
- **情况 B 变体**：provider 的 key 配成**纯空格** → 同样报错（不静默用别的 key）
- **情况 B env 变体**：provider 的 key 由 `B_API_KEY` 环境变量提供 → **正常放行**，不误报
- **情况 A 回归**：同 provider 只换模型名 → **仍正常使用**（防"修过头"，这是本章最易引入的退化）
- 拉远程模型列表路径行为**不变**

## 第三章 后端收到空字符串直接清空 key

**级别**：**高**

### 3.1

- `model_service.py:431` `if k in key_map and v is not None` —— **空字符串不是 None**，判定通过，`api_key: ""` 被写进配置
- 校验链不拦：`config_helpers.py:276-277` `if 'api_key' not in provider_config` —— **只校验字段存在**，空字符串也算存在，照过
- 前端有保护（`ProviderConfig.tsx:108` 拦截空值不发送），**后端完全裸奔**

### 3.2

任何非界面途径传入空字符串即**擦除密钥**：`PUT /api/v1/config` 旧通道、脚本 / curl / 将来编写的 E2E。接口返回 `{"ok": true}`，**调用方以为设置成功**。

"留空=保持原值"这个语义**只存在于前端**，后端无对应实现——契约保护放错了层。

### 3.3

三态语义在后端做实，且**成为唯一权威**（前端保护降级为体验优化）。

| 传入 | 语义 | 行为 |
|------|------|------|
| 字段不出现 / `null` | 不修改 | 跳过，不写 |
| `""` 或纯空白 | **不修改**（与前端"留空=保持原值"对齐） | 跳过，不写 |
| 非空字符串 | 设置 | `.strip()` 后写入 |
| `clear: true` | 清空 | 显式写 `""`（唯一允许清空的途径） |

- **主修** `model_service.py` `update_provider_config`：`key_map` 循环前对 `api_key` 做三态判定——空/空白值 `continue` 跳过（不进入 `node`），仅非空值赋值。`clear` 分支（`:437`）保持显式清空，但需与设置分支互斥（见第四章）。
- **配套** `config_helpers.py:276-277`：该校验仅在"字段完全缺失"时报警。由于界面上 `ProviderConfig.tsx:201` 明确显示"未配置，留空=保持原值"，说明**允许未配置状态**，故**空值合法、不应报警**。此处维持现状，仅补注释说明，避免后人误加校验导致无法保存未配置状态。
- **契约文档化** `model_routes.py:76-81`：在 `ProviderConfigUpdate` 字段说明中写明 `api_key` 三态（None/"" = 不修改），避免调用方误用。

### 3.4

`backend/app/services/model/model_service.py`、`backend/app/api/v1/model_routes.py`

### 3.5

- 对已配 key 的 provider 提交 `api_key: ""` → 配置**未被清空**，返回 ok
- 提交 `clear: true` → key 被清空
- 提交非空 key → 正常写入

## 第四章 clear 请求覆盖刚输入的新 key

**级别**：低

### 4.1

`model_service.py:437-438` 排在 api_key 赋值**之后**且**无条件覆盖**：

```python
for k, v in fields.items():
    if k in key_map and v is not None:
        node[key_map[k]] = v          # ← 先写用户输入的新 key
...

```

## 第六章 secret 设置项写入无「三态」保护（潜伏）

**级别**：中（潜伏未触发） | **方案**：**B 已定**（北京老陈 2026-09-26 07:20）

### 6.1 病根（现状：读路径已掩码，写路径未实现）

| 位置 | 事实 |

| `SettingRow.tsx:120,129` | 前端会提交 `''`（留空）与 `{clear:true}`（清空） |

### 6.2 什么是「三态」（大白话解释）

一个密钥输入框，用户有**三种不同意图**，但代码只用一种方式表达：

| 状态 | 用户做什么 | 他心里的意思 | 代码表示 |
|------|-----------|------------|---------|
| **状态1** | 什么都不填，直接点保存 | **"别动它"** | `''`（空字符串）或**不传该字段** |
| **状态2** | 输入 `sk-新值` | **"换成这个"** | `'sk-新值'`（非空字符串） |
| **状态3** | 点「清空」按钮 | **"删掉"** | `{clear: true}` |

**「三态」= 状态1 + 状态2 + 状态3。**

**问题根源：空字符串 `''` 被赋予了两种相反的含义**

```
用户心里：  我留空 = "这个字段我不想改"   → 状态1
代码理解：  收到空字符串 = "把值设成空"  → 状态3
```

**同一个 `''`，两种完全相反的意思。** 修"三态"的本质就是**把这两种意图拆开表达**：

| 意图 | 正确表示 |
|------|---------|
| 不修改 | **不传该字段**（或传 `null`） |
| 设置新值 | 传非空字符串 |
| 清空 | 传 `clear: true` |

### 6.3 两个具体坏例子

**例子 1：留空 = 擦掉**

```
某 provider 已配 key: "sk-真密钥"
用户打开设置页，只想改超时，密码框没碰，直接点保存
  → 前端送 api_key: ''        （含义："我没改它"）
  → 后端当普通值写入空串      （理解成"把 key 设成空"）  ← 反了
  → key 被擦掉，且界面显示"保存成功"
```

**例子 2：点清空 = 配置文件结构损坏**

```
用户点「清空」按钮
  → 前端送 clear: true              （一个 dict 对象）
  → `_to_stored_value` 当普通值处理
  → YAML 里写入：api_key: {clear: true}    ← 配置文件结构损坏
```

### 6.4 为什么叫「潜伏」

**因为现在还没有任何一个设置项开了 secret**：

```
settings_registry.py 72 处 _item() 调用 → 零个传 secret=True（已逐条 grep 确认）
```

所以**现在不会出错**。但这是个埋着的坑——以后有人给某个设置项加一行 `secret=True`，上面两个 bug **立刻生效**，且界面会自动显示"留空=保持原值"（`SettingRow.tsx` 走 secret 分支），**用户会被误导**。

**与第三章的关系**：同一个坑，已中一次、未中第二次。

| | 位置 | 状态 |
|---|------|------|
| 第三章 | `model_service.py:431` | **已实现**（key 就在用）→ 现行 bug，必须修 |
| 第六章 | `settings_service.py` 写路径 | **只预留字段、未实现** → 潜伏，尚未炸 |

修完第三章，key 写入路径就有三态了。第六章是同一件事在另一套系统里还没做。

> **v2.7 推翻重写**。原方案主张「留空=恢复默认地址，保留兜底 + 加提示」，**与北京老陈方案根本对立**。北京老陈主张：**URL 不能空 → 空是错误状态（红色提示）→ 保存就保存**。本章据其重写。

### 8.1 病根

**`base_url` 与同表单其它字段的留空语义相反**（`ProviderConfig.tsx:106-112`）：

| 字段 | 代码 | 留空语义 |
|------|------|---------|
| `api_key` | `:108` `if (apiKey.trim() !== '')` | **不修改**（保持原值） |
| `label` | `:110` `if (label.trim() !== '')` | **不修改**（保持原值） |
| `base_url` | `:109` `patch.base_url = baseUrl.trim()` | **清空**（无条件发送空串） |

**落盘确认**：`model_service.py:431` 空串通过（`'' is not None`）→ `api_base: ""` 写入配置（`:417` `key_map` 映射 `base_url → api_base`）。

**根子上的问题**：`base_url` **被设计成可空**，但它其实是 provider 的必要配置——没地址就无法调用。

### 8.2 现状：兜底机制是半成品

`client_sdk.py:304-312` `_default_base_url` 三段逻辑：

```
1. 读 get_config()["llm"]["provider_urls"][provider]   ← 自定义覆盖（可为空）
2. 回落 self._DEFAULT_URLS.get(provider, "")
```

`_DEFAULT_URLS` 的**全部内容**（`:298-302`）：

```python
_DEFAULT_URLS = {
    "deepseek": "https://api.deepseek.com",
    "qwen":     "https://dashscope.aliyuncs.com/compatible-mode",
    "ollama":   "http://localhost:11434",
}
```

**只有 3 个 provider 有地址**，其余（sensenova / glm / opencodeZen 等）**得空串**。

且 `client_sdk.py:268` 注释明写：

> "留空不填会向 httpx 传空 base_url（指向不存在的地址），**当前工作路径均不触发**"

→ **"默认地址"这套机制本身是半成品**：既不完整（只覆盖 3 家），也未被实际触发。**把"留空"解释为"恢复默认"是一个假便利。**

### 8.3 后果（准确版）

| provider | 清空 `api_base` 后实际行为 | 是否静默 |
|----------|--------------------------|---------|
| **ollama** | 变 `http://localhost:11434` | ⚠️ **静默**。远程 ollama 配的是 `http://192.168.x.x:11434`，清空后打向**本机**，请求自己的机器 |
| **deepseek / qwen** | 变硬编码官方地址 | ⚠️ **静默**。可能绕过用户想走的中转/代理，直连官方计费 |
| **sensenova / glm / opencodeZen** | 得**空串** → httpx 请求失败 | ✅ **会报错**，非静默 |

> 与第二章同一原则：**空就是空，不要瞎兜底。**

### 8.4 ⚠️ 对 v2.6 两处不实结论的纠正（小欧 2026-09-26）

**纠正一**：v2.6 写"清空后**静默改走官方直连**"，**表述过宽**。经核实（8.2/8.3），静默**仅 deepseek/qwen/ollama 三家**成立；sensenova/glm/opencodeZen 得空串会 fail-fast。且注释明写该路径"当前工作路径均不触发"。

**纠正二**：基于纠正一，危害范围大幅缩小，**级别由「中」降为「低」**。真正剩下的缺陷是**设计层**——`base_url` 被设计为可空，而它本应必填。

### 8.5 改法（**已定方案**，北京老陈 07:47）

**原则**：URL 是 provider 的必要配置，**不允许为空**；空即错误状态，明确报错，不做兜底。

**1. 加 Provider 时 base_url 必填**
- `ModelModals.tsx`（添加 Provider 弹窗）：base_url 输入框加必填校验，未填**不允许提交**
- 后端 `model_service.py` `add_provider`（`:396-409`）同步校验：`api_base` 为空 → 400，明确文案"api_base 必填"

**2. 回显：空 = 红色错误提示**
- `ProviderConfig.tsx`：检测 `config.api_base` 为空时，在输入框下方（复用 `:198-202` 的 `EXTRA_STYLE` 辅助文案行）显示**红色警示**：
  ```
  [ 空                                    ]
  ⚠️ URL 为空，此 Provider 无法调用（错误状态）
  ```
- **原样回显**——不做任何改写，用户填什么就显示什么（与 api_key 只显末 4 位不同，base_url 本身不是密钥，无需打码）

**3. 保存：空就拒绝**
- 前端 `doSave`：base_url 为空时保存按钮 **disabled 禁用**（v3.6 订正：原"不提交"+ 函数内静默 return 双保险中的后者是**死代码**——按钮禁用时点不到，已删；只留 disabled 一处把关），就地红字提示
- 后端 `update_provider_config`（`:412-442`）：收到 `base_url` 为空/纯空白 → **拒绝并报错**（400），不再"清空后照存"
  > 注意：与 `api_key` 的三态语义**方向相反**——`api_key` 空=不修改（第三章），`base_url` 空=**错误**（本章）。两者差异源于：`api_key` 允许"先建后填"，`base_url` 不可。

**4. 去掉兜底**
- `client_sdk.py:269` 的 `or self._default_base_url(llm_model.provider or "openai")` **删除**，改为：`_base_url` 为空 → **构造即报错**，文案"provider X 的 URL 为空，请到设置页填写"
- `_default_base_url`（`:304-312`）与 `_DEFAULT_URLS`（`:298-302`）**一并删除**（删后无人调用；`provider_urls` 自定义覆盖能力如有需要，应显式配置而非靠兜底）
  > **v3.5 实施记录（构造即报错的连带影响）**：构造即报错实测打死 **59 个无关单测**（`test_client_sdk_adapter` 22 + `test_tdd_*` 38 —— 它们以 `api_base=None` 构造 `LLMClient` 来测适配器/连接池/协议帧，与用户配置无关）。北京老陈裁定**坚持"构造即报错"**（8.7 验收要求"调用时明确报错"，构造时抛错更早暴露），并**改测试配合**：给这些测试的 `ModelRef` 补 `api_base="https://api.deepseek.com"`（显式表达"有地址"），使测试与被测契约一致。测试改动按项目铁律**不纳入本次提交**。
- `resolver.py:211` 的 `... or ai_service.llm_model.api_base`（回落到全局默认地址）**跨 provider 时删除**，避免跨 provider 时用别的 provider 的地址
  > **与第二章的同处改动（v3.0 审计补充，v3.6 修正确认）**：该行**同时被第八章与第二章要求删除**——第八章的理由是"不该用别的 provider 的地址"；第二章改为跨 provider 且 key 空白即报错后，这条 `or` 回落**在跨 provider 场景下同样不应再兜底**。但删除**仅限跨 provider**：实施中曾无条件删除，致**同 provider 内切换模型时 `api_base=None` → `LLMClient` 抛 400「URL 为空」、功能 100% 不可用**（已实测复现，属修 A 坏 B）。现按"是否跨 provider"区分：同 provider / 无覆盖沿用本代地址，跨 provider 留空即报错。两处**同一行、同一目的**，附录一已合并为一条（`resolver.py` 关联章标「二、八」），**实施时一次改掉，不可分两次改同一行**。

**5. 兼容历史坏配置**
- 若已有 provider 的 `api_base` 为空（手改坏 / 依赖过 ollama 兜底）→ 回显**红色提示**引导补填；调用时**明确报错**，不再静默指向 localhost 或官方地址
- 上线前需**先扫一遍现网配置**列出 URL 为空的 provider，并逐一确认其真实地址

- `_default_base_url` / `_DEFAULT_URLS` 全项目 grep → 零残留

## 第九章 全路由零鉴权（多人共用场景下的必做项）

**级别**：**高** | **状态**：**必做** | **部署前提**：**局域网多机共用 + 多人/半公开**（北京老陈 2026-09-26 08:01 确认）

> **v2.8 整章推翻重写，纠正小欧重大误判。**
>
> **误判**：v2.4~v2.7 建议「把 `--host 0.0.0.0` 改为 `127.0.0.1`」，理由是"同机使用不受影响"。该建议**基于"后端只在本机使用"的未确认假设**。北京老陈实际部署为**后端在 B 机器、局域网多机客户端访问**——若照此修改，**其他机器将全部无法连接，服务直接作废**。该建议**已撤回**。
>
> **纠正**：`--host 0.0.0.0` **必须保留**（多机访问的硬性前提）。真正的问题是**零身份验证**。

### 9.1 部署事实（本方案的前提）

| 项 | 事实 |
|---|---|
| 后端运行位置 | **B 机器**（非本机） |
| 客户端 | **局域网内多台机器** |
| 使用人数 | **多人 / 半公开** |
| 监听地址 | `--host 0.0.0.0`（`AGENTS.md:123`、`README.md:675`）——**多机访问必需，不可改** |

### 9.2 病根：门开着 + 没锁

| 项 | 事实 |
|----|------|
| 全局中间件 | `main.py:97-103` **唯一** `add_middleware` 是 CORS |
| 路由依赖 | 13 个 `APIRouter()`（`health`/`tool`/`chat`/`task`/`config`/`settings`/`model`/`sessions`/`messages`/`chat_execution`/`metrics`/`task_queries`/`token_usage`）**全部裸挂**，`Depends(` **零命中** |
| 鉴权代码 | `main.py` 无 `Security`、无 token 校验 |
| 前端 | `client.ts:77-86` 仅"若 localStorage 有 token 则附带"，**后端从不校验** |
| CORS | `main.py:97-103` `allow_methods=["*"]`、`allow_headers=["*"]`、`allow_credentials=True` |

→ **监听地址是"多人可达"的前提（合理），但没有任何身份验证是缺陷（不合理）。二者必须分开看。**

### 9.3 后果（多人场景）

局域网内**任何人的浏览器、任何程序**都能直接调用：

| 动作 | 接口 | 后果 |
|------|------|------|
| 读明文 key | `GET /api/v1/config/read` | **全部 provider 密钥被拿走**（见第五章） |
| 改 / 清空 key | `PUT /api/v1/providers/{name}` | **密钥被改或被擦除**，服务不可用 |
| 读配置结构 | `GET /api/v1/models` | 末4位、内网地址、模型清单泄漏 |
| 读写业务数据 | 消息 / 会话 / 任务等接口 | 越权访问他人会话与消息 |

**多人共用场景下，这不是"理论风险"**——同事浏览器装个插件、某个网页发个跨域请求，都可能命中。

### 9.4 「门开着」与「没锁」必须分开看

| 现象 | 性质 | 处置 |
|------|------|------|
| `--host 0.0.0.0`（多人可达） | **合理**——多机部署的硬性前提 | **保持不变，不可收窄** |
| 零身份验证（任何请求都放行） | **缺陷**——多人场景下无法区分"谁有权用" | **必须修**（见 9.6） |

> v2.4~v2.7 把这两件事混为一个"绑定问题"，并给出"收窄监听地址"的方案——**该方案在多机部署下有害，已撤回**（见本章开头误判声明）。

### 9.5 token 分发是什么（大白话说明）

> 本节为北京老陈 2026-09-26 要求补充的解释层。**token = 暗号，「分发」= 把暗号告诉需要用的人。** 没有更复杂的含义。

#### 9.5.1 token 是什么

**给这个服务设的一个"暗号"。知道暗号的人才能用，不知道的一律拒绝。**

```
请求带对暗号   → 放行，正常返回
请求没带/带错  → 401 拒绝（看不到、进不去）
```

暗号本身就是一个普通字符串（如 `omni-2026-abc`），存在配置文件里，服务端比对。

**为什么需要它**：现在局域网里任何设备都能连你的服务，能看你的密钥、能改你的设置。加暗号后，这些都被挡住。

#### 9.5.2 「分发」是什么意思

**把暗号告诉需要用这个服务的人。分发 = 告诉。**

你的实际情况：

| 谁 | 需要知道暗号吗 |
|----|--------------|
| 你的笔记本 | 要（你告诉它） |
| 你的手机 | 要（你告诉它） |
| 同事的电脑 | 要（你告诉它同一个） |
| 任何不知道暗号的人 / 任何自动运行的程序 | **不要，挡住** |

#### 9.5.3 最简单的四步操作

**第 1 步**：在设置里填一个暗号，比如 `omni-2026-abc`
（该字段存在配置文件里，你自己填一次即可）

**第 2 步**：别人打开网页时，弹一个框让他输暗号

```
┌─────────────────────────┐
│  请输入访问口令          │
│  [________________]     │
│         [ 进入 ]         │
└─────────────────────────┘
```

**第 3 步**：输对了就记住（存在浏览器 localStorage），以后不用再输；输错或压根没输，就是进不去

**第 4 步**：暗号泄露了怎么办 → **你在设置里改成一个新暗号，所有旧暗号立刻作废**

#### 9.5.4 实际使用效果

| 场景 | 结果 |
|------|------|
| 你的电脑输对暗号 | 正常用 |
| 同事输对暗号 | 正常用 |
| 同事浏览器里的恶意插件想偷密钥 | **被挡住**（没有暗号） |
| 某个网页偷偷发跨源请求 | **被挡住**（没有暗号） |
| 你的暗号被别人知道了 | 你改暗号 → 别人的旧暗号**立即失效** |

#### 9.5.5 成本

- **后端**：新增一个校验暗号的依赖（见 9.6 第 1 条）
- **前端**：加一个"输入暗号"的页面（`client.ts` 已具备带 token 的逻辑，需核实）
- **必须同步做**：项目里 **76 个后端 E2E + 8 个前端 E2E = 84 个自动化测试**都要带上这个暗号才能跑通，否则全部 401 失败。改的地方只有两处（`e2e_helpers.py` 与 `api-proxy.ts` 统一注入），但**这一步不能漏**。

#### 9.5.6 其它分发方式为何不选

| 办法 | 做法 | 问题 |
|------|------|------|
| 后端某接口直接返回暗号 | 调一下就拿到 | **等于没有鉴权**——任何人都能调这个接口拿到暗号 |
| 让人手工改配置文件 | 每人手动改 `config.yaml` | 易改坏配置，还涉及文件权限 |
| 打开网页自动放行 | 不要暗号 | **等于没做鉴权** |
| IP 白名单 | 配置允许的 IP 段 | 换 WiFi / 换设备就进不去 |

**结论：用登录页让用户输入暗号**——门槛低（粘一下）、真起效（服务端真校验）、不改配置文件、泄露可换。

### 9.6 改法：加 token 鉴权（唯一正解）

> **不动的部分**：`--host 0.0.0.0` 保持（多机必需）、CORS 保持（前端跨源访问必需）、第五章明文显示保持（见 9.7 逻辑）。

**1. 后端：统一鉴权依赖（DRY，不逐路由重复）**

- 新增 `app/api/v1/deps.py`，实现一个 `Depends` 鉴权依赖：校验请求头 token，失败返回 401
- token 存于服务端配置（如 `security.api_token`），支持从环境变量读取（便于多机部署时统一配置）
- **挂载方式**：在 `main.py` 用 `_mount()` 唯一入口挂载（v3.6 订正：原写"逐行 `include_router(..., dependencies=[Depends(verify_token)])`"；现前缀与"默认鉴权"只写一次，豁免须显式 `exempt=True`，新增 router 自动获得鉴权，杜绝"忘记手写 dependencies"致裸奔）
- **豁免项**：`/api/v1/health` 建议豁免（便于探活与排障），其余全部需鉴权

**1.5 豁免范围（v3.5 实施补齐 —— 北京老陈要求"本机和白名单豁免"）**

> 原设计 9.6-1 只写「`/api/v1/health` 建议豁免，其余全部需鉴权」。实施后经北京老陈确认，
> **补充本机与白名单豁免**（"每一个访问链接都要登录"在局域网多机场景下不现实）。

| 请求来源 | 是否需口令 | 配置位置 |
|---------|-----------|---------|
| **本机回环**（`127.0.0.0/8`、`::1`） | **豁免** | 恒生效，无需配置 |
| **IP/CIDR 白名单内** | **豁免** | `security.ip_allowlist`（设置页「外观 → 登录与准入」组可维护）或环境变量 `OMNIAGENT_IP_ALLOWLIST` |
| 白名单之外的**任何**客户端（同网段其他机器、外网） | **需口令** | — |
| `GET /api/v1/health` | 豁免（9.6-1 探活要求） | — |
| `POST /api/v1/echo` | 豁免 | 随 health router 一并豁免（无业务逻辑、不碰配置与密钥）；**v3.5 实施时发现此项超出原设计，此处显式记录** |
| `GET /api/v1/auth/status`、`POST /api/v1/auth/token` | **未配置口令时**豁免（首次设置自举）；已配置后需口令 | 见 2.5 |

⚠️ **风险边界（必须记录）**：
- **白名单内等于无鉴权** —— 可读全部 provider 明文密钥、可改可擦。只应放**可信设备网段**，且范围越小越好。
- `X-Forwarded-For` **默不采信**（可被客户端伪造，采信它等于让攻击者冒充白名单 IP 绕过鉴权）；
  仅当显式设 `TRUST_PROXY_HEADERS=1` 时才采信（仅用于确实部署了受信反向代理的场景）。
- 白名单条目**写错格式一律不放行**（fail-closed），不会因配置写错而全站放行。



**2. 前端：token 注入**

- `client.ts:77-86` 已有"若 localStorage 有 token 则附带"的逻辑，需**核实其是否真的在发**（本次核实只确认了"后端不校验"，前端是否正确发出需实施时复核）
  > **v3.5 实施核实结论**：该逻辑**已存在且真实生效**（`getAccessToken()` 读 `omniagent_auth`，request 拦截器确实附带 `Authorization: Bearer`；401 亦已跳 `/login`）。本次只补 `setAccessToken()`（登录页写入用，与读取结构对称）。
- 补充：token 获取入口（登录页 / 首次配置输入），存入 localStorage
- 若 token 失效（401），前端应跳登录页而非静默失败

**2.5 口令在哪里设置（v3.5 实施补齐 —— 原设计缺此项会导致死锁）**

> **实施中发现的设计缺口**：9.5.3 第 1 步要求"在设置里填一个暗号"、9.8 也列了"新增 `security.api_token` 配置项"，
> 但**实施前该键既未注册到 settings registry、前端也无任何设置界面**。结果是：后端挂上鉴权后，
> 用户被 401 跳到登录页，却**既不知道口令是什么、也不知道在哪设** → **死锁**（无口令进不去，无入口设口令）。
> 经北京老陈裁定：**注册为 secret 项 + 设置页可改**。落地如下：

| 项 | 落地 |
|----|------|
| 配置项 | `settings_registry` 新增 `security.api_token`（`secret=True` + `env_key=OMNIAGENT_API_TOKEN`），落在「外观」组最前（v3.6 订正：原写「安全」组有误；安全组只留 4 项操作安全，准入项在外观组「登录与准入」块） |
| 读路径 | 走既有 `mask_secret_value` → **永不回明文**（设置页只显示"已配置"与掩码） |
| 写路径 | **唯一权威 = 专用端点** `POST /api/v1/auth/token`（与 provider 通道同构）；settings 通用通道按第六章方案 B **显式拒绝**写 secret 项 |
| 自检登记 | `security.api_token` 登记进 `_SECRET_WRITTEN_BY_PROVIDER_CHANNEL`（第六章防半吊子自检），否则注册表**拒启** |
| 首次设置豁免 | `deps.verify_token`：**未配置**口令时对 `/auth/status`、`/auth/token` 放行（否则死锁）；**已配置**后不再豁免（改口令须持当前有效 token，防局域网内抢占） |
| 状态查询 | `GET /api/v1/auth/status` → 只回 `configured` + 掩码 + 配置键名/环境变量名（**不回明文**） |
| 关闭鉴权 | **不提供**"清空口令"入口（清空=全站失守，属部署级操作）：后端拒空口令，前端「清空」按钮前置拦截并指引用 `OMNIAGENT_REQUIRE_AUTH=0` |
| 前端 | 登录页进页先查 `auth/status`：**未配置**时显示明确指引，并支持"输入即首次设置"（一次输入即完成设置与进入）；设置页「外观 → 登录与准入 → 访问口令」可随时改（9.5.3 第 4 步"泄露可换"；v3.6 订正：原写「安全 → 访问口令」有误，该键在外观组） |

**3. E2E 统一注入（工作量最大的前置）**

- 76 个后端 E2E + 8 个前端 E2E 的**所有请求**都要带 token
- 统一在两处注入，不逐个用例改：
  - 后端：`e2etests/e2emodel/e2e_helpers.py` 的 HTTP 调用封装处统一加 header
  - 前端：`e2e_front_lib/` 与 `e2e_case/api-proxy.ts` 统一转发时注入
- **不做这一步，全量测试会 100% 失败**（401）

**4. 部署配套（多机场景）**

- token 需分发给各客户端；建议提供**简易登录页**而非让用户手工改 localStorage
- token 泄露时的轮换手段（改配置即轮换）

### 9.7 与第五章的关系（逻辑链）

```
第五章「配置明文可接受」的前提 = 只有你能访问
        ↓
第九章加 token 鉴权
        ↓
只有持 token 者能调接口
        ↓
前提恢复成立 ✅ → 第五章保持明文不改
```

**结论：鉴权是第五章"明文可接受"的前置条件，而非替代。** 二者不冲突，是先后关系。

# 三、新增功能

## 第十章 功能：key 正确性检测（测试连接）

**类型**：新增功能（非缺陷） | **实施顺序**：待定

### 10.1 现状：能力已存在，但不能直接用

**没有**"检测 key"的按钮。核实：`ModelLibraryTab.tsx:141` 调 `fetchRemoteModels`，目的是**拉模型列表**，不是**验证 key**。

但底层探测能力已具备：

```
model_service.py:537   api_key = os.environ.get(f"{name.upper()}_API_KEY") or str(p.get("api_key") or "")
model_service.py:538   headers = get_provider_adapter(name).static_headers(api_key)
adapters/base.py:17    return {"Authorization": f"Bearer {api_key}"}
model_service.py:488   await client.get(f"{api_base.rstrip('/')}/models", headers=headers)
```

→ 带真实 key 请求远端 `/models`，**这本身就是一次 key 有效性探测**。

### 10.2 病根：直接复用会误报

| # | 障碍 | 代码 | 后果 |
|---|------|------|------|
| 1 | status_code 丢失 | `model_service.py:543-552` `_fail()` **远端失败统一 HTTP 200 + ok:false** | 调用方拿不到状态码 |
| 2 | status_code 只进文案 | `_parse_remote_models_body:497-509` `message = f"HTTP {resp.status_code}"` 拼进字符串即丢 | 无法程序化区分错误类型 |
| 3 | **无错误分类** | 同上 | 401 / 404 / 超时 全变成同一句话 |

**第 3 条最要命**：部分 provider 的 `/models` 端点不存在或路径不同，若拿 404 判"key 无效"→ **给用户误报**。用户会反复改 key，浪费排查时间，且**可能把本来正确的 key 改坏**。

### 10.3 改法

**后端：先补错误分类（前提）**

- `fetch_remote_models` 的失败返回增加 `status_code` 字段，`_fail()` 增加该参数（`:543-552`）
- 增设分类判定：

| 分类 | 触发 | 含义（**注意第 3 行不能判 key 无效**） |
|------|------|------|
| `ok` | 2xx | key 有效 |
| `key_invalid` | **401 / 403** | key 无效或无权限 |
| `endpoint_unsupported` | **404 / 405 / 501** | 该 provider 无 `/models` 端点 → **key 可能是对的，不得判其无效** |
| `network_error` | 超时 / 连接失败（含 `500/502/503` 等服务端错误与未知状态码，v3.6 补：实现按"非 2xx 非 401/403/404/405/501 一律归网络问题"，前端按地址问题提示并附后端原文） | base_url 或网络问题，与 key 无关 |

- **两个维度必须分开报**：
  - **base_url 通不通** —— 连不上 → 地址写错或网络不通
  - **连上后 key 对不对** —— 401 → key 写错
  → 若一律提示"连接失败"，用户无法判断该改地址还是改 key，等于没说

**支持测未保存的 key（建议）**

- 新增参数允许传入待测 key（不入库、仅本次探测）
- 理由：用户**正在输入框里新输 key** 时是"保存前验证"的最自然场景；若只能测已保存值，验证时机太晚
- 注意：传入的 key 走内存即可，**严禁落盘、严禁进日志**
  > **v3.5 实施决策（传参方式）**：采用 **`POST /providers/{name}/test-connection` + body 传 key**，**不用 GET query** ——
  > GET 的 query 会进 **uvicorn access log**（服务器日志留下明文 key）并进浏览器历史，直接违反上一条"严禁进日志"的硬要求。
  > 端点内部**复用 `fetch_remote_models(name, probe_key=...)`** 的探测能力，不新造第二套探测逻辑（DRY）。

**前端**

- `ProviderConfig.tsx` 加"测试连接"按钮，按上述分类给**不同**提示文案（不得统一显示"失败"）
- 明确区分"地址问题"与"key 问题"两套文案

**安全前提（必须先确认）**

- `model_service.py:490` `logger.error(f"拉取失败: {e}")` 把 httpx 异常**原样打进日志**
- **该异常字符串是否回显请求 header，尚未实测**，不能假设安全
- 做本功能前**必须先实测确认**：若会回显，须先过滤再落日志，否则"测试连接"本身会成为泄露点

### 10.4 涉及文件

`backend/app/services/model/model_service.py`（分类 + `probe_key` + `get_provider_raw_entry` 明文取数公开入口）、`frontend/src/features/settings2/components/ProviderConfig.tsx`（表单本体）、`frontend/.../TestConnectionProbe.tsx`（v3.6 补：测试连接按钮与分档文案已从 ProviderConfig 拆出为独立组件，SRP）、`frontend/src/services/api/model.api.ts`（`testConnection`/`getApiKeyPlain`）

### 10.5 验收

- 有效 key + 正确 base_url → 提示"连接成功"
- 无效 key → 401 → 提示"key 无效或无权限"（**不提示"测试连接失败"**）
- 有效 key 但该 provider 无 `/models` 端点 → 404 → 提示"该 provider 不支持模型列表检测，key 未验证"（**不得说 key 无效**）
- base_url 写错 → 超时/连接错 → 提示"无法连接，请检查 base_url"（**不得说 key 有问题**）
- 日志中**不含**明文 key

### 11.1 病根

第三章只修了 `model_service.py` 的 `update_provider_config` 一处。但**同一条链路上还有第二个能擦掉密钥的入口**——旧通道 `PUT /api/v1/config` 的 `provider_api_keys` 字段，它同样**不做空串保护**。

**完整调用链（三遍核实，逐步确认）**：

```
PUT /api/v1/config                          config_routes.py:82-83
  → update_config_service(config_update)    config_routes.py:84
  → config_service.py:81  update_config()   config_service.py:81
  → handler map 键 "provider_api_keys"     config_helpers.py:452
  → _update_api_keys()                      config_helpers.py:411-417
      config_data['ai'][provider]['api_key'] = api_key.strip()   ← :414
```

**关键点**：`:414` 的 `api_key.strip()` 作用是**去空格**，**不是空串保护**。传入 `""` 或纯空白 → `.strip()` 得 `""` → **照样写入配置，照样清空密钥**，且该函数 `:415` 还会 `logger.info("更新Provider API Key成功")` —— **擦掉密钥还记成功日志**。

与第三章 `model_service.py:431` `if k in key_map and v is not None` 是**完全相同的缺陷**（空串非 None 就写入），只是发生在另一个入口。

**v2.2 结论升级**：该缺陷所在的整条 `PUT /config` 写端点**已是纯死代码**（11.2），因此正确处置是**整条删除**而非"补保护后保留"——补保护只是 v2.1 的保守方案，删除后不需要再补。

# 五、新增功能（二）

## 第十二章 功能：key 显示「前 4 位 + 后 4 位」+ 眼睛按钮切换明文

**类型**：新增功能（非缺陷） | **来源**：北京老陈 2026-09-26 07:29 新增需求
**实施顺序**：**待定**（明文接口须待第九章第一步落地后方可上线）

### 12.1 需求（北京老陈原话）

> 「对 api_key 不空、就是有 key 的时候，key 的显示前面 4 个字符串 + 后面 4 个字符串。在你的基础上再加一点需求：回显的时候这样显示，用眼睛按钮切换隐藏和真实。」

**三项决策（已定）**：

| # | 事项 | 裁定 |
|---|------|------|
| 1 | 眼睛切换要不要二次确认 | **要确认 + 30 秒自动恢复** |
| 2 | 前 4 位泄露（泄露面 4 位 → 8 位） | **接受**（前 4 位多为 `sk-1`/`sk-p`，泄露价值低） |
| 3 | 与第九章的先后 | **先写文档，实施时再定**（明文接口须待第九章第一步落地） |

### 12.2 目标效果

```
平时（打码）:  [ sk-1**********7890  ] 👁     ← 前 4 + 后 4
点眼睛:        [ sk-1234567890abc     ] 👁     ← 明文
再点眼睛:      [ sk-1**********7890  ] 👁     ← 恢复打码
30 秒后:       自动恢复打码
env 接管时:    整块只读，不显示（维持现状，见 5.x env 分支）
```

### 12.3 现状与两个技术前提（核实结论）

**前提一：前 4 位后端根本没返回**

```
现返回:  { "configured": true, "suffix": "7890" }        ← config_helpers.py:611-617
                                        ↑ 只有末 4 位
目标:    { "configured": true, "prefix": "sk-1", "suffix": "7890" }
```

必须扩 `mask_secret_value`（`config_helpers.py:611-617`）增加 `prefix` 字段。

**前提二：明文前端从未持有**

打码态前端有数据（末4位），但**真实明文前端从来没有过**——`get_models`（`model_service.py:179`）只返掩码。要切换显示真实值，**必须后端新开接口**传明文。

### 12.4 两个实现坑（识别于设计阶段，须在实施时处理）

**坑 1：双眼睛冲突**

`ProviderConfig.tsx:187-195` 现用 AntD `Input.Password`，其内置"眼睛" toggle（`:193` `autoComplete`、默认 `visibilityToggle`）作用是**显示用户刚输入的字符**——因为输入框初值恒为 `''`（`:87`），它**看不到已保存的 key**。

若再加一个"看已保存明文"的眼睛，会出现**两个眼睛按钮**，用户无法分辨。

- **处理**：`Input.Password` 设 `visibilityToggle={false}` 关闭自带眼睛，改用**自定义眼睛**，明确职责：
  - **自定义眼睛** = 查看**已保存**的密钥（本章新增，走后端接口）
  - 若还需查看刚输入内容，靠 `autoComplete="new-password"` + 选中即全选替代，或保留自带 toggle 但在其旁加文字说明"（仅显示本次输入）"

**坑 2：短 key 前后缀重叠**

`mask_secret_value:617` 现有规则是 `len(s) >= 4` 才给 `suffix`，否则置空。加 `prefix` 后需明确短 key 行为：

| key 长度 | 现状 | 本章须定 |
|---------|------|---------|
| ≥ 8 位 | 显示 prefix+suffix | `prefix` 前 4 + `suffix` 后 4，**不重叠** |
| 4~7 位 | 只给 suffix | **只给 suffix，prefix 置空**（否则 `12345` → prefix=`1234`、suffix=`2345`，中间 3 位重复展示，等于泄露 7/8 位） |
| < 4 位 | suffix 置空 | 维持（`configured: true`、`prefix`/`suffix` 均 `""`） |

> 注：`len(s) >= 8` 判定须在实现时用测试锁住，避免后人改回 `>= 4` 导致短 key 泄露。

### 12.5 改法

**后端**

- **扩掩码结构** `config_helpers.py:611-617` `mask_secret_value`：
  - 已配 key：返回 `{configured: true, prefix: s[:4], suffix: s[-4:]}`，**但仅当 `len(s) >= 8`**
  - `4 <= len(s) < 8`：返回 `{configured: true, prefix: "", suffix: s[-4:]}`
  - 未配：`{configured: false, prefix: "", suffix: ""}`（**三键恒定**，与第七章 7.3「形状恒定」同一目标）
  - 与第七章同批改，避免同一函数改两遍
- **新增明文接口** `model_routes.py`：`GET /api/v1/providers/{name}/api-key`，返回 `{"provider", "api_key": "<明文>", "configured"}`（v3.6 订正：原写单字段已过时；取数经 service 公开函数 `get_provider_raw_entry(name)`，路由层不直调 `_raw_ai` 私有函数）
  - **必须记审计日志**：provider 名、时间戳、来源 IP（`request.client.host`）——读密钥属敏感操作
  - **env 接管时一律拒绝返回明文**，文案"该 provider 由 {NAME}_API_KEY 环境变量接管，密钥不在配置文件中，无法查看"
    > 理由：env 优先消费（`config.py:112`），YAML 里那个可能**不是生效值**，给用户看是假象——与第二章"静默回落"同类陷阱
  - env 判定为路由内联实现（v3.6 订正：原写"复用 `model_service.py:176`"不准确——审计要来源 IP，只能在有 request 的路由层做；取数部分复用 service 公开函数 `get_provider_raw_entry`）
- **前端类型** `model.api.ts:34`：`api_key` 加 `prefix: string`，与后端形状对齐

**前端** `ProviderConfig.tsx`

- 默认显示 `sk-1**********7890`（由 `prefix` + 打码 + `suffix` 拼接）
- 自定义眼睛按钮 → **二次确认弹窗**（"将显示明文密钥，请勿截图或分享"）→ 调接口 → 明文填入输入框（v3.6：该块已拆为 `SecretRevealInput` 独立组件，见 12.7）

- env 接管时按钮不显示（整块只读，`:128-154` 早退逻辑已覆盖）

**明确不做**：不提供"永久显示""导出密钥文件"；不做"记住我的选择"（不能关掉自动恢复）。
