## 一、目标与约束

**一句话（目标）**：全仓事件（暂停+普通）统一经一个发射口 `publish` 进入 event_log，暂停时序由原语实现保证、不由调用方代码位置保证；yield 只保留 LLM 数据流一途（判定规则见1.1.2）；本阶段先实施。

**三条约束（需求）**（不可谈判，统一publish后的保证方式随节落定 — 小健-2026-09-05）：
1. paused必须在阻塞等待前到达前端（确认弹窗），resumed在恢复瞬间到达—— functional correctness，不可谈判。**保证方式**：由"调用publish的时刻"直保——网关内部固定顺序 `publish(paused)→wait→publish(resumed)`（构造保证），不再依赖yield写在await之前的代码位置（1.1.2路径1）。
2. event_log append-only + seq语义不动（断线重连/回放依赖，见agent_runner.py行199-210持锁模板）。**保证方式**：publish复用_append持锁模板（行199-210），只换发射入口、不换event_log语义。
3. agent_runner通道路由表语义不动（thought仅落库；thought-start、chunk、startinfo及通知类 error/usage/paused/resumed/retrying/cancelled 仅SSE；action/final/final_stats/其余 落库+SSE双写，见agent_runner.py行307-362）。**保证方式**：路由收敛为一张EVENT_ROUTE表（位置集中，语义等价）；"发射"上移到发射点publish、"路由+落库"留在agent_runner（角色变化见1.1.2 agent_runner角色段）。

**总判据（判定规则，一句话）**：
- yield 的产物是"要进 event_log 的 Step 事件" → publish 取代它；
- yield 的产物是"LLM 流式数据块（StreamChunk）" → 保留 yield。
（完整判定规则与路径1/路径2二分详述见1.1.2）

### 1.1 方案定稿：统一publish总线（核心设计 + yield二分法则，v1.2.21重写定稿 — 小健-2026-09-05）

#### 1.1.1 核心矛盾

**核心矛盾**：handler是async generator，"阻塞前先发射paused"依赖yield写在await之前的代码位置——这是三宗时序风险（位置耦合/双paused/事后补发）的唯一根。发射通道只有两类本质：**点发式**（publish，调用时刻即落event_log，时序与代码位置解耦）与**路过式**（yield，多跳透传，时序看位置）。本设计定稿：**全仓事件只走一个发射口 publish，发射面 yield 退役（数据流 yield 保留）**。

#### 1.1.2 yield 二分法则（全仓判定规则，定的死）

> **判定规则**：yield 的产物是"要进 event_log 的 Step 事件" → publish 取代它；yield 的产物是"LLM 流式数据块（StreamChunk）" → 保留 yield。publish 与 yield 职责不同、不并存、不混用。

**路径1：事件发射 yield → 全部退役（publish 取代）**。凡是 `yield emit(XStep)` 或 `yield event`（把下层事件再上送），都是"把 Step 事件送进最终 event_log"的运输通道——正是"时序看位置"的病根：真正落 event_log 的时刻取决于各层 `async for` 消费时机，而暂停事件正确性要求"发射在 wait 之前"，该依赖太脆弱。publish 在"构造时刻"写死 event_log，时序=调用时刻：

| 层 | 现状写法 | 统一publish后 |
|------|----------|--------------|
| handler（answer/action/safety/sandbox） | `yield agent._step_emitter.emit(XStep)` | 纯函数 `return list`，dispatch 统一 `await publish(each.to_dict())` |
| react_step（消费LLM后产元事件） | `yield emit(MetaStep(...))`等 | `await publish(emit(X).to_dict())` |
| react_step→dispatch（react_step.py L461 调 `_dispatch_handler`） | `async for event in _dispatch_handler(...): yield event` | `await`拿list→逐个publish |
| react_loop（start/final/重试/兜底） | `yield emit(...)` / `for _s in emit_final_with_stats: yield _s` | `await publish(...)` |
| base_agent 纯透传 | `async for event in _run(...): yield event` | 逐层透传链删除（发射点已下沉） |

**路径2：LLM 数据流 yield → 保留（publish 不取代）**。产出是 LLM 原始流分块（StreamChunk）：**不落event_log、不进路由表、不喂前端SSE**，只流式喂给 react_step 消费增量处理（chunk_buffer.append、首token标记）；它没有"必须在 await 之前到达"的时序依赖——chunk 顺序由 LLM 流本身保证。publish 是 event_log 的门，StreamChunk 不该进门，所以 publish 管不到它：

| 位置 | 现状写法 | 结论 |
|------|----------|------|
| llm SDK层 | `async for chunk in agent.llm_client.request_stream(...)` | **SDK接口天生就是异步迭代，publish 取代不了** |
| call_llm_stream / call_llm_with_fallback 出口 | `yield` 元组/response 混出 | 保留——数据管道，非事件（出口统一 `yield StreamChunk`） |

**边界厘清：chunk 的双重身份（最容易混的点）**：

```
LLM流 ──yield StreamChunk──▶ react_step 消费
                              │
                              ├─ 数据流身份：chunk_buffer.append / 首token标记   ← yield（保留）
                              └─ 事件身份：构造 ChunkStep ──await publish──▶    ← publish（取代原yield emit）
```

LLM层那个yield（call_llm_stream出口）=数据块，保留；react_step里那句 `yield emit(ChunkStep)` =事件发射，改 `await publish`。

**agent_runner 角色变化（约束3落地形态）**：现状 `async for event in run_react_cycle` → 按路由表 `_append`（写event_log+推SSE）+ `_persist`（写DB）。统一后 **主循环事件转发退役**（事件经 publish 直写 event_log，不再经 handler yield 透传）；agent_runner 改从 event_log 消费，按路由表（约束3）仍执行 **SSE 推送（含 final/final_stats 延迟补发、startinfo 合成）与 DB 落库 _persist** + 终态记账（_has_chunk_steps/_action_steps/current_content）。路由表语义不动（约束3），发射职责上移到发射点、路由与落库职责留在 agent_runner。

#### 1.1.3 候选方案对比（分析汇总）

| 方案 | 做法 | 发射机制 | 解决什么 | 遗留/代价 | 结论 |
|------|------|---------|---------|----------|------|
| A：统一暂停源头（混合） | 暂停事件走publish直写event_log，普通事件仍走yield | publish+yield 两套 | 三宗时序风险 | **yield链仍靠代码位置**（其他事件仍脆弱），两套机制并存，不是干净终态 | 排除 |
| **B：统一publish总线** | **所有事件（暂停+普通）统一publish直写event_log，发射面yield退役（数据流yield保留）** | **publish 一套** | 全部时序风险 + 架构清理 | 动agent_runner主循环（删_append双路由），路由表位置让位、语义保留 | **采纳** |
| C：只纯函数化不做publish | handler改async函数，无publish通道 | 无 | generator脆弱 | **没有publish通道，暂停事件无处发出，行不通** | 排除 |
| D：不改架构加固现有代码 | 不加publish不加网关，局部加固 | yield | 表面 | 治标不治本，位置耦合是架构缺陷，下次重构必重蹈 | 排除 |
| E：完整事件总线（pub/sub等） | 订阅/滤波/重放全套 | — | 过度 | YAGNI，改动面过大，当前不需要 | 排除 |

#### 1.1.4 采纳方案B：统一publish总线

**采纳理由**（老陈2026-09-05定案"最后统一：直接上统一publish"）：

1. **单一发射点**：不再有yield链，时序由调用时刻保证——"调用publish的时刻就是事件落event_log的时刻"，三宗时序风险连根拔除。
2. **架构干净**：handler返回list，事件经publish直写event_log；agent_runner从event_log消费、查一张EVENT_ROUTE表完成路由（SSE推送/DB落库/双写），删事件转发入口（_append双路由）。
3. **防止未来bug**：新事件类型自动获得时序保证，不再有"yield写在哪"的心智负担。
4. **每个改动更简单**：return list比yield更直观，generator的禁return值/输出参数透传（_verdict/_result_out/_emit_events）一并作废。

#### 1.1.5 统一后三件事各自归一

（不是"几种发射模式"，是三件不同的事）：
- 发射（事件怎么进event_log）：**一个publish**——调用那一刻即落event_log，无中间跳；
- 路由（哪些落库/哪些仅SSE）：**一张EVENT_ROUTE表**——thought仅落库；thought-start、chunk、startinfo及通知类（error/usage/paused/resumed/retrying/cancelled）仅SSE；action/final/final_stats/其余 落库+SSE双写（语义同agent_runner行307-362，收敛一处不散落）；
- 暂停时序（paused先于等待/resumed恢复瞬间）：**一个网关**——hitl_gateway 内部固定顺序 `publish(paused)→wait→publish(resumed)`，构造保证，调用方挪不动。

以上四件事（yield二分法则、候选对比、采纳理由、三件事归一）共同构成第一章的完整定稿口径：**发射统一publish、路由统一EVENT_ROUTE表、暂停时序统一网关、yield只留数据流一途**。

> **口径定死（v1.2.21 起承接）**：凡曾出现的"方案A＋方案B组合"表述一律作废，统一以本定稿"统一publish"口径为准。

### 1.3 实施/优化方法概要（路径1、路径2 的处理方法与代码范围 — 小健-2026-09-05）

**yield 二分法则（定死）**：
  [1]yield产物"要进event_log的Step事件"→publish取代（路径1）；
  [2]产物"LLM流式数据块StreamChunk"→保留yield（路径2）。
  [3]publish与yield职责不同、不并存、不混用

**总体次序**：先路径1的暂停发射链路（网关+发布，约束1/2/3 直保），再全体"事件发射 yield 退役"；路径2 协议统一与其同步收口；每步按 TDD 红→绿推进，可落盘 diff 见实施清单（v1.2.21 起按本口径修订）。

- **处理方式**：把"构造 Step→yield 上送"改为"构造即 publish（`await publish(step.to_dict())`）"，时序=调用时刻，与代码位置解耦。

  2. `safety_gate.py` / `sandbox_gate.py`：暂停对（paused/resumed，确认通道 #1-#4）按第 0 项改调网关、由网关固定顺序 publish；其余普通事件列表改经 dispatch 统一 publish——safety_gate 6 处 `yield emit(MetaStep)` + 3 处 `yield _st` 转发（L143/207/228）消除；sandbox_gate 已是纯函数返回 Step 列表（L78/106/125/132，无 yield），形态不动；

  4. `react_step.py`：`yield emit(MetaStep(...))` → `await publish(emit(X).to_dict())`；

**路径2：LLM 数据流 yield 保留 → 统一出口协议**（处理"数据管道"一条链）

- **处理方式**：不动 async generator 流式迭代本质，只统一出口为 StreamChunk 单协议。
- **处理的代码范围（3 个文件，数据链路 — 小健-2026-09-05）**：

1. **位置耦合**：paused正确性依赖"yield写在await之前"的手工顺序，任一重构挪行即违法序（如[5]v1.4曾误删paused改经_emit_events致弹窗迟到，[5]5.2.6有载）。

3. **事后补发诱惑**：任何把paused收进列表事后emit的方案都直接违法序（弹窗迟到）。

## 三、StreamBuffer.publish 概要设计

**一句话**：publish是全仓事件（暂停+普通）进入event_log的唯一入口——"调用它的时刻就是事件落event_log的时刻"，时序由发布动作保证，不由yield代码位置保证。本文档所有事件以此为准（1.1定案统一publish，v1.2.21起七章diff按此口径重写）。

### 3.1 为什么用 / 解决什么问题（2.3三宗时序风险）

暂停事件（paused/resumed）必须进event_log才能经SSE到达前端。现状发射靠generator `yield`"路过即发射"，yield必须手工写在await之前，代码位置一挪即违法序——这正是2.3三宗时序风险的共同根源。publish把"发射"从隐式路过改成显式调用：

| 问题（2.3） | 现状根因 | publish解决 |
|------|--------|-----------|
| 位置耦合 | 时序靠"yield写在await之前" | 时序靠"调用publish的时刻"，与代码位置无关 |
| 嵌套裁决双paused | 主路/sandbox各自yield各自的 | 统一收编网关，publish单一入口发paused |
| 事后补发诱惑 | 先把paused收进列表、事后才emit | 调用即落event_log，无从延迟补发 |

### 3.2 如何用（接口契约与调用时机）

- **签名**：`async def publish(step_dict: dict) -> int`；入参为完整Step的dict（先`to_dict()`再publish）；返回该事件分配到的seq。
- **动作**：分配seq + append event_log + 持锁`notify_all`，复用agent_runner._append持锁模板（行199-210），不另起队列、不动event_log语义（约束2）。
- **时机**：网关阻塞前`await publish(paused.to_dict())`、恢复瞬间`await publish(resumed.to_dict())`（见4.2行171/177）；普通事件由dispatch中枢统一`await publish(each.to_dict())`（v1.2.21起7.7按此改造），不再有"普通事件走yield透传"（1.1定案：发射面yield退役、数据流yield保留）。
- **注入**：publish由调用方注入`buffer.publish`，与`agent_streams.get(task_id)`同源；任务运行中buffer必存在（create_stream_buffer于任务启动时创建），None防御落盘时加。

### 3.3 有什么价值

1. **约束1（paused先于等待、resumed恢复瞬间）由发布时刻直保**：是"阻塞前调/恢复瞬间调"这个调用顺序的必然结果，不再依赖手工yield位置。
2. **单写**：全仓事件（暂停+普通）只从publish一个入口进event_log，位置耦合/双paused/事后补发三宗时序风险同根消失（ISS-004同根），无双发面。
3. **零侵入**：不动agent_runner路由表语义（约束3：thought仅落库/thought-start与chunk仅SSE/其余双写），路由收敛为一张EVENT_ROUTE表（位置集中，语义等价），event_log/SSE/DB/前端零改动（v1.2.21起7.x按此重写）。
4. **统一总线的一部分**：暂停事件与普通事件共用publish一个发射口，handler不再靠yield发事件，可纯函数化（见五章）。

### 3.4 如何体现在本文档

| 本文档位置 | 体现 |
|------|------|
| 二章2.3 | publish要消灭的三宗时序风险（问题清单） |
| 4.2 网关骨架 | `await publish(paused.to_dict())` / `await publish(resumed.to_dict())` 两处调用 |
| 七章7.2 | task_state.py publish方法落地diff（9.1清单#2） |
| 七章7.3/7.4 | sandbox/safety两侧暂停事件收编经publish |
| 七章7.5/7.6 | handler纯函数化后暂停事件经publish、普通事件仍yield |
| 七章7.7 | 驱动改await消费dict，状态推断输入改为dict+verdict |
