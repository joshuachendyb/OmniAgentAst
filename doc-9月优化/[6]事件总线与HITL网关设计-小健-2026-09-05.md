# 第一部分  需求和问题的分析

## 一、目标与约束

**一句话（目标）**：全仓事件（暂停+普通）统一经一个发射口 `publish` 进入 event_log，暂停时序由原语实现保证、不由调用方代码位置保证；yield 只保留 LLM 数据流一途（判定规则见1.1.2）；本阶段先实施。

**三条约束（需求）**（不可谈判，统一publish后的保证方式随节落定 — 小健-2026-09-05）：
1. paused必须在阻塞等待前到达前端（确认弹窗），resumed在恢复瞬间到达—— functional correctness，不可谈判。**保证方式**：由"调用publish的时刻"直保——网关内部固定顺序 `publish(paused)→wait→publish(resumed)`（构造保证），不再依赖yield写在await之前的代码位置（1.1.2路径1）。
2. event_log append-only + seq语义不动（断线重连/回放依赖，见agent_runner.py行199-210持锁模板）。**保证方式**：publish复用_append持锁模板（行199-210），只换发射入口、不换event_log语义。
3. agent_runner通道路由表语义不动（thought仅落库；thought-start、chunk、startinfo及通知类 error/usage/paused/resumed/retrying/cancelled 仅SSE；action/final/final_stats/其余 落库+SSE双写，见agent_runner.py行307-362）。**保证方式**：路由收敛为一张EVENT_ROUTE表（位置集中，语义等价）；"发射"上移到发射点publish、"路由+落库"留在agent_runner（角色变化见1.1.2 agent_runner角色段）。

**总判据（判定规则，一句话）**：
- yield 的产物是"要进 event_log 的 Step 事件" → publish 取代它；
- yield 的产物是"LLM 流式数据块（StreamChunk）" → 保留 yield。
（完整判定规则与路径1/路径2二分详述见1.1.2）

### 1.1 方案定稿：统一publish总线（核心设计 + yield二分法则，v1.2.21重写定稿 — 小健-2026-09-05）

#### 1.1.1 核心矛盾

**核心矛盾**：handler是async generator，"阻塞前先发射paused"依赖yield写在await之前的代码位置——这是三宗时序风险（位置耦合/双paused/事后补发）的唯一根。发射通道只有两类本质：**点发式**（publish，调用时刻即落event_log，时序与代码位置解耦）与**路过式**（yield，多跳透传，时序看位置）。本设计定稿：**全仓事件只走一个发射口 publish，发射面 yield 退役（数据流 yield 保留）**。

#### 1.1.2 yield 二分法则（全仓判定规则，定的死）

> **判定规则**：yield 的产物是"要进 event_log 的 Step 事件" → publish 取代它；yield 的产物是"LLM 流式数据块（StreamChunk）" → 保留 yield。publish 与 yield 职责不同、不并存、不混用。

**路径1：事件发射 yield → 全部退役（publish 取代）**。凡是 `yield emit(XStep)` 或 `yield event`（把下层事件再上送），都是"把 Step 事件送进最终 event_log"的运输通道——正是"时序看位置"的病根：真正落 event_log 的时刻取决于各层 `async for` 消费时机，而暂停事件正确性要求"发射在 wait 之前"，该依赖太脆弱。publish 在"构造时刻"写死 event_log，时序=调用时刻：

| 层 | 现状写法 | 统一publish后 |
|------|----------|--------------|
| handler（answer/action/safety/sandbox） | `yield agent._step_emitter.emit(XStep)` | 纯函数 `return list`，dispatch 统一 `await publish(each.to_dict())` |
| react_step（消费LLM后产元事件） | `yield emit(MetaStep(...))`等 | `await publish(emit(X).to_dict())` |
| react_step→dispatch（react_step.py L461 调 `_dispatch_handler`） | `async for event in _dispatch_handler(...): yield event` | `await`拿list→逐个publish |
| react_loop（start/final/重试/兜底） | `yield emit(...)` / `for _s in emit_final_with_stats: yield _s` | `await publish(...)` |
| base_agent 纯透传 | `async for event in _run(...): yield event` | 逐层透传链删除（发射点已下沉） |

**路径2：LLM 数据流 yield → 保留（publish 不取代）**。产出是 LLM 原始流分块（StreamChunk）：**不落event_log、不进路由表、不喂前端SSE**，只流式喂给 react_step 消费增量处理（chunk_buffer.append、首token标记）；它没有"必须在 await 之前到达"的时序依赖——chunk 顺序由 LLM 流本身保证。publish 是 event_log 的门，StreamChunk 不该进门，所以 publish 管不到它：

| 位置 | 现状写法 | 结论 |
|------|----------|------|
| llm SDK层 | `async for chunk in agent.llm_client.request_stream(...)` | **SDK接口天生就是异步迭代，publish 取代不了** |
| call_llm_stream / call_llm_with_fallback 出口 | `yield` 元组/response 混出 | 保留——数据管道，非事件（出口统一 `yield StreamChunk`） |

**边界厘清：chunk 的双重身份（最容易混的点）**：

```
LLM流 ──yield StreamChunk──▶ react_step 消费
                              │
                              ├─ 数据流身份：chunk_buffer.append / 首token标记   ← yield（保留）
                              └─ 事件身份：构造 ChunkStep ──await publish──▶    ← publish（取代原yield emit）
```

LLM层那个yield（call_llm_stream出口）=数据块，保留；react_step里那句 `yield emit(ChunkStep)` =事件发射，改 `await publish`。

**agent_runner 角色变化（约束3落地形态）**：现状 `async for event in run_react_cycle` → 按路由表 `_append`（写event_log+推SSE）+ `_persist`（写DB）。统一后 **主循环事件转发退役**（事件经 publish 直写 event_log，不再经 handler yield 透传）；agent_runner 改从 event_log 消费，按路由表（约束3）仍执行 **SSE 推送（含 final/final_stats 延迟补发、startinfo 合成）与 DB 落库 _persist** + 终态记账（_has_chunk_steps/_action_steps/current_content）。路由表语义不动（约束3），发射职责上移到发射点、路由与落库职责留在 agent_runner。

#### 1.1.3 候选方案对比（分析汇总）

| 方案 | 做法 | 发射机制 | 解决什么 | 遗留/代价 | 结论 |
|------|------|---------|---------|----------|------|
| A：统一暂停源头（混合） | 暂停事件走publish直写event_log，普通事件仍走yield | publish+yield 两套 | 三宗时序风险 | **yield链仍靠代码位置**（其他事件仍脆弱），两套机制并存，不是干净终态 | 排除 |
| **B：统一publish总线** | **所有事件（暂停+普通）统一publish直写event_log，发射面yield退役（数据流yield保留）** | **publish 一套** | 全部时序风险 + 架构清理 | 动agent_runner主循环（删_append双路由），路由表位置让位、语义保留 | **采纳** |
| C：只纯函数化不做publish | handler改async函数，无publish通道 | 无 | generator脆弱 | **没有publish通道，暂停事件无处发出，行不通** | 排除 |
| D：不改架构加固现有代码 | 不加publish不加网关，局部加固 | yield | 表面 | 治标不治本，位置耦合是架构缺陷，下次重构必重蹈 | 排除 |
| E：完整事件总线（pub/sub等） | 订阅/滤波/重放全套 | — | 过度 | YAGNI，改动面过大，当前不需要 | 排除 |

#### 1.1.4 采纳方案B：统一publish总线

**采纳理由**（老陈2026-09-05定案"最后统一：直接上统一publish"）：

1. **单一发射点**：不再有yield链，时序由调用时刻保证——"调用publish的时刻就是事件落event_log的时刻"，三宗时序风险连根拔除。
2. **架构干净**：handler返回list，事件经publish直写event_log；agent_runner从event_log消费、查一张EVENT_ROUTE表完成路由（SSE推送/DB落库/双写），删事件转发入口（_append双路由）。
3. **防止未来bug**：新事件类型自动获得时序保证，不再有"yield写在哪"的心智负担。
4. **每个改动更简单**：return list比yield更直观，generator的禁return值/输出参数透传（_verdict/_result_out/_emit_events）一并作废。

#### 1.1.5 统一后三件事各自归一

（不是"几种发射模式"，是三件不同的事）：
- 发射（事件怎么进event_log）：**一个publish**——调用那一刻即落event_log，无中间跳；
- 路由（哪些落库/哪些仅SSE）：**一张EVENT_ROUTE表**——thought仅落库；thought-start、chunk、startinfo及通知类（error/usage/paused/resumed/retrying/cancelled）仅SSE；action/final/final_stats/其余 落库+SSE双写（语义同agent_runner行307-362，收敛一处不散落）；
- 暂停时序（paused先于等待/resumed恢复瞬间）：**一个网关**——hitl_gateway 内部固定顺序 `publish(paused)→wait→publish(resumed)`，构造保证，调用方挪不动。

以上四个小节（yield二分法则、候选对比、采纳理由、三件事归一）共同构成第一章的完整定稿口径：**发射统一publish、路由统一EVENT_ROUTE表、暂停时序统一网关、yield只留数据流一途**。

> **口径定死（v1.2.21 起承接）**：凡曾出现的"方案A＋方案B组合"表述一律作废，统一以本定稿"统一publish"口径为准。

## 二、 路径2 的优化设计及实施

| 2.1-4 | 业务语义零退化 | action/answer/error 终结响应、L1/L2/FC 降级 retrying 通知、usage 累积、遥测、裁剪触发全部行为不变 | 回归：LLM 调用一次全链 Step 事件与现状逐项等价 |

**一句话**：发射 vs 数据流——路径1 把"事件发射 yield"全部退役换成 publish；路径2 把"数据流 yield"保留且把出口载体从"元组+dict 混出"统一成 StreamChunk 单协议。

**通俗解读：「StreamChunk 单协议」是什么** — 小健-2026-09-05

> 老陈问"StreamChunk 单协议"到底是什么意思，这里用大白话拆开讲：

**现状问题**：LLM 数据流出口，一次会往外扔**三种形态不同的东西**：

| 扔出来的东西 | 形状 | 含义 |
|------------|------|------|
| `("chunk", ChunkStep)` | 元组套一个 Step 对象 | 流式文本块（打字机效果逐字输出） |
| `("response", dict)` | 元组套一个字典 | 终结响应（action 调工具 / answer 最终回答 / error 出错） |
| `("meta", dict)` | 元组套一个字典 | 重试通知（LLM 重试了第几次） |

消费方 `react_step.py` 要判断接到的是什么，只能靠**元组里第一个字符串**（`"chunk"` / `"response"` / `"meta"`）去拆——这就是"三元组混出"：一个管道三种包装。

**"StreamChunk 单协议"的意思**：把这三种东西，**全部装进同一种容器——StreamChunk 对象**里再扔出去。出口不再出现元组，只有 StreamChunk 一种类型。

怎么区分里面装的是什么？给 StreamChunk 加一个 `payload` 字段：

```
StreamChunk(payload=None)                    → 流式文本块（读 content 原生字段）
StreamChunk(payload={"type":"retrying"})     → 重试通知
StreamChunk(payload={"type":"action"})       → 终结响应：调工具
StreamChunk(payload={"type":"answer"})       → 终结响应：最终回答
StreamChunk(payload={"type":"error"})        → 终结响应：出错
```

消费方只需要做**一个判断**：`payload` 是不是空的。空的→流式块；非空→看 `payload["type"]` 是什么。不再拆元组、不再对字符串标签。

**打个比方**：原来快递是三套不同包装（纸箱/信封/塑料瓶），收货人得按包装辨认；统一后全部用**同一种标准箱**，上面贴统一标签，拆箱只需看标签。收货逻辑（react_step 处理增量、算 usage、发事件）一字不改，只是"包装"归一了。

这样改的好处：**类型约束强**（编译层面只有 StreamChunk 一种），**判别简单**（一个 payload 字段定生死），和第一章路径1 的"事件发射统一 publish"形成对称——路径1 把"事件"收口到一个入口，路径2 把"数据"收口到一种载体。

### 2.5 归一化函数组织（10大规范分析）+ 六文件代码 diff

#### 2.5.0 归一化逻辑是否需要独立函数？（10大规范定案 — 小健-2026-09-05）

**结论：需要——收敛为一个 StreamChunk 构造工厂 `create_payload_chunk`，放 `llm/core.py`（与既有 `create_cancelled_chunk`/`create_error_chunk` 同族），并登记 FUNCTIONS.md。**

| 规范 | 判定 | 依据（实读代码） |
|------|------|-----------------|
| **DRY 不重复** | ✅ 必须收敛 | 若按"各装配函数各自内联构造"写（不经工厂），`create_payload_chunk` 调用会出现在 3 个装配函数 + llm_call 三处 retrying（L1/L2/FC 降级）= **6 处重复**；收敛为 1 个工厂 |
| **复用优先（先查后建）** | ✅ 有同族先例 | `llm/core.py` L115/L122 已有 `create_cancelled_chunk`/`create_error_chunk` 两个 StreamChunk 工厂，新增 `create_payload_chunk` 放同文件、同族先例，并登记 FUNCTIONS.md |
| **SRP 单一职责** | ✅ 职责分明 | 工厂=载体构造（一行 return）；装配函数=payload dict 组装（内容）；消费侧=payload 判别（读取）——三方各管一段 |
| **KISS-DIRECT** | ✅ 零抽象 | 工厂就是 1 行 return（单构造调用）；不建"归一化器类"、不建协议注册表 |
| **YAGNI** | ✅ 不建多余抽象 | 普通 chunk 本就是 StreamChunk（SDK 原生），直接透传即可，不需要工厂包；只有"终结响应/通知"需要 payload 承载 |
| **SLAP** | ✅ 同一抽象层 | 出口侧（llm_call）只 `yield` 不进 payload dict 组装细节；消费侧只读 payload 不关心 dict 来源 |
| **禁止backward** | ✅ 无兼容残留 | `("response", dict)` / `("chunk", Step)` / `("meta", dict)` 旧三元组出口彻底移除，不留别名 |
| **OCP/LSP/ISP** | ✅ 单点扩展 | 加字段+加工厂=对扩展开放；StreamChunk 无子类，LSP 不涉及；payload 只暴露一个判别入口，ISP 干净 |

**归一化最终形态（写死）**：

- 普通 chunk：SDK `request_stream` 原生 StreamChunk 直接透传（内容是 chunk，零加工）；
- 终结响应（action/answer/error）：装配函数返回 `create_payload_chunk(chunk_model, payload_dict)`；
- retrying 通知（L1/L2/FC降级）：llm_call 构造 `create_payload_chunk(chunk_model, payload_dict)`，其中 `payload_dict["type"] == "retrying"`；
- 消费侧唯一判别：`getattr(item, "payload", None) is not None` → 看 `payload["type"]`；否则走 chunk 增量。

> 关联逻辑检查（实施铁律）：`call_llm_with_fallback` 现有**两个消费方**——`react_step.py`（主消费，L197）与 `compaction/summary.py`（摘要引擎 `_extract_response_content`，L32）。两者都拆 `("response", dict)` 取 content，**改出口协议必须同步改两处**，漏一处即摘要断裂。— 小健-2026-09-05

## 三、StreamBuffer.publish 概要设计

**一句话**：publish是全仓事件（暂停+普通）进入event_log的唯一入口——"调用它的时刻就是事件落event_log的时刻"，时序由发布动作保证，不由yield代码位置保证。本文档所有事件以此为准（1.1定案统一publish，v1.2.21起七章diff按此口径重写）。

### 3.1 为什么用 / 解决什么问题（2.3三宗时序风险）

暂停事件（paused/resumed）必须进event_log才能经SSE到达前端。现状发射靠generator `yield`"路过即发射"，yield必须手工写在await之前，代码位置一挪即违法序——这正是2.3三宗时序风险的共同根源。publish把"发射"从隐式路过改成显式调用：

| 问题（2.3） | 现状根因 | publish解决 |
|------|--------|-----------|
| 位置耦合 | 时序靠"yield写在await之前" | 时序靠"调用publish的时刻"，与代码位置无关 |
| 嵌套裁决双paused | 主路/sandbox各自yield各自的 | 统一收编网关，publish单一入口发paused |
| 事后补发诱惑 | 先把paused收进列表、事后才emit | 调用即落event_log，无从延迟补发 |

### 3.2 如何用（接口契约与调用时机）

- **签名**：`async def publish(step_dict: dict) -> int`；入参为完整Step的dict（先`to_dict()`再publish）；返回该事件分配到的seq。
- **动作**：分配seq + append event_log + 持锁`notify_all`，复用agent_runner._append持锁模板（行199-210），不另起队列、不动event_log语义（约束2）。
- **时机**：网关阻塞前`await publish(paused.to_dict())`、恢复瞬间`await publish(resumed.to_dict())`（见4.2行171/177）；普通事件由dispatch中枢统一`await publish(each.to_dict())`（v1.2.21起7.7按此改造），不再有"普通事件走yield透传"（1.1定案：发射面yield退役、数据流yield保留）。
- **注入**：publish由调用方注入`buffer.publish`，与`agent_streams.get(task_id)`同源；任务运行中buffer必存在（create_stream_buffer于任务启动时创建），None防御落盘时加。

### 3.3 有什么价值

1. **约束1（paused先于等待、resumed恢复瞬间）由发布时刻直保**：是"阻塞前调/恢复瞬间调"这个调用顺序的必然结果，不再依赖手工yield位置。
2. **单写**：全仓事件（暂停+普通）只从publish一个入口进event_log，位置耦合/双paused/事后补发三宗时序风险同根消失（ISS-004同根），无双发面。
3. **零侵入**：不动agent_runner路由表语义（约束3：thought仅落库/thought-start与chunk仅SSE/其余双写），路由收敛为一张EVENT_ROUTE表（位置集中，语义等价），event_log/SSE/DB/前端零改动（v1.2.21起7.x按此重写）。

from typing import Optional
from app.services.agent.steps import MetaStep
from app.services.agent.status_table import set_status, AgentStatus  # AgentStatus真实位置status_table行19 — 小健-2026-09-05

@dataclass
class ConfirmSpec:
    """确认规格（与4.2同形，属性访问；auto_confirm默认None由mode推导） — 小健-2026-09-05"""

    path: Optional[str] = None
    content: str = ""
    safety_level: str = ""
    auto_confirm: Optional[bool] = None

async def _resolve_trust_path(tool_name, params) -> Optional[str]:
    from app.tools.trust import extract_trust_path        # 延迟import防环（真实位置tools/trust.py行66）
    params = params or {}
    # 网关内统一提取（原主路_extract_trust_path + sandbox回落扫描，收拢；回落键与sandbox_gate行101同源）

         if isinstance((v := params.get(k)), str) and v), None)

def _desensitize(params) -> dict:
    from app.tools.tool_constants import SENSITIVE_FIELDS      # 延迟import防环（真实位置，sandbox_gate行66同源 — 小健-2026-09-05）
    return {k: v for k, v in (params or {}).items() if k not in SENSITIVE_FIELDS}

async def _resolve_timeouts(mode):
    """返回 (backend_timeout, confirm_timeout) 二元组（调用处双解包 — 小健-2026-09-05）。
    点分扁平键（与三处同源，禁嵌套get("security")取法）+ 分mode公式：
    hitl→security.hitl_timeout兜底HITL_TIMEOUT，confirm=max(MIN, backend-HITL_CONFIRM_LEAD)；
    bypass→security.auto_confirm_delay兜底10.0，backend=max(MIN+LEAD, delay)，confirm=backend-BYPASS_AUTO_LEAD。

    from app.config import get_config                            # 延迟import防环
    from app.constants import HITL_TIMEOUT, HITL_CONFIRM_LEAD, HITL_MIN_CONFIRM_TIMEOUT, BYPASS_AUTO_LEAD
    cfg = get_config()
    if mode == "hitl":
        _bt = int(float(cfg.get("security.hitl_timeout", HITL_TIMEOUT)))
        return _bt, max(HITL_MIN_CONFIRM_TIMEOUT, _bt - HITL_CONFIRM_LEAD)
    _bt = max(HITL_MIN_CONFIRM_TIMEOUT + BYPASS_AUTO_LEAD,
              int(float(cfg.get("security.auto_confirm_delay", 10.0))))
    return _bt, _bt - BYPASS_AUTO_LEAD

async def hitl_confirm(agent, spec: ConfirmSpec, publish):
    """spec属性访问（与4.2同形）→verdict。网关内统一：超时计算/trust_path/脱敏/SUSPENDED→wait→EXECUTING。"""
    from app.services.task.hitl_confirmation import (            # 延迟import防环
        create_confirmation, wait_for_confirmation_result)
    _path = spec.path or await _resolve_trust_path(spec.tool_name, spec.params)
    confirm_id = await create_confirmation(agent.task_id, spec.tool_name, _path)
    _bt, _ct = await _resolve_timeouts(spec.mode)
    _auto = spec.auto_confirm if spec.auto_confirm is not None else (spec.mode == "bypass")
    paused = agent._step_emitter.emit(MetaStep(step=agent.llm_call_count, type="paused",
        content=spec.content, confirm_id=confirm_id, tool_name=spec.tool_name,
        params=_desensitize(spec.params), safety_level=spec.safety_level,
        severity="attention", trust_path=_path, auto_confirm=_auto,
        confirm_timeout=_ct, backend_timeout=_bt))
    set_status(agent, AgentStatus.SUSPENDED, f"等待用户确认: {spec.tool_name}")
    await publish(paused.to_dict())
    auth = await wait_for_confirmation_result(confirm_id, timeout=_bt)
    set_status(agent, AgentStatus.EXECUTING, "用户裁决完成")
    if auth.get("confirmed"):
        resumed = agent._step_emitter.emit(MetaStep(step=agent.llm_call_count, type="resumed",
            content=f"已确认执行: {spec.tool_name}", severity="info", confirm_id=confirm_id))
        await publish(resumed.to_dict())
    return {"confirmed": bool(auth.get("confirmed")), "expired": bool(auth.get("expired")),
            "trust_session": bool(auth.get("trust_session", False)), "confirm_id": confirm_id}
