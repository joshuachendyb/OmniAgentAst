## 二、任务2 问题分析（并行工具 + UI不完整渲染）

### 2.1 病根定位

**归属：前端bug**

**后端完全正常**，所有SSE事件都正确发出并到达了前端（console日志已证实）。

### 2.2 病因分析

#### 2.2.1 事件到达确认

从console日志确认，前端**收到了所有事件**：

```
15:59:20 [STEP] [type=thought] [step=5] ✅ 已收到
15:59:20 [ACTION] [type=action_preview] [step=5] ✅ 已收到
15:59:20 [STEP] [type=paused] [step=5] ✅ 已收到
15:59:22 [STEP] [type=resumed] [step=5] ✅ 已收到
15:59:42 [ACTION] [type=action_canonical] [step=5] ✅ 已收到
15:59:42 [STEP] [type=observation] [step=5] ✅ 已收到
15:59:42 [STEP] [type=thought-start] [step=5] ✅ 已收到
15:59:43 [STEP] [type=final] [step=6] ✅ 已收到
```

#### 2.2.2 UI不渲染的根因

**病根**：`useChatCallbacks.ts` 中 `onComplete` 回调的 **executionSteps 覆盖问题**。

**具体机制**：

1. `sseParser.ts` 的 `final` 分支调用顺序（第499-530行）：
   ```typescript
   // ① 先更新 ref（包含 final step）
   handlers.executionStepsRef.current = updatedSteps;
   // ② 再异步更新 state
   setExecutionSteps((prev) => [...prev, step]);
   // ③ 再调 onStep（也是异步 setMessages）
   onStep?.(step);
   // ④ 最后调 onComplete
   onComplete?.(fullResponse, metadata, finalStepsWithCurrent);
   ```

2. `onComplete` 中（第432-467行）：
   ```typescript
   setMessages((prev) => {
     const finalSteps = lastMessage.executionSteps || [];  // ← 读的是 prev
     updated[updated.length - 1] = {
       ...lastMessage,
       executionSteps: finalSteps,  // ← 用 prev 的值覆盖
     };
   });
   ```

3. **关键问题**：`onStep` 的 `setMessages` 和 `onComplete` 的 `setMessages` 在同一个事件循环tick中被调用。React 18 批量处理state更新时，`onComplete` 的 `setMessages` 读取的 `prev` 是**onStep更新前的状态**（因为onStep的setMessages是函数式更新，React需要等到下一个tick才应用）。这导致 `onComplete` 用**不含final step的旧 executionSteps 覆盖了 onStep 刚追加了 final step 的 executionSteps**。

4. 结果：`PipelineRenderer` 收到的 `steps` prop 中**缺少 step5 和 step6 的数据**，所以不渲染。

#### 2.2.3 涉及文件

| 文件 | 位置 | 问题 |
|------|------|------|
| `frontend/src/features/chat/hooks/useChatCallbacks.ts` | onComplete回调（第432-467行） | 用旧executionSteps覆盖新值 |
| `frontend/src/features/chat/services/sseParser.ts` | final分支（第499-530行） | 调用顺序导致state竞争 |

### 2.3 解决方法

**文件**：`frontend/src/features/chat/hooks/useChatCallbacks.ts`

**改法**：在 `onComplete` 中，优先使用 `executionStepsFromSSE` 参数（即 `sseParser` 传入的完整steps数组），而不是 `lastMessage.executionSteps`：

```typescript
// 第442行附近，修改为：
const finalSteps = executionStepsFromSSE && executionStepsFromSSE.length > (lastMessage.executionSteps?.length || 0)
  ? executionStepsFromSSE
  : lastMessage.executionSteps || [];
```

**原理**：`sseParser` 在调用 `onComplete` 前已经将 final step 追加到 `executionStepsRef.current`，并将其作为 `executionStepsFromSSE` 参数传入。使用这个参数可以确保 `PipelineRenderer` 收到完整的steps数据。

## 三、任务1 问题分析（UI冻住 + console日志不完整）

### 3.1 病根定位

**归属：正常行为 + 日志清理的表面现象**

### 3.2 病因分析

#### 3.2.1 "冻住"的真正原因

从console日志看时序：

```
15:46:09 [STEP] [type=thought-start] [step=5] ← 这里之后20秒无任何SSE事件
15:46:29 [STEP] [type=final] [step=6] ← LLM处理20秒后才返回
```

**这20秒是LLM处理时间**（后端在等待LLM API响应），期间**后端没有发出任何SSE事件**。前端在 `thought-start` 时渲染了等待图标（绿色缺口圆弧），这是**正常行为**，不是bug。

#### 3.2.2 为什么感觉"冻住10秒"而不是20秒

因为事件是**批量到达**的。当LLM响应到达后，以下事件在极短时间内（15:46:08-15:46:09，约1秒内）全部到达：

```
15:46:08 [STEP] [type=thought] [step=5]
15:46:08 [ACTION] [type=action_preview] [step=5]
15:46:09 [ACTION] [type=action_canonical] [step=5]
15:46:09 [STEP] [type=observation] [step=5]
15:46:09 [STEP] [type=thought-start] [step=5]
```

前端需要在**一次React渲染周期**内处理这5个事件，每个事件都要触发 `setMessages` → `PipelineRenderer` 重渲染 → `buildSegments` 重新计算。这导致了约10秒的渲染延迟。

#### 3.2.3 console日志"不完整"的原因

2026-09-09 的日志治理（sseParser.ts 第26-29行编辑历史）**有意删除了** `onStep` 中的 `📝 type= timestamp=` 每步打点日志。这是**正常清理**，不是bug。用户看到的"不完整"实际上是日志被清理了。

#### 3.2.4 涉及文件

| 文件 | 说明 |
|------|------|
| `backend/app/services/agent/handlers/handle_action.py` | 工具执行后批量发出多个SSE事件 |
| `frontend/src/features/chat/services/sseParser.ts` | 事件解析和console日志（已清理） |
| `frontend/src/features/chat/components/pipeline/PipelineRenderer.tsx` | 批量事件导致渲染延迟 |

### 3.3 解决方法

**这是正常行为，不需要修复**。但可以优化用户体验：

**方案**：在 `PipelineRenderer` 中，当 `waiting` 段是末段且 `taskActive=true` 时，可以显示更详细的等待提示（如"正在处理中..."），让用户知道系统在工作而不是卡死。

## 四、总结

| 任务 | 问题归属 | 病根 | 严重度 |
|------|---------|------|--------|
| 任务2 | **前端bug** | `onComplete` 的 `setMessages` 用旧 `executionSteps` 覆盖了 `onStep` 已更新的值，导致 `PipelineRenderer` 缺少 step5/step6 数据 | **高** |
| 任务1 | **正常行为** | LLM处理20秒无SSE事件 + 批量事件到达导致渲染延迟 + 日志清理的表面现象 | **低** |

## 五、修复优先级

1. **任务2 修复**（高优先级）：修改 `useChatCallbacks.ts` 的 `onComplete` 回调，使用 `executionStepsFromSSE` 参数
2. **任务1 优化**（低优先级）：可选的等待提示优化
