## 一、存放方案结论（已定）

1. 不开新文件。用现有 `config/config.yaml`，新增第 7 分组 `tuning`（调优）。
2. 理由：复用 [54] 设置体系全套机器（6分组→7分组、merge_region_patch单次落盘、备份/mtime、前端设置页只加一个Tab）；加键向后兼容；新文件要重造加载/校验/备份/UI四套，违背DRY/YAGNI。

## 二、第7分组`tuning`设计：1组8子组（组-子组-键三级）

结构（yaml嵌套块，读侧点路径`tuning.llm.temperature`）：

```yaml
tuning:
  llm:         # 2.1 大模型语义，7键
    temperature: 0.7
    tool_choice: auto
    # ... 余见2.1表
  llm_net:     # 2.2 大模型网络（超时+池+总闸），7键：三思拆分，llm原14键太胖
    read_timeout: 150
    # ... 余见2.2表
  concurrency: # 2.3 并发配额，2键（v1.8：sandbox已删，剩软配额等待/shell池）
    soft_pool_wait_timeout: 30.0
    # ... 余见2.3表
  agent:       # 2.4 Agent循环，3键
    default_max_steps: 100
    # ... 余见2.4表
  stream_task: # 2.5 流与任务，4键
  hitl:        # 2.6 人工确认，4键（hitl_timeout已删，见下）
  content:     # 2.7 内容裁剪，3键（含历史字符上限，其常量定义在compaction_constants.py，值迁tuning后读配置）
  network:     # 2.8 网络，1键（仅cors_origins；核查结论：池类已在llm_net，
               # 全局代理代码里不存在故无可配项，不写虚的预留位）
```

子组即嵌套dict；settings_registry按子组登记（每子组独立schema段，前端Tab内分8节展示）；
merge_region_patch点路径天然支持嵌套，单次落盘语义不变。
命名规则：键即常量小写原名，缺省值=现常量值；调用方缺键回退常量（向后兼容）。

三思结论（2026-09-21 小欧自查，结论先行）：

1. llm必须拆。14键的子组和大组一样臃肿，语义也分两类（调什么 vs 怎么连），
   拆成llm（语义7键）+llm_net（网络7键）后每组一眼看完。
2. hitl_timeout删。`security.hitl_timeout`已是单源，再配一个缺省源就是双源异味；
   tuning.hitl只留4个真孤儿键。
3. stream_options是风险点。它是dict结构，registry若表达不了就留代码，
   实施时以registry能力为准，不硬配（已在2.1表标注）。
4. 参数化必须加护栏才是最优。32个开关裸露给用户，heartbeat填大了会断流、
   max_tokens填错会爆内存。所以registry每键必须带类型+范围/枚举+说明，
   前端约束输入；危险键（如stream_total_timeout）给推荐区间。这是“可配”成立的前提。
5. 同类参数的取舍已定稿：本次共迁32键（constants.py层+4个二期前置键），
   其余9项不迁，逐条理由见四章。本期先收这一层验证链路。
6. 二期中本次值得加的4键（v1.5决议，标准：用户真会调+配出去安全+零成本）：
   软配额等待30s（PAR实证的并发排队旋钮）+shell池上限3（并行负载运维）+
   沙箱并发3（同上，且已是get_config源头）+历史字符上限50000（token账单相关）。
   前三者立新concurrency子组，历史字符入content。1组8子组32键。
   其余9项不加，理由：DB锁协议是地基（动则事故）、compaction是联动算法、
   推理轮上限因模型而异、SQL/观察字典/标题是边角美容、SSE缓冲与心跳单源、
   清理间隔不影响正确性、产物上限待确认存在。

## 三、不迁清单（留代码，理由）

1. 正则类（HTML_TAG/SCRIPT/STYLE/空白/UTC偏移）：洗数据规则，配出去无意义。
2. 算法内参与派生量（除已迁入2.6的以外；其余如LEAD钳制中间值）：改了易错。
3. 复杂dict结构键：除stream_options（纯透传保留）外，其余一律不迁。

## 四、余9项不加入的原因说明

能进配置的是“用户该做主的业务旋钮”，这 9 个要么是地基、要么是联动算法、要么配了没用。

DB busy_timeout（30000ms）：SQLite WAL 锁等待底线。调小→并发写直接报 busy 错；调大→卡死级联。动它等于动地基，用户调不出任何好处，只剩事故。
DB 重试（0.5/1/2s 退避）：和 busy_timeout 是一对的锁协议，改一个必须改另一个。拆开配就是给用户递两把互相打架的刀。
compaction 20 个阈值：压缩算法的联动参数（0.75/0.8/0.5 等互相咬合），改一个不改其余直接截断上下文或内存爆炸。这是调参，不是配置。
推理轮上限 3：不同模型行为差一个量级，3 对这个模型是护栏、对那个是枷锁。配成全局值等于用一把尺量所有布。
SQL 超时/limit（15s/50条）：dev 排障工具的护栏，不是业务开关。真卡了是 SQL 写得烂，该修 SQL 不该调参。
观察字典键上限 100：纯显示截断，配大配小都不影响正确性，只影响日志美观。为美观加配置不值。
SSE 缓冲：和心跳 25s 是同一根绳的两头（已配心跳），拆两处配，用户调偏一处就断流。单源原则。
标题长度：纯美容数字，无行为含义。
会话清理间隔：TASK_TIMEOUT（1h，已配）是“什么算过期”，间隔只是“多久扫一次”。扫勤扫懒不影响正确性，不值得占一个键。
