## 四、三条结论

**1. 设计的"演进型取代"占 28 项（11%），这部分是健康的。**
最大的一次是 **4 月把整个 LLM 响应解析体系推倒，换成 Function Calling**。这说明架构在收敛而不是发散。

**2. "Agent 智能化"这条线从 3 月提出、5 月密集设计，至今零落地。**
意图分类、预处理管线、多 Agent、多态交互（ask_user）、任务内模型切换 —— **五个连续的大设计全部停在文档**。
当前架构实际是"**单 Agent + 工具按需暴露 + Function Calling**"，这是 5 月自己做的技术选型（"走 FC 但无路由层"），但文档里仍保留着大量"Agent 架构"的未兑现承诺。**这是文档与现实最大的一处错位。**

**3. 9 月设计 60 篇、落地 13 篇，是设计产出与落地脱节最严重的月份。**
7 项"部分实现"里多项在文档中已被标为 ✅（如 Agent 继承层级 v1.5），但代码核对证明**从未存在**。

> **由此得出一条纪律**：**设计文档的自评完成度不可信，必须以代码为准。**
> 这与 `[73]` 系统架构文档十遍核查的结论一致 —— 那次核查同样发现多处"文档说已实现、代码里查无此物"。

## 六、未实现设计的实施优先级（基于本地代码现状）

**【判定标准】** 价值（是否解决真实痛点）× 地基（前置机制是否已存在）× 风险（是否动主链路）。
**【地基核实】** 本章每条"地基已齐"的断言均已实际打开代码确认（`hitl_confirmation.py` 确认返回结构、`config_helpers.py:reload_ai_config`、`compaction/assembler.py` 4 函数、`llm_call.py` fallback 结构、`settings_registry.py:GROUPS` 模式）。

### 6.1 P0：该做，价值高、地基现成（4 项）

#### 1. ask_user 多态交互工具

- **为什么**：今天 Agent **只能被动等用户点"确认/拒绝"**，遇到歧义（删哪个目录？用哪个模型？）只能猜或停。这是第三章一级清单里**唯一用户可感知的能力缺口**。
- **地基已齐**：`hitl_confirmation` 的 paused→SUSPENDED→confirm→resumed 全链路、前端 `AuthorizationModal`、SSE paused/resumed 帧**全部现成**。缺的只是一个文本通道：`wait_for_confirmation_result` 返回 `{confirmed, trust_session}`，**没有文本字段**——加一个 `user_text` 字段 + 弹窗加输入框 + 一个 `ask_user` 工具定义即可。
- **价值**：解锁"澄清-继续"循环；同时给多 Session 插话一个通道（今天只有 confirm 一种交互）。
- **工作量**：中。不碰主链路。

#### 2. 模型池 failover（有序队列 + 失败切换）

- **为什么**：今天**单个模型失败=任务整体失败**。`llm_call.py:call_llm_with_fallback` 只处理"格式降级"，不处理"换模型"。LLM 连接池（[70]）和 `get_service_for_model` 都已存在，failover 是**可靠性上最后一块拼图**。
- **地基已齐**：连接池所有权、按模型取服务、请求级 `provider/model` 指定。缺的是：有序备选队列 + 失败计数 + 切换点（在 fallback 耗尽处接）。
- **价值**：任务成功率。尤其免费/不稳定模型（Zen 免 key 层）场景下是刚需。
- **工作量**：中高。要动 `llm_call`，需后端 E2E 覆盖。

#### 3. T2 冷区合并 + overflow/413 回退 + 手动 compact 入口

- **为什么**：这是**烧钱项**。T1（剪枝）已落地，但长任务的工具输出不做概要合并，token 只增不减；`assembler.py` 的 4 个函数（`split_history_window` / `get_new_messages_since` / `inject_compressed_summary` / `remove_dangling_tool_calls`）**写好了没人调**；HTTP 413 溢出无回退分支，超长任务直接崩。
- **地基已齐**：assembler 函数、trigger、T1 链路全在。就是"接线"活。
- **价值**：token 成本 + 超长任务不崩。
- **工作量**：中。不碰主链路（compaction 是独立模块）。

#### 4. constants 配置化分组（22+ 平铺常量并入 registry）

- **为什么**：`constants.py` 里 22+ 个魔法数字（`DEFAULT_MAX_STEPS` / `LLM_*` / `HEARTBEAT_INTERVAL`…）只靠注释分组，用户调参要改代码。`settings_registry.py:GROUPS` 模式已成熟，**照抄即可**。
- **价值**：可调性 + 消灭魔法数字。用户能自己调重试/超时/心跳。
- **工作量**：低中。纯搬运 + fre2e_11 回归。

### 6.4 明确不做（给理由，这比"做"更重要）

| 设计 | 不做的理由 |
|---|---|
| **意图分类 / 预处理管线 / CRSS / 语义路由** | FC + BM25 `tool_search` 已经解决了"选工具"问题。再加一层意图分类 = **加延迟 + 加维护 + 加故障点**，零增益。**建议正式废弃，删掉 `requirements.txt` 里从未 import 的 `jieba`** |
| **多 Agent 架构** | 没有真实用例。单 `UniversalAgent` + 工具分解能覆盖现有场景。多 Agent 是"为架构而架构"。**推迟到有真实多角色需求那天** |
| **网关 / RBAC / DAG 编排** | 单用户桌面应用。RBAC 给谁用？DAG 编排 LLM 自己会拆步骤。**典型的过度设计，拒绝** |
| **Tauri / 托盘 / 全局快捷键** | Web UI + Python 桌面工具已覆盖。托盘是"想要"不是"需要"。**拒绝** |
| **Structured Outputs（json_schema）** | XML 路线可用，各 provider 对 json_schema 支持不均。**推迟** |
| **Hermes-Lite 立项** | 理念已被吸收（9 处注释引用），单独立项只会多一个没人维护的模块。**拒绝立项** |
| **paragraphs 统一（content+table_data 合并）** | 破坏性变更，影响现有文档工具；收益只是"好看"。**拒绝** |
| **IndexedDB 迁移** | sessionStorage 5s 防抖够用。**拒绝**（已被 sessionStorage 取代） |
| **8 个 file 工具里的文件监控/文件链接** | 监控=常驻进程，链接=平台差异大。只做前 4 个实用的 |

### 6.5 一句话总结

**P0 四项的共同点：地基都在，只差"接线"**——ask_user 差一个文本字段，failover 差一个队列，T2 差一次接入，constants 差一次搬运。**这四项做完，第三章一级清单的 5 项里能消掉 3 项**（模型池、ask_user、多态交互通道）。

**剩下的 2 项（意图路由、多 Agent）建议正式废弃**——不是"以后再做"，是"不做"。FC 路线已经赢了，留着这些设计文档只会让后人误判方向。
