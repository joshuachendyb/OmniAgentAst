## 二、一句话结论（先给病根）

- **Q1 不是"自动展开"，是"你根本没收起成功"或"事件区长高了"，两者都不是真 bug**，是"操作没生效 + 区域自己长高"引起的误会。
- **Q2 是真 bug**：右侧有个"你是否主动上翻过"的隐形开关，它一旦被拨到"翻过"，就再也不自动滚底；弹窗这个流程里，**没人帮它拨回来**。

## 三、Q1 病根详解：为什么看着像"自动展开"

### 3.1 先看这个条是怎么折叠的

任务信息条（TaskInfoBar）折叠只靠一个动作：**点它第一行**（整行可点）。

- 点一次 → 收起（事件区消失）
- 再点一次 → 展开（事件区又出现）

折叠状态存在组件的 `collapsed` 变量里，初始是"展开"。

### 3.2 我穷举了所有可能让它"自己展开"的路，全都不存在（这段是铁证）

能让"已收起"的条重新展开，只有 4 条路，我逐条查了代码：

| 路 | 会不会发生 | 证据 |
|----|-----------|------|
| ①有人调用了"展开"代码 | 否 | 全代码库只有**一处**改折叠状态的代码，就是"点击第一行"（`TaskInfoBar.tsx:126`），没有任何 AI/自动逻辑调它 |
| ②组件被重新创建，状态归零 | 否 | 外层用固定 key 渲染（`SessionLayout.tsx:47`），组件只重画不重造，`collapsed` 一直保留 |
| ③面板被卸载再挂载 | 否 | 面板可见性读的是 `readPanelVisible`，本面板"永远可见"（`SessionPanelRegistry.ts:38`），不会卸载 |
| ④第一帧数据丢了，导致区域凭空出现 | 否 | 首帧 `start` 数据**无条件**写入（`sseParser.ts:187`），不会丢 |

**结论（铁证）**：只要你真的收起成功了，它就绝不会自己展开。代码里没有这条"自动展开"的路。

### 3.3 那"自动展开"的感觉从哪来？（这段是推断，等你确认，不是铁证）

- **推断A——双击抵消**：收起=点第一行。如果你**两下点快了**，等于"收起"+"展开"连点两下，互相抵消=**没反应**。你觉得自己收了，其实没收到。旧版里曾有一个单独的"收起"按钮，因为和整行点击重复、点两下互相抵消被删掉了——同样的坑现在在整行点击上。
- **推断B——事件区长高**：HITL 弹窗一开一关，事件区会新增"⏸️ 已暂停""▶️ 已继续"这样的记录行。如果之前事件区是空的（没内容就不渲染），现在冒出几行 → **区域凭空出现**；如果之前有几行，现在变高 → **区域变高**。这两种都像"自动展开"，但其实只是"事件区有内容了/长高了"。

### 3.4 说人话

```
你眼睛看到：我没点它，它自己展开了。
真相是：要么你双击没收到（推断A），要么区域有新内容长高了（推断B）。
代码铁证：真收起了就绝不会自己展开。
```

## 四、Q2 病根详解：为什么弹窗后不自动滚底

### 4.1 背景：软件有一个"防打扰机关"

右侧 step 区（RightViewer）有个设计意图很好的机关（`RightViewer.tsx:137`）：

- 它拿一个**隐形开关**记录"你有没有主动往上翻过"（看历史记录）。
- **你没翻** → 开关关 → 新内容一到就自动滚到底部（跟直播）。
- **你翻过** → 开关开 → 就不再自动滚了（尊重你，不跟你抢滚动条）。

复位方式只有一个：**你手动滚回底部**，开关自己就关回"没翻"。

### 4.2 弹窗流程怎么把开关搞死的（这是真 bug）

HITL 弹窗（要你批准工具）出现的时机和开关有很大关系：

- 弹窗前，你很可能**往上翻过**（比如回头看工具干了啥）→ 开关已经"开"了。
- 弹窗盖整个屏幕（窗帘 mask），**你没法滚回底部** → 开关永远是"开"。
- 你点"允许"或等倒计时自动放行 → 弹窗消失 → 新内容进来，本应滚底——但**开关还开着**，代码一看"哦用户上翻了，不打扰"→ **不滚**。
- 更阴的一个小枝：工具行是可以聚焦的（`ToolCallLine.tsx:293`）。弹窗关掉时，浏览器会把"焦点"还给之前那个工具行，**顺手把页面滚一小格让那行露出来**。这一滚，就被当成"你上翻了"，开关也被误拨成"开"。这就是你"有时候"才遇到的的元凶。**这条是机制实锤，但它在你机器上是否真的发生，需要真机验证。**

### 4.3 说人话

```
开关：你没上翻 → 自动滚底；你上翻 → 不打扰。
弹窗：盖住屏幕 → 你没法滚回去 → 开关卡在"翻过"。
结果：新内容来了不滚底 —— 因为代码以为你还在读上面。
```

## 五、修复方案（改哪里、改成什么样、为什么这样改）

### 5.1 Q1 修复：F1-A「前沿防抖」

**改什么**：`TaskInfoBar.tsx` 的整行点击。

**改成什么样**：第一次点击立即生效（收起），**300 毫秒内的第二次点击忽略**——双击不再互相抵消。

```tsx
// 2026-09-08 小欧 三堂会审后定案(F1-A 前沿防抖):
//   已查 utils 现有 debounce 是后沿语义(延迟执行), 用在折叠上会"点了没立刻反应", 故就地3行实现前沿防抖(YAGNI, 不提前抽公共)
const lastToggleRef = useRef(0);
// onClick 由原来的 setCollapsed((v) => !v) 改为:
onClick={() => {
  const now = Date.now();
  if (now - lastToggleRef.current < 300) return; // 300ms 内只认第一次(双击不抵消)
  lastToggleRef.current = now;
  setCollapsed((v) => !v);
}}
```

**为什么这样修**：双击一次收一次=抵消，是最可能的"假自动展开"来源。防抖后"点一下收、点一下开"永远灵。

**（另一个备选 F1-B：把可点的范围收窄，只留折叠箭头）** 也能减少误触，但会缩小点击区域、改 UI 手感，改动更大。**二选一，推荐 F1-A**。两个都上是重复修一个问题（违规），不做。

### 5.2 Q2 修复：F2-A「确认即跟随直播」（两段式，官方钩子不用魔法数）

**改两处**：

**① 确认瞬间派信号**（`useAuthorization.ts` 的 `handleAuthorizationConfirm`，`setAuthorizationPending(null)` 关窗的同一行附近）：

```ts
// 2026-09-08 小欧 F2-A①: 确认/自动放行瞬间派"跟随直播"信号(项目已有多事自定义事件先例, 合规)
window.dispatchEvent(new CustomEvent('authorization_follow_live'));
```

**② 右侧消费信号并滚底**（`RightViewer.tsx`，它自己就攥着那个隐形开关和滚底函数，不用绕）：

```tsx
useEffect(() => {
  // 2026-09-08 小欧 F2-A②: 弹窗确认即恢复跟播——清上翻标志+滚底,
  //   两段式: 第一段立即; 第二段延迟再清一次, 吃掉Modal关窗时浏览器焦点回滚那记误置(时机在其后)
  const follow = () => {
    userScrolledUpRef.current = false;
    scrollToBottomNow();
  };
  const followLate = () => {
    window.setTimeout(() => {
      userScrolledUpRef.current = false;
      scrollToBottomNow();
    }, 300); // 300ms 为估算, 真机验收时校准(覆盖关窗动画+焦点回滚)
  };
  window.addEventListener('authorization_follow_live', follow);
  window.addEventListener('authorization_follow_live', followLate);
  return () => {
    window.removeEventListener('authorization_follow_live', follow);
    window.removeEventListener('authorization_follow_live', followLate);
  };
}, [scrollToBottomNow]);
```

**为什么两段式**：老版本只做第一段。我复核发现：确认瞬间清了开关，但弹窗关掉时**浏览器焦点回滚会把开关又误拨开**（4.2 那个小枝）——只清一次会被"反拨"回去。所以第二段在关窗动画结束后（300ms 前后）**再清一次 + 再滚一次**，正好把焦点回滚那记吃掉。这是这次重写比旧版多补的关键一锹土。

**为什么不打扰上翻读历史**：只有"点了弹窗/自动放行"才清开关；你**没碰弹窗**、只是上翻读历史 → 信号完全不发 → 行为与现在一模一样，不退化。

**（另一个备选 F2-B：靠 resumed 数据到达时清开关）** 但 resumed 数据比确认慢（要等后端回来），点完确认到滚底之间有肉眼可见的空档；而且"谁让它滚"的语义没 F2-A 准。推荐 F2-A。

## 六、三轮严苛三堂会审结论（修法为何过关）

`前方缩进`。术语速查：**合规**=守不守编码纪律；**合理**=绕不绕、是不是最直；**关联**=有没有把别的功能弄坏。

### 第一轮 合规（10大规范）

| 检查项 | 结果 | 说明 |
|--------|------|------|
| 复用（先查后建） | ✅ 查过了 | 现有 `debounce` 是**后沿**语义，直接用在折叠上会"点了没反应"，故 F1-A 就地 3 行做**前沿**防抖，不重复造轮子也不硬套不适用的工具 |
| YAGNI（别过度设计） | ✅ | F1-A/F1-B 二选一共一个；两段式是必要补丁（焦点回滚真实存在），不算过设计 |
| KISS-DIRECT（最直） | ✅ | F2-A 派信号处=关窗同一瞬间；消费方=自己攥着开关和滚底函数的 RightViewer，不绕 |
| SRP/DRY/SLAP/禁止backward | ✅ | 信号只管"跟播"一件；不保留旧行为 |

### 第二轮 合理（最优雅、直线）

- 派发位置选在 `handleAuthorizationConfirm` 关窗同一行——语义直接："人点了弹窗=我还跟着呢"。
- 项目自定义事件三个先例（`authorization_required` / `authorization_resumed` / `omni-trust-changed`），不是新发明。
- 两段式用**确认瞬间 + 关窗后**两个自然锚点，不用拍一个魔法数扛全局（350ms 只是第二段的兜底间隔，真机校准）。

### 第三轮 关联（增强不退化）

| 场景 | 改前 | 改后 | 评价 |
|------|------|------|------|
| 上翻读历史，不碰弹窗 | 不滚 | 不滚（信号没发） | ✅ 守卫保留 |
| 点确认/自动放行 | 不滚（bug） | 确认即清开关→新内容滚底 | ✅ 修复目标 |
| resumed 数据晚到 | — | 开关已清，由现有 ResizeObserver 自然滚底 | ✅ 不新增链路 |
| 左栏消息区 | 自己有另一套开关 | 不受影响（信号只在右栏消费） | ✅ 不越界 |
| 路由切回任务 | 有重置逻辑 | 不变 | ✅ |

**结论：两处被会审打回重写——F1-A 由"后沿防抖"改"前沿防抖"；F2-A 由"一次性清标志"补成"两段式吸收焦点回滚"。其余全部过关。**

## 七、怎么算治好（验收清单）

- Q1：连点两下第一行 → 只收起一次（不再抵消）；再点一下 → 展开。
- Q1：收起状态下，HITL 弹窗开→关，事件区**不出现在**（还是收着的）。
- Q2：先上翻一点 → 弹窗确认/自动放行 → 新内容**自动滚到底部**。
- Q2：上翻读历史、不碰弹窗 → 弹窗消失后**依然不滚**（守卫生效）。
- Q2：连续多次 HITL，每次确认后都滚底（无"第一次好了第二次又坏"）。
