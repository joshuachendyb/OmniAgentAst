## 一、技术缺陷清单

### 🔴 缺陷1：state和ref双写导致闭包陈旧（严重度：高）

**位置**: `useSSE.ts:405-415`

**问题代码**:
```typescript
const [serverTaskId, setServerTaskId] = useState<string | null>(null);
const serverTaskIdRef = useRef<string | null>(null);
const syncServerTaskId = useCallback((id: string | null) => {
  serverTaskIdRef.current = id;
  setServerTaskId(id);
}, []);

useEffect(() => {
  isReceivingRef.current = isReceiving;
}, [isReceiving]);
```

**技术缺陷**:
1. **state和ref必须手动同步**，遗漏同步就会导致bug
2. **useEffect同步isReceiving是异步的**，ref更新滞后于state
3. **闭包捕获的是旧state值**，定时器/重连逻辑读到旧值误判

**已发生的真实bug**（代码注释实证）:
```
// 2026-08-30 小欧 根治陈旧闭包: reader挂起帧运行在旧render上, 
// state版serverTaskId在空闲定时器/重连守卫闭包中读到旧null值误判
```
```
// 2026-09-02 小欧 44case审计修复: SSE-02 isReceiving加Ref防闭包陈旧
// (空闲超时读旧值误重连)
```

**影响**:
- 空闲超时读旧isReceiving导致误重连
- 重连逻辑读旧serverTaskId导致误判
- 组件卸载后定时器在已死组件上触发

**根因**:
- React state在异步回调（setTimeout/setInterval）中捕获的是**闭包创建时的快照**
- ref是可变容器，始终读最新值
- 两者混用必须手动同步，容易遗漏

## 三、技术缺陷根因分析

### 3.1 React状态管理的根本问题

**问题**: React state在异步回调中捕获的是闭包创建时的快照，不是最新值。

**表现**:
```typescript
const [count, setCount] = useState(0);

// 这个timeout会捕获count=0，不是最新值
setTimeout(() => {
  console.log(count);  // 输出0，不是最新值
}, 1000);
```

**影响**:
- 空闲超时读旧isReceiving导致误重连
- 重连逻辑读旧serverTaskId导致误判
- 组件卸载后定时器在已死组件上触发

**解决方案**:
1. 使用ref代替state（已采用，但需要手动同步）
2. 使用useSyncExternalStore（React 18+）
3. 使用useEffect监听state变化并更新ref

---

### 3.2 React批处理机制的问题

**问题**: React 18会批量处理多个setState调用，prev是上一次render的值。

**表现**:
```typescript
// 这两个setState会被批量处理
setCount(1);
setName('Alice');

// 这里读到的还是旧值
setMessages((prev) => {
  console.log(prev);  // 旧值
  return [...prev, newItem];
});
```

**影响**:
- onComplete读取lastMessage.executionSteps是旧值
- final步骤丢失
- PipelineRenderer渲染不完整

**解决方案**:
1. 使用ref代替state（已采用）
2. 使用await new Promise(resolve => setTimeout(resolve, 0))强制刷新
3. 使用useSyncExternalStore

---

### 3.3 异步操作的竞态条件

**问题**: 多个异步操作可能同时执行，产生竞态条件。

**表现**:
```typescript
// onStep和onComplete可能同时执行
onStep(step1);
onStep(step2);
onComplete(response);  // 可能在onStep2之前执行
```

**影响**:
- 步骤顺序可能错乱
- final步骤可能丢失
- 状态不一致

**解决方案**:
1. 使用锁机制（Mutex）
2. 使用队列确保顺序执行
3. 使用状态机管理状态转换

## 四、真实可实施代码修复方案

### 4.1 缺陷1修复：创建useStateWithRef hook

**新增文件**: `frontend/src/hooks/useStateWithRef.ts`

```typescript
// 编辑历史: 2026-09-10 小欧 - 新增: 解决state和ref双写导致闭包陈旧问题 — 小欧-2026-09-10
/**
 * useStateWithRef - 同步state和ref的自定义hook
 * 
 * 问题背景: React state在异步回调中捕获的是闭包创建时的快照，
 * 而ref始终读最新值。两者混用必须手动同步，容易遗漏导致bug。
 * 
 * 解决方案: 封装state和ref，提供统一的setValue方法，
 * 确保state和ref始终保持同步。
 * 
 * @param initialValue 初始值
 * @returns { state, ref, setValue } - state用于渲染，ref用于异步回调，setValue用于更新
 * 
 * @example
 * ```typescript
 * const { state: serverTaskId, ref: serverTaskIdRef, setValue: setServerTaskId } = 
 *   useStateWithRef<string | null>(null);
 * 
 * // 同步更新state和ref
 * setServerTaskId('task-123');
 * 
 * // 在异步回调中安全读取最新值
 * setTimeout(() => {
 *   console.log(serverTaskIdRef.current); // 'task-123'，不是闭包快照
 * }, 1000);
 * ```
 * 
 * @author 小欧
 * @since 2026-09-10
 * @遵守规范 SRP单一职责 - 只负责state和ref同步
 */
import { useState, useRef, useCallback } from 'react';

interface UseStateWithRefReturn<T> {
  /** React state，用于触发重渲染 */
  state: T;
  /** React ref，始终读最新值，用于异步回调 */
  ref: React.MutableRefObject<T>;
  /** 统一更新方法，同时更新state和ref */
  setValue: (value: T | ((prev: T) => T)) => void;
}

function useStateWithRef<T>(initialValue: T): UseStateWithRefReturn<T> {
  const [state, setState] = useState(initialValue);
  const ref = useRef(initialValue);

  const setValue = useCallback((value: T | ((prev: T) => T)) => {
    const newValue = value instanceof Function ? value(ref.current) : value;
    ref.current = newValue;
    setState(newValue);
  }, []);

  return { state, ref, setValue };
}

export default useStateWithRef;
```

### 4.7 缺陷6修复：创建错误处理中间件

**新增文件**: `frontend/src/hooks/useSSEErrorMiddleware.ts`

```typescript
// 编辑历史: 2026-09-10 小欧 - 新增: 错误处理中间件，统一错误处理路径 — 小欧-2026-09-10
/**
 * useSSEErrorMiddleware - 错误处理中间件hook
 * 
 * 问题背景: 错误处理涉及3层（useSSE.handleSSEError、useChatStreaming.sseOnError、
 * useChatCallbacks.onError），每层都有自己的判断逻辑，调试困难，容易遗漏。
 * 
 * 解决方案: 使用中间件模式，将错误处理逻辑集中管理，
 * 每个中间件只负责自己的职责，顺序执行。
 * 
 * @example
 * ```typescript
 * const { processError } = useSSEErrorMiddleware({
 *   onReconnect: reconnectHandler,
 *   onDenied: deniedHandler,
 *   onError: errorHandler,
 * });
 * 
 * // 处理错误时调用
 * processError(error);
 * ```
 * 
 * @author 小欧
 * @since 2026-09-10
 * @遵守规范 SRP单一职责 - 只负责错误处理中间件编排
 */
import { useCallback, useRef } from 'react';
import type { SSEError } from '@/types/sse';

/**
 * 错误处理中间件类型
 */
type ErrorMiddleware = (error: SSEError) => boolean | void;

/**
 * 错误处理中间件配置
 */
interface SSEErrorMiddlewareConfig {
  /** 重连处理器 */
  onReconnect?: (error: SSEError) => void;
  /** 拒绝聚合处理器 */
  onDenied?: (error: SSEError) => void;
  /** 最终错误处理器 */
  onError?: (error: SSEError) => void;
}

/**
 * 错误处理中间件hook返回值
 */
interface UseSSEErrorMiddlewareReturn {
  /** 处理错误 */
  processError: (error: SSEError) => void;
  /** 注册中间件 */
  use: (middleware: ErrorMiddleware) => void;
}

function useSSEErrorMiddleware(
  config: SSEErrorMiddlewareConfig
): UseSSEErrorMiddlewareReturn {
  const middlewaresRef = useRef<ErrorMiddleware[]>([]);

  const use = useCallback((middleware: ErrorMiddleware) => {
    middlewaresRef.current.push(middleware);
  }, []);

  const processError = useCallback((error: SSEError) => {
    // 1. 执行所有注册的中间件
    for (const middleware of middlewaresRef.current) {
      const shouldContinue = middleware(error);
      if (shouldContinue === false) {
        return; // 中间件返回false，停止后续处理
      }
    }

    // 2. 执行内置中间件：拒绝聚合
    if (
      error.error_type === 'blocked' || 
      error.error_type === 'timeout'
    ) {
      if (typeof error.step === 'number' && config.onDenied) {
        config.onDenied(error);
      }
    }

    // 3. 执行内置中间件：后端业务错误分道
    if (error.from_backend === true) {
      console.info('[ErrorMiddleware] 后端业务错误: 只进P3, 不弹窗/不替换消息/不停计时');
      config.onError?.(error);
      return;
    }

    // 4. 执行内置中间件：重连判断
    if (error.retryable !== false && config.onReconnect) {
      config.onReconnect(error);
    }

    // 5. 执行最终错误处理器
    config.onError?.(error);
  }, [config]);

  return { processError, use };
}

export default useSSEErrorMiddleware;
```

- [ ] **SRP单一职责**: 新增/修改的函数只做一件事
- [ ] **DRY不重复**: 没有重复代码，复用已有函数
- [ ] **KISS简单直接**: 逻辑直线，不绕来绕去

- [ ] **类型安全**: 使用TypeScript类型，不使用any
- [ ] **错误处理**: 所有异步操作都有错误处理
- [ ] **注释**: 关键逻辑有注释，包含署名和日期
