## 一、问题与新需求

**A. 原有问题现象（信任失效，根因链见 三）**

1. 前端`TaskInfoBar`第一行尾部`信任(N)`有数，展开可`×`撤销，但下一轮同工具仍弹`HITL`确认窗，体感`信任不起作用`。
2. `security.enabled:false`时`信任(N)`有数但永不生效（全量`auto_confirm`直放，信任无意义但不报错）。
3. 极端下连续两步同工具调用，第二步仍需确认（E2E 自动化无人值守场景必现）。

**B. 本次讨论新增需求（老陈驱动 2026-09-02，定案见 五）**

4. **信任对象升级 tool+path（3.7 定案）**：信任从"整个工具"精确到"工具+目标路径（含子目录树）"；无路径工具退化工具级（`shell › 任意`）；存量信任清空不迁移。
5. **授权弹窗信任文案含 path**：勾选"信任此操作"须展示精确对象 `delete › D:\A（含子目录）` / `shell › 任意`，杜绝"文案对操作、实现对整个工具"的认知错位。
6. **bypass 僵尸窗根治——前端自动代发确认 + 后端 S1 窗口等确认（v1.5.8 老陈流程定案；v1.5.13 演进见 10）**：`enabled:false` 时弹窗不再"一直停留等待"。**完整流程**：
   - ① 后端发 HITL 确认请求（paused）后，**后端开始计时 S1**（= `security.auto_confirm_delay`，默认 5s）；
   - ② 前端弹窗，**前端倒计时到 `confirm_timeout`**（= 后端下发的有效倒计时，bypass 下 = S1−提前量 `BYPASS_AUTO_LEAD`(2) = **3s**，非前端写死，见下第 10 条）；到 0 时前端**主动向后端发送确认消息**——与人工点"允许执行"发送的**同通道同格式**（`POST /chat/stream/confirm{confirmId, confirmed:true, trust_session:false}`）；
   - ③ 后端**若收到**该确认消息 → **走确认流程**（确认+临时授权+执行）；
   - ④ 后端**若没收到**确认消息 → **S1 计时到 5 秒**（= 前端 `confirm_timeout`(3) + 提前量(2)，比前端多 2s 缓冲）→ 走 **bypass 自动确认**兜底放行。
   - 语义：前后端走**同一条 confirm 通道**，后端 `wait_for_confirmation_result` 收到即走确认、无浏览器/断连则 5s 兜底；`security.auto_confirm_delay` 可配置、0 禁用。**仅 bypass 生效，真 HITL 保留用户裁决**。
7. **bypass 弹窗视觉区分**：蓝虚线边框 + 标题"将自动确认（安全开关已绕开）" + 隐藏信任勾选 + 按钮禁用（仅提示 3s 后自动确认，3s = 后端下发的 `confirm_timeout`，见下第 10 条），一眼区分"自动代发非裁决"；真 HITL 保持橙实线阻塞等待。
8. **bypass 明确透传标识**：后端 emit `paused` 加 `auto_confirm` 单参数（复用 `tool_safety_checker` 既有标志，不新增 bypass 布尔），前端识"自动放行=无裁决权"。
9. **超时加倒计时提示（倒计时由后端下发，v1.5.14 修订）**：弹窗显示剩余秒数，超时自动动作前给用户明确预告。前端不再写死 60s，倒计时长度由后端 `emit paused` 下发的 `confirm_timeout` 决定（详见下第 10 条）。
10. **倒计时机制 + 到时发送动作（v1.5.13 老陈公式定案，5.10）**：后端为唯一计时权威，前端倒计时=**后端窗口−提前量**，前端只消费展示、到 0 自动发，前后端不竞态：
   - **真·HITL**：后端窗口 `HITL_TIMEOUT`(120) − 提前量 `HITL_CONFIRM_LEAD`(10) = **`confirm_timeout` 110s**，前端环形+大数字从 110→0 倒数、提示「未响应将在 Ns 后自动拒绝」；到 0 **自动发送** `POST /chat/stream/confirm{confirmId, confirmed:false, trust_session:false}`（拒绝）；
   - **bypass**：后端窗口 `security.auto_confirm_delay`(S1=5) − 提前量 `BYPASS_AUTO_LEAD`(2) = **`confirm_timeout` 3s**，前端环形+大数字从 3→0 倒数、提示「将在 Ns 后自动确认（后端 Ns 兜底）」；到 0 **自动发送** `POST /chat/stream/confirm{confirmId, confirmed:true, trust_session:false}`（代发，同人工点"允许"格式）；
   - **两字段下发**：`confirm_timeout`(前端有效倒计时) + `backend_timeout`(后端实际窗口，供"后端 Ns 兜底"提示)；提前量固化为常量 `HITL_CONFIRM_LEAD=10`/`BYPASS_AUTO_LEAD=2`（constants.py）；**前端到 0 的动作必早于后端 wait/兜底**，后端"收到即走"，消除同归零竞态；改 config 一个数前端倒计时自动跟随。

## 二、现状链路（以本地代码为准）

### 2.1 写入主通道（唯一）

`AuthorizationModal:64`勾`信任此会话`→`useAuthorization:71 onConfirm(confirmed, trustSession=true)`→`task.api:57 POST /chat/stream/confirm{confirm_id, confirmed, trust_session}`→`chat_routes.py:74 resolve_confirmation(confirm_id, confirmed, trust_session)`→`hitl_confirmation.py:135 resolve_confirmation`→`entry.future.set_result`后`若confirmed&&trust_session&&tool_name`则后台`daemon Thread`投递`_persist_session_trust`→`storage.py:548 insert_session_trust(session_id, normalize(tool_name))`，`session_id`由`confirm_id`前缀`task_id`反查`get_session_id_by_task`（禁伪`agent.session_id`）。

### 2.2 读取/消费

`action_handler.py:281 _session_id = await db.atxn(get_session_id_by_task(agent.task_id))`→每工具`action_handler.py:303 _skip = await db.atxn(check_session_trust(_session_id, normalize(_cn)))`→`tool_safety_checker.py:184 if skip_confirmation: return SafetyResult(requires_confirmation=False, blocked=False, safety_level=safe)`→`action_handler.py:322 if requires_confirmation`分支跳过，不发`paused`，直行。

### 2.3 查询/撤销（D1/D3）

`trustApi.getTrust → GET /sessions/{session_id}/trust → storage:565 list_session_trust`；`trustApi.revokeTrust → DELETE /sessions/{session_id}/trust/{tool_name} → storage:575 delete_session_trust`。面板`TaskInfoBar:72`与`TrustPanel:37`均监听`omni-trust-changed`事件（`hitl`落库后`useAuthorization:83`派发）刷新。

### 2.4 归一化

落库`hitl_confirmation.py:171 normalize_tool_name(entry.tool_name)`与查询`action_handler.py:303 normalize_tool_name(_cn)`双归一，防`write_text/writefile/writetext`别名漏配（与`tool_safety_checker:257`写保护同模式）。

### 2.5 安全三级分级与信任豁免边界（v1.5 补全，北京老陈 2026-09-02 定案）

`tool_safety_checker.py check_before_execute` 返回 `SafetyResult`，其中 `safety_level` 三档（`safety_result.py:26`）：

| safety_level | 含义 | 行为 | 信任能否豁免 | 前端表现 |
|---|---|---|---|---|
| `safe` | 无危险 | 直接放行，不弹窗 | —（无需豁免） | 无任何提示 |
| `destructive` | 有危害 | `requires_confirmation=True`，HITL 弹窗确认后执行，并触发沙箱预检 | **能**（trust 会话信任跳过确认） | 弹窗确认框 |
| `dangerous` | 危险 | `blocked=True`，**后端直接拒绝执行**（`action_handler.py:313` `continue`，不进确认分支） | **不能**（信任/开关/bypass 均无效） | 收到 `error_type="blocked"` 事件 → TaskInfoBar 显示 `🛑 [被安全策略拦截: xxx]`，无任何按钮可放行 |

关键约束：**v1.5 tool+path 信任仅作用于 `destructive` 级（跳确认弹窗），`dangerous` 级永远拦截，`safe` 级无需干预**。信任不改变工具本身的危险程度，只决定是否弹窗询问。

> 前端处理：blocked 事件经 SSE → `sseParser.ts:465` 提取 `error_type="blocked"` → `onError` → `liveErrorText` → `TaskInfoBar.tsx:174-186` 渲染 `🛑 [被安全策略拦截: xxx]`；不入执行步骤列表（`sseParser.ts:503-506`），无交互按钮，仅通知。

## 三、根因分析（经得起三堂会审）

### 3.1 主因：落库异步竞态（可复现）

`hitl_confirmation.py:163-181`为避`API层直调`的`sqlite3 I/O+锁重试 sleep`阻塞，`resolve_confirmation`为`同步函数`，信任落库改`daemon Thread`异步投递，`API先返回True`、信任行后落。注释`hitl_confirmation.py:164`已自认：`极端下确认后毫秒级下一个工具调用可能因信任行未落而多弹一次`。实测：LLM在`confirmed`后`1s`内再调同工具，第二步`check_session_trust`查库`尚未提交`→`_skip=False`→仍弹窗。`security.enabled:false`路径虽全`auto_confirm`直放不走信任，但同窗在`true`时必现。

### 3.2 次因：反查失败静默丢弃

`hitl_confirmation.py:173 _sid = get_session_id_by_task(_conn, _task_id)`若`_task_id`尚未在`chat_tasks`建行（极早确认）或`session_id IS NULL`，则`warning`跳过落库，无重试。`action_handler.py:286`同理`_session_id=None`则`_skip`恒`False`（按需确认），信任永不命中。→ **修复见 5.1-①**（反查失败改 `raise`→atxn 回滚并告警，不再静默丢；HITL 只发生在 agent 执行工具阶段、`chat_tasks` 必已建行，正常路径不可达，遇异常数据显式暴露）。

### 3.3 非根因（已正确）

* `security.enabled`开关语义：仅`bypass`确认（`tool_safety_checker.py:140 auto_confirm`），危险`blocked`仍拦；信任豁免仅跳`requires_confirmation`不跳拦，层级正确。
* 前端链路：`AuthorizationModal`受控重置`trustSession`（`AM-01`已修）、面板`reqId`防切会话竞态（`#50`已修）、事件派发`sessionId`隔离均正确；面板仅展示，无逻辑缺陷。

### 3.4 真主因（v1.2 三堂会审补全）：known_risk 优先于 skip_confirmation，白名单外授权类信任必然失效

`tool_safety_checker.py:133-147`：白名单外路径/临时授权请求（`_check_known_risks` 返回 `requires_confirmation=True + auth_path`）在 **`skip_confirmation` 豁免分支（`tool_safety_checker.py:184`）之前先行 return**，且该分支**完全不检查 `skip_confirmation`**。

结论：凡命中"白名单外路径写入/临时授权"类工具（最常见的 HITL 场景），即使`check_session_trust` 命中、信任行已落库，**下一轮同工具仍必弹确认窗**——信任豁免对这类工具**必然失效**。

与 3.1 竞态的关系：竞态只解释"同批毫秒级连调"与"确认后极速再调"（现象3），**解释不了现象1（下一轮 LLM 回合>1s 仍弹窗）**；3.4 才是现象1的**必然主因**。v1.0/v1.1 将失效全归于竞态，定性偏差，需本补全修正。

### 3.5 豁免不携带 auth_path，信任"跳窗不放行"（授权不闭环）

`tool_safety_checker.py:184-190` 豁免返回 `SafetyResult(requires_confirmation=False, ...)` **不含 `auth_path`**；`action_handler.py:402` 的 `grant_temp_auth` 仅在 `requires_confirmation` 分支内执行，豁免分支（`action_handler.py:428-436` 插入点③）**不授权**。

结论：即使按 3.4 修正次序让豁免生效，对白名单外类工具"跳过确认却无临时授权"，工具内部 `validate_path` 仍拦截 → 工具执行失败。豁免要真正闭环，必须在豁免时**保留并授予 `auth_path`**。

### 3.6 `security.enabled:false` 时信任清单污染（v1.0 误归"已正确"）

`action_handler.py:352` auto_confirm 分支无条件 `resolve_confirmation(confirm_id, confirmed=True, trust_session=True)` → `security.enabled:false`（全量 bypass）时，每个需确认工具**自动落库一行信任**，TrustPanel 出现用户从未勾选的工具（清单污染）。v1.0 的 3.3 将该现象归为"非根因/已正确"，掩盖了此可见 bug；且若按 v1.1 的 5.1 改为同步 await 落库，此处**每工具必落一行成功，污染加重**（设计负效应）。

**危害升级（v1.3 补全）**：这批自动信任**不过期、不随 bypass 关闭而撤销**——切回 `enabled:true` 后 `check_session_trust` 照样命中，`action_handler.py:303 _skip=True` → 白名单外/需确认工具被**实际豁免**。即 bypass（免审旁路）期间的系统自动信任自动"转正"为长期用户授权，安全语义被破坏：用户从未同意、却获得永不失效的免审豁免。

**体验危害（v1.5.3 补全，老陈实测纠正）**：bypass 下 paused 确认消息**照常发**（`action_handler.py:330-339`），但前后端行为割裂：
- **后端不等用户**：paused 发出后 `action_handler.py:341 auto_confirm` 分支立即 `resolve_confirmation`（L352）→ 工具已实际执行，随后发 resumed（L369-373）badge 恢复。
- **前端弹窗不自动关**：弹窗只在两处关闭——①用户点按钮、②60秒超时（`useAuthorization.ts:53-59`）。**resumed 事件只更新 badge，不触发 `setAuthorizationPending(null)`**，故弹窗不会一闪而过，而是**"僵尸窗"一直停留等待操作**（最久 60s）。
- **误导无裁决权**：用户面对弹窗误以为仍有裁决权，实际无论点确认/拒绝，工具**早已执行完毕**，所选无效。此为 3.6 的第二重危害（第一重为信任污染，第二重为 UI 误导无裁决权）。

### 3.7 信任粒度放大：文案"信任此操作"、实现"信任整个工具"（v1.3 补全）

`check_session_trust`（`storage.py:556-562`）只查 `session_id + tool_name` 两列，**不比对参数/路径**；`insert_session_trust` 落库也只有 `(session_id, tool_name, created_at)`（`storage.py:548-553`）。表结构 `chat_session_trust`（`db_initializer.py:138-145`）即工具级。

后果：前端授权弹窗文案"本次会话信任**此操作**"（`AuthorizationModal:177`）与实现语义不符——实际授予的是"同会话**整个工具**任意参数任意路径"的豁免。例：用户允许删除 `C:\foo\旧文件.txt` 并勾信任 → 同会话 LLM 删除 `C:\bar\重要资料.txt` **免确认直删**。删除/写盘类高风险工具尤其危险。

**定案（2026-09-02 北京老陈）**：信任对象必须是 `tool+path` 才准确——"只有 tool 没有意义，tool+path 才是准确的一个对象，才谈信任与不信任"（老陈原话）。粒度取**路径前缀递归**（信任某路径则其子目录树一并豁免，与 temp_auth 递归语义对齐）；无路径参数工具退化**工具级**（path=NULL=通配任意）；存量信任**全部视为无效清空**。完整实现见 5.5。

### 3.8 confirm 接口无鉴权（v1.3 补全，低危知悉级）

`POST /chat/stream/confirm`（`chat_routes.py:69-84`）无任何身份/会话校验，只验 `confirm_id` 是否存在。`confirm_id` 结构 `task_id + ":" + uuid4().hex[:8]`（`hitl_confirmation.py:85`），task_id 可枚举、随机段仅 32bit。知悉 `confirm_id` 者即可代用户确认并在本会话写入信任。属内网弱边界，非本次主隐患，记录待加固。

## 四、正确逻辑（北京老陈定案）

1. **归属**：信任归`会话`（`session_id`），消费归`任务`（`task_id`），一行一工具`normalize_tool_name`，跨`task`复用，会话删`CASCADE`。
2. **触发**：仅`HITL`弹框勾`信任此会话`且`confirmed=True`时写入，无独立`POST /trust`；查询/撤销为`D1/D3`独立`REST`。
3. **生效**：下一次同会话同工具（归一化后）调用起即免`paused`，直到`DELETE /trust/{tool}`或会话删；`blocked/dangerous`永不豁免。
4. **可见性**：`落库成功`与`confirm`成功强一致——用户勾信任后`立刻`不弹窗，不允`多弹一次`。
5. **优先级**：`security.enabled:false`时信任无意义（全`auto_confirm`），不报错不落库分支可保留；`enabled:true`时信任为唯一免扰通道。

### 5.5 信任精确化 tool+path（v1.5 定案，病根 3.7，北京老陈 2026-09-02 定案）

**定案三则**（老陈原话"只有 tool 没有意义，tool+path 才是准确对象"）：
1. **路径前缀递归**：信任路径=P，豁免 P 及其整个子目录树（`P == target or P in target.parents`），与 `temp_auth` 递归语义对齐；精确文件信任则该文件本身。
2. **无 path 工具级退化**：无路径参数的工具（shell 等）信任行 `path=NULL`=通配任意，维持工具级语义。前端信任列表**每行必带 path 展示**：有路径显示 `delete › C:\foo`；无路径显示 `shell › 任意`（用户强调：列表中有 path 才是有意义的信任对象）。
3. **存量全部视为无效清空**：旧表无 `path` 列，首次迁移重建（DROP+CREATE），存量工具级信任不放行、需重勾。

**机制双分立（回答"豁免不携带 auth_path 怎么解决"）**：`chat_session_trust(…, path)` 是**信任持久化**（判定依据）；`grant_temp_auth(auth_path)`（5.3-⑤，不变，task 级 ContextVar）是**执行放行底座**（validate_path 关卡）。命中信任→still 需 grant 目标路径才过工具层校验——二者各司其职，不可互相替代。

    """工具安全检查豁免查询：会话已信任该 tool+path 则免二次 HITL 确认 — 小欧 2026-08-16; v1.5 增 path 前缀递归匹配

        "SELECT path FROM chat_session_trust WHERE session_id=? AND tool_name=?",
        (session_id, tool_name),

    if path is None:
        return any(r["path"] is None for r in rows)

    return False

### 5.8 bypass 自动放行：前端 confirm_timeout 倒计时到0自动代发确认 + 后端 S1 窗口等确认（收到即走确认流程 / 超时 bypass 兜底）（v1.5.8 老陈定案，v1.5.13 演进计时见 §5.10）

**问题（承接 3.6 体验危害）**：bypass（`security.enabled:false`）下 paused 确认消息照发、后端自动执行、但前端弹窗沦为"僵尸窗"——一直停留（最久60s）等待用户操作，而用户无论点什么都无效（工具早已执行）。老陈实测确认我此前"一闪而过"判断错误，正确体验是"一直呆着等待操作"。

**设计原则**：按是否 bypass 区分弹窗两种形态——
- **真·HITL**（`enabled:true`，需用户裁决）：保持当前**阻塞等待** + 橙色警示边框，用户有真实裁决权（不变）。
- **bypass 自动放行**（`auto_confirm=True`）：**前端 `confirm_timeout` 倒计时到 0 自动代发确认 + 后端 S1(=5s) 窗口等确认** + 区分边框——让流程"先跑起来而不挂死"，且复用真实确认通道统一前后端语义。

**bypass 参数（回应老陈"需要加什么参数让前端知道是 bypass"）**：**加 `auto_confirm: bool` 一个参数**足矣——后端 `tool_safety_checker.py` bypass 路径本来就置 `auto_confirm=True`（L157/L141），是 bypass 的天然信号，前端据此识别"自动放行=无裁决权=通知形态"。不需要额外 `bypass` 布尔标志（避免与既有 `auto_confirm` 语义重复、DRY 反模式）。`MetaStep` 已支持 `**kwargs` 透传，零基类 schema 改动。

**老陈流程定案（v1.5.8，v1.5.13 演进：前端计时改为后端 confirm_timeout 驱动）**：
1. 后端发出 HITL 确认请求（`paused`）后，**后端开始计时 S1**，同时 emit 下发 `confirm_timeout`(=S1−提前量2=3s) 与 `backend_timeout`(=S1=5s)。
2. 前端弹窗，**前端从 `confirm_timeout`(=3s) 开始倒计时**。倒计时到 0，前端**主动向后端发送确认消息**——与人工点击"允许执行"发送的 **同样格式**（`POST /chat/stream/confirm{confirm_id, confirmed:true, trust_session:false}`）。
3. 后端**若收到**该确认消息 → **走确认流程**（确认+临时授权+执行）。
4. 后端**若没收到**确认消息 → **S1 计时到 5 秒**（S1 = confirm_timeout(3) + 提前量(2)）→ 走 **bypass 自动确认**兜底（放行）。

**为什么 3+2=5（合理性，回应老陈"3秒、5秒怎么定"）**：前端 confirm_timeout(=3s) 是自动代发时刻（正常人眼识别+弹窗展示的舒适下限）；后端 S1=5s 是"等待窗口上限"，比前端 confirm_timeout 多提前量(2s)：正常时前端 confirm_timeout 到 0 发出的确认在 5s 内必然到达后端（走后端收到即返回，不必等满 5s）；异常时（前端崩溃/无浏览器/断连）5s 兜底，比"前端 confirm_timeout + 网络抖动"留出裕量。**S1 收到即返回**（不等满 5s），仅超时兜底才用满 5s。

**复用真实确认通道（核心机制，已核实 `hitl_confirmation.py`）**：
- `create_confirmation`(L70) 建 `_pending_confirmations[confirm_id].future`。
- 前端 confirm 消息 → API `/chat/stream/confirm` → `resolve_confirmation`(L135) `future.set_result({confirmed:true, trust_session:false})` → **后端据此"收到"**。
- 后端 `wait_for_confirmation_result(confirm_id, timeout=S1)`(L94) 在 future 上 `await`——**收到即返回**（不提前 resolve、不 sleep 满），超时返回 `{expired:True}`。
- 即：后端 bypass 从"自己立即 resolve"改为"**wait_for_confirmation_result 等前端消息**"，零新机制，前后端走同一条 confirm 通道（KISS-DIRECT 最优复用）。

**风险评估（必须只作用于 bypass auto_confirm 分支）**：无浏览器/纯后端 E2E 时，每个需确认工具等满 5s 才兜底（慢 5s/工具）——属故意代价（等前端确认，而非单方面放行），与"模拟人工确认"语义一致；`S1` 做成可配置（`security.auto_confirm_delay` 默认 5s，可设 0 跳过等待=旧立即放行）。**绝不可套用到真 HITL**（否则丢失真实裁决权，退化为全自动，严重退化）。

> **完整实现 diff（5 处）→ 统一由 §5.10 diff①-⑦ 实现**（v1.5.13 前后端计时关联+倒计时落地，取代本节旧写死计时代码）：action_handler auto_confirm 分支（diff①）/ paused emit `auto_confirm`+`confirm_timeout`+`backend_timeout`（diff①）/ sseParser 提取三字段（diff②）/ AuthorizationRequest 接口 + useAuthorization 透传（diff③④⑤）/ AuthorizationModal 倒计时+环形进度+到0自动动作（diff⑥⑦）。

### 5.9 HITL 确认时序与 TaskInfoBar 徽标状态机（v1.5.6，2026-09-02 老陈驱动，流程逻辑与显示更新对应）

**核心认知（三思三省结论）**：前端徽标是**纯派生态**——不读后端 `set_status`/AgentStatus，只认收到的 SSE 元事件类型（`paused`/`resumed`/`final`）。故"流程逻辑"与"显示更新"必须**逐事件对标**，任何一侧漏发/多发都会造成徽标与真实执行错位。

**徽标状态机（`useTaskInfo.ts:121-176` + `TaskInfoBar.tsx:45-52` BADGE_MAP）**：

| SSE 元事件（type） | 前端 badge | 徽标显示 | 触发点（后端） |
|---|---|---|---|
| `paused` | `paused` | **已暂停**（黄 ⚠️） | `action_handler.py:330`（需确认） |
| `resumed` | `running` | **执行中**（蓝 ◉） | `action_handler.py:409`（真HITL确认后）/ `:369`（bypass） |
| `final` | completed/failed/cancelled | 已完成/失败/已取消 | 终态 step |

**兜底（防卡死）**：paused 之后的**业务推进 step（thought/action/observation）** 会把 badge 自动回推 `running`（`useTaskInfo.ts:164-172`）——即使某路径漏发 resumed，耗时秒表也会恢复，不永久卡"已暂停"。

**场景一：真·HITL（`enabled:true`，用户裁决）**——既有路径，经纬标对照：

| 时序 | 后端行为 | SSE 事件 | 徽标 | 弹窗 |
|---|---|---|---|---|
| ① 遇需确认工具 | `set_status(SUSPENDED)` + emit paused（L330/376） | `paused` | **已暂停** | **橙实线阻塞窗**（等用户） |
| ② 用户点"允许执行" | `resolve_confirmation` → `set_status(EXECUTING)` + emit resumed（L402-415，含 grant_temp_auth/sandbox） | `resumed` | **执行中** | 关闭 |
| ③ 工具执行完毕 | emit final | `final` | 终态 | — |

> 说明：confirm 返回、能执行后徽标显示**执行中**最合理——工具真正开始跑，且耗时秒表被 resumed 解锁恢复走表（`:108` 需 `badge==='running'`）。用户勾"信任"后同工具下次调用直接跳过 paused（5.5 落地），徽标不再经历"已暂停"。

**成对性与回复驱动细则（老陈三思确认，v1.5.6 补充）**：

- **paused 语义**：后端**发起 HITL 确认动作时** emit 的 yield 类型（`action_handler.py:326-339`）——先 `create_confirmation` 落一条"待确认"记录，再 emit `paused`，前端据此弹窗。
- **resumed 语义**：后端**收到前端 confirm 回复且 `confirmed=True` 后**，才向前端 emit 的 yield 类型（`action_handler.py:376-409`）——`await wait_for_confirmation_result`（L377）等到回复后，若 `not auth.get("confirmed")` 走拒绝/超时分支，否则 `set_status(EXECUTING)` + emit `resumed`。
- **成对性载体=confirm_id**：`paused` 携带 `confirm_id`（L335），前端确认时原样回传 `POST /chat/stream/confirm{confirm_id,...}`（`task.api:54`），后端据此**精确定位**是哪一个暂停挂起被恢复——即"发起的确认"与"恢复的执行"由 `confirm_id` 一一对应成对。
- **拒绝/超时不发 resumed，走 error**：用户点"拒绝执行"→ `confirmed=False` → emit `MetaStep(type="error", error_type="user_rejected")`（L391-393）；60s 超时 → `error_type="timeout"`（L384-386）。此时 `paused` **不配 resumed**，徽标从"已暂停"直接由 error/final 收敛，不会误亮"执行中"。这是"成对"的**例外合法场景**。
- **bypass 的成对**：paused → resumed 仍成对（`action_handler.py:330/369`），但由**前端倒计时到 confirm_timeout=0 自动代发确认**驱动（v1.5.8/v1.5.13）：前端倒计时到 0 发 `confirm(confirmId, true, false)` → 后端 `wait_for_confirmation_result(S1=5s)` 收到即走确认流程；前端未发则 S1 到 5s 后端 auto_confirm 兜底放行（5.8）。

**场景二：bypass（`enabled:false`，前端 confirm_timeout 倒计时到 0 自动代发确认 + 后端 S1 窗口）**——v1.5.8/v1.5.13 落地后经纬标对照：

| 时序 | 后端行为 | SSE 事件 | 徽标 | 弹窗 |
|---|---|---|---|---|
| ① 遇需确认工具 | emit paused（带 `auto_confirm=True` + `trust_path`），开始计时 **S1(=5s)** | `paused` | **已暂停**（瞬时） | **蓝虚线窗**（"将自动确认（安全开关已绕开）"，提示 3s 后自动确认） |
| ② confirm_timeout 倒计时到 0 | （前端自动代发确认） | （无新事件，徽标仍"已暂停"） | **前端倒计时到 0 自动 `confirm(confirmId, true, false)` 发确认消息** |
| ③ 后端收到确认 | `wait_for_confirmation_result(S1)` 收到即返回 → set_status(EXECUTING) + emit resumed（含 grant_temp_auth/sandbox）。**收到即走确认流程，不必等满 5s** | `resumed` | **执行中** | 关闭 |
| ③′ 后端未收到（S1 满 5s） | `wait_for_confirmation_result` 超时返回 expired → bypass 兜底放行 → set_status(EXECUTING) + emit resumed | `resumed` | **执行中** | （前端若在线已代发；未在线则无弹窗） |
| ④ 工具执行完毕 | emit final | `final` | 终态 | — |

> **bypass 时序澄清（老陈定案 v1.5.8）**：
> - **前端 confirm_timeout**（=S1−提前量2=3s）= 自动代发确认时刻；**后端 S1=5 秒（confirm_timeout + 提前量）** = 等待确认上限；前端 confirm_timeout 到 0 发出的确认在 5s 内必达后端，**后端收到即走确认流程（不等满 5s）**，仅前端未发才用满 5s 兜底。
> - 前后端走**同一条 confirm 通道**（前端代发 = 人工点"允许"同格式），后端用 `wait_for_confirmation_result` 等待，语义统一（5.8）。
> - 若 `security.auto_confirm_delay=0`（禁用）：②③ 瞬间跳过，paused 后立刻 resumed，徽标"已暂停"只闪一瞬即归"执行中"（旧快闪语义）。

**显示与流程的更新闭环（本轮新增需求对应）**：

| 新需求（§一-B） | 流程逻辑更新 | 显示更新 |
|---|---|---|
| ④ tool+path 信任 | 5.5 check/insert 带 path | 弹窗勾选文案 `tool › path（含子目录）`（5.7-④） |
| ⑥ bypass 僵尸窗根治 | 5.8/5.10 前端 confirm_timeout 倒计时到 0 自动代发 + 后端 S1 wait 确认 | 徽标 已暂停→执行中；弹窗倒计时到 0 自动代发关闭 |
| ⑦ bypass 视觉区分 | — | 蓝虚线边框 + 标题 + 隐藏信任 + 禁按钮（5.8-⑤） |
| ⑧ bypass 透传标识 | 5.8-① emit `auto_confirm` | isBypass 分流渲染（5.8-⑤） |
| ⑨ 倒计时落地（后端 confirm_timeout 下发） | 5.10 后端 emit paused 下发 confirm_timeout | 弹窗环形进度+大数字倒计时 + 到 0 自动动作（5.7-④ + 5.10-⑥⑦） |

**结论**：paused→**已暂停**、resumed→**执行中**是唯一正确且已被前端实现的映射；新设计（5.7/5.8）不改变该映射，只改变"何时发 paused/resumed、弹窗与徽标如何配合展示"。**流程逻辑与显示须按上表同步落地，任何环节改动不得破坏 paused→resumed 配对的成对性**（否则徽标卡"已暂停"或误亮"执行中"，均为退化）。

### 5.10 前后端计时关联（后端唯一计时权威：前端倒计时=后端窗口−提前量）+ 倒计时视觉落地（v1.5.13，2026-09-02 老陈驱动三审定案）

**问题（老陈三问核实，基于真实代码）**：
1. **bypass 两计时无运行时关联**：前端 3s 自动代发倒计时**写死**（5.8 设计 `setTimeout(onConfirm(true,false),3000)`），后端 `S1=5s` 前端**根本不知道**——两计时只有文档上"约定 3+2"的静态关系，改后端 S1 前端毫无感知，关联性未体现。
2. **真 HITL 前后计时不一致（更严重）**：前端 60s 写死（`useAuthorization.ts:59` 的 `60000`），后端 `wait_for_confirmation_result` 用 `HITL_TIMEOUT`（`constants.py:123` = **120s**）——**前端 60 秒 vs 后端 120 秒根本对不上**；前端先到 60s 自动 `confirm(false,false)` 拒绝，后端却还要等到 120s 才超时。且 `useAuthorization.ts:50` 注释写着「60秒与后端一致」——**系假话**（后端实际 120s）。
3. **前端无倒计时数字显示**：`AuthorizationModal/index.tsx` 里**根本没有 countdown 状态**（L64 仅 trustSession），5.7 设计的"60s 超时倒计时提示"从未落地——用户看不见还剩多少时间。老陈要求：**倒计时数字必须落实**，且视觉要「醒目但不唐突」。
4. **（v1.5.12 老陈新发现）前端倒计时不应等于后端超时上限**：若前端倒计时/代发时刻与后端 `wait`/兜底窗口**同归零**，会引发前后端同时到点的**竞态**（前端动作慢半拍则被后端兜底抢先，语义错乱）。须让**前端倒计时提前于后端窗口一个安全量**。

**设计原则（老陈三审定案：后端为唯一计时权威 + 前端倒计时=后端窗口−提前量）**：前端倒计时的**有效长度**恒 < 后端实际窗口，用一个**安全提前量**错开归零点：
- **通用公式**：`confirm_timeout（前端倒计时长度）= 后端窗口 − 提前量`；
- 提前量固化为**常量**：真HITL `HITL_CONFIRM_LEAD = 10`、bypass `BYPASS_AUTO_LEAD = 2`；
- **前端倒计时到 0 即自动动作**（非中途点）：bypass → `confirm(true,false)` 代发；真HITL → `confirm(false,false)` 拒绝。

**两种情况下发给前端的秒数（老陈 v1.5.12 公式定案，v1.5.13 落实）**：

| 形态 | 后端窗口（权威） | 提前量（常量） | **前端倒计时 `confirm_timeout`** | 到 0 自动动作 |
|---|---|---|---|---|
| **真·HITL** | `HITL_TIMEOUT`（常量 **120s**） | `HITL_CONFIRM_LEAD`=**10** | **120−10 = 110s**（显示 110→0） | 自动 `confirm(false,false)` 拒绝 |
| **bypass** | `security.auto_confirm_delay`（S1=**5s**，可配置） | `BYPASS_AUTO_LEAD`=**2** | **5−2 = 3s**（显示 3→0） | 自动 `confirm(true,false)` 代发 |

> **合理性（老陈求证"这个逻辑对吗"——回答：方向对，采纳并细化）**：前端倒计时**提前**于后端归零，保证前端动作（代发/拒绝）总是在后端 `wait`/兜底**之前**发出——后端"收到即走"（`resolve_confirmation` 立即 `set_result`），不会与后端自超时（`expired`）同时到点竞态。
> - 真HITL 前端 110s 提前 `confirm(false,false)` 拒绝 → 后端收到即走 `user_rejected` 分支（非 `timeout`）——语义清晰，不再"前端 60 / 后端 120"漂移；
> - bypass 前端 confirm_timeout(=3s) 提前代发（后端 S1=5s 窗口内）→ 后端收到即走确认流程——前端代发时刻(confirm_timeout=3s) 与后端兜底(S1=5s) 两条线在**一条倒计时**（3→0）上可视关联；即使前端崩/断连未代发，后端仍保留 2s 裕量到 S1 满 5s 兜底放行。

**后端下发两字段（老陈定案：源头单一个配置/常量，前端零硬编码）**：
- **`confirm_timeout`**：前端**有效倒计时**长度（= 后端窗口 − 提前量，即 110 / 3）——前端环形据此倒数，到 0 自动动作；
- **`backend_timeout`**：后端**实际窗口**（真HITL=120 / bypass=5）——前端界面提示「后端 Ns 兜底」用，把"前端倒计时"与"后端窗口"两个数都下发，相关性可感。
- 原 `auto_confirm_after` 字段**废弃**（被 `confirm_timeout=窗口−提前量` + 到 0 自动动作 取代，避免字段冗余，KISS/DRY）。

> **如此前后端相关性真实建立**：`confirm_timeout`、`backend_timeout` 均源于后端同一权威（真HITL=`HITL_TIMEOUT` 常量 / bypass=`security.auto_confirm_delay` + 两提前量常量），前端只做"消费展示+到0回调"，**改后端 config（如 `auto_confirm_delay`）一个数，前端倒计时自动跟随**，不再各自硬编码。

**复用既有透传链路（零新机制）**：`MetaStep(**kwargs)`（`base.py:121/133/147`）已支持任意字段透传（5.7/5.8 同款）→ `sseParser` paused 分支提取 → `useChatCallbacks` `CustomEvent` → `useAuthorization` `setAuthorizationPending` → `AuthorizationModal`。仅新增两个字段，链路不变（KISS-DIRECT）。

**倒计时视觉落地（老陈定案：环形进度条 + 大数字，「醒目不唐突」）**：弹窗内新增倒计时组件，用 Ant Design `Progress` 环形 + 中央大数字：
- 环形进度 = 剩余秒数 / `confirm_timeout`（每秒递减，圆环收缩）；
- 中央大数字显示剩余秒数（`剩余 Ns`），字体大而不刺眼（`#8c8c8c`→最后 5s 转橙 `#fa8c16`→最后 3s 轻微脉动）；

- 真 HITL 形态下：环形 + 大数字 + 文案「未响应将在 N 秒后自动拒绝」，醒目但不打断阅读。
