## 二、Q1：HITL 弹窗先于 action 等待图标（弹窗顺序）

### 2.1 现象
HITL 确认：流水线先出"确认弹窗"，用户确认之后流水线里才出现工具等待图标（🔧+齿轮/扳手动画）。用户认为顺序反了——期望先看到等待图标（工具将执行），再出弹窗确认。

### 2.2 证据链（SSE 事件真实发射顺序，后端权威）

`handle_action.py:313-344`：
```python
_events.append(emit(ThoughtStartStep(step=step)))     # step 次序 1
_events.append(emit(ThoughtStep(...)))                 # step 次序 2
# step 次序 3（全程等待用户确认，paused 在此发布）
_events.extend(await check_safety_and_confirm(...))
# step 次序 4：仅确认通过后才 emit ActionStep
if _exec_calls:
    _events.append(emit(ActionStep(exec_type=..., tools=_action_tools)))
```

`safety_gate.py:86-105`：`hitl_confirm` 内部流程——
1. publish **SUSPENDED** / **paused**（授权等待事件，确认前）；
2. 挂起等用户确认（S1 超时 / 拒绝 / 允许）；
3. 返回 verdict → `check_safety_and_confirm` 继续 → `run_sandbox_gate` 汇合；
4. 全部返回后 `handle_action` 才 emit `ActionStep`。

**SSE 顺序结论**：`thought-start → thought → paused(弹窗) → [用户确认] → resumed → action(齿轮) → observation`

### 2.3 病根判定

**「先弹窗后图标」是后端协议顺序的必然结果，前端只是忠实执行，不是前端 bug。**

- 齿轮（`ToolCallLine` 的 `!hasResult && tools.length > 0`，`ToolCallLine.tsx:181-199`）数据源是 `ActionStep.tools`；
- `ActionStep` 必须等 `safety_gate` 返回（= 用户确认完成后）才 emit（`handle_action.py:334-344`）；
- 因此**确认前流水线里不存在工具行，齿轮不可能先出**。

**仙亊更正（重要）**：此前初步判断"React 18 automatic batching 把同一微任务内 action+paused 的 setState 合并一次渲染（齿轮与弹窗同帧）"——**经源码核实不成立**。action 与 paused 之间隔着用户确认的完整网络往返（秒级），不可能落入同一微任务，不存在"同帧合并"。撤销该判断。

### 2.4 体验缺口（可优化点）

确认等待期间（paused 已到、action 未到）：

- `lastSeg.kind === 'thinking'` → `showGreenCircle = taskActive && (!lastSeg || lastSeg.kind === 'obs')` 为 **false**（`PipelineRenderer.tsx:189-195`）；
- 流水线**只有 thought 文字，无任何"工具待确认"视觉标记**；
- 弹窗成为唯一提示 → 用户感知"弹窗突兀、图标迟到"。

`highlightToolName`（`useChatPanels.tsx:229`）虽在确认期间已点亮，但工具段尚未渲染，高亮无从挂载（`PipelineRenderer.tsx:296-298` 需 `seg.kind === 'tool'` 且 tools 匹配）。

### 2.4.1 前端链路代码级核实（北京老陈追问"前端是否也有问题"，2026-09-06 逐行复核）

把"确认等待期流水线无视觉"从推断升级为**代码级事实**：

1. **paused 步被渲染器丢弃**：`buildSegments`（`PipelineRenderer.tsx:78-150`）只处理 thinking/chunk/thought/action/observation/final/error 七个 case，`type='paused'` 走 `default`（L148-149）**不产出任何段**；
2. **StatusLine 仅渲染 error**（`StatusLine.tsx:25` `if (step.type !== 'error') return null`），paused/resumed/retrying 状态行一律不渲染；
3. **绿圈不亮**：`showGreenCircle = taskActive && (!lastSeg || lastSeg.kind === 'obs')`（`PipelineRenderer.tsx:195`），确认期间 `lastSeg` 为 thinking/text 段（paused 已被丢弃），非 obs → false；
4. **齿轮不显**：`ToolCallLine` 数据源是 action 段（`action.tools`），确认前无 action 段 → 无齿轮。

→ **确认等待期右栏流水线 = thought 文字 + 弹窗 + badge，无任何工具级视觉**（代码级实锤）。

### 2.4.2 钉死：前端不存在"paused+action 同帧/同批"设想（推翻并再确认）

- 后端 `hitl_confirm`：`await publish(paused)` → `await wait_for_confirmation_result(confirm_id, timeout=_bt)`（`hitl_gateway.py:81-82`）——**整个 safety_gate 被阻塞在等待确认上**，期间绝无 action 产出；
- 确认完成后 `publish(resumed)`（L93-96）→ `safety_gate` 返回 → `handle_action` 才 emit ActionStep（`handle_action.py:334-344`）→ 又一个独立 SSE 帧；
- **paused 与 action 分属相隔秒级的独立 SSE 数据帧**，前端 `processSSEData` 逐帧同步处理，React 18 automatic batching 无合并空间。
- 结论：此前"React automatic batching 同微任务合并 action+paused"的初次判断**双重推翻**——真实网络下不存在该窗口。
- 例外（非问题）：bypass 模式 `hitl_confirm` 亦 publish paused（`hitl_gateway.py:75-81` 无条件），前端弹窗带 `autoConfirm=true` 走倒计时自动代发，paused→resumed→action 全程仍分帧，仅间隔缩短（默认约 10s），不构成同批。

### 2.4.3 前端处理 paused 的时延（零延迟）

- `sseParser.ts:828-843` paused case → `onPaused?.()`（同步）→ `onAuthorizationRequired`（同步）→ `window.dispatchEvent('authorization_required')`；
- `useAuthorization.ts:38-75` 监听器：`pendingRef.current = newRequest; setAuthorizationPending(newRequest)` **同步写入**（2026-09-03 已修 React 子先父后竞态）→ 弹窗当帧出现，无额外延迟。

### 2.4.4 前端潜在真问题（新增，待北京老陈定案）：HITL 工具行高亮空转

- `useChatPanels.tsx:229` `highlightToolName = authorizationPending?.toolName ?? null`——确认期间 pending 非 null → 高亮值存在；
- 但 `PipelineRenderer.tsx:296-298` 高亮作用于 `seg.kind === 'tool'` 段，而 tool 段（action）**确认完成后才到达**；
- 确认点击瞬间 `handleAuthorizationConfirm` 同步 `setAuthorizationPending(null)`（`useAuthorization.ts:122`）→ highlight=null；action 段到达时已在 null 状态。
- **→ 工具行 `hitl-border` 高亮在整个 HITL 生命周期几乎从不生效**（确凿前无段、确凿后无值）。与设计"4.7 HITL 弹窗联动高亮"意图不符。
- 定案见 §2.6（2026-09-06 北京老陈要求补解决方法后定稿）。

**处理决定**：B1 前端先行（本轮可落地）→ B2 随事件总线主线（文档[6]）根治；A 现状为基线。

#### 2.6.1 B1 前端"已放行"短时高亮（先行，待实施）

- 改 `useChatPanels.tsx:229`：`highlightToolName` 来源由 `authorizationPending?.toolName` 扩为 `authorizationPending?.toolName ?? recentConfirmedTool ?? null`；

## 三、Q2：后台切回右栏/左栏不自动滚

### 3.1 现象
浏览器切后台，任务继续跑；切回浏览器，右栏流水线 / 左栏消息区停在半途，没有自动滚到底。增长内容被"盖住"，需手动下拉。疑似与 HITL 相关，实际**无关**（见 3.3）。

### 3.2 四大病根

**RG-1（主根因）右栏无 visibilitychange 重滚兜底**
- 右栏滚动 100% 依赖 `ResizeObserver(stickToBottom)` + `isCurrentLive` effect（`RightViewer.tsx:145-177`）；
- 浏览器后台时 rAF/布局回调被节流，RO 可能延迟/错过；**切回可见时无任何"重滚到底"兜底**；
- 左栏有 `visibilitychange → scrollToBottomDelayed`（`useChatScroll.ts:93-103），右栏没有——不对称。

**RG-2 `_hasFinal` 切历史后滚动逻辑销毁**
- 后台期间任务若已 final：`_hasFinal=true`（`RightViewer.tsx:110`）→ `isCurrentLive=false`（L113-117）→ 滚动 effect **直接 `return`**（L146）；
- 转历史模式拉 REST：`displaySteps` 切 `historySteps`，`hasSteps=false` 时渲染 Empty（L239），`pipelineEndRef` 不挂载；
- 历史数据到达后渲染 PipelineRenderer，但**无任何滚动逻辑**（历史模式本就无滚动 effect）→ 右栏停在半空。

**RG-3 effect 依赖 `hasLiveSteps`（0→1）不重跑**
- `hasLiveSteps = liveSteps.length > 0`（L112），effect 依赖 `[isCurrentLive, hasLiveSteps, ...]`（L177）；
- 后台保持 live（任务仍在 running）时，切回后 `hasLiveSteps` 已是 true（无 0→1 变化）→ **effect 不重跑** → RO 保持旧实例；
- 若 RO 后台被节流/中断，切回无兜底。此病根由 RG-1 的 visibilitychange 覆盖。

**RG-4 左栏仍用 scrollIntoView smooth + 100ms 延迟**
- `useChatScroll.ts:38-43`：`setTimeout(100ms)` → `scrollIntoView({behavior:'smooth'})`；
- 流式逐 chunk 高频下 smooth 动画反复被打断重启、追赶不及（后台积压 chunk 一次性渲染后停在中间）；
- 右栏已于 2026-09-02 弃 smooth 改 `scrollTop=scrollHeight` 即时（RightViewer 编辑历史 L14-17 明示），**左栏未同步**——前后不对称。

### 3.3 与 HITL 是否相关：**确认无关**

- HITL 弹窗是 portal 覆盖层，不占流水线高度、不参与流式增长，不触发 ResizeObserver；
- HITL 确认期流水线无新段（无 action），滚动需求本身不存在；
- Q2 触发要素（后台内容增长 + 切回欠滚）与弹窗生命周期（onAuthorizationRequired→弹窗→confirm）**无因果**。

## 十二、整批判定分母说明（2026-09-06 15:11:56 追加，编写人：小欧）

> **本节为 2026-09-06 追加指向（不升 v1.6，缘由见 §一 版本文档策略）。**

本节上文（§7.1 V2、§10.2、§11 验收表）中的 `deniedCount >= tools.length`、`deniedCount<tools` 表述，自 **B2 方案C 文档 v1.6（2026-09-06 15:11:56）** 起，分母统一按 **候选工具总数（candidateCount）** 理解：

- `candidateCount` = 预览 action 的 `tools` 全量候选数（后端 `all_calls` 数量），**并行多少就是多少、可高达 10+**；
- 不得用 `seg.action.tools?.length`——该字段在 canonical 到达后会被覆盖为执行集（只小不全），部分拒场景（拒7+3执行中）`denied=7 >= 执行集3` 会误停齿轮；
- 判定全文见 **B2方案C最终设计说明 §4.4/§4.8**（PipelineRenderer `candidateCount`、buildSegments 保留预览全量）。

本文档为实现参考记录，最终判定语义以 B2 方案C 文档 v1.6 为准。
