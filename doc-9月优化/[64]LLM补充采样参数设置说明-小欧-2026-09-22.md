## 一、缺什么常用参数

> 编写人：小欧 2026-09-22 22:19:22

### 1.1 现状请求体实际拼入的字段

后端 LLM 请求体构建唯一入口 `_build_request_body`（`backend/app/llm/client_sdk.py:51-89`）当前只拼：

| 字段 | 来源 |
|------|------|
| model / messages | 固定 |
| max_tokens | `provider_config.max_tokens` |
| temperature | `provider_config.temperature`（默认 0.7） |
| seed | `provider_config.seed`（可 None） |
| stream / stream_options | 流式开关 + tuning.llm.stream_options |
| tools / tool_choice / parallel_tool_calls | 工具调用 |
| extra_body | `model_params.{model}` 余量透传（服务层第二通道，绕过校验） |

### 1.2 缺失的常用采样参数清单

| 参数 | OpenAI 兼容字段名 | 值域 | 是否在注册表中 | 当前能否传到请求体 |
|------|------------------|------|:---:|------|
| top_p | `top_p` | 0~1（默认 1） | ❌ | ⚠️ 仅能躲进 extra_body 手写 config.yaml |
| frequency_penalty | `frequency_penalty` | -2~2（默认 0） | ❌ | ⚠️ 同上 |
| presence_penalty | `presence_penalty` | -2~2（默认 0） | ❌ | ⚠️ 同上 |
| stop | `stop` | 字符串/数组 | ❌ | ❌ 完全不可达 |
| top_k | `top_k`（**非 OpenAI 标准**） | 1+ | ❌ | ⚠️ 部分国内厂商（如 minimax）支持 |
| n / logit_bias / user / response_format | — | — | ❌ | ❌（评估不建议加，见第三章 3.4） |

结论：**系统当前对"除 temperature/seed 外的采样控制"零正式支持**，全靠 extra_body 透传逃生门（无类型校验、无 UI、有 400 风险）。这就是本文档要补的缺口。

## 二、有什么价值、什么场景有用、哪些国内模型支持

> 编写人：小欧 2026-09-22 22:19:22

### 2.1 各参数的价值与适用场景

| 参数 | 价值 | 典型场景（本系统视角） |
|------|------|------------------------|
| **top_p**（0~1） | 核采样：只从累计概率达标的最小候选集合里采样，等效"裁剪长尾噪声词" | ①**工具选择**：FC 模式下把 top_p 降到 0.8~0.9，减少模型在"多个可用工具"之间摇摆、误选伪工具名；②**代码/JSON 输出**：调低 top_p 提升结构化输出稳定性；③与 temperature 二选一（见 2.3） |
| **frequency_penalty**（-2~2） | 按"词/符号出现的频次"惩罚重复 | ①**Agent 长任务**：模型反复调用同一工具、反复输出同一路径/同一段代码——此项直接压制工具调用层面的重复；②结果汇总重复内容被有效降低 |
| **presence_penalty**（-2~2） | 按"是否出现过"惩罚（讨论过的话题整体降权） | ①长链推理中模型**绕圈子复述旧结论**；②多轮对话中换话题时甩不掉旧主题的粘性 |
| stop | 停止序列 | 输出到固定边界即止（如 JSON 收尾、表格结尾），需维护边界串列表，收益场景窄（本期不做，二期备选） |
| top_k | 截取概率最高的 K 个候选 | 仅对支持该非标字段的厂商有意义（如 minimax）；**OpenAI 兼容主流接口会 400 拒绝**（见 3.4 结论） |

### 2.2 哪些国内模型支持（按本项目实际配置的 provider 域）

本项目当前真实配置 5 个 provider（`config/config.yaml` ai 区，均走 OpenAI 兼容 /v1 接口）：**sensenova（商汤）、qiniu（七牛聚合：deepseek/glm/kimi/minimax）、zhipuai（智谱 GLM）、agnes、opencodeZen**。

| 参数 | DeepSeek 系 | 智谱 GLM 系 | Moonshot Kimi 系 | MiniMax 系 | 商汤 sense 系 | agnes / opencodeZen（聚合/桥接） |
|------|:---:|:---:|:---:|:---:|:---:|:---:|
| temperature | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| top_p | ✅ | ✅ | ✅ | ✅（另有 top_k） | ✅ | 🔶 按上游透传 |
| frequency_penalty | ✅ | 🔶 部分版本 | ✅ | ✅ | 🔶 需实测 | 🔶 按上游透传 |
| presence_penalty | ✅ | 🔶 部分版本 | ✅ | ✅ | 🔶 需实测 | 🔶 按上游透传 |
| seed | ✅ | 🔶 部分 | ✅ | ✅ | 🔶 需实测 | 🔶 按上游透传 |
| stop | ✅ | ✅ | ✅ | ✅ | 🔶 需实测 | 🔶 按上游透传 |

> **说明（诚信标注，不得夸大）**：
> 1. ✅ 表示各家官方 OpenAI 兼容文档明确支持；🔶 表示"厂商文档未明示/版本间不一致"，**必须按本系统一贯做法对目标 provider 发真实请求验证字段合法性**（同 [62] BY-08 对 reasoning_effort 的做法），不能仅凭推测上线。
> 2. **top_k 是特例**：DeepSeek/GLM/Kimi 的 OpenAI 兼容端点均**不认 top_k**（会 400），仅 MiniMax 型厂商接受 → 论证结论为"不做通用 top_k"（见 3.4）。
> 3. 所有 provider 最终都汇聚到本系统 `_build_request_body` 这一个拼体入口，参数是否生效取决于"拼进去了 + 对端认这个字段"两者同时满足。

### 2.3 temperature 与 top_p 的互斥提醒

OpenAI 官方建议：**temperature 与 top_p 不同时使用**（两者都作用于采样分布，同时改会产生叠加且互相掩盖）。落地时 UI 应给提示（如：修改 top_p 时提示"建议与 temperature 二选一为主控"），后端不做强制互斥（多做反而限制自由度，语义留给用户）。

## 三、可否设置为与模型无关的通用参数

> 编写人：小欧 2026-09-22 22:19:22

### 3.1 直接结论

**top_p / frequency_penalty / presence_penalty 可以，而且应当做成"模型无关的全局通用参数"。**

理由（OpenAI 兼容体系的事实）：
- 这三个字段在 OpenAI 兼容巨头（DeepSeek/GLM/Kimi/MiniMax）里是**同名同义同值域**的公共语言，不随模型变；
- 它们的语义（采样分布裁剪/重复惩罚）是"模型属性无关"的，不像 `context_limit`（受模型窗口硬约束）必须逐模型配置；
- 本系统 `tuning.llm.*` 已有温度等全局参数先例（`settings_registry.py:149-164`），同层级放置符合既有架构心智。

### 3.2 落点：`tuning.llm.*`（全局层，模型无关）

| 新键 | 类型 | 默认值 | 值域 | 说明 |
|------|------|--------|------|------|
| `tuning.llm.top_p` | float | 1.0 | 0~1 | 核采样阈值，留默认 1.0=不启用 |
| `tuning.llm.frequency_penalty` | float | 0 | -2~2 | 频次重复惩罚 |
| `tuning.llm.presence_penalty` | float | 0 | -2~2 | 话题重复惩罚 |

默认值语义："0/1.0" 即无损旁路 → **不设置的用户行为与现状逐字节一致**（这是"模型无关通用参数"的降级安全性第一原则）。

### 3.3 与"模型级参数"的关系辨析（不冲突）

| 维度 | 全局通用（tuning.llm.*） | 模型级（ai.{provider}.model_params.{model} → extra_body） |
|------|------------------------|----------------------------------------------------------|
| 面向 | 全系统采样基调 | 个别模型特调（如某模型吃不了 temperature） |
| 校验 | 注册表 range_ 强校验 | 无校验、裸透传 |
| 现状 | 已有 temperature 等 7 项 | 已有 reasoning_effort 先例 |
| 建议 | **首次实施主打这条** | 保留为高级逃生门，不做新 UI |

**实施策略**：新增三个键全部走 `client_sdk._build_request_body` 显式拼参（`tuning` 值默认即旁路），**不改成逐模型特殊处理**。个别模型的极端需求再走既有 model_params 逃生门，本次不扩展。

### 3.4 明确"不做"的（模型无关性反面）

| 候选 | 结论 | 理由 |
|------|------|------|
| top_k | **不做通用参数** | 非 OpenAI 标准，主流 vendor 400 拒绝；若个别厂商（如 MiniMax）需要，应走 model_params 逃生门逐模型配，归模型级而非通用级 |
| n / logit_bias / user / response_format | 不做 | 无消费方 / 结构难 UI / 非采样需求，YAGNI |
| stop | 二期备选 | 需维护边界串，收益窄；若做同样入 tuning.llm.stop |

## 四、如何实施

> 编写人：小欧 2026-09-22 22:19:22

> 遵循项目铁规：**能复制就复制、不重写**；TDD 红→绿→验证门全过再收尾；禁 commit 测试代码文件；代码加署名+日期注释。

### 4.1 改动清单（后端为主，前端迎合后端）

| # | 文件 | 改动 | 层 |
|---|------|------|-----|
| 1 | `backend/app/services/settings/settings_registry.py` | tuning.llm 组新增 3 键（top_p/frequency_penalty/presence_penalty），带 range_ 值域；notice 写清互斥提示 | 注册表（唯一 Schema 源） |
| 2 | `backend/app/llm/client_sdk.py` | `_build_request_body` 签名加 `top_p / frequency_penalty / presence_penalty: Optional[float]`，`if x is not None: body[key]=x`（模仿 temperature/seed 现有写法，三行） | 请求体拼装 |
| 3 | `backend/app/llm/base_service.py` | 构造参数加三字段 + `self.top_p=` 等（仿 L111-122 seed 先例）；`request` 三处调用点透传（L190-191/274-275/335-336） | 服务层 |
| 4 | `backend/app/services/lifecycle/service.py` | `create_service_instance` 从 tuning 取默认值传入（`get_config().get("tuning.llm.top_p", 1.0)` 等；仿 temperature 现写法 L119），provider_config 同名键可覆盖 | 实例装配 |
| 5 | `backend/app/services/model/resolver.py` | **L2 跨 provider 会话快照**按目标 provider 构造时同样透传三参（快照客户端应持有与全局一致的采样参数，防切会话后参数丢失） | 会话覆盖 |

> 关键设计：**默认值即旁路**（top_p=1.0、penalty=0 时行为与现状完全一致），故改动对存量用户零感知；服务层取值顺序 = provider_config 显式键 > tuning.llm 全局 > 函数默认值（与 temperature 现状同构）。

### 4.2 前端改动

| # | 改动 | 说明 |
|---|------|------|
| 1 | 注册表加键后，设置2版 tuning 子组**自动渲染新项** | 现有 settings2 为表驱 schema，增设条目无需改前端代码（对齐 [62] P9 "无新代码但验证走单测" 的既有事实） |
| 2 | 前端 notice 区显示互斥/旁路提示（文字来自注册表 notice 字段） | 无需硬编码 |

### 4.3 测试与验证（TDD，禁 commit 测试文件）

| 步骤 | 内容 |
|------|------|
| 红 | 写单测断言：`_build_request_body` 三参 None 时 body 不含对应键；设值时含且类型正确 |
| 绿 | 实现 4.1 改动后用例转绿 |
| 单测补充 | `parse_model_params`/快照构造透传断言（参照 BY-08 既有模式，零 mock 真实函数） |

### 4.4 实施顺序与风险

| 阶段 | 内容 | 验证门 | 风险 | 回退 |
|------|------|--------|------|------|
| P1 | 注册表 3 键 + client_sdk/base_service 透传（默认旁路） | 单测红→绿；真实请求 4 provider 接受 top_p | 低（三行 xxx 仿写） | 默认值旁路=零感知回退 |
| P2 | resolver 快照透传 + 全量单测 | 会话切换后参数仍生效 | 中（快照构造点） | 快照缺参仅回退到全局默认，不报错 |
| P3 | 不支持清单收集 + notice 文案 | 文档记录 + UI 展示 | 低 | 文案可改 |

### 4.5 最终效果（验收标准）

- 设置2版 → 调优 → LLM 语义参数子组出现 **top_p / frequency_penalty / presence_penalty** 三项，范围校验生效（负数/越界被拒，同 [62] #7 修复）；
- 保存后 `_build_request_body` 产物含三字段；不设置的用户请求体与改动前**逐字节一致**；
- 四个国内 provider 真实请求全部接受 top_p；penalty 项在"已实测支持"厂商生效、"不支持"厂商有 notice 提示；
- 全量回归无退化。
