## 二、系统数据流分析

### 2.1 实时事件流程

```
┌─────────────────────────────────────────────────────────────┐
│                     事件发射层                               │
│  handle_action.py / handle_answer.py / react_step.py        │
└──────────────────────────┬──────────────────────────────────┘
                           │ publish()
                           ▼
┌─────────────────────────────────────────────────────────────┐
│              StreamBuffer.event_log（内存队列）               │
│  - append-only 事件列表                                      │
│  - 每条含 seq(单调递增序号)                                   │
│  - 生命周期：任务结束即消失                                    │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                     stream_reader                            │
│  - 从 event_log 按 seq 偏移读取                              │
│  - 格式化为 SSE 发送到前端                                    │
│  - 支持断线重连(按 seq 续传)                                  │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                     前端实时显示                              │
│  - sseParser 解析 SSE 事件                                   │
│  - 渲染到聊天界面                                            │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 历史回放流程

```
┌─────────────────────────────────────────────────────────────┐
│                     前端点击历史任务                          │
└──────────────────────────┬──────────────────────────────────┘
                           │ REST API
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  GET /chat/execution/task/{task_id}/steps                   │
│  - 从 DB 读取 chat_task_steps 表                            │
│  - 返回历史步骤数据                                          │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                     前端回放显示                              │
│  - 加载历史步骤                                              │
│  - 渲染到右侧面板                                            │
└─────────────────────────────────────────────────────────────┘
```

### 2.3 两套数据存储对比

| 维度 | event_log（内存） | chat_task_steps（DB） |
|------|-------------------|----------------------|
| 存储位置 | StreamBuffer.event_log（Python list） | SQLite chat_task_steps 表 |
| 生命周期 | 进程内存，任务结束即消失 | 持久化DB，永久保存 |
| 消费方 | SSE实时转发 | 历史回放、消息列表、多轮上下文构建 |
| 写入时机 | publish() 追加 | append_execution_step() 逐行写DB |

**关键结论**：历史回放完全不依赖event_log，只从DB读取。

## 三、当前架构问题

### 3.1 架构图

```
┌─────────────────────────────────────────────────────────────┐
│                     事件发射层                               │
└──────────────────────────┬──────────────────────────────────┘
                           │ publish()
                           ▼
┌─────────────────────────────────────────────────────────────┐
│              StreamBuffer.event_log（共享队列）               │
└──────────────────────────┬──────────────────────────────────┘
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
┌─────────────────────┐    ┌─────────────────────────┐
│   stream_reader     │    │   agent_runner._scan    │
│   (SSE消费者)        │    │   (DB落库消费者)         │
└──────────┬──────────┘    └────────────┬────────────┘
           ▼                            ▼
    SSE → 前端                    DB落库(chat_task_steps)
```

### 3.2 问题（北京老陈发现，全量列出）

#### 问题一：前端显示thought重复

**现象**：前端聊天界面中，LLM 推理内容（thinking）与正文内容重复显示。

**链路**：
```
LLM流 → chunk(is_reasoning=true) → SSE → 前端显示推理正文
                                    ↓
handle_action publish(ThoughtStep) → event_log → stream_reader → SSE → 前端又显示一次
```

**根因**：`handle_action.py:345-359` 将 ThoughtStep publish 到 event_log，
stream_reader 不加区分转发为 SSE，前端收到 chunk 与 thought 双份推理内容，
`PipelineRenderer.tsx` 靠 `endsWith` 去重（过渡补丁）。

#### 问题二：文档[6]设计要点未实施——thought被裹挟进event_log

**文档[6]原文**（§1.4路由表）：thought 仅落库，不发SSE。

**设计漏洞**：文档[6]只定义了"去向"（仅落库），没设计"怎么去"。
实施时 thought 仍走 `publish()` 进入 event_log，再由 agent_runner 路由过滤不发SSE。

**对比**：

| 设计 | thought路径 | event_log中是否有thought |
|------|------------|------------------------|
| [6]文档实施现状 | publish → event_log → 路由过滤 → 仅落库 | ✅ 有（被裹挟） |
| [1]文档§10.3.3(1)设计意图 | 完整数据落库，实时不发送 | ❌ 应无 |
| 本文档[26]重构目标 | persist_step_to_db → 直接写DB | ❌ 无 |

**结论**：[6]把 thought 从"发SSE"改成"仅落库"，但 thought 仍进入 event_log，
违反[1]§10.3.3(1)"thought完整数据落库、实时不发送"的设计意图。

#### 问题三：测试不彻底——只验SSE未验event_log

**测试现状**：文档[6]实施后的测试只验证了"前端不收到thought"（SSE输出），
未验证"event_log中没有thought"（内存状态）。

| 测试项 | 验证内容 | 结果 |
|--------|---------|------|
| SSE输出 | thought不在SSE中 | ✅ 通过（正确） |
| event_log内容 | thought不应在event_log中 | ❌ 未测试（漏洞） |

**后果**：问题二（thought被裹挟进event_log）长期未被发现，
前端去重补丁（`endsWith`）掩盖了架构缺陷。

#### 问题四：架构层面问题

1. **共享队列导致职责混乱**：event_log 同时服务SSE和DB落库，需要标记区分
2. **过渡方案不优雅**：`_no_sse` 标记是补丁，不是设计
3. **违反SRP**：stream_reader 需要理解业务逻辑（哪些事件该发）
4. **扩展性差**：新增事件类型需要修改 stream_reader 过滤逻辑

### 3.3 根因汇总

```
根因1（问题一+问题二）：
handle_action.py → publish(ThoughtStep) → StreamBuffer.event_log
                                              ↓
                        stream_reader → SSE ❌ 不该发
                        agent_runner → DB落库 ✅

根因2（问题三）：
测试只断言SSE输出，未断言event_log内容 → 裹挟问题漏网

根因3（问题四）：
SSE与DB落库共享event_log → 职责混乱 → 需标记/过滤区分
```

**设计意图**（[1]§10.3.3(1)）：thought 仅落库不发SSE，不进入实时通道
**实际行为**：thought 被 publish 到 event_log → 依赖路由过滤/SSE过滤/前端去重三层补丁

## 四、重构设计

### 4.1 设计原则

| 原则 | 说明 |
|------|------|
| **职责分离** | SSE和DB落库完全独立，不共享数据源 |
| **KISS-DIRECT** | 简单直接，不绕弯 |
| **SRP** | stream_reader 只管SSE，不关心落库 |
| **OCP** | 新增事件类型不修改消费者代码 |
| **DRY** | 事件发射逻辑不重复 |

## 五、详细设计

### 5.0 操作规范：复制然后修改

**铁律**: `persist.py` 的创建必须采用「**复制然后修改**」方式，禁止重写。

| 步骤 | 操作 | 说明 |
|------|------|------|

| 维度 | 当前架构 | 新架构 | 影响 |
|------|---------|--------|------|
| thought落库 | event_log → agent_runner._persist → DB | persist_step_to_db() → DB | ✅ 相同结果 |
| 历史回放读取 | 从DB读 | 从DB读 | ✅ 相同路径 |
| event_log中的thought | 有（过渡方案） | 无（正确设计） | ✅ 不影响历史回放 |

### 6.2 原因

1. 历史回放从DB读取，不从event_log读取
2. 新架构仍然把thought写入DB（只是不经过event_log）
3. chat_task_steps表中的数据不变

### 6.3 persist_step_to_db 必须保留的逻辑

```python
# 从 agent_runner._persist() 中对thought的特殊处理，必须保留
# （5.1中该块已移入try内，规约失败同样静默跳过，见E1.7）— 小欧-2026-09-11
if event_dict.get("type") == "thought":
    for _k in ("content", "thought", "reasoning"):
        _v = event_dict.get(_k)
        if isinstance(_v, str):
            event_dict[_k] = normalize_blank_lines(_v)
```

**原因**：保持thought落库的数据格式一致，历史回放读取时格式不变。
