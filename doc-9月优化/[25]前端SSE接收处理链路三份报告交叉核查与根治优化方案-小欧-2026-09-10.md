### 3.4 重大修正：P4"空闲超时假中断"已被后端心跳化解

**证据链**：
1. 后端 `constants.py:127` `HEARTBEAT_INTERVAL = 25.0`（常量注释§6 明确"与前端 IDLE_TIMEOUT=60s 错开"）。
2. 后端 `stream_reader`（stream_orchestrator.py:460-470）：`cond.wait()` 每 25s 超时发 `: ping\n` 保活。

### 3.5 问题三维清单：架构 / 技术选择 / 技术实现

> 按北京老陈的要求：不用表格罗列；问题点改用规范的章节号（3 级标题 3.5、4 级标题 3.5.x、5 级标题 3.5.x.y）来锚定，"是什么"与"危害是什么"以段落方式紧随各章节号之下。三个维度虽并列，但本核查的结论是：**危害最大的三条（重复输出、短时冻结、丢最后几步）全部源于"架构——状态与数据源设计"这一维，技术实现维的缺陷是放大与叠加因素，技术选择维整体正确、仅有一处轻度误用**。

#### 3.5.1 架构维度（状态与数据源设计）——用户三症状的根

##### 3.5.1.1 executionSteps 五份状态无单一真源

executionSteps 同时存在五份互相独立、读写不齐的状态。分别是 useSSE 的 React state（useSSE.ts:383）、useSSE 的伴生 ref（:384）、useChatState 的同名 ref（:259）、消息消息体里的 executionSteps（useChatCallbacks.ts:266）以及 sessionStorage 持久化副本（useSSE.ts:485-500）。它们的写入方与读取方各不相同：解析层写 state 与 useSSE ref，错误清理写 useChatState ref，完成回调读 useSSE ref，消息区另走一套追加。

**病根**：五源不是偶然堆积，而是全链路普遍采用"state 与 ref 手工双写"编码模式累积出的结构病——serverTaskId 靠 serverTaskIdRef + syncServerTaskId 手动同步（useSSE.ts:408-410），isReceiving 同理，没有任何封装保证同步完备。对普通字段而言，同步遗漏只是一次性 bug；对 executionSteps 这类"高频变更且带清空语义"的对象，后果被放大成病态：**清的对象与读的对象错位**——onError 清的是 useChatState 的 ref（useChatCallbacks.ts:578），onComplete 读的是 useSSE 的 ref（:370/:392），两者同名不同物，清空永远清不掉正在读的那一份；同时 sseParser 六个分支每帧同时写 state、useSSE ref（:382/:431/:680/:831/:871）与 sessionStorage 三处，正常无重放时三处尚强一致，一旦重连重放或清空错位立即背离。

**危害**：同一份业务步骤在五处漂移，任何一处不同步，用户就会在同一界面上看到同一批步骤有的地方重复、有的地方丢失；更严重的是清空与读取操作对象不一致时（清的是甲 ref、读的是乙 ref），清理永远不生效，步骤残留在界面上的现象反复出现。

##### 3.5.1.2 SSE 事件流无单调序防线，每帧无条件整数组追加

后端在发布事件时已为每一帧分配了唯一且单调递增的 seq（task_state.py:51，持锁原子），但前端解析层只把这把现成的标尺用在了 usage 分之上（sseParser.ts:267-271），其余业务帧一律不做顺序校验，直接 `[...prev, step]` 追加进 executionSteps state、ref 和 sessionStorage 三处。指纹去重只保护消息气泡区（useChatCallbacks.ts:161-171），左流水线/右查看区读的 state 毫无防线，而 action 的 preview 与 canonical 双发（sseParser.ts:663-666）都会进入 state。

**病根**：写入方 processSSEData 单函数同时承担**解析、状态变更、持久化**三重职责（sseParser.ts:68-936，约 900 行处理 17 种 type），每个事件分支都内联"构造步骤 + setExecutionSteps + 写 ref + saveStepsToStorage"（如 :380-390/:678-688/:829-839），解析层与状态层之间没有任何边界。这使"统一的顺序守卫"根本无处安放——要拦重放必须在每个分支各写一遍守卫，而现状是一处都没写；也使 preview+canonical 双发（:663-666）这类由解析层自己制造的重复源被原样灌入 state，解析层对自身产出的重复毫无感知。

**危害**：断线重连经 after_seq 续传时，序号低于当前进度的重放帧会被三次累积，用户面前重复输出；正常任务里单步骤也被 preview+canonical 双条化，重复感被放大。

##### 3.5.1.3 实时显示源与终态数据源两套数据流，结束时刻靠"猜"交接

执行过程中右侧查看区读的是实时 state（liveSteps，RightViewer.tsx:303），final 一到便切换为读 REST /getTaskSteps 的历史接口（:307）；而历史接口依赖后端把步骤落库成功，落库存在时延（:273-278 的注释明确承认"SSE final 先发、DB 写入稍后"）。

**危害**：结束瞬间如果数据库还没写全最新几步，REST 结果就以"缺尾巴的完整历史"顶替了实时全量，最后几步从界面上永久消失；300ms 缓冲只是拍脑袋的猜测，不是同步点，丢尾窗口在任何一次网络偏慢时都会重新打开。

##### 3.5.1.4 生命周期终态由多个布尔与标记拼接，无唯一判定

是否结束要看 isCurrentLive、_hasFinal、hasBusinessSteps、receiving、activeTaskId 与 serverTaskId 的匹配等多个分散标记的组合（useTaskInfo.ts:125-149、RightViewer.tsx:303），判断彼此存在竞态（例如 liveSteps 已含 final 时先判结束再切历史，与 REST 尚未返回的空窗重叠）。

**危害**：结束与切换的时序每次不完全一样，症状忽隐忽现、非定时必现，正是"修了无数次仍不彻底"的典型特征——每次碰的地方对了、但切换的源始终是猜测的。

#### 3.5.2 技术实现维度（并发与主线程卫生）——放大与叠加因素

##### 3.5.2.1 高频热路径叠加 O(n) 数组复制与双路全量 JSON 序列化

每一帧事件都执行 `[...prev, step]` 的整数组拷贝（sseParser.ts:380/429/678/829 等）并触发 setState，触发 Pipeline 全量重渲染；同时 saveStepsToStorage 每 300ms 防抖内做一次同步的 `JSON.stringify(整个步骤数组)` 加 `sessionStorage.setItem`（useSSE.ts:493），useChatPersistence 又每状态变化或 500ms 对整份 messages（含每条消息的 executionSteps）再做一次全量 JSON.stringify 与写入（useChatPersistence.ts:192-220）。sessionStorage.setItem 是同步阻塞 API。

**危害**：数组上千条时，两路大数组序列化加同步写周期性锁死主线程数百毫秒，打字机输出出现可感知的冻结与"被堵"停顿，且步骤越多、任务越长，冻结越频繁。

叠加因素之二：chunk 正文的累积点散落三处——sseParser.ts:401 的 responseBufferRef、useChatCallbacks.ts:313 的 streamingContentRef、:451 的 finalContent 兜底，同一份流式正文被三个地方各累积一遍；而 onChunk 每块到达都 setMessages 全量重建消息区（useChatCallbacks.ts:313-327），与双路序列化叠加，进一步抬高打字机渲染期的主线程占用。

##### 3.5.2.2 React updater 回调内部执行副作用

sseParser 的多个分支在 `setExecutionSteps(prev => {...})` 的 updater 函数体内写 executionStepsRef 与 saveStepsToStorage（sseParser.ts:380-390/429-439/502-511/678-688/829-839/869-879）。updater 应当是纯函数，React 在 StrictMode 下会将其执行两遍以暴露此类违规。

**危害**：updater 不是纯函数使副作用被执行次数不可控（StrictMode 双调用时 ref 写两次、持久化被触发两次），并使"更新 state 的同时依赖读取 ref"这种时间耦合常态化，后续任何一次 React 升级或批处理策略调整都可能让表现漂移。

##### 3.5.2.3 复位逻辑依赖隐式时序，存在死循环与终态数量不定

`isPausedRef` 的复位被安排在 error 回放循环之后（useChatCallbacks.ts:739-747），而 onError 在暂停期间会把错误重新推回缓冲（:600-603），形成回放时错误永远处理不掉、被反复重推的死循环；cancel 进行中的判断用 `!isCancelEvent && step.type !== 'final'` 放行了取消后的 completed 终态（:184-190），且指纹与取消守卫对 final 帧无法区分，最终消息里 final 帧数量不定。

**病根**：错误处理链路横跨三层、各自独立行事——useSSE 的 handleSSEError（分类与重连判断，useSSE.ts:179/:882/:930）、useChatStreaming 的 sseOnError（denied/blocked/timeout 聚合，useChatStreaming.ts:233）、useChatCallbacks 的 onError（业务错误分道与终端提示），三者之间无统一的内存序约定，复位动作（isPausedRef、聚合状态）散落各层；链路上任何一层在回放循环内提前或延后复位，即触发上文死循环。链路每增一层，时序类缺陷的排查面就翻一倍。

**危害**：暂停恢复会卡死，取消后会出现双完成帧或完成后又插入旧步骤，界面上出现明显违背预期的行为。

##### 3.5.2.4 死代码与语义失真的配置，加深维护误判

包括只被清空而无写入点的 streamingStepsRef（useChatState.ts:261）、设置后从未被读取的 reconnectConfigRef.enabled（useSSE.ts:597-601）、从未使用第 3 参数的 processSSEData（sseParser.ts:120）、名为 180 秒 fetch 超时实际只在首响应 resolve 后就清除的 fetchTimeout（useSSE.ts:682/717-720）以及 50 多个依赖项互相纠缠的 useMemo（useChatFacade.ts:252-418）。

**危害**：死代码让"终态应该清哪个 ref"的排查无从下手，名字失真的超时配置让后续维护者对系统保活能力产生系统性误判，依赖纠缠让任何单点改动都波及大范围重渲染。

##### 3.5.2.5 模块与接口职责失衡：useSSE 六大职责、handlers 20+ 字段直透

useSSE.ts 承载连接建立/断开、重连退避、空闲超时、sessionStorage 备份/恢复、轮询观察、意图标记六大职责（约 1086 行），违反 SRP 单一职责；processSSEData 的 handlers 参数塞入 20+ 字段——setExecutionSteps、executionStepsRef、saveStepsToStorage、onChunk、onComplete、disconnect、syncServerTaskId 等（useSSE.ts:777-778/817-818/:794/:836），把"改状态的能力"与"中断连接的能力"原样交给解析层，违反 ISP 接口隔离。

**危害**：职责不分的直接后果是状态归属混乱——executionSteps 之所以漂移成五份，正因为连接、存储、解析、回调各自握有其读写权且无人统一；handlers 直透让解析层随意触碰 ref、持久化乃至 disconnect，3.5.1.1（多源漂移）与 3.5.2.2（updater 副作用）都是这层失守的下游。它不直接制造三症状，却是三症状持续存在、修了无数次仍反复的管理性根因。

#### 3.5.3 技术选择维度（整体正确，仅一处轻度误用）

##### 3.5.3.1 fetch + ReadableStream 手动解析 SSE 的整体选型正确

它绕开 EventSource 无法携带自定义头与无法显式退避重连的短板，配合后端 25 秒心跳保活、断线按 after_seq 续传、动态退避最大三次重连与轮询兜底，构成了完整的断线自愈体系，这些选择本核查未发现错误，予以维持。

##### 3.5.3.2 sessionStorage 作"刷新恢复 + 双路高频持久化"载体属轻误用

作为一次性、按会话隔离的浏览器同源存储，它适合低频、小体积的会话级快照；而此处既承担高频防抖全量数组写入，又承担每个 messages 快照的全量序列化，其同步阻塞写与容量限制与高频 SSE 流形同水火。

**危害**：它不成比例地放大了症状二的冻结，且在数据量大时会静默抛容量不足告警（useSSE.ts:495 的存在即证据）而丢失恢复数据。正确的归属应是低频兜底快照或迁移到异步存储。

#### 3.5.4 三维定性结论

> 本节的用途：把前面 3.5.1~3.5.3 的 11 个问题点汇总成 4 条行动结论，回答"先修谁、修到什么程度算根治、为什么以前修不好"。每条结论对应一个维度或一个核心判断，单独签名如下。

**结论①架构维（3.5.1，共 4 条）＝三症状的病根，此维不修，症状必复发。**
- 3.5.1.1 executionSteps 五源无单一真源 → 直接造成重复输出、丢步。
- 3.5.1.2 SSE 无单调序防线 → 直接造成重复输出（重放+preview/canonical 双发）。
- 3.5.1.3 实时/终态双源靠"猜"交接 → 直接造成丢最后几步。
- 3.5.1.4 生命周期无唯一终态判定 → 三症状忽隐忽现、非定时必现的原因。
- 对应关系：**症状①重复 ≈ 3.5.1.1+3.5.1.2；症状②冻结 ≈ 结构上由 3.5.2 放大、源头在 3.5.1；症状③丢尾 ≈ 3.5.1.3+3.5.1.1。**

#### 3.6.12 useStateWithRef 封装 state/ref 双写同步（来源：24 §缺陷1 / §4.1）

"state 与 ref 手工双写"是 3.5.1.1 点名的全链路结构病（serverTaskId 靠 serverTaskIdRef + syncServerTaskId 手动同步 useSSE.ts:408-410、isReceiving 靠 useEffect 异步同步 :405-415），S2/S4 只覆盖了 executionSteps 一类；对 serverTaskId/isReceiving 等**普通字段**，文档24 提供方法：新建 `useStateWithRef` hook（返回 `{state, ref, setValue}`，`setValue` 一次调用同时写 ref 与 state，`value instanceof Function` 时基于 ref.current 计算），替换各处手动双写与 useEffect 同步，异步回调一律读 ref 拿最新值。此方法补足 S2/S4 的覆盖面，落地时与 3.5.1.1 病根一并处置。

#### 3.6.13 sessionStorage 快照来源标记（来源：24 §缺陷4 / §4.5）

3.5.3.2 将 sessionStorage 定性为"高频持久化轻误用"，方向是降级为低频兜底快照；文档24 提供快照判据方法：写入时带 `{steps, source, timestamp, version}` 元数据外壳，恢复时校验来源并兼容旧格式（`parsed.steps || parsed`）。该元数据使"快照新鲜度/来源"可判别，与 S13"REST 结果与 settledSteps 等长校验、短则弃"同思路——降级为只读快照后，凭 timestamp/source 决定快照是否仍可信，作为 S2/S13 落地时的辅助判据。

#### 3.6.14 HITL 等待态 Map 计数管理（来源：24 §缺陷7 / §4.8）

`isHitlWaitingRef` 单布尔在**并发 HITL** 场景存在误判：一处分歧（wrappedOnResumed）即把整体等待态置 false，另一处仍在等时 IDLE 计时被错误恢复。方法：改用 `Map<key, boolean>` 计数（onPaused 后按 confirmId 增、onResumed 后删，等待数=size>0），并在组件卸载时 `clear()` 防状态残留——该方法支撑 3.5.1.4"生命周期终态拼接"的收敛，属防御性补充，非三症状根因修复。

#### S3.5 seq 守卫首帧陷阱——三份报告均未覆盖的死角

**陷阱**：seq=0 既可能是首帧（合法），也可能是重放帧（非法），两种方案均有致命缺陷：
- 小沈[23]：`if (_seq && _seq <= lastConsumedSeqRef?.current) return;` — `_seq` 为 `0` 时 falsy → **seq=0 重放帧永不拦截**（守卫对首帧退缩）。
- 小草[22]：若用 `seq <= lastSeq` 且 lastSeq 初始 0 → **首帧 seq=0 被误拦**，首条 thought/action 丢失。

**解法**：已处理最大 seq 语义(初始-1) + 守卫在 onSeq 之前 + `<=` 比较，两帧分离，双杀。验证矩阵：

| 帧 | lastSeq(已处理最大) | 守卫表达式 | 期望 |
|----|---------------------|-----------|------|
| 首帧 seq=0 | -1 | `0 <= -1` false | 放行 ✓ |
| 正常 seq=1 | 0 | `1 <= 0` false | 放行 ✓ |
| 重放 seq=0 | 0 | `0 <= 0` true | 拦截 ✓ |
| 重连续传 seq=5.. | 0 | `5 <= 0` false | 放行 ✓ |
