## 一、目标

让 `opencodeZen` provider 通过 **Zen 免费无key 认证**（`Authorization: Bearer public`）直连 `https://opencode.ai/zen/v1`，做到：

1. **零付费额度、零余额消耗**：免费模型名称带 `-free` 或为 `big-pickle`，`cost=0`，key 余额不动。
2. **架构可扩展、接入模式一次定死**：以 `opencodeZen` 为首个示范，建立「**一 provider 一适配文件**」的目录适配架构——以后任何 provider 需要特殊 HTTP 握手差异，**只新增一个适配文件**，其余代码零改动。
3. **无侵入默认路径**：本次改动不触碰 `agnes` 等既有 provider 的任何行为（零 backward 兼容性干扰）。

## 二、现状剖析（证据链）

### 2.1 Zen 免费层准入校验（2026-09-23 门禁重验，旧两条件结论作废）

经桌面端 1.18.31 独立抓包全量 body 隔离重放，服务端现为**请求头 + 请求体联合校验**，四者齐备即放行（返回 200），缺一即 403 FreeTierError：

| # | 位置 | 校验项 | 要求 | 实测通过值 |
|---|------|------|------|-----------|
| 1 | 头 | `User-Agent` | 必匹配 `opencode/<语义化版本>`，且版本 ≥ 1.17.0；缺失/非法/低于 1.17.0 分别返回 403 FreeTierError 或 426 UpgradeRequired | `opencode/1.18.31 ai-sdk/provider-utils/4.0.23 runtime/bun/1.3.14` |
| 2 | 头 | `x-opencode-session` | 合法格式会话ID：`ses_` + 12位小写十六进制 + 14位 base62 字符（共 30 字符）；随机生成即可，服务端只验格式不验存在性 | 自动生成，每 `LLMClient` 实例创建时生成一次（`static_headers()` 调用一次；每次 `snapshot()` 会话切模新建客户端即换新 session，无碍） |
| 3 | 体 | `tools` | 数组必须**同时包含**名为 `bash` 的 function 与名为 `read` 的 function；只看名字，description/顺序/其余 tool 不限；空数组、只含其一、无 tools 字段均 403 | 业务 tools 原样 + 追加 bash/read 两个最小 stub（见 5.2.3） |
| 4 | 体 | `stream` | 必须为 `true`；`false` 或缺省即 403 | 发送前强制置 `true`（见 5.2.3 `ensure_gate_body`） |

不参与校验：`Authorization` 值、`x-opencode-client` / `x-opencode-project` / `x-opencode-request`（仍每请求刷新 `msg_` + 6字节时间组件hex + 14位base62随机，不校验）、`tool_choice`、system 消息内容、messages 具体内容。

### 2.3 后端 LLM 出口链路（唯一出口）

`opencodeZen` 配置从 config.yaml 进入后端后，有 **两条平行创建路径**，最终都汇聚到唯一 HTTP 出口 `LLMClient`：

```
路径一（全局/默认模型）：
config.yaml opencodeZen
  → create_service_instance (lifecycle/service.py:95) 读 api_key/api_base/timeout/max_tokens/temperature/seed/model_params
  → BaseAIService.__init__ (base_service.py:84)
  → _ensure_client (base_service.py:124) → create_llm_client (client_sdk.py:252)
  → LLMClient.__init__ (client_sdk.py:108)
  → httpx.AsyncClient(headers={"Authorization": f"Bearer {api_key}"})   ← client_sdk.py:134 ONLY这个头!

路径二（L2 会话级切模，独立客户端快照）：
resolve_session_client (resolver.py:132) 按 _ov.provider 从 config 查配置
  → ai_service.snapshot() (base_service.py:140-168) 构造独立 BaseAIService 副本
  → _ensure_client → create_llm_client → LLMClient  → httpx.AsyncClient(headers=...)
```

### 2.4 关键结论

1. **缺口**：`client_sdk.py` 只发 `Authorization`，没有 UA/session，没有 body 门禁保障，且端点写死 `/chat/completions` → 匿名请求必死于 `403 FreeTierError`，muse 模型无路可达（实测证实）。
2. **校验层零阻碍**：`validation.py:49-53`（api_key 非空）+ `config_helpers.py:195-196`（api_key 字段存在）——配置填 `api_key: public` 即全部通过，**validation 无需改动**。
3. **需要扩展三个层面的 HTTP 行为**：
   - **静态头**（UA / session / x-opencode-client / x-opencode-project）：客户端创建时合并进 httpx `headers`，全连接生命周期固定。
   - **动态头**（x-opencode-request 每请求新 id）：走 `LLMClient.request()` / `request_stream()` 的 per-request `headers=` 参数（httpx 的 post/stream 均支持传 headers，自动与客户端默认头合并）。
   - **请求体门禁**（tools 含 bash 与 read + stream:true）：发送前调适配层 `ensure_gate_body(body)` 补齐；zen 的 `request()` 非流式语义改走流式收集（见 5.3）。
   - **端点路由**（muse 走 `/v1/responses`）：发送前按模型名调适配层 `endpoint_for(model)` 选路，chat 与 responses 用各自 body 格式。

### 2.5 provider 特殊处理散落点全核查（6 类，归属判定——北京老陈核查 2026-09-17）

全文排查后端，provider 相关特殊处理目前共 6 类、分散 4 个模块。逐一判定「该不该 provider 化」：

| # | 维度 | 现实现位置 | 现状 | 归属判定 | 是否进适配层 |
|---|------|-----------|------|---------|------------|
| 1 | 请求头/认证 | `client_sdk.py:134` 仅 Authorization + Zen 本次新增 | provider 维度，取决于认证方式差异 | **真 provider 维度** → 进适配层 | 是（本文件核心） |
| 2 | API 地址/端点 | `client_sdk.py` 写死 `/chat/completions` + `_DEFAULT_URLS` | muse 免费模型走 `/v1/responses`，按模型分路，现有单端点到不了 | **真 provider 维度** → 进适配层 `endpoint_for(model)` | 是（本文件核心） |
| 3 | 请求体 schema | `tools/schema_utils.py:24,49`（注册期统一生成） | 全局统一 anyOf（兼容 opencode/DeepSeek 严格校验） | **通用正确性**：anyOf 是标准 JSON Schema，所有 OpenAI 兼容 API 都支持 | 否（保持全局，不 provider 化） |
| 4 | 响应 reasoning | `core.py` StreamChunk / `llm_call.py:135` / `reasoning.py:62` | 三字段兼容已全局兜底：`content = full_content or full_reasoning`，纯思考(content空)有 observation 兜底 | **已通用已兜底**，ling-free 缺实测验证 | 否（保持全局 + 实测验证） |
| 5 | 工具幻觉名 | `tools/tools_alias_mapper.py:338` | 独立 dict，**32 处引用**遍布安全层/执行层/registry/trust | **安全正确性**：所有 LLM 通病（writefile 等）；provider 化 = 未配别名的 provider 直接安检漏洞 | 否（**必须保持全局**，绝非 provider 维度） |
| 6 | 错误分类 | `error_classifier.py:99-108` | 全局黑名单：403 一律 CLIENT 不可重试 | 403 不可重试是**普适语义**，全局正确；zen FreeTierError 只是消息可更友好 | 主体否（保持全局）；**错误消息映射为增强项**(已实现, 见 5.2.3) |

**统一/分散结论（三思三省）**：
- **统一进适配层**：真正 provider 独有、且发生在 **HTTP 接缝层**的握手差异——① 头/认证 ② 端点路由（chat/responses 按模型分路） ⑥ 错误消息映射(可选)，以及门禁 body 保障（tools 补 stub + stream 强制：网关只验名字与开关的准入探测，非业务语义）。
- **必须保持全局、绝不 provider 化**：③ schema、④ reasoning、⑤ 工具别名——前两者是通用正确性，⑤ 是安全正确性（provider 化会开安检漏洞）。
- **请求参数名差异（北京老陈核查 2026-09-17）**：不属适配层。chat 端点统一 OpenAI 兼容格式 + 服务端对未知参数静默 + config `model_params` 按模型粒度配特有参数（见 5.0），已天然覆盖；思考层参数（reasoning_effort 等）是**模型粒度**差异，落在 config，与 provider 无关。responses 端点用其自有 body 格式（input + flat tools），由端点路由连带确定，不另设映射层。
- **判据口诀**：*只按 provider 分道 HTTP 握手（含网关门禁探测与端点路由）；业务内容链(请求体语义/响应解析)与工具链(别名/安检)一律全局。*

## 三、设计原则（遵守 AGENTS.md 铁规 + 10 大规范）

| 原则 | 落实设计 |
|------|---------|
| KISS-DIRECT | 适配层三文件小目录：base(通用默认) + opencodeZen(定制) + __init__(查询)；client_sdk 只调统一接口 `static_headers()/per_request_headers()/ensure_gate_body()/endpoint_for()/force_stream()`，不感知 zen 细节 |
| OCP 开闭 | 新 provider 特殊 HTTP 握手 = `adapters/` 加一个文件（继承 base 覆写）；既有文件零改动 |
| SRP 单一职责 | base 只定义通用默认行为；每个 provider 文件只管自己的握手差异；查询接口只管分派 |
| DRY 不重复 | 通用逻辑在 base 一份；zen 专属（UA/ID 生成/stub/端点路由）在 opencodeZen.py 一份；client_sdk 不重复实现 |
| 禁止backward | 默认无适配 / base 基类行为 == 现状（仅 Authorization + 无动态头 + body 原样 + chat 端点），不留双份逻辑、不增加兼容开关 |
| 唯一出口 | 头/body/端点注入集中在 `LLMClient` 内部（调适配层接口），不散落在编排层/会话层 |
| 先查后建 | `_gen_session_id` / `_gen_request_id`（含 `_IdentifierGenerator`）为 opencodeZen.py 模块内私有能力，仅供该文件使用；若未来多 provider 复用再登记 FUNCTIONS.md |

## 五、详细设计

### 5.0 请求/响应载荷差异处置机制（核查定案——北京老陈 2026-09-17）

> **现状事实（北京老陈确认，2026-09-23 修订）**：chat 端点请求走**统一 OpenAI 兼容格式**（`client_sdk.py` `_build_request_body`）；provider/模型特有参数唯一走 `extra_body` 通道（config `model_params` 合并，含 `enable_thinking:True` 兜底）；**多余参数对不识别的模型服务端静默忽略**。responses 端点（muse 免费）用自有格式（`input` + flat tools，见 2.2）。响应 chat 端统一读 `choices/message/delta`，思考字段差异已由 `reasoning.py` 三字段链全局兼容；responses 端点 SSE event 形态差异待 E2E 实测验证（见八章 B26）。

**定案结论**：
1. **不引入任何参数名映射层**（YAGNI 充分成立）：chat 端统一格式 + 服务端静默 + config 按模型粒度配 `model_params` 已覆盖全部参数名差异。
2. **思考层次参数差异本质是模型粒度**（同 provider 不同模型也不同）——落在 config `model_params` 粒度，与 provider 适配层无关，**不进适配层**。
3. **门禁 body 是网关准入探测，不属业务参数差异**：tools 只验 bash/read 名字、stream 只验开关，与业务语义无关，故由适配层 `ensure_gate_body` 统一保障（见 5.2.3），不污染业务参数通道。
4. **例外预案**：若未来某 provider 服务端**不静默**（严格拒绝未知参数），再临时评估——按 YAGNI 当前不建空壳，真实案例出现时再议。

import time

# ---- ID 生成器：格式级兼容 opencode/packages/schema/src/identifier.ts ----
# 参考文件：F:\agenttool\opencode-1.18.31\packages\schema\src\identifier.ts
#          F:\agenttool\opencode-1.18.31\packages\schema\src\session-id.ts
#          F:\agenttool\opencode-1.18.31\packages\schema\src\v1\session.ts (MessageID)
# 原始逻辑：时间戳(ms) << 12 + counter，descending 用按位取反，ascending 不取反
# TS 的 ascending()/descending() 共享模块级 counter(同一毫秒内 ses_/msg_ 连续递增) — 结构对齐
# 前12字符=时间组件(hex)，后14字符=加密安全随机(base62) — 小欧 2026-09-17
# 兼容性声明(核查 2026-09-20)：服务端只校验格式(ses_/msg_+12hex+14base62)，不解析数值语义，
#   故本实现保证格式级兼容；Python `~` 为无限精度整数、TS `~` 为 32 位语义，大数下数值位
#   必然分叉——属可接受差异（YAGNI：数值拟真非必要）。外部 TS 源码逐行比对未独立验证，待确认。

_CHARS = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz"


class _IdentifierGenerator:
    """有状态 ID 生成器，与 TypeScript identifier.ts 共享 counter 语义对齐 — 小欧 2026-09-17"""

    def __init__(self):
        self._last_timestamp = 0
        self._counter = 0

    def generate(self, prefix: str, descending: bool) -> str:
        now_ms = int(time.time() * 1000)
        if now_ms != self._last_timestamp:
            self._last_timestamp = now_ms
            self._counter = 0
        self._counter += 1

        current = now_ms * 4096 + self._counter
        value = ~current if descending else current

        time_hex = "".join(
            format((value >> (40 - 8 * i)) & 0xFF, "02x")
            for i in range(6)
        )

        rand_bytes = os.urandom(14)
        rand_part = "".join(_CHARS[b % 62] for b in rand_bytes)

        return prefix + time_hex + rand_part


# 模块级单实例: ses_/msg_ 共享同一直计数器(与 TS identifier.ts 行为一致) — 小欧 2026-09-17
_gen_id = _IdentifierGenerator()


def _gen_session_id() -> str:
    """生成 session ID: ses_ + 12位hex + 14位base62，客户端生命周期内固定复用 — 小欧 2026-09-17"""
    return _gen_id.generate("ses_", descending=True)   # 与 session-id.ts 的 descending() 对齐


def _gen_request_id() -> str:
    """生成 request ID: msg_ + 12位hex + 14位base62，每请求刷新 — 小欧 2026-09-17"""
    return _gen_id.generate("msg_", descending=False)   # 与 v1/session.ts MessageID 的 ascending() 对齐

**扩展规则（一 provider 一文件）**：
- 新 provider 需特殊 HTTP 握手 → `adapters/` 新建 `{provider}.py`（继承 base 覆写 static_headers/per_request_headers/ensure_gate_body/endpoint_for/force_stream/error_message_map）+ `__init__.py` `_ADAPTERS` 加一行 `"{provider}": {Xxx}Adapter()`。
- 完全无特殊握手的 provider（agnes/openai/deepseek 等）→ 不建文件，自动走默认基类（==现状），**零文件零逻辑**。

**接入三步骤（新 provider 按此操作）**：
1. **判定**：差异是否属于 HTTP 接缝握手（含网关门禁探测与端点路由）？→ 是→进适配层；否（业务请求体语义/响应解析/工具别名/安检）→ 保持全局不动。
2. **建文件**：`adapters/{provider}.py` 继承 `ProviderAdapter`，覆写 static_headers / per_request_headers / ensure_gate_body / endpoint_for / force_stream / error_message_map 钩子。
3. **注册**：`adapters/__init__.py` 的 `_ADAPTERS` 加一行 `"{provider}": {Xxx}Adapter()`。

| 场景 | 做法 | 改动面 |
|------|------|--------|
| 新 provider 要自定义头（如某网关要求 x-api-key） | adapters/ 加文件 + __init__ 注册 | 2 处（新增文件+1行注册），既有代码零改动 |
| 新认证模式（azure/oauth 等不同握手算法） | 同上（覆写 static_headers 的逻辑差异化在定制文件内） | 2 处 |
| 无特殊握手的 provider（agnes/openai/deepseek） | 不建文件，自动默认基类 | 零 |

## 六、风险与边界

| 风险 | 等级 | 缓解 |
|------|------|------|
| 匿名免费层服务端随时可收紧（v3 已是弱校验绕过） | 中 | `api_key` 一键切回 `sk-`，架构不变 |
| IP 配额共享（约 200 次/天，全站同出口 IP） | 中 | 免费模型用于按需测试/低频场景；重负载走付费 key 或切换 provider |

| 全局单例 client 复用同一 session（多会话共享） | 低 | 实测服务端只校验格式不校验唯一性 |
| httpx 0.26.0 / httpcore 1.0.1 版本锁定不容破坏 | 高 | 本次改动不触碰任何依赖版本 |
| 适配器误将全局逻辑 provider 化（破坏 schema/别名安全） | 中 | 2.5 判定 + 三章"内容链/工具链一律全局"红线写死，评审把关 |

| 门禁持续收紧（9-17两条件→9-23四条件） | 中 | 适配层钩子已按"头+体+端点"分层，服务端再加条件时只改 opencodeZen.py；`api_key` 一键切付费兜底 |
| responses 端点 SSE event 形态与 chat delta 不同 | 中 | B26 E2E 实测验证；解析差异收敛在 `to_responses_body` 逆向一处，不碰全局 reasoning 链 |
