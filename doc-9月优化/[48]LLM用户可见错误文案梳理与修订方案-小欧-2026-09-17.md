## 一、问题背景

用户看到的原消息：

```
⚠️ [quota_exceeded] LLM流式错误: API配额/速率限制已耗尽(rpm exhausted)，请稍后重试或升级配额
```

三个问题：`[quota_exceeded]` 是内部英文枚举直接暴露；`LLM流式错误:` 是日志语言；`配额/速率限制已耗尽(rpm exhausted)` 中英混杂、两个概念并列、语句不通顺。

## 二、信息在哪里生成的

共四段：`backend/app/llm/base_service.py:438` 生成原始文案 → `backend/app/services/agent/llm_call.py:147` 拼接 `LLM流式错误:` 前缀 → `backend/app/services/agent/handlers/handle_answer.py:101-124` 原样装入 FinalStep 的 `error_message` → `frontend/src/features/chat/components/pipeline/PipelineRenderer.tsx:389` 按 `⚠️ [英文类型] 文案` 渲染。

## 三、文案消费落点（出现在哪些消息上）

### 3.1 配额类 LLM 错误文案的落点（走 final/failed 消息，共 5 处）

1. 右侧执行过程 final 段细节行（`PipelineRenderer.tsx:389`）：`⚠️ [quota_exceeded] …`，随 final 落库，历史回放可见。本次修改 7 覆盖。
2. 右侧任务统计块错误项（`StaticStatsBlock.tsx:391`），数据源自任务详情接口（读库）。本次修改 7 覆盖。
3. 中央聊天气泡：正文固定显示 `任务执行失败`（final.response），不显示具体原因；具体文案存于消息 `errorMessage` 字段，由错误详情组件呈现，不受修改 7 格式影响。
4. 顶部任务信息条第一行（位4）实时行，`error_message` 超长时 tooltip 展示全文，不受修改 7 格式影响。
5. 不出现的位置：toast。后端业务错误只进展示位、不弹窗（6.3.3 分道），故配额耗尽无 toast 提示。

### 3.2 其他后端文案的落点

1. error 事件消息（工具拒绝/超时类）：只进任务信息条位4（🛑行），不进执行步骤列表、不落库不回放，任务结束即消失，靠 final 终态留痕。
2. meta/retrying 重试提示（`LLM请求重试`、`LLM响应重试`、`FC模式降级`）：任务信息条位4（🔁行），过程态，任务结束即消失。
3. final/cancelled 取消终态：取消文案放 `response` 主行，另起一行橘红显示 `! 取消来源`。
4. 编排层兜底（`agent_operation_error`，原始异常直出）：走 final/failed，与 3.1 同链路、同 5 处落点。

### 3.3 前端自产文案（非后端，共 4 处）

- 空响应兜底（`useChatCallbacks.ts:432-438`）：气泡正文`抱歉，我暂时无法回答这个问题…`，`errorType` 记为 `empty_response`。
- 回退文案：`未知错误`（sseParser 解析兜底、useChatFacade 兜底）、`执行被拒绝`、`执行出错`（StatusLine 兜底），仅后端未给文本时出现。

## 六、术语准确性说明

1. 配额耗尽（Quota）与频率超限（Rate Limit）必须分开表述：配额用完需等重置或升级，限流稍后重试即可。原文案"配额/速率限制已耗尽"把二者混为一谈，是本次首要纠正的术语错误。修订后修改 1 只讲配额，修改 2.7 只讲限流。
2. HTTP 429 是标准状态码，既可表示频率超限也可表示配额耗尽（取决于服务商响应体的 reason 字段）。本项目把 429 统一按配额耗尽处理，故中文主句写"配额已用尽"，括号标注 HTTP 429 保留排错精度。
3. tool_calls 是 OpenAI 兼容接口的函数调用字段原名，服务商文档通用该词，保留原名比全译更利于对照排查，故用"工具调用（tool_calls）"中英对照。
4. Idle Timeout 指字节流间隙超时（非总时长），与 `base_service.py` 的 read 超时语义一致；Client Error / Server Error 分别对应 4xx 请求方问题与 5xx 服务方问题；Empty Response 指 HTTP 200 但无可用内容。
5. 标点统一全角（，。：（）），中英之间不空格。
