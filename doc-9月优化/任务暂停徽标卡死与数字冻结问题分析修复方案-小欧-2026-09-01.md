## 一、背景

1. 实时任务（SSE流式中 `receiving=true`）运行时，TaskInfoBar 第一行**长期稳定显示"已暂停"徽标**，而任务实际在后台持续推进（日志显示 LLM 已调至 #17，step 至 16+，`THINKING→EXECUTING→THINKING` 循环从未中断）。
2. 伴随徽标卡死，数字**不是逐刻实时**（北京老陈后续澄清：数字并非"冻结到死"，而是**更新滞后/慢**，见 §三.3 重新定性）。

**实时性硬要求**（北京老陈明确，2026-09-01 现场沟通）：
- **轮次相关信息和数字**：与轮次更新同步——"有新的轮次就实时更新"即可（随 stats/usage 帧每轮一次，帧到达即更新，边界满足）。
- **计时（耗时）**：**前端单独计时**（不依赖后端帧），**必须秒更新**。

本报告：先给出现象与日志铁证，再定位根因（后端事件语义缺失 + 前端badge推导缺陷 + 前端耗时秒表被badge掐死），最后给前后端配合修复方案（先文档后代码）。

## 三、根因分析（三思三省）

### 3.1 根因1（后端·事件语义缺失）：暂停后部分路径"不补发 resumed"

`useTaskInfo` 的 badge 唯一能离开 `paused` 的信号只有 `resumed` 或 `final`。但后端有**多处暂停路径在恢复后不补发 `resumed`**：

| # | 位置 | 暂停 | 恢复后行为 | 是否补发resumed |
|---|------|------|-----------|----------------|
| S1 | `action_handler.py:331-352` auto_confirm | `paused`(:320) | `resolve_confirmation(True,trust_session=True)` 后直接 `continue` | ❌ 不发 |
| S2 | `action_handler.py:354-398` 真HITL | `paused`(:320) | 用户确认后 `set_status(EXECUTING)`；`resumed`(:383) 在 `if auth_path` 内 | ⚠️ 仅auth_path才发，无auth_path不发 |
| S3 | `sandbox_gate.py:64-77` 沙箱裁决 | `paused`(:67) | `set_status(EXECUTING)`(:74)，确认后继续 | ❌ 从不发 |

> S2 的 `resumed` 被错误地绑在 `if auth_path` 分支内（:383）。实际上"用户确认"本身就是恢复信号，与是否授权白名单外路径无关，resumed 应无条件下发。

### 3.2 根因2（前端·badge推导缺陷）：仅靠 resumed/final 离开 paused

`frontend/src/features/chat/hooks/useTaskInfo.ts:92-129` 遍历累积的 `executionSteps`：

```ts
case 'paused':  badge = 'paused';  break;
case 'resumed': badge = 'running'; break;
case 'final':   badge = completed/failed/cancelled; break;
// thought / action / observation → default: 不改 badge
```

- `paused` 被当作**持久状态**，而它实际是**瞬时事件**；
- `thought/action/observation`（业务推进）**不改 badge**，导致 paused 之后即使任务已恢复并持续推进，badge 仍停 `paused`；
- 一旦 badge 卡 `paused`，`TaskInfoBar.tsx:96` `if (receiving && info.badge === 'running' && !detail)` 的 `liveElapsed` 计时器**不再启动**，`shownElapsed` 回退到 `info.elapsedSec`（来自 stats 帧）。

### 3.3 数字"冻结 vs 延迟"重新定性（北京老陈澄清后）

老陈现场澄清："task info 框框的数字后面发现并没有冻结，当时是否实时不确定，可能延迟；**要求是必须实时**"。据此核查前端数字来源，**重新定性**（修正 v1.0/v1.1"数字冻结"的过度表述）：

| 数字 | 来源 | badge卡paused影响 | 实时性现状 |
|------|------|-------------------|-----------|
| **耗时** | **前端独立秒表** `liveElapsed`（TaskInfoBar:93-116，`Date.now()-start` 每秒 setInterval） | **被 kill**：秒表只 `badge==='running'` 走表，卡 paused 后 `shownElapsed` 回退 `frames.stats.duration`（按帧更新） | ⚠️ 由逐秒退化为按 stats 帧——观感"变慢/滞后" |
| 步骤/轮次 | `frames.stats.step_count / llm_call_count` | **不受影响**（badge独立，帧到即更新） | ✅ 随 stats 帧（每 LLM 轮发一次，react_cycle.py:521-535） |
| 本轮/任务累计T | `frames.roundUsage / taskAccumulated` | **不受影响** | ✅ 随 usage 帧（每 LLM 轮发一次） |
| 上下文 tok | `frames.contextOverview` | **不受影响** | ✅ 随帧 |

**结论（修正）**：
1. 老陈观察正确——步骤/轮次/token **没真冻结**，它们由 `stats/usage` 帧驱动（**每 LLM 轮发一次**，react_cycle.py:521-535），帧到就更新，只是 LLM 单轮几十秒，观感"延迟/慢"。
2. **真正被 badge 卡 paused 掐死的，是"耗时"的前端独立秒表**（`liveElapsed`），它从"**秒更新**"退化为"按 stats 帧的 duration 更新"，观感变化最明显——这正对应老陈"必须实时"中对耗时的**秒更新**硬要求。
3. 鉴此，**修复焦点收敛为：让 badge 在 auto_confirm/恢复后正确回 `running`，从而恢复前端耗时秒表的逐秒走表**。轮次相关数字随帧更新已满足"有轮次就实时更新"语义，无需另动后端统计频率。

> 注：`liveElapsed` 为**纯前端独立计时**（不依赖后端任何帧，`Date.now()-start`），秒表一旦恢复 `badge==='running'` 即逐秒走，与后端帧频率完全解耦。故修好 badge 即恢复耗时的**秒实时**。

### 3.4 更深关联 bug（本修复同时解除）：auto_confirm 无 resumed 致聊天区执行步骤无限缓冲

三堂会审关联审查发现的**更深一层缺陷**（`useChatCallbacks.ts`）：

- `onPaused`（:601）设 `isPausedRef.current = true`；`onStep`（:164）在该标志为 true 时，把 **`thought/action/observation/chunk` 全部 push 进 `displayBufferRef` 缓冲、不直接显示**；缓冲**仅在 `onResumed`（:656）时回放释放并置 `isPausedRef=false`**。
- `sseParser`：`stats/usage/context_overview`（:189/224）走 `setMetaFrames` **直通通道**（不经 onStep 缓冲），故 TaskInfoBar 数字不受暂停缓冲影响——**佐证老陈"数字随帧更新、只是延迟"的观察**。
- 但 **auto_confirm 原本只发 `paused`、从无 `resumed`** → `isPausedRef` 永久为 true → **auto_confirm 场景下聊天区后续执行步骤（thought/action/observation/chunk）被无限缓冲、不显示**（附带的更隐蔽 bug）。

**本方案后端补发 `resumed` 的额外收益**：补发的 `resumed` 触发前端 `onResumed` → **缓冲回放 + `isPausedRef=false`** → 聊天区执行步骤恢复正常显示。**修复不仅解 TaskInfoBar 徽标/耗时，还一并解除聊天区执行步骤无限缓冲的关联 bug——典型的"增强且进化、无退化"。**

## 四、修复方案（前后端配合，最稳）

> 目标：**新数据根治（后端事件契约完整）+ 历史/漏发兜底（前端推导）**，双保险最稳，经得起三堂会审。
> 修复的直接效果（对齐老陈实时性要求）：
> - **耗时**：badge 正确回 `running` → `liveElapsed` 逐秒秒表恢复，**秒更新**（核心）。
> - **步骤/轮次/token**：随 `stats/usage` 帧（每 LLM 轮发一次）更新，"有轮次就实时更新"语义已满足，不依赖 badge。

### 4.0 关键前提（修正后的聚焦）

本次**必须修的是 badge 卡 paused** —— 它是唯一把前端耗时秒表掐死、且让徽标长期误显"已暂停"的根。修复 badge 后：
- 耗时恢复**秒实时**（前端独立秒表单走）；
- 徽标与实际执行态一致；
- 轮次相关数字本就随帧更新，语义即满足。

### 4.1 后端治本：暂停后补发 resumed（事件契约成对）

**改动点 S1**：`action_handler.py` auto_confirm 分支，`resolve_confirmation`/`set_status(EXECUTING)` 之后、`continue` 之前，补发 `resumed`：

```diff
  resolve_confirmation(confirm_id, confirmed=True, trust_session=True)
  set_status(agent, AgentStatus.EXECUTING, "安全策略自动确认工具执行")
+ yield agent._step_emitter.emit(MetaStep(
+     step=step, type="resumed",
+     content=f"已自动确认工具执行: {_cn}",
+     severity="info",
+ ))
```

**改动点 S2**：`action_handler.py` 真HITL分支，把 `resumed` 从 `if auth_path` 内**移出**，确认后无条件下发（恢复与授权解耦）：

```diff

- if getattr(safety_result, "auth_path", None):
+ if getattr(safety_result, "auth_path", None):
      grant_temp_auth(...)
      yield MetaStep(type="resumed", ...)      # 保留授权提醒

+ yield MetaStep(type="resumed", content="用户已确认工具执行", severity="info")  # 无条件恢复信号
```

> 说明：S2 改动需谨慎，避免与既有 `resumed` 重复。三堂会审时再精确裁定是"移出"还是"另发一条"。

**改动点 S3**：`sandbox_gate.py:74-77` 沙箱用户裁决确认后补发 `resumed`：

```diff
      logger.info(f"[sandbox] 用户裁决: 确认执行: tool={tool_name}")
+     steps.append(agent._step_emitter.emit(MetaStep(
+         step=step, type="resumed",
+         content=f"沙箱预检已确认执行: {tool_name}", severity="info")))

```

### 4.2 前端兜底：badge 按"最后确定性信号"推导（防御历史/漏发）

`frontend/src/features/chat/hooks/useTaskInfo.ts`：把 `paused` 从"持久状态"改为"瞬时事件"——遍历时，`paused` 之后**若出现业务推进 step（thought/action/observation）**，说明任务已越过暂停点，badge 推导为 `running`；只有 `paused` 之后**无任何推进**（真HITL挂起中）才保持 `paused`。

核心思路（伪码）：
```ts
let sawPausedAfter = -1;  // 记录最近一次 paused 的下标
for (let i = 0; i < steps.length; i++) {
  switch (steps[i].type) {
    case 'paused': badge = 'paused'; sawPausedAfter = i; break;
    case 'resumed': badge = 'running'; sawPausedAfter = -1; break;
    case 'final': ...; break;
    case 'thought':
    case 'action':
    case 'observation':
      if (sawPausedAfter !== -1) { badge = 'running'; }  // paused 之后有推进 → 已恢复
      break;
    default: break;
  }
}
```

> 说明：该推导是**纯函数式、确定、无时序依赖**的——对任意时刻的累积 steps 数组都能给出正确终态：真HITL挂起（最后是paused、无后续推进）→ paused ✓；auto_confirm/已恢复（paused后有thought/action）→ running ✓；历史/漏发旧数据同理正确。

### 4.3 为何必须前后端配合（三思三省结论）

| 维度 | 仅后端 | 仅前端 | 前后端配合 |
|------|--------|--------|-----------|
| 新数据根治 | ✓ 补发resumed | ✗ 需推导 | ✓ |
| 历史遗留旧数据 | ✗ 不修（旧数据无resumed） | ✓ 推导兜底 | ✓ |
| 后端多路径遗漏风险 | 高（S1/S2/S3不全补则漏） | 不依赖后端 | ✓ 不惧（前端兜底） |
| 改动面 | 中（后端3处核心路径） | 小（前端1处） | 两端 |
| 可靠性 | 依赖枚举全，易漏 | 语义推导，稳 | **双保险最稳** |

**结论**：前端兜底推导**是必须的**（历史数据 + 后端多路径难以100%枚举全），后端补resumed**是治本**（新数据契约完整，且让S2语义正确）。二者互补，缺一不可，故**前后端配合最稳**。

## 五、设计原则（待三堂会审）

- **事件契约成对**：`paused` 必须配 `resumed`（或 `final` 终止），恢复是显式事件而非推断的副作用。
- **前端纯推导**：badge 是"对累积步骤的确定性推导"，不引入时序/异步状态，`KISS-DIRECT` 直线、`DRY`。
- **最小最稳**：仅在暂停/恢复边界补事件 + 前端一处推导改造，不引新框架/状态机（`YAGNI`）。
- **禁止backward**：不加兼容开关，语义修正后直改。
