## 一、现状分析

### 1.1 当前运行模式: 自动确认(bypass)模式

实际 `config/config.yaml`:

```yaml
security:
  auto_confirm_delay: 6
  hitl_timeout: 120
  enabled: false      # ← 当前 false = bypass 自动确认模式
```

- `security.enabled: false` → `_is_skip_safety()` 返回 True(`tool_safety_checker.py:93-98`)。
- 本需确认的工具调用走 bypass 自动确认: **仍弹窗**(倒计时自动放行), `auto_confirm=True`(`tool_safety_checker.py:158-167`): paused 照发, 前端倒计时(默认 4s)到期自动 allow(`safety_gate.py:96-113`); 用户仍可在倒计时窗口内手动拒绝。
- **危险防护不受影响**: 路径越权/写入大小保护/系统禁区/delete R6 等无条件硬拦(`tool_safety_checker.py:131-155`)。

### 1.2 信任名单的对象: 工具名 + 路径(tool + path)

核心定案(2026-09-02 北京老陈), 落库表 `chat_session_trust(session_id, tool_name, path)`:

| 维度 | 说明 | 代码出处 |
|------|------|---------|
| tool_name | 规范化工具名(normalize_tool_name) | `trust.py:18,118` |
| path | 从调用参数提取的目标路径; 仅路径类参数参与, 非路径参数不进信任 | `trust.py:66-74` |
| path=NULL | 无路径参数工具 → 工具级通配行(整工具豁免) | `trust_db.py:27-34` |
| 豁免粒度 | 信任根 == 目标 / 是目标的祖先目录(前缀递归) | `trust_db.py:36-58` |

### 1.3 信任的产生渠道(唯一主通道)

```
前端确认(勾 trust_session=True)
  → POST /api/.../confirm  (chat_routes.py:89-96)
  → resolve_confirmation(confirm_id, confirmed=True, trust_session=True)  (hitl_confirmation.py:158-197)
  → save_session_trust(task_id, tool_name, entry.path)  (trust.py:106-120)
  → insert_session_trust(session_id, 规范化工具名, _norm_trust_path(path))  (trust_db.py:27-34)
```

防污染: bypass 模式下前端强制 `trustSession=false`(勾了也不落库), `index.tsx:152-158`。

> **v1.5 历史定案(bypass 不产生信任)**:
> 1. **确实曾经落库**。v1.5 前 bypass 无条件 `trust_session=True`, 每个自动放行工具都落信任——老陈记的"自动确认加入信任列表"是真实旧行为。
> 2. **2026-09-02 v1.5 定案移除**(`会话信任功能修复方案-小欧-2026-09-02.md` 5.4): bypass 直放不产生信任。理由: 清单污染(含用户从未同意的工具) + 长期豁免盲区(自动信任不过期, 切回 enabled:true 后仍命中)。
> 3. **恒空四环节**: ① `security.enabled: false` → bypass; ② 前端强制 `trustSession=false`; ③ `hitl_confirmation.py:187` 永不触发 `save_session_trust`; ④ bypass 分支仅 `grant_temp_auth` 不落表。
> 4. **结论**: 信任列表恒空是 v1.5 定案后的正确预期, 非 bug。

### 1.4 信任的消费(豁免判定)链路

```
safety_gate.check_safety_and_confirm(每 call)
  → resolve_skip(agent_task_id, tool_name, params)      # trust.py:81-99
  → check_session_trust(session_id, 规范化名, path)     # trust_db.py:36-58
  → check_before_execute(skip_confirmation=_skip)        # 豁免只跳确认不跳危险防护
```

豁免语义: `skip_confirmation=True` 只跳过确认询问, 已知风险/系统禁区仍 blocked。

### 1.5 信任的撤销

`DELETE /sessions/{id}/trust/{tool_name}?path=xxx` — path 传入精确删, 空则删通配行, 无匹配 404。

## 二、确凿问题(需修复)

### 2.1 全链路总览

```
[后端] safety_gate.check_safety_and_confirm
   │  ① trust.resolve_skip(会话信任预查)
   │  ② tool_safety_checker.check_before_execute(skip_confirmation)
   │        ├─ blocked → error 事件
   │        ├─ requires_confirmation → ③ hitl_gateway.hitl_confirm
   │        │      ├─ paused 事件(trust_path/auto_confirm/confirm_timeout/backend_timeout)
   │        │      ├─ wait_for_confirmation_result
   │        │      └─ resolve_confirmation 单点收口
   │        └─ 豁免/safe → sandbox 汇合 + grant_temp_auth
   │  ④ resolve_confirmation → confirmed+trust_session → save_session_trust
[前端] SSE paused → sseParser → useAuthorization → AuthorizationModal
   ├─ 用户点允许/勾信任 → confirm API(trust_session)
   ├─ 成功 → omni-trust-changed → TrustPanel 刷新

```

### 2.2 问题A: 落库/查询路径提取不对称 → 非文件工具路径级信任永不生效(实施错误)

**根因**: 落库侧 `_resolve_trust_path`(`hitl_gateway.py:36`) 复用了 sandbox 判断越界写意图的 6 键回落扫描, 但查询侧 `_parse_paths`(`trust.py:31-43`) 没有对应逻辑, 仅对 `FILE_OPERATION_TOOLS`/窗口工具提取 → **两侧不对称(DRY 违反)**。

**落库侧完整链路**(逐行验证):
1. `safety_gate.py:98`: `ConfirmSpec` 未传 `path` → `spec.path=None`
2. `hitl_gateway.py:71`: `_path = spec.path or await _resolve_trust_path(...)` → 走回落
3. `hitl_gateway.py:33`: `extract_trust_path` → registry_write 不在 `FILE_OPERATION_TOOLS` → None
4. `hitl_gateway.py:36`: **回落扫描** `("path","file_path",...)` → `params.get("path")` = `"HKCU\Software\X"` → 返回
5. `hitl_confirmation.py:107-108`: `create_confirmation` 存储 `entry.path = "HKCU\Software\X"`
6. `hitl_confirmation.py:190`: `resolve_confirmation` → `save_session_trust(task_id, "registry_write", entry.path)`
7. `trust_db.py:32`: `_norm_trust_path("HKCU\Software\X")` → `Path("HKCU\Software\X").resolve()` → **`F:\OmniAgentAs-repair\HKCU\Software\X`**(垃圾路径)入库

**查询侧完整链路**(逐行验证):
1. `safety_gate.py:71`: `_skip = await resolve_skip(...)`
2. `trust.py:93`: `_tgt = extract_trust_path("registry_write", params)` → `_parse_paths` 返回空集(None)
3. `trust_db.py:45-46`: `path is None` → 只查 `path IS NULL` 行
4. 落库的行 path = `"F:\...\HKCU\Software\X"`(非 NULL) → **永不命中**

**受影响工具**(三者共同特征: schema 参数名=`path` + `needs_confirmation=True` + 不在 `FILE_OPERATION_TOOLS`):

| 工具 | Schema出处 | 注册出处 | 症状 |
|------|-----------|---------|------|
| registry_write | `win_registry_schema.py:59` | `win_registry_register.py:70,91` | 路径级信任永不生效 + 垃圾路径入库 |
| registry_delete | `win_registry_schema.py:87` | `win_registry_register.py:70,91` | 同上 |
| execute_sql | `dataanalysis_schema.py:46` | `dataanalysis_register.py:135` | 路径级信任永不生效(路径本身正确但查询不命中) |

shell 类(参数 command/cwd 无 6 键)不受影响 → 工具级通配正常。

### 2.3 问题B: `_norm_trust_path` 对注册表键路径 `Path.resolve()` → 垃圾绝对路径入库(问题A的伴生症状)

`trust_db.py:17-24`: `_norm_trust_path` 对任意 path 做 `str(Path(path).resolve())`。

实测(`E:\Appsw\python31311\python.exe`): `Path(r"HKCU\Software\MyApp").resolve()` → `F:\OmniAgentAs-repair\HKCU\Software\MyApp` — 注册表键被当项目目录下相对文件路径解析。

组合问题A: registry 工具若真 HITL 勾选信任, 落库的是臆造的垃圾路径; 即便查询侧修复统一, 该路径也永远匹配不上真实注册表键。

建议: registry 类工具排除出文件路径信任域; `_norm_trust_path` 不应对非文件路径做文件系统 resolve。

### 2.4 问题C: 信任豁免 vs 沙箱 needs_ruling — 设计有意但产品语义未对齐(留白待定)

**代码链路**:
1. `tool_safety_checker.py:188-194`: skip_confirmation 分支 → `SafetyResult(sandbox_required=_needs)`, **auto_confirm 未设(默认 False)**
2. `safety_gate.py:168`(插入点③): `run_sandbox_gate` 缺省 `main_confirmed=False`
3. `sandbox_gate.py:88`: `pre.needs_ruling and safety_result.auto_confirm` → False → 不直通
4. `sandbox_gate.py:85`: `main_confirmed and pre.needs_ruling` → False → 不直通
5. → `sandbox_gate.py:101-113`: needs_ruling → 再弹 HITL

**但这是有意设计**: `tool_safety_checker.py:189` 注释"v1.6 会审F1: 信任豁免只跳确认不跳沙箱", 安全方向正确。

**触发面极窄**:
- registry 工具: `executor.py:295-298` 静态分析始终 passed → 永不触发;
- delete/copy/move: 正常影子副本预演 → passed → 不弹; 仅源不存在/预检超时/环境性失败等边缘场景 → 二次弹。

**留白**: TrustPanel 文案"免弹框"与"边缘场景仍弹"产品语义未对齐。需决策: 保持保守行为 / 信任时 needs_ruling 也直放 / 文案修正。

### 2.5 前端协同/呈现缺陷(3处)

> 前述问题A/B/C 的根因均在后端, 前端无法自行修复。但前端有 3 处协同/呈现缺陷:

**缺陷①(最重要, 老陈困惑的人因来源): bypass 弹窗勾选框静默失效无提示**
- `AuthorizationModal/index.tsx:296-310`: 勾选框始终渲染、可勾选;
- `:154-160`(handleConfirm): 对 `isBypass` 强制 `trustSession=false`;
- `isBypass` 前端已知(`:108`), 却不隐藏/禁用勾选框、不提示;
- 正是老陈"记着自动确认会进信任列表、列表却恒空"的 UI 误导来源。
- **建议**: bypass 模式下禁用勾选框并展示说明文案。

**缺陷②: trust_path 无校验原样展示**
- `index.tsx:301-303`: tooltip 显示 `{toolName} › {trustPath}，含子目录`;
- `TrustPanel.tsx:178`: 显示 `{path ?? '全局'}`, 撤销原样回传(`task.api.ts:227-238`);
- 后端垃圾路径原样展示给用户, 前端零校验。

**缺陷③: "含子目录"文案对非文件工具语义错误**
- `index.tsx:303`: 对 registry_write 等注册表键工具, "子目录"是文件系统语义, 注册表键层级 ≠ 文件目录树。
- **建议**: 按工具域区分文案。
