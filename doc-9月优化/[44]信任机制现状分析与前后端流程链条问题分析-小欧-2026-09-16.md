## 一、现状分析

### 1.1 当前运行模式: 自动确认(bypass)模式

实际 `config/config.yaml`:

```yaml
security:
  auto_confirm_delay: 6
  hitl_timeout: 120
  enabled: false      # ← 当前 false = bypass 自动确认模式
```

- `security.enabled: false` → 判定函数 `_is_skip_safety()` 返回 True(`tool_safety_checker.py:93-98`)。
- 一切**本需确认**的工具调用**走 bypass 自动确认: 仍弹窗(倒计时自动放行)、按 auto_confirm=True 语义不等真人点选即续行**(`tool_safety_checker.py:158-167`):
  - needs_confirmation 命中 → `SafetyResult(requires_confirmation=True, auto_confirm=True)` 提示照出、paused 照发, 前端倒计时(默认 confirm_timeout=4s)到期自动 allow(`safety_gate.py:96-113`);
  - 白名单外临时授权请求同样 `auto_confirm=True` 直放(`tool_safety_checker.py:141-151`);
  - v0.2 修正: **bypass 不是"不弹窗"**, 是"自动确认弹窗"——paused 帧/弹窗/倒计时仍完整, 只是 `_auto = spec.mode == "bypass"` 使前端不挂起等人(`hitl_gateway.py:74`); 用户仍可在倒计时窗口内手动拒绝。
- **危险防护不受影响**: 已知风险(路径越权/写入大小保护/系统禁区写删/代码注入/delete R6)为无条件防线, 开关 false 仍 `blocked` 硬拦(`tool_safety_checker.py:131-155`)。

### 1.2 信任名单的对象: 工具名 + 路径(tool + path)

核心定案(2026-09-02 北京老陈: "只有 tool+path 才是准确对象"), 落库表 `chat_session_trust(session_id, tool_name, path)`:

| 维度 | 说明 | 代码出处 |
|------|------|---------|
| tool_name | **规范化工具名**(normalize_tool_name, 防别名 write_text/writefile 写穿) | `trust.py:18,118` |
| path | 从调用参数经 PARAM_ALIASES 提取的**目标路径规范绝对化**; 仅路径类参数(path/file_path/source_path/dest_path/target/dir_path)参与, **非路径参数(content/action 等)一律不进信任** | `trust.py:66-74`(extract_trust_path) |
| path=NULL | 无路径参数工具/窗口工具 → **工具级通配行**(整工具豁免) | `trust_db.py:27-34` |
| 豁免粒度 | 命中工具级通配行, 或**信任根 == 目标 / 是目标的祖先目录(前缀递归)** → 信任"**该路径及其子目录树**", 非精确到单次参数快照 | `trust_db.py:36-58` |

### 1.3 信任的产生渠道(唯一主通道)

信任**只能**由"真 HITL 手动确认 + 勾选『信任此操作(本次会话)』"产生:

```
前端确认(勾 trust_session=True)
  → POST /api/.../confirm  (chat_routes.py:89-96)
  → resolve_confirmation(confirm_id, confirmed=True, trust_session=True)  (hitl_confirmation.py:158-197)
  → save_session_trust(经 task_id 反查 session_id)  (trust.py:106-120)
  → insert_session_trust(规范化工具名, path)  (trust_db.py:27-34)
```

防污染机制: 前端在 **bypass 模式下强制 `trustSession=false`**(勾了也不落库), 堵"bypass 期间勾出的信任, 切回 enabled=true 后转正为长期豁免"漏洞(`frontend AuthorizationModal/index.tsx:152-158`)。

> **v0.2 历史定案(回答老陈"自动确认不是也加入信任列表吗, 为何信任列表恒空")**:
>
> 1. **确实曾经落库**。v1.5 修复前 bypass 分支无条件 `resolve_confirmation(confirmed=True, trust_session=True)`, 每个自动放行的工具都会自动落一行信任——老陈记的"自动确认加入信任列表"是当时的**真实旧行为**。
> 2. **2026-09-02 v1.5 定案移除**(`doc-9月优化/会话信任功能修复方案-小欧-2026-09-02.md` 5.4, 病根3.6): bypass 直放**不产生信任**, 仅"真 HITL 显式勾选"才落库。理由:
>    - 清单污染: 自动放行沉淀出的信任含**用户从未同意**的工具;
>    - 长期豁免+过期盲区: bypass 期自动信任不过期, 切回 `enabled:true` 后 `check_session_trust` 仍命中, 使"自动信任"借道转正成"长期用户豁免"(用户从不曾主动同意)。
> 3. **恒空四环节链条**(代码实链):
>    - ① `config.yaml security.enabled: false` → 全局 bypass;
>    - ② 前端 `AuthorizationModal/index.tsx:158`(及 `:129-133` 倒计时代发)强制 `trustSession=false`;
>    - ③ 后端 `hitl_confirmation.py:187` `if confirmed and trust_session` 永不触发 `save_session_trust`;
>    - ④ 后端 bypass 分支只 `grant_temp_auth`(任务级临时授权), 不落 `chat_session_trust`(`safety_gate.py:104-117`)。
> 4. **结论**: 前端信任列表恒空(`可信(0)`)是 v1.5 设计定案后的**正确预期**, 非 bug。信任列表只会在 `enabled:true` + 真 HITL 勾选后才增生。

### 1.4 信任的消费(豁免判定)链路

```
safety_gate.check_safety_and_confirm(每 call)
  → resolve_skip(agent_task_id, tool_name, params)      # 信任预查(trust.py:81-99)
  → check_session_trust(session_id, 规范化名, path)     # 前缀递归匹配(trust_db.py:36-58)
  → check_before_execute(skip_confirmation=_skip)        # 豁免只跳确认不跳危险防护(工具:112-119)
```

豁免语义: `skip_confirmation=True` 时**只跳过确认询问**, 已知风险/系统禁区仍 blocked; 受保护区域/白名单外写入豁免时**保留 auth_path** 交调用方 grant_temp_auth 闭环, 防"豁免跳窗不放行"(`tool_safety_checker.py:240-272`)。

### 1.5 信任的撤销

`DELETE /sessions/{id}/trust/{tool_name}?path=xxx`:
- path 传入 → 精确删 (session_id, tool_name, path) 该路径行;
- path 为空 → 删工具级通配行(path IS NULL);
- 无匹配 → 404(`sessions.py:108-120`, `storage.py:579-591`)。

## 二、信任处理的前后端的流程链条的问题

### 2.1 全链路总览

```
[后端] safety_gate.check_safety_and_confirm
   │  ① trust.resolve_skip(会话信任预查)
   │  ② tool_safety_checker.check_before_execute(skip_confirmation)
   │        ├─ blocked → error 事件(防拦截)
   │        ├─ requires_confirmation → ③ hitl_gateway.hitl_confirm
   │        │      ├─ paused 事件(trust_path/auto_confirm/confirm_timeout/backend_timeout)
   │        │      ├─ wait_for_confirmation_result(等前端裁决)
   │        │      └─ 单点 resolve_confirmation 收口
   │        └─ 豁免/safe → 兜底 sandbox 汇合 + grant_temp_auth
   │  ④ resolve_confirmation(confirm_id, confirmed, trust_session)
   │      └─ confirmed+trust_session → save_session_trust → insert_session_trust
[前端] SSE paused 帧
   ├─ sseParser 解析(authorization_required 事件)
   ├─ useAuthorization 监听 → AuthorizationModal 弹窗
   ├─ 用户点"允许"/勾"信任此操作" → confirm API(trust_session)
   ├─ 成功 → 派发 omni-trust-changed 事件 → TrustPanel 自动刷新
   └─ TrustPanel 查询/撤销(GET/DELETE /sessions/{id}/trust)
```

### 2.2 链条各环节的问题点(实证问题清单)

**问题1: bypass 自动确认不产生信任 → 信任列表恒空(设计定案, 非 bug)**
- 完整链条与 v1.5 定案历史见 1.3 引文块(v0.2 回答老陈的核心问题)。
- 要点: 前端强制 `trustSession=false`(`index.tsx:129-133` 倒计时代发、`:158` 手动确认两路皆强制), 后端 `hitl_confirmation.py:187` 永不触发落库, bypass 分支仅 `grant_temp_auth` 不落表。
- **预期管理**: 信任列表只在 `enabled:true` + 真 HITL 勾选后增生; bypass 期间不产生任何信任是正确行为。

**问题2(新增实证): 落库/查询路径提取不对称 → 非文件工具路径级信任永不生效**
- **落库侧** `hitl_gateway._resolve_trust_path`(`hitl_gateway.py:29-40`):
  1. 先调 `extract_trust_path`(仅 FILE_OPERATION_TOOLS/窗口工具提路径);
  2. 提取不到时**回落扫描** 6 键 `("path","file_path","source_path","dest_path","target","dir_path")` —— 对**任意工具**只要参数含这 6 键之一即返回该值(`hitl_gateway.py:36`)。
- **查询侧** `trust.resolve_skip` → `extract_trust_path` → `_parse_paths`(`trust.py:31-59`): **仅** `FILE_OPERATION_TOOLS` 内工具或窗口工具解析路径, **无回落扫描**; 其他工具一律返回 `None`。
- **交锋结果**:
  - `registry_write`/`registry_delete`: schema 参数名恰为 `path`(`win_registry_schema.py:34/59/87`)。若真 HITL 勾选信任, 落库 path=`"HKCU\Software\X"`(经回落), 但查询侧 `_parse_paths` 返回空集 → `check_session_trust(conn, sid, tool, None)` 只匹配 `path IS NULL` 工具级通配行 → **该路径行永远不会命中**, 信任白落库永不生效;
  - `execute_sql`: schema 参数 **path**(`dataanalysis_schema.py:37-49`)、`needs_confirmation` 置位(`dataanalysis_register.py:135`)。同病: 落库非空 path(spec.path 经回落), 查询侧 execute_sql 不在 FILE_OPERATION_TOOLS → extract None → 只查通配行 → **路径级信任永不生效**, 每次都重复弹窗;
  - shell 类(参数 command/cwd 无 6 键)不受影响 → 无 path 落库, 工具级通配生效, 正常。
- **影响**: 非文件类工具(registry/execute_sql 等)**路径级信任形同虚设**; 即使切回 `enabled:true` 真 HITL, 勾选信任后每次执行仍会重复弹确认。且查询侧走 `tool_name` + `path` 双键, 落库侧走回落键, **命名约定不一致**(查询认 PARAM_ALIASES 规范名, 落库认原始键名)。

**问题3(新增实证): `_norm_trust_path` 用文件系统 `Path.resolve()` 处理注册表键路径 → 垃圾绝对路径入库**
- `trust_db.py:17-24`: `_norm_trust_path` 对任意 path 做 `str(Path(path).resolve())`(文件系统绝对化)。
- 实测(`E:\Appsw\python31311\python.exe`): `Path(r"HKCU\Software\MyApp").resolve()` → `F:\OmniAgentAs-repair\HKCU\Software\MyApp`(注册表键被当**项目目录下相对文件路径**解析成垃圾路径)。
- 组合问题2后: registry 工具若真 HITL 勾选信任, **落库的是臆造的 `F:\...\HKCU\Software\MyApp` 垃圾路径**; 即便查询侧修复统一, 该路径也永远匹配不上真实注册表键 `HKCU\Software\MyApp`。
- **建议**: registry 类工具应排除出文件路径信任域(单独按键路径处理或强制工具级通配但限高危审批), `_norm_trust_path` 不应机敏把非文件路径当相对路径 resolve 入库。

**问题4(新增实证): 信任豁免只跳 HITL 确认, 不跳沙箱"未完成有效验证"裁决 → 可能二次弹窗**
- 信任豁免分支返回 `SafetyResult(..., sandbox_required=_needs)`, **`auto_confirm` 未设置(默认 False)**(`tool_safety_checker.py:188-194` + `safety_result.py:27`);
- 插入点③ `run_sandbox_gate` 缺省 `main_confirmed=False`(`safety_gate.py:168`);
- `sandbox_resolve` 中 `pre.needs_ruling and safety_result.auto_confirm` → trust 豁免时 auto_confirm=False → **不直通**, 落入"needs_ruling → 转 HITL 用户裁决"分支(`sandbox_gate.py:88-113`);
- 即: 用户已信任的 destructive 级工具(delete/copy/move 等, `sandbox_required=True`), 若沙箱**未完成有效验证**(源不存在/预检超上限/环境性失败/操作类型不支持等, `executor.py 规则2/4/6/守卫①/F-B扫描`), 仍会**再弹一次 HITL**, 与"会话已信任该工具"豁免语义矛盾。
- **边界说明**: 预检 `passed`(正常影子副本预演/registry 静态分析)时仍直通不弹; 二次弹窗仅发生在 needs_ruling 分支。但此路径代码确凿存在, 需决策: 信任豁免时 needs_ruling 是否应视为"已信任按 bypass 语义直放"(安全隐患)vs"保持裁决"(体验矛盾)。

**问题5: bypass 的临时授权 vs 长期信任边界**
- bypass 分支 `grant_temp_auth` 是**任务级临时授权**(仅 auth_path, 不落信任表, `safety_gate.py:106-110`);
- 真 HITL 确认后也"仅凭 auth_path 授权, 不设 trust_session 门"(`safety_gate.py:142-149`);
- 即: 普通确认不落库, **只有勾选"信任此操作"才落库**。该边界清晰, 但需注意前端勾选状态在后端无直接印证(trust_session 由前端报, 靠前端强制 bypass=false 兜底)。

**问题6: path=NULL 工具级通配的豁免风险**
- 无路径参数工具(窗口工具等)信任落库 path=NULL → 后续该工具**全部调用免确认**;
- 注意: registry 工具**不会**落通配行——因为 schema 参数名恰为 `path`(问题2/3), 反而落垃圾路径行; 真正无路径的工具(shell/execute_sql 之外的)才落通配。
- 建议核查: 工具级通配是否应仅限低危工具, 高危(如 registrywrite/registrydelete)是否应限制禁止进入工具级通配。

**问题7: 前缀递归豁免的"父目录信任"放大面**
- 信任根为目标的**祖先目录**即可豁免 → 信任 `D:\work` 则 `D:\work\任意子目录` 全部免确认;
- 当前是设计意图(与 temp_auth recursive 语义对齐), 但 UI 文案仅提示"含子目录", 用户可能低估范围。撤销需逐路径精确删。

**问题8: resolve_skip 依赖 task→session 反查, 查不到安全回落**
- `get_session_id_by_task` 需 chat_tasks 已建行; 反查失败/异常 → resolve_skip 返回 False → 不豁免(走确认/直放), 属安全保守, 但**信任失效是静默的**(仅 debug 日志)。

**问题9: 豁免只跳确认不跳危险防护(设计正确, 消费侧需持续守着)**
- `skip_confirmation` 传入后 `_check_known_risks` 仍全量跑, 系统禁区/路径越权/写保护/delete R6 均拦截;
- 唯一注意点: 受保护区域/白名单外写入豁免时返回 `requires_confirmation=False + auth_path`, 调用方必须补 `grant_temp_auth` 闭环, 否则工具内部 `validate_path` 拦截致执行失败 —— 三处汇合点已统一收口(`safety_gate.py:160-171`)。

**问题10: 前后端字段契约的双份解析(维护同步成本, 非当下 bug)**
- `auto_confirm` 在前端有两份解析: `useAuthorization.ts:72-76` 与 `sseParser.ts:840`(normalizeBoolean);
- 2026-09-03 已修"false 误判", 且已核 normalizeBoolean 两侧语义一致、业务函数不同但无实际漂移; 剩余风险为后续改动需两侧同步。**v0.2 复核: 当前无漂移, 列为维护关注点而非 bug**。

### 2.3 前端协同/呈现缺陷(v0.3 补充)

> 前述问题1~10 的**根因均在后端**(落库/查询不对称、信任路径提取、沙箱裁决), 前端无法自行修复(收到的 trust_path 即后端计算值)。但核查前端全链路(`useAuthorization.ts` / `AuthorizationModal/index.tsx` / `TrustPanel.tsx` / `task.api.ts`)后发现 **3 处前端自身的协同/呈现缺陷**:

**前端缺陷①(最重要, 老陈困惑的人因来源): bypass 弹窗仍显示可勾选的"信任此操作", 却静默失效无提示**
- `AuthorizationModal/index.tsx:296-310`: 勾选框始终渲染、可勾选(仅 submitting 禁用);
- `:154-160`(handleConfirm): 对 `isBypass` 强制 `trustSession=false`;
- **无任何期间反馈**: 用户看到可勾选勾选框 → 勾选 → 点允许 → 静默丢弃。`isBypass` 前端已知(`:108`), 却不隐藏/禁用勾选框、不提示"自动确认模式不记录信任"。
- **影响**: 正是老陈"记着自动确认会进信任列表、列表却恒空"的 UI 误导来源——后端设计正确, 前端未同步呈现语义, 属前端 UX/逻辑缺陷。
- **建议**: bypass 模式下禁用勾选框并展示说明文案(或隐藏), 消除"可勾必失效"的误导。

**前端缺陷②: `trust_path` 无校验原样展示(垃圾路径直出)**
- `AuthorizationModal/index.tsx:301-303`: tooltip 显示 `{toolName} › {trustPath}，含子目录`;
- `TrustPanel.tsx:178`: 显示 `{path ?? '全局'}`、行键 `${toolName}|${path}`、撤销 `revokeTrust(sessionId, toolName, path)` 原样回传(`task.api.ts:227-238`);
- **影响**: 若后端落库了垃圾路径(问题3 的 `F:\..\HKCU\Software\MyApp`), 面板会把臆造路径原样展示给用户; 前端零校验、零过滤、零防御(显示的是后端红字垃圾数据)。
- **建议**: 前端对 path 增加基本形态校验(如窗口目标/注册表键不按文件路径展示), 或后端修复后由前端透传即可。

**前端缺陷③: "含子目录"文案对非文件工具语义错误**
- `AuthorizationModal/index.tsx:303`: tooltip 统一写 `，含子目录` —— 对 `registry_write` 等注册表键工具, "子目录"是文件系统语义, 注册表键层级 ≠ 文件目录树, 纯属误导;
- **影响**: 用户对注册表键信任范围(键及子键?)产生错误预期, 与后端前缀递归匹配(仅文件路径语义)也不对应。
- **建议**: 按工具域区分文案: 文件工具显示"含子目录", 非文件工具不显示或改为"该工具/该键"。

### 2.4 结论

机制主线清晰且防守到位(bypass 防污染 / 危险防护与开关解耦 / 豁免只跳确认 / tool+path 精确化)。v0.2/v0.3 基于逐行实证, 确认为如下口径:

**严重设计/实施问题: 2 个(根因全在后端)**
1. **信任域对"非文件路径工具"定义错乱**(问题2+问题3 同一根因): 落库侧 `hitl_gateway.py:36` 有 6 键回落扫描、查询侧 `trust.py:31-59` 无回落扫描, 不对称 → registry_write/registry_delete/execute_sql 路径级信任永不生效; 叠加 `_norm_trust_path` 用 `Path.resolve()` 把注册表键臆造成垃圾绝对路径入库(实测 `F:\...\HKCU\Software\MyApp`)。实施错误(落库/查询应共用提取函数) + 设计缺陷(未区分文件路径/逻辑路径/无路径三个信任域)。
2. **信任豁免与沙箱 needs_ruling 不自洽**(问题4): `tool_safety_checker.py:188-194` 豁免时不设 auto_confirm(默认 False), `safety_gate.py:168` 缺省 main_confirmed=False → `sandbox_gate.py:88` 不直通 → needs_ruling 仍二次弹 HITL。需显式决策而非留白。

**前端协同/呈现缺陷: 3 处**(v0.3, 非根因, 但直接造成用户误导)
- ① bypass 勾选框静默失效无提示(老陈困惑人因) ② trust_path 垃圾路径原样展示 ③ "含子目录"对注册表键文案错误。

**明确非问题(定案/合理设计)**: 问题1(bypass 不产生信任=v1.5 正确定案)、问题5/8/9(临时授权边界、反查失败安全回落、豁免不跳危险防护=保守正确)、问题10(双份解析复核无漂移=维护关注)。

**建议优先级(供决策)**:
- P0: 统一落库/查询路径提取(删除 `hitl_gateway._resolve_trust_path` 回落扫描或查询侧等价补齐), 并让 `_norm_trust_path` 对非文件工具不做文件系统 resolve;
- P1: 明确信任豁免下的 needs_ruling 处置(直放 vs 保持裁决); 前端 bypass 勾选框禁用+文案提示、trust_path 校验展示、非文件工具"含子目录"文案修正;
- P2: registry/execute_sql 等逻辑路径工具的信任域专门设计(当前"工具+文件路径"模型不适用)。
