## 二、P1：bypass 计时归 0 弹窗不自动消失

### 2.1 现象
弹窗标题"将自动确认（安全开关已绕开）"，倒计时正常走完到 0，但弹窗卡住不自动关闭。

### 2.2 链路分析
- 前端 `AuthorizationModal` 倒计时到 0 走 L115-126 effect：
  ```js
  autoHandledRef.current = request.confirmId;
  setSubmitting(true);
  onConfirmRef.current(true, false);  // → handleAuthorizationConfirm(true, false)
  ```
- `useAuthorization.handleAuthorizationConfirm`（useAuthorization.ts:81-113）：
  ```js
  await taskControlApi.confirm(cur.confirmId, true, false); // ← await 挂起
  setAuthorizationPending(null);  // ← 不执行 → 弹窗滞留
  ```
- 后端 `confirm_stream_endpoint`（chat_routes.py:70-85）→ `resolve_confirmation` → 唤醒 `wait_for_confirmation_result` 的 `asyncio.wait_for(future)`。

### 2.3 病根病因
**前端 confirm 请求的 await 挂起，导致 `setAuthorizationPending(null)` 永不执行，弹窗永久滞留。**

竞态拆解：
1. bypass 模式下后端 `_wait_confirm(confirm_id, timeout=10)`（action_handler.py:387）等前端确认消息；前端 confirm HTTP 响应被这次异步等待拖住。
2. 若后端 S1 窗口（10s）先超时，`wait_for_confirmation_result` 的 finally（hitl_confirmation.py:141-143）已把 confirm_id 从 pending dict pop；前端 confirm 才到 → `resolve_confirmation` 返回 `{"success": False}`（HTTP 仍 200）。
   - HTTP 200 不会触发 axios 抛错 → 不会进 catch → 本应 `setAuthorizationPending(null)`。
   - **但若 confirm 请求 HTTP 层迟迟不返回**（后端 `resolve` 里 `await db.atxn` 落库或 asyncio loop 被阻塞），前端 await 一直挂着 → `setAuthorizationPending(null)` 不执行 → 弹窗滞留。
3. 前端没有对 confirm 请求设置**超时兜底**，一旦挂起即无自律复位。

### 2.4 修复方向
- 前端 `handleAuthorizationConfirm` 对 `taskControlApi.confirm` 增加**超时兜底**（如 Promise.race + 超时回退），超时也强制 `setAuthorizationPending(null)`（一次 confirm_id 只收口一次，防双发）。
- 后端 `resolve_confirmation` 在 `{"success": False}`（confirm_id 不在/已处理）时保证 HTTP 语义明确，避免前端误判成功。
- 前端 bypass 自触发时，`autoHandledRef` 已收口，确保并发安全。

## 三、P2：thought 等待绿圈只第一次出现

### 3.1 现象
即 `waiting-cursor`（绿色缺口圆弧）只在第一个 thought 之前出现，流水线里一旦出现过工具段/观察段，绿圈就再也不出现。

### 3.2 链路分析
`PipelineRenderer.tsx:171-181` waiting 判定：
```js
const waiting =
  taskActive &&
  (!lastSeg ||
    (lastSeg.kind !== 'thinking' &&
      lastSeg.kind !== 'text' &&
      lastSeg.kind !== 'tool' &&   // 曾在 Bug-9 排除 tool
      lastSeg.kind !== 'obs' &&    // 曾在 D2-07 排除 obs
      lastSeg.kind !== 'final' &&
      lastSeg.kind !== 'error'));
```

### 3.3 病根病因
**waiting 判定把 `tool` / `obs` 段永久排除，导致 `lastSeg` 一旦是 tool/obs 就永远不是 thinking/text，`waiting` 恒为 false，绿圈从"每轮 thought 前复现"退化为"只在首 thought 前出现"。**
- 为"工具等待动画唯一承载"排除 tool（Bug-9）、为"防绿圈残留"排除 obs（D2-07），但未考虑"工具执行后下一轮 thought 前需重新出现绿圈"的复现语义。
- 属对既有功能（绿圈复现）的**退化**。

### 3.4 修复方向
- waiting 判定应改为"**末段非终态且无待渲染内容**"语义，而非简单排除 tool/obs。
- 建议：当末段为 tool/obs 时，**若其结果为已到位（hasResult）或已显示子行**，则不显示绿圈（避免双动画）；反之工具仍等待时仍承载等待动画，不应一遇 tool/obs 就永久灭圈。
- 需要真实 E2E 确认"每轮 thought 前应复现绿圈"的期望，避免修复过度。

## 四、P3 / P4 / P5：工具卡等待动画与超时误报

### 4.1 现象
- **P3**：结果已出现，等待图标仍在转。
- **P4**：结果已出现，仍显示"工具执行超时未返回结果，请重试或查看日志"。
- **P5**：工具执行成功，仍显示同一"工具执行超时未返回结果"提示。

用户实测日志：
```
🔧 并行 2 个工具 [readtext, readtext]
工具执行超时未返回结果，请重试或查看日志
🔧 并行 2 个工具 [readtext, readtext]
├─ readtext 参数：{"path":"...sandbox_gate.py"} ▼
│ ✔ 读取文件...sandbox_gate.py
└─ readtext 参数：{"path":"...temp_au"} ▼
✔ 读取文件...temp_au
```

### 4.2 链路分析
`ToolCallLine.tsx`
- `hasResult`（L74-79）：observations 的 tool_result 数组>0 或非空字符串。
- `timedOut`（L82-91）：无结果且 tools>0 时 30s 后置 true。
- 渲染分支（L167-206）：`!hasResult && tools>0 && timedOut` → 超时提示；`hasResult && tools>0` → 子行。
- 两分支互斥（一个 hasResult true/false）。

### 4.3 病根病因（applog 实证 2026-09-03 11:17:12-11:17:13 task-4c535）

**applog 证据**：
- `11:17:13 [action_handler] 分组并行执行: tools=['readtext','readtext']` → 2 组单工具，`tool_executor` 各 0.01s 成功，`工具执行完成耗时 0.02s`，`observation step=6` 已 emit（seq=216）。
- 其后 `AgentStatus.EXECUTING→THINKING`，`[LLM] 调用#7` 开始；**工具已成功但 UI 仍报"超时/转圈"**，与用户"结果显示后第一个还存在且转圈后报错误"吻合。

**病根 1 — 重复渲染**：`🔧 并行 2 个工具` 出现两次。applog 的 SSE 侧出现 `seq=214/215/216` 重复发送（同一 task_id 两次 `stream_reader seq=XXX`，且 `step_emitter thought-start/thought step=6` 重复 emit），`buildSegments` 若按 `steps` 数组直接映射 `action` 段，同一 `step=6` 的 action 会被渲染两次；一次命中 `!hasResult && timedOut`（空 observations），一次命中 `hasResult`（有 observations），故"超时提示"与"子行"并存。

**病根 2 — 等待/超时判定与真实执行时序脱节**：`ToolCallLine.tsx` 的 `timedOut` 为前端 30s 计时器，与后端真实耗时（0.02s）无关；`hasResult` 为全局 `some`，并行工具中任一结果到达即 true，但**首个 ToolCallLine 实例的 observations 为空数组**（分批到达/重复实例），仍走超时分支。前端"等待橙齿轮"由 `ToolCallLine` 与 `PipelineRenderer waiting` 双轨驱动，任一轨残留即"结果已出仍转圈"。

### 4.4 修复方向
- 统一"工具卡"渲染为**单实例**，杜绝 action 段重复（核对 buildSegments）。
- hasResult 与"该工具子行"按**工具索引**精确配对，非全局 some。
- timedOut 在 hasResult 变 true 时**幂等清幂**，且超时提示与子行严格互斥。

## 五、P6：task info 徽标卡在"失败"没改回"正在执行"

### 5.1 现象
工具执行时 task info 徽标显示"失败"，但后端任务一直在正常跑，状态未改回"正在执行"。

### 5.2 链路分析（纯前端）
- 徽标权威派生：`useTaskInfo.ts` useMemo `badge`，从 steps/frames/receiving/detail/liveErrorText 推导。
- `badge='failed'` 来源（useTaskInfo.ts:186-191）：`liveErrorText && badge 非终态 → badge='failed'`。
- `liveErrorText` 来源：ChatPage.tsx:37 `onError` → sseParser.ts:526 `type=error` 事件。
- 后端可恢复工具错误：react_cycle.py:176 `_RECOVERABLE_ERRORS = {"user_rejected","blocked","timeout"}`，对这些 **不置终态、主循环继续**（"拒绝≠失败…让 LLM 换工具"）。
- **前端没有 failed→running 的回推路径**：useTaskInfo.ts:164-172 仅 paused 回推 running；:195-196 仅 idle→running。

### 5.3 病根病因
**前端把"单工具可恢复错误（user_rejected/blocked/timeout）"经 `liveErrorText` 提升为"任务级 failed"，且 useTaskInfo 无 failed→running 复位逻辑；liveErrorText 运行中永不清空（仅在发新消息/切 session 置 null）。**
- 后端任务继续跑（符合用户所见），但前端徽标被锁定在 failed。

### 5.4 修复方向
- 对可恢复工具 error 的 liveErrorText **不提升**为任务级 failed。
- 或 useTaskInfo 增加：可恢复 error 后，出现后续 thought/action/observation 推进时为 failed 增加回推 running（与 paused 同理）。

## 六、P7：后端重试消息未推给前端

### 6.1 现象
后端日志有 `base_service.py:417 [Retry][L1] 重试 1/3, 等待3秒, 错误: [ReadTimeout]`，但前端 UI 未看到"LLM 请求重试"提示。

### 6.2 链路分析（代码层面已全链路通）
- 后端产出：base_service.py:420-423 `yield StreamChunk(retry_notice=..., retry_attempt=..., retry_total=...)`。
- llm_stream 消费：llm_stream.py:165-173 `isinstance(chunk, StreamChunk) and chunk.retry_notice → yield ("meta", {"type":"retrying", ...})`。
- react_cycle 转 MetaStep：react_cycle.py:439-450 `type=_m["type"]`（"retrying"）。
- SSE 发送：sse_formatter 转 `data: {"type":"retrying",...}`。
- 前端 sseParser.ts:788-867 `case 'retrying'` → step 入 executionSteps + `onRetry` 回调。前端确实消费并渲染。

### 6.3 病根病因（applog 实证 2026-09-03 11:17-11:27 task-4c535）

**applog 完整时序**：
```
11:17:13 调用#6 tool_calls=['readtext','readtext'] → 分组并行 0.02s 成功，observation 已发
11:17:13 调用#7 开始
11:18:13 stream_reader cond.wait 60s 超时（SSE 空转）
11:18:17 [TaskControl] 取消任务 task-4c535（用户取消，HTTP 连接强制关闭）
11:19:34 [Retry][L1] 重试 1/3 ReadTimeout（无对应 [StepEmit] retrying）
11:22:17 [Retry][L1] 重试 2/3 ReadTimeout（无对应 [StepEmit] retrying）
11:23:33 [Retry][L2] → [StepEmit] retrying step=7（仅 L2 有 StepEmit，L1 缺失）
11:23:33 [CancelCheck] → cancelled 步骤，11:27:28 FAILED
```

**病根**：
- **代码链路本应通**：`base_service.py:417-423 yield StreamChunk(retry_notice)` → `llm_stream.py:165-173 yield ("meta", type=retrying)` → `react_cycle.py:439-450 emit MetaStep(retrying)` → SSE → `sseParser.ts retrying` → UI。本次 applog 中 **L2 重试确实走通**（11:23:33 有 `StepEmit retrying`）。
- **L1 重试未落事件**：11:19:34 与 11:22:17 两次 L1 ReadTimeout 仅有 `base_service [Retry][L1]` 日志，**无 `StepEmit retrying`**，说明 `request_stream` 的 `yield StreamChunk(retry_notice)` 未被 `call_llm_stream` 消费并转 `("meta",...)` 到 `react_cycle`。**触发时序在任务取消后**（11:18:17 已 cancel，`_cancelled`/`HTTP 连接关闭`），`request_stream` 的重试循环仍在 `await asyncio.sleep(wait_time)` 后继续，但上游 `call_llm_stream → call_llm_with_fallback → react_cycle` 的 `async for` 消费链已因取消/异常路径不再拉取该 `yield`，导致重试通知**产出但未入 `event_log`，SSE 读侧（`stream_reader` 60s 空转）自然收不到**。
- **用户观感**："工具已成功（11:17:13 0.02s）却看不到重试" — 实为 **LLM 调用#7 的重试**（非工具重试），发生在工具成功之后、取消之后，故与工具卡"超时"视觉叠加。

### 6.4 修复方向
- **L1 重试通知必入事件流**：`base_service.py` 的 `yield StreamChunk(retry_notice)` 改为**同步入 `event_log`/直接 `emit` 或经 `buffer` 旁路**，不依赖 `request_stream` 调用方的 `async for` 拉取；或在 `call_llm_stream` 侧对 `retry_notice` 的 `yield ("meta",...)` 加**取消/异常兜底**，保证即使上游已取消也能落一条 `retrying` 事件。
- 前端 `retrying` 已有渲染位（TaskInfoBar 位4 / processEvents / 流水线），链路通后即刻可见，无需新增位。
- 同步修正 P3/P4/P5 的"超时"误报：工具卡超时仅对 `EXECUTING` 且无 observation 时计时，LLM 重试超时不混入工具卡（当前"工具执行超时"文案易与 LLM ReadTimeout 混淆，需分流展示）。

## 十二、额外修改复核（小沈补充发现） — 小沈-2026-09-03

> 以下为复核 44case 报告修改落地情况时，额外发现的代码问题与潜在退化。

### 12.1 BUG-01 修复未真正落地（RightViewer userScrolledUpRef 误重置）

- **44case 报告说**：移除 `liveSteps.length` 依赖，避免 liveSteps 增长时重新挂载监听器并重置 userScrolledUpRef
- **实际代码**：`RightViewer.tsx:169` effect 依赖仍是 `[isCurrentLive, liveSteps.length, findScrollContainer]`
- **且** `findScrollContainer:136` 的 useCallback 依赖也改成了 `[liveSteps.length]`
- **问题**：liveSteps 每次增长 → findScrollContainer 重建 → effect 重跑 → scroll 监听重挂载 + userScrolledUpRef 可能被重置
- **裁定**：⚠️ **BUG-01 修复未落地或被后续修改覆盖**，liveSteps.length 仍在依赖链中

### 12.2 BUG-04 修复引入 scroll 监听频繁重挂载

- **44case 报告说**：移除 scrollContainerRef 缓存
- **实际代码**：`RightViewer.tsx:121-136` 确实移除了缓存，但 findScrollContainer 依赖 `[liveSteps.length]`
- **问题**：liveSteps 每次增长 → findScrollContainer 重建 → effect:137 重跑 → scroll 监听 + ResizeObserver 重挂载
- **影响**：流式过程中每 chunk 到达都重挂载监听，虽然功能正确但性能有隐患（频繁 add/removeEventListener）
- **裁定**：⚠️ **性能退化**，应将 findScrollContainer 依赖改 `[]`（getComputedStyle 不需要 liveSteps）

### 12.3 BUG-16 CollapsibleText 展开状态跨消息残留

- **44case 报告说**：移除 `useEffect(() => setExpanded(false), [text])` 防打断用户展开
- **实际代码**：`CollapsibleText.tsx:33` 确实移除了该 useEffect
- **问题**：移除后 expanded 永不重置，用户展开消息 A → 切到消息 B（组件不卸载，同一实例）→ 消息 B 仍显示展开态
- **裁定**：⚠️ **潜在状态残留**，应按 message id 或 text 首段 hash 重置 expanded

### 12.4 BUG-25 MutationObserver 观察范围过宽

- **实际代码**：`useChatScroll.ts:76-86` `mo.observe(document.body, { childList: true, subtree: true })`
- **问题**：观察整个 document.body 子树，任何 DOM 变化（打字机逐字、Ant Design 弹窗、Tooltip 等）都触发回调
- **影响**：回调频繁触发，虽然每次只检查 `messagesEndRef.current?.parentElement` 但仍有性能开销
- **裁定**：⚠️ **性能隐患**，应缩小观察到消息容器的父级节点

### 12.5 BUG-29 乐观清空无失败回补（发送失败输入永久丢失）

- **实际代码**：`ChatInput.tsx:53-55` `setDraft(''); setLinked(false); onSend(content, ...)`
- **父级**：`ChatPage.tsx:115-121` `setLiveErrorText(null); void chatSend.handleSend(content, mode);`
- **问题**：onSend 是 fire-and-forget（void），失败时只设 liveErrorText，不回补 draft
- **影响**：网络错误/后端 500 时用户输入永久丢失，需重新输入
- **裁定**：⚠️ **真实退化**，应改 onSend 为 async，失败时回填 draft

### 12.6 RightViewer isCurrentLive 判定可能致历史拉取延迟

- **实际代码**：`RightViewer.tsx:107-110` `isCurrentLive = activeTaskId != null && activeTaskId === serverTaskId && (receiving || liveBadge === 'running' || liveBadge === 'paused')`
- **问题**：即使 receiving=false（SSE 断连），只要 badge 是 running/paused 就认为是 live → 不拉历史
- **场景**：任务已结束但 final 未到达、badge 仍为 running → isCurrentLive=true → 历史拉取 effect:172 不执行 → 用户看不到结果
- **裁定**：⚠️ **潜在卡死**，badge 应在 final 到达时立即转 completed/failed，但若 final 丢失则永久卡 live

### 12.7 P3/P4/P5 与第八章 applog 实证的代码层印证

- 第八章钉死"重复 seq + 重复 thought-start/thought 致同一 action 渲染两次"
- **代码层根因**：`PipelineRenderer.tsx:275` key=`seg.action.step ?? i`——重复 seq 的 action 段 action.step 相同 → key 相同 → React 复用实例 → 两个 ToolCallLine 实例同时存在（一个空 observations 走超时，一个有 observations 走子行）
- **修复方向**：buildSegments 应按 seq 去重，或 key 加 seq 后缀防碰撞
