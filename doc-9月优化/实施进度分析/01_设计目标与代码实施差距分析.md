## 一、最初的设计目标和计划

### 1.1 系统设计方案（v1.0, 2026-02-15）核心目标

**项目愿景**: 构建企业级、安全、可扩展的AI Agent操作系统，让AI Agent从"玩具"变成"生产工具"。

| 目标维度 | 原设计目标 | 实际技术选型 |
|---------|-----------|-------------|
| **安全性** | 企业级安全：沙箱、权限、审计 | ✅ 安全层已实现（safety/目录） |
| **可扩展性** | 插件化架构，动态加载工具 | ⚠️ 部分实现（registry.py存在，plugin_loader缺失） |
| **多用户** | 多租户RBAC权限系统 | ❌ 未实现（单机单用户场景合理排除） |
| **多模型** | 多模型智能路由 + 故障转移 | ⚠️ client_sdk.py存在，SmartModelRouter未实现 |
| **多模态** | 图像+语音+文本支持 | ✅ 已有readmedia工具 |
| **客户端** | Web+桌面+移动端三端 | ⚠️ Web(React)已实现，桌面(非Tauri/Electron)未做 |
| **可观测性** | Prometheus+Grafana监控 + ELK日志 | ⚠️ 监控目录存在，但未接入Prometheus/Grafana |

### 1.4 Agent 2.0设计目标（2026-05-22）

**语义路由范式（推荐C）**:
- 用Function Calling替代CRSS正则匹配
- 返回 categories + intent + confidence + reasoning
- Candidates预加载机制（基于confidence决定加载深度）

**安全四层体系**:
```
Layer 1: 语义路由过滤
Layer 2: 工具安全级别(ToolSafetyLevel四级)
Layer 3: HITL人工确认
Layer 4: ToolObserver异常检测+审计
```

### 1.5 旋智体设计目标（2026-05-30）

**核心概念**: 螺旋演进 + 智能决策 + 体系化积累

**三层架构**:
- L1: 结果持久化（对话历史、步骤记录、用量更新）
- L2: 意图分类 + 经验库管理（Agent编排层）
- L3: ReAct执行（薄转发器）

**两Agent模式**:
- univ-task-agent（主Agent，薄转发器）
- read-task-agent（子Agent，独立Session+只读工具）

**三阶段路线图**:
- Phase 1: 基础task能力（单Agent+内置tool）
- Phase 2: ArtTool合成（即兴代码→经验库→自动合成原子工具）
- Phase 3: FlowTool合成（编排模式→经验库→自动合成工作流）

## 三、设计与代码实施差距分析

### 3.1 架构层面差距

| 差距项 | 原始设计 | 当前实现 | 影响评估 |
|--------|---------|---------|---------|
| **微服务拆分** | Gateway/Agent-core/Tool-service/Model-router/Task-scheduler 5个独立服务 | 单体架构，全部在backend/app/下 | 🔴 高 - 扩展性受限 |
| **数据库选型** | PostgreSQL + Redis + MinIO + Elasticsearch | SQLite(单文件) | 🟡 中 - 单机场景够用，但缺乏分布式能力 |
| **缓存层** | Redis(7+) | 无Redis，使用TTLCache内存缓存 | 🟡 中 - 单进程可用，多进程/分布式场景不足 |
| **任务队列** | Celery + Redis | 无Celery，异步用asyncio | 🟡 中 - 单机场景够用 |
| **前端框架** | Electron+React(桌面) / Flutter(移动) | React+Vite(Web) | 🟡 中 - 缺少桌面原生能力和移动端 |
| **容器化** | Docker+Docker Compose | 无Docker配置 | 🟡 中 - 部署灵活性受限 |
| **多租户** | RBAC权限系统 | 无多租户 | 🔴 高 - 企业级场景无法支持 |
