## 一、问题

北京老陈发现：左侧任务列表里新任务/当前任务的回复区（灰底 #fafafa + 2px 左边线的框），在任务结束后立即显示了完整的回复正文（LLM最终答案），并非"空白"。

此前分析结论"实时新任务 final.response 为空则左侧留空"与页面实际表现不符。

核心疑问：**左侧任务回复区的数据究竟是什么？从哪来？什么时候写入？**

## 二、分析结论

### 2.1 回复区显示的字段

左侧任务项回复区（`TaskListPanel.tsx:246-280`）只显示 **`t.response`** 一项数据：

```tsx
{t.response && (
  <div className="task-text-block" style={{ backgroundColor: '#fafafa', borderLeft: '2px solid #d9d9d9' }}>
    <CollapsibleText text={t.response} />
    <button className="task-copy-btn" onClick={() => handleCopy(t.response!, '回复')} />
  </div>
)}
```

`{t.response && ...}` —— 有值才渲染，空则整个灰底框不出现。

### 2.2 实际生效的两条写入链路

| 链路 | 触发时机 | 写入内容 | 代码位置 |
|------|----------|----------|----------|
| **R3（即时写）** | `final` 帧到达 → `isReceiving=false` | `finalStep.response`（长条终态文本：失败/取消/return_direct） | `ChatPage.tsx:112-133` |
| **B16（DB刷新）** | `final_stats` 帧到达 = DB已落库信号 | `stream_state.current_content`（completed时是chunk累积的完整正文，failed/cancelled时是终态文案） | `RightViewer.tsx:424-429` → `refreshTasks()` |

### 2.3 三种场景下回复区的实际显示

| 场景 | R3写入 | B16写入 | 回复区最终显示 |
|------|--------|---------|---------------|
| completed短条（正常完成） | final.response=''→不写 | final_stats→DB完整正文 | **DB完整正文** |
| 长条终态（failed/cancelled/return_direct） | final.response=终态文本→立即写入 | final_stats→DB终态文案覆盖 | **DB终态文案**（与R3内容相同） |
| 历史任务（DB加载） | 不触发 | refresh()从DB拉 | **DB完整正文/终态文案** |

**结论：回复区最终显示的始终是DB落库的`stream_state.current_content`**。completed时是chunk累积的完整正文，failed/cancelled时是终态文案本身（不是chunk累积的正文）。R3和B16写入的内容在同一种终态下一致。

### 2.4 为什么"铁命令"说左侧只用final.response

铁命令（09-12北京老陈定案）约束的是**R3即时写入路径**：
- "左侧任务response只允许由updateTaskResponse(final.response)写入"
- "严禁用DB查询/消息正文/refreshTasks全量刷新或其他任何兜底顶替"

但B16（原R4，09-11新增，09-12保留在RightViewer L424）是**DB落库后的列表刷新**，属于合规的列表更新（不是"兜底顶替实时响应"），因为触发信号是`final_stats`（DB已落库），此时读DB是准确的。

### 2.5 三个文件各自负责什么

| 文件 | 职责 | 左侧回复区负责什么 |
|------|------|-------------------|
| **ChatPage.tsx** | 主页面组件，编排整个聊天流程 | **"什么时候写"**：SSE final帧到达时，把final.response写入左侧任务 |
| **useSessionTasks.ts** | 任务列表状态管理Hook | **"怎么写"**：提供`updateTaskResponse`（实时写入）和`refresh`（从DB拉完整response）两个方法 |
| **TaskListPanel.tsx** | 左侧任务清单面板组件 | **"怎么显示"**：渲染`t.response`，有值才显示灰底框（246-280行） |

### 2.6 三个文件相关代码片段的功能说明

**ChatPage.tsx:112-133 — 左侧回复区实时写入effect**

触发条件：`isReceiving`从true翻false（SSE final帧到达）。从`executionSteps`找`type=final`的step，取其`response`调用`updateTaskResponse`写入左侧任务。仅`final.response`非空时才写（failed/cancelled/return_direct长条终态），completed正常完成的`final.response`为空，本effect不写，左侧此时空白。

**useSessionTasks.ts:70-74 — updateTaskResponse方法**

接收`taskId`和`response`两个参数，用函数式`setTasks`遍历任务列表，找到匹配的taskId就用新response替换，找不到就原样保留。纯内存操作，不涉及DB。

**useSessionTasks.ts:32-48 — refresh方法**

调用`sessionTaskApi.listTasks(sessionId)`从后端DB拉取完整任务列表（含response字段），用`setTasks`整体替换。触发时机：serverTaskId变化（新任务诞生）、final_stats到达（RightViewer L424调refreshTasks）、切会话。

**TaskListPanel.tsx:246-280 — 回复区渲染**

判断`t.response`有值才渲染灰底框（`backgroundColor: '#fafafa'` + `borderLeft: '2px solid #d9d9d9'`），内容用`CollapsibleText`截断显示，右上角复制按钮。空则整个灰底框不出现。

### 2.7 回复区数据全链路（实时任务 + 历史任务统一说明）

**数据是什么**：`t.response`，一个字符串字段。completed任务存的是所有chunk累积的完整正文（LLM全部输出），failed/cancelled任务存的是终态文案（"任务执行失败"/"用户取消"等）。

**数据从哪里来**：后端 `stream_state.current_content`（`agent_runner.py:465`）。任务执行期间每个SSE chunk事件到达就 `current_content += chunk_text` 逐条追加，跨多轮ReAct循环累积。任务结束时写入DB `chat_tasks.response`（`agent_runner.py:604-605`）。

**前端什么时候拿到**，分两种情况：

**实时任务**：completed短条 → final帧到达时 `finalStep.response=''`，R3不写，左侧空白 → final_stats帧到达（DB已落库）→ B16调 `refreshTasks()` → `useSessionTasks.refresh()` 从DB拉 `chat_tasks.response` → `setTasks` 替换 → 左侧显示完整正文。failed/cancelled长条 → final帧到达时 `finalStep.response=终态文案`，R3立即写入 → 左侧显示终态文案 → final_stats到达后B16从DB拉相同内容覆盖，显示不变。

**历史任务**：打开页面或切换会话时，`useSessionTasks.refresh()` 从DB拉取完整任务列表（含response字段），`setTasks` 整体替换，TaskListPanel渲染 `t.response`。历史任务的 `t.response` 是静态的，DB里存什么就显示什么。

**字段映射链（同名传递）**：`chat_tasks.response`（DB列名）→ `dict(r)` Python字典key → API JSON key → `SessionTaskItem.response`（`task.api.ts:82`）→ `t.response` 渲染。一路同名，无转换。

### 5.3 历史任务回复区完整数据链

**后端落库（唯一写入点）**：

`agent_runner.py:576,591,604-605`：

`chat_tasks.response` = `stream_state.current_content`

**stream_state生命周期**：

`StreamState`每任务创建一次（`stream_orchestrator.py:288: state = StreamState()`），跨所有ReAct轮次不重置。

**current_content累积逻辑**：

| 事件 | 代码位置 | 操作 |
|------|----------|------|
| chunk | `agent_runner.py:465` | `current_content += chunk_text`（追加） |
| final（短条response=''） | `agent_runner.py:456-458` | `content=''` → 保留已有累积（不覆盖） |
| final（长条response非空） | `agent_runner.py:456-458` | `current_content = content`（覆盖） |

**DB查询**：

`storage.py:788` — 读 `chat_tasks` 表的 `response` 字段：
```sql
SELECT task_id, user_input, response, status, ... FROM chat_tasks WHERE session_id=? ORDER BY id ASC
```

**前端加载**：

`useSessionTasks.refresh()` → `sessionTaskApi.listTasks()` → 后端返回含 `response` 字段的 task 列表 → `setTasks(res.tasks)` → `TaskListPanel` 渲染 `t.response`。历史任务回复区显示的就是 `chat_tasks.response` 字段的内容。

**字段映射链（同名传递）**：`chat_tasks.response`（DB列名）→ `dict(r)` Python字典key `response` → API JSON key `response` → `SessionTaskItem.response`（`task.api.ts:82`）→ `t.response` 渲染。一路同名，无转换。

### 5.4 不同终态下chat_tasks.response的实际内容

| 任务终态 | chat_tasks.response内容 | 原因 |
|----------|------------------------|------|
| completed（正常完成） | LLM所有chunk累积的**完整回复正文** | final短条response=''不覆盖，保留chunk累积 |
| failed（失败） | `"任务执行失败"` 或具体error文本 | agent_runner.py:507兜底写入 |
| cancelled（取消） | `cancel_terminal_text(cancel_source)`返回的取消文案 | agent_runner.py:553写入 |
| return_direct | `return_direct_message`（工具直接返回的消息） | final长条response=消息文本 |

### 5.5 历史任务回复区显示机制

历史任务点击时：
1. **左侧任务项的`t.response`来自`useSessionTasks.tasks`**——这是之前`refresh()`从DB拉取并缓存在state里的
2. 只有新任务完成触发`refreshTasks()`时，才会重新拉DB更新state

**历史任务回复区是静态的**——DB里存什么就显示什么，不会被R3/B16覆盖。`t.response`的值 = 任务结束那一刻`stream_state.current_content`的快照。

## 六、wait-action的分析

### 6.1 wait-action出现时机

在 thinking 阶段，如果当前任务 active 且还有后续 action，就会在 thinking 后追加一个 wait-action。

### 6.2 代码位置

🔴 漏洞1（中-高）：action-waiting 在 thinking 流式输出期间提前出现，思考光标被蓝色波纹取代
位置：PipelineRenderer.tsx:289-292 + PipelineRenderer.tsx:345

根因：

// L289-292：只要末段是thinking + taskActive 就追加 action-waiting
const lastSeg = segs[segs.length - 1];
if (lastSeg && lastSeg.kind === 'thinking' && taskActive) {
    segs.push({ kind: 'action-waiting' });
}

// L345：thinking光标判定 i === segs.length - 1
const cursor = streaming && i === lastThink && i === segs.length - 1;

当 streaming=true（thinking chunk 还在流式到达）时，taskActive = streaming || badge 为 true，thinking 是末段 → 立刻追加 action-waiting → thinking 打字光标被蓝色波纹取代。

设计文档原文（第4.3节）明确要求：
