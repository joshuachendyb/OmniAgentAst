## 一、工具执行被拒绝 — 前后端增强方案

### 1.1 问题描述

后端工具执行被拒绝时（安全拦截、确认超时、用户拒绝），后端日志可以清晰看到原因，但前端用户无法快速区分三种拒绝类型：

- **安全策略拦截**（blocked）：工具被安全检查器阻止
- **确认超时**（timeout）：HITL 确认等待超时
- **用户拒绝**（user_rejected）：用户主动拒绝执行

当前前端 `ToolCallLine` 只显示橘红灰字 "未执行：{reason}"，三种拒绝视觉上完全一样，用户需要阅读文字才能区分。

### 1.2 现状分析

#### 1.2.1 事件分类原则（北京老陈定案）

**核心原则**：按职责分离，tool 相关和 agent/LLM 相关用不同的 `type`

| type | 职责 | 场景 |
|------|------|------|
| `type="rejected"` | 与 **tool** 相关的拒绝 | 安全拦截、确认超时、用户拒绝、沙箱拦截 |
| `type="error"` | 与 **agent/LLM** 相关的错误 | LLM 调用失败、响应解析错误、Agent 内部错误、请求级错误 |

**设计优势**：
- **SRP（单一职责）**：每个 type 只负责一个层面的问题
- **语义清晰**：看到 `type` 就知道是 tool 拒绝还是 agent 错误
- **前端简单**：按 type 分流处理，不需要额外判断

#### 1.2.3 当前设计问题

```
当前设计：
type="error" + error_type="blocked"    → 安全拦截/沙箱拦截（tool 层，错用 error）
type="error" + error_type="timeout"    → 确认超时（tool 层，错用 error）
type="user_rejected"                    → 用户拒绝（tool 层，语义正确但命名不统一）
```

**问题 1**：tool 层的拒绝事件混在 `error` 通道，违反 SRP

**问题 2**：`type="user_rejected"` 和 `type="error"` 命名不统一，前端需要同时处理两个 type

**问题 3**：前端无法从 `type` 直接判断是 tool 拒绝还是 agent 错误

#### 1.2.6 reject_type 分类方案（北京老陈定案）

**方案：折中（4 种 + content 细分）**

| reject_type | 含义 | 子场景数 |
|-------------|------|---------|
| `safety` | 安全检查器拒绝 | 6 种（通过 content 区分） |
| `sandbox` | 沙箱拒绝 | 16 种（通过 content 区分） |
| `timeout` | 超时拒绝 | 1 种 |
| `user` | 用户拒绝 | 1 种 |

- **优点**：分类简洁（4 种），不丢失具体信息（content 字段携带）
- **缺点**：需要从 content 解析具体原因

**选择理由**：

1. **用户视角**：用户只需要知道"被拒绝了"，不需要知道具体是哪种安全检查拒绝的
2. **实现细节**：具体原因可以通过 `content` 字段携带（如"工具未注册"、"命令含越界写意图"等）
3. **可扩展性**：未来如果需要更细粒度，可以在 `content` 中区分，不需要改 `reject_type`
4. **维护成本**：4 种 reject_type 比 24 种更容易维护

**最终确认方案（北京老陈定案）**：

| reject_type | 含义 | content 示例 |
|-------------|------|-------------|
| `safety` | 安全检查器拒绝 | "工具未注册"、"系统禁区写/删"、"写入大小保护"、"check_fn 拦截" |
| `sandbox` | 沙箱拒绝 | "命令含越界写意图"、"预检超时"、"工作区超上限"、"影子副本失败" |
| `timeout` | 超时拒绝 | "工具确认超时未响应: {tool_name}" |
| `user` | 用户拒绝 | "用户拒绝执行工具: {tool_name}" |

**符合新规定（agent/LLM 层，保留 `type="error"`）**

| 来源 | error_type | 说明 |
|------|-----------|------|
| `react_step.py:410` | `empty_response` | LLM 返回空响应 |
| `react_loop.py:290` | `chunk_buffer_timeout` | LLM 响应累积超时 |
| `handle_action.py:337` | `invalid_action` | LLM 返回的 action 中 tool_name 为空 |
| `react_inference.py:52` | 动态分类 | ReAct 循环中的错误（LLM 调用异常、网络错误等） |

**这 4 处都是 agent/LLM 层面的问题，符合新规定，保留 `type="error"`。**

**不符合新规定（tool 层，需要改为 `type="rejected"`）**

**这 3 处是 tool 层面的拒绝，不符合新规定，需要改为 `type="rejected"`。**

### 1.3 推荐方案：统一 type="rejected" + 职责分离

**核心设计**：按职责分离，tool 拒绝用 `type="rejected"`，agent 错误用 `type="error"`

#### 1.3.1 新设计

```
新设计（职责分离 + content 细分）：
type="rejected" + reject_type="safety"   → 安全策略拦截（tool 层，6 种子场景）
type="rejected" + reject_type="timeout"  → 确认超时（tool 层）
type="rejected" + reject_type="user"     → 用户拒绝（tool 层）
type="rejected" + reject_type="sandbox"  → 沙箱拦截（tool 层，16 种子场景）

type="error" + error_type="..."          → Agent/LLM 错误（agent 层）
```

**rejected 事件数据结构**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `type` | `"rejected"` | 事件类型（固定值） |
| `step` | `number` | 步骤号 |
| `tool_name` | `string` | 被拒绝的工具名 |
| `reject_type` | `"safety" \| "sandbox" \| "timeout" \| "user"` | 拒绝类型（4种） |
| `content` | `string` | 拒绝原因（携带具体信息） |

```typescript
// 前端 TypeScript 类型定义
interface RejectedEvent {
  type: "rejected";
  step: number;
  tool_name: string;
  reject_type: "safety" | "sandbox" | "timeout" | "user";
  content: string;
}
```

**content 字段携带具体原因**：

| reject_type | content 示例 |

| `user` | "用户拒绝执行工具: {tool_name}" |

**前端显示规则**：
- `reject_type` 决定图标（🔒/🛡️/⏱️/🚫）
- `content` 决定具体文案

```
│                                                     │
│ 💧 delete_file                                       │  ← 第3行：执行工具（有水滴）
│   执行结果...                                         │  ← 第4行：observation
└─────────────────────────────────────────────────────┘
```

**时序说明**：
1. **第1行**：显示 action 待执行的工具名称（多工具时显示完整列表）
2. **第2行**：显示被拒绝的工具信息（reject_type 图标 + 工具名 + 原因，**无水滴图标**）
3. **第3行**：显示执行完成的工具（有水滴图标）+ observation 结果

**图标使用规则**：
- 🔄 `ToolWaitingIcon`：工具**执行中**（橙色8臂loader旋转）
- 💧 `DropletIcon`：工具**执行完成**（结果有不同 status：成功/失败/警告）
- 🔒/⏱️/🚫/🛡️：工具**未执行（被拒绝）**（无水滴，因为工具根本没有执行）

#### 1.3.2 设计优势

1. **职责清晰**：`rejected`=tool 问题，`error`=agent 问题，一眼区分
2. **SRP 单一职责**：每个 type 只负责一个层面
3. **统一入口**：前端按 type 分流，不需要额外判断
4. **可扩展**：未来新增拒绝类型只需加 `reject_type` 值

### 1.7 方案优势

| 维度 | 旧设计 | 新设计 |
|------|--------|--------|
| **职责分离** | tool 拒绝混在 `error` 通道，职责不清 | `rejected`=tool 问题，`error`=agent 问题，职责清晰 |
| **SRP 单一职责** | `error` 承载两种不同层面的事件 | 每个 type 只负责一个层面 |
| **类型统一性** | `error` 和 `user_rejected` 两个 type 混用 | 统一 `type="rejected"` 一个入口 |
| **前端复杂度** | 需要同时处理 `error` + `user_rejected` | 按 type 分流，逻辑清晰 |
| **可扩展性** | 新增拒绝类型需要改 type 或 error_type | 只需加 `reject_type` 值 |
| **用户体验** | 图标区分四种拒绝类型 | 同上 |

**改动范围**：
- 后端：10 处改动（safety_gate 3 处 + sandbox_gate 2 处 + 路由层 5 处）
- 前端：7 处改动（sseParser 1 处 + useSSE 1 处 + useChatStreaming 4 处 + ToolCallLine 2 处 + PipelineRenderer 1 处）

## 二、后端心跳显示 — 利用心跳机制方案

### 2.1 问题描述

后端等待时间过长时（如复杂工具执行、LLM 思考），前端只有等待动画（齿轮/弧线旋转），用户不知道后端是否还活着、还要等多久。

后端已有心跳机制（每 25-30s 发送 `: ping\n`），但前端完全不显示，用户感知不到后端的存活状态。

### 2.2 现状分析

#### 2.2.1 后端心跳机制

```
stream_orchestrator.py:510-520
├── 每 25s 无业务事件 → yield ": ping\n" (SSE 注释行)
├── 注释行格式标准：浏览器/EventSource 忽略
├── 用途：刷新前端 IDLE_TIMEOUT=60s 空闲计时
└── 不携带任何业务信息
```

#### 2.2.2 前端心跳处理

```
useSSE.ts:867-896
├── fetch + ReadableStream 读取
├── 每次 reader.read() 返回 → 重置 lastDataTimeRef
├── ": ping\n" 到达 → split('\n') → processSSEData 过滤非 'data: ' 行
├── 字节到达本身重置 IDLE_TIMEOUT 计时器
└── 不产生任何 UI 变化
```

#### 2.2.3 前端等待状态显示

| 等待阶段 | 组件 | 视觉表现 |
|---------|------|---------|
| LLM 思考中 | `ThoughtWaitingIcon` | 绿色弧线旋转 |
| 工具执行中 | `ToolWaitingIcon` | 橙色 8 臂 loader 旋转 |
| 等待行动 | `ActionWaitingIcon` | 蓝色涟漪扩散 |

**所有等待动画都是静态的**：只有旋转/扩散动画，没有时间信息。

### 2.3 推荐方案：直接利用心跳信号

**核心思路**：心跳本身就是"后端还活着"的信号，直接利用它告知用户，不需要另搞一套计时器。

#### 2.3.1 后端改动

心跳间隔保持 25-30s（与前端 60s IDLE_TIMEOUT 错开即可）。当前 25s 已满足要求，无需改动。

#### 2.3.2 前端改动

**改动 1：`useSSE.ts` — 检测心跳到达，触发 `onHeartbeat` 回调**

```typescript
// useSSE.ts read loop 中 (约 line 950)
const trimmedLine = line.trim();
if (trimmedLine.startsWith(': ping')) {
  onHeartbeat?.();  // 新增回调
  continue;
}
```

**改动 2：`useSSE.ts` — 新增 `onHeartbeat` 回调参数**

```typescript
interface UseSSEOptions {
  // ...existing params...
  onHeartbeat?: () => void;  // 新增
}
```

**改动 3：`ToolCallLine.tsx` — 接收心跳计数，显示等待状态**

```typescript
interface ToolCallLineProps {
  // ...existing props...
  heartbeatCount?: number;  // 新增：心跳计数
}

// 渲染等待动画时
{!hasResult && tools.length > 0 && !interrupted && !replay && (
  <>
    <ToolWaitingIcon />
    {heartbeatCount != null && heartbeatCount > 0 && (
      <span style={{
        color: Colors.TEXT.SECONDARY,
        fontSize: FontSize.SECONDARY,
        marginLeft: Spacing.SM
      }}>
        仍在执行中... ({heartbeatCount * 25}s)
      </span>
    )}
  </>
)}
```

**改动 4：`useChatStreaming.ts` — 维护心跳计数**

```typescript
const [heartbeatCount, setHeartbeatCount] = useState(0);

// 心跳回调
const handleHeartbeat = useCallback(() => {
  setHeartbeatCount(prev => prev + 1);
}, []);

// 传递给 useSSE
const { ... } = useSSE({
  // ...existing params...
  onHeartbeat: handleHeartbeat,
});

// 任务结束时重置
useEffect(() => {
  if (!isReceiving) {
    setHeartbeatCount(0);
  }
}, [isReceiving]);
```

**改动 5：`PipelineRenderer.tsx` — 传递 heartbeatCount 到 ToolCallLine**

```typescript
<ToolCallLine
  action={seg.action}
  observations={toolObs}
  interrupted={toolObs.length === 0 && allDenied}
  replay={!streaming}
  highlight={...}
  deniedTools={...}
  heartbeatCount={heartbeatCount}  // 新增
/>
```

### 2.4 为什么直接利用心跳更好

| 对比 | 独立计时器方案 | 心跳方案 |
|------|-------------|---------|
| 计时来源 | 前端本地 `useEffect` 计时器 | 后端心跳信号 |
| 信息含义 | "我本地计时器显示等了 30s" | "后端确认还活着，已过 {N} 个心跳周期" |
| 与后端的关系 | 无关，纯前端估算 | 直接关联，心跳=后端存活证明 |
| 阈值问题 | 需要人为设阈值（30s/60s） | 不需要阈值，心跳到了就更新 |
| 可靠性 | 前端计时器与后端可能不同步 | 心跳由后端发出，与后端完全同步 |

### 2.5 心跳间隔选择

- **25s**：与 60s 错开（60/25=2.4，每 60s 窗口至少 2 次心跳）
- **30s**：也可以（60/30=2，每 60s 窗口恰好 2 次心跳）
- **关键是与 60s 错开**，避免同时到期竞态

当前 25s 已满足要求，无需改动。

### 2.6 方案优势

| 维度 | 说明 |
|------|------|
| **后端零改动** | 心跳机制已存在，间隔合理 |
| **信息准确** | 心跳是后端存活的直接证明，不是前端估算 |
| **实现简单** | 前端 5 处改动，核心是检测 `: ping` + 计数显示 |
| **用户体验** | 看到 "仍在执行中... (25s)" 就知道后端在工作 |
| **可靠性** | 心跳与后端完全同步，不会出现前端计时器与后端不同步 |
