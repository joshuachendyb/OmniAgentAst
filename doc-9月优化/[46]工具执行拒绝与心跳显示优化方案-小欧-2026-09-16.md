## 一、工具执行被拒绝 — 前后端增强方案

### 1.1 问题描述

后端工具执行被拒绝时（安全拦截、确认超时、用户拒绝），后端日志可以清晰看到原因，但前端用户无法快速区分三种拒绝类型：

- **安全策略拦截**（blocked）：工具被安全检查器阻止
- **确认超时**（timeout）：HITL 确认等待超时
- **用户拒绝**（user_rejected）：用户主动拒绝执行

当前前端 `ToolCallLine` 只显示橘红灰字 "未执行：{reason}"，三种拒绝视觉上完全一样，用户需要阅读文字才能区分。

### 1.2 现状分析

#### 1.2.1 事件分类原则（北京老陈定案）

**核心原则**：按职责分离，tool 相关和 agent/LLM 相关用不同的 `type`

| type | 职责 | 场景 |
|------|------|------|
| `type="rejected"` | 与 **tool** 相关的拒绝 | 安全拦截、确认超时、用户拒绝、沙箱拦截 |
| `type="error"` | 与 **agent/LLM** 相关的错误 | LLM 调用失败、响应解析错误、Agent 内部错误、请求级错误 |

**设计优势**：
- **SRP（单一职责）**：每个 type 只负责一个层面的问题
- **语义清晰**：看到 `type` 就知道是 tool 拒绝还是 agent 错误
- **前端简单**：按 type 分流处理，不需要额外判断

#### 1.2.3 当前设计问题

```
当前设计：
type="error" + error_type="blocked"    → 安全拦截/沙箱拦截（tool 层，错用 error）
type="error" + error_type="timeout"    → 确认超时（tool 层，错用 error）
type="user_rejected"                    → 用户拒绝（tool 层，语义正确但命名不统一）
```

**问题 1**：tool 层的拒绝事件混在 `error` 通道，违反 SRP

**问题 2**：`type="user_rejected"` 和 `type="error"` 命名不统一，前端需要同时处理两个 type

**问题 3**：前端无法从 `type` 直接判断是 tool 拒绝还是 agent 错误

#### 1.2.6 reject_type 分类方案（北京老陈定案）

**方案：折中（4 种 + content 细分）**

| reject_type | 含义 | 子场景数 |
|-------------|------|---------|
| `safety` | 安全检查器拒绝 | 6 种（通过 content 区分） |
| `sandbox` | 沙箱拒绝 | 16 种（通过 content 区分） |
| `timeout` | 超时拒绝 | 1 种 |
| `user` | 用户拒绝 | 1 种 |

- **优点**：分类简洁（4 种），不丢失具体信息（content 字段携带）
- **缺点**：需要从 content 解析具体原因

**选择理由**：

1. **用户视角**：用户只需要知道"被拒绝了"，不需要知道具体是哪种安全检查拒绝的
2. **实现细节**：具体原因可以通过 `content` 字段携带（如"工具未注册"、"命令含越界写意图"等）
3. **可扩展性**：未来如果需要更细粒度，可以在 `content` 中区分，不需要改 `reject_type`
4. **维护成本**：4 种 reject_type 比 24 种更容易维护

**最终确认方案（北京老陈定案）**：

| reject_type | 含义 | content 示例 |
|-------------|------|-------------|
| `safety` | 安全检查器拒绝 | "工具未注册"、"系统禁区写/删"、"写入大小保护"、"check_fn 拦截" |
| `sandbox` | 沙箱拒绝 | "命令含越界写意图"、"预检超时"、"工作区超上限"、"影子副本失败" |
| `timeout` | 超时拒绝 | "工具确认超时未响应: {tool_name}" |
| `user` | 用户拒绝 | "用户拒绝执行工具: {tool_name}" |

### 1.3 推荐方案：统一 type="rejected" + 职责分离

**核心设计**：按职责分离，tool 拒绝用 `type="rejected"`，agent 错误用 `type="error"`

#### 1.3.1 新设计

```
新设计（职责分离 + content 细分）：
type="rejected" + reject_type="safety"   → 安全策略拦截（tool 层，6 种子场景）
type="rejected" + reject_type="timeout"  → 确认超时（tool 层）
type="rejected" + reject_type="user"     → 用户拒绝（tool 层）
type="rejected" + reject_type="sandbox"  → 沙箱拦截（tool 层，16 种子场景）

type="error" + error_type="..."          → Agent/LLM 错误（agent 层）
```

**rejected 事件数据结构**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `type` | `"rejected"` | 事件类型（固定值） |
| `step` | `number` | 步骤号 |
| `tool_name` | `string` | 被拒绝的工具名 |
| `reject_type` | `"safety" \| "sandbox" \| "timeout" \| "user"` | 拒绝类型（4种） |
| `content` | `string` | 拒绝原因（携带具体信息） |

```typescript
// 前端 TypeScript 类型定义
interface RejectedEvent {
  type: "rejected";
  step: number;
  tool_name: string;
  reject_type: "safety" | "sandbox" | "timeout" | "user";
  content: string;
}
```

**content 字段携带具体原因**：

| reject_type | content 示例 |
|-------------|-------------|
| `safety` | "工具未注册"、"系统禁区写/删"、"写入大小保护"、"check_fn 拦截" |
| `sandbox` | "命令含越界写意图"、"预检超时"、"工作区超上限"、"影子副本失败" |
| `timeout` | "工具确认超时未响应: {tool_name}" |
| `user` | "用户拒绝执行工具: {tool_name}" |

**前端显示规则**：
- `reject_type` 决定图标（🔒/🛡️/⏱️/🚫）
- `content` 决定具体文案

**前端 UI 显示时序**：

**单工具情况**：
```
┌─────────────────────────────────────────────────────┐
│ 🔧 shell_exec                                       │  ← 第1行：action 工具名
│                                                     │
│ （二选一）                                           │
│ 💧 shell_exec                                       │  ← 第2行：observation（成功，有水滴）
│   执行结果...                                       │
│ 或                                                  │
│ 🔒 shell_exec  未执行：工具未注册                      │  ← 第2行：reject（被拒，无水滴）
└─────────────────────────────────────────────────────┘
```

**多工具情况**：
```
┌─────────────────────────────────────────────────────┐
│ 🔧 action: shell_exec, edit_file, delete_file       │  ← 第1行：待执行工具列表
│                                                     │
│ 🔒 shell_exec  未执行：工具未注册                      │  ← 第2行：reject（无水滴）
│ 🚫 edit_file  未执行：用户拒绝                        │
│                                                     │
│ 💧 delete_file                                       │  ← 第3行：执行工具（有水滴）
│   执行结果...                                         │  ← 第4行：observation
└─────────────────────────────────────────────────────┘
```

**时序说明**：
1. **第1行**：显示 action 待执行的工具名称（多工具时显示完整列表）
2. **第2行**：显示被拒绝的工具信息（reject_type 图标 + 工具名 + 原因，**无水滴图标**）
3. **第3行**：显示执行完成的工具（有水滴图标）+ observation 结果

**图标使用规则**：
- 🔄 `ToolWaitingIcon`：工具**执行中**（橙色8臂loader旋转）
- 💧 `DropletIcon`：工具**执行完成**（结果有不同 status：成功/失败/警告）
- 🔒/⏱️/🚫/🛡️：工具**未执行（被拒绝）**（无水滴，因为工具根本没有执行）

#### 1.3.2 设计优势

1. **职责清晰**：`rejected`=tool 问题，`error`=agent 问题，一眼区分
2. **SRP 单一职责**：每个 type 只负责一个层面
3. **统一入口**：前端按 type 分流，不需要额外判断
4. **可扩展**：未来新增拒绝类型只需加 `reject_type` 值

### 1.7 方案优势

| 维度 | 旧设计 | 新设计 |
|------|--------|--------|
| **职责分离** | tool 拒绝混在 `error` 通道，职责不清 | `rejected`=tool 问题，`error`=agent 问题，职责清晰 |

| **前端复杂度** | 需要同时处理 `error` + `user_rejected` | 按 type 分流，逻辑清晰 |
| **可扩展性** | 新增拒绝类型需要改 type 或 error_type | 只需加 `reject_type` 值 |
| **用户体验** | 图标区分四种拒绝类型 | 同上 |

## 二、后端心跳显示 — 利用心跳机制方案

### 2.1 问题描述

后端等待时间过长时（如复杂工具执行、LLM 思考），前端只有等待动画（齿轮/弧线旋转），用户不知道后端是否还活着、还要等多久。

后端已有心跳机制（每 25-30s 发送 `: ping\n`），但前端完全不显示，用户感知不到后端的存活状态。

### 2.2 现状分析

#### 2.2.1 后端心跳机制

```
stream_orchestrator.py:510-520
├── 每 25s 无业务事件 → yield ": ping\n" (SSE 注释行)
├── 注释行格式标准：浏览器/EventSource 忽略
├── 用途：刷新前端 IDLE_TIMEOUT=60s 空闲计时
└── 不携带任何业务信息
```

#### 2.2.2 前端心跳处理

```
useSSE.ts:867-896
├── fetch + ReadableStream 读取
├── 每次 reader.read() 返回 → 重置 lastDataTimeRef
├── ": ping\n" 到达 → split('\n') → processSSEData 过滤非 'data: ' 行
├── 字节到达本身重置 IDLE_TIMEOUT 计时器
└── 不产生任何 UI 变化
```

#### 2.2.3 前端等待状态显示

| 等待阶段 | 组件 | 视觉表现 |
|---------|------|---------|
| LLM 思考中 | `ThoughtWaitingIcon` | 绿色弧线旋转 |
| 工具执行中 | `ToolWaitingIcon` | 橙色 8 臂 loader 旋转 |
| 等待行动 | `ActionWaitingIcon` | 蓝色涟漪扩散 |

**所有等待动画都是静态的**：只有旋转/扩散动画，没有时间信息。

### 2.3 推荐方案：直接利用心跳信号

**核心思路**：心跳本身就是"后端还活着"的信号，直接利用它告知用户，不需要另搞一套计时器。

#### 2.3.1 后端改动

心跳间隔保持 25-30s（与前端 60s IDLE_TIMEOUT 错开即可）。当前 25s 已满足要求，无需改动。

#### 2.3.2 前端改动

**改动 1：`useSSE.ts` — 检测心跳到达，触发 `onHeartbeat` 回调**

```typescript
// useSSE.ts read loop 中 (约 line 950)
const trimmedLine = line.trim();
if (trimmedLine.startsWith(': ping')) {
  onHeartbeat?.();  // 新增回调
  continue;
}
```

**改动 2：`useSSE.ts` — 新增 `onHeartbeat` 回调参数**

```typescript
interface UseSSEOptions {
  // ...existing params...
  onHeartbeat?: () => void;  // 新增
}
```

**改动 3：`ToolCallLine.tsx` — 接收心跳计数，显示等待状态**

```typescript
interface ToolCallLineProps {
  // ...existing props...
  heartbeatCount?: number;  // 新增：心跳计数
}

// 渲染等待动画时
{!hasResult && tools.length > 0 && !interrupted && !replay && (
  <>
    <ToolWaitingIcon />
    {heartbeatCount != null && heartbeatCount > 0 && (
      <span style={{
        color: Colors.TEXT.SECONDARY,
        fontSize: FontSize.SECONDARY,
        marginLeft: Spacing.SM
      }}>
        仍在执行中... ({heartbeatCount * 25}s)
      </span>
    )}
  </>

```

**改动 4：`useChatStreaming.ts` — 维护心跳计数**

```typescript

// 心跳回调
const handleHeartbeat = useCallback(() => {
  setHeartbeatCount(prev => prev + 1);
}, []);

// 传递给 useSSE
const { ... } = useSSE({
  // ...existing params...
  onHeartbeat: handleHeartbeat,

  if (!isReceiving) {
    setHeartbeatCount(0);
  }
}, [isReceiving]);
```


### 2.4 为什么直接利用心跳更好

| 对比 | 独立计时器方案 | 心跳方案 |
|------|-------------|---------|
| 计时来源 | 前端本地 `useEffect` 计时器 | 后端心跳信号 |
| 信息含义 | "我本地计时器显示等了 30s" | "后端确认还活着，已过 {N} 个心跳周期" |
| 与后端的关系 | 无关，纯前端估算 | 直接关联，心跳=后端存活证明 |
| 阈值问题 | 需要人为设阈值（30s/60s） | 不需要阈值，心跳到了就更新 |
| 可靠性 | 前端计时器与后端可能不同步 | 心跳由后端发出，与后端完全同步 |

### 2.5 心跳间隔选择

- **25s**：与 60s 错开（60/25=2.4，每 60s 窗口至少 2 次心跳）
- **30s**：也可以（60/30=2，每 60s 窗口恰好 2 次心跳）
- **关键是与 60s 错开**，避免同时到期竞态

当前 25s 已满足要求，无需改动。

### 2.6 方案优势

| 维度 | 说明 |
|------|------|
| **后端零改动** | 心跳机制已存在，间隔合理 |
| **信息准确** | 心跳是后端存活的直接证明，不是前端估算 |
| **实现简单** | 前端 5 处改动，核心是检测 `: ping` + 计数显示 |
| **用户体验** | 看到 "仍在执行中... (25s)" 就知道后端在工作 |
| **可靠性** | 心跳与后端完全同步，不会出现前端计时器与后端不同步 |

## 四、心跳等待感知合理设计（定案）

本设计替代第二章 2.3.2 已被否决的方案（否决理由见 3.1）。

### 4.1 等待链路情况分析（A~J 十种）

| # | 情况 | 链路/业务状态 | 用户疑问 | 应显示 |
|---|------|--------------|---------|--------|
| A | 短等待(<10s) | 正常 | 无感 | 钟面不显示（避免闪烁噪音） |
| B | 中等待(10~60s) | 正常 | 等了多久？ | 钟面+纯秒数 |
| C | 长等待(≥60s 静默) | 长工具真在跑(业务静默) | 卡了吗？ | 钟面转黄（无文字，色传达） |
| D | 业务繁忙 | 事件流不断、工具未完成 | 还在推进 | 钟面照走（心跳此时不发） |
| E | 连接断开 | 完全无任何数据 | 还在跑吗 | 后端报错→error 事件接管；纯网络断开(无 error 可达)→IDLE 灰档"连接疑似中断" |
| F | 业务卡死 | 连接通(心跳在)但业务停 | 怎么没动静了 | 业务静默达 2 分钟→橙红+里程碑文字，每 +60s 逐级递增 |
| G | 历史回放/非实时 | 无流式 | — | 隐藏钟面与提示 |
| H | 多工具并行 | 正常 | 各等多久 | 每行各自独立钟面 |
| I | 中断/取消/出错 | 结束 | — | 计时清零，无残留 |
| J | 后台 tab | 正常但计时被节流 | 回来时几秒？ | 差值计算，恢复即校正 |

### 4.2 定案要点

1. **心跳只作保活兜底，与钟面是"健康兜底"关系而非"计数"关系**：25s 心跳仅保障连接不被 IDLE 判死（业务事件也刷新数据计时）。分两层：(a) 无计数关系——心跳在业务繁忙时静默、粒度 25s，不能当钟面计时源（否则即已否决的 2.3.2，失真/停滞）；(b) 有健康兜底关系——心跳保证每 25s 至少一次数据到达，撑住 60s IDLE 判据，让钟面正常时持续可信走字；心跳长期缺席（连同业务数据 60s 无到达）→ IDLE 触发 → 钟面变灰+"连接疑似中断"。
2. **连接判据复用现有 IDLE，不新增钟线**：60s 内无任何 SSE 数据（业务或心跳）→"连接疑似中断"，钟面变灰。触发点沿用 useSSE 现有 IDLE 处理。
3. **唯一新增业务钟 `lastBizTs`**：最近一次业务事件（status/step/observation）到达时刻，用于区分正常长工具(C、≥60s 转黄)与业务卡死(F、≥120s 橙红+里程碑文字)；断连(E)由连接判据(IDLE)区分，两者互不混淆。
4. **微型钟面做成独立控件函数 `ClockStopwatch`**：Thought/Action/Tool 三个等待图标统一声明式挂载（DRY，不内联）。短针贴内缘环带扫动＝时间流逝（60s 归零重扫，周期式无伪进度）；中央等宽数字＝纯秒计数（≥10s 显示、无单位，小尺寸可读）；收到心跳→盘外圈微闪光波＝存活确认（不参与计时）。**尺寸 1.4em**——与思考/行动等待图标（1.4em≈20px）同尺寸对齐，工具图标（1.1em≈15px）处钟面略大、作为其辅助时长信息；中央秒数 viewBox 内**字号 11**（36 单位 viewBox 渲染到 1.4em 时实际约 6.5px，4 位数仍可辨；原字号 8 实际仅约 4.5px，不可读）。
5. **颜色三档 + 里程碑式文字（同源，按业务静默 `lastBizTs`）**：绿(静默<60s)→黄(静默 60~120s，无文字——1 分钟属常见等待不打扰)→橙红(静默≥120s 持续)。文字为整数分钟里程碑如实报告、逐级递增：等 LLM 已达 2 分钟→3 分钟→…（工具场景"工具执行已达 N 分钟"；钟面中央纯秒数字提供精确值）。注：颜色与文字均随 `lastBizTs` 静默时长升档（业务繁忙不升档）；钟面短针与纯秒数字则随本地计时（等待起点）。互斥优先级：断连 > 橙红里程碑 > 黄色静默，只显最高级。
6. **钟面 ≥10s 才显示**：短等待一闪而过会闪烁；达到 10s 后钟面出现（短针扫动+纯秒数字）且持续不再隐藏。
7. **生命周期绑定**：钟面仅在流式实时等待时存在；历史回放隐藏；结束/中断/结果替换统一清理。
8. **计时硬约束**：`performance.now()` 差值计算（防系统时钟跳变、后台节流丢秒），严禁"+1 累加"；秒数等宽字体（tabular-nums）防布局抖动。
9. **断连区分两态，灰档非冗余**：(a) 后端可报错（业务异常/崩溃发出 error 事件）→ 走既有 error 错误展示，灰档不介入；(b) 纯前后端网络断开（error 根本发不出）→ 60s IDLE 触发灰档"连接疑似中断"，此时灰档是**唯一能显示的提示**、不可或缺。

### 4.3 设计（一条流 · 一个业务钟 · 一个本地钟面）

```
微型钟面秒表（短针版 · 独立控件 ClockStopwatch）：
   短针贴内缘环带扫动 = 时间流逝，60s 归零重扫（周期式，无伪进度）
   中央等宽数字 = 纯秒计数（≥10s 才显示，无单位，viewBox 内字号 11）
   尺寸 = 1.4em（与思考/行动等待图标 1.4em 对齐；工具图标 1.1em，钟面为其辅助时长信息）
   心跳微闪 = 收到后端心跳 → 盘外圈闪一道光波（存活确认，不参与计时）
   颜色三档 = 绿(静默<60s) → 黄(静默60~120s) → 橙红(静默≥120s)，与里程碑文字同源(按 lastBizTs)；短针与数字按本地计时

文字信息（里程碑式 · 整数分钟递增报告）：
   10~120s 无文字（颜色传达；1 分钟属常见等待不打扰）
   ≥120s 橙红持续 + "等 LLM 已达 2 分钟" → 180s"已达 3 分钟" → 每 +60s 递增
        （工具场景"工具执行已达 N 分钟"；钟面中央纯秒数字提供精确值）

   后端报错：走既有 error 事件错误展示，灰档不介入
互斥：断连 > 橙红里程碑 > 黄色静默
隐藏/清理：非流式/回放隐藏；结束/中断/结果替换清零
```

**三个时间信号 → 钟面（性能安全：高频走 ref，低频才 state）**

| 信号 | 含义 | 产生点 | 载体 |
|------|------|--------|------|

**三个关键决策（北京老陈 2026-09-17 定）**

1. **心跳微闪=真实心跳通路**：sseParser 入口识别 `: ping` 注释行，新增 `onHeartbeat` 回调 → useSSE `setHeartbeatTs` → 钟面盘外圈重放一道光波。

3. **挂载即从 0 计时**：`ClockStopwatch` 组件 mount 时刻为计时起点（等价于进入该等待场景时刻）。

**档位判定（每秒 tick 读 ref，零高频 setState）**

```
elapsedSec  < 10           → 不显示（短等待避免闪烁）
dataSilence >= 60s         → 灰档 指停 + "连接疑似中断"
else bizSilence >= 120s    → 橙红 + "等 LLM 已达 N 分钟" / "工具执行已达 N 分钟"
else bizSilence >= 60s     → 黄（无文字）
else                       → 绿（无文字）
```

### 5.2 新增文件 `frontend/src/components/WaitingIcons/clockStopwatch.tsx`

```tsx
// 编辑历史: 2026-09-17 小欧 - 新增: 心跳等待感知微型钟面秒表独立控件(北京老陈[46]第四章定案):
//   短针贴内缘环带扫动(60s归零重扫)＋中央纯秒数(≥10s)＋心跳微闪光波(存活确认)＋三档色(绿/黄/橙红)
//   ＋整数分钟里程碑文字; 与等待图标并存(追加不替换) — 小欧-2026-09-17
import React, { useEffect, useRef, useState } from 'react';
import { Colors } from '@/utils/stepStyles';
import type { ClockSignals } from '@/types/sse'; // 2026-09-17 小欧 [46]: 钟面信号打包类型(定义于类型层, 避免 types→components 反向依赖) — 小欧-2026-09-17

const APPEAR_SEC = 10; // 钟面出现门槛(短等待避免闪烁)
const YELLOW_SEC = 60; // 业务静默转黄
const ORANGE_SEC = 120; // 业务静默转橙红(里程碑文字起点)
const DATA_LOST_SEC = 60; // 任意数据静默≥60s=连接疑似中断(与 useSSE IDLE_TIMEOUT 同源)

const LEVEL_COLOR = {
  green: Colors.SUCCESS, // #52c41a
  yellow: Colors.WARNING, // #AD6800
  orange: Colors.ORANGE_RED, // #fa541c
  gray: Colors.TEXT.TERTIARY, // #999999
} as const;

type Level = keyof typeof LEVEL_COLOR;

export interface ClockStopwatchProps extends ClockSignals {
  /** 里程碑文字主语: llm="等 LLM 已达 N 分钟"; tool="工具执行已达 N 分钟" */
  kind?: 'llm' | 'tool';
}

export const ClockStopwatch: React.FC<ClockStopwatchProps> = ({
  lastBizTsRef,
  lastDataTsRef,
  heartbeatTs,
  kind = 'llm',
}) => {
  // 计时起点 = 组件挂载时刻(performance.now 差值, 防系统时钟跳变/后台节流丢秒)
  const startedAtRef = useRef<number>(performance.now());
  const [, setTick] = useState(0);
  const [beatTick, setBeatTick] = useState(0);

  // 每秒 tick: 驱动短针/秒数/档位刷新; 档位在渲染期直接读 ref(零高频 setState)
  useEffect(() => {
    const id = window.setInterval(() => setTick((t) => t + 1), 1000);
    return () => window.clearInterval(id);
  }, []);

  // 心跳到达 → 盘外圈重放一道光波(存活确认, 不参与计时)
  useEffect(() => {
    if (heartbeatTs > 0) setBeatTick((t) => t + 1);
  }, [heartbeatTs]);

  const elapsedSec = Math.floor(
    (performance.now() - startedAtRef.current) / 1000
  );
  if (elapsedSec < APPEAR_SEC) return null; // 短等待不显示

  // 基线未初始化(<=0)视为无静默, 防首帧误判灰档/升档
  const bizSilenceSec =
    lastBizTsRef.current > 0
      ? Math.floor((Date.now() - lastBizTsRef.current) / 1000)
      : 0;
  const dataSilenceSec =
    lastDataTsRef.current > 0
      ? Math.floor((Date.now() - lastDataTsRef.current) / 1000)
      : 0;

  let level: Level = 'green';
  let note: string | null = null;
  if (dataSilenceSec >= DATA_LOST_SEC) {
    level = 'gray';
    note = '连接疑似中断';
  } else if (bizSilenceSec >= ORANGE_SEC) {
    level = 'orange';
    note =
      kind === 'tool'
        ? `工具执行已达 ${Math.floor(bizSilenceSec / 60)} 分钟`
        : `等 LLM 已达 ${Math.floor(bizSilenceSec / 60)} 分钟`;
  } else if (bizSilenceSec >= YELLOW_SEC) {
    level = 'yellow';
  }

  const color = LEVEL_COLOR[level];
  const angle = (elapsedSec % 60) * 6; // 短针 60s 一圈归零重扫

  return (
    <span
      className="clock-stopwatch"
      role="img"
```
