## 一、要解决的问题是什么

### 1.1 用户看到的现象

会话页正在流式输出 step（thinking / 工具调用 / 执行结果 / 最终回答）时，用户切到历史页或设置页，再切回来：

1. 实时 step **不续传**，界面停在切走那一刻的画面；
2. 切走期间后台产生的中间步骤**看不到**；
3. 任务若在切走期间已完成，回来只剩最终结果，**中间过程丢失**；若还在跑，回来是**全新初始化**，接不上正在跑的流。

### 1.2 后端侧的三个根因

前端切页断流是前端病根（组件卸载即 abort），但**即便前端把续传凭据全保留住，后端也接不上**——这是后端要解决的：

| 根因 | 改造前现状 | 后果 |
|------|-----------|------|
| B1 续传源是进程内存且有回收期 | 事件只在 `StreamBuffer.event_log` 内存列表；任务结束 300 秒后内存缓冲被回收 | 300 秒是**内存回收点**不是数据保留期，超窗数据就没了 |
| B2 重连只查内存缓冲 | 重连端点 `get_stream_buffer(task_id)` 未命中就直接返回"任务不存在" | 后端没有可按 `task_id + seq` 回放的**持久事件源** |
| B3 已发生事件无跨进程留存 | 事件只经 `chat_task_steps` 落库 | 那是历史步骤表，不等于完整实时事件流；`chunk` / `thought-start` 这类实时信号**不可回放** |

### 1.3 本方案解决到哪一层（四级恢复）

| 级别 | 目标 | 本方案 |
|------|------|--------|
| R1 内存级续传 | 任务运行期间断线，按 `after_seq` 从内存续传 | 已原生支持 |
| R2 终态事件回放 | 任务完成、内存缓冲回收后，从持久 Journal 精确回放全部事件 | **本方案解决** |
| R3 重启后回放 | 后端重启后，已完成任务仍可回放 | **本方案解决** |
| R4 重启后续算 | 后端重启后从 LLM/tool checkpoint 继续执行未完成任务 | **本方案不做**（进程已消失，无法凭空继续；续算是独立立项） |

**诚实边界**：本方案让"重启后已发生的事件不丢"成立；"重启后任务自动继续"**不成立**，也**禁止**把后者包装成前者已解决。

## 二、采用的后端技术架构和原理

### 2.1 总体架构：内存快路径 + SQLite 事件 Journal 双层

```
写入侧（每个事件）
    Agent publish
        → StreamBuffer.publish 分配唯一 seq
        → stream_event_journal.append()  写入 SQLite        ← 先落库
        → event_log 追加 + 唤醒 SSE 读者                     ← 后可见
读取侧（重连/刷新）
    GET /chat/stream/{task_id}?after_seq=N
        → 内存缓冲命中：直接从 event_log 读          【快路径】
        → 内存未命中：从 SQLite Journal 按 seq 读   【兜底】
```

同一套 `GET` 端点、同一套 SSE 格式器、同一套事件白名单，**只是数据源从内存换成库**，不新增端点、不新增第二套协议。

### 2.2 核心原理（七条）

**① seq 单一分配权**
内存 `event_log.seq` 与数据库 `chat_stream_events.seq` 必须是**同一次分配的结果**。禁止前端重新编号、禁止数据库另行生成、禁止恢复时按时间猜顺序。

**② 先持久化、后对 SSE 可见**
落库成功后才进内存、才唤醒读者。理由：反过来做（先放内存、稍后异步落库）的话，进程在两步之间崩溃就丢事件。四种明确禁止的写法：

- 先放内存后异步落库（崩溃丢事件）
- 持内存锁等待 SQLite（阻塞生产者和读者）
- 数据库失败直接取消任务（把存储故障放大成执行故障）
- 每事件单独建连接/事务（写放大）

**③ 双锁分工**
任务级 `publish_lock` 管"分配 seq + 落库"；消费者级 `cond` 只管"内存可见 + 唤醒读者"。**数据库等待期间一律不持消费者锁**，所以慢库不会卡住正在读的 SSE 连接。

**④ 依赖注入，`task_state` 保持 DB-agnostic**
内存缓冲模块只管 seq、锁、内存可见性，**不 import 数据库、不写 SQL**。落库能力由外部注入。两条创建缓冲的路径（正常路径 + 直连兜底路径）**都必须注入**，漏一条该路径就只写内存、目标失效。

**⑤ 有限重试 + 降级打标**
写库失败重试 3 次；仍失败则在该事件上打 `persistence_degraded` 标记、记日志、**继续推实时流**。语义是"实时优先，但该任务失去精确回放保证"。降级事实必须**粘滞**（失败帧自己写不进库，只能由后续成功帧携带），否则回放侧永远看不到。

**⑥ 300 秒语义修正：内存回收 ≠ 数据保留**
任务结束后 300 秒回收的只是内存缓冲，**绝不删数据库事件**。函数因此从 `reclaim_stream_buffer` 改名为 `reclaim_memory_buffer`（名实相符，不改名反而误导）。

| 时间/状态 | 内存缓冲 | Journal | 重连走哪条路 |
|-----------|---------|---------|------------|
| 任务运行中 | 保留 | 持续追加 | 内存快路径 |
| 结束后 0~300 秒 | 保留 | 保留 | 内存快路径 |
| 结束后超 300 秒 | 回收 | 保留 | Journal 回放 |
| 重启、任务已完成 | 丢失 | 保留 | Journal 回放 |
| 重启、任务未完成 | 丢失 | 可能部分 | 报"任务已中断"，不续算 |

**⑦ 四层权威互不重叠**

| 状态 | 唯一权威 | 其他层 |
|------|---------|-------|
| 任务是否终态 | 数据库 `chat_tasks.status` | SSE/前端**不得自行推断**终态 |
| 事件是否可回放 | Journal 的 seq 连续性 + 终态事件 | 前端只消费回放结果 |
| 前端是否在接收 | 前端 Store 快照 | 页面卸载不改变后端任务状态 |
| 最终展示内容 | 数据库已完成步 | Journal 只管事件回放，不替代数据库 |

### 2.3 数据模型

```sql
CREATE TABLE IF NOT EXISTS chat_stream_events (
    task_id TEXT NOT NULL,
    session_id TEXT NOT NULL,
    seq INTEGER NOT NULL,
    event_type TEXT NOT NULL,
    payload_json TEXT NOT NULL,
    created_at TEXT NOT NULL,
    PRIMARY KEY (task_id, seq)                      -- 同时保证顺序与幂等
);
CREATE INDEX IF NOT EXISTS idx_stream_events_type
    ON chat_stream_events(task_id, event_type, seq);
```

四条自律：

- `payload_json` 存**完整事件内容（含 seq）**，不能用业务 step 编号替代；
- 读取只按 `task_id`，清理才与 `chat_tasks` 关联，**不建用不到的 session 索引**；
- `event_type` 只供查询诊断，SSE 白名单仍由编排层单点决定，**不引入第二套白名单**；
- **不复制 `chat_task_steps`** 当事件库（避免双源不一致）。

## 三、后端的业务流程说明

### 3.1 写链（每个事件都走这条）

```
1. Agent 调用 publish(event)
2. 持 publish_lock：复制事件、分配 seq = len(event_log)
3. 调 append(task_id, session_id, seq, type, payload) 写 SQLite   ← 落库在前
   ├─ 成功 → 继续
   └─ 失败 → 重试 3 次 → 仍失败则打 persistence_degraded 标记
4. 持 cond：event_log 追加该事件 + 唤醒 SSE 读者                    ← 可见在后
5. SSE 推给前端
```

**取消场景的特殊处理**（必须，否则静默丢帧）：落库是在线程里同步完成的，**协程取消不了它**。若不加保护，取消会落在"库已写、内存未追加"之间 → 内存序号不前进 → 下一帧复用同一序号 → 被数据库主键冲突**静默吞掉**。因此把"落库 + 进内存"整段放进独立任务并等它跑完再传播取消。

### 3.2 读链（内存优先，Journal 兜底）

```
重连请求（带 after_seq，语义是"从第 N 帧开始给我"）
  ├─ 内存缓冲命中 → 直接从 event_log 读 seq >= N
  └─ 内存未命中   → Journal 回放
        · 校验归属：该任务记录的 session 与请求 session 是否一致
        · 任务行存在性检查（先判后放）
        · 按 seq 升序分页读，"页不满 = 读完"
        · 逐帧检查序号连续性，跳跃则报缺口区间
        · 复用同一 SSE 格式器 + 同一白名单输出
        · 到终态事件或判定结束时收尾
  · 整个回放过程不启动新 Agent、不走新建会话入口
```

### 3.3 回放的六种结局（禁止含糊其辞）

| 情形 | 给前端什么 |
|------|-----------|
| 已追平（请求序号超过全部事件）且库里有终态 | **静默收尾，不发任何错误** |
| 序号跳号 | 报"事件不连续"并给出缺失区间 |
| 有事件、无终态事件，但任务已终态 | 报"任务终态事件缺失"（**禁止伪造完成**） |
| 无终态、任务未终态、**产出方已停止**（活窗内无新事件） | 报"任务已中断，请从历史继续" |
| 无终态、任务未终态、**产出方还活着** | 发心跳继续等（保护多实例/慢思考任务不被误杀） |
| 数据库无该任务行 | 报"任务不存在" |

**归属校验**：事件行自带 `session_id`，与请求不一致即拒绝返回（防知道 task_id 就能读他人会话）。请求未带 `session_id` 时归属无从校验，**放行但必须留日志**（不静默放行，也不误杀正常重连）。

### 3.4 清理链

- 独立后台任务定期执行，**绝不在请求链路扫全表**；
- 只删**已终态且超保留期**的任务事件；**活跃/未终态永不删**；
- 保留期走集中配置（默认 7 天，范围 1~30），**禁止多处写死**；
- 终态事件缺失不能成为永久不清理的理由 → 按事件自身创建时间兜底；
- 无对应任务行的孤儿事件也清理（否则永久泄漏，库无限增长）；
- 清理失败**只记日志，不阻断聊天**。

### 3.5 启动期收尾（诚实收敛，不续算）

进程被强杀时收尾逻辑不执行，任务状态会永久停在"执行中"，任务列表一直显示执行中。启动时把这类残留行收敛为**诚实终态**：标记为失败 + "任务被中断"。

- **不新增状态值**：复用"失败"+"任务被中断"，因为"已中断"这个词已被前端"工具被拒"占用；
- **不补算耗时**：被打断没有真实完成耗时，补算是编造；
- **不恢复、不重跑、不续算**（那属于 R4，独立立项）；
- 只收尾"启动时刻之前创建"的行，避免同机多实例启动时误伤另一进程正在跑的任务。

## 四、后端的能力实现说明

### 4.1 落点

| 能力 | 落点 |
|------|------|
| 表与索引 | `db_initializer.py`（幂等建表） |
| 落库/回放/判活/终态读/清理 | 新建 `services/chat/stream_event_journal.py`（6 个窄接口） |
| 序号、锁、内存可见性、降级 | `services/task/task_state.py`（保持不 import DB） |
| 两条路径注入 sink、内存回收改名 | `services/agent/agent_runner.py` |
| 注入 sink、Journal 回放兜底 | `services/chat/stream_orchestrator.py` |
| 路由异常兜底、`after_seq` 边界 | `api/v1/chat/chat_routes.py`（不新增端点） |
| 清理任务挂载、启动期收尾 | `main.py` |
| 启动期残留行收尾 | `services/chat/storage.py` |

### 4.2 窄接口

| 接口 | 职责 |
|------|------|
| `append` | 单事件落库 |
| `read_after` | 回放读取（返回**列序号 + 解析后内容**、是否有终态、归属 session） |
| `is_producer_alive` | 判定产出方是否还活着（最近事件是否落在活跃窗口内） |
| `get_persisted_task_status` | 读数据库权威终态 |
| `retention_cleanup` | 清理已终态且超期事件 |
| `checkpoint_wal` | WAL checkpoint（PASSIVE），把自动 checkpoint 的落库尖峰挪到空闲期 |

**`read_after` 为什么返回"列序号"而不是直接给内容**：内容是外部 JSON，形状不可信（可能不是对象、可能缺 `seq`）。**列序号是数据库整数、单调、必然存在**，游标推进与缺口检测一律用它。这样脏数据只会让那一帧不被转发，**不会让整条流崩掉或原地死循环**。

### 4.3 两个必须"不同名"的读取口

| 接口 | 读什么 | 语义域 |
|------|-------|-------|
| `get_running_task_status` | 内存活跃任务表 | 进程内活跃态 |
| `get_persisted_task_status` | 数据库任务行 | 跨重启的终态权威 |

两者语义正交，**严禁同名、严禁互相替代**。

### 4.4 关键实现细节

| 细节 | 做法 | 防止什么 |
|------|------|---------|
| 取消保护 | 落库+进内存整段 shield，取消时等其完成 | 序号被复用 → 下一帧被静默吞 |
| 降级粘滞 | 失败标志随后续成功帧携带 | 降级事实丢失 → 回放侧误以为完整 |
| 脏帧处理 | 类型闸门 + 聚合日志 | 单个脏帧崩掉整条流 |
| 未来时间戳 | 判活时不认（容差 5 秒） | 时钟回拨导致死任务永不收敛 |
| 缓冲复用闸门 | 只对"挂了落库能力"的生产缓冲生效；纯内存夹具每次新建 | 复用旧缓冲导致事件日志混入上一轮残留 |
| 保留期类型 | 入口归一为整数 | 配置写成字符串打死后台清理任务 |

### 4.5 配置

| 配置项 | 默认 | 范围 | 位置 |
|--------|------|------|------|
| 事件保留天数 | 7 | 1~30 | `tuning.live_front.journal_retention_days` |

集中管理在 tuning 配置，**不在多个模块写死**。

### 4.6 验证结论

| 层级 | 结果 |
|------|------|
| 守护测试 | 28/28 通过（12 项修复守护 + 新功能分支 + 边界探测） |
| 后端全量单测 | **7800 通过 / 0 失败**（703s） |
| 端到端（真实模型 + 真实后端） | 8/8 通过 |
| 写入压测（6 场景） | 6/6 通过；实测吞吐天花板约 100 帧/s，真实流量 3.7~13.5 帧/s，**余量 7~27 倍** |

**性能判定**：因余量充足且不变式（序号连续、零丢帧、降级语义）全部成立，**不引入高频事件合批**（异步尾任务 + 强制刷新时机 + 单写者约束的复杂度不值得）。

### 4.7 验收门逐项签字

签字口径：✅ 有直接证据；⚠️ 部分达标（写明差距）；❌ 未达标。

| # | 验收项 | 判定 | 证据 / 差距 |
|---|--------|------|------------|
| 1 | 落库后进程被杀，重启后已完成任务可按 `after_seq` 回放 | ✅ | `testscompress/verify_acceptance_replay.py`：造 5 帧 → 丢弃内存与连接（等价进程死亡）→ 重开库回放，5 帧类型序列完整、seq 连续；`after_seq=4` 只补 1 帧不重复 |
| 2 | 结束超 300 秒后 GET 仍能回放终态前后完整事件 | ✅ | 同上：`reclaim_memory_buffer` 后内存 0 行、Journal 5 行仍在（兼证第 8 项），`from_seq=0` 完整回放 5 帧且无错误帧混入 |
| 3 | `seq` 严格连续、无重复、无跳号，`after_seq` 边界正确 | ✅ | 压测 6 场景不变式（seq 严格单调、零丢帧）；守护测试负数钳位、分页跨页、缺 seq 不打转 |
| 4 | 正常路径与直连路径均注入落库能力，不漏写 | ✅ | 两处注入点代码审查 + 压测走真实 `create_task_stream_buffer(..., J.append)` 路径 |
| 5 | 实时事件与业务事件的回放策略符合白名单 | ✅ | 白名单单测：过滤事件不推进游标、不误报缺口，跨页不漏发 |
| 6 | 高频压测满足延迟预算，backlog 超限能进 degraded | ⚠️ | 压测 6/6 PASS（p99 14.9~16.0ms < 20ms 预算）；**backlog 背压未实现**——当前是 DB 慢时反压生产者（不丢帧），非主动降级。见 4.8 |

## 五、对前端的支持配合的能力说明

### 5.1 后端提供给前端的接口能力

| 能力 | 前端怎么用 |
|------|-----------|
| 按序号续传 | 重连时带上已收到的最大序号 + 1，后端只补发之后的帧，**不重复不遗漏** |
| 内存优先的快路径 | 任务运行中重连走内存，秒级接上 |
| Journal 兜底回放 | 300 秒后、后端重启后，任务已完成也能补齐全部过程 |
| 归属校验 | 请求带上会话标识，后端据此拒绝读他人会话 |
| 明确的错误事件 | 下列错误类型有固定语义，前端各自给中文文案，**不得都当成正常空流** |

### 5.2 前端必须处理的错误类型

| 错误类型 | 含义 | 前端应做什么 |
|---------|------|-------------|
| `task_not_found` | 任务不存在或已过期 | 提示并停止重连 |
| `task_interrupted` | 任务未完成且产出方已停止 | **转历史降级**（加载数据库历史），不得重跑任务 |
| `task_state_incomplete` | 任务已终态但终态事件缺失 | 提示过程不完整，**禁止当作正常完成** |
| `persistence_gap` | 事件序号有跳跃，缺失区间已知 | 提示"部分过程不可恢复"，**禁止当作正常最终结果** |
| `persistence_degraded` | 该任务事件落库曾失败，精确回放无保证 | 提示"部分过程刷新后不可恢复" |

### 5.3 前端接线要点

| 要点 | 说明 |
|------|------|
| 重连必须带会话标识 | 后端归属校验依赖它；缺失时后端只能放行 + 留日志（无法验证归属） |
| 序号守卫 | 后端只发 `seq >= after_seq`，前端需按序号去重 |
| 心跳注释行 | 回放等待期会发心跳注释行，前端需识别（用于刷新空闲计时），**不是业务帧** |
| 降级标记在事件体内 | 落库失败的那一帧自己写不进库，标记由**后续成功帧**携带，前端从帧字段读取 |
| 不自行推断终态 | 终态以数据库为准；前端 `isReceiving` 只是 UI 态，页面卸载不改变后端任务状态 |

### 5.4 后端明确**不**提供给前端的东西

| 不提供 | 原因 | 归属 |
|--------|------|------|
| 重启后从 checkpoint 继续执行 | 进程已消失，无法凭空继续 | 独立立项（续算方案） |
| 前端组件常驻 / 连接常驻 | 属前端页面生命周期范畴 | 前端方案 |
| 事件跨会话聚合视图 | 不属本方案范围 | — |

> 换句话说：后端把"**事件一旦发生就不会丢、且能按序号精确重放**"这件事做实了；"切页不断流""新步骤落在最新位置"属前端职责，二者缺一不可。
