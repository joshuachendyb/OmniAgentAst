# HITL弹框消息字段梳理


## 1、现状分析

### 1.1 消息字段（线上 13 个）

后端 HITL 网关（`hitl_gateway.py:95-100`）发出的 paused 帧线上一共 13 个字段。基础 4 个（`MetaStep.to_dict` 固定带）：

- `type`（=`paused`）
- `step`（轮号）
- `timestamp`
- `content`（提示文本）

弹窗专用 9 个（构造时传入）：

- `confirm_id`（`task_id:8位随机`，配对关闭弹窗用）
- `tool_name`
- `params`（已脱敏摘要，长值截断，防弹窗超高）
- `safety_level`
- `severity`（固定 `attention`）
- `trust_path`
- `auto_confirm`
- `confirm_timeout`（前端倒计时）
- `backend_timeout`（后端兜底超时）

### 1.2 前端消费链路（8 个进弹窗）

只透传其中 8 个字段进弹窗：`sseParser.ts:873` 取下述 8 个调 `onAuthorizationRequired` → `useChatCallbacks` 经 `authorization_required` 事件原样广播 → `useAuthorization.ts:66` 转驼峰装配 `AuthorizationRequest`（另带布尔归一与超时兜底清洗）→ `AuthorizationModal` 渲染。链路一线图：

```
paused 帧(13 字段) → sseParser 取 8 字段 → authorization_required 事件 → useAuthorization 转驼峰 → AuthorizationModal 渲染
                                                                          ↘ resumed 帧配对 confirm_id → 关框（与 8 字段无关）
```

- `confirm_id` → `confirmId`：发回后端确认兼新旧弹窗配对
- `tool_name` → `toolName`："工具名称"行展示（弹窗标题为"安全确认请求"/bypass"将自动确认"，非工具名）
- `params` → `params`：按 `key=value` 每行一条展示（09-16 定案禁 JSON 式）
- `safety_level` → `safetyLevel`：前端定义五档徽章（只读/安全/破坏性/沙箱危险/系统危险）；但线上出现过的值只有 destructive 一种，5 档中 4 档永不到达（见 1.3 末 level 结论）
- `trust_path` → `trustPath`：仅用于信任勾选框 tooltip（`{toolName} › {trustPath}，含子目录/子键`），无独立路径行；缺失时 tooltip 不展示路径（"未指定路径，仅本次"已随 09-16 改版移除，仅存历史注释）
- `auto_confirm` → `autoConfirm`：为 true 走 bypass 自动确认
- `confirm_timeout` → `confirmTimeout`：倒计时秒数，bypass 显示"将在 Ns 后自动确认（后端 Ns 兜底）"，hitl 显示"未响应将在 Ns 后自动拒绝"
- `backend_timeout` → `backendTimeout`：括号内"后端 Ns 兜底"

没进弹窗的 5 个字段去向（一行一个）：

- `type` → 进执行步骤列表
- `step` → 进执行步骤列表
- `timestamp` → 进执行步骤列表
- `content` → 进任务信息条状态行
- `severity` → paused 链路无任何消费（sseParser 未读取、未转发，弹窗无该字段）

关闭弹窗靠 `resumed` 帧配对 `confirm_id`（`sseParser.ts:889` 派发事件，`useAuthorization.ts:96` 比对后关闭），与 8 字段无关。

### 1.3 弹框触发点（2 处，7 项计数 + 4 项排除）

逻辑流：工具调用 → ① safety_gate 安检（`safety_gate.py:89-104`）：blocked 直接拒绝（rejected，不弹框）；`requires_confirmation` 进网关；通过则 → ② sandbox_gate 沙箱预检+裁决（`sandbox_gate.py:58-129`，预检 58-71、裁决含网关 74-129）：通过或 bypass 免验直接放行（不弹框）；拦截直接拒绝（不弹框）；`needs_ruling` 进网关。两处统一经 `hitl_confirm` 唯一网关暂停发框，网关内 publish paused → 等裁决 → publish resumed（confirmed 必发，bypass+expired 亦发），前端凭 `confirm_id` 配对关框。单 paused 不变量：主路已确认则沙箱跳过二次弹窗（`sandbox_gate.py:87`）。流程示意图：

```
工具调用（每轮 action）
  │
  ├─① safety_gate 工具安检
  │    ├─ blocked → rejected（拒绝，不弹框）
  │    ├─ 通过 → ②
  │    └─ requires_confirmation → [网关]
  │
  ├─② sandbox_gate 沙箱预检
  │    ├─ 通过/放行 → 执行工具（不弹框）
  │    ├─ 拦截 → rejected（不弹框）
  │    └─ needs_ruling → [网关]
  │
  └─[网关] hitl_confirm（唯一暂停源头，唯一 paused 发射）
       ├─ publish paused（13 字段）→ 前端凭 confirm_id 弹框
       └─ 等用户裁决
            ├─ confirmed → publish resumed（配对关框；bypass+expired 亦发）
            └─ 拒绝/超时 → 不发 resumed（rejected 事件留痕）
```

触发点 1：安全闸工具安检（`safety_gate.py:99`）。`tool_name/params` 为实际调用（网关内脱敏加摘要），`safety_level` 取自安检结果（动态），`mode` 按安检 `auto_confirm` 取 `bypass`（前端自动确认倒计时）或 `hitl`（真等待）。

触发点 2：沙箱预检裁决（`sandbox_gate.py:114`）。`mode` 固定 `hitl`，`tool_name/params` 为实际调用，`safety_level` 固定 `destructive`，`auto_confirm` 固定 False。

7 项计数核查（真实代码行，注释已剔除）：①`await hitl_confirm` 全仓 2 处（上两处）；②`await create_confirmation` 与 ③`await wait_for_confirmation_result` 全仓各 1 处（均在网关内）；④`ConfirmSpec(` 构造全仓 2 处（上两处）；⑤`MetaStep(type=paused)` 发射全仓 1 处（网关）；⑥前端 `onAuthorizationRequired` 调用全仓 1 处（`sseParser.ts:873`，且有 `confirm_id` 守卫）；⑦`setAuthorizationPending(新请求)` 全仓 1 处（`useAuthorization.ts:88`，另两处为关框置空）。

排除项（逐一核实非触发点）：①`task_runtime.py:197` 的 paused 是用户手动暂停任务（无 `confirm_id`，被前端守卫过滤，不弹框）；②`react_step.py:60` 的 `task_dir_authorization` 已于 2026-08-10 撤销，仅注释残留；③`authorization_required` 独立事件类型仅见于跳过名单与注释，全仓零发射；④`handle_action.py` 的 S1/bypass 注释均指向经 safety/sandbox 入网关，本文件无直接发射。

level 结论（全仓 25 处赋值加全仓发射点逐条核实）：后端内部产出三档（safe 放行 / destructive 确认 / dangerous 拦截），但序列化到前端的值只有 destructive 一种——paused 帧专属；两处 rejected 发射（安全闸拒绝、沙箱拦截）均不带 `safety_level` 字段；safe 无对应事件。因此前端 5 档徽章实际可达仅"破坏性" 1 档，"只读/安全/沙箱危险/系统危险" 4 档永不到达（有兜底不崩，但属瞎对应）。前版"两档死档""红色只在拦截行"表述有误，特此纠正：拦截行无 level 字段，红色徽章同样到不了前端。

### 1.4 提示信息内容（3 种 content，加参数摘要规则）

- 安全闸 bypass 分支（`safety_gate.py:101`）：`安全策略自动确认工具执行: {工具名}`。
- 安全闸 hitl 分支（`safety_gate.py:102`）：`是否允许执行工具: {工具名}`。
- 沙箱裁决（`sandbox_gate.py:116`）：`沙箱未能完成有效预检,需用户裁决是否直接执行: {工具名}`，`safety_level` 恒为 `destructive`。

以上 3 种 `content` 只进任务信息条状态行，均不进弹窗（见 2.2）。弹窗参数区另有摘要规则（`hitl_gateway.py:42-55`，[43]11.6-T4）：主键 path 优先展示，长值尾部截断 140 字符，截断结果压成单行，脱敏统一收口，保证每参数恒为一行。

## 2、发现的问题及解决方案

### 2.1 确认触发过宽（弹窗多的根因）

**问题是什么：** 确认触发与"危险"脱钩，改挂钩"工具名/兜底"——shell 全弹、沙箱验不出就弹、同批逐个弹。三个倾向即 2.1.3 过宽 3 条，下文按顺序展开：2.1.1 追踪链（看清确认机制）→ 2.1.2 默认清单（影响范围）→ 2.1.3 辨过宽 3 条 → 2.1.4 划合理边界（防误伤）→ 2.1.5 收紧策略。注：bypass 照弹是设计本意（自动确认但提示照出，弹框数不减），不属过宽，前版误判，纠正。

#### 2.1.1 追踪链（以 shell ls 为例）

注册层 `needs_confirmation=True` 写死（`fundamental_register.py:127`，与命令内容无关）→ 安检层 `requires_confirmation=True`（`tool_safety_checker.py:196-201`，信任与开关只能旁路改不了 flag 本身）→ 网关弹框#1（`safety_gate.py:99`，真等待）→ 沙箱预检只读白名单放行（`executor.py:241`，排在弹框之后）。注意：白名单本可免掉的第二次弹框（沙箱 needs_ruling 那一框）已被单 paused 不变量 suppress（主路确认后 `main_confirmed=True` 直放），故当前实现中白名单对减弹零贡献——只读命令的框一次也省不掉。

#### 2.1.2 工具默认需确认清单（字面 flag 共 7 个工具）

- file 类仅 delete（`CONFIRMATION_MAP={"delete": True}`，其余默认 False）；
- fundamental 类仅 shell（恒 True；附带 `action_confirmation={"write": True}` 仅 params 含 action 字段时生效，shell 命令无该字段，实际恒走 flag）；
- system 类 create_task/delete_task、win_registry 类 registry_write/registry_delete（各 `CONFIRM_TOOLS`）、dataanalysis 类 execute_sql；
- 其余分类注册行无 flag，默认 False。动态规则（路径/白名单外授权）在安检层 `_check_known_risks` 实现（白名单外/受保护区，见 1.3 触发链与 2.1.3 过宽 2），不在此重复。

#### 2.1.3 过宽 3 条（现象加证据加判定）

三条共性：确认被问在不需要问的地方——只读命令问（过宽 1）、已信任还问（过宽 2）、同批逐个问（过宽 3）。逐条：

过宽 1：shell 一刀切（工具级 flag，不看命令内容）。现象：`ls/pwd/echo` 等纯查询命令照弹。证据：上链（flag→安检→网关）全程不读命令内容（见 2.1.1）；只读白名单在沙箱内（`executor.py:241`），排在弹框（`safety_gate.py:99`）之后。判定：粒度过粗——沙箱本有能力区分只读与越界（白名单、F-B 意图扫描已建好），应把"只读放行"提到确认链路入口，先放行只读、再谈弹框（见 2.1.5 三级处置与 3.2）。缓解现状：信任可解（shell 无路径参数，信任提取走工具级通配，勾一次管全会话）；bypass 半解（照弹自动过）。

过宽 2：信任被沙箱击穿。信任豁免（勾"信任本次会话"或会话已信任）后，受信 destructive 工具跑到沙箱又弹一次框，前面的信任承诺落空。

分类（哪类"前面的确认"之后沙箱不该再弹，现状三开二）：①手动确认主路：已透传 `main_confirmed=True`，沙箱 `needs_ruling` 直放不再弹（`sandbox_gate.py:87`，单paused）✓；②bypass 自动确认：沙箱 `needs_ruling` 被 `auto_confirm` 直放不再弹（`sandbox_gate.py:90-94`）✓；③信任豁免：豁免只跳过安检弹框，`sandbox_required=True` 原样保留（`tool_safety_checker.py:244/263`），跑到沙箱 `needs_ruling` 又弹 ✗——错就错在这条。

错在哪：豁免结果 `requires_confirmation=False` 却带 `sandbox_required=True`；safety_gate 走 site③（`:170`）调 run_sandbox_gate 未传 `main_confirmed`（缺省 False），豁免又不置 `auto_confirm`，沙箱三个免弹闸（passed / main_confirmed / auto_confirm）全落空，`needs_ruling` 必弹。重灾区：受信 writetext 白名单外每次必弹（`executor.py:291-296` 沙箱不支持该操作，一律转裁决）；受信 shell 在超时/环境失败/越界意图时照弹；受信 flag 高危工具（create_task/delete_task/execute_sql/registry 等）经 skip 豁免同样保留 `sandbox_required`（`tool_safety_checker.py:194`），到沙箱走同一条 unsupported 二次弹。

正确应如何：信任应与手动/自动确认等价——沙箱需识别"该工具+该路径已被用户放行"，区分执行风险与能力缺口：验出真危险（risky）仍弹；验不了（unsupported，能力缺口）配 trusted 直接放行。即 3.3 的 ruling_kind 方案（site③ 透传 `trusted=_skip`），落地后受信 writetext 不再弹，未受信照弹。

过宽 3：同批多调用逐个弹。现象：一轮 3 个同类调用弹 3 次。证据：`safety_gate` 在循环内逐 call `await hitl_confirm`（`safety_gate.py:67/99`），主路无批合并（沙箱侧有单 paused 去重，主路没有）。判定：体验问题，安全语义不变——按批合并（见 3.4）不改变单次裁决的安全水位。

#### 2.1.4 合理的部分（8 条，不过宽）

- delete R3 放行 / R4R5 确认 / R6 硬拦（`delete_safety.py:82-92`），四档分明；
- create_task/delete_task、registry_write/delete、execute_sql 高危 flag，真高危不可逆；
- shell MEDIUM 内容规则（`execute_shell_command_safety.py:216-224`，MEDIUM 特征确认后放行，:1106-1107 仅日志；虽被 flag 全弹盖住而冗余）；
- 白名单外/受保护区首触确认，三重出路：信任勾选（会话持久，前缀递归）、临时授权（任务内有效）、`allowed_dirs` 配永久白名单；
- 系统禁区硬拦（blocked 直接拒，不弹框）；
- M2 沙箱置位精确（仅 destructive 置 `sandbox_required`，safe 零开销直通）；
- 单 paused 不变量（主路已确认跳过沙箱二次裁决）；
- 信任前缀递归加工具级通配（shell 勾一次管全会话，方向正确；但沙箱侧缺豁免消费，即过宽 2，需 3.3 补齐）。

#### 2.1.5 收紧方向（4 条，待立项）

**shell 三级处置总则（allowlist 放行 / blocklist 直拦 / 其余弹框，本章策略、第三章落码）：**

- allowlist 白名单：十类只读前缀直接放行，不弹框。现有五类（`get-`、`ls`、`cat`、`type`、`git status`），新增五类（`echo`、`pwd`、`dir`、`whoami`、`hostname`，逐条过安全评审）；带 `|;&>>` 拼接符一律不进白名单。落点：确认链路入口——`safety_gate.py:89`（`requires_confirmation` 分支）前置只读判定，命中即跳过整个确认链路、直落沙箱白名单放行（代码在 3.2）。
- blocklist 黑名单：HIGH 危险命令（格式化磁盘/关机/rm -rf 根/cipher/dd 直写等）直接硬拦，连确认机会都不给（已存在：工具执行层 `execute_shell_command.py:1098` 调 `check_shell_command_risk`，规则表 `execute_shell_command_safety.py:44-72`；位置说明在 3.2.2）。
- 其余：非白非黑的 shell（非常规只读、写操作、中风险命中）照旧弹框或拦截，安全水位不降。

①shell 只读命令前移免弹（即上述白名单扩展，详见 3.2.1；越界写意图仍弹）；②信任豁免透传沙箱（受信加能力缺口类 ruling 自动过，执行风险类照弹，详见第三章 3.3）；③同批同工具调用合并一次确认；④writetext 白名单外 trusted（并入 3.3 ruling_kind 机制，无独立实施，见第三章 3.5）。bypass 不在收紧范围（自动确认但提示照出是设计本意，非只读命令弹框数不动；只读命令经 3.2 前置短路 bypass 亦免提示——只读无风险、提示无信息量，属唯一例外，见 3.2 影响说明）。

**建议的解决方法是什么：** 按 2.1.5 四向立项实施，落码见第三章 3.2~3.5，本章不动代码。

### 2.2 content 到不了弹窗（确认理由缺失）

**问题是什么：** 后端 `spec.content` 可携带重要原因文本（实证：`sandbox_gate.py:116` 的"沙箱未能完成有效预检，需用户裁决是否直接执行"，用户裁决最需要的正是这句话），但它只进任务信息条状态行，弹窗的 `AuthorizationRequest` 无该字段，用户点开弹窗看不到事由，只能看到工具名和参数。

**建议的解决方法是什么：** `AuthorizationRequest` 加可选字段 `reason`（取 paused 帧 `content`），弹窗在标题下方加一行原因文本展示；`content` 为空时不渲染该行，老 frames 兼容。后端零改动，只动前端两处（`useAuthorization.ts` 装配加一字段，`AuthorizationModal` 加一行展示）。该改动待批准后实施。（注：第四章推翻了本节的"后端零改动"前提——content 文案要改构造行，后端动 2 行、前端动 6 处，以 4.2 注与 4.4 为准。）

### 2.3 severity 发而不用（冗余传输）

**问题是什么：** 后端每帧固定发 `severity=attention`，但 paused 链路自 sseParser 起即丢弃，弹窗用不到，执行步骤也不映射（核实：前端 `severity` 的消费仅存在于错误配置表、截断帧等其他消息类型）。无害，但属冗余传输。

**建议的解决方法是什么：** 保持现状，不删。理由：删减需先全仓确认 paused 无其他隐性消费者，且该字段为未来"按级别着色弹窗"预留了扩展位；当前成本仅为每帧几个字节。若日后做字段瘦身，再与 `content` 进弹窗一并处理。

### 2.4 safety_level 档位错位（前端 5 档瞎对应）

**问题是什么：** 后端内部虽产出三档，但送达前端的值只有 destructive 一种（paused 专属；两处 rejected 发射均不带该字段；safe 无对应事件）；前端 `SAFETY_LEVEL_CONFIG` 却备 5 档，其中 4 档（只读/安全/沙箱危险/系统危险）永不到达。前版称"两档死档"不准确，实际是四档，纠正。新人读前端会误以为后端有 5 种确认级别，属揣测性映射。有兜底回退，不崩，但误导大于实用。

**建议的解决方法是什么：** 删前端四个死档，只留 `destructive`（未知 level 走既有兜底回退显示原文，零风险）。该改动待批准后实施（与第四章无关，独立可先行）。

### 2.5 trust_path 展示浪费（操作对象无独立行）
