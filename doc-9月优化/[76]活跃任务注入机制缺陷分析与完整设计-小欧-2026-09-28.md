## 一、背景

2026-09-28 排查 `AttributeError: 'StreamChunk' object has no attribute 'encode'` 时，挖出「活跃任务注入」机制存在多处设计缺陷。本文档记录取证、根本矛盾与完整修复设计。

### 1.1 触发场景

同会话任务运行中，用户追加第二条消息。生产环境 100% 崩溃：

```
starlette/responses.py:252  chunk = chunk.encode(self.charset)
AttributeError: 'StreamChunk' object has no attribute 'encode'
ERROR: Exception in ASGI application
```

### 1.2 机制语义

`stream_orchestrator.py:376-383`：同 `session_id` 存在活跃任务时，新消息投进目标任务的 inbox，下一轮 LLM 调用前合并吸收，不打断工具执行（9-20 新增，北京老陈定案）。

## 二、链路全景（含两个落库点）

```
[前端] POST /sessions/{sid}/messages  →  insert_user_message → 行A  ★落库点1
[前端] POST /chat/stream              →  orchestrator
        ├ has_active_task_in_session 命中
        ├ inject_message_to_task(content)  →  inbox: Queue[str]   ← uid 在此丢失
        ├ yield retrying 事件(现状, 语义误用)  →  SSE 结束
        └ return（不启动 agent）
[agent 下一轮] _absorb_inbox
        ├ drain_inbox → List[str]
        ├ _merged = "\n".join
        ├ insert_user_message(_merged)  →  行B  ★落库点2（重复）
        └ add_user_message(_merged, user_message_id=_uid)
[下一轮对话] _load_previous_messages(linked) → fetch_session_user_message_pairs
        └ 无去重，ORDER BY cum.id → 行A、行B 全部读出
```

## 三、根本矛盾（所有缺陷的同一源头）

`storage.list_session_tasks` docstring 载明既定口径：**「任务数=用户消息数，一条用户消息=一个任务」**。

注入消息**是用户消息、却不对应任务**，1:1 假设被打破，派生多个缺陷：

| 缺陷 | 派生路径 | 严重度 |
|------|---------|--------|
| 重复落库 | uid 丢失 → `_absorb_inbox` 被迫重落 → 绕过唯一入口 | P0 |
| 归属缺失 | `chat_user_message.task_id` 留 NULL → 无法回答"消息属于哪个任务" | P0 |
| 刷新不可见 | 左侧列表按 `chat_tasks` 渲染 → 注入消息无 task 行 → 刷新后彻底不可见 | P0 |
| uid 锚覆盖 | 多条注入时 `_uid` 写到旧 user 消息，覆盖其原配对锚 | P1 |
| 内存/DB 不同步 | 内存并入末条（不新增条目），DB 落独立行 | P1 |
| 语义误导 | 注入复用 `retrying`，前端渲染为「🔄 重试」 | P2 |
| 队列无界 | `asyncio.Queue()` 无 maxsize | P3 |

### 3.1 关键取证

| 项 | 证据 |
|----|------|
| 重复落库 | 3 个 session 100% 复现，各 2 条相同记录，`task_id` 均 NULL |
| 历史无去重 | `fetch_session_user_message_pairs` 仅 `ORDER BY cum.id ASC`，无 DISTINCT |
| 兜底重复配对 | `COALESCE(ct.ai_message_id, fb.ai_message_id)` 使 N 条注入消息配到同一 assistant |
| 渲染重复 | `get_session_messages` 严格一对一 → 同一回复渲染 N 次 |
| 死代码化石 | `react_step.py:211-214` 的 `isinstance(tuple)` 分支永不命中 → 9-20 原设计传元组后退化为 str |
| **9-20 两个修复均失效** | 见 5.2 |
| **`task_id` 仅终态写入** | 唯一写入点 `update_user_message_final`（`storage.py:681`），仅被 `_finalize_task_db`（`agent_runner.py:621/650`）终态调用 |

### 3.2 已排除的误判

| 曾判为 BUG | 查证结论 |
|-----------|---------|
| 注入与任务结束竞态 | `async with running_tasks_lock` 包住检查+put，同锁内原子，非 BUG |
| `task_id=NULL` 本身是 bug | 靠 `chat_tasks.user_message_id` 关联，非 bug（但**归属仍需显式回填**，见 5.2） |
| 重复落库是测试假象 | `save_user_message` 调 `POST /sessions/{id}/messages`，生产前端同链路，真 BUG |

## 五、完整设计

### 5.0 设计概要与决策点

#### 5.0.1 这套机制是什么

用户在任务跑着的时候又发一条消息。设计上不打断当前任务，而是把新消息投进该任务的 inbox，等 Agent 下一轮调 LLM 前合并进上下文，任务继续往下跑。

```
任务A 正在跑 ──▶ 用户发消息2 ──▶ 投进任务A的inbox
                                    │
任务A 下一轮调LLM ◀── 合并吸收 ◀────┘
```

**为什么要有这个机制**：打断重开代价高（已完成的工作作废、上下文断裂）。合并吸收让用户可以边看边补指令。

#### 5.0.2 一个根因，三个症状

设计上「一条用户消息 = 一个任务」。但注入消息**是用户消息、却不对应新任务**，这个 1:1 假设被打破。

代码为绕开它，把消息**落库两次**（入口一次、Agent 吸收时又一次）。而 Agent 吸收时拿不到入口那条消息的 ID，**这才是真正的根因**：

```
拿不到消息ID ──▶ 被迫再落一次库 ──▶ 产生两条重复记录
                     │
                     └──▶ 拿不到ID，也就绑不上任务 ──▶ task_id 为 NULL
                                                            │
                                                            └──▶ 列表查不到归属 ──▶ 刷新后消息消失
```

一个根因（ID 丢失）派生三个症状（重复 / 归属空 / 不可见）。**所以修一处即可同时消解，不需要三个独立补丁。** 第三章缺陷表另列 4 项（uid 锚覆盖 / 内存DB不同步 / 语义误导 / 队列无界）为同一根因的次级派生，分别由 5.2、5.4、5.6 承接。

#### 5.0.3 修复的核心思路

**让消息 ID 在整条链路上不丢失，并让它在注入那一刻就绑到目标任务。**

于是三件事同时成立：只落库一次（入口那一行）、归属明确（`task_id` 有值）、执行期可见（不必等任务结束）。

复用 `chat_user_message.task_id` 这一已有列完成绑定 —— 该列本就是为此设计的，从未回填过。**零 DDL、零新表、零新组件。**

#### 5.0.4 三个关键概念

| 概念 | 含义 | 说明 |
|------|------|------|
| **消息 ID（`user_message_id`）** | 一条用户消息在 DB 里的行号 | 入口 `POST /sessions/{id}/messages` 落库时返回。**本次修复就是让它不再丢失** |
| **归属（`task_id`）** | 这条消息属于哪个任务 | 首轮消息由 `chat_tasks` 登记；注入消息需要**显式回填**，这是修复要点 |
| **inbox** | 任务内存里的待吸收队列 | 现在存裸字符串（丢了 ID），改为存 `(内容, ID)` 二元组 |

#### 5.0.5 角色与存储形态

**角色恒为 `user`**，role 层不区分「首轮发的」和「loop 中追加的」。注入消息投递时丢弃 role，Agent 侧统一按 user 消息重建。区分归属靠 `task_id`，不靠 role。

| 层 | 多条注入时的形态 | 理由 |
|----|----------------|------|
| **DB** | **分开存**，每条一行，靠同一 `task_id` 归属 | 保留原貌：用户发了什么就存什么，可追溯 |
| **内存 / LLM 上下文** | **合并成 1 条**（换行拼接） | OpenAI 兼容协议要求 user/assistant 交替，连续 user 部分 provider 判非法 |

**归属边界**（多条注入都挂同一 `task_id`）：

| 场景 | 归属结果 |
|------|---------|
| 同会话 + 同一活跃任务，连发 N 条 | N 条全挂该 `task_id`，左侧折叠成 1 个条目 |
| 同会话 + 首个任务已结束，再发 | 走正常新建任务路径，成为独立任务，不参与折叠 |
| 同会话 + 多任务并存 | 注入只认**当前活跃那个**，不跨任务串挂 |

即「一条消息=一个任务」仅在**独立发起**时成立；只有注入是「多消息共享一任务」，而这正是 `merged_inputs` 要表达的信息。

#### 5.0.6 左侧列表长什么样

前端是**任务粒度**，不是消息粒度 —— 每个条目 = 一条用户输入 + 一条回复，没有消息气泡列表。追加消息挂在**问题区与回复区之间**（语义上属输入侧）：

```
┌─ 任务条目 ──────────────────────┐
│ 13:16  gpt-4  ●成功  10轮        │  ← 元信息行
│ 请写一份关于人工智能技术发展的...    │  ← user_input（问题区）
│ ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄ │  ← 分隔（新增）
│ ↳ 追加 1 条              ▾      │  ← 折叠头
│   在报告里再补充一个量子计算的章节   │  ← 展开后显示
│ ┌────────────────────────────┐ │
│ │ AI 的完整回复内容...          │ │  ← response（回复区）
│ └────────────────────────────┘ │
└─────────────────────────────────┘
```

**选折叠而非平铺**：追加消息可能连发多条，平铺会把条目撑长、挤掉回复区。折叠后默认收起，条目高度基本不变。

#### 5.0.7 阶段总览

| 编号 | 层 | 解决 | 核心改动 |
|------|---|------|---------|
| 5.1 | S1 传输 | 重复落库 | inbox 存 `(内容, ID)` 二元组，orphan 路径同步 |
| 5.2 | S2 归属 | 归属为空 | 修属性名不匹配 + 注入即回填 + 删 D-1 造假行 |
| 5.3 | S3 展示 | 刷新不可见 | 任务列表折叠 + `merged_inputs` + 左侧折叠块 |
| 5.4 | S4 事件 | 语义误导 | 新增 `merged` 事件替代误用的 `retrying` |
| 5.5 | S5 历史 | 回复重复渲染 | 连续无配对 user 合并渲染 |
| 5.6 | S6 健壮 | 无界队列等 | 队列上限 + 满则降级 + 截断 + `QueueFull` 捕获 |
| 5.7 | S7 测试 | 无防护网 | 4 场景真实 LLM 回归 |
| 5.8 | — | 既有缺陷 | 记录在案，本设计不修 |

#### 5.0.8 关键决策点（7 个，均为"两难取舍"而非"做不做"）

| # | 决策点 | 取舍 | 理由 |
|---|--------|------|------|
| 1 | 多条注入的内存形态 | 合并成 1 条 ↔ 拆成 N 条 | **合并**。保 user/assistant 交替性；DB 侧仍保留 N 条独立行 |
| 2 | assistant 配对归属 | 配第一条 ↔ 配最后一条 ↔ 合并渲染 | **合并渲染**。与决策 1 同一规则（都按"合并块"处理），三处形态统一，无需单独的配对策略配置 |
| 3 | 追加消息展示形态 | 平铺并列 ↔ 折叠块 | **折叠**。默认收起不撑条目高度，展开可看全文 |
| 4 | 数据表达方式 | 新建关系表 ↔ 复用 `chat_user_message.task_id` | **复用**。该列本就为此设计、从未回填；零 DDL，不引入第二份真相 |
| 5 | D-1 假行处理 | 迁移清理 ↔ 查询折叠容忍 | **折叠容忍**。不写迁移、不动存量数据；加队列上限后新增假行为零 |
| 6 | 队列满的应对 | 报错拒绝 ↔ 降级新建任务 | **降级**。注入是优化路径而非必需路径，队列满时让用户等不如直接开新任务：消息不丢、用户有进度、无错误态 |
| 7 | 负 id 锚守卫 | 加 ↔ 不加 | **加**。虽现网负 id 不演进锚（不会 `WHERE id=-1` 落空），但 5.1 改二元组后 ID 由外部传入，一行守卫防新引入的传值失误 |

**决策的一贯原则**：凡"新建结构 vs 复用既有"，**选复用**（4）；凡"报错 vs 降级"，**选降级**（6）；凡"内存/DB/渲染三处需一致"，**只定一个规则三处共用**（1、2）；凡"信息平铺 vs 收起"，**选收起**（3）。这四条决定了全案**零新表、零新组件、零 DDL**。

### 5.1 S1 传输层：uid 随消息同行（根治重复落库）

| 改动 | 内容 |
|------|------|
| `inject_message_to_task(task_id, content, user_message_id)` | 投递 `(content, uid)` 元组，替代裸 str |
| `drain_inbox` | 返回类型契约改为 `List[Tuple[str, int]]` |
| **`_orphaned_inbox`** | **值类型同步改 `List[Tuple[str, int]]`**（`:60` 现为 `Dict[str, List[str]]`） |
| `react_step.py:211-214` | **删除** `isinstance(tuple)` 兼容分支（禁 backward） |

**orphan 路径为何必改**：`cleanup_task` / `cleanup_expired_tasks` 把未吸收消息转入 `_orphaned_inbox`（`:180` / `:216`），`drain_inbox` 在任务已删时从 orphan 找回（`:143`）。若只改 inbox 不改 orphan，**收尾窗口注入的消息 uid 会丢失，重演同一根因**。

### 5.2 S2 归属层：修属性名 + 注入时立即回填

#### 5.2.1 属性名不匹配（9-20 两个修复失效的根因）

| 位置 | 写法 |
|------|------|
| `react_step.py:248` 写锚 | `_current_user_msg_id`（**私有**） |
| `agent_runner.py:647` 读锚 | `getattr(..., "current_user_msg_id", None)`（**公开**） |

`message_builder` 只有 `_current_user_msg_id`（`:113` 初始化、`:142` 赋值），**无同名公开属性** → `getattr` 恒返 `None` → `_final_uid` 退回 `db_ops.user_msg_id`（第一条消息 uid）→ 注入消息的 UPDATE 永不命中；D-1 亦因 `user_message_id == _first_uid` 跳过。

实测（E2E-INJ-01 session `30b12310`）：

```
chat_tasks:        仅 1 行(user_message_id=1006113)      ← D-1 未生成
chat_user_message: 1006114 task_id=NULL / 1006115 NULL   ← 锚回填未生效
```

| 改动 | 内容 |
|------|------|
| `message_builder` | 新增**只读 property** `current_user_msg_id` → 返回 `_current_user_msg_id`（封装，禁外部直读私有） |
| `agent_runner.py:647` | 加守卫 `uid > 0`：`(_active_uid or 0) > 0 ? _active_uid : db_ops.user_msg_id` |

> 事实澄清：`message_builder.py:134/136/142` 载明负 id **不演进** `_current_user_msg_id`，故现网不会 `WHERE id=-1` 落空。守卫保留为防御 —— 防 S1 元组传值失误，成本一行。

#### 5.2.2 注入时立即回填（补执行期空窗）

`task_id` **仅终态写入**（见 3.1），故任务执行中注入消息的 `task_id` 恒 NULL → 5.2.3 精确归属与 5.3 展示在**执行期全部失效**，5.3 目标落空。

| 时机 | 动作 | 作用 |
|------|------|------|
| **注入成功即刻** | 新增 `storage.bind_message_to_task(uid, task_id)`（单条 UPDATE，零 DDL） | 执行期即可归属 |
| 任务终态 | 既有 `update_user_message_final` 照旧 | 补 `response`/`reasoning`/`outcome`/`chat_model`（`task_id` 幂等重写） |

两者**时机不同**（注入即刻 vs 任务结束），是补空窗而非重复。

#### 5.2.3 删除 D-1 补配对分支

**D-1 原意**：注入消息在 `chat_tasks` 无配对行 → 补一行避免 `fetch` 出 NULL 幽灵。

**但它复制源任务行**（`task_id`/`user_input`/`context_link_mode`/`start_time` 全同，仅 `user_message_id` 不同），一旦激活则：

| 影响 | 机理 |
|------|------|
| 左侧列表重复条目 | `list_session_tasks` = `SELECT ... FROM chat_tasks`，每条注入消息多一行 |
| **React key 冲突** | `TaskListPanel` `key={t.task_id}`，重复 task_id |
| 任务总数虚高 | `total = COUNT(*) FROM chat_tasks` |
| 破坏既定口径 | 违反「任务数=用户消息数」 |

**且该 INSERT 多余**：`COALESCE(ct.ai_message_id, fb.ai_message_id)` 兜底本已能配对（注入消息的回复本就属于该任务）。

**替代**（更精确，零 DDL）：`fetch_session_user_message_pairs` 以 `cum.task_id` 作精确归属，取代会话级模糊兜底：

```sql
LEFT JOIN chat_tasks ct ON ct.id = (
    SELECT MAX(id) FROM chat_tasks
    WHERE task_id = cum.task_id OR user_message_id = cum.id
)
```

注入消息凭 `cum.task_id` 找到所属任务，起始消息凭 `cum.id = ct.user_message_id` 找到所属任务，二者归一，**无造假行**。

### 5.3 S3 展示层：注入消息在左侧任务条目可见

| 层 | 改动 |
|----|------|
| `list_session_tasks` | ①按 `task_id` 折叠同 task 多行（保留 `ORDER BY id ASC` 首行）<br>②每行补 `merged_inputs: List[str]` |
| `SessionTaskItem` (TS) | 加 `merged_inputs?: string[]` |
| `TaskListPanel` | 「用户问题区」下方渲染「↳ 追加 N 条」`CollapsibleText` 折叠块 |

**存量旧数据直接清理（北京老陈 2026-09-28 定案）**：修复前产生的注入消息副本（`task_id IS NULL` + 非任何任务首条 + 同会话存在更小 id 的同内容行）**一次性 DELETE**，不搞兼容兜底，查询只走下面单一路由：

```sql
SELECT cum.content FROM chat_user_message cum
JOIN chat_tasks ct ON ct.user_message_id = cum.id
WHERE ct.task_id = ?        -- 目标任务
  AND cum.id <> ?           -- 排除任务登记的首条 uid（已作 user_input 显示）
ORDER BY cum.id ASC
```

- 新增（`bind_message_to_task` 填了 `cum.task_id`）：命中
- 存量：清理后不存在，无需通吃逻辑

清理 SQL（一次性 DML，`schema_migrations` 登记防重跑）：

```sql
DELETE FROM chat_user_message
WHERE task_id IS NULL
  AND id NOT IN (SELECT user_message_id FROM chat_tasks)
  AND EXISTS (SELECT 1 FROM chat_user_message b
              WHERE b.session_id = chat_user_message.session_id
                AND b.content = chat_user_message.content
                AND b.id < chat_user_message.id)
```

误删防护：正常首轮消息必在 `chat_tasks.user_message_id`（不命中第 2 条）；用户主动重复发同内容且已建任务的，后者也在 `chat_tasks` 里（不命中）。

故 `bind_message_to_task`（保证执行期归属与 `fetch` 精确关联）与 5.3 数据源（保证展示完整）**解耦**。

### 5.4 S4 事件层：`merged` 事件替代误用的 `retrying`

现状 `retrying` 被前端渲染为「🔄 重试」(`stepConstants.ts:20/34`)，与"已并入"语义不符。

| 步骤 | 改动 |
|------|------|
| 1 | `steps/__init__.py:ALL_STEP_TYPES` 注册 `merged`（"仅SSE"列，与 `retrying` 同列）→ 自动进 `_SSE_FORWARD_TYPES` |
| 2 | `_build_injected_ack` 改 `MetaStep(type="merged", ...)`，携带 `merged_into_task_id` |
| 3 | `stepConstants.ts` 加 `merged: '已并入'` + 图标 |
| 4 | `sseParser.ts` 加 `case 'merged'` → 提示条，**不进 `liveMeta` 错误位** |
| 5 | `stepFilter.ts` 白名单加 `merged` |

> `merged` 属 meta 类，`splitSteps().business` 不含它 → 不进右栏流水线（符合右栏只显 step 的既有分工），仅在 `sseParser` 提示 + 5.3 左侧角标呈现。

### 5.5 S5 历史层：连续无配对 user 合并渲染

`get_session_messages` 严格一对一（`:76-107`），配合 `COALESCE` 兜底会把同一 assistant **重复渲染 N 次**。

**改法**：渲染层把「无独立配对、且时间连续」的 user 行合并为 1 个气泡（换行拼接）+ 1 个 assistant。与「内存合并成 1 条」**同一规则** → 内存 / DB / 渲染三处形态一致，「配对归属」问题由该规则自动消解。

### 5.6 S6 健壮层

| 风险 | 设计 |
|------|------|
| inbox 无界 | `Queue(maxsize=INBOX_MAX)`，`INBOX_MAX = 20`，走 `constants.py` 配置化 |
| **队列满（必配）** | `task_registry.py:131` 现为裸 `put_nowait(content)`，加 maxsize 后会抛 `asyncio.QueueFull` **上抛到 orchestrator 使降级失效反崩溃**。必须 `except asyncio.QueueFull: return False`（复用既有 False=拒绝注入语义） |
| 队列满降级 | `inject_message_to_task` 返回 False → orchestrator **降级走正常新建任务路径**。消息不丢、用户有进度、无错误态 |
| 超长合并 | `_merged` 超 `project_context_max_chars` **尾部截断** + `logger.warning`（diff 见 6.2） |
| uid 缺失 | S1 元组后 uid 随消息同行；`uid <= 0` 时 `inject_message_to_task` **拒注入返回 False**（走降级新建任务），绝不重落库 |
| 归属竞态 | 任务在 bind 前结束 → UPDATE 影响 0 行 → `_bind_task_id` 记 warning，消息不丢（仍在会话可见）（diff 见 6.6） |

### 5.7 S7 测试层

`INJ-01` 扩充为 4 场景，全部真实 LLM：

| 场景 | 断言要点 |
|------|---------|
| 单条注入 | `merged` 事件 + `task_id` 已绑定 + DB **恰好 1 条**（`==` 而非 `>=`，抓重复） |
| 多条注入 | 合并为 1 轮 LLM 输入 + 渲染层 1 个 assistant（不重复）+ 旧锚不被覆盖 |
| 队列满 | 降级新建任务，消息不丢 |
| 刷新一致性 | `list_session_tasks.merged_inputs` 刷新后仍含注入消息 |

### 5.8 记录在案、本设计不修的既有缺陷

**orphan 溢出静默丢消息**：`_ORPHAN_MAX_ITEMS=100`，`_trim_orphaned_inbox`（`:67-71`）满时丢最老。DB 行仍在（会话可见）但**永不被任务吸收**，用户视角"发了没反应"。

属 orphan 机制范畴，超出注入缺陷范围。`INBOX_MAX=20` + 降级后进入 orphan 的量锐减，触发概率同步下降。

### 6.16 规范对照

| 规范 | 落地 |
|------|------|
| DRY | 落库单一来源；合并规则三处共用同一判定；`bind_message_to_task` 与 5.3 数据源解耦 |
| KISS-DIRECT | 零 DDL（复用 `task_id` 列 + 既有 JOIN）；不新增视觉层级；降级优先于报错 |
| YAGNI | 不建新表、不加 JSON 列、不引入配对策略配置项 |
| SLAP | 传输/归属/展示/事件/健壮/测试 六层职责不混搭 |
| 禁止 backward | 6.2 删 tuple 兼容分支（含 orphan），不留双形态 |
| 复用优先 | `CollapsibleText` 折叠块、`stepFilter` 分流、既有 JOIN 与 `update_user_message_final` 全复用，零新组件 |
