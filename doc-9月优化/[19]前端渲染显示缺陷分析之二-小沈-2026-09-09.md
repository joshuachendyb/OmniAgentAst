## 一、概要

任务1（执行面板冻结约20秒）和任务2（HITL恢复后步骤静默）两个问题，经代码核验判定**都是前端问题**，后端无问题。

| 问题 | 病根 | 确定性 | 核心机制 |
|------|------|--------|---------|
| 任务1 | saveStepsToStorage 同步写 sessionStorage 阻塞主线程 | **确定** | 每个SSE事件排队 setTimeout(0) 宏任务，依次同步阻塞，React 渲染被推迟 |
| 任务2 | HITL paused/resumed 缓冲与 setExecutionSteps 不同步 | 需验证 | 任务2有 HITL 暂停（任务1没有），解释"第一次出现" |

**关键修正**：
- 任务1 **与429无关**（用户明确质疑[17]此结论），正常任务 steps 累积大就触发，故反复出现。
- [13]修复**已落码**（useTaskInfo.ts:203），但只解决 badge 状态问题，**未解决主线程阻塞**，故问题反复出现。
- 12环节静态核验（执行面板20秒冻结文档）的盲区是**运行时主线程阻塞**，被"setTimeout 延迟保存，不阻塞 UI"的注释误导。

## 五、静态核验的盲区：运行时主线程阻塞

12环节静态核验逐环"证死"，但静态核验只能证明**代码路径正确**，无法证明**运行时主线程不被阻塞**。

实际阻塞点在 `saveStepsToStorage` 的同步写入。静态核验时被 sseParser.ts:380 注释"【小强修改 2026-04-10】使用 setTimeout 延迟保存，不阻塞 UI"误导，未深入验证 setTimeout(0) 的实际行为——**setTimeout(0) 不消除阻塞，只推迟到下一个宏任务**。

## 六、病根A：saveStepsToStorage 同步阻塞主线程（任务1，确定）

### 6.1 代码链

**sseParser.ts 三处同构**（thought/action/observation）：

| 分支 | 行号 |
|------|------|
| thought | sseParser.ts:377-389 |
| action | sseParser.ts:681-693 |
| observation | sseParser.ts:830-842 |

每处结构（以 thought 为例）：
```ts
setExecutionSteps((prev) => {
  const newSteps = [...prev, step];
  handlers.executionStepsRef.current = newSteps;
  setTimeout(() => {              // ← 排队宏任务
    saveStepsToStorage?.(newSteps); // ← 同步阻塞
  }, 0);
  return newSteps;
});
onStep?.(step);
```

**useSSE.ts:481-493 saveStepsToStorage 定义**：
```ts
const saveStepsToStorage = useCallback((steps: ExecutionStep[]) => {
  if (steps.length > 0 && config.sessionId) {
    const storageKey = `${SSE_STORAGE_KEY}_${config.sessionId}`;
    sessionStorage.setItem(storageKey, JSON.stringify(steps)); // ← 同步阻塞
  }
}, [config.sessionId]);
```

### 6.2 阻塞机制

1. **`JSON.stringify(steps)`**：steps 为全量累积步骤，round5 已累积数十步，每步含 thought/action/observation/tool_params/tool_result 等大字段，序列化耗时数十ms~数百ms。
2. **`sessionStorage.setItem`**：同步写 Storage，大字符串写入耗时数ms~数十ms。
3. **`setTimeout(0)`**：不消除阻塞，只推迟到下一个宏任务。sseParser.ts:380 注释"延迟保存，不阻塞 UI"是误解。

### 6.3 冻结过程

1. 后端连续发射多个SSE事件（如 round5 的 thought/action/observation/...）。
2. useSSE.ts:794-828 读取循环 `for (const line of lines)` 同步处理每个事件。
3. 每个事件调用 `setExecutionSteps(updater)`，updater 内排队一个 `setTimeout(0, saveStepsToStorage)` 宏任务。
4. N个事件 → N个 setTimeout(0) 宏任务排队。
5. React 18 自动批处理合并 setExecutionSteps，调度渲染（异步，用 MessageChannel）。
6. 但 N个 setTimeout(0) 宏任务在渲染前依次执行，每个同步阻塞主线程。
7. 且每次 newSteps 递增（`[...prev, step]`），第 N 次序列化全量 N 步，阻塞随 N 增大。
8. 总阻塞 ≈ Σ(每次 JSON.stringify 时间)，steps 线性增长时约 O(N²)，可达数秒~20秒。
9. React 渲染被推迟到所有宏任务执行完 → UI 冻结 + 齿轮停转。
10. console.log 被主线程阻塞节流 → 日志不完整。

### 6.4 解释所有现象

| 现象 | 解释 |
|------|------|
| 冻结约20秒 | N个宏任务依次阻塞，总时长≈20秒（steps越大越长，O(N²)增长） |
| 齿轮停转 | React 渲染被推迟，CSS 动画帧不更新 |
| console.log 不完整 | 主线程被阻塞，console.log 被节流/推迟 |
| 整批显示 | 渲染被推迟到最后一次性完成 |
| 反复出现 | 任何任务 steps 累积大就触发，与429无关 |
| 与429无关 | 阻塞源在前端 saveStepsToStorage，非后端429 |

### 6.5 为什么[13]修复后仍反复出现

[13]修复（useTaskInfo.ts:203）解决的是 **badge 状态问题**（idle→running），让 RightViewer.isCurrentLive 保持 true，不停齿轮、不切历史视图。

但[13]修复**未触及 saveStepsToStorage 的主线程阻塞**。即使 isCurrentLive 保持 true，主线程仍被 N个 setTimeout(0) 宏任务阻塞，React 渲染仍被推迟，UI 仍冻结。

故[13]修复后，"切历史视图"症状消失，但"冻结+整批显示"症状仍反复出现。

## 七、病根B：HITL paused/resumed 缓冲与 setExecutionSteps 不同步（任务2，需验证）

### 7.1 初步分析

任务2有 HITL 暂停（任务1没有），这是"第一次出现"的关键差异。

HITL paused 期间，后端暂停发射 step。resumed 后，后端重发。前端 onResumed（useChatCallbacks.ts:680-745）回放缓冲区，但缓冲区回放与 setExecutionSteps 的时序可能不同步，导致步骤静默。

### 7.2 待验证点

- 回放步骤是否被 onStep 指纹去重（useChatCallbacks.ts:150-166）误杀？
- paused 期间 executionStepsRef.current 是否被清空？

## 八、解决方法

### 8.1 病根A修复（saveStepsToStorage 防抖+非阻塞）

**方案**：saveStepsToStorage 改防抖，合并连续事件，只保留最后一次保存，避免每个事件都同步阻塞。

**useSSE.ts saveStepsToStorage 改造**：
```ts
const saveTimerRef = useRef<number | null>(null);
const saveStepsToStorage = useCallback((steps: ExecutionStep[]) => {
  if (steps.length === 0 || !config.sessionId) return;
  // 防抖：取消上次未执行的保存
  if (saveTimerRef.current !== null) clearTimeout(saveTimerRef.current);
  saveTimerRef.current = window.setTimeout(() => {
    const storageKey = `${SSE_STORAGE_KEY}_${config.sessionId}`;
    try {
      sessionStorage.setItem(storageKey, JSON.stringify(steps));
    } catch (e) {
      console.warn('[SSE] 保存失败:', e);
    }
    saveTimerRef.current = null;
  }, 300); // 防抖300ms，合并连续事件
}, [config.sessionId]);
```

**sseParser.ts 三处改造**：去掉外层 setTimeout(0)，直接调 saveStepsToStorage（防抖已在内部处理）：
```ts
setExecutionSteps((prev) => {
  const newSteps = [...prev, step];
  handlers.executionStepsRef.current = newSteps;
  saveStepsToStorage?.(newSteps); // ← 防抖内部处理，不阻塞
  return newSteps;
});
```

**效果**：N个事件只触发1次 setTimeout(300)，只序列化1次全量 steps，阻塞从 O(N²) 降到 O(1)。
