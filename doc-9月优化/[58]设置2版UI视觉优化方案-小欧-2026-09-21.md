## 一、总评

设置2版功能与结构已完成且健壮（见 [57] 核对报告），但**视觉层存在 23 处可优化点**：9 处硬编码违反 stepStyles 令牌铁律（含功能缺失 P0-9）、5 处交互反馈与结构一致性、9 处体验打磨，外加弹窗统一视觉规范与 8 条优化（第六章）。整体为"工程可用、视觉未精修"状态，按 P0→P1→P2 优先级收敛即可达到与主会话页一致的视觉水准。

**分级标准**：
- **P0**：硬编码色值/字号/宽度，违反 `stepStyles` 令牌铁律（[54] 7.9），必须令牌化，机械替换零风险；
- **P1**：交互反馈缺失（搜索未命中、高亮不消退、计数缺失等）与结构一致性（DRY 缺口），影响操作正确性感知与维护性；
- **P2**：视觉体验打磨（层级、间距、风格统一），锦上添花。

## 二、P0 — 硬编码令牌化（9 处）

### P0-1 页面/保存条背景硬编码 `#fff`【4 处】

**现状**：
- `SettingsPage.tsx:67`（loading 态）、`:77`（error 态）、`:239`（正常态）均 `style={{ padding: settingsSpacing.pagePadding, background: '#fff' }}`
- `SaveBar.tsx:49` sticky 条 `background: '#fff'`

**优化原因**：`#fff` 是主背景语义色，全项目统一入口为 `Colors.BG.PRIMARY`（stepStyles.ts:124）。硬编码后若全局改主背景（未来深色模式/主题切换），这 4 处会漏改产生色斑。与 [54] 7.9"不硬编码色值"铁律冲突。

**优化方案**：统一改为 `Colors.BG.PRIMARY`（4 处）。`SaveBar.tsx` 当前已 import `Colors`（用于 borderTop），直接复用 `Colors.BG.PRIMARY` 即可，无需新增 import。

**预期效果**：无可见变化（现值即等于 token），但消除未来主题迁移断点，符合令牌独一原则。

|---|---|---|

### P0-9 "添加 Provider"弹窗缺 API Key 输入框（功能缺失，2026-09-21 北京老陈发现）

**现状**：`ModelModals.tsx:83-111` "添加 Provider"弹窗仅 3 字段：名称（`name`）、显示名（`label`）、API 地址（`api_base`）。**无 API Key 输入框**。后端 `POST /providers`（model.api.ts:95-102）也仅接受 `{name, label?, api_base?}`——同样缺 `api_key` 字段。用户创建 Provider 后必须再到③Provider配置区（ProviderConfig.tsx:67-82）单独填 API Key 并保存，否则模型调用静默失败（无明确报错）。

**优化原因**：API Key 是 Provider 调用 LLM 的**必要条件**，创建时不给入口 → 用户创建完忘配 → 模型调用静默失败 → 体验极差。且"先创建再配置"两步操作违背 KISS-DIRECT 原则——添加 Provider 是低频操作，一步到位更合理。

**优化方案（需前后端同步改）**：
1. **后端**：`POST /providers` 扩 `api_key?: string` 字段，收到时写入 config（与 `PUT /providers/:name` 的 api_key 处理逻辑复用）；
2. **前端**：`ModelModals.tsx` 添加 Provider 弹窗增 `api_key` 字段（`<Input.Password>`），与 ProviderConfig:67-82 保持同一视觉语法（label="api_key"、extra 提示、placeholder）；
3. **契约**：`model.api.ts` `addProvider` 参数扩 `api_key?: string`。
   > 衔接 V-1/P2-7：api_key 三态语义（留空=保持/填值=覆盖/clear=显式清空）在添加弹窗中简化为"填值=设置/留空=未配置"（无"保持"概念，因为是新建），与 ProviderConfig 的三态保持语义一致。

**预期效果**：创建 Provider 时一步完成名称+地址+密钥配置，创建即可用；消除"创建后忘配 API Key → 模型调用失败"的静默断点。

## 三、P1 — 交互反馈与结构一致性（5 处）

### P1-1 搜索无命中时零反馈

**现状**：`SearchBox.tsx:16-28` 的 `jump()` 遍历 schema，命中即 `onJump` 返回；**未命中时静默结束**，用户回车后页面毫无反应。

**优化原因**：用户输入一个不存在的关键词（如 `tttt`）回车，以为搜索坏了或无结果。无"未命中"提示是交互盲区，违反"操作必有反馈"的 UX 铁律。

**优化方案**：给 `jump()` 加命中标志：
```tsx
const jump = (q: string): boolean => {
  const text = q.trim().toLowerCase();
  if (!text) return true;
  for (const [g, grp] of Object.entries(schema)) {
    const hit = grp.items.find(
      (i) => i.key.toLowerCase().includes(text) || i.label.includes(q.trim())
    );
    if (hit) {
      onJump(g as TabKey, hit.key);
      return true;
    }
  }
  showMessage(ErrorType.INFO, '未找到匹配的设置项');
  return false;
};
```
`SearchBox.tsx` 补 import `showMessage, ErrorType`（注意仓库 lint `no-restricted-syntax` 禁 `message.*` 直调，必须走 errorHandler）。

**预期效果**：命中→切 Tab+高亮（既有一致行为）；未命中→1 条 INFO 提示"未找到匹配的设置项"，消除盲操作。且 `onChange` 不触发提示（保持现有机制：仅回车提交时触发一次），不打扰输入过程。

### P1-2 搜索高亮永不消退

**现状**：`SettingsPage.tsx:51-54` `jumpTo()` 调用 `s.setHighlightKey(key)` 后，`highlightKey` 无任何自动清除机制（`useSettings.ts:91` 独立 state，仅在 `saveKeys` 校验失败时被覆盖）。`SettingRow.tsx:205` 据此 `background: chatTokens.colorPrimaryBg` 常亮。

**优化原因**：一次搜索后的高亮蓝底**永久停留**，变成视觉噪声，且用户无法区分"当前是哪次搜索命中的"。高亮是"指针"不是"常驻标记"，必须有生命周期。

**优化方案**：在 `SettingsPage.tsx` 加自动消退定时器：
```tsx
const [highlightKey, setHighlightKey] = useState<...>(s.highlightKey);
// 或更优：在 useSettings 内封装带 TTL 的 setHighlightKey
```
推荐在 `useSettings.ts` 内新增封装（DRY，所有入口统一 TTL）：
```tsx
const HIGHLIGHT_TTL = 2000;
const setHighlightKeyTtl = useCallback((key: string | null) => {
  setHighlightKey(key);
  if (key) setTimeout(() => setHighlightKey(null), HIGHLIGHT_TTL);
}, []);
```
`jumpTo` 与校验失败场景统一走 TTL 版，并在 `SettingRow` 高亮时给背景加 `transition: background 0.3s` 实现淡出。

**预期效果**：搜索定位→蓝底高亮约 2 秒→自动淡出。高亮从"永久横幅"变为"瞬时指针"，用户随时能分辨"当前高亮=最近一次搜索目标"。

### P1-3 "保存本组"按钮缺本组待存计数

**现状**：`SaveBar.tsx:53-58` "保存本组"仅 `disabled={!canSaveGroup}`，无计数；顶部 `DirtyBadge`（SettingsPage.tsx:264）只显示全局数"有 N 项未保存"。

**优化原因**：顶部全局计数是"总账"，本组待存几项用户在点保存前不可见，与右侧"保存全部（N 项）"（SaveBar.tsx:67 已带全局计数）不对称。信息层级不完整。

**优化方案**：`SettingsPage.tsx` 计算当前组待存数并下传：
```tsx
const groupDirtyCount = state.activeTab === 'model'
  ? (state.model.isDirty ? 1 : 0)
  : Object.keys(state.dirtyKeys).filter((k) => s.groupOfKey(k) === state.activeTab).length;
```
`SaveBar` 增加 `groupDirtyCount: number` prop，按钮文案改为 `保存本组${groupDirtyCount > 0 ? `（${groupDirtyCount} 项）` : ''}`，并复用 `disabled={!canSaveGroup}`。

**预期效果**：`保存本组（3 项）` / `保存本组`（无脏项置灰）与右侧 `保存全部（5 项）` 形成对称信息结构：顶部见全局账、本组按钮见本组账、全部按钮见全局账，三级计数齐备。

### P1-4 参数区"重置为默认"按钮悬空无间距

> **功能语义说明（2026-09-21 10:02 北京老陈提问后补充，供理解本项背景）**：
> 此按钮 = "撤销本组未保存的修改"——把 ② 参数区全部滑块/数字框一键恢复为 `defaults`（配置文件 `ai.{provider}.model_params.{model}` 中本次加载的基线值，由 `GET /models` 的 `default_params` 提供，useSettings.ts:135-139）。`resetParams = patchModel({ params: {...state.model.defaults}, isDirty: false })`（useSettings.ts:495）。**注意：它不是"恢复厂商出厂默认"，而是"回到上次保存/加载的状态"**——点"保存本组"成功后 `defaults` 会被更新为刚保存的值（useSettings.ts:350），基线随之抬升。使用场景：拖乱多个参数想全部放弃、切换模型（BUG-D）前不想保留乱改值时一键回退。属低频但语义明确的"撤销"入口，功能本身合理。

> **顺带发现的新瑕疵（2026-09-21 10:02，P1-4 实施时一并处理）**：
> ① 模型无 `model_params`（config 中该模型参数区为空 dict）时参数行零渲染，但"重置为默认"按钮仍孤立显示在下方（ModelParams.tsx:79 不在 map 内）→ 空参数区挂无用按钮；
> ② 按钮无 `disabled`——无脏态时也可点（点击无任何变化）。建议：无参数时隐藏按钮；有参数但无脏态时置灰。

**现状**：`ModelParams.tsx:79` `<Button onClick={confirmReset}>重置为默认</Button>` 紧贴最后一个参数行，无上间距。

**优化原因**：与 ①②③④ 区块分层（SettingsPage.tsx:120-148）对比，重置按钮与参数行同层粘连，视觉上"分不清是参数还是操作"。操作区职责应独立。

**优化方案（定案 = 方案 B，2026-09-21 09:33 北京老陈拍板）**：把"重置为默认"上移至 ② 参数区标题行右侧（右对齐小字链接），标题行双端对齐：左"② 参数区"，右"重置为默认"。操作与区块标题关联，视觉归属感更强。

具体落地：
1. `SettingsPage.tsx:109-111` ② 区块标题行改为 `display: flex; justifyContent: space-between; alignItems: center`，左文案"② 参数区（跟随当前模型）"、右放 `<Button type="link" style={{ padding: 0 }} onClick={() => s.resetParams()}>重置为默认</Button>`；
2. `ModelParams.tsx` 移除 `:79` 的尾部"重置为默认"按钮（职责上移到标题行）；
3. 标题行高度随 P0-5 用 `FontWeight.BOLD` 字重令牌，右按钮用 `Colors.TEXT.SECONDARY` 次要色，主次清晰。
> 衔接 P2-1：本方案与 P2-1（四区块标题改 SectionTitle）**互不冲突**——仅 ② 标题行保留右侧"重置为默认"链接，①③④ 标题保持纯文本 SectionTitle；② 的标题文案建议直接用 SectionTitle 文本节点承载（见 P2-1 落地注释），由 SectionTitle 统一字重/间距，右按钮浮在同行右端。

**预期效果**：重置操作悬于区块头右侧、与"② 参数区"块标题强关联，参数区主体保持纯列表零操作干扰；操作定位从"找按钮"变为"区块右上角即操作"。

### P1-5 参数区与设置区两套并行列表样式（DRY 缺口）

**现状**：`SettingRow.tsx:198-229` 与 `ModelParams.tsx:39-77` 各自实现"标签列 + 控件 + 辅助说明 + 脏标记"的行布局：行高 44、标签宽 132、滑块宽 160、辅助灰字、脏点——样式语义几乎一致但**零共享**。`ModelParams.tsx:46` 还硬编码 `minHeight: 44`（对应应复用 `settingsSpacing.rowHeight`）。

**优化原因**：违反 AGENTS 铁规 DRY。两列表并行演进必造成视觉漂移（如先调了设置行、忘调参数行），且每处重复都是后续令牌化的漏网点。

**优化方案**：
1. `ModelParams.tsx:46` 的 `minHeight: 44` 改 `settingsSpacing.rowHeight`；
2. 提取共用"参数行外层容器"常量到 `settingsTokens.ts`（只增派生常量；**禁止在常量体内再写死数值，全部引用既有 token**，否则与第 1 条自相矛盾、与 P0-7 重复定义）：
   ```ts
   export const settingsRowLayout = {
     display: 'flex',
     alignItems: 'center',
     minHeight: settingsSpacing.rowHeight,   // 44
     labelWidth: settingsSpacing.labelWidth, // 132（P0-7 已定义，勿重复）
     gap: Spacing.MD,                        // 8
   } as const;
   ```
3. `SettingRow.tsx` 与 `ModelParams.tsx` 均改用 `settingsRowLayout`，行分割线统一 `Colors.BORDER.LIGHT`（SettingRow 已用、ModelParams 补 1px 下边框可选）。
   > 衔接 P0-6：settingsRowLayout 的 `labelWidth` 必须引用 `settingsSpacing.labelWidth`（P0-7 定义的那一个），不得新造 `labelWidth: 132`，否则出现两个同值常量（违反 DRY-DRY、给后续视觉漂移留第二次口子）。

**预期效果**：设置行与参数行共享同一布局 token：行高、标签列、控件间距、分割线全对齐；未来任一行视觉微调动一处、两区同步。参数区与设置区视觉合一，模型 Tab 与其余 Tab 的"行"透过同一网格。

### P2-1 模型 Tab 四区块与其余 Tab 小节风格割裂

```tsx
<SectionTitle title="── ① 选择器 ──" />
<SectionTitle title="── ② 参数区（跟随当前模型） ──" />
<SectionTitle title="── ③ Provider 配置 ──" />
```

**预期效果**：全页六个 Tab 区块标题同一视觉文法；模型 Tab 从"临时页面感"升级为"正式设置分区感"；用户心智一致。

### P2-3 sticky 保存条无浮起层级

**现状**：`SaveBar.tsx:43-51` sticky 条仅 `borderTop: 1px solid Colors.BORDER.LIGHT`，内容滚动时按钮紧贴内容、无浮起感。

**优化原因**：sticky 的作用是"内容滚动时保存操作始终可见"，但仅靠 1px 浅边线，视觉上分不清"条与内容"的层次，滚动到长列表时按钮仿佛嵌在内容里。

**优化方案**：给 sticky 条补轻投影 + 更高层级：
```tsx
boxShadow: '0 -2px 8px rgba(0, 0, 0, 0.06)',
zIndex: 10,
```
白底 + 上投影形成"浮起平台"层级。
> 合规提示（三思三省遗留）：`rgba(0,0,0,0.06)` 属**值域型投影色**（半透明黑 + alpha），不是 `stepStyles` 里的语义色（solid hex），P0 令牌铁律针对的是 `Colors.*` 语义色，此处新增投影不违反令牌铁律。但为杜绝"新增即散落"，落地时把投影值并入 `settingsTokens.ts` 一处导出（如 `export const settingsShadow = '0 -2px 8px rgba(0, 0, 0, 0.06)' as const;`），SaveBar 引用之——与 P1-5 的 settingsRowLayout 同策略：**新常量统一收口、禁再散落**。

**预期效果**：滚动时长列表从浅色内容过渡到白色保存条有明确"浮起"视觉断点，保存操作区始终高可扫视，是设置页最常用的操作锚点。

### P2-5 外观预览小卡密度切换无感

**现状**：`SettingsGroup.tsx:45-63` 预览小卡只渲染"当前密度"单一样例（`padding: density === 'compact' ? 4 : 12`）。

```tsx
<div style={{ display: 'flex', gap: Spacing.MD, alignItems: 'flex-start' }}>
```

受控值（fontSize）同步两态显示。

**预期效果**：密度切换时用户直接看到"紧凑=小间距、舒适=大间距"的**左右对照**，感官差异立刻可辨；预览从"确认自己改没改"变成"确认改成什么样"。

**设计方案（新版 Modal，5 块结构）**：

```
┌─ 查看 Modal ────────────────────────────────────────────┐
│ Header: [FileText图标] config.yaml           [×关闭]    │

│ │  1 │ server:                                        │  │
│ │  2 │   host: 0.0.0.0                                │  │
│ │  … │                                                │  │
│ └───────────────────────────────────────────────────┘   │

└─────────────────────────────────────────────────────────┘
```

1. **Header**（Modal title 定制）：左侧文件图标 + 文件名（`config.yaml` / `version.txt`）+ 其次行小字完整路径（`Colors.TEXT.SECONDARY`）；右侧默认关闭按钮。标题层级、字号走 `FontSize` 令牌。
2. **元信息条**（Header 下横条）：行数 / 大小 / 更新时间 / "只读"徽标，`display:flex; gap` 排开，`Colors.BG.TERTIARY` 底 + 圆角，次要色文字——一眼给专业信息量。
3. **正文行号区**：外层 `display:flex` 两栏——左栏行号 `<pre>`（`Colors.TEXT.SECONDARY`、`text-align:right`、`user-select:none`），右栏内容 `<pre>`（保持现有 preStyle 等宽 CODE 字号 + VERTICAL 边框 + 过滚动）；两栏行高一致（`lineHeight: 1.7`）保证逐行对齐；外层 `maxHeight: 60vh; overflow:auto`，滚动条样式走系统但整体圆角边框收边。

   - 加载中：Modal 内 `Spin` 居中 + "正在读取文件…"（防白屏，当前仅按钮 loading、正文空白）；
   - 读取失败：Modal 内错误横幅（`Colors.ERROR` 系）展示 `showMessage` 文案 + 可选"重试"按钮（当前失败直接关 Modal，信息一闪而过 → 应保留在 Modal 内展示错误细节）。

**后端配套扩展（需 2 处 + 契约）**：
- `config_service.py` `read_config_file`（:389-396）与 `read_version_file`（:399-407）：返回体分别在现有键上扩字段——配置文件 `{config_content}` 扩为 `{ config_content, path, size, lines, mtime }`、version 文件 `{version_content}` 扩为 `{ version_content, path, size, lines, mtime }`（`path=str(路径)`、`size`/`mtime` 取自 `Path.stat()`、`lines=content.count('\n')+1`）；

- 兼容性：两端点返回体**只增字段不删字段**（`config_content` / `version_content` 键名不变），若前端未升级字段也无破坏——纯增量契约。

**验证清单**：打开两文件 Modal——元信息条数值与实际文件一致；行号与内容逐行对齐；长文件（version.txt 若干百行）滚动流畅不卡顿；字体中文正常；复制全文仍可用；模拟失败路径（文件被删）展示 Modal 内错误态而非直接关闭。

**预期效果**：查看页从"白底大字纯文本"升级为"专业只读文件视图"，元信息/行号/加载/错误态齐全，与主会话页视觉水准一致——作品级，非 demo。

## 五、"当前生效模型"（YAML 顶层 ai 块）高占位 UI 设计（新增章节，2026-09-21 北京老陈提出）

> 本章针对北京老陈发现："配置文件顶部的 `ai: provider/model`（当前模型）在设置页面没有体现"。经源码级研究确认：它**不是单个厂商或模型的配置，而是全局"当前生效模型"（全局默认模型）**，且背后有一套"缺失→静默兜底推荐"机制完全未被 UI 表达。本章给出全面的高占位设计。

### 5.1 语义澄清：ai 块到底是什么（研究结论）

配置文件顶部：
```yaml
ai:
  provider: agnes
  model: agnes-2.0-flash
```
- **正式标签**：全局"当前生效模型"／"全局默认模型"。代码中 = `ai.model_ref`（registry 键，`settings_registry.py:33`，type=`model_ref`，label=`"当前模型"`），前端契约 = `GET /models` 返回的 `current_model_ref: ModelRef{provider, model}`（`model_service.py:104`；`useSettings.ts:128` 读取 `models.current_model_ref ?? null` 并存为 state 的 `currentRef`，:147）。
- **它不是某个厂商的配置**：真正的厂商配置在 `ai.agnes:` 这类同名子块（含 api_key/api_base/models[]）。`ai:` 顶层 `provider` + `model` 两行是**整个系统当前用哪个模型的"总开关"**，运行时由 `resolver.resolve_model_ref()`（`resolver.py:87-100`）消费生成全局默认 LLM 客户端。

### 5.2 现状缺口：三态语义完全没表达（核心问题）

后端 `model_service.get_current_ref`（`model_service.py:57-64`）已有完整的"缺失→兜底"收敛逻辑，但**前端只有"正常态下拉"一种表达**：

| 配置文件状态 | 后端行为 | 当前 UI |
|---|---|---|
| `ai.provider`/`ai.model` 有效且模型在列表 | 用显式值 | 模型 Tab 下拉可见（但无"全局默认"认知） |
| **ai 块缺失 / provider 或 model 不在列表** | **静默兜底到第一个可用 Provider 的第一个可用模型**（`model_service.py:61-63`） | **毫无提示**——用户不知当前生效的是谁、为什么是它 |
| 无任何可用 Provider | 空 / 报错 | 无专门表达 |

即：**系统背地里已用"推荐替身"在干活，设置页对此零表达**。同时 `ai.model_ref` 在设置行里从未以"设置条目"形态露过面——model 组整组被 `renderModelTab()` 接管，`SettingRow.tsx:180` 的 `case 'model_ref'`（"由模型 Tab 选择器管理"）是死代码。用户"没看到"是事实。

### 5.3 位置定案：模型 Tab 顶部 0 号状态区（主位）+ Tabs 上方轻量常驻小字（辅位）

**主位：模型 Tab 顶部，新增"当前生效模型"全局状态卡**（位于现有"① 选择器"区块上方，成为 Tab 首屏第一视觉）。
理由：
1. **它承载 ai 级 provider/model 的更换操作**——更换入口就在本 Tab 的①选择器，状态卡 + 一键跳转形成闭环；

3. 不跨 Tab 常驻大卡片（避免干扰其他 Tab 低频浏览），但用辅位轻量提示补齐"全局可见"。

**辅位：Tabs 标签栏上方一行极轻小字**："当前生效模型：agnes / agnes-2.0-flash"（可点跳模型 Tab；仅渲染 model_ref 简写，不抢视觉）。

## 七、附带的非纯视觉提醒（定案纳入本轮实施，2026-09-21 09:33 北京老陈拍板）

### V-1 base_url 留空即提交 `''` 覆盖（行为隐患）

**现状**：`ProviderConfig.tsx:35-38`
```tsx
if (values.base_url !== undefined) patch.base_url = values.base_url;
```
而 `api_key` 有"留空=保持原值"保护（`:35-36`）。base_url 表单留空会提交 `''` → 后端 `update_provider_config` 把 base_url 覆盖为空串。

**优化原因**：数据安全不对称——api_key "留空不改"，base_url "留空即清空"，用户在 Provider 表单里清空 base_url 想"不提交"会意外毁配置。与 [54] 8.2 数据安全契约冲突。

**优化方案（定案，纳入本轮实施）**：对齐 api_key 语义：
```tsx
if (values.base_url !== undefined && String(values.base_url).trim() !== '')
  patch.base_url = values.base_url;
```
范围裁定（KISS，防止过度设计）：
- 只做"留空=保持原值"，对齐 api_key 三态之一；
- **不做** base_url 的独立 `clear` 入口——api_key 的 `doClear` 模式保留专用于密钥；base_url 留空即保持已覆盖"误清"场景，显式清空 base_url 属极少用操作，暂不新增 UI（YAGNI）。

**预期效果**：留空=保持，与 api_key 语义一致，杜绝误清 base_url；不新增界面入口，改动面最小（单行条件）。
