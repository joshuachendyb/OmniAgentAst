## 一、问题描述

### 1.1 问题现象

在会话页面的 Step 实时输出过程中，**快结束时**经常出现以下现象：
1. **Response 内容显示太快**：长文本回复在任务结束瞬间整段瞬间显示，没有打字机效果
2. **页面不能自动滚动到底部**：滚动条停在页面中间，内容未滚到底部
3. **需要手动滚动**：用户需要手动向下滚动才能看到最新内容

### 1.2 复现特征

- **触发时机**：任务即将完成时，final 帧到达后的短暂窗口期
- **表现程度**：Response 内容越长（如长文本回复、分析报告等），问题越明显
- **持续时间**：从 final 帧到达至 final_stats 帧+REST 接口返回（约数百毫秒至数秒）

### 1.3 问题定位文件

| 文件 | 说明 |
|------|------|
| `frontend/src/features/chat/components/right/RightViewer.tsx` | 右侧查看区主体，滚动控制核心 |
| `frontend/src/tests/setup.ts` | 测试基建：ResizeObserver mock（本次需升级以支撑滚动单测） |
| `frontend/src/utils/viewState.ts` | `computeIsCurrentLive` 判定函数 |
| `frontend/src/features/chat/components/pipeline/TextStream.tsx` | 打字机效果渲染 |

## 二、问题的病根病因分析

### 2.1 根本原因：final 帧到达瞬间的「竞态窗口」导致 ResizeObserver 永久断开

这是一个**三个环节的时序错位问题**，当 final 帧到达时，三个异步环节的执行顺序不一致，导致滚动监听机制永久失效。

#### 环节一：`isCurrentLive` 翻转 → pipeline 卸载 → RO 断开

**时序**：
1. final 帧到达 → `_hasFinal = true`
2. `computeIsCurrentLive`（`viewState.ts:39-52`）返回 `false`（因为 `hasFinal=true`）
3. `isCurrentLive` 立即翻转为 `false`（**同步执行，在渲染阶段**）
4. 此刻 `settledSteps` 还是空的（快照 effect 是异步 state，晚一轮渲染）
5. `historySteps` 也是空的（REST 接口还没返回）
6. 条件 `!isCurrentLive && !loading && !hasSteps` 命中 → 渲染 **Empty 空态**（RightViewer.tsx 空态分支）
7. `pipelineEndRef` 从 DOM **卸载** → **ResizeObserver（RO）断开**

**关键代码**（修改前，RightViewer.tsx 主滚动 effect）：
```typescript
useEffect(() => {
  if (!isCurrentLive && !hasHistorySteps) return; // ← 守卫：final 到达时直接 return
  const container = findScrollContainer();
  const pipeline = pipelineEndRef.current; // ← pipeline 已卸载，为 null
  if (!container || !pipeline) return; // ← RO 永不挂载
  const ro = new ResizeObserver(scrollToBottomNow);
  ro.observe(pipeline); // ← 此刻执行不到
  // ...
}, [isCurrentLive, hasLiveSteps, hasHistorySteps, ...]);
```

#### 环节二：settled 快照恢复 → pipeline 重新挂载 → RO 没重新接上

**时序**：
1. 快照 effect 执行 → `setSettledSteps(snapshot)`
2. 重渲染 → pipeline 以**新 DOM 节点**重新挂载
3. 但滚动 effect 依赖数组仍是 `[isCurrentLive, hasLiveSteps, hasHistorySteps, ...]`，**没有 settledSteps**
4. 此时三个依赖相对 Empty 渲染时刻都没变 → **effect 不再重跑**
5. **RO 永不重新 observe 新节点** → 滚动监听永久失效

#### 环节三：直到 final_stats + REST 返回，才恢复滚底

**时序**：
1. `final_stats` 帧到达 → `hasFinalStats=true`
2. REST 拉取 effect 重跑 → `setLoading(true)` → 返回 → `setHistorySteps(steps)`
3. `hasHistorySteps` 从 `0→1` → 滚动 effect 重跑 → RO 重新挂载 → 滚动恢复
4. 但此时内容已经跳完，滚动条"卡在中间"的问题已发生

### 2.2 为什么 Response "显示太快"

在 settled 模式下（`isCurrentLive=false`），`TextStream.tsx` 走 `typing=false` 分支：内容整段瞬时显示（`setShown(clean.length)`），无打字机效果；`typing` 由 `PipelineRenderer` 的 `streaming`（=`isCurrentLive`）决定。

**结论**：settled 模式下 `typing=false`，内容整段瞬时显示，同时 RO 失效无法滚底，用户看到"内容狂涨但滚轮停在半空"。

### 2.3 问题时序图

```
时间轴 →

[Live 阶段]          [Final到达]       [settled生效]        [REST返回]
  ↓                     ↓                ↓                   ↓
RO 正常滚底      isCurrentLive=false   RO 断开             RO 恢复
  ↓                     ↓                ↓                   ↓
打字机逐字输出   pipeline 卸载(Empty)  pipeline 重挂载      滚动恢复
  ↓                     ↓                ↓                   ↓
内容正常滚动     RO 断开              RO 未重新挂载         滚动正常
```

**窗口期**：final 到达 → REST 返回（约数百毫秒至数秒），此窗口内滚动永久失效。

## 三、解决方案（唯一方案：方案一·持久锚点版）

> 方案已由北京老陈定案：**只保留此方案**，原方案二/三/四/对比已删除（v3.1）。

### 3.1 设计原理

#### 3.1.1 为什么原机制有3个控制条件（条件膨胀）

原滚动机制的主 effect 有 3 个控制条件：`isCurrentLive`、`hasLiveSteps`、`hasHistorySteps`，是**历史补丁越打越多导致的条件膨胀**：

| 时间 | 补丁原因 | 新增条件 |
|------|---------|---------|
| 最初 | 只有live模式才滚动 | `isCurrentLive` |
| 9月2日 | 修"切历史任务不滚" | 加了 `hasHistorySteps` |
| 9月6日 | 修"final后停半空" | 加了 `!isCurrentLive && !hasHistorySteps` 守卫 |
| 9月10日 | 修"settled快照不滚" | 应该加 `hasSettledSteps` 但没加 ← **就是这次漏了** |

**本质**：这些条件在控制"RO要不要挂载"，但 RO 的挂载/卸载时机管理混乱，每次状态变化都重挂载，最终遗漏边界情况。

#### 3.1.2 精简设计：RO常驻 + 只判断 userScrolledUp

滚动的本质是**内容增长时自动滚底**，不管内容来自 live、settled 还是 history；用户行为（上翻/不翻）才是控制滚底的唯一条件。

- 滚动机制只需要 **2 个信号**：`!userScrolledUp`（用户没手动上翻）+ `pipelineEndRef.current != null`（DOM节点在）
- **正确做法**：RO 从 pipelineEndRef 挂载起就一直 observe，直到组件卸载才断开

#### 3.1.3 持久锚点：补全设计洞（v3.0）

> 经测试资产实测复核，仅改 effect 的 deps 会让两条路径滚动失效：
> ①挂载即空态→选历史任务（RO 从未挂载）；②final 后 Empty→settled 重挂载（RO 观察旧孤儿节点）。
>
> **解法（D3）**：把 Empty 移入 `right-viewer-body` 内层，使滚动锚点 div **恒挂载**，RO 常驻观察此锚点，deps 才能真正只留 2 个。

#### 3.1.4 删除 2 个冗余变量（v3.1）

`hasLiveSteps`（仅被主滚动 effect deps 使用）、`hasHistorySteps`（仅被主/visibilitychange 两处守卫与 deps 使用）：方案一去守卫 + deps 简化后，二者成为死代码，**连声明一起删**。已实测：全前端测试零引用，删除零波及。

### 3.2 改动点一览（代码细节以第四章 §4.4 为唯一权威）

### 3.3 验证方法（5 项，实机手动）

1. **实时任务正常滚底**：启动实时任务，Step 输出时应自动滚到底部
2. **final 到达时不卡中间**：任务完成瞬间，滚动条应滚到底部，不再停在中间
3. **历史任务正常滚底**：切换到历史任务，Step 回放时应自动滚到底部
4. **用户上翻不打断**：实时任务运行时手动向上滚动，自动滚底应停止
5. **用户滚回底部恢复**：手动上翻后再滚回底部，自动滚底应恢复

### 3.4 风险评估

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| RO常驻导致不必要的滚底 | 用户上翻时被滚回底部 | 低 | `!userScrolledUp` 判断已覆盖 |
| 空态也渲染 body 容器 | E2E 读到的空态正文为"暂无执行记录" | 仅影响断言口径 | fre2e_05 用 `len>baseLen` 轮询，不依赖空串（§4.2） |
| visibilitychange 无守卫 | 切回可见时多余滚底 | 低 | `!userScrolledUp` 判断已覆盖 |

**整体风险**：低。简化后逻辑更清晰，反而减少出错概率。

### 3.5 回滚方案

1. 恢复 D0：重新加回 `hasLiveSteps`/`hasHistorySteps` 声明
2. 恢复 D1：主滚动 effect 加回守卫与 5 项 deps
3. 恢复 D2：visibilitychange effect 加回守卫与 3 项 deps
4. 恢复 D3：空态 DOM 结构还原为"Empty 或 body 二选一"（锚点不在空态挂载）
5. 恢复 D4：setup.ts RO mock 还原为 no-op（罗列于 §4.4.5 改前）
