## 二、SSE 链路现状

### 2.1 数据流（一次完整对话）

```
用户发送 → executeSend(useChatStreaming.ts:368)
  → useSSE.sendMessage(:1001) → sendMessageInternal(:644)
    → fetch POST /chat/stream + fetch/空闲 双超时
    → reader 循环 read() 断帧 buffer.split('\n')
      → 每行 processSSEData(sseParser.ts:68)   ← 解析分发（16 类 type）
        → onSeq(刷新 lastSeqRef 供重连续传) + switch 分派
        → 且遇错误→handleSSEError→reconnect(GET after_seq)= 重连续传
      → onStep/onChunk/onComplete/onError/onDenied…（useChatCallbacks.ts）
        → 指纹去重(:161) → displayBufferRef 暂停缓冲 → setMessages 更新消息区
  → RightViewer liveSteps=useSSE.executionSteps（实时）｜historySteps=REST（回放）
```

### 2.2 分层职责与已确认的优点

1. **连接/解析/回调/状态四层拆开**——每层有明确落点，历次 bug 修复（2026-08~09 共 30+ 条编辑历史）都能定位到具体函数，这是正确的演化方向。
2. **重连续传复用 GET after_seq**（`stream_orchestrator.py:435` `stream_reader` 按 seq 偏移读）——避免"双 agent/僵尸任务"，已根治 08-30 的重复起任务问题。
3. **取消/暂停/拒绝/错误各走各通道**（`user_rejected` 独立、`final+outcome=cancelled` 终态统一）——通道语义清晰。
4. **meta 帧（usage/stats/context_overview）与业务步骤分离**（`stepFilter.splitSteps`）——渲染分流干净。

## 三、后端事件契约核验（diff 可行性的前提）

本次优化方案均依赖以下后端契约，已逐一读码实锤：

| 契约 | 证据 | 说明 |
|------|------|------|
| **每个事件必带全局单调 seq** | `task_state.py:51` `step_dict["seq"] = len(self.event_log)` | `StreamBuffer.publish` 无条件打 seq |
| **重连续传只发增量** | `stream_orchestrator.py:443` `offset = after_seq` | `after_seq=N` 只续传 seq>N，同学重复在总线层被消除 |
| **同 seq 覆写仅在总线内，前端增量读不到两遍** | `agent_runner.py` 5.8.6 注释"短条覆写 publish 原位（保 seq）" | 覆写发生在事件缓冲，流读取端只读一次，故前端按 seq 单调去重安全 |
| **error 之后必有 final 兜底** | `step_emitter.py:53` `emit 记录 _last_error 供守卫填充 final` | 正常终止路径 error→final(outcome=failed)，但**断链时 final 可能到达不了前端**——这正是 O2 要兜底的窗口 |
| **final 携带 outcome/error_type/error_message** | `step_emitter.py:76` `emit_failed_final` | 前端 09-09 已补解析，契约稳定 |

> 结论：**前端用 seq 做消费侧单调守卫是安全且自洽的**——不会与后端的"同 seq 覆写"冲突。

### 五-1 O1【A1 修复】：解析层 seq 单调守卫（根治 liveSteps/sessionStorage 重复累积）

**问题本质**：sseParser 对同一行（异常重发/边缘重连）会无条件 `setExecutionSteps` + `saveStepsToStorage` + 回调；`useChatCallbacks.onStep` 的指纹去重（`:161-171`）只拦消息区 `message.executionSteps`，**拦不住 sseParser 侧的 executionSteps state / sessionStorage**——右侧面板 liveSteps 会重复。

**方案**：既然后端 publish 全事件带全局单调 seq，且增量续传不会让前端收到同 seq 两遍（见第三章），在 sseParser **switch 入口加一次 seq 单调守卫**：已消费 seq 的行整条跳过（不追加、不落库、不回调）。保留回调层指纹作为内容级兜底（防"总线级双发"意外），职责分明、零删除、零行为回退。

### 五-2 O2【B1 修复】：后端请求级错误终态幂等兜底（防 waitTimer/loading 悬挂）

**问题本质**：`useChatCallbacks.onError` 的 `from_backend` 分道（:572-583）"只清 refs、不停计时"，依赖隐式契约"随后必发 final"。但断链路径（重连 N 次失败 → 轮询 `pollSessionTaskStatus` 提前终态/超时收尾）时 final 到达不了前端，`executeSend` 启动的 `waitTimer`（每秒心跳打点）与 `loading` 永久悬挂，UI 冻住。

**方案**：仅对 **request_level=true（请求级 = 整个请求失败，step 原始为 0）** 的错误做幂等终态清理——清 waitTimer/loading/refs。执行级错误（`blocked`/`timeout`，任务仍在等 HITL 或继续）保持"等 final"原语义不动。**幂等性保证**：即使随后 final 到达，`onComplete` 会再次清计时（现有的二次清空对已清状态无副作用）。

### 五-3 O3【B2 修复】：暂停期同步累积 streamingContentRef（双内容源收敛）

**方案**：暂停分支补一行累积，与 responseBuffer 语义对齐。低风险加固。

### 五-5 O5【C1 优化】：移除 useChatFacade 巨型 useMemo 依赖清单

**问题本质**：`useChatFacade.ts:252-419` 手写 50+ 项依赖数组（2026-09-09 已加 `eslint-disable` 并注明"整体入 deps 会全量重建"）——每次新增/删除返回字段都必须同步改清单，遗漏即陈旧引用（stale closure），是真实的维护地雷。

**方案**：改为每次渲染直返对象（去掉 useMemo）。
- 优点：清单与返回体二合一，永不失步；底层各 hook（useChatCallbacks/useChatStreaming/useChatSession/useChatPersistence/useChatSend/useChatTaskControl）内部均用 `useCallback` 做了精确依赖，单字段引用稳定，**facade 外壳的对象身份变化不影响其正确性**。
- 成本：ChatPage 每次 render 时少量包装回调（如 `handleSendWithMode`，deps 引用 `chatSend` 对象）会重建——纯轻量渲染开销，无功能影响。

#### Diff 5.1 `useChatFacade.ts` — 移除 useMemo 包裹

```ts
//     [
//       // ===== 会话状态 =====
//       chatState.sessionId, ...
//       （50+ 项）
//     ]
//   );
// 改为：
  return {
    // ... 返回体原样，一行不动 ...
  };
```

具体操作：
1. 删 `return useMemo(\n    () => ({`，改为 `return {`。
2. 删除尾部整个依赖数组块（:357-417 的 `[`, 50 项, `]`）与 `,\n  );`，改为 `};`。
3. 删除 :356 的 `// eslint-disable-next-line react-hooks/exhaustive-deps -- facade单次组装...` 注释（不再需要）。
4. `useMemo` 若文件中无其他使用，同步删 import（当前还用于 `chatCallbacksWithError`，保留 import）。

> 若团队仍希望保留 memo 化以减小下游重渲染，替代方案是**把 chatState/chatStreaming 等各 hook 的返回值各自包 `useMemo`**，让 7 个 hook 对象身份稳定后，facade 依赖缩为 7 项——但需逐个改造 7 个 hook，本期列入 P2 一并评估。
