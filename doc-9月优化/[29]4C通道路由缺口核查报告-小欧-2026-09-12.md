## 摘要

本报告对 4C 改造（2026-09-06，commit `80bfec61f`，事件流由「yield 订阅」改为「publish 直写 event_log」）后，**原订阅体通道路由是否被完整迁移**进行了逐事件核查。

**核心结论（北京老陈 2026-09-12 指出，均已 git/代码实证）：4C 改造把「转发前处理」从订阅体拆走，却没有在 stream_reader 咽喉点原样重建，导致通道路由多类事件语义丢失。**

**实证版本基线声明（重要）：**
- **当前代码现状结论** 基于本地 HEAD `4bf3ea987`（2026-09-12）实读（文件均已标注行号）。
- **历史对比结论**（4C 前后差异、缺陷引入/修复时间窗口）基于本地 git 历史追溯：`80bfec61f~1`（4C 前）、`80bfec61f`（4C 本体）、`164465882`（09-11 修补）等**中间版本**。
- **当前 HEAD 仍然存活的缺陷仅 G2（final 完整条实时读走）；G1（thought 漏发）为 09-06~09-11 的历史缺陷，09-11 `_SSE_EXCLUDE_TYPES` 已修复（当前代码不再漏发）。**

已确认缺口（按「当前存活 / 历史已修复」分级）：
1. **G1（历史缺陷，09-11 已修复）**：thought 实时漏发 5 天（09-06~09-11）——本应「仅落库、绝不实时发」，被 publish 后由 stream_reader 原样转发给前端；`_SSE_EXCLUDE_TYPES={"thought"}` 至 09-11 才补上。**当前 HEAD 已挡实时，不再发生。**
2. **G2（当前存活缺陷）**：final 短信号失效——实时流拿到 publish 完整条（含 response），与 chunk text 段二次渲染 → 右侧正文重复。
3. **G3（设计隐患，持续存在）**：event_log 语义偏移——从「仅该发 SSE 的事件子集」变成「全量事件仓库」（含 thought/仅SSE 类），过滤点从生产端移到消费端但规则未迁移完整。

本文档仅核查与方案设计，**未动任何代码**。修复实施待老陈批准。

## 一、背景：4C 做了什么

### 1.1 改动范围（commit `80bfec61f` 实证）

| 文件 | 改动 |
|------|------|
| `react_loop.py` | `run_react_cycle` 由 async generator（yield 逐事件）改普通 async；10 处发射点位收口 `publish` |
| `react_step.py` / `react_dispatch.py` | 同机制改造：事件内部 publish |
| `agent_runner.py` | 消费改为「扫描 event_log 快照」走通道路由 |
| `base_agent.py` / `observation_builder.py` | 调整配套 |

**关键点：4C 未动 `stream_orchestrator.py`（stream_reader 所在），而 stream_reader 只做「按 seq 原样读 event_log → 转发」，无任何按类型的过滤。**

### 1.2 机制变更本质

| 维度 | 4C 前（订阅时代） | 4C 后（publish 时代） |
|------|------------------|----------------------|
| 事件产出 | run_react_cycle `yield` 逐条 | 全部 `_publish` 直写 event_log |
| SSE 转发源 | stream_reader 读 event_log（只有 `_append` 过的事件） | stream_reader 读 event_log（**全部** publish 事件） |
| 「谁进 SSE/谁进 DB」过滤点 | **生产端通道路由**（thought 只 `_persist` 不进 event_log） | 消费端：订阅体扫描管 DB + stream_reader 只管转发（**无过滤**） |

**核心偏移：过滤点从「写 event_log 时（生产端判定）」移到「读 event_log 时（stream_reader 判定）」，迁移时只补了 `thought` 一类，规则迁移不完整。**

## 二、通道路由设计原貌（4C 前，`§10.3.3(1) + §10.4.3 P1` 实证）

4C 前 agent_runner 订阅体路由原文（git show `80bfec61f~1` 实证）：

```python
if event_type == "thought":
    await _persist(event_dict)              # 仅落库（历史回放用，实时不重复发）
elif event_type == "thought-start":
    await _append(event_dict)               # 仅SSE（纯实时信号，不落库）
elif event_type == "chunk":
    await _append(event_dict)               # 仅SSE（纯实时逐字正文，不落库）
else:
    await _persist(event_dict)
    await _append(event_dict)               # SSE + 落库
```

设计语义（`steps/__init__.py:10` 注释）：**「ThoughtStep (仅落库)」**。

| 事件 | SSE | DB落库 | 载体/用途 |
|------|-----|--------|----------|
| thought | **不实时发** | 落库 | 历史回放推理显示 |
| thought-start | 实时发（仅SSE） | 不落库 | 等待光标信号（09-07 前） |
| chunk | 实时发（仅SSE） | 不落库 | 正文逐字流 |
| start / action / observation / final / final_stats | 实时发 | 落库 | 主流程 |
| error/usage/paused/resumed/retrying/cancelled | 实时发（仅SSE） | 不落库 | 通知类（P3/P5/P6） |

### 3.2 thought 漏发实证（历史缺陷，基于中间版本追溯）

- 4C 前（`80bfec61f~1`）：`thought → _persist` 只落库，**不 `_append` → 不进 event_log → stream_reader 读不到 → 不实时发**。
- 4C 后（`80bfec61f`~`164465882` 中间版本）：`react_step.py`/`handle_action.py`/`handle_answer.py` 三处 ThoughtStep 发射全部经 publish 进 event_log；当时 stream_reader 读 event_log 原样转发 → **前端实时收到 thought**（违反「仅落库」）。
- 补丁时间：`git log -S "_SSE_EXCLUDE_TYPES"` 唯一命中 **`164465882`（2026-09-11）**——即 09-06 到 09-11 期间 thought 持续实时漏发；**09-11 起当前代码已挡实时，缺陷关闭**。
- 影响：该 5 天窗口内实时 thought + 落库回放 thought 双通道重复推理显示（历史会话留痕，不可逆）。

### 3.3 final 短信号失效实证

- 4C 前：final 短信号在订阅体构造进 `_pending_terminal_events`，finally 里 DB status 落库后统一补发。
- 4C 后：final 完整条先由 `react_step` publish → stream_reader **实时读走完整条转发前端**；订阅体扫描构造的短信号只能 `finally` 覆写 event_log 原位（`agent_runner.py:648`）——**覆写晚于实时转发，实时流前端永远拿到完整条**。
- 影响：completed 实时帧带完整 response，与 chunk text 段二次渲染 → 右侧正文重复（09-12 前已多次复现认定）。

### 3.4 final_stats 转发路径实证（对齐确认）

`agent_runner.py:302-327` `_publish_final_stats`：

```python
await _persist(_fs_dict)      # 先落库(t3, append_step 落 chat_task_steps)
...
await _publish(_fs_dict)      # 后发布(t3')——publish 进 event_log → stream_reader 实时转发
```

**结论：final_stats 4C 后走 event_log 实时转发给前端，实时收发对齐 ✅。** 仅时序延后到任务收尾（finally 内 DB 落库后）——这是 09-11 [27] 方案刻意设计（消除「SSE final 先到、DB status 后到」竞态），非缺陷。

## 六、根因总结

**4C 把「转发前处理」（谁进 SSE、谁进 DB、谁短信号）从 event_log 生产端拆走，却未在 stream_reader（唯一咽喉点）原样重建通道路由，只留订阅空壳扫描。thought 漏发（历史已修复）与 final 完整条重复（当前存活）是同一处设计缺口的两个表现。**
