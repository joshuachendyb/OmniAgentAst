## 二、任务2 病根（P0）：终态切换抢跑 + 单次快照永不定

### 2.1 证据链（时间线对照）

后端（完整，终态failed/quota_exceeded）：
- 15:59:20 action_preview（shell）→ paused → 授权 → 15:59:22 resumed
- 15:59:42 action_canonical（shell）+ observation → thought-start → 15:59:43 final（step6）

前端console（完整，解析层无丢）：
- preview/paused/resumed/canonical/observation/thought-start/final 逐条 `[STEP]/[ACTION]收到数据`，`✅ AI流式完成` 执行

前端UI（缺失，定格）：
- 仅显示并行find组，step5-shell/step6-final 无渲染，任务统计卡 `executing`，此后永不变

### 2.2 病根：三段式因果链（已逐段源码实证）

**第1段（后端结构，诱因）——终态SSE恒先于DB落库**：
- `react_loop.py:195-196` final/final_stats 由循环内 `await _publish()` **直接写** `event_log`，不等待任何DB。
- DB侧是另一条异步消费链：`agent_runner.py:357` 每事件 `await db.atxn()` 逐条落库（线程跳转，天然滞后发布者）；终态 `update_task(status)` 更在 `finally:599-604` 里，排在守卫补发、`log_task_end` 之后。
- 结论：final到达前端的那一刻，DB里必然还没有终态status，steps也可能缺尾巴。**这是结构性的，不是偶发**。

**第2段（后端放大器）——大observation拖慢消费链**：
- step5-shell是 `E:\` 递归搜索，observation结果体巨大，该条 `append_step`（JSON序列化+SQLite写入）耗时远超常规毫秒级，消费链在此停顿。
- 发布者（react_loop）不受影响继续直发 thought-start → final。前端在停顿窗口内拉DB → 快照缺step5尾+step6。事发时A3的300ms缓冲（13:59已上线）仍被击穿，反证滞后窗口>300ms。

**第3段（前端病根）——切历史+单次快照+无重拉**：
- `RightViewer.tsx:125` `_hasFinal` 在final进liveSteps瞬间翻转 → `:285` `displaySteps` 由live切history（空）→ `:259-263` REST effect触发C1/C2。
- effect依赖 `[activeTaskId, sessionId, isCurrentLive, _hasFinal, serverTaskId]`（`:269`）——首快照返回后**没有任何依赖再变化**，永不重拉。partial快照即最终画面，"就停止了"。
- 渲染层无辜：`PipelineRenderer.tsx:170` 空thought不产段但不丢组；`stepFilter` 按到达序；state里有就会渲染。问题在state源切换，不在渲染。

### 2.3 病因一句话

前端用"终态到达"事件同时做了两件事——切历史视图 + 取DB快照，而DB在此时点按设计就没写完；且只取一次。**病根在前端，诱因在后端。**

### 2.4 解决方法（准确落码点）

**前端根治**（`RightViewer.tsx:217-269` REST effect）：
- 终态后改"单次拉取"为"终态就绪轮询"：每500ms重拉C1/C2，直至 `detail.status ∈ {completed,failed,cancelled}` **且** steps含与live终态同seq的final（与 `liveSteps` 对齐校验），或超时5s降级用live快照。
- 轮询期间**不切空**：`displaySteps` 保持liveSteps直到就绪（现`:285`三元是病根行），就绪再切。
- A3的300ms保留作首轮延迟，轮询是根治。

**后端加固**（可选，不阻塞前端修复）：
- `agent_runner.py:331` `_persist` 加try/except：单步落库失败记日志+继续消费，防消费链被一条坏数据打死（H2类隐患，本次事发无此迹象但链路无防护）。
- 判据：修完后复现429失败任务，右栏应先保持live尾帧、就绪后一次切全；刷新页面前后一致。

## 三、任务1 病根：后端LLM请求挂起（前端无辜，后到帧均正常显示）

### 3.1 证据链

- 15:46:08 thought5 → action_preview → action_canonical（15:46:09）→ observation（15:46:09）→ thought-start（15:46:09）→ **等待约10多秒（后端零SSE输出）** → final（failed/quota_exceeded，时间戳15:46:29）。
- **用户症状（北京老陈实证）**：thought-start后**等待约10多秒**，后端到达的 **action/observation/final 均正常显示**——前端不是"冻住20秒"，而是后端本轮LLM响应慢；后端一旦发出事件，前端逐帧正常上屏。
- 后端：15:46:29一次 `client_sdk.py:226` 429 → `llm_response_builder.py:99` error → `handle_answer.py:106` error → FAILED。**全程无retrying事件**，429只出现一次且handle_answer直接error——证明是**单次LLM尝试挂起约10多秒后429**，不是重试循环（重试会走 `base_service.py:422` L1通知→前端必见retrying）。
- 前端chunk分支 `sseParser.ts:394-395` 明确"精简日志：chunk不打印"——即使有chunk console也无痕；`onChunk`（`useChatCallbacks.ts:287`）直写`setMessages`实时渲染——UI有输入必有输出。
- 到达时间实证：thought/action/observation三者console时间戳同为15:46:08-09（**同一秒**），"action发出10秒才渲染"在到达层不成立；等待窗口内后端确实零输出，前端转圈是正确行为。

### 3.2 病因一句话

第6轮LLM请求在网关侧挂起约10多秒后返回429，期间后端无任何SSE可发（无chunk、无retrying），前端正确等待；后端发出的事件（action/observation/final）前端均正常即时显示，无"冻住"现象。**病根在后端可观测性缺口，前端行为正确。** 用户感知的"等待约10多秒"= 后端LLM响应慢 + 黑盒等待的叠加，事件一经发出即正常渲染。

### 3.3 解决方法（准确落码点）

**后端**（主）：
1. LLM首包看门狗：首token/首响应超阈值（如10s）发一次 `MetaStep(type="retrying"，content="模型响应较慢，等待中…")`，走现有retrying通道（`base_service.py:422` L1通知链路已通），终结黑盒。注意与真实重试文案区分。
2. 核实429分类与行为矛盾：`client_sdk.py:226` 标注"可重试"但实际未重试直接error——要么改标签（去"可重试"字样），要么真进L1重试。二选一，不含糊。

**前端**（取证能力，不改默认行为）：
- 加 `?verbose=1` opt-in全量SSE日志开关（含chunk计数心跳，如"chunk累计N字"每5s一条），默认关闭（保刷屏治理成果）。下次同类问题5分钟定位，不用猜。
