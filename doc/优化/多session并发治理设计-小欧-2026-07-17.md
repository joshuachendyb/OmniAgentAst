## 1. 全局并发模型详述

### 1.1 进程与并发形态（实测，非假设）

| 维度 | 现状 | 并发含义 |
|---|---|---|
| 部署 | 单进程 `uvicorn`（可能多 worker，但本设计按单 worker 内的协程并发建模；多 worker 下进程间本就隔离，问题更小） | 多个 session 的 HTTP 请求在**同一事件循环**内交错执行 |
| 调度 | `asyncio` 单线程事件循环 | 同一时刻只有一个协程在跑；**仅在 `await` 点让出** |
| 锁 | CPython GIL | 字节码级原子；**单个 dict/list 的单一操作（如 `d[k]=v`、`d.pop`）是原子的**，但"读-改-写"复合操作非原子 |
| DB | 同步 `sqlite3`，非 `aiosqlite` | DB 调用**阻塞事件循环线程**，期间所有协程被卡住 |
| 共享态 | 多处模块级单例/字典 | 跨所有 session 共享，是并发风险的总源头 |

### 1.2 原子性边界（决定哪些需要锁、哪些不需要）

- **安全（无需锁）**：单条 `dict[k]=v`、单条 `list.append`、模块级变量单次读取、无 `await` 的纯同步函数整体（asyncio 单线程下不会被打断）。
- **不安全（需锁或改结构）**：
  - "检查再行动"（check-then-act）：如 `if k not in d: d[k]=v`（两 session 同时越过 `if`，都写）。
  - 跨多个 `await` 持有可变字段：如 `self._cancelled=False` 在某协程设置，另一协程在 `await` 后读取，看到的是他人写的值。
  - 迭代同时修改：如 `for k in d:` 时另一协程 `d.pop(k)`（`RuntimeError: dictionary changed size during iteration`）。
  - 阻塞调用：同步 `sqlite3.connect` / `conn.execute` 跨 `await` 持续占用事件循环线程。

### 1.3 本设计据此划分风险等级

- **雪崩级（A1/A3）**：资源被并发打满或事件循环被阻塞 → 全体请求退化。
- **越权级（C11/C12/C13）**：一个 session 能操控另一个 session 的任务/HITL。
- **污染级（A7/B8/B9/发现A/发现B）**：跨 session 的数据串台、备份错乱、配置读空。
- **加固级（D14）**：共享字典并发增删，概率性异常。

## 4. Phase 0 风险点深度分析

### 4.1 A1 — LLM 连接池在并发下耗尽（雪崩级）

**① 触发时序**
- Session A、B、…、K 共 11 个请求同时到达 `3.1` 各取同一单例 `ai_service`。
- 各自 `4.4` 同时进入 `request_stream`，复用同一 `self._llm_sdk`（httpx.AsyncClient，连接池上限 10）。
- 第 11 个并发 LLM 调用向池借连接时池空 → `httpx.PoolTimeout` → 该任务失败，且可能因重试放大（A5）。

**② 代码实锤**
- `client_sdk.py:107-120`：`LLMClient` 内部 `httpx.AsyncClient(limits=httpx.Limits(max_connections=LLM_MAX_CONNECTIONS, ...))`，`LLM_MAX_CONNECTIONS=10`（`constants.py:76`）。
- 因 `get_service()` 单例（`service.py:112` `_instance = create_service_instance(...)`），**所有 session 共用这 1 个池**，全局上限 10。

**③ 根因机制**
并发 LLM 调用数 = 并发 agent 数（ReAct 循环内 LLM 调用串行，但跨 session 并行）。当并发 agent > 10，池借空。连接池本身无外部排队，直接抛 `PoolTimeout`。

**④ 危害**
批量并发时大量任务以 `PoolTimeout` 失败；失败触发重试（A5）进一步加剧池争用，形成雪崩。

**⑤ 分步修复**
- 新增 `app/services/concurrency/governor.py`（详见第 10 章 P0-1），`global_sema = asyncio.Semaphore(MAX_CONCURRENT_AGENTS)`。
- `constants.py` 增 `MAX_CONCURRENT_AGENTS = LLM_MAX_CONNECTIONS`（=10），`MAX_CONCURRENT_PER_SESSION = 3`。
- `openai.generate()` 在 `3.4` 处 `await get_governor().acquire(session_id)`；`bg_task.add_done_callback(λ _: get_governor().release(session_id))`。
- 效果：并发 agent 数被钳制在 ≤10 = 池上限，池永不溢出，背压由准入层提供，**无需重写连接池**。

**⑥ 上下游关联**
- 与 A7 共用"共享单例"前提：正因池是共享单例，才需用准入信号量全局限流；若改成每请求新实例（A7 备选方案②），池会爆炸，A1 反而更糟。
- 与 A5 协同：并发被钳 ≤10 后，429 重试风暴被天然抑制。

**⑦ 验证**
压测 20 session 并发，断言：无 `PoolTimeout`；同一时刻 `_llm_sdk` 活跃连接 ≤10；总任务最终全部成功（背压排队而非失败）。

### 4.2 A2 — 无最大并发上限（雪崩级，与 A1 同源）

**① 触发时序**：同上，但即便池够大，无上限也会让单会话或全体把 CPU/内存/DB 连接打满。

**② 代码实锤**：`task_registry.register_task`（`task_registry.py:42`）仅 `running_tasks[task_id] = {...}`，无全局并发计数/上限。

**③ 根因机制**：缺少"准入闸门"，任何并发量都放行。

**④ 危害**：配合 A1 造成池溢出；单独也造成 DB/CPU 过载。

**⑤ 分步修复**：同 A1 的 `governor`（全局 + per-session 双层信号量）。per-session=3 防单会话独占。

**⑥ 上下游关联**：与 C11/C12/C13 共用 `session_id` 维度；per-session 信号量天然依赖 `register_task` 已写入的 `session_id`。

**⑦ 验证**：单会话发 10 个并发请求，断言仅 3 个同时运行、其余排队；总并发 ≤10。

### 4.3 A7 — 共享单例 BaseAIService 的可变请求态跨任务竞争（污染级，最严重且曾误判）

**① 触发时序（初判误报→纠正为严重）**
- 初稿曾认为"BaseAIService 每请求新建、字段实例级故安全"。**三思三省后发现 `get_service()` 返回进程级单例**（`service.py:89-114`），所有 session 共享同一实例。
- 具体交错：
  - T1（session A）：进入 `request_stream`，`reset_cancel()` 设 `self._cancelled=False`。
  - T2（session B）：进入 `request_stream`，`reset_cancel()` 又设 `self._cancelled=False`（覆盖，本无害）。
  - T3（session B）：用户取消 B → `cancel_task` → `ai_service.cancel()` 设 `self._cancelled=True`。
  - T4（session A）：流中对 `await self._check_stop()` 判断——若走 `self._cancelled` 分支，A 被**误取消**（张冠李戴）。
  - 更糟：`agent_runner.py:118-124` 每个任务都 `llm_service.set_stop_check(_stop_check)`，后设置的覆盖先前的 `self._stop_check`；而 `_stop_check` 闭包捕获的是**各自 task_id**，于是 session A 的流实际在检查 session B 的取消态。

**② 代码实锤**
- `service.py:89-114`：`get_service()` 返回缓存单例 `_instance`，所有请求共享。
- `base_service.py:68-70`：`self._cancelled=False; self._current_response=None; self._stop_check=None`。
- `base_service.py:82-97`：`cancel()` 读 `self._current_response` 并 `aclose`；`reset_cancel()` 置 `self._cancelled=False, self._current_response=None`。
- `base_service.py:99-107`：`set_stop_check(fn)` / `_check_stop()`（优先 `_stop_check`，否则 `_cancelled`）。
- `base_service.py:161`：`request_stream` 开头 `self.reset_cancel()`。
- `agent_runner.py:118-124`：`llm_service.set_stop_check(_stop_check)`，`_stop_check` 闭包 `return await check_cancelled(task_id)`。

**③ 根因机制**
可变请求态（`_cancelled/_current_response/_stop_check`）是**实例级单例字段**，却被多个并发任务当作"自己的"使用。共享单例 + 跨 `await` 持有可变字段 = 典型竞争。

**④ 危害**
- 取消检查张冠李戴：任务 A 被任务 B 的取消误停，或反之。

### 4.8 发现A — 全局配置 reload 无锁导致并发读到空（污染级，新增）

**① 触发时序**
- Session A 在前端改模型配置 → 调 API 触发 `Config.reload()`（`config.py:157-161`）。
- `reload()` 第一行 `self._config_data = None`（`config.py:159`）。
- 同一瞬间 Session B/C/D… 正在 `/chat/stream` 链路中多次调用 `get_config().get("ai.provider")` 等。
- `get_config()`（`config.py:166-178`）每次都调 `_config_instance._load_config()`；而 `_load_config` 在 `_config_data is None` 时 `_is_cache_valid` 返回 False → 进入 `_load_from_file` 重读。但在 `reload()` 把 `_config_data` 置 None 到重读完成的窗口内，B 的 `get()` 读到 `None`：`value = self._config_data`（`config.py:116`）为 None → `isinstance(None, dict)` 为 False → **静默返回 default**（错误配置）。

**② 代码实锤**
- `config.py:157-161` `reload()`：先置 `None` 再 `_load_config()`。
- `config.py:166-178` `get_config()`：每次 `_config_instance._load_config()`（mtime 变化即全量重读）。
- `config.py:104-124` `get()`：`value = self._config_data; for k: if isinstance(value, dict) and k in value: value=value[k] else: return default`。
- `config.py:33-47` `_load_config` / `61-75` `_load_from_file`：写 `self._config_data = yaml.load(...)`（整段无锁）。

**③ 根因机制**
- `reload()` 是**原地改写**共享单例字段（先 None 再填），reload 窗口内其他 session 的读看到中间态（None）→ 返回错误默认配置。
- 更严重：`get_config()` 每次调用都按 mtime 自动重读，**任一 session 触碰 config.yaml 都会触发全体重读**（惊群）。

**④ 危害**
- reload 期间并发请求拿到错误（默认）配置 → agent 用错 provider/model/api_key → 任务静默失败或行为错乱（跨 session 数据污染/雪崩隐患）。
- 惊群重读在高频调用下浪费 IO。

**⑤ 分步修复（copy-on-write，非加锁）**
- `config.py` 改 `reload()` 与 `get_config()` 为**构建新实例后原子替换全局**：
  ```python
  def reload():
      global _config_instance
      new_cfg = Config()
      new_cfg._load_config()          # 新实例独立加载，不影响正在被读的旧实例
      _config_instance = new_cfg       # 模块级赋值在 CPython 下原子

  def get_config() -> Config:
      global _config_instance
      if _config_instance is None:
          _config_instance = Config()
      # mtime 变化则构建新实例替换（不在原地改写）
      if _config_instance._need_reload():
          new_cfg = Config()
          new_cfg._load_config()
          _config_instance = new_cfg
      return _config_instance
  ```
- 读路径（含 `get()`）全程只读取 `_config_instance` 这个**完整实例**，永不看到 None 中间态。
- 热路径 `get_config()` 的读**无锁**（模块级读取原子），仅偶发 reload 替换全局，性能无损。

**⑥ 上下游关联**：与 A7 同理——共享单例的可变字段需避免"原地改写暴露中间态"。copy-on-write 是该模式的通用解法（OCP：读路径零改动）。

**⑦ 验证**：并发 50 协程循环 `get_config().get("ai.provider")`；另一协程周期性 `reload()`；断言任何时刻 `get()` 返回值均为合法非空字符串，绝不返回 default/None 引发的异常。

### 4.9 发现B — 注册表备份路径无 session 维度（污染级，新增）

  import threading

          if backup_key in _registry_session_backup:

**⑥ 上下游关联**：与 B8/B9 同属"模块级共享态缺 session 维度"，修复模式一致（键加 session_id + 锁）。

## 5. Phase 1 风险点深度分析

### 5.1 A3 — 同步 sqlite3 阻塞事件循环（雪崩级）

**① 触发时序**
- Session A 在 `4.5` 执行 `with db.get_conn("chat") as conn: append_execution_step(...)`（同步 `sqlite3` 读写）。
- 该调用在事件循环线程内**阻塞**（磁盘 IO + WAL 写）。期间 Session B/C… 的所有协程（含其 LLM 流式 chunk 转发、取消检查）全部被卡住，SSE 延迟陡增。

**② 代码实锤**
- `database.py:83` `conn = sqlite3.connect(str(db_path))` —— 同步阻塞建连。
- `agent_runner.py:153/159/188/208/247`：`with db.get_conn("chat") as conn: append_execution_step/finalize_message`。
- `stream.py:72`：`with db.get_conn("chat") as conn:`（`_load_previous_messages`）。
- `sse.py:56`：`with db.get_conn("chat") as conn:`（历史消息流）。

**③ 根因机制**：`db.get_conn` 是同步上下文管理器（内部 `sqlite3.connect` + `PRAGMA`），在 `async def` 内直接 `with` 调用 → 阻塞事件循环线程，违反 asyncio "不在循环内做阻塞 IO" 铁律。

**④ 危害**：并发下 DB 写成为全局瓶颈，所有 session 的响应延迟随并发数线性恶化，严重时 SSE 超时断开。

**⑤ 分步修复（asyncio.to_thread，零新依赖）**
- 调用点模式统一改为"把整块阻塞逻辑移入 worker 线程"：
  - `agent_runner.py` 每段 `with db.get_conn(...) as conn:` 块，原样搬进一个同步闭包，再用 `await asyncio.to_thread(闭包)` 调用。例：
    ```python
    def _append_step_sync(ai_message_id, session_id, step, event_dict):
        with db.get_conn("chat") as conn:
            append_execution_step(conn, ai_message_id, session_id, step, event_dict)
    # 调用处：
    await asyncio.to_thread(_append_step_sync, ai_message_id,
                            session_id, len(current_execution_steps)-1, event_dict)
    ```
  - `stream.py:72`：`prev = await asyncio.to_thread(_load_previous_messages, session_id)`（`_load_previous_messages` 函数体不变）。
  - `sse.py:56`：把 DB 读取块抽为同步函数 `await asyncio.to_thread(_read_session_rows, session_id)`，函数内 `with db.get_conn("chat") as conn:` 返回 rows，外层异步 gen 再 yield。
- 不引入 `aiosqlite`（全量迁移风险高、回归面大），`to_thread` 最小改动即解阻塞。

**⑥ 上下游关联**：与 A4 同处 `database.py`；与 A1 协同——事件循环不再被 DB 卡住后，A1 信号量下的并发 agent 才能真正流畅排队。

**⑦ 验证**：压测中监控事件循环"任务调度延迟"（如 `loop.time() - 预期` 抖动），断言 DB 密集写入期间 LLM 流式 chunk 转发延迟不出现 >1s 台阶；单测用 `asyncio.to_thread` 后主协程可被 `asyncio.sleep(0)` 即时让出。

### 5.2 A4 — busy_timeout=30000 过高（雪崩级，与 A3 同源）

**① 触发时序**：`chat_history.db` 在 WAL 下多 writer（多 session 逐步落库）偶发写锁竞争；某 writer 拿不到锁时按 `busy_timeout` 死等 30s，期间同步阻塞（叠加 A3 危害放大）。

**② 代码实锤**：`database.py:92` `conn.execute("PRAGMA busy_timeout=30000")`。

**③ 根因机制**：30s 写等待过长，单点写争用会把一次 DB 操作拖成 30s 阻塞，配合 A3 直接卡死事件循环 30s。

**④ 危害**：极端下 30s 全站无响应。

**⑤ 分步修复**
- `database.py:92` 改为 `PRAGMA busy_timeout=5000`（5s 上限足够 WAL 下短暂写竞争）。
- 在 `get_conn` 的同步体内，对 `conn.commit()` / `conn.execute()` 包一层指数退避（≤2 次，间隔 50ms/200ms），遇 `sqlite3.OperationalError: database is locked` 重试：
  ```python
  for attempt in range(3):
      try:
          conn.commit(); break
      except sqlite3.OperationalError as e:
          if "locked" in str(e) and attempt < 2:
              time.sleep(0.05 * (2 ** attempt)); continue
          raise
  ```

**⑥ 上下游关联**：与 A3 同文件；busy_timeout 收敛后，即使发生竞争也是快速失败+退避，而非 30s 死等。

**⑦ 验证**：制造高并发写（>10 session 同时落库），断言单次 DB 操作耗时 ≤~5s，且无 `database is locked` 未处理异常抛出。

### 5.3 A6 — Playwright 无节制并发启动浏览器（雪崩级）

**① 触发时序**：多 session 同时请求需 JS 渲染的网页 → 各自 `_fetch_via_playwright` 启动独立浏览器进程（Chromium）；并发 10+ 浏览器进程瞬间吃光内存/CPU → OOM 或系统卡死。

**② 代码实锤**：`fetch_webpage.py:533-539`：
```python
if sys.platform == "win32" and hasattr(asyncio, "ProactorEventLoop"):
    loop = asyncio.ProactorEventLoop()
    return loop.run_until_complete(_go())
return asyncio.run(_go())
```
`_go()` 内 `_pw_run` 启动浏览器（`fetch_webpage.py:542-549` 经 `run_in_executor`）。**无任何并发上限**。

**③ 根因机制**：浏览器进程重资源，无信号量限流即随并发线性放大。

**④ 危害**：资源雪崩（OOM / 系统无响应）。

**⑤ 分步修复**
- `fetch_webpage.py` 增加：
  ```python
  import asyncio
  _browser_sema = None
  def _get_browser_sema():
      global _browser_sema
      if _browser_sema is None:
          _browser_sema = asyncio.Semaphore(MAX_BROWSER_CONCURRENT)
      return _browser_sema
  ```
- `_fetch_via_playwright` 入口：
  ```python
  sem = _get_browser_sema()
  async with sem:
      return await loop.run_in_executor(None, _pw_run, ...)
  ```
- `constants.py` 增 `MAX_BROWSER_CONCURRENT = 4`。

**⑥ 上下游关联**：与 A1 同理，属"重资源并发需准入闸门"；浏览器信号量与 LLM 信号量并列，构成两类重资源的并发护栏。

**⑦ 验证**：并发 20 个 JS 渲染请求，断言同时运行的浏览器进程数 ≤4，且全部最终成功（排队而非失败/OOM）。

### 5.4 A5 — 429 重试风暴（雪崩级，依赖 A1 抑制）

**① 触发时序**：上游 LLM 返回 429（限流）；多 session 各自进入 `error_classifier` 识别为限流 → 各自重试；若无并发上限，重试瞬时叠加放大对上游压力，恶性循环。

**② 代码实锤**：`error_classifier.py:132-159`（限流类型识别，纯分类，无全局节流）；重试逻辑在 `base_service.request_stream`（`base_service.py:291-300`，`wait_time = 2**retry_count`）。

**③ 根因机制**：缺少"全局并发 LLM 调用节制"，429 后并发重试会放大。

**④ 危害**：上游限流恶化、雪崩。

**⑤ 分步修复（YAGNI：不加令牌桶）**
- 由 A1 的全局信号量（并发 agent ≤10 = 池上限）天然节制并发 LLM 调用量，从源头降低 429 概率与重试并发度。
- **不引入全局令牌桶**：令牌桶会新增一类需调参的全局状态，且 A1 信号量已提供等效的并发上限；违反 YAGNI。若后续实测 429 仍频繁，再单列 Phase 补充令牌桶（OCP：governor 可扩展）。

**⑥ 上下游关联**：完全依赖 A1；二者协同形成"并发上限 + 重试退避"双层防护。

**⑦ 验证**：模拟上游 429，断言重试并发度被 A1 信号量钳制，且重试间隔指数退避不叠加成瞬发洪峰。

## 6. Phase 2 风险点深度分析

### 6.1 B8 — file_state 跨会话污染（污染级）

**① 触发时序**
- Session A 读 `C:/x.txt` → `record_read` 写 `_state["C:/x.txt"]=(mtime,hash)`。
- Session B 同时读**同一文件** → 也写 `_state["C:/x.txt"]`，覆盖 A 的基线。
- A 随后写 `C:/x.txt` → `check_conflict` 看到的是 B 刚写的 mtime → 误判"文件被外部修改"（实则 B 的 read 基线覆盖了 A 的 read 基线）。

**② 代码实锤**：`file_state.py:15` `_state: Dict[str,Tuple[int,str]] = {}`（按 resolved path，无 session、无锁）；`:22-105` `record_read/record_write/check_conflict/is_unchanged/check_conflict_strict/clear_state` 全部以 `str(Path(file_path).resolve())` 为键。

**③ 根因机制**：文件在磁盘上虽是全局共享的，但"读基线"是**每会话视角**的；模块级字典按路径聚合、跨会话共享，导致 A 的读基线被 B 覆盖。

**④ 危害**：跨会话误报"外部修改"，干扰 A 的写决策（数据正确性退化）。

**⑤ 分步修复**
- 键改为 `(session_id, resolved_path)` + `threading.Lock()`：
  ```python
  import threading
  _state_lock = threading.Lock()
  def _key(session_id, file_path):
      return (session_id, str(Path(file_path).resolve()))
  def record_read(session_id, file_path, content):
      k = _key(session_id, file_path)
      with _state_lock:
          _state[k] = (mtime, hash)
  # check_conflict/is_unchanged/clear_state 同理加 session_id + 锁
  ```
- 调用方为各文件工具（`readtext`/`writetext`/`edit_text_file` 等），它们运行在 agent 上下文，可取到 `session_id`（经 `agent.session_id` 或工具参数透传），逐处补 `session_id` 形参。

**⑥ 上下游关联**：与 B9/发现B 同属"模块级共享态缺 session 维度"，修复模式一致；与 A7 同属"共享态需按会话/任务隔离"的总主题。

**⑦ 验证**：Session A、B 并发读写同一文件，断言 A 的 `check_conflict`（在 A 自己 read 后、write 前）返回 None（不被 B 干扰），B 同理。

### 6.2 B9 — PersistentShell 跨会话复用同一 PowerShell 进程（污染级）

**① 触发时序**
- Session A：`get_instance("C:/work")` 建/取 PS 进程 P1（cwd=C:/work）。
- Session B：同 cwd `get_instance("C:/work")` → 命中同一 P1（因为池键仅 cwd）。
- A、B 交替 `exec("Get-Location")`：P1 的 stdin 交错写入两条命令，stdout 混淆；且 `_exec` 内 `self._cwd = cwd_raw`（`:270`）被 B 的 cd 改写，A 后续相对路径命令跑错目录。

**② 代码实锤**：`shell_engine.py:146` `_instances: Dict[str,'PersistentShell'] = {}`；`:159-176` `get_instance` 以 `workdir or os.getcwd()` 为键；`:269-270` `_exec` 内 `if cwd_raw: self._cwd = cwd_raw`（在 `with self._lock` 内，但跨实例共享时无效——同一实例被两 session 共用）。

**③ 根因机制**：持久 PS 进程以 cwd 池化，但 cwd 不是会话隔离维度；同 cwd 多 session 共享同一进程 → 命令/工作目录互相污染。

**④ 危害**：跨会话命令结果错乱、工作目录串台（严重数据正确性缺陷）。

**⑤ 分步修复**
- 池键加 `session_id`：
  ```python
  @classmethod
  def get_instance(cls, workdir=None, session_id=None):
      with cls._class_lock:
          key = (session_id, workdir or os.getcwd())
          inst = cls._instances.get(key)
          if inst is None:
              inst = cls(key[1], session_id=session_id)
              cls._instances[key] = inst
          inst._last_used = time.time()
          return inst
  ```
- `_cwd` 写已在内层 `self._lock`；键隔离后每实例仅服务单一 session，串扰消除。
- `execute_shell_command.py` 调用 `get_instance(workdir, session_id=...)` 透传 session_id（工具上下文可取）。

**⑥ 上下游关联**：与 B8/发现B 同模式；与 A7 同主题（共享态按会话隔离）。

**⑦ 验证**：Session A、B 同 cwd 并发执行 `cd D:/tmp; Get-Location`，断言 A 看到的 cwd 始终 A 的目标、B 看到 B 的目标，互不串。

### 6.3 B10 — 注册竞态（裁定：删除，不修复）

**① 代码实锤**：`registry.py:380-404` `ensure_tools_registered` 遍历 `CATEGORY_MODULES` 逐个注册。
**② 触发场景核查**：全代码库唯一调用点在 `main.py:176`（启动期单次同步调用），**运行期无任何并发调用方**。
**③ 裁定**：无并发 → 加双检锁属过度设计（YAGNI）。**不修复**。若未来改为运行时懒注册，再补锁（OCP 预留）。

### 6.4 发现C — project_context 缓存无锁（裁定：可选，默认略）

**① 代码实锤**：`project_context.py:23` `_context_cache: OrderedDict`（workdir 键）；`:38-64` `move_to_end/[key]=/popitem`。
**② 安全判定**：`load_project_context` 为**同步且无 `await`** 函数 → asyncio 单线程下整体原子，不会被其他协程打断；键为 workdir、值来自同一文件（确定性）；最坏情况是冗余计算，无数据损坏。

## 7. 逐决策点深度权衡

> 每个决策点对比 ≥2 候选方案，给出"为何其他选项被否"与"裁定贴合哪条规范"。

**D1 · A1/A2 并发上限**
- 方案①重写 LLMClientPool 为排队池：根治但动连接池核心，回归风险高，且需重构 `client_sdk`——过度设计，否。

- 方案③全局+per-session 信号量（裁定）：零池改写、最小改动、背压由准入层提供；贴合 **KISS-DIRECT / YAGNI / SRP**。

**D2 · A7 共享单例可变态**
- 方案①每请求新实例：池爆炸（同 D1②）——否决。
- 方案②per-task 包装类委托共享 httpx 客户端：新增类、越 ISP/LSP、调用链变长——否决。
- 方案③共享实例上 `task_id` 隔离字典（裁定）：仅隔离微小可变态，保留共享池；贴合 **KISS-DIRECT / 禁止backward（行为不变）/ LSP**。

**D3 · 发现A 配置重载**
- 方案①加 `threading.Lock` 包 `_load_config/reload`：热路径 `get_config` 每次读都需竞争锁，性能损——否决。
- 方案②copy-on-write 原子替换全局（裁定）：读路径零锁，仅偶发 reload 替换；贴合 **KISS-DIRECT / OCP（读路径零改动）**。

**D4 · B8 file_state**
- 方案①保持全局：同文件多会话互相覆盖 read 基线误报——否决。
- 方案②键加 `(session_id,path)`+锁（裁定）：正确隔离；代价是 6 处签名透传，但正确性优先；贴合 **SRP / 复用优先**。

## 8. 10 大编码规范符合性详述

| 规范 | 本设计如何体现 | 若违背会怎样（反例） |
|---|---|---|
| **SRP** | governor 单职（准入+节流）；task_registry 单职（归属+生命周期）；每处修复只解决一个关注点（如 A7 只隔离取消态，不动连接池） | 若把信号量、归属、限流全塞进 openai.py 一个函数，则单函数职责爆炸、难测 |
| **DRY** | 归属校验统一 `check_task_ownership` 用于 cancel/pause/resume/reconnect/confirm 五处；per-task 态统一存 `running_tasks`/`_task_state` | 若每处各写一段 session 比对，则改规则要改 5 处、易漏改致不一致 |
| **KISS-DIRECT** | 信号量而非重写池；per-task dict 而非重写实例；copy-on-write 而非加锁读改写；to_thread 而非 aiosqlite | 若重写连接池，引入抽象层+回归，偏离直线逻辑 |
| **SLAP** | 治理在 API 入口（openai.py 做准入+归属）与基础设施（governor/db/config）接入，agent/tool 内部不被污染 | 若在 react_cycle 深处埋归属校验，高层编排与底层细节混搭，读如天书 |
| **YAGNI** | 删 B10 锁、不加令牌桶、略发现C、低危 `_PWSH_CACHE`/`agent_streams` 不加锁 | 若给所有共享 dict 一律加锁，徒增锁竞争与复杂度 |
| **禁止 backward** | `set_stop_check(task_id,fn)`、`register_task(...,session_id)`、`file_state` 各函数加 `session_id` 直接改签名，不留旧兼容分支（旧 `session_id=None` 仅在 confirm 兼容保留，因属外部契约） | 若保留 `set_stop_check(fn)` 旧签名并内部猜 task_id，则新旧混杂、行为歧义 |
| **OCP** | governor 限额可配置（constants 调整即扩展）；config reload 扩展不改读路径；A5 令牌桶预留扩展点 | 若把并发数硬编码散落多处，新增一类限制需改多个文件 |
| **LSP** | per-task dict 不引入继承；行为保持（取消/停止语义不变） | 若让 BaseAIService 子类覆盖 cancel 改语义，则父类约定被破坏 |
| **ISP** | 不堆砌接口；仅追加真正需要的参数（task_id/session_id） | 若给 BaseAIService 加一堆用不上的钩子方法，接口臃肿 |
| **复用优先** | 复用既有 `running_tasks_lock`、`running_tasks` 存储、`check_task_ownership`、`db.get_conn`、ContextVar 日志上下文；不局部重造 | 若在多处新建自己的 session 映射表，则与 `running_tasks` 重复、易不一致 |

## 9. 上下游关联与有机整合

- **数据流贯通**：`register_task` 写入 `session_id` 与 `_task_state[task_id]` 是 C11/C12/C13 与 A7 的共同数据源；governor 的 per-session 维度复用同一 `session_id`——一处写入，处处校验，无重复状态。
- **控制流贯通**：准入（`governor.acquire`）在 `generate()` 入口，`release` 在 `bg_task` 终态回调；与 `task_cleanup` 的终态清理天然衔接，无孤儿信号量。
- **异常流贯通**：A3 的 `to_thread` + A4 的退避，使 DB 异常被限制在 worker 线程内、按既有 `try/retry` 路径处理，不污染事件循环；A7 的 per-task cancel 使取消异常精准作用于本 task。
- **资源护栏贯通**：A1（LLM 信号量）+ A6（浏览器信号量）构成"两类重资源并发闸门"，与 per-session 信号量（防单会话独占）正交互补。
- **治理不污染业务**：所有改动集中在 `governor.py` / `task_registry` / `task_runtime` / `config.py` / `database.py` / 各共享态模块，**agent 内部 ReAct 循环、工具业务逻辑零改动**，仅透传 `task_id`/`session_id` 参数。

### 10.1 压测脚本设计（真实后端 + 真实 LLM + 真实 SQLite，禁止 Mock）
