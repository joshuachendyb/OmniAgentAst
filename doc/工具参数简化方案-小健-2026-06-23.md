## 一、背景

E2E 测试发现 LLM 调用工具经常传错参数。根因分析如下：

| 问题类型 | 举例 | 后果 |
|---------|------|------|
| **条件参数太多** | filter/max_lines 只在 action=output 生效 | LLM 忘记传条件参数 |
| **一个参数多种含义** | text_or_keys 在 type/shortcut/combo 时含义不同 | LLM 分不清该传什么 |
| **联合类型让 LLM 选** | data: Union[str, List[Dict]] | LLM 选错格式 |
| **参数太多** | grep_file_content 有 7 个参数 | LLM 记不全 |

**目标**：砍掉 LLM 不需要的参数，合并模糊的参数，让每个工具的参数一看就懂。

---

## 二、改动原则

1. **条件参数必须砍**——"只有在某个 action 下才生效"的参数，LLM 一定会忘
2. **一个参数只做一件事**——text_or_keys 既当文本又当快捷键，LLM 会乱
3. **不要让 LLM 选格式**——Union[str, List, Dict] 统一为一种
4. **LLM 自己能处理的事，不暴露**——过滤输出、记行数，LLM 自己来
5. **不改已经够简单的**——只有 1-2 个参数的、没有条件依赖的，不动

### 3.1 shell_session —— 问题：3 个条件参数[同意]

**第 1 遍：看当前参数**

| 参数名 | 类型 | 作用 |
|--------|------|------|
| shell_id | str | 会话 ID（必填） |
| action | output/terminate | output 读输出，terminate 终止 |
| filter | Optional[str] | 只在 action=output 时有用，用来过滤命令行输出 |
| max_lines | int | 只在 action=output 时有用，限制返回行数 |
| force | bool | 只在 action=terminate 时有用，强杀进程 |

**第 2 遍：分析每个参数**

- **shell_id**：必填，不能删。留着 ✅
- **action**：决定操作类型，不能删。留着 ✅
- **filter**：条件参数。只在 output 有效。**LLM 经常忘记传，而且 LLM 自己拿到完整输出后可以自己过滤。** 砍掉 ❌
- **max_lines**：条件参数。只在 output 有效。**有默认值 1000 但 LLM 不知道。而且 LLM 自己截断就行，不需要工具层限制。** 砍掉 ❌
- **force**：条件参数。只在 terminate 有效。**优雅终止还是强制终止，LLM 不会判断。统一强杀，省掉选择。** 砍掉 ❌

**第 3 遍：确认**

6 参数 → 2 参数（shell_id + action）。砍掉的 3 个都是条件参数，符合"条件参数必须砍"原则。terminate 直接强杀，不需要 force。

**改动**：改 schema + 改工具实现（删掉 filter/max_lines/force 处理逻辑）

### 3.2 query_calendar —— 问题：双模式，LLM 选错模式[同意]

**第 1 遍：看当前参数**

| 参数名 | 类型 | 作用 |
|--------|------|------|
| name | Optional[str] | 传节日名查节日（如"端午节"） |
| year | Optional[int] | 年份 |
| date | Optional[str/date] | 传日期查工作日（如"2026-06-23"） |
| check_type | Literal | 4 种检查类型：weekend/holiday/workday/next_workday |
| n | int | 只在 next_workday 时有用 |

**问题**：name 和 date+check_type 是两套互斥的模式。LLM 既可以通过 name 查节日，也可以通过 date+check_type 查工作日。**LLM 经常同时传 name 和 date，不知道哪套优先。**

**第 2 遍：分析每个参数**

- **name**：传节日名，直观。留着 ✅
- **year**：选填，传年份或默认当年。留着 ✅
- **date**：和 name 互斥。**LLM 搞不清传 name 还是传 date。** 砍掉 ❌
- **check_type**：4 种检查类型，LLM 记不住。**合并到 name：传"2026-06-23"自动检查。** 砍掉 ❌
- **n**：只在 next_workday 有效。条件参数。砍掉 ❌

**第 3 遍：确认**

方案改为：**name 参数既可以传节日名（返回节日信息），也可以传日期字符串（自动识别工作日/节假日）。** 5 参数 → 2 参数。LLM 不需要记住 4 种 check_type。

**改动**：改 schema + 重写工具实现（解析 name 自动判断是节日还是日期）

### 3.3 keyboard_control —— 问题：text_or_keys 三种含义

**第 1 遍：看当前参数**

| 参数名 | 类型 | 作用 |
|--------|------|------|
| action | type/shortcut/combo | 输入文本/快捷键/组合键 |
| text_or_keys | str | type=文本，shortcut=ctrl+c，combo=ctrl,shift,esc |
| interval | float | 字符输入间隔（仅 type 有用） |

**第 2 遍：分析每个参数**

- **action**：决定操作类型。留着 ✅
- **text_or_keys**：参数名不好，而且 combo 和 shortcut 本质相同。**combo 的 ctrl,shift,esc 其实可以用 shortcut 的 ctrl+shift+esc 替代。** 改成单一语义：type 时是文本，shortcut 时是快捷键。留 action=type/shortcut 两种 ✅
- **interval**：字符间隔，控制打字速度。**LLM 不需要管打字快慢。** 砍掉 ❌

**第 3 遍：确认**

3 参数 → 2 参数。combo 合并进 shortcut。interval 砍掉。text_or_keys 名称不友好但已经是注册名，不改名避免破坏接口。

**改动**：改 schema（删 combo、interval）+ 改工具实现

### 3.9 http_request —— 问题：params 和 json_body 分不清

**第 1 遍：看当前参数**

| 参数名 | 类型 | 作用 |
|--------|------|------|
| url | str | 请求 URL |
| method | Literal | GET/POST/PUT/DELETE/PATCH/HEAD/OPTIONS |
| headers | Optional[Dict] | 请求头 |
| params | Optional[Dict] | URL 查询参数 |
| json_body | Optional[Dict] | 请求体（POST/PUT 用） |

**第 2 遍：分析**

- **url**：必填。留着 ✅
- **method**：太多了。**LLM 只需要 GET/POST/PUT/DELETE，PATCH/HEAD/OPTIONS 基本不用。** 砍到 4 种 ✅
- **headers**：自定义请求头。**【修正】很多API需要Authorization、Content-Type、Accept等header才能调用（如OpenAI API、GitHub API），砍掉会导致无法调用需要认证的API。保留。** 留着 ✅
- **params**：URL 参数。**LLM 可以直接拼到 url 里。** 砍掉 ❌
- **json_body**：请求体。**改名为 body，类型保持 Dict。** 改名为 body ✅

**第 3 遍：确认**

5 参数 → 4 参数（url+method+headers+body）。params 砍掉，json_body 改为 body。**headers 保留**。

**改动**：改 schema + 改工具实现

### 3.10 grep_file_content —— 问题：7 参数太多

**第 1 遍：看当前参数**

| 参数名 | 类型 | 作用 |
|--------|------|------|
| pattern | str | 正则 |

**第 2 遍：分析**

- **pattern**：必填。留着 ✅

- **head_limit**：限制结果数。**LLM 拿到结果太多可以要求重新搜。** 砍掉 ❌

**第 3 遍：确认**

7 参数 → 5 参数（pattern+search_dir+glob+output_mode+ignore_case）。search_dir 改必填，砍掉 2 个。**glob 保留**。

### 修正1：http_request的headers参数

**原判断**：砍掉headers，理由是"LLM的API调用场景不需要设header"

**修正理由**：错误判断。很多API需要Authorization、Content-Type、Accept等header才能调用（如OpenAI API需要`Authorization: Bearer sk-xxx`，GitHub API需要`Authorization: token xxx`）。砍掉headers会导致无法调用需要认证的API，这是严重功能缺失。

**修正结果**：保留headers参数，只砍掉params。

### 修正2：grep_file_content的glob参数

**原判断**：砍掉glob，理由是"用pattern里写路径就够了"

**修正理由**：概念混淆。glob是过滤文件类型（如`*.py`、`*.ts`），pattern是搜索文件内容的正则表达式，两者完全不同互不替代。砍掉glob会导致搜索所有文件类型，无法限制只搜Python或TypeScript文件，返回大量无关结果。

**修正结果**：保留glob参数，只砍掉head_limit和context_lines。
