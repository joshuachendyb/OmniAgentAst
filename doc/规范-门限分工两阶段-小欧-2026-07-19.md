## 一、背景与问题（为何立此规矩）

grep 死循环（step48→99）排查中暴露门限处理混乱，根因是**同一类门限在被重复/错位放置**：

1. **输入输出不分**：输入校验（文件大小/超时/pattern长度）和输出截断混为一谈。
2. **输出两头都管**：grep 在 Format 层用 `OBS_MAX_DISPLAY_ITEMS`（500）管条数 + `OBS_MAX_STRING_LENGTH`（10000）管内容截断，粒度不统一。
3. **Format 无行×列**：只截单串（10000），没管"一共显示多少行×多宽"，36 条×7 行累加 919KB >> `MAX_CONTEXT_CHARS=200K`，被 `trim_history` 整条丢弃 → LLM 失明 → 退化重调。
4. **shell 同病**：Tool 截 `SHELL_OUTPUT_MAX_CHARS=20000`，Format 又截 `OBS_MAX_STRING_LENGTH=10000`。

结论：域不分、职责乱、缺行×列。必须立规矩。

## 二、三域架构定义

| 域 | 层 | 职责 | 产出 |
|----|------|------|------|
| **输入域** | 输入校验/安全层（App/validate、tool 输入校验） | 校验参数合法/安全，防 OOM/防超时/防 ReDoS | 合法参数或拒绝 |
| **输出-数据域** | Tool（`app/tools/*/_tools.py`） | 执行操作，产出**原始保真 data** | `data`（常规不设截断；仅 3.4 极端硬安全例外附 `truncated` 标志） |
| **输出-显示域** | Format（`app/services/agent/observation_formatter.py`） | 把 data 渲染成**给 LLM 的观察文本** | 观察字符串（行×列） |

`data` 的消费者不止 LLM：前端原始展示、日志、链式调用。故 `data` 必须**保真**。
上下文裁剪（`message_builder.py`）是第三阶段，与本规范的门限分工无关。

## 三、规矩（铁律）

### 3.1 输入限制
所有工具入参须做**安全类校验**（与输出无关），仅保留：
- ReDoS / 安全检测（嵌套量词等危险正则）
- 路径合法/安全校验（目录存在、权限等）
- 其它安全类检测（非大小/长度限制）

**注**：原"单文件读取大小上限 / pattern 长度上限 / context 范围限制"等输入大小/长度门限，依 3.6 铁律**全部去除**——参数已由 schema（5.1.1）规定，不必另立大小/长度限制。本 3.1 仅保留安全检测类校验，大小/长度类输入门限不再列入。

### 3.2 输出限制

#### 3.2.1 Tool（输出-数据域）——保真，不设任何限制

- **铁律（依 3.7）**：Tool 输出**不设任何限制**——结果条数、字段大小、字段长度统统不限制、不截断，依参数执行后是多少就是多少，全部保真返回。
- **禁止**：为"显示"截断任何字段字符串（只返 raw 保真）；不得用 `GREP_MAX_RESULTS` / `OBS_MAX_DISPLAY_ITEMS` / `SHELL_OUTPUT_MAX_CHARS` / `OBS_MAX_STRING_LENGTH` 等常量对输出设条数/大小/长度上限（已作废）。
- 原"结果条数上限 + `truncated=true`"方案作废：条数超限不再由 Tool 截断，统一收口于 Format 行×列（见 3.2.2 / 3.7）。

#### 3.2.2 Format（输出-显示域）——行×列（保 LLM 可理解为根本原则）

**根本原则（最高优先级，覆盖本条一切细则）**：截断的唯一目的是防 observation 撑爆 context / OOM；**任何截断都不得让 LLM 理解不了**。若截断导致信息丧失到 LLM 无法理解（如 JSON 未闭合、代码语句断半、关键 token 被截掉），则该截断违规，须调整策略或放宽列宽。

- **行数上限**：单条观察最多显示行数（含 content/上下文/空行）。超过则尾部截断并附说明行（见下）。
- **单行上限（列宽）**：每渲染行最长字符数。**禁止"无脑尾部截断"**——截断必须保可理解：
  - 匹配型载荷（有独立 `[matched]` / 关键标记，如 grep）：可尾部截断，`matched` 已前置保真。
  - 自由文本 / 代码 / 日志载荷（readtext / edittext / shell / fetchpage / readmedia 等）：**保头部 + 保关键 token/key + 高位宽**，不得盲截尾部使语义断裂。
  - 结构化载荷（JSON / httpget / 宽表）：不得截断到破坏结构；列宽取高位（≥2000）或原样，破坏结构即违规。
- 其余显示门限（snippet/头尾/预览）内嵌于行×列，不另立。
- **禁止**：修改 raw `data`。

**单列字符宽度分三档（按载荷类型，非一刀切）**：

| 档 | 载荷类型 | 列宽 | 适用 tool |
|----|---------|------|----------|
| 匹配型 | 有独立 matched / 关键标记的行 | 150–300 | grep / find / listdir / 批量文件操作结果 |
| 自由文本型 | 长代码行 / 日志 / Markdown / 媒体转写 / 搜索结果标题+URL+snippet | 500–1000 | readtext / edittext / shell / fetchpage / readmedia / searchweb |
| 结构化型 | JSON / 表格宽行 | 原样或 ≥2000 | httpget(JSON) / read_xlsx(宽表) |

> 行数上限统一 200（覆盖绝大多数场景，超则附说明行；各 tool 章（第 6–19 章）按其档定 `OBS_<TOOL>_MAX_ROW_CHARS`，行数统一 `OBS_<TOOL>_MAX_ROWS=200`。

- **截断说明行（铁律）**：观察详情末尾追加状态说明，首行标状态。有截断另起一行说明；无截断仅一行。两态格式（末尾追加）：
  - 有截断：
    ```
    ⚠ 已截断
    截断情况：保留{n}行,实际 {M} 行，截断 {K} 行；单列上限 {CHARS} 字符（超宽 {W} 行已保可理解截断）
    （完整数据可向原工具二次请求，或在前端 other_data 中获取）
    ```
  - 无截断：
    ```
    ✓ 无截断-完整
    ```
  此说明只说明截断、不改 raw `data`；末句引导 LLM 补全理解，闭合"可理解"闭环。

### 3.3 内部规范（非门限）
既不属于输入校验也不属于输出门限的代码内部约定，归为内部规范：
- **数据组织**：工具返回的字段结构、命名约定
- **实现策略**：snippet 构建、上下文组织、遍历策略等内部逻辑
- **内部常量**：与输入校验/输出门限无关的代码常量（如跳过目录名单、错误码）
- **与三域的关系**：内部规范不属于输入/输出-数据/输出-显示任何一域，不设门限值，只描述代码实际做法

### 3.4 例外：硬安全上限
某字段可能撑爆序列化/OOM 时（如单字段>数十 MB），Tool 可设硬安全上限作安全网；该上限属于**内部常量**（依 3.3/3.5 与输入/输出门限无关），**不进 `tool_constants.py` 门限区**；命名依 3.5 区分公用/私有——公用的保持原代码名不加前缀，私有（工具专属）的加 `INER_<tool名>_` 前缀（格式 `INER_<tool名>_<常量语义名>`，如 `INER_HTTPGET_JSON_PREVIEW_MAX_BYTES`）。各响应 tool 的 3.4 常量明细写在各自章节（第 6–18 章）的 6.4 实施计划内，触发时一律置 `data["truncated"]=True`（shell/fetchpage 为截断动作）。

按域约定前缀：
- **输入域常量**：仅安全检测类输入常量须工具专属（如 ReDoS 检测常量）；**大小/长度类输入门限依 3.6 已去除，不再设专用常量**。

**分组规则**：`tool_constants.py` 中，各工具专属常量（输入域 + 输出域）必须按工具集中分组，不得与公用常量混放。

### 3.7 Tool 输出零限制铁律（北京老陈 2026-07-20 01:42:24）

**铁律：Tool 输出不设任何限制。依 tool 参数执行后，输出是多少就是多少——结果条数、字段大小、字段长度统统不限制、不截断。唯一允许对输出数据做限制的地方，只有 Format 格式化过程（行×列截断）。**

- **范围**：凡属"输出数据"的门限一律去除——结果条数上限（如 `GREP_MAX_RESULTS` / `OBS_MAX_DISPLAY_ITEMS`）、字段字符串大小/长度上限（如 `SHELL_OUTPUT_MAX_CHARS` / `OBS_MAX_STRING_LENGTH`）、输出截断——Tool 层一律不设。
- **唯一收口点**：输出的限量只发生在 Format 输出-显示域，由行×列（`OBS_*_MAX_ROWS` + `OBS_*_MAX_ROW_CHARS`）负责（见 3.2.2）。除此之外，任何环节不得对输出设大小/条数/长度限制。

## 四、原则（对规矩的解释）

### 4.1 全域分三域
所有门限先确定属于哪个域，三域互不混淆：
- **输入域**：只管输入安全/合法，与输出无关。越过门槛直接拒绝，不产 data。
- **输出-数据域**：管"操作结果的真不真、全不全"——依 3.7 不设条数/大小截断，`data` 全量保真；仅 3.4 极端硬安全例外可附 `truncated`。
- **输出-显示域**：管"呈现给 LLM 的方块有多大"——行数 × 列宽。

### 4.2 输出-划分原则（数据归 Tool / 显示归 Format）
仅适用于输出域。**判据**：该门限改变的是"操作结果的真实性/完整性"（数据），还是仅改变"结果呈现给 LLM 的形态"（显示）？
- **数据（结果保真）→ Tool**：依 3.7，结果条数/大小一律不截断，`data` 全量保真返回；仅 3.4 极端硬安全例外才置 `truncated`。理由：`data` 多消费者，须保真；Tool 不知在喂 LLM，没资格替 LLM 定显示，也不得替 LLM 限制条数。
- **显示（行数 × 单行 / 头尾 / snippet）→ Format**，且不动 data 半分。理由：Format 唯一消费者是 LLM，只有它知道在为 LLM 渲染。
- **试金石**：套用后 `data` 还是对操作的忠实交代？否→ Tool（仅 3.4 极端硬安全例外 +truncated）；是→ Format（行×列截断，见 3.7）。

### 4.3 输出-大小原则（行×列，认知充分性驱动）
仅适用于输出显示域（Format）。任何输出展开都是**行×列（方块）**，Format 门限就两个：
- **列宽（单行上限）**：一行显示多宽。以 LLM 认知充分性定值（影响尺）。
- **行数（行数上限）**：一共显示多少行。以 LLM 认知充分性定值。
总观察量 = 行数 × 单行上限，自然导出，不需要独立"总预算"门限。

**影响尺操作法**：①问"截断到 N，LLM 理解/行动是否受损？"②受损大→加长，受损小→就取 N。③取影响变小的最小 N。④校验 ≪ 200K（护栏）。

**grep 行宽示例**：50 字符→关键 payload 被砍，影响大；100→覆盖级别+关键词，影响明显变小；150→覆盖大多数匹配行，影响很小。故单行上限定为 150。

### 4.4 两条原则正交
先按 4.2 定归属（数据→Tool / 显示→Format），再按 4.3 定大小（行×列认知充分性）。归属错或数值错皆违规。

### 5.3 输出规范

#### 5.3.1 Tool 输出限制（条数上限）——已去除，对齐 opencode-old

**决策**：grep Tool **不设结果条数上限**，返回全部匹配（对齐 rg 无条数限制）。理由：条数上限属多余防御——防上下文撑爆由 Format 行×列层负责；上限会漏掉第 N 条之后的关键匹配、造成结果失真、且与 rg 行为不一致（见 5.3 开头三省分析）。

`data` 结构（代码 `grep_file_content.py:346-348`）：
```python
{
  "matches": [...]        # 全部匹配，每字段原样保真
  "total_matches": 整数    # 实际匹配数（如实）
  "total_files": 整数     # 实际文件数
  "skipped_binary_files": [str]   # 跳过的二进制/超宽文件(警告时返回)
  "skipped_binary_count": 整数    # 跳过文件数(等于上述列表长度)
}
```
- 常规不再置 `truncated`（因不再因条数/大小截断）；仅 3.4 极端硬安全上限触发时才附 `truncated` 标志。`total_matches` 如实回报真实匹配总数。
- `OBS_MAX_DISPLAY_ITEMS` / `GREP_MAX_RESULTS` 等条数上限常量作废，grep 不再引用。

**禁止**：Tool 层不对单条 `content` 等字段做大小/长度截断（依 3.7 字段大小/长度不限制，全量保真）；Format 层亦不得用 `OBS_MAX_STRING_LENGTH` 一刀切截断字段字符串，须改用行×列（`OBS_GREP_MAX_ROWS` + `OBS_GREP_MAX_ROW_CHARS`）。

#### 5.3.2 Format 输出限制——行×列

Format（`observation_formatter.py` 的 `_format_matches`，行号随代码变动）渲染时遵守两个门限：

| # | 门限 | 常量名 | 值 | 说明 |
|---|------|--------|-----|------|
| 1 | 行数上限 | `OBS_GREP_MAX_ROWS` | **200** | 覆盖绝大多数搜索结果，超尾部截断+标记 |
| 2 | 单行上限（列宽） | `OBS_GREP_MAX_ROW_CHARS` | **150**（匹配型档 150–300 下限） | 够放 `[file:line] [matched] content + …` 标记；`matched` 前置保真，属匹配型档 |

注：原 `OBS_MAX_STRING_LENGTH=10000` 由 `OBS_GREP_MAX_ROW_CHARS=150` 取代（旧值偏大，改认知充分性）。

**行数规则**：每条结果占 1 行，context 行额外占。超过 200 行时尾部截断，并按 3.2.2 铁律于详情末尾追加截断说明行（不再用旧"…还有 N 条未显示"措辞）。

**单行规则（匹配型档）**：每行 ≥150 字符即按保可理解截断（追加`…`），`matched` 已前置保真，故 content 超宽尾部截断不损"匹配了什么"的理解；`file:line`、`[matched]`、`content`、`before`/`after` 竞争这 150 字符，优先保 `file:line` + `[matched]` + 关键 content，context 长则断。此属 3.2.2 匹配型档下限，必要时可放宽至 300。

snippet/头尾/预览等**内容组织方式**通过行×列自然实现（用行数装 snippet，用列宽装预览），不另设独立门限。

**与 Tool 的关系**：Format 只读 `data["matches"]`，不做任何修改；仅控制渲染后的文本形态。

**截断说明行（依 3.2.2 铁律）**：`_format_matches` 渲染后于该条观察详情末尾追加状态说明（有截断 `⚠ 已截断` / 无截断 `✓ 无截断-完整`，格式见 3.2.2）：
```
⚠ 已截断
截断情况：保留{200}行,实际 {M} 行，截断 {K} 行；单行上限 {150} 字符（超宽的{n}行尾部截断）
```
无截断仅一行 `✓ 无截断-完整`（不附冗余明细）。（注：仅说明，不改动 raw `data`）。

**已落地**：`grep_file_content.py` 已去除 `OBS_MAX_DISPLAY_ITEMS` / `GREP_MAX_RESULTS` 等条数上限引用（Tool 输出零限制，见 3.7/5.3.1）；`observation_formatter.py` 的 `_format_matches` 已改用 `OBS_GREP_MAX_ROWS` + `OBS_GREP_MAX_ROW_CHARS` 行×列渲染，并按 3.2.2 追加截断说明行。
