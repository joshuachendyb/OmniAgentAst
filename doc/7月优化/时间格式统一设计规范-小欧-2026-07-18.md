## 一、问题本质 — 小欧 2026-07-18

时间格式不统一，根因不在"20 个调用点各写各的"——而在于**写入边界没有强制归一化**。

| 现状 | 根因 |
|---|---|
| 4 种格式混存（空格秒/T微秒Z/整数毫秒/本地偏移） | 各模块靠不同方式生成时间（CURRENT_TIMESTAMP / datetime.now() / create_timestamp / astimezone().isoformat()） |
| `datetime.now()` 依赖已废弃的 sqlite3 默认适配器（Python 3.12+ DeprecationWarning） | 裸 datetime 对象直传 sqlite3.execute()，靠默认适配器兜成字符串 |
| 本地时区 naive 与 UTC 混存 | `datetime.now()` 是本地 naive，CURRENT_TIMESTAMP 是 UTC（无标记） |

---

## 二、最佳方案：边界自动归一化 — 小欧 2026-07-18

### 核心做法（一句话）

> **在 `_ParamSafeConnection` 这个唯一的 DB 写入闸门中，对参数列表里的 `datetime`/`date` 对象，统一用 `convert_to_utc()` 转为 UTC ISO 8601 带 Z 字符串再传给底层 sqlite3。**

```python
# 改动位置：_ParamSafeConnection._validate → 改为自动序列化（而非拒绝或裸传）
if isinstance(_p, (datetime, date)):
    _p = convert_to_utc(_p)  # → "2026-07-18T04:45:38.822063Z"
```

### 为什么它是"最优雅"（逐条对照 10 大规范）

| 规范 | 符合情况 |
|---|---|
| **SRP** | 从 SQL 参数中提取 datetime/date → 字符串的序列化职责，只在 `_ParamSafeConnection` 一层，调用方不关心格式 |
| **DRY** | 一份转换逻辑覆盖所有写入路径，不用重复改几十个文件 |
| **KISS-DIRECT** | 边界穿甲弹：一个闸门转换解决所有"不同写入格式"问题，不绕 5 层 |
| **SLAP** | 调用方写业务逻辑（传 datetime 或字符串），边界层负责格式归一化——不混抽象层 |
| **YAGNI** | 不新增 `parse_db_time`（前端 `Date.parse` / 后端 `datetime.fromisoformat` 已兼容 ISO 字符串），不过度 |
| **禁止 backward** | 现有 `datetime.now()` 裸传**一个都不用改**（旧代码行零变动），边界自动转；`CURRENT_TIMESTAMP` 改为应用层 INSERT 显式传 |
| **OCP** | 对新时间类型开放（边界可扩展转换分支），对调用方封闭（不改调用代码） |
| **复用优先** | `convert_to_utc()` 已在 FUNCTIONS.md 登记（`time_utils.py`），直接复用，不新建 |

## 四、两个不走参数边界的例外及处理 — 小欧 2026-07-18

边界自动转换只能拦截**走 `_ParamSafeConnection.execute()` 参数传入的 datetime**。两条路径需要单独处理：

### 例外 1：`CURRENT_TIMESTAMP`（SQL 默认值，不走参数）

- **位置**：`db_initializer.py` 共 11 处建表 DEFAULT
- **问题**：SQLite 的 CURRENT_TIMESTAMP 虽是 UTC，但格式为空格秒（`2026-07-18 04:45:39`），与 UTC Z 格式不统一
- **最优雅处理**：建表**去掉 `DEFAULT CURRENT_TIMESTAMP`**，所有 INSERT 语句**显式传入 `get_utc_timestamp()`**（彻底统一格式；违背"禁止backward"？不——这是统一规范的必要改法，且与边界转换的"调用方零改动"哲学一致——因为 DEFAULT 是 SQL 侧非参数侧）

### 例外 2：`create_timestamp()`（毫秒整数，不走参数路径）

- **位置**：`storage.py`(3处)、`sse.py`、`steps/base.py`、`messages.py` 写入 `chat_messages.timestamp` / `chat_message_steps.step_json` / 步骤表
- **问题**：存的是整数毫秒，违反 TEXT 列亲和，与字符串字段混存
- **最优雅处理**：改这 5–6 处写入为 `get_utc_timestamp()`（不改 20 个调用方，只改产生字符串的源头）；前端时间工具函数参数类型已是 `Date | string | number`，天然兼容 ISO 字符串，**无需改前端**（格式改变已在 `StepContent.tsx`/`timeFormatters.ts` 容错范围内）

5. **新增公用函数登记 FUNCTIONS.md**：若有新增函数（本次无新增，`convert_to_utc` 已存在，不需登记）
6. **历史数据 ETL 迁移脚本**：将存量 4 种格式读 → `datetime.fromisoformat` 解析 → `convert_to_utc` 写回
