## 二、P0（致命）: LLM 400 Bad Request → Agent FAILED

### 2.1 现象描述

Session 2（id=14591644）在第9轮LLM调用时（前8轮均成功），LLM服务端返回HTTP 400 Bad Request。经过HTTP级重试3次（等待 2s/4s/8s，400不耗timeout）全部失败后，Agent直接置FAILED。该轮耗时~15秒（总session 126.81s含前8轮成功部分）。

### 2.2 全链路追踪

```
时间戳: 00:11:08~00:11:23（~15秒）

```
client_sdk.py:170  response.raise_for_status()
  → httpx.HTTPStatusError("400 Bad Request")
  → base_service.py:263 except Exception
    → _should_retry(e)=True（SystemErrorClassifier: 400→SERVER retryable）
    → HTTP级重试×3（等待 2s/4s/8s，400立即返回不耗时）
    → 全部失败→_create_stream_error_chunk(e)
    → StreamChunk{stream_error="服务器错误,请稍后重试或更换模型"}
  → call_llm_stream.py:110 chunk.stream_error→break
    → yield ("response", {"type": "error", "content": "LLM流式错误: 服务器错误,请稍后重试或更换模型"})
    → return
  → call_llm_with_fallback.py:180-184 for loop
    → yield item  【直接透传，未捕获】
    → return    【正常退出，未触发exception重试路径】
  → react_cycle.py:295 _dispatch_handler(llm_response)
    → _dispatch_handler:129 "error" in seen_types
    → set_failed(agent, error_msg)  【Agent置FAILED】
```

### 2.3 根因定位

`call_llm_with_fallback`（L2重试层）只catch了`FCFormatError`这个Python异常。但400错误以流式error响应（非异常）到达，两个错误通路并存——流式error绕过exception重试机制，直抵`set_failed`。

**违反原则**:
- **KISS-DIRECT**: error响应不走异常路径，exception走异常路径→两条error通路并存→混乱
- **SLAP**: `call_llm_with_fallback`是L2重试层，只负责exception、不负责response error→职责不完整

### 2.4 是不是退化？Git历史分析

**结论**: 不是传统退化（无人删正确代码），而是**2026-06-28一次半截修正**——改了错误类型忘了改重试层。

#### 2.4.1 关键时间线

`llm_stream.py` 的 3 个关键节点：

| 时间 | commit | 变更 | 流式error行为 |
|------|--------|------|-------------|
| 2026-06-25 小欧 | `099c662ec` | 创建 `call_llm_with_fallback` + `call_llm_stream`（从`llm_caller`更名） | `_yield_error_response` 返回 `type:"answer"` |
| 2026-06-28 小欧 | `af2ecc755` | `_yield_error_response` 从 `type:"answer"` → `type:"error"` | 语义修正：error不再是answer |
| **现在** | — | `call_llm_with_fallback` 仍只catch `FCFormatError`异常 | 流式error `type:"error"` → 直抵 `set_failed` |

#### 2.4.2 退化原因追溯

**2026-06-25（`call_llm_with_fallback` 创建时）**：
- 流式error返回 `type:"answer"`（当时的设计缺陷）
- `call_llm_with_fallback` 只有 `except FCFormatError` 异常捕获
- 副作用：error被当作answer，但agent**不会FAILED**，可继续循环

**2026-06-28（`type:"answer" → "error"` 修正时）**：
- 作者小欧只改了`_yield_error_response`的返回值类型（第1处）
- 但**忘了同步更新**`call_llm_with_fallback`去拦截`type:"error"`响应（第2处）
- 从此：任何流式error → `type:"error"` → agent直死

#### 2.4.3 为什么你记得"之前是对的"

因为 **2026-06-28之前**，error走 `type:"answer"`：
- `_dispatch_handler` 走 `handle_answer` 分支
- error内容被当作LLM的普通回答写入history
- agent继续循环，下轮LLM可能成功
- 这虽然是语义错误（把error当answer），但**agent不会崩溃**

**2026-06-28之后**，error走 `type:"error"`：
- `_dispatch_handler` 看到 "error" → `set_failed`
- agent立即FAILED，无重试机会

**本质**: 不是退化（没人删正确的代码），而是**修正只做了一半**。

#### 2.4.4 正确修正应该是什么

修正时应同步修改**两处**：
1. ✅ `_yield_error_response` 返回 `type:"error"`（已完成）
2. ❌ `call_llm_with_fallback` 在yield前检查 `type:"error"`，转 `FCFormatError` 触发L2重试（**漏了**）

我提的修复方案正是补上第2处。

### 2.5 全链路错误路径地毯式扫描（无一遗漏）

为了确保修复没有漏网之鱼，对 `client_sdk.py:170` → `base_service.py:request_stream` → `call_llm_stream.py` → `call_llm_with_fallback.py` 整条链路的**每一种异常**做了遍历。

#### 2.5.1 完整异常分类表

```
Layer           Exception                         → SystemErrorClassifier  → L1结果    → 最终产出           → 当前命运
──              ─────────                         ──────────────────────  ────────    ──────────           ────────
A. HTTP请求时    httpx.ConnectError                → 未特殊匹配 → SERVER   retryable  → error chunk         → type:"error" → FAILED ❌
(client_sdk)    httpx.TimeoutException             → 未特殊匹配 → SERVER   retryable  → error chunk         → type:"error" → FAILED ❌
                httpx.HTTPStatusError(4xx/5xx)     → 400/401/...→ SERVER  retryable  → error chunk         → type:"error" → FAILED ❌
                httpx.NetworkError                 → 未特殊匹配 → SERVER   retryable  → error chunk         → type:"error" → FAILED ❌
                httpx.ProxyError                   → 未特殊匹配 → SERVER   retryable  → error chunk         → type:"error" → FAILED ❌
                httpx.PoolTimeout                  → 未特殊匹配 → SERVER   retryable  → error chunk         → type:"error" → FAILED ❌

B. SSE流式中   httpx.StreamError(断连)             → 未特殊匹配 → SERVER   retryable  → error chunk         → type:"error" → FAILED ❌
                _parse_sse_data异常               → 内部catch→返回None    [不传播]   → 跳过chunk            → 不影响 ✅

C. 流结束后    FCFormatError(tool_calls全解析失败) → UNKNOWN   NOT retry → re-raise  → except FCFormatError → L2 FC重试 ✅
(post-loop)    _json.JSONDecodeError              → 内部try_fix            [不传播]  → 修复或failed_parses  → 不影响 ✅
                其他意外异常                       → 任何      —          —          → error chunk          → type:"error" → FAILED ❌

D. call_llm    CancelledError                    → 不分类    —          —          → re-raise             → 调用方处理 ✅
_stream层      Exception(来自request_stream)      → 内部转error response    —          → type:"error"         → FAILED ❌
```

#### 2.5.2 关键结论

**红色 ❌ 行（共10种）** 全部以统一形态到达 `call_llm_with_fallback` 的yield点：
```
("response", {"type": "error", "content": "LLM流式错误: ..."})
```

**修复覆盖**：在 FC 重试循环内的 yield 前检查这个统一形态 → 转 `FCFormatError` → 触发 L2 重试。**10种异常一网打尽，无漏网之鱼。**

**绿色 ✅ 行（共4种）** 已正确处理，不受修复影响：
- `FCFormatError` → 异常路径已正确处理（L2重试）
- `_parse_sse_data` 异常 → 内部catch，不传播
- `_json.JSONDecodeError` → 内部try_fix，不传播
- `CancelledError` → re-raise，调用方处理

#### 2.5.3 为什么不需要区分子类型

因为任何异常在 L1 重试耗尽后都坍缩为同一个形态——`StreamChunk{stream_error=...}` → `("response", {"type": "error", ...})`。在 `call_llm_with_fallback` 的 FC 重试循环内，只要看到 `type:"error"`，就代表"当前FC调用没拿到有效响应"，都应该重试——这正是 `FCFormatError` 异常的逻辑语义。

> **形态说明（精确度修正）**：上句"统一形态"指 **Layers A/B/D**（HTTP/SSE/流式异常），其经 L1 重试耗尽后变成 `type:"error"` **响应**形态，由 2.6 拦截。而 **Layer C** 的 `FCFormatError`（tool_calls 全解析失败）本身是**异常**形态，不经 L1 重试、直接 `raise` 穿透，由 `call_llm_with_fallback` 既有的 `except FCFormatError` 捕获。两者殊途同归→都走 L2 重试，故"10种一网打尽"结论成立。

### 2.7 3轮复核结论

| 纬度 | 结论 |
|------|------|
| **正确性** | ✅ error响应在`yield`前拦截，不污染下游；FCFormatError触发L2重试，逻辑自洽 |
| **不退化** | ✅ `stream_error` chunk是`request_stream`返回的第一个（也是唯一）chunk，之前无content chunk流出，无残留状态 |
| **零副作用** | ✅ LLM调用期间不写conversation_history，重试前后history状态一致；FC降级兜底不变 |
| **极端场景** | ✅ 流中段断连（先有content chunk后error）→ history未commit，重试后新内容覆盖，前端有短暂闪现但不影响后端语义 |
| **重试叠加代价（已知权衡·非缺陷）** | ⚠️ `error_classifier.py:82` 确认 400→SERVER→retryable，L1（`base_service` L168 `while retry_count<=3`）对 400 实际发 **4 次 HTTP**（1初+3重试，2/4/8s）。2.6 让 error 转 L2 重试后：①**永久 400**（参数错）最坏 `2(L2)×4(L1)+4(Text降级L1)=12次HTTP/~42s`，但最终经 FC 降级→FAILED 终止，**无死循环、无崩溃**；②**瞬时 400**（真实P0场景）多 1 次 L2 即恢复→正修复收益。代价有界、终态正确，属设计权衡，非缺陷 |

### 2.8 修复方案片段二：降级关闭分支 `last_error=None` 兜底（[2.6](#26-修复方案片段一fc重试循环内拦截-typeerror28互文关系见末注) 互为互补，同属 P0 完整修复）

> **互文关系**：本片段（2.8）与 [2.6](#26-修复方案片段一fc重试循环内拦截-typeerror28互文关系见末注) 是两个**互补片段**，**不是替代关系**，**必须同时实施**。全部改动在 `call_llm_with_fallback` 这一个函数：
> - **2.6** → 重试循环内（L180-189）：拦截 `type:"error"` 转 `FCFormatError`，触发 L2 重试
> - **2.8** → 降级关闭 else 分支（L200-201）：`last_error=None` 兜底，防 AttributeError 崩溃
>
> 缺 2.6：流式 error 直抵 `set_failed`，agent 死。缺 2.8：`FC_MAX_RETRIES=0` 时崩溃。**缺一则不完整。**

本缺陷虽默认 `FC_MAX_RETRIES=2`（`constants.py:55`）不触发，但属逻辑漏洞，须一并堵死。

#### 2.8.1 触发条件与现象

```python
# call_llm_with_fallback 原代码结构
last_error = None
for attempt in range(FC_MAX_RETRIES):        # FC_MAX_RETRIES=0 → for不执行
    try:
        ...
    except FCFormatError as e:
        last_error = e                        # 永不执行 → last_error 恒为 None
        ...

if FC_FALLBACK_ENABLED:
    ...                                       # 降级分支（不触碰 last_error）
else:
    yield _yield_error_response(_format_fc_error(last_error), agent)
    #                                        ↑ last_error=None → _format_fc_error(None)
    #                                          → f"解析失败: {None.message}" → AttributeError 崩溃
```

- **触发组合**：`FC_MAX_RETRIES=0` **且** `FC_FALLBACK_ENABLED=False`（降级通道也关）
- **崩溃点**：`_format_fc_error(None)` → `None.message` → `AttributeError`
- **本质**：`last_error` 在 for 循环未执行时保持初始值 `None`，降级关闭分支未做 None 兜底。

#### 2.8.2 根因定位

`call_llm_with_fallback` 的 `else`（降级关闭）分支假定 `last_error` 一定被赋值，但 `last_error` 仅在 `for` 循环的 `except FCFormatError` 内赋值。`FC_MAX_RETRIES=0` 时 for 不执行，`last_error` 保持 `None`，直接格式化即崩。

**违反原则**：
- **KISS-DIRECT**：分支对 `last_error` 取值前提假设不完整（未覆盖"从未进入循环"的边界）
- **YAGNI 反例（健壮性缺口）**：边界未兜底，导致可配置参数组合触发崩溃

#### 2.8.3 设计提案（经3轮复核，待审核实施后）

```python
    else:
        # FC降级关闭: 以FC错误响应终止任务。
        # last_error为None仅当FC_MAX_RETRIES=0(从未发起FC调用且未捕获FCFormatError),
        # 此时直接_format_fc_error(None)会AttributeError崩溃, 故显式兜底为可读错误。
        if last_error is None:
            error_msg = f"FC模式不可用: FC_MAX_RETRIES={FC_MAX_RETRIES}且降级通道关闭, 任务无法执行"
        else:
            error_msg = _format_fc_error(last_error)
        yield _yield_error_response(error_msg, agent)
```

**设计点**：在降级关闭分支内对 `last_error` 做 None 兜底——为 `None` 时生成可读配置错误并终止（→ `set_failed`），非 `None` 时走原 `_format_fc_error` 路径。**未触碰 `_format_fc_error` 本身**（保持 YAGNI，不引入冗余防御代码）。代码尚未改动，待审核通过后再实施。

#### 2.8.4 3轮复核结论

| 纬度 | 结论 |
|------|------|
| **正确性** | ✅ `last_error=None` 边界显式兜底，不再 `AttributeError`；非 None 时行为与原代码逐字一致 |
| **不退化** | ✅ 默认 `FC_MAX_RETRIES=2` 路径：`for` 至少执行一次，`last_error` 必被赋值或 `return`，`else` 分支逻辑无变化 |
| **零副作用** | ✅ 仅影响"降级关闭+重试配0"的极端组合；`FC_FALLBACK_ENABLED=True` 分支、`_format_fc_error` 函数均未改动 |
| **与P0协同** | ✅ P0 修复让 error 响应转 `FCFormatError` 并赋值 `last_error`，本修复保证即使配0也能安全终止，互不冲突 |
| **10原则** | ✅ SRP/DRY/KISS-DIRECT/SLAP/YAGNI/禁止backward 全满足；无继承/接口扩展场景，OCP/LSP/ISP/复用优先不适用 |

**结论**：本修复是纯粹**增强**（堵死崩溃边界），无功能退化，与 P0 修复协同无冲突。

> **互文关系**：本片段（2.6）只修 `call_llm_with_fallback` 的 **FC 重试循环（L180-189）**，负责拦截流式 error 走 L2 重试。**降级关闭分支（L200-201）的 `last_error=None` 崩溃**必须由 [2.8](#28-修复方案片段二降级关闭分支none兜底26互文关系见末注) 补齐。两片段在同一函数的不同分支、修不同问题，**缺一则 P0 修复不完整**。

## 三、P1（严重）: Shell命令捆绑超时 + ping 127.0.0.1死锁

### 3.1 现象描述

Session 1和3中，LLM发出`cd /d/g/... && powerShell -Command "Get-ChildItem ..."`捆绑命令，运行120s后超时（注意：这120s恰好等于外层`asyncio.wait_for`的首次超时，而非内层）。随后`ping 127.0.0.1 -n 3`（应在3秒内完成）也超时——说明前一个命令的超时**污染了shell进程状态**，连带拖垮后续本应秒级完成的命令。

### 3.2 追踪分析（实测，非凭文档空想）

**双层timeout的真实来源（已逐行核对）**:

- **外层**：`tool_retry_engine._execute_tool_once`（L64-66）把同步`shell()`包进`asyncio.to_thread`，再套`asyncio.wait_for(tool(**params), timeout=timeout)`。该`timeout`来自`_execute_with_retry`（L271-277）：`timeout = min(base_timeout * (attempt+1), 300)`，其中`base_timeout = TOOL_TIMEOUTS["shell"] = 120`（`tool_constants.py`）。**首次尝试=120s，重试递增（240/300）**。
- **内层**：`shell()`的`timeout`参数（`execute_shell_command.py:328`默认60），经`validate_timeout(timeout,"shell")`校验范围**1~600**（`timeout_validator.py:13`），直接透传给`PersistentShell.exec(cmd, timeout)`→`_exec`里的`_poll_for_file(paths.code, timeout=timeout)`。

> **关键纠正（原分析两处误判）**：
> 1. 原文档称"内层timeout=120（固定）"错误——内层timeout是LLM的`timeout`参数（默认60，上限600），120属于外层`TOOL_TIMEOUTS["shell"]`，二者不是同一值。
> 2. 原文档称"`_get_retry_config`对`TOOL_TIMEOUTS`标量调`.get`会崩"错误——`_get_retry_config`（`tool_retry_engine.py:92-100`）用的是`TOOL_RETRY_CONFIG.get(action, {})`（嵌套字典）再`config.get(...)`，且`TOOL_TIMEOUTS`本身是扁平字典（L99 `TOOL_TIMEOUTS.get(action, TOOL_TIMEOUTS["default"])`），**安全不崩**。

**Shell引擎已有的保护机制**（仅在内层poll超时后生效）:
```python
# shell_engine.py:256-259 _exec
if not _poll_for_file(paths.code, timeout):   # 内层timeout（LLM的timeout参数）到期
    self._kill_tree()   # taskkill /T /F /PID
    self._close()       # proc.kill + _proc=None, _alive=False
    return _ERROR_TIMEOUT
```

**真正的死锁触发条件（实测推导）**:
- 当LLM传入 `timeout > 120`（外层首次超时）时（上限600，合法），**外层`asyncio.wait_for`先到120s**，`to_thread`被取消→抛`asyncio.TimeoutError`。但`to_thread`取消只中止"await"，**OS线程内的`_exec`仍在`_poll_for_file`阻塞等待（要等`timeout`秒，如300s）**，其后的`_kill_tree()`+`_close()`**永远走不到**。
- 结果：`PersistentShell`的powershell进程（`_proc`）继续运行那条已被上层放弃的命令；`_alive=True`、`_proc`未清理。`get_instance()`/`_ensure_alive()`（`shell_engine.py:203-206`）看到`_alive=True`且`poll() is None`→**复用这个僵尸实例**。
- 后续`ping 127.0.0.1`（默认timeout=60）把命令写进卡死/僵尸的shell stdin→也"超时"→与日志现象完全吻合。
- **默认`timeout=60`时**：内层60 < 外层120，内层先触发`_kill_tree`+`_close`，**不会死锁**。故原文档"120/120同一时刻必然死锁"前提错误——死锁仅在 `timeout>120` 这一合法范围内发生。

### 3.3 违反原则

- **SRP**：`PersistentShell`作为有状态的持久shell托管者，其进程生命周期（超时清理）被外层`asyncio.wait_for`的取消机制打断且无人兜底——状态一致性的责任既不在重试引擎（它只管抛异常）也不在shell引擎（它的清理逻辑因外层先取消而执行不到），出现"责任真空"。

### 3.4 修复方案（纠正原方案A的不完整）

**原方案A（仅把`TOOL_TIMEOUTS["shell"]` 120→180）是不充分的**：LLM仍可传`timeout`至600，只要`timeout>180`，外层仍会先于内层取消，死锁依旧。常量bump治标不治本。

**推荐方案（KISS-DIRECT + SRP，落点在重试引擎的超时计算）**：**让外层`wait_for`超时永远晚于内层`timeout`+清理缓冲**，从而内层`_exec`的`_kill_tree()`+`_close()`**必然先跑完**、把进程清理干净，外层只是"接住"已清理好的超时结果——`to_thread`线程无法被强杀，但只要外层不抢先取消，孤儿进程就不会产生。

```python
# tool_retry_engine.py _execute_with_retry（已实装）
# 原: timeout = min(base_timeout * (attempt + 1), 300)
# 改: 外层必须 > 内层LLM timeout + 30s缓冲, cap 630, isinstance防非timeout工具干扰
timeout = min(base_timeout * (attempt + 1), 300)
inner = params.get("timeout")
if isinstance(inner, int) and inner > 0:
    needed = inner + 30
    if needed > timeout:
        timeout = min(needed, 630)
```

```python
# tool_retry_engine.py try_once（同公式, 已实装）
timeout = min(base_timeout, 300)
inner = params_or_error.get("timeout")
if isinstance(inner, int) and inner > 0:
    needed = inner + 30
    if needed > timeout:
        timeout = min(needed, 630)
```

> **关键更正（v1.3）**：上一版(v1.2)写的"在`shell()`内 try/except 捕取消并`engine.close()`"**落点不准确**——取消信号发生在`_execute_tool_once`的`await asyncio.wait_for(...)`（L65-66）那一层，根本进不到`shell()`函数内部。正确且最省事的修法是**从超时计算根上消除"外层抢先取消"**：外层恒大于内层+缓冲，孤儿进程从源头不产生，连`close()`兜底都不需要。

**为什么落重试引擎而非shell工具**：超时值(`timeout`)本就是重试引擎在`_execute_with_retry`/`_execute_tool_once`里算好再传给`wait_for`的；只需让这一处计算"看一眼"LLM给的`timeout`参数即可。用`params.get("timeout")` + `isinstance` 守卫，只有真正有 timeout 参数的工具才会触发，无该参数的工具行为**零变化**（SRP：超时策略归重试引擎；进程清理仍归shell引擎，只是现在总能跑到）。

### 3.5 3轮复核结论

| 纬度 | 结论 |
|------|------|
| **正确性（前提已订正）** | ✅ 死锁根因是"外层取消先于内层清理"致进程孤儿化，而非"120/120同时到期"；修复从超时计算消除"外层抢先取消"（外层恒 > 内层timeout+缓冲），孤儿进程从源头不产生 |

## 四、P2（设计约束/局限性）: shell工具exit_code判定欠灵活

### 4.1 现象描述

LLM通过shell工具运行`config_validator.py`脚本（LLM在执行任务中临时生成，用于校验配置文件格式，返回1表示"配置有问题"），shell工具将exit_code=1判定为"命令执行失败"。

### 4.2 根因定位

`execute_shell_command.py:475`: `if returncode == 0:` → success分支  
`execute_shell_command.py:505-514`: `return build_error(...)` → 所有非零exit_code统一error

`config_validator` **不是系统的代码**——它不是代码库里的文件，也不是测试框架的代码。它是LLM**运行时实时生成**的Python脚本（`test_e2e_p1_05_config_manage.py:34` 要求"生成一个Python脚本config_validator.py"）。生成后LLM通过shell工具执行它做配置校验，它用 `exit 1` 表示"配置有问题"。

**这暴露了一个通用的shell工具设计约束**：`if returncode == 0: success else error` 对大多数命令是正确的（权限不足→1、语法错误→1），但有些命令用非零退出码表达**业务结果**（而非执行失败）：
- `grep` 无匹配 → 1、`diff` 文件差异 → 1、`findstr` 无匹配 → 1（shell_schema.py 第29行已注明"正常行为非错误"）
- LLM自生成脚本如 `config_validator.py` → 1 表示"配置有问题"
- 任何习惯用非零退出码传业务结论的命令行工具

**分类纠正**：这不是"系统坏代码"——`if returncode == 0` 作为简单通用的退出码判断逻辑是正确且一致的。它是一个**设计约束/局限性**：简洁性与灵活性的取舍。

**设计取舍**：
- 当前代码（`if returncode == 0:`）符合KISS-DIRECT（简单直接），覆盖99%的常见场景
- 但遇到"非零退出码=业务结果"的特殊命令时，无法区分"执行失败"和"正常但非零"——这是个已知局限而非代码错误

### 4.3 修复方案（待审核·尚未实施）

**需要改什么代码？**
- ✅ **系统代码**：`execute_shell_command.py`（退出码判断条件）+ `shell_schema.py`（新增参数）。这是**通用增强**，不是为了config_validator一个脚本。
- ❌ **测试代码不变**：`test_e2e_p1_05_config_manage.py` 不需改——修复后LLM运行时自动看见新参数。
- ❌ **config_validator.py**：不是代码库的文件（LLM运行时生成），不存在于仓库，无文件可改。

**修复内容**：给shell工具schema增加 `success_codes` 参数，LLM可在知道命令使用非零退出码表达业务结果时显式传入。**追加式语义**：0始终成功（无需列出），参数只追加额外的非零码。

**设计要点**：
- 默认 `None`→`or []` 保底：不传参时，行为**逐字不变**（只认0）
