## 一、问题现象

P1-04 测试用例 `test_e2e_p1_04_data_archive.py` 运行中，E2E 第 5 次 LLM 调用（LLM#5）全部返回 **HTTP 400 Bad Request** 错误，共 12 次重复（app log 行号 3247/3249/3251、3255/3257/3259、3264/3266/3268 各 4 次 × 3 块）。最终 test 断言失败（`verify_response_quality` 返回"回复为空"）。

---

## 二、根因分析

根因分三层：

### 2.1 直接原因：推理-only 注入产生非法 tool 消息（代码 bug）

**触发路径**：`backend/app/services/agent/handlers/answer_handler.py:261-269`

第 4 次 LLM 调用（LLM#4）返回空 content + 推理（reasoning），推理内容为：
```
文件太大，完全量太大，用分步方式统计，再分批次处理

<tool_call>
<function=shell>
<parameter=command>python3 -c "..." 2>&1 | Select-Object -First 100</parameter>
<parameter=timeout>600</parameter>
</function>
</tool_call>
```
——这是一个**完整的 `<tool_call>` XML 格式工具调用**，但 LLM 降级用了旧格式，未生成原生 FC JSON tool_calls。

现有代码未提取此 XML 工具调用，而是走虚构 FC 路径：
- `add_assistant_message("")` 写入空内容 assistant 消息
- `add_observation(reasoning, {"tool_call_id":"", "tool_calls":[], "llm_content":reasoning})` 伪造 FC 格式

**注入方法** `_append_observation`（`message_builder.py:146-151`）在 `tool_call_id=""` + `tool_calls=[]` 时依次产生：
- `add_assistant_tool_call([], content=reasoning)` → `{"role":"assistant","content":"<推理>","tool_calls":[]}`
- `add_tool_result(tool_call_id="", ...)` → **`{"role":"tool","content":"<推理>","tool_call_id":""}`**

三条畸形消息：
- **M1** `{"role":"assistant","content":""}` — 空内容、无 tool_calls
- **M2** `{"role":"assistant","content":"<推理>","tool_calls":[]}` — 空 tool_calls 数组
- **M3** `{"role":"tool","content":"<推理>","tool_call_id":""}` — **空 tool_call_id（最确定的协议违反）**

M3 的 `tool_call_id=""` 违反 OpenAI 协议（必须为非空且对应某 assistant tool_call.id），sensenova 返回 400。

**序列化行为**（`fc_message_types.py:175-177`）：`model_dump(exclude_none=True)` 只排除 `None`，空串 `""` 和空数组 `[]` **不是 None**，被保留。

**清洗漏洞**（`message_builder.py:376-380`）：`_trim_fc_pairs` 的 `elif not msg.get("tool_call_id"): result.append(msg)` 特意保留空 id 的 tool 消息，未清洗。

**这三条消息只来自推理-only 路径**。正常 FC 路径（`action_handler.py:366-369`）使用 LLM 返回的真实 tool_call id，不会产生空 id。

### 2.2 放大器：error_classifier 将 400 误判可重试

`error_classifier.py:80-83` 将 `400/401/403` 映射为 `SystemErrorCategory.SERVER`（`is_retryable=True`），导致 12 次完全相同的 400 重试。

HTTP 分类原则：
- **4xx** = 客户端错（请求畸形/鉴权/权限），**不应重试**
  - 400/401/403：确定性失败，重发必再失败
  - **429(限流)是唯一例外 4xx**：瞬态，**可重试**
- **5xx** = 服务端错，**可重试**

### 2.3 盲区：client_sdk 丢弃 400 响应体

`client_sdk.py:171` `response.raise_for_status()` 抛的 `HTTPStatusError` 不含响应体，sensenova 返回的具体错误字段从未被记录。

## 三、修复方案

### 3.1 Fix 0 — 核心：XML tool_call 提取 + 拦截执行（新增）

**设计意图**：当 LLM 降级使用旧 `<tool_call>` XML 格式时（FC 原生 tool_calls 为空），从 `reasoning`（FC 退化）或 `content`（Text fallback）中提取 XML 结构，恢复为合法 tool_call 执行，避免走向注入路径。

#### 3.1.1 `text_utils.py` — 新增 `extract_tool_call_xml(text)` + 重构 `_format_xml_tool_block`

新增公共函数（正则唯一来源，DRY），重构 `_format_xml_tool_block` 调用它。

```python
def extract_tool_call_xml(text: str) -> Optional[Dict[str, Any]]:
    """从文本中提取 <tool_call> XML 格式的工具调用

    解析 <tool_call><function=name><parameter=k>v</parameter></function></tool_call>
    返回 {"tool_name": str, "tool_params": Dict[str, str]}

    本函数是此 XML schema 的唯一解析源（DRY）。
    _format_xml_tool_block 调用本函数，正则定义不重复。
    """
    block_m = re.search(r'<tool_call>.*?</tool_call>', text, re.DOTALL)
    if not block_m:
        return None
    block = block_m.group(0)
    func_m = re.search(r'<function=([^>\n]+)>', block)
    if not func_m:
        return None
    tool_name = func_m.group(1)
    tool_params = {}
    for pm in re.finditer(r'<parameter=([^>\n]+)>\n?(.*?)\n?</parameter>', block, re.DOTALL):
        tool_params[pm.group(1)] = pm.group(2).strip()
    return {"tool_name": tool_name, "tool_params": tool_params}
```

### 3.5 10 大原则合规核验

设计经三遍复核，对照 AGENTS.md 10 大编码原则逐项核验：

| 原则 | 判定 | 依据 |
|------|------|------|
| SRP | ✅ | 提取(`extract_tool_call_xml`)与格式化(`format_tool_call_markup`)职责分离 |
| DRY | ✅(需补一步) | 重构 `_format_xml_tool_block` 改为调用 `extract_tool_call_xml`，正则只存一处 |
| KISS-DIRECT | ✅ | 一个 `re.search`+`re.finditer` 直接解析，无工厂/注册表/中间层 |
| SLAP | ✅ | 拦截点只做"判空→提取→构造"，与周边 type 判定同层级 |
| YAGNI | ✅ | 无多余接口；多 tool_call/去 XML 清洗等留待需要再加 |
| 禁止backward | ✅ | 提取成功走 action；失败自然落入原 answer 路径，无兼容壳 |
| OCP | ✅ | `call_llm_stream` 只加分支，FC 原生路径(:179-186)零改动 |
| LSP | N/A | 无继承体系 |
| ISP | ✅ | `extract_tool_call_xml(text)->Optional[dict]` 单一窄接口 |
| 复用优先 | ✅ | 无相似函数可复用（`is_xml_tool_call`/`convert_xml_tool_call_to_json` 处理另一种 schema 且零调用）；新增须登记 FUNCTIONS.md |

**复用核查结论**：`xml_adapter.py` 的 `is_xml_tool_call`/`convert_xml_tool_call_to_json` 处理 LongCat 风格 `<XXX_tool_call>` schema，对 LLM#4 的 `<tool_call><function=…>` 实测返回 False/None（零调用、零配置），属死代码/备用代码，本修复**不复用**也不扩张，单列清理项（见六）。

### 5.4 实现期验证点（来自设计复核）

1. **`_format_xml_tool_block` 复用改造**：重构为调用 `extract_tool_call_xml` 后，须保持原 `no-function→"[工具调用] unknown"` 兜底行为不变（仅显示层，无风险）。单测对比重构前后输出一致。
2. **tool_params 字符串 coercion**：提取的 `tool_params` 值为字符串（如 `timeout:"600"`），依赖工具层 Pydantic schema 做类型 coercion。FC 模式同样走此路径，预期可 coerce；E2E 重点验证 shell `timeout` 类型正确（int）。
3. **Text fallback 原始 XML 进 content**：Text 降级时 `full_content` 含原始 `<tool_call>` 文本会进 `content` 字段，按 YAGNI 暂保留，E2E 观察是否需清洗。
4. **Fix 0 防误提取守卫**：构造"推理中讨论 `<tool_call>` 语法但工具名不存在"的输入（FC 模式），确认不被当作工具执行、回落 answer 路径（无退化）；构造"工具名存在"的输入，确认正常执行。构造异常工具列表（含 None/非 dict 条目），确认守卫不崩溃。
