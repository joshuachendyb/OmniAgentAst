## 一、背景与问题定性

经全项目审计（复盘文档 v1.9 纠察），系统"内容/长度上限"现状：

1. **constants.py 第4节（78~95行）11 个常量全死**：`DEFAULT_MAX_OUTPUT_CHARS(5000)`/`DEFAULT_MAX_FILE_CHARS(8000)`/`DEFAULT_MAX_DOC_CHARS(10000)`/`DATA_TOO_LARGE_THRESHOLD(10000)`/`DEFAULT_MAX_CLIPBOARD_CHARS(5000)`/`DEFAULT_MAX_ENV_VALUE_CHARS(1000)`/`DEFAULT_MAX_DATA_CHARS(1000000)`/`DEFAULT_MAX_LIST_ITEMS(10000)`/`MAX_CHUNK_COUNT(5000)`/`MAX_EMPTY_CONTENT_COUNT(100)`/`LOG_PREVIEW_CHARS(500)` —— 全项目零 import 零引用。仅 `MAX_CONTEXT_CHARS(200000)`/`TEMP_HISTORY_CHAR_LIMIT(50000)` 存活。
2. **实际限制由三类承载**：
   - 机器二（observation 统一截断）：`tool_constants.py` 的 `OBS_*` 活常量（10000/500/100）
   - 机器一（工具层各自截断）：各 tool 文件内**自建硬编码**（shell `MAX_OUTPUT=30000`、fetchpage `max_tokens=8000`、search_web `300`、read_xlsx `max_rows=10000`、http_request `10MB`、download `100MB`）
   - 入参校验：Pydantic schema（writetext `max_length=10000`）
3. **同一概念多定义且值打架**：文件字符上限至少 3 处 —— `DEFAULT_MAX_FILE_CHARS=8000`、`file_schema max_length=10000`、`OBS_MAX_STRING_LENGTH=10000`，值不统一。
4. **成因**：早期 `constants.py` 第4节想做"统一输出/文件/文档字符上限"单一事实源，但实现时 observation 层另立 `OBS_*`（2026-07-04 小欧加进 tool_constants），工具层按业务各自硬编码（shell 输出、网页正文、搜索 snippet 上限差异大，套不上单一 8000），结果 `DEFAULT_MAX_*` 被架空成死代码，既没接上也没删。

**定性**：不是"没设限制"，而是"设了但散落硬编码 + 一堆永不被用的死常量 + 同一概念值不一致" —— 典型的**常量治理烂代码**。属基础性技术债，应先归一化。

## 二、治理目标与原则

1. **单一事实源（Single Source of Truth）**：所有长度/上限常量集中到 `tool_constants.py`（复用 `OBS_*` 已验证的成功模式），杜绝散落硬编码。
2. **归一化命名**：按用途分组前缀（`OBS_*`/`READ_*`/`SHELL_*`/`WEB_*`/`DOC_*`/`SEARCH_*`/`HTTP_*`/`DOWNLOAD_*`/`WRITE_*`）。
3. **值合理化**：逐 tool 审查当前值，偏大/冗余的一并调整（见第四章），不照搬原值。
4. **清理死常量**：删除 `constants.py` 第4节未启用常量（零引用，删之无运行时风险）。
5. **零行为退化**：迁移后各 tool 实际行为不变，或仅按"值合理化"预期微调（须在回归中确认）。

## 三、目标常量体系（tool_constants.py 单一事实源）

> **常量分级（老陈 2026-07-15 裁定）**：系统有两个常量文件——`constants.py`(系统级) 与 `tool_constants.py`(tool级)。
> `OBS_*` 系列逻辑上属**系统级**(observation 统一截断层, 归 Agent 系统), 但因与 tool 输出耦合极紧, 历史置于 `tool_constants.py`; 裁定:**不移位, 在 `tool_constants.py` 中标注为【系统级常量】**, 与真正的【tool 级】常量(SHELL_*/WEB_*/XLSX_* 等)区分。
> 故 `tool_constants.py` 内分两区: 【系统级】OBS_*(A/B组) 与 【tool 级】各工具上限(C组)。
> **【tool 级】常量(与 tool 紧密相关的)全部集中到 `tool_constants.py` 的【tool 级】区**, 便于查看对比检查; 且**每一个常量必须注释清楚使用对象**(引用它的文件/工具路径), 落实可追溯。

| 常量 | 值 | 用途 |

## 七、实施步骤

1. `tool_constants.py` 新增 B/C 组统一常量（含值合理化），保留 A 组与 `MAX_READ_SIZE`/`MAX_MEDIA_READ_SIZE`；并在文件内用分区注释明确区分：**【系统级】OBS_*(A/B组)** 与 **【tool 级】各工具上限(C组)**，落实老陈分级裁定。每个常量定义处必须加 `# 使用对象: <文件/工具>` 注释(如 `# 使用对象: execute_shell_command.py`)，确保可追溯。
2. 逐 tool 改引用（**每改一个立即跑该 tool 单测**，避免批量回归爆炸）。
3. `constants.py` 删除第4节死常量。
4. 全量 lint + typecheck + 全 tool 单测。

## 八、回归测试计划

- **单测**：shell（长输出头尾截断位置）、fetchpage（正文提取上限）、read_xlsx（行数上限）、search_web（snippet）、http_request（JSON 预览）、download（大小上限）、writetext（入参校验）逐工具验证。
- **E2E**：跑长 shell 输出、长网页抓取、大 xlsx 读取场景，确认 observation 截断位置符合新值且**不误伤**（内容完整性、LLM 续处理正常）。
- **重点验证 shell 30000→20000**：确认长日志场景尾部信息丢失不影响 agent 决策（头尾各半策略下仅中部丢失，风险低）。

## 九、风险与回滚

| 风险 | 等级 | 缓解 |
|------|------|------|
| shell 输出变短(30000→20000) 丢中部 | 低 | 头尾各半策略, 仅中部丢失; E2E 回归确认 |
| fetchpage 提取降为10000 | 低 | 本就被 OBS 二次截10000, 行为不变 |
| 改名遗漏导致 AttributeError | 中 | 逐 tool 改+单测, 全量 typecheck 拦截 |
| 删除死常量误伤活引用 | 极低 | 已审计零引用, 删除后全量 import 校验 |

回滚：git 按文件回退（本方案仅改常量定义与引用，无业务逻辑变更，回退成本低）。

## 十、排期建议

- 本治理为**独立重构项**，与 L1(final 质量护栏)解耦：L1 用独立常量 `EXTERNAL_THRESHOLD=2500`（final 答复专属门限，不复用死常量），**不依赖本治理**。
- 建议排期：**先于**后续任何涉及"长度/截断"的新功能；可与 L1 并行推进（互不阻塞），但归一化作为基础件优先收口。
- 执行方式：按第七章分步，每步配单测，禁止一次性大改。

## 十一、常量矛盾冲突分析与统一处理

> 老陈 2026-07-15 补充：常量之间有矛盾冲突的须一并分析, 做出合理处理或统一, 总之常量之间不能矛盾。

### 11.1 冲突清单与分类

| 冲突 | 涉及常量(当前值/位置) | 类型 | 处理 |
|------|----------------------|------|------|
| 文件字符上限不一致 | `DEFAULT_MAX_FILE_CHARS=8000`(死) / writetext `max_length=10000` / `OBS=10000` | **真矛盾(同概念值不一)** | 删 8000 死常量, 统一 10000(写/OBS 一致) |
| 项目规则注入上限 | `project_context MAX_CHARS=8000`(硬编码) vs OBS/文件=10000 | **真矛盾** | 迁系统级 `PROJECT_CONTEXT_MAX_CHARS=10000`, 统一 |
| 网页提取 vs observation | fetchpage 32000字符 vs `OBS=10000` | **真矛盾(冗余)** | `WEB_FETCH_MAX_CHARS=10000` 对齐 OBS |
| 数据过大量级 | `DATA_TOO_LARGE_THRESHOLD=10000` vs `DEFAULT_MAX_DATA_CHARS=1000000`(均死) | **真矛盾(同概念量级差100倍)** | 删死常量 |
| 输出 vs 文件/文档 | `DEFAULT_MAX_OUTPUT_CHARS=5000`(死) vs FILE/DOC=10000(死) | **潜在矛盾** | 删死常量 |
| 搜索 snippet 重复 | search_web `_SNIPPET_MAX_CHARS=300` 与 observation_formatter `SNIPPET_MAX=300` | **重复定义同值** | 合并 `SEARCH_SNIPPET_MAX_CHARS=300` |
| shell 字符 vs 字节 | execute_shell_command 30000字符 与 shell_engine 10MB字节 | **量纲/层级不同易误读** | 保留各自, 注释澄清(字符层 vs 引擎字节层) |
| xlsx 行 vs 条目 | read_xlsx 10000行 与 `OBS_MAX_DISPLAY_ITEMS=500` | **提取 vs 显示层级** | 保留各自, 注释澄清职责 |
| 读 vs 写 | `MAX_READ_SIZE=10MB` 与 writetext 10000字符 | **读全量 vs 写入参校验** | 保留各自, 注释澄清 |

### 11.2 处理原则

1. **真矛盾(同概念值不一)**：统一为一个值(取系统主流边界 10000), 删除冲突的死常量或冗余提取上限。
2. **重复定义同值**：合并为单一常量, 多处引用, 消除重复。
3. **量纲/层级不同**：非真矛盾, 但须注释澄清(字符 vs 字节、提取 vs 显示、读 vs 写), 避免后人误读为矛盾。

### 11.3 统一后常量值总表(无矛盾版)

| 概念 | 统一值 | 常量 | 级别 |
|------|--------|------|------|
| observation 字符串截断 | 10000 | `OBS_MAX_STRING_LENGTH` | 系统级(tool文件标注) |
| 文件内容/写入字符 | 10000 | `WRITE_TEXT_MAX_CHARS` / OBS(读后截断) | tool级/系统级 |
| 项目规则注入 | 10000 | `PROJECT_CONTEXT_MAX_CHARS`(原8000→10000) | 系统级 |
| 网页正文提取 | 10000 | `WEB_FETCH_MAX_CHARS`(原32000) | tool级 |
| 搜索 snippet | 300 | `SEARCH_SNIPPET_MAX_CHARS` | tool级 |
| shell 输出字符 | 20000 | `SHELL_OUTPUT_MAX_CHARS`(原30000) | tool级 |
| 文件读取字节 | 10MB | `FILE_READ_MAX_BYTES` | tool级 |
| xlsx 行 | 10000 | `XLSX_MAX_ROWS` | tool级 |
| 列表条目显示 | 500 | `OBS_MAX_DISPLAY_ITEMS` | 系统级 |
| 上下文字符 | 200000 | `MAX_CONTEXT_CHARS` | 系统级 |

> 统一后: 所有"内容/字符类"上限均为 10000 或其明确分数(300/500/20000), 无同概念值冲突; 字节类(10MB/100MB)独立量纲, 注释澄清。常量之间不再矛盾。
